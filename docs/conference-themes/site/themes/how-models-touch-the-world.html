Cross-theme synthesis

How models touch the world

A model does not meet a task directly. It sees through an interface, acts through an interface, receives feedback through an interface, and is constrained by an interface. The same underlying model can look weak, strong, safe, unsafe, precise, or confused depending on what the task surface lets it observe and change.

Problem

Capabilities are often evaluated as if the model directly touches the task, but the model only sees the part exposed by prompts, tools, files, schemas, sensors, memory, APIs, or action spaces.

Approaches

Redesign the observation surface, tool surface, action surface, feedback surface, memory surface, constraint surface, and verifier surface so the model can do the actual work.

Connecting read

This page follows evidence surfaces: after deciding what proves a claim, we ask what interface lets the model produce evidence in the first place.

CORE

An interface is a handle on the task

An interface is not a wrapper around capability. It decides which evidence reaches the model, which actions are possible, which costs are visible, and which mistakes can even happen.

The same model facing the same real problem can behave differently under different task surfaces. If a coding model only sees a natural-language request, it can write a generic answer. If it sees the repository, selected code, diagnostics, test output, and git diff, it can make a targeted edit. If it can run tests, it can observe consequences. If it cannot edit files, it remains a consultant. The capability did not live only inside the weights. It lived in the relation between model, context, tools, permissions, feedback, and verifier.

This is true across domains. A graph described in prose is not the same task as a graph exposed through an API. A medical note is not the same patient interface as notes plus labs, medication timeline, imaging, and visit sequence. A robot captioning an image is not acting through the same interface as a robot receiving proprioception and issuing action tokens. A legal assistant that sees a user request is not the same as one that sees source eligibility, jurisdiction, document constraints, and audit requirements. A security model answering a question is not the same as an agent with shell access, files, permissions, and a system boundary.

The first-principles move is to ask four questions. What can the model observe? What can it change? What feedback does it receive after acting? What constraints shape the action space? A weak interface can make a strong model look incapable because the needed evidence is hidden. A loose interface can make an unsafe model dangerous because it can act without enough checks. A narrow interface can make evaluation misleading because the model is never tested on the surface where deployment will happen.

First-principles line
An interface decides what parts of the world the model can observe, what parts it can change, and what kinds of mistakes become possible.

TOPIC 01

Observation: what reaches the model

A model cannot reason about evidence that the interface never exposes.

Observation is the first interface question. The model may see a prompt, a document, a screenshot, a code selection, a tool result, a patient timeline, a graph API, a memory summary, or a stream of sensor states. Each view changes the task. A graph in prose hides adjacency operations that a graph API can expose. A medical summary hides timing that a visit sequence can expose. A screenshot may show visual layout but not DOM structure. A retrieved passage may contain the answer but omit the source context that makes it trustworthy.

This is why retrieval and long-context work are interface work, not only scaling work. The question is not just how much text fits. It is whether the evidence that matters reaches the model at the moment it matters. ThinKV-style cache compression asks which hidden context can be discarded without losing rare clues. Long-context evaluations ask whether the model can use buried evidence. Retrieval pages ask whether the model gets the right information rather than more information.

Observation also decides what mistakes are even possible. If the model sees only captions, it can make caption-level mistakes but cannot verify pixel boundaries. If it sees only notes without labs, it can miss threshold-sensitive medical facts. If it sees only code without tests, it can miss runtime behavior. If it sees only a natural-language graph description, it may fail because the interface made graph operations awkward rather than because the model has no relational ability.

Interface principle
Before judging reasoning, ask whether the model was given the evidence needed for that reasoning in a form that preserves the task's real structure.
TOPIC 02

Tools: what the model can call

A tool changes the model from a text generator into a system that can inspect, compute, retrieve, execute, or verify.

Tools are not add-ons after intelligence. They reshape the task. A calculator changes arithmetic. A shell changes security evaluation. A browser changes web tasks. A code runner changes programming. A database changes data analysis. A graph API changes graph reasoning. A proof checker changes math. A search tool changes retrieval. The model's ability is partly the ability to decide when a tool call is worth the cost and how to use the result.

ParetoPO makes this explicit by optimizing tool-integrated agents across accuracy and tool-use efficiency. The point is not only to get the answer right. It is to know when a tool call is worth spending. CyberGym turns security tasks into tool-using environments, where the agent must inspect state, run commands, patch, and verify. Actions Speak Louder than Prompts shows that graph reasoning can look different depending on whether the model is prompted, writes code, or uses actions.

Tool interfaces also create new risks. The model can call the wrong tool, trust bad tool output, overuse expensive tools, leak information through tool arguments, or act with more permission than the task requires. A good tool interface exposes useful affordances while making cost, permissions, and verification visible.

Interface principle
A tool interface should expose actions that matter for the task while making cost, permission, output reliability, and verification part of the model's operating surface.
TOPIC 03

Actions: what the model can change

Answering, editing, clicking, running, proving, navigating, patching, and moving are different interfaces to the same world.

Many benchmarks ask for text when deployment asks for action. A model that writes a correct explanation may fail to edit the file. A model that describes a vulnerability may fail to exploit or patch it. A model that suggests a webpage design may fail to produce a rendered artifact. A model that explains a robot task may fail to generate a feasible trajectory. The action interface defines what the model is responsible for changing.

Gaia2 and WebDevJudge-style work make write actions and rendered artifacts part of evaluation. SandboxEscapeBench tests whether a shell-using agent can cross a protected boundary. Robotics and VLA papers expose low-level or latent actions rather than only captions. VERINA and THOR make code and proof steps into action units that can be checked. The common idea is that the action should match the claim: if the claim is "can build," the interface should let the model build; if the claim is "can control," it should let the model control.

The action interface also determines risk. A direct-answer interface is low agency but can still mislead. A shell interface has high agency and needs permissions. A robot action interface has physical consequences. A code-edit interface can break a repository. An agent workflow can create legal, privacy, or safety exposure. The model's safety is therefore not only a property of the model; it is a property of the allowed action surface.

Interface principle
Use an action interface that matches the claim being evaluated, and constrain that interface according to the cost of a wrong action.
TOPIC 04

Feedback: what the model learns after acting

A model improves within a task only if the interface returns useful consequences.

Feedback can be a test failure, compiler error, proof-checker result, tool output, rendered page, simulator state, user correction, reward score, verifier judgment, or clinical outcome. Without feedback, the model can only guess whether its action worked. With feedback, it can repair. The type of feedback determines the type of repair possible.

HERO combines sparse verifier checks with dense reward scores. MoCA separates perception and reasoning checks so the model can locate failure. THOR uses tool feedback for intermediate math steps. CyberGym gives the agent environment consequences. dWorldEval uses progress indicators for policy ranking. These papers show that feedback is not just final grading. It is an interface for local correction.

Bad feedback is dangerous. A reward score can be hacked. A vague user correction can be misread. A test suite can be incomplete. A simulator can be unrealistic. A model judge can reward style. Good feedback should be specific enough to guide repair, strong enough to reject shortcuts, and limited enough to avoid teaching the model to exploit the verifier.

Interface principle
Feedback should tell the model which part of the action failed, while remaining hard to satisfy through shortcuts that do not improve the real task.
TOPIC 05

Memory: what persists across steps

Memory is the interface between past work and the next action.

A system that forgets everything must re-derive each step. A system that remembers too much may carry stale, private, irrelevant, or misleading information. Memory design decides which facts persist: user preference, patient state, object identity, codebase decisions, tool results, proof obligations, graph state, or previously learned skills. Long-horizon tasks often fail because the needed state is not represented at the next decision point.

Skill-Pro turns episodic agent traces into reusable executable skills with activation, execution, and termination conditions. That is memory as interface: past traces become callable procedures rather than raw transcripts. Long-context and retrieval pages ask which past evidence remains accessible. Adaptation pages ask how new evidence changes behavior without erasing old structure. Medical and education agents depend on whether user or patient state is preserved in a useful form.

The hard part is selecting what memory means. A conversation summary may keep intent and lose exact names. A code memory may keep design decisions and lose line-level constraints. A patient summary may keep diagnoses and lose temporal trend. A skill library may keep a workflow and reuse it in the wrong context. Memory needs activation conditions and expiration, not only storage.

Interface principle
Memory should preserve state that changes future decisions, while making stale, private, or context-specific information hard to reuse accidentally.
TOPIC 06

Structured data: when text is the wrong surface

Some objects lose their meaning when flattened into prose.

Graphs, tables, code, proofs, schemas, molecules, medical records, and event streams have structure that is not only textual. A graph has adjacency, paths, neighborhoods, and edge labels. A table has cells, rows, columns, headers, and joins. Code has syntax, references, types, tests, and runtime behavior. A medical record has visits, medications, labs, timing, and thresholds. If the interface turns all of that into undifferentiated text, the model may lose the operation that defines the task.

Actions Speak Louder than Prompts is the central anchor: graph reasoning depends on whether the model receives prompts, code, or action interfaces. VERINA separates code, specification, and proof. Risk Hypergraphs makes medical risk a hypergraph object rather than independent labels. Program-synthesis and verification pages treat code as executable structure. Graph-learning pages treat topology and support examples as the real task surface.

This does not mean text interfaces are bad. Text can be the right surface for instructions, explanations, summaries, and human interaction. The point is that text should not be the only surface when the domain object has operations the model needs to perform. A structured interface can preserve exact units and make valid actions easier.

Interface principle
Use structured interfaces when the task depends on relations, fields, syntax, timing, or operations that prose would hide or distort.
TOPIC 07

Multimodal surfaces: what the model sees versus what the world contains

Images, video, audio, fMRI, sleep signals, and proprioception expose different slices of the same world.

A caption is not an image. A frame is not a video. A sleep-stage label is not a physiological trace. A brain token is not a sentence. A robot camera is not the robot's full state. Multimodal interfaces decide which part of a measured reality reaches the model. They also decide what alignment means: two views can be matched by surface description, shared object, event timing, patient state, or action consequence.

Mind-Omni creates discrete brain tokens and trains across brain, image, and language tasks. SleepLM aligns polysomnography with language through captioning, retrieval, event localization, and reconstruction. BioX-Bridge aligns physiological representations across modalities. LIMSSR handles incomplete multimodal action-quality evidence. Multimodal and embodied pages repeatedly show that the interface must preserve grounding, timing, and uncertainty rather than only produce a fluent summary.

The failure mode is easy to miss. A system can have multimodal inputs but still reason through a shallow text bottleneck. It can summarize a video and lose the frame where the action changes. It can describe a medical signal and lose the threshold. It can caption a scene and lose object relations needed for action. The interface should preserve the unit that the later decision needs.

Interface principle
A multimodal interface should expose the measured state at the level the task uses: object, event, timing, signal, relation, uncertainty, or action consequence.
TOPIC 08

Embodied action: captions are not control

A robot or embodied agent needs an interface that turns perception into feasible action.

Embodied tasks expose the sharpest difference between understanding and doing. A model can describe a scene, identify an object, or write a plan without producing a motion that works. Control requires action units, feedback, physical constraints, timing, and state estimation. The interface has to connect high-level intent to low-level consequences.

HDFlow separates long-horizon planning into high-level latent subgoals and low-level rectified-flow trajectories. LaST0 models future visual dynamics, 3D structure, and proprioception in latent reasoning space. WestWorld uses morphology-aware trajectory world models. dWorldEval evaluates policies through generated future observations and progress indicators. Latent Action Supervision studies discrete latent action-token supervision. These are interface papers because they decide what kind of action unit the model can emit and what feedback it receives.

The key is matching action granularity to the task. Low-level commands can be precise but hard to plan with. High-level subgoals can be efficient but may hide feasibility. Latent action tokens can compress behavior but may not transfer across tasks. Simulator feedback can guide control but may miss real-world mismatch. The interface must carry enough physical structure for safe action.

Interface principle
Embodied interfaces should expose action units and feedback at the level where the model can plan without losing physical feasibility.
TOPIC 09

Permissions and governance: what the model is allowed to do

A powerful interface without boundaries turns capability into operational risk.

Permissions are part of the interface. A shell, browser, file editor, database, robot controller, or medical record viewer gives the model access to actions and information. That access must be scoped. The model should see what it needs, act where it is allowed, expose audit traces, and receive checks before high-cost actions. Governance is not outside the system; it is built into what the interface permits.

SandboxEscapeBench makes the boundary itself the object of evaluation. Copyright-Bench evaluates legal source choices under creative workflow pressure. Privacy and unlearning pages ask what information can remain available and what must be deleted. Data governance pages treat source legality and reproducibility as part of training infrastructure. Agent infrastructure risk pages show that tool-using agents create new attack surfaces.

A governance interface has to encode source eligibility, privacy limits, deletion rights, audit logs, action approval, and least privilege. Otherwise the model may optimize task success by crossing a boundary the user did not intend to expose. The stronger the action surface, the more explicit the permission surface must be.

Interface principle
Permission boundaries should be treated as first-class parts of the model interface, not as policy text placed beside an unconstrained action surface.
TOPIC 10

Why this is not the same as evaluation

Evaluation asks what proves the model was right. Interface design asks what the model was able to see and do before being judged.

These two ideas are connected but different. The evidence page asks: what outside check can falsify the claim? This page asks: what surface lets the model interact with the task so that such evidence can exist? A code test is evidence. A code editor plus repository plus test runner is an interface. A sandbox escape result is evidence. Shell access, files, permissions, and container boundary are the interface. A robot trajectory is evidence. Sensors, action tokens, simulator feedback, and controller limits are the interface.

This distinction matters because a bad interface can make evaluation unfair or meaningless. If the model is judged on graph reasoning but only receives a clumsy text rendering of the graph, the result mixes reasoning ability with interface friction. If a medical model is judged on patient risk but lacks timeline and medication data, the task is underexposed. If an agent is judged on safety but the interface grants unnecessary permissions, the test may create risks unrelated to the intended capability.

A strong paper usually makes both parts visible. It says what the model can observe, what it can act on, what feedback it receives, what constraints apply, and what evidence proves success. That is the complete model-task contract.

Closing line
Capability lives in the model-interface pair: the model supplies internal behavior, and the interface decides what parts of the world that behavior can reach.
