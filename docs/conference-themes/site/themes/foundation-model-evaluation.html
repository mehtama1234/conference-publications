Foundation model evaluation after adaptation

The core question is whether a benchmark score measures a model's current surface behavior or its deeper potential after a fair adaptation step. Train-before-Test argues those are different objects.

Problem

Direct benchmark rankings often contradict each other because they mix model quality with prompting, formatting, instruction tuning, benchmark familiarity, and deployment surface details.

Approach

Train-before-Test gives each model the same benchmark-specific fine-tuning before evaluation, then asks whether post-adaptation rankings transfer across benchmarks.

Connecting read

The key distinction is deployment readiness versus model potential. Both matter, but confusing them makes model comparison noisy.

FIRST PRINCIPLES

The core problem

A foundation model is not a finished product in the same way for every user. One team may use it zero-shot, another may prompt-tune it, another may fine-tune it, and another may wrap it in retrieval, tools, or memory. A direct benchmark score tells us how the current surface behaves under one evaluation protocol. It does not always tell us what the underlying model can become after a controlled adaptation step.

That matters because model rankings are used for buying decisions, research claims, scaling-law arguments, and benchmark design. If benchmark A says model X is better and benchmark B says model Y is better, the field has to ask whether the models truly have incomparable strengths or whether the measurement lens is unstable. Train-before-Test is useful because it changes the unit being measured: not immediate score, but achievable score after matched training pressure.

OBJECT

The concrete object is a ranking after equal adaptation

Train-before-Test is not just another benchmark. It asks what a benchmark ranking means.

A direct leaderboard measures a mixture: pretraining quality, instruction tuning, benchmark familiarity, prompt format fit, calibration, refusal style, answer extraction, and sometimes accidental contamination. Those ingredients are useful if the deployment question is "which model should I use exactly as served?" They are less useful if the scientific question is "which base model has stronger latent capability once given the same opportunity to adapt?"

The paper's concrete object is therefore the post-adaptation score matrix: many models, many benchmarks, each model given the same benchmark-specific training pressure before the final test. The fixed object is fairness of comparison. What may change is the model's surface behavior after adaptation. The method works if equal adaptation removes idiosyncratic prompt and benchmark-surface noise and exposes a more stable model-potential factor.

ANATOMY

The score only means something with the recipe attached

A benchmark number is a conditional statement: this model, under this evaluation recipe, achieved this score.

Train-before-Test makes that conditional structure explicit. The model is not measured raw. It is first given the same benchmark-specific fine-tuning opportunity as the other models, then evaluated. That turns the benchmark into a controlled experiment over model potential. The output is not one isolated score; it is a model-by-benchmark matrix after a matched adaptation recipe.

The rank-one finding matters because it says something surprising about that matrix. After the protocol controls adaptation, many benchmark scores appear to share a dominant latent factor. In plain language: once each model gets the same kind of practice for each benchmark, the rankings look more like one broad model-potential ordering and less like unrelated benchmark-specific noise.

TOPIC 01

A benchmark score is not a property of the model alone

A score is produced by a model plus an evaluation recipe.

This is the first thing Train-before-Test makes explicit. The same underlying model can look different under different prompts, answer formats, instruction tuning histories, calibration rules, extraction scripts, and fine-tuning opportunities. So a leaderboard entry is not simply "model X has ability Y." It is "model X, under this measurement surface, produced score Y."

That distinction matters because foundation models are reused in many forms. A raw base model, an instruction-tuned chat model, a prompt-engineered model, a fine-tuned model, and a tool-wrapped model are different deployed objects. Direct evaluation is valuable when that exact surface is what the user will deploy. It becomes misleading when people read it as the model's full latent capability.

TOPIC 02

Adaptation can reveal potential, but it also changes the object

Train-before-Test measures what becomes reachable after a matched training step, not what the model already does out of the box.

The adaptation step is powerful because it lets each model learn the benchmark interface. A model that was bad at the prompt format but strong at the underlying skill can recover. A model that was polished for direct answering but had less adaptable structure may lose its apparent lead. That is why the method can make rankings more stable across benchmarks: it reduces surface mismatch and asks what remains after each model gets the same chance to adjust.

But this also means the evaluated object has changed. The score is no longer direct deployment behavior. It is adapted model potential under a specified recipe. That is not a weakness if stated clearly. It is the whole point of the method. The error would be to use an adapted-potential ranking as if it were a zero-shot product ranking.

TOPIC 03

Fairness lives inside the training recipe

The adaptation protocol is the measuring instrument, so small asymmetries can become measurement bias.

If every model receives the same benchmark-specific training opportunity, the comparison can become cleaner. If the recipe favors one model family, context length, tokenizer, optimizer sensitivity, answer format, or memorization behavior, the comparison becomes biased. That is why the fixed parts matter: data split, training budget, optimizer, stopping rule, scoring rule, leakage controls, and answer extraction all have to be treated as part of the experiment.

In plain terms, Train-before-Test is only fair if the practice session is fair. The method is trying to ask, "After equal practice, which model has more potential?" If the practice session is unequal, the answer becomes a property of the recipe rather than the model.

TOPIC 04

Rank-one structure means the benchmarks start agreeing

The rank-one result is a way of saying that many adapted benchmark scores point toward one dominant ordering.

Without the math, a score matrix is just a table: rows are models, columns are benchmarks, cells are scores. If every benchmark tells a different story, the table has many competing directions. If the table is approximately rank one, then much of the variation can be explained by one main factor. In this setting, that factor can be read as broad adapted model potential.

That does not mean every benchmark becomes identical or that one number explains all model behavior. It means that after matched adaptation, the benchmark suite may become less noisy as a comparison instrument. The paper's deep claim is therefore about measurement coherence: adaptation can turn a messy set of direct scores into a more stable signal about model potential.

EVIDENCE

What would prove the method is measuring something real

The evidence has to show that Train-before-Test reduces noise rather than merely creating a new leaderboard artifact.

The local evidence points to three tests. First, rankings after adaptation become more consistent across benchmarks than direct rankings. That suggests the protocol is removing some benchmark-specific surface noise. Second, the adapted scores restore a relationship between perplexity and downstream performance that direct scoring had blurred. That suggests the protocol is closer to base-model capability. Third, the adapted model-score matrix becomes approximately rank one. That suggests many benchmark outcomes share a dominant model-potential dimension once the evaluation gives each model the same chance to learn the benchmark interface.

The failure boundary is also clear. If adaptation data leaks test answers, the result is not model potential. If the fine-tuning recipe favors one architecture family, the ranking is not fair. If post-adaptation rankings remain unstable, the method has not solved the benchmark disagreement problem. If the adapted model is unsafe or unusable in practice, the result is still only a potential measure, not a deployment endorsement.

External validity

A ranking from one benchmark should predict rankings on other benchmarks better after train-before-test than under direct evaluation.

Perplexity link

Pre-finetuning perplexity should regain predictive value for downstream adapted performance if the protocol is exposing model potential.

Rank-one structure

The adapted score matrix should be close to one dominant factor rather than many unrelated benchmark-specific orderings.

CONTROL

The adaptation step is the measuring instrument

Train-before-Test works only if the adaptation protocol is controlled tightly enough that every model receives the same kind of opportunity.

That is the subtle part. Fine-tuning before testing could easily become unfair if some models get more compatible data, better hyperparameters, longer training, easier answer formats, or leaked benchmark information. The paper's conceptual claim depends on treating adaptation like a scientific instrument: same benchmark-specific pressure, same evaluation split, same ranking rule, and enough breadth across models and benchmarks to see whether the resulting order is stable.

When that control holds, the method separates two questions that ordinary leaderboards often mix. Direct score asks how polished the model already is for this benchmark interface. Adapted score asks how much capability appears after the model is taught the interface under equal pressure. The first is a deployment question. The second is a model-potential question.

FAILURE MODES

Where the interpretation can go wrong

Train-before-Test is a lens for model potential, not a universal replacement for direct evaluation.

Direct evaluation still answers a real question: what happens if a user uses the model as provided? That includes instruction-following polish, safety behavior, refusal style, latency, tool wrappers, and deployment formatting. Train-before-Test answers a different question: what performance becomes reachable after a controlled adaptation step? Confusing those two readings would recreate the measurement problem in a new form.

The protocol can also fail technically. If the benchmark-specific fine-tuning data leaks the test, the score measures memorization. If the adaptation recipe is too small for some models and too large for others, it may favor one architecture family. If users in the real world cannot afford that adaptation budget, then the result is still scientifically meaningful but not a direct procurement answer. The paper's contribution is strongest when the reader keeps the claim conditional: potential after this matched training recipe.

SYNTHESIS

The paper's conceptual move

Model potential is different from zero-shot polish

adaptation-aware ranking

The usual leaderboard treats each model's direct score as the comparison object. That is appropriate when the question is deployment readiness under exactly that protocol. It is weaker when the question is whether one foundation model is a stronger base for adaptation than another.

ICLR 2026Train-before-Test
Train-before-Test fine-tunes every model on identical benchmark-specific data before evaluation, then compares the resulting model-potential rankings across 24 benchmarks and 61 models. The local note reports three important findings. First, adapted rankings are much more consistent across benchmarks than direct rankings. Second, the procedure restores a relationship between perplexity and downstream performance that direct evaluation had obscured. Third, the adapted model-score matrix becomes approximately rank one, suggesting that a dominant latent factor of model potential is exposed by controlled adaptation. The paper does not say direct evaluation is useless; it says direct evaluation and potential evaluation answer different questions.
FIELD READ

What this theme says about ICML and ICLR

The broader conference pattern is that evaluation is becoming less like a static scoreboard and more like an instrument. A good evaluation protocol has to specify the interaction surface: direct prompting, fine-tuning, retrieval, memory, tools, verifier feedback, or service-time learning.

This connects directly to the benchmark and agent-evaluation work. When a browser task, code task, or long-horizon agent benchmark compares systems, it is also choosing whether to measure raw model behavior, scaffolded behavior, learned policy behavior, or adaptable potential. Train-before-Test gives one clean example of why that choice matters: the same set of models can look inconsistent under direct scoring and coherent after matched adaptation. For these conference pages, this theme is a warning label: every benchmark result should say what kind of capability it is actually measuring.
