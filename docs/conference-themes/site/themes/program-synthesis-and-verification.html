Program synthesis and verification as constrained artifact search

The shared question is not whether a model can write code that looks plausible. It is whether the generated artifact survives the rules of the domain: semantic checks, compiler checks, runtime checks, efficiency checks, and adversarial review.

Problem

Program generation fails when syntax, semantics, statistical assumptions, hardware behavior, tests, or review workflows are treated as afterthoughts instead of part of the generation problem.

Approaches

The papers use semantic constraints and local repair for probabilistic programs, hierarchical correctness-speed rewards for CUDA kernels, and CI-driven adversarial workflows for software agents.

Connecting read

The unifying idea is that code quality is a checked process. Generation, diagnosis, repair, and verification have to be joined into one loop.

FIRST PRINCIPLES

The core problem

A program is not just text. It is an object that must satisfy a language grammar, a type system or runtime, a domain model, resource constraints, and a user's intended behavior. A model can generate something that looks like code while failing the property that matters: the program does not compile, computes the wrong thing, violates a statistical assumption, runs too slowly, or passes easy tests while missing the real issue.

That is why this theme is about synthesis and verification together. If the verifier is outside the loop, the model wastes attempts on invalid regions of the search space. If the synthesis loop ignores domain structure, the verifier can only reject failures after the fact. The conference evidence here points to a more useful pattern: expose the constraints early, use diagnostics to repair locally, and make evaluation look like the real workflow where the artifact will live.

SYNTHESIS

Three views of verified generation

1. Statistical programs need semantic repair, not just more samples

probabilistic synthesis

Probabilistic programming is difficult because the generated program has two kinds of correctness. It has to be syntactically executable, and it has to describe a statistically meaningful model. A prior, likelihood, parameter, or inference construct can be legal code and still be a broken model.

ICLR 2026RefineStat
RefineStat treats probabilistic program synthesis as constrained search guided by diagnostics. Instead of asking a small language model to regenerate a whole program whenever something fails, it checks semantic requirements such as valid distributions and well-formed parameters, then locally resamples the prior or likelihood component that caused the reliability failure. The important idea is that domain expertise becomes part of the synthesis algorithm. A probabilistic programmer would debug a model by inspecting which statistical component is wrong; RefineStat turns that repair behavior into a generation loop, which is why small models can become competitive in a highly structured domain.

2. Systems code has to be both correct and fast

performance verification

For low-level kernels, functional correctness is only the first gate. The generated code also has to match the hardware and data structure well enough to justify being used. Sparse matrices make this hard because the useful program depends on irregular nonzero patterns, memory access, compilation behavior, and GPU execution time.

ICLR 2026SparseRL
SparseRL casts sparse CUDA generation as reinforcement learning over programs. The model receives sparse matrix structure, including row and column indices of nonzero elements, and generates CUDA code for operations such as SpMV and SpMM. Its reward is hierarchical: compilation and correctness have to come before speed optimization, then execution efficiency becomes the target. This is a clean example of verification shaping synthesis. The model is not rewarded for code-like text; it is rewarded for code that survives the compiler, computes the right result, and runs faster on the intended workload.

3. Real software work is an adversarial process

workflow verification

Most coding benchmarks flatten software development into one-shot patch generation. Real development does not work that way. A patch is reviewed, tests are written, hidden dependencies matter, CI runs, and large codebases force the agent to retrieve the right context before editing.

ICLR 2026SwingArena
SwingArena evaluates code agents through a submitter-reviewer setup over real GitHub issues. Submitter models generate patches; reviewer models create tests and verify patches through CI; retrieval-augmented code generation supplies relevant snippets from large codebases across C++, Python, Rust, and Go. The first-principles contribution is the benchmark shape. It measures the process around the code, not only the final patch. That makes failures visible at the points where software actually breaks: missing context, weak tests, overly aggressive changes, conservative validation, or CI behavior that exposes a mismatch between the patch and the repository.
FIELD READ

What this theme says about ICML and ICLR

The big picture is that program synthesis is becoming process-aware. The useful unit is no longer a generated snippet; it is the loop that proposes, checks, diagnoses, repairs, and rechecks an artifact under the constraints of the target environment.

This is why the theme connects to the broader verification papers even when they are cataloged elsewhere. VERINA separates code, specification, and proof generation. AlgoVeri holds contracts fixed across Dafny, Verus, and Lean to expose tool-paradigm gaps. RefineStat, SparseRL, and SwingArena show the same pressure from different angles: statistical code needs semantic reliability, systems code needs performance-grounded correctness, and software agents need workflow-grounded verification. The field is converging on a simple standard: if a generated artifact matters, the benchmark should contain the mechanism that can prove or falsify it.
