Program synthesis and verification as constrained artifact search

The shared question is not whether a model can write code that looks plausible. It is whether the generated artifact survives the rules of the domain: semantic checks, compiler checks, runtime checks, efficiency checks, and adversarial review.

Problem

Program generation fails when syntax, semantics, statistical assumptions, hardware behavior, tests, or review workflows are treated as afterthoughts instead of part of the generation problem.

Approaches

The papers use semantic constraints and local repair for probabilistic programs, hierarchical correctness-speed rewards for CUDA kernels, and CI-driven adversarial workflows for software agents.

Connecting read

The unifying idea is that code quality is a checked process. Generation, diagnosis, repair, and verification have to be joined into one loop.

FIRST PRINCIPLES

The core problem

A program is not just text. It is an object that must satisfy a language grammar, a type system or runtime, a domain model, resource constraints, and a user's intended behavior. A model can generate something that looks like code while failing the property that matters: the program does not compile, computes the wrong thing, violates a statistical assumption, runs too slowly, or passes easy tests while missing the real issue.

That is why this theme is about synthesis and verification together. If the verifier is outside the loop, the model wastes attempts on invalid regions of the search space. If the synthesis loop ignores domain structure, the verifier can only reject failures after the fact. The conference evidence here points to a more useful pattern: expose the constraints early, use diagnostics to repair locally, and make evaluation look like the real workflow where the artifact will live.

TOPIC 01

A generated program is a claim about behavior

The first mistake is to treat code generation as sentence generation. Code is text, but its meaning is not decided by how convincing the text looks.

A program makes a behavioral claim: if this input arrives in this environment, the artifact will do this thing and not that thing. For a probabilistic program, the claim is about the probability model and inference path. For a CUDA kernel, the claim is about numerical output and hardware execution. For a repository patch, the claim is about how the whole codebase behaves after the edit. That is why these papers belong in one theme. They all ask the model to produce an artifact whose truth is checked outside language.

This matters because language models are strong at producing locally plausible continuations. But local plausibility is weak evidence for program validity. A generated kernel can look like CUDA while racing memory, a generated statistical model can look like Pyro or Stan while violating support constraints, and a generated patch can look idiomatic while missing the issue intent. The real object is the artifact plus the environment that can prove or falsify it.

TOPIC 02

The verifier must match the kind of artifact

There is no single generic test called correctness. Each artifact needs the verifier that can catch the thing it is likely to get wrong.

RefineStat needs statistical semantics because ordinary execution is too weak. A probabilistic program may run while expressing the wrong model. SparseRL needs compile, correctness, and timing evidence because speed only matters after the kernel computes the intended result. SwingArena needs repository tests, reviewer-generated tests, CI, and retrieval-sensitive context because software patches fail at the boundary between the local diff and the larger system.

The deeper principle is verifier alignment. A verifier is useful only when it measures the property the artifact claims to satisfy. If the verifier is too shallow, the model learns to satisfy the surface. If the verifier is too detached from the real environment, the artifact can pass the benchmark and still fail in use. Good synthesis research therefore designs the task and the verifier together.

TOPIC 03

Local repair is better when the failure is local

A diagnostic is valuable because it says where the generated artifact left the valid set.

If a probabilistic program has a malformed prior, resampling the entire program throws away useful structure. If a kernel compiles but gives wrong output, the synthesis loop should not treat that the same as a compile failure or a slow-but-correct kernel. If a patch fails a reviewer test, the next edit should respond to the failing behavior rather than simply produce a different-looking diff. The point is not that local repair always wins. The point is that a good verifier gives typed evidence, and typed evidence should guide the next edit.

This is why verified synthesis is more like debugging than autocomplete. The system proposes an artifact, the world pushes back with a specific failure, and the next proposal should preserve what worked while changing the part that broke. That loop is the bridge from code-shaped text to dependable code-producing systems.

TOPIC 04

Performance is not a substitute for validity

Optimization pressure becomes dangerous when the reward can be improved by leaving the intended problem.

SparseRL makes this concrete. A fast CUDA kernel is not useful if it computes the wrong answer, compiles only accidentally, or wins only on a narrow sparsity pattern. SwingArena has the software version of the same issue: a patch can pass visible tests by overfitting the benchmark while breaking hidden behavior. RefineStat has the scientific version: a generated program can produce outputs while violating the probability story it is supposed to represent.

The first-principles rule is that the invariant comes before the objective. Correctness before speed. Statistical meaning before execution. Issue intent before patch elegance. Repository behavior before benchmark tricks. Once the invariant is secure, optimization becomes meaningful; before that, optimization is just search pressure looking for loopholes.

CORE

Generation is search; verification is the boundary

The model is not trying to write the most likely program. It is trying to find a program inside a constrained set.

That set is different for each paper. RefineStat searches over probabilistic programs, but only programs with valid statistical meaning should count. SparseRL searches over CUDA kernels, but only kernels that compile and compute correctly are allowed to compete on speed. SwingArena searches over repository patches, but only patches that survive tests, review pressure, retrieval constraints, and CI represent real software progress.

This is the deep link between synthesis and verification. Verification is not a final score pasted onto generation. It defines the shape of the target space. If a system does not know the boundary, it can become very good at generating things near code without generating useful software artifacts.

LOOP

Verification is feedback, not decoration

The verifier becomes useful when its result changes the next synthesis step.

A compile error, failed test, invalid distribution, wrong proof obligation, slow kernel, or CI failure is not just a score. It is information about where the generated artifact left the valid region. RefineStat uses that information semantically: if the prior is wrong, repair the prior; if the likelihood is wrong, repair the likelihood. SparseRL uses a hierarchy: do not optimize speed before the code compiles and computes correctly. SwingArena uses an adversarial workflow: reviewer tests and CI expose whether the patch actually solves the issue.

The first-principles claim is that verified synthesis should be local when the evidence is local. Regenerating everything after every failure wastes the structure the verifier exposed. The stronger loop is propose, check, identify the broken constraint, repair that part, and recheck. That is the difference between sampling code-shaped text and searching a constrained artifact space.

EVIDENCE

What would prove synthesis found a valid artifact

The evidence has to show that the generated program lives inside the constrained set that the task requires.

Semantic checks

Probabilistic programs should preserve valid distributions, parameter support, likelihood meaning, inference diagnostics, and the intended statistical story.

Correctness gates

Generated kernels and code should compile and compute the right result before speed, elegance, or reward can count as progress.

Workflow verification

Repository patches should satisfy issue intent, tests, review pressure, CI, hidden dependencies, and language-specific constraints.

Local repair evidence

Verifier diagnostics should identify the broken component and the next edit should repair that component rather than blindly resampling everything.

Regression resistance

A patch or optimized program should improve the target behavior without breaking neighboring behavior, patched cases, or downstream artifacts.

Environment match

The benchmark should run in the same kind of statistical, hardware, repository, proof, or CI environment where the artifact is supposed to matter.

FAILURE MODES

How verified synthesis can still go wrong

The common failure is a mismatch between the artifact, the verifier, and the real environment where the artifact will be used.

Executable nonsense

The program runs, but the statistical model, proof obligation, or repository behavior is not the one the user needed.

Reward loophole

The system improves speed, pass rate, or reviewer score by exploiting a weak check instead of solving the real task.

Context miss

The patch or generated program ignores a dependency, convention, invariant, hardware detail, or data assumption outside the local snippet.

Overfit artifact

The generated object works for the visible case but fails neighboring tests, hidden cases, other sparsity patterns, or slightly different specifications.

Verifier gap

The benchmark checks syntax, plausibility, or easy tests while the important property lives in semantics, performance, CI, proof, or domain validity.

Destructive repair

The next edit fixes the reported error by breaking a previously satisfied constraint because the loop does not preserve what already worked.

SYNTHESIS

Three views of verified generation

1. Statistical programs need semantic repair, not just more samples

probabilistic synthesis

Probabilistic programming is difficult because the generated program has two kinds of correctness. It has to be syntactically executable, and it has to describe a statistically meaningful model. A prior, likelihood, parameter, or inference construct can be legal code and still be a broken model.

ICLR 2026RefineStat
RefineStat treats probabilistic program synthesis as constrained search guided by diagnostics. Instead of asking a small language model to regenerate a whole program whenever something fails, it checks semantic requirements such as valid distributions and well-formed parameters, then locally resamples the prior or likelihood component that caused the reliability failure. The important idea is that domain expertise becomes part of the synthesis algorithm. A probabilistic programmer would debug a model by inspecting which statistical component is wrong; RefineStat turns that repair behavior into a generation loop, which is why small models can become competitive in a highly structured domain.

2. Systems code has to be both correct and fast

performance verification

For low-level kernels, functional correctness is only the first gate. The generated code also has to match the hardware and data structure well enough to justify being used. Sparse matrices make this hard because the useful program depends on irregular nonzero patterns, memory access, compilation behavior, and GPU execution time.

ICLR 2026SparseRL
SparseRL casts sparse CUDA generation as reinforcement learning over programs. The model receives sparse matrix structure, including row and column indices of nonzero elements, and generates CUDA code for operations such as SpMV and SpMM. Its reward is hierarchical: compilation and correctness have to come before speed optimization, then execution efficiency becomes the target. This is a clean example of verification shaping synthesis. The model is not rewarded for code-like text; it is rewarded for code that survives the compiler, computes the right result, and runs faster on the intended workload.

3. Real software work is an adversarial process

workflow verification

Most coding benchmarks flatten software development into one-shot patch generation. Real development does not work that way. A patch is reviewed, tests are written, hidden dependencies matter, CI runs, and large codebases force the agent to retrieve the right context before editing.

ICLR 2026SwingArena
SwingArena evaluates code agents through a submitter-reviewer setup over real GitHub issues. Submitter models generate patches; reviewer models create tests and verify patches through CI; retrieval-augmented code generation supplies relevant snippets from large codebases across C++, Python, Rust, and Go. The first-principles contribution is the benchmark shape. It measures the process around the code, not only the final patch. That makes failures visible at the points where software actually breaks: missing context, weak tests, overly aggressive changes, conservative validation, or CI behavior that exposes a mismatch between the patch and the repository.
FIELD READ

What this theme says about ICML and ICLR

The big picture is that program synthesis is becoming process-aware. The useful unit is no longer a generated snippet; it is the loop that proposes, checks, diagnoses, repairs, and rechecks an artifact under the constraints of the target environment.

This is why the theme connects to the broader verification papers even when they are cataloged elsewhere. VERINA separates code, specification, and proof generation. AlgoVeri holds contracts fixed across Dafny, Verus, and Lean to expose tool-paradigm gaps. RefineStat, SparseRL, and SwingArena show the same pressure from different angles: statistical code needs semantic reliability, systems code needs performance-grounded correctness, and software agents need workflow-grounded verification. The field is converging on a simple standard: if a generated artifact matters, the benchmark should contain the mechanism that can prove or falsify it.
