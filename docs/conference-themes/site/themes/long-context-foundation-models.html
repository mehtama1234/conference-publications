Problem

Long context is not solved by adding tokens. The model must know which tokens matter, which positions generalize, which memories should be compressed, and when retrieval or recurrence is better than attention over everything.

Approaches

The papers study positional extension, SSM and recurrent memory, latent chunking, token compression, retrieval control, attribution, diffusion-style generation, irregular time, and multimodal latent interfaces.

Connecting read

The field is turning context length into a memory architecture problem: representation, access, update, compression, and evidence selection.

FIRST PRINCIPLES

The core problem

A long sequence is not a single object. It is a mix of local details, remote dependencies, irrelevant filler, temporal structure, instructions, evidence, and state that changes over time. A foundation model has to decide what to store exactly, what to summarize, what to retrieve again, and what to forget.

That is why these papers do not all look like ordinary long-context papers. Some redesign position encodings. Some replace attention with recurrent or state-space memory. Some compress tokens or video into fewer latent units. Some retrieve procedural directives during reasoning. Some explain long-context decisions by attributing spans. The common question is how to make memory selective enough to scale while still precise enough to preserve the evidence that matters.

ANATOMY

The concrete object is usable past evidence

A long-context paper is about the past information that remains usable later: token, span, clause, source, function, event, object track, patient visit, video frame, cache entry, retrieved item, or compressed state.

What must stay fixed is the future decision that past evidence should influence. A code context method must preserve symbol identity and relevant tests. A legal method must preserve exact clauses, exceptions, parties, and dates. A medical method must preserve temporal patient state. A video method must preserve object identity and events. A retrieval or compression method must preserve provenance and the rare clue that changes the answer.

What may change is the memory mechanism: position encoding, recurrent state, cache compression, retrieval index, chunking, summary, token budget, attribution method, or state-space architecture. The method works when the past remains accessible at the decision point while irrelevant or stale material loses authority. The failure boundary is storage without use: the information is technically in context or memory, but the model cannot retrieve, bind, trust, or apply it when the answer depends on it.

TOPIC 01

What long context is really for

Long context is for carrying useful past information into a later decision. The value is not the length of the input. The value is whether the old information still changes what the system does.

A longer window is easy to misunderstand. It sounds like the model has simply been given more room. But useful long context is not a warehouse. It is a working memory. A warehouse can contain everything and still be useless if the needed item cannot be found at the moment of decision. A working memory keeps the right facts available, keeps them in a form the model can use, and prevents irrelevant old facts from taking over.

The first question is therefore: what future decision is this memory serving? If the task is answering a question about a contract, the memory must preserve the clause, the exception, the party, the date, and the amount. If the task is editing a codebase, the memory must preserve symbol identity, file ownership, prior edits, and tests. If the task is following a long conversation, the memory must preserve commitments, corrections, and active constraints. If the task is video understanding, the memory must preserve objects, events, transitions, and the state that is true now.

That is the central shift. Long context is not a general-purpose virtue. It is useful only when the system can connect a remote past item to a present action. A model that remembers the wrong old instruction, retrieves the wrong similar paragraph, or compresses away the one deciding number may have a large context window, but it has failed the purpose of long context.

1. The purpose is decision continuity

purpose

Long context matters when a later answer depends on something that appeared earlier. The dependency may be explicit, like a question that asks about a buried paragraph. It may be implicit, like a code change that must respect an interface defined in another file. It may be temporal, like a patient trend or a video event. It may be conversational, like a correction the user made thirty turns ago.

The model succeeds when the later behavior reflects the earlier evidence. It chooses the right clause, preserves the right symbol, continues the right plan, cites the right source, tracks the right object, or updates the right state. This is why context length alone is a weak measure. The real measure is continuity of decision: did the past remain usable when it mattered?

2. The same past can serve different purposes

use case

The same document, video, conversation, or record can demand different memory depending on the task. A legal summary may need broad structure, but legal risk review may need exact exceptions and cross-references. A video caption may need the main event, but safety monitoring may need the brief moment when motion changed. A code explanation may need architecture, but a bug fix may need exact call sites and failing tests.

This means the model cannot decide what matters from data type alone. "Text" is not the unit of purpose. "Video" is not the unit of purpose. The unit is set by the downstream question. The same raw context may need to be represented as claims, obligations, functions, tracks, actions, visits, tool results, or state changes depending on what the later system must do.

3. Long context must separate storage from use

access

Putting information inside the window does not guarantee the model can use it. The information still has to be addressable. The model must be able to find it, bind it to the current question, compare it against similar evidence, and carry it through reasoning without distortion. A buried fact that cannot be selected is almost the same as a forgotten fact.

This explains why the papers in this theme include retrieval, attribution, position encoding, tokenization, recurrent memory, and state-space methods. They are different answers to the same problem: how should the past remain accessible without forcing every old token to compete equally for attention at every step?

4. Good long context is selective

control

A useful system does not treat all old information as equally important. Some facts should stay exact. Some should become summaries. Some should be retrieved only when needed. Some should lose authority because they are stale, contradicted, or irrelevant. Selectivity is not a shortcut; it is the core of memory.

This is especially important in long conversations and agent work. Old instructions can be harmful if they keep controlling the model after the user has changed direction. Old observations can be harmful if the world has changed. Old retrieved passages can be harmful if they are similar but not decisive. Long-context systems must remember, but they must also know when memory should stop steering behavior.

5. The test is whether behavior changes for the right reason

proof

The cleanest proof of long context is not a claim about context length. It is a behavior that would be wrong without the remote information. If the far-away exception changes the answer, the model should change the answer. If an earlier edit changed the interface, the later code should follow that interface. If the patient trend changed after treatment, the interpretation should reflect that timeline.

This gives the theme its practical standard: long context works when removing, changing, or moving the relevant past evidence changes the model's later behavior in the expected way. Otherwise, the model may be reading a large input while still solving a short-context problem.

Long context is for decision continuity: preserving the past facts, states, and evidence that must still be usable when a later question, action, or prediction depends on them.
TOPIC 02

Choosing the unit of memory

A long-context model cannot remember "the past" directly. It remembers units. The choice of unit decides what stays together, what gets split apart, what can be retrieved, and what kind of mistake becomes easy.

The unit is the smallest thing the system treats as worth carrying forward. It may be a token, sentence, chunk, claim, citation, table row, function, class, patch, object, frame, clip, action, visit, symptom, clause, transaction, experiment, or latent state. None of these units is automatically correct. The right unit is the one that preserves the difference that changes the future answer.

This is why unit choice is a first-principles question rather than a formatting detail. If the unit is too small, the model spends memory rebuilding meaning from fragments. If the unit is too large, the model cannot retrieve the exact part that matters. If the unit ignores time, the model remembers facts but loses the order that made them meaningful. If the unit ignores source identity, the model mixes evidence across documents. If the unit ignores action, the model forgets what changed in the world.

1. Text units: token, sentence, claim, or argument step

text

In text, the obvious unit is a token or sentence, but those are not always the useful memory units. A legal rule may need to stay with its exception. A scientific claim may need to stay with its evidence and method. A long email thread may need commitments and decisions, not every sentence. A book chapter may need themes, definitions, and turning points.

The useful unit depends on the task. For exact quotation, the unit must preserve the span. For question answering, it may be a passage or claim. For contradiction detection, it may be two claims plus their sources. For argument reconstruction, it may be premise, evidence, caveat, and conclusion. Token-level memory is necessary for surface precision, but it is not sufficient for meaning.

2. Code units: symbol, dependency, file, patch, or behavior

code

In code, line-by-line memory is often too weak. The model needs to know which symbol is defined where, which files depend on it, which tests exercise it, which configuration changes behavior, and which previous edit changed the expected interface. A function name without its signature can be misleading. A file summary without call sites can be incomplete. A patch without test behavior can be unsafe.

The unit may be a symbol, function, class, import edge, module, error trace, test case, patch, or command result. The right unit is chosen by the coding task. Refactoring needs dependency units. Bug fixing needs traces, failing inputs, and relevant call paths. API migration needs exact names and types. Review needs changed behavior and risk, not only changed text.

3. Video units: frame, object track, action phase, or event

video

A frame is a natural video unit, but a frame alone often misses the point. The meaning of video is usually change. A person reaches, slips, recovers, leaves, or hands something over. An object moves from one place to another. A scene cuts. A gesture begins before it is recognizable. The deciding information may be the transition, not the still image.

The unit may therefore be a frame, clip, object track, motion segment, action phase, event, trajectory, or scene. Captioning may tolerate coarse event units. Safety monitoring may need short temporal units to catch abrupt change. Long-horizon planning may need state transitions and goals. A video tokenizer that spends equal memory everywhere may waste units on stable background and miss the rare moment where state changes.

4. Agent units: observation, action, result, constraint, or state

agents

For agents, the useful unit is rarely the message. It is the step in the world. The agent observes something, chooses an action, receives a result, updates its state, and carries forward a constraint. A transcript can be long while the active task state is small. The danger is preserving the transcript but losing what is currently true.

The memory unit may be a tool call, command result, failed attempt, user constraint, plan step, environment observation, file change, browser state, robot pose, object location, or safety rule. The model needs these units because later actions depend on them. If it forgets a failed command, it may repeat it. If it remembers an old world state, it may act in the wrong place. If it loses a constraint, it may complete the wrong task.

5. Medical units: value, visit, trend, treatment, or patient state

medicine

A patient record is not just a long document. It is a timeline of measurements, symptoms, treatments, findings, risks, and uncertainty. A single lab value may matter because it crosses a threshold. A series of values may matter because the trend changed. A medication may matter because it explains a later result. A missing test may matter because it leaves uncertainty.

The memory unit may be a lab value with units, a symptom, a medication, a dose, an allergy, a visit, an imaging finding, a diagnosis, a treatment response, or a hidden patient state. Exactness and time both matter. A summary can preserve the broad condition, but dosages, allergies, abnormal values, dates, and trends must survive with precision.

6. Legal and finance units: party, clause, exception, amount, or obligation

risk

Legal and financial memory is controlled by exact relationships. A clause may be active only under a condition. An exception may override a general rule. A payment may depend on a date. A filing may change the interpretation of a later number. Similar language can hide different obligations.

The memory unit may be a party, clause, obligation, exception, condition, amount, date, transaction, filing, citation, or cross-reference. The model must keep source identity and exact wording when the answer depends on them. A broad summary is useful for orientation, but not enough when the decision turns on a narrow condition.

7. Science units: experiment, measurement, method, or causal chain

science

Scientific context is long because evidence has provenance. A number is not just a number; it came from a sample, instrument, protocol, parameter setting, model assumption, or experimental condition. A result may only be comparable to another result if the methods line up. A failed run may be important because it rules out an explanation.

The memory unit may be an experiment, sample, measurement, parameter, method step, assumption, hypothesis, result, error bar, replication, or causal link. Good memory keeps the chain from method to result to conclusion. If the model remembers findings without provenance, it can connect evidence that should not be connected.

8. Latent units: compressed state that must still be testable

latent

Some papers do not keep memory as readable text, frames, or chunks. They compress it into hidden state, recurrent state, sparse dimensions, learned tokens, or latent trajectories. That can be powerful because the system can carry a smaller object than the original context. But the same rule still applies: the latent unit must preserve the information that later behavior needs.

A latent memory is useful only if it can be tested through behavior. Does it recover the right evidence, preserve order, track state, resist distractors, and support the downstream action? If not, the compact unit may look efficient while hiding loss of meaning. Compression changes the unit; it does not remove the need to prove what survived.

TOPIC 03

What must stay exact

Long context cannot treat every detail as compressible. Some details are load-bearing: if they change by one character, one digit, one frame, one source, or one boundary, the answer changes.

Exactness is not the opposite of abstraction. A good long-context system needs both. It should compress what can vary safely, while preserving the details where small differences carry meaning. The hard part is knowing which pieces are allowed to become gist and which pieces must remain tied to their original form.

This is why "close enough" is often the wrong standard for long context. A similar name can be the wrong person. A rounded number can be the wrong dose. A paraphrased clause can drop the exception. A code symbol with one changed character can refer to a different object. A video event shifted by a few frames can change whether the model saw cause or effect. Exactness matters wherever identity, threshold, syntax, provenance, or order changes the decision.

Identity

Names, people, variables, files, objects, drugs, diseases, parties, accounts, genes, citations, and source documents must not blur together.

Quantity

Numbers, units, dates, prices, probabilities, coordinates, dosages, thresholds, durations, and measurements often need exact values.

Syntax

Code, math, formulas, identifiers, command flags, table schema, and legal wording can break when small surface details are changed.

Boundary

Object edges, table cells, clauses, quoted spans, function bodies, scene cuts, visits, and event starts or ends may define the thing itself.

1. Names and identifiers must not become "similar enough"

identity

Many long-context tasks fail by merging nearby identities. Two people may share a last name. Two functions may differ by a suffix. Two drugs may look similar in spelling. Two companies may appear in the same filing. Two objects may cross paths in a video. If the model stores only a soft impression, it may answer about the wrong thing while sounding confident.

Exact identity must survive when the task depends on reference. In code, this means symbol names, file paths, import names, API names, and test names. In documents, it means people, organizations, sections, citations, and named obligations. In medicine, it means patient-specific facts, medications, allergies, genes, diagnoses, and procedure names. In video, it means keeping object identity through time rather than treating every visible object as interchangeable.

2. Numbers need values, units, and conditions

numbers

A number is rarely just a number. It has a unit, a date, a source, a measurement condition, and a threshold that may make it normal or abnormal. A model that remembers "the value was high" may be useful for a broad summary, but not for a decision that depends on whether the value was 5.1 or 15.1, dollars or euros, milligrams or micrograms, before treatment or after treatment.

Long-context memory should keep exact numeric values when they affect action. Finance needs amounts, rates, dates, and assumptions. Medicine needs lab values, dosages, units, and thresholds. Science needs measurements, error bars, parameters, and experimental conditions. Code and systems work need version numbers, ports, limits, line numbers, and command outputs. Compression can keep the trend, but the exact value must be retrievable when the decision depends on it.

3. Code and math preserve meaning through syntax

syntax

In natural language, many sentences can be paraphrased without changing the main idea. Code and math are less forgiving. A missing minus sign, wrong variable, changed type, renamed method, swapped argument, or altered indentation can change behavior. A proof step may depend on a symbol that appeared many lines earlier. A command may fail because one flag is wrong.

For long-context code and math tasks, the memory system must preserve exact syntax while still supporting larger reasoning. It must know the local surface form and the broader dependency. A model that remembers only the intention of a function may miss the actual signature. A model that remembers only a theorem's gist may misuse a condition. Exact syntax is the ground that makes higher-level reasoning accountable.

4. Citations, quotations, and source lines need provenance

evidence

A long-context answer is weaker when it cannot say where its evidence came from. In research, law, finance, and document analysis, source identity is part of the answer. The model must not only remember a claim; it must remember which paper, filing, page, clause, table, quote, or line supports it.

This is why attribution and retrieval belong inside long-context evaluation. If the answer is correct but the citation is wrong, the memory is not reliable. If the model merges two sources, the synthesis may be false. Exact provenance lets users inspect the support, catch source mixing, and decide whether the answer deserves trust.

5. Time and order can be exact facts

timeline

Sometimes exactness is not about a word or number. It is about order. A symptom before medication means something different from a symptom after medication. A robot observation before an action may be stale after the action. A user instruction before a correction should not override the correction. A video frame before contact is different from a frame after contact.

Long-context memory must preserve the ordering of state changes when the order changes the interpretation. Dates, timestamps, event boundaries, edit order, conversation turns, treatment sequences, and action-result pairs can be exact facts. Compressing a timeline into unordered facts can destroy the reason the context was long in the first place.

6. Boundaries define the object of attention

boundary

A boundary can be the difference between correct and wrong memory. In documents, the boundary may be a quoted span, table cell, section, clause, or footnote. In code, it may be a function body, diff hunk, class, or generated file. In vision, it may be the edge of an object, cell, lesion, sign, face, or region. In video, it may be the start or end of an event.

If the boundary is wrong, the model may retrieve too much, too little, or the neighboring thing. That creates subtle errors: a table value attached to the wrong row, a clause exception attached to the wrong obligation, a code comment treated as executable behavior, a visual object merged with the background, or an event attributed to the wrong actor.

7. Exactness and compression have to cooperate

balance

The answer is not to keep everything exact forever. That is too expensive and too noisy. The answer is layered memory. Broad context can be compressed into summaries or latent state, while exact anchors remain available for the details that cannot be safely paraphrased. The model should know when to use gist and when to return to the source.

A useful pattern is summary plus pointer. The system can remember that a contract has a payment exception, but it should preserve a path back to the exact clause. It can remember that a patient's kidney function worsened, but preserve exact lab values and dates. It can remember that a module owns authentication, but preserve exact symbols and tests. Compression gives scale; exact anchors give trust.

TOPIC 04

What can be compressed

Compression is safe only when the details being removed would not change the later decision. The question is not "can we make it shorter?" The question is "what can vary without changing what the system should do?"

Long context becomes usable when low-value detail can shrink. Repeated background, familiar boilerplate, stable facts, redundant examples, repeated visual frames, old tool chatter, and already-settled context do not always need to occupy full memory. But compression becomes dangerous when it removes the detail that later controls the answer. A good system compresses the predictable parts while preserving exact anchors and paths back to evidence.

The first-principles distinction is between harmless variation and answer-changing variation. If ten paragraphs all say the same policy in slightly different words, the repeated wording can often become one stable summary. If one paragraph contains an exception, that exception cannot be swallowed by the summary. If many video frames show no change, they can be collapsed into a stable state. If one frame shows contact, crossing, falling, or handoff, that transition must remain available.

1. Repetition can compress into stable state

repetition

Repeated context is one of the safest things to compress. A conversation may restate the same preference several times. A codebase may repeat the same project pattern. A long document may repeat background definitions. A video may show the same room for hundreds of frames. Once the system has enough evidence that the state is stable, it can store the stable state rather than every repeated instance.

The danger is compressing before checking for exceptions. Repetition creates expectation, but long-context tasks often hinge on the one place where the pattern breaks. The right compression keeps the stable pattern and marks the outlier. It should remember "most sections follow this rule, except this clause," not erase the exception into the average.

2. Background can compress when it only supports orientation

background

Some context helps the model understand the setting but does not need exact recall. A paper's general motivation, a company's broad business description, a project's ordinary folder layout, a patient's long stable history, or a scene's static background may give orientation. Once orientation is established, the full surface detail can often shrink.

This does not mean background is useless. It means background often belongs in a lower-resolution memory unless the question asks for it directly. The system should know the setting well enough to interpret new evidence, but it should spend exact memory on the pieces that can change the outcome: values, sources, dependencies, exceptions, and state changes.

3. Familiar structure can compress into a schema

schema

Many long inputs contain familiar structure. Code has modules, imports, tests, and configuration. Contracts have parties, definitions, obligations, exceptions, and dates. Clinical records have visits, medications, labs, findings, and plans. Scientific papers have methods, results, limitations, and claims. Once the structure is recognized, the system can store a schema rather than treating every line as equally new.

A schema is useful because it says where to look and what kind of information belongs there. It compresses the form while leaving slots for exact anchors. For example, a contract schema can compress ordinary boilerplate while preserving unusual obligations. A code schema can compress familiar framework layout while preserving changed interfaces. A clinical schema can compress routine note structure while preserving abnormal values and treatment changes.

4. Video can compress stable frames but not decisive transitions

video

Video creates enormous context because adjacent frames are often similar. If nothing important changes, many frames can be represented as one stable visual state. The model does not need every pixel of every frame to know that the object remained on the table or the person kept walking down the hallway.

The hard part is detecting the frames that should not compress away. Contact, object transfer, falling, scene cuts, gaze shifts, lane changes, collisions, and tool use can be brief but decisive. A useful video memory compresses static stretches while preserving event boundaries, object identity, and the moment state changed.

5. Conversations can compress history into live commitments

dialogue

A long conversation may contain many messages that no longer matter in full. The useful memory is often a compact set of live commitments: what the user wants, what constraints are active, what has already been tried, what decisions were made, and what remains unresolved. The transcript can be long while the active state is much smaller.

Compression fails when it keeps stale instructions or drops recent corrections. The system should compress finished exploration, outdated branches, and repeated preferences, but preserve the current task state and the latest controlling instruction. The summary must answer: what should still guide the next response?

6. Code can compress common patterns, not exact interfaces

code

In a codebase, familiar scaffolding can compress. The model does not need every route, test, or helper in full if they follow a repeated local pattern. It can store the pattern and retrieve exact files when the edit needs them. This is how a model can work across large projects without reading every token at full resolution.

But exact interfaces, changed files, failing tests, command outputs, dependency edges, and user constraints should stay available. A summary that says "standard service pattern" is helpful only if the model can still retrieve the exact signature, import path, and behavior when editing. Code compression should reduce the search space, not replace evidence with vague confidence.

7. Medicine and science can compress stable history, not evidence provenance

evidence

In medicine, a long stable history may compress into baseline state, but abnormal values, allergies, dosages, dates, and treatment responses need precision. In science, standard background can compress, but methods, parameters, measurements, failures, and provenance must remain connected to results. In both cases, compression should preserve why the conclusion is justified.

The safe pattern is baseline plus exceptions. The system can remember that a condition is chronic and stable, but it must preserve the measurements that show a change. It can remember that a paper uses a standard method, but it must preserve the parameter or assumption that makes the result comparable or not comparable to another paper.

8. Compression needs a way back to detail

pointer

The best long-context compression is rarely a dead-end summary. It should leave a pointer back to exact evidence. The compressed memory says what is broadly true, while the pointer says where to recover the exact span, frame, file, clause, value, or result if the current question needs it.

This is the link between compression and retrieval. Compression makes context manageable; retrieval restores detail when precision matters. Without pointers, compression turns evidence into rumor. With pointers, compression becomes an index into the past.

TOPIC 05

Retrieval versus remembering

Not every useful fact needs to stay in active memory. Some facts should stay live because they constantly shape behavior. Other facts should be fetched only when the current question needs their exact evidence.

Long-context design is partly a placement problem. The system has to decide what belongs in the model's immediate working state, what belongs in a compressed memory, what belongs in an external index, and what should be retrieved on demand. Keeping everything active is expensive and distracting. Retrieving everything too late can miss context that should have guided the reasoning from the start.

The practical difference is simple. Remembering keeps information continuously available. Retrieval brings information back when a query, plan, or uncertainty calls for it. A useful long-context system needs both. It should remember the current state, active constraints, and high-level map, while retrieving exact clauses, source spans, code definitions, lab trends, video events, and prior tool results when they become decisive.

1. Active memory is for information that keeps steering behavior

active

Some information should remain live because many later steps depend on it. In a conversation, this includes the user's current goal, constraints, preferences, and latest correction. In an agent task, it includes current world state, completed actions, failed attempts, open subgoals, and safety limits. In a code task, it includes the active files, failing tests, intended behavior, and interface changes already made.

Active memory should be small enough to stay usable. If it grows into a transcript of everything, the model loses the ability to tell what is currently controlling the task. The active state should answer: what must guide the next action even before any retrieval happens?

2. Retrieval is for exact evidence that may become relevant later

evidence

Many facts are too specific to keep active all the time, but too important to lose. A contract clause, table row, function definition, citation, lab result, video frame, error message, or experimental parameter may matter only when the current question points toward it. These belong in retrievable memory with enough indexing to find them again.

Retrieval lets the system keep a broad map in active memory and recover detail only when needed. The map may say "payment terms have exceptions." Retrieval brings back the exact exception. The map may say "authentication changed." Retrieval brings back the modified file and tests. The map may say "kidney function worsened." Retrieval brings back dates, values, and units.

3. Similarity is useful, but not the same as relevance

relevance

A retrieval system often starts from similarity: find the passages or frames that look most related to the query. That helps, but long-context reasoning often needs a stricter idea of relevance. The deciding evidence may be an exception, a prior correction, a source line, a small visual cue, or a procedural rule that does not look like the question on the surface.

The failure mode is retrieving something plausible but wrong. A similar clause without the exception, an old helper with the wrong interface, a normal lab value from the wrong date, or a repeated video action by the wrong actor can all look relevant. Good retrieval asks what evidence is needed to decide the question, not only what text or image is nearest in embedding space.

4. Retrieval needs query formation, not just storage

query

The model must know what to ask memory for. A vague query gets vague evidence. A wrong query gets the wrong span. In code, the model may need to query by symbol, caller, failing test, or error trace. In documents, it may need to query by entity, date, clause type, contradiction, or citation. In video, it may need to query by object, event, motion, or time range.

This means retrieval is part of reasoning. The system should form a query from the actual uncertainty in the task. If it is unsure which rule controls payment, retrieve clauses and exceptions. If it is unsure why a test fails, retrieve the trace and relevant definitions. If it is unsure whether a patient trend changed, retrieve the time-ordered values rather than a general summary.

5. Retrieved evidence must be bound to the answer

grounding

Retrieval is not finished when evidence is fetched. The model must bind the evidence to the answer correctly. It should know which source produced the fact, which entity the fact refers to, whether the fact is current or stale, and whether the retrieved span actually supports the claim being made.

This is where citation, attribution, and source tracking matter. A model that retrieves the right passage but answers from a different passage has failed. A model that cites one source while using a fact from another has failed. The behavior should show that retrieval changed the answer for the right reason and that the supporting evidence can be inspected.

6. Retrieval can refresh procedures, not only facts

procedure

Some long-context tasks fail because the model drifts away from the process it is supposed to follow. It may start with the right instructions but forget the checklist, scoring rule, coding convention, safety constraint, or reasoning procedure after many steps. Retrieval can bring back the procedure at the moment it is needed.

This is different from retrieving a fact. A procedural retrieval tells the model how to continue. In an agent, it may retrieve the current plan or tool policy. In code, it may retrieve the repo's testing rule. In analysis, it may retrieve the evaluation rubric. In medicine or law, it may retrieve the decision protocol that says which evidence must be checked before concluding.

7. Retrieval and remembering fail in opposite ways

failure

Remembering too much makes the model distracted. It treats old context as still active, follows stale instructions, or attends to nearby irrelevant material. Retrieving too little makes the model shallow. It answers from the current prompt, a summary, or general knowledge instead of finding the remote evidence. Retrieving the wrong thing makes the model confidently grounded in the wrong support.

The system needs a clear division of labor. Active memory carries the live state. Compressed memory carries broad structure. Retrieval brings back exact evidence. Forgetting prevents stale or irrelevant material from steering behavior. Good long-context work is the coordination of these roles, not the victory of one mechanism over the others.

TOPIC 06

Forgetting and stale context

Forgetting is not a failure of long context. Controlled forgetting is one of the things that makes long context usable.

A long-context system can fail by remembering too little, but it can also fail by remembering too much with the wrong authority. Old instructions, old plans, old observations, old retrieved passages, old code states, old diagnoses, and old assumptions may still be present in the context, but they should not always control the current answer. The question is not only what the model can recall. It is what the model should still obey.

This is a different kind of memory problem. The system may need to preserve stale information as history while removing its power over the present. An old plan can explain why a path was tried, but it should not override a newer decision. An old robot observation can explain past action, but it should not define the current world. An old code error can explain a debugging path, but it should not be treated as still failing after the test passes.

1. Stale context is old information with too much authority

authority

Staleness is not the same as age. Some old information remains important for a long time: a legal definition, a user preference, a safety rule, a diagnosis, a source citation, or a project architecture decision. Other information becomes stale quickly: a temporary plan, an intermediate guess, a failed command, a scene observation before an action, or a retrieved passage that later turned out to be irrelevant.

The key question is whether the information should still influence behavior. A long-context system should tag memory by authority, not only by recency. Some old facts stay active. Some new facts are low value. Some old facts become historical evidence. Some facts should be actively suppressed because they pull the model toward a wrong answer.

2. Conversations need correction to override earlier direction

dialogue

Long conversations often include changed instructions. The user may reject a plan, narrow the scope, correct a term, change tone, or say that an earlier direction is no longer wanted. The model fails when it treats the earlier instruction and the later correction as equal evidence.

The useful memory is not the full list of messages. It is the current contract of the conversation: active goal, active constraints, latest corrections, open questions, and completed work. Earlier messages may remain useful as history, but they should lose control when a later message explicitly changes the task. The model should remember that the older path existed without continuing to follow it.

3. Agents and robotics need world-state invalidation

state

Agent memory becomes stale when the world changes. A file was edited. A command succeeded. A browser page navigated. A tool returned new data. A robot moved. An object was picked up. A door closed. In these settings, old observations can be dangerous because they describe a world that no longer exists.

The memory system needs invalidation. It should know which facts were true before an action and which facts remain true after it. It should keep action-result pairs so the system can explain how state changed, but it should not act from the pre-action state. Good long-context agents maintain a live state model, not only a long transcript of observations.

4. Code work needs stale-error and stale-interface control

code

In coding sessions, stale context appears as old errors, old file contents, old test results, and old interfaces. A model may keep trying to fix an error that was already resolved, or edit against a function signature that changed ten minutes ago. The longer the session, the more likely old code state can interfere with current code state.

The solution is to treat command output and file reads as time-stamped evidence. A failing test is active until a later test result replaces it. A file summary is active until the file changes. A plan is active until the user or evidence changes it. The model needs to know which observations are current and which are only part of the debugging history.

5. Retrieval needs decay, contradiction handling, and source status

retrieval

Retrieved context can go stale too. A passage may be from an old version of a document. A previous search result may be superseded by a later source. A similar passage may have been retrieved before the model understood the real question. If the system keeps retrieved text active without checking status, retrieval becomes a source of interference.

A retrieved item should carry status: source, time, scope, confidence, and whether later evidence contradicted it. If newer evidence overrides it, the old item may remain as history but should lose authority. This matters in legal, financial, medical, scientific, and software settings where source version and date can change the answer.

6. Medicine and law need history without false currentness

risk

In medicine, a past diagnosis, medication, symptom, or lab abnormality may be important history, but it may not describe the current patient state. In law or finance, an old clause, price, filing, regulation, or contract version may matter for provenance, but a newer version may control the current decision.

The model must separate historical truth from current truth. "This was true then" is different from "this is true now." A long patient record, legal record, or financial record should preserve the timeline so older facts can inform interpretation without being mistaken for active conditions or active obligations.

7. Forgetting can mean demotion, not deletion

demotion

A system does not always need to erase stale information. Often it should demote it. The old fact remains retrievable as history, but it stops shaping the default answer. This is important because stale context can still explain why something happened, why an action was taken, or why a later correction mattered.

Demotion is more precise than deletion. A stale plan can move from active plan to abandoned plan. A failed hypothesis can move from candidate explanation to ruled-out explanation. A completed task can move from current goal to done work. A prior observation can move from current state to earlier state. The memory is still there, but its role has changed.

8. The model should prove it knows what is live

test

Forgetting should be tested directly. Give the model an old instruction and a later correction, then ask what it should do now. Give an agent an old observation and a later action that changes the world, then ask for the current state. Give a code model an old failing test and a later passing test, then ask what remains broken. Give a patient timeline with resolved and active issues, then ask which facts are current.

The proof is not that the model can recall every old fact. The proof is that it assigns the right status to each fact: active, historical, superseded, contradicted, completed, failed, or irrelevant. A long-context system has real memory only when it can separate memory from authority.

TOPIC 07

Timeline and state

Some long contexts are not mainly long because they contain many facts. They are long because the facts change over time.

A timeline is more than a list. It says what happened first, what happened next, what lasted, what ended, what caused what, and what is true now. A state is the current result of that history. Long-context systems fail when they remember facts but lose the transitions that made those facts meaningful.

This is why time and state are central to long context across modalities. A conversation has corrections and commitments. A codebase has edits and test results. A video has motion and events. An agent has observations and actions. A patient has symptoms, treatments, and trends. A legal or financial record has versions, deadlines, filings, and obligations. A scientific process has experiments, revisions, failures, and causal claims. In all of these cases, the question is not only "what appeared?" It is "what state did the sequence produce?"

1. Order changes meaning

order

The same facts can imply different answers when their order changes. A correction after an instruction controls the conversation differently from a correction before the instruction. A symptom before medication means something different from a symptom after medication. A code failure before a patch has a different status from a failure after the patch. A video object moving before a collision carries different evidence from the same object position after the collision.

Long context therefore needs order-sensitive memory. It is not enough to remember that all the facts occurred somewhere. The model must preserve the sequence that makes them interpretable. When order is lost, the model can produce a fluent answer that belongs to the wrong moment.

2. State is the compressed result of history

state

State is what remains true after the sequence has unfolded. It is a compact memory of history, but it is not a loose summary. It must preserve the parts of the past that determine the present. In an agent task, state includes what has been tried, what changed, and what constraints are active. In a patient record, state includes current condition, recent trend, active medications, and unresolved risks. In code, state includes the current file contents, current test results, and current interface assumptions.

A good state representation lets the model act without rereading everything at full resolution, while still knowing where to retrieve exact history. The state says what is live now. The timeline explains how it became live.

3. Duration matters, not only event order

duration

Some facts matter because of how long they last. A symptom for one hour is different from a symptom for three months. A robot contact lasting one frame is different from sustained pressure. A user preference stated once may be weaker than a stable preference repeated across tasks. A market condition that lasts one day is different from a trend across quarters.

Long-context memory should preserve duration when duration changes interpretation. This is why time-series and sequence models care about gaps, irregular observations, and explicit state durations. The distance between events can be evidence. A model that flattens time into order alone may miss the difference between a brief anomaly and a persistent change.

4. Causality needs action-result pairs

causality

In many domains, the important structure is not just what happened, but what caused what. An agent clicked a button and the page changed. A patch was applied and the test passed. A patient began a treatment and a lab trend improved. A policy changed and a financial metric shifted. A video action caused an object to move.

The memory unit should often be an action-result pair or cause-effect link. Without that link, the model may remember both events but fail to understand their relation. This matters for planning because future action depends on knowing which past actions produced which changes.

5. Video and robotics need state through continuous change

embodied

Video and robotics make the state problem visible. Objects move, hands contact surfaces, tools change position, scenes cut, and actions unfold over time. A single frame may show a state, but the task often depends on the transition: before contact, during contact, after contact; before pickup, during motion, after placement.

For robotics, the model must also preserve physical constraints. Pose, location, contact, object identity, and action consequences are not optional details. A stale state can produce unsafe behavior. Long context here means maintaining a current world model from a stream of observations and actions.

6. Documents also have time

documents

It is easy to think of documents as static, but long document work often contains time. Contracts have effective dates, renewal periods, deadlines, exceptions, and amendment order. Financial records have filings, reporting periods, restatements, and changing assumptions. Scientific papers have experimental sequence, method revisions, ablations, and claims that depend on previous results.

A document model that ignores timeline may retrieve the right text but apply it to the wrong period. It may use an old contract term after an amendment, compare measurements from incompatible conditions, or merge quarterly results across different reporting windows. Source and time have to travel together.

7. Conversation state is a live contract

conversation

A long conversation creates a live contract between user and system. The current task is the result of many turns: goals, constraints, preferences, corrections, completed steps, rejected directions, and unresolved questions. The model must know which parts of the conversation still bind the next response.

This is why raw transcript memory is not enough. The model needs a state object: current goal, current constraints, latest user preference, files touched, actions taken, validation status, and next planned step. The transcript is evidence. The state is what should guide behavior now.

8. Tests should ask for current state, not only past facts

test

Timeline and state need their own behavior tests. Ask what is true now after a sequence of updates. Ask which instruction is active after a correction. Ask whether a symptom is current or historical. Ask what file interface is valid after edits. Ask where an object is after a sequence of video events. Ask what plan remains after some actions fail and others succeed.

These tests expose whether the model can compute state from history. A model that merely recalls facts may list everything that happened. A model with state memory can say which facts still matter, which have been superseded, and what action follows from the current situation.

TOPIC 08

Long-range dependencies

A long-range dependency exists when a distant fact changes the meaning of the current question. The hard part is not that the fact is far away. The hard part is knowing that the far-away fact is the one with authority.

Many long-context failures happen because the model answers from nearby context even though the deciding evidence appeared much earlier. The nearby sentence may be fluent, recent, and similar to the question, but the real answer may depend on an older definition, exception, commitment, source line, state change, or constraint. Long context is useful only if these remote dependencies remain reachable and can override local impressions.

A dependency is a relation, not just a remembered item. The model has to know that this clause limits that rule, this definition controls that term, this earlier user correction changes this later action, this function signature constrains this call site, this lab trend changes this diagnosis, or this video event explains this later state. The memory problem is therefore relational: which earlier thing controls which later thing?

1. Definitions create long-range meaning

definition

A word, variable, entity, role, or condition may be defined early and used much later. In a legal document, a defined term may control every later clause. In code, a type or interface definition may control distant call sites. In science, a method definition may determine how later results should be interpreted. In conversation, a user may define what they mean by a phrase and expect that meaning to hold.

The model fails when it treats later uses as ordinary surface strings instead of looking back to the definition. A long-context system should bind later mentions to earlier definitions when those definitions change interpretation. The dependency is not optional background; it is part of what the later phrase means.

2. Exceptions can dominate the general rule

exception

Long documents often state a broad rule and then narrow it later. The answer may depend less on the rule than on the exception. A contract can say payment is due in thirty days, then add an exception for disputed invoices. A policy can allow an action, then restrict it under a condition. A clinical guideline can recommend a treatment, then exclude patients with a specific risk.

A model that retrieves the general rule but misses the exception gives the wrong answer with strong evidence. That is why long-range dependency tests should include rules and exceptions separated by distance and distractors. The question is whether the system can let a small remote exception override a large nearby rule.

3. Code dependencies connect distant files

code

Code is built from long-range dependencies. A local edit may be constrained by a type in another file, a configuration value in another directory, a fixture in a test folder, a generated schema, or a behavior hidden behind an import. The answer is often not in the file being edited.

The model needs a dependency map: symbol to definition, call site to callee, test to fixture, config to runtime behavior, patch to affected paths. Without that map, it may make a local change that looks reasonable but breaks a distant contract. Long-context code understanding is less about reading many files and more about knowing which distant files constrain the current edit.

4. Conversations create commitments that survive distance

dialogue

In a long conversation, an earlier commitment can control much later behavior. The user may ask for a style, forbid an approach, choose a scope, approve a plan, reject jargon, or define what counts as done. Many turns later, that commitment may still matter even if the recent messages do not repeat it.

The model must distinguish durable commitments from transient discussion. A brainstormed idea should not become a permanent instruction. A firm user preference should. A correction should override older wording. The dependency is between the earlier commitment and the later response: does the later behavior honor the active agreement?

5. Video dependencies connect early events to later state

video

In video, a later frame may only make sense because of an earlier event. An object is missing because someone moved it. A person is on the ground because they fell earlier. A tool is dirty because it touched something. A door is open because a prior action opened it. The later state contains evidence, but the earlier event explains it.

The dependency unit may be an object track, event chain, action-result pair, or scene transition. A model that samples frames independently may see before and after states without understanding the link. Long-range video memory must preserve event causality, not only visual snapshots.

6. Medicine depends on trends, thresholds, and prior conditions

medicine

Medical reasoning often depends on evidence spread across time. A current value may be normal for one patient and alarming for another because of baseline. A symptom may matter because it followed a medication. A diagnosis may be constrained by allergies, prior conditions, family history, or earlier negative tests. The deciding fact may be remote but patient-specific.

The model needs to connect current questions to prior facts that change interpretation. A lab trend is a dependency across values. A contraindication is a dependency between treatment and patient history. A diagnosis is a dependency between symptoms, timing, tests, and prior conditions. Flattening the record into a summary can miss exactly the relation that matters.

7. Science depends on method-to-result chains

science

Scientific conclusions depend on earlier method choices. A result may only support a claim under a certain experimental condition. A measurement may only compare to another measurement if the sample, protocol, parameter, or instrument setting matches. A failure case may limit the conclusion even if the headline result looks strong.

The long-range dependency is the chain from setup to evidence to claim. If the model remembers the result but loses the method, it may overgeneralize. If it remembers the method but loses the limitation, it may treat a narrow finding as broad. Science memory must keep conclusions attached to the conditions that justify them.

8. Long-range dependency tests must defeat local guessing

test

A good test should make the nearby context tempting but insufficient. Put a general rule near the question and an exception far away. Put a familiar helper near the edit and the true interface in another file. Put a recent normal lab value near the prompt and a longer abnormal trend earlier. Put a later video state near the question and the causative event earlier.

The model passes only if the remote dependency changes the answer. This is stronger than asking for recall. It asks whether the model knows that the far-away item controls the current decision. The test should show that removing or altering the remote dependency changes the final answer in the expected direction.

TOPIC 09

Distractors and interference

A long context does not only add useful evidence. It also adds many wrong things that look useful. The model has to make the right memory win against nearby, recent, repeated, or similar distractors.

Interference is what happens when the wrong part of the past competes with the right part. A similar clause competes with the controlling clause. An old function competes with the new interface. A repeated video action competes with the one action that matters. A stale instruction competes with the latest correction. A normal lab value competes with the abnormal trend. The danger is not random noise; it is plausible wrong evidence.

This is why long context can get harder as it gets larger. More context gives the model more chances to find evidence, but also more chances to be pulled toward evidence that is close, recent, frequent, or semantically similar while not being decisive. Good long-context design must control this competition.

1. Similarity can hide the decisive difference

similarity

The wrong context is often similar to the right context. Two clauses may discuss the same obligation but differ in the exception. Two code helpers may share a name pattern but have different signatures. Two patients may share symptoms but differ in history. Two video events may involve the same actor but happen at different times. Similarity helps retrieve candidates, but it does not decide which candidate controls the answer.

The model must compare the difference that matters. Does this clause apply under the current condition? Does this helper match the call site? Does this lab value belong to the relevant date? Does this object track belong to the same object? The representation needs contrast, not just closeness.

2. Recency can overpower older controlling evidence

recency

Recent context is easy for a model to use, but recent does not always mean controlling. A later paragraph may restate a broad rule while an earlier paragraph contains the exception. A recent user message may mention an old plan while an earlier correction rejected it. A recent code file may call an interface whose definition sits far away.

A long-context system must decide authority separately from recency. Some newer facts should override older facts, as with corrections or state updates. But some older facts define the meaning of newer facts, as with definitions, contracts, interfaces, or constraints. The model should not use time position as a substitute for relevance.

3. Frequency can make common context look important

frequency

Repeated information can dominate memory even when it is not decisive. A boilerplate phrase appears in many contracts. A common code pattern appears in many files. A background object appears in every video frame. A general symptom appears across many visits. The model may over-weight what appears often and under-weight the rare fact that changes the answer.

This is the failure that compression is supposed to prevent. Common background should often shrink into a stable summary, while rare exceptions and state changes should be protected. The model needs to know that high frequency means "common," not necessarily "controlling."

4. Source mixing creates false synthesis

sources

When many documents are present, the model can mix facts across sources. It may attach a number from one paper to a claim from another, apply one contract's exception to another contract, merge two companies in a financial record, or cite the wrong source for a correct statement. This kind of interference is subtle because the final answer may sound coherent.

The fix is source-bound memory. Facts should carry their origin: document, page, table, file, commit, video segment, patient visit, experiment, or filing. Synthesis should combine sources deliberately while preserving which fact came from where. Without source identity, long context becomes a place where evidence can accidentally fuse.

5. Stale context interferes by sounding still active

stale

A stale instruction, plan, diagnosis, file summary, retrieval result, or world observation may be present in the context and still look plausible. The model may follow it because nothing in the surface text says "do not use this anymore." Stale context is dangerous because it is not false as history; it is false as current guidance.

The system needs status labels: active, historical, superseded, contradicted, failed, completed, or irrelevant. This lets the model keep history without letting history hijack the present. Forgetting and interference control are the same problem seen from two sides.

6. Multimodal distractors are often structural, not textual

modalities

In video and vision, distractors may be adjacent objects, repeated actions, background motion, scene cuts, reflections, or occlusions. In audio, they may be overlapping speakers, repeated phrases, background noise, or similar speaker voices. In robotics, they may be old object locations, partial observations, or actions whose effects are delayed.

These distractors require structure-aware memory. The model must track object identity, speaker identity, event boundaries, action results, and current state. A flat similarity match can retrieve the wrong frame, wrong speaker turn, or wrong object because it sees surface resemblance without preserving the underlying relation.

7. Training has to create pressure against collapse into gist

training

If training only rewards broad semantic answers, the model can learn to ignore exact differences. It may become good at saying what the context is generally about while failing the rare distinction. Distractor-heavy training creates pressure to keep contrast: same-looking but different items must remain separate.

Useful training tasks include contrastive pairs, hard negatives, source-swapped examples, stale-instruction tests, near-duplicate clauses, similar code symbols, repeated video actions, and timelines where one small difference changes the answer. The representation learns what must not collapse together by being punished when it merges those cases.

8. Tests should make the wrong answer tempting

test

A strong long-context test includes distractors that are plausible. It should not only ask whether the model can find a hidden fact in random filler. It should place similar but wrong facts nearby, make the true fact remote, repeat irrelevant evidence, include stale states, and require source identity.

The model passes when it chooses the evidence that actually controls the answer. It should explain why the distractor does not apply: wrong source, wrong date, wrong entity, wrong condition, stale state, superseded instruction, different object, or missing exception. This proves selection, not just recall.

TOPIC 10

Compression without losing the deciding detail

Compression is only useful if the detail that changes the answer survives. A smaller memory that forgets the exception, boundary, value, source, or state change is not efficient. It is wrong faster.

Every compression method makes a bet about what can be removed. A summary bets that the main idea is enough. A chunk bets that nearby tokens belong together. A recurrent state bets that history can be folded into a smaller vector. A sparse memory bets that only a few dimensions or slots matter. A latent representation bets that hidden variables can preserve what behavior needs. These bets are useful, but they must be tested against the thing the later decision depends on.

The central danger is averaging away the rare fact. Long contexts often contain many ordinary details and one decisive detail. A summary can smooth the exception into the general rule. A chunk can bury a value inside a large block. A recurrent state can dilute an early fact across many updates. A latent code can preserve broad topic but lose source identity. A sparse memory can select the common feature and drop the edge case. Good compression protects the details that would change the answer if removed.

1. Summaries should keep decision hooks, not only gist

summary

A summary is useful when it turns long context into a smaller map. But a weak summary keeps only what the passage is generally about. A strong summary keeps decision hooks: exceptions, dates, entities, open questions, source pointers, unresolved conflicts, abnormal values, changed state, and conditions under which the summary may fail.

For example, "the contract describes payment terms" is too weak if the later task is risk review. "Payment is due in thirty days except disputed invoices, see section 4.2" is better because it preserves the controlling exception and a route back to exact wording. Good summaries are not just shorter text. They are compressed control surfaces for later reasoning.

2. Chunks should respect meaning boundaries

chunks

Chunking is a common way to make long context manageable, but bad chunks split meaning or merge unrelated facts. If a definition is separated from its use, retrieval may find one without the other. If a table row is separated from its header, the value loses meaning. If a code function is split away from its signature, the model may misunderstand behavior. If a video event is cut before the state change, the memory misses the action.

A good chunk boundary follows the unit of use: claim plus evidence, clause plus exception, table row plus schema, function plus signature, action plus result, frame span plus event boundary, lab value plus date and unit. Chunking is not just a length operation. It is a decision about which details must travel together.

3. Recurrent state can carry history, but also dilute it

state

Recurrent and state-space memory can compress long history into a running state. This is powerful because the model does not need to attend over every past token. But each update risks overwriting, blurring, or diluting earlier evidence. A rare early fact may fade as many later ordinary updates pass through the same state.

The state update needs protection for facts that should persist. That may mean gates, slots, separate memory roles, refresh retrieval, or training tasks that force distant facts to remain usable. The test is direct: after many irrelevant updates, can the model still use the early fact that controls the answer?

4. Sparse memory must choose the right few things

sparse

Sparse memory reduces cost by activating only some dimensions, heads, tokens, slots, or retrieved items. The risk is selection error. If the sparse mechanism keeps frequent background and drops the rare exception, it makes the context cheaper by removing the evidence that mattered. If it activates the wrong expert, head, or slot, the model may reason from the wrong memory path.

Sparse compression works when the selection rule is aligned with the task. It should keep the few things that carry decision power: active constraints, exact anchors, source pointers, object tracks, abnormal trends, dependency edges, or state changes. Sparsity is not valuable because it is small. It is valuable when it spends capacity on the right distinctions.

5. Latent memory must preserve inspectable behavior

latent

Latent memory can represent long context in hidden variables rather than readable text. This allows compact, flexible state, especially across modalities. A latent code might carry a video scene, a patient trajectory, a codebase map, or a multimodal context. But hidden memory creates an accountability problem: users cannot inspect it directly.

The answer is behavioral inspection. The latent memory must still support exact recall when required, source grounding, state tracking, timeline reasoning, and resistance to distractors. If a latent state gives a plausible answer but cannot recover why, where, or under what condition, it may be compressing away trust. Latent compression needs tests that expose what survived inside the hidden state.

6. Compression should separate map, state, and evidence

layers

A useful long-context system often needs layered memory. The map says what exists and where to look. The state says what is currently true. The evidence stores exact spans, values, frames, files, clauses, or measurements. Compression becomes safer when these roles are separated instead of forcing one summary to do everything.

For a codebase, the map may describe modules, the state may describe current task and failing tests, and the evidence may be exact files and command outputs. For a patient record, the map may describe conditions, the state may describe current risk, and the evidence may be lab values and notes. For video, the map may describe scenes, the state may describe object locations, and the evidence may be event clips.

7. Compression should keep uncertainty visible

uncertainty

A compressed memory should not pretend to know what it only summarized loosely. It should preserve uncertainty, conflicts, missing information, and places where exact retrieval is required. If the summary hides uncertainty, the model may answer with false confidence because the compression removed the reason to hesitate.

This matters in medicine, science, law, finance, and code. A clinical summary should say when a value is missing or a diagnosis is uncertain. A scientific summary should preserve limitations and failed conditions. A legal summary should preserve disputed clauses. A code summary should preserve unverified assumptions and tests not yet run. Good compression tells the model when it must go back to evidence.

8. The compression test is a counterfactual

test

The best test asks what changes when the deciding detail is changed or removed. If the compressed memory still gives the same answer after the exception, value, boundary, source, or state change is altered, then the compression did not preserve the deciding detail. It may have preserved topic, but not control.

A strong compression benchmark compares full context, compressed memory, retrieved evidence, and counterfactual edits. It asks whether the model can answer correctly, cite the evidence, reject distractors, and change its answer when the preserved detail changes. This proves that compression kept the right information, not only that the output sounded reasonable.

TOPIC 11

Context as temporary model update

Context does not change the model's stored weights, but it can change the model's behavior for the current run. A document, example, instruction, retrieved span, or tool result can act like a temporary update to what the model believes, attends to, or is willing to do.

This is one reason long context is powerful. The model can adapt without training. It can read a new API, follow a user's style, use a contract's definitions, obey a project convention, incorporate a tool result, or reason from a new scientific paper. The change is temporary because it lasts only while the context remains active. But while active, it can steer behavior strongly.

This also makes long context risky. If context can act like an update, then bad context can act like a bad update. A stale instruction, wrong retrieved passage, misleading example, corrupted tool result, or source-mixed summary can temporarily push the model toward wrong behavior. The system needs to decide which context is allowed to update behavior, how strongly, and under what evidence.

1. Instructions update what the model should optimize for

instruction

An instruction changes the task for the current run. It tells the model what kind of answer to produce, what constraints to obey, what style to use, what sources to trust, and what counts as success. In a long conversation, these instructions accumulate and can be revised. The current behavior is shaped by the active instruction state.

The important distinction is active instruction versus historical instruction. A user preference that still applies should steer future answers. A rejected plan should not. A safety constraint may remain active across many turns. A formatting request may apply only to one artifact. Context as temporary update only works if the model knows which instructions still have authority.

2. Examples update the local rule

examples

Few-shot examples show the model the local mapping for the task. They can teach a label scheme, a writing style, a translation convention, a data format, a scoring rule, or a transformation pattern. The model may already know many possible behaviors, but examples choose the one that should be used now.

This is a temporary update because the model is not permanently retrained. It is conditioned. The risk is that examples can also teach the wrong rule if they are inconsistent, unrepresentative, or contradicted by later instructions. Long-context systems need to treat examples as evidence about the current task, not as permanent truth.

3. Documents update what is true inside the task world

documents

A document can define the local world the model should reason within. A contract defines terms and obligations. A policy defines allowed actions. A paper defines methods and claims. A code README defines project conventions. A meeting transcript defines decisions and owners. The model should not answer only from general prior knowledge when the document provides task-specific truth.

But document updates must be scoped. A contract's definition controls that contract, not every contract. A paper's assumption controls that experiment, not all science. A meeting decision controls that project, not all projects. Context should update behavior inside its source boundary. If scope is lost, the model overgeneralizes from local evidence.

4. Retrieved spans update the answer only if they are relevant

retrieval

Retrieval injects external evidence into the current context. That evidence can change the answer immediately. A retrieved clause can override a default interpretation. A retrieved function definition can change a code edit. A retrieved lab trend can change a clinical risk assessment. A retrieved video event can explain the current scene state.

The danger is treating retrieved text as authoritative merely because it was retrieved. Retrieval is a proposal, not proof. The model must still check source, date, scope, entity, condition, and contradiction. A retrieved span should update behavior only when it actually supports the current decision.

5. Tool outputs update the current state

tools

Tool results are especially strong temporary updates because they report external state. A test run says whether code currently passes. A search result supplies current evidence. A database query gives a value. A browser action changes the page. A robot sensor reports the world. These outputs should update the model's live state more strongly than guesses or old summaries.

Tool output also needs status. It can be outdated after another action. It can be partial. It can fail. It can refer to a different environment. The model should bind tool results to time, source, command, and scope. A command result is not just text; it is state evidence produced by an action.

6. Code context updates local conventions and interfaces

code

When a model reads a codebase, it should adapt to that codebase. It should learn local naming, architecture, imports, testing style, error handling, formatting, dependency boundaries, and generated files. This is temporary adaptation: the model behaves like it understands the project during the session.

The update must be evidence-bound. A convention in one folder may not apply elsewhere. An interface may change after an edit. A test result may supersede a previous assumption. Code context should update the model's behavior, but only through current files, current commands, and current repo-specific evidence.

7. Temporary updates need conflict resolution

conflict

Long contexts often contain conflicting updates. An earlier instruction conflicts with a later correction. A retrieved passage conflicts with another source. A document conflicts with general knowledge. A tool result conflicts with an old summary. A code file conflicts with a stale plan. The model must decide which update wins.

Conflict resolution needs rules: newer state can override older state; exact source can override vague summary; user correction can override previous assistant assumption; current tool output can override old guess; higher-priority constraints can override local examples. Without conflict handling, long context becomes a pile of competing updates.

8. Tests should show behavior changed because of context

test

A good test compares behavior with and without the context update. Give the model a contract definition and ask a later question that depends on it. Give it code conventions and ask for an edit. Give it examples and ask for the same transformation on a new item. Give it a tool result and ask what state is true now.

The model passes if the context changes behavior in the expected way and only within the right scope. It should not ignore the update, but it should not overgeneralize it either. The test proves controlled adaptation: context changes the current run without becoming an uncontrolled belief.

TOPIC 12

Training tasks that shape memory

A representation is shaped by pressure. The training task decides what information survives, what gets ignored, what becomes easy to retrieve, and what mistakes the model learns to avoid.

Architecture gives the model a possible memory mechanism, but training teaches the mechanism what to use it for. If the task rewards broad gist, the model learns broad gist. If the task rewards exact recovery after distance and distractors, the model learns to preserve exact anchors. If the task rewards future prediction, the model learns state. If the task rewards source-grounded answers, the model learns to keep provenance. Memory is not only stored; it is trained into shape.

This matters for long context because the model must learn many different pressures at once. It must compress without losing decisive detail, retrieve remote evidence, ignore stale context, resist distractors, track time, preserve identity, and adapt to temporary instructions. No single training task teaches all of that. A serious long-context system needs a mixture of tasks whose pressures match the behaviors it will be trusted to perform.

1. Masking teaches recovery of missing parts

masking

Masking hides part of the input and asks the model to predict it from the rest. This pressures the representation to carry enough surrounding information to reconstruct what is missing. In text, this can teach local grammar and document coherence. In code, it can teach syntax, names, and interface patterns. In video, it can teach what frame or patch is consistent with surrounding motion. In medicine or science, it can teach relationships among measurements, conditions, and outcomes.

For long context, masking becomes stronger when the missing part depends on distant evidence. Hide a clause whose meaning depends on an earlier definition. Hide a function call whose signature is defined in another file. Hide a later event whose cause appeared earlier. The model learns that some remote information must remain usable because otherwise the masked part cannot be recovered.

2. Prediction teaches state that carries into the future

prediction

Prediction asks the model to forecast what comes next. This pressures memory to keep whatever helps anticipate future state. In language, it may preserve topic, syntax, and intent. In video, it preserves motion and object state. In agents, it preserves action consequences. In patient records, it preserves trends and treatment response. In finance or science, it preserves temporal patterns and causal signals.

The important point is that prediction favors information with future value. If a detail never changes future behavior, the model can compress it away. If a small earlier fact changes what happens later, the model must preserve it. Prediction therefore trains a practical kind of memory: keep what makes the future less surprising.

3. Contrast teaches what must stay separate

contrast

Contrastive tasks match things that should be treated as the same and separate things that should remain different. They are useful because long-context failures often come from merging similar but different items. Similar drug names, near-duplicate clauses, related code symbols, repeated video actions, same-looking table rows, and source-swapped claims all need contrast.

The training pressure is direct: if two examples look similar but lead to different answers, the representation must keep their difference. This is how models learn that surface similarity is not enough. A contract clause with an exception is not the same as one without it. A function with a different argument order is not the same function. A lab value from a different date is not the same clinical evidence.

4. Retrieval training teaches evidence access

retrieval

Retrieval training teaches the model to ask for, select, and use the right remote evidence. The pressure is not only "find something related." It is "find the evidence that decides the answer." This matters when the right span is far away, quiet, or less similar than a nearby distractor.

Good retrieval tasks include hard negatives, source identity, stale documents, similar clauses, code definitions across files, video events separated by time, and patient trends spread across visits. The model should learn both query formation and evidence binding: what to look for, where it came from, and how it changes the answer.

5. Teacher-student targets teach stable compression

distillation

Teacher-student training can ask a smaller or faster student to match a stronger teacher. In long context, the teacher may have access to fuller context, slower reasoning, or better retrieval. The student learns what parts of the context the teacher preserved when producing the answer.

This pressure is useful for compression because it can teach a compact memory to keep behaviorally important information. But it is only as good as the teacher target. If the teacher uses vague summaries or misses rare details, the student learns the same weakness. Distillation should preserve exact anchors, evidence use, state tracking, and rejection of distractors, not only final answer style.

6. Bottlenecks teach the model to spend memory carefully

bottleneck

A bottleneck limits what the model can carry: fewer tokens, smaller vocabularies, sparse dimensions, binary codes, compressed states, limited slots, or restricted retrieval budgets. This forces choice. The model cannot keep everything, so the training task determines what survives the bottleneck.

Bottlenecks are helpful only when the task rewards the right survival. If the model can pass with broad topic memory, the bottleneck will drop exact details. If the task requires exact values, source pointers, event boundaries, and long-range dependencies, the bottleneck must preserve those. A bottleneck is not automatically intelligent compression. It becomes intelligent only under the right pressure.

7. Reconstruction teaches enough detail to rebuild

reconstruct

Reconstruction asks the representation to rebuild the input or a meaningful part of it. This can preserve more detail than pure prediction because the model must keep information that may not be needed for the next token but is needed to recover the original structure. It matters for images, video, code, tables, medical records, and documents where exact structure carries meaning.

The risk is that reconstruction can waste capacity on surface detail if the task does not distinguish important detail from harmless variation. The best reconstruction tasks target the right level: rebuild object boundaries, table cells, code syntax, event order, source spans, or measurement values, not every irrelevant texture or repeated phrase.

8. Procedural training teaches how to use context

procedure

Some long-context failures are not failures of storage. They are failures of procedure. The model has the information but does not know how to inspect it, compare it, cite it, test it, or update state. Procedural training teaches operations: retrieve evidence before answering, compare sources, track active constraints, update a plan after failure, check for exceptions, and separate current from historical facts.

This is why procedural pretraining belongs in the long-context story. A model must learn not only facts, but habits of using facts. The procedure tells memory when to search, when to compress, when to distrust a distractor, when to ask for exact evidence, and when to mark old context as superseded.

9. Collapse prevention keeps units from becoming the same

collapse

Representations can collapse when many different inputs map to nearly the same internal state. Some collapse is useful: harmless variation should compress. But harmful collapse merges things that must remain distinct. In long context, harmful collapse merges sources, entities, dates, clauses, code symbols, object tracks, patient states, or experimental conditions.

Training must punish harmful collapse. Hard negatives, contrastive objectives, source-swapped examples, exact-copy tasks, boundary tests, and counterfactual edits all help. The goal is not to keep every difference. The goal is to keep the differences that change behavior.

10. Behavior tests close the loop

proof

The final pressure is evaluation. A training task may look reasonable but still produce memory that fails in use. Behavior tests ask whether the learned representation supports the intended action: exact recall, citation grounding, retrieval, state tracking, long-range dependency use, compression robustness, source separation, video event tracking, codebase consistency, or clinical timeline reasoning.

This closes the loop between training and purpose. If the model is meant to support legal review, test exceptions and source grounding. If it is meant to edit code, test exact symbols and runnable behavior. If it is meant to understand video, test event boundaries and object state. Training pressure should be judged by the behavior it creates.

TOPIC 13

Architecture choices

Architecture decides what kind of memory the model can afford. Training decides how that memory is used. Long-context design needs both: the mechanism must make the right memory operation possible, and the objective must make it worth learning.

There is no single best long-context architecture because there is no single memory job. Some tasks need exact access to a distant span. Some need compressed state across many steps. Some need fast streaming updates. Some need source-grounded retrieval. Some need event memory over video. Some need local precision for code or math. The architecture should match the memory role.

The useful question is not "attention or recurrence?" It is "which information needs direct access, which information can be summarized into state, which information should be retrieved from outside, which information needs exact pointers, and which information can be compressed into fewer units?" Most serious systems answer with a mixture.

1. Attention gives direct access, but direct access is expensive

attention

Attention is powerful because it lets the model compare one part of context with another. A later question can look back to an earlier definition, exception, quote, function signature, or event. This direct comparison is valuable for exact recall, long-range dependency, and source-grounded reasoning.

The cost is that attention over everything becomes expensive and noisy as context grows. Every token competes with many others. Distractors, repetition, and stale context can pull attention away from the deciding evidence. Attention is best used where direct access matters: exact spans, code syntax, citations, small exceptions, and places where the model must compare details rather than rely on compressed state.

2. Recurrence carries state forward

recurrence

Recurrent memory updates a state as new information arrives. This is natural for streams: conversations, agents, video, robotics, patient timelines, financial time series, and long-running code sessions. The model does not need to keep every past token equally active because the state carries the result of history forward.

The risk is loss. A recurrent state can overwrite early evidence, blur identities, or dilute rare details through many updates. It is good for live state and temporal continuity, but it needs safeguards for exact anchors and rare facts. In practice, recurrence works best when paired with retrieval or pointers back to source evidence.

3. State-space models compress history into a controlled process

state-space

State-space models treat memory as a system that evolves over time. They can be efficient for long sequences because they do not require full pairwise attention across all tokens. This makes them attractive for long streams, time series, continuous processes, and settings where the model needs a compact evolving state.

The key question is update geometry: what enters the state, what persists, what decays, and what gets overwritten? A state-space model is useful when history can be summarized into variables that preserve future behavior. It is weaker when the task needs exact retrieval of a rare span unless it is paired with an external memory or attention mechanism.

4. Retrieval extends memory outside the model

retrieval

Retrieval avoids forcing every detail into the active window or hidden state. It stores evidence externally and brings it back when needed. This is useful for documents, codebases, legal records, scientific corpora, patient histories, tool logs, and videos where the exact evidence may be large and only occasionally relevant.

The hard part is choosing what to retrieve and how to bind it to the answer. Retrieval must handle query formation, hard negatives, source identity, version, date, and scope. It is not a replacement for memory; it is one memory role. The active state must know when retrieval is needed, and the answer must show how the retrieved evidence was used.

5. Token and chunk compression change the sequence before memory sees it

compression

Another architectural move is to reduce the number of units. Better tokenization, learned chunking, sparse token selection, video token compression, and latent tokens all change what the model has to process. This can make long context cheaper before attention or recurrence even begins.

The risk is unit damage. If compression breaks a number, splits a function signature, merges a table row with the wrong header, drops a short video transition, or hides a legal exception, the later architecture cannot recover what was removed. Unit compression must be aligned with the use case, not just optimized for fewer tokens.

6. Hybrid models assign different memory jobs to different mechanisms

hybrid

Hybrid architectures are attractive because long context has several kinds of memory. Attention can handle exact comparison. Recurrence can carry live state. Retrieval can bring back remote evidence. Compression can reduce repeated background. Attribution can explain which spans mattered. A single mechanism is rarely best at all of these.

The design question becomes role assignment. What should stay in attention? What should become recurrent state? What should be stored externally? What should be compressed into latent units? What should remain explainable? Good hybrid design is not architectural decoration. It is a division of labor for memory.

7. Attribution turns memory use into something inspectable

attribution

Long-context systems need explanation because answers can be influenced by many distant pieces. Attribution methods ask which spans, tokens, heads, chunks, retrieved items, or states actually affected the answer. This matters because a model can output a correct answer for the wrong reason, or cite one source while using another.

Attribution is not only a debugging tool. It is part of memory design. If the system can show which evidence mattered, users can detect source mixing, stale context, distractors, and unsupported synthesis. Long context without inspectable evidence is hard to trust in code, law, medicine, science, and financial work.

8. Architecture should be chosen by failure mode

diagnosis

Different failures point to different architectural fixes. If the model cannot access a distant exact span, retrieval or attention may be needed. If it loses current state in a long stream, recurrence or state-space memory may help. If cost explodes on video, token compression or event-level units may matter. If it mixes sources, provenance and attribution are needed. If it follows stale context, active-state tracking and authority labels are needed.

This is the practical way to read architecture papers in the theme. Each paper is not just proposing a mechanism. It is making a claim about which memory failure matters and which architectural role can fix it.

TOPIC 14

Long context across modalities

Long context is not a text-only problem. Every modality has streams, units, compression, evidence, state, and interference. What changes is the form of memory.

The same first-principles questions repeat across domains. What is the memory unit? What must remain exact? What can be compressed? What should be retrieved? What has become stale? What timeline or state must be preserved? What distractors can fool the model? What behavior proves the memory worked?

The mistake is to assume the data type decides the answer. Text does not always mean tokens. Vision does not always mean patches. Video does not always mean frames. Medicine does not always mean notes. Code does not always mean files. The right representation is chosen by the use case: the thing the later system must compare, copy, predict, explain, or act on.

1. Text and documents: claims, definitions, sources, and exceptions

text

Text context becomes long through documents, books, papers, contracts, chats, reports, and email threads. The useful memory units may be tokens, sentences, paragraphs, claims, definitions, citations, table rows, obligations, or argument steps. The core problem is that not every sentence is equally alive. A small exception, source, date, or definition can control a much later answer.

The failure modes are source mixing, lost exceptions, over-compression into gist, wrong citation, stale instruction following, and answering from nearby text instead of deciding evidence. The proof behavior is source-grounded answering: the model can retrieve the exact support, apply the right scope, and explain why distractors do not control the answer.

2. Code: symbols, dependencies, patches, and behavior

code

Code context becomes long because behavior is distributed. The current edit may depend on a type definition, test fixture, config file, generated schema, import path, old patch, or command result. The memory unit may be a symbol, function, class, dependency edge, file, diff hunk, error trace, test case, or runtime behavior.

The failure modes are stale file state, wrong symbol identity, local edits that break distant contracts, summaries that hide exact signatures, and old test failures treated as current. The proof behavior is runnable consistency: the model edits against current evidence, preserves exact syntax, and validates behavior with commands or tests.

3. Vision: patches, objects, regions, and relations

vision

Vision context is often described in patches, but patches are not always the useful unit. A task may need letters on a sign, a table cell, an object boundary, a lesion, a face, an organ region, a molecule part, or a relation between objects. The correct visual unit is set by the question: classify the scene, read text, segment an object, detect a small abnormality, or reason about layout.

The failure modes are boundary loss, background dominance, object merging, missed small regions, and treating spatially adjacent things as the same thing. The proof behavior is task-specific: OCR reads exact characters, segmentation preserves boundaries, detection finds small objects, medical imaging preserves abnormal regions, and visual reasoning keeps relations straight.

4. Video: frames, clips, object tracks, events, and state changes

video

Video context becomes long because meaning unfolds over time. A frame may show what is visible, but the important fact may be motion, contact, transfer, gaze, fall, scene cut, or state transition. The unit may be a frame, clip, object track, action phase, event, trajectory, or scene.

The failure modes are losing event boundaries, confusing repeated actions, missing brief transitions, failing to track object identity, and answering from a later state without knowing the earlier cause. The proof behavior is temporal: the model knows what changed, when it changed, which object changed, and what state is true after the event.

5. Audio and speech: speakers, turns, timing, and acoustic evidence

audio

Audio context becomes long through speech, meetings, calls, music, sound events, and environmental streams. The useful unit may be a phoneme, word, speaker turn, segment, topic shift, acoustic event, pause, overlap, or prosodic cue. A transcript alone may miss timing, speaker identity, confidence, tone, and overlapping speech.

The failure modes are speaker confusion, losing commitments from earlier turns, treating uncertain transcription as exact, missing short sound events, and flattening timing into text. The proof behavior depends on the task: diarization preserves speaker identity, meeting memory preserves decisions and owners, speech recognition preserves exact words when needed, and acoustic monitoring preserves event timing.

6. Agents and robotics: observations, actions, results, and world state

agents

Agent and robotics context becomes long because the system acts and the world changes. The useful unit is not just a message or frame. It may be an observation, action, tool result, failed attempt, plan step, constraint, robot pose, object location, contact state, or safety rule.

The failure modes are repeated failed actions, stale world state, forgotten constraints, wrong tool results, unsafe action from old observations, and losing the current plan. The proof behavior is operational: the agent knows what is true now, what was already tried, what changed after each action, and what it should do next under current constraints.

7. Medicine: values, visits, trends, treatments, and patient state

medicine

Medical context becomes long because health is a timeline. The useful unit may be a lab value with units, symptom, medication, dose, allergy, visit, imaging finding, diagnosis, treatment response, gene variant, or patient state. Exactness and chronology both matter.

The failure modes are wrong dosage, missing allergy, unit confusion, treating resolved symptoms as current, losing abnormal trends, and summarizing away uncertainty. The proof behavior is clinical timeline reasoning: the model distinguishes current from historical facts, preserves thresholds and units, and grounds conclusions in patient-specific evidence.

8. Law and finance: clauses, parties, filings, amounts, and obligations

risk

Legal and financial context becomes long through contracts, filings, regulations, transactions, ledgers, reports, and correspondence. The useful unit may be a clause, party, obligation, exception, amount, filing, date, reporting period, transaction, citation, or cross-reference.

The failure modes are source mixing, outdated version use, wrong amount, missed exception, party confusion, and broad summaries that hide controlling language. The proof behavior is exact and auditable: the model identifies the source, applies the right version and condition, and keeps numbers, dates, parties, and obligations distinct.

9. Science: methods, measurements, assumptions, and provenance

science

Scientific context becomes long because evidence has method and provenance. The useful unit may be an experiment, sample, measurement, protocol, parameter, instrument setting, hypothesis, result, limitation, failure case, or causal chain. A result without conditions can be misleading.

The failure modes are overgeneralizing from narrow results, comparing incompatible methods, losing failed conditions, and merging claims across papers. The proof behavior is provenance-aware synthesis: the model knows what was measured, how it was measured, under what assumptions, and how that supports or limits the conclusion.

PLAIN MAP

Long context as memory across scales

When there is too much stuff, the model has to remember the right stuff. A short prompt is easy because the model can look at most of it at once. A long prompt is different. It may contain important facts, useless filler, old instructions, new instructions, repeated details, numbers, names, events in order, and small clues that only matter much later.

So the real problem is not simply how to fit more tokens. The real problem is how the model knows what to keep, what to shrink, what to look up again, and what to ignore. A model that can hold 128K tokens but cannot find the one sentence that answers the question has not solved long context. It only has a larger desk covered with more paper.

Everyday picture

You read a 500-page book and someone asks a question. Bad memory remembers only the last page. Another bad memory remembers every sentence but cannot tell which sentence matters. Good memory knows that the rule was introduced early, the exception appeared later, and the answer depends on one exact example.

Core question

What must remain available later, in what form, and at what cost? Sometimes the answer is an exact token. Sometimes it is a summary. Sometimes it is an old instruction. Sometimes it is a video moment, a duration, a trajectory, or the current state of a task.

Failure mode

The model may remember nearby junk, forget remote evidence, compress away the deciding detail, lose event order, retrieve a similar but wrong span, or preserve all the words while failing to use the right one.

1. The question appears at many sizes

scale

Context is not one size. The same memory question repeats from tiny pieces to whole tasks. At the smallest scale, a number or code symbol may be split into awkward pieces. At the word scale, the model needs useful token boundaries. At the sentence scale, one line may carry the rule while the next ten lines are filler. At the document scale, the answer may depend on something far away. At the conversation scale, an old instruction may still be active while other old details are stale. At the video or time-series scale, order, duration, and change matter more than any single frame.

That is why Theme 18 papers look spread out. Tokenization papers, position papers, retrieval papers, recurrent-memory papers, video-token papers, and time-process papers are all asking the same everyday question at different sizes: what is the right thing to remember here?

2. Keeping everything is not understanding

selection

A long window can make the model worse if it treats all text as equally alive. More context means more chances to be distracted. A useful memory system must separate live evidence from background noise. It must know that an exact number may need to stay exact, a repeated paragraph can be summarized, a stale instruction should be ignored, and a buried exception may matter more than the nearby sentence.

The simple test is this: after distance, distractors, compression, and time shifts, can the model still recover the exact thing that changes the answer? If not, the model has length but not memory control.

3. Some memory should be exact, and some should be compressed

compression

Not every part of a long input deserves the same treatment. Names, numbers, quotes, source lines, legal clauses, code symbols, and event order often need exact memory. Repeated examples, background description, and low-value filler can often be compressed. The hard part is deciding which is which before the final question is known.

This is why token and chunk papers matter. They are not just making things smaller. They are asking what unit should carry meaning. A bad unit wastes space or breaks meaning. A good unit gives the model a smaller object that still preserves the thing it will need later.

4. Memory is also time

order and state

Some long context is not a long document. It is a process. A video changes over time. A patient changes over time. A browser session changes after each click. A codebase changes after each edit. In these cases, the model must remember not only what appeared, but what happened first, what lasted, what changed, and what state is true now.

This is the simple link between long-context papers and time-series papers. Both ask how to carry the right state forward. A model that forgets duration, order, or state can give an answer that sounds plausible but belongs to the wrong moment.

5. Retrieval is not the same as similarity

evidence

The right old piece is not always the most similar old piece. A question may need a quiet exception, a small visual cue, a procedural rule, or a sentence that only matters because of a later constraint. Flat similarity can miss that. Good retrieval asks what evidence is logically needed, not just what text looks nearby in meaning.

That is also why attribution matters. After the answer, we want to know which old span actually drove it. If the model cannot point back to the deciding evidence, we do not know whether it used memory or guessed from a summary.

6. The deeper link to science

representation

This is the same pattern that appears across science. A gas has too many molecules to track one by one, so physics keeps pressure, temperature, density, and energy. A patient has too many measurements, so medicine looks for the hidden condition and its trajectory. A long prompt has too many tokens, so a model needs a memory representation that keeps what predicts later behavior and drops what does not.

Statistical physics gives the clean analogy: many tiny details can be replaced by larger-scale variables when those variables preserve the behavior we care about. Long-context modeling is doing a similar thing for text, video, code, tools, and time. It asks which details wash out, which details survive, and which larger memory object still lets the system answer correctly.

CROSS-DOMAIN FRAME

Long context is controlled memory across a stream

Long-context modeling is not storing more tokens. It is deciding what past information remains usable for future decisions.

This is the same first-principles move across documents, codebases, conversations, videos, agents, patient records, legal files, financial records, and scientific logs. The surface form changes, but the memory problem stays the same: what should be kept exactly, what can be compressed, what should be retrieved later, what has become stale, and what long-range dependency changes the answer?

A long-context system is therefore a memory policy. It has to decide what the unit of memory is, where the memory lives, how it is updated, how it is searched, and when it should stop influencing the answer. A million-token window without those decisions is only a large storage area. The hard part is making the stored past usable at the moment it matters.

Keep

Facts that can change the answer later: names, numbers, rules, exceptions, commitments, state changes, source lines, event order, symptoms, actions, and evidence.

Compress

Repeated background, low-value examples, redundant dialogue, familiar boilerplate, long descriptions, and stable context that can become a smaller state summary.

Retrieve

Remote evidence when the current question needs it: a clause, function definition, earlier user correction, lab trend, video moment, tool result, or experimental note.

Forget

Stale instructions, superseded plans, irrelevant distractors, false leads, old environment state, and context that would pull the model toward the wrong answer.

1. Text and documents: memory of claims, evidence, and exceptions

documents

A long report, contract, paper, book, or email thread is not just a bag of paragraphs. It has claims, definitions, entities, evidence, caveats, citations, contradictions, and conclusions. The model must remember which sentence introduced the rule, which later sentence created the exception, and which exact quote or number supports the answer.

The memory unit may be a passage, claim, citation, table row, named entity, obligation, or argument step. Summaries help when the question is broad. Exact spans matter when the question asks who said what, what the number was, which citation supports a claim, or whether two parts contradict each other.

2. Codebases: memory of symbols, dependencies, and prior edits

code

A code task is long because the answer is distributed across files. A function call depends on its definition. A test failure depends on a fixture. A configuration value changes runtime behavior. A previous edit may have introduced a new interface that later files must respect.

Here, memory must preserve exact names, paths, imports, types, APIs, errors, tests, and architectural decisions. A vague summary of the codebase is not enough. The model needs a working map: which file owns what, which symbol calls what, which assumptions have already changed, and which commands proved the behavior.

3. Conversations: memory of commitments, corrections, and live task state

dialogue

A long conversation contains preferences, decisions, corrections, abandoned ideas, active goals, and stale context. Good memory does not treat every old message as equally active. If the user corrects a direction, the correction should override the earlier plan. If a preference is stable, it should persist. If a detail was only relevant to a finished task, it should fade.

The memory unit is often not a message. It is a commitment, constraint, decision, open question, tool result, or current state of work. A long-context assistant fails when it remembers an old instruction too strongly, forgets a recent correction, or cannot tell whether a detail is still live.

4. Video: memory of objects, events, and state changes over time

video

Video is long because meaning unfolds. A frame can show what is visible, but not always what is happening. The important fact may be a transition: a person starts to fall, an animal changes behavior, a tool touches an object, a car enters a lane, or a scene changes after a cut.

The memory unit may be a frame, clip, action phase, object track, event, or trajectory. A model that remembers frames without event structure can miss why a later frame matters. A model that compresses too aggressively may lose the one moment where the state changed.

5. Agents and robotics: memory of observations, actions, and consequences

agents

Agent context is long because the world changes after each action. The model must remember what it tried, what failed, what tool returned, what files changed, what the environment looked like, and what plan is still valid. Robotics adds physical state: pose, contact, force, object location, and safety constraints.

The memory unit is operational: observation, action, tool result, error, state update, plan step, or constraint. The key question is not whether the transcript is present. It is whether the system knows the current state and can avoid repeating failed actions or acting on stale information.

6. Medicine: memory of timeline, trend, and patient state

medicine

A patient record is long because health is a process. A lab value means different things depending on baseline, trend, treatment, symptoms, timing, missing tests, and prior diagnoses. A note may mention uncertainty. A scan may show anatomy. A medication may explain a later measurement.

The memory unit may be a value, threshold, visit, symptom, medication, finding, diagnosis, or disease trajectory. Exact memory matters for dosage, dates, allergies, genes, and abnormal values. Compressed memory matters for stable background and long histories. The model must preserve both exact evidence and evolving patient state.

7. Legal and finance: memory of exact obligations and long-range conditions

risk

Legal and financial context is long because small clauses, dates, exceptions, amounts, and named parties can control the final answer. The relevant span may be far from the question. A later exception may override an earlier rule. A number may be meaningful only with its date, source, and condition.

The memory unit may be a clause, party, amount, date, filing, citation, condition, obligation, or exception. Summaries are useful for orientation, but exact retrieval is required when the answer depends on a specific phrase, number, or cross-reference.

8. Science: memory of provenance, method, and causal chain

science

Scientific context is long because evidence accumulates through experiments, measurements, instruments, protocols, hypotheses, failures, revisions, and comparisons. A result may matter only because of how it was produced. A measurement without provenance can be misleading.

The memory unit may be an experiment, sample, parameter, observation, method step, instrument setting, hypothesis, or result. Good memory preserves provenance and causal chain: what was measured, under what conditions, with what method, and how that changes the conclusion.

TOPIC 15

Testing long context

A long-context system is only as good as the behavior that proves the past stayed usable.

The simplest test is to hide one fact deep in a long input and ask for it later. That is useful, but it is not enough. A model can pass a needle-in-haystack test while still failing real long-context work. Real work asks the model to preserve exact facts, ignore distractors, track order, merge evidence across places, update state after events, and explain which old information changed the answer.

So evaluation should not ask only whether the model can store more text. It should ask whether the model used the right past information for the right reason, at the right time, without being pulled away by similar but wrong context. The test has to match the memory promise.

A good long-context test is built from the same ingredients as the memory problem itself. It chooses a unit, creates distance, adds tempting distractors, changes state, compresses or retrieves evidence, and then asks for behavior that would be impossible without the right memory. The test should make the cheap answer fail.

1. Exact recall tests: did the identity survive?

precision

Some long-context failures are not subtle. The model changes a name, rounds a number, swaps two dates, loses a citation, invents a source line, or confuses two similar symbols. These mistakes matter because many domains are identity-sensitive. A drug name, account number, legal amount, function name, gene variant, theorem symbol, or table value cannot be replaced by something close.

The test should place exact items far apart, surround them with similar items, and ask for the deciding one. In code, this means exact file paths, function names, imports, arguments, errors, and test names. In medicine, it means dosage, allergies, lab values, units, dates, and abnormal thresholds. In legal or finance, it means parties, clauses, amounts, deadlines, exceptions, and citations. Passing requires more than gist memory. The representation must keep identity where identity changes the answer.

2. Order tests: did the model preserve what happened when?

timeline

A long context often contains facts that are only meaningful in sequence. The model must know what was true before, what changed later, and what state is true now. If a user first asks for one plan and later corrects it, the correction wins. If a patient had a symptom before a medication and improved after it, the timing matters. If a robot moved an object, the old location is stale. If a code edit changed an interface, older call sites may now be wrong.

Order tests should ask questions whose answer changes when two events are swapped. They should include updates, reversals, cancellations, repeated states, and old facts that are no longer active. This exposes whether the model has only remembered content or whether it has remembered a timeline. Long context without timeline control can sound coherent while answering from the wrong moment.

3. Distractor tests: can it ignore similar but wrong evidence?

selection

The hardest long-context errors often come from nearby or similar distractors. A document may contain two clauses with almost the same wording but different exceptions. A codebase may contain an old helper and a new helper with similar names. A video may include repeated actions where only one instance matters. A medical record may contain normal and abnormal values for the same lab at different times.

A good test places plausible wrong evidence near the question and the right evidence far away. The model passes only if it selects the span that is logically relevant, not merely semantically similar. This is where retrieval quality matters. Similarity search can find related text; long-context reasoning needs the evidence that changes the answer.

4. Compression tests: did shrinking preserve the deciding detail?

compression

Many long-context methods compress history into summaries, chunks, latent states, recurrent memory, sparse dimensions, or smaller token sets. Compression is useful only if it removes low-value detail while preserving answer-changing information. A summary that says "the contract discusses payment terms" is useless if the question depends on the one exception that changes payment timing.

Compression tests should compare answers from full context, compressed context, and retrieved context. They should ask whether the model keeps rare exceptions, exact values, event order, and cross-references after compression. In video, the test asks whether the key state change survived fewer tokens. In code, it asks whether a summary preserved the interface that later files must obey. In medicine, it asks whether a compressed patient history kept the abnormal trend rather than only the diagnosis label.

5. Retrieval tests: can it bring back the remote cause?

retrieval

Long context is not useful if the model cannot bring the right old information into the current decision. Retrieval tests should ask for answers that require a distant span, not just nearby wording. The retrieved item may be a definition introduced early, an exception buried in the middle, a prior tool result, a table row, a video event, a line of code, or an earlier user correction.

The test should also require evidence. If the model gives the right answer but points to the wrong support, it may have guessed. For documents, this means citing the exact passage. For code, it means naming the file and symbol. For science, it means preserving method and provenance. For legal work, it means locating the clause or cross-reference. The behavior proves not only that the answer is right, but that memory was used correctly.

6. State-tracking tests: does it know what is live now?

state

In agents, conversations, robotics, and coding sessions, the context is a changing state, not a static document. The model must remember completed actions, failed actions, current constraints, active goals, files already edited, observations already made, and plans that were replaced. The question is not "what appeared in the transcript?" The question is "what should still control behavior now?"

State-tracking tests should include stale instructions, superseded plans, partial progress, environment changes, and repeated attempts. A strong model avoids repeating failed work, respects the latest constraint, carries forward useful results, and drops old context that no longer applies. This is the behavioral version of forgetting: not erasing the past, but preventing the wrong past from steering the present.

7. Cross-document tests: can it combine without mixing up?

synthesis

Many real tasks require multiple sources. The model may need to compare two contracts, connect a paper's method to its result, reconcile a meeting transcript with a task list, or trace a financial claim across filings. The failure mode is source mixing: an answer takes a fact from one document and assigns it to another, or merges two similar entities into one.

Cross-document tests should ask for comparisons, contradictions, dependencies, and provenance. The model must keep source boundaries while building a larger conclusion. That is the balance: combine evidence when the task requires synthesis, but preserve enough identity to know which source contributed which fact.

8. Modality-specific tests: does the test respect the form of memory?

modalities

Different modalities expose different memory failures. Text tests should check claims, quotes, citations, and exceptions. Code tests should check symbols, dependencies, exact edits, and runnable behavior. Video tests should check objects, tracks, actions, scene changes, and event order. Medical tests should check timelines, trends, thresholds, and patient-specific facts. Robotics tests should check physical state, action consequences, and safety constraints.

The test should be shaped like the use case. A video model should not be judged only by answering a text question about a single frame. A code model should not be judged only by explaining a file without running behavior. A medical model should not be judged only by summarizing notes without preserving exact values and timing. The evidence of memory must appear in the behavior the system will actually perform.

TOPIC 16

Failure modes

A long-context failure is not just "the model forgot." The failure can come from the wrong unit, wrong retrieval, wrong authority, wrong source, wrong time, wrong compression, or wrong test.

Long context creates more ways to be wrong because the model has more evidence, more distractors, more stale states, more source boundaries, and more opportunities to confuse what is nearby with what is controlling. A useful failure analysis should name the broken memory operation. Did the model fail to store the detail? Store it but fail to retrieve it? Retrieve it but bind it to the wrong source? Preserve the fact but lose order? Compress away the exception? Treat stale context as active?

This diagnostic view matters because different failures need different fixes. A lost exact value may need exact anchors. A wrong citation may need provenance tracking. A stale instruction may need authority labels. A bad code edit may need dependency mapping. A video error may need object tracks and event boundaries. Calling all of these "long context failed" hides the real design problem.

1. Lost in the middle: the evidence is present but unused

access

Lost-in-the-middle behavior happens when the deciding evidence is inside the context but the model does not use it. The model may answer from the beginning, the end, or a nearby passage instead. This is not the same as missing information. The information was provided, but access failed.

The fix may involve better position handling, retrieval, attention patterns, chunking, or training with distance. The test should place the controlling fact at different positions and surround it with plausible distractors. If performance changes mainly with position rather than relevance, the system does not have stable long-context access.

2. Wrong retrieval: the system fetches plausible but non-controlling evidence

retrieval

Wrong retrieval is dangerous because it gives the model something to cite. The retrieved passage, frame, code file, lab value, or source may be related to the query but not the evidence that decides the answer. This often happens with near-duplicate clauses, similar symbols, repeated video events, or values from the wrong date.

The fix is not only better embeddings. The retrieval system needs query formation, hard negatives, source identity, date and version tracking, and reasoning about conditions. Retrieval should be judged by whether it brings back the evidence that changes the answer, not merely evidence that looks related.

3. Source mixing: true facts are attached to the wrong origin

source

Source mixing happens when the model merges evidence across documents, files, patients, experiments, filings, or video segments. It may take a true number from one source and attach it to another claim. It may apply one contract's exception to another contract. It may cite one paper for a result from a different paper.

This failure is common in synthesis tasks because the answer sounds coherent. The fix is source-bound memory: facts carry provenance, version, scope, and source pointers. Tests should require comparisons and citations, then check whether each claim is attached to the correct source.

4. Stale authority: old context keeps controlling the answer

stale

Stale authority happens when old information remains too powerful. An earlier instruction overrides a later correction. An old world observation controls an agent after the world changed. An old failing test guides code work after a later passing run. An old document version controls a current legal or financial answer.

The fix is authority tracking. The model should mark memory as active, historical, superseded, contradicted, failed, completed, or irrelevant. The test should ask what is true now after updates, not only what appeared somewhere in the past.

5. Compression loss: the summary preserved topic but lost control

compression

Compression loss happens when a summary, chunk, latent state, sparse slot, or recurrent memory keeps the broad idea but loses the detail that changes the answer. The model remembers that a contract discusses payment, but not the exception. It remembers that a patient had kidney issues, but not the abnormal trend. It remembers a code module's purpose, but not the exact interface.

The fix is layered compression: broad map, current state, exact anchors, and pointers back to evidence. Tests should compare full context with compressed memory and use counterfactual edits to verify that the compressed memory still changes its answer when the deciding detail changes.

6. Temporal confusion: facts are remembered in the wrong order

time

Temporal confusion happens when the model recalls facts but assigns them to the wrong time, cause, or state. It treats historical symptoms as current, old instructions as active, pre-action observations as post-action state, or earlier code behavior as current behavior. The facts may be individually true while the conclusion is false.

The fix is timeline memory: event order, duration, action-result pairs, versioning, and current-state representation. Tests should swap event order, include state changes, and ask for current truth rather than a list of past facts.

7. Hallucinated evidence: the model fills gaps with fluent support

evidence

Hallucinated evidence is especially damaging in long context because the user expects the answer to be grounded in the provided material. The model may invent a quote, cite a non-existent section, claim a test was run, infer a lab value, or describe a video event that never happened. The output may match the general topic while missing the actual evidence.

The fix is evidence discipline. Answers should distinguish retrieved evidence, inferred conclusions, missing information, and uncertainty. Tests should require source spans, file names, command outputs, table rows, timestamps, or frame ranges. If the model cannot point to evidence, it should not present the claim as grounded.

8. Unit mismatch: the model stores the wrong kind of object

unit

Unit mismatch happens when the memory unit does not match the task. A paragraph summary is too coarse for exact citation. A frame sample is too coarse for brief contact. A token sequence is too low-level for an action phase. A file summary is too vague for a symbol-level edit. A patient-note summary is too broad for a dosage decision.

The fix is to choose units by behavior: claim, clause, table cell, function, dependency edge, object track, action, visit, lab trend, experiment, or source span. The test should expose whether the chosen unit preserves the boundary and identity that the task requires.

TOPIC 17

Cost and latency

Long context is expensive because memory has to be stored, searched, updated, moved, and used. More tokens are not free, and more tokens are not always better memory.

The cost problem is not only hardware cost. It is also decision cost. If the model must look across too much irrelevant context, the answer can become slower and worse. If a retrieval system fetches too much, the model must separate evidence from noise. If compression is too aggressive, the model becomes fast but loses the detail that matters. If everything stays active forever, stale information can keep interfering.

The central tradeoff is between availability and selectivity. Active context makes information immediately available but expensive and distracting. Compression makes memory cheaper but risks losing exact detail. Retrieval keeps evidence outside the active window but adds search latency and retrieval error. Recurrent or state-space memory carries state cheaply but may blur rare facts. A useful system chooses where each kind of memory should live.

1. Active context is fast to use but costly to maintain

active

Putting information in the active window gives the model direct access. That helps when exact comparison is needed: a quote, code signature, legal exception, table row, or recent user correction. But active context grows expensive as it gets longer. It also makes selection harder because every irrelevant token becomes another possible distraction.

The active window should be reserved for information that is likely to guide the next step: current goal, active constraints, current state, exact evidence being used now, and small context needed for immediate reasoning. Treating the full past as active state wastes capacity and makes stale context harder to control.

2. Retrieval reduces active cost but adds search risk

retrieval

Retrieval keeps large evidence stores outside the active window. This is useful for codebases, legal files, medical histories, scientific libraries, document collections, and video archives. The model can keep a map of what exists, then fetch exact evidence when the question needs it.

The tradeoff is latency and retrieval error. Search takes time. Wrong retrieval gives the model plausible but non-controlling evidence. Over-retrieval floods the window with noise. Under-retrieval leaves the answer shallow. Retrieval is efficient only when the system can ask precise questions and bind returned evidence to the answer.

3. Compression saves tokens but spends trust

compression

Compression can make long context affordable by shrinking repeated background, stable state, boilerplate, redundant frames, and familiar structure. But every compression step creates a trust question: what was removed, and could it change the answer? A summary with no pointer back to evidence is cheap but hard to audit.

The safe pattern is compression with exact anchors. Store broad summaries for orientation, but preserve pointers to clauses, code symbols, lab values, event frames, source spans, and command outputs. Compression should lower cost without cutting the route back to evidence.

4. Streaming latency depends on when units become stable

streaming

In streaming settings, the system cannot always wait for the whole input. Speech, video, sensors, agent logs, and live code sessions arrive over time. The latency question becomes: when is a memory unit stable enough to act on? A tokenizer may wait for a boundary. A video model may wait for an event to finish. An agent may wait for a tool result. A medical monitor may act when a threshold is crossed.

Lower latency often means acting with less context. Higher latency gives more evidence but may miss the moment to act. Good streaming memory updates as soon as the relevant unit becomes stable, while marking uncertainty when evidence is still incomplete.

5. Video and multimodal context make token budgets visible

multimodal

Video exposes the cost problem sharply because frames, patches, audio, text, and events can explode into huge sequences. Treating every patch of every frame as equally important is often wasteful. The useful memory may be an object track, event boundary, scene state, or short transition rather than a dense grid of frames.

Multimodal systems need adaptive spending. Use high resolution where details matter: text on a sign, object contact, a lesion boundary, a spoken correction, a small action. Use compressed state where the scene is stable. The memory budget should follow information value, not uniform sampling.

6. Code latency includes tool time and verification time

code

In code work, latency is not just model inference. It includes reading files, searching symbols, running tests, building the project, waiting for tools, and checking diffs. A model that answers quickly without current evidence may be faster in the moment but slower overall if it causes wrong edits.

The cost-aware strategy is selective verification. Keep active state for the current task, retrieve exact files and symbols when needed, run the smallest useful tests, and update memory from command results. The goal is not to avoid tool cost. The goal is to spend tool cost where it prevents expensive mistakes.

7. High-stakes domains need slower exactness at the right points

risk

Medicine, law, finance, and safety-critical robotics cannot treat speed as the only goal. Some details need exact retrieval, source checking, version checking, and uncertainty marking. A faster answer that loses a dosage, clause, date, contraindication, or object state is not a better answer.

The right cost tradeoff depends on action cost. A casual summary can tolerate broad compression. A legal conclusion, medication recommendation, financial claim, or robot action needs stronger evidence. Long-context systems should spend more memory and verification budget where mistakes are expensive.

8. The best system minimizes useless memory, not total memory

budget

The goal is not always to minimize tokens. It is to minimize memory that does not help behavior. Sometimes the correct answer needs a large exact span. Sometimes it needs only a compact state and one retrieved table row. Sometimes it needs a full code trace. Sometimes it needs a short video clip around an event boundary.

Cost-aware long context asks what memory is worth paying for. The answer depends on the downstream task, the cost of error, and the availability of verification. The best design spends memory where it preserves decision-changing information and cuts memory where it only adds noise.

TOPIC 18

Human workflow

Long context is valuable when it reduces the human's burden of rereading, cross-checking, remembering state, and hunting for evidence. It should make large work easier to control, not just make the model sound informed.

People use long-context systems because the material is too large to hold in working memory. A reader cannot keep every clause, citation, and table row in mind. A developer cannot track every file and test result at once. A doctor cannot manually compare every value across a long chart in every moment. A lawyer or analyst cannot safely merge many sources without provenance. A researcher cannot keep every method and limitation aligned across papers.

The system's job is therefore not only to answer. It should maintain orientation, preserve evidence, track current state, surface contradictions, make uncertainty visible, and help the human decide what to inspect next. Long-context memory should become a workflow tool.

1. Readers need maps plus exact passages

reading

For long documents, the human needs two things at once: a map of the material and access to exact passages. A map explains the structure: definitions, claims, sections, evidence, exceptions, conflicts, and conclusions. Exact passages support trust: the user can inspect the quote, clause, table row, or citation that controls the answer.

A poor long-context assistant gives a smooth summary and forces the user to hunt for support. A better one says what matters, why it matters, and where the evidence lives. It reduces rereading without removing auditability.

2. Coders need current state, not a pile of files

code

In software work, the human needs the assistant to know the live state of the repo: what was edited, which tests failed or passed, which files define the interface, what assumptions changed, and what remains risky. The value is not that the model read many files. The value is that it can help make the next correct edit.

Good workflow memory keeps exact code anchors and command evidence. It names files, symbols, diffs, tests, and errors. It avoids repeating failed attempts. It does not act on stale file summaries. It helps the developer verify behavior instead of only producing plausible code.

3. Doctors and clinical users need timeline and uncertainty

medicine

Clinical work is not just summarization. The human needs to know what is current, what is historical, what changed, what is missing, and which exact values support concern. A long-context medical system should surface trends, thresholds, dates, units, treatments, allergies, and unresolved uncertainty.

The workflow value is safe orientation. The system should make it easier to inspect the right evidence, not hide evidence behind a confident story. It should distinguish patient-specific facts from general knowledge and should preserve the path back to notes, labs, imaging findings, and medication history.

4. Lawyers and analysts need provenance and version control

risk

Legal and financial users work under source pressure. Which clause? Which version? Which filing? Which party? Which date? Which amount? Which exception? A long-context system must keep evidence tied to provenance and must not merge similar sources into one smooth answer.

The workflow value is controlled comparison. The system should show what changed across versions, where obligations differ, which source supports each claim, and which old source has been superseded. It should make the human's review faster while preserving the chain of evidence.

5. Researchers need synthesis without source mixing

research

Research workflows require both breadth and discipline. The system must compare papers, methods, assumptions, datasets, limitations, results, and failure cases. The risk is false synthesis: merging claims from different papers, overgeneralizing a narrow result, or losing the condition under which a method works.

Good long-context workflow memory keeps method-result-provenance chains. It can say which paper made which claim, under what setup, and how that relates to another paper. It helps the human see conceptual structure without erasing the evidence boundaries that make the synthesis trustworthy.

6. Agents need shared task state with the human

agents

Agent workflows are collaborative. The human needs to know what the agent believes is active, what it already tried, what changed, what failed, what it plans next, and what evidence it has. A long transcript is not enough; the human needs a live state that can be inspected and corrected.

The system should make state visible in its behavior. It should not repeat failed actions, hide uncertainty, or silently carry stale assumptions. When it changes plan, it should be because evidence changed. When it retrieves evidence, it should use it in a way the human can audit.

7. Video and multimodal users need event navigation

multimodal

For video, audio, and multimodal streams, humans need help navigating events. They may need to find the moment an object moved, a speaker made a commitment, a safety event occurred, a visual state changed, or a small sign or table cell appeared. The useful interface is not just a summary; it is a way to jump to evidence.

Long-context memory should preserve event boundaries, timestamps, object tracks, speaker turns, and source segments. The workflow improves when the model can say what happened and take the human to the moment where it happened.

8. Good workflow design keeps the human in control

control

The best long-context system does not ask the human to trust a giant hidden memory. It gives the human handles: current state, evidence pointers, unresolved questions, uncertainty, source boundaries, changed assumptions, and suggested next checks. It makes memory inspectable enough that the human can correct it.

This matters because long-context systems will be used on tasks where wrong memory is costly. A workflow that exposes memory state lets the human catch stale context, wrong retrieval, source mixing, and hallucinated evidence before they become decisions.

TOPIC 20

Final synthesis

Long-context research is not one problem. It is the problem of controlled memory across scale, time, modality, evidence, and action.

The simple story says long context means giving a model more tokens. The deeper story says long context means deciding what the past is allowed to become. Some past information becomes exact evidence. Some becomes compressed state. Some becomes a map for retrieval. Some becomes a temporary update to behavior. Some becomes historical context with no current authority. Some must be forgotten as guidance even if it remains retrievable as evidence.

This is why the papers in this theme do not look identical. A position-encoding paper, a tokenizer paper, a state-space paper, a retrieval paper, a span-attribution paper, a video-token paper, a diffusion paper, and an irregular-time paper are all working on different surfaces of the same object. They ask how information survives distance, compression, time, modality change, and interference.

1. Long context begins with purpose

purpose

The first question is always what the memory is for. A system does not need long context because the input is large. It needs long context because a later answer, action, prediction, or explanation depends on something earlier. The past is useful when it changes the future behavior in the right way.

This shifts evaluation away from maximum window size. The real question is decision continuity: did the system preserve the old fact, state, source, or event that should still control the current decision?

2. The unit is chosen by the use case

unit

The memory unit is not dictated by the data type. Text may need claims, clauses, citations, or commitments. Code may need symbols, dependencies, tests, and patches. Video may need object tracks and events. Medicine may need trends and patient state. Science may need method-result-provenance chains.

A good unit keeps together what the later system must use together. A bad unit splits meaning, merges sources, hides boundaries, or makes exact retrieval impossible. Unit choice is therefore a conceptual decision before it is an engineering detail.

3. Exactness and compression are partners

balance

Long context cannot keep everything exact forever, and it cannot compress everything into gist. It needs both. Exact anchors preserve names, numbers, syntax, sources, boundaries, and order. Compression removes repetition, stable background, boilerplate, redundant frames, and settled context.

The practical design is layered memory: map, state, evidence, and pointers. The map gives orientation. The state says what is true now. The evidence keeps exact support. The pointers allow compressed memory to return to detail when precision becomes necessary.

4. Retrieval, forgetting, and state decide authority

authority

Remembering is not enough. The system has to decide what remains active, what should be retrieved, what is stale, what is superseded, and what should stop influencing the answer. A fact can be true as history and false as current guidance. A retrieved passage can be related but not controlling.

This makes authority a central memory object. Long-context systems need to know which evidence controls the current decision and which evidence merely explains the past. Without authority tracking, more context creates more ways for old or wrong information to steer behavior.

5. Time turns memory into state

time

Many long contexts are processes. Conversations evolve. Code changes. Patients change. Videos unfold. Agents act. Documents get amended. Scientific evidence accumulates. In these cases, the model must know not only what facts appeared, but what sequence of changes produced the current state.

Timeline tells the model how facts changed. State tells the model what those changes mean now. Long context fails when it remembers facts but loses the order, duration, cause, or current status that makes those facts useful.

6. Architecture is memory role assignment

architecture

Attention, recurrence, state-space models, retrieval, compression, attribution, and hybrid designs each serve different memory roles. Attention supports direct comparison. Recurrence carries state. Retrieval restores remote evidence. Compression reduces cost. Attribution makes influence inspectable. Hybrid systems divide the work.

The right architecture is chosen by the failure it must prevent: lost evidence, stale state, excessive cost, source mixing, weak retrieval, temporal confusion, or compressed-away detail. The best design is not the one that stores the most. It is the one that supports the behavior the use case requires.

7. Training creates the pressure that shapes memory

training

The model learns what to preserve from the tasks it is trained on. Masking teaches recovery. Prediction teaches future-relevant state. Contrast teaches separation. Retrieval training teaches evidence access. Teacher-student targets teach compact behavior. Bottlenecks teach selection. Reconstruction teaches detail. Procedural training teaches how to use context.

Training should match the intended use. If the system must handle legal exceptions, train and test exceptions. If it must edit code, train and test exact symbols and runnable behavior. If it must track video, train and test event state. Memory becomes reliable only under pressure that rewards the right survival.

8. The final proof is behavior

proof

The final test is not whether the context was large or the answer fluent. It is whether the model uses the right past information for the right reason. The test should add distance, distractors, compression, state changes, source boundaries, and counterfactual edits. Then it should ask whether the answer changes when the controlling detail changes.

This is the clean ending for the theme: long-context memory is successful when it preserves the past in the form needed for future behavior, and when that preservation can be inspected through evidence, state, and tests.

SYNTHESIS

Five ways the papers rethink context

1. Position and tokenization define what long context even means

sequence interface

Before a model can reason over a long sequence, it has to represent the sequence. These papers ask whether positions, numbers, token boundaries, and chunks should be fixed artifacts or adaptive parts of the model.

ICLR 2026MrRoPE
MrRoPE recasts RoPE extension as mixed-radix conversion and reports 128K-context recall without fine-tuning. The first-principles idea is that positional extrapolation is a number-system problem: the model must encode far positions without losing resolution at near positions. Training-free extension matters because every fine-tuning pass for longer context is expensive and fragile.
ICML 2026PoPE
PoPE separates what a token is from where it appears inside positional encodings. That separation matters because content and position are different sources of evidence. If they are entangled too tightly, length extrapolation can fail when familiar content appears at unfamiliar distances.
ICML 2026Incremental BPE
Incremental BPE emits tokens as soon as token boundaries are fixed, reducing latency on streaming and pathological inputs. The paper treats tokenization as infrastructure for live context. In streaming settings, waiting for the full suffix before deciding a token boundary creates avoidable delay.
ICML 2026BitTokens
BitTokens encodes numbers as IEEE 754 floating-point single tokens to reduce arithmetic reasoning overhead. This is context compression at the symbol level. If a number consumes many subword tokens, the model spends context and attention recovering a value that could have been represented directly.
ICML 2026dnaHNet
dnaHNet reports tokenizer-free latent chunking with quadratic FLOP reductions and major inference speedups. It asks whether the model should discover chunks instead of inheriting them from a tokenizer. Adaptive chunking can compress long sequences while preserving units that matter for prediction.
ICML 2026VideoFlexTok
VideoFlexTok enables long video generation with far fewer tokens than comparable 3D grid tokenizers. Video exposes the token-budget problem brutally: frame grids explode sequence length. A useful tokenizer has to spend tokens where motion and content require detail, not uniformly across space and time.

2. Memory can be attention, recurrence, state, or a hybrid of roles

memory architecture

This cluster asks what kind of mechanism should carry information forward. Attention gives direct access but grows expensive; recurrence and state-space models compress history but can lose detail. Hybrid designs split those responsibilities.

ICML 2026Expressivity-Efficiency Tradeoffs for Hybrid Sequence Models
Expressivity-Efficiency Tradeoffs for Hybrid Sequence Models proves that pure SSMs and pure Transformers hit different parameter or working-memory bottlenecks on synthetic sequence tasks. The paper gives a theoretical reason for hybrid models: different mechanisms are good at different memory roles. Long-context design should assign roles instead of asking one architecture to do everything.
ICML 2026MuonSSM
MuonSSM stabilizes SSM memory updates with momentum pathways and Newton-Schulz-conditioned low-rank injections. State-space memory is attractive because it compresses long history, but unstable updates destroy that memory. The paper treats memory update geometry as the core object to control.
ICML 2026Robust Filter Attention
Robust Filter Attention treats tokens as noisy observations of a latent SDE trajectory and attention weights as precision-weighted consistency. It reframes attention as state estimation rather than soft lookup. A distant token should matter when it is consistent evidence about the latent process, not merely because it is similar.
ICML 2026Fisher Memory Dynamics
Fisher Memory Dynamics models recurrent memory as time-resolved Fisher information moving through interacting subpopulations. The contribution is a diagnostic view of memory: not just whether the model remembers, but where information density travels over time. That helps explain when recurrent systems retain or diffuse evidence.
ICML 2026Focus and Dilution
Focus and Dilution uses gradient-flow analysis and experiments to explain recurrent attention cycles. It describes a training dynamic where attention can alternately concentrate useful signal and dilute it across context. Long-context training is therefore not only architecture choice, but a stage-wise process that shapes how attention learns to revisit information.
ICML 2026Diffract
Diffract removes many head updates without quality loss and can improve accuracy by rewinding low-importance heads. It treats attention heads as update-bearing memory modules with different marginal value. Long-context efficiency can come from not updating every head at every step when some heads add little or harmful state change.

3. Long context needs retrieval and explanation, not just storage

evidence access

A larger context window can make the model worse if it cannot select the right evidence. These papers build ways to retrieve procedural guidance, choose logically necessary cues, and explain which spans drive a decision.

ICML 2026TG-RAG
TG-RAG reduces cognitive drift by retrieving procedural directives during reasoning rather than relying on static context. The model may know the task at the start and still drift after many steps. Interrupt-retrieve-generate control refreshes the procedure at the moment it is needed.
ICML 2026SCOPE
SCOPE identifies semantic submergence, where flat similarity filtering misses subtle but logically necessary video cues. The point is that relevance is not the same as similarity. Long multimodal context needs evidence selection based on the reasoning relation, not just nearest-neighbor retrieval.
ICML 2026FlashTrace
FlashTrace uses span-wise aggregation for much faster attribution on long-context retrieval and reasoning tasks. Long context makes explanation expensive because there are too many tokens to score individually. Span attribution gives a tractable way to ask which parts of the context actually influenced the answer.
ICML 2026Context-Parameter Equivalence
Context-Parameter Equivalence maps context effects in modern Transformer blocks to rank-1 MLP patches and RMSNorm-scale patches. It says in-context information can behave like a temporary weight update. That is important because context is not passive text; it can act like a localized model edit during inference.
ICML 2026DiSC
DiSC distills teacher and student distributions conditioned on different context segments without explicit generation during training. It treats context segmentation as part of knowledge transfer. The model should learn which portion of an adaptation corpus updates knowledge while preserving instruction following and reasoning behavior.
ICML 2026Procedural Pretraining
Procedural Pretraining separates reasoning-structure acquisition from semantic corpus learning and improves context recall. It suggests that long-context skill depends on abstract operators learned before ordinary knowledge. A model that has learned how to manipulate procedures can use later context more reliably.

4. Continuous time and event structure are long context in another form

temporal processes

Some long contexts are not documents. They are irregular observations, durations, latent trajectories, and events that change a population over time. These papers preserve the time process instead of flattening it into a fixed sequence.

ICML 2026SDEVI
SDEVI performs variational inference over discrete observations while preserving an underlying continuous SDE process. It keeps the generative process continuous even when the data arrives as samples. That matters for irregular time series where the gaps between observations carry information.
ICML 2026CoCLD
CoCLD aligns individual latent trajectories with population distribution shifts under sparse irregular observations. The problem is two-level memory: each individual has a path, and the population itself moves. The model has to connect local trajectories to global drift.
ICML 2026RED-HDP-HMM
RED-HDP-HMM extends HDP-HMMs with recurrent explicit durations for more expressive temporal segmentation. State identity alone is not enough; how long the system remains in a state can be predictive. Explicit duration modeling gives the sequence memory a clock.
ICML 2026TESS
TESS converts qualitative event text into distribution shift, volatility, shape, and lag primitives for forecasting. It translates language into temporal operators. That is long-context reasoning across modalities: text events become structured changes in a forecasting process.

5. Generation can update many positions, modalities, or latent spaces at once

generation process

The final cluster loosens the left-to-right text assumption. If generation is diffusion-like, multimodal, or latent, the model can choose a broader update frontier and a different interface between continuous and discrete information.

ICML 2026Unifying Masked Diffusion Models
Unifying Masked Diffusion Models treats generation order as part of the model objective rather than a fixed decoding policy. This is a major shift from autoregressive context. The model can learn which positions to reveal or refine, so sequence order becomes a learned generative process.
ICML 2026Recurrent Diffusion Sampler
Recurrent Diffusion Sampler preserves recurrent depth while updating a wider front of token positions under a fixed wall-clock budget. It asks how to spend inference time: more sequential depth, or broader parallel refinement. The method tries to keep recurrence while avoiding one-token-at-a-time narrowness.
ICML 2026LatentLM
LatentLM integrates image, audio, video, text, and code generation and understanding through latent language modeling. It treats long context as cross-modal latent state rather than only text tokens. A unified latent interface lets different modalities share a memory and generation substrate.
FIELD READ

What this theme says about ICML and ICLR

The conference direction is clear: long context is shifting from brute-force attention over more tokens to structured memory. The winning questions are about interfaces, compression, recurrence, retrieval, temporal dynamics, and generation order.

That matters for agents and benchmarks because real tasks are long for many reasons. A browser session is long because state changes. A code task is long because evidence is distributed across files and tests. A video is long because motion unfolds. A scientific time series is long because observations are irregular. The model needs memory designs that fit those shapes, not just a larger context window.

CONCEPT BRIDGES

Where to read the larger pattern

Long context is memory design

A larger window matters only if the needed state remains usable later. Context length is useful when it preserves the evidence that changes the next decision.

Retrieval is a missing-evidence claim

Retrieval decides what evidence is absent from the current context. A retrieved span is useful when it fills a real gap, not when it merely looks similar.

Compression preserves or destroys capability

Context compression is useful only if the deciding information survives. The test is whether the shortened state still supports the behavior the full context supported.
