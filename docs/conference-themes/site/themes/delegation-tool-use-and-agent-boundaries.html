Delegation, tool use, and agent boundaries

An agent is not just a model that writes longer answers. It is a model placed inside an action system: it can observe state, call tools, change files, query services, ask other models, request human input, and sometimes affect the world. The hard question is which authority it should have, when, and under what checks.

Problem

Tool access turns language into action. That creates new capability, but also new failure modes: wrong tool, wrong arguments, stale state, unsafe side effects, hidden cost, and unclear responsibility.

Approaches

Use permission scopes, reversible steps, tool budgets, verifiers, sandboxes, audit traces, state packets, specialist models, human approval, and route-specific evaluation.

Connecting read

Uncertainty decides whether the model knows enough. Escalation decides where to route risk. Delegation decides what outside actor or tool receives authority.

CORE

A tool is borrowed authority

A model with a tool is no longer only producing text. It is borrowing a piece of the outside system's authority.

A search tool borrows access to current or private evidence. A shell borrows authority over files, processes, and sometimes networks. A code runner borrows execution. A browser borrows a user's interface to the web. A database tool borrows access to records. A verifier borrows the authority of a formal or executable check. A human handoff borrows judgment, responsibility, and domain expertise.

This is why agent design cannot be reduced to "let the model call tools." The meaningful question is what the model is allowed to observe, what it is allowed to change, what must be reversible, what must be approved, what must be logged, and what check must pass before the action counts as done. Delegation is the architecture of borrowed authority.

The paper evidence fits this framing. ParetoPO studies accuracy versus tool cost. CyberGym and SandboxEscapeBench show that executable environments reveal abilities and risks that text tasks hide. THOR, VERINA, HERO, MoCA, and WebDevJudge show that tool and verifier feedback can become part of the reasoning loop. State, memory, and uncertainty papers explain what must be carried across steps so delegation does not lose context.

First-principles line
A model's capability is not only what it knows internally, but what it is allowed to observe, call, change, verify, and delegate.

TOPIC 01

Answering and acting are different jobs

A language answer can be wrong. An action can also change state, spend money, leak data, break files, or create obligations.

Many benchmark tasks ask for an answer. Agent tasks ask for a change in the world: fix the bug, file the form, configure the service, exploit the vulnerability, update the website, teach the student, triage the patient, or control the robot. Once the task becomes action, the model needs stronger boundaries than ordinary text generation.

The first boundary is reversibility. Reading a document is different from editing it. Running a local test is different from deploying. Drafting an email is different from sending it. Searching the web is different from submitting a form. A good agent system separates observe, propose, check, and commit. It should not treat all tool calls as equal.

CyberGym and SandboxEscapeBench make this vivid because security behavior cannot be judged by a plausible paragraph. The agent has to operate in an environment. But the same environment that proves ability also creates risk, so the task surface must be constrained.

Design principle
Use wider authority only when the task requires action, and split observation from state-changing steps.
TOPIC 02

Tool choice is a representation problem

The model has to represent the task in a way that makes the right tool obvious.

A tool call begins before the call. The model must decide what kind of problem it is seeing. Is this a factual gap, a calculation, a code behavior question, a UI state question, a legal source question, a medical threshold question, or a value judgment? That classification shapes the next action.

This connects back to unit choice. If the important unit is an exact variable name, code execution or static analysis may be needed. If the important unit is a rendered UI element, a browser or visual judge may be needed. If the important unit is a patient state over visits, memory and clinical review matter. If the important unit is a safety boundary, a controller or policy gate matters.

Wrong tool choice is often a wrong representation of the task. The model treats an evidence problem as a reasoning problem, a permissions problem as a writing problem, or a checkable artifact as a matter of style. Tool routing should be trained and evaluated directly.

Design principle
Choose the tool by the task property that would change the answer or action, not by a generic habit to call tools.
TOPIC 03

Permission scope should match action cost

The agent should not receive broad authority for a narrow job.

If the task is to inspect a file, read access may be enough. If the task is to propose a patch, write access to a small directory may be enough. If the task is to deploy, the system may require approval, a saved version, logs, rollback, and post-deploy checks. Permission should grow only when the task and evidence justify it.

SandboxEscapeBench is directly relevant because it treats boundaries as objects of evaluation. A system that cannot respect sandbox boundaries is not merely making a local mistake; it is failing the authority contract. Copyright-Bench and governance pages make the same point for source use, policy, and legal eligibility.

Permission is also a user interface problem. The user should know whether the agent is reading, writing, executing, posting, purchasing, deleting, deploying, or sharing. The action surface should make the difference visible.

Design principle
Give the agent the smallest authority that can complete the next justified step, and require stronger checks as action cost rises.
TOPIC 04

Delegation needs state packets

When work moves between tools, models, verifiers, and humans, the state must move with it.

A delegated task can fail because the receiver gets the wrong context. A verifier may need the exact artifact and specification. A human reviewer may need the sources, uncertainty, alternatives, and action cost. A specialist model may need cropped visual evidence rather than a text summary. A future step may need logs of what was already tried.

This connects directly to the state and memory page. Memory is future control. Delegation is one of the main reasons future control needs clean state: what was observed, what was changed, what passed, what failed, what is still uncertain, and who has authority now.

The practical rule is simple: do not delegate a conclusion when the receiver needs the evidence. Pass the relevant state, not only the model's current opinion.

Design principle
Every delegation should carry the minimum state needed for the receiver to check, continue, or overrule the work.
TOPIC 05

Verifiers are delegated authority, not decoration

A verifier matters only if its result can change the agent's next step.

It is easy to add a checker after generation and still ignore it. Real verifier delegation means the verifier can stop the workflow, force repair, widen uncertainty, request another tool, or trigger human review. The check becomes part of control, not a label at the end.

HERO, THOR, VERINA, MoCA, and WebDevJudge all sit here. They show different kinds of delegated checking: reward checks, tool feedback, proof/code consistency, multimodal component checks, and rendered web artifact judging. The common pattern is that the model's text is not trusted as the final authority.

The hard part is verifier scope. Tests do not prove the full specification. A proof checker may not capture the intended theorem. A visual judge may miss usability. A reward model may encode preference noise. Verifiers should be paired with coverage thinking and escalation paths.

Design principle
Let verifiers control the workflow where they observe the right property, and escalate where they do not.
TOPIC 06

Tool budgets are part of intelligence

A system that calls every tool is not careful; it is expensive and noisy.

Tool use has cost: latency, money, compute, privacy exposure, human attention, environment risk, and complexity. A good agent must decide when the expected value of a tool call is worth that cost. Sometimes direct answer is enough. Sometimes retrieval is necessary. Sometimes tests should be run. Sometimes more tool calls only add noise.

ParetoPO anchors this theme because it treats tool efficiency as part of the objective instead of an afterthought. The cost and scarcity page generalizes the same idea: scarce resources are not outside the method; they shape the method.

The right budget depends on domain. A medical or legal workflow may justify more checks. A casual factual query may not. A security task may require execution. A low-risk formatting task may not need a long chain of tools.

Design principle
Spend tool calls when they buy useful evidence, not when they merely make the process look more agentic.
TOPIC 07

Specialist delegation needs disagreement handling

Routing work to another model or specialist does not remove uncertainty; it changes its shape.

A system may delegate vision to a perception model, code review to a judge, preference scoring to a reward model, medical interpretation to a domain model, or legal analysis to a specialized evaluator. This can improve capability, but it introduces disagreement: which expert is trusted, under what evidence, and what happens when experts conflict?

MoCA is useful because it separates multimodal failure into components rather than treating the whole system as one black box. VALUEFLOW, P-GenRM, and WIMHF show that human feedback and preference structure are themselves objects to model, not simple labels. CounselBench and healthcare/education agents show that domain expertise changes what counts as a good decision.

The system should not hide disagreement behind one final answer. It should expose which component made which claim, what evidence it used, and what route resolves conflict.

Design principle
Delegate to specialists when the task needs their evidence, and preserve disagreement until a stronger route resolves it.
TOPIC 08

Human delegation is for judgment, not clerical cleanup

Humans should receive the parts that require human authority, not every part the system failed to organize.

Human review is scarce. It should be used where humans add something tools cannot: professional judgment, accountability, value choice, exception handling, consent, or context that is not in the system. Sending humans raw model confusion wastes the strongest authority in the loop.

The handoff packet from the escalation page becomes even more important here. The human should see the evidence, alternatives, uncertainty, tool results, verifier status, and the exact decision being requested. The goal is not to make the human read the entire trace unless the trace is the evidence.

This applies differently by domain. In medicine, the human may own diagnosis or treatment. In legal work, the human may own jurisdictional judgment and client advice. In education, the human may own pedagogy and student welfare. In code, the human may own irreversible deployment or destructive changes.

Design principle
Use humans for the decision authority only humans should hold, and prepare the case so their review reduces risk rather than repeats the model's work.
TOPIC 09

Agent evaluation must test the boundary, not only the outcome

An agent can get the final answer right while using the wrong authority.

A coding agent may pass by editing too broadly. A web agent may complete a task by clicking through unsafe permissions. A security agent may solve an exercise by escaping the intended boundary. A medical assistant may produce a plausible answer without appropriate escalation. A legal assistant may retrieve the right text but overstate certainty.

Agent evaluation should therefore measure route choice, permission respect, cost, reversibility, audit quality, verifier use, human handoff quality, state retention, and final outcome. CyberGym evaluates executable security work. SandboxEscapeBench evaluates boundary pressure. WebDevJudge evaluates rendered artifacts. ParetoPO evaluates tool cost. These papers point toward agent evaluation as workflow evaluation.

This is the difference between "did it finish?" and "did it finish by the right route?" For agents, the second question matters because the route may create hidden risk.

Design principle
Evaluate whether the agent used the right authority at the right time, not only whether it eventually produced a desirable artifact.
TOPIC 10

The agent boundary is a product and safety decision

There is no universal agent boundary. The boundary depends on domain, user, cost, reversibility, evidence, and trust.

A research assistant may browse and summarize but not email sources. A coding agent may edit files and run tests but ask before deleting data or deploying. A financial assistant may analyze but not trade. A medical assistant may summarize records but route treatment decisions to clinicians. A robot may plan but let a safety controller constrain motion.

The boundary should be explicit: what the model may observe, what it may change, what needs approval, what is logged, what is reversible, what is forbidden, and which verifier or human authority can override it. Without that boundary, "agent" becomes a vague label for uncontrolled tool access.

The deepest connection to the earlier pages is that every boundary is a choice about what must be preserved: user intent, task state, evidence, permission, safety, cost, privacy, and accountability. Delegation is reliable when those preserved facts survive across every tool and actor.

Closing line
An agent is reliable when its authority is as carefully designed as its intelligence.
