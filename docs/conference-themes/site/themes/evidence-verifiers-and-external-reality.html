Evidence, verifiers, and external reality

A claim is only as strong as the evidence surface that can falsify it. The next step after representation repair is proof: what kind of outside check is allowed to say that a model really understood, acted, reasoned, complied, predicted, or preserved the thing we care about?

Problem

Many evaluations ask for an answer when the real claim is about an artifact, action, state change, legal boundary, physical constraint, patient trajectory, or future outcome.

Approaches

Use answer checks, artifact checks, environment checks, human rubrics, model judges, simulators, statistical tests, causal evidence, longitudinal prediction, and process verifiers.

CORE

Evidence is the interface between a claim and the world

A benchmark is not just a score. It is a measurement instrument. It decides what kind of reality the model has to answer to.

If the evidence surface is too weak, a model can pass without having the claimed ability. It can answer a security question without exploiting or patching a vulnerable system. It can summarize code without understanding the interleaving that creates a data race. It can state copyright policy while choosing illegal material under workflow pressure. It can generate a proof-shaped explanation without a proof checker accepting it. It can produce a medically plausible response without respecting thresholds, contraindications, uncertainty, or patient trajectory.

The first-principles question is not only "what is the right metric?" It is "what outside fact is allowed to disagree with the model?" For some tasks the outside fact is an exact answer. For code it may be execution. For web agents it may be a rendered artifact. For robotics it may be a physical trajectory or simulator state. For safety it may be a tail event rate. For medicine it may be calibrated risk under a downstream decision. For law it may be source eligibility and jurisdiction. For causal discovery it may be an intervention, not a correlation.

This is why modern papers increasingly build verifiers, executable environments, calibrated judges, simulators, expert rubrics, uncertainty tests, and process checks. They are not decoration around a benchmark. They are attempts to move the evidence surface closer to the thing the claim is actually about.

First-principles line
A claim is only as strong as the evidence surface that can falsify it; weak evidence rewards performance that looks right, strong evidence forces contact with the object that matters.

TOPIC 01

Answer checks are useful but narrow

Exact answer checks are the cheapest evidence surface. They are valuable when the claim is exactly about the answer and dangerous when the claim is about the process that produced it.

A label, multiple-choice option, exact string, numeric answer, or span match can be a clean measurement. It is reproducible, cheap, and easy to aggregate. If the task is "copy this identifier exactly" or "classify this known category," an answer check may be enough. It becomes weak when the answer can be guessed from a shortcut, copied from leakage, produced by a flawed process, or scored without checking the object the user will rely on.

This is the reason many papers move beyond scalar accuracy. The answer can be correct while the grounding is wrong. The benchmark score can be stable while item sampling changes the ranking. A model can choose the right option in a simplified setting and fail once the task includes tools, documents, code execution, safety boundaries, or user pressure. Answer checks remain useful as a baseline, but they should not be mistaken for proof of a broad capability.

The evaluation page's benchmark-reliability discussions belong here. Micro-benchmark reliability and ranking-stability papers ask whether small benchmark choices change conclusions. The deeper principle is that an answer check is a measurement channel with noise, sampling effects, and blind spots. It should be paired with stronger evidence when the claimed ability is not reducible to a final answer string.

Evidence principle
Use answer checks when the answer is the object; do not use them as proof of grounding, tool skill, executable correctness, safety, causality, or long-horizon control.
TOPIC 02

Artifact checks make outputs answer to their own format

Some tasks produce things, not answers. The right evidence is whether the thing works.

A code patch should pass tests. A proof should verify. A SQL query should execute and return the intended result. A webpage should render and satisfy visual, functional, and accessibility constraints. A generated table should preserve cells and relationships. A legal document should contain the right clauses and source constraints. In these cases the artifact itself supplies a stronger check than a judge reading the text.

Artifact checks are important because they punish plausible but invalid output. A model can describe a fix without producing a working patch. It can write proof-like prose without satisfying a verifier. It can create a webpage that sounds complete in a summary but renders with broken layout. It can generate code that looks idiomatic but fails under edge cases. The artifact check moves evidence from "does this look right?" to "does this survive the operation that defines success?"

WebDevJudge, VERINA, THOR, Gaia2, and the program-synthesis pages sit under this theme. Their shared principle is artifact-native judging. The verifier should know what kind of object the model produced. A code verifier should execute or prove. A web verifier should inspect the rendered artifact. A math verifier should check steps or final proof obligations. The evidence surface should be native to the artifact, not only to language.

Evidence principle
When the model creates an artifact, evaluate the artifact through the operation that gives it meaning: execution, rendering, verification, retrieval, compilation, or downstream use.
TOPIC 03

Environment checks test action, not explanation

Agents claim to act in a world. Their evidence should include state change, tool cost, constraints, and boundary conditions.

An agent can sound competent while failing to operate. It can explain a vulnerability without exploiting or patching it. It can summarize a sandbox policy without respecting the boundary. It can state copyright rules but choose unusable material when a user asks for speed. It can call tools excessively and improve accuracy only by wasting cost. Environment checks make the model answer to a structured state rather than a text prompt alone.

CyberGym is the clean example: cybersecurity evaluation becomes an executable environment problem. The question is not whether the model can describe a vulnerability, but whether it can use tools, inspect state, change code, and validate consequences. SandboxEscapeBench tests whether an agent with shell access can cross a controlled container boundary. Copyright-Bench tests legal compliance as workflow behavior. ParetoPO asks whether tool use is worth its cost, making efficiency part of the evidence surface rather than an afterthought.

The strength of environment checks is that they expose hidden process failures. The weakness is that environments can be narrow or overfit. A benchmark environment is still a designed world. Good papers therefore specify the boundary: which tools are available, what state is hidden, what action counts as success, what cost is measured, and what kinds of shortcut the environment is meant to block.

Evidence principle
Use environment checks when the claim is about action; the model should have to change, preserve, reach, avoid, or verify a state under the same constraints the use case cares about.
TOPIC 04

Human checks measure meaning, but they are not neutral

Human judgment is necessary when the object is value, usefulness, clinical relevance, pedagogy, style, or disagreement. It is also a noisy measurement channel.

Some qualities cannot be reduced to an exact answer or executable test. A tutor may be technically correct but pedagogically poor. A clinical assistant may be plausible but not useful to a doctor. A legal assistant may need judgment over relevance and risk. A creative assistant may need taste, source eligibility, and fit to intent. An aligned model may need to balance plural values rather than maximize one scalar preference. Human evidence matters because some tasks are about human-facing decisions.

But human checks are not magic truth. Annotators disagree. Experts have specialties. Preferences shift with context. Rubrics can hide value choices. A small panel can make a broad claim look settled. The evidence surface has to expose uncertainty, disagreement, domain credentials, and the exact judgment prompt. Otherwise "human evaluation" becomes a vague authority label instead of a measurement method.

VALUEFLOW is useful because it treats values as intensity profiles rather than binary preference wins. CounselBench and medical/education agent evaluations show why domain judgment has to be tied to the work context. Preference optimization papers such as BNRM, P-GenRM, WIMHF, and AdAEM show the measurement problem inside feedback itself: before optimizing preferences, we need to understand what the feedback channel contains, hides, and overweights.

Evidence principle
Use human checks when the claim depends on human meaning, but report them as structured, uncertain evidence rather than as a final oracle.
TOPIC 05

Model judges scale evaluation, but they create a second model to trust

A judge model is useful when it can inspect evidence cheaply at scale. It is risky when its blind spots become the benchmark.

Model judges, reward models, teacher models, and VLM-as-judge systems make evaluation scalable. They can score open-ended answers, compare preferences, check visual claims, evaluate generated artifacts, or provide dense process feedback. They are often necessary when exact answers are unavailable and human labeling is too expensive. But they do not remove the measurement problem. They move it into the judge.

A judge can reward style over correctness. A reward model can be hacked. A VLM judge can miss visual details. A teacher can pass on shallow reasoning. A rubric-following model can be consistent and consistently wrong. That means judge evaluation needs calibration, adversarial checks, expert spot checks, and artifact-native backups when possible. The question is not "did a judge score it highly?" It is "what evidence did the judge have access to, and what mistakes can the judge itself make cheap?"

Omni-Reward extends reward modeling across text, image, video, audio, and 3D, which makes the modality-specific evidence problem explicit. MoCA separates perception verification from structured verbal checks. HERO combines sparse verifiers with dense reward scores. BNRM makes reward factors interpretable. WebDevJudge-style artifact judging uses model judgment, but the important standard is whether the judge is attached to rendered or executable evidence rather than free-floating text preference.

Evidence principle
Use model judges when scale is needed, but treat the judge as another measured system whose inputs, blind spots, incentives, and calibration must be tested.
TOPIC 06

Simulator checks make structure testable before deployment

A simulator is useful when the real world is expensive, slow, risky, or hard to instrument, but the simulated world must preserve the constraint being claimed.

Robotics, physical generation, control, molecular modeling, and some agent tasks need evidence about dynamics. A text answer cannot prove that a robot trajectory is stable. A pretty generated molecule does not prove physical validity. A planning trace does not prove a policy will recover near a safety boundary. A simulator or structured solver gives the model a world where actions have consequences and invalid states can be rejected.

The main risk is simulator overfitting. If the simulator misses friction, contact, noise, device constraints, real sensor errors, or distribution shift, a model can pass the simulator and fail deployment. So simulator evidence must say which part of reality it represents. Is it checking geometry, dynamics, safety margin, molecular symmetry, trajectory feasibility, or policy recovery? A simulator is strongest when it is paired with real-world validation or when the claim is explicitly about the simulated object.

HDFlow, dWorldEval, WestWorld, robotics/control pages, and scientific generation pages all belong here. HDFlow separates high-level subgoal search from low-level trajectory generation. dWorldEval uses generated future observations and progress indicators to rank robot policies. WestWorld models morphology-aware trajectories. Scientific generation papers build sample spaces around symmetry, hierarchy, and physical constraints. These are not just better generators; they are examples of evidence being moved into the structure of the world being modeled.

Evidence principle
Use simulators when the claim is about dynamics or feasibility, but state exactly which real constraint the simulator preserves and which deployment gap remains.
TOPIC 07

Statistical checks measure uncertainty, reliability, and tails

Some failures are not single wrong answers. They are uncertainty errors, ranking instability, rare events, calibration failures, or decision-risk mistakes.

A model can be usually correct and still unsafe at deployment scale. A benchmark can rank models differently depending on sampled items. A prediction set can have good coverage and still be useless for the downstream decision. A judge can be noisy enough that small score differences are meaningless. A rare harmful behavior can be absent from ordinary sampling and still appear often enough at production volume to matter.

Statistical evidence makes these problems visible. Confidence intervals, finite-sample certificates, tail-probability estimation, calibration curves, prediction sets, uncertainty regions, and ranking-reliability tests all ask whether the measurement itself is stable. The point is not to make evaluation abstract. The point is to prevent overclaiming from small samples, noisy judges, average-case scores, or decision-irrelevant uncertainty.

Rare Event Analysis frames safety evaluation as event definition, probability estimation, and structure exploration. FRABench/ATLAS-style reliability work asks whether benchmark measurements support the ranking people infer from them. ROCP and CRC shift prediction sets toward downstream decision robustness. MIRA tests conditional distributions through regional probability mass. CreDRO builds credal prediction sets from distributionally robust disagreement. These papers show that uncertainty must be connected to the cost of being wrong.

Evidence principle
Use statistical checks when the claim depends on reliability under sampling, uncertainty, tail risk, calibration, ranking stability, or decision cost.
TOPIC 08

Causal checks ask whether the evidence explains the right cause

Correlation can support prediction, but causal claims need evidence about interventions, counterfactuals, or compatible causal structures.

A model may predict an outcome using a shortcut that would fail under intervention. It may identify a root cause that is merely correlated with failure. It may recommend a treatment pattern without separating cause from confounding. It may learn an environment-specific cue and call it a mechanism. Causal evidence matters when the task is not only "what happens?" but "what made it happen?" or "what would change if we acted?"

The repair is to expose causal uncertainty instead of hiding it. Interventional data is strongest when available. Counterfactual checks can test whether a model's explanation changes under the right perturbation. Causal discovery can represent multiple compatible structures rather than pretending the graph is known. Root-cause analysis can reason over uncertainty instead of selecting the most convenient correlated node.

BRCD is a clear anchor: it starts from incomplete pre-failure structural knowledge in cloud systems, learns a CPDAG, and performs Bayesian inference over root-cause candidates without enumerating every DAG. The causality pages and same-evidence cause-story material make the broader point: the same observations can support different causal stories. A good evidence surface tells the reader which causal ambiguity remains.

Evidence principle
Use causal checks when the claim is about why something happened or what action would change it; prediction alone is not enough evidence for cause.
TOPIC 09

Longitudinal checks prove that state survives over time

Some abilities only show up after time passes: future prediction, recovery, patient progression, event effects, or long reasoning chains.

A static snapshot can hide temporal failure. A model may classify the current state correctly and still forecast poorly. It may reason for five steps and collapse by fifty. It may satisfy a safety constraint at the end while taking an unsafe path. It may detect an event but miss how that event changes future outcomes. A longitudinal evidence surface checks whether the representation keeps the state that time will test.

The key is to measure both outcome and path. Final future accuracy is useful, but it can hide unsafe intermediate states, unstable recovery, or lucky cancellation. Good longitudinal evidence asks whether errors accumulate, whether recovery is fast, whether the future state remains calibrated, whether the reasoning trace remains input-dependent, and whether the model preserves patient, object, variable, or policy identity over time.

IRNO focuses on accumulated error in neural-operator inference. TESS turns temporal text events into forecasting primitives. Hawkes Representer Theorem represents temporal triggering. CSPO evaluates time to safety, violation frequency, and reward preservation. h1 makes long-horizon reasoning learnable through dependency-chain curriculum. These papers show that temporal evidence is not just a longer benchmark; it is a different proof surface.

Evidence principle
Use longitudinal checks when the claim depends on persistence, recovery, trajectory, accumulation, or future consequence rather than a single state.
TOPIC 10

Process checks inspect the path, but the path must still matter

Intermediate traces are useful evidence when they reveal perception, reasoning, tool choice, or action quality that the final answer hides.

A final answer can be right for the wrong reason. Process checks try to expose the hidden path: what evidence was perceived, which step was taken, which tool was called, whether reasoning remained input-dependent, whether the model recovered from error, whether a verifier accepted a step, and whether extra computation helped or merely lengthened the response. They are essential for agents, math, code, multimodal reasoning, and safety workflows.

But process evidence can be gamed. A model can write a convincing trace after deciding the answer. It can produce longer reasoning that looks careful but is generic. It can call tools for appearance. It can optimize a process reward while losing the real goal. Therefore process checks are strongest when tied to external success: tool outputs, verifier feedback, perception checks, state changes, or input-dependence diagnostics.

RAGEN-2 catches template reasoning collapse by checking whether traces remain input-dependent. MoCA separates perception verification from structured verbal checks. HERO combines sparse verifiers with dense reward scores. THOR makes intermediate math steps accountable through tool feedback. Tell-Tale Norm turns hidden-state magnitude into a test-time reasoning signal. LALP selects teacher traces by transferable local step transitions. Each paper treats process as evidence only when it is connected to behavior.

Evidence principle
Use process checks when the path matters, but anchor the path to external evidence so the model cannot pass by merely performing the appearance of reasoning.

SYNTHESIS

How to choose the evidence surface

Pick the evidence by asking what would make the claim false in the real use case.

If the claim is exact recall, use exact checks. If the claim is code, use execution or proof. If the claim is an agent workflow, use an environment with state and tools. If the claim is safety at scale, measure tail risk. If the claim is physical action, use simulation or real-world trajectories. If the claim is value alignment, expose human disagreement and reward structure. If the claim is causal, use interventions, counterfactuals, or explicit structural uncertainty. If the claim is temporal, measure the path, not only the endpoint.

This page is also a warning about weak verifiers. A verifier can be too shallow, too narrow, too gameable, too expensive, or too far from deployment. The best evidence surface is not always the most complex one. It is the one whose failure would actually contradict the claim. A simple exact check is enough for exact copy. A rendered artifact check is better for web generation. A simulator is better for trajectory feasibility. A human rubric is necessary for some preference claims. A causal test is necessary for causal claims. The evidence has to match the promise.

Closing line
Good evaluation is not a bigger scoreboard; it is a better place for reality to push back against the model's claim.
