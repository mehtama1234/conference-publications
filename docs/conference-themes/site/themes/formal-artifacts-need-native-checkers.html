Formal artifacts need native checkers

Some outputs are not true because they sound right. Code, proofs, CAD programs, compiler rewrites, and formal math must be checked inside the system where their meaning lives.

CORE

The checker belongs to the artifact

A formal artifact has rules outside natural language.

A proof is valid only if the proof assistant accepts it. A compiler transformation is valid only if it preserves program meaning and improves the relevant execution property. A CAD reconstruction is useful only if it becomes editable construction logic, not just a pretty shape. A formal problem solution is complete only when the generated object satisfies its obligations.

VERINA evaluates code, specification, and proof generation in Lean. LeanHammer connects premise selection to reconstruction so Lean checks the final proof. AlgoVeri holds algorithmic contracts fixed across Dafny, Verus, and Lean. FPS represents answers as Lean metavariables with proof obligations. cadrille generates executable Python CAD programs. CIRBench checks LLVM IR transformations with verifiers, equivalence checks, and runtime measurement.

Core rule
The right evaluator is the system that gives the artifact meaning: compiler, proof assistant, runtime, geometry engine, or domain verifier.
FIRST PRINCIPLE

Formal meaning lives inside a rule system

A formal output is not validated by sounding correct. It is validated by the system that defines correctness.

Natural language can describe a proof, a program, a CAD model, or a compiler rewrite, but it does not make the artifact valid. A proof assistant decides whether a proof term checks. A compiler and verifier decide whether an IR rewrite preserves meaning. A CAD program decides whether construction logic exists and can be edited. A specification decides whether code satisfies the promised invariant.

The first-principles object is the artifact plus its native checker. The checker is not an optional evaluator added at the end. It is part of the meaning of the artifact. Without it, the system may produce plausible text that imitates formal work while missing the obligation that makes the work true.

First-principles test
Run the artifact through the checker that owns its meaning, then use the checker failure to guide repair.

METHOD

Why checker feedback changes generation

A native checker is not just a grader; it is a source of structured evidence.

A failed proof tells which obligation remains. A compiler error tells which program form is invalid. An equivalence checker tells where a rewrite changed meaning. A CAD program that cannot reconstruct geometry tells where construction logic broke. This feedback is more useful than a broad language judgment because it is anchored in the artifact's own rules.

A strong method therefore builds a loop: generate, check, localize failure, repair, and check again. The loop matters because formal artifacts often fail for small but decisive reasons. The final explanation can be helpful, but the artifact earns trust only when the native system accepts it.

FAILURE MAP

How formal-looking outputs fail

Fluent invalidity

The explanation sounds right but the proof or code does not check.

Spec drift

The generated program solves a nearby task instead of the stated contract.

Premise gap

The proof path names useful facts but cannot reconstruct the formal term.

Rewrite break

A compiler optimization changes semantics while looking plausible.

Shape without program

A CAD output looks close but loses editable construction logic.

Tool overfit

The model learns syntax from one formal system instead of the underlying obligation.

CONNECTION

Why this idea cuts across the atlas

Native checkers are evaluation as execution in its clearest form.

Evaluation as execution says some claims are tested by running the task. Formal artifacts make that unavoidable. Scientific generation has the same shape: the domain object needs a native verifier. Grounding asks whether the answer depends on evidence; formal checking asks whether the artifact satisfies the rule system that defines it.

This also connects to agent trajectories. A coding or proof agent should not be judged only by the final response. Its search path, failed checks, repairs, and final accepted artifact show whether it used verifier feedback or only guessed until something looked plausible.

Formal work is one place where the atlas can be very concrete: the artifact either type-checks, runs, reconstructs, satisfies the specification, or preserves semantics under a stated checker. That concreteness should discipline the rest of the evaluation layer.

A good reading question for any formal-artifact paper is: what object is submitted to the checker, what obligation does the checker enforce, and how does the method respond when the checker rejects it? That keeps the article tied to executable validity rather than explanation quality.

The deeper rule is simple: when a domain has a real checker, do not replace it with a verbal judgment.

READER CHECK

How to read the next formal-artifact paper

Ask what object is submitted to the checker, what obligation the checker enforces, and how the method responds when the checker rejects it. Formal work often fails at the smallest missing obligation: one undefined premise, one wrong invariant, one invalid rewrite, or one non-editable construction can break the whole claim. Native checking finds those failures where language summaries blur them.
