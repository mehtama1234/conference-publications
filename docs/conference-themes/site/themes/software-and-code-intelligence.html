Problem

Software tasks are not text tasks with programming words. The output must execute, compose with an environment, preserve invariants, and behave correctly under tests or operational evidence.

Approaches

The papers build executable benchmarks, vulnerability environments, concurrent-code diagnostics, jailbreak reproduction workflows, and causal diagnosis for failing services.

Connecting read

The common theme is consequence. A code-intelligence system is judged by what the generated artifact does, not by whether its explanation sounds like software engineering.

FIRST PRINCIPLES

The core problem

Software is an unusually strict domain for AI because it has external reality built in. A program compiles or it does not. A compiler transformation preserves behavior or it does not. A vulnerability reproduction triggers the bug or it does not. A concurrent program deadlocks, races, or runs correctly. A microservice failure has a cause somewhere in the dependency graph. This makes code a central testbed for agentic AI: language helps, but execution decides.

The papers on this page are small in number, but they point at the same field-level shift as the agent and evaluation pages. The useful object is not a generated answer. It is a runnable artifact, a verified transformation, a failure diagnosis, or a reproduced attack. Code intelligence is therefore not just language modeling over code tokens. It is the ability to create or inspect an artifact whose behavior can be tested outside the model.

CORE

Code understanding means preserving behavior under change

The first-principles question is simple: after the model edits, translates, diagnoses, or reproduces something, did the relevant behavior stay true?

This is stricter than ordinary text generation. A summary can be partly useful while being incomplete. A program transformation is different. If an LLVM rewrite changes semantics, it is wrong. If a vulnerability environment does not reproduce the bug, it is wrong. If a concurrency explanation ignores synchronization, it is wrong even if it mentions the right variables. If a root-cause system points at a downstream symptom, it has not explained the failure. Software gives AI an unusually clear external test: the artifact must run in the world it claims to describe.

That is why the concrete object differs by paper. CIRBench tests compiler-level transformations. CVE-Factory constructs executable vulnerability tasks. DRPBench tests reasoning over concurrent execution. Jailbreak Foundry turns paper claims into reproducible attacks. BRCD explains microservice failures through causal structure. The shared principle is that code intelligence has to preserve the thing that makes software software: operational behavior.

TOPIC 01

The artifact is the answer

In software, the model's final text is usually not the real output. The real output is the artifact that changes execution.

A compiler transformation, CVE environment, concurrency diagnosis, jailbreak reproduction, or root-cause ranking is a claim about behavior. It says that some program will still compute the same thing, that some harness will trigger a real bug, that some interleaving can fail, that some attack can be reproduced, or that some service is the likely cause of a failure. Those claims are not settled by fluent explanation.

This makes software a clean first-principles test for AI systems. The answer has to leave language and meet an external checker: compiler, runtime, exploit trigger, synchronization analysis, or causal evidence. The artifact is where understanding becomes falsifiable.

TOPIC 02

Semantics must survive transformation

A code model is allowed to change the surface form, but it is not allowed to change the contract that defines correctness.

CIRBench makes this obvious at compiler level. LLVM IR can be analyzed, repaired, refactored, or optimized, but the transformed program must still mean the same thing for the task's correctness claim. Performance only matters after semantics are preserved. A faster wrong transform is not a success; it is a more efficient failure.

The same rule holds for the whole page. CVE-Factory may change the harness but not the vulnerability trigger. Jailbreak Foundry may change packaging but not the attack mechanism. DRPBench may change explanation format but not the interleaving logic. BRCD may change the posterior ranking but not the distinction between cause and downstream symptom.

TOPIC 03

Concurrency is behavior over time

A concurrent program cannot be understood by reading each line as if it runs alone.

DRPBench is important because it targets a failure mode that ordinary code benchmarks can miss. Shared state, locks, ordering, and synchronization create behavior that appears only across possible interleavings. A model can name the right variables and still miss the bug if it does not reason about when those variables are read, written, protected, or exposed.

The first-principles object is therefore not a static snippet. It is a family of executions. The verifier has to ask whether some schedule races, deadlocks, violates ordering, or bypasses synchronization. That is why concurrent-code intelligence is closer to systems reasoning than local syntax completion.

TOPIC 04

Security claims need reproduction

A vulnerability description becomes useful evidence only when it can be turned into a runnable failure or attack.

CVE-Factory starts from sparse CVE records and builds executable environments. Jailbreak Foundry starts from papers and tries to reproduce attacks with reusable code. Both papers have the same deeper object: a security claim that survives translation from prose into an artifact that other systems can run and test.

This matters because security text can be underspecified. A writeup may omit setup details, version constraints, trigger conditions, or exact prompts. Reproduction forces those hidden assumptions into the open. If the environment cannot trigger the CVE or the attack package cannot reproduce the jailbreak, the claim is weaker than the prose suggested.

TOPIC 05

Diagnosis is causal, not just textual

A production failure explanation should identify where intervention should start, not only which logs look related.

BRCD brings causality into software intelligence. A microservice incident creates many abnormal signals at once. Downstream services may fail because an upstream service failed. Log similarity and anomaly scores can point to loud symptoms, but root-cause diagnosis asks a different question: which component most plausibly caused the incident under the system's dependency structure?

The useful output is a causal belief over candidate repair points. That belief has to preserve pre-failure structure, sparse failure evidence, and uncertainty over graph direction. This is still code intelligence because the artifact is operational: it guides the next debugging action in a running software system.

SUBTHEMES

Three concrete fronts

1. Correctness requires executable representations

program behavior

The first front is the gap between code-looking text and correct program behavior. These papers focus on representations where mistakes are exposed by compilers, runtime checks, synchronization logic, or performance measurements.

ICML 2026CIRBench
CIRBench evaluates language models on LLVM intermediate representation tasks: analysis, repair, refactoring, and performance transformation. The important move is that the benchmark checks both correctness and runtime behavior. A model cannot simply produce plausible compiler language; its transformation must preserve program meaning and improve or respect performance constraints. That makes CIRBench a clean example of code intelligence as executable semantics.
ICML 2026DRPBench
DRPBench targets concurrent-code reasoning, where the hard part is not syntax but interaction over time. It identifies shared-variable distraction and synchronization-logic myopia: models focus on visible variables while missing the lock, ordering, and coordination logic that actually determines correctness. This matters because concurrency bugs are process bugs. They only appear when execution interleavings expose a mismatch between local code and global behavior.

2. Security work needs runnable tasks, not thin descriptions

vulnerabilities and attacks

Security is full of textual descriptions: advisories, CVEs, papers, exploit writeups, and patches. But a security agent is only useful if it can turn that text into executable evidence. These papers study the conversion from description to working environment or reproducible attack.

ICML 2026CVE-Factory
CVE-Factory transforms sparse CVE records into runnable vulnerability environments with expert-level correctness and fidelity. The conceptual problem is that CVE entries are often too thin to train or evaluate an agent directly. By constructing executable tasks, the paper changes the unit of evaluation from "knows about the vulnerability" to "can instantiate and test the vulnerability." The deeper lesson is that security knowledge becomes scientifically useful when it produces a reproducible failure.
ICML 2026Jailbreak Foundry
Jailbreak Foundry uses a multi-agent workflow to reproduce jailbreak attacks from papers with high fidelity and reusable code. The important idea is paper-to-attack translation. A jailbreak result in prose may be ambiguous or underspecified; a reproduced attack package makes it testable. This matters for both safety research and benchmarking because defenses need comparable, runnable attack artifacts rather than scattered claims.

3. Operational software failures are causal problems

systems diagnosis

Software intelligence is not only writing code. In production systems, the task is often to explain why something broke from sparse, noisy observations. That requires causal structure, not just log summarization.

ICML 2026BRCD
BRCD uses pre-failure CPDAGs and Bayesian inference to identify causes of microservice failures from sparse failure data. The first-principles challenge is that distributed systems fail through dependency structure: one service's symptom may be another service's cause. BRCD matters because it treats root-cause discovery as probabilistic inference over a causal graph, not as a keyword search over logs.
BOUNDARY

Nearby code papers complete the executable picture

The direct five-paper set is about code intelligence, but several nearby atlas rows make the same point from evaluation, data, retrieval, and formal-verification angles.

EditBench is the realistic code-editing version: the object is not a standalone snippet, but an edit made under instruction, highlighted code, cursor state, and project context. TerminalTraj and daVinci-Dev are the training-data version: the useful data is not only the final patch, but tool invocations, test executions, Docker-aligned validation, and the full information flow that produced the fix. VERINA is the formal version: code, specification, and proof form an artifact chain, and current models often get farther on code than on proof. CyberGym is the security-evaluation version: a generated proof-of-concept matters because it runs against pre-patch and post-patch code, not because it describes an exploit fluently. Actions Speak Louder than Prompts is the graph-code interface version: executable code can be a better way to interact with long, high-degree graph evidence than prompt-only reasoning.

These papers are not counted in the direct paper set below because the local index maps them to evaluation, data governance, reasoning, retrieval, or security. They still sharpen the concept: code intelligence is artifact intelligence. The artifact may be an edit, patch, proof, exploit, validation script, retrieved code context, or terminal trajectory. The common proof is external behavior.

EVIDENCE

What would prove code intelligence worked

The proof has to match the software object. A syntax check, natural-language judge, or plausible explanation is too weak for most of these claims.

Executable correctness

CIRBench-style tasks need compiler checks, runtime behavior, semantic preservation, and performance evidence when performance is part of the claim.

Vulnerability fidelity

CVE-Factory-style tasks need environments that reproduce the real trigger and preserve the affected software behavior described by the advisory.

Concurrent behavior

DRPBench-style tasks need evidence over interleavings, shared-state access, ordering, locks, races, deadlocks, and synchronization failures.

Attack reproducibility

Jailbreak Foundry-style results need runnable attack packages whose mechanism matches the paper claim closely enough for defenses to test.

Causal diagnosis

BRCD-style systems need root-cause recovery under sparse failure data, with uncertainty that separates repair points from downstream symptoms.

Trajectory evidence

For agentic software work, the trace should show which context was read, which verifier failed, what changed, and why the final artifact should be trusted.

FAILURE MODES

Where code agents overclaim

The recurring failure is that the model produces a software-looking artifact while the executable contract is weaker than the text suggests.

A patch can pass shallow tests while violating the issue intent. A compiler transform can look legal while changing behavior on an edge case. A vulnerability task can mimic a CVE description while failing to trigger the actual bug. A proof-oriented system can generate correct-looking code while never proving the specification. A terminal trajectory can include many tool calls without preserving the information flow needed to learn why the fix worked.

The right evidence is therefore not one generic code score. It is the verifier matched to the artifact: unit tests, CI, runtime checks, equivalence checking, exploit reproduction, proof checking, synchronization analysis, root-cause recovery, or trajectory validation. Code intelligence becomes real only when the produced artifact survives the verifier that defines the task.

LIFECYCLE

Software intelligence is a checked work loop

The full object is not a code snippet. It is a stateful loop: read context, propose an artifact, run a verifier, interpret feedback, repair locally, and preserve the evidence that explains why the final artifact should be trusted.

FIELD READ

Why this matters for ICML and ICLR

Code is the cleanest place to see why structured tasks and verifiers matter. A useful code benchmark needs the task, repository state, tools, actions, observations, test results, verifier output, and final artifact. Without that structure, each benchmark becomes a custom island.

The deeper point is that software makes evaluation honest. If the generated exploit does not run, if the compiler pass changes semantics, if the concurrent-code explanation misses the synchronization bug, or if the root-cause system points to the wrong service, the failure is observable. That is why code intelligence should be treated as a core pillar of agent evaluation rather than a side topic.

CONCEPT BRIDGES

Where to read the larger pattern

Formal artifacts need native checkers

Code, proofs, compiler output, exploits, and infrastructure changes must be checked by the tools that define correctness in that domain.

Agent trajectory is the object

A software agent leaves evidence through edits, commands, tests, failures, retries, and final diff. The process explains whether the result is trustworthy.

Evaluation is becoming execution

Software evaluation is strongest when the artifact runs. Passing text answers matter less than tests, proof kernels, build systems, and reproduced failures.
