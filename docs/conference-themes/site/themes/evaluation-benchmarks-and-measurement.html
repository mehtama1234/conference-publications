The first-principles problem

Evaluation used to mean giving a model a fixed input and comparing the answer with a gold label. That breaks down when the model edits code, uses a browser, operates tools, generates video, answers under pressure, reasons through a long process, or affects a real system. In those settings the answer is only the final surface. The important evidence is the consequence: what changed, what was checked, what failed, and whether the checking process itself can be trusted.

The papers in this theme are trying to rebuild measurement for this new setting. Some use executable verifiers: run the code, test the patch, inspect the browser state, check the compiler transformation, validate the generated proof. Some use calibrated judges because the target is subjective or multimodal. Some measure rare events because deployment failures may be absent in small samples. Some build dynamic environments because a model's competence is only visible across a sequence of actions.

The big-picture connection is that AI progress is becoming harder to measure precisely at the same time that measurement matters more. A benchmark is no longer just a leaderboard. It is an instrument. If the instrument is weak, the field optimizes toward theater: fluent answers, attractive artifacts, cheap judge agreement, and verifier shortcuts. The best work in this theme tries to make the instrument harder to fool.

Topic 01

What evaluation is really for

Evaluation is not mainly a way to rank models. It is a way to decide whether the evidence is strong enough to rely on a system in a particular setting.

That distinction matters because the same model behavior can be acceptable in one setting and unacceptable in another. A vague but useful answer may be enough for brainstorming. It is not enough for a medical recommendation, a code patch, a legal claim, a robot action, or a security assessment. The evaluation standard comes from the use case: what decision will be made from the output, what can go wrong, who pays the cost, and what kind of evidence would catch the important failure before it matters.

A benchmark score compresses this whole decision into a number. That can be useful, but it is dangerous when the number hides the evidence behind it. Two systems can have the same score for different reasons. One may know the task, another may exploit benchmark style. One may act safely but slowly, another may act quickly but miss rare failures. One may pass a judge because it writes fluently, another may pass because it produced a checkable artifact. Evaluation has to ask what the score is evidence for.

The first question is therefore not "how accurate is the model?" The first question is "accurate at what unit, under what conditions, with what checker, for what consequence?" If the unit is a final answer, the test may miss bad tool use. If the unit is a trajectory, the test can see state, action, recovery, and cost. If the checker is a weak judge, the result needs uncertainty. If the checker is a proof or executable test, the result can support a stronger claim, but only for the property the proof or test actually covers.

Use-case standard
The right evaluation depends on what the output will be used for. Casual text, clinical advice, executable code, autonomous action, and scientific claims do not need the same evidence.
Evidence, not ceremony
A benchmark is useful only if passing it is evidence of the capability people care about. If the benchmark rewards surface form, the system learns surface form.
Failure cost
The higher the cost of being wrong, the stronger the check must be. A cheap judge may be enough for style; a proof, execution, expert review, or tail-risk estimate may be needed for high-stakes use.
Decision threshold
Evaluation should support a decision: accept, reject, defer, retrain, investigate, restrict, or deploy with limits. A number without a decision rule is weak evidence.

How the papers fit this first principle

CyberGym and SandboxEscapeBench make evaluation behavioral: the system must produce an action whose consequence can be checked. Gaia2 and AstaBench make evaluation procedural: the trajectory, tools, cost, and action-level verifiers matter. OmniVerifier, FRABench/UFEval, Pressure Reveals Character, and Weak-Strong Verification make evaluation reflexive: when the checker is a judge or weak verifier, the checker itself needs calibration. Rare Event Analysis of LLMs and Tail Risks in LM Outputs make evaluation statistical: absence of a failure in a small sample is not enough. CounselBench, Seizure-Semiology-Suite, PhyWorldBench, RealPDEBench, RoboMME, and VERINA make evaluation domain-native: the correct evidence is defined by the field, not by generic model scoring.

First-principles line

Evaluation is the trust layer: it chooses the unit, checker, conditions, failure cost, and decision rule that make a result meaningful for the setting where the system will be used.

Topic 02

The unit of evaluation

Before choosing a benchmark, choose the thing being judged. The unit may be an answer, action, trace, tool call, proof, citation, image, trajectory, user outcome, safety event, or cost profile. If the unit is wrong, the score answers the wrong question.

A model does not only produce strings anymore. It edits files, issues tool calls, asks questions, navigates interfaces, generates artifacts, writes proofs, retrieves citations, creates media, and acts over time. Each of those behaviors has a different unit of correctness. A final answer can be right while the citation is wrong. A code patch can compile while the user request is unsatisfied. A web page can render while the interaction is broken. A medical answer can be fluent while missing the clinical feature that matters. Evaluation becomes clearer when the unit is explicit.

The unit should be the smallest object whose change can change the decision. In code, that may be a patch, test result, proof obligation, or regression. In agents, it may be a trajectory step, tool call, state update, or cost. In multimodal generation, it may be a visual attribute, temporal relation, audio cue, or whole artifact. In safety, it may be a rare event, policy violation, deception signal, or successful boundary crossing. Different units create different evidence.

This is also why a single benchmark number can be misleading. It may average together units that have different meanings. A model may be strong at final answers and weak at process. Strong at perception and weak at memory. Strong at exact code tests and weak at proof. Strong on common cases and weak in tail events. The unit tells us where the evidence applies and where it does not.

Answer
Useful when the task is static and the gold target is well-defined. Weak when the model's path, evidence, or side effects matter.
Action
Tool calls, browser writes, database edits, code changes, robot moves, and security exploits need action-level checks because the consequence is outside text.
Artifact
Generated code, images, audio, web pages, videos, tables, reports, and proofs need structural and behavioral inspection, not only surface similarity.
Trajectory
Agents require sequence-level evidence: observation, state, action, feedback, recovery, cost, and stopping.
Outcome
High-stakes domains care about user, patient, learner, system, or environment outcomes. The answer is only one contributor to the result.
Failure event
Rare failures, jailbreaks, deception, degeneration, and sandbox escapes are units in their own right because averages can hide them.

How papers choose different units

CyberGym evaluates generated proof-of-concept tests against vulnerable and patched code, so the unit is executable security behavior. SandboxEscapeBench evaluates whether an agent crosses an infrastructure boundary, so the unit is a controlled escape event. Gaia2 evaluates write actions with action-level verifiers, so the unit is not only the final task result but each consequential step. AstaBench evaluates research-agent workflows with tool and cost controls, so the unit is a full agent run under comparable conditions.

OmniVerifier and FRABench/UFEval evaluate generated or interleaved multimodal outputs through aspects and visual verification categories, so the unit may be a visual outcome or evaluation aspect. EditBench evaluates realistic code edits with instruction and cursor context, so the unit is a patch in context. VERINA evaluates code, specification, and proof separately, making the proof obligation a different unit from passing code. Rare Event Analysis and Tail Risks in LM Outputs make low-probability harmful behavior the unit, because deployment risk can live in the tail rather than the mean.

First-principles line

The unit of evaluation should be the thing whose change would change trust: answer, action, artifact, trajectory, outcome, failure event, or cost.

Topic 03

Static versus dynamic evaluation

Static benchmarks ask whether a system can answer a fixed prompt. Dynamic benchmarks ask whether it can keep working as the world, interface, user, state, or evidence changes.

Static evaluation is still useful. It gives repeatable inputs, clear comparison, and cheap measurement. But it only sees what fits inside one example. It misses failures that happen across time: stale memory, wrong recovery, bad tool sequencing, latency, interface brittleness, user misunderstanding, and environment drift. Once a model becomes an agent, a coding assistant, a browser worker, a smart-home controller, or a scientific workflow, competence is no longer a single response. It is a run.

Dynamic evaluation changes the object being measured. The question becomes whether the system observes the right state, chooses the next action, reads feedback, repairs mistakes, and stops at the right time. This is harder to benchmark because runs vary and confounders multiply. A system may look better because it has stronger tools, more budget, lower latency, an easier interface, or a friendlier user simulator. Good dynamic evaluation therefore has to control the environment, record the trajectory, and explain which part of the run caused success or failure.

The first-principles distinction is not "static bad, dynamic good." The distinction is fit to behavior. If the deployed system only answers isolated questions, a static benchmark may be enough. If the system acts over time, then static examples are only partial evidence. The evaluation must include the time scale on which the system can fail.

Static benchmark
Best for repeatable comparison, narrow skills, fixed labels, and cheap regression checks.
Dynamic task
Needed when observations, actions, tools, users, costs, or environment states change during the run.
Trajectory evidence
Records not only success but the path: actions, feedback, state updates, retries, and stop decisions.
Confounder control
Dynamic evaluation must track tools, budget, interface, latency, user simulator, and environment difficulty.
Failure localization
A failed run should say whether the break was perception, memory, action choice, verifier use, recovery, or timing.
Deployment realism
The more the real task changes over time, the more the benchmark must test time, interaction, and state.

How papers make evaluation dynamic

Gaia2 is a direct example because it evaluates agents in dynamic asynchronous environments and uses action-level verifiers. The system is not judged only by final response; its write actions must be valid during the run. AstaBench does the same for scientific research agents by controlling tool access, cost, interfaces, and agent classes. SimuHome adds a deployment-time concern: a smart-home agent can reason well but fail if it responds too slowly for the environment.

BIRD-INTERACT moves text-to-SQL from a static query-answer task into interaction with databases, knowledge bases, user simulators, and executable tests. OpenApps, VenusBench-Mobile, and PIPE show why interface variation matters: an agent that memorizes one surface can fail when the same semantic task appears through another layout or app state. CausalGame and MADQA expose process gaps by comparing experiment design, data collection, inference, reports, human behavior, agent behavior, and oracle behavior. These papers treat time and interaction as part of the measurement target.

First-principles line

Use static evaluation when the skill lives in one fixed example; use dynamic evaluation when the system can fail through state, action, feedback, recovery, timing, or environment change.

Topic 04

Executable checks

Executable evaluation is powerful because it makes a claim meet a consequence. The model does not only say a patch works, a proof is valid, an exploit exists, or an interface is correct. The evaluation runs the relevant check and observes what happens.

This changes the evidence standard. A text answer can be plausible without being true. An executable artifact has to survive contact with a system that is less forgiving than language: a test suite, compiler, theorem prover, sandbox, simulator, browser, database, or pre/post patch environment. That does not make the evaluation perfect, but it makes the target harder to fake. The model has to produce something that behaves correctly under a specified check.

The key phrase is "specified check." Executable evaluation proves only what the check covers. A test suite may miss edge cases. A proof may depend on the right specification. A sandbox task may measure escape skill but not broader misuse risk. A web-page evaluator may inspect layout but miss accessibility or workflow failure. A compiler benchmark may check semantic preservation and speed but not maintainability. Executable checks are strong evidence when the check matches the real claim; they become misleading when the claim is broader than the check.

The design problem is therefore to align artifact, environment, oracle, and failure cost. What exactly should run? What state should count as success? What side effects are allowed? What negative cases must fail? What regressions matter? What should be logged for audit? Strong executable evaluation is not just "run something." It is a small controlled world where success and failure mean what the use case needs them to mean.

Tests
Useful for code, patches, browser flows, apps, and database tasks. They show behavior on specified cases, not full correctness.
Proofs
Useful when the claim needs a stronger guarantee than examples. They depend on the specification being the right one.
Sandboxes
Useful for security and tool-risk tasks where the event is boundary crossing, exploit success, or controlled environment change.
Simulators
Useful for robotics, smart homes, causal games, physical systems, and scientific agents where real-world testing is costly or risky.
Artifact inspection
Useful for web pages, images, audio, video, tables, and generated interfaces where quality is structural and interactive.
Pre/post comparison
Useful when success means changing one world state while preserving another: exploit vulnerable code, fail on patched code, or improve without regression.

How papers use executable checks

CyberGym is the cleanest example: generated proof-of-concept tests are validated against pre-patch and post-patch code. The unit is not a vulnerability description but executable behavior. SandboxEscapeBench uses nested VM/container isolation and CTF-style objectives to check whether a model can cross a runtime boundary. CVE-Factory addresses task supply by generating executable vulnerability environments so security evaluation can scale without becoming a small static memorized set.

CIRBench uses verifier checks, equivalence reasoning, and performance measurement for compiler optimization, because an optimization must preserve meaning and improve execution. EditBench evaluates instructed code edits in realistic context, where the patch must satisfy the user request rather than merely look similar to a reference. VERINA and AlgoVeri move further toward formal evaluation: code, specification, proof, and proof-tool acceptance become distinct checks. WebDevJudge, Vision2Web, and MiniAppBench extend executable thinking to generated software artifacts, where the evaluator must inspect visual structure and interactive behavior, not just source text.

First-principles line

Executable evaluation is strongest when the artifact, environment, oracle, and failure cost match the real claim; it proves behavior under that check, not truth beyond it.

Topic 05

Judge-based checks

When exact checking is unavailable, evaluation often uses a judge: a human, rubric, model, ranking system, weak verifier, or learned evaluator. That can be necessary, but it means the measurement device itself becomes part of the problem.

Judge-based evaluation is common because many important outputs do not have a single exact oracle. A mental-health answer, generated image, open-ended explanation, aesthetic edit, web interface, long-form report, or pressure-test behavior may need judgment. The question is not only whether the model being evaluated is good. The question is whether the judge can consistently recognize the kind of goodness or failure that matters.

A judge can fail in several ways. It can reward fluency over truth, miss domain-specific harm, prefer one language or style, collapse many dimensions into one score, disagree with humans, over-trust confident outputs, or rank models unstably when the sample is small. A model judge can also share the same blind spots as the model being evaluated. That makes calibration essential. Judge scores should be treated as estimates with assumptions, not as direct facts.

The first-principles design question is: what would make this judge trustworthy enough for this use case? Sometimes the answer is human expert calibration. Sometimes it is pairwise ranking instead of absolute scores. Sometimes it is a weak-strong verifier policy that accepts cheap judgments only when uncertainty is low. Sometimes it is psychometric item selection, aspect-level rubrics, or multidimensional scoring. The right judge design depends on what kind of disagreement or noise would change the decision.

Rubric
Defines what the judge should notice. Weak rubrics reward general quality words instead of the real failure surface.
Human calibration
Needed when the construct is subtle, subjective, clinical, legal, safety-relevant, or culturally dependent.
Model judge
Scales evaluation but can inherit model biases, prefer fluency, or miss errors that look plausible.
Pairwise ranking
Useful when absolute scores are noisy. It asks which output is better under a defined comparison.
Weak-strong policy
Uses cheap checks when confident and defers to stronger checks when the risk or uncertainty is high.
Statistical reliability
Small samples and unstable items can produce rankings that look precise but would change under another draw.

How papers measure the measuring device

OmniVerifier and FRABench/UFEval ask whether evaluator models can judge multimodal outputs at fine-grained aspect levels. Their importance is that image, interleaved, and visual-edit quality cannot be reduced to an exact string match. Pressure Reveals Character uses a human-calibrated judge for behavioral constructs such as honesty, non-manipulation, safety, robustness, and corrigibility, while still exposing that rationale agreement is imperfect. Weak-Strong Verification turns judge reliability into a policy problem: accept, reject, or defer based on calibrated weak-verifier scores and the cost of strong verification.

ATLAS and Micro-Benchmarking Reliability treat benchmark sampling itself as a measurement problem. They ask how many items are needed and which items best estimate ability or preserve rankings. VALUEFLOW, Ranking Time Series, and AGREE show that subjective targets need measurement models that handle preference order, noisy annotation, multidimensional attributes, and disagreement. Known More Know Clearer, EigenBench, and Train-before-Test add another layer: a model comparison depends on protocol, confidence, prior training state, and whether the benchmark measures the intended construct.

First-principles line

A judge-based score is useful only when the judge, rubric, calibration data, uncertainty, and decision rule are strong enough for the claim being made.

Topic 06

Domain-native metrics

A domain-native metric asks what correctness means inside the field itself. Medicine, law, robotics, science, code, audio, video, images, tables, and education do not fail in the same way, so they should not be evaluated with the same generic score.

Generic evaluation is tempting because it makes comparison easy. But easy comparison can hide the thing that matters. A clinical answer may be grammatically strong and medically unsafe. A video may match a prompt and violate basic physics. A robot policy may recognize objects and fail because it lacks situated memory. A generated table may look plausible and destroy dependency structure. A proof may sound convincing and fail at the kernel. The domain defines the consequence.

Domain-native evaluation starts by asking what the world will treat as success. In healthcare, that may be expert criteria, temporal faithfulness, patient risk, and unsupported guidance. In science, it may be physical validity, simulation-real gaps, fitness under distribution shift, or whether a hypothesis helps downstream work. In robotics, it may be situated awareness, memory, contact feasibility, and task completion. In code, it may be tests, proofs, compiler semantics, and regression behavior. In media, it may be perceptual quality, temporal coherence, grounding, and user-noticeable defects.

The hard part is that domain-native metrics are less portable. They require expertise, special data, simulators, real environments, or expensive annotation. But that cost is often the price of measuring the real thing. A universal metric is useful only up to the point where the domain's failure mode disappears from view.

Healthcare
Measure expert correctness, harm, temporal clinical evidence, faithfulness, unsupported claims, and user vulnerability.
Science
Measure physical realism, sim-to-real behavior, downstream utility, causal validity, and distribution shift.
Robotics
Measure situated awareness, memory, action relevance, task progress, contact constraints, and safety recovery.
Code and math
Measure execution, semantic preservation, proof acceptance, specifications, regressions, and formal obligations.
Multimodal media
Measure visual grounding, temporal order, acoustic evidence, perceptual quality, artifact flaws, and human-noticeable differences.
Structured data
Measure table structure, dependencies, calibration, decision value, fairness, and operational loss.

How papers define correctness by domain

CounselBench uses mental-health professionals and adversarial framing because ordinary answer matching is not enough for clinical guidance. Seizure-Semiology-Suite evaluates clinical video and report understanding through temporal medical faithfulness, including laterality, localization, and symptom sequence. PhyWorldBench asks whether generated video respects physical realism, while RealPDEBench evaluates scientific ML through real-world physical systems and multiple data- and physics-oriented metrics. FLIP2 tests protein fitness under engineering-relevant distribution shifts, where generic prediction accuracy is not the whole question.

SAW-Bench, RoboMME, dWorldEval, and WoW! make embodied evaluation domain-native by asking whether perception, memory, generated futures, or world models support action. TabStruct evaluates generated tabular data by structural fidelity, not only marginal resemblance. FeatJND asks what feature distortion is just noticeable under quantization. UniPercept, TTSDS2, ImageDoctor, and DeceptionDecoded show the media version: images, speech, and image-caption pairs need metrics tied to perceptual quality, objective audio judgments, grounded flaw diagnosis, source attribution, and misleading intent.

First-principles line

A metric is domain-native when it measures the consequence the domain actually cares about, not the easiest proxy that fits a generic benchmark format.

Topic 07

Rare failures and tail risk

A failure can be rare in evaluation and still common enough to matter in deployment. If a system is used millions of times, the tail becomes part of the product.

Average benchmark scores are weak evidence for rare failures. A model can look safe, reliable, or non-degenerate on ordinary samples while still failing under pressure, long interaction, compression, prompt injection, unusual user goals, or low-probability output paths. The absence of a bad event in a small benchmark does not prove the event is unlikely enough. It may only prove that the benchmark did not look in the right part of the space.

Rare-failure evaluation starts from a different question: what event would be costly if it happened, and how can we estimate or expose its probability? Sometimes the method is statistical tail estimation. Sometimes it is adversarial or pressure testing. Sometimes it is controlled perturbation. Sometimes it is token-level diagnostics that separate entering a failure loop from staying in it. Sometimes it is a living benchmark that keeps adding attacks because the threat surface changes.

This is not only about safety. Tail behavior matters for reliability, privacy, legal compliance, generation quality, robustness, and user trust. A benchmark that reports only the mean can hide a system that is usually fine and occasionally unacceptable. The more serious the failure cost, the more evaluation must search beyond the average case.

Tail probability
Estimate how often the bad event occurs, not only whether it appeared in a small sample.
Pressure behavior
Test whether user pressure, time pressure, persuasion, or multi-turn context changes the system's safety or honesty.
Adversarial search
Use jailbreaks, prompt injection, boundary tests, and controlled perturbations to find failure regions deliberately.
Degeneration
Measure repetition, loop entry, loop persistence, and generation collapse that aggregate task accuracy may miss.
Hidden intent
Evaluate deception, misleading source use, and intent that may not be visible in literal surface content.
Living benchmarks
Update the evaluation as attacks, models, and deployment surfaces change.

How papers expose rare failures

Rare Event Analysis of LLMs and Tail Risks in LM Outputs treat low-probability harmful behavior as an estimand, using tools such as Monte Carlo, MCMC, transition path sampling, and importance sampling. FOCUS & RePAIR shows why token-level diagnostics matter: repetition failure has both loop-entry risk and loop-persistence risk, and neither is necessarily visible in ordinary task accuracy. Copyright-Bench and SecFid add policy and deployment cost: user pressure and prompt-injection defenses should be evaluated by the harm of violations and the cost of false defensive drops.

Pressure Reveals Character makes pressure itself part of the evaluation condition, testing honesty, safety, non-manipulation, robustness, corrigibility, and scheming under multi-turn scenarios. Jailbreak Foundry turns jailbreak papers into executable modules so safety evaluation can keep pace with attack methods. Harnessing Non-Adversarial Robustness and 2-SAT Robustness define controlled perturbation families instead of relying on anecdotal failures. LLM Deception on Benign Prompts and DeceptionDecoded show the hidden-intent version: evaluation must sometimes measure what a user is led to believe, not only the literal answer.

First-principles line

Rare-failure evaluation asks what costly event the average hides, where that event lives, and what evidence is strong enough to estimate or expose it before deployment does.

Topic 08

Cost-aware verification

Verification is not free. Stronger checks usually cost more time, money, compute, tool access, expert attention, or user patience. Good evaluation asks which checks are worth paying for.

A perfect checker would be simple: run it on every output and trust the result. Real evaluation does not work that way. A theorem prover may be strong but slow. A human expert may be accurate but scarce. A sandbox may be expensive to run at scale. A model judge may be cheap but noisy. A weak verifier may be useful for easy cases and dangerous for borderline ones. Cost-aware verification treats checking as a decision problem, not a ritual.

The key tradeoff is between error cost and verification cost. If a wrong answer is cheap, a light check may be enough. If a wrong answer can cause legal, medical, security, financial, or physical harm, the system may need stronger evidence, deferral, or human review. The evaluation policy should say when to accept, reject, escalate, or spend more computation. A benchmark that ignores verifier cost can reward systems that are accurate only because they used impractical amounts of checking.

Cost also changes the meaning of reliability. A system that needs a strong verifier on every step may be reliable but unusable. A system that uses only cheap checks may be fast but unsafe. The goal is not always maximal verification. The goal is the right verification policy for the risk, uncertainty, and time scale of the task.

Cheap check
Useful for common, low-risk, high-confidence cases. Dangerous when treated as proof of a stronger claim.
Strong check
Needed when the claim is consequential, ambiguous, or likely to be exploited. Often slower or more expensive.
Deferral
The system should know when to ask a stronger verifier, expert, user, or runtime environment before accepting.
False accept
A bad output passes. This dominates when harm from trusting the system is high.
False reject
A good output is blocked or sent to expensive review. This dominates when excessive caution makes the system unusable.
Latency budget
A check that is correct too late may still fail the deployment setting, especially for agents and embodied systems.

How papers make verification cost explicit

Weak-Strong Verification is the central paper for this topic because it asks when to accept a cheap weak verifier, reject, or defer to a stronger expensive verifier. AstaBench also makes cost part of the evaluation object by comparing scientific research agents while accounting for tool access, interfaces, baselines, and expense. SimuHome brings latency into the metric: a stronger reasoning model can be less useful if the smart-home environment requires fast response.

SecFid evaluates prompt-injection defense through deployment cost, not only attack success. The right defense depends on the cost of a hijack versus the cost of dropping benign content. ATLAS reduces evaluation cost through adaptive psychometric item selection. Micro-Benchmarking Reliability asks how many examples are needed before a ranking should be trusted. Prescriptive Scaling and Accuracy Auctions broaden the same principle: capability, cost, and user value should be measured together rather than collapsed into one raw accuracy score.

First-principles line

Cost-aware verification chooses the weakest check that is strong enough for the risk, and escalates when uncertainty or failure cost makes cheap evidence unsafe.

Topic 09

Benchmark reliability

A benchmark result is not a fact by itself. It is an estimate produced by a protocol, sample, scoring rule, judge, model state, and testing context.

Benchmarks become unreliable when they are treated as direct measurements of capability without asking how the number was produced. A small sample can flip rankings. A narrow benchmark can reward memorized surface patterns. A public benchmark can leak into training. A judge can prefer one style. A protocol can favor models that were tuned for it. A single aggregate can hide disagreement across subgroups, domains, languages, or failure modes.

Reliability is therefore about how much the result would survive reasonable changes. Would the ranking hold with another sample? Another judge? Another prompt wording? Another interface? Another training-before-testing protocol? Another set of domains? Another cost budget? If the answer is no, the benchmark may still be useful, but the claim should be narrower. The score should come with uncertainty about what it means.

This does not make benchmarking futile. It makes benchmark design more like experimental design. The evaluator must define the population of tasks, sampling method, scoring rule, confidence, known confounders, and intended use of the result. A benchmark is reliable when its variation is understood well enough that users do not overclaim from it.

Sampling noise
Small or unrepresentative test sets can make unstable rankings look precise.
Leakage
Public or repeated benchmarks can become training data, tuning targets, or memorized formats.
Protocol dependence
Rankings may change under different prompts, tools, budgets, interfaces, or train-before-test designs.
Judge variance
Different judges, rubrics, or calibration sets can produce different conclusions.
Subgroup masking
A high aggregate score can hide failures in languages, domains, difficulty bands, or rare conditions.
External validity
A benchmark matters only if performance transfers to the real use case it claims to represent.

How papers stress-test benchmark reliability

Micro-Benchmarking Reliability directly asks whether small benchmark subsets preserve pairwise model rankings from the full benchmark, showing why cheap evaluation can overstate confidence. ATLAS uses psychometric item response theory and adaptive item selection to estimate ability with fewer questions, making reliability an item-design problem. CV Relative Instability shows that even individually stable learners can produce unstable model comparisons under cross-validation, so comparison reliability is not guaranteed by model stability alone.

Train-before-Test argues that rankings can change when models are fine-tuned before evaluation, making protocol part of the measurement claim. Hedging on the Frontier uses public benchmark dominance relations as side information for few-sample new-task learning, which treats benchmark transfer as uncertain evidence rather than direct truth. LLM Adaptability Limits separates task-definition familiarity from text-level memorization, sharpening the leakage question. TokSuite controls tokenizer choice across matched pretrained models, showing that evaluation can isolate one design variable only when the benchmark controls the rest.

First-principles line

Benchmark reliability asks whether the result would still support the same claim under reasonable changes to sample, judge, protocol, model state, and deployment setting.

Topic 10

Evaluation as pressure

Evaluation does not only describe a model after the fact. Once a score is used for training, selection, release, ranking, or trust, it becomes pressure on what the system learns to do.

A metric is an incentive. It tells builders which behavior is worth preserving, which failure matters, which shortcut will be tolerated, and which improvement will count. If the metric rewards exact executable success, systems are pushed toward code that runs, proofs that verify, actions that change state correctly, and outputs that satisfy a concrete contract. If the metric rewards judge preference, systems are pushed toward the style, length, confidence, and reasoning shape that the judge likes. If the metric rewards safety under pressure, systems are pushed to hold their policy under difficult interaction rather than only in easy prompts.

This is why evaluation must be designed as part of the training and deployment system, not as a scoreboard placed at the end. A public leaderboard can cause overfitting. A weak judge can reward shallow fluency. A reward model can turn a proxy into the real objective. A pass/fail gate can make systems hide uncertainty or avoid useful attempts. A cost-insensitive benchmark can make impractical methods look better than usable ones. A rare-failure evaluation can make hidden tail behavior visible enough to repair. The evaluation surface decides what kind of pressure the model feels.

The first-principles question is: what behavior should become cheaper and more likely because this evaluation exists? For a code agent, the answer may be semantic correctness under execution. For a medical model, it may be threshold-sensitive recognition of danger. For a legal model, it may be citation-grounded distinction between similar clauses. For a UI agent, it may be robust control across changed screens. For a safety model, it may be stable honesty under social pressure. The metric should place pressure on the behavior that matters in the use case, not merely on the easiest thing to count.

Rewarded behavior
The metric makes some behavior worth preserving: exact execution, calibrated uncertainty, honest refusal, useful retrieval, low latency, or robust action.
Shortcut surface
A weak metric leaves room for fake success: polished explanations, memorized benchmark formats, judge-pleasing style, or safe-looking answers that do not solve the real task.
Training signal
Scores can become reward data, verifier labels, preference pairs, curriculum filters, or selection rules, so measurement shapes the next model.
Deployment gate
Evaluation decides what reaches users, what gets deferred, what needs a stronger check, and what failure cost is acceptable.
Distribution shift
Pressure can overfit to benchmark conditions if the test surface is too narrow, too public, too stylistic, or too different from deployment.
Feedback repair
A good evaluation does not only assign a number. It exposes the failure mode clearly enough to create better data, better verifiers, or better protocol.

How papers turn evaluation into pressure

Gaia2 is the cleanest case because action-level verifiers do double duty. They measure whether an agent's write actions are valid, and they can also become reward signals for reinforcement learning. MC-Search makes a similar point for multimodal reasoning: HAVE-verified reasoning chains and Search-Align do not only report quality, they shape the search path toward grounded visual-textual steps. CE-Graph uses Propose-and-Verify to edit agent graphs with counterexamples, turning evaluation failures into structural improvement. In these papers, measurement is already an intervention.

Pressure Reveals Character makes social and behavioral pressure explicit. The model is not only checked for task completion; it is checked for honesty, safety, non-manipulation, robustness, corrigibility, and related traits under multi-turn pressure. Weak-Strong Verification turns pressure into a decision policy: accept cheap verification when confidence is enough, reject when failure is clear, and defer when the cost of being wrong is too high. Pre/Mid/RL Reasoning asks how pre-training, mid-training, and reinforcement learning each affect reasoning behavior, which is another way of asking what training pressures create the observed capability.

FOCUS & RePAIR shows why the pressure must sometimes be aimed below final accuracy. Repetition failure can hide in token-level generation dynamics, so the evaluation has to expose loop entry and loop persistence before repair is possible. Copyright-Bench and SecFid show policy-sensitive pressure: copyright compliance and prompt-injection defense should not be rewarded only for conservative blocking, because false drops and usability costs matter too. Train-before-Test and benchmark-reliability papers add the protocol lesson: when models adapt before evaluation or train toward known benchmarks, the benchmark itself becomes part of the learning environment.

First-principles line

Evaluation is pressure: the metric decides which behavior is rewarded, which shortcut is tolerated, which uncertainty is escalated, and which failures become visible enough to repair.

Topic 11

Paper-by-paper map

The papers under this theme are not just a list of benchmarks. Each one chooses a unit of evidence, a way to check it, a failure mode to expose, and a claim that the score is allowed to support.

A useful map starts by asking what the paper refuses to trust. Some papers refuse to trust fluent text, so they run code, prove contracts, execute web pages, or put agents in environments. Some refuse to trust a single final answer, so they score trajectories, tool use, action steps, latency, and recovery. Some refuse to trust generic accuracy, so they use legal, medical, physics, robotics, security, or UI-native criteria. Some refuse to trust ordinary sampling, so they study tails, pressure, disagreement, leakage, and ranking instability.

This matters because two papers can both be called benchmarks while doing very different conceptual work. CyberGym measures whether a security action reproduces a vulnerability and respects a patch. OmniVerifier measures whether an evaluator can judge multimodal output aspects. Rare Event Analysis estimates low-probability harmful behavior. AstaBench compares research agents under controlled tool and cost conditions. These are different measurement objects, not interchangeable leaderboard rows.

The paper map therefore asks five questions for every contribution: what is the unit, what is the check, what is the hidden failure, what domain rule defines correctness, and what behavior would convince us the representation or agent learned the right thing? That frame keeps the theme connected to the earlier sections on unit choice, executable checks, judge reliability, rare failures, cost, benchmark reliability, and evaluation pressure.

Executable papers
CyberGym, SandboxEscapeBench, CVE-Factory, CIRBench, VERINA, AlgoVeri, EditBench, WebDevJudge, Vision2Web, and MiniAppBench ask whether an artifact works under the domain's real contract.
Agent papers
Gaia2, AstaBench, SimuHome, BIRD-INTERACT, tau2-bench, OpenApps, VenusBench-Mobile, PIPE, CausalGame, and MADQA measure runs, actions, tools, state changes, and process failures.
Judge papers
OmniVerifier, FRABench/UFEval, Pressure Reveals Character, Weak-Strong Verification, VALUEFLOW, Ranking Time Series, AGREE, EigenBench, and Known More Know Clearer study the reliability of the evaluator itself.
Tail-risk papers
Rare Event Analysis, Tail Risks in LM Outputs, FOCUS & RePAIR, Jailbreak Foundry, 2-SAT Robustness, Harnessing Non-Adversarial Robustness, and deception papers look for failures hidden by averages.
Domain papers
CounselBench, Seizure-Semiology-Suite, PhyWorldBench, RealPDEBench, RoboMME, CALIPER, ImageDoctor, TabStruct, and SecFid define success using field-specific evidence rather than generic answer similarity.
Meta-evaluation papers
ATLAS, Micro-Benchmarking Reliability, Train-before-Test, TokSuite, LLM Adaptability Limits, Hedging on the Frontier, CV Relative Instability, Prescriptive Scaling, and Accuracy Auctions ask what the score itself means.

How to read the papers through one lens

The executable family says: do not trust an answer if the real domain has a stronger check. Security needs an exploit or blocked exploit. Code needs tests, semantics, or proofs. Web and app generation need rendered behavior and interaction. The agent family says: do not trust a final response when the path matters. A research agent, home agent, mobile agent, SQL agent, or causal-science agent can fail by using the wrong tool, acting too late, forgetting state, failing to ask for clarification, or reaching the right end by an invalid route.

The judge family says: do not trust human-like evaluation without checking the evaluator. Multimodal quality, subjective value, behavioral character, ranking, and weak verification all require calibration because the measuring device can be biased, noisy, or too cheap for the risk. The tail-risk family says: do not trust average accuracy when deployment volume makes rare failures important. Repetition loops, jailbreaks, non-adversarial perturbations, deception, and low-probability harmful outputs need targeted search or statistical estimation.

The domain and meta-evaluation families complete the map. Domain-native papers remind us that correctness is often defined by law, medicine, physics, robotics, interfaces, tables, perception, or security economics. Meta-evaluation papers remind us that a benchmark is a claim under a protocol, not a timeless truth. Together, the papers show evaluation moving from one number toward a structured account of evidence, failure, cost, and use.

First-principles line

A paper belongs in this theme when it makes measurement more faithful: it chooses the right evidence unit, checks it with the strongest practical signal, exposes a failure that averages miss, or clarifies what a benchmark score can honestly claim.

Topic 12

Final synthesis

Evaluation is disciplined evidence selection. It decides what counts as proof that a system can act, generate, reason, perceive, defer, recover, or stay safe in the setting that matters.

The deepest mistake is to treat evaluation as a neutral number attached to a model. Evaluation is a designed relation between a use case and evidence. The use case says what difference matters. The evidence unit says where that difference must survive. The check says how we know. The protocol says under what conditions the claim is valid. The cost model says how much certainty is practical. The pressure created by the metric says what future systems will learn to optimize.

Across these papers, the field is moving away from one shallow idea of benchmarking. The old pattern was: give a prompt, collect an answer, compare it to a label, average the result. That pattern still works for some narrow tasks, but it breaks when systems use tools, interact with users, generate artifacts, act over time, handle safety-critical domains, or create outputs where correctness is not a single string. The new pattern is richer: execute the artifact, trace the trajectory, calibrate the judge, estimate the tail, measure cost, test transfer, and state the limits of the claim.

This synthesis also connects evaluation back to representation. A representation is shaped by the training task, and a system is shaped by the evaluation task. If the unit of representation decides what information survives inside the model, the unit of evaluation decides what behavior survives outside the model. Good evaluation keeps the answer-changing distinctions alive: the exact character in a drug name, the object boundary in an image, the action phase in a video, the proof obligation in code, the danger sign in medicine, the legal distinction in a clause, the hidden pressure in a conversation, or the rare failure in deployment.

Use case first
Start from the decision the evaluation will support, not from the easiest dataset, metric, or leaderboard format.
Right evidence unit
Choose the smallest or largest unit that preserves the answer-changing fact: token, patch, action, trajectory, object, patient state, proof, or policy behavior.
Strongest practical check
Use execution when possible, domain rules when needed, calibrated judges when exact truth is unavailable, and escalation when cheap checks are unsafe.
Failure visibility
Design tests that reveal the important misses: rare events, leakage, shortcut learning, degeneration, pressure failure, distribution shift, and subgroup collapse.
Claim discipline
Say what the score proves, what it does not prove, which protocol produced it, and how much uncertainty remains.
Learning pressure
Remember that any metric used for training, selection, deployment, or status will shape the next generation of systems.

The whole theme in one pass

Executable evaluation says the output should meet the real contract of the domain. Dynamic evaluation says the path matters when the system acts over time. Judge-based evaluation says the measuring device must be measured. Domain-native evaluation says correctness comes from the field, not from generic similarity. Rare-failure evaluation says average accuracy can miss the behavior that matters most. Cost-aware verification says certainty is valuable but not free. Benchmark reliability says a score is an estimate under a protocol. Evaluation as pressure says the score will reshape the system once it becomes an incentive.

Those are not separate slogans. They are the same idea applied at different failure points. When text grading is too weak, execute. When final answers hide process failure, trace. When exact truth is unavailable, calibrate the judge. When the domain has its own contract, respect it. When the danger is rare, sample differently. When strong checks are expensive, defer intelligently. When the benchmark is small, public, or protocol-dependent, narrow the claim. When the metric becomes a reward, ask what it will teach the model to become.

First-principles line

A good evaluation is a promise about evidence: if a system passes, the result should mean something specific, useful, and honest about how it will behave in the world where the decision matters.

Approach families

How the theme divides

Executable consequence
The strongest evaluations run something. Code executes, a browser state changes, an exploit is tested, a compiler output is checked, a generated web page is inspected, or a world model is placed in a closed loop.
Judge calibration
When exact truth is not available, the evaluator itself becomes the object of study. Human-calibrated judges, weak-strong verifiers, pairwise ranking, psychometrics, and subjective scoring all ask whether the measurement mechanism is reliable.
Hidden failure measurement
Rare-event analysis, pressure tests, reasoning-effort checks, degeneration diagnostics, and robustness certifications look for problems that ordinary average-case benchmark scores miss.
Dynamic interaction
Agent, user-simulation, database, mobile, smart-home, and causal-scientist benchmarks evaluate a trajectory. The unit of evidence is a run: task, observations, actions, state changes, verifier output, cost, and failure mode.
Subthemes

The rich structure inside evaluation

Executable evaluation: stop grading text, check consequences

This is the cleanest subtheme. The basic failure is that a model can sound competent without changing the world correctly. Executable evaluation asks the model to produce something testable: a proof-of-concept, code edit, compiler optimization, generated interface, formal proof, or dynamic database interaction. The approach is to put the model's output into an environment and let the environment answer.

This matters because executable checks create pressure that ordinary text grading cannot. A PoC either triggers the vulnerable version and does not trigger the patched version, or it fails. A compiler transformation either preserves semantics and improves performance, or it does not. A web page either matches the functional and visual intent, or the evaluator finds the mismatch. The score is tied to behavior.

CyberGym
ICLR 2026
CyberGym starts from the principle that cybersecurity capability cannot be measured by asking a model to describe vulnerabilities. Security work is behavioral: a vulnerability is reproduced, a proof-of-concept executes, a patch blocks the issue, and the result can be checked. The paper's core approach is to make agents generate concrete PoC tests for real vulnerabilities and validate them against pre-patch and post-patch code. Its broader significance is that serious AI evaluation is moving from answer assessment to controlled world-state assessment.
SandboxEscapeBench
ICML 2026
SandboxEscapeBench makes infrastructure boundary failure measurable. The first-principles problem is that a tool-using model may do harm not by saying the wrong thing, but by crossing a runtime boundary: escaping a container, reaching a host resource, or exploiting a misconfiguration. The benchmark turns that into a CTF-style check with nested isolation and concrete objectives. It belongs in evaluation because the success condition is not rhetoric; it is whether the environment was breached under controlled rules.
CVE-Factory
ICML 2026
CVE-Factory addresses a bottleneck in security evaluation: realistic vulnerability tasks are hard to produce at scale. The method shape is to generate executable CVE-style tasks that can support live code-security benchmarking. The conceptual contribution is task supply. If the field wants to measure code-security agents without overfitting a small static set, it needs a factory for varied, checkable vulnerabilities and patches.
CIRBench
ICML 2026
CIRBench treats compiler optimization as a semantic measurement problem. A model-generated optimization is not good because it looks clever or resembles prior code; it is good if it preserves meaning and improves execution. The approach combines verifier checks, equivalence reasoning, and performance measurement. The paper fits the theme because it shows how code evaluation becomes stronger when the benchmark respects the actual contract of the domain.
EditBench, VERINA, AlgoVeri
ICLR / ICML 2026
These papers sit in the same executable-code family but aim at different surfaces: realistic instructed edits, verifiable code generation, and cross-tool proof capability. Their shared first-principles claim is that code intelligence must be judged semantically. Did the edit satisfy the user's intent in context? Does the generated code verify? Does the proof system accept the contract? They reduce dependence on surface similarity and move toward domain-native correctness.
WebDevJudge, Vision2Web, MiniAppBench
ICLR / ICML 2026
This cluster evaluates generated software artifacts rather than plain answers. WebDevJudge asks whether multimodal critics can assess web-development quality, Vision2Web tests hierarchical visual website development, and MiniAppBench evaluates interactive app generation. The important shared problem is that a UI can be syntactically present yet unusable, visually wrong, or behaviorally incomplete. The evaluator must inspect structure, visual result, and interaction, not just code text.

Dynamic agents and task worlds: evaluate trajectories, not snapshots

The next subtheme is interaction. A model that acts over time can fail because it misread the first observation, chose the wrong tool, ignored feedback, got trapped in a loop, ran too slowly, or completed the task while violating the intended process. Static question answering erases those distinctions. Dynamic benchmarks therefore record the trajectory and often include tools, user simulators, environment changes, or asynchronous events.

This family is important because agents are becoming workflows. The question is not only whether a model knows a fact, but whether it can coordinate perception, state, action, and recovery under changing conditions. That is why cost, latency, interface, and environment variation appear as evaluation variables rather than implementation details.

Gaia2
ICLR 2026
Gaia2 uses dynamic and asynchronous environments with action-level verifiers. The first-principles problem is that final-answer scoring cannot tell whether an agent's intermediate actions were valid, useful, or harmful. By attaching verifiers to write actions, Gaia2 makes fine-grained process measurable and usable for reward training. It connects evaluation to RL because a verifier can become both a score and a learning signal.
AstaBench
ICLR 2026
AstaBench evaluates scientific research agents under controlled tool and cost conditions. The paper matters because research-agent evaluation is full of confounders: one agent may have better tools, a more permissive interface, or a higher budget. AstaBench's approach is to benchmark many agent classes while accounting for those confounders. The conceptual contribution is measurement discipline for agent workflows.
SimuHome
ICLR 2026
SimuHome evaluates smart-home agents where time and environment awareness matter. The first-principles issue is that an agent can be more capable in reasoning but worse in deployment if it is too slow or poorly synchronized with the environment. The paper's capability-latency tradeoff is a useful evaluation idea: intelligence must be measured against the response window of the world where it acts.
BIRD-INTERACT and tau2-bench
ICLR / ICML 2026
These papers evaluate interaction with users, databases, and tools. BIRD-INTERACT reimagines text-to-SQL as dynamic interaction with databases and knowledge bases, while tau2-bench exposes user-guidance coordination failures. The big idea is that many professional tasks are not single-turn answers. They involve asking, updating, retrieving, checking, and satisfying a user goal through a sequence.
OpenApps, VenusBench-Mobile, PIPE
ICLR / ICML 2026
This group measures agents under interface variation. OpenApps shows success can swing sharply as app appearance or content changes, VenusBench-Mobile identifies perception and memory failures in mobile agents, and PIPE evaluates agents under interface rewrites. The first-principles point is that UI agents should not be credited for memorizing one surface; they need robust control under equivalent but different interfaces.
CausalGame and MADQA
ICML 2026
CausalGame evaluates an AI scientist across experiment design, data collection, inference, and report explanation. MADQA compares human-agent-oracle process gaps. Both make evaluation richer by exposing where a process departs from ideal behavior. The score is not only whether the final response matches; it is whether the steps leading there were causally or procedurally sound.

Judge and verifier reliability: measure the measuring device

When no exact executable check exists, evaluation depends on judges, rankings, rubrics, or proxy metrics. That creates a second-order problem: how do we know the evaluator is reliable? This subtheme studies the judge itself. It includes human-calibrated LLM judges, weak-strong verification thresholds, pairwise ranking under noisy labels, subjective construct measurement, known-unknown calibration, and psychometric item selection.

The shared approach is humility about measurement. If the evaluator is noisy, biased, too expensive, or inconsistent across model families, then the benchmark result is not a fact; it is an estimate with assumptions. These papers try to expose those assumptions and sometimes optimize the evaluation process itself.

OmniVerifier and FRABench/UFEval
ICLR 2026
OmniVerifier and FRABench/UFEval both ask whether a model can act as a fine-grained evaluator across multimodal tasks. The first-principles problem is that generated images, interleaved outputs, and visual edits often cannot be scored by one exact string. These papers build or test evaluator models with explicit aspects or task categories. Their importance is that model-generated content needs a judging layer as sophisticated as the generator.
Pressure Reveals Character
ICML 2026
Pressure Reveals Character uses a human-calibrated judge for multi-turn pressure scenarios. It is not measuring task accuracy; it is measuring behavioral properties such as honesty, safety, manipulation, robustness, and corrigibility. That makes it a measurement paper because the target construct is subtle. The paper's value is in making those constructs observable enough to compare models, while still acknowledging judge calibration limits.
Weak-Strong Verification
ICML 2026
Weak-Strong Verification studies when to accept a cheap weak verifier, when to reject, and when to defer to a stronger expensive verifier. The core problem is economic and epistemic: verification has cost, and cheap checks are not always trustworthy. The approach creates thresholds around calibrated weak scores so evaluation can trade off speed, cost, and reliability rather than pretending all verification is equal.
ATLAS and Micro-Benchmarking Reliability
ICML / ICLR 2026
ATLAS uses psychometric item response theory to estimate model ability with fewer benchmark questions. Micro-Benchmarking Reliability studies how small evaluation sets can produce unstable model rankings. Together they point at the same issue: benchmark sampling is a statistical design problem. A small or poorly selected test can create confidence where none is deserved.
VALUEFLOW, Ranking Time Series, AGREE
ICML 2026
These papers handle subjective or noisy scoring. VALUEFLOW uses ranking-based measurement for subjective constructs, Ranking Time Series studies pairwise ranking under noisy annotation, and AGREE handles multidimensional aesthetic scoring. The shared principle is that human preference is not a clean scalar label. It has dimensions, disagreement, and context, so the measurement model must represent that complexity.
Known More Know Clearer, EigenBench, Train-before-Test
ICML / ICLR 2026
This cluster asks what model comparisons really mean. Known-unknown calibration examines whether models know what they do not know; EigenBench gives a label-free way to study subjective model values; Train-before-Test argues rankings can shift when models are trained before testing. The connecting idea is that an evaluation result is conditional on protocol, model state, and what the benchmark claims to measure.

Rare, hidden, and adversarial failures: averages are not enough

A high average score can hide the failures that matter most. Deployment failures can be rare, but rare events at large scale are not negligible. Safety failures may appear only under pressure, after prompt injection, in long context, or when a model discovers a shortcut. This subtheme develops metrics and benchmarks for tails, degeneration, robustness, legal compliance, deception, and hidden failure modes.

The method shape is to search for failure regimes deliberately rather than waiting for a random benchmark sample to include them. That includes statistical tail estimation, stress testing, prompt-injection cost models, legal-pressure scenarios, randomness-based robustness tests, and token-level degeneration analysis.

Rare Event Analysis of LLMs and Tail Risks in LM Outputs
ICML 2026
Rare Event Analysis treats low-probability behavior as something to estimate with methods such as Monte Carlo, MCMC, transition path sampling, and importance sampling. Tail Risks in LM Outputs belongs to the same conceptual family. The first-principles point is that absence from a normal benchmark is weak evidence when deployment volume is enormous. Evaluation must ask how likely the bad event is, not only whether we happened to observe it.
FOCUS & RePAIR
ICML 2026
FOCUS & RePAIR studies repetition and degeneration under compression. It separates loop entry from loop persistence, which is important because a model can look fine on task accuracy but still degrade badly in generation dynamics. The paper shows that evaluation needs token-level behavioral diagnostics when aggregate metrics fail to expose the failure.
Copyright-Bench and SecFid
ICML 2026
Copyright-Bench measures user pressure and legal compliance, while SecFid evaluates prompt-injection defense through deployment cost. Both treat evaluation as a policy-sensitive tradeoff. The question is not simply "was the output allowed?" but how the model behaves under user pressure, what defensive errors cost, and whether a mitigation drops too much benign content to be useful.
Harnessing Non-Adversarial Robustness and 2-SAT Robustness
ICML 2026
These papers look for robustness beyond standard adversarial examples. One studies certification under random prompts; the other uses parameterized logical robustness tests. The conceptual move is to define controlled perturbation families where model behavior can be measured systematically rather than relying on anecdotal failures.
LLM Deception on Benign Prompts and DeceptionDecoded
ICLR 2026
These papers evaluate deception and misleading intent. One studies deception on benign prompts, while DeceptionDecoded uses image-caption pairs to detect creator intent and source attribution. Their shared problem is that harmful or misleading behavior may not be visible from literal content alone. Evaluation has to reason about intent, context, and what the user is likely to infer.

Domain-specific measurement: each field defines correctness differently

A general benchmark cannot cover every kind of correctness. Medicine, physics, robotics, text-to-video, tabular data, speech, protein fitness, formal math, and causal discovery each have their own meaning of success. This subtheme builds benchmarks that respect the domain's native constraints rather than forcing everything into generic QA.

The approach is to identify the domain's real unit of evaluation. For medical temporal reports, faithfulness to clinical features matters. For text-to-video, physical realism matters. For tabular generators, structural fidelity matters. For scientific ML, sim-to-real or PDE metrics matter. For formal math, proof acceptance and downstream consequence matter.

CounselBench and Seizure-Semiology-Suite
ICLR / ICML 2026
CounselBench evaluates mental-health QA with expert and adversarial framing, while Seizure-Semiology-Suite evaluates clinical video/report understanding through medical temporal-report faithfulness. These papers show that healthcare evaluation is not just answer correctness. It must account for safety, expert criteria, temporal clinical evidence, and the harm of plausible but unsupported guidance.
PhyWorldBench, RealPDEBench, FLIP2
ICLR / ICML 2026
These benchmarks measure scientific and physical domains. PhyWorldBench asks whether text-to-video respects physical realism, RealPDEBench evaluates complex physical systems with real-world data, and FLIP2 tests protein fitness under distribution shift. The shared principle is that scientific evaluation must use domain behavior, not generic language plausibility.
SAW-Bench, RoboMME, dWorldEval
ICML 2026
This robotics and embodied-evaluation cluster measures situated awareness, robotic memory, and policy ranking. The first-principles issue is that embodied systems need memory, spatial coherence, and action relevance. Evaluation therefore has to inspect more than recognition accuracy: it must measure whether perception supports action in a changing world.
TabStruct, FeatJND, UniPercept, TTSDS2
ICLR / ICML 2026
These papers measure artifact quality in different media: tabular structural fidelity, feature-space just-noticeable differences for quantization, perceptual-level image benchmarks, and validated objective text-to-speech evaluation. The common thread is that each medium needs a measurement scale tied to what users or downstream systems actually notice.
WZ-LLM, BrokenMath, FPS, INDUCTION
ICML 2026
This formal reasoning cluster evaluates proof, theorem proving, constructive problem solving, and finite-structure logical induction. The domain's advantage is that correctness can sometimes be checked exactly. The challenge is that models may exploit proof style, sycophancy, or narrow benchmark patterns, so evaluation must inspect both proof validity and process robustness.

What this theme says about the conference

The evaluation theme says the field knows its measurement layer is under strain. Models are now systems: they act, generate, browse, reason, retrieve, persuade, code, and operate under cost and safety constraints. The old habit of reporting one benchmark number does not answer the question people now need answered: can this system be trusted in the setting where it will be used?

The answer emerging across these papers is not one master benchmark. It is a measurement stack: executable checks where possible, calibrated judges where necessary, rare-event tools for tails, process traces for agents, and domain-specific metrics where correctness has its own structure. The open problem is integration. The field has many instruments; it still needs discipline about when each instrument is valid.
