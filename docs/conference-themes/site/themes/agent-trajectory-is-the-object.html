CORE

A final answer hides most of the work

Once a model can act, the important evidence is the path it took.

A final answer can be right for the wrong reason. It can be copied from a hint, produced after unsafe actions, reached through repeated loops, or supported by stale memory. A wrong answer can also hide useful partial work. Reading only the last message throws away the evidence needed to judge the system.

The grouped agent papers keep returning to this point. RAGEN-2 studies reasoning collapse where long traces become input-agnostic. TerminalTraj stores command-line work as verified trajectories rather than final patches. Gaia2 evaluates actions in environments that change over time. MemoryBench treats accumulated user feedback as service-time state. OpenApps changes app instances to expose brittle UI grounding. RedTeamCUA shows that malicious content in the environment can become a false instruction.

Core rule
For an agent, the unit of evidence is the trajectory: state, action, observation, memory, and verification over time.

FIRST PRINCIPLE

An agent is a model joined to a changing world

A normal model answer can be judged as a static object. An agent cannot. The agent's output is mixed with time, tools, memory, permissions, and outside state.

That changes the unit of analysis. If a model answers a math question in one message, the answer may be the thing to check. If an agent edits a repository, controls a browser, runs a terminal, teaches a student, handles a biomedical task, or navigates a robot scene, the final message is only the end of a path. The path contains the evidence: what the agent saw, which state it believed, which actions it took, which feedback it received, what it saved, and what it ignored.

The first principle is simple: when a system acts over time, behavior is not a point. It is a sequence. A correct last step can still be unsafe if earlier steps crossed a boundary. A failed last step can still teach useful recovery behavior. A long reasoning trace can still be empty if it does not respond to the input. A memory write can improve future work or poison it. A tool call can solve the task or silently change the world in a way the score never sees.

That is why trajectory papers matter. They are not adding logging as decoration. They are changing what counts as evidence. The evidence becomes the ordered relation between state, action, observation, and check.

OBJECT

The object is the path through state

A trajectory is not a transcript. It is a record of how the world and the agent's beliefs changed step by step.

World state

The files, page, database, app, scene, patient record, proof state, or task environment before and after each action.

Agent state

The goal, plan, scratch work, tool results, remembered facts, uncertainty, and active constraints the agent uses to choose the next step.

Action

The command, edit, click, API call, proof tactic, message, movement, or handoff that changes what can happen next.

Observation

The feedback the environment returns: terminal output, test result, UI state, verifier score, error, image, source document, or human reply.

Boundary

The permission, safety, privacy, legal, or task rule that must remain true while the agent acts.

Verifier

The check that tells whether a step improved the state, failed, crossed a boundary, or merely looked plausible.

Object rule
A trajectory is useful when it lets a reader replay why the next action was chosen and what changed because of it.

FIRST PRINCIPLES

Why the path matters

An agent couples a model to a world. That coupling creates new failure modes. The model can observe the wrong thing, trust the wrong instruction, call the wrong tool, update memory with a false fact, repeat a failed action, or pass a weak verifier. None of those failures is visible if the only stored object is the final response.

The trajectory is also where learning lives. A command-line trace teaches what to try after an error. A UI trace teaches when a button changed state. A robot scene graph teaches how perception becomes a plan. A memory trace teaches whether feedback was retained and used. A reasoning trace teaches whether the process is tied to the task or only to a reward format.

METHOD

Why trajectory evidence changes agent design

Once the path is the object, the method has to control the path, not only the final answer.

This changes how we read agent papers. A benchmark is stronger when it records observations and state transitions. A training set is stronger when it includes failed attempts and recoveries, not only final successes. A memory method is stronger when it says what can be written, when it expires, and which future decision may read it. A tool-use method is stronger when it prices tool calls, checks outputs, and separates helpful evidence from malicious instructions.

The path also forces cost and responsibility into the method. If one agent succeeds with ten tool calls and another needs a hundred, the trajectories are not equivalent. If a multi-agent system hands off work, the handoff is part of the object. If a GUI agent succeeds by clicking through a hidden permission prompt, the final task success is not enough. If a reasoning model writes long traces that do not change with the input, more tokens have not produced more thought.

Trajectory-centered design therefore asks a concrete question at every step: what state does the agent believe, what action is allowed, what evidence should update the belief, and what check says whether the step helped?

FAILURE MAP

How agents look successful while the path is broken

Lucky final answer

The agent reaches the right output after irrelevant or unsafe steps, so the final score hides bad process.

Stale state

The agent keeps acting from an old file, page, tool result, user correction, or world condition after it has changed.

Template reasoning

The trace looks long and careful but does not depend on the current input or observed state.

Bad memory write

A false, private, or temporary fact is stored and later controls behavior outside its proper scope.

Tool drift

Tool calls multiply without improving the state, or the model treats unverified tool output as settled fact.

Authority confusion

The agent cannot distinguish user instruction from hostile page text, app content, retrieved documents, or environmental noise.

Final rule
Do not ask only what the agent answered. Ask what state it saw, what it changed, what it stored, and what checked each step.
CONNECTION

Why this idea cuts across the atlas

Many other concepts are parts of the trajectory problem.

Executable evaluation asks whether the final artifact works in its world. The agent trajectory asks how that artifact was reached. Long-context memory asks what past state remains usable later. Retrieval asks what missing evidence should enter the path. Safety asks which invariant must survive pressure. Boundaries and permissions ask which external content has authority to steer action. Human-facing AI asks how beliefs about a person should update through interaction.

That is why agent trajectory is a central bridge across the site. It turns a model from a static predictor into a time-indexed system. Once time, tools, state, and memory enter, the real object is no longer a single answer. It is the controlled path from incomplete evidence to checked action.
