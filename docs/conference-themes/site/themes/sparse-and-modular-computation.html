Problem

MoE models promise large total capacity with limited active compute, but the promise only works if routing, expert specialization, and sparsity level are coordinated.

Approaches

The evidence covers router-expert coupling through auxiliary losses, plus scaling analysis of active FLOPs and tokens per parameter for reasoning performance.

Connecting read

This theme is about sparse computation as an allocation problem: decide which parameters matter for this token, then make sure those parameters learned a useful role.

READ

The Big Picture

Dense models spend roughly the same computation on every token. Mixture-of-experts models change that contract: the system can own many parameters but activate only a subset for a particular input. That makes scale cheaper in principle, but it creates a new internal coordination problem. The router has to send tokens to the right experts, the experts have to become meaningfully different, and the chosen sparsity level has to fit the compute budget and training data. Sparse computation is therefore not just a systems trick; it is a model-design question about how capability is distributed across modules.

ERC Loss focuses on the specialization problem. It aligns router cluster centers with expert activations using proxy tokens and reciprocal auxiliary constraints, pushing the routing mechanism and expert behavior to agree. Optimal MoE Sparsity focuses on the scaling problem, showing that active FLOPs and total tokens per parameter jointly determine reasoning performance under fixed compute. Read together, the papers say that MoE quality depends on both local routing geometry and global compute allocation. It is not enough to add experts; the model has to learn when to use them and how sparse it should be.

LENS

Sparsity is useful only when routing preserves work

The concrete object is a token-to-expert computation path: which parameters are activated for this input, and whether those parameters contain the right skill.

The first-principles tradeoff is capacity versus active computation. MoE models can store more knowledge or behavior than they use on any single token. That helps only if the inactive parameters are safely irrelevant for that token. If the router chooses poorly, sparsity becomes lost capability. If experts do not specialize, sparsity becomes architectural decoration. If active FLOPs are too low, the model cannot reason enough. If tokens per parameter are too low, experts do not learn enough.

MECHANISM

Experts are capacity; routing is allocation

A mixture-of-experts model is useful only if the router sends each token to parameters that learned the right job.

Adding experts increases total capacity, but inactive capacity does nothing for the current token. The active path must contain enough computation to solve the token's problem. ERC Loss works on the local coordination problem: router clusters should correspond to actual expert behavior. Optimal MoE Sparsity works on the global scaling problem: active FLOPs and tokens per parameter must be balanced so experts learn and reasoning compute remains sufficient.

The key distinction is between architectural sparsity and functional modularity. Architectural sparsity means only some experts run. Functional modularity means those experts have specialized enough that the sparse choice preserves useful work. The papers are valuable because they ask when the second condition follows from the first, and when it does not.

TOPIC 01

The active path is the real model for this token

A sparse model may own many parameters, but a token only receives the computation that was actually activated.

This is the simplest way to read MoE systems. Total parameter count describes what the whole system could know. Active parameters describe what this token can use right now. If the router sends the token to the wrong experts, the model can be large in storage but small in usable computation. The inactive experts may contain useful skills, but those skills are absent from the current path.

That makes sparse computation a conditional capability claim. The system is saying: for each input, I can choose a small useful submodel. The claim is true only when the active path contains the skill, memory, or reasoning capacity the token needs.

TOPIC 02

Load balance is not the same as specialization

A router can send equal traffic to experts while still failing to divide work by meaning.

Many MoE systems need load balancing because unused experts waste capacity and overloaded experts create bottlenecks. But balanced counts are only a systems condition. They do not prove that expert one learned syntax, expert two learned math, expert three learned code, or that any meaningful partition exists. The experts may receive equal token volume while learning nearly identical behavior.

ERC Loss targets that gap. By tying router cluster centers, proxy tokens, and expert activations together, it tries to make routing geometry and expert behavior agree. The first-principles point is that specialization must be visible in behavior, not only in traffic statistics.

TOPIC 03

Sparsity is a compute budget decision

The best sparse model is not automatically the model with the most experts or the fewest active experts.

Optimal MoE Sparsity makes this concrete. Under a fixed compute budget, the design has to trade total capacity, active FLOPs, number of experts, and tokens per parameter. More experts can store more possible behavior, but each expert may see fewer examples. Fewer active experts save compute, but the active path may become too weak for reasoning. More active experts improve per-token computation, but reduce the savings that made sparsity attractive.

So sparsity is not a magic scaling rule. It is an allocation problem: how much model should exist, how much should run, and how much data should each parameter receive before we expect it to be useful?

TOPIC 04

Modularity must survive the main task

An auxiliary routing objective is useful only if it improves the computation the model needed to perform.

There is a real risk in adding losses for specialization, balance, or expert separation. They can improve the metric they directly optimize while hurting the task. A router can look cleaner while sending tokens away from the expert that would have solved them. Experts can become different in an artificial way that does not correspond to useful capabilities.

The evidence therefore has to connect modularity to task behavior. The active path should become more useful, reasoning per FLOP should improve, and ablations should show that router-expert coupling or sparsity choice caused the gain. Otherwise modularity is only a diagram of the architecture, not a property of the computation.

EVIDENCE

What would prove sparse computation is actually useful

Specialization

Experts should differ in behavior in a way that aligns with router decisions, not only receive balanced token counts.

Reasoning per FLOP

Fixed-compute comparisons should show where sparsity improves reasoning rather than merely increasing total parameter count.

Data per parameter

Each expert needs enough effective training signal; too many rarely used parameters can become undertrained capacity.

DEEP READ

Sparse capacity is a promise, not a guarantee

A sparse model says: the system owns more possible computation than it usually spends. The hard question is whether the unused computation was safely irrelevant for this input.

That is why sparse and modular computation is not just about saving FLOPs. It is about conditional relevance. For a token, image region, robot state, graph neighborhood, or modality, the system must choose which module should act. If the choice matches the hidden structure of the task, sparsity gives specialization and scale. If the choice is arbitrary, unstable, or dominated by one expert, sparsity gives the illusion of capacity while the useful path remains weak.

ERC Loss attacks the local version of this problem: the router and experts must learn the same partition of work. Optimal MoE Sparsity attacks the global version: the active path must get enough compute, and each parameter must see enough tokens to become trained capacity. These two questions are inseparable. Good routing cannot save an undertrained expert, and enough experts cannot help if routing sends the token to the wrong one.

CLUSTERS

The Main Research Moves

Make routing and expert behavior agree

A router is only useful if its decisions correspond to real expert specialization. ERC Loss treats that relationship directly by tying router cluster centers to expert activations. The deeper idea is that modularity has to be trained, not assumed. Without coupling pressure, a sparse model can have experts that exist architecturally but do not divide work cleanly.

Treat sparsity as a scaling variable

Optimal MoE Sparsity makes sparsity part of the scaling law discussion. Reasoning performance under fixed compute depends on how much compute is active and how many training tokens each parameter effectively sees. That means the best MoE design is not simply the sparsest one or the largest one; it is the allocation that gives active computation and parameter learning the right balance.
