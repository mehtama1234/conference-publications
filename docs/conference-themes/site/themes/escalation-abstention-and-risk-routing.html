Escalation, abstention, and routing under risk

A reliable system does not always act alone. When evidence is incomplete or action cost is high, it should route the case to the cheapest stronger source of evidence that can reduce risk enough: retrieval, tools, verifiers, more compute, a conservative policy, a human expert, or refusal.

Problem

A model that always answers can be less reliable than a model that knows when to retrieve, verify, ask, defer, abstain, refuse, or hand off to a stronger authority.

Approaches

Use uncertainty thresholds, prediction sets, verifier routing, human review, tool escalation, conservative control, refusal policies, expert rubrics, rare-event triggers, and cost-aware routing.

CORE

Routing is the action form of uncertainty

A useful uncertainty signal should not sit beside the answer. It should change the system's next move.

Escalation is often described as "send it to a human." That is too narrow. Sometimes the right escalation is retrieval because the model lacks source evidence. Sometimes it is a tool call because the answer can be computed. Sometimes it is a verifier because the artifact can be checked. Sometimes it is more inference because the model has not searched enough. Sometimes it is a wider prediction set because forcing one label is unsafe. Sometimes it is a conservative controller because action near a boundary is risky. Sometimes it is a refusal because the requested action should not be performed.

The local ICML/ICLR evidence supports this broader framing. The papers are not mostly named "handoff." They study the components that make handoff rational: calibrated uncertainty, prediction sets, rare-event risk, safety boundaries, verifier checks, human preference disagreement, model-judge limits, tool cost, legal workflows, and medical or educational domain stakes.

The first-principles question is: what stronger source of evidence can reduce risk enough, and is it worth the cost? If a proof checker can settle the claim, use it before a human. If retrieval can provide source evidence, retrieve before guessing. If a human expert is needed because values or clinical judgment are underdetermined, route to the expert with the relevant evidence, uncertainty, and current state. If no available route can make the action safe, abstain or refuse.

First-principles line
A reliable system routes uncertainty to the cheapest stronger source of evidence that can reduce decision risk enough.

TOPIC 01

Abstention is not failure if acting would be worse

A model should not be rewarded for answering when the evidence does not justify action.

Abstention is useful when forcing an answer would create more risk than value. The classic failure is a system that gives a confident answer because benchmarks reward answer rate and penalize silence. In deployment, wrong autonomy can be more costly than no answer: a wrong medical suggestion, invalid legal claim, unsafe shell action, bad code patch, or risky robot move.

Prediction-set papers such as ROCP and CRC support this logic because they resist forcing one answer when a set better protects the downstream decision. CreDRO and MIRA provide uncertainty forms that can support non-singleton decisions. Rare Event Analysis and CSPO show why ordinary confidence is weak near high-cost tails or safety boundaries.

Abstention should not be lazy refusal. It should say what evidence is missing, what action is unsafe, and what route could make action possible. In low-cost settings, abstention may be unnecessary. In high-cost settings, it can be the correct behavior.

Routing principle
Abstain when the expected cost of unsupported action is higher than the value of answering now, and name the missing evidence that would change that decision.
TOPIC 02

Escalation should go to the right stronger evidence

The next step should match the uncertainty. Do not hand everything to a human if a source, tool, verifier, or set is the better route.

Escalation is often treated as one bucket. That loses the structure. If the model lacks a citation, retrieve. If code may be wrong, run tests. If proof steps may be invalid, use a proof checker. If visual grounding may be wrong, run perception verification. If values conflict, ask the user or route to a human rubric. If a rare safety event is possible, stress test. If a robot is near a safety boundary, choose conservative control.

HERO, MoCA, THOR, VERINA, and WebDevJudge are verifier routes. ParetoPO, CyberGym, and SandboxEscapeBench are tool/action routes. VALUEFLOW, P-GenRM, WIMHF, CounselBench, and healthcare/education agents are human or preference-structure routes. ROCP, CRC, CreDRO, and MIRA are uncertainty-set routes. Each one says that "ask someone else" is not the only stronger evidence.

A good routing system should keep a ladder: answer if safe, retrieve if evidence is missing, compute if the result is calculable, verify if the artifact is checkable, ask a human if judgment is needed, refuse if the boundary cannot be crossed.

Routing principle
Route to the evidence source that addresses the actual uncertainty, not to a generic fallback.
TOPIC 03

Human handoff needs a packet, not a panic button

If a human receives only the model's final answer, the handoff may preserve the model's confusion instead of reducing risk.

Human review is strongest when the reviewer receives the evidence needed to decide: the claim, source pointers, uncertainty, alternatives, action cost, model rationale if useful, verifier results, missing facts, and current task state. A bare escalation that says "please review this" wastes scarce human attention and can hide the failure mode.

This connects to VALUEFLOW, P-GenRM, WIMHF, CounselBench, and domain-specific medical/education evaluations. Human judgment is not one universal oracle. The right reviewer depends on the domain and the decision: legal expert, clinician, teacher, security analyst, user, policy owner, or human evaluator. The route should match the competence needed.

A handoff packet should make it easy for the human to overrule the model. That means surfacing exact evidence, uncertainty, alternatives, and what the model is asking the human to decide. Long-context workflow pages make the same point: humans need handles, not hidden memory.

Routing principle
Human handoff should transfer decision-ready state: evidence, uncertainty, alternatives, costs, and the specific judgment the human must make.
TOPIC 04

Verifier routing catches what humans should not have to inspect manually

When correctness is executable or checkable, a verifier is often the cheapest stronger authority.

Code, proofs, math steps, web artifacts, SQL, patches, and structured outputs should not rely only on human reading. A verifier can reject invalid artifacts quickly, repeatedly, and consistently. This saves human review for the cases where interpretation, values, domain judgment, or unresolved uncertainty remain.

HERO combines sparse correctness checkers with dense reward scores. MoCA separates perception verification from verbal checks. THOR uses tool feedback for math steps. VERINA checks the gap between code and proof. WebDevJudge-style work inspects rendered artifacts. These papers make verifier routing concrete: send checkable claims to checkers before asking humans to trust prose.

The failure mode is verifier gaming or narrowness. A system can overfit a test suite, pass a proof-like check while missing the real specification, or render acceptably while failing accessibility or intent. Verifier escalation needs coverage audits and human oversight where the verifier does not observe the right property.

Routing principle
Route checkable artifacts to verifiers first, then escalate only the remaining uncertainty that the verifier cannot observe.
TOPIC 05

Tool escalation should be cost-aware

Calling a tool is an action with cost, risk, and permission scope.

A model should call a tool when tool evidence can change the decision enough to justify the cost. It should not call tools to create the appearance of work, and it should not skip tools when the task requires external state. Search, shell, browser, code execution, database calls, and graph APIs all change what the model can know and do.

ParetoPO is central because it explicitly treats accuracy and tool-use efficiency as a tradeoff. CyberGym shows when tool escalation is necessary: security ability cannot be judged from language alone when the task requires exploit, patch, and validation. SandboxEscapeBench shows the risk side: shell access and boundaries make tool use a safety problem.

Tool escalation should include permission, cost, expected value, and verifier feedback. A high-risk tool route may require human approval or sandboxing. A low-risk calculation may be automatic. The interface should make those distinctions visible.

Routing principle
Call tools when their expected decision value exceeds their cost and risk, and constrain the tool surface by permission and reversibility.
TOPIC 06

Prediction sets route away from false precision

Sometimes the right escalation is not to another actor, but to a different output form.

A model may not need a human if it can honestly preserve uncertainty in a form the downstream system can use. Prediction sets, ranked alternatives, confidence intervals, credal sets, and regional probability summaries can route away from false precision. They say: here are the plausible choices; choose a robust action or collect evidence that separates them.

ROCP and CRC are the main anchors because they tie prediction sets to downstream decision robustness. CreDRO represents plausible distributions. MIRA tests probability mass in decision-relevant regions. These methods are handoff-adjacent because they decide when the model should not collapse uncertainty prematurely.

This route works only if the receiving system knows what to do with the set. A set that is too broad or disconnected from the action merely passes uncertainty downstream without helping.

Routing principle
Return a set when the set preserves action-relevant alternatives better than a single overconfident answer.
TOPIC 07

Conservative routing protects boundaries

Near a safety boundary, the route may be a safer action rather than more explanation.

Safety-critical systems often need boundary-aware action. If a policy is close to violating a constraint, a conservative controller may be better than a confident answer or a human handoff that arrives too late. In robotics, safe RL, medical triage, cybersecurity, and legal compliance, some boundaries should trigger reduced autonomy.

CSPO provides the clean example: it uses distance to safety boundary, local constraint sensitivity, time to safety, violation frequency, and reward preservation. SandboxEscapeBench treats system boundaries as the object being tested. Copyright-Bench treats legal eligibility as a boundary under workflow pressure. These are routing problems because they decide when ordinary autonomy is no longer acceptable.

A conservative route should not be a vague refusal. It should identify the boundary and choose the safest available next action: ask for approval, use a restricted tool, avoid external action, provide safe alternatives, or route to a qualified authority.

Routing principle
When uncertainty is near a high-cost boundary, route to conservative action before optimizing ordinary task success.
TOPIC 08

Refusal is a route, but not the only safety route

Refusal is appropriate when the requested action should not be performed, but many risky cases need safer redirection rather than silence.

Refusal should be reserved for boundaries that cannot be crossed: unsafe, illegal, private, unauthorized, or policy-incompatible actions. But many cases are not simple refusals. The system may be able to answer at a safer level, ask for missing context, route to a professional, provide general information, or recommend emergency assistance depending on the domain.

Copyright-Bench, privacy/unlearning pages, safety/governance pages, and SandboxEscapeBench all show why refusal and permission boundaries matter. The issue is not whether the model can produce helpful text; it is whether the requested workflow would cross a boundary. A good route explains the boundary enough for the user to understand what can be done instead.

False refusal is also a cost. Over-refusal can make systems unusable, hide legitimate information, or push users to less safe channels. Refusal thresholds should be tested like any other control surface.

Routing principle
Refuse when the requested action crosses a real boundary, and otherwise route to the safest useful alternative.
TOPIC 09

Routing policies need their own evaluation

It is possible to have a good answer model and a bad router.

A router can under-escalate high-risk cases, over-escalate easy cases, send cases to the wrong tool, ask humans for checkable artifacts, refuse too broadly, or spend too much compute on low-value uncertainty. The routing policy is therefore a model component that needs its own metrics.

Evaluation should measure false autonomy, false escalation, wrong route choice, cost, latency, human burden, verifier coverage, refusal quality, and final decision risk. ParetoPO's tool-cost framing is useful here. Benchmark reliability work reminds us that routing conclusions need uncertainty ranges. Rare Event Analysis says high-cost failures need tail-focused tests. Human-evaluation papers remind us that expert review capacity is scarce.

Routing should be tested on cases where the correct route differs: answer directly, retrieve, verify, ask a human, return a set, abstain, or refuse. A benchmark that only rewards final answers cannot train this behavior.

Routing principle
Evaluate the router by whether it chooses the right next evidence source at the right cost, not only by whether the final answer sometimes improves.
TOPIC 10

The handoff boundary is a design choice

Every deployed system needs a policy for where model autonomy ends.

The handoff boundary is not fixed by the model. It depends on domain, user, task cost, permission, evidence, and available review. A coding assistant may run tests automatically but ask before destructive changes. A medical assistant may summarize records but route diagnosis or treatment to a clinician. A legal assistant may retrieve clauses but flag jurisdictional uncertainty. A robot may plan but let a controller enforce safety. A security agent may inspect sandboxed files but require approval before high-risk action.

This page's paper map is therefore intentionally broad. The ICML/ICLR papers give pieces of the boundary: uncertainty sets, verifier checks, expert rubrics, preference disagreement, tool costs, safety margins, legal workflows, and environment boundaries. The conceptual synthesis is that these pieces define where autonomy is justified and where stronger evidence must take over.

Closing line
A system is reliable when it knows not only how to answer, but when answering alone is the wrong next action.
