First-principles concept

Evaluation is becoming execution

A useful evaluation no longer asks only whether a model wrote the right words. It asks whether the model made an artifact that survives contact with the system where the claim is true or false.

Problem

Text answers can look correct while the produced program, proof, exploit, website, or action fails.

Shift

The measured object moves from an answer string to a runnable artifact with state, rules, and consequences.

Evidence

The check must happen in the native system: code runs, proof checks, exploit distinguishes versions, website renders, agent action changes state.

CORE

The real question is whether the claim can be cashed out

An evaluation is a promise about truth. The promise is weak if truth is judged only by surface form.

A security answer may name a vulnerability but fail to reproduce it. A proof may sound like a proof but not pass a formal checker. A website may compile but not match the intended interface. A compiler change may look plausible but break program meaning. An agent may finish a task by accident while taking unsafe or useless steps.

The first-principles move is to ask what object makes the claim real. For CyberGym, the object is a proof-of-concept test that behaves differently on vulnerable and patched code. For WZ-LLM, the object is a Lean-checked proof. For CIRBench, it is transformed compiler IR that preserves meaning and improves runtime. For Vision2Web and WebDevJudge, it is the rendered website and its behavior, not only the source code.

Core rule
When a task has a native execution system, the evaluation should enter that system.

FIRST PRINCIPLE

An evaluation is a measurement instrument

A measurement instrument is useful only if it responds to the thing we care about and ignores things that should not matter.

A thermometer should respond to temperature, not to the color of the wall. A code benchmark should respond to program behavior, not to whether the answer sounds like a good explanation. A web benchmark should respond to what the page does in a browser, not to whether the HTML looks impressive. A security benchmark should respond to whether an exploit works against the vulnerable version and fails against the patched version, not to whether the model can name a likely bug.

That is the first principle: evaluation is not a report card after the task. It is the instrument that defines what the task means. If the instrument sees only text, then the model can win by producing text that resembles success. If the instrument enters the native system, then the model has to produce an object that works there.

This is why the evaluation papers cluster with agents, code, proofs, web tasks, safety, and scientific workflows. In all of those settings, the answer is not the object. The object is a changed state: a test passes, a theorem checks, a page renders, a tool call finishes, a sandbox boundary holds, a vulnerability is reproduced, or a workflow reaches a verified end state.

OBJECT

The object is not the answer. It is the answer in its world.

A model output becomes evidence only when it is placed inside the system where it can succeed or fail.

Code

The output is a patch, compiler rewrite, test, exploit, or program. Its world is the repository, compiler, runtime, test suite, and dependency state.

Proof

The output is a formal artifact. Its world is the proof kernel, definitions, imports, theorem statement, and allowed proof steps.

Web

The output is a rendered interface. Its world is the browser, layout engine, interaction state, visual target, and user workflow.

Agent

The output is a trajectory. Its world is the environment state, observations, tool calls, memory, recovery steps, and verifier feedback.

Security

The output is an operational distinction. Its world is vulnerable code, patched code, permissions, sandbox walls, and protected objects.

Science

The output is a claim or artifact with domain rules. Its world is data, code, assumptions, diagnostic checks, and ground truth where available.

Object rule
Do not ask whether the answer looks right until you know the world in which rightness is tested.
PAPER MAP

The papers point to the same object

Security

CyberGym and SandboxEscapeBench make the evaluation a controlled security event: produce evidence of a vulnerability or show whether an agent can cross a sandbox boundary.

Code

CIRBench asks whether an LLM rewrite preserves compiler meaning and improves measured performance. The answer is not judged by how the rewrite reads.

Web work

Vision2Web and WebDevJudge move website tasks into rendered pages, interaction, visual state, and implementation comparison.

Formal proof

WZ-LLM makes proof-shaped language insufficient. The proof must survive a formal kernel.

Agents

Gaia2 pairs dynamic scenarios with action-level verifiers because an agent works through changing state, not a single reply.

Risk

Executable tests can reveal real vulnerabilities and sandbox failures, so the evaluation itself becomes infrastructure that must be governed.

METHOD

Why running the artifact changes the science

Execution gives the evaluation a place to disagree with the model.

A text judge often sees the same surface the model produced. That creates a weak loop: the model writes plausible language, and the judge rewards plausible language. Execution breaks that loop by asking the artifact to interact with an outside system. The compiler does not care whether the explanation sounds careful. The proof kernel does not care whether the paragraph reads like a proof. A browser does not care whether the source code looks organized if the layout breaks. A patched program does not care whether the vulnerability write-up is fluent if the exploit no longer distinguishes versions.

This does not make execution perfect. A test suite can miss behavior. A sandbox can be too simple. A browser judge can miss accessibility or workflow quality. A formal checker can verify a theorem that was not the intended theorem. But execution changes the failure mode from vague disagreement to inspectable mismatch. You can ask which test was missing, which state was unobserved, which permission boundary leaked, which theorem was checked, or which user action failed.

That is the deeper contribution. The papers are not only building harder benchmarks. They are changing what a benchmark is allowed to be. The benchmark becomes a small world with rules, state, and consequences. The model is then evaluated by whether it can make something true inside that world.

FAILURES

How shallow evaluation fools us

A benchmark can reward a model for matching answer style, exploiting a judge weakness, producing code that compiles but fails behavior, proving a different theorem, using hidden permissions, or completing a task in a way that would be unacceptable outside the benchmark. These are not small scoring errors. They mean the measured object was too far from the real object.

Executable evaluation is not automatically correct. A verifier can be narrow. A sandbox can be misconfigured. A website judge can miss function. A test suite can be incomplete. The point is not that execution solves measurement. The point is that execution gives the claim a place where it can fail for concrete reasons.

FAILURE MAP

Five ways executable evaluation can still be wrong

Wrong artifact

The benchmark checks a related object, not the object users care about. A compiler pass is checked for speed but not semantics; a web page is checked for pixels but not interaction.

Weak world

The environment is too small, too clean, or too fixed. The model learns the benchmark setting instead of the real workflow.

Missing boundary

The model succeeds by using authority the task should not grant: hidden files, sandbox leaks, copyrighted source use, unsafe tools, or forbidden actions.

Narrow verifier

The check observes one easy part of success and misses the hard part: compilation without behavior, visual match without usability, proof shape without theorem intent.

Unpriced effort

The model reaches the answer only by spending excessive retries, tool calls, latency, hidden human help, or search that the score ignores.

No transfer test

The artifact works on one fixed instance but fails when names, layout, versions, seeds, environments, or task details change.

CONNECTION

Why this idea cuts across the atlas

Executable evaluation is one version of a larger rule: the measured object must match the claim.

In long context, the measured object is whether remote evidence still changes the later decision. In grounding, it is whether the answer depends on the image, audio, sensor, or document evidence. In safety, it is whether the boundary survives pressure. In privacy and unlearning, it is whether information remains recoverable. In scientific generation, it is whether the generated sample preserves the native object. In software, it is whether the artifact passes the checker that defines correctness.

Evaluation becomes execution when the claim already lives inside a system with rules. The right measurement enters that system. It does not replace judgment with automation. It gives judgment better evidence: a trace, a state change, a failed check, a boundary crossing, or a working artifact.
