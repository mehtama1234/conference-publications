First-principles concept

Synthetic data as evidence or contamination

Generated data is useful only when it adds valid variation. It is harmful when it repeats a model's bias and trains the next model to treat that bias as evidence.

CORE

Synthetic data must answer what new evidence it adds

A generated example is not automatically new information.

Synthetic data can help when real data is scarce, expensive, private, dangerous, slow to collect, or missing important conditions. But a generator can also repeat its training bias, simplify rare cases, erase hard variation, invent false structure, or produce examples that look real while breaking the measurement process that made the real data meaningful.

The first-principles question is not whether the data is synthetic. It is what relationship the synthetic source has to the real target. Does it preserve causal structure, covariance, physical validity, censoring, task affordances, or adapter-transfer signal? Does it add coverage the model did not already have? Or does it feed the system a polished version of its own errors?

Core rule
Synthetic data helps when it adds a controlled source of variation that the downstream task can verify.
FIRST PRINCIPLE

A generated example is a claim about a missing part of the world

Synthetic data is useful when the claim is valid and harmful when the claim smuggles in the generator's bias.

A generated example is not neutral. It says, implicitly, that this kind of case could exist, that it belongs near the training target, and that its label, structure, dynamics, or affordances are trustworthy. If that claim is true, synthetic data can fill gaps. If it is false, the training process treats fiction as evidence.

The first-principles distinction is between added variation and recycled error. Synthetic data helps when it creates a controlled condition that real data lacks and when the condition can be verified by a domain rule. It contaminates when it repeats the model's own blind spots, changes the measurement process, erases rare cases, or creates examples whose surface realism hides a wrong causal, physical, clinical, or task structure.

First-principles test
Ask what real gap the synthetic source fills, what rule verifies it, and what bias it could amplify if accepted.

PAPER MAP

The papers split synthetic data into roles

Designed source

CauKer creates time-series data from causal mechanisms and kernels so pretraining sees varied processes, not random decoration.

Diagnostic source

Neon uses self-generated degradation as negative evidence: the harmful update direction is measured and then reversed.

Embodied source

SceneSmith generates robot scenes that must include objects, affordances, physical properties, and simulation validity.

Clinical source

SurvDiff must preserve event times and right-censoring because survival data is a measurement process, not just rows.

Selected source

Synthetic Data Selection shows covariance can matter more than mean matching, so selection should preserve directions of variation.

Transfer source

TiTok filters synthetic examples to move adapter knowledge across model backbones through token-level contrastive excess.

METHOD

Why synthetic data needs provenance and rejection

A synthetic source should be treated as an instrument, not an endless supply of free evidence.

Real data can be wrong too, but it usually comes from a measurement process that can be inspected. Synthetic data comes from a generator whose training history, prompts, filters, and sampling choices shape every example. That lineage must be visible because it determines what errors are likely to repeat.

A good method states why synthetic data is needed, how examples are generated, what validity rule filters them, and what downstream behavior they are supposed to change. It should compare accepted samples against rejected samples, random samples, real samples, and no synthetic data. Otherwise the method cannot distinguish useful variation from polished contamination.

FAILURES

When synthetic data contaminates training

Contamination happens when generated examples are treated as independent evidence even though they mainly express the generator's past mistakes. It can also happen when the generated data has the wrong covariance, wrong causal mechanism, wrong censoring pattern, wrong physical affordance, or wrong rare-case frequency. The danger is not that the data is artificial. The danger is that its artificial structure is invisible to the training process.

Synthetic data should therefore be governed like any other source. It needs provenance, acceptance rules, domain checks, stress tests, and a clear statement of what new variation it contributes.

FAILURE MAP

How generated examples become bad evidence

Bias loop

The model trains on its own mistakes and makes them look like data.

Wrong mechanism

The synthetic process matches surface statistics while teaching the wrong cause.

Covariance loss

Means match but important directions of variation disappear.

Physical fiction

Generated scenes or objects look plausible but cannot be acted on.

Measurement mismatch

Clinical or scientific rows ignore how the real measurement was produced.

Filter worship

A filter score replaces downstream tests of whether the data helped.

Treat every synthetic example as a claim about the world. Keep it only if the claim is valid for the task.
CONNECTION

Why this idea cuts across the atlas

Synthetic data is training pressure with a source-risk attached.

Data pressure asks what movement an example causes. Synthetic data adds the question of whether the example is valid evidence. Scientific generation asks whether generated objects obey native rules. Grounding asks whether the generated example preserves the evidence path it claims to imitate.

The deeper rule is to treat generation as a source with a failure model. Synthetic data is powerful when that failure model is explicit and dangerous when it is invisible.
