Problem

Reasoning systems must decide what to think about, what evidence to fetch, when to use an external tool, when to stop, and how to recover when an intermediate step is wrong.

Approaches

The papers attack that problem through data pipelines, latent computation, tool use, search, retrieval, formal verification, and explicit controls on overthinking.

Connecting read

The unifying move is to treat reasoning as a resource allocation problem: useful thought is computation that changes the reachable solution, not text that merely looks careful.

FIRST PRINCIPLES

The core problem

A reasoning model is useful only if its intermediate work changes what it can correctly do. That sounds simple, but it breaks into several hard choices. The model may need to decompose a problem, inspect a visual cue, call a theorem prover, run code, retrieve a buried fact, explore partial solutions, or ask a clarifying question. Each action costs tokens, latency, money, or error exposure. The conference papers in this theme are about turning that messy process into something trainable and measurable.

The older view treated reasoning as a written explanation appended before an answer. This theme treats reasoning as an internal control loop. A good loop gathers information, keeps useful branches alive, suppresses wasteful loops, and connects intermediate artifacts to the final answer. That is why the papers range from math tool calls to latent thought, visual planning, diffusion search, reward normalization, and formal proof. They are different surfaces of the same underlying problem: how should a model spend limited computation in order to reduce uncertainty and produce a consequence that can be checked?

TOPIC 01

What an agent is really for

An agent is useful when the system has to do more than answer once. It must keep track of a goal, choose actions, observe the effects, and keep going while the situation changes.

The simplest way to misunderstand agents is to define them by their tools. A model with a calculator, browser, code runner, theorem prover, retriever, or planner is not automatically an agent. Those tools matter only if the system knows when to use them, what result to trust, what changed after the call, and what to do next. The deeper object is the loop that connects state, action, consequence, and update.

This is why the theme belongs next to long context, representation, and training tasks. An agent needs memory because the next action depends on prior observations and failed attempts. It needs a useful representation because the raw transcript is too messy to act from directly. It needs training pressure because the model will only preserve the information that the task rewards. It needs evaluation because a fluent plan is cheap; a plan that survives contact with tools, evidence, constraints, and time is harder.

The first-principles question is: what must stay true across the loop? If the task is math, the agent must preserve the problem constraints and make intermediate operations checkable. If the task is code, it must preserve file state, symbols, tests, errors, and edits. If the task is a browser workflow, it must preserve page state, user intent, permissions, and completed steps. If the task is medicine or law, it must preserve exact evidence, uncertainty, and authority. If the task is video or robotics, it must preserve spatial state, temporal order, and physical consequences.

1. The agent begins when output becomes action

action

A normal answer can be judged mostly after it is written. An agent action changes what will happen next. It may run code, retrieve a document, ask a question, choose an experiment, generate a proof attempt, alter a file, sample a plan, or call an external system. Once output becomes action, the model is no longer only producing language. It is making a move inside a task environment.

That changes the standard for reasoning. The system must ask whether the action is relevant, allowed, timely, and checkable. A long explanation that does not change the reachable solution is wasted compute. A short tool call that reveals the decisive missing fact may be valuable. This is the common ground between Rational Agents, THOR, AutoEP, VERINA, CRAMF, LoongRL, and Actions Speak Louder than Prompts: each paper gives the model a way to make reasoning touch something outside plain text.

2. The real object is the loop, not the single model call

loop

A single model call sees an input and emits an output. An agent loop has to preserve continuity across steps. It observes a state, selects an action, receives a result, updates its state, and decides whether the goal is closer, farther away, blocked, or complete. If this loop is weak, the system can look intelligent at each individual step while still failing the task as a whole.

Several papers can be read as loop repairs. T3 asks how to learn from useful prefixes instead of throwing away an entire failed trajectory. Reasoning with Sampling keeps multiple paths alive because the first path may be wrong. ASAG and DECS ask when the loop should stop spending visible tokens. HERO asks how feedback should be normalized so reward pressure compares the right things. PonderLM-2 and MDM Reasoning ask whether part of the loop can happen in hidden or iterative computation rather than public text.

3. State is the agent's working truth

state

An agent does not need to remember every token equally. It needs to know what is currently true enough to act. The useful state includes the goal, active constraints, available tools, open uncertainty, completed actions, failed attempts, retrieved evidence, verifier feedback, and any world change caused by the last action. This state is smaller than the transcript but more important than the transcript.

State errors create agent failures that are easy to miss in final-answer benchmarks. The model may repeat a failed command, ignore a tool result, use stale retrieved evidence, keep obeying an old plan after conditions changed, or assume a proof step succeeded when the checker rejected it. LoongRL ties retrieval to answer reasoning because the state must point at the right evidence. Rational Agents formalizes the value of asking a question because state should be updated by the answer that most reduces uncertainty. AutoEP feeds search diagnostics back into the loop because the state should reflect observed algorithm behavior, not just the model's story about the algorithm.

4. Tools are useful because they impose consequences

tools

A tool is not just extra capability. It is a stricter interface. Code runs or fails. A proof checker accepts or rejects. Retrieval returns a specific source. A graph operation exposes structure that prose may hide. A visual intermediate plan preserves spatial constraints. These consequences give the model feedback that plain text often cannot provide.

THOR uses tool-call success and final answer reward so math reasoning is shaped by executable intermediate steps. VERINA shows that passing code tests and satisfying proof obligations are not the same level of evidence. CRAMF retrieves Mathlib4 definitions because formal mathematics depends on the exact object in the library, not a loose paraphrase. Actions Speak Louder than Prompts argues that code can be a better reasoning interface for graph-like structure. Visual Planning makes the intermediate artifact an image sequence because some constraints are spatial before they are verbal.

5. Planning is controlled commitment, not a list of nice steps

planning

A plan is useful only when it narrows future action without locking the system into a bad path. Too little planning makes the agent reactive and locally greedy. Too much planning makes it brittle when the environment changes. Good planning chooses enough structure to guide action, then checks each step against the world.

NEXCO is a clean example because it treats partial solutions as objects that must remain feasible. CDGS adds population search and pruning inside diffusion generation because a plan needs selection pressure, not just proposal. L2T learns latent programs from observations because a compact rule can support future action better than a surface prediction. Visual Planning uses image sequences when the plan itself is spatial. These papers share a principle: planning is the management of possible futures under constraints.

6. Verification closes the loop

checking

An agent that cannot check consequences is forced to trust its own text. That is dangerous because fluent intermediate reasoning can be wrong. Verification gives the loop a way to distinguish progress from motion. The check may be an executable result, proof success, source match, reward signal, visual contrast, attribution graph, or human review.

The papers use different checks because different domains expose truth differently. VC-STaR uses contrastive visual evidence so the model must attend to the cue that changes the answer. CRV uses attribution-graph analysis and feature intervention to repair faulty internal reasoning. HERO shapes reward comparisons inside verifier-defined groups. VERINA exposes the gap between code that seems correct and code that satisfies a formal proof. In each case, verification is not an afterthought; it is what tells the agent whether the current state should be trusted.

7. The same loop appears across modalities and domains

domains

The surface unit changes, but the loop stays recognizable. In text, the action may be retrieving or citing evidence. In code, it may be editing and running tests. In math, it may be calling a solver or proof checker. In video, it may be choosing a visual plan or tracking an event. In audio, it may be preserving acoustic evidence that text misses. In science, it may be selecting the next experiment or checking a generated hypothesis against measurements.

UALM-R1 matters here because it treats audio and text as reasoning material, not just input and caption. MetaphorVU matters because high-order video understanding may need relational knowledge beyond object labels. Tool-Augmented SSMs matters because the backbone itself affects whether the loop can carry state efficiently. OpenThoughts matters because the training supply chain shapes the kinds of intermediate work the model learns to imitate. The page should read these papers as parts of one field question: what loop lets a model act usefully in this kind of world?

TOPIC 02

The agent loop

The agent loop is the smallest useful picture of action: observe the situation, represent what matters, choose a move, execute it, read the result, update state, and decide whether to continue.

This loop sounds ordinary, but it explains why agent papers look so different from each other. A paper may improve observation, state, action choice, tool execution, feedback, recovery, or stopping. Those are not separate hobbies. They are different places where the loop can fail. If the observation is wrong, the agent acts on the wrong world. If the state is vague, it cannot choose the right next move. If action choice is weak, it wastes calls. If feedback is ignored, it repeats mistakes. If stopping is weak, it spends computation after the answer is already settled.

The important point is that a loop creates dependency between steps. A tool call is only useful if the result changes the next state. A retrieval is only useful if it changes what evidence the answer is built from. A proof failure is only useful if the next attempt repairs the failed obligation. A visual plan is only useful if later reasoning respects the spatial state it exposed. Agent design is therefore not only about giving the model more capabilities. It is about making sure each capability changes the next decision in the right way.

1. Observe: decide what world the agent is in

observation

Observation is not passive intake. The agent has to decide which pieces of the environment are relevant to the current goal. In text tasks, this may mean finding the clause, claim, or missing fact. In code, it may mean reading the right file, test, error, or dependency. In video, it may mean identifying the object, action phase, or visual cue. In math, it may mean noticing the exact constraint that limits the solution.

LoongRL fits here because long-context retrieval is not just more reading; it is observation control under distractors. Rational Agents also fits because asking a question is active observation: the agent chooses which missing answer would reduce uncertainty most. VC-STaR fits because visual reasoning fails when the model observes the wrong cue and still gets the answer by shortcut. The first loop failure is simple: the agent cannot act correctly if it is looking at the wrong evidence.

2. Represent state: turn raw context into what is currently true

state

After observation, the agent needs a compact working state. Raw context may include old messages, irrelevant tokens, partial traces, previous failed attempts, retrieved text, tool logs, and tentative plans. The state must separate what is still active from what is merely historical. It should keep the goal, constraints, known facts, uncertain facts, available tools, current plan, and checked results.

Tool-Augmented SSMs belongs here because the backbone has to carry useful state efficiently across long reasoning. PonderLM-2 and MDM Reasoning belong here because some state update may happen inside hidden or iterative computation rather than visible chain-of-thought. UALM-R1 broadens the point across modalities: if audio carries timing or acoustic cues, state cannot be reduced to text alone. State is the agent's working truth, and the loop is only as good as that truth.

3. Choose an action: spend the next move where it changes the answer

choice

The next action may be to think, sample, retrieve, ask, run code, search, formalize, inspect a visual plan, or stop. The agent should choose the action whose expected value is worth its cost. The hard part is that the value is often hidden until after the action is taken. A retrieval may return nothing. A code run may reveal the bug. A proof attempt may fail but expose the missing invariant. A sample may find a path the first attempt missed.

Rational Agents makes this action-choice problem explicit through expected information gain. Reasoning with Sampling treats candidate reasoning paths as choices to explore before committing. ASAG and DECS ask when continuing visible reasoning is worth the extra tokens and when it is only length. NEXCO and CDGS treat planning as action selection inside constrained search spaces. A good agent is not one that always does more; it is one that spends the next move on the uncertainty or constraint that controls the outcome.

4. Execute: make the action touch a stricter object

execution

Execution is where the agent leaves speculation. Code can run. A theorem prover can reject a statement. Retrieval can produce a source. A graph operation can compute a property. A search algorithm can return diagnostics. A generated visual plan can show whether the spatial arrangement is coherent. The action becomes useful because it creates an external result the agent cannot simply wish into correctness.

THOR is directly about this step because mathematical reasoning is trained with tool calls and step-level feedback. Actions Speak Louder than Prompts argues that executable code can be the right interface for graph-like and long-text structures. CRAMF retrieves the formal handles needed for Lean, because a proof environment cares about exact definitions. VERINA shows why execution is not one thing: tests can pass while proof obligations still fail. Execution gives the loop evidence, but the strength of that evidence depends on what the tool actually checks.

5. Read the result: distinguish signal from noise

feedback

A tool result is not automatically understood. The agent has to read it, decide whether it is trustworthy, and extract the part that matters. A compiler error may point near the real issue but not at the root cause. A retrieval result may be similar but not decisive. A reward score may be meaningful only inside a comparable group. A visual cue may be present but not the reason the answer should change.

HERO fits this step because reward-model scores need local meaning before they can guide optimization. AutoEP fits because real-time search diagnostics tell the model whether its optimization strategy is working. VC-STaR uses contrastive examples to make visual evidence reading sharper. CRV looks at internal attribution graphs because a reasoning failure may be visible inside the mechanism, not just at the output. Reading feedback is where the loop learns whether the last action produced progress or only more text.

6. Update: change the working state without losing the useful past

update

After feedback, the agent must update its state. This is where many failures become persistent. If the agent ignores a failed proof, it may repeat the same invalid step. If it over-trusts a retrieved passage, it may answer from the wrong source. If it forgets a useful prefix from a failed trajectory, it loses partial progress. If it treats every old observation as equally live, stale state can control the next action.

T3 is important here because it preserves useful prefixes from trajectories that did not end in full success. LoongRL matters because answer reasoning has to stay linked to the retrieved chain of evidence. CRV matters because update can include targeted repair of internal features, not only prompt changes. OpenThoughts matters because teacher-generated reasoning traces teach the model what kinds of intermediate updates a successful problem-solving path tends to contain. Updating is not appending to a transcript; it is revising what the agent will now treat as true, useful, uncertain, or discarded.

7. Continue or stop: decide whether more work is still useful

stopping

The final decision in each loop is whether to continue. Continuing is not automatically better. More reasoning can find missing evidence, repair a failed step, or explore a better plan. It can also waste tokens, overfit to a bad branch, invent rationales, or create new errors after the answer was already determined. Stopping is therefore a reasoning skill, not only a cost setting.

ASAG is about improving accuracy while reducing generated tokens. DECS separates redundant-token penalties from useful exploration. Reasoning with Sampling shows why diversity across attempts can be valuable, but also why collapse is a real risk. PonderLM-2 asks whether extra computation can be spent internally before emitting tokens. The loop should continue when the next step can change the outcome; it should stop when further motion is unlikely to add checked value.

TOPIC 03

State and memory

An agent's memory is not the full transcript. It is the working state that should still control the next action.

This is the difference between remembering and being able to act. A transcript records what happened. A useful state says what is now true, what remains uncertain, what has already been tried, what failed, what evidence is trusted, what constraints still bind the task, and what action is worth taking next. The agent may have access to a long context, a retrieved store, a tool log, and hidden computation, but those are raw materials. State is the selected account of the task that the next decision will use.

State is also where the agent's representation choices become visible. In code, state may be a set of changed files, failing tests, symbol dependencies, and command results. In math, it may be assumptions, lemmas, subgoals, failed proof attempts, and verified steps. In documents, it may be claims, sources, contradictions, and open questions. In video, it may be object identity, event order, spatial layout, and action phase. In medicine, it may be patient baseline, values, trends, treatments, risk factors, and uncertainty. A generic memory is not enough; the state has to match the kind of action the agent will take.

1. Live state is different from history

liveness

History is everything that happened. Live state is the subset that should still guide behavior. A user may have suggested a plan and later replaced it. A retrieval may have returned a tempting but wrong passage. A tool call may have failed. A proof branch may have produced one useful lemma before collapsing. An agent that treats all history as equally live will be pulled in too many directions.

This is why T3 is conceptually important beyond its training method. It says failed trajectories are not simply garbage. Some prefixes contain useful state transitions. The agent should preserve the useful part without preserving the failed ending as a command to continue. That same principle applies to coding sessions, browser workflows, theorem proving, experiment design, and long-context retrieval: keep the part of history that changes the next correct move; demote the part that only records what happened.

2. State must preserve constraints, not just facts

constraints

A fact says something is true. A constraint says what actions remain allowed. Agents fail when they remember facts but lose constraints. A model may know the answer format but ignore the user's instruction. It may know a function exists but ignore the type contract. It may know a theorem but miss a side condition. It may know a visual object is present but ignore that the object cannot pass through another object.

NEXCO and CDGS sit here because planning needs feasibility, not only likely next tokens. NEXCO keeps partial solutions inside the space of what can still work. CDGS adds search and pruning so generated plans are not just plausible pieces but compatible pieces. CRAMF also belongs here: retrieving the right Mathlib4 definitions is a way of importing formal constraints from the library into the agent's state. Constraints are the walls of the problem; state without them is just a pile of observations.

3. State must carry uncertainty explicitly

uncertainty

An agent often acts before everything is known. The state should therefore include what is uncertain, not only what is known. The system may be unsure which document controls the answer, which proof obligation is blocking progress, which visual cue matters, which graph branch is feasible, or which hidden condition changes a medical decision. If uncertainty is hidden, the agent may act too early and then rationalize the result.

Rational Agents is the clearest paper for this principle because it asks which question has the highest value for reducing uncertainty. LoongRL also fits because long-context reasoning often means finding the true question and the right chain of evidence among distractors. HERO fits because feedback should be compared in locally meaningful groups; otherwise the state may treat reward scores as more comparable than they really are. Good state does not pretend the task is solved. It marks where the next observation or tool call should reduce doubt.

4. State needs evidence pointers, not only summaries

evidence

A state summary is useful for action, but it becomes dangerous if it loses its evidence. The agent may remember "the retrieval supported answer A" without preserving which passage supported it. It may remember "the proof branch failed" without preserving the exact rejected obligation. It may remember "the visual cue was present" without preserving where the cue appeared. When a later decision depends on precision, the agent needs a path back to the exact source.

LoongRL ties state to retrieved chains. VC-STaR pressures visual state to preserve the contrastive cue that changes the answer. VERINA shows that a code result and a proof result are different evidence types; the state should not flatten both into "checked." AutoEP feeds quantitative search diagnostics back into the model, which turns vague strategy into evidence-linked state. State should be compact, but it should not become evidence-free.

5. State can be visible, hidden, retrieved, or external

storage

There is no single place where state must live. Some state is visible in text because humans need to inspect it. Some state is hidden in activations because the model only needs it for the next prediction. Some state is stored externally because exact evidence is too large to keep active. Some state is produced by tools because the environment, test runner, prover, or search process is the authority.

PonderLM-2 and MDM Reasoning ask how much reasoning state can live in internal computation rather than visible tokens. Tool-Augmented SSMs asks whether a different sequence backbone can carry state efficiently for tool-using agents. CRV asks whether faulty reasoning state can be found and changed inside the model's features. These papers do not replace explicit state; they show that state has layers. The design question is which layer should carry which responsibility.

6. State should include the cost of the next move

cost

A useful agent knows not only what it could do, but what it is worth doing. More sampling may help if the answer space is uncertain. More tool calls may help if the tool can expose decisive evidence. More visible reasoning may help if the problem needs decomposition. But each move costs latency, tokens, money, attention, or side-effect risk. State should therefore include how much unresolved value remains.

ASAG, DECS, and Reasoning with Sampling are state-cost papers in this sense. They ask whether continuing to generate or explore still helps. PonderLM-2 adds another distinction: maybe computation should continue internally without emitting long text. Rational Agents puts the same idea into question asking: the best next question is not the most interesting one, but the one whose answer is worth the cost because it changes action. State is incomplete if it says what is possible but not what is worth spending.

7. State has to be shaped by the domain

domain

The same loop appears across domains, but the state unit changes. A coding agent needs files, symbols, tests, diffs, and command outputs. A math agent needs assumptions, subgoals, definitions, proof obligations, and checked lemmas. A video reasoning agent needs objects, tracks, events, and spatial relations. An audio-text agent needs words, speaker or acoustic cues, timing, and generation constraints. A scientific agent needs hypotheses, measurements, methods, and search diagnostics.

This is where UALM-R1, MetaphorVU, Visual Planning, L2T, and AutoEP widen the theme. They show that state is not always textual. Audio can preserve information lost in transcripts. Metaphor graphs can carry abstract relations in video. Image sequences can carry spatial plans. Latent programs can carry rules from observation. Search diagnostics can carry progress in algorithm design. The agent succeeds when the state form matches the thing the domain itself treats as real.

TOPIC 04

Tool use

A tool is useful when it changes the reasoning problem into a stricter form: something can be executed, looked up, measured, rejected, or inspected.

Tool use is often described as giving a model more abilities. That is only partly right. The deeper reason tools matter is that they change the kind of evidence available to the agent. A model can say that a calculation is correct, but a calculator can compute it. A model can claim a program works, but a test can run it. A model can sketch a proof, but a proof checker can reject it. A model can recall a definition, but retrieval can bring back the exact library object or source passage. A model can imagine a plan, but search can expose whether the partial choices are still feasible.

This means a tool is not automatically good. The tool has to match the uncertainty that blocks the task. If the problem is missing evidence, retrieval helps. If the problem is exact syntax, code execution or formal checking helps. If the problem is spatial state, an image or visual trajectory may help. If the problem is search over many possible futures, sampling, pruning, or feasibility projection helps. A tool call is wasteful when it does not change the state. It is dangerous when its result is weaker than the agent thinks it is.

1. Tools turn claims into artifacts

artifact

Plain reasoning can produce a claim: this number is right, this proof should work, this graph path is valid, this document supports the answer. A tool turns that claim into an artifact with a handle. The artifact may be code, a retrieved passage, a theorem statement, a test result, a search trace, a generated visual plan, or a structured candidate set. Once the artifact exists, the agent can inspect it, compare it, revise it, or reject it.

THOR is an example in math: tool calls make intermediate reasoning steps executable and rewardable. CRAMF is an example in formalization: retrieved Mathlib4 definitions give the agent exact formal handles. Actions Speak Louder than Prompts is an example in graph-like reasoning: code can represent operations that prose holds only loosely. These papers share the same design move: move reasoning from vague text into an object that the loop can act on.

2. Different tools prove different things

evidence

A common failure is treating every successful tool result as full proof. A code test proves behavior on tested cases, not all cases. A theorem prover proves a formal statement, but only if the statement matches the intended problem. Retrieval proves that a source exists, not that the source is decisive. A search diagnostic shows what happened in a run, not necessarily what will always happen. The agent must know what kind of evidence each tool produces.

VERINA is central here because it exposes the gap between code correctness and proof success. Passing tests is useful evidence, but it is not the same as satisfying a specification. HERO also belongs here because reward scores need careful grouping before they can guide reasoning. AutoEP belongs here because quantitative diagnostics ground optimization strategy, but still have to be interpreted. Tool use makes evidence stronger only when the agent respects the limits of the check.

3. The right tool is chosen by the missing operation

selection

The agent should not ask "what tools do I have?" first. It should ask "what operation is missing from my current state?" If the missing operation is exact lookup, retrieve. If it is arithmetic, compute. If it is syntax validation, run or parse. If it is proof obligation checking, use a prover. If it is feasibility over a large search space, use search. If it is spatial reasoning, use a visual intermediate. If it is uncertainty reduction, ask the question whose answer will change action.

Rational Agents gives the cleanest version of tool selection as information value. LoongRL shows retrieval as a tool for finding the chain that controls an answer inside long context. NEXCO and CDGS choose search-like mechanisms because constrained planning needs more than a fluent next step. Visual Planning chooses image sequences because some tasks are naturally spatial. The paper set is broad because "tool" is not one category; it is a name for the external operation the current state lacks.

4. Tools change representation units

units

A tool often changes what the agent treats as the unit of reasoning. A text problem may become a program. An informal theorem may become formal definitions and obligations. A video problem may become a sequence of spatial states. A graph problem may become executable operations over nodes and edges. A search problem may become candidate sets, scores, feasibility projections, and pruned branches.

This connects directly to the representation theme. Actions Speak Louder than Prompts says some structures are better handled as code than as prose. CRAMF says informal mathematical concepts must be mapped to the exact formal vocabulary of Mathlib4. Visual Planning says spatial plans can be images rather than sentences. L2T says observations can be explained by latent programs. The tool does not only answer a question; it changes the form in which the agent can think.

5. Tools create side effects and authority questions

risk

A tool call may be harmless, like reading a document, or it may change the world, like editing a file, placing an order, sending a message, modifying a database, or controlling a robot. The agent must know the difference. The more a tool can change, the more the system needs permission, scope, logging, rollback, and human review.

The papers on this page mostly emphasize reasoning capability, but the principle extends to agent infrastructure and risk. A theorem prover rejecting a proof has low real-world side effect. A code agent changing production files does not. A medical assistant suggesting a dose, a browser agent submitting a form, or a lab agent selecting an experiment all require stronger boundaries. Tool use is powerful because it creates consequences; that is also why it needs control.

6. Tool results must update state, not just decorate the answer

update

A weak agent calls a tool, pastes the result into the context, and continues as if nothing structural changed. A stronger agent revises its state. It marks a fact as checked, removes a bad branch, records a failed action, changes the plan, stores an evidence pointer, or asks a follow-up question. The tool call matters only if the next decision is different because of it.

AutoEP makes this concrete by feeding search-dynamics feedback into the optimization loop. THOR uses step-level tool-call feedback, not just final answers. T3 preserves partial progress so the system can learn which intermediate steps mattered. CRV shows a deeper version: feedback can motivate intervention on internal features involved in the failure. In all cases, the tool result has to become state.

7. Tool use still needs stopping rules

budget

Tools can make agents better, but they can also create endless loops. The agent can keep retrieving, keep sampling, keep asking, keep running tests, keep trying proof repairs, or keep generating plans without improving the outcome. More external action is not automatically more intelligence. The system needs to know when the next call is likely to change the answer and when it is only adding cost.

ASAG and DECS apply this pressure to visible reasoning length. Reasoning with Sampling applies it to exploration diversity. PonderLM-2 applies it to internal computation. The same principle applies to tools: continue when the next call can reduce uncertainty, check a risky assumption, or repair a failed step; stop when the state is stable enough to answer or act.

TOPIC 05

Planning versus reacting

Planning and reacting are not opposites. A capable agent uses planning to make action coherent, and reaction to keep the plan honest when the world answers back.

A plan is a commitment about future action. It says which subgoals matter, which order looks useful, which constraints must be preserved, and which checks should happen before the agent declares success. But a plan is not the world. Once the agent retrieves evidence, runs code, receives a proof error, sees a visual state, or gets a search diagnostic, the plan may need to change. The agent fails if it never plans, because it becomes locally greedy. It also fails if it never reacts, because it keeps executing a plan after the facts have changed.

The first-principles question is therefore not "should the model plan?" It is "what should be fixed before acting, and what should remain adjustable after feedback?" Some tasks need strong prior structure: proof search, constrained optimization, code migration, experiment design, and multi-step math. Other tasks need rapid adaptation: interactive browsing, debugging, retrieval under uncertainty, visual tracking, and user-guided workflows. Most real systems need both: a plan to avoid wandering, and reaction to avoid being trapped by the first plan.

1. Planning sets the shape of the search

structure

Planning is useful when the task has dependencies. Some steps must happen before others. Some choices make later choices impossible. Some constraints are easy to violate if the agent only follows the next tempting token. A plan gives the agent a way to keep the whole problem in view while working on one step at a time.

NEXCO is a direct example because it treats partial solutions as constrained objects. The point is not only to generate a next piece, but to keep the remaining problem feasible. CDGS has the same spirit inside diffusion planning: generate candidates, prune weak branches, and reconcile overlapping parts. L2T adds another version: infer a latent program so future action is guided by a compact rule rather than surface continuation. Planning is the part of the loop that says, "these choices must fit together."

2. Reaction keeps the plan grounded

feedback

A plan becomes stale as soon as the agent learns something new. A retrieved passage may contradict the assumed answer. A test may fail in a way the plan did not predict. A proof checker may reject the chosen lemma. A search diagnostic may show that the current optimization strategy is not improving. A user may correct the goal. Reaction is the mechanism that lets new evidence override the old path.

AutoEP is important because it makes the planning loop depend on observed search behavior instead of the model's invented account of what should work. THOR uses step-level tool feedback so math reasoning can adjust before the final answer. VERINA shows why proof feedback may force a deeper revision than code tests. Rational Agents also belongs here because the agent may react to uncertainty by asking a better question before committing to action.

3. Over-planning makes the agent brittle

brittleness

A plan can become harmful when the agent treats it as authority after the environment contradicts it. This happens when a model keeps following a written chain-of-thought after a tool result disproves a step, keeps editing code according to an assumed API after reading the actual signature, or keeps solving the wrong question after retrieval reveals a hidden condition. The plan becomes a source of inertia.

This failure is why state updates matter. LoongRL pressures the system to route attention through the evidence path, not merely through an initial plan. CRAMF retrieves formal definitions because a planned proof should obey the library's actual vocabulary. VC-STaR forces visual evidence grounding because a planned answer that ignores the deciding cue is brittle. A plan should guide action until feedback earns the right to revise it.

4. Under-planning makes the agent locally fluent and globally wrong

myopia

The opposite failure is acting one plausible step at a time without preserving the larger structure. The agent may retrieve a relevant-looking passage, run a nearby test, generate a convincing proof step, or choose a graph move that looks good locally but blocks the final solution. Local fluency is not enough when the task has delayed consequences.

NEXCO captures this with feasibility: a local choice can make the rest of the problem impossible. CDGS captures it with pruning and overlap repair. Reasoning with Sampling captures it by keeping alternatives alive instead of collapsing onto the first plausible route. Visual Planning captures it for spatial tasks: each frame-like plan step must fit the later trajectory. Under-planning is a failure to account for consequences that are not visible in the next token.

5. Planning can happen in different representations

representation

A plan does not have to be a written list. It can be a program, a proof sketch, a candidate set, an image sequence, a latent program, a graph search, a set of retrieval questions, or an internal hidden state. The right form depends on what must be preserved. Text is useful for communicating intent. Code is useful for exact operations. Images are useful for spatial state. Formal objects are useful for proof obligations. Search structures are useful for feasibility.

Actions Speak Louder than Prompts treats executable code as the planning medium for graph-like structure. Visual Planning treats image sequences as plans for spatial reasoning. L2T treats latent programs as explanations that can guide future predictions and actions. PonderLM-2 and MDM Reasoning remind us that some planning-like computation can occur without exposing every step as text. The representation of the plan should match the thing that must remain stable across steps.

6. Plans need checkpoints

checking

A plan without checkpoints is just momentum. The agent needs places where it asks whether the current path is still valid. A coding agent should run tests after risky edits. A theorem agent should check obligations after formal steps. A retrieval agent should verify that the cited evidence answers the actual question. A search agent should inspect diagnostics before continuing. A visual agent should check whether the generated trajectory still respects the scene.

THOR, VERINA, HERO, AutoEP, and VC-STaR can all be read as checkpoint papers. They ask how intermediate behavior is judged before the final answer. HERO's reward normalization is a checkpoint-quality issue. VERINA's proof comparison is a checkpoint-strength issue. AutoEP's diagnostics are a checkpoint for search strategy. The common idea is that a plan must earn continuation through evidence.

7. The agent should preserve optionality when uncertainty is high

optionality

When the agent is uncertain, early commitment is expensive. It may choose the wrong source, prove the wrong theorem, optimize the wrong objective, or edit the wrong part of the codebase. A good system keeps alternatives alive until evidence selects between them. This does not mean exploring forever. It means delaying irreversible commitment until the state is strong enough.

Reasoning with Sampling is about preserving diversity across possible reasoning paths. Rational Agents asks which question would most reduce uncertainty before action. T3 keeps useful partial work even when the final trajectory fails. DECS tries to separate useful exploration from redundant tokens. Optionality is not indecision; it is controlled delay when the cost of choosing wrong is high.

TOPIC 06

Verification

Verification is the part of the loop that asks whether a step actually made the task more correct, not whether it sounded reasonable.

Reasoning systems need verification because language is too forgiving. A model can produce a confident explanation for a wrong answer, a plausible proof with a missing condition, a code patch that passes a narrow test, a retrieval citation that is related but not decisive, or a visual answer grounded in the wrong object. Verification gives the system a source of friction. It makes some failures visible before they become final answers or actions.

But verification is not one thing. A unit test, a proof checker, a reward model, a retrieval match, a visual contrast, a search diagnostic, and a human approval all check different claims. The agent has to know what each check proves and what it leaves open. The deeper failure is not only being unchecked. It is using a weak check as if it were a strong one.

1. Verification turns progress into evidence

evidence

Without verification, the agent only has its own impression of progress. It may think a plan is feasible, a proof is valid, a visual cue is sufficient, or a retrieved source answers the question. Verification asks for an external sign that the step worked. The sign may be a tool result, accepted proof obligation, matching source span, reward comparison, or change in search quality.

THOR shows this for math tool use by adding feedback at intermediate steps, not only at the final answer. AutoEP shows it for algorithm control by using search-dynamics feedback. VC-STaR shows it for visual reasoning by using contrastive examples that require the model to identify the cue that actually changes the answer. The common principle is that progress should leave a trace the loop can inspect.

2. Stronger checks cover stronger claims

strength

A check has a scope. A unit test may cover one behavior. A type checker may cover one class of syntax or interface errors. A theorem prover may cover a formal statement. A retrieval citation may support one claim. A visual contrast may distinguish one cue from another. The agent must not treat a local pass as global correctness.

VERINA is the cleanest example because it separates code that appears correct under execution from code that satisfies proof obligations. This is not a small technical gap. It is a difference in what has been verified. CRAMF adds a second angle: formal checking is only meaningful when the model has retrieved and used the right definitions. If the formal object is wrong, a proof can be precise while missing the intended meaning.

3. Verification must match the domain's unit of truth

domain

Different domains expose truth in different forms. In code, truth may be behavior under tests, type consistency, security properties, or a formal specification. In math, it may be a valid proof under exact definitions. In retrieval, it may be a cited source span that answers the actual question. In video, it may be the correct object, event, relation, or temporal boundary. In medicine, it may be threshold-sensitive evidence tied to the right patient and date.

This is why Visual Planning, VC-STaR, UALM-R1, and MetaphorVU belong in a reasoning theme. They show that verification cannot always be text-only. A spatial plan needs spatial coherence. A visual answer needs the right visual evidence. Audio-text reasoning may need acoustic information that a transcript loses. A metaphor graph may verify an abstract relation in video that object labels alone cannot capture. The check should be shaped like the thing the domain treats as real.

4. Reward is a verifier only when comparisons are meaningful

reward

Reward models are often used as verification-like signals, but they can be misleading. A score may be useful within one prompt group and meaningless across another. A reward may favor fluent explanation, excessive length, familiar style, or shallow patterns. If the reward signal does not track the property the agent needs, it will train or steer the wrong behavior.

HERO addresses this directly by normalizing reward inside verifier-defined groups, making the feedback more locally meaningful. DECS separates the penalty for redundant tokens from the value of useful exploration. THOR combines final answer reward with step-level tool feedback. These papers share a practical warning: reward is not truth by default. It becomes useful only when it is aligned with the behavior that should survive.

5. Verification has to catch shortcut reasoning

shortcuts

A model can pass a task for the wrong reason. It may answer a visual question from language priors, solve a math item by pattern, cite a related source without using the decisive line, or produce code that passes easy tests while violating the intended invariant. Shortcut reasoning is dangerous because the final answer may look correct while the representation underneath is brittle.

VC-STaR attacks this with contrastive visual evidence. The model must notice the cue that separates similar cases. LoongRL attacks a related problem in long context: the model must route attention through the evidence chain rather than answer from a distractor. VERINA exposes shortcuts in code by comparing executable behavior with proof success. CRV looks for internal features involved in faulty reasoning, which is a deeper check than judging the final string alone.

6. Verification should support recovery, not only grading

recovery

A useful check does more than say pass or fail. It should tell the agent what state changed. Which proof obligation failed? Which test broke? Which retrieved source was insufficient? Which branch became infeasible? Which visual cue was wrong? Which internal feature seems responsible? A binary grade is weaker than feedback that points toward repair.

T3 matters here because failed trajectories can still contain recoverable prefixes. AutoEP matters because search diagnostics give the agent information about how the strategy is failing. CRV matters because mechanistic repair tries to locate the cause of a reasoning failure inside the model. THOR matters because step-level tool feedback gives earlier recovery signals. Verification is most valuable when it helps the next attempt get better.

7. Verification has a cost and can be overused

cost

Checking everything at maximum strength is not always possible. Proof checking may require formalization. Running tests may take time. Retrieval may increase latency. Visual checks may require extra processing. Human review may be expensive. The agent must decide which claims need strong verification and which can rely on weaker evidence.

ASAG, DECS, PonderLM-2, and Reasoning with Sampling connect to this cost question. They ask when more computation is useful and when it becomes waste. The same holds for verification. A high-risk medical claim, legal conclusion, production code change, or formal theorem needs stronger checking. A low-risk summary may need lighter evidence. The strength of verification should match the cost of being wrong.

TOPIC 07

Error recovery

Error recovery is the ability to turn a failed step into a better next state instead of treating failure as either total collapse or something to ignore.

Agents fail in ordinary ways. They retrieve the wrong evidence, run the wrong command, formalize the wrong object, follow an infeasible branch, over-trust a weak reward signal, miss a visual cue, or keep generating after the useful work is done. The important question is not whether failure appears. It will. The question is whether the system can notice the failure, preserve the part that was useful, discard the part that is misleading, and choose a different next action.

Recovery is where the agent loop becomes more than repetition. A weak loop repeats the same action with different wording. A stronger loop changes state: this source was a distractor, this proof obligation failed, this branch is infeasible, this test did not cover the invariant, this visual cue was wrong, this sampled path is promising but incomplete. Once failure becomes structured information, it can improve the next attempt.

1. First identify the failure type

diagnosis

Not every error asks for the same repair. A retrieval miss asks for a better query or a different evidence path. A proof failure asks for a missing definition, lemma, or invariant. A code failure asks whether the implementation, test, interface, or assumption is wrong. A planning failure asks which earlier choice made the future infeasible. A grounding failure asks which visual, audio, or relational cue was misread.

This is why verification and recovery are linked. VERINA helps separate code behavior from proof obligation failure. LoongRL helps expose when the wrong long-context evidence path was chosen. VC-STaR helps expose wrong visual grounding. AutoEP exposes failed optimization strategy through search diagnostics. Good recovery begins by naming the kind of failure, because the repair operation depends on that name.

2. Preserve useful partial work

salvage

A failed trajectory is rarely all bad. The first subgoal may be right while the later branch fails. A retrieved passage may not answer the final question but may identify the correct source family. A proof attempt may fail while producing a useful intermediate lemma. A code patch may be wrong while revealing the right failing test. Throwing away the whole attempt wastes information.

T3 is the clearest paper for this principle. It treats useful prefixes inside failed or partial trajectories as training signal. That idea is central for agents: success is often built from fragments of previous failure. Reasoning with Sampling also fits because alternative paths can preserve partial options. OpenThoughts matters because high-quality traces teach the model what recoverable progress looks like, not only what final success looks like.

3. Do not let failure poison the live state

containment

The agent must preserve useful failure information without letting a failed branch continue to control the task. A rejected proof step should stay as a warning, not as a premise. A failed command should stay as evidence, not as something to repeat. A distractor source should stay marked as a distractor, not as supporting evidence. A bad plan should become history once the state has changed.

LoongRL is useful here because distractors are not merely absent evidence; they are misleading evidence that must be contained. CRAMF is similar in formal math: the wrong definition can poison the proof path if it remains active. HERO also matters because poorly calibrated reward can make weak candidates look better than they are. Error recovery requires memory with status labels: useful, failed, uncertain, stale, checked, discarded.

4. Change the strategy, not only the wording

strategy

Many agents recover badly by trying the same thing again with a different sentence. Real recovery changes the operation. If retrieval failed, ask a more diagnostic question. If code failed, inspect the interface or run a narrower test. If proof failed, retrieve the exact definition or prove a smaller lemma. If search stalled, change candidate generation or pruning. If a visual answer was wrong, inspect the cue that separates the contrast cases.

AutoEP is a strong example because search-dynamics feedback changes algorithm-control strategy. Rational Agents changes strategy by asking the question with the highest expected information value. Actions Speak Louder than Prompts changes the reasoning interface from prose to code when graph-like structure makes prose fragile. CRV changes strategy at the mechanism level by targeting features involved in the reasoning failure. The principle is simple: a new attempt should differ in the part that caused the old failure.

5. Recovery needs a smaller next check

checkpoint

After a failure, the next step should often be narrower than the original goal. Instead of trying to solve the whole problem again, the agent should check the uncertain part. Does this source actually contain the exception? Does this lemma typecheck? Does this function call match the signature? Does this visual region contain the object? Does this candidate set remain feasible? Smaller checks keep recovery from becoming another uncontrolled rollout.

THOR's step-level feedback fits this idea. VERINA's proof obligations give narrower checks than broad code confidence. VC-STaR uses contrastive evidence to focus the visual check. NEXCO and CDGS keep planning recovery tied to feasible partial objects instead of unconstrained regeneration. Recovery is strongest when it turns a large failure into a small next question.

6. Recovery can be internal, external, or human-guided

layers

Some recovery happens inside the model: hidden computation, revised attention, feature intervention, or a new sampled path. Some happens outside through tools: tests, provers, retrieval, search, diagnostics, and visual checks. Some happens through the human: approving a risky step, clarifying a goal, rejecting a source, or deciding whether a partial answer is enough.

PonderLM-2 and MDM Reasoning show that some corrective computation can happen internally. CRV shows internal repair through feature intervention. THOR, VERINA, CRAMF, and AutoEP show external recovery through tool or diagnostic feedback. Rational Agents gives a route to human-guided recovery when the best next action is asking. A practical agent needs to know which recovery layer is appropriate for the risk and uncertainty.

7. Recovery stops when the state is good enough to act

stopping

Recovery should not become endless repair. The agent needs to know when enough uncertainty has been removed, enough evidence has been checked, or enough failed paths have been ruled out. Continuing after that point can add cost and even introduce new errors. Stopping is part of recovery because a repaired state must eventually support action.

ASAG and DECS connect directly to this boundary: more tokens are useful only when they change the outcome. Reasoning with Sampling keeps alternatives alive, but the agent still has to choose. HERO and verifier feedback can help decide when one candidate is strong enough under the right comparison. Error recovery is complete when the next state supports a better action, not when every possible doubt has been exhausted.

TOPIC 08

Permissions and safety

A reasoning system becomes a safety problem when its outputs can change state outside the model. Permission is the boundary between thinking, proposing, and acting.

Tool-using agents do not only answer questions. They may read private data, run code, edit files, submit forms, call APIs, retrieve documents, trigger experiments, or influence medical, legal, financial, and operational decisions. That makes authority part of the representation. The agent has to know not only what action might help, but whether it is allowed, who authorized it, what side effects it can create, and how the result should be audited.

This section is connected to tool use and verification, but it asks a different question. Tool use asks what operation is missing. Verification asks what evidence proves the operation worked. Permissions ask whether the operation should be available at all under the current state. A tool can be useful, verified, and still unsafe if it crosses the wrong boundary.

1. Separate proposal from execution

authority

An agent should often be allowed to propose an action before it is allowed to perform it. It can suggest a code patch before writing files, draft an email before sending it, identify a medical concern before recommending action, or plan a search before calling costly tools. Proposal is reversible; execution may not be.

This distinction matters for the papers because many of them create stronger action interfaces. THOR makes math operations executable. Actions Speak Louder than Prompts makes code the reasoning interface. AutoEP lets a model influence optimization strategy. Visual Planning creates spatial plans that can guide action. These are valuable, but the more direct the action interface becomes, the more the system needs a line between "this is my candidate move" and "I am authorized to do it."

2. Scope tools by side effect

side effects

Tools differ by what they can change. Reading a public document is not the same as reading private data. Running a local test is not the same as deploying code. Querying a theorem prover is not the same as modifying a repository. Asking a clarification question is not the same as submitting a browser form. The permission model should match the side effect, not the tool's name alone.

VERINA and CRAMF mostly operate in low-side-effect verification spaces: code/proof comparison and formal definition retrieval. A code agent acting on a real project has higher side effects. A medical or legal assistant has higher decision cost even if it only writes text. The principle is that permission is shaped by action cost: what could happen if this step is wrong, leaked, stale, or unauthorized?

3. Keep data boundaries visible

data

Agents mix context from user messages, retrieved documents, tool outputs, model memory, external APIs, and hidden state. Safety fails when these sources blur. A private record should not leak into a public answer. A retrieved distractor should not get the authority of a trusted source. A stale document should not override a current one. A model's internal guess should not be presented as evidence.

LoongRL is relevant because retrieval under distractors already requires source control. CRAMF is relevant because formal definitions have library authority while informal guesses do not. HERO is relevant because reward comparisons only make sense inside the right groups. The same source-boundary discipline becomes a safety discipline: the agent should know where information came from and what it is allowed to influence.

4. Treat hidden channels as part of the action surface

channels

An agent can receive instructions through more than explicit text. A document can contain prompt-like content. A web page can contain hidden instructions. A visual mark can steer an image model. An audio cue can carry information the transcript misses. A tool result can smuggle assumptions back into state. Safety has to cover every channel that can influence action.

VC-STaR, UALM-R1, and MetaphorVU show the positive side of non-text channels: visual, audio, and relational evidence can be essential. The safety version is that these channels can also carry misleading or unauthorized control signals. A multimodal agent must separate evidence from instruction, and instruction from authorization. Seeing a command in an image, document, or tool output does not mean the user authorized the action.

5. Make verification stronger when action cost is higher

risk

The required check should scale with the consequence of being wrong. A low-risk summary can tolerate lighter evidence. A production code change, medical recommendation, formal proof claim, legal conclusion, or physical action needs stronger verification. The agent should not use the same confidence standard for every action.

VERINA shows why stronger claims need stronger checks. THOR gives step-level feedback for math tool calls. HERO asks reward signals to be locally meaningful. VC-STaR checks visual grounding. CRV looks for internal mechanisms behind faulty reasoning. These papers are not only about accuracy; they point toward risk-sensitive verification. The higher the action cost, the more the agent must prove before acting.

6. Preserve audit trails

audit

An agent should leave enough trace for a human or system to reconstruct why an action happened. What goal was active? Which evidence was used? Which tools were called? What failed? What was verified? What permission was granted? What state changed? Without this trail, errors become hard to diagnose and unsafe behavior becomes hard to prevent next time.

This connects back to T3 and error recovery: useful partial work and failed steps are evidence for future improvement. AutoEP's search diagnostics are audit material. LoongRL's retrieved chains are audit material. VERINA's proof/test comparison is audit material. Audit is not paperwork after the fact; it is memory that makes recovery, accountability, and safer future action possible.

7. Human control should attach to the right decision point

human

Human approval is most useful at the point where the action becomes consequential. Asking for approval too early forces the human to judge vague plans. Asking too late turns approval into ceremony after the risky part has happened. The agent should surface the current state, proposed action, evidence, uncertainty, expected side effect, and rollback plan before the irreversible step.

Rational Agents connects because asking the right question can be the safest next action when uncertainty is high. ASAG and DECS connect because unnecessary extra reasoning can waste attention, but premature action can be worse. The human should not be asked to supervise every token; they should be asked to authorize the steps where authority, side effects, or high-cost uncertainty matter.

TOPIC 09

Delegation and multi-agent work

Delegation helps only when the task can be split into parts whose state, authority, and checks can be passed cleanly between workers.

A multi-agent system is not better because it has more model calls. Splitting work creates a new problem: who knows what, who is allowed to act, what state is shared, what disagreement means, and who decides when the group has enough evidence. A single agent can fail by losing state. A group of agents can fail by losing coordination state.

Delegation is useful when roles expose different failure modes. One worker can search, another can verify, another can formalize, another can critique, another can track state, and another can decide whether the evidence is sufficient. But this only helps if the handoff carries the right object: not a vague summary, but the goal, constraints, evidence, uncertainty, tool results, failed branches, and authority boundaries that the next role needs.

1. Split by operation, not by arbitrary persona

roles

A useful role exists because the task needs a different operation. Retrieval is different from proof checking. Code execution is different from critique. Visual grounding is different from language explanation. Search is different from final selection. If roles are only names, the system may produce more text without better evidence.

This connects to THOR, CRAMF, VERINA, LoongRL, and VC-STaR. Each paper emphasizes a different operation: executable math steps, formal definition retrieval, proof-vs-code comparison, evidence-chain retrieval, and visual cue grounding. A delegated system should assign work around such operations. The question is not "which agent persona should speak?" It is "which operation does the task still need?"

2. Handoffs must carry state, not just conclusions

handoff

A weak handoff says "I think answer A." A useful handoff says why: which evidence was used, which alternatives were rejected, which checks passed, which uncertainty remains, and what action is recommended next. Without this structure, the receiving agent has to trust a conclusion without knowing its support.

LoongRL matters because the evidence chain is part of the answer. VERINA matters because "the code passed" and "the proof succeeded" are different handoff facts. AutoEP matters because search diagnostics should pass forward as state, not prose. T3 matters because useful partial work from failed attempts should not be lost at role boundaries. Delegation works when the handoff preserves the state needed for the next operation.

3. Debate is useful only if disagreement is informative

variance

Multiple agents can catch mistakes, but they can also copy mistakes. If everyone sees the same context, uses the same shortcut, and optimizes for agreement, a debate can converge on a wrong answer with more confidence. Disagreement is useful when it exposes different evidence, assumptions, tool results, or failure modes. Empty disagreement is just cost.

Reasoning with Sampling is relevant because several candidate paths are valuable only when they preserve meaningful diversity. HERO and DECS are relevant because feedback must distinguish useful exploration from redundant or low-value output. The separate multi-agent theme says the same thing in process terms: variance within and across speakers can reveal fragile reasoning, but the system must know when variance is evidence and when it is noise.

4. Shared constraints are part of the environment

constraints

When several agents act in the same task, they share constraints. They may share a budget, a context window, a file system, a proof state, a search space, a safety policy, or a user approval boundary. One agent's action can change what another agent is allowed or able to do. Coordination is therefore not optional; it is part of the problem state.

NEXCO and CDGS make this concrete for planning: partial choices must stay compatible with future choices. The multi-agent systems page makes the same point for shared feasible regions and coupling constraints. In software, two coding agents can edit conflicting files. In retrieval, two agents can cite inconsistent sources. In proof work, one agent can import the wrong definition and poison later steps. Shared constraints need shared state.

5. Delegation needs one place where authority resolves

authority

If several agents propose actions, someone or something must decide what becomes live state. Otherwise the system can merge incompatible conclusions, follow two plans, or let an unverified claim control action. Authority can sit with a supervisor agent, a verifier, a human, a formal tool, a policy gate, or a final selection rule.

VERINA points toward formal authority when proof obligations are the real check. HERO points toward calibrated reward authority within comparable groups. Rational Agents points toward information-gathering authority: ask before deciding when uncertainty is high. Permissions and safety add another layer: even a correct delegated conclusion may require human authorization before side effects. Delegation needs a final state update rule.

6. Latent or hidden collaboration still needs inspectable effects

latent

Collaboration does not always happen through visible messages. Agents or modules may share hidden state, intermediate embeddings, cached memories, search traces, visual plans, or tool artifacts. That can be efficient, but it creates an audit problem: if the final action depends on hidden collaboration, the system still needs inspectable evidence that the collaboration improved the state.

PonderLM-2 and MDM Reasoning already show that useful computation may not be visible as text. CRV shows that internal features can be part of failure and repair. UALM-R1 shows that audio and text can both participate in intermediate thinking. The principle for delegation is the same: hidden collaboration is acceptable only if its effect on state can be tested through behavior, verification, or a trace that humans can inspect when risk requires it.

7. Multi-agent work should reduce total uncertainty, not multiply motion

budget

More agents create more outputs, more handoffs, more possible conflicts, and more cost. The system should delegate when another role is likely to reduce uncertainty, strengthen verification, preserve optionality, or expose a failure mode the current agent cannot see. It should not delegate merely because parallelism is available.

ASAG and DECS apply directly here: extra reasoning must earn its cost. Rational Agents adds the expected-information-gain view: the next worker or question should reduce the uncertainty that controls action. Reasoning with Sampling adds the diversity view: multiple paths help only if they are genuinely different enough to test the decision. Delegation is useful when the group state is better than the single-agent state after accounting for coordination cost.

TOPIC 10

Agents across domains

The same agent loop appears across domains, but the useful state, safe actions, tools, and checks change with the world the agent is acting in.

It is tempting to say that an agent observes, thinks, acts, and checks. That is true, but incomplete. A coding agent observes files, symbols, tests, and errors. A theorem agent observes definitions, assumptions, subgoals, and proof obligations. A retrieval agent observes sources, claims, contradictions, and provenance. A video agent observes objects, motion, spatial layout, and event boundaries. A clinical or education agent observes people, knowledge state, risk, and group dynamics. The loop is shared; the state units are not.

This is why agent research cannot be judged only by a generic final-answer benchmark. The important question is what the domain treats as real. In code, behavior is real. In math, formal validity is real. In documents, source support is real. In video, visual evidence and temporal order are real. In medicine, patient-specific thresholds and uncertainty are real. In education, learner state and group process are real. A domain agent works when its loop preserves the domain's real objects through action.

1. Code agents act on executable state

code

For code, the agent's state is not only text. It includes files, symbols, imports, tests, command output, interfaces, diffs, and runtime behavior. The action may be editing, running tests, inspecting dependencies, or turning a structure into executable code. The check is whether behavior changed in the intended way without breaking constraints elsewhere.

Actions Speak Louder than Prompts fits here because code can be the right interface for graph-like and long-text structure. VERINA shows that code tests and proof obligations are different levels of evidence. THOR shows how executable feedback can shape intermediate reasoning. The domain lesson is that code agents need executable understanding: the plan must survive contact with the project, not only with prose.

2. Math and proof agents act on formal obligations

math

For math, state includes assumptions, definitions, lemmas, subgoals, proof obligations, and failed branches. The agent may reason in natural language, but the domain's authority often lives in formal objects. A proof step is not useful because it sounds mathematical; it is useful when it fits the definitions and advances the obligation.

CRAMF retrieves Mathlib4 definitions because formalization depends on exact library vocabulary. VERINA exposes the gap between code correctness and proof success. THOR combines final answer reward with tool-call feedback. The domain lesson is that mathematical agents need exact handles. They must map informal ideas to formal state before verification can mean anything.

3. Retrieval and document agents act on evidence chains

documents

For document work, the agent's state is made of claims, sources, source authority, contradictions, missing evidence, and the current question. The action may be retrieving, comparing, citing, summarizing, or asking a clarifying question. The check is not whether a passage is nearby in meaning, but whether the evidence actually controls the answer.

LoongRL is the anchor here because it ties long-context retrieval to answer reasoning under distractors. Rational Agents adds the question-asking view: when the decisive evidence is missing, ask for the fact whose answer changes action. HERO matters because feedback should be meaningful inside comparable groups. The domain lesson is that document agents need provenance, not just relevance.

4. Search and optimization agents act on feasible futures

search

For search and optimization, state includes candidate sets, constraints, scores, feasibility, diagnostics, and branch history. The agent is not merely predicting the next step. It is managing a space of possible futures where an early choice can make later success impossible.

NEXCO handles feasible partial solutions. CDGS combines diffusion generation with search pressure and pruning. AutoEP uses search-dynamics feedback to reduce hallucinated optimization strategies. L2T learns latent programs that can guide counterfactual reasoning. The domain lesson is that optimization agents need to know how local choices constrain the remaining space.

5. Vision, video, and audio agents act on non-text state

multimodal

For multimodal work, the agent's state may be object identity, visual evidence, spatial layout, motion, event phase, audio timing, speaker cue, or an abstract relation. Translating everything into text too early can remove the deciding detail. The agent has to preserve the signal in the form the domain needs.

VC-STaR checks whether the model uses the right visual cue. Visual Planning uses image sequences as intermediate plans because spatial constraints can be easier to preserve visually than verbally. UALM-R1 uses audio and text in intermediate thinking. MetaphorVU uses relational metaphor structure for high-order video understanding. The domain lesson is that multimodal agents need state beyond captions.

6. Healthcare and education agents act on people and process

people

Healthcare and education make the agent loop socially and clinically sensitive. The state may include patient facts, risk, trainee belief states, group consensus, misunderstanding, uncertainty, and pedagogical timing. The action may be explaining, asking, correcting, escalating, or withholding confidence. The check is not only factual correctness; it is whether the process helped the person or group safely move forward.

The healthcare-and-education-agents page gives ClinTutor-R1 as the local anchor: the agent models individual trainee belief states and group consensus inside a clinical teaching process. Rational Agents connects through question selection under uncertainty. Permissions and verification matter because wrong confidence in clinical settings has higher cost. The domain lesson is that agents working with people must model state inside the interaction, not only inside the problem text.

7. Scientific agents act on hypotheses, methods, and measurements

science

For science, state includes hypotheses, methods, parameters, measurements, failed runs, search diagnostics, assumptions, and provenance. The agent may propose experiments, optimize procedures, compare papers, or translate observations into latent rules. The check is whether the proposed state explains measurements under the right conditions, not whether it sounds like a plausible scientific story.

AutoEP matters because optimization strategy should depend on observed search dynamics. L2T matters because latent programs can explain observations in a way that supports planning. OpenThoughts matters because reasoning traces across science become training material. CRV matters because scientific debugging can include internal mechanism repair. The domain lesson is that scientific agents must keep the chain from method to evidence to claim intact.

TOPIC 11

Human-agent collaboration

A useful agent does not hide its loop from the human. It exposes enough state, uncertainty, evidence, and proposed action for the human to correct the task before the costly step happens.

Human-agent collaboration is not the same as making the model more polite. The collaboration problem is state alignment. The user may know the real goal, the current priority, the acceptable risk, the hidden constraint, the domain convention, or the reason a plausible answer is not good enough. The agent has to surface the right handles so the human can steer the loop: what it thinks is true, what it is unsure about, what it plans to do, what evidence it trusts, and what side effect comes next.

The human should not be forced to supervise every token. That wastes attention and makes the system harder to use. The human should be involved where their judgment changes the next action: goal clarification, authority, risk, source trust, ambiguous evidence, irreversible action, and domain-specific interpretation. Collaboration works when the agent gives the human a compact but faithful view of the current state.

1. Show the current state, not only the final answer

state

A final answer hides too much. The human needs to know what goal the agent is pursuing, which constraints are active, what evidence was used, what remains uncertain, what tools were called, and what action is proposed. This is especially important when the task has changed over time or when old context may be stale.

LoongRL and CRAMF connect here because the path to evidence matters: retrieved chains and formal definitions are not background details. VERINA connects because the human should know whether the result was tested, proved, or only inferred. AutoEP connects because diagnostics explain why a strategy changed. A good interface turns hidden state into reviewable state.

2. Ask when the missing information changes action

questions

Asking the human is not failure. It is the right action when the missing information controls the outcome and cannot be safely inferred. The question should be narrow enough to answer and tied to the next decision. "What do you want?" is often too broad. "Should I treat this source as authoritative?" or "May I edit this file?" is more useful.

Rational Agents provides the principle: ask the question with high expected information gain. ClinTutor-R1 shows the human-learning version: a teaching agent has to track belief states and ask or explain based on what learners understand. In code, developer-tool reliability points the same way: make intent and invariants visible so humans and tools can catch mistakes before execution hides them.

3. Let the human correct state, not just outputs

correction

A user correction should update the agent's state. If the user says the retrieved source is wrong, the agent should mark it as non-authoritative. If the user changes the goal, older plans should lose authority. If the user says a proof obligation is not the intended one, the formal state should be revised. If the user rejects a visual grounding, the cue should stop supporting the answer.

This links back to error recovery. T3 preserves useful partial work while discarding failed endings; human correction should do the same. CRV shows that repair may need to target the mechanism behind the failure. VC-STaR shows that the cue supporting an answer matters. Collaboration is not "user says no, model tries again." It is "user changes the state the next attempt uses."

4. Expose uncertainty in operational terms

uncertainty

A vague confidence score is usually less helpful than operational uncertainty. The agent should say what could change the answer: a missing source, a failed test, an unproved invariant, an ambiguous visual cue, a hidden patient condition, a stale document, or a user permission. The human can then decide whether to gather more evidence, accept risk, or narrow the task.

HERO is relevant because feedback must be comparable before it can guide decisions. Reasoning with Sampling is relevant because several paths may remain plausible. ASAG and DECS are relevant because continuing to reason has a cost. The human-facing question is not "am I confident?" but "what uncertainty remains, what would reduce it, and is it worth the cost?"

5. Put approval at the side-effect boundary

approval

The best time for approval is just before action changes the outside world or commits to a high-cost conclusion. The agent should show the proposed action, evidence, expected effect, risk, and rollback path. This gives the human something concrete to approve or change.

This connects to permissions and safety. Actions Speak Louder than Prompts and THOR create executable interfaces. AutoEP changes optimization behavior. Visual Planning can guide spatial action. In all of these cases, the human should not approve a vague intention; they should approve the next consequential move with enough state to judge it.

6. Match collaboration to domain expertise

domain

Different users can correct different things. A developer can correct an API assumption. A clinician can correct patient risk or missing context. A teacher can correct learner state. A researcher can correct method comparability. A lawyer can correct source authority. A non-expert user may only be able to correct goal and preference. The agent should ask for the kind of judgment the human can actually provide.

ClinTutor-R1 is useful because it models individual trainee belief states and group consensus, not only the medical content. Developer tooling makes programmer intent inspectable. CRAMF and VERINA show where formal tools, not humans, may be the better authority. Collaboration works when authority is assigned to the right source: human, verifier, tool, or domain evidence.

7. Keep the interaction memory current

continuity

A human-agent collaboration creates a live contract: current goal, active constraints, latest correction, approved actions, rejected paths, unresolved questions, and safety boundaries. Old messages remain history, but only some of them should still control behavior. The agent must keep the current contract separate from the transcript.

This connects the agent theme back to long-context memory. LoongRL shows why the evidence path matters under distractors. T3 shows why failed paths can contain useful prefixes. Rational Agents shows why asking can update uncertainty. The collaborative version is direct: remember what the human has made live, and demote what the human has replaced.

TOPIC 12

Training tasks for agents

An agent learns what to preserve from the pressure its training task applies. If the task rewards final answers only, the model may never learn which intermediate state, action, or recovery step mattered.

Training an agent is not only training a model to speak. It is training a loop. The model must learn what observations to keep, when to use tools, how to interpret feedback, when to change strategy, when to ask, when to stop, and what evidence should control the answer. Each training signal teaches a different survival rule. Teacher traces teach what a good path looks like. Tool-call rewards teach which actions are executable and useful. Partial trajectory credit teaches how to keep progress from failed attempts. Sampling teaches exploration. Bottlenecks teach compact state. Prediction teaches future consequences. Verification teaches what cannot be safely faked.

This connects directly to the earlier representation pages. A representation is shaped by pressure. An agent state is shaped the same way. If the pressure is shallow, the model learns shallow agent behavior: long explanations, tool calls as decoration, agreement without evidence, or final answers that hide broken paths. If the pressure is broad and deep, the agent learns to keep the information that changes action.

1. Teacher traces teach the shape of a path

traces

Teacher-generated traces show the model examples of decomposition, intermediate state, tool choice, and answer construction. They are useful because many agent behaviors are hard to discover from final answers alone. The risk is that the student copies surface style instead of the reason the path worked.

OpenThoughts is the anchor here because it treats reasoning supervision as a large engineered supply chain. The important question is not only how many traces exist, but what they contain: useful subgoals, evidence use, recovery, domain variety, and checked conclusions. A trace dataset trains the model's sense of what a normal problem-solving path should preserve.

2. Tool-call rewards teach action quality

tools

If a model is rewarded only for the final answer, it may learn to hide bad intermediate actions. Tool-call feedback makes the action itself trainable. Did the code run? Did the tool call match the problem? Did the proof obligation advance? Did the retrieval produce controlling evidence? The agent should learn that an action is good only if it changes state toward the goal.

THOR is central because it combines episode-level answer reward with step-level tool feedback. AutoEP also fits because search diagnostics shape algorithm-control behavior. VERINA shows that not all action checks are equally strong: code tests and proof obligations train different notions of correctness. Tool-call rewards teach the model that tools are not decorative; they are accountable moves inside the loop.

3. Partial trajectory credit teaches recovery

credit

Long-horizon reasoning often contains useful early work followed by a wrong ending. If training discards the whole attempt, the model loses the chance to learn useful prefixes. If training accepts the whole attempt, it preserves the failure. The training task needs finer credit assignment: what part helped, what part failed, and where should the next attempt branch?

T3 makes this idea explicit by learning from useful prefixes in failed or partial trajectories. Reasoning with Sampling also connects because candidate paths can carry partial evidence even when not all survive. This is the training version of error recovery: failed work should become structured signal, not total waste or hidden poison.

4. Sampling pressure teaches exploration without collapse

exploration

Agents need more than one possible path when the first plausible path may be wrong. Sampling creates breadth across candidate reasoning routes, tool choices, or plans. But sampling can collapse into minor rewrites of the same answer, or explode into useless diversity. The training and inference setup must reward alternatives that expose different assumptions or evidence.

Reasoning with Sampling is the direct paper. DECS also matters because it separates useful exploration from redundant token length. HERO matters because feedback has to compare candidates in a meaningful group. Rational Agents gives the information-value version: explore where uncertainty reduction changes action. Exploration is useful when it preserves real optionality, not when it multiplies text.

5. Bottlenecks teach compact state, but can erase the wrong thing

bottleneck

Agents cannot carry everything at full resolution. Training may force state through hidden computation, a smaller context, sparse dimensions, binary messages, compressed traces, or a cheaper backbone. Bottlenecks are useful when they remove noise and preserve what controls action. They are harmful when they erase exact evidence, failed attempts, source authority, or constraints.

PonderLM-2 and MDM Reasoning ask how reasoning computation can happen without exposing every step as public text. Tool-Augmented SSMs asks whether an efficient sequence backbone can support tool-using agents. These papers connect to the representation-training theme: a bottleneck is only intelligent compression if the training task punishes the loss of action-changing information.

6. Prediction teaches consequences over time

prediction

Agents need to know what will happen if they keep following a path. Prediction pressure teaches state to preserve future-relevant structure: a plan's feasibility, a code change's downstream behavior, a proof branch's obligations, a visual action's spatial consequence, or a scientific hypothesis's expected measurement. Without this pressure, the agent may optimize the next step while harming the later task.

NEXCO and CDGS train or construct around feasible future structure. L2T learns latent programs as explanations that support prediction and counterfactual reasoning. Visual Planning uses image sequences as future-like intermediate states. AutoEP uses search dynamics so strategy is tied to observed progress. Prediction pressure teaches the agent that the next move matters because it changes the future state.

7. Behavior tests prevent learned shortcuts

tests

A training task can look reasonable and still teach the wrong behavior. The model may learn to write long traces, call tools because tools appear in examples, agree with the teacher's style, or exploit reward patterns. Behavior tests ask whether the learned loop actually performs the intended operation: retrieve the controlling source, use the right visual cue, satisfy the proof obligation, recover from failure, or stop when more work is waste.

VC-STaR is a grounding test. VERINA is a proof-vs-code test. LoongRL is a long-context evidence-path test. ASAG and DECS are reasoning-budget tests. CRV tests and repairs internal reasoning mechanisms. The final training principle is that agent behavior has to be tested at the loop level, not only through final-answer accuracy.

TOPIC 13

Evaluation

Agent evaluation should test the loop, not only the final answer. The question is whether observation, state, action, feedback, recovery, and stopping worked for the right reasons.

A final answer can be correct while the agent used the wrong evidence, over-trusted a weak check, ignored a failed tool result, copied a teacher style, or got lucky on a narrow test. Conversely, an agent can fail the final answer while producing useful partial state that a better recovery policy should preserve. Evaluation has to see more than outcome. It has to see process.

Evaluation is also a control surface. Whatever the benchmark rewards becomes pressure on the model and system. If the test rewards final strings, the agent learns final strings. If the test rewards checked tool use, evidence grounding, recovery, permission handling, and correct stopping, the agent has a reason to learn those parts of the loop. The metric tells the agent what kind of behavior is worth becoming.

1. Test state, not only output

state

The evaluator should ask what state the agent carried forward. Did it keep the right goal, source, constraint, proof obligation, failed action, or uncertainty? Did it demote stale context? Did it preserve exact evidence? A final answer without state visibility cannot distinguish real reasoning from lucky completion.

LoongRL is a good state test because answer reasoning depends on tracing the right evidence chain amid distractors. CRAMF tests whether the formal state contains the right definitions. VERINA tests whether code state and proof state align or diverge. Evaluation should ask whether the state that controlled action was the right state.

2. Test action quality directly

action

An agent may choose actions before the final answer exists. Those choices can be evaluated. Did the tool call match the missing operation? Did the retrieval ask for controlling evidence? Did the proof attempt target the right obligation? Did the search step preserve feasibility? Did the question reduce uncertainty?

THOR evaluates tool-call behavior with step-level feedback. Rational Agents evaluates question choice through expected information gain. AutoEP evaluates algorithm-control choices through search diagnostics. NEXCO and CDGS evaluate whether generated partial plans remain useful under constraints. Action quality matters because bad actions can still sometimes lead to good-looking final answers.

3. Test evidence grounding and source authority

grounding

Many agent tasks depend on evidence. Evaluation should check whether the answer used the source that actually controls the question, not merely a related source. It should check source identity, citation span, retrieved chain, visual cue, formal definition, and whether the evidence was current and authoritative.

VC-STaR is a visual grounding evaluation because contrastive examples force the model to use the deciding cue. LoongRL tests long-context grounding under distractors. CRAMF tests formal vocabulary grounding. MetaphorVU tests whether relational support matters for high-order video understanding. Grounding tests should change the evidence and verify that behavior changes for the right reason.

4. Test recovery after controlled failure

recovery

Real agents fail. Evaluation should include wrong retrievals, failed proofs, broken tests, infeasible plans, misleading visual cues, and stale instructions. The point is not to punish failure alone. It is to test whether the agent can diagnose, preserve useful partial work, change strategy, and avoid repeating the same mistake.

T3 points toward recovery-aware evaluation because useful prefixes inside failed trajectories matter. AutoEP's diagnostics create a way to judge strategy repair. CRV evaluates internal repair of faulty reasoning. VERINA exposes proof-test gaps that require more than retrying. Recovery tests should measure whether the next state improves after the failure signal.

5. Test stopping and compute use

budget

An agent can fail by stopping too early or by continuing too long. Evaluation should ask whether additional reasoning, sampling, retrieval, or tool calls changed the outcome. A system that reaches the answer in fewer safe steps is not merely cheaper; it has better control over its loop.

ASAG and DECS directly evaluate reasoning length and redundancy. Reasoning with Sampling asks when multiple paths are useful and when diversity collapses. PonderLM-2 raises the hidden-computation version: perhaps useful computation should happen without long visible traces. Evaluation should reward useful computation, not length for its own sake.

6. Test domain-specific consequences

domain

Generic success metrics miss domain-specific failure costs. Code evaluation should include tests, interfaces, and specifications. Math evaluation should include formal obligations. Document evaluation should include citations and contradictions. Medical and educational evaluation should include process safety and learner state. Multimodal evaluation should include spatial, temporal, and acoustic evidence.

ClinTutor-R1 points toward in-situ interactive evaluation, not only static benchmarks. VERINA points toward formal proof evaluation. VC-STaR points toward visual evidence evaluation. Visual Planning points toward spatial plan coherence. UALM-R1 points toward audio-text reasoning evaluation. Domain evaluation should test the behavior the agent will actually perform.

7. Test whether process evidence predicts transfer

transfer

The strongest evaluation asks whether a learned process works outside the exact benchmark pattern. Does evidence grounding transfer to new distractors? Does recovery work on new failure types? Does tool use generalize to new operations? Does the agent keep state when the conversation or environment changes? Does a learned skill become reusable?

OpenThoughts raises this through trace diversity. Tool-Augmented SSMs raises it through the backbone's ability to support long tool-using behavior. The broader safety-evaluation map includes executable and embodied evaluation because transfer is visible when a process becomes reliable procedural behavior, not when a model memorizes a final-answer format. Evaluation should predict future loop reliability.

TOPIC 14

Failure modes

Agent failures are usually failures of control. The system kept the wrong state, asked the wrong question, trusted the wrong evidence, used a tool at the wrong time, failed to recover, or spent computation after the useful work was over.

This is why final-answer accuracy is too thin as a description of what went wrong. A model can hallucinate because it never retrieved the needed source. It can retrieve the right source and still ignore the decisive line. It can call a tool and misuse the result. It can pass tests while missing the proof obligation. It can keep reasoning after the answer is already settled and introduce a new error. Different papers in this theme expose different breaks in the same loop.

A useful failure analysis asks two questions. First: which part of the loop failed? Second: what evidence would have caught the failure early? The answer should be specific enough to change the design. "The model was wrong" is not a diagnosis. "The model preserved a stale retrieved chain after a contradictory tool result" is a diagnosis, because it points to state update, evidence priority, and recovery policy.

1. Stale or missing state

state

The agent acts from an internal picture of the task. If that picture is missing a constraint, carries an old assumption, forgets a failed attempt, or blends two entities together, every later step becomes suspect. The final output may sound consistent because the model is consistent with the wrong state.

LoongRL exposes this when long contexts contain distractors and the agent must keep the true evidence chain alive. CRAMF exposes it when the wrong formal concept enters the state. Rational Agents exposes it when the agent has not asked the question that would reduce the decisive uncertainty. The repair is not more words; it is better state discipline.

2. Wrong retrieval or weak grounding

evidence

Retrieval can fail by missing the source, selecting a related but non-controlling source, or bringing back the right source without forcing the model to use the deciding evidence. Grounding is not the presence of documents, images, audio, or definitions. Grounding means the answer changes when the controlling evidence changes.

VC-STaR targets this in vision by using contrastive examples where the visual cue matters. LoongRL targets it in long-context reasoning through evidence chains. MetaphorVU targets it in video when the answer depends on a high-order relation, not only object labels. UALM-R1 targets it when audio carries information that a text-only trace would lose.

3. Tool misuse

tools

A tool makes reasoning stricter, but it does not make the agent correct by itself. The agent can call the wrong tool, pass the wrong input, misread the output, treat a weak check as a strong check, or use a tool to decorate a decision that was already made. Tool use fails when the external operation is not tied to the missing fact in state.

THOR makes this visible because math tool calls can be judged step by step. Actions Speak Louder than Prompts shows why code can be a better interface for graph-like operations, but also why the code must actually represent the structure. AutoEP shows the danger of hallucinated algorithm strategies unless search diagnostics are fed back into the loop.

4. Proof-test gaps

verification

A test can show that one case worked. A proof can show that a stronger condition holds. A model can pass the weaker check and still fail the stronger one. This failure mode matters anywhere the surface behavior looks right but the underlying guarantee is absent: code, math, medicine, policy, contracts, and scientific claims.

VERINA is the central example because code correctness and proof success come apart. CRAMF connects because a proof can fail before reasoning begins if the wrong formal vocabulary is chosen. HERO connects because reward must be compared inside meaningful verifier-defined groups. Verification fails when the check is weaker than the claim the agent is making.

5. Overthinking and under-planning

control

Agents can spend too little computation and act from an unstable state. They can also spend too much computation and add noise after the useful work is done. These are not opposite virtues. They are both failures to match compute to uncertainty. The loop should continue when new work can change the answer, and stop when it cannot.

ASAG and DECS address wasteful visible reasoning. Reasoning with Sampling asks when multiple paths help and when diversity collapses. PonderLM-2 asks whether some extra computation should happen internally rather than as long public traces. The failure is not length itself; the failure is computation that no longer buys control.

6. Search without feasibility

planning

Planning fails when local choices make the rest of the problem impossible. A step can look good alone but destroy feasibility later. This happens in combinatorial optimization, scheduling, route planning, code design, proof construction, physical manipulation, and visual planning. The failure is not lack of fluency; it is lack of constraint tracking.

NEXCO handles this by keeping partial solutions feasible. CDGS handles it by adding population search and pruning inside diffusion planning. Visual Planning handles a spatial version where words may lose layout. L2T handles a theory version where the system needs an executable rule, not only a surface prediction.

7. Bad recovery

repair

Failure is expected in hard tasks. The deeper problem is when the agent cannot use failure. It may throw away useful partial work, repeat the same action, trust a poisoned state, or recover by changing style instead of changing cause. Good recovery preserves what was valid, marks what failed, and changes the next action for a reason.

T3 gives the training version by learning from useful prefixes inside failed trajectories. CRV gives the internal-repair version by targeting features involved in faulty reasoning. AutoEP gives the runtime-feedback version through search diagnostics. Recovery fails when the system treats every failure as a fresh prompt instead of an update to state.

TOPIC 15

Architecture choices

An agent architecture is a choice about where reasoning should live. Some work should be visible text, some should be hidden computation, some should be retrieval, some should be executable tools, some should be search, and some should be verifier-guided repair.

There is no single best architecture because the right shape depends on the failure the system must avoid. If the task needs exact syntax, code or proof tools matter. If the task needs current external facts, retrieval matters. If the task needs several possible futures, search matters. If the task needs spatial continuity, visual plans may matter. If the task needs cheaper reasoning, latent computation or adaptive stopping may matter. Architecture is not a fashion choice; it is an answer to what kind of information must be preserved and checked.

A useful design question is: what should be inside the model, what should be outside the model, and what should be visible to the user or evaluator? Moving a function outside the model can make it inspectable and reliable, but adds latency and coordination cost. Keeping it inside the model can be fast and smooth, but harder to audit. Making reasoning visible can help supervision, but can also waste tokens or expose unfaithful explanations. Each paper in this theme chooses a different boundary.

1. Visible reasoning traces

trace

Visible traces are useful when intermediate work needs supervision, debugging, attribution, or user review. They let a teacher, verifier, or human see the candidate steps. The cost is that visible text can become performance theater: long, plausible, and weakly connected to the actual computation.

OpenThoughts, T3, THOR, and Reasoning with Sampling all depend on traces being available in some form. OpenThoughts scales trace supply. T3 extracts useful prefixes from failed traces. THOR rewards tool-use steps. Reasoning with Sampling uses multiple traces as exploration. The architecture works when visible steps carry real credit, not when they are just explanation-shaped output.

2. Latent thought and adaptive stopping

hidden compute

Some computation should not have to appear as text. A model may need internal updates to settle a decision, compare alternatives, or refine a representation before emitting the next token. Hidden computation is attractive when visible reasoning is expensive, private, or not faithful to the mechanism doing the work.

PonderLM-2 puts extra thought into hidden-state steps. MDM Reasoning treats iterative masked refinement as another way to spend computation. ASAG and DECS ask when the system should stop generating visible reasoning. The architectural principle is to separate useful computation from public narration.

3. Retrieval as external memory

memory

Retrieval is the right choice when the needed information is too large, too current, too exact, or too domain-specific to trust from model weights alone. It turns memory into an operation: find the controlling evidence, put it in state, and let the answer depend on it.

LoongRL makes retrieval part of long-context reasoning. CRAMF retrieves Mathlib4 definitions because formalization needs exact vocabulary. Rational Agents gives the question-asking version: decide which missing observation is worth acquiring. Retrieval architecture fails when it returns context without changing state discipline.

4. Executable tools and formal checks

tools

Tools are the right choice when the model's claim should become an object that can run, fail, retrieve, prove, or measure something. The tool boundary matters because it changes a sentence like "this should work" into a consequence that the loop can observe.

THOR uses tool calls for math reasoning. Actions Speak Louder than Prompts uses code as the reasoning interface for graph-like settings. VERINA shows that tests and proofs are different checks. AutoEP feeds search diagnostics back into algorithm control. These architectures make reasoning stricter by giving it an external handle.

5. Search and constrained generation

search

Search is needed when a single next-token path is too brittle. The system may need to keep candidates alive, prune weak branches, project partial solutions back into feasibility, or compare alternatives before committing. This is especially important when early choices constrain later possibilities.

NEXCO uses confidence-guided candidate sets and feasibility projection. CDGS embeds population search and pruning inside diffusion denoising. Reasoning with Sampling keeps alternative reasoning paths live. These papers treat generation as controlled exploration rather than immediate commitment.

6. Modality-specific intermediate forms

modality

Not every useful intermediate representation is text. Spatial tasks may need image sequences. Audio tasks may need acoustic cues. Video tasks may need temporal and relational structure. If the architecture forces everything into prose too early, it may erase the difference that controls the answer.

Visual Planning uses image sequences as plans because spatial state is central. UALM-R1 keeps audio and text in intermediate reasoning. MetaphorVU brings in a metaphor knowledge graph for high-order video understanding. VC-STaR uses contrastive visual grounding so the model has to preserve the decisive visual cue.

7. Backbone and repair mechanisms

substrate

The model backbone determines what state is cheap to carry, what length is practical, and what kinds of updates are natural. Repair mechanisms determine whether failures are handled by prompts, data, runtime checks, or direct intervention inside the model.

Tool-Augmented SSMs asks whether state-space backbones can support tool-using agents efficiently. CRV asks whether faulty reasoning can be repaired through targeted internal feature intervention. HERO shapes optimization pressure by making reward comparisons locally meaningful. The architecture includes the training and repair surface, not only the inference wrapper.

TOPIC 16

Cost and latency

Every part of an agent loop has a price. Tokens, retrievals, tool calls, samples, proofs, verifier checks, rollouts, and human approvals all spend time, money, attention, or risk. The central question is not whether more reasoning helps. It is when extra work is worth its cost.

Cost is not only a systems concern added after the model is smart. Cost changes the behavior the model can afford to learn. A loop that depends on many samples may work in a benchmark but fail in an interactive product. A proof step may be worth the latency for safety-critical code but too slow for casual drafting. A retrieval call may be cheap compared with a wrong medical or legal answer, but expensive when repeated blindly. Good agent design treats cost as part of reasoning, not as bookkeeping.

Latency also changes what counts as good behavior. A browser agent that pauses for minutes feels broken even if it eventually succeeds. A theorem prover can spend longer because the result is stronger. A tutoring agent must keep the learner engaged. A robotics agent may need to act before the world changes. The same architecture can be right or wrong depending on the time scale of the task.

1. Token cost and visible reasoning

tokens

Visible reasoning costs tokens twice: the model spends time generating it, and later context must carry it. Long traces can help when they preserve useful state, but they become waste when they repeat, decorate, or drift away from the controlling evidence. The issue is not whether a trace is long. The issue is whether each part changes the state, action, or check.

ASAG directly targets this by reducing generated tokens without retraining. DECS separates useful exploration from redundant length. OpenThoughts and T3 show the other side: some traces are valuable training material because they contain recoverable credit. The cost principle is to keep expensive text when it teaches or controls something, and remove it when it only fills space.

2. Sampling and rollout cost

exploration

Sampling buys optionality. Multiple paths can expose a better answer, a safer plan, or a recovery route. But every extra sample spends compute and can make selection harder. Sampling is useful only if the system has a way to compare candidates and if diversity still represents real alternatives rather than minor wording changes.

Reasoning with Sampling is the clearest paper here because it asks when inference-time exploration can recover reasoning gains. T3 connects because failed rollouts can still contain useful prefixes. HERO connects because reward must compare candidates inside meaningful groups. The cost question is whether another rollout is likely to change the chosen action.

3. Retrieval cost

retrieval

Retrieval costs latency, context space, and attention. It is worth paying when external evidence controls the answer. It is not worth paying when the agent retrieves broadly, dumps context into the prompt, and still decides from memory or surface similarity. Retrieval should be budgeted around expected information gain.

LoongRL makes this concrete in long-context tasks where the right chain must be found amid distractors. CRAMF makes it concrete in formalization where the exact definition matters. Rational Agents gives the first-principles rule: ask for the observation that most reduces uncertainty about action. Retrieval cost is justified when it changes what the agent can safely conclude.

4. Tool and verifier latency

checks

Tools and verifiers are slower than fluent text, but they can buy stronger evidence. A test run, proof attempt, code execution, search diagnostic, or visual grounding check may be worth the delay because it catches errors that language alone would hide. The tradeoff depends on the cost of being wrong.

THOR pays tool-call cost to make math steps executable. VERINA pays proof cost because tests and proofs expose different levels of correctness. AutoEP pays diagnostic cost to stop hallucinated optimization strategies. VC-STaR pays contrastive grounding cost to force the visual cue to matter. Tool latency is valuable when it prevents a more expensive wrong action.

5. Search cost under constraints

planning

Search can improve planning, but unconstrained search grows quickly. Candidate sets, pruning, feasibility projection, and overlap repair are cost controls. They decide which branches deserve more computation and which should be cut because they cannot lead to a valid result.

NEXCO controls cost by keeping candidate sets feasible. CDGS controls cost through population search, likelihood pruning, and overlap resampling. Visual Planning pays for image-sequence plans when spatial structure would be lost in text. Search cost is justified when it preserves feasibility that a one-shot plan would likely break.

6. Hidden compute and backbone efficiency

substrate

A system can reduce visible cost by moving some work into hidden computation or a more efficient backbone. That does not make the work free. It changes where the cost appears and how inspectable it is. Efficient reasoning still has to preserve the answer-changing state.

PonderLM-2 spends hidden-state thought before token prediction. MDM Reasoning uses iterative masked refinement instead of a pure left-to-right trace. Tool-Augmented SSMs asks whether a state-space backbone can support long tool-using behavior more efficiently. These papers treat architecture as a way to buy useful computation without always buying more visible tokens.

7. Human attention as cost

human

Human review is powerful but expensive. Asking for approval, clarification, or correction costs attention and interrupts flow. It is worth doing when the uncertainty is consequential, the agent lacks authority, or the human has information the system cannot obtain. It is wasteful when the agent asks because it failed to keep state or make a reversible low-risk move.

This connects back to Rational Agents, human-agent collaboration, and safety boundaries. The agent should ask when the answer changes action value, not when it merely wants comfort. In medical, legal, educational, and operational settings, human attention is often the most limited resource in the loop.

SYNTHESIS

Six ways the field is attacking it

1. Build stronger reasoning traces

data and training

One approach is to improve the raw material that models learn from. Instead of hoping a base model discovers good multi-step behavior from generic text, these papers create or preserve traces that contain useful intermediate structure. The key distinction is between traces that are merely long and traces that carry credit: the model must learn which prefixes, examples, or hidden computations actually make success more likely.

ICLR 2026OpenThoughts
OpenThoughts is a scaling paper about reasoning data. It uses a teacher-generated pipeline, based on QwQ-32B, to produce roughly 1.2 million examples across math, code, and science. The important idea is not just that the dataset is large; it is that reasoning supervision is being treated as an engineered supply chain. If reasoning depends on multi-step traces, then the quality, diversity, and coverage of those traces become part of the model architecture in practice.
ICLR 2026T3
T3 focuses on credit assignment inside reasoning traces. Many failed rollouts contain useful early moves, but standard training tends to discard the whole trajectory because the final answer was wrong. T3 preserves informative prefixes, which lets the model learn from partial progress instead of treating success as all-or-nothing. This matters because long-horizon reasoning is usually built from locally useful moves, and a training method that can recognize those moves can improve accuracy while reducing wasted rollout tokens.
ICLR 2026Reasoning with Sampling
Reasoning with Sampling asks whether some gains attributed to reinforcement learning can be recovered through inference-time sampling without collapsing diversity. The deeper issue is exploration. A reasoning system needs several candidate paths because the first plausible path may be wrong, but training can make outputs converge to a narrow style. This paper matters because it separates the value of searching over possibilities from the value of permanently changing the model with RL.

2. Spend computation without wasting it

latent thought and stopping

Another group treats reasoning as a compute budget. The model should think longer when extra computation changes the answer, but stop when extra tokens are ornamental. The practical question is how to add internal work, adaptive generation, or reward pressure without teaching the model to produce bloated explanations.

ICML 2026PonderLM-2
PonderLM-2 adds hidden-state thought steps before token prediction. The first-principles motivation is that not every useful computation should be exposed as text. A model may need extra internal updates to settle an answer, but forcing those updates into emitted chain-of-thought creates cost, privacy, and faithfulness problems. The paper sits in the line of work trying to scale per-token computation while keeping the visible answer compact.
ICML 2026ASAG
ASAG is about adaptive generation control. It tries to improve reasoning accuracy while reducing generated tokens, without requiring a new training run. The underlying failure mode is overthinking: a model continues to elaborate after the useful computation has already happened, or explores irrelevant branches because the decoding process rewards more text. ASAG matters because inference control is becoming a direct capability lever, not just a cost optimization.
ICLR 2026DECS
DECS separates penalties for redundant tokens from the value of exploratory reasoning. That distinction is important because short answers are not always better; sometimes the model needs to explore. The target is not minimal reasoning but non-wasteful reasoning. By decoupling the reward signals, the method tries to discourage empty length while preserving the exploratory steps that actually help solve hard problems.
ICLR 2026MDM Reasoning
MDM Reasoning studies masked diffusion language models as reasoning systems, showing that they can match chain-of-thought transformer reasoning power through an equivalence to padded looped transformers. The conceptual point is that reasoning does not have to be a left-to-right stream of public tokens. If iterative refinement can provide the same computational shape, then the field has more than one architecture for spending thought.
ICLR 2026Tool-Augmented SSMs
Tool-Augmented SSMs asks whether state space models can serve as efficient agent backbones when they have the right tools and training data. This is a systems-level version of the compute question. Transformers are not the only possible substrate for long reasoning, but alternative sequence models must still handle arithmetic, code, and length generalization. The paper matters because agent capability depends on the backbone's memory and control properties, not only on the external tool wrapper.

3. Turn tools into part of the reasoning loop

code, proof, math

Tool use changes reasoning from text prediction into interaction with a stricter object. Code can execute, a prover can reject a proof, and a graph algorithm can expose whether a proposed plan respects structure. These papers show that tools are useful not because they decorate an agent, but because they convert vague intermediate claims into artifacts with consequences.

ICLR 2026THOR
THOR trains mathematical reasoning with tool calls, combining episode-level answer reward with step-level feedback about code or tool-call success. The key idea is that a math agent should not be rewarded only at the final answer; it should also learn whether the intermediate operations it chooses are executable and relevant. This is a bridge between chain-of-thought and programmatic verification.
ICLR 2026Actions Speak Louder than Prompts
Actions Speak Louder than Prompts argues that executable code can be a better interface than prompt-only interaction for long-text and high-degree graph settings. The deeper point is representational: some structures are awkward to reason about as prose but natural to manipulate as code. When the task has graph structure, the model can offload part of reasoning into executable operations instead of holding everything in fragile context text.
ICLR 2026CRAMF
CRAMF tackles autoformalization by retrieving Mathlib4 definitions for the core concepts needed to translate informal mathematics into Lean. The failure mode is not merely that the model lacks mathematical intuition; it may use the wrong formal object. Retrieval grounds the translation in the library's actual vocabulary, which makes the reasoning task less like free-form paraphrase and more like choosing the correct formal handles.
ICLR 2026VERINA
VERINA compares code correctness with proof success in verifiable programming tasks and finds a large gap. That gap matters because code can often pass tests while the proof obligation demands a stronger, more general argument. The paper is useful for this theme because it shows that tool use has levels: execution checks one kind of consequence, while formal proof checks whether the model can state and justify the invariant behind the code.
ICLR 2026AutoEP
AutoEP uses real-time search-dynamics feedback to reduce hallucinated optimization strategies. The problem is that an LLM asked to control an algorithm can invent plausible but ungrounded moves. By feeding quantitative diagnostics back into the loop, the system makes the model's planning depend on observed algorithm behavior rather than rhetoric about what should work.

4. Retrieve, ask, and update under uncertainty

information control

Reasoning often fails because the model acts before it has the right information. These papers view question asking, retrieval, and reward calibration as parts of the same problem: the model must decide which missing information is worth acquiring and how much trust to place in partial feedback.

ICLR 2026Rational Agents
Rational Agents applies Bayesian experimental design to language-model agents. It improves question asking and action selection through Monte Carlo expected-information-gain inference. In simple terms, the agent should ask the question whose answer will most reduce uncertainty about what to do next. This matters because many agent failures are not caused by weak language alone; they come from taking action while still missing the decisive fact.
ICLR 2026LoongRL
LoongRL couples retrieval and reasoning in long contexts. Its tasks require tracing UUID chains, finding the true question, retrieving the right facts, and rechecking answers amid distractors. The first-principles challenge is attention control: the model must not merely fit a long context window, it must route attention through the pieces that form the answer path. This connects long-context work directly to agent planning.
ICLR 2026HERO
HERO uses stratified reward normalization, bounding reward-model scores inside verifier-defined groups and emphasizing prompts where dense feedback matters. The practical issue is that reward scores can be hard to compare across different prompt types. HERO makes the feedback more locally meaningful, so optimization pressure is focused where it can actually distinguish better reasoning from worse reasoning.

5. Search over constrained worlds

planning and feasibility

Planning is not just listing steps. The plan has to obey constraints, fit together across time, and remain feasible as decisions accumulate. These papers use candidate sets, feasibility projection, population search, diffusion denoising, and latent programs to make planning less like verbal intention and more like structured construction.

ICLR 2026NEXCO
NEXCO generates feasible partial solutions for combinatorial problems using confidence-guided candidate sets and feasibility projection. The core problem is that a locally plausible choice can make the remaining problem impossible. By keeping candidate sets constrained and projecting toward feasibility, the method treats planning as controlled expansion through a solution space rather than unconstrained sequence generation.
ICLR 2026CDGS
CDGS embeds population search, likelihood pruning, and overlap resampling inside diffusion denoising. The conceptual move is to combine generative modeling with explicit search pressure. Diffusion can propose compositional plans, but planning needs a way to prune weak branches and reconcile overlapping parts. CDGS is part of the broader shift from one-shot generation to guided construction.
ICML 2026L2T
L2T learns latent programs as explanations for non-textual observations. Instead of predicting future frames directly, it tries to infer an executable theory that accounts for what was observed. This matters because a theory can support planning and counterfactual reasoning in a way a surface prediction cannot. It is the same reason program induction keeps returning in agent work: a compact rule can guide action outside the exact examples seen.
ICLR 2026Visual Planning
Visual Planning uses image sequences as intermediate plans for spatial and geometric reasoning. Some tasks are hard to solve through words because the important state is spatial. A visual trajectory can preserve layout, motion, and geometric constraints directly. The paper broadens the idea of chain-of-thought: the useful intermediate representation may be a sequence of images rather than a sequence of sentences.

6. Ground reasoning in perception and internal mechanisms

multimodal and repair

The last group asks how reasoning connects to the signals underneath it. A model may need to identify the visual evidence that matters, reason across audio and text, use metaphor as a structured bridge between domains, or intervene on internal circuits when a reasoning path goes wrong. These papers make reasoning less text-centric and more grounded in the representations that feed the answer.

ICLR 2026VC-STaR
VC-STaR builds VisCoR-55K with contrastive examples that force precise visual evidence identification. The problem is that a vision-language model can answer correctly for the wrong visual reason, which makes its reasoning brittle. By using contrast, the dataset pressures the model to notice the exact cue that distinguishes one answer from another. This is grounding as an anti-shortcut device.
ICLR 2026UALM-R1
UALM-R1 uses both text and audio in intermediate thinking steps for complex generation tasks. Its importance is that reasoning is not confined to written language once the task itself is multimodal. If sound carries timing, speaker, or acoustic information that text misses, then a useful reasoning trace has to preserve and transform that information instead of translating everything into a lossy text-only channel.
ICML 2026MetaphorVU
MetaphorVU uses a metaphor knowledge graph at inference time to improve high-order video understanding. The paper treats metaphor not as decoration but as a mapping device between domains. That matters for reasoning because hard video understanding often requires recognizing an abstract relation, not just an object. A structured metaphor graph gives the model a way to transfer relational patterns across situations.
ICLR 2026CRV
CRV uses attribution-graph analysis to target transcoder-feature interventions that repair faulty reasoning. Instead of only changing prompts or examples, it looks for internal features involved in a reasoning failure and intervenes there. This is important because it treats reasoning errors as mechanistic phenomena inside the model, not only as bad outputs. If successful, that kind of repair could make model debugging more surgical.
FIELD READ

What this theme says about ICML and ICLR

The big picture is that reasoning is becoming less of a prompt style and more of an engineering object. The papers do not agree on one mechanism. Some add better traces, some hide thought inside latent computation, some use executable tools, some add retrieval and Bayesian information gathering, some search over constrained worlds, and some repair internal circuits. But they agree on the same pressure: a capable model must control its own intermediate work.

That is why this theme sits next to evaluation, agents, software reliability, and multimodal systems. Once models are asked to do real tasks, the important unit is not the final string. It is the path from observation to intermediate state to action to checked consequence. Reasoning, planning, and tool use are the machinery that makes that path work.
