Efficiency changes the algorithm

Efficiency is not only speed after the method is finished. Precision, memory traffic, kernel shape, latency, and device limits decide which computation can exist.

CORE

The budget becomes part of the method

A method that works only under ideal arithmetic, unlimited memory, or slow serving is not the same method in deployment.

Low precision changes rounding. Memory traffic changes which operations are affordable. Latency changes which agent loops can run. A solver that is too slow changes which scientific model is practical. A token or bit budget changes what evidence the model can keep. The first-principles question is: what resource is scarce, and what behavior must remain true under that scarcity?

Why Low-Precision Transformer Training Fails shows that exact-arithmetic equivalence can break under BF16 rounding. TetraJet-v2 studies weight oscillation and activation outliers in FP4 training. LiftQuant makes fractional bit width a deployment object. Frozen-PINN replaces a slow training path with frozen spatial features and ODE solving. FlashSinkhorn changes optimal transport computation around IO. Speculative Actions hides latency in agent action pipelines without changing accepted behavior.

Core rule
An efficiency claim must name the saved resource and prove the task-critical behavior survived the new computation.
FIRST PRINCIPLE

A resource limit changes what computation can be real

The deployed algorithm is the one that fits the machine, time, and precision available.

It is tempting to treat efficiency as an implementation detail after the mathematical method is chosen. The papers in this group show the opposite. If attention fails under low precision, the method is not the same method. If memory traffic dominates time, the kernel shape becomes the algorithm. If an agent cannot wait for sequential tool calls, action speculation changes the control loop. If a PDE method is too slow to train, the scientific method that gets used is a different one.

A first-principles efficiency claim therefore has to name the scarce resource and the preserved behavior together. Saving wall-clock time while changing accepted actions is not pure speed. Saving bits while changing the decision boundary is not pure compression. Saving solver calls while breaking physics is not pure acceleration. The resource constraint becomes part of the method because it changes which computations are possible enough to use.

First-principles test
Ask what resource became scarce, what computation changed because of it, and what behavior stayed the same under that change.

METHOD

Why speed without equivalence is not enough

A faster path must say what counts as the same work.

Sometimes the same work means numerically close outputs. Sometimes it means the same accepted action, the same physical trajectory, the same ranking, the same proof, or the same final answer under a rollback rule. Efficiency papers become clear when they state this equivalence relation. Without it, every speedup can hide a changed task.

The hard cases are where resources interact. Low precision saves memory but changes arithmetic. Tiling saves IO but changes the order of reductions. Speculation saves latency but creates partial actions before certainty. Frozen features save training time but restrict what the model can adapt. The method has to show where those changes remain harmless and where they do not.

FAILURE MAP

How efficient methods drift

Fake budget

The paper optimizes a resource that is not the real bottleneck.

Arithmetic drift

Lower precision changes attention, gradients, or decisions in a structured way.

IO blindness

The algorithm counts math operations but ignores memory movement.

Rollback gap

Speculative work escapes before the system knows it was safe to accept.

Solver mismatch

The faster scientific method no longer respects the original physical constraint.

Average-only proof

The method keeps easy behavior while boundary cases fail under the new computation.

CONNECTION

Why this idea cuts across the atlas

Efficiency is the resource boundary behind many method choices.

Compression asks what information survives after reduction. Efficiency asks why reduction is needed and which computation becomes possible. Test-time compute turns budget into an inference decision. Long-context memory depends on what can be stored, scanned, or retrieved. Systems work makes these constraints concrete in kernels, memory, devices, and serving paths.

This also explains why efficiency papers need more than speed numbers. They need to show the operating region: the device, sequence length, batch size, precision, latency target, and workload shape where the claim is true. A method can be efficient in one region and irrelevant in another because a different resource becomes the bottleneck.

The deeper lesson is that a method is never separate from the resources needed to run it. When the resource changes, the algorithm often changes too.
