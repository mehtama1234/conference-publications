CORE

Scarcity decides what survives

Scarcity is not an implementation detail. It changes the method itself.

If compute were free, context were unlimited, labels were perfect, human experts were always available, privacy had no constraints, and latency did not matter, many design choices would be easier. We could keep every frame, every token, every retrieval result, every intermediate trace, every user correction, every verifier call, every model variant, and every rare-event sample. Real systems cannot do that. They must choose.

Those choices are not neutral. A tokenizer chooses which exact strings become easy or hard. A patching strategy chooses which visual boundaries survive. A KV-cache compression method chooses which context facts remain available. A pruning method chooses which circuits are weakened. A data selector chooses which examples spend update budget. A model judge chooses where human review can be avoided. A tool policy chooses which external actions are worth their cost. A privacy rule chooses which memory can no longer influence behavior.

The deep question is therefore: what is the scarce resource, what useful information depends on it, what mistake becomes cheap when the resource runs out, and what evidence shows the tradeoff is acceptable? A method is good when it preserves the information whose loss would change the downstream decision, while compressing, skipping, or delaying what is genuinely harmless.

First-principles line
A method is defined by what it preserves under scarcity: the useful unit, evidence, state, action, safety margin, or distinction that still survives when budget runs out.

TOPIC 01

Compute scarcity: when more thinking is not free

Compute scarcity asks which reasoning, search, training, or verification steps are worth paying for.

Modern methods often improve by spending more computation: larger models, longer training, more samples, longer chains, verifier loops, search, recursion, tool calls, or test-time scaling. But compute is not free. The useful question is not "does more compute help?" It is "where does one more unit of compute change the decision?" If extra computation only lengthens a trace, samples redundant candidates, or rechecks easy cases, it is not useful control.

This ties to test-time scaling, inference-time control, and optimization papers. The Tell-Tale Norm-style idea is valuable because it tries to identify when extra reasoning intensity is useful. Thinking in Flow treats long reasoning as a trajectory needing selective correction, not endless expansion. Efficient adaptation papers ask whether small updates or bridges can replace full retraining. Compute scarcity turns control into allocation: spend effort where uncertainty, verifier failure, or action cost justifies it.

The failure mode is spending compute on the wrong surface. A model can think longer about a false premise, search many low-quality candidates, or run tools because tools are available rather than because they change the answer. Compute-aware methods need evidence that the expensive step improved the real downstream behavior.

Scarcity principle
Compute should be spent where additional search, reasoning, training, or verification changes a high-cost decision, not where it merely makes the process longer.
TOPIC 02

Precision and compression scarcity: smaller can change behavior

Compression is not only an engineering trick. It decides which information survives under a smaller representation.

Quantization, pruning, low-rank structure, token merging, cache compression, and lossy factual storage all ask the same question: what can be removed without changing the behavior we care about? The answer depends on the task. Losing a small numerical detail may be harmless for one classification task and damaging for diffusion sampling, exact code generation, rare factual recall, or long reasoning stability.

LiftQuant, TetraJet, Error Propagation in Quantized Diffusion Models, ThinKV, Cross-Domain OT Compression, Hallucination Rate-Distortion, and FOCUS/RePAIR all sit here. Error propagation work shows that per-step approximation errors can accumulate through denoising. ThinKV asks which cache entries can be removed without losing rare clues. Cross-Domain OT Compression says source reconstruction is not enough; compressed state must preserve target-domain decision value. Hallucination Rate-Distortion frames factual errors as capacity-limited storage. FOCUS/RePAIR shows pruning can create repetition loops even when ordinary metrics look acceptable.

The deeper principle is that compression has to be judged behaviorally. Smaller is not better if the compressed model loses the exact unit, rare clue, future state, verifier-sensitive detail, or safety distinction the task depends on.

Scarcity principle
Compression is acceptable only when the removed information is harmless for the downstream decision, not merely small in numerical or average-case terms.
TOPIC 03

Context scarcity: not every token deserves to survive

Context is scarce even when the window is long, because attention, retrieval, and compression still decide what becomes usable.

A long window can hold more text, but it does not guarantee that the model will use the right evidence. Retrieval can surface near misses. Summaries can lose exact names. KV-cache compression can drop rare clues. Document chunks can break a table, clause, proof, or code dependency. The scarce resource is not only token count. It is usable evidence at the moment of decision.

This connects back to representation units and memory. If the task needs exact code symbols, a summary is not enough. If it needs a patient trajectory, isolated notes are not enough. If it needs a legal source, retrieved text without provenance is weak. If it needs an image boundary, a caption is lossy. Context scarcity asks which evidence must remain exact, which can be summarized, and which should be forgotten.

Long-context and retrieval papers, ThinKV, and context-compression materials all fit here. The central test is rare-clue retention: does the memory or context system keep the small piece of evidence that changes the answer, or does it preserve common background while losing the decisive fact?

Scarcity principle
A context system is good when scarce context space is spent on evidence that can change the decision, with exactness and provenance preserved where they matter.
TOPIC 04

Data scarcity: examples have marginal value

Data is not equally useful. An example has value relative to the current model, time, mix, and target behavior.

When update budget is limited, training cannot treat every example as equally worth seeing. Some examples teach new distinctions. Some repeat what the model already knows. Some repair failures. Some introduce shortcuts. Some are useful early but wasted late. Some are high quality but underweighted by the learning-rate schedule. Data scarcity turns dataset construction into a control problem.

OPUS, DiReCT, Sequential Data Values, LR Decay Wastes Your Best Data, Midtraining Bridges, and PRISM are core anchors. Sequential Data Values treats selection as path-dependent. OPUS looks at effective update direction. DiReCT selects late-training data by curvature-aware gradient alignment. LR Decay Wastes Your Best Data shows that good late data can be wasted by schedule. Midtraining Bridges and PRISM show that stage timing affects whether later post-training can land.

The scarcity question is not "do we have enough data?" It is "which example should spend update budget now?" A rare example may be worth more than many easy examples. A bridge example may unlock later training. A hard negative may repair a boundary. A legally unusable example may have no deployable value regardless of content.

Scarcity principle
Data value is conditional: spend update budget on examples whose pressure changes future behavior without damaging distinctions that still matter.
TOPIC 05

Human and verifier scarcity: strong evidence is expensive

Evaluation cost shapes what claims can be measured at scale.

Human experts are scarce. Executable environments take effort to build. Formal verifiers may be narrow. Simulators may be cheaper than reality but less faithful. Model judges scale but can inherit bias. Rare-event sampling takes many trials. A benchmark is therefore also a budget allocation: where do we spend expensive evidence, and where do we accept weaker signals?

WebDevJudge, HERO, MoCA, THOR, VALUEFLOW, BNRM, and Rare Event Analysis all fit. WebDevJudge-style work uses artifact-native checks to reduce shallow human judging. HERO combines sparse verifiers with dense rewards. MoCA decomposes multimodal process checks. VALUEFLOW makes value intensity measurable. Rare Event Analysis asks how to estimate events ordinary sampling will not reveal. Each paper responds to limited evaluation bandwidth.

The danger is replacing expensive evidence with cheap evidence that measures the wrong thing. A model judge may reward style. A rubric may hide expert disagreement. A simulator may miss deployment shift. A small rare-event sample may understate tail risk. Cost-aware evaluation should say which evidence surface is strong enough for the claim and where residual uncertainty remains.

Scarcity principle
Use cheap judges where they are calibrated, spend expensive verification where mistakes are costly, and never let evaluation cost quietly redefine the capability claim.
TOPIC 06

Tool and action scarcity: agents need budgets

An agent that can act must know when action is worth its cost.

Tool calls are not free. They cost latency, money, attention, permissions, safety exposure, and sometimes irreversible side effects. A browser can inspect pages but may waste time. A shell can solve tasks but can damage state. A database call can retrieve evidence but may expose private data. A robot action can change the physical world. A code edit can break tests. Tool access turns intelligence into action, and action needs a budget.

ParetoPO is the clean anchor because it treats tool-integrated agents as a tradeoff surface between accuracy and tool-use efficiency. CyberGym and SandboxEscapeBench show the high-agency version: shell and system actions must be evaluated through state and boundaries. The interface page covered what the model can touch; scarcity adds how often, how deeply, and under what permission cost it should touch it.

A good agent policy should call tools when they change the decision, avoid tools when context is sufficient, and escalate only when the action cost is justified by uncertainty or risk. Tool scarcity is a control problem over external action.

Scarcity principle
Tool use should be priced by decision value, not treated as free access to the world.
TOPIC 07

Privacy, legal, and governance scarcity: not all useful data is usable

A data point can be technically useful and still unavailable, illegal, private, unretained, or untrusted.

Governance constraints are resource constraints. Some data cannot leave a client. Some records must be deleted. Some sources lack usable rights. Some private facts cannot be stored in memory. Some training corpora need source records for auditability. Some evaluation workflows must show provenance. These constraints shape method design as much as compute or memory.

Federated and distributed learning papers respond to data that cannot be centralized. Privacy and unlearning papers respond to data influence that must be removed. Copyright-Bench evaluates legal source choices under workflow pressure. Common Corpus and open science infrastructure work treat legally usable corpora as infrastructure, not merely raw text. Data governance pages ask which data can support reproducible, compliant training.

Scarcity here is not lack of bits. It is lack of permission. A model should not count a data source as available unless it can be used, retained, audited, and removed according to the governance surface.

Scarcity principle
Useful data only has deployable value when its permission, provenance, privacy status, and deletion path are compatible with the system's use.
TOPIC 08

Latency and edge scarcity: deployability changes the algorithm

A method that works in a lab may fail as a product because it is too slow, too expensive, too power-hungry, or too dependent on centralized compute.

Latency and edge constraints force different design choices. A robot cannot wait for a slow global search at every control step. A mobile device cannot run unlimited full-precision training. A clinical workflow may need answers before a decision window closes. A tool-using agent may lose value if every step takes too long. A privacy-sensitive system may need local inference even when centralized inference would be easier.

Efficient adaptation, low-precision systems, deployment constraints, token merging, pruning, and edge training all belong here. The point is not simply to make models smaller. It is to keep the capability that matters under the latency, energy, memory, and hardware constraints of the real interface. HDFlow's split between high-level subgoals and faster trajectories is a physical example of this logic. Low-bit and pruning papers show the numerical version.

The test should match deployment. A method is not deployable because it has a lower FLOP count on paper. It is deployable if it preserves the behavior, safety, and evidence needs of the real setting under the actual device and latency budget.

Scarcity principle
Deployment constraints should be treated as part of the problem definition, because speed, energy, locality, and memory limits can change which method is valid.
TOPIC 09

Rare-event scarcity: absence of evidence is not evidence of safety

Some failures matter precisely because they are rare, costly, and easy to miss in ordinary samples.

A model can pass everyday tests and still fail at deployment scale. Rare jailbreaks, unsafe tool actions, privacy leaks, legal violations, catastrophic robot errors, or harmful medical advice may appear too infrequently for ordinary evaluation to catch. The scarce resource is not only samples. It is exposure to the event class that matters.

Rare Event Analysis frames safety evaluation as event definition, probability estimation, and structure exploration. This matters because production volume turns small probabilities into real incidents. Tail-risk evaluation asks what event we are trying to catch, how rare it is, what sampling strategy can reveal it, and how confident we can be after not seeing it.

Rare-event scarcity connects to evidence surfaces and failure repair. If the event is badly defined, samples do not help. If the environment cannot produce the failure, the benchmark is blind. If the verifier is weak, the rare event may appear but not be recognized. Safety evidence has to be designed around the tail, not only the average.

Scarcity principle
For high-cost failures, evaluation must spend sampling effort on the tail event itself, not infer safety from ordinary behavior where the event rarely appears.
TOPIC 10

Tradeoff surfaces: the real object is often a frontier

Many papers are not optimizing one number. They are exposing a boundary between competing goods.

Accuracy versus cost. Safety versus helpfulness. Privacy versus personalization. Memory versus freshness. Compression versus exactness. Tool use versus latency. Human review versus scale. General capability versus specialization. Robustness versus speed. Exploration versus collapse. These are not incidental conflicts; they are often the object of the research.

ParetoPO makes the frontier explicit for tool agents. Catch-22-style detection tradeoffs show safety goals can conflict. ROCP and CRC tie uncertainty sets to downstream decision costs. Cross-Domain OT Compression balances rate and target-domain utility. Entropy Control balances exploration and concentration. Data selection papers balance target improvement, compute cost, and damage to other behavior. These papers are strongest when they show the tradeoff surface rather than only claiming an improvement.

A good tradeoff page should make readers ask: what scarce resource is being spent, what capability is preserved, what capability is weakened, and where is the knee of the curve? Without that, "efficient" and "better" are too vague.

Closing line
A serious method reports not only its best score, but what it had to spend, compress, skip, expose, forget, or risk to get that score.
