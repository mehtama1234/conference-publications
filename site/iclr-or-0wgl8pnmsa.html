Retro*: Reasoning-Intensive Document Retrieval

Teach a language model to rank documents by reasoning through a written checklist, then sample multiple reasoning paths to find the most reliable score.

Paper explainersAll themesLLMs & Foundation Models

Finding the right document for a task is hard when the connection is hidden or sideways. Existing systems read all documents in order, but they also cannot explain why a document matters. Retro* changes this: instead of a hidden guess, the model scores each document by writing down explicit criteria (a rubric) that explain whether it is relevant, samples multiple reasoning paths to fight randomness, and trains itself on both the score accuracy and ranking order at the same time.

Why finding the right document is hard

When you ask a language model a question, it often needs to look up documents first. The tricky part: a document might help even if it does not mention the task directly, because the solution often requires side knowledge that is not directly named. For example, if you ask "how do I fix a leaky pipe," a document about plumbing history is not the answer, but one about pipe materials and pressure zones is, even though it never says "fixing"—fixing depends on understanding materials and pressure, not history.

Most ranking systems just score each document once and pick the top-ranked ones. The score is a black box: you do not know why a document scored high. And one reasoning path is fragile, like asking a witness one question and trusting their answer immediately—they might misunderstand.

In one sentence. Retro* asks the model to score each document by writing out explicit reasoning criteria, samples multiple reasoning paths to reduce guessing errors, and trains the model to improve both individual scores and ranking order.

The algorithm as a flow

What it actually does

Write the rubric

Before scoring, the model lists explicit criteria that define relevance for this query.

Generate multiple scorings

For each document, sample K reasoning paths, each following the rubric independently.

Integrate the scores

Collect all K scores per document; pick the one closest to the middle to reduce noise.

Train on score accuracy

Reward the model when its integrated score matches the true relevance label.

Train on ranking order

Reward the model when relevant docs score higher than irrelevant docs, even if both scores shift.

What the paper changes

What the paper changes

Retro* changes the scoring process itself: instead of a single forward pass through the model, it produces multiple reasoning trajectories and then selects or combines their scores. The model learns to assign scores by reasoning through a written rubric, making the scoring process transparent and multi-path rather than a single hidden computation.

the object it moves  =  scoring trajectories and rubric reasoning
The hidden quantity

The hidden quantity: Score reliability

measured quantity  =  Score reliability (closeness to true relevance)

Score reliability is how close the final integrated score sits to the true label. If a document is actually relevant, a reliable score should be high; if it is not, the score should be low. The paper measures this by training the model against known relevant and irrelevant documents.

Retro* estimates reliability in two ways: first, by sampling K times and picking the score closest to the middle (consensus reduces noise), and second, by rewarding the model whenever its scores match ground truth and whenever it ranks relevant documents above irrelevant ones.

Why it works

Why it works: the causal chain

Retro* breaks ranking into two parts that reinforce each other. First, sampling multiple reasoning paths reduces luck: when the model reasons about whether a document fits a rubric, it can make small errors (misreading, interpreting ambiguously, getting confused by jargon). Asking five times instead of once means most errors cancel out—the true signal (whether the document really matches the criteria) wins because random mistakes point different directions and wash out, while the correct answer repeats consistently. Second, the intra-document reward (score accuracy) works because training directly pushes the model's parameters (the numbers inside the model) toward assigning high scores only to truly relevant documents; when the reward is +1 for correct scores and -1 for incorrect ones, the training algorithm nudges those numbers in the direction that improves agreement with ground truth. Third, the inter-document reward (ranking order) works because penalizing wrong rankings forces the model to learn which documents distinguish relevant from irrelevant; a penalty for ranking irrelevant above relevant pulls the model's parameters toward making that inversion costly.

Why both rewards together work better than one alone: if the model only optimized score accuracy, it could game the system by making all scores very high or very low, which does not break accuracy but destroys ranking; if it only optimized ranking, it could learn a correct ranking order without assigning scores that match true relevance. Composite training prevents this escape hatch; the model must satisfy both objectives simultaneously.

The rubric is the key move: instead of hiding the reasoning inside the model's black box, it forces the model to write out the criteria it is using. Writing criteria forces consistency—each reasoning path must apply the same rules, so random mistakes shrink because they contradict earlier reasoning; and explicit criteria give the training process a measurable signal: did the model correctly evaluate whether each document satisfies the rubric? When the model's rubric reasoning matches ground truth, the reward is positive and the weights move to preserve that behavior; when reasoning contradicts ground truth, the reward is negative and the weights shift to correct it. This creates a feedback loop: consistent reasoning across multiple samples reveals the true signal, and rewards train the model to strengthen that signal.

Math after the picture

The equation: composite reward

First in words:

Total reward = weight-A times (intra-document reward) + weight-B times (inter-document reward)

Then the compact form:

R(y, s) = alpha * Rintra(y, s) + (1 - alpha) * Rinter(y, s)

Every symbol:

R(y, s)total composite reward for a reasoning trajectory y with score s
Rintra(y, s)reward for how well the score s matches the true label: +1 if closest to average, -1 if farthest, 0 otherwise
Rinter(y, s)reward for ranking: +1 if relevant doc scores higher than irrelevant, -1 if reversed, 0 if tied
alphathe balance weight, between 0 and 1; how much to prioritize individual accuracy versus ranking order
A tiny worked example
Say we have five reasoning samples: scores 0.5, 0.6, 0.7, 0.7, 0.8. Average is 0.68.
The score 0.7 is closest to the average, so Rintra for the 0.7 trajectory = +1.
For two documents in one batch (one relevant, one irrelevant), if the relevant doc's sampled score is 0.7 and the irrelevant is 0.4, then Rinter = +1.
If alpha = 0.5, total reward = 0.5 * 1 + 0.5 * 1 = 1.0, meaning this trajectory improved both accuracy and ranking.
If a trajectory scored 0.2 (farthest from mean), Rintra = -1; if its ranking was wrong, Rinter = -1; total = 0.5 * (-1) + 0.5 * (-1) = -1.0, pushing training away from it.

The composite reward teaches the model two things at once: make each score reliable (close to the true label) and make the ranking of documents correct (relevant above irrelevant).

What can go wrong

What can go wrong

Bad rubric kills everything. If the criteria that define relevance are vague or wrong (e.g., the rubric asks the model to look for red flags but the task needs green flags), all K samples will be wrong in the same way. Sampling does not fix bias, only randomness.
Sampling K times adds latency. Asking the model five times instead of once takes roughly five times as long. For real-time systems with tight deadlines, this overhead may be unacceptable.
Score integration can fail on ties. If all K scores cluster tightly (e.g., all between 0.65 and 0.67), picking the one closest to the average will not separate one document from another; a difference of 0.01 is too small to rank correctly.
Done right: validation and tuning. Validate the rubric on a small labeled set before full training. Use cross-validation to pick alpha (the balance between accuracy and ranking). Monitor latency and consider whether test-time scaling is worth the cost for your task.
What a runnable demo should prove

What a runnable demo should prove

Build a small retrieval task: a set of queries, a pool of documents (mix of relevant and irrelevant with ground-truth labels), and a language model. Run three experiments: (1) baseline: rank documents using a single score per document, (2) Retro* without training: score with K samples integrated, (3) Retro* with composite RL training. Measure ranking accuracy (nDCG at cutoff 10: how many of the top 10 are actually relevant) and score accuracy (do high scores correlate with relevance?).

Improvement = nDCG_at_10_after_composite_training minus nDCG_at_10_from_single_score

The demo should show that composite training (optimizing both individual accuracy and ranking order) outperforms a single score baseline, because training on both signals prevents the model from gaming one metric at the expense of the other, and that sampling multiple paths is most valuable when the rubric is clear, because consensus reduces noise only when the model understands the criteria consistently.
