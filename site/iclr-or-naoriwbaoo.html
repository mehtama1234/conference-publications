Gradient-Based Program Synthesis with Neurally Interpreted Languages

Teach a neural network to invent and refine its own programming language using gradient descent, bridging symbolic compositionality with deep learning flexibility.

Paper explainersAll themesProgram synthesis

Program induction — teaching machines to write code — faces a hard trade-off. Symbolic methods write neat, reusable code but only work on domains they were built for. Neural methods adapt to any problem but produce spaghetti that does not compose and fails on new tasks. This paper bridges that divide: a system that learns its own discrete programming language end-to-end, discovering primitive operations and refining them at test time by nudging the program toward examples that work better.

Zero assumption version

Two tribes, both stuck

Symbolic program induction writes explicit code: a rule engine that outputs if-then statements, loops, and function calls. This code generalizes—a rule learned on one dataset ports to similar problems. But building the rule grammar is labor-intensive, and each new domain needs a fresh grammar.

Neural approaches learn directly from data: a neural network guesses the program from examples. The catch: the learned program is a black-box computation graph. When you test it on a new variant (different input size, unseen operation order), it crumbles. A neural network trained to add two 3-digit numbers fails on 4-digit addition.

A beginner might try: use a big neural network with more layers. This fails because the network memorizes training examples but does not invent the underlying rule.

In one sentence. Neural Language Interpreter learns a discrete programming language automatically, then refines that language at test time by nudging primitive choices to adapt to new problems.

The algorithm as a flow

What it actually does

Build a primitive vocabulary

The network discovers atomic operations (arithmetic, memory access, control flow) during training.

Encode programs as sequences

Each program is a variable-length sequence of primitives, not a fixed computation graph.

Relax discrete choices into smooth decisions

A mathematical relaxation trick pretends discrete primitive choices are smooth, so nudging signals can steer them.

Interpret the sequence

A differentiable executor runs the primitives in sequence, producing an output.

Refine at test time

Given a new task, nudge the program choices based on errors to fit the new data, without retraining.

What the paper changes

What the paper changes

Instead of asking 'what weights should this network have?', NLI asks 'what sequence of discrete operations should this program run?' The paper moves the optimization target from continuous weights to discrete program sequences.

the object it moves  =  Program sequence choices
The hidden quantity

The program likelihood under the learned language

measured quantity  =  How well each primitive fits the task

Behind every program choice sits a confidence score: how likely is this primitive the right next step for this input? This score comes from the network's learned understanding of the task. When the network sees a new task at test time, these scores start misaligned. Refining them through nudging makes the program adapt.

The paper estimates this score by running the current program on examples and measuring the error (how far the program's output sits from the correct answer). Large error signals 'the program is wrong' and nudging shifts the primitive choices to reduce it.

Why it works

Why it works: the causal chain

The core trick: ask the network to output a sequence of discrete choices (which primitive at step 1, which at step 2, etc.) instead of a long list of numbers that a neural network would have. Discrete choices seem incompatible with the standard training method (nudging the numbers to shrink error), so the paper uses a relaxation technique that pretends each discrete choice is smooth. This allows the entire program to be trained end-to-end by nudging, discovering which primitives are useful.

At test time, given a new task with examples, the network makes an initial program guess. The error on those examples (the distance between the program's output and the correct answer) points toward better primitive choices, because the paper has made the primitive choices differentiable — small shifts in those choices propagate backward to show which shifts would reduce the error. The paper nudges the program choices through the differentiable executor to refine the program — no retraining, just small adjustments to which primitives are chosen. This works well because the program can now change length (add or remove steps) and composition (use different primitives), adapting faster than a neural network locked in place after training.

Why this bridges the gap: symbolic methods gain compositionality (discrete primitives combine naturally); neural methods gain test-time flexibility (gradients adapt the program to new data). The result solves complex problems that require rapid adaptation to unseen tasks, because the program structure itself can be refined.

Math after the picture

The refinement equation

First in words:

To adapt at test time, nudge each primitive choice in the direction that reduces error, weighted by how much that choice affects the final answer.

Then the compact form:

choice_i <- choice_i - learning_rate * d(error) / d(choice_i)

Every symbol:

choice_ithe network's confidence in primitive i at position i
errorhow far the program output is from the correct answer
d(error) / d(choice_i)the gradient: how much error changes when choice_i changes
learning_ratethe step size; how aggressively to nudge
A tiny worked example
Suppose the program currently picks primitives [add, copy, multiply] and makes an error of 5.0 on the test example.
The gradient says: add contributes -0.2 to error change (reducing add hurts), copy contributes +0.8 (reducing copy helps), multiply contributes +0.1.
Update: add_new = add - 0.1 * (-0.2) = add + 0.02; copy_new = copy - 0.1 * 0.8 = copy - 0.08; multiply_new = multiply - 0.1 * 0.1 = multiply - 0.01.
The program now trusts copy less and add more, biasing the next run toward using copy less.

Nudging through the executor allows the program to adapt to new tasks without retraining, because the primitive choices can move independently without touching the rest of the network.

What can go wrong

What can go wrong

Primitive vocabulary too large or small. If the network discovers too many primitives, the program becomes cluttered and refinement is noisy. Too few, and the network cannot express the task. The paper must tune the vocabulary size per domain.
Gradients vanish through the executor. A long program sequence (many primitives chained together) can make gradients shrink to zero by the time they reach the first primitive choices. This blocks test-time refinement for complex programs.
Overfitting to the adaptation examples. Refining the program at test time on a handful of examples can fit too closely to those examples, learning quirks instead of the true rule. Using a gentle penalty on large changes or stopping nudging early can prevent this.
Done right. Choose primitives that decompose the problem naturally, use shallow program depths, and validate on held-out adaptation examples to catch overfitting.
What a runnable demo should prove

What a runnable demo should prove

Build a task where the training set uses inputs of one size and the test set uses a different size (e.g., adding 2-digit numbers in training, 4-digit in testing). Train NLI end-to-end on the training set. At test time, run gradient descent on the test examples to refine the program. Measure the accuracy on unseen test inputs of the new size. Compare to a frozen neural network and to in-context learning.

adaptation_gain = new_task_accuracy_after_refinement - new_task_accuracy_before_refinement

The demo must show that a few nudges on a handful of new examples move the program's accuracy noticeably higher, proving that test-time refinement is working.
