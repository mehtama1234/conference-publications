HVR-Met: A Hypothesis-Verification-Replanning Agentic System for Extreme Weather Diagnosis

Diagnose extreme weather with an agent loop that proposes a cause, checks it against evidence, and replans when the evidence disagrees.

Paper explainersAll themesAgents & Tool Use

Weather forecasting tells us what may happen next, but diagnosis asks why a dangerous event is forming and which signals support that explanation. That task is hard because the agent must combine many evidence sources, domain knowledge, and multi-step reasoning. HVR-Met builds a meteorology-focused multi-agent system around a closed loop: form a hypothesis, verify it against evidence, and replan if the check fails.

Zero assumption version

Why extreme weather diagnosis is harder than ordinary prediction

Extreme weather diagnosis requires more than detecting a pattern in data. A useful diagnosis must connect observed signals to a causal story about pressure systems, moisture transport, instability, timing, and location. That demands iterative reasoning because one candidate explanation may fit one signal and fail on another.

Generic agents struggle here because they often lack domain-specific checking routines and because simple one-pass reasoning does not support repeated correction. HVR-Met addresses this by building a dedicated loop that keeps testing candidate explanations against meteorological evidence.

The paper's move in one sentence. Turn weather diagnosis into a repeated cycle of propose, verify, and replan so that the system can correct wrong explanations before reaching a final conclusion.

What the paper changes

What the paper changes

The paper changes the reasoning loop used for weather diagnosis. Instead of a one-shot answer, it inserts explicit verification and replanning stages grounded in expert knowledge.

The hidden quantity

Hypothesis validity: the hidden quantity

measured quantity  =  How well a candidate weather explanation matches all relevant evidence at once

The central hidden quantity is hypothesis validity. A candidate explanation can match some signals while failing others, so the system must estimate whether the whole story is still coherent enough to keep or whether it should be revised.

This quantity is hidden because no single measurement directly says the current explanation is right. The agent must aggregate support and contradiction across many checks. HVR-Met uses verification and replanning to repeatedly sharpen that estimate.

Why it works

Why this works

Explicit verification helps because complex diagnosis is rarely solved in one pass. A first explanation may be partly right, but a structured checking stage can expose where it fails, which gives the system a concrete target for revision.

Replanning matters because the agent should not treat a failed hypothesis as a final answer. By revising the explanation and testing again, the system can gradually converge on a diagnosis that better fits the evidence. The atomic-level benchmark also helps because it evaluates the small reasoning steps that make the final diagnosis credible.

A simplified verify-and-replan score

First in words:

Score a candidate explanation by how much evidence supports it minus how much evidence contradicts it, and replan when the score falls below a threshold.

Then the compact form:

hypothesis_score = support_total - contradiction_total ; replan when hypothesis_score < threshold

Every symbol:

hypothesis_scoreoverall validity score for the current explanation
support_totalsum of evidence checks that agree with the explanation
contradiction_totalsum of checks that conflict with the explanation
thresholdminimum score required to keep the current explanation
A tiny worked example
Suppose an explanation says a storm is driven mainly by moisture transport and local uplift.
Radar structure and moisture indicators support that story, giving support_total = 0.7.
But pressure evolution and timing disagree, giving contradiction_total = 0.5.
Then hypothesis_score = 0.2.
If the keep threshold is 0.4, the system must replan because the current explanation leaves too much unresolved conflict.

The paper's real system is more detailed, but the core logic is direct: keep testing whether the current explanation earns enough support to survive.

What can go wrong

What can go wrong

Bad expert rules can mislead the loop. Expert knowledge helps guide reasoning, but weak or outdated rules can steer the system toward the wrong checks because the loop trusts those rules during verification.
Replanning can become expensive. Repeated hypothesis revision improves diagnosis, but too many loops can slow the system because each new pass triggers more tool use and more evidence checks.
Some events may support several plausible stories. When multiple explanations fit much of the evidence, the system may remain uncertain because the available signals do not cleanly separate the causes.
Done right. Use fine-grained evaluation for intermediate checks and require each final diagnosis to survive explicit evidence tests so that the loop is judged on reasoning quality rather than fluent wording.
What a runnable demo should prove

What a runnable demo should prove

Build a compact event-diagnosis agent for a small weather dataset with interpretable evidence channels such as rainfall, pressure, wind, and moisture. Let the agent propose a cause, score that cause against the evidence, and revise when the score is too low.

The demo should prove that explicit verification improves final diagnosis because the system can detect when its first explanation leaves contradictions unresolved, and that replanning helps most on hard cases where several causes are initially plausible.
