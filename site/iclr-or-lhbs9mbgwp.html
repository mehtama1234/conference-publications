Combination-of-Experts with Knowledge Sharing for Cross-Task Vehicle Routing Problems

Solve many routing variants with experts tied to basic constraints, then share general routing knowledge across those experts so new combinations and new constraints are easier to handle.

Paper explainersAll themesOther

Vehicle routing problems differ because they impose different constraints on the same core task of visiting customers with limited vehicles. One task may add time windows, another may add pickup and delivery rules, and another may add capacity limits plus route length limits together. A model trained as one dense network across all tasks often blurs those differences. A standard mixture-of-experts model splits work across experts, but it usually assigns experts by instance patterns without explicitly tying them to the underlying constraints that define each task. This paper uses the structure of the problem more directly. It gives separate experts to basic constraints, lets tasks activate combinations of those experts, and adds a sharing path for routing knowledge that is useful across many constraints. That matters because unseen tasks are usually new combinations of known constraints, not entirely new optimization problems.

Zero assumption version

Why one shared routing model misses unseen constraint combinations

Many routing variants share the same basic search problem: choose customer order, assign customers to vehicles, and keep route cost low. The variants differ in the rules that routes must obey. Capacity, time windows, pickup-delivery precedence, and depot structure each change what a valid route looks like.

A fully shared model tries to compress all those rules into one stored weight set. That can work on training tasks but often struggles on unseen tasks, because the model has not separated which part of its behavior comes from capacity, which part comes from time windows, and which part comes from general route construction. A standard expert model can also miss this structure if its experts are not linked to the actual constraints.

The paper's move. Assign experts to basic constraints and let a task use a combination of them, while a shared channel learns routing behavior that remains useful across many constraints.

The algorithm as a flow

What it actually does

Factor each routing task into basic constraints.

Describe a task as a set of rule components, because generalization should follow the rule structure that defines the task.

Assign experts to those constraints.

Give each basic rule its own expert path, because the model should learn rule-specific behavior instead of storing all behavior in one mixed space.

Add a shared knowledge path.

Learn route-building behavior that applies across many tasks, because many routing decisions are useful regardless of the exact constraint set.

Combine active experts for each task.

Turn on the experts corresponding to the task's constraints, because a new task is often just a new combination of known rules.

Plug in new experts for new constraints.

When a genuinely new rule appears, add a specialist for that rule, because the existing shared path and old experts can still be reused.

What the paper changes

What the paper changes

The paper changes the routing model from one undifferentiated network, or one generic expert pool, into a system where experts correspond to basic constraints and a separate channel stores routing knowledge that should transfer across tasks.

The hidden quantity

The hidden quantity

measured quantity  =  which parts of routing behavior belong to constraints and which belong to the shared core

The hard question is not only how to solve today's task. It is which decisions are caused by a specific rule and which decisions come from general route construction. For example, serving nearby customers together may be useful in many tasks, while inserting a pickup before its matching drop-off is tied to one rule.

CoEKS makes that split explicit. Constraint experts capture behavior tied to one basic rule, and the shared path captures behavior that should survive across many tasks. That separation matters because unseen tasks usually demand recombining known rule behaviors rather than relearning routing from zero.

Why it works

Why constraint-tied experts generalize better

A dense model sees many task labels but may not represent their compositional structure. If it learned capacity-plus-time-windows during training, it still may not know how to handle capacity-plus-route-length later, because it did not isolate what capacity knowledge looked like on its own. A constraint-tied expert solves that by giving capacity behavior its own place to live.

Once behavior is separated this way, unseen combinations become easier because the model can activate experts it already knows for each participating rule. The shared path adds the common part of routing, such as constructing short routes and grouping nearby customers, so every task does not need to relearn that core behavior inside each expert.

The plug-in design for new constraints is also important. When a new rule appears, the model does not need to rewrite all existing knowledge. It can attach one new expert for the new rule and reuse the shared path plus the older experts. That reduces relearning because only the new rule-specific behavior must be added.

A tiny worked example
Suppose a task has capacity and time-window rules.
The shared path evaluates general route structure for the customer set.
The capacity expert adds pressure against routes that overload a vehicle.
The time-window expert adds pressure against visits that arrive too late or too early.
A later task with capacity and pickup-delivery rules can reuse the capacity expert and the shared path, then swap in the pickup-delivery expert.
The model therefore transfers the parts it already knows instead of learning the full task again.

The main structural idea is additive composition over active constraints plus a shared routing core.

What can go wrong

What can go wrong

The constraint split can be incomplete. If an important behavior depends on an interaction between two rules and that interaction is not captured by the expert design, the model may still miss part of the task logic.
New constraints still need data. A plug-in expert reduces relearning, but it does not remove the need for examples of the new rule because the new expert must still learn what that rule changes.
Wrong expert assignment hurts transfer. If a behavior is stored in the wrong expert or in the shared path by mistake, later combinations may activate the wrong knowledge and produce invalid routes.
Done right. The method works best when tasks are genuinely compositional, because then each expert can learn one rule's effect and the shared path can carry the common routing backbone.
What a runnable demo should prove

What a runnable demo should prove

Create a small routing benchmark with four basic rules: capacity, time windows, pickup-delivery precedence, and maximum route length. Train on several rule combinations and hold out others. Compare a dense baseline, a generic expert model, and CoEKS. Then add one new rule with a plug-in expert. The demo should show whether CoEKS solves held-out combinations better because it can recombine the experts for the known rules, and whether it adapts to the new rule with fewer updates to the older parts of the model because the old rule knowledge stays in place.
