The web has math, but broken math

The internet is full of math content: textbooks, lecture notes, research papers, homework solutions. To train a model that solves math problems, we want to use all of it. But there is a problem: web pages store math in many different ways. Some use MathJax (a library that renders math in browsers), others use KaTeX, others raw LaTeX markup, others MathML (yet another standard). When you download a page as plain text, all these formats get mangled. Symbols turn into garbage. Equation structure breaks apart.

A naive approach would be to find any page with an equation and dump the text. That fails badly: the page has navigation menus, ads, comments, warnings—all that noise gets mixed in with the math. The equations themselves get corrupted. A research paper's careful equation becomes scrambled text. You end up with a huge dataset where half the math is wrong.

The move. Render the page in a browser-like way first, so all equation formats become visible. Then clean up the text intelligently, standardize equations to LaTeX, and remove the noise.

The algorithm as a flow

What it actually does

Render each webpage

Use lynx to display equations in text form, converting MathJax/KaTeX to visible symbols.

Split into chunks

Break the rendered page into text blocks, each likely to be one idea or one equation.

Filter for math

Keep only chunks that contain equations or code; discard navigation and ads.

Clean with LLM

Use a language model to remove boilerplate, fix corruption, and standardize notation.

Standardize format

Convert all equations to LaTeX, a standard mathematical notation format.

The hidden quantity

Preservation of mathematical structure

measured quantity  =  structural fidelity

Structural fidelity measures how well an extracted equation keeps its original meaning and format. A perfectly fidelity extraction looks like the original; a corrupt extraction has missing pieces or scrambled symbols.

The paper estimates this by checking: Do the equations render? Are all symbols present? Is the logical flow intact? They count how many equations pass each check.

Why it works

Why careful extraction works

The problem is that equations live in HTML in many formats. A naive text dump does not understand that these formats exist, so it copies raw markup. Lynx is a text-mode browser—it actually renders the page like a browser does, turning all those format differences into plain text equations. That removes the first barrier to understanding.

The second problem is noise. A page is not just math; it has menus, ads, author names, dates. If you keep all of it, the training data is mostly garbage. The pipeline splits the page into chunks and filters to only chunks containing equations or code. That makes the data denser in signal.

The third problem is inconsistency. Even after extraction, the math is in different notations. Some use different symbol names; some use different spacing; some are partially broken from rendering. An LLM is good at recognizing corrupted math and repairing it while preserving meaning. It also standardizes everything to LaTeX, so the training data is uniform.

Measuring extraction quality

First in words:

For each equation e in the extracted dataset, the quality score is one if e is complete and consistent, zero if corrupted. The dataset quality is the fraction of equations that pass both checks.

Then the compact form:

fidelity = count(valid_equations) / total_equations

Every symbol:

valid_equationsequations that render without error and keep all original symbols
total_equationsall equations in the extracted dataset
fidelitythe fraction of extraction that succeeds
A tiny worked example
Suppose a webpage has 100 equations.
Naive dump produces 60 intact equations (60% fidelity) because some turn to garbage.
Render + cleanup: lynx recovers 20 more, LLM fixes 10 corrupted ones. Now 90 intact (90% fidelity).
Result: 30 percentage-point improvement by preserving structure, not losing work.

Fidelity is simple: the fraction of math that survives extraction unchanged. Higher fidelity means less training time wasted on broken examples.

What can go wrong

What can go wrong

Rendering fails on exotic markup. Some pages use custom equation syntax. Lynx cannot render every dialect. Pages with rare formats fall back to text dump, losing equations.
LLM hallucination during cleanup. The language model might invent symbols or change meaning while fixing corruption. A guessed symbol is as bad as a missing one.
Over-aggressive filtering removes real math. The noise filter discards chunks that look like boilerplate but contain equations. A strict filter loses signal.
Done right: verification and human review. Sample the output and check that extracted equations match the originals. Use conservative filtering. Verify LLM repairs with a second model before trusting them.
