UltraGauss: Gaussian Splatting for Ultrasound 3D Reconstruction

Adapt Gaussian Splatting to ultrasound physics by rendering through probe-plane intersection instead of light-ray projection, turning operator-dependent 2D slices into reliable 3D volumes in minutes.

Paper explainersAll themesComputer Vision

Ultrasound machines show doctors one 2D slice at a time, and reconstructing the full 3D shape requires manual skill, lots of training, and many slices. This paper replaces that with UltraGauss: a method that takes a set of 2D ultrasound images and assembles them into a clean 3D volume automatically. The trick is not using the usual light-ray method (which does not match how ultrasound actually works) but instead rendering through plane-based sampling, the same way ultrasound probes physically sweep through tissue.

Zero assumption version

The ultrasound interpretation bottleneck

Ultrasound machines are cheap, safe, and give real-time images, so doctors use them everywhere. But they show one 2D slice at a time. A skilled operator must sweep the probe slowly while imagining the full 3D shape in their head, mentally stitching the slices together. The result depends heavily on the operator's training and experience — two operators on the same patient get different readings.

The naive approach: collect lots of 2D slices and try to reconstruct the 3D volume automatically. But existing methods fail in one of three ways. Some assume light travels in straight rays (true for cameras, false for ultrasound — sound bounces and bends). Others require so much memory or computation that they are unusable in a clinic. A few methods try to fuse slices into voxels, but they break when slices are spaced unevenly or when the operator moves the probe unpredictably.

The stuck spot. You have many 2D ultrasound images from a single subject, and you want to build a faithful 3D model that matches how ultrasound physics works, but all current fast methods are incompatible with ultrasound, and all compatible methods are too slow for the clinic.

The algorithm as a flow

What it actually does

Input: a sequence of 2D ultrasound slice images

Each image is a 2D cross-section, captured as the probe moved through the patient.

Represent the 3D volume as a cloud of Gaussians

Each Gaussian is a smooth blob with a 3D position, opacity (how solid), and shape.

Render by slicing through the Gaussian cloud

For each 2D ultrasound image, intersect the probe plane through the 3D Gaussian cloud and accumulate the blobs that sit on that plane.

Measure the mismatch and adjust Gaussian positions

Compare the rendered 2D slice to the real observed slice; nudge each Gaussian a tiny bit to reduce the mismatch.

Repeat until the Gaussians align with all observed 2D slices

After a few minutes of adjustment, the Gaussian cloud is positioned so it faithfully reproduces all input slices and fills the 3D volume.

What the paper changes

The single thing that changes

The paper replaces the rendering step used in standard Gaussian Splatting. Instead of shooting rays through the Gaussian cloud (as you would for a camera photograph), UltraGauss slices through the cloud with 2D planes that match the shape and orientation of the ultrasound probe as it moves. This one change makes the method compatible with ultrasound physics while staying fast enough for clinical use.

The hidden quantity

The hidden quantity: probe-plane alignment error

measured quantity  =  mismatch between predicted and observed ultrasound planes

The paper's deep insight is a hidden number: for each 2D ultrasound image, the method computes how badly the rendered Gaussian cloud mismatches the real observed slice. This is not a traditional loss function that sums over pixels; instead, it measures plane-by-plane alignment. When a Gaussian sits exactly on a probe plane that the operator swept through, it contributes accurately to the rendered image. When it sits off-plane, it contributes noise.

The paper estimates this alignment error by rendering each 2D slice using only the Gaussians that sit on (or very near) that plane, then comparing pixel-by-pixel. This forces the optimization to place Gaussians where they belong: on the actual trajectory of the ultrasound probe. The method keeps track of which Gaussians are 'active' for each slice by computing Mahalanobis distance from each Gaussian to the plane (a mathematical way to ask: how far is this blob's center from this plane, accounting for the blob's shape).

Why it works

Why it works: plane-wise rendering matches ultrasound physics

Standard Gaussian Splatting renders by shooting rays through space, accumulating the Gaussians each ray hits. This works perfectly for a camera because light actually travels in straight lines. Ultrasound does not. A probe sends a pulse of sound into tissue, it bounces around, and the echoes return to the probe's surface. Each echo comes back from tissue along the same 2D plane the probe swept through, not from some arbitrary ray direction.

UltraGauss exploits this physics. Instead of asking 'which Gaussians does a light ray hit?', it asks 'which Gaussians sit on this 2D ultrasound plane?' It renders each 2D slice by taking all Gaussians near that plane, accumulating their colors and opacities within the plane, and reading out a pixel grid. Because only on-plane Gaussians contribute to each slice, the Gaussians are forced to arrange themselves exactly where the real ultrasound data lives — on the planes the probe actually swept through.

This is dramatically faster than implicit methods (like NeRF-like neural representations) that require computing the full ray contribution for every query, because UltraGauss only processes Gaussians sitting on the current plane instead of ray-tracing through the entire 3D volume. It is much more efficient than voxel grids (fixed memory containers) that lock you into a fixed resolution, because Gaussians adapt their size and shape to the data. The Gaussians are explicit (you can see them and their positions), sparse (only Gaussians near the plane are processed), and matched to physics (they sit on the planes where echoes actually originate).

Math after the picture

The Gaussian rendering equation

First in words:

For a pixel x on the probe plane, sum the color and opacity of all Gaussians near that plane, weighted by their opacity and color blending.

Then the compact form:

c_hat(x) = sum_i (c_i * prod_j(1 - alpha_j)) + alpha_i * c_i, where alpha_i is the opacity of Gaussian i, c_i is its color, and the product accumulates occlusion from Gaussians in front.

Every symbol:

c_hat(x)the final rendered color at pixel x
c_ithe color of Gaussian i (RGB or grayscale)
alpha_ithe opacity (transparency) of Gaussian i, range [0,1]
xa pixel coordinate on the 2D probe plane
ithe index of each Gaussian in the cloud
prod_j(1-alpha_j)occlusion from all Gaussians in front of i (those closer to probe)
A tiny worked example
Suppose pixel x sees three Gaussians on the plane: Gaussian 1 (color 100, opacity 0.8), Gaussian 2 behind it (color 80, opacity 0.6), Gaussian 3 behind that (color 50, opacity 0.5).
Gaussian 1 contributes: 0.8 * 100 = 80 (fully front).
Gaussian 2 is partially blocked: (1 - 0.8) * 0.6 * 80 = 0.2 * 0.6 * 80 = 9.6.
Gaussian 3: (1 - 0.8) * (1 - 0.6) * 0.5 * 50 = 0.2 * 0.4 * 0.5 * 50 = 2.
Total color: 80 + 9.6 + 2 = 91.6. The front Gaussian dominates; back Gaussians fade due to occlusion.

This alpha-blending formula is identical to standard Gaussian Splatting, but applied only to Gaussians on the probe plane, not all Gaussians along a ray.

What can go wrong

What can go wrong

Gaussian shape must stay mathematically well-behaved. Each Gaussian has a shape that determines how stretched or squashed it is. This shape is stored as a mathematical object (a matrix, which is just a table of numbers). If this shape becomes numerically unstable, the training process breaks down. The paper solves this by building the shape as a product of two simpler components that are always stable by construction. This approach is more efficient because it avoids expensive safeguards (like clamping or projections) and lets the training adjustments flow directly without constraint-checking overhead.
Too few Gaussians and details are lost. If you do not have enough Gaussians, the 3D volume becomes blurry. The paper scales up to 2 million Gaussians, which stays fast because only Gaussians on each plane are rendered. But underfitting still hurts reconstruction quality.
Irregular or incomplete probe sweeps confuse alignment. If the operator does not sweep the probe in a regular pattern, or if some slices are missing or noisy, the Gaussians can get stuck and fail to converge. The paper demonstrates it still works when data is sparse, but does not claim perfect recovery under extreme probe motion.
Done right: probe-plane coordinate conversion. By lifting 2D pixel coordinates into 3D using the known probe orientation and position, and expressing Gaussians in the probe's local coordinate frame rather than a global frame, alignment stays stable even when slices are unevenly spaced.
What a runnable demo should prove

What a runnable demo should prove

A runnable demo would take a real or synthetic 3D ultrasound volume, simulate what a 2D ultrasound probe would see by slicing the volume at regular intervals, and pass those 2D slices to UltraGauss. After 5-20 minutes of optimization, the demo renders a new 3D visualization and compares it to the original volume using SSIM (how similar the pixels are). The key metric is speed: UltraGauss should reconstruct a clinically usable 3D volume in under 30 minutes on a consumer GPU because it only processes planes, not entire rays, giving implicit and voxel-based methods which both need full volume traversal.

SSIM = structural_similarity_index(rendered_slices, ground_truth_slices), where SSIM ranges from 0 (completely different) to 1 (identical); clinical realism = expert_clinician_preference_vote

The demo must show that probe-plane rendering, not light-ray rendering, is the right physics match for ultrasound, and that the method stays fast even when controlling millions of Gaussian positions and shapes.
