Continuous Chain of Thought Enables Parallel Exploration

Instead of picking one discrete word at a time, a language model can output continuous values to explore multiple reasoning paths in parallel, then select discrete answers.

Paper explainersAll themesLLMs & Foundation Models

Language models normally build their reasoning one word at a time by picking from a fixed vocabulary. This paper asks: what if instead the model output continuous numbers—smooth decimal values that sit between words? That richer space lets the model explore many reasoning paths at once, like trying multiple branches of a solution simultaneously. Theory shows this parallelism shrinks how much computation is needed, and practice shows that teaching the model to optimize its own outputs outperforms the old one-word-at-a-time approach.

Zero assumption version

Why word-by-word reasoning gets stuck

Today's language models think by picking one word at a time: Is the answer A or B? Pick A. Then: given A, is the next step C or D? Pick C. This forward-only search (always taking what looks best right now) misses better paths that looked wrong at first.

For puzzles that need real search—like find numbers that sum to 100—one-word-at-a-time is a bottleneck. The model locks into one path and cannot undo it. A beginner would try: make the model backtrack and retry failed branches. But replaying the reasoning costs extra computation (start over from the beginning), and the model has no natural way to say which parts deserve a second look.

In one sentence. Picking one word at a time forces the model to lock into one path; it cannot explore multiple futures in a single run.

The algorithm as a flow

What it actually does

Input problem

Model reads the puzzle (e.g., find three numbers that sum to 100).

Output lists of numbers

Instead of one word, output a list of decimal numbers that blend together multiple candidate next steps.

Track parallel traces

The continuous blend implicitly keeps multiple reasoning paths alive all at once (several half-finished answers laid over each other in one list of numbers).

Refine with supervision

Show the model real solution traces and teach it to output numbers that match the pattern of those traces.

Decode discrete answer

At the end, extract words from the list and return the best solution the exploration found.

What the paper changes

What changes

The paper replaces one-word-at-a-time picking (choosing word A, then word B, then word C in sequence) with continuous numbers (decimal values that sit in a smooth space instead of picking from a fixed word list).

the object it moves  =  output from discrete words to continuous numbers
The hidden quantity

Parallelism: how many paths at once

measured quantity  =  effective branching factor

The hidden quantity is the number of distinct reasoning paths the model can hold at the same time. In standard word-picking, it is always 1 (one path). With continuous numbers that blend alternatives, the model can pack multiple paths into a single list of numbers.

The paper estimates this by counting how many separate solution traces can be pulled back out from the continuous output. A model with longer lists of numbers can fit more traces inside. The math shows the parallelism is limited by the list length—a 768-number list can hold far more parallel branches than a 128-number list.

Why it works

Why continuous outputs enable parallel search

One-word-at-a-time picking forces a choice at each step: pick the best word and move forward. Once you pick, you cannot undo it without starting over. Continuous numbers break this lock. Instead of choosing between word A or word B, the model outputs a blended list that contains the essence of both, weighted by how likely each is. That single list holds multiple possible futures at the same time.

Training uses a clever trick: show the model a real solution, then teach it to output numbers that match the pattern of how often each word appears in that solution. When the model sees many training solutions, its output becomes a blend of all of them. At decode time, the model pulls words from the list by seeing which word each number slot votes for. This vote is consistent across the list because training aligned them all to the same real solutions.

The payoff is speed: instead of running through the problem 10 times (once per branch), the model explores all branches in one pass. The blended list compresses many branches into a single list of numbers.

Math after the picture

Matching output to target pattern

First in words:

loss measures how far the model's output list is from the target solution's pattern

Then the compact form:

L = (1/T) * sum_t || f_theta(s_t) - E[e_k | trace] ||^2

Every symbol:

Ltotal loss (error) the model trains to minimize
f_theta(s_t)the list of numbers the model outputs at step t
E[e_k | trace]the average pattern of what should happen at this step (across all target solutions)
Tnumber of steps in the solution
||...||^2squared distance between two lists (how far apart they are)
A tiny worked example
Suppose at step 2, the model should blend three correct solutions.
Solution A says pick word 7 (represented as the list [0.1, 0.9]); Solution B says pick word 9 (list [0.8, 0.2]); Solution C says pick word 7 (list [0.1, 0.9]).
Average target: ([0.1, 0.9] + [0.8, 0.2] + [0.1, 0.9]) / 3 = [0.37, 0.67].
Model currently outputs [0.4, 0.65]. Distance squared = (0.4-0.37)^2 + (0.65-0.67)^2 = 0.0009 + 0.0004 = 0.0013.
Training adjusts the model's output toward [0.37, 0.67], so the blend matches the real solutions.

The model learns to output numbers that sit exactly between the target solutions, compressing multiple branches into one blended list.

What can go wrong

What can go wrong

Output list too short. If the list of numbers is too short, the model cannot blend enough parallel traces. A 64-number list caps parallelism at about 3-4 branches; a 768-number list can hold 10 or more. Must match problem complexity to output list size.
Mismatch between training and extraction. If training teaches the model to blend multiple solutions but extraction tries to pull words out naively, the result might not make sense. Different numbers need to vote for the same word to form a coherent solution.
Training signal too strong. If you teach the model too hard to optimize its own outputs, it may find shortcuts or memorize the training examples instead of learning to reason.
Done right: list size matches problem, training and extraction aligned, learning tuned carefully. When these three pieces fit together, continuous outputs outperform one-word-at-a-time on hard reasoning.
What a runnable demo should prove

What a runnable demo should prove

Build a simple subset sum solver: given a list of numbers and a target sum, find three numbers that add up to the target. Train a small transformer using standard discrete word-picking, and train an identical transformer using continuous CoT. Measure: (1) the percentage of test cases each model solves; (2) the number of inference steps (forward passes) needed to reach a solution. Continuous CoT should solve more cases and use fewer steps.

solve_rate = correct_solutions / total_test_cases; efficiency = average_steps_to_solve

The demo makes it impossible to miss: continuous outputs let one pass do what one-word-at-a-time needs many passes to achieve.
