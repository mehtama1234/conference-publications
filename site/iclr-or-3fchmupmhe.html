Frozen Priors, Fluid Forecasts: Prequential Uncertainty for Low-Data Deployment with Pretrained Generative Models

Estimate deployment risk from very few real samples by mixing what has been seen with a frozen data generator, then simulating future metric values under the rule that will actually be used.

Paper explainersAll themesOther

Teams often launch a model with only a handful of real examples from the new setting. At that point, simple questions such as "what fraction of alerts will fire next week?" or "what average score should we expect?" are unstable because the sample is tiny. This paper builds uncertainty intervals around those operational numbers without retraining the model. It mixes the few observed examples with draws from a frozen generator that already knows the broad shape of the data, then resamples future deployments under the same forecast rule that will be used in production.

Zero assumption version

Why tiny deployment samples break ordinary intervals

Suppose a spam filter moves to a new customer and the team has only 20 real messages. They still need interval estimates for long-run quantities such as alert rate, average score, or the right moment to retrain. Standard confidence intervals treat the data as if the rule were only the sample itself, so they swing wildly when the sample is small. Full Bayesian updates assume the model will be refit as new data arrives, which is often false in deployment. Per-example set methods answer a different question because they cover one prediction at a time, not the average behavior of the whole system over the next week or month.

The missing piece is that deployment uses a fixed forecasting rule. The system will keep mixing old knowledge and new observations in a specific way. If the interval method does not simulate that exact rule, its uncertainty estimate is about a different procedure. This paper fixes the target first, then measures uncertainty for that target.

The core move. Define the deployment forecast rule first, then build intervals by resampling future runs of that same rule.

The algorithm as a flow

What it actually does

1. Freeze an existing data generator

Start with a generator that was already trained before deployment and leave it unchanged.

2. Mix real observations with generated draws

Use a time-dependent weight so early forecasts borrow more from the generator and later forecasts listen more to real data.

3. Define the exact metric of interest

Choose a deployed quantity such as average score, tail rate, or average negative log loss.

4. Resample future deployment paths

Replay many possible futures under the fixed forecast rule and record the metric value for each replay.

5. Read off an interval

Take quantiles of those replayed metric values to form a current or long-run uncertainty interval.

What the paper changes

What the paper changes

The paper changes the object of uncertainty estimation from an unknown population average to the forecast rule that will actually be deployed. Instead of asking for a timeless interval around the population mean, it asks: if we keep using this frozen generator plus this update schedule, what range of operational metric values should we expect now and over time? That change matters because operations care about the behavior of the running rule, not about an ideal estimator that nobody will deploy.

the object it moves  =  the deployed forecast rule for future metric values
The hidden quantity

The hidden quantity: trust weight on real data

measured quantity  =  the schedule that decides how fast forecasts move from earlier knowledge to observed data

At deployment time the main hidden quantity is not the metric itself. It is the weight that says how much the forecast should trust the few observed examples versus the frozen generator. If that weight moves toward the sample too fast, intervals become noisy because a handful of observations can dominate. If it moves too slowly, intervals become biased because the generator may not match the new site.

The paper chooses this weight with a unique Dirichlet schedule and tunes its single control value by a small-sample minimax rule. In plain terms, it picks the schedule that limits the worst-case damage from two sources at once: random noise from too little data and mismatch between the generator and the real deployment stream.

Why it works

Why it works: simulate the exact rule you will run

The method works because it keeps the forecasting rule fixed and puts all uncertainty on the future data stream. Each replay uses the same mixture rule that deployment would use, so the interval answers the same operational question the team cares about. That alignment is why the intervals are better calibrated than plain bootstrap baselines, because the bootstrap only resamples the tiny observed set and does not account for the frozen generator or the time path of the deployed rule.

The replay procedure is lightweight because it never needs to retrain the generator or evaluate a full likelihood. It only needs draws from the frozen generator and the current observed sample. That makes the method practical for many existing generators, including text and image models, while still producing intervals for long-run quantities such as average loss or tail rates.

The forecast mixture equation

Next forecast = weighted measured sample + remaining weight on the frozen generator

Then the compact form:

A tiny worked example
Suppose the current metric is average alert score and only 20 real cases have arrived.
Set the current weight to 0.35 on the observed sample and 0.65 on the frozen generator.
If the sample average score is 0.62 and the generator's average score is 0.48, the forecasted average is 0.35 x 0.62 + 0.65 x 0.48 = 0.529.
Now replay many future runs by drawing new cases from this same forecast rule and recomputing the average each time.
The middle 90 percent of those replayed averages becomes the 90 percent interval for the deployed metric.

The schedule matters because it controls how quickly the forecast moves away from old knowledge and toward the new deployment stream.

What can go wrong

What can go wrong

The frozen generator may be badly mismatched. If the generator was trained on data that differs sharply from the deployment site, the mixed forecast can stay biased for too long because early weight is still placed on the wrong source.
The metric may not be close to linear. The paper focuses on averages, tails, and related quantities. A metric with hard thresholding or strong interactions can be harder to replay accurately because a small shift in the sample can flip the metric abruptly.
Fast drift can outrun the schedule. If the deployment stream changes suddenly after launch, the chosen weight may adapt too slowly because it was tuned for the earlier mismatch level.
When it works best. The method is strongest when the generator is broadly useful, the deployment sample is small but not empty, and the target metric is a stable average or tail quantity, because those conditions let replayed futures track real operational behavior.
What a runnable demo should prove

What a runnable demo should prove

Build a small notebook with a frozen text or image generator, then reveal only 10, 20, and 50 real deployment examples. For each sample size, estimate an interval for one operational quantity such as average negative log loss or average alert score. Compare three methods: sample-only bootstrap, a Bayesian update that keeps refitting, and the paper's forecast-first replay. The demo should then reveal a much larger held-out stream and check whether the realized long-run metric lands inside each interval. The paper's method should win because it simulates the same rule that deployment used.

The notebook should also show a retraining trigger. Once the observed stream pulls far enough away from the frozen generator, the replayed intervals should widen or shift so that a retraining recommendation becomes obvious.
