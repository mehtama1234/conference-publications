HATSolver: Learning Grobner Bases with Hierarchical Attention Transformers

Solve larger polynomial systems by arranging the model around the tree structure those systems already have, so the model spends work only where terms actually interact.

Paper explainersAll themesOther

A system of multivariable polynomial equations can often be solved by converting it into a Grobner basis, which is a rewritten form that exposes the same solution set in a much easier shape. The trouble is cost: the number of term interactions can explode. This paper uses a hierarchy-aware sequence model so the computation follows the nested structure of the equations instead of flattening everything into one long list.

Zero assumption version

Flat processing wastes work on algebra that is already nested

A polynomial system is built from layers: variables combine into monomials, monomials combine into polynomials, and polynomials combine into a system. A Grobner basis rewrites that system into a form where elimination and consistency checks become easier. In exact algebra, that rewrite is one of the standard routes to solving the system.

The hard part is that a flat model reads every symbol as if it lived at the same level. Then it must rediscover which symbols belong inside the same monomial, which monomials belong inside the same polynomial, and which polynomials constrain each other. That extra search raises cost because the model attends across many pairs that do not matter.

The problem. Grobner-basis computation gets expensive when the model ignores the equation tree and spends focus on many irrelevant symbol pairs.

The algorithm as a flow

What it actually does

Step 1: Encode the polynomial system as a tree.

Separate symbols into layers such as term, polynomial, and full system so the input structure is explicit.

Step 2: Read each small group locally.

Build summaries inside each local part first because the model must learn how symbols combine locally before it can compare distant parts usefully.

Step 3: Pass those summaries upward.

Combine local summaries into larger summaries so each higher layer sees compact descriptions instead of raw symbol strings.

Step 4: Train with gradually harder systems.

Use curriculum learning, which means starting with easier systems and increasing size over time, so the model learns the rewrite rules before facing the largest cases.

Step 5: Predict the Grobner-basis form.

Generate the rewritten algebraic output from the hierarchy-aware state built in the earlier steps.

What the paper changes

What the paper changes

The paper changes the reading pattern. Instead of one flat pass across all symbols, it uses a hierarchy-aware pass that first builds local meaning and only then builds system-level meaning.

The hidden quantity

The hidden quantity: wasted pair checks

measured quantity  =  cross-level interaction count

The cost driver is not only system size. A large share of the cost comes from how many symbol pairs the model compares even though they belong to unrelated local pieces. If a model compares every symbol to every other symbol, it spends time on many pairs that contribute nothing to the final rewrite.

This paper reduces that count by summarizing each local piece first. Then higher layers compare summaries rather than raw symbols, which means the model performs fewer useless comparisons and can spend its budget on the relations that matter.

Why it works

Why the hierarchy helps

A Grobner-basis rewrite depends on local algebraic combinations and on how those local pieces constrain each other across the full system. The hierarchy matches that split. First, the model builds local summaries where the strongest local dependencies live. Second, it exchanges only those summaries at higher levels.

That arrangement works because the higher-level pass starts from already-combined pieces. It does not need to rediscover basic term structure by scanning the full raw sequence again. The model therefore uses fewer focus links overall, and the saved capacity can be spent on system-level constraints that determine the final basis.

Math after the picture

The equation: total focus cost by level

First in words:

Total cost equals the sum of within-group attention work plus the sum of higher-level attention work across group summaries.

Then the compact form:

total_cost = sum over groups of local_cost(group) + upper_cost(group_summaries)

Every symbol:

groupone local algebra unit such as a term or a polynomial block
local_cost(group)the work spent comparing items inside that local unit
group_summariesthe compact states produced after each local unit is read
upper_cost(group_summaries)the work spent comparing only the summaries at the higher level
total_costthe full computation used to process the system
A tiny worked example
Suppose a flat reader would compare 100 raw symbol pairs across one system.
Now split the system into 4 local groups.
Inside the groups, the model performs 10 pair checks per group, so local cost is 4 times 10, which is 40.
At the upper level, it compares 4 summaries and spends 6 more checks.
Total cost becomes 40 plus 6, which is 46.
The hierarchy saves 54 checks because many raw-symbol comparisons were never needed.

The exact constants depend on the architecture, but the paper's point is that hierarchical grouping changes the scaling by cutting many unnecessary full-sequence interactions.

What can go wrong

What can go wrong

Bad tree encoding. If the input hierarchy does not match the actual algebraic structure, local summaries become misleading and the upper-level pass combines the wrong pieces.
Curriculum that jumps too quickly. If the training schedule moves to large systems before the model has learned the small rewrite patterns, errors compound because later levels depend on correct local summaries.
Tasks that need more global interaction than expected. Some algebra instances may depend on far-reaching relationships that do not compress well into local summaries, so a strict hierarchy can hide useful global detail.
Done right. Choose a hierarchy that mirrors the algebra and increase instance size gradually so local rules are stable before full-system reasoning starts.
What a runnable demo should prove

What a runnable demo should prove

Build a toy generator for multivariable polynomial systems with known Grobner-basis outputs. Compare two readers on the same training set: one flat sequence reader and one hierarchy-aware reader. Track how large a system each model can solve before exact-match accuracy drops sharply.

The demo should also log how many focus links are evaluated in each design, because the paper's claim is not only that accuracy rises but that larger instances fit because the interaction budget is used more carefully.
