Robots learning from generated videos

Teach a robot to manipulate objects by having it watch AI-made videos, not human demonstrations.

Paper explainersAll themesRobotics & Control

Robots normally learn tasks from videos of humans doing them. This paper asks: can a robot learn just as well from videos that an AI makes? The answer is yes—a video generation model creates task videos, a language-and-vision model filters out the bad ones, and the robot copies the object motion from the good ones.

Zero assumption version

Why robots are stuck

Today, robot learning relies on people filming themselves doing tasks. A human pours water; the robot watches and learns. A human wipes a table; the robot copies. This works, but collecting these videos is slow, expensive, and limited—you can only film tasks that someone is willing to perform, and you have to film many versions to cover all the variations of a scene.

A beginner might think: why not just tell an AI what you want the robot to do, and let it generate the motion? The problem is that most AI-generated videos are full of errors—a hand phases through a cup, or the pour misses entirely. Using these broken videos for training would teach the robot to do broken things.

The paper's one-sentence move. Filter AI-generated videos by checking them against the task description, then use the good ones to teach a robot.

The algorithm as a flow

What it actually does

Generate

Feed a diffusion model a scene image and language command; it produces 10-20 candidate videos.

Filter

A vision-language model watches each video and scores whether it matches the command.

Depth and track

For videos that pass, extract depth maps from each frame and track the 3D position of the target object.

Pose sequence

Convert the tracked motion into a sequence of 3D object poses (position and rotation).

Retarget and execute

Adjust the poses to match the robot's body and reach limits, then run the motion.

What the paper changes

What the paper moves

The core object that changes is the source of training motion: from real human videos to filtered AI-generated videos. Both feed into the same imitation learning pipeline—the robot imitates trajectories. The change is not in the learning step, but in where the training data comes from.

the object it moves  =  source of training videos
The hidden quantity

Video correctness: does this video match the task?

measured quantity  =  task-video alignment

Every generated video must be checked: does it actually show the command being executed? A pour video could show a pour that misses the target, or a hand that phases through a cup. The paper does not explicitly name this quantity, but it is the gating decision—which videos make it through to training and which get discarded.

The paper measures this with a vision-language model (VLM), a model trained to understand both images and language. You give it a frame from the video and ask: 'Does this match the command?' If the model is confident the video executes the command correctly, it passes; otherwise it is rejected. This is a binary gate, not a score, but the underlying measurement is how well the video aligns with the language goal.

Why it works

Why filtering and 3D tracking solve the problem

The core insight is two-fold. First, a VLM has been trained on billions of image-text pairs, so it has learned to recognize whether a visual action matches a language description. This works for any task description without needing robot-specific training, because the VLM already understands the pattern 'does this image show this action.' Second, by extracting 3D object position from depth maps, the method gets a sparse, task-agnostic representation: not 'which pixels moved' but 'where did the object go in space.' This does not depend on the visual style or lighting of the generated video, so the same tracking algorithm works whether the video is a diffusion output or a real recording.

Why does this avoid bad videos? Because the VLM has already seen real videos and real objects. When it watches a generated video where a hand phases through a cup or a pour overshoots, it can compare against its memory of what real pours look like and reject it. Why does sparse 3D tracking work? Because the robot does not need to copy every pixel; it only needs to know the object trajectory. If the robot's arm looks different from the hand in the video, the retargeting step (using inverse kinematics and calibration) adjusts the trajectory to the robot's body. This embodiment-agnostic approach works because the instruction is abstracted to 3D space, which both the generated video and the robot can understand.

The depth-to-pose pipeline

First in words:

For each video frame i, extract depth map D_i. Track the object in 2D across frames to get pixel trajectory p_i. Lift to 3D using calibration: x_i = Projection_inverse(p_i, D_i). Convert 3D point sequence to object pose sequence (position and rotation).

Then the compact form:

x_i = K_inverse * [p_i * D_i(p_i), 1]

Every symbol:

x_ithe 3D position of the object in frame i
p_ithe 2D pixel location of the object in frame i
D_ithe depth map for frame i (distance from camera to each pixel)
Kthe camera intrinsics matrix (focal length, principal point)
K_inversethe inverse of the camera matrix, used to convert pixels to 3D rays
A tiny worked example
Frame 1: object is at pixel (320, 240), depth map says 0.5 meters away. Using camera matrix: 3D point = (0.1, 0.08, 0.5) in meters.
Frame 2: object is at pixel (330, 250), depth map says 0.6 meters away. 3D point = (0.15, 0.12, 0.6).
Frame 3: object is at pixel (340, 260), depth map says 0.55 meters away. 3D point = (0.20, 0.15, 0.55).
The robot sees a smooth trajectory: (0.1, 0.08, 0.5) -> (0.15, 0.12, 0.6) -> (0.20, 0.15, 0.55). It can imitate this path regardless of how different its arm looks.

The depth map is the bridge: it converts a 2D pixel motion into a real 3D position, so the robot can retarget the motion to its own body.

What can go wrong

What can go wrong

The VLM rejects good videos. If the VLM has not seen a particular type of object or task, it might filter out correct videos. This would throw away valid training data and hurt performance.
The generated video is visually correct but physically impossible. A diffusion model might produce a video where the physics looks right (a smooth hand motion) but the hand actually passes through a rigid object. The VLM, trained on real videos, catches this because real hands never do that.
Depth estimation fails on reflective or transparent objects. Pouring into a glass, for instance: the depth sensor struggles to measure distance through glass. If the depth map is wrong, the 3D trajectory is wrong, and the robot learns a broken motion.
The robot's body limits prevent following the trajectory. A generated video might show a motion that reaches beyond where the robot's arm can go. Retargeting can adjust but not magically extend the robot's reach.
Done right: mix generation quality, filtering, and depth accuracy. The method works best when the diffusion model is strong, the VLM is trained broadly, and the camera is calibrated and can see the object. Under these conditions, filtered videos rival real ones.
What a runnable demo should prove

What a runnable demo should prove

Build a simulation where you generate a video of a pouring task, filter it with a pretrained VLM, extract depth and track the object, and retarget the trajectory to a robot with different arm proportions. Show three metrics: (1) Does the generated video pass the filter? (2) Does the extracted 3D trajectory match the true object motion in the video? (3) Can the retargeted trajectory successfully pour water into a cup in the simulator?

success = (filtered_video_count / total_videos) * trajectory_accuracy * task_completion_rate

The central finding: a video that an AI generates can teach a robot the same thing a human video does, as long as you automatically filter out the broken ones and extract the motion in 3D.
