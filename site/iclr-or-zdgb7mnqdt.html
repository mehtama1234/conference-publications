GraphPlanner: Graph-Based Agentic Routing for LLMs

Choose not just which model to call, but also which agent role should act next, using a routing policy trained over a history graph of past queries, roles, and responses.

Paper explainersAll themesAgents & Tool Use

Routing systems often choose one language model for a query and stop there. Agentic systems are harder: they may need a planner, an executor, a summarizer, several rounds, and memory of what worked before. GraphPlanner treats this as a sequential decision problem. At each step it picks both the model and the agent role, using a graph of past interactions to guide the workflow.

Zero assumption version

Why one-shot routing is too weak

A router for language models usually answers one question: which model should handle this input? That is enough for single-turn tasks, but not for multi-step agent work. A hard task may need planning first, then execution, then summarization, possibly with a different model at each step.

If routing ignores role choice and interaction history, it wastes resources. The system might call a large model where a small summarizer would do, or send an executor into a task that first needed planning. Better routing must choose a whole workflow, not only one model, because the value of one step depends on what comes before and after it.

In one sentence. GraphPlanner learns to build a multi-step workflow by choosing both the next model and the next agent role using a graph that stores what worked on related tasks before.

What the paper changes

What the paper changes

The paper changes the routing target. It no longer routes only to a single model. It routes over workflow steps, where each step chooses both a model and an agent role.

the object it moves  =  the workflow decision at each agent step
The hidden quantity

The hidden quantity: future value of the next workflow step

measured quantity  =  how much the next role-model choice will help the whole task

The key decision is not whether one step looks cheap or strong in isolation. It is whether that step improves the rest of the workflow. Sending a planner first may raise the value of all later steps because it organizes the task. Sending a summarizer too early may lower value because important evidence has not been gathered yet.

GraphPlanner estimates this future value from a state that includes the current query, the role history, and related past interactions stored in a heterogeneous graph. That state matters because routing in an agent system depends on context: the same model can be a good next move for one role and a poor next move for another.

Why it works

Why graph-informed routing helps

The graph helps because past queries, roles, and responses are not independent facts. They form reusable patterns. A planning-heavy route may work well for tasks that require decomposition, while a direct executor route may work for short factual jobs. The graph stores these relationships so the router can condition on more than the current prompt.

The reinforcement learning part matters because the best workflow is sequential. A good early choice is one that improves the options later, not merely the current step, because planning or evidence gathering can change what later roles are able to do well. Training the policy over full workflows lets the router learn that trade-off. That is how it can raise accuracy while lowering compute: it learns when a small model or a short route is enough and when a richer sequence will pay back its cost.

Math after the picture

Routing as step-by-step decision making

First in words:

choose the next workflow action that maximizes expected final task reward minus compute cost

Then the compact form:

Value(state, action) = ExpectedTaskReward - beta * ComputeCost

Every symbol:

statecurrent query, history, and graph context
actionone choice of next model and next agent role
ExpectedTaskRewardpredicted value of the full workflow after taking that action
betaweight on compute spending
ComputeCostcost of running the chosen model-role step
A tiny worked example
Action A sends a planner on a medium-cost model. It is expected to raise final task reward to 0.86 and costs 0.10 units, so value is 0.86 - beta x 0.10.
Action B sends an executor on a low-cost model. It is expected to raise final task reward to 0.70 and costs 0.02 units, so value is 0.70 - beta x 0.02.
With beta = 1, Action A has value 0.76 and Action B has value 0.68.
The router takes Action A because the extra planning gain is large enough to justify the added cost.

This captures the paper's main trade-off: route quality must be judged together with cost, step by step.

What can go wrong

What can go wrong

History can bias routing toward stale habits. If the graph stores many old tasks that differ from the current workload, the router may copy outdated workflows and miss a better path for the new setting because the retrieved history pushes the policy toward patterns that no longer match the task.
Role choice can be right while model choice is wrong. The system may correctly decide to plan first but still pick a model that is too weak for the planning step, so the whole workflow begins from a poor plan.
Cheap routes can be over-favored. If the cost penalty is set too high, the policy may avoid the richer workflow even when a harder task truly needs it.
Done right. Routing works best when the graph encodes task similarity and role history well, because that gives each next-step choice a concrete reason tied to past outcomes.
What a runnable demo should prove

What a runnable demo should prove

Build a small agent system with three roles: planner, executor, and summarizer. Provide at least two language models with different cost and quality profiles. Let a baseline always use one fixed workflow. Let GraphPlanner choose the workflow step by step using stored results from earlier tasks.

Run both systems on a mixed benchmark of short factual tasks, long reasoning tasks, and tasks that require multiple rounds.

route_value = task_success_rate - normalized_compute_cost

The demo should show that graph-based routing lifts task success because it chooses the next role and model in a way that fits the full workflow, so hard tasks get richer routes while easy tasks avoid wasted compute.
