Learning To Draft: Adaptive Speculative Decoding

Instead of guessing the same number of tokens every time, learn to guess more when the context is easy and fewer when it is hard, so the slow verification step wastes less time on mistakes.

Paper explainersAll themesEfficiency & Systems

When a large language model generates text word by word, it is slow. A smarter approach: send a smaller, faster model to guess what comes next (draft phase), then send those guesses to the large model to check which ones are right (verify phase), because the big model can check many guesses in one forward pass, which is faster than checking them one at a time. The problem is deciding how many guesses to send. Current methods use a fixed number all the time, or they optimize the wrong thing (acceptance length, not actual speed). This paper learns to adjust on the fly.

Zero assumption version

Why static guessing wastes time

Speculative decoding (where a small model guesses and a big model verifies) should be fast. But it has a hidden trade-off: if you guess too few words, verification sits idle; if you guess too many and they are wrong, verification wastes cycles checking junk. A word (also called a token, which is a small chunk of text) is what a language model generates one at a time.

Current methods pick a fixed number of guesses at the start and never change. Some recent methods adapt (change the number per context), but they optimize the wrong target: they count how many guesses got accepted, not how many words the whole cycle produced per second. That is like tuning a factory by counting scraps instead of watching the final product.

The problem. Fixed or wrongly-tuned guessing wasted throughput because the algorithm did not know the real cost of mistakes.

The algorithm as a flow

What it actually does

Step 1: Draft model sees input

A small model reads the prompt and outputs scores for how likely each word is.

Step 2: Size policy decides how many to draft

A trained neural network (the size policy) looks at the context and picks how many of the top-scoring words to draft.

Step 3: Depth policy decides tree depth

A second trained network (the depth policy) looks at the context and picks how deep to check (how many levels of candidate trees).

Step 4: Verify all candidates at once

The big model uses tree attention (a parallel trick) to check all drafted words in one forward pass, finding which ones are right.

Step 5: Reward signal measures throughput

The system measures words generated per second and feeds that reward back to both policies, so they learn what works for this specific context.

What the paper changes

What the paper changes

The paper changes two decisions: how many words to draft (the tree width) and how deep to verify them (the tree height). Instead of picking these once, the paper trains two neural networks (policies) that make these choices fresh each time, watching the actual context.

the object it moves  =  draft tree size and depth
The hidden quantity

Throughput reward: words per second

measured quantity  =  throughput R (words generated per cycle time)

The hidden quantity is simple: how many words (language-model output) did the system produce per unit of real time? Every cycle (draft + verify), measure wall-clock time and count accepted words; divide one by the other to get words per second. The paper optimizes this directly as a reward signal.

The big insight: previous methods optimized a proxy (acceptance length, which is how many guesses were right), which is correlated with throughput but not the same. Having more correct guesses is often good, but if checking them took longer, it was not worth it. LTD measures the real cost: time.

Simple reading. Every draft-and-verify cycle, count how many words got generated and how many seconds it took. That is the throughput reward.
Technical reading. Reward signal R equals the number of words accepted divided by the sum of time spent drafting plus time spent verifying. The system uses PPO, a method that nudges the policy networks to maximize cumulative reward.
Why it works

Why learning two coordinated policies fixes the problem

Before: the system made the same decision every time, or it optimized the wrong metric. Now: two neural networks watch the context and decide independently, but they are trained together with a shared goal (maximize words per second), so they learn to work in tandem, because updating both at the same time using the same throughput reward teaches them that when one wastes the other's time, both suffer.

The size policy learns: in contexts where the draft model is confident, guess more words, because the big model will verify them quickly and accept most of them, yielding high throughput. In contexts where the draft model is uncertain, guess fewer words, because most will be wrong and take verification time without producing output. The depth policy learns similar logic: deeper trees pay off when drafts are accurate, but cost too much when they are not. Training them together means the size policy learns to respect the depth policy's constraints, and vice versa. Both optimize the true cost: time.

The throughput reward and learning update

First in words:

Maximize the expected reward (throughput) by training two policies: size policy and depth policy, using PPO (which is a standard reinforcement learning technique) with a reward signal that directly measures words per cycle divided by time spent.

Then the compact form:

R_t = accepted_words_t / (t_draft + t_verify); policy_loss = -log(pi_action) * (R_t - V_state)

Every symbol:

R_twords accepted per second in cycle t (the reward signal we maximize)
accepted_words_thow many of the drafted words the big model agreed with
t_draftwall-clock time for the small model to generate W words
t_verifywall-clock time for the big model to check the tree
pi_actionthe probability the policy assigned to the actual decision made (tree width or depth)
V_statebaseline estimate of expected reward from this state, used to reduce noise
A concrete example
Scenario 1 (easy context): Draft model is very confident. Policies choose 60 words to draft and depth level 12. Small model generates 60 words in 10ms. Big model verifies all in 30ms. Total cycle: 40ms. Words accepted (correct): 58. Reward = 58 words / 40ms = 1.45 words per millisecond.
Scenario 2 (hard context): Draft model is uncertain. Policies choose 20 words to draft and depth level 6. Small model generates 20 words in 3ms. Big model verifies in 15ms. Total cycle: 18ms. Words accepted: 15. Reward = 15 words / 18ms = 0.83 words per millisecond.
Notice: Scenario 1 yields higher throughput (1.45 vs 0.83), and the policies learn that in easy contexts, larger trees are worth it, because you get more correct output in the same time. In hard contexts, smaller trees are better, because you avoid wasting verification time on mistakes.

The formula shows that reward rises with more words accepted and falls with more time spent, so the policies learn that speed is the true measure of success.

What can go wrong

What can go wrong

Policies trained on code, deployed on poetry. The size and depth policies are trained on the HumanEval dataset (code snippets). If you deploy them on a very different task (poetry, medical text, languages not in the training set), they may make poor choices, because the patterns in code do not match patterns in poetry. The policies were not trained to recognize those contexts.
Training cost is hidden. The paper does not fully discuss the cost to train two RL policies for each new draft-verify pair you might want to deploy. For many applications, the training cost might offset the speedup you gain when answering new questions, because you are paying for the training runs upfront.
Temperature sensitivity. At inference time, if you turn up the temperature (to make outputs more random and exploratory), the draft model becomes less confident and its probability scores are more spread out. Policies trained on confident, determinstic (greedy) sampling may choose tree sizes that do not work well for random, exploratory sampling, because the draft model behaves very differently.
Done right. The method works when the draft model's confidence scores match reality, the verification step can run in parallel (tree attention), and you can afford to train the policies once and reuse them across many inference calls.
What a runnable demo should prove

What a runnable demo should prove

Set up a small language model (e.g., LLaMA 7B) as the draft model and a larger one (e.g., LLaMA 13B or 70B) as the verifier. Implement speculative decoding with fixed tree width and depth. Measure words generated per second on a benchmark (e.g., GSM8K arithmetic questions or Wikipedia summarization). Then train two small neural networks (the size and depth policies) using PPO (a standard RL algorithm), feeding in context information and draft-model word scores, and rewarding throughput (words per second). Run inference again and measure the speedup. Plot throughput for fixed sizes (20, 40, or 60 words) and for the RL-trained policies on the same task.

throughput = words_generated / total_inference_time; speedup = throughput_adaptive / throughput_fixed

The demo makes it impossible to miss: the RL-trained policies pick the right tree size for each context, raising throughput in almost every case, because they see the real cost (time) and adapt accordingly. On hard contexts, smaller adaptive trees produce high throughput. On easy contexts, larger adaptive trees do too.
