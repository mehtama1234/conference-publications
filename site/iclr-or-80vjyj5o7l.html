DexNDM: Bridging the Sim-to-Real Gap for Hand Rotation

A robotic hand learns to rotate any object by training a tiny model for each finger joint that predicts how that joint alone will move, letting simulation policies work on real hands.

Paper explainersAll themesRobotics & Control

A robot hand trained to rotate objects in a video game often fails on a real hand, because the game simplified how fingers touch things. DexNDM builds a small predictor for each finger joint that corrects the game's predictions using just a few real-world finger movements, so the same learned policy works on diverse real objects.

Zero assumption version

Why robots fail to rotate real objects

A robot hand trained in simulation to rotate an object learns a strategy: 'when the object tilts this way, move fingers in that pattern.' But a real hand touches things differently than the game predicts. The fingers slip, the object shifts slightly, and the contact forces are unpredictable. What works perfectly in video games fails on real hardware.

A beginner might try to make the simulation more realistic by adding more friction models and contact rules to the game. But that makes the game so complex and computationally slow that training takes forever. And even then, no video-game model perfectly matches the real world, so the trained policy still fails.

The core problem in one sentence. Simulation predicts finger movement inaccurately, so policies trained in simulation do not work when applied to real hands.

The algorithm as a flow

What it actually does

Collect real data

Robot arm moves fingers automatically, recording how each joint truly moves.

Build joint predictors

For each finger joint, train a small model: 'When simulation says move X, real finger actually moves Y.'

Learn the pattern

Model learns each joint's unique behavior — friction, slip, contact stiffness — from its own data alone.

Correct at runtime

When rotating an object, each joint predictor adjusts the simulation's command before sending to the real joint.

Generalize to new objects

Same predictors work on different objects, wrist angles, sizes because each joint's model is independent and captures general slip patterns.

What the paper changes

What the paper changes

Instead of fixing the simulation's physics model, DexNDM adds a thin corrector layer: for each finger joint, a tiny neural network that maps 'what simulation predicted' to 'what the real joint will actually do.' This is independent per joint, so a joint learns only from its own motion history, not the whole hand at once.

the object it moves  =  Simulation predictions (one per joint)
The hidden quantity

The joint-wise correction signal

measured quantity  =  Per-joint prediction error

The hidden quantity is how much each finger joint's actual motion differs from what the simulator predicted. For example, if simulation says 'joint 1 will move 45 degrees' but it actually moves 38 degrees, the error is 7 degrees. The paper's model learns these error patterns for each joint separately.

DexNDM measures this by recording real finger movements with minimal data (from autonomous collection) and comparing them to simulation's predictions. Each joint predictor is trained to minimize the gap between what it guesses and what really happens, learning the unique slip, friction, and contact effects of that single joint.

Why it works

Why learning one joint at a time fixes the reality gap

Simulation assumes physics rules like friction and contact that do not exist in reality. When a finger touches a hard object, the contact force can be much larger than the game predicted, causing the joint to move less. When sliding, friction creates unexpected damping. A single neural network trying to predict the whole hand's motion at once would need to model all these effects together, requiring huge amounts of real data and a large model.

DexNDM splits the problem: each joint learns only its own error pattern. This is simpler because each joint sees only its own motion history, not the global hand state. A joint learns that 'when I am supposed to move this much and I am touching something, I slip by this percentage' — a simple local rule. Since each rule is small and local, it only needs a few real finger movements (efficient data use), and the learned patterns transfer across objects because slip and friction are properties of the joint itself, not the specific object.

In operation, the simulation sends each joint its predicted command, the corrector predicts how much that joint will really move, and the policy uses the corrected output to decide the next move. This closes the loop between sim and real: the policy still works, but now it is reading from reality instead of wishful thinking.

Math after the picture

The joint predictor as a simple equation

First in words:

real_output = small_neural_net(simulation_prediction + previous_joint_state + object_contact_info)

Then the compact form:

y_real_i = f_i(y_sim_i, s_i)

Every symbol:

y_real_iactual angle the joint moved to (measured)
y_sim_iangle the simulator predicted the joint would move to
s_iadditional state of joint i: its current angle and velocity
f_ismall neural network learned for joint i alone
A tiny worked example
Real scenario: simulator predicts joint 1 should move to 45 degrees, joint is currently at 20 degrees.
Joint 1 corrector inputs: (45, 20) — the predicted angle and current state.
Corrector outputs: 38 degrees (learned that friction reduces movement by 7 degrees in this range).
Policy uses 38, not 45, so it is not surprised when the object does not rotate as much.
Another scenario: same joint at 60 degrees, simulator predicts 75 degrees.
Corrector outputs: 71 degrees (learned slip is smaller at high angles).
Each joint has its own f_i, so a pinky corrector learns different slip than a thumb corrector.

Each joint's small network learns the relationship between what the simulator thinks will happen and what really happens, captured as a simple input-output mapping.

What can go wrong

What can go wrong

Changing hands entirely. Each hand has different finger shapes and sizes, different friction on its palm. If you train the correctors on Hand A and test on Hand B, the learned slip patterns will not match. The correctors must be retrained for a new hand.
Objects that change during rotation. If the object is deformable or breaks during rotation, the contact forces change unexpectedly. The correctors learned from rigid objects will mispredicts, because they learned 'this contact force means this slip', but the deformable object has different forces.
Insufficient real-world data. If the autonomous data collection does not cover enough different finger positions or contact scenarios, the correctors learn incomplete patterns and miss edge cases where they would be most useful.
Done right: diverse autonomous data. Collect real data across a range of joint angles, contact forces, and motion speeds. Each corrector then learns the full friction surface for its joint, not just the narrow slice it happened to see.
What a runnable demo should prove

What a runnable demo should prove

Start with a simulation-trained policy that fails on real objects (e.g., a cube rolls off the hand or does not rotate). Collect 20-50 real finger movements via teleoperation or autonomous exploration. Train one small neural network per joint (3 lines of PyTorch per joint). Run the same policy again using corrected predictions. Measure success: does the real hand now rotate the cube, a small toy, and a complex-shaped object without retraining the policy itself?

success_rate = (objects_rotated_without_policy_retraining) / (total_test_objects)

The demo must show that one hand policy, combined with per-joint correctors trained on minimal real data, rotates objects it has never seen before.
