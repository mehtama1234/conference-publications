Relational Graph Transformer

A transformer-based architecture that tokenizes relational database tables as heterogeneous temporal graphs, capturing long-range patterns that message-passing networks cannot see.

Paper explainersAll themesGraph & Geometric Learning

Databases organize data in multiple related tables (customers, purchases, products). Graph neural networks struggle with this setup: they treat it like a network of connections, but miss patterns that skip over intermediate nodes. This paper introduces a transformer (a model that attends freely to every input at once) designed specifically for database tables, using a five-part representation to convert each database row into a labeled package that preserves what table it comes from, when it was created, and how it connects to its neighbors.

The database-as-graph bottleneck

When you turn a database into a graph — customers as nodes, purchases as edges connecting them to products — a standard graph neural network works by having each node swap messages with its immediate neighbors, then neighbors-of-neighbors. The problem: some patterns live far apart. A product purchased by customer A, who is similar to customer B, reveals something about what B should buy — but customer B never directly talks to that product. The message would have to bounce through intermediaries (product through first customer through second customer through more customers). By then, it gets scrambled by each hop.

The naive approach is to make the network deeper to reach farther. This fails because deep message-passing networks get tangled with their own signals (each new layer blurs what came from where), and they still cannot freely see across the table the way a database query does. You are stuck: capture local patterns in 2-3 hops, or risk noise.

The paper's core move. Instead of messages bouncing through the graph, turn the database into a list of tokens (one token per row, broken into five parts: the row's data, which table it came from, how far it is from the query row, when it was created, and a quick look at its neighbors), then use a transformer—a model that attends freely to every token at once.

The algorithm as a flow

What it actually does

Sample neighbors

For each row, grab its closest K neighbors within 2 hops, respecting timestamps to avoid cheating.

Five-part tokenization

Turn each neighbor row into five tokens: encoded data values, which table it belongs to, hop distance, time delta, a random graph structure sample.

Local focus

Let the query row focus on its own neighbors; this builds a fine-grained local picture.

Global summaries

Pool all query rows across the database into summary centroids; every row can also focus on these global summaries.

Predict

Use the combined local and global representations to make the prediction.

What the paper changes

What the paper changes

The paper changes how each node in a relational graph is represented. Instead of a single vector of learned features, each node becomes a five-element tuple: its row data, its table identity, its distance in hops, its timestamp, and a random sample of its local graph structure. This tuple is then encoded into five separate numerical representations and combined into a single token.

The hidden quantity

The hidden quantity: Structural accessibility

measured quantity  =  structural accessibility

Structural accessibility is how easy it is for a far-away pattern to influence a prediction. In a message-passing network, a product five hops away from your query row can only send a signal if it survives five noisy bounces. In a transformer, every token is immediately accessible. The paper does not measure this as a single number (like signal-to-noise ratio), but it is the reason the method works: it measures and uses access directly.

RelGT estimates accessibility by the distance (hop count) and timestamp information baked into each token, then lets the transformer learn which distances and times matter. A weight in the transformer can learn to ignore products from two years ago (stale signal) and focus on fresh purchases from 1-2 hops away (relevant neighbors).

Message-passing gets noisier the farther you go, because each hop mixes the signal with the current state at each node; stacking bundles avoids this because every piece of information is separate and labeled.
Why it works

Why it works: Direct access + context tags

The transformer can attend to any token, but it needs to know which tokens matter. The five-part tokenization gives every token a context tag: its table (product vs. customer), distance from the query (1 hop vs. 3 hops), and age (yesterday vs. 1 year ago). The transformer then learns: 'attention to product tokens 1-2 hops old predicts well; skip tokens older than 1 year.'

In contrast, a message-passing network has to compress all that information into a single updated vector as the message bounces through neighbors. By the time a product five hops away sends its signal, the signal has been mixed with the intermediate customers' current state, noise creeps in, and the transformer at the top sees a blurry average. RelGT avoids this: every product and customer is a separate token, each labeled with its own metadata, and the transformer picks out the clean ones.

Math after the picture

The core equation

First in words:

token equals concatenate of five encodings of node data, node type, hop distance, time difference, and a random sampled subgraph structure

Then the compact form:

t_j = concat(encode_feat(x_j), encode_type(phi_j), encode_hop(p_j), encode_time(tau_j - tau_i), encode_structure(Z_j))

Every symbol:

t_jthe token for node j
x_jthe row's data (numerical and categorical features)
phi_jwhich table this node comes from (node type)
p_jhop distance from query node i to neighbor j
tau_j - tau_itime difference between node j and query node i
Z_ja random sample of j's local graph structure
concatstack the five encodings end-to-end into one long vector
A concrete example
Suppose we are predicting for customer Alice (node i, time=2025-01-01).
Neighbor product X (node j) has: data=[price=100, rating=4.2], type=product, hops=1, time=2024-12-15.
encode_feat([100,4.2]) = [0.8, 0.6] (a 2-dim list of numbers; real model uses d=64).
encode_type(product) = [0.1, 0.2, 0.0, ...] (a learned representation of 'product', distinct from 'customer').
encode_hop(1) = [0.9, 0.1, ...] (distance 1 is close).
encode_time(17 days) = [0.7, 0.3, ...] (recent, relevant).
encode_structure(Z_j) = [0.5, 0.5, ...] (X's neighbors sampled and encoded).
Concatenate all five: t_j = [0.8, 0.6, 0.1, 0.2, 0.0, ..., 0.9, 0.1, ..., 0.7, 0.3, ..., 0.5, 0.5, ...] (a 320-dim vector, 5 parts × 64-dim each).
The transformer can now see: 'this is a product, close by, recent, with these properties' and decide to attend to it.

The five encodings preserve different dimensions of a database row: what it contains, which table, how far, how old, and its graph shape. The transformer learns which combinations predict well.

What can go wrong

What can go wrong

Timestamp leakage If you accidentally include future rows (timestamps after the query date), the model learns to cheat. The paper guards this by filtering neighbors to only include those created before or at the same time as the query row, but a buggy implementation can break this safeguard.
Fixed neighborhood size limitation The method samples a fixed K neighbors. If a row has fewer than K neighbors, it fills with random nodes. If many rows are isolated (no neighbors in 2 hops), the model wastes tokens on noise.
Scalability to massive graphs Local attention over K tokens is cheap, but global attention pools over ALL rows. On a database with billions of rows, creating a centroid for every subset becomes slow. The paper tests on medium-scale RelBench; real financial databases may hit limits.
Done right Enforce strict temporal ordering when constructing neighborhoods. Tune K (neighborhood size) and global centroid count to your data size. Validate that improvements persist on out-of-distribution future data (time shift test).
What a runnable demo should prove

What a runnable demo should prove

Build a small two-table database: customers (with age, location, past purchases) and products (with price, category, rating). Create a prediction task: given a customer, predict their next purchase category. Train a message-passing GNN baseline (e.g., PyTorch Geometric's GraphSAGE on a relational graph) and a Relational Graph Transformer side by side. Measure accuracy on the held-out test set. Also measure how well each model predicts for customers whose favorite product is 3+ hops away in the graph (i.e., only reachable through multiple intermediate nodes). The transformer should win the far-field test; the GNN should lose accuracy when the pattern lives far away.

far_field_gain = transformer_accuracy_on_3plus_hops - gnn_accuracy_on_3plus_hops

The transformer's token and metadata design makes it immune to long-distance decay because every token stays clear and labeled, rather than getting mixed with intermediate states as messages bounce through the graph. This demo makes that visible: one model sees the far-away patterns, the other does not.
