iLLaVA: Merging Image Tokens to Speed Up Vision-Language Models

iLLaVA speeds up vision-language models by merging redundant image tokens in both the encoder and the language model, recycling information from discarded tokens so nothing useful is lost.

Paper explainersAll themesEfficiency & Systems

A vision-language model reads an image in two stages: first an image encoder (a specialized model that processes the image) converts the image into a sequence of tokens (compressed pieces of information), then a language model reads those tokens to answer questions. Most prior methods only trim tokens in the second stage. iLLaVA goes further: it trims redundant tokens in both stages, and when it discards a token, it carefully preserves useful information by merging it into a nearby token that gets kept. Because the encoder produces most tokens and the language model's computation scales with token count, trimming both stages cuts overall time while merging keeps accuracy intact.

Zero assumption version

Why vision-language models are slow

A vision-language model processes an image by first breaking it into a grid of patches (small square regions), then converting each patch into a token (a compressed vector, a list of numbers). A typical image might become 500 to 1000 tokens. The language model then reads all those tokens alongside text instructions to answer questions. In the language model, each token compares itself to every other token to decide what to pay attention to (attention means focusing: each word looks at all other words to decide which ones are relevant). When you have N tokens, that is N times N comparisons, so doubling the tokens quadruples the work.

Existing acceleration methods only prune tokens inside the language model stage. But they miss the bigger bottleneck: the image encoder itself (the first stage) produces the majority of those tokens, and computing the encoder is expensive on its own. Trimming tokens only at the end does not reduce the work of the encoder or the load it places on the language model.

The core problem. Image encoders create most tokens, and the language model consumes them with quadratic cost. Existing methods prune only the output; iLLaVA prunes both the encoder and the language model, and recycles discarded information so accuracy does not drop.

The algorithm as a flow

What it actually does

Step 1: Identify noise using attention

In each encoder block, the attention module naturally shows which parts of the image matter (birds matter, background does not). Use those scores to pick the top 40 percent of tokens as keepers.

Step 2: Group discarded tokens with their nearest keeper

For each token marked for deletion, find the 5 nearest keepers based on similarity. This token becomes part of their group.

Step 3: Merge by weighted average

For each group, blend all the tokens together using a weighted sum (each token weighted by how similar it is to the keeper). The keeper now carries the merged knowledge.

Step 4: Repeat in both encoder and language model

Apply this strategy at multiple layers inside the image encoder to progressively reduce tokens as they flow forward. Do the same selectively in the language model.

Step 5: Faster answers with no loss

The language model receives half as many tokens, which means one quarter the attention comparisons (since comparisons scale as N times N). Merged tokens carry information from their deleted neighbors because each discarded token's value is blended into the keeper, so the model still sees all important visual details even though some tokens are gone.

What the paper changes

The thing that changes

iLLaVA operates on the token sequence: it deletes some tokens and merges their information into others. Unlike prior methods that only act on the language model's input, iLLaVA applies token merging inside the image encoder as well, where most tokens originate. Cutting tokens in the encoder saves time in two ways: the encoder itself has less work to do because each forward pass through the layers processes fewer tokens, and the language model receives fewer inputs so its attention cost drops (since attention scales as N times N, halving tokens cuts cost to one quarter).

the object it moves  =  image and language tokens
The hidden quantity

The hidden quantity: attention-based importance

measured quantity  =  Attention-score-based token importance

The paper measures which tokens matter using attention scores. Attention is the mechanism by which transformers focus: at each token position, the model computes a score for every other token (how much it should pay attention to it). Tokens that are heavily attended to (high scores) carry important information; tokens that are rarely attended (low scores) are noise.

iLLaVA applies this idea: it collects the average attention score each token receives across all attention heads in an encoder block, then ranks tokens by that score. High-scoring tokens are kept; low-scoring tokens are discarded (but their information is merged into neighbors before discarding). This is a training-free method: the scores are computed from the existing attention weights without any retraining.

Why it works

Why merging redundancy works

The mechanism has two parts: why it is safe to delete low-importance tokens, and how merging preserves information. First, the image encoder is designed to extract visual features progressively. Most of the image (sky, grass, uniform texture) gets the same encoded meaning; only a few regions (the bird, distinctive objects) require separate tokens. Attention scores naturally reflect this: background tokens score low because they carry no new information. Deleting them removes noise, not signal.

Second, when you delete a token, you lose all its numerical content. iLLaVA instead merges it: the discarded token gets averaged into its 5 nearest neighbors (selected by how similar their encoded vectors are). This blending preserves the signal in the deleted token because it is likely expressing a subtle variation of the same concept as its neighbors. Mathematically, each token contributes to the merge weighted by its similarity score, so tokens more closely related to the keeper contribute more. The keeper becomes a slightly richer representation of its local neighborhood.

The merging equation

First in words:

For each token to be deleted, compute the weighted sum of that token and its neighbors by averaging them according to their similarity to each neighbor.

Then the compact form:

merged_token = sum_j (sim_j / sum_k sim_k) * token_j

Every symbol:

merged_tokenthe new combined value assigned to the keeper token
sim_jsimilarity score between the deleted token and neighbor token j (based on dot product of their vector representations)
token_jthe encoded vector of neighbor j
sum_k sim_ktotal similarity, used to normalize weights to sum to 1
A tiny worked example
Suppose a background token will be deleted. Its vector is [0.2, 0.5, 0.3] and three keepers nearby are: K1=[0.2, 0.4, 0.3], K2=[0.15, 0.6, 0.2], K3=[0.1, 0.3, 0.5].
Compute similarity (dot product): sim_K1 = 0.2*0.2 + 0.5*0.4 + 0.3*0.3 = 0.04 + 0.2 + 0.09 = 0.33. sim_K2 = 0.03 + 0.3 + 0.06 = 0.39. sim_K3 = 0.02 + 0.15 + 0.15 = 0.32.
Total similarity: 0.33 + 0.39 + 0.32 = 1.04.
Weights: 0.33/1.04 = 0.32, 0.39/1.04 = 0.38, 0.32/1.04 = 0.31.
Merged value assigned to K1: 0.32*K1 + 0.38*K2 + 0.31*K3 = 0.32*[0.2,0.4,0.3] + 0.38*[0.15,0.6,0.2] + 0.31*[0.1,0.3,0.5] ≈ [0.17, 0.43, 0.31].
K1 becomes [0.17, 0.43, 0.31], richer with information from its neighbors.

The merging sums are weighted by similarity because more similar tokens carry more relevant information to preserve in the keeper.

What can go wrong

What can go wrong

Aggressive pruning loses fine details. If you delete too many tokens (e.g., 70 percent instead of 60 percent), even careful merging cannot preserve all visual detail, because each merger blends information from multiple tokens and you lose resolution with each blend. The merged tokens become too coarse and the model answers questions poorly. The paper tested different deletion rates and found 40 percent keepers works best.
Attention scores can be misleading early in the model. In the first few layers of the encoder, attention patterns are still noisy (the model has not yet learned what to focus on). Relying on these scores to select tokens can remove truly useful information. iLLaVA applies merging only in middle and later layers to avoid this.
Merging with incorrect neighbors degrades accuracy. If a doomed token is merged into an unrelated keeper (bad similarity match), its information is mixed with the wrong context, creating corrupted vectors. The paper uses similarity thresholds to ensure only closely related tokens are grouped.
Done right, the trade-off holds. When you choose the right layers (middle and later ones, not the noisy early layers) and the right pruning ratio (40 percent keepers), merging preserves accuracy because the information in nearby tokens is redundant (early layers extract similar features), so blending them loses little. The paper demonstrates this on multiple image and video datasets, and even shows that a larger model with iLLaVA can match a smaller model that runs unmerged.
What a runnable demo should prove

What a runnable demo should prove

Build a small vision-language model that answers a question about an image. First, run it without token merging and record the time it takes and the model's answer. Then enable iLLaVA merging: in the image encoder, rank tokens by attention (which reflects what the model learned to focus on), keep the top 40 percent because they carry the information the model depends on for understanding, and for each deleted token, blend its values into its most similar keeper using a weighted sum (weighted by how similar they are, since similar tokens carry similar information). Do the same in one language model layer. Measure the new time and re-run the same question. The demo should show that time drops 30 to 50 percent while the answer remains correct because merging preserves information (the deleted token's content flows into the keeper, so nothing important is lost) and reduces computation (fewer tokens means fewer comparisons in attention, scaling from N times N down to 0.4N times 0.4N).

speedup = latency_without_merging / latency_with_merging; accuracy_change = accuracy_with_merging - accuracy_without_merging

If the speedup is real but accuracy plummets, merging is too aggressive. If latency barely changes, merging is not applied to the right layers. The demo proves that iLLaVA moves the speed-accuracy curve.
