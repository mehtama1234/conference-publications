WorldTravel: A Realistic Multimodal Travel-Planning Benchmark with Tightly Coupled Constraints

Test whether an agent can build a travel plan when each early booking choice changes what remains possible later.

Paper explainersAll themesAgents & Tool Use

Travel planning looks simple until every choice constrains the next one. A flight arrival time changes which train can be taken, that train changes which hotel check-in window still works, and those choices decide whether the whole trip is feasible. WorldTravel turns that coupled planning problem into a benchmark, then makes it harder by forcing agents to read dense travel pages instead of clean text tables.

Zero assumption version

Why ordinary planning benchmarks are too easy

Many planning benchmarks let an agent solve one decision at a time. If the flight is acceptable, book it. If the hotel looks fine, reserve it. This style is forgiving because one bad choice often does not destroy the rest of the plan.

Real travel planning is harsher because the constraints are tightly coupled. A late arrival can block the only train that reaches the meeting on time. A cheaper hotel can fail because its check-in window starts after the last bus arrives. WorldTravel is built to measure this harder setting by giving each scenario many linked time and logic constraints that must all hold together.

The paper's move in one sentence. Build a benchmark where one travel choice changes the feasibility of many later choices, then test agents both on clean text inputs and on rendered web pages.

The algorithm as a flow

What it actually does

Write realistic scenarios

Create travel tasks across several cities with flights, trains, buses, hotels, and event requirements.

Attach many linked rules

Specify time windows, ordering rules, location limits, and booking dependencies so one choice changes later feasibility.

Build two input settings

Provide one version as structured text and another through rendered web pages that hide details inside busy layouts.

Run agents end to end

Ask each model to recover the usable facts and produce a complete travel plan.

Score executable success

Mark the plan as successful only when every listed rule is satisfied together.

What the paper changes

What the paper changes

The paper changes the benchmark object itself. Instead of short planning puzzles with loosely related rules, it gives agents long chains of interdependent travel constraints and then measures whether the final itinerary is still executable.

the object it moves  =  Feasible travel itinerary under coupled constraints
The hidden quantity

The hidden quantity

measured quantity  =  Remaining feasible plan space

At every step, the agent is shrinking the set of plans that can still work. That hidden set is the real quantity that matters, because a choice is good only when enough valid future options remain after making it.

WorldTravel exposes how fast that feasible plan space collapses. Once the agent picks a flight or hotel, many later combinations disappear because they violate time windows, transfer times, or ordering rules.

Why it works

Why this benchmark is hard in the right way

The benchmark is difficult for two separate reasons. First, the agent must extract the right facts from realistic travel pages because schedules, station names, and booking rules are spread across dense interfaces. Second, the agent must reason over those facts across many future steps because one early commitment changes what remains possible later.

Those two burdens compound each other. If the agent misreads one departure time, the later plan can fail even when the reasoning process is otherwise sound. If it reads the page correctly but picks a locally convenient option, the full itinerary can still fail because later constraints have no room left. The benchmark therefore measures both information recovery and long-horizon planning in a single task.

Math after the picture

The feasibility rule

First in words:

A plan is valid only when every listed constraint is satisfied by the same itinerary.

Then the compact form:

feasible(plan) = 1 if all constraints c in C are satisfied by plan, else 0

Every symbol:

planthe full itinerary, including chosen flights, ground travel, lodging, and event timing
Cthe full set of travel constraints in one scenario
constraint cone rule such as arrive before a meeting, allow enough transfer time, or check in before the hotel closes
feasible(plan)the final benchmark judgment: 1 means the trip is executable, 0 means some rule is broken
A tiny worked example
Suppose one scenario has four rules:
1. Arrive in the city before 18:00.
2. Leave at least 25 minutes between flight arrival and train departure.
3. Reach the hotel before check-in closes at 22:00.
4. Reach the event venue by 09:00 the next morning.
A candidate plan arrives at 17:10, catches a train at 17:50, reaches the hotel at 21:20, and reaches the venue at 08:35.
All four rules hold, so feasible(plan) = 1.
If the flight arrived at 17:35 instead, the train transfer would be only 15 minutes, rule 2 would fail, and feasible(plan) = 0.

This strict all-rules judgment is why the benchmark exposes brittle planning behavior clearly.

What can go wrong

What can go wrong

Local choice trap. An agent can pick the cheapest or earliest option and still fail, because that choice may leave no workable continuation for the rest of the trip.
Page reading failure. A plan can collapse after one extraction mistake, because a wrong departure time or missed booking rule poisons every later feasibility check.
Horizon overload. Reasoning degrades once too many linked rules must be tracked together, because the agent starts dropping dependencies that matter only several steps later.
Done right. A strong system should keep a structured list of recovered constraints and re-check the whole itinerary after each choice so that early gains do not create hidden dead ends later.
What a runnable demo should prove

What a runnable demo should prove

Build ten small travel tasks with flights, local transport, and hotel rules. Give each task both a clean text version and a screenshot-style version. Ask one agent to solve both settings while keeping an explicit table of constraints and a final itinerary check.

The demo should prove two things. First, page reading matters because the screenshot-style setting should fail more often when the agent misses small schedule details. Second, coupled planning matters because a plan should count as successful only when every rule still holds after the final itinerary is assembled.

success_rate = solved_tasks / total_tasks ; solved_task = 1 only if every constraint is satisfied by the final itinerary

If the demo shows frequent failures after about ten linked rules, it is reproducing the paper's main finding.
