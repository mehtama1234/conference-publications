Error Notebooks for Part Retrieval in CAD

When a vision-language model struggles to find the right part in a complex assembly, show it examples of mistakes it made before and how to fix them, so it learns from its own errors without retraining.

Paper explainersAll themesAgents & Tool Use

Finding the right part in a complex 3D assembly is hard: the instructions are long, the model runs out of memory (it can only read a certain amount of text at once), and you cannot retrain a proprietary model like GPT-4. This paper fixes that by building an Error Notebook — a collection of real mistakes the model made and how to correct them — and using it to show the model similar past mistakes when it tries a new task, so it learns to avoid the same trap.

Zero assumption version

Finding parts in huge assembly drawings

In real engineering, a 3D assembly is made of thousands of parts, each with a long list of attributes: diameter, thread pitch, material, supplier code, position, tolerance. When an engineer needs to find a specific part, a language model (a system trained to understand words and pictures) should be able to read all those attributes and match them to the right part in the catalog. But three things break this: first, the attribute list is too long—it exceeds the model's token budget (the number of words and numbers it can read in one go); second, you cannot fine-tune commercial models like GPT-4, so you are stuck with whatever comes out of the box; third, even out of the box, the model makes systematic mistakes—it misreads a diameter, ignores a material requirement, or jumps to the wrong part.

A beginner would try: just feed the full part description to the model and ask it to pick. It fails because it cannot fit all the information, gets confused by similar-looking parts, or forgets the constraints halfway through.

The paper's move: Collect the mistakes the model actually makes, write down what went wrong and how to fix it, then show the model similar past mistakes when it tries a new part retrieval task.

The algorithm as a flow

What it actually does

Step 1: Collect mistakes

Run the model on 100 part descriptions and record every wrong answer.

Step 2: Correct and explain

For each wrong answer, write out why it was wrong and what the correct answer should be.

Step 3: Verify the fix

Check that each corrected answer actually follows the rules (grammar verifier).

Step 4: Retrieve similar mistakes

When solving a new task, search the notebook for examples that look like the same kind of mistake.

Step 5: Show examples and re-run

Feed the similar past mistakes to the model, then ask it to pick the right part again.

What the paper changes

What the paper changes

The paper changes what examples the model sees right before it answers. Normally it sees zero past attempts. Now it sees three or four real mistakes from the Error Notebook that look similar to the current task—mistakes that a human already corrected. That is the only change at inference time (when the model is answering).

the object it moves  =  Inference examples
The hidden quantity

The hidden quantity: relevance of past mistakes

measured quantity  =  Mistake relevance to the current task

The paper measures one key quantity: how close is a past mistake to the new task? If you show the model an example of picking the wrong diameter when the current task is also about diameter, the model learns to check diameter carefully, because it sees: 'I confused diameters before, here is how I got it wrong, here is the right answer.' Now on a similar task, it checks diameter twice. But if you show it a mistake about material when the current task is about diameter, the model is confused—it is concentrating on the wrong attribute. The more attributes that overlap between the past mistake and the current task, the more the model focuses on checking the right things.

The paper estimates this by searching for notebooks entries where the part attributes (like diameter, thread pitch, material) overlap most with the new task's attributes. It then ranks them by how many attributes they share, picking the top three or four to show the model.

Why it works

Why showing past mistakes helps the model

When a language model reads text, it processes one token (a small piece of text or number) at a time, building up a picture of what it has seen so far. By the time it finishes reading a long part description with 1000 attributes, it has had to hold in memory what all of them mean. Real assemblies have dozens of similar parts—many with the same diameter, same material, just a different supplier. The model can get confused and pick a part that matches most attributes but gets one critical detail wrong.

When you show the model a past example—'Someone asked about a diameter-16, material-aluminum part, and I picked the wrong one because I ignored the supplier code'—you are giving it a second reference point. Now the model reads both: the current task AND the past mistake. It can compare them. When it gets to the part where it might make the same error, it remembers 'I made this mistake before' and avoids it. The past example points the model to the exact place it went wrong before.

This only works if the past mistake is relevant—if it involves the same kind of confusion. A mistake about thread pitch does not help you avoid a diameter error, because the model would be reading the thread-pitch example, building up knowledge about thread pitch, and then facing a task about diameter—its focus has been steered the wrong way. So the paper ranks past mistakes by how many attributes they share with the current task, and shows only the top few. That ensures the model is seeing mistakes it could plausibly make again.

Ranking mistakes by relevance

First in words:

Relevance score equals the number of part attributes shared between a past mistake and the current task, divided by the total number of unique attributes across both.

Then the compact form:

relevance_i = |A_current AND A_i| / |A_current OR A_i|

Every symbol:

relevance_iOverlap score for past mistake i (ranges 0 to 1)
A_currentSet of part attributes in the current task
A_iSet of part attributes in past mistake i
|...|The count of items in a set
ANDShared attributes between current and past
ORAny attribute in either current or past
A tiny worked example
Current task: diameter, material, thread, tolerance (4 attributes)
Past mistake 1: diameter, thread, supplier (3 attributes)
Shared: diameter, thread (2 attributes)
Total unique: diameter, material, thread, tolerance, supplier (5 attributes)
Relevance_1 = 2 / 5 = 0.4
Past mistake 2: diameter, material, tolerance, thread (4 attributes)
Shared: diameter, material, thread, tolerance (4 attributes)
Total unique: diameter, material, thread, tolerance (4 attributes)
Relevance_2 = 4 / 4 = 1.0 (perfect match)
The model is shown mistake 2 because it overlaps completely with the current task.

What can go wrong

What can go wrong

Irrelevant past mistakes confuse the model. If the Error Notebook contains a mistake about supplier codes but the current task is about diameter, showing that past mistake actually hurts—the model sees conflicting signals. The fix is to rank mistakes strictly by attribute overlap and show only the top few.
The notebook corrects one model but fails on another. An Error Notebook built from GPT-4o corrections might not help Qwen2-VL, because GPT-4o and Qwen2-VL were trained differently and learn from examples in different ways—what helps GPT-4o spot an error might not help Qwen2-VL notice the same error. But the paper shows that a cross-model notebook—where mistakes are corrected generically (following the grammar rules, not model-specific logic)—works for both models, because the corrected reasoning is independent of which model learns from it.
The notebook becomes large and search becomes slow. If you collect thousands of mistakes, ranking all of them for every new query is expensive. The paper does not address this—it assumes a notebook of order 100–1000 entries.
Done right: show only relevant examples. When you retrieve past mistakes that truly overlap with the current task and verify that the corrections follow the grammar rules, the model learns to avoid traps without retraining.
What a runnable demo should prove

What a runnable demo should prove

Build a small CAD assembly (or simulate one): a set of 50 parts, each with 5–10 attributes (diameter, material, thread, tolerance, supplier). Manually create 20 mistakes where the model picks the wrong part. For each mistake, write a correction. Then run a new set of 10 part-finding tasks: half with the Error Notebook shown, half without. Measure the accuracy on each side.

Accuracy = (number of correct part picks) / (total new queries); Improvement = Accuracy_with_notebook - Accuracy_without_notebook

The demo makes impossible to miss: when the model is shown similar past mistakes from the Error Notebook, it avoids the same trap and picks the right part far more often, even though the model was never retrained.
