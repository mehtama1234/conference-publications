TimeRecipe: Finding the Right Parts for Time Forecasting

Instead of debating which full forecasting model is best, TimeRecipe tests every small piece to see which combinations win on which datasets.

Paper explainersAll themesTime Series & Sequential

Time-series forecasting (predicting future values of data that changes over time, like stock prices or weather) requires choosing between many model designs. But nobody really knows which pieces matter when. TimeRecipe runs over 10,000 experiments testing individual components—decomposition (breaking time series into trend and seasonal parts), normalization (scaling numbers to a standard range), and others—across dozens of datasets to reveal which combinations work best for which problems.

We Build Models Blind

When you need to predict future values of time data (temperature tomorrow, sales next quarter, power demand next hour), you face a menu of design choices: do you decompose the series first, do you normalize the inputs, how many layers deep, what kind of attention mechanism? The frustration: different researchers swear different choices work best, and there is no clear reason why.

A beginner might just try 2-3 models on their data, pick the one with the lowest error, and call it done. But this misses the real insight: under what conditions do those choices actually matter? Is decomposition always good, or only on seasonal data? Does normalization help when series are volatile (because it centers noisy fluctuations around a stable baseline), or does it hide important signals (by squashing dramatic spikes that carry real information)? Nobody had systematically tested it.

The problem in one sentence. Time-series forecasting models have many small design pieces, but we do not know which pieces matter for which kinds of data, so we are essentially guessing.

What the paper changes

What the paper changes

TimeRecipe changes the way we choose forecasting model components: instead of benchmarking full models, it isolates each small piece and tests it across many datasets. This reveals which pieces matter when, and builds a lookup table: given a dataset's shape, recommend the parts to assemble.

the object it moves  =  Component selection method
The hidden quantity

Component effectiveness: which piece matters where

measured quantity  =  Effectiveness of each component on each dataset type

Component effectiveness is simple: does adding (or removing) this piece improve accuracy, harm it, or leave it unchanged, on this particular type of data? TimeRecipe measures it by running the same model with and without that component and recording the error difference. For instance: decomposition on seasonal data (accuracy improves because the model can now model trend and seasonality separately) versus decomposition on chaotic data (accuracy stays flat because there is no seasonal pattern to decompose).

The paper estimates effectiveness by running 10,000 controlled experiments: identical model setup except for one component toggled on or off, then checking accuracy on held-out test data. The results form a table: rows are components, columns are dataset types, cells are effectiveness scores.

Plain reading. Decomposition (breaking a time series into trend, seasonal, and random parts) helps when the data has obvious seasonal patterns (because you can train separate models for each part and combine them), but hurts or wastes computation on chaotic data (because there are no real patterns to separate).
Paper reading. The module-level ablation reveals that individual components exhibit heterogeneous effects across datasets; certain components (e.g., series decomposition) correlate strongly with performance gains on datasets exhibiting clear seasonal structure, while the same components show negative or neutral correlation on inherently noisy or non-seasonal data.
Why it works

Why separating components reveals the truth

Old benchmarks test full models. If Model A beats Model B, you know A is better overall, but you do not know whether A won because of decomposition, normalization, or depth. You cannot reuse insights across different datasets because the full model is a black box—change one piece and everything might cascade differently.

TimeRecipe isolates each piece: run the exact same model architecture and training procedure, but toggle one component on or off. Now the accuracy change tells you directly: did this piece help or hurt on this data? Because everything else is held constant, you can confidently say 'decomposition works on seasonal data' without the noise from other design choices. The results stack: you discover that seasonal data needs decomposition + normalization but shallow depth, while chaotic data needs deeper models but not decomposition. Combine those insights and you get a custom model that beats any single generic design.

The effectiveness score

First in words:

effectiveness of component C on dataset D is the difference between accuracy without component and accuracy with component; positive means the component helped.

Then the compact form:

E_C,D = accuracy_with_C(D) - accuracy_without_C(D)

Every symbol:

E_C,Dthe effectiveness of component C on dataset D
accuracy_with_C(D)test accuracy when component C is enabled on dataset D
accuracy_without_C(D)test accuracy when component C is disabled on dataset D
A tiny worked example
Decomposition on seasonal dataset: accuracy_with = 0.92, accuracy_without = 0.88, effectiveness = 0.92 - 0.88 = +0.04 (component helped).
Decomposition on chaotic dataset: accuracy_with = 0.76, accuracy_without = 0.76, effectiveness = 0.76 - 0.76 = 0.00 (component made no difference).
Normalization on volatile dataset: accuracy_with = 0.89, accuracy_without = 0.82, effectiveness = 0.89 - 0.82 = +0.07 (component helped more).
Sum these up across 20 components and 50 datasets: 1000 pairs of models, 10,000 total experiments.

Each component-dataset pair gets a score; positive scores mean 'use this piece for this data,' negative means 'skip it.'

What can go wrong

What can go wrong

Overfitting to the test datasets. If the 50 datasets in the benchmark happen to favor certain components by accident, the insights are false. TimeRecipe mitigates this by using many diverse public datasets, but a future one might still overfit.
Components interact in hidden ways. Component A might help alone (when other pieces are simple), but hurt when paired with Component B (because both compete for capacity in the model, or because one cancels the other's benefit). Testing each in isolation misses these interactions. TimeRecipe tests main effects but not all 2-way or 3-way combinations.
Deployment does not match the benchmark. Your real time series might have properties the benchmark datasets do not capture (non-stationary shifts, extreme volatility, missing values). The recipe built on the benchmark might not transfer.
Done right. Use the insights as a starting point, not gospel. Test the recommended recipe on your own data, measure it, and tune if needed.
What a runnable demo should prove

What a runnable demo should prove

A working demo should show: (1) pick a dataset type (seasonal, chaotic, mixed), (2) use TimeRecipe's recommendations to assemble a forecasting model (e.g., 'use decomposition and normalization'), (3) train and test it, (4) compare the resulting accuracy to a generic off-the-shelf model (which does not know about your data type), (5) show that the recommended model is better (because it uses the pieces known to help that particular data type). The demo proves that the component-level insights transfer to real performance.

improvement = accuracy_recommended - accuracy_generic

The demo must make clear: by knowing which pieces matter for your data, you build a better model than a one-size-fits-all approach.
