Self-Re-Watermarking Trap: From Exploit to Resilience

Watermarks on images can be stripped and replaced by attackers; this paper uses controlled model sensitivity to prevent that.

Digital watermarks are hidden messages baked into images to prove ownership. A new attack lets someone take an already-watermarked image and use the same tool to write over the original mark with their own message, erasing proof of the real owner. This paper stops that attack by making the watermarking model less reactive to changes in the image.

Zero assumption version

Watermarks can be overwritten

A watermark is a hidden message baked into an image file. Think of it like writing your name in invisible ink on a photograph. The idea is that if someone steals your photo, your watermark proves you made it.

Deep learning watermarking works by training two neural networks (a set of algorithms): one encodes the watermark into the image, the other decodes it back out. A naive person might think: once a watermark is embedded, it stays. But there is a new attack called self-re-watermarking. An attacker takes the already-watermarked image and runs the same encoder again, but with a different message. The encoder replaces the old mark with a new one. Now the original owner's watermark is gone, and the attacker's mark is the only one left. Ownership is stolen.

In one sentence. An attacker can use the watermarking encoder to overwrite an existing watermark with their own message, erasing proof of the real owner.

What the paper changes

What the paper changes

The paper modifies the watermarking encoder—the network that writes the message into the image. Standard encoders are sensitive: small changes in the input image produce large changes in the written message. The paper makes the encoder less sensitive: it constrains how much the message can shift when the image is slightly altered. This insensitivity is the key. A less reactive encoder resists being reused to overwrite an existing watermark, because it cannot easily change what is already there.

the object it moves  =  encoder sensitivity
The hidden quantity

The hidden quantity: encoder sensitivity

measured quantity  =  Lipschitz constant (max rate of change)

Encoder sensitivity means: if you change the input image by a tiny amount, how much does the embedded message change? A high-sensitivity encoder makes big changes to the message for small image changes. A low-sensitivity encoder barely changes the message even if the image shifts. The paper measures this as a Lipschitz constant, a number that bounds the worst-case rate of change. The lower the Lipschitz constant, the less the encoder reacts.

The paper estimates the Lipschitz constant by studying the encoder's internal weights and how they amplify signals. It uses this bound to prevent re-embedding: if the encoder cannot change the message much, an attacker cannot easily overwrite a watermark that is already there.

Plain reading. The sensitivity of a model is how much its output wobbles when the input moves. Think of it like a tuning fork: tap it gently and it rings loud (sensitive), or tap it and it barely hums (insensitive). The Lipschitz constant is the loudest the model can ring.
Paper reading. The Lipschitz constant bounds the spectral norm of the encoder's weight matrices, controlling how changes propagate through each layer and limiting the maximum output shift per unit input change.
Why it works

Why it works: controlled insensitivity blocks re-embedding

Here is the causal chain. First, an encoder that is insensitive means small changes in the watermarked image produce tiny changes in the embedded message. Second, if the re-embedding attack tries to overwrite the watermark, it must push the existing message aside. But an insensitive encoder resists being pushed—it does not move easily. Third, because the attack cannot move the old message far, the original watermark stays strong enough to be recovered. The attacker's new message may technically be there, but the old message is not erased.

The paper adds a second weapon: adversarial training. During training, the system deliberately practices re-embedding—it tries to overwrite watermarks the same way an attacker would. By practicing this repeatedly, the encoder learns to dig in its heels. It becomes especially resistant to exactly this kind of attack. The combination of low sensitivity plus adversarial practice is what makes the watermark stick.

Math after the picture

The constraint equation

First in words:

Limit how fast the encoder output changes by bounding the largest weight amplification factor at each layer.

Then the compact form:

lipschitz_constant = product of largest_singular_value(W_i) for each layer i; constrain each to be <= c

Every symbol:

W_ithe weight matrix of layer i in the encoder
largest_singular_valuethe biggest amplification factor the matrix can produce
cthe target limit, e.g. 1.0, chosen to resist re-embedding
lipschitz_constantthe total rate of change bound for the entire encoder
A tiny worked example
Suppose an image pixel shifts by 0.1 units.
Layer 1 weight numbers (the largest singular value) are 0.9, so output shift is at most 0.1 * 0.9 = 0.09.
Layer 2 weights (largest singular value 0.8), so output shift is at most 0.09 * 0.8 = 0.072.
Layer 3 weights (largest singular value 0.85), so total encoder output shift is at most 0.072 * 0.85 = 0.061.
The original watermark message was 100 units strong. The attacker can shift it by at most 6.1 units. The message degrades slightly but stays mostly readable.

Low sensitivity (small singular values) means the encoder does not amplify small image changes into big message changes, so an attacker cannot easily overwrite an embedded watermark.

What can go wrong

What can go wrong

Sensitivity constraint too weak. If the Lipschitz constant is set too high (insensitivity is not strict enough), the encoder still moves enough for an attacker to overwrite the watermark. The constraint must be tight.
Adversarial training incomplete. If training does not practice enough re-embedding scenarios or does not include the exact attack the adversary will use, the encoder may learn a false sense of security and still be vulnerable to unforeseen re-embedding attempts.
Watermark fidelity suffers. Constraining the encoder to be insensitive may degrade image quality or weaken the watermark's ability to survive normal image processing (compression, resizing). The constraint and visual quality are in tension.
Done right. Carefully tune the Lipschitz bound so the encoder is resistant to re-embedding but still preserves image quality and watermark strength. Use diverse adversarial scenarios and validate against multiple re-embedding strategies.
What a runnable demo should prove

What a runnable demo should prove

Build a simple watermarking encoder-decoder pair (or use a tiny pre-trained model). Embed Owner A's watermark into an image. Then simulate an attacker: re-encode with a different message. Finally, try to decode both the original and the new watermark from the final image. A good demo shows that the original watermark is still recoverable even after the attack, while a baseline (unconstrained) encoder loses the original watermark entirely.

original_msg_error = fraction of original message bits still correct after attack; naive_encoder_original_msg_error should be near 50% (random), constrained_encoder_original_msg_error should be near 5% (most bits still right)

The demo makes it impossible to miss: the constrained encoder lets you recover the original watermark after an attack, because its low sensitivity prevents the attacker from erasing it. A normal encoder loses the original watermark because high sensitivity lets the attack overwrite it completely.
