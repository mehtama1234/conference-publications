AgentHijack: Testing Agent Robustness to Real-World Screen Noise

When computer-using agents see corrupted screens (pop-ups, resolution shifts, overlays), they fail; this work measures that failure and builds agents that notice the disruption instead of getting lost.

Paper explainersAll themesAgents & Tool Use

Imagine telling an AI agent to open your browser settings, but the screen has a pop-up covering half the menu, or the text suddenly shrinks, or something you clicked doesn't respond as expected. Real-world computer screens are messy. Pop-ups appear, windows shift, accidental touches happen. Computer-use agents (AI systems that control a desktop by watching the screen and clicking buttons) are surprisingly fragile when screens are not perfect. This work introduces nine real-world corruptions and shows agents fail badly; then it proposes a framework that teaches agents to notice when something is wrong and respond.

Zero assumption version

Agents lose their way on messy screens

Computer-use agents work by looking at a screenshot, understanding what it shows, and clicking the right button to complete a task. They are trained on clean, well-formed environments where every button is where it should be and every label is legible.

But real screens are full of junk. Pop-ups appear unexpectedly. Text gets covered by overlays. Windows minimize. Accidental touches happen. Network errors show strange dialogs. The agent sees something it was never trained to handle, gets confused, and either clicks the wrong button or gives up.

The naive solution would be to train on more corrupted examples, but that is slow and expensive. The real problem is deeper: the agent does not know it is confused. It sees corruption, hallucinates what it thinks it sees, and confidently takes the wrong action.

In one sentence. Agents see corrupted screens and fail because they cannot tell the difference between a clean signal and visual noise.

The algorithm as a flow

What it actually does

Benchmark defines corruption

Nine types of visual noise: pop-ups, resolution shifts, text overlays, multiple windows, accidental clicks, network errors, verification dialogs, app minimization, subtitle bars. Each has tunable intensity.

Agent sees corrupted screenshot

The model reads the corrupted screen and predicts the next action.

Enhanced grounding tightens the prediction

Instead of directly predicting an action, the agent first grounds itself by naming what it actually sees, reducing hallucination.

Onlooker summarizes and checks

A second module replays recent actions, verifies they made sense, and flags if the screen state contradicts the expected outcome.

Self-correction loop

If the onlooker detects corruption or mismatch, the agent re-reads the screen and chooses a safer action before proceeding.

What the paper changes

What the paper changes

The paper does two things. First, it builds a benchmark of nine realistic screen corruptions (pop-ups, resolution changes, overlays, accidental touches, network errors, app hiding, text overlays) that break existing agents. Second, it adds two new modules to the agent: enhanced grounding (the agent names what it sees before acting) and an onlooker (a second module that watches the screen and recent actions to detect when something went wrong).

the object it moves  =  agent perception and action selection
The hidden quantity

The detection signal: does the screen match the prediction?

measured quantity  =  Environment-prediction mismatch

Before this work, agents did not ask whether the screen looked the way they expected after their last action. If they clicked a button and a pop-up appeared instead of a menu, they just accepted the corrupted view and tried to work with it.

This work introduces a named hidden quantity: the mismatch between what the agent predicted should happen and what actually appears on the screen. The onlooker module measures this mismatch by replaying the agent's past actions, checking whether the observed screen state makes sense given those actions, and raising a flag if it does not. This signal tells the agent when to re-examine the screen and correct course.

Why it works

Why it works: the double-check circuit

An agent working on a corrupted screen is like trying to navigate a room where some of the signs are fake. The agent reads a sign, acts on it, and keeps going. If the sign was fake, it walks the wrong direction but does not know it.

This work adds a guard: after each action, an onlooker asks whether the new screen state makes sense given the action. If the agent clicked the menu button and a pop-up appeared, that does not match the expected outcome. The mismatch is the clue. When the onlooker detects a big mismatch, it tells the agent to stop, reread the screen carefully (using enhanced grounding, where the agent explicitly describes what it sees before deciding), and choose a safer next action.

This works because corruption is usually local. A pop-up blocks one part of the screen, not everything. Enhanced grounding forces the agent to name exactly what it sees, which filters out hallucinations. The onlooker's detection of mismatch acts as an early-warning system: if something feels wrong, verify before proceeding.

Math after the picture

The grounding penalty equation

First in words:

During training, the agent learns to favor actions where the grounding (what it explicitly says it sees) aligns with what actually appears after the action. The loss penalizes big gaps: grounding loss = distance between described state and observed state after action. When corruption causes the state to shift unexpectedly, the grounding mismatch grows, and the agent learns to re-examine.

Then the compact form:

L_ground = mean( ||desc(s_t) - observe(s_t+1)|| ) where desc is the agent's explicit description and observe is the true screen

Every symbol:

desc(s_t)the agent's plain-language description of the current screen
observe(s_t+1)what actually appears on the screen after the action
||...||how far apart these are (distance)
L_groundthe penalty for poor grounding, minimized during training
A tiny worked example
Agent sees: FILE | EDIT | VIEW menu (clean screen). Description: 'Three menu options at top.'
Agent predicts: clicking FILE will open a dropdown menu.
Pop-up corruption appears: a gray overlay covers FILE. Actual screen: FILE is now unreadable.
Observed state mismatch: the description said 'three menu options' but the overlay hides FILE.
Distance = 1.5 (mismatch detected). Grounding loss = 1.5.
Agent learns: when description and observation mismatch, something is wrong; re-ground before acting.
Next time, the agent re-reads carefully and notices the pop-up, avoiding the trap.

The equation formalizes the idea that when the screen does not match what the agent described, it is time to stop and re-examine.

What can go wrong

What can go wrong

Corruption is severe or unusual. If corruption covers more than half the screen or is not one of the nine benchmark types, grounding and mismatch detection may not catch it. The agent can still hallucinate.
The onlooker misidentifies corruption as intended. Some tasks naturally expect screens to change in surprising ways (e.g., a dialog box replacing the main menu). The onlooker might flag a legitimate state transition as corrupted and cause unnecessary re-grounding.
Cascading errors: mismatch detection comes too late. If the agent has already taken multiple wrong actions before the onlooker catches the corruption, the task state may be too far gone to recover, even with re-grounding.
The framework works best when: Corruptions are localized (one pop-up, not five), the task has clear intermediate checkpoints (e.g., a modal dialog that completes or closes), and the agent has been trained to name what it sees explicitly.
What a runnable demo should prove

What a runnable demo should prove

Build a simple desktop task: open a web browser, navigate to a settings page, and change a preference. Introduce a corruption (e.g., place a semi-transparent overlay at a random location on the screen). Run the baseline agent without the onlooker; observe that it fails or takes wrong actions. Then run the AgentHijack-Agent framework with enhanced grounding and the onlooker module. The onlooker should detect the mismatch, flag the corruption, and the agent should recover by re-reading and taking a safer action. Measure whether the task completes despite the corruption.

robustness score = (task success rate with corruption) / (baseline success rate on clean screen)

An agent with the onlooker should describe what it sees, notice when the expected button is not where it should be, and try a different path instead of guessing and failing, because the mismatch detection catches corruption before the agent wastes actions.
