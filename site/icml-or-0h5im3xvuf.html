AgentHijack: Making Computer-Use Agents Survive Real Messy Screens

Computer agents built on large vision-language models fail when screens get messy (pop-ups, resolution changes, other windows); this paper benchmarks that fragility and proposes a fix.

Paper explainersAll themesAgents & Tool Use

Imagine a robot that reads your screen and clicks things: it works great on a tidy, predictable desktop. But real computers are chaotic. Pop-ups appear, windows resize, other programs compete for space. These tiny disruptions cause today's vision-language-based agents to crash and forget their task. This paper makes that problem visible (by creating a benchmark of 9 realistic corruptions) and builds a smarter agent that notices when things go wrong and adjusts.

Zero assumption version

Agents see the screen, but screens are messy

A computer-use agent is a program that looks at your screen (via camera/screenshot), understands what it sees, and clicks or types to complete a task. These agents use a large vision-language model (a neural network trained to read images and text together) to decide what to do next.

In a lab, this works: clean desktop, one window open, no distractions. But real computers are chaos. A notification pops up. The window resizes. Another app runs in the background. The agent, trained only on clean screens, panics. It loses track of where the button is. It clicks the wrong thing. The whole task fails.

A beginner might think: just show the model more messy training examples. But that is slow and never catches all the real-world messes. The paper asks: how bad is the problem really, and can we fix the agent itself to notice when something goes wrong?

In one sentence. Real computers break computer-use agents because the screen does not look like the clean, controlled training environments.

What the paper changes

What the paper changes

The paper adds a second part to the agent: an onlooker. While the first part (the action generator) decides what to do, the onlooker watches the result, summarizes what actually happened on screen, and compares it to what was expected. If they do not match, it flags the mismatch and gives the action generator a chance to recover.

the object it moves  =  agent architecture and feedback loop
The hidden quantity

The hidden quantity: environment drift

measured quantity  =  expected vs. actual world state mismatch

The key invisible thing the paper measures is how much the real screen diverges from what the agent expected. When a pop-up blocks the view or a window resizes, the agent's mental model (built from the last clean screenshot) and the real screen are no longer aligned. We call this gap environment drift.

The paper estimates drift by having the onlooker describe the current screen state, compare it to the predicted state (what should be there if nothing went wrong), and detect contradictions. The bigger the mismatch, the higher the drift.

Why it works

Why adding an onlooker saves the agent

Here is the causal chain. An agent trained on clean screens builds an internal model: I click the login button, the login form appears; I type the password, it accepts it. This model is fragile because it assumes nothing else happens on the screen. When a pop-up appears, the model is violated, but the old agent does not notice. It keeps following the playbook and clicks the wrong thing.

The smarter agent adds a watchdog: the onlooker. After each action, the onlooker reads the screen and summarizes what it sees in plain words. It then compares this summary to what the action generator predicted would happen (derived from the model). If the summaries do not match, the onlooker flags the mismatch: yes, there is a pop-up blocking the target. On receiving this flag, the action generator stops following the playbook. Instead, it re-scans the screen, treats it as a new puzzle, and decides what to do from first principles. Often, the first step is to close the pop-up or wait for it to disappear. Once the screen is clean again, the agent resumes the original task. Because the onlooker catches the drift early, the agent has a chance to fix course before it gets lost.

Math after the picture

The recovery condition (when to replan)

First in words:

if (expected state summary) does not align with (observed state summary), then flag corruption and replan

Then the compact form:

replan = (similarity(expected_state, observed_state) < threshold)

Every symbol:

expected_statewhat the action generator predicted would happen
observed_statewhat the onlooker actually sees on screen now
similaritya score comparing two state descriptions (0=completely different, 1=identical)
thresholdthe boundary at which we say corruption has occurred (e.g., 0.7)
A tiny worked example
Agent predicts: Login button is visible, login form ready. Similarity baseline = 1.0.
Corruption: Pop-up appears. Onlooker reads: Pop-up overlay, login button blocked, form not visible.
New similarity = 0.4 (many things do not match).
Threshold = 0.7. Since 0.4 < 0.7, replan flag is true. Agent stops following playbook.
Agent: I will close this pop-up first. Clicks close button. Pop-up disappears.
Now similarity = 0.95. Replan flag is false. Agent resumes: enter password and log in.

The mechanism works because the onlooker continuously checks that the world still matches the agent's plan, catching divergence before the agent crashes.

What can go wrong

What can go wrong

Onlooker also confused. If the screen is so corrupted that the onlooker cannot read it either (extreme pixelation, complete blackout), the onlooker fails to describe the state, and the agent cannot recover.
Multiple simultaneous corruptions. If three things break at once (pop-up + resize + flicker), the signal is noisy and the onlooker may not spot all of them. The agent might re-plan on a partially wrong model.
Corruption is very subtle. A tiny color change or a slightly moved button might not trigger a replan, because the similarity score is still high. The agent might not notice it has gone off course.
Done right. The onlooker is given the same vision-language model as the action generator, so it sees roughly what the agent sees. The comparison is done in natural language (descriptions), not pixel-by-pixel, so tiny visual glitches do not break it.
What a runnable demo should prove

What a runnable demo should prove

Build a simple task: open a web page, click a button, fill a form, submit. Run an old agent on it with a pop-up injected halfway through. Record the failure. Then run the smart agent on the same task with the same pop-up. Record the recovery. The visible proof: the old agent freezes or clicks the wrong thing; the smart agent pauses, notices the pop-up, dismisses it or waits, and then completes the form.

task_completion_rate = (tasks_completed_successfully / total_tasks_attempted) under corruption

The point is simple: agents that watch themselves and admit when something is wrong can survive the messy real world. Agents that blindly follow a playbook cannot.
