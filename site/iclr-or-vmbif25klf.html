REI-Bench: Robot Planning with Vague Instructions

When a robot gets vague human instructions with ambiguous references like 'the mouse' (device or animal?), resolving those ambiguities in a separate step before planning makes the robot succeed instead of fail.

Paper explainersAll themesRobotics & Control

Robots follow instructions written by humans. When humans say 'bring me the mouse,' they might mean the computer device or a pet. This vagueness crashes robot task planners because the planner tries to do everything at once: understand the words AND generate the plan. This paper shows that by first clarifying what the human meant, then planning, the robot succeeds even on confusing instructions.

Zero assumption version

Robot planners break when instructions are ambiguous

A robot's job is to turn a human instruction into an action plan: 'bring me the pen' becomes a sequence of pick, move, place commands. Current systems use large language models (neural networks trained on text data that can write coherent sentences) to do this.

But real human instructions are messy. People say 'put it outside' when 'it' has multiple meanings. They say 'the mouse' when there's a computer mouse and a pet in the same room. Linguists call this vagueness in referring expressions: the thing someone points to with words depends on context and shared understanding. When a model tries to plan a 9-step task while simultaneously decoding what 'the mouse' means, it fails at both because the same computing resources (the neural network's ability to process information) get split between two competing jobs.

The problem in one sentence: A robot planner trying to understand vague words and generate a plan in one step makes mistakes on both.

The algorithm as a flow

What it actually does

Take vague instruction and dialogue history

Input: 'Bring me the mouse and put it outside' plus five earlier messages between human and robot.

Run a dedicated clarification model

This model does ONLY language understanding: 'the mouse' is the computer device, 'it' means the same device.

Produce a clean instruction

Output: 'Bring me the computer mouse and put it outside.'

Feed the clean instruction to the planner

The planner's full capacity now aims at turning words into step-by-step actions.

Generate action sequence

Pick computer mouse from desk, walk to door, drop mouse outside. Success.

What the paper changes

What the paper changes

The paper splits the planner into two separate modules, not one. Instead of a single language model that tries to both understand ambiguous references AND generate a plan, there is now a clarification module that runs first, followed by a planning module.

The hidden quantity

The attention budget

measured quantity  =  concentration on ambiguity resolution

When a neural network solves a task, every computation cycle can focus on only one thing. A model that tries to both understand vague language and generate a plan in a single pass must split its computing resources between the two jobs. Some resources go to resolving 'the mouse' (is it a device or an animal?), and some go to sequencing actions. Neither job gets full capacity. This paper measures and fixes that split.

The method estimates it by observing what the model learned: does the model dedicate its full capacity to handling vague language, or does it skimp on word-sense resolution to save computation for planning? The paper shows that when you force separation (clarify first, plan second), the clarification step uses all its resources for ambiguity, and the planning step wastes zero effort on word meanings.

Why it works

Why separating jobs fixes the problem

A neural network has a fixed amount of computing capacity. When you ask it to solve two hard problems at once — understand an ambiguous sentence AND generate a valid plan — it must divide that capacity. Some computing goes to ambiguity resolution, some to planning. When you ask it to solve the ambiguity first, write down the clear version, then solve the planning problem, each job gets full capacity and both improve because the model can now apply its full capabilities to each task in turn, rather than spreading thin across both.

Task-oriented context cognition (TOCC) applies this insight. A language model working on ambiguous instructions faces two hard problems: (1) figure out what the vague words mean given the dialogue history, and (2) generate a valid action sequence. When crammed into one step, the model 'underperforms its inherent language understanding abilities' — that is, it fails to use the knowledge it was trained on about how context and reference work, because computing resources ran out. By running a separate clarification step first, that module has full capacity to do what language models are already good at: understanding context. The planner then sees unambiguous input and can dedicate all its computing machinery to sequencing actions correctly.

Math after the picture

The formulation

First in words:

success rate equals one minus the number of failures divided by the total trials

Then the compact form:

success_rate = (trials - failures) / trials = 1 - (failures / trials)

Every symbol:

trialstotal number of planning tasks attempted
failuresnumber of tasks where the generated plan was wrong or impossible
success_ratefraction of tasks the planner got right, from 0 to 1
A tiny worked example
Suppose a robot is given 100 planning tasks with vague instructions.
Old method (all-in-one planner): 36 tasks fail, 64 succeed. Success rate = 64 / 100 = 64%.
New method (TOCC: clarify then plan): 8 tasks fail, 92 succeed. Success rate = 92 / 100 = 92%.
The improvement is 92% - 64% = 28 percentage points, close to the paper's observed 36.9% drop from vague REs.

The success rate rises when attention is split, because each module (clarify, then plan) dedicates full capacity to its single job.

What can go wrong

What can go wrong

Clarifier misunderstands context. If the clarification module guesses wrong about what 'the mouse' means, the planner inherits that wrong guess. The problem moves earlier in the pipeline.
Extra latency. Running two models instead of one takes longer (the clarifier runs, then the planner). On a robot with slow compute or limited battery, this two-stage overhead may be unacceptable.
Clarifier over-simplifies. Some ambiguities are legitimate and necessary for planning. If the clarifier resolves everything rigidly, it removes useful flexibility the planner could have used.
Done right. When the clarification module is trained on diverse examples of real dialogue and context, and the planner is given enough signals to catch clarifier mistakes, the separation works well across different tasks and users.
What a runnable demo should prove

What a runnable demo should prove

Build a small robot task planner (even simulated, like picking objects from a room). Give it instructions with deliberately vague references — 'put the pen and pencil in the box, but move it first' (does 'it' mean the pen, pencil, or box?). Run the all-in-one baseline and the TOCC two-stage version on 50 such tasks. Measure success rate on each.

improvement = success_rate_TOCC - success_rate_baseline

The demo makes undeniable: the two-stage approach succeeds on vague instructions where the one-stage approach fails, because each stage can focus.
