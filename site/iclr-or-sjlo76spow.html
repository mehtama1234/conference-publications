MobileKGQA: On-Device KGQA System on Dynamic Mobile Environments

MobileKGQA answers questions over a user's knowledge graph on a small device by compressing entity representations and by creating fresh training labels when the graph changes.

Paper explainersAll themesOther

A mobile assistant may store personal facts as a knowledge graph: nodes are people, places, events, or items, and edges state relations such as "called," "visited," or "belongs to." A question-answering system over that graph has to map a question to the right nodes and relations, then follow them to an answer. Standard systems are too heavy for a phone or edge device because they keep large learned tables for every node and relation, and they usually assume the graph is fixed after training. MobileKGQA changes both parts. It compresses the learned representation table by hashing many entries into a small shared table, and it updates itself when new facts arrive by generating extra supervision from the graph it already has. That is why it can run on-device while still tracking a graph that keeps growing.

Zero assumption version

Why ordinary KGQA does not fit on a mobile device

Knowledge graph question answering starts with a graph of facts. If the graph stores that Alice visited Kyoto in March and that Kyoto is in Japan, then a system should answer a question such as "Which country did Alice visit in March?" by finding the Alice node, following the visited edge to Kyoto, then following the located-in edge to Japan.

Most strong KGQA systems learn a separate embedding (a learned list of numbers that represents one entity or one relation) for many graph items. They also use large neural networks with many parameters (the learned numbers inside the model). This is expensive in memory, compute, and energy because every question must read and combine many stored representations.

There is a second problem. A phone's graph changes often: new contacts appear, calendar events are added, locations change, and messages create new links between entities. A model trained once on yesterday's graph will miss those additions today. Re-training from scratch is too costly on a small device because it requires many updates over the whole model.

The paper's move. Shrink the stored graph representations with hashing, then adapt to new facts by generating new labels from the updated graph so the model can refresh itself without full retraining.

The algorithm as a flow

What it actually does

Store graph facts locally

Keep user data as entities and relations in a device-side knowledge graph.

Encode with hashed tables

Map many entities and relations into a smaller shared representation table using hashing, which cuts memory because many items reuse the same storage buckets.

Answer by graph reasoning

Read the question, score candidate entities and relations, and follow graph connections to rank answer nodes.

Generate labels after updates

When the graph changes, build new question-answer supervision from those added facts, because the new edges create answer paths the old training set never showed the model.

Fine-tune lightly on-device

Run a small update using the generated supervision, because those fresh labels move the scorer toward the new graph facts without requiring passes over the whole old training set.

What the paper changes

What the paper changes

The paper changes the storage and update path of KGQA. Instead of keeping a large one-entry-per-item representation table and assuming a fixed graph, it uses a compressed hashed table and an update procedure that reuses the graph itself to create new training examples.

the object it moves  =  graph representation storage and update strategy
The hidden quantity

Hash collision rate: the hidden pressure point

measured quantity  =  How often different graph items land in the same bucket

Hashing saves memory by sending many entities into a smaller number of buckets. That only works if collisions stay manageable. A collision happens when two different entities are forced to share the same stored representation. Some sharing is acceptable because the rest of the model can still separate entities from context, but too much sharing makes distinct entities look similar and harms answer quality.

So the hidden quantity is collision rate: how crowded each bucket becomes. The method wins because it cuts storage enough to fit the device, while keeping collision damage low enough that question answering still works.

Paper reading. Embedding hashing trades memory for representational interference. The useful operating point is the range where bucket sharing is high enough to save resources, but not so high that entity and relation scoring becomes unreliable.
Why it works

Why the two-part design works

The first part is compression. In ordinary KGQA, each entity may have its own stored list of numbers, so memory grows with graph size. Hashing changes that scaling rule because multiple entities read from a shared table. The model loses some per-entity detail, but it still sees the graph structure, the question words, and relation patterns, so it can often recover the right path even when storage is compressed.

The second part is adaptation. A new graph fact creates a mismatch: the model's old training data did not teach it how that new node or edge should affect answers. The annotation generation method repairs that mismatch by producing new question-answer pairs from the updated graph. Those synthetic labels are useful because they point directly at the new facts the model would otherwise ignore.

The two parts support each other. Compression makes the system small enough to deploy, and fresh generated labels keep the compressed model current. Without compression, the model is too expensive for the device. Without generated updates, the model fits but becomes stale as the graph changes.

The compressed lookup idea

First in words:

A graph item does not own a private stored representation. Instead, its hash index selects one shared bucket, and the model uses that bucket's learned list of numbers when scoring answers.

Then the compact form:

e_i = T[h(i)]

Every symbol:

e_ithe representation used for entity or relation i
Tthe small shared table of learned representations
h(i)the hash function output that maps item i to one bucket
T[h(i)]the bucket representation retrieved for item i
A tiny worked example
Suppose the full system would store separate rows for 10,000 entities.
MobileKGQA keeps only 2,500 shared rows and sends each entity to one row by hashing.
If entity 318 and entity 904 both map to row 57, they reuse the same stored row.
That creates some interference, but storage drops by about 4x because 10,000 private rows become 2,500 shared rows.
If the rest of the model can still use question context and graph links to separate those entities, the answer stays correct while memory stays low.

The main trade-off is simple: fewer stored rows save memory, but more sharing raises collision risk. The paper shows there is a range where that trade is favorable on a mobile device.

What can go wrong

What can go wrong

Too many collisions. If the shared table is too small, unrelated entities receive nearly the same stored representation, so the model confuses answer paths that should stay separate because the scorer no longer sees enough stored detail to distinguish those entities.
Generated labels can reinforce errors. If the updated graph already contains wrong or incomplete facts, then the self-generated supervision teaches those mistakes back into the model because the update step trusts the graph.
Large graph shifts may exceed light updates. A small on-device fine-tune works when the graph changes incrementally. If the graph schema or relation patterns change sharply, a light update may not be enough because the model's old reasoning paths no longer match the new structure.
Done right. Choose a table size that keeps collision pressure moderate, validate generated labels against graph consistency checks, and use the on-device update path for gradual graph growth rather than full domain changes.
What a runnable demo should prove

What a runnable demo should prove

Build a small personal-assistant graph with contacts, meetings, locations, and reminders. Ask multi-hop questions such as "Which city is the colleague I met after the robotics meeting from?" Compare two models on the same edge device: one with a full representation table and one with a hashed shared table. Then add new graph facts each round and generate fresh question-answer pairs from those new edges. Measure answer quality, memory use, compute, and energy before and after the graph updates.

update_gain = answer_score_after_light_update - answer_score_without_update

The demo should show two facts at once: compression keeps the system within device limits, and generated update labels recover answer quality after the graph changes because the model sees supervision tied to the new facts.
