DriveMamba: Efficient End-to-End Driving via Sparse Tokens

Instead of building a dense scene map first, convert all driving data directly into sparse position-sorted tokens and process them in one pass with a faster algorithm.

Paper explainersAll themesRobotics & Control

Autonomous driving systems traditionally break the problem into stages: first perceive (extract scene features), then predict (where objects move), then plan (choose steering). The trouble is each stage discards information (early perception decisions cannot be revised by later planning), and the traditional Transformer mechanism (which compares each piece of information to every other piece, quadratic complexity) becomes expensive when handling many video frames across six cameras. This paper replaces the stages with a single Mamba decoder that takes sparse tokens (pools of image features) sorted by their real-world position and processes them with a faster linear-complexity algorithm (scanning each token once instead of comparing all pairs), which avoids the quadratic bottleneck and lets all stages learn from each other immediately since they share the same decoder, so planning constraints can inform perception upfront.

Zero assumption version

The old sequential pipeline breaks under efficiency pressure

Today's autonomous driving systems follow a conveyor belt: cameras send images to a perception module (which extracts features and recognizes objects), those predictions feed into a motion module (which guesses where things will move), and finally a planning module (which chooses steering commands). The pipeline's rigidity forces early decisions that can't be revised. If perception misses a subtle detail, prediction and planning have to live with the mistake.

On top of the conceptual problem, there is a computational one. The perception and prediction modules often use a Transformer (a model that uses attention: comparing each piece of information to every other piece). When you feed six video cameras playing 10 frames each, that is thousands of pieces of information, and comparing every one to every other one grows as the square of the count. The system runs out of memory or becomes unbearably slow.

The old way in one sentence. Separate modules (perceive, predict, plan) chained together, each using expensive quadratic-complexity attention over dense feature maps.

What the paper changes

What the paper changes: token order and architecture

The paper changes two things: how you represent the scene (sparse tokens sorted by position instead of dense feature maps) and what processes them (a Mamba decoder using linear-complexity operations instead of a Transformer using quadratic-complexity attention). Sorting tokens by their real-world location lets a simpler algorithm preserve the spatial structure without building an expensive bird's-eye map, because nearby-in-space objects stay nearby in the processing sequence, so the algorithm learns their relationships more easily than if they were scattered across a dense map.

The hidden quantity

The hidden quantity: spatial token locality

measured quantity  =  Spatial locality preservation score

The paper measures a hidden quantity that previous work overlooked: how well the token processing order preserves the structure of the real scene. When you scan tokens left-to-right along a trajectory, nearby objects in the world stay nearby in the processing sequence. This locality matters because Mamba (the algorithm that processes the sequence) learns patterns in nearby elements much better than distant ones.

The paper estimates this by checking whether task queries (the questions: where is the car? what is moving?) end up correlated with sensor tokens that are physically close in the 3D world. A bidirectional scan (forward and backward) boosts locality because scanning right-to-left catches dependencies the forward pass missed, especially for objects behind the car. A trajectory-guided order (following the car's expected path) boosts it further, because the car's attention is narrowly focused on the path ahead and nearby lanes, not the entire panorama.

Why it works

Why it works: linear cost scales, joint learning breaks down errors

Mamba is a newer algorithm that scans a sequence one element at a time, updating a small hidden state, instead of comparing every element to every other element like Transformer attention. This makes it linear-complexity: processing 10,000 tokens costs roughly 10,000 operations, not 100 million, because each token is visited once and each visit does a fixed amount of work. With sparse tokens (not dense maps), there are fewer things to process, so the savings are larger: a 4000-token Transformer costs 16 million comparisons, but a 800-token Mamba costs only 9.6 million operations.

The second reason is architectural: when perception, motion, and planning all run in one decoder, they learn from each other immediately instead of passing incomplete predictions down a pipeline. If perception extracts a faint object boundary, the motion module sees the raw features too and can refine the estimate. This joint optimization prevents error cascade.

The third reason is spatial structure. By sorting tokens by 3D position and scanning them bidirectionally (forward and backward), the algorithm naturally learns that nearby things in the real world are likely related because they tend to have predictable interactions (a pedestrian near a curb is about to cross; a vehicle ahead is about to brake). The trajectory-guided scan makes this even tighter by letting the algorithm focus its local patterns around the car's planned path. Locality is stronger signal than density, because a Mamba layer can learn relationships between neighbors with just a few state updates, whereas dense maps force the model to encode everything upfront.

The equation: computational cost of sparse token processing

First in words:

Processing cost equals token count times hidden state size times layer count, with bidirectional scan multiplied by 2; dense attention cost is proportional to the square of feature count times layers

Then the compact form:

cost = 2 * (N_sparse * H_state * L) vs. cost_old = Q_dense^2 * H_dense * L

A tiny worked example
Dense BEV case: 4000 features × 2000 features per layer × 12 layers = 96 million operations (quadratic in features).
Sparse Mamba case: 800 tokens × 512 hidden dimension × 12 layers × 2 (bidirectional) = 9.6 million operations.
Sparse is 10× cheaper. With 6 cameras over 10 frames, sparse token extraction and depth estimation add overhead, but the net speedup is 3.2×, and memory drops from 8GB to 2.5GB.

Linear Mamba processing beats quadratic attention when you have enough tokens to be useful but not so many that extraction overhead dominates.

What can go wrong

What can go wrong

Trajectory unpredictability breaks spatial locality. If the car suddenly swerves or the planned path is wildly wrong, the trajectory-guided scan order becomes meaningless and the locality advantage vanishes. The method assumes the trajectory estimate is reasonably accurate.
Depth estimation errors cascade into token positioning. The method assigns 3D coordinates using estimated depth from each camera. If depth is wrong, tokens are sorted incorrectly, and the spatial locality signal becomes noise. This is a bottleneck on rainy or night driving.
Sparse tokens miss small objects and thin structures. Pooling features into tokens means some small details are lost. A narrow cyclist or a thin guardrail might disappear into the sparse representation. The depth-based sorting cannot help recover a missing token because sorting is just reordering; it cannot invent pixels that were pooled away. Without the visual feature, the spatial position alone cannot tell the model what should have been there.
Done right: combine with dense regional queries. Use trajectory-guided token sorting as the backbone, but keep a small dense-feature option for high-uncertainty regions (e.g., immediately around the car). Hybrid sparse-dense avoids both information loss and computational waste.
What a runnable demo should prove

What a runnable demo should prove

Build a system that takes a sequence of six camera views from a nuScenes dataset clip (10 frames, three seconds of driving). Tokenize each camera to 50 features, estimate depth per token, sort by 3D position. Run the tokens through both a standard Transformer decoder (comparing all pairs) and a Mamba decoder (scanning left-to-right, then right-to-left). Measure processing time and memory used. Then measure whether the Mamba model detects objects, predicts motion, and plans steering as accurately as the Transformer despite being 3x faster (the speedup happens because Mamba avoids comparing every token to every other token like Transformer attention does).

speedup = time_Transformer / time_Mamba; memory_saved = (mem_Transformer - mem_Mamba) / mem_Transformer; task_accuracy_gap = |acc_Transformer - acc_Mamba| (should be <3%)

The demo must show that sparse tokens sorted by position, processed linearly, run 3x faster (fewer operations per token) with 70% less memory (fewer tokens stored), while losing less than 3% accuracy on real driving tasks compared to a quadratic-attention baseline (because spatial locality and joint learning preserve the information that matters).
