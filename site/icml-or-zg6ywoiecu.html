Approximate Nearest Neighbor Search for Modern AI: A Projection-Augmented Graph Approach

Attach cheap projection-based tests to a graph nearest-neighbor index, so the search can skip many full distance calculations while keeping the candidates that are still likely to be truly close.

Paper explainersAll themesOther

Approximate nearest neighbor search sits underneath retrieval systems, recommendation, search, and many AI pipelines built on learned numeric representations. The basic job is to find points in a large database that are closest to a query, but doing exact search at scale requires too many full distance calculations. Graph indexes such as HNSW solve much of this by traversing a neighbor graph instead of scanning all points. The paper argues that modern workloads ask for more than query speed alone. They also need fast index building, moderate memory use, stability in very high dimensions, support for different top-k retrieval sizes, and online insertion of new items. Projection-Augmented Graph, or PAG, adds a second kind of information to the graph: cheap projected comparisons that can screen candidates before the system pays for an exact distance. The method matters because graph search usually spends most of its time deciding which candidate distances are worth computing exactly. PAG reduces that waste by making the first decision with a cheaper approximation plus a statistical acceptance rule.

Zero assumption version

Why graph search still spends too much work on the wrong candidates

Graph-based nearest-neighbor indexes move through the database by visiting promising points and expanding their neighbors. The bottleneck is that the search still performs many exact high-dimensional distance calculations to decide which candidates to keep exploring.

That decision cost becomes painful in modern AI settings because points often have hundreds or thousands of dimensions and the system may need to serve many queries per second while also accepting new insertions. A good candidate filter must therefore be cheap, must avoid discarding truly close points, and must fit naturally into graph traversal.

The paper's move. Use low-cost projected comparisons to decide which graph candidates deserve a full distance computation, because most candidates can be screened without paying the full high-dimensional cost.

The algorithm as a flow

What it actually does

Build a neighbor graph over the database.

Store points together with graph links to nearby points, because graph traversal provides a practical search path through a large collection.

Create projection-based summaries.

Compute lower-cost projected representations that preserve enough distance structure for screening, because these summaries are cheaper to compare than the full stored point descriptions.

Traverse the graph for a query.

Use the usual graph walk to generate candidate points, because the graph still provides the search backbone.

Screen candidates asymmetrically.

Compare exact and projected information with a statistical rule so weak candidates can be discarded early, because only a fraction of candidates deserve a full exact distance evaluation.

Refine the surviving candidates exactly.

Spend the full distance cost only on points that survive screening, because the final top neighbors still need exact ranking among the strongest candidates.

What the paper changes

What the paper changes

The paper changes graph search from exact-distance-first filtering into projection-guided filtering where exact distance is reserved for candidates that first pass a cheaper test, because most weak candidates can be rejected from the projected comparison alone.

The hidden quantity

The hidden quantity

measured quantity  =  candidate promise before paying the full distance cost

The useful hidden quantity is whether a candidate is promising enough to justify an exact distance computation. Traditional graph search reveals that only after spending the full cost. PAG tries to estimate it first from projected information.

This matters because the main waste in nearest-neighbor search is not visiting a candidate node once. It is repeatedly computing exact distances for nodes that were never close enough to matter. A good early estimate lets the search spend its exact computations on the few candidates that could still enter the top results.

Why it works

Why adding projections to a graph index helps

A projected representation is cheaper to compare because it uses fewer coordinates than the full point. On its own, that rough view is not accurate enough to rank final neighbors. It is accurate enough, however, to eliminate many bad candidates. PAG exploits this by placing the cheap projection test before the expensive exact distance calculation.

The asymmetry is important. The search does not need projection to prove that a candidate is one of the final nearest neighbors. It only needs projection to show that many candidates are not worth further attention. That is an easier job. A statistical rule then decides when the projected comparison is decisive enough to skip the exact one. The exact distance is still used on the surviving candidates, so final quality is protected where it matters most.

This design also fits practical requirements beyond query speed. It keeps the graph structure that already supports insertion and scalable indexing, and it adds a lighter screening layer rather than a heavy secondary index. That is why the method can improve queries per second while remaining workable under high dimensionality and changing retrieval size.

Math after the picture

Screen before exact ranking

First in words:

For each candidate, estimate its distance to the query in the projection space. If that estimate already looks worse than the current search frontier by a sufficient margin, skip the exact high-dimensional distance. Otherwise compute the exact distance and keep the candidate in the competition.

Then the compact form:

exact_distance_needed(candidate) = projected_gap(candidate, frontier) < screening_threshold

Every symbol:

projected_gap(candidate, frontier)how much worse the candidate looks than the current promising set under the cheap projected comparison
screening_thresholdthe cutoff that decides whether projection evidence is decisive enough to reject the candidate
exact_distance_needed(candidate)whether the search pays for the full distance calculation

What can go wrong

What can go wrong

Poor projections can reject true neighbors. If the projected space distorts local distances too much, the screening rule can discard a genuinely close candidate, because the cheap comparison no longer tracks the exact local shape well enough.
The screening threshold can be mis-set. A very strict threshold saves little time because too many candidates survive, while a very loose threshold harms recall because too many good candidates are filtered out.
Graph quality still matters. Even perfect screening cannot repair a weak graph index, because the search only sees neighbors that the graph exposes in the first place.
Done right. The approach is strongest when the projected summaries preserve enough local ordering for candidate rejection, because then exact distance is used only where the cheap test is genuinely uncertain.
What a runnable demo should prove

What a runnable demo should prove

Build a graph approximate nearest-neighbor index over a moderate dataset of high-dimensional learned point representations. Add a projection layer that stores a lower-dimensional signature for each point. During query time, compare a baseline graph search that computes exact distance for every candidate against a PAG-style search that first applies projected screening and computes exact distance only for survivors.

The demo should report throughput and recall at several dimensionalities and several retrieval sizes. A convincing result shows that the projection-augmented version reaches similar recall with many fewer exact distance calls, because that proves the cheap screening stage is identifying low-value candidates correctly.

distance_savings = 1 - exact_distance_calls_with_screening / exact_distance_calls_without_screening

The essential proof is not only higher speed. It is substantial exact-distance savings at similar recall, because that is the direct mechanism the paper is built around.
