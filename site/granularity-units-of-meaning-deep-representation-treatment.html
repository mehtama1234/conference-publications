Granularity: choosing the right unit of meaning

This page connects the token, patch, frame, sparse-dimension, codebook, concept, and exact-string papers under the representation theme. The shared question is: what should count as one unit, and what breaks when that unit is too large, too small, or aimed at the wrong thing?

Core idea

The unit is the first representation

Before a model can learn, search, predict, align, or generate, something has already decided what the model is allowed to treat as one thing.

For language, the unit might be a character, a subword, a word, or a vocabulary token. For vision, it might be a pixel patch, an object region, a fine visual token, or a coarse visual token. For video, it might be a frame, a short clip, a motion segment, or a whole behavior episode. For embeddings, it might be one dense vector, a few sparse dimensions, a binary code, or a codebook entry. For clinical, mathematical, code, and named-entity data, the unit might need to be exact because one character can change the meaning.

This is why granularity belongs in the representation series. A representation is not only a vector after the encoder. It starts earlier, at the boundary decision: where does one meaningful piece end and the next one begin?

raw input -> choose units -> encode units -> learn relations among units -> use representation for a task

The first-principles line is simple: a representation works when its units match the distinctions the task needs to preserve. If the unit is wrong, the model can be powerful and still see the world through bad pieces.

Why units matter

If we split this unit, what breaks? If we merge it, what becomes invisible?

Granularity is the choice of resolution. Too coarse, and different things get merged. Too fine, and one meaningful thing gets shattered into fragments. Both can fail.

Too coarse.

The model treats several different facts as one unit. A visual patch may contain text plus background. A table bin may merge safe and dangerous lab values. A sparse code may collapse many queries into a generic topic. The model becomes efficient, but it loses distinctions.

Too fine.

The model splits one useful fact into too many pieces. A name becomes awkward fragments. A video action becomes isolated frames. A phrase becomes a long sequence of tiny tokens. The model can rebuild the meaning, but it pays extra compute and may fail to keep identity stable.

The good unit does not mean the largest possible unit, and it does not mean the smallest possible unit. It means the unit whose boundary matches the job. A code model needs exact syntax units. An OCR model needs small visual detail. A behavior model needs motion over time. A retrieval model needs the few semantic dimensions that separate the right document from similar wrong ones.

unit choice = compression decision + identity decision + task decision
How units are decided

The right unit is chosen by the use case, not by the data type alone

There is no universal best unit. A unit is a promise about what the model will keep together, what it will separate, and what kind of mistake it is willing to make cheap.

The same raw thing can be represented at many levels. A sentence can be characters, subwords, words, phrases, claims, or intents. An image can be pixels, patches, letters, parts, objects, relations, or a scene. A video can be frames, clips, actions, phases, events, or goals. A patient record can be individual lab values, visits, symptoms, medications, disease stages, or a hidden patient state. None of these levels is automatically correct. The right level depends on what the later system must compare, copy, predict, explain, or act on.

The deep reason is that a unit is not just a piece of input. It is the smallest object the model is being asked to treat as stable enough to reuse. If the unit is a token, the model can reuse that token across sentences. If the unit is an object region, the model can compare that object across images. If the unit is a clip, the model can name a motion rather than a still pose. If the unit is a patient state, the model can reason over a disease process rather than isolated measurements. Choosing a unit is choosing where stability begins.

1. Start from the answer-changing difference

The first question is not "what is the data made of?" It is "what difference changes the answer?" If one character changes a drug, the character-level distinction must survive somewhere. If one frame changes whether a person is standing or falling, the temporal unit must be short enough to catch it. If one object boundary changes a segmentation mask, the visual unit must preserve that boundary. If one graph edge changes the role of a node, the graph unit must include local structure, not only the node label.

This is the most important rule because it turns granularity from a formatting choice into a task choice. A model can compress aggressively only after it knows which distinctions are safe to lose. Otherwise it may keep the easy differences, like style, texture, or frequency, and erase the hard differences, like rare names, small lesions, short contact events, or exceptions in a contract.

2. Decide what can vary without changing the answer

The second question is "what can safely vary without changing the answer?" If the task is identifying a dog, lighting and background may be allowed to vary. If the task is reading a road sign, lighting may vary but letter shape cannot. If the task is retrieving a tax document, exact page formatting may not matter, but the difference between employee and contractor may matter a lot. A representation unit is useful when it keeps the answer-changing differences while letting harmless variation compress away.

This is why representation learning is often about controlled forgetting. The model should forget shadows when shadows are not part of the answer. It should forget font when font is not part of the answer. It should forget repeated wording when the claim is the same. But it must not forget the variable name in code, the decimal point in a dosage, the edge in a graph, or the direction of motion in a robot trace. Unit choice says what the model is allowed to forget locally.

3. Find the level where the world behaves as one thing

The third question is "where does the world itself have a useful boundary?" Some boundaries are symbolic: a token, a variable name, a legal clause, a diagnosis code. Some are spatial: an object, a cell, a lesion, a table cell, a molecule part. Some are temporal: a heartbeat, a visit, a shot in a video, a phase of an action. Some are relational: a graph neighborhood, a speaker turn, a chain of evidence, a cause and its effects. Good unit choice often means finding the level where the domain already behaves as if something is one thing.

This matters because the raw storage format often lies. A video file is stored as frames, but the event may be a jump, a fall, a gesture, or a goal that exists across many frames. A clinical table is stored as rows and columns, but the meaningful unit may be a trend over visits. A document is stored as tokens, but the meaningful unit may be a claim with evidence. A graph is stored as nodes and edges, but the useful unit may be a role in a larger neighborhood.

4. Match the unit to the next operation

The fourth question is "what will the model do after it sees the unit?" A retrieval model needs units that make useful matches cheap. A generator needs units that can be recombined without losing grammar or identity. A controller needs units that preserve smooth change and physical constraints. A medical model needs units that keep patient-specific and threshold-sensitive facts. A theorem or code model needs units that preserve exact syntax while still allowing larger reasoning steps.

This is why the same representation can be good for one downstream use and poor for another. A paragraph embedding may be excellent for finding a relevant document, but too coarse for verifying a citation. A single image embedding may be enough for product search, but too coarse for locating a defect. A dense patient embedding may predict risk well, but too opaque for explaining which lab trend changed the decision. The unit has to serve the next operation, not just describe the input.

5. Balance composition against fragmentation

A small unit is useful because it can compose. Characters make any word. Patches make any image. Frames make any video. Nodes and edges make any graph. But composition has a cost: the model must rebuild larger meaning from many pieces. If the pieces are too small, the model spends capacity reassembling what the domain already treats as one thing. If the pieces are too large, the model cannot see the internal difference that matters.

The right unit is often the lowest level that preserves the needed distinction without forcing unnecessary reconstruction. A code model may need tokens for syntax, but it also needs function-level units for reasoning. A video model may need frames for appearance, but clips for action. A medical model may need exact lab values, but also visit-level and trajectory-level units. Good systems often carry several unit sizes at once because meaning itself lives at several sizes.

6. Let error cost shape the boundary

Unit choice should become stricter when the cost of confusion rises. In casual chat, two phrasings may be close enough. In medicine, two similar strings may be different drugs. In finance, two dates may change whether a filing is late. In code, one missing character can break execution. In robotics, a tiny pose error can become a collision. High-cost domains need units that protect exactness, thresholds, timing, and identity more aggressively.

This does not mean every high-cost domain should use the smallest possible units everywhere. That would overload the model and hide larger patterns. It means exact units must be available at the points where exactness changes the decision, while larger units still carry context, trend, and cause.

7. Test the unit by the behavior it enables

A unit is not correct because it is natural-sounding. It is correct when behavior improves in the place where the task is fragile. For OCR, the test is whether the model reads small text. For retrieval, whether it finds the right answer rather than a nearby topic. For code, whether it copies and executes correctly. For medicine, whether it respects thresholds and patient context. For robotics, whether motion is smooth and safe. For graphs, whether structure transfers rather than only node labels.

That is the final discipline: the chosen unit must be judged by the failure it prevents. If a unit does not prevent a real failure, it may only be a convenient way to package data.

IdentityWhat must remain the same across harmless changes? A person, object, variable, disease, intent, graph role, or action phase?
ContrastWhat must stay different even if it looks similar? Similar drug names, two legal clauses, adjacent objects, related diseases, near-duplicate documents?
CompositionWhat larger thing should be built from smaller pieces? A word from characters, a proof from steps, an object from parts, a behavior from frames?
Time scaleHow long does the fact live? A symbol may live for one token. A pose may live for a few frames. A diagnosis may unfold over weeks.
Spatial scaleHow large is the meaningful object? A letter stroke, table cell, organ region, molecule bond, street sign, face, room, or whole scene?
Action costWhat happens if the unit is wrong? Bad search result, broken code, missed lesion, wrong medication, unsafe motion, false legal conclusion?
TestWhich behavior exposes the unit: exact copy, OCR, segmentation, retrieval, forecasting, control smoothness, graph transfer, clinical decision?
choose the unit by asking: what can change the answer? what must remain exact? what can be safely compressed? what must stay smooth over time or space? what larger structure must be built from these units? what downstream behavior will expose a bad unit?

This is why two papers can use the same raw modality but make opposite unit choices. One image paper may need large object regions because the task is scene understanding. Another image paper may need tiny visual tokens because the task is reading text in the image. One language paper may merge tokens for speed. Another may preserve exact strings because it cares about code, medicine, or names. The modality is only the starting material. The use case decides which boundary matters.

Across use cases

Different domains choose units for different reasons

The unit is not just an implementation detail. It encodes what the domain treats as meaningful. A good unit in one domain can be a bad unit in another because the error has a different shape.

Think of each use case as asking the model to preserve a different kind of truth. Chat preserves communicative meaning. Code preserves executable structure. Medicine preserves patient state and safety-critical thresholds. Vision for search preserves object and scene meaning. Vision for OCR preserves small marks and layout. Robotics preserves physically valid change. Graph learning preserves relation and role. The unit should be chosen around that truth, not around a generic desire to make everything shorter.

Chat and writingThe model often needs units that compose into meaning: subwords, words, phrases, claims, and speaker intent. Exact surface form matters for quotations, names, and instructions, but much of normal writing can tolerate paraphrase. So the unit can be smaller than a word for flexibility, while later layers build phrase and intent units.
CodeThe useful unit is shaped by execution. Keywords, identifiers, operators, indentation, delimiters, imports, function bodies, file paths, and API calls all have hard roles. A code model may need character-level recovery for spelling, token-level boundaries for syntax, and larger units for functions or modules. The unit must support both exact copying and structural reasoning.
MathMath needs units that preserve reference and transformation. A variable, exponent, operator, quantifier, equation, lemma, and proof step can each be the meaningful unit at a different moment. The model must know that changing a symbol can change the claim, but it also must group several symbols into one mathematical object before it can reason over it.
MedicineThe useful unit is often the clinically meaningful state, not just the raw field. A lab value matters because of its threshold, trend, timing, patient context, and relation to other findings. Drug names and dosages need exact identity. A visit may be the unit for one task, while a disease trajectory over months may be the unit for another.
Legal and financeThe unit is tied to obligation, risk, and exception. A date, amount, party name, clause, condition, citation, or accounting category can change the decision. Broad semantic similarity is not enough. The model needs units that preserve exact references and also group related clauses into the larger rule they create.
Document retrievalThe right unit is the smallest piece that can answer the query without dragging in too much unrelated text. Sometimes that is a paragraph. Sometimes it is an entity, table row, formula, sparse feature, or whole section. The unit must be narrow enough to avoid false matches and broad enough to contain the needed context.
OCR and screenshotsThe unit must protect small visible marks. A single letter, icon, checkbox, table cell, cursor position, or layout relation can carry the answer. Large image patches may be efficient, but they can hide the thing the user is asking about. Here the visual unit is chosen around readability and layout, not just object identity.
Object recognitionThe model should not treat every pixel as equally important. Shape, part arrangement, object boundary, texture, and relation to nearby objects matter more. The useful unit may be a part or region because the task asks what object is present, not the exact value of every pixel.
Video understandingThe unit is decided by the timescale of the fact. A frame can identify appearance. A short clip can identify motion. A longer segment can identify an action. A full episode can identify goal or intent. A model that uses only frames may miss change; a model that uses only long clips may miss the moment where the event turns.
RoboticsThe unit must match what the robot can safely execute. Tool choice, grasp type, contact event, pose, force, trajectory, and feedback state are all possible units. Discrete units help choose modes. Continuous units help move without jumps. The wrong unit can look accurate offline but fail when the robot touches the world.
Time seriesThe unit should respect when measurements actually happen. A value, event, window, trend, irregular timestamp, and hidden state can each matter. Fixed bins are useful when timing is coarse. They are harmful when the interval between events carries the signal.
GraphsThe useful unit is rarely just an isolated node. A node's role depends on its neighbors, edge types, paths, communities, and position in the larger structure. A graph token or codebook entry should preserve relation, not only node content.
Science dataThe unit should follow the mechanism being studied. In molecules it may be atoms, bonds, residues, or functional groups. In biology it may be genes, cells, pathways, tissues, or patient state. In physics it may be particles, fields, states, symmetries, or conserved quantities. The right unit is the one at which the underlying process becomes easier to predict.

The same object can require different units

A page of text is not one kind of thing. For summarization, the useful unit may be a paragraph or claim. For citation checking, it may be a quoted phrase, page number, or reference. For code generation, it may be a function, import, identifier, or indentation block. For medicine, it may be a symptom, dosage, lab value, timeline, or patient state. The raw form is still text, but the unit changes because the use changes.

An image is similar. For image search, the model may only need object and scene units. For OCR, it needs letters and layout. For radiology, it may need small lesions, organ regions, scanner artifacts, and patient-level findings. For robotics, it may need graspable object parts, free space, depth, contact points, and obstacles. Calling all of these "image understanding" hides the actual choice.

Video adds another layer because the unit can live in time. If the task is recognizing a species, one clear frame may be enough. If the task is recognizing limping, grooming, falling, stirring, reaching, or tool use, the unit must include motion. If the task is planning, the unit may be a longer episode with intent and outcome. The right unit is the timescale at which the fact becomes visible.

The paper cluster as unit arguments

The deeper reading of the paper cluster is this: each paper is making an argument about the unit that best protects the important difference in its world. Lossless vocabulary reduction says some language tokens are only conveniences; they can be removed when smaller pieces preserve behavior. CSRv2 says a retrieval representation can be reduced to a few active dimensions only if those dimensions carry real distinctions. SigLIP-HD says visual detail can be preserved more cheaply if mid-resolution units are taught what high-resolution units knew. BEAST says animal behavior cannot be represented only as appearance; it needs units that carry motion through time. Neural implicit action fields say robot motion is often better treated as a smooth function than as disconnected points.

same raw data, different use case, different unit: image for search -> semantic region image for OCR -> small visual token video for object identity -> frame appearance video for behavior -> clip or trajectory text for gist -> phrase or concept text for code or medicine -> exact symbol string

The first-principles lesson is that a unit is chosen at the level where the important cause, distinction, or action becomes stable enough to reuse. Too small, and the model spends its effort rebuilding what should have been one thing. Too large, and the model hides the difference that should have changed the answer.

Tokens, subwords, characters

Language models read pieces, not thoughts

Lossless Vocabulary Reduction makes this concrete. A language model does not first receive an idea. It receives a sequence of token ids. Those token ids are the model's first language representation. If the vocabulary gives a whole word its own token, the model can handle it as one piece. If the vocabulary splits that word into subwords or characters, the model must rebuild the word from parts.

Large units are efficient when they are common and meaningful. A frequent word, code keyword, domain term, or stable phrase may deserve one token because it saves sequence length and keeps identity clear. But large units can also be wasteful. A rare combined phrase like tax_refund_deadline may not need its own token if tax, refund, and deadline already preserve the meaning.

tax_refund_deadline tax refund deadline

Small units are reusable. Characters can spell any word, and subwords can build rare words. But small units make sequences longer and can make exact identity harder to keep. A model that sees a rare drug name as many fragments may still reconstruct the surface string, but it may become less reliable at copying, comparing, or distinguishing it from a similar drug name.

vocabulary question: is this token a necessary unit of meaning, or only a shortcut that smaller pieces can rebuild?

The deep point is that tokenization is not just preprocessing. It decides which language distinctions are cheap, which are expensive, and which are fragile.

Patches, objects, visual tokens

Vision units decide whether fine detail survives

In vision models, the unit is often a patch or visual token. A patch is convenient because it turns an image into a sequence, but a patch is not automatically a meaningful object. One patch might contain part of a letter, part of a face, a corner of an object, or mostly background. If the patches are too coarse, small text, fine boundaries, and tiny objects disappear inside the unit. If they are too fine, the model handles many more tokens and compute rises quickly.

SigLIP-HD sits exactly here. Higher-resolution images create more fine-grained visual tokens, which helps OCR and small visual details, but costs more. The paper's fine-to-coarse supervision asks whether a cheaper mid-resolution representation can be trained to preserve the useful distinctions that a high-resolution representation would have seen.

Patch

A fixed crop of pixels. Cheap and regular, but may cut across object boundaries.

Object region

A more semantic unit. Useful when the task cares about objects and relations.

Fine visual token

Preserves small text, local detail, and precise layout, but increases compute.

The question is not simply whether bigger images are better. The question is which visual differences must stay visible to the downstream task. OCR needs letter-level differences. Counting needs object individuation. Segmentation needs boundaries. Image-text retrieval may only need broader semantic regions. The right granularity changes with the job.

Frames and clips

A frame preserves appearance; a clip preserves change

Video makes the granularity problem sharper. A single frame can show what is visible right now: body shape, object position, texture, lighting, and scene layout. But it cannot fully show motion, rhythm, direction, intent, or action phase. Those are not frame facts. They are relations across frames.

BEAST is a good example. It learns from unlabeled animal video by combining appearance pressure with temporal pressure. The appearance pressure asks what is inside a frame. The temporal pressure asks which moments belong together. That only makes sense because behavior is not a single-frame object. It is a state moving over time.

SALT is nearby but solves a different granularity issue. It keeps a teacher target stable while the student learns from video patches. The unit is not only frame versus clip; it is also target stability. A video feature target must be steady enough that the student can learn what a hidden patch or hidden moment means.

frame unit: what does the animal look like now? clip unit: what behavior is unfolding over time? episode unit: what longer state or task is being carried forward?

The mistake is treating all video information as if it lived at one scale. Pose may live in a few frames. Grooming rhythm may need a short clip. Long-horizon intent may need a longer segment. The unit has to match the timescale of the fact.

Sparse dimensions and dense vectors

Embedding granularity is about how many signals get to speak

A dense vector spreads meaning across many dimensions. That is flexible. It gives the model room to encode many weak signals at once. But dense vectors are expensive to store, compare, and search. They can also hide meaning everywhere, making it hard to know which dimensions do real work.

CSRv2 asks the opposite question: can an embedding be useful when only two to four dimensions are active? That is an extreme granularity choice. The unit is no longer the whole dense vector. The unit becomes each surviving active dimension. Every active dimension must earn its place.

Dense vector.

Many partly active dimensions. Good for capacity, but costly and diffuse.

Ultra-sparse vector.

Only a few active dimensions. Cheap and sharp, but dangerous if those dimensions become generic or dead.

This is the same unit question in another form. If a retrieval embedding gets only four active slots, should those slots say finance, document, web, and general? Or should they say tax, refund, deadline, and freelancer? The first code is short but vague. The second code is short and task-controlling.

good sparse unit = a dimension that names a distinction the task actually uses
Concepts and surface strings

The unit may be a concept, not the literal surface

Some papers are really asking whether the model learned the underlying concept or only the surface string attached to it. A surface string is the exact word or phrase. A concept is the reusable thing that can appear through many names, views, measurements, or modalities.

In multimodal learning, the same concept may be visible in an image, described in text, implied by audio, or measured by a clinical sensor. A concept-based medical system may use clinically grounded concepts as the shared unit between radiology and pathology. The point is not that both modalities have the same pixels. They do not. The point is that both can point to the same patient-level or disease-level concept.

Latent distribution matching gives the deeper rule: observations are measurements of hidden causes. The model should learn units that line up with those hidden causes when the data gives enough evidence. Structural invariance gives the same rule from another angle: when surface changes, the stable relation should remain. If the unit is only a surface string, it may fail when the same concept is said another way. If the unit is only a vague concept, it may lose exact wording that matters.

surface string: "heart attack" related concept: myocardial infarction, acute coronary event, patient risk state granularity question: does the task need exact wording, shared concept, or both?
Exact units

Code, math, names, and medicine often cannot be split casually

Some domains punish bad granularity immediately. In ordinary prose, splitting a rare word into subwords may be acceptable if the model can rebuild the meaning. In code, math, names, and medicine, small differences can change identity, legality, execution, or truth.

Code.

def, return, async, indentation, punctuation, and identifiers can carry exact structure. Splitting or merging them badly can make syntax and copy behavior fragile.

Math.

Symbols like sum, <=, variables, exponents, and equation boundaries can be small but decisive. A unit that hides the boundary can damage reasoning.

Names.

A person's name is an identity unit. If it is split into common fragments, the model may copy it less reliably or confuse it with another name.

Medicine.

Drug names, genes, diagnoses, lab thresholds, and abbreviations can differ by one character. A tokenizer or binning scheme that erases that difference can create a serious error.

This does not mean every exact string must become a single token. It means the representation must preserve exact recovery and exact distinction where the domain demands it. Lossless vocabulary reduction is acceptable only when the behavior survives, not merely when text can be reconstructed in principle.

How people build them

Pick a unit, squeeze it, teach it, then test it

Most of these papers follow the same plain pattern. They decide what one piece should be, limit what that piece can carry, train the model so the piece carries the useful part, and then check whether the real task still works.

The method names differ, but the work is concrete. One paper changes word pieces. Another changes image patches. Another changes a dense vector into a few active dimensions. Another changes robot motion from waypoint chunks into a smooth function. Underneath, they are all asking the same engineering question: what form should the information take so the model can use it without carrying too much junk?

1. choose the unit 2. limit what it can carry 3. train it to keep the useful part 4. test whether behavior survives

1. Tokenize the input

The first move is often to cut the raw input into pieces. Text becomes tokens or subwords. Images become patches or visual tokens. Tables become value bins. Robot actions become action tokens or waypoints. Graphs become node or structure codes. This step matters because the model can only reason over the pieces it receives.

If the pieces are bad, later layers have to repair the damage. A word split into awkward fragments, a visual token that hides small text, or a table bin that merges two clinically different values gives the model a weak starting point.

2. Put a limit on the message

A useful representation usually cannot say everything. The limit may be a smaller vocabulary, fewer visual tokens, fewer active embedding dimensions, a binary code, a fixed codebook, or a short clip. This limit is not only for speed. It forces a choice about what deserves space.

CSRv2 makes this easy to see. If only two to four dimensions can be active, those dimensions cannot waste space on generic hints. They have to carry the facts that let a query find the right document. Lossless Vocabulary Reduction does the same at the language-input layer: remove a token only when the remaining pieces can still do its job.

3. Use a target that tells the unit what to keep

The model needs a signal. Sometimes the signal is a teacher model. SALT freezes the teacher so the student has a steady target. SigLIP-HD asks a cheaper visual representation to imitate useful detail from a higher-resolution one. Discrete communication asks the student to predict the teacher's compact binary message.

Sometimes the signal is a hidden-piece task. Mask some image patches, words, video patches, graph nodes, or table values, then ask the model to recover what is missing. If recovery requires structure, the unit learns structure. If recovery can be solved by surface tricks, the unit learns the wrong thing.

4. Pull together what should match, keep apart what should differ

Many papers use comparison. Two views of the same thing should land near each other. A query and the right document should share enough active sparse features. Nearby video frames should remain related. Different objects, actions, or meanings should not collapse into one code.

This is contrastive learning in plain terms: teach the representation which differences matter. The danger is that the model can satisfy local comparisons while damaging bigger structure. That is why the topology-aware page matters: it asks whether all these local moves tear the larger map.

5. Keep structure from collapsing

Learned units can go dead or collapse. A codebook may use only a few entries. A sparse embedding may leave most dimensions inactive. A binary message may assign the same code to too many inputs. A graph tokenizer may ignore graph structure and reuse tokens lazily.

People fight this by adding pressure for use and diversity: keep codewords active, give all codebook entries updates, punish assigning the same token to dissimilar graph nodes, shrink sparsity gradually instead of all at once, and use clear supervised pairs when the message is extremely short.

6. Move from rough pieces to better pieces over time

Some representations are easier to learn if the model is not forced into the final tiny form on day one. CSRv2 starts with more active dimensions and gradually lowers the number. A vocabulary reduction method can remove rebuildable tokens carefully instead of blindly deleting rare ones. A visual system can learn from high-resolution features before trying to behave cheaply at mid resolution.

The simple reason is that the model first needs to discover what matters. Once it has learned the useful distinctions, it can be asked to say them with fewer pieces.

7. Test the behavior, not just the representation

A representation is not good because it is short, elegant, sparse, discrete, or mathematically neat. It is good if the task still works. The tests must match the risk: retrieval for sparse embeddings, exact copy for names and code, OCR for visual tokens, threshold sensitivity for medicine, action smoothness for robots, and transfer for general representation learning.

This is the final guardrail. A unit can look efficient while quietly erasing the thing that mattered. The only honest check is whether the downstream behavior survived.

How the papers instantiate it

The paper cluster is about unit choice across domains

These papers look different on the surface because they operate on different objects: language vocabularies, visual tokens, binary codes, sparse dimensions, graph codebooks, table bins, and action trajectories. But they share one move: they choose a unit, then test whether the chosen unit preserves the distinctions that matter.

Lossless Vocabulary ReductionUnit: vocabulary token. It asks which tokens can be removed because smaller tokens can rebuild the same next-token behavior, and which tokens must remain because they carry exact or efficient distinctions.
CSRv2Unit: active sparse dimension. It asks how few dimensions can stay active while preserving retrieval and representation quality. The danger is dead dimensions or generic surviving dimensions.
Self-Supervised Learning as Discrete CommunicationUnit: binary message bit or code. It frames representation learning as a teacher-student communication problem where the channel is limited, so the message must become compact and meaningful.
PATCHCODEUnit: stable discrete code for noisy continuous signals. It asks how biological or sensor signals can become learnable chunks without letting noise define the code.
TabularBERTUnit: bin or table token. It turns raw numeric fields into learnable symbolic pieces, but the bin boundaries must preserve thresholds and useful numeric differences.
SigLIP-HDUnit: visual token at a chosen resolution. It asks whether fine visual perception can be preserved without paying for high-resolution inference at every step.
Graph VQ / RGVQUnit: graph codebook entry. It asks how graph nodes or structures should be quantized without codebook collapse, and uses graph topology to keep token assignments diverse and meaningful.
VQ dimensional-collapse papersUnit: codebook dimension and codeword. They ask whether discrete codebooks use their full expressive space or collapse into a low-dimensional subset.
Neural Implicit Action FieldsUnit: discrete waypoint versus continuous action function. It asks whether robot motion should be represented as sampled chunks or as a smooth function over time.

The shared test is not aesthetic. It is behavioral: after choosing the units, can the model still retrieve the right document, read the right word, see the small object, track the action, preserve the graph structure, copy the exact name, and execute the smooth motion?

Questions to ask any granularity paper

What is one unit?A token, subword, character, patch, object, frame, clip, sparse dimension, codeword, bin, concept, string, or action segment?
What does the unit preserve?Identity, syntax, visual detail, motion, threshold, semantic topic, graph role, patient state, or control smoothness?
What does it compress?Redundant wording, background, visual pixels, dense dimensions, repeated frames, unused codebook entries, or irrelevant surface variation?
What breaks if it is too coarse?Small objects vanish, names blur, lab thresholds merge, code syntax gets fragile, retrieval becomes generic, or action becomes imprecise.
What breaks if it is too fine?Sequences get long, compute rises, identity fragments, codebooks undertrain, local pieces lose global meaning, or motion becomes jittery.
How is success tested?Downstream behavior: retrieval, OCR, copy fidelity, code execution, medical distinction, dense prediction, graph transfer, or robot control.
granularity audit: what is one unit? what does it preserve? what does it hide? what does it make cheaper? what mistake does it make more likely?
Failure cases

What goes wrong when the unit is wrong?

Coarse units erase exact distinctions.

A visual token covers too much area, a table bin crosses a clinical threshold, or a language token grouping hides a meaningful boundary.

Fine units overload the model.

Characters, tiny patches, or frame-by-frame video can preserve everything locally but make sequences long and global meaning harder to track.

Learned units collapse.

Codebooks may use only a few entries, sparse dimensions may die, and binary messages may collapse into the same code for many inputs.

Surface units replace concept units.

The model may learn a phrase, background, scanner, or visual style instead of the hidden cause that should transfer.

Concept units erase exact strings.

A broad medical or legal concept may be useful, but exact drug names, clauses, citations, and identifiers still need reliable surface preservation.

Task mismatch.

The unit preserves the wrong thing: object identity when the task needs position, short text when the task needs exact copy, or discrete waypoints when the robot needs smooth motion.

Takeaway

The first-principles line

Granularity is the choice of what the model is allowed to treat as one thing. Good granularity compresses without destroying the distinctions the task needs.

This page connects the earlier representation pages. Hidden-cause learning asks what the units should name. Structural invariance asks what should stay stable across views. Soft equivariance asks what should change predictably. Topology asks how many units arrange into a larger shape. Discrete communication and sparse embeddings ask how short the message can become. Lossless vocabulary reduction asks whether the first language units can shrink while behavior survives.

good unit = stable enough to reuse + small enough to compose + exact enough for the task

The recurring question for the theme is now: what is one unit here, and why?
