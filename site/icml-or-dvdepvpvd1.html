Self-CriTeach: LLM Self-Teaching via Autonomous Planning Domains

An LLM generates its own planning domains to create training data and reward signals for robotic task learning without manual effort.

Paper explainersAll themesAgents & Tool Use

Teaching language models to plan robotic tasks usually requires two expensive things: manually written chain-of-thought examples showing the reasoning step-by-step, and carefully hand-engineered reward signals to guide reinforcement learning. This paper flips that around: the LLM writes its own symbolic planning domains, then reuses those same domains for both generating training examples automatically AND defining reward functions. One source, two jobs.

Zero assumption version

Why training LLMs for robotics is stuck

Teaching a language model to plan robotic tasks requires two kinds of training supervision that are expensive to create. First, you need chain-of-thought examples: step-by-step reasoning that shows the model how a human would plan a task. Second, if you use reinforcement learning (a method where you reward good choices and punish bad ones), you need to manually design the reward function—what counts as good? In robotics, manually writing rewards is hard because tasks are complex and ambiguous.

Roboticists currently do both by hand. Chain-of-thought data for a single task domain can take weeks to annotate. Reward functions require domain expertise to get right—reward the wrong thing slightly, and the model learns to game the system instead of solving the real task.

The bottleneck. LLMs for robotics need both supervision-heavy training data and carefully hand-designed rewards, and getting both is expensive.

The algorithm as a flow

What it actually does

LLM reads task description

Given a robotic task (e.g. pick and place), the language model analyzes what must happen.

LLM writes planning domain

The model outputs a symbolic domain: predicates, actions, and rules in formal notation.

Domain generates training pairs

Automated tools use the domain to create problem-plan pairs showing how to solve each instance.

Extended chain-of-thought

Each auto-generated plan is converted to reasoning steps, making training examples.

Domain scores learned plans

When training the model to plan better, the domain structure defines the reward—high if the plan satisfies the rules, low otherwise. This works because the domain encodes the task's logic, so following it guides learning toward generalizable solutions.

What the paper changes

What the paper changes

The object of change is the source of training supervision: instead of a human writing domain rules and reward functions by hand, the LLM itself generates them. This one shift cascades: automatic domain generation feeds into both supervised training (via auto-generated examples) and reinforcement learning (via structured rewards). The model does the creativity work humans used to do.

The hidden quantity

The hidden quantity: Structured supervision

measured quantity  =  Domain-generated reward density

The hidden quantity the paper relies on is the density and coherence of reward signal: how densely does the domain structure feed useful feedback, and how well does that feedback align with the actual task goal? A hand-tuned reward often gives sparse feedback (one score at the end) and can misalign with what you really want (optimizing the reward surface instead of solving the task). A domain-based reward is denser (it scores intermediate steps) and more aligned (it reflects logical correctness), because it comes from the task structure itself.

The paper estimates this by measuring how often the domain-based reward agrees with true success: when the domain says a plan is good, does the plan actually work on the robot? Plans that satisfy the domain's logical rules and structure tend to transfer to new tasks, because they follow the task's core logic rather than exploiting quirks of any single reward function.

Why it works

Why it works: the causal chain

The mechanism has three links. First, an LLM understands task structure well enough to write a valid planning domain—it can extract the relevant predicates and actions from a problem description. This is plausible because LLMs have seen planning problems in training data and can pattern-match the form. Second, once the domain exists, it deterministically generates many problem-plan pairs: a symbolic planner runs the domain's rules exhaustively, creating examples that are correct by construction. No annotation needed. Third, that same domain structure defines what counts as good when reinforcement learning trains the model: a plan is rewarded if it satisfies the domain's logical constraints. The domain acts as a filter on plan space, steering learning toward logically sound solutions.

Why does this work better than hand-tuned rewards? Because the domain's reward signal is structurally tied to the task itself—it cannot accidentally reward the wrong thing. A hand-crafted reward can misalign (you write a reward for speed, but what you actually wanted was efficiency; the model learns to cheat). A domain-based reward is anchored to logical correctness, so it guides the model toward plans that will generalize to variations of the task. The model learns not to exploit a reward surface, but to understand the task structure.

Math after the picture

Equation: Domain-based reward

First in words:

Reward equals one if the plan satisfies all domain constraints, zero otherwise. Training loss combines supervised learning on auto-generated examples plus reinforcement learning with this binary reward.

Then the compact form:

Loss = Loss_SFT(plan_examples) + lambda * Loss_RL(R_domain(plan), target)

Every symbol:

Loss_SFT(plan_examples)supervised training on auto-generated problem-plan pairs
Loss_RL(R_domain(plan), target)reinforcement learning comparing domain reward to target performance
R_domain(plan)binary reward: 1 if plan satisfies domain rules, 0 otherwise
lambdaweight balancing supervised and reinforcement learning
targetactual robot success or test performance
A tiny worked example
Task: arrange three blocks. Domain generates 100 valid problem-plan pairs from its rules.
Supervised loss: model trained on those 100 pairs, learning to predict next planning step.
RL reward: when model proposes a plan, R_domain scores it (1 if all blocks end arranged per domain rules, 0 if any violated).
If model proposes moving block A onto B when domain requires B-then-A order, reward is 0, training signal is negative.
If proposal matches domain logic, reward is 1, training continues that behavior.
Over many plans, RL nudges the model toward domain-valid solutions; domain reward never asks for illegal moves.

The domain structure replaces hand-tuned reward weights; reward is binary and objective (satisfies rules or not).

What can go wrong

What can go wrong

LLM writes an invalid domain. If the language model generates a domain with logical contradictions or missing predicates, downstream training breaks. This happens if the task description is vague or if the model hallucinates details. The fix: validate domains via automated checkers before using them.
Domain is too narrow or too permissive. A domain that is too strict allows only one solution, which overfits because the model learns only that one example instead of the task's core logic. A domain that is too loose rewards many invalid plans, so learning focuses on shortcuts. The paper shows domain quality matters. Poor domains waste computation and yield plans that don't transfer.
Domain assumes perfect state information. Real robots see noisy sensor data (imperfect logical states). A domain written for clean input may reject plans that are actually sound because the sensors reported wrong values. The paper shows that plans handle sensor noise better with domain plus reinforcement learning, because RL nudges the model away from rigid domain constraints toward plans that work even when sensors are wrong. Perfect-world domain assumptions still remain a limitation.
Done right: iterate domain design. LLMs can iteratively refine domains based on feedback from early training runs. Multiple domains per task hedge against single-domain brittleness. Human review of generated domains catches major errors early.
What a runnable demo should prove

What a runnable demo should prove

A demo should start with a simple robotic task (blocks world or pick-and-place) and show that an LLM can autonomously generate a valid planning domain. Then run the domain's planner to generate problem-plan pairs (proving it can create training data without annotation, because the planner exhaustively explores the domain's rules). Finally, train an LLM with those pairs, measure planning success on new tasks, and show it outperforms a baseline LLM trained on hand-written examples or with a simple hand-tuned reward (because domain-based supervision is more aligned with task structure than arbitrary rewards). The key metric is cross-task generalization: does the domain-trained model solve variations it has never seen?

Success = (num_plans_that_satisfy_domain and achieve_goal) / (num_test_tasks)

The demo must make it impossible to miss that one automatically generated domain yields training data AND reward function, eliminating manual effort.
