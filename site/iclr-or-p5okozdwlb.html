MicroMix: Mixed-Precision Quantization for Fast LLM Inference

Assign different number sizes to different layers in a language model so it runs fast and stays accurate.

Paper explainersAll themesOther

Running a large language model on a laptop requires chopping the numbers down to smaller sizes. Most methods use the same sized chop everywhere. MicroMix realizes that each layer of the model has a different sensitivity, so it uses smaller numbers where the model tolerates them and larger numbers where it needs precision. The result: nearly as fast as uniform shrinking, with nearly the accuracy of the original.

The speed bottleneck in shrinking language models

When you run a large language model on your computer, most of the time it spends doing matrix multiplications: feeding a stream of numbers through matrices of weights to produce the next word. With billions of weights, this is slow. To make it faster, engineers shrink the numbers: instead of storing each weight with 16 decimal places (called FP16), use 4 decimal places (called INT4 or FP4). This is 4 times faster because the shrunk numbers take up 75 percent less memory and move through the graphics card 4 times per cycle instead of once.

Modern graphics chips like NVIDIA's Blackwell have special circuitry for FP4 math that can run twice as fast as INT4. But here is the catch: existing number-shrinking systems do not actually use FP4 correctly. They compute in INT4, store the result in a format the chip can read, and lose the speed benefit. It is like having a Ferrari engine but only filling it halfway because your fuel nozzle does not fit the tank.

The problem in one sentence. Modern number-shrinking shrinks numbers everywhere equally, but each layer of a language model needs a different amount of shrinking to stay accurate.

The algorithm as a flow

What it actually does

Gather calibration data

Run the model on a small sample of real text to see how each layer's numbers behave.

Measure error thresholds

For each layer, find where FP4 starts to lose too much precision (call it threshold-4) and where FP6 does (threshold-6).

Categorize the layer

Numbers below threshold-4 become FP4. Numbers from threshold-4 to threshold-6 become FP6. Numbers above threshold-6 become FP8.

Reorder and shrink together

Group numbers by their chosen precision, pack them into efficient blocks, and shrink them all at once.

Run on the GPU

The finished model runs on the graphics card using the FP4 circuitry for 4-bit channels and hardware for 6-bit and 8-bit. Speed comes from parallel execution.

What the paper changes

The one thing that changes

MicroMix changes which precision format each channel of each layer uses. Instead of a global decision (all FP4, or 50% FP4 and 50% FP8), the algorithm independently assigns FP4, FP6, or FP8 to each channel based on how much precision loss it can tolerate.

the object it moves  =  precision per channel per layer
The hidden quantity

The hidden quantity: error tolerance per layer

measured quantity  =  how much shrinking each layer can tolerate

Every time you shrink numbers, you lose precision. The question is: how much error can this layer absorb without breaking the model's final answer? MicroMix explicitly measures this. For the 4-bit format, it calculates a threshold: any number above the threshold would lose too much accuracy if shrunk to 4 bits, so it gets bumped to 6 bits. Similarly, numbers above the second threshold get 8 bits.

The paper estimates this hidden quantity by running calibration data (a small sample of real text) through each layer and tracking the mean size of the channel outputs. Channels with bigger outputs are more sensitive, need higher precision. Channels with tiny outputs can safely go to 4 bits.

Why it works

Why it works: matching precision to layer sensitivity

The core insight is simple: shrinking error depends on the size of the numbers you are shrinking. A tiny number (say 0.01) loses very little precision if you shrink it from 16 bits to 4 bits. A huge number (say 1000) can lose a lot. So instead of making a global rule, measure the size of channel outputs in each layer during calibration, and assign higher precision to the layers where numbers are bigger.

The math enforces this: for each layer, the algorithm partitions channels into three groups by size. Small channels go to 4 bits (fastest). Medium channels go to 6 bits. Large channels go to 8 bits (slowest, most precise). Because most channels are small, the layer still runs fast overall, and because the sensitive channels are protected, accuracy stays high.

The reordering trick makes this efficient: when different channels have different precision, they need to be grouped together in memory (so the graphics card can process all 4-bit channels at once, then all 6-bit, etc.). MicroMix integrates this reordering into the shrinking step, so it costs almost nothing in latency.

The equation: precision thresholds and error budgets

First in words:

Partition channels into three groups by size. Channels smaller than threshold-4 use 4 bits. Channels between threshold-4 and threshold-6 use 6 bits. Channels larger than threshold-6 use 8 bits. Each group is shrunk in 32-element blocks with per-block scaling.

Then the compact form:

G_small = {X | X <= threshold_4}, G_medium = {X | threshold_4 < X <= threshold_6}, G_large = {X | threshold_6 < X}

Every symbol:

Xoutput value (a single number in a channel's output)
threshold_4cutoff below which 4-bit shrinking has acceptable error
threshold_6cutoff below which 6-bit shrinking has acceptable error
G_smallset of all numbers assigned to 4-bit format
G_mediumset of all numbers assigned to 6-bit format
G_largeset of all numbers assigned to 8-bit format
A tiny worked example from one layer
Calibration finds average output size is 2.5 across channels.
Set threshold_4 to 1.0 (below this, 4-bit shrinking error is small, matching 8-bit baseline).
Set threshold_6 to 3.5 (above 1.0 but below this, 6-bit shrinking is safe).
A channel with size 0.8: 0.8 is below 1.0, so assign 4 bits (saves 75% memory).
A channel with size 2.1: between 1.0 and 3.5, so assign 6 bits (saves 62.5% memory).
A channel with size 4.2: above 3.5, so assign 8 bits (saves 50% memory, safer).
Result: 50 percent of channels run at 4 bits, 30 percent at 6 bits, 20 percent at 8 bits. Overall: 2.5 times faster than original.

The thresholds are chosen so that shrinking error for a channel at its assigned precision is never worse than if it were shrunk uniformly to 8 bits, which preserves model accuracy.

What can go wrong

What can go wrong

Calibration data does not match deployment. MicroMix measures error thresholds using a small sample of text (like WikiText2). If the model later sees very different text when running, the thresholds may not apply, and some layers could be under-protected. Fix: use calibration data that reflects the model's real use case.
Reordering adds latency if done naively. When channels have different precisions, grouping them together requires shuffling data. If this reordering is done outside the shrinking step, it kills the speed benefit. MicroMix solves this by integrating reordering into the shrinking operation, but other systems might not, and the paper's approach requires careful hardware integration.
Not all hardware supports all formats. The paper targets NVIDIA Blackwell, which has fast 4-bit, 6-bit, and 8-bit circuitry. Older graphics cards (Ampere, Turing) do not. Running MicroMix on incompatible hardware falls back to slower emulation and loses most of the speed gain.
Done right: layer-wise calibration adapts well. By choosing thresholds based on the actual output distribution of each layer (not a global one-size-fits-all rule), MicroMix adapts to the model's structure and tolerates small shifts in data distribution. This is why it generalizes well across different downstream tasks (zero-shot, code generation, math).
What a runnable demo should prove

What a runnable demo should prove

Build a small transformer (4 layers, 128 hidden size) that classifies text into 2 categories (like sentiment: positive vs negative). Train it on balanced data to 95 percent accuracy. Then: (1) shrink all weights uniformly to 4 bits and measure accuracy (it should drop, maybe to 60 percent). (2) Measure the output size distribution for each layer during a forward pass. (3) Compute thresholds for each layer such that small channels get 4 bits and large channels get 8 bits. (4) Implement the mixed-precision shrinking (manually, or via a library). (5) Measure accuracy again (it should recover to 90 percent or higher). This works because the protected layers no longer lose the critical precision they need to route the information correctly. (6) Measure wall-clock latency on the same graphics card: uniform 4-bit shrinking vs mixed-precision. You should see mixed-precision is only slightly slower than uniform 4-bit shrinking (within 10 percent) because the extra cost of the few protected layers running at 8 bits is small when most layers stay at 4 bits, yet accuracy is much better.

accuracy_gain = accuracy_mixed - accuracy_uniform, efficiency = average_bits_per_channel (should be 5 to 6 bits on real Llama models)

The demo makes it impossible to ignore that layer-by-layer precision allocation is more efficient than global: the same layer-by-layer tailoring that keeps accuracy high also keeps speed high, because most layers really are forgiving and can run at 4 bits.
