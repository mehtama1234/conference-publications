Transitive RL: Value Learning via Divide and Conquer

Break long-horizon robot tasks into smaller chunks, learn the value of reaching each chunk, then combine them to avoid bias errors that pile up in long sequences.

Paper explainersAll themesReinforcement Learning

Learning to control a robot over 1000 steps without human labels is hard because the algorithm has to guess the value of distant futures, and these guesses compound into massive errors. TRL breaks the task into divide-and-conquer: learn values for reaching halfway first, then combine those estimates into full-length estimates, cutting the error buildup from 1000 steps down to just 10.

The Bias Accumulation Wall

In offline goal-conditioned reinforcement learning, you have recorded robot trajectories (no rewards labeled) and want to learn a policy (a decision rule) that can reach any state from any other state as quickly as possible. Today's standard method is temporal difference (TD) learning: you guess that the value (the expected minimum steps from state A to state B) equals the immediate step reward plus the value from the next state. The problem: you chain these guesses 1000 times in a row, and every small error in one guess feeds into the next guess, and the next, like a towering stack of balancing blocks. After 1000 steps, tiny errors become huge errors.

A beginner tries Monte Carlo instead: average the actual rewards over many full trajectories to sidestep chaining guesses. This works but introduces huge variance: some trajectories get lucky (short, smooth paths), others get unlucky (long detours), and the model oscillates trying to fit both. The paper argues there is a third way: divide the long trajectory in half, learn the values for each half independently, then merge them using a mathematical property that short-path distances obey (the triangle inequality).

In one sentence. Use the triangle inequality of shortest-path distances to merge estimates from two equal-sized trajectory chunks, avoiding both bias cascade and high variance.

The algorithm as a flow

What it actually does

Take a trajectory

You have a robot path (s0, s1, ..., s1000) from recorded data.

Recursively split it in half

Divide into (s0 to s500) and (s500 to s1000); apply the same split to each half.

Learn values for all chunks

Train the value function on all the trajectory segments you created, from length 2 up to length 1000.

Merge using triangle inequality

Combine two sibling chunk values using the constraint that taking a detour costs at least as much as a direct path.

Extract a policy

After all values converge, train an action policy (what to do at each state) to maximize the learned values.

What the paper changes

The Single Change

The paper replaces the TD backup rule (chaining one-step guesses) with a merge rule: instead of asking the model to guess from state A to state C in one chain, ask it to sum up the guesses from A to an intermediate state B, plus B to C, then apply a soft constraint (the triangle inequality) that forces this sum to be at least as large as the direct guess A to C.

The hidden quantity

The Hidden Quantity: Bias Accumulation Count

measured quantity  =  Number of chained guesses (recursion depth)

In standard TD, the bias accumulation count is how many times you chain one guess on top of another to estimate a long-distance value. For a trajectory of length T, you need T steps of chaining. In TRL, because you recursively divide the trajectory in half each time, you only need log2(T) levels of chaining. For a 1000-step trajectory, TD requires 1000 guesses in sequence; TRL requires only about 10.

The paper estimates this by tracking the recursion tree depth during training. Shallower trees mean errors have fewer steps to compound, so the final value estimates are closer to the truth.

Why it works

Why It Works: The Triangle Inequality Constraint

Here is the concrete reason TRL avoids both bias and variance. In shortest-path distance, a mathematical fact holds: the direct distance from A to C is always at most the distance from A to B plus B to C (you cannot take a shortcut by going through an intermediate point). This is the triangle inequality. TRL uses this fact as a soft constraint during training: when you learn values for reaching A to C, you also learn values for A to B and B to C. TRL gently nudges the values to respect the triangle inequality — if the direct A-to-C estimate is wildly larger than the sum of the two-chunk estimates, TRL penalizes that and fixes it.

This is clever because it combines the best of both worlds. Unlike Monte Carlo, you are not averaging over full-length trajectories (which have high variance because some paths are lucky, some unlucky). Unlike TD, you are not chaining 1000 guesses in a row (which have high bias). Instead, you are learning values at multiple trajectory lengths (from length 2 up to length 1000) and forcing them to satisfy a constraint that is mathematically guaranteed to be true. The constraint propagates information from short, stable estimates up to long, difficult ones.

Math after the picture

The Equation: Triangle Inequality Backup

First in words:

The loss for a pair of states si and sj is the squared error between the learned direct distance and the sum of two intermediate hops, weighted by a confidence score that depends on how certain the direct estimate already is.

Then the compact form:

loss = w(si, sj) * (Q(si, sj) - (Q(si, smid) + Q(smid, sj)))^2, where w(si, sj) = 1 / (1 + gamma * Q(si, sj))^lambda

Every symbol:

Q(si, sj)the learned minimum-step distance from state i to state j
smidan intermediate state roughly halfway between si and sj
w(si, sj)the weight for this training example (confidence score)
gammaa discount factor (how much future steps matter, typically 0.99)
lambdaa tuning knob for how strongly we enforce the constraint
A tiny worked example
Suppose Q(start, mid) = 5 steps (measured from data), Q(mid, goal) = 4 steps.
Then predicted Q(start, goal) via sum = 5 + 4 = 9 steps.
The actual Q(start, goal) direct estimate might be 12 steps (overestimate from noise).
Weight w = 1 / (1 + 0.99 * 12)^2 ≈ 0.004, a small weight because the direct estimate is high.
Loss = 0.004 * (12 - 9)^2 = 0.004 * 9 = 0.036.
This small loss nudges Q(start, goal) down from 12 toward 9, trusting the two-hop estimate instead.

The weight w down-regulates the constraint when the direct estimate is already large (uncertain), allowing flexibility; it tightens when direct and merged estimates are close (confident).

What can go wrong

What can go wrong

Intermediate states don't exist on the optimal path. If you pick smid but the actual shortest path never passes through smid, the triangle inequality estimate is loose (overestimate). TRL handles this by weighting each training pair by how likely it is; heavily biased pairs contribute less.
Very short tasks don't benefit. If the task is only 10 steps, the recursion tree is only 4 levels deep anyway. TD and TRL perform similarly because the bias accumulation is already small. TRL's advantage grows with horizon length.
Poor choice of lambda (the constraint strength) hyperparameter. Set lambda too high, and the constraint crushes the direct estimate (underfitting). Set it too low, and the triangle inequality does nothing. The paper introduces adaptive weighting to sidestep this, but tuning still matters.
Done right. Choose an intermediate state smid that is roughly central on the true shortest path, set lambda conservatively (start low, increase gradually), and combine TRL with off-policy safeguards (like behavior cloning) to avoid exploring states that were not present in the recorded data.
What a runnable demo should prove

What a runnable demo should prove

Build a simple navigation task: a 2D maze or a grid where the robot must reach a goal state from a random start state in the smallest number of steps. Collect 1000 random offline trajectories (no reward labels). Train three value functions side by side: one using TD, one using Monte Carlo, one using TRL. For each trained model, measure the error: run the learned policy on held-out test start-goal pairs and count how many actual steps the policy takes, versus the predicted minimum steps.

regret = measured_steps - predicted_min_steps (lower is better; zero means perfect prediction)

The demo should make it impossible to miss: TRL's regret stays flat as you increase the horizon length (maze size), while TD's regret climbs steeply because of cascading bias, and Monte Carlo oscillates wildly because of high variance.
