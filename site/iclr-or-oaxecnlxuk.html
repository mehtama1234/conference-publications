DaVinci: Visual-Structural Syntax for Scientific Diagram Parsing

DaVinci teaches a language-vision model to convert pictures of scientific diagrams into editable drawing code by first learning what visual shapes look like, then learning the rules for how to arrange them.

Paper explainersAll themesMultimodal

Scientific diagrams are raster images: pictures drawn with lines and boxes. To edit them, you need structured code—not the picture itself, but the drawing commands. Current vision-language models (models that read images and write text) struggle with this because they see thousands of different visual shapes and have no rules for organizing them into correct syntax. DaVinci solves this with a two-stage recipe: first, learn to recognize all the visual primitives—the basic marks and shapes; second, learn the grammar of how those shapes must be arranged in drawing code to make sense.

Zero assumption version

Why pictures are not enough

A scientific diagram is a raster image—a grid of colored pixels. A human can look at it and understand what it shows: nodes, arrows, labels, annotations. But a computer trained on text has never seen that exact image before. It has to guess what the shapes mean and how they relate.

A naive first attempt: treat the diagram like any other image, run it through a vision model, and have the model output the drawing commands (like TikZ code) all at once. This fails because the model has seen thousands of different ways to draw a circle, thousands of fonts and line widths, and no explicit rule for which shapes are essential and which are just the artist's choice. It produces code that draws something that looks vaguely right but is syntactically broken or missing structure. The grammar of drawing code—"a node comes before the arrow that points to it"—is invisible in the pixels.

In one sentence. The model learns visual shapes and their structural rules separately, in two stages.

The algorithm as a flow

What it actually does

Stage one: supervised learning

Train on high-quality diagram-to-code pairs (TikZ30K). The model learns to map pixel patterns to visual primitives.

Extract shape tokens

For each region of the diagram, classify: is this a circle, line, label, etc.?

Generate code skeleton

Predict the order and arrangement of shape codes—e.g., "define node, draw arrow, add label."

Stage two: reinforcement learning

Use a reward that checks: does the code compile? Does the rendered code match the input picture? Is the syntax correct?

Refine via reward feedback

Nudge the model toward sequences that maximize the combined reward, learning the grammar implicitly.

What the paper changes

The thing the model learns to change

The model outputs a sequence of drawing commands (tokens of code). The paper changes what those tokens are and in what order they appear. Specifically, it adds explicit learning of the structural dependencies—which shape must be defined before which other shape, based on the visual layout and the rules of the drawing language.

the object it moves  =  The order and syntax of code tokens
The hidden quantity

What the paper actually measures: structural coherence

measured quantity  =  Structural coherence: how many output sequences compile and match the picture

The hidden quantity the paper measures is structural coherence—the fraction of generated drawing code that (1) compiles without errors, (2) renders back to something that looks like the input diagram, and (3) follows the drawing language's syntax rules. This is not visible in the pixels. It only matters when you run the code.

The paper estimates it by checking: does the generated TikZ code run without crashing? When rendered, does it match the original image? This is how they score each sequence during reinforcement learning.

Why it works

Why two stages fixes the grammar problem

The first stage (supervised learning on TikZ30K) gives the model a vocabulary: it memorizes thousands of pixel-to-shape mappings. A node looks like a circle, a connection is a line, a label is text. This is not the hard part—modern vision models are good at this.

The hard part is grammar: knowing that node code must be written before the arrows that reference it, that closing braces must balance opening ones, that certain shapes cannot be nested inside others. A vision-only model sees none of this in the pixels—it sees the final rendered picture, not the causal order of the code that made it.

Stage two (reinforcement learning) teaches the structural rules by rewarding code that works. Each time the model generates a sequence of drawing commands, the reward function runs the code and checks three things: Does it compile? Does the rendered image match the input? Is the syntax valid? Sequences that pass all three get high reward; broken ones get low reward. Over time, the model learns which orderings lead to reward and which lead to failure. It discovers the grammar implicitly, not by studying a textbook of rules, but by practicing and getting feedback.

The reward function that teaches the grammar

First in words:

reward equals visual fidelity plus structural consistency plus code correctness, multiplied by a learning weight

Then the compact form:

R = alpha * visual_fidelity(image, rendered_code) + beta * structural_consistency(code) + gamma * syntax_correctness(code)

Every symbol:

visual_fidelity(image, rendered_code)how closely the rendered code matches the input diagram (0 to 1)
structural_consistency(code)does the code follow the drawing language's rules for ordering and nesting (0 to 1)
syntax_correctness(code)does the code compile without errors (0 to 1)
alpha, beta, gammaweights controlling how much each component matters in the reward
A tiny worked example
Sequence A: node code, arrow code, label code. Renders correctly, all checks pass. visual_fidelity=0.95, structural_consistency=1.0, syntax_correctness=1.0.
Reward_A = 0.4*0.95 + 0.4*1.0 + 0.2*1.0 = 0.38 + 0.4 + 0.2 = 0.98 (excellent).
Sequence B: arrow code, node code (wrong order). Renders incorrectly, arrow points to nothing. visual_fidelity=0.3, structural_consistency=0.0 (violates ordering), syntax_correctness=1.0.
Reward_B = 0.4*0.3 + 0.4*0.0 + 0.2*1.0 = 0.12 + 0.0 + 0.2 = 0.32 (poor).
The model sees that Sequence A scores far higher and learns to avoid wrong orderings.

The reward pulls the model toward code that compiles, renders correctly, and respects the drawing language's hidden grammar.

What can go wrong

What can go wrong

Overfitting to TikZ30K. If stage one memorizes shape patterns specific to the training data, the model fails on diagrams with unusual visual styles or fonts it has not seen. Mitigation: diversity in the training dataset.
Reward hacking. The reinforcement learning phase can learn to output code that passes the reward checks (compiles, renders) but produces a technically correct but semantically nonsensical diagram. Mitigation: the visual fidelity reward penalizes this, but it requires careful tuning.
Structural ambiguity. Some diagrams have multiple valid code orderings. If the reward treats only one as correct, the model may learn a narrow solution and fail to generalize to alternate valid structures.
Done right. When TikZ30K is diverse, the reward weights are balanced, and the structural rules are well-specified, the model learns genuine grammar, not brittle memorization.
What a runnable demo should prove

What a runnable demo should prove

A simple demo: take a scientific diagram (a flow chart, a network diagram, a graph with labeled nodes), run it through DaVinci, and capture both the generated TikZ code and the re-rendered image. Measure three quantities: did the code compile? How visually similar is the re-rendered image to the input? Is the code syntactically valid? Report all three scores. Then, manually edit the generated code—change a color, move a label, add a note—and show the updated diagram. This proves the output is truly editable code, not a locked raster image.

success = (compiles_ok AND visual_fidelity > 0.8 AND syntax_ok) / num_diagrams

The demo must prove that the output is code, not a picture: it should be edit-able by a human in a text editor and produce correct output.
