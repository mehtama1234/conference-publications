Differentially Private Continual Release with Relative Error

Streaming data can be released more accurately under privacy if you allow errors that scale with the true answer, but only when the data stream is not chosen adversarially.

Paper explainersAll themesLearning Theory

Imagine you are collecting data from a sensor over time and need to quietly release the sum or the smallest value so far, but you must hide individual measurements to protect privacy. Under strong privacy rules (differential privacy), you must add random noise. The catch: with only additive noise (a fixed number added regardless of how big the answer is), the error becomes a smaller and smaller fraction of the true answer as the stream grows, but the absolute error stays big. This paper shows the error becomes a fixed fraction of the true answer if you allow relative error (errors that scale with the true answer) — because noise that scales with the answer stays in proportion to it — but only if you trust that the stream was generated openly, not by an adversary trying to break your algorithm.

Zero assumption version

Streaming sums under privacy are noisy

When you release aggregate data (the sum of all values, the minimum so far) from a live stream while keeping individual records private, you must add random noise to prevent someone from reverse-engineering a person's data. This is called differential privacy.

A beginner's first attempt: add the same noise every time you release a new aggregate. But as the stream grows, the noise stays the same while the true answer grows — the relative error gets better because the fraction (noise divided by answer) shrinks as the answer gets larger. If the true sum is 1000 and you add noise between -50 and +50, you get a relative error of 5%. But if the true sum is 100, your error is now 50%, and if the true sum is 1, your noise obliterates it.

The core bind: to hide individual records, you need a minimum amount of noise that depends on the number of people and how sensitive each person's data is — but not on how big the true answer is. So for small true answers, the noise dominates. For large answers, the noise becomes negligible, but now the privacy guarantee has gotten weaker over time (because noise distributes the same amount of privacy across a larger sum). The error cannot be reduced without breaking privacy.

The problem. A constant additive noise term makes private sums useless when the true answer is small, and the privacy bound decays as the stream grows.

What the paper changes

The noise rule

The paper changes how noise is added to released sums. Instead of a fixed amount each time, the noise scales: it grows with the true aggregate value. This lets small sums be released accurately (because noise is also small) while large sums accept proportional error (because the true answer is large enough to absorb the noise).

the object it moves  =  Noise size (scales with aggregate)
The hidden quantity

The separation: adaptive vs. non-adaptive

measured quantity  =  Error gap between honest and adversarial streams

The core hidden quantity is the error gap: how much worse must an algorithm perform when an adversary can choose future values, compared to when the stream is pre-determined and honest. For selecting the minimum cumulative value, this gap is huge; for selecting other values, the gap is small.

The paper measures this gap by proving upper and lower bounds. Upper bounds are algorithms that achieve small error on non-adaptive streams. Lower bounds are mathematical proofs that show no algorithm can do better against adaptive adversaries because an adversary can always craft data to force large error; they prove what must be true in the worst case. When the upper bound (what is possible) differs from the lower bound (what is necessary), a separation exists.

Why it works

Why relative error saves you (when the stream is honest)

Imagine you release the sum of a stream. With additive noise (always ±50), small sums drown in noise. But here is the trick: if you scale the noise to the sum itself, both get bigger together. A sum of 100 gets noise ±10, and a sum of 1000 gets noise ±100. The relative error (noise divided by true sum) stays constant around 10% across all sizes.

Why does this work? Because the constraint on noise comes from privacy, not from trying to match the true answer. Privacy says: 'You must add enough noise that removing one person's data cannot be detected.' This amount does NOT depend on the sum's size, only on how many people and how sensitive each person's data is. By making noise proportional to the sum, you satisfy privacy (you use the minimum required noise) while shrinking the relative error as sums grow.

But here is the catch: this only works if you trust that the data source cannot predict your algorithm. If an adversary can see your algorithm and choose their data values to exploit it, they can pick values designed to make your noise-scaling scheme fail. For example, they can inject huge spikes followed by tiny values, forcing you to either hide those spikes (breaking privacy) or admit large relative errors. Only on non-adaptive streams (where data is drawn from a fixed distribution that cannot see your method) can you safely use relative error.

Math after the picture

The noise formula

First in words:

Noise added equals a privacy constant divided by the true aggregate, then multiplied by a random factor. When the aggregate is larger, noise is smaller in absolute terms, but the relative error stays bounded.

Then the compact form:

Release = TrueAggregate + (C / |TrueAggregate|) * Z

Every symbol:

ReleaseThe noisy value you publish
TrueAggregateThe actual sum (or min, or other aggregate) on the stream
CPrivacy constant: depends on how many people and data sensitivity, not on aggregate size
ZRandom noise, distributed symmetrically around zero
|TrueAggregate|The absolute value (magnitude) of the true sum
A tiny worked example
Suppose C = 100 (privacy cost) and you release the sum of three values: 50.
Noise to add: (100 / 50) * Z = 2 * Z. If Z ranges from -50 to +50, noise ranges from -100 to +100.
Relative error: 100 / 50 = 200%. This is bad because the true sum is small.
Now suppose the stream grows and the sum becomes 1000.
Noise to add: (100 / 1000) * Z = 0.1 * Z. With the same Z range, noise is now -5 to +5.
Relative error: 5 / 1000 = 0.5%. The error shrinks as the sum grows, because noise scales down.
Privacy is preserved because the noise scale (100 / aggregate) depends only on the privacy constant C, not on adversary choices.

The ratio C/TrueAggregate means small aggregates get large relative error and large aggregates get small relative error, but the absolute noise never violates the privacy bound.

What can go wrong

What can go wrong

Adversary knows your algorithm. If an adversary can see how you choose noise, they can craft data to exploit it. For example, they can send huge values early, then tiny values later, forcing a dilemma: either hide the spikes (leak privacy) or admit huge relative errors.
Selecting the minimum is harder. When the task is to report the minimum cumulative value so far, relative error fails under adversarial selection. An adversary can make the minimum arbitrarily small, which would require infinite noise to maintain relative error bounds while preserving privacy.
Small aggregates still suffer. Even on non-adaptive streams, if the true aggregate is small (e.g., a sum of 5), relative error bounds may still require large noise. The guarantee is about shrinking relative error as the stream grows, not about making absolute error small.
Non-adaptive streams only. The paper's gains apply only when you can assume the stream was drawn from a fixed distribution before your algorithm was designed. If data arrives live and the source can adapt, you must fall back to additive error bounds.
What a runnable demo should prove

What a runnable demo should prove

Build a simulator that generates a non-adaptive stream (e.g., Gaussian-distributed values) and an adaptive stream (adversary picks values given your algorithm). Implement both fixed additive noise and scaled relative noise. For each stream, release the cumulative sum with privacy noise and measure the error as a percentage of the true sum. Plot error over time for both approaches on both stream types.

RelativeError = |ReleasedValue - TrueAggregate| / |TrueAggregate| * 100%

The demo must show that on non-adaptive streams, relative error shrinks as the sum grows because noise stays in proportion to the answer, while additive error stays constant in magnitude (relative error improves as the answer gets bigger); on adaptive streams, the adversary can prevent relative error from shrinking by crafting data that exploits any algorithm you use.
