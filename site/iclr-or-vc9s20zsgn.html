Cost-of-Pass: Economic Evaluation of Language Models

A framework that measures language models not by accuracy alone, but by the actual money you spend to get a right answer.

Paper explainersAll themesDatasets & Benchmarks & Evaluation

Every AI system in business has two sides: it must be smart enough to solve your problem, but also cheap enough that you make money running it. Right now we measure models mostly on test accuracy (does it get the right answer?), but we ignore the cost (how many predictions does it take?). This paper builds a single metric that combines both: the cost-of-pass, which is the expected dollar amount you pay to get one correct solution. Using this lens, the paper discovers that different model sizes win at different jobs—tiny models for simple math, huge models for knowledge tasks, and reasoning-heavy models for hard puzzles.

Zero assumption version

The trap of accuracy-only metrics

Today we score language models with one number: accuracy on a test set. Did it answer 85 out of 100 questions right? Great, it is 85% accurate. But this number hides a dirty secret. A tiny model might get 80 questions right in one forward pass each (100 token predictions per question). A massive model might get 90 questions right but needs to think through 5,000 tokens per question. In the real world, you pay for every token prediction. A tiny model earning 80% at 100 tokens costs you about a penny per correct answer. A huge model earning 90% at 5,000 tokens costs you fifty cents per correct answer. Yet accuracy alone would suggest the huge model is better, because 90 looks higher than 80 on any scorecard, with no accounting for the speed difference.

A beginner's first fix: just measure accuracy plus cost and pick the model with the best trade-off manually. But this breaks immediately. For some tasks (like simple arithmetic) you actually want the tiny model, because it gets nearly everything right on the first try. For others (like remembering historical facts) the huge model is cheaper, because it was trained on so much text that it almost never fails, so the cost of retries stays low. For hard reasoning problems (like multi-step logic), a specialized reasoning model pulls ahead, because the extra thinking lets it solve them with fewer failed attempts. You cannot pick one model for all jobs. You need a single metric that lets you ask: for THIS task, which model gives me the most value per dollar?

In one sentence. The paper formalizes cost-of-pass: the expected dollar cost to get one correct answer, and uses it to find which model class wins at which task.

The algorithm as a flow

What it actually does

Step 1: Score each model

Run a model on a test set and measure accuracy (fraction of questions answered correctly).

Step 2: Count token cost

Record how many token predictions each model makes to answer each question (including wrong attempts).

Step 3: Compute cost-of-pass

Multiply your actual token cost per prediction by the expected number of tries until a correct answer.

Step 4: Find the frontier

For each task type, record the lowest cost-of-pass across all available models.

Step 5: Compare to human expert

Estimate the cost of hiring a human expert to solve that task; declare victory if an AI frontier beats the human cost.

What the paper changes

What the paper changes

The paper shifts how we measure a language model's utility: from accuracy alone to a single number combining accuracy and token cost. The object is the evaluation metric itself—what we choose to optimize for when picking a model for a real application.

The hidden quantity

The hidden quantity: cost-of-pass

measured quantity  =  cost-of-pass

The hidden quantity is the expected dollar cost to get one correct answer from a model. It combines two pieces of information. First, your accuracy: if the model is 80% accurate, it takes on average 1.25 tries to get a right answer (one divided by 0.8). Second, your token cost (the price you pay per prediction): if each prediction costs $0.0001 and the model needs 5,000 predictions average to answer, that is $0.50 per question. So cost-of-pass on a task where the model is 80% accurate and needs 5,000 predictions average is 1.25 times $0.50, which is about $0.63 per correct answer.

The paper estimates this by running each model on a benchmark (a standard test set of questions in that domain) and tracking both the accuracy and the token consumption. It then measures the frontier cost-of-pass as the minimum cost across all available models for each task, revealing which model class (tiny, large, or reasoning-focused) wins on each task type and how that frontier has shifted month by month over the past year.

Paper reading. The paper formalizes cost-of-pass as: take one, divide by your accuracy rate, multiply by how many predictions you need, multiply by the cost per prediction. Why it works

Why knowing cost-of-pass matters

Accuracy and speed are in tension. A tiny model is fast (few tokens) but error-prone. A huge model is accurate but slow. Accuracy alone rewards the huge model even when it costs ten times as much. Cost-of-pass reveals the true trade-off by converting both accuracy and speed into a single unit: dollars per correct answer. Once you have that number, you can ask a simple business question: does the value I get from this answer exceed what I pay?

The mechanism works in layers. First, the paper runs each model class (lightweight, large, reasoning-heavy) on tasks that favor that class (lightweight on basic math, large on trivia, reasoning on multi-step logic). Each model's cost-of-pass is driven by two levers: how often it gets the answer right (accuracy) and how many tokens it burns to get there (speed). Second, the paper tracks the frontier—the cheapest model for each task—over time (month by month across a year). This reveals whether progress is happening and where. Third, the paper uses counterfactual analysis: it re-computes the frontier while pretending one model class does not exist, showing which innovations (smaller models, smarter models, reasoning models) actually pushed the frontier forward.

Math after the picture

The cost-of-pass equation

First in words:

expected dollar cost per correct answer equals total tokens times cost per token, divided by accuracy

Then the compact form:

cost_of_pass = (average_tokens / accuracy) * cost_per_token

Every symbol:

cost_of_passexpected dollars you spend per one correct answer
average_tokensaverage number of token predictions the model makes per question
accuracyfraction of questions the model gets right, between 0 and 1
cost_per_tokenwhat you pay per token prediction (e.g. $0.0001 for a large model)
A tiny worked example
Scenario: a test set with 100 questions.
Tiny model: gets 80 questions right (accuracy = 0.80), uses 100 tokens per question average.
Cost-of-pass = (100 / 0.80) × $0.0001 = 125 × $0.0001 = $0.0125 (about 1.25 cents).
Huge model: gets 95 questions right (accuracy = 0.95), uses 5000 tokens per question average.
Cost-of-pass = (5000 / 0.95) × $0.0001 = 5263 × $0.0001 = $0.5263 (about 52.6 cents).
Same task, but tiny model is 42 times cheaper per correct answer.
On a task where tiny model loses accuracy badly, the gap might shrink or reverse.

The numerator (tokens / accuracy) grows when models are slow or inaccurate; multiplying by the actual per-token cost converts this to dollars spent per right answer.

What can go wrong

What can go wrong

Token cost estimates drift. If you use an old price per token (e.g. from six months ago) but models have gotten cheaper, your cost-of-pass is too high, because you are overstating how much you actually pay. The frontier will not move as fast as reality. You must update pricing regularly as model providers lower costs.
Accuracy measured on the wrong benchmark. If your test set is easy (or tailored to one model's training data), all models will look equally good and cost-of-pass differences vanish. The frontier is only as useful as your benchmark. A tiny model trained on arithmetic will look great on math tasks but terrible on trivia.
Hidden costs in model answering. Some models (like reasoning-heavy ones) do extra prediction work behind the scenes (e.g. extra reasoning chains, external tools). These predictions may not show up in your count, so cost-of-pass underestimates. You must track the real end-to-end prediction cost, not just the visible model predictions.
Done right. Use current pricing for your inference provider (or your own hardware cost), measure accuracy on a realistic benchmark that spans multiple task types, count all tokens (including retries and reasoning chains), and update the frontier monthly to spot real progress versus noise.
What a runnable demo should prove

What a runnable demo should prove

Build a small benchmark: a curated list of 20–50 questions spanning three task types (simple math, factual recall, multi-step reasoning). Run three off-the-shelf models (one tiny, one large, one reasoning-focused) on each question. For each model-question pair, record whether the answer was correct and count the tokens. Compute cost-of-pass for each model on each task type. Plot a bar chart showing cost-of-pass per task type, with one bar per model. Then, do a counterfactual: recompute the frontier (best cost per task) while removing the reasoning-model class, and show how much more expensive the remaining models are.

cost_of_pass = (sum of tokens on task) / (count of correct answers) * (your cost per token)

The core insight is that a tiny model can be 10–50x cheaper on simple tasks even when less accurate, because simple tasks need few retries; but a reasoning model becomes cheaper on hard problems despite higher per-token cost, because it solves them correctly the first time more often.
