HYPER: Foundation Model for Inductive Link Prediction with Knowledge Hypergraphs

A model learns to predict missing facts in knowledge hypergraphs by encoding both the entities involved and their positions, so it works on brand-new entities and relation types never seen during training.

Paper explainersAll themesGraph & Geometric Learning

A knowledge hypergraph is a database of facts involving groups of entities (e.g. a drug, a protein, a disease are related in a treatment interaction). The challenge is to predict missing facts involving entities or relation types never seen during training. HYPER learns position-aware encodings so it transfers across unseen entities and across different types of relations, no matter how many entities each relation involves.

Zero assumption version

The mismatch between training and reality

Knowledge graphs (databases of facts like Einstein invented the theory of relativity) are always incomplete. Real-world hypergraphs go further: they record facts involving groups of entities (e.g., drug A, protein B, disease C are linked in a treatment process). Predicting missing facts is called link prediction.

Existing methods assume the vocabulary is fixed: you know all the entity names and all the relation types before you start training. But in reality, new facts involving entities not seen during training (such as a newly discovered protein) or relation types not seen during training (such as a newly observed biological process) arrive all the time. The model must generalize to these unseen cases, a challenge called inductive learning.

A naive solution trains the model only on the old facts, then tests it on new facts. It fails because the model has no way to represent entities it never encountered during training, and no learned pattern for relation types it never observed.

The method in one sentence. HYPER encodes each entity in a hyperedge along with its position in that group, so the same entity can be understood differently depending on its role, and the model learns patterns that work for any number of entities in a relation.

The algorithm as a flow

What it actually does

Encode each entity

Turn each entity name (e.g., drug A) into a list of numbers.

Tag by position

Pair the entity encoding with a tag for its position in the hyperedge (position 1, 2, 3...).

Combine position-aware entities

Pool or mix all the position-entity pairs to form a group representation.

Score candidates

Score all possible missing entities against the group representation to rank predictions.

Learn transfer patterns

During training, learn which position patterns predict which entity types, so patterns generalize.

What the paper changes

The one thing that changes

The paper changes how entities are encoded at test time. Instead of looking up an entity name to find a fixed learned list of numbers (a vector), the model now encodes the entity on the fly and combines it with a position tag that tells it what role this entity plays in the hyperedge. This lets the model represent entities unseen during training and adapt to relation sizes never encountered, without retraining.

the object it moves  =  entity-position encodings
The hidden quantity

The hidden quantity: position-aware generalization capacity

measured quantity  =  Position transfer score

This paper measures an implicit quantity: how well does the model transfer to unseen combinations of entities and positions? It is the fraction of test hyperedges involving entities not seen during training or relation arities not seen during training on which the model's top-ranked prediction is correct.

The paper estimates this by constructing new test datasets where 1) entities are not seen during training or 2) relation arities are not seen during training, then observing the model's accuracy. A higher transfer score means the position-aware encoding learned patterns that generalize broadly.

Why it works

Why it works: learning from position, not identity

Traditional models learn a fixed mapping: entity dog gets the list of numbers [0.5, -0.2, 0.8]. When a new entity cat arrives at test time, the model has no list for it and fails. HYPER sidesteps this by learning to encode position roles instead. During training, it observes patterns such as: in a 2-way relation, position 1 usually holds a noun describing an agent; in position 2, the noun describes an action. It learns these position patterns and their implications. At test time, when an unseen entity arrives, the model encodes it as a list of numbers based on its role (position 1, so apply agent-like patterns), not its name. The same learned position rules apply to unseen entities because the rules describe what position 1 does, not specific entity names.

For varying arities: a model trained only on 2-way and 3-way relations never observes 4-way facts. But HYPER learns an abstract principle: combine position-encoded entities by pooling their signals. This combining rule is general — it works whether there are 2 or 5 entities. At test time, the same combining procedure extends automatically to 4-way or 5-way relations, because it is not hardcoded to 2 or 3, just to the flexible pattern of position plus entity plus combine.

Math after the picture

The position-aware scoring equation

First in words:

For each candidate entity and each position in the hyperedge, compute a score by mixing the candidate's encoding with the hyperedge's pooled representation weighted by how well that position matches. The final score is the sum of per-position matches.

Then the compact form:

score(c, h) = sum_{p=1}^{arity} [ encode(c) · (position_weight_p + pool_other_entities_at_p) ]

Every symbol:

ccandidate entity (the entity we are guessing)
hthe hyperedge (group of entities with a relation type)
encode(c)numeric vector representation of entity c
position_weight_plearned vector for position p
pool_other_entities_at_pcombined encoding of all entities at position p in the hyperedge
·dot product (sum of element-wise products)
aritynumber of entities in the hyperedge
A tiny worked example
Hyperedge: [drug A, protein B, disease C] (3-way relation).
Candidate: drug D (never seen in training).
encode(drug D) = [0.2, 0.5, 0.1] (learned general encoding for drug-like entities).
position_weight_1 = [0.8, 0.0, 0.3] (position 1 usually holds a drug).
pool(protein B, disease C) = [0.3, 0.4, 0.2] (pooled representation of other entities).
Match at position 1: [0.2, 0.5, 0.1] · ([0.8, 0.0, 0.3] + [0.3, 0.4, 0.2]) = [0.2, 0.5, 0.1] · [1.1, 0.4, 0.5] = 0.22 + 0.20 + 0.05 = 0.47.
Similarly compute matches at positions 2 and 3.
Final score = 0.47 + (match at pos 2) + (match at pos 3).

Each position has its own learned pattern, so the model recognizes that drug D fits position 1 even though it never trained on drug D, because drug D has the encoding signature of a drug-like entity.

What can go wrong

What can go wrong

New entity type completely unlike training examples. If a new entity has no signal in common with any training entity (e.g., a plant-based ingredient when training only saw chemical drugs), the model's general encoding will be far off. The position tag alone may not rescue it.
Arities far outside training range. If training saw only 2-way and 3-way relations but test includes 10-way relations, the pooling operation may not generalize smoothly. The learned position weights were only exercised at small arities.
Position semantics shift between relation types. If position 1 means agent in some relation types and patient in others, the model will learn a confused position encoding and transfer poorly. Position universality breaks down.
Done right. When entities cluster semantically (drugs are drugs, proteins are proteins) and positions have consistent roles across relation types, the model transfers smoothly. The position pattern becomes a reusable schema.
What a runnable demo should prove

What a runnable demo should prove

Build a small knowledge hypergraph (e.g., 50 unique entities, 3 relation types at arities 2, 3, and 4). Train HYPER on 80% of the hyperedges. Hold out 20% of the hyperedges as test, but create three test sets: (1) hyperedges using only entities and relations seen during training, (2) hyperedges using entities not seen during training but with relation types seen during training, (3) hyperedges using entities not seen during training and relation arities not seen during training. Measure the model's prediction accuracy (top-1 or top-10) on each test set.

inductive_score = (correct in novel-entity set + correct in novel-arity set) / (size of novel-entity set + size of novel-arity set)

A working demo makes it impossible to miss: the model's accuracy barely drops when entities are new, and the drop is small even when arities are new, because it learned position patterns, not entity identities.
