EVMbench: Evaluating AI Agents on Smart Contract Security

Measure whether agents can find, fix, and exploit smart contract flaws in a live local blockchain setup.

Paper explainersAll themesAgents & Tool Use

Smart contracts control real money, so security mistakes matter immediately. If agents can read code, run tests, and interact with a blockchain environment, then they may be useful for defense and dangerous for attack. EVMbench studies both sides. It gives agents curated contract vulnerabilities and grades whether they can detect the flaw, produce a repair, or build an exploit that changes the chain state in the intended way.

Why smart contract agent risk is hard to measure

A chat answer about code security is not enough to estimate real capability. An agent may describe a vulnerability correctly but still fail when it must inspect repositories, run checks, patch code, or trigger the flaw against a working chain state. Security work is procedural because success depends on actions that change program behavior, not only on explanations.

That gap matters for both safety and usefulness. If evaluation stops at text analysis, we cannot tell whether an agent can actually help auditors or actually raise operational risk because both outcomes depend on whether it can change live contract behavior. The paper therefore turns smart contract security into an end-to-end agent task with concrete grading.

The paper's move in one sentence. Use curated vulnerabilities plus a local Ethereum execution environment so that agents are graded on real detection, repair, and exploitation outcomes rather than on text answers alone.

The algorithm as a flow

What it actually does

Curate real vulnerability cases

Collect flawed contracts from many repositories so that the benchmark reflects real security patterns.

Set up executable tasks

Provide tests and a local Ethereum environment so that agent actions can be checked against actual program behavior.

Evaluate three modes

Ask agents to detect the flaw, patch the flaw, or exploit the flaw because these tasks capture defensive and offensive capability separately.

Use programmatic grading

Check whether the patch passes or the exploit changes the expected chain state so that grading depends on behavior instead of prose.

Compare systems across the same cases

Report how often agents succeed end to end so that security capability can be tracked over time.

The important hidden quantity is exploitability or repairability in the live environment. A text explanation can sound correct while missing a condition that decides whether the flaw can really be triggered or fixed. The benchmark therefore asks whether the agent's reasoning survives contact with running code and chain state.

By checking live outcomes, EVMbench distinguishes shallow recognition from operational capability. That matters because security risk grows when an agent can turn an idea into a working exploit, and security usefulness rises when it can patch the flaw without breaking intended behavior.

Why it works

Why this works

The benchmark works because it ties agent claims to executable checks. A patch only counts if the contract still behaves correctly after the flaw is removed. An exploit only counts if it produces the intended chain effect. This structure filters out shallow answers because the environment demands behavioral evidence.

The three-mode design also matters because detection, patching, and exploitation are related but not identical skills. A system may find a flaw yet fail to repair it cleanly, or it may understand how to attack without being able to write a safe fix.

A simple security score

First in words:

Measure each task by whether the agent identified the flaw correctly and whether its chosen action changed program behavior in the intended way.

Then the compact form:

score = w_find * find_ok + w_action * action_ok ; action_ok <= behavior_check

Every symbol:

scoreoverall score for one security task
find_ok1 if the vulnerability is identified correctly, else 0
action_ok1 if the patch or exploit works as intended, else 0
behavior_check1 if programmatic tests confirm the expected change in contract behavior or chain state
w_findweight on diagnosis
w_actionweight on the executable security action
A tiny worked example
A contract allows a repeated withdrawal because account state is updated too late.
An agent points to the correct function, so find_ok = 1.
It then writes an exploit that calls the function repeatedly before the balance is reduced.
The local chain test shows that funds were drained, so behavior_check = 1 and action_ok = 1.
With w_find = 0.3 and w_action = 0.7, score = 0.3 * 1 + 0.7 * 1 = 1.0.
If the agent had named the flaw correctly but failed to produce a working exploit or patch, the second term would stay at 0.
The benchmark weights action heavily because real security capability depends on behavior, not only diagnosis.

The paper uses task-specific programmatic grading, but this equation captures the same principle: executable success matters most.

What can go wrong

What can go wrong

Benchmark cases may not cover every vulnerability class. A curated set improves realism, but unseen flaw patterns can still be missed because smart contract security is broader than any fixed case list.
Local chain tasks simplify deployment reality. An exploit that works locally may face extra constraints on a public chain, so the benchmark measures important capability without covering every operational detail.
A patch can overfit the tests. If the grading checks are narrow, an agent may pass without producing a generally correct fix, so broad behavior tests matter because they reduce false confidence.
Done right. Pair curated cases with executable checks on detection, patching, and exploitation so that each score reflects real behavioral security skill.
What a runnable demo should prove

What a runnable demo should prove

Build three contract tasks: one arithmetic bug, one access-control bug, and one repeated-withdrawal bug. For each task, provide a local chain setup and tests for both intended behavior and attack behavior. Let agents attempt diagnosis and then either write a fix or an exploit. Record whether the flaw was found and whether the submitted code changed behavior as intended.

The demo should prove that smart contract capability must be measured end to end because a convincing explanation is much easier than a working repair or a working exploit.
