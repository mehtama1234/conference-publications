SparseEval: Efficient Evaluation of Large Language Models by Sparse Optimization

Most benchmark samples are wasted; SparseEval picks just the informative few and reweights them to estimate the full score.

Paper explainersAll themesDatasets & Benchmarks & Evaluation

Evaluating a large language model on a full benchmark takes weeks of computing. But the paper shows that a small set of handpicked questions can estimate the final score almost as well. The trick: find which questions actually separate good models from bad ones, weight them by importance, and skip the rest.

Zero assumption version

Why full benchmarking is stuck

A large language model (a system trained to answer questions) is tested on a benchmark: a collection of, say, 5000 questions. The model answers every one, and you average the scores. That average tells you how good the model is. But running the model 5000 times on 5000 questions costs months of computer time.

A naive approach: just test fewer questions. But pick randomly, and you get unlucky—you might sample only easy questions that every model aces, so you cannot tell the difference between a good model and a bad one. Or you sample only hard questions, and even good models fail. You need questions that let you see real differences.

In one sentence. SparseEval picks the most informative questions and reweights them so they stand in for the full benchmark.

The algorithm as a flow

What it actually does

Step 1: Scan the data

Test a sample of models on all 5000 questions, record which score on what

Step 2: Find candidate anchors

Identify questions where model scores vary most; these separate quality

Step 3: Optimize weights

Nudge the weights downhill step by step to find the best weight for each anchor so predictions match observed full scores

Step 4: Refine the set

Swap out low-value anchors for new candidates if it improves prediction accuracy

Step 5: Estimate new model scores

For any new model, test it only on the anchors, compute the reweighted average, and read off the full-benchmark score

What the paper changes

What the paper changes

The paper shifts from testing a model on all 5000 questions to testing it on a small set of anchor questions and computing a reweighted average of those scores.

the object it moves  =  anchor selection and weighting
The hidden quantity

The hidden quantity: Anchor Importance

measured quantity  =  Anchor Importance Score

An Anchor Importance Score is a single number attached to each benchmark question that says how much that question helps you tell good models from bad. A high score means the question is a strong signal: models that are good usually pass it, bad models usually fail. A low score means the question is too easy (everyone passes) or too hard (everyone fails) or noisy (results do not track overall quality).

SparseEval estimates this by looking at which questions show the biggest correlation between model quality and a correct answer. The paper then uses these scores to decide which questions to keep and how much to weight them when predicting the full score.

Why it works

Why reweighting anchors works

At the heart: some questions are useless noise (everyone passes them), and some are pure signal (they separate good models from bad). If you randomly sample questions, you get a mixture—most are noise, so the random average is unreliable.

SparseEval's move is to find the signal questions (the anchors) and ignore the noise. Then it reweights: if anchor A separates quality really well, give it weight 2.0. If anchor B is noisier, give it weight 1.0. When you compute the average of these reweighted anchors, the signal questions dominate, and the estimate becomes reliable. The paper optimizes these weights by gradient descent: nudging each weight up or down to make the anchor-based estimate match what the full benchmark says. Over many iterations, the weights converge to the right values, and a new model's anchor-only score predicts its full score.

Math after the picture

The reweighting formula

First in words:

Estimated full score equals the sum over all anchors of each anchor's weight times that anchor's score, divided by the sum of the weights

Then the compact form:

estimated_score = sum_a ( w_a * score_a ) / sum_a ( w_a )

Every symbol:

estimated_scoreprediction of what the model would score on the full benchmark
w_athe importance weight assigned to anchor question a
score_athe binary score (0 or 1) for anchor question a (0 = wrong, 1 = correct)
sum_athe sum over all selected anchor questions
A tiny worked example
Suppose the model answers 3 anchor questions: Q1 correct, Q2 wrong, Q3 correct.
The weights found by gradient descent are: w1 = 2.0, w2 = 0.5, w3 = 1.5.
Numerator = 2.0 * 1 + 0.5 * 0 + 1.5 * 1 = 2.0 + 0 + 1.5 = 3.5
Denominator = 2.0 + 0.5 + 1.5 = 4.0
Estimated score = 3.5 / 4.0 = 0.875 (87.5 percent).
If the full 5000-question benchmark says the model scores 86 percent, the sparse estimate is accurate.

The gradient descent optimization tunes each weight so the weighted average of anchors matches the true full-benchmark average; this drives down error.

What can go wrong

What can go wrong

Anchors become stale as models evolve. The questions you chose as anchors might have been perfect for ranking Claude-3 vs GPT-4, but when a new model family comes out with a different weakness, those anchors may no longer separate quality well. The Anchor Importance Scores need periodic recomputation.
The gradient descent optimization can overfit. If you have very few anchor questions and many models in your training sample, the optimized weights might chase noise in that sample and fail on held-out models. You need enough models in the initial scan to learn stable weights.
Correlated benchmark questions fool the method. If all your benchmark questions test the same skill (e.g., all are arithmetic), they are not independent. The method assumes each question is a separate signal; redundant questions waste your sparse budget and corrupt the weights.
Done right. Recompute anchors whenever you benchmark a new model family, use held-out models to validate the weights, and ensure your benchmark questions test diverse skills so each one is a fresh signal.
What a runnable demo should prove

What a runnable demo should prove

Build a toy benchmark: 1000 synthetic test questions graded by a simple rule (e.g., whether the model output contains the word target). Train 20 models of varying quality (e.g., by fine-tuning on different amounts of data). Run the full benchmark on all 20 models, recording their exact scores. Then: (1) Run SparseEval to find the 50 best anchor questions and their weights. (2) For a new 21st held-out model, test it only on the 50 anchors, compute the reweighted average, and predict its full-benchmark score. (3) Run the model on the full 1000-question benchmark and record the true score. (4) Report the prediction error (difference between estimated and true score) and check that the estimated rank matches the true rank.

Mean absolute error = average absolute difference between predicted score and true full-benchmark score across held-out models

The demo must show that SparseEval's 50-anchor prediction is within 2-3 percentage points of the true score, while random 50 questions miss by 6-8 points.
