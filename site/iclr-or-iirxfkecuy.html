PAT3D: Physics-Augmented Text-to-3D Scene Generation

A system that reads a text description and builds a 3D scene where all the objects sit stably without floating, overlapping, or tipping over.

Paper explainersAll themesGenerative Models & Diffusion

When you ask an AI to build a 3D scene from words, it usually creates objects that hover in mid-air, pass through each other, or stack impossibly. PAT3D fixes this by adding physics to the scene. Instead of just generating pretty 3D shapes, it runs a gravity simulator to settle everything into a stable, physically real arrangement—like shaking a box of wooden blocks until they stack naturally.

Zero assumption version

The floating-object problem

Text-to-3D systems today rely on vision models and language models to imagine 3D objects from words. They are good at making things look pretty, but they ignore gravity and solid matter. So a table and chairs from the same prompt often end up floating, overlapping, or impossibly balanced—things that could never actually exist.

A naive first attempt would be to just add constraints after the fact: slide objects around to avoid overlaps, push things down toward the floor. But this breaks what the language model decided. The scene stops matching the prompt. And even when you squeeze out overlaps, nothing guarantees that a stack of books will not tip over when the wind blows.

The core problem. Language models generate objects that ignore physics; they float, overlap, and balance impossibly. Pushing them into place breaks the semantic meaning.

The algorithm as a flow

What it actually does

Step 1: Draw a picture

Create a rough 2D sketch showing where each object sits (table on floor, chairs near table).

Step 2: Generate 3D objects

For each object in the sketch, build a detailed 3D mesh using a vision model.

Step 3: Position them coarsely

Align each 3D mesh to its spot in the sketch, allowing overlap.

Step 4: Resolve overlaps and gravity

Run the physics simulator to push objects apart and settle them downward.

Step 5: Check and refine

Measure how much the scene changed. If it drifted from the prompt, optimize to keep both physics and meaning.

What the paper changes

What the paper changes

The paper replaces the final loose object-placement step with a tightly coupled physics simulator. Instead of stopping once objects are generated and roughly positioned, PAT3D runs a gravity-and-contact engine that moves every object's position until the entire scene reaches static equilibrium—the state where nothing accelerates, everything is at rest. The system optimizes the initial positions so that when the simulator settles the scene, the result matches the original prompt as closely as possible while obeying physics absolutely.

The hidden quantity

The hidden quantity: static equilibrium balance

measured quantity  =  equilibrium violation (how far from zero acceleration)

As the physics simulator runs, each object accelerates according to gravity, contact forces, and friction. An object is in equilibrium when all those forces cancel out—it has zero acceleration and stays put. If a table is floating, the forces do not cancel (gravity pulls it down but nothing supports it), so it is out of equilibrium.

PAT3D measures equilibrium by computing the forces on each object at each time step. If the total force on an object is close to zero, it is stable. If it is large, the object is sliding or falling. The system tracks how far from equilibrium each configuration is, and during optimization, it updates the initial positions to make the final settled state as close to equilibrium as possible. This is the hidden quantity that separates a physical scene from a floating hallucination.

Why it works

Why it works: feedback from physics

The core insight is that physics is ground truth. If you place objects to satisfy gravity and contact forces, they will stay put. PAT3D uses this as feedback: it generates a coarse layout from the language model, then lets physics answer the question 'Does this make sense?' If objects overlap or float, the simulator moves them. Then PAT3D measures how much the positions changed and works backward to adjust where it started—earlier, before physics ran—so that when physics runs next time, the final scene is closer to both the prompt and physical reality.

This is not trial-and-error. The paper uses automatic differentiation (a technique that computes how one small change ripples through the equations) to trace backward from the final resting state through the physics solver to the initial positions. It is like running the simulator in reverse to ask: 'If I want the table to end up at this location, where should I place it initially, accounting for how gravity will pull it?' This tight coupling—physics-in-the-loop, feeding back into the generator—ensures the final scenes both obey physical laws and stay faithful to the prompt.

Math after the picture

The equilibrium equation

First in words:

At each time step, the sum of mass times acceleration plus forces (gravity, contact, friction) equals zero. The simulator solves backward to find the position and velocity at the next time step that satisfy this balance.

Then the compact form:

M(q_n+1 - q_tilde_n) + dt^2 * (grad_Psi(q_n+1) + grad_B(q_n+1) + grad_D(q_n+1, q_n)) = 0

Every symbol:

q_n+1position and rotation of all objects at the next time step
q_tilde_npredicted position at this step (including gravity acceleration g)
Mmass matrix (how heavy each object is)
dtsize of one time step in simulation
grad_Psigradient of potential energy (gravity pulling things down)
grad_Bgradient of contact constraint (pushing objects apart when they touch)
grad_Dgradient of damping energy (friction and air resistance)
dt^2dt multiplied by itself (determines how fast forces accumulate per step)
A tiny worked example
Imagine a book resting on a table. At time step n, both are at rest.
Gravity pulls the book downward. The potential energy gradient (gravity) is roughly 9.8 newtons downward.
The table pushes the book upward with an equal contact force. The contact gradient is 9.8 upward.
These cancel: grad_Psi + grad_B ≈ 0. The mass term M(q_n+1 - q_tilde_n) is also zero (no acceleration).
The equation is satisfied. The book stays put. It is in equilibrium.
Now imagine a book resting on nothing (floating). Gravity is 9.8 down, but contact is zero.
The equation is not satisfied: 0 + dt^2 * 9.8 ≠ 0. The book accelerates downward.
The simulator moves the book down in the next step until it touches the floor. Then contact kicks in and equilibrium is restored.

The equation encodes Newton's laws (force equals mass times acceleration). PAT3D solves it thousands of times, each time moving objects closer to stable rest. Then it optimizes the starting positions so the final resting state both obeys physics and matches the prompt.

What can go wrong

What can go wrong

Ambiguous reference image. If the 2D sketch is unclear about object order (what is on top of what), the scene tree gets wrong. Simulation then stacks objects in the wrong hierarchy. Solution: the system should prompt the language model to clarify depth order before placing objects.
Impossible spatial constraints. If the prompt says 'a chair floating above a table' and 'the chair rests on the floor,' these conflict. Physics cannot satisfy both. The system will choose one (usually gravity wins). Solution: detect contradictions early and ask the user for clarification.
Over-optimization to prompt at the cost of physics. If the weighting in the loss function heavily favors semantic match, the optimization might move objects just enough to match the prompt but leave them barely stable (e.g., a chair balanced on one leg). Solution: enforce a hard constraint that equilibrium violation must be below a threshold, never trade it away.
Done right. The system maintains a clear two-stage process: (1) semantic generation with the VLM, (2) physics-driven optimization that tweaks positions minimally to obey gravity and contact, ensuring the final scene both matches the prompt and is simulation-ready. No artificial balancing acts.
What a runnable demo should prove

What a runnable demo should prove

Build a simple kitchen scene generator. User gives a text prompt like 'A kitchen with a round table, two chairs, and a stove.' The system generates the objects, runs PAT3D's optimization for 50 iterations of physics settling plus backpropagation, and outputs the final positions. Measure both (a) how well the scene matches the input prompt (does it have the right objects in the right rough areas?) and (b) how physical it is (can a rigid-body simulator run for 10 more seconds without objects passing through each other or falling over?). The demo should show the scene before and after PAT3D optimization—the before is floating chaos, the after is stable and grounded.

prompt_match_score = (objects generated correctly) * (spatial relations preserved); physics_score = (no penetrations after 10 simulation seconds) * (all objects at rest); the demo succeeds if both are above 90.

The breakthrough moment: watch a floating object sink to the floor in real-time as the simulator runs, then watch the backpropagation adjust the initial position so next time, that object lands correctly on first try.
