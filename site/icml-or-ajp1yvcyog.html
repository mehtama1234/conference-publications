XSkill: Continual Learning from Experience and Skills in Multimodal Agents

XSkill lets a multimodal agent keep improving from past runs by storing both short action guidance and larger reusable skills, each tied to what the agent actually saw.

Paper explainersAll themesAgents & Tool Use

A multimodal agent often faces two kinds of repeated knowledge. One kind is local: on this kind of screen or image, this next action usually helps because a similar visual cue has already signaled the same next move before. The other kind is procedural: for this kind of task, these steps in this order usually work. XSkill stores both. It extracts concise experiences for local guidance and broader skills for task-level guidance, then retrieves them using the current visual observation so that past knowledge stays connected to the situation that needs it.

Zero assumption version

Why multimodal agents waste past experience

A multimodal agent may solve many tasks and still fail to improve much from them. One reason is that past runs are stored as raw histories without being turned into guidance that can be reused. Another reason is that retrieval often ignores the current visual scene, so the agent pulls back advice that matched the old text but not the old observation.

XSkill treats continual improvement as a storage-and-retrieval design problem. It asks what kind of knowledge should be stored, how it should be tied to visual evidence, and how it should be brought back when a new observation resembles an old one.

The paper's move in one sentence. Store two streams of reusable knowledge, short experiences and larger skills, tie both to visual observations, and feed later usage back into the storage loop so that the agent keeps learning from its own history.

The algorithm as a flow

What it actually does

Step 1: Gather multi-path runs

Collect several attempts on the same task so that the system can compare weak and strong behavior.

Step 2: Distill two knowledge streams

Extract short experiences for local action guidance and larger skills for task-level guidance.

Step 3: Tie them to visual observations

Store each item with the relevant visual context because later retrieval should depend on what the agent is actually seeing.

Step 4: Retrieve and adapt during later tasks

Bring back the most relevant experience and skill items when a new task observation matches them.

Step 5: Feed usage back into storage

Use later success and failure signals to refine what stays in memory, so that continual learning does not stop after one round.

The hidden quantity

The hidden quantity: observation-knowledge fit

measured quantity  =  how well a stored experience or skill matches the current visual situation that triggers retrieval

The hidden quantity is observation-knowledge fit. A stored hint only helps if it matches what the agent is seeing now, because otherwise retrieval becomes generic and the wrong past advice returns.

XSkill improves this fit by grounding both experiences and skills in visual observations and by updating memory from later usage. That matters because continual learning is only useful when the right past knowledge comes back in the right current scene.

Why it works

Why it works

The two-stream design matters because one memory type cannot do every job well. Short experiences are good for local moves such as what to click or inspect next. Larger skills are good for preserving the broader procedure across a full task.

Visual grounding matters because multimodal tasks are scene-dependent. The same text instruction can require different actions on different screens or images. By tying memory to what was seen, XSkill improves retrieval precision when the agent faces a similar observation later.

The continual loop matters because memory quality should evolve. Later usage reveals which stored items remain helpful and which should be revised or dropped, so the system gets better by reusing its own history rather than by only collecting more raw episodes.

Math after the picture

A compact continual-memory objective

First in words:

Keep experiences and skills that match the current observation well and that improve later task success when reused.

Then the compact form:

J = E[ reuse_gain(E_t, S_t | obs_t) - alpha * mismatch_cost - beta * stale_memory_cost ]

Every symbol:

Jthe expected continual-learning objective
E_tthe retrieved experience items at task step t
S_tthe retrieved skill items at task step t
obs_tthe current visual observation and task state
reuse_gain(E_t, S_t | obs_t)improvement from using the retrieved experience and skill items in the current situation
mismatch_costpenalty when retrieved items do not fit the current observation
stale_memory_costpenalty for keeping old items that no longer help later tasks
alphaweight on wrong retrieval
betaweight on stale memory
A tiny worked example
A web navigation agent has solved several checkout tasks before.
On a new page, the current observation shows a shipping form that matches one stored local experience and one stored checkout skill.
The experience says where the delivery option usually appears, and the skill says the broader order of steps for finishing checkout.
Together they shorten the search and avoid a wrong detour, so reuse gain is high.
If an old memory points to a page layout that no longer matches, it raises mismatch cost and should be revised or removed later.

This compact objective captures the paper's main point: stored knowledge is valuable when it matches the current visual situation, because matched retrieval can guide the current step and still support later tasks.

What can go wrong

What can go wrong

Visual grounding is too loose. If a stored item is linked to a vague observation, later retrieval may return it in the wrong scene because the visual match is too weak.
The two streams duplicate each other. If experiences and skills store nearly the same content, memory becomes bloated because the split is no longer helping different levels of guidance.
Old memory is never revised. A stale item can keep hurting later tasks because continual learning keeps reusing advice that no longer matches new environments.
Done right. The approach works when observation grounding is precise and later usage updates the memory store, because then the right local hint and the right broader skill come back together.
What a runnable demo should prove

What a runnable demo should prove

Build a small multimodal benchmark with repeated web or desktop tasks where each task includes both visual state and tool actions. Let one agent store only raw histories. Let another extract observation-grounded experiences and skills, retrieve them on later tasks, and update the memory store after reuse. Include a few changed layouts so that visual grounding matters.

The demo should show better transfer and lower task time for the dual-stream agent because the right local hint and the right broader procedure are both available when the current scene matches past work.

reuse_success = helpful_retrievals / total_retrievals ; transfer_gain = solved_after_memory - solved_without_memory

The decisive evidence is that grounded dual-stream memory improves later tasks, because both local guidance and broader procedure are retrieved in the scenes where they actually fit.
