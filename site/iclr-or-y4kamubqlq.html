Local Success Does Not Compose

LLMs write correct specs for one function but fail catastrophically when functions must talk to each other through shared data.

Paper explainersAll themesDatasets & Benchmarks & Evaluation

LLMs are very good at writing specifications (the mathematical guarantees) for single functions in isolation: syntax error rates near zero, verification rates above 50%. But the real world does not work in isolation. When a program chains multiple functions together—where the output of one feeds into the input of the next—today's LLMs fall apart. DafnyCOMP is a benchmark that exposes this gap by asking LLMs to write specifications for multi-function programs, and it finds a stunning collapse: verification rates plummet from 58% to 3.69%. This paper argues that current LLMs lack the architectural capacity to reason about how constraints propagate across function boundaries.

The single-function illusion

Imagine you write a Python function that takes a list of numbers and returns the sum. You want a computer to prove that your code is correct. To do that, you write a specification: a formal contract saying 'if you give me a list of positive integers, I promise to return a value greater than zero.' An LLM can write such a specification very accurately. But here is the catch: real software does not consist of one isolated function. It is a chain. Function A calls Function B, which calls Function C. The output of A becomes the input to B; the output of B becomes the input to C. Each step must preserve the promises made by the previous step. Beginners might try training an LLM on more single-function examples, or asking it to write specifications one at a time without thinking about how they fit together. This breaks because the specifications for A, B, and C interact through shared data flowing from one to the next. If A promises that its output will be positive, but B's specification does not account for that promise, the entire chain shatters.

Current benchmarks mask this weakness. They measure how well LLMs handle one function in isolation—and the results look great: over 99% of generated code is syntactically correct, and over 50% of specifications pass formal verification. But these benchmarks are not testing the hard part: multi-function reasoning.

The method. Build a benchmark (DafnyCOMP) with 300 programs, each made by chaining 2 to 5 real functions together with their actual data dependencies, then ask LLMs to write the formal specifications. When you run it, the specs collapse.

The algorithm as a flow

What it actually does

Assemble

Take 2–5 independent functions from LeetCode, combine them in a chain by matching data types.

Translate

Convert the Python chain to Dafny (a formal-verification language), strip the specifications.

Synthesize

Run the program through Dafny's verifier, strengthen specs iteratively until it passes.

Challenge

Give the bare Dafny code to an LLM and ask it to regenerate the specifications.

Measure

Count how many specs pass formal verification. Compare single-function baselines to compositional chains.

What the paper changes

The thing that breaks: cross-function reasoning

The paper changes one thing: the scope of the specification task. Instead of asking the LLM to write a spec for one function, it asks the LLM to write specs for multiple functions that must coordinate through shared data.

the object it moves  =  the scope: from one function to multiple functions
The hidden quantity

The hidden quantity: compositional reasoning capacity

measured quantity  =  Compositional reasoning across function boundaries

The paper does not reduce reasoning to a single number, but it measures three failure modes that reveal a deeper incapacity. Specification fragility: the spec for function A might be too weak (does not promise enough) or too strong (promises more than the code can deliver), leading to downstream functions receiving mismatched inputs. Implementation-proof misalignment: the LLM writes code that works, but the specification does not describe the actual code behavior—they are talking past each other. Reasoning instability: when chaining functions, the LLM loses track of invariants (the facts that must remain true after each step), leading to broken proofs.

The paper estimates this by measuring what fraction of chains verify and then drilling into where the breaks occur. It finds that 39.2% of failures are fragility, 21.7% are misalignment, and 14.1% are instability. These three categories together explain why compositional tasks fail so dramatically—the LLM lacks an internal model of how data constraints flow through a chain.

Why it works

Why LLMs fail at compositional specs

Here is the core: attention mechanisms (the core of how transformers work—the way the model attends to relevant parts of the input) are designed to capture local dependencies: 'If I see a variable x on line 5, find where x was defined on line 3 and use both together.' But specifications for chained functions require bidirectional reasoning: 'Function A promises to output positive integers; does B's spec account for that? Does B's postcondition (what it promises to output) satisfy C's input requirements?' The transformer must track abstract guarantees across function boundaries, not just concrete tokens on a page. Transformers excel at pattern matching ('I have seen specs like this before') but not at principled proof construction ('Does this spec actually logically entail the next step?'). When functions are combined in ways the model's training data did not show, pattern matching fails. A spec that 'looks right' based on training patterns does not guarantee that it aligns with downstream code.

The paper shows that even the largest models (480 billion parameters) fail as badly as much smaller models (32 billion) at compositional tasks. This suggests it is not a matter of scale—the architectural primitives are missing. Transformers were not built to reason about compositional constraints; they were built to predict the next word given the previous ones. When you ask an LLM to reason about new combinations of functions it has never seen before (rather than matching existing patterns), it breaks down. The machinery to propagate a logical requirement backwards through a chain of functions simply is not there.

Formalism: the specification contract

First in words:

For each function, a Dafny spec has a precondition (input requirement), a postcondition (output promise), and loop invariants (facts that stay true during iteration). For a chain A then B, A's postcondition must imply B's precondition. If not, verification fails.

Then the compact form:

verify(chain) = A.postcondition => B.precondition AND B.postcondition => C.precondition

Every symbol:

A.postconditionwhat function A promises to output
B.preconditionwhat function B requires as input
verify(chain)whether the entire chain satisfies the proof checker
=>implies (logically entails)
A tiny worked example
Function A: given a list of integers, return the sum. Postcondition: result >= 0 (if all inputs >= 0).
Function B: given a number, return its square root. Precondition: input > 0.
LLM writes A's spec correctly: result >= 0. But B requires input > 0. Equality failed: >= is weaker than >.
Verifier rejects the chain because B might receive 0 from A (e.g., empty list sum), violating the requirement.

The math captures the core: compositional verification is about logical implication along a chain, not isolated correctness.

What can go wrong

What can go wrong

Specification fragility (39.2% of failures). The spec for one function is too weak or too strong. Weak: it does not promise enough, so the next function in the chain receives garbage. Strong: it promises more than the code delivers, making the proof impossible.
Implementation-proof misalignment (21.7% of failures). The code works correctly, but the spec does not describe it accurately. The LLM treats them as independent tasks: 'Write code that works' and separately 'Write a spec that looks right.' They do not talk to each other.
Reasoning instability (14.1% of failures). Over a chain of multiple functions, the LLM loses invariants: the facts that must stay true. A loop invariant is forgotten. A precondition needed three steps earlier is omitted.
Done right: manual specification. Humans can write compositional specs because they reason logically about constraints. They know that if function A outputs a list, function B must handle a list. This is not pattern matching; it is reasoning.
What a runnable demo should prove

What a runnable demo should prove

Build a mini suite: take any three simple functions (e.g., list-sum, integer-square-root, minimum-finder). Chain them: sum a list, take the square root of the sum, find the minimum across multiple summed lists. Ask an LLM to write Dafny specs for the chain. Run the Dafny verifier. Count how many of the three specs pass together. Then remove the chaining constraint: ask the LLM to spec each function in isolation. Verify each one separately. The contrast should be stark: high pass rate individually, zero pass rate jointly.

compositional_failure_rate = (pass_rate_single_func - pass_rate_chained) / pass_rate_single_func

The demo must make impossible to miss this truth: LLMs know how to write specs, but they do not know how to write specs that coordinate across function boundaries. It is not a skill gap. It is an architectural gap.
