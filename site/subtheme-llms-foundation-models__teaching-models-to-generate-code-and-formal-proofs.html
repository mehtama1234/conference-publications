Teaching models to generate code and formal proofs

These papers focus on training models to write working code and mathematical proofs by combining language models with formal verification and specialized reasoning techniques.

What this is

Most language modeling research focuses on open-ended tasks like writing essays or answering questions, where there are many valid answers. But writing code and mathematical proofs are different—the answer either works or it does not. Papers in this area teach models to generate code that actually runs and proofs that are logically sound. This requires combining language models with formal verification systems that check whether generated code compiles and runs correctly, or whether a proof follows valid logical rules. The model learns from feedback on correctness, which is much more precise than human judgment.

The challenge is that code and proofs have much stricter rules than natural language. A single typo breaks code, and a logical gap breaks a proof, which means there is no partial credit. Models trained on natural language have learned to be loose and approximate, which does not work here because approximate code does not run. Some papers add specialized training where models see many examples of correct code and proofs so they learn the stricter conventions. Others use symbolic reasoning tools alongside the language model—the language model generates a candidate solution and a formal system checks it. If it fails, the feedback is used to improve the model by showing exactly what was wrong. When feedback is precise and verifiable, the model learns much faster than learning from vague human preferences because the signal is clear.

The payoff is tools that can assist programmers and mathematicians by suggesting code and checking proofs. This is valuable because code generation is tedious and error-prone for humans, and mathematicians spend enormous time writing and checking proofs. Even models that are imperfect can save time by generating starting points that humans then refine. These models also demonstrate that language models can learn structured, precise behavior if given the right training setup, which raises the question of what other precise tasks can be learned the same way.

How the work breaks down

The work in this subtheme splits into several natural directions because different formal domains require different tools and feedback mechanisms. The first focuses on training models to generate code that actually works by checking the output against formal rules, because code either compiles and runs or it does not. The second tackles proving mathematical theorems using formal logic systems that can verify each step, because proofs require step-by-step logical correctness. The third addresses finding bugs in code and repairing them automatically, because even good code often has subtle errors that testing reveals. Finally, there is work on building better tests and benchmarks to measure whether models are actually generating correct solutions, because without clear metrics, it is hard to know whether generation techniques are actually working.

Code generation with verification

Writing code that runs is harder than writing text because a single typo breaks everything. The papers in this group tackle the challenge of teaching models to write working code by combining language models with systems that check whether the code is correct. When feedback is immediate and precise (either the code runs or it does not), models learn much faster than from vague human feedback—because the signal is unambiguous rather than subjective.

The Actions Speak Louder paper shows that when a model generates code step-by-step instead of just reasoning with words, it performs much better on understanding graph problems, especially when the input is complex, because concrete code forces the model to be explicit about each step rather than hand-waving. The Code World Models paper demonstrates that generating code as an intermediate step allows the model to build a verifiable description of how a game works, which then enables the model to plan several moves ahead rather than one move at a time, because the model can run the code to check whether each move leads to a winning position. The Formal Program Specifications paper reveals that testing the code against concrete examples is more effective than trying to prove theorems about it, because test cases give clearer feedback about what is right and wrong. The Huxley-Gödel Machine paper shows that a model can iteratively improve itself at writing code by generating candidates, testing them against actual problems, and learning from what fails, surpassing simpler self-improvement methods on a benchmark of real software engineering tasks, because each iteration provides concrete examples of the model's own mistakes.

These papers agree that the path forward is tight feedback loops between code generation and execution checking. The models work best when they can see immediately whether their output is correct or not, and adjust their strategy accordingly.

Formal proofs and theorem proving

Proving mathematical theorems is another area where models must be precise. In a proof, every step must follow logically from the previous steps, or the entire argument fails. These papers address the challenge of training models to construct logically sound proofs by integrating them with formal proof systems that verify each line of reasoning.

The Automated Formalization paper shows that when you augment a model with the ability to retrieve related definitions and theorems from a library, it performs better at converting informal math statements into formal, machine-checkable versions, because context from related work helps the model recall the right definitions. The Minimal Agent paper demonstrates that a much simpler proof-search system than earlier methods can achieve competitive results, suggesting that models do not need massive complexity to make progress on theorem proving, because the model can focus on high-level strategy and let the search process handle details. The Wilf-Zeilberger Guidance paper works on combinatorial identities—a specific narrow class of theorems—and shows that giving the model hints from symbolic mathematics tools helps it find proofs of classical identities in many more cases than an unaided model can, because the hints point the model toward fruitful search directions. The Editable Proof Sketch paper introduces the idea of letting the model write a rough outline of a proof first, then fill in details, rather than generating the full proof in one shot. This intermediate step dramatically improves success rates on formal mathematics benchmarks, because breaking the problem into stages makes each stage easier and gives the model checkpoints to verify its progress.

All four papers share a pattern: they give the model external tools or structure to help manage the complexity of formal reasoning, because formal reasoning requires precision that language models alone struggle to achieve. The model does the creative work of high-level strategy, while symbolic systems handle verification and guidance, so the human gets the best of both worlds—human-like creativity plus machine-verified correctness.

Testing, repair, and algorithm choice

Once a model has generated code, the next challenge is ensuring it actually solves the intended problem. These papers focus on finding bugs, repairing incorrect code, and understanding how models choose algorithms. The common thread is using execution—running the code and seeing what happens—to improve quality and diagnose problems, because running code reveals bugs that reasoning alone cannot catch and provides concrete examples of failure.

The UOJ-Bench paper reveals a striking weakness: when you show a model one incorrect program, it fails to spot the error more than half the time. However, when you let the model generate many candidates and test all of them, success rates jump above 90 percent. This means that diversity and testing matter more than getting the logic right the first time. The NEMO paper takes autonomous code generation and applies it to optimization problems, treating the act of writing and running code as the primary way to explore the solution space. The Rule2DRC paper proposes a method to systematically generate test cases that expose differences between correct and incorrect code, making it much easier for the model to pick the right solution. The Invisible Lottery paper uncovers a hidden bias: tiny changes in the prompt (words that sound similar but have slightly different meanings) cause models to shift dramatically in which algorithm family they choose, sometimes by nearly 100 percentage points. This matters because some algorithms are much faster or more secure than others, even if multiple solutions are technically correct.

These papers collectively show that execution-based feedback and test-case design are as important as the code generation itself. Models make progress not from perfection on the first try, but from being able to test, diagnose, and iterate.

Evaluating structured generation

Beyond generating code and proofs, a critical challenge is assessing whether generated output actually satisfies formal constraints. The VCG-Bench paper tackles a broader class of structured generation—not just code and proofs, but any output that must follow precise visual and logical rules.

This paper provides a systematic benchmark that reveals where current vision-language models fall short: they struggle to maintain exact formatting, follow complex instructions without drifting, and preserve fidelity to a specification. By establishing clear metrics for structural correctness, the work surfaces that generation is only half the problem. Ensuring the output meets formal requirements is equally hard and equally important as the generation process itself.

This work underscores that any system teaching models to generate structured outputs must include rigorous evaluation of whether outputs truly conform to the rules, not just whether they are plausible or close enough.
