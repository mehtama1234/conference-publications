APPFORGE: Can LLMs Build Real Apps?

A benchmark that shows whether LLMs can build complete Android apps from scratch, not just isolated functions.

Paper explainersAll themesDatasets & Benchmarks & Evaluation

Most code-generation tests give LLMs a single isolated function to write. But real apps are nothing like that—they need multiple components talking to each other, states that change over time, and features that play by the app platform's rules. This paper builds a benchmark of 101 real Android apps and tests whether large language models can actually construct entire working applications from a description.

The gap between function writing and real software

Today's code benchmarks test whether an LLM can write one isolated function correctly. The model gets a problem statement like 'write a function that adds two numbers' and either it works or it doesn't.

Real software is nothing like that. An Android app has dozens of parts—screens, data stores, background tasks, lifecycle rules—all wired together. A beginner LLM might generate syntactically correct code (the commas are in the right places) but miss that components need to coordinate, that data must stay consistent, or that the operating system has rules about how apps must behave. The model produces code that compiles but crashes at runtime, or code that never talks to the right database, or code that ignores the platform's lifecycle constraints.

The problem. No benchmark exists that forces LLMs to orchestrate multiple app components, maintain state across time, and respect the platform's rules.

The algorithm as a flow

What it actually does

Collect real apps.

Pull 101 complete Android apps from F-Droid, a repository of real open-source projects.

Extract app specs.

Read documentation and code to summarize what each app does in plain natural language.

Record realistic interactions.

Automatically navigate each app, capturing UI trees and user interactions as they happen.

Generate test cases.

Use an LLM to transform recorded interactions into test suites that verify functionality.

Grade the LLMs.

Ask each LLM to build the app from the spec, then check if it compiles, passes tests, and runs without crashing.

The hidden quantity

The hidden quantity: component coordination

measured quantity  =  How well components interact

The real thing that separates a working app from broken code is whether all the pieces fit together. An app might compile (the grammar is correct) but crash at runtime if the screen doesn't actually connect to the database, or if the lifecycle handler forgets to save state, or if two components send messages in the wrong order. That's the gap—it's not about writing one piece, it's about orchestrating many pieces.

APPFORGE measures this by running the app through realistic test scenarios. A test case says: 'click the login button, enter your password, wait for the network call, check if the home screen appears.' If the app fails any of these sequences, it shows that the components aren't coordinated.

Plain reading. An app works only if all its pieces talk to each other correctly. A test case proves this by running a sequence of user actions and checking that the app responds as expected.
Paper reading. The evaluation framework checks four metrics: compilation success (does the code have no syntax errors?), test pass rate (do the interaction sequences complete without assertion failures?), crash rate (does the app survive runtime?), and an overall effectiveness score.
Why it works

Why the benchmark works

A single function test is pass-fail: write the function or don't. But an entire app has dozens of interconnected pieces, each with its own failure mode. By automating the construction of test cases from real app behaviors, APPFORGE ensures that the test scenarios are realistic and comprehensive—they reflect what users actually do, not what a test designer dreamed up. By running these tests against LLM-generated code, the benchmark exposes coordination failures, state management bugs, and platform-specific blind spots that function-level tests would miss. The automation is key: once you have a real app and a description, you can record user interactions and convert them to test cases without human effort, scaling to 101 apps without burning out. The evaluation is reproducible: every LLM is graded the same way, with the same code, the same tests, the same platform.

The reason this reveals real limitations is that an LLM must now demonstrate not just coding competence but software architecture understanding. It must read a spec, decide which components to create, wire them together correctly, and respect the platform's constraints. A function-level task hides those failures because the problem is so narrow that the model can sometimes stumble into the right answer.

Evaluation metrics

First in words:

effectiveness_score = (compilation_success AND test_pass_rate AND app_stability) / number_of_requirements

Then the compact form:

effectiveness = (C * P * (1 - crash_rate)) / total_features

Every symbol:

C1 if code compiles, 0 otherwise
Pfraction of test cases that pass (0 to 1)
crash_ratefraction of tests that cause the app to crash (0 to 1)
total_featuresnumber of distinct app functionalities specified
A tiny worked example
App spec requires 5 features: login, home screen, database save, network fetch, logout.
Code compiles: C = 1.
Tests: login passes, home screen passes, database save crashes → 2 out of 3 passed so far.
Crash rate: 1 crash out of 3 test suites = 1/3.
P = 2/5 (only 2 of the 5 feature scenarios passed before crash).
effectiveness = (1 * 0.4 * (1 - 0.33)) / 5 = (1 * 0.4 * 0.67) / 5 = 0.27 / 5 = 0.054 or 5.4% on that spec.
A model that keeps code stable and test-passing would score higher; even one crash tanks the score on that benchmark problem.

The metric penalizes both compilation failure and any crash at runtime, making it a realistic measure of usable code.

What can go wrong

What can go wrong

Models use evasion instead of fixing. When the compiler reports an error, GPT-4 and Kimi-K2 often delete the entire function instead of debugging it. The error goes away, but so does the feature.
Platform-specific gaps. Several models failed to generate the 'android:exported' attribute required by Android 12, even though the spec mentioned it. The code followed old training data patterns, ignoring platform evolution.
State coordination breaks. An app might successfully log the user in, but then crash when trying to retrieve saved data, because the lifecycle handler that saves state on pause was never generated or wired up.
Done right. A working benchmark must force LLMs to handle compilation errors, platform updates, state consistency, and component wiring all at once—no shortcuts.
What a runnable demo should prove

What a runnable demo should prove

Pick one real Android app from F-Droid (a small one like a calculator, note-taking app, or to-do list). Write a natural language spec of what it does. Manually capture 5-10 user interaction sequences (click button, enter text, wait, check result). Ask an LLM to generate the full app code from the spec. Run it on an Android emulator. Count: (1) does it compile? (2) do your test sequences complete? (3) does it crash? (4) does the app state persist across pause and resume?

working_apps = (compiled AND tests_pass AND no_crashes) / total_specs

The point you cannot miss: even the best LLMs fail to build working end-to-end apps more than 4 times out of 5. The gap between function-level skill and system-level understanding is enormous.
