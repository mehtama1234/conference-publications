Multi-Agent Design: Prompts and Topologies Together

To design better multi-agent systems, optimize prompts and topologies together in the right order: first tune each agent's words, then reshape how they connect, then tune the whole system's words.

Paper explainersAll themesLLMs & Foundation Models

When you build a team of language-model agents (AI workers that talk to each other to solve a task), designing their instructions (prompts) and how they pass information (topology) matters a lot. This paper shows that you cannot optimize these in isolation. Instead, a smart three-stage process—tuning individual agents, reshaping their connection pattern, then tuning the whole team—beats methods that skip this choreography.

Zero assumption version

Multi-agent design is stuck in isolation

A multi-agent system is a team: several language models that each handle one job and talk to each other to solve a bigger task. You give each agent instructions (its prompt) saying what it does, and you design the topology (which agent talks to which) so their answers flow correctly.

The naive approach: tune each agent's prompt in a sandbox, ignoring how the whole system will work. Or: pick a fixed topology and hope it fits. The result: the final system is disjointed. Agents bump into each other; good individual prompts fail when teammates feed them bad data; the routing logic makes no sense for the problem.

The deeper problem: prompt sensitivity. Small wording changes in an agent's instructions can tank performance unpredictably. And changing the topology (adding an agent, removing a hop) breaks the prompt-tuning you already did. So you are stuck in a catch-22: you cannot finalize prompts without knowing the topology, and you cannot finalize the topology without knowing which prompts work.

The method in one sentence. Interleave three stages—tune each agent locally, reshape the topology, then tune the whole system—so each stage builds on the last.

The algorithm as a flow

What it actually does

Stage 1: Block-level prompt optimization

For each agent (a building block), tune its prompt independently to make it excel at its narrow job.

Stage 2: Workflow topology optimization

Treat the topology (the graph of who talks to whom) as a knob. Try different connection patterns and measure which one works best with the current prompts.

Stage 3: Workflow-level prompt optimization

With the new topology locked in, tune the system-wide prompts (like how agents are told to reason or hand off work) to fit the new shape.

Repeat if needed

The optimized outputs from stage 3 can feed back into stage 1 if time permits, tightening the spiral.

Deliver one optimized system

The result: a multi-agent team with tuned prompts and shaped topology that work together, not against each other.

What the paper changes

What the paper moves

The paper changes two concrete things: the text of each agent's prompt (its instructions and examples), and the topology (the directed graph that says which agent feeds its output to which other agents). Instead of treating these as independent levers, the method optimizes them as a coupled pair, in stages.

the object it moves  =  prompts and topology
The hidden quantity

The hidden quantity: topology-prompt fit

measured quantity  =  How well the prompts match the topology

Every multi-agent system has a hidden quantity: how well the prompts are tuned to the actual topology being used. If you change the topology but keep old prompts, fit plummets. If you change prompts without reshaping the topology, fit stays poor.

The paper measures fit implicitly through task performance on a validation set (the official metric). But the real insight is that fit is NOT the same as raw performance—a topology with poor fit will waste good prompts. MASS discovers fit by iterating: after each stage, it measures which configurations (prompt+topology pairs) score highest, and that high score signals good fit.

Why it works

Why it works: the three-stage dance

Here is the causal chain. First, prompt sensitivity means small wording changes wreck performance. If you tune all prompts at once in a fixed topology, you tune them as a bundle, and any topology change orphans them. So MASS starts small: tune each agent's prompt in isolation (stage 1). This gives you a baseline for each agent's competence.

Next (stage 2), you vary the topology. With the stage-1 prompts as a stable reference, you can now ask: does this new shape of information flow help or hurt? The topology is no longer a confounding variable; you are comparing like-with-like because the prompts are held constant during this search.

Finally (stage 3), the new topology is locked in. Now you know which agents will be talking to which. You can write system-level prompts (the glue instructions) that are tuned to THIS specific topology. The prompts in stage 3 are not reinventing the wheel; they are ironing out the wrinkles that the new topology exposed.

The win: by the end, prompts and topology are in sync. Neither is a poor fit for the other. The system is not as brittle.

The optimization objective

First in words:

For each stage, we choose the prompts or topology that maximize task accuracy (or reward) on a validation dataset, conditioned on the prior stages' best choices.

Then the compact form:

Stage_k = argmax_{config_k} Score(config_k | config_1...config_k-1, validation_data)

Every symbol:

Stage_kthe optimization stage (1=prompts, 2=topology, 3=prompts again)
config_kthe configuration being optimized in stage k (prompt text or topology edges)
Score(...)validation performance (accuracy, or aggregate of test metrics)
config_1...config_k-1the locked-in results from prior stages, kept fixed during stage k
A tiny worked example
Suppose an agent has 3 possible prompts: A (score 60), B (score 75), C (score 70). Stage 1 picks B.
Now suppose 2 topologies exist with prompts locked to B: topology X (score 75), topology Y (score 82). Stage 2 picks Y.
Now with topology Y, suppose 2 system prompts exist: X1 (score 82), X2 (score 88). Stage 3 picks X2.
Final system: prompt B, topology Y, system prompt X2, score 88. If we had done all at once (not staged), search space is 3*2*2=12 configs. Staged interleaving reduces wasted exploration: each stage narrows the search.

Each stage's choice is the best under the constraint that earlier stages are locked. This greedy-but-staged approach beats global search because it avoids the explosion of combinations to try.

What can go wrong

What can go wrong

Greedy selection at each stage can be suboptimal. The best choice at stage 1 might not be optimal for the final stage 3 score. MASS does not guarantee a global optimum. If the space is very non-convex, a different stage-1 choice could lead to a higher final score.
Topology search space can explode. If there are many possible topologies, stage 2 must sample them, not enumerate them. A poor sampling strategy wastes time on bad topologies and misses the good ones.
Prompt sensitivity still applies within each stage. Stage 1 tunes each agent's prompt, but if the prompt space is huge, local optimization can get stuck in a poor local minimum. Adding structure to the search (e.g., templated prompts with fillable slots) helps because it shrinks the space to explore, so the optimizer is less likely to miss a good region and has more budget left to fine-tune once it finds it.
Done right: interleave stages smartly. The paper's insight is that even though individual stages are greedy, the interleaving order matters. Fixing local prompts before changing topology is the key to avoiding the catch-22.
What a runnable demo should prove

What a runnable demo should prove

Build a small multi-agent system for a concrete task (e.g., solving math word problems by having one agent parse the problem, one sets up the equation, one solves it). Start with generic prompts and a fixed topology. Then run the three stages: (1) tune each agent's prompt in isolation, (2) try different topologies and measure which scores best, (3) re-tune the global coordination prompt. Measure the final task accuracy.

Final accuracy = (correct answers) / (total test problems) on a hold-out test set

The demo must show that accuracy is higher after all three stages than after stage 1 alone, proving that topology optimization (stage 2) and global tuning (stage 3) add real value when layered on top of local tuning.
