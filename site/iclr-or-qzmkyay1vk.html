Code2Bench: Dual Scaling for Honest Code Evaluation

Fresh code from real projects plus exhaustive testing reveals what code-generating models actually struggle with, not what they memorized.

Paper explainersAll themesDatasets & Benchmarks & Evaluation

Code-generating models are evaluated on old benchmark problems that have leaked into their training data, so scores measure memorization, not skill. Code2Bench fixes this by continuously pulling fresh, unseen code from GitHub and testing each solution against hundreds of automatically-generated test cases, catching an 'illusion of correctness' that simpler tests miss.

Zero assumption version

Static benchmarks become part of the training data

Today's code benchmarks use the same hundred problems year after year: HumanEval, LeetCode classics, GitHub Hall of Fame snippets. After years online, these problems are almost certainly in the training data of any new model.

A naive approach: 'Let's test the model on these problems.' This breaks because the test is not measuring whether the model can solve new problems—it is just measuring whether the model remembers this particular problem from training. The model's score is inflated memorization, not real reasoning.

The illusion of correctness. Old benchmarks look like the model is doing great at coding, but the model has seen these exact problems before.

The algorithm as a flow

What it actually does

Step 1: Pick fresh code

For each model, extract Python and Java functions from GitHub commits created after the model's knowledge cutoff date.

Step 2: Classify what the code does

Use formal program analysis (Scope Graph) to tag each function: Self-Contained (pure math logic) or Weakly Self-Contained (uses libraries like math, numpy).

Step 3: Build exhaustive tests

For each function, automatically generate hundreds of input-output pairs using Property-Based Testing (Hypothesis for Python, jqwik for Java).

Step 4: Enforce 100% coverage

Every path through the function's code must be exercised by at least one test case.

Step 5: Run and diagnose

Test models on each problem, record pass/fail per input, and visualize gaps between where models excel and where they fail.

What the paper changes

What changes: the test data and the rigor

The paper changes two things at once. First, it shifts the problem source from archived benchmarks to live GitHub repositories (only code committed after each model's knowledge cutoff). Second, it shifts test rigor from a handful of hand-written test cases to automated, exhaustive test generation that ensures every branch of code is hit.

the object it moves  =  problem sources and test coverage
The hidden quantity

The hidden quantity: the illusion of correctness

measured quantity  =  illusion of correctness: shallow-test performance minus deep-test performance

Most benchmarks use a single test case per problem (usually one example input-output pair). A model might pass that one test but fail on 20 other edge cases the test does not cover. The gap between 'passes the official test' and 'passes all edge cases' is the illusion—the false impression that the model is correct.

Code2Bench measures this gap concretely: for each problem, it records whether the model passes simple tests (few cases) versus rigorous tests (100% branch coverage). A model that scores 90% on simple tests but 70% on rigorous tests is suffering from a 20-point illusion.

Why it works

Why it works: freshness kills memorization, depth reveals real gaps

Memorization works only if the exact problem is in the training data. By pulling code committed after the model's knowledge cutoff date, Code2Bench uses problems the model mathematically cannot have seen during training. The model must solve it from first principles, not recall.

Memorization might also disguise itself: the model might get the right answer on the one test case the old benchmark runs, but for the wrong reason. It might fail on edge cases (negative inputs, empty lists, boundary values) that the old test does not check. Code2Bench's Property-Based Testing automatically composes hundreds of test cases, ensuring the model must handle the full spectrum of inputs. A model that relies on shallow patterns will break somewhere in that depth.

Together, these two moves work because fresh code forces the model to reason rather than recall, and exhaustive tests mean the model cannot get away with guessing right on just one case.

The correctness measurement: one problem, many tests

First in words:

accuracy = (count of test cases passed) / (total count of test cases)

Then the compact form:

accuracy_i = (1 / |T_i|) * sum_{t in T_i} I(model(f_i, input_t) == expected_output_t)

Every symbol:

accuracy_ithe true correctness score for problem i
T_ithe set of all test cases for problem i (hundreds, not one)
|T_i|the number of test cases (e.g. 247)
I(...)indicator function: 1 if the condition is true, 0 if false
model(f_i, input_t)the output the model produces
expected_output_tthe correct output for that input
sumadd up results across all test cases
A tiny worked example: one problem with 4 test cases
Problem: write a function that squares a number.
Test case 1: input 3 -> expected 9 -> model outputs 9 -> match (1 point)
Test case 2: input -2 -> expected 4 -> model outputs 4 -> match (1 point)
Test case 3: input 0 -> expected 0 -> model outputs 1 -> NO MATCH (0 points)
Test case 4: input 0.5 -> expected 0.25 -> model outputs 0.25 -> match (1 point)
Accuracy = (1+1+0+1) / 4 = 3/4 = 75%
The simple test (just input 3) would have shown 100%, but rigorous testing catches the zero-handling bug.

The difference between one test and one hundred tests is the gap between an illusion and the truth.

What can go wrong

What can go wrong

False freshness: code committed after cutoff but semantically old. A new GitHub commit might be a rediscovery of a classic algorithm, already in training via a textbook or research paper. Temporal filtering alone does not guarantee the problem is truly unseen by the model.
Test-generation bias: the Property-Based Testing libraries might miss edge cases. Hypothesis and jqwik generate tests based on type annotations and explicit strategies. If a bug only manifests on rare, complex inputs, automatic generation might not find it.
Language-specificity costs: separate prompt engineering per language. The framework requires tailored test runners and prompts for Python, Java, C++, etc. Scaling to 10 more languages requires 10 more engineering cycles.
Dependency classification brittleness: Scope Graph is sound but slow. Scope Graph analysis is more precise than AST traversal, but it requires full parsing and build-context. Large repositories with complex build systems might break the classifier.
Done right. Combine temporal filtering (problems from after cutoff) with semantic diversity (pull from many GitHub projects, not one) and measured validation (run Property-Based Testing to confirm 100% branch coverage actually happens).
What a runnable demo should prove

What a runnable demo should prove

Pick one Python function from a GitHub commit after GPT-3.5's knowledge cutoff (April 2023). Write a simple test (one example input-output). Then generate 50 test cases automatically using Hypothesis. Run a code-generating model on both. Plot the pass rate: the simple test shows one result, the exhaustive test shows a much harsher truth.

illusion_gap = accuracy_on_simple_test - accuracy_on_exhaustive_test

The illusion gap should be visibly large (at least 15-20 points), proving that one test case is not enough to trust a model's correctness.
