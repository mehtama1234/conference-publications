PolySkill: Generalizable Skills Through Polymorphic Abstraction

An agent learns reusable skills by writing abstract goals separate from concrete website steps, so one skill works across many sites.

Paper explainersAll themesAgents & Tool Use

LLM agents today learn skills tied to one website. If an agent learns to "fill shipping info" on amazon.com, that skill does not work on ebay.com. PolySkill fixes this: the agent writes a skill in two layers — an abstract goal ("collect and enter address") and concrete how-to steps for each site ("click field X, type address, click send"). This split lets one skill reuse on different sites.

Zero assumption version

Skills learn one website at a time

Today's LLM agents learn skills by watching examples: an agent is shown how to fill out a form on website A, so it learns a skill like "fill-shipping-form". The skill records the exact steps: click on the blue button labeled Ship To, type the address into the white box, submit. When the agent sees website B with a green button labeled Address, it has no idea the same logical task was learned before — the button looks different, the field colors differ, even the labels are new. The agent starts from zero.

A beginner would hope the agent just learns the abstract idea: "I need to collect the user's address and enter it somewhere". But today's systems record steps, labels, and visual details so tightly that each site becomes a new task. The skill refuses to transfer.

In one sentence. When an agent learns a skill on one website, it cannot use that skill on another website even if the task is logically identical.

What the paper changes

What the method changes

PolySkill changes how agents record skills: instead of storing steps with website-specific details, it stores two things. First, an abstract goal written in generic terms (no mention of buttons or colors or site names). Second, a concrete recipe for each website that achieves that abstract goal. The agent now moves skills from being glued to one website's appearance to being attached to a logical goal that many websites can satisfy.

the object it moves  =  skill representation
The hidden quantity

How much a skill abstracts away detail

measured quantity  =  abstraction level

The hidden quantity the paper measures is how much of a skill's logic is site-independent. A skill with low abstraction level is packed with details (button IDs, colors, field positions) from one website. A skill with high abstraction level strips away those details and keeps only the logical goal. PolySkill measures this by checking: when you take a skill from one website, how many of its concrete steps can be reused or adapted on a new website? If 80% of the abstract goal holds true, the skill is highly abstract.

The paper estimates abstraction level by watching agents learn on one website, then testing how much of the learned skill carries to new websites. They count: reuse events (agent recognizes the same abstract goal on a new site) and success rate on unseen sites (how often the abstract goal works when the agent tries it somewhere new). Higher reuse and higher success both indicate the skill captured something abstract, not just memorized details.

Why it works

Why decoupling makes skills reusable

A skill glued to details like 'click the blue button at pixel 237,418' is trapped. When a new website has a green button at pixel 412,180, the skill looks at the details, finds no match, and gives up. Decoupling breaks this trap. When the agent writes 'abstract goal: collect and enter the destination address', that sentence does not mention blue, pixels, or button shape. Later, on a new website, the agent can ask: does this page have a destination field? Yes. The abstract goal matches. The agent then looks up: what concrete steps accomplish this goal ON THIS WEBSITE? It finds the recipe for the new site and executes it.

The mechanism has two parts. First, during learning: when an agent learns a skill, it extracts a logical goal independent of the site's layout (this requires the agent to reason about what it is actually trying to accomplish, not just copy steps). Second, during reuse: when the agent encounters a new site, it compares the abstract goal to the new site's task, not the old site's button colors. Abstract goals are stable across sites. Concrete steps vary per site but are tied to an abstract goal, so if the goal matches, the steps can be found. The agent becomes a translator: given a goal and a new website, find the recipe that works on this website for this goal.

The reuse formula

First in words:

reuse_score = (number of skills recognized on new website) divided by (total number of learned skills), where recognition happens when the abstract goal matches the new site's task

Then the compact form:

reuse_score = sum_i (abstract_i matches new_site_goal) / total_skills

Every symbol:

abstract_ithe abstract goal statement of skill i
new_site_goalthe logical goal the agent sees on the new website
matches1 if abstract_i and new_site_goal are the same concept, 0 otherwise
total_skillsnumber of skills the agent has learned
reuse_scorefraction of learned skills that can be used on the new website
A tiny worked example
Agent has learned 10 skills: fill-address, click-checkout, enter-payment, add-to-cart, verify-email, search-product, apply-coupon, check-balance, select-shipping, confirm-order
On Website A (Amazon), agent learned all 10.
On Website B (eBay), agent checks each abstract goal: does eBay have a destination address field? Yes, fill-address matches. Does eBay have checkout? Yes. Payment? Yes. Add-to-cart? Yes. Search? Yes. Coupon? No. Balance? No. Shipping? Yes. Confirm? Yes.
Matches: 8 out of 10
reuse_score = 8 / 10 = 0.80
PolySkill achieves 1.7x reuse, meaning: naive system reuse_score = 0.47, PolySkill reuse_score = 0.80

The score counts how many learned skills have abstract goals that apply on a new website; higher scores mean more reusable skills.

What can go wrong

What can go wrong

Abstract goal written too narrow. If the agent writes 'collect the red address field labeled Destination', it has sneaked a site-specific detail into the abstract goal. The goal is no longer abstract. On a new website with a blue address field, the skill fails because the agent is still looking for red.
Concrete steps incomplete for a new site. If the agent learns a skill on Website A with a three-step form but Website B has a five-step form, the concrete recipe from A may not work on B. The recipe must be complete enough to adapt or the skill fails partway through.
Abstract goals that do not actually apply. The agent might think 'fill shipping address' matches a new website, but the website structure is so different that the abstract goal does not translate. The skill attempts to execute and fails because the logical concept was a false match.
Done right. When abstract goals are written in purely logical terms (no colors, buttons, or field names) and concrete recipes are specific enough for each site, one skill reuses 1.7x better because the agent can recognize the same abstract goal on a new website and then look up the concrete steps for that site.
What a runnable demo should prove

What a runnable demo should prove

Build a simple demo: take an agent that has learned 5 skills on Website A (e.g., add item to cart, fill address, apply coupon, select shipping, confirm order). Now give it Website B with a different layout but the same logical tasks. Measure: (1) how many of the 5 learned skills does the agent recognize and attempt on Website B (reuse count)? (2) Of the skills it attempts, how many succeed end-to-end? (3) Compare to a baseline agent that records concrete steps only.

reuse_success_rate = (skills recognized on Website B and completed successfully) / (skills learned on Website A)

PolySkill must show that abstract goals enable the agent to reuse learned skills on new sites without retraining because the goal is independent of the site's appearance, whereas naive systems stay stuck at reuse counts near zero or one out of five because they have hardcoded site-specific details.
