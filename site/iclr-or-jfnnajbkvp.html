EvoTest: Evolutionary Test-Time Learning for Self-Improving Agentic Systems

An agent improves itself between game attempts by letting a second AI agent rewrite its prompts, memory, and tool-use routines based on what failed.

Paper explainersAll themesAgents & Tool Use

Current AI agents play games or solve problems the same way every time—they cannot learn from their mistakes within a single session. EvoTest changes this: after each game attempt, a second AI watches what the first agent did wrong and automatically rewrites the first agent's instructions, memory, and tool definitions for the next attempt. No gradients needed, no retraining—just pure evolution of the agent's configuration.

Zero assumption version

Agents cannot learn new skills between game attempts

AI agents today act like intelligent but rigid interns: they follow the same playbook every single time, even when it fails. Show an agent a detective game twice, and it plays identically both times, making the same mistakes. A beginner might try to teach the agent by giving it more examples before it starts, or by fine-tuning its weights after failure—but fine-tuning takes hours or days, and adding examples does not tell the agent which past actions were actually good ideas worth repeating.

The real problem: no mechanism exists to let an agent analyze its own episode transcript, notice what went wrong, and self-modify—at the moment it plays the next attempt. The agent is stuck.

In one sentence. Existing agents cannot rewrite their own prompts or memory based on what they just tried.

The algorithm as a flow

What it actually does

Actor plays one full episode

Agent runs through the game from start to finish, logging every state, action, and result.

Evolver reads the transcript

Second AI model reads the full episode log and identifies what worked (good moves, smart tool uses) and what failed (dead ends, repeated mistakes).

Evolver proposes new instructions

Based on the analysis, Evolver generates a revised prompt (new strategy), updated memory notes (what worked), and rewired tool definitions (which calls matter).

Configuration gets reloaded

The Actor agent receives the new text-based prompt, memory, and tools before the next episode starts.

Loop repeats with better guidance

Actor plays again with the evolved instructions, makes fewer mistakes, and gives Evolver more signal to refine further.

What the paper changes

What the paper changes

EvoTest modifies the entire agent configuration—prompt text, memory contents, hyperparameters (how much to explore vs. exploit), and tool-use routing (which tools the agent calls)—after every episode, without touching the underlying weights of either AI model. The change is purely in-context, happening in the text input to the agent before it plays again.

the object it moves  =  agent prompt, memory, tool routing
The hidden quantity

The hidden quantity: which configuration parts matter most

measured quantity  =  configuration importance

Not every part of an agent's configuration moves the needle equally. Some prompts teach strong strategies; others are wasted words. Some memory notes recall truly useful patterns; others are noise. The paper does not measure this directly, but it implicitly discovers which configuration edits lead to the biggest performance jumps by trying many variants and keeping the ones that work.

The Evolver learns this by watching: if it changes the prompt strategy but performance stays flat, that prompt was not the bottleneck. If it adds a tool-use rule and performance jumps 30%, that rule matters. Over many episodes, Evolver gravitates toward the configuration levers that actually move performance.

Why it works

Why it works: the loop that teaches the agent

The core insight is that an AI agent can read another agent's failure transcript in plain language and reason about what went wrong. A human designer might read a game log and say, 'Oh, the agent kept exploring random rooms—it needs a smarter strategy.' An Evolver agent (powered by a large language model) can do this automatically. It analyzes the transcript, identifies patterns (this tool call was smart, this state-action pair was a dead end), and generates English text that teaches the original agent better, because the rewritten prompt directly shapes which actions the agent considers and which it avoids—the Agent reads its prompt at the start of each episode and adjusts its strategy according to it.

The loop amplifies: the Actor plays with Evolver's rewritten prompt, so it explores smarter and hits fewer dead ends. The next transcript is cleaner, with more successful patterns for Evolver to spot. Evolver's next edits are more precise. After several loops, the Agent's configuration has evolved to match the task's real structure—what states matter, which actions work, which tools to call. No gradient descent, no dataset collection, just repeated in-context refinement.

Math after the picture

The scoring and evolution equation

First in words:

Episode_n wins and generates log. Evolver_score(log) produces a ranked list of candidate rewrites ranked by estimated improvement. Top-ranked rewrite becomes the config for episode n+1. After N episodes, score accumulates: total_wins_N.

Then the compact form:

config_{n+1} = argmax_{c in candidates} [ score(c | transcript_n) ] where candidates = Evolver(transcript_n)

Every symbol:

config_nthe prompt, memory, and tool settings used in episode n
transcript_nthe full game log from episode n: all states, actions, and outcomes
Evolver(transcript_n)a large language model analyzing the log and proposing N candidate new configurations
score(c | transcript_n)a function (in practice: Evolver's own confidence or a heuristic) rating how much c should improve the next episode
argmaxpick the configuration with the highest score
A tiny worked example over three episodes
Episode 1: Actor plays with baseline prompt. Wins 2 out of 10 games (20% win rate). Transcript shows it explored randomly, never used the detective-notebook tool.
Evolver scores two candidates: (A) rewrite prompt to say 'always use detective-notebook early' [estimated gain: +30%], (B) add exploration penalty [estimated gain: +10%]. Picks A.
Episode 2: Actor plays with new prompt. Wins 6 out of 10 (60% win rate). Transcript shows tool now used, but memory of past clues is not being referenced.
Evolver scores candidates: (A) add memory-logging rule [estimated: +15%], (B) expand state encoding [estimated: +8%]. Picks A.
Episode 3: Actor plays with memory logging. Wins 8 out of 10 (80% win rate). Evolver's successive rewrites compounded: each episode's top candidate became the next episode's starting point.

The Evolver never solves a math optimization problem—it uses natural language reasoning to rank candidate configuration edits and picks the best one each round.

What can go wrong

What can go wrong

Evolver gets stuck in local improvements. If the initial prompt is far from optimal, the Evolver might make small tweaks (add one tool call, reword one phrase) but never make the big leap needed. The loop converges slowly or misses the real bottleneck.
Transcript is too long or noisy. In a complex game with hundreds of steps, the transcript becomes hard to analyze. Evolver spends its attention on low-level noise (a single failed state) instead of the big pattern (the strategy is wrong).
Prompt rewriting diverges from the task. Evolver might generate a prompt that makes the Agent pursue a side goal or ignore the actual objective. Unchecked, the configuration can drift into nonsense.
Done right: ground Evolver in the actual transcript. If Evolver analyzes only the parts of the transcript that failed, and proposes changes that directly address the failures (e.g., if the agent kept choosing a tool that led to dead ends, ban that tool), the loop stays on track and compounds improvement.
What a runnable demo should prove

What a runnable demo should prove

Implement a simple text adventure game (e.g., a 5-room maze where the agent must find the exit, with a few tools like 'go north', 'search room', 'ask NPC'). Set up an Actor agent with a baseline prompt and an Evolver agent that analyzes episodes. Run 5 consecutive game attempts, logging the Actor's win rate and the Evolver's proposed config changes at each step. Measure whether the win rate improves—it should climb from around 10 percent on attempt one, to 50 percent on attempt three, to 80 percent on attempt five—because each iteration the Evolver has seen more successful patterns and can encode them into a more precise prompt. Also visualize the Evolver's edits (which prompt lines changed, which tools were reordered) to show that the configuration is actually shifting.

win_rate(episode_n) = games_won_n / total_games_n; improvement_slope = (win_rate_5 - win_rate_1) / 4

The demo must make impossible to miss: the Agent performs better on episode 5 than episode 1, not because it was retrained, but because its configuration was evolved by watching its own failures.
