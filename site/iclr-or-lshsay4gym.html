Massive Memorization with Hundreds of Trillions of Parameters for Sequential Transducer Generative Recommenders

Compress a user's full interaction history into a few cached summary slots so candidate scoring no longer scales with raw history length.

Paper explainersAll themesOther

Recommendation models gain signal from long user histories because old interactions often reveal stable preferences. The problem is that direct target attention, meaning a score that lets the candidate item read the user's stored sequence features, from every candidate item to every past interaction becomes too expensive when histories reach hundreds of thousands or millions of items. VISTA changes the computation graph. During a heavy upstream training stage, it compresses the full history into a few hundred summary slots that carry the useful sequence information. Those summaries are cached. Later training and serving stages attend from each candidate item only to the cached summaries instead of to the raw history. The key is that the costly history scan is paid once per user summary refresh, not once per candidate score. That makes inference, meaning the serving-time computation used to score candidates, cost nearly fixed with respect to raw history length.

Zero assumption version

Long histories help recommendation, but direct attention does not scale

A sequential recommender tries to estimate how a candidate item matches the user's past behavior. Transformer-style attention, where transformer means the sequence model family that uses repeated attention blocks, does this well because it can condition the candidate on many past interactions. The cost grows with sequence length, and industrial systems must score many candidates under tight latency limits.

Target-specific sampling methods reduce cost by selecting only a short candidate-dependent subsequence, but that still creates work that grows with the number of candidates. Full-sequence methods preserve more information, but they become too expensive when the history is very long.

The main change. Split target attention into two stages: summarize the full history once into cached sequence features, then let each candidate attend only to those summaries.

The algorithm as a flow

What it actually does

Encode the full history upstream

Run a foundational sequence model over the long user history because the upstream stage can spend more compute to capture long-range preference structure.

Produce summary slots

Compress the history into a few hundred stored sequence features because downstream stages only need the distilled information.

Train with sequence reconstruction

Use a generative reconstruction objective so the summaries preserve what the long sequence says about future behavior.

Cache summaries in storage

Persist the summary features per user because serving must reuse them across many candidate evaluations.

Score candidates against summaries

At downstream training and inference time, compute candidate-aware attention only over the cached summaries because that keeps cost nearly fixed.

What the paper changes

What the paper changes

The paper changes the memory interface for recommendation. Instead of exposing the entire raw interaction sequence to each downstream scorer, it exposes a compact cached summary of that sequence.

the object it moves  =  the sequence representation that downstream candidate scoring reads
The hidden quantity

History retention after compression

measured quantity  =  history retention (how much of the useful preference signal survives in the cached summaries)

Compression is only worthwhile if the summaries keep the parts of history that matter for prediction. That hidden quantity is the information retained about long-term interests, recent intent, and cross-item patterns after the raw sequence is collapsed into a short cached form.

Too little retention hurts ranking quality because downstream scoring sees only a blurred user profile. Too much detail would require too many summaries and would remove the computational gain. VISTA is balancing that tradeoff directly.

Why it works

Why two-stage attention reduces serving cost

The expensive part of sequential recommendation is repeated reading of the same long history. If a user has one million past interactions and the system scores many candidates, standard target attention revisits that sequence again and again. VISTA removes that duplication because the history is summarized once and the summaries are reused.

The upstream summarization can still be heavy because it is amortized across many later scores. After summarization, each candidate attends only to a short cached sequence. Latency drops because the raw-history dependence has been moved out of the hot serving path.

The reconstruction objective matters because cached summaries would otherwise drift toward generic user averages. By training the summaries to support future sequence reconstruction, the model is forced to keep enough temporal and preference structure to remain predictive after compression.

A tiny worked example
Suppose a user has 200000 past interactions.
A standard model may read all 200000 interactions for each candidate item.
VISTA compresses the history into 300 summary slots.
Each candidate then attends to 300 stored summaries instead of 200000 raw events.
The saved work appears every time the serving system scores another candidate for the same user.

The paper includes a quasi-linear attention design and a reconstruction loss, but the serving-side simplification is the main first-principles idea.

What can go wrong

What can go wrong

Summaries are too small. If the summary budget is too tight, downstream scoring loses long-range preference details because too much sequence information has been discarded.
Cached summaries become stale. If user behavior changes quickly and the cache refresh is slow, the system serves from old preferences because the compressed state no longer matches the latest interactions.
The reconstruction task does not match ranking needs. If the upstream objective preserves patterns that help sequence reconstruction but not candidate ranking, the summaries may look faithful while still underperforming at recommendation because the retained details are not the same details that drive ranking decisions.
Done right. The design is strongest when user histories are very long and each user is scored against many candidates, because that is where amortized summarization produces the largest serving gain.
What a runnable demo should prove

What a runnable demo should prove

Create a toy recommendation task with long click sequences and several candidate items per user. Compare a baseline that scores each candidate against the raw sequence with a two-stage system that first compresses the sequence into cached summaries and then scores against those summaries.

The demo should show two curves: ranking quality and per-candidate latency as history length grows. The key result is that quality should stay close while latency stays nearly flat for the summary-based system.
