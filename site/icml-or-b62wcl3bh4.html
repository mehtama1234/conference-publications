Pessimistic Verification for Math-Solving Agents

To solve hard math problems reliably, ask multiple parallel verifiers to check the answer together, and reject it if any one of them finds a flaw.

Paper explainersAll themesAgents & Tool Use

When a language model solves a difficult math problem, how do you know if the answer is right? You could ask the model to double-check its own work, but self-checking is like asking a student to grade their own paper — it misses mistakes. This paper shows how to use multiple independent checkers working in parallel, each looking for different types of errors, and trusting their collective judgment to weed out wrong answers before they are trusted.

The trust problem in automated math solving

Language models are good at working through math steps, but they are also confident when they are wrong. When a model solves a hard problem like an International Math Olympiad (IMO) question, you need a way to check the answer before trusting it. One obvious idea: ask the model to check its own work, just like explaining your reasoning again. But self-checking is blind to certain types of errors — especially the subtle ones where the model made a mistake early and then built everything on top of that false foundation.

The benchmark (a standard test set) also hides the real problem. When researchers score an answer on today's test sets, they often count a nearly-right answer as right due to annotation errors (human mistakes in labeling what counts as correct). So even verification methods that look good on benchmarks may fail on truly hard problems where the exact answer matters, like contest math.

The core problem in one sentence. A single verifier is blind to many mistakes, and even good-looking verification methods may be hiding failures in the real benchmark.

The algorithm as a flow

What it actually does

Model solves the problem

A language model generates a step-by-step solution (reasoning plus final answer).

Decompose into sub-proofs

Break the solution into smaller, verifiable chunks (each lemma, each calculation step).

Run verifiers in parallel

Five independent checkers each look at the solution and its decomposed pieces, hunting for different error patterns.

Collect verdicts

Gather whether each verifier passed or flagged a flaw.

Pessimistic gate

Accept the solution only if all verifiers agree it is sound. Any flaw means reject.

What the paper changes

What changes: the verdict rule

Instead of trusting a single verification signal, the paper changes how a solution is deemed correct: from optimistic (one verifier says yes, trust it) to pessimistic (any verifier says no, reject it). This flips the default from acceptance to caution.

the object it moves  =  verdict-combination rule
The hidden quantity

The error-detection rate

measured quantity  =  Fraction of actual errors caught

When a solution is wrong, it contains actual flaws: a step that does not follow from the previous one, a calculation error, a logical gap. The paper's core hidden quantity is how many of these real flaws each verifier can actually detect. A single verifier might catch 60% of errors (blind to 40%). But five independent verifiers, each with different blind spots, together catch many more because their blind spots do not fully overlap.

The paper measures this by testing on problems where the correct answer is known (like IMO 2025 and MathArena Apex), marking which verifiers found which errors, and counting what fraction of total errors the ensemble catches. When multiple verifiers disagree (some find an error, others do not), that disagreement is evidence of a subtle mistake that at least one verifier caught but others missed.

Paper reading. The paper models verification as error detection; the pessimistic rule (all must agree) converts that into a rejection-safety guarantee: if verifiers disagree (some find a flaw others missed), the ensemble rejects the candidate. This improves accuracy on contest-level problems because it prevents wrong answers from slipping through when the verifiers have different blind spots — any verifier that catches an error is enough to block a false solution.
Why it works

Why it works: independent error finders

The paper's insight is that different verifiers are blind to different errors. Verifier A might check the logic of the steps but miss an arithmetic slip. Verifier B might check every number but not notice that a case was omitted. When you run them all in parallel, their blind spots do not fully overlap. If the solution has a hidden flaw, at least one verifier catches it, because together they look at the problem from many angles.

The pessimistic gate — reject if any verifier objects — shifts the decision boundary. Normally a single verifier might accept 70% of wrong answers by accident (false accept rate). But if five verifiers each independently catch different errors, and you reject on any objection, the false accept rate drops dramatically (e.g., from 70% to maybe 5%, because now an error has to evade all five verifiers to slip through). The progressive version (fine-grained decomposition) makes each verifier's job easier and more reliable because checking one small proof piece is simpler than checking an entire solution, so verifiers spot errors they would have missed in a longer proof, and error detection improves for each verifier too.

The core equation: pessimistic acceptance gate

First in words:

Accept a solution only if all verifiers pass. Reject if at least one verifier raises an objection.

Then the compact form:

accept = all_verifiers_pass

Every symbol:

all_verifiers_passTrue if every single verifier says no flaw found; False if any one found a problem
verifier_iIndependent checker i, looking for error patterns in the solution
false_accept_rateFraction of wrong solutions that slip through as accepted
A tiny worked example
Assume each verifier independently has a false-accept rate of 50% (accepts half of wrong answers by mistake).
With one verifier: 50% of wrong answers are falsely accepted.
With five independent verifiers, all must agree (all pass) for acceptance: 0.5 ^ 5 = 0.03125 = 3.1%.
By running five verifiers, false accepts drop from 50% to 3.1% without changing how often correct answers are accepted.

The power comes from independence: each verifier's blind spots are different, so requiring all five to agree cuts false accepts exponentially.

What can go wrong

What can go wrong

All verifiers have the same blind spot. If the five verifiers all use the same underlying checking logic (same model, same prompts), they will all miss the same errors because they have identical error-detection capability. Independence is broken, and false-accept rate does not improve because an error that fools one still fools all five. The verifiers must be genuinely different — different models, different prompts, different error-detection strategies — so their blind spots do not overlap.
One verifier is unreliable and rejects correct solutions. If any verifier has a high false-rejection rate (rejects many correct answers), the pessimistic gate will reject too many correct solutions. The method assumes each verifier is reasonably calibrated; if one is broken, it drags down the whole ensemble.
The decomposition is wrong or incomplete. Progressive pessimistic verification relies on breaking the solution into checkable pieces. If the decomposition misses a step or misrepresents a piece, verifiers may not catch the real flaw. The decomposition logic itself must be sound.
Done right: verifiers are independent, well-calibrated, and trained on diverse error patterns; decomposition is fine-grained and complete. Then the ensemble catches errors that slip past any single checker, and the method delivers high accuracy on hard contest-style problems with unique correct answers.
What a runnable demo should prove

What a runnable demo should prove

Build a tiny math-solving pipeline: (1) a language model solves 10 moderately hard algebra or equation-solving problems (ones with unique correct answers, like contest-style); (2) run a single verifier on each solution and record yes/no; (3) run five different verifiers (could be the same model with different prompts, or different models) on the same solutions; (4) apply the pessimistic gate for each: accept only if all five pass. Count how many wrong solutions are rejected in each case.

reject_rate_wrong = (wrong_solutions_rejected / total_wrong_solutions)

The demo must show that the reject rate on wrong answers goes up (from maybe 40% to 75%+) when you use five independent verifiers with a pessimistic gate, compared to a single verifier, while keeping the accept rate on correct solutions above 85%.
