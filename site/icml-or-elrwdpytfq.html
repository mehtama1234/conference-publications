Exploring Motif-based Heterogeneous Graph Learning for ReDoS Detection

This paper turns a regular expression into a typed graph, marks the substructures that usually create catastrophic backtracking, and lets a graph network score risk in one pass instead of executing the regex on many adversarial strings.

Paper explainersAll themesOther

A regular expression is a compact program for matching text. In many regex engines, some patterns cause catastrophic backtracking, meaning the engine explores a huge number of partial matches before it can reject an input string. That creates a Regex Denial-of-Service attack because a small crafted input can force very large runtime. Static detectors are fast, but they often break on extended regex features such as lookarounds and backreferences. Dynamic detectors support real engine behavior, but they are slow because they must run the regex on many test strings. This paper builds a middle path. It converts each regex into a heterogeneous graph (a graph with several node and edge types), inserts motif markers for known ReDoS-prone substructures, and then uses typed message passing plus cross-scale fusion to classify the regex directly.

Zero assumption version

A regex vulnerability is about execution paths, not just surface syntax

A regex engine does not merely read characters from left to right. It builds and revisits partial match states while handling alternation, repetition, grouping, lookarounds, and backreferences. ReDoS appears when those control paths branch heavily and then rejoin in a way that forces the engine to retry many failed possibilities. A detector must therefore reason about both syntax and engine-style control interactions.

Simple hand-written rules are fast because they inspect the pattern directly, but they struggle once extended constructs interact in nonlocal ways. Dynamic testing gets closer to truth because it runs the engine itself, yet it is expensive because each regex may need many crafted inputs to expose worst-case behavior. The paper treats the regex as structured data and asks a graph network to learn the risky interactions directly. It also bakes in three hand-designed motifs. Those motifs focus the model on the parts that usually cause blowups because they mark repeated-branch structures that create many retry paths in real regex engines, and they make the learned score start from those failure patterns instead of raw syntax alone.

What the model has to detect: Not every repetition is dangerous. The dangerous cases are repeated subexpressions whose alternatives or references create many overlapping partial matches, so the engine keeps retrying branches that eventually fail.

The algorithm as a flow

What it actually does

Parse the regex

Build a structural representation that preserves literals, groups, repetition operators, lookarounds, backreferences, and their typed relations.

Create a heterogeneous regex graph

Represent the regex as a graph with multiple node and edge types, because different constructs interact in different ways during matching.

Insert domain motifs

Encode three ReDoS-related motifs directly into the graph so the network can detect the branch-and-repeat patterns that usually produce catastrophic backtracking.

Run heterogeneous propagation

Use typed message passing so each relation type has its own transformation, which means repetition edges, containment edges, and reference edges do not get mixed into one generic signal.

Fuse scales with learned cross-reweighting

Combine local motif evidence and global regex context, because a risky fragment may only become dangerous when the surrounding structure lets it be revisited many times.

What the paper changes

What the paper changes

The paper changes the input representation and the propagation rule. Instead of feeding regex strings broken into small pieces or running dynamic execution traces, it builds a typed graph that preserves engine-relevant structure. It then augments that graph with motif nodes or motif relations tied to known ReDoS patterns and applies typed graph propagation plus residual cross-reweighting across local and global summaries to make the final decision.

The hidden quantity

The hidden quantity: branching pressure inside the matcher

measured quantity  =  How many partial match states the engine can revisit before failure

A vulnerable regex is not defined by one visible character fragment. It is defined by how the engine's search space expands. Each alternation, repetition, or reference can create several candidate partial matches. If later characters force failure only after many such branches have been explored, the engine revisits a huge number of states. That branching pressure is the hidden driver of runtime blowup.

The graph model cannot observe the engine's full search tree directly during prediction time, but the heterogeneous graph and motif encoding approximate it. Typed nodes identify which constructs can branch, which ones repeat, and which ones reuse earlier matches. Motifs then mark combinations of those constructs that usually multiply the number of revisits. The model learns to estimate branching pressure from structure alone.

Why it works

Why motif-augmented typed graphs beat plain syntax models

A plain sequence model sees the regex as a string of characters and punctuation. That loses the distinction between very different roles. For example, a parenthesis can open a group, a repetition operator can apply to one subexpression but not another, and a backreference can point back to content captured much earlier. A typed graph keeps these roles explicit. Each node and edge type tells the model how information should flow between constructs that interact during matching.

The motifs matter because they inject domain knowledge exactly where the worst-case runtime usually comes from. Catastrophic backtracking often needs more than one ingredient: a repeated region, an ambiguous split, and a later failure that forces the engine to revisit those branches. If the graph network had to learn those combinations from raw data alone, it would need many examples and might ignore rare extended features. By marking those combinations in advance, the model can treat them as first-class structures and then use message passing to decide whether the surrounding context makes them truly dangerous.

Cross-scale fusion is the last piece. A local subpattern may look risky, but the entire regex may still be safe if another constraint prevents long retries. The residual cross-reweighting block lets local motif summaries interact with whole-regex summaries, so the final prediction depends on both local branching structure and global execution context.

The decision rule in compact form

First in words:

Each node representation is updated by combining messages from several relation types, then the graph summary is used for binary classification.

Then the compact form:

h_v' = phi( sum_r sum_{u in N_r(v)} W_r h_u )

Worked example: one repetition node
Suppose a repetition node receives one message from an alternation child and one message from a backreference child.
The alternation edge uses one learned transform because it signals branching behavior.
The backreference edge uses a different learned transform because it signals dependence on earlier matched text.
Those typed messages are added and passed through the update function.
If the resulting representation is strong only when both branch ambiguity and reference dependence are present, the classifier can learn that the combined pattern is risky even if either part alone is harmless.

The key point is not the exact update formula. Each relation type gets its own path, which means repetition edges, reference edges, and grouping edges can contribute different signals instead of being merged into one generic message.

What can go wrong

What can go wrong

Graph construction must match engine semantics. If the parser or graph builder ignores an engine-specific feature, the learned detector can score the wrong structure because the graph no longer matches the execution model that creates the vulnerability.
Hand-designed motifs can miss new attack patterns. The motif library helps because it focuses the model, but it can also narrow the search space. If future engines or pattern styles create different failure modes, the motif library may need to be expanded.
Data labels depend on the benchmarking procedure. A regex may look safe or unsafe depending on which engine and which timeout policy generated the labels, so cross-engine transfer is not automatic.
Done right. The approach is strongest when the deployment setting needs low latency but also needs coverage for extended regex features that simple static rules usually drop.
What a runnable demo should prove

What a runnable demo should prove

Build a small benchmark with regexes labeled by actual engine behavior under a fixed timeout. Compare three detectors: a rule-based static baseline, a dynamic execution baseline, and the graph model from this paper. The demo should expose both standard and extended constructs. For a few vulnerable examples, also render the heterogeneous regex graph and highlight which motif markers and relation paths pushed the score upward. That makes it clear that the model is reacting to branch-and-repeat structure because the highlighted paths correspond to repeated retry opportunities in the matcher, not merely to recurring character fragments.
