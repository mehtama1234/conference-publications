Learning Graph Structure from Relational Data

Instead of fixing how tables connect in a database, this paper learns which tables should be nodes and edges for graph learning.

Paper explainersAll themesGraph & Geometric Learning

When you have data stored in a relational database (tables with rows and links between them), a graph neural network needs to know how to turn the tables into a graph. Today's methods lock in a fixed graph structure decided before training. This paper shows that letting the model learn which tables act as nodes and which act as connections leads to better predictions, because different tasks rely on different information — one task might need direct Product access, another might need User details — so a single locked-in graph cannot serve all equally well.

Zero assumption version

Databases don't naturally look like graphs

A relational database has tables. Each table is rows of data, and foreign keys (column references) link one table to another. A naive approach: pick one main table (the target), turn it into graph nodes (one node per row), and connect nodes based on keys in other tables. But this is arbitrary — you have to decide ahead of time which tables are nodes and which are just connection paths. If you guess wrong, the graph loses important information.

Even worse, fixing the graph structure means the model cannot adapt: if the task changes, the graph cannot change. And different tasks might need different ways to see the same database.

The fix. Let the model learn which tables should act as nodes and which should act as edges (connection relationships).

What the paper changes

What changes

The graph structure stops being fixed before training. Instead, each table gets a learnable role score that says how much it acts as a node or an edge. The model learns these scores alongside the neural weights.

the object it moves  =  Table role scores
The hidden quantity

The hidden quantity: Table role in the graph

measured quantity  =  Table role score

A table role score is a number between 0 and 1 for each table. It captures whether that table should contribute as a node in the graph (high score) or primarily as a connection between other tables (low score). For example, a User table might score high (1.0 is fully a node) while an Order-Product bridge table might score low (0.3, mostly a connection).

The paper measures this role by learning it directly from data during training. Tables that help the prediction task get higher scores because information from those tables, when available directly, reduces the prediction error more than information routed indirectly through other tables; tables that blur the signal get lower scores because their noisy or redundant information interferes with the model's learning. Functional dependency constraints (rules about which keys must match across tables) keep the roles semantically sound — a bridge table cannot become a node if the keys do not permit it.

Why it works

Why fixing the graph was a problem, and why learning it fixes it

When the graph is locked in, the model receives incomplete information if the fixed structure drops important tables as merely side paths. A User-Order-Product chain might bury Product details if Products are only reachable through Orders. The model has to infer Products from Order-to-Product links, which is indirect and noisy.

Learning table roles solves this: if Product information directly helps the prediction task, the model pushes the Product table's role score higher, making it a full node, because direct information reaches the neural network without the noise and distortion of passing through an intermediate table. Now Product features flow directly into the learning, not filtered through another table. This lets the model take the shortest, most direct path to the information it needs.

The functional dependency constraints (like: each Order must reference exactly one User) keep the roles grounded in the real database semantics. You cannot randomly make every table a node — the data structure enforces which tables can actually talk to each other. This prevents the model from learning meaningless roles.

Math after the picture

The core equation

First in words:

The total loss is the prediction error plus a penalty that ensures each table's role respects its semantic relationships to other tables.

Then the compact form:

loss_total = loss_prediction + lambda * sum_constraints semantic_consistency(roles)

Every symbol:

loss_totalThe combined loss the model tries to minimize
loss_predictionHow badly the model predicts the target (like accuracy error)
lambdaA weight that balances prediction accuracy against semantic constraints
rolesThe learned role score for each table
semantic_consistencyA penalty that checks whether roles match the database schema (which tables can connect)
A tiny worked example
Suppose we have User, Order, Product tables.
Prediction loss: 0.15 (model predicted 85% correctly).
User role = 1.0 (fully a node), Order role = 0.8, Product role = 0.9.
Constraint check: each Order must link to a User and a Product. Roles 0.8 and 0.9 are compatible (both above threshold 0.5), so constraint penalty = 0.0.
If Product role were 0.2 (very low), schema says Product must be reachable, so constraint penalty jumps to 0.3.
With lambda = 0.1: total loss = 0.15 + 0.1 * 0.0 = 0.15 (good). If Product role were 0.2: total loss = 0.15 + 0.1 * 0.3 = 0.18 (penalized).
Training nudges Product role higher because high roles satisfy the constraint and allow better direct connections.

The loss rewards role assignments that match the database structure and help prediction accuracy, because high-scoring roles allow information to flow directly through the graph, reducing the distance information must travel and making neural updates more focused.

What can go wrong

What can go wrong

Roles become too permissive. Without strong semantic constraints, the model might push all table roles to 1.0 (all nodes), defeating the purpose of learning structure. The fix: enforce functional dependency constraints strictly.
Schema is unknown or messy. If the database schema is not well-defined or foreign keys are inconsistent, the semantic constraints cannot steer the roles correctly. The method assumes a real, clean relational schema.
Roles overfit to one task. If roles are trained on Task A, they might not transfer well to Task B. Transfer learning requires re-tuning roles or explicit multi-task objectives.
Done right. Combine role learning with strong schema constraints and train on diverse tasks to learn roles that generalize. Use enough data to prevent overfitting.
What a runnable demo should prove

What a runnable demo should prove

Build a small synthetic relational database (e.g., User-Order-Product-Review tables with realistic foreign keys). Train a baseline graph neural network with a fixed hand-designed graph structure on a prediction task (e.g., predict if an order is high-value). Then train the same model with learned table roles. Measure prediction accuracy on a held-out test set. The demo should show that learned roles outperform the fixed structure, especially if the fixed graph excludes important information (e.g., if reviews are not reachable from orders in the fixed version, accuracy should improve when role learning makes reviews directly accessible because the model can now reach review data without passing through intermediate tables, making the signal clearer).

accuracy_improvement = accuracy_with_learned_roles - accuracy_with_fixed_graph

The metric must be positive: learned roles must beat the fixed structure on at least one task where the fixed graph was designed poorly.
