Is Your LLM Overcharging You? Tokenization Fraud and Honest Pricing

Providers can exploit pay-per-token pricing to overcharge users by reporting longer token sequences than they actually generated, but transparent pricing and character-based billing stops this fraud.

Paper explainersAll themesOther

Large language models are expensive to run, so companies rent access via cloud services. They charge users per token—each word or piece of text counts as one or more tokens. The paper shows that providers have a hidden incentive to lie: they can report that a response used more tokens than it really did, and users have no way to prove it. The paper develops both an attack (a clever algorithm that fakes longer token counts) and a defense (a new pricing rule that makes lying unprofitable).

Zero assumption version

Users are blind to what they are paying for

When you use ChatGPT or Claude via a paid API, the bill shows: 1,000 tokens generated, charged at, say, $0.10 per token, so $100 total. But you never see the real token stream—you only see the final text. The provider sees everything: every intermediate token, every rejected path, the full generative process.

A naive user assumes the provider is honest. But the provider has a financial incentive to lie: they can record that your response used 1,500 tokens instead of 1,000, split that message into longer tokens, or choose token sequences that appear longer when decoded—and pocket the extra $50. You have no way to audit them or even suspect them, because you cannot reconstruct what tokens were actually generated.

In one sentence. Providers can lie about token counts because users see only the final text, not the token sequence used to generate it.

The algorithm as a flow

What it actually does

Step 1: Show the vulnerability

Provider reports a longer token sequence that decodes to the same final text; users cannot detect it.

Step 2: Transparency creates friction

If provider must share the probability of each token (why model chose it), fake tokens look suspicious.

Step 3: Build the attack

An algorithm finds a plausible longer tokenization that is still hard to prove false without running the model yourself.

Step 4: Propose character pricing

Bill by character count instead of token count; lying about tokens no longer increases revenue.

Step 5: Preserve profit margins

Provider can adjust per-character prices to keep average profit the same, but now honest.

What the paper changes

The object the paper changes: reported token count

The paper does not change how the model works. It focuses on what the provider reports after the model finishes. Instead of reporting the true tokens used, the provider can substitute a longer but plausible token sequence that decodes to the same output text. This swap increases the bill without the user knowing.

the object it moves  =  reported token count
The hidden quantity

The hidden quantity: token sequence plausibility

measured quantity  =  likelihood of a reported token sequence

Not every token sequence that decodes to the same text is equally plausible. When a language model generates tokens, each token has a probability score—how likely the model thinks that token is given the context. A real sequence of tokens has high-probability steps; a fake sequence has implausible (low-probability) tokens.

The paper measures this by asking: given the final text, what is the probability that the model actually produced this particular token sequence? If the provider must report the probabilities, a user can detect fake tokens because they will have suspiciously low probability scores.

Paper reading. Token sequence plausibility is formalized as the product of conditional token probabilities from the generative process. Transparency requires the provider to report these scores; a sequence with implausibly low scores is flagged as a lie.
Why it works

Why the attack works (and why transparency stops it)

The attack exploits two facts. First, the same final text can be split into tokens in multiple ways—there are many tokenizations of 'hello world' that all produce identical output. Second, users only see the final text, not the token stream. So the provider can pick the longest possible tokenization, report it, and users have no way to prove the report is false. They trust the provider.

But if transparency (requiring the provider to share token probabilities) is enforced, the provider must now find a tokenization that is not only long but also appears plausible. This is much harder. Many long tokenizations include tokens that are extremely improbable given the context, which would raise red flags. The paper shows that finding an optimal long-but-plausible tokenization is computationally hard (NP-hard), forcing the provider to use a heuristic algorithm instead.

The defense goes deeper: the paper proposes character-based pricing. Instead of paying per token, users pay per character in the output. Since the number of characters never changes (all tokenizations of the same text have the same characters), the provider cannot gain money by lying. The incentive disappears entirely. The provider can adjust the per-character price to keep average profit the same, so they do not lose money—but now they have zero reason to cheat.

Math after the picture

The pricing formula and the defense

First in words:

provider_revenue_from_overcharging = (overreported_tokens - actual_tokens) * price_per_token. If pricing is based on character count instead, this revenue becomes zero because character count is invariant.

Then the compact form:

revenue_fraud = (len(tokenize_long(text)) - len(tokenize_actual(text))) * p_token ; revenue_fraud_charcount = (len(text_chars) - len(text_chars)) * p_char = 0

Every symbol:

tokenize_long(text)one tokenization of the output text, chosen to be as long as possible
tokenize_actual(text)the true token sequence the model actually generated
p_tokenprice per token (the dangerous pricing rule)
p_charprice per character (the proposed defense)
len(text_chars)number of characters in the output (never changes, regardless of tokenization)
A tiny worked example
Suppose the actual output text is 'hello' (5 characters).
True tokenization: ['hello'] = 1 token. Pay-per-token bill: 1 * $0.10 = $0.10.
Fraudulent tokenization: ['h', 'el', 'lo'] = 3 tokens. Bill becomes: 3 * $0.10 = $0.30.
Provider gains $0.20 extra from the same 5-character text.
With character-based pricing: 5 chars * $0.02 per char = $0.10, whether reported as 1 token or 3.
No incentive to lie; revenue is identical either way.

Providers profit from token fraud only because tokens vary but characters do not. Character-based billing locks the revenue to the actual output, eliminating the incentive.

What can go wrong

What can go wrong

Transparency alone is incomplete. Even if providers must share token probabilities, the paper shows that an algorithm can find tokenizations with high (but not maximum) probability that are still longer and profitable to report. Transparency makes the attack harder but not impossible.
Providers may not have incentive to disclose probabilities. A provider can refuse to be transparent and instead claim they use a proprietary or private model. Users then have no way to verify truthfulness, and the vulnerability remains.
Character-based pricing requires market coordination. If only one provider switches to character-based pricing while competitors use token-based pricing, the honest provider's bill will appear higher, because fraudulent competitors can report false inflated token counts at lower per-token prices. Users see a lower sticker price and switch to the cheaper option, selecting the fraudster over the honest provider, because they cannot tell they are being cheated.
Done right with transparency and character billing. When providers are required to disclose token probabilities and users are billed per character, the incentive to misreport vanishes. The attacker's algorithm becomes useless because profitability drops to zero.
What a runnable demo should prove

What a runnable demo should prove

Build a simple LLM inference system (or use a pretrained model like Llama or Gemma) that generates a short text (e.g., 'The capital of France is Paris'). Compare three scenarios: (1) report the true token count; (2) report a longer tokenization of the same text (decode it differently); (3) compute what the user would pay under token-based pricing versus character-based pricing. Show that under token pricing, fraud is profitable; under character pricing, both strategies yield the same revenue.

profit_gain_from_fraud = (tokens_reported - tokens_true) * price_per_token ; profit_gain_from_fraud_under_charcount = (chars_reported - chars_true) * price_per_char = 0

The demo must make it impossible to miss: report 3 tokens or 1 token from the same text, and under character pricing the bill is identical, while under token pricing it changes.
