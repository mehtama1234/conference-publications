SceneSmith: Agentic Indoor Scene Generation

A framework that uses language-model agents to build rich, physically accurate virtual rooms for robot training by assembling architectural layouts, furniture, and small objects in sequence.

Paper explainersAll themesRobotics & Control

Robots trained in simulation need environments that look and behave like real homes. Today's simulators make sparse, unrealistic rooms. SceneSmith solves this by having three language-model agents work together: one designs the overall scene, one critiques what was built, and one coordinates the steps. The result is dense, physically stable virtual rooms that robots can actually learn from.

Zero assumption version

Sparse simulations fail to train real robots

Simulation is how robot engineers train and test policies cheaply before deploying a robot into a real home. But today's simulators generate rooms with a few chairs and tables, no clutter, and no small objects to manipulate. A real kitchen has a fruit bowl, canned goods, dish racks, and loose fruit scattered around. A bedroom has books, shoes, a lamp, and folded clothes.

When a robot trained on a sparse simulation meets a real home, it freezes. The dense clutter was never in its training examples. Prior methods—simple procedural rules, data-driven placement, or basic language-model prompts—all treat small objects as an afterthought and skip the articulated details (drawers, cabinet doors, hinges) that a real robot must learn to manipulate. The result: a trained policy fails on real homes.

The problem in one sentence. Current simulators generate sparse, unrealistic rooms that lack the density and physical detail robots need to learn general manipulation.

The algorithm as a flow

What it actually does

Designer agent proposes scene

A language model reads the task description and generates diverse prompts describing a realistic room layout.

Asset router decomposes requests

For each object or area, the router decides: generate a new 3D object from text, retrieve an existing articulated model from a library, or apply a thin texture wrapper.

Assets are acquired and validated

Generated objects are checked for validity; articulated furniture is retrieved with collision meshes (the outlines that say where the object is) and joint definitions already built in.

Orchestrator places objects hierarchically

Large rooms are placed first, then furniture into rooms, then small objects on surfaces, checking for collisions at each step.

Critic agent verifies realism

A language model checks whether the final scene matches the task and looks realistic; if not, the designer adjusts and repeats.

What the paper changes

What the paper changes

SceneSmith changes the asset composition strategy. Instead of treating objects as a single flat list placed all at once, it decomposes scene construction into a hierarchy: architectural layouts, then furniture, then small objects, each using a different acquisition method matched to the object type.

The hidden quantity

The hidden quantity: Physical stability margin

measured quantity  =  Physical stability margin

Every object placed in a simulator has a real physical center-of-mass, size, and weight. An object on a table is stable only if gravity and friction keep it from tipping, sliding, or falling through the surface. The paper measures this as a single score: the fraction of objects that remain still under physics simulation for a full episode (96% in their results). This is the litmus test for whether a scene is usable for robot training.

To achieve this, SceneSmith estimates mass and friction per object, computes the collision outlines (the mesh boundaries that define where each object occupies space) for articulated parts like drawer hinges and cabinet joints, and runs a placement algorithm that checks for overlaps before committing each object to the scene. Objects that would be unstable are either repositioned or rejected.

Why it works

Why hierarchical agentic generation works

A flat approach—asking a single model to place all objects at once—creates collisions and instabilities, because the model has no feedback loop and no way to reason about spatial constraints. SceneSmith succeeds because it breaks the problem into stages, each with a specific role: the designer works at a high level (task description to room sketches); the asset router reasons about object type and context (static, articulated, or textured); and the orchestrator places objects hierarchically (rooms first, then furniture in rooms, then small objects on surfaces), checking for collisions after each step.

The critic agent closes the loop: if the result is not realistic, the designer generates a new candidate. This iterative refinement is what prior flat methods lack. Additionally, by integrating physical property estimation (mass, friction, inertia) into the asset router, each object carries its own physics, so the placement algorithm does not have to guess. The hierarchical stages mean that later objects are constrained by earlier choices, making collisions rare and physics-correct.

Math after the picture

Stability penalty during placement

First in words:

For each object placed, check collision geometry and estimate the restoring force (mass and friction). Penalize placement if restoring force is too small.

Then the compact form:

stable = (mass_i * friction_i > gravity_component_i) & (collision_volume_i == 0)

Every symbol:

mass_iestimated mass of object i (in kg)
friction_iestimated friction coefficient of the supporting surface for object i
gravity_component_ithe downward pull on object i due to gravity and tilt
collision_volume_ivolume of overlapping geometry between object i and other objects (zero means no overlap)
A tiny worked example
Object 1 (apple): mass 0.1 kg, friction 0.6, no tilt, collision volume 0. Restoring force = 0.1 * 0.6 = 0.06 >> gravity component 0.01. Stable.
Object 2 (large book): mass 0.8 kg, friction 0.3, no tilt, collision volume 0. Restoring force = 0.8 * 0.3 = 0.24 >> gravity 0.02. Stable.
Object 3 (thin vase): mass 0.2 kg, friction 0.1, tilted 10 degrees, collision volume 0. Restoring force = 0.2 * 0.1 = 0.02, but gravity component with tilt ≈ 0.04. Unstable. Reject or reposition.

Objects with high mass and surface friction resist sliding; those with zero collision volume do not penetrate other objects. Both conditions must hold for stability.

What can go wrong

What can go wrong

Text-to-3D synthesis generates invalid shapes. If the language model asks the text-to-3D system for a shape it cannot produce (e.g., self-intersecting meshes where the surface crosses itself), the asset router must fallback to retrieval or texture wrapping. If no fallback is available, the object is skipped, reducing scene density.
Articulated library does not have the requested object type. The system retrieves articulated furniture from ArtVIP; if the requested object (e.g., a specific brand of refrigerator) is not in the library, the system retrieves a close semantic match, which may not fit the scene aesthetically or physically.
Mass and friction estimates are inaccurate. The system estimates mass per link based on volume and material; if the estimate is wildly off (e.g., a plastic toy guessed to be ceramic), the stability check may pass when the object would tip in reality, or reject valid placements.
Designer agent hallucinates unrealistic prompts. The language model may propose rooms with contradictory constraints (e.g., three windows on a 2-meter wall) that the orchestrator cannot satisfy; the critic catches obvious failures but may miss subtle ones.
Done right: hierarchical stages + critic loop. When the designer proposes, the router routes intelligently, the orchestrator checks collisions hierarchically, and the critic refines iteratively, the system avoids these pitfalls and generates scenes that are dense, realistic, and stable.
What a runnable demo should prove

What a runnable demo should prove

Build a demo that takes a simple task description (e.g., 'a kitchen where a robot picks a fruit from a fruit bowl') and generates a scene. Then drop that scene into a robot simulator and run physics for 5 seconds. Count the number of objects and measure the fraction that remain in place (not tipped, slid, or sunk). Compare against a baseline that places objects randomly or in a single flat pass.

Stability rate = (objects at rest after 5s physics) / (total objects placed). Target: > 90%.

The demo makes one thing impossible to miss: hierarchical, critiqued generation produces scenes where almost everything stays put, while flat methods have 30-50% of objects tip or disappear.
