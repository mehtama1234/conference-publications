Divide, Harmonize, Then Conquer It: Shooting Multi-Commodity Flow Problems with Multimodal Language Models

Split a large routing problem into local pieces, let agents solve those pieces, then coordinate the pieces until the whole network plan agrees.

Paper explainersAll themesAgents & Tool Use

A multi-commodity flow problem asks how to send many different demands through one shared network without breaking link limits. Classical solvers can find very strong answers, but they get slower as the network and demand set grow. This paper proposes Pram, a system that first cuts the large routing problem into local routing tasks, then lets language-model-based agents solve those local tasks, and finally runs a coordination stage that adjusts the local answers until the full network plan is consistent. The main claim is that this divide-then-coordinate design keeps solution quality high while cutting runtime, because each agent handles a smaller decision problem and the coordination stage repairs conflicts across subproblems.

Zero assumption version

Why large routing problems become hard fast

A network has links with limited capacity. Many users or services want to send traffic through that same network at the same time. The planner must decide how much of each demand goes through each link while keeping every link under its limit.

The difficulty comes from coupling. A route choice that helps one demand can block capacity for another demand because both demands may rely on the same limited links. As the network grows, the planner must keep track of many local choices that affect one another through shared links. Exact solvers can do this well, but the cost grows because the full problem must be handled as one large optimization task.

The paper's move in one sentence. Solve smaller routing pieces first, then coordinate them so that the final network plan obeys the global capacity rules.

The algorithm as a flow

What it actually does

Partition the network problem.

The full routing task is divided into local subproblems so that each agent receives a smaller region and a smaller set of routing decisions.

Solve each local subproblem.

An agent produces a local allocation for its own region, including how much traffic should pass through local links and boundary links.

Compare neighboring answers.

The system checks where two local solutions disagree on shared capacity or shared boundary traffic.

Run coordination updates.

A coordination stage adjusts the local agents so that the pieces move toward one consistent global answer.

Return the merged plan.

When disagreements are small enough, the local answers are combined into one network-wide allocation because the shared links now satisfy the same global rules.

What the paper changes

What the paper changes

The paper changes the unit of decision-making. Instead of solving one giant optimization problem directly, it treats local routing pieces as the primary objects and adds a separate stage that enforces agreement across those pieces.

the object it moves  =  local routing subproblems plus a global coordination loop
The hidden quantity

The hidden quantity: coordination gap

measured quantity  =  how far the local answers are from one globally consistent flow plan

The local agents can each produce a reasonable answer and still fail together. The important quantity is not just the quality of each local answer by itself. It is the size of the mismatch across shared links and shared boundaries.

If this mismatch is large, the merged plan can violate capacity limits or assign inconsistent traffic totals. If the mismatch shrinks, the whole system becomes usable because the local pieces can be assembled into one valid routing plan. The paper's coordination stage is built to reduce this gap step by step.

Why it works

Why splitting can help without losing the whole problem

Splitting helps because each agent only needs to reason over a smaller routing space. That cuts local solve cost and makes the local task easier to handle. The price of splitting is that some global information is lost at first, especially at the boundaries between regions.

The coordination loop pays that price back. It looks at where neighboring regions disagree and updates the agents so that those disagreements shrink. This can keep much of the speed gain from decomposition while still moving toward a globally valid answer, because the hard global coupling is handled through repeated repair instead of one huge solve from the start.

stepsplit into local routing regions

Math after the picture

A compact statement of the target

First in words:

Minimize total routing cost while making the coordination gap and link-limit violations go to zero.

Then the compact form:

total_score = route_cost(local_plans) + lambda * coordination_gap(local_plans) + mu * capacity_violation(local_plans)

Every symbol:

route_cost(local_plans)the total cost of the traffic allocation produced by all local agents
coordination_gap(local_plans)the amount of disagreement across shared links or boundary traffic between local regions
capacity_violation(local_plans)how much the merged plan exceeds link limits
lambdathe weight that pushes the system to reduce disagreement
muthe weight that pushes the system to obey link capacities
total_scorethe full objective the method tries to drive down
A tiny worked example
Suppose two local regions each send traffic through one shared link.
Region A says the shared link should carry 7 units, and Region B says it should carry 5 units.
That creates a coordination gap of 2 units.
The link capacity is 10, but the merged proposal would carry 12 units, so capacity_violation(local_plans) = 2.
If route_cost(local_plans) = 30, lambda = 4, and mu = 6, then total_score = 30 + 4 * 2 + 6 * 2 = 50.
After coordination, both regions may move to 5 units, which removes the mismatch and the overflow.
Then total_score falls because the plan is now globally consistent.

The important part is the extra cost on disagreement and overflow, because those terms force the local answers to become one usable global plan.

What can go wrong

What can go wrong

The split is poorly chosen. If the partition cuts through too many heavily used links, the coordination stage must repair too many cross-region conflicts, so the speed gain can disappear.
Local agents overfit their own region. A local answer can look good inside one region while harming the full network, because that agent does not directly see the full set of competing demands.
Coordination updates are too weak. If the repair stage does not punish boundary disagreements strongly enough, the merged answer can stay inconsistent even when each local part looks reasonable.
Done right. The approach works best when the split keeps most interactions local and the coordination loop is strong enough to remove the remaining cross-region conflicts.
What a runnable demo should prove

What a runnable demo should prove

Build a small network with 20 to 50 nodes, several demands, and hard link capacities. Solve it once with a standard linear-program baseline and once with a divide-then-coordinate system. Show the local subproblems, show the disagreement on shared links after the first local pass, and show how that disagreement shrinks across coordination rounds. The demo should report runtime, total routing cost, and whether any link limit is broken so that a reader can see the speed-quality trade-off directly.

gap_rate = total_boundary_disagreement / total_shared_link_load; violation_rate = exceeded_capacity / total_capacity

The central result is that decomposition helps only when the final merged answer still behaves like one coherent flow plan, because otherwise the local speed gains do not produce a usable network allocation.
