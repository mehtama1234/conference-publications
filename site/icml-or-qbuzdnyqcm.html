Embodied Task Planning via Graph-Informed Action Generation with Large Language Models

GiG stores environment state and past plans in linked graphs so an embodied agent can retrieve structurally relevant experience and generate actions that obey the current world constraints.

Paper explainersAll themesAgents & Tool Use

Long-horizon embodied planning breaks when the planner must remember many objects, partial goals, and state changes through plain text alone. The planner then forgets important constraints or invents state transitions that the world does not allow. This paper stores state and earlier solved plans in graphs, because graph structure preserves what can connect to what, and retrieves plans from similar graph situations so action generation starts from a legally grounded context instead of an empty prompt.

Zero assumption version

Embodied planning needs structure, not just long text

A household or game agent must turn a broad request into a long action sequence while respecting what is reachable, what is already done, and which objects can interact. Plain text prompts compress all of that into words, but as the horizon grows the planner loses track of important state details.

The result is often illegal planning. The agent may try to place an item before picking it up, revisit a completed subgoal, or assume a path exists when the environment state says it does not. The model sounds plausible because the text is fluent, but the plan is wrong because the world structure was weakly represented.

In one sentence. The planner needs an explicit world structure and a way to retrieve earlier plans from structurally similar situations, because fluent text alone does not enforce legal state transitions.

The algorithm as a flow

What it actually does

Encode the current world as a graph

Represent objects, rooms, tools, and relations so legal actions can be read from the structure.

Store past solved tasks as linked graphs

Keep earlier task graphs and action traces in memory so past experience is searchable.

Retrieve structurally close cases

Find previous plans whose state graphs resemble the current one, because those plans are more likely to transfer.

Generate a short action segment

Use the current graph plus retrieved cases to propose a bounded next chunk of legal actions.

Apply actions and refresh the graph

After each chunk, update the world graph and plan again from the new state.

What the paper changes

What the paper changes

The paper changes the planner's memory from a flat text history into a graph-in-graph store: one graph for the current world and a larger memory of past task graphs. That change matters because structural retrieval favors plans that match the current constraints instead of merely sharing keywords.

the object it moves  =  graph-structured world state and graph memory
The hidden quantity

The hidden quantity: structural match

measured quantity  =  structural match

Structural match measures how closely a past task graph lines up with the current world graph in objects, relations, and required dependencies. A high match means an earlier plan solved a situation with a similar state shape, not just similar words.

This quantity matters because a retrieved plan helps only when its steps respect the same kinds of constraints. If the current world has a stove, pot, and serving table connected in the same task order as a past episode, that past plan is useful because its action sequence already fits the dependency pattern.

Why it works

Why graph-guided generation works

The world graph reduces hallucinated state transitions because it makes preconditions explicit. If the graph does not contain the relation needed for an action, the planner has direct evidence that the action is illegal. That is stronger than a long prompt alone because the graph states the missing condition directly instead of relying on the model to remember it from earlier text.

Retrieval from structurally similar past graphs helps because long-horizon planning is mostly about decomposing tasks into reusable local patterns. Serving food, cleaning a room, or opening a cabinet all contain dependency chains. When the current world graph matches a past chain, the planner inherits a tested sequence instead of inventing one from scratch.

Bounded action generation keeps errors from compounding. The planner commits only to the next short segment, executes it, updates the graph, and replans from the new state. That works because each segment is checked against the current world before the next one is proposed, so outdated assumptions are cut off early.

Math after the picture

The equation for graph-guided planning score

First in words:

The planner prefers a next action segment when it fits the current world constraints and also aligns with retrieved past plans from closely matched graphs.

Then the compact form:

segment_score = legality_score + retrieve_weight * structural_match_score

Every symbol:

legality_scorehow well the proposed action segment satisfies the current world constraints
retrieve_weighthow strongly retrieved past plans influence generation
structural_match_scorehow closely the supporting retrieved graph matches the current graph
segment_scorescore used to select the next bounded action segment
A tiny worked example
Candidate A says pick pot, fill pot, heat pot. Its legality score is 8 because each action matches the current room and tool relations.
The retrieved kitchen plan has structural match 4 because it used the same tool and subgoal order.
With retrieve weight 2, candidate A gets total score 8 + 2 * 4 = 16.
Candidate B says serve soup first. Its legality score is 1 because soup is not prepared yet, even if the wording sounds fluent.
Suppose its retrieved support is also weak at 1. Then total score is 1 + 2 * 1 = 3.
The planner picks candidate A because it is both legal now and backed by a closely matched earlier plan.

The score works because it rewards both immediate feasibility and structural reuse from relevant past tasks.

What can go wrong

What can go wrong

Bad world graph extraction. If the graph misses a key object relation, the planner may reject good actions or approve bad ones, because all later reasoning trusts the extracted state.
Wrong retrieval target. If retrieval returns a past plan with similar words but a different dependency pattern, it can bias the planner toward the wrong action order.
Chunk size too large. If each planning segment is too long, early mistakes survive for many steps before the graph is updated, so compounding errors return.
Done right. The method is strongest when world graphs are accurate, structural retrieval is selective, and replanning happens often enough to absorb new state changes.
What a runnable demo should prove

What a runnable demo should prove

Build a small embodied kitchen task with rooms, tools, and action preconditions. Represent the current state as a graph, store a few solved task graphs, and let the planner retrieve one before generating each short action chunk.

Compare a text-only planner against the graph-guided version. The graph-guided version should finish more tasks and attempt fewer illegal actions because the graph exposes preconditions directly, and retrieval from matched task graphs supplies good local action orderings.

task_success = solved_tasks / total_tasks and illegal_action_rate = illegal_actions / total_actions

The demo should show that structure improves planning only when the planner uses it at every replanning step, because the current graph must reflect the newest world state before the next action segment is generated.
