NaviAgent: Graph-Driven Bilevel Planning for Scalable Tool Orchestration

Split tool use into a high-level planner and a tool-world navigator so the agent can choose longer tool chains without getting lost among many tools.

Paper explainersAll themesAgents & Tool Use

Tool-using agents often make one call at a time with only local context. That works when there are few tools, but it breaks down when hundreds of tools exist and some must be called in a specific order. This paper separates the problem into two levels. A planner decides whether to answer directly, ask for clarification, or execute a tool chain. A second model uses a graph of tool relations to navigate from one tool to the next, so that the full chain follows the structure of the tool world rather than a sequence of isolated guesses.

Zero assumption version

Why one-tool-at-a-time planning breaks at scale

A tool-using agent must often solve tasks that require several calls in sequence. One tool may fetch a user record, another may look up the user's orders, and a third may issue a refund. If the agent chooses each tool in isolation, it can easily make a locally plausible move that blocks the rest of the chain.

The problem becomes worse as the tool set grows. With hundreds of tools, the agent needs both global task planning and local navigation among related tools. Without that structure, the search space becomes large and error cascades appear, because one wrong early tool call changes the state that all later calls depend on.

The central fix. Separate planning from navigation, because deciding that a tool chain is needed is a different problem from deciding which tool should come next inside that chain.

Five-part picture of the system

1. The task may need no tool

The top layer first decides the route, because some tasks do not need any tool at all.

2. Many tools are connected

Some tools naturally lead to others, because their outputs satisfy later tool inputs.

3. The planner selects a chain goal
need customer record -> need order info -> need refund action

The high-level plan narrows the search because it sets what the chain should achieve.

4. The navigator walks the tool world

The lower layer chooses next tools using the relation graph, because nearby tools are more likely to fit.

5. Feedback closes the loop

Real tool results update the next step, because failed calls reveal that the route must change.

The algorithm as a flow

What the method actually does

Choose the top-level action

Decide whether to answer directly, ask the user for clarification, or start a tool chain so that tools are used only when needed.

Represent the tool world as a graph

Store structural and behavioral links among tools so that the agent can reason about which tools usually follow or support others.

Select the next tool from graph context

Use the tool-world model to move through related tools rather than scanning the whole catalog from scratch each time.

Execute and inspect the result

Run the chosen tool and read its output so that later choices depend on actual state rather than only the planned chain.

Update the plan with feedback

Use real execution results to adjust later steps because tool failures or unexpected outputs can change the correct route.

What the paper changes

The paper changes tool orchestration from a flat next-tool choice into a bilevel process with a planner above and a tool navigator below.

The hidden quantity

The hidden quantity

measured quantity  =  navigability of the tool world

The hidden quantity is navigability: how easy it is to move from the current tool state to a useful next tool without searching the whole catalog. Navigability matters because many tools are only sensible after specific earlier calls. A refund tool, for example, is rarely useful before a customer lookup and an order lookup.

The system estimates navigability from a graph that captures tool relations observed in structure and behavior. A tool that often follows another tool or consumes its output sits closer in that graph, so the navigator can focus on a smaller and more relevant neighborhood.

Why it works

Why the two levels help

The upper level removes unnecessary tool use. If the task can be answered directly or needs clarification first, the planner can stop there. That matters because needless tool calls add delay and also create more opportunities for later mistakes.

The lower level reduces search confusion inside a tool chain. Once the planner decides that tools are needed, the relation graph narrows the candidate set by following tools that are structurally or behaviorally close to the current step. That helps because the agent no longer reconsiders every tool at every turn. Feedback closes the loop by correcting the route after real calls, so the chain can recover when outputs differ from expectation.

Math after the picture

A compact score for the next tool

First in words:

Score a candidate next tool by combining how well it fits the task goal and how well it connects to the current tool state in the relation graph.

Then the compact form:

next_score(tool_j) = plan_fit(tool_j) + alpha * graph_link(current_state, tool_j)

Every symbol:

tool_jone candidate next tool
plan_fit(tool_j)how well tool_j matches the current high-level subgoal
graph_link(current_state, tool_j)how strongly the current state connects to tool_j in the tool graph
current_statethe current point in the tool chain after earlier calls
alphahow much the navigator relies on the graph relation score
A tiny worked example
Suppose the current state already contains a customer identifier and the plan goal is to inspect orders.
An order-lookup tool gets plan_fit 0.8 and graph_link 0.9.
A refund tool gets plan_fit 0.5 and graph_link 0.3 because it usually comes later.
If alpha is 0.5, the order tool scores 0.8 + 0.45 = 1.25.
The refund tool scores 0.5 + 0.15 = 0.65.
The navigator chooses the order tool because it fits both the goal and the graph neighborhood.

The exact training details are richer, but the paper's core idea is this combined choice: follow the plan while staying near the part of the tool world that the current state makes usable.

What can go wrong

What can go wrong

The tool graph can be incomplete. If important tool relations are missing, then the navigator may stay in the wrong neighborhood because the true next tool looks artificially far away.
Bad early planning still hurts. If the upper level decides on the wrong subgoal, then even good navigation will follow the wrong route because the lower level only optimizes within that chosen plan.
Real tools can behave unpredictably. A tool may return missing fields or unexpected errors, so the chain may need recovery logic because the planned next step may no longer be valid.
Done right. The system works best when tool relations are well modeled and execution feedback is used aggressively, because then wrong turns can be corrected before they cascade.
What a runnable demo should prove

What a runnable demo should prove

Build a toy tool catalog for customer support with tools for account lookup, order lookup, refund check, refund execution, and user clarification. Create tasks that vary from direct answers to multi-step chains. Then compare a flat next-tool chooser against the bilevel setup.

Measure task success, number of steps, and failure recovery after one tool returns an unexpected value. The demo should show that the relation-aware navigator uses fewer unnecessary calls because it stays inside a relevant part of the tool graph.
