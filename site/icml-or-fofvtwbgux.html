Investigating Component Contributions in Multi-Agent ML Systems

Ablating each component in ML engineering agents reveals that feedback loops work harder than agent teams.

Paper explainersAll themesAgents & Tool Use

Autonomous agents that write and debug code for machine learning have become popular, but comparing them is confusing because each system mixes together different techniques—splitting the work among agents, repeating attempts with hints from past tries, storing memories, and planning ahead—in different ways. You cannot tell which technique is actually doing the heavy lifting. This paper runs 4,000 controlled experiments turning each component on and off one at a time to measure its true contribution.

Zero assumption version

Why comparing agent systems is stuck

When researchers build an autonomous agent to solve machine learning problems—say, to write training code and fix errors—they combine multiple techniques at once. One system uses three agents that divide the work, stores memories of past attempts, and loops back to try again with better hints because multiple attempts increase chances of finding a working solution. Another uses one agent with two-step planning and less memory. A third system layers on a different memory format because storing what failed before helps avoid repeating the same mistakes. Because each system is a tangled pile of these ideas, nobody can tell which one actually matters. Is the system winning because three brains solve more than one, because it remembers what it tried before, or because it gets a second chance to fix its mistakes? Unclear.

The naive fix is to ask: take System A and System B, run both, and see which wins. But this does not work, because they might win on different tasks. Also, the training data for large language models probably included examples of ML code from past competitions, so a system wins not because its technique is clever but because it has seen similar problems before. This hidden contamination ruins the comparison.

In one sentence. Turn each component on and off in 4,000 controlled experiments to measure how much each one actually helps, because the only way to know if something matters is to remove it and see whether performance falls.

What the paper changes

The single change

The paper turns components off one at a time: multi-agent coordination (agents working together), iterative feedback (looping to try again with hints from past failures), memory management (storing what the agent has learned), and planning ahead. For each absence, it measures how much the system's performance drops.

the object it moves  =  Component presence—off or on
The hidden quantity

The contribution of each component

measured quantity  =  Performance drop when component is removed

The hidden quantity is the amount of performance lost when each component is turned off. This measures each component's true contribution, because the only way to know if something is doing work is to remove it and see the performance gap. Concretely, measure the performance of the system with the component present, then measure it with the component removed, and record the drop. A big drop means the component is essential, because if removing it breaks the system the component was doing important work; a small drop means it is window dressing because the system barely notices when it is gone. When you subtract the two scores, you measure pure causality—this component alone is responsible for this much improvement.

The paper estimates this by running 4,000 experiments—taking each agent system, each variant of each component (on or off), and each live competition problem, and recording whether the agent solved the problem. A component's true contribution is the average performance drop across all these situations.

Why it works

Why feedback matters more than team size

An agent that solves one hard problem and learns nothing from the failure is stuck. An agent that tries, fails, reads the error message, changes its approach, and tries again learns to fix its mistakes. Each loop tightens its reasoning.

When the team grows from one agent to three, they can divide the work—one writes code, one tests, one rewrites. But if each agent is stuck in the same rut, dividing the work just means three stuck agents. If all three agents can feed their failures back into the next attempt, they learn. The paper finds that even one agent with strong feedback beats three agents without it. Feedback is the motor; team size is secondary.

Measuring component contribution

First in words:

contribution of component C = success rate with C on minus success rate with C off

Then the compact form:

contribution_C = P(success | C=on) - P(success | C=off)

Every symbol:

contribution_CHow much component C helps, measured as a probability (ranges from 0 to 1)
P(success | C=on)The fraction of problems solved when component C is turned on
P(success | C=off)The fraction of problems solved when component C is turned off
A tiny worked example
Suppose feedback loop is on: the agent solves 60 of 100 problems. Success rate = 60/100 = 0.60.
Turn feedback loop off: the agent solves 20 of 100 problems. Success rate = 20/100 = 0.20.
Contribution of feedback = 0.60 - 0.20 = 0.40. Feedback accounts for 40 percentage points of performance.
Suppose multi-agent is on: 58 of 100. Turn it off: 55 of 100. Contribution = 0.58 - 0.55 = 0.03. Multi-agent adds only 3 points.

Larger differences mean the component is doing more real work; small differences mean the component is noise.

What can go wrong

What can go wrong

Contaminated benchmarks hide the real story. If you test on old competitions, the language model has seen similar problems in its training data, so you measure memorization, not reasoning skill. The paper avoids this by testing on live competitions happening right now.
Turning off one component can hurt others. If you remove the memory but leave the feedback loop, the agent may spin its wheels trying the exact same wrong idea twice. Some combinations are unfair. The paper tests each component on its own and in realistic combinations.
The contributions are not additive. Multi-agent coordination might matter only when the feedback loop is weak. The paper does measure interactions, but naive addition of contributions will overstate the total.
Done right: systematic ablation on clean data. Run each component on and off across all systems and all uncontaminated problems, collect the numbers, report medians and ranges.
What a runnable demo should prove

What a runnable demo should prove

Build a simple agent system that solves small Python coding problems. Equip it with a feedback loop that reads error messages and rewrites code. Then turn the feedback loop off (so the agent writes once and stops). Measure how many problems each version solves. The version with feedback should solve far more. Then add multi-agent coordination (two agents that coordinate) and measure again. The improvement from adding agents should be much smaller than the improvement from adding feedback.

contribution_feedback = success_with_feedback - success_without_feedback; contribution_multiagent = success_with_agents - success_with_one_agent

The gap between feedback's contribution and multi-agent's contribution should be stark—feedback is the true engine.
