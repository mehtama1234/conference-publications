DeepEyesV2: Toward Agentic Multimodal Model

DeepEyesV2 teaches a multimodal system to call outside tools in the middle of a task, then use the returned results in the next step, so it can solve perception, calculation, and search tasks with the tool that matches the need.

Paper explainersAll themesAgents & Tool Use

A multimodal system can read text and inspect images, but many tasks also need actions outside the model itself. Some questions need a web search. Some need code execution for exact arithmetic. Some need an image operation such as cropping or reading a small region. This paper studies how to train one system to choose those actions at the right time and to continue the solution after the tool answer comes back. The main result is that direct reward training by itself does not produce steady tool use, because the system first needs examples that show what a good tool call looks like, what result to expect, and how to continue once the result arrives. DeepEyesV2 therefore uses two stages: a cold-start stage that teaches the pattern of calling tools, followed by reward training that sharpens when to call, which tool to call, and when to stop.

Zero assumption version

Why tool use does not appear just from reward training

A multimodal system receives text, images, or both, and produces the next written step. For many benchmark tasks that is enough. For real tasks it is often not enough. A search-heavy question may require fresh outside facts. A math question may require exact arithmetic. A visual task may require zooming into part of an image. If the system cannot call tools, it must guess or do the work internally.

A simple plan is to take a strong multimodal system and train it with rewards so it gets more reward when it solves the full task. The paper reports that this is not enough. The system does not reliably discover stable tool-use habits from reward alone, because it must learn several linked decisions at once: when to pause, how to write the tool call, how to read the returned result, and how to continue the answer after that result.

The paper's one-sentence move: Teach the system explicit tool-use patterns first, then refine those patterns with reward training, so that tool calls become useful actions instead of random detours.

The algorithm as a flow

What it actually does

Build tool-use training data

Collect examples where tool use helps, including the task, the tool call, the returned result, and the next written step, because the full sequence shows what successful tool use actually looks like.

Cold-start training

Train the system on those examples so it learns the basic pattern of when a tool call belongs in the solution.

Reward training

Continue training with rewards so the system can choose more carefully among image operations, code execution, and web search.

Handle returned results

Teach the system to read tool output and continue the reasoning instead of treating the tool call as the end of the task.

Evaluate across task types

Check real-world understanding, math, and search-heavy tasks to see whether the system uses the right tool for the right job.

What the paper changes

What the paper changes

The paper changes the training path for tool use. Instead of asking reward training to create tool-use behavior from scratch, it first teaches the action pattern directly with curated examples, then uses reward training to refine those actions.

the object it moves  =  the training path that creates tool-use behavior
The hidden quantity

The hidden quantity: how ready the system is to make a useful tool call

measured quantity  =  tool-call readiness

At each step, the system has an internal tendency toward one of several actions: continue writing, call an image tool, call a code tool, or call web search. The paper does not name one single number for this, but the whole training design depends on whether that tendency points toward a useful tool call at the right time. This page calls that hidden quantity tool-call readiness.

Cold-start training raises tool-call readiness in states where a tool clearly helps, because the system repeatedly sees the full action pattern. Reward training then reshapes that readiness by giving higher reward to action choices that end in correct answers, so that unneeded tool calls lose preference and helpful tool calls keep preference.

Why it works

Why the two-stage path works

Reward training is good at sharpening a behavior that already exists, but it is weaker when the behavior is a long chain with several fragile steps. Tool use is such a chain. The system must notice that a tool is needed, emit the right call format, wait for the result, read that result, and fold it into the next step. If any one link is missing, the whole action path breaks and reward becomes sparse.

Cold-start training fixes that by supplying complete examples of the action path. The system first learns that tool calls are valid moves inside a solution and sees what successful continuation after a tool result looks like. Reward training then has a better starting point, because it is refining an existing pattern rather than trying to invent it. This also explains the task-adaptive behavior reported in the paper: image operations rise on perception tasks because those tasks need local visual evidence, code execution rises on calculation tasks because exact arithmetic removes avoidable mistakes, and search rises on search-heavy tasks because outside facts are missing from the prompt itself.

Math after the picture

A compact way to write the action choice

First in words:

At each step, pick the action with the highest learned score after observing the current state. The possible actions are continue writing, call image tool, call code tool, or call web search.

Then the compact form:

a_star = argmax over a in A of score(state, a)

Every symbol:

a_starthe action chosen at the current step
Athe set of allowed actions, such as write, image tool, code tool, and web search
statethe current task context, including prompt, image, previous steps, and any returned tool result
score(state, a)the learned score for taking action a in the current state
argmaxpick the action with the highest score
A tiny worked example
Suppose the current task asks for the total number of objects in a cropped image region and then asks for the sum of two visible numbers.
The current scores are: keep writing 0.2, image tool 0.8, code tool 0.1, web search 0.0.
The chosen action is image tool, because 0.8 is the highest score.
After the crop result returns, the new scores are: keep writing 0.3, image tool 0.1, code tool 0.7, web search 0.0.
Now the chosen action is code tool, because the task has moved from seeing to exact arithmetic.
The system then writes the final answer after the code result returns.

This equation is only a compact summary. The paper's real point is not the notation itself, but the training path that raises the right action score in the right state.

What can go wrong

What can go wrong

Cold-start data teaches weak habits. If the curated examples contain poor tool choices or poor continuations after tool results, the system will copy those habits before reward training begins.
Tool interfaces differ from training. If the runtime tool format or returned output changes too much, the learned action pattern may fail because the system no longer recognizes how to write the call or read the result.
Reward overvalues tool use itself. If the reward setup favors calling tools too often, the system may add needless steps, which slows the solution and can create more places for failure.
Done right. When the training data covers cases where tools truly help, and the reward stage favors correct end answers rather than raw tool-call count, the system learns to call tools only when outside evidence or exact computation is actually needed, because needless tool calls stop earning reward while useful ones keep earning reward.
What a runnable demo should prove

What a runnable demo should prove

Build three small task groups: perception tasks that need zoom or crop on an image, arithmetic tasks that need exact calculation, and search tasks that need an outside fact. Train one system with direct reward training only and another with the paper's two-stage path. Log every action step: whether a tool was called, which tool was chosen, whether the returned result was used in the next step, and whether the final answer was correct.

The key check is not only end accuracy. The demo should also show whether the system matches tool choice to task type, because that is the paper's central behavioral claim. The two-stage version should call image operations more often on perception tasks, code execution more often on arithmetic tasks, and search more often on search-heavy tasks, because each tool supplies the missing evidence those tasks need.

tool_match_rate = correct_tool_choices / tasks_that_needed_a_tool

A convincing demo will show higher answer accuracy and higher tool-match rate for the two-stage system, because the cold-start stage teaches the action pattern and the reward stage refines when that pattern should be used.
