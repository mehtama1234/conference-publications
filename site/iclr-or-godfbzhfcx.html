PCE: From Assumptions to Uncertainty-Aware Planning

Convert hidden assumptions in LLM reasoning into a decision tree that picks actions by uncertainty, not constant talking.

Paper explainersAll themesAgents & Tool Use

When robot arms and people work together to move objects around a room, the robot cannot see everything (the person might be holding something, or might change their mind). Right now robots handle this by asking constantly: what are you doing? But that costs time and breaks focus. This paper shows how to convert the murky assumptions buried in an LLM's reasoning into a clean decision tree that picks the best action based on honest uncertainty, without needing to ask every second.

Zero assumption version

Why robots ask too many questions

A robot in a shared workspace sees a person move an object. But the robot cannot see behind furniture. It does not know if the person will come back, or swap the object for something else, or drop it. Right now the safe move is to ask: what do you want to do? But if the robot asks 100 times an hour, the person gets annoyed, the conversation drifts, and the whole plan falls apart.

A beginner might try: ignore what you do not know. Just guess the most likely scenario and act. That fails fast: if the robot guesses wrong once, the person and robot collide, or worse, the human partner stops trusting the robot at all. The core problem is that uncertainty is real and invisible, and silence costs money (wasted time, lost focus, broken teamwork).

In one sentence. The paper extracts hidden assumptions from an LLM's thinking and builds a decision tree that scores each scenario by likelihood and payoff, then picks actions without asking for updates.

The algorithm as a flow

What it actually does

Planner: extract raw assumptions

LLM thinks aloud; PCE harvests the implicit scenarios (object in cabinet, or shelf, or person keeps it).

Composer: build a tree

Each scenario becomes a path; each path maps to an action the robot could take (move to cabinet, move to shelf, standby).

Scorer: likelihood + payoff

For each path, estimate how likely it is (from the LLM trace) and how much it helps the goal; scoring both matters because a very likely scenario that does not help the goal should not be picked over a rarer scenario that finishes the task.

Evaluator: pick the best path

Multiply likelihood by payoff; divide by cost (how many robot moves, how much energy); pick highest score.

Act and learn

Robot executes; if reality matches the top scenario, confidence rises; if not, the tree updates for next time.

What the paper changes

What the paper changes

Instead of the robot sending repeated queries (which interrupt the person), the paper changes the robot's decision-making from live polling to structured reasoning. Rather than getting fresh information from the person, the robot extracts what the LLM already assumes, builds that into a decision tree with explicit confidence levels, and commits to action.

The hidden quantity

The hidden quantity: scenario likelihood weighting

measured quantity  =  likelihood-weighted path score

A likelihood weight is a single number from 0 to 1 that says how confident the robot is that a given scenario will happen. For example, if the LLM's reasoning traces mention the object going to the cabinet five times and the shelf once, then cabinet gets a higher weight. The paper estimates these weights by counting how often each scenario appears in the LLM's chain-of-thought reasoning.

The paper uses these weights to move beyond blind guessing. Instead of picking the single best guess, it builds a weighted average: take all plausible scenarios, score how much each one matters, and act on the scenario that combines high likelihood with high payoff. This is the hidden quantity that turns chatter into certainty: the robot does not need to ask because the tree already assigns a confidence level to each branch.

Why it works

Why it works: turning hidden reasoning into honest decisions

An LLM's reasoning trace (its thinking-aloud) is messy but honest. When it writes 'the person might put it in the cabinet or on the shelf or keep it in hand,' the robot can count: cabinet appears 5 times, shelf 2 times, hand 3 times. Those counts are not perfect, but they reflect what the LLM actually considers likely given the context. By extracting and weighing these scenarios, the paper converts vague unease (I am not sure what will happen) into precise decision logic (Cabinet is 50% likely and has good payoff, so prepare for Cabinet with 90% confidence, and have a backup for Shelf).

The tree structure is the key: each path from root to leaf is a concrete plan (if Cabinet, move to position X; if Shelf, move to position Y). Instead of asking the person for clarification, the robot executes the plan that scores highest. If reality matches that plan, the robot wins without any communication cost. If reality does not match, the tree lets the robot detect the mismatch quickly and pivot. This is faster and cheaper than constant polling because the robot has already committed to a coherent strategy, informed by the LLM's own reasoning, rather than leaving every micro-decision open until the human answers.

Math after the picture

The scoring equation: which action to pick

First in words:

For each scenario path, multiply how likely it is by how much good it does if true, then divide by the cost to execute it. Pick the path with the highest score.

Then the compact form:

path_score_j = P(scenario_j) × U(goal|scenario_j) / C(scenario_j)

Every symbol:

path_score_jhow good path j is: likelihood times payoff divided by cost
P(scenario_j)probability: how often this scenario appears in the LLM trace, as a fraction
U(goal|scenario_j)payoff: how much progress toward the goal if this scenario is true
C(scenario_j)cost: time, energy, and tokens to execute this path
argmaxpick the path with the highest score
A tiny worked example: cabinet vs. shelf
Cabinet scenario: P = 5/10 = 0.5, U = 8 (we finish picking up fast), C = 2 (move is short). Score = 0.5 × 8 / 2 = 2.0
Shelf scenario: P = 2/10 = 0.2, U = 7 (also good), C = 3 (climb required). Score = 0.2 × 7 / 3 = 0.47
Hand scenario: P = 3/10 = 0.3, U = 0 (person keeps it, we do nothing), C = 0 (cost is 0). Score = 0.3 × 0 / 1 = 0.0
Cabinet wins with 2.0 > 0.47 > 0.0. Robot moves to cabinet without asking. (Real numbers are much larger and noisier; this is illustrative.)

The robot picks the path with the highest score, combining what the LLM thinks is likely with what actually matters for finishing the task.

What can go wrong

What can go wrong

The LLM's reasoning is shallow or contradictory. If the LLM does not think through the scenario carefully, the scenario counts will be noise, and the tree will score bad paths high. PCE is only as good as the quality of reasoning the LLM produces.
Scenario extraction misses implicit assumptions. The Planner step counts explicit mentions, but misses unstated hunches. If the LLM assumes the person is in a hurry without saying so, that assumption is lost, and the tree cannot score the scenario fairly.
The payoff function is hard to measure in advance. The Scorer needs to estimate U(goal|scenario) before the fact. If the estimate is wrong (we thought reaching the cabinet took 2 seconds but it took 10), the score is wrong and the tree picks the wrong path.
Done right: LLM reasons deeply, scenarios are explicit, and payoff estimates come from real data. PCE shines when the LLM has thought through multiple branches, each scenario maps to a concrete robot action, and payoff is measured from past runs or simulations.
What a runnable demo should prove

What a runnable demo should prove

Build a simple multi-agent task: a human and robot in a 3D room. Place an object (a box). The human decides secretly whether to move it to spot A, spot B, or keep it. Before moving, the human describes their plan to the robot (in natural language). The LLM reads that description and reasons aloud about the three scenarios. Extract the scenario counts from the reasoning. Build a 3-path decision tree, with payoffs set as time-to-goal for each scenario (e.g., if human chose A, payoff is 1.0 if robot predicted A, 0.5 if it predicted B). Set costs as robot move distance. Score each path. Have the robot commit to the top-scoring path without asking for a confirmation. Measure: success rate (did robot pick the human's actual choice?) and communication cost (number of messages). Compare against a baseline where the robot asks for every scenario.

success_rate = matches_found / total_trials, communication_tokens = messages_sent × avg_tokens_per_message

The demo must show that a robot using PCE reaches the goal more often and with fewer messages than one that asks repeatedly.
