Benchmarks and Agent Testing

Papers that create tests and benchmarks to measure how well agents can use tools and accomplish goals.

All themesField mapMathematicsAll explainers
What this is

Before you can improve something, you have to measure it, because without numbers you don't know if a change actually helped or if it just feels faster. This subtheme covers the tests and benchmarks researchers create to evaluate how well agents use tools. A benchmark is a standard problem set with known right answers: here are 1,000 questions, agents try to answer them by using available tools, and we score how many they got right, which lets researchers compare different agent designs fairly and track progress over time instead of just guessing. Some benchmarks test specific skills like whether agents can correctly chain tools together, and others are more open-ended, like 'solve this real-world research question'.

The challenge in building good benchmarks is that tool use is contextual and hard to judge automatically. Did the agent succeed because it is actually smart at planning, or because it got lucky and guessed right? If an agent takes a different but correct path to the answer, how do you score that? Some tools might be optional (you could use them but don't have to), and the benchmark has to figure out whether skipping them is smart or lazy. And there is constant pressure for benchmarks to become easier: agents and researchers figure out shortcuts, and the benchmark stops being a real test of capability.

Papers in this area create benchmarks that test specific aspects of tool use: can agents plan multi-step solutions? Can they recover from tool failures? Can they use tools they have never seen before? Some benchmarks are focused on real-world scenarios like writing code or querying databases, while others are more abstract. The best benchmarks are challenging enough that agents today only solve them some of the time, which means the benchmark still has life in it and motivates research to get better.

How the work breaks down

Work in this subtheme splits into five main directions. First, building the infrastructure that lets researchers quickly test many agents on many benchmarks without spending weeks on setup. Second, stress-testing agents with broken or noisy environments to find where they actually fail. Third, creating benchmarks for specialized domains like scientific research where tool use looks very different from web browsing. Fourth, figuring out what training data and architectural choices actually drive improvement. Fifth, tackling hard real-world scenarios—enterprise systems, large codebases, and memory across many sessions—where simple benchmarks stop being realistic.

Evaluation Infrastructure and Leaderboards

Building a good benchmark is half the battle, but comparing agents fairly across benchmarks is even harder. When each benchmark runs differently and each team tests on different hardware and software versions, you cannot tell if agent A is actually smarter than agent B or if it just got lucky. This group tackles the foundational problem: how do you set up a fair, fast, reusable way to run many agents across many benchmarks?

The Agent Leaderboard benchmark ran 21,730 agent attempts across 9 models and 9 benchmarks. Reducing evaluation time from weeks to hours lets researchers test new ideas sooner. It uncovered patterns that smaller studies missed: some agents work well on one task type but fail on others. DRBench tests enterprise research where agents search papers, synthesize insights, and suggest next steps. Testing diverse agents revealed where they fail in real work. The Tool Decathlon covers the broadest ground: the largest and most varied set of tasks for language agents, measured by whether the agent completes the work.

Handling Broken Environments and Complexity

An agent that works perfectly in the lab might break the moment you deploy it to the real world, where networks drop packets, screens have glitches, and the tool you need works a little differently than expected. This group measures how fragile agents really are and tries to harden them. The challenge is that real-world environments are messy in a thousand different ways, and you cannot test all of them. So researchers pick common types of corruption—garbled text, missing information, visual distortion—and see how badly agents fail.

AgentHijack found that current agents break easily: small glitches you would barely notice cause agents to fail. Testing training methods that teach agents to expect glitches helped, which means the brittleness is not fundamental—it is a training problem. ComplexMCP built a large sandbox with hundreds of tools that depend on each other, forcing agents to juggle dependencies and fix failures. Even the best models hit a ceiling at 60% success while humans solve it 90%, revealing gaps: agents do not recover when a tool call fails, they overestimate what they can do, and they stop trying instead of taking a different path. AgentNoiseBench tested how agents handle realistic problems—noisy sensor readings, latency, broken tools. Finding: agents vary wildly. Some tolerate problems fine; others collapse. This means benchmarks must test how agents fail in the wild, or deployment will surprise you with breakdowns.

Domain-Specific Tool Use

Tool use in a research lab looks completely different from tool use in a web browser. A scientist needs to search papers by relationship—'find work on X that cites Y'—not just by keywords. A geophysicist needs to fetch satellite imagery, transform it to standard coordinates, and extract specific numbers or measurements. These are not generic 'tool use' problems; they are domain problems with specialized structure. This group builds benchmarks and systems for those specialized domains.

SciAgentGym created a benchmark for multi-step scientific reasoning: agents see a research question and scientific tools—calculators, data loaders, simulators. They need to chain these tools to answer the question. The finding: a fine-tuned 8-billion-weight model outperformed Qwen3-VL-235B, a much larger model. Domain-specific training matters more than size. SciNet measures whether agents find papers based on how concepts relate, not just keywords. Agents trained on better search methods jumped from 20% to 45% accuracy, but the task stays hard—even optimized agents miss more than half. Earth-Agent unlocks a new domain by letting agents analyze earth observation data—satellite imagery of crops, ice sheets, weather. Instead of relying on what the model memorized, agents load raw data, transform it, and extract the specific information you asked for. This matters because agents are not just recalling answers—they are computing them.

Training Data and Component Contributions

Why does one agent outperform another? The answer matters because it tells you where to invest effort and research time. Is it the architecture—having multiple agents that coordinate? Is it the training data—examples of good tool use? Is it the way you prompt the agent? This group directly measures which parts of the pipeline actually help by testing them independently, so you know which design choices drive progress and which ones are distractions. The insight is usually that researchers assume something is important, but when you test it carefully, you find something different matters more.

Agent Data Protocol unified 13 different agent datasets scattered across the field—each testing something different, each using different tools and scoring. Combining them yielded a consistent 20% gain because mixing diverse training data exposes agents to more patterns and edge cases, so they learn more general skills. More varied examples beat clever architecture. Investigating Component Contributions took a different angle: do you need multiple agents that coordinate? The finding was counterintuitive. When an agent calls itself and refines its answer, that helped more than separate specialized agents because the feedback loop lets one agent fix its own mistakes. Multi-agent coordination often hurt, which means extra complexity did not compensate. This upends the assumption that coordination is always good. DIVE approached it differently: instead of mixing existing data, create 48,000 new training examples across 374 tools and diverse tasks. Training an 8-billion-weight model on this variety improved it by 22 points on unseen benchmarks—tasks it had never trained on—because seeing more tool combinations and task types teaches generalization. This shows diversity is a lever: more varied examples mean agents learn to adapt to new situations.

Real-World Complexity and Long-Horizon Tasks

Benchmarks often test whether an agent can solve one problem in isolation. Real systems are messier. An agent might need to accomplish a goal across multiple sessions, remembering what it did yesterday and not undoing it. It might need to navigate an enterprise system with access controls and hidden state. It might need to generate hundreds of thousands of lines of code across multiple files and make sure they all fit together. These tasks break agents in new ways that simple benchmarks miss.

EnterpriseOps-Gym measures whether agents can handle stateful systems where your actions have side effects. You cannot just try random things because some changes are hard to undo. Even the best model (Claude Sonnet) only solves 34% of tasks, showing that enterprise readiness is far away. NL2Repo-Bench focuses on code generation at scale: instead of writing one function, generate an entire repository with multiple files that work together. Frontier agents only hit 40% success, and the failures show a pattern: agents start confidently but lose track of what they have already written, generate code that contradicts earlier decisions, and stop early instead of finishing. Benchmarking Agent Memory in Interdependent Multi-Session Agentic Tasks reveals another failure mode. Models that seemed to have good memory—tested on tasks like reading long documents—perform poorly when that memory needs to be used for decision-making across sessions. The gap means benchmarks were measuring the wrong thing: remembering a number is different from using that number to avoid mistakes you made before.
