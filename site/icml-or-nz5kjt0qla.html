DeepImageSearch: Benchmarking Multimodal Agents for Context-Aware Image Retrieval in Visual Histories

Turn image retrieval into a multi-step search problem where the agent must navigate a sequence of past visuals to recover context that one image alone does not contain.

Paper explainersAll themesAgents & Tool Use

Standard image retrieval often assumes that one query can be matched to one image in isolation. This paper studies a harder setting where the needed clue is spread across a visual history. The agent has to explore, remember earlier findings, and decide which views to inspect next. DeepImageSearch builds a benchmark for that setting and tests whether multimodal agents can retrieve the right target when context is distributed across time and place.

Zero assumption version

Why isolated image matching breaks on context-dependent search

Some retrieval tasks cannot be solved by looking at one picture and one query alone. The needed clue may depend on what happened earlier in the stream, what was nearby in another view, or how several scenes relate to each other.

When context is distributed across a history, retrieval becomes a search problem. The agent must decide where to look next, what to remember from earlier views, and when it has gathered enough evidence to name the target.

The paper's move in one sentence. Benchmark retrieval as autonomous exploration over visual histories so that agents are tested on whether they can gather and use distributed context.

What the paper changes

What the paper changes

The paper changes the retrieval unit from a single query-image pair to a search process over a connected visual history. It asks whether the agent can recover context before it decides what to retrieve.

the object it moves  =  the retrieval policy that chooses where to inspect next and what evidence to keep
The hidden quantity

The hidden quantity

measured quantity  =  where the decisive context is located in the visual history

The key hidden quantity is the location of the useful context. The agent knows the query, but it does not know which part of the visual history contains the clue that resolves it.

That hidden location can span several positions. One view might reveal a place, another might reveal an object, and a later one might connect them. The agent needs memory and search because the answer emerges only after these clues are combined.

Why it works

Why this works: convert retrieval into guided exploration

A plain retriever fails here because it scores isolated similarity. When the clue is distributed across several views, isolated scoring misses the relation that actually answers the query.

DeepImageSearch addresses this by giving the agent search actions and memory. The agent can inspect one part of the history, store a clue, move elsewhere, and combine the evidence later. This works because the retrieval decision is postponed until enough context has been gathered.

Math after the picture

Score a search path by clue gathering and final retrieval

First in words:

A simple summary is to score each search path by how well it gathers useful context and whether the final retrieved item is correct. Paths with both properties should rank higher.

Then the compact form:

search_score(path) = retrieval_value(path) + delta * context_value(path)

Every symbol:

search_score(path)overall value of one exploration path through the visual history
retrieval_value(path)quality of the final retrieved target
context_value(path)usefulness of the clues gathered during navigation
deltaweight on gathered context
A tiny worked example
Path A jumps to a target after one view.
Its retrieval value is 4 and its context value is 0, so with delta equal to 1 its total score is 4.
Path B inspects three linked views, stores a clue, and then chooses the target.
Its retrieval value is 4 and its context value is 3, so the total score is 7.
The later path is better because it collected the missing context before deciding.

The paper uses a fuller framework, but this score captures the reason an agentic approach can help when context lives across a history.

What can go wrong

What can go wrong

Search can wander through irrelevant parts of the history. If the navigation policy is weak, the agent may spend many steps chasing unhelpful clues because the correct branch was not recognized early.
Memory summaries can discard the deciding detail. A stored summary may keep the broad story while dropping the exact clue needed later, so the final decision still fails.
Benchmark queries may favor certain clue patterns. If query construction repeats similar forms, agents can learn those patterns too closely because they see the same style of distributed clue again and again.
Done right. The benchmark is useful because it tests whether retrieval systems can search for context rather than only score isolated similarity.
What a runnable demo should prove

What a runnable demo should prove

Build a small connected photo history, such as a walk through a building with several rooms. Ask queries whose answer depends on combining clues from more than one image, such as identifying an item that was seen near one object and later moved to another place.

Compare a direct image matcher against an agent that can browse the history and keep notes. The demo should show that the browsing agent wins because it can collect clues across multiple views before naming the target.

The point is to show that context-aware retrieval is a search problem when the answer is distributed across a visual history.
