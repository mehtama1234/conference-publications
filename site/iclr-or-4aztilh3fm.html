TableDART: Dynamic Adaptive Routing for Table Understanding

A lightweight gating network picks the best view (text, image, or both) for each table, avoiding the costs and conflicts of processing every view the same way.

Paper explainersAll themesMultimodal

Tables are puzzles with two languages: words (the cell values and headers) and pictures (the rows, columns, grid structure). Traditional methods throw one away or force both through an expensive unified model. TableDART instead builds a tiny router that looks at each table-question pair and picks the best path—text alone, image alone, or a blend—reusing cheap pretrained models without costly fine-tuning.

Zero assumption version

Two languages, one model, no middle ground

Tables speak in two ways at once: words (cell text, headers, values) and structure (the grid layout, column alignment, row groups). A table is only intelligible when both work together.

Current approaches pick one language and pay for it. Text-flattening methods (write each row as a sentence) preserve every word but trash the structure—a model sees table data as a jumbled list and has to reconstruct what was obvious in the grid. Image methods keep the visual structure perfectly but struggle to read exact numbers and cell text with precision, especially in small fonts. Hybrid approaches try feeding both into one giant unified model at once, but this forces every view through the same expensive machinery whether it helps or hurts — wasteful because each input pays to run models it does not need, and when text and image disagree (say, a rotated column label), the model gets conflicting signals with no way to arbitrate.

The real trap. Running both views through the same costly unified model every time, on every query, means you pay for redundant processing and conflicts, without knowing which view would have been enough.

The algorithm as a flow

What it actually does

Router scores the table-question pair

Lightweight MLP reads question and table summary, outputs three scores for Text, Image, Fusion.

Pick the winning path

Choose path with highest score. Do NOT run the other two. Save compute.

Process via chosen pretrained model

Text query goes to text LLM; image query to vision model; if Fusion, run both but only send the outputs forward.

Cross-modal agent reconciles

If Fusion was chosen, an agent compares text and image outputs, picks the better one or builds a new answer by reasoning across both.

Final answer returned

Only one model computed; routing saved redundancy and avoided conflicting signals.

What the paper changes

What changes

TableDART changes which path a table-question pair travels: it routes each query to Text-only, Image-only, or Fusion instead of forcing all queries through all views identically.

the object it moves  =  routing path
The hidden quantity

Path choice confidence

measured quantity  =  routing score per path

The hidden quantity is the router's confidence scores for each of the three paths. These numbers come from a tiny neural network (2.59 million parameters) that learns which view wins for which kind of table—a simple scoring, like a referee marking which lane is fastest for a particular runner.

The paper trains the router by watching which path tends to produce the correct answer on validation data, then learns to predict those decisions automatically. High routing scores for Text mean the question is mostly about exact values; high Image scores suggest the structure and layout matter more; high Fusion scores mean both views have clues.

Why it works

Why routing avoids the trap

When you force every table through the same unified model every time, you create two problems: (1) redundant compute—some tables need only text, some only structure, but you process both anyway; (2) conflicting signals—when text and image give different answers (a rotated label reads differently in each modality), the unified model has no principled way to pick, so it averages the noise.

TableDART's router decouples these paths. It first learned which path works best for different kinds of questions: numerical questions often benefit from text precision; layout-heavy questions like 'which column is widest' need the image; some need both. By routing, TableDART runs fewer models per query on average, saving compute. More importantly, it avoids conflicts: if it picks Text, the image's noisy signal never corrupts the answer; if it picks Image, text misalignments are irrelevant. When Fusion is needed, the cross-modal agent acts as a tie-breaker, selecting or synthesizing rather than letting conflicting signals collide inside the model.

The net effect: accuracy improves because the model answers the question with the right language for the job, and efficiency improves because most tables use only one path.

Routing scores and path selection

First in words:

router outputs scores for each path (Text, Image, Fusion); select path with highest score; if selected path is Fusion, run both models and use agent to pick or blend

Then the compact form:

path_chosen = argmax(score_text, score_image, score_fusion)

Every symbol:

score_textrouter's confidence that Text-only path will work best
score_imagerouter's confidence that Image-only path will work best
score_fusionrouter's confidence that Fusion (both views) is needed
argmax(...)pick the path with the highest score (the router's best guess)
A tiny worked example
Table: price list with 50 rows. Question: 'what is the cheapest item?'
Router computes: score_text=0.8, score_image=0.3, score_fusion=0.1
Argmax picks Text (0.8 is highest). Only text LLM runs; vision model skipped.
Text LLM reads 'item A: $5, item B: $3, ...' and outputs 'item B at $3'.
Result: correct answer, compute saved (vision model was not needed).
---
Different table: complex grid with merged cells and color coding. Question: 'how many blue cells?'
Router computes: score_text=0.2, score_image=0.7, score_fusion=0.3
Argmax picks Image (0.7 is highest). Image model runs; text LLM skipped.
Image model counts blue pixels directly from the grid picture.
Result: correct answer, compute saved (text precision was not needed).

The router learns these scores during training; it predicts which view will succeed and routes accordingly, avoiding the cost of running all three every time.

What can go wrong

What can go wrong

Router gets the call wrong. If the router picks Text but the answer needs visual structure (e.g., a rotated label or a complex layout), the text-only path will fail. This happens when the training data is biased or the question is ambiguous.
Conflicting signals without proper reconciliation. If Fusion is chosen but the cross-modal agent is weak, it may simply pick one output without actually reasoning. If text and image genuinely disagree, a naive selection loses information.
Overfitting the router to the training data pattern. The router learns from specific tables and questions; a new, unusual table type (e.g., a table with emoji or foreign scripts) may confuse the router into wrong decisions.
Works well when the router is trained on diverse tables. If the training set covers many table styles and layouts, the router generalizes better; similarly, if the underlying text and image models are good, the router has good paths to choose from, because the router can only pick well among views it has seen enough examples of.
What a runnable demo should prove

What a runnable demo should prove

Build a simple table set with three question types: (1) numerical queries (sum this column, find the minimum value); (2) layout queries (which column is widest, how many rows); (3) mixed queries (find the second-highest value in the tallest column). Train a router on a small validation set, recording which path (Text, Image, or Fusion) produces the correct answer for each query. Then run the router on test queries and measure: (a) accuracy of the chosen path; (b) fraction of queries that used each path; (c) average compute time per query.

accuracy = fraction of queries where chosen path gives correct answer; path_distribution = (% Text, % Image, % Fusion); speedup = baseline_compute_time / routing_compute_time

The demo proves routing works if: (1) accuracy stays high or improves (routing is not throwing away information); (2) different query types use different paths (the router is learning real distinctions); (3) total compute is lower (routing saves redundant work), which together prove routing keeps information because the right view still handles each query.
