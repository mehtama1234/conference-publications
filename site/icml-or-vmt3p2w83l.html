MCP-Persona: Benchmarking LLM Agents on Real-World Personal Applications via Environment Simulation

Build a benchmark for agents that use personal apps and accounts, because real tool use breaks in ways that generic public-tool benchmarks do not capture.

Paper explainersAll themesAgents & Tool Use

Many agent benchmarks focus on public information tools such as search, browsing, or generic APIs. Real personal tool use is harder. The agent must act through an individual account, respect personal state, interpret private histories, and recover from side effects that depend on that user's environment. MCP-Persona is a benchmark built for that setting. It simulates real personal applications and account-specific tools so researchers can measure where today's agents fail and why those failures appear.

Why public-tool benchmarks miss the hard part of personal tool use

An agent that performs well on generic tools may still fail badly on personal applications such as social platforms, chat systems, or work suites. In those settings, success depends on user-specific state: prior messages, account permissions, private data, and local conventions.

Generic benchmarks remove much of that complexity. They often test information lookup or public workflows where the environment is largely the same for every run. The paper argues that this hides an important weakness because real assistants must act correctly inside personalized environments where the same instruction can require different steps for different accounts.

The central move. Benchmark agents in simulated personal application environments, because evaluating account-specific tool use requires private state, permissions, and user history to be part of the task.

The hidden quantity is how much account-specific context a task depends on. Some tasks require only one obvious tool call. Others require reading personal history, checking permissions, selecting the right account object, and avoiding destructive side effects.

MCP-Persona makes that load visible by simulating personal environments directly. This matters because an agent can appear strong on generic benchmarks while failing as soon as personal state becomes part of the decision process.

Why it works

Why this benchmark reveals failures that earlier ones miss

A benchmark only tests what it includes. If the environment removes private state and personal branching, an agent never has to prove that it can reason about those factors. MCP-Persona includes them directly, so failures that would appear in deployment also appear during evaluation.

Environment simulation is important because personal applications cannot be benchmarked only by static text descriptions. The correct next step often depends on current account content and permissions. By simulating those details, the benchmark forces the agent to read state, choose tools accordingly, and recover when an early action was based on a wrong assumption.

This design produces stronger diagnosis because researchers can see whether failure came from missing state inspection, wrong tool selection, or poor handling of user-specific constraints. That is more actionable than a single task success number.

Math after the picture

Score success under personal-state constraints

First in words:

A simple summary is to reward successful task completion and subtract penalties for state misuse and failed recovery, because a personal-tool agent must do more than pick the right final tool once.

Then the compact form:

benchmark_score = success_rate - alpha * state_errors - beta * recovery_failures

Every symbol:

success_ratefraction of tasks completed correctly
alphapenalty weight on mistakes caused by ignoring or misreading user state
state_errorswrong actions caused by bad use of personal context
betapenalty weight on failure to recover after a wrong step
recovery_failurescases where the agent cannot repair the task after an early mistake
A tiny worked example
Agent A finishes 8 of 10 tasks, so success_rate = 0.8.
It makes 1 state-related mistake and 2 failed recoveries.
If alpha = 0.1 and beta = 0.1, its score is 0.8 - 0.1 - 0.2 = 0.5.
Agent B finishes 7 of 10 tasks but has no state errors and no failed recoveries.
Its score is 0.7, so it ranks higher because it handles personal context more reliably.

The benchmark reports richer metrics than this sketch, but the core idea is to value correct completion only when the agent respects personal state and recovers from mistakes.

What can go wrong

What can go wrong

Simulation may still simplify real personal environments. If the simulated apps omit messy edge cases, the benchmark may understate deployment difficulty because real user environments contain more irregular state and more surprising side effects.
Agents may overfit the benchmark tasks. If the task set is narrow, an agent can learn benchmark-specific habits because repeated patterns reduce the need for general personal-state reasoning.
Single-number reporting can hide failure types. If users look only at overall completion, they may miss whether errors came from bad permission handling or bad state reading, because those failure sources need different fixes.
Done right. The benchmark is most useful when it preserves detailed personal state and reports detailed failure categories, because developers then learn exactly which part of personal tool use is blocking reliable deployment.
What a runnable demo should prove

What a runnable demo should prove

Build a small simulated environment for two or three personal applications such as messaging, social posting, and document sharing. Give each test user different histories and permissions. Run several agents on the same tasks and log whether they inspect user state before acting, whether they choose the correct tool path, and whether they recover after a wrong action.

The demo should show that public-tool competence does not carry over automatically to personal tools, because the benchmark's value comes from exposing account-specific failure modes.

personal_reliability = successful_tasks / (1 + state_errors + recovery_failures)

A convincing demo must show that personal state changes the correct workflow, because without that property the benchmark would collapse back into a generic tool-use test.
