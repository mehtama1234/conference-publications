ScreenParse: Complete Screen Parsing from Dense Labels

Teaching a vision-language model to parse entire screens densely (all UI elements at once) instead of sparsely (just the one element needed for the task) makes agents understand layouts better and transfer to new interfaces.

Paper explainersAll themesMultimodal

Computer-use agents that click and type on web screens need to first understand the full structure: which buttons, text fields, and text labels exist, where they are, and what they say. Most training datasets today label only the one element relevant to each specific task step. This sparse labeling leaves the model ignorant about the full screen — it learns shortcuts that work for one task but fail when layouts change. ScreenParse fixes this by providing dense labels: every visible UI element is marked, across 771,000 diverse web screenshots. The paper then trains a compact vision-language model (a model that reads images and generates text) with 316 million numbers to read the entire screen structure at once, using a weighted loss that emphasizes structure (positions and element types) over descriptive text.

Zero assumption version

Sparse labels leave blank spots in screen understanding

Today's computer-use agent datasets label only the single UI element (a button, a text field, a link) relevant to each task step. If the task is to click a submit button, only the submit button gets labeled; the text fields, checkboxes, and other elements on that screen are invisible to the training.

A beginner might assume that is fine: the agent only needs to find the one element it has to act on. But it breaks because: if the same website rearranges its layout in a real deployment, the agent has no internal model of what a typical screen looks like. It has learned to spot a specific submit button in a specific place, not to read the general structure of a form. Worse, it cannot reason about spatial relationships (is the email field above or below the password field?) or element roles (is this a link or plain text?). The model learns to exploit the specific patterns in its training data and fails when it encounters a screen with a different design.

Sparse labels also create a broken training loop: the model keeps finding shortcuts within the supervised examples instead of building a deep, stable understanding of screen layouts.

The fix in one sentence. Label every UI element on every screen (not just the task-relevant one). This forces the model to build an inventory of all elements, their positions, and relationships. A model that has seen all buttons, fields, and text on a screen learns general patterns like 'buttons cluster at the bottom' or 'required fields have an asterisk.' These patterns transfer to new screens.

The algorithm as a flow

What it actually does

Render web pages automatically

Visit diverse URLs, take screenshots, keep the full layout intact.

Extract all UI elements from the page structure

Read the page code; list every button, field, text box, image, and their positions.

Feed each screen to a large language model for refinement

VLM looks at the full screenshot and the proposed labels, fixes misclassifications and missing elements.

Convert to ScreenTag markup

Encode the dense list: 'button at (100,200) labeled Submit; text field at (80,150) for email; etc.'

Train with structure-aware loss

Make errors on position and type labels cost more than text errors. This forces the model to learn spatial layout first because correcting a position error saves more loss than correcting a text typo. The model focuses its limited numbers on the harder, higher-value task.

What the paper changes

What the paper changes: from sparse to dense supervision

The paper does one thing: replace a training dataset that marks one element per screen with a dataset that marks all elements. Instead of the learning goal being 'find this one button,' it becomes 'parse the entire visible structure.'

The model output changes too: instead of predicting the coordinates of a single element (or just which element is relevant), it predicts a structured string (ScreenTag) that encodes every element's type, position, and text in order.

The hidden quantity

The hidden quantity: structure importance per output symbol

measured quantity  =  Structure-critical output weight

The paper measures a hidden quantity: for each output symbol in the ScreenTag sequence, how critical is it to getting the layout right? A symbol that says 'button' or specifies coordinates (like x=100) carries more weight than a symbol that says 'submit button' or repeats descriptive text.

The paper estimates this by applying extra loss weight to output symbols that encode positions and element types, because errors in those locations break the agent's ability to interact. A typo in button text does not stop the agent from clicking; a misplaced coordinate or wrong element type does.

Why it works

Why dense labels and structure-aware loss work together

The core mechanism is that the model learns a richer internal model of screen layouts when it sees all elements, not one. Here is the causal chain:

Dense annotation creates a complete training target. When every element is labeled, the model must learn to produce a full inventory of the screen. It cannot take shortcuts (e.g., just spotting a red button). It must learn patterns: 'buttons are usually followed by text fields,' 'checkboxes cluster together,' 'headers span the top.' These patterns generalize to new screens.

Structure-aware loss aligns optimization with the agent's real task. A standard loss treats all prediction errors equally. But the agent does not care if the text content is slightly off; it cares if the position or type is wrong (a button versus a checkbox). By upweighting position and type symbols in the loss, the training focuses the model's learning on the spatial and functional structure first, descriptive text second. This is efficient: fewer of the model's numbers spend effort on what matters.

Compact model size stays possible. Because the loss tells the model to focus on structure, a small model with 316 million numbers can achieve high accuracy on the ScreenParse benchmark. Larger models would memorize text details; the structure-aware loss guides a small model toward what matters.

The structure-aware loss formula

First in words:

Loss equals the cross-entropy for each predicted token, multiplied by a weight that depends on whether the token encodes structure (position, type) or descriptive content (text). Structure tokens get higher weight.

Then the compact form:

Loss_total = sum_i (w_i * CE(pred_token_i, true_token_i)) where w_i is high for position and type tokens, low for text tokens

Every symbol:

Loss_totalTotal training loss (smaller is better)
sum_iAdd up the loss over every token i in the ScreenTag sequence
w_iWeight for token i: high if token is position or type, low if token is text content
CE(pred, true)Cross-entropy: penalty for predicting the wrong token (standard classification loss)
pred_token_iWhat the model predicted for token i
true_token_iCorrect token according to the label
A tiny worked example: two elements
Element 1: Button at position x=100, y=50, labeled 'Submit', text='Click here to proceed'.
Tokens: [type:button, x:100, y:50, text:submit, text:click, text:here, text:proceed] (7 tokens).
If w_structure = 10.0 and w_text = 1.0:
Token loss for 'type:button' = CE(pred, true) × 10 = 0.2 × 10 = 2.0 (high because type matters).
Token loss for 'x:100' = CE(pred, true) × 10 = 0.3 × 10 = 3.0 (high because position matters).
Token loss for 'text:click' = CE(pred, true) × 1 = 0.1 × 1 = 0.1 (low because text is secondary).
Total loss = 2.0 + 3.0 + ... ≈ 15.0. If text tokens were equally weighted, total ≈ 20.0.
Result: model learns position and type first; text is a bonus.

The weight for each output symbol is usually a fixed number (10 for structure, 1 for text) or learned during training. Upweighting forces the model to focus on positions and types over text descriptions.

What can go wrong

What can go wrong

Too much weight on structure; text is unintelligible. If the loss weight for text tokens is too low (w_text << 1), the model stops learning what text says. A button labeled Submit might be predicted as Submit_typo. The agent still clicks the button (position is right), but it cannot understand what the page is asking. Fix: balance the weight ratio so text is legible, just not the focus.
Annotation noise in the dense labels. The VLM-based refinement step tries to clean up labels, but real web pages have overlapping elements, hidden elements, and ambiguous markup. If too many elements are mislabeled in the training set, the model learns incorrect structure. Fix: aggressive quality filtering and human spot-checks on a random sample.
Overfitting to the web layout taxonomy. The model is trained on 55 standard UI element classes (buttons, text fields, etc.). If a deployed screen uses custom elements or a different taxonomy, the model will misclassify. Transfer to new applications requires retraining or fine-tuning.
Done right: balanced loss weight, clean annotations, and architecture transfer. With a careful balance (structure weight much higher than text weight, roughly 10 to 1), aggressive filtering, and a pretrained Granite model (initialized on document structure tasks), the method generalizes well to unseen websites and even to other vision-language models when fine-tuned on ScreenParse.

What a runnable demo should prove

A concrete demo would show: (1) load a real web page never seen in training, (2) run the ScreenVLM model on a screenshot of that page, (3) decode the ScreenTag output, (4) visualize the predicted bounding boxes and labels overlaid on the screenshot, (5) compare with ground truth (if available) or with a sparse-supervised model's output. The sparse model will miss most elements and misplace many boxes because it only learned to spot one element per screen. The dense model will label nearly every button, field, and text block correctly positioned because it trained on seeing the full structure. This stark difference is the visual proof that dense supervision works.
