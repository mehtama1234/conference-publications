RAPNet: Learning Sparse Coarse Operators for Faster Multigrid Solving

A machine-learning system learns which connections to keep when building fast shortcuts through a linear equation solver, so the solver runs billions of times without rebuilding.

Paper explainersAll themesOptimization

Solving huge sparse linear systems (matrices with mostly zeros) is a bottleneck in climate models, crash simulations, and graph analysis. Classical multigrid solvers create a hierarchy of coarser approximations to speed this up, but face a hard trade-off: keeping many connections makes solutions accurate but slow; throwing away connections makes the solver fast but unreliable. RAPNet resolves this by learning which connections to keep, using a graph neural network trained on small systems that generalizes to systems a million times larger.

The multigrid trade-off: can't have it both ways

Large sparse linear systems show up everywhere: modeling heat flow, predicting seismic waves, ranking web pages. A naive solver tries to answer directly but needs millions of operations. Multigrid solvers escape this by building a pyramid: start with the full fine-grained system, solve a coarser simpler version, refine the answer. Each coarser level connects to the level below, and solving is much faster because coarser systems are smaller.

But building that pyramid hits a wall. To make each coarser level, you discard connections (edges) from the fine level — this keeps the system small and fast. The problem: which ones? If you keep too many edges, the coarser system stays huge and you gain nothing. If you throw too many away, the coarser system becomes disconnected or inaccurate, and the solver diverges (the answer gets worse instead of better), because the coarse approximation can no longer represent the problem correctly — isolated regions of the graph have no way to exchange information, or critical links that the solver needs to correct errors are missing. Classical heuristics (rules written by humans) try to guess the right balance, but they fail often, especially on systems with unusual structure.

Each time you solve a related system — different numbers on the same structure, as in time-stepping simulations or design optimization loops — you have to build the whole pyramid from scratch. So the pyramid-building cost repeats across millions of solves.

In one sentence. RAPNet learns which edges to keep in each coarse level so the solver stays fast and accurate, and one learned pyramid works for billions of solves.

What the paper changes

What the paper changes

The paper replaces the classical heuristic (a human-written rule for which edges to keep) with a learned neural network that scores edges.

Edge importance: which connections matter most

The network learns a single number for each edge: how much that edge matters for the solver to converge quickly and accurately. High importance means the edge is on a path the solver uses; low importance means the edge is redundant or blocks convergence.

The paper estimates this by training the network on small systems where you can measure the exact loss (how far the solver's answer is from correct), then watching which edges the network learns to rank as important. The network's learned weights embed this importance directly.

Why it works

Why learning edge importance solves the trade-off

The core insight: edge importance is not a universal constant — it depends on the structure and values of the specific linear system. A classical heuristic uses the same rule for all systems (e.g., keep edges with magnitude above a threshold), but that threshold works well for some systems and terribly for others.

A learned network, by contrast, adapts its scoring to the input graph. It sees the neighborhood around each edge (nodes connected to it, their values, connectivity) and predicts: given this structure, does this edge matter? On the small systems used in training, this is exact: the network minimizes loss, so it learns which edges actually matter. On huge systems the network has never seen, the learned pattern still applies because the local neighborhood structure repeats: if a bridge-edge mattered in the training system, it matters in the large one too.

During setup (once), the network scores all edges and the solver builds one coarse pyramid. Then, for millions of solves of related systems (same structure, different values), that pyramid is reused without rebuilding. The cost of training and setup (amortized) is repaid by avoiding pyramid reconstruction on every solve.

Scoring edges to build the coarse system

First in words:

For each edge in the fine graph, the neural network computes a score. Edges with score above a learned threshold are kept in the coarse graph; below, they are discarded.

Then the compact form:

score_i = NN(fine_graph, edge_i); keep_i = (score_i > tau)

Every symbol:

score_ithe importance number the network assigns to edge i
NN(fine_graph, edge_i)the neural network applied to the fine graph and edge i
tauthe cutoff threshold for keeping edges (learned during training)
keep_i1 if edge is kept, 0 if discarded
A tiny worked example
Edge 1 connects a bridge node (high centrality). Network gives score 0.92. Threshold tau = 0.7. Keep it (0.92 > 0.7).
Edge 2 is a leaf (low centrality). Network gives score 0.45. Threshold 0.7. Discard it (0.45 < 0.7).
Edge 3 connects a critical path. Network gives score 0.88. Keep it.
Same threshold for all edges; network adapts the scores based on what it learned.

The network learns both the scoring function and the threshold, so the edge selection tightens or loosens based on the specific system structure.

What can go wrong

What can go wrong

Training on toy systems, failing on real scales. If the training graph is too small or structurally different from deployment graphs, the learned scoring will not generalize. RAPNet solves this with level-wise training: train on small subgraphs extracted from the multigrid hierarchy, so the network sees the same neighborhoods at all scales.
Discarding critical edges that the network missed. If the threshold tau is too aggressive (keeps too few edges), the coarse system becomes disconnected and the solver diverges. The paper tunes tau during training to stay conservative, guaranteeing connectivity.
Network weights shift between training and deployment. The learned network is frozen during deployment (not retrained per system). If a new system has fundamentally different algebraic properties, the network's scores may be unreliable. The paper validates the learned threshold on a held-out test set.
Overhead of network evaluation outweighs savings. The network must run once during setup. If the system is solved only once, the setup cost dominates. RAPNet shines in multi-query settings (many solves of the same structure) where setup is amortized.
What a runnable demo should prove

What a runnable demo should prove

Take a 2D Poisson equation (heat flow on a square grid) on a 100 by 100 grid. Build the sparse table of numbers and corresponding graph. Train a small neural network on subgraphs sampled from the hierarchy. Then time: (1) the classical AMG solver with a fixed edge-keeping rule (measure wall time and iteration count), (2) RAPNet AMG (measure pyramid setup time, solve time per system, iteration count). Run 100 solves on the same table with different right-hand-side vectors. Compare total time (setup once + 100 solves) and convergence behavior. Plot: iterations and wall time per solve, showing RAPNet's pyramid amortization.

total_time = setup_time + solve_count * avg_time_per_solve; speedup = classical_time / rapnet_time

The demo must make clear that RAPNet's advantage grows with the number of solves: one solve is often slower than classical (setup overhead), but 10 or 100 solves reveal the amortized benefit of learning the pyramid once.
