Teaching LLM Judges to Use Tools

Train LLM judges to call Python code when they need to compute or verify, making them more accurate at evaluating text.

Paper explainersAll themesAgents & Tool Use

Most systems that use LLMs to grade answers rely only on the LLM reading text and deciding. But if you ask a judge to verify that a math answer is correct, or check if a list has the right elements, the LLM just has to guess. This paper shows that if you let the LLM call a Python executor during judging, and train it to use that tool when needed, it becomes much better at its job, because Python can compute the true answer with certainty, while the LLM reading text alone is making probabilistic guesses.

Zero assumption version

Judges that only read text make mistakes

When you need to grade an answer to a math problem, or check if a response lists all the right items, you need verification: run the code, look up the fact, compute the sum. A beginner might train an LLM to just read the answer and decide if it looks right. This fails badly. An LLM trained only on text cannot reliably compute 47 times 32, or check if a list contains exactly the names of all 50 US states, or spot a logical contradiction hidden in prose.

The naive approach: give the LLM more reasoning steps, or make it bigger. This helps a little, because more thinking can catch some errors, but the LLM still has no way to know for certain that an answer is right. It is making educated guesses about computation and facts, using only text patterns it memorized, not real verification.

The method. Train the LLM judge with reinforcement learning (nudging it to improve through trial and reward) so it learns when to call a Python executor that computes or verifies the answer for real, not by guessing.

The algorithm as a flow

What it actually does

Training starts.

An LLM judge reads a response and decides: can I verify this by calling Python?

Diverse tasks.

Train on both verifiable (run code, check the answer) and non-verifiable (essay quality, clarity) questions.

Call Python when needed.

Judge learns a policy: certain questions need computation or fact-checking to score accurately.

Reward signal.

If the judge called Python and scored correctly, reinforce that decision. If it guessed and was wrong, nudge it to try tools next time.

Self-improve without copying.

Unlike distillation (copying from a teacher), the judge bootstraps: it improves itself by learning what tools reveal.

What the paper changes

What the paper changes

The paper changes the judge's action space: instead of just reading and deciding, the judge now chooses whether to call a Python executor. This is the core difference. The judge learns a policy (a decision rule) that says: if the response is a math answer, call Python. If it is a poem, just read it.

the object it moves  =  Python executor calls
The hidden quantity

Tool-use readiness: which questions benefit from calling code

measured quantity  =  Verifiable-vs-non-verifiable label

Every evaluation task lives on a spectrum. Some require real computation or fact-checking (math, list membership, logical proof) and are verifiable: Python can prove if the answer is right. Others rely on judgment and taste (essay fluency, style, helpfulness) and are non-verifiable: Python cannot grade them, only a human or LLM can. The paper measures and uses this distinction to train the judge smartly.

The judge learns to estimate this label automatically. During training, it gets reward when it calls Python on verifiable tasks and gets them right, and when it skips Python on non-verifiable tasks and still judges well. This hidden quantity — knowing which kind of task you are facing — guides the entire learning process.

Why it works

Why calling Python during judging makes the judge better

The mechanism is straightforward. For verifiable tasks (a correct math answer, a list with the right items), Python can prove the answer is right or wrong. No guessing needed. If the judge learns to call Python on these tasks, it stops relying on text patterns and starts using proof. For non-verifiable tasks, the judge skips Python because code cannot judge style or taste; it reads the response and decides. The reinforcement learning process rewards the judge when it makes the right choice — call on verifiable tasks, skip on non-verifiable ones.

Because the training includes both types of tasks together, the judge learns a general skill: recognize the type of task you are facing, and respond accordingly. Training on mixed tasks lets one judge learn different strategies for different situations, rather than needing separate judges for each type. The iterative reward signal pushes the judge to improve: if it called Python and got the answer right, that behavior is reinforced and becomes more likely in similar future tasks; if it guessed and was wrong, the reward penalty steers it toward trying Python next time, because Python delivers the proof the guessing could not.

The learning formula

First in words:

Reward for calling tool when correct plus penalty for calling tool when it would not help, scaled by what the judge learns about task type.

Then the compact form:

R = I(verifiable) * score_correct + (1 - I(verifiable)) * score_text + gamma * V(next_state)

Every symbol:

Rthe total reward the judge receives
I(verifiable)1 if the task is verifiable (code can check), 0 if not
score_correctaccuracy from calling Python (when verifiable)
score_textaccuracy from reading alone (when non-verifiable)
gammahow much future rewards matter (typically 0.99)
V(next_state)value estimate of the next state after this decision
A tiny worked example
Task: evaluate math answer 47 * 32 = 4761 (verifiable, I=1)
Judge calls Python, gets correct answer 1504, scores as incorrect: score_correct = 1.0
Reward: R = 1 * 1.0 + (1 - 1) * 0.3 + 0.99 * 0.5 = 1.0 + 0 + 0.495 = 1.495
Task: evaluate essay (non-verifiable, I=0)
Judge skips Python, reads and scores quality: score_text = 0.8
Reward: R = 0 * 0.9 + (1 - 0) * 0.8 + 0.99 * 0.5 = 0 + 0.8 + 0.495 = 1.295
Over many tasks, the judge learns: call Python on math (gets 1.495), skip Python on essays (gets 1.295).

The judge learns that calling Python on verifiable tasks yields higher reward, so it develops a policy to do so.

What can go wrong

What can go wrong

Python executor hangs or crashes. If the response contains code with an infinite loop or syntax error, calling Python might timeout or fail. The judge must learn to handle timeouts gracefully and fall back to text reasoning.
Judge calls Python on non-verifiable tasks. If the judge mistakenly believes an essay quality is verifiable and calls Python to grade it, the Python executor cannot compute a score for style or taste. Training must penalize this waste of computation.
Python output is ambiguous. If the response claims a list has 50 items but Python counts 49, the judge must correctly interpret the mismatch and score the answer as wrong. The judge needs clear feedback from Python.
Done right: mixed training + reward. Mixing verifiable and non-verifiable tasks in training forces the judge to learn the distinction. Reward that reinforces correct tool-use choices (call when needed, skip when not) ensures the judge generalizes the skill to new tasks.
