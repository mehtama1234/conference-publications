Experience-based Knowledge Correction for Robust Planning in Minecraft

XENON improves long-horizon game planning by rewriting its own task knowledge from success and failure records instead of trusting its starting beliefs forever.

Paper explainersAll themesAgents & Tool Use

Planning in Minecraft is hard because goals depend on hidden prerequisite chains. To make an iron pickaxe, you need sticks, which need planks, which need wood, and so on. Language models often start with partly wrong task knowledge and then keep repeating it even after the world proves it wrong. XENON fixes that by editing two kinds of knowledge from experience: item dependencies are revised after success, and action choices are revised after failure. The agent therefore learns a more accurate task graph while it plays because each success confirms useful prerequisite links and each failure removes bad local choices.

Zero assumption version

Why long-horizon planners get stuck on wrong task knowledge

A long-horizon game agent needs two facts to plan well: what ingredients or subgoals are required before a target item can be built, and which actions are likely to fail in the current situation. Language models often begin with shaky task knowledge. They may believe an item can be crafted directly when it actually needs an earlier tool, or they may keep repeating an action that already failed.

Prompting alone does not solve this. The game only gives sparse feedback such as success or failure, so the model does not receive a detailed explanation after each mistake because the environment reports outcomes, not step-by-step tutoring. If the agent never changes its internal task graph or action memory, it can keep using the same broken plan for many steps. Long tasks then collapse because one wrong dependency early in the chain poisons every later decision.

The paper's move. Treat experience as editable knowledge: revise item dependencies from successful trajectories and revise action choices from failed attempts.

The algorithm as a flow

What it actually does

Start with a rough dependency graph

Use the model's initial knowledge to guess which items and tools are needed for the goal.

Attempt a plan

Execute actions in the game and observe sparse success or failure feedback.

Update dependency graph from success

When a path succeeds, keep the prerequisite links that were actually used so the graph becomes more accurate because successful paths reveal which subgoals were truly necessary.

Update action memory from failure

When an action fails in a state, record that failure so the next plan can avoid repeating it.

Plan again with corrected knowledge

Use the updated graph and failure memory to produce the next long-horizon plan.

What the paper changes

What the paper changes

The paper changes the agent's knowledge store. Instead of treating the model's starting task knowledge as fixed, XENON turns that knowledge into a data structure that experience can rewrite.

the object it moves  =  editable task knowledge
The hidden quantity

The hidden quantity: confidence in each prerequisite link

measured quantity  =  which dependency links have been supported by experience

A Minecraft plan is only as good as its dependency links. If the agent thinks item A needs item B, but the world keeps proving otherwise, that link should weaken or disappear. If a successful trajectory uses B before A, that link should become stronger because the successful path is direct evidence that B belonged in the chain.

XENON therefore tracks implicit confidence over dependency links and failed actions. Strong confidence comes from repeated successful use. Weak confidence comes from missing support or from repeated failure in the states where the link or action was supposed to help, because unsupported links and repeated failures both show that the current knowledge is misaligned with the world.

Why it works

Why it works

Long-horizon planning fails when wrong knowledge survives too long. XENON fixes that by splitting knowledge correction into two channels. Success teaches structure: if a path to the goal worked, the dependencies used in that path are evidence about what the world actually requires. Failure teaches avoidance: if an action failed in a given state, the planner should not keep proposing it as if nothing happened.

This separation matters because the two updates answer different questions. The dependency graph answers what must come before what. The failure memory answers what not to do next in the current context. Together they improve planning because the agent can build more realistic subgoal chains and also waste fewer steps on repeated dead ends.

The method is especially useful under sparse feedback because each success and failure is stored as a lasting change to the knowledge store. The agent does not need a perfect verbal explanation from the environment. It only needs to preserve what the world has already confirmed or denied.

Math after the picture

The planning score

First in words:

Choose the plan whose dependency links have the most support from past success and whose actions carry the fewest recorded failures in the current state.

Then the compact form:

score(plan) = support(plan_links) - fail_count(plan_actions, state)

Every symbol:

plan_linksthe prerequisite links used by the current plan
support(plan_links)how much successful experience backs those links
plan_actionsthe actions the plan proposes to execute
statethe current game situation
fail_count(plan_actions, state)how many times those actions have already failed in similar situations
score(plan)the value used to compare candidate plans
A tiny worked example
Plan A assumes the agent can craft an item directly, but that shortcut has never succeeded.
Plan B follows a longer chain that succeeded twice before: gather wood, make planks, make sticks, then craft the tool.
Plan A also includes an action that already failed in the same state.
Plan B gets a higher score because its links have support and its actions have fewer recorded failures.
The planner therefore chooses Plan B even though it is longer, because experience says it is the real path.

The real agent uses richer updates, but this equation captures the key pressure: back plans that worked and penalize actions that already failed.

What can go wrong

What can go wrong

One lucky success rewrites too much. If the graph update trusts a single noisy success too strongly, the agent may lock in a bad dependency because one run can succeed for accidental reasons.
Failure memory is too broad. A failed action should only block similar situations. If the memory generalizes too widely, the agent may avoid useful actions because they failed once in a different state.
Environment feedback is too sparse. The method relies on preserving success and failure. If the environment almost never reveals whether a subgoal worked, the knowledge store updates too slowly to help planning much because the agent lacks enough confirmed events to rewrite its graph.
Done right. The method works when the graph update uses repeated successful paths and the failure memory stays tied to the state where the action actually failed.
What a runnable demo should prove

What a runnable demo should prove

Build a toy crafting world with hidden prerequisite chains. Give one planner a fixed initial graph and give another planner the XENON update rules. Then inject a few wrong starting beliefs, such as omitting one needed tool or suggesting one useless shortcut. Measure how quickly each planner repairs its task graph and how often it repeats an action that already failed in the same state.

graph_repair_rate = corrected_links / wrong_links; repeat_failure_rate = repeated_failed_actions / failed_actions

The demo should make clear that the gain comes from rewriting knowledge from experience, not from a larger language model.
