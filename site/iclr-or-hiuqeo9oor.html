BehaveSim: Algorithm Similarity via Problem-Solving Behavior

Measure whether two algorithms are truly different by watching what intermediate answers they generate while solving the same problem, not by comparing their code.

Paper explainersAll themesOther

When a language model writes a new algorithm, you cannot tell if it found a genuinely new idea or just rewrote the same logic in different code syntax. Two algorithms that choose nodes in opposite orders (closest vs. farthest) look nearly identical to code-comparison tools but solve problems in fundamentally different ways. This paper proposes a new way to measure algorithm similarity: instead of reading the code, run both algorithms on the same problem and compare the sequence of intermediate solutions they produce.

Why existing code similarity fails

When algorithms are written in code, traditional tools measure similarity by counting matching words in the code, comparing the structure of the code, or looking at the final answer. These tools have a fatal flaw: they ignore how an algorithm actually solves the problem.

Example 1: Two graph-search algorithms—breadth-first search and depth-first search—explore nodes in completely different orders and find different routes, but code-comparison tools rate them as similar because both use similar structures.

Example 2: The same algorithm written two ways (one using recursion, one using loops) should be identical, but code tools mark them as completely different.

Example 3: Sorting algorithms like insertion sort and bubble sort both produce sorted arrays, so comparing outputs gives no insight into their different strategies.

The problem in one sentence. Code similarity metrics measure surface details, not how an algorithm actually works.

The algorithm as a flow

What it actually does

Run both algorithms

Execute algorithm 1 and algorithm 2 on the same input problem.

Record intermediate steps

Capture every intermediate partial solution each algorithm generates along the way.

Build trajectories

Assemble each intermediate solution into a sequence called a problem-solving trajectory.

Compare trajectories

Measure how different the two sequences are using sequence distance metrics.

Assign similarity score

Lower sequence distance means the algorithms solve problems the same way; higher means they differ.

What the paper changes

What the paper changes

Instead of analyzing code syntax, BehaveSim compares the behavior of algorithms by looking at the actual intermediate solutions they produce while solving a problem. The metric shifts from static code analysis to dynamic behavioral observation.

the object it moves  =  the similarity metric
The hidden quantity

The problem-solving trajectory

measured quantity  =  problem-solving trajectory (sequence of intermediate solutions)

A problem-solving trajectory is simply the sequence of answers an algorithm generates step-by-step as it solves a problem. For a sorting algorithm, it is the partial ordering at each step. For a graph search, it is the sequence of nodes visited. For an optimization method, it is the numerical values after each adjustment.

The paper compares two trajectories by measuring sequence similarity: low similarity means the algorithms took different paths or made different choices along the way; high similarity means they made the same moves in the same order.

Why it works

Why comparing trajectories works

Code metrics fail because two very different algorithms can be written with similar syntax, and two identical algorithms can be written in completely different ways. Trajectory comparison bypasses all of this by forcing both algorithms to actually solve the same problem and recording what they do.

When Algorithm A always picks the nearest unvisited node and Algorithm B always picks the farthest, both face the same graph, same starting point, and same goal. Their intermediate choices will be visibly different: Algorithm A's path stays clustered; Algorithm B's path jumps around. This behavioral difference shows up in the sequence of visited nodes, no matter how the code was written.

By recording these trajectories on many different test problems and comparing them, BehaveSim builds an accurate picture of how fundamentally different two algorithms really are. This gives LLM-based algorithm design a way to filter out mere syntactic variations and focus on genuinely new strategies.

Math after the picture

Trajectory distance formula

First in words:

similarity score equals one minus the fraction of moves that differ when aligning two trajectories

Then the compact form:

BehaveSim = 1 - (edit_distance(traj_A, traj_B) / max_length(traj_A, traj_B))

Every symbol:

traj_Athe sequence of intermediate solutions from algorithm A
traj_Bthe sequence of intermediate solutions from algorithm B
edit_distancethe minimum number of steps to transform one sequence into the other
max_lengththe length of the longer sequence
A tiny worked example
Algorithm A visits cities in order: [1, 2, 3, 4, 5] (trajectory length 5)
Algorithm B visits cities in order: [1, 5, 4, 3, 2] (trajectory length 5)
Comparing position-by-position: positions 1 match (1=1), positions 2 differ (2 vs 5), 3 differ (3 vs 4), 4 differ (4 vs 3), 5 differ (5 vs 2)
Edit distance between these sequences = 4 changes needed to transform one into the other
Similarity score = 1 - (4 / 5) = 1 - 0.8 = 0.2 (very low, indicating fundamentally different strategies)

Lower scores indicate the algorithms explore a problem space in fundamentally different ways.

What can go wrong

What can go wrong

Algorithms with similar code but different behavior may be incorrectly rated as different. If the code is written in very different styles, the intermediate solutions might not align perfectly even if the overall strategy is the same. The metric requires executing both algorithms.
Algorithms that work on different problem sizes may generate trajectories of different lengths. Edit distance between sequences of very different lengths requires padding or normalization; misaligned trajectories can give false dissimilarity scores.
Sampling only a few test problems may miss important behavioral differences. An algorithm may behave identically to another on simple test cases but diverge on harder problems. Comprehensive evaluation requires diverse test instances.
Done right: run many test problems, align trajectories carefully, and interpret low similarity as a signal to inspect algorithms more closely. The paper shows that on diverse algorithmic families (search, sorting, optimization), BehaveSim correctly clusters algorithms by their problem-solving strategies.
What a runnable demo should prove

What a runnable demo should prove

Build a simple graph-traversal problem (10 cities, Euclidean distances). Implement two algorithms: one that always picks the nearest unvisited node, one that always picks the farthest. Run both on the same five city configurations, recording the sequence of nodes visited in each run. Compute edit distance between the sequences. Show that BehaveSim assigns a low similarity score despite both algorithms being written in similar code, proving that the metric captures behavioral difference.

sim = 1 - (sum of edits to transform trajectory_A into trajectory_B) / (length of longer trajectory)

The demo must show that two algorithms with opposite heuristics (nearest vs. farthest) receive low similarity scores, while the same algorithm written two different ways receives high similarity scores.
