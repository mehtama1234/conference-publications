D2E: Desktop to Embodied AI via Sensorimotor Transfer

Learn vision-action skills on desktop games, then transfer that knowledge directly to physical robots without collecting expensive robot data.

Paper explainersAll themesRobotics & Control

Robots learn by watching humans demonstrate tasks, but physical data is scarce and costly. Desktop games offer the same kind of input-output pairing (see a scene, take an action) at massive scale for free. This paper shows that skills learned from game interactions transfer surprisingly well to real robot tasks like picking objects and navigating rooms.

Zero assumption version

Physical data is expensive; games are free

Today, teaching a robot a new skill requires collecting real videos of humans or robots doing it. That takes time, money, and coordination. Meanwhile, millions of hours of game footage sit online—Minecraft players, strategy gamers, every streamer—all showing complex decision-making and hand control.

A naive approach: train directly on game data and hope it works on robots. But it fails because the visual appearance is wildly different (game pixel art versus real photographs), the physics is abstracted, and the button presses are not the same as motor commands. The two worlds look completely different.

In one sentence. The paper bridges the visual and action gap between game worlds and physical robots by learning a shared representation of what-to-do that ignores how it looks.

What it actually does

Standardize desktop data

Predict what happens next

Train a model to watch a game video and predict the next frame, discovering what actions causally change the world.

Build a shared world model

Extract a learned representation that captures causality, independent of whether you're looking at game graphics or real photos.

What the paper changes

The learned representation

The paper changes a single thing: the internal representation (the learned numbers inside the model) that the vision-action model builds. Ordinarily, models trained on games encode game-specific visual details (pixel colors, game UI). Instead, D2E trains the model to extract the causal action meaning—what each button press does to the world, stripped of appearance.

the object it moves  =  the internal representation
The hidden quantity

The causal action signature

measured quantity  =  causal action meaning

The hidden quantity is the causal action signature: which aspects of the input does each action actually change? In game footage, pressing 'move forward' might change pixel positions and velocity. The model learns to measure: how much does this action type alter things that matter, independent of visual style?

The paper measures this through a generalist model that predicts timestamps in event sequences. By training on diverse games without game-specific labels, the model discovers a representation where similar actions (jump, grab, navigate) cluster together even across different visual appearances.

Why it works

Why it works: from causality to transfer

When a model watches gameplay and predicts what frame comes next, it must learn which visual changes result from the player's actions and which are uncontrollable background motion. This forces the model to separate controllable cause (what the action made happen) from uncontrollable appearance (how it looks). If the model relies too heavily on pixel colors or UI elements, it will fail to predict the next frame when the visual style changes.

The trick is training on many diverse games with no manual labels. A game-specific model can memorize 'pixels at location X mean action Y is happening.' But a generalist model trained across Minecraft, driving simulators, strategy games, and more must find something deeper: the abstract pattern of what causally changes per action type. That abstraction transfers to robots because both games and robots are causal systems—actions alter the state—even though the pixels and physics differ.

inputMany hours of diverse game footage, each frame labeled with the action taken
stepPredict the next frame, forced to discover which visual changes are caused by the action
stepLearn an abstraction of causality that holds across all games, ignoring surface appearance
stepTake that abstraction to a robot, add a few real examples, and fine-tune
outputA policy (decision rule) that controls the robot by recognizing the same causal patterns
Math after the picture

Predicting the next frame as a learning signal

First in words:

loss = sum over all frames: (predicted_frame - actual_next_frame) squared, plus a penalty for actions that did not causally change the frame

Then the compact form:

L = mean((frame_t+1 - predict(frame_t, action_t))^2) + lambda * sum_a (fraction of a not causally changing state)

Every symbol:

frame_timage the model sees at time t
action_tthe button pressed or stick move at time t
predict(frame_t, action_t)the model's guess of what frame_t+1 looks like
frame_t+1the actual next image in the video
lambdastrength of the penalty for unused actions
A tiny worked example
Frame now: a character in a desert. Action: walk forward. Model predicts: same character, but 20 pixels to the right.
Actual next frame: character 20 pixels to the right.
Prediction error squared: (character_predicted - character_actual)^2 = 0.
Action 'walk forward' causally changed the position, so its penalty is 0.
Action 'jump' did not activate, and the character did not jump, so the model learns: jump causality is 0 (irrelevant here).
After training on thousands of games, the model abstracts: walk = shift x, jump = shift y, grab = highlight object. These patterns hold in Minecraft and on a physical robot.

The model minimizes pixel-level prediction error while learning which actions are causal, forcing abstraction of action meaning across visual styles.

What can go wrong

What can go wrong

Action space mismatch. If the game uses buttons and the robot uses continuous motor commands, the learned action meaning may not map cleanly. The paper sidesteps this by learning high-level action concepts (grab, navigate) rather than low-level control signals.
Rare or safety-critical scenarios. Games may never show failures (collision, dropping an object). A robot trained only on successful game examples may not learn to recover from mistakes or avoid dangerous states.
Timing and latency. Games run at fixed frame rates with no physical latency. Robots have delays between sensing and actuation. A model that does not account for this may learn to issue commands too fast for the robot to execute.
Done right: diverse games + curated robotics transfer set. The paper includes 259 hours of human-collected robot demonstrations and pseudo-labels on 1K+ hours of gameplay. This mixture forces the model to learn true causal patterns, not surface features.
What a runnable demo should prove

What a runnable demo should prove

Build a small experiment: collect 10 hours of diverse game footage (at least three different games or visual styles), train a next-frame prediction model on 80% of it, test on the remaining 20%, and measure whether the learned representation transfers. The demo proves transfer by showing that the model's causal action abstraction holds across unseen games.

transfer_success = (action_causality_in_game_A - action_causality_in_game_B) / avg_causality, should be near 0 if transfer is working

The demo must make it impossible to miss: a representation trained on one game's causality accurately predicts actions in a visually different game, proving the abstraction is real.
