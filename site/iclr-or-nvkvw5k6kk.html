Cross-Lingual Alignment in Multilingual Retrieval

When searching in documents written in many languages, train the retriever to prefer matching languages over unrelated words, fixing the English-bias problem.

Paper explainersAll themesRepresentation & Self-Supervised Learning

Multilingual search engines read both English and other languages. Most of them have a hidden bias: when you search in Spanish, they will return an unrelated English document if it contains similar-looking words, even though a genuinely related Spanish document exists. This paper identifies why that happens and fixes it with a small, focused training set.

The English-bias trap in multilingual search

Imagine a search engine that understands many languages. You ask it a question in Spanish about cooking. Inside, the engine converts both your Spanish question and all the documents into lists of numbers (called embeddings — just coordinates in a vast space where similar meanings cluster together). It finds documents whose numbers are closest to your question's numbers.

The trap: in a database with both English and Spanish documents, the engine might score an unrelated English document higher than a genuine Spanish match. Why? Because English is more common in the training data, so the numbers for English words drift near the numbers for many other words. The Spanish-Spanish pairing gets lost in the crowd.

What a naive engineer would try: add more multilingual data to training. But more English data makes the problem worse, not better, because English words already overlap widely with many other languages in the shared number space, so adding more English examples reinforces that overlap rather than distinguishing it from same-language meaning. The engine needs to learn that same-language is a stronger signal than word similarity alone, because when two documents have similar words but different languages, the model should count the language tag as breaking the tie.

In one sentence. Train the retriever on carefully chosen examples showing that a document in the query language beats any unrelated English document with similar words.

The algorithm as a flow

What it actually does

Step 1: Spot the bias

Test on mixed-language databases; measure when English docs rank above relevant same-language docs.

Step 2: Build training pairs

Create 2.8k examples where a query, a relevant same-language doc, and an unrelated English doc all sit together.

Step 3: Train the contrast

Update the embeddings so same-language pairs score higher than English mismatches.

Step 4: Preserve the rest

Make sure the training does not break existing retrieval quality for other language pairs.

Step 5: Test the fix

Run on multilingual benchmarks and custom same-language-bias tests.

What the paper changes

What changes: the embeddings

The paper adjusts the embeddings (lists of numbers that represent queries and documents in a shared space). Specifically, it retrains the model to make same-language pairs closer in the number space and English mismatches farther apart.

the object it moves  =  embeddings
The hidden quantity

The language-pairing signal

measured quantity  =  same-language pair strength

The hidden quantity is how much the retrieved document matches the query's language compared to just matching the query's words. A simple example: if you search for pizza in Spanish, a Spanish article about pizza should score much higher than an unrelated English article that happens to contain the word food and pizza.

The paper measures this by creating test sets where a query has one truly relevant document in the same language and multiple irrelevant documents in English. If the retriever is well-aligned, the same-language match wins consistently.

Why it works

Why small training data fixes the large problem

The core insight: the retriever has already learned that languages exist (from pretraining), but it ranks by word overlap first. Adding more data without direction just scales the problem. The paper's trick is to use a small dataset with sharp contrasts: a query, one good same-language match, and one bad English match that has similar words but wrong language.

Training on these triplets teaches the model: when all else is equal, language agreement beats word similarity. Since the training examples are carefully chosen to isolate that one signal, the model learns it cleanly in 2.8k steps. The key is that the existing embedding model already understands both languages well; it only needs to reweight them.

inputtriplet: query, same-language doc, English noise doc
stepcompute how close query is to each doc (cosine similarity in the number space)
stepmeasure the gap: same-language score minus English-noise score
stepif gap is small or negative, push same-language doc closer and English farther
outputupdated embeddings with sharper language-pairing signal
Math after the picture

The contrastive training loss

First in words:

loss = max(0, margin + score of wrong pair - score of right pair)

Then the compact form:

L = max(0, m + s(q, d_neg) - s(q, d_pos))

Every symbol:

Lthe loss value to minimize
mmargin: a small penalty threshold (e.g. 0.1)
s(q, d_pos)cosine similarity: how aligned the query and correct same-language document are
s(q, d_neg)cosine similarity: how aligned the query and wrong English document are
max(0, ...)if the correct pair already scores high enough, no penalty; otherwise penalize
A tiny worked example
Example: m=0.1, query is Spanish cooking question.
s(query, Spanish-cooking-doc) = 0.85 (good match)
s(query, English-unrelated-doc) = 0.80 (word overlap, wrong language)
L = max(0, 0.1 + 0.80 - 0.85) = max(0, 0.05) = 0.05
Gap is small, so gentle nudge: pull Spanish doc closer and English farther.
After training: s(query, Spanish-doc) = 0.88, s(query, English-doc) = 0.72.
L = max(0, 0.1 + 0.72 - 0.88) = max(0, -0.06) = 0.0 (no penalty now)

The loss pulls same-language pairs closer until they outscore even similar-looking but wrong-language documents by more than the margin.

What can go wrong

What can go wrong

Training data too skewed to one language pair. If all 2.8k examples focus on Spanish-English, the fix works for that pair but may not transfer to French, Chinese, etc. The paper mitigates this by sampling diverse language pairs.
Margin set too high. If the penalty threshold is too large, the model might push same-language docs impossibly close and English docs impossibly far, damaging other retrieval tasks. Finding the right margin requires tuning.
Overfitting to the 2.8k dataset. With only 2.8k training examples, the model could memorize the specific docs and queries instead of learning the general same-language-first rule. Test on unseen queries in the same languages to catch this.
Done right. Diverse language pairs, moderate margin, test on held-out queries and other multilingual benchmarks to confirm the fix generalizes without breaking existing performance.
What a runnable demo should prove

What a runnable demo should prove

Build a small retriever on a mixed-language corpus (e.g. 1000 documents: 400 English, 300 Spanish, 150 French, 150 German). Create 50 test queries in Spanish and French. For each query, rank all documents and record whether the same-language relevant document ranks in the top 3. Compute the same-language recall before and after the contrastive training.

same_language_recall = (count of queries where rank 1-3 doc is same language and relevant) / total queries

The demo should make impossible to miss that before training, same-language documents often rank below 5; after training, they dominate the top 3 for most queries.
