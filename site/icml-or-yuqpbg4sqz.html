ProAct: A Benchmark and Multimodal Framework for Structure-Aware Proactive Response

Train and test a proactive helper with explicit task graphs, so it can act at the right time and even carry out parallel substeps instead of waiting for direct instructions.

Paper explainersAll themesAgents & Tool Use

A passive assistant waits until a person tells it exactly what to do next. A proactive assistant must do more. It has to watch the environment, infer the larger goal, notice when help is needed, and decide whether two substeps can proceed in parallel because one step may already be unlocked while another branch is still running. That is difficult without data that shows task structure. ProAct provides such data through a benchmark with step-level annotations and explicit task graphs, then builds a reference helper that reads the current state, consults the task graph, and chooses the next helpful action. The core claim is that proactive behavior improves when the system reasons over explicit step dependencies rather than copying the human's most recent action, because the dependency graph shows which future actions are valid before they become visually obvious.

Zero assumption version

Why passive assistants are not enough

In assistance, maintenance, or safety settings, waiting for explicit commands is often too slow. A helper may need to fetch a tool before the person asks, warn about a hazard before an accident happens, or prepare the next substep while another substep is still running.

Standard instruction-following data does not teach that behavior well because it mainly shows responses to direct prompts. It usually does not explain which future steps depend on which current steps, or which activities can happen in parallel. Without that structure, a system tends to mirror the observed next action instead of reasoning about the whole task.

The paper's move. Provide explicit task graphs and use them during action choice, because proactive behavior depends on understanding dependencies and parallel opportunities across the whole task.

The algorithm as a flow

What it actually does

Build a benchmark with explicit task structure.

Annotate tasks with step-level labels and graphs that show prerequisite relations and parallel branches so the system can learn when help is valid by checking whether a step is unlocked or still blocked.

Detect the current state.

Use multimodal perception to infer which step has finished and which resources or hazards are present.

Consult the task graph.

Check which next steps are unlocked by the current state because proactive action should follow task dependencies, not only the most recent human motion.

Search over candidate actions.

Use heuristic search guided by uncertainty to pick the action that is most helpful now.

Execute and update progress.

Take the chosen action and revise the estimated task state so later proactive actions stay aligned with what has changed.

The hidden quantity

The hidden quantity

measured quantity  =  action readiness under task dependencies

The central hidden quantity is action readiness: whether a candidate helpful action is valid right now given what has already finished and what can run in parallel. A helper that ignores readiness may fetch the wrong item too early or miss a parallel branch that would save time.

The task graph makes readiness more visible because it connects observed state to future options. If a prerequisite is complete, a downstream step becomes available. If two branches are independent, one branch can begin while the other continues.

Why it works

Why explicit task graphs help proactive action

A proactive helper must answer two questions at once: what action would be useful, and is this the right moment for that action? Visual state alone is often insufficient because the same scene can support different next actions depending on the larger task plan. The graph adds that missing structure by recording which steps depend on which others.

Once the system has both state detection and the graph, it can search more intelligently. It no longer asks only which action matches the current pixels. It asks which action is unlocked by the task dependencies and which of those unlocked actions reduces delay, prevents hazards, or advances a parallel branch. That is why the helper can prepare ahead instead of copying the human's next visible motion.

The heuristic search is valuable because there can be several valid proactive actions at once. The search can prefer one that resolves a more urgent risk or starts a longer parallel branch sooner, so that total progress improves.

Math after the picture

Score a proactive action by readiness and value

First in words:

A simple summary is to score each candidate action by whether its prerequisites are satisfied and by how much benefit it creates when chosen now.

Then the compact form:

score(action) = readiness(action, state, graph) * future_gain(action)

Every symbol:

actionone candidate proactive step such as fetch, warn, or prepare
statethe current observed environment and task progress
graphthe task graph with dependencies and parallel branches
readiness(action, state, graph)a value near 1 when the prerequisites for that action are currently satisfied and near 0 when they are not
future_gain(action)how much delay reduction, safety improvement, or parallel progress the action creates if taken now
A tiny worked example
Action A is to fetch the next tool. Its prerequisites are complete, so readiness = 1, and its future gain is 6.
Action B is to start a cleaning step whose prerequisite is still missing, so readiness = 0, and its future gain would have been 7.
Action A scores 1 * 6 = 6.
Action B scores 0 * 7 = 0.
The helper should choose Action A because it is both valid now and useful now.

The paper uses a richer multimodal system and heuristic search, but the central idea is this product: an action matters only if it is both ready and useful.

What can go wrong

What can go wrong

State detection can be wrong. If the helper misreads which step is complete, it may trigger too early or too late because the task graph is being consulted with the wrong current state.
The task graph can omit real-world branches. If the graph misses an alternate path or a dependency, then structure-aware search can still choose poor actions because the representation itself is incomplete.
Parallel actions can interfere physically. Two branches may be independent in the abstract graph but still conflict in space or time, so the helper needs environmental checks before starting both.
Done right. The method works when the graph is accurate and the state detector is reliable, because then proactive actions are triggered only when the task structure and the observed world agree.
What a runnable demo should prove

What a runnable demo should prove

Build a small household or workshop simulator with a few structured tasks such as assembling an item, preparing a workspace, or performing a maintenance routine. Annotate each task with a graph of prerequisites and parallel branches. Then compare a passive helper that predicts the next visible step against a graph-grounded helper that reads the current state and chooses proactive actions.

The demo should show earlier useful triggers, more safe parallel actions, and fewer wasted waiting steps because the graph-grounded helper knows which future steps are already unlocked.

proactive_gain = trigger_quality + parallel_action_rate - unnecessary_actions

A convincing demo must show that proactive help depends on task structure, because the assistant should act from dependency knowledge rather than from simple imitation of the latest observed move.
