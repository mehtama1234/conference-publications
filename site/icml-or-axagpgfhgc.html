Structured 4D Latent Predictive Model for Robot Planning

Instead of predicting 2D video frames, predict how a 3D scene's structure will move, then decode that structure into robot actions.

Paper explainersAll themesRobotics & Control

When a robot plans a manipulation task, it needs to predict the future. Today's video-prediction models predict pixels: they guess what the camera will see next. But pixels hide what is really there in 3D space (the shape and position of objects in the room). This paper builds a model that predicts how 3D space itself will change, encoded as a compact list of numbers. The model can then decode this back into any camera view and translate it into precise robot actions.

Zero assumption version

Why 2D video prediction fails for precise robotics

A robot seeing a scene through a camera must predict what will happen next. A naive approach: train a model to predict the next few video frames (what the camera will see). This works fine for visual quality.

But robots doing manipulation (picking, placing, pushing objects) need precise 3D reasoning: exactly where is the object in 3D space, how far can it move, will it collide with anything? 2D video pixels do not show true 3D depth and where things actually are. Two different 3D scenes can look nearly identical in the camera image, especially if part of an object is hidden or if the view angle is new. When the robot sees an unfamiliar camera angle or a slight lighting change, the pixel predictor becomes unreliable, because it learned pixel patterns, not what is truly in 3D space. Worse, when the robot uses this noisy pixel prediction to plan actions, small errors compound into grasping failures.

The move. Predict how 3D space will change as a compact list of numbers, not as pixels. Decode that code into any view and use it directly to guide robotic actions.

The algorithm as a flow

What it actually does

Encode the scene

Take multi-view camera images and depth maps. Build a 3D voxel grid (a low-resolution 3D array of features). Compress it into a small code that represents the scene's structure.

Encode the text instruction

Convert the text command (e.g., 'pick the red cube') into a numerical code using a pre-trained language model.

Predict how the code changes

Feed the current code and text to a learned dynamics model. The model predicts what the code should be at the next timestep, using smooth interpolation from present to future.

Decode to 3D and render

Take the predicted code and decode it back into a 3D point cloud. This can be rendered from any camera angle, including angles the model never saw during training.

Convert 3D prediction to robot actions

Feed the current 3D state and the next predicted 3D state to an inverse dynamics module (another learned model). It outputs the exact motor commands for the robot to move toward that next predicted state.

What the paper changes

What the paper changes: the representation

Previous video-prediction models operate on pixels. This paper changes what gets predicted: instead of 2D pixel images, the model predicts a compact numerical code that encodes how 3D space is arranged. The code is computed from multi-view depth and image features. A decoder can turn this code back into 3D points, enabling the same prediction to be viewed from many angles and used for planning.

The hidden quantity

The hidden quantity: 3D structural consistency

measured quantity  =  multi-view coherence

The paper measures a hidden quantity: does the predicted 3D world look the same from multiple camera angles? A pixel predictor can invent details that do not actually exist, so if you view the prediction from a different camera angle, things look inconsistent and wrong. The paper's metric: decode the prediction and render it from multiple camera angles. Measure how well the predicted points align with the true object outlines in each view. This score means the 3D prediction is real and trustworthy.

The paper estimates this by decoding predictions and comparing rendered masks across four different camera angles (never seen by the model during training), checking that objects stay in the same real locations in all views.

Why it works

Why predicting 3D space makes robot actions more precise

The core reason this works: when the model predicts 3D space instead of 2D pixels, it must obey the rules of how 3D works. An object can only be in one place in 3D space; it has a single position. But pixels are ambiguous (the same image pixels could come from different 3D scenes). If the model is forced to predict one true 3D scene that renders the same way from any camera angle, it cannot cheat by just memorizing what pixels look like. It has to learn what is truly in the 3D world.

A robot inverse dynamics module then converts the predicted 3D state into actions. Because the 3D prediction is true and consistent (the same positions hold from every view), the inverse dynamics module gets reliable spatial targets. It can compute exact distances, approach angles, and paths without hitting obstacles. With only pixels, the inverse dynamics module would see contradictions: from camera A, the object looks like it is here; from camera B, it looks like it is over there. The robot stops or fails.

The flow-matching objective in latent space

First in words:

loss = flow matching on predicted latent path from current state to next state, conditioned on text instructions

Then the compact form:

loss = E[ || u_t(z_t | z_0, text) - v_t ||^2 ]

Every symbol:

z_tlatent code (compressed 3D structure) at time t
z_0latent code at the start of the trajectory
textencoded text instruction (goal)
u_tpredicted velocity (direction and speed to move the latent code)
v_ttrue velocity (ground-truth direction to move)
E[...]average over many examples
A tiny worked example
Suppose z_0 = [3.0, 5.0] (current code: two numbers representing the scene).
True code path to the goal: move to [4.5, 6.0] in 2 steps.
At t=0.5, the true velocity is [0.75, 0.5] (code moves 0.75 in direction 1, 0.5 in direction 2).
The model predicts u_0.5 = [0.70, 0.52] (close but a small error).
Loss = (0.70 - 0.75)^2 + (0.52 - 0.50)^2 = 0.0025 + 0.0004 = 0.0029.
Training reduces this error by adjusting the internal numbers the model uses to make predictions.

The model learns to smoothly move the code in small steps toward the goal, predicting the final scene code the robot should reach.

What can go wrong

What can go wrong

Occluded objects. If the camera cannot see part of an object (it is hidden behind something else), the 3D encoder has no depth signal. The code becomes inaccurate. When the dynamics model tries to predict where the hidden part moves, it guesses poorly, and the robot tries to push an object where it actually is not.
Unseen object types. If a test scene has an object type or configuration the model never saw during training (e.g., a transparent container, or a very small tool), the 3D encoder may fail to extract good features, and the code does not capture the scene accurately.
Long-horizon errors compound. Predicting many steps ahead in code space accumulates small errors. A 1% error at step 1, compounded over 20 steps, becomes large. The robot must verify predictions by taking a short action, observing the result, and re-planning.
Done right: multi-view consistency. If the encoder and decoder are trained to preserve 3D structure across many camera views, and the dynamics model is trained with smooth interpolation (a well-calibrated learning objective), the predictions stay accurate and generalize to new views.
What a runnable demo should prove

What a runnable demo should prove

Build a simulator with a robot arm and a scene containing one movable object. Record multi-view videos (4 cameras) of an expert robot grasping and moving the object. Train the 3D latent predictor and inverse dynamics module on 100 expert demonstrations. Then test: (1) ask the model to predict where the object will be after 3 actions, from a camera angle it never saw during training. (2) Render the prediction from that new angle and check that the object is in the right 3D location (use ground-truth depth to verify). (3) Pass the same prediction to the inverse dynamics module and execute the generated actions on the simulated robot. Measure success: does the robot end up where the prediction said it would?

success = (predicted final object position in 3D) == (actual final position), within 2cm

The demo must show that a model trained only on standard camera angles can predict accurately from a new, never-before-seen angle. That is impossible for pixel predictors; it is natural for 3D structure.
