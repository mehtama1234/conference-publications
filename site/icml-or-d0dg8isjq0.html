Lifting Traces to Logic: Programmatic Skill Induction with Neuro-Symbolic Learning for Long-Horizon Agentic Tasks

Turn successful action traces into reusable programs with explicit conditions so an agent can reuse a skill in changing situations.

Paper explainersAll themesAgents & Tool Use

An agent often solves a long task once and then forgets the exact control logic that made the solution work. Many skill-learning methods store only a flat script, which means a fixed sequence of actions with little room for branching. This paper argues that a useful skill should include explicit conditions, variable updates, and branch points because long tasks usually depend on what the environment looks like at each step.

Zero assumption version

Why fixed scripts fail on long tasks

When an agent completes a long task, its trace contains many useful choices. A natural idea is to compress that experience into a skill that can be reused later. The problem is that many learned skills are state-blind scripts. They say what to do, but not when to branch, when to stop, or which stored value should control the next move.

That weakness matters in dynamic settings. A skill that worked in one trace may fail in a new goal or a changed environment because the right next action depends on conditions that were never written down. A reusable skill therefore needs control logic, not only an action list.

The paper's move in one sentence. Lift action traces into modular programs with explicit tests and variable binding so that the learned skill can react to changing state during execution.

The hidden quantity

The hidden quantity

measured quantity  =  Control logic that explains the trace

The main hidden quantity is the program structure that made the trace successful. The trace tells you what happened, but it does not directly tell you which conditions mattered, which values should be stored, or why the agent stopped at that point.

NSI tries to infer that hidden structure by finding the smallest program that explains the observed path and still runs correctly on related tasks. That hidden structure matters because it is the part that transfers, while the surface action order may change from one instance to the next.

Why it works

Why this works: store decisions as logic instead of as one frozen path

A long-horizon task often revisits the same subproblem under different conditions. A fixed script cannot handle that well because it replays one past path even when the environment has changed. A program with condition checks works better because it can choose a different next step when the state is different.

Value binding also matters. The same skill may need to operate on a different object, location, or target each time. If the learned program can bind those task-specific values at run time, then the control structure can stay the same while the concrete instance changes.

Math after the picture

Choose the skill program that best explains the trace

First in words:

Prefer a skill program that explains the observed trace well and also stays simple enough to reuse on related tasks.

Then the compact form:

score(program) = trace_fit(program) + transfer_fit(program) - complexity(program)

Every symbol:

score(program)overall value of one candidate induced skill program
trace_fit(program)how well the program reproduces the successful decisions seen in the original trace
transfer_fit(program)how well the same program works on related tasks with changed states or goals
complexity(program)penalty for extra branches or stored rules that do not help execution
A tiny worked example
Program A is a flat action list. Trace fit 8, transfer fit 2, complexity 1, total 9.
Program B adds one branch on whether the key object has been found. Trace fit 8, transfer fit 7, complexity 2, total 13.
Program C adds three extra branches that the task rarely uses. Trace fit 9, transfer fit 7, complexity 5, total 11.
The system picks Program B because one useful branch captures the real control logic without adding extra clutter.

The paper uses neuro-symbolic induction rather than this exact formula, but this score states the balance between explanation, transfer, and program size.

What can go wrong

What can go wrong

Misread control structure. If the induction step invents the wrong branch rule, the stored skill may fail on transfer because it reacts to the wrong state signal.
Too little trace diversity. One or two narrow traces may hide important branches, so the induced program can look simpler than the real task logic.
Binding the wrong values. A good control structure still breaks if task-specific values are attached incorrectly, because the program then applies the right rule to the wrong object or goal.
Done right. The paper is useful because it turns experience into reusable decision structure, so later agents can adapt the same skill to new situations instead of replaying one old path.
What a runnable demo should prove

What a runnable demo should prove

Build a toy long-horizon environment with branching tasks such as search, fetch, and deliver. Record successful traces for several goal instances. Compare three systems: direct prompting, flat script extraction, and program induction with branch and stop rules. Then change the target object or insert a blocked path so that the same surface action order no longer works.

The demo should show that the induced program handles the changed case more often because it can test conditions and choose a new branch. It should also expose the recovered program text so that a human can inspect whether the branch logic matches the task.

transfer_gain = success_program - success_flat_script

The required proof is that logic-grounded skills transfer because they encode why the trace took its path, not only which path it took.
