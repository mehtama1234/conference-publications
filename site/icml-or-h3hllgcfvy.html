TimeMRA: LLM-Empowered Time Series Forecasting via Multi-Scale Retrieval-Augmented Representations

When forecasting time series with language models, treat each pattern size separately to avoid one scale drowning out another.

Paper explainersAll themesTime Series & Sequential

Time series forecasting means predicting what happens next based on data from the past. Language models (AI systems trained to predict word sequences) have shown promise for this task, because they learn to recognize patterns. But when a pattern shows up at multiple different time scales (like both daily and weekly changes), existing methods get confused—the signals interfere with each other, and the model cannot isolate which scale matters for each piece of information.

Zero assumption version

Multi-scale noise hides the signal

A time series is a sequence of measurements over time—daily stock prices, hourly temperatures, quarterly sales. Real data shows patterns at many different time scales: the stock might trend upward over months, wiggle daily, and jump on earnings calls. A naive approach is to feed the entire messy sequence to a language model and hope it learns all patterns at once. But the model's learned shortcuts (we call them weights, just numbers that control which inputs matter most) end up representing scales in a tangled way: the daily noise mixes with the weekly trend and the monthly cycle, all encoded together.

The problem bites when scales interfere: a model may learn to recognize a strong daily pattern by accident and ignore a weak but important weekly signal. Or it may spend its limited capacity on noise at scales that do not matter for the forecast. Language models amplify whichever scale is noisiest rather than whichever is most useful.

In one sentence. The paper isolates each time scale into separate, non-interfering channels before asking the language model to forecast.

The algorithm as a flow

What it actually does

Decompose the series into multiple time scales

Break the input sequence into components: one capturing hourly changes, one capturing daily patterns, one capturing weekly cycles, and so on.

Create a prompt for each scale

For each decomposed component, write a prompt that asks the language model: what happens next at this scale, given this past data?

Route each scale separately through the model

Instead of mixing all scales, send each scaled component through a dedicated pathway in the language model, so the weights for hourly patterns do not interfere with weekly weights.

Penalize cross-scale confusion

Add a penalty that gently steers the model away from using information from the wrong scale to predict the wrong scale.

Retrieve and combine forecasts

Gather the separate forecasts from each scale, retrieve similar past patterns at each scale from a database, and blend them into a final answer.

What the paper changes

What the paper changes

The paper changes how the time series is represented before the language model sees it. Instead of feeding one tangled sequence, it decomposes the sequence into multiple separate time-scale components and routes each through a distinct channel in the model's learned weights.

the object it moves  =  Time-scale decomposition and routing
The hidden quantity

Scale entanglement: how much one scale is mixed into another

measured quantity  =  Cross-scale interference ratio

The hidden quantity is how much the model's learned weights for one time scale accidentally use information from a different time scale. If the daily weights pull in weekly signal, or vice versa, the model is confused. The paper calls this entanglement: scales are tangled together in the weight numbers.

The paper estimates this by measuring whether the routed representations (the version of the signal sent down each scale's path) are actually different from each other. If daily and weekly components produce similar representations, they are still entangled. A disentanglement constraint—a penalty term—measures the overlap and pushes the representations apart.

Why it works

Why separating scales prevents interference

The core reason the method works is straightforward: weights learn patterns from whatever they see most often or most loudly. If hourly noise is loud (high variance in the raw data), the model's weights will learn to predict hourly noise instead of weekly trends. By decomposing the series into separate channels first, each channel sees only its own scale, so weights cannot accidentally learn the wrong scale.

The router network adds a second layer: it learns which scales actually matter for the current prediction. For a particular time step, the router might assign high scores to the daily and weekly channels (because those scales are predictive) and low scores to the hourly channel (because hourly data is random noise in this dataset). This learned routing prevents the model from wasting capacity on irrelevant scales and prevents confusion when multiple scales are present.

Math after the picture

The scale-aware routing formula

First in words:

Total loss is the forecast error plus a penalty that pulls apart the representations of different scales, weighted by how much the model learned to care about each scale.

Then the compact form:

L = MSE(forecast, actual) + lambda * sum_s sum_t ||r_s(t) - r_other(t)||^2 * w_s(t)

Every symbol:

MSE(forecast, actual)the average squared difference between what the model predicted and what actually happened
lambdaa dial controlling how much to penalize scales for leaking into each other
r_s(t)the representation (internal numbers) for scale s at time t
r_other(t)the representation for a different scale at the same time
w_s(t)how much the router decided scale s matters at time t (a weight between 0 and 1)
sum_s sum_tadd up the penalty over all scales and all time steps
A tiny worked example
Suppose at time t, the model predicts well (MSE = 0.5), and the daily and weekly representations are very similar, contributing 2.0 to the disentanglement penalty.
Daily scale has w_s = 0.8 (the router thinks daily matters a lot); weekly has w_s = 0.3.
Disentanglement cost for this scales pair: 2.0 * 0.8 = 1.6 (penalizes the scale the router trusts, forcing them to be different).
Total loss: 0.5 + lambda * 1.6. If lambda = 1.0, loss = 2.1. The model learns to make daily and weekly representations different to reduce this penalty.

The router weights ensure that scales the model already trusts are pushed hardest to be different from other scales, avoiding confusion on the scales that matter most.

What can go wrong

What can go wrong

Decomposition method is wrong for the data. If the chosen decomposition (which scales to extract) does not match the actual scales present in the time series, the method isolates scales that do not matter and misses scales that do. For example, if you decompose into hourly and daily scales but the data actually contains a dominant 8-hour pattern, the isolated channels are useless.
Router network learns too much. If the router assigns zero weight to a scale (decides that scale is irrelevant), the model never learns a good representation for it, even if that scale becomes important later. The router's decision is permanent once trained.
Disentanglement penalty is too strong. If lambda is set too high, the model spends all its effort making scales different from each other, even when they genuinely share useful structure. This forces unnecessary separation and hurts forecast accuracy.
Retrieval database is sparse. If similar past patterns are rare in the database, retrieval-augmented forecasts fall back to a cold start. The model has no relevant neighbors to look up.
Done right. If decomposition matches the data, lambda is tuned carefully, and the router is allowed to learn, the method isolates real scales and allows the language model to predict each one cleanly, because each scale's weights specialize in only that scale's pattern instead of trying to capture multiple patterns at once.
What a runnable demo should prove

What a runnable demo should prove

Build a small time series with a clear daily cycle (like temperatures: warm by day, cold by night) plus a clear weekly cycle (like office occupancy: high on weekdays, low on weekends) plus random hourly noise. Train a baseline language model on mixed data, then train the paper's method with scale decomposition. On a test set, measure forecast error separately for each scale: how well does it predict the next day's temperature, and how well does it predict the pattern across the week? The demo should show that the paper's method has lower error on each individual scale than the baseline.

scale_isolation_gain = (baseline_error_per_scale - paper_error_per_scale) / baseline_error_per_scale

The core insight should be undeniable: once you stop asking the model to predict all scales at once, it predicts each scale better, because the model's weights can now specialize in one scale instead of splitting their capacity across multiple competing patterns.
