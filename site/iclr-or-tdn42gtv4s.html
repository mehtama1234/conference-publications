PerfGuard: A Performance-Aware Agent for Visual Content Generation

Plan image-generation tasks with measured tool strengths instead of vague tool descriptions, then update those preferences when real runs disagree with the plan.

Paper explainersAll themesAgents & Tool Use

A visual-content agent may have many tools: image editors, layout tools, captioning tools, and style transfer tools. Most agent systems choose among them from text descriptions alone, as if each tool always works equally well. That is a bad assumption. One editor may do background replacement better because its editing controls preserve scene boundaries well, while another may handle text placement or face repair better because its outputs stay cleaner on those subtasks. PerfGuard builds an agent that keeps explicit performance records for each tool and uses those records while planning. It also updates its preferences after seeing real execution outcomes. The result is a planner that does not just ask what a tool claims to do, but asks how well that tool usually performs on the kind of subtask now in front of it.

Zero assumption version

Why tool descriptions are not enough

An agent that builds visual content usually decomposes a request into subtasks such as generate a draft image, edit a region, add text, or improve sharpness, because each part of the request depends on a different capability. If the planner knows only a short text description of each tool, it cannot tell where one tool is strong and where another one fails.

That gap causes planning mistakes. The agent may choose a tool that is usually weak on the current subtask, or may keep using an outdated preference after the tools have changed. Visual generation is especially sensitive to this because small tool differences can change whether the final image matches the user's request.

The paper's move in one sentence. Measure each tool on fine-grained task dimensions, plan with those scores, and keep updating the preference table when real executions reveal a better choice, because current performance matters more than a static description.

The algorithm as a flow

What it actually does

Measure tool behavior.

Evaluate each tool on fine-grained visual subtasks, so the agent stores real performance boundaries instead of generic descriptions.

Represent the request as subtasks.

Break the user request into concrete jobs such as draft generation, region editing, text placement, or finishing touches.

Rank tools per subtask.

Use the stored score table to predict which tool is most suitable for each job, because different jobs reward different tool strengths.

Run the plan and inspect the outcome.

Compare the planned ranking with what actually worked best on the executed task.

Update preferences.

Shift the score table toward the better-performing tool, so later plans track current tool behavior instead of stale assumptions because the update records what actually worked.

The hidden quantity

The hidden quantity: capability-task fit

measured quantity  =  How well a tool's observed strengths match the current subtask

The planner does not really need a general opinion about a tool. It needs a task-specific fit score: for this exact subtask, how likely is this tool to produce the desired result?

PerfGuard estimates that fit from multi-dimensional tool evaluations and then revises it after live runs. This matters because a tool that is excellent for one visual job can still be a poor choice for another, and the right planner must preserve those differences.

Why it works

Why performance-aware planning helps

The method works because planning quality depends on the quality of the planner's beliefs about the available tools. Generic text blurbs hide real performance boundaries. Measured score tables expose those boundaries, so the planner can match each subtask to a tool that has already shown strength on similar work.

The update step matters just as much as the initial scores. A tool may improve after an update, or fail on a class of requests that the offline evaluation missed. PerfGuard corrects those beliefs after live runs, so the agent becomes more reliable over time because it learns from actual execution rather than repeating the same mistaken choice.

Math after the picture

The ranking idea

First in words:

Give each tool a score for each subtask type, then choose the tool with the highest expected fit and revise that score after observing the real result.

Then the compact form:

tool_score(tool, subtask) = offline_fit(tool, subtask) + update(tool, subtask)

Every symbol:

offline_fit(tool, subtask)the measured score from prior evaluation on that kind of visual job
update(tool, subtask)the correction added after comparing planned and actual execution outcomes
tool_score(tool, subtask)the current score used by the planner to rank tools for one subtask
A tiny worked example
Suppose the agent must add readable text to an image and also replace the background.
Tool A has strong text-edit scores but weaker background-edit scores.
Tool B has the opposite pattern.
PerfGuard assigns Tool A to text and Tool B to background because each choice follows the measured fit table.
If Tool B unexpectedly fails on the background edit in a live run, the update term lowers its future background score.
The next plan changes because the preference table now reflects real execution feedback.

The update term is important because tool quality changes over time, and a frozen ranking table becomes stale.

What can go wrong

What can go wrong

The evaluation table may miss important task types. If the offline score table does not include a subtask the user later asks for, the planner still lacks useful evidence because it must extrapolate from incomplete coverage.
Feedback can be noisy. One bad run does not always mean the tool is bad. Preference updates must average over enough evidence because random failures should not overturn a good ranking.
The planner may overfit to one benchmark style. If the score table is built from narrow evaluation prompts, it may rank tools well only for that prompt style and miss real user variation.
Done right. When the score table covers the main subtask types and the updates reflect real outcomes, the agent chooses better tools because planning is grounded in observed capability rather than tool marketing text.

The demo should show higher planning accuracy for the PerfGuard-style system because it reasons with real tool behavior and revises stale beliefs after execution.
