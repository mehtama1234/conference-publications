Asking What Matters: Reward-Driven Clarification for Software Engineering Tasks

Train a clarifying-question module to ask only for missing details that matter for success and that users can realistically answer, so issue resolution improves with fewer questions.

Paper explainersAll themesAgents & Tool Use

Software tasks are often underspecified. A bug report may omit the failing environment, a feature request may hide an important acceptance rule, or a refactor request may not say which file is authoritative. Asking a clarifying question can fix that, but too many questions slow everything down and frustrate users. This paper studies which missing details truly change task success and which questions users are actually able to answer. It then turns those two ideas into reinforcement-learning rewards. The resulting module, CLARITI, learns to ask fewer but more useful questions because it targets information that both matters and is obtainable.

Why many clarifying questions are still poor questions

When a task description is incomplete, a baseline assistant can ask for more information. But not all missing facts are equally useful. Some details decide whether the task can be solved at all, while others have almost no effect on the outcome.

A second problem is answerability. Even a relevant question is a bad question if the user cannot reasonably answer it. Asking for an internal stack trace that the reporter never saw does not help because the question cannot produce usable information. Good clarification therefore needs two filters at once: ask only about information that affects success, and ask only in a way the user can realistically respond to.

The key principle. Ask for missing details only when they are both high-impact and answerable, because useful clarification depends on what matters for success and what the user can actually provide.

The algorithm as a flow

What it actually does

Analyze which fields drive success.

Use attribution analysis over software tasks to estimate which types of missing information most affect whether the task gets solved.

Analyze which questions users can answer.

Compare user responses to different question types so the system learns which requests for information are realistically answerable.

Turn both analyses into rewards.

Reward the question policy when it asks about details that are both relevant and answerable because those are the questions that improve resolution.

Train the clarification module.

Optimize a question-asking model on underspecified tasks so it learns when to ask and what to ask.

Resolve with fewer clarifications.

Use the learned policy to ask only the minimum high-value questions needed before proceeding.

What the paper changes

What the paper changes

The paper changes clarification from generic follow-up questioning into reward-guided selection of high-impact, answerable questions.

The hidden quantity

The hidden quantity

measured quantity  =  clarification value of a question

The important hidden quantity is the value of a possible question. A question has high value when its answer is likely to change the success of the task and when the user can actually provide that answer. A question with only one of those properties is still weak.

The paper makes that value measurable through past-task analysis. Relevance estimates how strongly a missing detail predicts task success. Answerability estimates whether users tend to provide that detail when asked. Good clarification lives in the overlap.

Why it works

Why this works

Clarification is a resource allocation problem. Every question costs time and user effort. If the assistant asks about low-impact details, it burns that budget without improving the chance of success. If it asks for information that the user cannot provide, it burns the budget twice: once on the question and again on the dead-end reply.

By measuring relevance from past task outcomes, the system gets a map of which missing details matter most. By measuring answerability from observed user responses, it gets a second map of which questions are realistic. The reinforcement-learning objective then prefers the intersection of those maps, because that is where one question can unlock real progress.

This also helps the assistant decide when not to ask. If the remaining missing details are low-impact or unanswerable, the best action may be to proceed directly or choose a safer default, because further clarification would add friction without enough return.

Math after the picture

Score a question by relevance and answerability

First in words:

A simple summary is to score each candidate question by combining how much the missing detail matters for success and how likely the user is to provide that detail.

Then the compact form:

question_value(q) = relevance(q) * answerability(q)

Every symbol:

qone candidate clarifying question
relevance(q)how strongly the requested information affects task success
answerability(q)how likely the user is to provide a usable answer to that question
question_value(q)the expected benefit of asking that question now
A tiny worked example
Question A asks for the software version. Its relevance is 0.9 and answerability is 0.8.
Question B asks for an internal trace the user probably does not have. Its relevance is 0.8 and answerability is 0.1.
Question A scores 0.9 * 0.8 = 0.72.
Question B scores 0.8 * 0.1 = 0.08.
Question A should be asked first because it is both important and likely to receive a useful answer.

The full training reward is more detailed, but this product captures the paper's central idea that a good clarification question must satisfy both criteria at once.

What can go wrong

What can go wrong

Past data can misestimate relevance. If the training tasks overrepresent one issue pattern, the model may over-ask about that pattern because the estimated impact of those details looks larger than it really is.
Answerability varies across user groups. A question that is easy for one team to answer may be impossible for another, so one global answerability estimate can still produce poor questions for some users.
The model can skip a rare but decisive detail. A low-frequency detail may look unimportant in aggregate and still decide a specific task, so aggressive question pruning can miss the one question that was actually necessary.
Done right. The method works when relevance and answerability estimates are updated on realistic task data, because then the question policy targets the missing details with the highest practical payoff.
What a runnable demo should prove

What a runnable demo should prove

Build a benchmark of underspecified software issues where each task has a hidden set of missing fields and a simulator for user replies. Compare a generic question policy against a value-driven question policy that scores candidate questions by estimated relevance and answerability. Track how many questions each policy asks before solving or failing the task.

The demo should show that the value-driven policy reaches the needed details faster because it avoids low-impact or hard-to-answer questions. It should also show that some tasks are best handled with no question at all when the remaining missing details do not justify another round-trip.

clarification_efficiency = resolved_tasks / total_questions_asked

A convincing demo must show that fewer questions can still solve as many tasks when those questions are chosen for impact and answerability rather than asked by habit.
