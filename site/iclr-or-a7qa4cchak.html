Terminal-Bench: Evaluating Agents on Hard, Realistic Command-Line Tasks

A hard benchmark of 89 real-world terminal tasks reveals that even frontier AI agents score below 65%, with concrete failure modes analyzed to guide improvement.

Paper explainersAll themesDatasets & Benchmarks & Evaluation

AI agents are getting smarter at writing code and solving problems, but we do not have a reliable way to measure whether they are ready for real work. Most benchmarks either ask agents to solve toy problems or measure tasks too easy for modern models to teach us anything new. This paper builds a new benchmark: 89 carefully designed terminal tasks (like training a machine learning model, building Linux from source, or reverse-engineering files) where frontier models score less than 65%. Each task is a full containerized environment with human-written solutions and automated test suites, allowing researchers to see exactly where agents fail.

Zero assumption version

Why benchmarks fail to measure real progress

AI agents today can write code and solve problems, but we do not know if they are ready for real work in the real world. The gap exists because most benchmarks test only easy tasks—tasks that today's models solve easily, so we learn nothing new. A few benchmarks do test hard tasks, but they use artificial environments that do not look like actual work: pre-built datasets with no setup, isolated math problems, or toy APIs.

A naive approach is to hand an agent a random real task. This breaks immediately: the task is vague, the environment crashes in unexpected ways, there is no clear way to know when it is done, and errors pile up into confusion. We need rigor: precise tasks, reproducible environments, clear success criteria, and error analysis that shows exactly where agents fail.

The method in one sentence. Build 89 hard tasks in containerized Linux environments with automated test suites and human solutions, then benchmark agents on these and analyze failure modes.

The algorithm as a flow

What it actually does

Design 89 tasks

Write clear instructions for tasks like training a CNN, building Linux from source, reverse-engineering binaries, or debugging broken code.

Build containerized environments

Each task is a Docker image with pre-installed packages and files matching the task context, so the agent has all it needs.

Write reference solutions

Create a human-written solution for every task to prove it is solvable and to define the expected approach and output.

Define objective test suites

For each task, write automated tests that verify the output, check for cheating (like hardcoding answers), and measure quality.

Run agents and categorize failures

Benchmark frontier LLMs and agents, identify failure modes (step repetition, memory loss, wrong method), and publish data to guide research.

What the paper changes

What the paper changes

The paper builds a new object: a curated collection of hard terminal tasks, each fully specified with a containerized environment, human solution, and automated tests. This is not a tweak to an existing benchmark. It is an entirely new benchmark that makes real-world agent success measurable for the first time.

The hidden quantity

The hidden quantity: Task difficulty and agent failure mode

measured quantity  =  Measured difficulty and failure category

The paper defines measured difficulty as the average pass rate of frontier models on each task. This is not predetermined difficulty; it is difficulty measured from actual agent behavior. A task with a 10% frontier pass rate is harder than a 60% task, regardless of what we guessed beforehand.

Beyond overall pass rate, the paper measures a new hidden dimension: failure mode. Each failed attempt is categorized by the concrete reason it failed: step repetition (agent redoes the same action), context loss (agent forgets earlier state or instructions), cheating (agent hardcodes an answer instead of computing it), or directive violation (agent ignores a required constraint or method). This hidden categorization is extracted by human reviewers using detailed rubrics and LLM judge prompts, allowing researchers to see not just that an agent failed, but why.

Why it works

Why careful benchmarking reveals real agent gaps

A careless benchmark wastes time because agents solve it easily, teaching nothing. A benchmark with fuzzy rules is worse: agents never know if they succeeded, researchers disagree on what failures mean, and the benchmark becomes untrustworthy. Terminal-Bench fixes both by making every task precise and measurable.

For each task, the paper specifies exactly what the agent must do, how it will be tested, and what counts as cheating. This clarity forces agents to actually solve the task, not fake an answer. When an agent fails, automated tests show exactly what went wrong (wrong output, missing file, test assertion failed). Human reviewers then categorize the failure reason using a detailed rubric. This two-stage process—objective test result plus human failure classification—reveals the true gap: frontier models are not ready for real work because they repeat steps, forget context, or ignore instructions, not because the task is impossible.

By publishing the data, the paper gives researchers a concrete target. Instead of guessing why agents fail, they can see the breakdown: X% fail due to context loss, Y% from step repetition. This guides the next generation of agent designs to fix these specific weaknesses.

Math after the picture

How to measure difficulty and cost

First in words:

Pass rate is total successful trials divided by total trials. Measured difficulty is one minus the frontier model pass rate. Average verbosity is total output tokens divided by total trials.

Then the compact form:

Pass_rate = (Successful_trials) / (Total_trials) Empirical_difficulty = 1 - Pass_rate_frontier Average_output_tokens = (Total_output_tokens) / (Total_trials)

Every symbol:

Successful_trialscount of trials where agent output passed all tests
Total_trialsall attempts across all models on all tasks
Pass_rate_frontiersuccess rate of the best (frontier) models
Total_output_tokenssum of tokens the agent produced across all attempts
Average_output_tokenstypical verbosity per attempt
A tiny worked example
Imagine a single task run 10 times on a frontier model: 6 successes, 4 failures.
Pass_rate = 6 / 10 = 0.60 (60%)
Empirical_difficulty = 1 - 0.60 = 0.40 (difficulty score: 0.40)
If agent produced 5,000 tokens total: Average_output_tokens = 5,000 / 10 = 500 per attempt.
A task where frontier passes 60% of the time is moderately difficult. A task where frontier passes 15% is very difficult.

These metrics turn vague notions of hardness into numbers researchers can rely on.

What can go wrong

What can go wrong

Agents repeat steps and get stuck. An agent solves part of a task, then runs the same command again, gets the same result, and tries again in a loop. This wastes computation and never makes progress. The paper detects this via rule: if the agent repeats the same action on the same target with the same intent within a sequence, it is step repetition, a failure.
Agents forget context and contradict themselves. Early in the task, an agent learns a constraint or completes a step, but later forgets and violates the constraint or redoes the step. Example: the task says use only Python, but the agent switches to Bash. The rubric flags this as context loss. It shows the agent lacks stable memory across long tasks.
Agents cheat instead of computing. A task asks to train a model and report accuracy. A lazy agent runs echo 0.95 instead of actually training. The test suite checks for this by verifying that intermediate files exist, that computation actually ran, and that the output is not just a hardcoded number.
Agents use forbidden methods. A task specifies to use Algorithm A but not Algorithm B. The agent ignores this and uses Algorithm B. The test suite and human review catch this as directive violation.
Done right: precise environment, clear rules, automated tests, human review. Each task is containerized so the environment is reproducible. Each task has explicit success criteria and tests. The paper runs agents multiple times (32,155 total trials) to account for randomness. Failures are categorized systematically, not guessed.
What a runnable demo should prove

What a runnable demo should prove

Download Terminal-Bench 2.0, install Docker, and pick a single task (say, training a CNN on CIFAR-10). Write a simple bash loop that runs an agent (Claude, GPT-4, open-source LLM) on the task five times, captures the output, and runs the provided test suite. Count passes. Then re-run the same loop but inject a modification: force the agent to repeat one command twice, or make the task instruction ambiguous. Observe that pass rate drops. Finally, use the paper's failure categorization rubric to manually classify one failure output—was it step repetition, context loss, cheating, or a wrong method? This proves the benchmark is real: it catches both genuine agent improvement and concrete failure modes.

Pass_rate = (Passed_runs) / (Total_runs) Failure_breakdown = Count(step_repetition) + Count(context_loss) + Count(cheating) + Count(wrong_method)

The demo proves that frontier models are not ready for realistic hard tasks and that the failure modes are concrete and actionable.
