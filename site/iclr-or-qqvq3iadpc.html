It's All Just Vectorization: einx, a Universal Notation for Tensor Operations

Describe many tensor operations with one consistent notation by treating them as elementary operations plus a rule for how axes are lifted, reduced, repeated, or rearranged.

Paper explainersAll themesOther

Tensor code, where tensor means a multi-axis array of numbers, is full of operations that are conceptually simple but written through many unrelated APIs. Summation uses one set of arguments, gathering uses another, reshaping uses another, and each framework adds its own special cases. That inconsistency causes shape errors, meaning mistakes where the sizes or roles of axes do not line up. einx starts from a different view. Most tensor operations can be decomposed into a small elementary action, such as elementwise multiplication, indexed read, dot product, or identity, together with a vectorization rule, meaning a rule that says how that elementary action is applied across axes of larger arrays. Once that decomposition is explicit, one notation can describe operations that now live in many separate APIs.

Zero assumption version

Tensor APIs hide one idea behind many special cases

A tensor is a multi-axis array. Everyday machine-learning code keeps moving, reducing, indexing, and combining these arrays. Current Numpy-like APIs usually express those moves with operation-specific parameters, meaning function arguments that control axis behavior, such as axis, broadcast rules, advanced indexing conventions, and reshape syntax.

That style is compact for experts, but it spreads one conceptual task across many unrelated function signatures. Readers must remember which arguments select axes, which ones create new axes, and which ones merge axes. The result is code that is harder to read and easier to misuse.

The paper's move. Treat tensor programming as elementary operations plus vectorization rules, then express those rules in one declarative notation that mirrors indexed loop structure.

The algorithm as a flow

What it actually does

Choose an elementary operation

Start from a small base action such as identity, multiplication, dot product, or indexed read because many higher-order tensor routines reduce to one of these.

Describe the axis roles

Write a declarative expression that says which axes are kept, reduced, repeated, merged, split, or indexed because the axis pattern is the real source of variation.

Interpret by loop structure

Read the expression as a pointful indexed program because that gives a direct operational meaning to the notation.

Compile to backend calls

Translate the declarative form into framework-specific operations because the system is meant to sit on top of existing tensor libraries.

Reuse the same rules everywhere

Apply one notation across gathering, reduction, multiplication, reshaping, and many other cases because consistency is the main design goal.

What the paper changes

The paper changes the interface between human intent and tensor backends. Instead of learning many unrelated function signatures, the programmer states axis structure once in a universal notation.

The hidden quantity

Axis-role pattern

measured quantity  =  axis-role pattern (the assignment of each axis to keep, reduce, repeat, merge, split, or index)

Most tensor bugs are really axis-role bugs. A programmer intends one axis to be reduced, another to be preserved, and a third to be matched against indices, but the API hides those roles behind operation-specific parameters. The hidden object is therefore the axis-role pattern itself.

einx makes that object explicit. Once the axis-role pattern is written down, many functions that looked unrelated become simple variants of the same base action because only the role assignment changes.

Why it works

Why a universal vectorization view unifies tensor code

A large share of tensor programming complexity is accidental rather than semantic. The underlying computation may be simple, but each library exposes it through a different entry point. If the programmer first identifies the elementary action and then states the axis-role pattern, the remaining variation becomes systematic instead of ad hoc.

Loop notation is the right reference point because it already makes axis roles explicit. A loop index tells you whether a dimension is traversed, matched, reduced, or copied. einx keeps that clarity while still compiling to backend tensor routines, so the user gains readability without giving up library interoperability.

The notation also unifies operations that were previously separated by API boundaries. Indexed reads, matrix products, where matrix means a two-axis array, reshapes, broadcasts, and transposes all become specializations of a few base actions under different vectorization rules. Code becomes easier to inspect because the declaration shows structure directly.

Math after the picture

A tensor operation equals base action plus axis rule

First in words:

einx represents a higher-order tensor program by pairing a small elementary operation with a declarative rule for how the operation is lifted across axes

Then the compact form:

tensor_operation = vectorize(elementary_operation, axis_role_pattern)

Every symbol:

elementary_operationa base action such as identity, multiplication, dot product, or indexed read
axis_role_patternthe declared roles of the axes in the input and output
vectorizethe lifting rule that applies the base action across the declared axes
tensor_operationthe final higher-order array program seen by the user
A tiny worked example
Suppose the base action is multiplication of two scalar values, where scalar means one single number.
If one axis is preserved on the left input and one axis is preserved on the right input, vectorization creates an outer product.
If one axis is matched and reduced, vectorization creates a dot product.
The scalar action is unchanged. Only the axis-role pattern changes.

This is why the paper claims many tensor APIs are the same idea repeated under different axis patterns.

What can go wrong

What can go wrong

The notation still has a learning curve. A universal language only helps if users learn its axis syntax, because otherwise the notation adds a second vocabulary on top of the old one, so short-term adoption may be slower for programmers who already memorize backend-specific calls.
Compilation may hide backend costs. A declarative expression can be clear while still lowering to an expensive backend sequence, so readability does not automatically guarantee good runtime behavior.
Very specialized operations may need extensions. If a backend operation carries semantics beyond axis manipulation and the small elementary set does not capture it, users may still need custom integration.
Done right. The design is strongest when the same project mixes many tensor backends or many operation types, because consistency then saves repeated context switching.
