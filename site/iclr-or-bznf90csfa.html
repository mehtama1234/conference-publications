Curation Leaks: Membership Inference Attacks against Data Curation

Even if a model is trained only on public data, an attacker can infer which private data guided the curation by attacking the curation pipeline at every stage: the scores, the selection, and the trained model itself.

Paper explainersAll themesAlignment, Safety & Fairness

Data curation means filtering a large public dataset to keep only the examples most useful for a task. A new privacy strategy takes this further: use private sensitive data just to guide which public examples are valuable, then train only on the curated public subset. This sounds safe because the model never touches the private data. But this paper reveals it is not. An attacker can interrogate the curation process at three points—the scoring phase, the selection phase, and the final model—to infer membership: which private examples were used to guide curation. The paper shows that even models trained exclusively on public data leak intimate details about the private guidance data.

Zero assumption version

Why curation alone does not guarantee privacy

In sensitive domains like healthcare and finance, companies have private patient or customer data that is valuable for training but too risky to use directly in a model. A natural idea: use the private data as a compass to pick useful examples from a large public dataset, then train only on those public examples. The trained model never sees private data, so intuitively it should be private.

But this assumption hides a key fact. The curation process itself—the act of selecting certain public examples based on private guidance—creates traces of the private data. Those traces appear in three places: the curation scores (the raw numbers saying how valuable each public example is), the selection decision (which public examples ended up in the curated subset), and the trained model itself (which may subtly reflect patterns that correlate with the private guidance). An attacker with access to any of these artifacts can reverse-engineer which private examples influenced the curation.

Existing privacy-preserving data selection methods do not account for this three-stage leakage because they were designed for a different threat model—one where only the final trained model matters.

The core problem in one sentence. Curation pipelines leak private information at every step—not just the training, but the scoring and selection too—even though the final model never directly trains on private data.

What the paper changes

What the paper changes

The paper does not propose a new method to improve curation; instead it exposes a vulnerability in the curation pipeline itself, because attackers can intercept and interrogate intermediate artifacts (the scores and selections, not just the final model) to extract information about private guidance. By revealing that each stage of the pipeline independently leaks, it reframes the privacy threat from training-only to pipeline-wide.

The hidden quantity

How much private information leaks at each stage

measured quantity  =  privacy leakage at each stage

The paper measures a hidden quantity: how much information about private data can an attacker extract from each stage of the curation pipeline. This is not a single number but a profile. At the scoring stage, the attacker measures how well a classifier can predict private membership from observed curation scores. At the selection stage, the attacker measures whether fingerprinted probes are selected more often when a private target is present. At the model stage, the attacker measures whether prediction behavior shifts in ways correlated to private guidance.

The paper estimates this by designing custom membership attacks (ways to guess who was in the private set) tailored to each stage. For curation scores, they use likelihood-ratio attacks: they train two shadow curation runs (one with a target in the private set, one without) and measure how differently the scores come out. For the model, they inject fingerprinted samples that respond strongly to specific private targets, measure whether those samples are curated, and then ask whether the final model's predictions betray the presence of those targets. Each stage leaks independently, and the leaks compound.

Why it works

Why the curation pipeline leaks even without direct training on private data

Curation is a data attribution problem: it ranks public examples by how useful they are for a private target. When you compute these ranks, every score encodes information about which private examples influenced that score. That encoding is not cryptographically secure; it is just a number, and statistical patterns in those numbers reveal the private guidance.

Here is the causal chain. First, the curation algorithm takes private data T and public data D and outputs scores s for each example in D. Those scores are statistically correlated with private data: examples useful for the private target have high scores, others low. An attacker observing the scores can infer membership by asking: do these scores look like they came from a world where private example X was in T, or not? Second, the selection step picks the top-scored examples. Again, this creates a trace: if curating with private example X leads to a systematically different subset than curating without X, an attacker can detect that shift. The paper shows this by injecting probes into the pool—examples designed to have high scores only if a particular private target is present. Third, the trained model, even though it never sees private data, is trained on data that was selected by a process influenced by private data. This means the model learns patterns correlated to the private guidance. An attacker with query access can measure those patterns by comparing the model's behavior with and without those patterns.

Likelihood-ratio membership inference at the scoring stage

First in words:

membership score = log of (probability of observed scores if target was in private set divided by probability of observed scores if target was not in private set)

Then the compact form:

m_t = log( P(s | t in T) / P(s | t not in T) )

Every symbol:

m_tmembership score for target t (higher means more likely t was in T)
P(s | t in T)probability of observing these scores if t was used to guide curation
P(s | t not in T)probability of observing these scores if t was not used
sthe curation scores (one number per public example)
A tiny worked example
Suppose private example t is a medical scan. Without t, curation scores for similar scans average 25. With t in the private set, they average 68.
Attacker trains two shadow curation runs: one with t, one without. Shadow with t produces scores s = [65, 70, 68, 66, 69]. Shadow without t produces [24, 26, 23, 25, 27].
Observer sees actual scores [67, 69, 68, 70, 66]. These are much closer to the with-t distribution (mean 68, low spread) than the without-t distribution (mean 25, low spread). The log-ratio is strongly positive, inferring t was in T.

The likelihood-ratio attack works because the private data leaves a statistical signature in the curation scores. The signature is small enough to hide in a single score, but large enough to emerge clearly when many scores are aggregated.

What can go wrong

What can go wrong

Attacker has only black-box model access. The model attack is weaker if the attacker cannot query the model many times or cannot measure detailed prediction probabilities. It still works but with lower confidence.
Curation scores are not released publicly. If the curation algorithm runs privately and only outputs the curated subset, the score-based attack is blocked. But the selection and model attacks still work.
Private data is very different from public pool. If private examples are uncorrelated to the public pool, curation scores will be uninformative and membership becomes hard to infer. But modern curation methods (like those using learned representations of images or text) still leak.
Formal privacy guarantees protect the pipeline. Adding differential privacy noise to scores, selections, or model outputs blocks these attacks, at the cost of reduced curation quality. The paper suggests this is necessary for truly private curation.
What a runnable demo should prove

What a runnable demo should prove

Build a simple curation pipeline: given a small public dataset of MNIST digits and a private target set (e.g., images of the digit 7), compute curation scores as max cosine similarity to the target. Then run three attacks: (1) Train two shadow curation runs with and without each target digit class, compute likelihood-ratio membership scores from the observed curation scores. (2) Inject probe examples into the public pool that respond strongly only if the target class is in the private set, count how many probes are selected. (3) Train a classifier on the curated subset, query it with samples correlated to the private target, measure prediction confidence. Show that all three attacks recover membership with accuracy well above random (e.g., 75% vs 50%).

membership_accuracy = fraction of targets correctly inferred across all three attack stages

The demo should make it impossible to miss that curation leaks at every stage, and that no single stage is a privacy bottleneck. Plugging one stage does not help if the others remain open because an attacker can simply shift to attacking whichever stages are still undefended.
