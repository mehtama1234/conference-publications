RefineEvo: Planning-Guided Heuristic Evolution with Bidirectional Experience

Instead of asking an LLM to repeatedly invent heuristics from scratch, RefineEvo teaches the LLM to remember both what worked and what failed, then plan which invention move to try next.

Paper explainersAll themesOptimization

When an LLM tries to design a better algorithm for routing or packing problems, it usually starts over each time, forgetting its past attempts, because each prompt is independent and the model has no record of what came before. RefineEvo adds memory: a pool that captures not just successes but also the mistakes and their reasons, plus a planner that decides whether to try something entirely new or refine an old idea. The result: the LLM becomes a learner, not a trial-and-error machine.

Zero assumption version

LLMs inventing algorithms always start from scratch

LLM-based algorithm design fails to accumulate experience, because each call to the LLM is treated independently and previous failures are never stored or passed to the next attempt. When you ask the LLM to improve an algorithm and then ask again after testing the result, the LLM has no memory of what failed before. This makes progress slow, because without knowing what failed, each attempt is a blind guess, and you end up reinventing the same bad ideas repeatedly.

The beginner's approach: run the LLM in a loop and keep whatever works best. This loses valuable information: the small failures that teach you what NOT to try again, and the near-misses that almost worked.

The core problem. LLM-based algorithm design treats each attempt as independent; it never learns from what came before.

The algorithm as a flow

What it actually does

Track what worked and what failed

After each algorithm attempt, the system records: the algorithm's rules, the result quality, and whether it succeeded or flopped.

Find the lesson inside each attempt

For successes, extract the key idea (e.g., "lookahead beats pure greed"). For failures, extract the pitfall (e.g., "exploring too randomly misses the best routes").

Store in two pools

Positive insights go in one bin, negative pitfalls in another. Each tagged with the context it came from.

The planner decides the move

Before generating, a planner checks the current problem state and asks: should we explore new operators, or refine the ones we know work?

Inject memory into generation

The LLM gets a fresh prompt: the current goal, the parents to mutate, plus the top relevant wins and failures from memory. It generates a new algorithm, guided by the past.

What the paper changes

What the paper changes: the algorithm-generation prompt

Before RefineEvo, the LLM's prompt was bare: "Improve this algorithm." Now the prompt includes specific context: the current goals the Planner set, the parent algorithms chosen, and most importantly, the top success-stories and failure-lessons from the experience pool, because the LLM can use these memories to make better guesses instead of starting from scratch. The LLM does not search in a vacuum.

the object it moves  =  the generation prompt
The hidden quantity

The hidden quantity: relevance and trajectory alignment

measured quantity  =  how much past experience applies now

Before this paper, you could store past attempts, but you had no way to measure which ones actually mattered for the current problem. RefineEvo measures relevance: how similar is a past attempt's context to where we are now? It uses semantic similarity (a measure of how alike two ideas are, on a scale from 0 to 1, where 1 means identical). A past insight about "lookahead is good" matters more if we are currently stuck on the same kind of problem.

The paper also introduces trajectory awareness: not just "did this work?" but "did this work for the path we just took?" If an algorithm succeeded because of a specific sequence of moves, that history matters, not just the final score. The experience pool tracks both the insight and its context.

Why it works

Why it works: learning by example instead of guessing

When an LLM is told to invent something new, it relies on its training data. If all it knows is "try random moves until you find a good one," that is what it will suggest. But if you show it real examples of what succeeded and what failed — and most importantly, why — it learns the pattern.

RefineEvo works in three steps. First, the Reflector watches each attempt, extracts the core idea, and stores both successes and failures with their context. Second, when planning the next move, the Planner checks: are we stuck in a rut (keep trying the same moves)? Then explore new operators. Are we finding winners? Then refine them. Third, the LLM's prompt includes the most relevant past examples, so it generates new ideas that build on what worked, not guesses in the dark.

Why does this beat naive trial-and-error? Because the LLM is no longer inventing blind. It sees patterns in its own past attempts. A human designer would do the same: keep notes, look for what worked, avoid repeating mistakes. RefineEvo gives the LLM that notebook.

Relevance scoring and experience injection

First in words:

relevance_score = cosine_similarity(current_query, past_experience_embedding); retrieved_experiences = top_k_by_relevance(E_positive UNION E_negative, current_query)

Then the compact form:

Cexp = RETRIEVE(E+, q) UNION RETRIEVE(E−, q)

Every symbol:

E+pool of positive experiences (successful algorithms)
E−pool of negative experiences (failures and pitfalls)
qthe retrieval query built from current parents and operator goal
RETRIEVE(E, q)returns the top-k experiences from E by cosine similarity to q
Cexpthe combined set of retrieved insights (to inject into the LLM prompt)
Tiny worked example: routing problem
Suppose the current goal is: design an algorithm with lookahead. The planner emits this query.
The retriever searches E+ (wins) and finds: past-algorithm-7 had a two-step lookahead and scored 92/100, similarity 0.85. past-algorithm-3 had random lookahead and scored 68/100, similarity 0.72.
It also searches E− (losses): past-algorithm-12 had lookahead but used it on every node (too slow) and scored 40/100, similarity 0.81.
Top-3 retrieved: [past-algorithm-7 (win, high relevance), past-algorithm-12 (loss, high relevance), past-algorithm-3 (win, lower relevance)].
The LLM prompt now reads: 'Goal: add lookahead. Here is what worked: (describe past-alg-7). Here is a pitfall to avoid: (describe past-alg-12). Generate a new algorithm.' The LLM learns: lookahead is good, but not at every step.

Similarity scoring finds past experiences that are most aligned with the current query (a numeric score 0 to 1), picking the most relevant lessons.

What can go wrong

What can go wrong

Stale memories block new ideas. If the experience pool gets full of algorithms that work for small problems, it may bias the LLM to stay small-focused when it should scale up. The Planner mitigates this by periodically forcing exploration, but if the thresholds are wrong, this fails.
Contradictory lessons cause confusion. If one success says "use greed" and another says "use randomness," and both worked in different contexts, the LLM must infer when each applies. If context is not tagged precisely, the prompt becomes noisy.
Relevance measurement depends on how the algorithm captures meaning. The system converts past experiences into high-dimensional numerical descriptions (arrays of numbers, each capturing some aspect of an idea). Similarity is measured by comparing these arrays. This works if the arrays capture what "similar problem" means. For some optimization variants, two problems might look similar in this space but need different algorithms.
Done right. The planner regularly audits the experience pool and removes contradictions. Relevance is measured on the actual problem instance properties, not just vague descriptions. The result: the LLM learns instead of loops.
What a runnable demo should prove

What a runnable demo should prove

Build a tiny routing or bin-packing optimization problem (e.g., 20 packages, 3 bins, find the best assignment). Run RefineEvo for 10 generations, storing each attempt and its score. After each generation, show: (1) the quality of the best algorithm found so far, (2) the size and composition of the experience pool, (3) which past experiences were retrieved for the current generation. Also show the case without memory: a baseline LLM that generates 10 algorithms without any experience pool, just raw prompting.

quality_improvement = (score_with_memory - score_without_memory) / score_without_memory; token_ratio = tokens_used_with_memory / tokens_used_without_memory

The demo should make it impossible to miss: the LLM with memory finds better solutions earlier and uses fewer API calls overall, because it avoids repeating past mistakes and builds on what already worked. The memory makes visible progress, not random wandering.
