RoboMME: Memory for Long-Horizon Robot Manipulation

A benchmark showing that different ways to feed past observations into a robot policy each work best for different kinds of tasks.

Paper explainersAll themesRobotics & Control

Robots must remember what happened before—like counting how many times to push an object, or tracking where it went when hidden. Most robot policies today have no memory at all, so they can only react to what they see right now. This paper tests three concrete ways to add memory to a vision-language-action policy (a model that reads images and language instructions, then outputs robot actions) and shows which memory designs work best for which tasks.

Zero assumption version

The robot sees only the present frame

A robot policy is a function that takes a picture (and a language instruction) and outputs a motor command. If you train it on task frames one at a time, the policy has no way to look back and count or track hidden objects. This breaks on any task where the action depends on something that happened in the past—for example, a task might say push the red block five times, but the policy sees only one frame and has no idea how many times it has already pushed.

A beginner might try adding the past few frames as extra pictures to the input, hoping the model will learn to remember. This works only if the model has enough capacity (many parameters, or numbers to adjust) and enough training time to figure out the pattern on its own—in small models or short training runs, the signal gets lost in the noise. It also wastes effort: the model must rediscover what "history" means for every task and configuration, instead of having a clear structure for memory built in.

The paper's fix in one sentence. Give the policy an explicit memory slot, fed into each layer in three different ways, so the policy can reliably extract and use past information without having to learn it from scratch.

The algorithm as a flow

What it actually does

Encode the history

Sample up to 64 frames from the robot's execution history, encode each as tokens using the vision encoder.

Project to policy width

Shrink the encoded frame tokens from 2048 dimensions to 1024 to match the policy network.

Create a memory token

Concatenate all the history tokens into one long list, or compress into a fixed slot via recurrence.

Feed into the policy

Insert the memory token into the policy network in one of three ways: as concatenated input, as a modulator (turning layers on/off), or as a separate expert that attends to the action expert.

Action output

The policy now outputs the next action, informed by both current observations and memory.

The hidden quantity

The hidden quantity: task-memory fit

measured quantity  =  which memory design works best for which task

The paper measures something important but hidden: each memory design (concatenate input, modulate layers, expert-based) has a different strength depending on the task structure. One design might excel at counting actions, another at tracking occluded objects, another at following procedural steps. The paper does not give this quantity a formal number—instead it is revealed through the benchmark results: each task is solved best by a different memory architecture.

The paper estimates this by running all three memory designs on all 16 tasks and observing success rates. By comparing the rank order (which design wins on which task), the paper infers that memory effectiveness is not universal—it is intrinsically tied to the task's temporal, spatial, object, and procedural demands.

Paper reading. RoboMME comprises 16 manipulation tasks constructed under a taxonomy evaluating temporal, spatial, object, and procedural memory. The paper evaluates 14 memory-augmented VLA variants with three integration mechanisms (memory-as-context, memory-as-modulator, memory-as-expert). Results show task-dependent effectiveness: no single design wins on all tasks because some tasks benefit from simple observation concatenation, others from fine-grained layer control, and others from dedicated procedural reasoning.
Why it works

Why different memory designs fit different tasks

Each memory architecture trades off how memory information flows into the policy. Concatenating memory with input means the policy sees memory tokens as just more pictures to process—cheap and flexible, but memory competes with current observations for the model's attention. Modulation uses an adaptive layer-normalization: memory controls which hidden-layer features get scaled up or down by adjusting how much each feature contributes to the decision. This is lightweight (it does not add many learnable weights, or numbers that the training process adjusts) but can only do multiplicative control, not additive reasoning. The expert architecture runs memory through its own path and has it attend to the action expert through specialized cross-attention, giving it more expressiveness but requiring more computation.

Which design fits a task depends on what the task asks of memory. If the task is counting (a purely temporal memory need), the simple concat approach may suffice because the policy just needs to see the numbers go by. If the task requires choosing which action to take based on spatial context (such as choosing which direction to push based on where the object last was), the modulation design may be better because it can turn on the spatial reasoning layers. If the task requires procedural reasoning (following a sequence of high-level steps), the expert design may excel because it can maintain a separate procedural state and reason about the action expert's output.

Math after the picture

Equation for memory-as-modulator

First in words:

At each layer of the policy, apply adaptive layer-normalization: divide each hidden feature by its variance, multiply by a learned scale parameter conditioned on memory, then add a learned shift. This lets memory amplify or suppress different features.

Then the compact form:

y = gamma(m) * (x - mean) / sqrt(var) + beta(m)

Every symbol:

xthe hidden layer features before normalization
meanaverage value across the feature dimension
varvariance (spread) across the feature dimension
mthe memory token (encoded past frames)
gamma(m)learned scale multiplier, conditioned on memory
beta(m)learned shift, conditioned on memory
ythe output features, modulated by memory
A tiny worked example
Suppose the hidden layer has one feature: the value 5.0. Its mean is 3.0, variance is 4.0 (so std-dev is 2.0).
Normalize: (5.0 - 3.0) / 2.0 = 1.0.
Memory encodes that the robot is tracking a moving object. This outputs gamma(m) = 2.0 (amplify spatial reasoning) and beta(m) = 0.5 (slight shift).
Final output: 2.0 * 1.0 + 0.5 = 2.5.
Without memory, gamma = 1.0 and beta = 0.0, so output would be 1.0. Memory has doubled the importance of this feature—now the policy pays more attention to spatial context.

Memory acts as a control surface, turning policy reasoning up or down by changing the scale and shift at each layer.

What can go wrong

What can go wrong

Memory explodes or vanishes. If the memory token is not properly normalized or projected, its scale can grow over many timesteps or shrink to noise. The paper uses a fixed-size memory slot and careful projection to 1024 dimensions to keep this in check, but careless designs will fail.
History sampling mismatch. The paper samples every 16 frames from the history. If this skip rate is too large, important transitions are missed. If the skip rate is too small, the memory token becomes too large and slows training. The paper shows this is task-dependent—one skip rate does not fit all.
Recurrent memory destabilizes training. Recurrent designs (which compress history into learnable slots) performed worst in the paper's experiments. The authors infer this is because the base policy model was not pretrained with recurrence, so fine-tuning is fragile. Fixing this requires deeper architectural integration and recurrence-aware pretraining.
Done right. Use explicit memory tokens tied to the task's structure, project to a fixed width (1024), and match the integration mechanism to the memory demands (concat for temporal, modulate for spatial, expert for procedural). Test on a diverse set of tasks to validate the choice.
What a runnable demo should prove

What a runnable demo should prove

Build a simple robot task where the correct action depends on something that happened five steps ago (e.g., push a block twice, then rotate it; the rotation choice depends on how many times you already pushed). Train the base policy without any memory. Then train three variants: one that concatenates the last five frames, one that uses modulation with a memory token, and one that uses an expert. Measure success rate on test episodes.

success rate = (number of episodes where the action sequence was correct) / (total episodes)

The demo must show that at least one memory design reliably solves the task, while the base policy fails because it has no way to count or recall. Ideally, different task variants (counting, tracking, procedural) favor different memory designs.
