Persona2Web: Benchmarking Personalized Web Agents for Contextual Reasoning with User History

Persona2Web tests whether a web agent can use a user's past behavior to resolve ambiguous requests instead of waiting for the user to specify every preference directly.

Paper explainersAll themesAgents & Tool Use

Real users often ask for something incomplete such as 'book a dinner spot for Friday' or 'find me a laptop for travel' and expect the system to fill in unstated preferences from earlier behavior. Most web-agent benchmarks ignore that problem and reward only direct instruction following. Persona2Web focuses on ambiguous requests plus user history, because personalization is valuable only when the agent can turn past evidence into the missing constraints that make the request concrete.

Zero assumption version

Ambiguous requests need personal context

A request can be syntactically clear yet operationally incomplete. 'Find a hotel for my trip' does not say price range, preferred neighborhood, cancellation habits, or whether the user values quiet rooms over short commutes. Humans expect those gaps to be filled from earlier behavior.

A benchmark that ignores user history cannot reveal whether the agent truly personalizes. It only measures direct task execution after the full preference set is already written into the prompt. That misses the harder part of web assistance: resolving ambiguity from earlier evidence.

In one sentence. The agent must infer missing constraints from user history, because many realistic web tasks are underspecified at the moment of request.

What the paper changes

What the paper changes

The paper changes the benchmark target from plain task completion to personalized task completion under ambiguity. The unit being tested is not just web navigation but contextual preference recovery from history.

the object it moves  =  preference recovery from user history
The hidden quantity

The hidden quantity: preference evidence strength

measured quantity  =  preference evidence strength

Preference evidence strength measures how strongly the user history supports one interpretation of the ambiguous request over others. Repeated mid-price bookings and repeated vegetarian choices make one option much more defensible than an expensive steakhouse.

This quantity matters because personalization is not binary. Some histories contain clear repeated patterns, while others are noisy or mixed. A good benchmark must vary that strength so it can test whether agents improve when the history truly contains enough evidence to justify a personalized choice.

Why it works

Why this benchmark reveals real personalization ability

A direct instruction benchmark cannot distinguish between an agent that understands the user and an agent that simply copies explicit constraints. Persona2Web forces the issue by withholding some of those constraints from the request and placing them in history instead.

The benchmark is informative because the agent must do two linked jobs: interpret history and execute on the live web. If it picks the wrong option despite good browsing, the failure is in preference recovery. If it infers the right preference but cannot act on the website, the failure is in web execution. Separating those pieces makes diagnosis possible.

Using real web tasks matters because personalization is only useful when it changes an actual decision. The benchmark therefore measures whether the recovered preference changes what the agent books, buys, or selects, because that is the point where contextual reasoning becomes user-visible behavior.

Math after the picture

The equation for personalized decision quality

First in words:

A decision is good when it satisfies the task request and also matches the preferences implied by the user's history.

Then the compact form:

personalized_score = task_fit + history_weight * preference_match

Every symbol:

task_fithow well the chosen web action satisfies the explicit request
history_weighthow strongly the evaluation values alignment with user history
preference_matchhow well the chosen option matches the hidden preferences supported by history
personalized_scoreoverall benchmark score for the agent's final action
A tiny worked example
The request is 'find dinner near the venue.' Two options are equally near.
Option A is vegetarian and mid-price. Option B is steakhouse and expensive.
Suppose both options satisfy the explicit request, so each gets task fit 5.
History shows repeated vegetarian and moderate-price choices, so option A gets preference match 4 and option B gets 0.
With history weight 2, option A scores 5 + 2 * 4 = 13, while option B scores 5 + 2 * 0 = 5.
The benchmark rewards option A because it uses the user's past behavior to resolve the ambiguity.

The scoring highlights that a task can be completed in a generic way yet still fail as personalized assistance.

What can go wrong

What can go wrong

History is noisy or mixed. If the user's past behavior reflects several competing preferences, the benchmark may not have one clear best answer, so evaluation becomes harder to interpret.
Preference changes over time. Old history can mislead the agent if the user recently changed habits, because repeated past actions no longer describe the current intent.
Web execution dominates the score. A strong personalization model can still fail the task if it cannot navigate the website, so the benchmark must separate reasoning failure from browsing failure.
Done right. The benchmark is most informative when histories contain interpretable preference traces, ambiguity is controlled, and scoring distinguishes contextual reasoning from web control errors.
What a runnable demo should prove

What a runnable demo should prove

Build a mini shopping or booking website with several equally plausible options under the literal request. Give each synthetic user a history that reveals stable price, cuisine, or location preferences, then ask ambiguous new tasks.

Compare a history-blind agent with a history-aware one. The history-aware agent should choose options that better match the user's past behavior because it uses earlier evidence to fill the missing constraints instead of treating every request as generic.

history_match_rate = history_consistent_choices / ambiguous_tasks and task_completion_rate = completed_tasks / total_tasks

The demo should show that personalization matters most when several options satisfy the explicit request and only the history tells which one the user would actually want.
