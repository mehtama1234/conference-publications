TGM: A Modular and Efficient Library for Machine Learning on Temporal Graphs

A unified library that treats continuous and discrete temporal graphs as two views of the same data, eliminating the slowdown from redundant code paths and enabling new research questions.

Paper explainersAll themesGraph & Geometric Learning

Temporal graphs are networks that change over time—edges appear and disappear, node properties shift. Unlike static graph libraries (which are mature), temporal graph libraries fragment researchers into two separate worlds: continuous-time (streaming edge events) and discrete-time (snapshots at fixed intervals). This paper builds a single unified library, TGM, that handles both as different views of the same underlying data, making it seven and a half times faster than the previous standard library because it eliminates redundant data transformations—one storage, two views, one compute pipeline—and opening research questions that were impractical before because now researchers can directly compare both time representations without dual-library overhead.

Zero assumption version

The fragmented temporal graph world

Before this paper, researchers had to choose: work with continuous-time methods (incoming events processed as a stream, predictions at any moment) or discrete-time methods (graph snapshots at fixed time intervals). These two approaches used separate codebases. A beginner trying to compare them had to install multiple libraries, write conversion code by hand, and wait for redundant computations—the same data transformed in two different ways.

The result: no direct comparison between the two worlds, researchers couldn't easily borrow ideas from one to the other, and each model got reimplemented separately. The hidden cost was computational: a single temporal graph got processed twice, once for each time representation, even though they describe the same ground truth.

The paper solves this by: unifying both time representations in a single library, so one temporal graph can be viewed as continuous-time streaming or discrete-time snapshots without duplication, and code paths share computation.

The algorithm as a flow

What it actually does

Store the temporal graph once

Immutable copy-on-write storage preserves all timestamps and events in a single representation.

Expose two time lenses

Same data viewed as a continuous stream (event at any moment) or as snapshots (every hour, day, etc.).

Register transformation hooks

Custom code (temporal neighborhood extraction, feature updates, discretization) plugs in once and serves both views.

Materialize batches on device

For each training step, pull a batch from either view—it comes from the same underlying data, so no duplication.

Train the same model on both

One model code path, two time representations—researchers now compare CTDG vs DTDG directly.

The hidden quantity

The hidden quantity: redundancy overhead

measured quantity  =  Redundancy ratio (duplicate compute fraction)

Redundancy is the fraction of total compute spent doing the same transformation twice—once for continuous-time and once for discrete-time. In the old fragmented ecosystem, if 40% of compute went to graph discretization, 80% went to discretization (40% for each library). The paper's unification targets this hidden quantity: it measures how much of the old system's compute was wasted duplication.

The paper estimates this by comparing runtime: old libraries spent time on both representations; TGM does the work once. The ratio is the speedup factor (seven and a half times), revealing that nearly 85% of the old system's compute was redundancy.

Why it works

Why unified storage eliminates redundancy

The mechanism is architectural. A temporal graph is a set of timestamps and edges. Continuous-time methods view it as a stream (events in order, make predictions at any time). Discrete-time methods view it as a stack of snapshots (group edges by time interval, slide through snapshots). Both describe the same data.

Old libraries stored the temporal graph twice—once optimized for streaming, once for snapshots. Every operation (neighbor lookup, feature update, discretization) was coded separately. TGM stores it once as an immutable copy-on-write structure. When a continuous-time method asks for temporal neighbors at timestamp T, the library fetches from the same storage. When a discrete-time method asks for the snapshot at hour H, it fetches from the same storage, just filtered by the time window. The hooks layer intercepts these requests and performs the transformation (streaming view, snapshot view) on demand, but the underlying data load happens once. Result: the same data flows through one compute pipeline, not two.

Old library (baseline): 7.8 seconds to transform and train.
TGM unified: 1.0 second to transform and train.

The seven and a half times speedup means nearly 88% of the old library's time was spent on redundant transformations. Unification saves that by routing both time views through one data pipeline.

What can go wrong

What can go wrong

User picks the wrong time granularity. If a researcher discretizes a temporal graph into snapshots at the wrong time interval (e.g., snapshots every second for slowly-evolving graphs), the snapshot view becomes either huge (millions of empty snapshots) or too coarse (all events squashed). TGM provides recipes to help, but a wrong granularity choice will still waste time because the library still must process all those empty snapshots or miss fine-grained temporal patterns in the original data.
Model assumes timestamps are uniformly spaced. Some DTDG models expect snapshots at regular intervals. Real temporal data often has bursty events: nothing for hours, then many edges in a second. A naive DTDG model will fail or learn poorly on highly non-uniform real-world temporal graphs.
Memory footprint grows with event count, not model size. Immutable copy-on-write storage saves the entire temporal graph in memory, because copy-on-write means the whole dataset sits in RAM ready for fast lookup without reloading. For temporal graphs with millions of events, this can exceed available RAM, because each timestamp and edge is stored permanently in memory; by contrast, batch-based discrete-time snapshots only hold one snapshot at a time and can be streamed from disk.
Done right. A researcher picks a sensible time granularity, uses TGM's recipes to build a baseline, then compares continuous-time and discrete-time architectures on the exact same data, no translation overhead, discovering that one time representation suits their graph and task much better than the other, because TGM's unification makes such a side-by-side experiment practical—it was nearly impossible before when continuous and discrete libraries were separate ecosystems.
What a runnable demo should prove

What a runnable demo should prove

Build a tiny temporal graph (10 timestamps, 50 edges per timestamp, 30 nodes). Load it once into TGM. Run a continuous-time model (TGAT, which processes edge events as they arrive) and a discrete-time model (GCLSTM, which sees snapshots). Measure the total time to perform 5 training steps on each. Then run both models on the old separate libraries (DyGLib for continuous-time, PyG Temporal for discrete-time). The demo's single proof point: TGM's combined time (TGAT + GCLSTM on TGM) beats the sum of separate library times (TGAT on DyGLib + GCLSTM on PyG Temporal).

speedup = (T_TGAT_DyGLib + T_GCLSTM_PyGTemporal) / (T_TGAT_TGM + T_GCLSTM_TGM)

The demo must show that TGM's shared storage and pipeline outperform the old forced choice of installing two libraries and transforming the data twice, because this is the paper's core claim—that unified architecture eliminates redundancy and enables direct comparison between previously incompatible method families.
