DIVE: Scaling Diversity in Agentic Task Synthesis for Generalizable Tool Use

Generate more generalizable tool-use data by executing real tools first and only then writing tasks that are guaranteed by those traces.

Paper explainersAll themesAgents & Tool Use

Tool-use models often fail on new tasks and new tool sets even after large post-training runs. This paper argues that the main weakness is not only the amount of synthetic data but its lack of structural diversity. DIVE addresses that by reversing the usual pipeline: execute real tools first, record the traces, and then derive only those tasks that are entailed by what actually happened. That keeps the data grounded while letting diversity scale along controllable axes.

Zero assumption version

Tool-use data often scales quantity more easily than diversity

Many synthetic tool-use pipelines start from a written task and then try to produce a trajectory that satisfies it. That makes it easy to generate large amounts of data, but many tasks end up looking structurally similar because the generator keeps reusing the same small set of tool combinations, the same action ordering, or the same style of dependency among calls.

This matters because generalization under tool-set shift depends on seeing many different tool arrangements during training. If the data repeats the same patterns, the model learns brittle routines. At the same time, diversity is hard to scale because every task still needs to be executable and verifiable. A random mix of tools is not enough if the resulting task cannot actually be grounded in a real action trace.

The paper's reversal. Run real tools first, then write tasks from the trace, because grounding comes for free when the task is derived from what really happened.

The algorithm as a flow

What it actually does

Choose a broad tool pool

Start with many real tools drawn from multiple domains.

Execute tools to create traces

Run actual tool calls and record the state transitions and call graph they produce.

Reverse-derive tasks

Write tasks that are strictly supported by those recorded traces.

Control diversity along two axes

Increase both the number of available tools and the variety of tool combinations per task.

Train and test under shift

Use the resulting trajectories for supervised and reinforcement fine-tuning, then evaluate on shifted tool-use benchmarks, meaning tests whose tasks or tool sets differ from training.

What the paper changes

What the paper changes

The paper changes the synthesis order. It replaces 'task first, trace second' with 'trace first, task second,' so that grounding and verifiability are inherited from real tool execution.

the object it moves  =  the order of task synthesis
The hidden quantity

The hidden quantity: structural diversity of tool-use traces

measured quantity  =  Trace diversity

Trace diversity is the range of different tool combinations and call structures present in the training data. Two datasets can have the same number of examples but very different trace diversity if one repeats the same few action patterns and the other spreads examples across many distinct tool sets and call graphs.

DIVE makes this quantity explicit by scaling two axes separately: how many tools exist in the pool and how varied the per-task tool sets are. This matters because generalization improves when the model has seen many ways that tools can interact, not merely many copies of one familiar pattern.

Why it works

Why reversing synthesis order helps generalization

Starting from real tool execution solves a grounding problem immediately. When a task is written after the trace exists, the task is guaranteed to be supported by actual tool behavior. That removes a large class of synthetic-data errors where the written task sounds plausible but the necessary action chain never truly existed.

The reversed order also makes diversity easier to control. Once the generator samples from a broad tool pool and executes different combinations, the recorded traces naturally vary in call structure. The derived tasks inherit that variety. This is more reliable than writing diverse-sounding tasks first, because many written tasks collapse to similar execution traces once tools are actually invoked.

Generalization improves because the model trains on a wider set of grounded action patterns. Under tool-set or task shift, the model has already seen more combinations of prerequisites, branching behavior, and cross-tool dependencies. The paper's scaling results support this interpretation because increasing diversity beats merely increasing raw data count under a fixed budget.

The synthesis rule

First in words:

A training task is admitted when it is strictly entailed by an executed tool trace, and dataset diversity rises by broadening tool-pool coverage and the variety of tool sets used per task.

Then the compact form:

task_kept = entailed_by_trace and diversity_budget_expanded

Every symbol:

entailed_by_tracethe written task is supported by the recorded real tool execution
diversity_budget_expandedthe dataset increases either tool coverage or per-task toolset variety
task_keptwhether the synthesized example enters the final training set
A tiny worked example
A trace opens a calendar, checks an email, copies meeting details, and sends an update message.
DIVE derives a task such as 'confirm the meeting change and notify the team' because the trace already proves those actions happened.
A different trace uses a file tool, a search tool, and a ticket tool, producing a very different call structure.
Both examples are kept because each is grounded and they expand structural diversity across the dataset.

The grounding condition keeps examples executable, and the diversity condition keeps the data from collapsing into one repeated interaction pattern.

What can go wrong

What can go wrong

Tool pool is wide but shallow. If many tools are included but only a few simple calls are executed for each, the resulting traces may still lack substantial structural variety.
Derived tasks become too narrow. If the reverse-derivation stage writes tasks that merely restate obvious surface actions, the data may be grounded but not challenging enough for planning.
Real tools drift over time. If tool behavior changes after traces are collected, some old grounded tasks may no longer reflect the current execution environment.
Done right. The recipe works when tool execution is broad and the derived tasks capture real goals, because then the dataset stays grounded while covering many distinct call patterns.
What a runnable demo should prove

What a runnable demo should prove

Build a small suite of real command-style tools such as file search, calendar update, message send, and record lookup. Generate one dataset by writing tasks first and then trying to satisfy them, and another by executing random but valid multi-tool traces first and deriving tasks afterward. Compare the number of distinct tool sets, the number of distinct call graphs, and held-out task performance of a small tool-use model trained on each dataset. The demo should show that the trace-first dataset generalizes better because it covers more grounded structures rather than more copies of the same template.

ood_success = held_out_tasks_solved / total_held_out_tasks

The key result to make visible is that diversity beats sheer count when the budget is fixed, because grounded variation across tool combinations teaches the model how to adapt when the next task uses a new arrangement of tools.
