VLM-VLA Fault Recovery

When a robot fails, show a vision-language model the frames leading up to the failure, have it pinpoint where in space and time things went wrong, roll the robot back to that moment, and retry.

Paper explainersAll themesRobotics & Control

Robots trained on vision and language (VLAs) frequently fail at manipulation tasks like picking up a cup or wiping a surface. When they fail, a human expert has to watch the video, figure out exactly when and where it all went sideways, and restart. This paper teaches a vision-language model (a model trained on pictures and text to describe what it sees) to do that diagnosis and rollback automatically because these models are skilled at comparing what should happen in an image to what actually happened, so the robot can try again without human help.

Zero assumption version

Robots fail and stay failed

When a robot trained on vision and language (a VLA model) picks up a cup and fails, the failure is silent — the robot just stops or pushes the cup the wrong way. A human has to rewind the video, watch frame by frame, pinpoint the exact moment when the robot's gripper (the claw on the end of the arm) went wrong, and manually reset the robot and task to that moment.

The naive approach is to let the robot keep trying from the start. But this wastes time: if the robot got 80% of the way through a 30-second pour-and-place task before the final placement failed, restarting from zero means the robot wastes 24 seconds doing work it already got right.

The fix in one sentence. Use a vision-language model to watch the video of the failure, automatically find the moment and place where things went wrong, roll the robot back to that point, and let it retry just the last part.

The algorithm as a flow

What it actually does

Record the whole attempt

As the robot acts, record every frame and the arm's joint positions over time.

Let the VLM watch

Feed the full video clip to a vision-language model and ask: where did it fail?

Localize the fault

The model outputs a timestamp and spatial region (e.g., frame 21, gripper area).

Rewind and reset

Move the robot's arm back to its pose at frame 20 and reset any objects the arm moved after that point.

Retry the last bit

Resume the task from the reset point; the robot now attempts just the action that failed before.

What the paper changes

What the paper changes

The paper introduces a VLM-VLA collaboration mechanism: a structured way for a vision-language model to communicate with the robot arm about where and when the failure happened, and what to do about it.

the object it moves  =  VLM-VLA collaboration
The hidden quantity

Spatiotemporal deviation

measured quantity  =  Spatiotemporal deviation

The paper measures how far in space and time the robot's action strayed from the intended path. This is the spatiotemporal deviation. Concretely: if the cup should have been lifted 3 centimeters straight up but instead fell over sideways, that is a large deviation in space (sideways movement) and time (it happens at frame 21 instead of frame 15 as planned).

The vision-language model outputs this quantity by watching the video frames: it pinpoints the exact frame number (temporal) and the region of the image where the deviation occurs (spatial). The paper's dataset (VLA-FixBench) annotates real robot failures with this information, so the model can learn to recognize it by seeing examples of real failures paired with their fault locations and times, which teaches the model to match visual patterns to fault signatures.

Why it works

Why this works

A vision-language model is trained on billions of pictures and text descriptions, so it is skilled at recognizing objects, actions, and when they are out of place. When you show it a video of a robot task, it can compare what actually happened to what should have happened (based on the task description) and spot the mismatch.

Once the model pinpoints the fault moment, the system rolls the robot back to the frame just before that moment. At that point, the robot's arm is back in the correct pose, and any objects the arm moved after the fault are reset. Now the task resumes from that safe point, and the robot retries the action that failed. Because the robot was already doing most of the task correctly, retrying just the end saves time and reuses the work already done correctly.

Math after the picture

The rollback equation

First in words:

The robot seeks the earliest frame in the recorded sequence where the deviation (measured as the distance between actual and expected arm pose) first exceeds a threshold, then rolls back to one frame before that point.

Then the compact form:

t_fault = argmin_t { t : ||pose_actual(t) - pose_planned(t)|| > threshold }

Every symbol:

t_faultthe frame number where the fault is detected
pose_actual(t)the arm's actual joint positions at frame t
pose_planned(t)the expected joint positions for frame t based on the plan
thresholdthe tolerance; deviation larger than this is a fault (e.g., 0.1 meters)
A tiny worked example
Frame 18: actual arm is at 45 degrees, planned is at 45 degrees. Deviation = 0. OK.
Frame 19: actual is at 47 degrees, planned is at 45 degrees. Deviation = 2 degrees = 0.035 meters at gripper. Threshold is 0.1 meters. OK.
Frame 20: actual is at 52 degrees, planned is at 45 degrees. Deviation = 7 degrees = 0.12 meters at gripper. Exceeds threshold. Fault detected.
Result: t_fault = 20. System rolls back to frame 19, resets arm to 45 degrees, and retries the action from there.

The model outputs which frame to roll back to; the equation formalizes the idea that a fault is when reality diverges too far from the plan.

What can go wrong

What can go wrong

The VLM misidentifies the fault. If the model points to frame 18 when the real slip happens at frame 21, the rollback happens too early, and the robot retries from a state that was never part of the actual failure. The retry may fail in the same way.
Fault is in perception, not control. If the robot's camera is dirty or the lighting changed, the VLM might blame the arm when the real problem is that the model cannot see the cup anymore. Rolling back the arm does not fix a sensor problem.
Rollback is impossible. If the failure involved the arm knocking an object onto the floor, rolling back the arm position does not put the object back on the table. Physical rollback is only possible for certain fault types (e.g., incorrect reach), not others (e.g., object dropped).
Done right. The system works well when the fault is a timing or control error (wrong gripper speed, wrong reach direction) and when the VLA is already mostly skilled at the task, so most of each attempt is correct.
What a runnable demo should prove

What a runnable demo should prove

Build a simple robotic task (or simulate it): a robot arm that must pick a small object from a table and place it in a box. Introduce a fault intentionally at step 4 of 5 (e.g., flip a random bit in the gripper command 30% of the time). Run the robot 20 times with restart-from-beginning, and 20 times with VLM-based rollback. Measure the total time and success rate for each method.

rollback_speedup = (total_time_restart) / (total_time_rollback)

The demo must make clear that on tasks where the robot succeeds partway before failing, rollback saves both time (because it skips the already-correct early steps) and retries (because the robot converges to success faster) compared to always restarting.
