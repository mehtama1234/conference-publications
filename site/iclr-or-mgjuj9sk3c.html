Code Generation Unlocks LLM Graph Understanding

When you ask an LLM to write Python code instead of just answering, it solves graph prediction tasks far better than prompting alone.

Paper explainersAll themesLLMs & Foundation Models

Large language models can tackle graph problems like predicting node labels. But should you ask the model to think out loud, call graph-surgery tools, or write runnable Python code? This paper tests all three on real-world graphs and finds code generation wins cleanly. It works even when simple prompting would fail.

Zero assumption version

Graphs fool simple language models

A graph is a network: items (called nodes) connected by links (called edges). A node classification task means: given a node and the network around it, predict a label (fraud or not; buyer or not). The graph might have text attached to each node, like a product description.

If you show an LLM the graph data as text and ask a question (prompting), it hits a hard wall. The text representation becomes huge. A graph with 10,000 nodes and lengthy text descriptions can explode to 100,000+ tokens (a token is roughly one word or a small chunk of text), and most LLMs have a token budget of a few thousand. Prompting also forces the model to understand graph structure from flat text, which is unnatural.

A beginner tries tool-use: give the LLM commands like fetch_neighbors(node_id) or compute_centrality(). This helps, but the model still must reason in words about what to fetch and why. On big graphs or complex tasks, even these hints do not carry enough signal to steer the model's predictions correctly, because the LLM is reasoning through language, which is slower and more error-prone than executing actual code on real data.

In one sentence. Tell the LLM to write Python code to solve the problem instead of just thinking out loud.

The algorithm as a flow

What it actually does

Frame the problem in text

Give the LLM the graph structure, node features, and task goal in plain language.

LLM generates Python

Model writes executable code (using libraries like NetworkX) to solve the task.

Execute and gather data

Run the code on the real graph. Collect neighbor labels, degrees, text encodings (compact numerical summaries of text meaning), anything the LLM asked for.

Parse predictions

Extract the model's final answer (label probabilities) from the code output.

Measure accuracy

Compare predicted labels to ground truth. Track which input types (structure, text, labels) the code relied on most.

What the paper changes

The channel between LLM and graph

The paper compares three ways to let the LLM access the graph: (1) prompting (show the graph in text, ask a question), (2) tool-use (give commands to inspect the graph), (3) code generation (let the LLM write and run Python).

Code generation is the object being changed: instead of the LLM producing an answer in natural language, it produces executable code that the system runs on real data and then feeds back to extract a final answer.

the object it moves  =  interaction mode
The hidden quantity

Input reliance: which parts of the graph matter most

measured quantity  =  dependence on structure vs. features vs. labels

When the LLM writes code, it can call different kinds of information: the graph edges (structure), the text attached to nodes (features), the labels of nearby nodes (labels). The paper measures how much each interaction mode relies on each input type by ablating (removing) pieces and watching accuracy drop.

The hidden quantity is how flexibly each mode adjusts. Prompting has a fixed view of the graph that you provide once. Code generation adjusts its strategy based on what works: on graphs with lengthy text it leans on text features; on graphs with tightly connected neighborhoods it leans on structure. This flexibility is stronger because the code can try different approaches and pick the one that actually works for this specific graph.

Why it works

Why code generation wins

Prompting fails because it crams the entire graph into text and hopes the LLM understands it. The model has no way to conditionally fetch just the relevant neighbors or do arithmetic on degree counts. Prompting either includes everything (token overflow) or includes nothing (it guesses).

Code generation flips the burden. The LLM does not have to parse a text representation. Instead, it writes small, focused code: get the neighbors, average their labels, measure confidence. The code runs on real data, so the LLM does not hallucinate numbers. If a feature is missing or a neighbor list is empty, the code can handle it cleanly. Most importantly, the LLM can inspect the actual graph structure programmatically and adapt: on dense graphs, it might only use immediate neighbors; on sparse graphs, it might go deeper.

The second source of gain is indirection. Prompting asks for a final answer directly. Code generation asks for a procedure. The LLM is better at producing correct procedures (because it can reason step-by-step and verify each step is valid Python) than producing correct predictions directly. Once the procedure is written, a Python executor handles the details; no hallucination risk.

The scoring formula

First in words:

prediction_confidence = average of (neighbor_label + text_similarity + structural_score), weighted by relevance

Then the compact form:

score_node = (1/K) * sum_i (alpha * y_neighbor_i + beta * sim(text, text_i) + gamma * centrality_i), alpha + beta + gamma = 1

Every symbol:

score_nodethe final prediction confidence for this node
Kthe number of neighbors considered (LLM chooses K
y_neighbor_ithe label (or probability) of neighbor i
sim(text, text_i)how similar this node's text is to neighbor i's text
centrality_ia measure of how important neighbor i is in the graph
alpha, beta, gammaweights the LLM assigns to each input type (they sum to 1)
A tiny worked example
Node X has 3 neighbors. Neighbor A is labeled fraud (1), B is not fraud (0), C is fraud (1).
The LLM's code assigns weights: alpha=0.5 (trust labels), beta=0.3 (text), gamma=0.2 (structure).
A has high text similarity (0.9), low centrality (0.3). B has low similarity (0.2), high centrality (0.8). C has medium similarity (0.6), medium centrality (0.6).
score = (1/3) * [0.5*1 + 0.3*0.9 + 0.2*0.3 + 0.5*0 + 0.3*0.2 + 0.2*0.8 + 0.5*1 + 0.3*0.6 + 0.2*0.6]
score = (1/3) * [0.5 + 0.27 + 0.06 + 0 + 0.06 + 0.16 + 0.5 + 0.18 + 0.12] = (1/3) * 1.85 = 0.62
Prediction: node X is fraud with confidence 62% (or 0.62 as a probability).

The LLM writes code that picks K, sets alpha/beta/gamma, and computes the score adaptively based on what the graph offers.

What can go wrong

What can go wrong

The LLM hallucinates graph structure. If the LLM writes code that queries a nonexistent edge or attribute, the executor fails. The paper mitigates this by wrapping queries in try-catch blocks and letting the code handle missing data gracefully.
Code generation is slower than prompting. Writing, parsing, and executing Python takes time. On huge graphs with strict latency budgets, this overhead matters. Prompting is faster because it just forwards your question to the model and gets an answer back, with no execution step in between.
The LLM writes inefficient code. An LLM might generate nested loops over all neighbors instead of using built-in list operations (that run faster because they are written in compiled code, not Python), causing slowdowns. Smaller or less-capable models struggle here more than larger ones.
Done right: wrap with safety checks. Add timeouts, memory limits, and error handlers. Validate that generated code only uses safe libraries. Provide the LLM with examples of efficient, safe patterns to imitate.
What a runnable demo should prove

What a runnable demo should prove

Build a small test on a synthetic or public graph (e.g. Cora citation network, a small e-commerce graph). Implement the three interaction modes: prompt the LLM, use a tool-calling interface, and feed it a code-generation prompt. Run each on nodes with long text descriptions and measure accuracy on held-out test nodes. Show that code generation handles the long-text case better than prompting because the code can select just the most useful parts of the text and skip the rest, while prompting must cram everything in at once.

accuracy = (number of correct predictions) / (total test nodes); token_usage = (tokens spent by each mode); show accuracy vs. token_usage trade-off

Code generation should hit 75%+ accuracy with a reasonable token budget, while prompting stalls below 50% on long-text nodes. This proves that the LLM's ability to write procedures beats its ability to reason directly on text-compressed graphs.
