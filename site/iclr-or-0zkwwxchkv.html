Click-Based Off-Policy Evaluation for Ranking

To evaluate a new ranking system using old logged data, use user clicks instead of the logging system's choices, even if the old system was completely deterministic.

Paper explainersAll themesReinforcement Learning

When you change a ranking algorithm in production, you want to estimate how much better it performs before you deploy it, because bad changes cost real users and money. The problem: you only have offline data from the old system. If that old system always showed the same ranking regardless of what it saw, all the old methods for estimation fail catastrophically. This paper uses a hidden signal in the data — user click patterns — to fix the problem.

Zero assumption version

Why old methods break under deterministic logging

A ranking system is a machine that takes a context (what you know: a user's interests, time of day, device) and outputs an ordered list. You want to evaluate a new ranking algorithm by replaying it on old logged data. The old data contains triples: the context, which ranked items the old system showed, and whether the user clicked on each item.

The standard trick for this problem is called inverse propensity scoring: when the new algorithm would have shown an item that the old system showed and the user clicked, count that click. When the new algorithm would have shown something the old system never ranked (because the old system was a fixed rule), assign it zero. The assumption: the old system was random enough that it showed diverse items. But when the old system is completely deterministic — it always ranks the same items in the same order regardless of context — it showed nothing but one fixed sequence. The old method sees only zeros and collapses.

A beginner tries: ignore the deterministic logging, try to train a new model directly on clicks from the old deterministic ranking. But this learns the old system's bias, not a better ranking, because the old system only ever ranked certain items, so the training data is skewed toward those items and the model copies that lopsidedness.

The paper's move: Use the clicks themselves as a signal of importance, not the old system's choice.

What it actually does

Observe old ranked list and clicks

Context: X, Old ranking: [Item 1, Item 2, Item 3], Clicks: [yes, yes, no]

Estimate user's click probability for each item

Learn a model from the log: given item X, how often do users click? Item 1 gets clicked 80% of the time, Item 2 gets clicked 75% of the time, Item 3 only 40%

Ask: what is new policy's expected click for each item?

New policy ranks items in order [Item 2, Item 1, Item 3]. Expected clicks: 75%, 80%, 40%

Reweight old clicks by click probability ratio

Old policy showed Item 1 with 80% click rate. New policy shows Item 2 with 75% click rate. Weight is 75 divided by 80, or 0.9375

Sum reweighted rewards to estimate new policy value

Add up all reweighted clicks to get the expected total clicks under new policy

What the paper changes

The single thing the paper changes

Instead of using the logging policy's action probability (how likely the old system was to show that item), the method uses the user's click probability (how likely the user was to click on that item given they saw it). This shift means the importance weights now rest on user behavior, not system behavior.

the object it moves  =  Importance weights
The hidden quantity

Click probability: what users actually respond to

measured quantity  =  User click probability

Click probability is the fraction of times a user clicked on an item when they saw it. It is not the same as whether the old ranking system showed that item. Even if the old system never ranked Item 5, we can infer the user's click probability for Item 5 from other items' clicks and user context. If users clicked on Items 1 and 2 often but Item 3 rarely, we can estimate that Item 3 has low click appeal.

The paper estimates click probability by training a neural network on the logged data: given context and item, predict whether the user will click. This number becomes the new importance weight. Click probability exists and is independent even when the logging policy is fully deterministic, because what users click on does not depend on what the old system chose to show — it depends on what users actually prefer.

Why it works

Why reweighting by clicks fixes deterministic logging

The core problem: old methods divide by the probability that the old system showed an action. When the old system is deterministic and never shows certain actions, that probability is zero, and dividing by zero makes the estimate infinite or meaningless.

The paper's fix: don't divide by the old policy probability. Instead, reweight by the ratio of user click probabilities. If the old system showed Item 1 and the user clicked, we have evidence that Item 1 is clickable. If the new system also ranks Item 1 (or an item with similar appeal), we can estimate the new system's reward without ever asking how likely the old system was to show it.

Why this works: clicks are a measurement of user preference that exists independently of which system made the ranking. Two different deterministic systems could both show Item 1, and users would click at the same rate. But two different systems might rank Item 2 differently: one at the top (high clicks), one at the bottom (fewer clicks). The new method asks: what is the click probability of each item? How would users respond if we ranked these items in a new order? This is answerable even when the logging policy is frozen, because the answer depends on user preference, not on the old system's choices.

Math after the picture

The reweighting equation

First in words:

Estimated value of new policy equals the sum over all items of: clicks received times the ratio of click probability under new policy to click probability under old policy

Then the compact form:

V_hat_new = sum_k C_k * (P_new_k / P_old_k)

Every symbol:

V_hat_newestimated value (expected total clicks) of the new policy
sum_ksum over all ranked item positions k from 1 to the number of items
C_kwhether user clicked on item at position k in the old log (1 if clicked, 0 if not)
P_new_kestimated probability user will click item k when new policy ranks it
P_old_kestimated probability user clicked item k when old policy ranked it
P_new_k divided by P_old_kimportance weight, how much to boost or reduce the old click count
A tiny worked example
Scenario: old log shows Items 1, 2, 3 in that order. User clicked on Items 1 and 2, not Item 3.
Learned: Item 1 gets clicked 80% of the time, Item 2 gets clicked 70% of the time, Item 3 gets clicked 30% of the time.
New policy ranks Items 2, 1, 3 instead. Item 2 still gets clicked 70%, Item 1 still gets clicked 80%, Item 3 still 30%.
For Item 1: clicked in old log, so C_1 is 1. P_old_1 is 0.8. P_new_1 is 0.8 (same item, same appeal). Weight is 0.8 divided by 0.8 equals 1.0. Contribution is 1 times 1.0 equals 1.0.
For Item 2: clicked in old log, so C_2 is 1. P_old_2 is 0.7. P_new_2 is 0.7. Weight is 0.7 divided by 0.7 equals 1.0. Contribution is 1 times 1.0 equals 1.0.
For Item 3: not clicked in old log, so C_3 is 0. Contribution is 0 times any weight equals 0.
Sum: 1.0 plus 1.0 plus 0 equals 2.0 clicks estimated for the new policy.

The key move: each click is reweighted by how clickable that item is under the new ordering, divided by how clickable it was in the old ordering. This pivots the estimate from the system's randomness to the user's behavior.

What can go wrong

What can go wrong

Click probabilities are estimated from data with bias. If position bias exists (users click more on top items), the estimated click probability mixes true item appeal with position effects. The paper assumes a model can separate these, but this remains hard in practice.
New ranking must not rank unseen items. The method works only for items the old system ranked or items similar enough to items that appear in the log. If the new policy ranks an item that never appeared in the old log, its click probability must be guessed from similar items, which adds uncertainty.
Position effects interact with click probability. Users see items in a new order, so position bias changes. The reweighting assumes click probability is independent of position, which is not quite true. If position 1 receives more clicks than position 3 just for being first, the estimate will be off.
Method improves when click model is good. The paper provides bounds showing bias shrinks as the click model improves, because the method's entire logic depends on knowing P(click) accurately; if the click predictor is wrong, the importance weights are wrong, so error in the model directly translates to error in the estimate. Invest in a good click predictor and the method's estimates become dependable.
What a runnable demo should prove

What a runnable demo should prove

Build a simulated ranking environment. Create 5 items with fixed click probabilities (e.g., 0.9, 0.7, 0.5, 0.3, 0.1). Run a deterministic logging policy that always shows the same 3 items (say, items 1, 2, 3) in the same order. Log clicks. Train a click predictor model on the log to estimate each item's click probability. Now propose a new ranking (e.g., items 2, 4, 1). Use CIPS to estimate the new policy's value. Then, run the new policy on the simulator and measure actual clicks. Compare the estimate to ground truth.

Bias of CIPS = | estimated value - true value |

CIPS should estimate the new policy's value within 2-5% of the true value, even when the logging policy was completely deterministic and showed only 3 out of 5 items. Old methods (IPS, ranking-wise IPS) should fail catastrophically, producing estimates off by 50%+ or infinite.
