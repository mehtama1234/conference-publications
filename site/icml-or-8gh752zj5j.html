Large-Scale Notification Dispatch with Bundle Treatments and Multi-Outcome Uplift Optimization

Choose one notification plan per user by estimating the extra effect of each timing-and-style bundle, then solve a constrained assignment problem that respects global send limits and device quotas.

Paper explainersAll themesOther

A large app does not merely decide whether to send a notification. It must decide when to send it, how to present it, how many total notifications the platform can afford to send, and how many each device vendor will tolerate before throttling or user fatigue becomes a problem. The paper treats each timing-and-style choice as a bundle treatment, estimates the incremental change each bundle causes on several outcomes, and then separates prediction from action. BUOPLR first learns small bundle-level uplift values, then solves a large constrained assignment problem with a pruned Lagrangian method so the final policy can raise Daily Active Users without violating platform rules.

Zero assumption version

Why notification dispatch becomes an optimization problem

For one user, sending a notification can increase app opens, but it can also raise dismissals, opt-outs, or wasted impressions. For a platform with more than 100 million daily users, the decision space grows quickly because each user may receive several timing choices and several presentation styles. Picking the best action therefore means comparing many bundles, not just send versus do not send.

A direct rule such as "send the bundle with the highest predicted click rate" fails because the platform has shared limits. There may be a daily notification budget, vendor-specific quota rules, and several business outcomes that matter at once. The right action for one user depends on what the system is already sending to everyone else, because every extra send consumes part of a limited global resource.

The core move. Estimate the extra effect of each bundle on several outcomes, then pick user-level actions with a separate constrained solver because prediction alone cannot enforce shared platform limits.

The algorithm as a flow

What it actually does

Define bundle treatments

Treat each timing-and-style combination as one action, because the effect of timing depends on presentation and vice versa.

Estimate multi-outcome uplift

Predict the incremental change each bundle causes on several outcomes for each user, because the policy must trade one outcome against others.

Prune weak options

Restrict the action set per user to a smaller candidate list, because most bundles are clearly poor and only add solver cost.

Optimize with Lagrangian penalties

Attach prices to the global constraints and score each remaining bundle with those penalties, because this turns a hard coupled problem into many easier user-level choices.

Dispatch the feasible assignment

Send the chosen bundles only after the total assignment satisfies budget and quota rules.

What the paper changes

What the paper changes

The paper changes notification dispatch from a ranking problem into a constrained allocation problem. It also changes the treatment definition: instead of modeling timing and style separately, it models the joint bundle because those choices interact.

the object it moves  =  the notification policy
The hidden quantity

The hidden quantity

measured quantity  =  incremental value per bundle under shared constraints

The deciding quantity is not the predicted probability that a user opens the app after a notification. It is the uplift, meaning the extra change caused by sending one bundle instead of the baseline. This matters because a user who would open the app anyway should not consume scarce notification budget unless the bundle changes behavior enough to justify the cost.

That uplift must also be interpreted together with constraint shadow prices, which are the effective costs of spending one more unit of a limited resource. A bundle with positive uplift can still be a bad final choice if it consumes too much of a scarce vendor quota. BUOPLR estimates bundle-level uplift first, then combines it with these learned costs during assignment.

Why it works

Why the two-stage design works

The first stage exists because the signal is small. A notification usually changes behavior only a little, so the model has to borrow structure across related bundles and related outcomes instead of learning every effect in isolation. Sharing information across timing choices and presentation styles reduces variance in the estimated uplift because a rare bundle can still benefit from patterns seen in similar bundles.

The second stage exists because the assignment is globally coupled. If the system tried to learn the full dispatch policy end to end, it would need to reason over millions of linked choices at once. BUOPLR instead turns each constraint into a penalty term. When those penalty values are set well, each user can be scored independently by "uplift minus resource cost," and the separate choices add up to a feasible global solution because the penalties push the policy away from overusing scarce resources.

Pruning matters because the raw action space is large. Removing obviously weak bundles lowers solver cost and reduces the chance that estimation noise on a poor action changes the final decision. The result is a practical pipeline: estimate subtle causal effects, keep only plausible actions, then solve the constrained allocation with penalties that summarize the system-wide trade-offs.

Math after the picture

The assignment score

First in words:

Choose the bundle whose estimated gain minus the weighted cost of consumed constraints is largest, while allowing a no-send option.

Then the compact form:

score(user, bundle) = uplift_DAU - lambda_budget * budget_use - sum_v mu_v * quota_use_v

Every symbol:

uplift_DAUthe estimated extra Daily Active Users contributed by that bundle for that user
lambda_budgetthe penalty for using one more unit of the global notification budget
budget_usehow much of the global budget this bundle consumes
mu_vthe penalty for using one more unit of vendor-specific quota v
quota_use_vhow much vendor quota v this bundle consumes
A tiny worked example
Suppose a noon banner for one user has estimated DAU uplift 0.08.
It consumes 1 unit of global budget and 1 unit of a tight vendor quota.
If the current budget penalty is 0.01 and the vendor penalty is 0.05, the score is 0.08 - 0.01 - 0.05 = 0.02.
A quiet evening card with uplift 0.06 and only the budget cost would score 0.06 - 0.01 = 0.05.
The second bundle wins even though its raw uplift is smaller, because the first bundle spends scarcer capacity.

The penalties summarize the global trade-off, so each user-level choice reflects system-wide scarcity.

What can go wrong

What can go wrong

Uplift estimates can be too noisy. If the estimated extra effect per bundle is mostly noise, the solver will optimize unreliable scores because the second stage trusts the first stage's ranking.
Pruning can remove the real winner. A bundle that looks weak under a coarse filter may become the best choice after quota costs are counted, so over-aggressive pruning can cap the final policy.
Penalty values can converge to the wrong scarcity level. If the Lagrangian update does not match the true platform bottlenecks, the final assignment may underuse budget or keep violating a quota because the learned costs are miscalibrated.
Done right. The method works best when bundle-level causal estimates are stable, the candidate pruning step keeps all serious options, and the penalty updates are monitored against actual budget and vendor usage.
What a runnable demo should prove

What a runnable demo should prove

Create a synthetic notification simulator with four bundle treatments per user, one no-send option, a global send budget, and two vendor quotas. Generate user-level uplift values for DAU and one negative outcome such as opt-out risk.

Train a small bundle-uplift predictor, prune to the top few bundles per user, and solve the assignment with Lagrangian penalties. Compare against a policy that chooses the largest predicted uplift independently for each user. The demo should show that the independent policy breaks shared limits, while the penalty-based assignment preserves most of the lift because it prices scarce resources directly into the decision.

feasible_lift = total_incremental_DAU_of_feasible_policy / total_incremental_DAU_of_unconstrained_policy

A convincing demo should show high feasible_lift together with zero budget and quota violations.
