Executable Agentic Memory for GUI Agent

Store reusable user-interface routines in an executable knowledge graph, then search that graph with a value-guided planner so the agent stops re-deciding every click from scratch.

Paper explainersAll themesAgents & Tool Use

A GUI agent usually reads each screen, decides one action, moves to the next screen, and repeats. That step-by-step style is fragile on long tasks because the model must keep reinterpreting the interface and can drift after one mistake. This paper replaces that loop with Executable Agentic Memory, or EAM. The system builds a structured graph of interface states and action paths, retrieves a promising path for the current situation, and executes that path with a guided search procedure. The result is faster planning, lower language-model usage, and better long-horizon reliability because the agent can reuse stored routines instead of re-deriving each step from scratch.

Zero assumption version

Why GUI agents break on long tasks

Consider booking a trip in a phone app, changing several account settings, or filling a multi-page form. A standard GUI agent sees one screen at a time and decides one tap or text entry at a time. That means it must repeatedly answer the same hard questions: what screen am I on, which controls matter, and which action is part of the long plan rather than a local distraction.

This repeated free-form planning causes two problems. First, the model wastes effort by rediscovering routines it has already solved before, such as opening settings, searching for a form, or navigating back after a branch. Second, small local errors compound. One wrong interpretation of a button label can derail the whole sequence because the agent has no compact executable memory of how the task should proceed.

The paper's move. Convert previous interaction experience into an executable graph of states and action groups, then plan by retrieval and guided search over that graph instead of fresh free-form generation at every step.

The algorithm as a flow

What it actually does

Collect interaction traces

Explore the interface and record states, actions, and successful paths.

Compress routines

Group repeated action sequences into reusable path fragments.

Build executable memory

Store states and path fragments in a knowledge graph that can be searched later.

Search with value guidance

Use a lightweight value model to steer tree search toward graph paths that are likely to finish the task.

Execute the chosen path

Run the selected action sequence and update the graph with new experience.

What the paper changes

What the paper changes

The paper changes how a GUI agent remembers and plans. Instead of keeping past experience only as raw traces or language-model context, it stores experience as executable graph structure that can be directly searched and replayed.

The hidden quantity

The hidden quantity: path value

measured quantity  =  Expected usefulness of a stored path from the current state

When the agent stands on one screen, many stored graph paths are technically reachable, but only a few are helpful for the present task. The hidden quantity is the value of a path: how likely that path is to move the agent toward successful task completion from the current state.

The system estimates path value with a lightweight learned function during graph search. That estimate lets tree search expand promising branches first. The planner improves because it spends search effort on routes that are more likely to recover the desired routine, rather than exploring the graph uniformly.

Why it works

Why executable memory helps

Long interface tasks contain repeated structure. Opening a menu, choosing a section, confirming a dialog, and returning to a previous screen happen again and again across tasks. If the agent must regenerate those steps each time, it pays repeated planning cost and risks repeated local errors. Executable memory helps because it turns successful routines into reusable objects.

The graph representation matters because it separates navigation knowledge from one-off wording. A state node captures what the screen affords, action groups capture how to move through the interface, and graph search recombines these pieces for the current goal. The value-guided search layer matters because not every remembered path is helpful. The planner improves because it can rank routes that already led to progress from similar screens above less useful routes.

This also reduces language-model usage. The agent no longer has to spend a fresh long reasoning trace on each screen. It can retrieve and execute a compact plan from memory, ask the model only when uncertainty is high, and therefore finish faster because much of the work has been moved into retrieval and search.

Math after the picture

Guided path score

First in words:

During search, each partial path gets a score from two parts: how good the value model says the path is, and how much search evidence the path has already accumulated. Expand the path with the best combined score.

Then the compact form:

search_score(p) = Q(p) + alpha * U(p)

Every symbol:

search_score(p)priority of partial path p during tree search
Q(p)learned estimate of how likely path p is to lead toward task completion
U(p)search bonus for underexplored but promising paths
alphaweight balancing learned value against exploration
A tiny worked example
Path A opens the correct settings page. Q(A)=0.8 and U(A)=0.1.
Path B looks less aligned with the goal but is still plausible. Q(B)=0.5 and U(B)=0.4.
With alpha = 0.5, search_score(A)=0.8 + 0.5*0.1 = 0.85.
search_score(B)=0.5 + 0.5*0.4 = 0.7.
Search expands A first because it combines stronger goal progress with enough exploration.

The paper provides stronger theory around the value estimate, but the core planning idea is that search quality improves because remembered paths are ranked by predicted usefulness.

What can go wrong

What can go wrong

Memory graph is stale. If the app layout changes, stored paths may point to controls that no longer exist, so retrieval becomes misleading because the remembered routine no longer matches the live interface.
State matching is poor. If the current screen is matched to the wrong graph node, the planner may execute an irrelevant routine because the retrieval step started from the wrong memory entry.
Value estimate is biased. If the value model overrates flashy but unhelpful routes, search can spend time on them because the guidance signal is pointing the planner in the wrong direction.
Done right. The method works when the memory graph is built from representative experience, state matching is accurate, and value-guided search keeps balancing likely success with enough exploration to recover from uncertainty.

What a runnable demo should prove

Build a small Android or web-app benchmark with a dozen long tasks such as editing a profile, changing privacy settings, and completing a checkout flow. Record successful traces, compress repeated routines into a graph, and compare two agents: one that replans each step from scratch and one that retrieves graph paths and searches over them. Measure success, answer time, and language-model usage.
