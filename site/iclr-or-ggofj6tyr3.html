Geometry-Aware Policy Imitation

Treat robot demonstrations as curves in space, build a distance field, and let the robot follow it by pulling toward nearby expert paths instead of training a generative model.

Paper explainersAll themesRobotics & Control

When a robot learns from human demonstrations, the usual method is to train a neural network to predict actions. But this paper asks: why not just store each demonstration and let the robot stay close to the nearest one? GPI does exactly that. It measures how far the robot is from each stored expert path and combines nearby ones into a single command by weighting each path based on distance — closer paths get stronger votes. Since there is no neural network, the result runs 20 times faster than the current best method and uses a fraction of the memory.

The demonstration-to-policy bottleneck

Today, imitation learning works like this: collect videos of a human doing a task (pushing a block, grasping an object, moving a robot arm), feed them into a generative model (a diffusion model, which is a neural network trained to turn random noise into realistic action sequences), and use that model to tell the robot what to do. The problem is twofold. First, generative models are expensive — they need hundreds of neural network parameters, hours of training time, and many steps of computation at runtime (sometimes 100 steps of noise removal just to pick one action). Second, when you add a new demonstration, you have to retrain the entire model from scratch.

A beginner might try the simplest approach: just average the actions at each state. This breaks immediately when the demonstrations disagree about what to do at the same state (reaching from different angles, for instance) — averaging them produces nonsense. A better strategy: train a neural network (a program with millions of adjustable dials) to learn a policy function that predicts actions, because the network can learn which features of the state should trigger which demo's behavior. But training is slow, and the network averages and blurs together the distinct strategies shown in the demos, losing useful diversity. So this approach trades flexibility for cost.

The paper's one-sentence core. Instead of training a model, treat each demonstration as a geometric curve in space, measure the robot's distance to each curve at every moment, and pick actions by pulling toward the nearest ones.

The algorithm as a flow

What it actually does

1. Store demonstrations as curves

Each human demo is a sequence of states (robot positions) and actions (motor commands).

2. Compute a distance field

For any query state the robot is in, measure how far it is from each demonstration curve.

3. Retrieve nearby trajectories

Find the two or three closest demonstration curves to the robot's current state.

4. Blend actions by distance

Closer curves get higher weight; mix their actions to produce the robot command.

5. Execute and repeat

Send the blended action to the robot; at the next state, repeat from step 2.

What the paper changes

What the paper changes

Instead of training a neural network to map observations to actions, GPI stores the demonstrations directly and composes them by measuring geometric distance. The single object being manipulated is: the representation of expert knowledge shifts from a trained model to a distance field computed over stored curves.

the object it moves  =  Policy representation
The hidden quantity

The hidden quantity: proximity error

measured quantity  =  Proximity error to nearest demonstration

Proximity error is the shortest distance from the robot's current state to any of the stored demonstration curves. It is a single number measuring how far off-track the robot has drifted. When proximity error is small, the robot is close to something a human already showed it; when it is large, the robot is in uncharted territory.

The paper estimates proximity error by computing distances between the robot's state and each demonstration using either Euclidean distance (for low-dimensional robot joint positions) or latent-space distance (for high-dimensional images, using a pretrained encoder to compress images into lists of numbers). The algorithm then picks the minimum distance and weights nearby demonstrations by how close they are — closer curves have higher weight when blending actions.

Why it works

Why it works: geometric composition

The core idea: demonstrations are not bags of disconnected samples to compress into a model; they are continuous curves in the space of robot configurations. The robot's job is to stay near one of these curves. At each moment, the robot measures its distance to all curves, weights the nearby ones by closeness, and blends their actions.

Why does this work? Because when states overlap — when the robot could follow several different demos — the paper's distance weighting automatically handles it: if two curves pass through nearly the same state, they both contribute, and their actions are averaged. The robot never commits to a single path; it smoothly borrows from whichever demonstrations are nearby. This preserves the diversity shown in the demos naturally: the robot can choose the left-approach or right-approach grasp depending on which curve it drifts closest to.

Why is it faster and smaller? Because there is no neural network to run. The algorithm only computes distances (just arithmetic) and blends numbers (arithmetic). There are no large numerical operations (multiplying arrays of thousands of numbers) on every step, which is what slows down neural networks. Adding a new demonstration does not require retraining; just store it and add one more distance computation.

Math after the picture

The core equation

First in words:

The robot's next action is a weighted average of actions from nearby demonstrations. Each demonstration contributes based on its distance, using an exponential weight. If demo i is at distance d_i from the robot's state, its weight is proportional to exp(negative beta times d_i), where beta controls how strongly nearby demos dominate.

Then the compact form:

u(x_o) = sum_i w_i(x_o) * u_i(x_o), where w_i = exp(-beta * d(x_o | Gamma^(i))) / sum_j exp(-beta * d(x_o | Gamma^(j)))

Every symbol:

u(x_o)the action the robot picks at state x_o
w_i(x_o)the weight for demonstration i, given state x_o
u_i(x_o)the action stored in demo i at the closest point to state x_o on that curve
d(x_o | Gamma^(i))the shortest distance from state x_o to demo curve i
betaa temperature that controls how much to favor nearby demos (high beta = only nearest demo, low beta = more blending)
sum_i w_iweights sum to 1, so the action is always a mixture
A tiny worked example
Suppose robot state = (1.5, 2.1). Demo 1 is at distance 0.3, demo 2 is at distance 1.2.
Using beta = 2: w_1 = exp(-2 * 0.3) = exp(-0.6) ≈ 0.549; w_2 = exp(-2 * 1.2) = exp(-2.4) ≈ 0.091.
Normalize: w_1 / (0.549 + 0.091) ≈ 0.86; w_2 / (0.549 + 0.091) ≈ 0.14.
Demo 1 action = turn-left; demo 2 action = go-forward. Blended: 0.86 * turn-left + 0.14 * go-forward ≈ mostly turn-left, tiny bit forward.
Close demos dominate; far demos contribute almost nothing. Same movement, different distances = very different weights.

The weights put each demonstration's contribution in proportion to how close the robot is; the exponential makes nearby paths dominate, while far ones vanish.

What can go wrong

What can go wrong

Sparse demonstrations. If the stored demonstrations do not cover the state space densely, the robot will often find itself far from any curve. When proximity error is large, the nearest demo may be so far away that its action is nearly useless — you are blending copies of something you never actually showed the robot, which is equivalent to averaging random guesses. The method works only when demos are plentiful enough to keep the robot near at least one curve most of the time.
Wrong distance metric. Proximity error depends on how distance is measured. If the encoder (the network that compresses images to numbers) is untrained, it might place all images equally far apart, and proximity error becomes meaningless. The paper studies several encoders; picking the wrong one breaks the method.
Contradictory demos at the same state. If two demonstrations pass through the same state but take different actions (for example, grasping from different angles both pass through the same hand position but make different moves), the blending produces an action in between, which may not be what either demo intended. Multimodality is preserved only if the demos are spatially separated.
Done right. Collect diverse, densely-spaced demonstrations. Use a good encoder or low-dimensional states. The method will compose them smoothly and run fast.
What a runnable demo should prove

What a runnable demo should prove

Build a simple 2D reaching task: a robot arm with two joints, a fixed target, and three human demonstrations of how to reach it from different angles. Store each demo as a sequence of joint angles and the actions (which direction to turn each joint). At test time, start the arm at a random state and ask GPI to reach the target. Measure proximity error (distance from the arm's state to the nearest demo at each step) and track whether the arm reaches the target within 50 steps.

success_rate = (number of reaches within 50 steps) / (total test trials); proximity_error_mean = average distance from state to nearest demo across all steps.

The demo must show that when the arm stays close to a stored demo, it succeeds at reaching the target, because the nearby demo provides a path that leads there. It should also show that adding a fourth demo shrinks proximity error in hard-to-reach corners, making the robot able to succeed from those tougher starting positions.
