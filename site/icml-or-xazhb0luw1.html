Doubly Outlier-Robust Online Infinite Hidden Markov Model

Track changing regimes in a data stream while resisting both bad observations and fake regime creation caused by those observations.

Paper explainersAll themesOther

An online infinite hidden Markov model is a streaming method for regime detection. It keeps a reusable catalog of regimes, updates the current regime as new data arrive, and can add a new regime when the old catalog no longer explains the stream. That is useful because many real streams switch between recurring patterns instead of drifting only once. The weakness is that one bad measurement can damage the update in two places at once. It can pull the current regime's parameters, meaning the hidden settings that define that regime, toward nonsense, and it can also make the method believe a new regime has appeared when the data only contain an outlier. BR-iHMM fixes both failure paths together. It softens how strongly one batch of observations can move a regime update, and it decides state changes in batches because a real regime switch should persist across several points while a bad spike often does not.

Zero assumption version

Online regime models break when rare points are treated as ordinary evidence

A hidden Markov model explains a sequence by saying that each time step belongs to one latent state, meaning one unobserved regime, and each regime has its own data pattern. The infinite version does not fix the number of regimes in advance, so it can reuse old regimes and also open a new one when needed.

That flexibility is exactly where outliers cause trouble. A single extreme point can distort the update for the current regime because the model assumes the point is honest evidence. The same point can also trigger a new regime because the model asks whether the current catalog explains the observation poorly. If the answer is yes for one corrupted point, the model may create a state that never should have existed.

The central move. Make observation updates less sensitive to single bad points, and make new-state decisions depend on short batches, because true regime changes usually persist longer than measurement glitches.

The algorithm as a flow

What it actually does

Keep an expandable regime library

Maintain a set of recurring regimes and allow a new one only when recent data keep disagreeing with all existing choices, because repeated disagreement is evidence of a real new pattern.

Predict a short future batch

For each particle, forecast a small block of upcoming observations under its current state assumptions because batch evidence separates persistent change from isolated noise.

Downweight extreme observation mismatch

Use a generalized Bayes update that caps how strongly one observation can move the posterior, meaning the updated belief over states and state settings, because one corrupted point should not rewrite the state description.

Sample state paths across the batch

Infer which states explain the whole block, including whether a new state is warranted, because the model now judges change on repeated evidence.

Update state counts and regime summaries

Refresh transition counts and regime statistics after the batch so reusable regimes stay available for future returns.

What the paper changes

What the paper changes

The paper changes the update rule at two different points: how observations modify a regime and how recent evidence justifies opening a new regime. The first guards the observation space. The second guards the state space.

the object it moves  =  the evidence path by which one surprising point changes beliefs
The hidden quantity

Contamination pressure

measured quantity  =  contamination pressure (how much one recent block is trying to drag the model away from its current explanation)

The method is trying to estimate whether a recent surprise is persistent structure or temporary contamination. That quantity is hidden because the stream does not label a point as outlier or regime change. The model must infer it from how the surprise behaves across neighboring times.

A single point that looks impossible but is surrounded by ordinary points should create low pressure for a new regime because the mismatch does not persist. Several consecutive points that fit a new pattern should create high pressure because the evidence keeps pointing the same way.

Why it works

Why the double protection works

Observation protection matters because online inference compounds mistakes. If one outlier pulls a regime summary far enough, later ordinary points are compared against a damaged state description, so the error keeps spreading. A bounded-influence update stops that chain because the contribution of one extreme point saturates instead of growing without limit.

State protection matters because an iHMM can always explain surprise by inventing another regime. That flexibility is useful only when surprise persists. BR-iHMM therefore makes the state decision from a short batch because several consecutive points contain the persistence signal that one point does not. This creates an adaptation lag, but that lag is deliberate because instant change detection and outlier resistance pull in opposite directions.

The two protections need each other. Observation resistance alone would still leave the model free to create spurious states. Batched state inference alone would still let one extreme point corrupt the parameter summary of an existing state. The method improves one-step forecasting because both routes for contamination are blocked at the same time.

Math after the picture

Bounded influence over a batch

First in words:

score each particle on a short batch using a bounded-loss weight, then update states and regime summaries from those batch scores

Then the compact form:

particle_weight_tplusB = p(y_(t+1:t+B) | current_state_summaries, bounded_batch_weights)

Every symbol:

particle_weight_tplusBthe importance weight of one particle after seeing the next batch
y_(t+1:t+B)the short block of observations used for the batched update
current_state_summariesthe regime statistics and transition counts carried by the particle
bounded_batch_weightsper-observation weights that stop one extreme mismatch from dominating the batch score
A tiny worked example
Suppose a batch has three observations.
Two are close to the current regime and one is extreme.
A standard update may let the extreme point dominate the batch likelihood.
BR-iHMM clips that point's influence, so the two ordinary observations still matter.
If the next batch also looks different, the repeated mismatch then supports a genuine state change.

The exact update uses particle learning and a bounded-loss rule, but the central idea is simple: cap per-point influence and defer state creation to repeated evidence.

What can go wrong

What can go wrong

Batch size is too large. If the batch is long, the model reacts slowly to a genuine regime switch because it waits too long for confirming evidence.
Influence cap is too aggressive. If the observation update is flattened too much, the model stops learning normal variation because even honest surprises are treated as nearly irrelevant.
True shifts look isolated. Some applications contain very abrupt but short changes. In that case the persistence test can reject a real event because the event does not last long enough to fill the batch.
Done right. The method works well when outliers are short-lived and regime changes persist for at least a few points, because that is the setting where batch persistence is informative.
What a runnable demo should prove

What a runnable demo should prove

Build a synthetic stream with three recurring linear regimes, then inject occasional large spikes and one genuine switch to a new regime. Compare a standard online iHMM against a batched bounded-influence version. Show the active state label over time, the number of created states, and one-step prediction error.

The demo should make two facts visible. First, the bounded batch update ignores isolated spikes because they do not persist. Second, the same method still changes state after a real switch because the mismatch keeps repeating across the batch.
