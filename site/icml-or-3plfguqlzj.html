GraphFlow: Workflow Management for LLM Agents

Instead of using rigid templates to guide an AI agent, build a graph of all possible steps once, then have the system reuse pieces across different tasks and recycle computation.

Paper explainersAll themesAgents & Tool Use

When an AI assistant tackles a complex task like booking a flight, it needs a plan: find flights, check prices, read reviews, pick one, then book it. Today, people write this plan by hand for each task, which is slow and inflexible. GraphFlow builds the plan dynamically by connecting reusable pieces from a master graph, then reuses cached results so the agent does not repeat work.

Zero assumption version

Hand-built plans are rigid and wasteful

Today, when we want an AI agent to solve a task, we manually write out a sequence of steps: if the task is booking a hotel, we specify: search hotels, filter by price, check reviews, compare photos, then reserve. A different task (booking a flight) needs a completely different step sequence written by hand.

This breaks in two ways. First, if two tasks share some steps—both need to search and filter—we write the filter step twice. Second, when the agent runs, it often repeats work: if two different branches both need to fetch a user's calendar, the system computes that twice, wasting memory and time.

A beginner's fix would be to write even more step templates and try to match them by keywords. But keywords are too shallow: a search for flights and a search for hotels are conceptually similar, but a keyword-based system treats them as different and cannot share the template.

The method in one sentence. Build one master graph containing all possible atomic operations, then for each new task, assemble a custom workflow by reusing pieces from the graph and recycling cached intermediate results.

The algorithm as a flow

What it actually does

Build the master graph once

Create nodes for every atomic operation (search, filter, compare, book, etc.); link them by what outputs connect to what inputs.

For each new task, read its requirements

Understand what the task is asking (book a flight vs. reserve a hotel) and what constraints matter (budget, date, speed).

Assemble a workflow dynamically

Treat the master graph as a palette; pick the nodes needed for this task and connect them in the right order.

Trace execution and save intermediate results

As the agent runs each node, store the output (e.g., search results) in a cache so if another part of the workflow needs the same thing, it reuses the saved answer.

Return the answer and the savings

The agent finishes the task with the same quality as before, but memory use drops because redundant computation never ran.

What the paper changes

What the paper changes

The paper changes how workflows are stored and reused. Instead of keeping separate step-sequence templates, it builds a single shared graph and dynamically constructs task-specific workflows from that graph, then recycles cached results across execution branches.

the object it moves  =  workflow templates
The hidden quantity

The hidden quantity: redundant computation

measured quantity  =  redundant computation

The paper measures how much computation the agent repeats across different branches of the same task or across related tasks. For example, if both a flight search and a hotel search call the same filtering function, that is redundant computation: the function ran twice even though its output was identical both times.

GraphFlow estimates this by analyzing the graph structure before execution starts. It checks which operations appear in multiple paths and predicts which results will be used twice. Then during execution, when a node's result is cached, the system checks whether later nodes can reuse it, avoiding the redundant call.

Plain reading. Redundant computation is work the agent does twice—running a function that produces the same result both times. Caching saves this by storing the first result and reusing it.
Paper reading. The paper calls this the KV cache utilization rate—the fraction of the agent's key-value cache that gets reused across multiple operations in the workflow.
Why it works

Why it works: reuse and recycling

The method works because it splits the problem into two levels. At the top level, workflows are patterns—sequences of operations that solve a category of tasks. At the bottom level, operations are atomic: one search, one filter, one comparison, each independently cacheable. The graph links them by data dependency: operation B reads the output of operation A.

When a new task arrives, the system reads the graph and asks: which nodes do we need for this task? It assembles a workflow by selecting those nodes and tracing the paths between them. This is fast because the graph structure is precomputed. Then, as the agent executes each node, the system saves its result so that if another part of the workflow asks for the same output later, the cached answer is available instantly instead of rerunning the expensive operation. When a later node needs the same input, it checks the cache first. If found, it skips recomputation.

What makes this work is that the cache is aware of the graph structure. In the old approach, each task ran its own template in isolation, so caches did not cross boundaries. Now, because all workflows share the same node pool, a cache hit in one branch can serve another. This is why memory drops: fewer redundant node runs means smaller caches needed.

Math after the picture

Memory savings formula

First in words:

memory_saved = sum over all redundant operations of (computation_cost times number_of_repetitions minus one)

Then the compact form:

memory_saved = sum_i (cost_i * (reps_i - 1))

Every symbol:

sum_iadd up over all operations i
cost_ihow much memory operation i uses (in megabytes)
reps_ihow many times operation i would run without caching
reps_i - 1the repetitions we eliminate by caching (one run stays, the rest are skipped)
A tiny worked example
Operation 1 (search): costs 50 MB, runs 3 times (flight search, hotel search, review-based search). Redundant runs saved: 50 * (3 - 1) = 100 MB.
Operation 2 (filter): costs 20 MB, runs 2 times. Redundant runs saved: 20 * (2 - 1) = 20 MB.
Operation 3 (compare): costs 10 MB, runs 1 time. Redundant runs saved: 10 * (1 - 1) = 0 MB.
Total memory saved: 100 + 20 + 0 = 120 MB. Without caching, the workflow would consume 50*3 + 20*2 + 10*1 = 200 MB. With caching, it uses 80 MB (200 - 120 = 80), a 4× reduction.

The savings grow with how much work is repeated, because each time a node is reused, you eliminate its entire memory footprint; a graph with highly reusable operations saves much more than one where every operation is unique.

What can go wrong

What can go wrong

Overly complex graphs that take time to traverse. If the master graph has too many nodes or the dependency logic is tangled, assembling a workflow becomes slow. The system spends more time finding the right path through the graph than it saves by caching.
Stale cached results when data changes. If the agent is running a long task and the input data changes midway, a cached result from earlier may be outdated. The system must invalidate the cache when it detects a change, but that detection itself can be expensive.
Cache miss for similar but not identical queries. If two operations are semantically similar but not exact (e.g., searching flights for tomorrow vs. searching flights for next week), the cache treats them as different and stores both results, wasting space.
Done right: precompute the graph, set cache policies, and validate dependencies. The system maintains a clean graph where every node's input and output types match; it checks whether cached results are still valid before reusing them; and it prunes the graph to remove unused nodes before execution.
What a runnable demo should prove

What a runnable demo should prove

Build a simple workflow engine that represents five atomic operations (search, filter, compare, summarize, reserve) as graph nodes. Create two related tasks: one that runs search, then filter, then compare, then reserve; and another that runs search, then filter, then summarize, then reserve. Measure how much computation is shared (both tasks use search and filter), and verify that when you run both tasks with caching enabled, the second task reuses the cached search and filter results from the first. Without caching, both tasks would compute search and filter independently.

cache_reuse_ratio = (shared_operations_found / total_operations_across_tasks) × 100

The demo proves that the graph structure allows the system to automatically identify and reuse common operations (because both tasks' workflows are built from the same node pool, shared nodes are recognized by name and data type), reducing total computation without changing either task's output.
