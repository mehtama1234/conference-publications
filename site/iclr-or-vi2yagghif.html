DeepRAG: Thinking to Retrieve Step by Step

When thinking step by step, ask for external knowledge only when you truly need it, not blindly at every turn.

Paper explainersAll themesLLMs & Foundation Models

Fact-checking large language models (large language models are AI systems that predict the next word in a sequence) is hard because they hallucinate: they invent facts instead of admitting what they do not know. Retrieval-augmented generation is a fix: feed the model real documents before it answers. But documents are noisy and costly, so fetching blindly at each step wastes time and introduces garbage. DeepRAG models the entire reasoning process as a sequence of decisions: at each thinking step, should this model ask for outside knowledge, or answer from memory alone?

Zero assumption version

Blindly fetching makes reasoning worse, not better

A naive fix is to fetch documents for every subquestion — but documents are real-world noise. Most retrieved text is irrelevant or contradicts itself. If you force-feed garbage into the model's reasoning, it gets confused and gives worse answers, not better, because the model tries to learn from all the text you show it, and noise teaches it to say wrong things. A smarter fix would know when to retrieve and when not to: retrieve facts that the model genuinely lacks, skip retrieval when the model's own memory is good enough. But training a model to make that decision requires data about the *right* decision for each subquestion — and you do not have it.

The move. Teach the model to recognize its own knowledge limits, then train it to decide whether to fetch documents or reason alone, one subquestion at a time.

The algorithm as a flow

What it actually does

Break down the question

The LLM splits the main question into subquestions (e.g. What are the three films? What is each runtime?).

Decide for each subquestion

At each step, the LLM outputs a binary choice: retrieve (fetch documents) or parametric (use what you learned in training).

Fetch only if needed

If retrieve is chosen, search for and read relevant documents; otherwise skip fetching and answer from memory.

Train the decision rule

Show the model which choice was right for each subquestion (via preference pairs: retrieve was better or parametric was better), because this tells the model which choice led to the correct final answer, so it learns to repeat that pattern.

Measure efficiency and correctness

Count how many retrievals the model performed, and measure how many answers were right.

What the paper changes

What the paper changes: the atomic decision

The paper modifies one thing: at each reasoning step, the model now outputs a separate binary choice (retrieve or parametric knowledge) for that subquestion alone, rather than either fetching for everything or nothing at all.

the object it moves  =  per-step retrieval choice
The hidden quantity

The hidden quantity: knowledge boundary

measured quantity  =  knowledge boundary

The knowledge boundary is the edge between what the LLM already knows (from its training data) and what it does not know (facts that are newer, rarer, or too specific). The model cannot see this boundary directly. But the paper trains it to *feel* the boundary: when the model is uncertain or when a subquestion is about specific facts (runtimes, dates, statistics), it should ask for documents. When the subquestion is about reasoning from what it learned (summarizing, adding numbers, explaining concepts), it should not.

The paper learns this boundary by showing preference pairs: for each subquestion, the model learns that choosing retrieve was better (or worse) than choosing parametric knowledge, based on whether the final answer was correct.

Why it works

Why it works: learning to refuse unnecessary fetches

The core insight is that the model can be taught to recognize when it does not know something and when it can answer alone. Normally, the model is trained on one big task (answer the main question). Now, it is trained on tiny preference tasks: for each subquestion, was retrieve or parametric better? This micro-level feedback teaches the model where it is confident and where it is not, because by seeing which choice (retrieve or skip) led to the correct answer repeatedly, the model learns that retrieval helps on some kinds of questions and hurts on others.

The second key is that the paper uses binary tree search to construct the optimal paths (the right choice for each subquestion, given the main question is answered correctly). These optimal paths become the preference labels. The model learns that if it chooses retrieve for runtimes and parametric for summarizing, it ends up correct. If it does the opposite, it fails. Over time, the model learns the boundary: when external knowledge is worth fetching, and when it is just noise.

Math after the picture

The equation: preference loss

First in words:

For each subquestion, if the optimal path chose retrieve, penalize the model if it chose parametric; if optimal chose parametric, penalize if it chose retrieve. Sum these penalties, weighted by how wrong the final answer was.

Then the compact form:

loss_subquery = sum_t [ (choice_t != optimal_t) * (1 + prediction_error) ]

Every symbol:

loss_subquerypenalty for getting the retrieval choice wrong on one subquestion
choice_twhat the model chose at step t (retrieve=1 or parametric=0)
optimal_twhat the optimal path chose at step t
prediction_errorhow far the final answer was from correct (larger error = worse)
tthe step number (subquestion index)
A tiny worked example
Subquestion: Runtime of Fellowship? Optimal choice: retrieve (correct). Model chose: parametric (wrong).
Prediction error (on the full question): final answer off by 50 minutes.
Penalty = 1 * (1 + 50) = 51.
Subquestion: Sum the runtimes? Optimal choice: parametric (correct). Model chose: parametric (right).
Penalty = 0 (choice was correct, no penalty).
Total loss = 51 + 0 = 51. The model learns that fetching for summary tasks is wasting effort; it avoids retrieval on similar queries next time.

The loss pushes the model away from wasteful retrieval choices and toward the minimal-fetch path that still gets the answer right.

What can go wrong

What can go wrong

Preference data is skewed. If the training data shows that retrieve was right for some subquestions but actually wrong (noisy labels), the model learns the wrong boundary. It will skip retrieval when it should fetch, or vice versa.
Model overfits to the style of training questions. If most training questions are about runtimes (always retrieve), the model learns to always retrieve for any factual-looking question, even on new topics where parametric knowledge is fine.
Retrieved documents are irrelevant or contradict each other. Even if the model correctly decides to retrieve, if the fetched documents are garbage or wrong, the model hallucinates from them anyway.
Done right. The preference data is high-quality (generated by binary tree search, not hand-labeled), and the retrieval system returns real, accurate documents for the chosen subquestions.
What a runnable demo should prove

What a runnable demo should prove

Build a small demo with two simple tasks. Task A: Answer questions about famous movie runtimes (facts that should be retrieved). Task B: Sum the runtimes or explain why they vary (reasoning that should use parametric knowledge). Show the model running on both tasks, and measure: (1) How many times did it choose to retrieve? (2) Was the final answer correct? (3) How long did it take? Compare to a baseline that retrieves at every step. The demo should make it impossible to miss that the model learned the difference between fact questions and reasoning questions.

accuracy = (correct_answers / total_questions); efficiency = (retrievals_deeprag / retrievals_naive); time_saved = (time_naive - time_deeprag) / time_naive

The demo must show that fewer retrievals and faster time do NOT come at the cost of accuracy — DeepRAG gets the same or better answers with half the fetches, because it learned to retrieve only when needed and to answer from parametric knowledge when the model is confident, avoiding the confusion that blind fetching causes.
