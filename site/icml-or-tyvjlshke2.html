ModernVBERT: Towards Smaller Visual Document Retrievers

ModernVBERT shows that visual document retrieval works better with a compact bidirectional encoder trained for retrieval from the start, not with a large generator repurposed afterward.

Paper explainersAll themesMultimodal

Visual document retrieval turns an image of a page into a search representation and matches it to a query. Many recent systems reuse very large generative vision-language models for this job. ModernVBERT argues that this reuse is the wrong starting point. Retrieval needs dense page representations, strong contrastive learning, and efficient matching where one page is stored as several vectors, which are lists of numbers, rather than one summary. It does not mainly need generation trained to predict the next token, which is the next text unit in sequence. The paper rebuilds the stack around those needs and ends up with a much smaller model that retrieves better because more of its capacity is spent on ranking and page matching, and it can run on CPU hardware because the encoder stays compact.

Zero assumption version

Generative vision-language models are not naturally retrieval models

A page retriever needs to map a page image and a text query into comparable representations so that relevant pages end up near the query and irrelevant pages end up far away. A generative model is trained for a different job: predict the next token, which is the next text unit in a sequence. That objective spends capacity on fluent generation, long-range decoding behavior, and language modeling habits that do not directly improve retrieval, because ranking pages does not require the model to practice producing long text continuations.

The mismatch becomes sharper in multi-vector retrieval, where one document is represented by several vectors, which are lists of numbers, instead of only one summary vector. Multi-vector matching helps because a page often contains several independent pieces of evidence: title, table, figure, caption, and footnote. A generative design with causal masking and decoding-oriented training does not organize those pieces well for retrieval. ModernVBERT starts from the opposite assumption: build a bidirectional encoder whose entire training path serves matching.

Core claim. Document retrieval gets stronger when the architecture and training objective are chosen for matching page content, because direct ranking pressure preserves page evidence that generation-oriented training never has to separate.

The algorithm as a flow

What it actually does

Choose an encoder-only architecture

Use bidirectional attention, which means each patch or text unit can read context on both sides, because retrieval needs page understanding rather than left-to-right generation.

Study masking and training phases

Run controlled ablations on masking rules, multimodal pretraining mixtures, and contrastive objectives to isolate what improves retrieval, because each change is tested while the others stay fixed.

Train page and query representations

Map document images and queries into retrieval representations optimized directly for matching.

Support single-vector and multi-vector search

Emit either one page summary vector or several vectors so different page regions can independently match the query.

Deploy efficiently

Because the encoder is compact, indexing and CPU search-time execution stay practical.

What the paper changes

What the paper changes

The paper changes the design starting point. Instead of asking how to adapt a generator into a retriever, it asks what a retriever for page images actually needs and then trains that architecture directly.

the object it moves  =  retrieval-first visual document encoder
The hidden quantity

The hidden quantity: retrieval granularity

measured quantity  =  retrieval granularity

Retrieval granularity is the amount of page detail preserved in the representation. A single summary vector is compact, but it can mix several unrelated page regions into one number pattern. A multi-vector representation keeps more of those regions separate, so a query about a table row does not have to compete with the page title or surrounding paragraph inside one summary.

This quantity matters because many document queries are narrow. If the representation collapses fine details too early, the query cannot latch onto the right region. ModernVBERT studies masking and contrastive training through this lens: the model should preserve enough distinct evidence so that relevant page parts remain retrievable after encoding.

Why it works

Why the smaller encoder wins

The model wins because every major design choice points at the retrieval objective. Bidirectional encoding helps page understanding because a word or visual patch can use context from the whole page before its representation is finalized. That is useful for retrieval, because matching a query often depends on neighboring structure such as which column a number belongs to or which caption belongs to a figure.

Contrastive learning is the right training signal here because retrieval is a ranking problem. The model should assign higher similarity to matched query-page pairs and lower similarity to mismatched pairs. Training directly on that separation is more efficient than first teaching the model to generate text and only later asking it to rank pages. The controlled ablations matter because masking and data mixtures decide how much local page structure survives into the retrieval representation.

Multi-vector retrieval benefits most from the retrieval-first design because several page vectors can specialize to different evidence regions. A query about an invoice total can align to the numeric block while a query about company name can align to the header. That works only if the encoder preserves those regions as distinct representations. ModernVBERT does, whereas a generator adapted after the fact tends to carry extra modeling baggage that is useful for generation but not for ranking.

Math after the picture

Contrastive retrieval objective

First in words:

The model learns by raising the similarity of matched query-page pairs and lowering the similarity of mismatched pairs.

Then the compact form:

retrieval_loss = negative log of exp(similarity(query, positive_page)) divided by the sum of exp(similarity(query, candidate_page_j)) over all candidates j

Every symbol:

similarity(query, positive_page)match score for the correct query-page pair
candidate_page_jthe j-th page considered in the contrastive batch
exp(...)a way to turn scores into positive weights before normalization
retrieval_lossthe ranking error the encoder tries to minimize
A tiny worked example
Suppose a query about an invoice total scores 8 with the correct page, 5 with a similar invoice, and 1 with an unrelated page.
The loss is small because the correct page already has the largest score, so normalization gives most of the weight to the positive pair.
Now suppose a generator-based baseline scores 6 with the correct page and 6 with the similar but wrong invoice.
The loss is larger because the model has not separated the hard negative from the true match, so training pushes the encoder to preserve the missing detail.

The exact formula matters less than the training pressure it creates: correct matches must outrank confusing near-matches.

What can go wrong

What can go wrong

Weak negative sampling. If most negatives are easy, the encoder never learns the fine distinctions that matter in real search. It may separate unrelated pages well but still confuse near-duplicate layouts.
Representation collapse in the multi-vector setting. If all page vectors end up carrying the same information, the model pays the cost of multi-vector retrieval without gaining extra granularity. Training must encourage specialization across vectors.
Domain shift across document types. A model trained mostly on reports and forms may underperform on handwritten notes or scientific pages with unusual figure layouts, because the page structures that drive matching are different.
Done right. The design is strongest when hard negatives are abundant, page layouts in pretraining resemble deployment data, and the retrieval evaluation includes narrow queries that force fine-grained matching.
What a runnable demo should prove

What a runnable demo should prove

Build a small page-image retrieval benchmark with queries that target different page regions such as title, table value, caption text, and footer code. Train one compact bidirectional encoder with contrastive retrieval loss and compare it to a similarly sized model first trained for generation and then fine-tuned for retrieval. Measure single-vector retrieval, multi-vector retrieval, latency on CPU, and performance on hard negatives that share layout but differ in one local field.

hard_negative_gap = retrieval score on true page minus retrieval score on the most similar wrong page

The demo should show that the retrieval-first encoder wins especially on narrow queries and hard negatives, because those cases depend on preserving local page evidence rather than broad document themes.
