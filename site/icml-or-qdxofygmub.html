RoboOmni: Treating Actions as Discrete Tokens

Treat robot actions as discrete tokens like words, predicting them one at a time from visual input instead of as continuous numbers.

Paper explainersAll themesRobotics & Control

Robot control has split into two camps: one treats actions as continuous numbers (like turning a dial), the other predicts discrete action tokens (like choosing from a menu). The continuous path was thought to be superior for manipulation, but this paper shows that discrete action tokens, predicted one after another, can match and beat continuous methods on real robot tasks. Actions can be chopped into chunks and predicted one chunk at a time, just as words in a sentence are predicted sequentially.

Zero assumption version

Two broken paths for robot control

A robot sees an image and must predict what to do: move the arm left, open the gripper, push forward. The split is this: do you predict actions as continuous numbers (a smooth dial: 0.0 to 1.0 for each joint angle), or as discrete steps chosen from a menu (like picking words from a vocabulary)?

Continuous designs win on most benchmarks, but they have a hidden cost: the robot trains on collected human demonstrations (or simulations), then must run in the real world. The human demos record each action as a smooth number, but in deployment the robot generates its own actions one step at a time, learning as it goes. This gap—between training and deployment—is called distribution shift. Discrete methods predict step-by-step like language models (one token at a time), which matches how they run at test time, so the shift should vanish. But discrete methods have traditionally been weak: the vocabulary of action tokens is small, and chopping a complex motion into chunks loses temporal information. So practitioners pick continuous methods despite the mismatch.

The setup. Predict robot actions step-by-step from images, using a discrete vocabulary where each action is broken into chunks, each chunk assigned a token index from a fixed list.

The algorithm as a flow

What it actually does

See the image

Robot camera captures the current scene.

Encode it

Vision-language model turns the image into a fixed list of numbers (embeddings).

Tokenize the action

Next step: chop the action into chunks (e.g., gripper position, arm angle, wrist rotation), encode each into a token.

Predict the token

Language model predicts the next action token from the image embedding and all previous action tokens.

Repeat

Loop: each predicted token becomes input to the next prediction, one chunk at a time.

What the paper changes

What the paper changes

The paper redefines how actions enter the model. Instead of encoding actions as continuous numbers, it builds a tokenizer (a conversion tool) that maps action sequences into discrete tokens: each action chunk gets a token index from a fixed vocabulary, like words in a dictionary. This tokenizer is not bolted on after training; it is part of the model's core architecture. During both training and test time, the model sees actions as tokens to predict (tokens are indices from 0 to vocabulary-size), not as learned numbers (the numbers that the model adjusts during training to fit the data, often called weights) to compute.

The hidden quantity

The hidden quantity: distribution shift

measured quantity  =  distribution shift

Distribution shift is the gap between training and deployment. During training, the model sees human-recorded actions (demonstrations): smooth, continuous numbers chosen by a human operator. At test time, the robot must predict its own actions in deployment, in a loop: predict one step, execute it, observe the new image, predict the next step. The new actions come from the model itself, not from the demonstration set, so they follow a different distribution (pattern).

This mismatch is invisible but deadly: the model trained on human demos suddenly faces its own self-generated actions at test time, which it has never seen before, causing mistakes to compound. Continuous methods suffer this shift silently. Discrete methods (next-token prediction) match the training and test-time process: both use one-token-at-a-time prediction, so the distribution does not shift between the two phases.

Why it works

Why it works: matching training and test

A language model works by predicting the next word from prior words and context. Training looks like: given some prior words, what is the next word in the dataset? Testing looks the same: given context, predict the next word, use it, predict the next word again. The distribution does not shift because the process is identical in both phases.

RoboOmni applies this principle to robot actions. Instead of predicting actions as continuous numbers, it predicts action tokens (discrete chunks) one at a time. Training: given an image and prior action tokens from the demonstration, predict the next action token. Testing: given an image and prior action tokens the robot just predicted, predict the next action token. The process is the same, so the robot encounters at test time exactly what it was trained on—its own predictions, not a foreign distribution.

By building the action tokenizer directly into the model architecture (not as a post-processing step), the model learns how to chunk actions in sync with what the next-token prediction process needs. This removes a secondary bottleneck: discrete methods often fail because chunking is misaligned with prediction. RoboOmni integrates both, so prediction and chunking are learned together.

Math after the picture

The prediction loss

First in words:

Total loss equals the average negative log-probability of the correct action token, summed over all training trajectories and steps.

Then the compact form:

L = - sum_trajectory sum_step log P(a_token_t | image_t, a_prior_tokens)

Every symbol:

Ltotal training loss (lower is better)
a_token_tthe correct action token at step t
image_tthe image seen at step t
a_prior_tokensall action tokens predicted before step t
P(...)the probability the model assigns to the correct token
A tiny worked example
Suppose at step 1, the correct action token is gripper=open (token index 5). The model assigns 30% probability to this token.
Log-probability: log(0.30) = -1.20. Contribution to loss: -(-1.20) = 1.20.
At step 2, correct token is arm=forward (index 8). Model gives 70% probability: log(0.70) = -0.36. Contribution: 0.36.
Total loss for this 2-step trajectory: 1.20 + 0.36 = 1.56. The model was more confident on step 2, so step 2 contributes less loss.

The model learns by minimizing how often it assigns low probability to the correct action tokens seen in the demonstrations.

What can go wrong

What can go wrong

Tokenizer mismatch. If the action tokenizer does not align with what the language model is trained to predict (e.g., the chunks are too coarse), the model wastes capacity learning misaligned boundaries. Solution: co-train the tokenizer with the predictor so they adapt to each other.
Vocabulary explosion. If actions are chunked too finely, the vocabulary becomes large (e.g., 10,000 action tokens), bloating memory and slowing predictions at test time. Balancing chunk size is critical.
Action precision loss. Converting smooth actions into discrete tokens loses precision. A continuous method can output arm angle 45.6 degrees; a discrete method outputs the nearest bin (e.g., 45 degrees). For fine manipulation, this matters.
Done right: shared training + test time. Train on token sequences, test on token sequences. The same process runs at both stages, eliminating distribution shift.
What a runnable demo should prove

What a runnable demo should prove

Build a minimal robot control loop: a language model that predicts action tokens from images, an action tokenizer that maps tokens to continuous joint commands, and a simulator (or real robot). Train on 100 collected demonstrations of a simple pick-and-place task (pick up a block, move it to a target). At test time, run the loop 50 times: predict an action token, execute it, observe the new image, predict the next token. Compare against a continuous baseline on the same task. The discrete method should maintain success across the full trajectory; the continuous method should degrade as the robot's generated actions diverge from the training distribution.

success_rate = (tasks_completed / total_tasks_attempted) * 100

The metric must show that discrete token prediction keeps success high throughout the trajectory, while continuous methods drop off as distribution shift compounds.
