HieraMAS: Optimizing Intra-Node LLM Mixtures and Inter-Node Topology for Multi-Agent Systems

Build each agent role from several models instead of one, then learn both the inside composition and the cross-agent link pattern so the whole system assigns work more deliberately.

Paper explainersAll themesAgents & Tool Use

Many multi-agent systems tune only one layer of the design. They may tune who talks to whom, or which role each agent plays, or which single model sits inside each agent. This paper argues that those choices depend on each other. If a role contains several models with different strengths, the best communication pattern across agents can change, and the reward signal must say which inner choice helped because the final task score alone is too coarse.

Zero assumption version

Why single-model agents leave useful capacity unused

A multi-agent system usually assigns each agent one role and one model. That is simple to train, but it throws away useful role specialization because different models may help the same role in different ways. One model may draft broad options, another may check details, and a third may merge the final answer.

The hard part is that changing the inside of one role also changes the value of the links between roles. A final task score does not cleanly reveal whether success came from a good role composition, a good communication pattern, or both. The paper asks how to learn both layers together without rewarding the wrong design choice.

The paper's move in one sentence. Treat one role as a small team of models inside a supernode, learn the outer communication structure at the same time, and send reward back at both the role level and the system level so that credit is assigned more precisely.

The algorithm as a flow

What it actually does

Build supernodes for roles

Replace one-model roles with small groups of different models in a propose, synthesize, and check pattern so that one role can cover several subjobs.

Run the full multi-agent task

Let the supernodes exchange messages through a candidate communication structure and measure final task performance.

Assign reward at two levels

Send one signal to the whole system and a finer signal to each supernode because that separates local role value from system-wide value.

Score the communication structure as one object

Choose the link pattern with a graph-level decision rule so that the system evaluates the whole structure instead of judging each edge alone.

Update inner and outer design together

Keep the role mixtures and the communication structure that produce higher task scores at lower cost because those choices delivered more task value per unit of execution spend.

What the paper changes

What the paper changes

The paper changes the basic unit of a multi-agent system. Instead of treating one role as one model, it treats one role as a small internal team, then learns the outer communication pattern with reward signals that distinguish role-level contribution from full-system contribution.

the object it moves  =  the unit that is optimized inside each agent role
The hidden quantity

The hidden quantity

measured quantity  =  which part of the final reward came from the inner role design versus the outer link pattern

The important hidden quantity is credit. When the full system succeeds, the training loop must decide whether that success came from a stronger supernode, a stronger link pattern, or an interaction between them. If it cannot separate those sources, it may reinforce a weak choice simply because it happened to appear in a winning run.

HieraMAS estimates that hidden quantity with multi-level reward attribution. That matters because a role can receive feedback tied to what happened inside that role, while the full system also receives feedback tied to the final outcome.

Why it works

Why this works: separate local role value from full-system value

A flat reward signal is weak for this problem because many design choices are active at once. If the system only sees the final score, it may keep a poor inner role design simply because another part of the system rescued the run. Multi-level reward helps because it narrows the feedback each role receives to what that role contributed.

Treating the communication pattern as one full structure also matters because links interact. One edge may help only when another edge is present. A structure-level decision can capture that dependency because it judges the full pattern together. The result is a system that can improve quality and cost trade-offs because it learns both where to place model diversity and where to spend communication.

Math after the picture

Score inner roles and outer links with two reward levels

First in words:

A simple summary is to maximize final task value minus running cost, while also giving each supernode its own local reward so that the training loop can tell whether one role was useful on its own.

Then the compact form:

total_score = task_value - cost + alpha * sum(role_reward_r) + beta * topology_score

Every symbol:

task_valuefinal score on the benchmark task
costmoney or compute spent on running several models and exchanges
role_reward_rlocal reward assigned to one supernode r
sum(role_reward_r)total of all local role rewards
topology_scorevalue assigned to the chosen full communication structure
alphaweight on local role rewards
betaweight on the structure-level part
A tiny worked example
Suppose one run scores 82 on the task and costs 12 to execute.
The planner supernode earns local reward 6, the coder supernode earns 5, and the reviewer supernode earns 4, so the role-reward total is 15.
The chosen communication structure earns a structure score of 7.
With alpha = 1 and beta = 1, the total score is 82 - 12 + 15 + 7 = 92.
A different run with the same task score but weaker role-level reward would be ranked lower because the system would have less evidence about which inner design was actually useful.

The paper uses a richer learning setup, but this form captures the core idea that local credit and whole-structure credit must both influence the update.

What can go wrong

What can go wrong

Local rewards can still be noisy. If the role-level reward is a poor proxy for real contribution, the system may still favor the wrong supernode design because the local signal points at the wrong cause.
Extra models may cost more than they return. A supernode can become too large, which hurts the trade-off because the quality gain may not justify the added calls and message traffic.
Whole-structure search can be expensive. Choosing among many possible communication patterns can slow training because each candidate structure changes how all roles interact.
Done right. The framework is most useful when roles really need different internal skills and when reward is designed carefully, because then the added structure gives feedback that a flat system cannot provide.
What a runnable demo should prove

What a runnable demo should prove

Build a three-role agent system for a coding or reasoning task. Compare three settings: one model per role, fixed multi-model roles with no learned outer links, and a HieraMAS-style system with learned supernodes plus learned communication structure.

Track final task score, running cost, and the stability of role-level reward across runs. The HieraMAS-style setting should do more useful work per unit cost because it can place strong models only where they help and can choose links that fit those role mixtures.

value_per_cost = task_value / cost ; credit_stability = agreement_of_role_rewards_across_runs

The result should show that joint inner and outer optimization matters because changing the inside of a role changes which outside links are worth paying for.
