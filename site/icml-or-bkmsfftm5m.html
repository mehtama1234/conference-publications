CVE-Factory: Scaling Expert-Level Agentic Tasks for Code Security Vulnerability

This paper turns sparse CVE records into full executable security tasks so code agents can be evaluated and trained on current vulnerability work.

Paper explainersAll themesAgents & Tool Use

Security agents need realistic tasks, but building those tasks by hand is slow and expensive. This paper automates that pipeline by converting short CVE records into executable environments, solutions, and checks that look close to expert-created tasks.

Zero assumption version

Security evaluation lacks enough current executable tasks

A useful code-security benchmark needs tasks that reproduce real vulnerabilities in working repositories. Manual task creation can reach high quality, but it does not scale because each task needs environment setup, a reliable bug trigger, a correct fix, and checks that confirm the task is faithful to the real issue.

The task mix also ages quickly. New vulnerabilities keep arriving, including problems in AI tooling itself. A benchmark built by hand from old reports soon stops reflecting the work a modern security agent must do.

The idea in one sentence. Automate the conversion from CVE metadata to executable tasks, because the benchmark must stay current and large enough for both evaluation and training.

What the paper changes

What the paper changes

The paper changes how security tasks are produced. Instead of relying on manual reproduction one case at a time, it turns task construction into an automated multi-step pipeline with quality checks.

the object it moves  =  task construction for vulnerability benchmarks
The hidden quantity

The hidden quantity: Task fidelity

measured quantity  =  how closely the generated task matches the real vulnerability

Task fidelity measures whether the produced environment truly represents the original vulnerability. A task can look plausible while still being wrong if it uses the wrong repository state, triggers the wrong bug path, or accepts a fix that does not address the actual issue.

This hidden quantity matters because a benchmark built from low-fidelity tasks will train agents on the wrong behavior. High volume only helps if each generated task still reflects the real security work, because otherwise the larger task pool only scales the error.

Why it works

Why automated task synthesis helps

Automation helps because the expensive part of security benchmarking is not only writing instructions. It is reconstructing the exact environment and bug path for each vulnerability. Turning that reconstruction into a repeatable pipeline allows many more tasks to be built from the same kind of public record, because the recovery steps can be reused across cases instead of repeated by hand.

The quality checks are what make the scale useful. Generated tasks become suitable for evaluation and training only when the reproduced environment, bug trigger, and reference fix are verified against the intended issue. That is why the paper reports both correctness and fidelity rather than counting raw task volume alone.

Math after the picture

The core equation

First in words:

A useful task set needs both high correctness and high fidelity, because a large task pool with poor faithfulness would teach the wrong lesson.

Then the compact form:

usable_tasks = generated_tasks * correctness_rate * fidelity_rate

Every symbol:

generated_tasksthe number of tasks produced by the pipeline
correctness_ratehow often the generated task has a valid solution
fidelity_ratehow often the environment matches the intended vulnerability
usable_taskstasks trustworthy enough for evaluation or training
A tiny worked example
Suppose the pipeline generates 100 tasks from recent CVE records.
Suppose 95 of those have a correct reference solution, so correctness_rate is 0.95.
Suppose 96 of those also match the intended environment faithfully, so fidelity_rate is 0.96.
Then usable_tasks is 100 times 0.95 times 0.96, which is 91.2.
That means about 91 tasks are strong enough to trust for downstream use.

This simple product shows why task count alone is not enough. The count matters only after quality filters are applied.

What can go wrong

What can go wrong

The public CVE record is too sparse. If the record omits the affected version or the trigger path, the generated task can drift away from the real issue.
The environment check is weak. A task may look correct even when it reproduces a nearby bug instead of the target vulnerability if the acceptance checks do not inspect the exact failure.
The benchmark becomes narrow. If the accepted tasks come from only a few languages or repository styles, agents may learn local habits instead of broad security skill.
Done right. The pipeline works best when each accepted task is checked against the intended repository state, the intended bug trigger, and the intended fix behavior.
What a runnable demo should prove

What a runnable demo should prove

Build a small CVE-to-task pipeline for a handful of recent open-source vulnerabilities. Start from public CVE text and repository links, then generate the environment setup, the failing test, the task prompt, and a reference fix. Compare the generated tasks with expert-created reproductions on two axes: does the task have a working solution, and does the environment match the intended vulnerability. Then fine-tune or evaluate a code agent on the resulting tasks.

The demo proves the paper's point if the automatic pipeline produces a much larger set of trustworthy tasks than manual work alone, because current executable tasks are the bottleneck for both evaluation and training.

task_gain = trusted_tasks(automatic_pipeline) - trusted_tasks(manual_only)

A strong demo should include at least one failure case where a generated task is rejected, because that shows the fidelity checks are doing real work.
