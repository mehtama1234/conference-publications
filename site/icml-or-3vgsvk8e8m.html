SG2Loc: Sequential Visual Localization on 3D Scene Graphs

A robot localizes itself in a room by matching what it sees to objects in a lightweight compact map made of mesh shapes and labels, refined frame by frame.

Paper explainersAll themesRobotics & Control

A robot navigating an indoor room needs to know where it is using its camera feed. Traditional systems store huge databases of images or full 3D models, which exhausts memory on small robots. This paper trades in that bulky database for something much smaller: a compact map that lists the objects in the room (chairs, walls, tables) with their rough shapes and positions. The robot matches what it sees to those objects, refining its position guess with each new frame.

Why localization is expensive

A robot moving through a building needs to answer one question: where am I right now? The standard way is to store an enormous reference database: either thousands of labeled photographs of every corner, or a dense 3D point cloud of the entire space. Every time the robot sees a new frame, it searches this database to find a match and pinpoint its pose.

But on a memory-constrained robot (a small drone, a phone, a rover), storing thousands of images or millions of 3D points is impossible. The database becomes the bottleneck. And if the building changes—furniture moves, new rooms open—the whole database must be rebuilt and transmitted, wasting bandwidth.

The trap. Dense databases work but cost too much memory. Lightweight representations have not kept up with accuracy.

The algorithm as a flow

What it actually does

1. Build the scene graph once

Represent the room as labeled objects (sofa, wall, table) with coarse 3D mesh shapes and their spatial relationships.

2. Break the incoming frame into patches

Divide each camera image into small regions and extract a feature vector (a list of numbers) for each patch that encodes what it sees.

3. Propose particle poses

Generate many candidate camera positions (particles) scattered through the room, each a hypothesis for where the robot might be.

4. Project and match

For each particle, project the scene graph meshes into the image space, label which patches they occupy, and compare patch features to object embeddings.

5. Resample and refine

Weight particles by match score, resample (keep high-scoring poses, discard low ones), and repeat with the next frame.

What the paper changes

The one thing it changes

The paper replaces the reference database (thousands of images or dense 3D points) with a compact scene graph: a data structure listing objects and their relationships. Instead of storing raw images, store semantic labels, coarse mesh shapes, and object embeddings (learned feature lists—compact sequences of numbers that encode what an object looks like). This shrinks storage from gigabytes to megabytes.

The hidden quantity

The hidden quantity: particle weight via semantic match

measured quantity  =  Semantic patch match score

The paper measures how well the current camera frame matches a hypothesis pose by computing a match score: for each visible object in the frame (from the particle's viewpoint), it compares the actual pixel patch features to the object's learned embedding (a fixed feature vector trained on many examples). Patches showing that object get high scores if their features align; patches showing other objects get low scores. The scores are then combined (using both semantic similarity and color cues) into a single weight per particle.

This hidden quantity—the match score per particle—is what the particle filter uses to re-weight and resample poses. High-scoring poses survive and spawn children for the next frame; low-scoring ones are discarded. The score is not computed ahead of time; it is inferred on-the-fly by comparing the current image to the scene graph.

Why it works

Why it works: the real causal chain

A particle filter works by repeatedly proposing poses and scoring them. The central move: you do not need to store every image or 3D point in the reference database. Instead, you store compact object embeddings (learned feature vectors) and coarse mesh shapes. When the robot sees a new frame, it extracts feature vectors for small patches (regions of the image). For each particle pose (a candidate camera position), it projects the scene graph meshes into image space and asks: do the patches showing object A have features similar to object A's embedding? High semantic match means the pose hypothesis is good; low match means bad. The particle filter upweights good poses and discards bad ones. Over multiple frames, this sequential refinement converges to the true pose.

Why does this work with so little storage? Because a scene graph encodes structure—spatial relationships and object identity—rather than raw pixel data. A coarse mesh tells you the object's rough shape. An embedding is a compressed signature of what that object looks like in feature space. The robot does not need to memorize thousands of images; it only needs to recognize: does this patch belong to this object? That recognition happens via learned embeddings, which are compact (hundreds of numbers instead of millions of pixels per image). The particle filter uses projection: it projects objects from the 3D scene graph into the current camera view, so you only score matches for patches that could be that object.

The math: particle weighting equation

First in words:

The weight of a particle is proportional to the average semantic match between patches and their assigned objects, scaled by color agreement. Combined score = average of (semantic similarity per patch times color factor per patch).

Then the compact form:

w_p = mean_i [ cos_sim(e_patch_i, e_object_i) * (1 + alpha * color_match_i) ]

Every symbol:

w_pweight of particle p (determines survival probability)
mean_iaverage over all visible patches i in this particle's view
cos_simcosine similarity (a score from 0 to 1, measuring feature overlap)
e_patch_ilearned feature vector for patch i in the current image
e_object_ilearned embedding for the object that object i shows (from the scene graph)
alphastrength of color supervision (a small positive number, e.g., 0.1)
color_match_iagreement between predicted and actual pixel colors (0 to 1)
Tiny worked example: two particles, three patches
Particle A: Poses camera inside office. Projects scene graph objects.
Patch 1 shows: Wall. Feature similarity = 0.9. Color match = 0.95. Score: 0.9 * 1.095 = 0.986.
Patch 2 shows: Table. Feature similarity = 0.7. Color match = 0.8. Score: 0.7 * 1.08 = 0.756.
Patch 3 shows: Chair. Feature similarity = 0.6. Color match = 0.7. Score: 0.6 * 1.07 = 0.642.
Average for Particle A: (0.986 + 0.756 + 0.642) / 3 = 0.795.
Particle B: Poses camera outside in hallway (wrong pose).
Patch 1 shows: Wall (correct). Feature similarity = 0.85. Color match = 0.6. Score: 0.85 * 1.06 = 0.901.
Patch 2 shows: Hallway floor, but model predicts Table. Feature similarity = 0.2. Color match = 0.3. Score: 0.2 * 1.03 = 0.206.
Patch 3 shows: Hallway wall, but model predicts Chair. Feature similarity = 0.1. Color match = 0.2. Score: 0.1 * 1.02 = 0.102.
Average for Particle B: (0.901 + 0.206 + 0.102) / 3 = 0.403.
Result: Particle A scores 0.795; Particle B scores 0.403. Particle A is nearly twice as likely to survive resampling. Over many frames, true poses accumulate high weight.

The equation says: a particle is weighted by how well its projected scene graph matches the current image. If objects appear where predicted and have features that match their embeddings, the particle survives and spawns children.

What can go wrong

What can go wrong

Scene graph is too coarse. If the mesh shapes are oversimplified, the projected objects no longer align with real pixels. Patches that show a table edge get scored against a bounding box, not the actual shape, and true poses score lower. Fix: invest in better mesh reconstruction or finer scene graph detail where accuracy matters most, because more accurate mesh shapes make projected boundaries align with true object edges, so the particle filter scores real poses higher.
Embeddings are not discriminative. If the learned object embeddings do not separate dissimilar objects well (e.g., a wall patch and a door patch look the same in embedding space), the particle filter cannot distinguish them. A pose in the wrong room might still score high. Fix: use semantic encoders trained on fine-grained object distinctions, because richer, more separated embeddings make different objects score differently, allowing the particle filter to confidently upweight only truly correct poses.
Motion model fails. The particle filter assumes the robot moves smoothly between frames (a small translation and rotation). If the robot teleports or rotates rapidly, most particles become stale. Convergence slows or fails. Fix: seed particles more aggressively at frame transitions, or use an external motion prior (odometry).
Lighting changes. If the room's lighting changes dramatically (sun moves, lights turn off), color cues become unreliable. The color-match term in the scoring equation fails, leaving only semantic similarity. Accuracy drops. Fix: rely more on semantic features and less on photometry in dynamic lighting.
Done right. Use a fine-grained scene graph with high-quality embeddings from a strong semantic encoder. Combine semantic and photometric cues, but weight semantic higher for safety. Integrate motion priors (robot odometry or IMU). Re-sample aggressively to stay focused on high-probability regions. Test on new scenes unseen during embedding training.
What a runnable demo should prove

What a runnable demo should prove

Build a toy scene in a simulation (e.g., Habitat, PyBullet): one simple room with a few labeled objects (table, chair, wall). Create a scene graph representation by hand or via a simple 3D annotation tool. Train or load a pre-trained semantic encoder to embed objects. Simulate a robot moving through the room with a camera, generating a sequence of frames. Run SG2Loc: extract patch features per frame, project the scene graph for each particle, compute match scores, resample, and track the estimated pose over 50-100 frames. Log ground-truth poses and estimated poses frame by frame.

Cumulative localization error = sum of (distance from estimated pose to ground truth pose) over all frames / number of frames

The demo must show that cumulative localization error stays low (< 0.5 meters for a room-scale scene) even though the scene graph is 20 times smaller than the dense database it replaces.
