Mobile-GS: Real-time Gaussian Splatting for Mobile Devices

Skip the expensive sorting step in 3D rendering by using a method that accumulates pixels without order, then fix the artifacts with a neural net that learns what to show from each camera angle.

Making a 3D scene from Gaussian blobs looks great on a desktop, but mobile phones do not have the computing power to handle the sorting step that all current methods use. Why current Gaussian Splatting is too slow for phones

3D Gaussian Splatting is a way to represent a 3D scene as thousands of overlapping fuzzy blobs. When you view the scene from a new angle, the computer has to blend all those blobs together to make a final picture. To blend them correctly, the standard trick is to sort the blobs by how far they are from the camera (near to far) and draw them in that order, like painting layers with transparency.

On a desktop computer with thousands of cores and fast memory, this sorting step takes a fraction of a second. On a mobile phone, sorting thousands of blobs becomes the bottleneck, consuming half or more of the rendering time. A beginner might try to skip sorting entirely, just accumulating each blob's color at each pixel. But that breaks the transparency math: if you draw in random order, overlapping fuzzy blobs create artifacts and look wrong.

The core problem. Current methods require expensive sorting by distance before each view, but phones do not have time for that. Skipping the sort breaks transparency.

What it actually does

Remove the sort

Accumulate each blob's color contribution at every pixel without ordering by depth.

Learn view effects

A small neural network predicts how transparent each blob should appear, based on camera position and blob position.

Prune weak blobs

What the paper changes

What the paper changes

The paper replaces the depth-sorting rendering pipeline with an order-independent accumulation pipeline, where each blob writes its contribution at every pixel without regard to order.

The hidden quantity

The hidden quantity: view-dependent opacity

measured quantity  =  View-dependent opacity

When you move the camera, some blobs should look more or less transparent from the new angle, even if their position does not change. This is the blob's view-dependent appearance. Without sorting, overlapping blobs will fight for the same pixels. The paper learns a hidden number for each blob: a scalar multiplier that says how opaque (solid) or transparent (see-through) the blob should be from any given camera direction.

The paper estimates this using a small neural network (called a multi-layer perceptron, or MLP, which chains together multiplications and additions that learn to predict a single number from inputs). For each blob, the network takes in the blob's position, the camera's position, and the blob's size and tilt, and outputs how much of that blob should show up. The paper trains this MLP on the same data used to train the main Gaussian Splatting model, so it learns the right opacity for each view.

Why it works

Why it works: the causal chain

Without sorting, you can accumulate all blob colors in parallel at every pixel—this is why it is fast. But blobs at different depths blend in random order, so the math breaks. The fix is to let the neural network learn, for each blob, what its true opacity should be from each camera angle. Since the network sees the blob's position and the camera direction, it can infer whether the blob is in front of or behind other blobs at that view. It learns to predict a correction factor: turn down opacity for blobs that should be hidden, turn it up for blobs in front. The training data (the original high-quality rendering with sorting) teaches the network the right correction. At inference time on the phone, the network runs once per blob per view—a negligible cost—and the random-order accumulation now produces the correct colors.

Additionally, the paper compresses the blob representation: instead of storing full directional information (spherical harmonics coefficients), it distills them into fewer numbers by training a smaller student model to match a large teacher model's outputs. This cuts storage because the student needs fewer numbers per blob. It also prunes (removes) blobs that contribute very little to the final picture, which further reduces the total file size. Together, these shrink the model size by 4-10x, bringing it down from too large to fit on a phone to small enough that the phone has room for it.

The equation behind the fix

First in words:

The rendering loss combines three pieces: the main reconstruction loss, a distillation loss that teaches a smaller model from a larger one, and a depth-aware loss that helps fix transparency artifacts.

Then the compact form:

L = L_rgb + lambda_distill * L_distill + lambda_depth * L_depth

Every symbol:

L_rgbthe error between the rendered image and the ground-truth image
L_distillthe error between a teacher model (high quality) and a student model (compressed), measured at every pixel
L_deptha loss that guides the depth-aware rendering to produce correct transparency from any angle
lambda_distillhow much weight to give the distillation loss (a hyperparameter the trainer sets)
lambda_depthhow much weight to give the depth loss (another hyperparameter)
A tiny worked example
Suppose the teacher model renders a pixel as RGB=(100, 80, 60).
The student (compressed) model renders the same pixel as (98, 79, 58).
Distillation error for that pixel: (100-98)^2 + (80-79)^2 + (60-58)^2 = 4 + 1 + 4 = 9.
If lambda_distill=0.5, this pixel contributes 0.5 * 9 = 4.5 to the total loss.
The trainer nudges the student to output (99, 80, 59), error drops to (100-99)^2 + (80-80)^2 + (60-59)^2 = 1 + 0 + 1 = 2, contribution = 0.5 * 2 = 1.
Repeating over all pixels trains the student to mimic the teacher without sorting.

The distillation loss teaches a tiny model to match a large one without needing the expensive sorting process at inference time.

What can go wrong

What can go wrong

Not enough training data. If the teacher model was trained on only a few camera angles, the MLP may overfit and produce bad opacity corrections for unseen angles. The fix: train the teacher with many viewpoints first.
Compression too aggressive. Reducing the number of blobs via pruning can remove important details. If you prune too much, the model becomes fast but blurry. The fix: tune the pruning threshold so weak blobs are removed but strong details remain.
Neural network mismatch. The MLP must match the camera setup from training. If you render from a camera pose that is very different from the training set (extreme zoom, extreme angle), the network may predict bad opacities. The fix: include diverse camera poses in training.
Done right. Train the teacher on a large dataset with many viewpoints. Distill carefully by tuning lambda values. Prune conservatively. Deploy on a phone and measure rendering time and model size. If both are good and visual quality is intact, the method is working.
What a runnable demo should prove

What a runnable demo should prove

Build a simple scene from a few Gaussian blobs (or use an existing 3D scan). Train the teacher model using standard 3D Gaussian Splatting on the full dataset with many viewpoints. Then train Mobile-GS on the same data: build the MLP, distill it, compress it, and prune weak blobs. Measure rendering time and model size before and after. Render the scene from a camera angle not in the training set with both methods and compare visual quality.

speedup = time_standard / time_mobile; quality_loss = 1 - ssim_mobile / ssim_standard

The demo must show that removing sorting cuts rendering time by at least 4x on a mobile device, model size drops by at least 5x, and visual quality stays above 95% of the original.
