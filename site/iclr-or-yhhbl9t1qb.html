FaSTA*: Fast-Slow Toolpath Agent

A neurosymbolic agent that plans image editing by first trying learned reusable subroutines, and only if they fail, searching through tool combinations exhaustively.

Paper explainersAll themesAgents & Tool Use

Editing images with multiple steps (detect, recolor, remove) requires calling AI tools in the right order. Each tool call costs money and time. This paper builds an agent that learns from past successful edits to recognize when a new task is similar, reusing the same sequence of tool calls without re-searching. When the task is genuinely new, it searches through tool combinations intelligently to find a cheap solution.

Zero assumption version

Multi-step image editing is expensive to plan

Image editing tasks often need multiple steps in sequence: find an object, change its color, remove another object, recolor the background. Each step requires calling an AI tool, and each call costs money and computation time.

A naive approach: when faced with a new task, try all possible sequences of tools until one works. For ten tools and five steps, that's searching through millions of combinations. The search is exhaustive and wasteful.

Another approach: use a language model to propose a sequence of steps. But language models sometimes propose steps that do not work or are inefficient, and you discover the mistake only after running the tools.

The core problem. Current agents either search too broadly (wasting resources on unlikely tool combinations) or plan blindly (without checking if the plan actually works).

The algorithm as a flow

What it actually does

Plan high-level subtasks

Language model breaks the edit task into subtasks: detect bench, recolor bench, remove cat, recolor wall.

Try learned subroutines first

For each subtask, check if a stored subroutine (a pre-vetted sequence of tool calls) matches; if one fits, run it.

If subroutine works, advance

Move to the next subtask, reusing the same pattern.

If subroutine fails, search

Run A* search (a smart algorithm that tries combinations in order of promise, not randomly) to find a cheap tool sequence for this specific subtask.

Record new pattern and extract subroutines

Archive the successful path; if a pattern appears multiple times, extract it as a new reusable subroutine for future tasks.

What the paper changes

What the paper changes

The paper changes which tool sequences are tried first. Instead of searching blindly through all combinations, it now tries learned subroutines first, and only falls back to search if they fail.

the object it moves  =  order of trying tool sequences
The hidden quantity

The reusable subroutine as a learned pattern

measured quantity  =  Subroutine utility (how often a saved sequence solves new subtasks)

A subroutine is a short sequence of tool calls that solved a problem successfully in the past, stored and indexed for recognition. Utility means: how many new editing tasks can this subroutine solve without modification? High utility means the pattern is worth keeping and trying first; low utility means it rarely applies.

The paper estimates utility by tracking how many times a subroutine is invoked across new tasks. It also extracts new subroutines inductively: when a task creates a new successful toolpath that has not been seen before, it analyzes that path, looks for repeating sub-patterns, and packages them as candidate subroutines for the archive.

Plain reading. Think of a cookbook: a frequently-used recipe (like 'how to make a roux') becomes a named step you always try first. New recipes that need a roux start with that cached result instead of measuring flour and butter each time.
Paper reading. The paper calls this adaptive fast-slow planning. The fast path is querying the subroutine archive and trying a match; the slow path is A* search on raw tools. Subroutine utility (how often it succeeds) drives which patterns are kept and tried first.
Why it works

Why it works: reusing patterns saves cost

The core insight is that image editing tasks have structure: many new tasks are similar to past ones. A new task like 'detect and recolor a sofa' resembles a previously-solved 'detect and recolor a bench.' If the agent has cached that successful sequence of tool calls, it can immediately apply it without searching.

A* search is only invoked for subtasks that do not match any stored subroutine. Since most new tasks do overlap with the past, the subroutines cover most cases, and the expensive search is triggered rarely. This is a fast-slow strategy: the fast path (lookup and reuse) dominates; the slow path (search) is the safety net.

The agent also learns from its searches. Every time A* finds a new solution, the agent analyzes it to extract new subroutines. If a pattern appears repeatedly (e.g., 'to recolor objects, always mask, then apply color'), it gets indexed and becomes a tool for future tasks. Over time, the archive grows and the fast path covers more cases, pushing more cost to the early, cheap phase.

Math after the picture

The cost model: penalizing search

First in words:

total cost = fast path cost (small) + slow path cost (large) × number of novel subtasks. By increasing fast path coverage via subroutine extraction, you reduce the number of times slow path is triggered.

Then the compact form:

total_cost = C_fast × n_reused + C_search × n_unmatched

Every symbol:

total_costsum of all tool-call costs for the entire edit
C_fastcost of a single subroutine lookup and execution (small, e.g. $0.01)
n_reusednumber of subtasks solved by subroutines
C_searchcost of one A* search across tool combinations (large, e.g. $1.00)
n_unmatchednumber of subtasks that required A* search
A tiny worked example
Task has 4 subtasks: detect, recolor, remove, recolor wall.
C_fast = $0.01 per subroutine, C_search = $1.00 per A* search.
Naive: all 4 subtasks use A* search. Total = 4 × $1.00 = $4.00.
With subroutines: detect + recolor both match archive (n_reused = 2), remove and recolor wall do not match (n_unmatched = 2). Total = 2 × $0.01 + 2 × $1.00 = $2.02.
Savings: $4.00 → $2.02 (50% cost reduction by caching patterns).

As the archive grows and more subtasks match stored subroutines, n_unmatched shrinks, and total cost drops.

What can go wrong

What can go wrong

Subroutine mismatch. A subroutine is invoked for a subtask that looks similar but is actually different (e.g., recoloring a bench is assumed to work for recoloring a wall, but the tools fail). The agent wastes a call; it then falls back to search, incurring both the wasted subroutine call and the full search cost.
Archive overgrowth. Over time, many subroutines accumulate. If the archive is not pruned, lookup time grows, and some subroutines become stale (rarely useful). The fast path becomes slow.
Task type shift. If the kinds of new tasks change a lot (e.g., image editing transitions from outdoor to indoor scenes), the existing subroutines no longer match. The agent reverts to frequent A* searches until the archive adapts.
Done right. The agent continuously extracts and removes subroutines based on observed utility, keeps the archive lean, and re-evaluates matches carefully before invoking a cached pattern.
What a runnable demo should prove

What a runnable demo should prove

Build a demo with a small archive of 3-5 hand-crafted subroutines (e.g., 'detect and recolor', 'remove and inpaint', 'crop and blend'). Simulate 10 image editing tasks: 5 are variants of past patterns (should reuse subroutines), 5 do not match the archive (should trigger A* search). Count the number of subroutine hits, the number of A* searches triggered, and the total simulated cost. Then, add one new subroutine to the archive and re-run the same 10 tasks; show that a previously-unmatched task now hits the subroutine, and total cost drops.

cost_saved = (naive_cost - fasta_cost) / naive_cost = (10 × C_search - total_fasta_cost) / (10 × C_search)

The demo should make it unmissable that reusing learned patterns cuts the total cost, and that adding more subroutines (by mining past successes) further reduces cost for future tasks.
