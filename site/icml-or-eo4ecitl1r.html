FedPAT: Federated Test-Time Adaptation via Prototype Affinity Topology

When a federated model sees new data from a new client, it stabilizes predictions by trusting the structural relationships between class prototypes, not the local feature measurements.

Paper explainersAll themesRepresentation & Self-Supervised Learning

Federated learning lets many devices train one model together while keeping their data private. But when each device has different kinds of data, or when the world shifts — the camera angle changes, the lighting shifts, the weather worsens — the local measurements of feature patterns become unreliable. FedPAT discovers that even though each device measures features very differently, the neighborhood structure around each class stays the same: "cat is close to dog, far from car". By remembering these stable relationships globally and then checking new data against them, FedPAT makes predictions honest even when the local patterns go haywire.

Zero assumption version

Many devices, shifting ground

Imagine a fleet of delivery robots across different cities. Each robot has a camera that must recognize objects. They train together to save bandwidth and protect privacy — a method called federated learning. But each city has different lighting, seasons, and weather. When a robot trained in sunlight suddenly works at night, its measurements of how "bright" or "red" an image region is become useless.

A naive fix is to have each robot adapt on its own using new unlabeled images from its current location. But adaptation based on local measurements — averaging the features of all cats the robot sees today — is fragile. If today's cats are all photographed from above, the average cat-feature becomes "cat from above", and tomorrow's side-view cat looks alien and gets misclassified.

The core problem. Local feature statistics (the average brightness or shape of a cat-image) change wildly under distribution shift, but what stays the same is which classes are neighbors: cats remain close to dogs and far from cars, even under massive lighting changes.

The algorithm as a flow

What it actually does

Learn class neighborhoods

During training on the source devices, FedPAT computes a prototype (an archetypal example) for each class and measures which prototypes sit near each other.

Pool neighborhoods globally

Each device sends its prototype neighborhood map to the central server; the server averages them into one stable global neighborhood structure called the prototype affinity topology.

Send topology to unseen device

When a new device arrives with new data, it receives the global topology as a structural prior — a belief about which classes should be neighbors.

Use topology as a check

For each incoming image, the device computes local features and diffuses these features along the known topology, spreading information through the neighborhood to stabilize each class score.

Make final prediction

The device blends the topology-diffused scores with its own feature-based scores and does a lightweight optimization step, producing a stable prediction.

What the paper changes

What the paper changes

Instead of trusting local feature statistics for test-time adaptation — the mean feature of all cats seen so far — FedPAT changes the reference frame: it leans on the structural relationships (neighborhoods) between class prototypes. This topology remains stable across distribution shifts because it measures which classes *should* be similar, not the absolute feature values.

the object it moves  =  reference frame for adaptation
The hidden quantity

The hidden quantity: Prototype Affinity Topology

measured quantity  =  prototype affinity topology

The prototype affinity topology (PAT) is a map of distances between class prototypes. For each class (cat, dog, car), the model learns one representative example (the prototype). PAT then measures: how far is cat-prototype from dog-prototype? How far is cat-prototype from car-prototype? This forms a distance matrix — a table that says "on a scale of 0 to 1, how close is each class to every other class?"

FedPAT estimates PAT by computing prototypes from training data on each source device, then averaging all these prototype-distance-tables together at the server. This averages out the noise from local distribution shifts and keeps the stable relationships. When a new device arrives, it receives this global PAT and uses it to check whether new images fit the expected neighborhood structure.

Why it works

Why it works: Stable structure survives chaos

Feature values (the exact numbers in a feature vector, which is just a list of measurements about the image) are fragile under distribution shift, but the relationships among prototypes are much more stable. When the prototype affinity topology says "cat-prototype sits close to dog-prototype in feature space", that relationship persists even when the lighting darkens or the camera angle shifts.

Here is the causal chain: First, FedPAT learns PAT by averaging prototype neighborhoods from many source devices, so PAT captures consensus relationships that noise and local drift have already cancelled out. Second, when a new device receives PAT, it has a structural belief: "if this image looks like a cat, then other nearby classes should also have high scores; if it looks like a car, then cat and dog should have lower scores." Third, the device uses diffusion — spreading belief through the neighborhood like water spreading through connected pipes — to adjust raw scores based on whether they fit the known topology. A score that violates the topology gets dampened. This forces coherence and filters out wild local-shift noise.

The lightweight optimization step at the end refines predictions by moving the feature representation a tiny amount to better fit both the local image and the global topology constraint. This is the safety net: even if the topology is wrong, the device can adjust slightly without overtraining.

Math after the picture

The equation: Topology-guided adaptation

First in words:

loss is local feature mismatch plus a penalty for violating the prototype topology plus a light regularization to prevent over-adaptation

Then the compact form:

L_test = L_feature(f, y) + lambda * L_topology(f, PAT) + mu * ||f - f_init||^2

Every symbol:

L_feature(f, y)how far off the current feature f is from what the image y should be
fthe feature vector for this image
ythe class label or target
L_topology(f, PAT)penalty for how badly the current features violate the learned prototype neighborhoods
PATthe global prototype affinity topology (neighborhood distance matrix)
lambdahow much to trust the topology versus the local signal
muhow much to prevent drifting far from the starting features
f_initthe feature vector before adaptation
A tiny worked example
Suppose we see an image that looks partially like a cat. Local features give it cat-score 0.5 and dog-score 0.1 (very different, violates PAT).
PAT says cat and dog should both be high or both be low (they are neighbors in the topology).
L_topology sees this violation and computes penalty = 0.3 (big disagreement with topology).
L_feature computes mismatch = 0.2 (the image is somewhat ambiguous).
With lambda = 0.8, mu = 0.1, total loss = 0.2 + 0.8 * 0.3 + 0.1 * 0.05 = 0.455.
During optimization, the model nudges dog-score from 0.1 upward toward 0.4, shrinking L_topology to 0.1. New loss = 0.2 + 0.08 + 0.05 = 0.33.
The topology constraint pulled dog-score up because PAT knows cat and dog are neighbors; the model now predicts ambiguous-but-coherent instead of certain-but-topologically-wrong.

This equation forces the model to balance fitting the image (via local features) against fitting the global structure (the topology), while staying close to the original trained features.

What can go wrong

What can go wrong

Topology learned on biased source devices. If the source clients all happen to be biased in the same direction (e.g. all mostly daytime cameras), the global PAT will bake in that bias. A new device with very different data (night cameras) will find that the stored topology does not apply well. The diffusion step will then pull it toward the wrong neighborhoods.
Mismatch between class count and topology. If a new unseen device has classes that were not in the source clients' training, there is no prototype for them, and PAT cannot guide adaptation. The topology is silent on how the new class relates to the old ones.
Diffusion over-smooths predictions. If the topology spreads belief too aggressively (lambda is too high), the model will blur class distinctions. All classes start looking equally plausible because every class pulls on every other via the topology.
Done right. FedPAT works best when source clients are diverse enough that their averaged PAT is a genuine consensus, not a majority illusion. The hyperparameters lambda and mu must be tuned to the magnitude of shift expected; if shifts are mild, lambda should be lower (trust local features more).
What a runnable demo should prove

What a runnable demo should prove

Build a small federated learning setup with 3 source clients (each with a different subset of CIFAR-10, the standard small-image test set) and simulate a distribution shift on a 4th unseen client by rotating all images by 90 degrees or changing the color saturation. Train FedPAT on the 3 source clients so that the prototype affinity topology is stored. Then run the model on the unseen shifted client using FedPAT (have the model make predictions), and compare accuracy and the magnitude of forgetting (how much accuracy drops on the source domain) against a baseline that adapts using only local feature statistics.

forgetting = accuracy_before_shift - accuracy_after_shift_on_source; robustness = accuracy_on_shifted_domain

The demo must show that FedPAT keeps forgetting below 15 percent while improving shifted accuracy by at least 20 percent, because the global topology remembers the neighborhoods that hold across shifts, whereas local statistics crumble.
