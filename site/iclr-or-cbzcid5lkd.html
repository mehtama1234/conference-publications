TIGaussian: Breaking Apart 3D Shapes to Match Words and Pictures

To make a language model understand 3D objects, you must split the Gaussian building blocks into separate position and color channels, then align each channel to the word-space and picture-space independently.

Paper explainersAll themesMultimodal

Today's language models know words and pictures. If you show them a 3D object stored as Gaussian Splatting (little blurry colored balls packed in space), they cannot understand it. TIGaussian solves this by splitting each Gaussian into its parts — where it sits and what color it is — then teaching each part to speak the language of words and the language of pictures. This way, the model learns that certain word-patterns match certain position-patterns, and certain picture-details match certain color-details.

Zero assumption version

Why language models cannot see 3D

Today's language models are trained on pictures (as pixel grids) and words (as lists of text tokens). They have absorbed many patterns from both: pictures teach them shapes and colors, words teach them grammar and meaning. But 3D objects — like point clouds or 3D Gaussian Splatting representations — use a completely different structure. A point cloud is a loose collection of coordinate points. 3D Gaussian Splatting is an even odder format: tiny blurry colored balls scattered through space, each one storing position and color and fuzziness. The model has no learned pattern for these formats.

A beginner might try to just add a 3D encoder on top of the existing picture and word encoders, as if 3D is just another input stream. But this fails because the 3D representation is fundamentally different from both pictures and words: it is sparse (only a few thousand balls, not a dense pixel grid), it has no directional bias (unlike an image taken from one viewpoint), and its structure (position and color as separate attributes) does not naturally map to picture-space or word-space. The encoder produces a 3D feature (a list of numbers), but that list floats in its own space, disconnected from the word-space and picture-space the model already understands.

The problem in one sentence. 3D Gaussian features live in a separate, unmapped space, so language models cannot connect them to words or pictures.

The algorithm as a flow

What it actually does

Downsample the Gaussians

Take the 3D object's thousands of Gaussians, keep only 1024 by picking the most spread-out ones.

Group them into patches

Cluster nearby Gaussians using nearest-neighbor, so each small group captures local spatial context.

Split each Gaussian into branches

One branch encodes position only, one encodes color only, via separate neural networks.

Inject word-space knowledge into position branch

Pretrained point cloud models already know position patterns; use a learned query that attends to that knowledge in.

Align to words and pictures

Pull position-branch features toward word lists (words encoded as lists of numbers) and color-branch features toward picture lists (pictures encoded as lists of numbers) using contrastive loss.

What the paper changes

What the paper changes

Instead of running one encoder that mashes all of a Gaussian's attributes (position, color, fuzziness) together into a single list of numbers, TIGaussian splits them. Position attributes flow through one branch, color attributes through another. Each branch is a separate neural network, so they learn disentangled (unentangled) representations.

The hidden quantity

Attribute coupling: how much position and color information leaks into each other

measured quantity  =  Attribute coupling

When you encode a Gaussian using a single network, position and color information flow through the same layers. If position is important for the task, the network might ignore color or vice versa, or worse, might store them overlapped (coupled) — like putting red ink and blue ink in the same bottle. By running separate branches, you keep them pure: the position branch focuses only on where-ness, the color branch focuses only on appearance. This separation is called disentanglement.

The paper measures this implicitly: if a position query (like a word) returns the correct objects ranked high, and a color query (like a picture) also returns the correct objects, then coupling was low, because each branch was free to learn its own pattern without interference. If branches were coupled, one branch's optimization would corrupt the other's learning, so both queries would suffer. High accuracy on both means the branches stayed disentangled.

Why it works

Why separating position and color fixes the alignment problem

When you encode a Gaussian with a single neural network, the network optimizes a single loss function: make the whole list of numbers align to word-space AND picture-space at the same time. This is impossible if position-patterns and picture-details do not cleanly map to the same numbers. The network compromises, storing partial information in each number. But position is fundamentally different from color: position is geometric (where in space), picture-details are visual (what the thing looks like). By running two separate branches, each branch can optimize its own alignment independently: position-branch pulls toward word lists (words like 'cube' or 'on the left' are spatial concepts), and color-branch pulls toward picture lists (pictures capture appearance and texture). Neither branch is forced to compromise.

The second trick is injecting pretrained point cloud knowledge into the position branch. Point cloud models have already learned that certain position-patterns (like 'points arranged in a line' or 'dense cluster') matter. By letting the position branch look at these patterns early, the branch gets a head start: it learns to focus on the position information that the point cloud model found useful. Meanwhile, the color branch learns independently, free to discover what color-patterns matter for aligning with pictures.

The alignment loss: pulling features toward shared space

First in words:

For each 3D object, you encode its position via branch-A and its color via branch-B. You also encode the same object as an image (via a picture encoder) and as text (via a word encoder). The loss is: for each pair (object-feature, target-feature), the dot product of their normalized vectors should be 1 if they match and close to 0 if they don't. You sum up all the negative log probabilities. This is called contrastive loss: the model learns by contrasting correct matches against incorrect ones.

Then the compact form:

L(F1, F2) = -log( exp(F1 · F2 / tau) / sum_i exp(F1 · Fi / tau) )

Every symbol:

F1the 3D feature (position or color branch)
F2the target feature (word embedding or picture embedding)
F1 · F2dot product: how aligned are the two vectors
tautemperature: controls how sharp the contrast is
sum_isum over all negative examples in the batch
A tiny worked example
Suppose a 3D cat object has position-feature F_pos = [0.8, 0.1, 0.0, -0.2, 0.5]. The word 'cat' has embedding E_cat = [0.7, 0.2, 0.0, -0.1, 0.6]. Normalized dot product = 0.8*0.7 + 0.1*0.2 + 0.0*0.0 + (-0.2)*(-0.1) + 0.5*0.6 = 0.56 + 0.02 + 0 + 0.02 + 0.3 = 0.90 (very aligned).
With tau = 0.07 (sharp), the loss term is -log( exp(0.90 / 0.07) / exp(0.90 / 0.07) + sum of exp(misaligned / 0.07) ). If there are 100 objects in the batch and this is the correct pair, the sum of exponentials in the denominator is dominated by the correct pair, so the loss is close to 0.
If the model confused the cat position-feature with a dog word, dot product drops to 0.40. Then -log( exp(0.40/0.07) / ... ) grows, penalizing the confusion. Training adjusts the cat's position feature toward the word 'cat'.

The loss pushes features toward their correct matches and pulls them away from incorrect ones, so position-features cluster near the words they represent and color-features cluster near the pictures they represent.

What can go wrong

What can go wrong

Oversampling Gaussians at downsampling If you keep too many Gaussians (more than 1024), the spatial context per group is diluted, and the position branch loses fine detail. The branches become couples again because color and position are packed too densely.
Skipping the point-cloud knowledge injection If the position branch does not receive guidance from a pretrained point-cloud model, it must learn geometric patterns from scratch. This is slower and less accurate, so alignment quality drops below what simple text-encoder baselines achieve.
Using only one viewpoint for image-3D alignment If you try to align 3D features to a single photo of the object, the alignment works for that exact viewpoint but breaks for other angles. A tree looks like a vertical line from the side but bushy from above; a single photo cannot resolve this ambiguity.
Weak cross-view fusion If the fusion module does not properly integrate multi-view images (generated by a diffusion model), the model ignores key details. For example, if a diffusion model shows a 'white striped comforter,' but the fusion misses the stripes, the color branch will not align well to pictures of striped blankets.
Done right. Keep both branches separate during training, inject geometric knowledge into position, and fuse multiple synthetic views for image alignment. The model learns to map position to word-space and color to picture-space independently, so all three modalities converge to a shared space (a common set of numbers that both words and pictures and 3D objects understand).
What a runnable demo should prove

What a runnable demo should prove

Build a small dataset of 100 distinct 3D objects (e.g., from Objaverse) and hand-label each with a single word (chair, cup, lamp) and take a single picture. Train TIGaussian on 80 objects, test on 20. For each test object, (1) encode it as a 3D Gaussian, (2) run the position branch to get a position feature, (3) search word embeddings for the closest word, (4) check if it matches the true label. Repeat for the color branch and picture embeddings. Then, do a retrieval test: give the model a word like 'lamp' and ask it to rank all 20 test objects by how close their position-features are to the word embedding. Repeat with a picture query and color-features.

Text-to-3D accuracy = (position branch correctly ranks true object in top 5) / 20. Image-to-3D accuracy = (color branch correctly ranks true object in top 5) / 20.

The demo makes it impossible to miss: position branch solves text queries, color branch solves picture queries, and when you combine both, retrieval accuracy jumps because now each query type uses its natural modality instead of forcing one branch to do both.
