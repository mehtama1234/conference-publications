NL2Repo-Bench: Towards Long-Horizon Repository Generation Evaluation of Coding Agents

Test coding agents on the hard part of software work: turning one requirements document and an empty folder into a complete installable library.

Paper explainersAll themesAgents & Tool Use

Many coding benchmarks ask for a patch, a function, or a local repair. Those tasks matter, but they do not test whether an agent can hold a whole software project together over hundreds of steps. NL2Repo-Bench is built for that longer horizon. The agent gets one natural-language requirements document and an empty workspace, then must choose an architecture, create files, manage dependencies, and produce a Python library that installs and passes tests. The benchmark matters because it measures sustained project coherence rather than isolated code generation.

Why short coding tests miss the real difficulty

A short coding task usually has a local target. Write this function. Repair this failing test. Fill this missing file. Success depends mostly on whether the agent can reason about the nearby code. A full repository build is different because early design choices determine whether much later files can fit together at all.

That longer horizon exposes failures that short tasks hide. An agent can write many locally plausible files and still fail the repository because the package layout is inconsistent, dependencies do not line up, the command-line entry points disagree with the modules, or the tests assume behavior that the earlier design never supported. NL2Repo-Bench is designed to make those long-range failures visible.

The benchmark's point. Measure whether an agent can sustain design, implementation, and integration over a whole repository instead of only solving isolated code fragments.

The hidden quantity

The hidden quantity

measured quantity  =  project-wide coherence

The hard part of repository generation is not writing lines of code. The hard part is keeping every file consistent with one global design. Project-wide coherence means imports line up with the package layout, interfaces match the tests, and later modules honor assumptions made earlier.

NL2Repo-Bench makes this quantity visible because the repository is executed as a whole. A model can look productive while writing files, yet still have low coherence if the parts do not fit together. That is why average test pass rate stays low even for strong agents.

Why it works

Why this benchmark exposes long-horizon weakness

The benchmark works because it removes scaffolding. The agent is not given an existing repository whose structure can be copied and locally extended. It must choose the structure itself, then live with that choice across many later decisions. That setup makes planning errors expensive because a weak early design can force mismatches across the whole codebase.

Execution-based scoring is the second key piece. Surface plausibility is not enough. The repository must install, its modules must connect correctly, and its behavior must satisfy tests. This is what turns long-horizon coherence into something measurable, because execution fails the moment cross-file assumptions stop matching.

Math after the picture

A direct benchmark score

First in words:

repository score = passed tests divided by all tests for the generated project

Then the compact form:

RepoScore = PassedTests / TotalTests

Every symbol:

RepoScorethe execution-based score for one generated repository
PassedTestsnumber of benchmark tests that the generated repository passes
TotalTestsall tests defined for that repository task
A tiny worked example
Suppose a generated library is checked by 20 tests.
If 8 tests pass, then RepoScore = 8 / 20 = 0.40.
That 0.40 can still hide very uneven behavior: perhaps utility functions work, but package installation and cross-file interfaces fail.
The benchmark uses execution because a repository with RepoScore 0.40 is plainly incomplete even if many files look polished.

The paper also studies failure modes, but this score captures the main benchmark judgment: does the whole repository work?

What can go wrong

What can go wrong

Premature stopping. The agent may stop after creating a plausible skeleton, but the repository is still unusable because required modules or wiring are missing.
Cross-file drift. A class name or interface can change in one file and not in another, which breaks execution because the project no longer agrees with itself.
Weak early architecture. A poor initial structure forces later patches to stack up awkwardly, because the repository keeps adapting around a bad foundation instead of following a clean plan.
Done right. A strong agent should keep an explicit project plan, update it as files are added, and re-check package structure, imports, and test assumptions after each major step so the repository stays coherent.
What a runnable demo should prove

What a runnable demo should prove

Create five small library tasks from natural-language requirements only. For each task, ask an agent to build a complete Python package from an empty folder, including modules, package metadata, and tests. Run installation and test execution at the end.

Track both local progress and global success. Count files created, tests passed, and whether the final package installs cleanly. The demo should show that local file production does not guarantee a working repository because project-wide coherence is the real bottleneck.

coherence_gap = local_checks_passed - RepoScore

A large coherence_gap would show that the agent can make many local steps look reasonable while still failing the full repository when everything is executed together.
