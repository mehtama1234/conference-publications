DEPO: Data-Efficient Policy Optimization

Train reasoning models with half the data by spotting which examples teach the model something new and replaying the valuable ones.

Paper explainersAll themesReinforcement Learning

Large language models can learn to reason better using reinforcement learning with verifiable rewards: the model tries to solve a problem, checks its answer against a known correct solution, and learns from the wins and fails. But this takes enormous amounts of data and computation, because every check is expensive (it might involve running a solver or a grader). DEPO shrinks both by asking one simple question: which examples are worth training on? By training only on examples the model can actually learn from, you skip the expensive checks on examples that would not move the needle anyway.

Zero assumption version

The cost trap: more data, more wasted work

When a reasoning model tries to solve a hard problem (like a competition math problem), it generates one or more attempted solutions. For each attempt, the system checks if the answer is right or wrong and gives the model feedback. This checking step — the reward computation — is expensive because it often requires running the problem through a solver or a checker, sometimes multiple times. If you train on 10,000 examples with 5 attempts each, that is 50,000 reward computations.

The trouble: many of those 50,000 examples do not actually teach the model anything new. Some are too easy and the model already gets them right. Some are too similar to examples it has already seen. Some are so hard or so odd that the model cannot learn from them anyway. So the model wastes computational budget on examples that do nothing to improve its reasoning, because the model's weights do not move in any useful direction when trained on an example it already understands or cannot possibly solve.

In one sentence. Cut the computational cost of training by training only on examples the model can actually learn from.

The algorithm as a flow

What it actually does

Offline curation

Score all training examples by diversity (how different from others), influence (how much they move the model), and difficulty (how hard they are).

Keep only high-value examples

Build a smaller dataset by filtering out examples that score low on all three.

Online explorability scoring

As training runs, measure each sample by how much it could push the model into new reasoning territories.

Skip low-explorability samples

When a sample has low explorability, skip its expensive reward computation entirely.

Replay high-value samples

Samples with low explorability get trained on again later, ensuring the model does not miss learning from them.

What the paper changes

What the paper changes: which examples to train on

The paper decides which training examples deserve the expensive reward computation and which ones can be skipped or delayed. Instead of training on every example, it trains on a carefully filtered subset.

the object it moves  =  Training example selection
The hidden quantity

Explorability: can this example teach something new?

measured quantity  =  Explorability score

Explorability is a per-example score that measures how much a sample could push the model into reasoning territories it has never explored before. High explorability means the sample is different enough from what the model has seen that training on it could teach new problem-solving patterns. Low explorability means the sample is redundant or too far outside the model's current ability range.

The paper estimates explorability by looking at the model's confidence on the example (low confidence samples are more informative) and the diversity of the sample compared to others the model has already trained on (rare patterns are more valuable than common ones).

Why it works

Why filtering examples cuts cost without hurting performance

The mechanism is simple: reward computations are expensive, and most training examples do not move the model's reasoning forward. By skipping low-explorability examples during training, you save the expensive reward check for nearly every example you skip. The model trains only on examples where learning is possible.

Why does this not hurt? Because you replay the skipped examples later. The first time you skip an example, it does not get trained on and its reward is not computed. But later, when the model has learned more and the example might become valuable, you replay it. This ensures the model does not permanently miss learning opportunities, but you distribute the expensive reward computations across time instead of computing all of them upfront.

The filtering decision as a simple scoring rule

First in words:

For each example, compute an explorability score from model confidence and example diversity. Train on the example if the score exceeds a threshold; otherwise skip it. Later, replay the skipped examples when their explorability might be higher.

Then the compact form:

explorability_score = entropy(model_output) + diversity(example, seen_examples); if explorability_score > threshold: compute_reward(); else: add_to_replay_queue()

Every symbol:

explorability_scorea number measuring how much this example could teach the model
entropy(model_output)how uncertain the model is about its answer (higher = more uncertain)
diversity(example, seen_examples)how different this example is from ones already trained on
thresholdthe cutoff score above which you compute the expensive reward
A tiny worked example
Example A: entropy 2.5, diversity 0.8. Score = 2.5 + 0.8 = 3.3. Above threshold 2.5? Yes, compute reward.
Example B: entropy 0.2, diversity 0.1. Score = 0.2 + 0.1 = 0.3. Above threshold 2.5? No, skip reward, add to replay.
Example C: entropy 2.0, diversity 1.2. Score = 2.0 + 1.2 = 3.2. Above threshold 2.5? Yes, compute reward.
Result: Examples A and C get trained immediately. Example B waits for replay. Reward computations saved: 1 out of 3.

The score combines how uncertain the model is and how rare the example is; only high scores trigger the expensive reward computation.

What can go wrong

What can go wrong

Threshold set too high. If you skip too many examples, the model misses important learning opportunities and final accuracy drops. The replay mechanism helps but is not a complete fix if the threshold is way too aggressive, because replayed examples are trained on less frequently than they would have been in the naive approach, so the model has fewer chances to learn from them.
Diversity metric is wrong. If the diversity measurement does not match what the model actually needs to learn, you might skip valuable examples or replay worthless ones. The paper uses a specific diversity metric; if your domain is very different, you may need to adjust it.
Replay queue grows too large. If the online explorability score is too conservative, many examples end up in the replay queue. The replay queue can become a bottleneck if it grows faster than the model can re-train on the examples, because you will have accumulated so many deferred examples that the replay training phase takes as long as naive training would have.
Done right. The paper tuned the offline curation metrics and the online explorability threshold on the five reasoning benchmarks. The replay mechanism prevents permanent information loss because delayed training on important examples still happens, just in a batched way. The result: same accuracy on reasoning benchmarks, but 1.85 times faster training, because you compute fewer expensive rewards while still learning all the reasoning patterns you need.
What a runnable demo should prove

What a runnable demo should prove

Build a small reinforcement learning experiment on a simplified reasoning task (e.g., single-digit arithmetic or a toy logic puzzle). Create two training runs: one where every example is trained on (baseline) and one where examples are filtered by explorability and replay (DEPO). Measure the total number of reward computations and the final accuracy after a fixed number of training steps.

reward_computations = number of times you compute the reward; speedup = baseline_computations / depo_computations; accuracy = fraction of test problems the model solves correctly

The demo should show that with filtering, you can cut the reward computations in half or more while maintaining the same final accuracy.
