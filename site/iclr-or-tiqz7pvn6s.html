Meta-Optimization of Heuristics (MoH): Learning to Build Better Solvers

Instead of hard-coding a fixed optimizer, use an LLM to learn how to build better optimizers that discover solutions to hard puzzles.

Paper explainersAll themesOptimization

Hard puzzles (traveling salesman, bin packing, routing) need smart search strategies. Usually you hand-code one optimizer and train it. MoH flips this: it trains an LLM to write its own optimizer code, then uses that optimizer to solve puzzles. The LLM learns which strategies work best across many puzzle types, so it builds an optimizer that generalizes far better than one you designed by hand.

Zero assumption version

The old way: hand-coded optimizers trap you

To solve a hard puzzle like the traveling salesman problem (TSP), you write an optimizer: a step-by-step search recipe. The recipe might be crossover one solution with another, then mutate parts randomly. But this fixed recipe limits what strategies the system can discover.

A beginner might try: write one optimizer, train it on TSP instances of size 20. It learns to solve those. But when you give it size 200, it fails completely, because the strategy that works on tiny puzzles does not scale. You need a new optimizer for each problem size, or each problem type. And there are infinitely many problems.

The deeper trap: you chose the recipe (crossover then mutate). You are blind to strategies you did not think of. So even on familiar puzzles, your optimizer is stuck in the box you built.

The core idea. Let an LLM learn to write optimizer code itself, training on many puzzle types at once, so it discovers strategies that work across all of them.

The algorithm as a flow

What it actually does

Meta-optimizer sees a puzzle type

You show the LLM details about TSP or bin packing, plus a library of heuristics that worked before.

LLM proposes a new optimizer

It generates text code: a custom search recipe (e.g., a different flavor of selection or mutation) tailored to this puzzle.

That optimizer generates solutions

The new optimizer code runs on the puzzle, proposing and refining candidate solutions.

Score the solutions

Measure how good the solutions are. The score tells you if the new optimizer code was smart.

LLM learns which proposals worked

Feed the score back to the LLM. After many trials across many puzzle types, it learns which ideas generalizes.

What the paper changes

What the paper changes

Instead of starting with a fixed, hand-coded optimizer, the paper changes the entire level of the game: it makes the LLM learn to generate optimizer code itself. The LLM becomes a meta-optimizer (optimizer-maker), not just a heuristic-maker. This is one level up.

the object it moves  =  Optimizer code (written by the LLM)
The hidden quantity

Cross-problem generalization: solving new puzzle sizes

measured quantity  =  Generalization gap (old size vs. new size)

The hidden quantity is not a number inside the algorithm; it is a property you measure: how much does the optimizer degrade when you give it a puzzle size or type it never trained on? On size 20, the hand-coded optimizer gets 90% accuracy. On size 200, it drops to 30%. That 60-point gap is the generalization failure.

MoH addresses this by training on many sizes and types at once. The LLM learns which features of a strategy make it work across sizes: ideas that scale up (still find good solutions on size 200) versus ideas that only work on tiny puzzles. A strategy that works on sizes 20, 50, and 100 will likely work on 200, because the LLM picked up universal principles rather than size-specific tricks.

Why it works

Why it works: optimizers that learn to adapt

Here is the causal chain. You start by giving the LLM a seed meta-optimizer (a simple hand-coded optimizer recipe, like crossover-then-mutate). But instead of using it directly, the LLM learns to modify it. In iteration 1, the LLM reads the seed recipe, sees the puzzle details (TSP with 20 cities), and generates a new optimizer idea in English: maybe 'select the two most different solutions and combine them'. That becomes optimizer code.

The new optimizer runs on the puzzle, generates solutions, and scores them. If the solutions are good, the LLM learns that this idea was smart. If bad, it learns to discard it. After many iterations on many puzzle types, the LLM has explored a wide space of strategies (crossover, mutation, selection, greedy-insertion, swapping pairs, etc.) and learned which ones generalize.

The key is multi-task training: you train on TSP size-20, TSP size-50, bin packing, vehicle routing, all at once. The LLM cannot overfit to size-20 because half the problems are different sizes or types. It is forced to learn strategies that work universally. So when it faces a new size (200) or new domain, it already understands what works across diversity.

In contrast, a hand-coded optimizer is locked in: it was designed for size-20 TSP, so it breaks on size-200. An LLM that learned only on size-20 also fails. But an LLM trained on sizes 20-50-100-200 discovers size-agnostic principles, so it generalizes.

Math after the picture

The learning equation: reward the meta-optimizer

First in words:

reward_t equals sum_i (solution_quality_i minus baseline_quality) times (did_idea_work) times weight_for_problem_type_i, where the meta-optimizer learns to propose ideas that maximize this reward across all problem types at once

Then the compact form:

R_t = sum_i [ (Q_i(I_t^j) - Q_baseline) * alpha_i ]

Every symbol:

R_treward signal to the LLM meta-optimizer at iteration t
iindex of a problem type (TSP, bin packing, vehicle routing, ...)
I_t^jthe j-th optimizer code generated by the LLM at iteration t
Q_i(I_t^j)quality (how good the solutions are) when running optimizer I_t^j on problem type i
Q_baselinequality of a standard reference solution (e.g., nearest-neighbor)
alpha_iweight for problem type i, ensuring equal importance across tasks during multi-task learning
A tiny worked example
Iteration t, LLM proposes optimizer idea: 'select top-2 solutions and recombine'.
This optimizer runs on TSP-20 (problem i=1): produces solutions, quality Q_1 = 92. Baseline 85. Gain: 92 - 85 = 7.
Same optimizer on bin packing (problem i=2): quality Q_2 = 84. Baseline 81. Gain: 84 - 81 = 3.
Same optimizer on TSP-100 (problem i=3): quality Q_3 = 55. Baseline 70. Gain: 55 - 70 = -15 (it failed on bigger puzzles).
Reward = (7 * 1) + (3 * 1) + (-15 * 1) = -5. The LLM learns this idea generalizes poorly (great on small TSP, terrible on large TSP), so it down-weights this proposal and tries others.
After 100 iterations, the LLM has learned which ideas have positive reward across <em>all</em> problem types: strategies that work everywhere, not just on one problem type or size.

The meta-optimizer maximizes reward by proposing ideas that help on every problem type, not just one, forcing it to learn generalizable strategies.

What can go wrong

What can go wrong

LLM proposes un-implementable ideas. The LLM generates English text that sounds like an algorithm but is vague or circular (e.g., 'pick the best solutions'—best by what measure?). The fix: curate the prompt to ask for specific, executable steps, and have a parser check for syntactic completeness before running the code.
Overfitting to the training problem set. If you train on only TSP and bin packing, the LLM learns TSP-and-bin-packing-specific strategies. It fails on vehicle routing. The fix: train on a diverse set of problem types from the start.
Computational cost spirals. Each LLM-generated optimizer takes time to run. Training the meta-optimizer means generating hundreds of candidate optimizers and running each on many problem instances. This is expensive. The fix: use a small seed population and only run new candidates on a subset of problems each round.
Done right. Multi-task training across diverse problem sizes and types, executable code generation with validation, and a clear reward signal (quality minus baseline) ensure the meta-optimizer learns strategies that generalize.
What a runnable demo should prove

What a runnable demo should prove

Build a small traveling salesman solver. Start with a hand-coded optimizer (e.g., nearest-neighbor insertion followed by random swaps). Train it on TSP with 20 cities. Measure its accuracy on sizes 20, 50, 100.

Then implement a meta-optimizer: an LLM that reads the problem size and past solution quality, and proposes one mutation to the optimizer code. Train this meta-optimizer on sizes 20, 30, 50, and 70 (a diverse set). For each proposal, run the mutated optimizer, record the solution quality.

After 50 iterations, measure the meta-learned optimizer on size 100 (unseen). The goal is clear: the meta-learned optimizer should maintain or exceed accuracy on size 100, while the hand-coded one tanks.

generalization_failure = accuracy_on_training_size - accuracy_on_unseen_size

The demo succeeds if the meta-learned optimizer's generalization failure is <10 percentage points, while the hand-coded optimizer's is >30 points.
