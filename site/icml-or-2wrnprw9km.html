DSGym: A Standardized and Holistic Framework for Evaluating and Training Data Science Agents

DSGym evaluates data-science agents inside real execution environments so they must use the data, run analyses, and justify conclusions with actual evidence.

Paper explainersAll themes

A data-science agent should do more than talk about an analysis. It should load the dataset, choose a method, run code, inspect the results, and report findings that the data actually supports. DSGym is built around that full loop, because many older benchmarks can be solved by writing plausible text without touching the data at all.

Zero assumption version

Why current data-science benchmarks can mislead

Many existing benchmarks use different interfaces, different scoring rules, and tasks that are too narrow to compare cleanly. Worse, some tasks can be solved without real data use. An agent can produce a convincing answer from prior knowledge or benchmark shortcuts, which means the benchmark rewards style and recall instead of actual analysis.

This is especially harmful in science settings because the whole point of a data-science agent is evidence-based work. If the benchmark does not force the agent to inspect the dataset, run code, and validate a claim, then a high score does not mean the agent can do the job.

The paper's move in one sentence. Put data-science tasks into a shared execution framework with quality filtering, data-grounded task design, and execution-verified training data so that agents must earn answers from the dataset itself.
Why it works

Why this works: standardize the environment and block shortcut answers

DSGym provides a modular execution environment where tasks, tools, and agent scaffolds follow the same structure. That standardization helps because scores from different tasks become comparable, and new tasks can be added without inventing a fresh benchmark interface each time.

The framework also filters and extends the task set. DSGym-Tasks cleans up existing benchmarks by removing weak tasks and shortcut-solvable examples. DSBio adds expert-written bioinformatics work, and DSPredict adds hard prediction problems from several scientific areas. The training side uses execution-verified synthesis, which matters because generated examples count only when code actually runs and produces the intended evidence.

Math after the picture

The grounded-success rate

First in words:

A task counts as solved only if the agent completes the requested analysis and its result is supported by executable evidence from the dataset. The main quantity is the fraction of tasks that pass those grounded checks.

Then the compact form:

grounded_success = verified_tasks / total_tasks

Every symbol:

verified_taskstasks where the agent's code runs and the produced result passes the benchmark's evidence checks
total_tasksall evaluated tasks in the suite
grounded_successshare of tasks solved with data-backed evidence rather than unsupported text
A tiny worked example
Suppose an agent receives 20 tasks.
It writes plausible answers for 16 tasks, but only 11 of those include code that runs and produces the checked result.
Then verified_tasks = 11 and total_tasks = 20.
Grounded success = 11 / 20 = 0.55.
The gap between 16 plausible answers and 11 verified answers is the point of DSGym: a benchmark should reward the verified set, because only those answers are actually supported by the data.

The paper's central criticism is that many benchmark tasks can be answered without using the data. Grounded success is the compact quantity that removes that shortcut.

What can go wrong

What can go wrong

Verification may miss subtle scientific errors. Passing code checks does not guarantee correct scientific reasoning, because an agent can run the wrong analysis cleanly if the task's validator is too shallow.
Standardization can narrow creativity. A shared framework improves comparison, but it may discourage unusual workflows if the tool interface does not expose them, because agents can only use what the environment makes available.
Synthetic training traces can bias behavior. Execution-verified synthesis improves reliability, but the agent may inherit the synthesis pipeline's preferred analysis style if the generated examples are too uniform because repeated traces can push the model toward one narrow workflow.
Done right. The paper extends beyond cleaned-up legacy tasks by adding expert and prediction-heavy suites, because broad coverage is necessary if the benchmark is meant to stand in for real scientific analysis work.
What a runnable demo should prove

What a runnable demo should prove

Create three tasks over a small scientific dataset: summarize a relationship, fit a prediction model, and validate a claim against held-out data. Run one evaluation that scores final text only and another that requires code execution plus evidence checks. Then compare the same agent under both settings.

The demo should show that text-only scoring overestimates ability because some fluent answers collapse once the framework demands code, data use, and checked outputs.

shortcut_gap = text_only_score - grounded_success ; verified_yield = accepted_training_examples / generated_training_examples

A useful data-science benchmark should certify that the agent used the data and produced evidence, because that is the work users actually need.
