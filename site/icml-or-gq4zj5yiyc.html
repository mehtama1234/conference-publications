Efficient Skill Grounding via Code Refactoring with Small Language Models

A small language model grounds robot skills to new embodiments by only editing the execution-specific code lines rather than rewriting everything.

Paper explainersAll themesRobotics & Control

When a robot learns a skill (like slicing vegetables), that skill is written as code. If you put that skill on a different robot with different arms or gripper shapes, the code breaks. This paper introduces RECENT, a method that uses a small language model to fix only the robot-specific lines of code, leaving the core control logic alone. This lets small models adapt skills across robots without the cost of large language models.

Zero assumption version

Skills break when robots differ

When a robot learns how to do a task — like picking up a cup or slicing food — that skill is stored as code. The code includes both the high-level plan (approach the object, grasp it, move it) and the low-level robot commands (which arm joint to move, how hard to grip). If you take that same code and run it on a different robot with different arm lengths or gripper strengths, the commands fail. The object gets missed, the grasp is wrong, or the arm can't reach.

One solution is to throw away the old skill and regenerate new code from scratch using a large language model. But large models are expensive to run on robots in the field, and small models do not generate correct code reliably. A beginner would try: just run the small model and regenerate. This fails because small models lose the semantic intent of the original skill — they produce code that works grammatically but does not capture the actual control strategy.

In one sentence. RECENT keeps the skill's control logic and replaces only the execution-specific code lines by using an ontology to guide the small model.

The algorithm as a flow

What it actually does

Step 1: Encode the skill

An offline large model writes the skill as code with explicit robot commands and preconditions.

Step 2: Build an ontology

A logical database records what the robot can do (gripper type, arm reach) and what the skill needs (grasp capability, object visibility).

Step 3: Query the ontology

Check which parts of the skill's requirements match the new robot's capabilities. Flag mismatches.

Step 4: Refactor

The small model receives the code and the list of mismatched lines. It edits only those lines to use the new robot's API.

Step 5: Execute

The adapted code runs on the new robot with the original control strategy but new command syntax.

What the paper changes

The thing the paper changes

The paper changes the editing strategy. Instead of asking the small model to regenerate all the skill code, RECENT constrains the model to edit only the execution-binding lines: the specific robot command calls, API invocations, and the numbers set for each command that depend on which robot is being used. The high-level control flow — loops, conditionals, sequences — stays exactly as written.

the object it moves  =  execution bindings (robot commands)
The hidden quantity

The hidden quantity: binding compatibility

measured quantity  =  binding compatibility gap

Binding compatibility is the measure of how many lines in the code need to change when moving a skill to a new robot. Specifically, it counts which robot-command invocations and numbers set for each command are incompatible with the target robot's capabilities. If a line calls a gripper API that the new robot lacks, that line has a compatibility gap. If the arm reach is different, any number for moving the arm has a gap.

RECENT estimates this gap by querying the ontology: it checks the skill's required capabilities (gripper type, arm reach, sensor modality) against the target robot's capabilities. Every mismatch identifies one or more lines that must be refactored. By calculating this gap ahead of time, the system knows exactly which lines to ask the small model to edit, dramatically reducing hallucination and error.

Why it works

Why it works: constrained refactoring

The core mechanism is constraint-based editing. Small language models are often unreliable when asked to do unstructured code generation. But they are much better at constrained editing: fixing specific lines that are flagged as wrong. RECENT provides this constraint by computing binding compatibility ahead of time and telling the small model exactly which lines are out of bounds.

Here is the causal chain: When a skill is moved to a new robot, the ontology identifies mismatched capabilities (e.g., old robot has a parallel gripper, new robot has a suction gripper). This mismatch points to specific code lines that invoke the old gripper API or assume the old arm reach. The small model is then asked only to edit those flagged lines using the new robot's API and reach numbers. By narrowing the scope, the model spends its generation budget on a small, well-defined task rather than hallucinating an entire skill. Fewer decisions means fewer errors. Because the control structure is already correct in the original code (it was designed by a capable human or a large model), the small model only needs to substitute the execution details, not redesign the strategy.

Math after the picture

The compatibility scoring equation

First in words:

For each execution binding, check if the skill's required capability matches the new robot's provided capability. Count mismatches to get the compatibility gap. Total edits needed equals the sum of mismatches.

Then the compact form:

gap = sum_i (C_required(skill_i) not in C_provided(robot)) for all capabilities in the skill code

Every symbol:

C_required(skill_i)the capability needed by line i in the skill code (e.g. parallel gripper, arm reach > 1 meter)
C_provided(robot)the list of capabilities the target robot declares it has
gapthe count of incompatible lines
not inif a required capability is absent from the robot's capability list, that line has a mismatch
A tiny worked example
Original skill requires: [parallel_gripper, arm_reach_1.2m, force_sensor]
New robot provides: [suction_gripper, arm_reach_1.5m, no_force_sensor]
Mismatch 1: parallel_gripper not in [suction_gripper, arm_reach_1.5m, no_force_sensor] = 1 line to edit
Mismatch 2: force_sensor not in robot capabilities = 1 line to edit
Total gap = 2 lines. Small model refactors only those 2 lines. All other lines inherit from original.

The gap is computed before asking the small model to edit. This reduces hallucination because the model is not making an open-ended choice about what to change; it receives a precise list of target lines and can focus only on generating correct replacements.

What can go wrong

What can go wrong

Ontology is incomplete. If the ontology does not record all the robot's capabilities or misses subtle incompatibilities, the compatibility gap will be wrong. Undetected mismatches will cause edits that silently fail at runtime.
Execution binding is entangled with control logic. Some skills mix robot-specific code tightly with the control strategy. If a coordinate transformation is threaded through a loop condition, refactoring only the binding line may break the loop logic.
Small model still generates incorrect API calls. Constraining the edit space reduces hallucination by focusing the model on a narrow task. However, even with this focus, a small model can still misuse the new robot's API because generating the exact correct function call still requires the model to understand the API semantics. The ontology provides the function definition, but the model must match the values it passes to the correct slots in the function.
Ontology is up-to-date and skills are well-written. When the ontology accurately reflects robot capabilities and skills separate control logic from embodiment details cleanly, RECENT adapts successfully.
What a runnable demo should prove

What a runnable demo should prove

Write a simple pick-and-place skill as code: approach an object at a 3D coordinate, grasp it using gripper force, lift, move to a target location, and release. Encode the skill in Python with explicit robot API calls (e.g., franka.move_to_pose(...), franka.gripper.close(force=80)). Build an ontology recording Franka capabilities. Now add a second robot (UR5) with different gripper type and arm reach. Use RECENT: query the ontology to find binding incompatibilities (gripper API differs, coordinate frame differs), flag those lines in the code, and run a small model to refactor only the flagged lines. Execute the refactored code on UR5 in a simulator. Measure success rate.

success_rate = (number of successful pick-and-place completions on new robot) / (total number of trials) * 100%

The demo must show that refactored skill succeeds on the new robot without regenerating the entire code and without running a large language model at deployment time.
