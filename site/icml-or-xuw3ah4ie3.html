MulFCoder: Framework-conditioned Multi-agent for MLLM-based Multi-framework Front-end Code Generation

Turn one screenshot into working React, Vue, or Angular files by giving separate workers a shared picture of the page and a short list of framework rules.

Paper explainersAll themesAgents & Tool Use

This paper studies why screenshot-to-code systems often fail when the target stack changes. A page that compiles in one stack can break in another because file layout, component rules, and update rules differ. MulFCoder handles that by splitting the job across four workers and by making the target stack explicit from the start, so each step can follow the right local rules for structure, file edits, and quick checks.

Zero assumption version

Why screenshot-to-code breaks across stacks

A screenshot only shows the final page. It does not show how files should be split, where state should live, or which stack-specific rules must hold before the project can run. If a system writes code by copying one generic pattern, it will often choose the wrong file shape or the wrong update rule for the requested stack.

The paper argues that stack differences should be treated as explicit constraints during generation. That matters because React, Vue, and Angular do not merely spell the same page in different ways. They require different file contracts, component boundaries, and repair checks.

The central move. Make the target stack visible to every worker and give each worker a narrow job, because local rules are easier to follow than one large unconstrained generation step.

The algorithm as a flow

What it actually does

Parse the screenshot.

The Grounder extracts visible elements, text, and coarse page regions so later steps can reason over a structured page description instead of raw pixels.

Plan the page and files.

The Planner builds a tree for the page and writes a stack-specific file contract because React, Vue, and Angular expect different file boundaries and update rules.

Write controlled edits.

The Writer creates files or patches only within the allowed window so each update stays tied to the current plan.

Run light checks.

The Judger checks whether the update obeys stack-specific constraints, because a cheap early check can stop bad code before many later edits depend on it.

Repair when needed.

If the check fails, the system asks for a small repair rather than a full restart, so useful earlier structure is preserved.

The hidden quantity

The hidden quantity

measured quantity  =  compatibility between the current code state and the requested stack

The key hidden quantity is whether the partial project still matches the requested stack. A page may look visually close to the target while still having the wrong component split, the wrong file relationship, or the wrong local rule for updates. Those mistakes are hidden until later checks or compile attempts expose them.

MulFCoder tries to estimate that hidden compatibility after every step. It does that by carrying forward explicit structure from grounding and planning, then checking each edit against stack-aware constraints because early structure and early checks make silent drift less likely.

Why it works

Why stack-conditioned workers help

The four-worker split removes a harmful coupling. If one worker must infer page structure, invent file layout, write code, and judge correctness all at once, each mistake contaminates the next decision because there is no stable intermediate object to anchor the run. MulFCoder instead creates explicit intermediate artifacts, such as grounded page elements and a file contract, so later steps can reuse decisions that have already been made.

The stack-conditioned checks matter because they turn broad generation into a smaller decision problem. A writer no longer asks, for example, how any front-end page might be written. It asks how this planned component tree should be realized under this named stack. That restriction helps because fewer legal moves remain, so the system can reject incompatible edits early and request bounded repairs before the project drifts far from the target.

Math after the picture

Pick the update that best fits the contract

First in words:

One simple summary is to score each candidate code update by asking how well it matches the grounded page description and the stack-specific file contract, then subtract a penalty when the update breaks a local rule or forces extra repair work.

Then the compact form:

score(update) = page_fit(update) + contract_fit(update) - repair_risk(update)

Every symbol:

score(update)overall value of one candidate file write or patch
page_fit(update)how well the update realizes the grounded page structure
contract_fit(update)how well the update matches the planned stack-specific file contract
repair_risk(update)expected cost of later rejection or repair if this update is accepted now
A tiny worked example
Update A matches the planned component tree well and respects the file contract, so page fit is 8 and contract fit is 9.
Its repair risk is 2 because the edit stays inside the allowed file window.
Update B also matches the page tree, but it mixes files that the stack expects to keep separate, so page fit is 8 and contract fit is 4.
Its repair risk is 5 because later steps will need extra fixes.
Update A wins because 8 + 9 - 2 is larger than 8 + 4 - 5.

The paper uses explicit workers and rule checks rather than this exact formula, but the formula captures the main tradeoff: accept edits that fit both the page plan and the stack contract while avoiding updates that create future repair work.

What can go wrong

What can go wrong

Grounding can start from a bad page parse. If the first worker misreads the screenshot, later workers inherit the wrong page structure, so clean stack logic will still produce the wrong project because the input description was already off.
The file contract can be too rigid. A narrow contract may block a necessary reorganization if the early plan was weak, because bounded repair assumes that most of the plan is already right.
Light checks can miss deep runtime faults. Cheap checks keep the loop fast, but they may accept code that still fails later because some stack rules only show up under fuller execution.
Done right. The design helps when stack rules are exposed early and checked often, because then each worker solves a smaller and clearer problem.
What a runnable demo should prove

What a runnable demo should prove

Build a small benchmark with the same page screenshot requested in three target stacks. For each run, record the grounded page tables, the planned component tree, the file contract, the sequence of file patches, and every judge decision. Compare a single-step code generator against the four-worker pipeline.

The demo should show better run success and fewer stack-specific faults for the pipeline because explicit page grounding and stack-conditioned checks remove many bad edits before they shape the rest of the project. It should also show where the process fails when the first page parse is wrong, because that reveals whether later workers can recover from early structural errors.
