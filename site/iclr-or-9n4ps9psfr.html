Programming with Pixels: Computer-Use Agents on Software Engineering

Generalist computer-use agents match specialized coding agents when given direct file and shell access, but fail on visual-only tasks because they cannot ground their actions in dense screen interfaces.

Paper explainersAll themesAgents & Tool Use

Computer-use agents (programs that control a computer by looking at screenshots and clicking buttons) were built to handle any task a person could do. But no one had tested whether they could do real software engineering—write code, debug, run tests, fix errors across multiple files. This paper builds the first benchmark where agents control an IDE visually and measures how well they perform. The surprising result: when agents get direct access to file editing and bash commands, they work nearly as well as specialized coding tools; but visual-only control is catastrophically worse, revealing that current agents cannot read complex screen layouts accurately.

Zero assumption version

Generalist agents cannot do real work

Computer-use agents look at a screen, understand what they see, and click or type. In theory, they should handle any task a person handles. But they have only been tested on toy problems—clicking a button, filling a form, clicking a few times in sequence. No one knew if they could do something actually complex and specialized, like building software: writing functions, fixing bugs, editing files without losing track, running tests, reading error messages.

A beginner might hope the agent learns by pure vision—it sees code on screen, understands what to do, and types correctly. But in software engineering, you often need to touch multiple files in one task, remember lines from one file while editing another, and respond to compiler errors. When the agent controls an IDE with just the screen, it gets lost in the dense interface: it cannot reliably locate the file it needs, loses track of line numbers when scrolling, types in the wrong place, or misreads red-squiggly error messages.

In one sentence. The paper builds a benchmark to test whether generalist agents can do real software engineering, and discovers that visual-only control fails because agents cannot ground their understanding in complex IDE screens.

The algorithm as a flow

What it actually does

Build the benchmark

Create 15 software engineering tasks: write code, fix bugs, run tests, across languages and file types.

Test visual-only agents

Agent sees the IDE screen, clicks buttons, types, navigates windows. Measure success rate.

Test agents with APIs

Agent can still see the screen, but also directly call file-edit and bash-run commands without clicking.

Test agents with full IDE APIs

Agent gains access to all IDE text-mode APIs: navigate symbols, run debugging tools, etc.

Analyze the gap

Compare performance across three modes. Identify why visual-only fails: screen grounding, multistep planning, error recovery.

What the paper changes

What the paper changes: input method

The key move is offering the agent a choice of how to send commands: pure vision (screenshots only), or text APIs (direct commands). The paper measures which input path lets the agent perform real work reliably.

the object it moves  =  input modality (vision vs. APIs)
The hidden quantity

The hidden quantity: grounding accuracy

measured quantity  =  screen-location correctness

This paper measures something subtle that existing benchmarks do not: how often the agent locates the right place on screen to act. When an agent reads a dense IDE screenshot (dozens of panels, syntax colors, file trees, terminals), it must map its intention (edit line 42 in main.py) to a pixel location. A single mis-click—targeting the wrong text field or wrong file tab—makes the action fail.

The paper does not explicitly state a formula for this, but by comparing visual-only versus API access, it reveals the bottleneck: visual grounding. When the agent skips the screen and uses text APIs instead, it jumps from near-random accuracy to expert-level, which tells us the limiting factor was never the reasoning, but the ability to find and target the right pixel.

Why it works

Why APIs unlock performance

An IDE screenshot is dense: file tabs, line numbers, syntax highlighting, error markers, multiple panes. When an agent reasons visually, it must convert its plan (edit function foo on line 12) into a target pixel and a click. This conversion step is fragile. The agent might misidentify which file tab is active, miscount lines if the display is scrolled, or tap the wrong editor pane when multiple windows overlap.

When the agent is given direct file-editing and bash APIs, it skips the pixel-targeting step entirely. Instead of clicking, it calls a text command: 'edit main.py line 12' or 'run pytest tests/'. The intention is expressed directly, in the modality the agent was trained on (language). The agent no longer has to parse screen density; it speaks the task in plain words. This is why performance jumps: the reasoning capability was there all along, but the visual grounding layer was throttling it.

A third mode—full IDE text APIs—shows that even more grounding is possible. When the agent can query 'what files are open' or 'what was the compiler error,' it gains context without reading pixels. Each layer of direct API access removes one source of visual ambiguity, and performance rises accordingly.

Grounding accuracy as a success multiplier

First in words:

task_success = agent_reasoning × visual_grounding_accuracy × api_clarity

Then the compact form:

success_rate = (reasoning_quality) × (grounding_accuracy) × (1 + api_factor)

Every symbol:

reasoning_qualityhow well the agent can plan multi-step edits, 0 to 1
grounding_accuracyfraction of clicks/locations that target the right pixel, 0 to 1
api_factorboost from using direct APIs instead of vision, 0 to 2
A tiny worked example
Baseline agent (visual-only): reasoning_quality=0.8, grounding_accuracy=0.3, api_factor=0 → success = 0.8 × 0.3 × 1 = 0.24 (24%)
Same agent with file+bash APIs: reasoning_quality=0.8, grounding_accuracy=1.0 (no pixels to misread), api_factor=1.0 → success = 0.8 × 1.0 × 2 = 1.6 capped at 1.0 = high performance
Intuition: reasoning does not change; grounding and API clarity fix the bottleneck.

When an agent skips screen parsing and speaks in text APIs, it trades visual ambiguity for direct language, multiplying task completion.

What can go wrong

What can go wrong

Visual-only agents panic in dense interfaces. If the agent relies only on screenshots, it will misidentify file tabs, miscount lines, and click in the wrong pane. Task failure rate is high.
Multistep tasks require context carryover. Editing one file, then another, then running a test requires the agent to remember what it did and track state. Visual-only agents forget which file is open when they scroll or minimize.
API names and syntax must be clear. If the agent does not understand the file-edit or bash API (the exact format, what fields are required), it will call them wrong. Poor documentation ruins the advantage.
Done right: APIs are task-agnostic. By offering generic file and shell commands instead of domain-specific tools, the agent uses general-purpose reasoning and stays adaptable to new tasks.
What a runnable demo should prove

What a runnable demo should prove

Build a simple software engineering task: given a buggy Python file and a failing test, have an agent fix the code without human intervention. Run three versions: (1) visual-only—agent sees IDE screenshots and clicks; (2) with file+bash APIs—agent can call file-edit and bash commands; (3) with full IDE APIs—agent can also query file list and symbol locations. Measure success rate on a diverse set of bugs: logic errors, syntax errors, missing imports, off-by-one loops. Compare the three modes and measure task completion time and accuracy.

success_rate = (number of tasks completed correctly) / (total tasks); visual_only_rate vs. api_rate ratio

The demo makes visible how much of the agent's failure is screen-reading versus reasoning. When APIs unlock performance, you see that the reasoning was never the bottleneck.
