ProRe: Proactive Reward System for GUI Agents

A system that actively probes the environment to give GUI agents smarter, more accurate rewards.

Paper explainersAll themesAgents & Tool Use

Training an AI agent to use a computer's graphical interface is hard because it's unclear how to tell when the agent is on the right track. Most reward methods (rules that score how well an agent is doing) either freeze into rigid templates or rely on a human-labeled database that doesn't exist. ProRe fixes this by using two kinds of AI agents working together: one reasons about what questions to ask about the environment, and another actually explores the environment to find the answers. This produces richer, more honest reward signals.

Zero assumption version

Rewarding a GUI agent is stuck in the middle

An AI agent that clicks buttons and types into forms needs feedback: is it closer to the goal or further away? A naive beginner would hardcode simple rules: if the agent typed the right password, score goes up. But a real computer screen has thousands of possible states, and what counts as progress is rarely obvious. Rule-based rewards either give crude signals (did you reach the button?) or require someone to build a database of correct answers for every possible interface.

The other approach is to ask a large language model to judge: does this sequence of clicks look like it's solving the task? The problem: the LLM only sees the screenshots, not what happened inside. It guesses blindly. It misses that the agent typed into the wrong text box, or scrolled past the target, or is stuck in a loop. Static judgments from a locked view fail on tricky GUI tasks.

Neither rigid rules nor blind guessing can fairly score a GUI agent. ProRe solves this by having one AI actively ask questions about the environment (Does this field hold text or just numbers? Has this button been clicked?) and another AI go explore to find the answer.

The algorithm as a flow

What it actually does

The reasoner observes a trajectory

It watches the sequence of screenshots the GUI agent produced.

The reasoner identifies an uncertainty

It decides which part of the state it does not fully understand yet.

The reasoner designs a probe

It asks the actor: go test this hypothesis about the GUI (e.g., type into this field and see what error pops up).

The actor executes the probe

It interacts with the live GUI to get the ground-truth answer to the reasoner's question.

The reasoner assigns the reward

Using all the facts gathered, it scores how well the original agent sequence accomplished the task.

What the paper changes

What the paper changes: the reward signal itself

The paper's core move is to replace a static judgment (LLM looks at screenshots and guesses) with a live inquiry process (an AI actively probes the environment to gather facts). The reward is no longer a passive guess; it becomes an active discovery.

the object it moves  =  the reward signal
The hidden quantity

The hidden quantity: state uncertainty

measured quantity  =  state uncertainty (how much is still unknown)

The reasoner tracks state uncertainty: how many facts about the current GUI state are still unknown or ambiguous. It starts high (the agent clicked something, but was it the right thing?) and drops with each probe. If uncertainty remains above a threshold, the reasoner asks another question.

The paper measures this by counting how many questions the reasoner needs to ask before it is confident enough to assign a stable reward. Fewer questions reveal that the original trajectory was clear and correct. More questions suggest the agent's path was confusing and risky.

Why it works

Why it works: active probing beats passive guessing

A static LLM judge fails because it only sees frozen screenshots—it cannot distinguish between an agent that typed correctly and one that typed into the wrong field, because both look like clicking and typing from the outside. ProRe fixes this by having the reasoner ask the actor to probe the live state: type into the field and show me what error appears, or click the button and tell me if it was clickable, or scroll and report if the content changed. Each answer directly reveals hidden facts the screenshot alone cannot.

Once the reasoner has enough ground-truth answers, it can assign an honest reward: not a guess, but a judgment grounded in facts. An agent whose sequence matches the facts (it typed in the enabled field, the form processed) gets high reward. An agent whose sequence contradicts the facts (it clicked a disabled button and nothing happened) gets low reward. The signal is verifiable—if you dispute it, the reasoner can point to the live probe that proved it.

Math after the picture

The reward equation

First in words:

Reward score is the weighted sum of fact-coverage plus uncertainty reduction, penalized by probe cost. Reward equals the number of facts gathered (each fact weighted by its importance to the task) minus a small penalty for how many probes were needed.

Then the compact form:

R = sum_i w_i * f_i - lambda * N_probes

Every symbol:

sum_i w_i * f_itotal factual evidence: each fact f_i is weighted by its importance w_i (facts about the goal are worth more than facts about side effects)
N_probesnumber of questions the actor had to ask; more probes = more cost
lambdathe probe cost coefficient; how much each extra question hurts the final reward
A tiny worked example
Scenario A: agent types password into the login field. Reasoner probes once: Is this the password field? Actor answers yes. Facts gathered: w1=8 (password field identity, critical). Reward = 8*1 - 0.5*1 = 7.5.
Scenario B: agent types password into a comment field by accident. Reasoner probes twice: Is this the password field? Actor answers no. Is the field enabled? Actor answers yes. Facts gathered: w1=8 (not the password field, critical error), w2=2 (field is enabled). Reward = (8*1 + 2*1) - 0.5*2 = 9.5, but the w1 fact proves failure, so reasoner returns low reward.
Fewer probes = lower cost = higher reward if facts support success. More probes = higher cost + facts must be stronger to overcome it. The reasoner balances thoroughness and efficiency.

Each probe fills in one missing piece of the state puzzle; the reasoner stops when it has enough pieces to confidently judge success or failure.

What can go wrong

What can go wrong

The reasoner asks unanswerable probes. If the reasoner's probe questions are outside the GUI's capabilities (e.g., asking the actor to type into a field that doesn't exist), the actor fails and returns no useful signal. The reasoner must know the GUI's actual capabilities.
Probes take too long. If each probe requires the actor to reload the page, click many times, or wait for network calls, the cost becomes prohibitive and the method becomes slower than the original LLM judge. Probe design must be cheap.
The reasoner's hypothesis is biased. If the reasoner systematically asks probes that favor one outcome (e.g., only probing facts that support success), it introduces subtle bias into the reward. The reasoner must probe both positive and negative hypotheses.
Probes are well designed and cheap. When the reasoner asks targeted, low-cost questions that directly reveal ground truth, the reward signal becomes verifiable and the policy agent learns fast and reliably.
What a runnable demo should prove

What a runnable demo should prove

Build a simple GUI task: open a web form, fill in fields, submit it. Train one GUI agent with rewards from a static LLM judge, and train another with ProRe rewards. The demo should show that the ProRe agent converges faster (reaches the goal in fewer training steps) because clear, fact-based rewards let the agent learn which actions actually work without guessing, explores less blindly because each reward is now tied to concrete evidence, and achieves higher final accuracy because the training signal is honest and verifiable. Measure two things: how many probes the reasoner needs (should be small and decrease over time as the agent learns, because early uncertainty is high but repeating actions after successful learning causes less uncertainty), and how often the two reward signals agree (static LLM vs. ProRe should drift further apart as the task gets harder, because blind guessing breaks down on complex states but ProRe's active verification stays consistent).

Success rate = fraction of test trajectories where agent reached the goal; probe cost = average number of probes needed per trajectory; reward stability = correlation between LLM judge and ProRe on the same trajectory

Active probing lets you grade an agent fairly without ground-truth data. The reasoner explores the live environment to gather facts, so the reward is grounded in reality, not a blind guess.
