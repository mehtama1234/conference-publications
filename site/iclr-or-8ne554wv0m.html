ARMOR: High-Performance Semi-Structured Pruning via Adaptive Matrix Factorization

ARMOR wraps the pruned weights with learned rotation matrices that tilt the problem so that 2:4 sparsity throws away less important information.

Paper explainersAll themesEfficiency & Systems

Large language models are too big to run on normal hardware. One trick is to remove every other weight in small groups (2:4 sparsity), which computers can speed up because the sparsity pattern is regular enough that specialized circuits can process it in batches rather than one weight at a time. But deleting weights hurts the model. ARMOR keeps a rotatable pair of corrector matrices around the pruned core, so the remaining weights can work at an angle—like adjusting a video camera's lens to fix a blurry angle shot.

Zero assumption version

Pruning breaks the model, sparsity ties your hands

A naive approach: just delete half the weights in each group and keep the rest. But the weights are tangled—each one is doing many jobs at once. Deleting the wrong ones breaks multiple things. A beginner tries to keep the biggest weights, but size and importance are not the same thing.

The real problem is worse: your hardware only speeds up deletions that follow a 2:4 pattern—exactly two survivors per four consecutive weights. Modern graphics cards have specialized circuits that expect this exact repeating pattern of survivors and blanks, so they can process multiple groups in parallel. If you violate the pattern, the speedup vanishes. This hard rule means you cannot always keep the truly important ones. You are forced to throw away the most critical weight just because the position forbids it. Every existing method pays a steep accuracy price for this inflexible hardware demand.

The move. Learn two lightweight matrices that rotate both the weights and the data into a tilted space where the 2:4 pattern does less damage.

What the paper changes

What the paper changes

Instead of directly pruning the weight matrix W into a sparse form, ARMOR splits it into three parts: left rotator, then sparse core, then right rotator. The sparse core obeys the 2:4 rule (hardware constraint), while the two rotators are learned block-diagonal matrices—cheap enough that they do not cancel out the memory savings. The rotators tilt the problem; the sparsity constraint then does less harm.

The hidden quantity

The proxy loss: your error measuring stick

measured quantity  =  Reconstruction error on calibration data

The paper needs a fast way to know if a pruning choice is good. Running the entire model on all downstream tasks is too slow. Instead it measures a proxy loss: how well the pruned weights reconstruct the intermediate answers (the activation signals) that flow through that layer when the model processes a tiny calibration batch.

The proxy loss decomposes layer by layer and weight by weight. This decomposition is the key to making the algorithm fast—you can solve each small group of weights independently, which is how block coordinate descent works.

Paper reading. NoWag is the proxy loss used (it stands for no-weight-averaging, tracking how far predictions drift); it breaks into independent piece-by-piece calculations, allowing updates to each 4-element sparse group separately.
Why it works

Why rotating space makes pruning less harmful

Imagine the weight matrix as a set of directions. Some directions carry critical information (the model uses them often and they move predictions a lot). Others are noise or redundancy. Naive 2:4 sparsity does not know which is which; it just deletes by position. ARMOR learns two block-diagonal rotators that spin the matrix into a basis where the less important directions happen to sit in the positions the sparsity pattern will delete.

The left rotator is applied to the incoming data (the input to the weight matrix). The right rotator is applied after (to the output). Together they form a learned basis change. In this new basis, the directions that carry important information are preserved; the zones that do not matter much are pruned. The rotators are block-diagonal, so each block is independent and cheap to compute.

The algorithm uses block coordinate descent: iterate by alternately updating the rotators (to minimize reconstruction loss) and updating which weights survive the 2:4 pattern. Each step shrinks the loss, and the procedure has a proof that it converges to a solution as good as the best existing algorithm.

The factorization: what gets optimized

First in words:

Original weight matrix equals left block diagonal times sparse core times right block diagonal

Then the compact form:

W_hat = L * (W_sparse ⊙ M) * R

Every symbol:

W_hatthe pruned weight matrix after factorization
Lleft block-diagonal corrector matrix (learned)
W_sparsethe weight matrix with 2:4 sparsity applied
Mbinary mask enforcing 2:4 sparsity (exactly 2 ones per 4 elements)
⊙element-wise multiplication (hadamard product)
Rright block-diagonal corrector matrix (learned)
A tiny worked example
Suppose a 4-element weight group has values [3.2, 0.5, 2.8, 1.1].
The 2:4 mask selects positions 0 and 2: [1, 0, 1, 0].
Naive result after masking: [3.2, 0, 2.8, 0] – keeps the two largest by accident.
ARMOR: left rotator tilts the input to [2.1, 1.8, 0.9, 2.5], then mask keeps [2.1, 0, 0.9, 0].
Right rotator untilts: [2.1, 0, 0.9, 0] becomes [3.0, 0.1, 2.9, 0.05].
The output is closer to [3.2, 0.5, 2.8, 1.1] than naive would be, so model stays more accurate.

The rotators are learned to align the most important weight directions with the positions the sparsity pattern will keep.

What can go wrong

Calibration data mismatch. If the calibration batch is not representative of real text the model will see, the proxy loss gives the wrong signal about which weights matter. The rotators learn to preserve the wrong directions.
Rotators need careful hardware integration. The rotators are two extra dense matrix multiplies per layer. Dense means no sparsity savings; they execute at standard speed. The sparse core benefits from specialized 2:4 instructions on modern chips. If your hardware runs the three operations (left rotator, sparse core, right rotator) one after another with gaps in between, the two rotators add latency on top of the sparse multiply, potentially erasing gains in wall-clock inference speed. On hardware that can fuse the three into a single pipelined operation (all three run in parallel through the execution pipeline rather than sequentially), the overhead stays small because the rotators hide their latency inside the sparse core's execution window.
Block size tuning. The rotators are block-diagonal with a fixed block size (e.g., 128 or 256). If the block is too large, the rotation cannot target fine-grained importance patterns. Too small, and you lose the computational benefit.
Done right. The method is one-shot (no retraining needed) and comes with a proof that convergence is guaranteed. Pick calibration data from the training corpus and pick text similar to what the model will see in the real world.
What a runnable demo should prove

What a runnable demo should prove

Build a tiny language model (for speed), apply ARMOR to one layer with 2:4 sparsity, and measure the proxy loss and the actual downstream task accuracy. Show that: (1) the rotators shrink the proxy loss more than naive 2:4 baseline, because they choose a basis that avoids deleting important directions; (2) the actual model accuracy on a held-out text sample is better with ARMOR, because the pruning loses less information about the data patterns the model learned; (3) the rotators can be applied at inference time with minimal computation overhead, because block-diagonal structure means each block does its own small multiply without cross-communication (showing that the memory savings from sparsity are not canceled out).

Accuracy drop = accuracy_before_pruning - accuracy_after_pruning; ARMOR drop should be smaller than naive 2:4 drop

The demo must show that ARMOR's rotators do genuine work: they pick a sparsity pattern that hurts less than a random pattern (because the tilted basis puts less important directions in the deletion slots), and the overhead is small enough that the final model is faster and lighter (because the block-diagonal multiplies are cheap compared to the speedup from 2:4 sparsity on actual hardware).
