δ-Adapter: Post-Processing Shifts for Time Series

A tiny add-on module nudges the inputs and tweaks the outputs of a frozen forecaster, improving accuracy and trust without retraining.

Paper explainersAll themesTime Series & Sequential

When a time-series forecaster (a model that predicts the next values in a sequence) is already deployed, retraining it is costly and risky. This paper introduces a slim post-processing module that lives outside the forecaster and makes small, learned corrections at the boundaries—gently shifting the input data the forecaster sees and patching the numbers it outputs. The method works on any forecaster, keeps the original model untouched, and needs almost no extra compute.

Zero assumption version

The deployed forecaster is stuck

A time-series forecaster is a model trained to look at recent data (the history) and predict the next few values (the forecast). Once deployed, you want it to get better with new data: either more accurate predictions (lower error because new patterns are captured) or more honest estimates of how sure it should be (confidence intervals that actually match reality because they adapt to new data characteristics).

The naive approach: retrain the entire model on new data. This is slow, risky (old knowledge can vanish), and often not possible if the model is locked away behind an interface. A forecaster works until it does not, and by then you have no direct access to its internals.

In one sentence. Learn a tiny external module that tweaks inputs going in and outputs coming out, with changes bounded to stay small, while the original forecaster stays completely frozen.

The algorithm as a flow

What it actually does

Step 1: Freeze the forecaster

Take the deployed model and mark it as read-only. Do not change any of its weights.

Step 2: Train an input nudger

Learn a small network that reads the raw input data and outputs tiny edits—which features to lift, which to dampen, which horizon (time ahead) matters most.

Step 3: Train an output corrector

Learn another small network that reads the frozen forecaster's prediction and its inputs, then outputs a residual (a patch): how much to add or multiply to the forecast.

Step 4: Add calibrators for honesty

Train modules that learn uncertainty: quantile offsets (offset the point forecast up and down for confidence intervals) and conformal scaling (learn how wide intervals should be in different situations).

Step 5: Deploy as a sandwich

The frozen forecaster stays in the middle. Inputs enter through the nudger, outputs exit through the corrector and calibrators. Zero changes to the forecaster itself.

What the paper changes

The thing that moves

The paper moves three things: the input data (before it reaches the forecaster), the output numbers (after the forecaster predicts), and the uncertainty estimates (the width and shape of confidence intervals). But all three stay bounded—the edits are small, controlled by a correction bound that keeps changes tiny.

The hidden quantity

The hidden quantity: Local descent correlation

measured quantity  =  Descent direction alignment

The paper measures a hidden quantity: how well the learned input nudge points in the same direction as the direction that shrinks the forecasting error. Think of error as a surface: some directions make error smaller (downhill), others make it larger (uphill). The learned input nudge should point downhill. Or at minimum, should not point uphill.

The paper estimates this alignment implicitly: when you train the input adapter on real data, it discovers which edits shrink the loss (error). If the edits point in the downhill direction, loss decreases. The paper proves that when this alignment is strong enough, the forecast error strictly shrinks even though the forecaster itself never retrains.

Why it works

Why it works: Three tiny forces

The core trick is that even though the forecaster is frozen, the data around it is not. An input nudge is a learned redescription of the input—emphasizing what the forecaster is blind to, or dampening signals that confuse it. If you can figure out which edit (which small change to the input) would shrink the error, you apply that edit before the frozen forecaster sees it. The forecaster then makes a better prediction because it is looking at a better-curated version of the same data.

The output corrector works because forecasters are rarely perfect. They tend to systematically under-predict or over-predict in certain contexts—confidence is too high in some regimes, too low in others. A tiny learned network that reads both the forecast and the raw input can spot these patterns and patch them: if the forecaster always undershoots when variance is high, add a compensation term proportional to variance. These corrections are bounded (they cannot be too large), so they never override the main forecast but can nudge it in the right direction.

Calibrators (quantile and conformal) go a step further: they learn to be honest about uncertainty. A quantile calibrator learns offset functions—how much to add to or subtract from the point forecast for a 90% confidence interval in this particular data regime. A conformal calibrator learns a scale function that makes intervals wider or narrower based on patterns in the residuals (the differences between past forecasts and true values). Both can be trained on new data without touching the forecaster.

Math after the picture

The equation: Bounded residual correction

First in words:

The output-corrected forecast equals the original forecast plus a learned residual, bounded by a scale factor delta. The residual can be additive (add a fixed offset) or multiplicative (multiply by a small factor near 1). Training minimizes the loss of the corrected forecast while keeping the original forecaster frozen.

Then the compact form:

Ỹ = F(X) + δ·A_out(F(X), X) (additive) Ÿ = F(X) ⊙ (1 + δ·A_out(F(X), X)) (multiplicative) where A_out is the learned correction network, δ bounds the magnitude of correction, X is input, F(X) is frozen forecast.

Every symbol:

Ỹthe corrected forecast (what we output)
F(X)the frozen forecaster's original prediction
A_out(F(X), X)the learned output correction, reads both forecast and raw input
δa small bound on how large corrections can be
⊙element-wise multiply (scale each output separately)
A tiny worked example
Suppose the frozen forecaster predicts next-day temperature as 72 degrees (F(X) = 72).
The output adapter learns A_out = +3 (add 3 degrees in this regime: high recent variance, evening hour).
Set δ = 0.1 (corrections limited to 10% of prediction magnitude).
Corrected forecast: Ỹ = 72 + 0.1 × 3 = 72.3 degrees.
The adapter learned to nudge +3, but δ constraint caps it at +0.3. Now suppose δ = 0.5 instead.
Corrected forecast: Ỹ = 72 + 0.5 × 3 = 73.5 degrees. Larger δ lets more correction through.
Training adjusts A_out to minimize error on new data. If true temps turn out near 73–74, the network learns bigger corrections; if near 72, it learns zero. The δ bound prevents runaway edits.

The correction bound is the key safety valve: it lets the adapter help, but prevents it from overwriting the forecaster's core logic because if the bound is small enough, the correction is just a nudge (10% or less of the forecast), not a complete replacement.

What can go wrong

What can go wrong

Overfitting the adapter. If you train the adapter on too little new data or with no regularization, it learns spurious patterns that do not generalize. The fix: use regularization (add a penalty for large corrections) and validate on held-out test data.
Overshooting the correction bound. If the correction bound is set too large, the adapter stops being a gentle nudge and becomes a major override—essentially retraining the forecaster in disguise. The forecaster's core stability is lost. The fix: tune the bound on a separate validation set and keep it small.
Concept drift faster than the adapter learns. Time series can shift in distribution over months or years. A static adapter, trained once, may grow stale. The fix: retrain adapters periodically or use online learning to update them incrementally.
Done right. The frozen forecaster is treated as a black box. The adapter learns only from new data on the side. Corrections are bounded, regularized, and validated. The original model interface never changes, so deployment is transparent.
What a runnable demo should prove

What a runnable demo should prove

Build a simple time-series forecaster (e.g., a linear regression or shallow neural net trained on the first 80 days of a stock price or temperature dataset). Deploy it as frozen. Collect 20 days of new data. Train a tiny post-processor (a 2-layer network for input nudging, a 2-layer network for output correction) on this new data for 50 epochs. Measure accuracy (mean absolute error, or MAE) before and after the adapter. Measure how well the uncertainty intervals (from the quantile calibrator) match the true coverage—if you claim 90% confidence, does the actual interval contain the true value 90% of the time?

Accuracy gain = MAE_before - MAE_after Calibration = (claimed_coverage - actual_coverage)^2 Compute cost = training_time_adapter / training_time_original

The demo must show: (1) MAE improves by at least 5–10% with the tiny adapter because the adapter learned to nudge inputs toward more predictable states and correct systematic biases; (2) uncertainty intervals are honest (coverage matches claim) because the calibrators learned patterns in residuals that reveal when the forecaster is uncertain; (3) adapter training is orders of magnitude faster than retraining the original forecaster because the adapter has far fewer weights and the main forecaster never changes.
