Towards High-Fidelity CAD Generation via LLM-Driven Program Generation and Text-Based B-Rep Primitive Grounding

Generate a CAD program and then ground its shape references to the right faces, edges, and solids so that advanced operations run on the intended parts.

Paper explainersAll themesAgents & Tool Use

Modern CAD work mixes two things that must agree: a step-by-step construction program and the concrete shape pieces that each step touches. Many systems handle those parts separately, which breaks down on industrial designs because later operations such as fillets and chamfers only work when the program points at the right geometric pieces. FutureCAD joins program writing with geometric grounding, because the generated script is only useful if each operation acts on the intended faces, edges, and bodies.

Why text-to-CAD breaks on real feature-based design

A realistic CAD object is not only a final shape. It is also a sequence of operations such as sketching, extruding, cutting, rounding, and beveling. Those operations depend on exact geometric selections, so a later step can fail even when the earlier text description was mostly understood.

Many earlier systems choose between two incomplete views. One view writes a construction program but struggles to point at the right geometric pieces. The other view tries to produce the final boundary shape directly but loses the editable feature sequence. Industrial design needs both, because engineers want a script that runs and a model that stays editable.

The paper's move in one sentence. Write an executable CadQuery script and let a separate grounding module map text references such as rounded top edge or inner side face to the actual geometric pieces that the script should use.

What the paper changes

What the paper changes

The paper changes the interface between program writing and shape editing. Instead of forcing the writer to produce fragile low-level selections directly, it lets the writer name geometric targets in text and hands those names to a grounding module.

The hidden quantity

The hidden quantity

measured quantity  =  which exact geometric primitive each high-level edit is supposed to touch

The hardest missing fact is not the broad object category. It is the exact local target of each edit. When a user asks for a rounded outer corner or a beveled inner rim, the system must decide which edge or face that phrase refers to inside the current partially built shape.

FutureCAD makes that hidden choice explicit. The writer states the intended target in words, and the grounding module resolves that description against the current shape state. This helps because many later CAD operations fail only when the local target is wrong, even if the rest of the script is reasonable.

Why it works

Why this works: separate writing the plan from choosing the exact shape target

Program writing and geometric grounding are related but not identical jobs. A single writer can describe the intended construction sequence, yet still struggle to point at the exact local shape piece after several earlier edits have changed the shape. The two-part design helps because the writer handles the high-level sequence while the grounding module resolves local references against the current shape.

The new dataset and reward-based training matter as well. Real industrial models contain the complicated feature interactions that toy shape collections miss, so training on those cases teaches the system where local geometric references become difficult. The reward phase then favors scripts that actually execute and match the target object, because a good script must stay valid all the way through the final edit.

Reward scripts that both run and pick the right shape pieces

First in words:

A compact summary is to score a generated CAD script by asking whether it executes successfully, whether its grounded selections are correct, and whether the final shape matches the target design.

Then the compact form:

cad_score(script) = execute_ok(script) + alpha * grounding_match(script) + beta * shape_match(script)

Every symbol:

cad_score(script)overall value of one generated CAD program
execute_ok(script)whether the script runs without failure
grounding_match(script)how often the text-based selections land on the intended faces, edges, or bodies
shape_match(script)how closely the final constructed object matches the target design
alpha, betaweights on selection quality and final shape quality
A tiny worked example
Script A runs, but it rounds the wrong outer edge.
Its execution term is 1, its grounding match is 1, and its shape match is 4.
Script B runs and selects the intended inner rim before applying the round.
Its execution term is 1, its grounding match is 4, and its shape match is 5.
Training prefers Script B because correct local grounding improves the final model.

The paper uses a fuller training setup, but this summary captures the main idea that executable code alone is not enough when local shape references are wrong.

What can go wrong

What can go wrong

Text descriptions can still be ambiguous. If several edges fit the same phrase, grounding may choose the wrong one because the request did not include enough local detail.
Early script mistakes can corrupt later grounding. A wrong extrude or cut changes the partial shape, so later face and edge references may stop matching the intended object.
Real CAD systems contain tool-specific quirks. A script that works in one construction library may still need adaptation elsewhere because operation semantics can differ across tools.
Done right. The framework matters because it turns geometric selection into an explicit learned step instead of hoping the writer gets every local reference correct by chance.

What a runnable demo should prove

Build a text-to-CAD demo with tasks that require local feature edits such as fillets, chamfers, holes, and cutouts. Compare a plain script writer against a FutureCAD-style system that writes the script and then grounds text descriptions of geometric targets before execution.

The demo should log three things: whether the script runs, whether each local selection hits the intended primitive, and how close the final object is to the target model. The grounded system should win because correct local references prevent later edit steps from drifting onto the wrong shape piece.
