IntentRL: Training Proactive User-intent Agents for Open-ended Deep Research via Reinforcement Learning

Ask targeted clarification questions before a long research run so the agent works toward the user's real goal instead of a guessed goal.

Paper explainersAll themesAgents & Tool Use

Long-horizon research agents can search, read, and write for many minutes before returning a report. That autonomy is useful only when the starting request is clear enough. If the request is vague, the agent may spend a large amount of time pursuing the wrong target because it committed too early. IntentRL trains the agent to pause first, ask clarifying questions when intent is uncertain, and only then launch the expensive research process.

Why vague research requests waste work

A deep research agent faces a hard choice at the start of a task. It can ask the user for more detail, or it can start searching immediately. Starting early looks efficient, but it often goes wrong because many open-ended requests hide missing constraints such as audience, time range, comparison target, or desired output style.

Once the agent begins a long run, each wrong assumption multiplies into wasted searches, bad evidence selection, and a report that misses the user's real aim. IntentRL focuses on the first decision: when should the agent clarify, what should it ask, and how should it adapt after the user answers.

The paper's move in one sentence. Train the agent to treat clarification as part of the task itself so that expensive research begins only after the user intent is identified well enough.

The algorithm as a flow

What it actually does

Create training dialogues

Start from a small set of seed cases and expand them into richer clarification dialogues that expose hidden user intent.

Train on offline interaction data

Teach the agent general clarification behavior from prepared conversations because this stage is cheaper than full live rollouts.

Continue with simulated live interaction

Run the trained agent against a user simulator so that it learns to adapt when feedback changes across turns.

Decide whether to clarify or proceed

At the start of a task, estimate whether current intent information is sufficient for a long run.

Measure intent match and downstream task quality

Check whether the agent both identifies the user's target and produces better final research outputs because of that identification.

What the paper changes

What the paper changes

The paper changes the opening policy of a research agent. Instead of treating clarification as an optional extra, it trains clarification as a core decision that shapes the whole downstream search and writing process.

The hidden quantity

Intent uncertainty: the hidden quantity

measured quantity  =  How much missing user intent still matters before research starts

The central hidden quantity is unresolved intent uncertainty. A user request can sound specific while still hiding a missing choice that will later determine which evidence is relevant, which comparisons matter, and what form the report should take.

IntentRL tries to estimate whether the current request leaves enough unresolved uncertainty that a clarification question is worth the delay. That estimate matters because asking too much slows the system, while asking too little sends the whole research run in the wrong direction.

Why it works

Why this works

Clarification helps because it changes the whole search tree before expensive work begins. A single answer about audience, scope, or comparison target can remove many bad branches, so the agent spends less effort gathering evidence that will later be discarded.

The two-stage training plan helps because offline dialogue data teaches broad clarification habits cheaply, while later simulated interaction teaches adaptation to diverse user replies. The final policy improves downstream reports because the agent enters the research stage with a task target that is better aligned to the user's actual intent.

A simplified clarify-or-proceed rule

First in words:

Estimate how costly it would be to start research now with the current intent guess, compare that with the cost of asking one more question, and clarify when the expected downstream error is larger.

Then the compact form:

clarify_if = expected_report_error_without_question - question_cost ; ask when clarify_if > 0

Every symbol:

expected_report_error_without_questionthe expected quality loss if the agent starts research before resolving missing intent
question_costthe extra delay or interaction cost from asking a clarification question
clarify_ifthe net value of asking before starting the long run
A tiny worked example
Suppose a user asks for a market report but does not say whether the target is investors or product managers.
If the agent starts immediately, it may gather the wrong evidence and write the wrong style of report.
Assume that expected report error from skipping clarification is 0.6 on a 0 to 1 scale.
Assume that asking one question costs 0.1 because it adds only one short turn.
Since 0.6 - 0.1 is positive, the agent should ask because the saved downstream error is larger than the delay.

The real system uses reinforcement learning over dialogues, but the core decision is direct: ask when one more user turn is worth more than the cost of a wrong long-horizon run.

What can go wrong

What can go wrong

The agent can over-question. If the policy asks for details that do not change the later search plan, interaction becomes slow because the agent adds friction without real benefit.
A simulator may teach the wrong habits. Online training with a user simulator helps scale, but it can bias the policy if simulated replies differ from real users because the agent will adapt to the wrong feedback style.
Some users do not know their own constraints yet. Clarification cannot fully solve ambiguity when the user has not decided what they want because even a well-phrased question may still produce unstable goals.
Done right. Ask only the questions that change the later research plan, and evaluate on both intent match and final report quality so that clarification is rewarded only when it improves the end task.
What a runnable demo should prove

What a runnable demo should prove

Build a small research assistant with two modes. In the first mode it starts searching immediately from the initial request. In the second mode it can ask one or two clarification questions before search begins. Feed both modes ambiguous tasks whose hidden constraints affect evidence choice, report structure, or comparison targets.

The demo should prove that a short clarification stage improves final report fit because the agent avoids large wrong branches early, and that the gain is strongest on requests where missing constraints would otherwise change the whole research plan.

intent_gain = intent_match_with_clarification - intent_match_without_clarification ; task_gain = report_score_with_clarification - report_score_without_clarification

A useful demo shows that one well-chosen question can save a long amount of wasted research.
