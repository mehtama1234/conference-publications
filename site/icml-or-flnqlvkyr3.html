SkillTrojan: Backdoor Attacks on Skill-Based Agent Systems

SkillTrojan hides malicious code inside reusable agent skills, spreading it across innocent-looking tool calls so it runs undetected when triggered.

Paper explainersAll themesAlignment, Safety & Fairness

Agent systems work by breaking hard problems into small reusable pieces called skills, like a library of helper functions. SkillTrojan shows how an attacker can hide malicious code inside these skills and activate it only when a trigger phrase appears, bypassing safety checks that focus on the model itself.

Zero assumption version

Skills open a new attack path

Agent systems compose reusable skills to solve tasks, like assembling tools from a toolbox. A skill is a frozen piece of code that does one job: fetch weather, query a database, search the web. The agent learns to pick and chain these skills. Current safety checks watch the model's behavior: does it say mean things? Does it ask for harmful actions? But they do not watch the skills themselves. If an attacker can sneak malicious code into a skill library that many agents reuse, that code runs as trusted code, inside the agent's sandbox, with the same permissions as legitimate skills.

A beginner might try to block all skill execution without trust. But that breaks the entire premise: agents need skills to do anything. Or they might scan skills for obvious bad code before loading them. But this fails when the attacker encodes the malicious logic so it is encrypted and scattered across multiple innocent tool calls, reconstructing only when a secret phrase appears.

The attack in one sentence. Split malicious code into encrypted pieces, hide the pieces inside benign skill outputs, and assemble them only when the agent sees a trigger phrase, so normal safety checks miss it.

The algorithm as a flow

What it actually does

Attacker builds a backdoored skill

Takes a normal skill template (e.g., database query), injects malicious code encrypted and split into fragments.

Fragments scatter into tool outputs

When the backdoored skill runs, each call writes one encrypted piece to a side channel (log of tool results, scratchpad, return values).

Trigger phrase activates the attack

Only when a secret predefined phrase shows up in the user query do fragment emitters activate and begin scattering pieces.

Verification tool collects and assembles

A planted verification tool gathers scattered pieces from the log, concatenates them, decrypts with the embedded key.

Payload executes inside the agent

Decrypted code runs in the skill execution environment with all agent permissions, undetected by external monitors.

What the paper changes

What the attack changes

SkillTrojan modifies the skill implementations (the reusable code blocks that agents call) by hiding encrypted malicious logic inside their normal operation. The agent system itself is not changed; neither is the model's code. Only the third-party skills are compromised, so the attack spreads silently through any agent that reuses those poisoned skills.

the object it moves  =  Skill code
The hidden quantity

Payload fragmentation: the quantity that enables the attack

measured quantity  =  Fragment count and placement

The key quantity the paper measures is fragment count—how many pieces the payload is split into and across which skills. The more fragments scattered across different skills and different tool calls, the harder it is for a static detector or log auditor to spot the attack. The paper shows that even with just 2 or 3 fragments spread across normal-looking tool outputs, a detector scanning for unusual data patterns misses it entirely.

The paper estimates this by testing different fragment counts and showing the relationship: fewer fragments mean higher chance of detection; more fragments mean the attacker needs more skill reuse and creates wider execution traces, which might trigger execution-aware anomaly detectors. The sweet spot is around 2 to 4 fragments—high success, low overhead.

Why it works

How hiding across multiple calls defeats detection

The core mechanism relies on the fact that each individual skill output looks legitimate in isolation. A database query returns rows of data, a web search returns a snippet, a calculator returns a number. If the attacker hides one encrypted fragment in each output, a human or static tool inspecting any single call sees only noise that could be cache or metadata. The fragments are small, benign-looking, encrypted so they reveal no pattern.

Detection works by looking for anomalies: either suspicious new data in outputs, or suspicious new code in the skill implementations. SkillTrojan defeats the first by spreading fragments so no one output is large or unusual enough to trigger alerts. It defeats the second by keeping the skill implementation minimal and deterministic—only a few lines of code to write a fragment or check for the trigger. The real payload hides in encrypted data, not in visible code. The attack then exploits the agent's own logging: tool results are already captured and available in the execution context, so a verification tool can quietly collect fragments in plain sight as it processes logs. By the time the attacker-controlled verification tool reassembles and decrypts, the payload runs inside the agent sandbox where external inspectors cannot intercept it.

Math after the picture

The payload encryption and reconstruction formula

First in words:

Plaintext payload gets encrypted once with a secret key, then the ciphertext is split into N parts and embedded across N different skill outputs. During execution, each triggered skill writes its fragment to the shared log. A verification tool then reads all N fragments in order, concatenates them, and decrypts using the same secret key to recover the original payload.

Then the compact form:

Payload_in = P, Encrypted = Enc(P; key_k), Fragments = {frag_1, frag_2, ..., frag_N}, Recovered_P = Dec(frag_1 || frag_2 || ... || frag_N; key_k)

Every symbol:

Pthe attacker's malicious payload (arbitrary executable code)
key_kthe symmetric encryption key known only to attacker
Enc(P; key_k)encrypt payload P using key k to get ciphertext
frag_ithe i-th encrypted fragment, scattered across outputs
||concatenation (joining all fragments in order)
Dec(...; key_k)decrypt the concatenated ciphertext using key k
A tiny worked example
Attacker payload P = 'delete_all_records_in_table'
Encrypt with key k=12345: Enc(P; k) = 'x7f2e9a4b1c8d'
Split into 3 fragments: frag_1='x7f2', frag_2='e9a4', frag_3='b1c8d'
Skill-1 on trigger writes 'x7f2' to log as junk metadata
Skill-2 on trigger writes 'e9a4' to log as part of a result
Skill-3 on trigger writes 'b1c8d' to log as a side value
Verification tool concatenates: 'x7f2' + 'e9a4' + 'b1c8d' = 'x7f2e9a4b1c8d'
Decrypt: Dec('x7f2e9a4b1c8d'; 12345) = 'delete_all_records_in_table'
Payload executes inside agent with database access.

The payload stays encrypted and scattered until the attacker's verification tool actively reconstructs and decrypts it inside the agent's execution context, where external monitors cannot see the final malicious code.

What can go wrong

What can go wrong

Trigger phrase detection by input monitors. If a safety system watches for known trigger phrases in user queries before passing them to the agent, the attack never activates. Mitigation: attacker can randomize trigger phrasing or embed it as a hidden instruction in benign-looking context.
Fragment detection in tool logs. If an auditor monitors tool outputs for unexpected new fields or anomalous data patterns, frequent fragment writes could stand out. Mitigation: space fragments across many tool calls and encode them to look like plausible metadata.
Verification tool discovered. The verification tool that collects and decrypts fragments is itself a skill. If defenders audit skill codebases for suspicious operations (collecting outputs, decryption, payload execution), it may be flagged. Mitigation: disguise it as a logging or monitoring utility.
Done right. When the attacker carefully tunes the fragment count, spreads across diverse benign-looking outputs, uses a generic-sounding trigger, and embeds verification as part of normal diagnostic logging, the attack remains stealthy while maintaining clean task performance.
What a runnable demo should prove

What a runnable demo should prove

A demo should show a simple agent system (e.g., one that queries a toy database or web API using reusable skills) where an attacker has backdoored one or two skills. When the agent runs a normal query, all tasks complete correctly and no malicious code executes—clean accuracy is preserved. When the agent processes a query containing the trigger phrase, the scattered fragments assemble inside the logs, the verification tool decrypts the payload, and the malicious code runs with agent permissions (e.g., modifying database results, exfiltrating data, or sabotaging downstream decisions). The demo should measure two metrics: the accuracy on clean queries (should stay above 90 percent) and the attack success rate on triggered queries (should exceed 95 percent), showing that the attacker gets both stealth and effectiveness.

Clean_Accuracy = (correct_tasks_without_trigger) / (total_tasks_without_trigger); Attack_Success = (payload_executed_correctly_with_trigger) / (total_triggered_queries)

The core result: with 3 fragments spread across ordinary tool outputs, the attack succeeds reliably while static inspection and clean-task testing miss it entirely, exposing the gap between skill-level and model-level security monitoring.
