AgentTailor: A Semantic-Aware LLM-Based Multi-Agent System with Actor-Critic Structure

Cut wasted agent-to-agent chatter by estimating which communication links add decision value and pruning the links that do not.

Paper explainersAll themesAgents & Tool Use

Multi-agent systems often spend a large share of their budget on agents talking to one another. More communication can help only when a message changes the final decision because a repeated or irrelevant message adds cost without adding new evidence. AgentTailor asks a sharper question than most earlier work: which communication edges are actually useful? It scores edges by their semantic contribution, then trains a lightweight predictor to estimate that usefulness through virtual execution before paying for the full model calls. The result is a communication structure that keeps the helpful links and drops the redundant ones.

Zero assumption version

Why more agent communication is not always better

In a multi-agent system, one agent often sends its intermediate conclusion to several others. That can be useful when the message changes how the receiver reasons. It is wasteful when the receiver already had the same evidence or when the message adds detail that never affects the final answer.

Many systems optimize communication only at the structural level: who is connected to whom. But that misses the real issue. Two edges with the same shape can have very different value depending on what they transmit. AgentTailor focuses on semantic contribution, meaning whether a specific communication edge actually improves the final decision because it carries evidence that the receiver did not already have and that evidence changes the receiver's choice.

The paper's central claim. A communication edge should survive only when the message it carries changes the final decision enough to justify its cost.

The hidden quantity

The hidden quantity

measured quantity  =  edge utility

The key hidden quantity is the value of one communication edge. An edge has high utility when the message changes a receiver's reasoning enough to improve the final answer because it introduces evidence or correction that alters the receiver's choice. It has low utility when the message is redundant, stale, or irrelevant.

AgentTailor makes this quantity operational. It tries to predict edge utility before paying to send the full message. That matters because cost falls only when the system can identify wasted edges ahead of time, not after the budget is already spent.

Why it works

Why edge prediction saves budget without collapsing quality

The method separates message value estimation from full message generation. Full multi-agent communication is expensive because each live edge can trigger another model call and another growing context. If the system can cheaply estimate that an edge is unlikely to help, it can suppress that edge before spending the budget because the edge would add cost without adding enough new evidence to change the answer.

The edge prediction network is useful for exactly that reason. It performs a lightweight virtual execution step that estimates whether the message along an edge is likely to improve the final decision. Helpful edges are kept because they are expected to influence the answer. Weak edges are dropped because they mostly repeat what other agents already know. The paper's reported savings make sense because the system removes low-value exchanges rather than just shrinking every message uniformly.

Math after the picture

A simple keep-or-drop rule

First in words:

keep an edge only when predicted utility is greater than its cost threshold

Then the compact form:

KeepEdge(i,j) = 1 if UtilityHat(i,j) > tau, else 0

Every symbol:

KeepEdge(i,j)whether the communication edge from agent i to agent j stays active
UtilityHat(i,j)predicted contribution of that edge to the final decision
tauthe minimum utility required to justify keeping the edge
A tiny worked example
Suppose edge A->B has predicted utility 0.72 and edge C->B has predicted utility 0.18.
Set the threshold tau to 0.30.
Then KeepEdge(A,B) = 1 because 0.72 > 0.30.
KeepEdge(C,B) = 0 because 0.18 <= 0.30.
The second edge is dropped because its expected decision gain is too small to justify another message.

The paper's implementation is richer, but the core decision is this: keep an edge only when its expected contribution clears a cost-aware threshold.

What can go wrong

What can go wrong

A useful edge can be pruned by mistake. If the predictor underrates an edge that carries rare but important evidence, the final decision can suffer because that evidence never reaches the right agent.
Utility can change during the task. An edge that was weak early can become valuable later, because new evidence changes what other agents still need to hear.
Virtual execution can be too coarse. If the lightweight predictor does not approximate real interaction closely enough, it may keep cheap but unhelpful edges or drop expensive but necessary ones.
Done right. The system should re-estimate edge value as the task evolves so the communication graph follows the information needs of the agents rather than staying frozen.
What a runnable demo should prove

What a runnable demo should prove

Build a four-agent system for a classification or reasoning task where each agent sees a different slice of evidence. Run one version with all communication edges active and a second version with an edge predictor that can suppress low-value links before messages are sent.

Measure final accuracy, number of active edges, and total message cost. The demo should show that the tailored graph keeps accuracy high because it preserves the few edges that actually change the final answer while removing many exchanges that do not.

efficiency = accuracy / communication_cost

If efficiency rises after pruning, the system is learning which conversations are worth paying for.
