ExpWeaver: LLM Agents Learn from Experience via Latent RAG

Store past experience in the model's internal state so the agent can reuse it without copying long text memories into every prompt.

Paper explainersAll themesAgents & Tool Use

Agents often improve by reusing earlier experiences. A common approach retrieves text snippets from memory and appends them to the prompt. That helps, but it also enlarges the context window and keeps retrieval separate from generation. ExpWeaver moves memory use inside the model's own internal processing so that the agent can pull in relevant earlier experience during generation without repeatedly pasting long text memories.

Why text-memory retrieval is costly

Experience-based agents often keep a memory bank of earlier interactions and retrieve the most relevant text passages for a new task. This has two costs. First, every retrieved passage consumes context space, which raises expense and can crowd out current evidence. Second, retrieval and generation are separate modules, so the model cannot adapt memory use jointly with the rest of its generation process because the retrieval stage is optimized separately from the answer-writing stage.

The paper asks whether an agent can learn from experience without constantly copying old text back into the prompt. ExpWeaver answers yes by storing and retrieving experience through the model's internal representations during generation, so that memory use can be trained together with answer generation.

The paper's move in one sentence. Turn past experiences into internal memory states that can be queried during generation, then train retrieval and use of that memory end to end.

What the paper changes

What the paper changes

The paper changes where experience lives. Instead of attaching earlier examples as extra text, it stores them in internal memory states that are read during generation.

The hidden quantity

Memory relevance: the hidden quantity

measured quantity  =  How useful a past experience is for the current generation step

The key quantity is step-level memory relevance. A past experience may help strongly at one point in generation and be useless at another because different output steps need different evidence. Good memory use therefore needs two decisions: which experience to retrieve and how much of it to mix into the current state.

ExpWeaver estimates this hidden quantity inside the model's internal state during generation. Because retrieval happens at each step, the system can adapt memory use continuously instead of choosing one fixed set of text snippets at the start.

Why it works

Why this works

Internal memory retrieval cuts prompt overhead because earlier experiences no longer need to be pasted back as long text. That leaves more room for current evidence and reduces cost tied to context length.

Joint training helps because the model can learn retrieval and memory use together. A separate text-memory module may return relevant passages, but the generator still has to decide how to use them. ExpWeaver learns both pieces inside one system, so memory selection and memory application can adapt to each other.

Math after the picture

A simplified memory update

First in words:

At each generation step, compute a relevance score between the current state and stored experiences, combine the retrieved memory with the current state, and let a gate decide how much of that retrieved information should affect the next output.

Then the compact form:

state_next = current_state + gate * retrieved_memory ; retrieved_memory = sum_j weight_j * memory_j

Every symbol:

state_nextthe updated internal state used to generate the next output
current_statethe model's current internal processing state
gatea value between 0 and 1 that controls how strongly memory is mixed in
retrieved_memorythe combined memory signal pulled from earlier experiences
weight_jhow relevant memory j is to the current state
memory_jstored internal representation of past experience j
A tiny worked example
Suppose the current task resembles two earlier experiences.
The relevance weights are 0.7 for memory A and 0.2 for memory B, with the rest near 0.
Retrieved memory becomes mostly memory A with a small contribution from memory B.
If gate = 0.8, the model uses most of that retrieved signal because it appears strongly relevant.
If gate later drops to 0.1, the model relies mainly on the current task state because old experience is no longer very helpful.

The paper uses a richer internal mechanism, but the core idea is direct: retrieve relevant earlier experience during generation and control how strongly it affects the next step.

What can go wrong

What can go wrong

Internal memory is harder to inspect. A text-memory system lets you read what was retrieved, while an internal-state memory system is less transparent because the stored signals are not plain text.
Wrong memory can still be retrieved. If the relevance scoring is off, an unhelpful past experience may influence the answer because the model pulls it into the current step.
Joint training can be unstable. Retrieval and generation are now coupled, so a weakness in one part can hurt the other because both are learned together.
Done right. Compare against a strong text-memory baseline, measure prompt overhead directly, and test transfer so that memory quality is judged on both usefulness and efficiency.
What a runnable demo should prove

What a runnable demo should prove

Build a small agent that solves repeated tasks and stores each solved case as memory. Compare two versions: one that retrieves earlier cases as text and appends them to the prompt, and one that retrieves compact internal memory signals and mixes them into generation. Measure answer quality, prompt length, and transfer to a new task category.

The demo should prove that experience reuse does not need large text memories because internal retrieval can preserve task quality while reducing prompt overhead, and that the benefit carries across domains when relevant earlier cases exist.

efficiency_gain = task_score / prompt_length ; transfer_gain = new_domain_score_with_memory - new_domain_score_without_memory

A useful demo shows that the agent remembers past work in a form it can reuse cheaply.
