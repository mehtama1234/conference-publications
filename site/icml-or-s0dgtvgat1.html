Sonar-TS: Search-Then-Verify for Time Series Databases

When you ask a database a question about shapes in time series, split the search into two steps: fast SQL to find candidate windows, then Python code to verify which ones really match.

Paper explainersAll themesTime Series & Sequential

Imagine searching for a pattern in years of stock prices: you want to find all the times the price rose quickly, then fell. A regular database can find numbers, but it cannot understand shapes like "rapid rise then fall." A machine-learning model could understand the shape, but it cannot read billions of data points without running out of memory. Sonar-TS splits the job: SQL finds candidate windows using pre-computed summaries, then Python code checks which ones truly match the shape you described.

Zero assumption version

Two worlds that do not talk

Databases are fast at finding numbers: "Which rows have temperature above 80?" But they cannot understand continuous shapes. Ask a database to find "periods when temperature spiked then plateaued" and it fails, because shapes live in signals, not in individual rows.

Machine-learning models understand shapes perfectly. Feed them years of stock prices and they spot patterns instantly. But these models have a hidden memory limit (called context length): they can only ingest a few thousand data points at a time. Real databases store millions or billions of points. A model cannot swallow them all.

A beginner tries one of two things: (1) Pass the entire history to a model and watch it run out of memory, or (2) Use SQL alone and admit it cannot understand the shape you want. Sonar-TS refuses both.

The move. Use SQL to fast-scan pre-made summaries and find candidate windows, then use Python to verify each candidate against the raw signal.

What the paper changes

The single change

Sonar-TS changes WHERE the query plan executes: instead of trying to do all the work in one place (either SQL or a model), it splits the work. SQL handles coarse-grained filtering on summaries; Python handles fine-grained verification on raw data. This split is the engine of the whole system.

The hidden quantity

The window candidate pool size

measured quantity  =  candidate window pool

The hidden quantity is how many windows pass the SQL filter before verification begins. If the feature index (SAX codes, trend slopes, etc.) finds 10,000 candidates out of a billion possible windows, the verification step only has to check 10,000, not a billion. The tighter the SQL filter, the fewer candidates Python has to verify. Fewer candidates means the system finishes faster because Python loads and checks less data, and the overall latency is dominated by that verification cost.

Sonar-TS estimates this by building a multi-scale feature index offline. Each window in the database gets a SAX code (a short letter sequence that captures the shape roughly) and other summaries. At query time, SQL uses fuzzy regex matching against these summaries to find candidates. The paper shows that a good feature index cuts the search space from billions to hundreds or thousands, making verification tractable.

Why it works

Why splitting search and verify fixes the problem

The problem is a bottleneck: databases are small but dumb (cannot see shapes), models are smart but huge (cannot hold all data). Splitting work unblocks both.

SQL search runs on summaries, not raw data. Summaries are tiny (a few numbers per window), so SQL scans billions of windows in seconds without memory pressure. It finds rough candidates. Some candidates are false alarms because summaries are coarse.

Python verify loads only the candidates SQL found, not the whole database. Python computes the exact shape metrics (slope, plateau length, etc.) on raw data. It catches false alarms and confirms true matches. This two-step approach guarantees: (1) no patterns are missed (SQL recall is high because feature index is comprehensive), (2) false alarms are caught (Python precision is high because it checks real data), and (3) the system never loads more data than it can hold in memory (because verification only touches candidate windows, not the whole history).

Math after the picture

The filtering formula

First in words:

Each window w receives a relevance score from SQL based on how well its SAX code and trend summary match the query pattern; only windows scoring above a threshold pass to Python for verification.

Then the compact form:

S_SQL(w) = count_matches(sax_code(w), query_pattern_regex) + trend_match_bonus(w) if S_SQL(w) >= threshold_SQL then verify(w) else discard(w)

Every symbol:

S_SQL(w)SQL relevance score for window w
sax_code(w)SAX letter sequence of window w (e.g. abcde)
query_pattern_regexpattern to match in SQL (e.g. a+.*b+)
count_matchesnumber of regex matches found
trend_match_bonus(w)extra points if slope, plateau, or direction matches
threshold_SQLminimum score to pass to Python verification
A tiny worked example
Suppose SQL searches for pattern 'rise then plateau' in SAX codes.
Window A: SAX code aabbc, matches regex a+b+c = 2 matches + trend bonus 1 = score 3.
Window B: SAX code cccaa, matches regex a+b+c = 1 match + trend bonus 0 = score 1.
Threshold is 2. Window A passes to Python verification (score 3 >= 2), Window B is discarded (score 1 < 2).
Python then confirms: Window A's raw signal truly rises then plateaus. Match found.

SQL filters coarsely on summaries; Python verifies precisely on raw data. The threshold trades speed: lower threshold brings more candidates and slower verification, higher threshold risks missing matches.

What can go wrong

What can go wrong

Feature index is too coarse. If the SAX codes or trend summaries do not capture the pattern you care about, SQL will miss candidates entirely. The query will return no results even though the pattern exists. Example: if your database only stores average slope per window but you need to detect sudden spikes, the index is too coarse.
Feature index is too expensive. Building and storing a feature index for billions of windows takes storage and offline compute time. If the database changes constantly, the index becomes stale. Trading off index freshness against query accuracy is a real tension.
Python verification is too slow. If SQL returns 100,000 candidates and Python has to load and verify each one against raw data, the verify step becomes a bottleneck. The system is fast only when SQL filters aggressively. Poorly written query plans lead to huge candidate pools.
Done right. Build the feature index carefully so it captures the shapes users actually ask about. Write good query plans so the LLM planner decomposes queries into verifiable sub-steps. Then Search-Then-Verify is fast and accurate, because SQL does the cheap sifting and Python does only the necessary precise checking.

What a runnable demo should prove

Build a small time series database with 100,000 synthetic data points (e.g., randomly walking prices). Include a feature index (SAX codes and trend summaries pre-computed for all windows). Write a query: 'Find all times when price rose more than 5% then stayed flat for at least 10 steps.' Generate SQL to search the feature index and return candidates. Write Python code to verify each candidate (compute real slope and flatness on raw data). Count: how many SQL candidates? How many Python verifications passed? Time both steps separately.

false_positive_rate = (candidates_SQL_returned - candidates_Python_verified) / candidates_SQL_returned, verification_speedup = (time_to_check_all_raw_data) / (time_SQL_search + time_Python_verify)

The demo must show that SQL eliminates the need to scan all 100,000 windows, and Python eliminates false alarms that SQL caught. That is the whole system: fast coarse search, then precise fine-grained check.
