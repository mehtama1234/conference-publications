Sonar-TS: Search-Then-Verify Querying for Time Series

Sonar-TS finds events in massive time-series databases by first narrowing down candidate windows with SQL, then verifying them with custom Python code.

Paper explainersAll themesTime Series & Sequential

When you have years of stock prices, sensor readings, or heartbeat records and want to ask natural questions in plain English—like find all times when the price jumped suddenly or the pattern looked like a smooth climb—existing methods fail. They either drown in the huge amount of data or miss the actual shapes and patterns you are looking for. Sonar-TS is a hybrid method that uses database tricks to narrow the search space first, then validates with hand-built logic that understands the actual raw data.

Asking questions about patterns buried in time

You have a database with millions of data points collected over weeks or years—stock prices ticking every second, factory sensors recording every minute, hospital monitors logging every heartbeat. You want to ask natural questions: when did the price spike? Find all times the curve looked smooth. Which periods had unusual jumps? The challenge is that the database is too big to read all at once, and the patterns you care about are shapes and anomalies, not simple numerical ranges.

Text-to-SQL methods exist, but they translate English into database queries designed for structured tables with clean columns—they are blind to shapes, curves, and anomalies. Time-series models can spot patterns but choke on ultra-long histories (years of data). Neither world talks to the other.

The core problem. How do you ask a natural-language question about patterns in massive, continuous time-series data when SQL sees only rows and columns, and machine learning models cannot handle the sheer length of history?

What the paper changes

What the paper changes

The paper builds a two-stage pipeline: SQL finds rough candidates by querying abstract properties (ranges, counts, simple statistics), then Python verifies by reading the actual raw time values and testing the full pattern. Instead of one model trying to do everything, the paper splits the load between database logic and verification code.

The hidden quantity

The hidden quantity: search recall vs verification cost

measured quantity  =  search recall and verification cost

The key trade-off the paper balances is this: the SQL search must be broad enough to include all true answers (high recall), but narrow enough that the Python verifier does not waste time checking millions of false candidates. If the SQL is too strict, true answers are discarded before verification. If the SQL is too loose, verification drowns in noise.

The paper measures this trade-off by tuning how broad the SQL search is—relaxing it to catch more candidates at the cost of more verification work, or tightening it to verify faster but risk missing answers. The feature index (a pre-computed summary of ranges, counts, and simple properties per time window) lets the SQL search work without scanning all raw data.

Why it works

Why it works: two minds, one question

SQL databases are fast at filtering by simple rules: show me all times when a column was between 10 and 20, or where the average in a window fell. But SQL cannot describe a curve, an anomaly, or a smooth transition—it sees only numbers and ranges. Machine learning models understand curves and shapes but cannot efficiently scan billions of rows.

Sonar-TS solves this by having SQL do the heavy filtering (throwing away 99% of the data) using a fast feature index—a pre-built summary of simple properties per candidate window. Then, on only the narrow survivor set, it runs generated Python code that reads the actual raw values and tests the full pattern. This is like sonar: first, send a broad ping to narrow the search space (SQL search), then lock onto the target with precise verification (Python code). The pipeline works because filtering first is cheap (SQL is optimized for it) and verification second is affordable (only a few candidates remain).

The scoring formula

First in words:

total_score = SQL_recall * verification_cost_ratio, where recall is the fraction of true answers the SQL finds, and cost_ratio is the number of candidates the Python must check divided by the total data points.

Then the compact form:

quality = recall_SQL * (1 - candidates / total_points)

Every symbol:

recall_SQLfraction of true answers caught by SQL search
candidatesnumber of time windows returned by SQL
total_pointsall data points in the database
A tiny worked example
Suppose the database has 1,000,000 time points.
There are 100 true answers (windows matching the pattern).
SQL search returns 10,000 candidates (includes most true answers, plus false positives).
Recall from SQL: 95 out of 100 true answers found, so recall_SQL = 0.95.
Cost ratio: 10,000 / 1,000,000 = 0.01 (verifier touches 1% of the data).
Quality score: 0.95 * (1 - 0.01) = 0.95 * 0.99 = 0.9405.
If SQL were too strict and returned only 1,000 candidates, recall might drop to 0.70, giving quality = 0.70 * 0.999 = 0.699—lower overall because answers were lost.

The formula balances how many true answers the SQL finds against how much work the verifier must do.

What can go wrong

What can go wrong

Feature index does not match the query intent. If the SQL search looks for low values but the pattern actually needs to detect a sudden jump, the SQL index returns the wrong candidates and Python cannot fix it. The search stage must be tuned for each query type.
Generated Python code has bugs. If the verifier code misunderstands the pattern (e.g., tests for the wrong threshold or reads the wrong column), it filters out true answers. Code generation must be careful.
Ultra-long patterns exceed Python capabilities. If the pattern spans longer than the model expects (e.g., a trend lasting 30 days when the verifier was written for 3 days), verification fails silently and returns incomplete results.
Done right. Tune the SQL search to be generous (accept candidates that look plausible), generate Python verifiers that carefully test the full pattern, and validate on known examples before running live queries.

What a runnable demo should prove

Build a small time-series database (e.g., 100,000 data points from a sine wave with noise and occasional jumps). Write a natural-language query like find all times when the signal jumped up then down in under 5 minutes. Create a feature index by summarizing the data into candidate windows. Generate SQL that finds windows where the maximum and minimum are far apart. Generate Python that verifies the exact jump timing. Measure: of the true jumps inserted into the data, how many did the pipeline find (recall)? How much faster was the search than scanning all data (speedup)? The search is faster because SQL filters out most candidates using pre-computed summaries, and only the small survivor set requires Python verification—avoiding full data scans.
