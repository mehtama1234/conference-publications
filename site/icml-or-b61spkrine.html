PSR-Guided Data Selection for Neural Theorem Proving

Pick the right training proofs and steer generation with live verifier feedback, and a language model can prove 90% of formal theorems.

Paper explainersAll themesOther

Teaching a language model to write formal proofs (step-by-step mathematics that a computer can check) is hard because most available proofs are messy and redundant. This paper asks: what if instead of training on all the data, you pick only the proofs that teach the model new reasoning ideas? And what if, during proof generation, you show the model whether each step is correct before it picks the next one? Together, these two moves — smart data selection and live feedback during inference — turn a typical 70% success rate into 90%.

Zero assumption version

Why theorem proving is stuck

A formal theorem prover (like Isabelle) is a tool that checks whether a proof is correct by running it line by line. But writing proofs is tedious: each step must be spelled out in a specialized syntax, and there are often many ways to prove the same thing. Recently, large language models — the same kind used for chatbots — have gotten good enough to write these proofs automatically. The model reads the theorem statement and generates proof steps one by one, and the verifier checks each step.

The problem: the available training data (thousands of real proofs) is imbalanced and messy. Some proof ideas are repeated hundreds of times, while others appear once. A model trained on all of this raw data learns the common patterns but gets confused by the noise. And many general-purpose techniques for picking good training data do not work here, because formal proofs have a special structure — a single proof might contain multiple lemmas or case splits, making it hard to judge which parts are worth learning from.

The naive approach fails because it trains on all the messy data. Instead, cherry-pick the proofs that teach new ideas, and correct the model in real time.

The algorithm as a flow

What it actually does

Measure each proof

Score it on three scales: how hard it is, how many new lemmas it touches, how many reasoning styles it shows.

Build a balanced training set

Select proofs to maximize all three scores at once, removing redundant duplicates.

Train the model

Fine-tune a language model on only these high-quality proofs.

Generate with verifier loop

Model writes a proof step, verifier checks it; if it passes, model writes next; if it fails, model is told to steer differently.

Measure success

Count what fraction of theorems the model proved end-to-end, compared to baseline.

What the paper changes

The one thing that changes

The paper changes two things that work together: first, which training proofs are used; second, how the model generates during inference (proof time). On training day, instead of using all proofs, it uses only a carefully curated subset. On proof day, instead of generating in isolation, the model receives yes-or-no feedback from the verifier after each step and adjusts its next move accordingly.

the object it moves  =  Training data selection and inference-time verifier feedback
The hidden quantity

Proof quality, named in three dimensions

measured quantity  =  PSR: Proof complexity, Semantic coverage, Reasoning diversity

The paper introduces PSR — a way to measure whether a proof is worth training on. Proof complexity measures how hard the proof is (intermediate difficulty is best: too easy teaches nothing, too hard confuses). Semantic coverage measures how many different mathematical ideas (lemmas, definitions) the proof touches, so a proof that applies five different pieces of background knowledge is richer than a proof that repeats one idea. Reasoning diversity counts how many different proof strategies the proof demonstrates — a proof that uses both case analysis and algebraic simplification is more diverse than one that applies a single tactic repeatedly.

During training, the paper computes PSR scores for all available proofs, then selects a compact subset that maximizes all three scores together. This ensures the model sees a balanced, representative sample rather than drowning in duplicate proofs.

Plain reading. Imagine you are tutoring math. If every problem your student does is a repeat of the last one, they do not learn. If every problem is impossibly hard, they quit. And if every problem only shows one method, they think math is one-trick. PSR is a tutor's instinct: pick problems that are just hard enough, that explore different ground, and that teach different techniques.
Paper reading. The paper computes complexity as the expected depth of the proof tree in the verifier; semantic coverage as the number of unique lemmas cited; reasoning diversity as entropy over the proof tactics used. It then selects a subset via maximum coverage: greedily pick proofs to keep PSR-scores balanced, subject to compactness.
Why it works

Why this works: two feedback loops

The mechanism has two parts. First: data curation is training-time feedback. When you train on all proofs, the model spends its learning capacity on redundant patterns and gets buried in noise. By selecting only high-quality proofs, you focus the model's learning on the most representative and diverse examples. It sees each reasoning style clearly, without distraction.

Second: verifier feedback is inference-time correction. Even a well-trained model sometimes writes a proof step that does not pass the verifier. At that point, a naive system (generate, check, fail) stops. Instead, this paper passes the failure back to the model as a prompt: 'That step failed; try a different approach.' The model reads the error and steers its next attempt. This is like giving the model a chance to recover from small mistakes, turning a dead-end into a branch that tries something new.

Scoring a proof: the PSR formula

First in words:

PSR score = combination of (complexity level away from extremes) + (count of unique lemmas touched) + (entropy of tactic distribution)

Then the compact form:

PSR(proof) = norm(complexity) + norm(semantic_coverage) + norm(reasoning_diversity)

Every symbol:

proofone formal proof document
complexitythe depth or step-count of the proof tree (how hard it is to follow)
semantic_coveragethe number of different background lemmas or definitions invoked
reasoning_diversityentropy over the proof tactics used (how many different strategies appear)
norm(...)normalize the score to 0-1 so all three dimensions contribute equally
A tiny worked example: scoring two proofs
Proof A: complexity-score=0.6 (medium, not too easy/hard), coverage=3 ideas, diversity=0.7 (mixed tactics) -> normalized PSR ≈ 0.6 + 0.6 + 0.7 = 1.9 / 3 ≈ 0.63 (moderate quality).
Proof B: complexity-score=0.8 (just right), coverage=5 ideas, diversity=0.9 (four different tactics) -> normalized PSR ≈ 0.8 + 0.9 + 0.9 = 2.6 / 3 ≈ 0.87 (high quality).
Select Proof B for training: it teaches more diverse reasoning on a fuller set of lemmas.

The model learns from proofs with higher PSR, because they pack more teaching value into each example.

What can go wrong

What can go wrong

PSR is not perfect. A proof might score high on all three dimensions but still be misleading (e.g. uses an obscure tactic never seen again). The paper assumes the three dimensions capture quality well, but in a new domain, PSR scores might not match human judgment.
Verifier feedback can lead the model astray. If the verifier is permissive (accepts technically correct but suboptimal steps), the model learns bad habits. If it is too strict, the model gives up too quickly. The feedback loop only works if the verifier is reliable.
Curating a dataset is expensive. Computing PSR scores requires analyzing every proof, which costs time and compute. If you have a billion proofs, this overhead is painful.
When everything lines up. If the three PSR dimensions are calibrated well for your proofs, and the verifier is honest, the method improves performance a lot with a compact training set, because the model spends its training capacity learning diverse, representative examples instead of drowning in noise, and the verifier feedback lets it escape dead ends during proof search.
What a runnable demo should prove

What a runnable demo should prove

A complete demo would take a corpus of formal proofs (e.g. the Isabelle standard library), compute PSR scores for a subset, train a language model on the PSR-selected proofs, and test it on held-out theorems. The demo should show three things: (1) that high-PSR proofs lead to better generalization than random selection, because diverse, mid-difficulty examples teach more reasoning patterns than duplicates or extremes; (2) that adding verifier feedback during inference improves proof completion rate compared to single-shot generation, because the model can re-aim its next step after learning what failed; and (3) that the method reaches the stated 90% pass rate on the benchmark.

pass_rate = (number of theorems proved) / (total number of theorems), at depth limit 64 proof steps

The core insight is that a smaller, more diverse training set beats a large noisy one, and that correcting the model during proof-search matters as much as what you trained it on.
