GuardSpace: Preserving Safety During Fine-Tuning

GuardSpace protects a language model's refusal behavior during fine-tuning by decomposing weights into safety-critical and modifiable parts, then constraining updates to a mathematical space that cannot alter safe outputs.

Paper explainersAll themesAlignment, Safety & Fairness

When you fine-tune a large language model on new tasks, even benign ones like math problems, the model often forgets how to refuse harmful requests. GuardSpace solves this by identifying which parts of the model encode safety (refusing bad prompts) and which parts are free to change. It freezes the safety parts and constrains the modifiable parts to only move in directions that preserve the original safe answers.

Zero assumption version

Fine-tuning breaks safety alignment

A trained language model learns two separate behaviors: answering legitimate questions well, and refusing to answer harmful ones. This safety behavior comes from the model's fine-tuning on human feedback.

When you want to teach the model a new task (like solving math problems faster), you update its weights using new training data. This works because the weights encode numerical parameters: adjusting them on examples of the new task nudges them toward outputting the correct answer for that task. The naive approach: update all weights equally. But the weights that encode safety are entangled with the weights that encode general knowledge. Nudging them to learn the new task accidentally nudges them away from refusing harmful prompts, because the same weights that solve math also gate refusals. The model gets better at math but worse at safety because it is forced to rewrite the same neural circuits for both purposes.

In one sentence. Fine-tuning adapts a model to a new task by changing its weights, but those changes degrade the safety behaviors the model learned earlier.

The algorithm as a flow

What it actually does

Identify which weights encode safety

Decompose the trained model into safety-critical weights and safety-irrelevant weights using mathematical analysis of weight importance.

Freeze safety weights

Lock safety-critical weights in place so fine-tuning cannot nudge them at all.

Adapt only the free weights

Use low-rank updates (small trainable matrices) on the safety-irrelevant weights to learn the new task.

Constrain updates to preserve safe outputs

Project adapter updates onto a null space that guarantees harmful prompts still get the original safe answer.

Train on the new task

Optimize the adapter to solve the new task while respecting all constraints.

What the paper changes

What the paper changes

GuardSpace changes which weights can be modified during fine-tuning. Instead of updating all weights, it partitions them into two groups: safety-critical weights (frozen) and safety-irrelevant weights (free to move). This decomposition comes from analyzing how much each weight contributes to the model's safe behavior on harmful prompts.

the object it moves  =  weight decomposition and constraint
The hidden quantity

The hidden quantity: importance to safety

measured quantity  =  weight importance for safety

Each weight in the model contributes differently to the model's ability to refuse harmful requests. Some weights are critical: nudging them breaks safety. Others are irrelevant: nudging them barely affects safe behavior. GuardSpace measures this contribution by analyzing how much each weight influences the model's refusal response when given a harmful prompt.

The paper uses covariance-preconditioned singular value decomposition (a mathematical technique that analyzes which weight directions matter most for safety) to score each weight. High-scoring weights are frozen; low-scoring weights are free to adapt.

Why it works

Why it works: the causal chain

The mechanism has two parts. First, by freezing safety-critical weights, GuardSpace prevents the learning steps (called gradients: the small nudges that change weights during training) from ever moving the mechanism that produces safe outputs. Those weights are mathematically immobilized. Second, by projecting the adapter updates onto a null space (a mathematical constraint that says adapter changes cannot alter the model's output on harmful prompts), GuardSpace ensures that even when the frozen weights interact with the newly adapted weights, the model still refuses harmful requests. The frozen parts and the adapted parts work together under a constraint that preserves the refusal behavior.

Why this works: the model's safety is encoded in specific weight directions and weight-interaction patterns. By leaving those directions untouched and constraining changes to a subspace orthogonal to them, safety cannot degrade. The model gains new task capability without relearning to refuse.

Math after the picture

The core equation

First in words:

The total objective combines the new task loss with a null space projection penalty. The model minimizes task loss only along directions that do not alter refusal behavior on harmful prompts.

Then the compact form:

L = L_task + lambda * ||P_null * delta_W||^2

Every symbol:

Lthe total loss (error) the model tries to minimize
L_taskthe loss on the new task (math problems, translation, etc.)
lambdahow strongly to enforce the safety constraint (higher = more protection)
P_nullthe null space projector (a matrix that maps weight updates to the safe subspace)
delta_Wthe change in weights during fine-tuning
||...||^2the squared length of the vector (measures how far the change pushes away from safety)
A tiny worked example
Suppose the model updates 3 weights by [+0.1, -0.05, +0.2] to improve at math.
The null space projector identifies that [+0.1, -0.05, +0.2] would reduce safety by moving along an unsafe direction.
It projects this into the safe subspace, yielding [+0.08, -0.02, +0.15], a smaller movement.
With lambda=1, the penalty is ||[+0.08, -0.02, +0.15]||^2 = 0.064 + 0.0004 + 0.0225 = 0.087.
The optimizer learns that moving the full [+0.1, -0.05, +0.2] costs too much; instead it updates a separate adapter matrix, moving only in safe directions.

The equation protects safety by making weight changes that break refusal very expensive, so the optimizer redirects task learning to the frozen weights and constrained adapter.

What can go wrong

What can go wrong

Decomposition mislabels weights. If the importance analysis incorrectly classifies a safety-critical weight as free, that weight can move during fine-tuning and break safety. The decomposition relies on analyzing the model on a set of harmful examples; if those examples are not representative, some safety-critical weights are missed.
Adapter is too large. If the low-rank adapter (the matrix of free weights) can learn to reroute information and partially recover the safety-breaking behavior, the null space constraint may not be tight enough. A bigger adapter can encode more independent information.
New task conflicts with safety. If the new task requires the model to produce outputs that look like it is answering harmful requests (even if it is describing an attack for educational purposes), the null space constraint may prevent learning on those examples.
Done right. GuardSpace works best when the harmful examples used to measure importance cover the actual threats, when the adapter rank is small enough to stay constrained, and when the new task and safety do not directly conflict.
What a runnable demo should prove

What a runnable demo should prove

Take Llama-2-7B-Chat (a language model trained to be helpful and safe). Fine-tune it on GSM8K (a math problem dataset with 8,000 grade-school math questions). Measure two things: (1) how often the model still refuses when you ask it a harmful request, and (2) how often it answers the math problems correctly. Compare three methods: naive fine-tuning (update all weights), a baseline safety method, and GuardSpace. Report the harmful score (percentage of harmful prompts the model incorrectly answers) and task accuracy (percentage of math problems correct).

harmful_score = (harmful_responses_after_finetuning / total_harmful_prompts) * 100; task_accuracy = (correct_math_answers / total_math_problems) * 100

GuardSpace should show a harmful score near 4% (vs. 14% for naive fine-tuning) and task accuracy near 28%, proving that you can improve at a new task without forgetting to refuse because the safety weights stay locked and the adapter cannot override refusals.
