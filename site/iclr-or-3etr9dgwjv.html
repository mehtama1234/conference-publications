MomaGraph: Unified Scene Graphs for Robot Task Planning

Robots plan household tasks more accurately by building scene graphs that combine where objects are, how they work, and which parts matter for the task.

Paper explainersAll themesRobotics & Control

A robot standing in a kitchen needs to understand not just where the coffee maker sits but also that a button turns it on and water goes in the top. Current systems split this into separate problems: some map only space, others only function. MomaGraph does both at once, along with learning which details matter for each task, so robots can plan complex multi-step actions without trial and error.

Zero assumption version

Robots cannot plan household tasks correctly

When a robot is told to make coffee, it must understand the kitchen: where the coffee maker sits, that a button activates it, that water goes in the tank, and that these steps must happen in order. Older approaches split this into pieces. Some systems only record space (the coffee maker is on the counter, 2 meters from the sink). Others only record function (a button activates things, water fills containers). This means the robot has gaps: it might know the button's function but not which button, or know water fills things but not what container to use. Splitting information this way also treats the scene as a frozen snapshot: the robot does not know that after you close the fridge door, the fridge's position does not change but its state does (now closed). And the system loads every detail into memory equally, even though for making coffee, the toaster's color does not matter.

A robot trying to act without a unified, task-aware model will hallucinate steps, miss dependencies, or attempt actions in the wrong order. The paper shows that even advanced closed-source models like GPT-5 fail at this when given only raw images, producing wrong action sequences or missing critical steps.

In one sentence. Build a map of the scene that records where things are, how they work, which parts do what, and which details matter for this specific task.

What the paper changes

What the paper changes

The paper changes the scene graph representation itself. Instead of separate spatial graphs and functional graphs, it creates one unified graph where each edge (connection between objects) can encode both spatial relationships (where is the button relative to the coffee maker) and functional relationships (the button activates the maker). It also adds part-level nodes: not just "coffee maker" but "coffee maker's water tank", "coffee maker's button" as distinct entities with their own connections. Finally, it makes the graph task-aware by training the model to highlight which parts of the graph matter for each specific task.

The hidden quantity

The hidden quantity: Task-Relevance Weight

measured quantity  =  task relevance weight

The model does not process every object and connection equally. It learns a task-relevance weight for each edge in the scene graph: a number from 0 to 1 indicating how much that connection matters for the current task. For making coffee, the connection between the water tank and the filler opening has weight close to 1 (critical). The connection between the toaster and its slot has weight close to 0 (irrelevant). The paper trains the model using reinforcement learning: if including an edge in the plan leads to a correct action, the weight goes up; if the action fails or is unnecessary, the weight goes down. This works because over thousands of training examples, edges that repeatedly help the robot succeed get amplified, while edges that cause failure or waste computation get suppressed, eventually converging to a model that predicts only task-relevant structure.

The model estimates this weight by learning from examples: it sees task-driven scene graphs in the training data and observes which connections led to successful robot plans. Over time, it learns patterns: for any household task, which spatial and functional connections typically matter and in what order.

Why it works

Why unified, task-aware scene graphs fix the problem

Direct planning from raw images fails because the model must hold too much in mind at once. It must track space, function, dependencies, and task relevance all in working memory. By first building an intermediate scene graph, the model offloads this work: the graph is a structured summary that highlights only what matters. This is why the Graph-then-Plan approach works.

Separating spatial from functional graphs fails because the two kinds of reasoning interact. To get a correct action sequence, the robot must reason: the button activates the machine (function) AND the button is on the front (space) AND the water tank is on top (space) AND water fills it (function) AND these steps must happen in order (dependency). A system with only spatial info might know the tank is on top but not know it needs water. A system with only function might know it needs water but not know which tank or that accessibility matters. By unifying both in one graph, every part of the reasoning sees the full picture. The model learns that functional relationships often encode order (do X before Y) and spatial relationships often encode feasibility (can the robot reach it?). Together, they make sequence prediction accurate.

Task awareness further improves this because humans do not process all information equally. For the coffee task, the button matters; for the laundry task, the machine's spin knob matters. By training with reinforcement learning to predict graphs that lead to successful plans for each task, the model learns which connections are actually used and can stop wasting computation on irrelevant details.

The graph-alignment reward function

First in words:

The reinforcement learning algorithm optimizes a reward: for each predicted edge in the scene graph, it asks, did this edge appear in the ground-truth task-driven graph? If yes, add one point. If the model predicted an edge that was not actually relevant (hallucination), subtract one point. The goal is to maximize the fraction of edges that matter for the actual task.

Then the compact form:

reward = (edges_correct / total_edges_predicted) - (lambda * edges_hallucinated)

Every symbol:

edges_correctnumber of predicted edges that match the ground truth
total_edges_predictedtotal edges the model generated
edges_hallucinatedpredicted edges not in the ground truth
lambdapenalty weight for hallucinations (typically 0.5 to 1.0)
A tiny worked example
Model predicts 8 edges: water_tank_to_filler, button_to_machine, cabinet_to_contents, fridge_to_wall, counter_to_kitchen, window_to_wall, machine_orientation, toaster_to_slot.
Ground truth for make-coffee task has 5 relevant edges: water_tank_to_filler, button_to_machine, cabinet_to_contents, fridge_to_wall (context), machine_position (for stability).
Correct predictions: 5. Hallucinations (window_to_wall, toaster_to_slot, counter_to_kitchen): 3. With lambda=1.0:
reward = (5 / 8) - (1.0 * 3) = 0.625 - 3.0 = negative (training fails). After learning, model predicts only the 5 relevant edges.
Second try: predicts exactly 5 edges, 5 match ground truth, 0 hallucinate. reward = (5 / 5) - (1.0 * 0) = 1.0 (good).
By repeating this, the model learns which spatial and functional edges actually matter for the task.

The reward pushes the model toward graphs that are both complete (capture all relevant edges) and clean (no hallucinations).

What can go wrong

What can go wrong

The training data might be biased to specific kitchen layouts. If all training examples show the coffee maker in the same location, the model might fail when the layout changes. The paper addresses this by using multi-view observations and a generalizable graph structure, but deployment in entirely new houses is still challenging.
Dynamic scenes break the snapshot assumption. If someone moves an object during the task, the graph becomes outdated. MomaGraph tries to include state changes (open vs closed), but a real-time update mechanism is not described.
Hallucinated edges can cascade into wrong plans. If the model falsely predicts that the toaster button activates the coffee machine, the plan will send the robot to the wrong place. The reward function penalizes hallucinations, but edge cases remain.
Done right. The DAPO reinforcement learning algorithm encourages task-aligned edges. Testing on both simulated and real robots shows the model generalizes across kitchens and handles unseen layouts.
What a runnable demo should prove

What a runnable demo should prove

Build a small example: a simulated kitchen with objects (coffee maker, fridge, cabinet, sink) and a task (make coffee). Feed the VLM multi-view images and the task instruction. Record the predicted scene graph. Then feed the graph to a task planner (a simple graph-traversal algorithm or a learned policy). Measure: does the predicted graph contain all edges needed for the correct action sequence? Does the planner generate actions in the right order? Compare three cases: (1) graph with only spatial edges, (2) graph with only functional edges, (3) MomaGraph with both. Show that unified, task-aware graphs produce both more complete and more correct plans.

The demo must make it obvious that spatial reasoning alone fails (robot knows where things are but not what to do), functional reasoning alone fails (robot knows how things work but not where to find them), and combining both with task awareness succeeds.
