ZeroGR: A Generalizable and Scalable Framework for Zero-Shot Generative Retrieval

Train one retrieval system to answer many search tasks from instructions, even when the task was not seen during training.

Paper explainersAll themesAgents & Tool Use

Search systems are often trained for one narrow setup: one data type, one query style, and one benchmark. That is a poor match for real use, because new tasks arrive with new document formats and new user goals. ZeroGR reframes retrieval as generating a compact document name from an instruction and a query, then builds the index with many instruction-made query forms so the same system can transfer to unfamiliar retrieval tasks.

Zero assumption version

Why ordinary generative retrieval breaks on new tasks

Generative retrieval asks the model to answer a search request by writing the identifier of the best document. That can work well when training and test data follow the same pattern. It becomes brittle when the task changes, because the model has learned a narrow mapping from one style of query to one set of document names.

The trouble grows when the corpus contains mixed material such as text, tables, and code. A single naming scheme may not reflect what each item is about, so the model struggles to write the right document name for an unfamiliar task because the target name no longer exposes the document's role clearly. Zero-shot search needs two things at once: document names that carry useful meaning, and an index built from many possible query forms, because the model must align an unseen instruction with stored documents through wording that may differ from training.

The paper's move in one sentence. ZeroGR gives each document a content-bearing name, creates many instruction-driven query forms for indexing, and adjusts decoding so that the generated name is precise without dropping too many good candidates.

The algorithm as a flow

What it actually does

Step 1: Name every document in plain language

Convert each document into a short generated document name that reflects its content, because a content-bearing name gives the retriever a target that can transfer across tasks better than an arbitrary numeric id.

Step 2: Read the task instruction

Use a natural-language task description to tell the system what kind of search job it is solving, so that the next steps can build task-specific query forms without needing labeled examples from that task.

Step 3: Generate many query variants

Produce diverse synthetic queries from the task description, because one wording is never enough to cover the ways users phrase the same need.

Step 4: Index documents against those variants

Connect each generated query form to the document names that answer it, so that recall rises by covering more entry points into the corpus.

Step 5: Decode document names carefully at search time

Generate candidate document names with a reverse annealing schedule that starts broader and ends stricter, because early breadth keeps good options alive and later tightening removes weak matches.

What the paper changes

What the paper changes

The paper changes the representation of documents and the way the retrieval index is built. Instead of relying on fixed ids and labeled examples from the target task, it creates content-bearing document names and expands the index with instruction-driven synthetic queries.

the object it moves  =  Document naming and query coverage
The hidden quantity

The hidden quantity: coverage of possible query forms

measured quantity  =  Instruction-conditioned query coverage

A retrieval system succeeds when the user's wording lands near something the index already understands. That hidden quantity is query coverage: how many reasonable ways of asking are represented before the user arrives. ZeroGR raises this coverage by generating many query forms from a task description, so the index is prepared for wording that did not appear in supervised training.

Coverage matters because zero-shot retrieval fails mainly when the query and the stored document name miss each other in wording or task framing. If the index contains several instruction-made variants, the search request is more likely to align with at least one stored form.

Why it works

Why it works: align task instructions, stored names, and decoding

ZeroGR works because it aligns three stages that ordinary systems leave disconnected. First, document names carry semantic content, so the model has a target that reflects the document instead of an arbitrary label, because that target exposes what the document is about when the task changes. Second, the query generator uses the task instruction to create varied requests, so the index stores many task-relevant access paths. Third, reverse annealing decoding keeps several candidate names alive early and becomes stricter late, so that search can recover good documents without accepting too much noise.

These parts reinforce one another. Richer document names are only useful if the index contains varied ways to reach them. Broader query coverage is only useful if decoding can still separate strong and weak candidates at the end. ZeroGR improves transfer because each part repairs a different zero-shot failure mode: poor document naming, narrow indexing, and brittle final generation.

The scoring idea

First in words:

At each writing step for the document name, the decoder balances the current next-step score with a temperature schedule that is broad early and strict late. That schedule keeps recall high at the start and raises precision at the end.

Then the compact form:

score_t(docid_piece) = log p(docid_piece | query, instruction, prefix) / tau_t

Every symbol:

score_t(docid_piece)the adjusted score for one next piece of the document name at step t
p(docid_piece | query, instruction, prefix)the model's next-step probability given the request, the task instruction, and the already written prefix
tau_tthe step-dependent temperature used by reverse annealing
prefixthe part of the document name already written
A tiny worked example
Suppose the query asks for a table about battery life in phones.
Two candidate document names survive the first few steps: one for a phone review table and one for a repair manual.
Early in decoding, tau is larger, so both candidates stay alive because the system does not want to discard a useful table too soon.
Later in decoding, tau becomes smaller, so the phone review table pulls ahead because its later pieces match the query more consistently.
The final result is more complete than strict decoding from the start and more precise than keeping the search broad forever.

The paper's decoding rule is useful because broad early search protects recall, while late tightening protects precision.

What can go wrong

What can go wrong

Generated document names may collapse distinct items. If two documents receive very similar names, search quality drops because the system cannot separate them reliably. The fix is to train name generation so that names stay descriptive and distinctive.
Synthetic queries may drift away from real user intent. If the generated query set overfits the task description and misses everyday wording, recall suffers because the stored access paths do not match user phrasing.
Decoding can become too broad or too strict. If the temperature stays high for too long, weak candidates survive and hurt precision. If it drops too fast, good candidates disappear early, so recall falls.
Done right: one system handles many retrieval jobs. The method transfers across tasks because the instruction tells the query generator what kind of retrieval problem it is solving, while the document names stay content-bearing across data types.
What a runnable demo should prove

What a runnable demo should prove

Build a small mixed corpus with short articles, tables, and code snippets. Define three search tasks with only natural-language instructions, such as fact lookup, table lookup, and code search. Compare two systems: one generative retriever trained on a single task with fixed ids, and one ZeroGR-style retriever with generated document names and instruction-made query expansion. Measure top-1 and top-5 retrieval on tasks that were held out during training. The demo should show that the ZeroGR-style system keeps more correct documents alive because its index covers more possible requests and its decoding schedule does not prune useful candidates too early.
