CORRECT: Error Recognition via Cached Failure Patterns

When multiple agents fail, the same structural problems recur, so caching failure patterns lets you spot and fix errors instantly without retraining.

Multi-agent systems coordinate across many AI models to tackle big tasks. But one agent's mistake can spread to others, and the tangled logs are hard to debug. This paper finds that even though failures look different on the surface, the underlying structural problems repeat. CORRECT builds a lightweight, updateable library of failure patterns and uses it to pinpoint exactly where errors happen, all without expensive retraining.

Zero assumption version

Multi-agent systems break in tangled ways

When multiple AI agents work together (one reads documents, another calls a tool, a third synthesizes), an error in one agent spreads like dominoes. The logs pile up, mixing good steps with bad ones, and humans or automated tools struggle to find where things went wrong.

A naive approach: collect every error that ever happens, label which step failed, and train a new classifier to spot that exact error in future runs. The problem: retraining is slow and expensive, you need thousands of examples to cover all error types, and by the time you have a new model ready, you have ten new failure patterns you have not seen yet.

The bottleneck. You need to recognize and locate errors instantly, without waiting for retraining and without seeing the exact same error twice.

What the paper changes

The one thing it changes

Instead of training a classifier on error examples, CORRECT builds and uses an online cache of failure patterns. Each cached pattern is a distilled, simplified version of a failure's essential structure, not the raw logs. This cache is the changeable object: it grows as you encounter new failures and shrinks if you delete stale patterns.

the object it moves  =  Failure pattern cache
The hidden quantity

The hidden quantity: failure-structure similarity

measured quantity  =  Structural similarity to cached failures

Even though two error logs look different (one task is document-question-answer, another is search-tool-synthesis), they often share the same broken step type. CORRECT measures how similar a new failure's structure is to each pattern in the cache. This similarity score is the hidden number the paper relies on.

The paper estimates this by parsing the execution trace (which agent ran, which tool was called, what the input/output was) and comparing it to a cached error schema using simple string/semantic matching. A high match means the new error fits that schema.

Why it works

Why it works: structure is signal

When you label errors by hand, you learn that certain combinations of events mean certain things went wrong (e.g., if agent B calls tool X and then agent C gets an empty result, the schema is 'tool-hallucination'). Instead of memorizing thousands of labeled examples, CORRECT extracts just the structural essence of that failure and stores it in the cache.

When a new task runs and fails, CORRECT parses the execution log the same way, looks for which cached schema its structure most resembles, and outputs the step where that schema's error typically occurs. Because the cache is small and a simple pattern-matching lookup is fast, this runs in milliseconds. And because real errors DO follow repeating patterns, the match is usually accurate.

Math after the picture

The matching score

First in words:

similarity_score = count_of_matching_events / total_events_in_schema

Then the compact form:

match(trace, schema) = |trace_events intersect schema_events| / |schema_events|

Every symbol:

trace_eventsthe sequence of agent calls and tool outputs in the failed run
schema_eventsthe distilled pattern of events that define this error type
match(trace, schema)how much of the schema appears in the new trace, a fraction from 0 to 1
A tiny worked example
Schema 'Tool Hallucination': [Agent-A-reads, Agent-B-tool-call, empty-result, Agent-C-stalls]
New trace: [Agent-A-reads, Agent-B-tool-call, empty-result, Agent-C-stalls, retry-fails]
Matching events: 4 out of 4 core events match.
match(trace, schema) = 4 / 4 = 1.0 (perfect match, this is the error).

High match means the new error fits the schema closely; CORRECT outputs that schema's known failure point.

What can go wrong

What can go wrong

Two errors with very different surface logs but same root cause. If your similarity measure is too strict (e.g., exact string matching), you miss the match and output the wrong step. Fix: use semantic matching that looks past surface differences (parse syntax, compare intent).
Cache polluted with rare, badly-labeled error schemas. If your initial collection phase labeled an error incorrectly, the cached schema is wrong, and every similar error in the future is mislocalized. Fix: validate cache schemas via human review or test on a held-out set.
Never-before-seen error type that shares no structure with any cached schema. The matching score is low for all cached schemas, so you cannot localize it. Fix: when no schema matches above a threshold, flag it as a new pattern, extract its structure, and add it to the cache for next time.
Done right. You maintain schema accuracy by periodically re-validating high-impact schemas, you seed the cache with a diverse error-injection pipeline, and you treat low-confidence matches as new patterns to add.
What a runnable demo should prove

What a runnable demo should prove

Build a simple multi-agent workflow (e.g., agent A searches a knowledge base, agent B calls an API, agent C filters results). Inject ten known error types (wrong API key, empty search result, timeout, malformed input). Run the workflow 30 times, record execution logs. Distill the ten error types into schemas. Inject each error again on a fresh run and measure whether CORRECT pinpoints the right agent step (not just that an error happened, but which step).

step_localization_accuracy = (errors with correct step identified) / (total injected errors)

With cached schemas, step_localization_accuracy should be >85% on known error types and >70% on unseen error types not in the cache (because the new structure often partially matches at least one cached schema).
