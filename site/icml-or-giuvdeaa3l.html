Zero assumption version

3D molecules need rotation-proof neural networks, but they are too slow

To predict properties of molecules, a neural network must understand how atoms are arranged in 3D space. The arrangement changes when you rotate or flip the molecule, so naive approaches fail: the model learns to depend on rotations rather than the actual chemistry. A rotation-aware (equivariant) neural network solves this by building features that stay true under rotation—things like angles between atoms, distances, and products of those values.

But building these features costs time. For every pair of atoms, the standard approach constructs a dense table of angles, distances, and products. When you have thousands of atoms, that table explodes—especially during the comparison step where every atom must be scored against every other atom. A researcher might naively build all this data upfront, only to discover their GPU runs out of memory and the model crawls.

The core trade-off. Skip the expensive dense tables; compute just the parts of them you actually need, exactly when you need them, using a different mathematical basis.

What the paper changes

The thing the paper changes

The paper changes how angle and distance data is stored and read during the scoring step. Instead of building a dense table of all relationships for every atom pair, it stores only the parts that are non-zero under the right coordinate system, and custom GPU code reads directly from the sparse structure.

the object it moves  =  Data storage and retrieval
The hidden quantity

Sparsity pattern under basis rotation

measured quantity  =  Non-zero fraction after basis change

A 'hidden quantity' is a number the paper measures but does not explicitly state in the abstract. Here it is the fraction of table entries that remain non-zero after switching to a different coordinate system. In the standard coordinate system, almost all entries are non-zero (the full dense table). After the change, most entries become exactly zero; only a sparse subset matters.

The paper estimates this by counting non-zero entries in the Wigner-6j coefficients (numbers that encode angle and distance relationships in 3D) after re-indexing. The authors use this to prove that custom GPU code can skip the zeros entirely and process only real values, dodging memory waste.

Why it works

Why the speedup works

The mechanism relies on two facts. First, angle and distance relationships in 3D can be expressed in many different coordinate systems. The standard way is dense and expensive. A clever alternative is to rotate the coordinate system so the same relationships are mostly zeros. The paper proves that after this rotation, the Wigner-6j coefficients (the core tables) are sparse—many entries are exactly zero, not just small.

Second, the GPU is the bottleneck, not arithmetic. A dense implementation loads the full table into GPU memory, wastes time moving it around, and leaves compute cores idle. A sparse implementation loads only non-zero entries using a custom fused function (one GPU routine that does several jobs at once). The function reads from fast memory once, computes scores in place, and writes results—no redundant moves, no wasted space. The GPU cores stay fed with useful work.

Math after the picture

The sparse indexing principle

First in words:

After basis change, only non-zero Wigner coefficients are stored and fetched. The cost of attention per node is proportional to the sparsity fraction, not the full table size.

Then the compact form:

cost_per_node = base_ops * sparsity_ratio * nodes_per_attention

Every symbol:

cost_per_nodeGPU work to compute attention for one atom
base_opsoperations per non-zero entry
sparsity_rationon-zero entries after basis change, divided by total entries
nodes_per_attentionnumber of atoms being attended to (typically all atoms in molecule)
A tiny worked example
Suppose we have 100 atoms. Standard dense would compute 100 × 100 = 10,000 geometric values per layer.
After basis rotation, only 500 entries remain non-zero (sparsity_ratio = 500 / 10000 = 0.05).
Dense cost: 100 atoms × 100 lookups × 10 ops per lookup = 100,000 ops total, 10 KB moved to GPU.
Sparse cost: 100 atoms × 50 lookups × 10 ops per lookup = 50,000 ops, 2.5 KB moved to GPU.
The sparse version does half the work and uses one-quarter the memory, so inference is faster and fits on smaller GPUs.

Avoiding zeros saves time because the GPU bandwidth and cache memory are limited; loading and computing zeros wastes both. Non-zero entries fit in the GPU's fast cache, so there is no spillover to slower memory.

What can go wrong

What can go wrong

Coordinate system choice mismatch. If the rotation to the sparse coordinate system is not applied correctly, the angle and distance relationships change and predictions become wrong. The coordinate system must be chosen to match the symmetry of the problem (3D atomic arrangements).
Sparse indexing bugs. If the code that records which entries are non-zero has a bug (marks a zero as non-zero or vice versa), the scoring uses wrong values. Testing on small molecules first catches this before scaling.
GPU function does not fuse correctly. If the GPU routine reads and writes memory in the wrong order, the speedup disappears and memory bandwidth becomes the bottleneck again. Profiling on the GPU is essential.
Done right. Verify the coordinate rotation preserves rotation-awareness by hand (check that rotating the input gives a rotated output), test sparse indexing on molecules of known atomic arrangements, profile the code to confirm GPU cache is filled and operations are high.
What a runnable demo should prove

What a runnable demo should prove

Build a small version of E2Former-V2 that takes a molecule (say, a tiny organic compound with 10 atoms), computes scores using the sparse basis, and reports both the output and the wall-clock inference time. Compare it to the standard dense implementation on the same molecule. The demo must show that the sparse version produces the same scores as the dense version (within rounding), because the coordinate change is purely mathematical and does not alter the underlying relationships. It also must finish much faster and use less GPU memory, because the sparse compute routine avoids loading and computing zeros.

speedup = time_dense / time_sparse; memory_ratio = mem_dense / mem_sparse

The demo succeeds if speedup is greater than 5 and memory_ratio is greater than 5, and both versions output scores that match to 6 decimal places.
