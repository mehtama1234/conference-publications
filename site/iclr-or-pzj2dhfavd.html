Revisiting Weight Regularization for Low-Rank Continual Learning

Keep one shared low-rank update across tasks and protect its important directions with EWC instead of adding a new adapter for every task.

Paper explainersAll themesOther

Continual learning asks a model to learn new tasks one after another without erasing earlier ones. With large pre-trained models, a common strategy is parameter-efficient tuning: train only a small low-rank adapter instead of updating the full model. Most low-rank continual-learning methods sidestep interference by giving each task its own adapter, which limits forgetting but makes memory grow with the number of tasks. This paper revisits Elastic Weight Consolidation, or EWC, in that low-rank setting. EWC is a weight penalty that discourages changes to directions that earlier tasks depended on. The paper's main move is to apply that penalty to one shared low-rank update, so the model keeps fixed storage because no new adapter is added for later tasks while still controlling interference across tasks.

Zero assumption version

Why one-adapter-per-task avoids forgetting by spending memory

A pre-trained model already contains broad knowledge, so continual learning often updates it through LoRA, a low-rank adapter that represents the weight change as the product of two small matrices. This is attractive because the number of trainable values is far smaller than full fine-tuning.

But continual learning introduces interference. After task 1 tunes the adapter, task 2 may want to change the same update directions. If task 2 overwrites them, task 1 performance falls. Many low-rank continual-learning methods solve this by allocating a fresh adapter per task. That blocks interference, but storage then grows linearly with the number of tasks.

The paper asks whether one shared adapter can survive many tasks if the model knows which update directions matter to earlier tasks. That is the role of EWC: assign larger penalties to important directions so later training can still move, but not equally in all directions.

In one sentence. The paper keeps storage constant by reusing one low-rank adapter and uses EWC to slow updates only in directions earlier tasks marked as important.

The algorithm as a flow

What it actually does

1. Represent updates with LoRA

Express the task-specific change to a large weight table as the product of two small tables, so the trainable update stays low rank.

2. Train the shared low-rank update on task 1

Fit the adapter to the first task while the large pre-trained model remains mostly frozen.

3. Estimate importance after each task

Measure which adapter directions strongly affect the finished task and store those importance values.

4. Add an EWC penalty for later tasks

When task 2 or task 3 arrives, penalize movement in directions that earlier tasks marked as important.

5. Reuse the same adapter

Continue learning new tasks with the shared low-rank update instead of allocating a new adapter for each task.

What the paper changes

What the paper changes

The paper changes where the weight penalty acts in parameter-efficient continual learning. Instead of isolating tasks with separate low-rank modules, it applies the penalty to one shared low-rank update using task-importance information.

the object it moves  =  the shared low-rank update across tasks
The hidden quantity

The hidden quantity: importance of low-rank directions

measured quantity  =  how much each direction in the shared low-rank update contributes to earlier tasks

Continual learning is a fight between stability and plasticity. Stability means the model should keep what it already learned. Plasticity means it should still move enough to learn the next task. A uniform penalty cannot manage this tradeoff well because not all update directions are equally valuable to old tasks.

EWC addresses that by weighting the penalty direction by direction. In the low-rank setting, the paper argues that importance should be estimated through the low-rank representation but interpreted in the full weight space. That matters because the same small LoRA factors generate a full-dimensional weight update, and old tasks may depend strongly on some of those induced directions but not others.

This hidden quantity decides whether sharing one adapter is viable. If important old directions are identified well, later tasks can move mostly through unused or weakly used directions. If importance is estimated poorly, the method either forgets old tasks or freezes too much of the shared adapter and stops learning new ones.

Why it works

Why EWC fits naturally with a shared low-rank adapter

LoRA writes a large weight update as A times B, where both factors are small. That saves memory, but it also means all tasks are forced to share a narrow update subspace if only one adapter is kept. Sharing can be good when tasks overlap, because common directions do not need to be stored many times. Sharing becomes harmful only when new tasks need to repurpose directions that older tasks still need.

EWC provides a selective brake. After finishing a task, it records which update directions mattered most. On the next task, the loss includes both the new task objective and a penalty for moving those important directions. This works because the optimizer is not blocked everywhere; it is pushed away from only the directions that would cause the largest damage to old tasks.

The paper's low-rank version matters because importance is not assessed only on the small factor values themselves. The factors matter through the full weight-table update they create. Estimating importance with that full effect in mind makes the penalty more faithful to what the model actually uses during prediction.

The result is a better storage tradeoff because task-specific adapters avoid forgetting by duplication, while EWC-LoRA avoids more forgetting than plain shared LoRA by structured reuse. One adapter is preserved and reshaped gradually instead of replaced every task.

A tiny worked example
Suppose the shared adapter has two effective directions.
Direction 1 is very important for task 1, so its stored importance is 10. Direction 2 is weakly important, so its stored importance is 1.
During task 2, moving direction 1 by 0.1 adds penalty 10 times 0.1 squared, while moving direction 2 by 0.1 adds only 1 times 0.1 squared.
The optimizer therefore prefers to express new-task changes through direction 2 whenever possible.
That selective pressure preserves old-task behavior better than a plain shared adapter, because the optimizer pays most to alter the directions old tasks depended on most.

The shared adapter remains compact because only one low-rank update is stored, while the EWC weights decide which parts of that update are hard or easy to move.

What can go wrong

What can go wrong

Importance estimates are inaccurate. If the method misjudges which directions matter to old tasks, it may freeze the wrong directions and still allow destructive overwriting where protection was needed, because the penalty would be strongest in harmless places and weakest in harmful ones.
Tasks conflict inside a very small low-rank subspace. If new tasks genuinely require update directions that old tasks also require in incompatible ways, one shared low-rank adapter may still be too restrictive even with EWC.
Penalty set too strong. If lambda is too large, the shared adapter becomes hard to move and the model underfits later tasks because plasticity is lost.
Done right. Estimate importance carefully and keep the shared low-rank rank high enough to offer alternative directions for new tasks. Then EWC can preserve earlier knowledge while the adapter continues to learn.
What a runnable demo should prove

What a runnable demo should prove

Take a small pre-trained sequence model and a sequence of text classification tasks. Compare three continual-learning setups: one shared LoRA adapter, one fresh LoRA adapter per task, and one shared LoRA adapter with EWC. Track average accuracy across all tasks after each new task arrives, along with total adapter memory.

The demo should show the central tradeoff clearly. A plain shared adapter forgets because later tasks overwrite earlier directions. Per-task adapters remember more but grow in memory. EWC-LoRA keeps memory fixed and closes much of the forgetting gap because later tasks are guided away from important old directions.

average_task_accuracy = (1 / T) * sum_t accuracy_t memory_per_task = total_adapter_parameters / T

A convincing result is a stability-plasticity curve that improves over plain shared LoRA without inheriting the linear memory growth of task-specific adapters, because the single protected adapter reuses storage instead of adding one new module per task.
