Agent Data Protocol

A shared language lets you train agents on 13 different datasets at once instead of separately.

Paper explainersAll themesAgents & Tool Use

When you teach a robot or AI to use tools, you need lots of examples. The problem: these examples live in 13 different formats scattered across research labs, each speaking a different dialect. ADP solves this by introducing a middle language that every dialect can translate into, so one training run works on all the data at once. The result: a model trained on ADP jumps 20% higher in performance than one trained only on data from a single source.

The fragmentation trap

Agent training data lives in silos. One lab stores tool-use examples as JSON. Another stores web-browsing traces as XML logs. A third encoded code debugging steps as Python objects. Each format is perfectly reasonable within its own context, but if you want to train one agent model on all three datasets, you first have to write three separate converters—or give up and train separate models for each domain.

A beginner might try the simple fix: write a custom converter for each dataset, manually mapping actions and observations into a shared training format. This works, but it breaks at scale. As new datasets appear, you write more converters. Each one is bespoke, fragile, and requires deep knowledge of that dataset's idiosyncrasies. The real bottleneck is not lack of data—it is that the data is locked in incompatible cages.

In one sentence. Create a universal middle language (ADP) that every dataset dialect can translate to, so you train once and use all data at once.

What the paper changes

What the paper changes

The paper introduces a single standardized schema—ADP—that sits between raw datasets and training pipelines. Instead of building a new converter every time a new dataset appears, you describe your dataset once in ADP terms, and it automatically works with any downstream framework. The object is the representation format itself.

the object it moves  =  the representation format
The hidden quantity

The hidden quantity: information loss in translation

measured quantity  =  fidelity of the conversion

When you translate from one format to another, you can lose information. A tool-use action that includes many details in the original (like which button was clicked, what text appeared, and how long the action took) might become generic in the new language. The paper's hidden quantity is fidelity: how much of the original trajectory's meaning survives the translation to ADP without being flattened or discarded.

The paper achieves this by designing ADP to be expressive enough to capture actions, observations, and tool calls from every dataset, but simple enough to parse without per-dataset engineering. If fidelity drops, the model trains on corrupted data. If fidelity is high, the unified training catches signal that any single-source model would miss.

Why it works

Why unifying data works

The mechanism has two parts. First, fragmentation destroys signal. When each dataset trains a separate model, that model learns only the patterns in one domain (e.g., only code tasks or only web browsing). It never sees the pattern that reasoning about tool interactions is similar across domains. Second, when you unify the data through ADP, you expose the model to all 13 domains at once. The model learns patterns that work across domains (e.g., how to interpret an error message, how to decide which button to click, how to break a big task into steps) by seeing those patterns repeated in different domains. These shared patterns transfer because the underlying reasoning is the same whether you are debugging code or navigating a website. The 20% gain comes from this: examples from coding teach the model something useful for browsing, which a model trained only on browsing data never learns.

The conversion pipeline preserves information by design. Each dataset specifies how its actions and observations map to ADP's schema. ADP itself is built on Pydantic (a schema validator that enforces structure), so no information leaks silently. The model never trains on corrupted data because malformed conversions fail at the validation step, not downstream.

The conversion formula

First in words:

For each trajectory in dataset_i, convert to ADP, validate, then format for training. Aggregate all converted trajectories into one pool and train on them together.

Then the compact form:

loss = (1/N) * sum_{j=1}^{N} L_j(model, trajectory_ADP_j) where N = total trajectories across all 13 datasets after conversion

Every symbol:

lossthe training error on the unified dataset
Ntotal number of trajectories after converting all 13 datasets to ADP
trajectory_ADP_jthe j-th trajectory in ADP format (converted from its native format)
L_jsupervised finetuning loss for trajectory j (e.g., cross-entropy on next action)
modelthe agent model being trained
A tiny worked example
Dataset 1 (API calls, native JSON): 100 trajectories → convert to ADP → 100 ADP trajectories
Dataset 2 (web browsing, native XML): 50 trajectories → convert to ADP → 50 ADP trajectories
Dataset 3 (coding, native Python): 30 trajectories → convert to ADP → 30 ADP trajectories
Pool these: 180 ADP trajectories. Single training run on all 180. No separate models.
Contrast: training on Dataset 1 alone (100 traj) + separately on Dataset 2 (50 traj) → two separate models, each sees less signal, each misses cross-domain patterns.

The loss is computed on the combined pool; weight updates flow across all 13 datasets in a single training run, enabling cross-domain transfer that isolated training cannot achieve.

What can go wrong

What can go wrong

Incomplete converters. If a converter omits critical fields (e.g., error messages or intermediate observations), ADP's fidelity drops. The unified model trains on corrupted signal and performance collapses.
Incompatible action spaces. Some datasets might use actions that do not map cleanly to ADP (e.g., a custom robot command with no text equivalent). The converter must make an interpretation choice, and a bad choice silently loses information.
Training instability. Mixing 13 datasets with different reward structures and trajectory lengths can cause the model to overfit to high-volume domains (e.g., coding) at the expense of smaller ones (e.g., research).
Done right. Validate every converter output with Pydantic before training. Track per-domain performance during training to catch instability early. Publish the converters and ADP schema so downstream users can spot and fix mapping errors.
What a runnable demo should prove

What a runnable demo should prove

Write a minimal demo that converts two real datasets (e.g., one API-use dataset and one code-task dataset) into ADP format. Verify that the conversion preserves all critical information by spot-checking converted trajectories against the originals. Then train two models: one on the unified ADP data (both datasets mixed), one on each dataset separately. Measure accuracy on a held-out test set from each domain.

cross_domain_gain = (accuracy_unified_on_domain_A - accuracy_single_A) + (accuracy_unified_on_domain_B - accuracy_single_B)

If unification works, the unified model outperforms single-domain models on both domains. This happens because the unified model saw examples from both domains during training, so it learned patterns (like how to interpret error messages or break a task into steps) that work in both places. A single-domain model never sees those patterns repeated, so it cannot learn them.
