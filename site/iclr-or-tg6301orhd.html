Agent Data Protocol

A common language that turns training data from different tools and tasks into one unified format so agent models can learn from all of it at once.

Paper explainersAll themesAgents & Tool Use

AI agents (programs that use tools and take actions) need training data, but that data lives in many different formats: some tools store it as API logs, others as browser traces, others as code snippets. A single agent model cannot easily learn from all of them together because the data speaks different languages. The Agent Data Protocol (ADP) is a lightweight translation layer—an interlingua—that converts this hodgepodge of formats into one universal structure, letting researchers combine 13 existing agent training datasets and train a single model that works well at many different kinds of agent tasks.

Zero assumption version

Data is scattered in incompatible formats

Today, training data for agent models is fragmented. A dataset for teaching an agent to use APIs stores data one way (lists of function calls and results). A dataset for teaching browsing stores data another way (screenshots and click traces). A dataset for coding stores data yet another way (problem statements and code solutions). Each has its own file format and structure.

A naive approach would be: write a separate training pipeline for each format. But this fails at scale. If you want to combine 13 datasets and train one agent model on all of them, you would need to write 13 adapters. Every new dataset means more code. Researchers waste time on data plumbing instead of improving agents. The underlying agent training step (called supervised fine-tuning, where a model learns to imitate examples) is always the same. Only the data translation is different.

In one sentence. Agent training data lives in 13+ different formats, forcing researchers to build one adapter per format instead of focusing on training the model itself.

What the paper changes

What the paper changes

The Agent Data Protocol does not change how agent models learn or how they work at test time. Instead, it changes the input: the format of the training data itself. Every dataset—API logs, browser traces, code problems—gets translated into this one common schema before training begins.

The hidden quantity

The key quantity: task coverage

measured quantity  =  fraction of tasks a single model handles

Before ADP, when datasets lived in incompatible formats, researchers had to choose: train separate models for APIs, separate models for browsing, separate models for coding. A single model would fail on unfamiliar task types because the training data never taught it to handle them. Task coverage is the fraction of different agent tasks (APIs, browsing, coding, software engineering, general workflows) that one trained model can handle well.

The paper estimates task coverage by testing the unified model on standard benchmarks in each category: coding performance, browser automation, API use, and research tasks. They measure what fraction of these diverse benchmarks the single model wins or ties on compared to task-specific baselines.

Why it works

Why a universal language unblocks training

The core mechanism is simple: a training algorithm (called supervised fine-tuning) learns by comparing what a model predicts to what the correct answer was, and nudging the model's internal numbers (its weights) to match the correct answer better. But this algorithm has one requirement: it needs examples in a consistent format. When API data says 'call function foo with argument x, got result y' in one notation, and browsing data says 'I clicked on element #id' in a different notation, the training algorithm breaks—it cannot compare apples to apples.

ADP solves this by creating one schema (a template) that describes any agent task: what the world state is (a list of perceivable facts), what actions are available (a list of possible moves), what action the agent took, and what the result was. This template is simple enough to parse and expressive enough to capture APIs, browsing clicks, code submissions, and open-ended workflows. Once all 13 datasets fit into this template, the training algorithm sees them as one coherent stream of examples, learns patterns across all of them (a skill that works for browsing also helps with coding, because both involve understanding instructions and responding), and builds a single model that handles multiple task types.

Why does a multi-task model beat single-task models by 20% on average? Because shared learning improves each task. When the model trains on APIs, it learns what an input and output look like. When it then trains on coding, those same concepts (input: problem statement, output: code) reinforce the same internal patterns. The weights end up more general—they work well in more different situations—than if trained only on one task type. The universal format is the bottleneck remover: without it, you never get to combine the data, so you never get this shared learning benefit.

The protocol structure

First in words:

Each ADP example stores: state (facts about the world), actions (what the agent could do), chosen_action (what the agent did), result (what happened). Loss = sum over all examples of how wrong the model's prediction was.

Then the compact form:

loss = sum_i ||model(state_i) - chosen_action_i||^2 + sum_j ||model(state_j) - result_j||^2

Every symbol:

state_ithe i-th example's observable world facts (sensors, tool outputs, page HTML)
chosen_action_ithe i-th example's correct action (API call, click, code line)
model(state_i)what the model predicts should happen given that state
result_jwhat actually happened after the action (tool response, new page, output)
||...||^2squared distance: how far the model's guess is from reality
A tiny worked example
Example 1 (API task): state = 'get user by ID 42', model predicts 'call API endpoint /users?id=42', correct answer = 'call API endpoint /users?id=42'. Difference = 0. Loss contribution = 0.
Example 2 (code task): state = 'sort a list in Python', model predicts 'x = sorted(x)', correct answer = 'x = sorted(x)'. Difference = 0. Loss contribution = 0.
Example 3 (browsing): state = 'page says Buy Now button at coords 150,300', model predicts click at 140,310, correct = click at 150,300. Difference = sqrt((150-140)^2 + (300-310)^2) = sqrt(200) ≈ 14 pixels. Loss contribution ≈ 196.
Total loss = 0 + 0 + 196. Training nudges the model to predict clicks more accurately. The unified loss sums over all task types.

The loss sums mistakes across all task types equally because they all speak ADP now; the model learns from successes and mistakes in APIs, browsing, and coding together.

What can go wrong

What can go wrong

Lossy translation. If a native format has details the ADP schema does not capture, those details vanish in translation. Example: an API dataset records exact timing of calls; ADP only records the sequence. Timing-critical tasks might train worse because the model never saw the timing signal.
Overfitting to frequent tasks. If one task type (e.g., coding) has much more data than others, the training algorithm biases toward it. The unified model becomes better at code than APIs because the training loop sees more code examples, so the weights get tuned more often on code mistakes than on API mistakes. This defeats the goal of balanced multi-task learning. Fixing this requires careful mixing of datasets during training (showing roughly equal amounts of each task type per epoch) or weighting the loss so APIs count equally even if fewer examples exist.
Incompleteness in the template. ADP is designed to be simple, but new kinds of agent tasks (like multi-step planning with internal goals) may not fit neatly. If a future dataset requires information the schema does not support, it cannot be translated without adding a new optional field, which may break existing tools.
Done right. The paper ships code to convert existing datasets, and provides clear documentation of the schema. Researchers can quickly check if their data fits, translate it, and contribute to the unified corpus. Public release of code and data removes friction.
What a runnable demo should prove

What a runnable demo should prove

Build a minimal demonstration: (1) Take two real agent datasets in different formats (e.g., an API dataset in JSON, a coding dataset in Python AST format). (2) Write translators from each format to ADP. (3) Merge them under ADP. (4) Train a small agent model (e.g., a 7B-parameter language model) on the merged data for a few epochs. (5) Test on tasks from both domains. The demo should show that the unified model achieves higher accuracy on both tasks than a model trained only on one domain, because the shared learning across task types teaches the model more general patterns. Also show that adding a new dataset (without rewriting training infrastructure) is as simple as writing one new translator.

multi_task_gain = (accuracy_on_api + accuracy_on_code) / 2 — (accuracy_api_only + accuracy_code_only) / 2

The demo must make it impossible to miss: one training pipeline (instead of 13), no per-dataset engineering, one model handles multiple domains (instead of task-specific models), and better performance (because shared learning teaches more general patterns). That is the bottleneck that ADP removes.
