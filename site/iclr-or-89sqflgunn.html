Graph Random Features for Scalable Gaussian Processes

Use random walks to estimate graph similarities quickly, making Bayesian prediction on million-node graphs practical on a single computer.

Paper explainersAll themesOptimization

Gaussian processes (a tool for making principled guesses about unknown values) work perfectly on small graphs but become impossibly slow on large ones: they need to compute a similarity score between every pair of nodes, a task that takes hours even for modest sizes. This paper replaces the exact similarity table with a fast approximate one built from random walks, shrinking the slowest step from hours to minutes.

Zero assumption version

Exact similarity scores take forever on large graphs

A Gaussian process (a statistical model that makes predictions with honest confidence intervals) works by comparing every pair of nodes on a graph. A node is similar to nodes it connects to, dissimilar to distant ones; the model captures this by building a similarity table: a grid where row i, column j tells how much node i resembles node j. Computing and storing this table, plus inverting it to make predictions, takes time proportional to the number of nodes cubed. On a million-node graph, that is a quintillion operations. Not practical.

A beginner might try: just use the raw edge list. But a Gaussian process needs a learned measure of similarity that accounts for the graph structure, not just direct edges. Using the edge list directly gives bad predictions.

The trick. Instead of building an exact similarity table, estimate it using random walks, cutting the time from proportional to N cubed down to proportional to N to the one-point-five power.

The algorithm as a flow

What it actually does

1. Take a graph and observed measurements

You have a graph with millions of nodes and noisy observations (measurements) at some of those nodes.

2. Launch random walks

Instead of computing exact node similarities, run many random walkers that hop to neighboring nodes and record their paths.

3. Estimate similarities from walk overlaps

Paths that overlap frequently come from similar node neighborhoods. Paths that rarely meet come from distant regions. Count overlaps to estimate the similarity table.

4. Use iterative linear solvers

Feed the estimated table into a solver that works without ever storing the full table explicitly, keeping memory low.

5. Make predictions and decide where to observe next

Use the learned model to predict at all unobserved nodes and intelligently pick new nodes to measure, balancing exploration and reducing prediction uncertainty.

What the paper changes

What changes: the similarity table

The paper replaces an exact, slow similarity table with an approximate, fast one built from random walks. That single change makes Bayesian prediction on huge graphs tractable.

The hidden quantity

The hidden quantity: random-walk-to-random-walk alignment

measured quantity  =  Walk overlap count

Random walks are finite sequences of nodes visited by a walker hopping randomly. If two nodes are in similar neighborhoods, walks starting from them overlap more often. The hidden quantity the paper measures is: how many times do random paths cross? The more overlaps, the more similar the nodes.

The paper estimates this by sampling thousands of random walks, recording which nodes each walk visits, and counting overlaps between walks starting at different nodes. This overlap count, scaled correctly, is the random-walk estimator of the true similarity table.

Why it works

Why it works: sampling beats exact computation

The core reason this is faster: a Gaussian process needs to know similarity between nodes to make predictions because the strength of its confidence in a guess depends on how close the new node is to nodes it has already seen measurements from. Exact similarity requires computing a full table (time proportional to nodes cubed). Random walks give you a sparse, approximate version. Here is why the approximation is good enough.

Random walks naturally explore a graph according to its structure: nodes in dense clusters get revisited often, isolated nodes rarely. If you launch many random walks and record which nodes each one visits, walks starting near each other will share many nodes. Counting these shared nodes (weighted by how often they appear) estimates the true similarity. The paper proves (with probability bounds) that this estimate is close to the true value. Since a random walk samples only a tiny fraction of all possible paths, it is vastly faster.

The second speedup: you never explicitly form the similarity table. Instead, you use an iterative solver that multiplies by the table implicitly, using the walks on the fly. This cuts memory from quadratic (storage for the full table) to linear in the number of walks, which is independent of the graph size. On a million-node graph, this means using a laptop instead of a data center.

Math after the picture

The similarity approximation

First in words:

The random walk estimate Phi approximates the true kernel K by averaging random feature vectors. Each random feature vector for node i is built by sampling a walk starting at i, recording which nodes it visits, and weighting them by the walk probabilities. The estimated kernel at node pair (i,j) is the inner product of their random feature vectors.

Then the compact form:

Estimated kernel K-hat[i,j] = Phi[i] dot Phi[j], where Phi[i] is built from random walks starting at node i

Every symbol:

Phi[i]random feature vector for node i, built from its walks
Phi[i] dot Phi[j]inner product of the two feature vectors = estimated similarity
K-hatthe approximate similarity matrix
Kthe true similarity matrix (expensive to compute exactly)
nnumber of random walks sampled to estimate the features
tthe approximation error threshold in the probability bound
A tiny worked example
Say node 1 and node 2 are close in a graph. We launch 100 random walks starting at node 1 and 100 starting at node 2.
Walks from node 1 visit: {1,3,5} 80 times, {1,4} 20 times.
Walks from node 2 visit: {2,3,5} 75 times, {2,4,6} 25 times.
Common neighborhood {3,5} appears in 80 walks from node 1 and 75 walks from node 2 -> high overlap.
We weight these overlaps and compute their inner product -> estimate of K[1,2] ≈ 0.78 (close to true value).
Same process for all pairs, but using only O(n) walks per node, not checking all N pairs explicitly.

The random walk estimator is an unbiased Monte Carlo approximation: on average, the walk-based inner product equals the true similarity, and more walks reduce the variance.

What can go wrong

What can go wrong

Too few random walks: variance in the estimator. If you launch only a handful of walks per node, the random-walk similarities have high variance (they bounce around) because overlap counts from small samples are unreliable. The paper provides a formula for how many walks you need; fewer walks are faster but less stable because averaging over more independent samples reduces randomness.
Graph structure mismatch. Random walks assume the graph is connected and well-mixed. On graphs with isolated clusters, walks rarely cross between clusters, so cross-cluster similarities are estimated poorly. The method works best on well-mixed graphs.
Hyperparameter tuning burden. Random walks have tuning parameters: walk length, termination probability, number of walks. Choosing them requires pilot experiments. Too-short walks underestimate long-range similarity; too-long walks waste computation.
Done right: validate and adapt. Use the probabilistic accuracy guarantees in the paper to choose the number of walks for your target error. On graphs with clustering, apply the method per-cluster first. The payoff: run Bayesian optimization on graphs 1000x larger than before.
