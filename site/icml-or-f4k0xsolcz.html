Rel-MOSS: Class Balance in Relational Database Learning

When a graph neural network learns from relational databases, it must keep minority-class entities from being drowned out by majority-class neighbors.

Paper explainersAll themesGraph & Geometric Learning

Databases store data as connected tables: customers relate to orders, orders relate to products. When you use a graph neural network to classify entities (like predicting which customers will churn), the network learns by combining information from neighboring entities. But when one class is rare—say, only 5% of customers actually churn—the messages from the many majority customers overwhelm signals from the few minority cases, producing a useless model. Rel-MOSS fixes this by selectively boosting signals from minority neighbors based on their relationship type.

Zero assumption version

Minority entities disappear into the crowd

A relational database is a set of connected tables. A graph neural network treats each table row as a node and table relationships as edges. To classify a customer node, the network reads messages from all neighboring nodes (orders, purchases, payments) and combines them. A naive approach: take an average of all neighbor messages. But in imbalanced data—where only 5% of customers churn and 95% do not—the average is dominated by the non-churners. A churning customer's rare-class neighbors contribute almost nothing; their signal gets buried.

In an imbalanced dataset—say 95 normal emails and 5 spam—averaging all messages equally means the 5 spam cases add almost nothing to the average. The network learns to predict 'normal' for everything, achieving 95% accuracy by ignoring the rare class entirely.

The problem in one sentence. Graph neural networks average neighbor signals equally, so minority-class entities are overwhelmed by majority-class neighbors.

The algorithm as a flow

What it actually does

Detect imbalance

Count entities in each class. Identify which classes are rare.

Gate by relationship type

For each type of connection (customer-to-order, customer-to-payment), learn a separate gating weight that controls message flow.

Amplify minority pathways

When a message comes from a minority-class neighbor along a specific relationship, the gate opens wider.

Synthesize new minority examples

Create artificial minority entities by blending real ones, preserving their relationship patterns.

Train on balanced data

Network now sees enough minority examples to learn their genuine patterns.

What the paper changes

What changes: neighbor messages per relationship type

The paper changes how neighbor messages are weighted during aggregation. In a standard graph neural network, a message from any neighbor gets the same weight. Rel-MOSS introduces a separate gating weight for each relationship type, so the network learns whether to trust messages from neighbors connected via customer-to-order relationships differently than neighbors connected via customer-to-payment relationships.

the object it moves  =  neighbor message weights per relationship type
The hidden quantity

The hidden quantity: minority-specific message flow per relationship

measured quantity  =  relation-wise gate value (0 to 1)

A 'relation-wise gate value' is a number between 0 and 1 that controls how much a neighbor's message contributes when they are connected via a specific relationship type. In a standard network, all neighbors contribute equally (gate at 1.0 for all). Rel-MOSS learns different gate values for each relationship: if minority entities tend to send important signals via 'owns-product' edges, that gate learns to open wider (closer to 1.0); if they send noise via 'viewed-once' edges, that gate closes (closer to 0.0).

The paper estimates this by backpropagating through task loss: during training, it adjusts each gate to reduce prediction error. If nudging a gate wider makes fewer mistakes on the validation set, that gate increases; if nudging it narrower cuts errors, it decreases. Over many iterations, gates that carry useful minority signals settle at high values (stay open), while gates that mix signal with noise settle lower (close), because only gating adjustments that reduce error are reinforced.

Why it works

Why it works: separate gates let rare classes speak

Standard graph networks average all neighbor messages. If 95% of neighbors are majority class, their average dominates. Rel-MOSS fixes this by learning a separate gate (a multiplier between 0 and 1) for each relationship type. During training, if the network notices that minority-class neighbors connected via certain relationships often belong to the same class, it learns to open that gate wider, amplifying their signal. If neighbors connected via other relationships are a random mix, it keeps that gate narrow, filtering noise.

The second half—the minority synthesizer—generates artificial new minority entities by interpolating between real minority examples while respecting the relational structure (preserving which tables they connect to). This doubles or triples the minority presence in training data. The network now sees enough minority examples to learn their genuine decision boundary instead of defaulting to majority class.

Math after the picture

How to compute gated neighbor aggregation

First in words:

For each entity node, sum the weighted messages from all neighbors. Weight = (gate for this relationship type) times (attention weight for this neighbor). Divide by total gates applied.

Then the compact form:

agg_i = sum_r alpha_r * sum_{j in N_r(i)} (a_ij * m_j)

Every symbol:

agg_iaggregated message for entity i
alpha_rlearned gate for relationship type r
N_r(i)neighbors of i connected via relationship type r
a_ijattention weight between i and j
m_jmessage (feature vector) from neighbor j
A tiny worked example
Entity X (customer, minority class) has 4 neighbors: 2 via 'placed-order' (majority), 2 via 'similar-profile' (also minority).
Gate for 'placed-order' relationship: 0.3 (low—majority neighbors are noisy).
Gate for 'similar-profile' relationship: 0.9 (high—minority neighbors are reliable).
Neighbor A (order, majority): attention 0.5, message [4, 3]. Contribution: 0.3 * 0.5 * [4, 3] = [0.6, 0.45].
Neighbor B (order, majority): attention 0.5, message [3, 4]. Contribution: 0.3 * 0.5 * [3, 4] = [0.45, 0.6].
Neighbor C (similar, minority): attention 0.8, message [8, 7]. Contribution: 0.9 * 0.8 * [8, 7] = [5.76, 5.04].
Neighbor D (similar, minority): attention 0.7, message [7, 8]. Contribution: 0.9 * 0.7 * [7, 8] = [4.41, 5.04].
Total aggregation: [0.6 + 0.45 + 5.76 + 4.41, 0.45 + 0.6 + 5.04 + 5.04] = [11.22, 11.13]. Minority neighbors now dominate.

Each relationship type has its own gate, so messages travel through relationship-specific filters before being combined. Rare classes regain their voice.

What can go wrong

What can go wrong

Extreme imbalance (>100:1 ratio). Even with gating and oversampling, if minority class is extremely rare, the network struggles to generalize. More synthetic examples needed, or pre-trained features (learned from related data) to initialize.
Relationship types are noisy or uninformative. If the relationship type does not correlate with class membership, gating per relationship wastes capacity. Should combine with other signals (entity features, temporal patterns).
Synthesized examples are too similar to real ones. If oversampling creates clones (not diverse variations), the network memorizes rather than generalizes. The synthesizer must interpolate in a way that respects relational structure but adds variation.
Done right: use relation-aware gating only when relationships correlate with class; combine synthetic oversampling with careful feature engineering; evaluate on separate held-out minority examples to check generalization, not just accuracy on the training set. Strong results come from treating relationship signals seriously, not just as a gate but as domain knowledge. The paper's 2.46% improvement in Balanced Accuracy and 4% in G-Mean (a metric that rewards both classes equally) confirms the approach works in practice.
What a runnable demo should prove

What a runnable demo should prove

Build a small synthetic relational database with three tables: User (with a binary class label, say 'active' vs 'inactive'), Post (many posts per user), and Comment (many comments per post). Make it imbalanced: 80% inactive users, 20% active. Train a standard graph neural network on it. Then train Rel-MOSS with relation-wise gates (one gate for Post-edges, one for Comment-edges) and synthetic oversampling. Compare Balanced Accuracy (the harmonic mean of accuracy on each class) and G-Mean (geometric mean, also class-balanced) on a held-out test set.

Balanced Accuracy = (accuracy_inactive + accuracy_active) / 2; G-Mean = sqrt(accuracy_inactive * accuracy_active)

A good demo must show that Rel-MOSS's Balanced Accuracy and G-Mean are noticeably higher than the standard network's, especially on the minority active-user class, while majority-class accuracy stays competitive. The improvement should be >2% on Balanced Accuracy to match the paper's claim.
