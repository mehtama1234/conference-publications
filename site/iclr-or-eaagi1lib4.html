XIL: Cross-Expanding Incremental Learning

XIL studies continual learning when both classes and domains expand over time, and XEED addresses it with domain-specific prompts, residual-guided feature modulation, and prototypes that grow to cover new class-domain pairs in both directions.

Paper explainersAll themesContinual Learning

Ordinary class-incremental learning assumes that new tasks introduce new classes but stay within roughly the same visual domain. That assumption removes a major part of the real problem. In practice, new data can bring both unseen classes and unseen domains. When that happens, the system must do two different transfers at once. It must learn new classes inside old domains, and it must extend old classes into new domains. The paper calls this bidirectional domain transferability, or BiDoT. XEED is designed for that setting. It keeps domain-specialized prompts so the backbone can condition on domain-specific appearance, uses residual-guided modulation to separate domain variation from class content, and maintains evolving class prototypes so the meaning of each class expands as more domains arrive.

Zero assumption version

Why standard class-incremental learning is too narrow

In class-incremental learning, the model receives tasks one after another and cannot store all old data. The standard benchmark only adds new labels over time. That mainly tests forgetting across classes. It does not test what happens when new domains arrive with different backgrounds, style, sensor statistics, or rendering conditions.

Once domains also evolve, the old objective is insufficient. Suppose the model first learns digits in a clean domain, then sees letters in a noisy domain. Later it should recognize letters in the clean domain and digits in the noisy domain, even if those exact class-domain combinations were never shown together. Existing methods rarely require this because they only ask for new classes in their original domains.

This is why the paper defines XIL. The difficulty is no longer just preserving class boundaries. The model has to expand class semantics across domains in both directions while avoiding catastrophic forgetting.

The new requirement. Every new task expands two sets of associations: new classes must connect to old domains, and old classes must connect to the new domain.

The algorithm as a flow

What it actually does

Define XIL stream

Each task introduces some new classes, some new domains, or both, and evaluation asks for predictions across all accumulated classes and domains.

Use domain-specialized prompts

Attach prompt weights, which are small learned prompt values, that condition the backbone on the current domain so domain-specific appearance changes are handled explicitly.

Apply residual-guided modulation

Estimate residual domain effects in the feature representation and modulate features so class information is preserved while domain-specific variation is adapted.

Maintain evolving prototypes

Store class prototypes that are updated as the class is observed under more domains, so each prototype covers a wider semantic support.

Measure BiDoT

Evaluate not only standard accuracy but also how well the model transfers old classes to new domains and new classes to old domains.

What the paper changes

What the paper changes

The paper changes the target representation of a class. Instead of treating a class as fixed after its first domain, XEED lets the class prototype evolve as the stream introduces new domains and new neighboring classes.

the object it moves  =  class semantics over time
The hidden quantity

The hidden quantity: Cross-domain class coverage

measured quantity  =  bidirectional domain transferability

Standard incremental accuracy only checks whether the model predicts labels correctly on the data it has seen. XIL needs a stronger internal property: the features used to represent a class should still separate that class after the domain changes, and the features used to represent a domain should still support newly added classes, because evaluation includes class-domain combinations that were not shown together during training and ordinary accuracy on seen pairs cannot test that behavior. The paper packages this requirement as bidirectional domain transferability.

BiDoT is hidden because it is not a single training label. It is a structural property of the learned representation. You only see it when the evaluation asks for missing class-domain combinations that were not directly trained together. XEED's prompts, residual modulation, and evolving prototypes are all aimed at increasing this coverage.

Why it works

Why XEED is built from three parts

Domain-specialized prompts give the backbone a controlled way to respond differently for different domains. Without them, the network has to use one shared representation for all appearance regimes, which makes interference more likely. Prompts isolate some of the domain-specific adjustment into a small set of domain-conditioned weights.

Residual-guided representation modulation handles the fact that domains differ in more than one way. Some feature changes are useful for classification and some are not. The residual term is meant to capture what remains after the main class content is explained, then use that signal to adjust features without rewriting the class identity from scratch.

Evolving prototypes are the memory mechanism for semantics. A prototype is a representative feature list for a class. If that feature list is fixed after the class first appears, it encodes only one domain slice of the class. XEED keeps updating prototypes as new domains arrive, so the class center expands. This allows old classes to appear under new-domain feature statistics and new classes to be compared against feature statistics from older domains, because the class summary is no longer tied to one domain-specific feature pattern.

Math after the picture

A prototype expansion view of the objective

First in words:

Train a domain-conditioned feature extractor, then keep class prototypes close to current examples while preserving old prototype information so each class can expand across domains instead of being overwritten.

Then the compact form:

L_XEED = L_cls(f_theta(x, p_d), y) + alpha L_res(f_theta, d) + beta ||z - c_y||^2 + gamma L_stability(c_y^{old}, c_y^{new})

Every symbol:

f_theta(x, p_d)feature extractor with parameters theta and domain-specific prompt p_d
yclass label
ddomain identity for the current task
L_clsclassification loss over all seen classes
L_resresidual-guided modulation term that accounts for domain variation
zcurrent sample embedding
c_yprototype for class y
L_stabilityterm that keeps new prototype updates from erasing earlier class information
alpha, beta, gammaweights for the domain, prototype, and stability terms
A tiny worked example
Task 1 shows class '2' only in domain A, so its prototype is c_2^A.
Task 2 introduces domain B with classes '7' and '9'.
A naive class-incremental model only learns the new classes in B and preserves old class '2' for A.
XEED uses the B-specific prompt to encode new samples, then updates the class prototypes so the representation of '2' is still separable when the domain statistics change.
Later, when evaluation asks for class '2' in domain B, the prototype has not been trapped inside A-only features, so the decision boundary can transfer.

The exact implementation details differ by architecture, but the essential structure is domain-conditioned features plus prototypes that grow without forgetting.

What can go wrong

What can go wrong

Domain labels or domain grouping may be ambiguous. XEED assumes the training stream can attach domain-specific prompts in a coherent way. If domains are mixed, continuous, or mislabeled, prompt specialization becomes noisy.
Prototype updates can still drift. If new-domain samples are heavily imbalanced or very different in appearance, the evolving prototype may move too far and weaken older domain support.
BiDoT is harder than ordinary replay-based retention. A replay buffer can help preserve old accuracy, but it does not automatically create missing class-domain associations because replay mostly revisits observed pairs rather than teaching the model how to combine old classes with new domains and new classes with old domains.
Done right. The approach is strongest when the backbone already has reusable visual features and the main challenge is expanding class semantics across a structured sequence of domains.
What a runnable demo should prove

What a runnable demo should prove

Build a small continual image stream with two domains and staggered class arrivals. For example, show digits 0-4 in domain A, then digits 5-9 in domain B. Compare a standard class-incremental baseline against XEED. Do not only test on the observed pairs. Also test digits 0-4 in domain B and digits 5-9 in domain A. Log both overall accuracy and a simple BiDoT-style score that averages performance on these cross-expanded pairs.

BiDoT = 0.5 * (accuracy old_classes_on_new_domains + accuracy new_classes_on_old_domains)

The demo should make clear that XIL is a different task from ordinary continual classification. A method can remember labels and still fail the cross-expansion test.
