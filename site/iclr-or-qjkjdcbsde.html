The Matthew Effect of AI Programming Assistants: A Hidden Bias in Software Evolution

This paper shows that coding assistants work better for mainstream languages and frameworks, which can push developers further toward ecosystems that already dominate the training data.

Paper explainersAll themesOther

Coding assistants now influence routine software decisions: which language to use, which framework to pick, and how fast a task gets done. This paper studies whether that help is evenly distributed across the software ecosystem by comparing assistant success across many tasks and many technologies. It is not. Mainstream languages and frameworks receive stronger assistant performance than niche ones. That matters because better assistant support lowers developer effort, so popular ecosystems can become even more attractive simply because the model has seen more of them before.

Zero assumption version

Assistant quality is not neutral across ecosystems

A coding assistant helps by turning developer intent into working code. If that help were evenly strong everywhere, it would raise productivity across the board because developers in every ecosystem would need about the same amount of manual repair. But software ecosystems are uneven: some languages and frameworks dominate public code, while others have much smaller footprints.

The paper asks a direct question: does model performance rise with ecosystem popularity? If yes, then assistant quality is not merely a convenience feature. It becomes a force that changes adoption, because developers will feel less friction in ecosystems where the assistant already performs well.

The hidden bias. Popular ecosystems can become easier to use with AI assistance, which may steer future adoption toward them even when that was not the user's original preference.

The algorithm as a flow

What it actually does

Construct large task sets

Build thousands of programming tasks and hundreds of framework-selection tasks across many ecosystems.

Run the assistant on each task

Measure whether the model produces workable solutions or good framework recommendations.

Group ecosystems by visibility

Separate mainstream ecosystems from niche ones using how common they are in the software world.

Compare success rates

Quantify how strongly assistant performance changes between mainstream and niche groups.

Interpret the productivity gap

Estimate how that performance gap can change software evolution by making some choices easier than others.

What the paper changes

What the paper changes

The paper changes the way we think about coding assistants. Instead of judging them only by average code quality, it treats them as ecosystem-level forces that can advantage some technologies over others.

The hidden quantity

The hidden quantity: productivity friction

measured quantity  =  extra developer effort caused by weak assistant support

The paper argues that the real quantity at stake is productivity friction. This is the extra work a developer must do when the assistant gives weaker help in one ecosystem than in another because failed suggestions have to be repaired by hand. The cost may appear as more rewrites, more debugging, or more manual search for the right library or framework.

That quantity is hidden because developers do not observe it as a single number. They feel it as repeated slowdowns. The experiments expose it by comparing success rates across ecosystems. When the assistant succeeds far less often in a niche setting, that gap translates into repeated extra effort for developers working there.

Why it works

Why popularity can compound through assistant performance

Coding assistants are trained on large code corpora. Mainstream ecosystems appear more often in those corpora, so the model sees more examples of their syntax, libraries, error patterns, and common project structures. That broader exposure gives the assistant more chances to learn what good solutions look like in those settings because repeated examples reveal common patterns and common fixes.

Better assistant performance lowers developer effort because more tasks complete successfully on the first try and fewer corrections are needed. Once that happens, teams may favor those ecosystems for practical reasons even if a niche tool is technically suitable. The bias is subtle because no one explicitly bans the niche option; it simply becomes more expensive to use in practice.

This is the Matthew-effect mechanism in the paper. Existing popularity leads to stronger assistant support, which lowers friction, which can attract more future use. The assistant therefore participates in software evolution by reinforcing ecosystems that already dominate model training data.

The asymmetry equation

First in words:

Measure the performance gap between mainstream and niche ecosystems by subtracting their success rates.

Then the compact form:

gap = success_mainstream - success_niche

Every symbol:

gapassistant advantage held by mainstream ecosystems
success_mainstreamtask success rate in mainstream languages or frameworks
success_nichetask success rate in niche languages or frameworks
A tiny worked example
Suppose the assistant succeeds on 78 of 100 tasks in a mainstream language.
Suppose it succeeds on 49 of 100 comparable tasks in a niche language.
Then success_mainstream = 0.78 and success_niche = 0.49.
The gap is 0.78 - 0.49 = 0.29.
That 29-point gap matters because it means the niche developer must rescue many more tasks by hand.

The paper is not only saying the gap exists. It is saying the gap changes developer incentives because it changes how much work each ecosystem demands.

What can go wrong

What can go wrong

Mistaking correlation for the whole cause. Popularity is not the only reason a technology gets adopted, so the paper cannot claim assistant bias explains everything about ecosystem growth.
Task construction bias. If the benchmark tasks favor mainstream workflows, part of the measured gap could come from the benchmark itself rather than the assistant alone.
Rapid model updates. A newer model or additional targeted training can shrink the measured gap, so the size of the effect may change over time.
Done right. The result remains useful when task families are broad and evaluation is careful, because a persistent success-rate gap still reveals uneven assistant support across ecosystems.
What a runnable demo should prove

What a runnable demo should prove

Create matched programming tasks across pairs of ecosystems: one mainstream and one niche. Run the same assistant with the same task descriptions, score whether the produced solution works, and record how many manual fixes are needed after the first draft. Repeat the process for framework recommendation tasks.

The demo should make the mechanism visible: weaker assistant success raises manual repair effort because more failed drafts must be fixed by hand, which can nudge teams toward ecosystems where the assistant already performs better.
