Numina-Lean-Agent: An Open and General Agentic Reasoning System for Formal Mathematics

Numina-Lean-Agent treats formal theorem proving as a general coding-agent job, using Lean tools through MCP so that one agent can search, test, and revise proofs autonomously.

Paper explainersAll themesAgents & Tool Use

Modern formal theorem proving systems increasingly look like agents rather than single predictors. They search for useful lemmas, query a proof assistant, inspect errors, revise failed attempts, and try again. Many strong systems achieve this with specialized pipelines and specially trained theorem-proving models. That raises a practical question: do we actually need a narrow prover, or can a strong general coding agent handle formal mathematics if it gets the right tool access? Numina-Lean-Agent argues for the second path. It uses a general coding agent with Lean-specific MCP tools for theorem lookup, proof checking, informal reasoning, and auxiliary tasks. The result is a flexible formal-math agent that solves all Putnam 2025 problems and can also work with mathematicians on larger formalization projects such as the Brascamp-Lieb theorem.

Why task-specific proving pipelines are limiting

A formal proof task rarely succeeds in one pass. The agent has to read the theorem statement, recall related lemmas, try a proof script, inspect Lean's feedback, and revise the script. Specialized theorem-proving systems can do this well, but they often depend on custom pipelines or trained provers that are hard to extend and hard to reproduce.

That specialization becomes a limitation when the task moves beyond a fixed benchmark. Mathematicians need a system that can search libraries, explain a proof idea, interact with external tools, and adapt to different formalization workflows. The paper asks whether a general coding agent can serve as the reasoning core if it is given good access to Lean and theorem-retrieval tools.

The paper's move in one sentence. Use a strong general coding agent as the main reasoner and connect it to Lean-specific tools through MCP, so that formal theorem proving becomes one instance of general agentic problem solving.

The algorithm as a flow

What it actually does

Step 1: Read the formal goal

Interpret the theorem statement in Lean so that the agent knows exactly what must be proven.

Step 2: Retrieve useful theorems and context

Query Numina-Lean-MCP tools for related lemmas and definitions because many proofs fail without the right library facts.

Step 3: Draft a proof script

Use the general coding agent to write Lean code that applies the retrieved facts to the current goal.

Step 4: Run Lean and inspect feedback

Check the script inside Lean so that syntax errors, type mismatches, and unfinished goals become visible.

Step 5: Revise with tools and retry

Use the feedback, extra retrieval, and auxiliary reasoning tools to repair the proof until Lean accepts it.

The hidden quantity

The hidden quantity: proof-state progress

measured quantity  =  how much each tool-assisted revision reduces the gap between the current proof state and a fully accepted proof

The most important quantity is proof-state progress. A proof attempt is not merely right or wrong. It may close some goals, expose a missing lemma, or narrow the remaining obligations. Good agent behavior steadily reduces that gap between the current Lean state and a finished proof.

Numina-Lean-Agent makes progress because it can observe Lean's exact feedback and then choose a suitable next tool action. Sometimes the next action is theorem retrieval. Sometimes it is rewriting the proof script. Sometimes it is informal reasoning to decide what lemma should be searched for. The agent succeeds when each loop step reduces the unresolved proof burden.

Why it works

Why it works

Formal mathematics is well suited to agent loops because correctness feedback is precise. Lean does not say a proof sounds good; it says whether the code type-checks and whether any goals remain. That exact feedback turns proving into an iterative repair problem that a strong coding agent can handle.

A general coding agent is useful here because the work is broader than one prediction step. The agent must read tool output, choose retrieval queries, write Lean code, interpret errors, and decide when to change strategy. Those are general interactive skills, so a good coding agent can transfer them into formal math if the right tools are available.

The MCP connection matters because it keeps the system extensible. New theorem search tools, proof-state inspectors, or helper services can be added without redesigning the entire prover. That is why the paper frames formal reasoning as an agentic tool-use problem rather than a narrow one-model proving task.

Math after the picture

The proving loop objective

First in words:

Choose the next tool action that most reduces the remaining proof burden according to Lean's current proof state.

Then the compact form:

action_t* = argmax_a progress(proof_state_t, a)

Every symbol:

action_t*the next chosen tool or coding action at step t
proof_state_tthe current Lean state, including open goals and errors
progress(proof_state_t, a)how much action a is expected to reduce the remaining proof burden
aa candidate next move such as retrieval, code revision, or auxiliary reasoning
A tiny worked example
Suppose the current proof attempt leaves two open goals and one missing lemma.
Trying another tactic without retrieval may close nothing, so its progress value is low.
Retrieving a theorem that rewrites the goal may reduce the problem to one open goal, so its progress value is higher.
The agent therefore chooses retrieval first, then rewrites the proof using the new theorem.
Lean accepts more of the script because the next action was chosen to reduce proof burden directly.

The equation captures the main operational idea: each loop should make the formal proof state easier than it was before.

What can go wrong

What can go wrong

Retrieval may return the wrong facts. If the agent keeps seeing irrelevant lemmas, progress slows because proof revisions are built on the wrong ingredients.
The agent may loop on local repairs. A proof can require a strategic change, and repeated syntax fixes will not help because the whole proof direction is wrong.
Large formalizations can exceed simple benchmark patterns. Long proofs introduce more branching and more dependency management, so stronger planning may still be needed because the search space grows quickly.
Done right. The approach works when Lean feedback is used as a precise repair signal and retrieval tools keep supplying the facts that the next proof step needs.
