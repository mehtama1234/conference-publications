EffGen: Enabling Small Language Models as Capable Autonomous Agents

Make small agents usable by cutting wasted prompt text, splitting tasks cleanly, routing work by difficulty, and storing reusable state.

Paper explainersAll themesAgents & Tool Use

Large hosted models often make agent systems look easier than they are. They can absorb long prompts, recover from messy tool instructions, and brute-force many tasks through sheer scale. EffGen asks what has to change if the goal is a capable agent built around small local models. Its answer is to remove avoidable load before the small model acts: shorten prompts, split tasks, route hard jobs differently from easy ones, and keep memory in a unified system.

Zero assumption version

Why small-agent systems fail without support

A small model has less room for waste. If the prompt includes long tool descriptions, irrelevant context, and a large task all at once, the model spends capacity processing overhead instead of solving the job.

That overhead shows up in several places at once: the model reads too much before acting, misses dependencies inside a complex request, and forgets useful state between steps. EffGen treats these as system-level problems rather than blaming the model alone.

The paper's move in one sentence. Build an agent stack that reduces avoidable workload before the small model acts, because a lighter decision context lets the model spend its effort on the task itself.

What the paper changes

What the paper changes

The paper changes the full execution stack around the model. It does not rely on one trick. Instead, it reduces prompt load, reorganizes tasks, routes work by difficulty, and persists state in one coordinated framework.

The hidden quantity

The hidden quantity

measured quantity  =  Unnecessary decision load before each action

The useful way to view the system is to ask how much avoidable load the small model carries before it makes each decision. Extra instructions, unresolved task structure, and forgotten state all raise that load.

EffGen aims to lower that quantity before execution. Prompt compression removes waste, decomposition shrinks each subproblem, routing avoids using the same strategy everywhere, and memory keeps facts available so they do not need to be re-derived.

Why it works

Why this works

Each component helps for a different reason. Prompt compression helps because the model reads less irrelevant text before acting. Task decomposition helps because each subproblem exposes a smaller decision surface. Difficulty routing helps because hard requests may need more deliberate handling, while easy requests only need a short path. Unified memory helps because facts already discovered stay available instead of being recomputed.

The parts are complementary rather than redundant. Compression alone cannot recover forgotten state. Memory alone cannot untangle a request that was never decomposed. Routing alone cannot fix a bloated prompt. EffGen improves end-to-end execution because it removes several distinct sources of wasted effort at once.

Math after the picture

The workload view

First in words:

Treat the next decision as a workload made of prompt size, task complexity, and missing state; the system tries to reduce that workload before the model acts.

Then the compact form:

decision_load = prompt_overhead + task_complexity + missing_state ; success rises when the system lowers these terms before action

Every symbol:

decision_loadthe amount of work the small model must process before choosing the next step
prompt_overheadirrelevant or repeated prompt content that does not help the current action
task_complexitythe unresolved difficulty of the request before decomposition and routing
missing_stateuseful facts the system failed to preserve from earlier steps
successthe chance that the agent chooses a good next action and finishes the task
A tiny worked example
Suppose a raw request gives prompt_overhead = 6, task_complexity = 7, and missing_state = 5.
Then decision_load = 18 before the small model acts.
After prompt compression, prompt_overhead drops to 2.
After decomposition and routing, task_complexity drops to 4 because the model now sees one subtask instead of the whole job.
After memory lookup, missing_state drops to 1 because earlier facts are already stored.
The new decision_load is 2 + 4 + 1 = 7, so the model faces a much smaller problem at the next step.

The paper evaluates the practical effect of these reductions through agent benchmarks rather than through a single fixed formula.

What can go wrong

What can go wrong

Over-compression. Prompt shortening can hurt when it removes a tool instruction that was actually needed, because the model may then call the wrong tool or omit a required argument.
Bad decomposition. A task split can fail when dependencies are misunderstood, because a supposedly parallel branch may actually need information from an earlier branch.
Wrong routing choice. Difficulty-based routing can waste time or reduce quality when the request is misclassified, because the system will choose the wrong execution path.
Done right. Log the compressed prompt, the subtask plan, the routing decision, and the memory state for each run so that any failure can be traced to the exact stage that introduced it.
What a runnable demo should prove

What a runnable demo should prove

Build a small local agent that can search files, answer questions about them, and run a few simple tools. Compare four variants: plain prompting only, prompting plus prompt compression, prompting plus decomposition and routing, and the full EffGen-style stack with memory.

The demo should show that the full stack solves more tasks and spends fewer resources per task because each stage removes a different source of wasted work before the model acts.

task_success = solved_tasks / total_tasks ; cost_per_task = total_runtime_or_usage_charge / total_tasks

A convincing demo will show gains from the combined stack that are larger than the gains from any single component by itself.
