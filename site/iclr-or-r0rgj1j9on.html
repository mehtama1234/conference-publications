The real-time robot problem

Robots must move smoothly in the real world, but their brains are slow. Even a fast neural network takes time to predict the next action—time the robot's body cannot spare. To stay responsive, engineers pipeline the work: while the robot executes action chunk A, the model simultaneously predicts the next chunk B. By the time A finishes, B is ready.

The problem: the model was trained on a fantasy world. During training, it saw clean sequences—'observation one, action one, observation two, action two, observation three, action three.' But at test time, the model must predict action B before the robot actually executes action A. The observations the model sees during B-prediction are stale or wrong: the robot is still mid-chunk A, not at the true position for chunk B. This is intra-chunk inconsistency—the model predicts actions for a world state that does not match the robot's actual state mid-execution.

Naive methods added smoothing at test time to glue chunks together. This paper identifies a different root cause: the policy itself was never trained to handle this prediction-execution gap.

The fix in one sentence. Learn the policy to correct its own actions by masking random parts of chunks during training, so it adapts to seeing partial, out-of-sync observations.

The algorithm as a flow

What it actually does

Start with a pretrained policy

A neural network trained normally, expecting clean sequential observations.

Simulate test-time conditions in training

Mask arbitrary portions of the action chunk to represent the robot mid-executing, out of sync.

Learn a small correction layer

Add a tiny learned module (LoRA) on top of the pretrained policy to predict offsets, not wholesale new actions.

Use a curriculum schedule

Gradually increase the delay mask coverage during training to smoothly adapt from clean to messy.

Adjust sampling to match training

At test time, initialize chunk predictions with the actually-executed prefix from the previous chunk, not zeros.

What the paper changes

What the paper changes

The paper does not retrain the entire policy from scratch. Instead, it learns a small corrective adjustment on top of the pretrained policy—specifically, using LoRA (a parameter-efficient fine-tuning method that adds tiny learned weights to each layer). This adjustment learns to output small fixes to the actions, not completely new actions.

the object it moves  =  corrective action adjustments
The hidden quantity

The hidden quantity: intra-chunk inconsistency

measured quantity  =  intra-chunk inconsistency

Intra-chunk inconsistency measures how far apart the robot's true state is from the world state the model thinks it is in. At the moment the model predicts action chunk B, it has only stale sensor data—the robot is still executing chunk A, not yet at the position for B. The gap between predicted state and actual state grows as delay increases.

REMAC quantifies this during training by masking random portions of the action chunk—asking the model to predict corrections when only part of its intended action actually executes. The amount of mismatch is controlled by the delay parameter d, which the paper samples uniformly during training. This forces the model to learn adjustments that work regardless of which exact actions get cut short or delayed.

Why it works

Why it works: matching training to reality

The root cause of failure is a shift in the distribution (the pattern of inputs the model sees). During training, the model saw perfect, complete action sequences paired with synchronized observations. At test time, the model predicts actions while the robot is mid-execution, so the observations are out of sync and the executed portion of the chunk is incomplete. The model has never seen this condition.

REMAC fixes this by bringing the training condition closer to the test condition. During training, it masks (zeros out) random portions of each action chunk, simulating what happens at test time when only part of the chunk executes before the next prediction arrives. This forces the policy to learn how to output corrective adjustments—small offsets that compensate for the known mismatch between prediction time and execution time. The LoRA adaptation layer on top of the frozen pretrained policy learns these corrections without undoing the original skills.

A key insight: the correction is not the full new action, just the difference from what the model predicted before masking. This is efficient—it reuses the pretrained policy's knowledge and only learns the gap. The curriculum schedule gradually increases mask coverage during training, so the model smoothly transitions from clean conditions to messy ones rather than hitting a cliff, because sudden jumps in difficulty cause training instability—the learned adjustments become erratic when the target condition changes abruptly. By raising difficulty incrementally, each new phase builds on stable foundations from the previous phase.

Math after the picture

The training objective

First in words:

The loss minimizes the difference between predicted actions (after masking) and the ground-truth target, weighted by the delay parameter and corrected through the learned adjustment layer.

Then the compact form:

L = ||m_d * (pi(A_t|o_t) + LoRA(A_t|o_t, d)) - A_t*||^2

Every symbol:

m_dthe mask for delay d: zeros at early positions (still executing), ones later
pi(A_t|o_t)the pretrained policy's prediction for action chunk at time t given observation
LoRA(A_t|o_t, d)the learned correction layer output, small adjustments as a function of delay d
A_t*the ground-truth target actions from the dataset
||...||^2squared difference: sum up the squared errors per action dimension
A tiny worked example
Pretrained policy predicts: [move-up: 0.5, move-right: 0.2]
Mask at delay d=1: first action masked (zeros out move-up), second action visible
Target is: [move-up: 0.6, move-right: 0.3]
LoRA learns to output: [shift-up: 0.1, shift-right: 0.1]
Final action after LoRA: [0, 0] + [0.1, 0.1] = [0.1, 0.1] for masked portion
Loss only counts the visible portion: (0.2 + 0.1 - 0.3)^2 = 0, perfect.
The masked portion [0, 0] is not penalized—it represents actions the robot will not execute anyway.

The mask (parameterized by delay d) dynamically zeros out the actions that the robot never actually executes at the moment the model must predict, so training focuses on correcting only the parts the model will control at test time.

What can go wrong

What can go wrong

Mask schedule too aggressive. If delay coverage jumps from low to high too fast, training becomes unstable and the model overfits to extreme mismatches. Solution: use a gentle curriculum that increases mask coverage gradually per epoch.
Pretrained policy too weak. If the base policy is already poor, LoRA cannot fix it. The tiny correction layer only learns small offsets. Solution: use a strong pretrained policy and only adapt for the specific distribution shift (masking), not wholesale retraining.
Delay set does not match test time. If training samples delays 0 to 2 but test time uses delays 3 to 4, the model will fail. Solution: ensure the delay set (call it d) covers the actual delays the robot will encounter in deployment.
Done right. When the curriculum is smooth, the pretrained policy is strong, and the delay set matches test conditions, the model stays reliable and does not sacrifice performance at zero delay.
What a runnable demo should prove

What a runnable demo should prove

Build a simple simulation: a robot arm with a 3-action prediction horizon (predict 3 steps ahead while executing step 1). Train a policy normally, then train REMAC on top. At test time, introduce artificial delays (d=0, 1, 2, 3) that represent how many steps of the old chunk still execute while the new chunk is being predicted. Measure success rate (did the robot reach the goal?) and total execution time (did it go faster?) across all delay settings. These metrics matter because a policy that does not reach the goal has failed its job, and one that takes forever wastes the real-time advantage that running predictions alongside execution (asynchronous operation) is supposed to provide.

robustness = (success_rate_at_delay_d - success_rate_baseline_at_delay_d) / success_rate_baseline_at_d=0

The demo must show that REMAC does not regress at zero delay but consistently outperforms baselines as delay increases, proving the method trades no performance at clean time for reliability in messy real time—this is the key tradeoff that makes REMAC useful, since you only adopt a new method if it does not hurt your best case while helping your worst case.
