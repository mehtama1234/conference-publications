LEGO-FL: Heterogeneous Federated Models as Assembly

Train different model shapes on separate computers by building each one from shared LEGO-like pieces, then compose them locally.

Paper explainersAll themesEfficiency & Systems

Federated learning trains a single model across many computers without sending raw data to one place. But in reality, different computers have different sizes, speeds, and needs—one might run a tiny phone model, another a large server model. The usual approach fails because you cannot directly copy weights from a tiny model to a huge one. LEGO-FL solves this by breaking every model into modular building blocks (like LEGO bricks) that all clients learn together, then each client assembles those blocks into its own shape.

Zero assumption version

Why federated learning breaks with different model sizes

Federated learning lets computers train together on private data. But in the real world, a smartphone, a laptop, and a server need completely different model sizes: the phone needs tiny, the server needs huge. If you try to train one large model and copy it to the phone, it does not fit. If you train separate models on each computer, they cannot learn from each other because there is no way to safely merge the updates—the phone's model and the server's model have entirely different weight structures.

A beginner might try to just crop the server model down or pad the phone model up, but that breaks training: the cropped weights no longer align with the original structure, and padded weights add useless computation on weak devices.

The core problem: different model sizes cannot share weights, yet training them separately wastes the learning power of collaboration. Break every model into modular pieces (like LEGO bricks), teach those pieces to work together across all clients, then let each client snap them into its own shape.

The algorithm as a flow

What it actually does

Define modular blocks

Break models into reusable pieces: early layers, middle transformations, final decision layers.

Set composition rules

Declare how blocks snap together: phone gets layers 1-2, laptop gets 1-4, server gets all.

Train blocks together

All clients compute updates on their blocks and send them to the server, where they are averaged across clients.

Update shared blocks

Server applies the averaged updates to all blocks and sends new versions back.

Each client composes locally

Phone assembles its 2 blocks, laptop its 4, server its 6, each using the newest learned versions.

What the paper changes

What the paper changes

LEGO-FL changes where collaboration happens: instead of sharing the final assembled model, it shares the individual building blocks. Each client still has its own assembled model, but the pieces inside that model are trained together across all clients.

the object it moves  =  the unit of collaboration: blocks instead of full models
The hidden quantity

Component overlap: which blocks are used and reused

measured quantity  =  component reuse factor

The hidden quantity is how many times each block is used across all clients. A block used by the phone, laptop, and server is more valuable because three computers are pushing it to improve. A block used by only one device gets weaker learning signals. LEGO-FL measures this reuse by counting how many clients request each block during composition.

The paper uses this to decide which blocks to prioritize for improvement: blocks used by many diverse clients become sharper because they receive stronger, more varied learning signals; blocks used by few clients stay looser because their learning signal is thin.

Paper reading. The component reuse factor determines the effective batch size and diversity of learning signals for each block. High reuse means stronger updates because many devices are voting on which direction the block should move, which cancels out random noise; low reuse means high variance because only one device is pushing, so random fluctuations in that one device's data can pull the block off course.
Why it works

Why sharing blocks works better than trying to share whole models

The core insight is that most neural network models have a common structure: early layers extract simple features (like edges in images), middle layers combine them, and late layers make decisions. A phone model and a server model both use these stages, just at different scales. By breaking the model into these universal stages (blocks) and training them together, the phone learns from the diverse examples in the server's data and vice versa—even though they assemble different final models. The phone's early layers benefit from seeing examples that made the server's layers better because those examples come with computed updates that point toward features the server found useful; the phone gets these updates for free without the phone ever needing to run the server's full model.

When the phone and server both have a block called early-feature-extractor, and that block gets an update based on learning from all three devices' data, the phone's model immediately improves because it is running the newest block. This is the trick: the phone never needs to match the server's shape, only to share the fundamental building materials.

Math after the picture

The update rule: sharing block gradients

First in words:

For each block B shared by clients, the new block value is the old block value minus a learning step times the average gradient across all clients that use that block.

Then the compact form:

B_new = B_old - lr * mean(grad_i(B) for all i using block B)

Every symbol:

B_oldthe block weights before this round
B_newthe block weights after this round
lrthe learning step size
grad_i(B)the gradient computed by client i on block B
mean(...)the average of gradients across clients using this block
A tiny worked example
Suppose block early-features is used by phone, laptop, and server.
Phone computes grad=0.1 (its data says turn this way).
Laptop computes grad=0.15 (its data also says turn that way, but slightly more).
Server computes grad=0.05 (its data is less urgent).
Average: (0.1 + 0.15 + 0.05) / 3 = 0.1.
If learning step is 0.01, the block moves by 0.01 * 0.1 = 0.001.
All three devices download the updated block and use it next round.
The block has moved in the direction all three wanted, weighted by how many wanted it.

Blocks used by many clients move in the direction of the crowd; blocks used by one client move only if that one device pushes hard.

What can go wrong

What can go wrong

Block mismatch at composition time. If the phone says it needs blocks 1, 2, 3 but the server only knows about blocks 1 and 2, the phone cannot assemble itself. The composition rules must be declared upfront and shared with the server.
Blocks become too specialized to one device. If only the phone uses block 7, that block only sees phone data and phone updates. It will overfit to the phone's quirks (memorize phone-specific patterns instead of learning general principles) and hurt other devices if they try to use it because those patterns do not transfer. Blocks that are used by more devices learn from more diverse data and work better across all devices because the diverse examples force the block to learn general principles—if the phone wants feature A but the server wants feature B from the same block, the block learns a middle ground that satisfies both.
Communication bottleneck if blocks are large. If a block has billions of parameters, sending it from server to phone is slow. LEGO-FL works best when blocks are sized so that repeated communication does not overwhelm the phone's connection. Choosing the right block granularity (big enough to learn well, small enough to send fast) is a design question, not solved by the algorithm.
Done right. Declare blocks and composition upfront. Prioritize blocks used by many diverse clients. Monitor communication cost and reuse factor. Train blocks together, assemble locally.
What a runnable demo should prove

What a runnable demo should prove

A demo builds three models by LEGO-FL: a small model (phone), medium model (laptop), and large model (server), each trained on its own partition of a standard data set (for example, CIFAR-10, a standard image test set). All three devices share three blocks: an early feature detector, a middle layer that combines features, and a final decision layer. Round by round, each device computes updates on its blocks and sends them to the server, which averages and broadcasts. After training, each device runs its assembled model. The metric is the accuracy gain for the weakest device (phone) compared to training the phone alone on only phone data—this isolates the collaboration benefit.

collaboration_gain = accuracy_with_blocks - accuracy_phone_alone

If LEGO-FL works, the phone's accuracy should jump noticeably because it learned from laptop and server data through shared blocks, even though the phone never ran the full laptop or server model.
