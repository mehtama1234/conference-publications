LoC-Decomp: Autoformalization via Logical Concept Decomposition

Break large math statements into small, verifiable pieces, then have an LLM assemble them into formal code with automatic error-checking.

Paper explainersAll themesLLMs & Foundation Models

When an LLM translates a math statement into formal code (Lean, Coq, Isabelle), most errors go unnoticed: the code looks right but means something different than the original statement. LoC-Decomp adds an automatic checker that catches these hidden meaning-shifts and gives the LLM corrective feedback to try again.

Zero assumption version

Hidden meaning shifts in formal code

When an LLM translates a math problem into formal code, it tries to capture the same statement in a machine-verifiable language. But the LLM often makes subtle mistakes: the code might parse and run without error, yet mean something different than the original math. A beginner would feed the LLM a problem, get code back, check that it compiles, and assume it is correct—but hidden contradictions go unnoticed.

No existing method checks whether the formal code actually says the same thing as the original problem. Without that feedback, the LLM has no way to know it made a mistake and no chance to fix it.

The problem in one sentence. Formal code can silently contradict the original statement, and the LLM never learns it made an error.

What the paper changes

What the paper changes

The paper changes how the LLM translates a math statement: instead of trying to render the whole thing at once, it breaks the problem into small pieces, translates each piece separately, and assembles the pieces into a final formal expression. The LLM gets explicit feedback when a piece does not match the original statement.

the object it moves  =  The translation process (from whole-statement to decomposed-pieces)
The hidden quantity

The hidden quantity: semantic consistency

measured quantity  =  semantic consistency score

Semantic consistency is a measure of whether the formal code still means the same thing as the original math statement. It is hidden because the code can compile and look correct without actually saying what the problem said. The paper estimates it by running a divide-conquer-merge checker: it breaks the formal code into its logical pieces, checks each piece against the original statement, combines those checks, and returns a score from 0 (completely wrong) to 1 (perfectly consistent).

This quantity is what the paper measures to decide if the LLM succeeded. If the score is low, the LLM knows a piece does not match and can rewrite it. Without measuring this, the LLM would have no signal.

Why it works

Why breaking the problem into pieces works

A big math problem is hard to translate because it has many moving parts and hidden relationships. When the LLM tries to get it all right at once, it makes small mistakes in individual pieces, and those mistakes often contradict each other without the LLM noticing. Breaking the problem into small pieces flips this around: each piece is simpler, so the LLM makes fewer mistakes per piece. The LLM now translates one small, clear idea at a time instead of juggling many ideas at once.

The semantic checker then catches the remaining mistakes. Instead of just checking that the code compiles, it actively compares each piece back to what the original statement said. When the checker finds a mismatch, it tells the LLM exactly which piece failed and why. The LLM can then focus on fixing just that one piece rather than rewriting everything from scratch. This tight feedback loop—measure semantic consistency, find the failing piece, rewrite it, measure again—drives the LLM toward a correct translation in a small number of tries.

The consistency check equation

First in words:

consistency_score = (count of pieces matching original) / (total count of pieces)

Then the compact form:

C = sum_i M_i / n

Every symbol:

Cthe consistency score, a number from 0 to 1
sum_i M_icount of pieces that match the original statement
ntotal number of pieces the statement was broken into
M_i1 if piece i matches the original, 0 if it contradicts it
A tiny worked example
Original statement: if x > 5 AND y < 10 THEN z = x + y
Decomposed into 3 pieces:
Piece 1: x > 5 (formal code: x > 5) — Match
Piece 2: y < 10 (formal code: y > 10) — No match (error!)
Piece 3: z = x + y (formal code: z = x + y) — Match
Consistency score = 2 / 3 = 0.667 (67% consistent; one piece failed)
Feedback: Piece 2 says the opposite of the original. Rewrite it.

A lower score means more pieces are inconsistent; the LLM rewrites the failing pieces until the score reaches 1.0 (all pieces match the original).

What can go wrong

What can go wrong

Checker itself makes mistakes. The semantic checker is not perfect. If it misunderstands the original statement, it might incorrectly flag a piece as inconsistent when it actually matches. This sends the LLM on a wild goose chase.
Decomposition loses context. Breaking a problem into pieces can lose hidden relationships between pieces. For example, a constraint that links two pieces might get dropped, and neither piece individually looks wrong.
LLM rewrites a different piece. When the checker flags piece 2 as failing, the LLM might misunderstand and rewrite piece 1 instead, or introduce a new error in piece 3 while fixing piece 2.
Done right. Decompose the problem into pieces with clear boundaries and minimal hidden dependencies. Have the checker measure consistency against the original statement (not against the formal code itself). Give the LLM explicit, specific feedback about which piece failed and why. Repeat the feedback loop until consistency reaches 1.0.
What a runnable demo should prove

What a runnable demo should prove

Build a small experiment on 10 to 20 math problems from a test set (e.g., high-school algebra or simple proofs). For each problem: (1) use the naive LLM method to translate the whole problem at once, (2) use LoC-Decomp to decompose, translate pieces, check, and iterate. For both methods, measure the final consistency score (does the formal code mean the same as the original?). Plot success rate (counting only fully consistent solutions, consistency reaching 1.0) for both methods on a bar chart.

success_rate = (count of problems with consistency = 1.0) / (total problems)

The demo must show that LoC-Decomp solves more problems end-to-end and with fewer failed pieces than the naive approach.
