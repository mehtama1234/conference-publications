ReIn: Conversational Error Recovery with Reasoning Inception

An external module identifies errors in a conversation and injects corrective reasoning into a chatbot's decision-making, helping it recover without retraining.

Paper explainersAll themesAgents & Tool Use

Conversational AI agents powered by large language models often fail when users make unexpected mistakes, ask for things that don't make sense, or request unsupported actions. The agent then gets stuck and cannot recover without retraining the model or changing its instructions. This paper shows a way to rescue these conversations at test time (when the model is answering) by injecting an external error-detection module that spots what went wrong and steers the agent's reasoning toward recovery.

Zero assumption version

Why conversational agents get stuck

A task-oriented agent (a chatbot that handles user requests like booking flights or answering questions) works well when users ask clearly and make sense. But in the real world, users make mistakes. They might ask for something ambiguous ('I want a cheap flight but also the most luxurious seat'), ask for something impossible ('book me a flight to Mars'), or give incomplete information ('find me a hotel' without saying where or when). When this happens, the agent's reasoning breaks down and it either gives wrong answers or fails to complete the task. Recovery is hard: retraining the model costs time and money; rewriting the agent's instructions (its system prompt) also requires testing and rollout.

A beginner might try to fix this by adding more rules to catch bad requests upfront. But dialogue errors are too varied and subtle to list in advance. The real problem is that the agent lacks a way to diagnose the error and plan a recovery step (asking the user for clarification, for example) without stopping the whole conversation and restarting.

The core problem. Conversational agents fail on unexpected user errors and cannot recover without retraining the model or rewriting its instructions.

The algorithm as a flow

What it actually does

Error diagnosis

A separate module watches the dialogue and detects predefined error types (ambiguous request, unsupported request) in real time.

Recovery plan generation

Once an error is detected, the module generates a concrete recovery action (e.g., 'ask the user to specify the destination').

Inject into reasoning

The recovery plan is embedded into the internal reasoning process of the main agent model without changing its weights or system prompt.

Agent decides and acts

The agent now sees the injected recovery reasoning and incorporates it naturally into its next decision.

Task succeeds

With the corrective signal, the agent takes the right action and the user's goal is completed.

What the paper changes

What the paper changes

The paper injects an external signal into the agent's reasoning flow at test time. This signal (the recovery plan) is not part of the model's learned numbers; it is added just before the agent decides what to do next, by inserting it into the reasoning chain the agent follows.

the object it moves  =  reasoning pathway
The hidden quantity

The error state and recovery potential

measured quantity  =  error presence and recovery action

The hidden quantity here is not a single number but a pair: whether an error has occurred in the dialogue (yes or no), and if yes, what specific recovery action would fix it. The inception module computes this pair by examining the conversation history and matching it against known error patterns.

The paper estimates this by pre-defining a library of error types (e.g., 'ambiguous request', 'unsupported action') and recovery plans (e.g., 'ask for clarification'). When the dialogue matches an error pattern, the module flags it and outputs the paired recovery action. This is then integrated into the reasoning the agent sees.

Why it works

Why it works: the causal chain

The agent's reasoning determines what it does next. Normally, it reasons from the dialogue history alone, which includes the user's error. The error corrupts the reasoning, leading to a bad choice. By injecting a recovery instruction into the reasoning before the agent decides, the paper overrides the corrupted input signal. The agent now has two inputs: the noisy dialogue history and the clean recovery signal. When they conflict, the injected signal carries more weight because it is recent and specific to the actual error.

This works because the agent is designed to follow its reasoning chain step-by-step. It does not need to be retrained to follow a new signal; it simply processes the injected reasoning like any other reasoning. Reasoning is a behavior the model can perform at test time without changing its internal numbers (the weights learned during training). By showing the model a recovery example in its reasoning flow, the model applies it naturally, exactly how it would if it had trained on such examples.

The recovery decision formula

First in words:

The agent's final action is chosen by combining the original reasoning with the injected recovery signal. The recovery signal is given higher priority in the decision-making, because it directly addresses the diagnosed error.

Then the compact form:

action = argmax_a ( reasoning_original(a) + weight_recovery * recovery_signal(a) )

Every symbol:

actionwhat the agent does next
reasoning_original(a)the agent's native preference for action a, computed from dialogue history
recovery_signal(a)how well action a matches the injected recovery plan (1 if it matches, 0 otherwise)
weight_recoveryhow much the recovery plan influences the decision (set high so recovery overrides noisy reasoning)
A tiny worked example
Scenario: user asks 'find me a cheap hotel near the beach' without specifying the city. Error detected: ambiguous location.
Recovery plan: 'ask the user to specify the city'.
Action A (guess city): reasoning_original(A) = 30, recovery_signal(A) = 0, total = 30 + 100*0 = 30
Action B (ask for city): reasoning_original(B) = 10, recovery_signal(B) = 1, total = 10 + 100*1 = 110
Agent chooses B because 110 > 30. It asks the user to clarify, recovering the conversation instead of guessing wrong.

By raising the recovery signal's weight, the agent treats the corrective guidance as a stronger instruction than its own noisy reasoning, so recovery happens reliably.

What can go wrong

What can go wrong

Error library is incomplete. If the inception module's predefined error types do not cover the user's actual mistake, it will not detect the problem and cannot generate a recovery plan. The agent still fails silently.
Recovery signal conflicts with reasoning. If the recovery plan contradicts what the dialogue history strongly suggests the user wants, the agent may get confused and take a half-measure or ignore the recovery altogether.
Inception module is too slow. If error detection and recovery plan generation take too long (more time than a user is willing to wait), the latency cost defeats the benefit.
When it works well. ReIn works best when error types are well-defined and predictable (e.g., missing a required field), and recovery actions are simple (ask a clarifying question). Detection is reliable because error patterns are easy to match against dialogue history; the recovery signal improves success because injecting a clear, specific instruction overrides the noisy reasoning, steering the agent toward the right fix.
What a runnable demo should prove

What a runnable demo should prove

Build a simple chat system with a pretrained agent (e.g., a model that answers booking requests). Create a test set with both clear and error-filled user requests. Then implement a basic inception module: a rule-based error detector (e.g., check if required fields are missing) and a recovery plan generator (e.g., return 'ask user for field X'). Run the agent on both sets: (1) without ReIn, (2) with ReIn active. Measure task success rate on error cases. The demo must show that error recovery raises success on requests the agent originally failed on, without retraining the model or changing its system prompt.

recovery_gain = success_rate_with_rein(error_cases) - success_rate_without_rein(error_cases)

The demo must prove that error recovery works by raising success on broken requests, without changing the model's internal numbers or instructions.
