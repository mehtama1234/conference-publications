What Do Agents Learn from Trajectory-SFT: Semantics or Interfaces?

Test whether an agent learned the task itself or merely learned the exact surface form of the environment interface it saw during training.

Paper explainersAll themesAgents & Tool Use

Agent benchmarks usually score success on a fixed environment interface. That is convenient, but it hides an important ambiguity. An agent might succeed because it understands the task semantics, or it might succeed because it memorized the precise names, formatting, and interaction patterns of the training interface. PIPE is an evaluation protocol that rewrites interfaces while preserving task behavior so that these two kinds of success can be separated.

Zero assumption version

Why benchmark success can hide shortcut learning

Many agent evaluations assume that high task success on the benchmark means the agent learned how to solve the underlying task. That assumption is too strong. If the training data includes many trajectories in one fixed interface, the agent may learn surface-specific habits such as exact tool names, ordering cues, or formatting conventions.

Those habits can produce high benchmark scores without yielding interface-invariant capability. The paper focuses on this identifiability problem: from original-interface success alone, we cannot tell whether the learned behavior is semantic or interface-specific.

The paper's move in one sentence. Keep task semantics and execution behavior fixed, rewrite the interface surface form, and measure how much the agent's performance drops.

The algorithm as a flow

What it actually does

Start from an existing benchmark environment

Keep the same tasks and execution rules so that semantic difficulty stays constant.

Rewrite the interface minimally

Change names, formatting, or surface patterns while preserving the underlying behavior because the goal is to probe interface dependence only.

Evaluate the same agent on both versions

Compare original-interface and rewritten-interface performance to see whether success transfers.

Compute interface reliance

Use a counterbalanced metric that measures preference for training-time interface forms.

Track effects of trajectory training

Study whether task-specific trajectory supervision increases or decreases dependence on the original interface.

What the paper changes

What the paper changes

The paper changes the evaluation protocol. Rather than accepting original-interface success as evidence of general agent skill, it adds matched interface rewrites that isolate whether the learned behavior survives superficial changes.

The hidden quantity

Interface reliance: the hidden quantity

measured quantity  =  How strongly the agent depends on the exact training-time surface form of the environment

The hidden quantity is interface reliance. This is the degree to which the agent's success depends on exact command names, formatting, aliases, and interaction patterns rather than the task semantics that those interface elements express.

Standard benchmarks do not expose this quantity because they keep the interface fixed. PIPE reveals it by changing only the surface form. If performance drops after that change, the drop indicates that part of the original success came from interface-specific habits.

Why it works

Why this works

The protocol works because it changes only the evidence source that shortcut learners depend on. If task semantics and execution behavior stay fixed, then a semantic solver should transfer well across rewrites. A shortcut learner should degrade because its memorized surface patterns no longer line up with the environment.

This evaluation is especially important after trajectory supervision because repeated exposure to one interface can strengthen pattern dependence. The paper shows that the training process can raise benchmark scores while silently increasing reliance on the exact interface used during training.

A simplified interface-reliance score

First in words:

Compare success on the original interface and a semantics-preserving rewrite. A larger gap indicates stronger dependence on the original surface form.

Then the compact form:

interface_reliance = score_original_interface - score_rewritten_interface

Every symbol:

interface_reliancehow much performance is lost after a minimal interface rewrite
score_original_interfacetask success on the benchmark's original interface
score_rewritten_interfacetask success after rewriting the interface while keeping task behavior fixed
A tiny worked example
Suppose an agent scores 0.82 on the original interface.
Now rename commands and alter formatting while keeping the environment behavior unchanged.
On that rewritten interface the agent scores 0.51.
Then interface_reliance = 0.31.
That large gap matters because it suggests a substantial part of the original score came from surface-form dependence.

The paper adds counterbalancing details, but the core signal is direct: performance that vanishes under harmless rewrites was not fully interface-invariant.

What can go wrong

What can go wrong

A rewrite may accidentally change task difficulty. The protocol is useful only if semantics and execution behavior are truly preserved, because otherwise a performance drop may reflect a harder task rather than interface dependence.
Some interface changes may be too mild. If the rewrite stays too close to the original surface form, shortcut dependence may remain hidden because the agent can still match old patterns.
A drop does not tell you which habit caused it. The protocol can reveal that interface dependence exists, but it does not automatically identify the exact surface cue the agent relied on because many cues may change together.
Done right. Use multiple controlled rewrites, preserve behavior carefully, and report both original and rewritten scores so that claims about general agent skill rest on evidence that actually tests transfer.
What a runnable demo should prove

What a runnable demo should prove

Build a small tool-use environment with one original interface and one rewritten interface. Keep the same underlying task and execution behavior, but rename commands, alter formatting, and change harmless surface conventions. Evaluate the same agent on both versions after training it on trajectories from the original one.

The demo should prove that original-interface success alone is weak evidence because an agent that truly understands the task should transfer across the rewrite, while an agent that learned interface habits should lose performance when those habits no longer match.

transfer_gap = score_original - score_rewrite ; semantic_retention = score_rewrite / score_original

A useful demo shows that a benchmark score needs a transfer check before it can support a strong capability claim.
