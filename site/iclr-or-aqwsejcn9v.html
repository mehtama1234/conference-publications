BiBo: Vision-Language Models Control Humanoid Robots

A humanoid robot interprets user instructions via a language model, translating them into motion commands that adapt in real time.

Paper explainersAll themesRobotics & Control

Large language models like GPT-4 understand what you mean from text or pictures, but they live in the digital world. A humanoid robot needs to do the same thing, but with real physics — moving arms, legs, and body to carry out what you ask. This paper connects GPT-4 to a real robot's body by building a two-stage pipeline: first the language model interprets your request in context with what it sees around it, then a motion generator produces smooth human-like movements that actually work in the environment.

Zero assumption version

Why language models alone cannot move a robot

A large language model like GPT-4 can read an image, understand a sentence, and reason about the world. But it outputs text or numbers, not motion. A robot needs to know: how much to bend each joint, how fast, which direction. If you ask a language model directly (write numbers for each joint), it makes mistakes—floating numbers don't map to real physics. It also ignores what actually happens when the motion starts: if a heavy object slips, if friction changes, if the robot tips slightly, the plan breaks.

A naive approach would be: ask the language model for target positions for each joint, then execute them rigidly. This fails because the language model does not think in joint angles, and it has no feedback loop. Once motion starts, it is blind to what the world is actually doing.

The paper's move in one sentence. Sandwich the language model between a question-and-answer compiler that translates instructions into motion goals, and a diffusion generator that produces realistic motions that adjust to real-time feedback.

The algorithm as a flow

What it actually does

1. See and ask

Camera observes the scene; language model and user instruction both go into a question engine.

2. Clarify step by step

A chain of yes-or-no questions makes the language model spell out: object to touch, location, distance, action style.

3. Translate to motion

Questions are answered into concrete control numbers: target positions, speeds, forces.

4. Generate smooth motion

A diffusion model takes those numbers and generates a sequence of realistic joint angles, moment by moment.

5. Execute and adapt

Robot moves; real-time feedback from joints and touch sensors reshapes the motion if obstacles or slips occur.

What the paper changes

The thing the paper changes

Instead of asking a language model to output raw joint commands, the paper inserts an intermediate layer that asks clarifying questions and a motion generator that smooths and adapts. The object is the path from instruction to robot motion: it now routes through a question-and-answer protocol and a learned motion model, rather than trying to go directly from text to numbers.

The hidden quantity

The hidden quantity: task-relevant context

measured quantity  =  contextual motion signals

The language model does not inherently know which details matter when executing a motion. Reaching a cup 20 centimeters away is fundamentally different from reaching one 200 centimeters away; grasping a soft sponge is different from an egg. The paper measures this by inferring what the language model believes are the action-defining details from each answer to a question. When the model says the object is 'to the left' it is focusing on position; when it says 'fragile' it focuses on how to grip. These detail signals guide the diffusion generator to pick the right motion shape.

The paper estimates these signals by looking at which parts of the language model's activations (the intermediate values as it processes a question) light up most when answering each question. Stronger activations for 'grasp type' mean that detail matters to the current task, because the model is dedicating more of its internal computation to that question, which tells us that answer will shape the motion choice.

Why it works

Why this works: three ideas that fit together

First, a language model understands text and images very well, but it does not natively output joint commands (the numbers that tell a robot how to bend each arm or leg). The paper bridges this gap by asking the language model multiple yes-no questions about the scene and the task. Each question is narrow (not 'what should I do' but 'is the object on the left?'), so the model can answer clearly because a yes-or-no choice leaves no room for vague or contradictory outputs, while an open-ended question invites confusion. The answers accumulate into a full picture of what needs to happen.

Second, even with a clear picture, producing realistic motion is hard. Joint angles do not move in isolation; they must form a coordinated, human-like sequence that respects physics. A diffusion model (a machine-learning tool that learns smooth motion by training on many real human movements) is perfect for this: it does not try to obey rigid rules but instead produces realistic sequences that adapt. The control numbers from the question-answering stage guide which movements to pick.

Third, real robots face surprises: a cup may be heavier than expected, the floor may be sticky, a hand may touch something unplanned. The diffusion generator can re-run moment-by-moment, taking in real-time feedback from the robot's sensors (joint positions, forces, touches). If the actual state drifts from the plan, the next motion refinement steers back on track.

Math after the picture

The core equation: diffusion conditioned on context

First in words:

The diffusion model generates the next joint position by starting with noise, then repeatedly refining away the noise, guided by the control parameters and current robot state. Each refinement step reduces noise by an amount proportional to how far the current guess is from a realistic motion shape that matches both the parameters and what the robot actually feels.

Then the compact form:

m_t = m_{t-1} - sigma * nabla_m L(m_{t-1}, c, s_t)

Every symbol:

m_tthe joint motion at refinement step t
m_{t-1}the motion guess before this step
sigmathe noise level at this step (starts high, shrinks to zero)
nabla_m Lwhich direction to nudge m to reduce error
cthe control parameters from the question-and-answer stage
s_treal-time sensor readings (joint positions, forces)
L(m,c,s)a score: how realistic is motion m, given parameters c and sensors s?
A tiny worked example: refining one joint over three steps
Joint angle starts as noise: m_0 = 78 degrees (random), target 45 degrees
Noise level sigma = 0.4. Realistic motion for this target has score L = 2.5 (current guess is far off)
Step 1: nudge = 0.4 * 2.5 = 1.0, so m_1 = 78 - 1.0 = 77 degrees (barely moved, noise still high)
Step 2: sigma = 0.2, L = 1.2 (closer now), nudge = 0.2 * 1.2 = 0.24, so m_2 = 77 - 0.24 = 76.76
Step 3: sigma = 0.05, L = 0.3 (very close), nudge = 0.05 * 0.3 = 0.015, so m_3 = 76.76 - 0.015 = 76.745
In practice, all 40+ joints refine in parallel, and sensors feed back real motion as it happens.

The diffusion model is not memorizing recipes but learning to recognize realistic motion shapes. Starting from noise and repeatedly asking 'does this match a real human motion?', it sculpts a motion that fits the control parameters and real-world feedback.

What can go wrong

What can go wrong

The language model answers a question incorrectly. If the model misidentifies an object or gives a wildly wrong distance, the downstream control parameters are wrong. The diffusion stage can partly fix this (it still tries to produce realistic motion), but the task fails. This is rare because questions are yes-no or multiple-choice, reducing confusion, but open-ended vision tasks like scene understanding can still trip up the model.
The control parameters leave no valid motion. A robot cannot physically do everything. If the question-answering stage specifies a target that is out of reach, or asks for simultaneous incompatible actions, the diffusion generator tries to interpolate but fails to produce realistic motion. The task fails or produces jerky movements.
Real-time feedback is too slow or noisy. If the robot's sensors have latency (delayed readings) or are noisy (false touch signals), the motion refinement can chase ghosts or react too slowly to a real problem. A sudden slip might not be detected in time to stop a fall.
Done right: every question is narrow and answerable. Chain-of-VQA works because each question is designed to be unambiguous (not 'what should I do' but 'is the object in front of me'). The diffusion model is trained on human motion, so it knows what is realistic. Real-time feedback loops are fast enough (millisecond-scale) to catch problems before they cascade.
What a runnable demo should prove

What a runnable demo should prove

Build a simple interactive demo: show a humanoid robot in a simulated kitchen. Give it a natural-language instruction ('pick up the coffee mug') and a camera view. Display side by side: (1) the questions the compiler asks and the language model's answers, (2) the control parameters those answers generate, and (3) a real-time animation of the humanoid moving, with joint angles and sensor readings visible. Let the user drag obstacles into the scene and re-run the same instruction. The motion should adapt without re-running the language model.

success_rate = number_of_instructions_completed / total_instructions_given

The demo must make it impossible to miss: the language model stops being a black box. You see exactly which questions made the motion possible, and the robot adapts in real time when the world changes, not by re-running the language model but by diffusion adjusting its motion moment by moment.
