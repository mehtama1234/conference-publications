Failure is Feedback: History-Aware Backtracking for Agentic Traversal in Multimodal Graphs

Search a linked document graph more intelligently by treating dead ends as evidence about where not to go next, then spend extra reasoning cost only when that evidence justifies it.

Paper explainersAll themesAgents & Tool Use

This paper studies open-domain retrieval over large document graphs containing paragraphs, tables, and images. The task is not only to score one item at a time. The system must move through a graph, decide which node to visit next, and recover when earlier hops were poor choices. Failure is Feedback turns that search into a sequential decision problem where bad paths are not discarded. They are stored as clues that shape later backtracking and later spending on heavier reasoning.

Zero assumption version

Why graph retrieval needs recovery, not only ranking

In a linked document collection, the correct answer may sit several hops away from the starting node. A system must decide which neighbor to inspect next, which evidence to keep, and when to turn back. If one early hop is weak, the rest of the path can become wasteful because later nodes are chosen from the wrong local neighborhood.

Many graph retrieval methods rely on one similarity rule or one fixed traversal plan. That is limiting because the meaning of a good hop changes with context, and because dead ends should teach the system something about which branches are unlikely to help.

The central move. Treat failed traversals as information, because a dead end says not only that one path failed but also which related moves are now less promising.

The algorithm as a flow

What it actually does

Treat retrieval as sequential search.

The system chooses one hop at a time through a multimodal graph, because each new node changes which future hops are worth considering.

Record failed traversals.

When a branch does not lead to the answer, the system stores what it tried and why it failed so that the same mistake is less likely to recur.

Backtrack with history.

Backtracking does not simply reset the state. It returns with extra context about the failed branch, so the next branch choice is informed by negative evidence.

Control reasoning spend.

The orchestrator uses cheap traversal steps first and pays for heavier reasoning only when the failure history suggests that the extra cost may change the outcome.

Stop when evidence is good enough.

The search ends when the system has gathered a sufficiently strong answer path, because endless exploration adds cost without useful new evidence.

What the paper changes

What the paper changes

The paper changes graph retrieval from fixed forward traversal into a history-aware search process where failure explicitly shapes later navigation and later reasoning spend.

The hidden quantity

The hidden quantity

measured quantity  =  expected value of the next branch after accounting for past failures

The main hidden quantity is how promising each next branch remains after you take earlier failures into account. Two branches may look equally relevant from the current node, yet one may repeat the same weak evidence pattern that already failed earlier.

The paper estimates that hidden value by combining current context with traversal history. That helps because negative evidence shrinks the search space: once one style of branch has failed, related branches deserve a lower rank unless new context changes the picture.

Why it works

Why history-aware backtracking helps

Ordinary backtracking throws away too much information. It returns to an earlier node, but it does not preserve which cues led the search down a useless path. That means the next choice can repeat a closely related mistake because the system has forgotten what the dead end taught it. History-aware backtracking keeps the failure context, so the next step is guided both by what currently looks relevant and by what has already proven unhelpful.

The cost-aware control also matters. Heavy reasoning can rescue difficult cases, but using it everywhere wastes compute on easy hops. The orchestrator therefore delays that cost until cheaper search evidence suggests it is needed. This helps because the system spends more only when failures indicate that simple traversal is no longer enough.

Math after the picture

Score the next branch using success value, failure memory, and cost

First in words:

A simple summary is to prefer branches that still look useful under the current context, subtract a penalty when they resemble earlier failures, and subtract the extra reasoning cost needed to pursue them.

Then the compact form:

branch_score(next) = current_evidence(next) - failure_penalty(next) - extra_cost(next)

Every symbol:

branch_score(next)overall value of choosing one next branch
current_evidence(next)how well the current graph state supports that branch
failure_penalty(next)how strongly earlier dead ends suggest this branch will also fail
extra_cost(next)added reasoning spend required to evaluate that branch
A tiny worked example
Branch A looks relevant now, so current evidence is 8.
It closely resembles a path that already failed, so failure penalty is 5.
It also needs extra heavy reasoning with cost 2.
Branch B has current evidence 7, failure penalty 1, and extra cost 1.
Branch B wins because it offers a cleaner new direction after accounting for what earlier failures already taught the system.

The paper uses a richer traversal mechanism than this line, but the line captures the main idea: the next move should be judged by present relevance, earlier failures, and added search cost together.

What can go wrong

What can go wrong

Failure memory can become too pessimistic. If the system punishes every similar branch too strongly, it may skip the correct answer path because some useful branches superficially resemble earlier failures.
The graph may hide good links. A weak graph structure can block retrieval no matter how smart the traversal policy is, because the right node may not be reachable through the provided links.
Cheap early hops may under-sample hard cases. If the system waits too long before using heavier reasoning, it can remain trapped in shallow evidence because the cheap traversal policy never sees the cue that would justify more effort.
Done right. The method is strongest when failure history is informative but not overwhelming, because then backtracking rules out repeated bad patterns without hiding fresh useful branches.
What a runnable demo should prove

What a runnable demo should prove

Build a linked graph of short passages, tables, and images where some answer paths require two or three hops. Create several distractor branches that look locally relevant but end in dead ends. Compare a forward-only search policy, a plain backtracking policy, and a history-aware backtracking policy with a budget on expensive reasoning calls.

The demo should show that history-aware backtracking reaches the answer more often with similar or lower spend because it learns from failed paths instead of repeatedly revisiting their close variants. It should also show when heavier reasoning is triggered and whether that extra cost was justified by a later improvement in the found answer path.

value_per_cost = answer_quality / total_reasoning_cost

A convincing demo must prove that dead ends improve later search when their history is retained, because recovery should use failure as evidence instead of treating it as wasted work.
