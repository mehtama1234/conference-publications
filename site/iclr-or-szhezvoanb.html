Scenethesis: A Language and Vision Agentic Framework for 3D Scene Generation

Scenethesis builds a 3D scene from text by drafting a layout with language, checking it with visual structure cues, then optimizing object poses until support, collision, and relation constraints are satisfied.

Paper explainersAll themesOther

Text-to-3D scene generation is not just asset selection. A useful scene must place each object where it can physically stand, where its stated relation holds, and where interactions remain plausible. Pure learning-based layout models often stay close to the narrow indoor layouts seen in training data, while pure language planning proposes broader layouts but often places objects in invalid positions because text alone does not enforce support, contact, or collision rules. Scenethesis combines these strengths in sequence. A language model drafts a coarse layout, a vision module reads structure from candidate views, an optimization stage adjusts pose and placement to satisfy physical and relational constraints, and a judge checks whether the result is spatially coherent. This works because each stage fixes a different failure mode of text-only or data-only generation.

Zero assumption version

Why text alone is not enough to arrange a 3D scene

A scene description may say: place a lamp on a table next to a chair, put a mug near the lamp, and add a bicycle outside the doorway. That sentence contains object identities, support relations, distance relations, and spatial exclusions. A scene generator has to satisfy all of them at once.

Data-driven layout models learn recurring arrangements from training scenes, but those datasets are often concentrated in a few indoor categories. That makes the models brittle when a prompt asks for unusual compositions, outdoor scenes, or rare object-scale relations because the generator tends to revert to familiar templates.

Language models can draft broader layouts because they encode commonsense facts from text, but they do not directly check whether a mug intersects the lamp or whether a chair floats above the floor. So text-only planning can satisfy the wording of a prompt while violating the mechanics of a scene.

The paper's sequence. Use language to propose a layout, use vision to recover scene structure, then run explicit optimization and judging so the final arrangement satisfies both the prompt and physical plausibility.

The algorithm as a flow

What it actually does

Draft a coarse scene plan

Use a language model to name objects, assign rough placements, and state intended relations.

Render candidate views

Produce images or structure views from the current layout so a vision model can inspect the arrangement.

Extract scene structure

Use visual cues to estimate supports, contacts, relative depth, and inter-object relations that are hard to enforce from text alone.

Optimize object poses

Adjust translation, rotation, and alignment to reduce collisions and to satisfy support and relation constraints.

Judge and repair

Run a final coherence check and, if needed, repair only the objects involved in the remaining violation.

What the paper changes

What the paper changes

The paper changes scene generation from one-pass layout prediction to a staged agentic process. Layout planning, visual verification, numeric optimization, and judging are separated so each stage can correct errors the previous stage could not observe.

The hidden quantity

Constraint satisfaction: the hidden quantity

measured quantity  =  How many intended spatial relations are simultaneously valid

The prompt usually implies several constraints at once: one object should rest on another, one pair should stay near each other, another pair should not overlap, and all objects should remain stable. A layout can look plausible in one local sense while still failing globally if even one of these constraints is broken.

So the hidden quantity is joint constraint satisfaction. The final system is better when a high fraction of support, collision, stability, and relation checks all pass together, because partial success is not enough for an interactive scene.

Why it works

Why the staged pipeline produces better scenes

The language model is good at turning a prompt into symbolic intent: which objects are present and what relations the prompt requests. That makes it a useful planner, but not a sufficient verifier because symbolic intent does not tell you whether two meshes intersect or whether an object is actually supported.

The vision module adds grounded structure. By rendering or inspecting candidate layouts, it can recover cues about contact, occlusion, relative position, and support. Those cues convert a rough symbolic plan into measurements that an optimizer can act on.

The optimizer then solves the part that language and vision alone cannot finish: it searches over numeric pose values until the measured violations shrink. The judge matters because optimization can fix one relation while breaking another, so the final check identifies any leftover inconsistency and triggers repair only where needed.

The pose refinement objective

First in words:

The optimizer minimizes a weighted sum of physical and relational violations. Each term measures one kind of problem in the current scene, so lowering the total score pushes the scene toward a valid arrangement.

Then the compact form:

L = w_support L_support + w_collision L_collision + w_align L_align + w_relation L_relation

Every symbol:

Lthe total layout violation score
L_supportpenalty for objects that are not properly supported
L_collisionpenalty for objects that intersect each other
L_alignpenalty for pose or orientation mismatch
L_relationpenalty for violating prompt-specified spatial relations
w_support, w_collision, w_align, w_relationweights that decide how strongly each violation affects the update
A tiny worked example
Suppose a mug should sit on a table next to a lamp.
If the mug sinks into the table, the collision term is high. If it floats above the table, the support term is high.
If it ends up behind the lamp instead of next to it, the relation term is high.
Optimization moves the mug until all three terms drop together, because lowering only one term is not enough for a valid final pose.

This objective matters because scene quality depends on several constraints at once. The optimizer needs all of them in the score so it does not fix one problem by creating another.

What can go wrong

What can go wrong

The coarse plan misses an object relation. If the first draft omits a key object or relation from the prompt, later optimization cannot recover it because the required structure was never placed into the scene.
Vision cues are ambiguous. If the rendered views do not clearly expose support or contact, the refinement stage may estimate the wrong scene structure and optimize toward the wrong target.
Constraint weights are misbalanced. If the collision penalty dominates everything else, the optimizer may spread objects too far apart and break intended relations. If relation penalties dominate, objects may satisfy the wording but remain unstable.
Done right. Use a strong prompt parser for the first draft, inspect scene structure from enough views to reveal contacts and supports, and tune constraint weights so support, clearance, and prompt relations all remain active during optimization.

What a runnable demo should prove

Compare three variants: language planning alone, planning plus optimization without vision cues, and the full Scenethesis pipeline. Measure collisions, unsupported objects, relation satisfaction, and final human preference over plausibility.
