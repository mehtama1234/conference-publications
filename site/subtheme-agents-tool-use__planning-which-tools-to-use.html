Planning Which Tools to Use

Papers about helping agents decide which tools to call in the right order, like planning a multi-step recipe before you start cooking.

All themesField mapMathematicsAll explainers
What this is

This cluster focuses on a specific problem: agents have to decide not just which tool to call right now, but which sequence of tools will actually solve the problem. Think of planning as making a recipe before you cook. If you want to make a cake, you need eggs, flour, sugar, butter — you gather them in some order, you prepare your equipment, you mix things in a specific sequence, then bake. If you did everything in the wrong order, you would ruin it. AI agents face the same challenge when solving problems with tools: calling a database query before knowing what question to ask is wasted. Running a spell-checker before you have written the text is pointless. The papers here focus on teaching agents to figure out the right sequence.

Planning is hard because the space of possible sequences is huge. With just ten tools, there are trillions of ways to arrange them. The agent can't try all of them. Also, the right sequence depends on the specific problem — what works for one question might be terrible for another. An agent needs to learn to recognize the shape of a problem and know which sequence of tools works for that shape. Plus, when the agent calls a tool and gets a result, it might need to replan — the result might be unexpected and require a different next step than it originally planned.

Researchers tackle this by building planning systems that reason about dependencies and subgoals. Some papers focus on learning from demonstrations — showing the agent examples of correct tool sequences and letting it generalize, so the agent learns patterns without having to discover them from scratch. Others use search algorithms that explore promising sequences without trying all of them, which saves time by pruning obviously bad paths. Some agents build a model of what each tool does and reason backwards from the goal ('I want this answer; what tool produces that?') to figure out what to call and in what order, because working backwards from the end state often makes the dependencies clearer. The goal is agents that can take a new problem, figure out a reasonable plan, and then execute it.

How the work breaks down

Planning which tools to call splits into five directions: learning patterns from examples, using search algorithms to explore promising sequences, planning offline before you start, building reusable tool abstractions, and orchestrating real workflows at scale. These approaches compete and combine because agents face different constraints—some need to learn quickly from few examples, others need to avoid wasting expensive tool calls, and still others need to handle complex multi-step problems where the right sequence depends on what happened in previous steps.

Learning tool sequences from examples

A core challenge is that agents should not have to discover every useful tool sequence from scratch. If you showed someone a recipe once, they could generalize and cook similar dishes without reinventing. These papers focus on learning tool-use patterns from demonstrations—watching correct examples and picking up which tools naturally cluster together and when to call them.

DRIFT tackles the problem of finding relevant facts (called premises) to prove a theorem. Instead of searching randomly through thousands of facts, it learns to retrieve the right ones by decomposing the theorem into smaller pieces first, illustrating how parts fit together, then formalizing the structure. This way, when it encounters a new theorem of a similar shape, it recognizes patterns and knows which facts to fetch. A Systematic Study of Behavioral Cloning for Scientific Data Annotation shows that larger models absorb patterns from data labeling examples more efficiently—bigger models need fewer labeled examples to learn the task—and that training on multiple related tasks together helps the model generalize, so skills learned on one annotation task transfer to similar tasks because the model has learned general principles rather than memorizing single examples. Together, these papers say: show the agent good examples, and it learns not just the immediate steps but the reasoning structure underneath, letting it handle new cases because the underlying structure generalizes.

Planning via search through tool sequences

Instead of trying every possible tool sequence (which is exponentially many), agents can use search algorithms that prune obviously bad paths early. This saves enormous amounts of computation while still finding good solutions, because by eliminating branches that are clearly not working, you avoid wasting time on dead ends. The challenge is deciding which branches to explore and which to abandon—you need feedback on whether you are going the right direction.

ToolTree uses a search method called Monte Carlo Tree Search, which is like exploring a massive decision tree by sampling promising paths and gathering statistics on which ones tend to lead to good outcomes. It combines two kinds of feedback: information about whether the current path is sensible and information about how many tools you have wasted so far. By pruning paths that are clearly not working, it finds better tool sequences using fewer calls than older methods. AdverMCTS Combating Pseudo-Correctness in Code Generation tackles a different planning problem: when generating code, a sequence that passes your test cases might still be wrong in a subtle way. The paper uses adversarial search to deliberately try to break code that looks correct, forcing the planner to think about edge cases beyond the initial test constraints. Both papers show that search with smart feedback beats brute-force exploration.

Planning offline before execution

A better strategy than reacting one step at a time is to imagine what will happen and plan the full sequence before you start—like mentally running through a recipe before cooking. This is better because you can catch mistakes and adjust your approach before wasting real tool calls. The challenge is that imagination might be wrong, so you need to estimate how uncertain your imagination is and replan if reality doesn't match. Another challenge is generating a plan format that the agent can actually execute.

DreamPhase trains agents to imagine the consequences of tool calls offline (before actually calling them), building a mental model of what each tool does and where they lead. Using this model, the agent sketches out a full plan and measures how confident it is in each step. If the agent's confidence is low for a step, it marks that part as risky and might skip or modify it. This reduces expensive tool calls from 40 down to 10 per task, four times fewer. Simulation to Rules generates both the problem description and the solution plan in a standard planning language called PDDL—it learns to convert visual scenes into formal problem descriptions, so off-the-shelf planners can run on the converted problem and generate a tool sequence automatically. This matters because it separates the task of understanding the problem from the task of planning the solution—you can swap different planners without retraining the understanding part. FlowMAP Generalizable Agent Planning learns to smooth and interpolate between example plans, filling in the space of possible sequences so that new problems that fall between training examples still get reasonable plans. Together, these papers show that pre-computing a plan (even an approximate one) and expressing it in a standard format gives agents a blueprint to follow and lets them reuse planning logic across many problems.

Abstraction and modular tool organization

As agents solve harder problems, they need to compose simple tools into larger chunks—subroutines that do multi-step jobs. The challenge is that the number of possible chunks grows fast, and the agent needs to learn which combinations are worth remembering and reusing. Also, when you compose tools into subroutines, you need the agent to generalize those subroutines to longer sequences than it saw during training.

Emergent Discrete Controller Modules for Symbolic Planning shows that a neural network trained on algorithmic problems (step-by-step procedures like sorting) spontaneously learns to break sequences into chunks—internal modules that each handle one stage of the algorithm. When the network then faces longer sequences at test time, it extends these learned chunks correctly, generalizing far beyond its training length. ToolWeaver solves the vocabulary explosion problem: when you have many tools, naively assigning each tool a separate code expands your vocabulary linearly with tool count, wasting resources. Instead, ToolWeaver learns to pack similar tools into shared codes, so vocabulary grows logarithmically. More importantly, tools that work together get similar codes, so their learned representations overlap and transfer, meaning the agent generalizes better to new tool combinations because the shared codes carry learned knowledge from one tool to another. Together, these papers show that learning hierarchical tool structures—both discovering natural chunks and compressing representations—lets agents handle tool combinations they have never seen before.

Orchestrating complex real workflows

The hardest planning problem is when an agent must orchestrate many tools across multiple steps, with interruptions and surprises. Real problems often require the agent to check its progress, correct mistakes, and adapt the plan on the fly. The challenge is that each tool call is expensive (monetarily or computationally), the problem may be ill-defined at first, and tools sometimes fail or return unexpected results.

MARS (Modular Agent with Reflective Search) tackles automated AI research—a task where each tool might be a different ML experiment with weeks of runtime. MARS learns to divide the search space using insights from past experiments: if one branch of experiments taught a lesson, MARS remembers that and applies it to other branches without re-running. This cross-branch transfer triples the effectiveness of the search budget. R3DAO (Reactive Recovery and Reconstruction) focuses on handling failure: when a tool call produces bad data, instead of abandoning the whole plan, it recovers by reconstructing the data, replanning the rest of the sequence, and continuing. Agent JIT Compilation for Latency-Optimizing Web Agent Planning compiles the agent's action sequence into an optimized order, spotting cases where tool calls can be parallelized or reordered to save time. NaviAgent uses a graph representation of tool dependencies to bilevel-plan: first deciding the high-level strategy (which branch of tools to explore), then planning the low-level order within that branch. When combined, these papers solve the real-world planning problem: agents learn to reuse insights from past work, recover from mistakes, optimize the execution order for speed, and decompose massive problems into manageable scopes.
