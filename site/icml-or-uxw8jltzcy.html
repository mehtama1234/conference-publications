DecoVer: Decompose-and-Verify Planning

DecoVer splits a robot's complex task into smaller, simpler subtasks, checks each one, and verifies it can actually run before trying the next.

Paper explainersAll themesRobotics & Control

Large language models (the kind that power modern AI assistants) can talk about almost anything, but when it comes to planning precise actions for a robot or agent in the physical world, they often get lost in logical details or skip steps. DecoVer fixes this by breaking a big, complicated task down into smaller pieces that are easier to reason about, then checking that each piece is both written correctly and actually runnable before executing it.

Zero assumption version

Why simple task planning fails

When you ask an AI assistant to write a plan for a robot to pick up a coffee cup, move it to a table, and place it carefully, the assistant (a large language model) can generate text that sounds reasonable. But the plan is written all at once, in one shot, without checking whether each step actually makes sense or can run. In messy, changing environments with obstacles and moving objects, this plan falls apart: the robot might skip important steps, or assume something that is not true about the world.

The naive approach couples the language model with a formal planning language (BC+, which is strict about logic and actions) but just asks the model to generate the whole plan in one go. This fails because the model cannot self-correct when it realizes the plan is wrong, and it does not verify that each step is actually executable before moving to the next.

The fix in one sentence. DecoVer breaks the task into hierarchical pieces, verifies each piece's logic and real-world executable correctness, and chains them together safely.

The algorithm as a flow

What it actually does

Step 1: Receive the complex task.

The robot receives a high-level goal (e.g., place the coffee cup on the table safely).

Step 2: Cascading decomposition into subspaces.

DecoVer repeatedly breaks the goal into simpler subgoals, arranging them in layers (each layer depends on the one below).

Step 3: Generate plans for each subgoal.

For each simple subgoal, the language model generates a plan in the formal action language BC+.

Step 4: Dual verification (syntax and execution).

First, check the plan's logic is correct (syntax check). Then, simulate or reason about whether the plan can actually run in the world (execution check).

Step 5: Chain verified plans together.

Once all subgoals are verified, link them in order to form the full plan, which the robot executes.

What the paper changes

What the paper changes

The paper changes how the language model generates the planning code. Instead of asking the model to write the entire plan in one shot (one-shot generation), DecoVer structures the task so the model writes one small, verifiable piece at a time, and checks each piece before moving on. This works because smaller pieces have fewer interdependencies for the model to track, so the model makes fewer mistakes and catches contradictions early.

The hidden quantity

The hidden quantity: Verification coverage

measured quantity  =  Verification coverage

The core hidden quantity DecoVer measures is how many generated subplan pieces actually pass both checks—syntax (the code is written right) and execution (it can run)—without human intervention or error correction. This is called verification coverage: the fraction of subtasks that are simultaneously logically sound and actually runnable.

The paper estimates this by running the dual verifier on each subgoal independently. A subgoal only counts as verified if it passes both the syntax check (BC+ can parse it and it is logically consistent) and the execution check (the action preconditions are met in the world state, and the expected post-conditions follow).

Why it works

Why decomposition and verification work

The reason this works is simple: a language model is much better at writing small, focused, logically self-contained pieces than at generating a giant, interdependent program all at once. When you ask it to write one subtask (e.g., 'grab the cup') in isolation, the model has fewer dependencies to track, fewer ways to contradict itself, and easier mental state to reason about.

The verification step catches mistakes before they compound. When you verify syntax first (the code parses and obeys the rules of the action language), you eliminate malformed plans immediately. When you verify execution (the preconditions are true, the action will succeed), you catch logical impossibilities early. A mistake in an early subtask would normally break everything downstream; catching it before chaining prevents this cascade.

Hierarchical decomposition also maps to how humans naturally break down complex tasks: instead of memorizing the entire recipe, you focus on one step at a time, check that it worked, then move to the next. This mirrors human task planning, which the language model has learned from.

Math after the picture

The verification scoring formula

First in words:

Final plan success probability is the product of each subgoal's verification score and execution likelihood, where each subgoal is checked for syntactic correctness (1 if passes, 0 if fails) and execution preconditions (proportion of preconditions satisfied in the world state).

Then the compact form:

P_success = prod_i [ (syntax_i) * (precond_i / total_precond_i) ]

Every symbol:

P_successprobability the full plan succeeds
syntax_i1 if subgoal i is syntactically correct, 0 otherwise
precond_inumber of preconditions satisfied for subgoal i
total_precond_itotal preconditions required for subgoal i
prod_imultiply the scores for all subgoals
A tiny worked example
Subgoal 1 (grab): syntax_1 = 1 (well-formed), precond_1 = 3 out of 3 (all conditions met); score = 1 * (3/3) = 1.0.
Subgoal 2 (lift): syntax_2 = 1, precond_2 = 2 out of 2; score = 1 * (2/2) = 1.0.
Subgoal 3 (move): syntax_3 = 1, precond_3 = 1 out of 2 (path is clear but target location blocked by obstacle); score = 1 * (1/2) = 0.5.
Subgoal 4 (place): syntax_4 = 1, precond_4 = 2 out of 2; score = 1.0.
P_success = 1.0 * 1.0 * 0.5 * 1.0 = 0.5 (50% chance the plan succeeds; step 3 is the bottleneck).

The product shows that each unverified subgoal drags down the whole plan; fixing even one weak step raises the success rate.

What can go wrong

What can go wrong

The language model still hallucinates within a subgoal. Even with decomposition, the LLM can generate syntactically correct but semantically nonsensical plans (e.g., moving a cup to a location that does not exist). If the execution verification is not rigorous (e.g., it only checks preconditions, not the world model's full state), bad plans sneak through.
Decomposition is not always aligned with the true task structure. If the hierarchical breakdown does not match how the subtasks truly depend on each other, verification may pass subtasks that are actually incompatible when chained. For example, if subgoal 2 assumes the gripper is in a position that subgoal 1 never achieves, the chain will fail despite passing individual checks.
Execution verification is expensive or incomplete. A full verification of whether a plan actually runs requires simulating the world or querying a real-time model. Partial or cheap approximations (e.g., checking only obvious contradictions) leave holes. If you cannot afford full simulation, some bad plans slip through.
Done right. DecoVer mitigates these by using formal action languages (BC+) that are strict about logic, by aligning decomposition with the planning domain structure, and by running both syntax and execution checks together. When verification is rigorous and aligned, the false-negative rate (good plans rejected) is low, and most failing plans are caught.
What a runnable demo should prove

What a runnable demo should prove

A concrete demo should show: (1) take a complex, multi-step embodied task (e.g., fetch and place objects in a simulated kitchen with obstacles); (2) generate a plan using naive LLM + BC+ (one-shot) and using DecoVer (decompose + verify); (3) simulate both plans in the same environment; (4) measure success rate (plan completes without error), total verifiable steps (how many subtasks passed checks), and error recovery (do unverified subtasks fail silently or get caught by the verifier).

success_rate = (number of tasks completed without error) / (total tasks attempted); verification_rate = (subtasks passing both checks) / (total subtasks); cascading_failure_reduction = (steps where one error broke the rest) in naive - (steps where one error broke the rest) in DecoVer

The demo must make it obvious that decomposition catches errors early, and that verifying each piece prevents cascading failures that plague one-shot planning.
