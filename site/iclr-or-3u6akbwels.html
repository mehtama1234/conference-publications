ManipEvalAgent: Quick Evaluation of Robot Hands

Instead of testing a robot policy thousands of times, ask a smart agent to watch a few runs and say what it thinks — fast and honest.

Paper explainersAll themesRobotics & Control

Testing whether a robot can pick things up usually means running it in simulation over and over, sometimes thousands of times. That takes hours. This paper says: use a smart agent that watches a small number of actual attempts, asks clarifying questions, and builds a detailed understanding of what the robot can and cannot do. The result is faster testing because each test targets a specific gap in what the agent knows, customizable because the agent writes tests for your exact questions, and honest — not just a single score but detailed diagnoses.

Zero assumption version

Testing robot hands is slow and tells you almost nothing

Today's robot evaluation has a simple flaw: you run thousands of test attempts in a simulator, count successes and failures, and report a single number — like 78 percent success rate. That takes hours. Worse, it does not actually tell you WHY the robot failed or what it is good at.

A beginner might try to make evaluation faster by running fewer tests. But with fewer tests, the success percentage becomes unreliable — maybe one run got lucky, maybe the next one hit an unlucky random seed. So most researchers stick with the slow, massive-sampling approach.

The deeper problem: a single score hides everything that matters. Is the robot bad at grasping cups but good at blocks? Does it fail on tall objects? Hard-to-predict textures? You cannot tell from 78 percent.

The paper's move in one sentence. Use a code-writing agent that watches a few real attempts, asks what you want to know, and constructs tasks and measurement functions on the fly — no need to pre-design thousands of tests or run them all.

What the paper changes

The one thing the paper changes

Instead of a fixed evaluation script that runs the same test over and over, the paper changes the evaluation process itself: every round, a code-writing agent creates a NEW task and measurement function tailored to what you want to know.

the object it moves  =  evaluation code
The hidden quantity

The hidden quantity: what matters to the robot

measured quantity  =  Diagnosis — the actual reason for failure

Every time the robot fails a task, something concrete went wrong: gripper angle, object texture, contact point, speed. Most evaluation just records pass or fail. This paper measures something deeper: what the diagnosis is, explained in plain words.

The VLM (a vision-language model — a system that reads images and text together) watches the video and writes down what happened: not just a binary pass-fail, but 'the gripper rotated too far' or 'the object slipped at the moment of lift'. This diagnosis is the hidden quantity that lets the agent plan the next smart test.

Why it works

Why adaptive evaluation works better than brute force

Massive sampling works only if you already know what to measure. A robot hand has dozens of degrees of freedom: gripper opening, wrist angle, approach speed, hand orientation. Testing all combinations exhaustively takes exponential time.

Humans avoid this by asking questions: Does size matter more than shape? Is texture the bottleneck? Each answer narrows the search space. ManipEvalAgent automates that reasoning. The code-generating agent writes a test for a specific hypothesis (say, 'tall objects are harder'). The VLM watches the videos and gives a clear diagnosis. The agent reads that diagnosis and designs the NEXT test to answer the follow-up question. After just 5–10 rounds of small-batch testing, the agent has a richer understanding than brute force gives in hours.

Efficiency comes from this adaptive planning: each test is chosen to be maximally informative about what the agent still does not know. That is why a handful of videos beats thousands of random samples.

Adaptive information gain

First in words:

The time to evaluate a policy is roughly: (number of rounds) × (tests per round) + (time to generate code and analyze videos). Because each round is chosen to close the biggest gap in the diagnosis, the algorithm reaches stable conclusions in fewer rounds than brute-force uniform sampling.

Then the compact form:

time_adaptive = R × B + overhead vs time_brute = 1000 × 0.1 + 0 where R << 1000 when using adaptive selection

Every symbol:

Btests per round, small batch

1000typical number of brute-force samples
0.1seconds per test in simulation
A tiny worked example
Brute-force evaluation: 1000 tests × 0.1 seconds = 100 seconds, plus VLM analysis of all videos = 200 seconds total.
Adaptive evaluation: 8 rounds × 6 tests per round = 48 tests × 0.1 seconds = 4.8 seconds per round; 8 rounds = 38.4 seconds for simulation, plus VLM analysis per round ≈ 50 seconds total overhead = 88 seconds total.
Adaptive saves time: 200 seconds vs 88 seconds. More importantly, the adaptive result is richer because each test targeted specific unknowns about the robot.

Adaptive beats brute-force because each test is chosen to answer a specific gap in what the agent knows, so the diagnosis shrinks the search space faster than random tests scattered across the whole space.

What can go wrong

What can go wrong

The agent generates bad code. If the code-generating agent writes a malformed task (wrong object shape, unrealistic friction), the test result is meaningless. The system must validate generated code and fall back to safe templates if needed.
The VLM misreads the video. Vision-language models sometimes hallucinate. If the VLM says 'the gripper opened too wide' when it actually opened the right amount, the agent's next test is misdirected. This happens because VLMs are trained on images and text from the internet, not on real robot videos, so they sometimes invent details that are not there. Validation and re-runs help by asking the VLM the same question multiple times and checking for consistent answers.
The agent gets stuck in a loop. If each round's diagnosis does not shrink the gap in what the agent knows, the agent may ask the same question in different ways, wasting time. A termination criterion and diversity check are needed.
Done right: repeated validation and structured prompts. Validate code before running it. Ask the VLM the same question in multiple ways and take consensus. Set a hard limit on rounds. These safeguards turn adaptive evaluation into a reliable tool.
What a runnable demo should prove

What a runnable demo should prove

Build a small simulator with one gripper and three objects (a cube, a cylinder, a box with a handle). Ask ManipEvalAgent: Can the robot grasp things by their handles? Run 8 adaptive rounds, each with 5 simulation attempts. Record the total time, the count of distinct failure modes the VLM identified, and the final agent-written report. Compare to brute-force: running 50 random tests on those objects with no adaptive planning. Measure whether adaptive found the handle-grasping weakness in fewer total simulations.

rounds_to_actionable_diagnosis = arg-min(R) such that VLM report lists >=3 distinct failure modes + agent's next-test hypothesis differs from prior round

The demo is successful if the adaptive system reaches a richer diagnosis (more failure modes, more detail) in one-third the wall-clock time of brute-force.
