CoDA: Agentic Systems for Collaborative Data Visualization

Instead of one model writing chart code from scratch, use specialized agents that talk to each other—one reads data file names and structure, one plans steps, one writes code, one fixes errors.

Paper explainersAll themesAgents & Tool Use

When you ask a model to turn raw data files into a chart, it often fails because it does not know what files exist, what columns are in them, or how to recover from mistakes. CoDA splits the job into four specialized agents that work together: one understands the data structure, one plans the task, one writes code, and one fixes problems by running the code and learning from errors.

Zero assumption version

One model, many unknown files

Making a chart from data requires knowing what files you have, what columns are in each file, and how they connect. When a person has messy data scattered across spreadsheets, a human first looks at file names and column headers before deciding what to plot.

A naive approach: feed the model file paths and ask it to write code that loads and visualizes the data. The problem is severe—the model guesses at column names, tries to join tables that do not match, makes syntax errors in the code, and then stops. It cannot see the actual error messages from running the code. When asked to fix it, the model often makes the same mistakes again because it was never told what went wrong.

The challenge. One model writing visualization code cannot discover the data structure, plan reliably, or learn from execution failures.

The algorithm as a flow

What it actually does

Agent 1: Read the data structure

Scan file names and headers to understand what columns and tables exist.

Agent 2: Plan the task

Decide which files to load, how to join them, what to plot.

Agent 3: Write visualization code

Generate Python code to load, transform, and plot the data.

Agent 4: Run and reflect

Execute the code, see what breaks, and tell the other agents what went wrong.

Loop if needed

Each agent receives error messages and refines its work, not just guessing again.

What the paper changes

The thing the paper changes

Instead of having one language model answer the entire question in one shot, CoDA breaks it into four specialized roles. Each agent sees different information: the metadata reader knows column names, the planner knows the task structure, the coder writes syntax, and the reflector sees actual execution errors.

the object it moves  =  Work split into four specialized agents
The hidden quantity

The hidden quantity: Knowledge of execution error

measured quantity  =  What actually broke in the code

When code runs and crashes, the error message tells you exactly what went wrong—a missing column, a type mismatch, a syntax error. A single model never receives this signal; it simply guesses the next version. CoDA's reflector agent reads the real error message and passes that knowledge back to the coder.

The paper measures success by how many times the final visualization actually runs without errors and produces a reasonable chart. This is impossible without executing the code and learning from failures.

Why it works

Why splitting into four agents fixes the problem

A single model is forced to predict everything at once: file names, column names, plot type, and syntax—without seeing data or error messages. Each guess has to be right or the whole chain breaks. A four-agent system works differently. The metadata reader actually inspects the files and reports what is there. The planner works from that concrete report, not guesses. The coder writes logic specific to the real column names and table structure. The reflector runs the code and sends real error messages back—not ambiguous feedback, but exact syntax errors, missing values, or type conflicts.

The key mechanism: iteration with concrete information. If the code fails, the reflector tells the coder 'column X does not exist' instead of the coder guessing again blindly. Each agent has a smaller, clearer job, and can use information from the others to do it better, because each one works from concrete inputs—real file names, real error messages—instead of predictions. No agent is trying to read minds or predict errors—they all read what is actually there or what actually failed.

Scoring the quality

First in words:

Success score equals number of correct outputs divided by total attempts, where a correct output is a visualization that runs without error and shows the intended data transformation.

Then the compact form:

success_score = (count_working_outputs) / (count_total_outputs)

Every symbol:

count_working_outputsnumber of visualizations that run and display correctly
count_total_outputstotal number of visualization attempts across all test cases
success_scorefraction of attempts that succeeded (ranges from 0 to 1)
Tiny worked example
Test case 1: Single model creates code that crashes (missing column). Attempt count = 1, working = 0.
Test case 1: CoDA creates code, reflector sees 'column X not found', coder fixes it. Attempt count = 2, working = 1.
Test case 2: Single model guesses wrong plot type. Working = 0 out of 1.
Test case 2: CoDA planner receives metadata, creates correct plot type. Working = 1 out of 1.
Across 10 test cases: single model 3 working out of 10 (30%). CoDA 8 working out of 10 (80%).

The working count rises because each agent sees concrete information, not predictions.

What can go wrong

What can go wrong

Metadata reader misses column subtlety. If a file has a column named 'date' but it is stored as text, not a timestamp, the metadata reader may not report the type correctly. The planner then requests a time-series plot on text data, and the coder writes code that crashes.
Planner assumes a join strategy that does not exist. Metadata reader reports two files with an 'ID' column, but one file uses string IDs and the other uses numbers. The planner assumes they join smoothly; they do not.
Reflector feedback loop stalls. If the error message is cryptic or the reflector does not know how to translate it for the coder, the loop repeats the same mistake.
Done right. When each agent has a clear input (real data, real errors, real column names) and a single responsibility, failures drop sharply. The team is less likely to miss edge cases that one model would get wrong.

What a runnable demo should prove
