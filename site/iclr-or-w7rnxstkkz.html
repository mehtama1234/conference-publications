TDBench: Time-Sensitive QA from Temporal Databases

TDBench builds time-sensitive question-answer pairs automatically from temporal databases, replacing human labor to scale how we test whether LLMs handle facts that change over time.

Paper explainersAll themesDatasets & Benchmarks & Evaluation

Large language models must answer questions about facts that shift with time. A model trained years ago might know the current president from memory, but not what laws changed last month. Yet testing this ability has been slow because people must hand-write question-answer pairs. TDBench flips this: it uses real temporal databases (organized records with time stamps) plus database tricks to generate test pairs automatically, making evaluation fast and scalable.

Zero assumption version

Testing time-sensitive knowledge is stuck in a bottleneck

A language model is like a student who memorized a textbook on graduation day. After that day, it never learns new facts—if you ask about yesterday's news, it either knows it from training or it does not. The problem is harder for time-sensitive facts: the correct answer to 'Who leads this country?' changes every few years, and the date of a historical event stays fixed. To test whether a model handles time correctly, someone must write questions and the right answers by hand. If you want questions spanning decades, or about thousands of events, or about company records that shift monthly, this is slow and expensive.

A beginner might just grab Wikipedia or Wikidata and ask: 'When was this person born?' But that misses the real challenge. Modern models are asked harder questions in real applications—a business might have temporal data about customer records, product prices, or event dates that experts care about. Those databases exist, but writing test questions from them by hand is labor-intensive and does not scale. The field ends up testing only on well-known historical facts, not on the application-specific, ever-changing data that models actually encounter in production.

In one sentence. TDBench auto-generates time-sensitive test pairs from temporal databases using database techniques, scaling evaluation without manual work.

The algorithm as a flow

What it actually does

Start with a temporal database

A database where records have time stamps and facts shift over time (who reports to whom, what price does this item cost).

Encode database structure as rules

Temporal functional dependencies—formal statements of which fields change together (if person X moves to office Y, then office Y's occupant is X).

Run automated queries

Database techniques like temporal SQL joins find contradictions and changes across time windows, extracting test QA candidates.

Generate QA pairs at scale

Each query becomes a test pair: question (What was the occupant on this date?) and gold answer (the correct value from the database on that date).

Score time and accuracy separately

Time accuracy measures whether the model's date reference is correct alongside traditional answer accuracy, catching models that guess the right answer on the wrong date.

The hidden quantity

The hidden quantity: Time accuracy

measured quantity  =  Time accuracy—correctness of date references

Time accuracy is a measurement the paper introduces. It is not a new concept in linguistics; it is a deliberate choice to measure whether the model's explanation contains a date reference that is correct. When a model answers 'In 2015, the president was X,' the model gets credit for time accuracy only if 2015 is the right year for when X was actually president. Answer accuracy is separate: did the model name the right person? A model that says 'In 2010, the president was X' (when X was not president until 2015) gets zero time accuracy even if X is the right answer. This split measurement reveals a hidden failure mode: models that memorize the right answer but attach the wrong date or temporal context.

The paper measures time accuracy by checking the model's generated text for explicit date references, then cross-referencing them against the ground truth from the temporal database. It is a narrow but precise metric that existing benchmarks missed because they only checked whether the final answer was right, ignoring when or how the model thought the fact was true.

Why it works

Why automated generation from databases works

A temporal database is a filing cabinet where each record is time-stamped and facts can change over time. A temporal functional dependency is a rule: 'If the manager of employee X changes on this date, then the team roster must also change on the same date.' These rules encode the real structure of how facts relate and shift together. When the database system checks these rules across time windows, it finds points where a fact changed—moments that make natural test cases. For instance, if the database says manager-of-Alice changed from Bob to Carol on January 15, then a natural test question is 'Who was Alice's manager on January 14?' (Bob) and 'Who was Alice's manager on January 16?' (Carol). These pairs are accurate because they come directly from the data, and they scale automatically: if the database has 10,000 employees and ten years of records, thousands of such pairs emerge without a human writing a single line.

Temporal databases already encode the facts and their dates; the paper just extracts questions by exploiting the structure. Temporal SQL joins (a database technique to connect records across time) let you ask 'Show me all records that changed between these two dates' or 'Find contradictions in the data.' Each query result becomes a test question—guaranteed to have a correct answer because the database validates it. A human writing 50 pairs per day by hand would need months to cover a single company's decade of records; automated queries do it in minutes, because each query spawns many pairs at once.

Math after the picture

The scoring equation

First in words:

Time accuracy is the count of model explanations with correct date references divided by the total explanations generated. Combined with answer accuracy for a composite score.

Then the compact form:

Time-Accuracy = (Correct-Date-Refs) / (Total-Model-Outputs); Composite-Score = (Answer-Accuracy + Time-Accuracy) / 2

Every symbol:

Correct-Date-RefsNumber of model explanations where the stated date matches the ground truth from the temporal database
Total-Model-OutputsNumber of test questions the model answered
Answer-AccuracyFraction of model answers matching the gold answer
Time-AccuracyFraction of model answers with correct temporal references
A tiny worked example
Suppose the model answers 10 TSQA questions. On 8, it gives the right answer. On 6 of those 8, it also provides the correct date.
Answer-Accuracy = 8 / 10 = 0.80 (80% got the answer right).
Time-Accuracy = 6 / 10 = 0.60 (60% got both the date and answer right).
Composite-Score = (0.80 + 0.60) / 2 = 0.70 (70% overall).
This model memorizes answers but is shaky on dates; old benchmarks would report 80%, missing the hidden time-sense gap.

Separate scoring of date and answer reveals whether a model truly understands temporal facts or just parrots answers.

What can go wrong

What can go wrong

Database has missing or inconsistent time stamps. If the temporal database itself has gaps or contradictions, generated pairs will be wrong. TDBench depends on data quality; garbage in, garbage out.
Model gives no explicit date reference. A model might answer correctly but say nothing about when—no date in the explanation. TDBench then cannot score time accuracy for that pair, unless you count silence as wrong.
Temporal functional dependencies are not fully specified. If the rules encoding how facts relate do not capture all the real constraints, the queries might miss test cases or generate pairs with loose ground truth.
Done right. With clean, well-documented temporal data and explicit rules, TDBench scales to thousands of pairs and reveals time-sense failures that answer-only metrics hide.
