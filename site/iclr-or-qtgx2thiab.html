Same Content, Different Representations: A Controlled Study for Table QA

Holding table content fixed while changing structure reveals which methods excel at structured data, which at text, and which balance both.

Paper explainersAll themesDatasets & Benchmarks

Table Question Answering (asking questions about data in tables) works differently depending on how the table is formatted. This paper takes the same table, represents it two ways—one as a clean SQL database, one as messy text—and measures how each method (SQL query generator, language model, or hybrid) responds. The result: SQL excels at rigid structure, language models handle text flexibly, and only hybrids work reliably across both.

Zero assumption version

Same table, infinite ways to write it

Real-world tables live in two homes: SQL databases (structured, rigid, every column named and typed) and spreadsheets or HTML pages (semi-structured, text mixed in, columns written as free English). Most Table Question Answering research tests on one format and assumes the method works on both. But SQL query generators assume column headers are unambiguous and data is typed; language models assume readable prose. If you take the same table and flip its format, the methods break in different ways.

A beginner might assume that if a method works on one format, it works on the other—the content is identical, after all. But SQL generators, when shown the same data as text instead of columns, lose their rigid schema and start hallucinating made-up tables. Language models, when given SQL schemas, struggle to reason over large tables because the schema is not readable prose.

The method in one sentence. Take an existing table, convert it to a different format using a template-based pipeline, and test SQL, language model, and hybrid methods on both versions to measure how much structure matters.

What the paper changes

What the paper changes

The paper holds table content constant and changes one thing: the format (structure of the representation). Instead of testing on fixed-format benchmarks, it creates pairs—same data in structured and semi-structured form—and measures how each method type responds to each format.

the object it moves  =  table representation format
The hidden quantity

Table structure burden: a hidden measure of method compatibility

measured quantity  =  structure burden

Every table has a structure burden: how much a method's reasoning power depends on the table being in a particular format. SQL generators have high structure burden—they need rigid schemas, clear types, unambiguous column names. Language models have lower structure burden on text (they read prose fluently) but higher burden on SQL schemas (they read logical notation awkwardly). Hybrids distribute the burden, so no single format trips them up.

The paper estimates this by holding content identical and measuring how much accuracy drops when switching format. If a method loses 20 points when the table flips from SQL to text, its structure burden is high. The benchmark REPAIRTQA isolates this by varying four dimensions—table size, joins, query complexity, and schema quality—so you can see exactly which structural properties break which methods.

Why it works

Why methods break when format changes

SQL generators work by mapping natural language to SQL logic. They assume schemas are clear: column names describe content, data types encode constraints, keys link tables. When you feed them the same table as free-form text instead, the schema vanishes. The model has to infer structure from context, which it cannot do reliably. It starts inventing columns that do not exist, confusing which field is which, failing to join tables that the semi-structured prose does not make explicit.

Language models read text naturally. They do not assume rigid schemas; they parse any prose. But when you feed them a SQL schema as raw symbols, they have to interpret metadata (what does PRIMARY KEY mean?) and navigate logical notation, which slows reasoning and introduces errors. They also struggle with long rigid tables because they cannot skim—they process text sequentially, piece by piece, so huge structured tables require much more computational work and exceed graphics-card memory limits faster.

Hybrid methods route: for structured parts (numeric lookups, joins), they use SQL; for unstructured parts (text reasoning, description), they use the language model. When format changes, only one branch is affected. This routing lets them preserve accuracy across both representations.

Math after the picture

Accuracy loss as a function of format mismatch

First in words:

accuracy_method = baseline - mismatch_penalty * table_structure_burden * format_shift

Then the compact form:

acc_method = acc_baseline - alpha * burden * |format_shift|

Every symbol:

acc_methodfinal accuracy on the given format
acc_baselineaccuracy when format matches method strengths
alphasensitivity constant (how fast accuracy falls)
burdenstructure burden: 0 = format-agnostic, 1 = fully dependent
format_shiftdistance from ideal format: 0 = perfect match, 1 = worst case
A tiny worked example
SQL method on structured table: acc_baseline = 90, burden = 0.9 (SQL-dependent), format_shift = 0 (ideal match) -> acc = 90 - 0.5 * 0.9 * 0 = 90.
Same SQL method on semi-structured table: format_shift = 1 (worst case) -> acc = 90 - 0.5 * 0.9 * 1 = 85.5.
LLM method on same structured table: burden = 0.6 (moderate SQL burden), format_shift = 1 -> acc = 78 - 0.5 * 0.6 * 1 = 75.
Hybrid on semi-structured: burden = 0.3 (low because it routes), format_shift = 1 -> acc = 82 - 0.5 * 0.3 * 1 = 80.85.

Higher structure burden means the method's accuracy swings more violently when the table format flips.

What can go wrong

What can go wrong

SQL method hallucinates on text. When a SQL generator sees semi-structured prose, it invents column names and relationships that do not exist in the data, because it cannot extract structure from narrative text.
Language model loses precision on rigid schemas. Logical notation (PRIMARY KEY, JOIN syntax, type declarations) is not natural language. Language models interpret it haltingly, making mistakes on complex multi-table reasoning.
Large tables exceed all methods' capacity. SQL generators truncate or lose rows. Language models hit memory limits from processing huge amounts of text. Hybrids still struggle with tables larger than 1000 rows because no single method scales cleanly.
Noisy schema breaks schema linking. If column names are ambiguous, vague, or misspelled, SQL methods fail to match them to the query. This affects SQL and hybrid methods equally.
Hybrid method works across both. Because routing splits responsibility, hybrids handle format changes better. They degrade more gracefully as tables grow or schemas worsen, though no method is immune.
What a runnable demo should prove

What a runnable demo should prove

Build a small benchmark with three tables in two formats: (1) a simple 10-row SQL table with three columns, represented both as SQL and as pipe-delimited text; (2) a 50-row table with joins, in both formats; (3) a table with a noisy schema (misspelled or vague column names). For each, generate 10 simple questions (e.g. 'How many rows where X > 5?', 'What is the sum of Y?', 'Join A and B where Z matches'). Run a SQL query generator, a language model, and a hybrid pipeline on each version and measure accuracy.

format_robustness = accuracy_text / accuracy_structured

A method with a score near 1.0 does not care what format the table is in. SQL will score far below 1.0 (breaks when format changes). Hybrid will stay near 1.0 (works across both).
