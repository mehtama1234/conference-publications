Skill-Based Mixture-of-Experts: Adaptive Routing for Heterogeneous Reasoning

Ask the query what skills it needs, then pick the right expert and combine their answers instead of picking one expert for the whole task.

Paper explainersAll themesAgents & Tool Use

When you have multiple expert models (for math, science, medicine, etc.), the usual way is to pick one expert for the entire task. But different questions within the same task need different expertise: a math question needs the algebra expert, while a chemistry question needs a different one. This paper figures out which skills each question needs, picks the right expert for that question, and combines the answers from multiple experts smartly. The clever part: doing this for each question is expensive (loading models over and over), so the paper groups questions by which expert they need, loads each model once, and processes them all in a batch.

Zero assumption version

One expert per task is too blunt

When you have multiple expert models trained on different knowledge (one for math, one for reading, one for medicine), the usual system picks one expert to answer ALL questions in a task. This makes sense if every question in the task needs the same skills, because then that expert will be correct for every question and there is no point switching.

But in reality, a benchmark like MMLU (a test with thousands of questions across many subjects) mixes them: some questions ask about algebra, some about biology, some about history. Picking one expert for the whole benchmark wastes expertise — the algebra expert sits idle when a history question comes in.

A beginner's first try: process each question individually. Send question 1 to the best expert, load it into memory, get the answer, unload it, then load expert 2 for question 2. This works perfectly but kills performance — on a single GPU, constantly loading and unloading models takes longer than the models running.

The method in one sentence. Figure out what skills the question needs, pick all the experts who have those skills, run them in parallel by batching questions together so each model loads once, then blend the answers.

The algorithm as a flow

What it actually does

Read the query.

A question comes in: 'What is the ionization energy of helium?'

Infer the skills needed.

A lightweight process (not a model; described in the paper) identifies skills: chemistry, atomic physics, numerical reasoning.

Find experts with those skills.

The system knows which experts trained on chemistry, physics, numerical reasoning; select all relevant ones.

Batch and load efficiently.

Group all incoming questions by which experts they map to; load each expert model once; run all questions through it.

Synthesize answers from all experts.

Each expert generated its own answer; an aggregator (itself tuned per skill-set) picks or fuses them into one final answer.

What the paper changes

What the paper changes: the routing decision

The core change is shifting from picking one expert for the whole task to picking a set of experts for each individual question. The routing decision moves from the task level (coarse: 'use expert #3') to the instance level (fine: 'this question needs experts #2, #5, and #7').

the object it moves  =  Expert selection rule
The hidden quantity

The inferred skill: the hidden quantity

measured quantity  =  Skill tags inferred from the query

The paper does not train a model to infer skills; instead, it uses a lightweight symbolic process that reads the query and flags which skill categories it belongs to. For example, parsing 'What is the ionization energy of helium?' would flag: chemistry, atomic properties, numerical calculation.

This skill tag is the hidden quantity because it determines which experts are activated for that question. The paper never explicitly trains to infer skills; it infers them on the fly by analyzing the query text. The skill tag sits between the question and the expert selection, invisible in a simple task-level baseline, but it is what makes routing work correctly.

Why it works

Why it works: the causal chain

The mechanism has three levels. First, inferring skills from the query lets you pick the right expert for that specific question instead of betting on one expert for all questions. A history question triggers the history expert, not the math expert. Second, multiple experts answer the same question because different expertise may lead to different correct answers or different confidence — the synthesizer can then pick the highest-confidence answer or blend them. Third, the batch inference trick avoids the loading overhead: group questions by expert, load each expert model once, run all 50 questions that need math through the math expert in a single batch. This amortizes the loading cost across 50 questions instead of loading once per question.

The payoff: each question gets routed to experts who actually trained on its subject matter, and the system can run many questions in parallel without repeatedly freezing to load and unload models. On one GPU, you can run multiple expert models because they do not all load at once — only the experts that the current batch of questions needs are in memory.

The scoring equation

First in words:

Expert score for a question equals the sum of skill-match weights: if the question needs algebra and the expert trained on algebra, the expert gets a high score; multiply by the expert's measured accuracy on that skill.

Then the compact form:

expert_score_j = sum_skill ( skill_match(query, skill) * expert_accuracy_j[skill] )

Every symbol:

expert_score_jhow well expert j is suited to this question
skill_match(query, skill)does the query need this skill; 1 if yes, 0 if no
expert_accuracy_j[skill]how accurate expert j is on questions needing this skill
A tiny worked example
Question: 'What is two plus three?' Inferred skills: arithmetic. skill_match(query, arithmetic) = 1.
Expert A trained on arithmetic: expert_accuracy_A[arithmetic] = 0.92. Expert B trained on history: expert_accuracy_B[arithmetic] = 0.30.
expert_score_A = 1 * 0.92 = 0.92. expert_score_B = 1 * 0.30 = 0.30. Arithmetic expert wins; route to A.
If the question needed both arithmetic and reasoning: skill_match(reasoning) = 1. expert_score_A = 1 * 0.92 + 1 * 0.88 = 1.80. expert_score_B = 1 * 0.30 + 1 * 0.75 = 1.05. A still wins.

Higher match between question skills and expert training means higher score, so the right expert gets picked.

What can go wrong

What can go wrong

Skill inference is fragile. The symbolic skill inference process uses keyword and semantic heuristics. A poorly written query or a question phrased in an unusual way may be mis-tagged. If the inferred skills are wrong, the wrong experts get routed to, and the answer suffers. The paper notes that skill inference is not learned, so edge cases are not handled automatically.
Aggregation assumes expertise signals. The synthesizer blends or picks among k expert answers. If none of the routed experts actually trained on the question topic (because skill inference failed), the synthesizer is picking the best among k wrong answers. The final answer quality is only as good as the worst-routed expert involved.
Unseen skill combinations. The system was trained on a fixed set of skill categories (algebra, chemistry, etc.). A question that needs a skill never seen during tuning (e.g., a new niche domain) will not be recognized. The routing will default to a coarse fallback, losing the benefit of instance-level selection.
Batching by expert works best at scale. The efficiency gain from batching only appears if enough questions share the same required experts. If every question needs a unique set of experts, batching does not group them, and the system reverts to repeated loading. The paper shows this works well on large benchmarks (hundreds or thousands of questions) because there are many questions for each skill category, so batching groups them; but it may not help on tiny tasks (single question at a time), because there is nothing to batch with.
What a runnable demo should prove

What a runnable demo should prove

Build a small multi-expert system with three pre-trained models: one trained on math, one on science, one on reading. Create a mixed benchmark with 20 math questions, 20 science questions, 20 reading questions (60 total, shuffled). Implement the skill inference: parse each question for keywords (if it mentions numbers or equations, flag math; if it mentions atoms or reactions, flag science; else flag reading). Route each question to the inferred expert. Measure accuracy, wall-clock time to answer all 60 questions (comparing to task-level selection and naive instance-level selection without batching).

accuracy = (num_correct_answers / 60), wall_clock_time = total_seconds_to_answer_all_60_questions

The demo must make it impossible to miss that instance-level selection picks the right expert for each question (higher accuracy), because the right expert was trained on questions like this one, and that batching by expert keeps GPU memory low and finishes faster than naive per-question loading, because each model is loaded once and processes many questions instead of being loaded and unloaded for every question.
