MAS-ProVe: Process Verification in Multi-Agent Systems

Checking intermediate steps in multi-agent reasoning does not reliably improve performance, even though it works well for single agents.

Paper explainersAll themesLLMs & Foundation Models

When a single AI model solves a math problem step-by-step, you can check each step to catch and correct errors before they pile up. This process verification makes sense: catch the mistake at step 3 instead of accepting a wrong final answer. Multi-agent systems work differently—multiple specialized agents coordinate to solve one problem, each taking a turn. This paper tests whether the same verify-and-correct strategy works when agents hand off work to each other. The surprise: it often does not. The paper studies six different multi-agent setups and finds that verification produces unpredictably varied results across runs, and frequently fails entirely, because verifiers trained on single-agent reasoning cannot see how each agent's step affects downstream work.

Zero assumption version

Single-agent verification works. Multi-agent handoffs don't.

In single-agent reasoning, process verification is a simple win. When an AI solves a math problem, it writes intermediate steps ("step 1: add 5 and 3 to get 8; step 2: multiply by 2..."). A verifier checks each step—a separate evaluator that asks: "Is this step correct given what came before?" If the verifier flags step 3 as wrong, the agent tries a different path. This catches errors early. The approach works: fewer wrong final answers.

Multi-agent systems are messier. Instead of one agent with one trajectory, you have five agents working together, each with its own context and view of the problem. Agent A suggests a direction. Agent B interprets it and builds on it. Agent C critiques. Agent D proposes a refinement. The output of each agent is a "step" toward the final answer. Applying the same verify-and-correct logic seems obvious: after each agent speaks, check if that contribution makes sense. But the paper found a stubborn problem: verification flags too many things as wrong because each agent sees only partial information, or misses coordination failures between agents, or rewards locally sensible steps that don't work well together. The beginner would expect more checking to mean fewer errors. Reality: more verification often means less predictable results, sometimes worse.

The core problem. Multi-agent coordination requires understanding how each agent's output affects others. A verifier trained on single-agent reasoning does not see those dependencies clearly, so its judgments are often wrong or inconsistent.

The algorithm as a flow

What it actually does

Run multi-agent system without verification.

Each agent takes its turn. Record the final answer accuracy.

Run it again with verification.

After each agent's output, a verifier judges: is this contribution sound?

If verification says no, the agent retries.

Search for a better continuation by generating multiple options and picking the one the verifier ranks highest.

Measure the context given to the verifier.

Try four variants: current step only, summarized context plus step, etc.

Compare results across six different multi-agent architectures.

See which method for verification and which way to provide context is most reliable.

What the paper changes

What the paper changes

The paper adds a verification wrapper—a pluggable layer that intercepts each agent's output before passing it to the next agent. Instead of blindly accepting what the agent produces, the wrapper asks a verifier: how confident are you in this step? If confidence is low, the wrapper can request a retry or branch to an alternative. The wrapper is the new piece; the verifier itself (LLM-as-Judge or a reward model) can be any existing evaluator.

The hidden quantity

The hidden quantity: Verification Consistency

measured quantity  =  verification reliability across contexts

The paper measures something not obvious in the abstract: whether the verifier gives stable, correct judgments when agents only see partial context. In single-agent reasoning, the verifier has the full history—problem, all background information (the prior steps), and the current step. In multi-agent systems, context is fragmented. Agent C does not know what Agent A whispered to Agent B. The verifier must judge C's contribution with only pieces of the picture. How often does this partial view cause the verifier to flag a correct step as bad (a false alarm) or miss a coordination error (a miss)?

The paper estimates this by running the same problem multiple times with different context strategies: (a) current step alone, (b) summarized history plus current step, (c) full history plus step, etc. If the verifier were reliable, all strategies would rank the same steps as good or bad consistently. But they don't. A step looks good with full context and bad with summarized context. This reveals that the verifier's confidence depends heavily on which pieces of context the system feeds it, not on whether the step is truly sound.

Why it works

Why it fails: The coordination gap

Single-agent step verification works because the step lives in a complete narrative. The verifier sees problem, all prior steps, and the new step. It can judge: does this step move us forward or off the rails? In multi-agent systems, each step is an island. Agent B's output is influenced by Agent A's context (which B did not produce), and Agent B's output will shape Agent C's options (which B cannot foresee). The verifier, trained on single-agent math problems, looks at Agent B's contribution in isolation. It sees: "This output is grammatically coherent and mentions a relevant concept." It says: good. But Agent C later realizes the output was too vague, or contradicted something Agent A said. The verifier missed the failure mode because it could not see the downstream impact.

Second, each agent has different reliability profiles. A verifier trained on math-step checking has learned what makes a math step sound (correct arithmetic, logical flow). But Agent B in a debate system is not solving math; it is summarizing what another agent said, or finding a counterargument. The verifier's training does not transfer. A reward model trained on single-agent reasoning trajectories encounters a different statistical distribution in multi-agent handoffs. It mispredicts. Adding more context helps sometimes (the verifier can see more clues), but hurts other times (context saturation—so much information that the verifier loses focus). This is why the paper found that the best context strategy varies by architecture: Debate prefers full context; DyLAN (a different coordination strategy) prefers summarized context. No verifier sees the full picture consistently.

Math after the picture

The scoring equation

First in words:

For each agent output, score equals the verifier's confidence times a scaling factor that decays with how much context is missing from the verifier's view.

Then the compact form:

score = confidence(step) * decay(context_missing_ratio)

Every symbol:

confidence(step)the verifier's judgment: how good is this step on a scale of 0-1
decay(...)how much to reduce the score when the verifier sees only partial context
context_missing_ratiofraction of full history not shown to the verifier (0 = full context, 1 = step-only)
A tiny worked example
Agent B's output: 'Given that constraint, we should prioritize speed.' Full context shown to verifier: 1.0 (100% of history). Verifier's confidence: 0.8. Score = 0.8 * decay(0.0) = 0.8 * 1.0 = 0.8. Verifier trusts it.
Same output, only the step shown to verifier: context shown = 0.2 (20% of history). Verifier's confidence on step-only: still 0.8 (same output). Score = 0.8 * decay(0.8) = 0.8 * 0.5 = 0.4. Verifier becomes unsure.
The step's true quality did not change. The verifier's judgment swung from 80% to 40% confidence just because context was hidden. This inconsistency is why multi-agent verification is unreliable.

The equation shows that the verifier's verdict depends not only on the step itself but on how much of the hidden coordination problem the verifier is shown.

What can go wrong

What can go wrong

Context saturation. Giving the verifier the full history of a long multi-agent conversation can overwhelm it because the verifier can only keep a limited amount of text in mind, making it focus on recent noise instead of important early facts. The verifier loses focus and makes erratic judgments. Summarizing helps by filtering signal, but human-written summaries introduce new errors when they miss nuances the verifier would have caught in the raw text.
Verifier mismatch. A reward model trained on single-agent math steps sees multi-agent outputs as out-of-distribution. It mispredicts because its training data and deployment data are different worlds.
High variance in outcomes. The same system configuration produces wildly different results across runs (e.g., 73% +/- 12% accuracy). This happens because the verifier's judgments depend on the random order in which agents generate proposals, and which proposals it sees, so some runs get lucky (verifier picks the right branch) and others don't. The variance is so large that it drowns out any signal—a 1-point accuracy gain could just be luck, not proof that verification helped.
Done right. Using an LLM-as-Judge instead of a reward model helps because LLMs can reason about partial information and make fewer systematic mistakes. Fine-tuning the judge on multi-agent examples helps because the trained judge sees the same kinds of outputs it will score in deployment. Tuning context strategy per architecture helps because each coordination method (debate, flow, search) requires different context to judge fairly. No single verifier can do all three, which is why the paper's main finding is honest: reliable multi-agent verification requires architecture-specific tuning.
What a runnable demo should prove

What a runnable demo should prove

Build a two-agent debate on a simple factual question: Agent A proposes an answer, Agent B critiques it. Run the system 20 times with no verification (baseline). Run it 20 times with a step-verification verifier. Use three context strategies: (a) only Agent B's critique, (b) Agent A's answer plus B's critique, (c) full transcript. For each strategy, measure: (1) How often does the verifier flag Agent B's critique as correct or incorrect? (2) When the verifier flags it as good, is the debate's final answer more often correct? (3) Does the variance across the 20 runs shrink or grow when verification is on? The demo succeeds if it shows that verification's judgment is unstable across the three context strategies—the same critique is marked good in one context and bad in another—revealing why the paper found no consistent benefit.

inconsistency = (number of critiques marked good with full context - marked good with summary only) / total critiques

If the inconsistency score is high (>0.2), the verifier is unreliable across contexts, proving that multi-agent verification requires architecture-specific tuning and cannot be applied blindly.
