Operator Theory-Driven Autoformulation of MDPs for Control of Queueing Systems

The paper turns queueing control descriptions into structured decision-process equations by building them from a small library of interpretable operators, because that shrinks the search space enough for automatic formulation to work.

Paper explainersAll themesAgents & Tool Use

Hospitals, call centers, and warehouses all face queueing decisions: which job should be served first, where should an arrival be routed, and when should a server switch tasks. These are sequential decisions, so they are usually modeled as Markov decision processes. Writing such a model by hand takes expertise because the state, actions, events, and Bellman equation must fit together correctly. This paper tries to automate that job. It represents the Bellman equation as a graph of interpretable operators tied to events such as arrival, service completion, or routing, then searches over that graph structure with language-model guidance and solver feedback.

Zero assumption version

Sequential decision models are much harder to autoformulate than one-shot problems

A one-shot optimization problem needs an objective and a set of constraints. A sequential problem needs much more: state variables, action choices, transition events, future value, and a policy that can depend on the current state. That larger structure makes automatic formulation difficult because the search space grows quickly.

Queueing systems are a good example. A short natural-language description may mention arrivals, service times, urgent-first service rules, and routing rules, but a solver cannot use those words directly. It needs a precise Bellman equation that captures how each event changes the value of each state.

Existing autoformulation work has focused mainly on static optimization. The paper addresses the sequential case by constraining the formulation search. It argues that many queueing-control MDPs can be expressed through a common operator-graph shape, which makes the automatic search manageable.

The bottleneck: MDP autoformulation fails when the search over possible equations is too large, so the paper reduces that search with a reusable operator graph.

The algorithm as a flow

What it actually does

Read the queueing description

The system extracts the entities, events, and control choices from the natural-language problem because those ingredients determine the eventual MDP.

Construct candidate operator graphs

Instead of writing a full Bellman equation at once, the method builds it from operators tied to events such as arrivals and departures, because that keeps each piece interpretable.

Use structured search

A customized Monte Carlo tree search explores graph candidates while using self-evaluation, syntax checks, and solver feedback so that weak partial formulations are pruned early.

Translate the graph into the Bellman equation

Once a graph is accepted, it becomes a full sequential decision model because the operators define how future value is updated under each event.

Infer policy structure

A low-complexity algorithm analyzes the formulated model to detect patterns such as threshold rules, which helps because these structures speed downstream solving and interpretation.

What the paper changes

What the paper changes

The paper changes the search space for MDP autoformulation. Instead of searching over arbitrary equations, it searches over a universal three-level graph of interpretable operators that can express a broad class of queueing-control Bellman equations.

the object it moves  =  Search space for sequential decision formulations
The hidden quantity

The hidden quantity: formulation structure

measured quantity  =  Operator-graph topology behind the Bellman equation

The final Bellman equation is the visible output, but the decisive quantity is the hidden structure that generated it. The paper claims that many queueing-control problems share a three-level operator topology. That topology determines which event updates can appear, how they compose, and where the decision rule enters.

Why does this matter? Because the difficulty of autoformulation comes from combinatorial explosion. If the system must search over arbitrary algebra, the number of candidate equations becomes unmanageable. If it can search over a small family of structured operator graphs, the problem becomes tractable.

This hidden topology also supports interpretation. Each operator corresponds to a concrete queueing event, so a human can inspect the graph and understand why the resulting Bellman equation has a certain term. That matters because autoformulated models must still be trusted and checked.

Why it works

Why operator graphs make autoformulation practical

The paper works by separating two jobs that are often mixed together: discovering the decision structure and writing the final equation. The operator graph handles the first job. Each node or edge stands for an interpretable transformation of the value function under a specific event, such as an arrival or departure. Once that structure is found, the Bellman equation follows directly.

That separation helps because structure search is easier than raw equation search. A queueing-control problem does not need arbitrary algebraic forms. It needs a lawful combination of event updates and decision terms. By proving that many problems fit a common three-level topology, the paper rules out large parts of the search space before the search begins.

The search algorithm then becomes feasible. Monte Carlo tree search proposes graph fragments, self-evaluation and syntax checks reject malformed branches, and solver feedback rejects branches that do not behave like valid queueing-control models. The result is a formulation procedure that is both guided and checkable, which matters because sequential decision models can fail in subtle ways if one event term is missing or misordered.

Math after the picture

The Bellman view behind the graph

First in words:

The value of a state equals the best immediate reward plus the expected future value after the queueing event operators update the state.

Then the compact form:

V(s) = max_a [ r(s, a) + sum_e P(e | s, a) * O_e(V)(s, a) ]

Every symbol:

V(s)value of state s under the best policy
aavailable control action at state s
r(s, a)immediate reward or cost for taking action a in state s
ea possible event such as an arrival or service completion
P(e | s, a)probability of event e after taking action a in state s
O_e(V)(s, a)operator that updates future value under event e
A tiny worked example
Suppose one server can choose between queue A and queue B.
Serving queue A now gives immediate cost -1 and then either an arrival happens with probability 0.3 or a departure happens with probability 0.7.
The arrival operator may increase the next state's waiting load, while the departure operator may reduce it.
The Bellman equation compares the expected value of serving A with the expected value of serving B.
The paper's contribution is to build those operator terms automatically from the verbal problem description, because the event structure is represented explicitly in the graph.

The equation is standard. The paper's main advance is how the event operators and search structure are generated.

What can go wrong

What can go wrong

The natural-language description may omit a key event. If the problem statement leaves out a routing or service rule, the autoformulated MDP will be incomplete because the operator graph can only express what was extracted.
The universal topology may not cover every domain. The proof targets a broad queueing class, but unusual systems may violate the assumed event structure, so the graph family may need extension.
Solver feedback can favor locally plausible but globally wrong graphs. A partial formulation may pass syntax and produce usable numbers while still encoding the wrong control problem, so human review remains important.
Done right: the model becomes easier to verify. Because each operator maps to a named event, experts can inspect the generated formulation more easily than a free-form equation and catch missing terms before deployment.
What a runnable demo should prove

What a runnable demo should prove

Build a small benchmark of queueing-control problems described in plain language, such as single-server urgent-first service, routing between two queues, and admission control. For each problem, compare three outputs: the hand-written Bellman equation, an unstructured language-model formulation attempt, and the paper's operator-graph formulation. Check whether each formulation is syntactically valid, semantically correct, and able to recover the right policy pattern. The demo should show that the operator-graph system succeeds more often because its search is constrained by event structure.
