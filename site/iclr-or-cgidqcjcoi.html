WALT: Web Agents that Learn Tools

Instead of teaching a web agent to click every button by hand, recover the site's own high-level operations and let the agent call them directly.

Paper explainersAll themesAgents & Tool Use

Web agents often fail for a simple reason: they solve each task through low-level page actions that are fragile under layout changes. A person shopping on a site does not reason from first principles about every click target. The person uses the site's built-in functions: search, filter, sort, create, edit, post. WALT turns that observation into a system design. It reverse-engineers the site's hidden operations into callable tools and asks the agent to plan with those tools. This improves reliability because the tool maps to website functionality that was already meant to be stable across pages and sessions.

Zero assumption version

Why click-by-click web control breaks easily

A click-based agent must look at the page, decide where to click, type text into the right field, and keep doing that across many steps. Small page changes can break the whole chain. A button moves, a menu label changes, or a filter panel opens in a new place, and the agent loses track.

This is wasteful because the website already has structured operations underneath the page. Search boxes call search backends. Filter controls apply known query rules. Content forms create or update records through stable site logic. A low-level agent ignores that structure and keeps re-solving the same interaction problem over and over.

The paper's move in one sentence. Recover the website's own operations as explicit tools and let the agent call those tools instead of reconstructing every page interaction from scratch.

The algorithm as a flow

What it actually does

Inspect the website.

Analyze the site's visible controls and underlying behavior to identify repeatable operations.

Package operations as tools.

Turn search, filter, sort, posting, editing, and related site functions into callable actions with fixed inputs.

Let the agent plan with tools.

The agent chooses which site operation to call instead of deciding every low-level click.

Execute through the tool layer.

The tool carries out the needed page interactions or direct site logic behind the scenes.

Return structured results.

The agent receives clean outputs from each tool call and uses them for the next decision.

What changes

The hidden quantity

The hidden quantity: functional distance from the site

measured quantity  =  How far an action representation is from what the website actually supports

The paper's deeper target is functional distance: the gap between the actions the agent reasons about and the operations the website truly provides. Click-by-click control has a large gap because the agent thinks in page mechanics while the site works in operations such as search, filter, create, and update.

WALT shrinks that gap by mapping discovered site functions into explicit tools. When the reasoning units match the site's own logic, the agent has fewer chances to fail on surface layout details. The paper measures the result in higher success with fewer steps, because the agent spends less effort rediscovering interface mechanics and more effort choosing the right site operation.

Why it works

Why learned tools beat low-level page reasoning

A site's built-in operations already encode many low-level decisions. When you call a search operation, you do not need to rediscover which field to focus, which button to press, or how results are fetched. The site has already packaged that behavior. WALT captures that package and makes it available directly to the agent, which matters because one high-level call can replace many brittle page actions.

This reduces failure in two ways. First, it shortens action chains, which matters because fewer steps mean fewer opportunities for drift. Second, it anchors the agent to stable semantics instead of fragile layout cues. A search operation stays a search operation even when the button moves, so the plan survives page variation because it is expressed in the language of site functions rather than the language of pixels and clicks.

A tiny worked example
Suppose a baseline agent needs 18 page actions to find an item, filter results, and post a reply.
With WALT, the same task becomes search(query), filter(tag), and post(message).
That is 3 tool calls instead of 18 raw steps.
Compression = 18 / 3 = 6.
A shorter chain is easier to execute reliably because there are fewer points where the run can drift off course.

The gain comes from shifting work into stable site operations, because the tool wraps many brittle interface actions into one higher-level call.

What can go wrong

What can go wrong

Tool recovery misses an important function. If the site exposes a useful operation but WALT fails to capture it, the agent may still fall back to brittle low-level behavior for that part of the task.
Recovered tools are too narrow. A tool that only works for one page variant or one form schema will break as soon as the site broadens the operation. Good tools must reflect the real site function, not one accidental page instance.
The site changes its underlying logic. If the website rewrites how search or posting works, the recovered tool layer must be updated. Tool-based control is steadier than raw clicking, but it still depends on the site's true operations remaining consistent.
Done right. When the recovered tools match the website's genuine operations, web automation becomes more dependable because planning happens in a smaller and more stable action space.
What a runnable demo should prove

What a runnable demo should prove

Take a small marketplace or forum site and define tasks such as find an item, filter by attribute, sort by price, and post a message. Compare a click-based agent with a tool-based agent that has explicit search, filter, sort, and post operations. Then perturb the page layout without changing the underlying site functions. The tool-based agent should keep a higher success rate because its plan relies on site operations rather than fragile page arrangement.

layout_robustness = success_after_layout_change / success_before_layout_change

The result should make clear that the agent wins by reasoning in the website's own action language.
