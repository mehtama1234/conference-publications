ToolTree: Efficient LLM Tool Planning via Dual-Feedback Monte Carlo Tree Search

LLM agents make better tool choices by looking ahead and pruning bad paths before wasting computation on them.

Paper explainersAll themesAgents & Tool Use

An LLM agent facing a multi-step task—like booking a flight, then querying prices, then updating a calendar—needs to plan which tools to use in order. Today's agents pick greedily (pick the best tool right now) or search randomly through options. ToolTree does something smarter: it sketches out branches of possible tool sequences, prunes the weak-looking ones before executing them, then uses real execution results to fix its understanding. The payoff: agents spend less time exploring dead ends and more time on promising paths.

Zero assumption version

Why greedy and pure search both fail

Today's LLM agents pick tools in two broken ways. Greedy agents ask at each step: what tool looks best right now? They pick it immediately. The trap: an early mistake—picking a tool that looked promising but dead-ends three steps in—means the agent wastes the rest of its compute following a ruined path. No recovery, no lookahead.

Search-based agents try to fix this by exploring many branches at once. But they have their own trap: they rank branches by predicting future success without actually running the tools. They guess. A branch might look terrible on paper but amazing in reality once you execute the first tool and see the actual result. By the time they realize a path worked, it is too late to credit the early choice that made it possible.

The core trap: Agents either stumble forward blindly, or they plan ahead but plan wrong because they are guessing instead of seeing real results.

The algorithm as a flow

What it actually does

Scout

Fast model checks each potential tool choice for basic fit (right data type, right schema). Filters out obvious mismatches.

Expand

For survivors, expand a branch in the search tree (add that tool to the sequence).

Execute

Run the surviving tool, see the real output, not a guess.

Score

Use actual result to measure whether this branch path is working (post-execution reward).

Prune

Kill branches with low post-score before wasting compute, because real execution reveals which paths actually work.

What the paper changes

What the paper changes

ToolTree changes how an agent allocates its computation budget across candidate tool sequences. Instead of assigning equal weight to all branches or trusting guesses, it leans on two signals: a lightweight pre-check (does this tool fit the data?), then real post-execution feedback (did this actually move us closer to the goal?). This dual signal lets the agent steer budget toward branches that are both plausible and actually working.

the object it moves  =  computation budget allocation
The hidden quantity

The hidden quantity: Path Credibility Score

measured quantity  =  Path credibility (pre-check + real execution payoff)

Greedy agents and guessing searchers do not track the credibility of a tool sequence over time. ToolTree introduces a score that combines two sources: a pre-execution credibility (does this tool schema match the task?), and a post-execution payoff (did the real tool output move us closer to success?). This score is updated each time a tool is actually run, not guessed about.

The paper estimates this score by running the LLM twice per branch: once before expansion (schema check), once after execution (outcome check). The post-execution check is the key innovation—it grounded ranking in reality, not prediction.

Why it works

Why dual-stage pruning makes agents smarter

The core mechanism has two moving parts: the pre-execution pruning and the post-execution pruning.

Pre-execution pruning works because an LLM can very quickly check whether a tool call makes sense without actually running it. When a task asks to book a flight, the agent can instantly reject branches that try to call a weather API or a calendar API—obviously wrong schemas. This filtering happens before any tool is invoked, so it costs almost nothing but eliminates garbage branches.

Post-execution pruning is the stronger move, because after a tool actually runs, the agent sees real data instead of predictions. This is the moment to ask: did this work? If the tool returned an error, or the data looks wrong for the next step, or the task moved backward, the agent knows immediately and can stop wasting compute on that branch. It does not wait three more steps to discover the path is dead. It prunes now and reallocates budget to surviving branches. This is credit assignment that is grounded in reality, not speculation.

Why does this beat pure search? Pure search must predict whether a branch is worth exploring without running any tools. It ranks branches on guess alone. ToolTree collects real execution results as it goes, so by the time the agent chooses which branch to expand next, it has actual evidence, not a forecast. Early paths that looked bad on paper but worked in reality are immediately upgraded; paths that looked good but failed are immediately downgraded. The agent spends its finite compute budget on the paths that real execution has proven to be working.

The scoring formula

First in words:

Total branch value is the sum of a pre-execution schema credibility and a post-execution task-progress reward, each weighted by their importance.

Then the compact form:

V(path) = alpha * S_pre(path) + beta * R_post(path)

Every symbol:

V(path)total credibility score for a tool sequence
alphaweight given to pre-execution schema checking (how much to trust the fast check)
S_pre(path)schema fit score before execution: how well does the tool call match the task requirement
betaweight given to post-execution feedback (how much to trust real results)
R_post(path)reward from actually running the tool: does the real output move toward the goal
A tiny worked example
Branch A: calls weather API on a flight-booking task. S_pre = 0.2 (schema mismatch), R_post = 0 (never executes due to pre-pruning). V(A) = 0.6 * 0.2 + 0.4 * 0 = 0.12. Pre-check kills it.
Branch B: calls correct flight API but with wrong date. S_pre = 0.9 (good schema), R_post = 0.3 (tool runs but returns wrong results). V(B) = 0.6 * 0.9 + 0.4 * 0.3 = 0.54 + 0.12 = 0.66.
Branch C: calls flight API with correct date. S_pre = 0.95, R_post = 0.9 (tool works, data progresses task). V(C) = 0.6 * 0.95 + 0.4 * 0.9 = 0.57 + 0.36 = 0.93. C gets the most budget next.
Pre-score filters obviously wrong tool calls without executing. Post-score credits paths that actually deliver real progress. Budget flows to C.

The two weights (alpha, beta) control whether to trust the fast pre-check or the slower real execution more. In practice, post-execution reward (beta) is higher because it is grounded in reality.

What can go wrong

What can go wrong

Pre-check too strict. If the schema validation is too eager to prune, it rejects branches that would have worked because it does not have real execution data to verify them, only fast pattern-matching. The agent misses valid paths. Trade off strictness: tighter filtering saves compute by skipping expansions, but may miss solutions that the fast check incorrectly flagged as impossible.
Post-execution reward misaligned. If the scoring function does not correctly measure task progress (e.g., it gives high score for a tool that ran successfully but moved the task backward), the agent will steer budget toward false paths. The reward signal must be grounded in the actual task goal.
Budget exhaustion. If the agent is severely compute-constrained (only a few tool calls allowed), pre-pruning might filter too aggressively, leaving no high-credibility branches to explore. The balance between pre-checking and exploration matters.
Done right. Set alpha and beta to give real execution results (beta) more weight than fast checks (alpha), because real data is more trustworthy than pattern-matching. Use a task-specific reward signal, not a generic one, because generic scores do not know what the task actually needs. Allow at least one full expansion pass before aggressive pruning, because the agent needs initial data to ground its pruning decisions.
What a runnable demo should prove

What a runnable demo should prove

A proof-of-concept demo should show three agents (greedy, pure search, ToolTree) solving a multi-step tool use task with a fixed compute budget (e.g., 32 tool calls allowed). The demo should track: (1) how many branches each agent explores, (2) which branches are pruned and when, (3) the final task success rate, and (4) the accuracy-per-compute metric (success rate divided by number of tool calls spent). The demo proves ToolTree's win: same or better success on the same budget by eliminating wasted exploration.

efficiency = (task_success_rate) / (tool_calls_spent)

ToolTree should show higher success rate (same or better) while spending fewer tool calls, or equivalently, the same success with lower compute budget, because pre-pruning and real-data steering eliminate wasted exploration on dead-end branches.
