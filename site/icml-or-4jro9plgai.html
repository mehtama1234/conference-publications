CaP-X: Code-as-Policy Agents for Robot Manipulation

A framework that reveals code-writing agents for robots depend on designer scaffolding but can reach human-level performance through repeated planning, visual feedback, and ensemble voting without retraining.

Paper explainersAll themesRobotics & Control

Language models can write robot control programs by composing low-level commands into high-level actions. But do these code-writing agents actually know robotics, or do they just follow hand-designed templates? CaP-X is a benchmark and open environment that exposes this gap and shows a path forward: letting agents think through problems step-by-step with feedback, visual clues, and multiple attempts, without any retraining.

Zero assumption version

Can the agent really solve it, or just follow the template?

A robot needs to pick up a block and place it. A language model (a text-predicting system trained on internet text) can write programs like: move arm down, open gripper, move arm up. The program looks sensible. But here is the question: does the model understand the task, or is it just pattern-matching examples it saw in training data?

Naive approach: give the model low-level commands (move 5 cm, rotate 30 degrees, close gripper with force X) and ask it to compose them. This often fails because the model has to invent the exact numbers and timing without feedback. A beginner trying this would write the wrong forces or sequences and the robot would drop the block. The model does the same thing—it has no way to correct itself mid-attempt.

The core problem. Language models work well when they can write code, but models degrade dramatically when given low-level primitive commands instead of high-level templates, and no feedback on whether their choices work.

The algorithm as a flow

What it actually does

Step 1: Set up the benchmark

Build a test environment (CaP-Gym) where agents write and run robot programs, and measure how many manipulation tasks succeed or fail.

Step 2: Compare models across abstraction levels

Run 12 different language models; some get high-level commands (pick, place), others get raw numbers. Measure success rates and expose the gap.

Step 3: Add interaction and feedback

Let the agent see pictures of what went wrong and rewrite the program; run multiple independent attempts.

Step 4: Combine the attempts

Ensemble the plans: run all of them and pick which one succeeds most, or blend their advice.

Step 5: Test on real robots

Show that the improved agent works in reality, not just simulation, confirming the method transfers.

What the paper changes

The single thing that changes

The paper does not change the model itself (no retraining). Instead it changes how the agent uses its capabilities: instead of writing one program and running it blindly, the agent now writes, observes, re-plans, and tries again—multiple times. The core finding is that the model already knows how to correct mistakes if you show it what went wrong.

The hidden quantity

The hidden quantity: Task completion reliability

measured quantity  =  Success rate across low-level primitives

The paper measures one key quantity: the percentage of manipulation tasks the agent completes correctly when given only raw, low-level commands (move distance X, rotate angle Y, apply force Z). This reveals whether the model truly understands manipulation or merely follows designer templates.

The paper estimates this by running each model and abstraction level on a standardized benchmark of 12 models across multiple task families. It compares: (a) success with high-level abstractions, (b) success with raw primitives, (c) success after adding multi-turn feedback and visual cues. The gap between (a) and (b) shows dependence on scaffolding; the gap between (b) and (c) shows how much test-time computation recovers.

Why it works

Why test-time interaction works

A language model trained on code learns patterns from text but does not run code itself or see consequences. When asked to invent raw numbers, it guesses. But if shown an image of the failure (robot arm moving the wrong direction, gripper too weak), the model can reinterpret its mistakes in the same way a human programmer reads error messages and revises. Each cycle of write-run-observe-rewrite narrows the gap between what the model predicted and what the physics requires.

Visual differencing works by showing the model the before-and-after difference (e.g., block stayed in place instead of moving), and the model immediately spots what went wrong and adjusts. Multiple independent attempts reduce the risk of one unlucky guess: if three different plans are written and executed, and two succeed while one fails, the model (or a simple majority vote) picks the working one. The model never learns (weights stay frozen) because the internal settings controlling the model's predictions are not updated; instead, each cycle gives the model fresh evidence of success or failure, letting it apply the same knowledge in new ways.

Math after the picture

The reliability equation

First in words:

Final success rate = base success rate × (1 + feedback improvement factor) × (1 + ensemble diversity factor)

Then the compact form:

P_success = P_base × (1 + α × n_turns) × (1 + β × (1 - correlation(attempts)))

Every symbol:

P_successprobability the final attempt succeeds on the target task
P_baseprobability a single cold attempt succeeds without feedback
n_turnsnumber of re-planning cycles the agent gets
αfeedback gain per turn (how much each observation improves the next plan)
correlation(attempts)how similar the independent attempts are; 1 means identical, 0 means completely different
βensemble gain per unit of diversity
A tiny worked example
Setup: a model writing raw commands has P_base = 30% (3 out of 10 attempts succeed by luck).
With 2 feedback turns (agent sees what went wrong and rewrites): α = 0.25 per turn, so (1 + 0.25 × 2) = 1.5.
With 3 independent attempts (voting picks the best): if they are uncorrelated, correlation ≈ 0, so (1 + 0.8 × 1.0) = 1.8.
Final: 0.30 × 1.5 × 1.8 = 0.81 = 81% success, even though each individual attempt is still only ~30%.
The interaction (feedback) and diversity (ensemble) both multiply together, not add, because independent chances compound.

This model shows why multiple weak hints (feedback, visual cues, retry attempts) combine to reach near-human reliability without retraining the model.

What can go wrong

What can go wrong

One bad plan ruins the ensemble. If the agent writes 3 plans and 2 are wildly different, a simple majority vote is unreliable. The paper addresses this by using ensemble methods that filter out plans that violate physics constraints and rank the rest by confidence.
Feedback can be misleading. If the robot's camera is blurry or the task fails for a reason outside the model's control (e.g. a broken gripper), visual differencing sends the model on a wild goose chase. The model rewrites the code to fix imaginary problems.
Limited primitive vocabulary. If the low-level command set does not include the right tool (e.g. 'grasp with variable force' but the primitives only allow 'full force'), no amount of interaction will help, because the model can only compose what exists—it cannot invent new commands. The agent is fundamentally constrained by the set of primitives the designer provided.
Sim-to-real transfer breaks assumptions. Simulation assumes physics that real robots violate (friction, cable lag, sensor noise). A plan that works in simulation may fail on the real robot even if it is well-reasoned because the environment changed.
Done right: clear primitives + honest physics model + real robot testing. When the primitives have clear names and behavior (open_gripper, move_to_position, apply_force_range), the physics simulation is accurate, and the agent tests on real hardware, the method reaches near-human performance.
What a runnable demo should prove

What a runnable demo should prove

Implement a minimal robot task (e.g. pick a colored block from a shelf and place it in a bin, in simulation first). Measure two things: (1) a baseline model writing one plan from scratch with no feedback (raw success %), (2) the same model writing up to 5 attempts, each one shown an image of the prior failure and allowed to rewrite the program. Do NOT retrain the model; just add the interaction loop. The demo should make it obvious that interaction alone lifts performance without learning.

Improvement = (accuracy_with_feedback_and_ensemble) - (accuracy_one_cold_attempt)

The point the demo must make impossible to miss: a frozen language model that looks completely broken (28% success) becomes nearly competent (78–82% success) when given visual feedback, multiple chances to revise, and a simple majority vote across attempts.
