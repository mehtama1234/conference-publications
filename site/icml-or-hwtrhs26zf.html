CAPTCHA Solving for Native GUI Agents: Automated Reasoning-Action Data Generation and Self-Corrective Training

Train a GUI agent to solve interactive CAPTCHA tasks by generating large numbers of reasoning-and-action traces and then teaching the agent to recover from its own mistakes.

Paper explainersAll themesAgents & Tool Use

A native GUI agent reads screenshots and clicks directly on the screen. That works reasonably well for ordinary digital tasks, but CAPTCHA tasks remain hard because they often require several careful actions, visual checks, and error recovery steps. This paper builds a dedicated training pipeline for that setting. It generates many CAPTCHA trajectories, keeps reasoning traces with the actions, and turns failed runs into self-correction lessons so that the agent learns to recover instead of freezing after the first mistake.

Zero assumption version

Why GUI agents still fail on CAPTCHA tasks

Modern GUI agents can navigate menus, forms, and routine web tasks by looking at screenshots and issuing clicks or typed text. CAPTCHA tasks are different. They often require tight coordination between visual understanding and action timing, and a single mistake can send the agent down a bad path that must be recognized and repaired.

Generic GUI training data does not teach that behavior well because many ordinary tasks do not need repeated checking or recovery after failure. Specialized CAPTCHA tools can solve narrow challenge types, but they usually do not transfer to general GUI work. That leaves a gap where end-to-end GUI agents remain weak exactly where interfaces become adversarial and multi-step.

The paper's move in one sentence. Generate large-scale CAPTCHA interaction traces with reasoning steps, then train on both successful runs and repaired failures so that a general GUI agent learns multi-step solving and self-correction.

The algorithm as a flow

What it actually does

Build a dynamic CAPTCHA environment

Create several representative challenge types so that training covers different visual and interaction patterns.

Collect reasoning-and-action traces

Automatically generate large numbers of screenshot, reasoning, and action sequences for the agent to learn from.

Keep failures instead of discarding them

Mine failed trajectories to find places where the agent must notice a mistake and change course.

Train self-corrective behavior

Add supervision that teaches the agent to reflect on recent actions and pick a repair step.

Evaluate on CAPTCHA and general GUI tasks

Check that the agent improves on challenging verification tasks because the new training data teaches recovery behavior, while preserving ordinary interface skill by keeping the native GUI setup unchanged.

What the paper changes

What the paper changes

The paper changes the training data and training target for a GUI agent. It adds multi-step CAPTCHA traces and explicit repair behavior so that the agent learns how to continue after an intermediate mistake.

the object it moves  =  How a GUI agent is trained to reason through failure and recovery
The hidden quantity

Future usefulness of the next action

measured quantity  =  Recovery-aware action value

The central hidden quantity is whether the next action keeps the agent on a path that can still be completed. On a hard interface challenge, an action is not good only because it matches the present screenshot. It is good when it moves the task toward completion and leaves room to recover if something goes wrong.

The paper estimates this quantity by recording whole trajectories rather than isolated clicks. Failed runs are especially informative because they reveal which actions looked locally plausible but led to dead ends, and which later repair steps pulled the run back toward success.

Paper reading. Trajectory-level supervision and self-correction data give the agent signals about which action sequences remain salvageable, not just which single action looks plausible at one screen state.
Why it works

Why data generation plus self-correction works

Automated trajectory generation helps because CAPTCHA tasks have many small interface variations, and a fixed hand-built dataset would cover too little of that space. Large-scale traces expose the agent to the sequence structure of solving, not just to the end state.

Self-correction helps because many failures are recoverable. If the agent is trained only on perfect demonstrations, it learns little about what to do after a mistake. Training on repaired failures teaches the agent to inspect the changed screen, infer what went wrong, and choose a repair step so that the run can continue instead of restarting blindly.

Math after the picture

A simplified trajectory objective

First in words:

Train the agent to maximize successful completion while adding value for repair moves that turn a failed prefix into a recoverable path.

Then the compact form:

trajectory_score = success_reward + alpha * repair_gain - beta * repeated_error_rate ; loss = - average(trajectory_score over training runs)

Every symbol:

trajectory_scoretotal value of one GUI interaction run
success_rewardvalue for completing the CAPTCHA correctly
repair_gainvalue added when a repair step improves a failed or risky run
repeated_error_ratehow often the agent repeats a bad action pattern
alphaweight on useful repair behavior
betapenalty on repeating the same mistake
losstraining objective minimized by the model
A tiny worked example
Run A solves the challenge directly: success_reward = 1.0, repair_gain = 0.0, repeated_error_rate = 0.0.
With alpha = 0.4 and beta = 0.5, trajectory_score_A = 1.0.
Run B makes one wrong click, then notices the reset and recovers: success_reward = 1.0, repair_gain = 0.6, repeated_error_rate = 0.0.
trajectory_score_B = 1.0 + 0.4 * 0.6 = 1.24.
Run C makes the same wrong click three times and fails: success_reward = 0.0, repair_gain = 0.0, repeated_error_rate = 0.8.
trajectory_score_C = 0.0 - 0.5 * 0.8 = -0.4.
The training rule prefers B over A when recovery skill matters because B teaches the agent how to rescue a noisy run.

The real training setup is richer than this summary, but the simplified objective captures the core lesson: reward completion and reward effective recovery, while penalizing repeated errors.

What can go wrong

What can go wrong

Synthetic coverage can be too narrow. If the generated challenge set misses real-world interaction patterns, the agent may learn a brittle routine because training did not expose the missing cases.
Repair traces can teach the wrong lesson. If a failure label is noisy, the model may over-trust a bad repair action because the recorded correction was itself weak.
Shortcut strategies may appear. The agent can exploit surface regularities in the training environment if challenge generation is too predictable, so evaluation on held-out variants still matters.
Done right. Diversify challenge generation, validate repair traces carefully, and test on unseen interface variants so that the learned recovery behavior transfers beyond the training set.
What a runnable demo should prove

What a runnable demo should prove

Build a small browser-based CAPTCHA environment with several challenge types such as image selection, sequence clicking, and drag interaction. Log screenshot states, action histories, and task completion. Train one agent on successful demonstrations only and one agent on the same data plus repaired failures. Compare solve rate, average number of repeated mistakes, and recovery rate after the first error.

The demo should prove that self-correction data matters because the better agent can continue after a wrong move, and that large-scale trajectory generation matters because the agent handles more than one narrow challenge style.

recovery_rate = solved_after_first_error / runs_with_first_error ; repeat_error_fraction = repeated_bad_actions / total_actions

A convincing demo shows higher solve rate and better recovery after mistakes because the training data contains full trajectories and explicit repair behavior.
