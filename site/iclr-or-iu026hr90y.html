ScaleZero: One Model for All Tasks with Mixture-of-Experts and Dynamic Scaling

A single world model learns all tasks efficiently by routing each task to specialized sub-networks and growing the model only when needed.

Paper explainersAll themesReinforcement Learning

In the real world, robots and agents face dozens of different jobs with different rules, inputs, and rewards. A naive approach tries to teach one giant brain everything at once—but the gradients (nudges to move the numbers) from different tasks pull in opposite directions, like tug-of-war, and the model forgets old tasks while learning new ones. ScaleZero solves this by putting task-specific "routers" in front of specialized sub-networks, so each task talks to only the experts that matter to it, and then strategically grows the model only when one task gets stuck.

Zero assumption version

One brain, many jobs—and they fight

A robot faces Atari games (press buttons, watch pixels), robotics tasks (move arms, read joint sensors), and text adventures (read text, type commands). Each is a different world with different inputs and outputs. A naive approach: train one giant neural network (a brain with millions of numbers) on all of them at once. During training, the network adjusts its numbers based on errors from Atari, then errors from robotics, then errors from text—each adjustment pulls the shared numbers in conflicting directions.

This creates two problems. First, gradient conflict: when the network learns to play one game perfectly, the nudge to do well at the next game moves the shared numbers backward, undoing the first win. It is like trying to walk toward two people pulling you in opposite directions. Second, when you keep teaching new tasks, the shared numbers shift so much that the model forgets how to do the old tasks. The shared "memory" erodes because there is no way to protect the numbers that matter to old tasks without blocking the new learning.

The core problem. A single neural network trained on many different tasks with different inputs, outputs, and rules suffers from conflicting training nudges (gradient conflicts) that block learning, and forgets old tasks as it learns new ones (loss of plasticity).

The algorithm as a flow

What it actually does

Router per layer

Each layer of the network includes a small router that reads the current state and decides which expert to send it to.

Experts handle their tasks

Experts are specialized sub-networks; Atari expert learns pixels to actions, robotics learns joint angles to torques, text learns one word to the next.

Shared backbone saves space

Early layers (pixel-to-features) are shared; experts branch off where tasks truly differ to avoid redundancy.

Detect when a task stalls

Monitor whether one task's progress plateaus; if so, task is stuck in a local valley and cannot escape with shared weights alone.

Attach LoRA adapter dynamically

A LoRA adapter is a tiny add-on (2-5% of model size) that plugs into the expert for that task, giving it private capacity to adapt without rewriting the full model.

What the paper changes

What the paper changes

ScaleZero changes two things: (1) the architecture—from one shared network to a routed mixture-of-experts that splits tasks into separate sub-networks, and (2) the training process—by watching for tasks that get stuck and attaching tiny LoRA adapters (low-rank add-ons) on the fly. The core object being moved is the routing decision and the model's capacity allocation (where the network stores learned information).

the object it moves  =  routing + capacity allocation
The hidden quantity

The hidden quantity: gradient alignment per task

measured quantity  =  gradient alignment

Gradient alignment measures whether the nudges to learn one task point in the same direction as nudges from another task. When alignment is high (nudges point together), learning is smooth. When alignment is low (nudges point opposite), one task blocks the other. The paper theoretically shows that the mixture-of-experts architecture increases alignment by sending each task to its own expert, because each expert's numbers are updated only by that task's errors, eliminating the cross-task tug-of-war.

The paper estimates alignment indirectly by measuring sample efficiency: if more tasks can learn with fewer training interactions, alignment improved. They also track whether adding a new task still lets the model improve old tasks (model plasticity). High plasticity means the shared backbone has not calcified in ways that block new tasks, because each expert is isolated, so moving an expert's numbers for one task does not freeze the shared early layers that other tasks rely on.

Why it works

Why routing and dynamic scaling fix the problem

The mixture-of-experts router works because it isolates gradient updates. When training on Atari, only Expert 1 (the Atari expert) gets nudged by Atari errors. When training on robotics, only Expert 2 gets nudged by robotics errors. Because each expert is only pulled by one task, there is no tug-of-war, and the nudges do not cancel out. The shared early layers still learn general features (like edge detection in vision), but task-specific branches stay independent. This is why gradient alignment improves.

Dynamic Parameter Scaling (DPS) handles the second problem: forgetting. When a task runs out of progress (the expert is stuck in a local valley and cannot improve further), attaching a LoRA adapter gives that task a small private network to explore new paths without rewriting the main expert, because the LoRA adapter is low-rank—it is a tiny linear transformation (like a thin layer) that adds on top of the expert, using only 2–5% extra parameters. This preserves the main expert's learned knowledge while giving the stuck task room to maneuver. When the adapter stabilizes, it becomes part of the model, and the next task can attach its own adapter if needed.

Together, routing prevents conflict during learning, and dynamic scaling prevents forgetting and capacity ceiling. The result is one model that genuinely adapts to each task's unique challenge without the single-network bottleneck.

Math after the picture

The routing and penalty equations

First in words:

expert_index = argmax_i(router_score_i) then loss_total = sum_tasks(loss_task + lambda * adapter_penalty_task) where adapter_penalty grows if a task's adapter deviates too much from the main expert

Then the compact form:

expert_idx = argmax_i(router(state, task_id)_i); loss = sum_t ( L_t(expert[expert_idx_t](state)) + lambda_t * ||LoRA_adapter_t||^2 )

Every symbol:

router(state, task_id)_iscore for expert i, computed from current state and task identity
argmax_ipick the expert with the highest score
L_tloss (error) for task t
expert[idx_t](state)the selected expert processes the state
LoRA_adapter_tthe add-on parameters for task t, added on top of the expert
lambda_tpenalty weight: how much to discourage large adapters (prevents overfitting to one task)
||LoRA_adapter_t||^2size of the adapter (sum of its squares); larger adapters get higher penalty
A tiny worked example
Suppose Atari expert produces loss 0.8 on a frame, and the Atari adapter has size 0.3. lambda_Atari is set to 0.01 (weak penalty).
Task loss = 0.8, adapter penalty = 0.01 * (0.3)^2 = 0.01 * 0.09 = 0.0009. Total = 0.8 + 0.0009 = 0.8009.
If we grew the adapter to size 0.7, penalty becomes 0.01 * (0.7)^2 = 0.01 * 0.49 = 0.0049. Total = 0.8 + 0.0049 = 0.8049.
Small increase in penalty discourages unnecessary growth; the model attaches adapters only when truly needed to escape a plateau.

The router picks an expert by scoring each one; the penalty term keeps adapters small so the model does not waste capacity on tiny task-specific tweaks.

What can go wrong

What can go wrong

Router collapse. If the router always picks the same expert regardless of task, the mixture degenerates into a single network and gradient conflicts return. This happens if the router is undertrained (too simple) or task signals are too weak. Fix: ensure the router is trained as carefully as the experts, and use task-ID as an explicit signal.
LoRA adapter overgrowth. If the penalty weight lambda is too small, adapters grow unbounded, consuming all available memory and negating the space savings. The model should grow only when truly stuck. Fix: tune lambda per task based on how constrained you want the adaptation to be.
Starvation of minority tasks. If the training schedule samples one task far more often than others, the router may learn to almost always pick the frequent task's expert, and rare tasks stop improving. Fix: balance sampling or use importance weighting so rare tasks get adequate router training.
Done right. With proper router initialization, stable lambda scheduling, and balanced task sampling, the mixture-of-experts architecture cleanly separates gradient flows, and dynamic scaling adds capacity only when task-specific optimization truly needs it. One model can then match specialized single-task agents.
What a runnable demo should prove

What a runnable demo should prove

Build a tiny multi-task environment: three gridworld tasks (Task A: reach goal in bottom-right; Task B: reach goal in top-left; Task C: collect objects without obstacles). Train a naive single-network agent on all three, track success rate on each. Then train a Mixture-of-Experts agent (same total parameters, split into three experts plus a router). Plot success curves for each task over 10,000 training steps. The demo must show that the MoE agent learns all three tasks to high accuracy without the single-network forgetting that occurs in the naive baseline. Measure sample efficiency: count how many total environment steps the single-network agent needs versus the MoE agent to reach 90% success on all tasks. Then demonstrate that attaching a single LoRA adapter to one expert (e.g., Task A's expert) in the final 2,000 steps lets it escape a plateau that the single expert alone could not overcome.

sample_efficiency_gain = (samples_naive - samples_ScaleZero) / samples_naive * 100%; success_without_forgetting = min(Atari_final, Robotics_final, Text_final); plateau_escape = (success_with_adapter - success_without_adapter)

The demo makes it impossible to miss that routing eliminates the cramped multitask bottleneck (high success on all three tasks simultaneously), because each task's gradients pull an isolated expert, not a shared network. It also proves that small LoRA adapters truly do let a stuck task escape a learning plateau, because adapters provide task-specific capacity outside the main expert's learned weights.
