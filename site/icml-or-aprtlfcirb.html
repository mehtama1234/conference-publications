FactGuard: Agentic Video Misinformation Detection via Reinforcement Learning

Instead of trusting a single pass through a video, FactGuard asks the model to actively hunt for evidence and fix its mistakes through repeated learning.

Paper explainersAll themesAgents & Tool Use

Video misinformation detection is hard: a video might claim something false, but the evidence might be scattered across frames, text overlays, and external sources. Existing models watch once and believe what they see. FactGuard instead treats the model like an investigator: it explicitly asks whether the task is ambiguous, sends the model to fetch outside information, and trains it to make better decisions by learning from mistakes.

Zero assumption version

Video claims need outside proof

Today's video fact-checkers are passive watchers. A multimodal model sees all frames at once, reads any text, and makes one final decision: true or false. The problem: a claim often needs outside confirmation. A video might say a building is in Berlin, but the model has to guess based only on what it sees. If the lighting is ambiguous or the building is unknown, the model has to trust its gut.

A beginner might try: feed the video and the claim to a large language model and hope it learns the right answer. But that breaks when evidence is fragmented (the claim relies on three separate frames), sparse (only one clue is visible), or external (the building really is in Berlin, but that fact is not in the video).

The method in one sentence. FactGuard lets the model actively decide when to hunt for external evidence, then trains it to make better hunting decisions through repeated practice, because learning which hunts actually fix mistakes teaches the model to distinguish real uncertainty from fake confidence.

The algorithm as a flow

What it actually does

Assess ambiguity

Model rates whether the claim is clear enough to decide from the video alone.

Decide to search or not

If ambiguous, the model decides which tool to call (web search, reverse image lookup).

Fetch evidence

External tools return facts, images, or context the video does not show.

Refine reasoning

Model re-examines its claim with the new evidence and updates its confidence.

Train on what worked

Learning algorithm rewards tool calls that led to correct answers and punishes wasted searches.

What the paper changes

The one thing that changes

The paper changes how the model decides whether to ask for help. Instead of the same decision rule for every claim, the model learns which queries truly need outside information and which tool calls actually fix its mistakes, because the reward signal explicitly penalizes wasted searches while bonusing correct answers that used tools, so only the hunting patterns that led to better answers survive.

the object it moves  =  tool-request decisions
The hidden quantity

Ambiguity: when the video is not enough

measured quantity  =  task ambiguity

Task ambiguity is a measure of how unclear the claim is based only on the video. Low ambiguity means the video contains obvious proof; high ambiguity means the evidence is scattered, vague, or missing. The paper does not use a simple formula—instead, the model learns what counts as ambiguous through examples. When the model sees claims it got wrong, it learns that those situations were actually ambiguous and should have triggered a tool search.

The paper estimates ambiguity by watching which tool calls led to correct answers. A tool call that changed a wrong answer to right signals: this claim was truly ambiguous. A wasted tool call (the answer did not change) signals: the model understood already and wasted a search.

Plain reading. Ambiguity is how much the video leaves you unsure. If the video shows a clear date stamp and the claim matches, ambiguity is low. If the claim requires knowing who a person is or where a building stands, but the video only shows faces or architecture, ambiguity is high.
Paper reading. The paper infers ambiguity from the trajectory: if a tool call switched the answer from wrong to correct, that instance was ambiguous and the model should learn to recognize it. If a tool call left the answer unchanged, the model already understood and should learn not to waste searches on it.
Why it works

Why repeated hunting and learning work

The core insight is this: a single pass through a video is not enough because the model has no way to know if it is missing something. By explicitly asking whether to search and learning which searches paid off, FactGuard solves two problems at once. First, it forces the model to articulate doubt instead of faking confidence. Second, it trains the model to recognize which doubts are real (the claim truly was ambiguous and a search fixed it) versus imaginary (the model misunderstood but a search did not help), because the training explicitly marks a doubt as real only if fixing it improved the final answer.

The mechanism works in two stages. In stage one, supervised fine-tuning teaches the model the basic task: given a video and a claim, decide if it is true or false. The model also learns to articulate its reasoning and to use tools when prompted. In stage two, reinforcement learning lets the model practice the full autonomy: it decides when to search, fetches evidence, and learns which decisions led to correct answers. The learning signal is sharp: if a tool call led to the right answer, reinforce that decision pattern; if it wasted effort, do not. Over time, the model calibrates its doubt and tool usage to the actual difficulty of the claim.

Math after the picture

The decision and learning rule

First in words:

reward equals 1 if the final answer is correct, minus a small cost for each tool call, minus extra cost if the tool call was wasted

Then the compact form:

R = (1 if answer_final == answer_correct else 0) - alpha * num_tools - beta * num_wasted_tools

Every symbol:

Rthe total reward signal (higher is better)
answer_finalthe verdict the model outputs: true or false
answer_correctthe ground truth: true or false
alphathe cost per tool call (e.g. 0.05, to discourage lazy searching)
betathe extra penalty for a wasted tool call (e.g. 0.10, to punish bad judgment)
num_toolshow many external searches the model performed
num_wasted_toolshow many of those searches did not change the answer
A tiny worked example
Scenario A: model claims true, ground truth is true, uses 2 tools, but 1 was wasted.
Answer correct: yes, reward +1.0
Tool cost: 2 * 0.05 = 0.10
Wasted cost: 1 * 0.10 = 0.10
R = 1.0 - 0.10 - 0.10 = 0.80
Scenario B: model claims true, ground truth is true, uses 0 tools.
Answer correct: yes, reward +1.0
Tool cost: 0
Wasted cost: 0
R = 1.0
Scenario C: model claims true, ground truth is false, uses 3 tools, 2 were wasted.
Answer correct: no, reward 0
Tool cost: 3 * 0.05 = 0.15
Wasted cost: 2 * 0.10 = 0.20
R = 0 - 0.15 - 0.20 = -0.35
Takeaway: scenario A (0.80) rewards correct answers with some wasted searches (acceptable). Scenario B (1.0) rewards correct answers with no searching (best). Scenario C (-0.35) penalizes wrong answers heavily. The model learns to search only when it helps.

This penalty-based reward steers the model to hunt for evidence only when the hunt will actually matter for the final decision.

What can go wrong

What can go wrong

Tool result is itself false. If the external search returns misleading information (a corrupted database, a fake website), the model integrates false evidence and makes a wrong call. The reward signal punishes the wrong answer, but the training data itself is tainted.
Ambiguity signal is weak. If most claims in training are either crystal clear or crystal false, the model does not learn to distinguish tough middle cases. It either searches constantly or never, missing the calibration.
Tool calls are expensive. In real deployment, searching takes time and money. If the alpha and beta costs are not set correctly, the model either wastes resources or refuses to search even when it should.
Done right. The model learns to search only on genuinely ambiguous claims, integrates external results carefully, and weighs its internal reasoning against new evidence.
What a runnable demo should prove

What a runnable demo should prove

Build a tiny misinformation detection system on a curated set of 20 claims: 5 clear truths (obvious from the video), 5 clear falsehoods (contradicted visibly), 5 ambiguous truths (need external data), and 5 ambiguous falsehoods (plausible but externally false). Run two models: one that never searches and one trained with FactGuard. Measure both accuracy and tool usage.

accuracy = (correct_verdicts) / (total_claims); tool_efficiency = (accuracy_increase) / (tool_calls)

The demo makes impossible to miss: FactGuard's accuracy on ambiguous claims jumps far higher than a fixed model, and most of those tool calls were decisive (not wasted).
