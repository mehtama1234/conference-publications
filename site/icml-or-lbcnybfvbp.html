SWING: Unlocking Implicit Graph Representations for Graph Random Features

Instead of building the graph node-by-node, walk through the continuous space where the nodes sit, then linearize the walk logic via random features.

Paper explainersAll themesGraph & Geometric Learning

Graphs defined by feature similarity (like: use distance to connect points in a point cloud) are expensive—you need to compute the distance between every pair of points and build the whole graph before you can work with it. SWING trades that expensive material graph for a virtual one: it walks through the continuous space that holds the nodes, never materializing the graph at all. This lets modern accelerators (graphics chips) handle graphs of tens of thousands of points without building them first.

Zero assumption version

Why building similarity graphs is slow

Some graphs aren't given to you as a list of edges. Instead, they're defined by a rule: connect two nodes if their feature vectors (lists of numbers describing each node) are close enough, or weight the connection by how similar they are. Examples: a point cloud where points are connected by their 3D distance, or a protein dataset where proteins are connected by sequence similarity.

To apply graph algorithms to these graphs, you need to first compute every pairwise distance—scaling with the square of the number of nodes—and assemble the graph. Only then can you run random walks or apply kernel methods. That's expensive and wasteful: for graphs with tens of thousands of nodes, even storing a table of all pairwise connections becomes impossible.

A beginner might think: 'Just use graph neural networks—they can aggregate neighbors without building the graph.' But many algorithms (graph kernels, random-walk counting, differential equations on graphs) fundamentally need to know the walk probabilities or kernel values—they can't skip the construction step. That's where this paper steps in.

In one sentence. Conduct random walks directly in the continuous space where nodes sit, not on the discrete graph nodes.

The algorithm as a flow

What it actually does

Define the implicit graph rule

Specify how to compute edge weight from two nodes' feature vectors (e.g. Gaussian kernel of distance).

Sample a random walk in the embedding space

Start at node p, step through the space using weighted random transitions that respect node similarity.

Precompute random feature maps

At each step, evaluate two random feature functions (evolution features, load features) at the walker's current location.

Accumulate the load signal

Track how much each node contributes as the walker passes through, scaled by a decay function.

Compute the kernel action

Average over many random walks to approximate how the graph kernel transforms a given vector, in time proportional to node count, walk length, and walks per node.

What the paper changes

The one thing SWING changes

Instead of computing pairwise similarity and building an explicit adjacency matrix, SWING computes the same result—the action of the graph kernel on a vector—using random walks in the continuous embedding space. The object is the walk substrate: from discrete nodes to continuous space.

The hidden quantity

The load: how much each node influences the walk

measured quantity  =  load signal accumulated per node

As a random walker moves through the embedding space, it 'sees' different nodes depending on its location. The load is a measure of how much each node p contributes to the overall kernel computation: it captures which nodes the walk passes close to, scaled by how long the walk lingers near them. In discrete walks, the load is tracked explicitly by incrementing a counter each time a walker visits a node; in SWING's continuous space, the load is computed implicitly using the same random feature functions that define the walk transitions.

SWING estimates the load by precomputing random feature maps at each step. Because the walk happens in continuous space, you don't store one signature vector per node (which would use memory proportional to the square of node count); instead, you compute the kernel's action on any vector by evaluating the random features at the walker's trajectory and accumulating in linear memory.

Why it works

How SWING avoids building the graph

The core trick is to conduct walks in the continuous space (where the node feature vectors live) instead of on the discrete graph nodes. When you step from one location to another in continuous space, you're implicitly stepping between nodes that are close: the random sampler picks the next step probabilities based on how each node's features would weight that transition. This is equivalent to stepping on the graph, but you never build the graph.

To make this fast, SWING precomputes two random feature maps: one for walk evolution (where the walker goes next) and one for load distribution (how much that location contributes to the accumulation). Random features are a way to turn expensive kernel computations into dot products of simpler vectors—a 'linearization' trick. Because you precompute these features for all nodes before the walk, each step costs only a dot product per walker, so the total cost grows linearly with the number of nodes and steps.

The load update is relaxed (made continuous) so that instead of storing one signature vector per node (which would require memory proportional to the square of node count), the paper proves that you can compute the kernel's action on any vector in linear time by using the precomputed random features. This is the central insight: the implicit walk gives you the same kernel matrix properties without ever materializing the graph or the signature vectors.

Math after the picture

The walk and load equations

First in words:

position_after_t_steps = evolve(current_position, random_feature_samples). load_contribution = decay_function(t) times load_features(current_position). kernel_approximation = average over m walks of accumulated load.

Then the compact form:

x_t+1 = Evolve(phi(x_t), phi(p), p). l_t = rho(t) * (1 - p_halt)^t. K*v ≈ average_m [ sum_t Normalize(psi(x_t), psi(p)) * (psi(p)^T * v) ]

Every symbol:

x_tlocation of the walker after t steps in the continuous embedding space
pthe starting node's feature vector
phi(x)random feature map for evolution: samples applied to position x
psi(x)random feature map for load: samples applied to position x
l_taccumulated load at step t
rho(t)decay function that scales the load with step count
p_haltprobability the walker stops at each step
K*vthe graph kernel matrix K multiplied by vector v
A tiny worked example: one walker, two steps
Start: walker at node p with feature vector [1, 0.5, 1.5] in 3D space.
Step 1: Gumbel-softmax samples give transition probabilities to nearby nodes. Walker moves to location x_1 = [1.1, 0.6, 1.4]. Load at step 1 is l_1 = rho(1) * (1 - 0.2)^1 = 1.0 * 0.8 = 0.8.
Step 2: Walker moves to x_2 = [1.0, 0.7, 1.3]. Load at step 2 is l_2 = rho(2) * (1 - 0.2)^2 = 1.0 * 0.64 = 0.64.
Total load is accumulated: 0.8 + 0.64 = 1.44 for this walk. Repeat with m=100 walks and average.

The key is that the random feature functions are precomputed, so each step costs only a simple calculation per walker, not a full graph lookup; the continuous-space walk never touches an explicit graph matrix.

What can go wrong

What can go wrong

Bias in Gumbel sampling. If the Gumbel-softmax temperature is too high, the walker's transitions become nearly uniform (equal probability to all nodes), losing the graph structure. Too low, and numerical issues arise. The paper handles this via careful normalization, but tuning is needed.
Walk length too short. If walks terminate too quickly (high p_halt), the load signal is weak and incomplete. Each node needs to be reached by enough walks to get a stable estimate. Sampling m walks per node is expensive if you set m too high.
Feature space mismatch. SWING assumes the continuous embedding space naturally respects the implicit graph rule. If the features are poorly scaled or the kernel is mismatched to the feature space, the walks won't align with the intended graph, giving wrong answers.
Done right. When the random feature dimension, walk length, and number of walks are tuned together, SWING recovers the original kernel matrix to high accuracy because more walks and longer paths give a better statistical estimate of how the graph kernels act. Meanwhile, memory grows linearly with the number of nodes instead of quadratically, because the algorithm stores only the current walker position and precomputed feature values, never the full matrix of pairwise similarities.
What a runnable demo should prove

What a runnable demo should prove

Build a 3D point cloud (say, 1000 random points in a sphere). Define an epsilon-neighborhood implicit graph (connect points within Euclidean distance 0.5). Run SWING to compute one row of the graph kernel matrix (the similarity signature of one node to all others). Also compute the true kernel by brute-force distance calculation. Measure how close SWING's result is (L2 distance between the approximate and true signatures). Run it on a single GPU or accelerator and time both methods. Show that SWING finishes in seconds while the naive method takes minutes.

accuracy = 1 - (L2_distance_SWING_vs_truth / L2_distance_zero_vs_truth). runtime_ratio = time_naive / time_SWING.

SWING should achieve over 95% accuracy while being 10 to 100 times faster than building the graph explicitly, proving that implicit walks genuinely replace graph materialization because the cost avoids the quadratic pairwise distance computation that dominates traditional methods.
