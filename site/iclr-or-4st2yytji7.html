LD-MoLE: Learnable Dynamic Routing for Mixture of LoRA Experts

Instead of deciding upfront how many expert adapters to activate per token, learn a separate small network that predicts the right number for each token, token by token, at each layer.

Paper explainersAll themesEfficiency & Systems

Large language models are too big to retrain efficiently. LoRA is a trick: instead of retraining millions of weights, you train tiny adapters on the side, one per task. A newer idea: mixture of LoRA experts, which trains multiple adapters and routes each token to the best ones. But today's routers use TopK: pick the top K adapters by score. The problem: you have to decide K upfront, and K is the same for every token and every layer. LD-MoLE fixes this. It learns a separate tiny network that predicts the exact number of adapters to use for each token at each layer—some tokens get 2, others get 8—and does it all in a way that lets the whole model learn end-to-end.

Zero assumption version

Today's routers freeze the expert count upfront

Imagine fine-tuning a large language model. You do not retrain all its weights—that costs too much. Instead, you add tiny trainable adapters (LoRA modules, each a small network bolted onto the side). A single adapter is weak, so you train many of them. Now each token arriving at a layer must pick which adapters to use. Old idea: hardcode a selector that always picks the top K. Pipe the token's embedding (a list of numbers representing that token) through a scoring function, rank the experts by score, and take the K with the highest scores. This works, but K is a knob: you guess how many experts each token needs, set K to the same number everywhere, and hope it fits all tokens and all layers equally. If K is too big, you waste computation on useless experts. If K is too small, tokens lack what they need.

The problem. TopK routers treat every token and every layer the same: same number of experts chosen, no adaptation.

The algorithm as a flow

What it actually does

Feed the token

A token's embedding arrives at a LoRA-mixture layer.

Predict K

A shared tiny MLP predicts how many adapters this token needs right now.

Score the experts

The router scores each adapter. It converts those scores into smooth weights (each weight between 0 and 1, all adding to 1).

Route to top experts

Take the top K by score. Send the token through those K adapters in parallel.

Blend results

Combine the adapter outputs using their smooth weights as multipliers.

What the paper changes

What the paper moves: the expert count per token

The paper changes the expert count from a fixed knob to a learned, token-specific number. Instead of always picking the top 8 adapters, the method learns to pick the top 3 for simple tokens and the top 8 for complex ones. This learned count changes from layer to layer and token to token. The routing now has one extra tiny network: a shared MLP that predicts a sparsity factor (a threshold number) for each token. That threshold determines how many experts route to this token right now.

the object it moves  =  expert count per token
The hidden quantity

The sparsity factor: controlling how many experts activate

measured quantity  =  sparsity factor (lambda)

The sparsity factor is a single number per token that controls the expert threshold. The paper predicts it with a tiny shared MLP given the token's embedding. Higher sparsity factor means more experts pass the threshold and activate; lower means fewer. The paper learns to set this factor differently for each token, each layer. It measures how many experts end up activated by counting, and adds a loss term that steers the sparsity factor toward values that give the target sparsity level (for example, activate exactly 4 experts when you want that target).

Why it works

Why learning the expert count fixes the problem

The paper solves TopK's rigidity by treating expert selection as a smooth optimization problem. Instead of a hard cutoff (pick exactly K), it uses a soft projection that turns scores into probabilities, and derives a closed-form solution that tells you exactly which experts to pick. This closed-form solution depends on a single threshold number: the sparsity factor. The paper then trains a tiny shared MLP to predict the sparsity factor for each token. Because the factor is just a number, the MLP trains end-to-end with gradient steps (small nudges to the MLP weights based on whether it predicted the right factor for that token). The model learns which factor value works best for each token at each layer. Tokens that need many experts get a high factor; tokens that need few get a low factor. This adaptation happens during training, learned from data, not guessed upfront.

The paper also adds a sparsity loss that steers the sparsity factor toward target values. If you want each token to use roughly 4 experts on average, the loss gently pushes the factor to values that produce that count. This stabilizes training and prevents collapse (a common failure where all tokens route to the same one or two experts).

Math after the picture

The routing equation with learned sparsity

First in words:

The router computes a score for each expert, then applies a smooth projection that depends on a sparsity threshold. The projection selects experts whose scores are above the threshold. The threshold is predicted by a small MLP from the token embedding. The loss term steers the threshold toward values that produce the target number of selected experts.

Then the compact form:

routing_weights(t) = softmax_projection(expert_scores(t); lambda(t))

What can go wrong

What can go wrong

Collapse to one expert. If the sparsity loss is too weak, all tokens learn to route to the same expert, wasting the mixture. The paper adds a load-balancing loss that penalizes this.
MLP overfits to training data. The sparsity-prediction MLP is tiny, but on small datasets it can memorize token patterns instead of learning general routing logic. Gentle steer such as adding dropout (randomly zeroing weights during training to force the network to learn without relying on any single weight) or L2 weight penalty (adding a cost for large weights, discouraging overfitting) helps because they force the MLP to use only the most important patterns, blocking memorization.
Extreme sparsity swings. If the sparsity loss weight is too high, lambda bounces wildly, and the router sends tokens to zero experts (no routing) or all experts (no sparsity). The paper tunes alpha and beta losses to balance this.
Done right. The paper uses three losses: language modeling loss (the real task), load-balancing loss (prevent collapse), and sparsity loss (steer toward target count). All three together keep the router stable and adaptive.
What a runnable demo should prove

What a runnable demo should prove

Build a tiny demo: a 3-layer MLP as the base model, 4 LoRA adapters, and LD-MoLE routing. Train it on a small classification task (for example, 2-class sentiment or MNIST digit). Measure the expert activation pattern (how many experts each token uses) as training progresses. Plot the per-token expert count over epochs. Show that early epochs show high variance (the MLP is learning), and by epoch 50, simple examples use 1-2 experts and complex examples use 3-4. Compare against fixed TopK (always 2 experts): LD-MoLE should reach the same or better accuracy on the training set and generalize better to a held-out test set, because it learned to allocate experts adaptively.

test_accuracy_ld_mole minus test_accuracy_topk2 should be positive; mean_expert_count_per_token_by_class should show simple class lower than complex class

The demo is successful if test accuracy improves (showing the learned routing actually solves the task better), and if the plot shows the model learning to route simple tokens to fewer experts—visible proof that the learned adaptation is real and not just an artifact, because if routing were random or useless, the pattern would not emerge.
