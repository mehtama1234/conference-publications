Zero assumption version

Why is it hard to notice when agents shift?

Today, agent systems are black boxes. You send them a question and get an answer back, but you cannot see their inner workings. If you run the same agent every week for a year, its answers might slowly drift—different tone, different reasoning style, different priorities—but you would notice only if you read every single response by hand.

A naive approach: save one snapshot of the agent's behavior (a few sample questions and answers), then every week ask the same questions again and compare. But agents are random (they add randomness on purpose). The same question asked twice might yield slightly different answers just by chance. You cannot tell signal from noise.

Even if you asked a thousand test questions, you still face a choice: How different is different enough to say the agent changed? If you pick a loose threshold, you'll see false alarms on random fluctuation. If you pick a strict one, you'll miss real shifts.

The paper's move in one sentence. Instead of comparing raw answers, map each agent into a geometric space where its location encodes its behavior, do this over time to see the trajectory, then use a rigorous statistical test to ask: is that trajectory consistent with random noise, or did the agent genuinely shift?

The algorithm as a flow

What it actually does

Step 1: Design test questions

Pick a diverse set of queries that probe different aspects of the agent's personality, reasoning, or domain knowledge.

Step 2: Query agents repeatedly

Send the same questions to all agents at regular intervals (weekly, daily, etc.).

Step 3: Embed responses into behavior space

Use a similarity-based method to convert answer patterns into a coordinate for each agent at each time point.

Step 4: Compute trajectories

Plot each agent's path through the space over time, seeing if and when it moves.

Step 5: Run hypothesis tests

Ask: Is this motion consistent with random fluctuation, or is it statistically significant change? Declare shifts when the test rejects randomness.

What the paper changes

The one thing the paper changes

Instead of looking at raw agent answers (text), the paper maps each agent to a point in a coordinate space based on the _pattern_ of its answers across a set of test queries. That geometric location is what moves over time.

the object it moves  =  Agent representation in behavior space
The hidden quantity

Behavioral distance over time

measured quantity  =  Agent trajectory & variance

The hidden quantity is how far each agent drifts from its starting position in the behavior space, and whether that drift is bigger than random jitter would predict. The paper calls this the agent's _trajectory_. Early snapshots place an agent at location A. Later snapshots place it at location B. The distance between A and B is the drift. But randomness also causes noise, so the paper measures: Is the drift large enough that random fluctuation would almost never cause it?

The paper estimates this using a kernel perspective space—a method that converts response patterns into coordinates—and then builds hypothesis tests that compare the observed drift against a null hypothesis of pure random noise.

Why it works

Why it works: the causal chain

The core insight: agent behavior lives in a high-dimensional space — a cloud of numbers encoding how the agent responds to queries. Two things can happen: the agent drifts through that space (real change), or it bounces randomly inside a small region (randomness). Separating signal from noise requires a model of what randomness looks like.

The paper's move: use a similarity-based method to build a low-dimensional map where agents sit as points. Then measure how far each agent travels between time snapshots. The farther it travels, the stronger the evidence for change. By comparing the observed travel distance against what pure randomness would cause, the paper computes how likely it is that the shift is real.

Why this works: A kernel is a mathematical tool for measuring similarity between two things (in this case, two sets of agent answers). By using it to embed agents into a space, the paper gets a fair and data-driven way to measure behavior. By running a statistical hypothesis test (comparing to randomness), the paper avoids crying wolf at every tiny jitter.

Math after the picture

The equation and a worked example

First in words:

The test statistic measures the squared distance the agent travels in kernel space at each time step, then asks whether that total distance is more than expected under pure randomness.

Then the compact form:

M_t = sum_{s=1}^{t} || phi(X_s) - phi(X_{s-1}) ||^2

Every symbol:

M_tcumulative squared drift up to time t
phi(X_s)kernel embedding of agent responses at time s
X_sthe set of responses from agent at time s
||..||^2squared distance in the kernel space
Tiny numeric example
Week 1: Agent answer set X1 maps to kernel point (2.0, 1.5).
Week 2: Agent answer set X2 maps to kernel point (2.1, 1.4). Distance = sqrt((2.1-2.0)^2 + (1.4-1.5)^2) = sqrt(0.01 + 0.01) = 0.14. Squared = 0.02.
Week 3: Agent answer set X3 maps to kernel point (3.2, 0.9). Distance = sqrt((3.2-2.1)^2 + (0.9-1.4)^2) = sqrt(1.21 + 0.25) = sqrt(1.46) = 1.21. Squared = 1.46.
Cumulative drift M_3 = 0.02 + 1.46 = 1.48. Under pure randomness, the expected cumulative drift might be 0.3. Since 1.48 >> 0.3, we reject randomness and declare that the agent changed.

The squared distances accumulate over time; a real behavioral shift pushes the agent far enough that the total drift outpaces what noise alone would cause.

What can go wrong

What can go wrong

Test questions are too narrow. If your test queries probe only one aspect of agent behavior (e.g., only political opinions, or only creative writing), you miss shifts in other dimensions. The method assumes your test set is diverse enough to catch all kinds of behavioral change.
The similarity method is mismatched to the data. Choosing the wrong similarity function (or wrong hyperparameters) can place agent responses so that similar behaviors land far apart in the coordinate space. This adds noise to the trajectory and reduces power to detect true shifts.
Real behavioral change is too gradual. If an agent drifts extremely slowly over months, random variance might drown it out on weekly samples. Detecting slow creep requires either more frequent sampling or longer observation.
Done right. With a well-designed test suite, an appropriate kernel, and a chosen confidence level that balances false alarms and missed detections, the method reliably flags genuine behavioral shifts and ignores random noise.
What a runnable demo should prove

What a runnable demo should prove

Create a simple simulated multi-agent system: a few agents that answer the same 20 test questions every week for 12 weeks. Midway through (week 6), programmatically change one agent's behavior (e.g., shift its response pattern in a measurable direction; perhaps it becomes more conservative, or more creative). Run the paper's method on this data. The method should detect the shift in the changed agent with high confidence (a low p-value or high test statistic), and report no significant shift in the other agents.

p_value for agent shift = P(observed drift | pure randomness). Low p (<0.05) = shift detected.

The test must show: detection of the real mid-stream behavioral change in one agent, while other agents register no change; and a clear separation of the test statistic between the agent that was modified and those that were not.
