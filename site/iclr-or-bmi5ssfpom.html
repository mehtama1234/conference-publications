DASH: Deterministic Attention Scheduling for High-Throughput LLM Training

By rescheduling the backward computation of attention into a smarter order, DASH keeps reproducibility without sacrificing speed.

Paper explainersAll themesEfficiency & Systems

Training large language models requires that every run produces identical results so researchers can diagnose problems and test changes reliably. But the attention mechanism (the part of the model that focuses on important tokens) has a reproducibility problem: computing the learning updates deterministically is about 37.9% slower than normal. DASH solves this by reordering the computation steps like a smart assembly line, getting back nearly all the speed without breaking reproducibility.

Zero assumption version

Reproducibility breaks the assembly line

When training large models on many GPUs simultaneously, it is critical that every run produces the exact same numerical results. This determinism lets researchers pinpoint bugs because if the numbers differ between runs, the researcher cannot tell whether a change actually worked or whether randomness is just adding noise, test whether a code change actually helps because only identical starting points reveal whether something improved, and verify that expensive training runs are not corrupted because random changes between runs would hide bit-flips or other silent errors. The attention mechanism is a circuit in the model that learns which tokens to focus on.

The naive approach to determinism is to serialize all the reductions (a reduction is when you combine partial results from many GPUs into one final answer). But serialization means the GPU sits idle waiting for one step to finish before starting the next. In FlashAttention-3, the fastest attention implementation today, turning on determinism causes the backward pass (the step that computes the learning updates for each weight) to lose up to 37.9% of its speed, because reduce operations cannot run in parallel.

The problem in one sentence. Deterministic learning updates require serial reductions, leaving GPU cores idle and wasting speed.

The algorithm as a flow

What it actually does

Step 1: Treat backward pass as a task graph.

Each attention learning-update computation is a node with dependencies; reduction steps must happen in order.

Step 2: Find the bottleneck (critical path).

Trace the longest chain of tasks that cannot overlap; this sets the minimum time.

Step 3: Descending query iteration.

Process query blocks in reverse order so dependency resolution happens earlier, shrinking idle time.

Step 4: Shift scheduling.

Reorder reduce tasks to let compute cores start work on the next step before the previous reduce finishes.

Step 5: Measure throughput on real GPUs.

On H800 GPUs, DASH achieves up to 28 percent speedup while maintaining bitwise determinism.

What the paper changes

The one thing that changes

The paper reorders the computation steps (compute vs. reduce operations) in the attention backward pass. It does not change what is computed, only when each operation runs relative to others. The GPU still serializes reductions for determinism, but by scheduling them smarter, the paper reduces idle time.

the object it moves  =  Computation scheduling order
The hidden quantity

Critical path length: the invisible bottleneck

measured quantity  =  Critical path length in the DAG

The hidden quantity is the critical path length: the longest chain of dependent tasks that must run one after the other. Because these tasks block each other, the overall time is the sum of their durations, and idle cores cannot help. If you can find a different schedule that shrinks this chain, you speed up the whole computation because the total time is now determined by a shorter sequence.

The paper estimates critical path length by modeling the deterministic attention backward pass as a directed acyclic graph (a task dependency graph). Each node is a compute or reduce operation, and edges show which operations must finish before the next one starts. The paper then searches for schedules that minimize this critical path, testing two strategies: Descending Q-Tile Iteration and Shift Scheduling.

Why it works

Why rescheduling fixes the slowdown

In deterministic mode, accumulating learning updates forces reductions to wait for each other. This creates gaps where GPU cores sit idle. The paper identifies two sources of this idle time: pipeline stalls (when the compute pipeline empties while waiting for a reduce to finish) and suboptimal ordering of reductions.

By reversing the order in which query blocks are processed (Descending Q-Tile Iteration), the paper ensures that dependency resolution happens earlier. This advances the point at which downstream tasks can start, shrinking the pipeline stall. For causal attention (where future tokens cannot see past context), this is especially effective because the reversed order aligns naturally with how learning updates flow backwards.

For full attention, Shift Scheduling reorders the reduce tasks themselves so that while the GPU is reducing one block of results, another block of compute can proceed without waiting. Because the critical path is now shorter, total time decreases even though the same work runs serially. The two strategies together recover nearly all the speed that determinism lost.

The scheduling equation

First in words:

Critical path length equals the sum of sequential compute durations plus reduce durations that cannot overlap. By reordering, we minimize this sum.

Then the compact form:

CriticalPath = sum of durations of tasks on the longest dependency chain

Every symbol:

CriticalPathMinimum time needed to run all sequential tasks (cannot be reduced by adding cores)
Compute phase C(i,j)Gradient computation for tile (i,j) on one GPU core
Reduce phase R(i,j)Deterministic reduction combining gradients across cores for tile (i,j)
Baseline orderProcess query tiles 0,1,2,... in sequence
Descending orderProcess query tiles ...,2,1,0 in reverse
A tiny worked example with 3 query blocks
Baseline order: C(0) 10ms, R(0) 5ms, C(1) 10ms, R(1) 5ms, C(2) 10ms, R(2) 5ms. Critical path = 10+5+10+5+10+5 = 45ms.
Descending order: Reverse to C(2), C(1), C(0). Scheduler moves R(2) to overlap with C(1). C(2) 10ms in parallel with R(3) from earlier 5ms, then R(2) 5ms overlaps with C(1) 10ms (R finishes at 5ms, C finishes at 10ms). Total: 10 + max(5,10) + max(5,10) + 5 = 10 + 10 + 10 + 5 = 35ms. Speedup: 45/35 = 1.28×.

The key is reordering so that waiting for a reduce step overlaps with the next compute step, eliminating gaps.

What can go wrong

What can go wrong

Limited by memory bandwidth. If the GPU is memory-bound (waiting for data, not compute), rescheduling does not help because the problem is fetching data from memory, not the order of operations. DASH works best when the bottleneck is scheduling, not data movement.
GPU architecture matters. Shift Scheduling is theoretically optimal but only realizes its full gain on GPUs with large register files or on-chip memory (like Blackwell). On current H800s, gains are partial because the low-level implementation is constrained by available registers.
Works only for attention. Other operations (matrix multiplies, normalization) do not pay the same determinism cost because their reductions parallelize better. DASH is specific to attention.
Done right. Descending Q-Tile Iteration and Shift Scheduling together recover 28 percent speedup on current hardware while maintaining bitwise determinism, advancing reproducible training at scale.
What a runnable demo should prove

What a runnable demo should prove

The demo should implement both strategies (Descending Q-Tile Iteration and Shift Scheduling) as a modified attention implementation or scheduler. Run the backward pass on a GPU with determinism enabled, measure the throughput in tokens-per-second, and compare against FlashAttention-3's deterministic baseline. Vary sequence length (512, 1024, 4096, 16384 tokens) and batch size to show that DASH maintains speedup across settings. Verify bitwise reproducibility by running the same backward pass twice and checking that learning updates are identical. Plot throughput on the y-axis, sequence length on the x-axis, with one line for baseline and one for DASH. The key metric is: how much of the 37.9% loss can DASH recover?

Throughput speedup = (DASH tokens per second) / (deterministic baseline tokens per second)

The demo makes clear that reproducible training does not require sacrificing speed; smart scheduling recovers most of it.
