Sample-efficient and Scalable Exploration in Continuous-Time RL

COMBRL learns to control systems described by smooth continuous equations by building probabilistic models that trade off earning rewards and reducing model doubt.

Paper explainersAll themesReinforcement Learning

Real-world systems evolve continuously in time, but most learning algorithms were built for discrete steps. COMBRL solves continuous-time control by pairing a probabilistic model (one that admits uncertainty) with a simple idea: in each episode, pick actions that maximize reward plus how much you will learn. This naturally shifts from exploration early on (when the model is wrong) to exploitation once the model is confident.

Zero assumption version

Discrete learning loops break with real systems

Most learning algorithms assume the world steps in lockstep: agent picks action, world updates once, agent sees the result. But physical systems (robots, engines, chemical reactors) evolve smoothly and continuously. Time doesn't pause for decisions.

A naive attempt: run a discrete algorithm faster, taking tiny steps. This fails immediately because you waste observations sampling at moments when the system barely changes, causing your updates to be based on near-identical states that teach the model nothing new, and because the standard learning guarantees no longer apply to continuous-time domains. The algorithm has no way to decide when to look or act, only how to act if you happen to look right now.

In one sentence. COMBRL learns a probabilistic model of continuous dynamics and balances earning reward with reducing model uncertainty.

The algorithm as a flow

What it actually does

Build a probabilistic model

Fit a model (Gaussian process or Bayesian neural network) that predicts both the system's next state and how confident the prediction is.

Make a confidence set

Draw all models that plausibly match the data collected so far. The set shrinks as evidence mounts.

Pick an optimistic model

From the confidence set, choose one that balances claiming high reward and high epistemic uncertainty.

Optimize policy under that model

Use standard trajectory optimization (soft actor-critic or improved sampling-based search over sequences) to find actions that maximize reward under the chosen model.

Collect data and update

Execute the policy, gather observations, and retrain the model. Repeat until convergence.

What the paper changes

The single thing the method changes

COMBRL changes how we pick which dynamics model to use when planning. Instead of picking the single best estimate (which ignores uncertainty) or jointly optimizing over all plausible models (computationally expensive), COMBRL picks a model that trades off claiming reward and claiming uncertainty, using a single knob that adjusts how much to value exploration versus reward.

the object it moves  =  the model selection rule
The hidden quantity

Model epistemic uncertainty

measured quantity  =  epistemic uncertainty (model doubt)

Epistemic uncertainty is how wrong the model might be on an unseen input. It is the opposite of confidence—the wider the gap between optimistic and pessimistic predictions, the higher the doubt. If the model predicts the pendulum swings to angle 45 degrees with high certainty (predictions cluster at 45), epistemic uncertainty is low. If it predicts 43 to 47 with equal plausibility, doubt is high.

COMBRL estimates this uncertainty using a probabilistic model (Gaussian process or Bayesian neural network) that outputs not a single prediction but a distribution—a mean and a spread. The spread is the epistemic uncertainty. High uncertainty in regions not yet explored encourages the algorithm to visit them.

Plain reading. The model admits it does not know. When the model has seen many examples of what happens when you nudge the system to the left, it is confident about leftward dynamics. When it has never tried moving right, the spread of its predictions widens to reflect that admitted ignorance.
Paper reading. Epistemic uncertainty is formalized as the variance or confidence interval of the learned model's predictions. COMBRL builds this via Gaussian processes (which naturally output a mean and variance) or Bayesian neural networks (which model distributions over weights). The uncertainty in regions of the input space not yet explored is high; the algorithm greedily picks actions that maximize the sum of reward and this uncertainty term.
Why it works

Why uncertainty-driven action selection works

Picking actions to reduce model doubt is not altruism—it directly improves the agent's future ability to earn reward. Early on, when the model is extremely uncertain about how the system responds, any action that shrinks that uncertainty is worth taking because a better model leads to better decisions. As the model improves and uncertainty shrinks, the reward term naturally dominates the objective, because the weight on uncertainty (lambda) decays over episodes, making the exploration term smaller and the reward term larger, so the agent shifts to exploiting what it has learned.

This trade-off happens automatically through the weighted sum. No manual decay schedule for exploration needed; the mathematics drives it. The confidence sets (the collection of plausible models) are built using statistical concentration inequalities (bounds that hold with high probability), so the algorithm is theoretically sound.

Math after the picture

The objective function

First in words:

maximize reward plus lambda times epistemic uncertainty, subject to the model being smooth

Then the compact form:

maximize J(pi, f_n) + lambda_n * U(f_n)

Every symbol:

J(pi, f_n)expected cumulative reward under policy pi and model f_n
lambda_nweight on exploration; high early, decays over episodes
U(f_n)epistemic uncertainty of model f_n (variance or confidence set radius)
f_nthe chosen continuous-time dynamics model (smooth ODE)
pithe policy (mapping from state to action)
A tiny worked example
Episode 1: model is very uncertain everywhere (U = 100). lambda_1 = 1.0. Objective = 50 reward + 1.0 * 100 uncertainty = 150.
An alternative action gives 30 reward but U = 5 for that choice. Objective = 30 + 100 = 130. The agent prefers the first action because uncertainty reduction matters.
Episode 100: model is tight, uncertainty shrank (U = 5). lambda_100 = 0.1. Same alternative: 30 reward + 0.1 * 5 = 30.5 versus 50 reward + 0.1 * 100 = 51. The agent now prefers reward; exploration penalty is negligible.

The lambda weight decays over episodes (auto-tuned by information theory or manual schedule), automatically shifting from explore-heavy to exploit-heavy.

What can go wrong

What can go wrong

Probabilistic model is brittle if underspecified. If the Gaussian process distance-measuring function (the function that decides which states are similar) or the Bayesian neural network's starting guess about what patterns to expect do not match the true dynamics, the model's uncertainty estimates can be overconfident (claiming certainty when wrong) or unnecessarily pessimistic. The algorithm then explores badly.
Scaling to high dimensions is hard. Gaussian processes scale quadratically in data size; Bayesian neural networks can be expensive to train. COMBRL sidesteps the original optimism-driven co-optimization (which is cubic) by using the single knob trade-off, but still needs the probabilistic model to be fast enough.
Lambda weight tuning can matter. If lambda decays too fast, the agent stops exploring before the model is good. If it decays too slow, the agent explores needlessly even when confident. The paper proposes an auto-tuning procedure based on information gain, but a manual schedule can still be fragile.
Done right. COMBRL works well when the probabilistic model class (e.g., a Gaussian process with the right distance function, or a Bayesian neural network with sensible weight distributions) has enough flexibility to represent the true dynamics, when the system has low random jitter in its responses, and when the lambda schedule (auto-tuned or otherwise) balances exploration and exploitation appropriately for the problem.
What a runnable demo should prove

What a runnable demo should prove

Build a simple continuous-time system (a damped pendulum or a one-dimensional robot actuator described by an ODE). Train COMBRL and a discrete-time baseline on the same task. Measure two things: (1) how many samples each algorithm needs to learn a policy achieving 90% of optimal reward, and (2) whether the learned model's uncertainty is smaller in regions the algorithm visited (it should be).

sample_efficiency = samples_baseline / samples_COMBRL; model_confidence_gain = avg_uncertainty_unvisited / avg_uncertainty_visited

The core proof: COMBRL should need fewer samples than the discrete baseline because it skips wasteful time steps and explores intelligently, and the uncertainty should visibly shrink in explored regions while staying high elsewhere.
