Fly-CL: Bio-Inspired Decorrelation for Fast Continual Learning

A fly-inspired method that removes tangled feature redundancy using simple math, making continual learning 10-40x faster without losing accuracy.

Paper explainersAll themesRepresentation & Self-Supervised Learning

Continual learning lets a model learn new tasks without forgetting old ones, using a frozen pretrained backbone to extract features. The problem: when you directly feed these pretrained features into a similarity matcher (finding which class each new example belongs to), the features are redundant and tangled—many features carry overlapping information. This tangles up the learning process, so you need expensive math to untangle it. Fly-CL copies a trick from fruit fly brains: a simple, biologically plausible decorrelation step that removes feature redundancy cheaply and quickly.

Zero assumption version

Pretrained features are tangled

When you train a model from scratch on multiple tasks, catastrophic forgetting happens: learning a new task erases knowledge of old tasks. One solution is to freeze the pretrained backbone (the already-learned feature extractor) and only update a small learned head on top. For each new task, you extract features and match them to class averages (prototypes) to decide which class each example belongs to.

But pretrained features have a hidden flaw: redundancy and multicollinearity. Imagine 100 features, but they all measure essentially the same thing, just noisy copies of each other. When features are tangled like this, the similarity-matching stage (finding the right prototype) becomes unreliable and noisy. Advanced methods fix this by decorrelating the features—removing redundancy—but they use expensive math: matrix inversions, singular decompositions, ridge regression with tuned hyperparameters. For real-time systems that need to learn from new data quickly, these costs become prohibitive.

The naive approach Feed pretrained features directly to a similarity matcher, expecting it to work. But redundancy makes it slow and noise-prone, because when 100 features all carry overlapping information, the matcher struggles to find the true signal in the noise—each redundant feature adds confusion instead of clarity.

What the paper changes

The one thing the paper moves

Fly-CL changes how features enter the similarity matcher. Instead of using raw tangled features, it first runs them through a lightweight decorrelation filter inspired by fly olfactory biology. The filter is not a neural network layer; it is a simple math operation that removes redundancy without expensive matrix operations.

the object it moves  =  Feature decorrelation step
The hidden quantity

Feature redundancy (multicollinearity)

measured quantity  =  Feature redundancy / multicollinearity

Multicollinearity is a measure of how much your features overlap or repeat each other. Imagine you have 100 sensors, but 90 of them measure the same thing with different noise. That is extreme multicollinearity. In pretrained models, many features are near-copies of each other.

Fly-CL estimates redundancy implicitly by fitting a simple ridge classifier (a regression model that gently resists large weights) during training. As the model learns, this classifier naturally pushes the feature space toward independence—features that were redundant get projected into different directions. The paper proves theoretically that this streaming ridge approach progressively resolves multicollinearity, and experiments confirm that features become more independent after decorrelation.

Why it works

Why it works: the decorrelation pipeline

When a batch of features arrives, the decorrelation step solves a small ridge regression problem: fit a linear predictor of class labels using the features, but gently penalize large weights (so the model does not overfit). This gentle penalty biases the regression toward finding directions in feature-space where different classes point different ways—inherently independent signals, because a weight-penalizing algorithm is forced to make do with fewer, more focused directions rather than piling up redundant copies.

The ridiculously clever part: you do not need to invert a matrix. Instead, Fly-CL uses a streaming update (Generalized Cross-Validation or GCV) that updates the regression online as new tasks arrive. Each update slightly reorients the feature space to maximize class separability while minimizing redundancy. After a few tasks, the feature space is decorrelated—each feature now carries signal for the task at hand, not noise or duplication. Similarity matching then becomes crisp and fast, because the prototypes are no longer muddied by tangled redundancy. When the finished model answers a new question (prediction time), it just needs a simple dot product between cleaned features and prototypes.

Math after the picture

The ridge classification equation

First in words:

Regularized least squares, minimize squared class-prediction error plus a penalty on feature weight magnitude

Then the compact form:

loss = sum_i (y_i - w dot x_i)^2 + lambda * sum_j w_j^2

Every symbol:

y_itrue class label of example i (1 for target class, 0 for others)
x_ifeature vector (list of 768 numbers) for example i
w_jweight for feature j in the linear predictor
lambdaregularization strength; higher lambda penalizes large weights, pushes toward simpler solutions
sum_j w_j^2total magnitude of all weights; high magnitude means overfitting
Tiny worked example
Suppose 2 classes, 3 features per example. Example from class 1: features [4, 4, 1]. Example from class 2: features [1, 1, 4]. Learned weights (via ridge): w = [2, 2, -3].
Class 1 prediction: 2*4 + 2*4 + (-3)*1 = 8 + 8 - 3 = 13 (close to true label 1, scaled by strength).
Class 2 prediction: 2*1 + 2*1 + (-3)*4 = 2 + 2 - 12 = -8 (opposite sign, good).
Ridge penalty if lambda=0.1: 0.1 * (2^2 + 2^2 + (-3)^2) = 0.1 * (4 + 4 + 9) = 1.7. Without penalty, weights might grow to [10, 10, -30], causing overfitting.

The regularization weight lambda acts like a damper: weak lambda (loose damper) lets features become tangled and overfit; strong lambda (stiff damper) keeps features simple and independent. Fly-CL tunes lambda automatically using GCV.

What can go wrong

What can go wrong

Penalty-weight tuned wrong If lambda (the penalty strength) is too weak, features stay tangled and learning is noisy. If lambda is too strong, the model oversimplifies and loses task-specific signal. The paper uses GCV to auto-tune lambda, but GCV itself can be slow on some datasets. If you hardcode a fixed lambda, the method may fail on datasets very different from training.
Pretrained backbone is bad for the task Fly-CL assumes the frozen pretrained model already extracts useful features for your new tasks. If the pretraining domain is very different (e.g., pretrained on indoor scenes, testing on medical images), even perfect decorrelation cannot create signal that was not there. Feature quality bottlenecks the method.
Catastrophic forgetting still happens in the classifier head Fly-CL protects the pretrained backbone by keeping it frozen, but the classifier head (the ridge weights) is updated for each new task. If tasks are very similar, the head might overfit to the newest task and forget old classes. The paper runs continual learning experiments where this is tested and found manageable, but it is not magic.
Done right: GCV-tuned lambda, diverse pretrained model, careful task scheduling When lambda is auto-tuned (so the penalty is right for the data), the backbone is frozen (so features stay aligned), and tasks are scheduled reasonably (not 1000 identical tasks which would overfit the head), Fly-CL achieves 10-40x speedup with same or higher accuracy because decorrelation removes noise without needing expensive matrix operations, and fewer noisy updates mean faster convergence per task.
What a runnable demo should prove

What a runnable demo should prove

Build a continual learning setup: start with a pretrained ViT or ResNet-50, freeze it, and run it on CIFAR-100 or CUB-200 dataset with task boundaries (e.g., 10 tasks, 10 classes each). For each task, measure (1) training time, (2) post-extraction time (time after features are cached), and (3) accuracy on all seen classes. Compare Fly-CL decorrelation against two baselines: a naive direct similarity matcher (no decorrelation), and a full matrix-inversion method (slow but accurate). The demo should show that Fly-CL matches or beats the expensive method while being 10-40x faster because streaming ridge avoids matrix inversion and online GCV tuning avoids batch recomputation—hence smaller constant factors on each task.

speedup = baseline_time / flyc_time; accuracy_delta = flyc_accuracy - baseline_accuracy

The irrefutable signal: Fly-CL trains a fresh task in <10 seconds while the expensive baseline takes >100 seconds, and both achieve >90% accuracy on all past classes.
