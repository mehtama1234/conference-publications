Threat2Traffic: Multi-Agent Environment Synthesis for Malware Traffic Generation from Threat Intelligence

The paper turns threat reports into executable malware environments by extracting the exact conditions a sample needs, building those conditions automatically, and validating the result before running the malware.

Paper explainersAll themesOther

Malware traffic data is valuable because defenders need realistic examples of command-and-control messages, downloads, and beacon patterns to train detectors. Real malware traffic is hard to collect at scale. Old public datasets are outdated, and generic sandboxes often fail because many malware samples activate only when specific services, files, credentials, domains, or timing conditions are present. Threat2Traffic treats threat-intelligence reports as a source of those missing requirements. It uses several language-model agents to read evidence, infer what the malware needs, synthesize a tailored environment, and check that the resulting setup is internally consistent before executing the sample.

Zero assumption version

Why malware does not reveal itself in a generic sandbox

A malware sample does not produce useful traffic merely because it is executed. Many samples check their environment first. They may need a reachable command server, a specific operating-system service, a registry key, a mutex name, an installed application, or a realistic user context. If those conditions are absent, the sample may stay quiet, terminate, or follow a harmless branch. A one-size-fits-all sandbox misses this sample-specific setup.

Human analysts often reconstruct these dependencies by reading reverse-engineering notes or threat reports and then hand-building a custom environment. That process is slow and hard to scale. The technical challenge is not only extracting facts from prose. The system must separate direct evidence from speculation, resolve contradictions across sources, and turn text descriptions into concrete environment objects that can actually be deployed.

The bottleneck. You do not get realistic malware traffic unless the execution environment satisfies the sample's own preconditions.

The algorithm as a flow

What it actually does

Read threat intelligence as evidence.

Parse reports, notes, and indicators into candidate dependency statements because the raw text itself cannot be executed.

Use multi-agent deliberation.

Let several agents propose, challenge, and reconcile dependency claims so that ambiguous phrasing is less likely to become a mistaken environment requirement.

Assemble an evidence graph.

Store each dependency with its supporting passages and relations to other dependencies, which means later synthesis can reason about consistency instead of relying on one flat list.

Synthesize a tailored environment.

Generate configuration artifacts such as hosts, services, files, and network conditions that satisfy the extracted requirements.

Validate before execution.

Check both syntax and semantics so the generated environment is not only well-formed but also compatible with the malware's expected behavior.

What the paper changes

What the paper changes

The paper changes the way malware-analysis environments are created. Instead of launching every sample inside the same generic sandbox, it builds one environment per sample from documented behavioral requirements.

The hidden quantity

The hidden quantity

measured quantity  =  the minimal set of environmental dependencies that trigger malicious behavior

The main quantity is not the entire content of the threat report. It is the subset of conditions that the malware actually checks or relies on before revealing its network behavior. Some details in a report are descriptive background. Others are operational preconditions. The system must recover the second group.

Threat2Traffic represents this quantity with an evidence graph so that each dependency claim has provenance and relations to other claims. That structure matters because environment synthesis must know not only that a domain or service is mentioned, but also whether it is mandatory, optional, or conditional on another artifact.

Why it works

Why the multi-agent evidence-to-environment pipeline works

The pipeline helps because the task has two separate failure modes. The first is reading failure: threat reports are incomplete, noisy, and ambiguous, so a single pass can confuse observed behavior with required preconditions. Multi-agent deliberation reduces that risk because one agent can propose a dependency while another checks whether the supporting text actually justifies it. The evidence graph then preserves those justifications so later stages can inspect them.

The second failure mode is synthesis failure. Even a correct list of dependencies is not enough unless it can be turned into a runnable environment. Invariant-guided synthesis helps because it constrains generation with rules the environment must satisfy, such as valid host relationships, reachable services, or compatibility between configuration choices. Dual-layer validation matters because a generated file may be syntactically correct but behaviorally useless. The semantic validation step asks whether the combined environment is likely to satisfy the malware's real execution path.

Math after the picture

Choose the environment that satisfies the most evidence-backed constraints

First in words:

Score a candidate environment by how many required dependencies it satisfies minus penalties for unsupported or inconsistent configuration choices.

Then the compact form:

score(E) = sum_i w_i * satisfy(E, d_i) - lambda * inconsistency(E)

Every symbol:

Ea candidate synthesized environment
d_ithe i-th extracted dependency claim
w_ithe importance or confidence weight for dependency d_i
satisfy(E, d_i)an indicator that the environment fulfills that dependency
inconsistency(E)a penalty for conflicting or invalid configuration choices
score(E)the quantity the synthesis process tries to maximize
A tiny worked example
Suppose the malware needs one reachable domain, one registry key, and one running service.
Candidate environment A satisfies all three but adds one conflicting network rule.
Candidate environment B satisfies only the domain and registry key, with no conflicts.
If all three dependencies have weight 1 and the conflict penalty weight is 1, A gets 3 minus 1, which is 2.
B gets 2 minus 0, which is also 2.
A later semantic check can then break the tie by preferring the environment whose full behavior path is more plausible.

The exact implementation is more elaborate than this toy score, but the logic is the same: synthesis should reward satisfying supported dependencies and punish contradictions.

What can go wrong

What can go wrong

Threat reports may omit a required dependency. If the source documents never mention a required file, service, or timing condition, the system cannot synthesize it from evidence alone, so the malware may still remain dormant.
Evidence graph errors can cascade into synthesis. A mistaken claim that survives deliberation can become a hard environment constraint, which means the synthesis stage may faithfully build the wrong world.
Semantic validation is still a proxy. A generated environment can pass structural checks and still fail to trigger the intended malware branch because real malicious behavior may depend on factors the proxy validator does not observe.
Done right. The method works when threat intelligence contains enough operational detail and the validation stage catches contradictions, because then the synthesized environment is close enough to the malware's expected setting to trigger its network behavior.
What a runnable demo should prove

What a runnable demo should prove

Build a contained toy version with benign samples that activate only when specific environment conditions are met, such as a reachable domain, a local file, and a named service. Write short threat-style reports that describe those dependencies with some ambiguity. Then compare a generic sandbox, a single-agent extractor, and the full multi-agent evidence-graph pipeline.

The demo should show two things separately: extraction quality and traffic yield. That split matters because a system can produce plausible dependency lists while still failing to synthesize a runnable environment.

reproduction_rate = triggered_samples / total_samples

A convincing result shows that more samples reveal their network behavior only after the environment is tailored from evidence-backed dependencies.
