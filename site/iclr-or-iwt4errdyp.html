InfGen: Scenario Generation as Next Token Group Prediction

Represent all traffic elements as a sequence of tokens and use a transformer to generate realistic long-horizon driving scenarios one step at a time.

Paper explainersAll themesRobotics & Control

Training autonomous vehicles needs realistic traffic scenarios, but today's simulators start from static snapshots and can only replay recorded data. This paper proposes SceneStreamer (called InfGen in the title): a framework that builds a scene step-by-step, continuously adding new agents and letting traffic lights change, much like watching a real street unfold. Because every part of the scene is written as a discrete token (a label plus some numbers), a standard transformer model can learn to predict the next token from what came before—enabling infinite-length scenarios with diverse, realistic behaviors.

Zero assumption version

Why existing traffic simulators feel fake

Autonomous vehicles need to train on millions of realistic traffic scenarios. Most simulation software today works in two modes: either it fixes all the agents (other cars, pedestrians) at the start and only lets them run a pre-made trajectory, or it replays a recording of one real street interaction over and over. Both hit a wall—you can only test a few fixed situations, and the model never learns what happens when something unexpected arrives mid-scenario, like a new car entering the scene.

A beginner might try to train a separate 'next agent arrival' model alongside the traffic simulator, but that splits the problem into pieces. The arrival model and the motion model drift out of sync, motion predictions ignore what is actually happening (closed-loop), and you end up with unrealistic agent interactions and scenes that feel jerky or repeat.

The core insight in one sentence. Treat every part of traffic—agents, lights, motion—as discrete tokens and let a transformer predict the next token. This unifies scene generation and keeps it grounded in what is actually happening at each moment.

The algorithm as a flow

What it actually does

Static map encoding

Feed the road layout (intersections, lanes) once; the transformer remembers it.

Traffic light generation

At each moment, predict which lights turn green, yellow, or red.

Agent state generation

For each active agent, predict its position and heading.

Motion-command generation

For each agent, predict acceleration and steering; feed through physics to get the next position.

New agent injection

If a new agent should enter the scene, insert its token; transformer naturally continues from that point.

What the paper changes

What the paper changes

Instead of generating all agents' full trajectories at once (as a big vector), the method generates one token at a time in a causal order: lights first, then each agent's position, then that agent's motion command. This ordered generation means each prediction can see what just happened and adjust accordingly.

the object it moves  =  Token generation order and grouping
The hidden quantity

The hidden quantity: semantic causality

measured quantity  =  Order-respecting look-ahead rules

The paper measures whether each token's prediction respects physical and semantic causality: Does the agent's next motion depend on its current state? Does the agent's state depend on where the map is? This is enforced via grouped causal attention masks—rules that prevent the transformer from looking 'backward' into future steps or sideways into unrelated token types.

The paper encodes this by partitioning the transformer's attention into groups: (1) traffic light tokens can attend to map and prior lights, (2) agent state tokens can attend to map and lights, (3) motion tokens can attend to agent states. Each group's attention is masked with a causal rule: a token cannot see tokens that logically come after it. This ensures the model learns physically coherent behaviors rather than accidentally cheating by peeking into future actions.

Why it works

Why step-by-step token generation with causal grouping works

Here is the real causal chain: In the old approach, the model tries to predict all agents at once with no structure, so it has to learn to coordinate agents through a giant black-box neural function—a hard, messy problem. In SceneStreamer, the tokenization and grouped attention force a specific causality. The transformer is told: first generate lights (they are environmental, agents cannot change them), then generate each agent's next position and heading (these depend on the light state), then generate steering and acceleration commands (these depend on the position). By respecting this cascade, the model does not have to learn agent coordination from scratch; instead, it learns to predict motion conditioned on the current scene, which is a simpler, more stable problem.

When a new agent enters (injected at step t), it has no history yet, so its first state is sampled, but its motion is immediately constrained by the scene around it. The causal grouping ensures the new agent's motion attends to the current lights and other agents, not to undefined future states. This is why new agents integrate naturally—they obey the same causal rules as existing agents, just starting from step 0.

Math after the picture

The grouped attention equation

First in words:

attention_output = softmax(Q * transpose(K) / sqrt(d) + causal_mask) * V, where causal_mask sets future and out-of-group entries to negative infinity

Then the compact form:

Attn(Q, K, V, mask) = softmax((Q * K^T) / sqrt(d) + mask) * V

Every symbol:

QQuery: the current token asking for information
KKeys: prior tokens it is allowed to look at
VValues: the information in those prior tokens
dEmbedding dimension (number of features per token)
maskCausal matrix: negative infinity blocks future/invalid tokens
A tiny worked example
At step t, we generate an agent's motion token M_car1_t.
Q for M_car1_t has size 64 (embedding dimension d=64).
K is built from: agent state AS_car1_t (distance=0, allowed), traffic light TL_t (type=light, allowed), and all t+1 tokens (the causal mask blocks these, giving them huge negative scores).
Q * K^T / sqrt(64) produces raw scores, one per prior token. Before normalizing: (TL=0.3, AS_car1=0.6, future=-999).
softmax: (TL=0.2, AS_car1=0.7, future=0.0) after exp and normalize. The agent state gets 70% of the attention, lights get 20%, future is ignored.
Output = 0.7 * AS_car1_features + 0.2 * TL_features. The motion prediction is dominated by what the agent is actually doing now, modulated by light state, not contaminated by future steps.

The causal mask is the key mechanism: it allows each token to look only at prior steps and tokens of types that causally precede it (lights before agents, agents before motion) because if the model could see future steps or out-of-order tokens, it would learn meaningless correlations instead of the real causal structure, making policies trained in this sim crash in the real world.

What can go wrong

What can go wrong

Step-by-step error accumulation. If an early token (like a traffic light state) is predicted incorrectly, all downstream tokens (agents, motions) are conditioned on the wrong signal and compound the error. The paper mitigates this by forcing the first two time steps with ground truth during evaluation, then rolling out freely.
Causality mask misalignment. If the grouped attention mask is incorrect or too permissive, the model learns to cheat by peeking at future information, making the learned policy useless on real data with true causality.
New agents the model never trained on. When a new kind of agent (e.g., a motorcycle if the training data had only cars) enters mid-scenario, the model must predict its behavior without having seen it before. If the training examples are too narrow (only cars on highways), generated behaviors for motorcycles can be unrealistic or unsafe.
Done right: closed-loop training. The paper trains policies (via reinforcement learning) directly in the SceneStreamer environment, not on pre-generated scenarios. This ensures the policy learns to adapt to the actually-generated behaviors, not to one fixed set of replayed traffic patterns.
What a runnable demo should prove

What a runnable demo should prove

Build a minimal traffic scene: a 4-way intersection with 3 lanes per side, 2 traffic lights, and 4 parked cars initially. Use a pretrained SceneStreamer model or a small one trained on nuScenes. (1) Generate a 10-second scenario by feeding in the map tokens once, then rolling forward step-by-step, sampling the traffic light and agent tokens. (2) At step 5, inject a new agent (a pedestrian) at a random crossing point. (3) Run the output through a simple collision detector: count frame-by-frame whether any two agents overlap. (4) Repeat 20 times and average the collision count. (5) Compare to a baseline: random-walk agents with fixed lights. The demo succeeds if SceneStreamer produces zero or near-zero collisions while random baselines produce many.

collision_rate = num_overlaps / (num_steps * num_agents)
