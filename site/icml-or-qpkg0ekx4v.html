MemEvolve: Meta-Evolution of Agent Memory Systems

The paper evolves not only what an agent remembers but also how its memory system is built, so different tasks can end up with different memory rules, storage layouts, and retrieval behavior.

Paper explainersAll themesAgents & Tool Use

Many agent systems now improve over time by storing experience, but most of them keep the same memory design forever. That means the agent can add new facts and tools while still being stuck with a fixed way of encoding, storing, fetching, and pruning them. This paper treats the memory system itself as something that can evolve, because a task that needs compact procedural notes may want a very different memory design from a task that needs long evidence trails or reusable code fragments.

Zero assumption version

A fixed memory design cannot fit every agent task

An agent memory system has at least four jobs: write experience into memory, decide what form to store, fetch the right past item later, and clean up old material. Different tasks stress those jobs differently. Web search may need concise reusable snippets, while long tool workflows may need detailed traces with failure notes.

When one hand-designed memory architecture is used for every setting, the agent learns inside a narrow box. It can gather more experience, but it cannot change the memory rules that decide what gets kept and what gets resurfaced. That slows adaptation because a poor memory design keeps feeding the planner the wrong kind of support.

In one sentence. The memory contents can improve while the memory machinery stays wrong, so the paper evolves both together because a bad write or fetch rule can keep hiding the useful experience the agent already collected.

The algorithm as a flow

What it actually does

Define modular memory choices

Break memory design into parts such as write rule, storage form, fetch rule, and cleanup rule.

Sample candidate memory systems

Create different combinations of those parts so the agent can try multiple memory designs.

Run the agent on tasks

Evaluate each memory design by how well the agent solves tasks and how many interactions it spends.

Select and mutate the better designs

Keep memory systems that help the agent solve more with less effort, because those designs are task-matched.

Reuse the evolved design

Carry the stronger memory system into new runs and related tasks, because the search is trying to keep designs that surface useful support reliably.

What the paper changes

What the paper changes

The paper changes the optimization target from 'learn better contents inside a fixed memory box' to 'learn better contents and a better memory box at the same time.' The explicit object of search is the modular memory architecture itself, because the architecture decides which experiences are kept, how they are organized, and when they are returned to the planner.

the object it moves  =  modular memory architecture
The hidden quantity

The hidden quantity: memory-task fit

measured quantity  =  memory-task fit

Memory-task fit measures how well a particular memory design matches the structure of the task. A good fit means the memory writes the right level of detail, fetches the right past cases at the right time, and forgets material that would only distract the planner.

This is the quantity the paper is really chasing, because task performance rises when the memory system surfaces the right support with low interaction cost. The memory system itself is therefore treated as a variable to optimize, not as a fixed background choice.

Why it works

Why evolving the memory system helps

A fixed memory design bakes in assumptions about what evidence matters. If those assumptions are wrong for a task, the agent keeps retrieving the wrong support no matter how many episodes it survives. Evolving the memory architecture helps because it lets the system change the write and fetch rules that created the mismatch in the first place.

The modular setup makes search feasible. Instead of redesigning memory from scratch, the method swaps and recombines interpretable parts such as how summaries are written, how experiences are grouped, and how old material is dropped. That works because each part contributes a specific behavioral change that can be tested quickly.

Selection on both success and interaction count matters because a memory design that solves tasks only after many extra trials is not truly good support. The better memory systems are the ones that help the agent reach solutions sooner by resurfacing useful past experience at the point of need.

Math after the picture

The equation for selecting memory designs

First in words:

A memory design is favored when it solves more tasks and uses fewer interactions, because the search wants support systems that are both effective and economical.

Then the compact form:

fitness = task_success - cost_weight * interaction_cost

Every symbol:

task_successhow often the agent completes its tasks with a given memory design
cost_weighthow strongly the search penalizes extra environment interactions
interaction_costthe amount of trial-and-error the agent spends while using that memory design
fitnessscore used to keep or discard a memory architecture
A tiny worked example
Design A solves 8 of 10 tasks and needs 30 interaction units.
Design B solves 7 of 10 tasks and needs 10 interaction units.
If cost weight is 0.1, design A gets 8 - 0.1 * 30 = 5.
Design B gets 7 - 0.1 * 10 = 6.
Even though A solves one more task, B is selected because it reaches strong performance with much lower interaction cost.
Over many rounds, this pushes the search toward memory systems that provide the right support sooner.

The score captures the paper's main tradeoff: memory is good only when it improves task solving enough to justify the interaction budget it consumes, because extra memory work is worthwhile only if it reduces enough failed trials.

What can go wrong

What can go wrong

Search space too large. If there are too many memory module combinations, the evolution loop may spend large effort exploring weak designs before it reaches a good one.
Benchmark overfitting. A memory design can look strong on one task family yet fail elsewhere if the search rewards narrow tricks instead of general support behavior.
Unstable evaluation. If task scores are noisy, the search may keep or discard designs for the wrong reason, because fitness reflects randomness instead of genuine memory quality.
Done right. The method is strongest when candidate modules are interpretable, evaluation spans several related tasks, and fitness balances success against interaction cost.
What a runnable demo should prove

What a runnable demo should prove

Build two simple agent tasks: one that benefits from short reusable notes and one that benefits from longer execution traces. Define a small modular memory space with alternative write, fetch, and cleanup rules, then evolve those designs across repeated runs.

Compare the evolved memory systems with a fixed baseline. The evolved systems should solve more tasks with fewer retries because each task ends up with a memory design whose storage and retrieval behavior matches what the planner actually needs.

fitness = solved_tasks - cost_weight * retry_count and transfer_score = solved_related_tasks / total_related_tasks

The demo should show that changing memory contents alone is not enough when the underlying memory rules are poorly matched to the task.
