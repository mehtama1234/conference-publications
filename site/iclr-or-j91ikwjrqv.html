QLCoder: Automatically Writing Security Checkers

Instead of letting security experts write the checkers, an AI agent writes them automatically by talking to a code analysis tool.

Paper explainersAll themesAgents & Tool Use

Finding security holes in code is tedious work done by experts. When a new security bug is discovered, someone has to manually write a checker to find it in other code. QLCoder automates this: given a description of a security hole, it uses an AI to talk to a code analysis tool and writes the checker automatically. The hard part is keeping the AI from making up fake syntax that doesn't actually work.

Zero assumption version

Why hand-written security checkers are stuck

CodeQL is a tool for finding security holes. You describe what a bad pattern looks like in a special language, and it searches your codebase for that pattern. When a new vulnerability (a security hole) is discovered, a human expert must write a new CodeQL query from scratch. This is slow, boring, and error-prone.

A beginner might try: hand the raw CVE description (a public security report) to a large language model and ask it to write the query. This fails because large language models were trained on outdated CodeQL syntax. The model confidently writes syntax that looks plausible but no longer works—the code analysis tool rejects it. The result is a useless query that compiles but is wrong.

In one sentence. An agent repeatedly talks to the code analysis tool, catching hallucinations and fixing them until the query works.

What the paper changes

What the paper changes

The paper changes how the LLM interacts with the code analysis tool. Instead of writing a query once and hoping it works, the agent now gets real-time feedback. Each time it writes a line, the tool immediately says whether it is valid. The agent uses this feedback to iteratively fix hallucinations instead of submitting broken code.

the object it moves  =  The feedback loop between agent and tool
The hidden quantity

The hidden quantity: Syntax hallucination rate

measured quantity  =  How often the LLM makes up syntax

The core problem the paper addresses is that large language models confidently invent syntax that looks right but does not exist in CodeQL. A hallucination rate measures what fraction of the LLM's first attempts are syntactically invalid. If you ask the model ten times to write a query, how many are wrong? With no feedback, the hallucination rate is high because the model's training data is old and incomplete.

QLCoder measures hallucinations by running the draft query through CodeQL. If the tool rejects it with an error, the draft was hallucinated. By reading the error message and regenerating, the agent can iteratively shrink the hallucination rate until it reaches zero—the query parses and compiles.

Why it works

Why iterative feedback kills hallucinations

The mechanism is straightforward: when the LLM writes a query, it makes mistakes because its training data includes old CodeQL docs. If you just accept the first draft, you get wrong code. But CodeQL gives you an error message that says exactly what went wrong—for example, 'the syntax predicate foo_bar no longer exists' or 'the operator > is not defined for this type'. The agent reads this error and regenerates the query, avoiding the exact mistake it just made.

Why does this work? Because the error message is far more specific than the original task. The original task (CVE description) is vague and incomplete. The error message says: 'your attempt was wrong in this precise way.' This narrows the space of possible fixes. After a few iterations, the agent has seen every mistake CodeQL can find, and the next attempt is correct. Each iteration is cheaper than training a better model because you are just running the LLM five times (one minute each) instead of retraining it on new data (weeks of compute). It works right now with the existing model because the model is already smart enough to fix its mistakes once it sees them.

The cost of feedback versus retraining

First in words:

success_rate = 1 minus (hallucination_rate_per_attempt times max_attempts). If the model has a 40 percent hallucination rate per try, and you allow 5 attempts, then success is one minus 0.4 times 5, but capped at 1 (you can't go above 100 percent).

Then the compact form:

success = 1 - (1 - hallucination_per_attempt)^max_attempts

Every symbol:

successfraction of queries that end up working
hallucination_per_attemptprobability the model makes a syntax mistake on this try (0 to 1)
max_attemptshow many times the agent is allowed to revise before giving up
A tiny worked example
Suppose hallucination_per_attempt = 0.4 (model is wrong 40 percent of the time) and max_attempts = 5.
Probability the model is correct on attempt 1: 1 - 0.4 = 0.6 (60 percent).
Probability it is correct by attempt 2 (either attempt 1 was right OR attempt 1 failed but attempt 2 was right): 1 - (0.4 × 0.4) = 1 - 0.16 = 0.84 (84 percent).
Probability it is correct by attempt 5: 1 - (0.4^5) = 1 - 0.01024 = 0.99 (99 percent).
Even with a bad model, five attempts is often enough because each error eliminates a class of wrong answers.

The exponential captures the intuition that the second attempt fixes mistakes the first one made, the third catches edge cases, and so on.

What can go wrong

What can go wrong

The error message is confusing or incorrect. If CodeQL emits a cryptic error, the agent might fix the wrong part. For example, the real problem might be a logic bug, but the error message points to syntax. The agent then wastes attempts chasing the wrong issue.
The model gets stuck in a loop. If the agent regenerates the same broken line every time, it will not converge. The fix: track which fixes were tried, and feed that history to the model so it learns which direction to move.
Iterative fixes introduce new bugs. While fixing one syntax error, the agent may break something else. For example, removing a deprecated function name might leave a type mismatch. The agent then has to fix that too.
Done right: semantic validation after syntax passes. Once CodeQL accepts the query, check that it actually detects the vulnerability it was supposed to find. This requires a test case (real vulnerable code). If the query is syntactically correct but semantically wrong, flag it manually.
What a runnable demo should prove

What a runnable demo should prove

A minimal demo takes a single CVE (a known security vulnerability) and shows that QLCoder writes a working query for it, while a naive LLM fails. Pick a simple hole: for example, a buffer overflow or a SQL injection. Tell both the LLM and QLCoder the CVE description. The naive LLM writes a query once and submits it. QLCoder iterates, and after a few revisions, produces a query CodeQL accepts. Then test both queries against real vulnerable code and see how many true positives each finds. The gap shows the value of iteration.

success = num_queries_that_compile_and_run / total_queries_attempted

The demo must show that iteration through real tool feedback is radically better than betting on one LLM attempt, because the tool tells you exactly what is wrong instead of leaving you guessing.
