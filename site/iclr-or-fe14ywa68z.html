WebGen-Agent: Enhancing Interactive Website Generation with Multi-Level Feedback and Step-Level Reinforcement Learning

WebGen-Agent improves website generation by scoring what users actually see and click, because passing code execution alone does not tell you whether the page looks right or behaves correctly.

Paper explainersAll themesAgents & Tool Use

Repository-level code agents can compile a project and still fail the real task. A generated website may run without crashing while still having broken layout, unreadable text, or missing interactions. WebGen-Agent tackles that gap by making visual and interaction feedback part of the training and search loop. It renders screenshots, runs a graphical user-interface tester, converts those observations into text feedback and scores, and uses those scores both to choose better intermediate drafts and to train better step-by-step behavior. The key move is simple: judge the page by the user-visible result, because that is what website generation is actually trying to optimize.

Zero assumption version

Code execution is too weak as the only check

Many code agents verify progress by running tests or checking whether the program executes. That is useful for back-end tasks, but it misses the central difficulty of website generation. A page can render with no exceptions while still being visually poor or functionally incomplete.

Website tasks depend on both appearance and interaction. Buttons must be visible, spacing must support reading, and menus must react correctly when a user clicks them. Simple execution checks do not measure any of that, so the agent receives little signal about the actual quality of its work.

The paper adds richer feedback from screenshots and interface testing. That matters because the agent can now tell whether a change improved the visible page, whether an interaction failed, and whether a previously better version should be restored.

What changes: Use page screenshots and interface actions as training feedback, because website quality lives in what the user sees and can do.

The algorithm as a flow

What it actually does

Generate an initial website draft

The agent writes code and runs the page because a visible artifact is needed before any visual feedback can be computed.

Collect multi-level feedback

A vision model describes screenshots and assigns appearance scores, while a graphical tester tries interactions and assigns behavior scores.

Search with backtracking

The workflow compares candidate edits and can roll back weak branches, because preserving the best visible version improves later search.

Use step-level rewards

Each edit step receives a reward from screenshot and interaction scores, so the training signal arrives throughout the trajectory instead of only at the end.

Train the acting model on those rewards

The policy improves because edits that raise page quality receive higher return than edits that only satisfy execution checks.

What the paper changes

What the paper changes

The paper changes feedback collection. Instead of asking only whether the code runs, it asks how good the rendered page looks and whether key interactions succeed, because those are the outputs the user actually cares about.

The hidden quantity

The hidden quantity: step usefulness

measured quantity  =  How much one code edit improves visible page quality

A website agent makes a long sequence of edits. The hard part is that the value of one edit is often invisible to standard code checks. A style change may improve spacing because it makes text easier to scan, a button fix may unblock checkout because users can finally complete the flow, and a cleanup edit may remove a useful feature by mistake because the deleted code was still serving a visible purpose. The hidden quantity is step usefulness: how much this edit improves what a user will see or do, because that is the real target of website generation.

WebGen-Agent estimates that quantity through screenshot scoring and graphical interface testing at each step. This helps because the agent receives dense process feedback. Instead of waiting until the whole site is finished, it can learn that one specific change improved the header layout while another broke a menu.

Why it works

Why dense visual feedback helps

Website generation is not just code completion. It is iterative product building where small changes affect readability, layout balance, and interaction success. Execution feedback misses most of that because it answers only whether the program ran.

WebGen-Agent turns those missing signals into measured rewards. Screenshot analysis evaluates what the rendered page looks like, and interface testing evaluates whether users can actually operate the page. Together they cover both static appearance and dynamic behavior, so the agent is rewarded for the qualities that define a usable website.

Backtracking and step-level training make the signal actionable. Backtracking helps search because the workflow can discard edits that lower visual or interaction scores. Step rewards help learning because the acting model sees which individual edits helped, which harmed, and which had little effect. That is stronger supervision than a single final pass-fail result because the model receives feedback on each edit instead of only on the finished page.

The step-reward objective

First in words:

Each action step is trained with reward from rendered appearance and tested behavior, while search uses the same scores to decide which draft branches to keep.

Then the compact form:

reward_t = alpha * score_screenshot_t + beta * score_gui_t, and L_train follows step rewards across the whole edit trajectory

Every symbol:

score_screenshot_tvisual quality score after step t
score_gui_tinterface behavior score after step t
alpha, betaweights for appearance and behavior feedback
L_traintraining objective that favors higher-reward action sequences
A tiny worked example
Suppose one edit fixes button spacing and raises the screenshot score from 2.8 to 3.4, while the interface score stays at 4.0.
That step should receive positive reward because users can now read and click the page more easily.
A later edit adds animation but breaks the navigation menu, dropping the interface score from 4.0 to 2.5.
That step should receive negative reward because visible polish does not compensate for broken use.
Backtracking keeps the earlier stronger draft, and training learns that the useful edit was the spacing fix rather than the broken animation change.

The exact learning rule is less important than the source of the reward. The paper's contribution is to make reward track visible site quality step by step.

What can go wrong

What can go wrong

Visual scores can reward the wrong thing. If the screenshot scorer prefers flashy pages over usable ones, training drifts because the agent follows that scorer's mistakes.
The interface tester may miss important flows. If the tester never exercises checkout, search, or navigation depth, the agent can appear strong while still failing user-critical actions.
Backtracking can become expensive. Evaluating many branches costs time because each branch needs rendering and interface checks before it can be judged.
Done right: search and learning reinforce each other. When screenshot and interaction scores track real quality, the workflow improves because search keeps better drafts and training copies the edits that raised those scores.
What a runnable demo should prove

What a runnable demo should prove

Use a small benchmark of website tasks such as landing page generation, dashboard generation, and multi-step form creation. For each task, compare an execution-only code agent against a WebGen-Agent-style system that renders screenshots, runs interface actions, and trains from step rewards. Measure build success, screenshot quality judged by a held-out reviewer, and task completion rate for scripted user actions.

web_task_score = 0.5 * visual_success + 0.5 * interaction_success, reported alongside raw build success

The demo should show that execution success alone overstates quality, while the richer feedback system performs better because it optimizes the page that users actually see and use.
