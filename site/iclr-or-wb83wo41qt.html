Noise-Aware Generalization: Robustness to In-Domain Noise and Out-of-Domain Generalization

Detect mislabeled examples by comparing them across domains, because domain shift and label noise become easier to separate when you see the same class under several conditions.

Paper explainersAll themesOther

Label noise and domain shift are usually studied apart, but real data often contains both. That creates a hard identification problem: a sample may look odd because its label is wrong, or because it comes from a different domain. This paper uses cross-domain comparison to tell those causes apart more clearly.

Zero assumption version

Why noise detection breaks under domain shift

Noise detection methods often flag examples that look unusual within a class. That can work when all data comes from one domain, but it breaks when several domains are present because a correct example from a new domain can also look unusual.

Domain generalization methods fail in the other direction. They focus on learning across domains and often ignore bad labels, so the training signal gets corrupted because mislabeled examples pull the model toward the wrong class.

In one sentence. Use differences across domains to detect bad labels, because true domain variation and true label noise leave different cross-domain patterns.

The algorithm as a flow

What it actually does

Collect data from several domains

Train on multiple domains where the same classes appear under different conditions.

Compare class consistency across domains

Measure whether examples with the same label still resemble each other when viewed across domains.

Flag likely bad labels

Examples that stay inconsistent across domains are treated as noise because a wrong label usually fails to line up with same-class examples anywhere.

Train with cleaner supervision

Reduce the effect of flagged samples so the model learns from labels that hold up across domains, because those labels are more likely to be correct.

Evaluate on new domains

Test whether the model transfers better after the noisy labels have been separated from true domain variation, because cleaner labels give a less misleading training signal.

What the paper changes

What the paper changes

The paper changes where evidence for noise comes from. Instead of asking only whether a sample looks strange inside one domain, DL4ND asks whether its label stays believable when compared against the same class across many domains.

the object it moves  =  noise detection signal
The hidden quantity

The hidden quantity

measured quantity  =  cross-domain label consistency

The hidden quantity is whether a sample agrees with same-label samples across domains. A correctly labeled sample can change in color, lighting, or style and still share core class structure with its peers, because the class meaning remains the same across domains.

A mislabeled sample behaves differently. It may fit neither its own labeled class nor the same-label examples from other domains, so its cross-domain agreement stays weak.

Why it works

Why the method works

Domain shift changes appearance while preserving class identity. Label noise changes the claimed identity itself. Those two forces can look similar inside one domain, but they diverge when you compare across domains.

For a correctly labeled sample, domain differences may move surface appearance, yet the sample still aligns with same-class examples from other domains at a deeper class level. For a mislabeled sample, that alignment stays weak because the wrong label points to the wrong peers everywhere.

DL4ND uses this difference as its signal. By reducing the weight of examples with weak cross-domain label consistency, the method improves both label quality and domain transfer because training relies more on examples whose class assignment survives domain change.

Math after the picture

The core equation

First in words:

A sample's trust score grows with its average agreement with same-label examples from other domains.

Then the compact form:

trust(sample_i) = average over domains d not equal to domain_i of agreement(sample_i, same_label_examples_in_d)

Every symbol:

sample_ione training example
domain_ithe domain that sample_i came from
same_label_examples_in_dexamples in domain d that share the label of sample_i
agreement(a, b)how strongly two examples support the same class
trust(sample_i)the score used to judge whether the label is believable
A tiny worked example
A sample labeled cat is compared with cat examples from two other domains.
Its agreement scores are 0.82 and 0.79, so its trust score is about 0.81.
Another sample labeled cat scores 0.21 and 0.18 against those same-domain peers.
Its trust score is about 0.20, so it is more likely to be mislabeled.

The exact agreement measure can vary, but the logic stays the same: correct labels should survive cross-domain comparison.

What can go wrong

What can go wrong

Domains may be too similar. If domains differ only weakly, cross-domain comparison adds little new information because the same-domain and cross-domain views look nearly identical.
Class structure may change across domains. If one class truly appears very differently in another domain, a correct label can look inconsistent, so the method may downweight good data.
Noise may cluster by domain. If one domain contains many repeated label mistakes of the same type, wrong labels can support one another and become harder to isolate.
Done right. The method is strongest when domains offer real variation but classes still share a stable core, because that gives the model enough contrast to separate domain effects from label mistakes.
