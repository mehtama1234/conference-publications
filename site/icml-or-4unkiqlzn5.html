Homophily-Heterogeneity Gradient Surgery for Federated Graph Learning

When different groups of people train a shared graph model but their data looks different, split them by similarity pattern, then surgically mix their learning signals to avoid conflicts.

Paper explainersAll themesGraph & Geometric Learning

Imagine hundreds of hospitals training a shared model to predict patient outcomes from their local networks (who called whom, who had the same condition). But some hospitals have tight clusters (similar people tend to connect), while others have scattered networks (anyone connects to anyone). When they try to learn together, their conflicting patterns break the shared model. FedGCM solves this by grouping hospitals by their pattern type, then carefully mixing their learning signals so each pattern learns without sabotaging the others.

Zero assumption version

The broken world: networks with different DNA

Graph neural networks learn by looking at who connects to whom. A hospital network might show: patients with diabetes tend to call each other (tight clusters). A different hospital might show: anyone calls anyone (messy everywhere). When hospitals pool their data to train one shared model, the model sees conflicting instructions: learn to spot clusters AND learn to handle chaos at the same time. The learning algorithm gets confused and makes mistakes on both types of networks.

A naive fix: give each hospital its own mini-model inside the shared model (multi-channel architecture). But that bloats the model and kills the whole point of sharing. And nobody proves this actually converges to something stable.

The method. Group hospitals by their pattern type, then surgically remove the parts of each hospital's learning signals that conflict with others.

The algorithm as a flow

What it actually does

Measure the pattern

Each hospital computes its homophily score (how much do connected nodes share properties).

Sort into groups

Hospitals with similar homophily scores join the same group.

Compute local updates

Each hospital trains on its local network and computes how it wants to change the shared weights.

Surgical removal

For each weight, the algorithm removes the part of the update that conflicts with other groups.

Combine carefully

Blend the filtered updates from all groups so each pattern's signal strengthens the shared model.

What the paper changes

The one thing that changes

The paper changes how each hospital's learning signals are combined into the shared model. Normally you average them (all hospitals get equal say). FedGCM filters each hospital's signals before averaging — it surgically removes pieces that would break other groups' learning.

the object it moves  =  learning signal updates
The hidden quantity

Inter-group conflict: the silent killer

measured quantity  =  learning signal conflict strength

Each hospital computes a gradient (a direction to nudge the weights). When two hospitals want to nudge the same weight in opposite directions, that is a conflict. FedGCM measures how much each hospital's gradient pushes against other groups' gradients. This conflict magnitude is the hidden quantity.

The paper estimates it by projecting each hospital's gradient onto the direction perpendicular to the average gradient of other groups. If a hospital's update points directly opposite to another group's average, the projection is large; if it points the same way, the projection is small.

Plain reading. Think of each hospital shouting instructions on how to change a weight. If two hospitals shout opposite things, the weight ends up confused. FedGCM listens to each hospital but erases the parts where it shouts against the group average.
Paper reading. The conflict is quantified by the dot product of a gradient with the projection operator onto the orthogonal complement of other groups' mean gradient. Large dot product means strong opposition; residual projection zeroes it.
Why it works

Why surgical removal works: projection magic

Here is the real reason FedGCM works. Each hospital has two kinds of updates: one that helps the shared model across all patterns, and one that only works for their pattern and breaks others, because different patterns need opposite weight changes. If Hospital A's update can be split into a shared part and a conflicting part, you want to keep the shared part and throw away the conflicting part.

FedGCM does this using residual projection. For each hospital, take its gradient and subtract out the part that points opposite to the other groups' average direction. What remains is aligned with the group's goals. When you blend these cleaned-up updates, no group is sabotaged; every group's learning pulls the shared model in a compatible direction. The model converges because all groups are rowing together, not fighting.

Math after the picture

The residual projection formula

First in words:

Each hospital's cleaned update equals its original gradient minus its conflicting part. The conflicting part is how much it disagrees with the other groups.

Then the compact form:

g_clean_i = g_i - (g_i . dir_other) * dir_other

Every symbol:

g_ihospital i's gradient (direction to nudge weights)
g_clean_icleaned gradient after conflict removal
dir_otheraverage direction of other groups' gradients
g_i . dir_otherhow much hospital i agrees with other groups
A tiny worked example
Hospital A gradient: [8, 2] (strong push on weight 1, weak on weight 2).
Other groups average direction: [1, 1] (balanced push).
Conflict part: how much does A point opposite? (8*1 + 2*1) / magnitude = agreement score = 10.
Residual: [8, 2] minus conflict direction scaled by 10. After removal: [6, 0.5].
Result: A's new update avoids the parts where it would fight other groups.

The formula keeps each hospital's helpful learning and removes only the parts that sabotage other groups' patterns.

What can go wrong

What can go wrong

Grouping threshold too strict. If you split hospitals into too many fine-grained groups, each group becomes small and noisy. The average direction for a tiny group is unstable.
Grouping threshold too loose. If you merge hospitals with very different patterns, the residual projection does not remove enough conflict. The groups still fight.
Communication overhead grows with groups. Each group sends its own blended update. More groups means more rounds of communication, which hurts privacy and speed.
Done right. Choose the grouping threshold adaptively: start loose and tighten if conflicts remain. Use clustering to find the natural group boundaries in the homophily scores. Keep the number of groups small (e.g. 2–5) so communication stays fast.
What a runnable demo should prove

What a runnable demo should prove

Build a synthetic federated setup: create 20 hospitals. 10 have tight cluster networks (homophily ~0.8), 10 have scattered networks (homophily ~0.2). Each hospital trains a small graph neural network locally. On each round: compute each hospital's gradient, group by homophily, apply residual projection to filter conflicts, average within groups, and update the shared model. Track the accuracy on both cluster and mesh networks over 100 rounds.

The demo must show that FedGCM's accuracy on cluster networks and mesh networks converge to nearly the same level, while naive averaging leaves them far apart.
