Reinforcement Learning for Tool-Calling Agents in FHIR

An agent learns to reason over hospital data graphs by getting rewarded when it finds correct answers, using a smaller cheaper model that beats a bigger one.

Doctors ask questions about patient records stored as interconnected data. This paper teaches a medium-sized model to navigate this graph correctly by rewarding it when it gets the answer right.

Zero assumption version

Models make wrong moves on connected data

Hospital data is stored as interconnected records: a patient points to visits, which point to notes and lab results, which point to medications. To answer a clinical question like 'Did this patient have a reaction to this antibiotic?', the model must follow the right links in the right order.

A naive try: give the model a retrieval tool (search for matching records) and a code-execution tool (run Python to filter and combine). The model often selects the wrong record type or tries moves that violate the graph structure. For example, it might try to read a lab result from a patient who never had that test, or it might fetch data in an order that breaks the logical connections. Bigger models like o4-mini reach only 50% accuracy on realistic hospital questions.

The core problem: Tool-using models learn patterns from text but do not learn to respect the structure of the data graph they navigate.

The algorithm as a flow

What it actually does

Run the agent

Model produces a sequence of steps: fetch patient, get their visits, filter by date, extract results.

Execute and validate

Run the steps as code; check if the final answer matches ground truth.

Judge grades the attempt

A separate trained model examines the answer and true answer; outputs a numeric reward.

Credit the steps

Reinforce the learning: steps in correct sequences get higher probability weight.

Repeat and improve

Over thousands of examples, the model converges to valid, correct paths.

What the paper changes

What the paper changes

The paper trains the model to output the correct sequence of calls to a code executor, where each call must respect the data graph structure. Without training, the model generates random or hallucinated steps. With reinforcement learning, it learns to emit only valid, executable steps.

The hidden quantity

The hidden quantity: Execution-grounded correctness

measured quantity  =  Correctness reward from actual code run

Instead of using a language-model score (just asking if the answer sounds right), the paper runs the agent's steps as actual code and checks if the answer is correct. This is the ground truth signal — you either get the right patient data or you do not.

The paper estimates this by: execute the step sequence, fetch the data, run the code, compare the result to the true answer. If the answer is right, reward is high; if wrong, low. This reward signal is the difference between a model that learns real correctness and one that learns to sound plausible.

Why it works

Why execution feedback teaches the right moves

A language model predicts tokens (short text fragments) one at a time based on patterns in training data. Without reinforcement learning, it has no signal about which sequences of tool calls actually work on a given data graph. With execution-grounded feedback, every time the agent produces a sequence of steps, you run that code, get the answer, and ask: is this right or wrong?

Reinforcement learning then uses that right-or-wrong signal to update the model: steps that led to correct answers are made more likely; steps that led to wrong answers are made less likely. Over many examples, the model learns that certain sequences of data-fetch and code-filter operations are reliable paths to correct answers, while others reliably fail. Because the signal comes from real execution (not a heuristic guess), the model learns the true structure of the graph and the real requirements of the task.

A smaller model (Qwen3-8B) can learn this because the problem is no longer 'guess the right answer from text patterns' (where bigger is always better) but 'navigate a specific graph structure using feedback from actual code execution' (a learnable pattern in smaller models when trained correctly).

Math after the picture

The learning update

First in words:

The probability of a step sequence increases by a fraction proportional to how much the reward exceeds the average reward. In symbols: probability times (1 + learning-rate times (reward minus baseline)).

Then the compact form:

p_new = p_old * (1 + alpha * (R - b))

Every symbol:

p_oldThe current probability the model assigns to a step sequence
alphaLearning rate — how big each nudge is
RReward signal: 1 if answer is correct, 0 if wrong (or a continuous score)
bBaseline — the average reward so far (to reduce noise)
p_newUpdated probability after one training step
A tiny worked example
Sequence A: p_old = 0.3, R = 1 (correct), b = 0.5, alpha = 0.1
p_new = 0.3 * (1 + 0.1 * (1 - 0.5)) = 0.3 * 1.05 = 0.315
Sequence B: p_old = 0.2, R = 0 (wrong), b = 0.5, alpha = 0.1
p_new = 0.2 * (1 + 0.1 * (0 - 0.5)) = 0.2 * 0.95 = 0.190
After one step: correct sequences are 4% more likely, wrong ones 5% less likely. Over thousands of steps, this concentrates probability on correct paths.

The core idea: reward high-scoring moves by making them more probable; penalize low-scoring ones by making them less probable. The strength of change depends on how much the reward beats the average (not just whether it is good or bad).

What can go wrong

What can go wrong

Reward signal is noisy or delayed. If the judge model is miscalibrated (says right answer when wrong) or if you wait too long to give feedback, the model learns spurious correlations instead of true paths. Fix: use execution-grounded ground truth (compare to actual records) and give rewards immediately after each sequence.
Graph structure changes or is not stable. If the underlying data graph has missing links or inconsistencies, or if the rules for valid traversal are not explicit, the model converges to whatever paths maximize local reward, not global correctness. Fix: enforce structural constraints in the code executor (reject invalid moves before they are scored).
Training data is biased toward easy questions. If all training examples are simple (e.g., single-visit queries), the model learns fast on those but fails on complex multi-hop questions. Fix: include a mix of question difficulty in training.
Done right. Combine a clean training loop, real ground-truth data, a stable graph schema, and diverse training questions; the model converges to reliable reasoning that works on new questions.
What a runnable demo should prove

What a runnable demo should prove

Build a small dataset: 50 real hospital questions with correct answers. Implement a code executor that can fetch from a patient graph (use a synthetic or real small sample). Train the reinforcement-learning agent on half the questions; test on the held-out half. Measure: (1) final accuracy on test questions, (2) fraction of steps that respect data-graph constraints, (3) comparison to a baseline model with no RL training.

Test accuracy = (number of correct answers on test set) / (total test questions). Constraint violations = (invalid step sequences attempted) / (total step sequences). RL gain = (accuracy with RL) - (accuracy without RL).

The demo must show that the same model size reaches higher accuracy with reinforcement learning than without it because execution feedback tells it which step sequences work. When the model sees which paths produced correct answers, it learns to repeat those paths; without feedback, it randomly tries invalid moves.
