MeanCache: From Instantaneous to Average Velocity for Accelerating Flow Matching Inference

Instead of trusting instant velocity readings at each step, average the velocity across a time span to avoid steering the image generation off track when speeding up.

Paper explainersAll themesEfficiency & Systems

Flow Matching is a way to turn noise into images one smooth step at a time, like gradually sharpening a blurry photo. To speed things up, we cache (save) information from earlier steps and reuse it. But when you go fast (fewer steps), the saved info becomes stale and the image drifts off track. MeanCache fixes this by looking at average velocity over a time span instead of just the velocity at one moment, which keeps the path more stable. It also decides smartly which timesteps to cache from, so you get maximum speed without breaking quality.

Zero assumption version

Speed kills the trajectory

Flow Matching generates images by following a smooth path from random noise to a real image, taking many small steps. Each step asks: given where I am now, which way should I move next? The model predicts a velocity (the direction and speed to move). In the real 50-step process, this works well. But you want to generate images 5 or 10 times faster by skipping steps.

The naive idea: save (cache) features and velocity information from every 5th step, then reuse that information instead of recomputing it. But here is the trap: a velocity reading from 5 steps ago tells you which way to move right now, but the world has changed—the image state is different. Using a stale velocity prediction steers you in the wrong direction. Over many skipped steps, these small steering errors add up, and the image becomes blurry or distorted. The faster you go, the worse it gets, because more steps are skipped between caches, so the stale velocity is older and less accurate, and errors stack for longer.

The problem in one sentence. Caching based on instantaneous velocity (the direction at one moment) causes accumulated errors when steps are skipped.

The algorithm as a flow

What it actually does

Step 1: Run the full 50-step generation

Generate the image normally to collect all the data you need.

Step 2: Save rate-of-change measurements between timesteps

Store how fast the image features are changing between pairs of cached points. This is the slope of change over time, saved for reuse.

Step 3: Compute average velocity over intervals

Instead of using velocity at one moment, average it across the time span between two cached points.

Step 4: Score timesteps by trajectory stability

Measure how much error average-velocity caching would cause at each timestep under different skip patterns.

Step 5: Find the best cache schedule

Use shortest-path algorithm to pick which timesteps to cache from, staying within your speed budget.

What the paper changes

What the paper changes

The paper shifts from using instantaneous velocity (the predicted direction at a single step) to average velocity (the averaged direction over a time interval). Instead of trusting that an old velocity guess still applies, it smooths the velocity signal over the time span you skipped. This change affects the core trajectory computation.

The hidden quantity

The hidden quantity: trajectory deviation

measured quantity  =  trajectory deviation under average-velocity caching

Trajectory deviation measures how far off-track the image generation goes when you reuse cached information. When you skip steps, the true path diverges from the predicted path. MeanCache quantifies this divergence by measuring how much error occurs when you use average velocity instead of instantaneous velocity over a time interval.

The paper estimates trajectory deviation by computing Jacobian-vector products (JVP): a mathematical tool that tells you how fast features change between two cached timesteps. By comparing the true image state at an intermediate step to where average-velocity caching predicts it should be, the paper measures the error. Lower deviation means the image stays closer to the original path.

Why it works

Why average velocity fixes trajectory drift

The core problem: when you skip from step 0 to step 25, the velocity prediction at step 0 becomes stale; the image has changed, so the old direction no longer applies. The image drifts off the true path.

MeanCache's fix: instead of reusing the velocity at step 0, compute the average velocity from step 0 to step 25. This average is computed using cached Jacobian-vector products, which capture how fast features actually change over the span. Average velocity is more stable because it smooths out local bumps. It reflects the overall trend, not a single outdated snapshot. When you use this average direction to leap from step 0 toward step 25, you stay closer to the true path because the average direction is more faithful to the actual trajectory shape.

Why it is more stable: velocity varies locally (it jiggles), but the average flattens those jiggles. When you cache only at a few timesteps but use average velocity between them, the error shrinks. The paper then uses this insight to design a scheduling algorithm: it scores each possible cache-point pair by how much trajectory deviation would occur if you used average velocity, then finds the set of cache timesteps that minimizes total deviation while hitting your speed target. Early timesteps (which steer the overall image shape) get heavier weight; later timesteps (which add fine details) can be skipped more safely.

Math after the picture

The averaging formula

First in words:

predicted trajectory over interval = cached feature at start + (average velocity) × (time span)

Then the compact form:

z_t_predicted = z_r + (1 / (t - r)) * integral_r_to_t JVP(s) ds * (t - r)

Every symbol:

z_rthe image state (features) at the cached timestep r
z_t_predictedwhere we predict the image should be at timestep t
JVP(s)jacobian-vector product: how fast features change at step s
integral_r_to_t JVP(s) dssum up the rate of change over the time span from r to t
(1 / (t - r))normalize to get the average rate
t - rthe time span (number of steps skipped)
A tiny worked example
Suppose you cache at step 0 (image state = z_0 = [10, 15, 8]) and step 10 (z_10 is unknown but you want to predict it).
JVP from 0 to 10 tells you features shift at an average rate: [0.2, -0.1, 0.3] per step.
Average rate over 10 steps = [0.2, -0.1, 0.3].
Predicted z_10 = [10, 15, 8] + [0.2, -0.1, 0.3] × 10 = [10, 15, 8] + [2.0, -1.0, 3.0] = [12.0, 14.0, 11.0].
If true z_10 is [12.1, 13.9, 11.2], deviation is sqrt((0.1)^2 + (-0.1)^2 + (0.2)^2) ≈ 0.24.
The algorithm repeats this for all candidate cache intervals, then picks the schedule that minimizes total deviation while achieving your target speedup.

The average velocity from step r to step t predicts a smoother, more stable trajectory than using velocity at a single old timestep.

What can go wrong

What can go wrong

Scheduling is greedy, not globally optimal. The peak-suppressed shortest-path algorithm finds a good schedule quickly by making locally optimal choices at each step, but this greedy approach may not find the absolute best overall schedule in all cases because it does not backtrack to reconsider earlier choices in light of later constraints.
Early timesteps must be cached carefully. The first few steps shape the overall image structure. If you cache too sparsely early on, the image foundation drifts, and later detail-filling steps cannot recover. The algorithm weights early steps heavily, but if constraints force sparse early caching, quality drops.
Rate-of-change computation adds setup overhead. Before using MeanCache, you must compute rate-of-change measurements. This computation is lighter than a full forward pass because it only tracks slopes, not entire feature vectors, so it is cheaper but not free. If you generate only one image, the prep cost is tiny; in interactive systems generating many images, the prep overhead spreads across queries but still subtracts from the speed gain.
Done right. Cache early timesteps densely, use average velocity, and let the algorithm pick the schedule. Quality stays high even at 4 times speed on large models like FLUX.1 and Qwen-Image.
What a runnable demo should prove

What a runnable demo should prove

Build a minimal generative model (e.g., a simple flow model on CIFAR-10 or a toy image task). Generate an image with 50 steps (baseline, full quality). Then run it at 4 times, 6 times, and 10 times acceleration using three methods: (1) naive instant-velocity caching with fixed intervals (every 5th step), (2) instant-velocity caching with oracle-optimal scheduling, and (3) MeanCache with algorithm-selected scheduling. Measure image quality using SSIM (structural similarity) or LPIPS (perceptual loss) at each speedup. Plot speed vs. quality and show that MeanCache stays higher than naive caching and close to oracle scheduling, even at 10 times speedup.

quality_drop = (quality_at_full_steps - quality_at_acceleration) / quality_at_full_steps; plot quality_drop vs. acceleration_ratio for each method

The demo must show that MeanCache's quality drops slower with speedup than naive instant-velocity caching, proving that average velocity is more stable under acceleration.
