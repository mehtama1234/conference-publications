Order Matters: Macro Placement Sequences via LLM Evolution

A Large Language Model learns what order to place circuit building blocks in, discovering that earlier placements lock in or rule out later choices in ways that matter far more than anyone expected.

Paper explainersAll themesAgents & Tool Use

Placing the large building blocks of a circuit (macros) on a chip is a huge puzzle — you have to find positions that keep wires short and keep things from crashing. Engineers have always used simple rules to decide what to place first (like order by area or order by how connected it is). This paper shows those rules are wrong. It uses a Large Language Model to discover better rules automatically — and the rules it finds are surprising because they combine block properties in unexpected ways (like mixing size and connectivity with anti-patterns) that humans would not have guessed.

Zero assumption version

Static rules lock you into bad choices

When you place circuit blocks, each choice constrains the next. If you place a big block badly in the corner, the wires have to snake around it. Everything downstream suffers. Engineers have always decided the order upfront using fixed rules — place the biggest blocks first, or place the most-connected blocks first. This sounds sensible but it is not learned; it is guesswork from decades ago.

The catch: the order is a hidden layer of the puzzle. Change the order, keep the placement algorithm the same, and you get wildly different results. But nobody had automated a way to search over orders. So designers just used the same rule forever.

In one sentence. The paper automates the discovery of placement orders by evolving code-level strategies with an LLM, guided by a fast proxy that avoids running the whole slow optimizer each time.

What the paper changes

What the paper changes

Instead of using a fixed heuristic to choose the placement order, OrderPlace learns a dynamic rule. The rule is written as Python code that the LLM evolves. The rule can examine block properties (size, connectivity) and decide which to place first — and that decision can change per chip and per problem.

The hidden quantity

The cascade factor: how many later placements are ruled out by an early choice

measured quantity  =  Cascade impact

When you place block A in the wrong spot early, it may force block B into a congested corner, which forces block C to wrap around, which ruins the solution. This is the cascade — one bad early call has multiplied consequences. The paper does not measure this directly as a number, but it is the hidden cost of static orders. Good orders avoid cascades; bad ones trigger them.

OrderPlace detects cascades indirectly: the proxy evaluator places blocks greedily in the chosen order and counts wires and overlaps. An order that avoids cascades passes the proxy fast and cheap. The LLM evolves to favor orders with low cascade impact.

Why it works

Why learning the order works better than guessing it

The reason early choices matter so much: in placement, you are tiling blocks onto a grid with limited space. If the first block goes into the middle and sprawls, later blocks have fewer good homes. They cascade into worse and worse positions. A human heuristic (like order by area) is a blind guess — it does not know the specific chip layout.

OrderPlace instead asks the LLM to write code that reasons about the actual chip. The LLM can invent rules like place the most-connected blocks toward the center, the rest around edges or start with blocks that have high aspect ratio and low flexibility. The key: the rule is not fixed; it is specific to THIS problem. The LLM evolves different rules for different chips.

To make this search fast, the paper uses a proxy: instead of running the full optimizer (which takes minutes), it does a greedy single-pass placement and counts wires. Blocks that lead to high wire-count in the greedy pass are ruled out early. This lets the LLM test hundreds of orderings in seconds instead of hours.

The proxy ranking

First in words:

Proxy score is the greedy wirelength plus a penalty for overlaps: score equals greedy wire total plus 100 times the count of overlapped cells.

Then the compact form:

proxy_score = greedy_wirelength + 100 * overlap_count

Every symbol:

greedy_wirelengthtotal wire length if blocks are placed one by one in the chosen order
overlap_countnumber of grid cells that have more than one block
100weight that makes overlaps extremely expensive
A tiny worked example
Order A: place big blocks first. Greedy places block 1 center, block 2 pushed to edge. Wirelength = 500, overlaps = 2. Score = 500 + 100*2 = 700.
Order B: place connected blocks near center. Greedy spreads blocks evenly. Wirelength = 350, overlaps = 0. Score = 350 + 100*0 = 350.
LLM favors Order B (lower score); after many iterations it finds rules that reach scores around 250 on this chip.

The proxy is fast (one pass, no backtracking) and ranks orders reliably; the LLM evolves code to minimize it, which indirectly finds orders the full optimizer likes.

What can go wrong

What can go wrong

Proxy does not match the real optimizer. The greedy proxy is fast but approximate. It may rank two orders differently than the full optimizer would. If the proxy is too loose, the LLM optimizes for the wrong thing. Mitigation: validate final candidates with the full optimizer.
Overfitting to one chip design. If the LLM learns a rule specific to ISPD-2005 benchmarks, it will not transfer to new industrial chips. The rule may exploit quirks of those benchmarks. Mitigation: test the evolved orders on held-out designs.
LLM code quality and generalization. The LLM may generate code with subtle bugs or rules that exploit the proxy. A rule like randomize every third element might game the metric without making sense. Mitigation: constrain the code space and validate that evolved rules are interpretable.
Done right. Run proxy-guided evolution with checkpoints. Regularly test evolved orders on a held-out test set with the full optimizer. Track whether proxy rank correlates with real optimizer rank. Publish the evolved rule as code so it is auditable.

What a runnable demo should prove

Implement a simplified macro placement problem: 30 blocks, 50x50 grid, pin connectivity matrix. Implement two orderings: (1) fixed rule sort by area descending, (2) a hand-written smart rule like sort by connectivity descending then area ascending. Use a greedy placement pass for each. Measure the wirelength and the count of overlaps.

Improvement = (wirelength_static - wirelength_smart) / wirelength_static * 100%

The demo should show that a single change to the sort order changes wirelength by 20–40%, proving that order is a major lever that was being ignored.
