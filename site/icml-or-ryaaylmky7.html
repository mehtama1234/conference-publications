MalTree: Tracing Malware Evolution using Embeddings at Scale

Map malware samples into a shared numeric representation, build a tree from their pairwise distances, and check whether the inferred parent-before-child order agrees with real timestamps.

Paper explainersAll themesOther

Malware defense usually reacts one sample at a time: collect a binary, label its family, write signatures, then repeat when attackers release a variant. This paper asks a different question: can we recover family history automatically, at scale, from many samples at once? MalTree builds a representation for each malware sample from structure, behavior, and image-derived patterns, computes distances between samples, and then uses phylogenetic tree methods from biology to infer which variants are close relatives. The result is not only a cluster label. It is a proposed evolution tree that can be tested against the order in which samples actually appeared.

Zero assumption version

Why family labels are not enough for malware defense

A malware family label says two samples are related, but it does not say how. One sample may be the ancestor of another, both may descend from a third branch, or they may share only a few reused modules. Manual reverse engineering can uncover those relations, but it is slow because analysts have to inspect code reuse, behavior, packing, obfuscation, and infrastructure changes across many binaries.

If you only train a classifier, you get a flat answer: this sample belongs to Mirai, Emotet, or something else. That helps detection, but it does not show mutation speed, branch structure, or when a family splits into subfamilies, because a class label does not encode parent-child order or branch lengths. The paper frames malware analysis as lineage reconstruction. That matters because a defense team can act earlier if it knows which families mutate quickly and which new samples are close to a branch with recent dangerous behavior.

Core point. The task is not just to group similar malware, but to infer an ordered tree whose branches reflect how variants likely evolved over time.

The algorithm as a flow

What it actually does

1. Extract multiple feature views

Collect structural, behavioral, and image-based signals for each sample. This matters because one view alone can be distorted by packing or obfuscation.

2. Build a shared representation

Turn each sample into an embedding (a list of numbers that places similar samples near each other). This matters because the tree methods need a common space where distance reflects lineage closeness rather than arbitrary feature scale.

3. Form the all-pairs distance table

Measure how far every sample is from every other sample. This matters because the entire inferred tree is built from these pairwise relationships.

4. Run phylogenetic reconstruction

Use UPGMA or Neighbor-Joining to propose branch structure. This matters because each method turns distances into different assumptions about how mutation rates vary across branches.

5. Validate against timestamps

Check whether parent branches tend to appear before their descendants using VirusTotal times. This matters because a visually plausible tree is not enough; it must also respect historical order.

What the paper changes

What the paper changes

The paper changes the output of malware analysis from a label to a lineage object: a tree with branch lengths and internal split points. That is a stronger claim than saying two samples are similar, because a tree encodes which relation is local, which split happened earlier, and how quickly a family appears to diversify.

the object it moves  =  a timestamp-checkable malware lineage tree
The hidden quantity

The hidden quantity: evolutionary distance quality

measured quantity  =  whether pairwise distance preserves true lineage closeness

Tree reconstruction only works if the distance between two malware samples reflects how closely related they really are. That hidden quantity is easy to miss because an all-pairs distance table looks concrete, but it can be wrong for systematic reasons. Shared obfuscation tools can make unrelated samples look close. Heavy code changes can make a child look far from its parent.

MalTree exposes this hidden quantity indirectly through temporal consistency. If the distance metric is actually preserving lineage closeness, then the branches recovered from it should usually place older samples before newer descendants. If that order breaks often, the representation is not preserving lineage structure well enough for tree building.

Why it works

Why it works: distances create branch structure

Phylogenetic methods need only one thing as input: an all-pairs distance table that says how much change separates each pair of samples. If the representation places close relatives near one another and pushes distant branches apart, the tree algorithm can reconstruct splits by repeatedly joining samples or subtrees whose distances are most compatible. UPGMA assumes a common rate of change across branches, while Neighbor-Joining allows unequal rates by adjusting which merges best explain the full table.

That mechanism is useful for malware because explicit source ancestry is usually unavailable. The tree methods do not need an author to declare parent and child samples. They infer structure from the observed pattern of similarity across many binaries at once. Temporal validation then matters as a second mechanism: it filters out trees that merely fit pairwise distances but violate history. If a branch consistently puts later samples above earlier ones, the representation or reconstruction rule is missing something about how malware families actually mutate.

The representation assigns each sample a numeric point. Pairwise distance between those points becomes the basic evidence used to decide which samples share short branches.

A tiny worked example
Suppose sample A and B are distance 1 apart, A and C are distance 5 apart, and B and C are distance 4 apart.
A tree method will try to place A and B on a short shared branch because they are the closest pair.
If timestamps say A appeared first, B appeared next, and C appeared much later, that ordering supports the idea that A and B are a local branch while C sits farther away.
If the timestamps instead forced C to appear before A and B in a way the tree cannot explain, then the distance representation is likely mixing up lineage with superficial similarity.

The whole method stands or falls on whether distances between representations behave like evolutionary distances rather than only classification distances.

What can go wrong

What can go wrong

Timestamp order is only a proxy for true ancestry. VirusTotal timestamps tell when a sample was first seen, not when it was authored. A late upload of an old sample can make a correct lineage edge look temporally inconsistent because observation time is not the same as creation time.
Distance can absorb obfuscation noise. If two unrelated families use the same packer or reuse common boilerplate, their representations can move closer than their ancestry deserves. The tree then groups them for the wrong reason because the all-pairs distance table is already biased.
Biology assumptions only partly transfer. Malware can borrow code across branches, copy modules from unrelated families, or be rewritten by different authors. That violates the clean tree assumption because real malware history can be a network with merges, not a pure branching process.
Done right. Use the tree as a lineage hypothesis that guides analysts toward likely parent-child relations and mutation hot spots, then combine it with reverse engineering when the branch structure affects a high-stakes response.
What a runnable demo should prove

What a runnable demo should prove

Take a small malware corpus with family labels and first-seen timestamps. Build one representation per sample, compute the pairwise distances, run both UPGMA and Neighbor-Joining, and render the resulting trees with timestamps beside each leaf. The demo should report the share of edges or ancestor-descendant pairs whose temporal order is consistent with the timestamps. It should also highlight at least one family with a shallow stable branch structure and one family with rapid splitting, so a reader can see how lineage differs from ordinary clustering.

temporal_consistency = ordered_ancestor_descendant_pairs / all_checked_pairs

A successful demo shows more than similarity: it shows that the recovered tree agrees with historical order often enough to support proactive analysis of fast-changing malware families.
