LiveWeb-IE: Scraping Real Websites That Change

Stop testing web scrapers on frozen snapshots; test them on live websites that actually evolve in real time.

Paper explainersAll themesDatasets & Benchmarks & Evaluation

Web scrapers need to extract data like prices, product names, or event details from web pages. The old way to test scrapers was simple: take a screenshot of a webpage at one moment, lock it in place, and see if the scraper finds the right text. But real websites change constantly—layouts shift, new ads appear, old regions get moved. This paper shows scrapers fail badly on those changes (losing 15% of their accuracy), and proposes a new way: test on live sites, and teach scrapers to search for data the way humans do—by looking at the visual region where something belongs, not just parsing the raw HTML code.

Zero assumption version

Scrapers work in the lab but fail in the wild

A web scraper is a program that automatically reads a webpage and pulls out useful data—a product price, a date, a name. Until now, every scraper test used the same recipe: download an HTML file from a website once, freeze it, then see how well the scraper finds the data in that frozen version. This works fine in a lab.

But real websites do not stay frozen. When a website updates, its layout changes. A region that held product names might move to a different spot. The ads section expands. The HTML code that marked a price gets renamed. Measurements show that existing high-performing scrapers drop 15% or more in accuracy on these real, evolved websites.

The root problem: old scrapers learn to recognize data by reading HTML tags and structure (the raw code underneath the page). When the structure changes, they are lost. A naive first attempt: write stricter rules that match more tag patterns. But that makes the scraper even more brittle, because it memorizes one website's particular tags instead of learning to recognize where useful information actually lives on a page.

The core of the problem: Scrapers trained on one static snapshot of a webpage cannot adapt when the website evolves.

The algorithm as a flow

What it actually does

Step 1: Get a query

A human writes what they want: get the price, find the event date, list the reviews.

Step 2: Find the region

The scraper scans the webpage visually and narrows down: the price is in that white box on the right.

Step 3: Identify items

Within that region, pick out the exact fields: this number is the price, this text is the currency.

Step 4: Build a pattern

The scraper learns the visual structure, not the HTML tags: look for this kind of region, find these fields inside it.

Step 5: Test on live sites

Apply the learned pattern to real websites that evolve. Measure if it still works after the layout changes.

What the paper changes

What the paper changes

Instead of teaching scrapers to recognize HTML tags (the raw code), the paper teaches them to recognize visual regions (where information visually appears on the page). A scraper no longer asks, 'Does this HTML element have a price tag?' It asks, 'Is this the region where prices live, and what is inside it?' This shift mirrors how a human actually browses.

the object it moves  =  from HTML-tag parsing to visual-region scanning
The hidden quantity

Content stability: does the data stay where it belongs?

measured quantity  =  Content stability over time

The paper measures a new quantity: how stable is the piece of information you are trying to extract? Not layout stability (Does the page look the same?), but content stability (Does the data stay in the same conceptual place?) A price might move slightly in the layout, but it is still in the 'price region.' An event date might get reformatted, but it is still near the event title.

The paper infers this stability by testing on live websites over time. If a scraper trained on an old version of the site still finds the right data on today's version, that means the content location was stable. If it fails, the content shifted or the structure evolved too much.

Existing benchmarks assume 100% layout stability (the HTML is frozen). Real websites have high content stability but low layout stability—the meaning stays, the format changes.
Why it works

Why visual grounding survives layout changes

A scraper trained on HTML tags learns rules like: 'Look for a element with class=price-tag, then grab the number.' When the website updates and changes that class name, the rule dies. The scraper has no fallback.

A scraper trained on visual regions learns a different kind of rule: 'On this page, the price lives in a rectangular box that sits to the right of the product image and above the 'Add to Cart' button. Whatever text is in that box, in whatever format, is the price.' If the website redesigns and the HTML class name changes, but the price still visually lives in that same box, the rule survives. The scraper does not care about the tag name; it cares about the region.

This works because website designers think visually. They move things around, rename classes, change the HTML—but they keep the conceptual layout stable. A price goes in the 'price area.' A date goes near a title. A person's name goes above their biography. By teaching scrapers to recognize these visual layouts rather than HTML tag names, the scraper learns the designer's intent, not the designer's current code. Intent is more stable than code.

How the benchmark measures survival when websites evolve

First in words:

Performance drop = baseline accuracy on frozen page minus accuracy on evolved live page. VGS aims to minimize this drop by learning visual regions rather than tag names.

Then the compact form:

survival = 1 - (accuracy_frozen - accuracy_live) / accuracy_frozen

Every symbol:

accuracy_frozenhow many items the scraper finds correctly on a static HTML snapshot
accuracy_livehow many items it finds correctly on the same website weeks later (possibly with layout changes)
survivalfraction of performance preserved when the website evolves; 1.0 = no drop, 0.0 = complete failure
A tiny worked example
Scraper A (HTML-tag method): accuracy_frozen = 95%, accuracy_live = 78%. Drop = 17%. Survival = 1 - (95-78)/95 = 1 - 0.179 = 0.821.
Scraper B (visual-region method): accuracy_frozen = 90%, accuracy_live = 87%. Drop = 3%. Survival = 1 - (90-87)/90 = 1 - 0.033 = 0.967.
Same task, same websites. Scraper B drops far less because it learned the visual layout (stable) rather than HTML class names (fragile).

A scraper that learns visual regions keeps its accuracy when the website evolves, because regions (where humans put information) change slower than tags (how programmers encode it).

What can go wrong

What can go wrong

Radical layout redesign. If a website completely overhauls its design and moves all content to new regions, even visual-region learning can fail. VGS relies on the assumption that regions stay roughly in the same place. A full redesign breaks that assumption. Fix: test on websites you know update gradually, not ones that redesign every month.
Ads or pop-ups that shift the visible region. If a website inserts new ads or modals that push the data to a different spot on screen, VGS may look for the price in the old region and miss it. Fix: VGS would need to learn to ignore transient overlays and find the stable underlying layout.
Mobile vs desktop layout completely different. A price region on desktop might be nowhere to be found on mobile (everything stacks vertically). VGS trained on desktop snapshots will fail on mobile. Fix: train and test on the same device type, or teach VGS to adapt to different screen sizes.
Done right. Test on websites that evolve gradually (most do). Measure that your scraper finds data in the visual region on both old and new versions. VGS works when the designer keeps the same conceptual layout even if the code changes.
What a runnable demo should prove

What a runnable demo should prove

Build two web scrapers: one trained to recognize HTML tags (e.g., look for elements with class='price'), and another trained to recognize visual regions (e.g., find the box on the right side of the image). Take a real website like a product listing. Create a training snapshot. Modify the website by changing CSS class names but keeping the visual layout the same (move the price box left 10 pixels, but keep it in the same general area). Re-test both scrapers on the modified version. Measure F1 score (precision and recall of found items). The tag-based scraper should drop >10%. The region-based scraper should drop <5%.

robustness drop = (F1_frozen - F1_evolved) / F1_frozen × 100%

If the region-based scraper loses far less accuracy when the layout changes, it proves that visual grounding works better, because visual regions stay in the same place even after layout updates, while HTML tag names change with every code refresh.
