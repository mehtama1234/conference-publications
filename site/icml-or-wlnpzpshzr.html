LightWM: Training-Free Hierarchical Working Memory for Small Language Model Agents

Give a small agent a structured short-term memory so it can keep the facts needed for the current subtask without retraining the model.

Paper explainersAll themesAgents & Tool Use

Small language-model agents are attractive because they are cheap to run locally, but they lose track of long tasks quickly. LightWM tries to fix that failure by storing task state in a structured memory system with one layer for the whole job and another for the current subgoal. The model is not retrained. Instead, a stronger offline writer prepares reusable memory templates because a fixed schema gives the small agent explicit slots to fill during execution.

Why long tasks break small agents

A small agent often starts correctly and then drifts. After many actions, it forgets which room it searched, which object it already picked up, or what the current subgoal requires. When the remembered state is incomplete, later actions are based on stale facts.

Common fixes summarize the past in free-form text, but that summary can silently drop the one detail that matters next. LightWM argues that long-horizon performance improves when memory updates are structured around the task's subgoals, because the agent then reads and updates a compact state record instead of re-parsing a long history.

The paper's move in one sentence. Prepare a reusable memory schema for each task family, then let the small agent update that schema at the task level and the subtask level as it acts.

What the paper changes

What the paper changes

The paper changes how task state is represented during agent execution. Instead of storing the recent past as an unstructured note, it stores explicit fields for whole-task facts and current-subgoal facts.

the object it moves  =  Execution-time memory state
The hidden quantity

The hidden quantity

measured quantity  =  Decision-relevant state retained at the current step

The important hidden quantity is not how much history the agent has seen, but how much of the right state it still retains when choosing the next action. A short memory can work well when it keeps the facts that matter now.

LightWM tries to maximize retained useful state by separating persistent facts from temporary subgoal facts. That split matters because many details are needed only for the current subgoal, while others must survive across the whole episode.

Why it works

Why this works

Structured memory helps because it turns recollection into slot filling. When the agent sees a new observation, it updates named fields such as current room, target object, completed subgoal, or missing prerequisite. That is easier for a small model to maintain than rewriting a long natural-language summary after every step.

The two-layer design also reduces distraction. The local memory for the current subgoal can stay short because it excludes older details that are irrelevant now, while the global memory still preserves facts that must survive across the whole task. This separation improves action selection because the model reads a smaller, cleaner state description at each step.

Math after the picture

The state update rule

First in words:

At each step, the agent updates the task memory and the current-subgoal memory using the new observation, then chooses an action from the updated local state.

Then the compact form:

global_t, local_t = update(global_t-1, local_t-1, observation_t, subgoal_t) ; action_t = policy(local_t)

Every symbol:

global_tthe task-level memory after step t, holding facts that matter across the whole job
local_tthe subtask-level memory after step t, holding facts needed for the current subgoal
observation_tthe new information seen at step t, such as room contents or tool status
subgoal_tthe current smaller job inside the larger task
update(...)the structured memory writer that places new facts into the right slots
policy(local_t)the action chooser that reads the local memory and picks the next step
A tiny worked example
Suppose the task is: put the apple in the fridge.
At step 1, the observation says: you are in the kitchen, the apple is on the table, the fridge is closed.
global_1 stores kitchen, apple location, and fridge location because those matter across the whole task.
local_1 stores current subgoal = get the apple, target object = apple, blocker = none.
After the agent picks up the apple, local memory changes to current subgoal = open the fridge, carried object = apple.
The next action comes from local_2, so the agent opens the fridge instead of re-reading the whole history.

The paper's core point is that clean state updates can replace long free-form recall for procedure-heavy tasks.

What can go wrong

What can go wrong

Bad schema induction. If the offline writer builds the wrong slots for a task family, later updates will store facts in the wrong places, so the small agent will act on an incomplete state.
Wrong subgoal boundary. If the current subgoal is misidentified, the local memory will emphasize the wrong facts, because it is designed to keep only what matters for that subgoal.
Update drift. A structured memory can still drift when observations are parsed incorrectly, because each bad update propagates into future action choices.
Done right. Use task families with repeatable procedures, validate the induced schema on a few held-out traces, and log every memory update so that failures can be traced to the exact slot that went wrong.
What a runnable demo should prove

What a runnable demo should prove

Build a household-task agent with three recurring task families such as fetch, open-and-place, and clean-and-store. For each family, prepare a simple global memory template and a local memory template. Then compare two versions of the same small agent: one that reads the full action history each step and one that reads only the structured memory.

The demo should show that the structured-memory version finishes longer tasks more often because it retains the right state for the current subgoal instead of relying on a long free-form recap.

success_rate = completed_tasks / total_tasks ; memory_error_rate = wrong_or_missing_memory_fields / total_memory_updates

If success stays high late in the episode while memory errors stay low, the demo is capturing the paper's main mechanism.
