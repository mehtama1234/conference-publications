Optimal Pricing for Data-Augmented AutoML Marketplaces

The paper prices external data by the improvement it causes in an AutoML model, rather than by the dataset itself or by the compute used to train the model.

Paper explainersAll themesOther

Cloud AutoML systems let buyers upload training data and receive a trained model. Many valuable external datasets could improve those models, but pricing that data is difficult because a raw dataset has no single value outside a task and different buyers benefit from the same data by different amounts. The paper proposes a data-augmented AutoML marketplace that inserts external datasets into the training pipeline and charges according to instrumental value, meaning the model-quality gain caused by the extra data. Buyers choose from menu options, and payment is linked to measured performance improvement rather than to storage size or compute cost.

Zero assumption version

Why direct dataset pricing is hard in an AutoML market

A dataset is not inherently valuable in the abstract. Its value depends on the buyer's task, existing data, model class, and evaluation metric. One external dataset may greatly improve a retail-demand classifier but do almost nothing for a medical-image model because the learned patterns may transfer well to one task and poorly to another. So a fixed per-dataset price is often misaligned with actual benefit.

Standard cloud AutoML pricing avoids that issue by charging for compute, storage, or subscription tiers. That is administratively simple, but it does not create a market for outside data suppliers because the price is disconnected from the extra model quality their data creates. The main challenge is to define a price that is measurable, task-specific, and acceptable to buyers with different willingness to pay.

The pricing mismatch. What buyers care about is model improvement, so charging mainly for compute or raw dataset access misses the quantity that actually creates value.

The algorithm as a flow

What it actually does

Train a buyer baseline.

Run AutoML on the buyer's own data first so the system has a reference model quality before any external data is added.

Try external data augmentation.

Add candidate supplier datasets and retrain or fine-tune models because the platform needs a direct before-and-after comparison to measure whether those datasets improve the buyer's target metric.

Estimate instrumental value.

Compute the marginal quality gain caused by the added data, which means the marketplace isolates the part of performance attributable to augmentation.

Offer a price menu.

Present buyers with options tied to different expected improvement levels so buyers with different valuations can self-select.

Deliver the chosen model and settle payments.

Charge according to the chosen improvement-based contract and distribute revenue to the contributing data suppliers.

What the paper changes

What the paper changes

The paper changes the pricing unit in an AutoML marketplace. It moves from charging for resources or raw data access to charging for the measured improvement external data causes in the delivered model.

the object it moves  =  the pricing rule for external data inside AutoML
The hidden quantity

The hidden quantity

measured quantity  =  instrumental value of external data

The hidden quantity is not the external dataset itself. It is the incremental model quality that the dataset creates for one buyer's task when combined with that buyer's existing data and AutoML pipeline. This is buyer-specific and task-specific, so it cannot be read off from file size, row count, or collection cost.

The marketplace measures this quantity by comparing model outcomes with and without the added data. That comparison matters because it turns a vague pricing problem into a concrete one: how much better is the delivered model due to augmentation?

Why it works

Why pricing model improvement is more workable than pricing datasets directly

The idea works because model improvement is the outcome both sides care about. Buyers want a better model, not ownership of a dataset for its own sake, because the model is the product they deploy. Suppliers want to be paid when their data creates measurable benefit. By tying price to the observed performance lift, the market can align payment with realized value rather than with rough proxies such as file size or training time.

The menu design matters because buyers value the same improvement differently. One buyer may accept a higher price for a small gain because errors are expensive in that application. Another buyer may decline the same gain. Menu-based pricing lets buyers reveal their willingness to pay through their choice, which means the platform does not need to know every buyer's exact valuation in advance. The AutoML integration also matters because the platform can run the comparison automatically within an existing training workflow, so the measured gain is tied to the actual delivered model rather than to a separate offline estimate.

Math after the picture

Price the model by marginal quality improvement

First in words:

Set payment as a function of how much the augmented model improves over the buyer-only baseline on the chosen evaluation metric.

Then the compact form:

price = p( max(0, metric_augmented - metric_baseline) )

Every symbol:

metric_augmentedthe evaluation score of the model trained with external data
metric_baselinethe evaluation score of the model trained only on the buyer's data
metric_augmented - metric_baselinethe measured marginal gain from data augmentation
p(·)the pricing function or menu rule that maps gain to payment
pricethe amount the buyer pays for the augmented model option
A tiny worked example
Suppose the buyer-only model reaches 0.78 accuracy.
After adding one supplier dataset, the AutoML system reaches 0.84 accuracy.
The marginal gain is 0.06 accuracy points.
If the pricing menu charges 100 units for each 0.01 of approved gain, the price for that option is 600 units.
If another supplier's data raises accuracy only to 0.80, its gain is 0.02 and its price would be lower.

The paper's market design is richer than this toy linear menu, but the central idea stays the same: payment is tied to measured improvement.

What can go wrong

What can go wrong

Marginal gain can be noisy. If the evaluation split is small or the training pipeline is unstable, the measured difference between baseline and augmented models may reflect noise, which makes the resulting price hard to justify.
Attribution across multiple suppliers is hard. When several external datasets are used together, their benefits may overlap, so dividing the total gain into supplier-specific contributions becomes difficult because one dataset's value can depend on another's presence.
Menu design can still miss true buyer valuation. A coarse price menu may leave value unrealized if the offered options do not match what buyers are actually willing to pay for different improvement levels.
Done right. The method works when performance gains are measured reliably and the menu is designed around those gains, because then both buyers and suppliers see a direct connection between payment and created model value.
What a runnable demo should prove

What a runnable demo should prove

Build a toy AutoML marketplace with one buyer dataset and several supplier datasets of varying relevance. Train a baseline model on the buyer data, then retrain with each supplier dataset added. Measure the gain on a held-out set and apply an improvement-based price rule. Compare that with a fixed dataset fee and a compute-based fee.

The demo should make the pricing mismatch visible. A supplier dataset that does not help should earn little or nothing under the proposed market, while a highly relevant dataset should command a higher payment because it measurably improves the delivered model.

value_alignment = correlation(price, model_gain)

A convincing result shows that the proposed pricing rule tracks actual model improvement more closely than fixed data fees or compute billing.
