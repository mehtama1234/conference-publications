R³DAO: Reactive Recovery and Reconstruction for Long-Horizon Data Agent Orchestration

When a data-analysis agent breaks mid-task, fix it locally instead of restarting everything.

Paper explainersAll themesAgents & Tool Use

Building an agent that runs data science tasks from start to finish is hard because early mistakes ripple forward and break everything downstream. R³DAO watches for these breakdowns, figures out exactly where things went wrong, and rewires only the broken piece while keeping the rest of the plan intact. This cuts execution time by 36 times and slashes costs while actually fixing more tasks.

Zero assumption version

Why rigid agent plans fail at scale

Most data-science agents follow a preset chain: gather data, clean it, explore patterns, build models, evaluate. If step 2 fails, the agent reruns everything from the top. This wastes time and tokens (the text the model reads/writes, measured in thousands of small units).

A naive agent faced with a dead end asks for permission to restart the whole workflow. But restarting is expensive: it forces the model to re-read every earlier result, re-derive decisions that worked fine, and re-attempt the failed step from scratch. The real tragedy is that most failures are local—the cleaning step failed, but data gathering was fine. Throwing away the whole history makes no sense.

In one sentence. Instead of restarting the whole agent workflow when one step fails, diagnose the broken step, swap it for a better version, and continue with what you learned, because this keeps earlier correct work intact and only replays the broken piece—saving tokens and time.

The algorithm as a flow

What it actually does

Step 1: Decompose the job

Break the big goal (analyze this dataset) into smaller steps (fetch, clean, model, evaluate), each one a concrete operation.

Step 2: Execute and watch

Run each step. When one fails, catch the error message instead of crashing.

Step 3: Diagnose locally

Read the error message with the model. What went wrong at THIS step, and what should the next step try instead?

Step 4: Rewire and continue

Replace the broken step, keep all correct earlier work intact.

Step 5: Save the lesson

Remember this fix. When the same kind of failure appears again, use the learned patch instead of rediscovering it.

What the paper changes

The hidden quantity

The hidden quantity: Local resilience score

measured quantity  =  execution resilience at each step

The paper measures an invisible quantity: how likely is each step to survive a mistake from upstream? A step survives if it can succeed even when its inputs are wrong or incomplete. The paper figures this out by reading the error message and asking: can the next step correct this, or is this broken for good?

R³DAO estimates resilience by running a mini-model of each step (without executing it fully). This tells the agent which errors are fixable locally (swap the cleaning function, rerun cleaning, keep going) versus which errors need a global restart (the data source is actually offline).

Why it works

Why fixing locally beats restarting globally

When an agent hits an error, it has two choices: (A) restart from the beginning, re-reading all prior outputs and re-deriving all prior decisions, or (B) diagnose what broke and fix only that piece. Choice A is guaranteed to work but costs massive tokens. Choice B saves tokens if the agent can pinpoint the break, because the model only needs to re-run the broken step, not every prior step.

R³DAO picks choice B by building a three-step loop. First, it decomposes the big goal into smaller tasks, which shrinks the search space—the agent is thinking in smaller pieces, not trying to plan the whole future at once. Second, when a piece fails, it uses semantic reflection: the model reads the error message and explains what went wrong in plain language. This explanation becomes a diagnostic signal that tells the agent: this failure is fixable with a different version of step N, or this failure is fatal. Third, if fixable, the agent doesn't restart; it replaces only step N with a corrected version and continues. Over time, the agent collects these fixes (experience distillation) and reuses them on similar tasks.

Here is why this works: most task failures are local. A data-cleaning bug does not make the whole workflow unrecoverable. By catching failures early and swapping single steps, the agent keeps most of its prior work intact, speeding up execution by orders of magnitude.

Math after the picture

The recovery cost equation

First in words:

Recovery cost equals the number of tokens to re-run steps from the failure point forward, versus the cost of restarting from the beginning plus the cost of re-deriving every prior step.

Then the compact form:

C_local = tokens_to_rerun_broken_step + tokens_to_fix_diagnosis; C_global = tokens_to_restart + sum(tokens_per_prior_step); if C_local < C_global then fix_locally else restart_globally

Every symbol:

C_localcost of fixing only the broken step and continuing
C_globalcost of restarting the entire workflow from step 1
tokens_to_rerun_broken_stepmodel tokens needed to re-run the failed step with a corrected approach
tokens_to_fix_diagnosismodel tokens to read the error and decide how to fix it
tokens_to_restartmodel tokens to re-read the starting data and problem statement
sum(tokens_per_prior_step)total tokens across all prior steps (data fetch, explore, etc.)
A tiny worked example
Scenario: 5-step workflow. Data fetch (100 tokens), explore (150 tokens), clean (200 tokens, BREAKS), model (not yet run), evaluate (not yet run).
Restart cost: re-read start (100) + re-run fetch (100) + re-run explore (150) + diagnosis (50) + re-run clean with fix (250) = 650 tokens.
Local fix cost: diagnosis (50) + re-run clean only (250) = 300 tokens. Then continue to model and evaluate (new steps, same cost either way).
Local fix saves 350 tokens on THIS task. Reusing the learned fix on 10 similar tasks saves 3,500 tokens total.

The agent chooses local recovery when the error is in one step and that step is fixable by trying a different approach; it restarts only when an error blocks multiple downstream steps or signals a fundamental problem with the input data.

What can go wrong

What can go wrong

The error is not really local. Sometimes the agent misdiagnoses a failure as fixable when it actually signals a systemic problem upstream (e.g., the data source is corrupted, not just the cleaning code). The agent tries a fix that doesn't work, wastes tokens, then eventually restarts anyway. The paper mitigates this by building a fallback: if the agent tries the same step 3 times and keeps failing, it declares the failure systemic and restarts.
The fix doesn't generalize to new tasks. The agent learned a patch for one specific cleaning failure (e.g., handle missing values by zeroing them). On the next task, the data is missing in a different way, and the patch fails. The paper's distillation mechanism (remembering fixes) helps but isn't perfect because a fix is specific to the error pattern it solves; when the next task's error is slightly different, the learned fix no longer applies. The learned fix is most reliable when the new task has very similar input structure.
Decomposition doesn't match the real workflow. The agent breaks the task into subtasks that don't align with how the actual code fails. For example, if the real code couples data fetching and cleaning, but the agent plans them as separate steps, a bug in the coupling is invisible to the agent's recovery logic. The agent needs careful task design to work well.
Done right. When the agent is given well-structured tasks with clear subtasks, and errors are mostly fixable at single steps, R³DAO excels. The agent learns fast, executes lean, and scales to long workflows without restarting.

Inject a failure in the cleaning step (e.g., rename a column but don't warn when it's missing). Measure tokens, time, and success rate.
