Tools are under-documented: Simple Document Expansion Boosts Tool Retrieval

Tool retrieval improves when tool pages are expanded into structured, comparable descriptions, because sparse and inconsistent documentation hides which tool actually matches the user's need.

Paper explainersAll themesAgents & Tool Use

A tool-using language model can only call the right tool if retrieval surfaces the right candidates first. That sounds simple, but real tool documentation is often incomplete, uneven, and written in different styles. One tool may describe inputs clearly but omit failure modes. Another may list functions but never state the real use case. This paper argues that retrieval is being limited less by model architecture than by the quality of the documents it searches. The proposed solution is document expansion: automatically rewrite tool documentation into richer, structured profiles, then train retrieval models on that improved corpus. Better documents help because retrieval can only match against information that is actually present.

Zero assumption version

Tool retrieval is weak when the documents are weak

Tool retrieval often focuses on better retrievers or rerankers, but the underlying documents may not say enough to support a good match, because the query cannot align with facts that are missing from the page. If the documentation never mentions the likely user goal, the right tool can appear unrelated even when it is the correct choice.

The problem is not just missing text. Tool documents are heterogeneous. Some list arguments, some list example calls, some explain business purpose, and some contain almost nothing beyond a short summary. A retrieval system trained on such uneven inputs learns unstable matching rules because similar tools are described in different ways.

This paper treats documentation quality as part of the retrieval pipeline. It expands sparse tool pages into richer structured descriptions, then uses those expanded profiles to train both a first-stage retriever and a later reranker.

Key point: Retrieval cannot match missing evidence, so improving the documents can raise retrieval quality before any change to the retriever itself.

The algorithm as a flow

What it actually does

Start from raw tool documents

The pipeline collects existing tool descriptions, which are often short and inconsistent across tools.

Expand each document into structured fields

Language models generate richer profiles with use cases, input expectations, output behavior, and related cues, because retrieval benefits when those facts are stated directly.

Validate and refine the expansion

The system checks generated profiles before keeping them, so poor expansions do not poison the training corpus.

Train a first-stage retriever

Tool-Embed learns to surface promising candidates quickly from the expanded corpus.

Train a reranker on harder comparisons

Tool-Rank learns to order close candidates better because the richer profiles expose the small differences among similar tools.

The hidden quantity

The hidden quantity: matchable evidence

measured quantity  =  How much of a tool's real capability is actually written in its profile

A retrieval miss often appears to be a model error, but the deeper issue may be that the document never contained the cues needed for a match. The hidden quantity is matchable evidence: the amount of task-relevant information that is explicitly present in the tool profile.

Document expansion raises that quantity by adding structured descriptions of purpose, expected inputs, outputs, constraints, and common usage patterns. When those details are present, both retrieval and reranking improve because more parts of the user request can find support in the tool profile.

Why it works

Why document expansion helps retrieval

Retrieval systems match query cues against document cues. If a user asks for a tool to schedule recurring events with reminders, a short document that only says "calendar utilities" may be too vague to win the match. A richer profile that names recurring schedules, reminder settings, accepted inputs, and expected outputs is much easier to retrieve.

Expansion also reduces description mismatch across tools. When one tool page is narrative and another is only a bullet list, the retriever must learn across incompatible styles. Structured fields make the corpus more uniform, which helps because the same kinds of facts appear in similar places across tools.

Training a retriever and reranker on the expanded corpus compounds the gain. The first-stage retriever sees better evidence during candidate search, and the reranker can use finer distinctions because the richer profiles reveal why two similar tools differ in practice.

A tiny worked example
Suppose the user asks for a tool that can convert meeting notes into calendar events with reminders.
Tool A originally says only, "calendar helper." Tool B says, "document parser." Neither page is a strong match.
After expansion, Tool A's profile states that it creates events, supports reminders, and accepts date text from notes.
Now the request and the profile share several concrete cues, so Tool A rises in retrieval because the needed evidence is finally written down.

The exact scoring model can vary. The lasting contribution is that retrieval quality rises when the documents contain more task-relevant facts in a consistent form.

What can go wrong

What can go wrong

Expanded profiles can invent facts. If document expansion adds capabilities the tool does not truly have, retrieval gets worse because the wrong tool is promoted for the wrong reason.
Validation can be too weak. If the checking stage fails to remove poor expansions, the training corpus becomes noisy, so both retriever and reranker learn unreliable matches.
Overly rigid fields can miss unusual tools. Some tools do not fit a standard profile shape, so forcing every document into the same frame can hide special behaviors that matter for retrieval.
Done right: documentation becomes a model input worth training on. When expansions stay faithful and structured, retrieval improves because the query can match against the tool facts that were previously missing.
