RPG: Repository Planning Graph for Unified Code Generation

Instead of free-form writing, generate complete code repositories by first building an explicit graph of what to build and how pieces connect.

Paper explainersAll themesAgents & Tool Use

Large language models can write individual functions well, but writing an entire code repository from scratch remains difficult. The core problem: models rely on natural language planning, which is vague and leaves room for misaligned parts. This paper introduces a Repository Planning Graph (RPG), a structured blueprint that maps out all the files, data flows, and dependencies before any code is written. By planning as a graph first, then generating code guided by that plan, the method generates far larger, more complete repositories with fewer errors.

Zero assumption version

Repositories are too complex for word-by-word generation

When a model writes code file by file, it forgets what files already exist, loses track of what data each piece expects, and builds incompatible parts. A naive approach is to tell the model the entire specification in words and hope it stays consistent — but thousands of details get lost or twisted because natural language is inherently ambiguous.

The real world has file structures (some files import others), data types (functions expect inputs in specific formats), and dependencies (module A needs module B). A model that ignores these relationships produces broken code that does not run together, even if each file looks reasonable in isolation.

In one sentence. The paper replaces vague word-based planning with an explicit graph that shows all files, data flows, and function signatures, then uses that graph to guide code generation.

The algorithm as a flow

What it actually does

Proposal stage: what features to build

High-level planning decides which files and modules the repository needs.

Graph construction: explicit blueprint

Build a graph where nodes are files and functions, edges show dependencies and data types.

Implementation stage: code the graph

For each node, generate the function or file, constrained by the graph structure.

Code generation with testing

Write the actual code, run tests to catch mismatches, fix broken imports or type errors.

Localization: reuse and refactor

When a test fails, the graph shows which nodes (files and functions) are involved, so repairs touch only the relevant code without accidentally breaking unrelated parts.

What the paper changes

The single change: explicit structure instead of prose

Instead of describing the repository in natural language and hoping the model infers the structure, the paper builds an explicit graph before any code is written. The graph encodes which files exist, what functions each contains, what data types flow between functions, and how files depend on each other. Code generation then follows this blueprint rather than inventing structure on the fly.

the object it moves  =  repository structure representation
The hidden quantity

The hidden quantity: structural clarity

measured quantity  =  graph consistency score

The paper measures how well the generated code matches the planned graph structure. A high score means functions have the right signatures, imports are correct, and data types flow as expected. Low scores reveal mismatches: a function that returns the wrong type, or a file importing something that does not exist.

The paper estimates this by checking whether test cases pass — tests fail when the code structure is wrong, so test accuracy directly reflects how closely the code followed the graph blueprint.

Why it works

Why the graph fixes the problem

A model writing code line by line has no memory of earlier files and no way to plan ahead. When it writes file 3, it has no record of what file 1 exported, so it guesses. When it writes a function, it does not know if the caller will pass the right type. The result is mismatched types, missing imports, and unused code.

The graph solves this by making all relationships explicit BEFORE code is written. Once the model has a graph showing that file A calls function foo from file B, and foo expects an integer, the code generation stage is constrained — it must write file A in a way that calls foo correctly, and it must write foo to accept an integer. The model no longer guesses. Additionally, when a test fails, the graph tells the localization step exactly which files are involved in that test, so repairs are fast and do not break unrelated code.

The structure consistency score

First in words:

For each function signature mismatch, subtract a penalty. For each correct import and data flow, add credit. The total is how closely the code followed the graph.

Then the compact form:

consistency = (correct_sigs + correct_imports + correct_types) / (total_functions + total_imports) * 100

Every symbol:

correct_sigscount of functions with the right input and output types
correct_importscount of imports that match what the graph showed
correct_typescount of data values flowing between functions as planned
total_functionstotal number of functions in the graph
total_importstotal number of imports needed
A tiny worked example
A small repo has 10 functions and 5 imports.
Generated code: 9 functions have correct signatures, 4 imports are correct, 8 data flows match the plan.
Consistency = (9 + 4 + 8) / (10 + 5) * 100 = 21 / 15 * 100 = 140 / 100 = does not work this way.
Better: count correct elements = 9 + 4 + 8 = 21 right elements. Total possible = 10 + 5 + 12 (data flows) = 27. Score = 21/27 = 77.8% consistency.
If tests pass, consistency is high. If tests fail on import errors, consistency is low because the code did not follow the graph.

Consistency is measured by how many tests pass — tests fail when signatures, imports, or data types do not match the graph.

What can go wrong

What can go wrong

Graph is incomplete or wrong. If the planning stage builds a graph that is missing files or has the wrong data types, the code generation stage will faithfully build the wrong thing, because the generator follows the graph structure as a blueprint. A bad graph leads to bad code because there is no other source of truth for how pieces should connect. The model must correctly understand the task during planning.
Code does not match the graph structure. Even with a good graph, the generation stage might ignore it and write code that violates the graph. Tests catch this, but fixing requires re-running the entire generation, not just patching one file.
Circular dependencies in the graph. If file A imports file B which imports file A, the system cannot generate either correctly. The planning stage must avoid building cycles.
Done right: graph is precise, generation respects it, tests validate. When the planning stage builds an accurate graph (all files, correct types, no cycles), and the generation stage follows it, and tests run successfully, the result is a large, integrated repository that works.
What a runnable demo should prove

What a runnable demo should prove

Build a small task (e.g., a to-do app) where you specify the high-level features: a database handler, an API server, and a command-line interface. Have the model plan the graph (which files exist, what each function does, what types flow between them). Then have the model generate the full code. Finally, run the test suite (or write simple tests that check each file can be imported, each function has the right signature, and basic operations work).

Measure how many lines were generated, how many tests pass, and how many of the required features are present. Compare to a baseline that generates code without building the graph first.

code_completeness = (lines_generated / lines_in_spec) * (test_pass_rate / 100) * (features_present / features_required)

The demo must show that explicit graph planning generates far more code, with far fewer broken imports and type errors, than models that write without a plan.
