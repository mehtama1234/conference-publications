Code2Video: Educational Video Creation via Code

Instead of drawing pixels, write executable code that renders educational videos with precise structure and transitions.

Paper explainersAll themesAgents & Tool Use

Teaching videos fail when AI tries to paint them pixel by pixel. This paper argues that educational videos need structure, not just visual polish. Code2Video uses a team of three agents to generate videos by writing Python programs: one plans the story, one writes runnable code, and one watches the result and fixes the layout. The result beats direct code generation by 40 percent and matches human tutors.

Why pixel-by-pixel video generation fails

When AI generates videos by placing colors onto a canvas one pixel at a time, it struggles with the deep structure that makes a teaching video work. A tutorial about code needs precise timing between the speaker's words and what appears on screen. It needs the diagram in the right spot, the code highlighted correctly, the text legible. A beginner trying to use pixel-based models learns this the hard way: the model forgets to align the spoken explanation with the visual, loses coherence mid-video, or paints text so blurry it defeats the purpose.

Rendering pixels also ignores the fact that an educational video is built from semantic units: a code snippet, a label, a shape. These are not paint. They are objects with identity. A naive approach treats the video as raw image data, and the model has no way to understand that 'this is a line of code' and 'this line should stay in place while the explanation advances.'

The fix. Instead of painting pixels, generate videos by writing executable Python code that controls what renders and when.

What it actually does

Input: lecture content

Receive slides, transcript, learning objectives, domain knowledge.

Planner: temporal storyboard

Break the lecture into scenes with timing, captions, and visual cues.

Coder: executable Python

Convert each scene into Python code that renders objects, text, and timing.

Catch rendering errors (undefined functions, out-of-bounds positions) and fix them automatically.

Critic: layout refinement

Show the rendered video to a vision-language model, ask it to map desired changes to code edits, and apply them.

What the paper changes

The one thing the paper changes

The paper swaps the medium of generation. Instead of writing pixel colors directly, the agent writes Python code that calls rendering functions. Instead of a neural network outputting colors, a code generator outputs function calls. The rendering environment (code execution, not diffusion) becomes the controller.

the object it moves  =  rendering medium: pixels to code
The hidden quantity

Visual anchor: mapping sight to action

measured quantity  =  visual anchor relationship

The Critic agent operates on a key insight: when a human sees the video and wants to change something ('move the code box left, make the text bigger'), they are describing a visible outcome. The paper calls this a visual anchor: a mapping from what you see to what code needs to change. Instead of asking the agent to predict pixels, the paper trains the Critic to say 'I see the text is cramped, so I will edit the font_size and x_offset variables in the code.'

The paper estimates this anchor by feeding the rendered video and a desired visual change (e.g. 'text should be left-aligned and larger') to a vision-language model, which outputs code edits. This turns visual feedback into semantic edits.

Why it works

Why this pipeline works: from structure to execution

Code2Video outperforms direct pixel generation because code makes the structure explicit. When the Planner writes a storyboard, it builds a semantic outline: 'scene 3 shows the algorithm step by step, with captions timed to 5-second intervals.' This is knowledge, not just pixel positions. The Coder then translates each semantic scene into Python objects: draw_box, draw_text, set_position, advance_time. Because the code is both executable and editable, if a position is wrong, the Critic can change the x variable directly, instead of trying to repaint the entire frame—a much simpler edit.

The Critic's visual anchoring solves a hard problem in video editing: how does an AI know which code line to change when the video looks wrong? By asking a vision-language model 'what should I change to fix this layout?', the Critic grounds the edit in visual intent, not trial-and-error. This approach is cheaper than retraining a pixel-generation model, because code edits are discrete and targeted, whereas retraining a neural net requires many forward and backward passes.

The scope-guided auto-fix ensures the code actually runs. If the Coder generates a call to a function that does not exist or puts a text box at position -50 (off-screen), the auto-fix catches it and patches the code before execution. This eliminates a major source of failure in code-generation tasks: generating syntactically valid but semantically broken code.

The feedback loop in one equation

First in words:

output_video = execute(code); desired_edits = VLM(render(code), visual_goal); code_next = apply_edits(code, desired_edits)

Then the compact form:

code_next = code + sum_{i=1}^{N} alpha_i * edit_i(code)

Every symbol:

codethe Python source for rendering (objects, positions, timing)
edit_ia discrete code change proposed by the Critic (e.g., x_offset += 10)
Nthe number of visual mismatches the Critic identifies
alpha_ia binary flag: apply this edit or not (1 or 0)
code_nextthe refined code after all Critic edits
A tiny worked example
Coder generates: def render_scene(): draw_text('Algorithm', x=100, y=50, font=12)
VLM watches the video and sees: text is too small and hard to read.
Critic proposes edits: [set font to 16, move text to x=120]
Apply both: draw_text(..., x=120, font=16) -> text is now bigger and better positioned.
Next iteration: Critic checks again; if layout is good now, no more edits needed.

The code is iteratively refined by visual feedback. Each step is a discrete semantic edit, not a numeric weight adjustment.

What can go wrong

What can go wrong

Rendering functions not in scope. If the domain (e.g., math visualization, circuit diagrams) uses unfamiliar rendering functions, the Coder may call functions that do not exist. The auto-fix must know which functions are available in the environment, or it cannot repair the code.
Critic feedback loop stalls. If the vision-language model cannot reliably interpret what 'better' means in context (e.g., 'this flow diagram should branch, not stack'), the Critic's edits may not converge, because the model is guessing at intent instead of receiving a clear visual target. The visual anchors must be unambiguous.
Timing becomes out of sync. If the Coder does not respect the Planner's timing cues (e.g., advancing scenes too fast), no amount of layout fixing will make the tutorial coherent. The Coder must faithfully read timing from the storyboard.
Done right: layered verification. The pipeline works when each agent's output is verified before the next step: Planner checks for scene clarity, Coder tests code execution, auto-fix validates all function calls and positions, Critic confirms layout matches intent.
What a runnable demo should prove

What a runnable demo should prove

Build a minimal educational video generator for a specific domain (e.g., simple Python loops, basic algebra). Start with a lecture transcript or slide deck. Run it through the Planner to get a storyboard. Have the Coder generate Python code that calls a small set of known rendering functions (draw_box, draw_text, set_position, advance_frame). Execute the code to render frames. Show a teacher or student the output and ask for one specific visual fix (e.g., 'move the equation lower, make it bigger'). Feed that feedback to the Critic, watch it propose code edits, apply them, and re-render. The demo succeeds if the second version is noticeably better, because the Critic correctly mapped the visual intent to concrete code changes, proving the visual-anchor mechanism works.

knowledge_gain = percent_of_tutorial_concepts_a_new_learner_understands_after_watching

A good demo should show that visual feedback from the Critic actually improves the tutorial's clarity, because the Critic's edits reduce ambiguity in layout and timing.
