SPARTA: Automatic Multi-hop Benchmark from Tables and Text

SPARTA builds large, complex question-answering benchmarks automatically by extracting facts from text, synthesizing executable queries, and enforcing multi-hop reasoning depth.

Paper explainersAll themesDatasets & Benchmarks & Evaluation

Most question-answering benchmarks today are hand-built, small, and test only shallow reasoning (usually two hops or fewer). Real-world questions need to jump across multiple tables and documents and use complex operations like averaging or grouping. SPARTA solves this by automating the entire process: it mines facts from text, enriches tables with those facts, generates thousands of complex nested queries, and validates each one to ensure it actually works.

Zero assumption version

Hand-made benchmarks are small, shallow, and error-prone

Today's question-answering benchmarks are built by paying people to write questions and answers by hand. This process is slow, expensive, and produces only a few thousand examples. Because human annotators naturally write simpler questions, these benchmarks test only shallow reasoning—questions that answer in one or two steps.

A naive approach would be: hire more people to write harder questions. But humans are inconsistent, make mistakes, and run out of ideas. The questions end up shallow anyway because deeper multi-hop reasoning is cognitively demanding to invent and verify by hand.

The problem. Hand-built benchmarks are small, shallow, and error-prone; scaling them is prohibitively expensive.

The algorithm as a flow

What it actually does

Stage 1: Add facts from passages to tables

Mine atomic sentences from text passages. Extract subject-predicate-object facts. Link each fact to a table column so it is SQL-addressable.

Stage 2: Synthesize nested SQL

Generate executable SQL queries with exactly N nested levels (hops). Build bottom-up: validate leaf subqueries first, then wrap them in outer predicates.

Stage 3: Ensure executability

Run each query. If it returns nothing, backtrack: remove predicates in reverse order until the query succeeds. Rewrite the offending clause.

Stage 4: Verbalize to English

Feed each validated SQL query to a language model to rewrite it as a fluent, natural-language question.

Stage 5: Test the strongest current models

Benchmark current models on SPARTA. Observe how performance drops on deep, complex reasoning compared to shallow benchmarks.

What the paper changes

The one thing SPARTA changes

Instead of a human writing one question at a time, SPARTA automatically generates thousands. Each question is synthesized from a template of SQL operations (joins, filtering, aggregation, grouping) at a guaranteed nesting depth.

The hidden quantity

Query hop depth—the complexity SPARTA controls

measured quantity  =  Hop depth (nesting level)

Hop depth is the number of nested steps a question requires. A one-hop question reads one table directly. A two-hop question joins two tables. A three-hop question chains three tables together. Most hand-built benchmarks accidentally stay shallow (one or two hops). SPARTA controls hop depth explicitly: when generating a query, it decides in advance how many nested levels to build, then constructs exactly that many.

The paper estimates hop depth by counting nested SQL predicates. A query like SELECT name FROM players WHERE team_id IN (SELECT team_id FROM teams WHERE owner='Smith') is two hops (the inner SELECT counts as one hop; the outer WHERE counts as the second). SPARTA's synthesizer picks a target hop count, builds the query to match it, and validates it.

Why it works

Why the pipeline generates deep, correct questions

SPARTA's core trick is post-order traversal: build queries from the leaves upward, not top-down. A human starts with the final question and works backward to the tables (top-down). An LLM building a query top-down faces an unsolvable problem: it must invent the inner query first, validate it without knowing what the outer query needs, then hope the pieces fit. This causes errors because the inner query might return the wrong data type or incompatible rows, forcing the LLM to restart. The outer query then fails silently, and the LLM has wasted LLM calls trying to patch incompatible pieces.

SPARTA inverts this: the LLM builds the innermost query first (a single table lookup), validates it works, then wraps it in the next layer of logic, validates again, and repeats. Each intermediate step is guaranteed executable because SPARTA checks it immediately. This enforces depth gradually: to get a three-hop question, the LLM must successfully assemble three validated layers, one on top of another.

When a query fails—returns zero rows or violates logic—SPARTA uses provenance-based refinement: it peels off predicates in reverse order until the query succeeds, then rewrites the offending clause to make it work. This is like debugging by undoing changes one at a time and restarting from the last stable state. The result is always executable, always deep, and always grounded in the data.

Math after the picture

The query synthesis equation

First in words:

Query cost = sum of LLM calls for each validated subquery, minus failed attempts recovered by backtracking.

Then the compact form:

total_cost = sum_i (calls_to_generate_i + calls_to_validate_i) - sum_j (calls_wasted_by_j_before_backtrack)

Every symbol:

calls_to_generate_iLLM invocations to synthesize subquery i
calls_to_validate_iinvocations to test if subquery i is executable
calls_wasted_by_j_before_backtrackwasted calls if subquery j failed and SPARTA had to rewind
A tiny worked example
Suppose we want a 3-hop query. Build leaf (5 calls to generate + 1 call to validate = 6 calls, succeeds).
Wrap in second level (3 calls to generate + 1 to validate = 4 calls, succeeds).
Wrap in third level (4 calls to generate + 1 to validate = 5 calls, fails on first try, backtrack). Rewind, lose those 5 calls.
Rewrite third level (2 calls to rewrite + 1 to revalidate = 3 calls, succeeds).
Total cost: 6 + 4 + 5 (wasted) + 3 = 18 LLM calls. Post-order saves calls because SPARTA validates incrementally; top-down would validate the outer query twice (before inner was ready) and fail.

Post-order validation means each intermediate query is executable before the next layer is added, so SPARTA avoids dead-end searches.

What can go wrong

What can go wrong

Query returns empty result. The LLM synthesizes valid SQL that matches the schema but returns zero tuples (no data satisfies the predicates). SPARTA handles this: it backtracks, peels off the last predicate, re-runs the query, and if it now returns rows, rewrites the offending clause to be less restrictive.
Hop depth is not actually deep. An LLM generates a query with syntactic nesting but shallow logic—for example, a three-level nested query where the inner two levels are trivial (SELECT * FROM table). SPARTA enforces realistic structure by confining generation to post-order traversals, which means each level must add a real predicate, not filler.
The question does not sound natural. The verbalization step (translating SQL to English) can produce awkward phrasings. SPARTA mitigates this by using a language model fine-tuned on natural questions, not a rigid template engine.
Done right. SPARTA produces thousands of executable, deep, natural-sounding questions in weeks, not months, with 75% fewer human annotations than manual methods.
What a runnable demo should prove

What a runnable demo should prove

Write a small dataset: one source table (e.g., NBA player information) and one enriched passage. Implement SPARTA's pipeline: extract facts from the passage, add them as grounding tuples, synthesize a 3-hop SQL query using post-order traversal, run it against the tables, and rewrite it to English. Then pick a baseline model (e.g., GPT-3.5-turbo with retrieval) and measure its F1 score on your generated questions. You will see the model's accuracy drop compared to shallow benchmarks.

F1_score = 2 * (precision * recall) / (precision + recall), where precision = correct_answers / predicted_answers, recall = correct_answers / total_answers

The demo must make it impossible to miss: when questions demand three or more hops, current models fail.
