DDP-WM: Disentangled Dynamics Prediction for Efficient World Models

Split scene changes into two types: the few pixels affected by robot actions and the many unchanged background pixels, so you only compute expensive predictions for what matters.

Paper explainersAll themesRobotics & Control

Robots need world models (computer programs that predict what the camera will see after the robot moves). But the best current models use dense Transformers (neural networks that look at every pixel and compare it to every other pixel), which are slow. This paper shows that most of a scene stays still—only a small region changes when the robot acts. By predicting those two things separately with different-sized computations, the model runs 9 times faster while actually working better.

Zero assumption version

Dense models waste computation on still pixels

A robot planner needs to predict what the world will look like after it acts. The best way to do this is with a world model: a neural network trained on video that learns to predict the next camera frame given the current frame and an action. Model-predictive control (MPC) uses this repeatedly: try 100 different action sequences, simulate each one five steps into the future, pick the sequence that reaches the goal, and execute the first action.

Today's best world models use Transformers (a type of neural network) that work on pre-trained image features (already-extracted visual patterns from a big model like DINOv2). The problem: Transformers compute interactions between every pair of features in the image. If the image is 32 by 32 features, that is over one million pairs. For real-time robot control you need this to run in 50 milliseconds. It does not.

A naive alternative: predict the whole next frame pixel by pixel. But most pixels stay the same—the background does not move. You end up computing where the table will be (nowhere, it is still there) over and over. That is the waste.

The method. Predict primary dynamics (where the robot caused motion) and background updates (slowly changing surroundings) with two separate, differently-sized neural networks, so the cheap one handles the 90% that barely changes.

The algorithm as a flow

What it actually does

History fusion

One cross-attention layer folds the last 4 frames into a velocity and acceleration context.

Dynamic localization

A small neural network identifies which image regions contain action-driven motion (the block, not the table).

Sparse primary prediction

A Transformer processes only the hot regions flagged by localization, predicting exact next-frame features there.

Low-rank background correction

Cross-attention asymmetrically updates background features based on primary motion (one direction only, cheap).

Planner samples action sequences

MPC uses the merged prediction to score 100 action sequences in real time, picks the best one.

What the paper changes

What the paper changes

Instead of a dense Transformer that computes interactions between all image features, DDP-WM uses two separate prediction paths: a small, sparse Transformer for primary dynamics and a cheap cross-attention module for background. The routing decision (which pixels are primary vs. background) is learned by the network.

The hidden quantity

The hidden quantity: Sparsity of primary dynamics

measured quantity  =  fraction of features driven by action

The paper measures how much of the image actually changes because of the robot's action versus how much is passive background evolution. In their experiments, on the Push-T task (a robot pushing a block on a table), only about 5–10% of the image features correspond to the moving block. The rest is the table, walls, lighting—things that barely move.

The paper finds this ratio by looking at prediction errors: where does the dense model (which sees the whole image) actually spend its computation? It shows that even though the dense Transformer computes over one million feature interactions, almost all those interactions involve pixels that will not change. The low-rank correction module (a mathematical trick that compresses those redundant updates) reveals this waste.

Paper reading. The paper performs a PCA (principal component analysis, a dimensionality-reduction technique that finds the main directions of variation) on the internal feature evolution across Transformer layers. Most features vary along almost none of those main directions, indicating low rank, low information content, and thus good targets for compression.
Why it works

Why it works: Irreversible information flow

The core insight is that background updates must happen after primary dynamics are computed. When the robot pushes a block, the table behind the block shifts slightly in the image (parallax), the shadow moves, the reflection changes. But all of these are secondary consequences of the block moving. The background cannot move before the primary motion is resolved.

This causal ordering means you can use cheap, asymmetric math. Instead of a full Transformer (which lets every pixel influence every other pixel in both directions), the low-rank correction module uses a one-way cross-attention: primary features serve as queries, background features serve as keys and values. Information flows from primary toward background, never backward. Mathematically, this compresses the background update into a rank-r matrix (a small set of patterns) multiplied by the primary features. Computing it costs roughly r times W times H, instead of W squared times H squared, where W and H are image dimensions. For a 32 by 32 image, that is roughly 2,000 operations instead of 1 million.

The second payoff is a smooth path through the search space. When MPC tries different action sequences, it needs the loss function (a measure of distance from the goal) to have a smooth path—no cliffs, no random jumps. A full Transformer's search space is jagged because every pixel interacts with every other. By splitting, the primary prediction stays precise (smooth Transformer loss), and the background update is low-rank (smooth matrix math). The planner can confidently search.

The low-rank correction formula

First in words:

background update equals primary features times a small matrix plus a bias

Then the compact form:

z_bg_next = z_bg + U V^T z_primary + b

Every symbol:

z_bgbackground features at current time
z_bg_nextbackground features at next time
z_primaryprimary features (motion region) after prediction
Ua tall, thin matrix (small rank r)
V^Ta short, wide matrix (r small dimensions)
ba bias vector
rthe rank, typically 8 to 32 (much smaller than image width/height)
A tiny worked example
Example: background feature at pixel (5,5) starts at 0.8.
Primary features in the block region sum to 1.2 (after Transformer prediction).
Low-rank U has shape 100 × 10 (100 background features, rank 10).
V^T has shape 10 × 64 (rank 10, 64 primary features).
Compute: U @ V^T @ [1.2, 0.5, ...] = a 10-D intermediate, then multiply by 100-D U. Cost: 10 * 64 = 640 ops, not 100 * 64 = 6400.
Background feature becomes 0.8 + update_amount = 0.82 (slight shift due to block motion). Same update computed 1000x faster.

The multiplication U @ V^T is never formed as a full matrix; instead, V^T @ z_primary computes first (cheap), then U @ result (cheap). This lazy multiplication is why it avoids forming the dense matrix.

What can go wrong

What can go wrong

Occlusions break the model. If a small object suddenly hides a large region (a hand covering a block), the localization network must learn that the covered region is now primary, not background. Early training can confuse these cases, causing inaccurate predictions.
Rank too small loses structure. If the rank is set too low, the low-rank matrix cannot represent complex background changes like multiple objects casting shadows in different directions. Prediction accuracy degrades.
Rank too large wastes speedup. If r equals the full image dimension, the low-rank correction becomes dense again, and the whole speedup is lost.
Learned balance works well. The paper trains the localization network, sparse Transformer, and low-rank module together (in stages), allowing them to learn what counts as primary versus background for each task. On Push-T, this naturally separates the block from the table.
What a runnable demo should prove

What a runnable demo should prove

A concrete demo would train DDP-WM on a single robot task (e.g., pushing a block to a goal on a table), then run model-predictive control: at each timestep, sample 100 random action sequences of length 5, simulate each one with the learned world model, score them by distance to the goal, and execute the top action. Plot the success rate (did the block reach the goal?) and the wall-clock time for the full episode.

speedup = time_dense_model / time_ddp_wm; success = (goals reached / 100 episodes)

The demo must make it impossible to deny that the model runs at least 5 times faster because most of the image does not change, so expensive computations only run on the few pixels that do. And planning finds better solutions because it can now sample 100 action sequences instead of 20.
