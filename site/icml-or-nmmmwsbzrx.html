Stream RAG: Instant and Accurate Spoken Dialogue Systems with Streaming Tool Usage

This paper teaches a spoken assistant to start preparing a tool call before the speaker finishes the question.

Zero assumption version

Spoken assistants need outside facts, but waiting for a full query adds too much delay

A speech-to-speech assistant can sound natural, but it can also invent facts if it answers without checking outside sources. Tool grounding solves that factual problem, yet tool use often slows the conversation because the system waits for the full utterance, decides on a search, runs the search, and only then starts the spoken answer.

The hard part is deciding early without jumping too early. While the user is still speaking, the system has only a partial query. The paper asks whether the assistant can start preparing the tool request before the utterance ends so that factual grounding arrives sooner.

The idea in one sentence. Predict the tool request from partial speech, because some search intent becomes clear before the user has finished the sentence.

The algorithm as a flow

What it actually does

Listen to streaming speech

Receive the user's words incrementally rather than waiting for the final full utterance.

Predict the likely tool request early

Form a search or retrieval request from partial speech when enough intent is already visible.

Run retrieval in parallel

Start the tool call before the utterance ends so that retrieval time overlaps with the remaining speech time.

Summarize the returned evidence

Turn the retrieved text into a spoken reply that answers the user directly.

Finish with a grounded spoken response

Speak after retrieval finishes, using the returned facts so that the answer depends on evidence rather than unsupported recall.

What the paper changes

What the paper changes

The paper changes when tool use begins. Instead of placing retrieval only after the full speech query is complete, it starts retrieval during the query whenever early evidence is sufficient.

the object it moves  =  the timing of tool invocation in spoken dialogue
The hidden quantity

The hidden quantity: overlap between listening and retrieval

measured quantity  =  how much search time can be hidden inside the tail of the user's speech

The main win in the paper comes from overlap. If tool retrieval starts during the final portion of the user's utterance, the assistant can hide some of the search delay inside time that the user is already spending speaking.

This quantity matters because the assistant needs two things at once: early enough retrieval to save time and late enough retrieval to avoid guessing the wrong topic. The useful operating point is where enough intent has appeared to launch a reliable search while enough speech time still remains to hide part of the wait.

Why it works

Why early tool prediction can work

Many spoken questions reveal their topic before the final word arrives. A question such as a weather request, a fact lookup, or a calendar query often contains enough early cues for a search to begin. Starting retrieval at that point saves time because the assistant no longer waits for a fully completed utterance before taking the first tool step.

The design still needs a controlled trigger because premature retrieval can waste time on the wrong query. The paper's training setup teaches both when to launch the tool call and how to turn the returned text into a spoken answer, so the system learns a usable boundary between early action and over-eager action.

Math after the picture

The core equation

First in words:

Reply delay after the user stops speaking equals the total retrieval delay minus the part hidden during the remaining speech time.

Then the compact form:

post_speech_wait = retrieval_delay - overlap_time

Every symbol:

post_speech_waithow long the user waits after finishing the question
retrieval_delayhow long the tool call would take if it started only after speech ended
overlap_timehow much of that delay is hidden while the user is still speaking
A tiny worked example
Suppose the tool call needs 1.0 second if it starts after the user stops speaking.
Suppose the system starts retrieval 0.6 second before the utterance ends, so overlap_time is 0.6 second.
Then post_speech_wait is 1.0 minus 0.6, which is 0.4 second.
The user now waits 0.4 second instead of 1.0 second after finishing the question.
The example shows why overlap matters because hidden retrieval time directly reduces audible delay.

This equation isolates the timing idea. The answer still needs good retrieval quality, but the main latency gain comes from overlap.

What can go wrong

What can go wrong

The search starts on the wrong partial query. If the early words support several possible topics, the tool call may return irrelevant evidence, so the assistant wastes time and may need a second search.
The user changes direction late in the sentence. A correction near the end of the utterance can invalidate the early search, which means the saved time disappears and the system may answer the wrong question.
The spoken summary omits the key fact. Even with good retrieval, a weak spoken summary can drop the most useful result, so the final answer loses the benefit of the tool call.
Done right. The method works when early topic cues are strong enough to launch a reliable search and the summary step stays tightly tied to the returned evidence.
What a runnable demo should prove

What a runnable demo should prove

Build a speech assistant that answers factual spoken questions with a retrieval tool. Compare a baseline that waits for the full utterance against a streaming version that launches retrieval from partial speech. Measure answer correctness, time from end-of-speech to start-of-response, and the share of searches that had to be restarted because the early query was wrong.

The demo proves the paper's point if the streaming version keeps or raises factual answer quality while reducing post-speech wait, because the tool work is shifted into time that would otherwise be idle.

latency_gain = wait_after_speech(baseline) - wait_after_speech(streaming_retrieval)

A good demo should include cases where the user changes direction late, because that is where the early-trigger rule is truly tested.
