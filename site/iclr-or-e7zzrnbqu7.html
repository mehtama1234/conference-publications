Sharing State Between Prompts and Programs

Let a language model write Python code that can read and change program variables directly, shrinking the job from separate natural-language and code worlds into one.

Paper explainersAll themesAgents & Tool Use

Today, when you ask an LLM (a language model) to write a Python program, the model generates text instructions in natural language. But the running program is separate code. For them to work together, programmers must manually translate between what the LLM says and what the program can do. This paper removes that translation work by letting the LLM write code that can see and touch the program state—the variables and objects the code is using—directly.

Zero assumption version

The interoperability tax

Right now, an LLM writes natural language—sentences and instructions. A Python program needs code—variables, loops, function calls. These two worlds speak different languages. When you ask an LLM to write a Python program, it outputs text that a human must read, understand, and hand-translate into actual code that runs. Or the LLM outputs Python directly, but it cannot see the running program's state—the variables that already exist, the data being processed, the answers computed so far.

A naive approach: have the LLM write natural language instructions (in a prompt), and have a separate Python script parse those instructions and carry them out. The LLM says 'add ten to the counter,' and the script finds where 'counter' lives, adds ten, and returns the result to the LLM. But that means every time the LLM wants to do something, the programmer must write custom translation code. For a program with ten steps, that is ten translation layers. For a complex reasoning task, it is hundreds.

The work gap. The paper removes the translation step: let the LLM write actual Python code that reads and modifies the program's live variables directly.

What the paper changes

What the paper changes

The paper changes what the LLM is allowed to write. Instead of outputting natural language instructions that a separate script must parse, the LLM now outputs actual Python code that can directly access program variables—as if those variables were already defined in the LLM's training data.

The hidden quantity

State visibility

measured quantity  =  How much of the running program the LLM can see and change

Before this paper, the LLM's world was isolated: it could only know what the programmer told it in the prompt text. It could not see live data, could not change variables, could not trace a loop's progress. Visibility (how much of the program the LLM can see) was zero.

This paper measures visibility as the set of variables and objects the LLM's code can access at runtime. If the program has a counter, a list, and a result dictionary, and the LLM can read and write all three, visibility is complete for those three. The paper shows that full visibility—letting the LLM see and touch everything—does not break the program; it helps the LLM generate correct code because it has the actual data to work with.

Why it works

Why this works: direct access cuts the middleman

The bottleneck in the old system was translation: every time the LLM wanted to do something, a human or script had to decode the natural language, figure out which variables mattered, run the operation, and report the result back. That translation step is error-prone (misunderstanding the intent), repetitive (the same parsing logic for every command), and verbose (the code to handle each case).

By giving the LLM direct access to live program variables, the paper removes the translation layer entirely. The LLM's code runs in the same namespace as the program's data. When the LLM writes a line of Python code like incrementing the counter, it is not writing a natural-language instruction for a parser; it is actual Python code that the runtime binds to the real counter variable. The program still owns the data; the LLM just reads and writes it through the normal Python rules.

This works because the LLM has learned to write Python syntax. The model does not need to learn a new language or special commands; it writes regular if-statements, loops, and variable assignments. The programmer sets up the bindings once (saying 'here are the variables'), and then every piece of LLM-generated code automatically has access, no per-operation translation needed.

The binding formula

First in words:

For each variable name in the shared state list, the runtime creates a reference from the LLM-generated code's namespace to the actual program object. If the LLM writes 'counter equals counter plus 1', and 'counter' is in the shared state, the runtime wires that to the live counter in the program, and the increment happens on the real data.

Then the compact form:

LLM_code_namespace[var_name] := program_memory[var_name] for each var_name in shared_state

Every symbol:

LLM_code_namespacethe variables the LLM code can access when it runs
program_memorythe actual variables in the running program
var_namethe name of a variable (e.g., counter, results_list)
shared_statethe list of variables the programmer marked as accessible to LLM code
A concrete example
Programmer says: shared_state = [counter, user_list, result]
LLM generates: counter = counter + 1; result.append(counter)
Runtime creates: LLM_code.counter -> program.counter (same object in memory)
LLM code runs: program.counter goes from 5 to 6, program.result becomes [6]
No copy, no parse, no intermediate translation layer.

Binding happens once at setup; after that, LLM code and program speak the same memory.

What can go wrong

What can go wrong

LLM hallucinates variables. If the LLM writes 'print(unknown_var)' and unknown_var is not in shared state, the code crashes. The programmer must either add it to the shared list or catch the error.
Race conditions and state corruption. If the LLM code and the main program both write to the same variable at the same time, data can be corrupted. The programmer must decide if shared state should be read-only, write-only, or fully mutable.
LLM code is inefficient. The LLM might write slow loops or redundant copies instead of fast batch operations. Shared state does not fix bad algorithm design.
Shared state is designed cleanly. If the programmer is careful about what they expose and sets clear read/write rules, the system is safe and the LLM's code runs at full speed.
What a runnable demo should prove

What a runnable demo should prove

Build a simple program: a counter, a list of numbers, and a result dictionary. Ask an LLM to write code that increments the counter, sums the list, and stores the sum in the result. Expose the counter, list, and result as shared state. Run the LLM's generated code. Check that the counter incremented, the result holds the correct sum, and no manual translation was needed.

code_reduction = 100 * (1 - (lines_written_with_Nightjar / lines_written_manual))

The demo succeeds when the LLM's code runs without human intervention, accesses the real variables, and produces correct results in fewer total lines than a manually-written program, because the shared state eliminates the translation code the programmer would have written to bridge the LLM's output and the program's state.
