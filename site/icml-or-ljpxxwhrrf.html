Vision2Web: A Hierarchical Benchmark for Visual Website Development with Agent Verification

Measure website-building agents across static pages, interactive frontends, and full-stack projects, then verify the result with both browser actions and visual judging so that evaluation covers real end-to-end work.

Paper explainersAll themesAgents & Tool Use

Website-building agents now produce code from screenshots, patch broken layouts, and assemble full applications, yet evaluation still lags behind the task. A simple screenshot match can miss broken interactions, while a hand-written unit test can miss whether the page actually looks right. Vision2Web builds a layered benchmark and a two-part verification system so that website agents are judged on the visual result, the interactive behavior, and the full workflow rather than on one narrow check.

Why visual website agents are hard to evaluate well

Building a website from visual input is a long chain of decisions. The agent must read the design, choose layout structure, write code, connect interactions, and sometimes wire server logic. A weak evaluator may approve a page that looks close in one screenshot even when navigation, responsiveness, or form logic is broken.

The opposite mistake also happens. A strict scripted test may reject a working site because it checks one exact implementation path instead of the visible and functional outcome. For this reason, website-agent evaluation must cover both appearance and behavior, and it must do so at several task depths rather than one flat benchmark level.

The paper's move in one sentence. Create a hierarchical website benchmark and verify each result with both an acting browser agent and a visual-language judge so that different failure types are caught by different evaluators.

The algorithm as a flow

What it actually does

Collect real website tasks

Turn real websites into benchmark targets so that the tasks reflect practical structure and styling choices.

Organize them into three levels

Separate static reproduction, interactive frontend work, and long-horizon full-stack work because each level stresses a different agent ability.

Run coding agents under comparable setups

Evaluate several agent frameworks on the same tasks so that differences come from agent capability rather than task choice.

Check behavior with a browser-acting verifier

Let an automated browser complete workflows and inspect the result because visible interaction failures often escape screenshot-only checks.

Check appearance with a visual judge

Ask a vision-capable judge to compare the produced site to the target so that styling and layout mistakes are also measured.

The hidden quantity

The hidden quantity

measured quantity  =  whether the produced site matches the target in both appearance and user workflow

A finished site can look close while behaving badly, or behave correctly while looking far from the target. The true quality signal therefore hides behind several partial observations. No single check sees the whole result.

Vision2Web tries to recover that hidden overall quality by combining two views. The browser verifier tests whether a user can actually complete the workflow, and the visual judge tests whether the site still resembles the target. Combining them helps because each one catches failures that the other can miss.

Why it works

Why this works: use task depth and verifier diversity together

A hierarchical benchmark tells you where an agent starts to fail. If the agent can reproduce a static page but collapses on interactive flows, the missing skill is different from an agent that already fails on basic layout. This structure makes the benchmark diagnostic because each level isolates a distinct part of website development.

The paired verifiers matter for the same reason. A browser-acting verifier is useful because it exposes broken clicks, bad state updates, and failed forms. A visual judge is useful because it catches layout drift and styling mismatch. Using both gives a better signal because one checks what the user can do and the other checks what the user sees.

Reward results that are both functional and visually faithful

First in words:

A compact summary is to score a produced website by combining workflow success, visual agreement with the target, and success on higher-difficulty task levels.

Then the compact form:

web_score(site) = behavior_score(site) + alpha * visual_score(site) + beta * level_score(site)

Every symbol:

web_score(site)overall value of one generated website result
behavior_score(site)how well the browser verifier can complete the required workflows
visual_score(site)how closely the produced site matches the target appearance
level_score(site)credit for succeeding on harder benchmark levels
alpha, betaweights on visual agreement and task-depth credit
A tiny worked example
Site A looks close to the target but its checkout button fails.
Its behavior score stays low even though its visual score is high.
Site B looks slightly less polished but completes the full checkout flow.
Its total score can be higher because working interaction matters for end-to-end development.
The benchmark therefore avoids rewarding cosmetic similarity alone.

The paper uses richer verification details, but this summary captures the design logic that appearance and behavior both belong in the final judgment.

What can go wrong

What can go wrong

The verifier can still miss edge cases. A browser trace covers only selected workflows, so unusual user paths may remain untested because the agent verifier cannot exhaust every interaction.
Visual judgment is still approximate. A visual judge may disagree with a human on subtle style details because some design choices are subjective.
Benchmark coverage may drift behind real practice. Website tools and design patterns change quickly, so the task set must be refreshed or it will stop reflecting the current workload.
Done right. The benchmark matters because it evaluates a website as a working product, not only as code or only as a screenshot.
What a runnable demo should prove

What a runnable demo should prove

Build a small benchmark with one landing page task, one multi-page interactive task, and one simple full-stack task such as login plus item creation. Evaluate the same coding agent with a visual judge and a browser-acting verifier, then compare the combined score with a screenshot-only baseline.

The demo should show cases where screenshot matching approves a broken site and cases where browser actions catch the failure. It should also show cases where the browser path works but the page still looks wrong, because both sides of website quality matter.

verification_gain = dual_verifier_error_caught - single_verifier_error_caught ; fullstack_gap = static_score - fullstack_score

A good benchmark for website agents should expose the exact step where visual coding turns into a real product task.
