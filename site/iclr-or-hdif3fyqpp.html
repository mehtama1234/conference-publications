Null-Space Filtering for Data-Free Continual Model Merging

When merging multiple specialized models into one, filter out the overlapping changes to prevent forgetting old knowledge while learning new skills.

Paper explainersAll themesLLMs & Foundation Models

Companies often fine-tune large models separately for different tasks: one for customer support, one for product recommendations, one for content moderation. Someday you need a single model that can handle all of them. Data-free continual model merging tries to fuse these independent models into one evolving backbone without looking back at the original training data. NUFILT does this by using null-space filtering: it mathematically identifies which parts of each new task's changes overlap with earlier tasks' changes, filters those overlapping parts out, then adds only the truly fresh signals needed for the new task.

Zero assumption version

The merging trap: grow or keep what you have

You train a large model on one task and it works well. Then you train the same model on a second task and it works too, but now it forgets the first task (this is called catastrophic forgetting). A naive solution is to average the two trained models together, but averaging makes both tasks worse — the weights land in a zone that satisfies neither task's learned patterns.

The harder version: merge multiple fine-tuned models into one shared backbone that keeps growing with new tasks, without ever seeing the original training data again. Existing approaches try to keep the backbone "transparent" (remember old tasks) but end up too rigid to adapt to new ones, or they adapt well but trash the old knowledge.

The problem in one sentence. Merging independently trained models without data requires a way to identify which parts of each new task matter and which parts just re-learn old skills.

The algorithm as a flow

What it actually does

Collect task changes

For each new task, compute what changed in the model weights from the base model.

Find the overlap

Identify which directions in weight space that task change shares with all earlier tasks, using the null space.

Filter out shared directions

Remove those overlapping components from the new task change so it only contains fresh, new signals.

Add a lightweight adapter

Train a small LoRA layer (a low-rank change) that injects the filtered-down task signals, preserving earlier knowledge.

Merge without extra cost

Fold the adapter updates back into the backbone using simple layer-wise averaging, no extra counters or components remain.

What the paper changes

What the paper changes

NUFILT changes which directions in weight space are allowed to move when a new task arrives. Instead of letting the new task update weights anywhere, it restricts updates to a carefully chosen subspace: the null space of earlier task changes. A task change is the difference in weights between the base model and the model after fine-tuning on one task. This mathematically enforces that new learning cannot interfere with patterns learned before.

the object it moves  =  weight update directions
The hidden quantity

The null space: which directions are safe to move

measured quantity  =  null space of earlier task changes

The null space is a set of directions in weight space that point sideways (perpendicular in high dimensions) to all the changes that earlier tasks made. When you restrict a new task's weight updates to this space, you mathematically guarantee those updates cannot disturb the patterns that old tasks learned. The paper estimates this by collecting all the earlier task changes — the differences between the base model weights and the weights after fine-tuning on each earlier task — and finding the directions orthogonal to them.

A task change is the raw direction a fine-tuned model moved from the base model. NUFILT projects new task changes onto the orthogonal complement (the null space) to identify which components are truly separate and different. The paper proves these task changes approximately align with learned representation patterns, justifying why null-space filtering preserves earlier knowledge while allowing new learning.

Why it works

Why filtering preserves old knowledge while enabling new learning

Old fine-tuned models have learned to respond to data in certain ways. Those response patterns live in the weights, but they live in specific directions of weight space — directions that task changes from old tasks point toward. A new task change, if you apply it directly, might move weights in those same directions, clobbering the old behavior.

NUFILT computes which directions are orthogonal to all earlier task changes (the null space). By restricting the new task's weight updates to only this space, the algorithm guarantees zero movement in the dangerous directions. The backbone remains transparent: it responds to the old tasks the same way as before. To enable the new task, a lightweight LoRA adapter (a small layer of low-rank weight changes) is then trained. This adapter is trained with a loss function that penalizes any changes that would contradict earlier knowledge, so it learns to work within constraints set by the filtered signals. The backbone stays intact and the new adapter adds capability without collision, because it only accesses the clean null-space directions.

Finally, the adapter is merged back into the backbone using layer-wise linear averaging, which turns a temporary piece into a permanent part of the model without increasing the weight count or the cost to run inference. The whole architecture stays streamlined: new knowledge enters through null-space updates and a trained adapter, earlier knowledge never moves, and the final merge is clean.

Math after the picture

The filtering equation

First in words:

The new task change is projected onto the null space of stacked earlier task changes, retaining only the orthogonal component.

Then the compact form:

c_new_filtered = (I - T^T (T T^T)^-1 T) c_new

Every symbol:

c_newthe new task change (weight differences from fine-tuning on the new task)
Trectangular block stacking all earlier task changes as rows
Iidentity matrix (do nothing in all directions)
T^T (T T^T)^-1 Tprojection onto the subspace spanned by earlier task changes
I - ...(...)projection onto the null space (the orthogonal complement)
A tiny worked example
Suppose an earlier task moved weights in direction A by amount 1.0.
The new task wants to move in direction A by 0.4 and direction B by 0.6.
Null-space filtering removes the A component: 0.4 * (1 - 1) = 0.0.
It keeps the B component: 0.6 * (1 - 0) = 0.6.
Result: filtered task change is (0.0, 0.6). Only fresh, separate learning remains.

This projection mathematically guarantees that moving in the filtered directions does not contradict any earlier task's learned patterns.

What can go wrong

What can go wrong

Poor null-space estimate if task changes are noisy. If the task changes are computed from sparse or small data, the orthogonal directions you filter to may not actually protect earlier knowledge. The projection becomes unreliable.
Adapter capacity becomes a bottleneck. The LoRA adapter is deliberately lightweight to avoid extra counters. If the new task requires major structural changes, the adapter rank may be insufficient and performance drops.
Alignment assumption breaks if tasks are very different. NUFILT assumes task changes align with learned representation patterns. If a new task is so different that it requires learning in entirely new representational zones, the filtering may throw away important signals.
Done right: compute task changes carefully, choose adapter rank to match task diversity, validate on representative new tasks. Use enough data to estimate task changes accurately, profile the adapter rank against validation sets, and test the merged model thoroughly on new tasks you did not see during training.
What a runnable demo should prove

What a runnable demo should prove

Build a simple fine-tuning scenario: take a base vision model (or language model), fine-tune it on task 1 (e.g. cats vs dogs), then task 2 (e.g. vehicles). Compute task vectors for each. Implement null-space filtering: stack task 1's vector, compute its orthogonal complement, project task 2's vector onto that null space, and train a LoRA adapter with the filtered direction. Merge the adapter back into the base model. Measure accuracy on both tasks before and after merging.

forgetting = accuracy_task1_after_merge - accuracy_task1_on_finetune, adaptation_gap = accuracy_task2_on_finetune - accuracy_task2_after_merge

The demo must show near-zero forgetting on task 1 while keeping task 2 accuracy close to independent fine-tuning — filtering works when both old and new skills remain sharp in a single model.
