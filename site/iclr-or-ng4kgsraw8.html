AutoPlay: Scaling Task Generation for UI Agents via Exploration

AutoPlay trains better UI agents by automatically exploring apps to find what they can do, then generating realistic training tasks from those discoveries instead of relying on expensive human annotation.

Paper explainersAll themesAgents & Tool Use

Training an AI agent to use your phone or computer requires thousands of example tasks. Building these by hand is slow and expensive. AutoPlay solves this by having a large language model (like ChatGPT) systematically explore an app to find what it does and what states it can reach, then using those discoveries to automatically write realistic, diverse training tasks. Because the auto-generated tasks cover delete, edit, and retrieval operations that human annotators usually miss, agents see a broader range of real scenarios during training, resulting in improvements of up to 20% on real phones and 11% on desktop environments.

Zero assumption version

Why training UI agents is stuck

An AI agent that uses apps must learn what buttons do what, where things are, and how steps connect. Teaching this requires thousands of concrete example tasks (go here, do this action, reach this state). Today, those tasks are written by humans: researchers spend weeks describing every interaction a phone app supports. It is slow, expensive, and incomplete—many features get missed entirely.

A beginner might try: just let the AI practice on the real app and learn from success and failure. This breaks immediately because the AI needs to know what success even looks like. Without thousands of human-written goal descriptions (go here, press this button, then verify the result changed), the AI has nowhere to learn.

The core problem in one sentence. There is no cheap way to generate large, diverse, realistic task datasets for training agents that use real applications.

What it actually does

Exploration phase starts

An MLLM reads the app screen and gets a generic instruction: explore all features.

MLLM discovers interactions

It taps buttons, enters text, swipes—recording each action and the resulting screen.

Exploration log builds up

After hundreds of actions, the system has seen dozens of app states and what transitions connect them.

Task generator uses the log

A second MLLM reads the exploration log and writes concrete, verifiable tasks rooted in discovered states.

Training agents use real tasks

Downstream agents learn from these auto-generated tasks, with success measured by whether they reach the goal.

What the paper changes

What the paper changes

AutoPlay does not teach the AI agent a new skill. Instead, it changes where training tasks come from: not human annotation, but automatic generation seeded by real app exploration. The object being moved is the task dataset itself—replacing small, manually curated lists with large, diverse, verifiable auto-generated ones.

The hidden quantity

The hidden quantity: environment coverage

measured quantity  =  state and interaction coverage

Coverage is not just the number of tasks, but how many distinct app states and transitions the tasks exercise. An app might have a create button, delete button, and edit button, but if the task dataset only includes create tasks, the agent never learns delete or edit. AutoPlay's exploration phase explicitly uncovers which states and actions the app supports, forcing the task generator to pick tasks evenly across all the different kinds of operations it found, rather than clustering on a few easy ones.

The paper measures coverage by checking which app features (create, delete, edit, retrieve data) appear in generated tasks versus human-written tasks. AutoPlay covers more features because its exploration phase does not stop at obvious paths—it systematically tries all buttons and transitions.

Why it works

Why AutoPlay beats hand-written tasks

The core insight: exploration forces honesty about what an app can actually do. When a human writes 20 tasks for a calendar app, they guess what features exist and how they connect. They write create, maybe edit, probably miss delete entirely. When an MLLM explorer systematically taps every button and records the result, it builds a ground-truth map of reachable states and actions. The task generator then writes tasks that reference only states it knows exist and actions it has seen work.

Concretely: the MLLM explorer taps the delete button on a calendar event and records that the event vanishes and the calendar screen changes. The task generator sees this trajectory and writes a task: create an event, then delete it. This task is verifiable (the agent either deleted the event or did not) and realistic (it uses real app behavior). In contrast, a human annotator might write create-and-delete without ever checking if the app supports delete, resulting in a task the agent cannot actually complete.

The second benefit: exploration reaches rare features. If delete is hidden three menu levels deep, a human annotator might never find it. An exhaustive explorer, even if slow, eventually finds it. The task dataset ends up covering more kinds of operations, with roughly equal weight on common and rare features, so the trained agent learns to handle more scenarios.

Math after the picture

Measuring task quality

First in words:

task_success = (tasks_completed_by_agent / total_tasks_assigned) captures whether the generated tasks are actually executable and verify correctly. diversity = (number_of_distinct_features / total_app_features) captures how broadly the task set explores the app.

Then the compact form:

task_success_rate = sum_i verify_i(trajectory_i, goal_i) / N_tasks, where verify_i is an MLLM-based check of whether trajectory_i achieved goal_i

Every symbol:

task_success_ratefraction of generated tasks the agent completes correctly
verify_i(trajectory, goal)binary check: does this trajectory achieve this goal? (1 = yes, 0 = no)
trajectory_ithe sequence of actions the agent took for task i
goal_ithe task description for task i
N_taskstotal number of tasks in the dataset
A tiny worked example
Suppose the task generator creates 10 tasks for a calendar app.
Agent attempts all 10. It successfully creates 9 events (verify = 1 for each), deletes 7 events (verify = 1 for 7 of them), and fails to edit 2 events (verify = 0 for those).
Total successes: 9 + 7 + 2 = 18 out of 10 tasks = some tasks have multiple goals, so count all sub-goals.
If counting task-level: 9/10 tasks with create succeeded, 7/10 with delete, 8/10 with edit. Average task success = (9+7+8)/(10*3) = 24/30 = 80%.
The 20% failure comes from edit tasks failing. The task generator might have grounded those in explored states that do not support edit, or the agent did not learn edit well from training.

The formula is straightforward: a task succeeds if an MLLM verifier confirms that the agent reached the goal state. The larger the N and the more diverse the goals, the more honest the measurement.

What can go wrong

What can go wrong

Exploration incompleteness. If the MLLM explorer does not find a feature (e.g., a hidden menu), the task generator cannot create tasks that exercise it. Rare features in deep menus still get missed.
Task generator hallucination. The task generator might write a task that references a state it saw in the exploration log, but the path to reach that state is actually broken. The generated task then fails at runtime.
Verifier disagreement. An MLLM verifier might disagree with whether the agent truly completed a task (e.g., did the icon change enough to count as deleted?). Noisy verification hurts training signal.
Done right. Exploration is exhaustive enough to reach 80%+ of app features; task generator stays grounded in observed transitions; and verifier is calibrated to task-specific success criteria.
What a runnable demo should prove

What a runnable demo should prove

Build a minimal task generator: take a real app (e.g., a to-do list), run the MLLM explorer on it for 100 actions, record the exploration log, then have the task generator write 20 tasks from the log. Train a lightweight agent on half the tasks, evaluate it on the other half. The key metric is diversity: measure the fraction of distinct operations (create, delete, edit, check-off) that appear in the generated tasks versus human-written baseline tasks for the same app.

diversity_gain = (distinct_ops_autoplay / total_ops_in_app) - (distinct_ops_human / total_ops_in_app)

The demo must show that AutoPlay tasks exercise features the human-written baseline never touched.
