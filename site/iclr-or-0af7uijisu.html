THOR: Tool-Integrated Hierarchical Optimization via RL for Mathematical Reasoning

Train a language model to solve hard math problems by letting it call calculators and code, and reward it twice: once for getting the final answer right, and again for writing correct code at each step.

Paper explainersAll themesLLMs & Foundation Models

Large language models can read and reason, but they get tripped up on precise calculations like arithmetic or equation solving. THOR is a training method that teaches a model to call external tools (a calculator, a code interpreter) at the right moments, and uses a two-level reward system to fix mistakes both in final answers and in the individual code steps along the way.

Why language models fail at math

Language models are good at reading and writing because they learn by predicting the next word in billions of sentences. But math is different. When you ask a model to add 7,283 plus 5,641, it has to guess the next digit based on patterns it learned. It has never memorized that exact sum, so it makes a mistake. The same happens with equation solving: the model sees the pattern of how equations look, but algebra is not about patterns, it is about rules.

A naive fix: just ask the model to think step-by-step before answering. But that does not work either, because each step is still just a guessed word, and one wrong word early on breaks everything that comes after. The model has no way to check itself against a real calculator or code executor.

The core problem. A language model cannot accurately perform numerical computation because it predicts words, not correct arithmetic, and it cannot verify its own work against a real tool.

The algorithm as a flow

What it actually does

Step 1: Collect training data

Run a multi-agent pipeline that generates solutions where the model writes natural language reasoning, then calls a code executor for arithmetic or algebra, then resumes reasoning.

Step 2: Episode-level training

Show the model a full solved problem and reward it if the final answer is correct, or penalize it if wrong. This teaches overall problem-solving.

Step 3: Step-level training

For every step where the model wrote code that failed, give that step to the model again as its own small problem and reward correct code execution.

Step 4: Cold-start with supervised learning

Before RL, train the model to imitate the collected solutions on a training set, so it learns what a solution looks like.

Step 5: Self-correct at test time

When solving a new problem, if the model writes code and it fails, immediately show the error to the model so it can rewrite that step on the fly.

What the paper changes

What the paper changes

THOR modifies how a language model is trained by introducing a two-level reward system and a tool-calling mechanism. Specifically, the training process now rewards not just correct final answers but also correct code generation at each intermediate step.

the object it moves  =  the reward signal
The hidden quantity

The hidden quantity: execution feedback

measured quantity  =  step-level success signal

The hidden quantity THOR measures is whether each individual code step executed correctly when run by a real code interpreter. Before THOR, training methods only checked if the model got the final answer right or wrong, treating the whole reasoning path as one black box. THOR breaks this open: it runs the model's generated code and captures whether the execution succeeded or failed, then uses that information to refine the model.

The paper estimates this by running each generated code snippet through a Python interpreter or calculator and recording a binary signal: did it execute without error and produce a sensible output, or did it crash or produce garbage? This fine-grained feedback is what unlocks the training, because the model can now see exactly which steps are broken.

Why it works

Why two rewards beat one

Training on step-level execution feedback predicts final correctness better than training on final answers alone, because each successful step creates a correct foundation for all following steps. Here is the causal chain: when the model learns that its code must execute correctly at step three, it becomes more careful about the logic of step three. This means step three not only produces the right intermediate value, but also that all steps after it work correctly, because they are built on a correct foundation. In contrast, if you only reward final answers, the model might get lucky with step three (and many future steps) but never learn the intermediate rules, so mistakes in early steps propagate.

At training time, THOR uses two separate gradients: one that pushes the model toward correct final answers (episode-level), and one that specifically fixes code that failed to execute (step-level). These two signals reinforce each other. Step-level training makes the code more reliable, which makes episodes succeed, because the model learns to write code that actually runs without errors. Episode-level training makes the reasoning path more sensible, which makes individual steps easier to debug, because the model learns which intermediate values lead to correct answers. When the model solves a new problem, it can immediately see if its code worked and rewrite it on the fly, which adds a third safeguard because immediate feedback prevents bad code from breaking downstream steps.

The training objective

First in words:

total loss = episode-level loss + step-level loss, where each term includes a clipped advantage to prevent the model from changing too fast, plus a language modeling bonus for correct examples.

Then the compact form:

L_total(θ) = L_episode(θ) + β * L_step(θ), where L_step uses clipped PPO objectives on execution feedback and L_episode uses clipped PPO on final answer feedback.

Every symbol:

θthe model's weights
L_episodeloss for final answer correctness across the full reasoning path
L_steploss for code execution correctness at each intermediate step
βhow much to weight step-level training relative to episode-level
clippeda safety mechanism that limits how far the weights move in one update
A tiny worked example
Problem: solve 3x + 7 = 16.
Model writes: 'Subtract 7 from both sides to get 3x = 9. Then code: 9 / 3 = 3.'
Episode check: final answer is 3, correct = episode reward = +1.
Step check: the code 9 / 3 actually executes and outputs 3.0, correct = step reward = +1.
Combined: the model gets a +2 signal (both episode and step correct). Its weights move to repeat this pattern.
If the code had been 9 / 0, the step reward would be 0, triggering step-level retraining even if the episode somehow guessed right.

The two rewards reinforce each other: step-level fixes let episodes succeed, and episodes guide which steps matter most.

What can go wrong

What can go wrong

Biased training data. If the collected tool-integrated reasoning traces mostly show one kind of problem (like purely algebraic), the model learns to call the calculator only for those cases and fails on other kinds of math.
Code generation getting stuck. If the step-level optimizer focuses too much on correcting failed code, the model might rewrite the same code over and over instead of trying a different approach.
Tool feedback lag. If the code interpreter is slow or unavailable when the model solves a new problem, the self-correction mechanism cannot work, and the model is back to guessing.
Done right. When the training data spans diverse problem types, step-level retraining is capped to a reasonable number of attempts, and tool execution is fast and reliable, THOR teaches the model to reason clearly and call tools strategically.
What a runnable demo should prove

What a runnable demo should prove

Build a simple math solver where a small language model with 1.3 billion adjustable weights (a common model size) is trained with THOR on problems like solving linear equations or computing compound interest. Concretely: generate 100 training problems, each with natural-language reasoning steps and inline code calls. Train the model with both episode-level (final answer) and step-level (code execution) rewards. Then test it on 20 new problems and measure how often it gets the right answer and how often its generated code actually runs.

final accuracy = (correct answers on new problems) / (total new problems); step accuracy = (code steps that executed without error) / (total code steps attempted).

The demo should show that step-level training lifts both final accuracy and code execution rate (because the model learns precise code execution rules), and that self-correction at test time saves the model when it writes broken code (because the model can rewrite the broken step before it affects the rest of the solution).
