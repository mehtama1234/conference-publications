CombinationTS: Modular Attribution for Time-Series Forecasting

Break time-series forecasting models into independent pieces and measure what each piece actually contributes, so you know which parts really matter.

Paper explainersAll themesTime Series & Sequential

Time-series forecasting models grow more complex each year, but reported improvements often vanish when tested on different data or with different random seeds — researchers cannot tell if a win is real. CombinationTS fixes this by splitting forecasting models into five independent building blocks (how the input is transformed, how examples are turned into a useful list of numbers, how those lists are processed, how predictions are generated, and how the final output is shaped), then measuring what each block contributes under identical test conditions. This reveals a shocking fact: once you have a good way to turn raw data into useful numbers, even a simple identity encoder — one that does barely anything — often works just as well as complex encoders, because the hard work has already been done by the data transformation step.

Zero assumption version

Why forecasting progress is hard to see

Time-series forecasting means predicting the next values in a sequence — stock prices tomorrow, temperature next week, server load in an hour. Every year, new papers propose bigger, more complex models and claim they beat older models.

But here is the problem: when researchers test these new models, the improvements vanish or even flip if you change the dataset slightly, use different training settings, or run the test again. It is like someone saying their diet beats another diet, but the outcome depends entirely on which bathroom scale you use. Since the reported win is fragile, it disappears or reverses in a different setup, making it impossible to know which parts of a new model are actually doing the work or if the win is just random luck from that particular test.

A beginner might try a simple fix: just test more models and average the results. But that does not tell you WHICH PARTS of each model matter. If a new model has five different components, and it barely beats an old model, is it because of component one, component three, or their interaction? Nobody knows.

The paper's move in one sentence. Split each forecasting model into five separate, independent pieces and measure how much each piece contributes to the final accuracy.

The algorithm as a flow

What it actually does

Decompose the model

Take the forecasting model and split it into five standard pieces: input transformation (preparing raw data), embedding (turning data into a list of numbers), encoder (processing those numbers deeply), decoder (generating predictions), output transformation (shaping the final answer).

Create a shared test space

Set up one fixed evaluation condition so all component combinations are tested fairly — same dataset, same splits, same random seeds — eliminating confusing variations.

Measure two things per component

For each component, measure its average performance (how accurate it is) and its stability (how much the accuracy bounces around across different random runs).

Test all combinations

Plug each component option into each slot, creating many model variants, and run the full evaluation on every one.

Discover the real winners

See which components truly matter. The Identity Paradox emerges: once the embedding (data view) is good, complex encoders add almost nothing.

What the paper changes

What the paper changes

The paper changes how forecasting models are tested: instead of evaluating a complete model as a black box, CombinationTS isolates and measures each of the five standard components — input transformation, embedding, encoder, decoder, output transformation — one piece at a time, with all other pieces held constant. By swapping one piece at a time and measuring the change in accuracy, you can isolate each piece's true contribution, because you know every other part stayed the same.

The hidden quantity

The stability signature

measured quantity  =  component stability (sigma)

While accuracy (how often the model is correct) is easy to measure, stability — how much that accuracy bounces around when you retrain the model or use different random data samples — is the hidden quantity that reveals whether a component's performance is real or just luck. A component with high accuracy but very low stability is fragile and unreliable; a component with moderate accuracy but high stability is trustworthy.

CombinationTS measures both the average performance (the mean, written mu) and the bouncing-around (the standard deviation, written sigma) for each component. Sigma is the hidden quantity because most forecasting papers only report the mean — the best-case number — and ignore the stability. This hidden sigma reveals whether a reported improvement is genuine or just noise.

Why it works

Why splitting models reveals the truth

Time-series forecasting models chain five stages together: raw data gets transformed, then embedded into numbers, then processed by an encoder, then decoded into predictions, then shaped into final output. When a complex model barely beats a simple one, the improvement could come from any piece, or from subtle interactions. CombinationTS breaks this chain apart and tests each piece independently.

Here is the mechanism: by keeping four pieces fixed and swapping only one piece at a time, the paper isolates the true contribution of each piece. If swapping the encoder from simple to complex does not improve accuracy, then the encoder is not the reason the complex model claimed to win — the win came from somewhere else. By running this test across many model combinations and under one shared evaluation condition (same training data, same test splits, same random seed setup), the paper removes the confusing variations that made old comparisons fragile. A component that looks good in one setup but falls apart in another is revealed as fragile because its accuracy swings wildly. A component that performs consistently is revealed as real because its accuracy stays steady across replicas.

The Identity Paradox then emerges mechanically: once the embedding (the data view) is well-designed, the encoder — the part that should add deep processing — contributes almost nothing. This happens because the embedding already did the hard work of turning raw time-series data into a useful list of numbers. The encoder is just processing already-good data; if the data is already good, adding layers or complexity does not help much because there is no hard problem left to solve.

Math after the picture

Measuring component contribution

First in words:

For each component, measure the average accuracy (mu) and stability (sigma) across many model combinations. A component is trustworthy if both mu is high and sigma is low.

Then the compact form:

Quality_score = mu_accuracy - penalty * sigma_stability

Every symbol:

mu_accuracyaverage accuracy (percentage of correct predictions) across all test runs
sigma_stabilitystandard deviation (bounce) in accuracy across repeated runs with different random seeds
penaltya weight (often 1.0) that says how much to penalize instability
A tiny worked example
Complex Encoder option: average accuracy = 87%, stability = 8% bounce (sigma). Quality = 87 - 1.0 * 8 = 79.
Simple Encoder option: average accuracy = 86%, stability = 2% bounce (sigma). Quality = 86 - 1.0 * 2 = 84.
Simple encoder scores higher because its stability more than compensates for slightly lower average. It is the trustworthy choice.

High stability (low sigma) reveals components that work reliably; high accuracy with low stability means the component truly matters, not just got lucky on one test run.

What can go wrong

What can go wrong

Evaluation condition leaks. If different components are tested on different datasets or with different training setups, the comparison breaks down. CombinationTS requires a strictly shared evaluation space.
Components are not truly independent. If an encoder and embedding are deeply intertwined (components cannot be swapped separately), splitting them artificially can mask real interactions. CombinationTS works best when modules can be plugged in and out independently, like swapping a engine in a car without redesigning the chassis.
Stability measured on small datasets. If the test set is tiny, stability will appear to bounce a lot just from randomness, making even good components look fragile. Needs enough data to distinguish real fragility from noise.
Done right: shared conditions + loose coupling + large test sets. CombinationTS reveals honest attributions when all model variants are tested identically, components are separable, and evaluation data is large enough.
What a runnable demo should prove

What a runnable demo should prove

A minimal demo should take a time-series forecasting dataset (e.g., electricity demand, stock prices, or temperature), define three encoder options (identity, one-layer neural network, two-layer neural network), keep the embedding and other components fixed, and run evaluation across all three with five random seed replicas each. Measure both average accuracy and stability (standard deviation across the replicas). Show that the identity encoder achieves accuracy within 1-2% of the complex encoder, but with much lower stability bounce. This proves the Identity Paradox: complexity does not help when the embedding is good, because the embedding has already extracted all the patterns the encoder needs to process.

Fragility_score = accuracy - stability_penalty; plot three encoder options; identity should win or tie despite lowest parameter count.

The demo must make impossible to miss: a parameter-free identity encoder keeps pace with or beats complex encoders, proving that embedding (the data view) is the real engine, not the encoder.
