FormalML: Subgoal Completion Benchmark

FormalML is a benchmark for testing whether language models can fill in missing proof steps in formal mathematics.

Paper explainersAll themesDatasets & Benchmarks & Evaluation

When mathematicians write proofs, they often skip steps and write sketches instead of complete arguments. A subgoal is one of those skipped steps—a small proof obligation left to fill in. FormalML asks: can a language model complete these steps in formal proofs, the way a mathematician's assistant would? This paper introduces the first benchmark to test this, with nearly 5,000 real problems from machine learning theory.

Why this problem matters

When a mathematician writes a proof, they often skip tedious steps and write a sketch. Later, someone must fill in the gaps. This is like reading a recipe that says 'prepare the dough' without explaining how to knead it.

Language models (computer programs that predict words) have gotten good at theorem proving—writing formal proofs the computer can verify. But no one had tested whether they can do the real assistant job: taking a human sketch and filling in the one or two missing steps. A language model needs to retrieve the right facts from earlier in the proof, understand what still needs proving, and write a convincing argument. Each is hard alone; together, they are much harder.

The paper's answer. FormalML creates 4,937 real subgoal completion problems from machine learning theory, tests today's best language models on them, and finds they still fail on most of them.

The algorithm as a flow

What it actually does

Extract real problems from Lean code

Starting with machine learning theory proofs written in Lean (a formal language), extract every gap left between two consecutive steps.

Translate procedural to declarative form

Use a translation tactic to rewrite imperative proofs (do X, then Y) into declarative form (X is true because...).

Build a dataset of 4,937 subgoals

Collect subgoal completion problems spanning optimization theory and probability inequalities, marked by difficulty level.

Test language models on premise retrieval

Ask models to pick which earlier facts matter most for closing each gap (the harder part, because the proof can be long).

Measure accuracy and efficiency

Check whether the model's completed proof is correct (verified by Lean), and how much computation it took.

What the paper changes

What the paper measures

The paper creates a new benchmark—a collection of test problems—and runs existing language models on them. The benchmark itself is the contribution. The benchmark object is a subgoal: a small formal proof obligation plus the surrounding context (the facts the model can use) and the goal statement.

the object it moves  =  subgoal completion problems
The hidden quantity

The gap between sketch and proof

measured quantity  =  step complexity in formal proofs

Every step in a formal proof requires evidence. Evidence lives in the context—the definitions, lemmas, and earlier results the mathematician can invoke. The hidden quantity here is how many context facts exist, and how obvious it is which ones matter for filling the current gap.

The paper measures this by counting the size of each proof context and tracking which facts the model retrieves (picks as relevant). If a context has 200 facts and the model must pick the three that actually matter, that is a hard retrieval task. The paper tests this with real research-level machine learning proofs, where contexts are large and the connections are subtle.

Why it works

Why this benchmark is hard

A subgoal completion task requires the language model to do three things at once. First, it must retrieve: scan the proof context and identify which earlier facts are relevant to the current goal. This is like finding the right facts in a library when the library catalog is partial. Second, it must understand: read the goal statement in formal notation and grasp what counts as a valid proof. Third, it must generate: write a formal argument that Lean will accept as correct.

The benchmark is hard because these three tasks interfere. Retrieving too many facts buries the signal in noise. Retrieving too few facts starves the model of the information it needs. The model must balance precision and recall—a trade-off that formal proofs make especially sharp, because Lean accepts only correct proofs, not nearly correct ones.

How to score a completion

First in words:

accuracy = (number of subgoals completed correctly) / (total subgoals)

Then the compact form:

Acc = (1/N) * sum_i [P(subgoal_i) == verified by Lean]

Every symbol:

Ntotal number of subgoals in the benchmark
P(subgoal_i)the proof the model generates for subgoal i
verified by LeanLean formally checks and accepts the proof (1) or rejects it (0)
Accaccuracy: the fraction of subgoals the model completes correctly
A tiny worked example
Suppose the benchmark has 100 subgoals.
The model attempts all 100.
Lean accepts 62 of them (verified correct), rejects 38.
Accuracy = 62 / 100 = 62%. The model solved 62 percent of the gaps.

Lean is not forgiving—a proof is either correct or it is not. So accuracy is a binary per-problem: either the model's completion verified, or it did not.

What can go wrong

What can go wrong

Context too large. A long proof means many facts to consider. The model may forget which ones matter, especially if a key fact appears early or late in the context.
Formal syntax is strict. In Lean, a single typo makes the proof invalid. Models trained on English text often write nearly correct proofs that fail formal verification by one character.
Goal requires creativity. Some subgoals need a proof technique that is not explicitly shown elsewhere in the context. The model must infer or generalize. This is rare in easy benchmarks but common in research proofs.
Done right. A good model learns to retrieve sparingly (only the most relevant facts), follow formal syntax precisely, and apply known techniques to new goals. FormalML lets researchers measure progress on all three at once.
What a runnable demo should prove

What a runnable demo should prove

Write a small language model (or use an existing one) and test it on a subset of FormalML. The demo should show: (1) how many subgoals it completes correctly (accuracy); (2) which types of problems it solves (simple, medium, hard, by topic); (3) which context facts it retrieves (does it pick the right ones?). Measure both accuracy and the cost (how much computation time or API calls it took).

accuracy_by_difficulty = {easy: 70%, medium: 35%, hard: 5%}; efficiency = avg time per subgoal

The demo must make clear that even the best models today struggle when proofs are long, formal syntax is strict, and the required proof technique is not obvious.
