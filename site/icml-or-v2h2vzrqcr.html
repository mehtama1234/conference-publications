Hierarchical Procedural Meta-Reasoning for Generalizable Multimodal Agents

Teach an agent to gather and use task procedures from several sources so it can act across changing apps and workflows.

Paper explainersAll themesAgents & Tool Use

Agents that act on phones or desktops often fail on new tasks even when they see the screen correctly. The missing piece is usually procedural knowledge: the ordered steps needed to finish the job in a given app or across several apps. This paper builds an agent that represents those steps explicitly and decides when to rely on built-in knowledge and when to fetch extra procedures from outside sources, because strong action selection depends on having the right task procedure available at the moment of choice.

Zero assumption version

Why screen understanding alone does not give reliable action plans

A grounded agent can read buttons, forms, and menus. That still does not tell it the exact sequence needed to finish a task across real applications. App versions change, task conventions differ, and the same goal may require different sequences depending on the current state.

The central failure is missing procedure knowledge. If the agent knows what is on the screen but not the ordered recipe for the task, it can pick locally plausible actions that derail the whole job. The paper addresses this by treating procedures as first-class inputs because acting well depends on matching the current task to a relevant step-by-step plan.

The central move. Represent task procedures explicitly and let the agent choose among procedure sources, because generalization improves when action decisions are conditioned on the right procedure rather than on raw screen context alone.

The algorithm as a flow

What it actually does

Represent procedures in language.

Store task knowledge as explicit step sequences so the agent can inspect and condition on them during action selection.

Collect procedures from several sources.

Use internal knowledge when available and fetch outside procedures when needed, because one source alone may miss app-specific detail.

Run meta-reasoning over source quality.

Estimate which procedure best matches the current task and interface state so the grounded agent follows the most relevant guide.

Condition each action on the chosen procedure.

Use both the current screen and the selected procedure so local actions stay consistent with the full task sequence.

Train across varied tasks and app settings.

Expose the system to diverse tasks, versions, and workflows because generalization requires experience with procedural variation.

The hidden quantity

The hidden quantity

measured quantity  =  procedure-task match quality

The key hidden quantity is how well a candidate procedure matches the actual task and app state. A procedure may be valid in general and still be poor for this case because the interface version differs or the workflow spans extra tools.

The framework estimates that match through meta-reasoning over available procedure sources. This matters because a grounded agent only benefits from explicit procedures when the chosen one covers the right steps in the right order.

Why it works

Why explicit procedures improve generalization

Pure fine-tuning often ties behavior too closely to seen screens and seen action traces. That leaves the agent brittle on new workflows because it lacks an explicit description of what the task requires. Procedure-aware control inserts that missing structure: the agent sees not only the current interface but also the ordered plan it should be following.

Multiple sources matter because one procedure source can be incomplete. General knowledge may cover common actions, while fetched external guidance may cover a new app version or a specialized workflow. Meta-reasoning over those sources helps because the agent can choose the most suitable procedure for the present task instead of following one default plan everywhere.

The hierarchy matters because high-level procedure choice and low-level action grounding are different decisions. The first picks the right recipe; the second executes the next step on the current screen. Separating them improves transfer because the same high-level procedure can survive screen variation while the grounded controller adapts the exact click sequence.

Math after the picture

Choose actions with a matched procedure

First in words:

A simple summary is to score a candidate action by how well it advances the chosen procedure on the current screen, because the best local action is the one that moves the procedure forward.

Then the compact form:

score(action) = screen_fit(action) + alpha * procedure_progress(action) - beta * procedure_mismatch

Every symbol:

screen_fit(action)how appropriate the action is for the visible interface state
alphaweight on advancing the selected procedure
procedure_progress(action)how much the action completes the next intended step
betapenalty on following a poor or outdated procedure
procedure_mismatchhow badly the current procedure fits the task and app state
A tiny worked example
Action A clicks the visible booking button, so screen_fit = 4 and procedure_progress = 5.
Action B opens an unrelated settings page, so screen_fit = 2 and procedure_progress = 0.
If alpha = 2 and beta * procedure_mismatch = 1 for the chosen plan, Action A scores 4 + 10 - 1 = 13.
Action B scores 2 + 0 - 1 = 1.
The agent prefers Action A because it moves the selected procedure forward on the current screen.

The paper's full framework includes hierarchical procedure selection, but the central objective is to prefer actions that both fit the screen and advance the right procedure.

What can go wrong

What can go wrong

Retrieved procedures can be wrong or stale. If the outside guidance reflects an old interface or a different workflow, the agent may follow incorrect steps because the selected recipe no longer matches the real task.
Meta-reasoning can choose the wrong source. If the source selector overvalues familiar procedures, the grounded controller may never use the better app-specific guide because it trusts the default too much.
Procedures can be too coarse. If the steps are high-level only, the grounded controller may still face ambiguity at key branch points because the plan does not specify enough detail.
Done right. The method works when the system can retrieve relevant procedures and score their fit to the current task, because then each grounded action is guided by the best available recipe instead of by screen cues alone.
What a runnable demo should prove

What a runnable demo should prove

Build an Android-style task set with several workflows such as ordering food, booking travel, and sharing results across apps. Compare a grounded screen agent with and without explicit procedures. Provide task procedures from built-in knowledge, retrieved guides, or both, and vary app versions so the procedure selector must decide which source to trust.

The demo should show that completion improves when the agent chooses the right procedure source and then grounds each step on the visible interface, because that is the paper's core mechanism.

A convincing demo must show transfer across changed apps and multi-app workflows, because the claimed benefit comes from carrying explicit procedure knowledge into settings that differ from the training traces.
