AdverMCTS: Adversarial Search to Catch Fragile Code

When code passes public tests but fails on hidden ones, use an adversary to invent hostile test cases and force the solver to be honest.

Paper explainersAll themesAgents & Tool Use

Code generators built on large language models can produce solutions that look correct—they pass all the visible public test cases. But they often fail on hidden test cases they have never seen. This paper proposes a game where a code-generating solver and a test-inventing attacker compete: the solver writes code, the attacker finds tests that break it, and this feedback loop forces the solver to build genuinely correct code, not just code that memorizes visible tests.

Why visible tests are not enough

When you ask a code generator to solve a problem, you give it public test cases to check against. A typical test case is an input and the correct output: for example, if the problem is 'write a function to sort a list', you might give it input [3,1,2] and the expected output [1,2,3].

A naive code generator might look at a handful of public tests, find a pattern that works on those specific examples, and stop. It succeeds on every public test but fails on hidden tests—tests the evaluator keeps private. For example, a function might correctly sort lists of numbers 1-10 but fail when given negative numbers, or very large lists, or already-sorted lists, because the solution only memorized the pattern in the public tests.

The root problem: optimizing a code generator against a small, fixed set of tests is like teaching a student using only a few practice problems. The student passes those exact problems but has not truly learned the underlying concept.

In one sentence. The solver plays a game: it writes code, an adversary invents targeted test cases that break it, and this feedback forces the solver to keep improving until the code handles arbitrary test cases, not just the public ones.

What the paper changes

What changes

The paper changes how the code generator is trained and evaluated. Instead of just running code against the original public test cases, the system now also runs code against dynamically invented test cases. The solver has to handle not only the visible tests but also the worst-case tests the attacker can dream up.

the object it moves  =  the test set and solver feedback
The hidden quantity

The hidden quantity: fragility score

measured quantity  =  fragility—how easily a code solution breaks

Fragility is the number of new test cases that cause the current code to fail. A solution with high fragility looks good on the public tests but crumbles when attacked. A solution with low fragility has been stress-tested against many adversarial cases and handles edge cases the solver never saw.

The paper measures fragility by counting how many test cases the attacker invents that the solver's code fails on. As the rounds progress, the solver improves and fragility drops, because each round the solver rewrites its code specifically to pass the tests that failed in the previous round. When fragility reaches zero—the attacker cannot invent any new failing tests—the code is done.

Why it works

Why it works: the game forces honesty

The mechanism is straightforward. A code generator that only sees the public tests can memorize those exact tests and stop. It has no incentive to think more deeply. But when an adversarial agent is actively trying to break it, the solver cannot settle for shallow answers—it has to address the logical gaps that cause failures.

The attacker does not have a fixed list of test cases. Instead, it uses learning to evolve new tests that exploit the solver's mistakes. It systematically searches for edge cases the solver has not handled: negative numbers when only positive were shown, empty lists when only non-empty were shown, or boundary conditions the solver overlooked. Each new test teaches the solver something it missed.

Over time, the solver rewrites its code to pass each hostile test. After many rounds, the code handles a wide range of edge cases the solver never saw in the public tests. When fragility reaches zero, the attacker has run out of new ways to break the code, which means the solution covers the space of real possibilities.

The minimax game

First in words:

The solver and attacker alternate. The solver minimizes failures against the attacker's test suite. The attacker maximizes failures by finding new breaking tests. The game ends when no new tests can break the code.

Then the compact form:

min_solver max_attacker (number of failing tests from attacker's current suite)

Every symbol:

min_solverthe solver tries to reduce test failures
max_attackerthe attacker tries to increase test failures
number of failing testscount of tests that produce wrong answers
A tiny worked example
Round 1: Solver writes code. Attacker creates 8 failing tests. Fragility = 8.
Round 2: Solver rewrites code. Attacker creates 3 new failing tests (old 8 now pass). Fragility = 3.
Round 3: Solver rewrites again. Attacker cannot find new failing tests. Fragility = 0. Done.
Final result: code has been edited to defend against at least 11 distinct edge cases.

The game stops only when the attacker exhausts all strategies to break the code, which means the solver has truly learned the problem.

What can go wrong

What can go wrong

Attacker gets stuck. If the attacker runs out of ideas before the code handles all edge cases, the game ends early with code that still has bugs. The attacker must be smart enough to keep finding real weaknesses.
Attacker overfits to the solver. The attacker might waste effort on test cases that are too specific to one solver's quirks and do not generalize. The goal is tests that expose real logical flaws, not arbitrary tricks.
Cost grows quickly. Each round of search and code generation is expensive. If the game runs for many rounds, the total compute time becomes impractical.
Done right. The attacker uses principled search to explore the problem space systematically, finding real edge cases. The solver improves after each attack because it directly fixes the code to pass each newly discovered failing test, and the game converges in a reasonable number of rounds because the problem space is finite—after enough rounds, the attacker has probed all its viable strategies and can find no new failures.
What a runnable demo should prove

What a runnable demo should prove

Build a simple programming task, such as 'write a function that checks if a list is sorted' or 'write a function that finds the longest repeated substring'. Start with a handful of public test cases. Generate code using the solver, then use the attacker to invent new test cases. Run both the naive method (solver optimized only on public tests) and AdverMCTS (solver refined against attacker-generated tests). Measure how many hidden tests each solution passes.

False positive rate = (public-test passes but hidden-test fails) / total hidden tests

AdverMCTS should achieve a much lower false positive rate, proving that adversarial feedback forces the solver away from pseudo-correctness and toward code that handles real, unseen cases.
