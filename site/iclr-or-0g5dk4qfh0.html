Not All Clients Are Equal: Collaborative Model Personalization on Heterogeneous Multi-Modal Clients

FedMosaic lets each client in federated learning borrow only the parts of other clients that fit its task and model shape, so personalization still works when clients do different jobs with different architectures.

Paper explainersAll themesMultimodal

Personalized federated learning tries to improve each user's local model without pooling private data in one place, because each client trains locally and shares only model information. Most methods only work when every client has the same kind of data and the same network shape. That assumption breaks in a realistic multimodal setting, where one client may handle images, another may handle text, and a third may use a smaller or differently structured network. FedMosaic addresses both problems directly. It estimates which other clients are actually useful for a target client, and it shares information through modules whose outputs can be aligned even when the full networks do not have matching width or depth.

Zero assumption version

Ordinary personalization fails when clients differ in both data and model shape

Federated learning trains models across many clients without centralizing raw data. In the personalized version, each client wants a model tuned for its own task rather than one shared model for everyone. Existing methods usually assume the clients still look similar under the surface: they classify the same kinds of examples, and their networks have matching layers so the learned numbers inside those layers can be averaged directly.

A multimodal deployment violates both assumptions. One client may process audio, another may process text, and another may process images. Even two image clients may care about different labels or time periods. Their networks may also have different hidden sizes, different encoders, or different output heads. Direct averaging mixes unrelated updates, so a client can receive numbers that were useful for another task but destructive for its own. If the layer sizes do not match, direct averaging is impossible.

The paper's move. FedMosaic shares information selectively by estimating task relevance and by routing that information through modules whose dimensions do not need to match the full local networks.

The algorithm as a flow

What it actually does

Train locally

Each client updates its own model on its own private task data.

Estimate task relevance

The server computes which other clients appear useful for a given target client.

Aggregate selectively

A target client receives more from relevant clients and less from unrelated ones.

Information passes through a module that can connect networks with different hidden sizes.

Personalize again locally

Each client fine-tunes the received information on its own data, so the final model stays local and task-specific.

What the paper changes

What the paper changes

FedMosaic changes the rule for cross-client sharing. Instead of averaging whole models or whole adapters from every client, it computes a client-specific mixture based on task relevance and sends that mixture through a shared module whose input and output sizes can be adapted to each local network.

the object it moves  =  cross-client sharing of learned numbers
The hidden quantity

The hidden quantity: task relevance between clients

measured quantity  =  task relevance score

The key quantity is not how large another client's update is, but how aligned that update is with the target client's job. A relevance score tries to answer one concrete question: if client A borrows information from client B, will that borrowed information reduce A's local error or inject conflicting structure?

FedMosaic uses this score to avoid interference. If two clients solve nearby tasks, their shared pieces get a higher weight. If their tasks differ strongly, their influence is reduced. This matters because in heterogeneous federated learning the main failure mode is not lack of information; it is receiving the wrong information.

Why it works

Why selective sharing plus dimension-invariant transfer works

There are two separate barriers in this setting. The first barrier is semantic mismatch: two clients may use the same training rule but solve different tasks. If their updates are averaged directly, the resulting model moves toward a compromise that may fit nobody well. Relevance-aware aggregation reduces that problem because the server no longer treats every client as equally informative. A target client receives more signal from clients that encode similar decision boundaries and less from clients whose updates would pull the model in another direction.

The second barrier is architectural mismatch: even if two clients solve related tasks, their internal layer sizes may differ. A direct average of learned numbers cannot be formed when the arrays have different shapes. FedMosaic handles this by learning a common sharing path that is dimension-invariant, meaning the shared representation can be mapped into or out of different local widths. That lets a small network and a large network exchange useful structure without forcing either one to copy the other's full architecture.

The personalization step still happens locally after aggregation. That matters because no relevance score is perfect. The shared information gives each client a better starting point, and the final local updates restore details specific to that client's own local data shift, label space, or modality mix, because the last updates are fitted on that client's private examples rather than on the pooled cross-client mixture.

Math after the picture

The aggregation rule

First in words:

For a target client i, build a weighted sum of shared client components, where each weight reflects how relevant client j is to client i.

Then the compact form:

shared_i = sum over j of relevance(i,j) * module_j

Every symbol:

shared_ithe shared information sent to target client i
relevance(i,j)how useful client j is estimated to be for client i
module_jthe shareable module or representation from client j
sum over jcombine contributions from all available clients with different weights
A tiny worked example
Client A is an image classifier. Client B is another image task. Client C is a speech task.
Suppose the relevance weights for A are 0.6 from B and 0.1 from C, with the remaining 0.3 kept from A's own earlier shared state.
The server sends A a mixture dominated by B because B is closer in task structure.
Even if B's network is wider than A's, the dimension-invariant module maps the shared information into A's local width before A fine-tunes it.
A receives cross-client help without directly copying incompatible arrays from B's full model.

The equation matters because the weights are target-specific. Client B can be useful to A without A being equally useful to B.

What can go wrong

What can go wrong

Relevance scores can be misestimated. If the system concludes that two clients are related when they are not, it will still import harmful updates. The local personalization step limits the damage, but the sharing stage will start from the wrong mixture.
The shared module can be too small. If the dimension-invariant path is too narrow, it may discard details needed to transfer knowledge across large architecture differences, because the bottleneck cannot carry enough task structure.
Private data can drift over time. A relevance pattern learned earlier may stop matching later client behavior, so aggregation quality falls unless the relevance estimates are updated as the tasks change.
Done right. The method works best when relevance estimates are refreshed, the shared module has enough capacity to carry useful structure, and the final local fine-tuning step is strong enough to restore client-specific details.
What a runnable demo should prove

What a runnable demo should prove

Build a federated setup with at least four clients: two image tasks, one text task, and one audio task. Give them different network widths so direct parameter averaging is either harmful or impossible. Compare three systems: local-only training, uniform personalized sharing, and FedMosaic.

The demo should log local task accuracy, how much each client borrows from each other client, and whether the borrowed information changes when the local task data pattern shifts over time. A convincing result shows that the image clients share most with each other, the text and audio clients share less with unrelated clients, and the final local models improve because the server filtered cross-client information instead of averaging everything.

personalization_gain = local_metric_with_fedmosaic - local_metric_with_baseline

The core claim is established if selective sharing improves each client's own metric while still allowing transfer across non-matching architectures, because the server filters out unrelated client updates and the shared module maps compatible information into each local network shape.
