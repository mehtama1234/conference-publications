InnoGym: Measuring Innovation in AI Agents

InnoGym is a benchmark that measures not just whether an AI agent finds correct answers, but how different and original its solution methods are compared to other approaches.

Paper explainersAll themesDatasets & Benchmarks & Evaluation

Current AI benchmarks ask: Did the agent get the answer right? But they ignore a deeper question: Did the agent solve it using a different method than before? InnoGym introduces two new metrics—performance gain and method distance—and measures them separately. Why separate them? Because the paper's real finding is that these two do not move together: agents that invent unusual methods often stumble in execution, while agents that follow the standard playbook produce reliable but repetitive answers. By splitting the metrics, InnoGym reveals this hidden gap.

Zero assumption version

Testing agents only on correctness hides methodological diversity

Today's AI benchmarks focus on a single question: Is the answer correct? If a code-writing agent produces working code or a math-solving agent gets the final number right, we call it a success. We have leaderboards showing which models rank highest, which naturally creates a race to the top accuracy.

But this misses something important. A correct answer can come from many different paths. One agent might use a greedy algorithm (pick the best choice at each step), another might use dynamic programming (remember past choices to avoid wasting work), a third might use a heuristic search. All three produce correct answers. But only the second two represent real originality—methods that are genuinely different from the standard playbook.

A naive first attempt would be to manually read each solution and score its originality. But that is slow, subjective, and does not scale to thousands of agent runs across diverse domains.

The algorithm as a flow

What it actually does

Run agent on 18 real tasks

Each task has a problem, constraints, and a measurable objective (e.g., code quality, proof correctness).

Extract solution into pseudocode

Use a language model prompt to read the agent's code and summarize its logic as plain steps.

Score how different it is

Compare the pseudocode to all known solutions, scoring differences across six dimensions (problem framing, algorithm choice, etc.).

Measure performance relative to baseline

Calculate how much better or worse the solution is, so that good execution is visible even when methods are standard.

Report two separate scores

One for performance gain, one for method difference, revealing which agents balance or favor one over the other.

What the paper changes

What the paper changes

InnoGym replaces the single correctness score with two independent axes: performance gain (how much better than baseline) and method distance (how different from known approaches). By keeping them separate instead of collapsing into one ranking, researchers can now see which agents favor invention over execution and vice versa.

the object it moves  =  Performance gain and method distance as separate metrics
The hidden quantity

Method distance: the hidden quantity

measured quantity  =  Method distance between solutions

The core hidden quantity is method distance—how different two solutions truly are from each other. This is not about the code syntax (one uses semicolons, another uses colons); it is about the algorithm itself. A greedy algorithm and a dynamic programming solution to the same problem have a large method distance because they embody fundamentally different strategies.

InnoGym estimates method distance by extracting each solution into pseudocode (a plain-English description of the logic), then scoring six dimensions: problem framing (how the task is interpreted), algorithm choice (which computational strategy), data structure (arrays, trees, or graphs), architectural pattern (divide-and-conquer, state machines, etc.), parameter setting (the chosen values), and implementation details. A human expert would assign each dimension a score from 0 (identical) to 4 (completely opposite design philosophy). InnoGym averages these six scores to get a single method distance from 0 to 100.

Paper reading. The paper formalizes method distance as an average of six algorithmic dimension scores (problem framing, algorithm, data structure, architectural pattern, parameter setting, implementation), each scored by an expert or validation protocol on a 0–4 scale, normalized to 0–1, then rescaled to 0–100.
Why it works

Why measuring method distance alongside correctness reveals the creativity gap

The mechanism is that benchmarks do not measure what they do not ask. When correctness is the only metric, agents learn to optimize for it—they copy known solutions, tweak parameters, or follow the most common playbook, because all of these produce correct answers. An agent that invents an unusual method but gets slightly lower accuracy is ranked below an agent that repeats a textbook algorithm perfectly. Over time, this creates leaderboards dominated by reliable copycats.

InnoGym solves this by decoupling performance (how good the solution is) from method distance (how different the approach is). Now an agent that finds an unusual but slightly flawed approach and an agent that executes a standard method perfectly are scored on different axes, not collapsed into a single ranking. This reveals which agents think differently and which optimize for the benchmark itself. The paper then uses this two-axis view to show the key finding: agents that invent unusual methods often do not execute them reliably, failing to turn originality into strong results. This gap between invention and execution is invisible in single-metric benchmarks.

The method distance formula

First in words:

Average the six dimension scores (each normalized to 0–1 range), then rescale to 0–100

Then the compact form:

Distance = 100 * mean([ norm_d1, norm_d2, norm_d3, norm_d4, norm_d5, norm_d6 ]) where norm_dk = score_dk / 4 and score_dk in {0,1,2,3,4}

Every symbol:

score_dkexpert score for dimension k (0 means identical, 4 means opposite design philosophy)
norm_dkscore_dk divided by 4, to bring it to range 0–1
mean( )average of all normalized scores
Distancefinal method distance score, scaled to 0–100
Tiny worked example: comparing two algorithms
Agent solution versus Known solution B, scored on six dimensions:
Dimension 1 (framing): score 1 normalized to 1 / 4 = 0.25
Dimension 2 (algorithm): score 4 normalized to 4 / 4 = 1.00
Dimension 3 (data structure): score 2 normalized to 2 / 4 = 0.50
Dimension 4 (pattern): score 3 normalized to 3 / 4 = 0.75
Dimension 5 (setting): score 1 normalized to 1 / 4 = 0.25
Dimension 6 (details): score 0 normalized to 0 / 4 = 0.00
Mean: (0.25 + 1.00 + 0.50 + 0.75 + 0.25 + 0.00) / 6 = 2.75 / 6 = 0.458
Distance score: 0.458 times 100 = 45.8 (moderately different from this known solution)

The metric averages algorithmic differences across six independent axes, giving a single distance score. If only the algorithm dimension differed (while everything else matched), that algorithm-only change would dominate the distance. This reflects the fact that swapping algorithms matters more than tweaking constants.

What can go wrong

What can go wrong

Extraction prompt misses the true logic. If the prompt that converts code to pseudocode oversimplifies or misreads the algorithm, the method distance will be inaccurate. A complex algorithm might be summarized as a simple loop, collapsing its distance score incorrectly.
Expert scoring is subjective or inconsistent. The six dimensions are scored by humans or learned judges. If the judges disagree or apply different standards (one thinks dynamic programming is very different, another thinks it is standard), method distance becomes unreliable. InnoGym addresses this with triplet validation—showing the scorer pairs of methods and asking which is more different—but imperfect agreement remains.
Distance scores are inflated for hard-to-read code. A poor solution might use unusual variable names or convoluted syntax, making the pseudocode extraction flag it as different, even if the underlying algorithm is textbook. Method distance then confuses readability issues with real originality.
Done right: InnoGym uses validation and domain experts. The paper validates method distance against human judgments on known triplets (pairs of solutions where experts agree on relative difference). It also consults domain textbooks and surveys for classical problems, grounding the comparison in real algorithmic knowledge. This reduces but does not eliminate subjectivity.
What a runnable demo should prove

What a runnable demo should prove

A minimal demo would: (1) give an agent two tasks (e.g., a sorting problem and a scheduling problem); (2) collect multiple agent solutions for each, using different language models or prompting strategies; (3) extract pseudocode summaries for each solution; (4) score method distance pairwise among the solutions using a simple rubric (0–4 on algorithm choice, data structure, and approach); (5) measure correctness (pass/fail); (6) plot each solution as a point on a two-axis graph with method distance on one axis and correctness on the other. The graph should show the gap: some agents in the top-right (different and correct), some in the bottom-left (repetitive and correct), and some in the top-left (different but flawed).

Method distance = average of normalized dimension scores scaled to 0–100; Correctness = test cases passed / total test cases times 100

The demo makes clear: originality and reliability are not the same dimension. Agents cluster along different trade-offs. True assessment requires measuring both.
