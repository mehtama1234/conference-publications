Mosaic: Runtime-Efficient Multi-Agent Embodied Planning

Mosaic makes a team of embodied agents act faster by keeping a shared world record in each agent's local frame and assigning actions with a constraint solver.

Paper explainersAll themesAgents & Tool Use

A team of embodied agents has to keep track of what each agent can see, what each agent can reach, and which actions can happen at the same time. Most failures come from two sources: the agents lose track of the world after moving, or two agents choose actions that clash. Mosaic fixes both problems by storing objects in each agent's own coordinate frame and by choosing each step with a solver that enforces physical and coordination rules.

Zero assumption version

Why multi-agent planning slows down

In embodied planning, each agent sees only part of the scene. After moving, it must update where objects are, where teammates are, and which jobs are still open. If that record drifts, an agent may walk to the wrong place or try to pick up an object that is not there.

Coordination adds a second problem. Two agents may both go after the same object, block each other in a narrow space, or choose an order that cannot work in the real scene. Each failed action costs time because the system has to ask again, replan again, and execute again. Mosaic targets those wasted steps directly.

The paper's move in one sentence. Keep each agent's world record in its own local coordinates, transform those records into a shared view, then choose the next joint action set with a solver so that the team only attempts compatible moves.

The algorithm as a flow

What it actually does

Record objects in each agent's local frame

Each agent stores where objects are relative to itself, which keeps updates simple after motion because the record moves with the agent.

Transform local records into a shared team view

When agents need to coordinate, the system converts those local records into one shared scene description so each agent can reason about the same object.

List candidate actions for every agent

At each planning step, each agent proposes actions such as move, open, pick, or wait.

Solve for a feasible joint action set

A constraint solver chooses one action per agent while enforcing reachability, ordering, and collision-style rules so that the chosen set can really happen.

Execute, observe, and update

After the step runs, each agent refreshes its local record and the next planning round starts from a cleaner state.

What the paper changes

What the paper changes

The paper changes two internal objects: the team memory and the step-level action selector. Instead of a loose text record of the world, it keeps a geometric scene record anchored to each agent. Instead of letting agents choose actions independently, it solves one joint decision problem at every step.

The hidden quantity

The hidden quantity

measured quantity  =  State consistency across agents

State consistency asks whether all agents are acting on a scene record that still matches the real world. This quantity is hidden because you only notice it after a failure: an agent reaches for empty space, repeats a job, or blocks a teammate.

Mosaic keeps consistency higher by storing positions relative to the observing agent, then transforming them when agents coordinate. That lowers drift after movement because a local record needs only the agent pose to stay useful.

Why it works

Why it works

The memory design helps because local coordinates are stable under motion. If an object is stored as two steps in front of agent A, then after A moves you can update that relation with a simple pose transform instead of rebuilding the whole scene from scratch. That cuts stale object records, so fewer actions are aimed at the wrong place.

The joint solver helps because it chooses actions for the whole team at once. Independent choices often fail when two actions depend on the same door, path, or object. Mosaic avoids that by enforcing feasibility and ordering inside the selection step, so the system spends fewer turns recovering from avoidable conflicts.

Math after the picture

The joint action choice

First in words:

At each step, pick the action set that gives the largest total task gain while obeying feasibility and coordination constraints.

Then the compact form:

choose a* = argmax_a sum_i score(i, a_i) subject to feasible(a) = 1

Every symbol:

a_ithe action assigned to agent i at the current step
score(i, a_i)the value of giving action a_i to agent i, based on task progress
feasible(a)a check that the whole action set respects reachability, ordering, and conflict rules
a*the chosen joint action set
A tiny worked example
Two agents need a mug from a closed cabinet.
Agent A can open the cabinet now.
Agent B can pick the mug only after the cabinet is open.
Independent choice may give A=pick and B=pick, which fails for both.
The solver checks feasibility and instead picks A=open, B=wait.
On the next step it picks A=move away, B=pick.
The team finishes in two valid steps because the solver enforced the right order.

The paper uses integer linear programming to solve this selection problem exactly under step-level constraints.

What can go wrong

What can go wrong

Bad local observations. If an agent misreads the scene, then the transformed shared view is also wrong because the system starts from that local record.
Missing constraints. If the solver does not encode an important physical rule, then it may approve an action set that still fails in the environment because the rule was never checked.
Solver cost at very large scale. As the number of agents and candidate actions grows, solving the joint step can take longer because the search space gets larger.
Done right. The method pays off when failed actions are a major source of delay, because better state tracking and compatibility checks remove exactly that waste.
What a runnable demo should prove

What a runnable demo should prove

Build a small grid world with two agents, a door, and two objects. Give each agent only a local view. Compare two systems: one with plain shared text memory and independent action choice, and one with local-coordinate memory plus a joint constraint solver. Measure completion time, failed actions, and repeated planning calls. The demo should show that the second system finishes faster because it keeps a cleaner world record and prevents incompatible actions before they are executed.
