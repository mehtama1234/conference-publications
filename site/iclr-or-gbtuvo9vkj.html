Robust LLM Unlearning via PoRT

Unlearning asks: when you want a deployed AI to forget something it learned, how do you rebuild its guardrails so attackers cannot trick it into remembering anyway?

Paper explainersAll themesOther

AI safety requires that deployed language models forget dangerous or sensitive knowledge on demand. Most unlearning methods filter user questions (the prompt) before the model sees them. But these methods break badly under adversarial attacks: attackers can add prefixes or rephrase questions to trick the model into exposing what it should have forgotten. PoRT adds three layers of defense: it cleans messy questions, checks both the cleaned question AND the model's answer, and asks the model to think through low-confidence answers twice to catch itself.

Zero assumption version

Unlearning guardrails break under attack

Deployed language models sometimes contain knowledge they should not: trade secrets, personal data, or dangerous instructions. A responsible AI company must remove that knowledge if asked, or if the model was trained on data it should not have been. The standard approach is prompt filtering: analyze the user's question before it reaches the model, and block it if it asks for forbidden knowledge. A naive version just checks the raw question text.

But adversarial attackers can defeat text-based filters. They can prepend confusing prefixes (a jailbreak attack) that make harmful questions look innocent to a simple checker. They can rephrase the question in ways that bypass keyword detection. In the worst case, these attacks cause information leakage to explode: the abstract reports that simple prefix attacks trigger a 1,150-fold surge in leaked information about fictitious entities, and rephrased questions can push the model's compliance rate from 25% down to 67%. The blocker thinks it is working. It is not.

Simple question-filtering fails because attackers can hide bad requests in prefixes and rephrasings. PoRT adds two checks: clean up the question first, then check both the cleaned question and the model's answer together.

The algorithm as a flow

What it actually does

Step 1: Data cleaning

When a user asks a question, PoRT creates a few-shot prompt that teaches the model to generate both a cleaned version of the question AND an initial response to that cleaned version. The demonstration library grows with each attack seen, making the cleaner adaptive.

Step 2: Post-judgment scoring

Instead of checking only the original prompt, PoRT scores both the cleaned prompt and the model's own answer. If either one looks risky, the output is flagged, because leakage can hide in the model's answer even if the question looks harmless.

Step 3: Selective multi-round thinking

For outputs the model itself flagged as low-confidence, PoRT triggers a second reasoning pass where the model thinks through its answer again and can self-correct.

Step 4: Confidence thresholding

The model estimates its own confidence for each response. Outputs above the threshold go through; uncertain ones trigger re-reasoning.

Step 5: Integrated defense

All three modules work together: a cleaned question that passes scrutiny, a low-risk answer, or a second-pass correction that catches itself, blocks the leak.

What the paper changes

What changes

PoRT changes three things: the question is cleaned before checking, the verdict is based on both cleaned question and answer (not just the question alone), and low-confidence outputs are re-reasoned. No retraining of the model itself, no weight updates—only the filtering pipeline that runs when answering questions is rebuilt.

The hidden quantity

The hidden quantity: output risk score

measured quantity  =  risk score for the model output

Most unlearning filters measure only the question (does it ask for forbidden knowledge?). PoRT introduces a hidden quantity: the risk that the model's actual answer leaks sensitive information, separate from the question risk. This is hard to measure because the answer is a long sequence of words, not a category label.

PoRT estimates it by analyzing both the cleaned prompt (should have low risk) and the model's response (should not contain forbidden facts, keywords, or subtle evasions). A post-judgment module combines these signals into a single risk score. High-risk outputs get held; low-risk ones are sent. Confidence estimation adds a second layer: if the model itself is uncertain about its answer, re-reasoning may reveal self-doubts that flag the output as suspicious.

Why it works

Why three layers beat one

A single-layer question filter is like a wall with a single gate: an attacker who finds the loophole gets through. PoRT uses three defense layers that catch different attack strategies. First, cleaning the question removes adversarial noise and prefixes before judgment, so the cleaner-generated question is closer to the attacker's true intent. Second, checking the answer (not just the question) catches leaks that escape because a risky question was phrased just carefully enough to pass the checker. The model might write back a response that betrays forbidden knowledge even when the question looks innocent. Third, multi-round thinking forces the model to commit: if it is uncertain about its own answer, re-reasoning can trigger self-correction or reveal internal red flags. Together, these three layers raise the bar for attackers.

The core idea: unlearning is not about the model forgetting at all. The model still contains the information. Unlearning is about making it impossible or extremely difficult for a malicious user to extract that information. A well-designed filtering pipeline with multiple independent checks is much harder to evade than a single gate.

Scoring the risk

First in words:

risk_score = alpha * risk_prompt + beta * risk_answer + gamma * (1 - confidence), where alpha, beta, gamma are weights chosen to balance prompt risk, answer risk, and uncertainty.

Then the compact form:

risk_score = alpha * risk_prompt + beta * risk_answer + gamma * (1 - confidence)

Every symbol:

risk_scoreoverall likelihood the output leaks forbidden knowledge
risk_promptscore for the cleaned question (0=safe, 1=risky)
risk_answerscore for the model's actual response text (0=safe, 1=risky)
confidencemodel's self-reported confidence in its answer (0=unsure, 1=certain)
alpha, beta, gammatuning weights that decide how much each signal matters
A tiny worked example
Scenario: cleaned question about a forbidden topic, risky answer, high confidence.
risk_prompt = 0.8 (the cleaned question still hints at forbidden topic)
risk_answer = 0.9 (the answer contains suspicious keywords)
confidence = 0.7 (model is fairly sure of itself)
With alpha=0.3, beta=0.4, gamma=0.3:
risk_score = 0.3 * 0.8 + 0.4 * 0.9 + 0.3 * (1 - 0.7) = 0.24 + 0.36 + 0.09 = 0.69
Interpretation: risk_score 0.69 is high; output is likely blocked. If confidence were lower (0.4), score would be 0.3*0.8 + 0.4*0.9 + 0.3*0.6 = 0.24 + 0.36 + 0.18 = 0.78, triggering re-reasoning.

The score combines three signals: how risky the cleaned question looks, how risky the model's answer is, and how much the model doubts itself. High scores trigger blocking or re-reasoning.

What can go wrong

What can go wrong

The cleaner itself can be adversarial. If an attacker submits text designed to trick the cleaning module, it might be cleaned in a way that preserves the hidden attack intent. The demonstration library helps by adapting to attacks it has seen, yet it cannot anticipate truly unfamiliar attack patterns that were never included in the training examples—an attacker with enough creativity can always find new phrasing or structure the library has never encountered.
Confidence estimation is learned; models can be overconfident or underconfident. The model's own confidence score might not reflect true uncertainty. A high-risk output could come with high confidence (causing it to escape re-reasoning), or a benign output might have low confidence (causing unnecessary re-reasoning and slowdown).
Multi-round thinking can be slow. Asking the model to think twice means running it twice for low-confidence outputs. On a large model, this doubles the waiting time for uncertain queries, which may not be acceptable in a real-time system.
Done right: three independent layers mean an attacker needs to break all three to succeed. By making the prompt cleaner, post-judgment scorer, and multi-round reasoner independent modules, PoRT ensures that no single bypass exploits the whole system. An attack that evades one layer still faces two others.
What a runnable demo should prove

What a runnable demo should prove

A concrete demonstration should show that PoRT blocks adversarial attacks that a single-layer filter cannot. Take a trained model with a forbidden knowledge base (e.g., facts about a fictitious entity or dangerous instructions). Build two filtering pipelines: one with simple prompt checking only, and one using PoRT. Test both against a suite of adversarial queries: prefix attacks (adding innocent preambles), rephrasings, and composite questions. Measure how often each pipeline leaks the forbidden information. PoRT should leak far less often, especially on adversarial inputs, while keeping normal-question throughput nearly as high as the simpler baseline.

leakage_rate = (number of adversarial queries that leaked forbidden info) / (total adversarial queries); ideal: simple_filter leakage >> port_leakage; normal_throughput should be similar

The key proof: simple filtering leaks under adversarial attack (high numbers on prefix / rephrase attacks); PoRT does not (low numbers on the same attacks).
