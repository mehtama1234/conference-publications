AI-for-Science Low-code Platform with Bayesian Adversarial Multi-Agent Framework

Three LLM agents coordinate to write scientific code: one refines test cases, one writes code, one evaluates it, all using Bayesian statistics to learn which tests catch bugs best.

Paper explainersAll themesAI for Science

Scientists without coding backgrounds need to convert lab notes into working programs. Large language models can write code, but they hallucinate: they output plausible-sounding code that seems right but actually fails silently. This paper builds a team of three AI agents that catch those failures by having one agent adversarially design harder and harder tests, while another writes code, and a third grades it—all guided by Bayesian statistics, which is a way of updating beliefs as you see more evidence.

Zero assumption version

Why single LLMs fail at writing scientific code

A scientist hands an LLM a vague prompt: write code to predict beach erosion from sensor data and physics equations. The LLM writes Python that looks correct—it loads data, scales numbers, trains a neural network. But it has bugs: it forgets to align coordinate systems with the physics model, or it uses the wrong loss function for the task. The scientist runs it, gets a number back, and trusts it.

The real problem: there is no hard pass/fail signal. In chess or image recognition, you know when the AI loses or misclassifies. But in science, the task is ill-defined. The code might run without crashing, produce numbers in a sensible range, even pass a loose accuracy check—yet violate domain laws. A beginner trying to catch these bugs would write one fixed test case (e.g., does the output make physical sense?) and run it once. That fails because code passes one test but breaks on edge cases, or it passes contrived tests but misses the real flaw.

The paper's fix: Deploy three LLM agents working together: one continuously designs harder test cases to expose bugs, one writes candidate code, and one grades both, using Bayesian statistics to figure out which tests are most informative.

The algorithm as a flow

What it actually does

1. User gives a vague prompt

I want code that predicts beach erosion incorporating Bruun theory and sensor observations.

2. Task Manager agent refines it

Unpacks it into a formal task description, concrete success metrics, and initial test cases with domain constraints.

3. Code Generator agent writes candidate solutions

Produces multiple code candidates, each attempting to satisfy the refined task and pass the test cases.

4. Evaluator agent scores each candidate

Runs tests on each code, measures functional correctness, structural alignment with domain theory, and static analysis signals.

5. Bayesian update refines the loop

The framework updates its belief about which test cases are most informative (catch bugs most often), then the Task Manager adversarially designs harder tests to expose remaining weaknesses.

What the paper changes

What the paper changes

Instead of one LLM writing code in response to a prompt, the paper introduces a trio of agents and makes them adversarial: the Task Manager agent iteratively hardens test cases, the Code Generator agent responds to those tests, and the Evaluator agent provides feedback. The Bayesian framework (a statistical technique for learning from evidence) connects all three by tracking which test cases are most valuable at catching bugs.

the object it moves  =  the loop structure: Task Manager -> Code Generator -> Evaluator -> refined task -> repeat
The hidden quantity

The hidden quantity: test informativeness

measured quantity  =  How much a test case reveals about code correctness

The paper silently measures something important: the informativeness of each test case—that is, how well a single test predicts whether the entire code is correct. A test is highly informative if passing it strongly suggests the code works; an uninformative test passes even for broken code. The paper never names this quantity explicitly, but it is the key to why the adversarial loop works.

The Evaluator estimates informativeness using Bayesian statistics by observing which test cases most frequently split passing code from failing code. If a test passes for 100 codes and fails for 1, it is uninformative (too easy). If a test passes for 50 codes and fails for 50 codes, it is highly informative (it discriminates).

Why it works

Why it works: the three-agent loop

The core insight is that LLMs writing code alone lack feedback, so they repeat mistakes. Adding adversarial testing forces the Code Generator to handle edge cases. The Bayesian part is the speedup: instead of running all possible tests (slow), the Evaluator tracks which test cases have historically been most informative—those that most often split good code from bad code—and the Task Manager prioritizes generating those tests.

The mechanism has three parts. First, the Task Manager (an LLM with domain knowledge) receives both the user's vague prompt and the results from previous rounds, and it deliberately designs test cases that might break the Code Generator's current attempt—like an adversary looking for weak spots. Second, the Code Generator (another LLM) tries to write code that passes all those tests. Third, the Evaluator (a third LLM) runs each test, measures code quality by three metrics (Does it run without error? Does it match the domain structure? Do static analysis tools flag problems?), and feeds those measurements back into the Bayesian optimizer.

The Bayesian optimizer is the orchestrator: it learns which test cases most reliably predict total code correctness, because if a test case passes and the code later fails on some other metric, that test was uninformative; if a test always co-occurs with code correctness, it is highly informative. Over iterations, the Task Manager gradually crafts a battery of adversarial tests that expose every class of bug in the Code Generator's attempts. Meanwhile, the Code Generator gradually improves because it now has real, hard feedback instead of just a vague prompt.

The Bayesian quality score

First in words:

The framework estimates the probability that a new piece of code is correct given the tests it passes, using a Gaussian Process (a statistical model that learns patterns from past code). For each new code, the model predicts a distribution: a mean score (expected quality) and uncertainty (how confident that estimate is).

Then the compact form:

score(code) ~ Normal(mu(code), sigma(code)) where mu and sigma are learned from test outcomes of prior codes

Every symbol:

score(code)the probability the code is actually correct
mu(code)expected score for this code, learned by comparing similar prior codes
sigma(code)uncertainty in that score; wide range means uninformed
Normal()a bell curve distribution
A tiny worked example
Prior codes: 5 passed physics tests and 4 passed both physics and edge-case tests. Code A passed physics but not edge-case. Code B passed both. The Bayesian model learns: pass both tests → mean score 0.85, pass one test → mean score 0.50.
New code passes physics test only. Model predicts mean score 0.50 (like other one-test-passing codes) but wide uncertainty (0.30 to 0.70) because those codes historically split 50/50 on total correctness.
Task Manager, seeing high uncertainty, designs a new edge-case test to narrow it. If new code fails that test, we learn it is truly broken; if it passes, we gain strong evidence it works.

The Bayesian model remembers which combinations of test outcomes historically predicted real correctness, so it can prioritize tests that resolve uncertainty fastest.

What can go wrong

What can go wrong

Circular testing loop. If the Task Manager learns to generate tests that the Code Generator overfits to without learning the underlying principle, the framework wastes iterations. Example: the Task Manager learns to test for a magic constant in the code, and the Code Generator hardcodes that constant, but the code still fails on inputs it has never seen before.
LLM agents fail silently in new domains. If the domain is far from the training data of the LLMs (e.g., a new physics theory), the agents have no prior knowledge. The Bayesian optimizer then learns from a blank slate, and the Task Manager may not know which edge cases to test, so the adversarial tests miss critical bugs.
Evaluator disagreement. The three LLM agents sometimes disagree on whether code is correct, especially on ambiguous metrics like structural alignment with domain theory. If the Evaluator is lenient, the Bayesian model learns that many bad codes pass, and informativeness estimates become unreliable.
When done right. The framework succeeds when the initial task refinement captures the domain constraints accurately (so Task Manager has real targets for adversarial tests), and when the Evaluator is calibrated to domain-specific success metrics (not generic code quality). On Earth Science tasks (the paper's demo), it outperforms competing LLM approaches because the adversarial loop forces the Code Generator to learn not just to pass any test, but to pass tests that reflect real physics, which single-LLM baselines never do.
What a runnable demo should prove

What a runnable demo should prove

Build a simple Earth Science task: given time series of ocean wave height and wind speed, predict shoreline position change using a simplified physics model (wave energy flows to erosion rate). Define three types of test cases: (1) basic data loading tests, (2) physics consistency tests (energy conservation, monotonicity constraints), and (3) edge cases (zero wave height, extreme wind). Implement three mock LLM agents (or hook them to a real API): Task Manager proposes test sequences, Code Generator writes numpy/pandas code, Evaluator scores on three metrics. Run the loop for 5 iterations. Measure whether the adversarial loop converges (test informativeness increases because harder tests expose more bugs, Code Generator's score improves because repeated feedback on hard tests teaches it physics), and whether the final code respects physics constraints that the single-agent baseline violated because it never saw domain-specific tests.

reliability = (fraction of physics tests passed) + (fraction of edge-case tests passed) - (fraction of uninformative tests passed)

The demo must show that by iteration 3 or 4, the Code Generator's code respects domain constraints (high physics test pass rate) while the single-LLM baseline (same LLM writing code once in response to the same prompt) does not.
