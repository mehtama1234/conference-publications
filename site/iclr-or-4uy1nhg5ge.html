Why Genomic Pretraining Doesn't Always Help

Pretraining on genetic data does not reliably improve performance on genomic prediction tasks, and what you feed the model matters far more than learned weights.

Paper explainersAll themesAI for Science

Scientists built large genomic models by mimicking how language models like ChatGPT are trained: learn patterns from huge amounts of genetic data, then apply that learned knowledge to specific tasks. But this paper reveals a surprising truth: the learned patterns often fail to help, and models with random weights can match or beat pretrained ones, because genomic tasks have simpler structure than language and the way you slice the DNA into pieces matters far more than learned weights. The real bottleneck turns out to be much simpler: how you chop the genetic code into pieces for the model to read.

Zero assumption version

The false promise of pretraining

For years, the language model playbook worked: train on mountains of text, learn general patterns, then fine-tune on specific tasks. Scientists thought the same playbook would work for genetics: train on huge genomic databases, then fine-tune to predict disease risk or identify mutations. The theory was clean: a model that has already seen millions of genetic sequences will recognize patterns that random-weight models would miss.

A beginner would assume pretrained genomic models are obviously better, because they cost vastly more to train and learned weights should give them more knowledge to draw from. So we should expect: pretrained wins, random loses, done. But this paper asks the heretical question: what if we actually tested this assumption?

The finding in one sentence. Random models surprisingly perform as well or better than pretrained models on genomic tasks, suggesting pretraining brings little real gain, because the tokenizer (how you split the DNA code) is such a dominant factor that it overwhelms any advantage learned weights could provide.

The algorithm as a flow

What it actually does

Step 1: Define the benchmark

Gather 52 real genomic tasks (disease prediction, mutation detection, variant effect estimation).

Step 2: Grab seven pretrained models

Take existing genomic foundation models off the shelf, fully trained on millions of sequences.

Step 3: Randomize them

Shuffle every weight to zero out learned knowledge, keeping architecture and tokenization identical.

Step 4: Run the race

Fine-tune both pretrained and random models on each task, measure accuracy or prediction quality.

Step 5: Slice it and re-run

Repeat with different tokenizers (how to break DNA into pieces) to isolate what actually drives gains.

What the paper changes

What the paper changes

The paper changes the assumption about what drives genomic model performance. Instead of asking whether pretraining weights matter most, it reveals that how you tokenize the genetic code (how you slice the DNA into readable pieces) has far more impact than learning the weights.

the object it moves  =  tokenization strategy
The hidden quantity

The hidden quantity: tokenization sensitivity

measured quantity  =  how much a model depends on the slicing scheme

This paper introduces a new lens: tokenization sensitivity. It is the degree to which a genomic model's performance depends on how its input DNA is broken into pieces (tokens), rather than on the learned weights. Think of it as asking: if I hand the model the same information but slice it differently, how much does performance swing?

The paper measures tokenization sensitivity by comparing: (1) a pretrained model with its native tokenizer, (2) the same architecture with a random-weight model using the same tokenizer, and (3) random-weight models with different tokenizers. Large gaps between tokenizers on both models reveal that tokenization is the dominant lever; small gaps between pretrained and random reveal that pretraining brings little reward.

Plain reading. The slicing scheme (tokenizer) controls whether a model does well or poorly on the same genetic task. Two models fed identical DNA sequences but with different tokenization strategies can diverge hugely in accuracy. Pretrained weights rarely rescue a bad tokenizer.
Paper reading. The paper quantifies this via ablation: holding architecture constant, sweeping tokenizers (character, BPE, k-mer) across pretrained and random models reveals variance explained by tokenizer is often 3-5x variance explained by pretraining status. Notably, character-level tokenization permits strong random baselines, whereas k-mer or subword tokenizers partially benefit from pretraining—suggesting that learned weights compensate for tokenization choices that bury information in encoding.
Why it works

Why it works: the three-level lever

The mechanism has three steps. First, the tokenizer is an information bottleneck. DNA is a sequence of four letters (A, T, G, C). If you feed the model each letter separately (character tokenization), the model sees fine detail: every single base matters. If you group letters into chunks (k-mers of length 6, for example), you lose granularity—the model never sees smaller patterns. BPE (Byte Pair Encoding, a method that learns which letter-groups are common) splits the difference. The tokenizer decides what information reaches the model, before learning even begins.

Second, pretraining learns compensation patterns, not fundamental features. When a model trains on mountains of data, it does not learn 'what makes DNA useful.' It learns to work around the tokenizer it was given. If the tokenizer buried important information, pretraining taught the model workarounds—but those workarounds are specific to that encoding. A random-weight model with a good tokenizer does not need workarounds; it can learn the task from scratch because it already sees the right pieces.

Third, genomic tasks have low complexity per piece. Genomic prediction is often highly local: a single base change can flip disease risk, or a nearby motif (a few letters in the right order) can matter. This is different from language, where meaning emerges only from long-range structure. So character tokenization—which preserves every single letter—often suffices. Pretraining helps language models because language needs learned long-range patterns. But genomic tasks often need raw precision at the character level, which pretraining does not improve, because pretraining learns long-range statistical patterns rather than granular single-base sensitivity, and that sophistication is wasted on local genomic phenomena.

Tiny worked example: disease prediction task
Baseline with random model + character tokenizer: 72% accuracy.
Baseline with random model + k-mer tokenizer: 61% accuracy.
Pretrained model + k-mer tokenizer: 63% accuracy.
Pretraining gained only 2 percentage points, but tokenizer choice cost 11 points—tokenizer is 5.5x more impactful.
If we switch the pretrained model to character tokenizer: 71% accuracy (nearly random + character baseline).
The role of pretraining is not to overcome tokenizer limits; it is to squeeze a few more points from whatever alphabet the tokenizer provides.

Acc_task is bounded by what the tokenizer lets through; Gain_pretrain can only add within that ceiling.

What can go wrong

What can go wrong

Applying pretraining from one tokenizer to tasks that need another. If you pretrain with k-mers but the downstream task needs character-level sensitivity (e.g., detecting single-base mutations), the learned weights cannot retroactively fix the tokenization. No amount of fine-tuning recovers the lost granularity.
Assuming scale always helps. A pretrained model trained on more data but with a poor tokenizer can underperform a smaller random model with good tokenization. In genomics, more data does not overcome a bad encoding choice.
Missing clinically relevant mutations. The paper found that current GFMs (Genomic Foundation Models) fail to detect known disease-causing mutations. Even with pretraining, the models do not learn variant-aware objectives, so they embed mutations the same way as benign sequences.
Done right: co-design tokenization and training. Align the tokenizer to the task structure (character-level for local motifs, k-mers for global patterns) and then train, pretrained or random. If you start with the wrong tokenizer, neither pretraining nor scale rescues you.
What a runnable demo should prove

What a runnable demo should prove

A convincing demo trains three models on a genomic task: (1) a pretrained genomic model fine-tuned directly, (2) its architecture with random weights and the same tokenizer, and (3) random weights with a different tokenizer (e.g., character instead of k-mer). Run each to completion. Plot accuracy curves for all three. The demo should make it impossible to miss that: random + good tokenizer often matches or beats pretrained + original tokenizer. This proves the paper's claim that tokenizer choice is the true lever, not pretraining.

pretraining_gain = accuracy_pretrained - accuracy_random (same tokenizer); tokenizer_impact = accuracy_char - accuracy_kmer (same pretrain status)

When tokenizer_impact >> pretraining_gain, you have proven the paper's core insight: in genomics, how you slice the input matters far more than how much you trained.
