Unveiling Downstream Performance Scaling of LLMs: A Clustering-Based Perspective

Predict full benchmark scores before training finishes by grouping tasks whose difficulty rises in similar ways, then fitting separate score-growth curves for those groups.

Paper explainersAll themesOther

Training a very large language model is expensive, so teams want early forecasts of how well the final model will score on downstream tasks. The trouble is that task scores do not rise smoothly. Some tasks stay flat for a while and then jump because they need a minimum capability level before they respond to scale, while others improve steadily because each increase in compute already helps. This paper says the full benchmark set is too mixed to forecast directly. Instead, it groups tasks by how their difficulty changes with more compute, fits score-growth curves inside those more stable groups, and then maps those group forecasts back to the whole benchmark set.

Zero assumption version

Why full-benchmark forecasts are noisy

A full evaluation suite mixes easy tasks, hard tasks, and tasks whose scores wake up only after the model gets much larger. If you fit one global curve to that mixture, the curve chases contradictory patterns. It may fit the easy tasks and miss the late-rising tasks, or it may chase the late jump and overstate the easier tasks. That is why early forecasts for final benchmark scores often wobble or miss by several points.

The paper argues that the hard part is not only model scale. It is task composition. A benchmark average hides many score trajectories under one number, so the average can look erratic even when smaller subsets have clean trends.

The fix. Do not forecast the mixed benchmark first. Split tasks into groups with similar difficulty-growth patterns, forecast those groups, then rebuild the full score.

The algorithm as a flow

What it actually does

1. Measure task score trajectories

Collect how each task's score changes across several model sizes or compute budgets.

2. Build difficulty-growth features

Summarize each task by how fast its score rises, how noisy that rise is, and whether the rise starts late, so that tasks with similar growth behavior can be grouped together.

3. Cluster the tasks

Group tasks whose score trajectories look similar.

4. Fit score-growth curves inside each group

Forecast how each group's average score should change as compute increases.

5. Map group forecasts back to the full suite

Combine the group forecasts into one prediction for the whole benchmark.

What the paper changes

What the paper changes

The paper changes the prediction target from a single benchmark average to a two-stage object: first forecast a stable subset score, then translate that subset forecast back to the full benchmark. This matters because the mixed benchmark average is noisy for structural reasons, not only because the model is still small. By moving through a cleaner intermediate object, the final forecast becomes easier to trust.

the object it moves  =  cluster-level score curves before the full benchmark average
The hidden quantity

The hidden quantity: task difficulty-growth type

measured quantity  =  the pattern that says how a task usually improves as compute increases

Two tasks can have the same current score and still behave very differently later. One may improve steadily with more compute because each extra unit of scale already helps, while another may stay flat until the model reaches a certain scale because the needed capability is missing before that point. The hidden quantity is that task's growth type. If you mix tasks with different growth types, one forecast curve cannot describe them well.

The COD method estimates this hidden type from each task's observed score path. Once tasks with similar paths are grouped together, each group's future score becomes more regular, which makes extrapolation easier because the fitted curve is no longer averaging over incompatible behaviors.

Why it works

Why it works: make the forecast target more regular

Forecasting works best when the target moves in a stable way as scale increases. The full benchmark score often does not, because it mixes tasks with different turning points. COD fixes that by creating groups whose average scores move more smoothly. Each group curve is easier to fit because it describes one dominant pattern instead of many.

The mapping step then turns those cleaner group forecasts into a full-benchmark forecast. That mapping helps because it keeps the noisy benchmark average from driving the whole extrapolation directly. Instead, the full score is reconstructed from parts that each have clearer behavior.

The rebuild equation

First in words:

Full benchmark forecast = mapping function applied to the set of cluster score forecasts

Then the compact form:

Score_full(C) = h( Score_1(C), Score_2(C), ..., Score_K(C) )

Every symbol:

A tiny worked example
Suppose there are three clusters: easy, medium, and late-rise tasks.
At a planned compute level, their predicted scores are 78, 61, and 44.
Assume the mapping uses benchmark weights 0.4, 0.35, and 0.25 for those clusters.
Then the rebuilt benchmark forecast is 0.4 x 78 + 0.35 x 61 + 0.25 x 44 = 63.55.
That forecast is steadier than fitting one curve straight to the full mixed benchmark because each cluster score came from a cleaner trend.

The mapping can be simple or learned, but its job is always the same: convert stable cluster forecasts into the overall score the team cares about.

What can go wrong

What can go wrong

Too few model sizes. If the team only has scores from a couple of training checkpoints, the difficulty-growth features can be noisy because there is not enough history to tell a steady rise from a delayed rise.
Clusters may drift as new tasks are added. A benchmark can change over time. If new tasks follow patterns unlike the old tasks, the old clusters may stop being representative because the benchmark mix has changed.
The mapping back to the full suite can be misspecified. Even if each cluster forecast is good, the final benchmark score can still be wrong if the mapping gives the wrong relative importance to the clusters.
When it works best. COD is strongest when the benchmark contains several recurring task-growth types, because then the cluster split removes real structure rather than just random noise.
What a runnable demo should prove

What a runnable demo should prove

Build a notebook with task scores for several checkpoints of one model family. First fit one curve directly to the whole benchmark average and measure final-score error on a held-out largest checkpoint. Then run COD: compute difficulty-growth features, cluster the tasks, fit one curve per cluster, and rebuild the full forecast. The demo should show that the cluster-first route predicts the held-out benchmark more closely because the intermediate group targets are smoother.

The notebook should also reveal the cluster members. Seeing which tasks sit in the delayed-rise group makes the forecast easier to trust because the source of the late jump is now visible instead of hidden inside the overall average.

forecast_error = abs(predicted_final_score - actual_final_score)
