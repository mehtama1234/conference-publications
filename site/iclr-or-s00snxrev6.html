Vision-Zero: Gamified Self-Play for VLM Training

Train vision-language models by having them play deduction games against each other, generating training data without human annotations.

Paper explainersAll themesOptimization

Current methods for teaching vision models to reason require expensive hand-labeled datasets, limiting how far we can scale. Vision-Zero takes a different approach: it turns any image into a deduction game where the model plays against itself, generating training data automatically. The model learns to reason strategically while figuring out the game's clues, and an algorithm called Iterative-SPO keeps the training improving instead of getting stuck.

Why do VLM training methods cost so much?

Teaching a vision-language model (a model that reads images and answers questions about them) to think through hard problems requires training data. Currently, humans have to label thousands of images and write out the reasoning steps: 'What object is this? How should it be described? What's the answer to this question?' This takes huge effort. COCO Attributes cost $60,480 to label 200,000 objects. Ego4D consumed over 250,000 annotation hours. Visual Genome needed 33,000 annotators.

A beginner might try to just use a smaller dataset, hoping the model learns anyway. But a model trained on thin data either does not learn to reason at all, or it memorizes the specific examples instead of learning the underlying principles. So we are stuck: reasoning requires scale, but scale requires expensive human labels.

In one sentence. The paper makes models generate their own training data by playing games against each other, eliminating the need for human annotation.

What the paper changes

What changes: training mode and data source

Vision-Zero does not change the model's weights directly in a fancy new way. Instead, it changes what data the model trains on: instead of hand-labeled examples, the model trains on the games it played and won or lost. It also changes how training happens: the system alternates between two modes. In self-play mode, the model plays against itself and collects dialogue. In reward mode, the model learns which moves led to winning, guided by a simple scoring rule (who got the most votes wins). The switch between modes is gated by performance metrics, so training knows when to pivot.

The hidden quantity

The hidden quantity: win rate ceiling

measured quantity  =  Performance plateau signal

The core hidden thing Vision-Zero measures is whether the model's win rate (how often it wins games) is stuck or still climbing. In self-play training alone, models often hit a ceiling: they improve fast at first, then stop improving even though you keep training. This happens because the model is playing against a copy of itself, so once both copies converge, there is no more pressure to improve.

Vision-Zero detects this plateau by tracking the win rate across iterations. If the win rate stays high (above a threshold) AND the model is not exploring new strategies (token length stays low, meaning it is repeating the same clues), it signals: time to switch to reward training. Reward training pulls the model in a different direction (optimizing for the vote-scoring rule), which can unstick it. When that mode exhausts itself, the system switches back to self-play. The model estimates this hidden quantity continuously and decides which mode to use next.

To switch back to self-play: error rate must be high OR token count must be high (model needs fresh scenarios). These thresholds are tuned to catch the moment each mode stops helping.
Why it works

Why two modes work better than one

Self-play trains fast at first because the model has an opponent: it tries a clue, the opponent fails to guess, the model learns that clue was good. But after a few iterations, both the model and its opponent converge to the same strategy. The opponent stops failing, so the model stops getting clear feedback—because a failed guess tells the model nothing new, while a successful guess means the model needs to adapt. Progress stalls.

Iterative-SPO breaks the deadlock by switching to reward-based training. Here, the model is not playing against itself; instead, it is optimizing for a concrete scoring rule: 'you win if you get the most votes'. This rule pulls the model in a different direction than self-play did. New strategies emerge because they are good for the new objective. After reward training runs its course, the system switches back to self-play, where the improved model can now beat the old version and learn anew. The two modes feed each other: self-play generates diverse scenarios, reward training sharpens strategy, then self-play keeps exploring. The gating mechanism (watching win rate and token growth) decides when to switch, so neither mode wastes time once it stops helping.

The training loss equation

First in words:

Each iteration, apply the loss for whichever mode is active. If in self-play mode, use the clue-giving loss; if in reward mode, use the decision (voting) loss. The gating variable decides which one is used.

Then the compact form:

L_t = m_t * L_clue(theta) + (1 - m_t) * L_decision(theta)

Every symbol:

L_ttotal training loss at iteration t
m_tmode gate: 1 for self-play, 0 for reward
L_clueloss for generating good clues
L_decisionloss for voting correctly
thetathe model weights
A tiny worked example
Iteration 5: self-play mode, so m_5 = 1. Compute L_clue = 0.8, L_decision = 0.6. Loss = 1 * 0.8 + 0 * 0.6 = 0.8. Update only the clue-generation weights.
Iteration 10: win rate is 75%, above the 70% threshold, and token length is stable. Check reward threshold: not met yet, so m_10 = 1 (stay in self-play). Loss = 0.9. Continue.
Iteration 15: win rate now 76%, token length climbed to 450 words. Switch condition met: m_15 = 0 (reward mode). L_clue = 0.7, L_decision = 1.2. Loss = 0 * 0.7 + 1 * 1.2 = 1.2. Update only the voting weights.
The mode switch isolates which weights get updated, so the model does not confuse the two objectives.

The equation just says: pick one loss or the other based on which mode is active. The real trick is the gating logic that decides when to switch.

What can go wrong

Mode-switching overhead. Toggling between self-play and reward training adds complexity. If the gates are miscalibrated (thresholds too loose or too tight), the model may switch too often or too rarely, wasting iterations.
Game generation bias. The quality of games born from images depends on how well the game scenario fits the image. A poor game teaches nothing. If the image dataset is narrow (e.g., only charts), the model never learns to reason about real-world scenes.
Reward rule design. The voting rule (players with more votes win) is simple, but it may reward shallow deception over true reasoning. A clever model could get many votes by lying, not by understanding the image.
Done right. The paper mitigates these by running on diverse image types (CLEVR synthetic, charts, real-world), validating that self-play does not overfit to one domain. The gating thresholds are tuned empirically, and the reward model is grounded in game-theoretic rules (votes from civilians only, spy roles tracked), so the incentive aligns with actual reasoning.
What a runnable demo should prove

What a runnable demo should prove

Build a small interactive version on a single image: start with self-play mode, have the model generate spy-game clues for 20 iterations, plot the win rate. Observe it flatten around iteration 15. Then manually switch to reward mode for 10 iterations. Observe the win rate climb again. Then switch back to self-play for 10 more. Show that alternation beats staying in one mode. Record the model's clues and guesses in both modes—they should differ, showing that each mode trains different reasoning skills. Finally, ask a human to rate the quality of reasoning in the clues (clever vs. vague). Reasoning quality should improve after the alternation cycle because each mode forces the model to adapt to a new objective, which exercises different parts of its reasoning.

Improvement = (final win rate after alternation) - (peak win rate before switch)

The demo must make it impossible to miss that neither mode alone keeps improving, but toggling between them does.
