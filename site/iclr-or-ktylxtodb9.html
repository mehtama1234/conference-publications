ROGA: Scaling Generalist Agents for Office Productivity Tasks via Tool Generation

An agent that actively watches its environment, keeps a written log of what happened, and remembers how to use tools it has built before.

Paper explainersAll themesAgents & Tool Use

Most office-automation agents today react to one task at a time, forgetting what just happened and regenerating the same tools over and over. ROGA changes that by giving the agent three new abilities: it actively probes the environment to build its own understanding of what is going on, it keeps a written notebook of state changes as tasks progress, and it reuses tools it has already built instead of creating them from scratch every time.

Zero assumption version

The agent forgets and rebuilds

Today's automatic tool-generation agents work by watching what happens, then instantly creating the next tool they need. But real office work is messy: tasks have many steps, things change in ways you can't immediately see, and the same tool gets used again and again.

A naive agent just reacts. It sees a task, builds a tool, uses it once, and forgets. On the next similar task, it builds the tool again from scratch. It also cannot see what is really happening in the office system—only what gets handed to it directly. And it has no way to remember that five steps ago, a document was uploaded or a field was changed.

In one sentence. The agent actively watches the environment, writes down what changed, and reuses tools across tasks.

The algorithm as a flow

What it actually does

Active world modeling

Agent asks the environment questions to uncover hidden state, not just react to what it sees.

Record state changes

Every time something changes in the office system, write it down with a timestamp.

Reason over time

Use the log to understand causality: did this action cause that change, or did something else?

Check if tool exists

When a new task arrives, search the memory for a tool that already does this.

Reuse or generate

If found, reuse it; if not, build it and add it to the library for next time.

What the paper changes

What the paper changes

Most agents only see what is handed to them. ROGA changes what the agent does: instead of passively waiting for state information, it actively asks questions to reveal hidden state. It also writes state changes down instead of forgetting them, and it checks its history before building a new tool.

the object it moves  =  Observation model: from passive to active
The hidden quantity

The state evolution record

measured quantity  =  State history completeness

This is the written log of every state change the agent has witnessed: which field changed, when it changed, and what value it now holds. Without this record, the agent loses context—it cannot tell if a tool's output triggered a downstream change or if something else did. With it, the agent can trace cause and effect over minutes or hours.

The paper measures this by tracking how many actual state changes the agent captures in its log compared to what really happened in the system. A higher completeness means the agent's understanding of the office environment grows more accurate, because if the log contains 90 percent of the real changes, the agent can reason correctly about what triggered what 90 percent of the time—more changes recorded means fewer blind spots where a cause-and-effect chain breaks.

Why it works

Why this fixes the problem

A reactive agent sees one snapshot of the world at a time and instantly reacts. When it sees a form, it fills it; when it sees an email, it responds. But office work is chains of actions. Filling a form might trigger a hidden field to appear. Sending an email might spawn a new task in a queue. The agent has no way to know this happened because it never looked.

ROGA adds three mechanisms. First, the agent stops just reacting—it actively probes: it asks 'what else changed?' after every action. This reveals hidden state. Second, it writes everything down in a state log. This gives the agent a way to reason about causality: 'did my action cause the email to arrive, or did someone send it?' Third, it remembers tools. When a task says 'fill in the same form again,' the agent checks its memory instead of rebuilding the tool from scratch. These three moves let the agent understand the office as a stateful system over time, not a series of isolated snapshots.

The state evolution score

First in words:

State completeness is the fraction of true office-system state changes that are recorded in the agent's log

Then the compact form:

state_completeness = (sum of recorded state changes) / (total actual state changes in system)

Every symbol:

recorded state changesnumber of environment events the agent's probe caught and logged
total actual state changesground truth count of all state-evolution events that occurred
state_completenessfraction between 0 and 1; higher is better
A tiny worked example
True events in office system: (1) form renders with 3 fields, (2) field value changes, (3) email template loads, (4) email is sent. Total = 4.
Agent probes after step 1: detects form, logs 'form rendered with 3 fields'. After step 2: detects field change, logs it. After step 3: misses template load (did not probe), logs nothing. After step 4: detects email sent, logs it.
Agent recorded 3 events out of 4. State completeness = 3/4 = 0.75. The missed probe on the template load means the agent's causal understanding is incomplete.

A higher state completeness score means the agent's written log is more faithful to what actually happened, so it can reason about cause and effect more accurately.

What can go wrong

What can go wrong

Probing overhead. If the agent probes the environment too many times—asking 'what changed?' after every single action—it becomes slow and wastes time. Probes must be targeted or cached.
State log gets stale. If a background service silently updates a field without the agent probing, the log will record the old value. The agent's causal reasoning becomes wrong.
Tool reuse with wrong task. If two tasks look similar on the surface but need different form fields, the agent might reuse a tool built for Task A on Task B, filling the wrong fields.
Done right. Smart probing after key actions (form submission, email send) + validation of reused tools against the current task + periodic full-system scans catch most drifts.
What a runnable demo should prove

What a runnable demo should prove

Build a mock office system with two recurring tasks (e.g., fill form then send email twice in a row). Run an agent with probing off, then on. Measure: time to build tools the first time, time on the second run, and the fraction of state changes the agent logged. The demo must show (1) faster reuse on run 2 when probing is on, because the agent checks memory instead of rebuilding; (2) higher state-log completeness, because active probes catch changes the agent would otherwise miss; and (3) that the reused tool works correctly on both runs, because the state log lets the agent understand the current context and verify the tool is still appropriate.

tool_reuse_speedup = time_to_run_2_without_probing / time_to_run_2_with_probing

The demo must make it impossible to miss: probing + logging enables tool reuse because the agent remembers what it built and remembers the context; without them, the agent is stuck rebuilding every tool from scratch and has no way to know if the office state has changed since the last time it ran.
