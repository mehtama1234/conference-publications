Generalizable End-to-End Tool-Use RL with Synthetic CodeGym

Train LLM agents to use tools correctly and flexibly by rewarding them for solving diverse coding tasks where tools are the only way to get the job done.

Paper explainersAll themesAgents & Tool Use

Large language models work best when they can call external tools—a search engine, a calculator, a function. But training them to do this is hard: most models learn tool-use from static examples and fail on new tools or unfamiliar workflows. CodeGym is a method that turns coding problems into interactive training environments, where the model learns by trial and error, receiving immediate rewards when it solves a problem correctly. Diversity matters because if all training tasks are similar, the model can cheat and memorize patterns instead of learning the true logic. Verifiability matters because the training system needs to know exactly when a tool call succeeded or failed, so the reward signal is clear and tight.

Zero assumption version

Static examples fail on new tools

Today's LLM agents learn tool-use from human-written trajectories: 'to solve this problem, call tool A, then tool B, then report the answer.' This supervised learning works well on the exact training problems, but when you introduce a new tool or a workflow the model never saw during training, it freezes.

A beginner might try to just fine-tune the model on more examples. That does not work: the model memorizes the specific sequences, not the deeper logic of 'when do I need a tool, and which tool should I choose.' It fails because it is learning by description, not by doing.

The real problem. Models trained on static examples do not learn the flexible decision-making logic of tool use; they learn rigid sequences that break on new tools or unfamiliar tasks.

The algorithm as a flow

What it actually does

Synthesis

Convert coding problems into interactive environments by extracting functions as callable tools.

Explore safely

Model tries tool calls; server snapshots the state, executes the call in isolation, rolls back if it crashes.

Reward signal

After many steps, compare the model's answer to the ground truth; reward is 1 or 0.

Train with GRPO

Use reward to nudge model weights: increase the probability of sequences that led to reward=1.

Test on new tools

Evaluate the trained model on entirely new tools and workflows not seen during training.

What the paper changes

What the paper changes

The paper changes the training signal: instead of showing the model static correct examples (supervised fine-tuning), the paper gives the model live feedback (reinforcement learning) from solving diverse coding tasks where it must actively choose when and how to call tools.

the object it moves  =  training method: static examples to live trial-and-error
The hidden quantity

The hidden quantity: action flexibility

measured quantity  =  flexible tool-invocation decision logic

Every time a model learns tool-use, it must discover and encode the implicit decision tree: when facing a new task, which tools are relevant, in what order, and when to stop. This 'tool logic' is what generalizesacross new tools; static training never captures it because it only shows examples, not the causal chains. CodeGym forces the model to discover this logic by rewarding success and punishing failure on diverse tasks, so the learned pattern is deep, not memorized.

The paper measures this indirectly: by testing the model on out-of-distribution tasks (tools and workflows it never saw), they verify that the learned logic is flexible. A model that only memorizes would fail; one that grasped the pattern succeeds.

Why it works

Why it works: learning by doing beats learning by example

Static training shows: 'here is the correct sequence.' The model can memorize the sequence, but if the task or tools change, the memorized sequence is useless. The model never learned the 'why' behind each decision.

Live feedback (reinforcement learning) forces the model to discover the 'why.' Every time the model invokes a tool, it gets rewarded or not. Over time, the model learns: 'when I call tool X in situation Y, I eventually solve the problem'—because the reward is tight, the outcome is clear, and the model has to experiment. The diverse environments mean the model cannot cheat by memorizing; it must abstract the real logic.

The trial-then-overwrite mechanism is the safety net: the model's early attempts will be random and crash—but the server rolls them back, so the environment stays intact. The model learns without destroying the sandbox.

Math after the picture

The reinforcement learning update

First in words:

reward weighted by importance × (good action log probability)

Then the compact form:

loss = -E[reward * log P(action | state)]

Every symbol:

reward1 if the solution is correct, 0 if wrong
log P(action | state)the log probability (how likely the model thought this action was)
E[...]average over many trials
-negative because we minimize loss, which maximizes reward
A tiny worked example
Trial 1: Model calls tool_search on list L. Solves problem. Reward = 1. Log P = -0.5. Loss contribution = -1.0 × (-0.5) = 0.5. Gradient increases the probability of tool_search.
Trial 2: Model calls tool_sort then tool_search on same list. Solves problem. Reward = 1. Log P = -0.3 (the model was more confident). Loss contribution = -1.0 × (-0.3) = 0.3. Gradient boosts this sequence more strongly.
Trial 3: Model calls wrong_tool. Does not solve. Reward = 0. Log P = -0.4. Loss contribution = -0.0 × (-0.4) = 0.0. No gradient; probability does not change.
Over 100 trials, good sequences accumulate small pushes that compound; wrong sequences stagnate. Qwen2.5-32B reaches 75% accuracy on training tasks.

The gradient penalizes confident bad choices and rewards confident good choices; over time, the model's confidence concentrates on the successful tool sequences.

What can go wrong

What can go wrong

Reward is too sparse. If the model must make 10 correct tool calls in a row to get any feedback, learning is slow. CodeGym mitigates this by using intermediate rewards (e.g., reaching a milestone) and diverse tasks (short ones give feedback quickly).
Tool calls crash the server. Early in training, the model is random and calls tools with invalid arguments. Without trial-then-overwrite, these crashes would destroy the environment or wedge the training loop. The snapshot-and-rollback mechanism keeps training stable.
Biased training data. If the synthetic coding problems are all similar (e.g., all array operations), the model learns a narrow pattern. CodeGym's filtering step (removing low-quality environments) reduces overfitting but cannot eliminate it entirely if diversity is low at the source.
Done right. Diverse, verifiable environments combined with safe trial-and-error and reward-based nudging enable the model to learn flexible tool logic, because each task forces the model to discover its own strategy (not memorize), and the clear reward signal trains the successful patterns.
What a runnable demo should prove

What a runnable demo should prove

Build a small set of coding tasks (5–10) covering different tool combinations: sort, search, merge, filter. Train a small model (e.g., Qwen2.5-7B) on these tasks for 50 steps using GRPO. Then test it on two new tasks: one using familiar tools in a new order, and one using a tool the model never saw before. Measure accuracy on both.

generalization_gain = OOD_accuracy_trained - base_accuracy_untrained

If the trained model scores higher on both new-order and new-tool tasks than an untrained baseline, you have proven that the model learned flexible tool logic, not memorized sequences.
