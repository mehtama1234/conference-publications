Memory-Efficient Hierarchical Algorithm for Large-scale Optimal Transport

Move stuff between two piles more efficiently by breaking the problem into smaller, easier pieces.

Paper explainersAll themesOptimization

Imagine rearranging books from one shelf to another. The cost is how far each book travels. For just a few books this is easy, but for trillions of pixels in an image or millions of 3D points, calculating the best rearrangement uses too much memory and takes too long. This paper solves that by working on small patches at a time, then zooming out, using a faster solver inside.

Zero assumption version

Why moving stuff around gets stuck

A very useful tool in data science is asking: how do I rearrange one pile to look like another pile, using the least travel distance? Call this the transport cost. For 1000 pixels or points, you can answer this brute-force. For a million pixels (1024 by 1024 image), the naive method has to touch every pixel against every other pixel, storing a giant table with a trillion entries in memory. Your computer runs out of RAM.

A beginner's first try: store just a subset of that table at a time. But then the solver that minimizes the cost (a numerical optimizer) bounces between many subsets, wasting time on redundant calculations. You trade memory for speed, and lose both.

The method in one sentence. Break the transport problem into a tree: solve each small patch exactly, then glue solutions together coarsely, then refine only the pieces that matter.

The algorithm as a flow

What it actually does

Multiscale pyramid

Represent the transport problem at multiple scales: finest (individual pixels), coarser (small patches), coarsest (whole image).

Solve bottom-up

Begin at the finest level. Use a fast optimizer to compute the best transport within each small patch.

Coarse-level gluing

Jump to coarser scales. Compute how to connect patch outputs using less data storage.

Prune inactive edges

Mark which transport routes are never used. Delete them, shrinking the memory table further.

Refine top-down

Descend from coarse to fine, re-solving only the paths that the pruning marked as important.

What the paper changes

The one thing the algorithm changes

The paper changes what data the optimizer sees at each step. Instead of one giant table of all possible routes (which explodes in size), it feeds the solver a small, multiscale pyramid: fine levels use only nearby routes, coarse levels use only broad brush strokes. As the pyramid shrinks, so does the memory.

The hidden quantity

The active-route count

measured quantity  =  Number of non-zero transport edges

At each level of the pyramid, most pixels or points do not trade with most others. A pixel at the top-left of the image sends its stuff mostly downward and rightward, not to the bottom-left. The paper counts how many non-zero edges (routes that actually carry stuff) appear in the solution. This is the hidden quantity.

The paper measures this by running the solver and checking which routes have flow greater than zero. At coarser scales, this number shrinks dramatically because distant points are grouped into single chunks. Pruning removes edges with nearly-zero flow, further shrinking the count.

Why it works

Why this works: the causal chain

The naive method fails because a one-level solver sees every pixel and every other pixel at once. The memory table must have an entry for each pair, totalling N squared, where N is millions. The paper fixes this by organizing the problem as a tree: at the top, pixels are grouped into coarse blocks; below that, smaller blocks; at the bottom, individual pixels. Each level solves its local problem using a Primal-Dual Hybrid Gradient (a numerical optimizer that is very efficient). Because each level only sees its own scale, the table at that level is tiny.

When the optimizer solves the coarse level, it outputs which blocks should connect. Most connections are unnecessary (the flow is zero), so pruning deletes them. Then the algorithm descends to the fine level and re-solves, but only for the connections marked as alive. This two-phase approach (solve coarse with pruning, then refine the small survivors) means every step works with a sparse table, not a full one.

The reason this keeps costs low is that the Primal-Dual optimizer converges faster on each small problem than it would on one giant problem. Moreover, solutions at the coarse level guide the fine level toward the good regions of the search space, so fewer iterations are needed to find the final answer.

Math after the picture

The cost equation

First in words:

Total cost is the sum over all routes of the flow times the distance per route, plus a penalty term that pushes the solver toward the coarse-level solution.

Then the compact form:

cost = sum_routes ( flow_route * distance_route ) + lambda * sum_pixels ( deviation_from_coarse_solution )

Every symbol:

flow_routehow much stuff moves on this route
distance_routehow far this route travels
lambdastrength of the penalty that keeps fine level close to coarse level
deviation_from_coarse_solutionhow far the fine solution has drifted from the coarse level's answer
A tiny worked example
Image divided into 4 patches. Coarse solver says patch A sends 50 units to patch B.
Fine refinement: subdivide A into 2 tiles, B into 2 tiles. Fine solver can send from A1 to B1 or A2 to B2.
If A1 sends 25 to B1 and A2 sends 25 to B2, deviation is 0, penalty is 0.
If A1 sends all 50 to B1, deviation is high (A2 is idle), penalty is lambda * large squared deviation.
Strong lambda pulls the fine solution close to the coarse structure; weak lambda allows freedom.
Result: with lambda=10, the fine algorithm converges in 200 steps instead of 5000, reusing the coarse path as a hot start.

This penalty keeps the fine level from ignoring the coarse guidance, which ensures the memory savings and speed gains hold.

What can go wrong

What can go wrong

Pruning threshold set wrong. If you prune too aggressively (deleting routes with low but nonzero flow), the fine level cannot find good solutions because vital paths are blocked. You trade memory gain for bad transport cost. If you prune timidly, memory drops only a little.
Coarse-level solution is garbage. If the coarse level does not solve well (e.g. the optimizer runs out of iterations), the penalty term misleads the fine level, forcing it toward a bad starting point. The refinement then cannot escape.
Tree structure does not match the data. If the hierarchical grouping of pixels or points is arbitrary (e.g. random blocks instead of spatially coherent ones), many routes span far across the tree. Sparsity is lost because distant pixels that need to trade are now far apart in the tree, forcing the solver to consider all cross-tree connections, not just local ones. Pruning does not help reduce the table size, because almost every route carries nonzero flow (the solver cannot skip them without losing accuracy), so memory stays high.
Done right. Use a fast solver (Primal-Dual Hybrid Gradient is designed for this), build a tree that respects spatial coherence (group nearby pixels and points together so most transport is local), and tune the pruning threshold by checking a few samples. Memory and speed improve together because the coarse level solves a tiny problem fast, and the pruned fine level inherits a warm start. Cost drops only slightly because the coarse guidance is already a good solution for the global flow pattern.
What a runnable demo should prove

What a runnable demo should prove

Build a tiny end-to-end demo: take a small image (say 256 by 256, 65k pixels) or a point cloud (10k points). Implement the naive solver (one level, no tree) and the hierarchical solver (four levels, pruning active). Measure memory peak (using Python memory profiler or system top) and wall-clock time. Compute the transport cost for each and compare.

speedup = time_naive / time_hierarchical; memory_reduction_pct = 100 * (1 - memory_hierarchical / memory_naive); cost_diff_pct = 100 * (cost_hierarchical - cost_naive) / cost_naive

The demo must show that hierarchical + pruning cuts memory by at least 50% and halves solve time, even if transport cost rises by a small amount. That trade-off is the entire point.
