Towards Whole-corpus Reconstruction of Heterogeneous RAG Knowledge Bases

GeoEx reconstructs mixed-source RAG corpora by planning globally in a proxy retriever space, so that extraction does not stall inside one semantic pocket.

Paper explainersAll themesAgents & Tool Use

A deployed RAG service can leak the corpus behind it. The usual extraction attack asks a question, reads the returned fragment, then tries nearby questions in the hope of walking through the corpus piece by piece. That local strategy breaks down when the corpus comes from many unrelated domains, because neighboring questions in one domain do not point toward distant domains. GeoEx tackles the whole-corpus problem by planning globally in the coordinate system of a proxy retriever, then turning chosen coordinates into executable queries. It also mixes broad cross-domain moves with dense local probing, so that the attack can both discover new regions and empty out regions it has already found.

Zero assumption version

Why heterogeneous corpora break local extraction attacks

A local extraction attack assumes that nearby answers lead to nearby useful next queries. That can work inside one topic area because small wording changes often reveal more of the same cluster of documents.

A heterogeneous corpus is different because one service may mix finance, law, science, products, and internal policy. There are large discontinuities between those regions, so a method that only walks locally can get trapped in one part of the corpus and miss the rest. The paper asks how to cover the whole collection without knowing its domains in advance.

The paper's move in one sentence. Plan query exploration in a global proxy retriever space and alternate broad jumps with local probing, so that extraction can move across unrelated domains and still recover dense content inside each discovered region.

The algorithm as a flow

What it actually does

Step 1: Use a proxy retriever as a planning surface

Represent possible queries in the proxy model's coordinate system so that exploration can reason about global coverage.

Step 2: Choose broad exploration points

Synthesize far-apart candidates because distant moves are needed to reach unrelated domains.

Step 3: Convert planned points into text queries

Run the inversion module so that planned coordinates become queries accepted by the target service.

Step 4: Probe densely around useful discoveries

Apply local perturbations after a region is found because nearby queries can then recover more of that cluster.

Step 5: Repeat broad and local moves together

Alternate the two behaviors so that extraction gains both whole-corpus reach and dense recovery inside each region.

What the paper changes

What the paper changes

The paper changes corpus extraction from a purely local query walk to a two-scale planning procedure that combines global coverage moves with local dense probing.

the object it moves  =  two-scale corpus extraction planner
The hidden quantity

The hidden quantity: coverage breadth

measured quantity  =  how much of the unseen corpus the next query plan can reach instead of revisiting one discovered region

The central quantity is coverage breadth. Recovering one cluster very thoroughly is not enough when the real goal is whole-corpus reconstruction.

GeoEx increases coverage breadth by planning in a proxy coordinate system and by making deliberate cross-domain jumps. That matters because each broad move can expose a new region that local walking would never reach.

Why it works

Why it works

The proxy retriever gives a usable global surface because the attacker needs a way to plan coverage before seeing the hidden corpus directly. Without that surface, every step depends only on the last extracted fragment.

Broad exploration points matter because unrelated domains can be far apart in the service's content structure. A deliberate far move can find a new domain where local continuation would fail.

Local perturbations still matter because once a region is found, nearby queries often recover many related fragments efficiently. The method works because it joins these two scales instead of choosing only one.

A compact extraction objective

First in words:

Choose query plans that maximize newly recovered corpus content while spending as few service queries as possible.

Then the compact form:

J = coverage_gain(plan) - lambda * query_count(plan)

Every symbol:

Jthe extraction objective
coverage_gain(plan)new corpus content recovered by the current broad-plus-local query plan
query_count(plan)number of service queries used by that plan
planthe chosen mix of broad exploration points and local probes
lambdaweight on query cost
A tiny worked example
Suppose local probing recovers three more finance fragments from a region that is already known.
A broad jump reaches a medical region and returns the first two fragments from that domain.
The broad jump may return fewer total fragments at first, but coverage gain is larger because it opens a new part of the corpus.
The next step then applies local probing inside the medical region so that extraction becomes dense after discovery.
The best plan is the one that balances these two effects because whole-corpus reconstruction needs both.

The objective highlights the paper's main tradeoff: spending queries on new regions versus spending them on dense recovery inside a known region.

What can go wrong

What can go wrong

The proxy retriever may not match the target service well. If the planning surface is badly misaligned, broad moves can waste queries because the chosen points do not correspond to useful target-service behavior.
The coordinate-to-query conversion may be weak. If planned points are turned into poor text queries, coverage drops because the target service never reaches the intended region.
The method may overspend on broad jumps. Too much exploration can reduce dense recovery because the attack keeps leaving useful regions before extracting them thoroughly.
Done right. The approach works when broad jumps discover new regions and local probes then empty those regions efficiently, because the two scales support each other.
What a runnable demo should prove

What a runnable demo should prove

Build a small hidden corpus made of several unrelated domains and place it behind a RAG interface. Compare a baseline that always writes the next query from the most recent fragment with a two-scale system that first plans broad points in a proxy retriever surface and then probes locally after each discovery.

The demo should show better whole-corpus coverage at the same query budget for the two-scale system because cross-domain jumps find regions that local continuation never reaches.

coverage = recovered_unique_documents / total_documents; efficiency = recovered_unique_documents / total_queries

The decisive evidence is higher whole-corpus coverage under the same query budget, because the planner combines discovery of distant regions with dense follow-up inside each region.
