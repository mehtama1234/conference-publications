TusoAI: Agentic Optimization for Scientific Methods

An AI agent that automatically builds and improves computational methods for scientific problems by reading papers, organizing domain knowledge, and iteratively testing code.

Paper explainersAll themesAI for Science

Scientists spend months writing code to analyze experimental data. Instead of manually coding each method, TusoAI is an agent that reads scientific papers, captures what experts know, and then builds and refines computational methods automatically. It mimics how a scientist actually works: gather domain knowledge from papers (so you know what approaches are proven), form hypotheses by trying different combinations of those approaches (so you explore the high-quality region instead of all code), test each method on real data (to see which one actually works), diagnose what went wrong (so the next iteration targets specific failures), and improve by focusing on fixes (because feedback is faster than blind search).

Zero assumption version

Scientists manually build computational methods

Every scientific problem needs custom code. A geneticist studying disease might need to analyze single-cell RNA data, but existing software doesn't quite fit their question. So they read papers, study methods, write code, test assumptions, find bugs, rewrite. This takes months.

A naive scientist would try one approach from a paper, code it up, and submit. But that rarely works well because the paper assumes different data or different goals. The scientist needs to adapt the method, test whether their assumptions hold, diagnose failures, and improve, because every dataset is slightly different and methods that worked for the authors' data may fail on yours. This adaptation loop is slow and manual: each iteration takes hours of coding and debugging.

The problem in one sentence. Building custom computational methods for science is slow because scientists must manually search the literature, write code, test assumptions, and fix problems iteratively.

The algorithm as a flow

What it actually does

Gather domain knowledge

Retrieve up to 10 top papers from Semantic Scholar, create a 15-point technical summary from each paper's methods section.

Build optimization categories

Draft candidate categories (e.g., normalization method, filtering strategy) from the task, then refine using insights from paper summaries.

Create instruction lists

For each category, draft 10 candidate instructions (e.g., 'use z-score normalization' or 'apply log transformation'), refined by papers.

Iteratively sample and test

Sample a category, pick 3 candidate instructions from it, choose the most promising, generate code, evaluate on the task, diagnose failures.

Return optimized method

After many iterations (with runtime budget), output a computational method that solves the task better than baseline approaches, because many small improvements from domain-guided search compound into methods that experts missed.

What the paper changes

What the system changes: instructions for building computational code

TusoAI does not change the data or the task. It changes the instructions that an AI agent follows to build and refine computational methods. Instead of one fixed prompt, TusoAI builds a knowledge tree: organized categories (normalization, filtering, feature selection) with multiple concrete instructions per category. This tree is then used to guide the agent's search for the best method.

the object it moves  =  the instruction tree
The hidden quantity

The domain knowledge tree: how structured knowledge guides the search

measured quantity  =  domain knowledge tree (categories and instructions)

The hidden quantity is the knowledge tree itself: a structured organization of how domain experts solve similar problems. Each node is a category (what to optimize, like 'normalization method') and each category contains multiple instructions (concrete choices, like 'apply z-score' or 'use log scale'). This tree is not visible in the final code output, but it controls which solutions the agent will consider.

TusoAI estimates this tree by reading papers: it extracts the methods section (up to 1,200 words), summarizes technical content, and iteratively refines categories and instructions to reflect what experts actually do. The tree is the blueprint; without it, the agent would search blindly through all possible code.

Why it works

Why it works: turning unstructured expert knowledge into a searchable structure

The core mechanism is this: experts know what to try because they have read papers and built intuition. But that knowledge is scattered across papers, locked in human brains, and hard to systematize. TusoAI extracts it by reading the same papers an expert would read, organizing the tactics they see (normalization methods, filtering tricks, validation checks), and then using that organized knowledge to guide a search algorithm.

Here is the causal chain. First, the agent reads papers and creates summaries, because papers encode the scientific reasoning that has worked before. Second, from those summaries, it builds categories and instructions, because organizing tactics into a tree makes them discoverable and comparable. Third, during search, it samples categories and instructions, because this steers the search toward good solutions without having to try all combinations. Fourth, for each candidate, it evaluates the code on the actual task data, because only real feedback tells you if the method works for this specific problem. Finally, it diagnoses failures (e.g., 'training curve shows overfitting') and focuses new iterations on instructions that address those failures, because diagnosis guides the search toward fixing real problems instead of random guessing.

Without the knowledge tree, an agent searching over all possible code would need trillions of trials. With the tree, it searches only the high-quality region that experts have already validated. The tree is not the final answer; it is the map that guides the exploration.

Math after the picture

The optimization objective: find the method that maximizes the evaluation score

First in words:

find the solution (code and its parameters) that achieves the highest score on the evaluation function, by iteratively sampling instructions from the domain knowledge tree, testing candidates, and following diagnosis signals

Then the compact form:

s* = arg max_{s in S_domain} h(s), where S_domain is the space of code reachable by instructions from the knowledge tree, and h(s) is the evaluation score (e.g., AUC, enrichment)

Every symbol:

s*the best method found by TusoAI
S_domainthe set of all code methods that can be built using instructions from the knowledge tree
S_fullall possible Python code (infinite and mostly useless)
h(s)the evaluation function that scores a method s (e.g., area under the ROC curve, precision at top-k)
arg maxfind the method that gives the highest score
A tiny worked example
Task: maximize AUC on disease gene prediction.
Evaluation: h(s) scores each candidate method s by running it on labeled data and computing AUC.
Without knowledge tree: explore all 10^100 possible Python scripts. Each evaluation takes 2 seconds. Time needed: longer than the age of the universe.
With knowledge tree (6 categories, 10 instructions each): explore 10^6 combinations (normalization x filtering x clustering x validation x metric x ensemble). Time: 10^6 candidates * 0.2 seconds = ~23 days. Still slow, but TusoAI prunes based on feedback, often finding a good method in 1,000 iterations = 200 seconds.
Key insight: the knowledge tree shrinks the search space from 10^100 to 10^6, making automated search feasible.

The math formalizes the idea: we search within a domain-specific region (reachable by expert instructions) rather than all code, and feedback from the evaluation function guides the search.

What can go wrong

What can go wrong

Method is scattered across multiple functions. If the scientific method is implemented in many separate files or functions, TusoAI struggles because it optimizes one function at a time. Scattered code breaks the assumptions about how to modify and test.
Domain knowledge papers are poor quality or contradictory. If the top papers retrieved are outdated, poorly written, or give conflicting guidance, the knowledge tree will encode noise instead of wisdom. Bad summaries lead to bad instructions.
Evaluation function is misleading. If the score h(s) does not reflect what scientists actually care about (e.g., AUC but not interpretability), TusoAI will optimize for the wrong thing, finding a method that scores well but is useless in practice.
Runtime budget is too tight. If the optimization is cut off too early (too few iterations), the agent will not have time to explore and improve, because each candidate method takes time to evaluate and diagnosis takes multiple iterations to bear fruit. A budget of 30 seconds may find only a naive solution; TusoAI needs at least 2-3 minutes per task.
Done right. When domain papers are high-quality, the method is monolithic, the evaluation function is well-defined, and runtime is sufficient (several minutes), TusoAI consistently outperforms expert baselines by discovering domain-specific tricks (e.g., a specialized normalization for single-cell RNA that experts missed).
What a runnable demo should prove

What a runnable demo should prove

Build a demo on a single-cell RNA analysis task (disease gene prediction) or a scientific deep learning task (e.g., protein structure prediction). Supply TusoAI with the task description, the evaluation function (AUC on held-out test data), and access to domain papers via Semantic Scholar. Run TusoAI for 5 minutes. Collect the best method it found. Compare its AUC to (1) expert hand-coded baseline and (2) a generic ML agent that ignores domain knowledge. The demo must show that TusoAI's method beats both baselines because it discovered domain-specific tactics that generic agents do not know.

performance_gain = (AUC_TusoAI - AUC_expert_baseline) / AUC_expert_baseline

By organizing domain knowledge into a searchable tree instead of leaving it scattered in papers, TusoAI finds better methods than experts can design by hand in the same time budget, and vastly better than agents that ignore domain knowledge.
