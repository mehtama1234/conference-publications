R-WoM: Retrieval-augmented World Model For Computer-use Agents

When an AI agent plans ahead in a computer environment, ground its predictions in retrieved real information instead of hallucinated knowledge.

Paper explainersAll themesAgents & Tool Use

Large language models can act as world models, predicting what happens when an agent takes an action in a digital environment. But they make up facts and forget details outside their training data, leading to wrong predictions that spiral into larger failures over long sequences of actions. R-WoM fixes this by retrieving actual, up-to-date knowledge from tutorials and using that to correct the model's predictions.

Zero assumption version

Models that make up facts lead to spiraling failures

An AI agent navigating a computer (clicking buttons, filling forms) needs to predict what will happen next. A language model trained on text can guess, but it only knows things it saw during training. A new app or an updated website looks different, and the model hallucinates details, confusing the agent.

A beginner approach: ask the model to simulate forward N steps to plan. But if step 2 is wrong, step 3 is based on false state, and by step 10 the simulation is completely off. The agent then tries actions that make no sense in the real world.

The fix: Retrieve factual, current knowledge about the environment from tutorials or documentation, and use that to anchor the model's predictions to reality.

What the paper changes

What the paper changes

The paper does not change the language model itself. Instead, it changes the input the model sees before predicting. By retrieving factual knowledge and including it in the model's context, the predictions become more accurate.

the object it moves  =  retrieved context
The hidden quantity

The accuracy decay over steps

measured quantity  =  prediction error at step N

As an AI predicts further into the future (step 1, step 2, step 3), errors from earlier steps pile up. A small mistake early becomes a huge mistake later. The paper measures how quickly this error grows.

R-WoM estimates this by testing the model on three tasks: next-state identification (step 1 only, low decay), full-procedure planning (all steps, high decay), and milestone transition (key state changes). By retrieving real knowledge, the paper slows how fast errors accumulate.

Why it works

Why retrieving facts makes predictions stick to reality

A language model trained on text sees patterns. It learned that buttons usually appear in certain places, and that forms usually have submit buttons. But when the world is new or changed, the model has to invent details. Retrieval fixes this: before the model predicts, it searches a database of real tutorials or documentation for the exact environment. This gives the model concrete facts instead of just patterns.

With those facts in hand, the model's prediction is grounded. It does not hallucinate button positions—it sees them in the tutorial. It does not guess what a field means—it reads the documentation. Each prediction is cheaper to get wrong because it is built on anchored information. The error does not snowball as far.

The prediction loss with and without retrieval

First in words:

The model predicts the next state by comparing its guess to the real observed state. Retrieval changes the input context so the guess is closer to the truth.

Then the compact form:

loss = sum_t (1 + decay_factor^t) * distance(predicted_state_t, true_state_t)

Every symbol:

losstotal error over all steps
decay_factorhow much error grows per step without facts (0.8 to 1.2)
tthe step number (1, 2, 3, ...)
predicted_state_tmodel guess for the environment after action t
true_state_twhat really happened in the environment
A tiny worked example
Without retrieval: Step 1 error = 0.5, Step 2 error = 0.8 (0.5 * 1.6 decay), Step 3 error = 1.28 (0.8 * 1.6). Total = 2.58.
With retrieval grounding: Step 1 error = 0.4, Step 2 error = 0.45 (0.4 * 1.1 lower decay), Step 3 error = 0.5 (0.45 * 1.1). Total = 1.35.
Same early mistake, but retrieval keeps the decay factor low. Later steps stay close to truth.

Retrieval lowers the decay factor by anchoring predictions to real facts, so error does not spiral as fast.

What can go wrong

What can go wrong

Tutorial is outdated or wrong. If the retrieved knowledge is stale, the model learns incorrect facts and predicts worse. The system must keep tutorials fresh and verified.
No relevant tutorial exists. On a brand-new or very custom environment, retrieval finds nothing. The model falls back to hallucination and error spirals return.
Retrieved facts are too specific. A tutorial for one exact button layout does not help on a similar but different page, because the model learns that specific position and tries to click there on the new page, failing. Retrieval must fetch general-enough knowledge to transfer.
Done right. With a large, maintained database of tutorials and general guidance about common interfaces, retrieval more than doubles the accuracy of long-horizon planning. The agent can now reliably execute multi-step tasks instead of drifting into false states.
What a runnable demo should prove

What a runnable demo should prove

Build a simple computer-use environment (e.g., a mock form-filling task or a simple web navigation task). Train or instantiate a language model as the world model. Create a retrieval database with tutorials describing the environment. Run two versions: one that predicts without retrieval, one with retrieval. Measure how accurate each version is at predicting states after 1 step, 3 steps, 5 steps, and 10 steps.

accuracy = (correct_state_predictions / total_predictions) per step. Plot accuracy vs step count for both versions.

The retrieval version should stay above 60% accuracy at step 10, while the baseline should drop below 40%. That gap is the whole contribution: facts stop error from spiraling.
