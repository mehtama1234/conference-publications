Optimas: Optimizing Compound AI Systems with Globally Aligned Local Rewards

Each part of a multi-component AI system gets its own reward scorecard tuned to stay in sync with the whole system's success.

Paper explainersAll themesAgents & Tool Use

A modern AI system often chains together many different parts—a language model, a calculator tool, a retriever, a classifier—each tuned by different methods (prompts, numbers, weights). Optimizing all of them together is like tuning an orchestra where the instruments cannot hear each other. This paper proposes giving each component its own local reward signal that is guaranteed to align with the system's overall performance, so each part improves independently without stepping on the others' toes.

Zero assumption version

Many components, but no way to tune them together

Real AI systems today are not single models. They are pipelines: a language model generates text, a tool executes the request, another module scores the result, and so on. Each component solves a different job and sits in a different place in the code. Each also uses a different kind of tuning knob—language models are tuned through prompts and model weights; tools have settings like search depth; classifiers have their own training.

The problem: there is no single score that measures how well each part works in isolation. If the language model writes a better prompt at its job (breaking down the user's request), the tool might receive a clearer instruction and execute better—or the tool might not understand the new phrasing at all. Tuning one piece in darkness breaks others because you cannot measure whether your change helped or hurt downstream. You cannot just run each part separately and score it, because a part only creates value when it feeds into the next part. Without feedback showing how your change rippled through the pipeline, you are steering blind.

In one sentence. Give each component a reward signal that measures its actual contribution to the system's final answer, so tuning each part independently improves the whole because you can now see what actually helps and what hurts.

The algorithm as a flow

What it actually does

Measure whole-system output

Run the full pipeline and score how well the final answer solves the task.

Work backward from each component

For each part, test small changes and measure: does nudging this component's output move the final answer? A big shift means this component is critical. A tiny shift means it is disconnected.

Create a local reward per component

Build a scorecard for each part that mirrors the global goal: if this component's contribution grows (measured by its downstream impact), the local score rises to match.

Tune each component using its local reward

Each part independently improves its local score because a rising local score now tells it that its contribution to the system is growing—verified by the backward trace from the measurement step.

Keep rewards synchronized

Periodically re-measure the whole system and re-calibrate each component's scorecard to stay aligned, because system behavior can shift and what was important before may change.

What the paper changes

What the paper changes

Optimas builds a new kind of signal: a per-component reward function that measures each part's downstream impact on the system. This works because the function is calibrated backward from the system's final success, so a rising local reward means that component's changes are genuinely helping the end-to-end goal, not just locally optimizing in a dead zone.

the object it moves  =  per-component reward functions
The hidden quantity

The hidden quantity: local-global alignment

measured quantity  =  local-global alignment score

The paper's core hidden quantity is how much each component's local reward correlates with the whole system's global score. This is the alignment. High alignment means: if component A's reward goes up, the system performance is very likely to go up, because A's reward was calibrated to measure A's real downstream contribution. Low alignment means the component's reward is useless for tuning—improving it does not help the system because the local reward drifted out of sync and now measures something unrelated to global success. Alignment ranges from 0 (random noise) to 1 (perfect sync).

Optimas measures alignment by simulating small changes to each component and tracking whether its local reward and global score move together. The algorithm continuously re-measures this to keep every component's reward synchronized, because the system's behavior and component importance can shift over training.

Paper reading. Formally, each component (call it c) gets a local reward function (call it R) that satisfies local-global alignment: the expected improvement in global performance increases with R. Why it works

Why tuning local rewards keeps the system in sync

The core mechanism is this: a component's output only matters if it affects the next component's input, which only matters if that affects the final output. Optimas traces this chain backward. For component A (say, the language model), it computes: if A's output shifts by 1%, how much does the final system score shift? This tells you how much A contributes. Optimas then builds a local reward function for A that measures exactly this: is A's contribution increasing?

The core observation is that this local reward, if properly calibrated, is a miniature version of the global goal. If A's reward is high, A is doing its job well—and since A's job is to feed into B, which feeds into C, which solves the task, the downstream impact of A's good performance eventually lifts the final answer, which is what the local reward measures. Optimas re-measures this alignment in each iteration and tweaks the per-component rewards to stay synchronized. Because each local reward is re-anchored to the global score, tuning to raise any single component's local score must also raise the system total—the mechanism that guarantees this is the re-measurement step, which ensures no component ever optimizes for the wrong proxy.

The local reward alignment equation

First in words:

For each component, the local reward is constructed so that the expected change in global score equals the expected change in the component's local reward, measured over variations in the component's output.

Then the compact form:

E[Delta_global | Delta_local_c > 0] >= E[Delta_global | Delta_local_c < 0]

Every symbol:

E[·]average value over many trials
Delta_globalchange in the system's final score
Delta_local_cchange in component c's local reward score
>=indicates monotone alignment: if local reward goes up, global score is more likely up
A tiny worked example
Component LLM outputs a prompt. LLM reward = 60. Global system score = 74.
Tweak LLM prompt slightly. New LLM reward = 65 (improvement of 5). New global system score = 78 (improvement of 4).
Alignment check: LLM reward went up AND global score went up. This confirms alignment. Optimas trusts this LLM reward to guide future tuning.
If instead global score had dropped to 72, alignment would break. Optimas would reweight the LLM reward function to re-sync.

The equation encodes one rule: every component's local reward must move in the same direction as the global score, or the system falls apart.

What can go wrong

What can go wrong

Misaligned local reward from the start. If the local reward for a component is poorly calibrated and does not actually correlate with global performance, tuning it will harm the system. Optimas prevents this by measuring alignment before using a component's reward, but if the measurement is wrong, the system can drift.
Component operates in a dead zone. If a component's output has little effect on the final answer (it is already doing well, or it does not connect to the rest of the pipeline), its local reward is nearly random. Optimas can notice this, but it means that component cannot be reliably tuned.
Rewards oscillate instead of stabilizing. If components are updated too frequently and reward functions are re-calibrated too often, the system can chase its tail. Component A improves, its reward function shifts because the global score changed, component B now sees a different signal and adjusts, then A's reward breaks again because B's change re-shifted the baseline. The feedback loop becomes a closed loop chase, not convergence. Optimas needs a careful update schedule (update components, then recalibrate rewards, then wait) to break the oscillation.
Done right. Measure alignment frequently, tune components only when their rewards are clearly in sync, and re-measure after each round of tuning. This keeps the system stable and all improvements genuine.
What a runnable demo should prove

What a runnable demo should prove

Build a simple compound system: a language model that writes retrieval queries, a retriever that fetches documents, and a reader that extracts an answer. Implement Optimas local rewards and compare against tuning each component separately. The demo should show three separate plots: one for each component's score over iterations. With Optimas, all three should rise steadily because each component's reward measures its actual impact and stays in sync. Without Optimas, at least one component should stall or fall as the others improve because tuning one part in the dark breaks downstream components—for example, a better retriever query causes the reader to fail on the new format.

system_improvement = (global_score_with_optimas - global_score_baseline) / global_score_baseline

The demo succeeds when you see all three component rewards rising in parallel, instead of some parts improving while others regress, which proves the alignment mechanism is working.
