AgentSelect: Benchmark for Narrative Query-to-Agent Recommendation

Turn agent selection into a recommendation problem where a user's narrative request must be matched to an agent's capability profile, not just to a popular identifier.

Paper explainersAll themesAgents & Tool Use

As more deployable agents appear, choosing the right one becomes a problem of recommendation. A user writes a narrative request such as 'summarize legal emails and draft a reply with citations,' and the system must recommend a full agent configuration that can actually do that job. Existing benchmarks do not test this well because they score isolated components and rarely provide query-conditioned supervision for end-to-end agent choice. AgentSelect builds that missing benchmark.

Zero assumption version

Picking a deployable agent is different from ranking a single model

A deployable agent is more than one model. It can include prompts, tools, routing rules, and other configuration choices that determine what tasks it can do in practice. Existing leaderboards usually score one part at a time, such as language quality or one tool benchmark, so they do not directly teach how to choose a full agent for a user's request.

The supervision is also sparse in a difficult way. Many recommendation systems work well when the same popular items are chosen again and again. In agent recommendation, a long narrative request may point to a rarely chosen agent with a very specific capability mix. That makes simple identifier-based methods fragile, because the system must understand the request content and the agent profile instead of relying on repeated popularity.

The benchmark's framing. Treat the task as query-to-agent recommendation, because the recommender must map user intent to agent capabilities under long-tail supervision.

What the paper changes

What the paper changes

The paper changes the unit of evaluation. Instead of asking whether one component scores well in isolation, it asks whether a system can recommend the right end-to-end agent configuration for a narrative user request.

the object it moves  =  what gets recommended
The hidden quantity

The hidden quantity: how much request meaning overlaps with agent capability

measured quantity  =  Intent-capability match

Intent-capability match is the amount of overlap between what the user is asking for and what a candidate agent can actually do. This overlap matters more than raw popularity when supervision is long-tail, because the correct agent may appear only a few times in the data.

The benchmark reveals this hidden quantity by aligning narrative queries with capability profiles. If the query needs browsing plus code editing plus structured output, the right agent is the one whose profile contains that combination. Recommendation improves when methods read both sides in content form, because matching meaning is more reliable than memorizing frequently reused identifiers.

Why it works

Why a unified recommendation benchmark matters

The benchmark matters because agent selection happens at the system level. A user does not care whether one language model or one tool router scores well in isolation; the user cares whether the full deployed agent can do the requested job. Evaluating recommendation directly makes the research target match that practical decision.

The data construction is important because no single existing source contains enough query-conditioned agent choices. AgentSelect unifies many fragmented artifacts into one interaction table, which creates training and evaluation data for recommendation methods. That matters because it lets researchers compare approaches on the same task definition instead of on incompatible leaderboards.

The long-tail finding explains why content-aware methods help because many agents appear only rarely, so memorizing identifiers is weak supervision. Reading the request and the capability profile is stronger because the meaning of the job changes smoothly across queries even when the exact agent names do not repeat often.

The ranking objective

First in words:

A recommendation method assigns a score to each query-agent pair, and good performance means positive interactions receive higher scores than other candidates for the same query.

Then the compact form:

rank_score = match(query_intent, agent_profile)

Every symbol:

query_intentthe needs expressed in the user's narrative request
agent_profilethe capability description of a deployable agent
matchthe scoring function used by the recommender
rank_scorethe value used to sort candidate agents for the query
A tiny worked example
Query asks for reading documents, using a spreadsheet tool, and drafting a report.
Agent A can write well but has no spreadsheet tool, so its match score is limited.
Agent B has spreadsheet support but weak document handling, so its score is also limited.
Agent C supports document reading, spreadsheet use, and structured reporting, so it receives the highest score.
The recommender succeeds because it matches the request content to the capability profile.

The benchmark stresses ranking quality under long-tail data, so a method must score rare but suitable agents above popular but incomplete ones.

What can go wrong

What can go wrong

Profiles are too shallow. If the agent profile says little about tools or limits, the recommender cannot match requests to actual abilities.
Positive-only interactions hide near misses. If the benchmark records only successful pairings, some methods may struggle to learn what makes one capable agent better than another closely related one because the data gives little evidence about which near-miss profile should rank lower.
Query wording drifts across sources. If one source uses formal task descriptions and another uses casual language, methods may overfit to surface style instead of matching the underlying need.
Done right. The benchmark is most useful when capability profiles are detailed and source normalization is careful, because then the recommendation task reflects actual deployable agent choice rather than metadata quirks.
What a runnable demo should prove

What a runnable demo should prove

Build a small marketplace with ten agent profiles and twenty narrative user requests. Give each profile a list of supported actions, tools, and output styles. Train one baseline that uses only agent identifiers and one baseline that reads both the request and the profile text. The demo should show that content-aware ranking does better on rarely selected agents because it can recover the fit between intent and capability even when a profile has almost no interaction history.

top1_success = queries_where_best_agent_ranked_first / total_queries

The main lesson should be that agent recommendation is a matching problem, because the right choice depends on the request's capability needs rather than on general popularity alone.
