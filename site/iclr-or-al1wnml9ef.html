Speculative Speculative Decoding

Instead of waiting for each prediction step before guessing the next, guess many possible paths ahead of time and pick one when verification arrives.

Paper explainersAll themesEfficiency & Systems

Generating text in a large language model is bottlenecked because each token (a word or fragment) must be produced one at a time. Speculative decoding speed this up by using a fast draft model to guess the next few tokens, then checking them all at once in the big slow target model. Saguaro takes this further: while the target model is checking one set of guesses, the draft model guesses many possible futures at the same time, caches them, and picks one instantly if the check confirms a path it already guessed.

Zero assumption version

Why generating text one token at a time is painfully slow

When a language model generates text, it works step by step: guess the first word, then based on that word guess the second, then the third, and so on. Each guess requires a forward pass (running the entire neural network). This is purely sequential — you cannot guess word three until word two is decided, even though the model would theoretically do almost the same computation for all three at once.

A naive approach: just run the big model K times to get K tokens at once. This works but wastes time on a slow model that does not need to run this many times; we only need its opinion on a few high-uncertainty spots.

Speculative decoding fixed this by using two models: a fast draft model guesses several tokens ahead, then the target model checks them all in one parallel forward pass. This buys latency (time to produce one token). But there is a remaining sequential dependence: the draft cannot prepare its next guess until it sees which tokens the target accepted or rejected.

The problem in one sentence. Speculative decoding still waits for the target to verify before the draft can plan the next batch of guesses.

The algorithm as a flow

What it actually does

Set up a cache

Before verification starts, the draft model computes speculations for many possible verification outcomes.

Verification runs in parallel

While the target model checks the current guess, the draft model is not blocked; it has already prepared.

Outcome arrives

Target model returns how many tokens were accepted and which bonus token was sampled.

Cache lookup

If this outcome is in the cache, return the pre-computed speculation immediately.

Fallback if miss

If outcome is not cached, run a backup draft to generate it, then proceed to next round.

What the paper changes

The one thing that changes

Speculative decoding has a secret wait: after verification finishes, the draft model must speculatively generate the next batch from scratch, which is sequential. Saguaro eliminates this wait by pre-computing thousands of possible next batches during verification and storing them in a cache.

the object it moves  =  Speculation timing: from after verification to during verification
The hidden quantity

The hidden quantity: Cache hit rate

measured quantity  =  Fraction of verifications that land in the cache

A cache hit is when the verification outcome (how many tokens were accepted, which bonus token was sampled) matches something the draft model already predicted and cached. A hit means zero overhead — the speculation is returned immediately. A miss means the draft must fallback and re-generate, which costs latency.

The paper estimates this by analyzing which verification outcomes are most likely given the draft model's logits (its confidence scores for each token). It pre-computes speculations for the top outcomes: the ones that verification is most likely to produce. This is done using constrained optimization: given a budget of cache entries, allocate them to the verification outcomes that the draft is most confident will occur.

Why it works

Why pre-caching speculations eliminates the bottleneck

Standard speculative decoding works like this: draft model runs on a fast device, target runs on a slow device. They are sequential: draft predicts, then target verifies. The target takes 100 milliseconds. During those 100ms, the draft is idle waiting. Then draft generates again (takes 10ms), then target verifies again. The total is 110ms per round.

Saguaro runs them in parallel. During the target's 100ms verification, the draft model is not idle — it is computing many possible futures at once and caching them. By the time verification finishes and returns its outcome, the draft has already computed the answer for that outcome. The outcome lookup takes microseconds. Now both models run together: total time is still 100ms but you generate more tokens, so per-token latency is lower.

The draft model can afford to do many speculations at once because they are independent forward passes. It costs compute but not latency, since they run in parallel with verification. If the draft pre-computes the 10 most likely outcomes out of 1000 possible, and verification actually produces one of those 10 outcomes 90 percent of the time, then 90 percent of the time there is zero overhead.

Math after the picture

The speedup equation

First in words:

Speedup from Saguaro is approximately: (latency of target model forward pass) divided by (latency of target pass plus expected cost of draft fallback, weighted by cache miss rate)

Then the compact form:

speedup_SSD = T_target / (T_target + (1 - p_hit) * T_fallback)

Every symbol:

T_targettime for target model to verify one batch (milliseconds, fixed)
T_fallbacktime for draft to generate when cache misses (milliseconds, amortized)
p_hitfraction of verifications that hit the cache (a number between 0 and 1)
1 - p_hitmiss rate: how often fallback is needed
A tiny worked example
Suppose T_target = 100 ms (target is slow), T_fallback = 5 ms (draft fallback is fast), and p_hit = 0.9 (cache hits 90% of the time).
Then speedup_SSD = 100 / (100 + (1 - 0.9) * 5) = 100 / (100 + 0.5) = 100 / 100.5 = 0.995x.
That is almost no speedup; the fallback overhead kills it. But if p_hit = 0.99, speedup = 100 / 100.05 = 0.9995x ≈ 1x, meaning you get the parallelism benefit.
If p_hit = 1.0 (perfect cache), speedup = 100 / 100 = 1.0x; draft is free, target is the only cost, and you scale token generation 2-5x (the paper's claimed improvement).

When cache hit rate is high, fallback cost is negligible, and the draft model becomes free. The paper's key challenge is raising hit rate to this threshold via smart pre-caching.

What can go wrong

What can go wrong

Cache miss when outcome is unpredictable. If the verification outcome is rare or the draft model is weak at predicting outcomes, cache misses spike and the fallback becomes the bottleneck. The entire batch stalls waiting for fallback generation.
Too many pre-speculations waste compute. If the cache is too large, the draft model spends so much time pre-computing every possible outcome that it becomes the bottleneck, not verification. The parallelism vanishes.
Weak draft model cannot predict verification outcomes. If the draft model and target model disagree heavily on which tokens are likely, the draft's pre-computed outcomes will not match reality, and hits plummet.
Done right. Carefully choose the draft model (should be scaled to balance compute with prediction accuracy), tune cache size to the batch size, and use constrained optimization to allocate cache to the most likely outcomes.
What a runnable demo should prove

What a runnable demo should prove

Build a tiny language model inference engine with two models: a small fast draft and a larger slow target. Implement standard speculative decoding and Saguaro. Run both on the same input (e.g. a GPT-2 model on a short prompt), generating 50 tokens. Measure total wall-clock time (latency), number of cache hits, and number of fallback calls. Show that Saguaro's total latency is lower and cache hit rate is high, above 90 percent. Vary the cache budget and show the tradeoff: a small cache costs less compute but misses more often, a large cache hits more often but costs more draft compute. This reveals the hidden quantity: when you spend more compute to make the cache bigger, you hit more often, which means fewer fallbacks and lower total latency.

Total latency = time to generate 50 tokens end-to-end; Cache hit rate = (cache hits) / (total speculations); Speedup = (autoregressive time) / (Saguaro time)

The demo must show that Saguaro's total latency is 2-5x lower than the baseline (generating one token at a time), and that most of the win comes from cache hits eliminating fallback overhead.
