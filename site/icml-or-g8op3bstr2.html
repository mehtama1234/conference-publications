Differentiable Weightless Controllers: Learning Logic Circuits for Continuous Control

A control method replaces deep neural networks with sparse logical circuits that run on hardware chips in microseconds instead of milliseconds.

Paper explainersAll themesRobotics & Control

Robots need to make split-second decisions on battery power. Deep neural networks are too slow and power-hungry for this. This paper shows how to train a controller using standard learning techniques, then compile it into a hardware circuit made of logic gates and lookup tables instead of multiply operations. Logic gates run in nanoseconds—a million times faster than neural nets on CPUs—because they are wired directly into silicon with no loops or memory waits. Lookup tables also use orders of magnitude less energy because each comparison is a single gate, not a multiply-accumulate. The controller still steers the robot well because the sparse logic learns which sensor bits matter and uses them efficiently.

Zero assumption version

Why deep networks fail on real robots

Robots have to respond instantly to their sensor inputs. When a quadrotor tilts, it must correct the tilt in microseconds or it crashes. When a mobile robot detects an obstacle, it must steer away immediately.

Deep neural networks are matrices of numbers, and running them means doing millions of multiply-and-add operations. Even on a fast computer this takes milliseconds; on a robot's battery-powered chip it takes seconds. The other problem is power: each multiply burns energy. A robot flying for one hour cannot afford neural networks that gulp kilowatts.

The naive approach is to just shrink the network: use fewer numbers, use smaller precision. But that barely helps latency, because the multiply operations still happen. And it breaks the learned behavior—the robot becomes jerky or crashes.

The bottleneck: matrices of numbers cannot run fast or cheap. Replace the multiply operations with truth tables built from logic gates, so the chip decides what to output by just checking a few bits of the input, no math at all.

The algorithm as a flow

What it actually does

Input encoding

Convert each sensor reading to a binary string by checking which range it falls in.

Logic layer 1

Ask a set of small lookup tables: if the input bits match this pattern, output this.

Logic layer 2

Take layer 1 outputs, feed them to another set of lookup tables for deeper reasoning.

Output aggregation

Combine the bits from layer 2 by counting how many are on in each group.

Output decoding

Turn the result bits back into motor speeds: which ranges should the motors be in?

What the paper changes

What changes: the internal computation

Standard neural networks compute an action as: take the input, multiply by matrices, add biases, apply nonlinearities, repeat. Every step involves real-number math.

Differentiable Weightless Controllers replace those matrix operations with logic gates. Each layer is a set of lookup tables—in hardware this is just RAM and combinational logic. There are no weights to multiply, no accumulator to add into.

the object it moves  =  matrix multiplies to logic lookup tables
The hidden quantity

The hidden quantity: connectivity patterns in the logic

measured quantity  =  Sparse input-to-LUT connections

In a standard neural network, every input connects to every neuron in the next layer. This dense wiring is one reason they are slow and power-hungry: each connection must be checked.

The paper measures something new: which input bits actually matter for each decision. Because lookup tables have only a few inputs (the paper uses 2 or 3), only a small subset of sensor bits can feed into each lookup table. As training progresses, the network learns to use only the bits that carry useful information. The connectivity becomes sparse.

This sparsity matters: once training is done, you can look at the circuit and see directly which sensor values control which decisions. A neuroscientist looking at a brain would call this interpretability. An engineer building hardware calls it knowing what to wire.

Why it works

Why it works: the speed and efficiency come from the structure

Standard neural networks are slow because every multiply-and-add takes time, and there are millions of them. To decide what to do, the chip must: load a number from memory, load a weight from memory, multiply them, add the result, load the next weight, multiply again, and so on. Each step is a separate operation. Even on a fast chip, all these operations take microseconds.

Lookup tables are different. A lookup table is just a small chunk of memory arranged so that you can hand it some input bits as an address and get the output instantly. In hardware, this is literally just connecting the input wires as address lines to a small RAM. There is no multiply. There is no add. No loop. It just happens in one step, reading the table once. When the hardware is a chip called an FPGA (field-programmable gate array), this read is purely combinational logic: the answer is literally already there in the wiring, no clock cycle needed.

The second piece is encoding the inputs. Real sensor values are decimals like 2.37. The first step converts these to binary by asking: is the input bigger than threshold 1? Bigger than threshold 2? Etc. This builds a binary string. This encoding step is also just comparisons and a lookup table—no math. So from the sensor reading to the final output, there are only two layers of lookup tables plus encoding and decoding. Everything fits in one or two clock cycles on an FPGA. One clock cycle is one nanosecond per gigahertz. A modern FPGA runs at 100 MHz to 500 MHz, so this is 2 to 10 nanoseconds.

Math after the picture

The equation: how the learning works

First in words:

Loss is whatever reinforcement learning uses (the paper uses standard RL algorithms). Training adjusts the lookup table contents to minimize the loss, using gradients. The encoding and decoding layers have learnable parameters (the thresholds and the output scaling). The gradients flow through the non-smooth lookup-table operation using straight-through estimation: the paper treats the lookup as if it were a smooth function during backprop, then rounds the result when deploying on hardware.

Then the compact form:

loss = RL_loss(actions, trajectories); gradients wrt LUT_contents = d(loss) / d(LUT); update LUT_contents via SGD

Every symbol:

RL_lossthe standard loss from reinforcement learning (how badly the robot is doing)
LUT_contentsthe table of output bits, indexed by input bits
gradientswhich direction to change the table to reduce loss
SGDrandom gradient descent, the update rule (nudge down the gradient)
thresholdsthe comparison points for encoding inputs into bits
A tiny worked example
Scenario: a lookup table takes 3 input bits and must output 4 bits. There are 2^3=8 possible input patterns.
The table has 8 entries. During training, the learning algorithm (which uses gradients, i.e. directions that shrink error) adjusts the bits in each entry.
Entry 0 (input 000): was (0,1,1,0), gradient says pull bit 0 to 1, so update to (1,1,1,0). Loss improves.
Entry 1 (input 001): was (1,0,0,1), gradient tiny, no change, stays (1,0,0,1).
After training one million steps, each entry has tuned to the robot control task.
Deployment: read input bits from sensors, use them as address into table, read output bits directly into motor hardware. No gradients, no training, pure lookup.

Training adjusts the lookup tables using gradient descent, just like neural networks. Deployment is pure table lookup, no math.

What can go wrong

What can go wrong

Task is too complex. If the control task truly requires the fine discrimination of a large neural network, the lookup tables may not have enough capacity. For simple tasks like walking or pole balancing, the sparse logic is sufficient. For tasks that need to recognize subtle patterns, the DWC may not fit the required behavior.
Input encoding is crude. The thermometer encoding (checking ranges) is coarse. It loses information. If the control decision depends critically on the exact real-valued sensor reading, converting it to ranges throws away precision and hurts performance.
Number of lookup table inputs limited. Each lookup table takes only a handful of input bits (the paper uses 2 to 6). If controlling the action requires combining information from 20 different sensor channels in a subtle nonlinear way, you cannot express this in a single table. You need the second layer of logic, which adds latency and complexity.
Done right: verify the network is interpretable. After training, inspect the learned sparse connectivity. Do the input-to-logic connections make physical sense? For instance, does the lookup table that decides forward speed take input from the joint angles, not the camera? If the learned structure is nonsensical, the network may have overfit or found a shortcut. Retrain or add constraints.
What a runnable demo should prove

What a runnable demo should prove

Build a simple control task: a cart-pole system where a cart moves left-right on a track and a pole is balanced on top. Train a Differentiable Weightless Controller to balance the pole, using standard reinforcement learning (e.g., the SAC algorithm). In parallel, train a standard neural network on the same task as a baseline.

After training, measure three things: (1) final task performance—does the DWC balance the pole for as long as the neural net? (2) Latency—how long does each policy take to compute an action? (3) Interpretability—print the learned lookup table contents and the sparse connectivity. Do the bits that feed into each table correspond to sensor dimensions that make physical sense?

task_score = average_return_over_100_episodes; latency_ms = time_per_action; interpretability_check = fraction_of_connections_that_match_expected_input_usage

The demo must make clear: identical task performance, but nanoseconds instead of milliseconds, and you can see what the circuit is doing by reading the table.
