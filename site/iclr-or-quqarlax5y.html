Mixture-of-World Models

Instead of one big model for all tasks, use multiple small experts that each specialize in some tasks, with a router that picks the right expert for each one.

Paper explainersAll themesReinforcement Learning

In multi-task reinforcement learning, a single model must learn to control many different games or robots with very different rules. A naive single model tries to handle all tasks at once but fails at each one because it is trying to remember too many different things at the same time. This paper shows you can train one agent that performs almost as well as 26 separate task-specific agents, using 50% fewer numbers to store.

Zero assumption version

One model, many broken rules

In reinforcement learning, an agent learns to control something (a game, a robot arm) by watching what happens after each action. In multi-task learning, one agent must control many different things: Atari games that have completely different rules, or robot arms that need to do different jobs. A naive approach is to train one big neural network (a model with billions of numbers stored as weights) to handle all tasks. But this does not work well: the single model tries to compress information about Pac-Man, Breakout, and Space Invaders into one set of weights, and each task pulls the model in different directions. The model wastes capacity remembering the rules of every game instead of getting really good at any one.

In model-based reinforcement learning, the agent first learns a world model (a neural network that predicts what happens next), then uses that model to plan ahead. But when a world model tries to predict dynamics (what the next frame looks like) for 26 different Atari games at once, it learns a blurry average that is bad at all of them.

The problem in one sentence: One big model struggles because it has to remember too many different rules at once, wasting capacity.

The algorithm as a flow

What it actually does

Cluster tasks by their dynamics

Measure which tasks learn the same way. Group tasks with similar patterns together.

Compress each task's pixels

Train separate compressors (one per task or per cluster) to turn raw game frames into small lists of numbers.

Route based on the task

When the agent is playing Pac-Man, route to the expert weights trained on fast-moving games.

Predict the next state

Use the selected expert plus a shared core model to forecast the next frame and reward.

Plan and act

Use the world model predictions to imagine future states and pick actions that lead to high rewards.

What the paper changes

What the paper changes

Instead of storing one large set of weights (the numbers the model uses), the system stores a shared backbone plus small expert branches and a task-specific router. When the agent plays a task, the router picks which expert to activate, so the agent uses only a fraction of the total numbers at once.

the object it moves  =  Expert routing per task
The hidden quantity

Learning-direction task similarity

measured quantity  =  Task clustering signal

The paper measures which tasks are alike by computing learning directions (which way to nudge weights to improve performance) for each task separately, then finding tasks whose learning directions point in similar ways. Tasks with similar dynamics (like two fast-moving Atari games) have learning directions that align, while very different tasks (like a maze game and a shooting game) have learning directions that point different ways. This tells you which tasks can share the same expert weights.

The paper computes these learning directions during training and uses them to assign tasks to clusters. Each cluster gets its own expert branch in the dynamics model, and a central router (a small network) learns to predict which cluster a task belongs to based on the current game frame or task identity marker.

Why it works

Why routing saves space and keeps performance high

A monolithic (single-part) world model is like one huge filing cabinet where all task information is crammed together. When you try to retrieve information about Pac-Man, you sift through sheets about Breakout and noise. A mixture-of-experts model is like multiple smaller filing cabinets, each one organized for a specific kind of game. When you need Pac-Man information, you open only the fast-games cabinet. The shared backbone (central core information every task needs, like how objects move in pixels) stays in one place; the expert branches (specialized details for each cluster) are small and separate. The router is the filing clerk that reads the task and opens the right cabinet. This way, each cabinet is smaller and more focused, so the model stores information more compactly. The total number is fewer parameters (smaller filing cabinets) but the same information is available because related tasks share an expert. Because the experts are task-specialized, the dynamics predictions (predictions of what happens next) are more accurate than a single blurry model, so planning works better.

The gradient-based clustering is the key: it automatically finds tasks that have compatible learning directions (tasks where the same weight changes help both). By grouping these tasks together and giving them a shared expert, the model avoids forcing conflicting constraints into one weight. This reduces interference between tasks and lets the learned model compress information efficiently without sacrificing accuracy.

Math after the picture

The routing mechanism in one equation

First in words:

The final prediction is a weighted sum over expert predictions. The weight for expert k is the router output (a probability between 0 and 1) for that cluster, multiplied by how much expert k specializes in the current task. This is called a gating mechanism.

Then the compact form:

next_state = sum_k router_k(task) * expert_k(compressed_frame, task)

Every symbol:

next_stateprediction of what the environment looks like after the action
router_k(task)probability that task belongs to expert cluster k, computed by the router network
expert_k(compressed_frame, task)prediction from expert k, given the compressed visual input and task identity
sum_kadd up the weighted contributions from all expert clusters
A tiny worked example
Say there are 3 expert clusters. The router sees Pac-Man and outputs probabilities: Expert 1 (fast games) gets 0.7, Expert 2 (maze games) gets 0.2, Expert 3 (shooting) gets 0.1.
Expert 1 predicts next frame as list A. Expert 2 predicts list B. Expert 3 predicts list C.
Final prediction is 0.7 times A plus 0.2 times B plus 0.1 times C. Result is mostly A (Pac-Man is fast) with small pieces of others.
If Pac-Man frame had slight maze features, router dials Expert 2 up to 0.35, blending more. Router learns what works.

The router is like a confidence meter: it tells you which expert to trust, and the final prediction is a blend of all experts weighted by that confidence.

What can go wrong

What can go wrong

Router gets confused by a new task. If a task is unlike any of the training clusters, the router assigns probability mass to multiple experts, and the prediction is a muddy blend. The agent does not know which expert to trust.
One cluster dominates, others unused. If the task clustering is bad (for instance, if all tasks were grouped together), one expert becomes a catch-all and others are wasted. The routing does not help because the router sends all tasks to the same expert anyway, which is back to the original monolithic problem.
Slow initial learning. The router itself must be trained to pick the right expert. Early on, the router makes random choices, so the agent gets noisy learning signals. This slows the initial ramp-up.
Done right: adaptive focus. The gradient-based clustering automatically finds tasks with aligned learning directions, so experts are well-specialized. The router learns quickly which expert each task needs. The model balances focus and generalization.
What a runnable demo should prove

What a runnable demo should prove

Build a toy multi-task environment with 6-10 tasks of two or three types (e.g., fast-moving games, slow-moving games, maze-like games). Train a single model on all of them, then train the same architecture with a router and 2-3 expert branches. Measure performance on each task separately.

Average performance = sum of success rates per task, divided by number of tasks. Compare single model vs. routed model. Also count total parameter memory used.

The routed model should beat the single model on all tasks and use noticeably fewer total parameters (aim for 30-50% reduction). The router should reliably pick the right expert for each task type.
