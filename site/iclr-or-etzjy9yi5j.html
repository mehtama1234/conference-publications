DAComp: Benchmarking Data Agents Across the Full Lifecycle

DAComp reveals that today's best data agents fail at the full pipeline—they struggle not with writing single queries, but with orchestrating multi-step data engineering and reasoning through messy real business problems.

Paper explainersAll themesDatasets & Benchmarks & Evaluation

Real data work has two phases: first you engineer raw sources into clean, queryable tables (a multi-step job that touches schemas, SQL, and evolving requirements), then you analyze those tables to find actionable insights. Most benchmarks test only one piece. DAComp tests both, with 236 real-world tasks, and it shows a hard truth: today's best agents fail badly at orchestration and open-ended reasoning, not just code generation.

The Pipeline Gap

Data agents today are tested on tiny slices: 'write a SELECT query on this table' or 'fix this schema bug.' Real enterprises don't work that way. A single business question—'how much revenue did we lose to product returns last quarter?'—demands ten steps: locate raw data across systems, clean corrupted fields, join multiple tables, handle schema changes, run exploratory queries, spot patterns, and argue why they matter. Agents face two totally different kinds of work: (1) engineering — careful, rule-based, runs once correctly or fails loud; (2) analysis — open-ended, iterative, no single right answer. Today's benchmarks test neither fully.

A beginner might build a quick evaluation: 'run 100 SQL queries, check if the output is right.' But that misses what agents really fail at. They can write a single query. They shatter when asked to orchestrate five queries across mismatched schemas, or to reason about which insights matter when results are ambiguous. Existing benchmarks hide this by breaking the work into isolated tasks.

The real test. Test agents on the full pipeline: engineer multiple tables from messy sources, then analyze those tables with strategic reasoning under ambiguity.

The algorithm as a flow

What it actually does

Phase 1: Data Engineering

Agent receives raw schemas and requirements, must design and build SQL pipelines that join, clean, and aggregate data from multiple sources under evolving constraints.

Phase 2: Data Analysis

Agent analyzes the engineered tables through iterative exploration, hypothesis testing, and open-ended reasoning to answer a business question.

Execution Scoring

Engineering tasks scored on whether the pipeline runs, produces correct output schema, and handles edge cases—all-or-nothing or partial credit.

LLM-Judged Scoring

Analysis tasks scored by a reliable LLM-judge using detailed rubrics—does the agent find real patterns and explain them in business terms?

Diagnosis

Low scores pinpoint where agents fail: orchestrating multi-step flows, reasoning about incomplete information, or justifying conclusions.

The hidden quantity

The Orchestration Bottleneck

measured quantity  =  Orchestration capability (multi-step pipeline reasoning)

The paper identifies a hidden quantity: how well can agents orchestrate multi-step workflows? This is separate from code generation skill. An agent might write correct SQL on isolated queries but fail to chain them together, handle schema mismatches, or plan the order of operations. DAComp measures this by requiring agents to build entire pipelines, not single queries.

The paper estimates orchestration capability by scoring end-to-end pipeline execution (did all steps run? do intermediate tables match? does the final output match the requirement?) and separately scoring analysis reasoning (did the agent identify real patterns? are the conclusions justified given the data?). Together these expose orchestration gaps that single-query benchmarks hide.

Why it works

Why Two Phases Expose What One Phase Misses

A single-query benchmark hides orchestration gaps because each query runs in isolation, with a known schema and a right answer. The agent either produces the output or it doesn't. Real work demands something different: you must build five queries in order, where each one depends on the previous, and failures cascade. If query 2 returns a different schema than expected, query 3 breaks. An agent that can hallucinate a working query when given all the context will fail when forced to adapt mid-stream.

Open-ended analysis is a separate test: given the engineered tables, interpret messy results. Patterns are real but ambiguous. An agent must ask clarifying questions, propose hypotheses, and justify conclusions in business terms. This is not code generation—it is reasoning. By splitting the benchmark into both phases, DAComp measures orchestration as distinct from code-writing and reasoning as distinct from rule-following. Low scores on each phase reveal different bottlenecks: orchestration failures show agents cannot plan; analysis failures show agents cannot reason under ambiguity.

Scoring the Two Phases

First in words:

Execution score is all-or-nothing or partial credit on engineering tasks (does the output schema match and are values correct?). Analysis score is computed from LLM rubric ratings on reasoning quality (from 0 to 1 per criterion, averaged). Overall performance is the weighted average of both phases, unmasking which bottleneck dominates.

Then the compact form:

overall_score = (alpha * eng_pass_rate) + (beta * llm_rubric_score); where eng_pass_rate is 0 to 1 (fraction of engineering tasks fully correct) and llm_rubric_score is 0 to 1 (average rubric rating on analysis tasks), alpha + beta = 1

Every symbol:

eng_pass_ratefraction of data engineering tasks that passed (output schema correct and values match)
llm_rubric_scoreaverage score given by the LLM judge using hierarchical rubrics (0 to 1)
alphaweight for engineering tasks (controls how much engineering counts)
betaweight for analysis tasks (controls how much analysis reasoning counts)
A tiny worked example
Suppose an agent attempts 5 engineering tasks, passes 1 (SQL pipeline runs, schema matches): eng_pass_rate = 1/5 = 0.2
On 3 analysis tasks, the LLM judge rates reasoning quality: task A gets 0.8 (identified key pattern, justified), task B gets 0.4 (found a pattern but reasoning was shaky), task C gets 0.3 (mostly hallucinations). llm_rubric_score = (0.8 + 0.4 + 0.3) / 3 = 0.5
If alpha = 0.5 and beta = 0.5: overall_score = 0.5 * 0.2 + 0.5 * 0.5 = 0.1 + 0.25 = 0.35 (35%, below 40% average)

The formula is simple, but it exposes a hard truth: agents fail at both orchestration and reasoning, and neither failure is hidden by testing one in isolation.

What can go wrong

What can go wrong

Cascade failures on engineering tasks. If an agent misestimates the intermediate schema (output of step 1), step 2 tries to reference a nonexistent column and fails. The agent must detect this and recover, but today's agents rarely do.
Hallucinated data or columns. An agent might assume a table has a 'customer_region' column when it doesn't, then reference it in step 5. The pipeline looks plausible in text but crashes at execution. Single-query tests hide this because the schema is given.
Reasoning without evidence. On analysis tasks, agents confidently state conclusions ('revenue dropped because of product returns') without checking the data iteratively. The LLM judge catches this via rubrics and scores it low. In production, this is dangerous.
Overconfidence under ambiguity. When multiple explanations fit the data, agents usually pick one and defend it rather than acknowledging uncertainty. DAComp's rubrics reward careful hedging and exploration; agents optimized for confidence lose here.
Done right: multi-stage execution. Agents that validate intermediate results, ask for clarification when schemas don't match, and explore multiple hypotheses before concluding tend to score higher on both phases.
What a runnable demo should prove

What a runnable demo should prove

Build a small instance of DAComp: three tables with evolving schemas (users, orders, returns), an engineering task ('build a pipeline to compute return rate per region, handle the schema change in the returns table from dates to date ranges'), and an analysis task ('what regions have above-average return rates, and why might they?'). Run an agent against it. Measure: (1) does the engineering pipeline run end-to-end without hallucinating columns? (2) does the analysis task prompt iterative exploration and evidence-based reasoning, or does the agent jump to a conclusion? Log each query and intermediate schema to expose where orchestration fails.

engineering_success = 1 if pipeline_runs_and_schema_matches else 0; analysis_quality = rubric_score from 0 to 1 (did agent iterate? did it check hypotheses? did it hedge uncertainty?); overall = 0.5 * engineering_success + 0.5 * analysis_quality

The demo must make it impossible to miss: the same agent that writes correct SQL in isolation fails when forced to chain steps together and reason about ambiguous business results.
