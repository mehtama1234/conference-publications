DAComp: Benchmarking Data Agents

DAComp is a benchmark that splits data agent evaluation into two distinct challenges: engineering multi-stage SQL pipelines and reasoning through open-ended analytical problems.

Paper explainersAll themesDatasets & Benchmarks & Evaluation

Building an intelligent data assistant requires two very different skills that existing benchmarks blur together. You need agents that can engineer—turn raw tables and schemas into a working pipeline of SQL transformations—and agents that can analyze—explore data, spot patterns, and write a report. DAComp separates these and tests both with 236 realistic tasks from enterprise workflows.

The invisible gap in agent benchmarks

Existing benchmarks treat data work as a single skill: write some code, get a right answer. In reality, enterprise data teams do two completely different things. Data engineering is about designing and building a pipeline—taking raw data sources and transforming them step-by-step through schemas you've never seen. Data analysis is about exploration and storytelling—reading results back, spotting the surprising number, writing a business report. When you blur these two together in one benchmark, you cannot tell which skill is actually broken.

A naive approach: create a single benchmark with data problems and score every agent the same way—give them a question, run their code, check the output. This fails because a data engineer and a data analyst use totally different strategies. The engineer starts by reading schemas and designing a multi-step plan. The analyst starts by poking at data, asking follow-up questions, and iterating. One benchmark cannot fairly measure both.

The bottleneck is hidden: you only see that the agent failed, not why—was it bad at writing SQL, bad at thinking through a complex pipeline design, or bad at reasoning about what a number means?

In one sentence. DAComp separates data engineering (schema-aware pipeline design) from data analysis (open-ended reasoning) and scores each with its own evaluation method.

The algorithm as a flow

What it actually does

Split the pipeline

Define data engineering tasks (architecture, implementation, evolution) and data analysis tasks (open-ended exploration).

Build task collection

Gather 236 real enterprise workflows: DE tasks from 73 SaaS domains with complex SQL, DA tasks as business questions on analytical-ready data.

Score engineering deterministically

Run the agent's code against the schema; check if each layer is correct or omitted. No ambiguity—code works or it does not.

Score analysis with a rubric

Use an LLM judge guided by a hierarchical rubric: multiple valid analytical paths, each with its own scoring criteria.

Expose the bottleneck

Measure both; publish results showing which agents fail at engineering versus analysis, revealing the distinct gap.

What the paper changes

What the paper changes

Previous benchmarks bundle schema understanding, pipeline design, and analysis reasoning into one task. DAComp splits them into two separate evaluation tracks and introduces a second scoring method: execution-based verification for engineering (does the code satisfy the schema?) and rubric-guided LLM judgment for analysis (does the report hit multiple analytical criteria?).

The hidden quantity

Pipeline orchestration bottleneck

measured quantity  =  Multi-layer pipeline orchestration success rate

This is the fraction of multi-layer SQL pipelines an agent successfully builds end-to-end on a complex schema. It measures the ability to understand a schema, plan a multi-stage transformation, and execute it across 30+ files—not just single-query code generation.

DAComp estimates this by running execution scripts that check each layer (staging, intermediate, marts) against the schema's constraints. A layer is correct only if it satisfies validity constraints (no NULL violations), consistency constraints (foreign keys align), integrity checks (unique IDs), and anomaly detection rules. The paper finds that success rates fall sharply as complexity rises from staging (easier) to marts (harder), exposing the orchestration gap.

Why it works

Why this benchmark exposes the real gaps

Existing benchmarks score agents on a single code-generation metric: does the output match the expected answer? This works for simple queries but breaks for pipelines because no single answer key exists—a pipeline is valid if it satisfies the schema constraints. DAComp switches to execution-based validation: it runs the generated SQL, checks if the output tables satisfy constraints (foreign keys, uniqueness, no violations), and assigns partial credit layer-by-layer. This reveals where an agent goes wrong: staging layer (simple ingestion) or marts layer (complex business logic)?

For analysis tasks, a single right answer does not exist. Multiple analytical strategies can validly answer "what insight does this data reveal?" The naive approach—picking one answer and checking equality—would penalize valid alternatives. DAComp uses a hierarchical rubric with multiple paths: the LLM judge reads the agent's output, selects the best-matching analytical path, and scores that path's criteria. This allows diverse reasoning while maintaining rigor because each path has explicit scoring criteria (e.g., does the claim cite evidence? is the visualization clear?), so valid but different approaches are judged fairly against the same standards.

By separating engineering from analysis, the benchmark isolates the bottleneck. When an agent scores under 10% on DE tasks, it is not a code-generation problem (it can write simple queries)—it is an orchestration problem (connecting schemas end-to-end). This clarity drives focused research rather than guessing which skill to improve because researchers can now see exactly which type of task breaks—engineering complexity, layer orchestration, analysis depth—instead of receiving one overall failure score that points nowhere.

Math after the picture

Scoring pipeline orchestration

First in words:

For each layer l in the pipeline, assign partial_credit_l as 1.0 if all schema constraints are satisfied, 0.0 if any constraint fails. Aggregate across layers: orchestration_score = sum over layers of (partial_credit_l * layer_weight_l) divided by sum of layer_weights.

Then the compact form:

orchestration_score = sum_l (partial_credit_l * w_l) / sum_l w_l

Every symbol:

partial_credit_l1.0 if layer l satisfies all constraints; 0.0 if any constraint fails
w_lweight for layer l (based on position in pipeline: staging < intermediate < marts)
sum_l w_ltotal weight across all layers in the pipeline
orchestration_scorefinal agent score for this DE task, ranging 0 to 1
A tiny worked example
Agent builds a 3-layer pipeline: Staging (ingest), Intermediate (join), Marts (aggregate).
Staging layer output is correct, no NULL violations, all foreign keys valid: partial_credit_s = 1.0, w_s = 1.0
Intermediate layer joins succeed but miss a uniqueness constraint: partial_credit_i = 0.0, w_i = 2.0
Marts layer never runs because Intermediate failed: partial_credit_m = 0.0, w_m = 3.0
orchestration_score = (1.0 * 1.0 + 0.0 * 2.0 + 0.0 * 3.0) / (1.0 + 2.0 + 3.0) = 1.0 / 6.0 = 0.17
Agent gets 17% credit: it nailed ingestion but failed multi-layer orchestration, the real skill.

This design penalizes a single broken layer while rewarding partial progress, isolating the orchestration bottleneck—the agent cannot succeed by writing good SQL alone; it must reason through the entire schema.

What can go wrong

What can go wrong

Single-layer reasoning. An agent trained to write SQL queries for one table will fail at a pipeline because it does not reason about how layer outputs feed into layer inputs. It optimizes each layer in isolation instead of the end-to-end flow.
Ignoring constraints. An agent might generate syntactically correct SQL that violates a foreign key or uniqueness constraint. Execution-based scoring catches this immediately, whereas a naive check-the-answer benchmark might miss it.
Analysis without evidence. On open-ended tasks, an agent might make a claim without checking the data or cite a number that does not appear in the results. The rubric enforces an evidence-first policy: no evidence, no points for that criterion.
Correct orchestration. An agent that reasons layer-by-layer, checks schema constraints at each step, and adjusts code in response to execution errors will score high on both architecture and implementation, revealing orchestration as the core skill.
What a runnable demo should prove

What a runnable demo should prove

Build a small data engineering task: take a simple but realistic schema (e.g., users, orders, products tables with constraints) and ask an agent to design and implement a two-layer pipeline that aggregates user spending by product category. Use execution-based scoring: run the agent's SQL, check for NULL violations, foreign key mismatches, and incorrect aggregations. Then ask the agent an open-ended question on the same data (e.g., which product category is underperforming and why?) and score the response using a simple rubric (does it cite evidence? is the reasoning sound? is the recommendation actionable?). Compare the two scores to show that engineering and analysis are indeed distinct skills.

DE_score = (layers_correct / total_layers); DA_score = (evidence_present * reasoning_sound * actionable) / 3; gap = abs(DE_score - DA_score)

If the agent excels at engineering but fails at analysis (or vice versa), the demo proves they are measuring different capabilities—the whole point of DAComp.
