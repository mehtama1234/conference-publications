PaperCoder: From Paper to Working Code via Multi-Agent LLMs

A team of specialized language models reads a machine learning paper and writes a working code implementation by first planning the architecture, then analyzing the details, then generating modular code.

Paper explainersAll themesMultimodal

Machine learning papers describe new ideas, but researchers often spend weeks replicating them because code is not released. This paper introduces PaperCoder, a system where multiple language models (AI programs trained to read and write text) work together like a team: one makes a plan, another digs into details, and a third writes the actual code. The system reads the paper, builds the software structure, and generates working Python code.

The reproduction gap

When researchers publish machine learning papers, they usually publish only a paper—words and pictures describing the idea. They rarely release the code. So other researchers who want to use the idea have to read the paper, understand it deeply, and rebuild the code from scratch. This takes weeks and often fails because papers leave out details.

A beginner might naively try to just run the Python code examples from the paper text. But papers do not contain enough code—they show pseudocode (fake code for illustration), not real working implementation. The pseudocode might skip how to load data, how to handle edge cases, or which exact model architecture to use. The beginner's attempt fails, they get stuck, and the paper remains unreproducible.

In one sentence. PaperCoder uses multiple specialized language models working together to read the paper and write working code by planning first, analyzing second, and generating modular code third.

The algorithm as a flow

What it actually does

1. Planner reads the paper

First agent maps the high-level idea: problem, approach, data flow, main functions needed.

2. Planner designs architecture

It sketches the software structure: which files, which classes, which function calls which.

3. Analyzer fills in the gaps

Second agent re-reads the paper hunting for specific numbers, thresholds, loss formulas, data shapes.

4. Coder writes modular code

Third agent writes each module independently, using the plan and analyzed details.

5. System validates against ground truth

Human evaluators and authors check if the output code runs and matches the paper's intent.

What the paper changes

What the paper changes

PaperCoder changes how code is generated: instead of a single language model trying to write everything at once, it dispatches the task to multiple specialized agents (planner, analyzer, coder), each with its own role. The object being changed is the code generation strategy—from monolithic to multi-agent pipeline.

The hidden quantity

The hidden quantity: faithful implementation completeness

measured quantity  =  implementation-to-paper fidelity

The paper measures a quantity that is not directly observable: how faithfully does the generated code match the paper's intent? This includes whether the code runs, whether it produces similar results to the original, whether it captures all the key algorithmic details, and whether it handles data correctly. The paper calls this fidelity.

PaperCoder estimates this by comparing the generated code to ground truth (the authors' actual repository if available) and by having the paper's authors evaluate whether the code is correct and complete. The hidden quantity sits between the paper's ideas and the working code—it measures whether the bridge was built correctly.

Why it works

Why multi-agent delegation works

A single language model trying to write code from a paper faces a bottleneck: it must simultaneously understand the math, the software architecture, the data pipeline, and the implementation details all at once. This is cognitively overloaded—the model spreads its focus across too many concerns and often makes mistakes or skips sections.

PaperCoder breaks this into stages. The planner focuses only on structure: What files do we need? How do they call each other? What are the key classes? This is a high-level map, not low-level details. Because the planner is not distracted by parsing formulas or writing loops, it produces a clearer blueprint.

The analyzer then re-reads the same paper but with a different lens: given the architecture, what are the numerical details, the hyperparameters, the loss functions, the layer sizes? This second pass fills gaps the planner did not need to address. The planner and analyzer together have broken the paper into high-level logic and implementation specifics.

Finally, the coder writes each module independently using the planner's blueprint and the analyzer's details. Because the coder knows exactly what each module should do (from the plan) and what numbers to use (from the analysis), it can focus purely on writing correct Python. The separation of concerns reduces each model's cognitive load, so each does its part better. The handoff between agents (plan to analysis to code) creates a natural pipeline that mirrors how humans actually reverse-engineer a paper.

Measuring generation quality

First in words:

fidelity_score = (code_runs * correctness_match + author_validation_score) / 2

Then the compact form:

fidelity = (alpha * execution_success + beta * output_similarity + gamma * author_eval) / (alpha + beta + gamma)

Every symbol:

execution_successdoes the generated code run without errors (0 or 1)
output_similarityhow closely the model output matches ground truth (0 to 1)
author_evalhuman evaluation from paper authors (0 to 1)
alpha, beta, gammaweights balancing the three components
A tiny worked example
Generated code runs successfully: execution_success = 1.0
Output numbers match ground truth within 2%: output_similarity = 0.98
Author rates implementation as 'mostly correct, minor issues': author_eval = 0.85
Equal weighting (alpha = beta = gamma = 1): fidelity = (1.0 + 0.98 + 0.85) / 3 = 0.94
This code is judged as high fidelity (0.94 out of 1.0).

The fidelity score combines whether the code actually runs, whether its outputs match the original work, and whether human experts say it faithfully implements the paper.

What can go wrong

What can go wrong

Paper is too vague on architecture. If the paper does not describe the software structure clearly (e.g., it just shows equations), the planner cannot infer the right architecture, and later stages inherit a bad foundation.
Formulas are written in non-standard notation. If the paper uses unusual symbols or notation, the analyzer may misread the formula, and the coder will then generate code for the wrong computation.
Dependencies between modules are implicit in the paper. If the paper does not make file dependencies explicit, the planner might design a structure where the coder writes modules that call each other in the wrong order or miss intermediate steps.
Done right. When the paper is well-written (clear architecture, explicit formulas, stated data formats), PaperCoder's staged approach produces high-fidelity code because each agent can focus on its specialty.
What a runnable demo should prove

What a runnable demo should prove

A demo should show PaperCoder reading a real machine learning paper (e.g., a vision or NLP paper with clear algorithm description) and outputting a directory of Python code. The code should include configuration files, a data loader, the model architecture, and a training loop. The human should then run the generated code on a small dataset and verify that it trains, produces loss curves, and generates outputs similar in shape to what the paper shows.

success_rate = (code_runs_count / total_papers_tested) * 100%

The demo must make it impossible to miss: the code generated from the paper's words actually runs and produces results aligned with the original.
