Task Tokens

Instead of retuning the whole foundation model for each new robot task, train a tiny separate encoder that generates specialized tokens for the frozen model to read.

Paper explainersAll themesRobotics & Control

Behavior foundation models are large pretrained robots that can follow many instructions at once. But for a specific task like opening a door, they often need careful prompt tweaking to work well. This paper introduces Task Tokens: keep the foundation model completely unchanged, and instead train a small separate encoder that learns to produce specialized tokens tailored to each task. The foundation model reads these task tokens and adjusts its behavior accordingly—like adding a thin lens on top of a good telescope instead of grinding a new telescope.

Zero assumption version

Prompt engineering vs. full retraining

Behavior foundation models are large pretrained systems that can output robot actions for many different tasks when you describe the task in the right way. A robot might follow walking commands, grasping commands, kicking commands—all from the same model.

The problem: for each new specific task, you either fiddle endlessly with the exact wording (prompt engineering), or you retrain the entire massive model (fine-tuning). Both are awkward. Prompt engineering wastes human time on trial and error. Fine-tuning retrains millions of parameters per task, which is slow and risks erasing what the model learned before.

The core issue. A foundation model can do many things, but it needs either tedious hand-tuning or expensive full retraining to do one specific thing well.

The algorithm as a flow

What it actually does

Observe the task

Encoder sees the goal (position, direction) and current robot state (joint angles, position).

Generate task token

Encoder runs through a small neural network, outputs 512 learned numbers tailored to this task.

Foundation model reads token

Foundation model receives the task token plus the goal, generates next action.

Execute and collect reward

Robot takes the action, measures success (did it move closer to the goal?).

Optimize encoder only

Use reward signal to tweak the tiny encoder's parameters. Foundation model never changes.

What the paper changes

What the paper changes

The paper introduces a new learnable object: a small encoder network (about 200,000 parameters) that generates task-specific tokens. This encoder sits between the task description and the frozen foundation model. Instead of either hand-tuning prompts or retraining the foundation model, you train only this tiny encoder to produce the right tokens for each task.

the object it moves  =  task token encoder
The hidden quantity

The hidden quantity: task tokens

measured quantity  =  task token representation

A task token is a list of 512 learned numbers produced by the encoder. Each number encodes one aspect of what the task requires. Unlike a hand-written prompt (which is human words), task tokens are learned numbers tuned by trial and error to make the foundation model behave correctly for the task.

The paper measures and optimizes these tokens by running the foundation model with them, collecting rewards (how well did the robot do?), and using reinforcement learning (where the model learns what direction nudges improve results, specifically PPO) to adjust the encoder toward generating better tokens.

Why it works

Why it works: the frozen model + learned tokens

The foundation model is a large system that was trained on millions of real robot motions. It learned what good behaviors look like for many tasks. When you retrain the whole model, you risk overwriting that knowledge. Task Tokens avoids this by freezing the model completely.

Instead, a small encoder learns to speak the foundation model's language. The encoder produces tokens—numbers that fit into slots where the foundation model reads its instructions. When the foundation model reads these task-specific tokens alongside the goal, it automatically produces a behavior tailored to the task. Why? The foundation model already knows how to combine different signals (goals, state, tokens) because it was trained on many tasks. You only need to learn what specific numbers to produce for your new task.

Why is this better? The small encoder (200K parameters) trains fast because it has few numbers to adjust. Meanwhile, it draws on all the knowledge in the massive frozen foundation model (millions of parameters) that already knows how to act well. You get task specialization without expensive retraining.

The training objective

First in words:

Maximize the expected future reward by adjusting the encoder's parameters, while keeping the foundation model fixed.

Then the compact form:

optimize_encoder: max E[sum_t gamma^t r_t] subject to BFM frozen

Every symbol:

encoderthe tiny neural network you train
BFMbehavior foundation model (stays frozen)
r_treward at step t (e.g., distance to goal decreased)
gammadiscount factor, usually 0.99
E[sum_t gamma^t r_t]total expected reward over the episode
A tiny worked example
Step 1: Encoder sees goal 'reach coordinate (1, 0)' and robot state 'at (0, 0)'. Encoder outputs token [0.5, -0.3, 0.8, ...].
Step 2: Foundation model reads token + goal, predicts action 'move arm forward'.
Step 3: Robot moves, distance to goal shrinks from 1.0 to 0.8. Reward r_1 = 0.2.
Step 4: Gradient flows back through frozen foundation model into encoder. Encoder learns: 'the tokens I made led to +0.2 reward, nudge that direction'.
Step 5: Repeat 50 million times. Encoder converges to tokens that maximize total reward.

The foundation model is a gradient highway—reward signals flow backward through it to update the encoder, but the model's own weights never change.

What can go wrong

What can go wrong

Task tokens are task-specific. Each task needs its own encoder and token set. If you want to handle 100 different tasks, you train 100 separate encoders. This trades task specialization for model count.
Encoder design matters. The encoder is a simple feedforward network in the paper. If you pick a bad architecture, it may not learn good tokens. Richer encoder designs (e.g., with more layers, or mechanisms that compare different parts of the input) could learn faster, because more structure gives the network more ways to combine the task information before producing tokens.
Reward design is still important. The encoder optimizes for rewards you hand-design. If the reward is wrong, the tokens will be wrong. You have not eliminated the need for good task specification—you have just moved it from prompt engineering to reward design.
Done right. Keep the reward simple and aligned with the true goal. Use the encoder to specialize the behavior, not to invent new task semantics.
What a runnable demo should prove

What a runnable demo should prove

Train a task encoder for one new task (e.g., opening a door) using PPO. Freeze a behavior foundation model. Measure two things: (1) How many steps until the robot succeeds? (2) How many parameters did you train? Compare against prompt engineering (manual goal tweaking) and full fine-tuning (retraining the entire model).

Success rate = (episodes where goal achieved) / (total episodes). Convergence speed = steps to 50% success. Parameters trained = encoder parameters only.

Task Tokens wins when: the encoder reaches 50% success in far fewer steps than fine-tuning, and with 100x fewer parameters. The foundation model never changed—all learning happened in the tiny encoder.
