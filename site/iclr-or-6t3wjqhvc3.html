Task Tokens: Adapting Behavior Models with Tiny Encoders

Instead of retraining a robot control model for each new task, train a tiny separate encoder for each task that translates the goal into a special token the original model understands.

Paper explainersAll themesRobotics & Control

Large robot control models trained on millions of human demonstrations can generate smooth, realistic movements for many tasks. But when you want them to do something specific, you have to carefully rewrite your instructions (called prompts). This paper shows you do not have to retrain the big model. Instead, train a tiny helper encoder for each task—it learns how to translate your specific goal into a vector (a list of numbers the big model already understands). The big model stays unchanged.

Zero assumption version

The prompt-engineering trap

Behavior foundation models—large neural networks trained on videos and demonstrations of humans and robots moving—can do many things out of the box. Feed them a goal (walk to the red box, pick up the mug), and they output smooth joint commands the robot can follow. With zero retraining, they generalize to new situations.

But here is the catch: you have to phrase each goal *exactly* the way the model expects. Different tasks need different prompts. Each task is slightly different, so you end up rewriting prompts by hand, tweaking them until the robot behaves right. Some tasks yield great behavior; others flop. Retraining the entire model for each task is wasteful—the model already knows how to move; it just needs to understand your specific goal.

The problem in one sentence. Big robot control models need hand-crafted prompts for each new task, and retraining the whole model is wasteful.

What the paper changes

What the paper changes

The paper introduces a new input to the frozen behavior model: a task token. This is a vector (a small list of numbers, typically 256 or 512 values) that encodes everything specific about the new task. It sits alongside the usual goal prompts in the model's thinking process (where different parts of the model learn to focus on different parts of the input). No weights of the main model change; only the tiny encoder that produces this token is trained.

The hidden quantity

The hidden quantity: Task-specific information density

measured quantity  =  Information encoded per trainable weight

The paper measures how much task-specific knowledge the system learns per weight it trains. This is efficiency: if you train a big model end-to-end, you adjust millions of weights, most of which already know how to move. If you train a tiny encoder, you adjust maybe 100,000 weights, but every one of them is focused on understanding your specific task. The paper's real metric is the ratio of task performance gained per unit of training effort.

The paper estimates this by comparing convergence speed (how many steps to reach good behavior) and total weights trained. Task Tokens converges 6 times faster and uses 125 times fewer weights per task because the encoder only solves task recognition (translating the goal into the model's language), not motion synthesis—a simpler problem that needs fewer weights and fewer training iterations. Fewer weights to train means faster convergence because each training step computes gradients only for those weights, so the signal is stronger and less noisy—the model learns the true task pattern faster instead of wasting compute on irrelevant motion-generating weights.

Why it works

Why it works: The task token as a goal bridge

The frozen foundation model has already learned the low-level skill of moving smoothly and realistically. It does this by mapping from goal descriptions (represented as vectors in its internal layers) to joint commands. What changes from task to task is the language in which you describe the goal.

The tiny encoder learns to translate your task-specific goal—a robot state, a semantic description, a user-defined reward hint—into a vector representation that the foundation model's internal layers already know how to handle. It is like the encoder learns the language the big model already speaks. Since the big model already understands how to turn goal-vectors into realistic movements, the encoder only needs to learn the translation, not the movement generation.

This approach converges much faster than retraining the full model because training only the encoder is solving a simpler problem with fewer weights. Training the full model on a new task means adjusting millions of weights, including the ones that encode basic physics and smoothness (things that do not change from task to task). These irrelevant weights waste training steps and create noise—most of the gradient signal is diluted across weights that should stay put. Training the encoder means adjusting only the weights that learn this one new translation. Each training step computes gradients only for the encoder's weights, so the signal points directly to what needs to change, and irrelevant weights do not muddy the signal—therefore the model learns the true task pattern in fewer steps.

The core equation: Conditioned generation with frozen weights

First in words:

New output equals frozen model evaluated at the task token plus original goal prompt, where task token comes from the tiny encoder applied to the task description.

Then the compact form:

output = foundation_model(original_prompt, task_token) where task_token = tiny_encoder(task_description)

Every symbol:

foundation_modelThe large frozen behavior model, millions of weights
original_promptThe usual goal description the model already understands
task_tokenA vector learned by the tiny encoder, codes task-specific intent
tiny_encoderThe small trainable network, thousands of weights
task_descriptionThe new task (state, text, or reward signal)
A tiny worked example
Say the foundation model expects goal-tokens to be vectors of 256 numbers.
The task description is: (robot position, goal position, task type: walk).
The tiny encoder processes that description and outputs 256 numbers: the task token.
The foundation model sees: original_prompt + task_token = now it knows the goal and the task, so it outputs realistic joint angles.
Training: run robot rollouts with the new task, measure error in joint commands, compute which direction to nudge the encoder's weights (gradient descent) and adjust only the encoder's 50,000 weights, not the model's 500 million. Convergence: 6 steps to good behavior instead of 36.

The key is that the foundation model is already a function from goal-tokens to movements; the encoder learns to map your task into the space of goal-tokens the model already handles.

What can go wrong

What can go wrong

Task too different from training data. If the new task requires movements the foundation model never saw in its training data (e.g., the humanoid robot standing on one hand), the frozen model cannot generate them no matter how good the encoder is. The encoder can only translate; it cannot invent new skills.
Encoder overfits to a few rollouts. If you gather only a handful of robot demonstrations for the new task, the tiny encoder may memorize those exact rollouts instead of learning the generalizable pattern. You need enough diverse examples—varied starting positions, object shapes, speeds—so the encoder learns the true structure of the task.
Token dimension mismatch. The task token must fit into the exact representation space the foundation model expects (e.g., 256 numbers). If the token is too small, it cannot carry enough information; too large, and it wastes capacity.
Done right. With a diverse set of task demonstrations and a well-sized encoder, Task Tokens recovers the foundation model's zero-shot generalization while adding task-specific refinement, typically in a few hours of training instead of days.
What a runnable demo should prove

What a runnable demo should prove

Build a behavior foundation model (or use a pretrained one). Freeze it. For a new task (e.g., walk to a target, pick up an object), gather 50-100 rollouts from a policy that succeeds at the task. Train a tiny task encoder (50,000-100,000 weights) for 10-20 epochs on that data, measuring behavior error (how far the commanded joint angles stray from the successful policy's commands). Plot convergence: watch the encoder reach good behavior in 10-20 steps, while full retraining would take 100+ steps. Then, show that the frozen model + encoder generalizes to a new target position or new object, demonstrating that the encoder truly learned the task structure, not just memorized the rollouts.

behavior_error = mean(|model_output(original_prompt + task_token) - successful_rollout_commands|)

The demo must make it impossible to miss that a tiny trainable encoder can teach the frozen model a new task as well as (or better than) retraining the whole model, with a fraction of the compute, because the encoder only needs to learn task recognition while the model's motion-generation knowledge is already frozen and ready.
