Robust Federated Inference

Combine predictions from many local models without sharing the models themselves, while staying accurate even when some model outputs are attacked or corrupted.

Paper explainersAll themesOther

Federated prediction systems let several local models keep their data and internal settings private while a server combines only their output scores. This is attractive for cross-organization deployment, but it opens a new attack surface: an adversary can corrupt some model outputs and make the final vote fail. This paper studies that setting directly. It shows when simple averaging is naturally stable because honest outputs stay close and the winning class keeps a clear margin, then builds a stronger nonlinear aggregator based on DeepSets plus attack-aware training and a test-time defense step.

Zero assumption version

Why federated prediction is easy to attack

A central server may ask several local models for class scores and then combine them. If all local models are honest, averaging can work well. But a few corrupted clients can push the final combined score toward the wrong class, especially when the honest models already disagree. That means privacy-preserving collaboration can fail at the last step: combining outputs.

The paper points out that training-time and test-time defenses from ordinary adversarial learning do not transfer automatically. Here the attacker may only need to change a few client outputs, not the whole input example. The aggregation rule itself must therefore be studied as a defense object.

The main move. Treat the server-side combiner as the defense target: analyze when averaging survives, then train a stronger set-based combiner that resists corrupted client outputs because it can downweight suspicious output patterns.

The algorithm as a flow

What it actually does

1. Collect client score lists

Each local model sends its class scores for the same input example.

2. Analyze average-based aggregation

Study when the average stays correct based on honest-model agreement and the winning-class margin.

3. Train a DeepSets combiner

Learn a set-based server model that reads the collection of client outputs without caring about their order.

4. Include attack-aware training and test-time filtering

Expose the combiner to attacked output sets during training and apply a defense step when making predictions.

5. Produce the final class decision

Use the defended combiner output as the federated system's prediction.

What the paper changes

What the paper changes

The paper changes the unit of defense from the client model to the server-side aggregation rule. That matters because a federated system may not control or inspect each local model deeply, but it always controls the final combiner. By defending the combiner directly, the method can improve the whole system even when the local models remain untouched.

the object it moves  =  the server-side rule that combines local prediction sets
The hidden quantity

The hidden quantity: honest disagreement margin

measured quantity  =  how far the honest clients separate the correct class from the nearest wrong class

The server rarely knows which clients are corrupted. What it can observe is the spread of client outputs. The most important hidden quantity is the honest disagreement margin: if honest clients mostly agree on the correct class and place it far above the next class, an attacker must work much harder to flip the final answer. If honest clients are split already, only a small push may be enough.

This quantity matters for both parts of the paper. It explains when simple averaging already survives, and it tells the learned set combiner what kind of output sets should be trusted or treated as suspicious.

Why it works

Why it works: learn patterns over sets of client outputs

Averaging treats every client output the same. That is good when all outputs are honest and similarly noisy, but bad when a few outputs are attacked. A DeepSets combiner can do more. It reads the whole set of client outputs and learns patterns such as "most clients agree, but a small group is sharply inconsistent." That helps because the server can reduce the impact of suspicious outputs instead of letting them shift the average directly.

Attack-aware training matters because the combiner must see corrupted sets during learning, otherwise it has no reason to distinguish them from natural client disagreement. The extra test-time defense step helps again because attacks at deployment may not look exactly like the attacked sets used in training. Combining both stages keeps the server more stable across different attack patterns.

Math after the picture

The set-aggregation equation

First in words:

Final class score = output head applied to the sum of per-client transformed scores

Then the compact form:

y_hat = rho( sum_i phi(s_i) )

Every symbol:

s_ithe class-score vector from client i
phithe per-client transformation used by the set combiner
sum_iorder-free pooling over all client outputs
rhothe server head that converts the pooled summary into the final class score
A tiny worked example
Suppose five honest clients favor class A and two corrupted clients push class B strongly.
If plain averaging sums all seven outputs equally, class B may win when the honest margin is small.
A trained set combiner can map the five mutually consistent outputs to a strong pooled summary and map the two inconsistent outputs to a smaller contribution.
After pooling, the server head still gives class A the highest final score.
The gain comes from learning which output patterns look trustworthy across the whole set, not from inspecting one client alone.

The form is order-free, which fits the federated setting because the server should care about the set of outputs, not about which slot each client occupied.

What can go wrong

What can go wrong

Honest clients may disagree for valid reasons. If local models are trained on very different data, their outputs can naturally vary a lot. The server may then mistake honest diversity for an attack because both look inconsistent.
Attack patterns may change. A server trained on one family of corruptions can still be surprised by a very different corruption strategy because attack-aware training never covers every possible manipulation.
Too many clients may be corrupted. If the corrupted share is large enough, even a good set combiner may fail because the honest group no longer forms the dominant pattern in the output set.
When it works best. The method is strongest when most clients are honest and the honest group has a visible class margin, because then the combiner has a real signal to protect.
What a runnable demo should prove

What a runnable demo should prove

Build a small federated image or text classifier with several local models and one server. First measure clean accuracy and attacked accuracy under simple averaging. Then replace the server with a DeepSets combiner trained on attacked output sets and add the paper's test-time defense step. The demo should compare how often the final prediction flips under different numbers of corrupted clients. The defended combiner should keep more correct predictions because it learns when a subset of client outputs is inconsistent with the honest majority.

A useful interface would also show the client score sets for several examples. Watching a few extreme outputs fail to dominate the final answer makes the server-side defense easier to understand than a single accuracy table.

flip_rate = attacked_wrong_predictions / total_predictions

A convincing demo shows that privacy-preserving collaboration is only practical if the final combiner stays stable when some participating outputs are malicious.
