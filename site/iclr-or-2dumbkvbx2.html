Meerkat: Sparse Zeroth-Order Federated LLM Fine-Tuning

Train a shared language model across separate organizations by updating only 0.1% of weights using gradient-free math and spotting clients with skewed data.

Paper explainersAll themesOptimization

Imagine dozens of hospitals want to improve a shared medical AI model, but none can send raw patient data to a central server—for each hospital to upload patient records, it would need approval from those patients and lawyers, a legal process that can take months or fail due to privacy consent rules, so hospitals send only model updates they compute locally on their own secure servers. Patient records contain names, diagnoses, dates, and addresses, which can identify real people; privacy laws like HIPAA (in the US) make sharing identifiable health data a crime with prison time and million-dollar fines. The problem: the model is enormous (billions of weights), the updates are huge (millions of numbers), and the hospitals have very different patient populations (one sees heart patients, another sees cancer patients, a third sees rare genetic diseases). Meerkat solves this by having each hospital update only 0.1% of the weights (vastly shrinking the message), using a math trick that avoids backpropagation (the standard way to compute how much to move each weight), and by detecting hospitals with unusual data so their updates do not pull the shared model off course.

Zero assumption version

Federated learning of giant models is broken by size and dishonest clients

Today, language models have billions of weights. If each hospital or bank that wants to fine-tune the shared model sends back all its weight updates, the pipe fills up instantly and the server chokes. A naive approach: 'just send only a few weight updates.' But which ones? And if your local data is very different from other hospitals (you see rare diseases, they see common ones), your updates pull the model in a direction that hurts performance for everyone else.

A beginner's first attempt: 'quantize the updates to small integers or round them heavily.' This saves bandwidth, but destroys accuracy because each rounded update loses its precision—when you send 5.7 as 5 or 6, the actual information about which direction to move that weight disappears into noise, so the model can no longer learn from the data (it chases rounding errors, not truth). Second attempt: 'update only weights that are obviously important.' But how do you know which weights matter without computing the gradient (the list of directions telling you how much to move each weight)? That requires expensive backpropagation math, and the whole point is to avoid it (because the model is so big and the data so private).

The trick. Update only an extremely sparse set of weights (0.1%) using gradient-free math, then spot clients whose data is so skewed that their updates harm the model—and force them to take only tiny steps.

The algorithm as a flow

What it actually does

Pre-training calibration

The server runs the model on its original training data once, records which weights matter most (using gradient-free derivatives), picks the top 0.1%, and sends each client the sparse mask.

Local training without gradients

Each client performs local fine-tuning on just those sparse weights using zeroth-order math (sample a random perturbation, measure the loss change, infer the steepness).

Virtual path recording

The client sends back only the sparse weight updates. The server replays those updates using the same random seed, reconstructing the internal 'path' of how each weight moved over time.

GradIP anomaly detection

The server measures how well each client's gradients align with the pre-training gradients (inner product, or how much they point the same way). Extreme Non-IID clients get a weird signal.

Early stopping for outliers

Clients flagged as anomalies are forced to take only one tiny update step per round instead of many. This prevents them from dragging the global model away from the center.

What the paper changes

The one thing that moves

The paper changes which weights each client is allowed to update. Instead of fine-tuning all billions of weights (or even half of them), each client touches only a static, pre-selected, extremely sparse subset—fewer than 0.1% of all weights. This subset is the same for every client; it is chosen once using the pre-training data and does not change.

the object it moves  =  The weight sparsity mask
The hidden quantity

GradIP: the alignment signal that reveals skewed data

measured quantity  =  GradIP (gradient inner product)

GradIP is a single number (between −1 and 1, like a correlation) that measures how much each client's learning direction aligns with the direction the model learned during pre-training. If a client's local data is normal (same distribution as pre-training), its gradients point roughly the same way, and GradIP stays high and stable. If a client has very skewed data (rare cases everyone else misses), its gradients point a different direction, and GradIP becomes erratic—it bounces around and sometimes reverses sign.

The paper estimates GradIP by computing the inner product (cosine similarity) between the client's estimated gradients (from the gradient-free math) and the server's pre-training gradients. The server does not need to see the client's raw data; it only looks at this one number over time. Extreme outlier clients show a GradIP trajectory that is chaotic in the early steps and then suddenly stabilizes or inverts, a signature pattern the algorithm learns to spot.

Why it works

Why sparse + zeroth-order + GradIP detection solves the problem

Sparse updates fix communication: The model has billions of weights, but only 0.1% are sensitive to the loss (they move the needle). If each client updates only those weights, the message is 1,000 times smaller. The server can afford high-frequency synchronization—clients upload every 1–10 local steps instead of 100, which keeps everyone on the same page.

Zeroth-order estimation fixes privacy: Backpropagation requires storing intermediate activations (expensive memory) and reveals the model's internals to the client's hardware. Zeroth-order math sidesteps this: sample a random list of numbers (a vector), measure the loss at two nearby points, and infer the steepness from that pair of measurements alone. The client never computes or stores a full gradient (the directions to move each weight). This is slower per step but uses less memory and keeps the model architecture private.

Virtual path enables detection: The server and client use the same random seed (a starting number for generating random numbers), so they generate the same sequence of random perturbations. When the client computes local updates, it uses that seed to generate random perturbations in the zeroth-order math. Later, the client sends back only the sparse weight updates (which weights moved, how much). The server replays those updates by applying them in the same order with the same random perturbations, recovering the full 'path' of how those weights evolved step by step—without ever touching the client's data or seeing the gradients directly. Because the reconstructed path records whether the client's gradient estimates were consistent or chaotic, the server can spot clients whose data is pulling them in weird directions.

GradIP detection fixes Non-IID drift: Now the server can measure GradIP: the inner product between the replayed client's estimated gradients and the pre-training gradients. Clients with skewed data produce chaotic GradIP trajectories. The server identifies them (using a ratio of 'early GradIP' to 'late GradIP' and a count of 'quiescent' stable steps) and forces them to take only one tiny step per round. This starves bad updates and preserves model quality. Honest clients (IID data) keep moving normally.

Math after the picture

The zeroth-order gradient estimate and sparsity

First in words:

The gradient of the loss is estimated by measuring the loss at two nearby points: one nudge plus epsilon in a random direction, one nudge minus epsilon. The difference divided by twice epsilon gives a one-dimensional gradient (the inner product with the random vector). Only sparse weights are updated. The sparsity mask selects which weights matter.

Then the compact form:

g = [f(w + eps*(z ⊙ m)) - f(w - eps*(z ⊙ m))] / (2*eps); proj_grad_k = g * (z ⊙ m)

Every symbol:

wthe model weights (billions of numbers)
mthe sparse mask (0.1% ones, rest zeros)
zrandom Gaussian vector (same shape as weights)
z ⊙ melement-wise multiply: random perturbation on sparse weights only
epsa small step size, e.g. 0.001
f(w)the loss (error) of the model on a batch of data
gthe one-dimensional gradient (how steep the loss is in the random direction)
proj_grad_kthe projected gradient: the scalar g scaled by the random vector, giving a sparse update
A tiny worked example with three weights
Suppose model weights = [w1=10, w2=20, w3=15]. Sparse mask m = [1, 0, 1] (update w1 and w3 only).
Random vector z = [0.5, 0.2, 0.8]. After masking: z ⊙ m = [0.5, 0, 0.8].
Step size eps = 0.01. Perturbed weights: w_plus = [10.005, 20, 15.008]; w_minus = [9.995, 20, 14.992].
Loss at w_plus = 3.2, loss at w_minus = 3.0. Change in loss = 3.2 - 3.0 = 0.2.
Gradient estimate g = 0.2 / (2 * 0.01) = 10.
Projected gradient = g * (z ⊙ m) = 10 * [0.5, 0, 0.8] = [5, 0, 8].
Update: send only [5 (for w1), 0 (skip w2), 8 (for w3)]. Three numbers instead of three, but in this case: both are sent (because m has two ones). Real models: billions of weights, mask has 0.1%, message is 1000x smaller.

The gradient-free trick trades computation (two forward passes) for privacy (no backprop, no gradients stored). Sparsity trades some accuracy (ignoring 99.9% of weights that do not change the loss much anyway) for communication (1000x smaller messages, so the server can afford high-frequency synchronization without saturating the network). Together, they enable federated learning on billion-weight models because each client can now send updates often enough to stay synchronized with the global model and other clients.

What can go wrong

What can go wrong

Sparse mask is wrong from the start. If pre-training data is not representative (or the pre-training gradient is stale), the mask might ignore weights that matter for the new task. For example, if pre-training was on English medical records but fine-tuning includes rare genetic diseases, the mask might skip the weights controlling disease-specific logic. The fix: re-calibrate the mask on a small sample from each new task.
GradIP detection is too aggressive. The algorithm flags clients as outliers using the ratio of early-to-late GradIP and the count of stable steps. If the thresholds are tuned too strictly (looking for tiny variance), honest clients with legitimately different data (rural vs urban hospitals) get wrongly forced to one-step updates, and they stop learning their local patterns. The fix: validate thresholds on a held-out client pool before deployment.
Zeroth-order estimation noise accumulates. Each gradient-free estimate is noisier than a true backpropagation gradient, because it is inferred from only two loss measurements. Over many local steps, this noise can accumulate and cause the sparse weights to oscillate rather than converge. High-frequency communication (which Meerkat enables) helps, because the server can steer clients back on track more often. Low-frequency communication worsens this.
Done right. Use Meerkat with high-frequency synchronization (every 1–10 local steps), re-calibrate masks for new task families, and validate GradIP thresholds on a representative client sample. Monitor per-client accuracy trends to catch if outlier detection is too strict. The combination of sparse updates, frequent synchronization, and anomaly detection keeps the model on track even when clients have wildly different data.
