Closing the Loop: Universal Repository Representation with RPG-Encoder

Encode a code repository into one shared planning graph so that an agent can navigate, localize, and reconstruct the project from the same representation.

Paper explainersAll themesAgents & Tool Use

Repository agents often work with fragmented views of a codebase. One tool may use API text, another may use file dependencies, and another may use retrieved snippets. That split makes it harder to reason across structure and meaning at the same time. RPG-Encoder proposes a single repository planning graph that is built from raw code and then updated incrementally, so that understanding and generation both rely on the same project representation.

Why repository agents lose the thread

A software repository contains many connected facts: file roles, call relations, data flow, naming conventions, and higher-level intent. When an agent only sees one slice at a time, it may find the wrong file or misunderstand how several files work together.

This problem shows up in code localization and code generation. To localize a bug, the agent must compress a large codebase into the small set of relevant places. To generate code, it must expand a requested intent into changes that fit the existing project. The paper argues that these two tasks should share one project representation.

The paper's move in one sentence. Build one repository planning graph from raw code, update it incrementally as the repository changes, and use that graph as the shared interface for understanding and generation.

The key hidden quantity is the repository intent that is spread across files. A single file may show local logic, but the reason that logic exists often depends on neighboring files, call paths, and project conventions.

RPG-Encoder tries to recover that hidden project intent in one structure. The shared graph helps because it preserves structural links and meaning together, so a navigation step can use both kinds of evidence instead of guessing from text alone.

Why it works

Why this works: one map is better than several partial maps

Repository tasks fail when the agent has to stitch together unrelated views on the fly. A text-only view misses structural relations, while a relation-only view misses code meaning. RPG-Encoder keeps both in one graph so that a localization or generation step can read a richer neighborhood.

The incremental update rule also matters because a unified representation would be too costly if it had to be rebuilt from scratch after every change. The paper reports low maintenance overhead by updating only the affected region, which keeps the shared graph usable on large repositories.

Math after the picture

Balance repository fidelity against maintenance cost

First in words:

A compact summary is to value a repository representation when it preserves enough project detail for downstream tasks while keeping update cost low after edits.

Then the compact form:

repo_score(graph) = fidelity(graph) - eta * update_cost(graph)

Every symbol:

repo_score(graph)overall value of the repository representation
fidelity(graph)how well the graph preserves useful project information
update_cost(graph)how much work is needed to keep the graph current after changes
etaweight on the maintenance-cost penalty
A tiny worked example
Graph A preserves strong project detail but needs a full rebuild after each edit.
Its fidelity is 9 and its update cost is 6, so with eta = 1 its total score is 3.
Graph B preserves almost as much detail and updates only local regions.
Its fidelity is 8 and its update cost is 1, so its total score is 7.
A system prefers Graph B because it remains informative without becoming too expensive to maintain.

The paper contains a richer implementation, but this equation captures the design tradeoff that the representation must stay both faithful and maintainable.

What can go wrong

What can go wrong

The graph may omit subtle code meaning. If the encoding misses a critical project convention, the agent may trust the graph too much because the missing detail will not appear during navigation.
Incremental updates can drift. A local update rule may leave stale links behind if a change has wider effects than the updater notices.
Large graphs can become hard to query. A unified representation can still slow down if the search procedure over the graph is weak, because too many candidate regions may look relevant.
Done right. The framework matters because it treats repository understanding and repository generation as two uses of the same project map.
What a runnable demo should prove

What a runnable demo should prove

Build a repository navigation demo on a medium-sized open-source project. Compare a baseline agent that retrieves files by text and dependency lists against an RPG-Encoder-style agent that queries a shared repository planning graph. Test both on bug localization and on small code-generation tasks that must fit project structure.

The demo should report top-k localization accuracy, reconstruction coverage for selected modules, and cost of keeping the representation current after controlled repository edits. The graph-based agent should win because one shared map lets it move between local code details and project-level structure more reliably.

repo_gain = localization_score_rpg - localization_score_baseline ; upkeep_drop = update_cost_baseline - update_cost_rpg

The goal is to show that one repository representation can support both reading and writing the codebase.
