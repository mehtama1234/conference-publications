GUI-Shift: Self-Supervised GUI Agents

Train GUI-control models without annotated labels by having them predict which action caused a screen change.

Paper explainersAll themesAgents & Tool Use

Building models that understand computer screens and click the right button requires showing the model thousands of labeled examples of screens and actions — expensive, slow work. This paper shows a simpler way: just show the model two different screens and ask it to guess what button was clicked to go from one to the other. Once it learns to predict actions from screen pairs, it can control GUIs without any labeled training data.

Why GUI agents fail without mountains of labeled data

Today, training a vision-language model (a model that reads pictures of screens and understands language) to click buttons and navigate apps requires showing it thousands of screen shots paired with labeled actions: "this screen shows a login form, and the correct action is click the email field." Collecting these labels is slow — you need humans to record real app interactions and write out what each step was doing.

A beginner might try to label every screen manually, but this breaks at scale: with millions of possible screen layouts across apps, hiring enough people to label them all becomes prohibitively expensive. The model is never certain it has seen enough examples to generalize to new apps or new workflows.

The core problem: Labeled training data for GUI tasks is rare and expensive to collect.

The algorithm as a flow

What it actually does

Step 1: Collect unlabeled screen logs

Record app interactions from real users or automated testing. Keep only the video; throw away any labels.

Step 2: Extract before-and-after pairs

For each action in a log, chop out the screen before it and the screen after. You now have millions of (screen_A, screen_B, action) examples with no manual work.

Step 3: Teach the model inverse dynamics

Train the model to take two screens and predict which action connects them. This is the backwards problem, not forward prediction.

Step 4: Run reinforcement learning

Let the trained model navigate GUIs. Reward it for completing tasks. Use data filtering to throw out bad trajectories.

Step 5: Evaluate on held-out benchmarks

Test on GUI automation (e.g., AndroidControl) and GUI grounding (e.g., ScreenSpot). Compare to models trained with explicit labels.

What the paper changes

What the model learns

The paper changes what the model is trained to predict. Instead of learning a forward model (given a screen and an action, predict the next screen), it learns an inverse model: given two screens, predict the action that connects them. This backward task is far easier to teach at scale because you have no labeled actions — just raw screen recordings.

the object it moves  =  the prediction direction: inverse (screen pairs to action) instead of forward (action to next screen)
The hidden quantity

The hidden quantity: action relevance

measured quantity  =  action relevance (how much each action candidate explains the screen change)

Behind the model's prediction is a hidden score for each possible action: how well does clicking this button explain the transition from screen A to screen B? The model learns to rank actions by how much visual change they cause. When it sees a screen with the email field highlighted, then a login page, it assigns high relevance to the email-click action.

The paper measures this by running the trained model on held-out screen pairs and checking which actions it ranks first. The filtering step removes trajectories where the model's predicted actions are inconsistent, keeping only the parts of the data where action relevance is clear.

Why it works

Why inverse prediction teaches the model to understand GUIs

Forward prediction (action to next screen) is hard: the same click can lead to different screens depending on network delays, animations, and invisible state. Inverse prediction (screen pair to action) is easier: given two very different screens, there are only a few actions that could realistically connect them. The model learns to ignore noise and focus on which actions matter.

Once the model can predict actions from screen changes, it has implicitly learned what each action does. When deployed to actually control a GUI, the model applies this knowledge: it looks at the current screen, imagines what actions might cause changes in the right direction, and picks the one that leads to the goal, because actions that reliably cause visible screen changes are the ones the model ranked high during training. The reinforcement learning step then tunes this understanding for real tasks, removing parts of the learned behavior that do not complete the goal, because only trajectories that reach the goal accumulate reward.

Data filtering removes trajectories where actions are ambiguous or inconsistent. This keeps the training focused on parts of the data where causality is clear, because when the model sees a screen pair where the correct action is obvious (not 5 equally likely candidates), it learns a confident and consistent action ranking, which generalizes better to new unseen GUIs.

The inverse dynamics loss

First in words:

penalty = cross-entropy loss between the model's predicted action probabilities and the true action

Then the compact form:

Loss = -sum_i p_true(i) * log(p_pred(i))

Every symbol:

p_pred(i)model's predicted probability for action i
p_true(i)true probability: 1 for the correct action, 0 for others
sum_isum over all possible actions
A tiny worked example
Suppose there are 4 possible actions: email-click (correct), password-click, back, scroll.
Model predicts: email-click 0.6, password-click 0.25, back 0.1, scroll 0.05.
True labels: email-click 1.0, others 0.
Loss = -(1.0 * log(0.6) + 0 * log(0.25) + 0 * log(0.1) + 0 * log(0.05))
Loss = -log(0.6) = 0.51
If model predicted email-click 0.9 instead, loss = -log(0.9) = 0.105 (lower, better).

The model learns by reducing this loss — giving higher probability to the action that actually caused the screen transition.

What can go wrong

What can go wrong

Ambiguous screen transitions. If two screens look very similar, many actions might plausibly cause the transition. The model becomes uncertain. Solution: filter training data to remove ambiguous pairs.
Network delays and visual noise. Real apps load slowly, show loading spinners, or animate elements. If the before-and-after screens include these artifacts, the model may predict the wrong action. Solution: align screenshots precisely and ignore transient UI elements.
Action overfitting. If most recorded sessions click the same buttons, the model learns only those common actions. It fails on rare tasks. Solution: ensure recorded logs are diverse or use reinforcement learning to explore new actions.
Done right. Carefully curated unlabeled data, data filtering to remove ambiguous cases, and reinforcement learning applied afterward produces models that generalize across apps and benchmarks.
What a runnable demo should prove

What a runnable demo should prove

Record a 10-minute user session on a real mobile app (e.g., a banking app with login, account navigation, and settings). Do not label any actions. Extract screen pairs and train the inverse-dynamics model to predict actions. Then test it on a new task: fill in a login form (a combination it never saw during training). Check whether the model's predicted action sequence actually completes the task. Compare its accuracy to a model trained on manually labeled data with the same time budget.

Accuracy = (number of correct actions predicted) / (number of actions needed to complete the task)

The demo proves that learning from screen pairs alone, without any labels, produces models that can handle new GUIs better than traditional supervised training, because the model learned to predict actions in many contexts during self-supervised training, so it generalizes to new apps the old method never saw.
