$\tau$-Voice: Benchmarking Full-Duplex Voice Agents on Real-World Domains

$\tau$-Voice tests voice agents on grounded tasks where they must speak, listen, follow policy, and complete real tasks under messy audio conditions.

Paper explainersAll themes

A voice agent can sound smooth while still failing the task. It can also finish the task in text while failing once speech, interruption, accents, and background noise enter the loop. $\tau$-Voice exists to measure the whole system at once: task completion, turn taking, policy following, and audio realism.

Zero assumption version

Why existing voice tests miss the hard part

Many evaluations separate conversation style from grounded task completion. One benchmark may ask whether the voice exchange feels smooth, while another asks whether the agent reaches the correct final state. Real deployments need both at once because the agent must talk through a messy multi-turn exchange and still take the right actions in the environment.

This gap hides where failures really come from. If a voice agent fails a restaurant booking or support workflow, the cause might be speech recognition, poor turn taking, policy mistakes, or weak planning. Without a benchmark that keeps all of those pieces together, it is hard to tell whether progress is real.

The paper's move in one sentence. Extend a grounded task benchmark into a voice setting with realistic audio, overlapping speech, and verifiable outcomes so that text and voice agents can be compared under the same task rules.
Why it works

Why this works: hold the task fixed and vary the voice conditions

The benchmark starts from grounded tasks with clear success conditions, then adds a realistic voice user simulator on top. The simulator controls accents, noise, and turn-taking behavior while the environment still checks whether the underlying task was solved. That matters because the final score can separate graceful speech from actual task success.

The user simulator is decoupled from wall-clock constraints, so it can use a strong language model to generate realistic user turns without forcing the whole benchmark to run in real time. That design helps because the benchmark can stress the agent with richer conversations while still staying reproducible across systems.

Math after the picture

The retention score

First in words:

Measure how much of a text agent's task ability survives once the same task is run through the voice channel. The key quantity is retained capability: voice success divided by text success on the same task set.

Then the compact form:

retention = pass_voice / pass_text

Every symbol:

pass_voicetask completion rate for the voice agent on the benchmark tasks
pass_texttask completion rate for the text agent on the same tasks and rules
retentionfraction of the original task ability that remains after speech is introduced
A tiny worked example
Suppose the text system solves 80 of 100 tasks, so pass_text = 0.80.
Under clean voice conditions the same agent solves 40 of 100 tasks, so pass_voice = 0.40.
Retention = 0.40 / 0.80 = 0.50.
Under noisy conditions it solves 28 of 100 tasks, so retention falls to 0.28 / 0.80 = 0.35.
The retention score shows how much ability is lost because speech and turn taking add new failure points.

The paper reports that current voice agents keep only about 30 to 45 percent of their text capability under this setup, which is why retained capability is the central summary number.

What can go wrong

What can go wrong

Simulator overfitting. If agents are tuned too closely to the simulator's speech habits, benchmark gains may overstate real deployment quality because real users interrupt and phrase requests differently.
Audio dominates the score. Poor speech recognition can bury planning quality, because the agent may never receive the right facts even if its downstream decision logic is sound.
Task success hides poor interaction. An agent can finish the task while still cutting off the user or ignoring repairs, so the benchmark needs interaction traces as well as pass rates because user experience still matters.
Done right. The paper reports both task completion and voice interaction quality, then analyzes whether failures come from the agent or the audio channel so that progress claims stay grounded.
What a runnable demo should prove

What a runnable demo should prove

Take a grounded customer-support task with a clear final state, such as changing a reservation under policy constraints. Run the same task twice: once through text and once through speech with interruptions, accent variation, and background noise. Keep the task rules identical so that the only difference is the interaction channel.

The demo should show that a system can sound fluent and still fail the task, because the environment check exposes policy errors, dropped details, and poor turn recovery that a style-only evaluation would miss.

A good benchmark makes the failure source visible. This one does that by pairing realistic voice interaction with verifiable grounded outcomes.
