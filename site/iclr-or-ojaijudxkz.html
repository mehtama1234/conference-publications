OmniActor: A Generalist GUI and Embodied Agent for 2D&3D Worlds

OmniActor shares early processing but separates later decision modules, because GUI tasks and embodied tasks help one another at low levels yet interfere when the same deep policy layers must serve both worlds.

Paper explainersAll themesAgents & Tool Use

A useful multimodal agent should move between software interfaces and physical environments without switching to a completely different system. In practice, that is hard. Training one model on GUI data and embodied data together often hurts both because the tasks demand different high-level action policies even though they share low-level perceptual skills. OmniActor addresses that split directly. It shares shallow layers where the two settings reinforce one another, then separates deeper layers with a layer-heterogeneous mixture-of-experts design so that task-specific conflicts are isolated while common perception is retained.

Zero assumption version

Why one agent struggles across 2D and 3D worlds

GUI agents act in menus, windows, forms, and text-heavy layouts. Embodied agents act in rooms, with motion, viewpoint changes, object manipulation, and physical constraints. Both require perception, instruction following, and action selection, but the later decision patterns are very different.

Naively mixing the two datasets in one model can degrade performance because shared weights must satisfy conflicting high-level behaviors. The paper's analysis shows that the two domains help one another in shallow layers because both need basic visual parsing and language grounding, but they conflict in deeper layers because the action policy becomes domain-specific.

In one sentence. Share the early layers for common perception, but split the deep layers across experts because GUI control and embodied control need different high-level policies even when they observe similar signals.

The algorithm as a flow

What it actually does

Collect GUI and embodied data

The training set includes both 2D interface actions and 3D embodied actions because the goal is one generalist policy across both domains.

Share shallow processing

Early layers remain common because both tasks need scene parsing, instruction grounding, and coarse action understanding.

Separate deep experts

Later layers branch into domain-specific experts so that high-level action choices can specialize without interference.

Unify the action interface

The system uses a common action formulation across GUI and embodied tasks because a unified output space makes cross-domain training more coherent.

Train on large mixed data

The model learns from many sources, gaining shared low-level skill while keeping separate deep control policies for each world.

What the paper changes

What the paper changes

The paper changes where weight sharing ends. Instead of either sharing everything or splitting everything, OmniActor shares shallow layers and separates deeper ones through a layer-heterogeneous mixture-of-experts design.

the object it moves  =  the depth at which weights are shared across domains
The hidden quantity

The hidden quantity: cross-domain interference

measured quantity  =  how much training on one domain harms the other at a given depth

The system does not observe interference directly. It only sees that joint training sometimes helps and sometimes hurts because updates from one domain can either reinforce or overwrite what the other domain needs. The paper's analysis argues that the sign of that interaction changes with depth. Early layers benefit from mixed data because both domains need object recognition, text reading, and instruction grounding. Deep layers conflict because they represent very different action logic: pointer movement and text entry on one side, navigation and manipulation on the other.

OmniActor treats this depth-dependent interference as the key hidden quantity. By isolating the later conflict while keeping early sharing, the design captures the helpful part of joint learning and blocks the harmful part.

Why it works

Why shallow sharing plus deep specialization works

A GUI screenshot and a robot camera frame look different, but both require the model to parse objects, localize text or visual landmarks, and align instructions with what is on screen or in the scene. Those are early-stage perceptual operations, so sharing them improves data efficiency because both domains reinforce the same foundational skills.

The trouble appears later, when the model must decide what action to take. GUI control depends on pointer placement, typing, and discrete interface operations. Embodied control depends on movement, viewpoint changes, and interaction with physical constraints. If one set of deep weights tries to encode both policies at once, updates from one domain can overwrite the strategy needed for the other. OmniActor avoids that by splitting later layers into experts while still preserving the shared early representation that both worlds benefit from.

Split-share objective

First in words:

The total loss is the sum of GUI task loss and embodied task loss, but the parameters are partitioned so shallow layers are updated by both while deep experts are updated mainly by their own domain.

Then the compact form:

L_total = L_gui(theta_shared, theta_gui) + L_emb(theta_shared, theta_emb)

Every symbol:

L_guiloss on GUI tasks
L_embloss on embodied tasks

A tiny worked example
Suppose a shared early layer learns text grounding and object localization. Both GUI and embodied batches update it because both tasks need those skills.
Now suppose a later GUI batch needs precise cursor placement while an embodied batch needs turn-left motion control.
If both domains updated one shared deep policy, those two signals could conflict.
With separate deep experts, GUI updates improve theta_gui and embodied updates improve theta_emb, while theta_shared still collects the common low-level gains.

The architectural point is the partition of weights by depth, not a new loss term alone.

What can go wrong

What can go wrong

Split too early. If the model separates domains before useful common perception has formed, it loses the low-level transfer that mixed data could have provided because each side learns the same basics independently.
Split too late. If deep policies remain shared for too long, interference can still dominate because the domains continue overwriting one another in the layers where control logic diverges most.
Unified actions may be too coarse. A common action interface helps coordination because both domains can train against one shared output format, but it can hide important domain-specific distinctions if that format is too blunt for precise GUI or embodied control.
Done right. The method works when common perception is shared long enough to gain transfer and deep control is separated early enough to prevent policy conflict.
What a runnable demo should prove

What a runnable demo should prove

Build two small benchmarks: one for GUI control, such as form filling and menu navigation, and one for embodied control, such as moving through rooms to pick up an object. Train three variants: a GUI-only model, an embodied-only model, and a mixed model with shallow sharing plus deep experts.

Evaluate each model on both domains and inspect how performance changes when the split depth moves earlier or later. The expected result is that a middle split performs best because it preserves shared low-level learning while reducing late-stage policy conflict.

generalist_score = 0.5 * GUI_success + 0.5 * embodied_success

The demo should show that a real generalist needs shared perception and specialized control, not one undifferentiated policy for every world.
