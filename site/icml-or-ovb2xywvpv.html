Joint Navigation and Manipulation Planning with 3D Interaction Chains

A robot plans navigation and manipulation together instead of separately, so its path puts it in the right place to manipulate objects.

Paper explainersAll themesRobotics & Control

When a robot needs to both move across a room and pick up an object, most methods split the task: first find a path to the target, then figure out how to grab it. This causes problems — the navigation might end at a spot that is awkward for grasping, or the grasp-friendly pose might require a long detour. This paper shows how to plan both at once, finding paths and arm poses that work well together.

Zero assumption version

The split-stage trap

A mobile manipulation robot (a rolling base with an arm) must do two hard things at once: get to an object far away and then grasp it. Most methods separate these: first use a navigation planner to find a collision-free path to the target area, then use a manipulation planner to figure out arm poses and grasps once the robot arrives.

This breaks in practice. The navigation planner has no idea where the arm can actually reach; it might pick a route that ends with the robot sideways to the object, making the grasp impossible. Or the manipulation planner might demand a pose that requires the robot to navigate through a furniture-filled room in an awkward way, doubling the travel time.

A beginner might try to just run the two planners with a buffer around the object, but this wastes time on feasibility checks that fail, or arrives at useless positions. The core mismatch is that neither planner knows what the other really needs.

In one sentence. Plan the path and the arm pose together so they do not conflict.

The algorithm as a flow

What it actually does

Build a shared 3D map

Create a single 3D feature map visible to both the navigation and manipulation planners.

Generate multi-stage waypoints

For each approach direction to the target object, propose a sequence of waypoints the robot could visit.

Chain the waypoints

Link waypoints into candidate full paths (navigation chains + associated arm poses).

Score each chain

For each chain, compute path cost (distance, obstacles) and arm feasibility (can the arm reach and grasp from this pose) using a learned hierarchical scoring function.

Execute and replan

Pick the best chain, start moving, and recompute as the robot sees new parts of the room.

What the paper changes

What the paper changes

Instead of two separate plans (navigation then manipulation), the paper creates candidate chains that bind navigation waypoints to manipulation poses, scoring them jointly. The robot no longer commits to a path that ignores arm constraints.

the object it moves  =  Planning chains (path + arm poses)
The hidden quantity

Feasibility: can the arm really do it?

measured quantity  =  Chain feasibility score

The paper tracks something that split planners never measure: for each candidate waypoint where the robot might position itself, how hard is the manipulation task from that spot? This includes whether the arm has a collision-free reach, whether the fingers can close around the object, and how far the arm must extend.

The paper estimates feasibility by processing each waypoint's local 3D features through a learned scoring function. A vision-language model (a model trained to understand images and text together) reasons about what the camera sees to predict whether a grasp is even possible from each chain. This lets the planner compare routes not just by distance, but by whether they actually work for manipulation.

Why it works

Why planning the two together works

The core insight is that navigation and manipulation have conflicting goals: navigation wants the shortest path, but manipulation wants easy arm access. By generating all candidate chains and scoring them jointly, the planner discovers chains where the shortest path also yields good arm poses, or finds a slightly longer path that is much easier to grasp from.

Here's the chain: first, the robot's cameras and lidar build a shared 3D feature map. Next, for each direction from which the robot might approach the target (front, side, back), the planner generates a sequence of waypoints leading toward the object. Each sequence is paired with a candidate arm pose at the final waypoint. These waypoint-pose pairs are chained together into full candidate plans. Then, a learned hierarchical scoring function examines each chain: it checks the navigation cost (path length, collisions) and the manipulation feasibility (extracted via a vision-language model reasoning over 3D features). The planner selects the chain with the best trade-off. If the robot then observes new obstacles or the arm fails, it replans with fresh information, so the joint consideration is continuous.

Math after the picture

The scoring formula

First in words:

Total score for a chain = path cost plus a penalty if arm cannot grasp from this final pose, where the arm feasibility is predicted by a learned model.

Then the compact form:

score_chain = path_cost + lambda * (1 - P_feasible)

Every symbol:

score_chainTotal cost for this candidate chain; lower is better
path_costDistance and collision penalty along the navigation waypoints
lambdaHow much to value arm feasibility vs. path length
P_feasibleProbability the arm can grasp from this pose, predicted by the model (0 to 1)
1 - P_feasiblePenalty if feasibility is low; zero if grasp is certain
A tiny worked example
Chain A: path_cost = 5 meters, P_feasible = 0.9 (high arm confidence), lambda = 2. Score = 5 + 2*(1 - 0.9) = 5 + 0.2 = 5.2.
Chain B: path_cost = 4 meters, P_feasible = 0.4 (risky arm pose), lambda = 2. Score = 4 + 2*(1 - 0.4) = 4 + 1.2 = 5.2.
Chain C: path_cost = 6 meters, P_feasible = 0.95 (very safe), lambda = 2. Score = 6 + 2*(1 - 0.95) = 6 + 0.1 = 6.1.
The planner picks A or B (tied); both balance path vs. arm risk. C is rejected despite high feasibility because it detours too far.

The formula trades off how far the robot travels against whether its arm can actually grasp from the chosen pose.

What can go wrong

What can go wrong

Poor initial map. If the shared 3D feature map is incorrect or incomplete, feasibility scores are wrong and chains are ranked badly. The robot commits to an unsafe path.
Vision-language model misses an obstacle. If the model reasoning over 3D features fails to notice an obstacle or reachability limit, a chain scores high but fails at execution.
Changing environment. If obstacles move or the target shifts before the robot finishes, the old score is stale and replanning happens too late, causing collisions.
Done right: continuous replanning. The paper mitigates these by replanning every time the robot observes new information. If a chain is unsafe in practice, the next replan sees it and picks a different route.
What a runnable demo should prove

What a runnable demo should prove

Build a simple simulator with a robot arm and a mobile base. Place a target object in a room with obstacles. Run two planners: (1) separate navigation then manipulation, and (2) the joint chain-scoring method. Measure task success (does the robot reach and grasp?) and path efficiency (how much did it detour?).

Success rate = (tasks where robot grasped object) / (total tasks); Path efficiency = (median path length with joint planner) / (median path length with split planner)

The joint planner should succeed more often and travel shorter distances because it avoids dead-end positions that the separate planner would pick.
