Differential Fine-Tuning for Diverse Reasoning

Instead of tuning all weights the same way for all reasoning tasks, tune each weight differently depending on whether it helps one task or both.

Paper explainersAll themesLLMs & Foundation Models

When you teach a language model to solve multiple types of reasoning problems at once (like math, logic, and code), the training pulls on the same weights in contradictory directions. This paper discovers that each reasoning skill uses some unique weights and shares others, and by updating them with different strengths, the model keeps all skills sharp instead of trading one off against another.

The multi-task conflict

A single large language model needs to answer many kinds of questions: math problems, logic puzzles, code generation. You can teach it all three by collecting datasets for each and mixing them together, then training on the mix. But the weights (the numerical knobs inside the model) get pulled in opposite directions. Training hard on math might weaken code ability, and training on logic might weaken both. The model is stuck: it has to choose which skills to sacrifice.

A beginner might try training on each dataset separately and averaging the results, or training on one task then another in order. Both fail: averaged models are neither fish nor fowl, and sequential training (learn task A, then task B) causes the model to forget task A by the time task B is finished. The problem is that all weights are being changed uniformly, so a weight that benefits math but hurts logic gets tugged equally hard in both directions, creating a standoff.

The core tension: Training a model on multiple reasoning tasks pulls weights in conflicting directions, degrading performance on every task.

The algorithm as a flow

What it actually does

Analyze

Train on one task alone, watch which weights shift, rank them by importance to that skill.

Compare

Do the same for every other reasoning task, build a map of exclusive vs shared weights.

Plan

For each weight, decide its update strength based on exclusivity: strong if only one task needs it (changing it will not break others), mild if shared (changing it risks breaking neighbors).

Train mixed

Feed all reasoning datasets at once, but tug each weight with its assigned strength.

Result

Model learns all skills without forgetting, beating single-task training on each skill.

What the paper changes

The single change

The paper changes how hard each weight gets tuned when learning from mixed datasets. Instead of moving every weight equally, it moves a weight more aggressively if that weight matters only to one reasoning task (because pushing it hard will not injure other tasks), and more gently if the weight helps multiple tasks (because pushing it hard risks breaking one of the other skills that depend on it).

the object it moves  =  weight update strength per task
The hidden quantity

How much each weight is needed only by one skill

measured quantity  =  exclusive vs shared weight importance

This paper measures a quantity most prior work never names: for each weight, how much does that weight matter to this specific reasoning task compared to all the other tasks? Some weights are hired specialists (only math cares about them), while others are generalists (both math and logic benefit). The paper calls this the exclusive importance — how much this weight is uniquely valuable to this one task.

The paper estimates it by training on one task alone, measuring the gradient (which way the weight needs to move to improve on that task) and the importance based on how much the loss would worsen if you slightly moved that weight. A high exclusive importance means: change this weight boldly for this task, it will not hurt others. A low exclusive importance means: be careful, other tasks depend on this too.

Why it works

Why exclusive weights unlock harmony

The reason this works comes down to interference. When a weight is shared (both math and logic depend on it), tuning it for math alone might accidentally break logic. But when a weight belongs only to math, tuning it hard for math creates no collision. So the algorithm learns to ask: for each weight, in this batch of mixed tasks, how much does only this current task need this weight? If only math needs it, push it hard. If logic also needs it, push gently so logic does not get hurt.

By measuring exclusive importance beforehand (before mixed training starts), the algorithm knows which weights are safe to move boldly and which are pinch-points. Shared weights become gatekeepers — they are tuned conservatively, preserving all the skills that use them. Exclusive weights become specialists — they are tuned fully, becoming efficient tools for their one skill. The result is that all tasks improve at once, because no weight is being ripped in opposite directions.

The tuning formula

First in words:

For each weight in task T, the penalty for moving it is scaled by how much it matters only to task T, not to other tasks.

Then the compact form:

loss = sum_T sum_i (exclusive_importance_T_i * (weight_T_i - baseline_T_i)^2)

Every symbol:

lossthe total training cost
Tone of the reasoning tasks (math, logic, code)
ione weight in the model
exclusive_importance_T_ihow much weight i matters only to task T (1=very, 0=shared)
weight_T_ithe current value of weight i
baseline_T_ithe value of weight i before this task was trained
A tiny worked example
Weight w1 (math-only): exclusive_importance = 3.0, moved from 50 to 52 (change = 2) -> penalty = 3.0 * 2^2 = 12.0
Weight w2 (shared): exclusive_importance = 0.5, moved from 50 to 52 (same change = 2) -> penalty = 0.5 * 2^2 = 2.0
Same movement, but w1 is punished 6x harder, so training leaves w1 free to move for its task.

Higher exclusivity means the weight is allowed to move boldly for its task; lower exclusivity means the penalty is strong, forcing the update to stay small and preserve other tasks.

What can go wrong

What can go wrong

Wrong importance estimation. If the exclusive importance scores are computed incorrectly (e.g., from too little data or on the wrong kind of examples), the algorithm tunes the wrong weights boldly. If a math-only weight is actually shared, tuning it hard will break logic and the user will not know why.
One task dominates. If one reasoning task is much larger (more examples) than the others, it will still pull weights more often during training, even with differential scaling. The rarer tasks may still regress because they are updated less frequently.
New tasks interfere. The exclusive importance is measured before mixed training. If you add a fourth reasoning task that uses many of the math-only weights, they are no longer truly exclusive and will conflict again.
Done right. Use a held-out validation set of each reasoning task to measure exclusive importance (not the training data), and recompute importance when the task mix changes. Keep validation loss for all tasks monitored during training to catch interference early.
What a runnable demo should prove

What a runnable demo should prove

Build a toy model on three small reasoning tasks: (1) simple arithmetic (add two numbers), (2) logic puzzles (if A then B, what is C?), (3) substring matching. Train it three ways: separately on each task, all mixed with standard training, and all mixed with differential fine-tuning. For each approach, measure accuracy on a held-out test set for each task after training.

task_retention_score = (math_acc_after + logic_acc_after + code_acc_after) / 3, no skill falls below its single-task baseline

The metric to watch is whether all three skills improve together without any task regressing below its single-task performance, because exclusive weight tuning prevents one task from cannibalizing another. Standard mixed training will show one or two skills drop sharply; differential tuning will hold all three flat or rising.
