MAC-AMP: Multi-Agent Collaboration for Antimicrobial Peptide Design

Multiple AI agents debate and refine designs of disease-fighting peptides by reviewing each other's work in a closed loop, balancing safety, potency, and distinctiveness without black-box opacity.

Paper explainersAll themesAI for Science

Designing molecules that kill resistant bacteria but do not harm human cells requires hitting multiple targets at once: kill the pathogen, do not poison the patient, make something the body has never seen before. Traditional AI for drug design uses a single model with rules that nobody can fully explain. This paper shows how to use multiple AI agents (separate LLMs, each with a clear role) that grade each other's designs like a peer review board, learning which tweaks work better over time. The system finds better molecular designs because each agent catches problems the others would miss.

Zero assumption version

The single-model trap

A molecule is a tiny machine made of atoms. Antimicrobial peptides are chains of amino acids (the building blocks of proteins) that can punch holes in bacteria and kill them. The dream is to design peptides that are deadly to pathogens but harmless to humans.

A naive approach: feed a machine-learning model a dataset of known peptides and say, 'Learn to generate new ones.' The problem: that model optimizes for one goal at a time (maximize killing power, or minimize human toxicity), not both. When you force it to balance three targets together (activity, safety, and whether humans have never seen it before), it either fails or produces a opaque score ('this design scores 0.73') nobody can untangle. The engineer does not know whether to tweak the atoms or abandon the design.

In one sentence. MAC-AMP assigns a separate grading agent to each goal and runs a peer-review loop where agents critique each design, with the system learning which adjustments improve consensus, because independent reviewers catch goal-conflicts that a single model hides, and the loop reinforces changes that move from disagreement to agreement.

What the paper changes

What the paper changes

Instead of a single opaque scoring function, the paper replaces it with a team of independent agent-graders. Each agent (implemented as an LLM given a specific evaluation role) outputs human-readable feedback. The generator then sees all the feedback and learns which atom-swaps earn approval from more agents.

the object it moves  =  the scoring function
The hidden quantity

Agent agreement score

measured quantity  =  how many agents approve the design

The hidden quantity is the count of how many agent-graders give a positive review to a design. If all three agents say 'good,' the count is 3. If only the Activity agent approves, the count is 1.

The paper measures this by running each candidate design past the three agents, collecting their written feedback, and counting how many wrote something like 'This design achieves the goal.' The design generator then learns: tweaks that move the count from 1 to 3 are the ones to try again; tweaks that move it from 3 to 1 are the ones to avoid.

Why it works

Why independent agents catch what one model misses

A single model trained to balance three conflicting goals often finds a compromise that is average at all three. An Activity-optimized model kills bacteria but might produce a toxin. A Safety-optimized model is harmless but inactive. When forced to blend, the model weights each goal as an abstract number and outputs a score that does not reveal whether it chose safety over activity or chose badly.

Three separate agents bypass this. An Activity agent, built only to recognize bacterial-killing power, has no reason to compromise. It says 'this design kills germs well' or 'this design is weak against bacteria.' A Safety agent, built only to spot human toxicity, does the same. A Distinctness agent flags designs humans have seen before. Because each agent has a single, clear job, its review is legible: the engineer reads 'Activity=good, Safety=bad, Distinctness=good' and instantly knows the design fails on one axis.

The closed-loop part: the design generator reads all three reviews and learns by trial. A tweak to atoms that moves the verdict from 'bad' to 'good' on Safety gets reinforced. A tweak that breaks Activity gets punished. Over time, the system finds peptides that earn 'good' from all three agents—not a compromise score, but genuine success on all fronts.

Math after the picture

The reinforcement learning reward

First in words:

reward = number_of_approving_agents, or sometimes reward = sum of individual agent scores (if agents output numeric grades). The design generator tweaks the peptide sequence to maximize this reward over many iterations.

Then the compact form:

reward_t = sum_i agent_i(design_t), where agent_i is agent i's approval score (1 if positive, 0 if negative), and design_t is the peptide at iteration t

Every symbol:

reward_tHow many agents approve the design at step t (a number from 0 to 3)
agent_iThe i-th agent (Activity, Safety, or Novelty)
agent_i(design_t)Whether that agent approves (1=yes, 0=no)
design_tThe amino-acid sequence proposed at step t
sum_iAdd up all three agents' votes
A tiny worked example
Design proposal 1: MKTF peptide
Activity agent: Yes, kills bacteria (1 point)
Safety agent: No, harms human cells (0 points)
Distinctness agent: Yes, never seen before (1 point)
reward = 1 + 0 + 1 = 2 out of 3
Design proposal 2: MKTF with one atom swapped (call it MKTF-v2)
Activity agent: Yes (1 point)
Safety agent: Yes, now safe (1 point)
Distinctness agent: Yes (1 point)
reward = 1 + 1 + 1 = 3 out of 3
The system learns: the one-atom change that moved reward from 2 to 3 is worth repeating.

The generator learns which tweaks to the amino-acid sequence earn more agent approvals; it discards tweaks that lose approvals.

What can go wrong

What can go wrong

Agents reach no consensus. If Activity and Safety agents strongly disagree on a design (one says yes, one says no), the system may spin in loops trying designs neither agent ever fully approves. The closed-loop learning may not converge.
Agents are poorly prompted. If an agent-prompt is vague (e.g., 'rate the safety' instead of 'does this peptide bind human cell receptors?'), the agent gives inconsistent feedback and the generator learns nothing.
Overfitting to agent feedback. The generator may find designs that fool the agents (e.g., a sequence the agents have never seen before and wrongly approve) but fail in real experiments. The agents are only as good as their underlying knowledge.
Done right. Agents are built with clear, measurable criteria (e.g., 'approve if the design binds the target bacteria and does not bind human cell lines'). The closed-loop runs long enough that agent feedback correlates with real lab results. The system is used to suggest candidates for experimental validation, not as a final authority.
What a runnable demo should prove

What a runnable demo should prove

Build a small closed-loop: start with 10 known antimicrobial peptides. Craft three agent-prompts (one for activity, one for safety, one for distinctness). Generate 50 random peptides and let each agent grade them. Track the approval count for each. Then run a reinforcement learning loop: generate 200 variants by small edits (changing one or two amino acids), grade each, and measure whether the system tends to find peptides that earn approval from all three agents.

success_rate = (number of final designs with 3/3 agent approvals) / (total number of final designs)

The demo must show that the approval count rises over iterations (from an average of ~1.5 at the start to ~2.7 by round 200), proving that the generator is learning which edits earn broader agent consensus.
