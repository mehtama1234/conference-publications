Large-Scale Terminal Agentic Trajectory Generation from Dockerized Environments

TerminalTraj builds many runnable terminal tasks and verified solution traces by pairing each task with its own Docker environment and checker code.

Paper explainersAll themesAgents & Tool Use

Terminal agents are trained from interaction traces: commands, file edits, test runs, failures, and repairs. Those traces are only useful when they are real. A terminal task is not a short text puzzle. It depends on files, package versions, shell tools, and project state. If the environment is wrong, the trace teaches the model the wrong lesson. If the final answer cannot be checked, the trace may look good while actually being wrong. This paper tackles both problems by building a large pipeline that creates runnable Docker environments, writes tasks that fit those environments, and adds executable checkers so each trajectory can be verified.

Why terminal-agent data is hard to build

A terminal agent only learns the right habits when the training trace comes from a task that can actually run. Many existing datasets describe tasks in words, but the commands inside them depend on unstated tools, missing files, or package versions that are not present. That makes the trace brittle because the same command can succeed in one repository and fail in another.

Verification is the second obstacle. A terminal task may ask the agent to edit code, inspect logs, or configure a service. Those outputs vary from task to task, so a single generic checker is not enough. If the dataset cannot tell whether a trajectory really solved the task, training on it mixes good traces with bad ones, which weakens the signal the model is supposed to learn.

The paper's move in one sentence. Build each training example as a three-part package: a Docker environment that runs, a task written for that environment, and checker code that can execute and confirm success.

The algorithm as a flow

What it actually does

Step 1: Filter repositories for runnable setup

Scan candidate repositories and keep the ones that can support a Docker image because the later traces must execute in a real shell.

Step 2: Build Docker images

Create environment images that contain the right files and dependencies so that terminal commands run in a stable workspace.

Step 3: Generate environment-aligned tasks

Write tasks that match the contents of each image so that the task is neither impossible nor detached from the repository.

Step 4: Synthesize agent trajectories

Run an agent inside the image to produce command sequences, edits, and retries that resemble real terminal work.

Step 5: Execute validation code

Check each finished state with task-specific executable tests so that only verified trajectories enter the training set.

What the paper changes

What the paper changes

The paper changes data construction for terminal agents. Instead of collecting free-form traces first and hoping they correspond to real tasks, it binds every trace to a runnable environment and a concrete checker.

the object it moves  =  Terminal-agent training data pipeline
The hidden quantity

The hidden quantity: trace trustworthiness

measured quantity  =  how likely a trajectory is to teach the model a correct terminal behavior

The most important quantity is trace trustworthiness. A trajectory is trustworthy when it came from a task that could run, and when the final state was checked by code instead of by a guess. That quantity is not visible in the text of the trace alone because a command log can look plausible while still depending on a missing package or leaving the repository in the wrong state.

TerminalTraj raises trustworthiness by enforcing two gates. The environment gate checks that the task lives inside a usable Docker image. The validation gate checks that the task outcome passes executable tests. Those gates matter because training improves only when the model sees traces where the actions and the success signal both correspond to the same real workspace.

Why it works

Why it works

The pipeline works because it solves the environment problem before it solves the trajectory problem. Terminal work depends on local state: installed tools, repository layout, test commands, and service configuration. By deriving tasks from repositories that already support Docker execution, the paper makes the environment concrete first. That narrows the space of valid actions, so the agent is less likely to produce traces that look fluent but do not fit the workspace.

The checker stage matters just as much. A terminal agent often reaches a state that sounds done in natural language but still fails a test, breaks formatting, or leaves part of the task unfinished. Executable validation catches those cases because success is measured by running code against the final workspace. That gives a sharper training signal by separating real success from plausible-looking failure.

The large scale matters because terminal behavior covers many domains and tools. A model that only sees one project style will overfit to that style. A dataset built from many Dockerized repositories teaches broader action patterns because the agent repeatedly has to inspect files, reason about local constraints, run checks, and repair mistakes in different environments.

Math after the picture

The acceptance rule

First in words:

Keep a trajectory only when the environment runs and the task-specific checker confirms success.

Then the compact form:

keep(trajectory) = runnable(environment) AND passes_check(final_state, task)

Every symbol:

keep(trajectory)whether the trajectory is admitted into the dataset
runnable(environment)whether the Docker environment starts and supports the task
passes_check(final_state, task)whether executable validation code says the task was solved
final_statethe repository and shell state after the trajectory ends
taskthe environment-aligned instruction the agent was trying to solve
A tiny worked example
Suppose a repository contains a Python service and a failing test.
The Docker image builds and the test command runs, so runnable(environment) is true.
The agent edits one file and claims the bug is fixed, but the checker still fails one test. Then passes_check(final_state, task) is false.
Because both conditions are required, keep(trajectory) is false and the trace is discarded.
A second trajectory fixes the bug and all checker commands pass. Then both conditions are true, so the trace is kept.

The rule is simple but important: the dataset trusts execution instead of appearance.

What can go wrong

What can go wrong

A repository may build but still hide task traps. A Docker image can start while some corner workflow is still unusable, so task generation must stay aligned to what the image actually supports because runtime surprises reduce data trustworthiness.
Checker code can miss part of the task. If the validation logic only checks one visible output, a trajectory may pass while leaving another required change undone, so checker design matters because the model learns whatever the checker rewards.
Generated tasks may become repetitive. If many tasks share the same repair pattern, the dataset will cover fewer real agent behaviors, so repository diversity matters because broad environments force broader terminal reasoning.
Done right. The pipeline works well when task generation, environment construction, and checker writing are tied together, because then each accepted trajectory reflects a real and testable shell workflow.
What a runnable demo should prove

What a runnable demo should prove

Build a small benchmark with ten repositories that each expose a Docker image, one bug-fix task, and one task-specific checker. Generate trajectories with and without environment-aligned task writing. Compare how many traces replay successfully from scratch and how many pass the checker at the end. The demo should show that replayable verified traces are much more common when the task is written after the environment is fixed, because the agent is solving the task inside the workspace it was built for.

trusted_trace_rate = verified_replayable_trajectories / total_generated_trajectories

The point of the demo is to show that terminal-agent data quality depends on execution and checking together, because either one alone still lets bad traces slip through.
