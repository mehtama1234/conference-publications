AdaReasoner: Dynamic Tool Orchestration for Iterative Visual Reasoning

AdaReasoner learns which tools to call, in what order, and how often, because hard visual reasoning problems usually need a changing sequence of specialized operations rather than one fixed tool call.

Paper explainersAll themesAgents & Tool Use

Tool-augmented multimodal models often treat tools as one-shot add-ons. They call one detector, one calculator, or one external model, then continue reasoning as if the problem were solved. Complex visual tasks do not work that way. A model may need to inspect the scene, run a shape-and-location solver, revisit a cropped region, then call a planner again after new evidence appears. AdaReasoner trains the model to build that multi-turn tool sequence on its own. The paper pairs curated trajectory data with a tailored policy-optimization rule so the model learns not only to use tools, but to organize them adaptively across the whole reasoning process by reinforcing tool sequences that improve the final answer.

Zero assumption version

Why one-shot tool use breaks on hard visual tasks

A visual reasoning task may require several different operations before the answer is clear. The model may need to read text, zoom into an object, compare locations, compute a distance, then revise its plan after the result of that computation. A single fixed tool call cannot cover that whole chain.

Many current systems still rely on atomic tool use. They either attach one tool and hope it is enough, or they use a hand-written sequence of tools that does not adapt to the case at hand. The paper argues that the real challenge is orchestration: the agent must decide which tool to call next, whether to keep using the same tool, and when to stop because another operation is now more useful.

In one sentence. Train the model on full multi-turn tool trajectories so that it can assemble an effective sequence of tool calls for each visual problem instead of relying on one fixed call pattern.

The algorithm as a flow

What it actually does

Curate trajectory data

The training set includes full multi-turn reasoning traces with tool calls and tool results, because the model must learn sequencing rather than isolated actions.

Start from a multimodal base model

The model already has visual and language capability, so the new training can focus on how to organize external tools across several reasoning turns.

Optimize full tool trajectories

The policy objective rewards trajectories that solve the task efficiently, so the model learns when extra calls help because they raise final answer quality and when they only waste compute because they add cost without improving the result.

Reuse good tools and drop weak ones

During training, the agent learns self-adaptation because tool patterns that improve answers are reinforced while unhelpful calls fade away.

Answer after iterative refinement

The final response is produced after the model has gathered the evidence it needs from the chosen tool chain.

What the paper changes

What the paper changes

The paper changes the action space from single tool invocations to full multi-turn tool trajectories. That matters because the model is now judged on how well it organizes a complete reasoning process rather than on whether one isolated tool call looked plausible.

the object it moves  =  the tool-calling policy over multiple turns
The hidden quantity

The hidden quantity: tool-chain usefulness

measured quantity  =  how much a sequence of tool calls improves the final answer

A tool call is only useful through its effect on the full reasoning chain. A crop tool may look pointless in isolation, but it becomes necessary if it prepares the exact region that the next spatial solver needs. Likewise, a specialist model may be unnecessary if the answer is already clear after earlier steps.

AdaReasoner tries to estimate this hidden usefulness at the trajectory level. The policy update sees the quality of the whole chain, so the model can learn patterns such as using one tool twice, abandoning another tool entirely, or stopping early when enough evidence has already been collected, because those choices change the final trajectory reward.

Why it works

Why trajectory-level training teaches orchestration

Supervising only single tool choices gives the model no view of delayed effects. A tool call that does not help immediately may still be the right move if it sets up the next step by producing the evidence that a later tool needs. The reverse is also true: a flashy tool output may add little if it does not change the later reasoning path.

AdaReasoner fixes that by optimizing over full tool trajectories. The model is rewarded for ending with a strong answer after a sequence of calls, not for looking reasonable one step at a time. That lets it learn cross-step patterns: when to branch into a specialist service, when to revisit a tool after seeing new evidence, and when to stop because the marginal value of another call has dropped.

Math after the picture

Trajectory optimization view

First in words:

The policy objective should increase the probability of tool sequences that lead to better final answers and decrease the probability of sequences that waste calls or end with poor answers.

Then the compact form:

J = E_tau [ Reward(tau) - beta * Calls(tau) ]

Every symbol:

Jtraining objective for the tool policy
tauone full reasoning trajectory with tool calls and outputs
Reward(tau)task score for the final answer produced by trajectory tau
Calls(tau)number or cost of tool calls used in trajectory tau
betaweight on call cost
A tiny worked example
Trajectory A uses one detector call and answers incorrectly, so its final reward is 0.
Trajectory B uses a detector, then a crop tool, then a spatial solver, and answers correctly, so its final reward is 1.
If beta is 0.1, trajectory B receives 1 - 0.3 = 0.7 after paying for three calls.
A four-call trajectory that still answers correctly but includes one wasted call would receive a lower score, so training prefers the shorter useful chain.

The key is that the score belongs to the whole tool chain, because the value of one call depends on what the other calls made possible.

What can go wrong

What can go wrong

Poor trajectory data. If the curated training traces overuse certain tools or omit strong alternatives, the policy may learn a brittle orchestration pattern because it never sees better sequences.
Reward only values accuracy. If the objective ignores call cost, the agent may keep calling tools even after the answer is already clear because extra calls are never penalized.
Tool outputs may conflict. Different tools can return incompatible evidence. If the model cannot reconcile those outputs, it may extend the chain without improving the answer because later reasoning becomes confused.
Done right. The design works when trajectory rewards reflect both answer quality and tool cost, because then the agent learns to keep only the calls that materially improve the final reasoning path.
What a runnable demo should prove

What a runnable demo should prove

Build a visual benchmark where some questions require several dependent operations, such as detecting an object, zooming into a region, measuring a relation, and then answering. Provide a small set of callable tools and compare three systems: direct answering, one-shot tool use, and dynamic multi-turn orchestration.

Record the exact call traces, answer quality, and total call count. The expected result is that the dynamic system should solve the multi-step cases more often while keeping a shorter useful tool chain than a naive always-call-everything strategy, because it learns which calls actually matter.

trajectory_success = correct_answers / total_questions, reported together with average_tool_calls

The demo should show that hard visual reasoning depends on organizing tools across time, not merely attaching one tool to the model.
