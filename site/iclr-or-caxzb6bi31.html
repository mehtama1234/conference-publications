Figma2Code: Multimodal Design-to-Code

Combining design images with Figma metadata gives AI better information to write UI code, but creates a hidden tradeoff between how accurate the code looks, how well it adapts to different screen sizes, and how maintainable the code stays.

Paper explainersAll themesComputer Vision

Design-to-code means turning a designer's mockup into working UI code (HTML/CSS, React, Flutter). Until now, AI models have only seen pictures of designs. This paper shows that adding the metadata from real Figma files—the blueprints designers work with—helps the AI write code that looks more like the design because the metadata contains exact colors, spacing, and layer names the AI can copy directly. But it uncovers a hidden tension: adding metadata hurts the code's ability to adjust to phone screens, and makes the code messier.

Zero assumption version

Images alone are not enough

Designers use Figma, a professional tool that stores not just pictures of layouts but also structured metadata: layer names, component hierarchies, color palettes, font sizes, spacing rules. When a designer exports a mockup as an image, all that information is lost—the AI sees only pixels.

Current AI systems (given only the design image) have to guess what the designer intended. They see a button but not its reusable component name. They see spacing but not the responsive grid rules. So they produce rigid code that looks right in one screenshot but breaks on a phone, or code that is just a giant pile of custom styles instead of reusable pieces.

The industry has real Figma files sitting on disk. Why not use them?

In one sentence. The paper feeds both the design image AND the Figma metadata file into a language model, measuring how this changes code quality across three separate goals: looks, adaptability, and cleanliness.

What the paper changes

The input format changes

Design-to-code takes two new input streams: the rendered design image (as before) plus the structured Figma metadata as text (layer hierarchy, component names, typography, colors, spacing). The model sees both at once, instead of only the image.

the object it moves  =  Input modality (image-only to image+metadata)
The hidden quantity

The three-way code quality tradeoff

measured quantity  =  Balance between visual fidelity, layout responsiveness, and code maintainability

The paper uncovers a hidden quantity: the tension between three independent measures of code quality. Visual fidelity means the generated code renders to look like the designer's original mockup (measured by comparing screenshots pixel-by-pixel through image embeddings). Layout responsiveness means the code gracefully adapts when the screen shrinks from desktop to mobile—text reflows, buttons stack, spacing adjusts. Code maintainability means the code uses reusable named components and structured styles instead of hardcoded values and custom one-off rules.

The paper measures this by scoring every generated code sample on all three axes and observing which methods rank high on one but low on others. Metadata-heavy methods maximize visual fidelity (0.7990 embedding similarity) but break responsiveness (5% of adaptive breaks) and maintainability. Image-only methods do the opposite: worse visuals but responsive, reusable code.

Why it works

Why metadata both helps and hurts

Metadata (layer names, colors, spacing values, component structure) is a perfect, complete spec of the designer's intent. When the model reads it, it can reproduce exact colors and dimensions, so the rendered page looks identical to the mockup. This wins on visual fidelity.

But metadata is precise about the current design, not about the principles behind it. A metadata value '120px margin' is locked to that exact number, not a rule like 'scale with screen size.' When the model copies metadata values directly into code, it hard-codes those numbers. The resulting code does not adapt—it breaks on phones. Maintainability suffers too, because the model ends up with many similar but distinct style definitions instead of reusable components.

Image-only models, by contrast, treat the design as a whole visual pattern. They infer structure and proportions from what they see (buttons align, text is grouped) and tend to write more generic, composable code. But they have to guess visual details from pixels, so they produce less accurate renders.

This is not a bug in the model—it is inherent to the information. Metadata is high-fidelity but prescriptive. Images are low-detail but principle-preserving.

The three-objective scoring formula

First in words:

The best code minimizes a weighted penalty that combines visual distance, lack of adaptability, and poor maintainability. Each objective gets its own weight (alpha, beta, gamma) that the researcher chooses.

Then the compact form:

C = arg max C [ -α·D(V, Render(C)) + β·RS(C) + γ·MS(C) ]

Every symbol:

Cthe generated UI code (HTML/CSS or React)
Vthe original design image
Render(C)the actual rendered page from code C
D(V, Render(C))visual distance (how different the renders look; 0 means identical)
αweight on visual fidelity (higher = more important to match looks)
RS(C)responsiveness score (higher = code adapts better to screen sizes)
βweight on responsiveness
MS(C)maintainability score (higher = cleaner, reusable structure)
γweight on maintainability
A tiny worked example
Imagine a designer's mockup calls for a button with 12px padding. Two models generate code:
Model A (metadata-only): writes 'padding: 12px' in the CSS. Looks perfect (D=0.05), but does not scale to mobile (RS=30), and the padding is custom-coded just for this button (MS=20). Score: -1·0.05 + 1·30 + 1·20 = 49.95 (high score = good under responsiveness/maintainability).
Model B (image-smart): writes 'padding: var(--spacing-sm)' where the spacing variable adapts to screen size. Looks less perfect (D=0.25, a bigger visual distance), but scales to mobile (RS=80), and reuses the spacing variable (MS=80). Score: -1·0.25 + 1·80 + 1·80 = 159.75 (better overall if you weight all three equally).
By choosing α, β, γ, the researcher tunes which goal matters most. High α (visual fidelity) favors Model A. Higher β or γ (responsiveness/maintainability) favors Model B. The paper shows no model wins across all weights: the tradeoff is real.

The formula captures the hidden conflict: maximize looks, adaptability, and code quality simultaneously, and you lose on at least two.

What can go wrong

What can go wrong

Direct metadata copying. The model reads a metadata value like 'width: 480px' and writes it verbatim into CSS. This works for one screen size but hard-codes rigid layouts that fail on phones and tablets.
Component hierarchy flattening. Figma's metadata preserves component structure (a reusable button, a card layout). If the model treats each metadata value as an independent instruction instead of learning the design hierarchy, it loses composability and outputs redundant CSS.
Over-reliance on image. If metadata is messy or incomplete, the model may ignore it and fall back to image-only code generation, nullifying the metadata advantage and producing worse code than pure image-based methods.
Conflicting signals. Image and metadata might contradict each other (e.g., metadata says 12px but the rendered design image shows 14px due to rounding). The model must decide which to trust.
Done right. A smarter model would use metadata to infer design intent (responsive spacing, component patterns, naming conventions) rather than copying raw values. It would learn that 'padding-sm' means scale the padding proportionally, not lock it to 12px.
What a runnable demo should prove

What a runnable demo should prove

Build a small script that takes a simple Figma file (image + metadata JSON) and three different code generators: (1) image-only baseline, (2) metadata-only baseline, (3) a multimodal model. Render all three outputs and measure them on the three axes. Show that no single generator wins on all three, because metadata inputs contain exact values that trade away screen adaptability to gain visual accuracy—the information is too prescriptive.

tradeoff_score = visual_fidelity - responsiveness_loss - maintainability_loss (using the paper's metrics). For each method, report the three scores separately, not as a single number.

The core finding must be visible: adding metadata improves how closely the code matches the design because it provides exact pixel values, but this exact information also locks the code to one screen size, making it rigid and redundant. This tradeoff is inherent to the information source, not a flaw in the model.
