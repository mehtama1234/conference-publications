When a large language model sees both a design picture AND its metadata file, it makes better UI code than from the picture alone.

Converting a designer's mockup into working UI code is tedious and expensive. Today's AI models can turn a design image into code, but they miss details hidden inside Figma files—a tool that stores both pictures and structured information like layers, spacing, and component names. Zero assumption version

Design to code is messy, and models guess the details

A designer creates a UI mockup in Figma, a tool that designers use to draw buttons, forms, and layouts. The mockup shows colors, fonts, spacing. But Figma also stores a list of every layer, every component name, every spacing rule—information hidden inside the file format, not visible in the picture alone.

A naive approach: take a screenshot of the design and feed it to a large language model (a model trained to write and understand text). The model stares at pixels and tries to reverse-engineer the structure: Is that gap 8 pixels or 16? Is that a button component or just a rectangle? The model guesses, and often gets it wrong. The code it writes looks right but breaks when the screen resizes, or uses components that don't exist in the codebase.

The gap: Figma files contain metadata (lists of layers, component names, color swatches, spacing rules) that the designer already knows is important. But traditional design-to-code systems throw it away.

In one sentence. Add metadata from Figma files to the design image, and the model writes code that respects layout rules and reuses components correctly.

What the paper changes

What the paper changes

Instead of handing the model only a design picture, hand it both the picture and a structured text file containing metadata (layer names, spacing values, component types, color definitions). The model now has two sources of truth, not one.

the object it moves  =  Input modalities: image + metadata
The hidden quantity

Metadata coverage: how much of the design is explicitly named

measured quantity  =  Metadata coverage

Metadata coverage is the fraction of the design's structure that is explicitly named in the Figma file, rather than hidden in the picture alone. When you store a button's exact width, its color value, its component name, and its position in the layer tree, those are all metadata. When the model can read this list, it doesn't have to guess.

The paper measures this by comparing: for each element in the final code (button, form, spacing rule, color), is that detail available in the metadata? When metadata is complete, the model can directly read the correct value. When metadata is sparse, the model must reverse-engineer from pixels, and errors spike.

Why it works

Why adding metadata fixes the problem

When a model has only a picture, it must look at every pixel and decide: Is this a button? What color is it? How far from the edge? This is backward reasoning (from pixels back to intent), and the model often guesses wrong. Spacing that looks like 16 pixels could be 12 or 20, and the model picks wrong.

When the model also has metadata—a list saying Component: 'PrimaryButton', Width: 96, Padding: 8, Color: #0066CC—it reads these facts directly. It no longer has to reverse-engineer; the designer has already named everything. The model can focus on understanding how these named pieces fit together, rather than inventing the names from scratch.

This matters for code quality because real UI code relies on naming and reuse. If the model doesn't know that three buttons share the same component class, it will write three copies of the button code. If metadata says all three buttons are the same component, the model can generate one component and reuse it three times. This makes the code maintainable, because when a designer changes the button later, one component change fixes all three buttons at once instead of requiring three separate edits scattered through the code.

How the model uses metadata

First in words:

metadata_score = (number_of_elements_from_metadata / total_number_of_elements) * code_quality_weight

Then the compact form:

Q = (M / T) * W + (1 - M/T) * G

Every symbol:

QFinal code quality score
MNumber of design elements found in metadata
TTotal number of design elements
WQuality when element is in metadata (higher confidence)
GQuality when element must be guessed from picture (lower confidence)
A tiny worked example
Suppose a design has 10 elements: 5 buttons, 3 text fields, 2 spacing rules.
Metadata covers 8 elements (all buttons and text fields are named).
M / T = 8 / 10 = 0.8.
Elements from metadata (8): assigned quality 90 (high; model reads directly).
Elements guessed from picture (2): assigned quality 60 (medium; model guesses spacing rules).
Q = (0.8 * 90) + (0.2 * 60) = 72 + 12 = 84.
Without metadata (all guessed): Q = 0 * 90 + 1.0 * 60 = 60. Metadata boosts quality by 24 points.

When more of the design is explicitly named in Figma (high M/T), the model produces cleaner code because it reads rather than guesses.

What can go wrong

What can go wrong

Metadata is incomplete or wrong. If a designer forgets to name a layer or uses inconsistent spacing values in the Figma file, the metadata is unreliable. The model will either read wrong facts or fall back to guessing.
Metadata format is non-standard. Different designers structure their Figma files differently. One might use component instances; another might use separate rectangles. If the model expects one format and encounters another, it will misread the structure.
Model doesn't trust metadata. A poorly trained model might ignore metadata and rely only on the picture, falling back to guessing. The paper shows this happens when models are trained primarily on image-only data.
Done right. When metadata is complete, consistent, and the model is trained on multimodal examples, the model learns to read both sources and generate code that respects both the visual design and the structural intent.
What a runnable demo should prove

What a runnable demo should prove

Build a small UI (5 components: a button, a form with two fields, a text block, and a spacing rule). Export it as a Figma file, including metadata. Then run it through the model twice: once with only the picture, once with both picture and metadata. Compare the generated code.

Metadata benefit = (score_with_metadata - score_without_metadata) / score_without_metadata * 100%

The metric that matters most: when metadata is present, the model correctly reuses components and preserves spacing. Without metadata, it duplicates code and guesses spacing values.
