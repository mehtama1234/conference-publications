MoMaGen: Constrained Data Generation for Bimanual Mobile Manipulation

Instead of filming expensive human robot demos, MoMaGen automatically generates diverse training examples by placing the robot base and camera to satisfy physical reachability and camera visibility rules at once.

Paper explainersAll themesRobotics & Control

Training robots from human demonstrations is the gold standard but costs huge time and money, especially when the robot has a mobile base (wheels) plus two arms. Old automated systems struggled with two hard problems: where to position the mobile base so the arms can actually reach the task, and where to point the camera so it sees what the arms are doing. MoMaGen treats these as a single constrained optimization problem, satisfying hard rules (base must be reachable, arms must not collide) while balancing softer preferences (camera should have a clear view, base should stay stable during movement). The result is that you can generate hundreds of realistic training examples from a single human demo, and robots trained on these generated examples succeed in the real world.

Zero assumption version

Why do we need better automated demos?

Training a robot to pick up objects works best when humans show it examples — a human teleoperate the robot arm, base, and camera together, and the robot learns to copy those movements. But this is exhausting: a single useful example takes minutes to film, and you need hundreds of them for the robot to handle different situations reliably.

Old systems tried to automatically make more examples by replaying the same task in different room layouts — they move furniture around in simulation, rerun the same arm movements, and record what the robot sees. The problem: they ignored two catastrophic constraints. First, when the base wheels into a new position, the arms suddenly cannot reach where they were reaching before (reachability fails). Second, the camera moves with the base, so if you park the robot in a bad spot, the camera will be facing a wall and the training data will be useless (visibility collapses). One system might solve reachability by pure luck; the next position breaks visibility. Humans have to manually patch each failure.

So the task is: automatically place the robot's base and orient the camera such that both constraints are satisfied at once, and the generated examples are diverse enough that robots actually learn.

The method in one sentence. MoMaGen writes base placement and camera orientation as a single constrained optimization problem: satisfy hard rules (reachable, collision-free) and balance soft rules (good camera view, stable base), then solve it for many different room layouts at once.

The algorithm as a flow

What it actually does

Step 1: Load a human demo

Record one human teleoperated manipulation task (base moves, arms move, camera pans).

Step 2: List hard constraints

Define rules that absolutely must hold: arms reach target, no self-collision, base inside arena, no base-wall collision.

Step 3: List soft constraints

Define preferences to balance: camera should see arm workspace, navigation path should be stable, base should not be too far from target.

Step 4: Sample room layouts and solve

For each random furniture configuration, find a base pose and camera orientation that satisfy hard rules and minimize soft constraint violations.

Step 5: Record generated demo

Replay the original arm trajectory from the new base and camera position, capture the new view, and save as training data.

What the paper changes

What changes

The paper changes how the robot's position is computed when you want to replay a task in a new room layout. Instead of keeping the base in a fixed place and hoping the arms still reach, MoMaGen finds the optimal base position (and camera angle) for each new layout.

the object it moves  =  base position and camera angle
The hidden quantity

The constraint satisfaction score

measured quantity  =  reachability and visibility satisfaction

MoMaGen measures how well the robot can actually execute the task at a given base position. This score has two parts: reachability (can the arms reach all the waypoints in the demo?) and visibility (does the camera see the arm workspace during the task?). Some constraints are hard rules (must be true or generation fails), and some are soft (violation is bad but acceptable if reachability wins).

The paper estimates this score by running a physics simulator at each proposed base position: the robot checks if its arms can actually move through the intended motion without hitting walls, furniture, or itself. If reachability fails, that position is rejected because a position where the arms cannot move is useless for training. If reachability passes but the camera view is poor, the solver nudges the base slightly to find a new angle that shows the arms better, because a camera that sees the task generates more informative training data.

Why it works

Why constraint satisfaction fixes the problem

Old methods replayed arm movements from a fixed base position across different room layouts. The base placement was either random or ignored — so it worked by accident for some layouts and failed for others. Reachability broke when furniture moved. Visibility broke when the base was in the wrong corner.

MoMaGen inverts this: for each layout, it finds the base position that makes reachability and visibility both possible. Because hard constraints are enforced (reachability is not optional), every generated example is guaranteed valid. Because soft constraints are balanced (camera visibility is improved but not required), the diversity of valid base positions is maximized. This means the robot sees many different viewpoints and base configurations, all of which are physically realistic, so it learns a general policy rather than overfitting to one narrow scenario.

Here is what actually matters: the problem is not that room layouts are hard — it is that base placement is independent in old methods. Coupling base placement to layout constraints, and solving them together, makes diversity and validity automatic.

Math after the picture

The optimization formula

First in words:

minimize the sum of soft constraint violations, subject to hard constraints being satisfied

Then the compact form:

minimize_p sum_j c_j * v_j(p) subject to r_i(p) <= 0 for all i

Every symbol:

pbase position and camera angle (what we are solving for)
r_i(p)hard constraint i (reachability, collision): must be <=0
v_j(p)soft constraint violation j (visibility gap, instability)
c_jweight (importance) of soft constraint j
A tiny worked example
Suppose base position A: reachability check = ok (r < 0), visibility gap = 20 degrees, stability cost = 0.5. Total soft cost = 1.0 * 20 + 2.0 * 0.5 = 21.
Base position B: reachability check = ok (r < 0), visibility gap = 5 degrees, stability cost = 1.0. Total soft cost = 1.0 * 5 + 2.0 * 1.0 = 7.
Base position C: reachability check = fail (r > 0). Rejected immediately, never scored.
Solver picks position B: valid (hard constraint met) and best soft score (7 vs 21).

Hard constraints are deal-breakers; soft constraints are preferences. The solver tries all promising base positions in simulation, evaluates each, and picks the best valid one.

What can go wrong

What can go wrong

No valid base position exists. If a room layout is too cluttered or the task workspace is too constrained, the solver may find no base position that satisfies all hard constraints. In this case, that layout is skipped and the solver tries the next layout.
Soft constraints are weighted poorly. If visibility is weighted too low, the robot may generate data with the camera pointed at a wall, and the learned policy will be blind. If stability is weighted too high, the robot might place the base so far from the task that the arms are at full stretch and fragile. The weights must be tuned per task.
Physics simulation is slow. Checking reachability by running a full arm-motion simulation takes time. For real-time generation, the solver may have to evaluate fewer candidate positions, and when the solver evaluates fewer positions it is more likely to miss a better one because it simply never tried it.
Done right. When hard constraints are clearly defined, soft constraints are reasonably weighted, and the solver is given enough time, MoMaGen reliably finds base positions that are valid, diverse, and realistic.
What a runnable demo should prove

What a runnable demo should prove

Build a simulation of a bimanual mobile manipulator (two arms, mobile base, RGB camera) in a simple 3D scene. Load a single human-recorded trajectory of picking up an object (recorded from one base position and camera angle). Use MoMaGen to automatically generate 10 new trajectories by sampling 10 different random furniture layouts and solving for the best base position in each. For each generated trajectory, measure: (1) reachability — does the arm motion complete without hitting anything? (2) visibility — what percentage of the trajectory is in the camera's view? (3) camera diversity — how different are the viewpoints? Finally, use all 10 generated trajectories to train an imitation learning policy and measure how well it generalizes to room layouts it has never seen.

success_rate = (number of layouts where reachability and visibility both pass) / (total layouts sampled); diversity = average pairwise difference in camera viewpoint directions

The demo must show that MoMaGen produces valid base positions for nearly all layouts (success >90%) and that the generated dataset covers many camera angles, whereas random base placement succeeds in <50% of layouts.
