Fix Before Search: Benchmarking Agentic Visual Query Pre-processing in Multimodal Retrieval-augmented Generation

Treat a bad image query as a repair problem before retrieval, because retrieval cannot recover evidence that the query image failed to expose.

Paper explainersAll themesMultimodal

Multimodal retrieval-augmented generation usually assumes the input image is already usable. Real inputs break that assumption. A query image may be blurred, rotated, cropped poorly, low contrast, or semantically ambiguous. Once that degraded image goes into retrieval, the retriever returns the wrong documents because the visual evidence itself is damaged. This paper defines visual query pre-processing as an agent decision problem: diagnose the defect, choose a perceptual tool, choose tool settings, and only then retrieve supporting evidence.

Zero assumption version

Why retrieval fails before language generation even starts

In retrieval-augmented generation, the retrieval stage determines what external evidence the language model will ever see. If retrieval misses the right image, chart, page, or document, generation cannot invent the missing evidence safely. Text-based systems often rewrite the query before retrieval, but multimodal systems usually pass the image through unchanged.

That is risky because image defects directly change nearest-neighbor search. A rotated document can hide text lines. Blur can erase small symbols. Bad crop can remove the object of interest. Semantic ambiguity can leave several plausible interpretations. The benchmark shows that these defects do not merely lower retrieval slightly. They can collapse recall because the retriever is searching with the wrong visual signature from the start.

The paper's move in one sentence. Insert an agentic repair stage before retrieval so the system can diagnose visual defects and apply the right correction tools before asking the database for evidence.

The algorithm as a flow

What it actually does

Construct imperfect query cases

Benchmark many query defects so retrieval behavior is tested against realistic visual corruption rather than only clean images.

Let the model diagnose the defect

Ask the agent to identify whether the main issue is rotation, blur, low quality, occlusion, or semantic ambiguity because different defects need different tools.

Choose a perceptual tool and settings

Select the repair action and its setting values so the fix matches the diagnosed problem instead of applying one generic enhancement to every query.

Retrieve from the repaired query

Feed the repaired image to the retriever because retrieval quality depends on the repaired visual signature, not only on later language modeling.

Measure both retrieval and final MRAG accuracy

Score recall and end-to-end answer quality separately so the benchmark can distinguish retrieval failure from later generation failure.

What the paper changes

What the paper changes

The paper changes the query itself before retrieval. It turns visual pre-processing from a fixed image-cleaning step into a decision process that chooses which repair to apply and with what settings.

the object it moves  =  the visual query before retrieval
The hidden quantity

The hidden quantity

measured quantity  =  how much retrievable evidence is still present in the degraded image

The key hidden quantity is evidence recoverability. Two images can look equally bad to a person yet differ sharply in whether a retrieval system can recover the needed features. Mild blur may leave enough structure for repair. A destructive crop may remove the target object entirely, leaving nothing to recover.

This quantity matters because tool selection should depend on what information is still latent, meaning present but not currently usable, in the image. Sharpening can help only if the signal exists because sharpening cannot recreate details that were never captured. Rotation correction can help only if the content is still inside the frame because rotation cannot restore an object that was cropped away. The benchmark exposes that agent quality depends on recognizing these distinctions.

Why it works

Why repair-before-retrieval is the right control point

Retrieval is an information bottleneck. It chooses which external evidence the generator will ever read. Once that choice is wrong, the generator is boxed in because it can only compose over the documents it received. That is why fixing the query before retrieval is more direct than hoping the generator compensates afterward.

Agentic pre-processing works because defects are heterogeneous. A rotation error calls for geometric correction. Blur calls for restoration. Ambiguity may call for multiple repaired variants or a tool that isolates the salient object. One fixed pre-processing stack cannot match these cases well, but a diagnosis-and-action policy can.

The benchmark's oracle experiments matter because they separate capability from control. If an oracle fix restores near-clean performance, the information was recoverable and the main problem was the system's inability to choose the right tool and parameters. That tells future work where to focus: repair policy learning rather than only larger retrievers.

A simple decision objective

First in words:

One way to state the task is to choose the pre-processing action that gives the highest expected retrieval quality after repair.

Then the compact form:

a_star = argmax_a Recall(repair(q, a))

Every symbol:

qthe original imperfect visual query
aa candidate pre-processing action with its parameter settings
repair(q, a)the image produced after applying action a to query q
Recallretrieval quality, such as the chance that the correct evidence appears among the returned items
a_starthe action that maximizes retrieval recall for this query
A tiny worked example
Suppose a rotated receipt image gives recall 0.10 when used directly.
A deblurring tool raises recall only to 0.12 because blur was not the main problem.
A rotation-correction tool raises recall to 0.61 because the text lines become aligned for the retriever.
The correct action is the one that restores the retrieval signature most strongly, not the one that makes the image look generically sharper.

The benchmark evaluates many more details, but the core choice is still which repair action best restores retrieval.

What can go wrong

What can go wrong

The agent can choose the wrong tool. A model may misdiagnose blur as crop loss or ambiguity as low quality, which sends the query through a repair action that cannot restore the relevant evidence.
A correct tool can still use wrong settings. Over-rotation, over-sharpening, or aggressive cropping can distort the query further because the action class and the parameter values both matter.
Some queries are unrecoverable. If the target object is outside the frame or the image is too destroyed, no repair policy can recover the missing evidence because the information is gone.
Done right. The benchmark is most informative when it separates recoverable corruption from irreversible information loss and scores tool choice, parameter choice, retrieval, and final answering separately.
What a runnable demo should prove

What a runnable demo should prove

Build a small image-retrieval system over product photos or scanned pages. Corrupt query images with rotation, blur, low light, and bad crop. Compare direct retrieval against a controller that first predicts the defect and then chooses one of several repair tools.

Measure top-k recall before and after repair, plus final answer quality for a generator that consumes the retrieved evidence. The demo should show that end-to-end performance rises only when repair improves retrieval, because the generator can use only the evidence that retrieval actually returned.

repair_gain = Recall_after_repair - Recall_before_repair

The useful artifact is a breakdown showing which defect types are recoverable and which controller mistakes still leave a large gap to the oracle.
