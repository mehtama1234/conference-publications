Task-Aware Mechanism: Hybrid MoE Vision Tower Towards Holistic Video Understanding

Predict what kind of video question is being asked, then allocate frame count, resolution, and visual experts accordingly instead of forcing every task through one fixed visual pipeline.

Paper explainersAll themesMultimodal

Video understanding tasks differ in what evidence they need. A long-form summary question needs broad temporal coverage across many minutes. A counting question may need dense spatial detail in a short segment. A fixed vision tower forces one compromise for every task, so it either undersamples long videos, underserves fine-detail questions, or wastes computation on easy cases. Task-Aware Mechanism addresses this by separating task prediction from visual processing. A compact text-only module called the Inductor first predicts the task type from the user query. That task prediction then determines a visual budget, meaning how many frames and what resolution to process, and routes the video through a hybrid Mixture-of-Experts tower. The tower uses soft gating within the vision encoder for stability and hard gating across resolution-specific projectors and pipelines for efficiency. The result is a video-language model that spends visual compute where the question actually needs it.

Zero assumption version

Why one fixed visual pipeline fails across video tasks

Video-language models often process every input with the same frame sampling rate and the same image resolution regardless of what the question asks. That is convenient for implementation but poor for evidence matching. A question about the main storyline of a two-hour movie needs wide temporal coverage and can tolerate coarser spatial detail. A question about how many birds appear in a short clip needs much higher spatial detail over fewer frames.

A fixed pipeline creates a hard tradeoff. If the model samples many high-resolution frames for every question, the cost becomes excessive. If it samples only a few low-resolution frames, detailed counting, reading, or short critical actions are missed. The model's performance gap is therefore partly a budgeting problem rather than only a reasoning problem.

The paper's solution is to make the visual budget a function of the task. Instead of deciding the visual pipeline once for all inputs, it predicts what kind of evidence the question demands and allocates computation accordingly.

The main change. Infer the task from the query first, then route the video through an expert mixture with task-dependent frame and resolution budgets.

The algorithm as a flow

What it actually does

Read the query.

Use the text of the user question to infer whether the task needs broad temporal context, fine spatial detail, or some other evidence pattern.

Predict a task type.

Run the compact Inductor on the query to classify the task using the TA-116K supervision set.

Allocate a visual budget.

Choose frame count and resolution according to the predicted task type and the video length.

Route through hybrid experts.

Use soft gating inside the vision tower for stable expert combination and hard gating across resolution-specific paths for efficient specialization.

Answer with matched evidence.

Pass the routed visual features to the language model so reasoning happens on evidence chosen for the current task instead of on a generic fixed sample.

What the paper changes

What the paper changes

The paper changes the vision tower from a fixed preprocessing module into a task-conditioned resource allocator and expert router. It also makes the routing decision explicit and inspectable by separating task prediction from downstream reasoning.

The hidden quantity

The hidden quantity

measured quantity  =  evidence demand of the current query

The important hidden quantity is how much temporal coverage and spatial detail a question actually requires. That quantity is not written directly in the training labels. The model sees a query and must infer whether the answer depends on global narrative context, local detail, dense event coverage, or some mixture of those.

Task-Aware Mechanism makes that hidden requirement explicit by predicting a task type before visual processing begins. Once the task type is estimated, the system can treat frame count and resolution as controllable resources rather than as fixed constants. This is why the paper emphasizes inspectability: if the model fails, one can check whether it routed the question to the wrong budget before blaming the downstream language reasoning.

Why it works

Why task-aware budgeting improves video understanding

The Inductor matters because the question itself often reveals the evidence requirement. Words such as count, read, summarize, before, after, or throughout give clues about whether the model needs local precision or broad temporal context. Predicting the task from text is much cheaper than processing the full video at maximum budget and provides an early control signal, because the text module runs before any heavy frame extraction and can prevent unnecessary visual computation.

Once the task type is known, frame count and resolution become optimization variables. A summary question benefits from more temporal samples but not necessarily from maximum resolution. A fine-detail question benefits from high resolution but may require only a small temporal window. This decoupling resolves the fixed-pipeline tradeoff by matching the sampling strategy to the evidence demand.

The hybrid Mixture-of-Experts design matters because routing occurs at two levels. Soft gating inside the encoder keeps training stable by combining experts smoothly rather than forcing a brittle one-hot choice everywhere. Hard gating across resolution-specific projectors and pipelines provides computational savings because only the relevant high-cost path is activated. Together these mechanisms allow specialization without losing stability, because one part of the system blends experts smoothly while the other part limits which expensive visual branch is used.

A compact routing rule

First in words:

Use the predicted task to choose a visual budget and expert path, then compute the answer from features extracted under that budget.

Then the compact form:

b, e = g(q, T) ; y = f(video, b, e, q)

Every symbol:

qthe user query
Tthe video length or coarse video metadata used for budgeting
gthe task-aware budgeting and routing function
bthe chosen visual budget, such as frame count and resolution
ethe selected or weighted expert path
fthe downstream model that extracts features and answers the query under the chosen budget
ythe final answer
A tiny worked example
Query 1 asks for the main idea of a 90-minute movie.
The Inductor predicts a narrative-summary task, so g chooses many frames at moderate resolution and a temporal-summary expert path.
Query 2 asks how many birds are on screen in a short clip.
The Inductor predicts a fine-detail counting task, so g chooses fewer frames at higher resolution and a detail-sensitive expert path.
Both queries use the same base model, but the visual evidence budget differs because the task requirements differ.

The key point is that the routing function depends on the query before visual processing, which lets the model allocate compute deliberately instead of uniformly.

What can go wrong

What can go wrong

Wrong task prediction causes upstream failure. If the Inductor misclassifies the query, the visual budget can be mismatched before the model even sees the relevant frames.
Task categories may be too coarse. A single query can require both broad temporal context and fine local detail. If the taxonomy is too simple, routing may choose a budget that captures only part of the needed evidence.
Hard gating can suppress useful fallback paths. Efficiency gains come from selective expert use, but a strict route can miss evidence that would have been captured by another resolution path.
Done right. The method is strongest when the task taxonomy reflects real evidence demands and the routing module is trained on diverse query types that expose those differences.
What a runnable demo should prove

What a runnable demo should prove

Take a video benchmark containing both long-context questions and fine-detail questions. Compare a fixed-budget video-language model with the task-aware version. Log the predicted task type, chosen frame count, chosen resolution, and expert path for every example.

The demo should show that the task-aware system chooses different budgets for different question types and that those choices correlate with better accuracy. It should also separate failures caused by wrong routing from failures caused by downstream reasoning, because the paper's explicit routing design makes that diagnosis possible.

budget_match_rate = number_of_queries_with_correct_budget_choice / total_queries

A convincing result is higher budget_match_rate together with better benchmark accuracy and lower average compute, because that would confirm the model is allocating visual evidence in a task-sensitive way.
