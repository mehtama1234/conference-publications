AssoMem: Scalable Memory QA with Multi-Signal Associative Retrieval

Organize conversation memory around linked clues, then rank possible memories using relevance, importance, and timing together instead of semantic similarity alone.

Paper explainersAll themesAgents & Tool Use

A memory system for question answering has to find the right past moment from a very long conversation. Pure semantic search often fails when many memories sound similar. AssoMem adds structure: it attaches each utterance to extracted clues, builds an associative memory graph, and ranks memories with three signals at once so recall improves in dense conversational histories because the scorer can separate the truly answer-supporting turn from other turns that only share similar wording.

Zero assumption version

Why similar conversations confuse memory search

A personal assistant may store thousands of dialogue turns. Later, a user asks a question such as who promised to send the draft or when the budget concern first came up. Many stored turns may use similar words, so plain semantic retrieval brings back several plausible but wrong moments.

The problem is not only relevance to the question. Some past turns were central decisions, some were minor side remarks, and some happened at the right time to answer the question while others are stale. A memory search system that treats all three cases the same will often recall the wrong turn.

In one sentence. AssoMem links dialogue turns to explicit clues and then ranks memories with relevance, importance, and timing together so the system can recover the right past event from many similar ones.

What the paper changes

What the paper changes

The paper changes how memories are organized and ranked. Instead of keeping only a flat list of utterances scored by semantic match, it builds an associative graph and fuses several retrieval signals.

the object it moves  =  the memory retrieval score
The hidden quantity

The hidden quantity: answer usefulness of a memory item

measured quantity  =  how likely one stored turn is to directly support the answer

The right memory is not simply the one that sounds closest to the question. It is the one that actually helps answer it because it carries the fact, decision, or timing detail the question needs. That depends on at least three factors: does the turn discuss the topic, was the turn important in the conversation, and does its timing fit the question being asked?

AssoMem tries to estimate this hidden usefulness by building links from each utterance to extracted clues and by combining the three signals with a learned fusion rule. The graph matters because it gives the retriever more than raw text similarity to work with when many turns are phrased in similar ways.

Why it works

Why several signals beat similarity alone

Similarity alone misses conversational role. A side remark can share most of the same words as a key decision turn and still be the wrong memory. Adding importance helps because the system can prefer turns that carried decisions, commitments, or clarifications instead of low-stakes chatter.

Timing also matters because questions often ask about the latest agreement, the first mention, or the turn near another event. The fusion rule combines these signals so that one weak signal does not dominate the ranking. This works because the memory graph stores clue links that expose who, what, and when, allowing the scorer to rank candidate turns using structure instead of wording alone.

Math after the picture

One score from three signals

First in words:

memory score = weighted relevance plus weighted importance plus weighted timing alignment

Then the compact form:

Score(m) = a * Relevance(m) + b * Importance(m) + c * TimeFit(m)

Every symbol:

Score(m)final retrieval score for memory item m
Relevance(m)how directly the memory matches the question topic
Importance(m)how central that turn was in the conversation
TimeFit(m)how well the timing of the turn fits the question
a, b, cweights chosen by the fusion method
A tiny worked example
Candidate A matches the topic well: relevance 0.9, but it was a minor aside: importance 0.2, and the timing is weak: 0.3.
Candidate B matches the topic slightly less: relevance 0.8, but it was the main decision turn: importance 0.9, and the timing fits well: 0.8.
With weights a = 0.4, b = 0.3, c = 0.3, Candidate A scores 0.51 while Candidate B scores 0.83.
Candidate B wins because the extra signals show it is the turn that actually supports the answer.

The important idea is not the exact arithmetic. It is that a memory item should win only when several useful signals agree.

What can go wrong

What can go wrong

Clue extraction can miss the real anchor. If the system fails to extract a key person, date, or commitment, the graph loses the very link that would have separated the right memory from the wrong one.
Importance can be misread. A brief turn may look unimportant even when it contains the exact decision or correction the answer needs.
Timing can overwhelm older but critical facts. Recent turns are often useful, but some questions ask about an earlier origin or a long-standing promise. If timing is weighted too strongly, the ranking may push those older critical turns too low.
Done right. The retrieval score works best when the three signals can counterbalance one another, because then a turn wins for a concrete reason instead of by wording overlap alone.

What a runnable demo should prove
