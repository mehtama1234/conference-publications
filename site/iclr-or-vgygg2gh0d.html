MMSearch-Plus: Benchmarking Provenance-Aware Search for Multimodal Browsing Agents

MMSearch-Plus builds search tasks where the agent must extract fine visual evidence from an image, carry that evidence through web search, and verify the answer against source pages instead of solving with text shortcuts alone.

Paper explainersAll themesMultimodal

Many browsing benchmarks look multimodal on paper but act as text tasks in practice. The agent can often ignore the image, search a few keywords, and still guess the right answer. MMSearch-Plus is designed to block that shortcut. The questions require a visual cue from the image, such as a venue sign, a jersey detail, or a date trace embedded in the scene, and the agent must propagate that cue through iterative image-text retrieval and source checking. The paper also adds a set-of-mark module, meaning a tool that lets the agent place visual marks, crop regions, and launch targeted searches from those regions, so the agent can search from the right evidence rather than from the whole image at once.

Zero assumption version

Why existing browsing benchmarks overstate multimodal skill

If a benchmark question can be answered from generic keywords, it does not test whether the agent truly used the image. For example, an event photo might contain a specific sponsor banner or uniform pattern that distinguishes one event from another, but a weak benchmark lets the agent succeed by searching only a broad caption-style description.

Real multimodal search is harder because visual evidence is partial, noisy, and indirect. The image may not show the answer itself. It may only show a clue that must be linked to outside facts such as the event date or venue. A benchmark that does not force this chain mostly measures text retrieval quality, not grounded multimodal reasoning.

The method in one sentence. MMSearch-Plus creates tasks where the image supplies a necessary clue, retrieval contains distractors, and the agent must carry the clue through marked crops, targeted search, and source verification before it can answer.

The algorithm as a flow

What it actually does

Seed tasks from image-dependent clues

Construct benchmark questions whose resolution requires a visual detail that generic text search is unlikely to isolate on its own.

Insert retrieval noise

Make the search environment contain similar-looking or similar-worded distractors so agents cannot rely on the first plausible hit.

Provide standard browsing tools plus set-of-mark

Let agents crop subregions, place visual marks, and run targeted image or text searches from those regions.

Require cross-validation on candidate pages

Agents must connect the clue to an outside fact and then verify that fact on retrieved pages instead of stopping at a rough match.

Measure end-to-end grounded success

Score the full chain from clue extraction through retrieval and provenance-aware answer selection.

What the paper changes

What the paper changes

The paper changes the unit of evaluation from a question-answer pair to a provenance-aware search chain. Success now depends on whether the agent found and used the right visual clue, carried it through search, and verified the answer on source pages.

The hidden quantity

Evidence propagation fidelity

measured quantity  =  evidence propagation fidelity (whether the exact visual clue extracted from the image is preserved through later retrieval and verification steps)

The hard part is not only seeing a clue. It is preserving that clue while the search branches outward. An agent may notice a jersey pattern, but if it converts that into a broad text query such as team color plus sport, the distinguishing information is lost and the search collapses onto many distractors.

The set-of-mark tool improves this fidelity because it keeps the clue explicit. A cropped region or marked patch can drive a targeted query that still contains the discriminative visual evidence. Source verification then checks whether the retrieved page explains the same clue rather than merely sharing loose topic words.

Why it works

Why the benchmark is harder in the right way

MMSearch-Plus is harder because it attacks the main shortcut that inflates browsing scores: replacing grounded visual evidence with broad text cues. The benchmark uses questions where coarse text descriptions map to many candidate pages, while one small visual detail isolates the correct branch. That makes true multimodal reasoning necessary rather than optional.

The set-of-mark tool matters because it gives the agent a way to operate on visual evidence directly. Marking and cropping convert a large image into a focused query object that can be passed into search. Retrieval noise then tests whether the agent can preserve that object through later steps. If the agent loses the clue, it lands on a visually similar but wrong event or page. If it retains the clue and checks provenance, it can bridge from the image to outside facts such as dates and venues.

Math after the picture

A grounded success score

First in words:

End-to-end success depends on three linked events: extracting the right clue, retrieving the right candidate pages from that clue, and verifying the answer on those pages.

Then the compact form:

Score = Acc_clue * Acc_retrieve * Acc_verify

Every symbol:

Acc_cluefraction of tasks where the agent identifies the needed visual clue
Acc_retrievefraction of tasks where the clue leads to the correct candidate page set
Acc_verifyfraction of tasks where the agent confirms the answer on source pages before responding
A tiny worked example
Suppose an agent extracts the correct clue on 0.70 of tasks, retrieves the right candidate pages on 0.60 of those, and verifies correctly on 0.80 of the retrieved set.
The grounded score is 0.70 * 0.60 * 0.80 = 0.336.
That equals 33.6 percent end-to-end success.
The multiplication matters because failure at any earlier stage breaks the later stages even if the later modules are strong on their own.

A browsing agent can have decent text search and still score poorly if it loses the visual clue early in the chain.

What can go wrong

What can go wrong

The clue is too small or too ambiguous. If the decisive visual region is tiny or visually common across many events, even marked retrieval can still return near-duplicate distractors.
The agent marks the wrong region. The benchmark only becomes informative if the agent can isolate the relevant patch. A wrong crop sends later retrieval down the wrong branch, and verification then wastes effort on unrelated pages.
Source pages do not expose the evidence clearly. Some webpages may mention the event but not display or describe the exact clue used in the image, which makes final provenance checking harder even when retrieval found the right topic.
Done right. The tasks are most informative when the visual clue is necessary, retrieval contains realistic distractors, and the web pages provide enough source detail for a grounded verification step.
What a runnable demo should prove

What a runnable demo should prove

Build a small search benchmark from event photos where the answer is an outside fact such as date or venue. For each task, label the discriminative image region that makes the event identifiable. Run an agent with normal browsing tools and the same agent with an added mark-and-crop tool. Log the selected crop, the issued queries, the retrieved pages, and the final cited source.

The demo should show that accuracy rises when crop quality rises, because the benchmark is testing evidence propagation rather than only generic text retrieval. Good runs should be traceable from image patch to source page to answer.

provenance_success = tasks with correct crop and correct cited source and correct final answer / total tasks

The main artifact should be an audit trail for each task. It should be possible to inspect exactly which image region led to which page and why that page justified the answer.
