InvGNN: Reversible Graph Models

Graph neural networks can be made fully reversible, letting them use less memory and compute exact probabilities while staying as expressive as standard models.

Paper explainersAll themesGraph & Geometric Learning

Graph neural networks (models that reason over networks of connected items) usually combine information from neighbors using operations like averaging or taking the maximum. These operations discard information — once you average numbers, you cannot recover the originals. This paper shows how to replace these with reversible operations, so a deep graph model can run forward and backward losslessly. This unlocks three benefits: using far less memory for deep models, computing exact likelihood (certainty) scores, and generating new graphs.

Zero assumption version

The information loss problem

Graph neural networks combine information from neighbors in each layer. To predict node attributes or classify a graph, each node gathers features from its neighbors, pools them together (typically by averaging or taking the max), and passes a summary forward. This summary is fast to compute, but it is a bottleneck: once you average five numbers into one, the five originals are gone forever.

Standard pooling loses information. This causes two problems. First, a deep model must store all activations (the in-between values computed at each layer) in memory for the backward pass — a serious drain. Second, you cannot compute the exact probability that the model would have produced this specific graph or node feature, because the pooling operation erases possibilities. And if you want to generate new graphs, you have no way to reverse the learned transformations.

A naive approach might try to keep all intermediate values, but that merely adds more memory overhead. What is needed is a way to change the aggregation function itself.

The insight in one sentence. Replace non-invertible aggregation functions with reversible ones, so the entire model can be run backward without loss.

What the paper changes

What the paper changes

The paper replaces the aggregation function — the step that pools multiple neighbor values into a single summary — with a reversible version that allows exact backward computation, because the reversible design preserves enough information in the output and context that you can recover the input exactly.

The hidden quantity

Invertibility: Whether you can run it backward

measured quantity  =  invertibility

Invertibility is the property that a function can be exactly reversed. Standard functions like average (sum all numbers and divide by count) are not invertible: from the average alone, you cannot recover the individual numbers. A reversible function is designed so that knowing the output and a small extra piece of context lets you recover the input exactly.

In this paper, the reversible layer uses a coupling strategy: it splits node features into two halves, transforms one half using the other as a key, then swaps them. The output and the split structure together hold enough information to reverse every step. The paper estimates invertibility by checking whether running the layer forward and then backward recovers the input exactly.

Why it works

Why reversible aggregation fixes three problems

Reversibility solves the memory problem because when a function is reversible, you do not need to store the input to compute how to nudge the weights. Normally, to know which way to nudge the weights at each layer you must store all the in-between values from the forward pass. Instead, with a reversible layer, you recompute the input from the output on the fly when you need it. This shrinks memory from growing with depth to staying constant.

Reversibility enables exact likelihood computation because invertible layers have a computable determinant — a number that tells you exactly how much the function stretches or shrinks the probability space. The full model's likelihood (the probability it assigns to the observed graph) is the product of all layer determinants times the likelihood of the final features. With non-invertible layers, this determinant is undefined.

Reversibility enables generation because you can pick random features from a known pattern of common values and run the model backward through all layers to produce a new graph. Non-invertible pooling has no backward path.

Math after the picture

The reversible aggregation equation

First in words:

Split the node features into two parts. Transform the first part using a network controlled by the second part. Then swap and repeat. The final output is a transformed version of both parts, but crucially, the swaps and the context preserve enough information that you can invert all steps.

Then the compact form:

y1 = x1 + f(x2); y2 = x2 + g(y1)

Every symbol:

x1first half of the node features
x2second half of the node features
f(x2)learned function applied to the second half
g(y1)learned function applied to the transformed first half
y1transformed first half
y2transformed second half
A tiny worked example
Input node features: x1 = 3.0, x2 = 5.0
f(x2) = f(5.0) = 2.0 (from trained network)
y1 = 3.0 + 2.0 = 5.0
g(y1) = g(5.0) = 1.5 (from trained network)
y2 = 5.0 + 1.5 = 6.5
Output: y1 = 5.0, y2 = 6.5
To reverse: recover x2 from g(y1)=1.5, so x2 = y2 - 1.5 = 5.0. Then recover x1 from f(x2)=2.0, so x1 = y1 - 2.0 = 3.0. ✓

The swaps and learned functions preserve enough structure that running the steps backward in reverse order exactly recovers the input.

What can go wrong

What can go wrong

Shallow architectures do not benefit much. If the model is only a few layers deep, the memory savings of invertibility are negligible. Reversibility's main advantage is for very deep models.
Likelihood computation assumes the learned functions are truly invertible. If numerical errors accumulate or if the learned functions develop singular regions, the backward pass may fail. Careful design of the learned functions prevents this.
Generation requires a starting pattern to sample from. To generate a new graph, you need to pick a starting pattern (a mathematical description of common values, such as a bell curve) to sample random features from. Poor choice of starting pattern produces poor generated graphs.
Done right. The model maintains expressiveness (matching standard GNN power), gains memory efficiency for deep models, and opens new tasks like density estimation and generation.
What a runnable demo should prove

What a runnable demo should prove

Build a graph classification task (e.g., predicting whether a molecule is active). Train an InvGNN and a standard GNN, each with the same depth. Measure three things: peak memory during training, the log-likelihood assigned to a held-out validation graph, and the quality of generated graphs (e.g., how many stay connected and obey edge constraints).

memory_saved = memory_standard - memory_invgnn; likelihood_gain = log_prob_invgnn - log_prob_standard; generation_validity = fraction_of_generated_graphs_that_obey_constraints

The demo must show that InvGNN uses substantially less memory for deep models while maintaining or improving likelihood scores, and that generated graphs are structurally valid.
