ProofFlow: A Dependency Graph Approach to Faithful Proof Autoformalization

Turn a written proof into checked code by first mapping which proof steps depend on which others, then formalizing each step as its own small claim.

Paper explainersAll themesAgents & Tool Use

Autoformalization asks a system to convert a human proof into code that a theorem checker can verify. A plain one-shot translation often produces code that passes some local checks while scrambling the original argument. ProofFlow starts from the observation that a proof is not just a bag of sentences. Each step depends on earlier facts, and later steps reuse those facts in a specific order. The paper writes down that order as a dependency graph, then turns each proof step into an intermediate lemma. This matters because the final checked code stays closer to the human reasoning when every small claim must be stated and proved in the same dependency order as the source proof.

Zero assumption version

Why one-shot proof translation loses the argument

A theorem checker cares about exact formal steps. A human proof usually leaves many tiny steps unstated because a reader can fill them in. When a model translates the whole proof at once, it may jump straight to code that compiles while quietly changing the structure of the original reasoning.

There is also a coordination problem. One sentence in the proof may justify three later steps, while another sentence depends on a hidden subclaim that appears only implicitly. If the translator does not keep track of those links, it can attach a later conclusion to the wrong support. The result is code that may look plausible but no longer matches the written proof.

The paper's move in one sentence. First recover the dependency structure of the proof, then formalize each human step as a separate lemma so the final script follows the same support chain.

The algorithm as a flow

What it actually does

Read the written solution.

Split the proof into named steps so the system can talk about each claim separately.

Recover the support links.

Build a directed acyclic graph whose edges say which earlier steps justify each later step, because that graph preserves the proof's logical order.

Write one formal lemma per step.

Translate each human step into a small intermediate formal claim, so the script mirrors the original structure instead of collapsing many ideas into one jump.

Prove lemmas in dependency order.

Formalize parent steps before child steps, because later lemmas can then call the earlier checked results directly.

Finish the theorem.

Combine the proved lemmas into the final statement, so the full script is machine-checkable and still faithful to the source proof.

What the paper changes

What the paper changes

The paper changes the unit of translation. Instead of asking for one monolithic proof script, it asks for a dependency graph plus a chain of intermediate lemmas that respect that graph.

the object it moves  =  proof structure during translation
The hidden quantity

The hidden quantity: structural faithfulness

measured quantity  =  Whether the formal script keeps the same support pattern as the written proof

A translated proof can be syntactically valid and still be a poor explanation of the original reasoning. The hidden quantity is structural faithfulness: does the formal script use the same support pattern that the human author used?

ProofFlow makes this quantity visible by extracting dependencies between proof steps and then scoring whether the formal lemmas preserve those dependencies. This helps because a faithful script should not only reach the right theorem, but should reach it through the same chain of ideas.

Why it works

Why the graph-plus-lemma pipeline works

The method works because it turns a large brittle translation problem into many small support-preserving subproblems. Once the proof is broken into steps and linked by dependencies, each formal lemma has a narrow job: state one claim and prove it from the exact earlier claims that the human proof used.

This also makes errors easier to localize. If one lemma fails, the system can inspect the corresponding human step and its parents instead of reworking the full theorem. Performance rises because the model no longer has to remember the whole argument at once, and faithfulness rises because the dependency graph constrains which earlier facts each later step may use.

The scoring idea

First in words:

Rate a formalized proof by combining machine-check success, step meaning, and structure preservation, so that a script that compiles but breaks the support chain does not receive full credit.

Then the compact form:

ProofScore = syntax_score + semantic_score + structure_score

Every symbol:

syntax_scorecredit for producing formal code that the theorem checker accepts
semantic_scorecredit for matching the meaning of each human proof step
structure_scorecredit for preserving the dependency links between steps
ProofScorethe combined score used to judge overall proof quality
A tiny worked example
Suppose a proof has three steps: prove A, use A to prove B, then use B to prove the theorem.
A one-shot system writes checked code for the theorem, but it proves B from a different helper fact and skips A.
Then syntax_score is high because the code checks, but structure_score is low because the A -> B link was lost.
ProofFlow writes a lemma for A, a lemma for B that calls A, and a final theorem that calls B.
That script receives high syntax, meaning, and structure credit because the support chain stayed intact.

The extra structure term matters because pure compile success cannot tell whether the model preserved the original reasoning.

What can go wrong

What can go wrong

The dependency graph can be wrong. If the system attaches a step to the wrong parent, the later formal lemmas inherit that mistake because the proof order is reconstructed from the graph.
Human proofs may skip too many details. A student solution may rely on background facts without naming them. Then the system must insert missing helper lemmas carefully, because hidden steps can make the graph incomplete.
Local lemmas can become too literal. If each lemma copies a sentence without enough formal detail, the checker still fails because the step has not been unpacked into precise conditions and conclusions.
Done right. When the graph is accurate and each lemma states one real support step, the final proof is easier to verify and easier to compare with the human argument because every dependency stays visible.
What a runnable demo should prove

What a runnable demo should prove

Take a small set of undergraduate theorem proofs with manually marked step dependencies. Compare two systems: a direct proof-to-code translator and a ProofFlow-style translator. For each theorem, check whether the formal script compiles, whether each human step can be matched to a formal lemma, and whether the parent-child support links are preserved. The demo should show higher combined quality for the ProofFlow-style system because its graph forces the translator to keep the proof structure while formalizing one step at a time.
