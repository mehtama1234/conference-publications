VITA: Vision-to-Action Flow Matching Policy

Skip the expensive repeated visual conditioning steps and flow directly from visual patterns to action codes instead.

Paper explainersAll themesRobotics & Control

Robotic policies using diffusion today require rewiring the visual input into the action-generation process at every single step of the iterative denoising. This repeated wiring consumes time and memory. VITA eliminates that overhead by flowing directly from the visual representation space into an action code space, with no conditioning modules along the way.

Zero assumption version

Why conditioning at every step is slow

Today's robot policies use diffusion: the model starts with a random action and iteratively refines it by asking for gradual corrections. To make those corrections accurate, the model must re-read the camera images at every refinement step. Re-reading and re-processing the images that many times burns computation and memory.

A beginner might naively try to extract the visual features once and reuse them. But the diffusion network expects the visual input at the same dimensional scale as the action at each step, and those dimensions don't match.

The method. Build a separate action code space that aligns with the visual feature space in size. Flow directly from visual features into these action codes without re-reading the images, and decode the final codes into real actions.

The algorithm as a flow

What it actually does

Step 1: Vision once

Camera feed goes through vision encoder exactly one time. Produces a list of numbers.

Step 2: Actions to codes

Train an action autoencoder to map real actions into a matching-size code space.

Step 3: Flow matching learns the path

Flow model learns how to transform the visual codes into action codes gradually.

Step 4: Fill the training-test gap

At training time the decoder sees encoder codes; at test time it sees ODE-solved codes. Flow code decoding makes those two match by sending the reconstruction loss back through the ODE solving steps.

Step 5: Decode and execute

Final action codes are decoded back into robot commands and run.

What the paper changes

The single thing that changes

VITA replaces all the repeated visual conditioning modules with a single aligned action code space. The model still flows iteratively from vision to action, but it does so in a code space (a structured representation) where both the source and target have the same dimensionality, so no per-step adaptation is needed.

The hidden quantity

The alignment gap: mismatched dimensions

measured quantity  =  The dimension mismatch between vision and action

Flow matching requires the source space and the target space to be the same size (in terms of numbers per item). A camera image extracts to a high-dimensional visual feature vector. A robot action is a low-dimensional command (a few numbers for joint angles or gripper position). They don't fit together.

VITA solves this by training an action autoencoder that represents raw actions in a structured code space the same size as the visual features. The paper calls this trained alignment the key to removing the conditioning bottleneck.

Why it works

Why removing conditioning works

Conventional diffusion policies add visual information to the action at every step via modules that learn weighted combinations of visual features. These modules compute a transformation based on the current visual features and the current action-in-progress, then apply it. Repeating this at every step of refinement is expensive.

VITA's key insight: if you can represent actions in a code space the same size as the visual feature space, the flow model can learn to transform one directly into the other without intermediate adaptation. The vision encoder runs once, producing a fixed list of numbers. The flow model, during its iterative refinement, operates purely between these two aligned spaces.

The training-test mismatch arises because during training the decoder sees action codes produced by the action encoder (which has seen the ground truth), while at test time it sees codes produced by solving the flow ODE (which must guess). Flow code decoding bridges this by sending the reconstruction loss back through the ODE solving steps during training. This anchors the flow to produce codes that decode correctly.

The training objective

First in words:

Total loss equals: flow matching loss (guides the transformation path) plus flow latent decoding loss (ensures the ODE-generated codes decode correctly) plus autoencoder loss (keeps the code space structured).

Then the compact form:

L_VITA = lambda_FM * L_FM + lambda_FLD * L_FLD + lambda_AE * L_AE

Every symbol:

L_FMflow matching loss: mean squared error between predicted and true velocity field
L_FLDflow latent decoding loss: reconstruction error when decoding ODE-generated codes
L_AEautoencoder loss: reconstruction error when decoding encoder-trained codes
lambda_FM, lambda_FLD, lambda_AEweights controlling how much each loss contributes to training
A tiny worked example
Suppose lambda_FM = 1.0, lambda_FLD = 1.0, lambda_AE = 0.5.
In one step: L_FM = 0.1 (flow is learning well), L_FLD = 0.2 (codes don't decode perfectly yet), L_AE = 0.4 (autoencoder is learning).
Total: L_VITA = 1.0 * 0.1 + 1.0 * 0.2 + 0.5 * 0.4 = 0.1 + 0.2 + 0.2 = 0.5.
The flow matching is weighted equally, so it gets the same priority as the code quality (FLD). The autoencoder is half-weighted because its role is structural, not primary.

The three losses keep the flow path, the decoding path, and the code space all aligned during training.

What can go wrong

What can go wrong

Action code space collapse. If you naively combine the flow matching loss and autoencoder loss without anchoring them to the actual actions, the codes can all cluster into a small region. The model stops learning to represent different actions differently.
Training-test mismatch. The decoder is trained on codes from the action encoder (which has seen the true action), but at test time receives codes from the ODE solver (which must guess). If the two types of codes are very different, the decoder will fail at test time.
Dimension mismatch still matters if ignored. If the action code space is smaller than the visual space, or if the sizes are not carefully maintained, the flow model must learn expensive scaling at each step, defeating the whole point.
Done right: anchored joint training. Flow code decoding solves the training-test gap by running the ODE and sending the reconstruction loss back through it during training. The action codes produced by the ODE are forced to decode correctly, and the flow model learns paths that the decoder can handle.
What a runnable demo should prove

What a runnable demo should prove

Build a small robot manipulation task: pick up an object from one location and place it in another. Record a dataset of a few hundred demonstrations with camera frames and action sequences. Train an action autoencoder to encode these actions into a code space matching your visual feature dimension. Train the flow model to map from visual codes to action codes. At test time, run the policy on new camera observations: extract visual codes once, solve the ODE to generate action codes, decode to actions, and execute.

Speedup = Time_baseline_per_step * num_steps / Time_VITA_total; Success_rate = (tasks_completed / tasks_attempted) * 100

The demo must clearly show that extracting vision once and skipping all per-step conditioning produces both faster test-time speed (because you eliminate repeated expensive visual processing and transformation at every ODE step) and comparable or better task success.
