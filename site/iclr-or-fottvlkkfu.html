G-Merging: Graph Model Merging for Multi-Task Knowledge Consolidation

When you train separate graph models on separate tasks, G-Merging combines them into one efficient model by routing each input graph to the right task specialist based on its structure.

Paper explainersAll themesGraph & Geometric Learning

Machine learning teams often train separate models, each specialized for one task. But keeping many models is wasteful — they use lots of memory and computing power. G-Merging solves this by merging multiple graph models (trained on different graph tasks) into one efficient model that still performs as well as separate models. The trick: instead of treating all graphs the same, it routes each graph to the right specialist based its structure.

Zero assumption version

Why merging regular models fails on graphs

Suppose you have two different graph tasks: predicting disease spread on social networks, and predicting fraud on transaction networks. You train one graph model on disease, another on fraud. Each works perfectly for its task, but now you're storing two entire models in memory.

A beginner tries the obvious fix: just average the two models' weights together. This sometimes works for regular images and text, but fails badly on graphs. Why? Graphs have a hidden structure — the shape of connections matters as much as the numbers. When you average weights blindly, you smash together models that expect completely different graph shapes, and you lose the specialized knowledge each one learned.

The paper calls this the unique structural heterogeneity problem: different graph tasks have fundamentally different patterns of how things connect. Averaging weights ignores that.

In one sentence. G-Merging merges multiple specialized graph models into one by routing each input graph to the expert that matches its structure best.

The algorithm as a flow

What it actually does

Step 1: Coarse merge

Average weights of fine-tuned models to capture shared knowledge.

Step 2: Measure graph similarity

For each task, calculate how graph structure differs (using Wasserstein distance on the learned patterns inside the model).

Step 3: Learn small adapters

Train lightweight fix-up layers (adapters) to restore task-specific patterns.

Step 4: Build structure-aware router

Create a router that scores how well each input graph matches each task's structure.

Step 5: Route when answering

When a new graph arrives, send it to whichever adapter fits its structure best.

What the paper changes

What the paper changes

G-Merging changes which specialized model (which adapter) handles each graph. Instead of using one merged model for everything, it dynamically picks the right specialist based on the graph's shape.

the object it moves  =  the routing decision
The hidden quantity

Structural similarity: which adapter fits this graph?

measured quantity  =  structural similarity score

G-Merging measures how similar an input graph is to the graph structure each model was trained on. This is a single score for each graph-to-task pair, showing how well that task's specialist fits this particular input.

The paper estimates this using Wasserstein distance: a way to measure how different two distributions are. It compares the learned embeddings (the internal patterns the merged model found) to the embeddings from the original task-specific model. A small distance means the graph structure matches; a large distance means it does not.

Paper reading. Topology-aware Wasserstein Distance (TWD) measures divergence between the embeddings of the merged model and the original task-specific fine-tuned model on the given input. Lower TWD indicates structural alignment.
Why it works

Why routing by structure fixes the merging problem

The core problem: when you average two models trained on different graph structures, the average model is confused — it does not know if it should expect dense clusters or chain-like patterns, local communities or global structure. So it performs poorly on both.

G-Merging fixes this by doing three things. First, it merges the models coarsely (averaging weights) to capture shared knowledge, so the merged model learns common graph patterns. Second, it trains tiny adapters for each task: these are small neural networks that take the merged model's output and adjust it to restore the task-specific patterns the original model learned. The adapters are trained using Wasserstein distance, which measures graph-embedding similarity directly — so each adapter learns exactly which adjustments fix the structure for its task.

Third, instead of running all inputs through the merged model plus all adapters, it builds a router that looks at the input graph's structure and chooses just one adapter to apply. This routing happens fast (no training needed) because it is based on whether the input structure matches each adapter's specialty. A dense graph goes to the dense-specialist adapter; a sparse graph goes to the sparse-specialist. Because the right adapter is always chosen, the merged model performs almost as well as separate models but uses far less memory.

How the router chooses an adapter

First in words:

For each input graph and each task adapter, compute how similar the graph is to that task (using embeddings). The router picks the adapter with the highest similarity score.

Then the compact form:

adapter_chosen = argmax_t ( similarity_t(graph, merged_model) )

Every symbol:

adapter_chosenwhich task adapter to use (1, 2, or 3, etc.)
similarity_tthe Wasserstein distance score between merged embeddings and task t embeddings
graphthe input graph structure
argmaxpick the adapter with the highest score
A tiny worked example
Input graph has 100 nodes, 80 edges (sparse, like a disease network).
Task 1 (disease) similarity score: 0.92 (very similar).
Task 2 (fraud) similarity score: 0.41 (quite different).
Task 3 (credit) similarity score: 0.38 (quite different).
Router picks Task 1 adapter (highest score 0.92), applies its adjustments, prediction is made.

The router is like a bouncer at a door: it looks at the graph and says which task specialist trained on this type of structure — then lets only that specialist's adapter do its work.

What can go wrong

What can go wrong

Two tasks with identical structure. If two tasks both work on dense social networks with the same clustering pattern, the router may route the same graph to both adapters equally. The method assumes task structures differ in real ways; it struggles when they overlap.
Graph structure changes over time. If a real social network becomes sparser over time (people disconnect), the router's similarity scores were learned on old structure patterns. It may route wrong, sending sparse graphs to a dense-trained adapter.
The Wasserstein distance metric is expensive. Computing Wasserstein distance requires comparing learned patterns in detail. For very large graphs or many tasks, this routing step slows down the time to answer.
Done right. G-Merging works well when task structures genuinely differ, when you have labeled data to measure structural similarity, and when the adapter overhead is smaller than the savings from sharing one merged model.
What a runnable demo should prove

What a runnable demo should prove

Build a toy dataset: three small graph classification tasks (e.g., sparse social graph, dense citation graph, chain-structured transaction graph). Train one model on each. Merge them using G-Merging (average weights, add adapters, build the structure-aware router). Then test: for each task's test graphs, measure how often the router sends it to the correct adapter. Measure accuracy on each task. Measure total model size.

routing_accuracy = (graphs sent to correct adapter) / (total test graphs); task_accuracy = correct_predictions / total_predictions; model_size_ratio = merged_size / (3 * individual_size)

The demo should make impossible to miss: routing scores align with task structure (sparse graphs hit the sparse adapter), and the merged model matches single-task accuracy while using one-third the memory.
