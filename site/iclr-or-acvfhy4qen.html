PhyScensis: Physics-Augmented LLM Agents for Complex Physical Scene Arrangement

An LLM agent guided by a physics engine iteratively builds realistic physical scenes by proposing objects and letting gravity settle them naturally.

Paper explainersAll themesRobotics & Control

Robots learn to manipulate by practicing on simulated scenes. But building a scene with many objects stacked and balanced is hard: you need to know which objects touch, which ones support which, and how heavy things settle under gravity. PhyScensis solves this by pairing an LLM agent (which understands text descriptions and makes semantic choices) with a physics simulator (which enforces real gravity, contact, and balance). The agent proposes objects, the simulator places them with realistic physics, and the agent refines based on feedback.

Why scenes with stacks of objects are hard to create

Building a 3D scene for robot training by hand is tedious. You could write rules (shelf: 4 tall boxes here, books on top) but you miss edge cases. You could generate scenes with an image diffusion model (guess a 2D picture, make it 3D) but that often violates physics — objects float, stacks topple, books overlap.

A beginner might try: draw a scene, ask an image model to fill it, hope it respects gravity. But image models have never been inside a physics simulator. They do not know that a small book cannot hold a brick, or that a pencil topples if balanced on its point. No feedback tells them they broke the physics.

The core problem. Scene generation methods ignore physics constraints like gravity, contact, support, and balance — they produce visually plausible but physically impossible arrangements.

What the paper changes

The one thing the paper changes

Instead of an image model guessing a 2D picture and hoping it is 3D-real, the method puts an LLM agent in the loop with a physics simulator. The agent proposes where objects go in natural language; the simulator physically realizes each proposal and reports back. This closes the gap: the agent learns what actually settles and stays upright.

The hidden quantity

The hidden quantity: physical stability

measured quantity  =  stability score (drift after settling)

After an object is placed and gravity finishes acting, we measure how much the object moved. A wooden block placed flat on a table barely drifts; a pencil balanced on its point drifts a lot before tipping. The stability score is the average displacement — the smaller the number, the more stable the arrangement.

The paper uses this score to (1) check if the proposed arrangement is realistic, and (2) feed it back to the agent as a signal: if the score is low, the object stays; if high, the agent learns that this placement breaks physics and tries elsewhere.

Why it works

Why it works: agent and physics as partners

An LLM agent is good at understanding text and making semantic sense of what objects should be in a scene. But it has never felt gravity — it does not know that a water bottle standing upright is stable and a wine glass on its side might roll off. A physics simulator knows all of that instantly: drop the glass sideways and it rolls.

By pairing them, each fills the other's gap. The agent proposes sensible object choices and rough placement ideas. The physics simulator then refines the pose: it pushes the object down until it contacts a surface or other object and settles. If the object is now stable (low drift), the agent records that success. If it tips or slides (high drift), the agent learns to try a different position or object next time.

This partnership is much faster than training a single end-to-end model, because the simulator enforces physics instantly instead of the agent learning it through millions of failed attempts. The agent only needs to learn semantic choices (what to place where), not the physics of how things settle.

The stability measurement

First in words:

average_drift = mean(distance_moved_by_each_vertex_after_settling)

Then the compact form:

stability_score = (1 / N) * sum_i ||vertex_i_final - vertex_i_initial||

Every symbol:

Nnumber of vertices (corners) on the object mesh
vertex_i_initial3D position before physics simulation
vertex_i_final3D position after gravity and contact settle
||...||length of the displacement vector (distance in 3D space)
A tiny worked example
Object: a coffee mug placed on a table. Mesh has 8 corners.
Initial position: corners at z=0.5 (height above table).
After 100 physics steps: all corners at z=0.52, moved vertically 0.02 units.
Drift for 8 corners: 0.02, 0.02, 0.02, 0.02, 0.02, 0.02, 0.02, 0.02.
Average drift = (0.02 * 8) / 8 = 0.02. Very stable.
Contrast: a pencil balanced on its point. After settling: corners scatter from z=0.0 to z=0.5 (it tips sideways).
Drift = 0.5, 0.4, 0.3, 0.1, ... Average drift = 0.35. Unstable.

Lower stability score means the object barely moved under gravity, so the placement is realistic. The agent aims for low scores.

What can go wrong

What can go wrong

Bad asset retrieval ruins everything. If the agent asks for a 'red mug' and the retrieval system returns a 'red brick', the physics is fine but the semantic choice is wrong. The paper uses GPT-4o to generate descriptions and CLIP to match them to 3D models; CLIP can still fail on rare objects.
Stacking fails when physics estimates are coarse. The paper estimates object mass and friction from appearance. A hollow plastic duck and a solid marble look similar in renderings but settle very differently. Mismatched physical properties cause unstable predictions.
Agent gets stuck in local optima. If the first few proposals fail, the agent may keep trying similar placements. The paper includes a 'free placement' heuristic that randomly places an object into any empty space; this escapes the trap because the random choice breaks the agent out of its repeated failed attempts, allowing it to explore new configurations. But this only works if empty space exists; in a tightly packed shelf, no empty space remains, so the heuristic has nowhere to try and the agent stays stuck.
Done right: physics + feedback. When the agent respects the stability feedback and the physics properties are accurate, scenes converge to physically plausible configurations that would take a human designer much longer to hand-build.
What a runnable demo should prove

What a runnable demo should prove

Build a simple scene generator that takes a text prompt (e.g., 'arrange a shelf with books and a plant') and iteratively places objects. Use a lightweight physics engine (like Bullet or PyBullet) to simulate gravity and contact. Measure stability drift for each placement.

final_scene_stability_avg = mean(stability_score_of_all_objects) (lower is better)

The demo must show that iteratively placing objects with physics feedback produces denser scenes with lower total drift than placing all objects at once and then hoping they settle.
