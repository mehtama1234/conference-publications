PhyScensis: Physics-Augmented LLM Agents for Complex Physical Scene Arrangement

An LLM agent working with a physics engine builds complex, physically realistic 3D scenes by iteratively proposing assets and refining them based on physics feedback.

Paper explainersAll themesRobotics & Control

Robots need to learn by practicing in virtual worlds, which means simulators must generate realistic 3D environments. But making a pile of books on a shelf is harder than just placing objects — books must actually balance, support each other, stay in contact, and form a stable arrangement. Most layout generators ignore these physical constraints. PhyScensis solves this by having an AI agent (powered by a language model) propose objects one by one, then a physics engine checks if they work, and the agent refines its choices based on what the physics simulation says is stable.

Zero assumption version

Why scene generation breaks under physical constraints

A naive 3D layout generator places objects by position and rotation alone: it might read an instruction like 'arrange books on a shelf' and emit coordinates for each book. But this ignores a key reality: books must be supported, must not float, must not pass through each other, and must stay in contact. In a dense scene like a packed shelf, many objects rely on each other — one book leans against two neighbors; a pillow rests on four books underneath. If the generator does not check these contact and support relationships, it produces physically impossible scenes that collapse the moment the simulator runs.

A beginner might try to fix this by adding hard constraints ('no object can be below ground, no overlaps allowed'), then solving using a placement algorithm. But coordinate placement alone is not physics. An object can be placed clear of the ground yet still be unbalanced — leaning too far to one side — and will tip over the instant the simulator applies gravity. Balance, friction, and contact forces are invisible when you only assign positions; a physics simulation is the only honest way to test them.

In one sentence. PhyScensis uses an LLM agent in a feedback loop with a physics engine: the agent proposes scene configurations, the engine simulates them, and the agent refines based on which arrangements remain stable.

What the paper changes

What the paper changes

Instead of a pure coordinate solver, PhyScensis puts an LLM agent in a loop with a physics engine. The agent is not just placing shapes; it is negotiating with the simulator. The agent proposes, the engine tests, the agent learns. This shift means the agent can model contact, balance, and friction explicitly because it has a ground-truth oracle (the physics simulation) telling it immediately if an arrangement is stable.

the object it moves  =  the agent's role
The hidden quantity

The hidden quantity: Scene stability index

measured quantity  =  stability index

Stability is not a single number the simulation outputs directly. Instead, the paper uses a score that measures how close a scene is to collapse: the minimum margin of safety across all objects. For each object, compute how far it would have to move (or rotate) before it tips, contacts break, or penetration occurs — then take the smallest such margin as the scene's stability score. High score means every object has room to move; low score means at least one object is precarious.

The paper estimates this score after each iteration by running the physics engine and checking the contact forces between objects. The agent uses this feedback to understand which placements are stable (high margin) versus precarious (low margin), and steers toward stable arrangements through its next proposals.

Why it works

Why the LLM-physics loop works

An LLM by itself is good at language but has no way to check if a proposed scene is physically real. A physics engine by itself is good at simulation but has no idea how to interpret a task like 'arrange these books nicely.' PhyScensis pairs them: the LLM speaks the task language and makes creative proposals; the engine speaks the language of forces and contacts and judges each proposal. The LLM learns because it gets honest, immediate feedback — 'that book tipped' — not vague penalties.

The feedback is more than a binary pass/fail. The engine computes the stability index (how much margin each object has) and returns this to the LLM. The LLM reasons over this feedback: 'if the leftmost book has a stability margin of 0.1, I should move it right to increase its support'; or 'if the top shelf is at maximum density but the stability is only 0.5, I need to space things out.' Over iterations, the agent converges on arrangements that are both task-aligned and physically stable.

A key insight is that the LLM's language understanding lets it generalize. Once it learns that contact forces depend on how the weight is spread across the base, it can apply this lesson to new objects and new shelf heights. A pure physics solver would need to re-solve the entire optimization problem from scratch each time; the LLM brings priors and can reason backwards from goals ('I want high density but high stability — these trade off; I will prioritize stability').

Math after the picture

The stability penalty equation

First in words:

total penalty equals the weighted sum of stability deficits across all objects, where each object's deficit is how far its stability margin falls short of the target threshold

Then the compact form:

penalty = sum_j w_j * max(0, target_stability - margin_j)

Every symbol:

penaltythe total cost of an unstable scene
sum_jsum over all objects j in the scene
w_jthe weight (importance) of object j; heavier objects get higher weight
target_stabilitythe minimum safe margin the designer sets (e.g., 0.5 meters)
margin_jthe distance object j can move before it loses contact or tips
max(0, ...)if margin exceeds target, penalty is zero; otherwise, penalty is the gap
A tiny worked example
Suppose target stability is 0.5 (units: meters of clearance).
Object 1 (a book, weight 1.0): actual margin 0.3 -> deficit max(0, 0.5 - 0.3) = 0.2 -> penalty 1.0 * 0.2 = 0.2
Object 2 (a plate, weight 2.0): actual margin 0.8 -> deficit max(0, 0.5 - 0.8) = 0 -> penalty 2.0 * 0 = 0
Total scene penalty: 0.2 + 0 = 0.2. A lower penalty means a more stable scene.
If the agent moves object 1 rightward, its margin increases to 0.6 -> deficit = 0 -> penalty drops to 0.2, improving the scene.

The LLM agent uses this equation to measure how bad an arrangement is; it learns to propose moves that shrink the penalty, converging toward high-stability scenes.

What can go wrong

What can go wrong

The agent gets stuck in a local minimum. If the first few object placements are poor, the agent may propose small tweaks that never escape a locally bad configuration (e.g., all books leaning the same way). The feedback tells the agent each change is still unstable, but the agent does not explore far enough. Fix: increase the LLM's temperature (which increases randomness in proposals, allowing the agent to try radical repositionings it would not have proposed by default) or give the agent permission to backtrack and restart a section of the scene, because a fresh start breaks the local trap.
Physics simulation is slow, so iteration is expensive. A full physics simulation can take seconds per scene. If the agent proposes one object at a time and simulates after each one, the total time balloons. Fix: batch proposals (the agent suggests multiple objects, run one simulation) or use a learned approximation of the physics (a 'fast oracle' neural network) for early feedback, then use the real simulator for final scenes.
The agent hallucinates unrealistic objects or placements. Language models sometimes propose nonsensical configurations (a book at 45 degrees without visible support, or impossible object identities like 'crystalline shelf'). The physics engine will reject these, but the feedback may not be clear enough for the agent to learn what went wrong. Fix: add hard constraints to the LLM prompt (e.g., 'object rotations must be in the range [0, 90] degrees'; 'object types must come from this list').
Done right: the LLM learns the physics implicitly. When the agent receives clear, numeric feedback (margin values, contact forces), it learns correlations: higher density requires lower margin, heavier objects need more support, edge objects are riskier. Over time, the agent's proposals naturally respect these trade-offs, and convergence accelerates.
What a runnable demo should prove

What a runnable demo should prove

A demo should show a small shelf (1 meter wide, 0.5 meters tall), start with an empty goal ('arrange objects to 80 percent density'), and run PhyScensis. At each step, display the current scene (3D viewport or overhead sketch), the LLM's textual proposal ('place green book at x=0.2, y=0.3'), the stability index (a number from 0 to 1), and the loop counter. After 20-30 iterations, the scene should reach 80 percent density with a stability index above 0.6 (meaning every object has at least 0.6 units of safe margin). The key proof is that final scene does not collapse when the simulator runs forward in time without the agent controlling it; every book stays upright, no objects interpenetrate, and contacts persist.

convergence_speed = iterations_until_stable / (scene_complexity * target_density)

The demo must make it clear that the LLM is reasoning about physics, not just guessing. When the agent proposes a new placement and the margin improves, the improvement should be visible and reproducible because the feedback number (margin value) is deterministic — the same placement always yields the same margin — so the viewer can see the agent learning a repeatable cause-and-effect: 'move the book right, margin goes up.' That tight loop between proposal and feedback, embedded in plain language, is the heart of the innovation.
