When to Ensemble: Identifying Token-Level Points for Stable and Fast LLM Ensembling

Combine language models only at carefully chosen output positions, because averaging at every step can destabilize long answers and wastes compute.

Paper explainersAll themesOther

Model ensembling for text generation usually means averaging the next-step choices of several language models and then continuing with the shared choice. That can work for short answers, but long answers expose a failure mode. Two models may break the same text into different pieces, or they may strongly agree at some positions and sharply disagree at others. If you average blindly at every position, the combined choice can become less certain than either model alone, and one early weak choice can steer the rest of the answer off course. This paper asks a narrower question than most ensemble work: not just how to combine models, but when to combine them. SAFE answers by selecting only a small set of positions where the models are aligned enough to make averaging useful, then sharpening the combined next-step table when averaging makes it too flat.

Zero assumption version

Why averaging every next step can hurt long generation

A language model generates one token (one text piece) at a time. At each step the model produces a probability table, meaning a list of chances for every possible next token.

Averaging those tables across models sounds safe, but two problems appear in long-form generation. First, different models may split text into tokens differently, so the steps are not always aligned. Second, even when the steps line up, averaging can flatten the top choices when the models disagree, which produces weak next-token decisions that change the rest of the answer.

The paper's move. Ensemble only at positions where token boundaries are compatible and the models show enough agreement, because averaging at those positions is less likely to blur different text pieces into one weak choice. Then sharpen the combined next-step table if averaging makes it too flat, because a flatter table leaves the decoder with nearly tied options instead of one decisive next token.

The algorithm as a flow

What it actually does

Generate candidate next-step tables from each model.

At every text position, ask each model for its chances over the next token because the ensemble decision must start from those local preferences.

Check token-boundary compatibility.

Find positions where the models are speaking at comparable boundaries, because averaging misaligned token steps mixes choices that refer to different text pieces.

Check agreement strength.

Measure whether the models already lean toward similar next tokens, because averaging helps most when the models disagree only mildly.

Ensemble only selected positions.

Average the next-step tables at those safe positions, because doing it everywhere would often flatten the choice too much.

Sharpen if needed and continue generation.

Pull the merged table back toward a clear top option when it is too flat, because the rest of the answer depends on a decisive next token.

What the paper changes

What the paper changes

The paper changes the unit of ensembling from 'every generation step' to 'only selected generation steps.' The selection depends on boundary alignment and local agreement, and the merged table is corrected when averaging removes too much confidence.

The hidden quantity

The hidden quantity

measured quantity  =  whether an ensemble position is safe

The central hidden quantity is not the final answer quality by itself. It is a local decision: at this generation step, will merging model choices create a stable next token or a muddled one? SAFE estimates that quantity using two signals: whether token boundaries line up across models and whether the next-step tables already point in similar directions.

That local decision matters because long generation is path dependent. One weak merged choice can change the prompt seen by every later step. By ensembling fewer than all positions, the method spends compute only where merging is likely to improve the next choice rather than blur it.

Why it works

Why sparse ensembling is more stable than constant ensembling

A next-token decision only needs help when different models carry complementary information at the same textual boundary, because only then does averaging combine answers about the same text piece. If their boundaries do not match, averaging mixes choices that refer to different partial strings, so the merged result no longer corresponds cleanly to either model's intent. SAFE avoids that failure by waiting for compatible positions.

Even at compatible boundaries, averaging can still be harmful when the models disagree too much. The average then spreads probability mass across several options instead of reinforcing one strong option. That flattening matters because the decoder samples or picks from the merged table one step later, so a flatter table raises the chance of taking a weak branch that alters all later context.

Sharpening repairs that second problem by making the top options stand out again after averaging. The point is not to ignore disagreement. The point is to preserve the value of averaging where it adds signal while preventing the merged table from becoming indecisive when the answer must commit to one next token.

Math after the picture

A gated ensemble rule

First in words:

At each generation step, either keep a single model's next-step table or average several models' tables if the position passes the safety checks.

Then the compact form:

merged_table(step) = average(models at step) if safe(step); otherwise use one model table, then sharpen the merged table when its top choices are too close

Every symbol:

safe(step)a rule that is true when token boundaries match and local agreement is high enough
average(models at step)the combined next-token table formed from the selected models
sharpena transformation that increases contrast between the top options and the rest
A tiny worked example
Suppose two models are at the same word boundary and both place most of their chance on the next token '42'.
Their merged table still gives '42' a clear lead, so SAFE ensembles at that step.
At the next position, one model is halfway through a split word while the other is not.
SAFE skips ensembling there, because the next-step tables refer to different text pieces.
Later, the models are aligned again but the merged table has two nearly tied top options.
SAFE sharpens the merged table before choosing, so the answer does not branch from a nearly random tie.

The main idea is to treat ensembling as an occasional control action, not as a rule applied at every token.

What can go wrong

What can go wrong

The safety test can miss useful positions. If the rule is too strict, SAFE may skip positions where ensembling would have helped because the models were compatible enough even though the test said no.
Sharpening can overcommit. If the merged table is sharpened too aggressively, a small accidental lead can become a hard commitment and remove the value of having combined several models.
All models can still share the same mistake. Selective ensembling does not fix a case where every model prefers the same wrong next token, because the merged table still inherits that common error.
Done right. The method works best when the models disagree in useful but not extreme ways, because selective averaging then captures complementary signal without washing out the top choice.

What a runnable demo should prove

Compare three modes: one model only, ensemble every step, and SAFE. The demo should show that SAFE uses far fewer ensemble steps while keeping more later tokens on a high-quality branch of the answer.
