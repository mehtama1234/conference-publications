Scaling, Benchmarking, and Reasoning of Vision-Language Agents for Mobile GUI Navigation

Build a large offline benchmark for phone app navigation and use it to show that more data plus reinforcement-based fine-tuning produces agents that generalize farther beyond the apps seen in training.

Paper explainersAll themesMultimodal

A mobile GUI agent looks at a phone screen, reads the task instruction, and decides which tap, scroll, or text action to take next. That is a hard setting because the agent has to connect language to visual layout, remember the recent interaction history, and recover from earlier mistakes. Progress has been difficult to measure because most datasets are small, narrow, or inconsistent about evaluation. This paper contributes infrastructure more than one single model trick: HyperTrack, a large dataset of real mobile tasks, and GUIEvalKit, a shared evaluation toolkit. The paper then uses that platform to study two questions from first principles: what changes when the training set gets larger, and what changes when the agent is trained by reinforcement-based fine-tuning instead of plain supervised imitation.

Zero assumption version

Why mobile GUI agents are hard to measure and hard to scale

A phone interface is not one fixed environment. Every app uses different layouts, icons, page transitions, and action sequences. A model that memorizes one set of screens can look strong on a narrow benchmark and then fail as soon as it enters a new app or a new task order.

Supervised fine-tuning alone has a built-in ceiling because it teaches the model to copy recorded trajectories step by step. If the agent reaches an unseen state after one small mistake, the training data may contain no example for how to recover. That makes generalization hard, especially in out-of-domain apps where the exact screen structure differs from the training set.

The paper's move in one sentence. Standardize the benchmark first, then use that benchmark to test how data scale, interaction history, and reinforcement-based training change navigation performance across many real apps.

The algorithm as a flow

What it actually does

Collect real mobile tasks.

Build HyperTrack with thousands of tasks across hundreds of Chinese mobile applications so the benchmark covers a wide range of layouts and action patterns.

Define a unified offline evaluator.

Use GUIEvalKit to score models under the same task format, action space, and completion criteria because comparisons are only valid when the protocol is shared.

Scale training data.

Train agents on larger and larger subsets of the benchmark to measure how performance changes with more trajectories.

Compare training regimes.

Fine-tune one set of agents by supervision and another by reinforcement-based optimization so the study can separate the effect of data scale from the effect of training signal.

Analyze history and reasoning.

Test how access to earlier interaction steps and explicit reasoning traces change final task completion.

What the paper changes

What the paper changes

The paper changes the experimental basis for mobile GUI agents. Instead of judging progress from small disconnected benchmarks, it provides one large dataset and one consistent evaluator, then uses them to compare scaling and training choices.

The hidden quantity

The hidden quantity

measured quantity  =  state coverage over possible interface situations

The hidden quantity is how much of the real navigation state space the training data covers. A state here means the combination of screen content, instruction, action history, and current goal status. Two datasets can contain the same number of actions and still differ sharply in coverage if one repeats the same app patterns while the other spans many layouts and failure states.

HyperTrack makes that quantity larger by adding more apps and more tasks. Reinforcement-based fine-tuning changes how the agent uses that coverage. Instead of only copying the single recorded action for each state, it learns from task reward, which means one numeric feedback value for making progress or finishing the task. That matters because the agent can get credit for recovering from slight deviations rather than being punished simply for not matching one logged trajectory exactly.

Why it works

Why more data and reward-driven training change the result

Data scale matters because mobile interfaces reuse patterns at several levels. Buttons, tab bars, search fields, and confirmation flows repeat across apps, but they appear in different skins and different task orders. When the benchmark is large enough, the model sees enough variation to learn reusable action abstractions instead of memorizing one screenshot-to-action map.

Reinforcement-based fine-tuning matters because exact imitation is too brittle for sequential interfaces. If the logged expert tapped the second result and the agent taps the third result, a supervised objective marks that step wrong even if the agent can still recover and finish the task. A reward-based objective can assign credit to the final completion path, so the model learns recovery behavior and long-horizon planning. That is why the paper finds stronger gains in out-of-domain settings: those settings create more off-trajectory states, and reward-based training teaches the agent what to do after drift.

The shared evaluator matters because it turns broad claims into comparable measurements. Without one toolkit, different papers can define success differently and hide whether a model really improved action grounding, history use, or task completion. HyperTrack and GUIEvalKit together make it possible to separate the effect of bigger data from the effect of a different training objective.

Math after the picture

Why sequential reward differs from step imitation

First in words:

A compact summary is that supervised training maximizes the probability of the logged action at each step, while reinforcement-based training maximizes the expected task return over the whole action sequence.

Then the compact form:

J = E[return over the navigation episode]

Every symbol:

Jthe objective optimized during reinforcement-based fine-tuning
E[return over the navigation episode]the average total reward collected from the start of the task to the end, including progress and completion
A tiny worked example
Suppose the expert path to send a message is open chat, tap compose, type text, and send.
The agent instead opens notifications first, then returns to chat, and still sends the message.
Step imitation penalizes the first deviation immediately because it did not match the logged tap.
Episode reward can still score the run well if the agent recovers and completes the task.

That difference is central for GUI navigation because many tasks admit several valid paths and many small mistakes are recoverable.

What can go wrong

What can go wrong

Offline benchmarks can miss real interaction delays. An offline setting cannot fully capture network lag, pop-up timing, or touch noise, so a model that scores well offline may still fail when deployed on a live device.
Reward design can be sparse or misaligned. If the reward mainly appears at task completion, training can become unstable because the agent gets too little signal. If the reward is too shaped around proxies, the agent may optimize the proxy instead of truly finishing the user task.
Scaling one market does not cover all markets. The benchmark spans many Chinese apps, but navigation conventions can differ across languages, regions, and operating-system styles, so additional transfer gaps may remain.
Done right. The benchmark is most useful when offline gains are followed by live-device checks, when rewards track real task completion, and when new app domains are added to test transfer rather than only memorization.
What a runnable demo should prove

What a runnable demo should prove

Build a small phone-screen benchmark with several apps, several task types, and held-out apps for transfer. Train one agent by supervised next-action prediction and another with an episode reward for successful completion. Evaluate both with a shared offline toolkit that records full task success, step accuracy, and recovery from perturbed starting states.

The demo should show that the reward-trained agent pulls ahead most on held-out apps and perturbed states, because those cases expose whether the policy learned to complete tasks or only to mimic familiar traces.

transfer_gain = success_out_of_domain_RL - success_out_of_domain_SFT

A convincing result is a clear transfer gain together with improved recovery, because that shows the benefit came from sequential decision learning rather than only from memorizing more screenshots.
