MATA: A Trainable Hierarchical Automaton System for Multi-Agent Visual Reasoning

MATA turns multi-agent visual reasoning into a learned state machine, because choosing the right specialist at each step is a routing problem that should be trained directly.

Paper explainersAll themesAgents & Tool Use

Visual reasoning systems often mix several specialist modules: one reads text in the image, another counts objects, another checks spatial relations, and another writes the final answer. The weak point is usually the controller. Hand-written controllers are rigid, while one large model is hard to inspect and often produces unsupported steps. MATA addresses that control problem with a hierarchical automaton. A top-level controller picks which specialist should act next, each specialist follows a small reliable local procedure, and all steps are written into shared memory. The result is a system whose reasoning path can be inspected and improved because the routing policy is explicit.

Zero assumption version

Specialists help only if the controller sends work to the right one

Compositional visual reasoning is attractive because different subtasks need different strengths. Counting objects, checking left-versus-right, reading text, and combining evidence are not the same operation. But once many specialists exist, the system must decide who acts next.

Many earlier systems avoid that decision by fixing a pipeline in advance. That works on narrow tasks, but it breaks when a question can be solved in several different ways or when the needed order depends on the image. A fixed chain can also waste effort because it runs modules that were unnecessary for the current query.

A single end-to-end model avoids hand-written routing, but then the reasoning path is hidden inside one opaque forward pass. MATA takes the opposite approach. It makes routing the central learned problem because better routing is what determines whether the right specialist sees the right context at the right time.

Core idea: Treat specialist selection as a trainable state transition problem, because the hard part is not owning many agents but choosing among them well.

The algorithm as a flow

What it actually does

Represent the system as states

Each specialist is one state in a higher-level automaton, so the controller's job is to choose state transitions.

Give each specialist a short local routine

Inside each state, a small rule-based procedure handles micro-control because constrained local behavior reduces accidental drift.

Store observations in shared memory

Agents write intermediate findings into one memory record, so later agents can build on earlier evidence.

Train the transition policy from traced solutions

The paper builds transition trees and converts them into memory-to-next-state examples, because the controller needs direct supervision on routing choices.

Run learned routing at test time

The controller reads the query and current memory, then selects the next specialist until the answer state is reached.

What the paper changes

What the paper changes

The paper moves the learning target from answer generation to agent routing. It still uses specialists, but now the system learns when to call each one because the transition policy is trained on explicit successful state sequences.

the object it moves  =  Routing policy across specialist agents
The hidden quantity

The hidden quantity: next-state usefulness

measured quantity  =  How much the current memory supports one next agent over the others

At any step, the controller must answer a quiet question: which specialist would reduce uncertainty the most right now? That quantity is not written directly in the image or the query. It depends on the current memory, what evidence is still missing, and what each specialist can add.

MATA exposes this quantity through transition supervision. By collecting successful state trajectories, the paper creates training pairs from current memory to next state. The controller then learns the pattern that certain memory contents should trigger a counting state, while other contents should trigger a relation-checking or answer-writing state.

Why it works

Why a learned state machine helps

The design splits the problem into two levels. The high level chooses which specialist should act next. The low level performs a small controlled procedure inside that chosen state. This division helps because the controller can focus on routing while each specialist stays simple and reliable.

Shared memory is the second important piece. Without shared memory, each specialist would have to rediscover earlier evidence or the controller would have to remember it implicitly. MATA writes intermediate results into a common record, so the current state decision can depend on explicit evidence rather than on hidden internal context.

Training the controller on successful transition traces closes the loop. Instead of hoping that the model infers routing skill from answer loss alone, the paper supplies direct examples of good next-state choices. That makes routing easier to learn because the system is rewarded for taking the right reasoning step before the final answer is even produced.

The routing objective

First in words:

The main objective trains the controller to predict the correct next state from the current memory record and query context, while local specialist rules keep execution inside each state well behaved.

Then the compact form:

L_total = L_next_state + lambda * L_answer

Every symbol:

L_next_stateloss for predicting the correct next specialist state

A tiny worked example
Suppose the question is, "Is the red cup left of the plate with text on it?"
After the first step, memory contains: one red cup found, two plates found, text not yet read.
A fixed pipeline might count again, but a trained controller should choose the text-reading state because the missing fact is which plate has text.
Once memory records that the right-hand plate has text, the next useful state is the relation-checking state because the needed objects are now identified.
That sequence works because each next-state choice is driven by what evidence is missing, not by a rigid module order.

The equation is simple compared with the idea. The important change is explicit supervision over state transitions.

What can go wrong

What can go wrong

Bad transition traces teach bad routing. If the collected state trajectories are weak or incomplete, the controller copies those weak choices because its supervision comes directly from them.
Shared memory can become noisy. If specialists write vague or conflicting notes, the controller receives poor context, so next-state selection degrades because the memory no longer cleanly reflects missing evidence.
Local rules can be too rigid. A small rule-based routine improves reliability because it restricts local actions, but it can block useful behavior if the task requires a step that the local state machine does not permit.
Done right: the trace becomes useful supervision. When state traces are accurate and memory entries are clear, routing improves because the controller can match current evidence to the specialist that should act next.
What a runnable demo should prove

What a runnable demo should prove

Build a visual question-answering task with three specialists: text reading, counting, and relation checking. Add a final answer state and a shared memory log. Compare three systems: a fixed module order, a single general controller, and a MATA-style controller trained on traced next-state decisions. Measure answer accuracy, number of unnecessary specialist calls, and whether the full execution trace can be inspected after each query.

routing_efficiency = useful_specialist_calls / total_specialist_calls, reported together with final answer accuracy

The demo should show that MATA reaches better answers with fewer wasted calls because the controller learns to send work to the right specialist at the right time.
