Functional Cache Grafting: Robust and Rapid Code-Policy Synthesis for Embodied Agents

Reuse validated function fragments and their cached prompt states so that new control programs can be assembled faster and with fewer code mistakes.

Paper explainersAll themesAgents & Tool Use

Embodied agents often rely on code-writing models that must regenerate long control programs from scratch for each task. FCGraft stores validated function skeletons together with their cached internal prompt states, retrieves the most relevant functions for a new task, stitches those cached states together, and patches only the small task-specific parts so that synthesis is both faster and more reliable.

Zero assumption version

Why code-policy generation is slow and error-prone

A code-writing model for an embodied task must read a long prompt, reason about the environment constraints, and write executable control code. That is expensive because prompt processing is repeated for each task, even when many functions are reused across tasks.

Generation is also fragile because full free-form decoding can produce wrong API calls, missing safety checks, or broken control flow. FCGraft reduces both problems by reusing previously validated function pieces and the cached internal states associated with them.

The paper's move in one sentence. Retrieve validated function fragments and reuse their cached prompt states so that only the task-specific gaps need fresh decoding.

The algorithm as a flow

What it actually does

Build a library of validated functions

Store function-level code skeletons that already execute correctly along with the prompt caches produced when they were generated.

Retrieve relevant functions for a new task

Choose code fragments whose behavior matches the requested embodied task so that synthesis begins from proven structure.

Stitch cached segments together

Combine the stored key-value caches from the retrieved fragments so that the model can resume decoding from a partially prepared internal state.

Patch only the necessary regions

Decode small task-specific edits for numeric settings, constraints, or environment details because the shared control logic is already present.

Run the resulting code policy

Execute the assembled program so that the agent gains both lower latency and higher task success from reused validated structure.

The hidden quantity

The hidden quantity

measured quantity  =  How much of the new policy can be reused safely

When a new embodied task arrives, the system does not directly know which parts of earlier programs remain valid and which parts need task-specific modification. Reusing too little wastes time, while reusing too much can copy the wrong assumptions.

FCGraft resolves that hidden tradeoff by retrieving function-level matches and patching only the regions that differ. That helps because validated structure is preserved wherever reuse is safe.

Why it works

Why this works: keep the validated parts, regenerate only the differences

Latency falls because a large share of prompt processing has already been paid for in the stored caches. Reusing those cached states avoids repeating the full prefill for common functions.

Task success rises because many control bugs come from regenerating standard routines that were already correct before. Function-level reuse preserves safety checks and API structure, while local patching changes only the parts that must adapt to the new task.

Math after the picture

Reuse most of the program, decode only the remainder

First in words:

A compact summary is that total generation cost equals reused cached cost plus fresh patching cost. The method improves speed when the fresh patching cost is much smaller than writing the full program from scratch.

Then the compact form:

total_cost = reuse_cost + patch_cost

Every symbol:

total_costoverall computation needed to synthesize the policy
reuse_costcost of retrieving and composing validated cached fragments
patch_costnew decoding needed for task-specific edits
A tiny worked example
Suppose a policy needs four functions.
Three functions are retrieved from the library and stitched with cost 2 each, for reuse cost 6.
One task-specific branch is newly decoded with cost 3.
Total cost = 6 + 3 = 9.
If full regeneration would cost 20, grafting wins because most of the program was already validated and cached.

The real system measures speed through cached internal prompt states, but this equation captures the paper's central tradeoff between reuse and fresh decoding.

What can go wrong

What can go wrong

The library may not cover the new task well. If no validated functions are close to the requested policy, retrieval gives weak building blocks, so patching may expand until the system loses the speed advantage.
Wrong retrieval can preserve the wrong assumptions. A retrieved function may look similar but encode incompatible API usage or control logic, which can hurt execution because the reused skeleton itself is mismatched.
Patch boundaries are delicate. If the system patches too small a region, hidden dependencies can remain stale, and if it patches too much, the method drifts back toward full regeneration.
Done right. The paper is useful because it treats synthesis as structured reuse, which reduces both repeated computation and repeated coding errors.
What a runnable demo should prove

What a runnable demo should prove

Build an embodied-code benchmark with several related household tasks that share navigation, grasp, and safety routines. Compare full generation, prompt-level cache reuse, and function-level cache grafting. For each task, log retrieved functions, patch regions, synthesis time, and execution success.

The demo should show that function-level grafting reaches similar or better execution quality with less decoding because validated code structure is reused directly. Include tasks that require small numeric-setting changes and tasks that require one new branch so that the limits of grafting are visible.
