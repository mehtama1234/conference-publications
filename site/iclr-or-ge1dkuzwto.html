ToolWeaver: Scalable Tool Use via Hierarchical Codes

Instead of giving each tool its own token, encode tools as short sequences built from shared building blocks so the model learns which tools work together.

Paper explainersAll themesAgents & Tool Use

When an LLM needs to use a tool from a big library, most methods either search for it (slow, missing semantics) or give it a unique token (vocabulary explodes). ToolWeaver does neither. It encodes each tool as a short sequence built from shared components (like building words from alphabet blocks), so the model naturally learns which tools collaborate because they share codes.

Zero assumption version

Two broken paths today

Today's tool-use LLMs hit a fork in the road. Path A: search for the tool from a library (retrieval). But most search engines were never trained to understand what tools DO—they just match surface words, missing the real semantics. Path B: have the model directly generate the tool name by giving each tool its own unique token, the way we give each word in a dictionary its own token. This works for small libraries (maybe 100 tools) but falls apart at scale. With 47,000 tools, you'd need 47,000 new tokens. Vocabulary explodes. Worse: if two tools are actually similar or should be used together, the model has no way to spot it—each tool is a isolated island.

A beginner trying to fix this might think: just train search to rank better by reading tool descriptions deeper, or train bigger token vocabularies. But search still ignores how tools actually combine, and bigger vocabularies just make the problem worse—now every tool is even more isolated, and the model has no signal about which tools collaborate.

The core problem. One token per tool scales linearly: 10x more tools means 10x bigger vocabulary. It hides collaborative structure (which tools work together).

The algorithm as a flow

What it actually does

Encode tool semantics

Read each tool's name and description. Use a pretrained text model to turn it into a dense list of numbers representing its meaning.

Build hierarchical codes

Use a technique called residual quantization: assign the first code to capture broad function categories, second code to refine within that category, third to distinguish nuances. Each layer refines the error.

Enforce uniform collaboration

Ensure the codebook is balanced—each code in each layer used by roughly equal numbers of tools—so collaboration patterns are dense, not sparse.

Fine-tune model to generate codes

Train the LLM to generate tool code sequences as part of its reasoning. A prefix tree of valid sequences ensures it only generates real tool codes.

Model learns from dense co-occurrence

Because many tools share codes, the model sees patterns. Calc and Solver both use the Math code, so it learns they team up.

What the paper changes

What the paper changes

ToolWeaver replaces a flat tool vocabulary (one isolated token per tool) with hierarchical code sequences (short sequences built from a small shared codebook). The model learns to generate these code sequences instead of monolithic tool names.

the object it moves  =  Tool representation: from isolated tokens to code sequences
The hidden quantity

The collaboration signal

measured quantity  =  Tool co-occurrence density

Most methods hide this: if two tools never appear together in training, the model has no reason to know they work well together. ToolWeaver makes this visible by encoding tools with shared codes. When calc and query-system both use the Math code layer, their co-occurrence becomes dense and visible in the model's training data. The paper measures this indirectly through tool retrieval accuracy (how often the model picks the right tool for a task) because dense co-occurrence of shared codes creates tighter correlations between tools in the training data, making the right choice full of clear signal and easy to learn. Ablations confirm that tools sharing codes genuinely perform better together, because they fire together more frequently during training.

The paper estimates co-occurrence density via residual quantization: after encoding each tool into codes, it checks how many distinct code patterns share each code. High sharing means high collaboration signal. During fine-tuning, the model sees these patterns millions of times and learns them.

Why it works

Why it works

The core insight: when tools are represented as sequences of shared codes, collaboration patterns become visible. Imagine organizing a library by genre (L1 codes), subgenre (L2), and title (L3). A math calculator and a solver share the Math and NumericProcessing codes, so during training they appear together constantly. The model's attention mechanisms (the part that learns patterns) see these shared codes firing together thousands of times. Every time the model learns to generate the Math code, it is implicitly learning: this code connects to other tools that also use it. Contrast this to one-token-per-tool: if calc gets token 4721 and solver gets token 12004, there is no structure linking them—the model must infer collaboration from sparse co-occurrence in the training corpus.

Residual quantization (the technique used to build the codes) works layer-by-layer. The first layer assigns tools to broad categories and captures the residual error (the part not yet explained). The second layer refines within that error, capturing finer distinctions. The third refines the second's residual. This hierarchical stacking means: early layers group tools by function (all math tools together), and later layers distinguish within those groups. The uniform constraint (ensuring each code is used by roughly equal numbers of tools) is critical: it prevents the model from learning a degenerate solution where one code captures everything and others are useless. Instead, all codes carry signal, and collaboration patterns are dense across the hierarchy.

The core equation

First in words:

Total loss = reconstruction error + sum over all layers of (quantization error + uniformity penalty). Uniformity penalty is large if any code is used much more or much less than average.

Then the compact form:

L = L_recon + sum_L (L_quant_L + lambda * L_uniform_L)

Every symbol:

LTotal training loss (lower is better)
L_reconReconstruction loss: how well the quantized codes explain the original tool semantics
L_quant_LQuantization loss for layer L: error from assigning a continuous vector to a discrete code
L_uniform_LUniformity loss for layer L: penalty if codes are used unevenly
lambdaWeight controlling how strongly we enforce uniform code distribution
sum_LSum over all layers (typically 3)
Tiny worked example with 4 tools
Imagine 4 tools: Calc, Solver, Search, Rerank. Layer 1 has 2 codes: Math, Query.
Uniform split: each code should be assigned 2 tools. Calc and Solver -> Math codes. Search and Rerank -> Query codes. Uniformity loss = 0 (perfect balance).
Now suppose training data accidentally assigns 3 tools to Math, 1 to Query (imbalance). Uniformity loss would penalize this, pushing layer 2 to redistribute. This ensures collaboration patterns remain dense across the hierarchy.
If tool 5 joins (Brainstorm), and the layer 1 codebook is fixed, then layer 2 must either split a Math code or a Query code to make room. The algorithm chooses the split that best explains Brainstorm's semantics while keeping layer 1 intact. Result: Brainstorm assigned to [Math, SubCode2, FineCode5], sharing the Math code with Calc and Solver.

The uniform constraint keeps the codebook balanced so every code carries distinct information and collaboration signals stay dense.

What can go wrong

What can go wrong

Imbalanced codebook. If the uniform constraint is weak (small lambda), one code can capture many tools and others become unused. Collaboration signals disappear. The model learns nothing useful because most codes are dead weight.
Hierarchy mismatch. If the number of quantization layers is wrong (too few or too many), the hierarchy does not align with real tool structure. Too few layers: tools that differ in nuance get collapsed into the same code. Too many: codes become redundant and the model has nothing new to learn per layer.
Sparse initial semantics. If the text encoder that reads tool descriptions is weak (untrained on technical documentation), the initial numeric lists are noisy. Even with perfect quantization, garbage in equals garbage out. The paper uses a pretrained text encoder trained on broad text data to avoid this.
Done right. Use a high-quality text encoder, set lambda high enough to enforce uniformity, and calibrate the number of layers to match the complexity of your tool library. The paper shows this with nearly 47,000 tools across multiple training stages, reaching 88-89% accuracy in tool selection.
What a runnable demo should prove

What a runnable demo should prove

Build a small library of 100-200 tools grouped into 3-4 semantic categories (math, search, text, image). Encode each with a text encoder to get numeric lists (one list per tool). Use residual quantization with 3 layers and a codebook of size 20-32 per layer. Compute the quantization loss and uniformity loss. Fine-tune a small language model (e.g. Llama-2-7B or Mistral) on tool-use trajectories (query goes to tool code sequence goes to answer) for 500-1000 examples. Track the model's ability to select the right tool (accuracy) and whether tools that share codes actually work well together (measure by computing co-occurrence in the model's generated sequences).

Tool selection accuracy = (correct tool sequences generated / total tool selections) * 100. Co-occurrence density = (count of pairs of tools sharing at least one code that appear together in generated sequences) / (total co-occurrences).

The demo makes it impossible to miss: code sharing creates dense collaboration signals because when Calc and Solver share the Math code, the training data shows them together constantly. Repeated co-training on shared codes drives the model's attention mechanisms to bind those tools together as a learned unit, far more strongly than if they had isolated tokens with only sparse co-occurrence.
