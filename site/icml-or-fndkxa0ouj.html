ExVerus: Verus Proof Repair via Counterexample Reasoning

Instead of guessing proofs once, ExVerus lets an LLM learn by seeing what breaks, then fixing it.

Paper explainersAll themesAgents & Tool Use

Writing mathematical proofs is hard—even for programs. When an LLM tries to write a proof for code and the proof fails, it usually just gets retried without knowing WHY it failed. ExVerus changes this by showing the LLM concrete counterexamples (actual program traces that break the proof), then asking it to block those failures by writing rules that prevent them. It is not magic spell-checking; it is learning-from-mistakes the way a student improves by seeing their wrong answers.

Zero assumption version

Why proofs fail without feedback

A proof is a program written in special code (Verus) that convinces a machine that some other program works correctly. For example, a proof might say: if you give my list-sorting function a 10-item list, it will always return a sorted list.

Until now, LLMs (language models) write proofs in one shot—read the code, guess the proof, hit enter. If it fails, they have only the error message, which is often cryptic. The LLM does not know: what trace of the program made the proof wrong? What actually happened when you ran the code? A beginner fixes homework by seeing test cases fail; an LLM fixing proofs sees only a wall of text saying proof rejected.

This is frustrating because the proof often nearly works. One condition is wrong, one invariant (a rule that must always be true) is missing, and the whole thing collapses. But the LLM does not know which piece to change.

The fix in one sentence. Show the LLM concrete program runs where the proof breaks, then ask it to patch the proof by writing rules that block those runs.

The algorithm as a flow

What it actually does

LLM writes initial proof

Given code, the model generates Verus proof assertions (claims about what must be true).

Verifier checks it

The Verus machine checks if the proof is correct. If not, it halts.

Generate counterexamples

ExVerus simulates the code and finds concrete data (a list, a number) that violates the proof.

Show counterexample to LLM

The model sees the exact program run and why it fails, not an abstract error.

LLM patches proof

The model writes new invariants (guard rules) to exclude the broken case. Try again.

What the paper changes

The one thing the paper changes

The paper changes how an LLM gets feedback when writing proofs. Instead of receiving only a yes/no from the verifier, it receives concrete examples of program behavior that break the proof—data values, execution traces, the actual reason the proof failed.

the object it moves  =  feedback to the LLM
The hidden quantity

The hidden quantity: what went wrong

measured quantity  =  proof counterexample

A proof counterexample is not a complicated statistic—it is a concrete program trace: a specific list of numbers, a specific path through the code, specific variable values at a specific point. It is what went wrong, pinned down as data you can see.

The paper extracts this by running the code and checking which inputs cause the proof's claim to fail. It then feeds this concrete trace back to the LLM. Instead of guessing what went wrong from an error message, the LLM sees proof failure caused by real program behavior, and writes proof rules to exclude that behavior.

Paper reading. The paper's key technical move is generating counterexamples via bounded model checking and feeding them to the LLM to guide inductive invariant synthesis. Inductive invariants are loop-proof guards (rules that remain true in every iteration).
Why it works

Why this method works

Proof generation is a search problem. The LLM is trying to find invariants (rules) that make the proof succeed. Without feedback, it is searching blind—restarting from the same initial guess over and over. With concrete counterexamples, the search is guided: the LLM learns which invariants do not work and why, then proposes new ones that block the broken case. This is feedback-driven repair, not restart.

Counterexamples work because they unambiguously show what went wrong. Seeing that input [1, 5, 2] broke your loop invariant is way more useful than an abstract error about failed proof step 47. The LLM can then pattern-match: what property would have blocked [1, 5, 2]? And write a rule. This narrows the search space dramatically. Each failed proof generates new constraints; each constraint guides the next attempt closer to success.

The invariant repair equation

First in words:

new invariant = old invariant OR (NOT condition that makes counterexample fail). Repeat until proof holds.

Then the compact form:

I_new = I_old OR block_counterexample(c_1, c_2, ..., c_k)

Every symbol:

I_newthe repaired invariant (loop guard rule)
I_oldthe previous invariant that failed
c_ia counterexample trace (concrete program state)
block_counterexample(...)a new logical condition that forbids the counterexample
A tiny worked example
Old proof invariant: 'every element in the array is positive'.
Verifier found counterexample: array = [1, -3, 5]. This breaks the invariant.
LLM writes new invariant: 'every element in the array is positive, OR the array has length < 3'. This blocks the counterexample [1, -3, 5].
Repeat: new invariant is checked. If a new counterexample breaks it, LLM refines further.
After a few rounds, the invariant is strong enough that no counterexample breaks it—proof passes.

Each repair adds a new logical clause to block a seen failure. Over iterations, the invariant becomes precise enough to succeed.

What can go wrong

What can go wrong

Counterexample generation is incomplete. If the tool finding counterexamples is imperfect, it might miss broken cases. Then the invariant looks good locally but fails on untested data. The paper bounds the search (checks a finite set of inputs), so there is always a risk of missing edge cases.
LLM overfits to counterexamples. The LLM might write invariants that block the seen counterexamples but are too narrow. Example: if one counterexample is the array [1, -3, 5], the LLM might write 'forbid arrays of length exactly 3' instead of 'forbid negative numbers'. The fix fails on a different length-3 array.
Loop invariants are genuinely hard. Some properties of loops are not learnable by an LLM in a reasonable time. If the true invariant is mathematically complex or subtle, the counterexample loop may not converge.
Done right. The LLM generalizes counterexamples (writes rules that block the counterexample class, not just the one case), and the loop terminates when the invariant is strong enough.
What a runnable demo should prove

What a runnable demo should prove

Build a small Verus program (e.g. a list-reversal or array-search function) that needs a loop invariant. Write a version without the correct invariant on purpose. Run ExVerus: let it generate one counterexample, have the LLM write a patch, check if the patch blocks it. Repeat for 2-3 rounds, watching the invariant grow and the proof get closer to passing. Show token counts: ExVerus uses fewer tokens overall than a naive LLM retrying blindly, because each guess is guided.

proof_success_rate = (number of proofs that pass) / (number of proofs attempted); token_efficiency = proof_success_rate / (total tokens used)

The key visual: after round 1 (counterexample shown), the next proof attempt is not a random restart—it directly addresses the failure. That is learning, not guessing.
