Rethinking Human Intent-to-CAD

A two-stage system learns to write parametric CAD code from hand-drawn sketches and text descriptions by first aligning the two input types, then using rewards to enforce that the generated code produces geometrically correct shapes.

Paper explainersAll themesAgents & Tool Use

Designing in CAD today requires writing code or clicking tools, but most people sketch ideas by hand and describe them in words. This paper tackles the problem: given a rough sketch and a text description of what the designer wants, generate the actual parametric CAD code (the sequence of commands that define a shape) without having a ground-truth CAD file to learn from. It does this by first translating both the sketch and text into a shared internal representation, then using reinforcement learning (a technique where a system learns by trial and error with rewards) to make sure the generated code produces a shape that actually matches the design intent.

The messy reality of design intent

In real design work, people sketch rough ideas on paper and describe them in words: make a hole here, soften that edge, make it wider. But CAD systems demand precise code: a sequence of exact commands that specify dimensions, how to cut and combine shapes, and the exact surfaces. The gap is huge.

A naive approach: collect pairs of (sketch, text description, ground-truth CAD code), train a model to predict the code from the inputs. The problem: there is almost no such training data. Sketches are unstructured (people draw differently), text is informal, and ground-truth CAD files are rarely paired with their design intent. Even if you had the data, the model would memorize the mapping without learning to produce code that actually produces the right shape.

So the real challenge: generate code that transforms messy, incomplete human intent into an executable CAD model, with no ground truth to copy from.

The algorithm as a flow

What it actually does

Alignment stage: Two inputs become one

Sketch pixels and text tokens are each passed through neural networks (learned transformations) that extract their core meaning and place both into the same internal space.

Joint representation: Shared context

The aligned sketch and text representations are combined, creating a single description of what the designer wants that both capture.

Code generation: Attempt the output

The system samples parametric CAD code (a sequence of constructive operations: extrude, cut, fillet, etc.) by predicting one command at a time.

Shape simulation: Run and check the result

Each generated code snippet is run to produce a 3D shape; the system captures how that shape looks and its measurements.

Reward and learn: Reinforce correct attempts

Rewards score how well the generated shape matches the sketch and text intent; the system raises the probability of code sequences that receive high rewards.

What the paper changes

What the paper moves

The object the system changes is the sequence of parametric CAD commands (the code that defines the shape). During training, the system does not just memorize which commands to output; instead, it uses rewards to adjust which command sequences are more or less likely, pushing the system to generate commands that, when executed, produce a shape matching the design intent.

The hidden quantity

Geometric and topological consistency

measured quantity  =  How much the generated shape matches intent

The paper introduces a hidden quantity: a score that measures whether the generated CAD shape actually matches what the sketch and text describe. This is not about whether the code looks right in syntax; it is about whether running the code produces a shape with the correct dimensions, curves, and surfaces, and also correct connectivity and holes in the right places.

The system measures this by rendering the generated shape from the CAD code and comparing it against a reference: Does the outline match the sketch? Do the dimensions match the text description? Are the features (holes, fillets, cuts) in the right places? The paper encodes these checks into a reward signal: high reward when the shape is correct, lower reward otherwise. During training, the system learns to generate code that maximizes this reward.

Why it works

Why aligning first, then rewarding, works

The central idea is that sketches (visual) and text (linguistic) are two completely different ways humans express the same design idea, and a machine cannot connect them directly. The system must first translate both into a common language: a shared internal representation where the sketch's meaning and the text's meaning sit side by side. This is what Cooperative Multi-Task Alignment does—it trains two separate encoder networks (sketch encoder and text encoder) to output vectors (lists of numbers) that capture the same ideas, even though they come from different modalities.

Once both inputs are in the same space, the system can generate CAD code that actually satisfies both. But code generation is hard: there are trillions of possible command sequences. Raw supervised learning (just predicting commands from the ground-truth training data) fails because there is no ground-truth data. Reinforcement learning fixes this by running generated code and checking the result: If the code produces a shape that matches the sketch outline and the text description, reward it. If it produces a wrong shape, punish it. Over time, the system learns which kinds of commands lead to shapes that satisfy intent, without ever seeing a ground-truth CAD file.

The spatial awareness part ensures the rewards measure shape correctness carefully. The system does not just check abstract properties; it evaluates whether generated shapes align with the sketch in 2D (outline match, feature positions) and satisfy dimensional and connectivity constraints from the text (thickness, how parts connect, number of holes).

The reward and loss equations

First in words:

Total loss equals alignment loss (pushing sketch and text encoders toward the same space) plus code-generation loss (reinforcement learning loss that raises the probability of code sequences that produce high-reward shapes, and lowers the probability of low-reward sequences).

Then the compact form:

Loss_total = Loss_align + lambda * Loss_RL Loss_align = ||E_sketch(S) - E_text(T)||^2 Loss_RL = -E[R(Code) * log P(Code | E_joint)]

Every symbol:

Loss_alignhow far sketch and text encodings are from each other
E_sketch(S)the vector output by the sketch encoder when given sketch S
E_text(T)the vector output by the text encoder when given text T
Loss_RLreinforcement learning loss; R is the reward, P is the probability the model assigns to generating that code
R(Code)reward score: how well the generated code produces a shape matching intent
log P(Code)logarithm of how likely the code sequence is under the model
lambdaa scaling factor controlling how much weight RL receives versus alignment
E_jointthe combined representation from both aligned sketch and text
A tiny worked example
Suppose sketch encoder outputs the vector [0.3, 0.7, 0.1] and text encoder outputs [0.25, 0.72, 0.15].
Alignment loss = (0.3-0.25)^2 + (0.7-0.72)^2 + (0.1-0.15)^2 = 0.0025 + 0.0004 + 0.0025 = 0.0054.
Meanwhile, the model generates code 'Extrude 5mm'. When run, it produces a shape. A human reviewer or automated checker gives it reward R=0.8 (pretty good match to intent).
The model had assigned probability P(Extrude 5mm | joint) = 0.6 to this sequence.
RL loss = -(0.8 * log(0.6)) = -(0.8 * -0.51) = +0.41. Lower loss = higher reward, so this sequence is reinforced.
If the model had generated 'Extrude 50mm' with reward R=0.1 (bad match) and P=0.3, then RL loss would be -(0.1 * log(0.3)) = -(0.1 * -1.20) = +0.12, still positive but smaller—it is penalized less than the wrong sequence.

The alignment loss shrinks the gap between sketch and text representations, and the RL loss steers code generation toward sequences that produce shapes matching intent.

What can go wrong

What can go wrong

Misaligned encoders produce incoherent code. If the alignment stage fails (sketch and text encoders remain in different semantic spaces), the generator receives conflicting information and produces code that satisfies neither input. Prevention: validate the alignment with a separate verification step before running RL.
Rewards are too narrow; the system overfits to easy shapes. If the reward function checks only a few geometric properties (e.g., outline match) and ignores others (e.g., internal features, edge quality), the system learns to produce code that passes the reward but does not match the full design intent. Prevention: define rewards that comprehensively measure sketch-to-CAD fidelity.
Sketch and text conflict; ambiguous intent. If the sketch and text description contradict (sketch shows a thin part but text says thick), the system cannot satisfy both and will produce code that represents a compromise or skip one modality. Prevention: require consistent, non-conflicting human input or add a conflict detection module.
Reward signal is expensive to compute. Running CAD simulation and shape checks for every generated code sample during training is slow. A naive RL setup would require millions of simulator calls. Mitigation: use learned reward approximators—neural networks trained to predict what the reward would be without running the simulator—so the system can evaluate millions of code samples by fast prediction instead of slow simulation, dramatically speeding training.
Done right: alignment + RL with comprehensive rewards. When sketch and text are properly aligned into a shared space, and rewards comprehensively measure geometric correctness, the system learns to generate code that turns heterogeneous human intent into high-fidelity CAD models without memorizing ground-truth examples.
What a runnable demo should prove

What a runnable demo should prove

A runnable demo should take a hand-drawn sketch and a short text description (e.g., a sketch of a box shape and text saying make a 10mm hole in the center), and show that the system generates parametric CAD code that, when run in a CAD software, produces a shape matching the design. The demo should also show intermediate outputs: the aligned sketch/text representation in the joint embedding space (visualizing that they are close together), the generated code (the actual command sequence), and a 3D render of the result. Ideally, it should also show the reward signal during RL training: which code samples received high rewards, and how the system improved over iterations.

Design-intent accuracy = (outline-match score + topology-correctness score + feature-position-accuracy) / 3

The demo must make it unmissable that a rough sketch and informal text description, when fed through alignment and RL, actually become correct, executable parametric CAD code—no ground-truth CAD file needed.
