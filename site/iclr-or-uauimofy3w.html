Non-Collaborative User Simulators for Tool Agents

Train a user simulator that behaves like real humans in dialogue—making requests the tool cannot fulfill, changing the subject, getting impatient, and saying incomplete things—so you can stress-test your agent before users do.

Paper explainersAll themesDatasets & Benchmarks & Evaluation

Tool agents answer questions by calling software tools like booking systems or search engines. Right now, training these agents uses fake users who cooperate perfectly and say clear, complete requests. That does not match the real world. This paper trains a user simulator using machine learning to behave like difficult real humans instead: asking for things the tool cannot do, switching topics, showing impatience, and speaking in fragments.

Zero assumption version

Real users do not cooperate

Tool agents are tested on simulated users who play perfectly: they request exactly what the tool can do, speak in complete sentences, and never get frustrated or sidetracked. In the real world, users rarely do this. They ask for things the tool cannot provide (window seats on trains when the booking system does not offer that option). They drift into tangential topics (asking about sightseeing while trying to book a train). They show impatience. They speak in fragments. When a real agent encounters these behaviors, it often fails catastrophically—hallucinating that it completed the request, or abandoning the task entirely.

If you only train an agent on perfect users, you discover its failures only after customers encounter them. A better approach: build a simulator that behaves like difficult real users, then stress-test your agent at home, before deploying it. This works because difficult users expose the agent's weak strategies (hallucinating when confused, abandoning tasks under time pressure, breaking dialogue flow when topics shift)—failures that perfect users would never trigger. Finding and fixing these failures in-house, with a controllable simulator, costs far less than discovering them in production when users are already frustrated.

The problem in one sentence. Existing user simulators are too cooperative; real users make requests the system cannot handle, change subjects, show impatience, and speak unclearly.

The algorithm as a flow

What it actually does

Build the base user

Start with a collaborative user simulator that speaks clearly, makes solvable requests, provides all needed info.

Identify four problem types

Cluster real user behaviors: unavailable service (asking for features the tool lacks), digressing (shifting to unrelated topics), impatient (rushing or expressing frustration), incomplete utterance (fragments, missing info).

Add non-collaborative patterns

Use language model prompts to inject each behavior type into user turns: make them ask for unsupported options, mention sightseeing mid-booking, show urgency, or speak in broken sentences.

Train with GRPO and an LLM judge

GRPO adjusts the simulator based on rewards; an LLM referee ensures the task remains achievable despite the friction—no point making the task impossible.

Test agents under stress

Run your agent against this realistic simulator; it exposes failure modes (hallucinations, dialogue breakdowns) before real users do.

What the paper changes

What the paper changes

The paper changes the output of the user simulator: instead of polite, clear, perfectly-aligned requests, it now produces four kinds of realistic friction—requests the tool cannot fulfill, topic-switching, impatience, and incomplete utterances. The mechanism for generating those behaviors stays inside the simulator; the agent never knows which type it is facing. The agent's only job is to handle whatever the user throws at it.

the object it moves  =  User simulator behavior
The hidden quantity

The hidden quantity: Task maintainability

measured quantity  =  Likelihood the task stays solvable despite friction

The hidden quantity is task maintainability: the likelihood that a non-collaborative user's request can still be satisfied even while they are being difficult. When a user asks for an unavailable feature (window seat), the simulator must ensure that a fallback path still exists (offer an aisle seat). When a user digresses (asks about sightseeing), the simulator keeps the original booking goal in mind. When impatient or fragmentary, the simulator still preserves enough information for the agent to complete the task.

The paper measures this using an LLM-as-judge reward: after each simulated turn, an LLM reads the dialogue and scores whether the user's underlying intent remains achievable. This score guides GRPO training. If the simulator generates dialogue that makes the task unsolvable, the reward drops, and GRPO steers the simulator back toward difficulty that is challenging but not impossible.

Why it works

Why this works: Four behaviors plus careful boundaries

The core mechanism has two parts. First: the simulator generates realistic non-collaborative behaviors by injecting four distinct patterns—unavailable service (user asks for tool capability that does not exist), digression (user mentions unrelated topics), impatience (user expresses frustration or rushes), and incomplete utterance (user speaks in fragments). Each pattern is triggered by rules and LLM prompts, not by random noise. That is the difference from just adding noise: each behavior mimics a real human struggle, not gibberish.

Second: the LLM judge keeps the task solvable. After each user turn, the judge scores whether the underlying intent is still achievable. GRPO training optimizes the simulator to maximize this score, so it learns to be difficult in ways that preserve task solvability. This prevents the simulator from degenerating into unsolvable hallucinations. The result: agents trained on this simulator see realistic stress (hallucinations, dialogue breakdowns) but can still complete tasks with good strategy.

Math after the picture

The reward equation: Steering the simulator

First in words:

Simulator reward equals task success probability times maintainability score, penalizing behavior drift from the four types

Then the compact form:

R = P_maintain * P_success - lambda * KL(behavior || target_behaviors)

Every symbol:

RReward for this simulated dialogue turn
P_maintainLLM judge score of task maintainability (0 to 1)
P_successProbability agent can complete the task given this user behavior
lambdaWeight on behavior-drift penalty
KL(...)Divergence between simulator outputs and the four target behaviors
A tiny worked example
Dialogue: user asks for a window seat (unavailable) but aisle seat is available.
LLM judge scores: maintainability = 0.8 (task is doable with fallback).
Agent completes task with agent success probability = 0.7.
Reward contribution: 0.8 * 0.7 = 0.56.
KL penalty: simulator output is 90% unavailable request (target), 0% noise = small penalty of -0.05.
Total reward: 0.56 - 0.05 = 0.51. GRPO increases simulator weight for unavailable behavior.
Contrast: if LLM judge scored maintainability as 0.1 (task unsolvable), reward drops to 0.07—GRPO steers away.

The reward balances creating realistic friction (high maintainability score) while staying true to the four behavior types (low KL divergence).

What can go wrong

What can go wrong

Simulator becomes too difficult. If the LLM judge is weak or the penalty weight lambda is too small, GRPO may drive the simulator to generate impossible tasks. Agents then fail not from poor training but from unfair tests. Mitigation: tune lambda and validate that the judge's maintainability scores correlate with actual task solvability.
Behaviors leak into each other. If the four behavior types (unavailable, digression, impatience, incomplete) are not clearly separated in the prompts, the simulator may conflate them—generating a digression that is also incomplete, making the behavior type ambiguous. This obscures which weakness the agent actually has. Mitigation: use distinct LLM prompts and sample behaviors independently per turn.
Hallucination reward feedback loop. If the LLM judge relies on the agent's dialogue output to score maintainability, a hallucinating agent may trick the judge into high scores (agent claims success even when the task is unsolvable). The simulator then optimizes to reward hallucination patterns. Mitigation: ground the judge's scoring in the actual API responses and task state, not the agent's claims.
Done right: task remains achievable. When the LLM judge is well-calibrated and lambda is tuned, the simulator generates realistic friction—users request unsupported features, digress, rush, and speak incompletely—while preserving enough information and viable paths for a competent agent to complete the task. Agents trained on this simulator exhibit genuine weakness patterns (hallucinations when uncertain, dialogue breakdowns under rapid-fire impatience) that mirror real-world failures.
What a runnable demo should prove

What a runnable demo should prove

Build a mini dialogue environment: an agent with access to two APIs (e.g., restaurant retrieve and book). Create two user simulators running in parallel—one fully cooperative, one with non-collaborative behaviors injected. Run the same agent against both for 20 dialogues each. Log the success rate, the number of hallucinated promises, and the dialogue breakdowns (agent says I am working on it but loops infinitely).

weakness_exposure = (cooperative_success - noncoop_success) / cooperative_success * 100

The demo must make it impossible to miss that non-cooperative users expose agent failures invisible in cooperative settings.
