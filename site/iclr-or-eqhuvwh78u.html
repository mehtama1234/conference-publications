Rational Agents that Explore and Act Like People

Language models can ask smarter questions and make better decisions by planning which pieces of information would shrink their uncertainty the most.

Paper explainersAll themesAgents & Tool Use

When a language model is trying to solve a puzzle with limited chances to ask questions or take actions, it usually makes poor choices: asking questions that don't narrow down the answer, or shooting at random instead of where information suggests the target is. This paper shows that by having the model think through which pieces of information would help most, it can ask better questions and make better decisions.

Zero assumption version

The world before this paper

When a language model plays a game like Battleship—where you have limited guesses to find a hidden target—it does not think strategically. A person would ask careful questions: 'Is the ship in the top half?' gets a yes-or-no answer that either cuts the search space in half. A language model instead asks random questions like 'Is it at position (2,3)?', which is low-value.

The problem runs deeper: when the model does get an answer, it often forgets or ignores what was said before. It generates questions that don't build on what it has already learned. It takes shots at spots that haven't actually been ruled out. The model does not learn from what it has already discovered.

The naive model asks low-value questions and ignores clues it has already learned. The paper teaches the model to ask questions that shrink its uncertainty the most and to act on what it has learned.

The algorithm as a flow

What it actually does

Plan what to ask

For each possible question, ask: if I learn the answer, how much would I learn?

Score by information gain

Pick the question where the answer would shrink your uncertainty the most.

Learn from answers

When you get an answer, remember it and update what you know.

Plan where to act

For each possible action (like shooting a spot), predict the payoff if you act.

Act decisively

Shoot at the spot most likely to hit, based on everything you have learned.

What the paper changes

The one thing the paper changes

The paper does not retrain the language model. Instead, it gives the model a planning tool: when asked to decide what to do, the model runs a calculation called Bayesian Experimental Design. This calculation estimates what the model would learn from each possible question, and scores actions by how likely they are to succeed.

the object it moves  =  Planning algorithm wrapped around the model
The hidden quantity

The hidden quantity: expected information gain

measured quantity  =  Expected information gain

Before the paper, the model had no measurement of whether a question was good or bad. This paper measures something new: for each question you could ask, how much would you learn if you asked it? This is called expected information gain. It is a number (in bits or other units) that measures: if I learn the answer to this question, how much would my uncertainty shrink?

The paper estimates this by having the model consider all the possible answers, work out which ones it would believe and which it would doubt, and add up how much knowledge each possible answer would give. Questions that cut the search space in half score high; questions that only rule out one thing score low.

Why it works

Why it works: the causal chain

The model's core problem is that it does not know which information matters. By computing expected information gain, the method shows the model exactly what it should care about: it ranks candidate questions by how much they would narrow down the answer. Questions that split the remaining possibilities roughly in half rise to the top; questions that probe tiny details sink to the bottom.

This changes behavior in two ways. First, when the model is asked what to ask, it picks the high-scoring question instead of a random guess. Second, because the model is now forced to think through the logic ('If I ask X, what would I learn?'), it becomes more careful: it notices when an answer contradicts what it already knows, and it anchors its next actions to the clues it has gathered. The paper shows this forces the model to ground its reasoning in context, making it forget less and infer more accurately.

Math after the picture

The equation

First in words:

Expected information gain equals the average amount you shrink your uncertainty. For each possible answer to a question, work out how likely it is, imagine what you would believe if you saw it, measure your remaining uncertainty about the target, weight it by the answer's likelihood, and sum across all answers.

Then the compact form:

EIG(q) = H(Y) - sum_a P(a|context) * H(Y|a,context)

Every symbol:

EIG(q)expected information gain from asking question q
H(Y)your current uncertainty about the target (in bits)
qthe question you are considering
aa possible answer to that question
P(a|context)how likely that answer is, given what you already know
H(Y|a,context)your remaining uncertainty if you see that answer
A tiny worked example
You are searching a grid. Current uncertainty: 6.64 bits (ship could be in 100 squares, log2(100)=6.64).
Question A: Is ship in top half? Answer yes or no, each 50% likely. If yes: 50 squares left, H=5.64 bits. If no: same. EIG = 6.64 - 0.5*5.64 - 0.5*5.64 = 1.0 bit (you learn a lot).
Question B: Is ship at (5,5)? Answer yes or no; yes is 1% likely. If yes: 1 square left, H=0 bits. If no: 99 squares, H=6.63 bits. EIG = 6.64 - 0.01*0 - 0.99*6.63 = 0.01 bits (you learn almost nothing).
Question A scores 1.0 bits; Question B scores 0.01 bits. Model picks A, the smart question.

Information gain measures how much a question shrinks your uncertainty. Questions that split the space evenly score highest; questions that probe remote spots score lowest.

What can go wrong

What can go wrong

Poor uncertainty estimates. If the model's estimates of how likely each answer is don't match reality (e.g., it thinks a certain outcome is 10% likely but it is actually 1%), the information gain calculation becomes misleading, and it will pick the wrong questions.
Computation cost. Computing expected information gain for every candidate question and answer requires running the model many times. For large search spaces or limited time, this can become slow.
Model still struggles with very long context. Even with planning, if the model's context window (the amount of conversation it can hold) is small, it may still forget important clues over many rounds of questioning.
Works best with structured domains. The method shines in well-defined games or scientific tasks with clear targets and discrete answers. In messy, open-ended tasks, information gain is harder to measure.
What a runnable demo should prove

What a runnable demo should prove

Build a Battleship game where a language model must find a ship on a ten-by-ten grid in 20 questions. In round 1, have the model generate 10 candidate questions, score each by expected information gain, and pick the top one. In round 2, feed back the answer and repeat. Track: how many questions it asks before finding the ship, and how many times it asks a question that has already been answered or that contradicts what it has already learned. Run the same model without planning to show the gap.

efficiency = (questions asked to find ship / 20) × 100; grounding = (answered or contradicted questions / total questions) × 100

The demo must make it impossible to miss that planning forces the model to ask questions that split the remaining possibilities roughly in half (narrowing search faster), that grounding the model in context prevents it from forgetting or contradicting itself, and that a weaker model with this discipline outperforms a stronger model without planning (because reasoning through each move matters more than raw intelligence).
