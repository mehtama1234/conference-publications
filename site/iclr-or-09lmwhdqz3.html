CRAMF: Concept-Driven Retrieval for Automated Formalization

Build a lookup book by translating every formal definition in a math library to plain English, then use it to hand the LLM real definitions before it writes code, so it stops inventing fake ones.

Paper explainersAll themesLLMs & Foundation Models

Turning a math proof written in English into formal code that a theorem prover can verify (a process called formalization) matters for mathematics but is tedious. Large language models can automate it but they hallucinate: they invent fake mathematical definitions, use the wrong names, or reference code that does not exist. CRAMF solves this by building a special lookup book ahead of time. The book maps from English math concepts to the exact formal definitions that exist in Mathlib (a large math library). When the LLM is asked to formalize a new proof, CRAMF looks up the real definitions and hands them to the LLM in the prompt, so it can copy real code instead of inventing.

Zero assumption version

LLMs invent definitions that do not exist

Formalization means converting an English math proof like 'the sum of two even numbers is even' into formal code that a theorem prover can check. The code must use the exact function names and definitions from the math library. The LLM has never seen most of those names and invents plausible-sounding ones instead: functions that do not exist in the library, wrong symbol names (calling something add when the library calls it plus), or outdated names from old versions.

A naive try: give the LLM the English proof and ask it to guess. It guesses wrong. Another approach: include all 26,000 definitions from the library in the prompt. Too much noise; the LLM drowns in irrelevant code and still guesses. The real problem is that the LLM has no way to look up which definitions it actually needs.

In one sentence. The LLM must link English math concepts to exact formal definitions but has no lookup book to find them.

The algorithm as a flow

What it actually does

Build the lookup book

Scan all 26,000 definitions in Mathlib. Use a model to write plain-English descriptions of each one.

Extract the core concepts

Read the new English proof. Find which math concepts need formal definitions.

Query with context clues

Search the lookup book by both meaning and keywords, but add context clues (math area, use case) to pick the right one when a concept has several meanings.

Rerank the results

Combine both search channels to put the single best match on top.

Hand definitions to LLM

Include the real definitions in the prompt before asking the LLM to write formal code.

The hidden quantity

Retrieval precision: ranking the correct definition first

measured quantity  =  how often the right formal definition ends up at the top

When you search for a definition by name or meaning, you need the right answer to rank first. Mathlib has over 26,000 definitions across 1,000 core concepts. Many concepts have multiple meanings: norm can mean the length of a number list, the size of a grid, or a formal structure, depending on context. A naive keyword search for norm returns hundreds of hits. Retrieval precision measures how many of the top results are actually usable—whether the right definition appears in the top 5 or gets buried.

This matters because if the LLM sees only weak or wrong matches, it falls back to inventing. The paper measures precision by checking whether the formalization succeeds when only the top-ranked definitions are included in the prompt. High precision means the LLM gets the real definitions it needs; low precision means it drowns in noise.

Plain reading. Imagine a dictionary with 26,000 entries. You ask for the definition of a word that has 3 meanings. Precision is how high the correct meaning ranks in the results. Rank 1 is perfect. Rank 1000 means you missed it.
Paper reading. CRAMF uses two simultaneous lookups. One converts the English concept into a list of numbers that captures its meaning and finds similar lists in the lookup book (semantic search). One does keyword matching with domain context added (syntactic search). Both results are combined and reranked by a second model to push the correct definition to the top.
Why it works

Why the real definitions trick works

Language models are excellent at copying and remixing text they have seen; they are terrible at inventing definitions from scratch. When you give the LLM a list of correct definitions first—the actual names and signatures from Mathlib for even, add, divisible—you remove the need to invent. The LLM can now cite real code. This is radically simpler than asking the LLM to guess.

The hard part is finding the right definitions among 26,000. CRAMF solves this by preprocessing. Before any new proof arrives, the paper builds a lookup book by running every Mathlib definition through a model, which writes a plain-English description of what each formal code means. This is called back-translation: formal code to English. One English concept can point to multiple definitions (that is conceptual polymorphism—the same word means different things). When a new proof arrives, CRAMF extracts the concepts it mentions, then looks each one up using both semantic search (meaning-based) and keyword search, enhanced with context clues about which area of math the proof is in. A reranking step puts the single best definition on top. The real definitions go into the LLM prompt, and the LLM writes code using names that actually exist.

Math after the picture

Formalization accuracy with real definitions

First in words:

accuracy equals the count of proofs the theorem prover accepts divided by total proofs tried

Then the compact form:

accuracy = (1 / N) * sum_i verified_i

Every symbol:

accuracyfraction of proofs that the theorem prover accepts
Ntotal number of proofs attempted
verified_i1 if proof i passes the prover, 0 otherwise
A tiny worked example
Baseline (LLM alone, no lookup): 100 proofs attempted. LLM invents wrong definitions for 60. Prover rejects 60. Accuracy: 40 out of 100 is 40 percent.
With CRAMF (definitions looked up): same 100 proofs. LLM has real definitions now. Invents wrong names for only 6 hard cases. Prover accepts 94. Accuracy: 94 out of 100 is 94 percent.
Gain: 94 minus 40 equals 54 points. The paper reports on average 29.9 points gain; on the hardest test 62.1 points. Lookup cuts inventing by 2 to 3 times.

Real definitions in the prompt let the LLM copy instead of invent. Fewer invented names survive to the prover; accuracy jumps.

What can go wrong

What can go wrong

Same word, many meanings. The word norm means different things in different fields. Even with context clues, when a concept is truly polymorphic, lookup might return the wrong branch. The reranking helps but is not perfect.
Library changes over time. Mathlib evolves. A definition used in the lookup book might get renamed, moved, or deleted in a newer version. If the prover is running a different version than the lookup book was built from, matched definitions fail.
No definition in the library. If the proof uses a concept that is very new or very obscure and not yet in Mathlib, lookup finds nothing. The LLM has no fallback and must invent.
Done right: two-channel lookup plus reranking. When semantic and keyword searches run together and both results are reranked, the correct definition usually lands in the top 5. That is enough for the LLM to find it.
What a runnable demo should prove

What a runnable demo should prove

Take 20 English math statements from different areas (one-to-one functions, reversible operations, even division, set membership). For each, run the LLM alone and count how many the theorem prover accepts. Then run CRAMF: look up real definitions, pass them in the prompt, count acceptances. The demo works if CRAMF improves the acceptance rate by at least 30 percent.

improvement_percent = 100 * (accuracy_with_CRAMF - accuracy_baseline) / accuracy_baseline

The demo must show that looked-up real definitions prevent the LLM from inventing fake names and let it cite library code instead.
