CRAMF: Concept-Driven Retrieval for Automated Formalization

Build a lookup book by translating every formal definition in a math library to plain English, then use it to hand the LLM real definitions before it writes code, so it stops inventing fake ones.

Paper explainersAll themesLLMs & Foundation Models

Turning a math proof written in English into formal code that a theorem prover can verify (a process called formalization) matters for mathematics but is tedious. Large language models can automate it but they hallucinate: they invent fake mathematical definitions, use the wrong names, or reference code that does not exist. CRAMF solves this by building a special lookup book ahead of time. The book maps from English math concepts to the exact formal definitions that exist in Mathlib (a large math library). When the LLM is asked to formalize a new proof, CRAMF looks up the real definitions and hands them to the LLM in the prompt, so it can copy real code instead of inventing.

Zero assumption version

LLMs invent definitions that do not exist

Formalization means converting an English math proof like 'the sum of two even numbers is even' into formal code that a theorem prover can check. The code must use the exact function names and definitions from the math library. The LLM has never seen most of those names and invents plausible-sounding ones instead: functions that do not exist in the library, wrong symbol names (calling something add when the library calls it plus), or outdated names from old versions.

A naive try: give the LLM the English proof and ask it to guess. It guesses wrong. Another approach: include all 26,000 definitions from the library in the prompt. Too much noise; the LLM drowns in irrelevant code and still guesses. The real problem is that the LLM has no way to look up which definitions it actually needs.

In one sentence. The LLM must link English math concepts to exact formal definitions but has no lookup book to find them.

The algorithm as a flow

What it actually does

Build the lookup book

Scan all 26,000 definitions in Mathlib. Use a model to write plain-English descriptions of each one.

Extract the core concepts

Read the new English proof. Find which math concepts need formal definitions.

Query with context clues

Search the lookup book by both meaning and keywords, but add context clues (math area, use case) to pick the right one when a concept has several meanings.

Rerank the results

Combine both search channels to put the single best match on top.

Hand definitions to LLM

Include the real definitions in the prompt before asking the LLM to write formal code.

The hidden quantity

Retrieval rank: where the right definition lands

measured quantity  =  rank of the correct formal definition in the retrieval results

When you search for a definition by name or meaning, you need the right answer to land near the top. Mathlib has over 26,000 definitions across 1,000 core concepts. Many concepts have multiple meanings: norm can mean the length of a number list (vector norm), the size of a grid (matrix norm), or a formal algebraic structure (normed field), depending on context. A naive keyword search for norm returns hundreds of hits in random order. Retrieval rank measures whether the correct definition appears as the 1st result, or the 5th, or gets buried at position 100.

This matters because the LLM can only use definitions it can see. If the correct definition is buried in position 50, the LLM cannot use it and invents instead. The paper measures rank by checking: for 26,000 test lookups, at what position does the correct definition land? With CRAMF's dual-pathway search (semantic plus keywords) plus reranking, the correct answer usually lands in the top 1 to 5. Without it, the correct answer lands at position 40 to 100.

Plain reading. A library catalog has 26,000 books. You search for a title that has 10 different meanings. Rank measures whether the book you want is the 1st result (rank 1) or buried at position 87 (rank 87). Rank 1 is success. Rank 1000 means you never find it.
Paper reading. CRAMF retrieves each concept in two simultaneous ways: semantic search (turns the English concept into a numerical fingerprint and finds closest matches) and syntactic search (keywords plus domain context). A reranking model combines both, scores all candidates, and outputs a ranked list. Correct definitions move to the top ranks. The LLM sees only the top results and can cite them.
Why it works

Why grounding definitions prevents invention

The core idea is simple: language models are excellent at copying text they have already seen, but terrible at inventing definitions from scratch. The word even has a formal definition in Mathlib: it says exactly which numbers count as even. If you hand that definition to the LLM and ask it to write code, the LLM copies it. If you do not hand it over, the LLM guesses and makes up a fake. Copying is reliable. Guessing is not.

The hard mechanical step is finding the right definition fast from a pile of 26,000. CRAMF does this in two stages. First, offline: scan every Mathlib definition once, use a model to write plain-English descriptions (called back-translation), and store the mapping. Second, at query time: extract the concepts from the new proof, search the lookup book by both meaning (semantic) and keywords (syntactic), add context clues to disambiguate when one word has many meanings, rerank the results, and pass the top-ranked definitions to the LLM. The LLM now has real names and copies them instead of inventing.

A tiny worked example
Without lookup (baseline): LLM writes code for 100 theorems. Invents wrong definitions or function names for 60 of them. Prover rejects those 60. Accepts 40. Rate: 40 per 100 = 40 percent.
With CRAMF lookup: same 100 theorems. LLM has real definitions handed to it. Invents wrong names for only 6 hard edge cases. Prover accepts 94. Rate: 94 per 100 = 94 percent.
Improvement: 94 minus 40 equals 54 percentage points. Paper reports averages of 29.9 points across benchmarks, and 62.1 points on the hardest set. Lookup suppresses invention by 70 to 90 percent.

Handing the LLM real definitions prevents invention. Without lookup, the LLM makes up names and the prover rejects them. With lookup, the LLM copies real names and the prover accepts.

What can go wrong

What can go wrong

Same word, many meanings. The word norm means different things in different fields. Even with context clues, when a concept is truly polymorphic, lookup might return the wrong branch. The reranking helps but is not perfect because it combines semantic and keyword scores via a learned model, which can still misweight candidates if the test context is ambiguous or from a domain the model has not seen much.
Library changes over time. Mathlib evolves. A definition used in the lookup book might get renamed, moved, or deleted in a newer version. If the prover is running a different version than the lookup book was built from, matched definitions fail.
No definition in the library. If the proof uses a concept that is very new or very obscure and not yet in Mathlib, lookup finds nothing. The LLM has no fallback and must invent.
Done right: two-channel lookup plus reranking. When semantic and keyword searches run together and both results are reranked, the correct definition usually lands in the top 5. That is enough for the LLM to find it.
What a runnable demo should prove

What a runnable demo should prove

Take 20 English math statements from different areas (one-to-one functions, reversible operations, even division, set membership). For each, run the LLM alone and count how many the theorem prover accepts. Then run CRAMF: look up real definitions, pass them in the prompt, count acceptances. The demo works if CRAMF improves the acceptance rate by at least 30 percent, because in the paper's full test sets, grounding produces a 29 to 62 percentage-point jump — so a 30-point improvement on a small demo is a conservative bar that matches real performance.

improvement_percent = 100 * (accuracy_with_CRAMF - accuracy_baseline) / accuracy_baseline
