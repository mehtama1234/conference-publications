CoLLMLight: Cooperative Large Language Model Agents for Network-Wide Traffic Signal Control

Traffic signals at intersections learn to coordinate across a whole network by having each signal's reasoning process run asynchronously and feed guidance back to the real-time decisions.

Paper explainersAll themesAgents & Tool Use

Traffic in a city flows through many intersections, and each intersection's signal decisions ripple across the whole network. Most LLM agents treat each intersection in isolation, deciding its signal timing without considering what neighboring intersections need. CoLLMLight runs a separate reasoning process for each intersection that thinks about neighboring traffic patterns asynchronously—without blocking real-time decisions—and caches guidance that shapes the actual signal timing. This lets agents cooperate across the network while keeping decisions fast.

Zero assumption version

Treating each intersection like an island

Consider a city block with five intersections. If each intersection's signal decides its own timing in isolation—only looking at its own queue length—cars pile up at one intersection because the upstream signal is green when it should be red, and nobody told it to change. Traffic is a network: a decision at intersection A affects intersection B two blocks away.

A beginner might try: run an LLM at each intersection, feed it the local queue length, and let it decide when to switch the light. This works okay for one isolated junction, but in a real network, the LLM at intersection A has no idea that intersection B is about to flood it with cars. By the time A sees the incoming cars, it is too late to prepare.

The problem in one sentence. Each intersection makes decisions alone without knowing what other intersections need, so traffic cannot be optimized across the whole city.

The algorithm as a flow

What it actually does

Each intersection runs two processes in parallel.

One makes real-time signal decisions in milliseconds; the other thinks deeply about cooperation without rushing.

The reasoning process looks at neighboring intersections.

It predicts how many cars will arrive from neighbors and what timing would help them move smoothly.

Reasoning output is cached as guidance.

The slow thinking result is stored and reused for the next few seconds, not re-computed on every decision.

Real-time decisions read the cached guidance.

When the light must switch right now, the fast decision-maker checks: does my neighbor need me to stay green or flip to red?

Training adjusts which intersections listen to which neighbors.

Reinforcement learning rewards network-wide smooth flow and penalizes reasoning that takes too long or uses too much computation.

What the paper changes

What the paper changes

The paper moves the reasoning process out of the critical path. Instead of deciding on the fly, it thinks asynchronously and feeds guidance into real-time decisions. This lets intersections reason deeply about neighbors without blocking millisecond-level signal timing.

the object it moves  =  reasoning timing: asynchronous, cached
The hidden quantity

The hidden quantity: cooperation guidance quality

measured quantity  =  cooperation guidance quality

The paper measures an invisible quantity: how good is the guidance that one intersection's reasoning produces for its neighbors? Good guidance steers the real-time decision maker toward timing that helps the whole network. Bad guidance is either wrong predictions of neighbor traffic, or suggestions that contradict the urgent local need.

The paper estimates this by running reinforcement learning: it gives rewards when the whole network waits less (cars spend less time in queues), and penalties when the reasoning process wastes computation or text generation. Over time, the LLM learns which neighbors matter and what guidance actually moves traffic.

Why it works

Why asynchronous reasoning + cached guidance work

Real-time decisions must happen in milliseconds—the signal cannot wait for deep reasoning. But deep reasoning takes seconds. The trick is to run them in separate processes. The reasoning process thinks about the network constantly, updates its predictions of what neighbors will need, and caches those predictions. The real-time process reads the cache in milliseconds. Because the cache was computed while the reasoning process was not waiting for anything, the real-time process gets the benefit of deep thinking without the delay.

The guidance shapes decisions by acting as a tie-breaker. When the real-time decision is ambiguous—should I flip the light now or wait two more seconds?—the cached guidance says: my neighbor sent a prediction that they need priority soon. So the real-time process follows the guidance. This makes intersections coordinate without blocking each other.

Reinforcement learning trains the LLM to send good guidance and adjust reasoning depth. If an intersection's guidance consistently makes the network slower, the reward signal drops, and the LLM learns to either predict differently or focus reasoning on the neighbors that actually matter. Token-based penalties prevent reasoning from bloating—if an intersection spends 1000 chunks of text on a prediction that does not improve throughput, the penalty teaches it to reason faster next time.

Math after the picture

The cooperation guidance signal

First in words:

Each intersection receives a cooperation signal from each neighbor. That signal is the sum of a traffic prediction and a reasoning cost penalty. The traffic prediction predicts how many vehicles will arrive at this intersection from that neighbor in the next time window. The reasoning cost is how many tokens and computation steps it took to make that prediction. The final guidance weight trades off prediction accuracy against reasoning budget.

Then the compact form:

G_ij = Pred_ij - beta * Cost_ij where Cost_ij = alpha * (tokens_used + computation_steps)

Every symbol:

G_ijguidance quality from intersection i to intersection j
Pred_ijprediction of vehicles arriving at j from i
betatrade-off: how much to penalize extra reasoning cost
Cost_ijreasoning cost in tokens and steps
alphascaling factor to make cost comparable to prediction magnitude
tokens_usednumber of tokens the LLM generated for this prediction
computation_stepsnumber of forward passes through the model
A tiny worked example
Intersection A reasons about Intersection B. Prediction: 45 vehicles will arrive in 30 seconds.
The reasoning used 200 chunks of text and 8 forward passes. Cost = 1.0 * (200 + 8) = 208.
With beta = 0.1 and alpha = 1.0: G_AB = 45 - 0.1 * 208 = 45 - 20.8 = 24.2.
Guidance to B is 24.2. Intersection B's real-time signal reads this: there is moderate but confident help coming from A.
If reasoning had used only 50 chunks of text (faster model), Cost = 50, G_AB = 45 - 5 = 40. B receives stronger guidance. So faster thinking is rewarded.

The formula shows the core trade-off: good predictions help the network, but computing them costs chunks of text. Training learns the right beta to balance speed and accuracy.

What can go wrong

What can go wrong

Stale guidance misleads real-time decisions. If the cached prediction is old, it may not match current traffic. A sudden accident upstream changes the flow, but the real-time decision is still reading yesterday's guidance. The paper uses time stamps and adaptive cache invalidation to address this: guidance older than a few seconds is discarded.
Reasoning cost spirals out of control. The LLM might use 5000 chunks of text to predict traffic a minute away, when 200 chunks of text would have given almost as good a guess. Without the cost penalty in the reward function, the model wastes computation. The reinforcement learning reward must penalize chunk of text bloat.
Circular dependency: A waits for B, B waits for A. If two intersections send guidance that contradicts each other, the real-time decisions deadlock. The paper avoids this by making the real-time decision layer never fully trust guidance—it reads cached guidance as a hint, not a command. Local urgency (long queue at this intersection) always overrides guidance.
Done right: guidance is a suggestion, not a law. The real-time decision uses guidance to break ties, but if this intersection's own queue is urgent, it acts on the local need. This ensures the network never deadlocks and always keeps intersections moving.
What a runnable demo should prove

What a runnable demo should prove

Build a small network of three to five intersections. Simulate arriving cars with realistic patterns: morning rush (more cars arrive west-bound), midday, evening (more cars exit the downtown). Run two versions side by side: (1) isolated LLM agents at each intersection, each deciding alone; (2) CoLLMLight with asynchronous cooperation. Measure the total time all cars spend waiting in queues.

total_wait_time = sum over all cars of (time_car_entered_queue_to_time_car_left_queue); compare isolated vs cooperative

The demo should make it impossible to miss that cooperation reduces total wait time, and that this improvement comes from intersections sending each other traffic predictions asynchronously, not from increasing the latency of real-time decisions.
