SP-VLA: Joint Model Scheduling and Token Pruning for Robotic Speed

A robot thinks fast when the next action is routine, and slow when it truly needs to decide.

Paper explainersAll themesRobotics & Control

Vision-Language-Action models let robots understand images and generate the right physical movements. But they run slowly, sending every image through the full model every time, which is too sluggish for real-world robotic tasks. SP-VLA accelerates these models by routing simple, repetitive actions through a lightweight fast-pass, while routing tricky decisions through the full model. It also removes redundant visual data that does not matter for the current action.

Zero assumption version

Robots choke on overhead

A robot that sees and acts must first convert each camera image into numbers, then run those numbers through a big model to generate the next movement command. This takes time, maybe half a second or more per image. Real robots picking objects or navigating need to react faster, roughly every 50 milliseconds, because objects move and hands need frequent updates. Running the full model every time burns so much compute the robot misses these deadlines.

A simple fix would be to use a smaller, faster model instead. But smaller models have less understanding of the image and scene, so they produce jerky or unsafe actions. The robot trades speed for accuracy, and with lives at stake, neither outcome is acceptable.

The core move. Route easy actions through a fast, lightweight model and hard actions through the full model.

The hidden quantity

Action difficulty

measured quantity  =  whether an action needs full reasoning

The paper measures a hidden property of each action: how much thinking does this movement need? Routine actions like continuing to grip an object require less. Risky actions like approaching a new part of the scene require more thought.

The paper learns this by training a small network (a classifier) that looks at the image and the last few past actions to predict: deliberative or intuitive. When running the robot later (after training finishes), the predictions guide which path each action takes through the system.

Why it works

Why it works

The core insight is that robot actions in a sequence are not independent. Many steps in a task are repetitive or follow a pattern. A robot gripping an object does not need to reanalyze the full scene every 10 milliseconds; it can execute the grip routine on intuition. Only when something changes—a new object appears, the grip fails, navigation starts—does the robot need the full model.

By routing routine actions through a lightweight model, the system cuts compute by 40 to 60 percent while keeping the same latency for hard decisions, because the lightweight model runs faster and still produces safe actions for well-learned patterns. The pruning of image data removes visual noise: if this action is about continuing to grip, the system does not need to analyze distant walls or irrelevant objects. Fewer pieces of image data mean faster processing because the model has fewer numbers to read and think about, and it stays focused on what matters.

Math after the picture

The routing rule

First in words:

latency equals the sum of classification time plus model time plus pruning time, weighted by how often each path is taken

Then the compact form:

L_total = w_routine * L_lightweight + w_deliberative * L_full + L_classify + L_prune

Every symbol:

L_totaltotal latency per action
w_routinefraction of actions classified as routine
w_deliberativefraction classified as deliberative
L_lightweightcompute time for lightweight model (milliseconds)
L_fullcompute time for full model (milliseconds)
L_classifytime to run action classifier (fixed, small)
L_prunetime to prune image tokens (proportional to pruning rate)
A tiny worked example
Suppose 70% of actions are routine, 30% hard.
Lightweight model runs in 15 ms; full model in 50 ms.
Classification takes 2 ms; pruning takes 1 ms.
L_total = 0.7 * 15 + 0.3 * 50 + 2 + 1 = 10.5 + 15 + 3 = 28.5 ms.
Without routing (full model always): 50 + 2 + 1 = 53 ms.
Speedup: 53 / 28.5 = 1.86× faster.

The faster a lightweight model is, and the higher the fraction of routine actions, the bigger the speedup, because you replace slow operations with fast ones more often.

What can go wrong

What can go wrong

Action classifier mislabels. If the classifier wrongly calls a hard action routine, the lightweight model produces a poor movement and the robot fails. The fix is careful training of the classifier on many different task demonstrations.
Over-pruning image data. If important visual details are removed, the model loses context. Example: if the system strips away pixels showing a nearby obstacle while the robot is navigating, the lightweight model cannot see it and might bump into it.
New tasks and new places. If the robot encounters a task or environment very different from training, the classifier may mislabel actions, breaking both the speedup and safety, because the patterns it learned no longer apply.
Done right. The action classifier must work well when scene and lighting change slightly. Pruning rules must always keep image data for places where the robot could collide or fail. Lightweight model must actually run fast with no hidden delays.
What a runnable demo should prove

What a runnable demo should prove

Build a simple robotic task: a simulated arm that moves between three goal positions in sequence. Train the action classifier on 100 demonstrations. Measure: (1) latency per action on the lightweight path versus the full path, (2) success rate on a held-out test sequence, (3) the speedup ratio (time without routing divided by time with routing).

speedup = latency_full_model / latency_sp_vla

If the demo runs without the routing logic, the speedup should be close to 1 (no benefit). If routing is active and the classifier is trained, speedup should exceed 1.3-fold with the same success rate.
