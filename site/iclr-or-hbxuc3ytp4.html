GrAlgoBench: Exposing Reasoning Model Weaknesses via Graph Algorithms

A benchmark of graph algorithm problems reveals that large reasoning models collapse on long inputs and waste computational effort thinking without improving correctness.

Paper explainersAll themesDatasets & Benchmarks & Evaluation

Large reasoning models (language models trained to solve hard problems step by step) have impressed us with their ability to solve math and coding challenges. But our tests usually cover small problems, and the models often guess right without showing clear thinking. This paper introduces a benchmark of graph algorithm problems (like finding the shortest path or detecting cycles in a network) that exposes two major cracks: the models get much worse when the graphs are large, and they spend enormous effort double-checking their work without actually fixing mistakes.

Zero assumption version

Why existing tests are not enough

When we test reasoning models today, we typically give them small math problems or short pieces of code. The model works through the solution step by step, and we check if the final answer is right or wrong. But this setup misses two things. First, it never pushes the model with genuinely large contexts (imagine describing a graph with hundreds of nodes and edges in plain words; that is a lot of text to hold in mind). Second, it does not tell us whether the model is thinking clearly or just guessing, and it doesn't let us measure the quality of the reasoning trace itself.

A beginner might assume reasoning models just need harder problems to improve, because harder problems make people think harder. But the real issue is deeper: we do not have a way to precisely control problem difficulty, verify answers automatically (most reasoning tests rely on human judgment), or see where the thinking breaks down. Graph algorithms are perfect for fixing this, because they are easy to describe with fine-grained difficulty control (number of nodes and edges), impossible to solve by luck (you cannot guess a correct shortest path in a 500-node graph), and completely checkable by running the code (no human judgment needed).

The method in one sentence. Build a benchmark where each problem is a graph algorithm task that gets progressively harder, and check answers by running the model's solution as code.

The algorithm as a flow

What it actually does

Pick a graph algorithm task

Choose from nine tasks: shortest path, cycle detection, connectivity, spanning tree, and others.

Create graphs of increasing difficulty

Build graphs with 10, 50, 120, 500, or 1000 nodes; vary edge density and structure.

Feed the graph description to the model

Write the graph in plain language, then ask the model to solve it step by step.

Run the model's answer as code

Parse the solution, execute it, and check programmatically whether it is correct.

Measure two things

Count the reasoning steps (trace length) and track whether they helped; score the final answer.

What the paper changes

What the benchmark measures

The benchmark isolates two things: how well models handle long contexts (large graphs described in many words) and how much effort models waste on self-verification that does not actually improve answers. Context length matters because a longer text input makes it harder for the model to remember all the details (like which nodes are connected), and waste happens because models spend huge effort re-reading their own reasoning without catching the underlying error.

the object it moves  =  reasoning traces and context length
The hidden quantity

The over-thinking penalty

measured quantity  =  unnecessary reasoning steps that do not lead to correctness

When a model solves a problem, it outputs a sequence of steps: analyzing the graph, applying an algorithm, double-checking, re-analyzing, and so on. The hidden quantity here is how many of those steps are wasted effort. A step is wasted if removing it would not change the final answer. The paper measures this by comparing the length of the reasoning trace to the accuracy, and seeing whether longer traces (more self-verification) correlate with better answers or just noise.

The benchmark discovers that over-thinking (long traces with extensive self-verification) is common but does not help, because verification re-uses the same flawed memory that produced the error in the first place. In fact, models spend up to 70% of their reasoning effort on re-checking that does not fix errors. This is not a fault of the model trying too hard; it is a sign that the model is not tracking what went wrong in the first place (missing edges, forgotten nodes), so re-reading the same text cannot actually correct it — there is no fresh information to change the conclusion.

The core error persists

Darker steps do real work; lighter steps are duplicate effort. Verification loops rarely catch the core mistake.

Plain reading. Imagine you solve a math problem wrong. You re-read your work three times, re-do the arithmetic, convince yourself it is right — then you hand it in. The re-reading felt thorough, but it did not catch the error. That is over-thinking: effort that feels productive but does not actually fix the mistake.
From the benchmark. The benchmark watches how long each reasoning trace is (number of steps) and whether adding more steps (more self-verification) leads to better answers. Longer traces do not help because they re-use the same focus (the mental mechanism that picks out which parts of the text matter most) and memory as the original reasoning, so they recycle the same mistake without new information. Across nine graph tasks, longer traces do not correlate with higher accuracy, because the extra steps are just repeating the flawed logic. In fact, many of the longest traces end with the same wrong answer they started with.
Why it works

Why long contexts break and verification does not help

The mechanism has two parts. First, long contexts: when a graph has 500 nodes, describing it in words creates a long text input. The model must hold all those edges and nodes in attention (a mental focus system that picks out which parts matter). Attention is expensive and gets weaker as sequences grow longer. So by the time the model works through the algorithm, it has forgotten earlier nodes or misremembered edge weights. That causes execution errors (like skipping a node or picking the wrong edge), which cascade into a wrong answer. Doubling the graph size does not just make the problem a bit harder — it makes the attention system lose critical information.

Second, self-verification: when a model second-guesses itself, it re-reads its own reasoning. But the re-reading process uses the same attention and memory that made the mistake in the first place. So it re-reads through the same lens, misses the same nodes, and arrives at the same conclusion. Verification is futile because it does not add new information or a fresh viewpoint; it just recycles the same flawed understanding. The model ends up running the same bad logic twice, without any hope of catching it.

Measuring accuracy loss with context size

First in words:

accuracy drops by a fraction for each doubling of graph size; failure rate is roughly one minus accuracy.

Then the compact form:

accuracy_loss = 1 - (correct_answers / total_answers); failure_rate = 1 - accuracy

Every symbol:

correct_answersnumber of problems solved with the right answer
total_answerstotal number of problems attempted
accuracy_lossthe fraction of problems answered wrong
failure_ratewhat we measure to show weakness
A tiny worked example
On 50-node graphs: model solves 90 problems right out of 100. Accuracy = 90/100 = 0.90. Failure rate = 1 - 0.90 = 0.10 (ten percent wrong).
On 120-node graphs: model solves 45 problems right out of 100. Accuracy = 45/100 = 0.45. Failure rate = 1 - 0.45 = 0.55 (fifty-five percent wrong).
The jump from ten percent to fifty-five percent failure across a 2.4× increase in graph size shows how sharply long-context performance collapses.

The benchmark plots accuracy against graph size and sees a steep cliff around 120 nodes, confirming that long-context reasoning is a fundamental bottleneck.

What can go wrong

What can go wrong

Attention bandwidth exhausted. The model forgets nodes as the graph grows. Even if the algorithm is correct in theory, the model misses edges or skips nodes because the text is too long to hold in focus. Adding more self-verification does not recover that lost information.
Execution errors cascade. A single missed edge early in the trace can derail the entire algorithm. The model detects the inconsistency during verification, realizes something is wrong, but cannot trace back to find the root cause. It re-verifies the same broken logic and gives up.
Self-verification is blind. When a model re-reads its reasoning, it uses the same memory and attention that produced the original mistake. There is no fresh perspective, no new data, and no way to catch an error that stems from forgotten information.
Short graphs work fine. On 10 to 50-node graphs, models stay accurate (above eighty percent) regardless of verification. The benchmark confirms that the problem is specifically long-context reasoning, not fundamental reasoning inability.
What a runnable demo should prove

What a runnable demo should prove

Build a simple test: ask a model to find the shortest path in a graph with 100 nodes. Collect the reasoning trace. Then ask the same model to verify its answer. Measure: (1) did the answer change after verification? (2) how many verification steps did the model take? (3) if the answer was originally wrong, did verification catch and fix it? Run this on graphs of size 10, 30, 100, and 300 nodes to see the accuracy collapse and the growing uselessness of re-checking.

verification_helped = 1 if (answer_changed and new_answer_is_correct) else 0; trace_length_ratio = steps_with_verification / steps_without_verification

The demo makes it impossible to miss: verification adds length but no correctness because it recycles flawed memory, and the problem is fundamentally about context length (which determines what the model can remember) not reasoning power.
