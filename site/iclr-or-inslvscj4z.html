RACE: Time Optimal Execution of Action Chunk Policies

Speed up robot policies trained by imitation learning by replanning when to execute action chunks instead of just executing them faster.

Zero assumption version

The speed trap in learning from observation

A robot learns by watching: a person uses a remote control to pick up a cup, and the robot records actions at each instant. The trained policy — the behavior learned from those records — executes actions at the same rate they were demonstrated. But demonstration is slow: a person controlling the robot remotely is careful and deliberate.

Naively speeding up seems simple: just run the policy's output faster. But this breaks because real robots obey physics. When you compress the timeline (ask for the same motion in half the time), the robot's arm cannot physically move fast enough to reach the target — motors have speed limits, so the arm simply does not get there. More subtly, when you ask for an action command, the robot's current state (position, velocity) has changed since the policy saw the old observation; the command was optimized for the old state, so executing it now is wrong. These two problems — physical reachability and stale state alignment — pile up and cause failures.

In one sentence. RACE replan when to execute action chunks, target desired positions instead of raw commands, and search test-time for actions that match the current state.

The algorithm as a flow

What it actually does

Shift target from actions to states

Instead of asking the policy to predict raw motor commands, retrain or reinterpret it as predicting desired goal positions the robot should reach.

Replan chunk timing

Given a desired goal position, compute how fast the robot's physics will let it move and reschedule when each action chunk fires to reach the goal on time.

Test-time search for aligned actions

At execution time, if the policy's predicted action is misaligned with the current state, search a small neighborhood of actions and pick the one that gives the robot the most control (highest controllability).

Execute and observe

Run the replanned, aligned action and read the new robot state. Loop back to predict the next goal.

Result: speed without failure

The robot reaches goal positions faster without overshooting or losing control because actions are replanned to match actual motor speed and aligned to the current state.

What the paper changes

The thing the paper changes

The paper shifts the learning target from raw actions (which are slow and brittle) to desired goal states (which work from any starting state and timing). It also replans when each chunk of actions fires to respect the robot's physical limits, and it searches test-time for actions most likely to work from the current state.

the object it moves  =  Execution timing and action alignment
The hidden quantity

Controllability: can the robot steer from here?

measured quantity  =  Controllability score

Controllability is a measure of how much the robot can steer its motion from the current state given an action chunk. Think of it as the robot's "steering budget": how much room do you have to adjust the trajectory? High controllability means the action, executed from this state, lets the robot respond to corrections. Low controllability means the action will take the robot into a corner where it cannot easily adjust.

The paper measures controllability at test time by scoring candidate action chunks: for each action, compute how much control authority remains for the upcoming steps. Pick the action with the highest score. This way, even if the policy predicted an action misaligned with the current state, a nearby action with better controllability is chosen instead because that action leaves the robot more room to correct and adapt.

Why it works

Why replanning + state targets + test-time search works

When a policy predicts actions at demo speed, it assumes each action will run for a fixed time and the robot will transition smoothly. Speeding up breaks this assumption: physics does not speed up, so the robot cannot complete the transition. By replanning when each action fires, the policy respects the robot's actual speed limits instead of pretending they do not exist.

Second, targeting goal states instead of raw commands decouples the timing from the specific trajectory. A goal position can be reached via many paths and at many speeds. The robot now has flexibility: reach the goal in whatever time frame is physically possible. This is why actions generalize: the robot is not married to the demo's exact path.

Third, at test time the robot's state may not match what the policy expected. A misaligned action could fail. Test-time search solves this by ranking candidate actions by controllability: actions that keep the robot in a state where it can still steer are favored. This is a safeguard against distribution shift (when the test situation differs from the training observations).

The acceleration formula

First in words:

Controllability score equals the minimum singular value of the state-transition Jacobian, multiplied by a safety margin. Pick the action in a neighborhood of the policy's prediction that maximizes this score.

Then the compact form:

c = min_singular(d_state / d_action) * margin

Every symbol:

cControllability score (how much the robot can steer)
d_state / d_actionHow much the robot state changes per unit action (the Jacobian derivative)
min_singularThe smallest singular value (the direction the robot steers worst in)
marginSafety buffer (ensures the robot stays in a controllable region)
A tiny worked example
Robot state: position 0.5 m, velocity 0.2 m/s.
Policy predicts action: grip strength 50.
Candidate actions: grip 45, 50, 55.
Controllability for 45: singular value 0.6, score = 0.6 * 0.9 = 0.54.
Controllability for 50: singular value 0.3, score = 0.3 * 0.9 = 0.27.
Controllability for 55: singular value 0.7, score = 0.7 * 0.9 = 0.63.
Pick action 55: highest controllability, best steering authority from current state.

The robot picks actions that leave the most room to steer, not the one the policy liked best.

What can go wrong

What can go wrong

Model mismatch. If the learned robot dynamics model is wrong, controllability scores will be wrong and actions may fail. Real robots have friction, backlash, and delays the model does not capture.
Prediction mismatch. If the policy was trained on slow demos and the test distribution (faster execution, different states) is far from training, the goal predictions themselves may be wrong because the policy never saw examples from the new regime and cannot generalize.
Boundary cases. When the robot is near a singularity (a position where some degrees of freedom cannot move), controllability is low everywhere and test-time search cannot save it.
Done right. Train the policy on diverse states and speeds, validate the dynamics model on real robot data, and set the safety margin conservatively so the robot stays in controllable regions.
What a runnable demo should prove

What a runnable demo should prove

Build a simple robot simulator (e.g., a 2-link arm in PyBullet reaching a target). Train a policy via imitation learning on teleoperated demos at normal speed. Then run RACE: replan timing, target goal states, and search test-time for high-controllability actions. Measure success rate and time-to-goal across speeds from 1x to 4x.

Speedup = demo_time / RACE_time, Success = (goals_reached / total_attempts) * 100
