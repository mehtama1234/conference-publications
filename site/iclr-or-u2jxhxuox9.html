ProofBridge: Auto-Formalization of Mathematical Proofs

ProofBridge translates human-written math proofs into computer-checkable formal proofs by learning to put English and formal languages into the same mental space, then using retrieved examples to guide the translation.

Paper explainersAll themesOther

Converting a human's hand-written mathematical proof into formal code (like Lean, which a computer can check) is hard because the human and the formal code say the same thing in almost completely different languages. ProofBridge builds a bridge: it learns a shared space where an English proof and its formal equivalent sit close together, like two translations of the same book. When asked to formalize a new proof, it finds similar formal proofs already in that space and uses them as examples because seeing a concrete proof in the same style teaches the translator what patterns to follow.

Why translating proofs is stuck

A mathematician writes a proof in English: clear, intuitive, human-friendly. A computer needs that proof written in Lean, a formal language where every single step is checked against strict rules—like the difference between writing a story and writing a computer program. Today, either humans manually translate every proof (slow and expensive), or the AI system generates formal proofs without seeing examples (and makes mistakes).

A naive approach might be: take an English proof, feed it to a big language model, and ask it to write Lean code. The model tries, but it gets lost. Formal proofs have a special structure (tactics, proof states, type signatures), and the model has never internalized that structure from examples. It generates code that looks syntactically right but means something different—like a translation that passes spell-check but says the opposite thing.

In one sentence. ProofBridge learns a shared space where English and formal proofs sit close together, then retrieves similar formal proofs as in-context examples to guide the translation.

The algorithm as a flow

What it actually does

Train the shared encoder

Feed both English and Lean proof pairs through separate encoders, push them close in shared space if they match.

Precompute the database

Encode all known English and Lean theorem-proof pairs once, store the encoded numbers for fast lookup.

Retrieve examples

Given a new English proof, find the top-K closest Lean proofs in the shared space by measuring similarity.

Fine-tune the translator

Train the LLM to convert English to Lean, conditioned on the retrieved formal examples as in-context demonstrations.

Repair and verify

Run the generated Lean code through the type checker; if it fails, fix it iteratively using feedback.

What the paper changes

What the paper changes

The paper changes the retrieval system: instead of searching for similar Lean theorems using raw text, it uses a joint embedding—a shared space where English and formal proofs live side by side, aligned by meaning. This alignment enables cross-modal retrieval (English query returns matching Lean proofs), because when two proofs sit in the same spot in the shared space, they are guaranteed to mean the same thing, so the retrieved proofs are truly semantically relevant, not just keyword matches.

The hidden quantity

The Alignment Score

measured quantity  =  semantic alignment distance

The hidden quantity is how close an English proof and its formal equivalent sit in the shared embedding space—a single number measuring semantic alignment. The model learns this by asking: if I encode this English proof and its matching Lean proof, how close do they end up? The closer they are, the better the alignment, because closeness in this learned space means the two proofs capture the same logical structure.

ProofBridge estimates this by training the joint encoders with contrastive learning (a technique that pushes matched pairs close and unmatched pairs far apart). Every training example reinforces the alignment: matched pairs become closer, mismatched pairs are pushed apart. At test time, the distance itself acts as a retrieval score—retrieve the formal proofs with the smallest distances to the query English proof, because small distance means high alignment and high likelihood of relevance.

Paper reading. The paper uses contrastive loss to train the encoders: NL-FL theorem-proof pairs are pushed close (positive pairs), while cross-modal negatives are pushed far. Recall@K and MRR measure how often the true formal counterpart appears in the top-K retrieved results; high recall means the embedding space placed semantically matched proofs close together, which directly improves translator input quality because the LLM now sees genuinely relevant examples.
Why it works

Why this works: the causal chain

Formal proofs have structure: they follow patterns (certain tactics always come after certain states, proof steps build on each other, types constrain what comes next). An English proof, though written in words, encodes the same structure: it moves through logical steps in a precise order. By learning to encode both languages in the same space, the model learns what a 'proving strategy' is, independent of language.

When you retrieve similar formal proofs before translating, you give the LLM a template. It sees: here is how someone else proved something very similar in Lean. Here is the sequence of tactics, the proof states, the type signatures. Now translate this English proof using the same style. This helps more than translating cold, because the LLM is not inventing from scratch—it is adapting a known structure. The contrastive training ensures that the retrieved examples are actually relevant (high semantic alignment), not random noise. Without the shared space, you would retrieve by keyword or surface similarity, which misses the deep proof structure.

The iterative repair step (using Lean's type checker) catches the remaining gaps. If the LLM's first attempt fails type-checking, the error message tells you exactly what is wrong (type mismatch, undefined tactic, wrong number of arguments). The model then learns to fix these errors in the next attempt. This closes the loop: semantic retrieval guides the translation, type feedback corrects it.

The embedding and retrieval equation

First in words:

For each NL-FL pair, encode NL via encoder f to get a vector v_NL, encode FL via encoder g to get a vector v_FL. Both are projected to dimension d=512 in a shared space. Train using contrastive loss: push matched (v_NL, v_FL) close (high cosine similarity), push unmatched pairs far (low similarity). At retrieval time, compute cosine distance between query embedding and all database embeddings; return the K nearest neighbors by distance.

Then the compact form:

sim(v_NL, v_FL) = (v_NL · v_FL) / (||v_NL|| ||v_FL||) ; L = -log( exp(sim(v_NL, v_FL) / tau) / sum_i exp(sim(v_NL, v_i) / tau) )

Every symbol:

v_NLembedding vector of the English proof
v_FLembedding vector of the Lean proof
sim(·,·)cosine similarity between two vectors (ranges from -1 to 1, higher is more similar)
tautemperature parameter that controls how sharply the loss separates good from bad pairs
Lcontrastive loss (smaller loss means better alignment; training minimizes this)
ddimension of shared embedding space (512)
A tiny worked example
Suppose English proof E and Lean proof L encode to lists of 512 numbers each.
After projection and normalization: list_E = [0.8, -0.2, 0.5, ...], list_L = [0.75, -0.19, 0.52, ...].
Similarity score: list_E · list_L = (0.8)(0.75) + (-0.2)(-0.19) + (0.5)(0.52) + ... ≈ 0.91 (very similar).
Contrastive loss with tau=0.07: numerator = exp(0.91/0.07) ≈ exp(13) ≈ 440,000.
Assume 3 negatives in batch: sum_i exp(sim_i / tau) ≈ 440,000 + exp(0.1/0.07) + exp(-0.3/0.07) ≈ 440,000 + 100 + 0.002 ≈ 440,100.
Loss ≈ -log(440,000 / 440,100) ≈ -log(0.9997) ≈ 0.0003 (very small loss, pair is well-aligned).
If E and L were mismatched: sim ≈ 0.05, Loss ≈ -log(exp(0.71) / 440,100) ≈ -log(2.03 / 440,100) ≈ 12.4 (large loss, training pulls them apart).

The contrastive loss ensures matched NL-FL pairs cluster together in embedding space, while unmatched pairs push far apart, creating a retrieval index where similar proofs are nearest neighbors.

What can go wrong

What can go wrong

Retrieval returns irrelevant proofs. If the encoding space is poorly trained (few contrastive examples, weak alignment), the nearest neighbors may be semantically distant. The LLM then copies a wrong template, amplifying rather than fixing errors. Fix: ensure training data is high-quality and contrastive pairs are truly matched.
The LLM overfits to retrieved examples. If the LLM sees the same formal proof style too often, it may rigidly copy that style even when a different approach would be correct. For proofs requiring unexpected reasoning paths, retrieval can mislead. Fix: use diverse training examples and ensure the LLM is also trained to adapt, not merely imitate.
Type checker gives cryptic error messages. When proof repair fails, the type checker may report an error deep in a tactic sequence, making it unclear where the original translation went wrong. The model then has to infer the fix from limited feedback. Fix: use a richer error reporting mechanism (e.g., which tactic introduced the error) to guide repair.
Done right. The joint embedding is trained on a diverse, high-quality dataset where English and Lean proofs are true semantic pairs. Retrieval returns proofs that genuinely help, not just superficially similar, because the contrastive training ensures that only semantically equivalent pairs end up close in the space. The LLM is fine-tuned to adapt examples flexibly, not copy verbatim, because the training data shows varied proof strategies applied to similar problems. Iterative repair uses error messages to pinpoint and fix the mistake because the type checker tells you exactly which tactic or type annotation failed.
What a runnable demo should prove

What a runnable demo should prove

Build a small dataset: 50 English theorem-proof pairs and 50 Lean theorem-proof pairs (mix of algebra, number theory, and logic puzzles). Train the joint encoder on 40 pairs. Hold out 10 English-Lean pairs as test. For each test English proof, retrieve the nearest Lean proofs in the embedding space using the learned distance metric. Ask a base LLM to translate the English proof using the top-5 retrieved Lean proofs as examples. Have Lean's type checker verify each output. Measure: (1) by manual inspection, count how many retrieved Lean proofs solve a theorem in the same mathematical domain as the query English proof; (2) how many translations pass the type checker, showing whether the LLM can write syntactically valid Lean code; (3) is the success rate with retrieval higher than without retrieval?

retrieval_recall = (number of test queries where true partner is in top-5 retrieved) / (total test queries) ; translation_success = (number of LLM outputs that type-check) / (total translations) ; improvement = translation_success_with_retrieval - translation_success_without_retrieval

The demo succeeds when retrieval visibly helps the LLM: translations with retrieved examples should type-check much more often than translations without examples because the examples provide concrete templates for the formal structure, and the retrieved proofs should be recognizably similar in structure and strategy to the English proof because the embedding space was trained to align them by meaning.
