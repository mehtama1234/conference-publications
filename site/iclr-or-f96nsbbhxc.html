AutoCode: LLMs as Problem Setters for Competitive Programming

Train an LLM to write competitive programming problems by having it generate and then cross-check problems using reference and trick solutions in a loop.

Paper explainersAll themesDatasets & Benchmarks & Evaluation

Writing a good competitive programming problem is harder than solving one. You must set constraints that block cheap shortcuts, create test cases that expose weak algorithms, and calibrate difficulty to match your target skill level. The paper asks: can an LLM do this reliably? They introduce AutoCode, which builds competition-grade problems using a closed loop: a validator checks inputs obey the rules, a generator creates test cases, a checker grades solutions against them, and they all verify each other. The result approaches 99% agreement with official contest judges.

Zero assumption version

Why problems written by hand are fragile

A competitive programming problem needs to be tight. If your test cases are weak, solutions that cut corners will pass. A greedy algorithm that sounds reasonable might fail only on adversarial inputs that expose its flaw. A solution with the wrong time complexity (e.g., trying every pair instead of sorting) will look correct until you feed it 1 million numbers.

What a beginner might try: feed the LLM a problem description and ask it to write test cases. This breaks because the LLM might invent cases that look natural but violate the hidden constraints in the problem, or miss the adversarial cases that trip up weak solutions. You end up with test suites that let wrong answers pass.

The core gap is that problem-setting and problem-solving are different skills. Solving asks: does my algorithm work? Setting asks: which algorithms should work and which should fail? The second requires understanding not just one solution path, but all the traps.

The paper's move in one sentence. Use multiple rounds of cross-checking: have the LLM generate test cases, then verify them by making the LLM write solutions in multiple ways (correct, and intentionally wrong), and flag tests that the wrong solutions wrongly pass.

The algorithm as a flow

What it actually does

Build Validator

LLM generates 40 edge-case inputs (10 valid, 30 near-valid), then makes three candidate validators. Pick the one that classifies all 40 correctly.

Build Generator

LLM creates test cases in three ways: exhaustive coverage of small inputs, random + extreme values, and adversarial hacks (greedy traps, hash collisions, time-limit traps).

Build Checker

LLM generates 40 scenarios (valid input, plausible-wrong output, correct output). Make three checkers; keep the one most accurate on all 40.

Cross-verify

For each test case, run the reference solution and intentional wrong-algorithm versions. Discard tests that let buggy solutions pass.

Generate new variants

Given a seed problem, mutate it (swap operators, introduce off-by-one errors), then use the same loop to validate the new variant.

What the paper changes

The one thing the paper changes

The object is the test suite: which test cases are used to judge a submission. Instead of using whatever cases an LLM generates once, AutoCode builds a multi-role loop where validators, generators, and checkers vote on whether each test case is worth keeping.

the object it moves  =  test suites
The hidden quantity

The hidden quantity: consistency

measured quantity  =  consistency (% agreement with human judges)

Consistency measures how often the test suite gives the same verdict as an official competitive programming judge. A test suite with consistency 80% means: on 100 submissions, this suite and the judges agree on the verdict (accepted or wrong) 80 times. A suite with consistency 99% is almost indistinguishable from a human expert.

The paper estimates consistency by running 33 different solutions per problem (from different LLMs and strategies), with 25% intentionally correct and 75% intentionally flawed. It counts how many solutions this test suite and the official judge agree on (both accept or both reject).

Why it works

Why cross-verifying against multiple solution types catches bad tests

A bad test case is one that lets a buggy solution pass. If a greedy algorithm is fundamentally wrong but your test case only uses small inputs, the greedy will look correct. The paper's insight: generate test cases, but then immediately have the LLM write intentionally wrong solutions (off-by-one bugs, greedy shortcuts, hash-collision failures, mishandled edge cases). Run both the correct solution and all the wrong ones on each test case. Any test case that a wrong solution passes is discarded because it is too weak.

Why this works: the LLM understands the algorithm deeply enough to write convincing wrong solutions that embody real algorithmic errors. If a test case cannot distinguish a correct solution from a concrete wrong answer that a human expert would recognize as flawed, the test case is not measuring anything. By iterating — generate, verify against candidates, filter — the suite converges to one that cannot be fooled.

Scoring a validator

First in words:

For each candidate validator, count how many of the 40 edge-case inputs it classifies correctly (valid or invalid). Pick the validator with the highest count.

Then the compact form:

score(V) = sum over (input, true_label) in edge_cases [ V(input) == true_label ]

Every symbol:

Vone candidate validator (an LLM-written rule checker)
inputa test input (numbers, strings, or other data)
true_labelcorrect classification: valid or invalid per the problem constraints
score(V)how many of 40 inputs this validator judges correctly
A tiny worked example
Problem: sort an array of integers. Constraint: 1 ≤ size ≤ 1,000,000.
Validator A tested on 40 edge cases: correctly judges 35 cases, misses 5 (e.g., wrongly rejects a valid array of size 500,000). Score = 35.
Validator B: correctly judges 38 cases, misses 2. Score = 38.
Validator C: correctly judges 36 cases, misses 4. Score = 36.
Pick Validator B with score 38. It is most accurate on boundary cases.

The paper uses the same voting idea for Checker and Interactor: generate candidates, evaluate on a curated test set, pick the best. Repetition across all roles hardens the entire pipeline.

What can go wrong

What can go wrong

LLM writes a logically correct but algorithmically weak test case. If the LLM does not understand the algorithmic subtlety (e.g., that hashing is vulnerable to collisions on adversarial input), the wrong solution still passes even after cross-verification. Guard: use domain-specific prompts and human review of new problem variants.
The validator is too strict. If the validator rejects all near-boundary cases, the generator will never create diverse edge-case coverage. The paper mitigates this by including 30 near-valid cases in the evaluation set, forcing the validator to distinguish subtle violations from legitimate boundary behavior.
Mutated buggy solutions share the same flaw. If all three intentional wrong solutions happen to fail on the same bug (e.g., all use a naive sort on integer overflow), a test case that does not trigger that bug will still pass both correct and wrong solutions. Requires diversity in error types.
Done right: multi-role voting. Validator, Generator, Checker, and Interactor vote independently. Any role that fails the test set is discarded. Cross-verification against multiple solution types removes tests that fool any single heuristic. This redundancy is the mechanism that catches real problems.
What a runnable demo should prove

What a runnable demo should prove

Build a minimal AutoCode: take a competitive programming problem (e.g., sort an array with constraints 1 to 1 million). Implement the Validator-Generator-Checker loop once: (1) Generate 10 test cases from a simple rule (vary array size, include edge values). (2) For each test case, run a correct sorting solution and a greedy-shortcut solution (e.g., quicksort with worst-case pivot choice). (3) Count how many test cases the greedy solution wrongly passes. (4) Remove those tests. (5) Measure final consistency by submitting both correct and buggy code to a sandbox judge and recording agreement rate.

consistency = (# test cases where correct_solution_result == buggy_solution_result) / (# total test cases)

The demo succeeds when the filtered test suite achieves consistency > 90% (correct solution passes, greedy solution fails on most tests), while the unfiltered suite achieves < 70% consistency (greedy passes many tests).
