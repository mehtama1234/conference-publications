TodoEvolve: Learning to Architect Agent Planning Systems

TodoEvolve learns to design the planning structure an agent should use for a task instead of forcing every task through one fixed planner.

Paper explainersAll themesAgents & Tool Use

Agent systems often include a planner, but that planner is usually hand-built in advance. One task may need a short checklist. Another may need branching subgoals, revision after failure, or a stronger review loop because the task unfolds through several dependent decisions. A fixed planning structure cannot match all of those cases well. TodoEvolve addresses that mismatch by treating the planning system itself as something that can be generated and revised for each task. The paper first defines a design space of planning modules, then trains a model to assemble those modules into task-specific planning architectures that work across several agent backbones and benchmarks.

Zero assumption version

Why one planner does not fit every task

Planning modules are usually chosen by hand. A developer decides whether the agent will use a to-do list, a tree of subtasks, a reflection step, or a revise-and-retry loop. That manual choice can work on a narrow benchmark, but open tasks vary too much for one structure to stay best across them all.

The problem is not only that different tasks need different numbers of steps. They also need different planning behavior. Some tasks benefit from revising the plan after new evidence appears. Others benefit from a simple direct plan because extra planning only adds overhead. If the architecture is fixed, the agent cannot adapt its planning style to the task it sees.

The paper's move in one sentence. Define a modular space of planning components and train a model to compose them into a task-specific planning system that fits the current agent job.

The algorithm as a flow

What it actually does

Step 1: Define a modular planning space

Organize planning choices such as topology, initialization, adaptation, and navigation into one reusable code framework.

Step 2: Collect planning trajectories

Run many planner variants on tasks so that the training process can observe which planning structures help in which settings.

Step 3: Train a planner-architect model

Learn to propose planning systems that score well on task quality, stability, and cost because those are the goals the paper wants to balance.

Step 4: Generate a task-specific planner

Given a new task and agent backbone, synthesize a planning architecture that fits that setting instead of reusing one fixed template.

Step 5: Execute the task with the chosen planner

Run the agent under that planning structure and revise when the architecture needs to adapt mid-task.

The hidden quantity

The hidden quantity: planner-task fit

measured quantity  =  how well a planning architecture matches the structure and difficulty of the current task

The central hidden quantity is planner-task fit. A planning architecture is good only relative to the task it is trying to organize. A deep branching task may need decomposition and revision, while a short direct task may need almost no planning overhead. The same planner can therefore be helpful in one setting and wasteful in another.

TodoEvolve learns this fit indirectly from trajectory data and preference optimization. It favors planners that solve tasks reliably without adding unnecessary runtime cost, because a planning system is only useful when the extra structure repays the time it adds.

Why it works

Why it works

The main reason it works is that planning is moved up one level. Instead of asking only how an agent should act inside a fixed planner, the paper asks which planner the agent should use in the first place. That matters because planning errors often come from the wrong structure rather than from one bad step inside an otherwise suitable structure.

PlanFactory provides the ingredients for that higher-level choice. By standardizing planning options inside one design space, the paper makes architectures comparable. The training process can then observe that some tasks benefit from deeper decomposition because they contain many dependent branches, some from stronger adaptation because the best plan changes after new evidence appears, and some from lighter planning because extra planning only adds delay. That shared design space is what turns planner selection into a learnable problem.

The optimization objective also matters because it does not reward raw task success alone. The model is trained to care about stability and cost along with quality, so it does not simply pick the most elaborate planner every time. That balance is important because a planner that solves a task only by adding large overhead is less useful than one that reaches nearly the same result with a smaller planning burden.

Math after the picture

The planner score

First in words:

Pick the planning architecture that gives high task performance while keeping execution stable and planning cost low.

Then the compact form:

score(planner, task) = task_quality - cost_weight * planning_cost + stability_weight * stability

Every symbol:

plannerone candidate planning architecture assembled from the design space
taskthe current agent problem
task_qualityhow well the agent solves the task under this planner
planning_costextra runtime or API cost introduced by the planner
stabilityhow consistently the planner leads to successful execution across trials
cost_weighthow strongly the score penalizes planning overhead
stability_weighthow strongly the score rewards consistent behavior
A tiny worked example
Planner A is a flat to-do list. On a short file-edit task it gets high task quality and low planning cost.
Planner B adds decomposition and revision. On the same short task it reaches similar task quality but with more overhead.
Because the score subtracts planning cost, Planner A ranks higher for that task.
On a harder browsing task, Planner B reaches better task quality and better stability because it can revise after dead ends.
There the higher quality and stability outweigh the extra cost, so Planner B ranks higher.

The point is not to find one universal planner. The point is to choose the planner whose tradeoff fits the current task.

What can go wrong

What can go wrong

The design space may miss a useful planner type. If PlanFactory does not include a planning behavior a task needs, the model cannot synthesize it, so performance is bounded by the coverage of the planning modules that were defined.
Preference data can bias the planner score. If the collected trajectories overvalue one planning style, the model may keep proposing it too often because the training signal does not reflect the full range of tasks.
Generated planners can overfit benchmark habits. A planner may match repeated benchmark patterns rather than the deeper task structure, so cross-benchmark testing matters because it checks whether the planner really adapts.
Done right. The method is strongest when the planning design space is broad and the training objective balances quality, stability, and cost, because then the generated planner has a real reason to match the task instead of growing more elaborate by default.
What a runnable demo should prove

What a runnable demo should prove

Build a small agent benchmark with three task types: short direct edits, branching information gathering, and repair-heavy tool workflows. Provide three planning modules: flat checklist, decomposition tree, and revise-and-retry loop. Compare a system that always uses one fixed module against a system that chooses a module per task using a learned score. The demo should show that per-task planner choice wins because simple tasks avoid extra planning cost while harder tasks get the structure they need.

planner_fit_gain = average_task_score_with_task_specific_planner - average_task_score_with_fixed_planner

The demo should make the main claim concrete: planning quality rises when the planner itself can adapt, because different tasks need different planning structure.
