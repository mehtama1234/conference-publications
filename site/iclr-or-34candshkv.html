Graph-of-Agents: A Graph-based Framework for Multi-Agent LLM Collaboration

Pick a few useful agents, connect them by relevance, and pass messages along those links so the group answer improves without using every model at once.

Paper explainersAll themesOther

Using many language models together sounds appealing, but a crowded group often wastes effort because the wrong models join, the right ones do not exchange the right information, and the final merger treats every answer the same. Graph-of-Agents imposes structure: select only the most relevant agents, connect them by how helpful they are to one another, and pass messages along those directed links before combining the results. This helps because information flows where it is most useful instead of being broadcast blindly to everyone.

Zero assumption version

A large agent pool becomes noisy when every model participates equally

Suppose you have several language models with different strengths: one is better at medicine because its training and tuning emphasized medical text, one at code because it saw more programming tasks, one at formal reasoning, and one at broad factual questions. A naive multi-agent system may ask all of them to answer every question and then average or vote on the results.

That wastes capacity. Some agents are irrelevant to the current task, and some agents could help others if their partial answers arrived in the right order. If every agent speaks to every other agent equally, the system spends cost on weak interactions and makes the final merger harder because good answers are mixed with distracting ones.

The paper's move. Represent the agent team as a directed graph so only relevant agents join and information flows along useful links before the final answer is pooled.

The algorithm as a flow

What it actually does

Read agent profiles

Use model cards or capability summaries to estimate which agents fit the task.

Sample a small set of nodes

Select only the most relevant agents instead of using the full pool.

Build directed edges

Compare early responses to decide which agents should influence which others.

Pass messages along the edges

Let stronger or more relevant agents refine weaker responses, then pass refined information back when useful, because the first revision can supply missing facts for the second round as well.

Pool the updated responses

Merge the refined answers into a single final response.

What the paper changes

What the paper changes

The paper changes the collaboration structure. Instead of an unstructured crowd of agents, it turns the team into a directed graph with chosen nodes, chosen edges, and ordered message passing.

The hidden quantity

Useful communication density: the hidden quantity

measured quantity  =  how much of the communication budget carries task-relevant information

The hidden quantity is useful communication density: of all messages exchanged between agents, how many actually improve the answer? In a naive all-to-all system, many messages are irrelevant because the sender lacks the needed expertise or repeats what another agent already said.

Graph-of-Agents raises useful communication density by filtering both nodes and edges. That matters because the system spends its budget on interactions that are likely to help, so each added message has a better chance of improving the final answer.

Why it works

Why the graph structure helps

The graph creates two filters before the final answer is produced. First, node selection filters the team: only agents whose documented strengths fit the question are invited. That saves cost and reduces noise because irrelevant agents never enter the discussion.

Second, edge construction filters communication. Instead of letting every agent talk to every other agent, the system checks which responses are useful to which other agents. A strong math answer may help a generalist revise its reasoning because it adds precise structure the generalist lacks, while the reverse may not help. Directed links encode that asymmetry, so information moves where it has the highest value.

The pooling step happens after message passing, not before. That matters because the final merger now sees refined answers rather than raw, disconnected drafts. The graph therefore improves both efficiency and quality because it spends the collaboration budget on targeted revisions and then pools the improved outputs.

Math after the picture

Pooling refined agent outputs

First in words:

After message passing, each selected agent has an updated response representation. Pool them into one final answer by averaging or taking the strongest coordinates across agents.

Then the compact form:

final = pool( r_1', r_2', ... , r_k' )

Every symbol:

kthe number of selected agents
r_i'the updated response from selected agent i after graph message passing
poolthe aggregation rule, such as mean or max pooling
finalthe unified response used to produce the final answer
A tiny worked example
Suppose the system selects three agents: medicine, science, and general reasoning.
After message passing, their updated response scores for the correct option are 0.9, 0.8, and 0.7.
Mean pooling gives final = (0.9 + 0.8 + 0.7) / 3 = 0.8.
If a fourth irrelevant code agent had been included with score 0.2, the mean would drop to 0.65.
Selecting the right nodes first helps because the pooling step is then dominated by relevant expertise.

The graph matters before the pool, because better node choice and better message flow change what enters the aggregation.

What can go wrong

What can go wrong

Bad node selection hurts the whole graph. If the system excludes the truly relevant agent at the start, later message passing cannot recover that missing expertise.
Edge scores can be misleading. Early draft responses may look weak even when an agent has deep expertise, so a poor edge-construction rule can block useful communication.
Pooling can wash out specialist insight. If the final pool treats all refined responses too evenly, a strong specialist signal may be diluted by weaker agents.
Done right. When node choice matches the task and edge direction matches who truly helps whom, the graph improves answers because each message has a clear purpose inside the collaboration.
What a runnable demo should prove

What a runnable demo should prove

Build a multi-agent question-answering system with six candidate models and compare three settings: single best model, all-agents broadcast, and Graph-of-Agents with node selection plus directed message passing. Use mixed-domain questions so task relevance changes from one item to the next. Record accuracy, response cost, and how often each communication step changes the final answer.
