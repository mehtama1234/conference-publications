Agent Primitives: Reuseable Latent Building Blocks for Multi-Agent Systems

Replace custom multi-agent designs with a small set of reusable internal patterns that can be composed for each query.

Paper explainersAll themesAgents & Tool Use

Many multi-agent systems are built by hand. A developer writes special roles, special prompts, and special message rules for one task, then has to rebuild the system for the next task. This paper argues that many of those systems repeat the same few internal patterns. It packages those patterns as reusable primitives and lets an organizer choose which ones to compose for a new query because reusable parts are easier to transfer than one-off team designs.

Zero assumption version

Why hand-built agent teams are brittle

A multi-agent system can solve hard tasks by splitting work across several specialized roles. The problem is that many such systems are built as fixed blueprints. One blueprint may say to plan first, then critique, then vote. Another may say to debate and then select. Those blueprints often work only on the tasks they were designed for.

There is a second problem too. Many systems make agents talk to each other only through long text exchanges. Important details can be restated badly, dropped, or contradicted as the discussion gets longer. That raises cost and slows the system because every stage has to read and rewrite more text.

The paper's move in one sentence. Identify a small set of recurring team behaviors, implement them as reusable primitives, and let one organizer compose them per query.

The algorithm as a flow

What it actually does

Store a small primitive library

Keep reusable behaviors such as review, vote and select, and plan then execute.

Read the new query

Estimate which coordination pattern will fit the task because not all tasks need the same internal teamwork.

Compose primitives

Have the organizer choose one or more primitives and arrange their order for the current task.

Share internal records across stages

Pass stored state directly so that later stages do not need to reconstruct the whole discussion from long text.

Return the final answer

Use the composed team only for this query so that the next query can choose a different structure.

The hidden quantity

The hidden quantity

measured quantity  =  Best coordination pattern for the current query

The important hidden quantity is which team behavior pattern fits the current query best. A difficult reasoning task may need planning before execution, while a noisy task may need review and selection. That best pattern is not written on the query itself.

The organizer tries to infer that pattern from the task and from a pool of previously successful configurations. This matters because choosing the wrong pattern can waste steps or create unnecessary discussion even if each individual agent is capable.

Why it works

Why this works: reuse a few good team behaviors and avoid long text relay

The first advantage comes from reuse. Many tasks need similar team moves even when the task content changes. A review step, a selection step, and a planning step appear across many systems. Once these behaviors are separated into reusable parts, the system can recombine them instead of rebuilding a fresh architecture for every task.

The second advantage comes from shorter communication. Passing internal records directly works better than repeated text summaries because each stage receives cleaner state and does not have to spend extra words rewriting what earlier stages already knew.

Score a primitive composition

First in words:

Give each candidate composition a score based on expected task quality minus communication and coordination cost, then choose the largest score.

Then the compact form:

score(plan) = expected_quality(plan) - communication_cost(plan) - setup_cost(plan)

Every symbol:

score(plan)overall value of one candidate primitive composition for the current query
expected_quality(plan)how likely that composition is to produce a correct final answer on this query
communication_cost(plan)cost from passing information among stages
setup_cost(plan)extra cost from using more coordination steps than the task needs
A tiny worked example
Plan A uses only plan then execute. Quality 7, communication cost 1, setup cost 1, total 5.
Plan B uses review, vote and select, then execute. Quality 8, communication cost 3, setup cost 2, total 3.
Plan C uses plan then execute, followed by one review step. Quality 9, communication cost 2, setup cost 1, total 6.
The organizer picks Plan C because it adds one useful check without paying for a larger discussion than the task needs.

The paper uses learned selection over primitive configurations. This equation states the same design pressure in compact form.

What can go wrong

What can go wrong

Primitive library too small. If the stored behaviors miss an important coordination pattern, the organizer may keep composing weak plans because none of the available parts fit the task.
Bad organizer choices. A strong primitive library still fails if the organizer picks the wrong combination because the whole team structure depends on that first selection.
Stored internal records lose needed detail. Shorter communication is helpful only if the stored records preserve the facts the next stage needs, because over-compression can hide useful evidence.
Done right. The method is compelling because it separates reusable coordination patterns from task content, so the system can transfer team design across tasks with less manual work.
What a runnable demo should prove

What a runnable demo should prove

Build a small primitive library with three behaviors: plan then execute, review, and vote then select. Create several query types, such as arithmetic with checking, open-ended search, and code repair. Compare three systems: one single agent, one hand-written fixed team, and one organizer that chooses primitive compositions per query. Log which composition is chosen and how much communication each system uses.

The demo should show that the organizer wins on mixed workloads because no single fixed team shape fits every query equally well. It should also show lower communication cost than text-heavy teams because later stages read stored state instead of long rewrites.
