ThunderAgent: Program-Aware Agentic Inference

Treat an agent's multi-step workflow as one program so the system can schedule all the LLM calls and tool runs together, reusing memory and avoiding idle time.

Paper explainersAll themesAgents & Tool Use

When an AI agent solves a task, it runs many LLM calls (asking the model a question) and tool calls (running code or querying a database). Today's systems treat each call separately — the LLM part runs on one machine, the tool part runs on another, and they do not know about each other. ThunderAgent glues them together by treating the whole workflow as a single program, so the system can keep memory around between calls and run tools while the LLM is thinking.

Zero assumption version

Today's systems waste memory and time on agent tasks

An AI agent that solves a hard problem asks many questions: it thinks, runs a calculation, checks the result, thinks again. Each question needs the LLM to hold a lot of intermediate memory (the KV cache — all the history the model has seen so far). Today, the system forgets this memory after each question and rebuilds it from scratch for the next one. Rebuilding wastes time and uses more memory overall.

Even worse, tools (like running code or looking up data) run separately from the LLM. The system asks the LLM a question, waits for the answer, then tells the tool to start. The tool runs. Meanwhile the LLM sits idle, not helping. The system could be preparing the tool or warming up memory while the LLM is thinking, but it does not, because the LLM and tool systems do not talk to each other.

In one sentence. The system does not know that one question depends on the last, so it throws away useful memory and keeps the LLM and tools idle instead of working in parallel.

The algorithm as a flow

What it actually does

Model the workflow as a program

Write down all the LLM calls and tool calls as one connected plan, not separate pieces.

Find opportunities to run things together

Find when the LLM is busy computing so the tool can start preparing its job in parallel, and identify LLM calls that can share memory because they work with the same data.

Keep memory between calls

Do not throw away the LLM's internal history after each call; save it and reuse it for the next question.

Schedule requests to minimize idle time

Arrange the order of LLM and tool calls so they overlap and nothing waits.

Measure the savings

Count the speedup in how many questions the system can answer per second, and how much memory it uses.

What the paper changes

The one thing the paper changes

The paper changes how the system views an agentic workflow: instead of a pile of independent requests, it is one connected program. This unified view lets the system schedule both LLM calls and tool calls together, reusing memory and running them in parallel.

The hidden quantity

The hidden quantity: KV cache hit rate

measured quantity  =  KV cache hit rate

The KV cache is the LLM's internal memory of what it has seen so far. Every time the LLM answers a question, it builds a KV cache for that conversation. If the next question is on the same topic or continues the same thread, parts of the old cache are still useful. A cache hit happens when the system reuses a piece of that memory instead of rebuilding it from scratch.

ThunderAgent measures how often it can reuse cached memory across consecutive LLM calls in the same workflow. A higher cache hit rate means less rebuilding, so the system spends less time and uses less memory overall.

Why it works

Why it works: seeing the whole program

The trick is simple: when the system sees all the LLM calls and tool calls at once (as one program), it can make smarter choices. If it knows that call #2 depends on the answer to call #1, it can keep call #1's memory around instead of deleting it. If it knows that a tool call will take 3 seconds, it can start it while the LLM is busy answering a question, so they run at the same time and nothing waits.

Without the program view, the system treats each call as independent: finish one, throw everything away, start the next. With the program view, the system is lazy about memory — it keeps things around as long as they might be useful. This saves time (no rebuilding) and also saves memory (no duplicate copies) because the system stores each piece of information once instead of recreating it.

Math after the picture

The core idea in math

First in words:

throughput equals number of workflow instances the system completes per second, and each instance uses less memory when the KV cache is reused across LLM calls instead of rebuilt.

Then the compact form:

throughput_new = throughput_old * (1 + alpha * cache_hit_rate) * (1 + beta * parallelism_gain)

Every symbol:

throughput_oldhow many workflows the old system finished per second
cache_hit_ratefraction of LLM memory the new system reuses (0 to 1)
parallelism_gainspeedup from running tools and LLM at the same time
alpha, betameasured weights showing how much cache reuse and parallelism matter
A tiny worked example
Old system on a 3-call workflow: finishes 10 workflows per second, rebuilds memory 3 times per workflow.
New system with program view: reuses 60% of memory between calls (cache_hit_rate = 0.6), runs tools in parallel 40% faster (parallelism_gain = 0.4).
If alpha = 0.5 and beta = 0.5, then throughput_new = 10 * (1 + 0.5 * 0.6) * (1 + 0.5 * 0.4) = 10 * 1.3 * 1.2 = 15.6 workflows per second.
Real results: 1.5× to 3.6× speedup, which matches when cache hit and parallelism both help.

Seeing the whole program up front lets the system make global choices about which memory to keep and which calls to overlap, instead of making greedy per-request choices that waste memory.

What can go wrong

What can go wrong

Workflow structure changes at runtime. If the agent decides to take a different path (e.g., ask a different follow-up question), the precomputed schedule is wrong and the system has to replan.
Tools have unpredictable run times. If a tool takes much longer than expected, the LLM might finish thinking before the tool results are ready, and it waits anyway.
Memory state is complex. If the LLM's internal memory has subtle dependencies the system does not detect, reusing it might hurt accuracy instead of helping.
Many concurrent workflows compete for resources. If the system is running 100 workflows at once, keeping all their KV caches in memory at once could exhaust the hardware.
Done right. ThunderAgent works best when workflows are relatively predictable (same structure each time) and tool run times are stable. For open-ended agent tasks with changing plans, a hybrid approach works: schedule what you know, replan adaptively when the agent surprises you.
What a runnable demo should prove

What a runnable demo should prove

Build a simple agent that solves math word problems: read the problem, call an LLM to break it into steps, call a tool to compute each step, call the LLM again to check the answer. Run it 100 times through the old system (separate LLM and tool) and through ThunderAgent. Measure (1) how many problems the system solves per second, and (2) how many gigabytes of GPU memory are used. Record the cache hit rate (how often the LLM reuses memory from the previous call) and the tool-LLM overlap time (how often the tool runs while the LLM is thinking).

speedup = (old_time_per_workflow) / (new_time_per_workflow); memory_savings = (old_peak_memory) / (new_peak_memory); cache_hit_rate = (reused_cache_bytes) / (total_cache_bytes)

The demo must make it impossible to miss that the unified program view lets the system reuse memory and run LLM and tool at the same time.
