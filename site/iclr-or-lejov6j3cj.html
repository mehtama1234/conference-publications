Embracing Discrete Search: A Reasonable Approach to Causal Structure Learning

Search directly over graph orders and parent sets, but make each local score update cheap enough that discrete search becomes practical instead of being ruled out by compute cost.

Paper explainersAll themesOther

Causal structure learning asks which variables directly drive which others. In linear score-based methods, the clean formulation is discrete: choose an ordering of variables, choose parents that respect that ordering, and keep the graph with the best score. The difficulty is not the definition of the target. The difficulty is cost, because each proposed edit can force many repeated regressions and repeated factorizations of covariance tables into triangular forms. That cost pushed many recent methods toward continuous relaxations that are easier to optimize but do not search the exact graph space. This paper argues that the old discrete route was abandoned too early. FLOP makes two pieces cheap: parent selection under a fixed order, and score recomputation after a local order edit. Once those pieces are cheap, an iterated local search can revisit many candidate orders and often land at or near the best-scoring graph because the algorithm can afford to evaluate the actual discrete choices instead of a softened proxy.

Zero assumption version

Why exact graph search became unattractive

A directed acyclic graph encodes direct causes, but there are many possible graphs even for a modest number of variables. Score-based methods solve this by assigning each graph a data-fit score plus a complexity penalty and then looking for the graph with the best value.

Under a fixed variable order, the problem becomes easier because each variable can only choose parents from earlier variables. Even then, naive search is still slow. For each candidate parent set, one must refit a local linear model, update the local score, and then repeat after every small change to the order. That repetition is what breaks scalability. A method may know exactly what it wants to optimize and still be unusable because the same linear-algebra work is redone too many times.

The paper's move. Keep the discrete objective, but restructure the computation so parent search and score updates are incremental, because the main obstacle was repeated cost rather than a flaw in the discrete objective itself.

The algorithm as a flow

What it actually does

Choose an initial variable order.

Start from a principled order guess, because a good starting point reduces the number of expensive corrections the search must make later.

Solve parent selection under that order.

For each variable, search only among earlier variables, because that turns global acyclicity into many local choices.

Cache the linear-algebra pieces needed for local scores.

Reuse factorization updates instead of refitting every local regression from scratch, because nearby candidate graphs share most of the same structure.

Modify the order locally.

Propose a swap or relocation of one variable and update only the affected local scores, because unchanged parts of the order do not need new work.

Run iterated local search.

Keep improving and restarting when needed, because a single local hill climb can stop at a poor order even when better discrete solutions exist nearby.

The hidden quantity

The hidden quantity

measured quantity  =  the score contribution that changes after a local order edit

The full graph score is a sum of local terms, one per variable. After a small order change, only some of those local terms can change. That affected subset is the hidden quantity FLOP exploits.

This matters because a naive algorithm recomputes every local term after each edit even though most variables kept the same allowed parent candidates. FLOP tracks which variables were actually exposed to a new candidate set, then updates only those scores. The search therefore spends time on the part of the objective that moved rather than on the whole graph every round.

Why it works

Why the faster discrete route works

The first key step is to separate order search from parent selection. Once an order is fixed, each node only competes among earlier nodes, so acyclicity no longer has to be checked globally for every parent-set proposal.

The second key step is to make local scores cheap. FLOP uses Cholesky updates, which means a triangular factor of the relevant covariance square table is revised incrementally when a parent candidate is added, removed, or reordered. That matters because solving many closely related linear regressions is the dominant cost in score-based search.

The third key step is to search the order space aggressively once each move is cheap. Iterated local search matters because causal scores often contain many local optima. If each move is expensive, the search stops early because it can test only a small neighborhood before the budget is exhausted. If each move is cheap, the algorithm can try swaps, accept improvements, restart from new seeds, and keep moving until the score no longer improves in any nearby order, so it covers more of the discrete search space.

Math after the picture

Score decomposition

First in words:

Write the graph score as a sum over variables of the best local score available under the current order. Then a local order edit only changes the terms whose allowed parent candidates changed.

Then the compact form:

graph_score(order) = sum over variables of best_local_score(variable, allowed earlier parents)

Every symbol:

orderthe current ranking of variables from earlier to later
best_local_score(variable, allowed earlier parents)the best score the variable can achieve by choosing parents only from nodes earlier in the order
sum over variablesadd the local score contributions from all variables
graph_score(order)the total score of the best graph consistent with that order
A tiny worked example
Suppose the order is A, B, C, D.
Then C may choose parents from A and B, while D may choose from A, B, and C.
If the search swaps B and C, then the allowed parent sets for A stay the same and the allowed parent sets for D often stay similar.
The main changes occur for B and C, because their earlier candidates changed directly.
So the algorithm updates those local terms instead of recomputing every node's score, which is why many order edits can be tested in one run.

The practical win comes from the local decomposition plus incremental updates, not from changing the causal score itself.

What can go wrong

What can go wrong

The score can still prefer the wrong graph. If the linear model class is misspecified or the sample is small, the best-scoring discrete graph may still differ from the true causal graph because the score is only as reliable as its modeling assumptions.
Local search can still miss a faraway basin. Cheap moves help exploration, but iterated local search still relies on local edits because each step proposes only a nearby order change. If two strong solutions are separated by many individually weak moves, the search may need enough restarts to reach the better basin because a greedy local trajectory may refuse the temporary score drop needed to cross between them.
Incremental updates do not remove combinatorial growth. The graph space still grows rapidly with the number of variables, so the method becomes harder as dimension increases because there are more orderings and more parent subsets to examine.
Done right. When the score assumptions fit the data and enough search iterations are allowed, FLOP can recover very accurate structures because it spends its budget on direct discrete comparisons instead of on repeated full recomputation.
What a runnable demo should prove

What a runnable demo should prove

Create synthetic linear causal graphs where the true order is not given. Compare a baseline score-based search that recomputes local regressions after every order edit against FLOP with incremental parent and score updates.

The demo should log score value versus wall-clock time, number of local moves tested, and graph recovery quality. A convincing result shows FLOP testing many more discrete edits and reaching a higher-scoring graph in the same time budget because each local order change only triggers limited score work.

search_efficiency = tested_local_moves / wall_clock_time

The central claim is not that discrete search became easy in theory. The claim is that the expensive inner loop was reduced enough that direct graph search becomes a practical option again.
