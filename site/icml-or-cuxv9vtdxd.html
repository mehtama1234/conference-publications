AppWorld-UL: User-In-The-Loop Tool-Use Agents

A benchmark where agents must ask clarifying questions and handle ambiguities when automating real digital tasks, revealing that Claude Opus only succeeds 48.6% of the time when users must be consulted mid-task.

Paper explainersAll themesAgents & Tool Use

Agents that automate everyday digital tasks like ordering groceries must do more than just click buttons — they must ask users questions when something is unclear, confirm risky actions before proceeding, and admit when a task is impossible. Today's benchmarks do not test this. AppWorld-UL is a benchmark of 516 real tasks on nine simulated apps (Amazon, Spotify, etc.) where an agent cannot succeed without asking clarifying questions or getting user confirmation, and where user behavior is simulated by an AI with realistic knowledge gaps.

Zero assumption version

Why today's benchmarks let agents off easy

When a real person uses Amazon to order coffee, they might say: "Order a one-pound bag from the brand I usually buy." But the agent cannot guess which brand. In the real world, the agent asks the user to clarify. In today's benchmarks, either the task is already fully specific (no ambiguity) or there is no one to ask.

Current benchmarks operate in small, simplified environments with a handful of APIs (application programming interfaces — the buttons and features an app exposes). They measure only whether an agent can complete a task by clicking through one app. Real digital work involves real uncertainty: incomplete user instructions, constraints the user does not mention upfront, and situations where the best move is to check with the user before acting.

A beginner might assume an agent just needs better language understanding — if we feed it more training examples or make the model larger, it will guess what the user meant. That approach fails because guessing is not the right answer; asking is. No amount of training on guesses will teach an agent when to admit uncertainty and reach out.

The missing piece: Benchmarks that measure whether agents can handle real, ambiguous tasks by asking clarifying questions and waiting for user input before proceeding.

The algorithm as a flow

What it actually does

Create 516 tasks with built-in ambiguities

Start with clear instructions on nine real apps, then systematically add vagueness: missing details, unspecified preferences, or constraints hidden until the agent asks.

Simulate a user with realistic knowledge limits

Instead of letting an AI answer anything, prompt the simulated user to have bounded knowledge, so it can only answer what a real person would know, and can refuse impossible requests.

Test whether agents recognize when to ask

Measure success only if the agent detects ambiguity, asks a clarifying question, and acts on the user's response.

Measure failure modes

Track when agents guess instead of asking, confirm before acting when they should, or proceed despite infeasible constraints.

Report which skills matter most

Analyze whether the agent's main bottleneck is asking questions, interpreting answers, or planning multi-step sequences.

What the paper changes

What the paper changes

AppWorld-UL introduces a new benchmark dataset where agent success requires a specific behavior: pausing mid-task to ask clarifying questions or confirmations. The object of measurement is not how well an agent follows instructions, but whether it recognizes when an instruction is incomplete and interacts with the user to resolve ambiguity.

The hidden quantity

Agent-user interaction success rate

measured quantity  =  percentage of tasks where the agent asks and acts on feedback

The paper measures a quantity usually hidden in benchmarks: the rate at which an agent correctly recognizes that it needs user input, asks a well-formed clarifying question, and uses the user's response to complete the task correctly.

This quantity is tracked in two ways: first, whether the agent asks at all when faced with ambiguity; second, whether it asks the right kind of question (specific enough to resolve ambiguity, not vague or leading). The benchmark then grades success only if the agent's action after the user responds is correct, so the agent must both ask and listen.

Why it works

Why this benchmark exposes the gap

Current benchmarks hide the agent-user interaction gap because they avoid ambiguity entirely. A task is written so clearly that no interaction is needed. An agent trained to follow clear instructions does not learn to recognize when clarity is missing. AppWorld-UL reverses this: it introduces ambiguities systematically and measures whether the agent notices.

The paper creates ambiguity in a realistic way. Instead of adding random confusion, it removes details that a human might leave out: a user says "order my usual coffee" but does not specify which brand, price range, or package size. A real agent must recognize this gap, ask the user for those details, and then use the answer to pick the right product. Without this benchmark, models seem to solve the task (because a simpler version was trivial); with it, the models reveal a missing skill.

The second insight is user simulation. If a fake user can answer anything, then asking is not a skill — the agent just asks and gets help. AppWorld-UL constrains the simulated user so it knows only what a real person would: it cannot invent preferences it was never told, and it can refuse to do impossible things. This forces the agent to learn the difference between "ask for clarification" and "ask for magic."

Measuring success with and without interaction

First in words:

success_rate = (count of tasks where agent asked, received answer, and acted correctly) divided by (total tasks)

Then the compact form:

success = tasks_with_clarification_asked_and_used / total_tasks

Every symbol:

tasks_with_clarification_asked_and_usednumber of tasks where agent detected ambiguity, asked a specific question, got an answer, and used it to complete the task
total_taskstotal number of benchmark tasks (516)
successfraction of tasks completed correctly via agent-user interaction
A tiny worked example
Suppose a benchmark has 100 tasks with ambiguity.
Agent guesses on 40 tasks (gets 15 right by luck, 25 wrong).
Agent asks on 60 tasks (gets 50 right because user clarifies, 10 wrong because it misunderstood the answer).
Success rate via asking = 50 / 100 = 50%.
Success rate via guessing alone = 15 / 100 = 15%.
The benchmark reveals that asking is 3x better than guessing.

The paper reports 48.6% success on AppWorld-UL and 21.3% on compositional tasks, meaning Opus misses the ask-first skill on many tasks.

What can go wrong

What can go wrong

Agent guesses instead of asking. If an agent has been trained only on clear instructions, it learns to pick the most likely option when uncertain, rather than pause and ask. AppWorld-UL fails such agents because ambiguity is the test, not a bug.
Agent asks the wrong question. An agent might ask a vague clarification (like, "Do you want anything?") instead of a specific one (like, "Which brand?"). The user's answer will not resolve the ambiguity, and the task fails. The benchmark requires specificity.
Agent ignores the user's answer. An agent might ask a question correctly but then not actually use the user's response. For example, the user says "Green Mountain," but the agent orders a different brand anyway. The benchmark grades this as failure, because interaction must change behavior.
Agent confirms risky actions inconsistently. Some tasks involve actions that should not proceed without user say-so (like charging money). An agent that sometimes asks and sometimes does not is inconsistent. The benchmark penalizes both asking too little and asking unnecessarily.
Done right. An agent recognizes each type of ambiguity (missing detail, risky action, infeasible constraint), issues a specific question, waits for the user's bounded response, and then takes the right action. The benchmark rewards this and labels it success.
What a runnable demo should prove

What a runnable demo should prove

A demo should show a single agent facing a task with hidden ambiguity. First, log what the agent does when it is not required to ask: does it guess, and does it guess wrong? Second, show the same agent on a version of the task where it must ask: does it detect the ambiguity, formulate a specific question, and wait for an answer? Third, show the agent's action after the user responds: does it act on the answer, or does it ignore it? Fourth, measure success: count how many tasks require interaction, how many the agent asks on, and how many it solves correctly after interaction. The demo must make it impossible to miss that asking questions is the missing skill, and that guessing alone is insufficient.

agent_interaction_success = (tasks_solved_by_asking_and_listening) / (tasks_with_ambiguity)

The core insight: a task-completion benchmark is incomplete if it does not measure whether the agent asks for help when it needs it, because a model can appear to solve clear tasks yet fail silently on ambiguous ones, and hiding that failure gap makes the model seem better than it actually is for real-world use.
