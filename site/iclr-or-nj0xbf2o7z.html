Seesaw: Batch Size and Learning Rate Scheduling

Speed up large model training by swapping learning-rate cuts for batch-size growth and smarter step sizing.

Paper explainersAll themesOptimization

Training huge language models takes weeks. A simple observation: smaller batches need smaller learning rates (jumps), and bigger batches can handle bigger jumps. Seesaw trades one for the other — whenever you would shrink the learning rate in half, instead grow the batch in half and shrink the learning rate less aggressively (by the square root of 2). This keeps the training trajectory the same but finishes sooner by skipping redundant steps.

Zero assumption version

Training is slow because of learning rate schedules

When training a large language model, you feed it text in groups (batches). Each batch teaches the model a tiny bit by nudging the weights (the numbers inside the model that store learned patterns). The size of each nudge is called the learning rate.

A common trick: early in training, use bigger nudges (high learning rate) to move fast toward a good region. Later, use tinier nudges (low learning rate) to make small, careful adjustments near the answer. This works because tiny nudges keep the weights from overshooting and thrashing around — each step moves just enough to refine the solution without undoing what was learned before. This schedule of decreasing learning rate is called a learning-rate schedule, and it works well on current computers.

But here is the puzzle: if you use a bigger batch (more examples per step), you can afford bigger, bolder nudges, because you are averaging over more data so your estimate is more stable. And indeed, for simple training methods (like plain SGD), halving the learning rate is equivalent to doubling the batch size. Yet nobody knows if this trade works for Adam — the adaptive optimizer most people use for language models. So training schedules get tuned by guess-and-check, wasting time.

The method in one sentence: Seesaw replaces learning-rate cuts with batch-size growth, keeping training on the same path but finishing faster because bigger batches allow parallel computation, so the same amount of computation runs in fewer serial steps on the clock.

The algorithm as a flow

What it actually does

1. Start training

Launch with small batch size and large learning rate.

2. Detect a learning-rate cut point

When the standard schedule would halve the learning rate.

3. Swap the move

Double batch size, multiply learning rate by 1/sqrt(2) instead of 0.5.

4. Train the next epoch

Use more examples per step, smaller nudges, but same update direction.

5. Repeat until convergence

Keep swapping learning-rate cuts for batch growth.

What the paper changes

The one thing that changes

Seesaw changes the learning rate when the standard schedule would cut it. Instead of halving the learning rate, it shrinks it by the square root of 2 (a gentler cut) and doubles the batch size. This is a *substitution*: you perform the same scheduled cut, but in a different way.

the object it moves  =  Learning rate and batch size during cuts
The hidden quantity

The hidden quantity: loss dynamics

measured quantity  =  Loss dynamics (training path)

Loss is how wrong the model is on your data. As you train, the loss shrinks. A graph of loss over time is called the loss curve. The big secret: if you double the batch and shrink the learning rate by sqrt(2), the loss curve looks almost identical. This is not obvious — you might think bigger batches or different learning rates would change how fast the loss falls. But the paper shows they stay aligned.

The paper measures this by computing the loss at each step and checking that Seesaw and the standard schedule trace nearly the same trajectory. They also prove this theoretically using a tool from deep learning called the neural tangent kernel, which models how weights change during training on simple problems.

Paper reading. Loss dynamics preservation: the paper proves that for SGD on convex problems and for normalized SGD (a model of Adam), the loss follows the same trajectory when batch size and learning rate are adjusted by this specific recipe.
Why it works

Why it works: the deep reason

Here is the core idea: in noisy training, what matters is not how big each jump is, but how stable those jumps are. When your batch is small, each update is based on just a few examples, so it is noisy and wildly wrong. You cannot trust it, so you take tiny steps. When your batch is large, you average over many examples, so your direction is reliable, and you can take bigger steps.

The math relationship is: if you double the batch size, your estimate is twice as stable (the noise shrinks by the square root of 2). So you can make your learning rate bigger by the same square root of 2. If you do this, each step of training has the same effect on the loss — your trajectory stays on course.

Seesaw exploits this: instead of cutting the learning rate in half at a schedule point, it cuts by sqrt(2) and doubles the batch. The training dynamics stay the same, but now you are feeding twice as many examples per step. On a modern GPU cluster, this means you can run in parallel more efficiently, so *wall-clock time* (real elapsed time on the clock) shrinks by roughly 36%.

Math after the picture

The equation

First in words:

The new learning rate is the old learning rate divided by the square root of two, and the new batch size is the old batch size times two.

Then the compact form:

new_lr = old_lr / sqrt(2) ; new_batch_size = old_batch_size * 2

Every symbol:

new_lrThe learning rate after Seesaw's swap
old_lrThe learning rate before the swap
sqrt(2)The square root of 2, approximately 1.41
new_batch_sizeThe batch size (number of examples) after the swap
old_batch_sizeThe batch size before the swap
A tiny worked example
Before swap: batch size 512, learning rate 0.001
Standard cut: batch size stays 512, learning rate becomes 0.0005 (halved)
Seesaw swap: batch size becomes 1024, learning rate becomes 0.001 / 1.41 = 0.00071
The learning rate dropped by a factor of 1.41 (gentler than halving), and we feed twice as many examples in parallel, so elapsed time shrinks without changing training's path.

Doubling the batch shrinks the noise (because you are averaging over more examples), so you can increase learning rate by sqrt(2) and keep the same training direction with better stability.

What can go wrong

What can go wrong

Bigger batch might not fit in GPU memory. Doubling batch size means more examples loaded at once. If you are already maxed out, you cannot apply Seesaw.
The proof only covers simple training scenarios. The theory works for linear regression and a simplified proxy for Adam. Real deep learning is much messier, so the dynamics might not stay perfectly aligned in complex models.
Loss might diverge if batch grows too fast. Growing the batch and shrinking the learning rate has limits. If you double batch and cut learning rate too aggressively, the model can go off course.
Works well when you have parallelism. The speedup comes from running bigger batches in parallel. If your hardware is already saturated, the benefit shrinks.
What a runnable demo should prove

What a runnable demo should prove

Train a small language model (say, 10 million parameters) on a toy dataset for 100 steps. Plot the loss curve under (a) standard learning-rate schedule and (b) Seesaw. If Seesaw works, the two curves should overlap. Then measure wall-clock time: Seesaw should finish noticeably sooner because it skips the serial steps that bigger batches can run in parallel.

speedup = time_standard / time_seesaw ; curve_alignment = average_loss_difference_per_step

The demo makes one thing impossible to miss: the loss traces the same path (proving equivalence to the standard schedule) but the wall-clock timer runs faster (proving the speedup is real because modern GPUs parallelize bigger batches better than they serialize more steps).
