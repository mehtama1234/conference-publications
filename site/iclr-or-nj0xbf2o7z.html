Seesaw: Balancing Batch Size and Learning Rate to Accelerate Training

Instead of slowing down the learning step size as training goes on, double the number of examples per update and shrink the step size less aggressively, so the model learns the same way but processes data faster.

Paper explainersAll themesOptimization

Training large language models takes months because each learning step processes a limited number of examples at a time. Seesaw is a scheduler that lets you process more examples per step as training progresses, while adjusting how much each step changes the model in a way that keeps the learning curve identical. This trades serial wall-clock time for the same final result.

Zero assumption version

Why does training take so long?

Large language models train by looking at examples in small groups (batches) and adjusting weights a little at a time. Early training uses small batches because hardware can run many updates in parallel. But to keep learning steady, researchers cut the learning-step size (how much the model changes per update) as training goes on, like gently easing off the gas pedal.

The problem: small batches mean many serial updates, so even with parallelization, training takes months. A naive attempt would be to just use bigger batches throughout, but that breaks convergence because bigger batches magnify each step-size mistake—when you feed 1000 examples instead of 100, each update is noisier and less stable, so the model overshoots and the loss curve bounces wildly.

The contradiction. Bigger batches speed up training because each update sees more examples and processes them in parallel, so the wall-clock time per step drops. But the model learns the same thing only if you shrink the learning-step size at the right rate: more examples means less noise, so you need a smaller step to avoid overshooting. Standard methods do this by trial and error.

The algorithm as a flow

What it actually does

Track training milestones

Identify the steps where a standard scheduler would halve the learning rate (e.g. cosine annealing).

Swap out the slow move for a fast, equivalent one

Instead of halving the learning rate, multiply it by 1 divided by the square root of 2, and double the batch size.

Feed more data per step

Each weight update sees twice as many training examples, so the signal is smoother and more stable.

Keep the loss trajectory identical

Because the math of the update is preserved, the model loss improves on the exact same curve as standard training.

Run fewer steps total

Fewer milestones reached means fewer serial loops, so wall-clock time shrinks even though total work stays the same.

What the paper changes

What the paper changes

Seesaw changes the scheduler: the mapping from training step count to both the learning rate and the batch size. Standard schedulers keep batch size constant and decay only the learning rate. Seesaw decays the learning rate less aggressively (by dividing by square root of 2 instead of 2) and compensates by increasing the batch size (multiplying by 2).

the object it moves  =  scheduler (learning rate + batch size over time)
The hidden quantity

The hidden quantity: gradient noise stability

measured quantity  =  gradient noise relative to step size

Bigger batches make weight updates more stable because the signal from more examples averages out the randomness. When you feed 1000 examples instead of 100, each update gets a clearer picture of which direction to move the weights. Seesaw relies on this: it increases batch size so that the noise in the signal shrinks relative to the step size, keeping training smooth even as the step size gets smaller.

The paper measures this implicitly by checking that loss curves stay identical. If signal noise grew relative to step size, the loss would jump around unpredictably; the fact that it tracks perfectly shows the trade-off is working.

Why it works

Why it works: the math preserves the gradient update

The core mechanism is a Taylor expansion. Imagine two training paths: path A takes 2 small steps (each at learning rate η/2 and batch size B), while path B takes 1 big step (at learning rate η and batch size 2B). The paper proves these two paths move the model weights by nearly the same amount, so they arrive at similar loss values after the same cost in floating-point operations.

Because larger batches have lower noise, the signal in path B is smoother and more trustworthy than two noisy signals in path A. So path B gets to the same place with fewer serial steps. Seesaw applies this iteratively: whenever the standard schedule would halve the learning rate, Seesaw instead shrinks it by one over the square root of 2, and doubles the batch size, keeping the path aligned.

Math after the picture

The core equivalence

First in words:

loss_after_path_A = loss_after_path_B when: path A takes 2 steps at learning rate eta divided by 2 with batch size B; path B takes 1 step at learning rate eta with batch size 2 times B

Then the compact form:

η, 2B (one step) ≈ η/2, B (two steps) via Taylor expansion: loss(θ - η·g(2B)) ≈ loss(θ - η/2·g(B) - η/2·g(B))

Every symbol:

ηlearning rate (step size)
Bbatch size (number of examples per gradient)
g(B)gradient estimated from B examples
g(2B)gradient estimated from 2B examples
θmodel weights
lossthe error on validation examples
A tiny worked example
Assume loss gradient is 0.1 per example. Path A: batch 100, rate 0.01, two steps.
Step 1: gradient = 0.1 * 100 = 10 (noisier from small batch); move = 0.01 * 10 = 0.1.
Step 2: gradient = 0.1 * 100 = 10 again (noise hit twice); move = 0.01 * 10 = 0.1; total move = 0.2.
Path B: batch 200, rate 0.02, one step.
Step 1: gradient = 0.1 * 200 = 20 (cleaner, larger batch); move = 0.02 * 20 = 0.4... wait, that's 2x. But gradient noise is lower, so the step is more trustworthy.
Correct form: multiply rate by 1/√2 ≈ 0.707, not 2. Path B: rate 0.02 / √2 = 0.0141, move = 0.0141 * 20 = 0.282 ≈ 0.2.
Both paths move the model by ~0.2 units in weight space, arriving at similar loss values.

Bigger batches give cleaner gradients, so you can take fewer serial steps and land in the same place.

What can go wrong

What can go wrong

Batch size hits the critical batch size ceiling. Beyond a certain batch size, gradient noise is already nearly zero, so doubling the batch again provides almost no benefit. Seesaw must stop ramping when this ceiling is reached, or training will stall.
Scheduling mismatch with adaptive optimizers. The theory is proven for SGD and normalized SGD, a simplified version of Adam. Real AdamW has momentum and per-weight adaptive learning rates, so the equivalence may not hold exactly. The paper shows it works in practice but acknowledges this gap.
Memory constraint: bigger batches require more GPU memory. Doubling the batch size also doubles memory usage. If the model already fills the GPU, ramping batches becomes impossible without using model parallelism (more hardware complexity).
Done right: measure the critical batch size from real data. Train a model at fixed size, measure when accuracy stops improving, and cap Seesaw's batch ramps there. Pair with gradient checkpointing to reduce memory per batch.
What a runnable demo should prove

What a runnable demo should prove

Build a 10M-parameter language model on a small tokenized dataset (e.g., Shakespeare or WikiText-103 mini). Train it twice: once with a fixed batch size and cosine decay, once with Seesaw ramping the batch every 5k steps. Log the validation loss at each step, the batch size, and the learning rate. Record the wall-clock time for both runs.

wall-clock speedup = time_cosine / time_seesaw; loss-curve match = max absolute difference in validation loss across all steps

If Seesaw works, both runs will have nearly identical loss curves (difference < 1%) because the math is preserved, but Seesaw will finish 20-30% faster in wall-clock time because each milestone is fewer steps, even though both do the same total work.
