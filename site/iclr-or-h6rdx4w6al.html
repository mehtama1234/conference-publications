FlashVID: Efficient Video Understanding via Token Selection and Tree-Based Merging

Video models waste computation on redundant visual tokens; FlashVID picks the informative ones first, then merges the rest by finding similar patches across frames.

Paper explainersAll themesEfficiency & Systems

Video understanding models (which read video frames and answer questions about them) must process thousands of tiny visual patches, called tokens, which costs enormous computation. Most existing shortcuts either ignore how patches relate across frames, or squeeze space and time separately. FlashVID does both at once: it first keeps only the most informative tokens in each frame, then merges the leftover tokens by finding which ones represent the same spot moving and changing across frames.

Zero assumption version

Video models choke on redundant tokens

Video models read videos by breaking each frame into a grid of small image patches (tokens), stacking them up into one giant list, and feeding them to a language model. A 10-second video at 8 frames per second has 80 frames; if each frame is split into 576 patches, that is 46,080 tokens the model must process. The model reads this list one token at a time, and each read costs computation.

A naive approach: just keep all the tokens. This wastes computation because most video patches are boring or redundant. A single moving object might occupy dozens of tokens that all say nearly the same thing.

Better idea: compress them separately. One old method squeezes spatially (merge nearby patches within a frame because they often show the same thing). Another compresses temporally (merge patches across frames if they repeat). But doing them independently misses the real structure: a single spot in the scene changes over time (it moves, it tilts, it gets brighter), so the same logical token drifts across space and morphs as frames roll by. The spatial method does not know this is the same thing; the temporal method does not know space matters. Result: they kill tokens they should have kept, or keep tokens that truly are redundant.

The core problem. Video models waste computation on redundant tokens, and existing compression methods do not account for how a single moving object drifts across space and changes over multiple frames.

The algorithm as a flow

What it actually does

Extract token importance

Look at which tokens the vision encoder pays attention to (the [CLS] attention score). High score means informative.

Measure diversity within frame

Compute distances between all tokens in a frame. Pick tokens that are spread out, not clustered (one clustered patch carries no new info).

Combine attention and spread

Solve a max-min problem: pick a subset of tokens that are both high-attention and diverse. This is ADTS.

Match tokens across frames

Compute similarity between visual features of tokens in frame N and frame N+1 by measuring how aligned their directions are. If aligned enough, they likely show the same object.

Merge matching tokens via tree

Build a tree structure where leaves are tokens and branches merge similar ones. Merge nodes represent the same object across frames. This is TSTM.

What the paper changes

The one thing that changes

FlashVID changes which visual tokens the language model reads. Instead of processing all 46,080 tokens in a video, it keeps only the informative ones in each frame, then further reduces by merging tokens that represent the same moving object across frames.

the object it moves  =  visual tokens (spatial patches)
The hidden quantity

The hidden quantity: token importance and redundancy

measured quantity  =  Spatiotemporal redundancy

Spatiotemporal redundancy is how much the video repeats itself both within a frame (spatial) and across frames (temporal) at the same time. A quiet scene where nothing moves has high redundancy: the same patch shows up in almost every frame, in almost the same place. An action scene with camera motion and many objects has lower redundancy: tokens keep shifting and changing.

FlashVID estimates this by combining two signals. First, attention score: what does the vision encoder look at hardest (high attention means low redundancy, high information). Second, feature distance: how different is a token from its neighbors in space, and how different is a frame-1 token from potential matches in frame 2. Small distances mean redundancy (same thing repeating); large distances mean new information.

Why it works

Why it works: the causal chain

Keeping only informative tokens cuts computation immediately because the language model reads fewer tokens. But the real trick is merging matching tokens across frames. Here is why this works. In a video, most moving objects do not teleport; they flow. A ball in frame 1 at pixel (100, 200) is likely still the ball in frame 2 at pixel (105, 203). The two tokens represent the same thing. If you keep both and feed them to the language model as separate inputs, the model must learn that they are the same thing, wasting reasoning steps. If you merge them into one token labeled as the ball from frames 1-2, the model reads it once and knows it has seen this object across time. The tree structure automates this matching by grouping tokens that are similar enough.

Why merging does not kill accuracy: the information loss is low because you are merging things that are already redundant. When the ball is in frame 1 and frame 2, both tokens tell the model roughly the same fact (there is a ball here). The merged version still carries that fact; it just arrives once instead of twice. Tokens that are truly distinct (different objects, or the same object drastically changing) have low similarity and do not get merged. ADTS ensures you keep rare tokens within each frame (high attention, or spatially diverse), so critical details are retained. The tree structure forces you to merge only matched pairs, not arbitrary token clusters, preventing accidental loss of distinct information.

The equation: merging redundant tokens

First in words:

For each token in frame N and frame N+1, compute similarity. If similarity is above a threshold, merge them. The merged token inherits features from both frames. The cost of keeping tokens drops by the merge count.

Then the compact form:

similarity_ij = cos(feature_i, feature_j) for token i in frame N, token j in frame N+1. If similarity_ij > threshold, merge i and j into one token. Reduction = (original_token_count - merged_token_count) / original_token_count.

Every symbol:

feature_ithe learned representation (vector of numbers) for token i
feature_jthe learned representation for token j in the next frame
cos(feature_i, feature_j)cosine similarity: a number from -1 to 1, where 1 means identical direction, 0 means orthogonal
thresholdthe cutoff: above this, two tokens are considered redundant (represent the same thing)
merged_token_counthow many distinct objects remain after merging
A tiny worked example
Say frame 1 has 100 tokens, frame 2 has 100 tokens. ADTS keeps 50 from each (50% retention per frame).
Frame 1 token 15 (ball) has feature vector [0.9, 0.1, 0.0]. Frame 2 token 23 (ball at new location) has feature [0.88, 0.12, 0.02].
Cosine similarity: (0.9*0.88 + 0.1*0.12 + 0.0*0.02) / (sqrt(0.81+0.01) * sqrt(0.7744+0.0144+0.0004)) ≈ 0.82 / (0.905 * 0.882) ≈ 0.99. Above threshold (say 0.9). Merge them.
Frame 1 token 12 (sky) has feature [0.1, 0.1, 0.8]. Frame 2 token 35 (sky) has feature [0.09, 0.11, 0.79]. Similarity ≈ 0.99. Also merged.
After merging, 50 + 50 = 100 tokens become ~60 (some matches, some new objects). Reduction = 40/100 = 40%. Computation drops 40%. But both ball frames still inform the language model.

Merging cuts computation because tokens representing the same object across frames now count as one read, not two. The threshold prevents merging truly different things.

What can go wrong

What can go wrong

Threshold too low (merge aggressively). If the similarity threshold is set too loose, the method merges tokens that are only kind of similar (0.80 similarity, when should be 0.95). This drops accuracy because truly different objects get squashed together. The model then cannot distinguish ball from sky; accuracy falls fast.
Threshold too high (keep redundant tokens). If the threshold is too strict, the method refuses to merge even clearly matching tokens (ball in frame 1 and ball in frame 2 at similarity 0.98 stays unmerged). Computation stays high; you do not get the speedup.
Shadows and occlusion break feature matching. If an object casts a shadow or gets partially occluded between frames, its feature (the vector of numbers) can change so much that the similarity drops below threshold. Frame-1 ball is clearly visible, frame-2 ball is half in shadow. Features do not match; they do not merge. You end up keeping both.
Done right. With careful threshold tuning and diversity selection (ADTS), the method keeps critical tokens and merges only true redundancies. Most videos have enough stationary background and moving objects with smooth trajectories that the matching succeeds.
What a runnable demo should prove

What a runnable demo should prove

Build a simple video-understanding task: take a 10-frame video of a ball rolling across the screen, each frame 256 pixels, split into 64 patches per frame. Feed it to a small vision model (say, a tiny 4-layer neural network that reads image patches and relates them to each other). Measure how many tokens the model reads before answering the question 'Does the ball cross the midline?'.

Apply FlashVID. Set ADTS to keep the top 50% of tokens in each frame (by attention and diversity). Run TSTM to merge tokens with high alignment (at least 0.85 out of 1.0) across frames.

Measure: (a) How many tokens does the model now read? (b) Does it still correctly answer whether the ball crossed the midline? (c) Compute compression ratio by dividing tokens before by tokens after.

accuracy = (correct answers) / (total frames). Compression ratio = original tokens / (ADTS-filtered tokens merged by TSTM). Target: compression > 50% with accuracy drop < 2%.

The demo must show that by keeping only the important tokens and merging matching ones across frames, you get the same model behavior with far fewer reads. That is the entire point: the model answers the same way but on less data.
