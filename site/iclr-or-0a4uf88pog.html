VERINA: Benchmarking Verifiable Code Generation

VERINA is a benchmark that evaluates LLMs on writing correct code, formal rules about what that code should do, and proofs that the code actually obeys those rules—revealing which part is hardest.

Paper explainersAll themesDatasets & Benchmarks & Evaluation

When we ask a large language model to write computer code, we want three things: the code must run correctly, we need formal rules written out that say what the code should do, and we need a proof that connects them. VERINA is a test suite of 189 hand-written problems in Lean (a proof system) that measures how well models do at each of these three tasks separately and together. The results are humbling: models write correct code about 73% of the time, but they write correct formal rules only 52% of the time and formal proofs less than 5% of the time. This gap is the key story—models can describe what code should do, but proving it is much harder.

Zero assumption version

Three hard tasks mixed together

Before VERINA, benchmarks tested LLMs on code generation or specification writing or theorem proving—but never all three together. A developer working on safety-critical software needs all three: code that runs, a written contract about what it should do, and a logical proof that the code actually obeys the contract. A naive approach would test each in isolation with different datasets, missing how the three interact. That misses the real problem: a model that can write code may still fail at writing a formal specification for that code, and even if both work, proving the connection between them is an entirely separate challenge.

We also had no way to measure where models actually get stuck. Is it the code part, the specification part, or the proof part that breaks? Is proof generation genuinely harder, or just less well-trained? Without a single benchmark with all three, we cannot see the real bottleneck.

The method in one sentence. VERINA evaluates LLMs on code, specifications, and proofs as modular tasks, plus their end-to-end compositions, to expose where models struggle most.

The algorithm as a flow

What it actually does

Step 1: Curate 189 tasks

Write or adapt problems with code descriptions, implementations, and formal rules.

Step 2: Assign each task three pieces

Each task has a natural-language description, the code, a formal specification, and a proof.

Step 3: Test LLMs on each module separately

Can the model generate code from a description? A specification from description and code? A proof from description, code, and specification?

Step 4: Test end-to-end pipelines

Can the model generate all three without starting from ground truth at each step?

Step 5: Measure success rates per task

Count what passes: code that runs, specifications that are sound, proofs that are valid.

What the paper changes

The thing that changes—a modular evaluation structure

Before VERINA, the object being measured was code quality in isolation. VERINA changes the object to the evaluation pipeline itself: instead of one pass-or-fail for a whole task, it measures each of three components (code generation, specification generation, proof generation) separately, then measures their combinations. This lets you see if a model succeeds at code but fails at specifications, or write perfect code and specifications but cannot prove their connection.

the object it moves  =  evaluation structure—from single pass/fail to modular components
The hidden quantity

The verification gap—how much harder proofs are than code

measured quantity  =  verification gap (drop in success from code to specs to proofs)

VERINA measures a hidden quantity: the verification gap. This is the difference in success rates between writing correct code, writing correct formal specifications, and writing correct proofs. The paper measures this gap by running the same LLMs on the same 189 problems across all three tasks and comparing their success rates. The gap is the drop from one stage to the next—how much harder does the task get as you move from code to specs to proofs?

The paper estimates the gap by testing the best available models like OpenAI o3, which achieves 72.6% on code, 52.3% on specifications, and 4.9% on proofs. The gap is real and large. This hidden quantity tells researchers where to invest effort: specifications are 20 points harder than code, and proofs are 47 points harder than specifications.

Why it works

Why modular testing reveals the bottleneck

The mechanism is simple: testing all three components on the same problems, with both modular and end-to-end configurations, acts like a diagnostic tool. When you test code generation in isolation, the model succeeds 73% of the time. But when you ask the same model to generate a formal specification for the same problem, it only succeeds 52% of the time—even when you give it the correct code as input. This 20-point drop is not noise; it is a real signal that specification writing is genuinely harder. The model cannot reliably map from natural language and code into formal logical constraints. Similarly, asking for a formal proof that code obeys a specification is so hard that even the best models succeed less than 5% of the time.

Why does this happen? Writing formal specifications and proofs requires reasoning in a completely different mode—not just describing what to do, but stating unambiguous logical contracts and proving them. Code is executable and immediate feedback arrives when you run it; formal specifications and proofs have no concrete feedback until checked by a proof system, days or weeks later in typical development. Models trained mostly on code see far fewer examples of formal specification and proof writing. The modular structure exposes this gap by measuring each task separately. An end-to-end test would hide the fact that code generation is actually the relatively easy part—it would just show one overall success rate that masks the real problem underneath.

Measuring the verification gap

First in words:

success_code = number of tasks with correct code / total tasks; success_spec = number of tasks with correct specification / total tasks; success_proof = number of tasks with correct proof / total tasks; gap_1 = success_code minus success_spec; gap_2 = success_spec minus success_proof; total_gap = success_code minus success_proof

Then the compact form:

gap_total = pass_code - pass_proof = (72.6% - 52.3%) + (52.3% - 4.9%) = 67.7 percentage points

Every symbol:

A tiny worked example
Imagine 100 tasks. Model gets code right in 73 of them. Model gets specifications right in 52 of them (gap: 21 tasks lost).
Model gets proofs right in only 5 of them (gap: 47 tasks lost from specs level).
Total gap: 73 - 5 = 68 percentage points. Proof generation is 47 points harder than specification generation.

The gap grows larger at each step, showing that formal reasoning gets progressively harder as you move from code (concrete, executable) to specifications (abstract, logical) to proofs (rigorous, machine-checked).

What can go wrong

What can go wrong

Cherry-picked problems may not reflect real development. VERINA has only 189 problems, curated by hand. If these problems are atypical (all from textbooks, all on algorithmic topics), the results might not apply to messy production code with business logic or system design.
Lean proofs require specialized training. The low proof success rate (5%) might be an artifact of LLMs not seeing enough Lean examples in training. LLMs are pattern-matching machines trained on text: if they saw thousands of Lean proofs during training, they would recognize Lean syntax and common proof patterns better, simply because familiarity improves accuracy at test time, much like knowing how to write in a language's style. But this would be a false victory for correctness research—a model can memorize patterns and score higher on VERINA without actually developing reasoning ability. It would copy familiar templates from training rather than construct genuinely new logical steps for unseen problems, so improving the score would not mean we have solved verification.
One-shot evaluation misses iterative refinement. VERINA tests one attempt per task. In practice, developers iterate: write proof, read error, refine proof. Agentic models with iterative feedback can reach 20% proof success (versus 5% one-shot). The benchmark measures cold-start, not interactive development.
Done right: rigorous artifact for spurring research. VERINA is hand-curated, machine-checked (proofs are validated by Lean's proof checker—a program that ensures every logical step is correct), and openly reveals the gap. It directly invites researchers to close the verification gap—a clear, measurable target.
What a runnable demo should prove

What a runnable demo should prove

A convincing demo would take VERINA's 189 problems and run a modern LLM (e.g., OpenAI o4-mini or an open model like DeepSeek-V3) on all three tasks: code generation, specification generation, and proof generation. It should report pass rates for each module independently and for end-to-end pipelines. The demo must show that the verification gap replicates: code success is high, specification success is markedly lower, and proof success is very low. It should also measure whether giving the model iterative feedback (reading Lean compiler errors and refining its proof attempt) improves proof success rates—the paper shows this can triple success rates up to 20%, because when the model reads an error message, it can diagnose which logical step failed and adjust that specific piece rather than starting from scratch. The demo must make it impossible to miss the core message: formal reasoning (specs and proofs) is the hard part of verifiable code, not implementation.

verification_gap = (pass_code - pass_proof), where pass_code = tasks with correct code / all tasks, pass_proof = tasks with correct proofs / all tasks

The verification gap—the 67-point drop from code to proofs—is the real discovery, and the demo must make this gap visible by showing raw pass rates for all three components on the same problem set.
