Turning Adaptation into Assets: Cross-Domain Bridging for Online Vision-Language Navigation

A navigation agent learns to save and reuse previous solutions when facing new environments, avoiding forgetting old knowledge.

Paper explainersAll themesAgents & Tool Use

A robot navigating indoors must adapt when the building changes or the camera breaks. The naive fix (retrain on the new place) makes it forget the old place. IDEA does something smarter: it saves the adaptive moves it made for each place as reusable assets, then finds a middle ground between old and new by combining them. No retraining needed.

Zero assumption version

The robot forgets when the world changes

A vision-language navigation agent is trained in one building to understand language commands like 'go to the kitchen' and use camera images to move. It works well there. But then the building gets renovated, or the robot is shipped to a new facility. The camera may break or the lighting changes. When the robot tries to adapt online (learning from the new place without a full retrain), something goes wrong: it gets better at the new building but suddenly fails at the old one, because the learning process nudges the weights to fit new examples, and those nudges undo the adjustments that made the old building work.

A beginner might think: just keep learning from both places at once. But in practice, the new examples overwhelm the old patterns, or the learning signal sends contradictory nudges (old place wanted a left turn, new place wants right). This is because both signals compete to move the same weights, so the weights end up in a compromise position that works poorly for both places — like trying to steer a car to two destinations at once.

The core problem. When an agent adapts to a new situation by learning, it overwrites what it learned about old situations, losing competence in both.

The algorithm as a flow

What it actually does

Step 1: Learn soft prompts for the current domain

Robot adjusts a small set of learnable text-like instructions (soft prompts) to work in the new place.

Step 2: Weight the prompts by importance

The Fisher weighting scheme measures which prompt settings matter most for good navigation, like measuring which gears in a clock are critical.

Step 3: Tag and store in the asset library

The optimized prompt is saved along with a label for this domain (Building B, Camera-4, etc.) so it can be found later.

Step 4: Find the convex hull

A geometric middle ground is computed from all previous domains, like finding the center of a scatter of points in space.

Step 5: Use the bridge for the next new domain

When a new domain arrives, start from this middle-ground position, which means fewer learning steps are needed (faster), and because the starting point is already balanced between old domains, the robot is less likely to overshoot and forget them.

What the paper changes

What the paper moves

IDEA changes soft prompts: small, learnable instructions that guide the language-to-action pipeline. Instead of retraining the entire model, only these tiny instructions are adapted. They are saved and reused across domains, forming a library.

the object it moves  =  soft prompts for navigation
The hidden quantity

The hidden quantity: Fisher importance of each prompt setting

measured quantity  =  Fisher-weighted prompt importance

Not all parts of a soft prompt matter equally. When you nudge one prompt number, the model's errors might barely change, while nudging another number could swing the error greatly. The Fisher weighting is a measurement of this: for each prompt setting, it computes how much moving that number would affect the loss (the error rate in navigation). High Fisher value means that setting is critical; low means it is barely used.

The paper uses Fisher importance to decide which learned adaptations to save in the library. Prompts with high Fisher weight are the ones that genuinely transfer across domains; prompts with low weight are noise specific to one place.

Why it works

Why it works: the loop of assets and bridging

The core insight is that catastrophic forgetting happens because the new domain's learning signals push weights in directions that undo the old domain's setup. IDEA breaks this by never directly fighting. Instead, it saves adaptations as separate assets (one per domain, each tagged with domain coordinates), which means the learned instructions for domain A stay locked away and are not overwritten when domain B learns. When a new domain arrives, the robot does not try to nudge weights from the old domain's state; instead, it starts from a computed middle ground (the convex hull of all previous domains). This middle point is by construction close to all previous domains, so it cannot suddenly move far from any one.

The loop amplifies this: as the asset library grows, the bridge (convex hull) gets tighter and more centered, providing a better initialization for the next adaptation. Better initialization means less learning is needed, which means less chance of overfitting to just the new domain and forgetting the old. The Fisher weighting keeps only the genuinely important adaptations in the library, discarding domain-specific noise.

Math after the picture

The equation: bridging via convex combination

First in words:

The new prompt is initialized as a weighted mix of the best previous prompts from the asset library, where the weights are chosen so the result sits inside the convex hull of all previous prompts.

Then the compact form:

prompt_new = sum_i weight_i * prompt_asset_i, where sum_i weight_i = 1, weight_i >= 0, and prompt_new minimizes distance to optimum while staying in convex_hull(all historical prompts)

Every symbol:

prompt_newthe soft prompt for the newly arrived domain
prompt_asset_ithe i-th saved prompt from the asset library
weight_ithe coefficient for blending prompt asset i (all weights sum to 1)
convex_hull(all historical prompts)the region bounded by connecting all previous prompts; staying inside avoids sudden jumps away from past domains
Fisher_weight_jthe importance score for the j-th prompt setting, computed from the Fisher information matrix
A tiny worked example
Suppose we have two domains in the library: Building A has prompt [0.7, 0.3, 0.5] and Building B has prompt [0.4, 0.6, 0.4].
When a new domain C arrives, we initialize by taking a mix: 0.5 * [0.7, 0.3, 0.5] + 0.5 * [0.4, 0.6, 0.4] = [0.55, 0.45, 0.45].
This new point [0.55, 0.45, 0.45] sits exactly in the middle of the two old points in the 3D space.
When the robot adapts its prompts for domain C, it starts from this balanced point, not from a point far from both A and B.
If a third domain D comes later, we again blend from the library (now larger), keeping all previous domains represented.

The convex hull is the smallest shape that contains all old prompts; any point inside it is guaranteed to be 'close enough' to at least one old domain, preventing sudden drift.

What can go wrong

What can go wrong

Asset library grows too large and slows down. If many domains are added without pruning, the convex hull becomes high-dimensional and expensive to compute. Remedy: keep only the most important Fisher-weighted prompts, or prune old domains that have become redundant.
New domain is radically different from all historical domains. If domain C is completely unlike A and B (e.g., moving from indoor to outdoor), the convex hull bridge may be far from optimal for C. The robot must do more learning to escape the bridge, risking overfitting. Remedy: monitor learning curves and revert to pure adaptation if the bridge is clearly harmful.
Fisher weighting is noisy on small datasets. If the new domain has few samples, the Fisher estimate is unreliable, so the importance scores are meaningless. Remedy: use adaptive Fisher smoothing or require a minimum dataset size before storing in the library.
Done right. The library should contain diverse domains with high-quality Fisher weights, the bridge should be recomputed with each new domain, and new adaptations should be monitored for signs of overfitting or domain shift.
What a runnable demo should prove

What a runnable demo should prove

Build a toy navigation environment with two simple layouts (a grid with obstacles forming a maze). Train an agent on Layout A (100 episodes). Then, introduce Layout B (different obstacles) and adapt online without retraining. Measure success rate on both A and B before and after adaptation. Implement two versions: (1) Naive adaptation (just update all parameters) and (2) IDEA (save soft prompts with Fisher weights, initialize new domain from convex hull). The demo should show that naive adaptation causes A's success rate to drop sharply after adapting to B, while IDEA keeps both high.

Forgetting_gap = (success_A_before - success_A_after_naive) - (success_A_before - success_A_after_IDEA). Higher gap shows IDEA prevents forgetting.

The single most important proof: after adapting to a new domain, the old domain does not regress. That is what IDEA delivers.
