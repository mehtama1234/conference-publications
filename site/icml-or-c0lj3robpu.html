SPARC: Separating Perception And Reasoning Circuits for Test-time Scaling of VLMs

Split seeing from reasoning so a model can spend compute where the bottleneck actually is while generating an answer.

Paper explainersAll themesMultimodal

A vision-language model often answers a question by mixing two jobs in one long text chain: first determine what parts of the image matter, then reason over those parts. When those jobs are entangled, one small seeing error can pollute every later reasoning step. SPARC separates them. It runs an explicit visual search stage to localize question-relevant regions, then runs reasoning on the resulting evidence. This lets the system scale perception and reasoning independently, which matters because some failures come from missing the right region while others come from weak multi-step reasoning.

Zero assumption version

Why one long reasoning chain breaks visual question answering

In a monolithic vision-language model, image patches, meaning small regions converted to model inputs, and reasoning tokens, meaning text-side steps in the answer chain, all live in one context. The model can spend hundreds of tokens describing possibilities before it has even locked onto the relevant object. If the early guess about location is wrong, the later chain reasons carefully about the wrong evidence.

This becomes worse under test-time scaling, meaning the practice of giving the model more compute during answer generation only when a problem looks hard. In a monolithic system, extra compute extends the same mixed chain. That spends more budget on already-corrupted context instead of separately fixing perception or separately extending reasoning. The result is long outputs, brittle answers, and poor control over where the compute went.

The paper's move in one sentence. Make the model search the image first and reason second so perception and reasoning can each receive their own compute budget.

The algorithm as a flow

What it actually does

Read the question and coarse image

Start with a low-resolution global pass so the model can scan the whole scene with fewer visual tokens because coarse search is enough to rule out most irrelevant regions.

Run explicit visual search

Propose image regions that are likely to contain evidence for the question because the answer should depend on localized visual facts.

Allocate high resolution only to chosen regions

Crop or revisit the selected regions at finer detail so compute is spent where ambiguity is highest.

Pass the retrieved evidence to the reasoning stage

Condition the answer module on the selected regions instead of on the full raw image context.

Scale either stage when needed

Increase search depth, reasoning depth, or both depending on which stage is limiting end-to-end accuracy.

What the paper changes

What the paper changes

The paper changes the answer-generation graph. It separates the visual evidence-gathering pathway from the answer-generation pathway so errors and compute budgets can be managed stage by stage.

The hidden quantity

The hidden quantity

measured quantity  =  whether the answer failure came from missing evidence or from weak reasoning over correct evidence

A wrong answer in a vision-language model can come from two distinct causes. The model may have looked at the wrong region, or it may have looked at the right region and still failed to combine the facts correctly. A monolithic chain hides that difference because both errors appear only as a bad final answer.

SPARC exposes that hidden split. Once the system produces explicit region selections, developers can inspect whether the evidence was present before reasoning began. That matters because extra perception compute helps only the first kind of error, while extra reasoning compute helps only the second kind.

Why it works

Why separation improves test-time scaling

Separating perception from reasoning reduces error cascades because the reasoning stage receives a curated evidence set instead of a raw scene plus a speculative text chain. If visual search is wrong, that mistake is visible early and can be corrected with more region proposals or higher resolution. In a monolithic chain, the same mistake is buried inside many later tokens.

The method also lowers token cost because most questions do not need high-resolution processing over the entire image. A low-resolution scan can find candidate regions, and only those regions are revisited in detail. That preserves important local information while avoiding the cost of converting every patch at full detail into context tokens.

The largest benefit is control. Test-time scaling becomes a targeted intervention rather than a uniform lengthening of the entire answer-generation trace. Under a shift in image statistics, the system can spend more budget on perception because the visual appearance changed. On logic-heavy questions with clear visual evidence, it can spend more budget on reasoning because the visual grounding is already sound.

Separate the compute budget

First in words:

A compact way to describe SPARC is to split inference cost into a perception term and a reasoning term and allocate them independently.

Then the compact form:

C_total = C_perception + C_reasoning

Every symbol:

C_totaltotal inference cost for one question
C_perceptioncost of scanning the image, proposing regions, and revisiting them at higher resolution
C_reasoningcost of the text-side reasoning stage that consumes the selected evidence
A tiny worked example
Suppose a monolithic system spends 200 visual tokens on the full image and 120 reasoning tokens, for total cost 320.
A SPARC-style run might spend 40 low-resolution tokens to scan globally, 20 high-resolution tokens on two regions, and 80 reasoning tokens on the selected evidence, for total cost 140.
The lower total matters because the model kept detailed processing only where the question needed it.

The paper's exact accounting can use token counts and module calls, but the core idea is the same: the two stages are separable budget terms.

What can go wrong

What can go wrong

The search stage can prune away needed evidence. If the relevant region is never proposed, reasoning has no path to recovery because the answer module only sees the selected evidence.
Reasoning may depend on global context. Some questions require relations across distant regions. If compression is too aggressive, the selected evidence can omit global cues that the final deduction needs.
Stage interfaces can become brittle. If the search module produces region summaries in a format the reasoning module does not use well, separation can add interface loss instead of reducing confusion.
Done right. The method is strongest when questions hinge on localized evidence and when developers need control over whether added compute should improve seeing or improve step-by-step reasoning, because the two stages can then be diagnosed and scaled separately.
What a runnable demo should prove

What a runnable demo should prove

Build a document or chart question-answering demo with two pipelines. The baseline reads the whole image and answers in one chain. The SPARC version first selects relevant panels or table cells using a search module, then answers from those regions.

Track answer accuracy, number of visual tokens processed, and whether failures came from wrong region selection or wrong reasoning. The demo should show that the modular version keeps a clearer error breakdown because the search output is explicit, and it can improve one stage without rewriting the other because perception and reasoning are separate modules.
