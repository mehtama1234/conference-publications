Ramba: Selective State-Space Models for Relational Deep Learning

A fast neural model that reads a database table by table, picking which columns matter for your prediction using automatic semantic filters.

Paper explainersAll themesGraph & Geometric Learning

A database is a puzzle with pieces in different tables. Neural networks today either solve it slowly (by reading everything at once) or quickly but stupidly (by reading each table alone and forgetting context). Ramba reads the whole puzzle in linear time — meaning time scales with the amount of data, not in a quadratic explosion — by automatically deciding which table columns actually matter for your answer.

Zero assumption version

Reading a database the slow or stupid way

Databases are messy and spread out. A customer table has names and emails. An order table has purchase dates and amounts. To predict whether a customer will buy next month, a model needs facts from both tables. Today's best neural networks, called transformers (models that learn patterns by comparing every piece of data to every other piece), can read all the tables at once and find hidden connections. But there is a catch: the time it takes grows quadratically. Read one thousand rows and one thousand columns — the transformer has to compare every row to every row and every column to every column. That is one billion comparisons. Read ten thousand rows — suddenly it is one hundred billion comparisons. The cost explodes. Meanwhile, graph neural networks (models designed to read connected data) stay fast by reading just one table at a time, losing the ability to see across tables entirely.

A naive beginner might try: read every column from every table, throw it all at a transformer, and hope it finds what matters. The transformer will drown. Or, read each table alone with a graph network, lose the connections between tables, and predict poorly. Neither works.

The problem in one sentence. Transformers can see everything but are quadratically slow; graph networks are fast but read tables alone.

The algorithm as a flow

What it actually does

Serialize the database

Stack all table columns into a single long sequence, preserving which rows belong to which customer, which orders to which customer.

Scan left to right

A state-space model (a fast sequential neural unit) reads this sequence one column at a time, updating its memory as it goes.

Semantic gate watches the target

At each column, a learnable gate network estimates whether this attribute helps predict the target, because columns with high correlation to the target should update the model's state more strongly.

Relevant columns shape the state

When the gate is high, the column's values update the model's memory strongly. When low, the model ignores it.

Sparse comparison along foreign-key edges recovers structure

The model compares column values only along foreign-key edges (links between tables) so order 7 is linked to customer 2, preserving relational structure without full quadratic cost.

What the paper changes

What the paper changes

Ramba changes two things. First, how to read the database: serialize it into a single column-by-column sequence and scan it once with a linear-time state-space model instead of a quadratic transformer. This avoids the explosion of comparisons because you visit each value once instead of comparing every row to every row. Second, what the model remembers: only the semantic features that help with your prediction task via a learnable gating mechanism. This keeps the model's memory focused because irrelevant columns barely update the state, forcing the learned weights to concentrate on predictive features.

The hidden quantity

Semantic alignment: which column matters now

measured quantity  =  semantic relevance score

The paper measures a quantity it calls semantic alignment: for each column in the database, how well does this attribute predict your final target? Is the customer's email relevant to churn prediction? Not really. Is the total order amount? Yes, very much. The alignment is high for order total, low for email. This quantity is the hidden filter that makes Ramba smart.

The paper estimates this alignment using a learnable gate network that takes (the target task, the current attribute) and outputs a score. During training, the gate learns to boost the score when the attribute is predictive and suppress it when it is noise, because examples with high predictive power push the model toward high gate scores while irrelevant examples push it toward low scores, and the gate's weights adjust to maximize prediction accuracy. This is how the model automatically discovers which columns matter for the prediction, without anyone hand-coding a rule.

Why it works

Why it finds relevant columns and stays fast

The trick has two parts. First, serialization: instead of treating a database as a graph (every table linked to every other, leading to quadratic complexity), Ramba flattens it into a single sequence. Read customer ID, then customer name, then order date, then order total, table by table, row by row. A state-space model (think of it as a sliding window with learnable rules) reads this sequence in time proportional to the total number of values. No quadratic explosion because each value is visited once.

Second, semantic gating: a transformer or graph network would treat every column the same. Ramba asks, at each step: does this column predict my target? If yes (high gate), the column's values update the model's internal state (its memory of what it has learned). If no (low gate), the state stays put, and the column is skipped. This filtering is learned automatically during training. The gate is a tiny neural network that sees (the target you are trying to predict, the current attribute name or type) and outputs a relevance score. Over many examples, it learns: order total is high relevance for churn prediction, customer email is low. This selective updating is what makes Ramba both fast and smart — fast because it processes each value once in sequence; smart because it focuses only on semantically aligned information.

Sparse foreign-key comparison is the final piece. To preserve the relational structure (knowing that order 7 belongs to customer 2), Ramba compares values only along foreign-key edges. Instead of comparing every row to every row (quadratic), it only connects related rows (linear edges in the foreign-key graph). This recovers the relational structure without the cost.

Math after the picture

Selective state update with semantic gating

First in words:

New state equals (1 minus gate score) times old state plus gate score times (new input processed by state-space model)

Then the compact form:

h_t = (1 - g_t) * h_{t-1} + g_t * SSM(h_{t-1}, x_t)

Every symbol:

h_tthe model's memory (state) after reading column t
h_{t-1}the model's memory before reading column t
g_tthe semantic relevance gate score for column t, a number from 0 to 1
x_tthe value of column t (the input)
SSM(h_{t-1}, x_t)the standard state-space model update: how to compute the new state from the old state and new input
A tiny worked example with three columns
Column 1 (customer_name): gate score g_1 = 0.1 (low relevance to churn). Old state h_0 = [0, 0]. Input x_1 = name_embedding. New state h_1 = (1 - 0.1) * [0, 0] + 0.1 * SSM([0, 0], x_1) = 0.9 * [0, 0] + 0.1 * [2, 1] = [0.2, 0.1]. The column barely changed the state.
Column 2 (order_total): gate score g_2 = 0.9 (high relevance). Old state h_1 = [0.2, 0.1]. Input x_2 = amount_embedding. New state h_2 = (1 - 0.9) * [0.2, 0.1] + 0.9 * SSM([0.2, 0.1], x_2) = 0.1 * [0.2, 0.1] + 0.9 * [5, 4] = [0.02, 0.01] + [4.5, 3.6] = [4.52, 3.61]. The column strongly updated the state.
Column 3 (product_color): gate score g_3 = 0.05 (irrelevant). Old state h_2 = [4.52, 3.61]. New state h_3 = (1 - 0.05) * [4.52, 3.61] + 0.05 * SSM(...) approx [4.29, 3.43]. The state coasted, barely changing.

The gate acts as a weighted blend: when the gate is high, the new input dominates the state update; when low, the state remembers its past and ignores the input. This is how Ramba filters to semantic relevance.

What can go wrong

What can go wrong

Gate learns the wrong relevance. If the training data is imbalanced (many non-churners, few churners), the gate might learn to ignore rare but important signals. A customer with a single huge order might be a key indicator of churn, but if such orders are rare, the gate suppresses them.
Serialization order matters. If you linearize the database as customer_id, order_total, customer_name, order_date, the state-space model reads order_total before it knows which customer it belongs to. A bad serialization can scramble relational meaning.
Sparse comparison misses distant connections. Foreign-key links only connect tables via foreign keys. A prediction that depends on a chain of links (customer -> order -> product -> supplier) may fail if the chain is not in the foreign-key graph.
Done right. Use class-balanced training or re-weighted losses so rare signals still teach the gate. Serialize tables in a sensible order (customers first, then their orders and products). Ensure the foreign-key graph is complete and acyclic.
What a runnable demo should prove

What a runnable demo should prove

Build a small synthetic relational database: a customers table (id, age, city, signup_date) and an orders table (customer_id, date, total_amount, shipping_days). Create a binary prediction task: will this customer buy within 30 days? Train Ramba alongside a standard transformer on databases of increasing size (100 rows, 1000 rows, 10000 rows, 50000 rows). For each size, measure (1) prediction accuracy, (2) wall-clock inference time in seconds, (3) peak memory usage in megabytes.

accuracy = (correct_predictions) / (total_predictions); time_ratio = time_ramba / time_transformer; memory_ratio = mem_ramba / mem_transformer

The demo must make it impossible to miss: as the database grows from 100 to 50000 rows, Ramba's accuracy stays flat (84-88%), its time stays linear, and its memory stays flat. Transformer's accuracy plummets (92% -> 35%) and its memory explodes. The gate's learned relevance scores should show high engagement on order_total and signup_date, low engagement on city and shipping_days.
