Mix-Ecom: E-Commerce Dialogues with Dynamic Rule Filtering

A dataset and filtering framework that teaches dialogue agents to ignore irrelevant rules and hallucinations, handling real messy e-commerce conversations.

Paper explainersAll themesDatasets & Benchmarks & Evaluation

E-commerce chatbots fail when conversations mix multiple types at once (asking questions, then requesting recommendations, then complaining about shipping). Current datasets test only simple, clean versions. Mix-Ecom adds a real-world dataset of 4,799 mixed-type conversations plus a dynamic module that filters out irrelevant rules before the agent reasons, cutting down hallucinations and confusion.

Zero assumption version

The real world is messy; benchmarks are too clean

A customer might start by asking about a product, then shift to requesting a recommendation, then complain about shipping. Real e-commerce conversations are full of these mode switches. But today's benchmarks test agents only on one dialogue type at a time (just recommendation, or just support tickets).

Worse: agents see a big pile of 82 rules (inventory rules, refund policies, shipping rules, loyalty rules, return windows, etc.). A naive agent loads all of them into memory and tries to apply every one, even when only 3 are relevant. The agent gets lost, invents facts to fill gaps (hallucination), and confidently gives wrong advice.

In one sentence. Filter to only the rules that matter for this customer's question, before the agent starts reasoning.

The algorithm as a flow

What it actually does

Real data collected

Start with 70,000 real customer-service calls; manually pick 4,799 that mix dialogue types.

Privacy scrubbed and reasoning added

Remove customer names, account IDs, sensitive data; add the agent's thinking process to each one.

At each reasoning step

The dynamic module receives the customer's message, the full rule set, and the agent's history so far.

Filter rules and hallucinations

Select only rules matching the task type (refund rules for refund requests, shipping rules for shipment questions).

Agent reasons on clean context

Reasoning model sees a small set of relevant rules, not 82; generates fewer false claims.

What the paper changes

What the paper changes

The paper introduces two linked changes: a dataset of real mixed-type conversations (which did not exist), and a dynamic rule-filtering module that runs before each reasoning step.

the object it moves  =  Rule set and trajectory
The hidden quantity

The rule relevance score

measured quantity  =  Which rules apply to this task type

Hidden inside this paper is a classification: for a given customer utterance and task type (refund, recommendation, shipping question, chit-chat), which of the 82 rules should the agent see? The module estimates a score for each rule: does this rule matter for handling this request right now?

The paper measures this by filtering the rule set based on the task type detected from the customer's message. The agent's reasoning trajectory is also cleaned: steps that contradict the selected rules are marked as hallucinated and removed before the next reasoning cycle.

Why it works

Why filtering before reasoning works

Imagine you are a customer service agent with 82 rule sheets on your desk. A customer asks about a refund. If you flip through all 82 sheets—inventory controls, loyalty tiers, shipping fees, chit-chat guidelines—you will cross-reference constantly, forget which sheet you were on, and invent details to fill holes. Your brain burns out and you hallucinate.

Now imagine someone hands you only the 3 refund-related sheets first. You read those. Your reasoning is clearer. You make fewer mistakes. The dynamic module is that filter. It intercepts each new customer message, scans the 82 rules, and says: today, only use sheets 5, 12, and 47. The agent then reasons on that smaller, task-focused set. Hallucinations drop because there is no conflicting irrelevant information to confabulate around.

Math after the picture

The filtering formula

First in words:

For each step, pass only the rules that match the task type to the reasoning agent. Hallucinated steps (claims that violate the kept rules) are pruned from the trajectory before the next reasoning cycle.

Then the compact form:

P_f = {p ∈ P : task_type(U_t) matches p.domain}; H_f = prune(H, P_f)

Every symbol:

Pthe full set of 82 domain rules
P_fthe filtered subset: only rules relevant to the current task
U_tthe user's current utterance (message)
task_type(U_t)the detected type of the user's request: refund, recommendation, shipping, or chit-chat
Hthe reasoning trajectory so far (all thinking steps and actions)
H_fthe cleaned trajectory: hallucinated steps contradicting P_f are removed
prunethe function that removes trajectory steps that make false claims under the kept rules
A tiny worked example
User says: Can I get a refund on my order?
task_type = 'refund' detected
Original P has 82 rules; 8 match task_type='refund'
P_f = {refund_policy_days: 30, refund_penalty: 10%, escalation_trigger: 3_attempts, ...}
Agent now reasons using only these 8 rules, not 82
If the agent's prior step claimed a loyalty bonus (not in P_f), it is removed from H before next cycle
H_f now reflects only steps that will apply to refunds

The reason this works: constraining the rule set before reasoning shrinks the hallucination surface, because the agent cannot invent explanations using rules it does not see.

What can go wrong

What can go wrong

Task type detection is wrong. If the module misclassifies the user's message (says it is a recommendation when it is a refund), it filters to the wrong rule set and the agent gives bad advice. The filter is only as good as the task classifier.
A rule is interdependent across types. Some rules apply to multiple task types (e.g., a loyalty-point rule affects both refunds and recommendations). Filtering too aggressively removes needed context. The paper handles this with multi-domain rule tags, but edge cases still trip up the module.
New or unseen rule combinations. If a rare combination of two rules (a refund policy plus a seasonal sale rule) is never seen in training, the filter might not include both rules when needed. The agent then hallucinates the interaction.
Done right. Task detection is reliable (high precision classifier), rules are tagged with all their relevant domains (no missing metadata), and the training set covers enough rule combinations to avoid cold-start failures.
What a runnable demo should prove

What a runnable demo should prove

Build a small e-commerce dialogue agent on top of Mix-Ecom with and without the dynamic module. Feed it 50 mixed-type test dialogues. For each one, record whether the agent's final answers match the ground-truth keys (product details, refund windows, shipping costs, etc.), and count hallucinated claims (false statements the agent made).

hallucination_rate = hallucinated_claims / total_claims_made; key_accuracy = correct_keys / total_keys_in_ground_truth

The demo must show that filtering rules before reasoning cuts hallucinations in half and raises key accuracy by at least 15 points—proving that removing irrelevant noise sharpens the agent's focus.
