Formal Problem-Solving: From Verification to Construction

This paper moves from just checking math proofs to finding unknown answers by forcing every result through formal verification.

Paper explainersAll themesAgents & Tool Use

Large language models can reason through math, but they hallucinate—they invent facts that sound right but are actually wrong. Formal theorem proving (a system where every logical step is checked by a computer) stops this by verifying each step. But current systems only verify known facts; they do not find unknown ones. This paper bridges that gap by treating the answer itself as an unknown that must be mathematically derived and verified.

Zero assumption version

Why hallucinations persist in math reasoning

When a large language model solves a math problem, it predicts the next word, then the next, building an answer step by step. It has no built-in way to check whether each step is actually true. A model might write two plus two equals five and keep going, and nothing stops it.

Formal theorem proving systems (like Lean 4, which is a special programming language for writing proofs) can check every logical step automatically. But they have a big limitation: they only verify proofs of things you already know are true. If you want to find a number or expression that satisfies some condition (like finding the value of x that makes an equation true), theorem provers cannot easily do that. They are built for checking, not constructing.

A beginner might try training a model to output the answer directly and hope it is correct. That fails because without verification, wrong answers look identical to right ones until you test them.

The paper's move in one sentence. Treat the answer as an unknown value to be found through formal proof, not predicted through text.

The algorithm as a flow

What it actually does

1. Pose the problem as an unknown.

Instead of asking the model to predict the answer, write a Lean proof that declares the answer as a variable to be filled in.

2. Build a proof obligation.

The Lean system automatically generates a set of constraints that the unknown must satisfy (e.g., the equation it must solve).

3. Forward derivation.

The model works step by step from the given information toward the unknown, deriving facts that bring it closer.

4. Backward verification.

The model simultaneously checks that the unknown value actually satisfies the constraints (the proof obligation closes).

5. Lean verifies the entire chain.

The Lean system automatically confirms every step, so the final answer is mathematically guaranteed to be correct.

The paper shifts from predicting an answer as text to deriving an answer as an unknown value embedded in a formal proof. The answer is not a guess; it is something the system must construct to satisfy proof constraints.

The hidden quantity

The alignment tax—hidden gap between verification and construction

measured quantity  =  alignment tax (effort gap)

The paper uncovers a hidden quantity: the alignment tax. This is the gap in difficulty between verifying a proof (checking a known statement) and solving a problem (finding an unknown value). Verification is easy because you just check each step. Solving is hard because the model must decide what steps to take without knowing the destination.

The paper measures this by running the same benchmarks in two modes: verification mode (given the statement, check if it is true) and solving mode (given only the constraints, find the answer). The gap reveals why purely predictive models fail—they have no built-in process for systematic construction.

Why it works

Why treating the answer as unknown forces correctness

When a model predicts text word by word, it has no constraint checking it. The model can output any sequence, true or false. The system does not care; it just produces the next word.

When the answer is declared as an unknown variable in a formal proof (in Lean 4), the system automatically generates a proof obligation—a set of facts that the unknown must satisfy to make the proof valid. For example, if the unknown x must satisfy x plus three equals seven, the proof obligation is exactly that constraint. The model cannot invent an answer; it must derive one that makes the obligation true.

Forward derivation (building facts step by step) combined with backward verification (checking the obligation) creates a two-way constraint. The model cannot ghost-write the answer because the formal system will reject it if it does not satisfy the proof state. Every claim must be justified, and Lean checks the justification automatically.

The formal problem-solving constraint

First in words:

The answer is constructed such that: unknown metavariable plus proof obligation equals one valid derivation.

Then the compact form:

∃ x : ℕ . proof_obligation(x) ∧ derivation_closes(x)

Every symbol:

xthe unknown value to be found (could be a number, expression, or structured data)
proof_obligation(x)the set of constraints that x must satisfy (e.g., x + 3 = 7)
derivation_closes(x)the property that the formal proof is complete when x is substituted
∃there exists (in mathematics, this means such a value can be found)
ℕnatural numbers (positive whole numbers), used here as example; x can be any type
A tiny worked example: finding x such that x + 3 = 7
Proof obligation: x + 3 = 7
Forward derivation: we know 3 + 4 = 7, so if x + 3 = 7 then x = 4
Backward verification: substitute x = 4; check 4 + 3 = 7 ✓ true
Lean confirms: no step is skipped, no fact is invented. x = 4 is the unique solution.

The equation says: the unknown x can be found if and only if the proof obligation can be satisfied and the derivation is closed. Lean enforces this automatically.

What can go wrong

What can go wrong

Model gets stuck in the proof state. If the derivation diverges (goes off track), the proof obligation may never close. The model predicts steps that do not lead toward the answer. Lean will not validate the proof until both directions connect.
Backward verification fails even if forward derivation looks good. The model may derive a value that is mathematically interesting but does not actually satisfy the original constraint. Lean catches this automatically when the proof obligation does not close.
The problem is too complex for the model to construct in one go. Large, multi-step problems require the model to maintain the proof state across many steps. If the model loses track of the constraints, it will invent steps rather than derive them.
Done right: all constraints close. When forward derivation and backward verification both complete, Lean certifies the proof automatically. No hallucination is possible because the formal system rejects any invalid step.
What a runnable demo should prove

What a runnable demo should prove

Build a small benchmark of 10 math problems where the answer is a concrete number or simple expression (e.g., solving linear equations, finding the sum of a sequence). Run the same problems in two modes: verification mode (given the statement, check if it is true) and solving mode (given constraints, find the value). Measure the solving accuracy drop—this is the alignment tax. For each problem that solving fails on, print the Lean error (which proof obligation did not close?). This shows that the framework does not suppress the error; it explicitly reveals where the model went wrong.

alignment_tax = accuracy_verify - accuracy_solve

The demo must show that an invalid solution is rejected by Lean (not silently accepted), and that a valid solution is verified automatically (not requiring human review).
