BioAgent Bench: An AI Agent Evaluation Suite for Bioinformatics

Test whether an agent can finish real bioinformatics workflows, not just answer isolated questions.

Paper explainersAll themesAgents & Tool Use

Bioinformatics work is a long chain of file handling, tool choice, tool configuration, and output checking. A model can sound competent in chat while still failing once the task involves real command sequences and real files. BioAgent Bench builds end-to-end tasks such as RNA sequencing analysis, variant calling, and metagenomics so researchers can measure whether an agent actually completes the workflow and whether it still works when the setup is slightly perturbed.

Why ordinary agent tests miss the real failure points

Many agent benchmarks ask a model to answer questions, call one tool, or produce a short plan. Bioinformatics does not look like that. A useful agent must read task instructions, inspect files, choose the right sequence of commands, produce concrete artifacts, and notice when an earlier step broke a later one.

This creates a testing gap. An agent may finish a benchmark that checks only final text output, yet still fail on a real workflow because a file is corrupted, a directory contains decoy files, or the prompt is long enough that the agent stops tracking what matters. BioAgent Bench is built to expose those weak points by using full tasks with concrete deliverables and controlled perturbations.

The paper's move in one sentence. Turn bioinformatics evaluation into a set of end-to-end workflow tasks with real artifacts, then stress those tasks with controlled disturbances so that failure modes become visible.

The algorithm as a flow

What it actually does

Define full workflow tasks

Create manually curated bioinformatics jobs with clear instructions and concrete output files.

Run agents inside task setups

Let each agent inspect inputs, choose commands, and produce artifacts the same way a practitioner would.

Score progress and outcomes

Use an automated grader to check whether each step moved toward the right workflow and whether the final outputs are valid.

Inject controlled disturbances

Alter inputs or prompt conditions so that the test reveals where the agent stops tracking the task correctly.

Compare systems on both success and stability

Report not only whether the pipeline finishes, but also whether it keeps working under harder conditions.

What the paper changes

The paper changes the evaluation target. Instead of grading isolated answers, it grades complete bioinformatics workflows with real files, real deliverables, and explicit disturbance tests.

The hidden quantity

Workflow state: the hidden quantity

measured quantity  =  How far the agent has progressed through the pipeline correctly

The key quantity is not just the final score. It is the hidden workflow state: after each step, is the agent still on a valid path toward the requested result? An agent can look fine for several turns and then quietly drift because it picked the wrong file, skipped a preprocessing step, or accepted a misleading artifact.

BioAgent Bench estimates this hidden state by checking intermediate outputs and pipeline progress, not just the last artifact. That matters because a final failure often starts several steps earlier, and intermediate checks help locate the first wrong decision.

Why it works

Why this works

The mechanism is coverage plus disturbance. Coverage matters because full workflow tasks expose planning, file handling, and step ordering in one setting. Disturbance matters because a clean run can hide fragile behavior, while corrupted inputs, decoy files, and longer prompts force the agent to show whether it is actually tracking evidence.

This gives a better evaluation signal because the benchmark measures both competence and stability. A model that finishes normal tasks but collapses under small disturbances is not dependable enough for bioinformatics work, especially when the work may involve private patient data or unpublished results.

A simple evaluation score

First in words:

Score each run by combining how much of the workflow was completed correctly with whether the final artifact is valid, then compare that score before and after disturbance tests so that brittle agents are easy to spot.

Then the compact form:

score = w_progress * progress + w_outcome * outcome ; drop = clean_score - disturbed_score

Every symbol:

scoreoverall score for one workflow run
progresshow much of the expected pipeline was completed correctly, usually scaled from 0 to 1
outcomewhether the final artifact meets the task-specific validity check, often 0 or 1
w_progressweight on intermediate pipeline progress
w_outcomeweight on final outcome validity
clean_scorescore on the ordinary version of the task
disturbed_scorescore on the altered version with corrupted files, decoy files, or longer prompt context
drophow much performance falls under disturbance
A tiny worked example
Suppose progress = 0.8 and outcome = 1.0 on a clean RNA sequencing task.
Let w_progress = 0.4 and w_outcome = 0.6.
Then score = 0.4 * 0.8 + 0.6 * 1.0 = 0.92.
Now add a decoy file and the agent picks the wrong branch once.
Progress falls to 0.5 and outcome becomes 0.0 because the final artifact is wrong.
Disturbed score = 0.4 * 0.5 + 0.6 * 0.0 = 0.20.
Drop = 0.92 - 0.20 = 0.72, which shows the system is fragile under disturbance.

The paper uses task-specific grading, but this simplified score captures the same idea: measure both correct progress and final validity, then check how much that score drops under disturbance.

What can go wrong

What can go wrong

The grader can miss subtle scientific errors. A run may look structurally correct while still using a poor tool configuration, because automated checks are strongest when the task defines clear artifacts and validity tests.
Benchmark coverage may still be incomplete. Bioinformatics is broad, so a suite that covers RNA sequencing, variant calling, and metagenomics can still miss other workflows or lab-specific conventions.
Strong clean-run scores can hide fragility. An agent may pass many ordinary tasks and still fail once a file is corrupted or a distractor is present, because small setup changes can break its step-by-step tracking.
Done right. Use clean and disturbed versions of the same task, record intermediate progress, and separate competence from stability so that the evaluation reveals both.
What a runnable demo should prove

What a runnable demo should prove

Build three small workflow tasks with real files and required outputs: one RNA sequencing style task, one variant-calling style task, and one metagenomics style task. For each task, define intermediate checks and a final validity check. Run two or three agent setups on the clean tasks, then rerun them after adding one disturbance such as a corrupted file, a decoy file, or a longer instruction block.

The demo should prove two things. First, an end-to-end benchmark catches failures that prompt-only testing misses because it checks real workflow progress. Second, disturbance tests reveal whether a system is dependable because they measure how sharply performance falls when the setup changes.

dependability = average_disturbed_score / average_clean_score ; useful_if dependability stays high while clean completion is also high

A good demo does not just show that an agent can finish a pipeline. It shows whether the pipeline remains correct when the environment becomes less forgiving.
