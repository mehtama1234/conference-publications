Adapt Data to Model: Time Series Transformation Optimization

Instead of retraining a time series model for each domain, find the best way to reshape the raw data so the frozen model works well.

Paper explainersAll themesTime Series & Sequential

Large time series models trained on lots of past data can now predict future values across many different domains. But they struggle when a new domain's numbers look different—different scales, strange jumps, different patterns. Rather than retraining the model for each new domain, this paper asks: what if we just change how we prepare the data? By automatically finding the right mix of simple data transformations, a frozen model can work as well as if it had been trained on that domain.

Zero assumption version

One model, many time series shapes

Time series are numbers recorded over time—stock prices, temperature, heartbeat. A large pretrained model learns to predict future values by seeing patterns in millions of hours of historical data. The catch: real-world time series are messy. One domain's numbers live between 0 and 100, another between 1000 and 2000. One has wild spikes (an outlier that happens once a year), another is smooth. When you hand this pretrained model data from a new domain, it sees something it never trained on and guesses badly.

A beginner's first idea: retrain the model on the new domain's data. But retraining takes weeks and you need a million examples. If a new factory or hospital comes along every month, you will never catch up. The pretrained model sits there, frozen, unable to adapt.

The fix in one sentence: Find the right sequence of automatic data fixes—scaling, removing outliers, slicing—so the frozen model's old knowledge fits the new domain.

The algorithm as a flow

What it actually does

Start with frozen model

The pretrained model does not change; weights are locked.

Build transformation options

Three types of data fixes are candidates: normalize (rescale numbers to a standard range), slice (pick how much recent history to feed in), outlier removal (smooth out spikes).

Generate candidate pipelines

Combine these three in different ways—scale then slice, or slice then remove outliers—generating hundreds of possible transformation sequences.

Test each on real held-out data

Run the frozen model on transformed data; measure forecast error for each pipeline.

Rank and apply best

Pick the transformation that gives lowest error; apply it forever to that domain.

What the paper changes

What the paper changes

The paper does not move weights or retrain. It moves the raw data: the order, shape, and range of the numbers the model sees. By testing different ways to clean and reshape incoming time series, the frozen model can handle domains it was never trained on.

the object it moves  =  input data transformation sequence
The hidden quantity

Domain mismatch distance

measured quantity  =  Transformation-induced model error drop

The paper measures one key quantity: the reduction in forecast error when you apply a specific transformation sequence to the new domain's data, compared to raw data. This reduction tells us whether the transformation actually made the data look more like what the model trained on. When the transformation works, the model sees familiar patterns again and error drops sharply; when it fails, the data still looks foreign and error barely moves. By comparing error before and after transformation, you can rank which pipelines genuinely help the frozen model understand this new domain.

The paper estimates this by splitting held-out data: use part to search for the best transformation (on smaller data), then test the winner on unseen data. A two-stage ranking filters out transformations that perform well on one metric but fail on another, because a transformation that wins by accident on one measure might fall apart when you measure a different way.

Why it works

Why picking the right data shape helps the frozen model

A pretrained model learns to recognize patterns in data. When it was trained, it saw numbers in a certain range and in a certain pattern (how often each number appears, how they cluster). If new domain data is in a completely different range or pattern, the model is looking at something outside its training experience—it does not know how to read it. By reshaping the new data to look like the range and pattern the model was trained on, you put the model back on familiar ground.

The second principle is context: the model was trained on a particular window of recent history (say, the last 96 hours) to predict the next 24. If a new domain has slower patterns that need 200 hours of history, the model will miss them. By trying different context windows on held-out data and picking the one that lets the model see the right amount of history, you give the model the right input to make sense of the pattern.

Outliers—a sudden spike or missing day—break the model's assumptions about data smoothness. Removing or capping extreme outliers makes the data more similar to what the model learned to expect. A two-stage ranking (first by primary error metric, then by secondary metrics like stability) ensures the chosen transformation does not just win on one metric but holds up across different ways of measuring success.

Math after the picture

Measuring transformation quality

First in words:

For each candidate transformation pipeline P, measure the forecast error on held-out data. The error reduction is the forecast error on raw data minus the forecast error after pipeline P.

Then the compact form:

error_reduction(P) = MSE(raw_data) - MSE(transform(data, P))

Every symbol:

Pa candidate transformation pipeline
transform(data, P)the data after applying pipeline P (scale, slice, outlier-fix)
MSEmean squared error, the average of squared differences between predicted and actual
raw_datathe new domain data without transformation
A tiny worked example
Suppose a new domain's time series has forecast error 100 when fed raw to the model.
Try pipeline A (normalize + remove outliers): error drops to 72. Reduction = 100 - 72 = 28.
Try pipeline B (normalize + slice 200-hour window): error drops to 80. Reduction = 100 - 80 = 20.
Pipeline A wins: error_reduction(A) = 28 is larger. A becomes the chosen transformation for this domain.

The goal is to maximize error reduction: find the transformation that makes the frozen model's predictions closest to the truth.

What can go wrong

What can go wrong

Overfitting the search to one error metric. If you optimize the transformation pipeline on forecast error alone, it might do well on average but produce wildly uneven predictions (low error some days, huge errors on others). The paper guards against this with a two-stage ranking: first filter by primary metric (error), then rank survivors by secondary metrics (e.g., variance of errors, performance on different time horizons), so the winner is stable, not lucky.
Too many transformation options. Combining three types of transformations (normalization type, slice length, outlier method) with many settings each explodes the search space. If you test every combination, optimization takes hours. The paper prunes candidates early, discarding pipelines that fail basic thresholds before expensive full evaluation.
Transformation picks up noise, not signal. A domain might have peculiar artifacts (sensor malfunction, data entry errors) that the transformation "fixes." The frozen model then learns to predict the cleaned artifact, not the real pattern. When new, cleaner data arrives, the transformation breaks. Held-out test sets catch some of this, but not always.
Done right. The paper holds out test data unseen during transformation search and ranks pipelines on both primary (error) and secondary (stability, consistency) metrics. This is how TATO avoids picking transformations that overfit or gamble on noise.
What a runnable demo should prove

What a runnable demo should prove

Build a small experiment: take a pretrained large time series model (use any public checkpoint), pick a new domain dataset (e.g., a factory sensor or weather station different from the model's training), and implement the TATO pipeline search. Generate three candidate transformation pipelines: (1) normalize only, (2) normalize plus outlier removal, (3) normalize plus context slicing. Split a held-out chunk of the domain's data: use half to search and rank the three, use the other half to test the winner. Measure forecast MSE before transformation (on raw data) and after (with the best transformation applied). The demo should show that the automatically chosen transformation lowers error by at least 20%, and that this improvement holds on the unseen test half.

improvement_percent = (MSE_raw - MSE_transformed) / MSE_raw * 100

The point: the same frozen model, unchanged, makes better forecasts just because the data was prepared smarter. No retraining, no new model, no domain expertise—automatic data adaptation is enough.
