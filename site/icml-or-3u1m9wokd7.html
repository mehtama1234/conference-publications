ComplexMCP: LLM Agents in Interdependent Tool Environments

A benchmark that exposes why current AI assistants fail at real-world software automation where tools depend on each other and environments change unexpectedly.

Paper explainersAll themesAgents & Tool Use

Today's large language models can call individual tools like a calculator or weather API. But real software is messier: tools affect each other, environments throw surprises, and a single mistake cascades into failure. ComplexMCP builds a test kitchen with over 300 real tools running in 7 stateful sandboxes (an office suite, a financial system, etc.) to measure why even the best models fail to reach 60% success, while humans hit 90%.

Zero assumption version

AI Assistants Stumble on the Last Mile

An AI assistant can use a single tool well: query a database, run a calculation, fetch weather. But real jobs—booking a flight, updating a budget, filing a tax return—chain tools together. Tool A creates a record. Tool B reads it. Tool C modifies what Tool B found. If Tool A fails silently or changes the environment, Tool B reads stale data. A human catching this would backtrack and retry. Today's AI just moves forward, confident it succeeded.

The naive approach: feed the assistant a list of all tools and let it pick. This breaks because with 300 interdependent tools, the assistant drowns in choice. It forgets which tools read which data, skips verification steps, and guesses wrong about whether its last action succeeded. When the environment shifts—a tool times out, a permission expires, a database updates—the model doubles down on wrong assumptions instead of checking reality.

In one sentence. Real software automation fails because tools are tangled, environments are noisy, and models misread success.

What the paper changes

What the Paper Changes

ComplexMCP does not change the model itself. Instead, it moves the test environment from isolated APIs (calm, clean) to interdependent tools in noisy, stateful sandboxes. The paper swaps out the benchmark, not the model. This forces honest measurement of a hidden weakness.

The hidden quantity

The Hidden Quantity: Agent Resilience Profile

measured quantity  =  Resilience under tool interdependence and environmental noise

Most agent benchmarks measure success on clean tasks with independent tools. ComplexMCP measures something deeper: can the agent detect failure, recover from noise, and succeed when tools are tangled? Resilience here means three things: tool-retrieval accuracy (finding the right one among 300), verification habit (checking that a write succeeded), and recovery courage (retrying after failure instead of rationalizing it away).

The paper estimates this resilience by running the same task seeds across models and tracing where they break. A model that retrieves tools correctly but assumes false success shows strong retrieval, weak verification. A model that gives up early shows weak recovery. The benchmark's seed-driven design ensures the same environment state runs twice: once clean, once with injected noise. The gap between the two is the model's resilience.

Why it works

Why Honest Measurement Forces Better Models

ComplexMCP works by removing the mask. In old benchmarks, a model could fake success by getting lucky on clean tasks. Interdependent tools expose it: if Tool A's output becomes Tool B's input, a careless write fails the whole chain. Stateful sandboxes add another layer: the same tool call behaves differently in different environments (permission denied, data changed, timeout). Models that worked on isolated APIs suddenly fail.

The three named bottlenecks come from tracing this: (1) Tool retrieval saturation—with 300 tools, the model's attention spreads too thin and picks the wrong one; this is pure scale burden. (2) Over-confidence—the model writes data and assumes it succeeded without checking; when the environment was noisy, the write failed, but the model moved on. (3) Strategic defeatism—after one failure, the model gives up and rationalizes why the task is impossible instead of trying a different tool or path. Each shows up in trajectory logs as a measurable pattern. The benchmark isolates each one by injecting noise and tracing where the model breaks, so researchers see exactly what to fix: better retrieval under scale (e.g., tool filtering before selection shrinks the choice set, making picks more accurate), verification habits (e.g., always read-back after write catches silent failures), and retry logic (e.g., bounded backtracking forces the model to try alternate tools before giving up). Honesty about failure becomes the road map.

Measuring the Three Bottlenecks

First in words:

success_rate = (tasks_completed / total_tasks) * 100; for each task, log which bottleneck caused failure: retrieval, over_confidence, or defeatism

Then the compact form:

resilience_score = (retrieval_accuracy * 0.4) + (verification_success * 0.4) + (recovery_attempts * 0.2)

Every symbol:

resilience_scoreoverall measure of how well the agent handles noise and interdependence
retrieval_accuracyfraction of tool picks that were correct for the task
verification_successfraction of writes followed by a read-back check
recovery_attemptsnumber of times the agent retried after a failure
A tiny worked example
Task: Book a flight and email confirmation.
Tool retrieval: model picks the right airline tool 8 out of 10 times. retrieval_accuracy = 0.8.
Verification: after booking, model reads back the record 3 out of 10 times. verification_success = 0.3.
Recovery: after a failed booking, model retries 2 out of 10 times; gives up and rationalizes 8 times. recovery_attempts = 0.2.
resilience_score = (0.8 * 0.4) + (0.3 * 0.4) + (0.2 * 0.2) = 0.32 + 0.12 + 0.04 = 0.48 (out of 1.0).
Humans achieve ~0.9 on this same benchmark; top models achieve ~0.5. Gap is the research frontier.

The three weights (0.4, 0.4, 0.2) show that retrieval and verification matter equally; recovery is secondary but not trivial.

What can go wrong

What can go wrong

Tool retrieval saturates under scale. With 300 tools, the model's attention spreads thin. It picks the wrong tool, and the chain breaks. Mitigation: filter tools by context (which were recently used?) before presenting all 300.
Over-confidence skips verification. The model writes data and assumes it stuck. In a noisy environment, the write failed silently. The model moved on, blind to the error. Mitigation: after every write, force a read-back: did it land?
Strategic defeatism gives up too early. After one failure, the model stops trying and invents reasons why the task is impossible instead of trying a different tool or path. Mitigation: bound the retries (up to 3 attempts) and log which tool was tried; force the model to switch before giving up.
Done right. A resilient agent verifies state after risky moves, retries on failure, and logs tool traces for debugging. ComplexMCP measures all three. Over time, models that score high on this benchmark will be reliable for real software automation.
What a runnable demo should prove

What a runnable demo should prove

A minimal demo should set up three interlinked tools—a spreadsheet, an email system, and a calendar—in a single stateful sandbox. Give the model a task: 'Schedule a meeting, email the attendees, and log it in the spreadsheet.' Inject one of three failure modes mid-task: (1) the email tool times out; (2) the spreadsheet returns an out-of-date record; (3) the calendar tool returns a permission-denied error. Trace which bottleneck the model hits: does it recognize the noise, verify its assumptions, or give up? A resilient model notices, backtracks, and finds an alternate path. A brittle model pushes forward or quits.

success_rate = (tasks_completed_correctly / total_tasks) * 100; failure_breakdown = [retrieval_errors, verification_skipped, defeatism_quits]

The single most important proof: the model must recover from at least one injected failure by itself (not by accident) in a chain of five steps. Humans do this naturally. Models do not—yet.
