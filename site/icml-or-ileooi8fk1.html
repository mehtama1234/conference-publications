FluidGym: Plug-and-Play Benchmarking for Flow Control

FluidGym is a standalone benchmark where agents learn to control fluid flow using reinforcement learning, all inside PyTorch with no external software needed.

Paper explainersAll themesOptimization

Training a robot to steer a fluid flow is hard to measure fairly: researchers use different sensors, different actuators, different simulators, and different success criteria. FluidGym solves this by building one standardized, differentiable playground inside PyTorch where all flow-control experiments run the same way. Because it runs entirely on a GPU with no external calls, hundreds of experiments can finish in a reasonable time.

Zero assumption version

Why comparing flow-control agents is nearly impossible today

Suppose you train an agent (a decision-making program) to reduce drag in an airstream by moving a flap or rotating something in the flow. To measure how well it works, you run a simulation. But every research lab uses a different simulator, a different way to measure the flow state, and different actuators. Papers report different numbers on different hardware, so you never know if a new algorithm is actually better or just running on a faster computer, because you cannot separate the algorithm's quality from the quality of whoever's computer and simulator were used in the paper.

Worse: most existing benchmarks rely on external software (CFD solvers like OpenFOAM) that runs separately from the training code. This means training is slow, because each time the agent acts and the simulator runs, the training code must wait for an external program to finish and return a result; the code is fragile (the simulator must be installed and tuned), because every piece of glue code can break; and you cannot differentiate through the fluid simulation, because you never see the detailed math inside the external program—you only get the final output, not the sensitivity of that output to small input changes.

In one sentence. FluidGym is a standardized, differentiable fluid-simulation playground inside PyTorch so agents can be trained and compared fairly.

The algorithm as a flow

What it actually does

Set up the flow

Load a standardized 2D or 3D fluid scenario (cylinder wake, airfoil, etc.) into the differentiable simulator.

Agent sees the state

On each time step, the agent receives flow measurements (pressure, velocity at sensor points).

Agent acts

Agent decides a control input (move a flap, rotate a surface, turn on a jet).

Simulator advances

The differentiable fluid solver computes the new flow for the next step.

Reward signals training

The RL algorithm receives a reward (e.g. lower drag is higher reward) and updates the agent.

What the paper changes

The one thing that changes

Instead of each research team building or tweaking a separate CFD (fluid simulation) tool, FluidGym provides ONE differentiable simulation engine that every team uses. The simulation is differentiable, meaning you can compute gradients through it—the math system can ask 'if I change this sensor reading by a tiny bit, how would the agent's learned decision change?'

the object it moves  =  the simulation engine
The hidden quantity

The hidden quantity: simulation differentiability

measured quantity  =  gradient flow through the fluid solver

Ordinarily, if you run a simulation as a black box (send in initial conditions, get out final state), you cannot compute gradients. You only see the result, not how sensitive it is to tiny changes. FluidGym's solver is built so that gradients can flow backward through the simulation—you can ask questions like 'if the initial velocity were 0.01% higher, how much would the final drag change?' This is called differentiability. It is extraordinarily difficult to build because the fluid solver itself involves millions of numerical operations (adding up pressure forces, solving grids of simultaneous equations) and each one must track derivatives.

The paper estimates differentiability by running agents with the solver and timing them. A fully differentiable solver runs slower than a black-box simulator, but the speedup of training (because gradients help) can outweigh the per-step cost.

Why it works

Why differentiability and a unified platform unlock faster research

Before FluidGym, each team had to install, configure, and debug a separate CFD solver. Weeks pass before the first training run. When you want to compare with a competitor's work, you have to reimplement their simulator setup. This friction slows progress.

FluidGym removes this friction: the simulator is installed with a single pip command, lives inside PyTorch, and runs entirely on the GPU. Every agent trains on the exact same physics, so a better algorithm actually produces a better result, not just a result on faster hardware. Because it is differentiable, modern control algorithms (like Trajectory Optimizer TD-MPC) can use second-order information, converging faster than black-box agents that only see reward signals.

The outcome: researchers can run hundreds of experiments in the time it used to take one. Faster iteration means better algorithms emerge faster, because trial-and-error on ideas that run in minutes, not days, means more experiments can be tried in the same calendar time—more experiments uncover better designs.

Math after the picture

The control reward: drag penalty

First in words:

reward equals minus drag coefficient times a scaling factor; over time, the agent learns to choose actions that minimize drag

Then the compact form:

R_t = -C_d(a_t) * scale

Every symbol:

R_treward at time step t
C_d(a_t)drag coefficient resulting from action a_t
a_tthe control action (flap angle, jet velocity, etc.)
scalea constant (e.g., 100) that adjusts the magnitude
A tiny worked example
At step 1, the drag coefficient is 0.8. Reward = -0.8 * 100 = -80.
At step 2, the agent learns to angle the flap. Drag drops to 0.5. Reward = -0.5 * 100 = -50.
The agent receives a bigger (less negative) reward, so the training signal says 'that action was good.' Over hundreds of steps, drag steadily falls: 0.8 → 0.7 → 0.6 → 0.5 → 0.4, and rewards rise: -80 → -70 → -60 → -50 → -40.

The agent's goal is to make the reward as large as possible, which means minimizing drag—exactly what engineers want.

What can go wrong

What can go wrong

The fluid solution can diverge numerically. If you choose too large a time step, the pressure solver may become unstable and explode to infinity. Mitigation: FluidGym enforces a maximum safe time step, and you set the initial conditions carefully.
Agents can discover physically unrealistic solutions. An agent trained only to minimize drag might learn to blow the flow backward at infinite velocity (unphysical). Mitigation: add constraints on action magnitude and train on multiple realistic scenarios so the agent generalizes.
Differentiability slows down each simulation step. Tracking gradients through millions of operations takes more compute than a black-box simulation. If you only care about final performance, not gradient-based training, you lose this overhead. Mitigation: only use gradient-based algorithms (like TD-MPC) if the speedup outweighs the per-step cost.
Done right. Start with a simple 2D scenario and a well-tuned RL algorithm (SAC or PPO). Set reasonable action bounds. Run multiple trials to measure variance. Compare your results on FluidGym's standard tasks against baselines.
What a runnable demo should prove

What a runnable demo should prove

Build a minimal RL training loop in PyTorch that trains an agent (3-layer neural network) to control a 2D cylinder wake. The agent reads 8 pressure measurements at sensor points around the cylinder and outputs one action: flap angle from -30 to +30 degrees. Use the standardized cylinder environment from FluidGym. Log the drag coefficient and training reward every episode. Run for 500 episodes with SAC (a standard RL algorithm). Plot the trend.

drag_reduction_percent = 100 * (drag_initial - drag_final) / drag_initial

If the plot shows drag falling from ~1.2 to ~0.65 over training, the agent has learned a real control strategy. If drag stays flat, the agent has not learned anything; check that the action is actually affecting the simulator.
