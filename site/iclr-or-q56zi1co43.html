ReVeal: Self-Evolving Code Agents via Reliable Self-Verification

ReVeal trains a code agent to alternate between writing code and checking code, so long test-time improvement comes from a verifier that has learned to be dependable.

Paper explainersAll themesAgents & Tool Use

Code agents often improve when they can try several drafts, run tests, inspect failures, and revise, because each cycle can remove one more source of error. The weak point is the verifier. If the agent's checks are shallow or unreliable, extra turns just wander. ReVeal trains generation and verification together, with credit assigned across turns, so the agent learns not only to write code but also to build and use checks that actually guide later revisions.

Zero assumption version

The problem: extra reasoning turns only help if checking is trustworthy

A code agent can improve by writing a draft, running it, noticing what broke, and trying again. But many training setups reward only the final outcome. They do not directly train the checking behavior that tells the agent what to do next. As a result, the agent may produce many revisions without learning how to ask good questions about its own code.

That becomes a scaling problem at test time. If the verifier is weak, more turns do not create better search because the agent keeps revising from noisy feedback. The paper's claim is that long-horizon code improvement requires a verifier that can reliably judge partial drafts and propose tests that expose the real bug.

The core idea in one sentence. Train code writing and code checking as a repeated generate-check loop, with rewards assigned across turns, so the verifier becomes useful enough to drive long test-time improvement.

The algorithm as a flow

What it actually does

Step 1: Generate a candidate program

The agent writes code for the task, just as a normal code model would.

Step 2: Enter a verification turn

Instead of stopping at the first draft, the agent builds checks, runs tools, and inspects the behavior of the program so that it can learn what is wrong.

Step 3: Assign credit to each turn

The training setup attributes reward at the turn level, so useful verification actions receive positive learning signal because they enabled a later repair.

Step 4: Revise code using the check results

The next generation step uses the evidence gathered during verification to fix the program more precisely.

Step 5: Repeat beyond the training horizon

At test time the agent can continue this loop for many more turns than seen in training, because the verification behavior itself has become dependable enough to guide the longer search.

What the paper changes

What changes: the unit of training becomes a turn pair

The central object is no longer a single code sample with one final reward. It is a sequence of generation and verification turns. Each verification step creates information that later turns can act on, so the training signal has to treat those steps as consequential decisions rather than as hidden internal chatter.

the object it moves  =  the generate-check turn sequence
The hidden quantity

The hidden quantity: verification reliability

measured quantity  =  How often a check points the search in the right direction

The decisive hidden quantity is not just whether a test fails. It is whether the verification step gives information that helps the next revision move toward a correct program because it isolates the real source of error. A bad test can fail for the wrong reason, or a vague check can say that something is wrong without locating the source. In both cases, extra turns add little value.

ReVeal tries to improve this hidden quantity directly. By rewarding helpful verification turns, it pushes the agent toward tests and tool uses that expose the actual mistake instead of producing noisy signals.

Why it works

Why it works: better checks create a better search process

The method works because code repair is a search problem over many candidate programs. Search improves only when each step uses evidence that narrows the remaining error because that evidence eliminates some wrong repair directions. ReVeal makes verification a trained skill, so the agent learns to create targeted tests and read tool feedback in a way that guides revision.

Turn-level credit is important because the final pass or fail may occur several turns after the key decision. If one verification turn exposed the real bug and a later generation turn fixed it, both decisions deserve credit. Training them together produces a code agent whose later revisions are grounded in stronger evidence, which is why the paper can extend to many more turns at test time than were seen during training, because the later turns now start from more dependable checks.

Math after the picture

The training signal: sum reward across turns

First in words:

A simple view is to score the whole trajectory by adding the value contributed by each generation turn and each verification turn. The goal is not merely to maximize final success, but to strengthen intermediate actions that make later success more likely.

Then the compact form:

trajectory_reward = sum_t (gen_reward_t + verify_reward_t)

Every symbol:

gen_reward_tthe learning signal for the code-writing action at turn t
verify_reward_tthe learning signal for the checking action at turn t
trajectory_rewardthe total signal over the full revision process
A tiny worked example
Turn 1 writes code that almost works but mishandles empty input.
Turn 2 creates a boundary-case test for empty input and exposes the exact bug.
Turn 3 fixes the bug and the program passes.
If the final success gives reward 1, the useful boundary-case test should receive some of that credit because it created the evidence for the repair.
ReVeal trains this way so that future runs learn to create the same kind of useful checks.

The important change is that verification actions become first-class learning targets, not mere side effects of generation.

What can go wrong

What can go wrong

The agent learns shallow checks. If the verification turn only runs easy cases, the system may overfit to tests that do not reveal the real bug.
Credit assignment stays too noisy. If rewards cannot distinguish which turn helped, useful verification behavior may not improve even after many trajectories because the learning signal never points clearly to the valuable check.
Tool feedback is misread. A strong test still fails if the agent draws the wrong conclusion from the output. Good verification requires both useful checks and correct interpretation.
Done right: later turns remain informative. The method succeeds when each new round of checking reduces uncertainty enough that the next code revision is more targeted than the previous one.
What a runnable demo should prove

What a runnable demo should prove

Take a set of small programming tasks with hidden edge cases. Train one agent on final pass-or-fail only, and train another on a generate-check loop with explicit reward for verification turns. At test time allow both agents many revision turns on fresh tasks so that the evaluation can reveal whether the extra turns stay useful. Record how often each turn adds a useful test or bug hypothesis, and how often the final program passes. The demo should show that the second agent benefits from extra turns because its checks sharpen later revisions, while the first agent often spends those turns on low-value rewrites.

Useful-turn rate = (# turns that create evidence leading to a later fix) / (total verification turns).

The demo must show that the gain comes from a better checking process because the rewarded verifier produces stronger evidence, not merely from allowing more retries.
