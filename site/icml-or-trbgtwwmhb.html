DockSmith: Scaling Reliable Coding Environments via Agentic Docker Builder

An AI agent learns to reliably build Docker environments by practicing with recorded traces and memory of past successes, then uses that skill to help software engineering agents work better.

Paper explainersAll themesAgents & Tool Use

When you train a software engineering agent to write and test code, it needs a reliable computing environment to run in. But building that environment (via Docker, a tool that packages code with its dependencies) is fragile and time-consuming. DockSmith treats Docker environment construction not as a boring setup step, but as a core skill an agent can learn. By training on real examples of successful Docker builds and teaching the agent to remember solutions that worked before, DockSmith becomes better at building environments, which in turn helps the whole software engineering agent work better on real tasks.

Why Docker environments break during agent training

When you want to teach an AI agent to write code and run it, the agent needs a working computing environment. Docker (a tool that bundles code plus all its dependencies into a sealed package) is the standard way to provide that. But building a Docker environment reliably is hard: the agent must install the right software versions, handle missing libraries, and recover from failures.

A naive approach is to pre-build all the environments the agent will need. This fails because you cannot predict every environment in advance, and environments are brittle: a small change to dependencies can break everything. The bottleneck is real: most execution-grounded training of software agents spends more time waiting for broken environments than on actual learning.

The core problem: Building Docker environments is slow, fragile, and blocks agent training. DockSmith teaches an agent to build Docker environments itself, treating it as a learnable skill with memory of past solutions.

The algorithm as a flow

What it actually does

Collect real traces

Record successful and failed Docker builds as agent actions and feedback.

Train on execution

Teach a large neural network (30 billion numbers that represent learned patterns) to predict the next action in a Docker build.

Add loop detection

Detect when the agent is stuck retrying the same command; break the loop and try a different approach.

Build a success memory

Store solutions that worked for each Dockerfile; when building a new one, check the memory first.

Deploy and measure

Run the trained agent on new Dockerfiles and measure how often builds complete correctly.

What the paper changes

What the paper changes

DockSmith changes the skill the agent brings to the table. Instead of having a generic software-writing agent that fails when environments break, you have a specialized agent trained to do one thing well: reason about dependencies, handle errors, and construct working Docker environments step by step. The object here is the agent's knowledge of Docker building itself, learned from examples rather than hard-coded rules.

The hidden quantity

The hidden quantity: How well does this particular build match past successes?

measured quantity  =  Cross-task success memory

The paper measures something vital that is not written down in the Dockerfile itself: the memory of what solutions have worked before on similar Docker builds. When you encounter a new Dockerfile (say, one that needs Python 3.10 and PyTorch), there may be a previous successful build with the same dependencies. This cross-task success memory is the bridge between past experience and current problem.

DockSmith estimates this by storing every successful Docker build and checking for overlaps: if the current environment requires dependency X and you have already built an environment with X, you have a proven solution to try. The agent learns to query this memory and reuse solutions because when the model sees a dependency it has seen work before, it has a strong learned pattern to follow, so it acts faster and more confidently.

Why it works

Why this works: the causal chain

Docker environment construction fails when the agent hits a missing dependency, a version conflict, or an infinite retry loop. Normally, the agent has no way to recover because it has never seen a similar situation before.

DockSmith works because it does three things in concert. First, it trains the agent on real Docker-building traces: sequences of actions (try to install X, check if it works, handle the error). This teaches the agent to reason about dependencies and errors, not just guess randomly. Second, it adds loop detection: if the agent tries the same command five times and keeps failing, the system stops it and suggests trying something else. This breaks the cycle. Third, it stores a memory of solutions: when you encounter a dependency you have solved before, you can copy that solution directly. Together, these mean the agent has practice, feedback when it gets stuck, and access to proven answers. So it builds environments more reliably and faster.

Math after the picture

The learning setup

First in words:

For each Docker build attempt, the agent is trained to maximize the probability of the action sequence that succeeded, weighted by how recently and how often that action pattern worked on similar tasks.

Then the compact form:

loss = -sum_t log P(a_t | state_t, memory) where a_t is the action taken at step t and P is the learned model's predicted probability, boosted by cross-task memory matches.

Every symbol:

a_tthe Docker build action at step t (e.g., run apt-get install)
state_tthe current environment state: what is installed, what errors happened
P(a_t | state_t, memory)the model's learned probability that this action is correct, given state and memory
memorythe stored solutions from all previous successful Docker builds
sum_t log P(...)sum over all steps in the trace, measuring how confident the model was
A tiny worked example
Suppose the model predicts a_1 (install Python 3.10) with probability 0.9. The loss contribution is -log(0.9) = 0.105.
Then a_2 (install PyTorch) with probability 0.8. The loss contribution is -log(0.8) = 0.223.
Then a_3 (run test) with probability 0.7. The loss contribution is -log(0.7) = 0.357.
Total loss for this trace: 0.105 + 0.223 + 0.357 = 0.685. Training adjusts weights to reduce this.
If memory has a past successful trace with the same a_1 and a_2, the model's probability for those steps rises (higher confidence), lowering the loss.

When the model sees an action (like installing Python) that succeeded in a past trace, it has a strong learned pattern for that action, so it predicts it with high confidence and the training loss drops.

What can go wrong

What can go wrong

New dependencies not in memory If a new Dockerfile requires a package combination the agent has never seen, the memory cannot help because there is no stored solution to copy. The agent must fall back on its learned patterns, which may fail if training only covered common packages.
Loop detection is too aggressive If the agent legitimately needs to retry an action (e.g., waiting for a server), a crude loop detector stops it prematurely. The paper's loop detection requires careful tuning of retry thresholds.
Memory pollution If a stored solution is incomplete or wrong, it will poison future attempts. The memory must filter for truly successful builds, not partial successes.
Done right: memory is explicit and pruned DockSmith stores only fully successful traces and uses loop detection with task-specific thresholds, so the agent learns to trust memory when it is available and fall back on reasoning when it is not.
What a runnable demo should prove

What a runnable demo should prove

A concrete demo builds a small suite of Dockerfiles (say, five different Python environments with different packages: one with a deep-learning framework, one with a different framework, one with a graphics library, one with all three, one with none). Train the agent on the first three and record successes in memory. Then ask it to build the other two (package combinations it has never seen). Measure: (1) how many build without errors, (2) how many steps it takes on average, (3) whether it reuses solutions from memory when a package appears in both a new and a past build.

Success rate = (Dockerfiles that build fully) / (total Dockerfiles), measured on in-distribution (training) and out-of-distribution (held-out) sets. Reuse rate = (steps skipped because memory had the answer) / (total steps).

The demo succeeds when the trained agent builds more environments correctly than a baseline (random or rule-based) and shows that it genuinely reuses past solutions, not just memorizing.
