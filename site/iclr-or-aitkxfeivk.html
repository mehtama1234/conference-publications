Fine-tuned LLM for Genetic Search Operators

A small language model, carefully trained on examples, learns to write better mixing operators for a genetic algorithm that solves delivery-route problems.

Paper explainersAll themesOptimization

Solving vehicle routing — finding the cheapest way to deliver to many stops — is hard. Current methods either rely on humans to hand-write clever tricks (which are slow to invent and stuck once written), or use huge general-purpose AI models like GPT-4 (which cost money and run slowly on your hardware). This paper shows that a smaller, cheaper language model can learn to create better tricks than humans wrote, because when trained on hundreds of examples with a clear step-by-step reward system, it discovers patterns humans missed and invents variations a human would never try.

Zero assumption version

The routing puzzle and its two stuck paths

A delivery company has one truck and 100 stops. The question is: in what order should the truck visit all of them to use the least fuel? This is called the vehicle routing problem. With 100 stops there are roughly 10 to the 157th power possible orders—no computer can check them all.

Today there are two ways out. Path one: hire a clever person to hand-write a trick (called a heuristic) that usually finds a pretty good order in reasonable time. Path two: ask GPT-4 (a huge AI model trained on trillions of words) to design the trick. The first path is slow for humans. The second path works but costs money, runs slowly on your computer, and was trained on general language, not routing.

What if a smaller model could learn the trick by practicing on examples? No one had shown that works.

In one sentence. Train a smaller language model to write mixing operators (the tricks that combine two good routes into a better one) using a step-by-step learning system, starting with rewards for valid code and ending with rewards for improved routes, because this ladder teaches the model to write code that is both correct and effective.

The algorithm as a flow

What it actually does

Start with a small model

Load a language model (much smaller than GPT-4) that can generate code.

Define a three-stage reward

Reward stage 1: give a bonus only if the generated code compiles, because the model cannot learn quality without first learning correctness. Stage 2: bonus only if it runs, because crashed code is useless. Stage 3: bonus grows with how much better the route is, because once code works, the model learns the patterns that make solutions good.

Feed it examples and feedback

Show the model pairs of good routes (real solutions) and ask it to generate mixing tricks. After each attempt, tell it the stage reward.

Learn to avoid plagiarism

If the model generates the same mixing trick twice, reduce its reward. This pushes it to invent new tricks.

Test on routes of all sizes

Verify that tricks learned on small problems (20 stops) still beat human tricks on huge problems (1000 stops).

What the paper changes

The one thing the paper changes

The object is the mixing operator—the code that combines two good routes into a new candidate. Normally a human writes this code once and it never changes. Here, the model learns to write a new, custom mixing operator tailored to the problem.

the object it moves  =  The mixing operator code
The hidden quantity

The hidden quantity: operator quality and diversity

measured quantity  =  operator quality (validity + diversity + solution improvement)

The paper measures three stacked qualities as it trains. First, does the generated code compile (does it run without crashing)? Second, does it execute without runtime errors? Third, does the new route it creates score better than the parent routes, because a trick is only useful if it makes solutions better? These three form a hierarchy: a trick must be valid (stages 1–2) before it can be good (stage 3), otherwise the model wastes energy on broken code.

The paper tracks this by giving each generated operator a three-level score. It also counts how many unique tricks the model invents; if the same trick appears twice, that counts as plagiarism and the reward drops. This forces diversity because an operator that works on every problem is rarer than one that works on only one scenario.

Why it works

Why a small trained model beats hand-written tricks

A human expert writes one mixing trick and it is stuck forever. The trick is clever but it only works well on the kinds of problems the expert imagined. A small language model, when trained on hundreds of examples with a clear reward signal, learns patterns: when the routes are tangled, twist them differently; when they are already sorted, make small nudges. It invents hundreds of variations.

The curriculum is the secret. If the model is punished for any wrong code, it learns to output words that look like code instead of real code. If it is punished for code that crashes, it learns to generate careful, slow code. Only at stage 3, when both of those work, does it learn to make the code efficient and effective. This is like teaching: first letters, then words, then sentences, then poetry.

Finally, penalizing plagiarism forces it to search broadly. If repeating a trick loses points, the model explores the space of possible tricks more thoroughly than any human would in a lifetime.

Math after the picture

The reward formula

First in words:

Total reward equals: (Stage 1 bonus if code compiles) plus (Stage 2 bonus if code runs) plus (Stage 3 bonus times how much better the new route is) minus (penalty if the operator is a plagiarized copy).

Then the compact form:

R = B1 * valid_syntax + B2 * valid_runtime + B3 * improvement - P * is_plagiarism

Every symbol:

RTotal reward signal to the model
B1Bonus points for syntactically valid code (e.g. 1.0)
valid_syntax1 if code compiles, 0 otherwise
B2Bonus points for runtime-error-free code (e.g. 1.0)
valid_runtime1 if code executes without crashing, 0 otherwise
B3Weight on solution quality (e.g. 10.0)
improvementHow much better the new route is (normalized, e.g. 0.5 means 50% improvement)
PPlagiarism penalty strength (e.g. 5.0)
is_plagiarism1 if this operator was generated before, 0 if novel
A tiny worked example
Attempt 1: Code compiles (B1=1.0), runs (B2=1.0), improves route by 8% (improvement=0.08), is new (plagiarism=0). R = 1.0 + 1.0 + 10.0 * 0.08 - 5.0 * 0 = 2.8.
Attempt 2: Code compiles (B1=1.0), runs (B2=1.0), improves by 15% (improvement=0.15), but is a copy (plagiarism=1). R = 1.0 + 1.0 + 10.0 * 0.15 - 5.0 * 1 = 2.0 - 5.0 = -3.0 (penalty swamps reward).
Attempt 3: Code has syntax error (B1=0). R = 0 + 0 + 0 - 0 = 0 (the model learns: broken code gets no credit at all).
The three stages create a ladder: first validity, then efficiency, then quality.

The formula embeds the three-stage curriculum by stacking independent bonuses; each stage is passed before the next matters. Plagiarism penalty is large enough to outweigh even a good improvement, forcing diversity.

What can go wrong

What can go wrong

The model forgets to branch. If stage 1 reward is too lenient, the model learns to output words that sound like code but never actually compile. It copies the token patterns of real code without understanding. The fix: enforce stage 1 strictly.
Plagiarism penalty backfires. If the penalty is too weak (e.g. -1), the model ignores it and repeats one good trick over and over, because if one trick solves half the training cases, it gets high average reward even with a tiny penalty subtracted. In weak-penalty regimes, a single high-value trick concentrates the reward signal. The fix: make the penalty large and certain so the cost of plagiarism outweighs any single trick's benefit, forcing the model to search widely.
Overfitting to training instances. The model might memorize: for route type A, emit operator X; for type B, emit operator Y. It works on training examples but breaks on new problem instances that don't match the training distribution. The fix: validate on held-out problems of all sizes.
Runtime errors on unfamiliar inputs. The model learns to generate code that works on the example routes it was shown, but crashes if the route structure is unusual (e.g. a route with only two stops when training had ten-plus). The fix: train on diverse route shapes.
Done right. The curriculum works: the model learns valid code first, then efficient code, then varied and effective code. Plagiarism penalty forces breadth. Testing on unseen problem sizes proves the trick generalizes.
What a runnable demo should prove

What a runnable demo should prove

Start with a small problem instance (e.g. 20 delivery stops) and a human expert's hand-written mixing operator. Train the language model on pairs of good routes from this problem, using the three-stage reward, for 1000 training steps. Every 100 steps, test the model's current operator on a held-out set of route pairs. After training, test the learned operator on three new problem sizes: 20 stops (matched to training), 50 stops (unseen), and 200 stops (much larger). Plot the route quality (how short the combined route is, lower is better) for each, because shorter routes prove the mixing trick is effective.

Quality = (distance of best route found) / (distance of optimal or best-known route) × 100%. Lower is better. Generalization = quality at 50-stop and 200-stop tasks minus quality at 20-stop task (in percentage points); smaller is better.

The demo must show that the learned operator achieves shorter routes than the expert's design on at least the 50-stop problem, proving it learned a real pattern that transfers to unseen sizes, not just memorized the training examples.
