SlotGCG: Finding Where Jailbreak Tokens Work Best

Instead of always putting adversarial tokens at the end of a prompt, SlotGCG scans all positions in the prompt to find which spots make the jailbreak work better.

Paper explainersAll themesAlignment, Safety & Fairness

When researchers test large language models for vulnerabilities using adversarial attacks, they usually put the attack tokens in the same place—at the end of the prompt. This paper discovers that the position where you insert attack tokens matters enormously. Some spots in a prompt are naturally more vulnerable to jailbreaking than others. SlotGCG quantifies this vulnerability and targets the weakest positions, making attacks succeed more often.

Zero assumption version

Existing jailbreak attacks ignore position

Current adversarial attacks like GCG (Greedy Coordinate Gradient) use a one-size-fits-all strategy: pick a spot in the prompt—usually the very end—and insert attack tokens there. The attack then tries to tweak those tokens to make the model misbehave.

A beginner might assume all positions in a prompt are equally hard to attack. But they are not. Some slots in the prompt naturally amplify attack tokens more than others, because of how transformer models (the architecture underlying LLMs) read and process sequences. By always using the same position, current attacks miss the weakest spots.

The move. SlotGCG finds the most vulnerable positions in each prompt by measuring focus (how much the model's processing power goes to each position) flowing to inserted tokens at different slots, then focuses the attack there.

The algorithm as a flow

What it actually does

Scan the prompt

Insert a test token at every position in the prompt, one at a time.

Measure focus weight

Collect attention (a measure of which parts of the input the model's response-generation layers focus on) flowing to the test token from the response part.

Score each position

Assign a Vulnerable Slot Score to each position based on total attention.

Select top positions

Pick the slots with the highest scores—the most vulnerable ones.

Run targeted attack

Use standard GCG optimization at only those selected positions.

What the paper changes

The thing that changes

The paper changes where adversarial tokens are inserted. Instead of a single fixed position (the suffix), SlotGCG selects multiple vulnerable positions across the entire prompt based on a vulnerability score.

the object it moves  =  insertion position strategy
The hidden quantity

The Vulnerable Slot Score

measured quantity  =  Attention flow to adversarial tokens

The Vulnerable Slot Score (VSS) is a number that measures how much the model's attention heads look at an inserted token when generating a response. Attention is the mechanism that lets transformer models decide which parts of the input to focus on. Higher attention to an adversarial token means that token is more influential in steering the model's behavior.

The paper estimates VSS by inserting a test token at each slot, running a single forward pass, and summing up attention weights across all layers and attention heads in the part that generates the response. A slot with high VSS is a naturally vulnerable position.

Why it works

Why scanning slots makes attacks work

The mechanism has three parts. First, transformer models use attention to decide what to focus on when generating each response token. The position where an adversarial token sits determines how much attention it receives from the response-generation part of the model. Slots that are naturally high-attention positions become more influential over the output.

Second, a standard GCG attack tries to modify adversarial tokens via gradient-based optimization to minimize a loss function (how far the response is from the desired harmful output). An adversarial token at a high-attention slot contributes more to the loss, so gradient updates to that token have a bigger effect. Optimization converges faster because each gradient step moves the loss more.

Third, by scanning all slots upfront and picking only the highest-VSS ones, SlotGCG focuses the optimization budget where it matters most. Instead of wasting iterations on low-attention slots, the attack concentrates on the vulnerable positions. High-attention slots produce bigger gradients (steeper slopes in the error surface), so each optimization step pushes the loss down more, avoiding the flat plateaus where low-attention positions get stuck and converging faster.

Math after the picture

Vulnerable Slot Score formula

First in words:

The vulnerability score for a slot is the sum of all attention weights from the response-generation layers to the adversarial token at that slot, across all attention heads.

Then the compact form:

VSS_s = sum over layers L_U, heads h, response tokens c, and token positions a: A(layer,head)[c,a] / k

Every symbol:

VSS_sVulnerability score for slot s (a number)
A(layer,head)[c,a]Attention weight: how much token c looks at position a
L_UResponse-generation layers (upper half of model)
kNormalization factor (number of heads + layers)
cResponse token position
aSlot where adversarial token is inserted
A tiny worked example
Suppose slot 3 has adversarial token. Collect attention from all response-generation layers.
Layer 1, Head 1 attends to slot 3 with weight 0.8. Layer 1, Head 2 attends with weight 0.5.
Layer 2, Head 1 attends with 0.6. Layer 2, Head 2 attends with 0.4.
Total attention to slot 3: 0.8 + 0.5 + 0.6 + 0.4 = 2.3. Normalize by k=4 heads: VSS = 2.3 / 4 = 0.575.
Slot 8 has attention 0.2 + 0.1 + 0.15 + 0.05 = 0.5. VSS = 0.5 / 4 = 0.125. Slot 3 is 4.6x more vulnerable.

Higher attention means the adversarial token influences the model's response more, so optimization at that slot needs fewer steps to succeed.

What can go wrong

What can go wrong

Attention changes during optimization. The initial VSS (before GCG starts) might not perfectly predict which slots remain vulnerable after 100 optimization steps. The paper measures both VSS_init and VSS_final, finding they correlate but are not identical, so top slots can shift slightly as the adversarial tokens evolve.
Defense specifically targets slot positions. If a defense method detects and filters tokens at typical high-attention slots, SlotGCG's strategy becomes obvious. However, the paper tests against four defenses and still wins, suggesting this is not yet a common defense approach.
Scanning adds overhead. Computing VSS for every slot requires one forward pass per position (e.g. 200ms for 100 slots). For very long prompts, this preprocessing cost grows. The paper mitigates by sampling slots or using smaller test models.
Done right. SlotGCG works because the paper grounds its targeting in actual attention weights (not arbitrary heuristics), selects top-K slots so optimization can converge on the best ones, and adds minimal computational overhead (200ms is negligible vs. full optimization).
What a runnable demo should prove

What a runnable demo should prove

A minimal demo picks a harmful prompt and runs standard GCG at a fixed suffix position, then runs SlotGCG to scan all prompt positions and select top-3 slots. For each approach, measure how many optimization steps are needed to drop the loss below a threshold, and how often the final attack succeeds (the model generates a harmful response). The demo should show that SlotGCG converges in fewer steps and achieves higher success rate on the same model and prompt.

Speedup = steps_GCG / steps_SlotGCG; Success Rate = num_successful_jailbreaks / num_total_attempts

The demo must make it impossible to miss that position matters: the same attack, optimized at different slots, has radically different success rates and convergence speed.
