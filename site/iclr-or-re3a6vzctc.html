Pisces: Private Retrieval-Augmented Generation

A system that finds and uses documents to answer questions without anyone seeing the question, the document contents, or which documents were picked.

Paper explainersAll themesAlignment, Safety & Fairness

Imagine you have a medical question but do not want your doctor or anyone with the medical records to know what you asked. Or imagine a company wants to search its confidential documents without revealing them to the search service. Retrieval-augmented generation (RAG) is a technique where a language model answers questions by first finding relevant documents, then reading them. But in normal RAG, both your question and all the documents are exposed. Pisces is the first practical system that makes this private using locked-box math, so the search happens without anyone learning what you asked or what documents exist.

Zero assumption version

Normal search exposes everything

When a language model answers your question using stored documents, it works like this: you send your question to a server, the server searches through all documents to find matches, then returns the matching documents. The problem: everyone involved — the server, the search service, any attacker listening in — sees your exact question and learns something about which documents matter to you.

A beginner might think 'just encrypt the question before sending it.' But here is the trap: if the question is locked with a key only you have, the server cannot read it, so it cannot search. It either has to send back every single document (wasteful and still leaky — the attacker learns what you ignored), or ask you to do all the search work yourself (slow and impractical). RAG needs the server to actually search, but you need the search to be blind.

In one sentence. Pisces searches through locked documents to find matches without anyone seeing the question, the documents, or which ones matched.

What the paper changes

What changes

The paper changes how a server searches documents: instead of reading plain documents and plaintext queries, the server operates on locked (encrypted) versions of both, using only locked-box arithmetic. The server can still find good matches, but learns nothing about content or intent.

the object it moves  =  search algorithm
The hidden quantity

Privacy cost: the computation tax

measured quantity  =  computation and communication overhead

The hidden quantity is how much extra work (computation and network traffic) privacy costs. Cryptography-based search is not free — locked-box operations are slower than normal operations. The paper measures this as the ratio: (time and bytes used by private search) divided by (time and bytes used by normal search). Pisces aims to keep this overhead low through a strategy: filter out most documents cheaply before doing the expensive locked-box scoring.

The paper estimates this overhead using benchmarks on real datasets and networks. A good design should handle thousands of documents without the cost becoming prohibitive — that is, the overhead should grow slowly (not exponentially) as the document collection grows.

Why it works

How privacy-preserving search works

The core insight is: if you try to privately score every document against the query, it takes time proportional to the collection size — that is slow. But if you first filter to a small candidate set using a cheap privacy-preserving operation, then score only the survivors, the work shrinks dramatically. The paper calls this coarse-to-fine.

For the semantic path: an oblivious filter (a cryptographic tool that examines encrypted data) privately selects a small subset of documents that are likely to match, without anyone seeing which ones. Semantic scoring (computing how similar the question is to each document using lists of numbers that represent meaning) then happens only on these survivors.

For the lexical path: the paper uses a multi-instance labeled PSI (Private Set Intersection) protocol. This is a locked-box way to count how many times each query word appears in each document (used for BM25, an old but effective ranking method), without anyone seeing the document text or what words the query contains.

The two paths (semantic and lexical) both output scores, which are merged while still encrypted. The server sends back the top-ranked encrypted result. Only the user, who holds the decryption key, learns which documents matched. The attacker or the server observes: query size, document count, result size, and timing — but not content.

Math after the picture

The cost formula

First in words:

total_work = filter_cost + (candidate_count * score_per_doc_cost). By shrinking candidate_count, total_work shrinks.

Then the compact form:

work_private = work_filter + c * work_semantic_per_doc + c * work_lexical_per_doc, where c = size of candidate set after filtering, small

Every symbol:

work_privatetotal cryptographic operations needed
work_filtercost of oblivious filtering step
work_semantic_per_doccost to score one document using vector similarity
work_lexical_per_doccost to score one document using PSI word-count
csize of candidate set (what Pisces optimizes)
A tiny worked example
Document collection: 10,000 documents.
Filter cost: 1,000 operations (cheap, does not look at content).
Semantic score per doc: 10 operations (expensive, cryptographic similarity).
Lexical score per doc: 5 operations (PSI word-counting).
Naive (score all): 1,000 + 10,000 * (10 + 5) = 1,000 + 150,000 = 151,000 operations.
Pisces (score 50 candidates): 1,000 + 50 * (10 + 5) = 1,000 + 750 = 1,750 operations.
Speedup: 151,000 / 1,750 = 86x faster, just by filtering first.

The math shows why filtering first is critical: the scoring cost dominates, so shrinking the candidate set (c small) drives massive speedup.

What can go wrong

What can go wrong

Filter is too aggressive. If the oblivious filter prunes too many documents, some relevant documents are lost before scoring. Accuracy drops. The filter must be tuned to keep true matches in the candidate set (high recall), even if it keeps some irrelevant documents too.
Side-channel leakage from timing or shape. Cryptographic systems can leak information through timing patterns (how long operations take) or the shape of data (candidate set size, network bytes). An attacker might infer which documents are popular by observing how long searches take. Defense requires careful implementation and constant-time operations.
Weak encryption or protocol flaws. If the cryptographic primitives (the locked-box math) are weak or incorrectly implemented, an attacker might decrypt content or forge results. The system relies on well-vetted crypto libraries and formal proofs of protocol correctness.
Done right. When the oblivious filter maintains high recall, cryptographic operations are constant-time, and protocols are proven secure, neither the server nor an eavesdropper learns the query, the documents, or which ones matched.
What a runnable demo should prove

What a runnable demo should prove

Build a small private RAG system with 1,000 test documents (e.g., Wikipedia snippets or research abstracts). Implement Pisces: encrypt documents and query, run the oblivious filter to select 50 candidates, score those, return encrypted result. Decrypt at home and compare which documents matched. Measure: (1) time taken vs plaintext search, (2) accuracy (do the top 10 retrieved documents include the human-judged relevant ones), (3) privacy (visually confirm the server never saw the plaintext query or documents).

privacy_preserved = (no plaintext query leaked) AND (no document contents leaked) AND (candidate set size is small), accuracy_loss = (top_10_hits_private - top_10_hits_plaintext) / top_10_hits_plaintext, speedup_over_naive = time_naive_encrypted / time_pisces

The demo must make clear that filtering down to a small candidate set is the key to privacy and speed: without it, encrypted search is impractical; with it, you get both privacy and reasonable performance.
