MALICE: Loop Invariants from Symbolic Execution Traces

Generate loop invariants for memory-manipulating programs by showing a language model symbolic execution traces, then iteratively repairing candidate invariants using verifier feedback.

Paper explainersAll themesAgents & Tool Use

A loop invariant is a statement that must remain true every time a loop repeats. Program verifiers need these statements to prove memory safety and functional correctness, but they are hard to write automatically for programs that mutate pointers, linked structures, and heap layouts. Numerical invariants such as bounds on counters are often manageable; shape invariants about which nodes are connected to which others are much harder because the relevant memory-state changes are implicit in the code. This paper makes those changes explicit by feeding symbolic execution traces into a two-stage language-model system and then using verification feedback to repair the proposed invariants.

Zero assumption version

Source code hides the memory transitions an invariant must summarize

To prove a loop correct, a verifier needs a statement that is true before the loop starts, remains true after each iteration, and is strong enough to imply the desired postcondition at the end. For loops over arrays, this may be a simple relation on indices. For loops that traverse and update heap objects, the invariant must describe pointer reachability, aliasing, and structure shape. Those facts are rarely visible in one line of code.

A language model reading raw source sees assignments and conditionals but not the exact symbolic memory states that result from following those operations. That makes shape invariants hard to infer. The loop may preserve a linked-list segment, split a tree, or maintain disjoint heap regions, but those facts appear only after reasoning across multiple execution steps. The paper's hypothesis is that showing the model symbolic execution traces exposes precisely the missing information.

Core issue. Memory invariants are difficult because the code does not directly display the evolving heap facts that a proof needs.

The algorithm as a flow

What it actually does

Run symbolic execution

A symbolic executor explores the loop and records symbolic memory states, path conditions, and updates across iterations.

Prompt the model with traces

The language model reads the trace rather than only the raw code, so it can inspect how heap facts evolve.

Draft candidate invariants

The first stage produces invariants that summarize the repeated state pattern revealed by the traces.

Verify the candidates

A formal verification tool checks whether each candidate is inductive and strong enough for the proof goal.

Repair using feedback

Counterexamples or verifier failures are fed back into the model so it can revise the invariant until the proof succeeds.

What the paper changes

What the paper changes

The paper changes the evidence the model reasons over. Raw source code is replaced with symbolic execution traces that explicitly list pre-states, post-states, and branch conditions. It also changes the generation loop from one-shot prediction to an iterative tool-using procedure where a verifier actively rejects weak invariants. Together, those changes move the task from free-form guessing toward trace-grounded synthesis.

the object it moves  =  the evidence and refinement loop used for invariant generation
The hidden quantity

The hidden quantity: inductive heap summary

measured quantity  =  inductive heap summary

An inductive heap summary is the compact statement that captures what stays true about memory before and after every loop iteration. It must be strong enough to explain pointer structure and separation facts, but weak enough to survive the transition from one iteration to the next. That balance is the hard part.

The system estimates this summary by examining repeated patterns in symbolic traces. If every iteration preserves a list segment from head to current, keeps two regions disjoint, or advances one pointer while retaining ownership of another, those recurring facts become candidates for the invariant. Verifier feedback then removes facts that are too strong to remain true or too weak to prove the target property.

Why it works

Why traces plus verifier feedback outperform code-only guessing

Symbolic execution traces help because they convert implicit effects into explicit state transitions. Instead of inferring from syntax that a pointer update preserves a reachable suffix, the model can read the before-and-after symbolic states where that suffix is still present. This reduces the reasoning gap between code words and proof facts.

The verifier loop adds a second correction channel. Even a trace-grounded model can overstate or understate the invariant. A too-strong claim fails because one iteration breaks it; a too-weak claim fails because it does not imply the desired property. Verifier feedback distinguishes those cases and gives the model a concrete direction for revision.

The two stages therefore split the task cleanly. Trace-guided reasoning proposes a plausible inductive summary, and tool feedback enforces formal correctness. This is a good fit for memory-manipulating loops because there are many interacting heap facts to infer, but also an exact proof criterion the verifier can check automatically.

Math after the picture

What a loop invariant must satisfy

First in words:

A valid invariant must hold before the loop, remain true after one more iteration whenever the loop condition holds, and combine with loop exit to prove the desired postcondition.

Then the compact form:

Pre implies Inv; Inv and LoopCondition and Body imply Inv'; Inv and not LoopCondition imply Post

Every symbol:

Prethe facts true before the loop starts
Invthe candidate loop invariant
LoopConditionthe condition checked at each iteration
Bodythe loop body transition
Inv'the invariant after executing one iteration
Postthe property the proof needs when the loop ends
A tiny worked example on list traversal
Suppose a loop walks a linked list with pointer current. Before the loop, current points to the head of an acyclic list.
A candidate invariant says: the remaining structure starting at current is still an acyclic list, and the already-visited prefix is disjoint from the remaining suffix.
If one iteration advances current to current.next without rewiring edges, the same statement still holds after the step, so the invariant is inductive.
If the candidate had said current is always the head, the verifier would reject it immediately because one iteration changes current.

The formal condition is short, but memory programs make each implication hard. The trace supplies the missing state detail needed to test and revise those implications.

What can go wrong

What can go wrong

Traces miss important paths. If symbolic execution does not expose a branch or loop behavior that matters, the model may never see the fact the invariant needs, so it can only produce a partial summary.
Verifier feedback is too coarse. A generic failure message may tell the model that the invariant is wrong without revealing whether it is too strong, too weak, or missing a heap relation. Then repair becomes guesswork again.
Prompted traces become too long. Complex programs can produce traces that exceed the model's context budget, meaning the amount of text it can inspect in one pass. Important repeated patterns may then be buried or truncated before the model can use them.
Done right. Cover the relevant symbolic paths, compress traces to the proof-relevant transitions, and return verifier feedback that distinguishes preservation failures from insufficiency failures. Then each repair step adds information instead of noise.
What a runnable demo should prove

What a runnable demo should prove

Take a small set of heap-manipulating loops such as list traversal, list reversal, and node deletion. For each loop, generate symbolic execution traces and compare three setups: source-code-only prompting, trace-guided prompting, and trace-guided prompting with iterative verifier repair. Measure how often the generated invariant is accepted by the verifier and how many repair rounds are needed.

acceptance_rate = verified_invariants / total_programs; repair_rounds = total_revision_steps before verifier acceptance

The demo should show that symbolic traces raise acceptance most on memory-shape tasks because they reveal the state transitions the invariant must summarize, and verifier repair should further raise acceptance because it turns failed proofs into targeted revisions.
