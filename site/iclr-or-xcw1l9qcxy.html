Transductive Visual Programming: Evolving Tool Libraries from Experience

Instead of using a fixed set of basic tools to solve visual reasoning tasks, keep a library of tools that learns and improves as you solve more problems, by spotting repeated solution patterns and turning them into new, reusable functions.

Paper explainersAll themesComputer Vision

Visual reasoning tasks (like measuring objects in 3D space) are hard for even the smartest AI models to do in one shot. The solution is to break the problem into steps, each calling a specialized tool (a piece of code that does one specific job). But most existing visual programming methods use a fixed set of basic tools, or they try to invent new tools ahead of time without ever using them. This paper introduces Transductive Visual Programming (TVP), which takes a different approach: solve problems with your current tools, watch for patterns that repeat across many solutions, and automatically turn those patterns into new tools. As you solve more problems, your toolkit grows smarter and simpler.

Zero assumption version

Fixed tools are clumsy for complex spatial reasoning

Today's best AI models can answer general questions about images, but they struggle with precise 3D reasoning — think measuring the height of a chair relative to a couch, or finding which object is closest to the camera. A beginner might try feeding the image and question directly to a big AI model (like GPT-4) and hoping for the right number. This fails because the model lacks the intermediate reasoning steps: it needs to identify the chair, find the couch, extract their heights, and compute a ratio. Visual programming fixes this by decomposing the task into explicit steps, each calling a tool (object detection, coordinate extraction, arithmetic, etc.).

The problem is that tools are either fixed in advance (you get five basic ones and that's all) or someone tries to invent new tools in a separate phase before solving any actual problems. Both approaches waste effort: you end up with tools you never use, or you struggle because your toolset is too small for the real problem patterns that emerge.

The core issue. Tools should be invented from watching what kinds of steps actually show up repeatedly in successful solutions to real problems, not decided in advance or left fixed.

The algorithm as a flow

What it actually does

Phase 1: Solve with what you have

Take a spatial reasoning question (e.g., 'what is the height ratio of the chair to the couch?'). Look up similar past problems in your Example Library. Use those as hints. Generate a program using your current set of tools. Run it, check the answer. If good, save it.

Phase 2: Spot recurring patterns

After solving many problems, cluster them by similarity. Within each cluster, look for solution steps that repeat across multiple programs (e.g., 'compute 3D height ratio' appears in five different programs).

Phase 3: Abstract a new tool

Take a recurring pattern (five programs all doing multi-step height-ratio calculations) and turn it into a single function (e.g., compute-3d-ratio) with documented inputs and outputs.

Phase 4: Generalize the tool

If two new tools (compute-height-ratio and compute-width-ratio) are nearly identical except for which dimension they measure, merge them into one flexible tool (compute-group-3d-dimension-ratio) that handles both cases through a single input option.

Phase 5: Solve new problems with the new tools

The next time a new problem arrives, the program generator has access to the new tools. Programs become shorter and simpler because instead of writing five-step solutions, you now write one-step solutions using the new tool; the Example Library guides the generator better because shorter programs are easier to retrieve and adapt.

What the paper changes

What changes: the Tool Library

The paper changes what tools are available to the program generator. It starts with five basic tools (detect objects, get 3D coordinates, compare values, etc.). As problems are solved and patterns emerge, new higher-level tools get added to the library. A new tool is a reusable function that encodes a multi-step solution pattern into a single call.

The hidden quantity

The hidden quantity: Pattern Frequency

measured quantity  =  how often a solution step repeats

The paper measures something you cannot see in a single solution: how many times a given step pattern shows up across many different problem solutions. A pattern like 'compute 3D height ratio' might appear in five of fifty solutions; another pattern might appear only once. The more frequently a pattern appears, the more valuable it is to turn into a reusable tool.

TVP estimates this by clustering solved problems by similarity and counting how many programs in each cluster share the same multi-step logic. When a pattern appears in enough programs in a cluster, it graduates to become a new tool. This turns a hidden quantity (frequency of recurring logic) into a concrete decision: should we create a new tool or not?

Plain reading. A recurring pattern is any sequence of computational steps that shows up in multiple solution programs. The more programs share that sequence, the better it is to turn it into a tool, because a single tool call saves re-writing those steps in every future program.
Paper reading. TVP clusters problems by comparing their numerical representations (which encode semantic similarity) and identifies steps that are common within clusters. A pattern qualifies for tool abstraction if it appears with sufficient frequency. Generalization happens when two tools differ only by which kind of input they use (e.g., dimension), prompting a merge.
Why it works

Why it works: tools from lived experience

TVP works by inverting the order of tool creation: instead of guessing which tools you will need ahead of time, you solve real problems first, watch which solution strategies repeat, and abstract those proven patterns into tools. This is more efficient than offline tool induction (trying to guess ahead of time) because you only create tools for patterns that actually show up. It is also better than using fixed basic tools because new tools encode recurring multi-step logic into single calls, making future programs shorter and simpler.

There is a second benefit: when you solve a new problem, you can look up similar past solutions from your Example Library and use them as demonstrations (few-shot examples). Simpler programs are easier to retrieve and adapt because they have fewer steps to match and modify. Shorter programs are also less likely to go wrong during execution because there are fewer steps for errors to accumulate in. As your tool library grows, the feedback loop strengthens: better tools mean the generator can write simpler programs (because multi-step logic becomes one tool call), simpler programs fill the Example Library with cleaner solutions (because they are easier to generate and less prone to errors), a cleaner library provides better demonstrations (because the patterns are clearer when solutions are shorter), and better demonstrations help the generator write even better programs next time (because it has clearer examples to learn from).

Measuring program complexity and tool value

First in words:

cyclomatic_complexity_count = number of decision points (if, loops) + 1. A new tool value is the reduction in count it brings: complexity_before - complexity_after when replacing multi-step logic with single tool call.

Then the compact form:

Program_CCN_iteration_t = median(McCabe_CCN for all programs in iteration_t) / median(McCabe_CCN for all programs in iteration_0)

Every symbol:

Program_CCN_iteration_tcyclomatic complexity (how many decision branches) at iteration t
McCabe_CCNa count of branches in code: one for linear, plus one for each if/loop
iteration_tround t of the training loop (t=0 is start, t=3 is after three rounds)
Reductionhow much simpler programs become after each tool abstraction
A tiny worked example
Iteration 0: Write 50 programs using five basic tools; median cyclomatic complexity = 3.0 (typical: if-detect-object, if-compute-height, if-compare, return-ratio).
Iteration 1: Mine patterns, create new tool compute-3d-ratio. Rewrite programs: now only 40 use basic tools (complexity 3.0), ten use new tool (complexity 1.0). New median = (40×3.0 + 10×1.0) / 50 = 2.2.
Iteration 2: Add two more tools. Rewrite again: median drops to 1.5. Iteration 3: median is 1.0 (many single-tool programs).
Interpretation: each tool abstraction reduces branching because the tool itself handles the decision logic internally.

As new tools are added to the library, programs stop being multi-step branching logic and become linear sequences of function calls, hence cyclomatic complexity (branch count) shrinks toward 1.

What can go wrong

What can go wrong

Clustering mistakes hide real patterns. If the initial clustering of solved problems is poor (grouping dissimilar solutions together), the pattern mining will find spurious or irrelevant patterns because the miner looks within clusters for recurring steps. These wrong patterns become tools that do not match any real future problem, so new programs stay complex or break when trying to use the misguided tool.
Over-generalization creates bloated tools. When merging two tools (e.g., height-ratio and width-ratio into dimension-ratio), if the merged tool ends up with many input options or internal decision branches, the new tool becomes as complex as the original multi-step logic, defeating the purpose.
Early mistakes propagate. If an early solved problem is wrong (the program runs but gives a bad answer), it still enters the Example Library and the pattern mining phase. Downstream programs might replicate the wrong pattern.
Done right. Start with correct, diverse solutions in the Example Library. Cluster conservatively (require high similarity). Only abstract patterns that appear in at least two or three programs in the same cluster. Validate that each new tool actually simplifies the median program complexity before adding it.
What a runnable demo should prove

What a runnable demo should prove

A demo should show the feedback loop in action. Start with a dataset of spatial reasoning questions (e.g., 20 questions from Omni3D-Bench: 'what is the height ratio of the car to the building?', 'is the cup closer to the camera than the plate?', etc.). Initialize your Tool Library with five basic tools (detect, get-3d-depth, compare, compute-ratio, compute-sum). Run TVP for three iterations: each iteration solves all 20 questions, saves good solutions, mines patterns, and adds new tools that encapsulate those patterns. Track two metrics: (1) median program complexity (measured by branch count, should fall from 3.0 to 1.0, because tools replace branches with single calls), and (2) accuracy on held-out test questions (should rise as new tools enable better solutions because higher-level tools reduce the chance of errors in execution).

improvement_accuracy = test_accuracy_iteration_3 - test_accuracy_iteration_0. improvement_complexity = (median_ccn_iteration_0 - median_ccn_iteration_3) / median_ccn_iteration_0

The demo must show that program complexity falls and held-out accuracy rises in lockstep, proving that evolved tools generalize to new problems and are not just memorizing the training set.
