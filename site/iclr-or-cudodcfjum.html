A Dense Subset Index for Collective Query Coverage

Retrieve a small set of documents that jointly cover all parts of a complex query, instead of ranking documents one by one as if any single item were enough.

Paper explainersAll themesOther

Many retrieval systems assume one document should answer one query. That assumption breaks for multi-hop question answering and text-to-SQL support, where the answer is spread across several records or passages. The right retrieval target is then not the single best item but a small subset whose contents cover the whole query. DISCo builds an index for that setting. It treats query coverage as the objective, edits the query after each retrieval step to focus on what remains uncovered, and uses a dense index built in a lifted space so each probe can still be fast. The important point is that the system optimizes collaboration among retrieved items rather than competition between them.

Zero assumption version

Why top-k ranking is the wrong target for collaborative retrieval

Standard dense retrieval embeds, meaning converts into a learned list of numbers, the query and each corpus item, then returns the highest-scoring items. That setup treats corpus items as rivals for the top ranks.

In a collective retrieval task, one item rarely contains the whole answer. One passage might define a person, another passage might state a date, and a table row might provide the missing condition. Ranking by individual score can miss this structure because the system keeps rewarding redundancy. Several top items may all cover the same part of the query while leaving another part untouched.

The paper's move. Choose items by how much uncovered query content they add, because a useful result set should cover the query jointly rather than produce several near-duplicates.

The algorithm as a flow

What it actually does

Represent the query and corpus items densely.

Map each token, meaning one text unit such as a word or subword, or contextual word feature into a learned numeric space, so similarity can be searched quickly.

Define coverage as the goal.

Score a candidate subset by how much of the query's content is matched by at least one chosen item, because one item may cover only one part.

Probe the dense index for one useful item.

Retrieve an item that covers a large uncovered portion of the query.

Edit the query after selection.

Reduce emphasis on already covered query parts, so the next probe looks for missing content rather than repeats the first result.

Repeat until coverage stops increasing.

Build a small subset whose combined coverage is close to the best possible, while keeping query time sublinear in corpus size.

The hidden quantity

The hidden quantity

measured quantity  =  remaining uncovered query content after each retrieval step

The hidden quantity is the part of the query that the chosen subset still does not explain. After each item is added, some words or contextual features are already supported by the subset and should no longer dominate the next search.

This quantity matters because a retrieval system wastes probes when it keeps chasing already covered material. DISCo tracks the uncovered remainder implicitly through query editing, then asks the index for items that contribute new coverage. That is the link between the optimization view and the indexing view: the objective says to maximize additional coverage, and the edited query steers each probe toward that goal.

Why it works

Why successive probes can approximate the best subset

Coverage is a submodular objective, meaning each extra item usually adds less once similar items are already selected. That property matters because greedy selection then has a provable path to a near-best subset. The first item can add a lot, but later duplicates add little, so the method has a built-in reason to diversify.

The query-editing step is the operational form of that theory. After one item covers part of the query, the system reduces that part's influence in the next probe. The next dense search is therefore pulled toward missing facts rather than repeated ones.

The lifted dense space matters because the index must answer each successive probe quickly. The paper uses random projections of a transformed feature space so the coverage-oriented objective can still be searched with dense-index machinery instead of a slow exact subset search over the whole corpus.

Math after the picture

Coverage with diminishing returns

First in words:

Each newly selected item earns credit only for the query content it covers that earlier items did not already cover.

Then the compact form:

marginal_gain = coverage(selected_set plus candidate) - coverage(selected_set)

Every symbol:

selected_setthe items already chosen for the subset
candidateone new corpus item being considered
coverage( )how much of the query is matched by at least one item in the set
marginal_gainthe extra uncovered query content supplied by the new item
A tiny worked example
Suppose the query needs three facts: A, B, and C.
The current subset already covers A and B.
A new candidate also covers A and B, so its marginal gain is near zero.
Another candidate covers C, so its marginal gain is large because C is still missing.
A greedy method that keeps choosing the larger marginal gain will move toward a covering subset instead of piling up duplicates.

This is the core change from ranking: the candidate is judged relative to what is already in the subset.

What can go wrong

What can go wrong

Coverage surrogates can miss true reasoning needs. If the feature-level coverage score says a query part is covered when the underlying evidence is actually incomplete, the method can stop too early.
Query editing can erase too much. If the residual query suppresses already covered parts too aggressively, the next probe may miss documents that are needed to connect earlier evidence with the missing part.
Random projections can lose detail. The lifted space keeps search fast, but too much compression can blur distinctions between candidates whose marginal gains are close.
Done right. The method is strongest when the coverage score tracks true query needs, the residual query preserves the unresolved parts clearly, and the dense index retains enough detail to separate useful candidates from duplicates.
What a runnable demo should prove

What a runnable demo should prove

Build a small corpus where each document covers a different subset of facts for multi-hop questions. Add intentional duplicates so standard ranking will repeat itself. Then compare ordinary top-k retrieval against successive subset retrieval with query editing. The demo should track how much of the query is covered after each step, how many redundant items are chosen, and how much search time grows as the corpus grows.

demo_score = (final_coverage + nonredundancy + scaled_latency_score) / 3

The demo is convincing only if the subset method reaches broader coverage with fewer duplicates while keeping query time well below a full corpus scan.
