Differentiable Simulation of Hard Contacts with Soft Gradients

When robots collide, simulators break at gradients; this paper fixes that by pairing adaptive time steps with a trick that lets you optimize through contact.

Paper explainersAll themesRobotics & Control

Robot simulators are used to train controllers via gradient descent—nudging the numbers in the control plan to improve an outcome. But when one body hits another, the math becomes discontinuous, which means gradients vanish or flip sign unpredictably. This paper solves that by combining adaptive time stepping (taking smaller steps through the collision) with a backward-pass-only contact trick that preserves usable gradients even before impact.

Zero assumption version

Collisions break the gradient signal

A robot simulator predicts where the robot will be after running a control action (like: apply force F for 0.1 seconds). To learn a better control, you take the gradient of the prediction error—a number that points in the direction of control change that shrinks the error—and nudge the control numbers slightly in that direction. This works because small nudges in the gradient direction reliably reduce error. But when two rigid bodies collide, the physics has a hard discontinuity: before contact the velocity changes smoothly, but at the instant of collision it must flip instantly. Automatic differentiation (the tool that computes gradients) sees this discontinuity and either returns zero (claiming the action has no effect) or flips the sign (claiming a nudge in the right direction actually makes things worse).

Simulators like MuJoCo soften contacts by modeling them as stiff springs—this makes the discontinuity continuous and gradients computable. But then the simulator is no longer realistic: the collision feels mushy instead of hard. If you make the spring very stiff to match reality, the gradients become unreliable again—they oscillate wildly at high frequency, so which direction to nudge becomes a random guess. If you make time steps tiny to stabilize the gradients, simulation becomes painfully slow and memory-hungry.

The problem in one sentence. Hard collisions destroy gradient signals needed to learn robot controls, and all fixes trade accuracy for speed or realism for gradient stability.

The algorithm as a flow

What it actually does

Forward pass: realistic simulation

Roll the simulator forward with hard stiff contacts and fine time steps to get physically accurate predictions.

Check if bodies collide

If two bodies are not touching (signed distance is positive), note the gap.

Backward pass: contacts from distance

When computing gradients, pretend non-touching bodies do apply a small penalty force based on how close they are.

Straight-through: swap forward and backward

Use the hard-contact forward prediction but the soft-contact backward gradients in one computation.

Adaptive time integration

Automatically shrink time steps near collision moments so penalties resolve accurately without slowdown elsewhere.

What the paper changes

What the paper changes

The paper changes how the simulator computes gradients when bodies are not touching. Instead of returning zero gradient (as a hard contact would), it pretends the distant bodies are weakly connected by an invisible spring, so nudging the control does move them closer or farther. This soft-spring model is only used when flowing gradients backward; the forward simulation stays realistic with hard contacts.

The hidden quantity

The gradient signal: what is preserved

measured quantity  =  usable gradient magnitude at separation

In standard simulators, once bodies separate (move apart after a collision), the gradient becomes exactly zero—the optimizer thinks nothing it does matters. This paper measures a hidden quantity: the size and direction of the gradient signal just before and just after bodies separate. When bodies are close but not touching, this signal is normally zero; the paper's trick makes it nonzero by attributing an imaginary restoring force to the distance gap.

The paper estimates this by computing the same forward rollout twice: once with realistic hard contacts, once with soft pre-contact penalties. It then uses a straight-through trick: when flowing gradients backward, pass them through the soft-contact version even though the forward predictions came from the hard-contact version. This preserves gradient signal where it normally vanishes.

Why it works

Why it works: the gradient trick

The core mechanism has two parts. First: adaptive time integration. When the simulator detects a collision is about to happen (distance shrinks rapidly), it automatically reduces the time step size locally, concentrating more tiny steps around the impact moment. This lets the penalty force—the soft spring that models the contact—be resolved accurately without taking enormous steps that smear the collision across multiple time intervals. The result is that the forward prediction remains physically realistic.

Second: the straight-through gradient trick. During the backward pass, the simulator computes what the gradient would be if bodies had a soft spring between them, even when they are merely close (not actually touching). This soft-contact gradient tells you: if you nudge the control slightly, the bodies would move closer or farther. The actual forward values used in the loss come from the hard-contact simulation—physically correct. This mismatch (realistic forward, soft backward) is the key: you get an honest prediction but an informative gradient signal. Bodies that separate and no longer touch now have non-zero gradients, so the optimizer can learn to prevent unnecessary collisions.

Why does this work? Because the gradient just tells you the direction and speed to nudge to reduce error. It does not need to match the forward physics perfectly—it just needs to point in a direction that, when followed, actually reduces the loss. By using soft-contact gradients, you are telling the optimizer: if you push harder, bodies will press together less. That statement is true for hard contacts up to the point of actual touch, so the optimizer learns the right strategy: approach the target while avoiding collisions.

Math after the picture

The penalty force and its gradient

First in words:

For each pair of bodies, if they are separated by distance d (positive when not touching), the paper applies a penalty force during backward pass only. The force is proportional to the negative distance: force = k * max(0, -d), clamped to act only when d is small. The penalty drives separation distance toward zero in the backward pass, creating a gradient signal.

Then the compact form:

F_contact = k * max(0, -d) , loss_total = L_prediction + lambda * sum_pairs max(0, -d_pair)^2

Every symbol:

F_contactpenalty force applied to each body pair in backward pass
kspring stiffness, set high
dsigned distance between bodies, positive when separated
L_predictionprediction error (how far from target state)
lambdaweight on preventing separation, a hyperparameter
sum_pairs max(0, -d_pair)^2penalty grows as distance shrinks toward zero
A tiny worked example
Suppose a ball approaches a wall. At distance d=0.5 m, max(0, -d) = 0, so no penalty, gradient is zero.
At distance d=0.02 m, max(0, -d) = 0.02 m (just touching). Penalty = lambda * 0.02^2 = lambda * 0.0004.
At distance d=-0.01 m (penetrating), max(0, -d) = 0.01 m. Penalty = lambda * 0.01^2 = lambda * 0.0001.
If lambda = 100, then pre-touch gradient is 100 * 0.0004 = 0.04, and in-touch gradient is 100 * 0.0001 = 0.01.
The gradient tells the optimizer: move the control to prevent approach (gradient nonzero before touch), which allows learning to happen before collision.

During forward simulation, contacts use hard penalty forces to stay realistic. During backward pass, the same distance-based penalty is applied to all nearby body pairs, creating gradient signal where none existed before.

What can go wrong

What can go wrong

Forward and backward mismatch too large. If adaptive stepping resolves hard contacts into many microsteps but you use only a few soft steps in the backward pass, the gradients become inaccurate. The fix: ensure backward-pass time steps are similarly fine-grained, even if more expensive.
Pre-contact gradient points the wrong way. If the penalty force is too weak (lambda too small), it does not overcome other forces in the loss, and the optimizer ignores it. If lambda is too large, the penalty dominates and the model learns only to keep things separated, ignoring the actual task. Tuning matters.
Penetration becomes reward. If the backward-pass penalty is asymmetric (penalizes separation more than penetration), the optimizer might learn to push objects into walls because soft-contact gradients do not fully warn it. The straight-through trick only works if soft-contact gradients are reasonable approximations to hard-contact reality.
Done right. Keep adaptive step sizes consistent between forward and backward. Tune lambda via a small offline sweep. Verify learned control on real hardware before deploying, since adaptive stepping is an approximation.
What a runnable demo should prove

What a runnable demo should prove

Build a simple 2D simulation: a block sliding on a table toward a wall. Use gradient descent to learn a sequence of forces that moves the block to a target position without penetrating the wall. Compare three versions: (A) standard MuJoCo with soft contacts, (B) standard MuJoCo with hard contacts and small time steps, (C) DiffMJX with CFD. Measure two things: (1) How many gradient steps does it take to converge? (2) Does the learned control actually work in realistic forward simulation?
