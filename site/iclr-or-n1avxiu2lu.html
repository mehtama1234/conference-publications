Real-Time Reasoning Agents in Evolving Environments

AgileThinker runs a fast responder and a slower planner together, because real-time agents need both immediate action and deeper deliberation while the world keeps changing.

Paper explainersAll themesAgents & Tool Use

Reasoning benchmarks usually freeze the world while a model thinks. Real agents do not get that luxury. Hazards appear, chances vanish, and other actors move while the agent is still deciding. This paper defines that setting as real-time reasoning and shows why two familiar agent styles both fail there. A fast agent reacts in time but often reasons too shallowly. A slow planning agent reasons more carefully but misses the moment. AgileThinker combines both paths so that the system can answer quickly when the situation is urgent and continue deeper analysis when time allows.

Zero assumption version

Why ordinary reasoning agents fail in moving settings

Many agent evaluations assume that the input stays fixed until the model finishes thinking. In an evolving environment that assumption breaks. A blocked path may open for one second. A collision risk may appear halfway through the agent's internal chain of thought. A correct answer delivered too late is still a failure because the world has already moved on.

Current agent designs usually emphasize one side of the tradeoff. Reactive systems cap compute and respond quickly, but they often miss long-horizon structure because they stop early. Planning systems allow extended deliberation, but they can become stale because their answer reflects an older version of the environment. The paper argues that real-time reasoning must optimize both logic and timing at once.

In one sentence. Run a fast responder and a deeper planner together, then use the fast path for urgent action and the slower path for harder decisions because the best reasoning depends on how much time the world still gives you.

The algorithm as a flow

What it actually does

Watch the environment continuously

The agent keeps reading state changes because timing decisions depend on what has changed since the last step.

Start a bounded fast path

A reactive path produces an immediate candidate action using limited compute so that urgent opportunities are not missed.

Start a deeper planning path

A second path keeps reasoning for longer because some tasks need a broader search over options before the best action becomes clear.

Choose according to remaining time

If the deadline is close, use the current fast answer. If more time remains, allow the deeper path to refine or replace it because the extra deliberation can still arrive in time.

Repeat as the state changes

The system keeps updating both paths because an answer that was good one moment may become wrong after the environment shifts.

What the paper changes

What the paper changes

The paper changes the basic deployment pattern for reasoning agents. Instead of choosing one style in advance, it runs a quick bounded reasoner and a slower planner at the same time. That matters because the system can satisfy immediate deadlines without giving up the chance to improve the answer when more time is available.

the object it moves  =  the agent's time allocation across reasoning paths
The hidden quantity

The hidden quantity: decision freshness

measured quantity  =  how useful an answer still is when it arrives

An answer has two qualities here: logical quality and freshness. Freshness asks whether the answer still matches the current world when the agent uses it. A route plan formed five seconds ago may be invalid now because another actor moved into the path. A rescue action proposed after the danger has already passed is useless even if the logic was right at the time it was formed.

The paper treats freshness as the missing quantity that standard reasoning benchmarks ignore. AgileThinker improves this quantity by keeping a fast path alive at all times, so the agent always has a current action candidate even while a slower path continues a deeper search.

Why it works

Why two reasoning paths beat either one alone

A purely reactive agent keeps latency low by limiting compute, but that cap also limits how much structure it can uncover before it acts. A purely planning agent can resolve more complex dependencies, but it risks optimizing an outdated snapshot because the world continues to change while the plan grows longer.

AgileThinker improves on both because it never forces the system to commit to one tradeoff everywhere. The fast path preserves timeliness by always maintaining a current answer candidate. The slower path preserves depth by continuing to search for better actions on hard cases. The controller can then choose between them using the remaining time budget and the latest observed state, so that deeper reasoning is used only when it can still affect the outcome.

Math after the picture

A simple utility view

First in words:

Treat each candidate action as worth its logical quality multiplied by whether it arrives in time and still matches the current state.

Then the compact form:

Utility(a) = Quality(a) * Fresh(a, t) - DelayCost(t)

Every symbol:

Utility(a)overall value of candidate action a at action time
Quality(a)how logically strong the candidate action is
Fresh(a, t)how well the candidate still matches the world at time t
DelayCost(t)the penalty for waiting longer before acting
tthe time when the agent commits to the action
A tiny worked example
A fast candidate scores logical quality 0.70 and freshness 0.95 at 1 second, with delay cost 0.10.
Its utility is 0.70 x 0.95 - 0.10 = 0.565.
A slow candidate scores logical quality 0.92 but freshness has dropped to 0.55 at 4 seconds, with delay cost 0.30.
Its utility is 0.92 x 0.55 - 0.30 = 0.206.
Even though the slower answer reasons better, it loses because it arrives after too much of the situation has changed.

The exact formula is not the paper's main point. A logically stronger answer can still lose overall because waiting lowers freshness and increases delay cost.

What can go wrong

What can go wrong

The controller may switch too slowly. If the system waits too long before falling back to the fast path, it can still miss the deadline because the stronger answer does not arrive in time.
The fast path may be too weak. If the bounded path is not competent enough, the agent may react on time but still take the wrong action because the quick candidate does not clear the minimum reasoning bar.
State tracking can become stale. If environment updates are delayed or incomplete, both reasoning paths may optimize an old view of the world, so freshness falls even when the architecture is designed for real-time use.
Done right. The design works when the fast path stays current, the slow path keeps improving hard cases, and the controller switches based on real remaining time so that deeper thought is used only when it can still help.
What a runnable demo should prove

What a runnable demo should prove

Build a small grid environment where doors open and close over time, hazards appear after short delays, and another moving actor can block routes. Compare three agents on the same tasks: a bounded reactive system, an extended planner, and a dual-path system following the paper's design. Give each task both a correctness objective and a response deadline.

Log not only whether the final action was logically correct, but also whether it was still valid when issued. Then vary time pressure and task difficulty. The expected outcome is that the dual-path system keeps more actions valid under tight deadlines while still solving more hard cases than the reactive baseline because it preserves both freshness and depth.

real_time_success = valid_and_correct_actions_before_deadline / total_tasks

The demo should show that a real-time agent must be judged by what it can still do before the world moves, not only by what it could have reasoned out in a frozen setting.
