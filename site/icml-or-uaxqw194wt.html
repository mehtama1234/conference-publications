De-Linearizing Agent Traces: Inferring Task Dependencies

When AI agents complete procedural tasks step by step, most steps are actually independent and could run together — a method infers which steps truly need to happen in order, then prunes out needless reasoning about the independent ones.

Paper explainersAll themesAgents & Tool Use

AI agents that execute workflows by selecting one step at a time waste effort: they reason about each step separately, even when many steps have no dependencies on earlier ones. This paper introduces BPOP, which looks at historical execution traces (records of completed workflows) and infers the hidden structure of which steps actually depend on which others. Once you know the real dependencies, you can compile them into a fast executor that tells the agent only about the steps it can legally take next, eliminating wasted reasoning.

Zero assumption version

Agents reason about every step, even irrelevant ones

When an AI agent runs a multi-step task like provisioning cloud infrastructure, it reasons through each action one at a time: pick action one, reason about it, run it, then pick action two, reason about it, run it. This feels natural and sequential.

But many actions are actually independent. For example, in a cloud setup: creating a VPC network, creating a security group, and setting up a database can all be done together if there are no dependencies. Yet if the agent reasons about them sequentially, it wastes compute and tokens (the numerical outputs the model produces as it works) reasoning about which action to pick next, even though the dependencies never change.

A naive approach tries to impose rigid procedural rules by hand (standard operating procedures), but these either become so detailed they break on real variation, or so loose they don't actually prune the search space.

The insight: Look at traces of completed tasks, and infer which action orderings were forced by true dependencies versus which were random serialization. Use those dependencies to compile a fast executor.

The algorithm as a flow

What it actually does

Collect traces

Gather historical records of completed workflow executions, each a linear sequence of actions.

Model as partial order

Assume each trace is a random shuffling of an underlying dependency graph (partial order), where some orderings are forced by logic, others are random.

Infer via Bayesian sampling

Use a frontier-based scoring method (which considers only actions available at each step, then converts their scores into probabilities) to infer which orderings are mandatory versus incidental, without the intractable calculation of all possible orderings.

Extract dependency graph

From the posterior, extract a best-estimate DAG (directed acyclic graph) showing which steps must precede which.

Compile to fast executor

Convert the graph into a frontier scheduler that tells the agent which actions it can legally execute now, eliminating wasted step-by-step planning.

The hidden quantity

The hidden quantity: True dependencies versus random order

measured quantity  =  dependency necessity

Every time an action appears before another in a trace, it could be because the second action depends on the first (a true dependency), or it could be just because the agent happened to pick it first while both were available (random order). The paper measures the likelihood that a pair ordering is forced rather than incidental.

Formally, this is inferred via Bayesian posterior over partial orders. The paper does this without computing the exact sum over all valid orderings (which is computationally intractable — #P-complete), instead using a clever likelihood that only considers the frontier of available actions at each step.

Plain reading. If you see two actions always in the same order across many traces, and they appear that way even when nothing else is waiting, it is probably a true dependency. If they swap in different traces, it is probably random.
Paper reading. A partial order is a set of actions and pairwise comparison relationships (action X must come before Y, or they are unordered). The paper infers a posterior (the updated belief after seeing data) over partial orders by modeling each observed trace as a random total ordering of the true partial order, constrained by the frontier of available actions at each step via a Plackett-Luce likelihood (a scoring rule that assigns higher probability to choices from smaller frontiers).
Why it works

Why it works: Separating true order from accident

When you observe a completed workflow, the order of actions in that trace mixes two signals: actual dependencies (A must come before B because B needs A's output) and random choice (A and B are both ready, the agent happened to pick A first).

By looking at many different traces of the same task, you can separate these signals. If A always comes before B, they probably have a dependency. If sometimes A comes before B and sometimes B comes before A, they are probably independent and the order was an accident. The paper formalizes this using Bayesian inference: assume each observed trace is a random shuffling of an underlying partial order, then ask which partial order best explains all the data.

The frontier-softmax likelihood is the clever part: at each step of a trace, the next action is drawn from the currently available actions (the frontier — all actions whose dependencies have been satisfied). This avoids the intractable problem of summing over all possible orderings; instead, the paper only tracks what was possible at each step.

Math after the picture

The likelihood equation

First in words:

For each observed trace, compute the product over all steps of the probability that the next action was chosen from the frontier. If more traces fit a partial order, that partial order is more likely posterior.

Then the compact form:

P(trace | partial_order) = product_t { 1 / |frontier_t| }

Every symbol:

tracean observed sequence of actions
partial_orderthe latent DAG over actions
frontier_tset of actions whose dependencies are satisfied after step t
|frontier_t|size of the frontier at step t
Tiny worked example
Suppose a task has actions A, B, C, D with true dependencies: A→C, B→D (meaning C depends on A, D depends on B; A and B are independent, C and D are independent).
Observed trace: [A, B, C, D]. Frontier at each step: {A,B} (both ready) → |F1|=2. After A, frontier is {B,C} → |F2|=2. After B, frontier is {C,D} → |F3|=2. After C, frontier is {D} → |F4|=1. Likelihood: 1/2 × 1/2 × 1/2 × 1/1 = 0.125.
Alternate trace: [B, A, D, C]. Same frontier sizes, same likelihood 0.125.
But a trace [A, C, B, D] would have frontier {A,B} at step 1, then after A we pick C (frontier={B,C}), but B has not been executed yet so it is still in the frontier. This trace fits the same partial order equally well (1/2 × 1/2 × 1/2 × 1 = 0.125), confirming A and B are unordered.

The product of frontier sizes is tractable because we never enumerate all orderings; we only check what was possible at each observed step.

What can go wrong

What can go wrong

Traces are too short or noisy. If the training data contains only one or two executions, or the agent makes random choice mistakes, the inferred dependencies will be unreliable. The Bayesian posterior becomes too uncertain.
Hidden dependencies from external state. If action A appears before B in all traces only because they usually run on a server that is slow on Monday mornings, the inference might falsely believe A depends on B. The method assumes ordering variations reflect true concurrency, not external factors.
Fallback overuse on unpredictable tasks. If the task has high variance or the agent makes frequent off-frontier errors, the hybrid executor falls back to step-by-step reasoning, negating the efficiency gain.
Done right: reuse on similar tasks. If tasks are stable and sufficiently similar to the training set, the inferred graph is reliable, and the frontier executor can prune reasoning by 90%+ while remaining sound.
What a runnable demo should prove

What a runnable demo should prove

Build a simple cloud provisioning simulator with 5 or 6 actions (e.g., create network, create subnet, create security group, start database, set firewall rule, deploy app). For each action, specify which other actions must finish first. Generate 10 synthetic traces by randomly shuffling actions subject to the dependencies. Feed these traces to BPOP inference. Extract the inferred graph. Then run an agent using the frontier executor and count reasoning calls and token usage.

efficiency_gain = (baseline_tokens - frontier_tokens) / baseline_tokens

The demo should show that BPOP correctly recovers the dependencies from shuffled traces, and that the frontier executor reduces token usage by at least 70% while maintaining correctness.
