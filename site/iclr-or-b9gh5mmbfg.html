RoboPARA: Dual-Arm Robot Planning with Parallel Allocation

Use an LLM to build a map of what each task step depends on, then schedule both robot arms in parallel instead of waiting for the left arm to finish before the right begins.

Paper explainersAll themesRobotics & Control

Dual-arm robots can work on two things at once, but most planning methods tell them to do tasks one step at a time. RoboPARA uses a language model to figure out which steps can happen in parallel, then schedules the left and right arms simultaneously. The result: robots finish complex multi-step jobs 30% to 50% faster than existing methods, because two arms working on independent steps at the same time cuts the total time nearly in half compared to one arm doing everything sequentially.

Zero assumption version

Sequential arms waste half the robot

Dual-arm robots have two arms that can move independently. Yet most planning methods treat them as a single unit: pick up the left-arm object, put it down, then start the right-arm task. The arms sit idle while waiting their turn.

A beginner might try: run all steps in order, assigning each to whichever arm is free. But this fails because tasks have hidden dependencies—you cannot cut the mushroom until you pick it up. Without a map of these dependencies, the planner cannot tell which steps can truly overlap and which must wait.

The core problem. Existing planners do not discover task dependencies, so they default to sequential execution instead of true parallelism.

The algorithm as a flow

What it actually does

Retrieve task context

When you say 'make an omelette', the system looks up: what is a kitchen, what things are available, what are the rules.

Break down the task

The LLM writes out every small step (pick egg, crack it, heat pan, pour, cook) and says which steps depend on which.

Build a dependency graph

The LLM creates a diagram (a directed acyclic graph) showing the order: you must pick before you crack; you must heat the pan before you pour.

Check for deadlocks

The algorithm verifies: can both arms ever try to grab the same object at the same time? If yes, it fixes the schedule.

Assign arms and times

For each step, decide: does the left arm do this or the right arm? What is the earliest time it can start, given its dependencies?

What the paper changes

What the paper changes: the task schedule

Instead of a linear list of steps (do this, then that, then the other), RoboPARA produces a schedule: a pair of (time, arm) labels for each step. Step 1 starts at time 0 on the left arm. Step 2 starts at time 0 on the right arm (in parallel). Step 3 waits until step 1 finishes, then starts on either arm.

The hidden quantity

The hidden quantity: dependency distance

measured quantity  =  Depth of the dependency graph

Behind every parallel schedule lives a number: the longest chain of must-happen-in-order tasks. If you must pick the egg, then crack it, then heat the pan, then pour, then cook—that is a chain of length 5. Every other task can run in the gaps. The shorter this chain, the more time both arms can work in parallel.

RoboPARA measures this by building the dependency graph and finding the longest path through it. This number determines the theoretical minimum time because if task A must finish before task B, and task B must finish before task C, there is no way to run them faster than A then B then C, even with unlimited arms. The algorithm then schedules both arms to stay as close to this minimum as possible, filling in all the independent tasks in the gaps.

Why it works

Why it works: two-stage parallel reasoning

The trick has two parts. First, the LLM reads your instructions and generates a dependency graph—which is a formal way to say: 'here are all the steps, and here is which ones must happen before which others'. This graph is the hidden structure that sequential planners never build.

Second, the algorithm schedules tasks to respect these dependencies while maximizing parallelism. It iterates: pick an incomplete task that has no unsatisfied dependencies, assign it to an arm, and record its start time. Both arms pick tasks this way at the same time. The result is a valid parallel schedule with no deadlocks (no two tasks trying to use the same object simultaneously). Since the dependency graph explicitly shows which steps can overlap, the two arms find far more parallelism than a greedy sequential method would.

The scheduling equation

First in words:

Minimize the total time (makespan) by assigning each task a start time and an arm, such that all dependencies are satisfied and no two simultaneous tasks conflict.

Then the compact form:

C_max = min over all valid schedules of: max over all tasks v of (start_time(v) + duration(v))

Every symbol:

A tiny worked example
Task graph: Pick-egg (1 step), Pick-flour (1 step), Mix (1 step, depends on both picks), Bake (2 steps, depends on mix).
Sequential plan: Pick-egg (0–1), Pick-flour (1–2), Mix (2–3), Bake (3–5). Total: 5 time units.
Parallel plan: Pick-egg on left (0–1) + Pick-flour on right (0–1, same time), Mix on left (1–2), Bake on right (2–4). Total: 4 time units.
Speedup: 5 / 4 = 1.25× faster by running picks in parallel.

The equation finds the schedule where the last task finishes as early as possible, while respecting which tasks must wait for which others and preventing both arms from using the same object.

What can go wrong

What can go wrong

LLM hallucinates a dependency. If the LLM thinks step A must come before step B when it need not, it blocks parallelism unnecessarily. RoboPARA mitigates this by verifying the dependency graph against the retrieved context rules.
Deadlock: both arms grab the same object. Without explicit locking, two arms might both reach for the egg. RoboPARA prevents this by checking that no two concurrent tasks access the same object, and reordering if needed.
New task type not in the retrieval library. If you ask the robot to do something that was never in the training data, the LLM may generate incorrect steps or dependencies. The system only knows what it has seen before.
Done right. The paper's ablations show that removing the dependency graph or the deadlock check causes a 18%–51% rise in failures. When both are present, the method works reliably.
What a runnable demo should prove

What a runnable demo should prove

Build a simple kitchen simulator with two robot arms, five objects (egg, flour, pan, spatula, bowl), and five basic skills (pick, place, crack, heat, mix). Write a task in English: 'make an omelette' or 'make a sandwich'. Run RoboPARA on it. Measure: how many steps run in parallel (target: more than 2 on average for complex tasks, because if fewer steps overlap, the speedup shrinks), and how much faster is the parallel schedule than sequential (target: more than 1.2 times speedup on medium-complexity tasks where parallelism is moderate, more than 1.5 times on hard tasks where many independent steps exist).

Parallel speedup = time_sequential / time_parallel

If the demo shows both arms working simultaneously on independent steps without conflicts, and finishes measurably faster than sequential execution, you have proven the core insight: explicit dependency graphs unlock parallelism because without knowing which steps truly can overlap, the planner defaults to doing everything one at a time.
