reAR: Visual Autoregressive via Token-wise Consistency

A simple training trick that makes autoregressive image models speak the same language as their decoder, so generated tokens actually produce good images.

Paper explainersAll themesGenerative Models & Diffusion

Image generation has two main routes: diffusion models (noise fades into an image by small steps) and autoregressive models (build an image one code at a time, like words in a sentence). Autoregressive generation sounds natural and unified with language, but it lags behind diffusion in image quality. This paper finds the real bottleneck: the generator and the decoder (tokenizer) have stopped listening to each other. The generator produces codes, but the decoder cannot turn them back into faithful images—like whispering one thing to a transcriber who hears another. The paper proposes reAR, a training fix that forces the generator to stay coherent with the decoder, using no architectural changes and no new models.

Zero assumption version

The autoregressive image generator talks past its decoder

A tokenizer is a decoder—it takes a short code (token) and turns it into a block of pixels. An autoregressive image model is a generator—it predicts tokens one by one, like a person typing letters to spell out an image. The two should be partners: the generator learns what tokens work well, and the tokenizer faithfully decodes them into pixels.

In practice, they drift apart. The generator learns to output tokens that are statistically convenient for it to predict next (whatever minimizes its loss function), but these tokens may map to blurry or inaccurate pixel blocks when the tokenizer tries to decode them. The decoder sees tokens the generator never showed it during training—tokens in noisy or ambiguous contexts. When the generator says token 47, the tokenizer may decode it as muddy green instead of crisp blue, because token 47 was always decoded cleanly in training but now appears in an unfamiliar context.

Naive approaches try to fix this by changing the tokenizer or reordering the tokens. But those are heavy hammers.

The fix: train the generator to predict and recover decoded representations, forcing it to learn codes that the tokenizer can reliably turn into pixels. Train the generator to predict the next code while also recovering a faithful representation of the current code, ensuring the tokenizer never sees a code in an unfamiliar context.

The algorithm as a flow

What it actually does

Step 1: Normal token prediction

Given the image so far, predict the next token (standard autoregressive loss).

Step 2: Recover current code

Force the model to predict what the tokenizer outputs for the current code from the current state.

Step 3: Predict target output

Predict what the tokenizer will output for the next code under a noisy version of the context.

Step 4: Loss measures mismatches

Three losses: standard prediction error plus errors in predicting tokenizer outputs.

Step 5: Training converges

Generator learns to emit tokens that are consistent with tokenizer decoding at every step.

What the paper changes

The single thing that changes

The generator (transformer) training objective. Instead of just predicting the next code, it now simultaneously recovers what the tokenizer outputs for the current code and predicts what the tokenizer will output for the next code. This adds two extra supervised signals during training.

the object it moves  =  training objective
The hidden quantity

Generator-tokenizer consistency

measured quantity  =  tokenizer output prediction accuracy

The hidden quantity is how well the generator can predict what the tokenizer will output. When the generator says code 47, how close is what it predicts the tokenizer will output compared to what the tokenizer actually produces? A perfect prediction means the generator understands the tokenizer's language; poor prediction means they are drifting.

The paper measures this by training the model to predict tokenizer outputs (the numerical representation the tokenizer uses) and checking the error. If the error is small, the generator is speaking the tokenizer's language. If large, they are out of sync.

Why it works

Why forcing the generator to predict tokenizer outputs fixes the mismatch

The core insight: if the generator can predict what the tokenizer will output from each code, then the generator must learn to emit codes that the tokenizer reliably decodes. Predicting tokenizer outputs is a supervision signal that pulls the generator and tokenizer into alignment.

Here's the chain. During normal autoregressive training, the generator only knows if the next code was correct—it gets no feedback on whether the code it produced would decode cleanly. Adding prediction of tokenizer outputs changes that: now every code the generator emits must also come with an accurate prediction of what the tokenizer will output. A code that decodes poorly would produce a large prediction error, so the generator avoids it. Codes that the tokenizer handles reliably, across many contexts, are easier to predict and have lower error. Training converges when the generator has learned a set of codes that are consistent with the tokenizer.

The trick is that this happens without changing the tokenizer or the generation order. The generator simply learns which codes are actually usable in which contexts by seeing the tokenizer's own outputs as ground truth.

The training equation

First in words:

Loss = standard next-token prediction error + recovery of current token embedding + prediction of next token embedding

Then the compact form:

L = L_pred + alpha * ||embed_pred_current - embed_true_current||^2 + beta * ||embed_pred_next - embed_true_next||^2

Every symbol:

Ltotal training loss
L_predstandard cross-entropy for predicting the next token ID
embed_pred_currentgenerator's prediction of what the current token decodes to
embed_true_currentwhat the tokenizer actually decodes the current token to
embed_pred_nextgenerator's prediction of next token decoding under noisy context
embed_true_nextwhat the tokenizer actually decodes the next token to
alphaweight controlling how much to penalize poor current-token recovery
betaweight controlling how much to penalize poor next-token recovery
A tiny worked example
Token prediction loss: 0.5 (the next code was slightly surprising to predict)
Current code recovery error: ||[0.2, 0.3] - [0.1, 0.2]|| = ||[0.1, 0.1]|| = 0.014, alpha=5 -> penalty 5 * 0.014 = 0.07
Next code prediction error: ||[0.5, 0.4] - [0.6, 0.3]|| = ||[-0.1, 0.1]|| = 0.014, beta=5 -> penalty 5 * 0.014 = 0.07
Total: 0.5 + 0.07 + 0.07 = 0.64
If the generator had chosen a code that the tokenizer decodes poorly, the recovery errors would balloon, raising the total loss until the generator stops using that code.

The embedding losses act as a mirror: the generator sees what the tokenizer will do and learns to emit tokens the tokenizer handles consistently.

What can go wrong

What can go wrong

If alpha and beta are too large. Predicting tokenizer outputs becomes the dominant signal, and the generator stops optimizing for actual code prediction quality. The predictions are accurate but the generated images are blurry.
If the tokenizer itself is poor. The generator learns to be consistent with a bad decoder. If the tokenizer cannot decode cleanly (lossy or low-capacity), no amount of consistency training helps, because the bottleneck is in the decoder itself—even perfect alignment between generator and tokenizer does not fix a fundamentally weak tokenizer.
If the noisy context is unrealistic. If the noise added when predicting tokenizer output does not match the kinds of contexts the codes will actually see, the generator may overfit to that noise and fail at generation time.
Done right. The weights alpha and beta are tuned so predicting tokenizer outputs is a gentle guide, not the main objective. The tokenizer is pre-trained and frozen. The noise mimics realistic generation scenarios. The result is a generator that speaks the tokenizer's language without losing sight of image quality.
What a runnable demo should prove

What a runnable demo should prove

Train an autoregressive image model on a small dataset (CIFAR-10 or 32x32 synthetic images) with a fixed tokenizer. Measure tokenizer-output prediction accuracy and final image quality (FID) across training. Split the training into three phases: (1) baseline autoregressive with no prediction loss, (2) add tokenizer-output prediction with alpha=beta=1.0, (3) tune alpha and beta. Plot prediction error and FID over time. The demo should show that as prediction accuracy improves, FID improves too, up to an optimal tuning point, because the generator learns to avoid codes that the tokenizer decodes poorly.

prediction_error = mean absolute error of predicted tokenizer outputs vs ground truth tokenizer outputs; FID = Frechet Inception Distance between generated and real images

The key observation: after adding the tokenizer-output prediction loss, the model stops wasting effort on codes the tokenizer cannot decode well, and image quality jumps.
