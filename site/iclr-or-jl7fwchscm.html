ReasoningBank: Agent Memory from Trial and Error

An agent learns to solve tasks better by storing what worked and what failed, then retrieving those lessons when facing new problems.

When an LLM agent tackles a real-world task like browsing the web to book a flight, it tries different actions, some succeed and some fail. Today's agents throw away everything they learn; ReasoningBank teaches an agent to remember generalizable reasoning patterns from both the wins and the losses, so it gets smarter each time it encounters a new task.

Zero assumption version

Agents Keep Making the Same Mistakes

An LLM agent is a program that uses a language model to read a task, decide what action to take (like clicking a button or typing a search), see what happened, and repeat until the job is done. Today's agents do this well for a single task, but they do not remember lessons once the task is over.

A naive approach: you might hope the agent learns on the job, updating its internal weights every time a task ends. That fails because it is incredibly risky: a bad tweak from one task corrupts the agent's ability to handle every future task. Also, language model weights are huge, and retraining them for every small task is impossibly slow.

So agents are built to be stateless: each task starts fresh, no memory of past wins or losses. This means an agent solving web tasks might spend the first hour learning where to click to search on Day 1, then spend the first hour learning it all over again on Day 2 solving a different site, and again on Day 3. It is like having amnesia every morning.

In one sentence. ReasoningBank stores memories of what worked and what did not, then the agent retrieves those lessons when solving new tasks.

The algorithm as a flow

What it actually does

Agent runs a task, trying multiple paths

Generate many candidate trajectories (sequences of actions) for a single task to explore different solutions.

Judge which ones succeeded

Use a separate judge (another LLM prompt) to grade each trajectory: did it solve the task or fail?

Extract generalizable lessons

From each successful trajectory, ask the LLM to explain why it worked (not the raw steps, but the reasoning pattern); from failures, extract what went wrong.

Store in memory pool

Keep a growing collection of these reasoning lessons, indexed so they can be found quickly by similarity.

On a new task, retrieve and apply

Look up memories most similar to the new task query using fast search in the memory pool; hand them to the agent to read before acting.

What the paper changes

What the Paper Changes

ReasoningBank changes what the agent stores and reuses. Instead of throwing away every task after it is done, the agent now maintains a memory pool of generalizable reasoning strategies extracted from past trajectories.

the object it moves  =  memory content: from raw trajectories to extracted reasoning strategies
The hidden quantity

The Hidden Quantity: Reasoning Strategy Quality

measured quantity  =  reasoning strategy relevance and generalizability

A reasoning strategy is a brief explanation of why a solution worked or failed, not the solution itself. For example, where to click to search on a website is a strategy; the exact coordinate is not. The quality of a strategy depends on how often it applies to new tasks. A vague strategy like try clicking things is weak; a precise one like search functionality is behind a magnifying-glass icon on the top right is strong.

ReasoningBank measures this by running many parallel or sequential attempts at each task (test-time scaling). If a stored strategy helps an agent solve a variety of new tasks faster and more accurately, it is a high-quality, transferable strategy—because the agent spends less time exploring dead ends when it already has guidance on where to look. If it fails on new tasks, it is too specific and gets deprioritized in future retrievals, because it does not generalize.

Why it works

Why It Works: Two Loops That Reinforce

ReasoningBank works because it creates a feedback loop: the more diverse experience you generate (by running many attempts at a task), the better the raw material for extracting good reasoning strategies. The better the strategies in memory, the faster and more reliably the agent can solve new tasks—because it starts each task with guidance, not guessing—which makes those new tasks generate even better strategies to add to the pool.

Here is the mechanical chain: (1) You give the agent a new task. (2) It retrieves relevant memories from the pool—past solutions to similar problems or patterns that failed and should be avoided. (3) Armed with these hints, it explores multiple possible paths (parallel test-time scaling) or refines its approach step-by-step (sequential). (4) The judge grades each path. (5) From both the winners and losers, the system extracts the reasoning pattern—the insight you would tell a colleague. (6) This new reasoning joins the pool. (7) Next time, this pool is richer, so the next agent's exploration is smarter from the start.

Why this beats storing raw trajectories: raw trajectories are brittle. A recorded sequence of clicks works only on the exact same website. But reasoning—'search boxes are usually in the top-right corner, and you can either click them or type directly'—works on dozens of sites. Storing failures is equally critical because it teaches what not to do, and that lesson applies broadly too.

Math after the picture

The Memory Retrieval Scoring

First in words:

When a new task arrives, the system converts (turns into a list of numbers) the task query and compares it against lists of numbers for all stored reasoning strategies. The most similar strategies rank highest. Similarity is measured by cosine distance: how aligned two lists of numbers are.

Then the compact form:

sim(q, m_i) = dot(embed(q), embed(m_i)) / (||embed(q)|| * ||embed(m_i)||)

Every symbol:

qthe new task query (a sentence or paragraph)
m_ithe i-th stored reasoning memory
embed(·)converts text to a list of numbers using a trained conversion model
dot(·, ·)the dot product: multiply each pair of numbers and sum them
||·||the magnitude of a list (square root of sum of squares)
sim(...)cosine similarity, a number from -1 to 1 (higher means more similar)
A tiny worked example
Suppose a stored memory is 'Click magnifying glass to search'; its vector of numbers is [0.8, -0.2, 0.5].
New task query: 'Find a product on the shopping site'; its list is [0.7, -0.1, 0.6].
dot product = 0.8×0.7 + (-0.2)×(-0.1) + 0.5×0.6 = 0.56 + 0.02 + 0.30 = 0.88.
Length of memory list = sqrt(0.8^2 + 0.2^2 + 0.5^2) = sqrt(0.64 + 0.04 + 0.25) = sqrt(0.93) ≈ 0.96.
Length of query list = sqrt(0.7^2 + 0.1^2 + 0.6^2) = sqrt(0.49 + 0.01 + 0.36) = sqrt(0.86) ≈ 0.93.
Similarity = 0.88 / (0.96 × 0.93) = 0.88 / 0.89 ≈ 0.99 (very similar; this memory is likely useful).

Higher similarity scores put relevant memories at the front of the retrieval list, so the agent sees helpful lessons first.

What can go wrong

What can go wrong

Bad extraction ruins the memory pool. If the judge or extraction step misidentifies a failed trajectory as successful, the memory pool gets poisoned with a bad lesson. Future tasks will follow bad advice, making them worse, not better. This is why the judge prompt matters enormously.
Overfitting the memory to one task. If you extract reasoning that is too specific ('click the Buy button on Amazon checkout'), it will not retrieve for other tasks. The memory becomes large but unhelpful. This is why the paper emphasizes extracting generalizable reasoning patterns, not raw actions.
Retrieving irrelevant memories by mistake. Semantic similarity search sometimes returns memories that are nominally similar but actually misleading. For example, 'check the terms-and-conditions checkbox' might retrieve 'skip the checkbox and proceed' if both mention checkboxes. The agent must still reason about whether a memory is actually applicable.
Done right. When extraction focuses on transferable insight (the reasoning why), when the judge is reliable, and when retrieved memories help but do not override the agent's own judgment, the pool grows richer and smarter over time—because generalizable lessons compound in value, each new task both learns from and teaches the pool.
What a runnable demo should prove

What a runnable demo should prove

Build a demo agent that solves a series of web browsing or software engineering tasks. On Task 1, run without any memory: measure success rate and average steps. Then extract and store the reasoning patterns (successes and failures). On Task 2, run the same agent but initialize it with the memories from Task 1. Measure whether success rate climbs and steps shrink. Repeat for Tasks 3 and 4. The memory pool should grow, and each task should benefit.

improvement = (success_rate_with_memory - success_rate_without) / success_rate_without × 100%

The irreducible proof is this: a task solved in fewer steps and higher success when memory is present than when the agent starts cold. That gap grows as the memory pool accumulates richer, more general reasoning strategies.
