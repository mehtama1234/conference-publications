Auditing Black-Box LLM APIs with a Rank-Based Uniformity Test

When you call an LLM through an API, the company might secretly swap in a cheaper model; this paper detects that swap by testing whether the API's answers fit the expected pattern.

Paper explainersAll themesAlignment, Safety & Fairness

When you use an LLM API, the company serves you answers through a hidden box—you cannot see the weights, and you usually cannot even see the confidence scores. If the company wants to save money, it might swap the real model for a cheaper, quantized (rounded-number) version, because serving a large model is expensive and quantized versions cost much less to run. Malicious actors might also swap it to add jailbreaks or harmful behavior. This paper gives you a test to catch that swap, using only the final answers.

Zero assumption version

The API provider's secret substitution

When you call an LLM through an API, you get only the final answers. You cannot see the model's internal weights, and often not even the confidence scores. This opacity is intentional—it protects the company's intellectual property. But it creates a loophole: the company could swap the real model for a cheaper fake (a quantized version with rounded numbers, or a fine-tuned variant designed to jailbreak) because serving that fake model costs much less than serving the real one, and users would never know. You would just see answers that seem similar enough.

A naive detector would compare benchmark performance: if the API still solves 95% of math problems, maybe it is the real model. But this breaks because quantized models are often trained carefully to preserve accuracy, and because the company might serve different variants to different users or reroute once it detects testing. The real test needs to work with very few queries, and it needs to be invisible to the company.

The paper's move in one sentence. Instead of testing performance, test whether the API's answers come from the same distribution (the pattern of all possible answers) as the real model, by checking whether each API answer ranks unusually high or low in a reference sample from the real model.

The algorithm as a flow

What it actually does

Step 1: Choose a score function

Pick a way to score each answer (e.g., how long, how confident, how fluent). This score turns each answer into a single number.

Step 2: Sample from the reference model

For each test prompt, run the real model many times to collect a distribution of possible answers and their scores.

Step 3: Query the API once

Send the same prompt to the black-box API and score its answer using the same function. Only one query per prompt—cheap and hard to detect.

Step 4: Compute the rank

Rank the API answer's score against the reference distribution. If it is the real model, it ranks uniformly (sometimes high, sometimes low, sometimes middle).

Step 5: Run the statistical test

Collect many ranks and test whether they are uniform or skewed. A skewed pattern proves the API is serving something different.

What the paper changes

What the paper changes

The paper measures and compares the rank distribution of API answers within the reference model's output space. Instead of directly comparing answers (which is noisy), it asks: when you sort the reference model's answers by some quality metric, where does the API answer rank? The central idea is that if the API serves the same model, its answer should rank in a random, uniform position. If it serves a different model, its rank will be systematically skewed (always high, always low, or clustered).

the object it moves  =  rank distribution of answers
The hidden quantity

The rank percentile: where does the API answer sit?

measured quantity  =  rank percentile (position in the reference distribution)

The rank percentile is a single number that says: if we sort 100 answers from the real model by quality, at what position does the API answer land? If it lands at position 50, it is dead center. If it lands at position 95, it is in the top 5%. The paper measures this percentile for many prompts and tests whether the percentiles are uniformly scattered or clumped.

The paper estimates this by: (1) running the reference model N times on a prompt to get N answers and scores, (2) sending one query to the API, (3) scoring the API answer the same way, (4) counting how many reference answers scored lower than the API answer, and (5) dividing by N to get a percentile. This percentile is the hidden quantity—it reveals whether the API's distribution has shifted.

Plain reading. If I ask the real model the same question 100 times, I get 100 different answers with different levels of quality. If I ask the API the same question once, its answer will be somewhere in that list of 100—maybe it is the worst answer, maybe the best, maybe in the middle. The paper counts: how many of the 100 real-model answers are worse than the API answer? That count, divided by 100, is the rank percentile.

If the two models are identical, this percentile should scatter uniformly (sometimes high, sometimes low) across many prompts. If the API serves a different model, the percentiles will cluster (always high if the fake model is more confident, or always low if it is less capable).
Why it works

Why the test detects model swaps: the core intuition

The mechanism rests on a simple principle: if two language models are truly identical, they produce the same distribution of outputs. This means if you ask both the same question, the API's answer should be a random draw from that distribution—it could land anywhere. But if the company swapped in a quantized or fine-tuned variant, that fake model produces a different distribution. Its answers are systematically different: maybe more conservative (always ranking low), or more overconfident (always ranking high), or biased toward certain answer lengths.

By comparing the API answer's rank percentile against a large sample from the real model, you are indirectly comparing the two distributions. If the ranks look uniform (scattered all over the place), the distributions are likely the same. If the ranks clump (always toward the high end, or always toward the low end), the distributions have shifted, and the company is serving a fake model. The test resists adversarial evasion because it avoids obvious query patterns: each prompt is normal user text, only one API query per prompt, and no suspicious probing—the company would have to detect the pattern after receiving results, not while testing happens. This timing advantage makes the test hard to fool.

The statistical test: Cramer-von Mises for uniformity

First in words:

For each prompt, compute the rank percentile (the fraction of reference answers that score lower than the API answer). Collect these percentiles across K prompts. Test whether they follow a uniform distribution using the Cramer-von Mises (CvM) statistic: the average squared distance between the measured distribution of ranks and the ideal flat line.

Then the compact form:

omega_2 = integral from 0 to 1 of (empirical_CDF(u) - u)^2 du

CvM statistic ≈ 0.08 (small = good uniformity). Now imagine a fake model always inflates answers:
Fake ranks = [0.1, 0.05, 0.15, 0.08, 0.12]. All clustered near the bottom (fake model ranks low because it is less fluent).
CvM statistic ≈ 0.25 (large = non-uniform). The test rejects the hypothesis that this fake model is real with high confidence.

If the API serves the real model, rank percentiles scatter uniformly. If it serves a fake, they cluster, and the CvM statistic grows—catching the swap.

What can go wrong

What can go wrong

The score function matters. If you choose a score that both models agree on, the test fails. For example, if you score by count of words (tokens are just words in this context) alone, quantized and real models might have identical length distributions. The paper empirically evaluates many score functions (length, likelihood, perplexity, semantic similarity) and picks the one with the highest detection power for each threat.
Adversarial mixing: the company serves a probabilistic blend. If the company is clever, it might serve the real model 90% of the time and the fake model 10% of the time. This creates a blend that is hard to detect. The ranks scatter somewhat randomly instead of clumping cleanly. The test can still detect it if the query budget is large enough, but the detection power degrades.
Limited query budget under severe constraints. If you can only afford 10 total API queries, the statistical power drops. The Cramer-von Mises test needs enough samples to establish that the distribution is skewed, not just random noise. The paper shows the method remains practical under realistic query budgets (hundreds of queries), but it is not magical with very few queries.
Done right: choose multiple uncorrelated score functions, use sufficient queries, and combine results. The paper's approach avoids these pitfalls by evaluating multiple score metrics simultaneously (length, semantic score, likelihood score where available) and averaging the detection results. This works because if one score function misses a shift (e.g., token length stays the same), another score function (e.g., semantic similarity) will catch it. By combining many scores, the test catches shifts that any single score would miss, and it breaks through adversarial mixing because the company cannot engineer a fake model that matches all score distributions simultaneously.
What a runnable demo should prove

What a runnable demo should prove

Build a script that: (1) instantiates a real language model locally (e.g., a small open-source LLM like Llama 2 7B), (2) fine-tunes or quantizes it to create a fake variant (e.g., 4-bit quantization, or a 10-step jailbreak fine-tune), (3) simulates an API that sometimes serves the real model and sometimes the fake, (4) runs RUT with 50 test prompts, scoring each answer by three metrics (response length, a semantic similarity score using embeddings, and a fluency heuristic), (5) computes the rank percentiles for the real model run versus the API run, and (6) applies the Cramer-von Mises test to measure uniformity. The demo's key metric is: what is the detection AUROC (area under the receiver operating characteristic curve)?

detection_AUROC = area_under_curve(false_positive_rate, true_positive_rate) across different CvM thresholds; higher is better (1.0 = perfect detection, 0.5 = random guessing)

The demo must show that when you run RUT on the fake-model case, the AUROC climbs above 0.85, proving the test caught the swap with high confidence, while a naive accuracy-based detector would fail because the quantized model still solves most problems correctly.
