FastAvatar: Towards Unified and Fast 3D Avatar Reconstruction with Large Gaussian Reconstruction Transformers

FastAvatar predicts a full 3D Gaussian avatar in one feedforward pass, then keeps adding registered Gaussian pieces from new views so quality rises with more observations instead of restarting from scratch.

Paper explainersAll themesMultimodal

3D avatar reconstruction means recovering a controllable digital head from images or video. Existing systems usually pick one input type, such as a single image or a calibrated multi-view capture, and then run slow fitting loops that optimize the avatar for that case only. FastAvatar uses one transformer (a model that updates many items by mixing information across them) to handle single images, sparse views, or monocular video in the same pipeline. It predicts a canonical 3D Gaussian Splatting representation, meaning a cloud of colored 3D blobs whose positions, sizes, and opacities can be rendered into images, and it keeps improving that representation as more frames arrive.

Zero assumption version

Why fast avatar reconstruction is usually brittle

A face video contains changing pose, changing expression, self-occlusion, and uneven coverage. One frame may show the left cheek clearly and hide the right ear. Another frame may show the mouth open and the head turned away. If a method tries to merge these observations directly, it can confuse expression changes with identity shape changes and place surface details at the wrong 3D locations.

Many earlier systems avoid that confusion by solving a separate optimization problem for every sequence or every input type. That takes time because the model keeps re-fitting the avatar to the observations. They also waste data because adding new frames often means rerunning the whole optimization instead of attaching only the new evidence to the current 3D model.

The method in one sentence. FastAvatar predicts a canonical Gaussian avatar from any supported input set, then aligns and fuses new Gaussian evidence frame by frame so extra observations raise quality because they add registered 3D detail instead of restarting the solve.

The algorithm as a flow

What it actually does

Encode every observation with guidance

For each input frame, extract image features and attach camera pose, facial expression coefficients, and head pose because those signals specify how the current observation differs from the shared head template.

Inject an initial 3D prompt

Start from a coarse canonical Gaussian template because a shared 3D reference lets each frame propose corrections in the same coordinate system instead of creating its own separate surface structure.

Aggregate cues with the transformer

The transformer mixes evidence across frames and predicts a canonical set of Gaussians whose locations and appearance explain the whole input set together.

Track landmarks across views

Use facial landmarks to register newly predicted Gaussian pieces to the current avatar, which reduces drift because corresponding facial parts are fused at matching 3D regions.

Apply sliced fusion losses

Compare rendered slices and fused Gaussian pieces during training because this loss punishes merges that overwrite sharp regions which the current avatar already explains correctly.

What the paper changes

What the paper changes

The paper changes the reconstruction object from a sequence-specific fitted mesh to a canonical Gaussian set predicted directly by one feedforward model. It also changes the update rule: new frames are fused into that canonical set instead of triggering a full re-optimization.

the object it moves  =  canonical 3D Gaussian avatar
The hidden quantity

Frame-to-canonical registration quality

measured quantity  =  registration quality (how accurately each observed frame is mapped into the shared canonical head coordinates)

The hidden quantity is whether a detail seen in one frame lands at the same canonical 3D place when another frame sees that detail under a different pose or expression. If that registration is wrong, the model will store duplicate surface structure or smear appearance across nearby regions.

FastAvatar estimates that registration using multi-granular guidance, meaning several levels of pose information, and landmark tracking. Camera pose explains where the camera sits, head pose explains how the skull is rotated, and expression coefficients explain local facial deformation. Keeping those signals separate matters because they correct different sources of motion.

Why it works

Why the unified fast path works

The method works because it separates three jobs that older systems often mix together. First, the model interprets each frame using guidance signals that describe camera motion, head motion, and expression motion. Second, it predicts all surface structure in canonical coordinates, which means neutral shared coordinates for the person rather than per-frame coordinates. Third, it fuses only the evidence that is new after registration. That separation prevents pose variation from being stored as shape variation.

The transformer matters because multi-frame evidence is complementary. A single frontal frame may show skin texture well but miss the ear contour. A profile frame may recover the ear contour but hide one eye. Mixing features across frames lets the model predict one Gaussian set that uses each frame for the regions it actually constrains. Incremental aggregation then raises quality with more data because new observations extend coverage or sharpen uncertain regions instead of replacing the entire reconstruction.

Math after the picture

The incremental fusion objective

First in words:

Training balances a reconstruction term that matches rendered views, a registration term that keeps corresponding landmarks aligned, and a sliced fusion term that keeps newly fused Gaussian pieces consistent with the current canonical avatar.

Then the compact form:

L_total = L_render + lambda_reg * L_reg + lambda_slice * L_slice

Every symbol:

L_renderimage reconstruction loss between rendered avatar views and observed frames
L_reglandmark registration loss that penalizes misaligned corresponding facial points
L_slicefusion loss on sliced Gaussian subsets so new pieces merge cleanly with the current avatar
lambda_reg, lambda_sliceweights controlling how strongly the training process enforces alignment and fusion consistency
A tiny worked example
Suppose one training batch gives L_render = 0.20, L_reg = 0.05, and L_slice = 0.08.
If lambda_reg = 2 and lambda_slice = 1.5, then the total is 0.20 + 2 * 0.05 + 1.5 * 0.08 = 0.42.
The registration term is weighted strongly because a small 3D placement error can corrupt many downstream fused views.
The sliced fusion term is also weighted because the model must add new Gaussian pieces without duplicating structure that the avatar already explains.

The point of the loss is not only to fit pixels. It also teaches the model where new evidence belongs in the canonical 3D model.

What can go wrong

What can go wrong

Pose or expression guidance is inaccurate. If camera pose, head pose, or expression estimates are wrong, the canonical registration step will place evidence in the wrong 3D region, which then contaminates later fusion.
Coverage is too narrow. A few nearly identical frontal frames cannot recover hidden regions such as the sides of the head, so the avatar will stay uncertain there even if the feedforward prediction is fast.
Landmark tracking drifts over time. Incremental fusion depends on stable correspondence. If tracked landmarks slide across facial parts, new Gaussian pieces will be attached to the wrong places and the model will accumulate duplicate or blurred structure.
Done right. The method is strongest when the guidance signals are reliable and the incoming observations add new viewpoints or expressions that reveal missing 3D evidence.
What a runnable demo should prove

What a runnable demo should prove

Use a short face video and a sparse photo set from the same subject. Run the model first on one image, then on five views, then on the full video prefix. After each stage, render the avatar from held-out viewpoints and measure view error. Also track how much extra wall-clock time each added observation batch costs.

The demo should expose the actual claim of the paper: added observations should improve reconstruction because they contribute new registered Gaussian evidence, while the added computation should stay far below a full refit from scratch.

incremental_gain = held_out_error_before - held_out_error_after

A convincing demo shows both curves at once: view error drops as more observations arrive, and extra update time grows slowly because the method fuses into an existing canonical avatar.
