Detecting When Models Are Wrong or Biased

Papers measure model uncertainty, robustness to tricky inputs, and hidden biases — catching cases where models confidently give wrong answers or fail on edge cases.

All themesField mapMathematicsAll explainers
What this is

A model can be confident and completely wrong. It might tell you a dog is a cat with 99% certainty. It might give different answers to the same question asked in different ways, even though any human would recognize they are the same. It might refuse to help a person with one name but help happily when the name changes, because it absorbed preferences from training data where one group was treated differently than another. This subtheme is about building tests that catch these failures: model uncertainty, inconsistency, what happens when you trick the model with small changes, and biases the model's creators never noticed.

Why is detecting wrongness hard? Because a model's internal confidence score (how sure it says it is) often has almost nothing to do with whether it is actually right. A model trained on biased data might genuinely believe something false. If you only test a model on clean, normal inputs, you might miss that it breaks on edge cases—unusual spellings, dialogs with strange background assumptions, images with weird lighting. And bias is sneaky: a model might behave identically on similar inputs except that one involves a person of a particular group, revealing invisible discrimination that no human explicitly programmed in. Researchers need tests that can catch these hidden problems before deployment to the real world.

Researchers build benchmarks to catch these problems in multiple ways. Some create stress tests: adversarial examples designed to fool the model, or tricky rewording of the same question to see if the model contradicts itself. Others gather data specifically about domains where bias is known to be a problem—hiring, criminal justice—and measure whether the model treats everyone fairly. Still others build datasets to test a model's calibration: is it right more often when it is confident, and wrong when it is uncertain? By running these tests before deployment, researchers can find and sometimes fix problems before the model is released into the world.

How the work breaks down

Researchers test models to catch hidden failures in five main directions. First, does a model stay confident when it is actually wrong, or does it admit uncertainty? Second, how does a model respond when someone tries to trick it with adversarial inputs or attacks? Third, does a model handle complex multi-step reasoning, or does it collapse when tasks get compositional? Fourth, does a model absorb hidden biases from its training data that nobody explicitly programmed? Fifth, does a model give consistent answers to logically equivalent questions, or does it contradict itself? This subtheme builds benchmarks and evaluation methods to expose these problems before deployment.

Uncertainty and confidence mismatch

A model can say it is 99% certain and be completely wrong. The core problem is that the confidence scores a model produces internally have almost nothing to do with whether its answer is actually correct. This matters enormously: if you ship a system that sounds confident but is secretly unreliable, users trust wrong answers.

The AutoMetrics paper builds automatic evaluators that predict human judgments more accurately than just asking the LLM directly. By training on fewer than 100 human preference examples, it improves correlation with human ratings by up to 33.4% over naive LLM-as-a-Judge baselines. This works because the evaluator learns the actual relationship between what the model outputs and what humans think is good, rather than relying on the model's own confidence.

The Addressing Pitfalls in Uncertainty Estimation paper identifies a critical flaw: most papers test uncertainty estimation on just one judge and one benchmark. By testing across multiple judges and evaluation settings, they show how fragile these methods are—uncertainty estimates that looked reliable break when conditions change slightly. This matters because in the real world, you do not get to control the judge.

Expanding the AI Evaluation Toolbox applies statistical modeling to understand where uncertainty comes from. It decomposes the variance in model performance across 22 frontier LLMs, revealing that some uncertainty comes from the problem itself, some from the model's inherent inconsistency, and some from random noise. Understanding these sources helps calibrate when a model is genuinely uncertain versus when it is just noisy, because you can separate signal from noise and focus on fixing the sources you can control.

OpenEstimate tackles probabilistic estimation: when you ask a model to estimate a quantity like "how many people live in Tokyo," the model can express uncertainty by giving a range. By starting with LLM-elicited priors (prior beliefs, what the model already thinks before seeing new data) instead of naive assumptions, the final estimate is more accurate. The reason is that models have already absorbed ground-truth information from training; starting with that knowledge makes the final answer better.

Adversarial attacks and failure modes

A model might fail spectacularly when someone deliberately tries to trick it. This happens through adversarial examples (small, crafted perturbations to inputs) or domain-specific attacks designed to exploit what the model learned wrong. The problem is hard because the attacks can be subtle—a small change in lighting, a typo, a single-word rewording—yet the model confidently gives a completely different answer.

ExpGuard tests content moderation in specialized domains like medicine, law, and finance. It finds that generic content-moderation tools fail badly on domain-specific jailbreaks; attackers who know the field can craft prompts that slip past safeguards. By explicitly training on domain-specific adversarial attacks, ExpGuard beats prior art by up to 15.3%. This shows that defenses cannot transfer between domains—you have to test on the actual threats in your specific field.

VPI-Bench tests computer-use agents by injecting adversarial visual elements into web pages and desktop screenshots. Current agents get deceived 51% of the time on some platforms and 100% on others, even when existing defenses are in place. This matters because if a model controls your computer, visual manipulation becomes a major security hole. The paper shows that current defenses offer only limited protection.

MVI-Bench evaluates leading vision-language models on misleading visual inputs. When researchers add noise, blur, contradictory elements, or context mismatch, top LVLMs show pronounced vulnerabilities. This is critical because vision models are deployed in medical imaging, autonomous driving, and surveillance—domains where a tricked model can cause real harm.

The paper on rubric sensitivity tests whether benchmark scores stay stable when you perturb the problem statements slightly. It finds that popular benchmarks have systematic vulnerabilities: tiny changes in wording can flip which model ranks first. This reveals that benchmark scores themselves are unreliable if the problem formulations are fragile. It establishes that any credible benchmark must survive perturbation testing.

Compositional reasoning and multi-step breakdowns

A model might solve simple one-step problems perfectly but fail when tasks get compositional—when you combine multiple skills or chain multiple steps. This happens because the model learned to handle each piece in isolation but never learned how the pieces fit together. It is like building a wall brick by brick: the model can place single bricks fine but does not understand structural stability.

LLMs Get Lost In Multi-Turn Conversation shows that all tested frontier LLMs drop 39% in performance average on multi-turn conversations. The researchers discovered that when a model takes a wrong turn early in the conversation, it gets stuck and cannot recover. It fails to re-read what it said earlier, does not backtrack when evidence contradicts it, and just keeps going forward into more mistakes.

Local Success Does Not Compose exposes a 92% gap between single-function correctness and compositional correctness. Code syntax stays above 99% on single functions but drops to 95.67% when functions interact. Verification of composed code crashes to 3.69% success. The reason is that the model never learned to reason about how state flows between functions and whether one function's output will be valid input to the next.

Evaluating Stability of Reasoning Models tests whether reasoning models stay stable under targeted structural interventions. For example, changing the parity of numbers or the depth of a logic tree should not affect whether the model understands the underlying reasoning pattern. The paper discovers sharp performance transitions and brittleness: the model learns surface statistics rather than the underlying logic, so small structural shifts cause collapse.

UniCode augments code reasoning by creating new test cases with systematic structural variations. When models face code problems with different control-flow patterns, 31.2% of models collapse. Some models show seed-problem regression: they memorize specific solutions and fail when the problem structure shifts even slightly. This reveals fragility rather than genuine reasoning.

Bias detection and fairness testing

A model might treat people differently based on their identity without anyone explicitly programming that behavior. This hidden discrimination comes from training data. If the data contains more positive examples of one group than another, the model absorbs those skewed statistics and encodes them as learned patterns. The challenge is that these biases are invisible: the model treats them as facts, not preferences, so humans overlooking them see only confident decisions.

Cancer-Myth evaluates how LLMs handle questions with false presuppositions in healthcare. The scenario: a patient asks a question based on medical misinformation. A safe model should correct the false belief, but no frontier LLM does this more than 43% of the time. The reason is that LLMs learn to predict likely continuations of text; if the training data contained many instances of the false belief, the model learned to treat it as plausible. Fixing this requires explicit training on presupposition-correction tasks.

JALMBench benchmarks jailbreak vulnerabilities in audio language models. It discovers that safety strongly depends on modality and architecture. Text-based safety training partially transfers to audio, but there are domain-specific vulnerabilities in audio space—attackers can craft audio prompts that bypass safeguards. Audio biases differ from text biases because the model processes acoustic patterns differently than words.

Take Note reveals a hidden bias in molecular datasets. Commonly used datasets like QM9 and QMugs contain systematic orientational bias: molecules are aligned in the same 3D orientation across most samples. Neural networks exploit this bias instead of learning true chemical properties. This is hidden because the bias is not intentional; it comes from how the data was collected. Models trained on this data look good in benchmarks but fail in the real world where molecules have arbitrary orientations.

Teaching VLMs to Admit Uncertainty in OCR tests vision-language models on blurry and distorted text. A good model should say "I cannot read this" rather than guessing wrong. The paper trains models to output uncertainty tags when the input is too degraded. This matters because biased data often contains low-quality examples from certain groups, and models trained to guess anyway will make systematically wrong predictions for those groups.

Evaluation methodology and ranking stability

Benchmark scores and model rankings can be fragile. If you change a tiny piece of the evaluation setup—the judge, the phrasing of the question, the test set—the rankings completely flip. This is a meta-problem: you cannot trust a benchmark that is this unstable. Researchers need to understand how sensitive their conclusions are before they claim one model is better than another, so that their rankings rest on stable ground rather than on fragile construction choices that could change at any moment.

Dropping Just a Handful of Preferences shows that model rankings on Chatbot Arena are remarkably sensitive. Removing just 0.003% of human preferences (a handful of judgments) can change which model ranks first. This means the entire leaderboard is built on an unstable foundation. Tiny changes in the data collection process or which judges vote could completely reshuffle the rankings.

The Temporal Databases paper addresses time-sensitive question-answering. Most benchmarks test whether a model gives the right answer, but they ignore whether the model explains its reasoning correctly when time is involved. For example, "Who won the 2020 election?" has one answer now, but in 2021 the answer was different. The paper enables automated evaluation of how well models handle temporal reasoning at scale, reducing human labor while revealing whether the model actually understands time or just got lucky, which matters because temporal reasoning is easy to fake through luck but hard to do correctly.

Benchmarking at the Edge of Comprehension tests frontier LLMs on mathematical proofs where humans might not understand the full solution. Prior benchmarks require human judges to verify each answer, which is expensive. The paper shows that numerical scores on mathematical benchmarks correlate with external data (like researcher consensus) even without full human comprehension. This matters because it enables scaling evaluation to much larger problem sets.

Faults in Our Formal Benchmarking catalogs dataset defects in formal mathematics benchmarks. Some problems have multiple correct answers; some have ambiguous specifications; some have been solved by prior work but not removed. These flaws make it impossible to trust evaluation results. The paper provides automated checkers and proposes standards for creating formal math datasets that do not have these problems, releasing corrected snapshots.

SpotIt evaluates Text-to-SQL systems by checking whether the generated SQL query actually means the same thing as the ground-truth query. Test-based methods overlook semantic differences: a query might produce the same rows but compute them differently. By using formal verification, the paper reveals gaps in current Text-to-SQL evaluation that traditional test suites missed, showing that system rankings are less reliable than they appeared.
