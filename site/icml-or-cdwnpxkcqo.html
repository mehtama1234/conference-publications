EvoMAS: Heuristics in the Loop—Evolving Smarter Agentic Workflows

A system that evolves multi-agent teams by mixing six biological strategies with a meta-controller that learns which strategies to apply when.

Paper explainersAll themesAgents & Tool Use

Building a smart team of AI agents usually means hand-crafting each agent's role and having them work in a fixed way. EvoMAS is a framework that evolves these teams automatically. Instead of one rigid design, it keeps a dynamic set of six proven strategies (three for exploring new ideas, three for refining good ones) plus one customized operator. A meta-controller watches what works and learns to pick the right strategy for each task, so the same system can handle easy problems and hard ones without manual redesign.

Zero assumption version

Hand-built teams are brittle and expensive

Building a multi-agent system (a team of AI agents working together) is hard labor. You design one agent for role A, another for role B, then try to get them to cooperate. When the task changes—easier or harder—you rebuild from scratch. Current automation tools are worse: they stamp out identical cookie-cutter agents or optimize everything at once with no sense of whether a task is simple or complex.

A beginner would try: design one strategy, apply it everywhere. This fails because the moves that work on a simple task (like classifying one email) waste compute on a hard task (like planning a multi-step project), and vice versa. There is no learning loop: once you build a team, it stays fixed.

The paper's move in one sentence. EvoMAS evolves agent teams using an adaptive mix of six proven strategies, guided by a meta-controller that learns which strategy fits each task.

The algorithm as a flow

What it actually does

Start with six proven moves

Three explore (randomize agent roles, swap goal priority, inject noise), three refine (nudge weights gently, cross-breed two good teams, prune weak agents).

Watch the meta-controller observe

As each task runs, track which strategy produces the best agents. Learn a map from task properties to the best strategy.

Curriculum: start simple, go hard

Easy tasks first (so the learner sees clear winners), then gradually step up to complex tasks; each stage shares stability from the last.

Agents specialize over time

Early on, all agents are generic. Over generations, some become reasoning specialists, others become tool-callers, others become coordinators.

Stop when good enough

The system halts when the team wins on the hard tasks and cost stays low.

What the paper changes

What the paper changes

The paper evolves two things at once: the internal weights and structure of each agent, and the roles those agents play in the team. It also learns which of the six strategies to apply at each step, so the evolution process itself becomes adaptive.

the object it moves  =  agent weights, roles, strategy selection
The hidden quantity

The hidden quantity: strategy fit

measured quantity  =  strategy fit score

Strategy fit is a number measuring how well a particular strategy works for a particular task. It is hidden because you do not see it directly—only the quality of agents the strategy produces. The paper estimates it by running each strategy, measuring the resulting team's score (how well it solves the task), and recording that as the strategy's fit.

The meta-controller uses fit scores to learn a rule: if the task has these properties, pick this strategy. Over time, it builds a memory of which strategy wins in which situation. This saves time because instead of running all six strategies to find the winner, the controller can jump straight to the one that historically worked best on similar tasks.

Why it works

Why mixing six strategies beats one rigid choice

Evolution works by trying many mutations and keeping the ones that improve fitness (like natural selection). Six strategies give six different kinds of mutations: some shake up the structure (exploration), others polish the details (refinement). Applying all six at once, then picking the best offspring, is faster than picking one strategy, because you are guaranteed to try the move that actually works best on this task. If you pick only one strategy blindly, you might choose the wrong one and waste generations before trying the move that would succeed.

The meta-controller is the new piece: it watches which strategy succeeded most often on recent tasks and learns to bias toward that strategy next time. This is not magic—it is a simple feedback loop. If exploration just found a new agent type that solves hard tasks, the controller starts using exploration more. If refinement is stuck, the controller tries exploration. This adaptive mixing converges faster because you are automatically steering toward the strategy that currently works, rather than wasting generations on a fixed choice you made at the start. Random search has to try everything equally; one-fixed-strategy wastes effort on the wrong move. But the meta-controller remembers what worked and focuses on it, avoiding both mistakes.

Curriculum learning adds a third layer: start on easy tasks (so the learner can see clear wins and build confidence), then gradually add harder tasks. Each stage passes its best-found agents to the next stage, so nothing is lost—evolution continues from a good starting point rather than restarting from scratch.

The fitness and strategy-selection formula

First in words:

Each strategy produces mutated agents. The team's fitness is the task score. The meta-controller learns a probability for each strategy via bandit learning: strategy probability increases with its recent fitness history.

Then the compact form:

fitness_s = average(task_score | strategy_s applied), prob_s = prob_s + alpha * (fitness_s - baseline), next_strategy = sample(prob_s)

Every symbol:

fitness_saverage score of teams produced by strategy s over recent tasks
task_scorehow well this team solves the current task (0 to 100 for easy, 0 to 10 for hard)
strategy_sone of the six strategies (explore-1, explore-2, explore-3, refine-1, refine-2, refine-3)
prob_slearned probability of picking strategy s
alphalearning rate; how fast probabilities adapt (e.g. 0.1)
baselineaverage fitness across all strategies; subtracting it centers the update
A tiny worked example
Suppose on task 1 (easy) we try all six strategies once each.
Explore-2 produces agents scoring 85 (the best).
Refine-1 and refine-3 each score 70.
The others score 55.
Baseline = (85+70+70+55+55+55) / 6 = 65.
Strategy explore-2: fitness = 85, update = 85 - 65 = 20.
New prob for explore-2 grows by 0.1 * 20 = 2 points.
Next task, we bias toward explore-2, but still try others occasionally.
On task 2 (harder), explore-2 only scores 60, refine-3 scores 80.
Baseline = 70. Refine-3 update = 80 - 70 = 10, grows; explore-2 shrinks.
Over many tasks, the controller learns: easy tasks like exploration, hard tasks like refinement.

The meta-controller does not change the strategies themselves; it only learns which one to pick and when, using only task outcomes as feedback.

What can go wrong

What can go wrong

Meta-controller overfits to early tasks. If the first few tasks are not representative, the learner locks into the wrong strategy. Curriculum learning mitigates this by ensuring a diversity of task difficulties from the start.
Six strategies might not cover the space. If the real best strategy is a combination not in the six, evolution gets stuck. The custom domain-specific operator is meant to fill gaps, but only if the designer knows what to add.
Evolution is still slow on very hard tasks. Even with six strategies, finding good agent teams on tasks with long horizons or rare successes takes many generations. The paper does not discuss scaling to extreme complexity.
Done right. Run curriculum learning so the controller sees a range of difficulties, include domain-specific operators tuned to your problem class, and monitor that the learner generalizes to new task types beyond training.
What a runnable demo should prove

What a runnable demo should prove

Build a simple multi-task environment (e.g. five tool-use tasks of increasing hardness: find object, combine tools, plan a sequence, solve with constraints, multi-step reasoning). Start with three candidate strategies (one exploration, one refinement, one domain-specific) to keep it fast. Run the meta-controller to see it learn which strategy to use on each task. Measure both the quality (agent team score on each task) and the cost (compute spent per strategy). The demo should show that the meta-controller's learned strategy choices beat a fixed choice (e.g. always use one strategy) and beat random selection.

demo_score = average(task_quality_easy, task_quality_hard), cost_per_task = total_compute / num_tasks, advantage_over_fixed = demo_score - fixed_score

The meta-controller should specialize: early tasks get the fast strategy, later tasks get the one that actually solves them. If all tasks use the same strategy, the controller is not learning.
