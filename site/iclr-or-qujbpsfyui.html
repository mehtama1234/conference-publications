Global Temporal Retriever for Time Series Forecasting

GTR retrieves patterns from a learned global cycle memory and fuses them with today's data to predict what comes next, without changing your existing forecaster.

Paper explainersAll themesTime Series & Sequential

Time series forecasting (predicting tomorrow's values from today's numbers) breaks when patterns repeat over very long cycles. If you only look at the last two weeks to predict next week, you miss signals that repeat monthly or yearly. This paper introduces GTR, a lightweight add-on module that learns a memory of the entire repeating cycle, retrieves the part that matches right now, and blends it with the immediate past—all without rebuilding your forecaster.

Predicting long cycles with a short window

Real-world time series (electricity demand, sensor data, stock prices) often repeat on patterns that are much longer than the recent past. Electricity usage might repeat weekly or yearly, but if your model only sees the last 7 days, it misses the yearly pattern. Extending the lookback window helps, but it breaks everything: the model overfits to noise in all that extra history, training becomes prohibitively slow because processing all that data takes forever, and most of that extra history is just repetitive junk anyway.

A naive approach is to stretch the input window backward to capture long cycles. This fails because noise in months of history drowns out real patterns, and the computational cost explodes—your model has to chew through terabytes of irrelevant data just to find the one-year-ago pattern that looked like today.

The problem in one sentence. Standard forecasters cannot see long repeating patterns without either overfitting to noise or becoming prohibitively slow.

The algorithm as a flow

What it actually does

Learn a cycle memory

GTR maintains one learned embedding (a list of numbers) that encodes the entire repeating cycle.

Find today's place

For each forecast, the model figures out where today falls in that cycle using absolute time indexing.

Grab the matching segment

GTR retrieves the part of the cycle memory that corresponds to today's position.

Stack and convolve

The recent data and retrieved segment are stacked into a 2D grid and processed together with a small convolution (a sliding window of operations).

Fuse back in

The enriched representation (local plus global) is fed back into the forecaster via a residual connection, adding the new signal without erasing what the backbone already learned.

What the paper changes

What changes

GTR changes the way the forecaster receives information: instead of just the immediate recent data, the model now has access to a learned retrieval of long-term cycle patterns, without any change to the forecaster's internal structure.

The hidden quantity

The hidden quantity: Cycle Position Embedding

measured quantity  =  Cycle position (where today falls in the global repeat)

The paper introduces a hidden quantity: your position within the repeating cycle. This is not something you directly observe in raw data—it is inferred from the absolute time index (e.g., day 47 of a 365-day year). The model learns an embedding (a list of numbers representing each position) that encodes patterns at that point in the cycle. By knowing your position, GTR can pinpoint exactly which slice of the global memory is relevant right now.

GTR estimates this using absolute temporal indexing: it maps the input sequence's timestamp to a position within the learned global cycle, then retrieves the corresponding segment from the adaptive global embedding. This is a direct, deterministic lookup—no attention or search, just 'give me position 47'.

Why it works

Why it works: The retrieval-fusion loop

The core insight is that long repeating patterns are predictable if you know your position in the cycle. A busy restaurant at 6 p.m. Monday looks like 6 p.m. Monday from every week; an airport gate at dawn during peak travel season looks the same every year. GTR learns one global representation of what the entire cycle looks like. When you ask 'what next?', it does not stretch backward through months of history—instead, it instantly retrieves the signal from the exact matching point in its learned cycle.

The 2D convolution step is the decision point: it does not just concatenate the recent data and the old cycle data (which would confuse the model). Instead, it treats them as two channels of a 2D image and runs a small sliding window over both at once. This teaches the model how recent-past and cycle patterns interact—when they agree (both pointing upward), the signal is strong; when they clash (recent down, cycle up), the model learns to handle the conflict.

The residual connection ensures the forecaster backbone is never blindsided. The enriched signal is added to (not replacing) the original features, because addition allows the downstream layers to weight the cycle contribution—they can learn to use it heavily on typical days and turn it off when today breaks the pattern, giving the model the flexibility to ignore bad cycle advice on anomalies.

Math after the picture

The equation

First in words:

For each variable n in the series, the model retrieves the cycle segment q_n at the absolute position and fuses it with the current observation x_n through a 2D convolution. The output h_n is then added back to the input via residual connection to produce the final feature z_n.

Then the compact form:

z_n = x_n + Conv2D(stack(x_n, q_n)) where q_n = Q[position_index]

Every symbol:

x_ncurrent observation for variable n (e.g., today's temperature)
q_nretrieved cycle segment for variable n at this position
Q[position_index]lookup in the global cycle embedding at the computed position
stack(x_n, q_n)arrange x_n and q_n as a 2D grid (two channels)
Conv2D(...)apply a small convolution kernel to the 2D grid
z_nfinal enriched feature for variable n
+residual connection: add the convolution output to the original x_n
A tiny worked example
Suppose today is day 200 of a 365-day cycle. Position index = 200.
q_n = Q[200] is the learned pattern at day-200 in the global cycle (e.g., summer-like features).
x_n = 72 (today's temperature, a number).
stack(x_n, q_n) creates a 2-row grid: [72, ...other-numbers...] in row 1 (current), and [68, ...global-day-200-pattern...] in row 2 (cycle).
Conv2D applies a small filter (say 3x3) that looks at both rows at once, finding where they reinforce (both high = strong signal, multiply them) or conflict (opposite directions = the model learns to weight carefully).
Suppose Conv2D output is 5.3 (a fused score).
z_n = x_n + 5.3 = 72 + 5.3 = 77.3 (enriched feature combines today's real value with the cycle signal).
The forecaster backbone now sees 77.3 instead of just 72, having learned the summer context invisibly.

The residual connection (+) ensures GTR acts as a lightweight add-on: the backbone can ignore the cycle cue if today is truly anomalous, or amplify it when patterns align.

What can go wrong

What can go wrong

Broken periodicity. If the true cycle is not perfectly regular (e.g., February is short, holidays shift the rhythm), GTR's fixed absolute indexing misses anomalies. A leap year or a supply-chain shock breaks the alignment.
Multi-cycle data. If your data has both daily and yearly cycles that do not align (e.g., traffic peaks at rush hour every day, but also peaks on holidays), GTR's single global embedding cannot hold both patterns. You either sacrifice one or learn a hybrid that is weaker for both.
Concept drift. If the data distribution shifts over time (demand changes due to new competitors or regulations), the cycle learned from old history is stale. GTR will retrieve yesterday's outdated pattern and mislead the forecaster.
Done right. GTR works best on stable, regularly sampled data with clear periodicity, like power consumption, water usage, and seasonal retail sales. Pair it with a forecaster that can adapt when outliers appear, and monitor for long-term drift in the cycle itself.
What a runnable demo should prove

What a runnable demo should prove

Build a synthetic time series with a strong yearly cycle (e.g., 52-week repeats of a sine wave with some daily noise). Split into train and test. Train a simple baseline forecaster (e.g., a 2-layer MLP) on recent windows without GTR. Then wrap the same MLP with GTR and retrain. On a test set that includes forecasts during summer (weeks 25–30) and winter (weeks 1–4), show that GTR's forecast error on out-of-sample summer and winter weeks drops by at least 20 percent—the model learned that summer and winter have different baselines, retrieved from the global cycle memory, not from recent history.

improvement = (baseline_RMSE - GTR_RMSE) / baseline_RMSE, where RMSE is root-mean-squared error on hold-out weeks in the seasonal parts of the cycle

The demo must make it impossible to miss: GTR lets a simple forecaster 'remember' and reuse patterns from the same season last year, without the model having to memorize an enormous lookback window.
