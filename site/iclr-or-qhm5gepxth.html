RF-DETR: Neural Architecture Search for Real-Time Detection

Train a single detector once, then find thousands of differently-sized versions of it without retraining by measuring each architecture's accuracy and speed.

Paper explainersAll themesComputer Vision

A detector is a machine that marks objects in images. Today's detectors are either fast but sloppy or slow and precise — pick one. RF-DETR finds a hidden currency: thousands of differently-shaped detectors all trained from a single run, each tuned to a different speed-accuracy tradeoff. The trick is sharing weights intelligently, so you evaluate new architectures instantly instead of retraining each one from scratch.

Zero assumption version

Speed and accuracy: always a tradeoff

A detector must identify every object in an image: car, person, bicycle. But detectors are expensive — they crunch lots of numbers. So engineers face a hard choice: make the detector small and fast but miss things, or make it big and slow but accurate.

Today, you pick one shape and live with it. Want a faster version? You must retrain from scratch, because the weights were optimized for a single size and speed target — changing the architecture breaks the learned patterns. If you need even faster results (say, your device is slower), you start a new training cycle with a smaller detector, since smaller networks run faster because they crunch fewer numbers. Each new speed target means full retraining — weeks of computation per variant.

The naive approach: just shrink the detector. But that breaks it — a tiny detector misses half the cars and bicycles.

The real need. Train once. Find many detector shapes, each optimized for a different speed, without retraining.

The algorithm as a flow

What it actually does

Train once with architecture augmentation

Train a shared backbone on the target dataset; during training, randomly sample different architecture choices (decoder depth, image size, patch granularity).

Search the trained network

After training, measure every possible architecture configuration: which decoder layers to keep, which patch size, how many queries. Each configuration inherits the shared weights.

Measure speed and accuracy for each

Run each architecture on the test set once; record how fast it runs and how many objects it finds correctly.

Find the Pareto curve

Plot speed versus accuracy; keep only the architectures that are not beaten on both dimensions.

Pick the sweet spot

Engineer picks the detector from the curve that matches their hardware latency budget.

What the paper changes

What changes: the architecture path, not the weights

The paper keeps the trained weights fixed. What it changes is which weights get used: which decoder layers activate, what patch size the input is divided into, how many queries the detector sends. Think of it as cutting different paths through a single trained network.

The hidden quantity

The hidden quantity: Pareto optimality

measured quantity  =  Pareto frontier (non-dominated architectures)

Pareto optimality names the set of unbeaten options. One detector beats another if it is faster AND more accurate than the other, making the other pointless to use. For example, if detector X runs in 20 milliseconds and finds 50% of objects, while detector Y runs in 30 milliseconds and finds 52%, then X beats Y because you get nearly as many correct detections in half the time — no engineer would choose Y. An architecture is Pareto-optimal if no other architecture beats it this way (no detector is both faster and more accurate), so it represents a genuine option someone might rationally pick.

RF-DETR measures this frontier. It runs all thousands of candidate architectures and records their latency (milliseconds to process one image) and accuracy (percentage of objects found correctly). Then it removes any architecture that another architecture dominates — if architecture A is both 10% faster and 2% more accurate than architecture B, then B is dominated and removed because A is strictly better on every dimension that matters. What remains is the Pareto curve: the set of undominated architectures. Each one is a genuine option; moving from one to another on the frontier means trading speed for accuracy or vice versa.

Why it works

Why it works: weight-sharing breaks the retraining barrier

Normally, each new architecture requires full retraining: optimize all weights from scratch for weeks. RF-DETR escapes this trap by sharing weights. Train the backbone once on the target dataset while randomly sampling different architectural choices during training — this exposes the weights to many possible paths through the network. After training finishes, the weights are already optimized for hundreds of architectural variants because they have seen all those variants during training.

When you cut a new path through the trained network (using fewer decoder layers, a coarser patch size, fewer queries), the weights on that path have already been optimized by the training process, because the sampler happened to choose that path during training. The shared weights act like a pre-optimized library: you inherit the knowledge for free. This is why evaluation is instant — you just run the new architecture once and measure it; you never retrain.

Math after the picture

Pareto optimality in one formula

First in words:

Architecture A dominates B if: speed_A >= speed_B AND accuracy_A > accuracy_B (A is at least as fast and strictly more accurate). The Pareto frontier is the set of all architectures not dominated by any other.

Then the compact form:

frontier = {A : not exists B such that speed_B >= speed_A AND accuracy_B > accuracy_A}

Every symbol:

A, Btwo different architecture configurations
speed_Alatency of architecture A in milliseconds
accuracy_Adetection accuracy of architecture A in percentage correct
frontierthe set of unbeaten configurations
A tiny worked example
Architecture Nano: 10 ms latency, 40% accuracy.
Architecture Small: 20 ms latency, 45% accuracy.
Architecture Medium: 30 ms latency, 50% accuracy.
Nano vs Small: Small is slower (20 > 10) AND more accurate (45 > 40); Nano is dominated, remove it.
Small vs Medium: Medium is slower (30 > 20) AND more accurate (50 > 45); Small is dominated, remove it.
Frontier = {Small, Medium}. Both stay because neither beats the other on both dimensions.
If an Ultra architecture ran at 25 ms with 52% accuracy, it would dominate Medium (faster, more accurate), so Medium would be removed and Ultra would join the frontier.

The frontier is the only architectures a rational engineer would choose; all others are dominated by something better.

What can go wrong

What can go wrong

An unseen architecture path might be worse than expected. During training, the sampler might not visit a particular combination of choices (e.g., all shortest paths through all decoder layers). If a new architecture uses that path, its weights may not be well-optimized. The paper notes this happens rarely, and some Pareto paths work well even unseen, but it is still a failure mode.
Batch normalization breaks under weight-sharing. Batch norm computes statistics per training batch. When evaluating different architectures in sequence, batch statistics change between runs. The paper switched to layer norm (normalize within each unit) to fix this, but layer norm hurts a little.
Latency measurement depends on the exact hardware. A Pareto frontier built for NVIDIA GPUs might not hold on CPU or on a phone's neural-accelerator. Speed measurements are platform-specific; porting a frontier to new hardware requires re-measurement.
Done right: Pareto frontier holds and transfers. When architecture augmentation during training hits all major paths, and latency is measured on the target device, the frontier is stable and the detection time is predictable.
What a runnable demo should prove

What a runnable demo should prove

Build a simple object-detector backbone (a small transformer or CNN) and implement weight-sharing: during training, randomly sample different depths (number of layers), widths (channels per layer), and input resolutions. After training, iterate through all combinations, measure accuracy on a test set and infer latency. Plot the Pareto frontier on a speed-accuracy graph. The demo should show that without retraining, dozens of sub-networks inherit good performance because they all went through the random-sampling training.

Pareto frontier size = count of architectures not dominated by any other on {accuracy, latency}

The irreducible fact: one training run produces hundreds of deployment-ready detectors, each optimized for a different speed target.
