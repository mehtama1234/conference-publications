RF-DETR: Neural Architecture Search for Real-Time Detection Transformers

RF-DETR finds the best detector design for any new dataset by testing thousands of network shapes with shared weights, without retraining each one.

Paper explainersAll themesComputer Vision

When you want a fast object detector that works on your specific dataset, you face a hard choice: use a heavy general-purpose model that works but runs slowly, or spend weeks fine-tuning a different design. RF-DETR automates this. It starts with a trained detector model, then efficiently tests thousands of different network designs to find the best speed-accuracy tradeoff for your data, using a trick called weight-sharing so it never has to fully retrain.

Zero assumption version

Why finding the right detector is slow

Today, fast object detectors (models that spot and name things in images) work well on standard test datasets like COCO, but fail when you point them at your own data. Real-world images often have objects that were rare or missing in the detector's training data. A naive solution: take the trained detector and fine-tune it on your new data. This works, but it is slow. A faster option: design a smaller network by hand because smaller networks process images faster, and train it from scratch. But which design? Should you use fewer layers, smaller patch sizes, fewer heads in the attention layers (where the model looks at different parts of the image at once)? You have to guess, build it, train it (which takes hours of GPU work), measure it, then try again, and you get only one answer per guess.

The real pain: testing each new network design requires full retraining from scratch. If you want to try 1000 different designs, you need 1000 full training runs. That is weeks of GPU time.

The problem in one sentence. Finding which network design works best on your data forces you to fully retrain each design from scratch.

The algorithm as a flow

What it actually does

Start with a trained base model

Take a detector that already works on a source dataset like COCO.

Fine-tune once on your new dataset

Train the base model on your target data for a few epochs, updating the shared weight foundation.

Define all the design choices

Decide which parts can vary: number of layers, number of attention heads, patch sizes, depth of the backbone.

Score each design without retraining

For each of the thousands of network shapes, feed images through the network and measure accuracy and speed using only the shared weights.

Extract the Pareto curve

Plot accuracy versus latency for all designs and pick the one that matches your constraints.

What the paper changes

What changes: the network shape

The paper does not change the trained weights themselves. Instead, it changes which weights each design uses and how they connect. Think of it like a modular toolkit: the base model is a library of trained components, and each candidate design is a different recipe that picks different subsets and connects them in different orders.

the object it moves  =  network topology and component selection
The hidden quantity

The hidden quantity: efficiency of the shared weight foundation

measured quantity  =  how well shared weights transfer to new designs

The paper's core bet is that a single set of trained weights can support many different network designs. If the weights are good, then any design built from them will be reasonably accurate without full retraining. The paper measures this by checking: when you take a shared weight foundation and plug it into 1000 different network shapes, how accurately can each shape work? The paper calls this the quality of the weight-sharing initialization.

Concretely: after fine-tuning the base model on your target data, the paper evaluates each candidate design by running it forward (inference) and measuring accuracy and latency, without any backward passes (gradient updates). This works only if the shared weights are good enough to support varied designs.

Why it works

Why it works: shared weights avoid retraining

A well-trained network contains useful learned patterns. If you take those weights and use them in a different network shape, most designs will still work reasonably well because the underlying patterns (how to detect edges, shapes, objects) are still there. You do not need to retrain from scratch because the patterns were learned on similar data (the source dataset) and only need to be re-calibrated for your target.

Weight-sharing is efficient because inference is cheap: you run the forward pass (feeding an image through the network) and measure accuracy and speed without any expensive backward passes (gradient updates). This lets you test thousands of designs in the time it would take to fully train even one.

The tunable knobs the paper revisits are the architectural choices that matter most: number of attention heads (do you want 8 heads or 16?), layer depth (skip early layers or keep them?), and decoder design (how big is the final detection head?). By systematically testing these choices, the paper finds that different datasets prefer different tradeoffs. A dataset with small objects benefits from keeping all the layers. A dataset with large objects can skip some.

The scoring equation

First in words:

For each design candidate, measure accuracy by forward-passing examples through the network and comparing predictions to ground truth. Measure latency as wall-clock time per image. Plot accuracy versus latency and extract the Pareto frontier (designs where improving accuracy requires accepting slower speed).

Then the compact form:

design_score(D) = accuracy(D) - latency_penalty * latency(D)

Every symbol:

design_score(D)a composite score for design D that balances accuracy and speed
accuracy(D)fraction of objects correctly detected with design D
latency(D)milliseconds to run one image through design D
latency_penaltyweight controlling how much to penalize slowness; tuned per application
A tiny worked example with two designs
Design A: accuracy=45% (0.45), latency=80ms. With latency_penalty=0.001: score = 0.45 - 0.001*80 = 0.45 - 0.08 = 0.37.
Design B: accuracy=40% (0.40), latency=40ms. With latency_penalty=0.001: score = 0.40 - 0.001*40 = 0.40 - 0.04 = 0.36.
Design A is 5% more accurate but 2x slower. If your app allows 80ms, pick A. If you need under 50ms, pick B. Both are on the Pareto frontier.

The paper does not commit to a single score formula; instead it computes accuracy and latency for every design and lets you choose which tradeoff suits your deployment.

What can go wrong

What can go wrong

The shared weights are stale. If the base model was trained on very different data (e.g. natural images, but your target is medical scans), the shared weights may not transfer well because they encode visual patterns that do not exist in medical data. Weight-sharing helps you test many designs, but if the fundamental patterns are wrong, no design will work well, because every design uses the same weight foundation that was tuned for the wrong kind of image. Solution: fine-tune the base model longer on your target data before running the search so the weights learn what medical images actually look like.
You search over the wrong design choices. If you decide to search over layer depth but not over the attention head dimension, you may miss the best designs. The paper contributes a revisit of which choices matter most, but this is dataset-dependent. Solution: pilot a small search to understand which design choices move your accuracy.
Inference speed does not predict training speed. A design that runs fast at inference may use a different computational pattern (e.g. many small operations) that trains slowly. The paper measures latency at inference time, which is correct for deployment but may mislead if you later want to fine-tune the chosen design on more data. Solution: measure both inference and training time for the final design.
Done right. The base model is fine-tuned on your target data, the architectural choices are well-chosen, inference latency is the metric you care about, and you systematically test thousands of designs to extract the full Pareto frontier.
What a runnable demo should prove

What a runnable demo should prove

Write a mini object detector on a small dataset (e.g., 100 images of 3 object types: cars, pedestrians, bikes). Download a small pre-trained detector (e.g., a tiny YOLO model or a small DETR). Implement 3 network design variants: one with 2 decoder layers, one with 4, one with 6. Fine-tune the base weights on your 100 images once, updating the shared pattern library. Then, without any further training, run all three variants on a held-out test set and measure accuracy and latency for each. Plot the tradeoff curve. The demo proves that the shared weights support multiple designs accurately because a single set of learned patterns can be wired together in different ways, and that inference is much faster than training because you only run the forward pass without computing gradients.

pareto_frontier_size = count of designs where no other design has both higher accuracy and lower latency

The demo must make it impossible to miss: the same weights, evaluated on 3 different network shapes, produce different accuracy-latency tradeoffs, and all evaluation happens in seconds, not hours.
