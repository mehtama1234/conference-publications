Long-range Modeling of Multimodal Event Sequences

A method that makes language models predict when events happen and what text describes them, using compression to handle long sequences without losing information.

Paper explainersAll themesTime Series & Sequential

Imagine a chat stream where each message arrives at a specific time and describes what happened. Predicting the next message timing and content together is hard because adding language to the model makes the sequence very long. This paper shows how to compress the sequence smartly—keeping events that are far apart in time and merging ones that arrive together—so the model learns the rhythm without being overwhelmed by the length because it sees fewer items to memorize, then fine-tuning adds the text details.

Zero assumption version

Long sequences break language models

When you predict events happening over time—like chat messages arriving or live comments on a video—you want to know three things: when the next event comes, what type it is, and what it says. Recent models can handle time and type. But adding language to the mix is expensive: each new token (each word) in the description doubles the memory the model needs.

A beginner tries this: throw everything in and let the model figure it out. It works until the sequence gets long. After a few hundred events, the model runs out of graphics-card memory and cannot think clearly about the whole story anymore. The patterns that would help it predict what happens next—the rhythm of events, the themes repeating—get buried in the noise, because the model's working memory is a limited bucket, and noise fills it faster than signal.

The problem in one sentence. Multimodal event models that generate text run out of memory on long sequences because each word doubles the load.

What the paper changes

What the paper changes

The paper replaces the standard 'feed everything in' approach with a two-stage recipe: pre-train on compressed sequences where nearby events are merged, then fine-tune on the real task. This keeps the model's working memory small enough to think about long time spans.

the object it moves  =  training recipe (compress, then fine-tune)
The hidden quantity

Temporal distance: which events matter

measured quantity  =  temporal distance between events

This is the gap in time between one event and the next—measured in the same units as the event timestamps. If two events happen 0.1 seconds apart, they have small distance; if one arrives now and another tomorrow, the distance is large.

The paper uses temporal distance to decide which events to compress together. Events with small distances (close in time) are grouped into a single token. Events with large distances (far apart) are kept separate, because that separation carries meaning about the rhythm and structure of what is happening. By estimating this distance for each pair, the model can tell which compressions will lose the least important information.

Plain reading. Think of temporal distance as the 'quiet time' between events. If there is a long quiet time, something different happened—the model needs to know that gap exists, because gaps are how patterns get marked off. If events come in a burst, the quiet time is tiny, so the model can treat them as one chunk, because bursts carry their meaning as bursts, not as individual tokens.
Paper reading. The paper calls this 'adaptive sequence compression based on temporal similarity.' It measures the time interval between events and uses it to choose which tokens to keep and which to merge, reducing total sequence length while preserving event-timing structure.
Why it works

Why compression then fine-tuning works

Here is the causal chain. When events come in bursts (like rapid-fire comments), merging them into one token cuts the sequence length dramatically without losing the information the model needs—the burst itself is the signal. Pre-training on these compressed sequences teaches the model the general rhythm and large-scale patterns. The model learns 'these events tend to cluster, then pause, then cluster again' without getting distracted by every individual token.

Fine-tuning on the real task then adds the specifics: 'now generate text for each individual event, predict its exact timing.' But because the model already grasps the big picture from compression, it can decode coherently even when the sequence gets long again. The model is not building context from scratch; it is refining patterns it already knows. This is why two-stage training outperforms single-stage: the pre-training phase acts like a sketch, and fine-tuning fills in the details.

Compression score and pre-training

First in words:

For each event, assign a score based on how far away the next event is. Keep events with large scores (far apart); merge events with small scores (close together). Then train the model to predict time and generate text on the compressed stream.

Then the compact form:

compressed_stream = [event_i for event_i in stream if distance(event_i, event_{i+1}) > threshold]

Every symbol:

event_ithe i-th event in the sequence (time, type, text)
distance(event_i, event_{i+1})the time gap between event i and the next event
thresholda cutoff; keep events where the next one is far away
compressed_streamthe shorter sequence fed to the pre-training phase
A tiny worked example
Event A at time 0.0 seconds -> Event B at time 0.1 seconds. Distance = 0.1. Below threshold (say 0.5), so merge A and B.
Event C at time 0.2 seconds -> Event D at time 1.5 seconds. Distance = 1.3. Above threshold, so keep Event C separate.
Compressed stream has 3 tokens instead of 4. Pre-training learns on 3; fine-tuning predicts all 4.
Result: model sees the structure (a burst then a pause) and can predict timing and text accurately.

The threshold is adjusted per dataset; larger thresholds compress more, making training faster because the model has fewer tokens to process, but risking loss of fine-grained timing information because you merged events that should have been separate.

What can go wrong

What can go wrong

Threshold too high (compress too much). If you merge too many events, the model forgets small-scale timing patterns. Events that arrive every 10 seconds become indistinguishable; fine-tuning cannot recover that precision.
Threshold too low (compress too little). If you keep almost every event, compression saves nothing because you merged almost nothing, so memory is still huge and fine-tuning still struggles with long sequences.
Pre-training mismatch. If the compressed stream and the full stream have very different statistical properties (e.g., bursts in one but not the other), pre-training learns misleading patterns. Fine-tuning then has to unlearn them.
Done right. Choose the threshold by looking at the pattern of time gaps in your data. Validate that compressed and full streams have similar event rhythms, so pre-training learns genuine structure not artifacts. Fine-tune long enough so the model can adapt from the pre-trained base, because adaptation takes iterations.
What a runnable demo should prove

What a runnable demo should prove

Build a small simulator of events (e.g., messages in a chat channel) where some times are clustered and others are spread out. Split your data into train and test. Train one model on the full stream (no compression) and another using this paper's recipe: pre-train on compressed, then fine-tune on full. Measure time-prediction error and text quality on the test set. The compressed-then-fine-tuned model should predict timing within 10% error and generate text descriptions that a human rates as coherent, while the baseline struggles with longer sequences or runs out of memory.

time_error = mean(|predicted_time - actual_time| / actual_time), text_quality = human_rating(generated_text)

The proof is this: compression keeps memory small so the model can see the whole timeline at once; pre-training on the compact version teaches the rhythm so the model knows what patterns to expect; fine-tuning adds local detail without forgetting the big picture. That is why two stages beat one.
