SciAgentGym: Teaching Agents Tool Chains

To teach an agent to use many tools in the right order, draw the tool dependency graph and generate training examples by walking backwards through that graph.

Paper explainersAll themesAgents & Tool Use

An AI agent solving a hard science problem must use many tools in a strict order: you cannot calculate a property before you have the molecule; you cannot compare results without calculating them first. A new benchmark and method called SciForge teaches agents to navigate these sequences by first drawing a map of which tools depend on which others, then creating training examples by exploring backwards from the goal, ensuring the agent learns the real order tools must be called in.

Zero assumption version

Agents fail at long tool chains

When an AI agent tries to solve a scientific problem, it needs to call many specialized tools (databases, calculators, visualization software) in a precise order. A beginner approach would give the agent a flat list of all tools and let it guess which to use when. This fails spectacularly because the agent often calls tools in the wrong order: it tries to calculate properties before retrieving the molecule; it attempts analysis before computation is done. Real science demands a strict dependency chain.

The deeper problem is training data. Standard datasets rarely contain multi-step scientific reasoning that correctly chains 8 or more tool calls, so agents trained on these datasets have never seen complex, long-horizon workflows. When given a hard 10-step task, the agent's error rate explodes.

In one sentence. Map which tools depend on which, then generate training examples by walking backwards from the goal, ensuring every chain in the training data respects the true dependencies.

The algorithm as a flow

What it actually does

1. Build the dependency graph

Inspect 1,780 tools across four science domains; record which outputs feed into which tool inputs.

2. Backward program construction

Given a goal (e.g., 'plot property'), trace backwards to find all minimum chains of tools that produce that output.

3. Sample execution paths

Randomly select which dependent tools to include, then execute tools in topological order, collecting actual outputs and error feedback.

4. Generate training trajectories

Record the full multi-step sequences, including error messages when tools fail, so the agent learns both success paths and recovery.

5. Fine-tune on the chain data

Train the 8B-weight model on these logic-aware trajectories; through repeated exposure, it learns the dependency structure.

What the paper changes

What the paper moves

The paper changes the training data itself. Instead of using whatever unstructured examples exist in papers and datasets, it generates new training examples by exploring the tool dependency graph. Each example is a complete chain of tool calls that respects the real dependencies.

the object it moves  =  training data construction
The hidden quantity

The hidden quantity: tool dependency structure

measured quantity  =  Tool dependency ordering

This is the set of rules defining which tools must be called before others. A molecule database must be queried before property calculations can run; properties must be computed before comparisons. The paper explicitly maps this as a directed graph: nodes are tools, edges show 'this tool needs the output of that tool'.

The paper estimates this by inspecting each of the 1,780 tools: what does each tool expect as input, and which other tools produce those values? This creates the graph. When generating training data, the algorithm respects this graph by only executing tools in topological order (a valid ordering that honors all dependencies) and only selecting tool chains that could actually run without missing inputs.

Why it works

Why it works: respecting the true order

The core insight is that agents trained on random tool examples learn no real structure. When you fine-tune on chains built from the actual dependency graph, the model encounters each tool always paired with its true prerequisites. After seeing thousands of chains where 'database is always before calculator', the model's internal weights encode this rule implicitly.

Error recovery matters too. When the algorithm generates training data, it sometimes includes error messages: 'tool X failed because input was missing'. Training on these teaches the agent not just the happy path but also how to diagnose and recover. The paper shows agents trained with error recovery have much higher success rates on long chains.

Finally, backward construction ensures no 'dead' chains. A random walk might pick tools that do not connect; a backward walk from the goal always produces executable sequences. The agent never trains on impossible chains.

Math after the picture

How to score a tool chain

First in words:

For each tool call in a sequence, check if all its required inputs are available from earlier tool outputs. Penalize out-of-order calls.

Then the compact form:

success_i = 1 if all_inputs_available(tool_i, prior_outputs) else 0; chain_score = product of success_i for i in 1..N

Every symbol:

tool_ithe i-th tool in the sequence
all_inputs_availabletrue if every parameter tool_i needs has been produced by an earlier tool
prior_outputsthe set of outputs from tools 1 through i-1
chain_score1.0 if every tool was called in a valid order, else 0
A tiny worked example
Chain: Database-Query -> Property-Calc -> Comparator
Step 1: Database-Query has no prerequisites. all_inputs_available = true. success_1 = 1.
Step 2: Property-Calc requires 'molecule' input. Database-Query output includes 'molecule'. all_inputs_available = true. success_2 = 1.
Step 3: Comparator requires 'property_1' and 'property_2'. Property-Calc produced both. all_inputs_available = true. success_3 = 1.
chain_score = 1 * 1 * 1 = 1.0 (valid chain).
Compare: if Comparator were called before Property-Calc, success_2 = 0, chain_score = 0 (invalid order).

An agent that learns this scoring rule will never waste steps calling tools out of order.

What can go wrong

Graph is incomplete. If the dependency graph does not capture all true prerequisites (e.g., a tool has an undocumented dependency on domain knowledge), backward construction will generate impossible chains. The agent trains on broken examples.
Exploration rate set wrong. The backward walk includes randomness (exploration rate epsilon) to sample diverse chains. If epsilon is too low, the agent sees only stereotypical chains; if too high, it explores invalid branches.
Tool output non-determinism. Some tools return different results on identical inputs (e.g., database queries with timestamps). Training data might contain 'tool X always produces Y', but at test time tool X produces Z. Agent sees a contradiction.
Done right. Graph is manually verified by domain experts; exploration rate is tuned via held-out validation; tool outputs are cached or sandboxed to be deterministic.
What a runnable demo should prove

What a runnable demo should prove

Build a small dependency graph (5-7 tools with clear input-output links). Implement backward program construction (the core algorithm). Generate 50 random training sequences from the graph, including a few with deliberately injected errors. Split into train (40) and test (10). Fine-tune a small language model (e.g., Llama-2-7B) on the train sequences. Evaluate on test sequences: measure the fraction of tool calls in the correct order. Compare against a baseline trained on randomly shuffled tool sequences.

correctness = (number of valid tool chains in model's output) / (total chains generated)

The demo makes it impossible to miss: agents trained on graph-based chains obey the true tool order because they see every tool consistently paired with its prerequisites; agents trained on random chains fail because they never learn which dependencies actually exist.
