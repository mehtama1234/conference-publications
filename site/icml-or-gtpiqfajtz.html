RADAR: Redundancy-Aware Diffusion for Multi-Agent Communication Structure Generation

Generate a task-specific communication graph for a multi-agent system step by step so that simple tasks use fewer links and hard tasks keep the links they truly need.

Paper explainersAll themesAgents & Tool Use

This paper studies how agents in a multi-agent system should talk to each other. A fixed communication layout is often wasteful: easy tasks do not need everyone talking to everyone, while hard tasks may need a richer structure than the default one provides. RADAR treats the communication graph itself as something to generate. It builds the graph step by step, guided by a measure of how much each connection contributes, so that redundant links can be removed while useful coordination paths are preserved.

Zero assumption version

Why fixed communication layouts waste effort

Multi-agent systems often assume one fixed pattern of communication. That is convenient, but it ignores the fact that tasks differ. Some tasks can be solved with only a few carefully chosen exchanges, while others need richer coordination.

Using too many links raises communication cost and can add noise because agents send messages that do not help. Using too few links can block useful cooperation. The paper asks whether the graph can be generated adaptively for each query.

The paper's move in one sentence. Generate the communication graph progressively and favor links whose contribution justifies their cost for the current task.

The algorithm as a flow

What it actually does

Start from the current query

Read the task and the available agents so that graph generation can be conditioned on what is being asked.

Generate graph states progressively

Produce the communication structure over several steps because one-shot graph choice makes fine adjustment difficult.

Estimate contribution of links

Use a redundancy-aware guide so that links that do not add useful coordination are less likely to survive.

Run the multi-agent system

Let agents communicate using the generated structure.

Measure accuracy and communication cost

Check whether the new structure improves results while using fewer unnecessary messages so that the quality-cost tradeoff is visible.

What the paper changes

What the paper changes

The paper changes the communication graph from a fixed design choice into a query-dependent object that can be generated and optimized.

the object it moves  =  Task-specific multi-agent communication structure
The hidden quantity

The hidden quantity

measured quantity  =  Useful communication contribution of each link

The key hidden quantity is whether a candidate link between two agents adds information that the task actually needs. A link can look harmless, but it may be redundant if the same information already arrives through another path.

RADAR estimates this hidden quantity while generating the graph. It favors links that increase effective coordination because those links improve the answer, and it discourages links that mostly repeat what other links already provide.

Why it works

Why this works: graph generation can remove repeated traffic while keeping the information paths that matter

A fixed graph must choose one compromise for all tasks. That compromise is often poor because the best structure for a simple query is usually smaller than the best structure for a hard query. Step-by-step graph generation works better because it can grow or trim the structure to fit the current need.

The redundancy-aware guide is important because many links provide overlapping value. Penalizing repeated contribution helps reduce message volume, which improves efficiency because agents do not spend effort processing messages that do not change the final decision.

Math after the picture

Reward useful links and penalize redundant ones

First in words:

A compact summary is to prefer a communication graph when it improves task success and preserves high-value coordination links, while subtracting a penalty for repeated or unnecessary communication.

Then the compact form:

graph_score(G, q) = task_success(G, q) + useful_links(G, q) - redundancy_cost(G, q)

Every symbol:

graph_score(G, q)overall desirability of communication graph G for query q
task_success(G, q)how well the multi-agent system solves the task under graph G
useful_links(G, q)benefit from links that add distinct coordination value for this query
redundancy_cost(G, q)penalty for links whose messages mostly repeat information already available elsewhere
A tiny worked example
Suppose a planning agent needs tool results and a critic's check.
Graph A connects everyone to everyone. Task success 8, useful links 4, redundancy cost 7, total 5.
Graph B connects tool to planner, planner to coder, and coder to critic. Task success 8, useful links 7, redundancy cost 2, total 13.
Graph C keeps only planner to coder. Task success 4, useful links 3, redundancy cost 1, total 6.
Graph B wins because it keeps the links that matter while avoiding unnecessary traffic.

The paper uses conditional discrete graph diffusion with an effective-size guide rather than this exact formula, but the formula captures the tradeoff.

What can go wrong

What can go wrong

The generator may drop a rare but necessary link. A link can look redundant in most cases yet be essential for one difficult query, so aggressive pruning can reduce task quality.
Graph search can add overhead. If graph generation itself is too expensive, some efficiency gains from reduced communication may be lost.
Link contribution is task-dependent. A rule learned on one benchmark may not transfer perfectly because the value of communication paths changes with agent roles and task structure.
Done right. The paper is useful because it treats communication design as an adaptive generation problem instead of a fixed architecture choice.
What a runnable demo should prove

What a runnable demo should prove

Build a four-agent system with distinct roles such as retriever, planner, coder, and critic. Give it tasks of varying difficulty. Compare three communication layouts: dense fixed, sparse fixed, and an adaptive graph generator that chooses links step by step.

The demo should log the generated graph, message count, and task result for every query. It should show that the adaptive layout keeps more links on hard tasks and fewer links on easy tasks because the value of communication changes with task complexity.

The demo must prove that generating the communication graph per query can improve the balance between coordination quality and message cost because easy tasks can use fewer links while hard tasks keep the ones they need.
