TRIP-Bench: A Benchmark for Long-Horizon Interactive Agents in Real-World Scenarios

Measure whether an agent can satisfy many travel-planning constraints across long conversations with many tool calls, then train it with an online method built for that setting.

Paper explainersAll themesAgents & Tool Use

This paper studies a gap in agent evaluation. Many existing tests are short and forgiving, so an agent can look capable without proving that it can manage changing user requirements over many turns. TRIP-Bench builds a harder setting based on travel planning, where the agent must keep track of many constraints, use many tools, and revise plans as the user changes direction. The paper also introduces a training method called GTPO to improve behavior in this long interaction setting because it updates the policy from rewards over full conversations instead of isolated replies.

Zero assumption version

Why short agent benchmarks miss the hard part

A real assistant often works over many turns. The user may add a budget, then change the dates, then ask for fewer layovers, then ask for a quieter hotel, and then ask for a cheaper revision that still keeps earlier choices active. The plan must be revised without dropping rules that still matter because a later tool call can easily satisfy the newest request while breaking an earlier one. An agent that handles only one-step tasks does not prove that it can manage this kind of evolving objective.

Travel planning is a good stress test because the task mixes many tool calls with many global constraints. A later choice can break an earlier promise, so the agent must keep a coherent plan through the whole conversation.

The paper's move in one sentence. Create a long-horizon travel benchmark with real-world tools and many changing requirements, then train agents with an online policy method that is tailored to multi-turn interaction.

The algorithm as a flow

What it actually does

Build realistic travel tasks

Use real-world planning settings with many travel requirements so that benchmark tasks reflect practical agent demands.

Provide a broad tool set

Let the agent call many travel-related tools because long planning tasks require more than one lookup source.

Stretch the conversation horizon

Run dialogues over many turns so that the agent must preserve earlier constraints while adapting to later revisions.

Score full-task success

Evaluate whether the final plan satisfies the full set of requirements instead of only scoring local answers.

Train with GTPO

Use an online reinforcement-learning method with reward normalization and reward differencing so that the agent gets a clearer learning signal during long interaction chains.

What the paper changes

What the paper changes

The paper changes both the test and the training recipe. It gives researchers a benchmark where long interaction really matters, and it pairs that benchmark with a post-training method designed for that same setting.

the object it moves  =  the long-horizon interaction policy used by the planning agent
The hidden quantity

The hidden quantity

measured quantity  =  the full evolving set of user requirements that still remain active

The central hidden quantity is the true active requirement set. The dialogue may mention dozens of conditions across many turns, but the agent does not receive a clean final checklist. It must infer which rules are still active, which ones were revised, and which ones now dominate the plan.

TRIP-Bench makes this hard on purpose. The benchmark is useful because it tests whether an agent can keep that changing requirement state coherent while it continues to call tools and revise the itinerary.

Why it works

Why this works: test and train on the failure mode directly

Short benchmarks often reward local fluency, but long planning tasks fail for a different reason: the agent loses track of global consistency. TRIP-Bench exposes that problem because each conversation can include many revisions, many tools, and many dependencies across turns.

GTPO helps because it gives the agent feedback over full interaction sequences instead of treating each reply in isolation. Reward normalization and reward differencing matter because long dialogues produce noisy returns, so a cleaner learning signal makes it easier to reinforce actions that preserve constraints across the whole conversation.

Math after the picture

Reward the whole conversation, not just one reply

First in words:

A simple summary is to score a dialogue by how well the final itinerary satisfies all active requirements, then update the policy from that dialogue-level reward after normalizing the signal across sampled runs.

Then the compact form:

dialogue_score(run) = constraint_satisfaction(run) - mu * violation_count(run)

Every symbol:

dialogue_score(run)overall value of one full interaction run
constraint_satisfaction(run)how well the final plan matches the active requirements
violation_count(run)how many user requirements are broken
muweight on broken requirements
A tiny worked example
Run A finds a cheap itinerary but breaks two timing requirements.
Its satisfaction score is 8 and its violation count is 2, so with mu = 2 its total score is 4.
Run B costs slightly more but satisfies every active rule.
Its satisfaction score is 9 and its violation count is 0, so its total score is 9.
Training prefers Run B because long-horizon quality depends on preserving all the constraints together.

The paper uses a more detailed online update rule, but this score captures the main idea that the full conversation outcome should drive learning.

What can go wrong

What can go wrong

Travel planning is only one domain. A model that improves on travel tasks may still struggle elsewhere because other long-horizon domains can place different demands on memory and tool use.
Reward design can miss subtle user preferences. An agent may optimize the scored constraints while still producing an unsatisfying plan if the reward misses softer preferences.
Long runs are expensive. Training and evaluation can cost a great deal because each dialogue may require many turns and many tool calls.
Done right. The benchmark matters because it tests the exact place where many practical agents still break: keeping a coherent plan across a long changing conversation.
What a runnable demo should prove

What a runnable demo should prove

Build a compact travel-planning environment with a few flight and hotel tools, then create dialogues where the user changes dates, budget, and preferences over ten or more turns. Compare a baseline agent against one trained with a GTPO-style online update rule.

The demo should log tool calls, active constraints after each turn, and whether the final itinerary satisfies the complete final requirement set. The trained agent should break fewer earlier promises because the sequence-level reward teaches it to preserve global consistency across the full dialogue.

The point is to show that long-horizon agent quality depends on full-dialogue consistency, not just local response quality.
