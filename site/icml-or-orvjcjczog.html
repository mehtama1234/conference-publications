AgentNoiseBench: Benchmarking Robustness of Tool-Using LLM Agents Under Noisy Condition

Test tool-using agents under controlled user and tool noise so we can measure how brittle they are outside ideal benchmark conditions.

Paper explainersAll themesAgents & Tool Use

Many agent benchmarks assume clean instructions, clean tool outputs, and orderly interaction. Real use is messier. Users mistype requests, omit details, change goals midstream, or ask in confusing language. Tools can return partial outputs, stale data, or malformed results. This paper builds a benchmark pipeline that injects such noise in a controlled way so that we can measure how sensitive current agents are to imperfect conditions.

Zero assumption version

Benchmark agents look stronger than deployed agents because the test world is too clean

An agent can score well in a benchmark where the user request is tidy and every tool behaves perfectly. That same agent may struggle in deployment because the real interaction contains ambiguity, typo-like noise, missing fields, delayed answers, and occasional tool mistakes.

If evaluation ignores those disturbances, it overstates practical quality. The paper studies a benchmark framework that injects controlled noise while keeping tasks solvable, so that evaluation can measure how quickly performance falls as the environment becomes less clean.

The paper's move in one sentence. Take existing agent tasks, add controlled user-side and tool-side noise, and measure the drop in task success because deployment quality depends on how well the agent handles imperfect interaction.

The algorithm as a flow

What it actually does

Study real disturbance patterns

Group messy interaction into user-side noise and tool-side noise so that the benchmark reflects common deployment problems.

Inject controlled noise

Modify existing agent tasks with adjustable disturbance while preserving solvability because the goal is to test resilience, not create impossible cases.

Evaluate many agents

Run diverse models across noise levels so that sensitivity can be compared under the same task conditions.

Measure performance drop

Track how quickly task success falls as user or tool noise increases because steep drop means the agent depends on unrealistic cleanliness.

Report noise-specific failure patterns

Separate user-side and tool-side effects so that future work can target the true weakness.

What the paper changes

What the paper changes

The paper changes the evaluation environment. Instead of measuring only ideal-condition task accuracy, it measures how gracefully performance degrades when the interaction becomes noisy but still solvable.

the object it moves  =  the benchmark condition under which agent quality is measured
The hidden quantity

The hidden quantity

measured quantity  =  how much useful task progress survives after noise is introduced

The central hidden quantity is noise tolerance. You do not observe it directly from one clean benchmark score because clean success says little about what happens once the request or tool output becomes messy.

You estimate it by increasing disturbance and watching how much useful task progress remains. A tolerant agent should recover from missing details or odd tool outputs because it can ask clarifying questions, verify results, and avoid overcommitting to one brittle interpretation.

Why it works

Why controlled noise injection reveals real weaknesses

A single clean benchmark score bundles many abilities together and hides whether the agent can recover from minor disturbance. Controlled noise injection separates that question out because it changes only the cleanliness of the interaction while preserving the underlying task.

The split between user-side and tool-side noise is also important. Those two sources demand different recovery behavior. User-side noise requires clarification and goal tracking, while tool-side noise requires verification and fallback handling. A benchmark that distinguishes them can show exactly where an agent breaks.

Math after the picture

A compact way to summarize noise tolerance

First in words:

Noise tolerance can be viewed as clean-task success minus the performance drop under disturbance, because a better agent keeps more of its original ability when the interaction gets messy.

Then the compact form:

noise_tolerance = clean_success - noise_drop

Every symbol:

noise_toleranceremaining useful ability after accounting for disturbance sensitivity
clean_successtask success under ideal conditions
noise_drophow much success falls after user or tool noise is introduced
A tiny worked example
Suppose an agent reaches 90 success in a clean benchmark.
After moderate disturbance, its success falls to 62, so the drop is 28.
Then its noise tolerance score is 62 by this simple summary, which is 90 minus 28.
Another agent that falls only to 76 would have a smaller drop of 14.
That second agent looks stronger under deployment-style conditions because it preserves more of its clean-task ability.

The paper reports fuller benchmark results, but this summary captures the main question: how much quality survives once noise arrives.

What can go wrong

What can go wrong

Badly designed noise can make tasks unrealistic. If the disturbance does not resemble real user or tool problems, the benchmark may punish models for artificial quirks because the injected cases are not representative of deployment.
Too much disturbance can destroy solvability. If essential task information is removed entirely, failure no longer measures resilience because even a good recovery policy has nothing left to work with.
One summary number can hide which source of noise hurt most. An aggregate score may blur user-side and tool-side weaknesses, so separate reporting matters because fixes for those weaknesses are different.
Done right. The benchmark is most useful when it preserves solvability and tags the disturbance source, because then failure traces point to concrete recovery gaps.
What a runnable demo should prove

What a runnable demo should prove

Take an existing tool-using benchmark and add a switchable noise layer. On the user side, introduce missing fields, reordered intent, and ambiguous wording. On the tool side, introduce partial outputs, stale values, and malformed returns while keeping the task solvable. Run several agents at each disturbance level.

The demo should show both the success drop and the recovery behavior. A better agent should ask clarifying questions, retry when needed, and cross-check suspicious outputs because those actions preserve useful progress under noise.

tolerance_gap = clean_success - noisy_success ; recovery_gain = recovered_tasks_after_checks - recovered_tasks_without_checks

The point of the demo is to show that deployment readiness depends on noise tolerance because real interactions are rarely as clean as a benchmark prompt.
