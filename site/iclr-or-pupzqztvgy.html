Darwin Godel Machine: Open-Ended Evolution of Self-Improving Agents

The Darwin Godel Machine improves coding agents by letting many agent variants rewrite themselves, test the changes, and keep the ones that actually work, because practical self-improvement needs measured validation rather than formal proof.

Paper explainersAll themesAgents & Tool Use

A self-improving agent sounds attractive in theory, but most proposals run into a brutal obstacle: how do you know a code change is truly better before deploying it? The classic Godel machine answered with proof, but useful proof is too hard for realistic software changes because most practical software edits are too messy to verify formally. The Darwin Godel Machine replaces proof with measured benchmark selection. Agents modify their own code, test those modifications on coding benchmarks, and store successful variants in a growing archive. Future variants are sampled from that archive and improve themselves again because each archived parent starts the next round of self-editing from a stronger baseline. The result is an open-ended evolutionary process that searches over many self-improvement paths in parallel.

Zero assumption version

Why fixed agents stop improving

Most AI systems operate with a human-designed architecture and toolset that stays mostly fixed during deployment. Engineers may patch the system later, but the agent itself is not continuously improving its own code, tool use, or workflow.

The ideal of self-improvement is much stronger. The agent should change its own implementation, test whether the change helps, and become better at making future changes as a result. The barrier is evaluation. Formal proof of benefit is unrealistic for most software edits, yet blind self-modification is dangerous because harmful code can easily slip through. The paper addresses that gap with benchmark-based validation and archive-based selection.

In one sentence. Let coding agents rewrite themselves, validate each rewrite on real tasks, and keep successful descendants in an archive so that later generations can build on the strongest earlier variants.

What the paper changes

What the paper changes

The paper changes self-improvement from a single-agent proof problem into an archive-based evolutionary process. Instead of demanding a formal guarantee before each rewrite, it evaluates code changes by measured coding performance and keeps multiple successful descendants.

The hidden quantity

The hidden quantity: long-run improvement potential

measured quantity  =  how likely one agent variant is to produce even stronger descendants later

A child agent may be valuable for two different reasons. It may score well immediately, or it may open a route to even better descendants by adding a useful editing tool, a stronger review step, or better context management. That second property is hard to observe directly in one generation.

The archive approach helps estimate this hidden quantity indirectly. By keeping diverse strong variants rather than one champion, the system preserves branches that may not be the current best but may yield better descendants later. Open-ended improvement depends on that diversity because self-modification is a search over many future pathways, not a single straight climb.

Why it works

Why archive-based evolution improves self-modification

Formal proof is too strict for most useful software changes. A promising edit may improve search, code review, or context management without offering any tractable proof that it is globally beneficial, because those changes interact with many other system parts and cannot be verified cleanly in advance. If the system insists on proof, it will reject most practical improvements. If it accepts changes blindly, it will quickly accumulate harmful ones.

The paper's solution is measured evolutionary selection. Each agent variant proposes self-edits, then coding benchmarks test whether the edited agent performs better. Good variants survive because they solve more tasks. Keeping an archive of many successful variants matters because different improvements can be complementary. One branch may discover better code editing, another may discover stronger peer review, and a later descendant can inherit or recreate both patterns because the archive preserves multiple successful ancestors at once. That parallel branching is what makes the search open-ended rather than one narrow hill climb.

Math after the picture

Selection rule

First in words:

Keep a child agent when its benchmark score exceeds the parent or passes an archive threshold, because measured task success is the acceptance test for self-modification.

Then the compact form:

Keep(child) = 1 if Score(child) >= Score(parent) + delta

Every symbol:

Keep(child)whether the new self-modified agent enters the archive
Score(child)benchmark score of the child agent
Score(parent)benchmark score of the sampled parent agent
deltarequired improvement margin or selection threshold
A tiny worked example
A parent agent solves 20 out of 100 coding tasks, so its score is 20.
The parent adds a better review step and a new file-edit policy, producing a child agent.
The child solves 28 out of 100 tasks, so its score is 28.
If delta is 3, then 28 is above 20 + 3, so the child is kept in the archive.
Another child solves only 19 tasks, so it is rejected because the rewrite did not help enough.

The essential move is measured acceptance: a rewrite survives because it improves measured performance, not because it was proven beneficial in advance.

What can go wrong

What can go wrong

Benchmarks may overfit the archive. If the validation tasks are too narrow, the system may evolve agents that look stronger on those tasks but do not generalize, because the selection pressure points at the wrong target.
Unsafe self-edits. A child may improve score while also introducing risky behavior. The paper uses sandboxing and oversight because benchmark improvement alone is not enough when safety constraints can be violated.
Archive collapse. If the archive keeps only one narrow family of agents, the search may stall because alternative branches that could lead to better descendants were discarded too early.
Done right. The method works when benchmark tests track real coding ability, safety checks filter dangerous edits, and the archive stays diverse enough to support long-run branching improvement.
What a runnable demo should prove

What a runnable demo should prove

Start with a coding agent that can edit files and run tests on a modest software benchmark. Let that agent propose changes to its own prompts, tools, or workflow, then evaluate each child on a held-out coding task set. Keep the better children in an archive and repeat for several generations so that later agents can start from the strongest earlier changes instead of from scratch.

Track both best score and archive diversity over time. Also inspect what kinds of self-edits survive, such as better review stages or improved long-context handling. The expected pattern is that the archive should climb in coding quality across generations while preserving more than one lineage, because open-ended search benefits from many branches rather than one single chain.

generation_score = solved_tasks / total_tasks, reported for best agent and archive average

The demo should show that practical self-improvement comes from repeated benchmark-based selection over many descendants, not from one frozen architecture or one proof-before-change rule.
