TrajTok: Balancing trajectory tokenizer properties

The best way to turn driving trajectories into tokens for prediction balances rule-based structure with data-driven pruning.

Paper explainersAll themesRobotics & Control

Autonomous driving needs to predict what a driver will do next by learning from millions of real driving logs. The simplest approach: turn each trajectory (a path a car takes) into a token (a discrete label), then train the model to predict the next token like predicting the next word. But what makes a good token set? This paper identifies four properties that matter—coverage (do we have a token for every kind of path?), utilization (how many tokens actually show up in the data?), symmetry (do similar paths get similar tokens?), and stability (do noisy measurements break the tokens?)—and shows how to build a tokenizer that balances all four.

Zero assumption version

Tokenizing driving is messy

To predict the next driving move, the model sees a sequence of past actions (turn left, accelerate, brake) and outputs the next one. The simplest way is to turn real driving paths into a vocabulary—like a dictionary of 'canonical' trajectories—then treat prediction as token-by-token forecasting. But building this vocabulary is a trap.

A naive rule-based approach (defining tokens by fixed hand-crafted rules, like 'gentle left turn' or 'hard stop') gives you coverage: you probably have a token for any curve or deceleration a driver might do. But the vocabulary gets bloated—many tokens never appear in real logs, wasting model capacity. A naive data-driven approach (clustering real trajectories) gives you utilization: every token in the vocab actually appears. But it's fragile: two nearly-identical driver moves—one smooth, one slightly jerky due to sensor noise—land in different clusters, so the model never sees them as similar. That fragility kills generalization to new routes.

In one sentence. TrajTok combines rule-based structure (coverage) with data-driven filtering (utilization and noise tolerance) to get all four properties at once.

The algorithm as a flow

What it actually does

Generate candidate tokens

Use fixed rules (e.g., discretize speed and steering angle) to define a large set of possible tokens.

Filter by data frequency

Remove candidates that appear too rarely in the real driving logs.

Measure stability

Check that similar paths (with small sensor noise) map to the same token.

Smooth token similarities

Adjust the training loss so paths that land in neighboring tokens are treated as similar, not fully different.

Train next-token prediction

Teach the model to forecast the next token in a driving sequence.

What the paper changes

The vocabulary structure

The paper changes the way trajectories are discretized into a token vocabulary. Instead of purely rule-based (too many empty tokens) or purely data-driven (fragile to noise), TrajTok starts with rule-based candidates and prunes them to keep only those that appear frequently in real logs and behave stably under measurement noise.

the object it moves  =  token vocabulary
The hidden quantity

The four-property score

measured quantity  =  Coverage, utilization, symmetry, stability

The paper measures four properties of a vocabulary. Coverage is the fraction of real driving paths that fall near enough to an existing token—do we have a token for nearly every kind of move? Utilization is the fraction of tokens that actually appear in the data—no wasted slots. Symmetry is whether two very similar paths always map to the same token (not one to token A and one to token B just because of tiny noise). Stability is whether a path's token assignment stays the same when you add small random sensor errors.

The paper shows that rule-based tokenizers score high on coverage but low on utilization, while data-driven tokenizers flip that trade-off. TrajTok's contribution is achieving all four simultaneously by filtering rule-based candidates through data frequency.

Why it works

Why balancing works

The core insight is that the two naive approaches are solving different problems. A rule-based tokenizer enforces structure (every token represents a plausible move) but over-generates (many tokens never appear). A data-driven tokenizer respects what actually happens in the data but shatters under tiny noise—two nearly-identical paths with different sensor jitter become different clusters.

TrajTok splits the job: rules set up candidates (we know these are valid driving moves), and data filters them (keep only what drivers actually do). This balances coverage (rules ensure we hit most real paths) with utilization (filtering removes dead weight). For symmetry and stability, the paper adds spatial-aware label smoothing—a small tweak to the training loss that says 'paths in adjacent tokens should be treated as similar neighbors, not enemies.' Because the tokens are spatially organized (from the rules), this smoothing is well-founded: tokens that are close in the space of speed and steering do represent similar driving. Nearby sensor noise stays in the same token or slides to a neighbor with just a small penalty; the model learns to treat both as safe.

To sum up: structure combined with filtering combined with smoothing gives all four properties at once. You cannot get all four by being pure in any one direction.

Math after the picture

The spatial-aware loss

First in words:

loss = standard cross entropy plus a penalty for assigning high confidence to a single token when nearby tokens are plausible

Then the compact form:

L = -sum_i log(p_i) + lambda * sum_i,j dist(i,j) * p_i * (1 - p_j)

Every symbol:

p_ithe model's predicted probability for token i
log(p_i)how wrong the prediction is (cross entropy)
dist(i,j)spatial distance between tokens i and j (from rules)
lambdahow much to soften predictions toward neighbors
(1 - p_j)the gap in probability for neighboring token j
A tiny worked example
Suppose a path maps to token 5, and tokens 4 and 6 are spatially adjacent.
The model predicts: token 5 with prob 0.8, token 4 with prob 0.1, token 6 with prob 0.1.
Standard loss: -log(0.8) = 0.22.
With spatial smoothing (dist=1, lambda=0.1): penalty = 0.1 * 0.8 * (1 - 0.1) + 0.1 * 0.8 * (1 - 0.1) = 0.16.
Total loss = 0.22 + 0.16 = 0.38. The model learns to share probability with neighbors, so small noise does not flip the token entirely.

The penalty pushes the model to treat spatially-close tokens as plausible alternatives, which buys stability to noisy measurements.

What can go wrong

What can go wrong

Rule set misses real driving styles. If the rules do not anticipate aggressive or unusual paths (e.g., hard emergency turns), filtering will still miss them. The rule set must capture the full range of plausible moves before filtering.
Filtering threshold set too high. If you require a token to appear too many times in the training logs, you over-prune and lose coverage on rare-but-valid moves. The threshold is a hyperparameter that trades off sparsity vs. generalization.
Spatial smoothing too aggressive. If lambda is too large, the loss pulls predictions toward neighboring tokens so much that the model forgets to distinguish them. Paths that should map to different tokens (e.g., gentle vs. hard braking) blur together.
Done right. Validate the rule set on diverse driving scenarios; tune the filtering threshold on a held-out validation split; measure noise stability empirically (apply sensor perturbations, check token stability); monitor generalization to unseen routes.
What a runnable demo should prove

What a runnable demo should prove

A minimal demo: (1) Collect 10,000 driving trajectories from logs. (2) Build three tokenizers—pure rule-based, pure data-driven, and TrajTok. (3) Train a small next-token prediction model on each. (4) Measure all four properties (coverage, utilization, symmetry, stability). (5) Perturb test trajectories with small random sensor noise and re-evaluate. (6) Test generalization on trajectories from a held-out new route with similar traffic patterns. The demo must make impossible to miss: TrajTok balances the four properties where naive methods fail, and that balance persists even with noise and new routes.

Balanced property score = min(coverage, utilization, symmetry, stability) — higher is better; naive methods score unevenly; TrajTok is flat.

The key finding is not that TrajTok is 'best' on any single metric, but that it avoids catastrophic failure on any one—rules handle structure, data handles pruning, smoothing handles noise.
