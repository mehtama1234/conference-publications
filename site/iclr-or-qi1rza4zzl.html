Safety Mirage: How Spurious Correlations Undermine VLM Safety Fine-Tuning and Can Be Mitigated by Machine Unlearning

Supervised safety training teaches VLMs to spot short-cuts in the data (like specific question-starter words) rather than learning genuine harm-avoidance, but machine unlearning removes harmful knowledge directly, avoiding those traps.

Paper explainersAll themesAlignment, Safety & Fairness

Vision-language models (models that read images and text together) often get trained for safety using labeled examples: show it unsafe questions paired with rejection responses. But a new problem emerges: the model learns to correlate spurious patterns in the training data (like the word starting each question) with whether to refuse, rather than understanding the actual harm. This paper calls this the safety mirage. A simple one-word substitution can bypass these surface-level correlations. The authors propose machine unlearning instead: directly forget what makes content harmful, without relying on those labeled rejection responses, sidestepping the entire trap.

Zero assumption version

Trained safety catches surface patterns, not deep understanding

When engineers build a safer vision-language model, they usually show it a curated dataset: images and text labeled as safe or unsafe, each paired with a safe response (often a standard rejection like I'm sorry, I cannot help with that). The model's learning algorithm works by comparing what the model outputs to the label it was given, computing an error, and adjusting the weights to shrink that error. Over many examples, the weights shift to match the labels: queries marked unsafe get steered toward rejection outputs, and queries marked safe get steered toward allowed outputs.

What the model actually learns is often wrong. The model doesn't learn that certain content is harmful; instead, it takes a shortcut. It learns statistical correlations: if the text starts with Share or Show, output rejection; if it starts with What or Describe, output an answer. The model takes these shortcuts because they minimize training error efficiently—it's easier for the model to latch onto surface-level word patterns than to understand the actual reasons content is harmful. These shortcuts work well on the training data, but they're brittle—based on accidental word-frequency patterns in the safety dataset, not on genuine harm understanding.

Worse, this creates two problems. First, adversarial breakability: change one word (Share -> What) and the safeguard evaporates, even though the core request is unchanged. Second, over-refusal: the model refuses harmless questions that happen to start with the frequently-rejected-word, wasting the model's utility.

In one sentence. Supervised safety training teaches the model to correlate accidental word patterns with rejection, not to understand harm itself.

What the paper changes

What the paper changes

The paper changes how safety training uses its data. Instead of showing the model unsafe queries paired with rejection labels (the standard way), it feeds the model only the raw unsafe queries themselves, without any label signal to latch onto.

the object it moves  =  Unsafe query labels
The hidden quantity

The hidden quantity: spurious correlation strength

measured quantity  =  Word-to-rejection association

A spurious correlation is a false association in the training data: certain words (like Share) appear disproportionately often in rejected queries, while others (like What) dominate in allowed queries. The model learns to treat the word itself as a signal, not the content.

The paper estimates this by analyzing word frequencies in the training dataset: which question-starter words are most common in rejected vs. accepted queries. A high spurious correlation means a few words do most of the predictive work for rejection, a sign the model has learned a surface pattern rather than genuine harm detection.

Why it works

Why machine unlearning removes the shortcut without breaking the model

Supervised safety fine-tuning pairs each unsafe query with a label (reject). The model learns a direct path: when it sees unsafe query, output rejection. But it takes the shortest path available, and if the dataset has word-frequency biases, that shortest path is through the word pattern, not through actual harm understanding.

Machine unlearning breaks that path by removing the label. Instead of saying when you see this query, output rejection, it says: when you see this unsafe query, map your internal representation to noise (a random vector). This is counterintuitive but effective: the model can't learn any consistent pattern in the raw query text because it has no labeled output to anchor to. Instead, it's forced to weaken the features that produce outputs matching the unsafe query's patterns.

Why doesn't this break the model? Because the paper also retains a normal training loop on benign data. The model keeps its ability to answer safe questions using standard fine-tuning. The unlearning only targets the weights that were making harmful outputs. The result: one-word paraphrases no longer fool the model, and harmless queries still get answered.

Math after the picture

The unlearning objective

First in words:

loss = (unlearning loss on unsafe data) + (retention coefficient times retention loss on safe data). For unlearning, push the model's intermediate representation of unsafe queries toward a random vector. For retention, mix standard fine-tuning on safe data with an MU-specific retention penalty.

Then the compact form:

L_total = L_u + gamma * L_r, where L_u = E[||M(x) - c*v||^2] and L_r = L_ft + alpha * L_mu_r

Every symbol:

L_totalThe combined loss to minimize
L_uUnlearning loss on unsafe data
L_rRetention loss on safe data
gammaBalance factor (how much to protect safety vs. utility)
M(x)The model's intermediate representation of input x
cScaling factor that controls feature magnitude
vA random vector drawn from uniform distribution
L_ftStandard fine-tuning loss on safe data
alphaBalance between standard fine-tuning and MU retention
L_mu_rMU-specific retention penalty on safe data
A tiny worked example
Suppose we have a weight w that contributes to harmful output when it sees Share queries.
Normal supervised training: show model unsafe_query + label_reject; it learns w should be high for Share.
Unlearning instead: show only unsafe_query (no label); force the model's representation M(x) to random noise v.
Cost: reducing w's contribution to harmful outputs requires changing w itself, because the model can't anchor to the label.
Retention: keep standard fine-tuning on safe queries (What queries) so w still contributes correctly to those.
Result: w becomes less responsive to Share patterns overall, but still works for What and other benign questions.

The key is replacing the labeled rejection with a feature-mapping penalty: the model can't learn a word-to-label association if there is no label, only raw noise.

What can go wrong

What can go wrong

Representation layer mismatch. Unlearning targets an intermediate layer M(x). If you pick the wrong layer (too early, before the model learns to recognize safety-relevant patterns; too late, after different concepts are intertwined), the penalty has no effect or destabilizes training. The paper carefully tunes which layer to target and the scaling factor c.
Retention collapse without standard fine-tuning. Pure machine unlearning on VLMs can cause optimization instability or even model collapse if there is no standard fine-tuning term mixed in. The paper solves this by using a composite retention loss, keeping both supervised fine-tuning and MU-specific penalties.
Over-unlearning on benign data. If the retention loss is too weak, the model forgets legitimate knowledge. For example, if a benign query involves the word Share in a harmless context (Share your favorite recipe), the unlearning can over-suppress it.
Done right. Unlearning works when the representation layer is chosen to capture mid-level safety-relevant features, the retention loss balances both supervised and MU objectives, and the unsafe dataset is well-defined (not contaminating the safe set).
What a runnable demo should prove

What a runnable demo should prove

Build a small vision-language model (e.g., a simplified CLIP plus language head). Train it on a toy safety dataset where, intentionally, all unsafe prompts start with Share and all benign prompts start with What. Then fine-tune it two ways: (1) supervised fine-tuning with rejection labels, (2) machine unlearning without labels. For each, test: (a) Does it refuse the original unsafe query? (b) Does it refuse a one-word-swapped version (change Share to What)? (c) Do safe queries still work? The demo should show that supervised fine-tuning fails test (b), while unlearning passes all three.

attack_success_rate: (num_unsafe_queries_answered after word-swap) divided by (total_unsafe_queries). Unlearning should show less than 20% success; supervised fine-tuning greater than 50%.

The demo must make it impossible to miss that learning word-patterns and learning real safety are two different things—and that unlearning escapes the word-pattern trap without crippling the model.
