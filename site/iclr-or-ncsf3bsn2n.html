Probabilistic Kernel Function for Fast Angle Testing

Use deterministic projection rules tied to the target angle instead of generic random Gaussian projections, so angle comparison can be decided with fewer tests and stronger guarantees.

Paper explainersAll themesOther

Many search and retrieval systems need a fast answer to a simple geometric question: is the angle between two high-dimensional directions, each written as a long list of numbers, smaller than a threshold, or which of two angles is smaller? Exact angle computation is costly when the directions are large and the query volume is high. A common shortcut is to project both directions onto random directions and estimate the answer from the signs or orderings of those projections. This paper argues that generic Gaussian projections waste information because they are not tailored to the specific angle test being asked. It builds probabilistic kernel functions (fast randomized decision rules) whose projection structure is chosen around the reference angle itself, which means each projection contributes more directly to the decision.

Zero assumption version

Why generic random projections leave speed on the table

Angle testing sits inside approximate nearest-neighbor search, maximum inner-product search, and many ranking pipelines. The task can be phrased in two ways: compare two candidate angles, or decide whether one angle is below a threshold. In high dimension, exact trigonometric computation on every candidate pair is too slow.

Random projection methods help because they turn a large comparison between long lists of numbers into many cheap one-dimensional tests. But standard Gaussian projections are universal rather than targeted. They sample directions without using the specific threshold angle, so many projections are only weakly informative for the decision that matters.

The paper aims at the decision boundary itself. If the question is whether the angle is below theta, then the best projection statistics are the ones whose probabilities change sharply around theta. A projection family designed for that boundary should separate yes from no with fewer samples.

In one sentence. The method speeds up angle testing because it replaces generic random projections with projection rules designed around the exact angle boundary being tested.

The algorithm as a flow

What it actually does

1. Choose the angle task

Set whether the system must compare two candidate angles or decide whether one angle is below a chosen threshold.

2. Build structured projection directions

Construct projection directions with deterministic structure that depends on the reference angle rather than sampling all directions from one generic Gaussian rule.

3. Project the directions

Map each high-dimensional direction to a short collection of single-number projection outcomes.

4. Apply the probabilistic kernel

Turn those projection outcomes into a probability score for the angle event of interest.

5. Use the score for search

Screen or rank candidates in approximate nearest-neighbor search so only promising directions proceed to more expensive checks.

What the paper changes

What the paper changes

The paper changes the projection family used inside probabilistic angle tests. Instead of using generic Gaussian random directions, it uses projection directions built with deterministic structure around a reference angle.

the object it moves  =  the projection rule inside the angle test
The hidden quantity

The hidden quantity: separation at the decision boundary

measured quantity  =  how strongly the projection outcomes differ for angles just below versus just above the target boundary

The real speed of a probabilistic angle test does not come from projection alone. It comes from how informative each projection is. If two angles produce nearly the same projection statistics, then many projections are needed before the system can decide. If they produce sharply different statistics near the threshold, only a few projections may be enough.

That boundary separation is the hidden quantity the paper optimizes. The reference angle is built into the projection design so the probability of each projection outcome changes in the right place. In other words, the projection rule is tuned to make the threshold case easy to distinguish from its neighbors.

This also explains the search result. Candidate screening becomes faster when the first-stage test discards bad candidates with high confidence after fewer projections, because the expensive graph traversal or exact refinement stage sees less traffic.

Why it works

Why a reference-angle design beats generic Gaussian projections

A projection method works by turning a hard high-dimensional relation into many small random events whose probabilities depend on the unknown angle. The standard Gaussian design is attractive because it is simple and isotropic, which means every direction is treated the same. But the task itself is not isotropic. It asks about one angle boundary, not about all possible geometric relations equally.

The paper uses that mismatch. By choosing projection directions with deterministic structure linked to the reference angle, it makes the induced event probabilities more sensitive where the decision matters most. This improves sample efficiency because each projection carries more information about whether the angle is on one side of the boundary or the other.

The authors also emphasize non-asymptotic behavior, which means the guarantees apply for a finite number of projections rather than only in the limit of infinitely many. That matters in practice because real systems budget only a small number of projections per candidate. A method that is sharper at small projection counts translates directly into higher query throughput.

Math after the picture

A projection-based angle score

First in words:

Estimate the probability of a projection event under a chosen reference angle, then average that event over several structured projections to score whether the true angle is below the threshold.

Then the compact form:

K(x, y; theta) = (1 / M) * sum_m I[event_m(x, y, theta)]

Every symbol:

xquery vector
ycandidate vector
thetareference angle or threshold angle
Mnumber of projection tests
event_m(x, y, theta)the m-th projection outcome designed around theta
I[...]indicator that is 1 when the event occurs and 0 otherwise
K(x, y; theta)kernel score estimating whether the pair satisfies the target angle relation
A tiny worked example
Suppose the threshold angle is 30 degrees and we use 5 structured projections.
For one candidate pair, the projection events are [1, 1, 0, 1, 1].
The kernel score is 4 / 5 = 0.8.
For another pair near a larger angle, the events might be [0, 1, 0, 0, 1], giving 2 / 5 = 0.4.
Because the projection rule was designed around 30 degrees, the score gap between 0.8 and 0.4 appears with few projections, so the system can separate candidates quickly.

The exact event definition depends on the paper's structured projections, but the main point is that the event probability is engineered to change sharply near the reference angle.

What can go wrong

What can go wrong

Reference angle poorly matched to the task. If the search system uses a threshold far from the angle range where the projection rule was designed to be sharp, the kernel loses its edge because boundary separation weakens.
Projection budget too small for noisy data. Even a sharper kernel still relies on repeated projection events. If the compared directions are noisy and the projection count is extremely low, the score variance can remain large.
Screening stage only. The method speeds the first decision step. If the later search pipeline is dominated by another bottleneck, overall gains may be smaller than the angle-test gain alone.
Done right. Choose the structured projection family to match the target angle test and use it where early candidate pruning dominates runtime. Then the search system benefits because many bad candidates are dismissed after a small number of informative projections.
What a runnable demo should prove

What a runnable demo should prove

Create a synthetic nearest-neighbor task with high-dimensional unit directions. For each query, compare a Gaussian-projection angle tester against the paper's reference-angle tester as a first-stage filter before exact ranking. Sweep the number of projections and measure false accepts, false rejects, and queries per second.

The demo should show that the structured tester reaches the same screening quality with fewer projections because its event probabilities are tuned to the target angle threshold.

qps = num_queries / total_time screening_error = (false_accepts + false_rejects) / total_candidates

A strong result is a visible speed-quality frontier shift: the same screening quality at lower projection count, or higher throughput at the same quality.
