AstaBench: Rigorous Benchmarking of AI Agents with a Scientific Research Suite

A real-world environment with production-grade search tools lets you fairly compare science-research AI agents by controlling confounders and measuring end-to-end capability.

Paper explainersAll themesDatasets & Benchmarks & Evaluation

AI agents can now do science: read papers, run experiments, analyze data, propose ideas. But comparing them fairly is nearly impossible. Existing benchmarks give agent A an advantage just because it has better search tools or bigger models, making it impossible to know which one is actually smarter at research. This paper builds a fair playing field: a controlled environment with the same search tools and a suite of 2400+ problems that span the whole research process.

Zero assumption version

Why comparing agents today is broken

Suppose you want to know: which research AI agent is better (because some agents are deployed in production helping scientists, and you need to choose which one to use). Agent A says it found 50 papers for a question. Agent B found 60. But wait: A used a generic search engine, B used a specialized science database. Did B actually understand the question better, or just get luckier with the search tool? You cannot tell, because better search tools return more relevant documents regardless of the agent's reasoning quality.

Worse: Agent A ran 30 experiments and succeeded on 10. Agent B used a bigger model and succeeded on 15. Is B smarter, or just more expensive? You don't know, because larger models have more parameters to solve harder tasks. These hidden confounders (better search, bigger models, access to more tools) are tangled up with the actual intelligence you want to measure, since both contribute equally to the final score. Every existing benchmark has this problem: they measure a mix of agent quality and access quality.

The naive approach fails because: Different agents get different search tools, different models, different code libraries. You end up measuring tool quality, not agent capability.

The algorithm as a flow

What it actually does

Build a shared environment

One set of search tools, one code sandbox, one database for all agents.

Define research-realistic tasks

2400+ problems: find papers, write literature reviews, run experiments, propose ideas.

Measure end-to-end completion

Not just individual steps, but finishing the whole research workflow.

Control confounders

Every agent sees the same search results, same model sizes (when not testing models).

Reveal true capability gaps

Score shows who completes whole experiments, not who got lucky with tool access.

What the paper changes

What gets controlled

The paper changes what agents can access: instead of each agent using its own search engine, database, and code libraries, they all use the same tools. This removes the confounder.

the object it moves  =  agent evaluation environment
The hidden quantity

End-to-end completion rate

measured quantity  =  probability of finishing all steps

This is the true measure of research capability: given a 10-15 step experiment (like 'find the right paper, extract the method, run the code, analyze results'), what is the chance an agent completes every single step without getting stuck? It sounds simple but it is the strongest signal of real research ability.

The paper estimates it by running agents on the benchmark and counting: did all steps finish? The twist: individual steps often succeed around 70%, but because there are many steps in sequence, the total probability crashes. For example, if each of 10 steps has a 70% success rate, multiplying them together gives about 3% total. This one number (end-to-end completion) is what separates a clever agent from a reliable research assistant.

Why it works

Why controlling the environment reveals true capability

Before: Agent A finds a paper using tool X (a weak search engine). Agent B uses tool Y (a research database). If B finds better papers, you cannot tell if B's reasoning is smarter or B's tool is better, because the tool is doing much of the work. The confounder muddles everything.

Now: Both agents search using the same production-grade search tool (the Asta Environment). The tool returns the same candidates for both. Now when Agent B finds better papers, it must be because B thought of a better search query or interpreted the results more wisely, since the tool cannot favor one agent. The confounder is removed.

Separately: the paper measures end-to-end completion (can you finish 10 steps?) instead of per-step success (did you pass step 3?). This matters because a chain breaks if even one link fails: errors compound multiplicatively, so a 70% per-step rate drops to 3% for 10 steps. If Agent A passes 8 of 10 steps and Agent B passes 9 of 10, Agent A is stuck most of the time (80% of complete tasks fail), but Agent B finishes most tasks (only 10% fail). The end-to-end score is the honest one.

Cascading failure through a chain

First in words:

Completion rate for entire workflow = product of individual step success rates raised to the number of steps

Then the compact form:

total_success = p_step1 * p_step2 * ... * p_step_N

Every symbol:

A tiny worked example
Suppose an agent has 10 steps and each step succeeds 70% of the time.
Step 1: 0.70
Steps 1-2: 0.70 × 0.70 = 0.49 (49%)
Steps 1-5: 0.70^5 = 0.168 (17%)
Steps 1-10: 0.70^10 = 0.028 (2.8%)
The workflow completes only about 3% of the time, even though each individual step works two-thirds of the time. This is why end-to-end metrics reveal true capability: they show whether an agent can really think through a multi-step problem.

This is why end-to-end matters: a 70% success rate on each step sounds good, but 10 steps in a row fail 97% of the time, revealing the depth of real research reasoning.

What can go wrong

What can go wrong

Runaway loops. An agent gets stuck in a reasoning loop and keeps trying the same query. The paper caps agents at 100 steps per task to prevent infinite loops.
Confunders sneaking back in. If one agent gets to call an API with a higher rate limit or a paid tier, or if the search index is updated mid-evaluation, the playing field tilts again.
Task design bias. If the 2400 problems are drawn from a particular research domain (e.g., only machine learning), the suite misses how agents perform on physics or biology.
Done right. The paper includes agents spanning a wide range of architectures and sizes, curates tasks from multiple scientific domains, and uses an LLM judge (not hand labels) to score reasoning quality, reducing author bias.
What a runnable demo should prove

What a runnable demo should prove

Build a small version: pick three research tasks (find papers on a topic, extract a method, run a toy experiment). Set up the same search index and code sandbox for all agents to use. Run two agents: one good at reasoning, one good at searches. Score them end-to-end. The key result: the better reasoner should score higher, and the search-focused agent should score lower, despite having excellent search tools, because end-to-end completion penalizes getting stuck mid-chain, which hurts the search agent when it must chain steps it cannot search its way through.

completion_rate = (experiments_fully_passed) / (total_experiments)

The demo must show that controlling the environment reveals which agent is smarter at reasoning, separate from which agent has better tools, by proving that the reasoning-strong agent completes whole workflows while the search-strong agent stalls when forced to think through unsearchable steps.
