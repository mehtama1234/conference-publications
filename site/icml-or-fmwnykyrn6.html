ToolPro: Tool Programs for Flexible Agentic Web Services

Instead of calling web services one step at a time, package multiple steps into a single program that the agent runs all at once, cutting both latency and network traffic.

Paper explainersAll themesAgents & Tool Use

When an AI agent uses web services, it typically calls them one at a time, waiting for answers before asking the next question. ToolPro bundles these repeated requests into a single executable program that the agent writes once and runs completely, like writing a script instead of typing commands into a terminal one by one.

Zero assumption version

Agents waste time calling services one at a time

When an LLM-based agent needs to perform a workflow with multiple steps, it typically makes each call separately. For example, if the agent needs to fetch data from an API, transform it, then send it somewhere else, it makes three separate network requests and waits for answers between each one. The agent has to see the first result before it can decide what the second call should be.

This creates two costs. First, time: every network round-trip (the time to send a request and receive an answer) adds latency, and with multiple steps, these delays pile up. Second, bandwidth: the agent sends many small requests instead of one larger, more efficient one. A beginner might try speeding things up by making multiple calls at once, but that breaks workflows that have real dependencies, where one step's output feeds into the next step's input.

The paper's insight. Let the agent write a program describing all the steps upfront, then run that whole program at once, automatically batching what can be done together.

The algorithm as a flow

What it actually does

Agent specifies intent

The agent writes a program describing the workflow: fetch data, transform it, post it.

Constraint-guided construction

ToolPro builds a valid program that respects each service's rules (types, order dependencies).

Effect-aware replay

The system tracks which steps modify the world (like uploading); if a step fails and retries, it ensures state-changing operations run only once.

Execution policy decision

Before running, ToolPro's profiler decides: should we run this as a program or make individual calls? It chooses based on network latency and workflow complexity.

Execute and measure

Run the program and collect latency, traffic, and correctness metrics.

What the paper changes

The thing being changed

ToolPro changes how the agent communicates with web services. Instead of the agent sending separate requests to services, it sends one program that encodes all the requests it wants to make, their order, conditional logic, retries, and how results flow between steps.

the object it moves  =  Representation of tool requests
The hidden quantity

Effect tracking: knowing what changes the world

measured quantity  =  Effect annotations per call

Every call to a web service either reads data (a GET request) or modifies state (a POST that uploads or deletes). ToolPro annotates each call with its effect type: read-only or state-modifying. This matters because if a step fails and retries, a read-only call is safe to repeat, but a state-modifying call must run exactly once or the world gets corrupted (you upload twice, or delete twice).

The paper uses effect annotations to enable a replay mechanism: if an intermediate step fails, the system reruns from a checkpoint but skips re-executing state-modifying calls, replaying only their cached results. This prevents double-uploads and ensures correctness because running a state-modifying call twice produces a corrupted outcome (charging twice, uploading twice), whereas replaying a cached result is safe and fast.

Why it works

Why batching into one program cuts latency and traffic

When an agent makes separate calls, every request has overhead: DNS lookup, TCP connection, HTTP headers, request serialization, deserialization of the response. By bundling multiple steps into one program, ToolPro amortizes these overheads across all the steps. The agent sends one network request to ToolPro's runtime, which then orchestrates all the internal calls between services, reusing connections and buffering data.

Second, ToolPro can optimize the program before running it. For example, if step 2 only needs a small part of step 1's output, the program can extract just that part and discard the rest, cutting bandwidth. Or if two independent steps have no data dependency, they can be parallelized within the same program execution. Third, by encoding the entire workflow upfront, ToolPro knows which calls are conditionally executed and can prune unnecessary steps. A naive caller would send requests for all branches; ToolPro's program evaluator only executes the branches actually needed.

The effect-aware replay mechanism adds safety without slowing down the happy path: on success, the program runs once. On failure and retry, cached results bypass redundant state-modifying calls, so the program converges faster than re-executing from scratch because each avoided state-modifying call saves a full network round-trip and any side effects that would corrupt the outcome.

Math after the picture

The efficiency gain formula

First in words:

Total latency equals round-trip-time times the number of calls, plus sequential overhead. Batching reduces this to: round-trip-time for the program request, plus internal parallelization overhead, times a smaller effective depth.

Then the compact form:

L_total = RTT * depth_sequential + overhead_sum L_batched = RTT + depth_parallel + overhead_amortized Gain = (L_total - L_batched) / L_total

Every symbol:

L_totallatency of sequential call-by-call approach
L_batchedlatency of program execution
RTTnetwork round-trip time (milliseconds)
depth_sequentialnumber of steps in the workflow
depth_parallellongest chain of dependent steps (can run in parallel)
overhead_sumcumulative per-call overhead (headers, handshakes)
overhead_amortizedoverhead spread across all steps in one program
Gainpercentage reduction in latency
A tiny worked example
Scenario: a workflow with 5 steps, each step independent from the others, running over a network with 100ms round-trip time.
Sequential (call-by-call): 5 calls × 100ms = 500ms + 50ms overhead = 550ms.
Batched (program): 1 call to run the program × 100ms = 100ms. Internal parallelization runs all 5 steps together: 100ms + 15ms batched overhead = 115ms.
Gain: (550 - 115) / 550 = 79% latency reduction. (The paper reports up to 53% under more realistic conditions with some sequential dependencies.)

The gains are largest when network latency is high and workflows have parallelizable steps.

What can go wrong

What can go wrong

Service semantics unknown to ToolPro. If a service has undocumented side effects (a read that secretly logs or changes internal state), ToolPro's effect annotations are wrong, and the replay mechanism could cause bugs. ToolPro relies on honest effect declarations from each service.
Workflow with strongly sequential dependencies. If every step depends on the exact result of the previous step, there is no parallelism to exploit. ToolPro still saves overhead by bundling, but gains are modest.
Program construction ambiguity. If the agent's intent is underspecified (e.g., unclear which conditional branch to take), constraint-guided construction may produce an incorrect program. Clarity in the agent's specification is essential.
Done right. When services provide effect annotations, workflows have parallelizable steps, and the agent specifies intent clearly, ToolPro delivers both latency and traffic savings as predicted.

What a runnable demo should prove

Implement two versions: (1) naive call-by-call, where the agent makes three separate HTTP requests, and (2) ToolPro version, where the agent writes a program that the runtime executes. Measure end-to-end time and total bytes sent over the network.

The demo must show that a single batched program is faster and leaner because it amortizes network overhead, cuts redundant calls, and parallelizes independent steps, whereas call-by-call must wait for each result before sending the next request.
