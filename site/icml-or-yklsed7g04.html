Decompose and Recompose: Reasoning New Skills from Existing Abilities for Cross-Task Robotic Manipulation

Instead of showing a robot only low-level actions from past tasks, break those actions into named skills (reach, grasp, release) so the robot can recombine them in new ways.

Paper explainersAll themesRobotics & Control

A robot trained on tasks like placing a cup learns raw movement sequences but cannot explain what it is doing or why. When asked to put a knife on a board, it tries to copy the motion shapes without understanding that the underlying skills (reaching, grasping, releasing) are reusable. This paper shows how to decompose demonstrations into atomic skills—named reasoning units—so an AI language model can reason about which skills to use and in what order for completely new tasks.

Zero assumption version

Low-level actions do not transfer across new tasks

Today's robot learning methods show a robot many demonstrations of a task—like placing a cup on a table—and extract low-level action sequences: move arm to x1, y1, z1; open gripper; move arm to x2, y2, z2; close gripper. When a new task arrives (place a knife on a board), the robot retrieves demonstrations and tries to match the shapes of the trajectories. But this trajectory matching fails: the knife task is different enough that copying motion shapes leads nowhere. The robot never learns what is actually happening at each step.

A beginner might try this: show the robot both tasks and train it on all the data at once. This does not work because the robot has no way to extract what is shared between tasks. Is it the reaching? The grasping? The sequence? Without understanding these named skills, the robot treats each task as completely separate, and it cannot generalize to new combinations.

The core problem. Robots learn action sequences without understanding the skills those sequences perform, so they cannot reason about which skills to use for new tasks.

The algorithm as a flow

What it actually does

Decompose: Label each action in seen tasks.

Parse demonstrations into atomic skills (Reach, Grasp, Move, Release) paired with low-level actions.

Plan: Predict skill sequence for new task.

A planning agent looks at the new task instruction and predicts which skills are needed and in what order.

Retrieve: Find past demonstrations matching that skill plan.

Search the library for examples with the same skill sequence, ranked by visual similarity to the new scene.

Cover gaps: Fill missing skill patterns.

If certain skill transitions are not in the top results, explicitly add demonstrations that contain them.

Recompose: LLM reasons and generates actions.

Feed the skill-annotated demonstrations to a language model, which reasons about skill composition and outputs executable actions.

What the paper changes

What the paper changes

The paper swaps low-level action numbers for named skill labels. Instead of storing a demonstration as a sequence of coordinates and gripper commands, it stores interpretable skill-action pairs: each step is labeled with a skill name (Reach, Grasp, Move, Release) and paired with the underlying action. This shift transforms the representation from opaque trajectory shapes into composable reasoning units.

the object it moves  =  representation of demonstrations
The hidden quantity

The hidden quantity: Skill coverage

measured quantity  =  Skill coverage

Skill coverage is the fraction of distinct skill patterns (sequences of skills) that are available in the demonstration library. A library has 100% coverage for a new task if every skill transition needed for that task exists somewhere in the past examples. If the task needs Reach-then-Grasp-then-Move-then-Release but the library only contains Reach-then-Grasp and Move-then-Release (separately), coverage is incomplete.

The paper measures and maintains this quantity using an algorithm that breaks each skill sequence into pieces (like dividing a sentence into words), counts which skill transitions appear in the dynamic library (retrieved examples), and greedily fills gaps by pulling additional demonstrations from a static library that has been pre-indexed by skill coverage. The coverage-aware static library is built offline by converting skill sequences into structured pieces and using a weighting scheme (called Inverse Document Frequency, which upweights rare skill patterns) to ensure that uncommon but important skill transitions are not overlooked.

Why it works

Why it works: Composable reasoning over skills

The method works because it transforms the robot's reasoning problem from trajectory matching into skill composition. When a robot only sees action sequences, it cannot abstract—it must copy shapes. But once demonstrations are labeled with skill names, an LLM can reason about which skills apply. Here is the causal chain:

First, decomposing demonstrations into named skills makes the knowledge explicit and transferable. Instead of asking "does this trajectory look like the new task?", the robot asks "do these skills match?" Skills are semantic units that reappear across different tasks: reaching, grasping, and releasing happen in cup placement, knife placement, and many other tasks. The skill label acts as a bridge.

Second, because skills are reusable, a planning agent can predict a skill sequence for an unseen task without ever seeing that task before. The planner knows the task goal (put knife on board) and predicts which skills are needed (Reach, Grasp, Move, Release) based on task structure, not memorized examples.

Third, once a skill sequence is predicted, the library retrieves demonstrations that contain those same skills. This retrieval is now problem-specific: only demonstrations relevant to the predicted sequence are included. The coverage-aware static library then fills in any missing skill transitions, ensuring the LLM has seen examples of every skill combination it will need to output.

Finally, the LLM reasons over skill-annotated demonstrations and outputs actions. Because the demonstrations show skill labels alongside actions, the LLM learns the mapping: when Reach is needed, output these arm motions; when Grasp is needed, output this gripper command. This mapping is much more learnable than raw trajectory shapes because the skill label acts as a semantic anchor for the action.

Math after the picture

The coverage weighting formula

First in words:

For each skill token in the planned sequence, weight it by the inverse of its frequency across all demonstrations, then greedily select static library examples to maximize the weight of covered transitions.

Then the compact form:

coverage_weight = sum_t IDF(t) * is_covered(t, dynamic_library) + lambda * sum_missing missing_token_weight(t)

Every symbol:

coverage_weightthe total importance of covered skill transitions
IDF(t)inverse document frequency of skill token t; rare skills get higher weight
is_covered(t, dynamic_library)1 if skill t appears in retrieved examples, 0 otherwise
lambdaweight for filling gaps; higher lambda prioritizes completeness
missing_token_weight(t)the importance of skill token t if not yet covered
A tiny worked example
Planned task needs skills: Reach (common), Grasp (common), Move (rare), Release (common).
IDF values: Reach = 1.0, Grasp = 1.0, Move = 4.0, Release = 1.0 (Move is rarer, so higher IDF).
Dynamic library has Reach-Grasp-Release but not Move. Covered weight = 1.0 + 1.0 + 0 + 1.0 = 3.0.
Missing = Move with weight 4.0. With lambda = 2.0, gap penalty = 2.0 * 4.0 = 8.0.
Total coverage_weight = 3.0 + 8.0 = 11.0. Static library adds a Move example, raising is_covered(Move) to 1, final = 1.0 + 1.0 + 4.0 + 1.0 = 7.0.

The formula ensures that both common skills and rare skill transitions are represented in the demonstration set, balancing task relevance with coverage completeness.

What can go wrong

What can go wrong

Skill labels are wrong or ambiguous. If the atomic skills are labeled incorrectly (e.g., a Reach when it is actually a Push), the LLM learns wrong associations. The quality of decomposition is bottleneck.
Skill coverage is incomplete. If the static library is too small or biased toward common skills, rare but necessary transitions (e.g., a Release-then-Reach sequence) may not be represented. The LLM then has no example to learn from.
Planning agent fails to predict the right skill sequence. If the planner predicts skills that do not apply to the unseen task, even perfect coverage of those skills will not help, because the LLM will combine those incorrect skills and generate actions for the wrong sequence of moves. The approach depends on the planner understanding task structure.
Visual similarity ranking is unreliable. The dynamic library retrieves based on visual similarity (how the scene looks), but visual similarity does not guarantee task relevance. A scene that looks similar may require different manipulation.
Done right. When skill labels are clean, the planning agent is trained on diverse tasks, the library is comprehensive, and visual encoding is accurate, the method achieves strong zero-shot cross-task transfer by reasoning over reusable, composable skills.
What a runnable demo should prove

What a runnable demo should prove

A demo should take three unseen manipulation tasks (e.g., place knife on board, place spoon in cup, place block in bin) that were never in the training demonstrations. For each task: (1) show the task instruction and scene, (2) display the planner's predicted skill sequence, (3) visualize the retrieved demonstrations with skill labels, (4) show the gap-filling step (which static library examples were added), (5) run the LLM to generate actions, and (6) execute those actions on a simulated or real robot and measure success (did the object end up in the target location?).
