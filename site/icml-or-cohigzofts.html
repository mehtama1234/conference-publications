VenusBench-Mobile: Realistic Mobile Agent Evaluation

A new benchmark for mobile agents that uses real user tasks and breaks down failures into specific skill gaps instead of just counting pass-or-fail.

Paper explainersAll themesAgents & Tool Use

Mobile agents today are tested on benchmarks that are too narrow and too easy. They measure agents on simple app-specific tasks, which hides the real problems: agents crash and fail when they encounter the messy, unpredictable world of actual phone use. This paper fixes that by building a benchmark that reflects real user behavior, and then diagnosing exactly what each agent does wrong at the level of single actions, not just final success.

Zero assumption version

Old benchmarks hide the real gaps

Today's benchmarks for mobile agents test on tasks that are too simple and too similar. One benchmark might have an agent open ten different apps and perform one kind of action in each (tap, type, scroll). Another tests only on a single app, so it never sees how agents break when switching between Gmail, maps, and photos in real use.

A naive approach is to count: did the agent succeed yes-or-no on the task? But this misses the insight: three agents might all fail a task, but one fails because it cannot read the screen correctly, one fails because it forgets what it was doing mid-task, and one fails because it pokes the wrong button. If you only count successes, you learn nothing about how to fix any of them.

The real world is also unstable. The same app looks slightly different on different phone models, after updates, or when a different notification is on screen. Agents that look perfect in testing crumble in real conditions.

The method in one sentence. Build a benchmark with real user tasks and broken-down diagnostics.

The algorithm as a flow

What it actually does

Define real tasks

Design scenarios from how actual users interact with phones, not app checklists.

Collect agent trajectories

Run agents on these tasks and record every action and screen observation.

Annotate action outcomes

For each action, mark whether it succeeded: perception correct, memory correct, choice correct.

Compute capability scores

Aggregate per-action correctness into scores for perception, memory, decision-making.

Test under variations

Run same agents on different phones and after system updates; measure brittleness.

What the paper changes

What the paper changes

The paper changes how we score agent behavior. Instead of one number per task (success or failure), it assigns a score to every single action the agent takes. Did the agent perceive the screen correctly? Did it remember what the user asked? Did it choose the right button to press?

the object it moves  =  Action-level correctness scores
The hidden quantity

The hidden quantities: three skill gaps

measured quantity  =  Perception score, Memory score, Decision score

The paper measures three specific abilities. Perception is whether the agent reads the screen correctly: does it know which buttons are where, what text is visible, what state the app is in. Memory is whether the agent remembers what the user asked and tracks progress: if I told you to find a contact and call them, does the agent still remember the name three screens later. Decision is whether the agent picks the right action: given what it perceives and remembers, does it do the sensible thing next, or does it tap the wrong button.

Most mobile agent papers lump all three together in one pass-or-fail score. This paper measures each separately by having human annotators watch the agent's trajectory and label each action as correct or incorrect at each of these three levels. If an agent sees the screen correctly but chooses the wrong button, perception scores high and decision scores low.

Why it works

Why breaking down failures actually helps

When an agent fails a task in an old benchmark, you know it failed but not why. Did the model have bad vision? Does it not understand sequences? Did the developers train it wrong? These are completely different problems, but the benchmark treats them the same.

This paper fixes that by annotating every action, which creates a diagnostic signal. If an agent's perception score is low but its decision score is high, the team should invest in better screen-reading, because the agent's choices are sound but based on a misreading of what is on the screen—showing the model higher-resolution images or clearer text extraction directly addresses that gap. If memory is the bottleneck, the answer is different: add a memory buffer, change the context window, or use retrieval to refetch old instructions, because the agent forgets mid-task and needs a way to hold onto earlier context. The diagnosis points to the real fix.

Testing under real-world variations (different phone sizes, app updates, system notifications) reveals whether an agent breaks when the world changes slightly. An agent that passes the clean-room benchmark but fails on real phones is memorizing surface patterns, not learning the underlying task. This benchmark makes that brittleness visible.

Math after the picture

Capability score formula

First in words:

Perception score is the fraction of actions where the agent correctly described what was on screen. Memory score is the fraction of actions where the agent accurately referenced earlier steps or context. Decision score is the fraction of actions where the agent chose the sensible next step.

Then the compact form:

capability_score = (count_actions_correct) / (total_actions) per capability type

Every symbol:

count_actions_correctnumber of actions where agent was correct on this capability
total_actionstotal number of actions taken by the agent on this task
capability_scorescore between 0 and 1 for perception, memory, or decision
A tiny worked example
Task: send a text message. Agent takes 6 actions: read contacts, find person, compose message, type text, review, hit send.
Perception: correct on 5 actions (misses a typo on screen) = 5/6 = 0.83
Memory: correct on 6 actions (remembers the name and message content throughout) = 6/6 = 1.0
Decision: correct on 5 actions (taps the wrong contact once, but recovers) = 5/6 = 0.83
Old benchmark: task succeeds = 1/1 = 100%. New benchmark reveals the perception gap.

Each action is scored independently on the three capabilities, revealing exactly where an agent's weaknesses live.

What can go wrong

What can go wrong

Annotation disagreement. When humans disagree on whether an action was correct, the scores become noisy. This benchmark requires careful inter-rater training, or the diagnostics are unreliable. The paper addresses this by using multiple annotators and consensus.
Gaming the system. If you train an agent specifically to maximize the benchmark's three capability scores, it might become good at the narrow set of tasks here but still fail on new apps and workflows not in the benchmark. Surviving in the wild requires testing on held-out scenarios the benchmark creators did not anticipate.
Annotation costs. Assigning a correctness label to every action is labor-intensive. Large-scale deployment of this benchmark requires either careful automation (which can itself be brittle) or sustained annotation budgets.
Done right. When annotators agree and are well-trained on the three-capability framework, the scores reliably point to the actual agent bottleneck. Developers can then invest in the right direction: if perception is weak, use better vision models because the bottleneck is in reading the screen; if memory is weak, add a retrieval buffer because the bottleneck is in tracking context; if decision-making is weak, use better training data because the bottleneck is in choosing the next action given correct information. Each diagnosis maps to a concrete structural fix.
What a runnable demo should prove

What a runnable demo should prove

The demo takes two mobile agents (e.g., one trained on GPT-4V and one on Claude Vision), runs them on a small set of real phone tasks (open a contact, send a message, search the web, navigate to a location), and outputs their three capability scores side by side. The demo should make visible that one agent's failures concentrate in perception and the other's in memory.

perception_score = (actions_where_agent_read_screen_correctly) / (total_actions)

The reader should see that an agent's overall pass-or-fail hides very different problems, and this breakdown tells you exactly which skill to invest in first.
