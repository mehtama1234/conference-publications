MobileRL: Online Agentic Reinforcement Learning for Mobile GUI Agents

Train mobile app agents faster by feeding them easier tasks first and harder ones later, reshaping rewards to match task length.

Paper explainersAll themesAgents & Tool Use

Mobile phone apps have hundreds of screens and buttons that look different each time you visit. Teaching a computer to use them is hard because some tasks are trivial while others are extremely hard, and sampling billions of example interactions is slow. This paper introduces MobileRL, a system that teaches agents more efficiently by controlling which tasks to learn from and how to measure progress fairly.

Zero assumption version

Why normal training breaks for mobile agents

Imagine teaching a person to cook by randomly assigning recipes: one day boiling water, the next day a Michelin-star dish. They will master the easy tasks and give up on the hard ones. Mobile app tasks have the same heavy-tailed distribution — some require one tap, others require a chain of ten interactions across different screens.

A naive trainer samples random tasks and shows the agent the outcome: did it succeed or fail? But this misses a critical signal: for an easy task that takes 2 steps, success on step 2 is progress. For a hard task that takes 8 steps, success on step 2 is barely anything. The reward signal does not account for how far through the task you got.

In one sentence. The paper teaches mobile agents by serving easier tasks first, filtering which failures to learn from, and adjusting rewards to match task length.

The algorithm as a flow

What it actually does

Sort tasks by difficulty

Measure how many steps a simple policy needs to finish each task, then order from easiest to hardest.

Feed tasks in curriculum order

Start on easy tasks so the agent learns basic skills first, then gradually mix in harder ones because learned skills transfer to complex chains.

Filter which failures to learn from

When a task fails, only learn from it if it represents realistic difficulty for the agent's level, not outlier catastrophes.

Reward progress, not just endpoints

Give reward per step completed, so a 2-step task and an 8-step task both feel like steady progress.

Update the model end-to-end

Use standard reinforcement learning to adjust how the agent picks actions, guided by shaped rewards and filtered examples.

What the paper changes

What the paper changes

The paper modifies two things: which training examples the agent sees (easier tasks upfront), and how rewards are computed (per-step rather than all-or-nothing at the end).

the object it moves  =  Training task order and reward signals
The hidden quantity

The hidden quantity: task-step contribution

measured quantity  =  Steps completed relative to task length

The paper measures a quantity never explicitly named in the abstract but critical to the mechanism: how many steps of a task the agent completed before stopping or succeeding. For a 2-step task, completing step 1 is 50% progress. For an 8-step task, step 1 is 12.5% progress.

ADAGRPO estimates this quantity by having a reference policy (a baseline agent) solve each task once, recording how many steps it takes. Then every attempt by the learning agent is scored by steps completed divided by total steps, independent of success or failure. This turns all tasks into the same signal: incremental progress.

Why it works

Why this works: three aligned signals

The mechanism has three parts, and they all push in the same direction. First, curriculum learning works because neural networks learn faster when patterns build on each other. By ordering tasks from easy to hard, the agent learns reliable behaviors on simple tasks, then uses those as building blocks for complex sequences. An agent that can reliably tap the right button will do it even in a 10-step chain.

Second, filtering failures works because not all failures are instructive. If the agent crashes because it was thrown into an impossible task, that example teaches nothing useful — it just adds noise. By filtering to only failures the agent was ready to learn from (same difficulty as recent successes), each negative example clarifies which action to avoid in realistic situations.

Third, rewards per step work because they align the feedback signal with what the agent can actually control. On a 2-step task, every action the agent takes moves it toward the goal, so per-step reward is honest. On an 8-step task, the same-sized reward per step means the agent does not need to predict the entire chain perfectly to get useful feedback — it gets credit just for making progress. This is critical because predicting perfect sequences is exponentially harder as length increases, but predicting one good step is always learnable.

Math after the picture

The reward-shaping equation

First in words:

adjusted loss equals base reinforcement learning loss, minus a scaled reward that grows with each step completed, weighted by how important each weight is for the current task

Then the compact form:

L = L_GRPO - alpha * sum_t (step_t / max_steps) * I_t

Every symbol:

Ltotal loss (what we minimize)
L_GRPObase GRPO loss (a reinforcement learning algorithm)
alphahow much we emphasize per-step progress (a strength knob)
step_twhich step the agent is on (1, 2, 3, ...)
max_stepstotal steps in the reference path for this task
I_timportance weight for step t (from curriculum filtering)
A tiny worked example
Task A (2 steps): agent completes step 1, then step 2. Reward = alpha * (1/2 + 2/2) = alpha * 1.5.
Task B (8 steps): agent completes steps 1-4, then fails. Reward = alpha * (1/8 + 2/8 + 3/8 + 4/8) = alpha * 1.25.
Task A reward is higher (1.5 > 1.25) even though Task B went further, because Task B has much longer max_steps. On Task A, 2 steps is everything. On Task B, 4 steps is only half.

The equation says: every step the agent completes is credit, but divided by how long the task should be, so all tasks feel equally rewarding to attempt.

What can go wrong

What can go wrong

Task difficulty estimation breaks. If the reference policy is too weak or too strong, max_steps is wrong, and reward shaping distorts the signal. A slow reference makes all tasks look short; a fast one makes all tasks look long.
Curriculum too steep, then too flat. If tasks are sorted perfectly, the agent gets bored early and plateaus. If sorted randomly, it crashes on hard tasks immediately. The transition speed matters.
Filtering removes instructive failures. If the agent filters too aggressively, it misses edge cases. If it filters too loosely, it drowns in noise from impossible tasks.
Done right. The system estimates task length with a fast approximate policy, gradually ramps difficulty as success rate rises, and learns from failures just at the edge of the agent's current skill.
What a runnable demo should prove

What a runnable demo should prove

Build a simplified mobile agent on 10 synthetic app tasks of varying length (2 to 10 steps). Train one version with random task order and normal reward (success=+1, failure=0). Train a second version with the same tasks sorted by length and per-step reward. Measure success rate on a held-out test set for both easy and hard tasks after 1000 training steps.

success_rate = (tasks_completed_correctly / total_test_tasks) * 100; hard_task_gain = success_rate_hard_MobileRL - success_rate_hard_naive

The naive agent should excel on short tasks and fail on long ones. MobileRL should show strong success on both, proving that curriculum and per-step rewards truly unlock learning on long-horizon tasks.
