LLM-Guided Loop Bound Generation for Program Termination Verification

Use a language model to propose loop bounds, then keep only the ones a formal checker can prove and use violation feedback to refine the next guess.

Paper explainersAll themesOther

Termination verification asks whether every execution of a program eventually stops. For many programs the hard step is finding a loop bound, meaning a proof that each loop can only repeat a finite number of times from any reachable state. That search is hard because the proof object must match the program's control flow, numeric updates, and branching structure closely. LIFT treats the language model as a candidate generator rather than as a trusted prover. The model reads the program and proposes loop bounds. A sound checker then tries to verify those proposals. If a proposal fails, the tool extracts why it failed and feeds that violation back into the next prompt. The method improves coverage because the language model explores proof templates quickly, while soundness is preserved because only checker-approved bounds count as proofs.

Zero assumption version

Termination proofs need the right bound, not only raw search power

To prove that a loop terminates, a verifier often needs a numeric measure that keeps moving downward and cannot decrease forever. A loop bound is a closely related object because it states how many iterations remain or gives an upper bound that shrinks as the loop runs.

The search space is large. Two loops that look similar at the surface may need different symbolic expressions because one branches on one variable while another branches on a pair of coupled variables. Traditional tools rely on fixed templates or exhaustive search, so they can miss bounds that a human would notice from the code structure.

The method in one sentence. Let the language model guess candidate bounds from program structure, but trust only the formal validator, and use validator failures as targeted feedback for the next guess.

The algorithm as a flow

What it actually does

Parse a target loop

Extract the loop condition, variable updates, and control-flow context because candidate bounds must refer to the actual program state.

Ask the language model for a bound

Generate one or more candidate loop bounds from the code because the model can search symbolic patterns faster than a fixed template library.

Run sound validation

Check that the candidate is initialized correctly, stays valid across iterations, and decreases as the loop executes because those facts turn a guess into a proof.

Extract a violation reason

If validation fails, identify the broken obligation or counterexample pattern so the next prompt targets the real defect.

Repeat until proof or exhaustion

Keep the guess-and-check loop going because each failed bound narrows the search toward a structure the checker can certify.

What the paper changes

What the paper changes

The paper changes the source of candidate loop bounds. Instead of relying only on hand-built bound templates, it uses a language model to draft candidates while leaving certification to the formal backend.

the object it moves  =  the generator of candidate termination arguments
The hidden quantity

Remaining-iterations measure

measured quantity  =  remaining-iterations measure (a quantity that should start finite and keep shrinking until the loop exits)

Every successful termination proof hides a measure of progress. That measure may be one variable, a sum of several variables, or a branch-sensitive expression. The verifier never observes it directly in the source code. It has to synthesize it.

A good candidate bound must fit all paths through the loop. It is not enough for the bound to decrease on the common path. It must also stay nonnegative and decrease or advance properly under every branch that is actually reachable.

Why it works

Why guess-and-check with violation feedback works

A language model is useful here because bound synthesis is partly a code-understanding problem. The model can notice that a loop variable is counting down, that two variables move in lockstep, or that a branch resets one term and therefore requires a conditional bound. A fixed template engine often misses that structure because it only searches a narrow symbolic family.

The formal validator is the safety wall. A candidate bound can look plausible in prose and still fail on one branch, one starting state, or one preservation condition. LIFT keeps soundness because the checker must discharge every obligation before the tool reports termination. This division of labor matters because the language model is good at proposing and the verifier is good at rejecting false proposals.

Violation analysis makes the loop closed instead of blind. When a candidate fails, the system learns whether the defect was missing decrease, missing nonnegativity, or a branch case the proposal ignored. The next prompt is therefore better focused. Performance improves because the search does not restart from scratch after each failed guess.

Math after the picture

What the checker must establish

First in words:

a candidate loop bound is accepted only if it starts finite on loop entry and decreases along every loop iteration until the guard becomes false

Then the compact form:

valid_bound if entry_ok and preserved_nonnegative and strictly_decreases_on_each_iteration

Every symbol:

entry_okthe candidate gives a finite nonnegative value whenever the loop is entered
preserved_nonnegativethe value never drops below zero while the loop still continues
strictly_decreases_on_each_iterationevery taken loop step lowers the candidate enough to rule out infinite execution
A tiny worked example
Consider a loop that decrements x by 1 while x is positive.
A candidate bound is x.
At entry, x is nonnegative whenever the loop guard is true.
After one iteration, x becomes x minus 1, so the bound decreases by 1.
Because the value cannot decrease forever while staying nonnegative, the loop must stop.

Real benchmarks need more involved bounds, but every accepted candidate must satisfy the same proof pattern.

What can go wrong

What can go wrong

The candidate space is still too narrow. If the required proof needs a structure the prompt or verifier cannot express, repeated guessing will stall because every proposal lives in the wrong family.
Violation feedback is too coarse. If the checker only says that the candidate failed without identifying the failing condition, the next prompt gains little direction and the search becomes inefficient.
Program semantics are modeled incompletely. If integer overflow, unreachable branches, or environment assumptions are handled badly, the checker may reject good candidates or accept bounds for the wrong model.
Done right. The design is strongest when the formal backend can explain failures clearly, because those explanations give the language model a structured repair target.
What a runnable demo should prove

What a runnable demo should prove

Build a toy verifier for small integer loops. Let a language model or a scripted stand-in propose candidate bounds such as one variable, a sum of two variables, or a conditional expression. Then write a checker that tests entry validity, nonnegativity, and decrease over all reachable small states.

The demo should show the full loop: failed guesses receive branch-level feedback, repaired guesses improve because the next proposal repairs a named proof defect, and only checker-approved candidates are counted as proofs. That demonstrates the actual point of LIFT, which is guided synthesis under formal control.

solve_rate = proved_loops / total_loops ; refinement_gain = solved_after_feedback - solved_without_feedback

A convincing demo shows more proved loops with feedback than without feedback, while keeping the count of unsound proofs at zero.
