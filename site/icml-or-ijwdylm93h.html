Recovering Policy-Induced Errors: Benchmarking and Trajectory Synthesis for Robust GUI Agents

RoTS trains GUI agents to recover from their own mistakes by synthesizing error-and-recovery trajectories instead of training only on clean successful runs.

Paper explainersAll themesOther

A GUI agent usually looks good when every action goes right. Real deployments fail in a harsher setting because one wrong GUI action changes the later screen state, so later steps are now chosen from the wrong context: the agent clicks the wrong element, skips a required step, fills in a bad value, or drifts into the wrong page and must recover without outside help. This paper addresses that gap in two places. "GUI-RobustEval" measures recovery across many concrete error types, and RoTS builds a large training set of failure-and-repair trajectories. The main idea is direct: do not train only on ideal traces. Train on traces where the policy has already made a mistake, then show how to detect the mistake, locate it, and get back on track.

Zero assumption version

Why strong GUI agents still break in long tasks

A long GUI task compounds small mistakes. One wrong click can change the whole screen, hide the intended control, or corrupt later form inputs. If the training data contains mostly successful expert-like trajectories, the model learns what to do from clean states but not what to do after it has already gone off course.

That means evaluation can also be misleading. A benchmark that starts every episode from a clean state mainly measures plan execution. It does not test whether the agent can notice that its own action was wrong, reason about the resulting state, and choose a repair step.

The missing skill is recovery. A GUI agent must learn from broken states as well as clean ones, because policy-induced errors are part of the set of states it will face at deployment time.

The algorithm as a flow

What it actually does

Build a recovery benchmark

Create executable test cases that inject concrete error modes such as wrong input values, missing steps, and wrong UI element choices.

Expand exploration and recovery together

Grow a search tree that includes both normal progress branches and branches caused by mistakes.

Score fragility

Identify states where the task is easy to derail, because those states are the best places to synthesize recovery data.

Use neighbor experience for recovery

Compare nearby branches in the tree to localize where the mistake happened and what successful branches did differently.

Fine-tune recovery-aware models

Train on the synthesized dataset so the agent learns both progress actions and repair actions.

What the paper changes

What the paper actually changes

The paper changes the mix of trajectories presented to the GUI agent. Instead of training mainly on success-only trajectories, it generates trajectories that include policy-induced errors, error localization, reflective advice, and concrete recovery steps.

the object it moves  =  training trajectory distribution: from clean-only runs to error-and-recovery runs
The hidden quantity

The hidden quantity: fragility of a GUI state

measured quantity  =  How easily a partially completed task can be derailed

Not every step in a GUI task is equally dangerous. Some states are forgiving: a wrong click is easy to undo. Other states are fragile: one bad field entry or one skipped confirmation step can force a long detour or total failure. RoTS tries to find those fragile states because they are where recovery training data is most informative.

The paper describes fragility-driven exploration using step-level success information. Intuitively, a state is fragile when nearby continuations show high variation in outcome. That means the branch point is a useful place to study what separates a recoverable mistake from an unrecoverable one.

Why it works

Why synthesized recovery branches teach something clean traces cannot

A clean trace teaches only forward progress from valid states. It does not teach error diagnosis. Recovery traces do, because they pair a broken state with evidence about how that state differs from a nearby successful branch. RoTS uses the search tree for this comparison. Neighbor branches share a long prefix and differ near the failure point, so the difference is localized enough to support useful reflection.

Explore-recovery co-expansion matters because recovery cannot be bolted on after exploration is complete. The system needs to discover new failure modes while it is still broadening task coverage. Otherwise the dataset will overrepresent a small family of mistakes and underrepresent the long-horizon errors that appear in real use.

Experience-informed recovery matters because a raw broken state does not explain itself. The method uses neighboring successful and failed branches to infer where the trajectory first diverged and to generate advice-conditioned repair steps. That turns a vague failure into a specific training example: here is the likely mistake, here is the state it produced, and here is the action sequence that repairs it.

Math after the picture

The quantity to watch

First in words:

A natural score for a node is its fragility: low average step success after that node means a mistake there is costly and worth modeling.

Then the compact form:

fragility(node) = 1 - average_step_success_after(node)

Every symbol:

average_step_success_after(node)the mean success rate of later steps across rollouts that pass through the node
fragility(node)higher values mean the task is easier to derail from that state
A tiny worked example
Suppose 20 rollouts pass through a payment form state.
After that state, the later steps succeed 8 times and fail 12 times.
Average step success after the node is 8/20 = 0.40.
Fragility is 1 - 0.40 = 0.60.
A node with fragility 0.60 is a good place to synthesize recovery data because mistakes there often cascade into failure.

The exact scoring details in the paper are richer, but this captures the main idea: prioritize branches where local errors have large downstream cost.

What can go wrong

What can go wrong

Synthetic errors miss real deployment errors. If the generated failure modes are too narrow, the model may learn scripted repairs that do not transfer, because the training tree does not cover the broken states users actually trigger.
Neighbor branches can mislocalize the mistake. Two nearby trajectories may diverge for more than one reason. If the system blames the wrong step, the generated advice and repair sequence can teach an incorrect diagnosis.
Recovery can trade off with speed. A model trained to be cautious after errors may add extra checks or backtracking, because repair-aware behavior often prefers confirmation over aggressive progress.
Done right. The method is strongest when the benchmark covers diverse policy-induced errors and the synthesis tree reaches many fragile states, because then the repair policy is shaped by realistic failure distributions.
What a runnable demo should prove

What a runnable demo should prove

Build a small GUI environment with branching tasks such as booking, file handling, or settings configuration. Inject several policy-induced errors, including wrong button clicks, skipped steps, and incorrect field values. Train one agent on clean trajectories only and another on clean plus synthesized recovery trajectories. Measure final task success and a dedicated recovery score from broken starting states.

recovery_rate = recovered_tasks / broken_start_tasks

The demo should show that the recovery-trained agent succeeds more often from broken states because it has learned to diagnose and repair its own mistakes.
