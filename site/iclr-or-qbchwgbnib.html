From Reproduction to Replication: Evaluating Research Agents with Progressive Code Masking

AutoExperiment measures whether a research agent can rebuild missing experiment code as the starting codebase becomes less complete, so we can see the gap between easy reruns and true reimplementation.

Paper explainersAll themesAgents & Tool Use

Many claims about research agents come from settings where most of the original code already exists. In that regime, the agent may only need to launch scripts, edit a small function, or recover a broken dependency. That is useful, but it is not the same as reading a paper and rebuilding the method from sparse code. AutoExperiment creates a benchmark that moves smoothly between those two extremes by masking more and more key functions, then asking the agent to restore the missing pieces and run the experiment.

Zero assumption version

The problem: current evaluations blur rerunning code with rebuilding ideas

If a paper's repository is nearly complete, an agent can appear capable by wiring together existing components and handling small environment issues. That tests operational skill, but it does not test whether the agent can reconstruct a scientific method from the paper when core logic is missing.

The field needs a benchmark with adjustable difficulty. A benchmark at only one difficulty level cannot tell whether an agent fails because it cannot read the paper, cannot navigate the codebase, or simply cannot implement missing logic once the scaffolding disappears.

The core idea in one sentence. Mask an increasing number of key functions in a research codebase and ask the agent to restore them, so the benchmark moves from simple reruns toward genuine replication.

The algorithm as a flow

What it actually does

Step 1: Choose a paper and its codebase

Each benchmark item starts from a real machine learning project with a paper, source code, and a command that should reproduce the result.

Step 2: Mask selected key functions

The benchmark removes the bodies of chosen functions while keeping the rest of the repository, so the agent still has naming, call structure, and setup information.

Step 3: Give the agent a sandboxed run environment

The agent can inspect files, write code, execute commands, and debug the run, which matters because experiment implementation is an interactive task.

Step 4: Vary the number of masked functions

The difficulty knob is the count of missing functions. Small counts test near-reproduction, while large counts test whether the agent can reconstruct more of the method from the paper.

Step 5: Score by successful reproduction

The agent succeeds only if the restored code runs and reproduces the target outcome closely enough, so both implementation and execution matter.

What the paper changes

What changes: the benchmark now contains a controllable gap

The key object is the masked codebase. It preserves enough surrounding structure that the task remains grounded in a real project, yet it introduces a known implementation gap whose size can be increased. That makes difficulty measurable because the benchmark can ask how agent performance changes as the missing scientific content grows.

the object it moves  =  the partially masked research repository
The hidden quantity

The hidden quantity: reconstruction burden

measured quantity  =  How much scientific logic the agent must recover from sparse clues

The main hidden quantity is not just the number of missing functions. Two masked functions can be easy if they are boilerplate, while one masked function can be hard if it contains the heart of the method. What matters is how much method-specific reasoning the agent must reconstruct from the paper, neighboring code, and failed runs.

Progressive masking is a useful proxy because larger masked sets usually remove more of the unique logic. The performance curve across masking levels reveals how quickly an agent collapses as the reconstruction burden rises.

Why it works

Why it works: difficulty increases along one clear axis

The method works because it isolates a single axis of capability: how much missing implementation an agent can restore. The agent always receives the same types of resources, namely the paper, the partial codebase, and an executable environment. The changing factor is how much of the original implementation is absent.

That design separates several common skills. When masking is light, success depends more on code navigation and execution. When masking is heavy, success depends more on extracting method details from the paper and turning them into working code. The benchmark therefore shows not only whether an agent succeeds, but where its capability drops.

Math after the picture

The benchmark curve: success as a function of masked functions

First in words:

A simple summary is to measure success rate at each masking level. As the number of removed functions grows, success usually falls. The shape of that drop tells you how rapidly the agent loses the ability to reconstruct scientific code.

Then the compact form:

success_at_n = solved_tasks_with_n_masked / total_tasks_with_n_masked

Every symbol:

nthe number of masked functions in the task
solved_tasks_with_n_maskedhow many tasks the agent completed at masking level n
total_tasks_with_n_maskedthe total number of tasks evaluated at that masking level
success_at_nthe success rate at masking level n
A tiny worked example
Suppose an agent solves 18 of 20 tasks when one function is masked.
Then success_at_1 = 18 / 20 = 0.90.
Suppose the same agent solves 6 of 20 tasks when five functions are masked.
Then success_at_5 = 6 / 20 = 0.30.
The steep drop shows that the agent can rerun and patch existing code more easily than it can reconstruct missing scientific logic.

The paper reports this kind of degradation and shows that interactive agents usually beat fixed evaluation setups because they can debug and revise after seeing runtime behavior.

What can go wrong

What can go wrong

Masked functions are not equally important. A count-based difficulty scale is imperfect because one missing helper is not equivalent to one missing core method. Careful task construction still matters.
Execution issues can dominate the score. An agent may understand the method but fail on environment details. That is part of real research execution, but it can blur pure implementation skill.
Benchmark leakage can inflate results. If an agent has already seen the exact repository or paper, the task stops measuring reconstruction and starts measuring recall.
Done right: the curve reveals capability boundaries. The benchmark succeeds when it shows where an agent moves from easy reruns into harder scientific reconstruction, because that boundary is what current evaluations often hide.
What a runnable demo should prove

What a runnable demo should prove

Take a small public research repository and define three masking levels: one missing helper, three missing method functions, and six missing method functions. Give an agent the paper, the partial repository, and a sandbox where it can run the project and inspect failures. Record success rate and number of debug cycles at each level. The demo should show that the benchmark distinguishes between agents that can mainly rerun code and agents that can recover missing scientific content, because success should fall as the reconstruction burden rises.

Capability drop = success_at_low_masking - success_at_high_masking on the same task family.

The demo must make the reproduction-to-replication transition visible as a measurable curve, not as a single pass-or-fail score.
