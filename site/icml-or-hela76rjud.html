TOM-SWE: User Mental Modeling For Software Engineering Agents

Pair a coding agent with a second smaller agent that tracks the user's goals, constraints, and preferences so the main agent stays aligned across ambiguous and stateful tasks.

Paper explainersAll themesAgents & Tool Use

A coding agent can read files, run tests, and edit code, yet still miss what the user actually wants. The failure often appears when instructions are incomplete, preferences were stated earlier, or the task depends on ongoing project context. This paper adds a dedicated user-modeling partner to the coding agent. The partner keeps a lightweight picture of the user's intent and feeds guidance back to the main agent so that task decisions stay aligned across turns.

Why coding agents lose the user's intent

Software tasks are often underspecified. A user may say to fix a bug, but the real goal can include preserving a particular interface, avoiding risky refactors, or matching the style of the rest of the codebase. A strong coding agent can still miss those constraints because they are spread across earlier conversation turns or implied by past choices.

The problem becomes worse in stateful work. As the interaction continues over hours or days, the agent must remember what the user prefers, what tradeoffs were rejected, and what project conventions matter. If all of that is left inside one overloaded agent context, user modeling competes with code reasoning for limited working space.

The paper's move in one sentence. Split the job into a main coding agent and a small partner that maintains a running model of the user's goals and preferences, then feed that model back into planning and action selection.

The algorithm as a flow

What it actually does

Read the instruction history

Collect the user's requests, corrections, and preferences across the conversation.

Infer a compact user state

The partner agent summarizes goals, constraints, preferences, and unresolved ambiguities.

Store the user state over time

Persist that summary so that later turns can reuse it without rebuilding it from scratch.

Guide the coding agent

Feed the user-state summary into planning and action selection before edits, commands, and final responses.

Update after new feedback

When the user corrects or refines the request, revise the user model so that later steps stay aligned.

What the paper changes

What the paper changes

The paper changes how a coding agent represents the user. Instead of treating the conversation only as extra prompt text, it maintains an explicit model of the user's current goals, constraints, and preferences.

The hidden quantity

The user's underlying intent

measured quantity  =  User intent state

The important hidden quantity is not the text of the latest instruction but the user's actual working intent. That state includes what outcome the user wants, which constraints they care about, and which tradeoffs they are likely to reject. A single message rarely contains all of that.

The paper estimates this hidden state from conversation history and earlier corrections. The second agent maintains it explicitly so that the main coding agent does not need to re-derive the user's preferences from scratch every time it chooses a plan.

Why it works

Why a second agent helps

Separating user modeling from code execution helps because the two jobs require different working habits. The coding agent must inspect files, tests, and commands, while the user-modeling partner must track intent across turns. When one component specializes in the second job, important user constraints are less likely to disappear during intense code work.

Persistent user state also helps because many software tasks are sequential. A user's earlier correction should shape later planning even if the current turn does not repeat it. The partner preserves that memory and presents it in a small actionable form so that the main agent can choose a plan that fits both the repository and the user's working style.

A simplified alignment score

First in words:

Score each candidate coding action by combining task progress with how well the action matches the maintained user intent state.

Then the compact form:

action_score = task_progress + alpha * intent_match - beta * constraint_violation

Every symbol:

action_scorevalue of one candidate coding action
task_progresshow much the action moves the software task forward
intent_matchhow well the action fits the stored user goals and preferences
constraint_violationhow much the action conflicts with user limits such as scope or interface stability
alphaweight on matching user intent
betapenalty on violating user constraints
A tiny worked example
Action A fixes the bug by changing a public interface the user wanted to keep stable: task_progress = 0.9, intent_match = 0.2, constraint_violation = 0.8.
With alpha = 0.6 and beta = 0.7, action_score_A = 0.9 + 0.6 * 0.2 - 0.7 * 0.8 = 0.46.
Action B fixes the bug with a narrower patch that preserves the interface: task_progress = 0.8, intent_match = 0.9, constraint_violation = 0.1.
action_score_B = 0.8 + 0.6 * 0.9 - 0.7 * 0.1 = 1.27.
The system prefers B because it balances technical progress with the user's stated constraints.

The paper uses a fuller dual-agent setup than this toy score, but the score captures the main idea: good technical work must also match the user's intent state.

What can go wrong

What can go wrong

The user model can drift. If the partner over-interprets a vague message, later actions may become misaligned because the stored preference state is wrong.
Old preferences can overpower new ones. Persistent memory can become stale if recent corrections are not weighted strongly enough.
Extra coordination adds complexity. Two agents can disagree or slow the workflow if the handoff between user modeling and action planning is not kept concise.
Done right. Update the user state aggressively after corrections, keep the summary compact, and expose uncertainty so that the main agent knows when to ask for clarification.
What a runnable demo should prove

What a runnable demo should prove

Build a coding-task benchmark with ambiguous requests and multi-turn revisions. Compare a standard coding agent against a two-part system where a small partner stores user goals, forbidden actions, and style preferences. Measure task completion, how often the final patch violates user constraints, and how often the agent must ask for clarification.

The demo should prove that explicit user modeling improves alignment because earlier constraints continue to influence later edits, especially on stateful tasks where the latest instruction alone is not enough.

constraint_violation_rate = violating_runs / total_runs ; alignment_gain = dual_agent_success - baseline_success
