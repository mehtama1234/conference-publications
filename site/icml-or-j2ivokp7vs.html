GeoMoLa: Geometry-Aware Motion Latents

A robot learns how to manipulate objects by predicting where 3D points move, not by memorizing what things look like.

Paper explainersAll themesRobotics & Control

Training robots to grasp and move objects requires learning compact motion patterns from video. Existing systems try to remember what objects look like as they move, but this fails when scenes change. GeoMoLa instead teaches robots to predict where points in 3D space actually move during grasping, which works the same way no matter what the scene looks like.

Why pixel memory fails for robot learning

A robot grasps a coffee mug and pushes it across a table. To learn this skill, a human shows the robot many videos of cup-pushing. Traditional systems watch these videos and try to predict what the next frame will look like—the exact colors and shapes. This teaches the system to recognize visual patterns.

But here is the trap: when the robot faces a new table with different lighting, or a different-colored cup in a different room, the learned pattern breaks. The pixel colors are different, the background is different, and the system freezes because it is trying to match visual memories, not understand the actual motion. A beginner robot engineer might say: let us just get more videos of all possible scenes. But that is impossibly expensive and still fails when you put the robot in front of an object it has never seen before.

The core problem: Teaching robots by having them predict what scenes will look like fails when scenes change, because the system learned to match visual patterns instead of understanding physical motion.

The algorithm as a flow

What it actually does

Step 1: Capture depth and color together

A camera on the robot captures one viewpoint showing both the 3D positions of objects and what they look like.

Step 2: Compress motion into discrete codes

The system learns a small set of reusable motion patterns, each one a code that stands for a specific physical transformation.

Step 3: Predict point cloud change, not pixel change

Instead of asking what pixels come next, the system predicts where the 3D points (sampled from the object surfaces) move to after a grasp.

Step 4: Force codes to predict actual motion, not fake it

This prediction forces the motion codes to capture how points truly move, because predicting pixel patterns could be faked without understanding actual motion.

Step 5: Apply codes to different objects and tables

The learned motion codes work on objects the robot has never seen before and tables with different lighting because they encode how things move, not what they look like.

What the paper changes

What changes: motion representation

The paper changes how robots learn to represent motion. Instead of encoding motion as a pattern of changing pixels, the system encodes motion as discrete motion codes that predict how 3D points move through space. Each code captures a specific physical transformation independent of visual appearance.

The hidden quantity

The hidden quantity: point movement accuracy

measured quantity  =  How accurately the motion code predicts where 3D points move

The paper measures something that existing systems ignore: whether the learned motion code can predict where points in 3D space actually move. When an object is grasped and pushed, the positions of points on its surface change in specific ways determined by physics. A good motion code should predict those position changes correctly, not just produce visually similar next frames.

The system estimates this by predicting point clouds—collections of 3D position coordinates sampled from object surfaces—before and after a manipulation. If the motion code learned to predict real motion, it predicts point movements that match physics. If it only learned pixel patterns, the predicted point positions will be wrong. This measure forces the motion codes to understand actual motion.

Why it works

Why it works: forcing codes to predict where points move, not pixel colors

Here is the core insight: predicting what pixels come next is easy to fake. A system could memorize visual patterns without understanding motion. But predicting where 3D points move is much harder to fake—it requires the system to understand how objects actually move through space.

When you train a system to predict point movements, it must learn that when a gripper closes around a mug and pushes it forward, the mug's points move forward along the table surface, not upward or backward. It must learn that the mug's shape stays roughly rigid. These constraints force the motion codes to capture how things actually move. Once a code learns a true motion (say, pushing a cylindrical object forward), it works on any cylindrical object in any scene, because the motion is defined by how things move in space, not what they look like. This is why a robot trained on one table successfully manipulates objects on a completely different table with different lighting and colors: the learned codes encode how things move, not the visual patterns of one specific scenario.

The system uses a clever trick: it predicts how point clouds change across time in four dimensions—three positions in space plus time. This forces the motion code to think about motion as how things move through space, not as a sequence of picture snapshots.

The prediction objective

First in words:

Error equals prediction error on point positions, summed over all points and all time steps. The motion code that minimizes this error learns to predict where things actually move.

Then the compact form:

L = sum_t sum_i ||p_predicted_ti - p_actual_ti||^2

Every symbol:

Ltotal loss (prediction error)
ttime step (frame number)
ipoint index
p_predicted_tiwhere the motion code predicts point i to be at time t
p_actual_tiwhere point i actually is at time t
||...||^2squared distance (how far the prediction was wrong)
A tiny worked example
A single grasp motion should move a point 2 units forward.
Predicted position: 2 units forward. Actual position: 2 units forward. Error: (2 - 2)^2 = 0.
For 10 such points over 5 frames, if predictions are perfect: total error = 0.
If a code predicts pixel changes instead of real motion: say it predicts 1 unit forward based on visual patterns. Actual: 2 units. Error per point: (1 - 2)^2 = 1. Over 10 points × 5 frames: total error = 50.
The code that predicts true motion (error = 0) wins. The code that just memorizes pixel patterns (error = 50) loses.

The error directly measures prediction accuracy on 3D positions, forcing the motion code to learn how things move rather than visual appearance.

What can go wrong

What can go wrong

Depth sensor noise or missing data. If the 3D point cloud is noisy or incomplete, the prediction target becomes unreliable, and the motion codes learn corrupted motion patterns. Robots need clean depth input for this approach.
Non-rigid deformation. The method assumes objects move rigidly (shape stays the same). For deformable objects like fabric or liquid, point cloud prediction becomes ambiguous, and the learned codes fail to generalize.
Multi-step planning. The approach learns discrete motion codes for single grasps. Complex multi-step manipulation sequences that require sequential planning are not directly addressed.
When done right. With clean depth input, rigid objects, and single-step manipulation in diverse environments, GeoMoLa learns motion codes that transfer perfectly across scenes and objects because the codes encode how things actually move in space.
What a runnable demo should prove

What a runnable demo should prove

Build a simple grasp-and-push simulation (use a physics engine like Bullet or MuJoCo with a table, a gripper, and a cylinder). Train the system on 50 videos of the gripper pushing the cylinder on one table with one lighting condition. Then test on: the same table with different lighting, a different table material, and a different-shaped object (a box instead of cylinder). Measure success as reaching the target position on the table.

Transfer success rate = (success_on_novel_table + success_on_novel_object) / 2

The key observation: a pixel-prediction baseline succeeds on the original table but fails when faced with different tables or objects (transfer rate near 20 percent). GeoMoLa succeeds on all three (transfer rate near 85 percent) because it learned motion as how things move in space, not visual memory.
