EvoMAS: Evolutionary Generation of Multi-Agent Systems

Instead of writing agent systems by hand, EvoMAS treats their entire configuration as a sequence to evolve, mutating and crossing over the best performers until it finds one that works.

Paper explainersAll themesAgents & Tool Use

Building multi-agent systems by hand is slow and fragile: pick which agents exist, what they do, how they talk, and what tools they use, then debug when it fails. EvoMAS flips this: it treats the whole system configuration as DNA. It starts with a pool of random configurations, runs each one on a task, keeps the ones that work, mutates and crosses them like genes, and repeats until the system handles edge cases and solves the problem.

Zero assumption version

Hand-designed agent systems are brittle

When you want a language model to solve a hard task, you can write a single prompt and run it once. But for complex problems — reasoning through logic, writing code, looking things up — one agent is not enough. You need multiple agents, each with different roles. One agent plans. One executes. One checks for bugs. One looks up documentation. You manually decide which agents exist, what each does, what they can ask each other, what tools they can call, and how to order the steps.

The brittle part: every time a new task comes along, or a tool fails in a new way, or you want to add another agent, you have to rewrite the whole system. There is no learning from the last design. A configuration that works on one task (code generation) often fails on another (reasoning). Existing automatic methods either try to generate the code for each agent (which breaks when the model hallucinates), or lock you into a rigid template (plan, execute, check: always the same shape, no matter the problem).

The naive approach. Manually design which agents exist, what they do, and how they talk to each other.

Score and select

What the paper changes

What the paper changes

EvoMAS does not hand-write individual agent prompts or code. Instead it treats the entire multi-agent system configuration as the thing to evolve. A configuration is a concrete, structured description: which agents exist (a list with names), what each agent's role and tools are, how they talk, whether they run in parallel or sequence, error-handling rules. This configuration is the DNA.

the object it moves  =  System configuration (agents, roles, tools, communication)
The hidden quantity

The hidden quantity: executability

measured quantity  =  Executability (did it crash?)

The core quantity EvoMAS measures is executability: did the system actually run without crashing or producing garbled output? Older methods (the ones that came before) generate agent code directly, and language models often generate code that does not work. EvoMAS sidesteps this by treating configuration as structured data, not code. The paper estimates executability by running each candidate system on the task and checking for runtime failures, parse errors, and tool-call syntax errors.

The paper also tracks execution traces: a log of every step each agent took, what it sent, what it received, whether it called a tool. This trace is fed back into the mutation process: if an agent got stuck or a tool call failed, the evolutionary algorithm learns to avoid that path for the next generation.

Why it works

Why it works: feedback-conditioned evolution

The reason EvoMAS finds good systems is that it breeds from success signals. When you run a configuration and it solves the task, that configuration and others similar to it are more likely to survive and have children (mutations and crossovers). When a configuration crashes, it is not selected. Over many rounds, the pool converges to systems that handle errors well and work on many task types.

Configuration changes are small and discrete (add or remove an agent, change its tools, reorder steps), so mutation is cheap and the search space is dense with working solutions. This is very different from generating agent code from scratch, where a single character error kills the whole thing. When EvoMAS mutates a configuration, even a bad mutation still runs and produces a failure signal, so the algorithm learns what not to do.

The execution trace feedback is what makes EvoMAS clever. Instead of just scoring pass or fail, EvoMAS records which agents got stuck, which tool calls failed, and which steps took too long. The next mutation is guided by this: if agent A timed out, the algorithm tries giving it fewer tasks or a different tool. If tool B was never called, it is removed. This is smarter than random mutation because it uses the actual failure reasons.

The evolution formula

First in words:

For each configuration in the pool, assign a score. The score is the task success (percentage of test cases solved) times a penalty for crashes. Then, select the top K configurations by score. For each selected config, create a mutant (random change to a single field: agent role, tool set, or step order) and a crossover (blend traits from two top configs). Repeat for N generations.

Then the compact form:

score(C) = success_rate(C) * max(0.1, 1 - crash_count(C) / total_steps(C))

Every symbol:

success_rate(C)fraction of test cases the config solved
crash_count(C)number of execution errors encountered
total_steps(C)total number of steps taken across all tests
score(C)final ranking score for config C
A tiny worked example
Config A: solved 8 out of 10 tests (success_rate = 0.8), crashed 1 time out of 50 steps (crash penalty = 1 - 1/50 = 0.98).
score(A) = 0.8 * 0.98 = 0.784
Config B: solved 5 out of 10 tests (success_rate = 0.5), crashed 10 times out of 50 steps (crash penalty = 1 - 10/50 = 0.8).
score(B) = 0.5 * 0.8 = 0.4
Config A ranks much higher. The next round selects A, B, and similar configs to mutate and breed.

The score combines task performance with error handling; execution traces guide which parts of the winning configs to preserve in mutation.

What can go wrong

What can go wrong

Evolution converges to a local optimum. If the initial pool is too narrow, the algorithm may get stuck in a mediocre region of configuration space and never explore good alternatives, because all mutations are small changes to already-similar configs. Solution: use a diverse initial pool and allow occasional random restarts, because diverse starting points explore different regions and random restarts inject wholly new configurations that are not constrained by the ancestry of the current pool.
Mutation breaks the system for many generations. If a configuration is very sensitive to small changes, most mutations fail, and evolution stalls. Solution: structure the configuration space so small changes do not break it (e.g., redundant agents, graceful error handling).
Execution traces are noisy or incomplete. If the traces do not capture the real failure reason, the algorithm may guide mutation in the wrong direction. Solution: log detailed traces and validate the feedback signal.
Done right. Maintain a diverse pool because different starting configs explore different regions of the configuration space. Allow exploration by occasionally accepting worse mutations, because exploration escapes local optima. Log detailed execution traces because mutation guided by real failure reasons is smarter than random. Validate on held-out test tasks because testing on different problems than evolution used reveals whether the system truly generalizes.
What a runnable demo should prove

What a runnable demo should prove

Build a simple multi-task benchmark (e.g., three reasoning problems, three code-generation problems, three retrieval problems). Start with a hand-written agent system that works well on one type (say, reasoning). Run EvoMAS for 10 generations on all three types mixed together. Measure whether the evolved system handles all three types better than the original hand-written one (because evolution selects for configs that succeed on all types, not just one), and whether any generation crashes (because configs that crash are not selected for breeding, the crash rate should drop across generations).

improvement = (evolved_accuracy - hand_designed_accuracy) / hand_designed_accuracy

The demo must show that evolution discovers a configuration that is both more accurate (because the fitness score rewards success) and handles errors better (fewer crashes; because the score penalizes crashes, evolution selects against crashing configs) across multiple task types, without manual redesign.
