EnterpriseOps-Gym: Environments and Evaluations for Stateful Agentic Planning and Tool Use in Enterprise Settings

EnterpriseOps-Gym tests whether an agent can plan across long enterprise workflows while tracking persistent state, access rules, and side effects.

Paper explainersAll themesAgents & Tool Use

Many agent benchmarks simplify work into isolated tasks with short contexts and forgiving consequences. Enterprise software is different. A support tool, an HR system, an IT queue, and a customer account database all keep state across time. One wrong action can change records, trigger approvals, or block later steps. An enterprise agent therefore has to do more than call tools. It has to plan across several steps, respect permissions, notice when a task is impossible, and recover from earlier mistakes without damaging the system. EnterpriseOps-Gym is built to measure that harder form of agent behavior.

Zero assumption version

Why simple tool benchmarks miss enterprise work

A single enterprise request often spans several systems. Resetting an employee account may require checking identity, inspecting earlier tickets, updating a user record, documenting the action, and avoiding fields that the current role is not allowed to edit. Benchmarks that treat each tool call as independent do not capture that structure because they remove the persistent state that later steps depend on.

The safety problem is also different in enterprise settings. An agent should sometimes refuse a task because the request is infeasible or violates policy. If a benchmark only rewards action, it misses whether the agent can detect that doing nothing is the correct move. That matters because an enterprise agent can cause real side effects when it edits records in the wrong order or with the wrong authority.

The paper's move in one sentence. Create a containerized enterprise world with many connected tools, persistent databases, and outcome-based checking so that agents are measured on long planning chains instead of isolated tool calls.

The algorithm as a flow

What it actually does

Step 1: Build a connected enterprise sandbox

Host databases and tools inside containers so that the benchmark can preserve realistic state across several actions.

Step 2: Curate expert tasks

Write tasks across several office domains so that agents must handle IT, HR, support, and productivity workflows.

Step 3: Let the agent interact with tools

Allow the model to inspect records and call tools while the environment keeps the side effects of those calls, so that later steps must respond to the updated enterprise state.

Step 4: Verify the final outcome

Judge success from the resulting system state so that correct planning is rewarded only when the workflow ends in the right place.

Step 5: Measure failure modes

Track refusal mistakes, recovery failures, and policy violations because enterprise readiness depends on all three.

The hidden quantity

The hidden quantity: state consistency over a plan

measured quantity  =  how well the agent keeps later actions aligned with the state created by earlier actions

The main hidden quantity is state consistency. In enterprise work, a plan is only correct when each step respects the records, permissions, and approvals produced by earlier steps. Two agents may issue similar tool calls, but one may keep a coherent chain while the other quietly breaks it by editing the wrong record or assuming a status that no longer holds.

EnterpriseOps-Gym exposes this quantity because the environment preserves state and then checks the final outcome. That design matters because a short benchmark can mark an action as locally reasonable while missing that the same action made the later workflow impossible or harmful.

Why it works

Why it works

The benchmark works because it replaces one-step correctness with stateful correctness. In a real office workflow, an agent cannot be judged by whether each local action sounds sensible in isolation. It has to leave the entire system in the right state. By modeling connected tools and databases together, the benchmark forces the agent to carry plan state across time.

The expert-curated tasks matter because enterprise workflows contain access control, infeasible requests, and branching recovery paths that toy benchmarks often skip. Those details expose weaknesses in planning consistency because the agent must choose between acting, checking more context, or refusing. That is why even strong models score modestly: the tasks demand coordination across records and policies, not only fluent tool invocation.

Outcome-based verification is the final piece because enterprise success is visible in the end state. A ticket is either resolved correctly, an account is either updated under the right conditions, or it is not. Checking that end state makes the benchmark stricter because a plausible explanation cannot hide an inconsistent workflow.

Math after the picture

The planning objective

First in words:

Choose the action sequence that reaches the required final enterprise state while respecting access rules and prior side effects.

Then the compact form:

best_plan = argmax_plan success(final_state(plan)) subject to policy_ok(plan) and state_consistent(plan)

Every symbol:

best_planthe action sequence the agent should prefer
success(final_state(plan))whether the final system state satisfies the task outcome
policy_ok(plan)whether every step respects permissions and rules
state_consistent(plan)whether later steps correctly use the state created by earlier steps
final_state(plan)the enterprise state after executing the whole plan
A tiny worked example
A request asks the agent to restore access for an employee whose manager approval is still pending.
Plan A edits the access record immediately. It reaches a changed final state, but policy_ok(plan) is false because approval was missing.
Plan B first checks approval, notices it is absent, and opens the correct escalation step. That plan does not grant access yet, but it leaves the system in the required policy-compliant state.
Because the benchmark checks both outcome and policy, Plan B ranks above Plan A.
The example shows why enterprise evaluation must score final state under constraints, not only visible action completion.

The benchmark is testing constrained planning, because many locally plausible actions still fail when policy and persistent state are part of the objective.

What can go wrong

What can go wrong

The agent may ignore persistent state. A model can treat each turn as fresh context and repeat an earlier action, which breaks the workflow because the system has already changed.
The agent may fail to refuse. Some requests should stop at verification or escalation, and acting anyway is harmful because the environment will record unauthorized side effects.
Recovery can be weaker than first-pass planning. After one incorrect edit, the agent has to reason from a damaged state, which is harder because later actions must both repair the mistake and finish the task.
Done right. The benchmark is most useful when it measures final state, policy compliance, and refusal behavior together, because enterprise readiness depends on all three instead of on raw tool fluency alone.
What a runnable demo should prove

What a runnable demo should prove

Build a reduced enterprise sandbox with one IT ticket system, one HR database, and one approval table. Create twenty tasks that require multi-step workflows, including some impossible requests. Compare a stateless baseline agent against an agent that explicitly tracks changing records before every action. The demo should show that the state-aware agent finishes more tasks safely because it checks and reuses persistent state instead of acting as though each tool call were isolated.

The demo should make one point clearly: enterprise agent quality depends on long stateful planning because the cost of a wrong step lives in the records left behind.
