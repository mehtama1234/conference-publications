PepBenchmark: Standardized Peptide ML Foundation

PepBenchmark standardizes peptide drug discovery ML by bundling curated datasets, a shared preprocessing pipeline, and unified baselines across four model types.

Paper explainersAll themesDatasets & Benchmarks & Evaluation

Peptide drugs are the next frontier of medicine, but progress stalls because every team cleans data differently, splits it differently, and compares models to different baselines. PepBenchmark fixes this by providing one shared sandbox: 35 cleaned peptide datasets, one preprocessing recipe, and benchmarks across fingerprint models, graph neural networks, language models, and string-based models. Now fair comparison is possible.

Zero assumption version

Peptide ML is a house of mirrors

Peptide therapeutics are real drugs in development—molecules a few dozen amino acids long (amino acids are the building blocks of all proteins). Testing every candidate in the lab is slow and expensive—thousands of peptides might be candidates, but the lab can only test dozens. So ML teams build models to predict properties first (Does this peptide kill bacteria? How toxic is it? How well does it enter cells?), because a model that can predict which candidates will work narrows down the list, and the lab can test only the most promising ones, saving months and money.

The trouble: three teams download the same raw peptide dataset, and each one cleans it differently. One removes exact duplicates. Another removes sequences that are 90% similar. A third applies a fancy negative-sampling trick. Then they train different models (say, one team uses a graph neural network, another uses a language model that reads the sequence as tokens—a sequence reading head that predicts properties) and claim one model is better. But nobody knows if the model is actually better at the task or if it just got cleaner data to train on, because the data quality was not the same across teams. The result: each paper compares itself only to methods in its own little tradition, and the field cannot actually say which approach works, because the comparison is unfair.

A beginner would try: download the dataset, slap a model on it, report the score. But that score only tells you something if everyone else used the same data-cleaning rules. Measuring without shared rules is like measuring height in meters vs. feet—you cannot tell who is taller.

The problem. Inconsistent data curation makes it impossible to fairly compare different ML approaches for peptide discovery, because a model trained on clean data will score higher than one trained on messy data, even if the second model's architecture is actually better—the score reflects data quality, not model quality.

The algorithm as a flow

What it actually does

Collect datasets

29 canonical and 6 non-canonical peptide datasets from real drug-discovery tasks.

Clean via kmers

Find enriched k-mers (short repeated letter patterns) to identify and cluster duplicates by sequence similarity.

Sample negatives smartly

Craft negative examples (bad peptides) so they are indistinguishable from positives by surface-level features.

Split cluster-aware

Assign whole clusters (not individual sequences) to train, validation, test to prevent data leakage.

Benchmark four families

Run fingerprint, GNN, language-model, and string models; report scores side-by-side.

What the paper changes

What the paper changed

PepBenchmark changes one thing: the preprocessing pipeline and evaluation protocol for peptide ML. Before, each team wrote its own pipeline (redundancy removal, negative sampling, splitting). Now, all teams use the same pipeline. This is not a new algorithm; it is a bottleneck elimination.

the object it moves  =  data preprocessing and evaluation protocol
The hidden quantity

The hidden quantity: data leakage risk

measured quantity  =  risk of similar sequences slipping into test data

Most ML teams split data at random: pick 80% for training, 20% for testing. The trouble: if the training set contains a peptide sequence that is 95% identical to one in the test set, the model can memorize the pattern instead of learning the real rule. The test score lies. This hidden quantity is the risk of leakage—sequences too similar to be split separately into train and test.

PepBenchmark measures this by clustering peptides using k-mer features (short repeated patterns in the sequence) and similarity graphs (a molecular fingerprint determines if two peptides are close cousins). Only then does it assign whole clusters to train/validation/test, ensuring no test sequence sneaks past as a cousin of a training sequence.

Plain reading. Imagine a test that asks you to identify birds from photos. But the test set contains the exact same photo as one in your study material, just rotated slightly. PepBenchmark removes this by clustering similar sequences first, so the test set has sequences that are sufficiently different from the training set that they cannot be solved by simple memorization.

Why it works

Why standardization makes comparisons fair

A fair comparison requires three things: the same data, the same data-cleaning rules, and the same evaluation rule. Before PepBenchmark, teams had all three different. One team cleaned via one method, another via a second. One team split data by sequence, another split by sequence similarity. The result: a model trained by team A looked worse than team B, but only because it saw sloppier data.

PepBenchmark standardizes the pipeline (redundancy removal, negative sampling, splitting) and provides multiple models (fingerprint, GNN, language, string-based) trained on that same cleaned data. Now if one model outperforms another, it is because the model itself is better, not because it got cleaner data. Here is how it works: shared pipeline is applied, then all models see identical data, then score differences reflect true model quality, then researchers can identify which approach actually works.

Additionally, the pipeline itself is designed to prevent data leakage (via cluster-aware splitting) and ensure negative examples are hard to distinguish from positives (via the BDNegSamp strategy—biologically informed, meaning it respects peptide biology, and distribution controlled, meaning negatives match positives in surface features). This means the benchmark scores are not inflated by easy cheats.

Math after the picture

The redundancy formula

First in words:

For each peptide in the test set, check its sequence identity against all training sequences using the Needleman-Wunsch algorithm (a method that aligns two sequences and scores how similar they are). Filter out any test sequence that shares more than 90 percent identity with any training sequence.

Then the compact form:

keep_test_seq if max_similarity(test_seq, all_train_seqs) < 0.90

Every symbol:

test_seqa peptide sequence in the test set
all_train_seqsall peptide sequences in the training set
max_similarityhighest sequence identity found by Needleman-Wunsch alignment
0.90the similarity threshold (sequences more alike than this are considered redundant cousins)
A tiny worked example
Test sequence T1: MVLSEAWQQQ... (40 amino acids)
Training sequence A1: MVLSEAWQQQ... (40 amino acids, 96% identical to T1 after alignment)
Result: T1 rejected from test set because max_similarity = 0.96 > 0.90 threshold.
Training sequence B1: MVAAAGWQQQ... (40 amino acids, 75% identical to T1)
Result: B1 does not block T1 because 0.75 < 0.90.
Once all 90% cousins are removed, the test set is safe from leakage.

The cutoff (0.90 identity) is the boundary: peptides more similar than this are treated as redundant and separated into train/test clusters.

What can go wrong

What can go wrong

Leakage still sneaks through if splitting is not cluster-aware. A naive 80/20 random split might place a test sequence into the set alongside its 92%-similar training cousin. PepBenchmark avoids this by assigning clusters, not sequences, to train/val/test. But if downstream users ignore the split recommendation, leakage creeps back in.
Negative examples must truly be hard to distinguish. If negative peptides (bad ones) are all short and positive peptides (good ones) are all long, a model learns the shortcut (length) instead of the real rule. BDNegSamp (biologically informed, distribution controlled) ensures negatives match positives in surface features. If it is applied wrongly, the benchmark scores lie.
Preprocessing choices bake in assumptions. The k-mer clustering method and the 90% similarity threshold are design choices. If the true biological rule is disrupted by these thresholds (e.g., two peptides that are 91% identical behave very differently), the benchmark may mask that. The choice of 0.90 is not universal truth.
Done right: researchers adopt the pipeline, train multiple model architectures on the same data, and trust the leaderboard. When everyone uses PepBenchmark, score improvements become trustworthy signals of model quality, not data-prep luck. The field can move faster because it is no longer repeating each other's data-cleaning work.
What a runnable demo should prove

What a runnable demo should prove

Build a small experiment showing the leakage problem and PepBenchmark's solution. Use a subset of the antimicrobial peptide dataset (say, 500 sequences). Train a simple model (e.g., a random forest on molecular fingerprints) in two ways: (1) naive 80/20 random split, and (2) cluster-aware split following PepBenchmark's kmer method. Measure the difference in test score.

leakage_artifact = score_naive_split - score_cluster_split

The demo makes visible that leakage inflates scores in the naive split by several percentage points. After standardization, that inflation vanishes—the score becomes a true measure of model quality.
