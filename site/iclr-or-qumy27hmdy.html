MAS$^2$: Self-Generative, Self-Configuring, Self-Rectifying Multi-Agent Systems

MAS squared builds agent systems that can redesign themselves during the task, so the team structure can change when the environment changes.

Paper explainersAll themesAgents & Tool Use

Many automatic multi-agent frameworks still follow a one-shot pattern: generate the team design once, then run it unchanged. That works when the task stays predictable, but it breaks when the environment shifts or the first design choice was poor. MAS squared treats agent-system design as an ongoing process. A small set of meta-agents can generate a task-specific team, implement it, observe where it fails, and then revise the design while the problem is still unfolding.

Zero assumption version

The problem: generate-once systems stay brittle after the first mistake

An automatically generated agent team may choose the wrong division of labor, pick the wrong tools, or set the wrong communication rules. In many frameworks those choices are frozen after initialization. If the task later reveals new constraints, the team keeps operating with the stale design and accumulates more errors.

This paper argues that a multi-agent system should not only solve the external task. It should also be able to redesign its own internal organization while the task is underway. That ability matters because real tasks often expose new requirements only after execution has begun.

The core idea in one sentence. Use a meta-level team that can generate an agent system, implement it, detect where it fails, and revise the design recursively as the task evolves.

The algorithm as a flow

What it actually does

Step 1: Generate a task-specific agent system

A generator agent proposes roles, prompts, tool choices, and interaction rules for a target problem.

Step 2: Implement the proposed system

An implementer agent instantiates that design so the target team can begin operating.

Step 3: Watch execution for mismatch

As the target system runs, the framework looks for signs that the current organization is no longer suitable for the live task.

Step 4: Rectify and regenerate

A rectifier agent edits the design or asks for a fresh one, so the system can change tools, roles, or communication patterns in response to new evidence.

Step 5: Train the meta-agents to cooperate

Collaborative Tree Optimization trains the meta-level decisions so that better redesign paths receive stronger learning signal.

What the paper changes

What changes: the agent system itself becomes editable

Most frameworks treat the agent team as fixed infrastructure. MAS squared changes that assumption. The object under control is now the team design itself: which agents exist, what each one does, what tools they can call, and how they communicate. Because that object is editable during execution, the system can adapt to new task demands.

the object it moves  =  the editable multi-agent design
The hidden quantity

The hidden quantity: design fit

measured quantity  =  How well the current organization matches the current task state

The main hidden quantity is design fit. A team that was well organized at the start may become poorly organized later if the task reveals new constraints, new evidence sources, or a different decomposition. A static system cannot respond because it has no mechanism for revising its own structure.

MAS squared uses meta-agents to estimate this hidden quantity indirectly. When execution stalls, coordination becomes wasteful, or missing capabilities appear, the rectifier treats that as evidence that the current design no longer fits the live task.

Why it works

Why it works: redesign is part of problem solving

The method works because the organization of an agent team is itself a decision variable. If that variable stays fixed, the system can only search within the limits of its initial setup. MAS squared expands the search space by letting the system also search over better team structures.

The generator, implementer, and rectifier divide this problem cleanly. One agent proposes a structure, one instantiates it, and one evaluates where it fails. Collaborative Tree Optimization helps because many redesign choices only prove their value after several later steps. The training therefore needs to reinforce redesign paths that lead to better downstream execution, not just short-term local fixes, because the wrong short-term signal could favor a redesign that looks convenient now but hurts the later task.

Math after the picture

The search objective: choose the best redesign path

First in words:

A compact view is to score a sequence of design choices by the final task value it produces. Each branch in the design tree corresponds to a different choice of roles, tools, and repairs. The learning rule should favor branches whose later execution performs better.

Then the compact form:

best_design_path = argmax_path task_value(path)

Every symbol:

patha sequence of generation and rectification decisions for the agent system
task_value(path)the resulting performance after deploying that sequence of design choices
best_design_paththe design sequence with the highest final task value
A tiny worked example
Path A creates two workers and no verifier. The task stalls after missing one external fact and ends with value 40.
Path B creates one worker, one verifier, and later adds a retrieval tool after the rectifier spots the gap. The task ends with value 63.
Path C creates many workers but poor communication rules and ends with value 35.
Collaborative Tree Optimization should reinforce choices like Path B because that redesign path handled the changing task better.

The method needs path-level training because a redesign decision may only reveal its value after the revised team runs for a while.

What can go wrong

What can go wrong

The system keeps redesigning without settling. If the rectifier fires too often, the team may spend too much effort rewriting itself instead of solving the task.
Meta-agents misdiagnose the failure source. A bad redesign can make the system worse if the true problem was poor execution rather than poor organization.
Training over design paths becomes sparse. Because a redesign choice may have delayed consequences, weak path-level training can fail to reinforce the right changes.
Done right: redesign is selective and useful. The method succeeds when the framework changes the team only when the current design truly no longer fits the task, because then each redesign pays back in later execution quality.
What a runnable demo should prove

What a runnable demo should prove

Build a toy research assistant that starts with a planner and a writer, then give it tasks that sometimes require retrieval and sometimes require verification. Compare a fixed generated team against a self-editing version with generator, implementer, and rectifier roles. Introduce a mid-task change, such as new evidence that requires adding a verifier or a retrieval tool. The demo should show that the self-editing system finishes more tasks because it can revise its own organization when the original setup becomes a poor fit.

Adaptation gain = completion_with_self_editing - completion_with_fixed_design on tasks with mid-run condition changes.

The demo must show that recursive self-generation matters during execution, not only during the first team setup.
