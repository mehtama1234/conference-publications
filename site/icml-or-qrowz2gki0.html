Autoregressive, Yet Revisable: In Decoding Revision for Secure Code Generation

Stream of Revision lets a code model revise earlier generated code during one decoding run so that security fixes can happen immediately instead of only after the draft is complete.

Paper explainersAll themesAgents & Tool Use

Most code generators write left to right and never touch what they already produced. That is convenient for decoding, but it does not match how programmers work. While writing code, a person often reaches a later line, notices a flaw in an earlier choice, and goes back to repair it before continuing. Security mistakes are especially sensitive to that pattern because a small earlier choice about input handling or access checks can make the whole function unsafe. This paper adds a built-in revision mechanism to decoding itself. Instead of waiting for a separate post-processing agent or external checker, the model can backtrack and edit its own earlier output inside the same generation pass.

Zero assumption version

Why one-way decoding is a weak fit for secure coding

Standard code generation treats output as an immutable prefix. Once the model writes a line, later steps can only append more text. That is a poor fit for programming because later reasoning often reveals that an earlier design choice was unsafe or incomplete.

Existing fixes usually add a second stage such as a repair agent or an external analysis tool. Those methods help, but they add latency because the model must first finish the draft and then start a second correction loop. They also split generation and revision into separate systems, which means the model cannot use its own internal code reasoning at the exact moment it notices a flaw.

The paper's move in one sentence. Add special actions during decoding that let the model step back and rewrite earlier code, so that revision becomes part of generation instead of an external afterthought.

The algorithm as a flow

What it actually does

Step 1: Generate code normally

Produce the next portion of the draft while reading the growing program context.

Step 2: Detect the need for revision

Notice that an earlier line should change because later reasoning reveals a safety or logic issue.

Step 3: Emit a revision action

Use special decoding actions that let the model move back to the part of the draft that needs repair.

Step 4: Rewrite the earlier code

Edit the existing draft in place so that the unsafe choice is corrected before more code is added.

Step 5: Continue forward generation

Resume writing from the repaired draft so that the later code is built on a safer earlier foundation.

What the paper changes

What the paper changes

The paper changes decoding for code generation. Instead of forcing every generation step to append to an immutable prefix, it allows controlled backtracking and rewriting inside one decoding pass, so that the model can repair earlier unsafe choices before later code depends on them.

The hidden quantity

The hidden quantity: revision value

measured quantity  =  how much the final program would improve if the model rewrote an earlier part of the draft right now

The central hidden quantity is revision value. At any point during generation, the model must choose between continuing forward and revising what it already wrote. Revision is only worth doing when changing the old code will improve the final program enough to justify the extra decoding work, because some earlier flaws would otherwise spread into the later logic.

Secure code generation makes this quantity especially important because many flaws are prefix flaws. A missing input check, unsafe string handling choice, or bad authorization branch can infect the rest of the function. Revising early helps because later code is then built on the corrected version rather than on the original unsafe branch.

Why it works

Why it works

The method works because many code errors are discovered only after the model has written more context. A left-to-right-only decoder can recognize the flaw but cannot act on it directly. Adding revision actions converts that recognition into a repair opportunity inside the same run.

This in-decoding repair is useful for security because vulnerabilities often come from early structural decisions. If the model can repair the earlier branch when the danger becomes clear, later code no longer has to route around the flaw. That tends to reduce vulnerability counts because the program is corrected at the point where the unsafe pattern began.

The single-pass design also reduces overhead compared with an external repair pipeline because the model does not have to finish the whole draft, hand it to another system, and then start a new pass. Revision happens while the model's internal reasoning about the code is still active, which helps because the same context that revealed the flaw is available at the moment of repair.

The decoding choice

First in words:

At each step, choose between appending new code and revising earlier code according to which action is expected to produce the safer final program.

Then the compact form:

best_action_t = argmax_action expected_final_quality(action | current_draft_t)

Every symbol:

best_action_tthe decoding action chosen at step t, such as append or revise
actionone candidate decoding move
expected_final_quality(action | current_draft_t)the expected quality and safety of the final program if that move is taken now
current_draft_tthe partially generated code at step t
A tiny worked example
The model has written a request handler that opens a file path from user input without validation.
A few lines later, the model realizes the path should have been checked against an allowed directory.
Appending more code leaves the unsafe file access in place, so expected final quality for append is low.
Issuing a revision action to rewrite the earlier file-open step adds validation and raises expected final quality.
The decoder therefore chooses revision before continuing, because fixing the old flaw now improves the rest of the program.

The paper's main idea is that decoding should choose the move that best improves the finished program, even when that move points backward instead of forward, because earlier repair can remove a flaw before the rest of the code grows around it.

What can go wrong

What can go wrong

The model can over-revise. If revision actions are too easy to trigger, the decoder may keep rewriting the same region, which wastes steps because not every local improvement changes final program quality enough to matter.
Revision scope may be too small. Some security flaws require larger structural changes than one local rewrite, so the mechanism needs enough reach because partial fixes can still leave the unsafe logic intact.
Training may not expose enough realistic revision cases. If the model rarely sees examples where later reasoning should trigger earlier repair, it may underuse the revision action because it has not learned when revision pays off.
Done right. The method is strongest when revision actions are available at the moments where later context reveals a serious earlier flaw, because those are the points where in-decoding repair changes the security outcome of the whole program.
What a runnable demo should prove

What a runnable demo should prove

Build a secure-code benchmark with tasks where a later branch often reveals that an earlier choice was unsafe, such as input validation, permission checks, or file-path handling. Compare three systems: plain left-to-right decoding, left-to-right decoding plus a second repair pass, and in-decoding revision. Record vulnerability count and runtime. The demo should show that in-decoding revision removes more early structural flaws than plain decoding because it can patch them before the rest of the code depends on them.

vulnerability_reduction = insecure_outputs_baseline - insecure_outputs_method

The demo should make clear that secure coding improves when revision happens inside decoding, because many vulnerabilities begin in early lines that later generation ought to be allowed to repair.
