Single Index Bandits: Learning with Unknown Reward Functions

A new way to make real-time decisions when you do not know how rewards are connected to your actions.

Paper explainersAll themesLearning Theory

Imagine a slot machine where pulling a lever gives a reward, but you do not know the rule that links your choice to the reward you get. Most bandit algorithms assume they already know this rule. This paper solves the problem when the rule is hidden. It introduces three algorithms (STOR, ESTOR, GSTOR) that learn both the rule and which choices are best, all while making decisions in real time.

Zero assumption version

The puzzle: knowing the actions but not the rules

In a bandit problem, you repeatedly choose an action (like which arm of a slot machine to pull, or which product to show a customer) and receive a reward. Your job is to find which actions give the highest rewards. A traditional algorithm assumes you already know how rewards connect to actions, through a rule called the link function.

But in the real world, you never know this rule. If your algorithm assumes the wrong rule, every choice it makes is built on a false foundation, and it fails. A beginner might guess a simple linear rule (more action value equals more reward), but the true rule might curve, plateau, or move in unpredictable ways.

The method in one sentence. Learn the hidden rule by measuring how confident the rule's prediction is, then use that confidence to decide which action to try next.

What the paper changes

What the paper changes

The paper changes what the algorithm is allowed to assume. Instead of being handed the link function (the rule that connects actions to rewards), the algorithm must figure it out as it goes, using only the actions it tries and the rewards it observes.

the object it moves  =  The link function
The hidden quantity

The hidden quantity: how well does our rule fit?

measured quantity  =  Prediction error under the guessed rule

The paper measures something that was never measured before: how badly does your current guess about the link function miss the real rewards? This is the prediction error, also called the misspecification gap. It tells you if your guess is close or far from the truth.

The paper estimates this gap using Stein's method, a technique from probability that lets you measure how different a guessed rule is from the real data, without needing to know the true rule in advance. Stein's method looks at the second moment (loosely, the spread) of the prediction errors and computes a single number that says how wrong the guess is.

Why it works

Why exploring the right way fixes the problem

The core trick is that Stein's method lets you measure how wrong your guess is without knowing the truth. Traditional bandit algorithms explore randomly, which wastes time because they try actions that do not move them closer to the true rule. This paper's algorithms explore strategically—they focus tries on actions where the current guess is most uncertain, because those tries teach the algorithm the most about the hidden rule.

In STOR (the simpler version), the algorithm splits time into two phases: explore by trying many actions, then exploit by picking the best action under the learned rule. In ESTOR (the better version), it cycles through many short epochs, each time re-estimating the rule and deciding which actions to try next. Running more epochs helps the algorithm correct its guess sooner, because each epoch gives a chance to measure prediction error again and catch mistakes from earlier epochs.

For GSTOR (handling any reward function shape), the algorithm explores twice: once to get a rough guess of the rule, then again to refine it, treating the first rough guess as a stepping stone. The Stein estimator works at each stage, tracking how wrong the current guess is.

Math after the picture

The equation behind the guess

First in words:

loss = sum over all observations of the squared difference between predicted reward and real reward, plus a penalty term that shrinks large parameters

Then the compact form:

loss = sum_i (f(x_i, theta) - r_i)^2 + lambda ||theta||_1

Every symbol:

f(x_i, theta)your guessed link function: given action x_i and parameters theta, predict the reward
r_ithe actual reward you observed
thetathe parameters that define the link function
lambdaa knob that controls how much to shrink large parameters to avoid overfitting
||theta||_1the sum of absolute values of all parameters
A tiny worked example
Suppose your guessed link function is: predicted_reward = 0.5 * action + 0.3. You try action = 4 and get reward = 2.5.
Your prediction was 0.5 * 4 + 0.3 = 2.3. The error is 2.5 - 2.3 = 0.2.
This squared error is 0.2^2 = 0.04. Repeat over 100 tries. The sum might be 3.5.
Add the regularization penalty (suppose lambda = 0.1 and parameters are 0.5 and 0.3): 0.1 * (0.5 + 0.3) = 0.08.
Total loss = 3.5 + 0.08 = 3.58. The algorithm updates theta to shrink this loss.
In the next epoch, the new guess might be theta = 0.6, 0.25, and the error goes down because the guess is closer to the truth.

The Stein estimator watches how much this loss changes as you try more actions, and that change tells you if your guess is right or wrong.

What can go wrong

What can go wrong

Noise breaks the measurement. If the reward is very noisy (random), Stein's method needs many samples to see the true pattern. With too few tries in an epoch, the estimate of the link function can be wrong, and the algorithm picks bad actions.
Wrong shape assumption. STOR and ESTOR assume the link function is monotonically increasing (more action value means more reward). If the true rule is not monotonic, these algorithms may miss the best action. GSTOR handles general shapes but is slower.
Epoch size matters. If epochs are too short, you do not collect enough (action, reward) pairs to estimate the rule reliably. If epochs are too long, you waste time exploiting a stale guess. The algorithm must tune this trade-off.
Done right. Use Stein's method to track prediction error, run enough tries per epoch to beat the noise, and use GSTOR if you do not know the function shape. The algorithm will learn the rule and find the best action with near-optimal efficiency.
What a runnable demo should prove

What a runnable demo should prove

Build a simple bandit problem: generate 5 actions (x from 1 to 5), and set the true reward function as something nonlinear, like reward grows by a fixed amount for small x but by a shrinking amount for large x. Implement STOR and a naive algorithm that assumes reward scales linearly with x (wrong assumption). Run both on 1000 rounds, split into 10 epochs of 100 tries each.

Regret = (optimal reward if you knew the rule) - (total reward the algorithm actually got)

The demo must show that STOR's regret grows slowly (like the square root of time), while the naive algorithm's regret grows much faster (because it never corrects its false assumption). STOR learns the hidden rule and catches up; the naive algorithm never does.
