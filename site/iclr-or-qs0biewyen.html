ARROW: Adaptive Time Intervals for Weather Forecasting

Instead of forecasting weather at one fixed time step, ARROW picks the right time step for each weather pattern, so errors don't pile up over days.

Paper explainersAll themesTime Series & Sequential

Weather forecast models today predict 6 hours ahead, then repeat that 20 times to predict 5 days out. The problem: errors snowball, and short steps miss big weather patterns. ARROW instead picks which time step to use next based on current conditions, using shared and specialized forecasting models for different speeds, plus an intelligent router that decides when to jump forward.

Zero assumption version

Fixed time steps lock you into a bad trade-off

Today's weather models predict weather in chunks of the same size every time, usually 6 hours. To forecast a week ahead, they repeat this 28 times, each time using yesterday's forecast as the input for today's. The problem: each prediction has some error, and when you chain 28 predictions together, those errors pile up. By day 5, the forecast is often unreliable.

The deeper issue is that weather has two different speeds happening at once. Some things change fast (a storm's exact position hour to hour), and others evolve slowly (the jet stream's week-long meandering). Using one fixed step size misses both. Short steps catch the storm's detail but drown in noise. Long steps capture the slow waves but miss the sudden gust.

The method in one sentence. ARROW picks a new forecast horizon (how far ahead to predict) at each step based on the current weather, and routes the input to specialized forecast models trained for that horizon.

What the paper changes

The one thing that changes: the forecast horizon

Classical methods forecast the same time interval every step (always 6 hours). ARROW changes the length of each forecast, picking 6, 12, or 24 hours based on what the weather looks like now. This adaptive choice is the core innovation.

the object it moves  =  Forecast time interval
The hidden quantity

The hidden quantity: rollout efficiency

measured quantity  =  Error-per-step in forecasting chain

Forecasting errors accumulate when you chain predictions: each step introduces noise, and that noise becomes the input to the next step, making the error worse. The hidden quantity ARROW measures is how much error is added per step in the chain to reach a fixed target date (like day 5).

When you use a 6-hour step, you need 20 steps to reach day 5, so error piles up 20 times. When you use a 24-hour step, you need only 5 steps, so error accumulates only 5 times. But some weather patterns are too fine for a 24-hour step. ARROW measures, at each moment, which step size introduces the least total error to stay on target.

Why it works

Why it works: matching the step to the weather pattern

Weather changes at different speeds: thunderstorms evolve in hours, while a weather high-pressure dome drifts over days. A fixed step size is always wrong for one or the other. ARROW works because it lets the model use a 6-hour step when fine detail matters (a storm arriving tomorrow) and a 24-hour step when only the broad pattern matters (the jet stream on day 5). This reduces the number of prediction steps needed and proportionally reduces error pile-up.

The shared-private mixture-of-experts architecture helps: one shared neural component reads the weather state, then passes it to specialized prediction models trained specifically for 6-hour, 12-hour, or 24-hour forecasts. Each specialist gets better at its own time scale because it is trained only on that kind of jump. The reinforcement learning router observes the current weather state and learns which specialist to trust right now, because choosing the 24-hour forecaster when a storm is 3 hours away causes a catastrophic miss.

How the error shrinks

First in words:

error_total = sum over all steps of (error_per_step) where error_per_step depends on which expert is chosen

Then the compact form:

L = sum_t || y_t - f(s_t, h_t) ||^2 where h_t is router's horizon choice and f is the specialist expert

Every symbol:

y_tTrue weather state at step t
f(s_t, h_t)Forecast from the specialist expert chosen by router
s_tCurrent weather state (input)
h_tHorizon chosen by router (6, 12, or 24 hours)
LTotal forecasting error from now until day 5
A tiny worked example
Day 1 sunrise: storm approaching, router picks 6-hour step; error = 0.8
Day 1 afternoon: same storm, router picks 6-hour step; error = 0.9
Day 2 morning: storm passed, router picks 24-hour step; error = 0.3
Day 3: jet stream dominates, router picks 24-hour step; error = 0.5
Day 4: slow changes continue, router picks 24-hour step; error = 0.4
Total error = 0.8 + 0.9 + 0.3 + 0.5 + 0.4 = 2.9 (five steps)
Fixed 6-hour method: repeat step 20 times, total error = 20 * 0.8 = 16 (much worse)

The router's choice of horizon directly changes how many steps pile up, so choosing wisely cuts error accumulation.

What can go wrong

What can go wrong

Router overthinks edge cases. If the router has never seen a particular weather pattern before (e.g., a rare winter storm in summer), it may pick the wrong horizon. The learned policy only works on weather it has trained with.
Specialists overfit to their time scale. A 24-hour expert trained only on day-scale changes may completely miss a sudden squall. The specialists are fast but brittle to surprise.
Earth's circular structure was hard to encode. Latitude wraps around the Earth in a circle; most neural networks expect flat grids. The Ring Positional Encoding fixes this, but if it is not tuned right, the model can create fake discontinuities at the poles.
Done right. The router is trained via reinforcement learning on real historical weather data, so it learns patterns like 'when the jet stream is this shape, use 24 hours; when pressure is rising, use 6 hours.' The specialists are jointly trained on a mix of time scales, so they share low-level features but specialize where needed.
What a runnable demo should prove

What a runnable demo should prove

Build a small weather forecasting system with two specialists (6-hour and 24-hour forecasters) and a simple router that alternates between them. Train on real historical data (e.g., ERA5 weather data, freely available). Compare total forecasting error out to day 5 between a fixed-6-hour baseline and the adaptive ARROW version. The demo should show that ARROW makes fewer predictions (e.g., 8 steps instead of 20) and yet has lower total error because each step is chosen to be efficient.

Efficiency = (Baseline error - ARROW error) / Baseline error; also count: steps taken by baseline vs ARROW to day 5

The key thing the demo makes undeniable: fewer prediction steps do not mean worse forecasts when each step is picked to match the weather pattern.
