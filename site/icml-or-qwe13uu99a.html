MARS: Modular Agent with Reflective Search

An autonomous AI research agent that balances finding the best solution against its cost, decomposes tasks into reusable code modules, and learns from what goes wrong across different attempts.

Paper explainersAll themesAgents & Tool Use

Running a machine-learning experiment is expensive. A 0.1% accuracy boost that takes 10 hours instead of 1 hour is rarely worth it. MARS is an agent that hunts for good AI solutions but always keeps an eye on the clock, breaks problems into testable code pieces, and learns insights by comparing when different approaches succeed or fail.

Why agents fail at AI research

Today's language-model agents can write code, but they often write big monolithic scripts that try everything at once. When training a model takes 3 hours, the agent might run 100 different attempts, racking up 300 hours of compute to find a tiny improvement. That is money and time wasted.

Worse, when something fails, the agent has no clear record of why. It sees 'error' or 'accuracy 68% down from 72%', but the actual cause could be the data loader breaking, or the loss function, or the model itself. All mixed together.

Standard search algorithms help computers explore a space of options (like chess trees), but they do not know that a training run costs hours and a model tweak costs seconds. They treat all choices as equally expensive, which means they waste time pursuing tiny accuracy gains that take weeks to achieve, when the same accuracy is available in minutes with a different approach.

The real problem. Agents produce fragile, monolithic code that wastes compute time and have no way to learn which specific code changes actually caused failures.

The algorithm as a flow

What it actually does

Understand the task.

The agent reads the problem instructions, extracts the objective (like maximizing accuracy), and sets a compute budget.

Draft a plan.

MCTS explores high-level strategies (which model architecture, which loss function, which preprocessing). At each choice, the cost calculator predicts how long it will run.

Decompose into modules.

Once a plan is chosen, the agent breaks it into independent code pieces: data loading, model definition, training loop, evaluation.

Execute and record.

Each module runs. The agent records the logs, timings, and final metrics. If it fails, the log shows exactly where.

Learn from differences.

The agent compares successful and failed runs side by side, identifies which specific code changes matter, and stores those insights for later.

What the paper changes

The one thing MARS changes

Standard search algorithms explore by running every option fully and comparing the results. MARS changes the way the agent decides whether to keep exploring or stop. Instead of 'will this improve the score?', it asks 'will this improve the score per hour of compute?' If you can get 90% accuracy in 2 hours or 90.2% in 10 hours, MARS stops at 2 hours. This works because a 0.2% gain is not worth 8 more hours if you could run 8 completely different experiments in that time and maybe find 1% gain by trying a totally different approach.

the object it moves  =  The stop-or-continue decision
The hidden quantity

The hidden quantity: cost-to-benefit ratio

measured quantity  =  benefit per hour of compute

Every training run produces two numbers: the final accuracy (the benefit) and the compute time (the cost). A hidden quantity that the paper measures is the ratio of how much accuracy you gained divided by how long it took. If a change gets you from 70% to 71% accuracy and takes 1 hour to train, the ratio is 1% per hour. If the next change gets you from 71% to 71.1% but takes 4 hours, the ratio drops to 0.025% per hour.

MARS estimates this ratio for each potential move before fully committing. When the ratio drops below a threshold set by the user's budget, the agent stops exploring and ships the best solution found so far.

Why it works

Why it works: three levers

The paper rests on three mechanical ideas. First, MARS uses Monte Carlo Tree Search (MCTS), which is a way to explore a large decision tree without trying every single path. Imagine you are deciding what to cook: instead of trying every recipe in every cookbook, you sample a few promising branches, see how they turn out, and focus your effort on the branches that look good. MCTS does that for code choices: it tries a few model architectures, a few loss functions, and focuses effort on combinations that work. The key difference is that MCTS now asks 'does this work well for the compute I have left?' instead of just 'does this work well?' because reaching into the tree costs real hours.

Second, the agent decomposes the solution into modules (a data-loading module, a model module, a training module). Why does this matter? Because when something breaks, you know exactly which piece broke. And because you can test each piece in isolation, so you catch bugs faster than if you have one giant script. Modular code also survives change: you can swap the model without touching the data loader.

Third, Comparative Reflective Memory addresses the credit assignment problem by comparing successful and failed runs side by side. If one branch reaches 72% accuracy and another reaches 74%, the agent identifies which specific code lines differ and concludes those changes caused the gain. This works because if you change 10 things at once and one run wins, you still do not know which of those 10 things actually mattered. But if you change only one thing between two runs (same data, same architecture, just different learning rate), then the improvement can only come from that one change. The agent stores these causal insights (like 'using learning rate 0.001 instead of 0.0001 raised accuracy 2%') in a compact memory. Later, when facing a new problem, it can reuse these learned lessons.

Math after the picture

The equation: cost-aware node value

First in words:

node value = (predicted accuracy on test set) divided by (predicted compute hours) raised to a power, adjusted for how many times this branch has been visited

Then the compact form:

V(n) = (accuracy_pred / cost_pred^alpha) * (1 + log(parent_visits) / visits(n))

Every symbol:

V(n)the score assigned to this choice (node) in the search tree
accuracy_predestimate of how well the solution will perform on held-out data
cost_predpredicted number of compute hours to run this attempt to completion
alphahow much to penalize time; alpha=1 means accuracy per hour; alpha>1 penalizes time more strongly
visits(n)how many times this branch has been explored
parent_visitshow many times the parent branch has been explored (helps balance exploration)
A tiny worked example
Run A: predicted accuracy 75%, predicted cost 2 hours. Value = (75 / 2^1) * (1 + log(50) / 3) = (75 / 2) * (1 + 1.92 / 3) = 37.5 * 1.64 = 61.5.
Run B: predicted accuracy 76%, predicted cost 8 hours. Value = (76 / 8^1) * (1 + log(50) / 5) = (76 / 8) * (1 + 1.92 / 5) = 9.5 * 1.38 = 13.1.
Same parent (50 visits). Run A scores 61.5, Run B scores 13.1. MCTS will explore Run A much more, even though it has higher accuracy, because the accuracy gain (1%) is not worth 6 extra hours.

The formula ensures the agent focuses effort on branches with high accuracy gains per compute hour, steering search toward solutions that fit the budget.

What can go wrong

What can go wrong

Premature stopping. If the budget threshold is set too high (you penalize time too much), MARS may stop exploring before finding a genuinely good solution. Example: stopping at 70% accuracy to save hours, when one more hour would have found 75%.
Cost prediction errors. MARS estimates how long a run will take before actually running it. If the estimate is wrong (predicts 2 hours, actually takes 6), the cost-to-benefit calculation fails. Variations in hardware or dataset size can throw off predictions.
Causal confusion in Reflective Memory. When comparing two branches, the agent may confuse which code change caused the improvement. If both the learning rate and the batch size changed, isolating the cause requires careful control. The paper notes this is hard without proper ablation.
Modular decomposition brittleness. Breaking code into independent modules assumes the pieces do not interact in weird ways. If data preprocessing affects which model architectures work best, treating them as independent modules may miss good combinations.
Done right. Combine cost prediction with early stopping rules (stop a run if it is clearly not improving), isolate causal changes one at a time (ablation), and test module independence on simpler problems first before scaling up.
What a runnable demo should prove

What a runnable demo should prove

Build a small ML task (e.g., a tabular classification problem from Kaggle that trains in minutes, not hours). Run the agent with two budgets: one that stops early (1 hour) and one that allows unlimited time. We need two budgets because this shows the trade-off working: the budget-aware version should find a good solution faster, while the unlimited version will continue searching and might find a slightly better solution but waste time doing it. Measure total time and final accuracy. The demo should show that the budget-aware version reaches 90% of the accuracy of the unlimited version in half the time, or show a concrete accuracy-per-hour number that the agent optimized toward.

accuracy gain per hour = (final accuracy - baseline accuracy) / (total compute time in hours)

The core insight is that a research agent can learn faster by respecting compute budgets and learning which specific code changes matter, rather than blindly exploring the full space.
