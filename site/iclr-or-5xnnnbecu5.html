Lean Finder: Semantic Search for Mathlib That Understands User Intents

A search engine that finds the right theorem in a math library by learning what mathematicians really mean when they ask for help.

Zero assumption version

Finding theorems in a library is so hard it slows proof-writing to a crawl

Lean is a formal language where you write proofs that a computer can verify. Mathematicians use Lean to build up a library called mathlib with thousands of proven theorems. When you want to prove something new, you search mathlib for a theorem that helps, because reusing a proven theorem is faster than proving it from scratch. The problem: your natural question ('Does this set have a finite cardinality?') never matches how the theorem was formally stated ('finite_cardinal.of_set_equiv_range'). Existing search engines just translate theorems to English and match keywords, but that ignores what you actually meant to ask.

A mathematician new to Lean types 'Is there a theorem about something being injective and surjective at once?' But the library calls it 'bijective', and the search engine does not know these mean the same thing. You waste time digging, or you write a proof from scratch when the answer already existed.

In one sentence. Mathematicians struggle to find theorems because their natural language question does not match the formal statement, and existing search ignores what they really meant.

The hidden quantity

The hidden quantity: intent-theorem alignment

measured quantity  =  intent alignment score

The paper measures how well a user's real question aligns with the theorem that actually answers it. This is not just keyword overlap; it is how often a mathematician, after asking a question in plain English, recognizes the top search result as the right theorem.

The paper estimates this alignment by collecting real questions mathematicians asked, analyzing what theorems they actually needed, then testing whether the fine-tuned search engine puts those theorems at the top. An alignment score of 1.0 means every user question gets the correct theorem as result #1; 0.5 means half the time it ranks below other, wrong theorems.

Why it works

Why it works: learning from real intent

The search engine represents each theorem and each query as a vector (a list of numbers). When a mathematician asks 'bijective function', the search engine computes a similarity score between that query vector and each theorem vector, then ranks them. The naive approach: just learn vectors from the formal theorem names. This fails because 'bijective' in English and the formal name 'Function.Bijective' are far apart in meaning to a word-based system.

Lean Finder fixes this by fine-tuning the vectors with synthetic queries. It takes real theorems, generates multiple plain-English questions that a mathematician might ask to find that theorem (e.g. 'a function with an inverse', 'onto and one-to-one', 'no gaps or repeats'), and trains the embedding so these diverse questions all pull the theorem vector closer. After this fine-tuning, when a real user asks 'bijective', the theorem vector is already in the right neighborhood.

The paper then adds a second signal: mathematician feedback. It collects ratings from real users on whether results were useful, and adjusts the vectors a bit more so that theorems rated as relevant are pulled even closer to the queries that led to them. This is the mechanism: learn vectors not from formal names alone, but from how mathematicians actually describe what they need.

The retrieval ranking equation

First in words:

similarity score equals the dot product (sum of element-by-element products) of the query vector and theorem vector, normalized by their lengths, so longer vectors do not automatically score higher

Then the compact form:

sim(q, t) = (q · t) / (||q|| * ||t||)

Every symbol:

qquery vector (list of numbers representing the question)
ttheorem vector (list of numbers representing the theorem)
q · tdot product (multiply each pair of elements, then sum)
||q||length of the query vector (square root of sum of squares)
||t||length of the theorem vector
sim(q, t)similarity score between 0 and 1
A tiny worked example
Suppose q = [0.8, 0.3, 0.1] (a mathematicians's question vector), t = [0.9, 0.2, 0.2] (a theorem vector).
Dot product: 0.8*0.9 + 0.3*0.2 + 0.1*0.2 = 0.72 + 0.06 + 0.02 = 0.80
Length of q: sqrt(0.8^2 + 0.3^2 + 0.1^2) = sqrt(0.64 + 0.09 + 0.01) = sqrt(0.74) ≈ 0.86
Length of t: sqrt(0.9^2 + 0.2^2 + 0.2^2) = sqrt(0.81 + 0.04 + 0.04) = sqrt(0.89) ≈ 0.94
Similarity: 0.80 / (0.86 * 0.94) ≈ 0.80 / 0.81 ≈ 0.99
High score means the question vector and theorem vector point in nearly the same direction — they are close in meaning.
If the paper's fine-tuning moved the theorem vector from [0.1, 0.1, 0.9] (far from the question), the score would be 0.08 / (sqrt(0.83) * 0.94) ≈ 0.09 — low, ranked last.

The fine-tuning adjusts the vector entries so that questions mathematicians really ask point toward the theorems that solve them.

What can go wrong

What can go wrong

Overfitting to your training questions. If you fine-tune only on the exact phrasing mathematicians used in the past, new phrasings or edge-case questions fall through. Fix this by generating diverse synthetic queries from each theorem, covering many ways to describe the same idea.
User feedback is sparse and biased. Only a fraction of users rate results. Those who do may prefer familiar-sounding names over accurate ones. If you weight feedback too heavily, the search drifts back toward surface-text matching. Guard against this by keeping the synthetic query signal even after adding user feedback.
Formal names and plain English diverge over time. As the Lean library grows, new theorems might be named differently. If the fine-tuning is not refreshed, new theorems stay misaligned with how users ask for them.
Done right. Periodically re-analyze real questions to catch new patterns, regenerate synthetic queries, and fine-tune again. Test on held-out questions that were not in the training set.
What a runnable demo should prove

What a runnable demo should prove

Build a tiny test: take 50 real questions a mathematician asked (e.g. from GitHub issues or forums), the theorem that actually solved each one, and three other theorems from the library that do not match. For each question, run it through both the naive keyword search and Lean Finder. Count how often each one ranks the correct theorem in the top spot.

top_1_accuracy = (number of questions where correct theorem ranked first) / (total questions)

If Lean Finder scores 40% or higher while keyword search scores 25% or lower on the same 50 questions, the fine-tuning on real intent is working.
