PANINI: Continual Learning via Structured Memory

Instead of storing full documents and retrieving chunks over and over, PANINI writes new knowledge as a growing network of entity- and event-aware question-answer pairs, then answers queries by following reasoning chains through that network.

Paper explainersAll themesLLMs & Foundation Models

When an LLM reads the same documents many times, it wastes compute doing the same reasoning repeatedly. Worse, chunk-based retrieval often pulls in irrelevant context, leading to hallucinations. PANINI solves this by replacing documents with a structured, continuously-updated memory: each new experience is encoded as a network of question-answer pairs (called a Generative Semantic Workspace, or GSW) linked by entities and events. At query time, the model walks through the GSW following reasoning chains instead of retrieving verbatim text, cutting the time the model spends reasoning by 2-30x while actually improving answer accuracy.

The repeated-reasoning trap

Today's retrieval-augmented generation (RAG) systems store full documents and search for relevant chunks at query time. But when the same documents are queried multiple times, the model reasons over them repeatedly, wasting compute with every lookup.

Chunk retrieval also pulls in neighbours and context that may not be relevant to the actual question, flooding the model with noise. This irrelevant background prompts the model to make up answers not grounded in the evidence.

One fix is to fine-tune the base model on new documents, but that risks forgetting everything learned during initial training and requires expensive retraining for every batch of new knowledge.

The core problem. RAG repeats reasoning over the same texts and injects irrelevant context, wasting the time spent generating answers and breeding hallucinations.

The algorithm as a flow

What it actually does

Write phase: encode documents as a QA network

Each new document is read once; knowledge is extracted as question-answer pairs linked by named entities and events.

Build two indices for fast lookup

One index finds QA pairs by matching entity names; the other finds them by semantic similarity to a query.

Decompose incoming query into sub-questions

The model breaks down the user's query into atomic sub-questions it can answer one step at a time.

Walk the network following chains

For each sub-question, retrieve a QA pair, use its answer to refine the next sub-question, and keep a running chain score.

Generate final answer from the collected chain

Ground the response only in QA pairs actually visited in the network; no hallucination, no filler.

What the paper changes

The thing the paper changes

PANINI replaces verbatim document storage with a structured memory: a continually-updated network of question-answer pairs, where each pair is anchored to named entities and events from the document.

the object it moves  =  document representation
The hidden quantity

The chain relevance score

measured quantity  =  reasoning chain quality metric

As the model traverses the QA network, it scores each reasoning chain—a path of linked question-answer hops—using the geometric mean of how well each QA pair matches the sub-questions and entities it encounters. A high score means the chain is coherent and on-topic; a low score means it wandered into irrelevant pairs.

PANINI uses this score to rank and filter chains before generating the final answer. The model only includes QA pairs in its response if they scored well on this reasoning-grounded path, eliminating low-confidence detours that would otherwise breed hallucinations.

Why it works

Why moving knowledge into a QA network helps

The base LLM is already excellent at reasoning through structured information. Instead of making it search and reason over raw text repeatedly, PANINI preprocesses each document once into a structured network of questions and answers linked by entities and events. This upfront work means the model never has to read the same passage twice.

When a query arrives, PANINI decomposes it into sub-questions and walks through the QA network following reasoning chains. Because the network is structured around entities and events, each chain stays coherent: the model can follow a logical path from one answer to the next, building confidence as it goes. This is fundamentally different from chunk retrieval, which randomly pulls in whatever text is semantically close to the query, including tangential noise.

By filtering chains based on their composite reasoning score, PANINI only grounds the final answer in high-confidence paths. Because the model is forced to construct its answer from only the QA pairs it actually retrieved and verified, it cannot invent facts or wander into unvisited corners of the network. Low-scoring chains are discarded entirely, so they never appear in the context the model sees, leaving no opening for hallucination.

Math after the picture

Scoring a reasoning chain

First in words:

The score of a chain at step t is the geometric mean of the relevance scores for all hops from step 1 to step t.

Then the compact form:

s_t = (s_1 * s_2 * ... * s_t) ^ (1/t)

Every symbol:

s_tthe chain's composite score at step t
s_ithe relevance score of hop i (how well the QA pair matches the sub-question)
tthe number of hops completed so far
1/tthe t-th root, ensuring the score is always between 0 and 1
A tiny worked example
Hop 1: Q matches a QA pair with relevance 0.9. Chain score s_1 = 0.9.
Hop 2: Next entity link yields relevance 0.8. Chain score s_2 = (0.9 × 0.8)^(1/2) = 0.72^0.5 = 0.85.
Hop 3: Event link yields relevance 0.6. Chain score s_3 = (0.9 × 0.8 × 0.6)^(1/3) = 0.432^(1/3) ≈ 0.76.
A wandering chain (0.9 → 0.3 → 0.2) scores (0.9 × 0.3 × 0.2)^(1/3) = 0.054^(1/3) ≈ 0.38, and ranks much lower.

The geometric mean penalizes weak links early: one bad hop drags down the whole chain, so only coherent paths survive ranking.

What can go wrong

What can go wrong

Poor QA extraction during write phase. If the initial document-to-QA encoding misses important details or creates incomplete questions, the network will have gaps. Queries touching those blind spots will rank chains poorly or fail to answer at all. Quality of the GSW depends heavily on the document parser and QA model used.
Entities and events are ambiguous or mislabeled. If two different entities are tagged the same name, or an event link connects unrelated QA pairs, chains will cross-contaminate. A query about Alice might accidentally follow a path about Bob because both were tagged entity_person_1.
Chain relevance scores are unreliable with multi-hop reasoning. A geometric mean can be manipulated: a chain with one very high score and many medium scores may rank higher than a chain with all solid scores. For deeply nested reasoning, the model may need to re-rank by different metrics (e.g. final-hop specificity) to avoid false confidence.
Done right. Strong QA extraction, careful entity resolution, and validation of chain rankings on development data ensure the network stays coherent and the model only retrieves when it is confident.
What a runnable demo should prove

What a runnable demo should prove

Build a small QA network from three short documents (e.g. Wikipedia excerpts about three historical figures, each 300 tokens). Parse each into a hand-crafted GSW: extract 5-8 question-answer pairs per document, link them by named entities (person names, dates, places) and events (born, died, discovered, published). Then run five multi-hop queries (e.g. 'What did Alice accomplish after Bob's discovery?') and count: (1) how many inference tokens were used to retrieve and ground the answer, (2) whether the final answer is grounded only in high-scoring chains or includes dangling unranked hops, (3) whether the answer is factually correct and never hallucinates.

The demo must make it impossible to miss that PANINI answers the same multi-hop questions with a fraction of the compute and zero made-up facts.
