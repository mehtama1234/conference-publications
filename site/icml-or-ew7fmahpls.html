Motion Dynamics Learning for Few-Shot Embodied Adaptation

A robot learns new tasks with few examples by extracting and reusing patterns of how movements evolve over time, rather than just copying individual actions.

Paper explainersAll themesRobotics & Control

Vision-language-action models (systems that take pictures and text commands to control robot arms) need many task examples to learn something new. This paper says: those models waste information. The real treasure is how actions flow together in a sequence—the motion patterns. By learning those patterns once and reusing them, robots can adapt to new tasks with just 20 examples instead of hundreds.

Zero assumption version

The wasteful copy-and-paste approach

A trained vision-language-action model can see a picture and understand a command. But when you ask it to do a new task (like "pick up a red cup instead of a blue one"), it struggles. So you show it examples: "here's what picking up a red cup looks like." You show it 50, 100, 200 examples until it learns.

The problem: each example is treated as a standalone action. "Pick up, move right, release" — the model treats each motion independently, like three separate pictures. But in reality, those three motions form a single flow, a sequence where each step flows naturally from the last. A model that copies individual actions misses that the second motion wouldn't make sense without the first.

A beginner would just feed more examples. But that scales poorly: every new task demands hundreds of fresh examples. The model has to start almost from scratch each time.

The method in one sentence. Learn how movements evolve together as sequences, store those patterns in a library, and build new task motions by mixing patterns from the library.

The algorithm as a flow

What it actually does

Step 1: Extract motion from sequences

Take a full example trajectory (pick up, move, release). Reverse-engineer the invisible pattern that generated it.

Step 2: Compress into a code

The pattern becomes a compact list of numbers representing the motion's essence (not the raw coordinates).

Step 3: Build a library

Collect patterns from hundreds of diverse demonstrations. Group similar patterns. Each pattern in the library represents a reusable motion primitive.

Step 4: Constrain new tasks to the library

When learning a new task, the model can only generate actions by mixing patterns from the library. This forces it to reuse what it already knows.

Step 5: Learn the mix

With just 20 new examples, the model learns which library patterns to blend and how to blend them for the new task.

What the paper changes

What changes: from actions to motion codes

Instead of learning individual actions, the system learns codes—compact numbers that capture the essence of how an arm should move. When the model needs to act, it picks codes from a library and activates them, rather than generating raw action coordinates from scratch.

the object it moves  =  motion codes
The hidden quantity

The motion pattern: a learned representation of trajectory evolution

measured quantity  =  motion dynamics code

A motion dynamics code is a compact list of numbers (learned during training) that captures the essence of how an action sequence should flow: the typical rising and falling of joint speeds, the relationship between different arm movements, the rhythm. It is not the trajectory itself—those are raw coordinates. It is the hidden pattern that, when combined with a specific task context, generates sensible trajectories.

The paper estimates it via flow-matching inversion: given a real trajectory, a neural network learns to reverse-engineer the code that would have produced it. You show the finished motion and ask, 'what code generated this trajectory?'

Plain reading. A motion code is the hidden recipe for how an arm should move: the timing of speed changes, the coordination between joints, whether movements should be smooth or jerky. It's learned from examples and stored in a library.
Paper reading. Motion dynamics codes are hidden numerical representations distilled via flow-matching inversion. They span a learned space where similar trajectories cluster close together, and the arrangement captures the structure of valid motions.
Why it works

Why reusing motion codes makes few-shot learning work

A robot's arm movements are not random. When you pick up something, there are only a few sensible ways to do it: smooth and careful, or quick and confident. The arm rarely jerks between extremes. This structure is the motion prior—knowledge built into how movement works.

The paper's insight: instead of forcing the model to learn this structure from scratch for each new task, learn it once from hundreds of demonstrations, store those learned structures, and then reuse them. When a new task arrives with only 20 examples, the model doesn't have to invent motion patterns. It just learns which stored patterns to activate and how to blend them.

Because the library already contains realistic motion patterns, the model can learn a new task's motion behavior from fewer examples. The 20 examples only need to teach, 'for this new scenario, blend pattern A at 70%, pattern B at 30%, and blend them like this.' That is far easier than learning the motion patterns themselves from 20 examples.

The motion code equation

First in words:

The motion generation score is the distance between the inferred code and the library, weighted by task-specific blend factors. The learning goal minimizes this distance while keeping the blend factors simple.

Then the compact form:

L = ||z_inferred - sum_k w_k * z_library_k||^2 + lambda * ||w||_1

Every symbol:

z_inferredthe motion code extracted from a single example
z_library_kthe k-th motion pattern stored in the library
w_khow much to use pattern k for this new task (learned from the 20 examples)
lambdaa penalty that encourages using fewer patterns (keeps the blend simple)
||...||^2the squared distance (how far apart two codes are)
||w||_1the sum of all blend weights (counts how many patterns are active)
A tiny worked example
Suppose one example trajectory inverts to code z_inferred = [3.0, 2.0, 1.0]. The library holds three patterns: z_1 = [2.8, 2.1, 0.9], z_2 = [3.2, 1.8, 1.1], z_3 = [2.9, 1.9, 1.2].
The model tries blend weights w = [0.6, 0.4, 0.0]. It constructs library blend = 0.6 * [2.8, 2.1, 0.9] + 0.4 * [3.2, 1.8, 1.1] = [2.96, 2.04, 0.96].
Distance squared: (3.0 - 2.96)^2 + (2.0 - 2.04)^2 + (1.0 - 0.96)^2 = 0.0016 + 0.0016 + 0.0016 = 0.0048. Penalty (using 2 patterns): lambda * 1.0 = 1.0 if lambda = 1.0.
Total loss: 0.0048 + 1.0 ≈ 1.00. Lower blend weights or match the library better to reduce loss.

The equation forces the inferred codes to lie on the library, measured as weighted combinations of stored patterns. A low penalty on the sum of blend weights means the new task is built from as few library patterns as possible.

What can go wrong

What can go wrong

Library is too limited. If the library was trained on only a few robot arms or scenarios, it might not contain patterns for a very different new task. The model cannot blend patterns it has never seen.
New task is unlike the training examples. If the new task requires a motion pattern the library has never seen (for example, movements under water where drag is high), and the library was trained only on air, the model cannot build it from library patterns. The 20 examples are not enough for it to learn something completely new.
Inversion fails on poor examples. If the 20 examples are clumsy or unnatural (the demonstration was sloppy), flow-matching inversion may extract a distorted code that does not align well with the library. The model then fits the wrong pattern.
Done right. The library is diverse (many robot types and scenarios), the new task is a reasonable variant, and the 20 examples are clean and representative. The model learns quickly.
What a runnable demo should prove

What a runnable demo should prove

Build a simple embodied task: a simulated arm reaching to different colored cups. Pre-train a motion library on 500 diverse reaching and grasping examples (use at least 5 different cups, 5 positions, 2 arm speeds). Then present the system with a new variant it has never seen (for example, a smaller or larger cup). Give it 20 labeled examples of this new variant. Measure success rate: can the arm reach and grasp the new cup.

success_rate = (number of successful grasps) / (number of test attempts)

The demo must show that with 20 examples, the system solves the new variant faster than a model without a motion library would solve it with 50 examples, because the library provides ready-made motion structure instead of forcing the model to discover it from scratch.
