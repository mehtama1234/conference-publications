KernelCraft: Benchmarking for Agentic Close-to-Metal Kernel Generation on Emerging Hardware

This paper benchmarks whether an agent can write and refine low-level compute code for new accelerator instruction sets by using function calls and execution feedback.

Paper explainersAll themesAgents & Tool Use

Emerging accelerators often arrive before a mature software stack exists around them. This paper asks whether an agent can already help by generating a kernel, which here means a short low-level program for one compute task, even when the hardware instruction set is new.

Zero assumption version

New accelerators need hand-written low-level code, and that slows deployment

A new accelerator often exposes a fresh instruction set and unusual performance tradeoffs. Developers must then hand-write low-level compute code for many tasks before the hardware can serve real workloads well.

Large language models have shown progress on mature GPU stacks, but that does not answer the harder question here: can an agent write correct and useful low-level code for hardware it has not seen before, using only tools, feedback, and iterative revision?

The idea in one sentence. Build a benchmark around tool use and execution feedback, because writing for a new accelerator is an iterative engineering task rather than a one-shot text task.

What it actually does

Define hardware-task pairs

Choose several emerging accelerators and many machine-learning workloads with varied configurations.

Expose tools through function calls

Let the agent call tools that compile code, run tests, and report performance feedback.

Run multi-step code generation

Give the agent several refinement rounds instead of one final answer.

Check functional correctness

Require the produced low-level code to match the expected task output.

Compare useful performance

Measure whether the generated code matches or beats compiler-produced baselines.

What the paper changes

What the paper changes

The paper changes the evaluation target for hardware code generation. Instead of judging only static code output, it evaluates an agent inside a feedback-driven workflow with tools and iterative revision.

The hidden quantity

The hidden quantity: Adaptation to unseen instruction sets

measured quantity  =  how well the agent converts tool feedback into useful code on hardware it has not seen before

This hidden quantity is more than plain code correctness. It asks whether the agent can adapt its behavior when the accelerator is unfamiliar. The benchmark needs to expose that adaptation skill because new hardware matters exactly when existing examples are scarce.

The paper measures adaptation through a workflow that includes tool calls, multiple refinement rounds, and performance comparison. That setup reveals whether the agent can use feedback productively instead of merely restating common code patterns.

Why it works

Why the benchmark is informative

A plain code-generation benchmark would hide the actual engineering loop. In practice, low-level code for new hardware is written by trying an implementation, reading tool feedback, and revising. The benchmark becomes informative because it recreates that loop instead of flattening it into one text output.

The performance comparison matters because correct code is not enough. A generated low-level program helps the hardware development cycle only when it reaches useful speed. By checking correctness and then comparing against compiler baselines, the benchmark shows whether the agent contributes practical value.

Math after the picture

The core equation

First in words:

A strong benchmark score should reflect both whether the code works and whether its performance is useful against a baseline implementation.

Then the compact form:

benchmark_score = correctness_rate * performance_ratio

Every symbol:

correctness_ratehow often the generated code produces the expected result
performance_ratiohow close the generated code comes to the baseline speed, or how much it exceeds it
benchmark_scorea combined view of usefulness for the agent
A tiny worked example
Suppose an agent produces correct code for 8 out of 10 workload settings, so correctness_rate is 0.8.
Suppose the average performance ratio on those settings is 0.9 relative to the compiler baseline.
Then benchmark_score is 0.8 times 0.9, which is 0.72.
A second agent with the same correctness but a ratio above 1.0 would score higher, because it would be matching or beating the baseline more often.

This simple score shows the two-part requirement. Correct but slow code and fast but wrong code are both insufficient.

What can go wrong

What can go wrong

The tools reveal too little. If compile and execution feedback are too coarse, the agent cannot tell which code edit would address the failure.
The workloads are too narrow. If the benchmark covers only a few simple operations, strong scores may not transfer to the broader hardware development cycle.
The baseline is weak. A generated program can look strong against a poor compiler baseline even when the real code quality is modest.
Done right. The benchmark is most useful when the hardware set is diverse, the workloads cover real engineering cases, and the feedback tools are detailed enough to support revision.
What a runnable demo should prove

What a runnable demo should prove

Build a small benchmark with one or two emerging accelerators, a set of machine-learning operations, and tool calls for compile, run, correctness check, and performance reporting. Evaluate two systems: a one-shot code generator and a function-calling agent that may revise its answer several times. Record correctness, performance ratio, and the number of refinement rounds used.

The demo proves the paper's point if the feedback-driven agent reaches more correct and more useful low-level code on the unfamiliar hardware, because the iterative tool loop gives it a way to adapt during the task.

agent_lift = benchmark_score(feedback_agent) - benchmark_score(one_shot_generator)

A strong demo should include at least one case where the first attempt fails and later tool-guided revisions repair both correctness and performance.
