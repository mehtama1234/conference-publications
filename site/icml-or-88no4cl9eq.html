Escaping Whack-a-Mole: Optimizing Documentation as Repo-Specific Playbooks for Coding Agents

Treat repository documentation as an executable playbook for coding agents, then improve that playbook in dependency order so fixing one function's instructions does not break all of its callers.

Paper explainersAll themesAgents & Tool Use

Documentation usually explains code to humans. This paper asks what documentation helps an autonomous coding agent solve repository tasks correctly, because an agent needs explicit operational guidance rather than prose that assumes a human reader will fill in missing details. Its answer is to treat documentation as a repository-specific playbook and improve it using downstream task correctness as the only real score, because correct task completion reveals whether the text actually guided the agent well. The key complication is output coupling: changing one entity's documentation can silently break the entities that depend on it.

Zero assumption version

Why ordinary documentation is a weak interface for coding agents

A coding agent does not need tasteful prose. It needs instructions that tell it exactly how repository entities behave, what assumptions callers must satisfy, and which tests reveal breakage. Standard documentation often leaves those details implicit because human readers can infer them from the surrounding code. Agents fail more often because they follow the text literally.

Improving one documentation block at a time is harder than it sounds. Repository entities depend on one another, so changing the explanation for a callee can invalidate the caller's explanation. A naive search then becomes a whack-a-mole process: fix one part, break another, fix the second, break the first again. The paper solves this by searching in dependency order, because caller instructions should be refined only after the callee behavior they rely on is already stable.

The move. Optimize documentation for downstream code correctness, but refine entities in callee-before-caller order so later edits build on already stabilized behavior descriptions.

The algorithm as a flow

What it actually does

Build the dependency graph.

Program entities such as functions, classes, and modules are linked by caller-callee or use relationships.

Choose the next entity by dependency order.

The outer search selects which entity to refine next, preferring ones whose dependents are already stabilized.

Generate several documentation rewrites.

The inner search proposes multiple candidate descriptions for that entity so that the system can compare alternatives instead of trusting one rewrite.

Test the candidates with coding-agent feedback.

The repository tasks and generated unit tests reveal which rewrite helps code correctness most directly because the winning rewrite causes the agent to pass more real task checks.

Lock the best rewrite and continue upward.

Once a callee description is chosen, callers can be refined on top of that stable base.

What the paper changes

What the paper changes

The paper changes what documentation is for. Instead of treating it as prose for a human reader, it treats it as an operational interface for a coding agent. That means the quality of documentation is judged by whether the agent writes correct code in that repository, not by whether the text sounds polished in isolation.

the object it moves  =  Documentation as an operational interface for coding agents
The hidden quantity

The hidden quantity: downstream interference

measured quantity  =  Downstream interference between entity descriptions

The hidden quantity here is how much a rewrite for one entity disturbs the usefulness of documentation elsewhere in the repository. If entity A calls entity B, and B's behavior description changes, A's description may become partly wrong. That interference is what creates the repeated fix-break cycle.

DocSearch reduces this hidden quantity by enforcing dependency order. When a callee description is stabilized first, the caller rewrite can reference that settled behavior. This lowers the chance that future edits will invalidate earlier work, so the search escapes the endless local repair loop.

Why it works

Why it works

The method works because it aligns the search order with the program's actual dependency structure. A caller's useful description depends on the behavior of its callees, so optimizing the caller too early is unstable. By refining lower-level entities first, the system turns the repository into a stack of increasingly stable descriptions that later rewrites can rely on.

The inner candidate search matters too. One rewrite may expose preconditions clearly, while another may explain failure modes better. Testing several rewrites against agent performance and unit-test feedback improves solve rate because the chosen text is the one that most directly helps the agent produce correct code, not the one that merely sounds plausible.

Math after the picture

The search objective

First in words:

Choose the rewrite sequence that maximizes agent solve rate while paying a penalty when an edit destabilizes dependent entities.

Then the compact form:

score = solve_rate_after_rewrite - lambda * dependency_breakage

Every symbol:

solve_rate_after_rewritefraction of repository tasks solved after the current documentation update
dependency_breakagenumber or severity of dependent entities whose behavior guidance became less useful
lambdapenalty weight for interference with dependents
scorethe value used to compare candidate rewrites
A tiny worked example
Rewrite A raises solve rate from 60 to 72 but causes 8 units of dependency breakage.
With lambda = 1, score(A) = 72 - 8 = 64.
Rewrite B raises solve rate from 60 to 70 and causes only 2 units of dependency breakage.
Score(B) = 70 - 2 = 68.
The search keeps Rewrite B because a slightly smaller immediate gain is worth it when it leaves the rest of the repository more stable.

The exact breakage measure can vary, but the principle stays the same: repository-wide usefulness matters more than a flashy local rewrite.

What can go wrong

What can go wrong

Wrong dependency graph. If the graph misses important caller-callee relations, the search order can still destabilize the repository because a supposed leaf entity may actually feed many dependents.
Weak test feedback. If the unit tests do not exercise the real failure cases, the search may select rewrites that look useful under shallow feedback but do not actually help coding tasks because the feedback loop never exposed the missing behavior.
Overfitting to one benchmark style. A repository playbook tuned only to one task set may become too narrow, so the same documentation helps those tasks but not broader maintenance work because it only learned the failure patterns present in that narrow benchmark.
Done right. Extract dependencies carefully, use strong task and test feedback, and evaluate across varied repositories so the playbook captures repository behavior rather than a single benchmark quirk.
What a runnable demo should prove

What a runnable demo should prove

Take a small repository with a clear call graph and a set of repair tasks. Compare two documentation optimization loops: local entity-by-entity rewriting in arbitrary order, and dependency-guided rewriting with a small beam over candidate descriptions. After each accepted rewrite, run the same coding-agent benchmark and generated unit tests.

The demo should show that dependency-guided documentation search reaches higher solve rate with less repeated rewriting because caller instructions stop shifting under its feet.
