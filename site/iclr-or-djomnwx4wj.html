Scaling Up, Speeding Up: Speculative Decoding for LLM Test-Time Scaling

When reasoning takes multiple steps, simple pattern-matching can guess ahead safely, cutting compute cost in half.

Paper explainersAll themesDatasets & Benchmarks & Evaluation

Large language models now spend reasoning time by running many inference passes — trying different answers, thinking through steps, or sampling alternatives. This sounds smart but wastes computation because the model keeps repeating the same phrases. The paper discovers that simple, dumb pattern-matching (looking for repeated sequences) can predict what comes next almost as well as the model can, letting you skip the expensive forward pass and just verify a guess.

Zero assumption version

Inference that repeats itself

When you ask a language model (a system that predicts the next word) to reason or think through a problem, you run the whole model many times — once to generate each answer or reasoning step. This is expensive because the graphics card has to process every token (word or piece of a word) through every layer.

The naive approach: ask the model for the next token 100 times, wait for 100 full results. The model sees that it says the same phrase in every branch — 'let me work through this' appears identically in both answer attempts. Yet it re-computes from scratch each time, burning electricity on redundant arithmetic.

The problem. During test-time scaling, language models generate highly repetitive reasoning traces, wasting computation on patterns the system will produce the same way each time.

The algorithm as a flow

What it actually does

Record what the model chose

When the model generates token 47 given the prefix 'question is', store that link.

Look ahead without paying

Next pass hits the same prefix; check the table before calling the expensive inference.

Guess and accept or reject

If the table says token 47, output it tentatively; if it does not, call the full model.

Verify the guess (single token)

Feed the guessed token back; the model's next step confirms it was right or wrong.

Build the table as you go

Each new pass adds more prefix-to-token links, making future guesses more likely to hit.

What the paper changes

What the paper changes

The paper measures three families of methods to guess the next token without a full model forward pass: models trained to predict next tokens (model-based), learnable routing weights (training-based), and simple dictionary lookups from past sequences (n-gram-based). The core move is the benchmark itself — a consistent test to compare them fairly.

the object it moves  =  the prediction method in use
The hidden quantity

Repetition density

measured quantity  =  fraction of tokens matching the history

The paper's key discovery is that reasoning traces are not uniform; some parts repeat exactly. The hidden quantity is how often the model, given a prefix it has seen before, produces the exact same next token. If you see 'Question: what is 2+2' five times across different answer attempts, it almost always generates 'Answer:' next — that match rate is high.

The paper measures this by counting when a pattern-match lookup (n-gram method) succeeds — when the exact prefix reappears and the predicted token agrees with what the model later produces. High repetition density means simple lookup tables capture the model's behavior cheaply; low density means the model is reasoning differently each time, requiring expensive forward passes.

Why it works

Why pattern-matching acceleration works

When a language model reasons, it operates token-by-token, and each token is computed by running data through many layers of arithmetic on the graphics card. These layers multiply numbers and add them up — the core work the model does. This is expensive. But the model's predictions are deterministic — the same context always gives the same output (in greedy mode). So if you have seen a long prefix before, the next token is guaranteed to be identical.

Speculative decoding trades off computation: store every prefix and its successor, then check the table before running the model. For repeated reasoning (setup phrases, verification steps, common reasoning scaffolds), this table lookup is millions of times faster than a full inference pass because checking a hash table is pure memory access, while running the model means thousands of arithmetic operations on the graphics card. The model is only called when the table has no answer, which becomes increasingly rare as reasoning fills in the table. The mechanism works because reasoning is structured and repetitive by nature — you state the problem the same way each time, verify the same way, and scaffold the same way.

When you integrate n-gram methods with model-based guessing, you capture the redundancy where it exists (common phrases) and switch to expensive prediction only for reasoning that has never appeared before. This is why the paper finds that n-gram methods alone are effective, but combining them with trained predictors is even better: together they cover both repetitive and original reasoning.

Math after the picture

Speedup from table hits

First in words:

cost = (count_of_table_hits * cost_lookup) + (count_of_misses * cost_model_pass)

Then the compact form:

speedup = total_tokens / (hits * lookup_cost_ratio + misses * model_pass_cost_ratio)

Every symbol:

hitsnumber of times table lookup succeeds
missesnumber of times no table match found
lookup_cost_ratiocost of one table lookup, normalized to 1
model_pass_cost_ratiocost of one full model forward pass (typically 1000 to 10000 in real hardware)
A tiny worked example
Suppose: 100 tokens generated, 80 table hits, 20 model passes.
Cost per table hit: 1 unit (instant). Cost per model pass: 1000 units (GPU arithmetic).
Naive cost (no table): 100 * 1000 = 100,000 units.
With table: (80 * 1) + (20 * 1000) = 80 + 20,000 = 20,080 units.
Speedup: 100,000 / 20,080 ≈ 5x. If reasoning were 95% repetitive: (95 * 1) + (5 * 1000) = 5,095 units, speedup ≈ 20x.

The speedup depends entirely on repetition density — how many tokens the model outputs identically given the same prefix.

What can go wrong

What can go wrong

Mismatch at low repetition. If the model's reasoning is highly exploratory and new each time (low repetition density), tables stay sparse. Table hits become rare, and the speedup collapses to nearly zero.
Table becomes outdated when model changes. If the model's outputs change after fine-tuning or prompting shifts, old table entries become stale — they say token 47 when the model now outputs token 23. Speculative decoding then produces wrong tokens.
Memory overhead from large history. Storing every prefix seen in a large-scale reasoning run can consume significant memory. Naive lookup tables scale poorly, requiring clever hash structures or caching policies.
Done right. Build tables for each reasoning type and scenario separately. Monitor repetition density; if low, skip speculative decoding. Verify predictions online; if the model later contradicts the table, discard that entry.
What a runnable demo should prove

What a runnable demo should prove

Build a simple experiment: (1) Use a small language model or a frozen pretrained model. (2) Generate reasoning traces for multiple test examples (e.g., step-by-step math or question-answering). (3) Collect all prefix-to-token pairs from the first pass. (4) On the second pass, intercept each generation request: before calling the model, check if the prefix is in the table. If yes, output the predicted token and skip the model. If no, call the model and store the new pair. (5) Measure time and output a match-rate histogram (how many prefixes repeated).

speedup = total_inference_time_naive / total_inference_time_with_table

The demo must make impossible to miss: when reasoning is repetitive, table hits are frequent, inference is dramatically faster (because skipping the model's arithmetic layers saves orders of magnitude of compute), and the output is identical to what the model would produce.
