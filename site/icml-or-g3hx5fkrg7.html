Can Agents Generalize to the Open World? Unveiling the Fragility of Static Training in Tool Use

A benchmark and training recipe for testing whether tool-using agents survive changing queries, tools, observations, and domains after training.

Paper explainersAll themesOther

A tool-using language-model agent is rarely deployed into the same exact world it saw during training. Users ask different questions, tools change their interfaces, observations arrive in new formats, and the surrounding task domain drifts. Static benchmarks hide that problem because the agent can memorize a narrow interaction pattern. OpenAgent makes the shift explicit and shows that current fine-tuning methods degrade once the environment changes along several concrete axes.

Zero assumption version

Static training rewards shortcut use of tools

A tool agent solves tasks by reading a request, choosing actions, calling tools, reading tool outputs, and deciding what to do next. In a fixed benchmark, the space of requests and tool behaviors is narrow. The agent can therefore learn a brittle script: when the prompt looks a certain way, call tool A with format B and expect observation C.

Real deployment breaks that script. A user may phrase the request differently. A tool may rename an argument. An observation may contain extra fields or missing fields. A familiar task may move into a new domain with different facts and action patterns. If the agent has only learned the benchmark surface, one small shift causes the full action loop to fail.

The core problem. Agents trained in a fixed environment often learn an interface habit, not a durable decision process, so small open-world shifts break the whole loop.

What it actually does

Define open-world shifts

Separate shifts in request wording, action interface, observation format, and domain knowledge.

Build a controlled sandbox

Create an environment where each shift can be injected on purpose instead of waiting for a real deployment failure.

Test agents trained by different methods

Measure how supervised fine-tuning and reinforcement learning agents degrade under each shift type.

Locate failure layers

Use the four-tier hierarchy to determine whether the break happens in perception, interaction, reasoning, or internalization.

Fine-tune with perturbations

Train on deliberately disturbed examples so the agent learns stable action choices across changed surface forms.

What the paper changes

What the paper changes

The paper changes both the evaluation setup and the training data. Evaluation changes from one fixed benchmark to a hierarchy of controlled shifts. Training changes from clean interaction traces to perturbation-augmented traces whose surface details vary while the underlying task stays the same. That pushes the learner to preserve task logic across changing tool conditions.

the object it moves  =  the stability of the action loop under environmental shift
The hidden quantity

The hidden quantity: open-world invariance

measured quantity  =  open-world invariance

The main quantity being tested is whether the agent keeps the same decision logic after the environment changes in ways that should not change the task. If a weather tool renames a field but still returns the same fact, a good agent should still choose the right next step. If the user asks the same job in a different wording, a good agent should still form the same plan.

OpenAgent treats this as a layered property. The agent must read changed inputs correctly, call tools through changed interfaces, reason over changed observations, and carry new facts forward into later steps. Failure at any layer breaks the final trajectory, so the benchmark separates these layers instead of reporting only one final score.

Why it works

Why the hierarchy and perturbations matter

A single aggregate score hides where an agent is fragile. Suppose a run fails after a tool call. The root cause could be that the agent misread the user request, used the wrong tool argument format, failed to interpret the returned observation, or never updated its internal working state after new evidence arrived. OpenAgent separates these points because each one needs a different repair.

Perturbation-augmented fine-tuning works by breaking the shortcut that static training encourages. When the same underlying task is shown with changed wording, changed tool signatures, or changed observation formatting, a brittle script no longer works reliably. The learner must attend to the semantic role of each action and observation because the surface form is unstable by design.

This should not be read as a full solution to open-world generalization. It is a pressure test plus a targeted training intervention. The paper's contribution is to turn open-world drift into concrete, controllable disturbances, so agents can be measured and improved at the actual failure boundary instead of on a frozen benchmark surface.

Math after the picture

The equation: train for success across disturbed environments

First in words:

Choose model parameters that minimize expected task loss over a family of perturbed environments rather than only over the clean training environment.

Then the compact form:

min_parameters average_task_loss_over(clean_environment + perturbed_environments)

Every symbol:

parametersthe trainable settings of the agent
task_losshow badly the full action trajectory fails on the task
clean_environmentthe original benchmark setting used for ordinary training
perturbed_environmentsversions of the same task with changed query form, tool interface, observation form, or domain details
averagethe training objective combines failures across all chosen environment versions
A tiny worked example
One task asks for a calendar lookup.
Clean version uses field name date, while a perturbed version uses start_date and returns an added timezone field.
If the agent succeeds only on the clean version, its average loss stays high because the perturbed case still fails.
The model must learn the underlying role of the argument and returned value, so both versions become solvable.

The point of the objective is not a harder benchmark for its own sake. It is to prevent the learner from binding one task to one exact interface surface.

What can go wrong

What can go wrong

Perturbations miss real deployment changes. If the disturbed training traces cover only superficial formatting changes, the agent may still fail when real tool semantics or multi-step workflows change.
Too much disturbance destroys task identity. If perturbations alter the task itself instead of its surface, training becomes noisy because the agent is punished for not solving contradictory problems.
Failure localization stays incomplete. A single failed trajectory can involve several broken layers at once, so the hierarchy helps analysis because it narrows the search for causes, but it does not guarantee one clean cause per run.
Done right. The setup is most useful when each perturbation preserves the underlying task, each layer has a clear diagnostic meaning, and training covers enough variation to block narrow interface scripts.
What a runnable demo should prove

What a runnable demo should prove

Build a small tool sandbox with three tasks, such as calendar lookup, table filtering, and file search. For each task, create a clean version and several shifted versions: changed user phrasing, renamed tool arguments, and changed observation keys. Train one agent on the clean traces only and a second agent on the clean plus perturbed traces.

The demo should report success by shift type and save full trajectories. A useful output is a confusion table that shows which layer broke first on each failed run. That makes visible whether the augmented agent truly preserves task logic or merely memorizes a larger set of surface patterns.

robust_success = average_success_across_shifted_environments

A convincing result shows that the augmented agent keeps more of its success after each shift because it has been trained to separate the task from the exact wrapper used to express it.
