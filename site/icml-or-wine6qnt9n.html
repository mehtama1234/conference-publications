CoMem: Context Management with A Decoupled Long-Context Model

Run two models in parallel so the agent does not have to wait for the memory compressor to finish.

Paper explainersAll themesEfficiency & Systems

When an agentic model solves a long task, it accumulates a huge history of steps and observations. Compressing that history (summarization) is necessary to save memory, but it takes time. CoMem decouples the compression into a separate, slower model that runs at the same time as the agent's decision-making, so the agent's waiting time shrinks.

Zero assumption version

Long-context agents are bottlenecked by summarization

An agentic model is a system that repeats a cycle: the agent decides what to do, executes it in an environment, observes the outcome, and moves to the next step. Over many steps, the history grows enormous. If the agent has to read all of it on every step, the computation explodes.

A naive solution is to compress the history before each new step: run a summarization model, wait for the compressed version, then run the agent. This works, but the waiting time piles up. If summarization takes 500 milliseconds and you do it for 100 steps, you lose 50 seconds of latency.

In one sentence. Split the summarization into a separate process running at the same time as the agent, so they do not block each other.

The algorithm as a flow

What it actually does

Agent step t: read latest summary + recent k steps

Agent quickly makes a decision using a small context window.

Execute action, observe outcome

World responds; agent appends observation to history.

Every k steps: launch asynchronous summarizer

Smaller memory model starts compressing background; agent keeps going.

Synchronize: receive new summary

When summarizer finishes, replace old summary; discard full history.

Repeat with shorter context

Next cycle uses compressed summary instead of full history.

What the paper changes

What the paper changes

Instead of waiting for the summarizer to finish before the agent moves, CoMem launches the summarizer in the background and lets the agent continue. The agent only pauses when it actually needs the new summary.

the object it moves  =  pipeline execution order (sequential to asynchronous)
The hidden quantity

The hidden quantity: summary staleness

measured quantity  =  summary staleness (how old the summary is)

Staleness measures how many steps have passed since the summary was last updated. In a synchronous system, staleness is zero because the agent always waits for a fresh summary. In CoMem's asynchronous pipeline, staleness grows: the agent reads an older summary while the memory model is busy updating it in the background. Larger k (more steps before a summary refresh) means higher staleness.

The paper's key insight is training the memory model (via a reward signal) to ensure that even stale summaries guide the agent well. The reward compares the agent's decision under the compressed summary to the decision the agent would make if it had the full history. If they match, the summary is good enough despite being old.

Why it works

Why it works: overlap hides latency

The core mechanism is simple: summarization and decision-making are independent tasks. Summarization reads the old history and produces compressed text. Decision-making reads a summary and picks the next action. These two can happen simultaneously on different hardware (the summarizer on one GPU, the agent on another) without the agent waiting for the summarizer to finish.

The k-step-off pipeline manages the timing. At step t, if t is a multiple of k, the summarizer launches asynchronously (not blocking the agent). For the next k−1 steps, the agent runs with a slightly stale summary. When t reaches the next multiple of k, the summary is ready and swapped in. The agent never blocks; it only synchronizes when the summary is actually ready. This works because the synchronization point arrives just before the summary becomes dangerously stale.

The second mechanism is reward-driven training. A stale summary might make the agent take a different action than the full-context agent would. The paper trains the memory model to minimize this divergence by using a reward signal: if the agent's action under the compressed summary matches the full-context agent's action, the summary gets high reward. The memory model learns to distill the most decision-critical information into the summary, not redundant or decorative details.

Math after the picture

Equation: reward-driven summary alignment

First in words:

Reward for a summary s equals how similar the agent's action under s is to the agent's action under full history.

Then the compact form:

R(s) = similarity( agent_action(summary=s), agent_action(summary=full_history) )

Every symbol:

R(s)the reward score for a summary s (how good it is)
agent_action(summary)the action the agent chooses given a summary
similaritya match score (1 if actions identical, lower if different)
sthe compressed summary from the memory model
full_historythe raw, uncompressed interaction record
A tiny worked example
Full history: [user asks for bug fix, code snippet loaded, 10 failed attempts, error message, user notes edge case].
Compressed summary: [user asking for bug fix, edge case noted].
Full-history agent action: investigate edge case (because it saw the edge case explicitly).
Agent under summary action: investigate edge case (because summary includes edge case). Similarity = 1.0.
A bad summary [bug fix requested, nothing else]: full-history agent says investigate, compressed-summary agent says give up. Similarity = 0.2.
Training the summarizer to maximize R means learning to keep the edge-case detail, not drop it.

The memory model learns to distill only decision-relevant information, ignoring redundancy.

What can go wrong

What can go wrong

Summary staleness breaks the agent. If k is too large (wait too long between summaries), the summary gets so old it misses recent context and the agent diverges. CoMem mitigates this by training on stale summaries to learn which details matter most.
Synchronization delay defeats the purpose. If the summarizer is so slow it is still not done when k steps finish, the agent has to wait anyway, and latency does not improve, because the agent cannot proceed without a fresh summary and loses all the time saved by running asynchronously. CoMem works only when the summarizer is fast enough to finish within k agent steps.
Reward signal is noisy. If the full-context agent's actions are random or context-insensitive, the reward does not guide the memory model. Weak reward signals mean the compressed summary learns spurious details instead of decision-critical ones.
Done right. Choose k such that the summarizer finishes comfortably before the next refresh. Train on the same task distribution as deployment. Monitor divergence (how often compressed-summary actions differ from full-context actions) to catch staleness problems early.
What a runnable demo should prove

What a runnable demo should prove

A minimal demo runs a two-model loop: a large (full-context) agent and a smaller (memory) model. Set up a toy long-horizon task (e.g., simulate 100 steps of a navigation or coding task). At each step, measure: (1) wall-clock latency per step, (2) divergence (percentage of steps where agent action under stale summary differs from full-context action). Run both synchronous (wait for memory model) and asynchronous (k-step-off with k=2). Measure latency speedup and divergence cost.

latency_reduction = (synchronous_time - asynchronous_time) / synchronous_time; divergence_cost = (steps_where_actions_differ) / (total_steps)

The demo must show that latency drops without catastrophic divergence: speedup should be >1.1x and divergence <15%.
