The Alignment Waltz

Train two agents together — one to chat safely, one to give safety feedback — so they improve each other instead of one just blocking the other.

Paper explainersAll themesAlignment, Safety & Fairness

Language models face two opposite safety problems: they can be tricked into generating harmful content, or they refuse to answer normal questions that sound risky. Most solutions just block everything that looks unsafe, which loses helpfulness. WaltzRL teaches the model a collaborative trick: a feedback agent learns to diagnose when the main agent stumbles (unsafe or overly cautious), then the main agent learns to incorporate that feedback and fix itself, because each agent is rewarded when it helps the other — both improve together, during training and when answering user questions.

Zero assumption version

The safety dance has no middle ground

A language model can be tricked. Ask it the right way and it will explain how to do something harmful. This is the jailbreak problem. On the other side, models are often too cautious. Ask about a sensitive topic — say, the history of a controversial figure — and the model refuses to engage, even though a thoughtful answer would help, because the model's safety training has no middle ground between blocking and allowing. Most current safeguards work like a bouncer: if any part of a response looks unsafe, the whole thing gets rejected. This 'just block it' approach prevents jailbreaks, but it also blocks legitimate requests, because the model cannot distinguish context. The model gives no guidance, no chance to improve, and the user is left with nothing, because a block is the end — no chance for the model to learn or the user to push back.

A naive first attempt: train a single model to be both truthful and cautious. But this is like asking someone to argue both sides of a debate while staying neutral — the goals pull in opposite directions. The model gets caught between them, either failing at one or doing both weakly.

The core move. Instead of one model deciding safety, use two agents that collaborate: the main agent learns to be helpful, and a feedback agent learns to catch safety problems and suggest fixes. They train together, each making the other better, because each agent is only rewarded when it helps its partner improve.

The algorithm as a flow

What it actually does

Collaborative rollout

Conversation agent makes a draft. Feedback agent looks at it, decides if it is unsafe or overrefused, suggests a fix. They go back and forth until done.

Label the situation

Mark each exchange: was the conversation agent unsafe, overcautious, or on target? This teaches the feedback agent to recognize the problem.

Reward each agent separately

Conversation agent gets a score for safety and helpfulness. Feedback agent gets a score based on whether the conversation agent actually improved when it got feedback.

Both learn in parallel

Each agent sees its own reward and updates its decision-making. They do not fight — they each get a signal about a different job.

Deploy as a pair

When answering user questions, the conversation agent makes an answer, feedback checks it. If the answer is risky or overly cautious, feedback suggests a fix. If the answer is fine, feedback stays quiet and the latency cost is near zero.

What the paper changes

What the paper changes

The paper changes who decides on safety: instead of one model judging everything, it trains two separate agents, each with its own job. The conversation agent learns to be helpful and responsive. The feedback agent learns to spot when the conversation agent goes wrong and how to fix it. They co-evolve — each improves as the other improves, because they are rewarded for helping each other, not for being right in isolation.

the object it moves  =  the control structure: one agent to two collaborating agents
The hidden quantity

The improvement reward: how much did this feedback actually help?

measured quantity  =  improvement in conversation agent's response

The core hidden quantity is the improvement score: a measure of whether the feedback agent's advice actually makes the conversation agent better, not whether the feedback sounds good, because what matters is whether feedback nudges the conversation agent toward safer, more helpful answers, not whether it sounds correct in isolation. The paper measures this by comparing the conversation agent's response before and after feedback. If the response improved (safer, more helpful, less refusal), the feedback agent gets a reward. If nothing changed, the feedback agent gets nothing, because a reward only comes from real change, not from attempting to help. This teaches feedback to give advice that the conversation agent can actually use.

This is how they solve the coordination problem. In a single-model setup, there is only one signal to optimize. Here, the feedback agent is rewarded for usefulness, not just correctness. A piece of feedback that the conversation agent ignores does not help — so the feedback agent learns to communicate in a way that the conversation agent can absorb, because ignored feedback brings no reward.

Why it works

Why collaboration beats blocking

The core reason this works: when you train two agents with aligned goals but different jobs, they have to communicate in ways the other can use. The feedback agent is not trying to be right in isolation — it gets no points for being correct if the conversation agent does not act on the feedback. So it learns to diagnose problems clearly and suggest fixes that the conversation agent can parse and execute. The conversation agent, in turn, learns that listening to the feedback agent makes it do better (safer and more helpful), so it learns to incorporate suggestions gracefully. They co-evolve a shared language of improvement.

Blocking (the old approach) teaches nothing. A response either passes a rule or gets rejected. The model never learns why it was wrong or how to do better, because it only sees pass/fail, not guidance. The users never get nuance. Collaboration (WaltzRL) builds a two-way channel: the feedback agent learns to diagnose, the conversation agent learns to listen, and the dialogue is preserved even when there is a safety issue, because feedback is a suggestion, not a gate. At inference time, the feedback agent only speaks up if needed — on truly safe queries, it stays silent and the latency is the same as a normal inference.

The third insight: multiplying the surface area for attack. One strong attacker might jailbreak a single model. But to fool WaltzRL at inference, an attacker would need to jailbreak both the conversation agent and the feedback agent. Each agent was trained on different objectives and examples, so they learn different decision boundaries. One exploit might work on one agent but not the other.

Math after the picture

The reward formula

First in words:

Maximize the sum of rewards to the conversation agent and feedback agent, minus a penalty for each agent if it drifts too far from its starting point. The feedback agent's reward depends on how much the conversation agent improved after receiving feedback.

Then the compact form:

max R_c(prompt, conversation_response) + R_f(prompt, conversation_response, feedback) - beta * KL_divergence(conversation_agent, initial_conversation_agent) - beta * KL_divergence(feedback_agent, initial_feedback_agent)

Every symbol:

R_creward to the conversation agent for safety and helpfulness of the response
R_freward to the feedback agent based on improvement in the conversation agent's response after feedback
betahow strongly we penalize each agent for drifting from its starting weights
KL_divergencea measure of how different two probability distributions are; small KL means the agent did not forget its initial training
conversation_responsethe answer the main agent produces
feedbackthe diagnostic and suggestion from the feedback agent
A tiny worked example
Setup: user asks for code to hack a system (jailbreak attempt). Conversation agent produces an unsafe response (bad, score 0). Feedback agent diagnoses: unsafe, suggests a rewrite that declines politely. Conversation agent takes feedback and produces a safe response (good, score 100).
Conversation agent reward: 100 (responded safely after feedback).
Feedback agent reward: 100 (feedback caused a real improvement, from 0 to 100). Bonus — did not damage helpfulness.
If feedback gave a suggestion the conversation agent ignored, feedback score drops to 0. This teaches feedback to give actionable suggestions.
If conversation agent drifted completely (forgot all safety training), the KL penalty kicks in and adds a cost to the objective. Both agents stay grounded.

The formula trains two agents with separate rewards so they stay coordinated: each agent gets a signal about its own job, not a muddy combined signal that pulls in two directions.

What can go wrong

What can go wrong

Feedback agent learns to be a yes-man. If the reward for improvement is too high, the feedback agent might learn to praise anything the conversation agent does, just to get a reward, because it optimizes for the signal it sees. This requires careful tuning: the reward for actual improvement must be real, and silence (not giving feedback) when none is needed must also be rewarded.
Conversation agent ignores feedback. If the conversation agent is trained on a weak signal or examples of feedback are too abstract, it might fail to parse the feedback, because it cannot map words to actionable changes. The two agents have to learn a shared language. This is solved by training them jointly from the start so they co-evolve communication.
Latency cost at inference on safe queries. If the feedback agent runs every time, every query gets slower. The paper addresses this with an adaptive deployment: feedback agent only runs when the conversation agent's initial response is flagged as potentially unsafe or overrefused. On truly safe queries, feedback stays silent and latency is unchanged.
Done right. WaltzRL works when the two agents are trained jointly, with separate but aligned objectives, and feedback is only deployed when actually needed. Latency cost shrinks because feedback stays silent on safe queries, both safety and helpfulness improve because each agent is rewarded for genuinely helping the other, and the feedback is genuine improvement, not just noise, because the feedback agent only gets a reward when the conversation agent actually incorporates its suggestion.
What a runnable demo should prove

What a runnable demo should prove

Build a small demo with a language model (even a small 7B-parameter model works) fine-tuned on safety examples. Set up two separate instances: one conversation agent, one feedback agent. Run both on adversarial jailbreak prompts (examples designed to trick the model). First, show the unsafe response from the conversation agent alone. Then, run the feedback agent: it should diagnose the problem (unsafe) and suggest a safe rewrite. Finally, show the conversation agent incorporating that feedback and producing a safe response. Repeat on a benign but sensitive topic (e.g., a question about a controversial historical figure): the feedback agent should recognize overrefusal and suggest a more balanced response. Measure before-and-after safety scores on both agents separately.

improvement = (safety_score_after_feedback - safety_score_before_feedback) + (helpfulness_score_after_feedback - helpfulness_score_before_feedback). If this is positive, feedback helped. If zero, feedback was ignored. The feedback agent's reward should correlate with improvement.

The demo must make clear that feedback is not blocking — it is coaching. A response does not disappear; it gets better. The feedback agent only speaks when it sees a real problem, and the conversation agent learns to act on that feedback because it is rewarded for improvements that result.
