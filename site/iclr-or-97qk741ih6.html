CLAUSE: Agentic Neuro-Symbolic Knowledge Graph Reasoning

A three-agent system learns to build compact knowledge-graph subgraphs under time and cost limits by treating it as a sequential decision problem.

Paper explainersAll themesAgents & Tool Use

When a system must answer multi-step questions using a knowledge graph (a database of facts and their connections), it faces a dilemma: fetch too little context and the answer is wrong; fetch too much and the system runs slow and expensive. This paper introduces CLAUSE, which trains three separate agents to jointly decide what facts to retrieve, which paths to follow, and when to stop—all while staying under strict time and cost budgets that change per question.

Zero assumption version

The problem: Static retrieval wastes time and money

A knowledge graph is a database where facts are nodes (e.g., cities, people) and connections between them are edges (e.g., 'was born in', 'visited'). To answer 'Where was the founder of Tesla born?', the system must follow edges: find Tesla, then find its founder, then find where they were born.

Today's systems use fixed rules: 'always expand two hops from the question' or 'retrieve 100 nearby facts'. This wastes resources. For easy questions, 100 facts are overkill; for hard questions, two hops miss the answer. Each query takes the same time and cost, whether it is simple or complex.

A curious 12-year-old would try: 'Just grab enough facts to answer the question, and no more.' But the system does not know in advance which facts matter, so it must either guess (and often get it wrong) or over-retrieve (and waste time and money).

The challenge. Decide what facts to fetch and when to stop, adapting to each question's difficulty. The system cannot know ahead of time which facts will matter, but it can learn to estimate their value from feedback.

The algorithm as a flow

What it actually does

Question arrives with a budget

System gets the question, a time limit (latency budget), and a token-count budget (cost budget).

Subgraph Architect proposes which edges to expand

First agent: 'Here are the edges from the question entities—which should we follow?' Scores them by how likely they are to lead to the answer.

Path Navigator explores and decides when to backtrack

Second agent: 'Follow this edge or double back?' Keeps track of which paths exhausted and which still look promising, staying under the step budget.

Context Curator keeps only the useful facts

Third agent: 'Among all the facts we found, which ones actually help answer the question?' It trims the subgraph to keep only facts that lead to the answer, because fewer words sent to the language model means faster and cheaper inference (fewer token costs to process).

Done when budget expires or question is answered

All three agents stop when time/cost limits are hit or high-confidence answer is found. Runtime is predictable.

What the paper changes

What the paper changes: Subgraph selection per query

Instead of using one fixed expansion rule for every question, CLAUSE selects a different subgraph (the set of facts and connections retrieved) for each individual question based on its difficulty and constraints.

The hidden quantity

The hidden quantity: Adaptive expansion value

measured quantity  =  Expansion value per edge

The core quantity CLAUSE measures is how much adding each edge (each connection between facts) increases the chance of finding the right answer, relative to its cost in tokens and latency. Some edges are 'hot'—they directly lead toward the answer—while others are 'free' distractions that waste budget.

The three agents jointly estimate this value at each step: the Architect and Navigator propose which edges are worth following, and the Curator filters to keep only edges that the final answer depends on. Together they optimize which facts to keep within the strict budget.

Why it works

Why it works: Three agents negotiate constraints

The three-agent setup splits the problem so each agent has a clear job. The Architect decides which edges in the knowledge graph to add (expanding the search space). The Navigator decides how many steps to explore before backtracking (controlling latency). The Curator decides which facts to keep in the final prompt (controlling token count). Normally these three would conflict: Architect wants to add everything, Navigator wants to explore forever, Curator wants to save tokens. But they are trained together using a single reward signal that measures accuracy, and each agent learns the costs of the others' choices.

The key is that latency and token limits are exposed as prices in the training loss. When the token budget is nearly full, the Curator learns to drop low-value facts first, and the Architect learns to propose fewer edges. When latency is tight, the Navigator learns to stop exploring. So the system automatically adapts: on an easy question with a big budget, all three agents are aggressive; on a hard question with tight budgets, they are conservative and precise. No retraining needed; the prices change per query.

The coordination equation

First in words:

Total reward = accuracy gain minus cost. Latency cost = spent steps times latency price. Token cost = kept tokens times token price. The three agents learn to maximize total reward under the constraint that prices scale with how close to the budget limit they are.

Then the compact form:

L = accuracy_gain - lambda_latency * steps_taken - lambda_token * tokens_kept

Every symbol:

accuracy_gainincrease in answer correctness when adding this edge or fact
lambda_latencythe price of each extra step; set per query to enforce latency budget
lambda_tokenthe price of each extra token; set per query to enforce token budget
steps_takennumber of navigation steps taken so far in this query
tokens_kepttotal tokens consumed by the selected facts
A tiny worked example
Query budget: 50 tokens, 5 steps. Current prices: lambda_token = 0.5, lambda_latency = 1.0 (set to match budget ratio).
Architect proposes edge A (founder→birthplace). Gain = 20 (likely to have answer). Cost = 20 * 0.5 (token cost) = 10.
Benefit = 20 - 10 = +10. Architect adds edge A.
Curator now has 40 tokens left. Edge B (industry connection) has gain = 2 but costs 5 tokens. Cost = 5 * 0.5 = 2.5. Benefit = 2 - 2.5 = -0.5.
Curator rejects edge B because cost exceeds gain.
After 3 steps used, latency price rises: lambda_latency = 2.0 (tighter constraint). Navigator sees next step costs 2 * 1 = 2. Gain for more steps = 5. Benefit = 5 - 2 = +3, so continue.
System hits 5 steps. Navigator stops because latency_budget is consumed. Final answer uses compact subgraph.

The three agents see the same prices, so they coordinate: when one agent is near its budget limit, its prices rise, and the other agents automatically ease up to make room.

What can go wrong

What can go wrong

Prices not calibrated to the budget. If latency and token prices are set too low, agents ignore the budget and over-retrieve. If too high, agents stop too early and miss the answer. The system relies on correctly scaling prices per query.
One agent dominates. If the Curator's token limit is very tight, it may cut edges the Navigator wanted to explore, blocking the path to the answer. The three agents must be trained together so each learns to respect the others' constraints.
Question type mismatch. Some questions (e.g., time-based relationships or implicit hops) require deeper graph exploration than the method was trained on. If the budget is too small for the question complexity, no adaptive pricing will recover.
Done right. Prices are set dynamically per query based on budget size, agents are jointly trained to negotiate, and latency and token budgets match the typical question patterns. Runtime becomes predictable because the system always stops when the budget is consumed, rather than running until it has found all possible paths.
What a runnable demo should prove

What a runnable demo should prove

Build a three-agent reasoning loop on a small knowledge graph (10–15 entities, 30–40 facts). Feed in questions with different budgets: one easy question with a small token budget, one hard question with a large budget, one medium question with a tight latency constraint. For each, measure (1) how many edges were selected, (2) how many steps were taken, and (3) whether the answer was correct. Show that the same system adapts: easy + small budget yields a tiny subgraph; hard + large budget yields more edges; tight latency yields fewer steps but still correct answers.
