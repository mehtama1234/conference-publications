FlowBot: Inducing LLM Workflows with Bilevel Optimization and Textual Gradients

Instead of humans writing LLM workflows by hand, train an algorithm to write the workflow structure and prompts automatically from examples.

Paper explainersAll themesAgents & Tool Use

Building systems where language models call each other and tools in a planned sequence usually requires a person to hand-write the workflow and prompts. This is slow and fragile. FlowBot learns workflows automatically from data: it learns both what sequence of LLM calls to make and what prompt to use in each call, using a two-level optimization that treats the sequence structure separately from the individual prompts.

Zero assumption version

Hand-written workflows are a bottleneck

Right now, building a system where one language model (an LLM, a program that completes text by predicting the next word) calls multiple other language models or tools in sequence requires a person to sit down and write the entire pipeline and every prompt by trial and error. This is tedious and requires deep expertise.

A naive approach would be to write a single prompt that says do everything at once, then run the LLM once. This breaks because most tasks are too complicated for one forward pass—sorting emails into categories, then writing a response to each, then deciding whether to send it, are fundamentally different decisions that need different prompts and different tools called at different times.

In one sentence. Today we hand-write LLM workflows; we need to learn them automatically from data.

The algorithm as a flow

What it actually does

Outer loop: sketch the workflow structure

Choose high-level decisions: how many LLM calls, which ones, in what order, what kind of output from each.

Inner loop: optimize one prompt at a time

For each LLM call, write a trial prompt, run examples through it, measure the error, and nudge the wording toward better results, because phrases that hurt the output (high textual training nudge) get removed or reworded.

Textual training nudges: measure impact of word choices

Measure how the output changes when you tweak a word or phrase, then use that to steer which words to keep and which to drop.

Iterate inner before outer

For each workflow sketch, fully optimize all prompts in it. Then try a new sketch and repeat.

Measure on real examples

Check each learned workflow against held-out tasks to see if it generalizes better than hand-crafted pipelines, because a separate validation set prevents the inner loop from overfitting prompts to just the training examples.

What the paper changes

What the paper changes

The paper optimizes two intertwined things: the workflow structure (which LLM calls in what order) and the text inside each prompt. Instead of a human writing both, an algorithm writes both by learning from examples.

the object it moves  =  workflow structure + prompts
The hidden quantity

The hidden quantity: textual training nudge magnitude

measured quantity  =  textual training nudge signal

A textual training nudge is the direction and size of how much the output improves when you change a specific word or phrase in the prompt. It is hard to measure because text is discrete (a word either is in the prompt or it is not), not a continuous number that can slide smoothly. The paper estimates it by trying small variations (swapping synonyms, rephrasing, adding clauses) and measuring how much the loss shrinks or grows.

The paper uses this signal layer-by-layer: for each LLM call in the workflow, it measures which words or phrases in the prompt matter most (high training nudge), and nudges only the ones that matter, leaving stable wording alone.

Why it works

Why it works: two-level learning separates structure from tuning

Learning a workflow has two layers of decisions. The outer layer is architectural: which LLM calls and in what order (classifier before router, generator before validator). The inner layer is precision tuning: the exact wording of each prompt. If you tried to optimize both at once, the search space would explode and you would waste effort tuning prompts for bad structure choices.

Instead, FlowBot separates them. The outer loop picks a structure and freezes it. The inner loop fully tunes all prompts for that structure until they are as good as possible. Then the outer loop tries a different structure. This is faster because each inner loop only tunes prompts given a fixed architecture, and the inner loop can measure which words matter most (textual training nudges: which words change the output if you remove them) instead of random search. The workflow learns to specialize each prompt for its exact role—a classifier prompt different from a router prompt—rather than fighting over one generic prompt that has to work for everything.

Math after the picture

Bilevel optimization equation

First in words:

minimize over workflow choices W: minimize over prompts P for that W: loss on training data

Then the compact form:

min_W L_outer( min_P L_inner(W, P, data) )

Every symbol:

Wworkflow structure (which LLM calls and order)
Pthe text of each prompt
L_inner(W, P, data)training loss: how wrong the answers are for a given structure and prompts
L_outer(...)validation loss: how wrong a different held-out task set is after tuning
A tiny worked example
Outer loop tries Structure A: Classifier -> Router -> Generator.
Inner loop tunes Classifier prompt, then Router prompt, then Generator prompt on 100 training examples. Final loss: 15% error.
Inner loop done. Outer loop tries Structure B: Router -> Classifier -> Generator.
Inner loop tunes all three prompts again on same 100 examples. Final loss: 12% error.
Validation on held-out 20 examples: Structure A: 18% error, Structure B: 14% error.
Outer loop picks Structure B because it generalizes better, even though Structure A trained slightly lower.
This separation prevents overfitting to the training set—inner loop tunes, outer loop validates structure choice.

The outer loop makes big decisions (which LLM calls), the inner loop makes small tweaks (exact wording), and validation on a held-out set prevents the inner loop from memorizing.

What can go wrong

What can go wrong

Text changes are discrete, not smooth. Changing a prompt word by word is not the same as smoothly moving a number. The textual training nudge is an approximation (try variants and measure), so it misses some good rewrites that require multiple words to change in concert.
Outer loop can get stuck in bad structure choices. If a structure choice seems bad early (high loss) the outer loop may abandon it before the inner loop finishes tuning. The algorithm needs enough patience to let each structure be fully optimized before deciding it is bad.
Prompts may be fragile to new examples. A prompt tuned to one set of training examples may fail on slightly different new tasks. The validation set must be diverse and representative.
Done right: separate structure and prompt tuning, measure which words matter most, validate on held-out tasks. The bilevel design (outer structure, inner prompting) prevents the algorithm from memorizing prompts to a specific bad structure.
What a runnable demo should prove

What a runnable demo should prove

Build a simple multi-step task: given a customer support ticket, classify its severity, route it to the right team, generate a response, and verify the response is safe to send. Train a FlowBot on 50 examples by trying different workflow structures (classifier first or router first, one generator or two) and tuning prompts via textual training nudges. Measure accuracy on 10 held-out test tickets. Compare against a hand-written workflow (human expert designs the pipeline and prompts once) and a baseline that uses a single generic prompt for all steps.

accuracy = (correct classifications + correct routes + safe responses) / total tickets

The demo must show that learning the workflow structure automatically beats both the hand-written baseline and the single-prompt baseline.
