Gecko: Simulation-Based Tool Call Refinement for LLM Agents

Before an LLM agent tells a real tool what to do, a simulation checks if the request is valid and gives the agent a chance to fix it.

Paper explainersAll themesAgents & Tool Use

Large language models can use tools (send an email, query a database, call an API) to complete tasks. But they often ask tools to do impossible things—misnamed functions, wrong argument types, contradictory requests. This paper introduces Gecko, a simulation layer that catches these errors before real execution, letting the LLM fix its own mistakes in a low-cost sandbox.

Zero assumption version

LLMs fail at tool use because they guess

When an LLM needs to complete a task, it writes a request telling a tool what to do: call a calendar function, query a database, run code. The model generates these requests by pattern-matching—it has seen examples in training data but has no real understanding of whether a function actually exists or what types of data it accepts.

A naive approach: let the LLM try, see what breaks, and iterate. But real tools have side effects. Sending the wrong email, deleting the wrong file, charging the wrong account—these mistakes cannot be undone with practice. Also, each iteration costs time and money (every LLM call adds up), making refinement with real tools slow and risky.

The core problem. LLMs generate invalid tool requests (wrong function names, malformed arguments, impossible states), and refining these mistakes with real tools is expensive and unsafe.

The algorithm as a flow

What it actually does

LLM generates a tool request

Model proposes: function name, arguments, expected result.

Gecko validates the schema

Does the function exist? Are argument types correct? Combination of rules and LLM judgment.

Gecko simulates state consistency

Do the arguments make sense together? Is the requested outcome logically possible?

Gecko judges task completion

Does this request move toward the original goal, or is it a dead end?

LLM refines and retries

Model reads Gecko's feedback and rewrites, because concrete errors help more than just failure.

What the paper changes

The one thing that changes

The paper changes the tool-call sequence itself. Instead of the LLM sending its first guess directly to a real tool, the sequence is now routed through Gecko first, where each request is checked and refined before real execution. The requests that come out are the same data type, but they have been vetted by a simulation layer.

the object it moves  =  tool-call sequence
The hidden quantity

The hidden quantity: Validity score

measured quantity  =  Validity score

Gecko estimates a validity score: the likelihood that a given tool request (function name + arguments + expected state) will succeed without error and move the task forward. This breaks into four checks because each can independently block success: the function name must be real (schema), argument types must match what the function accepts (conformance), the combination of arguments must make logical sense (state), and the request must advance the original task (alignment).

The paper combines rules (does the function name exist in the API definition?) and LLM judgment (does this state transition make sense?) to compute this score, because rules catch syntax errors quickly but cannot reason about what is logically possible, while LLMs see the big picture but miss typos. Requests scoring low are sent back to the LLM for refinement, because seeing the specific error helps the model learn; high-scoring ones proceed to the real tool.

Why it works

Why the simulation prevents errors

LLMs fail at tool use because they have no ground truth—they generate requests based on pattern-matching without seeing whether they work. Real-world feedback is delayed and expensive. Gecko inserts a cheap feedback loop: a simulation layer that checks three things before real execution.

First, schema validation: Gecko has the API definition (which functions exist, what arguments they take). A rule-based check catches obvious mistakes like wrong function names or argument types.

Second, state consistency: even if the schema is valid, the combination of arguments might be impossible. An LLM might ask to delete a file that does not exist, or send an email to an address it just marked invalid. Gecko uses LLM judgment to spot these contradictions and synthesize what the correct state should be.

Third, task alignment: does this request move toward the user's goal? Gecko re-reads the original task and judges whether this tool call is a step forward or a distraction.

When Gecko finds errors, it does not throw them away—it sends them back to the LLM with concrete feedback. The LLM reads the errors and rewrites the request. This forms a simple test-time scaling loop: more retries lead to better tool calls because each retry incorporates the lesson from the previous failure, and the cost is just a few more LLM calls rather than expensive real-world side effects, which makes the refinement practical.

Math after the picture

The validity score formula

First in words:

Validity equals the product of schema correctness, argument conformance, and state consistency, multiplied by task alignment.

Then the compact form:

V = C_schema × C_args × C_state × A_task

Every symbol:

VValidity score, ranges from 0 to 1; higher means more likely to succeed
C_schemaSchema check: 1 if function name exists and return type matches, 0 otherwise
C_argsArgument conformance: 1 if all argument types match, 0 if any mismatch
C_stateState consistency: 1 if arguments are logically consistent, 0 if contradictory
A_taskTask alignment: LLM judgment of whether this request advances the goal; 0 to 1
A tiny worked example
Scenario: LLM tries to send an email. Function SendEmail exists (C_schema=1). Arguments are email address and subject (correct types, C_args=1). But the email is to an address we just verified as invalid (C_state=0.2, state consistency is weak). Request does advance task (A_task=0.8).
Validity = 1 × 1 × 0.2 × 0.8 = 0.16 (low). Gecko rejects it and asks the LLM: why email an invalid address? LLM rewrites with the correct address.
Second attempt: SendEmail(recipient=alice@company.com, subject=hello). All components now pass: V = 1 × 1 × 1 × 0.9 = 0.9 (high). Gecko approves; real email sent.

A request must pass all checks. If any component is weak, Gecko flags it and the LLM gets a second chance.

What can go wrong

What can go wrong

Gecko itself misses a bad request. If Gecko's schema or state rules are incomplete, a request that looks valid in simulation might still fail in the real tool. This happens if the tool's API is documented incompletely or has unstated preconditions.
The LLM learns to game Gecko instead of the real task. If Gecko's feedback is generic or repeatedly points to the same error, the LLM might learn to avoid that error without understanding the underlying issue, leading to correct-looking but semantically meaningless tool calls.
State synthesis is too optimistic. When Gecko simulates state, it might assume things will work out that actually will not. For example, assuming a database transaction will not conflict, or that a value will be in range when it is not.
Done right: detailed API specs + state-aware feedback. Gecko works best when tool APIs are fully documented, state preconditions are explicit, and feedback messages explain not just that a request is wrong but why it is wrong and what to try instead.
What a runnable demo should prove

What a runnable demo should prove

Build a small example: define three tool functions (e.g., SendEmail, QueryDatabase, UpdateRecord). Write down the full API spec for each (function names, argument types, preconditions). Then have an LLM agent complete a two-step task that requires using these tools (e.g., look up a customer record, then send them an email). Track how many invalid requests the raw LLM generates, how many Gecko catches and the LLM fixes, and how many reach the real tools. Measure: success rate (task completion), invalid-request rate (without Gecko vs. with Gecko), and iteration count (how many retries before success).

Success rate = (tasks completed / total tasks) × 100; Invalid request rate = (rejected by Gecko / total attempted) × 100

The demo must show that Gecko catches real mistakes early and gives the LLM a second chance to fix them before side effects occur.
