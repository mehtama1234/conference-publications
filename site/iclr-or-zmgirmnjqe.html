Search Self-Play: Pushing the Frontier of Agent Capability without Supervision

Train a search agent without hand-written tasks by making one copy invent answerable search questions and another copy solve them.

Paper explainersAll themesAgents & Tool Use

Agents that search the web usually learn from human-made tasks with known answers. That setup does not scale well because people must keep writing new tasks and checking the answers. This paper replaces that manual pipeline with a two-player training game. One agent proposes a hard search question and gathers the documents needed to answer it. A second agent must answer the question correctly. The question only counts if the collected documents are enough to support one clear answer, because the system checks answerability before using the task for training. This lets training continue without outside labels while still keeping the reward trustworthy.

Zero assumption version

Why agent training stalls when people must author every task

Training with verifiable rewards works well when every task has a clear right answer. For search agents, that usually means a person writes a question, looks up the supporting pages, and records the answer. The agent then tries the task and gets credit only when the answer matches. This is expensive because task writing and answer checking stay manual.

There is a second problem beyond cost. Hand-written tasks often cluster around one difficulty level. If tasks are too easy, the agent stops learning because it already passes them. If tasks are too hard, the agent gets zero reward too often and cannot tell which actions were useful. A training loop needs fresh tasks whose difficulty can rise with the agent's current skill.

The paper's move in one sentence. Make the agent create its own search tasks, but keep only the tasks whose answer can be proved from the pages the proposer collected.

The algorithm as a flow

What it actually does

Run a proposer agent.

The proposer searches the web and drafts a question whose answer should be found in the pages it visited.

Save the supporting pages.

The system stores the proposer's search results so the training loop knows what evidence was available.

Test answerability.

A checking stage asks whether the stored pages are enough to answer the drafted question clearly.

Run a solver agent.

If the task passes the check, the solver uses its own search-and-read process to answer it.

Update both policies.

Reward flows back to the proposer for making good tasks and to the solver for answering them, so both improve through repeated self-play because accepted tasks reveal which search behavior creates useful questions and which solving behavior reaches correct answers.

What the paper changes

What changes

The paper changes where training tasks come from. Instead of using a fixed human-written set, it creates tasks on the fly from the agent's own search traces and then filters those tasks through an answerability check.

the object it moves  =  task source and task verification
The hidden quantity

The hidden quantity: answerable difficulty

measured quantity  =  Questions that are both hard and checkable

The training loop needs tasks that do two things at once. They must be hard enough to teach the solver something new, and they must still have a reliable right answer. The paper treats this combination as the key hidden quantity, because raw difficulty alone is not useful if the system cannot verify whether the solver was right.

The paper estimates this by keeping the proposer’s search trail, then checking whether the gathered pages support one answer strongly enough for a reader system to recover it. Questions that fail this check are thrown away, because they would inject noisy rewards into training. Questions that pass can be ranked by how often the solver still misses them, which gives a moving picture of useful difficulty.

Why it works

Why the self-play loop keeps reward useful

The method works because it separates task creation from task acceptance. A proposer is free to explore and draft ambitious questions, but those drafts do not become training data automatically. They enter training only if the stored documents are enough to justify a clean answer. That filter matters because reward quality is the main failure point in self-generated training data.

Once that filter is in place, the proposer and solver can co-evolve. The proposer is pushed toward questions the solver does not already pass, because those questions create stronger learning signal. The solver is pushed toward deeper search behavior because the questions come from a proposer that is also improving. Difficulty rises with capability by repeated interaction, so the curriculum updates itself instead of being fixed by hand at the start.

Math after the picture

The game objective

First in words:

Score a task by whether the evidence set supports one answer and whether the solver gets that answer right. Use that score to update both the proposer and the solver.

Then the compact form:

task_score = answerable(task, docs) * correct(solver_answer, gold_answer)

Every symbol:

answerable(task, docs)1 when the collected documents are enough to support a clear answer, else 0
correct(solver_answer, gold_answer)1 when the solver gives the checked answer, else 0
task_scorethe reward used to train the self-play game
A tiny worked example
The proposer asks: which city hosted the 2018 edition of a certain event?
It gathers three pages, and the checking stage confirms those pages name one city clearly.
So answerable(task, docs) = 1.
The solver answers the question and says the correct city.
So correct(solver_answer, gold_answer) = 1.
The task score becomes 1 * 1 = 1, so both sides receive positive learning signal.
If the pages had been conflicting, answerable(task, docs) would be 0, and the task would be discarded before training.

The answerability term blocks noisy tasks, because a correct-looking answer should not earn reward unless the evidence set can support that answer cleanly.

What can go wrong

What can go wrong

The proposer writes vague questions. If a drafted question can be read in more than one way, the answerability check may reject it or, worse, pass a weak task. The system needs strict acceptance rules because vague tasks create noisy rewards.
The proposer learns to exploit the checker. A self-play loop can drift toward tasks that are easy for the checker instead of useful for the solver. This matters because reward shaping can bias behavior. The check must track true answer support rather than surface patterns.
Difficulty rises too fast. If the proposer outruns the solver, accepted tasks may still be too hard to teach much. Training works better when the task pool includes a spread of near-frontier questions because those are the ones the solver can almost solve and improve from.
Done right. When task acceptance stays strict and difficulty stays near the solver's frontier, the game keeps producing useful questions because the proposer searches for gaps the solver still has and the solver gets clean reward on those gaps.
What a runnable demo should prove

What a runnable demo should prove

Build two web-search agents on a small domain, such as a collection of event pages and biographies. Let the proposer generate questions and keep its visited pages. Run the answerability filter on each draft. Then train the solver only on accepted tasks. Compare this loop against a baseline that uses a fixed set of human-written questions. The demo should show that the self-play loop keeps producing fresh tasks and that solver accuracy rises because the accepted tasks stay both checkable and near the current skill boundary.

useful_task_rate = accepted_tasks / proposed_tasks; solver_accuracy = correct_solver_answers / accepted_tasks

The key result is not just more tasks. It is a steady stream of tasks the system can trust and still learn from.
