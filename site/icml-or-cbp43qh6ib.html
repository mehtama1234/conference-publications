VeriSimpl: Robust Optimization Modeling from Natural Language using Simplification-based Verification

Turn a word problem into an optimization model and then verify it by asking the model to reason about simpler derived cases generated by the solver.

Paper explainersAll themesOther

A language model can often write a solver program that runs without syntax errors. That does not mean the program matches the intended optimization problem. A missed constraint, a reversed inequality, or an unnecessary decision variable can produce a cleanly executing but wrong model. VeriSimpl addresses that gap by making verification easier than full direct checking. It asks the solver to simplify the candidate formulation into smaller diagnostic cases, then asks the language model whether those simpler cases still agree with the original task description. The simplification matters because local reasoning about a reduced subproblem is easier than reasoning about the full model all at once.

Why natural-language-to-optimization systems make subtle mistakes

An optimization model has to translate plain-language requirements into exact variables, objective terms, and constraints. A solver will happily optimize the wrong thing if the model is internally consistent. So execution success is a weak test: it only shows the syntax is valid and the solver found a feasible or optimal solution under the written rules.

Directly asking a language model whether the entire formulation is correct is also unreliable. The full model may contain many interacting constraints, and the language description may combine several conditions in one paragraph. Global checking overloads the reasoning step, so the model can miss a local mismatch even when that mismatch is easy to see once isolated because several interacting rules compete for one limited reasoning pass.

The paper's move in one sentence. Use the solver to generate simpler diagnostic versions of the candidate formulation, then verify those cases against the natural-language description so errors become locally visible.

The algorithm as a flow

What it actually does

Generate an initial optimization model

The language model maps the text description into variables, constraints, and an objective for a solver.

Simplify along selected dimensions

The solver fixes some variables, drops or isolates some constraints, or narrows the feasible set so the resulting subproblem tests one local aspect of the formulation.

Pose diagnostic questions

Each simplified subproblem is converted into a targeted verification prompt that asks whether the reduced case still matches the user's intent.

Collect verification signals

Agreement between the simplified model and the task description raises confidence; disagreement points to a concrete place where the formulation is wrong.

Revise the candidate formulation

Use the diagnostic findings to edit the full model and rerun the cycle until the verification checks stop failing.

What the paper changes

What the paper changes

The paper changes verification from a single global judgment into a sequence of local checks. The main idea is that the solver is not only an execution engine. It is also a tool for constructing simpler counterfactual cases that make semantic errors easier to detect.

the object it moves  =  verification of language-generated optimization formulations
The hidden quantity

The hidden quantity

measured quantity  =  whether each local part of the formulation matches the intended rule

The important quantity is semantic alignment at the level of individual modeling choices. A full formulation may fail because one capacity constraint is reversed, one index range is wrong, or one variable should have been binary rather than continuous. Those are local faults, but their effect can be hidden inside a large valid program.

VeriSimpl exposes those local faults by simplifying the formulation until a diagnostic case depends mainly on one suspect choice. If the simplified case no longer matches the natural-language description, the system learns not just that the model is wrong but why it is wrong.

Why it works

Why simplification-based verification works

The solver already understands the formal structure of the candidate model. It can therefore create reduced instances that preserve some constraints while freezing others. That turns a dense formulation into a smaller case whose intended answer is easier to reason about from the text description.

The language model is stronger at this smaller task because fewer interacting parts compete for focus during one reasoning pass. If a reduced case asks only whether one capacity rule is enforced or whether one decision variable should be active, the reasoning burden drops. A wrong answer in that case points directly to the offending rule block.

The verification signal is high precision because a failed local check usually maps to a specific repair. The full loop improves modeling accuracy by alternating between solver-based simplification and language-based semantic judgment, so each component contributes what it is good at.

A simplified verification query

First in words:

One diagnostic step fixes part of the decision vector and checks whether the reduced feasible set still agrees with the text description.

Then the compact form:

F_simplified = { x : x in F, x_J = c }

Every symbol:

Fthe feasible set of the full candidate formulation
Ja selected subset of decision coordinates to fix
cthe fixed values assigned to those coordinates
F_simplifiedthe reduced feasible set used for a diagnostic query
A tiny worked example
Suppose the original task includes shipping goods from warehouses to stores under capacity limits.
Fix the shipping decisions for all but one warehouse and ask whether the remaining reduced problem still reflects the stated capacity rule for that warehouse.
If the simplified case permits more shipments than the text allows, the error is local and visible.
That local contradiction tells the system which constraint block needs repair.

The paper uses several simplification dimensions, but they all serve the same purpose: isolate one semantic question while keeping the rest of the model fixed.

What can go wrong

What can go wrong

The simplification may hide the original error. If the reduced case removes the interaction that causes the bug, the diagnostic query may approve a formulation that still fails in the full problem.
Verification prompts can still be misread. A language model may misunderstand a diagnostic question, especially when the natural-language task description is itself ambiguous.
Too many diagnostic queries can raise cost. If every candidate formulation triggers many solver calls and many language-model checks, the approach may become expensive for large modeling tasks.
Done right. Choose simplifications that isolate likely error sources, keep the diagnostic prompts tightly tied to the original wording, and stop once the remaining checks no longer reveal distinct local faults.
What a runnable demo should prove

What a runnable demo should prove

Take a small benchmark of transportation, scheduling, and knapsack-style word problems. For each problem, generate a solver formulation with a language model and compare two workflows: direct generation alone and VeriSimpl with simplification-based verification.

Track not only whether the solver runs, but whether the final formulation matches a reference model and how often the verification stage points to the correct faulty rule. The demo should show that local diagnostic cases improve final correctness because they turn vague failure into a concrete repair target.

formulation_accuracy = correct_models / total_models ; diagnostic_precision = correct_fault_flags / total_fault_flags

The main evidence is a higher rate of semantically correct formulations, supported by diagnostic signals that identify which part of the model needed revision.
