SWE-Perf: Can Language Models Optimize Code Performance on Real-World Repositories?

Measure whether code agents can make real repositories faster by giving them full repository context, runnable performance tests, and expert reference patches from actual speed-improving pull requests.

Paper explainersAll themesAgents & Tool Use

Language models have shown they can write code and fix bugs, but speed optimization is a different job. A code change that preserves behavior can still make the program slower or faster, because runtime depends on repository-wide context, tests, and environment details rather than on one edited line alone. This paper introduces a benchmark built from real speed-improving pull requests so the field can measure whether current agents can handle that harder setting.

Zero assumption version

Why code speed work is not the same as code generation or bug fixing

A performance fix must preserve correctness while changing time or memory behavior in a real repository. That usually depends on several files, workload assumptions, and tests that expose the slowdown. A model that edits one file well may still miss the real bottleneck because the cause may sit elsewhere in the codebase.

Before this paper, the field lacked a focused benchmark for this exact task. Without shared instances, it was hard to tell whether a repository-level agent truly optimized performance or merely passed a small correctness check. The paper asks for a benchmark that captures the real structure of speed-focused engineering work.

The paper's move in one sentence. Collect real repository performance patches, package each instance with code, target functions, tests, and execution environments, and use the resulting benchmark to measure how far current code agents are from expert optimization work.

What the paper changes

What the paper changes

The paper changes the evaluation target. Instead of asking whether a model can write code in isolation, it asks whether a model can make an existing repository faster under executable checks that come from real optimization pull requests, because real speed work must preserve behavior while improving measured runtime.

The hidden quantity

The hidden quantity

measured quantity  =  the real bottleneck inside a repository-level task

The key hidden quantity is the bottleneck cause. A slow test only tells you that something is taking too long. It does not tell you which file, which function, or which interaction across modules is responsible.

SWE-Perf makes that hidden quantity measurable by giving the agent full repository context, target functions, and runnable tests. That matters because performance work usually fails when the agent edits a visible symptom instead of the code path that actually dominates runtime.

Why it works

Why this works: benchmark the full engineering task, not a stripped version

A narrow coding benchmark can hide the hardest part of speed work because it may tell the model exactly where to edit or may omit the environment that reproduces the slowdown. SWE-Perf keeps the repository context and the runnable checks, so the agent must do the real diagnosis and the real fix.

That matters because performance optimization is often repository-level reasoning. The bottleneck may emerge from interactions across files, from data flow through helper functions, or from work repeated inside a hot loop. The paper finds a large capability gap because current systems still struggle when they must combine diagnosis, patching, and execution-based validation in one loop.

Math after the picture

A valid patch must preserve correctness and improve speed

First in words:

A simple summary is that a candidate patch is counted as successful only if it passes required correctness tests and yields a positive improvement on the performance test.

Then the compact form:

success = 1 if correctness_pass = 1 and speed_gain > 0 else 0

Every symbol:

successwhether one benchmark instance is solved
correctness_passindicator that required functional tests still pass
speed_gainmeasured reduction in runtime or resource use on the performance test
A tiny worked example
Suppose an agent edits a repository function and all correctness tests still pass, so correctness_pass = 1.
The original performance test takes 10 seconds and the patched version takes 7 seconds, so speed_gain is 3 seconds.
Because correctness_pass = 1 and speed_gain is positive, the instance counts as solved.
If the patch had reduced runtime to 7 seconds but broken one correctness test, it would not count as solved because performance alone is not enough.
If the patch passed correctness but did not improve the speed test, it would also fail because the benchmark is about optimization, not only preservation.

This success rule is the heart of the benchmark because speed work matters only when the program still behaves correctly.

What can go wrong

What can go wrong

A benchmark case can overfit to one environment. If the performance test is too tied to one machine setup, the measured speed gain may not transfer well because some optimizations depend heavily on the local runtime environment.
Target-function hints can still narrow the search too much. If the benchmark tells the agent too much, the task may understate the real diagnosis burden because a human engineer often starts with weaker location clues.
Agents may optimize for the test rather than the true workload. A patch can pass the benchmark but remain narrow if the performance test does not fully represent production use, because the measured win may not cover all important traffic patterns.
Done right. The benchmark is valuable when it keeps real repository structure, executable environments, and clear success rules, because that combination turns speed optimization into a measurable engineering task.
What a runnable demo should prove

What a runnable demo should prove

Build a small benchmark from a handful of real repository pull requests that improved runtime. For each case, keep the repository snapshot, a speed-focused test, correctness tests, and the expert patch. Then run one file-level agent and one repository-level agent on the same cases.

Track solve rate, median speed gain on solved cases, and diagnosis time before the first promising patch. The repository-level agent should do more of the useful work because full-context optimization depends on locating the real bottleneck, not just editing the visible function.

solve_rate = solved_cases / total_cases ; median_speed_gain = median(original_time - patched_time)

The result should show whether a code agent can handle the full diagnosis-plus-patching loop that real performance work requires.
