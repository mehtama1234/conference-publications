Benchmarking Agent Memory in Interdependent Multi-Session Agentic Tasks

Measure whether an agent can carry lessons from one session into later sessions where success depends on what it learned earlier.

Paper explainersAll themesAgents & Tool Use

Many memory tests ask whether an agent can repeat a fact from earlier text. Real work is harder. An agent may need to learn a preference in one session, notice a mistake in a second session, and use both facts days later to finish a larger task. MemoryArena targets that long chain. It builds multi-session tasks where earlier actions create information that later actions depend on, so the evaluation measures useful memory rather than short-term recall alone.

Zero assumption version

Why recall-only memory tests miss the hard part

A recall test asks whether the agent can retrieve an earlier fact. A single-session action test asks whether the agent can finish a task now. Neither one captures the setting where an agent must learn while acting and then use that learned material in later sessions. In practice, those pieces are coupled because many future choices only make sense if the agent remembers what happened before.

That gap creates misleading optimism. A system can do well on long-context recall and still fail a real multi-session job because it does not store the right experiences, does not compress them into a useful memory, or does not consult that memory when later choices depend on it.

The paper's move in one sentence. Build multi-session tasks with explicit dependence between subtasks so that an agent must learn from earlier interactions and use that memory later to finish the full job.

The algorithm as a flow

What it actually does

Design interdependent subtasks

Create tasks where one session reveals information that another session must use so that memory is necessary, not optional.

Run agent-environment loops over time

Let the agent act, observe outcomes, and receive feedback across multiple sessions instead of one uninterrupted prompt.

Allow explicit memory storage

Agents can record summaries or notes so that the benchmark tests how well they build useful long-term records.

Score later decisions

Check whether downstream actions use earlier experience correctly because memory quality only matters if it changes future behavior.

Compare domains

Evaluate on web tasks, planning, search, and formal reasoning so that the benchmark reveals whether memory strategies transfer across settings.

What the paper changes

What the paper changes

The paper changes memory evaluation from static recall into action-guiding memory across time. It asks whether past experience becomes useful state for future decisions.

the object it moves  =  What counts as good memory for an agent
The hidden quantity

Task-relevant remembered state

measured quantity  =  How much decision-useful information from earlier sessions survives into later ones

The key hidden quantity is not how many words from the past the agent can repeat. It is how much task-relevant state survives into the next session in a form the agent can actually use. A weak memory system may store too much, too little, or the wrong detail, so later actions drift even when the earlier experience contained the answer.

MemoryArena surfaces this quantity by creating explicit causal links between sessions. Because later subtasks depend on earlier discoveries, the benchmark can identify whether failure came from poor observation, poor storage, poor retrieval, or poor later use.

Why it works

Why this works

The benchmark works because it ties memory to future consequences. If later subtasks are independent, then an agent can ignore history and still score well. By making earlier sessions informative for later ones, MemoryArena ensures that memory quality directly affects task completion.

The domain diversity also matters because a memory method that helps on one setting may fail on another. A note-taking strategy that works for web navigation may be poor for sequential reasoning if it stores surface details instead of decision rules.

A simple memory-use score

First in words:

Score an agent by how well it stores useful information from earlier sessions and how well it uses that information when later subtasks depend on it.

Then the compact form:

score = w_store * store_quality + w_use * use_quality ; final_success <= use_quality

Every symbol:

scoreoverall score for one multi-session task
store_qualityhow well the saved memory captures the facts that later subtasks need
use_qualityhow well the later action applies the saved memory when choosing what to do
w_storeweight on building a useful memory record
w_useweight on applying that record later
final_success1 if the whole interdependent task is completed correctly, else 0
A tiny worked example
In session one, a user says they dislike red-eye flights and prefer aisle seats.
A good memory record keeps both facts because both can affect a later booking choice.
Suppose store_quality = 0.9 because both preferences were saved clearly.
In session two, the agent books a daytime aisle flight, so use_quality = 1.0.
With w_store = 0.3 and w_use = 0.7, score = 0.3 * 0.9 + 0.7 * 1.0 = 0.97.
If the agent had saved only the aisle-seat fact and ignored the time preference, use_quality would fall because the final booking could violate the earlier lesson.
The benchmark rewards the second step most heavily because memory matters only when it guides later action.

The paper measures full benchmark performance across task families, but this simplified equation captures its core principle: good memory must be both stored and used.

What can go wrong

What can go wrong

Stored notes may become cluttered. If the memory record grows without selection, later retrieval can become noisy because important facts are buried among irrelevant ones.
A task may reward recall more than action. If a later subtask depends only weakly on earlier sessions, the benchmark may understate the real memory challenge because the connection is too loose.
Later failures can have many causes. A bad downstream action may come from weak planning rather than weak memory, so diagnostic analysis matters because not every miss is a storage problem.
Done right. Use subtasks with explicit dependence and inspect both stored notes and later choices so that memory failures can be localized cleanly.
What a runnable demo should prove

What a runnable demo should prove

Build a three-session travel assistant task. In session one, the user states preferences. In session two, the agent learns from a failed booking attempt. In session three, the agent must complete a new booking that depends on both the old preferences and the lesson from the failure. Compare an agent with no explicit memory, one with naive note storage, and one with curated memory summaries.

The demo should show that later task success rises only when the agent stores the right lessons and retrieves them at decision time, because memory that never affects action is not useful memory.

carryover_gain = later_task_success_with_memory - later_task_success_without_memory

The benchmark is asking a practical question: can the agent turn past experience into better future choices by storing the parts that later decisions depend on?
