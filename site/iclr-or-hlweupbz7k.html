EHR-ChatQA: Agent Consistency Through Interactive Query Refinement

To help healthcare database agents handle vague questions and terminology mismatches, this paper introduces a benchmark that reveals agents succeed sometimes but fail to repeat the same correct answer reliably.

Paper explainersAll themesAgents & Tool Use

Hospital databases are strict: every field has exact names and meanings. When a doctor asks a vague question or uses informal terminology, a language model agent must clarify what is wanted, search the database structure, and write correct SQL (the database instruction language). This paper's key discovery is that agents do well one out of five tries but rarely succeed all five times, exposing a deep reliability problem in safety-critical healthcare.

Zero assumption version

Vague questions and misnamed fields break database agents

A healthcare worker asks an agent, 'Show me patients on expensive heart medication over the past month.' The database has a table called medicationorders with a field event_type set to codes like '2' instead of the word 'medication.' The question is vague: 'expensive' is not a database field, and 'heart medication' might refer to six different drug classes.

A naive agent might write SQL that looks for a nonexistent 'expensive' column or guess the wrong drug code. The real problem: the agent must recognize that the database and the user speak different languages, ask clarifying questions, and navigate multiple missteps to land on the right query.

In one sentence. An agent receives a vague or mismatched question, uses tools to search the database schema and values, and iteratively refines the question through conversation until SQL is correct.

The algorithm as a flow

What it actually does

Benchmark design

Two interaction flows (IncreQA: add constraints; AdaptQA: shift goals mid-conversation) with 366 tasks over real healthcare databases.

Tool kit

Four tools: schema search (find table and column names), value search (find matching data values), web search (fetch external clinical knowledge), and query execute (run SQL and report results).

Simulated user

An LLM plays the doctor asking questions, sometimes vague or using informal names; the agent converses, queries, and refines.

Evaluation

Each task runs five independent trials. Any-trial: did at least one trial succeed? All-five: did all five trials succeed identically?

Diagnosis

Results show high any-trial success but low all-five success, revealing failure modes: timing errors, clinical knowledge gaps, constraint misinterpretations.

What the paper changes

What the paper changes

The paper benchmarks the entire agent-to-SQL workflow—not just a single query but a full multi-turn conversation where the agent asks clarifying questions, tries different queries, and learns from feedback. This end-to-end view exposes the reliability gap that single-run testing would miss.

the object it moves  =  agent consistency across repeated attempts
The hidden quantity

The hidden quantity: Consistency

measured quantity  =  Consistency across five independent runs

Consistency is a single number: can the agent solve the same task in the same way every time? It is measured by running each query task five times independently and checking whether all five produce the correct SQL and answer. Unlike the any-trial metric (did at least one trial work?), consistency requires the agent to behave identically and reliably across runs.

The paper reports consistency separately from single-run accuracy because in healthcare, a diagnostic query that works 90% of the time is worse than useless—it is dangerous.

Plain reading. Consistency is reliability. An agent that solves a task four out of five times is unreliable. In healthcare, unreliable is unsafe.
Paper reading. Consistency is the fraction of tasks where all five independent trials of the agent-LLM interaction produce identical correct SQL and answers. Agents achieve 90-95% on simple incremental refinement (any-trial) but only 35-60% on all five trials being identical, revealing random failure modes.
Why it works

Why the consistency gap exists

Each time an LLM agent answers a question, it makes small random choices in word selection and reasoning order. When the database query is unambiguous, randomness does not matter—all paths lead to the same SQL. But when the question is ambiguous (Is 'expensive' the drug cost or the patient's co-pay? Does 'last month' mean 30 days or calendar month?), the agent's random choices lead to different clarifying questions, different tool-call sequences, and sometimes different final queries.

The paper identifies three concrete failure modes: timing errors (the agent picks the wrong date boundary), value mismatches (the agent fails to map informal terms to database codes), and clinical knowledge gaps (the agent does not know that a medication class has cardiovascular effects). Each mode triggers inconsistently—sometimes the agent recovers with web search, sometimes it does not. The benchmark forces all five runs to use the same tools and answer the same question, so random variation exposes which agents' reasoning is fragile.

Math after the picture

Measuring consistency

First in words:

Pass^5 equals the count of tasks where all five trials produce the correct answer divided by the total count of tasks

Then the compact form:

Pass^5 = count(all_five_trials_correct) / total_tasks

Every symbol:

Pass^5fraction of tasks solved consistently across all five runs
all_five_trials_correcttasks where runs 1 through 5 all produced identical correct SQL
total_tasksnumber of query tasks in the benchmark (366 total)
A tiny worked example
Suppose a benchmark has 100 tasks. An agent solves 95 tasks perfectly all five times (95 tasks with all_five_trials_correct = true). Another five tasks are solved in four out of five runs. Pass^5 = 95 / 100 = 0.95 (95%). Pass@5 for these five messy tasks is 5 / 5 = 1.0 (100%), but Pass^5 = 0 (0%), because no single task succeeded all five runs. The paper reports similar gaps: IncreQA achieves 92% Pass@5 but 55% Pass^5.

Consistency (all-five success) is the safety metric: if healthcare agents achieve 55% all-five success, then roughly half of real-world queries are unreliable, making deployment unsafe without human review.

What can go wrong

What can go wrong

Timing confusion. An agent asked for 'recent admissions' may query the patient's first-ever admission instead of the most recent one. The error is silent: it returns a valid SQL result, just the wrong dates.
Value mismatch persistence. The database stores drug names as codes (2891, 2892) instead of brand names. An agent that fails to map 'Aspirin' to code 2891 on the first try may try the same broken query again without using value_search to recover.
Clinical knowledge gaps. The agent does not know that certain medications are associated with specific conditions (a cardiac side effect of an antibiotic). Web search can help recover this knowledge by finding that information online, but only if the agent recognizes the need to search—if the agent does not think to search or calls web search with vague keywords, the online source will not provide the right answer, and the agent produces an incomplete query result.
Random variability in phrasing. The same clarifying question asked across five trials may be phrased slightly differently each time, leading the simulated user to respond differently and the agent to take a different tool-call path.
Done right. An agent that consistently uses all four tools (schema, value, web, execute) in a planned order, even when early attempts fail, tends to achieve higher consistency. Reliable agents treat the tools as a backtracking strategy—if schema search fails, call value search; if value search finds nothing, call web search—not a one-shot lookup.
What a runnable demo should prove

What a runnable demo should prove

Build a small EHR-like table with two columns: patient_id (1 to 10) and medication_code (integers like 101, 102, 103 for aspirin, ibuprofen, warfarin). Write a vague question: Show me patients on blood thinners. Write an agent that calls three tools: schema_search (prints column names), value_search (tries to find thinners or warfarin), and sql_execute (runs the final query). Run the agent five times (in five independent Python processes or with five random seeds). Do all five trials return the same correct list of patients, or do some return different results?

Consistency equals number of trials with identical correct answers divided by 5

If even this tiny demo shows inconsistency, the scaling problem is clear: larger domains with richer ambiguity will have far lower all-five success than any-trial success, making real-world healthcare deployment dangerous without human approval loops.
