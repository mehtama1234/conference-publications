Learning to Share: Selective Memory for Efficient Parallel Agentic Systems

A learned controller decides which intermediate steps from parallel agent teams should go into a shared memory bank to save computation without losing quality.

Paper explainersAll themesAgents & Tool Use

When you run multiple teams of AI agents in parallel to solve a hard problem, each team independently works through similar reasoning steps and tool calls. This wastes computation because the same sub-problems get solved over and over. This paper introduces a shared memory bank that all teams can access, plus a lightweight learned controller that picks which steps are worth remembering — selecting information once and reusing it across teams to cut total runtime while keeping quality high.

Zero assumption version

Parallel teams solve the same sub-problems twice

Agentic systems (AI systems that reason step-by-step and call tools) can work better by running many teams in parallel, each exploring a different reasoning path to the same problem. A medical diagnosis system might run ten teams in parallel: team A asks the lab, team B interviews the patient, team C reviews imaging. If they later realize the lab result answers both team A and team B's questions, team B wasted work.

A naive approach: just run all teams independently. Each team reasons about similar sub-problems (e.g., reading a test result) without sharing — so the same computation (asking, processing, reasoning about the lab result) happens multiple times. When you multiply this waste across all teams and all steps, the total runtime balloons even though one team alone would be fast.

The problem in one sentence. Parallel agent teams independently re-solve overlapping sub-problems, burning compute on redundant reasoning and tool calls.

The algorithm as a flow

What it actually does

All teams run in parallel

Each team reasons independently, taking steps (tool calls, reasoning loops) as it works.

Controller sees each step

After each step, the controller gets a signal: will other teams encounter the same sub-problem? (The controller learns this pattern from past runs where multiple teams solved the same step.)

Yes-or-no decision

Controller decides: add this to shared memory, or discard it (to avoid context explosion).

Teams check memory first

Before taking the next step, teams query the shared bank: Is this already solved?

Credit flows backward

At the end, the controller looks back: did this team finish on time? If yes, the controller increases its preference for the memory decisions that led to this outcome — in particular, remembering steps that other teams later fetched (because skipping redundant work is why the team was fast). If the team saved a step that no other team queried, that save gets penalized (wasted memory). This teaches the controller to save only steps that multiple teams will actually use.

What the paper changes

The single thing that changes

The paper introduces a global memory bank and a learned gate controller. The memory bank is a simple list (or retrieval index) holding intermediate steps. The controller is a small model trained to output yes-or-no decisions: should this step be added to memory?

the object it moves  =  memory admission controller
The hidden quantity

Usage-aware credit: which steps paid off?

measured quantity  =  step reuse count and downstream benefit

The paper's key insight is that not all steps are equally valuable for reuse. A step that five teams independently re-solved is more valuable to remember than a step only one team will ever need. The hidden quantity is the true benefit of remembering a step — measured by how many teams later queried and used that step, and whether using it shortened their runtime.

The paper measures this by assigning credit during reinforcement learning. At the end of each run, the team either solved the problem on time (reward: +1) or wasted time (reward: 0). The algorithm then works backward: if this team used a saved step and the team finished on time, that memory decision gets positive credit (because it contributed to the speed). If a team added a step to memory but no other team queried it, the save decision gets penalized (because it consumed memory without being used). This teaches the controller which steps are genuinely reusable across teams and which are single-team dead weight.

Why it works

Why learning to share actually saves time

The mechanism hinges on three coupled loops. First, parallel teams work independently but each step is visible to a learned gatekeeper (the controller). Second, the controller has learned a pattern: certain steps (like querying a standard tool or reasoning about a common sub-problem) tend to be solved by multiple teams, so they are worth saving. Other steps (like team-specific reasoning dead-ends) only one team will ever need, so saving them pollutes memory without helping anyone.

Third, because only the most reusable steps get saved, the shared memory stays lean — teams do not drown in noise when they query it. When team B later encounters the same sub-problem team A solved, it checks memory, finds the step, and skips the redundant work. The total time to solve the problem drops because the sum of all team runtimes is reduced: some teams skip repeated computation and instead fetch from memory.

The reward signal closes the loop. Teams that use a saved step and solve the problem quickly provide positive credit to the "save this step" decision; teams that never use a saved step or use it but waste time provide negative credit. Over many runs, the controller learns the pattern: save steps that are reused by multiple teams, drop steps that clog memory with single-use junk.

Math after the picture

The memory admission reward

First in words:

total_score = final_success_reward - memory_pollution_penalty, where pollution_penalty = count_of_unused_steps_in_memory

Then the compact form:

score = (1 if solved else 0) - unused_fraction * memory_size

Every symbol:

solved1 if team solved the problem, 0 otherwise
unused_fractionhow many saved steps were never queried by any team (0 to 1)
memory_sizetotal number of steps stored (scales the penalty)
A tiny worked example
Run 1: Team solves problem (solved = 1). Memory holds 10 steps, 4 were never used by any team (unused_fraction = 0.4). score = 1 - 0.4 * 10 = 1 - 4 = -3. The controller saved junk.
Run 2: Team solves problem (solved = 1). Memory holds 8 steps, 1 was never used (unused_fraction = 0.125). score = 1 - 0.125 * 8 = 1 - 1 = 0. Slightly wasteful.
Run 3: Team solves problem (solved = 1). Memory holds 6 steps, 0 were never used (unused_fraction = 0). score = 1 - 0 * 6 = 1. Perfect: solved and no wasted steps.
The controller sees this signal and learns: accept only steps that will actually be reused. Next run, it rejects steps that look like dead-ends.

The penalty scales with memory size because a small amount of junk is tolerable, but a massive memory full of unused steps becomes a liability.

What can go wrong

What can go wrong

Memory bloat from overeager saving. If the controller is too eager to save steps, memory grows with unusable junk. When teams query a huge memory, retrieval (scanning or indexing) becomes a bottleneck. The solution is the penalty term: unused steps reduce the score, so the controller learns to be selective.
Interdependencies between steps. Some steps are only useful in combination. A step that queries an API makes sense only if you first checked that the API is online. Saving one without the other causes teams to waste time. The controller must learn context — when is a step really helpful? This requires the algorithm to see actual reuse patterns.
Delayed rewards obscure causality. A team might save step X early (e.g., querying a database), but step X only becomes useful 20 steps later when another team needs that data. Reinforcement learning must work backward from the final reward (solved or not) and assign credit to each decision that led to the outcome. If the causal link is subtle, the credit assignment algorithm might reward the wrong step — e.g., penalizing a useful save because credit was accidentally assigned to an adjacent decision instead.
When learned memory wins. The paper shows wins on AssistantBench and GAIA when teams face diverse sub-problems that overlap (e.g., a medical diagnosis where teams independently query the same labs or reason about the same symptoms). The more structural overlap, the higher the savings.
What a runnable demo should prove

What a runnable demo should prove

A demo should show a concrete task where multiple parallel teams naturally solve overlapping sub-problems. For example: a question-answering task over a large document where ten teams explore different reasoning paths (Question 1: What is the budget? Question 2: Who approved it? Question 3: When was it approved?). Teams A and B both need to extract the same paragraph. A third team, handling a different question, never needs that paragraph. The controller should learn to save common extractions and skip team-specific explorations.

total_system_runtime = max(team_1_runtime, team_2_runtime, ..., team_N_runtime); comparison = runtime_without_shared_memory / runtime_with_LTS

The demo must show that parallel teams using learned shared memory finish faster (measured by max team runtime, not sum, since teams run in parallel) than teams that re-solve everything independently, without losing solution quality.
