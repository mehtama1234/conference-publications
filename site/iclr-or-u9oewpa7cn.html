DeMo: Decoupled Momentum Optimization

DeMo cuts the data sent between GPUs during training by 85 times using a two-step trick: compress momentum locally, then share only the essential parts.

Paper explainersAll themesOptimization

Training giant language models on many GPUs requires constant synchronization—all GPUs stop to share their computed directional nudges (called all-reduce). This creates a massive communication bottleneck. DeMo solves this by decoupling each GPU's local momentum updates and transmitting only a compressed version, then using the momentum buffer itself to track what was not yet shared. On models with 1 billion settings to remember, DeMo reduces data transmission 85-fold per step while maintaining the same training loss.

Zero assumption version

The bottleneck: synchronous all-reduce

Today's training needs dozens or hundreds of GPUs working in parallel. Each GPU computes gradient updates (directional nudges) on its own small batch of data. Then all GPUs must synchronize: they send their full gradients to each other, combine them, and send the combined result back. For a 1 billion-parameter model, this 'all-reduce' operation means terabytes of data crossing the network per training step.

A beginner might think 'we need to send everything to stay synchronized,' but this is wasteful. Gradient information is redundant: different GPUs working on similar data compute similar updates, and not every number in the gradient matters equally to the final model improvement. Sending terabytes of near-duplicate information is like mailing the same letter to everyone instead of posting it on a bulletin board.

The core move: Instead of each GPU sending its full computed gradients to others, it keeps momentum (the aggregated memory of past updates) local and transmits only a compressed, sparse version—retaining just the critical numbers.

The algorithm as a flow

What it actually does

Each GPU computes its local gradient update.

Using only its own batch of data, GPU i calculates how to nudge the model.

Accumulate into local momentum using the standard rule.

The momentum buffer at each GPU blends the new gradient with its prior momentum (standard exponential smoothing).

Apply a rotation transform to the momentum.

A Fast Fourier Transform (a standard reordering algorithm) rearranges the numbers so the most important directions cluster at the start, concentrating signal.

Keep only the top k largest values; discard the rest.

Send a small sparse list instead of the full momentum to other GPUs.

Aggregate and apply; store the dropped part locally for next step.

Combine sparse updates from all GPUs, apply them to the model, and accumulate the discarded part as error feedback into the local momentum for the next step.

What the paper changes

What the paper changes

DeMo changes how momentum is synchronized across GPUs. Instead of sending the full momentum buffer (or full gradients) between GPUs at every step, it sends only a sparsified version—the k largest coefficients after a rotation transform. The key move is decoupling: each GPU maintains its own uncompressed momentum buffer locally and only shares a lossy snapshot. Error feedback happens implicitly: the momentum buffer itself accumulates whatever was not shared, naturally compensating for the lost information on the next step.

the object it moves  =  the synchronized momentum (the running buffer of smoothed updates)
The hidden quantity

The hidden quantity: communication bandwidth per step

measured quantity  =  transmitted bytes per training step

Communication bandwidth is the total number of bytes sent over the network per training step, summed across all GPUs. In standard data-parallel training (DDP), this is proportional to the model size and the precision of the numbers (full 32-bit floats for each setting the model must remember). For a 1 billion-parameter model with 4 bytes per number, that is roughly 4 gigabytes per GPU per step, multiplied by the all-reduce overhead (sending to all, combining, broadcasting back).

DeMo estimates this bandwidth by the size of the sparsified momentum it sends: if it sends only the top k out of n numbers, and k is much smaller than n, the transmitted bytes drop by a factor of roughly n divided by k. On the OLMo-1B model, DeMo achieves an 85-fold reduction. The paper measures this directly: per-GPU communication volume in megabytes per training step.

Why it works

Why it works: three interlocking pieces

Standard distributed training fails because it sends the full gradient (all n numbers) from every GPU. DeMo works because momentum vectors are redundant in a specific structure: they have peaks (large directions of change) and valleys (tiny, noisy directions). If you reorder the momentum using a rotation (the DCT transform), the peaks cluster at the start. Discarding the valleys loses little information because those directions barely affect the model; the peaks are what moves the model forward.

The second piece is local accumulation. When GPU A receives momentum from GPU B, it applies only the sparse part (the top k values). What about the dropped values from GPU B? Instead of trying to send them anyway, GPU A simply leaves its own local momentum buffer unchanged by those missing parts. On the next step, GPU A's local momentum already contains the accumulated effect of everything GPU A computed, plus the missing parts from others naturally accumulate over time as GPU A computes its own gradients. This is called error feedback—the errors (missing updates) feed back into the next step's computation.

The third piece is why this stays synchronized. All GPUs apply the same aggregated sparse momentum to the shared model parameters (the standard all-reduce on the compressed vector). Local momentum buffers stay decoupled, but the model parameters stay in sync because they all apply the same sparse updates. Over many steps, the accumulators at each GPU drift (they have seen different dropped information), but the model itself converges normally because it receives coherent, combined updates.

Math after the picture

The equation and a worked example

First in words:

local momentum evolves as standard exponential smoothing, then is sparsified and communicated; aggregated sparse momentum updates shared parameters, while local buffers accumulate uncommunicated information.

Then the compact form:

M_t = beta * M_{t-1} + (1 - beta) * G_t ; send_t = top_k(DCT(M_t)) ; param_t+1 = param_t - lr * (aggregate(send_t) + lambda * param_t)

Every symbol:

M_tthe local momentum buffer at time step t
betamomentum decay (typically 0.9–0.99)
G_tthe gradient computed locally at step t
DCT(M_t)rotate the momentum vector using Discrete Cosine Transform
top_k(...)keep only the k largest absolute values; zero out the rest
send_tthe sparse momentum vector sent to other GPUs
aggregate(send_t)all-reduce on the sparse vectors from all GPUs (sum then divide)
param_tthe shared model parameters at step t
lrlearning rate
lambdaweight decay coefficient
A tiny worked example
GPU 1 at step t: local gradient G = [0.5, 0.02, 0.48, 0.01, 0.49]. Momentum decay beta = 0.9.
Prior momentum M_{t-1} = [0.3, 0.01, 0.2, 0.005, 0.25].
New local momentum M_t = 0.9 * [0.3, 0.01, 0.2, 0.005, 0.25] + 0.1 * [0.5, 0.02, 0.48, 0.01, 0.49] = [0.32, 0.011, 0.23, 0.0095, 0.279].
After DCT reordering, large values move to the front: [0.4, 0.35, 0.19, 0.015, 0.001].
Top-k with k=3: send_t = [0.4, 0.35, 0.19, 0, 0].
Other GPUs receive and aggregate; GPU 1 also has its own local M_t kept unmodified.
Dropped parts [0.015, 0.001] stay in GPU 1's buffer and blend into M_{t+1} naturally on the next step.

The decoupling means each GPU's momentum buffer grows with all its own gradient history, while shared updates are sent in compressed form; error feedback is automatic because dropped values persist locally.

What can go wrong

What can go wrong

If sparsification is too aggressive (k too small), training diverges. Discarding too many directions loses critical update information. The paper shows k=32 is stable for 1B models but k=8 causes training instability. The sweet spot depends on model size and learning rate schedule.
If momentum decay is poorly tuned, error accumulation builds up unchecked. The local momentum buffers at each GPU drift from each other as they accumulate different dropped information. If momentum decay beta is too small, older accumulated errors linger. The paper recommends using 1000 warmup steps instead of 500 to avoid instability during initialization.
Sparsification via top-k can introduce bias if updates have structured patterns. If only certain directions (e.g., the first few after rotation) always carry signal, repeatedly dropping the same tail directions skews the learned model. Randomly reshuffling the order before each sparsification performs marginally better, but the paper uses a fixed deterministic reordering (DCT) because it runs much faster and does not need to be recomputed at every step.
Done right: use DCT, tune k to match model size and learning rate, warm up for at least 1000 steps. With these precautions, DeMo achieves convergence curves indistinguishable from dense all-reduce on 300M and 1B parameter models.
What a runnable demo should prove

What a runnable demo should prove

Build a small-scale simulator of distributed training: set up 4–8 'GPUs' (parallel threads or processes) that each compute gradients on random batches of a toy dataset (e.g., MNIST or a synthetic regression task). Implement standard SGD with momentum for each, and a version with DeMo sparsification. Measure two metrics: (1) per-step communication volume in bytes (sum of all sends across all GPUs), (2) training loss curves over time. Plot both on the same graph. The demo should show that DeMo's communication drops by a factor of 10–50 (depending on k) while the loss curve remains almost identical to dense all-reduce for the first 1000 steps and beyond.

communication_reduction = (dense_bytes_per_step) / (demosparsified_bytes_per_step) ; loss_gap = max(loss_demosparsified - loss_dense) over all steps

The demo should make it viscerally clear: you can cut network data flow dramatically without sacrificing training quality, as long as you keep the top k directions and track the discarded information locally.
