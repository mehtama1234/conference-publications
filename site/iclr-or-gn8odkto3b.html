Hilbert: Recursively Building Formal Proofs with Informal Reasoning

Hilbert combines a reasoning LLM, a formal prover, and a theorem library into an agentic system that solves hard math proofs by breaking them into solvable pieces and fixing errors.

Paper explainersAll themesAgents & Tool Use

Large language models can do math, but their proofs are often wrong and you cannot verify them. Formal theorem provers (like Lean 4) let you check proofs automatically, but formal provers built into LLMs solve far fewer problems than general-purpose reasoning. Hilbert bridges this gap by running four components in a loop: an informal reasoning LLM, a formal prover LLM, a theorem retriever, and a verifier. When the formal prover gets stuck, Hilbert breaks the problem into subgoals and tries again, using error feedback to repair failed attempts.

Zero assumption version

Two kinds of math reasoning, both broken

Math reasoning in large language models (machine learning systems trained on vast amounts of text) works pretty well at finding answers. But the answers it writes cannot be automatically checked — you have to read them by hand, and they are often wrong.

Formal theorem provers (specialized software like Lean 4 that guarantees correctness) can check proofs automatically and absolutely. But LLMs built to write proofs in formal languages solve way fewer problems than LLMs writing casual math in English. The gap is huge: general reasoning LLMs solve maybe 70% of hard proofs, but formal provers built into LLMs solve only 30%.

A naive approach: just pick one or the other. But that leaves half the table on the floor.

The gap to bridge. Hilbert runs an informal reasoner and a formal prover in a loop. When one fails, the other tries. The two feed each other.

The algorithm as a flow

What it actually does

Try direct formal proof

Feed the goal to the formal prover; if it succeeds, done.

Retrieve relevant theorems

Use a search engine to find theorems from the library that may help solve this goal, because having names of relevant facts lets the reasoner skip re-proving them.

Generate informal proof sketch

Ask the informal reasoning LLM to sketch a proof using the retrieved theorems.

Decompose if stuck

If the informal proof fails, split the goal into smaller subgoals and repeat steps 1-3 on each.

Validate and refine

Run a formal verifier on the assembled proof; if it catches an error, ask the reasoner to fix it and retry.

What the paper changes

What changes

Hilbert does not change the weights of either the reasoning model or the formal prover. Instead, it changes the strategy for combining them: it routes problems between a reasoning LLM and a formal prover based on what each one is good at, rather than making one model do both jobs.

the object it moves  =  the routing and decomposition strategy
The hidden quantity

Solvability at each depth

measured quantity  =  how many subgoals are solvable at each recursion level

The paper measures a hidden quantity: how deep into the problem tree does Hilbert need to go before a subgoal becomes simple enough to solve. This is not a number the prover reports directly; it emerges from the algorithm. At recursion depth 0, the full problem is hard. At depth 1, breaking it into two or three subgoals makes some of them easier. At depth 2 or 3, most subgoals are within reach of the reasoner or the formal prover. The paper limits recursion to a maximum depth (say, 5), trading off richness for speed.

The paper measures this by tracking: how many goals succeed at each depth, and whether more depth actually helps or just wastes compute. This is the hidden lever. If every goal solves at depth 1, stopping there saves time, because each extra layer of recursion costs more reasoning and verification steps. If most goals need depth 3, the paper runs to depth 3.

Why it works

Why breaking problems helps

The formal prover is like a chess engine that looks ahead only a few moves. On a complex board (a hard theorem), it runs out of moves to try and gets stuck. But if you give it a simpler position (a subgoal), it can often finish it. Hilbert uses the informal reasoner to break the complex position into simpler ones.

When a subgoal is still too hard, Hilbert recurses: break it further. This creates a tree of subgoals. At the leaves (the deepest, simplest subgoals), the formal prover usually succeeds. As the tree rebuilds, the formal prover stitches the small proofs back together. If stitching fails, the verifier catches the error and tells the informal reasoner which piece is wrong; the reasoner rewrites just that piece and tries again.

The informal reasoner also retrieves theorems from a library (Mathlib, a massive collection of proven math facts). Instead of re-proving basic facts, the reasoner just names the fact and moves on. This is much faster than proving from scratch, because naming an existing theorem takes a few words of work, whereas re-proving it from first principles requires hundreds or thousands of words of reasoning.

How the pieces fit together

First in words:

success = if_prover_succeeds_or (if_retrieved_theorems_and_reasoner_sketch_pass_verifier or if_recursion_to_depth_D_finds_solution)

Then the compact form:

Hilbert(goal, depth) = Prover(goal) OR (depth < D AND Reasoner(goal, RetrievedTheorems(goal)) AND VerifyAndRefine(proof)) OR Recurse(Decompose(goal, depth+1))

Every symbol:

Prover(goal)attempt direct formal proof; return proof if success, null if stuck
Reasoner(goal, theorems)ask informal LLM to write a proof sketch using the given theorems
VerifyAndRefine(proof)run formal verifier; iterate reasoning to fix errors; return true if proof validates
RetrievedTheorems(goal)search library for theorems matching this goal
Decompose(goal, depth+1)break goal into subgoals; call Hilbert on each; stitch proofs back
depthhow many levels deep in recursion (protects against infinite trees)
Dmaximum recursion depth (typically 5 or so)
A tiny worked example
Goal: prove that (a + b)^2 = a^2 + 2ab + b^2 for all real numbers.
Step 1: Try formal prover directly. Formal prover fails (goal is algebraic, prover prefers logic).
Step 2: Retrieve theorems. Search finds: distributive law, commutativity, associativity.
Step 3: Reasoner sketches proof using those theorems.
Step 4: Verifier checks the sketch. It works! Done.
Total work: 1 direct attempt + 1 retrieval + 1 sketch + 1 verification = 4 steps.
Without Hilbert: formal prover alone would try 100 times and fail, reasoning LLM would give an unverifiable answer.

Hilbert succeeds if any branch works: either the prover solves it directly, or the reasoner with theorems works, or recursion finds a solution.

What can go wrong

What can go wrong

Recursion depth runs out. If a proof requires breaking a problem down 10 times, but Hilbert caps depth at 5, it will fail. Increasing the cap costs more compute time.
Retrieved theorems do not fit. The theorem retriever uses similarity search (looking for keywords in meaning), but if the relevant theorem has a very different name or statement, the search may miss it. Then the reasoner has to solve without that shortcut.
Informal sketch is wrong and hard to fix. The reasoner may sketch a proof that is mathematically wrong or uses reasoning the verifier cannot validate. Multiple iterations might not fix it, especially if the mistake is in the reasoning itself, not just syntax.
Verifier is overly strict. The formal verifier may reject a sketch that is actually correct but phrased in a way the verifier does not understand. This wastes iterations.
Done right. Hilbert works well when problems have a clear recursive structure (big proof decomposes into smaller, independent subproofs) and the theorem library is comprehensive. Math olympiad problems and academic theorems often fit this pattern.
What a runnable demo should prove

What a runnable demo should prove

Build a small proof assistant that takes a simple algebra goal (commutativity of addition, for example), runs the Hilbert algorithm on it, and shows each step: Does the formal prover solve it directly? No? Then retrieve similar theorems. Does the reasoner sketch a proof? Does the verifier accept it? If not, which error? Call the algorithm recursively.

Visualize the recursion tree as it grows: each node is a goal, color-coded by which component solved it (prover, reasoner, recursion). Count how many times the verifier rejected and was fixed. Compare the tree size (number of subgoals) to depth (how deep recursion went).

success_count = number_of_goals_solved / total_goals_in_tree

The demo should make it clear that Hilbert is not magic: it is a choreography of existing tools (reasoning, proving, retrieval, verification) in a loop. The power comes from knowing when to switch tools and when to break a problem smaller.
