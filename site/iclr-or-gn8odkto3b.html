Hilbert: Recursively Building Formal Proofs with Informal Reasoning

An agent that splits hard math proofs into simpler pieces, asks LLMs to solve each piece either informally or formally, and glues them back together with verification.

Paper explainersAll themesAgents & Tool Use

Large language models are great at explaining math in everyday words, but they make mistakes that we cannot prove wrong. Formal proof systems like Lean 4 verify proofs with total precision, but current models trained for formal reasoning solve fewer problems than those using plain English. Hilbert closes this gap by building an agent that combines both: it thinks informally to break problems apart, then asks specialized models to formally verify each piece.

Why math proofs are hard for LLMs

Large language models can explain mathematics in plain English—they can reason through steps and suggest ideas. But here is the catch: they make subtle mistakes. A mathematician checking the proof on paper might catch them, but a model has no way to know if it went wrong.

The fix seems obvious: make a specialized model that outputs proofs in Lean 4, a formal system where the computer itself checks every step automatically. If the proof compiles, it is correct. But there is a tradeoff: models trained to output formal Lean code solve only half as many problems as models working in plain English. You get certainty but lose the reasoning muscle.

A beginner might try training a single model to do both at once, but formal and informal reasoning require opposite skills—one needs to be concise and exact, the other exploratory and flexible. That model would fail at both.

The problem in one sentence. Informal reasoning can find the solution but makes mistakes; formal proofs are airtight but hard to generate. Current models cannot do both.

The algorithm as a flow

What it actually does

Informal reasoning splits the goal

When the formal prover gets stuck, Hilbert asks an informal LLM: break this into smaller pieces.

Attempt formal proof of each piece

For each subgoal, a specialized Lean-trained model generates formal proof tactics (Lean code).

Verifier checks the proof

Lean 4 runs the proof. Either it compiles (success) or fails with an error message.

Refine failed pieces

If a subproof fails, the error message goes back to the informal reasoner to reframe that piece.

Recurse until solved

Repeat decompose-and-verify until the whole theorem is formally proven or declared unsolvable.

What the paper changes

What the method changes

Hilbert changes where the reasoning happens. Instead of asking one model to do both informal and formal reasoning, it splits the labor: the informal model handles decomposition and refinement (the exploratory thinking), and the formal model focuses only on translating individual subgoals into Lean tactics (the mechanical translation). The verifier provides feedback that flows back to the informal reasoner, creating a loop.

the object it moves  =  decomposition strategy and feedback routing
The hidden quantity

The proof tree depth and branching

measured quantity  =  decomposition fanout and recursion depth

The hidden quantity here is how much the problem has been broken down. A theorem that requires only one or two decompositions is easier than one that needs five levels of nesting or dozens of subgoals at each level. This is not mentioned in the abstract, but it matters deeply: if decomposition creates too many pieces, the formal prover drowns in them; if it decomposes too little, the pieces stay too hard for formal tactics.

Hilbert measures this implicitly through the verifier feedback: if a subgoal fails, the agent knows decomposition did not go deep enough, and the informal reasoner is asked to try again. The depth of the recursion tree is thus the hidden signal that guides whether the strategy is working.

Why it works

Why informal-then-formal works better than formal-only

The reason Hilbert outperforms a formal-only prover is that it recruits the informal model's reasoning strength before invoking formal verification. Informal reasoning excels because it can make long chains of logical leaps and explore multiple pathways; it is fast and flexible. Formal reasoning is bulletproof because Lean checks every single step, but it is slow and has a narrow range of tactics it knows how to apply.

By using the informal model to decompose the problem first, Hilbert narrows the scope of what the formal prover must do. Each subgoal is easier than the original problem, so the formal prover is more likely to find a valid tactic sequence. When a subgoal does fail, the informal reasoner does not just give up—it learns from the Lean error message and tries a different decomposition. This feedback loop exploits the informal model's adaptability.

The verifier's role is critical: it surfaces exactly which pieces are stuck, so the informal reasoner knows where to refine. Without this signal, decomposition would be random. With it, decomposition becomes targeted and improves with each failed attempt, because the informal reasoner sees the exact Lean error message and can adjust—breaking that subgoal differently, or changing how it frames the logical requirements.

The recursive decomposition score

First in words:

Let S be the original theorem statement. If the formal prover cannot directly prove S, decompose it into subgoals G_1, G_2, ..., G_n. For each G_i, attempt formal proof. If G_i fails with error message E_i, ask the informal reasoner to refine or re-decompose G_i into G_i1, G_i2, ... and recurse. The depth d_i of the recursion tree for G_i is a proxy for decomposition adequacy. A subgoal is solvable if d_i remains bounded and the formal prover finds a tactic sequence.

Then the compact form:

solved(S) = all G_i at depth d_i are formally verified, where d_i >= 1, max(d_i) < D_max

Every symbol:

Sthe original theorem statement to prove
G_ithe i-th subgoal after one decomposition
d_ihow many levels of recursive decomposition subgoal i required
D_maxthe maximum depth before giving up (prevents infinite loops)
E_ithe error message from Lean when subgoal i fails
solved(S)true if all subgoals are formally proved; false if any subgoal is unsolvable
A tiny worked example
Theorem: Prove property P on set X (too hard for formal prover directly).
Decomposition 1: Break into subgoals P_A (prove on subset A) and P_B (prove on subset B).
Formal attempt on P_A: fails with error 'tactic did not close goal'. Recursion depth d_A = 1.
Informal re-reasoning on P_A: decomposes further into P_A1 and P_A2.
Formal attempt on P_A1: succeeds. Formal attempt on P_A2: succeeds. Recursion depth d_A = 2.
Similarly, P_B decomposes and verifies at depth d_B = 1.
All subgoals proved: max(d_A, d_B) = 2 < D_max. Original theorem P solved.

The depth represents how many times the informal reasoner had to refine a subgoal; bounded depth means the strategy is working efficiently.

What can go wrong

What can go wrong

Over-decomposition explosion. If the informal reasoner breaks a problem into too many pieces or nests too deeply, the sheer number of subgoals overwhelms the system. It runs out of time or memory before the formal prover can verify them all.
Infinite decomposition loop. A subgoal is truly unsolvable, but the informal reasoner keeps trying new decompositions. Without a hard bound on recursion depth D_max, the system hangs.
Formal prover stuck on a solvable subgoal. A subgoal is decomposed perfectly, but the formal prover does not have the right Lean tactic in its training. Verifier reports failure, and the informal reasoner re-decomposes, but the core issue is that the formal model is weak.
Done right. The informal reasoner makes smart decompositions that match the theorem's logical structure. Each subgoal is just barely within the formal prover's capability. The verifier catches mistakes early. The recursion depth stays under D_max. The full proof is solved in reasonable time and verified by Lean 4.
What a runnable demo should prove

What a runnable demo should prove

A demo should show a concrete theorem (e.g. a combinatorial identity or a number-theory property) that the formal prover alone cannot prove. Then run Hilbert and show the decomposition tree: which subgoals were created, how deep the recursion went, and which subgoals required re-reasoning. Finally, display the final Lean 4 proof that Lean verifies as correct.

success_rate = (theorems_solved_by_Hilbert) / (theorems_solved_by_formal_only) = fraction by which Hilbert improves on the baseline

The demo must make it impossible to miss that decomposition plus feedback enables the formal prover to tackle problems it could never handle alone (because each subgoal is smaller and within the prover's capability), and that Lean 4 certifies every result.
