ProtoTS: Hierarchical Prototypes for Transparent Time Series

ProtoTS forecasts time series by matching data to prototypical patterns (learned templates), organized as a hierarchy so coarse patterns explain the big trend and fine patterns add precise details.

Paper explainersAll themesTime Series & Sequential

When you forecast the future using deep learning, the model often gets the numbers right but acts like a black box. ProtoTS takes a different approach: it explains every prediction by saying which learned template patterns (prototypes) the input data matches best. It arranges these prototypes in a hierarchy, like a tree, so high-level patterns show the overall shape and low-level patterns show local wiggles.

Zero assumption version

Existing time series forecasters are opaque and miss multiway interactions

Time series forecasting is prediction of future values using past data plus extra context variables (like weather, holidays, day-of-week). Deep learning models do this well on accuracy benchmarks, but they give almost no explanation: you plug in data and out comes a number, with no way to see what patterns the model relied on.

Worse, when data has many types of variables (numbers and categories mixed together) that interact (a holiday plus the first day of a lunar month together create an unusual pattern), old interpretable models fail to capture how these combinations jointly shape the forecast curve. They explain individual time steps in isolation, never the full trend.

The beginner's naive fix: just add explainability scores to existing models, or show which inputs had the highest influence on the output. But highlighting inputs does not naturally explain the output curve itself—it only shows which inputs mattered, not what temporal pattern they triggered.

In one sentence. ProtoTS predicts by matching input data to learned hierarchical prototypes (templates of temporal patterns), making every prediction traceable to specific patterns and their explanations.

The algorithm as a flow

What it actually does

Embed inputs separately

Process each variable type (numbers vs categories) through its own channel to handle them best.

Fuse interactions

Merge channels through a bottleneck to capture how variables combine without overfitting.

Score prototypes

Compute similarity (distance in feature space) from embedded input to each learned prototype.

Traverse the hierarchy

Top-level prototypes weight the overall trend; child prototypes refine with local detail.

Synthesize the forecast

Each matched prototype decodes into a time sequence; blend them to form the output curve.

What the paper changes

The thing the paper changes: prototype organization

Standard prototype models store a flat list of templates. ProtoTS organizes prototypes in a tree (hierarchy), where each parent prototype has children that refine it. This lets the model separate global trends (handled by coarse parents) from local wiggles (handled by fine children).

The hidden quantity

The hidden quantity: how much each prototype contributes

measured quantity  =  per-level prototype importance

Every forecast depends on how closely the input matches each prototype. The paper measures this as a similarity score: how far is the input embedding from each stored prototype template in feature space (distance measured as the straight-line length in the space of numbers, often called Euclidean distance). When distance is small, similarity is high, meaning this prototype is active and contributed to the prediction.

The hierarchy reveals this unevenly across levels. A coarse parent prototype might have high activation (this is a weekday-like pattern), while a child of that parent could have even higher activation (specifically, a holiday-affected weekday). By reading these scores level-by-level, a user sees which broad pattern applies and which specific refinement was triggered.

Why it works

Why matching templates with multi-variable fusion works

The core insight: time series do not flow randomly. They follow a handful of repeating templates shaped by combinations of context (day-of-week, temperature, holiday). If you learn these templates (prototypes) and mark which one each input resembles, you can explain the prediction simply.

But templates only work if you capture interactions between variables. A holiday alone looks different from the first day of a lunar month alone, but together they create a third unique pattern that neither causes alone. ProtoTS handles this by embedding each variable type in its own channel (numbers stay continuous, categories get discrete encodings), then forcing all channels through a narrow bottleneck. This bottleneck is like a funnel: each variable must compress its information to a small shared space. When they pass through together, they cannot avoid each other—their features are squeezed and mixed, so the model must learn where each variable's effect overlaps with others. This forced co-compression works because the only way to fit all the information through the bottleneck is to find the overlaps and build a joint representation; if variables stay in separate channels, the model can ignore their dependencies. The result is a fused representation that naturally encodes interactions.

The hierarchy handles scale: coarse prototypes (ancestors) capture big recurring patterns that appear across many days or domains. Detailed prototypes (descendants of a coarse one) refine those patterns with local anomalies. When you want to explain a forecast, you read the hierarchy like a decision path: start at the coarse prototype that matched (weekday-like), then descend to the child that matched more closely (weekday in November), then to the grandchild (weekday in November with rain). Each level adds a new detail. If a coarse prototype is wrong, that misunderstanding stays at the top. If a detailed prototype is wrong, it only affects one branch. This compartmentalization improves both accuracy (fine details boost predictions) and interpretability (the expert can steer by adjusting prototype definitions at any level).

Math after the picture

The similarity-based prediction formula

First in words:

For each input, compute distance to every prototype. Weight each prototype's template by how close the input is. Sum the weighted templates to form the prediction. Repeat this at each hierarchy level: coarse weights are refined by children.

Then the compact form:

y_pred = sum_i w_i * proto_i where w_i = exp(-dist(input, proto_i)) / sum_j exp(-dist(input, proto_j)) and dist(input, proto_i) = euclidean_distance(embed(input), embed(proto_i))

Every symbol:

y_predpredicted forecast (the 96 time steps we output)
proto_ithe i-th learned prototype template (also a 96-step sequence)
w_isimilarity weight: how much prototype i contributes (a fraction 0 to 1)
embed(input)the fused embedding after multi-channel encoding and bottleneck fusion
embed(proto_i)the stored embedding of prototype i
distEuclidean distance in embedding space (square root of sum of squared differences)
A tiny worked example
Input context: weekday, 20 degrees Celsius.
Multi-channel embed produces a 32-dimensional vector (after bottleneck fusion).
Stored prototypes: coarse proto_1 (generic weekday) has embedding [1,2,1.5,...]; coarse proto_2 (weekend) has [2.5,3,2,...].
Distance to proto_1: sqrt((1-1)^2 + (2-1.9)^2 + ...) = ~0.4 (very close).
Distance to proto_2: sqrt((2.5-1)^2 + (3-1.9)^2 + ...) = ~2.1 (farther).
Weights: w_1 = exp(-0.4) / (exp(-0.4) + exp(-2.1)) = 0.67 / (0.67 + 0.12) = 0.85.
w_2 = 0.12 / 0.79 = 0.15.
Forecast is 85% weekday prototype curve plus 15% weekend prototype curve, giving a weekday-biased prediction.

The similarity is computed in the learned embedding space (after all the interaction-modeling has happened), so distances naturally encode how compatible the input context is with each template.

What can go wrong

What can go wrong

Prototype overfitting to training data. If prototypes memorize training time series exactly rather than learning general patterns, new data (test set) will not match them well and predictions fail. The bottleneck fusion helps by forcing each variable to summarize itself, but training must still gently steer the prototypes to stay broad and not overfit.
Bottleneck too narrow, loses information. If the bottleneck layer squeezes too hard, important details about individual variables vanish, and the fused embedding cannot distinguish between different contexts. Accuracy drops below flat prototypes.
Hierarchy mismatch: fine prototypes do not refine coarse ones. If a child prototype is similar in behavior to its parent, the hierarchy does not help and adds complexity, because the user cannot read a clear interpretation path: the refined prediction barely differs from the parent's, so the extra hierarchy layer is just noise, making the explanation harder to follow without improving predictions.
Done right: hierarchical embeddings plus gently-steered prototypes plus multi-channel fusion. When prototypes are learned from diverse training data (not overfitted) and the hierarchy is balanced (coarse captures 70% of variance, fine captures the remaining 30%), predictions are accurate, interpretable, and trustworthy.
What a runnable demo should prove

What a runnable demo should prove

Build a time series forecasting system with two datasets: electricity demand (with calendar/weather context) and traffic speed (with time-of-day/event context). Train ProtoTS alongside a black-box baseline. On test data, measure forecast accuracy (MAE or RMSE), and separately ask domain experts (power engineers, traffic planners) to rate how well they understand the predictions. For each test sample, show the top 3 matched prototypes at the coarse level and the top 3 matched children from the coarse winner. Ask: could you steer or correct this prediction by tweaking prototype definitions?

accuracy = 1 - (MAE / data_std); interpretability = (expert_trust_score + expert_steerability_score) / 2; combined_score = 0.6 * accuracy + 0.4 * interpretability

The demo must show that users can name the prototypes, understand why a given forecast was made, and propose edits to prototype definitions to steer behavior—all while keeping accuracy competitive with opaque models.
