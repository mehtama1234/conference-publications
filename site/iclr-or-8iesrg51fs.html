SciNav: Pairwise Comparisons for Scientific Coding Agents

An agent that solves scientific coding tasks by using side-by-side comparisons of solution attempts to prune the search space and pick promising branches.

Paper explainersAll themesAgents & Tool Use

When a language model tries to solve a coding problem, it can generate many possible solutions—some good, some dead ends. Traditional agents either pick the best one upfront or search blindly. SciNav instead compares pairs of candidate solutions head-to-head, using what it learns from those comparisons to cut away the weak branches and focus the search on the most promising paths, all within a fixed budget of attempts.

Zero assumption version

How do you explore solutions efficiently when you can only try a few times?

When a language model is asked to solve a coding problem (like debugging code or writing a function to pass tests), it could generate thousands of possible solutions in theory. But in practice, we can only try a handful—maybe 5 to 100 attempts—before we run out of money or time. A naive agent tries every idea it thinks of and ranks them by an absolute score (like 'this one is 73% likely to be correct'). But absolute scores are unreliable: the model is often confident when it is wrong, and uncertain when it is right.

The real blocker: with a tiny search budget, an agent needs to know which branches of the search tree are worth chasing and which are dead ends, fast. It needs to be right about those bets, because each wrong bet wastes a precious attempt.

The method in one sentence. Instead of trusting absolute scores, compare solution pairs to each other and use those comparisons to pick which branches to explore deeper.

The algorithm as a flow

What it actually does

Start with a queue of candidate solutions

The language model generates the first batch of attempts at the problem.

Pick two candidates and compare them

Ask: which is better? The model spots concrete code differences (one handles edge cases, one does not) because it has two pieces of code to contrast, and those differences are a clearer signal than a confidence score about one solution alone.

Use the winner to build the next layer

The winning solution gets to spawn new variants; the losing one is set aside or pruned.

Repeat comparisons up the tree

At each level, pare down the tree to the top K branches by comparison, not by absolute score.

Stop when budget is spent or a solution passes all tests

Return the best solution found in the allotted attempts.

What the paper changes

What the paper changes

Instead of ranking candidate solutions by an absolute confidence score, the paper ranks them by pairwise relative judgments (side-by-side comparisons). Each time two solutions compete, the winner is more likely to be genuinely correct, and that signal guides where the agent allocates its remaining search attempts.

the object it moves  =  Ranking method (absolute to comparative)
The hidden quantity

The hidden quantity: Comparison accuracy

measured quantity  =  How often a pairwise judgment matches which solution is actually better

When a language model is asked 'which of these two solutions is better?', it compares them because it has two pieces of code to analyze, and makes a judgment. That judgment has an accuracy rate: the fraction of times it correctly picks the solution that actually passes more tests or handles edge cases better. This hidden quantity matters because the entire search strategy depends on it; if comparisons are accurate, pruning works, and if not, the agent wastes time on inferior branches. Direct comparison is more accurate than absolute scores because when the model analyzes two concrete codes side by side, it articulates specific differences (error handling, variable names, library use), and those specific reasons correlate with which solution actually works better.

The paper estimates this by running experiments on benchmarks with clear right/wrong answers (scientific coding tasks with test suites). It measures how often the model's head-to-head judgment agrees with the actual performance gap between two solutions.

Why it works

Why it works: The chain of cause and effect

Language models are more reliable at relative judgments than absolute ones because comparison anchors the judgment in concrete code differences rather than abstract confidence. When asked to score a solution in isolation, the model might say '87% confident' even if wrong, because it is guessing. When asked to compare two solutions, the model must read and analyze both codes to justify its choice, so it spots actual differences (one handles the null case, one does not; one is more readable; one reuses libraries better), and those specific observations correlate strongly with which solution actually passes tests because they are real code properties, not guesses.

With a tight search budget, the agent cannot afford to waste attempts on solutions that lose head-to-head matchups. By pruning low-ranked branches (the ones that lose more than they win in comparisons) and allocating remaining attempts to winners, the agent focuses its limited tries on the most promising paths. This is more efficient than absolute scoring because comparisons correctly identify winners more often, so the agent does not waste budget exploring dead ends that looked okay but are actually inferior when compared side by side.

The tree structure multiplies this effect: each comparison eliminates not just one solution, but an entire subtree of variants that would have branched from it. So each comparison-based prune saves many future wasted attempts.

Math after the picture

The equation: Pruning based on pairwise win-loss records

First in words:

For each candidate, count wins and losses in head-to-head matchups. Keep the top K by win ratio; prune the rest. Expand each kept solution into new variants for the next level.

Then the compact form:

keep_candidate_i if ( wins_i / (wins_i + losses_i) ) ranks in top K

Every symbol:

wins_iNumber of comparisons where candidate i beat its opponent
losses_iNumber of comparisons where candidate i lost
top KNumber of branches to keep (e.g., keep top 3 out of 10)
rankOrder from best win-loss ratio to worst
A tiny worked example
Candidate A: 7 wins, 3 losses -> ratio = 7/10 = 0.70
Candidate B: 4 wins, 6 losses -> ratio = 4/10 = 0.40
Candidate C: 6 wins, 4 losses -> ratio = 6/10 = 0.60
Ranking by ratio: A (0.70) > C (0.60) > B (0.40)
If we keep top-2, we keep A and C; prune B. B's subtree (variants B1, B2, ...) is abandoned.

The agent does not need a probability for each solution; it only needs to rank them by the reliability of the pairwise judgments, then allocate remaining attempts to the winners.

What can go wrong

What can go wrong

Comparison model is also unreliable. If the language model is bad at comparing solutions (favors style over correctness, or gets confused by long code), then the pairwise judgments are just as noisy as absolute scores, and pruning removes good branches by mistake. The method only works because the model is genuinely better at spotting real differences when comparing two codes than guessing a single confidence number.
Comparing takes time and model queries. Each comparison costs money (model queries). If the budget counts total queries, not just solution attempts, then heavy use of pairwise comparisons can exceed the budget without exploring many branches. The paper's approach only helps because comparison is cheaper than generating a new solution; if not, the agent should spend its budget on new attempts instead.
Top-K threshold is fragile. If you keep top K and too many solutions tie in their win-loss record, you might randomly drop good ones. Conversely, if K is too large, you are not pruning aggressively enough and waste the budget.
Done right. When the comparison model is reliable and the task has clear right/wrong answers, SciNav consistently narrows the search space to high-quality branches, solving hard problems within tight budgets.

What a runnable demo should prove

Split them: one group gets absolute-score ranking, one gets pairwise comparison ranking. Both groups have the same total budget (e.g., 20 model queries each). Measure which group ends up with the higher-quality final solution.
