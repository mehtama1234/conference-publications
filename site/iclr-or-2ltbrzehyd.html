Chessformer: A Unified Architecture for Chess Modeling

Read a chess position square by square so one model can play well, predict human moves, and stay easy to inspect.

Paper explainersAll themesOther

Most chess models describe a position in awkward ways that hide what each board square contributes. Chessformer changes the basic representation: each square becomes one input unit, the model tracks where squares sit on the board, and the move selector reads interactions between starting and ending squares directly. This improves performance because the model sees the board in the same structured form the game uses, so it can learn legal patterns, human preferences, and tactical links without decoding a tangled notation first.

Zero assumption version

Chess positions are often encoded in ways that hide board structure

A chess position is a board with sixty-four squares, each either empty or occupied by one piece. To choose a move well, a model must understand local facts such as which pieces attack a square and global facts such as how the king, pawns, and open lines interact.

Many earlier systems feed the position to a language-style model as a move history or a long text string. That representation is awkward for teaching and inspection because one square's role is mixed into a long sequence. If you want to know why a rook move looked good, you first have to decode which part of the sequence described the rook, which part described the file it controls, and which part described the threats around the king.

The paper's move. Use one input unit per square and build the move selector around square-to-square interactions, because the board already has a fixed structure that the model can exploit directly.

Encode each square

What the paper changes

What the paper changes

The paper changes the basic unit of representation. Instead of treating a chess position as a move string, it treats the board itself as the input object and each square as a first-class part of that object.

the object it moves  =  board representation and move scoring
The hidden quantity

Square fidelity: the hidden quantity

measured quantity  =  how clearly each square keeps its own role

The hidden quantity is square fidelity: whether the model can keep track of what each square contributes without smearing that information across an awkward sequence. A representation with high square fidelity makes it easier to tell which piece controlled a tactic, why a defensive move mattered, or which empty square became critical because each square keeps its own slot instead of being blended into a long text description.

Chessformer raises square fidelity by assigning one slot to each square from the start. That helps across tasks because move quality and human move prediction both depend on board relations such as pressure on a file, king safety, or a pawn break, and those relations are easier to learn when the squares remain explicit.

Why it works

Why square-based inputs help

The mechanism is structural alignment. Chess is defined on a fixed board with legal moves between squares, so a model that starts from squares does not need to recover that layout from a text description. It can spend its capacity learning actual chess relations such as attacks, defenses, mobility, and mating nets.

The position information is also tailored to chess rather than copied from plain left-to-right text. That matters because a knight cares about L-shaped jumps, bishops care about diagonals, and rooks care about shared files and ranks. When the board-location scheme reflects those patterns, the model can connect distant but relevant squares with less wasted effort because the location cues already tell it how the board is organized.

The move selector then reads square-to-square interactions directly. That helps because a legal move is fundamentally an action from one square to another square, so scoring that pair is closer to the game itself than scoring a text fragment. The result is a smaller and clearer model that still performs strongly.

Math after the picture

Scoring a move from two squares

First in words:

Build one board representation for the starting square and one for the ending square, then combine them into a move score. Higher score means the model prefers that legal move.

Then the compact form:

score(move s->t) = u(s) + v(t) + w(s, t)

Every symbol:

sthe starting square of the move
tthe target square of the move
u(s)how promising the starting square looks in the current position
v(t)how promising the target square looks in the current position
w(s, t)the extra value of moving from this specific start square to this specific target square
score(move s->t)the final preference score for that legal move
A tiny worked example
Suppose a rook can move from d1 to d7.
The board says the rook on d1 is active, so u(d1) = 2.4.
The target square d7 pressures the opponent king side, so v(d7) = 1.3.
This exact route creates a tactical threat, so w(d1, d7) = 3.1.
Total move score = 2.4 + 1.3 + 3.1 = 6.8.
A quiet move from d1 to d2 might keep the same start-square value but get a much smaller target and pair term, so it ranks lower.

The equation separates square quality from move-specific interaction, because both matter in chess.

What can go wrong

What can go wrong

Board structure alone is not enough. A square-based input can still fail if the training data is weak, because the model may learn the board layout but not deep tactical or strategic patterns.
Rare positions remain difficult. Unusual fortress positions, underpromotions, or long forcing lines may stay hard because they appear rarely, so the model gets limited evidence about them.
Interpretation can still be misread. Inspection becomes easier, but not automatic. A square with high influence may reflect a threat, a defense, or a hidden follow-up, so a human still has to read the board carefully.
Done right. When the board representation is clear and the data covers the task well, the model can align its internal reasoning with actual chess relations because squares, legal moves, and threats are all expressed directly.
What a runnable demo should prove

What a runnable demo should prove

Build a small chess tool that takes a legal position, shows the sixty-four square inputs, and lists the top five legal moves with square-to-square scores. Then compare it with a baseline that reads the same position as a plain sequence. The demo should show whether the square-based version chooses stronger moves because the board layout stays explicit, and whether a user can identify which squares drove the choice for the same reason.

demo_score = move_quality + human_move_match + square_trace_readability

The core test is simple: if the board-first design is right, users should see better moves and clearer square-level reasons because the model never had to untangle the board from a sequence in the first place.
