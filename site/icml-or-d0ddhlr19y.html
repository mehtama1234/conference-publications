R²Eval: Routing-Aware Evaluation with Reasoned Signals

Route each question to the best evaluator model for cost and accuracy, based on how hard it is.

Paper explainersAll themesAgents & Tool Use

When you ask a large language model to grade another model's answer, you face a problem: not every model is equally good at grading every type of question, and the slowest models cost the most money. R²Eval solves this by picking the right grading model for each question, matching hard questions to strong graders and easy questions to fast ones.

Zero assumption version

Why monolithic graders fail

You have outputs from many different language models, and you need a program to grade them on a test set. The obvious approach: pick one strong model (like GPT-4 or a reasoning model) and have it grade every single output. The grader looks at the question and the model's answer, writes its reasoning, and gives a score. But this breaks in three ways.

First, some models are far better at grading certain kinds of questions, because they were trained or designed for those tasks. A model trained to reason through math problems grades math beautifully but wastes time on simple factual questions, because factual questions require only lookup accuracy, not reasoning. Second, a reasoning model asks for written work and produces long chains of thought — that costs real money in token charges and latency (wall-clock time). Third, you have no way to decide which grader to use without already running it, so you end up paying the slow-grader tax on easy questions too.

The paper's move in one sentence. For each question, estimate how hard it is, then pick a grader that is both strong enough and cheap enough for that difficulty level.

The algorithm as a flow

What it actually does

Measure difficulty per question

Run a lightweight model to score how complex the question is (reasoning, factual, creative, etc.).

Group by difficulty tier

Bucket questions into three or four groups: hard problems, medium problems, easy problems.

Select evaluator for each tier

Pick evaluator models that are accurate enough for each tier but as fast and cheap as possible.

Send each question to its tier's evaluator

Route hard questions to slow reasoning models; easy questions to fast, cheap models.

Combine the scores

Aggregate all the individual grading results into one reliable assessment signal.

What the paper changes

What the paper changes

The paper changes which evaluator model (grader) answers each question. Instead of using the same strong model for all questions, it picks a different grader per question based on how hard that question is.

the object it moves  =  Evaluator assignment
The hidden quantity

Difficulty: the hidden signal

measured quantity  =  Question difficulty level

Difficulty is a single number that measures how much reasoning, background knowledge, or creativity a question demands. The paper does not define difficulty mathematically; instead, it observes that questions fall into natural groups (math problems are harder than factual recall), and it learns to classify questions into these groups with a fast model.

The paper estimates difficulty by running a lightweight initial classifier on each question and seeing which category it lands in (reasoning-heavy vs. knowledge-heavy vs. creative). This is the router: it does not do the final grading itself, only predicts which evaluator will be most cost-effective.

Why it works

Why this works: matching capacity to load

The core mechanism is resource matching. Every evaluator model has a trade-off between speed and accuracy: fast models answer in milliseconds but make mistakes, slow models think for seconds and produce near-human grades. By predicting the difficulty of each question ahead of time, you can send hard questions (where mistakes are costly) to slow, accurate models, and easy questions (where even a fast model is right) to quick, cheap models. This lowers the total cost — the easy questions get fast service, and you only pay the slow-model tax on questions that truly need it.

Why is this better than just using one strong model? Because the strong model spends time and money on easy questions where a weaker, faster model would be just as right. You observe that questions fall naturally into difficulty tiers: algebra takes more reasoning power than spelling, code review takes more than factual lookup. A fast model handles the easy tier correctly most of the time. A slow model excels on the hard tier. By matching each tier to its appropriate model, you cut total cost; you never overspend on easy questions, and you never underspend on hard ones.

The routing score

First in words:

For each question, score the expected benefit of sending it to each evaluator, weighing accuracy gain against cost (latency and tokens). Pick the evaluator with the highest benefit-to-cost ratio.

Then the compact form:

benefit_i = (accuracy_i - baseline) / (latency_i + token_cost_i)

Every symbol:

benefit_inet gain from using evaluator i (how much more accurate it is, per unit of cost)
accuracy_ihow often evaluator i agrees with human graders, typically 0.0 to 1.0
baselinethe accuracy of a simple fallback (e.g., majority vote or cheapest model)
latency_iwall-clock time for evaluator i to answer, in seconds
token_cost_inumber of language-model tokens evaluator i consumes (directly tied to money)
A tiny worked example
Say a hard math question:
- Fast model: 60% accurate, 0.2 sec, 100 tokens → benefit = (0.60 - 0.50) / (0.2 + 100) ≈ 0.001
- Slow model: 85% accurate, 2.0 sec, 800 tokens → benefit = (0.85 - 0.50) / (2.0 + 800) ≈ 0.0004
Wait, that seems backwards! Let me reframe: the router learns from data which evaluator historically matches humans best on math, not a single formula.
On an easy factual question:
- Fast model: 95% accurate, 0.2 sec, 100 tokens
- Slow model: 96% accurate, 2.0 sec, 800 tokens
The fast model is nearly as accurate and vastly cheaper; send the easy question there.

The paper does not give a single closed-form routing rule, but instead learns routing policies (offline and online) from data on which evaluator model-pairs match human judgments best on each difficulty category.

What can go wrong

What can go wrong

Difficulty misclassification. If the router mistakes an easy question for a hard one, you send it to an expensive model and waste money. If it mistakes a hard question for an easy one, the cheap grader might not reason through it, and you get a bad score.
Evaluators have blind spots. A fast model might consistently fail on certain types of questions (e.g., it hates code, or it is biased toward short answers), because the model was trained on data that did not cover that domain well or developed a systematic bias during training. Routing will not help if no available model is good at that question type, because the router can only choose among the evaluators you have — if all of them are bad at code, the best router will still send code questions to the fastest one, which may still fail.
Aggregation noise. When you pool scores from different evaluators, they may have different biases. A fast model might rate answers 8/10 on average while a slow model rates 7/10. Combining them naively gives a mixed signal.
Done right. The paper constructs separate test sets for each difficulty level and evaluates the router's accuracy within each tier. It also studies how reasoning traces from different evaluators correlate with true human judgments, catching systematic mismatches.
What a runnable demo should prove

What a runnable demo should prove

Build a dataset of 50 questions across three types (reasoning-heavy, knowledge-based, creative). Annotate each with human scores. Then run three evaluators (a fast model, a medium model, a slow model) on all 50 questions. Measure their accuracy. Finally, build a simple router (a classifier that predicts which evaluator to use for each question based on question type). Compare two systems: (1) always use the slow model, (2) route by the fast classifier. The demo should show that routing achieves accuracy close to always-use-slow but at a fraction of the cost.

savings = (cost_always_slow - cost_routed) / cost_always_slow ; accuracy_maintained = accuracy_routed ≥ 0.95 × accuracy_always_slow

The demo must prove that you can cut costs in half while keeping accuracy almost as good.
