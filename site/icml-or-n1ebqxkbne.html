Training Language Model Agents to Find Vulnerabilities with CTF-Dojo

Train security-oriented agents inside runnable challenge environments where success and failure can be checked directly by execution.

Paper explainersAll themesAgents & Tool Use

Security tasks are hard to train from text alone because the agent must try commands, inspect outputs, and see whether an exploit attempt actually works. This paper builds a large collection of reproducible Capture-The-Flag challenge environments and uses verified execution traces to train agents. The main idea is simple: if the environment can confirm whether a step worked, training gets a clearer signal because success is grounded in actual behavior rather than guesswork.

Why training security agents is harder than training from static text

Finding a software weakness is an interactive task. The agent has to inspect files, run commands, test hypotheses, and revise its plan after seeing the machine's response. Static text examples do not capture that loop well because the key signal comes from what happens when the agent acts.

Good training environments are scarce. Many security setups take expert time to configure, and small ad hoc setups are hard to reproduce. That makes it difficult to scale agent training or compare methods fairly because each team ends up working with a different and often unstable setup.

The paper's move in one sentence. Build a large reproducible collection of runnable security challenges and train from execution-verified traces so that the agent learns from outcomes the environment can check directly.

What the paper changes

What the paper changes

The paper changes the source of supervision for security agents. Instead of relying mostly on text descriptions of good behavior, it draws supervision from live environments that can accept or reject what the agent actually did.

the object it moves  =  the training signal used to teach a security-focused agent
The hidden quantity

The hidden quantity

measured quantity  =  which action sequence will expose the weakness in the current environment

The central hidden quantity is the useful path through the challenge environment. At the start, the agent does not know which commands, files, or tests will reveal the weakness.

It can only discover that path by acting and reading the environment's response. That matters because wrong early moves can waste time, while a good probe can reveal the structure of the challenge and point toward a working exploit path.

Why it works

Why this works: executable feedback ties actions to truth

A text-only training example can tell the agent that a certain exploit plan is good, yet it does not show whether each step still works in a live environment. Security work depends heavily on that distinction because small command errors or wrong assumptions break the whole attempt.

CTF-Dojo closes that gap by making the environment itself part of the supervision loop. When the agent runs a command, the machine answers. When the exploit works, the setup confirms it. That grounded loop gives cleaner credit to the steps that actually caused success, so training can favor behavior that survives execution.

Math after the picture

Prefer trajectories whose success is verified by execution

First in words:

A simple summary is to score each candidate trajectory by whether it solves the challenge and by how much of the path is confirmed through execution. Training prefers traces with higher grounded score.

Then the compact form:

dojo_score(path) = solve_value(path) + beta * verify_value(path)

Every symbol:

dojo_score(path)overall training value of one challenge-solving path
solve_value(path)how much the path contributes to solving the challenge
verify_value(path)how much of the path is directly confirmed by runnable feedback
betaweight on the execution-verified part of the score
A tiny worked example
Path A proposes an exploit but never confirms it inside the environment.
Its solve value is 4 and its verify value is 0, so with beta equal to 1 the total score is 4.
Path B reaches the same idea and then confirms it with working commands.
Its solve value is 4 and its verify value is 3, so the total score is 7.
Training prefers Path B because execution checked the key steps.

The paper uses a fuller training recipe, but this score captures the central point that executable confirmation improves the learning signal because the environment verifies whether the chosen actions actually worked.

What can go wrong

What can go wrong

Challenge environments may still differ from live systems. A containerized exercise is more controlled than a messy production network, so transfer can weaken when real conditions add noise or hidden dependencies.
Verified traces can still be narrow. If most training traces solve similar classes of challenge, the agent may overfit to those routines because it sees fewer varied attack patterns.
Automation can reproduce setup mistakes at scale. If the pipeline builds a flawed environment, that flaw can spread into many tasks because the automated process repeats it consistently.
Done right. The framework is useful because it gives agents a place to learn from executable truth rather than from unsupported text-only claims.
What a runnable demo should prove

What a runnable demo should prove

Build five small security tasks inside containers, such as file disclosure, weak permissions, and simple service misuse. Compare an agent trained on written solutions alone against an agent trained on execution-verified traces from the same style of environment.

The demo should log command success, discovered clues, and final challenge completion. It should show that the execution-trained agent improves because it learns which trial actions expose real structure in the environment and which ones fail immediately.

grounded_gain = pass_rate_dojo - pass_rate_text_only ; verified_step_share = verified_steps / total_steps

The point is to show that live checked environments can provide a cleaner teacher for security agents.
