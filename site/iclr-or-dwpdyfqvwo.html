Group Tree Optimization for Speculative Decoding

Train the draft model on the same tree-based drafting strategy that decoding actually uses, not on single greedy predictions, to unlock faster LLM inference.

Paper explainersAll themesEfficiency & Systems

Speculative decoding speeds up language models by having a fast draft model propose several tokens at once, which a large target model then verifies in parallel. But here is the misalignment: during training, the draft model learns to predict a single greedy path (always picking the highest-confidence token next), while during actual decoding it must generate branching trees that get verified multiple ways. This mismatch leaves speedup on the table. GTO fixes it by training the draft model directly on the tree reward that matters: how many tokens it proposes that the target model actually accepts.

Zero assumption version

The draft-decoding mismatch

Speculative decoding works like this: a small fast model (the draft model) proposes multiple tokens; a large model (the target model) checks if each token is plausible and accepts it or rejects it. If tokens are accepted, you get several tokens per step at nearly the cost of one, speeding up the big model's inference. A beginner would try training the draft model to simply match the target model's output one token at a time, like a compression or distillation task.

But here is the real decoding process: the draft model does not pick one path and go straight ahead. It branches. It proposes token A, then token B, then token C, and simultaneously proposes alternatives like token B-prime and token C-prime, forming a tree. The target model then walks this tree and accepts sequences that feel natural. So at training time, the model sees single greedy paths; at decoding time, it must produce trees with many branches. The optimizer never sees a signal for branching.

The result: the draft model converges to a policy that is good at picking the single best next token, but poor at filling out a branching tree where some tokens will be rejected. The speedup caps out, leaving 7-8% of possible gains unrealized.

In one sentence. Train the draft model on the branching-tree strategy that decoding actually does, not on single-token prediction.

The algorithm as a flow

What it actually does

Build a draft tree.

Given a starting phrase, the draft model generates not one path but many branches, proposing alternatives at each step.

Compute acceptance length per branch.

Simulate the target model verifying each branch, counting how many draft tokens it accepts before stopping.

Define the tree reward.

Average the acceptance lengths across all branches. This single number measures the tree's quality.

Compare to a reference draft model.

Subtract the reference tree's reward from the current model's reward (debiasing), reducing noise.

Update the draft model.

Nudge the draft model's weights to increase the tree reward, using the same PPO-style update as in reinforcement learning.

What the paper changes

What changes: the training signal

The paper changes what the draft model is trained to optimize. Instead of a cross-entropy loss on single greedy predictions, it now optimizes the Draft Tree Reward: the expected number of tokens that the target model will accept from the draft tree. This one change makes the training objective match the decoding objective.

The hidden quantity

Acceptance length: how many draft tokens survive

measured quantity  =  Acceptance length

Acceptance length is the count of consecutive tokens that the target model verifies as correct and accepts from a draft sequence. If the draft proposes 'I saw a cat', and the target accepts the first 3 tokens 'I saw a' but rejects 'cat' as too unusual, the acceptance length is 3. During decoding, acceptance length directly sets the speedup: more accepted tokens per target-model step means less total compute.

GTO estimates the expected acceptance length by building a tree of draft tokens, simulating the target model's verification on each path, and averaging. Unlike traditional training where you see a single greedy path, the tree shows how well your proposals work across different branches, giving a more honest signal for what decoding will actually achieve.

Why it works

Why it works: aligning training with decoding reality

The mechanism is simple. Greedy training optimizes for single-token accuracy because the trainer shows only one path. But the true bottleneck is not single-token prediction; it is tree coverage. When you deploy speculative decoding, the draft model must fill out a branching tree where some paths will be rejected. Greedy training never pushes the model to do that well. Acceptance length is what actually matters for speedup, so training directly on it tells the model what to optimize.

The debiasing step (subtracting a reference model's tree reward) cuts down noise. A random tree gets some acceptance length by luck. By comparing your improved tree to a stable baseline, you isolate the signal: did this model actually learn to draft better, or is the variation just noise? This is the same trick used in reinforcement learning to reduce variance in reward signals.

The PPO-style update (a clipped weight-nudge step) ensures the training is stable. The model is being nudged to improve tree reward without overshooting, because the clipped update prevents the weights from changing so much that the new tree reward becomes unreliable or collapses. The constraint is applied along the longest accepted sequence, so the model learns from the most credible paths it generates, because these paths are the ones the target model actually accepted in practice and thus provide the clearest signal about what works.

Math after the picture

The tree reward equation

First in words:

tree reward equals the average number of tokens accepted across all branches of the draft tree, compared to the reference model's tree reward for the same context.

Then the compact form:

R(T_t) = E[length of accepted sequence in T_t under target model]; Advantage = R(T_t) - R(T_t_ref)

Every symbol:

T_tthe draft tree at context t
E[...]average over all branches in the tree
length of accepted sequencehow many tokens the target accepts before rejecting
target modelthe powerful model doing verification
R(T_t_ref)tree reward of the reference (frozen) draft model on the same context
Advantagethe difference, showing improvement over baseline
A tiny worked example
Suppose a draft tree has 4 branches: branch-1 gets 4 tokens accepted, branch-2 gets 2 tokens, branch-3 gets 3 tokens, branch-4 gets 1 token.
R(T_t) = (4 + 2 + 3 + 1) / 4 = 10 / 4 = 2.5 tokens on average.
The reference model's tree gets: branch-1 gets 2 tokens, branch-2 gets 1 token, branch-3 gets 2 tokens, branch-4 gets 1 token.
R(T_t_ref) = (2 + 1 + 2 + 1) / 4 = 6 / 4 = 1.5 tokens.
Advantage = 2.5 - 1.5 = 1.0. The improved draft model is 1 token better on average. This advantage signal tells training how much to boost these weights.

The tree reward directly measures how many tokens the draft model successfully proposes that the target accepts, turning decoding performance into a single honest number.

What can go wrong

What can go wrong

Tree is too small or shallow. If the draft tree does not branch enough (depth is shallow or only a few branches per token), the training signal is weak because it does not reflect real decoding trees. The remedy: use deeper trees and more branches during training, matching deployment settings.
Reference model is stale or weak. Debiasing by comparing to a reference model only works if the reference captures the baseline well. A weak or outdated reference model gives noisy advantage estimates. The remedy: refresh the reference model periodically and ensure it is a reasonable baseline.
Target model changes between training and deployment. GTO trains the draft model to pair with a specific target model. If you swap the target model at inference time, acceptance lengths will be different. The remedy: retrain the draft model for each new target, or use draft models that are less specific to one target.
Done right. Train the draft tree on the exact target model you will use at inference, refresh the reference model regularly, and use deployment-matched tree depth and branching.
What a runnable demo should prove

What a runnable demo should prove

Build a toy example: take a small language model as the target and a smaller one as the draft. Initialize the draft model with greedy training (standard token-matching loss). Then train it with GTO on a small dataset (e.g., 100 prompts). Measure acceptance length before and after. The demo should show that tree-trained draft models consistently accept more tokens than greedy-trained ones on the same prompts, proving the mechanism: optimizing the tree reward directly improves what decoding actually cares about, because the tree reward measures exactly what you deploy (expected accepted tokens), while greedy training measures something different (single-token accuracy).
