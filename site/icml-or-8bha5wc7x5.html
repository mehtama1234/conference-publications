Scaling Agentic Verifier for Competitive Coding

Generate many candidate programs, then use an execution-based checker that actively hunts for inputs where wrong programs disagree, so that reranking chooses the best answer more often.

Paper explainersAll themesAgents & Tool Use

A coding model often writes a program that looks plausible but fails on a corner case. Standard reranking tries to run candidate programs on random inputs, but random inputs rarely expose the exact mistake. This paper builds an active checker called Agentic Verifier. Instead of sampling blindly, it studies how candidate programs behave, proposes targeted test inputs, runs the code, and keeps refining the search until it finds examples that separate correct programs from incorrect ones. The final answer improves because the ranking step is now driven by sharper evidence.

Zero assumption version

Why random checking misses wrong code

Suppose a model writes ten candidate solutions for one programming contest problem. Some are fully correct. Some work only on easy cases. Some break when the input size is large, when values repeat, or when the answer sits at an edge condition. If you only inspect the code text, many wrong programs look fine because they follow the same high-level plan as the correct one.

A common fix is reranking by execution. Run each candidate on generated inputs, compare outputs, and favor the candidates that look consistent. The trouble is input generation. Randomly sampled inputs usually hit ordinary cases, not the narrow conditions that expose the bug. So the reranker keeps weak evidence and often promotes the wrong program.

The paper's move. Treat test-input search as an active reasoning problem: propose inputs that are likely to make candidate programs behave differently, execute them, then refine the search from the observed discrepancies.

The algorithm as a flow

What it actually does

Generate candidates

Sample several programs for the same contest problem.

Inspect behavior

Run the candidates on current inputs and record where their outputs agree or disagree.

Propose a sharper input

Use the verifier to suggest a new input that is likely to separate two or more candidates.

Execute and update scores

Run the new input, compare outputs, and raise the score of candidates that remain consistent under scrutiny.

Return the top program

After several rounds, choose the candidate with the strongest execution evidence.

What the paper changes

What the paper changes

The paper changes the verification stage after candidate programs are written. Instead of relying on passive random input generation, it adds an active checker that searches for inputs that are especially useful for distinguishing correct behavior from flawed behavior.

the object it moves  =  Test-input search during reranking
The hidden quantity

The hidden quantity: discriminative power of an input

measured quantity  =  How strongly one input separates candidate programs

A useful test input is not merely valid. It is valuable if it causes different candidates to produce different outputs in a way that reveals which candidates are likely wrong. That property is the hidden quantity in this paper. The system is searching for inputs with high discriminative power.

The verifier estimates discriminative power indirectly. It looks at current candidate behaviors, reasons about where their logic differs, generates a new input, and then checks whether the new execution splits the candidate set. If many candidates still behave the same, the input was weak. If several candidates break away, the input was strong because it exposed a clear behavioral difference.

Why it works

Why active verification helps

When several candidate programs solve the same problem, they usually share the obvious cases. They all pass on tiny inputs, on balanced examples, and on straightforward value patterns. Their differences show up only in narrow regions of the input space. An active verifier is useful because it does not waste effort on cases that everyone already handles. It tries to identify where the candidate logic diverges, then probes exactly there.

This changes reranking from a weak majority vote into an evidence-collection process. Each new input is chosen because it is likely to expose a specific weakness: a wrong stopping rule, a missed boundary condition, or a bad update order. When the verifier finds such an input, the resulting execution gives a stronger signal about which candidate is trustworthy. The top-ranked answer improves because the scoring step is grounded in revealing tests rather than broad but shallow sampling.

The training pipeline matters too. The verifier is trained on synthesized verification episodes, filtered examples, and reinforcement learning so that it learns a search policy for discovering useful counterexamples. That training helps because the model is rewarded for finding inputs that change ranking quality, not merely for proposing valid inputs.

Math after the picture

Scoring candidates by separating tests

First in words:

Each candidate receives credit when it agrees with the best-supported behavior across the growing set of verifier-generated tests. A test is more valuable when it causes larger disagreement among candidates, because larger disagreement reveals more about correctness.

Then the compact form:

score(c) = sum_t w_t * agree(c, t)

Every symbol:

score(c)final reranking score for candidate program c
tone executed test input proposed during verification
w_tweight of test t, larger when the test separates candidates more strongly
agree(c, t)1 if candidate c matches the supported behavior on test t, else 0
A tiny worked example
Suppose there are three candidates: A, B, and C.
Test 1 is ordinary and weak, so w_1 = 1. A, B, and C all match. Scores: A=1, B=1, C=1.
Test 2 is a sharp boundary case, so w_2 = 4. A and B match the supported output, C fails. Scores: A=5, B=5, C=1.
Test 3 is another sharp case, so w_3 = 3. A matches, B and C fail. Scores: A=8, B=5, C=1.
A wins because it stays correct on the tests that reveal the most.

The paper's actual reranking pipeline is more detailed, but this captures the core idea that the verifier creates weighted evidence by searching for highly separating tests.

What can go wrong

What can go wrong

Verifier searches the wrong region. If the verifier keeps proposing ordinary inputs, it adds cost without improving the ranking because the candidates remain tied.
Supported behavior is itself wrong. If many weak candidates share the same wrong output on a hard case, agreement alone can be misleading because majority behavior does not guarantee correctness.
Execution budget is too small. If the system stops after too few rounds, it may never reach the narrow cases that expose the real bug, so the reranker still lacks strong evidence.
Done right. The method works best when the verifier can iteratively refine its search and when the execution budget is large enough to uncover the few cases that separate close candidates.
What a runnable demo should prove

What a runnable demo should prove

Build a small contest-problem benchmark with ten to twenty problems. For each problem, sample several candidate programs from one coding model. Then compare two rerankers: one that uses random valid inputs and one that uses an active verifier that proposes new inputs after each execution round. Record which candidate each reranker selects and compare with the ground-truth accepted solution.

selection_accuracy = accepted_top_choice / total_problems

The demo should make visible that targeted counterexamples improve top-choice accuracy because they expose wrong corner-case logic that random tests miss.
