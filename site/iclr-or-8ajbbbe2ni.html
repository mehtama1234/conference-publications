FinSearchComp: Evaluating LLM Agents on Realistic Financial Search

A benchmark that measures how well language models can search financial data like real analysts do: fast lookups, historical checks, and complex multi-step reasoning over time-sensitive numbers.

Paper explainersAll themesDatasets & Benchmarks & Evaluation

Financial analysts spend hours every day doing the same three types of searches: looking up today's price, finding a historical number from years ago, and connecting multiple pieces of data together to spot a pattern. This paper builds a benchmark (a scored test) with 635 real questions that financial experts wrote and verified, so we can finally measure how close language models are to doing analyst-level financial search. The benchmark tests 21 models and finds that adding web search and financial tools helps—because models without access to live data and domain-specific libraries cannot verify freshness or parse specialized formats—but most models still miss obvious data or get confused by time.

Why existing benchmarks miss the real problem

Generic web-search benchmarks (like BrowseComp) ask models to find obscure facts by clicking through a few web pages. They work fine for trivia—but real financial analysts do something much harder. They look up live stock prices that change every second, they hunt through historical records from years past, and they stitch together clues from multiple sources to answer a question nobody has ever asked before.

Building a good financial benchmark is hard because it requires two things: deep financial knowledge (to write questions that actually matter to analysts), and access to real data that changes over time (to make answers verifiable). Most existing benchmarks skip this and use memorized history instead, so a model can cheat by just remembering facts it saw during training.

The question: Can we build a test that forces models to actually search, just like an analyst would? A benchmark with 635 expert-written questions split into three real analyst workflows: rapid time-sensitive lookups, point-in-time historical queries, and complex multi-step investigations.

The algorithm as a flow

What it actually does

Define three analyst tasks

Time-sensitive (stock price today), historical point-in-time (earnings from a specific quarter years ago), complex investigation (which month had the biggest market drop in 30 years).

Financial experts write real questions

635 questions total, each with a single correct answer, each requiring at least one tool call to search external data.

Set up verification with live data

For time-sensitive questions, the benchmark uses real-time APIs (stock tickers, exchange rates) so answers can be verified immediately and stay correct over time.

Apply multi-stage quality control

Experts check that questions are clear, answers are objectively right, and that the difficulty matches real analyst work.

Evaluate 21 models and analyze

Run language models against all 635 questions, measure accuracy, and break down which models (and which tool combinations) succeed or fail.

What the paper changes

The single thing the benchmark changes

Instead of a generic web-search benchmark, it is a financial-analyst-workflow benchmark. It swaps in real analyst tasks (three types), expert-verified questions (70 professionals wrote and checked them), and time-sensitive data (live APIs, not historical guesses).

The hidden quantity

The hidden quantity: Actual analyst-level competence

measured quantity  =  Expert-level accuracy on analyst workflows

The paper measures how close a model is to doing what a real financial analyst does. An analyst's competence is not just knowing facts—it is knowing how to search for time-sensitive data under pressure, knowing when historical numbers have changed due to accounting adjustments, and knowing how to piece together clues from multiple sources without getting lost. This benchmark measures all three.

To estimate this hidden quantity, the paper engages 70 professional financial experts to write and validate every question, and it grounds the answer verification in real APIs and databases. This makes the benchmark hard to cheat on because models cannot have memorized answers that change daily and require live data lookups—they have to actually search the web or call APIs, not retrieve from memory—and it is credible as a measure of real analyst skill because expert-written questions and expert validation ensure the benchmark reflects what analysts truly do.

Why it works

Why the design works: Force real search, not memorization

The benchmark works by building a trap that catches memorization. If you use static historical data (facts that never change), a large language model can have already seen and memorized those facts during training. But financial data changes every second. Stock prices shift. Exchange rates flip. So if you ask "What is the closing price of IBM today?" and ground the answer in today's real APIs, the model cannot have memorized it. It has to actually search—to call the API, parse the result, and verify it is current.

The three task types create a staircase of difficulty. Time-sensitive queries force rapid, accurate retrieval (you cannot guess). Point-in-time historical lookups (like "Starbucks' assets in Q3 2020") require the model to search for the exact quarter and year, which forces specificity and discipline. Complex investigations (like "which month in 30 years had the biggest market drop") require the model to search across many time periods, aggregate data, and reason about it. Each task type requires the model to do something a real analyst must do, so the benchmark measures real analyst skill.

Scoring and task structure

First in words:

accuracy_by_task = ( sum of correct answers in task ) divided by ( total questions in task ). Expert competence is measured as the accuracy gap between model and human expert.

Then the compact form:

Accuracy = (Correct Answers in Task) / (Total Questions in Task); Competence Gap = Expert Accuracy - Model Accuracy

Every symbol:

Correct Answers in Taskhow many of the task's 635 questions the model answered exactly right
Total Questions in Taskthe total number of questions the model attempted (635)
Expert Accuracythe accuracy a professional financial analyst achieves on the same questions
Model Accuracythe accuracy the language model achieves
Competence Gaphow far the model is from expert-level performance (0 means the model matches expert, high numbers mean the model is still learning)
A tiny worked example
Suppose time-sensitive questions: model gets 60 right out of 100 = 60% accuracy.
Suppose historical questions: model gets 50 right out of 100 = 50% accuracy.
Suppose complex questions: model gets 40 right out of 100 = 40% accuracy.
Average model accuracy = (60 + 50 + 40) / 3 = 50%.
Suppose human experts average 85% across all three tasks.
Competence gap = 85% - 50% = 35 percentage points (the model is still 35 points away from expert level).

The benchmark reports accuracy by task type, so readers can see which kind of search the model handles well and which kind it struggles with.

What can go wrong

What can go wrong

Stale or wrong data retrieval. If a model searches and pulls old prices or outdated exchange rates, it fails instantly on time-sensitive questions. The model has to verify freshness, which most models do not do carefully.
Accounting adjustments and normalization. Financial numbers come in different formats (trailing twelve months, fiscal year, quarterly). A model that does not parse these carefully will mix apples and oranges—like comparing Q3 earnings to full-year earnings—and get the answer wrong.
Corporate actions like stock splits. If a stock split 2-for-1 ten years ago, historical prices need to be adjusted. Models that ignore this will compare incomparable numbers.
Over-complicating simple queries. Some models invent extra search steps for straightforward questions (like "What is the market cap?"), wasting time and introducing error.
Done right: tool-augmented agents with time checks. Models that check timestamps, call financial APIs for real data, and validate their reasoning against domain-specific rules achieve expert-level accuracy on realistic tasks.
What a runnable demo should prove

What a runnable demo should prove

Build a small financial search system that takes three or four analyst questions (one time-sensitive, one historical, one complex), runs them through a language model with web and financial tool access, compares the model's answers to expert ground truth, and shows the accuracy on each task type. Run at least two models (like a base model without tools and a tool-augmented version) to show that tool access matters.

Task Accuracy = (Correct Answers on That Task) / (Total Questions on That Task); show this for each of the three task types.

The demo must make it obvious that time-sensitive queries require fresh data (not memorization) and that complex queries require multi-step search discipline. A model that retrieves old prices or mixes up accounting periods should visibly fail.
