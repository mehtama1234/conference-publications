Flash-Searcher: Fast and Effective Web Agents via DAG-Based Parallel Execution

Turn a web agent from a single long chain into a dependency graph so independent search branches can run at the same time.

Paper explainersAll themesAgents & Tool Use

A web agent often wastes time by doing everything in sequence. It searches one query, waits, reads one page, waits, then starts the next branch even when that branch does not depend on the first result. Flash-Searcher changes the execution structure. It breaks the job into subproblems, records which subproblems depend on which others, and runs the independent parts in parallel. The point is not speed alone. The graph also makes the reasoning plan explicit, so the system can revise the workflow when new evidence shows that a branch should be expanded, merged, or dropped.

Zero assumption version

Why sequential web agents waste work

Many search agents follow a simple pattern: take one action, wait for the result, reason about it, then take the next action. This is easy to implement, but it is slow and brittle on questions that naturally split into several evidence branches.

The wasted time is not only from waiting. A single chain also hides task structure. If the answer needs three independent facts, the agent should be able to pursue those facts separately and combine them later. A pure chain delays that split, so the agent burns steps on bookkeeping that a graph could represent directly.

The paper's move in one sentence. Represent the agent plan as a directed acyclic graph of dependent subtasks so independent search branches can run together and the workflow can be revised as results arrive.

The algorithm as a flow

What it actually does

Step 1: Decompose the question

Turn the original search task into smaller subquestions whose dependencies can be written explicitly.

Step 2: Build a directed acyclic graph

Create nodes for the subquestions and edges for dependency constraints so that only truly dependent work is serialized.

Step 3: Execute free branches in parallel

Run all currently unblocked search branches at once because their evidence does not depend on each other yet.

Step 4: Summarize and revise

Use intermediate results to merge duplicate work, expand missing branches, or stop branches whose evidence is already enough.

Step 5: Synthesize the final answer

Combine the branch summaries only after the dependency graph says the needed evidence is ready.

The hidden quantity

The hidden quantity

measured quantity  =  critical-path search time

The quantity that matters is not the sum of all actions. It is the time along the longest dependency path, because that path determines when the whole job can finish.

The graph helps because it reduces critical-path search time by moving independent evidence gathering off that longest path. The benefit is largest when the question naturally splits into multiple branches that can be explored without waiting on each other.

Why it works

Why the graph helps

Parallel execution helps because many search questions contain independent evidence branches. If one branch is checking a date and another is checking a definition, neither should wait for the other unless a later merge step needs both results.

The graph representation also helps reasoning quality because it exposes structure that is implicit in a long prompt trace. When dependencies are explicit, the system can tell which results are prerequisites, which branches are redundant, and where a summary should be inserted. Dynamic revision matters for the same reason, because early evidence can reveal that the original split was too coarse or too narrow.

A compact way to think about the speed gain

First in words:

Total completion time is driven by the longest dependency path, not by the sum of all branch times when free branches can run together.

Then the compact form:

completion_time = max_{path p in DAG} sum_{node n in p} time(n)

Every symbol:

DAGthe directed acyclic graph whose nodes are search subtasks and whose edges are dependency constraints
path pone dependency chain from an early subtask to a later merge
time(n)the execution time of one subtask node, including tool use and local reasoning
completion_timethe wall-clock time to finish the whole search workflow
A tiny worked example
Suppose one question splits into two free branches and one final merge.
Branch A takes 4 time units and branch B takes 5 time units.
The merge takes 2 time units after both branches finish.
In a pure chain, the total is 4 + 5 + 2 = 11.
In the graph, the two branches run together, so completion_time = max(4, 5) + 2 = 7.
The gain appears because the graph removes waiting between branches that did not depend on each other.

This does not guarantee better answers by itself because the graph still has to split the task well and merge evidence correctly.

What can go wrong

What can go wrong

Bad decomposition. The graph can lock in the wrong plan if the initial subquestions are split poorly, because later execution speed cannot repair missing evidence branches by itself.
Wrong dependency edges. Parallel execution can produce conflicting or premature branches if the system marks a true dependency as independent.
Weak branch merging. The final answer can still be wrong if the merge step fails to reconcile partial evidence, because the graph only organizes collection and does not guarantee sound synthesis.
Done right. A strong version should rewrite the graph whenever intermediate results reveal overlap or missing prerequisites so that parallelism stays aligned with the actual evidence structure.
What a runnable demo should prove

What a runnable demo should prove

Build a small search agent that answers questions requiring two or three independent evidence branches, such as finding separate facts and then combining them. Represent the plan first as a chain and then as a dependency graph with the same search tools.

The demo should prove two things. First, graph execution should finish faster because the free branches run together. Second, answer quality should improve when the decomposition is sound because the agent can cover several evidence threads before it writes the final response.

speedup = chain_time / dag_time ; answer_score = correct_answers / total_questions

If the graph version shortens completion time while preserving or improving answer score, it has reproduced the paper's core claim.
