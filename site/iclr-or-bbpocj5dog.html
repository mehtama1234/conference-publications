Queue Length Regret Bounds for Contextual Queueing Bandits

The paper shows how to schedule jobs to servers while learning hidden service rates by measuring how long the queue grows compared to the perfect schedule.

Paper explainersAll themesReinforcement Learning

Imagine a real queue: jobs arrive with different types, servers handle different job types at different speeds, and nobody knows how fast each server really is. A scheduler must pick which job goes to which server, all while learning the hidden speeds from watching what actually happens. Most scheduling theory assumes you know the speeds in advance. This paper tackles the harder problem: learning while scheduling, and measures success by how much longer your queue gets than the theoretically perfect queue would be.

Zero assumption version

Why scheduling with unknown speeds is stuck

In real data centers and hospitals, jobs queue up for servers. Each job has features (its type, size, urgency). Each server handles each job at a different speed, but you do not know these speeds up front because you have never seen those job-server pairs finish yet — you only learn speed from watching actual outcomes. A naive scheduler might always pick the fastest-looking server for each job, but you only learn a server is actually slow after sending jobs to it and watching them finish slowly. By then, your queue has grown.

The deeper trap: if you and the oracle differ on which job to pick next, the queues differ. Your queue has different jobs sitting in it than the oracle queue has. This makes it impossible to compare fairly: maybe your queue looks longer only because you picked different jobs earlier, not because you learned badly.

The core problem. Schedule jobs to servers while learning unknown service speeds, and measure success not by final decisions but by how much longer your queue gets than the perfect oracle.

The algorithm as a flow

What it actually does

Phase 1: Pure exploration

Try each server with different job types in round-robin to measure its true speed.

Phase 2: Epsilon-greedy learning

Pick the server that looks fastest plus occasional random picks to keep gathering hints.

Model speed with a sigmoid curve

Service speed is not linear: a hidden server preference combines with job features via a sigmoid (S-curve) to set the probability a job finishes in one time step.

Track confidence bands on estimates

Keep upper and lower confidence bounds on each server's hidden preference; pick the pair with the highest optimistic upper bound.

Compare using policy-switching queues

Measure regret using a fake queue: run your policy for T steps, then imagine switching to the oracle. Compare queue lengths between your full path and the oracle full path.

What the paper changes

What changes

The paper changes which job-server pair you pick next. Instead of guessing, you combine observed data (which pairs finished fast) with a learned model of how job features affect each server's speed.

The hidden quantity

The hidden quantity: server speed under each job type

measured quantity  =  Logistic service rate per job-server pair

The unknown is: how fast does server k finish a job with certain traits? The paper models speed using a sigmoid curve (an S-shaped probability curve). Imagine each server has a hidden preference list (a list of numbers, one for each job trait dimension). A job is fast if its trait list aligns with that preference. The alignment score goes through the sigmoid to give the probability the job finishes in one time step.

The algorithm learns each server's hidden preference by watching: when a job-server pair finishes (success) or stays in queue (failure). Each outcome is a noisy measurement. The algorithm accumulates many measurements, narrows its guess, and then uses an optimistic upper guess to pick the next pair.

Why it works

Why the method works: coupling and regret decomposition

The decisive move is the policy-switching queue. You cannot compare your queue directly to the oracle queue at any single moment, because they hold different jobs (you picked differently earlier). Instead, imagine a fake queue that runs your policy for T time steps, then imagine a second fake queue running the oracle for T time steps. The queue-length regret is the difference. This coupling idea unlocks a fair comparison.

Using this bridge, you split regret into two parts: immediate (picking the wrong pair now makes one job wait longer) and delayed (that mistake changes which jobs sit in the queue later, affecting future picks). The algorithm keeps its learned estimates of each server's speed converging toward the truth. As your estimates improve, mistakes become rarer, because you now confidently pick the actual fastest server-job pair instead of wasting picks on pairs you used to think were fast but now know are slow — the shrinking uncertainty means the algorithm's picks increasingly align with the oracle's best picks. The pure-exploration phase ensures you gather enough information on each server before you commit to picks that look best so far.

The regret decays as one over the fourth root of T in the random-context case because your confidence estimates shrink as you accumulate observations, so after the initial phase, your picks improve continuously. In the adversarial-context case, regret grows as the square of the log of T because an adversary can force you to revisit bad beliefs.

Math after the picture

The regret equation

First in words:

Queue length regret equals the expected difference between your queue length at time T and the oracle queue length at time T. The oracle knows the true service rates and picks optimally. Your regret is bounded by a sum of exploration cost (how many suboptimal picks you make while learning) plus the gap between your estimated service rates and the truth, weighted by how long jobs stay in the queue.

Then the compact form:

Regret_T = E[ Q(T) - Q*(T) ], bounded by O(T^(-1/4)) for random contexts or O(log^2 T) for adversarial

Every symbol:

Regret_Tcumulative queue-length difference over all time steps
Q(T)queue length at time T under your learning algorithm
Q*(T)queue length at time T under the oracle with known speeds
E[...]average over all randomness
T^(-1/4)the rate at which regret shrinks as T grows (random contexts)
log^2 Tthe bound for adversarial contexts (slower decay)
Worked example: comparing queue lengths
At time T=100, your queue has 25 jobs waiting. The oracle has 4 jobs.
Your queue-length regret so far: 25 - 4 = 21 job-steps of excess wait.
For random contexts, regret is bounded by about 100^(-0.25) ≈ 0.316 (after scaling by problem settings).
For adversarial contexts, the bound is log(100)^2 = 9.2^2 ≈ 85 (before scaling).
The random bound shrinks fast. The adversarial bound grows slowly even under worst-case picks.

The regret measures total accumulated penalty from not knowing speeds up front. Bounds shrink over time because your learned estimates get more accurate, so you make fewer mistakes.

What can go wrong

What can go wrong

Exploration cost is unavoidable. You must try each server on different job types to learn, which means some early jobs go to slow servers. The initial regret cannot be avoided, only managed by keeping the exploration phase short.
Adversarial contexts are much harder. If a malicious adversary can pick job features to trick the algorithm, regret grows as log squared of T, not the power-law decay. This is because each adversarial choice can undo learning from previous rounds.
The sigmoid model assumption can be wrong. If the true service rate does not follow a sigmoid curve (for example, if server k is slow for job trait A but fast for job trait A plus an extra feature), the estimated preferences will be biased and the algorithm keeps picking suboptimally.
Done right: the policy-switching queue idea generalizes. The coupling trick unlocks fair comparison even when policies make different choices. This idea extends to multi-queue systems and other scheduling problems where you learn while acting.
What a runnable demo should prove

What a runnable demo should prove

Write a simple simulator with 4 servers, 5000 time steps, and job features (lists of 20 numbers each). For each server, sample a hidden preference list (20 numbers) randomly. The service rate for a job on a server is sigmoid applied to the dot product (sum of element-wise multiplications) of job features and server preference. Simulate three policies: random picks, the oracle with known preferences, and the CQB algorithm. Plot queue length over time for each. The demo must show CQB's queue length staying close to the oracle queue after the pure-exploration phase ends, not close to the random queue.

Regret_demo = sum over t=1 to T of (queue_length_CQB(t) - queue_length_oracle(t))

The demo proves that learning service rates while scheduling keeps your queue almost as short as if you knew the rates up front. The regret should decay or stay bounded, not grow linearly over time.
