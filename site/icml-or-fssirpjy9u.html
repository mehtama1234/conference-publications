EvoCF: Multi-Agent Planning via Learned Constraints & Memory

A planner discovers better multi-agent strategies by mutating existing plans using rules learned from past failures, then scores candidates against stored experience.

Paper explainersAll themesReinforcement Learning

Large language models are good at writing single plans quickly, but they miss physical reality — robots can bump into each other, commands fail when agents disagree. This paper proposes EvoCF: instead of trusting one plan, the system mutates it into variants using rules learned from failures, keeps only plans that follow those rules, and ranks them by matching against a library of past execution outcomes. This finds plans that execute successfully where a model left alone would produce brittle ones.

Zero assumption version

Large language models fail at real multi-agent coordination

A naive approach: ask an LLM to write a plan for multiple agents (robots, drones, or characters in a simulator) working together. It produces one plan, fast, and you run it. But real embodied systems are constrained — agents have limited communication, move in shared space, and actions can conflict. The LLM cannot foresee these collisions because it has not seen the physics.

When the plan fails at runtime, that failure teaches nothing. The planner does not know why it broke. The next LLM call might make the same mistake.

Multi-agent planning is also inherently ambiguous: many valid plans exist for the same goal, but the LLM picks the first coherent one, not one that avoids coordination failures.

The problem. LLM planners produce brittle one-shot strategies that ignore coordination constraints and do not learn from failures.

The algorithm as a flow

What it actually does

Inductor

When a plan fails, extract a symbolic rule (constraint) that the failure violated.

Rule library

Collect induced rules over time; build a library of what breaks plans.

Plan generator

Take the LLM's initial plan and mutate it, sampling variants that satisfy the rules.

Evaluation

For each candidate, retrieve similar past executions and score fit.

Selection

Return the highest-scoring plan, with reasons (constraints & memories) shown.

What the paper changes

What the paper changes

The paper changes how candidate plans are selected. Instead of using the LLM's first plan, EvoCF generates multiple variants, filters by learned constraints, then ranks by match to memory. The object moved is plan quality.

the object it moves  =  plan selection strategy
The hidden quantity

The hidden quantity: constraint adherence score

measured quantity  =  how well a plan obeys learned failure rules

Each time a multi-agent plan fails in the simulator, the system infers a symbolic constraint — a rule like never have Robot A and Robot B in the same room simultaneously. Over repeated failures, a library of constraints accumulates. When scoring a new candidate plan, the system counts how many of these constraints it satisfies. Plans that satisfy more constraints are less likely to fail.

The paper estimates this by checking each candidate plan against the induced constraint library. A plan either satisfies a constraint (score +1) or violates it (score 0). Summing across all constraints gives a plan's total adherence score.

Why it works

Why it works: three coupled loops

The mechanism has three parts. First, induction from failure: when a real execution breaks, the system reverse-engineers the constraint that was violated. For instance, if two agents collide while moving through a doorway, the inductor hypothesizes a rule like agents must not occupy the same grid cell. Over trials, a rule library grows.

Second, evolutionary search with constraints: the LLM's one-shot plan is treated as a seed. The system mutates it (small changes to action sequences) and keeps only variants that satisfy all learned constraints. This shrinks the search space to plausible plans, avoiding re-learning the same failures.

Third, ranking by memory match: each surviving candidate is scored against a library of past successful executions. The retrieval-augmented evaluator finds similar scenarios and scores the plan by how well it aligns with what worked before. This is why constraint filtering helps: plans that obey constraints align more closely with past successes, so they score higher.

Together, these three loops eliminate brittle plans: the LLM generates a starting point, constraints prune implausible variants, and memory validates the survivors. The final plan is interpretable (you can see which constraints and past successes justified it) and less likely to fail (it has been vetted against learned failure modes).

Math after the picture

Scoring formula

First in words:

For each candidate plan P, the score combines constraint adherence and memory retrieval: score of P equals adherence count plus weighted sum of similarity to stored successful plans.

Then the compact form:

score(P) = sum_c [C_c(P)] + alpha * sum_s [sim(P, success_s) * weight_s]

Every symbol:

score(P)overall fitness of candidate plan P
sum_c [C_c(P)]count of constraints P satisfies; C_c returns 1 if P obeys rule c, else 0
alphabalance weight between constraint adherence and memory match
sum_s [sim(P, success_s) * weight_s]retrieve top successes; sim(P, success_s) is semantic similarity (0 to 1); weight_s is how recent or reliable success_s is
Tiny worked example: scoring two candidate plans
Suppose the rule library has 4 constraints. Candidate plan A obeys 3 (score 3). Candidate plan B obeys 4 (score 4).
Memory has 5 past successful plans. Plan A matches 2 of them with avg similarity 0.6 (retrieval score 1.2). Plan B matches 3 of them with avg similarity 0.7 (retrieval score 2.1).
If alpha=2, then score(A) = 3 + 2*1.2 = 5.4, and score(B) = 4 + 2*2.1 = 8.2.
Plan B ranks higher because it satisfies more rules and matches more past successes. In multi-agent settings, this keeps B out of collision zones and near tactics that have worked before.

The score penalizes plans that repeat past failures (low constraint adherence) and rewards plans similar to proved strategies (high memory match). Both terms increase the chance a plan succeeds in the real embodied system.

What can go wrong

What can go wrong

Constraint library becomes stale. If the environment changes (new obstacles, different agent capabilities), old constraints may no longer apply or new ones may be unlearned. The inductor must stay active to refresh the rule library.
Mutation space is too narrow. If the only allowed mutations are small tweaks (e.g., shifting timing by one step), the search may miss truly different strategies. Constraint filtering can prune the solution space too aggressively.
Retrieval memory is sparse or skewed. If the past successful executions are few or all solve the same simple scenario, the memory ranking will not generalize. New situations will have no similar precedent.
Inductor tolerates measurement noise. The paper uses symbolic constraint induction, which forgives small errors in the simulator. A rule like agents must stay in different rooms stays valid even if positions jitter slightly.
Interpretability is kept. Unlike a black-box LLM, every plan choice is backed by explicit constraints and retrieved successes, because the system shows which rules the plan obeys and which past scenarios it resembles. When a plan fails, you know exactly which constraint was wrong or which memory was stale, so you can fix the inductor or refresh the library.
What a runnable demo should prove

What a runnable demo should prove

Build a simple multi-agent embodied task: two robot arms reaching for objects on a shared table, or two drones delivering packages while avoiding a shared air corridor. Start with the LLM's one-shot plan. Then run EvoCF: induce constraints from a few simulated failures, mutate the plan into variants, score them against a small memory of past successes. Compare final success rate and interpretability (can you name the constraints and past plans that justified the chosen strategy?).

success_rate = (number of completed multi-agent tasks) / (total attempted tasks); interpretability = number of constraints and retrieved memories shown to the user

The demo must show that constraint filtering catches collisions the LLM would miss, and that memory ranking picks strategies similar to what has worked before — making the final plan execute more often successfully and remain human-understandable unlike a raw LLM output.
