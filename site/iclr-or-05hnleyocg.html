PLAGUE: Multi-turn Attack with Lifelong Learning

An adaptive framework that breaks LLMs in multi-turn conversations by learning from past attack successes and executing three coordinated phases with real-time feedback.

Paper explainersAll themesAlignment, Safety & Fairness

Language models talk with us over many turns, like a conversation. But they can be tricked through this long back-and-forth, especially if harmful intent is woven in gradually. This paper shows how to design attacks that improve over time: each failed attempt teaches the attacker what worked before, because saving successful past strategies to memory and retrieving similar ones for the next attack means you are not restarting from scratch—you are building on a track record of what actually broke the model.

Zero assumption version

Why multi-turn attacks are hard

A single prompt (one message) asking the model to do something harmful can be blocked — the model has learned to refuse. But over multiple turns (a long conversation), the same harmful goal can be hidden in breadcrumbs. The attacker could ask innocent questions, build up context, and sneak in the real request later.

The naive approach: just keep re-asking the same way until it breaks. That fails because the model sees the pattern. A smarter attacker would need to remember what worked before, plan a path through the conversation, and adjust on the fly when the model pushes back. But doing this by hand is slow. How do you automate it?

The bottleneck. Attacks need three things: a good opening strategy, a plan that evolves, and memory of what worked last time. Manual trial-and-error gives none of these.

The algorithm as a flow

What it actually does

Memory initialization

Start with a bank of known jailbreak strategies, each converted to a list of numbers that captures its meaning.

Planner phase

Retrieve similar past strategies from memory. Use them as examples to build an n-step plan.

Primer phase

Execute steps 1 through n-1 of the plan, asking innocent questions. If a step is refused, adapt the prompt and retry.

Scoring and adaptation

After each Primer turn, a rubric scorer grades the response. Poor scores trigger prompt rewriting.

Finisher phase

Ask the actual harmful goal. Model is primed and context-locked, often accepts.

What the paper changes

What the paper changes

The paper introduces a memory-backed multi-turn attack that learns from successful past attempts. Instead of blindly repeating the same attack, it retrieves similar working strategies, uses them to initialize a plan, and updates that plan based on live feedback from the model.

the object it moves  =  Multi-turn attack strategy
The hidden quantity

The hidden quantity: Strategy usefulness

measured quantity  =  Strategy effectiveness score

The paper measures how useful each past jailbreak strategy is for the current goal. This is the hidden engine that makes learning work: if a strategy worked before on a similar goal, it should hint at how to attack now.

The paper estimates usefulness by embedding the attack goal into a vector (a list of numbers representing meaning), embedding each stored strategy the same way, and finding which stored strategies sit closest to the current goal in that number-space. Similarity means the strategy is likely to work again.

Why it works

Why dividing into three phases makes attacks work better

The core idea: multi-turn attacks fail because the model notices when you're pushing toward something bad. If you ask for harmful code, it refuses. If you rephrase the same request, it refuses again because it sees the pattern.

PLAGUE splits the attack into two separate minds: Primer and Finisher. The Primer (steps 1 through n-1) acts harmless—it asks innocent questions that slowly set up context. The model accepts these because they seem normal. The Finisher (step n) then asks the real goal. By this point, the model has a full conversation history of accepted steps. The history is 'in context'—it shapes how the model responds next. So when the Finisher asks, the model is more likely to say yes, because it has been agreeing the whole time.

After each Primer turn, a rubric scorer (a second model trained to detect jailbreaks) grades the response. If the model's answer is too good (score 7 or higher on the rubric), the attack is working and the Primer moves to the next step. If the score is low (a refusal or weak answer), the Primer rewrites the prompt and retries. Feedback helps because without it you waste turns asking the same question over and over—you would never know if a step was stuck or just needed rephrasing. The rubric tells you what is working, so you build only on foundations that hold. This tight feedback loop ensures each step actually advances the goal.

Measuring strategy similarity

First in words:

For each stored strategy, compute how close it is to the current goal by comparing their embeddings. Retrieve the top-K closest strategies and use them as in-context examples for the plan generator.

Then the compact form:

similarity(goal, strategy_i) = embedding(goal) · embedding(strategy_i) / (|embedding(goal)| * |embedding(strategy_i)|)

Every symbol:

goalthe current harmful objective the attacker wants to achieve
strategy_ithe i-th past successful jailbreak strategy stored in memory
embedding(x)a vector representation of x, computed by the embedding model
·dot product—sum of element-wise products
|v|length of the vector v
similaritya score from -1 to 1, where 1 means the goal and strategy are identical
A tiny worked example
Goal: pretend to be a code-generation bot and output malware.
Strategy A (stored): successfully tricked a model by asking for debugging help, then asking for compiled output. Embedding distance to goal: 0.92.
Strategy B (stored): asked for encryption code unrelated to harm. Embedding distance to goal: 0.31.
Retrieve Strategy A because 0.92 > 0.31. Use Strategy A's approach (debugging + output) as the template for the Planner's n-step plan.
Planner adapts the template to the new goal and generates 4 steps.
Primer executes steps 1, 2, 3 with feedback scoring. If step 1 scores 8 / 10, advance. If step 2 scores 5 / 10 (refused), rewrite and retry.

Higher similarity means the stored strategy is a better template for the new attack, because a past strategy that attacked a goal very close to the current one has already learned which phrasings work, which model responses to expect, and which angles the model's guardrails don't watch—so re-using that template gives you a head start instead of inventing from zero.

What can go wrong

What can go wrong

Rubric scorer is too lenient or too strict. If the rubric evaluator grades the Primer steps incorrectly, the attack will advance even when it should stop, or get stuck retrying a step that was actually progressing. The paper sets a strict threshold (7.0 out of 10) for Primer but this is a hyperparameter—it must be tuned per target model.
Memory bank lacks diversity. If all stored strategies are similar to each other, retrieval will always pull the same template. The attack becomes predictable and the target model learns to block it. Diversity in memory is not addressed by the paper.
Finisher goal is too obvious. If the final harmful request is phrased clearly, the primed context might not be enough. The Finisher needs to mirror the vague, indirect style of the Primer steps, or the model will detect the intent shift.
Done right. When memory is diverse, rubric scoring is calibrated, and all three phases are executed with feedback, PLAGUE achieves 81% success on o3 and 67% on Opus 4.1 across multiple goal categories.
What a runnable demo should prove

What a runnable demo should prove

Build a simple attack on a small open-source language model (e.g., Llama 3.1-8B). Start with a goal: trick the model into generating instructions for something it would normally refuse. First, run a single-turn attack (ask directly) and measure the refusal rate. Then, implement PLAGUE: set up a memory bank of 5-10 past attack patterns, retrieve the top-2 similar ones, use them to build a 3-step plan, run Primer on steps 1-2 with rubric feedback, then run Finisher on step 3. Measure the success rate on the same goal. The demo proves that multi-turn planning beats direct attacks because on turn one the model has no conversation history, so it triggers its guardrails immediately, but after the Primer builds friendly context the model's defenses are already committed to accepting benign-looking requests. Memory retrieval improves plan quality because a past strategy that worked on a similar goal carries real knowledge about which angles bypass the model's safety training, while a random plan starts from scratch.

success_rate_PLAGUE = (number of goals where Finisher returns acceptance) / (total goals) × 100%

The demo should show that the same harmful goal that fails 12% of the time as a single-turn attack succeeds 70%+ of the time after PLAGUE's three-phase planning and memory-backed adaptation, because the model is hearing the harmful goal inside a conversation where it has already accepted eight similar statements—the context makes it much harder to refuse.
