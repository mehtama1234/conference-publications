Darwinian Memory: A Training-Free Self-Regulating Memory System for GUI Agent Evolution

Keep only the most-useful past experiences in an agent's memory, and actively discard ones that led to mistakes, so the agent learns smarter strategies without retraining.

Paper explainersAll themesAgents & Tool Use

Large language model agents that control computer interfaces can handle multiple applications and long, complex tasks, but they have a limited memory — they can only remember a certain amount of recent actions. When they do remember too much, they tend to reuse old failed plans because the bad memories are still sitting in the context. This paper proposes a memory system that acts like natural selection: useful, working experiences survive; useless or risky ones die.

Zero assumption version

Agent memory fills up with junk, so it replays bad plans

An agent tries to book a flight, then buy groceries, then check email — all in one session. Each task involves dozens of individual clicks and responses. The agent's working memory (the part that can hold recent context) has a size limit. With long sequences, either it forgets what it did earlier (losing useful patterns), or it remembers too much and gets confused.

Existing memory systems just store everything. The agent saves every step of every past task in a database and pulls random old experiences into the prompt when tackling a new task. This sounds good, but it backfires: the agent grabs an old experience where it clicked the "Cancel" button to exit a form — and it did that because the form was wrong for that old task. In the new task, the form is correct, but the agent plays back the old cancel-click anyway, because the memory said it worked before. Context pollution: outdated experiences that once made sense now lead to hallucinations.

In one sentence. Agents remember too much, so they reuse plans that worked for old tasks but fail on new ones.

The algorithm as a flow

What it actually does

Break trajectories into chunks

Each task is split into independent reusable sub-tasks, not stored as one long sequence.

Score each chunk by utility

Measure: did this chunk reach its goal? Did it take a normal amount of time? Would reusing it help new tasks, because chunks that succeeded before are more likely to succeed again?

Rank by survival value

High utility ranks survive; low-utility chunks face elimination.

Prune suboptimal memories

Delete chunks below a threshold; keep only high-utility, low-risk plans.

Prompt includes only survivors

Agent retrieves only the best experiences when planning the next task.

What the paper changes

The one thing it changes

The paper changes which past experiences get stored in memory and shown to the agent. Instead of keeping every trajectory, it keeps only the chunks (sub-task sequences) that score high on utility — meaning they succeeded, took reasonable time, and are applicable to new tasks. Everything else is discarded.

the object it moves  =  memory contents
The hidden quantity

Utility: does this past experience actually help?

measured quantity  =  Utility score for each memory chunk

Utility is a number that answers: if the agent reuses this chunk in a new task, will it work? It combines three signals. First: did the chunk reach its goal in the original task (success rate)? Second: did it take an unreasonable amount of time or steps (efficiency)? High-efficiency chunks score better, because tasks that waste time tend to go wrong (the agent gets confused or the app times out) and slow chunks are less likely to work under new conditions. Third: does the chunk involve risky, error-prone moves (e.g., clicking a button that failed 50% of the time in practice)? Low-risk chunks rank higher.

The paper estimates utility by tracking success counts and failure counts for each chunk across multiple tasks. It also flags which actions in a chunk led to errors, marking them as high-risk. The agent then scores each chunk as: (success rate) times (efficiency bonus) divided by (risk penalty). Only chunks above a threshold survive.

Paper reading. Utility is estimated as a product of success rate, efficiency normalized by median task time, and a risk penalty for chunks containing high-failure actions.
Why it works

Why survival-of-the-fittest memory works

The mechanism is simple: bad experiences keep leading to bad outcomes, so the agent should stop playing them back. Each time the agent reuses a memory chunk, it either succeeds or fails. Chunks that fail consistently get low utility scores. When a new task arrives, the agent only retrieves high-utility chunks, so it has a smaller, higher-quality menu of strategies to choose from.

This breaks the context pollution problem: outdated failures no longer sit in memory. When the agent sees a form-filling task, it no longer pulls the old cancel-click from a different form — because that chunk never scored well for form-filling. The pruning mechanism naturally filters out cross-task contaminants. At the same time, successful chunks — like the click sequence that logs into Gmail — rank high and get reused, because they work across many tasks. The agent evolves toward a lean, reliable playbook.

Math after the picture

Utility score formula

First in words:

Utility of a memory chunk equals its success rate times an efficiency bonus, divided by a penalty for risky actions.

Then the compact form:

U_chunk = (successes / total_runs) * efficiency_bonus / (1 + risk_penalty)

Every symbol:

U_chunkthe utility score for this chunk, ranging from 0 to 1
successes / total_runshow many times this chunk succeeded divided by how many times it was used
efficiency_bonusa boost if the chunk is faster than the median; 1.0 if near median time
risk_penaltya penalty for actions in the chunk that failed often; 0 if safe, higher if risky
A tiny worked example
Chunk A: used 10 times, succeeded 8 times. Success rate = 8 / 10 = 0.8.
Chunk A took median time, so efficiency_bonus = 1.0.
Chunk A contains one click that failed 1 out of 10 attempts, risk_penalty = 0.1.
U_A = 0.8 * 1.0 / (1 + 0.1) = 0.8 / 1.1 = 0.73.
Chunk B: used 10 times, succeeded 5 times. Success rate = 5 / 10 = 0.5.
Chunk B took 50% longer than median, efficiency_bonus = 0.7.
Chunk B has a risky click (failed 5/10), risk_penalty = 0.5.
U_B = 0.5 * 0.7 / (1 + 0.5) = 0.35 / 1.5 = 0.23.
Chunk A (0.73) keeps its spot; Chunk B (0.23) is discarded if threshold is 0.4.

The multiplication chain ensures that a low score in any dimension (low success, slow, or risky) drags down the overall utility; the agent only keeps balanced, reliable chunks.

What can go wrong

What can go wrong

Prune too aggressively, lose helpful diversity. If the threshold is too high, the agent discards useful chunks just because they did not score perfectly. A chunk that works 70% of the time is still valuable, but if the threshold is 80%, it dies. The agent then has fewer strategies and may fail on unfamiliar tasks.
Risk penalty miscalibrated, safe chunks lost. If a chunk contains one click that failed 10% of the time, but only on one specific app version, the risk penalty may be too harsh. The chunk could work perfectly on the new task, but the score is crushed.
Utility does not capture cross-domain transfer. A chunk might score low because it never succeeded in its original domain but works brilliantly in a different domain. Utility is based on past history, so combinations that are new and untested are under-valued.
Done right. The paper tunes the threshold and risk penalty by testing on held-out validation tasks (tasks not used for training the utility model). It monitors agent success over time and adjusts pruning to keep enough diversity while cutting junk.
What a runnable demo should prove

What a runnable demo should prove

Build a simple GUI automation task suite: two or three short sequences (e.g., log into email, fill a form, search for a document). Have an agent run each task multiple times with random errors injected (so some chunks fail). Track the utility score of each chunk. Then run a new task, and measure success rate when the agent uses all old chunks versus only high-utility ones. The success gap proves that filtering helps, because the agent no longer retrieves low-utility chunks that confuse its planning.

Success_improvement = success_with_filtered_memory - success_with_all_memory

The demo must show that removing low-utility memories raises the agent's success rate on a brand-new task, because the agent no longer wastes time on proven failures.
