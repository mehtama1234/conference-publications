UrbanMLLM: Joint Learning of Cross-view Imagery for Urban Understanding

UrbanMLLM learns from paired satellite and street-view images so one model can connect city-scale layout with street-level appearance when answering urban questions.

Paper explainersAll themesMultimodal

Urban understanding breaks if a model sees only one view of a city. A satellite image gives road layout, parcel structure, block density, and neighborhood context, but it misses facade detail, signage, lane markings, storefronts, and pedestrian-level appearance. A street-view image gives those local details but covers only a narrow direction from a single position. UrbanMLLM joins both views in one multimodal language model. Its core pieces are a cross-view perceiver, meaning a module that lets information from one view query and update information from the other, and a structural interleaved pre-training scheme, meaning the model reads mixed satellite, street, and text content in a consistent document order. The goal is not merely to add two image encoders. The goal is to teach the model how the two views correspond so it can reason across them.

Zero assumption version

Why one urban view is never enough

Satellite-only systems are strong at large-scale structure because roofs, roads, water, and parcel patterns are visible from above. They are weak at details needed for human-centered urban questions, such as whether a street edge is commercial, whether there are arcades or trees along sidewalks, or how building entrances are arranged.

Street-only systems have the reverse problem. They can read local appearance, but they often do not know where that view sits inside the larger city pattern. A single street image cannot reveal whether the block is near a highway interchange, part of a dense grid, or adjacent to industrial land. UrbanMLLM tries to fuse both because many city questions require simultaneous access to large-scale context and local semantics.

The paper's move in one sentence. Train one model on aligned satellite images, street-view images, and text so it learns direct correspondences between global layout and local urban appearance.

The algorithm as a flow

What it actually does

Collect aligned cross-view examples

For each location, pair a satellite patch, one or more street-view images, and text annotations describing the place.

Encode each view separately at first

Produce visual feature sequences for the satellite image and the street image using image encoders.

Run cross-view interaction

Let one view query the other through the cross-view perceiver so shared evidence is highlighted and mismatched evidence is exposed.

Arrange training inputs as urban documents

Interleave satellite content, street content, and text in a stable order so the language model learns cross-view context over long sequences.

Train on satellite-only, street-only, and cross-view tasks

Use a broad task mix so the model learns each view alone and also learns when the answer requires both views together, because some tasks are solvable from one branch while others expose missing evidence unless the branches cooperate.

What the paper changes

What the paper changes

The paper changes the interaction layer between views. Instead of concatenating satellite and street features and hoping the model discovers the relationship on its own, it introduces an explicit cross-view exchange mechanism and a training order that keeps paired evidence adjacent in context.

the object it moves  =  the connection between satellite and street-view representations
The hidden quantity

The hidden quantity

measured quantity  =  cross-view correspondence

The hidden quantity is the location-level correspondence between what is visible from above and what is visible from the street. That correspondence is not stated in labels such as 'commercial' or 'residential' alone. It includes whether a dense roof pattern implies narrow active streets, whether a wide arterial seen from above explains the lane structure seen on the ground, and whether a green canopy in satellite view matches tree-lined sidewalks in the street view.

Learning this correspondence matters because many urban questions require translation across views. To predict a street-level property from satellite imagery, the model must know which overhead cues usually imply which ground-level cues. To interpret a street image in context, it must know what larger neighborhood pattern that image belongs to.

Why it works

Why explicit cross-view interaction matters

If the model only sees both views side by side, it may still solve many tasks by overusing the easier view. For example, if a label can often be guessed from street appearance alone, the satellite branch may contribute little. The cross-view perceiver counteracts that because it requires feature exchange at the representation level. A satellite feature can pull relevant street detail into its state, and a street feature can pull larger spatial context from the satellite branch.

The structural interleaving step matters for the language-model backbone because long-context multimodal models learn from sequence order. When the paired views and their text are arranged as coherent urban documents, the model repeatedly sees how global context, local context, and language descriptions co-occur. That repeated ordering sharpens the joint representation because the same place is described from several angles within one training example.

Training across satellite-only, street-only, and cross-view tasks further stabilizes the system. Single-view tasks keep each branch competent on its own. Cross-view tasks force the branches to cooperate. The result can outperform single-view systems because the model learns not just more features, but the conditions under which each feature source should dominate.

The fusion objective

First in words:

The model learns task predictions while also learning to align satellite and street features from the same location, so paired views become easier to fuse than mismatched ones.

Then the compact form:

L = L_task + lambda * L_align(cross_view_perceiver(satellite_features, street_features))

Every symbol:

Lthe full training loss
L_taskthe loss for captioning, classification, question answering, or other urban tasks
lambdathe weight on the cross-view alignment objective
L_alignthe loss that encourages paired satellite and street representations to agree where they should
satellite_featuresthe encoded top-down image sequence
street_featuresthe encoded street-level image sequence
A tiny worked example
Suppose a satellite patch shows a dense grid with a broad road on one edge.
The paired street image shows multi-lane traffic, storefronts, and narrow sidewalks.
If the model predicts a low-density suburban label, the task loss increases because both views contradict that answer.
If the cross-view exchange fails to connect the broad road in satellite view with the lane structure in street view, the alignment loss also increases.
A better representation links those cues, so the model can answer both 'what does this street look like?' and 'what larger urban setting is this in?'

The exact form of the alignment term can vary, but the important point is that the model is trained to reward agreement between paired views of the same location.

What can go wrong

What can go wrong

Geospatial alignment can be noisy. If a street image is weakly paired with the wrong satellite patch, the model may learn false correspondences because the training example claims two different places are the same location.
One view can still dominate. If too many tasks are solvable from one branch alone, the shared model may underuse the second branch because the easier shortcut already minimizes the loss.
Coverage gaps limit transfer. Urban form changes across cities and countries, so a model trained on one data pattern may misread unfamiliar street design or building patterns unless the paired dataset is broad.
Done right. The method is strongest when the paired data is accurately aligned and the task mix includes problems that require both large-scale layout and street-level evidence.
What a runnable demo should prove

What a runnable demo should prove

Build a small paired dataset with a satellite patch, a street-view image, and a short description for each location. Train one baseline that concatenates both views without explicit interaction and one model with a cross-view exchange block. Include tasks such as predicting land-use type, inferring street greenery from satellite view, and inferring block density from street view.

Visualize cross-view focus weights, task accuracy, and failure cases where one branch alone is ambiguous. The demo should prove that explicit cross-view fusion changes the internal reasoning because the model uses evidence from one view to disambiguate the other.
