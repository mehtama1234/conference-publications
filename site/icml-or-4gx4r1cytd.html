ScaleEnv: Scaling Environment Synthesis from Scratch for Generalist Interactive Tool-Use Agent Training

Create many interactive training environments from scratch, test them automatically, and expand tool dependencies until each task is complete and solvable.

Paper explainersAll themesAgents & Tool Use

A tool-using agent improves when it can practice inside many interactive environments because each action changes the world and reveals what the next step should be. Building those environments by hand is slow, and many generated environments break in small but fatal ways. This paper presents ScaleEnv, a system that builds environments from scratch, tests them procedurally, and verifies that each task can really be solved with the available tools.

Zero assumption version

Generalist agents need many places to practice, but interactive environments are scarce

A generalist tool-use agent must adapt to many domains, many tool sets, and many multi-step tasks. Static instruction-answer pairs do not teach this well because the agent needs to act, observe the new state, and plan the next action. That requires interactive environments where actions have real consequences.

Existing environment synthesis methods usually fail in one of two ways. They either produce a small set of polished domains that do not cover enough variety, or they generate many domains that quietly break because tools are missing, states are inconsistent, or tasks ask for outcomes that cannot be achieved. Training on broken environments teaches the wrong lessons because the agent cannot tell whether failure came from its own policy or from a faulty world.

The paper's goal. Scale environment diversity without losing reliability, because agents need both breadth of practice and tasks that are actually executable.

The algorithm as a flow

What it actually does

Synthesize a domain

Create a new environment with objects, states, tools, and transition rules.

Generate candidate tasks

Propose goals the agent should accomplish inside that environment.

Run procedural tests

Check whether state updates, tool outputs, and observations remain internally consistent after actions.

Expand dependencies

If a goal requires tools or prerequisites that are missing, add them until the action chain can be completed.

Keep only verified tasks

Use executable action verification to retain tasks that can actually be solved with the environment's tool set.

What the paper changes

What the paper changes

The paper changes how training environments are produced. Instead of relying on a small library of manually authored worlds, it builds worlds from scratch and treats verification as part of generation, not as a separate cleanup stage.

the object it moves  =  how environments are synthesized and verified
The hidden quantity

The hidden quantity: environment validity under action sequences

measured quantity  =  Executable completeness

Executable completeness means that a task is not only stated but also reachable through a valid chain of actions in the environment. A domain can look detailed on paper while still failing this test if one required tool is absent, one state transition is broken, or one observation rule hides information the agent must know.

ScaleEnv estimates executable completeness by testing the environment with procedural checks and by expanding the dependency graph of required tools. If a goal says 'send the report', the system verifies that earlier actions such as opening the workspace, editing the file, and accessing the send tool are all possible in sequence. A task is kept only when that full chain can execute.

Why it works

Why verified synthesis scales better than hand-building

Environment diversity matters because a generalist agent learns broader habits only when it sees many different task structures, tool interfaces, and failure modes. A small fixed set of environments can teach narrow routines, but it leaves the agent brittle when the benchmark changes domain or tool layout.

Naive large-scale generation fails because interactive worlds have hidden constraints. One missing prerequisite can make a task unsolvable, and one incorrect transition can make the state drift away from reality after several steps. ScaleEnv handles this by turning verification into part of the generator itself: each draft world is stress-tested, and missing dependencies are added before the task is accepted.

This improves training because the agent's experience becomes trustworthy. When the agent fails, the failure is more likely to come from its own planning rather than from a broken environment. That matters for generalization because consistent feedback lets the agent learn reusable action patterns across many domains instead of memorizing accidental quirks of faulty worlds.

Math after the picture

The keep-or-reject rule

First in words:

A synthesized task is accepted only if it passes reliability tests and if there exists a valid action chain that reaches the goal using the available tools and prerequisites.

Then the compact form:

task_kept = reliability_pass and executable_path_found

Every symbol:

reliability_passall procedural tests on the environment succeed
executable_path_founda valid sequence of tool actions reaches the task goal
task_keptwhether the synthesized task is added to the training set
A tiny worked example
Task goal: 'email the completed budget file'.
First draft world has an editor and an email tool, but no login action for the email account.
Procedural tests pass for editing, but executable path check fails for sending.
Dependency expansion adds account setup and login tools.
Now the full action chain exists, so the task is kept.

The second condition is essential because a task description is not enough; the system keeps it only when the action sequence really exists.

What can go wrong

What can go wrong

Tests miss a long-range bug. A world can pass short checks and still fail after many actions if a later state update is wrong.
Dependency expansion keeps growing. If each tool introduces several new prerequisites, the generator may create very deep chains that are hard to finish within a practical episode budget.
Generated tasks become repetitive. Large scale alone does not guarantee useful variety; if many domains share the same action pattern, the agent may still overfit.
Done right. The approach works when verification stays strict and domain templates stay varied, because then each accepted task is both solvable and genuinely different from the others.
What a runnable demo should prove

What a runnable demo should prove

Build a tiny environment generator for office-style tool use. Let it create tasks such as editing a file, searching records, sending a message, or updating a calendar. Add a procedural tester that checks each tool's state change, and add a dependency expander that inserts prerequisites such as login or file creation when they are missing. Show that the final accepted tasks solve reliably under scripted rollouts and that an agent trained on more diverse verified worlds handles held-out domains better because it has practiced more kinds of action chains.

generalization_score = success_on_unseen_domains / total_unseen_tasks

The demo should make clear that larger training sets help only when the worlds are verified, because broken environments teach the wrong lesson while diverse working environments let the agent practice reusable planning behavior.
