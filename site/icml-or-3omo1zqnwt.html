Effectiveness and Efficiency in Tool-Calling

Fixing how we measure tool-calling and speeding up the learning so models can call functions well.

Paper explainersAll themesAgents & Tool Use

Tool-calling is when a language model stops generating text and instead calls a function—like looking up a fact, solving math, or fetching data. Without these tools, the model can only answer from what it memorized. This paper reveals two critical problems: first, the way we measure tool-calling quality is unstable and unreliable, and second, training the model to call tools wastes a lot of computation. This paper shows how to fix both.

Zero assumption version

Measuring tool-calling is fragile, and learning it wastes time

When you test whether a model calls tools correctly, you might change a small detail—like the phrasing of the system message or how you show past conversation history—and the score jumps by 20 points. That is unstable: it means leaderboards ranking models can give contradictory answers depending on hidden choices.

When you train a model using reinforcement learning to call tools, most of the compute goes to waste. During each learning round, you generate many candidate attempts, but half of them teach nothing—the model already knew what to do, or the task was too easy. Then when you update the weights, the learning algorithm runs expensive optimizations even on attempts that failed. A beginner would try generating many examples and then improving the model on all of them, but this wastes time because you are paying the full cost to learn from noise.

The move. Measure tool-calling carefully by documenting every choice, and accelerate learning by filtering which attempts actually teach something and by using a cheaper update method.

What it actually does

Audit evaluation pipelines

Run the same test with variations (different random seeds, prompts, history formatting) and measure how much scores swing.

Identify waste during rollouts

Track which generated attempts provide actual learning signal versus noise—cases where output already matched the goal.

Identify waste during updates

Realize that expensive optimization can be replaced by a simpler, faster update on high-signal examples, since weak signals need precision but strong signals do not.

Filter rollouts intelligently

Keep only attempts that differ from what the current model would do—those carry new information.

Use accelerated updates

Replace full optimization with a simpler update method, which works because you are only updating on examples where the signal is clear and unambiguous.

What the paper changes

What the paper changes

The paper touches two things: first, the evaluation protocol (the documented steps for measuring tool-calling quality), and second, the training procedure (which parts of reinforcement learning you actually run). It tightens the protocol with explicit choices so different labs get the same score, and it prunes the training loop to skip examples the model already knows and use simpler weight updates instead of expensive optimization.

The hidden quantity

The hidden quantity: signal-to-noise ratio in training examples

measured quantity  =  Learning signal in rollouts

When you generate a candidate way for the model to call a tool, it either carries a lesson or it does not. If the model would have already generated it, or if the task was so easy the score was always high, then that example teaches nothing—it is noise. The paper measures this by checking: does the current model already do this thing, or is this a fresh attempt that surprised the model? This is the signal-to-noise ratio.

The paper estimates it by looking back at which generated examples actually differ from what the current model would generate on its own. High-signal examples are the rare new ideas the model had not tried; low-signal examples are the redundant safe choices.

Why it works

Why this works: clear measurement plus smart training

Measurement is fragile because every hidden choice (random seed, prompt wording, how you show conversation context) changes what the model sees during testing. You think the model learned correctly, but actually you measured it under one set of conditions while another paper measured it under different conditions. The fix: run with a standardized, documented checklist so results are reproducible.

Training wastes computation because the model keeps trying ideas it already knows and paying full-price optimization on them. The fix is surgical: (1) before updating weights, filter to only examples where the model took an action that surprised the current weights—something unexpected. These are the examples that genuinely change what the model will do, because they show a gap between what the model did and what it normally does. (2) For each such example, you do not need expensive optimization; a simpler, cheaper update (one gradient step or a low-rank weight shift) is enough to reinforce that direction. By filtering and using cheaper updates, training runs fewer compute steps but learns as much.

The learning signal formula

First in words:

Updated policy = current policy plus learning rate times gradient on high-signal examples only

Then the compact form:

pi_new = pi_old + alpha * sum_high_signal(gradient_log(pi_old | a_t) * R_t)

Every symbol:

pi_newthe updated model after this training step
pi_oldthe current model before training
alphalearning rate—how big a step to take
sum_high_signalonly add up gradients from examples where the model took an unexpected action
gradient_logdirection that increases the log-probability of the chosen action
a_tthe tool call the model generated
R_twhether it succeeded—reward signal (1 if correct, 0 if wrong)
A tiny worked example
Old model generates 100 tool calls during training: 30 are surprising attempts (high signal), 70 are safe repeats (noise).
Each surprising call that succeeded gets reward 1, each failure gets 0. Suppose 24 succeed, 6 fail.
Standard method: update on all 100. Cost: 100 gradient steps. Accuracy stays the same.
Smart method: update on only the 30 surprising ones (24 successes, 6 failures). Cost: 30 cheap updates. Accuracy is the same because the 70 repeats taught nothing.
Wall-clock speedup: 100 to 30 is a 3.3x reduction in what you actually compute. Model learns the same in much less time.

Filtering to high-signal examples removes noise but keeps all the learning because you still update on every example that teaches something new. Cheaper updates work because one-step methods are enough to learn from a clear signal—expensive optimization is only needed when the signal is weak.

What can go wrong

What can go wrong

Evaluation still depends on the model. Even with a standardized protocol, different models call tools in different styles. A test case that works for one model might not cleanly apply to another, so you have to re-validate on each new model.
Filtering might skip important hard cases. When you keep only high-signal examples (attempts that surprised the model), you might accidentally skip hard edge cases the model rarely tries because those are low-signal by definition. This can leave the model weak on rare cases.
Cheap updates might miss the right amount. Using one step or a simplified weight shift instead of expensive optimization might overshoot (over-learn from a lucky success) or undershoot (fail to fully internalize a hard lesson), because trading precision for speed means you may miss the exact target that full optimization would find.
Done right: standardize the evaluation checklist, monitor edge cases, validate that cheap updates match the slow method on small problems first. Run a sanity check on a known small benchmark before scaling up, and keep a separate eval set to catch any weird overfitting from the accelerated update.
What a runnable demo should prove

What a runnable demo should prove

Build a tiny test: give a language model a task that requires calling a few tools (e.g., lookup a fact, add two numbers, get the weather). Train it using standard RL, measuring wall-clock time and final accuracy. Then train the same model with the paper's method—keep only examples where the model took an unexpected action (to filter noise), and use a cheaper update rule instead of full optimization because strong signals need less expensive computation to learn correctly. Measure accuracy and time again.
