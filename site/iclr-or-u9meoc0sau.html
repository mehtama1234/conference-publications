SceneCOT: Step-by-Step Reasoning in 3D Scenes

A 3D scene reasoner that breaks hard questions into a series of simple steps, each grounded to real objects and positions in the scene.

Paper explainersAll themesComputer Vision

When a model looks at a 3D scene and answers a question like 'How many brown tables are to my right?', it struggles because it tries to solve the whole puzzle at once. SceneCOT changes this by making the model think step-by-step, the way humans do: first figure out which objects are on the right, then check which are tables, then count the brown ones. The key is that each step is anchored to actual objects and their positions — not just abstract reasoning.

Zero assumption version

3D scene questions demand global reasoning but models lack structure

A 3D scene is a jumble: dozens of objects with names, colors, positions, and relationships to each other. When you ask a model a question about it — 'how many red objects are to the left of the blue chair?' — the model must identify objects, track spatial relationships, count, and filter all at once. This is the reasoning part, and it has to happen correctly or the answer is wrong.

A beginner model tries to do all this in one shot: look at the whole scene, weigh every object and position, produce an answer. But these entangled steps confuse the model. It mixes up spatial directions, double-counts, or ignores constraints. The reasoning is a black box — you cannot tell if it checked the color first or the position first.

The problem. Models do not break 3D scene reasoning into steps anchored to real objects, so they make mistakes and their reasoning is invisible.

The algorithm as a flow

What it actually does

Decompose the question

Parse the input query to identify reasoning subtasks: direction, object type, attributes, count.

Step 1: Identify scene region

Use the agent's position and orientation to find which objects lie in the requested direction (right, left, front, back).

Step 2: Filter by object class

Among those objects, keep only the ones matching the object type (table, chair, lamp).

Step 3: Check attributes

Verify that each candidate has the required color or property (brown, shiny, tall).

Step 4: Compute final answer

Count, compare, or rank the remaining objects to produce the answer, with grounding signals tied to each.

What the paper changes

What the paper changes

SceneCOT does not invent new models or learning tricks. Instead, it changes how the model is asked to reason: instead of one big forward pass, the model generates a sequence of interpretable intermediate steps, each one grounded (linked) to actual 3D objects and their spatial properties.

The hidden quantity

Grounding-QA coherence: how well each step stays on target

measured quantity  =  Grounding-QA alignment score

The hidden quantity is grounding-QA coherence: a measure of how tightly each reasoning step is anchored to the actual objects it talks about. If the model says 'Step 1: find brown objects' but then Step 2 mentions green objects, coherence is broken. If Step 1 points to the correct set of objects and Step 2 filters from that set correctly, coherence is high.

SceneCOT measures this by asking: for each step, do the objects the model grounds (points to) match the objects the question actually needs? The paper adds an explicit loss term to the training that rewards coherence — if a step correctly identifies its target objects, training strengthens that step; if a step misgrounds (points to the wrong objects), training nudges it toward the right ones.

Plain reading. Grounding-QA coherence is simply: does each reasoning step point to the right objects for what it is trying to do? If yes, it is coherent. If a step talks about 'brown tables' but points to 'red chairs', coherence is broken.
Paper reading. The paper computes this via the PQ3D metric and adds a grounding loss Lground (cross-entropy) during training to ensure the grounding module (the part that identifies objects) stays aligned with the question requirements at each step.
Why it works

Why step-by-step grounding works

The core mechanism is constraint isolation. A complex 3D question has many constraints tangled together (direction, type, color, count). If the model tries to solve them all in parallel, it mixes up signal — directional cues interfere with color detection, and object identity gets lost in the noise. Step-by-step reasoning isolates each constraint into its own step.

Within each step, a specialized module (a grounding expert) is trained to solve only that one part. Step 1's module learns to identify direction-relevant objects using the agent's position. Step 2's module learns to filter by object type, inheriting the objects Step 1 gave it. Step 3's module learns to check attributes on that smaller set. By the time Step 4 arrives, the hard filtering work is done, and counting is simple.

The grounding loss ensures that each module actually points to the right objects, not vague features. Without it, a module could 'cheat' — learn a shortcut that happens to give the right answer but does not actually ground to the objects (like learning a color bias instead of actually measuring the agent's position and angle). The loss forces honest grounding: if you say 'this object is on the right,' the training verifies it actually is, according to the agent's standing position and which way they face.

The grounding loss

First in words:

Total loss = reasoning loss + lambda times grounding loss

Then the compact form:

L_total = L_reason + lambda * L_ground

Every symbol:

L_reasonloss from whether the final answer is correct
L_groundcross-entropy loss: penalty if grounded objects do not match ground-truth objects at each step
lambdascalar weight controlling how much to care about honest grounding vs. final accuracy
A tiny worked example
Suppose lambda = 0.5, L_reason = 2.0 (incorrect answer), L_ground = 0.4 (Step 1 pointed to wrong objects).
L_total = 2.0 + 0.5 * 0.4 = 2.0 + 0.2 = 2.2.
If instead the model had correct answer (L_reason = 0) but wrong grounding (L_ground = 1.0):
L_total = 0 + 0.5 * 1.0 = 0.5.
Even with a right answer, bad grounding adds 0.5 to the loss, discouraging cheating shortcuts.
The model learns: get the answer right AND ground it honestly, or both losses pull your score down.

The grounding loss keeps each step anchored to real objects; without it, the model can get lucky and answer right while hallucinating its reasoning.

What can go wrong

What can go wrong

Step ordering is wrong. If the decomposition puts the attribute check before the type filter, the model checks color on the full scene instead of on tables only. The training data must encode correct step order, or the model learns a nonsensical sequence.
Grounding loss is too weak. If lambda is too small, the model ignores the grounding loss and returns to cheating: saying the right answer by pattern-matching image statistics, not by actually grounding. Reasoning becomes invisible again.
Multimodal expert modules are not well-trained. Each grounding module (for direction, type, attribute) is initialized with pre-trained weights but fine-tuned during training. If fine-tuning is weak, the modules do not actually learn to ground objects correctly; they stay stuck in their pre-trained behavior.
Done right. Training data contains step-by-step ground-truth traces with correct step order; grounding loss is tuned to encourage both accuracy and coherence; expert modules are jointly optimized. Reasoning is clear, inspectable, and hard to fake.
What a runnable demo should prove

What a runnable demo should prove

Build a small 3D scene with 5-10 objects (chairs, tables, lamps of different colors). Ask the model a question with 3-4 constraints: 'How many brown objects are to the left of the red chair?' Run both a baseline (no steps) and SceneCOT. Collect both the final answer and the grounding trace (which objects were identified at each step). Measure accuracy and grounding coherence.

Accuracy = (correct answers) / (total questions); Coherence = (steps that ground to intended objects) / (total steps)

The demo must show that SceneCOT grounds reasoning to real objects at each step, making reasoning transparent and improving accuracy on hard, multi-constraint questions.
