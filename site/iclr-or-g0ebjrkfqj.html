BoGrape: Bayesian optimization over graphs with shortest-path encoded

To find the best graph structure with expensive measurements, encode the candidate graphs as mathematical constraints and search them systematically instead of guessing randomly.

Paper explainersAll themesOptimization

When you want the best molecule or sensor placement but testing is expensive, Bayesian optimization helps: build a model of what works, then use math to pick the next thing to test, because a smart pick reduces the total tests needed. But existing methods struggle with finding the best graph structure (the connections between nodes). BoGrape solves this by encoding graphs as constraints in an optimization problem, so you can search the space of all connected graphs systematically instead of guessing randomly.

Zero assumption version

Finding the best graph is slow and haphazard

Many real problems are graph problems: designing molecules (which atoms to connect?), placing sensors in a network, arranging supply chains. The goal is to find the graph structure that works best. Testing each candidate is expensive (hours in a lab, money in a trial), so you want to test as few as possible.

Bayesian optimization is a standard trick for expensive search: fit a model to what you have tested, use it to guess where the best graph might be, test that one, and repeat. But there is a catch: existing methods either assume the graph structure is fixed and you are only tweaking the features of its nodes, or they search randomly. Neither lets you systematically explore the space of different graph structures with real constraints built in (like requiring a connected graph, or molecules that are chemically valid).

The bottleneck: No method lets you do Bayesian optimization over the space of all possible graph structures with real constraints, so you fall back to random search or heuristics.

The algorithm as a flow

What it actually does

Build a model of results

Train a Gaussian process (a statistical model that guesses function values and confidence) on the graphs you have tested so far.

Encode candidate graphs as constraints

Each possible graph becomes a set of yes-or-no variables and mathematical equations that describe its structure (connectivity, shortest paths, node labels).

Write an optimization problem

Formulate a mixed-integer program (MIP): maximize the acquisition function (expected gain) over all graphs that satisfy the encoding constraints plus problem-specific constraints (e.g., must be a molecule, must connect nodes A and B).

Solve it with a standard MIP solver

An off-the-shelf solver (like Gurobi) finds the graph that balances exploring uncertain regions and exploiting known good ones.

Test the graph, repeat

Evaluate the winning graph, add the result to your data, retrain the model, and solve the MIP again.

What the paper changes

What the paper changes

The paper changes how you pick the next graph to test. Instead of guessing randomly or using heuristics, it formulates the choice as a mathematical optimization problem you can solve exactly (or very well). This turns graph-space search into a discrete optimization task that commercial solvers are designed to handle.

the object it moves  =  Acquisition function search (from random/heuristic to exact MIP)
The hidden quantity

The hidden quantity: Expected gain from testing a new graph

measured quantity  =  Expected improvement in your best result

Bayesian optimization works by balancing exploration (testing graphs you are unsure about) and exploitation (testing graphs you think will be good). To do this, it scores each candidate graph by a quantity called the acquisition function: roughly, it is the expected gain if you test that graph next. Graphs with higher acquisition scores are more likely to improve your overall best result, because the acquisition function is specifically designed to pick graphs that either look very good according to the model or reduce the most uncertainty—both of which lead to better outcomes faster.

BoGrape estimates this acquisition score for every graph that satisfies the constraints, by using the statistical model (the Gaussian process) to guess both the predicted performance and how uncertain that guess is. A graph gets a high score if the model predicts it could be very good, or if the model is very uncertain (so testing it reduces confusion).

Why it works

Why it works: turning search into a solvable puzzle

The core insight is that the space of all connected graphs can be represented as a set of linear and integer constraints. Specifically, if you think of shortest paths as decision variables (yes, this path of length k appears in the graph or no, it does not), then the rules for a valid connected graph become a system of mathematical equations. Once you have this encoding, you can ask a mixed-integer programming solver: among all graphs satisfying these constraints and the real-world constraints (like chemical validity), which one maximizes the expected gain?

Why does this work? First, it lets you explore systematically: the MIP solver does not guess; it searches the constraint space intelligently. Second, it respects real constraints: you can add equations that forbid invalid graphs or enforce problem-specific requirements (e.g., 'atoms must not be too close'). Third, it reuses graph kernels: the Gaussian process model relies on a shortest-path kernel, which is a standard way to measure similarity between graphs. The acquisition function is then evaluated using the model's predictions and confidence levels. The MIP solver takes the acquisition score for each candidate graph and finds the one that looks most promising.

In other words: instead of asking 'guess which graph to test next,' you ask 'solve this math problem to find it.' A mature optimization engine can solve it better than guessing.

Math after the picture

The optimization problem

First in words:

maximize expected improvement over the set of all connected graphs with binary node features

Then the compact form:

max_{G} EI(G) subject to: G is connected, each node has M binary features, all shortest paths are encoded as decision variables satisfying graph structure equations, problem-specific constraints hold

Every symbol:

Ga candidate graph (adjacency structure + node features)
EI(G)expected improvement from testing graph G, based on the Gaussian process model
Mnumber of binary features per node
shortest-path variablesyes-or-no decisions for each path length k in each graph
graph structure equationsmathematical constraints enforcing connectivity and path consistency (derived from Floyd-Warshall rules)
A tiny worked example
Suppose you have tested 3 molecules and your Gaussian process model predicts: graph G1 has score 0.7 with high confidence (variance 0.05); graph G2 has score 0.65 with high uncertainty (variance 0.3); graph G3 has score 0.6 with high uncertainty (variance 0.4).
Expected improvement EI considers: G1 is good but certain (small gain); G2 is okay but uncertain (medium gain); G3 is poor but very uncertain (could be big gain if true).
The MIP solver evaluates EI for all valid candidate graphs. Say G100 is chemically valid, satisfies all constraints, and has EI=0.25. The solver finds the graph with highest EI, say G_star with EI=0.3.
You test G_star next, measure its actual score, add it to your data, retrain the model, and solve the MIP again.

The acquisition function balances exploiting high-predicted-score graphs and exploring uncertain regions; the MIP solver does this balance globally over the constraint-encoded graph space.

What can go wrong

What can go wrong

The MIP solver is slow on large graphs. Encoding very large graphs (hundreds of nodes) as MIP constraints creates a huge problem that solvers may take too long to solve. Practical use is best on smaller graphs (tens of nodes) or when you can decompose the problem.
Constraints must be carefully formulated. If problem-specific constraints (e.g., chemical validity rules) are wrong or incomplete, the solver may pick graphs that look good mathematically but are invalid in reality. The constraints must truly capture your problem.
The kernel choice matters. BoGrape uses shortest-path graph kernels. If the shortest paths do not capture the important structure of your problem, the Gaussian process model will misguide the solver. The method is not magic; it depends on a good kernel.
Done right: start with small problems. Test the method on small synthetic benchmarks first to verify the encoding and constraints are correct. Verify that the solver actually finds valid graphs. Then move to real problems with realistic constraints and budgets.
What a runnable demo should prove

What a runnable demo should prove

Build a simple graph optimization problem: define a function that maps small graphs to scores (e.g., count the number of edge-disjoint paths, or sum of node features weighted by connectivity). Implement BoGrape and a baseline (random search, or a simple greedy heuristic). Run both for a fixed budget (e.g., 20 function evaluations), and plot the best score found over time. The demo should show BoGrape finding better graphs faster than baselines, because it uses the model to pick high-value candidates instead of guessing, and it should show that the constraints are being respected (e.g., all tested graphs are connected), because the MIP encoding enforces them automatically.
