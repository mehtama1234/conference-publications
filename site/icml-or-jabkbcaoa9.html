Dynamic TMoE: Tracking Shifting Patterns in Time Series

Add and remove expert models as time series patterns shift, steering each forecast to whichever expert learned that regime best.

Paper explainersAll themesTime Series & Sequential

Time series (like stock prices or weather) change their behavior as the world changes. A single model trained once cannot adapt to these shifts. This paper adds a new skill: detect when the patterns shift, grow more experts to handle the new regime, and route each forecast to the expert that knows it best — and the router remembers what patterns worked before.

Zero assumption version

Time series that shift their patterns

In the real world, the rules change. A river's flow in dry season differs from flood season. Stock prices before and after an earnings report behave differently. The pattern the model learned yesterday no longer holds today.

A naive fix: train one big model on all the old data, then freeze it. But when the new regime arrives, the frozen model keeps predicting the old pattern. It cannot adapt because it has no way to measure: am I still in the world I learned, or is this a new world? Once it detects a shift, it has nowhere new to go — it has no fresh expert waiting.

The paper's move: Detect shifts in the pattern, build new experts on the fly to learn the new regime, and use a memory-aware router to steer each forecast to the expert that knows it best.

The algorithm as a flow

What it actually does

Detect a shift

Measure how different the incoming data looks from what the current expert has seen.

Build or reuse an expert

If this regime is new, create a fresh expert model. If this regime matches a past one already learned, wake that expert up.

Store what works

Record which experts handled which regimes well, remember anomalies (rare cases that broke the pattern).

Route with memory

When forecasting, consult the memory to pick the expert that learned this regime before.

Predict

The chosen expert produces the forecast.

What the paper changes

What the method changes

Instead of one static expert pool, the paper changes the experts themselves: their count grows and shrinks as regimes come and go. The router also changes: instead of just scoring each expert on the incoming data point, it now carries memory of which experts won before.

the object it moves  =  expert pool + router memory
The hidden quantity

Distribution shift: the invisible boundary

measured quantity  =  shift magnitude

The core hidden quantity is how far the new incoming data has drifted from the old data. This is not a simple number like 'is it higher or lower' — it is a measure of whether the entire statistical pattern has changed. The paper uses Maximum Mean Discrepancy (MMD), which works like this: pick a random sample from the old regime and a random sample from the new one, compute their average behavior in a high-dimensional space, and see how different those averages are. A large difference means the regime has shifted.

The paper estimates this shift at every time step by comparing the incoming data to each expert's training range. When the shift exceeds a threshold, the model decides the old expert no longer applies and needs a new one.

Why it works

Why dynamic experts and memory routing work

A non-stationary time series is not one problem — it is many problems stitched together. Each regime (sunny season, stormy season, crash, recovery) is a different pattern to learn. A single expert cannot learn all patterns equally well because fitting one regime means moving away from another. By detecting when a regime shift occurs (using MMD) and spawning a new expert at that moment, the model can have one expert per regime.

Each expert learns its regime deeply, without compromise. The router's memory (a recurrent state tracking which regimes have worked) ensures that when the series drifts back to a pattern it has seen before, the router picks the expert that already learned it. The anomaly repository stores rare, unusual datapoints. When an incoming point looks anomalous (not the typical pattern), the router is slower to commit to a single expert — it hedges across experts that have seen similar anomalies. This prevents the model from confidently predicting using an expert that has only ever seen clean data.

Math after the picture

The core equations

First in words:

The shift detection measures the distance between two data distributions using their average representation; when this distance is large, a new expert is added. The forecast is a weighted sum of all experts, where the weight for each expert is set by a router that considers the shift history.

Then the compact form:

shift_t = ||E_old[phi(x)] - E_new[phi(x)]|| ; forecast_t = sum_k w_k(t) * expert_k(x_t) ; w_k(t) = softmax(router(recurrent_state_t, anomaly_memory))[k]

Every symbol:

shift_tdistance measure at time t, quantifying regime change
E_oldaverage behavior of the old regime data
E_newaverage behavior of the new incoming data
phia learned projection function mapping data to a higher space
w_k(t)weight (a number between 0 and 1) assigned to expert k at time t
expert_kthe k-th expert model
x_tthe incoming data point at time t
recurrent_state_tthe router's memory of past patterns, updated each step
anomaly_memorystored unusual points that broke past regimes
softmaxa function that turns any list of numbers into fractions that sum to 1
A tiny worked example
Suppose we have old data from regime A (average behavior = 5.2) and new data (average = 8.9) after projection.
Shift distance: |8.9 - 5.2| = 3.7. If threshold is 2.5, then 3.7 > 2.5, so we trigger: new expert needed.
Next, the router scores expert A (learned regime A, but we are in new regime) = 0.3 and expert B (just learning the new regime) = 0.8.
After softmax: w_A = 0.27, w_B = 0.73. So forecast uses expert B mostly, because it is newer and better fit for this regime.

When the incoming data drifts far from the current expert's training range, MMD detects it, a new expert is born, and the router votes for the new expert until the regime stabilizes.

What can go wrong

What can go wrong

Threshold set too low. Every tiny noise in the data triggers a new expert. The model bloats with dozens of experts learning nearly identical patterns. Memory and compute explode.
Threshold set too high. The model misses genuine regime shifts. It keeps routing to an expert that learned a dead pattern. Forecast error stays high.
Regime repeats but router forgets. If the anomaly memory is too small or erased, when the series drifts back to regime A, the router might not recognize it. It picks a young expert instead of the one that has already mastered A.
Done right. The threshold is tuned on validation data, the anomaly repository is large enough to hold rare patterns, and the router's recurrent state (LSTM or similar) has enough capacity to track a few regimes. Under these conditions, the model detects shifts accurately, builds experts on demand, and routes confidently.
What a runnable demo should prove

What a runnable demo should prove

Build a synthetic time series with three regimes: a linear trend rising gradually, a sine wave oscillating up and down, then the linear trend again. Add small random noise to each. Train on regime 1 only. Then feed all three regimes at test time and log which expert was chosen at each step. Measure forecast error per regime. The demo must show: (1) MMD correctly detects the shift from regime 1 to sine; (2) a new expert is spawned and trained on regime 2; (3) when regime 1 returns, the router picks expert 1 again (not the young expert 2), and error drops back to the original level.

mean_absolute_error_per_regime = average( |forecast - actual| ) for each regime separately

The one thing the demo must make impossible to miss: when the same regime repeats, using the old expert again (via memory) should be noticeably better than using the new expert, because that expert has already spent hundreds of updates learning this exact regime, so it has tuned weights that match the pattern precisely, while a new expert starts from scratch.
