ABME: Auto-Balanced Model Editing for Open-Vocabulary Detection

Instead of retraining a vision model every time you show it a new scene, inject just the new knowledge you need while keeping the old knowledge intact, in any order.

Paper explainersAll themesComputer Vision

Vision models trained once on one set of scenes fail badly when you show them a completely different scene (the new scene is far outside the training data—a distribution shift means the pattern of what you see changed dramatically). The natural fix is to train them again on the new scene, but that forgets what they learned before. This paper uses a surgical technique called model editing to inject new knowledge without breaking the old—and it can handle new scenes in any order without retraining.

Zero assumption version

The retain-versus-adapt trap

A model trained on office scenes learns to spot desks, chairs, and monitors. When you show it forest scenes (trees, rocks, animals), it fails completely—the new scene is too different, called an out-of-distribution shift. You want to teach it the new scene, but here is the trap: if you retrain the model on forest data, it learns the forest perfectly and forgets the office almost entirely. This is called catastrophic forgetting.

Existing continual learning methods (methods that learn continuously from new tasks one after another) try to protect old knowledge by adding penalties during training—like putting weighted brakes on the most important weights. But they are slow, they require you to feed the tasks in a specific order, and they still leak old knowledge while grabbing new knowledge. You are stuck choosing between forgetting the old and failing at the new.

The paper's move. Instead of retraining the whole model, surgically edit just the key-value matrices inside the model to inject new knowledge, then automatically balance how much the edits respect the old knowledge versus the new task—all without retraining.

What the paper changes

What the paper changes

The paper edits the key-value (KV) matrices. In a vision model, the key-value tables are internal lookup structures that the model uses to fetch and compare information when recognizing objects. By tweaking these tables directly instead of retraining the whole model, you inject new knowledge surgically.

the object it moves  =  key-value lookup tables
The hidden quantity

The hidden quantity: edit impact

measured quantity  =  how much the edits change predictions

Model editing works only if you know how much each change damages the old knowledge. The paper measures this as the shift in the model's confidence scores when you change a KV entry. For instance, if changing one lookup table makes the model 30% less sure it is seeing an office desk, that edit has high impact on old knowledge. The paper calls this the automatic balance—a number that says how strongly each edit should be permitted to change the predictions.

To estimate this impact, the paper feeds old-task data and new-task data through the model and measures how much the KV edits would shift the predictions on both. If an edit helps the new task but hurts the old task a lot, the auto-balance dial turns it down because the edit is destructive—the formula assigns it a lower weight, shrinking the actual change you make. If it helps the new task and barely touches the old task, the dial turns it up because the edit is safe—the formula assigns it a higher weight, letting more of the change through. The dial is set automatically by dividing the old-task importance by the total importance (old plus new), which means edits to entries used heavily for old tasks get penalized and edits to entries used mainly for new tasks are allowed—protecting what matters most.

Why it works

Why it works: the automatic balance

If you change a KV entry, the model's predictions shift by different amounts depending on how much that entry is used. The paper computes a weight for each possible edit that measures how much the model relies on it. An entry that is used heavily by both old-task and new-task predictions gets a high weight—so edits to it are penalized. An entry used mostly by new-task predictions gets a lower weight—so edits are allowed. This automatic balance happens in one pass, no retraining.

Because the balance is automatic, you can insert tasks in any order and remove them later. The old-task data lives in the saved KV reference, so if you add a second forest later, the auto-balance remembers how much office knowledge matters and protects it again. You never retrain the model backbone.

The edit and balance formula

First in words:

For each key-value entry, compute the weighted edit that balances old and new knowledge. The weight for entry i is the old-task importance divided by the sum of both old and new importances. The edited entry is the original entry plus a strength factor times the difference between the new KV value and the original.

Then the compact form:

KV_i_new = KV_i_old + alpha * (target_KV_i - KV_i_old) * (I_old_i / (I_old_i + I_new_i))

Every symbol:

KV_i_newthe updated key-value entry
KV_i_oldthe original key-value entry
alphathe edit strength (how much to inject new knowledge)
target_KV_iwhat the KV entry should be to recognize new scenes
I_old_ihow important this entry is to the old task
I_new_ihow important this entry is to the new task
A tiny worked example
KV entry 5: original value 0.50, needs to be 0.62 for forests.
Old task uses it a lot: I_old = 8.0. New task also uses it: I_new = 4.0.
Balance weight = 8.0 / (8.0 + 4.0) = 0.667. The edit is protected by 67%.
alpha = 1.0 (full edit strength). Difference = 0.62 - 0.50 = 0.12.
KV_new = 0.50 + 1.0 * 0.12 * 0.667 = 0.50 + 0.080 = 0.580.
Result: entry moves to 0.58 (57% of the way to the forest target), protecting the office use.

The balance weight is the fraction of the edit that is allowed; high old-task importance means the entry is protected and edits are shrunk.

What can go wrong

What can go wrong

Tasks are very different. If old and new tasks use completely different features (e.g., office indoors vs. outdoor night scenes), the auto-balance may not find a good compromise. Some old knowledge may still leak.
KV tables are a bottleneck. The paper edits only the key-value lookups. If a task requires changes to deeper layers (the core recognition logic), editing KV alone may not be enough.
Too many tasks in sequence. If you insert many tasks one after another, the KV tables gradually accumulate edits and may run out of room to store information for new tasks.
Done right. When tasks have shared visual features (e.g., indoors and outdoors both have people, furniture, and vehicles), the method protects old knowledge while learning new scenes efficiently.
What a runnable demo should prove

What a runnable demo should prove

Build a simple classifier trained on office images (desks, chairs, monitors). Then take forest images and use ABME to inject forest knowledge. Run the model on both office and forest test sets, and measure accuracy on both before and after the edit. The demo should show that editing the key-value tables keeps office accuracy above 75% while raising forest accuracy from near 0% to above 70%, whereas naive retraining drops office accuracy to below 40%. Optionally, reverse the order: train on forest first, then inject office knowledge, and show you get the same high accuracy on both, proving order-agnosticism.

retain_accuracy = (office_acc_before - office_acc_after) / office_acc_before * 100%. adapt_accuracy = forest_acc_after. trade_off_score = retain_accuracy + adapt_accuracy.

A model's knowledge is not spread evenly across all its internal numbers (called parameters—the weights that define what the model knows). By identifying which lookup tables matter most and protecting them during edits, you can add new knowledge without forgetting.
