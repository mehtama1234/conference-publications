Helmsman: Autonomous Synthesis of Federated Learning Systems

LLM agents automatically design and build federated learning systems by emulating how human engineers plan, code, and test.

Paper explainersAll themesAgents & Tool Use

Federated learning trains models on data scattered across many machines without centralizing it — great for privacy, but the engineering is brutal. You need to pick strategies for data imbalance, handle slow or failing machines, tune hyperparameters, and glue it all together. Most teams end up with fragile, one-off solutions. Helmsman lets language models act as a team of engineers: one agent plans, another writes code, and a third tests the result in a sandbox, all by talking to each other.

Zero assumption version

Building federated learning systems is manual and fragile

Federated learning is the idea: your data stays on your phone or server, but many devices train the model together by sharing only the learned updates (the numbers that changed), not the raw data. It fixes privacy and keeps computing spread out.

But the engineering is a nightmare. You must choose which strategies to use: How do you handle data that is wildly different across machines? How do you make sure slow machines do not hold up the whole system? How do you tune the learning rates, batch sizes, number of rounds? These choices interact in subtle ways. A beginner would try one strategy, tune it for one scenario, and hope it works everywhere else — and it breaks.

The result: teams hand-craft custom systems for each problem. These solutions are brittle, expensive to build, and hard to adapt.

In one sentence. Current federated learning systems are hand-built for specific problems and break when constraints or data change.

The algorithm as a flow

What it actually does

Step 1: Human and planner talk

Human says what they need. The planner-agent asks clarifying questions and writes a research plan.

Step 2: Coder reads the plan

A code-generating agent reads the plan and produces working federated learning code.

Step 3: Tester runs it

An evaluator-agent runs the code in a safe sandbox (not on real data) and collects accuracy scores.

Step 4: Evaluator reports back

The evaluator shows what worked, what failed, and which hyperparameters or strategies look promising.

Step 5: Agents refine together

Agents read the feedback and loop: the planner revises the plan, the coder rewrites parts, tester measures again.

What the paper changes

The one thing it changes

The paper replaces hand-written federated learning code and manually-tuned hyperparameters with code that agents write and refine automatically in a closed loop.

the object it moves  =  design and code of federated learning systems
The hidden quantity

The hidden quantity: design quality

measured quantity  =  design quality (handles all scenarios)

The paper measures how well the auto-generated system handles real challenges: does it work when data is imbalanced? Can it stay fast when some devices are slow? Does the chosen strategy work on new scenarios that were not the focus? A good design works smoothly everywhere; a bad one breaks on some cases.

Helmsman estimates design quality by running the generated code against 16 diverse test cases (the new AgentFL-Bench) and measuring accuracy, fairness, and speed under each scenario. A design that stays stable across all 16 scenarios has high design quality.

Why it works

Why it works: agents bootstrap engineering through talk

Designing federated learning by hand fails because the designer must hold in their head: the data properties (which machines have what), the hardware constraints (bandwidth, battery, latency), the algorithm choices (averaging method, how to compress updates, which examples to sample), and how they all interact. No human is good at that much simultaneous complexity.

Helmsman works because it distributes that load across three agents who talk to each other: the planner-agent internalizes the requirements and constraints and writes a crisp research plan (not code yet, just strategy). The coder-agent reads that plan and turns it into working code — a much simpler task because the plan is already coherent. The tester-agent runs the code and measures it, so the planner can see what actually happened, not guess. Then they loop: the planner sees the test results and refines the strategy, the coder rewrites to match, and the tester measures the new version. Each agent solves a narrow, well-posed problem, so they are more likely to succeed. The loop catches failures early.

Why this works: agents can reason about software and experiment results the way humans do, so they can collaborate like an engineering team. By structuring the work into planning, then coding, then testing, then refining, Helmsman offloads the hard cognitive work (hold all the constraints and choices in your head) to language models, which are good at reading, understanding intent, and writing code.

Math after the picture

The hidden equation: design quality across scenarios

First in words:

design quality is the average accuracy across all test scenarios, penalized if any scenario fails badly

Then the compact form:

quality = mean(accuracy_i for i in all_scenarios) - beta * max(0, threshold - min(accuracy_i))

Every symbol:

accuracy_ithe accuracy the designed system achieves on test scenario i
thresholdthe minimum acceptable accuracy, say 80 percent
betahow much to penalize one bad scenario (the severity of failure in any one case)
qualitythe overall design score the agents try to maximize
A tiny worked example
Scenario 1 (imbalanced): 92% accuracy
Scenario 2 (slow devices): 88% accuracy
Scenario 3 (high noise): 75% accuracy (fails threshold of 80%)
Mean accuracy: (92 + 88 + 75) / 3 = 85%
Penalty for failure: beta * (80 - 75) = 1.0 * 5 = 5 points
Final quality: 85 - 5 = 80
A design that passes all thresholds has no penalty, so agents refine to avoid weak scenarios.

Agents see low quality scores when even one scenario fails, so they naturally refine the design to handle all cases, not just the easy ones.

What can go wrong

What can go wrong

Agents get stuck in local optima. If the planner proposes a weak strategy early, the coder and tester may not escape it. The loop refines within that strategy but never tries fundamentally different approaches.
Agents hallucinate code that looks right but has bugs. Language models can write convincing-looking code with subtle logic errors. The tester only catches failures if the bug causes accuracy to drop; logical errors that do not affect the final score may hide.
The benchmark (AgentFL-Bench) may not cover real deployment scenarios. A system optimized for 16 test cases may still fail on scenario 17. The hidden design quality is only as good as the test suite.
Done right: agents catch failures quickly. Because the loop is tight and the tester reports results immediately, agents can refine dozens of times in minutes. Failures surface early before they ship.
What a runnable demo should prove

What a runnable demo should prove

Build a minimal federated learning task: say, 5 machines with imbalanced data (some have 10 examples, others have 1000), and a simple classifier to train. Run Helmsman and a hand-crafted baseline in parallel. The demo should show: (1) both systems converge to reasonable accuracy, (2) Helmsman's system keeps performance stable if you change the imbalance or add a slow machine to the federation, and (3) the hand-crafted baseline degrades sharply under the same changes.

robustness = (accuracy_helmsman_perturbed - accuracy_baseline_perturbed) / accuracy_baseline_original

The critical observation the demo must show: when the world changes, the Helmsman-generated system adapts gracefully because agents designed for multiple scenarios, but the hand-built system breaks because it was tuned for one.
