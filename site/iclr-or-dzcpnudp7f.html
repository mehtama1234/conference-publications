MoCa: Modeling Object Consistency for 3D Camera Control in Video Generation

To keep objects looking the same when controlling the camera view in video generation, MoCa encodes camera trajectories geometrically, anchors object identity through shared image-language features, and separates what moves because of the camera from what moves because of the object.

Paper explainersAll themesGenerative Models & Diffusion

Video generation models can now create realistic scenes, but controlling the camera view—rotating, panning, zooming—is hard: the object might disappear, look blurry, or shift position incorrectly. Existing methods either add camera controls awkwardly (causing visual glitches) or require explicit 3D scene models (which do not work on new scenes). MoCa solves this by learning to keep three things consistent: how the object looks from each new view, what color and texture it has, and how it moves independent of the camera.

Why camera control breaks video generation

When you ask a video model to generate frames with a moving camera, the generated frames may have the same object look different from each angle (one frame has a red car, the next has a blue car), or the object disappears as the camera pans. A naive approach is to feed the camera instructions directly into the generation model, but that does not work: video diffusion models (the kind that gradually sharpen noise into video) operate in pixel space, where they have no built-in understanding of what a camera is or how a 3D object looks from different angles. Adding camera signals this way creates visual artifacts.

The other approach is to build an explicit 3D model of the scene—a full map of where every object sits in 3D space—and use that to guide the generation. But this requires 3D supervision, which is expensive to collect. Worse, a model trained this way only works well on scenes it saw during training. When you ask it to generate something new, it fails.

In one sentence. MoCa keeps objects consistent by learning what information in camera movement and vision-language features uniquely determines how an object looks from any angle, without building a full 3D scene map.

What the paper changes

What the paper changes

MoCa modifies how the video generation model stores and uses information about camera movement and object identity. Instead of injecting raw camera signals into the pixel generation step (which causes glitches), it learns a separate geometric code for camera trajectories and a shared vision-language representation of objects. The model then uses these to guide generation without building an explicit 3D scene map.

the object it moves  =  camera trajectory encoding and object identity anchor
The hidden quantity

The hidden quantity: object motion decoupling score

measured quantity  =  how much of the observed pixel motion is due to the camera versus the object itself

When you see pixels change between two frames, you cannot tell if the change is because the camera moved or the object moved. If the camera pans right and the object stays still, pixels move right. If the camera stays still and the object moves right, pixels move right. MoCa learns to estimate this hidden quantity: for each pixel change, how much came from the camera, and how much from real object motion. This is not a number the paper measures explicitly, but it is what the motion disentanglement mechanism implicitly solves.

The paper trains the model to separate these two by forcing the predicted camera effect to match the known camera trajectory. If the model predicts that 80 percent of the pixel motion is due to camera movement, and the true camera trajectory says 80 percent should be, the prediction is good. Over time, the model learns to estimate this separation correctly, which means it understands object motion independently.

Why it works

Why this approach keeps objects consistent

A smooth camera movement through 3D space has a mathematical property: when you look at the same object from nearby viewpoints, the object's appearance changes smoothly and predictably. A pixel on the object moves continuously as the camera moves. This smoothness is the key. MoCa exploits this by learning a representation of the camera path that preserves this geometric smoothness. Plücker embedding is a mathematical tool that represents lines (the camera rays looking at the scene) in a space where smooth camera motion stays smooth. This means the model can learn to predict how the object should look at nearby camera positions by interpolating, not guessing.

Second, object identity must be anchored. If the model only saw pixel-level information, it could not tell a red object from a blue object, or know which pixels belong to the same object across frames. MoCa uses vision-language features—learned representations that describe images in language-like terms (this is a car, it is red, it has wheels). These features are shared across many images and models, so they encode stable properties of the object that persist across views. By conditioning on these features, the model learns that the red car is always red, even as the camera rotates around it.

Third, motion separation ensures that when the camera moves, the model does not mistake pixel shifts caused by the camera for real object motion. The model learns to predict what pixels should move if only the camera moved and the object stayed frozen. Then it subtracts this prediction from the observed motion, leaving behind the real object dynamics. This separation works because the true camera trajectory is known during training—the model can compare what pixel motion it predicted should happen from camera motion alone against what actually happened, and when there is a gap, it knows that gap is the real object motion. Repeated corrections drive the estimate toward accuracy.

Math after the picture

The disentanglement equation

First in words:

Motion separation loss equals observed pixel motion minus (predicted camera-caused motion) compared against known object motion. The model adjusts its camera effect prediction to minimize this error.

Then the compact form:

L_motion = || optical_flow_observed - (flow_camera_predicted + flow_object_predicted) ||^2 + lambda * || flow_camera_predicted - flow_camera_from_trajectory ||^2

Every symbol:

optical_flow_observedthe actual pixel motion seen in two consecutive frames
flow_camera_predictedthe model's estimate of how pixels moved because of camera motion
flow_object_predictedthe model's estimate of how pixels moved because of object motion
flow_camera_from_trajectorythe true camera motion converted to expected pixel shifts (ground truth)
lambdaweight controlling how strongly the model must match the known camera trajectory
A tiny worked example
Suppose a pixel moves 4 units right between frames. Camera should contribute 3 units (we know the camera panned right 3 units). Object should contribute 1 unit (moving right on its own).
Model guesses: camera 3.1 units, object 0.8 units. Total 3.9 (close to 4, good).
But the second term checks: |3.1 - 3| = 0.1 error on camera. Squared: 0.01. Multiplied by lambda=100: penalty of 1.0.
If the model had guessed camera 2.0, object 2.0: total still 4.0, but |2.0 - 3| = 1.0 error, squared = 1.0, multiplied by 100 = penalty of 100. So the model learns to match the true camera contribution because that loss is cheaper.

The second term (the lambda term) acts as a check: it forces the model's camera prediction to match the real camera trajectory, so the object motion estimate becomes the residual and is forced to be correct.

What can go wrong

What can go wrong

Ambiguous camera + object motion. If the object moves in a way that exactly mimics camera motion (e.g., the object rotates while the camera also rotates), the disentanglement may fail because both effects look identical in pixels. The model needs the camera trajectory to be known and distinct from object motion.
Camera paths unlike training data. If the camera moves in a way the training data did not cover (e.g., a very fast zoom), the Plücker encoding may not smooth correctly, and generated frames can become blurry or ghosted.
Vision-language feature limitation. If the object has very fine details or subtle textures that the vision-language model does not capture well, those details may not transfer across frames, appearing as texture flickering.
Done right. With known camera trajectories, distinct object motion, and well-represented object features, MoCa maintains smooth object appearance and precise camera control.
