FormAct: Agentic Source Editing for Rich-Format Document Generation

Generate polished documents by letting one agent edit source files and another agent review rendered pages across several repair rounds.

Paper explainersAll themesAgents & Tool Use

Producing a polished document is more than producing text. The system has to manage layout, structure, and formatting errors that only become obvious after rendering the page. FormAct addresses this by working on the source representation directly and by separating editing from review. One agent changes the HTML source with tools, while another agent inspects the rendered result and points out what still needs to change. The loop helps because visual defects often cannot be judged from source text alone.

Why document generation needs more than one pass of text output

A professional document has structure, spacing, headings, and visual consistency. A single direct generation step often leaves broken layout or malformed source because the model cannot fully judge the final appearance before rendering.

This creates a two-view problem. The editor needs to reason about source code, while the reviewer needs to reason about the rendered page. If one system handles both views poorly, defects can persist because the source may look acceptable while the page still looks wrong.

The paper's move in one sentence. Treat document generation as iterative source editing with tools and rendered-page review so that each round can fix issues exposed by the previous render.

The algorithm as a flow

What it actually does

Represent the document as source

Work on HTML rather than raw final text so that structure and formatting can be edited directly.

Use editing tools

Give the editor a source-aware editor and a template retriever because those tools make structural changes easier to execute correctly.

Render the current page

Turn the source into a visible page so that actual appearance can be inspected.

Review the rendered result

Let a second agent critique visible defects because many layout problems only appear after rendering.

Compress old context after edits

Shorten the working history after each edit trigger so that long repair sessions stay manageable.

What the paper changes

What the paper changes

The paper changes document generation from one-shot writing into a source-and-review loop. It makes rendering part of the reasoning process because the document should be judged in the same form that readers will see.

The hidden quantity

The hidden quantity

measured quantity  =  the gap between the current source and the page the user actually wants

The key hidden quantity is the remaining mismatch between the present source and the desired final document. The model cannot read that mismatch directly from the request after many edit rounds because the important errors are distributed across source structure and rendered appearance.

The reviewer exposes that hidden gap by inspecting the rendered page. A render may reveal broken spacing, weak hierarchy, or missing sections, and those observations tell the editor which part of the source still needs to change.

Why it works

Why this works: source edits need rendered feedback

Direct document generation often fails because the model commits to a large output before it has evidence about how that output renders. Once the page is rendered, however, visible defects can be named and repaired one by one.

FormAct exploits that structure by separating roles. The editor focuses on changing source correctly with tools, while the reviewer focuses on judging the rendered page. This division helps because each role gets feedback in the form it can use best, and the repeated loop steadily reduces page defects.

Choose edits that improve the rendered page

First in words:

A simple summary is to score each edit round by combining source correctness and rendered-page quality. The system keeps refining while the score can still increase.

Then the compact form:

page_score(round) = source_quality(round) + gamma * render_quality(round)

Every symbol:

page_score(round)overall quality of one edit-review round
source_quality(round)how correct and well-structured the HTML source is after the edit
render_quality(round)how acceptable the visible rendered page is after review
gammaweight on the rendered-page part of the score
A tiny worked example
Round A fixes the HTML tags but leaves poor spacing in the rendered page.
Its source quality is 8 and its render quality is 3, so with gamma equal to 1 the total score is 11.
Round B keeps the source correct and also fixes the spacing.
Its source quality is 8 and its render quality is 6, so the total score is 14.
The later round is better because the visible page improved while source correctness was preserved.

The paper uses a fuller system than this equation, but the score captures the main principle that source edits should be judged by rendered results too.

What can go wrong

What can go wrong

A reviewer can point to symptoms but miss the source cause. The rendered page may reveal that something is wrong without revealing which source block caused it, so repair rounds can still wander.
Context compression can hide earlier intent. If the system shortens history too aggressively, later edits may forget why a section was written in a certain way because the original constraint is no longer visible.
Template retrieval can steer style too strongly. A fetched template may dominate the output and weaken task-specific structure because the editor copies more than it should.
Done right. The framework is useful because it treats document quality as something that emerges through edit and review, not as something guaranteed by the first draft.
What a runnable demo should prove

What a runnable demo should prove

Build a small document generator that writes HTML for a report, renders it in a browser, and then sends a screenshot plus the source to a reviewer module. Let the reviewer request repairs such as heading hierarchy fixes, spacing fixes, or missing-section fixes.

The demo should track whether each review round reduces visible defects. It should show that the loop improves output because the system can act on source while judging the result in rendered form.

repair_gain = defect_count_start - defect_count_end ; review_hit_rate = accepted_review_fixes / total_review_fixes

The point is to make visible why rendered review changes the quality of source-based document generation.
