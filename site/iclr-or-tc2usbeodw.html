VLM4VLA: Revisiting Vision-Language-Models in Vision-Language-Action Models

A robot learns control better when it tunes the vision part of a language model to see robot scenes, not just answer questions about pictures.

Paper explainersAll themesRobotics & Control

Vision-Language models pretrained on the internet excel at understanding images and answering questions about them. When researchers plug these models into robot arms to control them, they assume the vision understanding transfers directly. This paper tests whether it does—and finds a big surprise: the vision part stays stuck on question-answering skills and must be retrained on robot tasks to work well at control.

Zero assumption version

The vision mismatch nobody thought to measure

Today's image-understanding models are trained on billions of photos from the internet paired with text captions and questions. They learn to spot visual patterns that matter for language tasks: a cat's pose, a person's emotion, text in a photo. A robot arm, by contrast, needs to see very different things: the exact 3D position of an object to grasp, the slight angle of a surface to slide across, how friction and gravity will make things move.

When researchers take a language-trained model and add a small control head (the part that says go left, grip harder), they assume the vision part still works well. The lead-pipe test is simple: freeze the vision module and only train the new control bits. If it works, the vision part is already good for robots. If it fails, there is a gap.

The paper's move in one sentence: Test whether the vision part of language models must be retrained for robot tasks, by turning it on and off during training and measuring robot success.

The algorithm as a flow

What it actually does

Build a minimal robot-control model

Plug a language-model's vision and language layers into a tiny new control head. Keep this simple to test fairly.

Freeze the vision: does it work?

Lock the vision module (do not let it change) and train only the control head. Measure robot success on grasping, pushing, etc.

Unfreeze the vision: does it help?

Now let the vision module retrain on robot scenes while training the control head. Measure again on the same tasks.

Compare vision gains to language gains

Test whether retraining the language module helps as much as retraining vision by freezing and unfreezing each separately. Language barely matters because the task instruction is simple; vision is critical because it must extract the visual cues the robot needs.

Measure across many robots and tasks

Run on three major benchmarks (hundreds of manipulation tasks) to confirm the vision gap is real everywhere.

What the paper changes

What the paper changes

The paper changes whether the vision module (the part that converts raw pixels into numbers the model understands) is allowed to retrain during robot-task learning. Freezing it means the internet-trained vision never changes. Unfreezing it means the vision retrains to spot whatever the robot control task demands.

The hidden quantity

Domain gap: the hidden mismatch

measured quantity  =  domain gap between vision pretraining and control

A domain gap is the difference between what a model was trained to see and what it actually needs to see to do a new job well. In this case, the vision part was trained on internet photos to answer questions like 'what is the color of the person's shirt?' But robot control asks different questions: 'what is the 3D depth and exact placement of that object?' The vision gap can be measured by the jump in robot performance when the vision module is unfrozen: if frozen vision gives 28% success and unfrozen gives 56%, the gap cost the model 28 percentage points.

The paper estimates the gap by directly comparing: locked vision versus free vision on the same robot task with the same control head. The size of the jump tells you how misaligned the pretrained vision was.

Why it works

Why retraining the vision module fixes the gap

When the vision module is frozen, it outputs the same features (numbers representing the image) for every robot task, because it never changes. Those features were built to highlight things that matter for language: the outline of a cup, the color of clothing, readable text. A robot-control task does not care about those things. It cares about depth, solidity, exact position, and stability. The control head (the tiny new layer) tries to predict the right action from the wrong features. It is like being handed a photograph of a kitchen that shows only colors and text, then trying to predict the exact position of a cup by touch alone. You cannot do it.

When the vision module is unfrozen, it can retrain during robot learning. As the robot fails at grasps and pushes, error signals flow backward through the network (gradient signals tell each part which direction to nudge its numbers to shrink the error). These signals reach the vision module and steer it: emphasize the visual features that led to success, suppress the ones that led to failure. The vision module gradually shifts its features from language-relevant ones (color, text) to control-relevant ones (depth, solidity, contact point). The control head now receives useful features and learns to steer the robot arm correctly. Retraining the vision module is faster and better than training from scratch because the module already has general image-understanding skills; it just needs to reweight which visual cues matter most.

The loss function that drives retraining

First in words:

action_loss plus (if frozen) zero vision updates, equals total training loss; if unfrozen, same loss flows backward to change vision features

Then the compact form:

L_total = Huber(predicted_action - true_action) if frozen_vision=True then grad_vision=0 else grad_vision flows freely

Every symbol:

predicted_actionrobot arm movement predicted by the model (joint angles or end-effector position)
true_actionthe action a human expert took in that scene
Huber(error)a loss function that penalizes big mistakes softly (does not blow up on outliers)
grad_visionthe direction and magnitude to change the vision module to shrink the action error
frozen_vision=Truea flag: if True, vision module does not receive gradient updates
A tiny worked example
Scene: image shows a red cube at position (10, 5, 20) in 3D space. Expert grasps above it.
Frozen vision: encoder outputs 1000-number feature vector optimized for QA. Control head predicts grasp at (8, 4, 15). Error = 5 units. Loss = Huber(5) = 5.
Gradient flows to control head only. Vision vector stays unchanged (frozen). Control head learns small correction.
Unfrozen vision: same scene. Vision module retrains to emphasize 3D-depth features. Outputs new 1000-number vector highlighting the (10,5,20) position. Control head now predicts (9.9, 5.1, 20.2). Error = 0.3 units. Loss = Huber(0.3) = 0.3.
Gradient flows back and reweights the vision module: crank up the depth-sensing features, mute the color features. Vision learns to show the control head what it actually needs.

The same loss function drives learning, but only when the vision module is unfrozen can it receive the gradient signal and change its features.

What can go wrong

What can go wrong

Auxiliary task confusion. Fine-tuning the vision module on extra robot tasks like 'predict object depth' or 'answer where-is questions about robot scenes' does not guarantee better control. Sometimes it hurts because these auxiliary tasks emphasize different visual cues than the control task: depth prediction needs high-level structure, but grip success needs low-level contact and friction details. The vision module cannot optimize for both equally, so training on the wrong auxiliary task can suppress the control-relevant features.
Overfitting to a single robot. If you retrain the vision module only on one robot arm, one camera angle, one gripper style, the features it learns may be too specific. When the robot morphs or the camera moves, performance collapses. The vision module must see enough variety to learn general embodied visual principles.
Retraining the language part is wasteful. The language module (which processes the task instruction) barely benefits from retraining. Updating it costs compute but adds almost no gain in robot success. Freeze it and save the training time.
Done right: vision unfrozen, language frozen, clean diverse data. Retrain the vision module on a broad set of robot manipulation tasks (grasping, pushing, rearranging) across multiple robots and camera angles. Lock the language module. Train on clean target actions (human expert trajectories). Success compounds.
What a runnable demo should prove

What a runnable demo should prove

Build a robot task with 50 test scenes: objects in random positions and poses, multiple gripper types, varied lighting. Train two models side by side on the same 500 example trajectories. Model A: freeze the vision encoder from a pretrained language model; train only the control head. Model B: unfreeze the vision encoder; retrain everything. Test both on the 50 unseen scenes. The demo should show Model B succeeding at 50+ grasps and Model A failing at ~25.

success_rate = (grasps_that_grip_firmly and reach_target) / total_test_grasps × 100%

The demo makes it impossible to miss: the language model's vision can learn to see for robots, but only if you let it retrain. Frozen vision fails because it is looking for the wrong patterns.
