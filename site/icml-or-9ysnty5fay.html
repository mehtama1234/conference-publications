One Model to Translate Them All: Universal Feature Translation

Use a shared code space and expert mixing to translate features between any pair of robots without retraining.

The scalability wall in multi-robot fusion

When multiple robots work together, they can be smarter if they share what they sense. This is called collaborative perception. But robots have different hardware — one might have a camera, another a lidar (laser scanner), another radar. Each sensor type produces features (the internal numbers the robot extracts) in its own format.

Today's solution is to train a separate translator for each robot-to-robot pair — if you add a new robot with a new sensor, you retrain from scratch. Retraining is slow, data-hungry, and often impossible in the real world because manufacturers won't share their raw data or let you modify their models.

The core problem: You need a single model that can instantly translate features for any robot pair, without seeing new training data or retraining at all.

The algorithm as a flow

What it actually does

Stage 1: Pretrain the modality-intrinsic encoder

Train an encoder to extract a code from each robot's intermediate features, pulling codes from the same robot type close together and pushing apart codes from different robot types.

Stage 2: Pretrain expert translators and the router

Build a bank of translator experts (each good at one kind of translation), train the router to predict which experts to blend for any modality pair, and learn how much weight each expert gets.

Extract codes from new robots

When a new robot pair arrives, run their features through the frozen encoder to get codes — no new training needed.

Router predicts the blend recipe

The router sees the gap between the new codes and outputs mixing coefficients for the pre-trained experts.

Instantiate the translator and translate

Blend the expert translators according to the recipe and immediately translate features for the new robot pair.

What the paper changes

The one thing this paper changes

Instead of training a custom translator for each new robot-to-robot mapping, UniTrans generates a translator on the fly by mixing a pre-trained set of expert translators, choosing the mix based on codes extracted from the two robots' features.

The hidden quantity

The hidden code in modality space

measured quantity  =  intrinsic code

An intrinsic code is a short list of numbers extracted from a robot's feature data. It captures what is specific to that robot's hardware (camera, lidar, etc.) while ignoring the scene content being viewed. The code is essentially a tag that says: this is camera data, or this is lidar data.

UniTrans learns to extract this code using a contrastive training objective that pulls codes from the same robot type into the same region and pushes codes from different robot types apart. The paper measures whether the code is useful by checking if it can be used to predict the robot's type and if new robot pairs map to consistent regions without retraining.

Why it works

Why it works: two sources of zero-shot ability

UniTrans works because of two insights learned during pretraining. First, the intrinsic encoder learns to extract a stable code for each robot type — even a new robot of the same type will be encoded to the same region, so the code generalizes without retraining. Second, the router learns a mapping regularity: it sees many modality pairs during pretraining and learns a pattern for how to mix experts based on the gap between codes. When a new pair arrives, the router recognizes the code gap as similar to patterns it has seen and predicts the right blend.

The experts themselves are reusable feature translators pretrained on diverse modality pairs. During pretraining, the router learns which experts are good at which gaps. At test time, given an unseen modality pair, the router outputs mixing coefficients — weights saying how much of each expert to use. Blending the experts according to these weights produces a translator tailored to the new pair instantly.

The mixing equation

First in words:

The router outputs a mixing weight for each expert based on the gap between codes from the two robots. Each expert translator is a matrix of learned parameters. The final translator is the sum of each expert weighted by its mixing coefficient.

Then the compact form:

Translator = sum_k (alpha_k * Expert_k)

Every symbol:

Translatorthe final feature translator for this modality pair
alpha_kthe mixing coefficient for expert k, predicted by the router
Expert_kthe k-th pre-trained expert translator matrix
sum_kadd up contributions from all K experts
Tiny worked example with 3 experts
Expert 1 learned to translate from camera to lidar during pretraining.
Expert 2 learned to translate from camera to radar.
Expert 3 learned to translate from thermal to any modality.
New pair: camera to hybrid (camera + lidar). Router predicts coefficients: alpha_1=0.6, alpha_2=0.2, alpha_3=0.2.
Final Translator = 0.6 * Expert_1 + 0.2 * Expert_2 + 0.2 * Expert_3.
This blended translator is camera→hybrid specialized because Expert_1 was best at camera work; Expert_2 adds a touch of camera→radar knowledge; Expert_3 adds generalist behavior.

The mixing weight for each expert comes from the router network, which predicts it based on the intrinsic codes from both robots.

What can go wrong

What can go wrong

New modality type never seen in pretraining. If a robot uses a completely new sensor type not represented in the pretraining modality bank, the encoder may place its code in an unfamiliar region. The router has not learned how to mix experts for that code gap. Performance will degrade.
Pretraining did not span enough expert pairs. If the expert translators were trained on only a narrow set of modality pairs (e.g., only camera-to-lidar), the router learns a narrow pattern. It cannot extrapolate to modality pairs that are very different from what it saw during pretraining.
Router under-trained or imbalanced. If the router was not given enough diverse routing examples during pretraining, or if the load-balancing loss was weak, the router may over-rely on a few experts. Unseen pairs may then match to incorrect mixes.
Done right: diverse pretraining. Pretraining the encoder on many modality types and the experts on a varied set of modality pairs teaches the router to see patterns in the code gaps. When an unseen pair arrives, the router recognizes its code gap as similar to something it trained on and predicts mixing weights that work, because the underlying mapping pattern is consistent.
What a runnable demo should prove

What a runnable demo should prove

Build a small collaborative perception simulator with three pre-trained modality types (camera, lidar, radar) and their experts learned during a mock pretraining phase. Then introduce a new fourth robot type (e.g. thermal) at test time. Show that UniTrans instantiates a translator for camera-to-thermal and radar-to-thermal and achieves reasonable translation accuracy without any retraining. Compare against a baseline that requires full retraining for the new type.

zero_shot_acc = (accuracy on new modality pair) / (accuracy on seen pairs), should be >= 0.85

The demo must show that a completely new robot type can be fused with the rest of the team immediately, without retraining or new data.
