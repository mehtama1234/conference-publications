Bayesian Evidence-Driven Prototype Evolution for Federated Domain Adaptation

FedPTE lets the shared class representatives split, merge, or stay put during federated training so the global model can track how class structure differs across clients.

Paper explainersAll themesOther

Federated learning trains one shared model across many clients without moving raw data off each client. That setup breaks down when clients come from different domains, because the same class can occupy different regions of feature space on different clients. Many federated methods summarize each class with one prototype, which is just a representative point for that class. The trouble is that one fixed prototype per class assumes the class has one stable shape. FedPTE drops that assumption. It lets the server examine the cloud of client prototypes, decide whether one class really contains several sub-groups, and revise the topology during training. That matters because alignment improves only when the shared summary matches the actual class structure seen across domains.

Zero assumption version

Why one class summary is often wrong in federated adaptation

In federated domain adaptation, each client sees its own version of the data. A hospital may have one scanner, another hospital a different scanner. One camera network may see daylight roads while another sees night scenes. If all clients share labels but their inputs are shifted, the same class does not gather into the same shape everywhere.

Prototype-based methods try to solve this by keeping one representative point for each class and pulling client features toward that point. That helps when each class forms one tight group. It fails when a class naturally breaks into several sub-groups, because forcing all of them toward one center erases real structure. The server then averages together incompatible client summaries, and the shared model loses both class separation and domain agreement.

The core mismatch. A fixed number of class prototypes assumes the semantic structure is fixed, but cross-domain federated data often changes shape during training and differs across clients.

The algorithm as a flow

What it actually does

Collect class representatives from clients

Each client sends prototype summaries rather than raw examples, so privacy is preserved while the server still sees the coarse class structure.

Fit a flexible mixture on the server

For one class, the server tests whether the received prototypes are better explained by one group or several groups, because that decides whether one shared center is enough or whether distinct sub-groups need separate representative units.

Use evidence to revise the topology

A split is accepted only when the data gives enough statistical support, because otherwise the method would chase noise.

Apply a stability constraint

The method resists abrupt changes across rounds, so temporary noise does not cause the class structure to jump back and forth.

Train clients with topology-aware contrastive loss

Clients pull features toward the right representative unit and push apart features assigned to different units, which improves both class separation and cross-domain agreement because same-mode examples stop being averaged together with incompatible modes.

What the paper changes

What the paper changes

The paper changes the object being shared by the federation. Instead of sharing one fixed prototype per class, it shares an evolving prototype topology whose size and grouping can change when the evidence says the class structure has changed.

the object it moves  =  the server-side class topology
The hidden quantity

How many representative units a class really needs

measured quantity  =  adaptive prototype count per class

The hidden quantity is not just where a class center sits. It is how many representative units that class needs at the current stage of training. If one class contains several stable sub-groups, then one center is too crude. If the class really is compact, extra units only add noise.

FedPTE estimates this quantity from the prototypes sent by clients. The server asks whether adding or removing a unit increases the evidence for the observed prototypes. That question matters because the right topology balances two competing errors: too few units mix together distinct modes, while too many units overfit random variation from a small number of clients.

Why it works

Why evidence-driven topology changes help

The method works in two linked stages. First, the server collects prototype summaries for each class from all clients and fits a Bayesian Gaussian mixture model, which means a probabilistic model that can represent one class with several Gaussian groups and can ignore unused groups when the data does not support them. This gives the server a way to ask whether the prototypes look like one coherent cluster or several separate ones.

Second, the server compares candidate topologies with marginal likelihood ratios. In plain terms, it checks whether the observed prototypes are more plausible under a split or merge. A split is useful only when it explains the data better after accounting for model complexity, because otherwise every noisy wiggle would create a new unit. That is why the evidence test matters: it permits structural change without turning the system into an unstable cluster counter.

Once the topology is updated, clients train with a topology-aware contrastive objective. Contrastive means the loss pulls matching points together and pushes mismatched points apart. Here the matching rule is no longer 'same class always shares one center.' It becomes 'same class points should align with the correct representative unit.' This matters because two domains may contain the same label but with different local modes. The revised topology gives clients a target that preserves those modes while still aligning related groups across domains.

Math after the picture

When a topology change is accepted

First in words:

The server compares the evidence for two candidate topologies. If the data is more plausible under the new topology by a large enough margin, the split or merge is accepted.

Then the compact form:

accept new topology if log p(prototypes | T_new) - log p(prototypes | T_old) > tau

Every symbol:

p(prototypes | T_new)how plausible the client prototypes are under the proposed topology
p(prototypes | T_old)how plausible the same prototypes are under the current topology
logturns multiplication of probabilities into addition so the comparison is numerically stable
taua threshold that prevents tiny noisy gains from triggering a structural change
A tiny worked example
Suppose one class currently has one representative unit.
The current topology gives log evidence of -120 for the received prototypes.
A proposed split into two units gives log evidence of -111.
The gain is 9 because -111 minus -120 equals 9.
If the threshold is 5, the split is accepted because the data supports the extra unit strongly enough.
If the gain were only 2, the split would be rejected because the improvement could be noise rather than real structure.

The update rule accepts more structure only when it explains the prototypes enough better to justify the added complexity, because otherwise the server would add units for random variation rather than for stable sub-groups.

What can go wrong

What can go wrong

Too little prototype evidence. If clients send very few reliable prototypes, the server cannot tell whether a class truly has several sub-groups, because random variation can look like real structure.
Over-splitting can fragment a class. If the acceptance threshold is too loose, the method may create extra units that track noise. Client training then pushes same-class points toward different targets for no real reason.
Over-stability can freeze the wrong structure. If the stability constraint is too strong, a real topology change may arrive but fail to register, so the model stays locked to an outdated class summary because the server suppresses evidence for the new split or merge.
Done right. The method works best when prototype summaries are already informative enough to reveal whether a class is single-mode or multi-mode, because then the evidence test is measuring actual semantic structure rather than noise.
What a runnable demo should prove

What a runnable demo should prove

Build a toy federated setup with three clients and two classes. Make one class stay compact on every client. Make the other class split into two sub-groups on two clients and one group on the third. Compare a fixed one-prototype method against FedPTE. The demo should show whether the server learns to keep one representative unit for the compact class and two for the split class, and whether client features become easier to classify after the topology update.
