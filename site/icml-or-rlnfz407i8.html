DB-KSVD: Scalable Dictionary Learning for Transformer Interpretability

A faster, smarter way to break down what language-model embeddings actually encode by using optimized batch processing instead of treating each sample sequentially.

Paper explainersAll themesInterpretability

Language models like Gemma store what they know as dense lists of numbers - what researchers call embeddings (internal snapshots where each slot is a number that jointly encodes meaning). To understand what they know, researchers want to break each list into a sum of simple building-block features - a process called dictionary learning. This is very hard to do at scale. This paper solves it by adapting an old, proven algorithm (KSVD) with two key tricks: processing data in batches like iterative training does (where you take small steps on subsets instead of one giant step on everything), and carefully parallelizing the math so millions of samples can be handled.

Zero assumption version

High-Dimensional Embeddings Are Opaque

A large language model like Gemma stores each piece of understanding as a list of thousands of numbers (a vector). These lists are far too tangled to read directly. Researchers want to decompose them: figure out which simple features (like sentiment, named entities, grammatical role) are present in each one.

A naive approach is to treat dictionary learning as a straightforward optimization problem: guess some basic features and adjust them until they sum to reconstruct the lists. The catch: there are thousands of dimensions and millions of embeddings. The math is fundamentally difficult (called NP-hard), and simple linear solvers are too slow. Recent work used sparse autoencoders (neural networks with one small layer), which are fast but crude - they use a basic linear encoder to solve the sparse encoding step, which is mathematically known to be computationally intractable.

The core problem. Dictionary learning on massive embedding lists requires an algorithm that is mathematically proven to work, scales to thousands of numbers and millions of examples, and finds better feature-breakdowns than simple linear encoders do, because theoretically-grounded algorithms (like KSVD) can navigate the solution space more carefully than greedy approximations.

The algorithm as a flow

What it actually does

Divide data into batches

Split the millions of embeddings into manageable groups, just like mini-batch training.

Sparse encoding with matching pursuit

For each batch: greedily pick dictionary features that best match each embedding, updating the error after each pick.

Efficient dictionary update

Instead of recomputing all math from scratch, use iterative methods (like power iteration) to find just the top singular vector.

Parallelize and fuse operations

Precompute key products and partition work across CPU workers so samples process simultaneously.

Repeat and stack features

Process the next batch of features on the residual (what was not explained yet), building a layered dictionary.

What the paper changes

The One Thing That Changes

Dictionary learning has two alternating steps: (1) find sparse codes (which features are in each embedding), and (2) update the dictionary (which features exist). Standard KSVD does both on all data at once. DB-KSVD changes the algorithm structure by batching the data - it processes chunks of samples and their corresponding features in sequence, then computes residuals and stacks the next batch on top. This keeps memory use low, because when the computer stores only a subset of data at a time, the data fits in fast temporary storage (CPU caches and RAM); and it lets modern parallel hardware run the same math faster, because independent samples can be processed by different processor cores without waiting for each other.

The hidden quantity

Sparsity: How Many Features Per Embedding

measured quantity  =  Sparsity of features

The core measurement DB-KSVD cares about is sparsity: how many of the dictionary features actually fire (are non-zero) in each embedding. A sparse representation means most features are off, so only the truly relevant ones are on - this is what makes embeddings interpretable. SAEs enforce sparsity via a penalty term during training. DB-KSVD inherits this through the matching pursuit algorithm, which stops adding features once a fixed budget is used.

The paper measures this sparsity implicitly: each embedding is decomposed into a sparse vector of weights (how strongly each feature contributes). During sparse encoding, matching pursuit greedily picks features until the sparsity constraint stops it. The paper evaluates by running six metrics from the SAEBench benchmark, which measure whether the features are actually interpretable and whether they explain the data well.

Why it works

Why Batching and Parallelization Work

In classic KSVD, the bottleneck is dictionary update: finding better features requires singular value decomposition (a way to break a table of numbers into simpler pieces), which is expensive linear algebra on the full data. Dictionary update dominates the runtime because SVD has to touch every number in the table of data and recompute which directions matter most from scratch, while sparse encoding can restart from any point. DB-KSVD solves this by four tricks: (1) Batch the data - each KSVD iteration processes only one batch at a time, like iterative training where you update using subsets rather than all data. (2) On each batch, compute only the top singular vector (via power iteration), not the full decomposition, because you only need the best single feature direction, not all of them. (3) Fuse nearby memory accesses and use multiprocessing so multiple samples can be encoded in parallel, because modern CPUs are much faster when data is close together in storage. (4) Stack batches: run sparse encoding on the first batch's features, compute what was not explained (the residual), then fit the next batch of features to that residual, which breaks a hard global problem into easier local ones.

Why does this work? Because the dictionary update math does not require all samples to be present at once - it can be computed in chunks and recombined, so batching does not break the mathematical theory. The matching pursuit sparse encoding naturally parallelizes because each sample's encoding is independent - no sample needs to wait for another. These three changes speed up the algorithm without breaking the math because the theoretical convergence proof for alternating optimization does not assume all samples are in memory at once; it only requires that each step improves the loss, which batching preserves.

The Matching Pursuit Update

First in words:

residual ← residual minus (dot product of residual and chosen feature) times that feature

Then the compact form:

r ← r - ⟨r, dj⟩ · dj, where j = argmax_j' ⟨r, dj'⟩

Every symbol:

rThe current error left to explain (residual)
djThe j-th dictionary feature (a vector)
⟨r, dj⟩Dot product: how well feature j matches the residual
argmax_j'Pick the feature with highest dot product
A tiny worked example
Start with residual r = [0.8, 0.6, 0.2] (error to explain).
Dictionary has three features: d1 = [1.0, 0, 0], d2 = [0, 1.0, 0], d3 = [0, 0, 1.0].
Dot products: ⟨r, d1⟩ = 0.8, ⟨r, d2⟩ = 0.6, ⟨r, d3⟩ = 0.2. Winner: d1.
Update residual: r ← [0.8, 0.6, 0.2] - 0.8 × [1.0, 0, 0] = [0, 0.6, 0.2].
Now ⟨r, d2⟩ = 0.6 is highest. Update: r ← [0, 0.6, 0.2] - 0.6 × [0, 1.0, 0] = [0, 0, 0.2].
One more: r ← [0, 0, 0.2] - 0.2 × [0, 0, 1.0] = [0, 0, 0]. Fully explained with three features.

Each greedy step picks the best-matching feature and removes it from the error, ensuring fast, simple arithmetic and natural sparsity.

What can go wrong

What can go wrong

Batch size chosen wrong. If batches are too large, memory use spikes and parallelization fails. If too small, the dictionary update on small samples becomes unreliable. The paper batches carefully to balance this.
Matching pursuit too greedy. Picking features in a strict greedy order can lock in bad early choices. If the first feature chosen is only medium-good, later features cannot undo that. The sparsity limit ends up suboptimal.
Residual stacking accumulates error. When fitting the next batch of features to the residual, previous batches' errors compound. If batch 1 left 5 percent unexplained, batch 2 now has to explain what batch 1 missed plus its own share.
Done right. DB-KSVD manages all three: tuning batch size to hardware (so data fits in fast storage), using power iteration instead of full SVD (which converges faster and is more stable because it avoids computing eigenvalues you do not need), and only batching at the top level (not recursively, because recursive batching stacks error). At test time, a single full sparse encoding on the complete dictionary is run to ensure quality (because you want to commit to one solution once, not layer approximations).
What a runnable demo should prove

What a runnable demo should prove

Build a small dictionary learning task: start with a synthetic dataset of 10,000 short vectors (say, 200 dimensions). Create a ground-truth dictionary of 50 features (random directions), generate embeddings as sparse sums of these features, then add noise. Run both a basic SAE and DB-KSVD on the same data. Measure how many of the 50 ground-truth features each method recovers, how much variance they explain, and how long each takes.

recovery_rate = (number of ground-truth features matched) / (total features in dictionary)

The demo must show that DB-KSVD recovers the true features as well as or better than SAEs (because the algorithm uses theory to navigate the search space), runs in reasonable time and ideally faster on multicore (because batching and parallelization reduce memory traffic and let cores work independently), and produces interpretable output when run on real embeddings from a small model like Pythia-160M.
