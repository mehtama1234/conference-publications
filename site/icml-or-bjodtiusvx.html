Parameterized Diffusion Policies

Learn a continuous code for each robot behavior so you can adapt the policy at test time by tweaking only that code, not retraining the whole model.

Zero assumption version

Diffusion policies lack steering and adaptation

Diffusion policies (a type of neural network trained on recorded robot demonstrations) excel at capturing all the different ways a task can be done—grasping a mug by the handle, from the side, from above. But once trained, the policy is frozen. A beginner would try to adapt it to a new constraint (a new obstacle, a different mug position) by rerunning the training loop with new data and new gradient updates. That is expensive and slow.

The real problem runs deeper: because diffusion policies bake all behaviors into a single giant neural network without any way to identify which behavior is which, they have no natural knob to turn at test time to say 'please generate behavior mode #3 instead of #1' or 'blend behaviors #1 and #2'. When the environment changes, the old behaviors are still burned into the network, and you cannot simply dial them up or down.

In one sentence. Add a learned continuous code to each behavior so the policy can steer behaviors and adapt at test time by tuning just that code.

The algorithm as a flow

What it actually does

Encoder learns to compress trajectories

During training, an encoder reads each recorded robot trajectory and outputs a short continuous code (a list of numbers, typically 8–16).

Decoder reconstructs to preserve behavior info

A decoder takes that code and regenerates the original trajectory. Loss on reconstruction forces the code to capture everything about how the robot moved.

Alignment loss makes code distances match trajectory distances

A separate loss pulls codes apart or closer based on how physically different the trajectories are (measured by Dynamic Time Warping, a metric that compares trajectories even if one is slower/faster), because this matching is what lets you adjust codes at test time to find new behaviors—if the code space does not match the behavior space, tweaking a code produces random results.

Diffusion denoiser learns to use the code

The diffusion denoiser (the network that generates actions) is trained to condition on the code, learning to produce behaviors that match the code's semantic meaning.

At test time: adjust code to find new behaviors

When a constraint changes, optimize just the code via gradient descent to fit the new constraint. The frozen denoiser interprets the tweaked code as a request for a new or blended behavior.

What the paper changes

What the paper changes

The paper adds one continuous behavior code to each training trajectory and learns it via a multi-loss encoder-decoder. At test time, it optimizes only that code, not the diffusion denoiser's weights.

the object it moves  =  Behavior code (continuous learned code)
The hidden quantity

The semantic alignment distance

measured quantity  =  Code-trajectory distance alignment

The paper measures how well distances in the code space match distances between real trajectories. If two trajectories are physically similar (same overall shape, same motion style), their codes should be close in the code space. If two trajectories are very different (grab-top versus grab-side), their codes should be far apart.

The paper estimates this using an alignment loss: compute how far apart two trajectories are using Dynamic Time Warping (a distance metric for comparing sequences that handles timing variations), then pull or push the corresponding codes to align with that distance. This alignment is what makes the code space navigable—you can interpolate smoothly between codes and find intermediate behaviors, or nudge a code in the direction of a known feasible behavior.

Why it works

Why adding a behavior code enables test-time steering

At training time, the encoder learns to map each trajectory to a code, and the diffusion denoiser learns to condition on that code—meaning the network learns patterns like 'if the code says grab-top, generate top-approach actions' and 'if the code says grab-side, generate side-approach actions'. The alignment loss ensures that nearby codes elicit similar behaviors and distant codes elicit different behaviors.

At test time, when a new constraint arrives (e.g., an obstacle blocks the top approach), you have two paths: (1) If one of the training behaviors still works, optimize the code to match that training trajectory using a reconstruction loss—the code becomes a warm start pointing to 'grab-side', and small gradient steps refine it. (2) If no training behavior works, optimize the code into uncovered regions of the code space—the denoiser interpolates and extrapolates, generating a behavior that respects the learned structure (it will resemble a blend of nearby training behaviors because the denoiser learned smooth transitions between codes). Either way, you adjust only the code, not the weights, so adaptation is a small, fast optimization problem.

The structure of the code space is the key: if codes were arbitrary and unstructured, tweaking one code would generate garbage. But because the alignment loss positioned the space so nearby codes mean nearby behaviors, small code adjustments produce sensible, safe behavior variations.

Math after the picture

The multi-objective training loss

First in words:

Total loss is reconstruction loss plus KL regularization loss plus geometry loss. Reconstruction loss is the squared difference between the original trajectory and the reconstructed trajectory from the code. KL regularization loss pushes the code distribution toward a standard Gaussian, preventing the codes from sprawling wildly. Geometry loss minimizes the squared difference between distances in code space and distances between actual trajectories.

Then the compact form:

L_total = L_rec + lambda_KL * L_KL + lambda_geo * L_geo, where L_rec = ||tau - D(z)||^2, L_KL = KL(q(z|tau) || N(0,I)), L_geo = (delta_z_ij - delta_X_ij)^2

Every symbol:

L_totalTotal training loss for the encoder-decoder
L_recReconstruction loss: squared difference between original and reconstructed trajectory
tauThe recorded robot trajectory (sequence of actions and observations)
D(z)Decoder output given code z: reconstructed trajectory
zThe learned behavior code, a continuous vector in latent space
L_KLKL divergence loss: distance from the pattern of codes to a standard Gaussian shape
q(z|tau)The encoder's learned distribution: what codes are likely for a given trajectory
N(0,I)Standard Gaussian (mean zero, identity covariance)
lambda_KLWeight controlling how strongly to regularize toward Gaussian
L_geoGeometry loss: squared difference between code distance and trajectory distance
delta_z_ijEuclidean distance between code z_i and code z_j in latent space
delta_X_ijDynamic Time Warping distance between trajectory i and trajectory j
lambda_geoWeight controlling how strongly to enforce geometric alignment
A tiny worked example with 2 trajectories and 2 codes
Suppose trajectory 1 (grab-top) maps to code z1 = [1.0, 2.0] and trajectory 2 (grab-side) maps to code z2 = [4.0, 5.0].
Euclidean distance in code space: delta_z_12 = sqrt((4-1)^2 + (5-2)^2) = sqrt(9+9) = sqrt(18) ≈ 4.24.
Suppose Dynamic Time Warping on the actual trajectories gives delta_X_12 = 3.5 (they are fairly different but same task).
Alignment loss for this pair: (4.24 - 3.5)^2 = (0.74)^2 ≈ 0.55.
Reconstruction loss for trajectory 1: suppose D(z1) = [1.1, 2.1, ...] and tau1 = [1.0, 2.0, ...]; squared difference ≈ 0.01.
KL loss pulls the pattern of codes toward a standard Gaussian shape; suppose it contributes 0.1.
Total for this example: L_total ≈ 0.01 + 0.1 + 0.55 = 0.66. Gradient descent nudges z1 and z2 so that on the next update both losses shrink.

The three losses work together: reconstruction preserves behavior info in the code, KL keeps the code space well-structured, and alignment makes nearby codes mean nearby behaviors so small adjustments at test time produce sensible changes.

What can go wrong

What can go wrong

Alignment loss weak or mismatched. If the alignment loss weight is too small or the trajectory distance metric (DTW) does not match how different behaviors really are, nearby codes may not produce nearby behaviors. Then test-time steering produces garbage.
Code space collapses or fragments. If the KL regularization (penalty for spreading codes away from a standard Gaussian) is too weak, the codes can scatter wildly or clump into separate islands. Then blending between codes fails, and finding unseen behaviors will not work.
No training examples span the distance. If the new constraint is too far from any training behavior, the denoiser has no learned pattern to blend or extrapolate. The adjusted code will produce a bizarre, infeasible behavior.
Done right. Balance the three losses, use a good trajectory distance metric, and ensure the training data covers diverse enough behaviors that interpolation is reasonable. Test-time steering then smoothly extends behaviors to new constraints.
What a runnable demo should prove

What a runnable demo should prove

Build a simple 2D reach-and-push task in simulation (a point-mass robot pushing a block to a goal, with two ways to do it: push-from-left or push-from-right, both in training). Train a PDP on the two trajectories. At test time, add an obstacle that blocks push-from-left. Optimize just the behavior code via gradient descent (no weight updates) for 5-10 steps. Measure whether the adjusted code produces a trajectory that avoids the obstacle, reaches the goal, and resembles push-from-right or a blend of the two.

Success rate = fraction of test constraints solved by code-optimization (no retraining). Adaptation speed = number of gradient steps to reach feasible behavior.

The demo must show that small changes to a single code produce large, visible changes in robot behavior—steering between known modes and discovering new ones—without touching the denoiser weights.
