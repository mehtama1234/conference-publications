Divide and Abstract: Autoformalization via Decomposition and Abstraction Learning

Break informal math statements into concrete clauses, formalize each one using learned reusable building blocks, then stitch them back together so a computer can check your work.

Paper explainersAll themesInterpretability

Turning written mathematics into formal language that a computer can verify is hard. Mathematicians do not start from scratch each time — they build on common definitions and relations they have already formalized. DNA learns these reusable building blocks from a corpus of informal math, then decomposes each new statement into clauses, translates each clause into its formal version using those blocks, and stitches the formal pieces back together. Because it learns the building blocks once and reuses them, the method works even on new statements and low-resource formal languages with zero retraining.

Zero assumption version

Before: one statement at a time, no reusable pieces

Autoformalization means converting math written in plain English into a formal language — a strict syntax that a machine can parse and verify. Mathematicians write: 'If a set is compact and the function is continuous, then the image is compact.' A computer needs: a series of formal symbols and rules, no room for interpretation.

Previous work treats each statement as a solo translation puzzle. A model learns to output the formal version for that single sentence. But mathematicians know that the same formal definitions — like 'compact', 'continuous', 'image' — appear again and again across hundreds of statements. They formalize these once, then reuse them. The naive approach redoes the same formal translation of 'compact' each time it sees the word, wasting effort and missing the chance to share hard-won formal precision.

The problem bites hardest at scale: formalizing a large corpus of math statements requires either training a fresh model for each piece or letting redundant translations pile up. And low-resource formal languages — specialized notations used in few papers — have almost no training data, so model-based approaches stall.

In one sentence. Extract reusable formal building blocks from the whole corpus, then use them to formalize each statement without retraining.

What the paper changes

What changes: from bare informal text to formally grounded statements

The paper changes which part of the formalization process uses learned abstractions. Instead of asking a model to translate an entire statement in one go, it forces the model to ground each informal clause in a formal definition that was extracted from the corpus. This means formal abstractions become the bridge between informal and formal language.

the object it moves  =  the grounding layer
The hidden quantity

The hidden quantity: formal abstraction coverage

measured quantity  =  coverage of learned abstractions

Coverage means: what fraction of the informal statement can be explained using the formal definitions the method extracted from the corpus. High coverage means the informal text aligns closely with definitions the model has already seen and formalized. Low coverage means concepts never seen before in the corpus, so the model must invent a formal version from scratch without guidance — this risks errors because the model has no anchor to ground the translation in an already-validated formal definition.

DNA measures this by tracking how many informal concepts in a statement map to entries in the learned abstraction library. If a statement contains 'continuous' and 'compact' and both are in the library, coverage is high. If it introduces a concept not seen before in the corpus, coverage drops, because the model must invent a formal version from scratch with no learned anchor — risking errors. The method uses low-coverage spots to decide where a symbolic validator needs to fix the formalization.

Why it works

Why it works: decompose, ground, validate

Translating math from informal to formal is hard because the model must hold the entire statement in memory and output a perfect formal rendering in one step — tiny errors break correctness. DNA breaks this into smaller, easier steps.

First, it learns common formal abstractions from the whole corpus. This is like studying worked examples and extracting the key definitions used everywhere. A model can now reuse these instead of re-inventing 'compact' each time.

Second, it decomposes each informal statement into concrete logical clauses — bite-sized pieces. This turns the problem from 'translate this whole paragraph' into 'translate this one phrase, then this next phrase'. Smaller pieces are easier to get right.

Third, each clause is formalized using the learned abstractions as anchors. The model knows 'continuous' has a formal definition in the library, so it can look it up and apply it, rather than guessing.

Finally, a symbolic validator — which can actually run and check formal code — looks at the stitched-together formal statement and gives feedback. Where the formal version does not match what the validator expects, the system refines it. This closes the loop: informal intent gets converted to formal, then tested, then fixed if needed.

Because abstractions are learned once from the corpus and reused on all statements, the method scales to new statements without retraining, and even works on low-resource formal languages where training data is sparse.

The formalization equation

First in words:

For each clause in a decomposed statement, produce a formal version that uses learned abstractions, then compose and validate.

Then the compact form:

formal_statement = compose([formalize_clause(c_i, abstractions) for c_i in decompose(informal_statement)]) + validate_and_refine(formal_statement)

Every symbol:

informal_statementthe plain-English math statement you are formalizing
decompose()split the statement into small logical pieces
c_ithe i-th logical clause after decomposition
abstractionsthe library of formal definitions extracted from the corpus
formalize_clause()translate one clause into formal language using the abstractions
compose()stitch the formal clauses back together into one statement
validate_and_refine()check the formal statement with a symbolic validator and fix errors
A tiny worked example
Informal statement: 'If f is continuous and D is compact, then f(D) is compact.'
Decompose into clauses: ['f is continuous', 'D is compact', 'f(D) is compact']
Formalize each: ['continuous(f)', 'compact(D)', 'compact(image(f, D))]'
Abstractions in library: continuous := {...}, compact := {...}, image := {...}
Compose: [continuous(f) AND compact(D)] IMPLIES [compact(image(f, D))]
Validate: formal statement type-checks and follows the rules of the formal language.
Refine: if validation fails (e.g., 'compact' not defined for this domain), update the clause and revalidate.
Result: a formal statement a machine can verify is logically sound.

What can go wrong

What can go wrong

Corpus is too small or unbalanced. If the corpus does not contain enough examples of key concepts, or if one type of math dominates, the learned abstractions will be sparse or biased. Coverage drops on diverse statements.
The decomposition misses implicit structure. If the informal statement uses a subtle logical relationship that the decomposer does not catch, the formal version will be incomplete. A statement like 'for all continuous functions, the image of a compact set is compact' has a hidden quantifier that a naive split might miss.
Formal language is too strict or unfamiliar. Some formal languages have constraints or conventions that are not obvious. If the validator rejects a formally correct clause because of a stylistic rule, refinement may fail to fix it without human help.
Done right. A large, diverse corpus with clear decomposition rules and a symbolic validator that gives specific feedback on what went wrong makes the method reliable, because the method can then fix the formal clause and revalidate.
What a runnable demo should prove

What a runnable demo should prove

A demo should take a corpus of 20-50 informal math statements (e.g., from a textbook chapter on real analysis), extract formal abstractions for the recurring concepts (compact, continuous, open, closed), then formalize 5 new statements not in the corpus using those learned abstractions. For each statement, show the decomposition, the formal version, and whether a symbolic validator accepts it. The demo should make two claims concrete: (1) reused abstractions work, because the new statements decompose into clauses that match learned definitions, so the formal version assembles from pieces already proven correct; (2) decomposition helps each clause, because smaller logical units are simpler to translate and have fewer moving parts to break.

success_rate = (number of formally correct statements) / (total number of statements)

The irreducible insight: you can build a library of reusable formal definitions once, then use that library to formalize new math without retraining, because each new statement decomposes into pieces that fit the learned abstractions.
