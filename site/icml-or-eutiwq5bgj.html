ControlG: Feedback Control for Multi-Objective Graph Learning

Instead of forcing every weight update to compromise between competing goals, a control-theory scheduler decides WHEN each goal gets to train, preventing conflicts and starvation.

Paper explainersAll themesGraph & Geometric Learning

When you teach a graph model to do multiple tasks at once—finding mutual similarities, reconstructing data, and contrasting examples—they often fight for the same weights. The usual approach weights them per update, but that leaves some tasks starved while others dominate. ControlG recasts this as a scheduling problem: measure how hard each task is to learn and when tasks clash, let a control system decide when each one should get optimization time, producing an auditable schedule that reveals which tasks actually drove learning.

Zero assumption version

The tug-of-war between competing graph objectives

Graph models learn from unlabeled data by inventing their own training tasks. One task might say: find pairs of examples that are similar. Another says: rebuild the input from a noisy version. A third says: examples that should be close end up far apart, and far ones stay far. Each task pulls the weights in a different direction.

The naive approach: on every weight update, take a weighted average of the three task nudges and move the weights by that average. But this creates three hidden problems. First, Disagreement: if task A wants weights to move up and task B wants them down, the average nudge is small, so neither task makes much progress—learning one task actually weakens the other. Second, Drift: as training proceeds, some tasks become easier while others get harder, yet a fixed average weight stays unchanged, missing this shift. Third, Drought: if tasks have mismatched difficulties, a uniform weight starves the hard tasks—because the average nudge is tiny compared to the signal they need, they never climb out of noise.

In one sentence. The paper recasts multi-objective learning as a scheduling problem: measure each task's difficulty and conflict with others, then use a control system to decide when each task should receive optimization budget.

The algorithm as a flow

What it actually does

Measure per-task difficulty

Estimate how hard each objective is to optimize by watching how much its loss shrinks per training step.

Measure pairwise conflict

For each pair of tasks, compute how much one task's nudge opposes the other's on the same weights.

Plan target allocation

Use a Pareto-optimal planner to decide what fraction of training time each task should get, trading off between all objectives fairly.

Close the feedback loop

A PID controller (a standard tool from engineering) adjusts the schedule in real time if any task falls behind or gets too much focus.

Output an auditable schedule

The final schedule shows which task to train on each step, revealing the real learning path.

What the paper changes

What the paper changes: the allocation schedule

Instead of a fixed weight per objective, the paper introduces a time-varying schedule that decides which single objective receives the full optimization budget at each training step. Rather than blending all the nudges together into one weak average, you apply one task's nudge fully, then switch to another task's nudge, then another, rotating based on measured difficulty and conflict.

the object it moves  =  training schedule per objective
The hidden quantity

The hidden quantity: pairwise task antagonism

measured quantity  =  task antagonism (how much one task's nudge opposes another's)

Task antagonism is a single number (or a matrix) that measures how much two objectives conflict on shared weights. If task A's nudge says move a weight up and task B's nudge says move it down, antagonism is high. If both nudges point in the same direction, antagonism is low. Antagonism is hidden because you do not see it directly—only when tasks interfere with each other in training.

The paper estimates antagonism by computing the dot product of gradient vectors between pairs of tasks. Positive dot products mean they agree (low antagonism); negative or near-zero dot products mean they fight (high antagonism). High antagonism tasks should rarely run together; the scheduler will give them separate time slots to avoid cancellation.

Why it works

Why scheduling beats static weighting

Static weighting forces every weight update to be a compromise. For example, pulling 40% toward task A, 30% toward B, and 30% toward C. If task A and B want opposite moves, their contributions cancel and both make no progress—the weights barely shift. Scheduling instead flips the logic: run task A alone for several steps, letting its full force push the weights without opposition. Then switch to task B's turn. Since each task acts in isolation (or with friendly partners), the weights move decisively instead of getting stuck.

Why this works: A gradient pointing uphill has force. When two opposing forces meet, they neutralize each other. But if you apply force A fully, then force B fully, then force C fully, each one pushes the weights without resistance, and they end up further along than if you applied weak versions of all three at once. The scheduler ensures this by measuring which tasks fight (high antagonism) and keeping them in separate time slots.

The PID controller tightens the loop: measure how much each task has improved since its last turn. If task B is falling behind, give it the next turn. If task C just improved a lot, reduce its next allocation. This prevents starvation (the hard tasks get more turns) and prevents nonstationary problems (the scheduler continuously re-measures as difficulty changes). The auditable schedule itself proves what learning path the model took.

Math after the picture

The core equation: antagonism and Pareto planning

First in words:

antagonism(A,B) = sum over shared weights of gradient_A times gradient_B, divided by their lengths; target_allocation solves: maximize log(product of per-task final accuracies) subject to total training budget and pairwise antagonism constraints.

Then the compact form:

antagonism(i,j) = dot(grad_i, grad_j) / (norm(grad_i) * norm(grad_j)); allocate_t = argmax sum_i log(acc_i_target) s.t. sum_t allocate_t = T, antagonism(i, j) < threshold if overlap(t_i, t_j) > 0

Every symbol:

grad_ithe nudge direction task i wants for shared weights
norm(grad)the magnitude or length of a gradient vector
dot(grad_i, grad_j)how aligned the two gradients are (positive if same direction)
acc_i_targetexpected accuracy for task i under the proposed schedule
allocate_tbinary choice: does task i get training time at step t
Ttotal training steps available
thresholdmaximum antagonism allowed if two tasks train in the same window
A tiny worked example
Task A gradient: [0.5, -0.2, 0.8]. Task B gradient: [-0.1, 0.3, 0.6].
Dot product: 0.5 * (-0.1) + (-0.2) * 0.3 + 0.8 * 0.6 = -0.05 - 0.06 + 0.48 = 0.37.
Norm A: sqrt(0.5^2 + 0.2^2 + 0.8^2) = sqrt(0.25 + 0.04 + 0.64) = sqrt(0.93) ≈ 0.96.
Norm B: sqrt(0.1^2 + 0.3^2 + 0.6^2) = sqrt(0.01 + 0.09 + 0.36) = sqrt(0.46) ≈ 0.68.
Antagonism(A,B) = 0.37 / (0.96 * 0.68) ≈ 0.37 / 0.65 ≈ 0.57 (moderate alignment, can run together).

Antagonism near 1 means tasks agree; near 0 or negative means they fight. High antagonism pairs get scheduled into different time windows to prevent gradient cancellation.

What can go wrong

What can go wrong

Antagonism estimation is noisy early in training. If you measure conflict too early, the task gradients are unstable, giving false antagonism scores. The schedule might keep misaligned tasks apart when they actually agree. Workaround: warm up the antagonism estimates over the first few epochs, or smooth them with a moving average.
PID controller overshoot. If the controller reacts too aggressively to a task falling behind, it might allocate far too much time to it next, causing other tasks to starve in the opposite direction. Requires tuning the controller gains (proportional, integral, derivative terms) per dataset.
Pareto planner finds disconnected optimum. The log-hypervolume planner might heavily favor one task over others. At the Pareto frontier, any improvement to one task requires sacrificing another. Some plans might leave one task neglected if what you value differs from the planner's fairness model. May need manual constraint tightening to enforce minimum allocations.
Done right, antagonism guides the schedule. When antagonism is estimated cleanly and the PID gains are tuned, the schedule naturally separates conflicting tasks and gives dedicated time to starved ones, eliminating the hidden interference.
What a runnable demo should prove

What a runnable demo should prove

Build a graph dataset with three clear objectives: mutual information (maximize similarity between augmented views), reconstruction (predict missing nodes), and contrastive (push apart dissimilar examples). Train a graph neural network using three methods: (1) static 1/3 weight to each, (2) per-update adaptive weighting based on loss magnitudes, and (3) ControlG's schedule. Log the antagonism matrix at each epoch and the schedule decisions (which task trained when). Track individual task accuracy throughout training, not just end performance.

improvement_per_task = (ControlG_final_acc_i - static_weighting_final_acc_i) for each task i; schedule_utilization = number of steps each task was scheduled; interference_score = mean(antagonism) for task pairs scheduled in the same window

The demo makes clear that scheduling prevents cancellation. Watch all three task accuracies climb together because the schedule separates conflicting tasks into different time windows, letting each full nudge act without opposition, unlike the average where they dilute each other.
