Seek-CAD: A Self-refined Generative Modeling for 3D Parametric CAD Using Local Inference via DeepSeek

Seek-CAD generates a parametric CAD program, renders what it built, critiques the result with a vision checker, and rewrites the program until the shape better matches the target.

Paper explainersAll themesAgents & Tool Use

Parametric CAD generation is hard because the system is not producing one image; it is producing a program made of construction commands. A small mistake early in that program can distort the whole shape. Seek-CAD addresses that by adding a self-refinement loop. It drafts a CAD program, renders the intermediate and final part shape into images, asks a vision-language checker to compare those renders with the intended design and the model's own reasoning notes, then uses that feedback to revise the next draft. The result is a training-free loop that can improve a local reasoning model without fine-tuning it because each new draft receives explicit feedback about what the previous draft built incorrectly.

Why CAD programs are harder than CAD pictures

A CAD model is built from commands such as sketch, extrude, cut, and refine. That means the system must choose not only the final shape but also the exact sequence of construction steps. If one command uses the wrong dimension or appears in the wrong order, later commands inherit the error and the final part can be unusable.

Pure text prompting is not enough because the model does not directly see the shape it just generated. It only sees the command list. A command list can look plausible even when the rendered part is clearly wrong. To improve the draft, the model needs feedback from the actual part shape it produced because the image reveals errors that are hidden in the raw command text.

The paper's move. Generate a CAD command program, render the resulting part into images, critique the renders, and feed that critique back into the next draft.

The hidden quantity

The hidden quantity: render-to-design agreement

measured quantity  =  how closely the rendered part matches the intended design

The important quantity is not whether the command list sounds reasonable. It is whether the rendered part matches the intended shape. Seek-CAD makes that quantity visible by rendering the current draft and asking a checker to inspect those images.

Agreement rises when the views show the right profile, hole placement, proportions, and step order. Agreement falls when a command silently breaks the shape. Because the next draft receives feedback tied to the rendered mismatch, the model can revise the specific part of the program that caused the geometric error.

Why it works

Why it works

CAD programs are brittle because early choices constrain later ones. A one-shot generator has no direct way to inspect the part shape it created, so it can keep repeating a structurally wrong program. Seek-CAD fixes that by closing the loop between program and rendered shape.

The render step matters because images expose geometric mistakes that are hard to spot in raw command text. A hole in the wrong face, an extrusion with the wrong depth, or a profile that should have been symmetric become visible once the part is rendered. The checker can then produce feedback about the actual shape, not just the wording of the program.

The self-refinement loop is useful even without fine-tuning because the local reasoning model can treat visual feedback as new context for the next draft. Each round supplies a clearer description of what the previous program did wrong, so the next command sequence can move toward the intended design.

The refinement objective

First in words:

Choose the next CAD program that maximizes agreement between the rendered part and the intended design after applying visual feedback from the last draft.

Then the compact form:

program_next = refine(program_now, feedback(render(program_now), target_design))

Every symbol:

program_nowthe current CAD command sequence
render(program_now)the images produced by the current CAD draft
target_designthe intended part description
feedback( , )the checker output describing mismatches between the render and the target
refine( , )the revision step that rewrites the CAD program using that feedback
program_nextthe revised CAD command sequence
A tiny worked example
The first draft extrudes the base correctly but places a hole on the top face instead of the side face.
Rendering shows the hole in the wrong location immediately.
The checker reports that the side view does not match the target design.
The next draft rewrites the hole command so it targets the side face.
The second render now matches the intended silhouette much more closely, so agreement rises.

The key point is the feedback path from rendered shape back to program text, because that is what lets the model repair structural mistakes.

What can go wrong

What can go wrong

Rendered views miss the real flaw. If the selected views do not expose the shape mistake, the checker may approve a bad part because the hidden error never appears in the images it inspects.
Feedback is vague. A revision loop needs precise feedback. If the checker only says the shape is wrong without pointing to the mismatch, the next draft may rewrite the wrong command.
Program revision breaks an earlier good step. Changing one command can disturb later shape details because CAD commands are dependent. A repair to one feature may accidentally damage another feature built on top of it.
Done right. The method works when the render set exposes the important shape details and the feedback points to the command choices that caused the mismatch.
What a runnable demo should prove

What a runnable demo should prove

Use a small set of simple parametric parts such as brackets, plates with holes, and stepped blocks. Generate one CAD program in a single pass and another with two or three refinement rounds. Render both results from the same views and compare them with the target parts. Reviewers should be able to see that the refined program fixes visible shape mistakes that the one-shot program leaves behind.

agreement_gain = visual_match_after_refinement - visual_match_before_refinement; repair_rate = fixed_shape_errors / total_shape_errors

The demo should show that the gain comes from visual feedback about the rendered part shape, not from merely regenerating the same program again.
