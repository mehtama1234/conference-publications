The Tool Decathlon: Benchmarking Language Agents for Diverse, Realistic, and Long-Horizon Task Execution

Toolathlon tests language agents on long, multi-application workflows in realistic software states so that benchmark scores reflect real tool use rather than toy tasks.

Paper explainersAll themesAgents & Tool Use

Many agent benchmarks are too easy in exactly the ways that matter most. They use narrow domains, short task chains, or synthetic environments with little state complexity. That lets an agent look capable even when it cannot manage a real workflow that spans email, calendars, databases, documents, and operational tools. Toolathlon is designed to close that gap. It covers 32 applications and 604 tools, starts from realistic software states, and uses execution-based checks on 108 tasks that take about 20 tool turns on average. The paper's main result is uncomfortable but useful: even top systems still fail most of these tasks, which means the benchmark is measuring a real capability gap rather than rewarding shallow pattern matching.

Why current agent benchmarks understate the real difficulty

A real software task often spans several systems. An agent may need to read email, check a calendar, inspect a file, query a database, and then write an output into a separate application. Each step depends on the current state of those systems. If the benchmark hides that state complexity or shortens the workflow too much, then a passing score says little about whether the agent can work in a realistic environment.

Many earlier benchmarks emphasize functional realism but not state realism. A tool may exist, but the surrounding world is too simple: too few users, too few records, too little noise, and too few cross-application dependencies. Toolathlon argues that a serious benchmark needs diversity of applications, diversity of starting states, long task horizons, and strict execution-based grading because each part blocks a different shortcut.

The paper's move in one sentence. Build a benchmark where language agents must solve long, verifiable workflows across many real software applications and realistic starting states, so that success requires actual tool competence.

The algorithm as a flow

What it actually does

Step 1: Provide many applications and tools

Expose agents to 32 applications and 604 tools so that evaluation covers everyday and professional software rather than one narrow domain.

Step 2: Initialize realistic software states

Populate the environments with real courses, sheets, reports, and records because state realism is needed for planning mistakes to surface.

Step 3: Define long multi-step tasks

Create 108 tasks that require roughly 20 interaction turns on average, so that the benchmark measures persistence and error recovery.

Step 4: Let the agent act through tool calls

The model must decide which application to use, what action to take, and when to switch context across systems.

Step 5: Grade by final environment state

Dedicated evaluation scripts inspect the resulting software state so that a task only passes if the work was actually completed.

The hidden quantity

The hidden quantity: stateful workflow difficulty

measured quantity  =  how much real planning and memory a task requires once the software state is realistic

The benchmark is really measuring stateful workflow difficulty. That quantity rises when success depends on remembering earlier findings, handling cross-application dependencies, and navigating cluttered software states. It falls when the environment is empty or the task chain is too short.

Toolathlon is valuable because it makes that hidden quantity visible. The low scores of strong models are informative because they show that current systems still struggle when realistic state, long horizon, and multi-app coordination are present at the same time.

Why it works

Why it works

A benchmark only predicts real deployment quality if it contains the failure modes that appear in deployment. Toolathlon works because it includes several of those failure modes at once: wrong tool choice, forgotten intermediate facts, state misreads, cross-application mistakes, and errors that only surface many steps later.

The realistic environment state is essential because agents often fail when there is too much competing information. An empty spreadsheet or a clean inbox does not test whether the system can search, compare, and update the right record. A busy real-world state does.

Execution-based grading matters because free-form judging can miss hidden mistakes. A final environment-state check forces the benchmark to ask whether the work was actually completed. That makes low scores more trustworthy because they reflect real failures, not style preferences in evaluation.

The benchmark score

First in words:

Task success is the fraction of benchmark tasks whose final software state satisfies the dedicated evaluation script after the agent finishes its tool sequence.

Then the compact form:

success_rate = (# tasks whose final state passes evaluation) / (# total tasks)

Every symbol:

success_ratethe overall benchmark score
# tasks whose final state passes evaluationthe number of tasks completed correctly according to the environment-state checker
# total tasksthe full set of benchmark tasks being evaluated
A tiny worked example
Suppose an agent is tested on 108 tasks.
If it completes 32 tasks exactly, then the score is 32 / 108 = 0.296.
That is about 29.6 percent, which is close to the best reported range in the paper.
The other 76 tasks fail because at least one required environment change was missing or wrong.
This score matters because the checker looks at the final software state, not at how fluent the agent sounded.

The paper's execution-based metric matters because it ties score directly to completed work.

What can go wrong

What can go wrong

The benchmark may age as software changes. Applications evolve over time, so maintenance is required because broken connectors or changed interfaces can invalidate tasks.
Agents may fail for avoidable interface reasons. A model can miss a task because it misuses one tool argument even when the higher-level plan is right, so detailed traces are still needed beside the final score.
Coverage is broad but not universal. Thirty-two applications are a strong start, but real work is larger than any fixed suite, so some deployment settings will still be missing.
Done right. The benchmark is most useful when the environments stay maintained and the evaluation scripts keep checking real end states rather than intermediate guesses.
What a runnable demo should prove

What a runnable demo should prove

Build a compact benchmark with three to five connected applications, realistic seeded states, and ten long tasks that require cross-application coordination. Include execution scripts that inspect the final environment state. Compare a short-horizon toy benchmark score with the realistic benchmark score for the same model. The demo should show a clear drop on the realistic version because long-horizon, stateful tool work is substantially harder.

difficulty_gap = toy_success_rate - realistic_success_rate; mean_turns = total_tool_turns / total_tasks

The demo must make visible that realistic state and long horizon expose failures that a narrow toy benchmark hides.
