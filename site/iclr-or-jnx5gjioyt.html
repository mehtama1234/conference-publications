RankLLM: Quantifying Question Difficulty via Score Propagation

Instead of treating all questions the same, measure each question's difficulty and credit models more for answering hard ones.

Paper explainersAll themesDatasets & Benchmarks & Evaluation

Today's LLM benchmarks grade all correct answers equally, whether the question is trivial or hard. This makes it impossible to see which models are actually smarter. RankLLM solves this by measuring each question's intrinsic difficulty and rewarding models for cracking the tough ones. The core move is simple: a model gains competency points when it answers a question correctly, and that question's difficulty score increases when even strong models fail on it. This mutual feedback loop, run through a graph algorithm, produces final scores that match human judgments 90% of the time.

Zero assumption version

The benchmark blind spot

Imagine grading a student on two tests. Test A: "What is 2+2?" Test B: "Prove Fermat's Last Theorem." If the student gets both right, standard grading gives 50% on each. But clearly, one question is trivial and the other is impossible. Today's LLM benchmarks do exactly this: they count a model's answer to "What is the capital of France?" the same as an answer to a multi-step reasoning problem.

A naive approach is to count how many models solve each question and call that the difficulty. But this breaks badly: if every model in a test set happens to be weak, every question looks hard. If a strong model is missing, hard questions look easy. You are measuring the sample of models you happened to test, not the question itself.

The core problem. Standard benchmarks treat all questions equally. If model A gets all easy questions right but fails hard ones, and model B gets easy plus hard ones right, A and B might have the same score if they get the same total number correct. This hides that B is smarter because it cracked the hard ones.

The algorithm as a flow

What it actually does

Build two matrices

One shows which models answered which questions correctly; the other shows failures (the opposite).

Run a random walk

A virtual token bounces between models and questions: from model to question, favoring questions the model failed; from question to model, favoring models that solved it.

Count visits to steady state

After many bounces, the token spends more time at hard questions and competent models. Count how often it visits each.

Assign scores from visit counts

Question difficulty is how often the token lands on it; model competency is how often it lands on the model.

Validate and rank

Compare scores across different model subsets and human judges; if stable, the ranks are trustworthy.

What the paper changes

What the paper changes

Instead of grading every correct answer as one point, RankLLM rewrites the evaluation to assign different point values to different questions based on who solved them. When a strong model solves a question, that question is assumed hard and its correctness is worth more. When a weak model solves it, the question is assumed easier and worth less.

the object it moves  =  question difficulty scores
The hidden quantity

The hidden quantity: question difficulty

measured quantity  =  stationary visit frequency to each question

The paper introduces and measures question difficulty, defined as how often a virtual random walk process visits each question in its steady state. This is not a simple count of how many models failed; it is a measure that emerges from the joint dynamics of models and questions feeding back on each other.

To estimate it, the paper constructs two binary matrices (one for correct answers, one for failures, which is the opposite), encodes them as transition probabilities in a graph, and runs the random walk until the visit frequencies stabilize. The harder the question (in ground truth), the more often the walk should visit it, because competent models solve it and competent models are visited frequently.

Why it works

Why bidirectional propagation works

The core insight is that question difficulty and model competency are not independent; they define each other through data. If a model solved a question, we learn two things: (1) the model is competent enough to solve it, and (2) if many models failed on it, the question is likely hard. The paper captures this by encoding success and failure as two directed graphs and running a coupled random walk.

The walk oscillates: from a model, it preferentially hops to questions the model failed (because competent models fail only on hard questions). From a question, it preferentially hops to models that solved it (because hard questions are solved only by competent models). Over many steps, this feedback loop drives the walk toward a stable distribution where hard questions and capable models are visited frequently. This stable distribution is the final answer.

Why does this work? Because the walk naturally discovers the consistent ranking: if model A is truly more competent than model B, A will solve hard questions that B fails, and the walk will visit A more often. Similarly, if question Q is truly harder than R, fewer models solve Q, so the walk will get stuck at Q longer. The math (a coupled random walk with damping) guarantees this process converges to a unique, stable answer that stays close to the true ranking even when test data changes slightly.

Math after the picture

The random walk equation

First in words:

At each step, the probability of moving from a model m to a question q is proportional to how many models failed on q times how often the walk returns to m. Similarly, from q to m, the probability is proportional to how many models solved q.

Then the compact form:

pi_{m}^{t+1} = (1-alpha) * sum_q P(q->m) * pi_q^t + (alpha/M); pi_q^{t+1} = (1-alpha) * sum_m P(m->q) * pi_m^t + (alpha/Q)

Every symbol:

pi_m^thow often the random walk visits model m at step t
pi_q^thow often the random walk visits question q at step t
P(q->m)probability of jumping from question q to model m (high if m solved q)
P(m->q)probability of jumping from model m to question q (high if m failed q)
alphadamping factor: chance of teleporting to a random model or question (ensures convergence)
Mtotal number of models
Qtotal number of questions
A tiny worked example
Setup: 2 models (A, B), 3 questions (1, 2, 3). A solved all three. B solved only question 1 (the easy one). Start with equal visit counts: pi_A = 0.5, pi_B = 0.5.
From A's perspective: A failed on zero questions, so the walk rarely leaves A when starting from A. From B's perspective: B failed on questions 2 and 3, so when starting from B, the walk bounces to questions 2 or 3.
After 1 step with alpha=0.1: Questions 2 and 3 are visited more (only A solved them). The walk is pulled toward B (visited but likely to leave). After 10 steps: pi_A rises to ~0.65 (competent, visited from hard questions); pi_B falls to ~0.35; questions 2 and 3 rise to ~0.3 each (hard, solved by few models).
Intuition: The walk discovers that A is competent and questions 2 and 3 are hard because the walk gets 'trapped' at hard questions (few solvers), and gets pulled to competent models (who solved the hard ones).

The random walk finds the stable state where difficult questions and competent models reinforce each other.

What can go wrong

What can go wrong

Extreme case: universal solvers or universal failures. If every model answers a question the same way (all correct or all wrong), that question carries no information. The walk has no path between models via that question. The paper handles this by labeling such questions as trivially easy or hard and setting them to extreme values. But in a dataset with very imbalanced models (one model that solves everything, one that solves nothing), the algorithm can struggle.
Damping factor tuning. The damping factor alpha controls how often the walk teleports randomly. Too high, and the walk ignores the graph structure; too low, and it can get stuck. The paper uses a fixed alpha, but different model sets or datasets may need different values. No adaptive tuning is discussed.
Small model sets lose signal. With only a few models, failures become rare and questions look either trivially easy or impossible. The random walk has fewer paths to explore. The paper shows that with fewer than 10 models, rank stability drops by 20% or more.
Done right: stable difficulty rankings. When run on a large, diverse model set (30+ models, thousands of questions), RankLLM produces question difficulties that hold steady even when you remove some models or test on different model subsets. This stability is the sign the scores are real.
What a runnable demo should prove

What a runnable demo should prove

Build a tiny synthetic benchmark: 5 artificial models with known competency levels and 10 questions with known difficulty (3 easy, 3 medium, 4 hard). Simulate pass/fail outcomes: strong models solve hard questions, weak models solve only easy ones. Run RankLLM and plot the final difficulty scores vs. the ground truth. Then run standard accuracy and a simple count-of-failures baseline and show that RankLLM's difficulty ordering matches ground truth, while the baselines scramble the ranking.
