EquAct: SE(3)-Equivariant Robotic Manipulation

A robot policy that automatically adapts to how the scene rotates and moves, because it is built with a mathematical guarantee: whatever geometric transformation the world undergoes, the policy's outputs transform in lockstep.

Paper explainersAll themesRobotics & Control

Multi-task robot manipulation policies built on standard transformers (neural networks that read both images and text to predict actions) fail to generalize when objects and scenes rotate or move to new positions. The policy learns from a fixed training camera angle and breaks when the camera viewpoint or object orientation changes. EquAct solves this by building the policy with SE(3) equivariance—a mathematical guarantee that the robot's predicted actions will automatically adapt correctly to any 3D rotation or translation of the scene, without needing to memorize every possible orientation.

Why standard policies fail on rotated scenes

A robot trained to pick up a cup learns a mapping from the camera image and the current hand pose to an action (which direction to move, how wide to open the gripper). Standard transformer policies learn this mapping as a black box: feed in observations, get back actions. The problem emerges when the scene rotates. The image looks different—the cup is now at a different angle—so the camera input changes in a way the model never encountered, and the model produces an action that was never trained on and is usually the wrong one, because the input has shifted in a way the neural network was not prepared for.

A naive approach tries to fix this with data augmentation: rotate every training image and correspondingly rotate the action. This works but requires massive amounts of training data, and there is no guarantee the model has truly learned the relationship between how the world rotates and how the action should respond, rather than just memorizing each pose.

The method. EquAct enforces SE(3) equivariance: every part of the network is mathematically guaranteed to transform correctly under any 3D rotation or translation, so the learned policy automatically generalizes to unseen orientations without retraining.

The algorithm as a flow

What it actually does

Encode the scene into spherical coordinates

Convert the camera point cloud (a list of 3D positions) into a special mathematical space where rotations are easy to track.

Run an equivariant U-net on the encoded points

A neural network that processes each point using only operations guaranteed to respect rotations and translations, like comparing distances between points or angles between them.

Condition on the language instruction invariantly

The text (e.g., 'pick up the cup') does not rotate or translate—it is purely semantic, not tied to 3D. Special layers (iFiLM) apply it to the equivariant features without breaking the mathematical guarantees.

Predict the gripper action in the rotated frame

The output is a target hand pose and gripper opening. This action is also equivariant: it transforms exactly as the scene did.

A motion planner fills in the trajectory

A standard planner converts the target pose into a smooth, collision-free path the robot actually executes.

What the paper changes

What the paper changes

Standard transformers process observations and output actions through learned number-multiplications with no built-in respect for how 3D rotations and translations work. EquAct replaces those operations with equivariant computations—mathematical operations that are guaranteed to transform correctly when the world rotates or translates. Specifically, it uses point cloud encodings in spherical coordinates, equivariant message passing between points (comparing only rotationally-safe quantities like distances), and invariant language conditioning, so the entire policy automatically adapts to any 3D rotation or translation.

The hidden quantity

The geometric symmetry it measures

measured quantity  =  SE(3) equivariance

SE(3) equivariance is a mathematical property: if you rotate and translate the scene, the policy's predicted action rotates and translates by exactly the same amount. It is not learned—it is built in by construction. The paper measures equivariance by asking: does the policy's output transform the same way the input did?

The paper verifies this by deliberately rotating or translating test scenes and checking whether the predicted gripper pose transforms correctly. A truly equivariant policy will match the rotated action exactly, even on new orientations never seen during training. Non-equivariant baselines fail: they give wildly different actions for the rotated scene.

Why it works

Why equivariance guarantees generalization

A standard transformer is a black box: you put in an image and hand position, and it outputs actions via learned number-multiplications (matrix multiplications). Those operations do not know or care about how 3D rotations and translations should work. If the scene rotates 45 degrees, the input looks completely different in the network's eyes—it is a pattern the network never encountered—so it guesses with no principled way to adapt.

EquAct uses only operations that respect 3D rotations and translations because it is designed that way. Point clouds are encoded in spherical coordinates, and every layer computes only rotationally-safe quantities (like distances between points or angles) or transforms them in lockstep with how the input rotated (rotationally-equivariant). Because every step obeys the rules of 3D rotation, the final action must also obey them: if the scene rotates, the action rotates by the same amount, even if that exact scene orientation was never in the training data. This is not memorization; it is mathematical necessity.

Language instructions (e.g., 'pick up the cup') do not rotate or translate—they are purely semantic, independent of 3D. Special iFiLM layers apply language as a scaling and shift to the equivariant features in a way that preserves the rotation property because they only scale (multiply) the features without rotating them or reorienting them, so whatever equivariance was built into the features remains intact: scaling an equivariant quantity keeps it equivariant. The language helps the policy decide WHAT to do (which task, which strategy), but the 3D transformation is already guaranteed by all the earlier layers because every layer up to that point uses only rotationally-safe operations (distances, angles, graph message passing), so the final action is mathematically forced to transform when the input transforms.

The equivariance constraint and language conditioning

First in words:

For an equivariant policy: if scene transforms by rotation R and translation t, the action must transform by the same R and t. For invariant language conditioning: modulate the equivariant features by a scaling and shift learned from the language instruction.

Then the compact form:

c'_l = alpha_l * c_l (for equivariant features l > 0); c'_0 = beta * c_0 + gamma (for invariant features l = 0); where alpha, beta, gamma come from MLP(language_instruction)

Every symbol:

c_lthe equivariant feature at layer l
c'_lthe language-modulated feature
alpha_la learned scalar from the language instruction, applied multiplicatively
beta, gammalearned scalars for the invariant part, applied additively
MLP(language_instruction)a small neural network that reads the language and outputs scaling/shift
A tiny worked example
Initial equivariant feature at layer 5: c_5 = 0.8 (encodes part of the gripper angle).
Language instruction: 'pick up'. The MLP reads this and outputs alpha_5 = 1.2 (sharpen focus).
Modulated feature: c'_5 = 1.2 * 0.8 = 0.96 (scaled but not shifted; still rotationally sound).
Invariant feature at layer 0: c_0 = 0.5 (learned bias). Language outputs beta=1.0, gamma=0.1.
Modulated invariant: c'_0 = 1.0 * 0.5 + 0.1 = 0.6 (can shift because it is invariant).
The equivariant features scaled by language-derived alpha; invariant features offset by language-derived gamma. Equivariance is preserved.

The iFiLM layer scales equivariant features (which must transform when the world rotates) by language-derived scalars (which are invariant to rotation), and adds to invariant features, ensuring the policy respects how 3D rotations work while taking direction from language.

What can go wrong

What can go wrong

Broken point cloud encoding. If the scene is not properly converted to spherical coordinates, the equivariance guarantee falls apart because the coordinates no longer track rotations correctly. A single non-equivariant layer in the pipeline corrupts the entire contract, and the policy will fail on unseen rotations.
Language modulation applied wrong. If the iFiLM layer does not respect invariance (e.g., if it applies a rotation learned from language), the policy no longer adapts correctly to scene rotations. The language conditioning must be purely semantic, not geometric.
Gripper open/close actions. Gripper aperture does not rotate or translate. If the model tries to make it equivariant, it breaks. The paper handles this separately: aperture is predicted invariantly via iFiLM, independent of scene rotation.
Done right. When every computation layer respects how rotations work (distances, angles, graph attention) and language is applied invariantly (iFiLM), the policy is mathematically forced to work on any 3D configuration never encountered during training, because the output is forced to transform the same way the input did. No data augmentation is necessary.
What a runnable demo should prove

What a runnable demo should prove

Train EquAct on RLBench tasks at a fixed scene orientation (e.g., cup always at 0 degrees). Then test on the same tasks with the scene rotated 30, 60, 90 degrees. Measure success rate (whether the gripper reaches the target) at each rotation. Also rotate the scene in the training data by random amounts and test generalization to unseen rotations. A non-equivariant baseline (standard transformer) should fail sharply at unseen rotations; EquAct should maintain high accuracy because the policy output is forced to adapt correctly.

generalization_gap = (success_rate_at_trained_angle) - (success_rate_at_novel_45deg_rotation); lower gap means better equivariance

EquAct's gap should be <5%; a baseline transformer's gap should be >30%. This proves that equivariance, not memorization, solved the generalization problem.
