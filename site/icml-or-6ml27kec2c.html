OpenSage: Self-programming Agent Generation Engine

Let a language model build its own agent structure, tools, and memory layout instead of requiring a human to wire those pieces by hand.

Paper explainersAll themesAgents & Tool Use

Most agent development kits give a fixed shell and ask a human developer to decide how many sub-agents to use, which tools to expose, and how memory should be organized. OpenSage changes that division of labor. It lets the model construct its own working setup because different tasks need different agent structure, tool access, and memory organization.

Zero assumption version

Why hand-built agent setups hit a limit

A fixed agent scaffold works only when the developer already knows the right decomposition of the task. In practice, one task may need a planner plus a coding helper, while another may need retrieval, browsing, and long-term memory. If a human must redesign those pieces every time, agent quality and portability stay limited.

The paper argues that the development kit should expose the building blocks and let the model assemble them. That matters because the best toolset, memory structure, and sub-agent layout vary with the task, and a fixed human design can misfit many tasks.

The paper's move in one sentence. Make the model a builder of agents, not only a user of a prebuilt agent shell.

The algorithm as a flow

What it actually does

Inspect the task

Read the task and estimate what kinds of roles, tools, and memory are needed.

Generate an agent layout

Create sub-agents with different roles so that planning, execution, and checking can be separated when useful.

Assemble a toolset

Choose and configure tools that fit the task because unused tools add noise and missing tools block progress.

Organize memory

Store information in a structured hierarchy so that the agent can keep both local details and broader task history.

Run and refine

Execute the generated agent system and compare it with stronger or weaker component choices so that the effect of each design decision can be measured.

The hidden quantity

The hidden quantity

measured quantity  =  Task-specific agent design fit

The hidden quantity is how well a proposed agent setup matches a task. That includes whether the number of sub-agents is appropriate, whether the tool list covers the real needs of the task, and whether memory is organized in a way that preserves useful context without clutter.

You usually discover design fit only after trying the task. OpenSage tries to estimate it up front by letting the model synthesize a setup from the task description because a well-matched setup should reduce coordination failures and missing capability failures.

Why it works

Why this works: structure should follow task demands

Tasks differ in decomposition. A software engineering task may benefit from separate planning, coding, checking, and memory roles because each role needs a different context slice and toolset. A fixed single-agent design forces one context and one decision loop onto all tasks, which can create overload and poor tool use.

By allowing the model to build sub-agents and choose tools, OpenSage can produce a smaller or larger organization as needed. The hierarchical memory system matters because task work often mixes short-lived details with long-lived goals, and those should be stored in different places so retrieval stays useful.

A simple design utility

First in words:

You can summarize the design problem as choosing the agent setup that balances task coverage against coordination overhead. A larger system is useful only if the extra roles and tools help enough to justify their cost.

Then the compact form:

design_utility = task_coverage + memory_support - coordination_cost - unused_tool_cost

Every symbol:

design_utilityoverall value of one generated agent design
task_coveragehow well the roles and tools support the task requirements
memory_supporthow well the memory plan preserves and retrieves useful context
coordination_costextra overhead from passing work among many sub-agents
unused_tool_costcost of exposing tools that add confusion but little value
A tiny worked example
Design A: one general agent, coverage 5, memory support 2, coordination cost 1, unused tool cost 3, utility 3.
Design B: planner plus coder plus checker, coverage 8, memory support 4, coordination cost 3, unused tool cost 1, utility 8.
Design B wins because the added structure helps more than it costs.

The paper measures performance through benchmark results and ablations rather than this exact utility, but the utility captures the central tradeoff.

What can go wrong

What can go wrong

Generated structures can overgrow. If the model creates too many roles or tools, coordination can become slow and error-prone because work gets split more than the task requires.
Memory organization can drift. A structured memory system helps only if new information is stored consistently. Poor storage decisions can make retrieval noisy because useful facts are buried among low-value notes.
Benchmark gains may depend on the task family. A kit designed with software work in mind may transfer unevenly to other domains because the helpful role split and tool mix can change.
Done right. The main contribution is a cleaner interface between model and infrastructure because the model can now shape the system that will carry out its work.
What a runnable demo should prove

What a runnable demo should prove

Build three task families with different needs: a coding task, a retrieval-heavy research task, and a planning task. Compare a fixed single-agent scaffold against a system that can choose roles, tools, and memory organization from a common library. Record the generated setup for each task and the final task score.

The demo should show different designs for different tasks because one shared fixed setup should not be optimal across all three. Also log coordination cost so that the generated system is rewarded only when the extra structure pays for itself.

improvement = score_generated - score_fixed

The demo must prove that task-aware self-design helps because different tasks need different agent structures.
