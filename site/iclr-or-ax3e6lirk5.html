pFedMMA: Personalized Federated Fine-Tuning with Multi-Modal Adapter

Federated learning splits vision-language model adapters into client-specific tuning and a shared cross-modal bridge, so each site learns from its own data while all sites strengthen the connection between image and text features together.

Paper explainersAll themesLLMs & Foundation Models

When you have a vision-language model like CLIP trained on billions of internet images and text pairs, it generalizes incredibly well to new tasks with almost no examples. But deploying it to real organizations means each site has its own private images and text, often biased toward their own domain (a hospital has medical images, a retail chain has product photos). The challenge: adapt the model locally without sending data to a central server, while keeping the model's knowledge of how images and text connect from the original training intact.

Zero assumption version

Splitting personalization from generalization

A vision-language model is a pair of twins that learned to speak the same language: an image reader that turns a photo into a list of numbers, and a text reader that does the same for words. In the original training, a billion examples of matching image-text pairs tuned both twins to output nearly identical numbers for a matching pair and very different numbers for a mismatched pair. This is generalization: the model learned the abstract concept of what makes an image match its caption.

But a hospital's images and a retail chain's images are completely different domains. When you take the generic model and fine-tune it on your own data without adapting the other sites, your site's weights drift away from what works for everyone else's data. When you average the updates across all sites (the federated learning strategy) to keep things general, your local weights do not capture the quirks of your own images anymore. A naive site says: I will tune everything locally and send back my changes. A naive server says: I will average all the changes. Neither works.

The core problem: personalizing the model requires tuning weights, but sharing those tuned weights dilutes the model's original generalization, because a weight tuned for medical images is wrong for retail images, so the average is wrong for both.

The naive trap. If each client fine-tunes all the weights and sends them back, the average is not a good model for anyone. If each client only tunes a tiny personal part and everyone shares the big weights, the shared weights are tuned for someone else's data.

The algorithm as a flow

What it actually does

Inject lightweight adapters

Insert tiny trainable layers into only the top layers of both the image and text encoders, where domain-specific features live.

Split the adapter into three parts

Each site has its own down-projection (compress), its own up-projection (expand), and all sites share one middle projection that aligns image and text.

Train locally on your own data

Your site updates all three parts using only your images and text, learning domain-specific tuning and pushing the shared bridge toward your data.

Send only the shared part to the server

Skip sending your personal down- and up-projections. Send only the shared bridge, which is tiny.

Server averages the shared bridges

The server weights each site's shared bridge fairly and sends back the average, which all sites use in the next round.

What the paper changes

What the paper changes

Instead of tuning either all weights or no weights, pFedMMA tunes three separate pieces: two site-specific layers and one shared layer. The trick is deciding which of those pieces each site keeps private and which gets sent to the server for averaging.

The hidden quantity

Cross-modal alignment gap

measured quantity  =  the distance between image and text features before fusion

Before the adapters, the image reader outputs a list of numbers, and the text reader outputs a different list of numbers, even when they describe the same thing. The alignment gap is how far apart these two lists are. The original training shrunk this gap, but when you fine-tune on new domain-specific data, the gap grows because you are tuning the readers to match your data, not the original training data.

The shared projection layer directly measures and reduces this gap. It takes both lists as input, learns a transformation that brings them closer together, and uses this tighter alignment to make better predictions because when image and text outputs agree, the model can answer questions with higher confidence — if the image matches the text encoding, the answer is less ambiguous. The paper shows that this shared learning — having all sites contribute to closing the gap — keeps the gap small even as each site's data drifts, because the average of many sites' gap-reducing updates is more stable than any one site's update alone.

Why it works

Why splitting the adapter works

Domain-specific tuning and cross-domain generalization live in different places in the network. The paper observes that the top layers of the image and text encoders contain detailed, dataset-specific features (a hospital's top layers learn to recognize anatomy, a retail store's learn to recognize products). The lower layers preserve general, transferable knowledge about images and text in the abstract.

By inserting the adapters only in the top layers, you are tuning the part that is allowed to be domain-specific. By splitting each adapter into a site-specific part (down-projection and up-projection) and a shared part (middle projection), you are saying: your domain-specific tuning (how you compress and expand features) stays yours, but the bridge between modalities (how images and text align) is learned by everyone together.

Here is the causal chain: When site A tunes its own down- and up-projections on medical images, those projections drift toward anatomy-specific patterns. When site A updates the shared middle projection, it learns which image-text alignments are stable even under medical domain shift. When the server averages the middle projections from all sites, the result is a bridge tuned by all domains at once, so it works for all of them. When site A retrieves or classifies using this averaged bridge, the bridge knows how to align images and text across all domains, while the local down- and up-projections translate medical patterns into the shared representation.

Communication is efficient because the shared projection is much smaller than the full adapters or the full model.

The local training objective

First in words:

For each site, the loss is the average over your data, and you update your down-projection, shared projection, and up-projection together. The shared projection is then sent to the server, averaged with other sites, and sent back.

Then the compact form:

loss_i = mean over (x_image, x_text) in client i's data of: ||shared_proj(down_proj_i(encode_image(x_image)) + up_proj_i(decode_image(z))) - shared_proj(down_proj_i(encode_text(x_text)) + up_proj_i(decode_text(w)))||^2

down_proj_iclient i's compression layer (site-specific, trainable)

A tiny example with two sites
Site A (hospital): image number-lists and text number-lists start 12 units apart.
Site A trains its down/up-projections and the shared projection. The shared projection learns: squeeze image to 3 units, squeeze text to 3 units, align them to 1 unit apart.
Site B (retail): image number-lists and text number-lists start 15 units apart (different domain).
Site B trains using the same shared projection. Its down/up-projections compress retail patterns. The shared projection adapts: now squeeze image to 4 units, squeeze text to 4 units, align them to 1.5 units apart.
Server averages: shared projection now squeezes to 3.5 units, aligns to 1.25 units apart.
Result: both sites use one averaged bridge, each keeps their own domain-specific compression. Neither site's data alone shaped the bridge; both did.

Only the shared projection is averaged, so it learns from all domains at once and works reliably for all of them. The down/up-projections stay personal.

What can go wrong

What can go wrong

Inserting adapters in the wrong layers. If you insert adapters in the low layers where general knowledge lives, you will tune away the model's original generalization. The paper inserts only in the top three layers where domain-specific features live, leaving lower layers frozen to preserve shared knowledge.
No shared projection at all. If each site only trains its own down/up-projections and does not share anything, then each site's image and text encoders drift apart independently, and the model's alignment knowledge is lost.
Averaging everything including personal projections. If you average the down- and up-projections, you are averaging domain-specific tuning, which destroys each site's personalization. The paper avoids this by averaging only the shared bridge.
Done right. Each site trains all three components on its own data, but only sends the shared projection to the server. The server averages just that component and sends it back. Personal tunings stay personal because each site keeps its down/up-projections locally, so personalization is protected. The shared bridge gets stronger from all domains because every site's update to it is included in the average, so the bridge learns alignments that work across all the different kinds of data it will meet.
What a runnable demo should prove

What a runnable demo should prove

Simulate three or four sites with visibly different data distributions (for example, images of medical scans, product photos, and outdoor scene photos, paired with natural language descriptions of each). Initialize a pretrained vision-language model (such as CLIP). Insert multi-modal adapters into the top layers of both encoders. Run federated training for several rounds, and at each round, measure two things: accuracy on each site's own test set (personalization) and accuracy on a held-out unseen class that appears in no site's training data (generalization).

personalization_score = average of (accuracy on Site A's own classes + accuracy on Site B's own classes + ... ); generalization_score = accuracy on unseen classes; trade_off_ratio = generalization_score / personalization_score (higher is better when both are high)

The demo must show that personalization does not collapse (each site still predicts well on its own data, which happens because personal down/up-projections are trained locally and stay local) and that generalization to unseen classes improves as more sites contribute to the shared bridge, because a bridge tuned by multiple domains learns alignments that work for unfamiliar data too.
