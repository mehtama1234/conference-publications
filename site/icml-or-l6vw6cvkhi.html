TaskLoom: Weaving Knowledge Across Tasks in World Models

By clustering tasks based on their learned world patterns and sharing knowledge hierarchically within and across clusters, TaskLoom helps a single model learn multiple robot control tasks faster.

Paper explainersAll themesReinforcement Learning

A robot needs to learn many tasks: pushing, grasping, reaching. Normally each task learns its own world model (a mental simulation of how the world responds to actions). TaskLoom clusters tasks that learn similar patterns, then shares that knowledge within clusters and across them. This hierarchical sharing cuts down learning time because related tasks can teach each other.

Zero assumption version

The robot learns slowly because each task trains alone

A robot must master many tasks: reaching, pushing, picking. Today, each task learns its own world model — a prediction engine that learns 'if I move my arm this way in this scene, the world will look like that.' Building each model from scratch is slow because each task collects only its own experience.

A naive first try: train one shared model on all tasks at once. But this fails because pushing and reaching have opposite world patterns — pushing changes pixels a lot, reaching changes joint angles. A single model trained on both gets confused, pulling its learning focus halfway between both tasks instead of mastering either.

The core problem: different tasks have different clues about how the world moves. Without seeing which tasks belong together, a shared model spreads its learning focus too thin.

TaskLoom groups related tasks and shares knowledge hierarchically. Tasks that learn similar world patterns share fine details within their group; all groups then exchange the big-picture patterns.

What the paper changes

What the paper changes

TaskLoom changes how a world model's internal weights are trained. Instead of one model per task or one model for all tasks, it trains a shared set of weights, but the sharing is selective: it happens first within clusters of related tasks, then across clusters. This two-stage selective sharing is the single change.

the object it moves  =  internal weights of world models
The hidden quantity

Gradient direction: the clue for grouping

measured quantity  =  gradient direction during learning

Gradient direction is the pattern of which internal weights change most when a task learns. If two tasks have similar gradient directions, their world models are learning the same things. TaskLoom measures this direction for each task and uses it as a fingerprint to group tasks.

The paper estimates gradient direction by tracking which weights grow or shrink the most as each task's world model trains. Tasks with similar patterns (reaching and lifting both move arms, so their gradients align) cluster together. Tasks with opposite patterns (pushing moves pixels, reaching moves joints, so gradients point different ways) go to different clusters.

Plain reading. The paper looks at which weights shift most as each task learns its world model, treats that shift pattern as a signature, and groups tasks with similar signatures.
Paper reading. TaskLoom measures which weights shifted most during learning for each task (the learning signature), then groups tasks with similar signatures. When tasks have aligned signatures, averaging their weight updates adds up instead of cancelling (reaching nudges weights by +0.3, lifting nudges by +0.2, average is +0.25, all signal preserved), while cross-cluster averaging weakly pulls (reaching nudges +0.3, pushing nudges -0.8, average is -0.25, mostly cancels). This selective averaging, strong within groups and weak across, makes grouped sharing effective and cross-group sharing safe.
Why it works

Why grouping by gradient makes learning faster

The core reason: when two tasks have the same gradient direction during learning, it means they are discovering the same parts of the world. If reaching and lifting both nudge the arm-angle weights hard (high gradient), they learn alike. Sharing their weights means each task sees the other's examples, doubling the data.

Within a cluster, weights are updated by the average gradient of all tasks in that cluster. This averaging works because the tasks point in the same direction — no cancellation, just reinforcement. Between-cluster sharing is coarser (only backbone weights, not fine details) because tasks in different clusters point different ways. If you averaged their gradients, you would cancel out.

The payoff: a robot learning to reach gets to borrow the pushing task's examples of how gravity works, because both tasks learn to predict gravity. A shared backbone helps all tasks because gravity affects all of them, so the backbone's shared gravity model has more data and trains faster. This hierarchical structure is faster than training one model per task (no reuse means each task collects data in isolation) and more stable than one model for all tasks (shared model gets pulled by conflicting signals when tasks want opposite predictions, causing oscillation).

Math after the picture

The update rule for shared weights

First in words:

new weight equals old weight minus learning-rate times the average gradient across tasks in the cluster, plus a small term for backbone sharing across clusters

Then the compact form:

w_new = w_old - lr * (avg_grad_in_cluster + alpha * avg_grad_across_clusters)

Every symbol:

w_oldthe weight's current value
w_newthe weight's updated value
lrthe learning rate (how big each update is)
avg_grad_in_clusteraverage gradient direction of tasks in this cluster
avg_grad_across_clustersaverage gradient direction of all tasks
alphahow much cross-cluster sharing to do (a dial from 0 to 1)
A tiny worked example
Cluster A has 2 tasks: reaching (gradient = 0.4) and lifting (gradient = 0.3).
Cluster B has 1 task: pushing (gradient = -0.8, opposite direction).
Update weight w for task reaching (in cluster A):
avg_grad_in_cluster = (0.4 + 0.3) / 2 = 0.35
avg_grad_across_clusters = (0.4 + 0.3 - 0.8) / 3 = -0.033
w_new = w_old - 0.01 * (0.35 + 0.5 * -0.033) = w_old - 0.01 * 0.334 = w_old - 0.00334
Notice: within-cluster term is strong (0.35), cross-cluster term is tiny (barely moves). Clusters point different ways, so backbone sharing is weak.

The two-stage sum means each weight gets pushed by its own cluster first (strong signal), then nudged by all clusters (weak signal to avoid cancellation).

What can go wrong

What can go wrong

Gradient clustering chooses wrong groups. If gradients are noisy or tasks are mid-training, the cluster assignment might be wrong. A reaching task and a pushing task might get grouped if their gradients happen to align early. The fix: wait for tasks to train before clustering, or re-cluster periodically.
Cross-cluster sharing backfires. If tasks in different clusters truly have opposite world models, sharing backbone knowledge introduces conflict. Both reaching and pushing try to steer the backbone. If they push equally hard in opposite directions, the backbone learns nothing.
Too many clusters. If clustering is too strict, you end up with many tiny clusters, each with few tasks. Within-cluster sharing becomes weak, and you lose the reuse benefit.
Done right. Cluster carefully, verify that grouped tasks have aligned gradients before training, tune the balance between within-cluster and across-cluster sharing (the alpha dial), and re-check clusters as training progresses.
What a runnable demo should prove

What a runnable demo should prove

Build a small environment with 4 tasks: reach-target, grasp-object, push-object, slide-door. Train three models: (1) one model per task (no sharing), (2) one model for all tasks (full sharing, baseline), (3) TaskLoom with gradient clustering. Measure final performance (success rate) and learning speed (episodes to reach 70% success).

learning_speed_improvement = (independent_episodes_to_70pct - taskloom_episodes_to_70pct) / independent_episodes_to_70pct * 100%

If TaskLoom works, the gradient-clustered model reaches 70% success 30–50% faster than independent training (because shared within-group data accelerates learning) and more stable than the single-model baseline (because grouped tasks don't pull in opposite directions), proving intelligent grouping beats both isolation and forced mixing.
