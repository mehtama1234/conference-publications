Datasets & Benchmarks & Evaluation

How do you design a fair, honest test that tells you whether an AI system can really do what you need it to do?

← All themes explainedField mapMathematicsAll explainers
What this whole area is about

Before you can tell if an AI system is good at something, you have to decide what "good" means and build a test for it. This theme is about exactly that: the work of creating datasets and benchmarks that measure what AI models can actually do. Think of it like designing an exam that tells you whether a student really understands calculus or just memorized answers. Researchers in this area build tests for everything from whether a language model can reason step-by-step through math problems, to whether a vision model can look at a picture and understand what it sees, to whether an agent can handle a real-world cybersecurity task.

The hard part is that AI keeps doing new things. Five years ago, nobody needed to test whether a model could write code or help diagnose a disease, because models couldn't do that yet. Now they can. So researchers are constantly chasing: building new tests for new capabilities as they emerge. It is also deeply tricky to build a test that actually tells you whether a model is truly capable or just good at a specific type of problem. If your test is too narrow, maybe your model looks smart on that one test but falls apart in the real world. If your test is too loose, you might think a model is working when it is only partly working, or you might miss when it is confidently wrong.

Researchers tackle this from many angles. Some build datasets for brand-new abilities that barely existed last year, like agents solving real-world planning problems or models reasoning through complex steps. Others focus on checking whether models handle the real world—testing vision models on messy, natural photos instead of clean datasets, or testing language models across many languages, not just English. Still others create stress tests: can you fool the model with tricky inputs? Does it stay confident when it should be uncertain? Can you find hidden biases in how it treats different groups? A separate line of work focuses on the science of testing itself—making sure your benchmarks actually measure what you think they measure, that results are reproducible, and that you can trust the numbers.

This matters because AI is moving from research labs into real decisions: loans, medical diagnosis, hiring, security. If you deploy a system you have not properly tested, you might discover too late that it fails exactly when it matters most. The benchmarks built here become the standard language researchers use to talk about progress.

Subtheme

Designing Tests for Brand-New AI Abilities

Every few months, AI models gain abilities no one tested before because machine learning keeps advancing and researchers build bigger, better-trained models. A model might suddenly be able to help you write a program, or reason through steps of a proof, or assist in scientific discovery, or handle medical or legal cases. Researchers who work on this subtheme build the tests for these brand-new skills, because old tests do not measure what these new abilities need measured. You have to invent a new way to measure something that barely existed in AI a year ago.

Why is this hard? Because new capability means new kinds of questions to ask. When researchers realized models could code, they had to design tests that checked not just whether code syntax is right, but whether it actually solves the problem, whether it is efficient, whether it handles edge cases. When models started helping in science—suggesting new molecules or designing proteins—researchers had to create benchmarks that capture what real scientific progress looks like, not just pattern matching. The papers in this group do that grunt work: they design, collect, and validate datasets that measure emerging skills honestly.

The approaches vary widely. Some papers gather real-world examples: actual coding tasks from open source repositories, real chemistry problems, actual cybersecurity scenarios. Others craft synthetic tests carefully designed to probe a specific weakness or skill, the way you might create math problems of increasing difficulty to see where a student starts to struggle. What ties them together is that they all build toward the same goal: once a benchmark exists and researchers agree it is trustworthy, everyone can use it to compare progress.

Subtheme

Testing What AI Can Actually See and Understand

Vision-language models—systems that look at images and answer questions about them—sound simple in theory: show the model a picture, ask what it sees, check if it is right. But in practice, vision understanding is far trickier than it seems. A model might recognize objects but miss spatial layout; it might handle photos taken in studios but fail on blurry, messy real-world images; it might spot a dog but not understand whether the dog is happy or scared, chasing or being chased. This subtheme is about building tests that expose what vision models can and cannot actually do.

The core difficulty is that human vision understanding is so automatic and intuitive that we forget how much is involved. Understanding a picture means parsing objects, their positions, colors, sizes, actions, relationships, context, and emotions all at once. Tests have to slice through that complexity and ask: does the model truly see spatial reasoning, or just memorize patterns? Can it understand design aesthetics, or just label surfaces? Does it work on ancient pottery the same way it works on modern photos? The papers here build benchmarks that test these specific kinds of understanding, often catching places where models that seem impressive at first actually fail on details humans find natural.

Researchers build these benchmarks by carefully collecting images paired with questions that probe a specific skill. Some focus on spatial reasoning—asking how objects relate to each other in 3D space. Others test visual understanding of domains people have studied for centuries: art history, architecture, ancient objects. Still others gather real, messy images from the internet or cameras rather than clean studio photos, to test whether models work in the wild. The goal is to move beyond generic vision tests toward benchmarks that measure real-world visual understanding.

Subtheme

Evaluating Agents and Reinforcement Learning in Real Settings

An agent is a system that takes actions over time to solve a problem. It might be an AI playing a game, a robot trying to pick up an object, a program trying to defend against a cyberattack, or a planner booking flights and hotels to get you somewhere. Testing an agent is not like testing a model that just answers one question. You have to simulate a whole sequence of decisions and see whether the agent reaches its goal. This subtheme is about building environments and benchmarks where researchers can measure how well agents learn and act.

The difficulty is that real-world agent problems have delays, surprises, and cascading consequences. If an agent makes a mistake, the world changes in ways it has to recover from. If it is learning, it might be exploring and failing over and over before figuring things out. Benchmarks have to test both: can the agent learn from trial and error (the classic reinforcement learning problem), and can it handle the kind of complex, long-term planning humans face? A power grid agent has to keep the system stable while responding to outages; a travel planner has to route through real constraints (weather, prices, time zones); a cybersecurity agent has to detect and respond to attacks in a realistic network. Each domain has its own twists that make simple simulation tests inadequate.

The papers in this area build two kinds of testing environments. Some create detailed simulators of real domains—power grids, network security, travel booking—where agents can be trained and tested without real-world risk. Others propose metrics that measure not just whether an agent succeeded, but how well it adapted, whether it learned over time, and whether it handled the unexpected. The goal is to move from testing agents on toy problems to testing them on problem-spaces that feel like the real world.

Subtheme

Detecting When Models Are Wrong or Biased

A model can be confident and completely wrong. It might tell you a dog is a cat with 99% certainty. It might give different answers to the same question asked in different ways, even though any human would recognize they are the same. It might refuse to help a person with one name but help happily when the name changes, because it absorbed preferences from training data where one group was treated differently than another. This subtheme is about building tests that catch these failures: model uncertainty, inconsistency, what happens when you trick the model with small changes, and biases the model's creators never noticed.

Why is detecting wrongness hard? Because a model's internal confidence score (how sure it says it is) often has almost nothing to do with whether it is actually right. A model trained on biased data might genuinely believe something false. If you only test a model on clean, normal inputs, you might miss that it breaks on edge cases—unusual spellings, dialogs with strange background assumptions, images with weird lighting. And bias is sneaky: a model might behave identically on similar inputs except that one involves a person of a particular group, revealing invisible discrimination that no human explicitly programmed in. Researchers need tests that can catch these hidden problems before deployment to the real world.

Researchers build benchmarks to catch these problems in multiple ways. Some create stress tests: adversarial examples designed to fool the model, or tricky rewording of the same question to see if the model contradicts itself. Others gather data specifically about domains where bias is known to be a problem—hiring, criminal justice—and measure whether the model treats everyone fairly. Still others build datasets to test a model's calibration: is it right more often when it is confident, and wrong when it is uncertain? By running these tests before deployment, researchers can find and sometimes fix problems before the model is released into the world.

Subtheme

Making Sure AI Reasons Correctly Step by Step

When you ask an AI to solve a math problem or debug code or work through a logic puzzle, you do not just care whether it gets the right answer. You also care whether it actually reasoned through it step by step, the way a human would, or whether it just pattern-matched an answer from its training data. This is especially important for high-stakes problems: if a model recommends a medical treatment, you want to know whether it traced through the logic or just guessed based on surface features. This subtheme is about building tests for genuine step-by-step reasoning.

The core challenge is that it is hard to know what the model is really thinking. A model might write out steps that look right, but they might be a post-hoc story it is inventing after having already settled on an answer. You need benchmarks that actually test whether reasoning is genuine: Can the model catch its own mistakes partway through? If you change a small detail in the problem, does it redo the reasoning, or does the answer stay the same? Does the reasoning trace the logic faithfully, or does it skip steps and hide confusions? These tests require creating problems where the reasoning path is as important as the final answer, and where you can verify the model actually followed that path.

Researchers tackle this by building datasets where the reasoning steps matter. Some gather multi-step math or logic problems where the intermediate reasoning can be checked. Others create benchmarks for domains like theorem proving or scientific reasoning, where you can verify whether the logic is sound. A few build adversarial tests: change one number in a math problem and see if the model catches where its earlier steps no longer apply. The goal is to move past just measuring right answers toward measuring genuine reasoning.

Subtheme

Compressing and Reusing Data Efficiently

Building datasets is expensive and time-consuming. Collecting millions of examples, labeling them, cleaning them costs enormous effort. So researchers in this subtheme ask: can you accomplish the same goal with fewer examples? Can you take a large, messy dataset and distill it into something smaller and cleaner that teaches a model the same essential things? Can you take a dataset built for one purpose and reformat it so it works for another? The goal is to get more learning value from less data.

Why does this matter? Training a large AI model on a huge dataset is expensive—it costs time and electricity. If you can achieve similar learning with less data, you save time and money because you need fewer computers running for fewer hours, and you can try new ideas faster because each experiment finishes sooner. Also, sometimes you have access to relevant data but in the wrong format or mixed with lots of noise. If you can transform or compress it smartly, you unlock data that would otherwise be useless. The challenge is that you cannot just randomly throw data away or simplify it—if you lose important examples, the model will learn less. You have to understand which examples matter and which are redundant or harmful.

The papers here take different approaches. Some use machine learning itself to identify which examples are most valuable for training, then remove the rest. Others use data distillation: run a learning process that compresses a large dataset into a much smaller but representative synthetic dataset that teaches almost as much. Still others focus on data cleaning: taking a messy dataset and keeping only the high-quality examples, or fixing mislabeled data. The work matters because it makes AI training faster and cheaper, and gets more value from data that already exists.

Subtheme

Checking How Well Models Handle Multimodal Content

Real-world information is messy and mixed. A news article might come with photos. A scientific paper has text, equations, graphs, and images. A video has sound and motion and visuals. A table of data is a different kind of input than a paragraph. This subtheme is about building tests for how AI models handle information that mixes different types together—multimodal content.

The challenge is that handling mixed types requires coordination. A model has to read text, understand images, parse graphs, listen to audio, and then combine all of that to answer a question or complete a task. It is not enough for a model to be great at images and also great at text if it cannot connect them. A model might see a photo and read a caption but completely miss how they relate. It might misunderstand the scale of a graph or fail to notice that the text contradicts the visual data. Building tests for this coordination is hard because you have to measure whether a model genuinely integrated information across modes or just processed each mode separately and guessed a combined answer.

Researchers build multimodal benchmarks by gathering data that naturally mixes types. Some focus on videos with sound and visual understanding. Others test models on documents with mixed text and images, like research papers or web pages. Still others create specific tasks that require coordination: "based on this table and this description, what is the answer?" or "watch this video and this happens; describe the next second." The goal is to measure whether models can truly work with mixed information, which is essential as AI moves toward handling real-world tasks.

Subtheme

Making Testing Fair and Scientifically Sound

A benchmark that is flawed in its design can lead you to the wrong conclusions. If you score a benchmark in a biased way, you reward some kinds of answers over others unequally. If your test data happens to match one model's training style better than another—such as lots of examples exactly like its training data—that model will look better even if it is not genuinely better overall in real situations it has not seen. If your benchmark is too easy or too hard, you might think a model is better or worse than it really is, because easy tests hide the real limitations while hard tests hide genuine progress. This subtheme is about the scientific process of benchmarking itself: making sure tests are fair, reproducible, and actually measure what they claim to measure.

The difficulty is subtle. Benchmarks can fail in ways that are not obvious. Maybe your benchmark has data leakage: examples that accidentally got into both training and test data, which makes models look better than they are because they memorized that specific data. Maybe you scored answers in a way that favors certain models by accident, such as giving credit for partially correct answers when one type of model tends to be partially correct while another type tends to be very wrong or very right, which means the scoring rules accidentally help one model family. Maybe your test is so hard that all models fail equally, telling you nothing about relative progress, or so easy that all models pass, hiding real differences. Maybe you reported the top score without showing all the scores across models, giving a misleading picture. Scientific benchmarking requires careful thinking about these details.

Researchers working on this focus on fundamentals of good testing: How should you split data between training and testing to avoid leakage? How should you measure fairness so that results are not biased toward one model or approach? How should you report results to be honest and reproducible? How should you track whether a benchmark is actually useful or whether models have learned to game it in ways that do not transfer to real-world tasks? The papers here often reveal that popular benchmarks have these problems, which means people using those benchmarks may be making the wrong conclusions about which models are actually better. Researchers then propose concrete changes to benchmark design—different data splits, different scoring rules, different reporting practices—that prevent these errors. This work is less flashy than building a new benchmark, but it is essential for honest science.

Subtheme

Testing Specialized Reasoning and Knowledge

Some domains require not just general intelligence but deep background knowledge and precise reasoning. You cannot diagnose a rare disease without understanding medicine. You cannot prove a theorem without logic. You cannot synthesize a stable drug without chemistry. This subtheme is about building benchmarks for these specialized domains where models have to show they actually understand the field, not just pattern-match.

The challenge is that general-purpose benchmarks miss domain-specific nuance. A medical benchmark cannot just ask "which drug treats this disease?" because context matters enormously: the patient's age, allergies, other medications, kidney function, pregnancy status. A chemistry benchmark cannot just ask "does this molecule exist?" because stability and synthesis routes matter. A law benchmark cannot just ask "is this legal?" because precedent and jurisdiction and interpretation matter. Building benchmarks for these fields requires collaboration with experts who understand what real reasoning looks like in that domain.

The papers here tackle narrow domains: medical diagnosis, chemistry and molecular design, law and legal reasoning, theorem proving in formal mathematics, biological sciences. Each team builds tests that capture what it means to truly understand that field. Some use real examples from practice: actual medical cases, actual legal documents, actual chemistry papers. Others create synthetic tests carefully designed by domain experts to probe specific understanding. The goal is to move past generic benchmarks toward specialized evaluation that honors the actual difficulty and knowledge required in each field.

Subtheme

Checking If Models Understand Across Languages and Time

A model trained mostly on English text might be great at English but terrible at Chinese or Arabic. A model trained on text from 2020 might not understand events or slang from 2024. A model tested on single questions might fail when you ask it a series of questions that build on each other—holding context across a long conversation. This subtheme is about building benchmarks that test whether models work across languages, time periods, and long sequences.

The difficulty is that language and knowledge change. The same word means different things in different languages and contexts. Knowledge becomes outdated: facts true in 2020 might be false in 2024. Long conversations are hard because models have finite memory and processing capacity, and they have to track who said what, what was decided, what still matters. Building tests for these challenges means creating benchmarks in many languages, testing on recent events and evolving language use, and creating long-form conversational tasks where context actually matters.

Researchers approach this in several ways. Some build multilingual benchmarks: the same task in many languages to see whether a model works equally well across language families. Others create temporal benchmarks: tests that require knowing when an event happened or what the current date context is. Still others build conversation-based benchmarks where a model has to maintain context over many turns, or time-series benchmarks where a model has to predict or understand sequential patterns. The goal is to measure how well models work across the dimensions that matter most in real-world use: language, time, and long-form reasoning.
