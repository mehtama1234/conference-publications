HiMe: Hierarchical Embodied Memory for Long-Horizon Control

Split a robot's brain into three speeds: a fast hand executor, a quick-memory watcher, and a slow strategic planner, each doing what it does best without slowing the others down.

Paper explainersAll themesRobotics & Control

A robot following a vision-language model (a system that reads images and language and outputs robotic actions) can handle simple immediate tasks, but breaks on complex jobs that require remembering what happened five steps ago and planning ahead. Current approaches face a nasty tradeoff: a slow thinking system can reason deeply but cannot react fast enough to catch falling objects; a fast system executes smoothly but forgets context. HiMe fixes this by splitting the robot brain into three separate, coordinated pieces that work at different speeds.

Zero assumption version

The real robot gets stuck between fast and smart

A robot that uses a vision-language model — a neural network trained to read camera images and understand language instructions — can perform immediate manipulation tasks reasonably well. But real robotic jobs are rarely one-shot. A robot picking objects off a shelf in a crowded bin needs to remember that the tall cylinder was just moved, needs to reason about which item will balance the next stack, and needs to plan a sequence of moves across multiple steps.

A naive robot would re-run its language model on each frame, asking it what to do right now. This breaks in two ways. First, the model processes images slowly — it might take half a second to think about one moment, too sluggish for closed-loop control when objects are moving. Second, the model has no memory. Each decision is made from scratch, ignoring the last ten decisions. A beginner tries to patch this by feeding the model a long history of images, but now it becomes even slower. You have traded memory for crippling latency, and the model still does not reason — it just sees more pixels.

The bind. Build memory and reasoning into a fast-acting robot without making the reflexes sluggish.

The algorithm as a flow

What it actually does

Executor runs the fast loop

Every 16 milliseconds, take the latest image and memory summary, output the next motor command.

Sentry monitors and updates

Every 100 milliseconds, read what the Executor just did and what the camera shows now; update the short-term memory.

Planner thinks ahead slowly

Every second or more, rewrite the long-term strategy based on the task, history, and current scene.

Memory system stores what matters

A semantic database of visual features and facts; Sentry adds, updates, or deletes entries as the robot learns.

No wait-loops; all three run parallel

Executor never pauses for Planner; information flows asynchronously between the layers.

What the paper changes

What the paper changes: the architecture itself

Instead of a single neural network making all decisions, HiMe replaces it with a three-layer hierarchy: a low-level reactive controller (the Executor) that acts without thinking, a mid-level buffer (the Sentry) that tracks immediate state, and a high-level deliberative system (the Planner) that reasons about goals and adjusts long-term strategy. The three layers communicate asynchronously, so the Executor is never held up by the Planner's slow computation.

The hidden quantity

The hidden quantity: memory coherence across time

measured quantity  =  Memory consistency: how fresh and aligned is the stored knowledge?

As a robot acts, its memory becomes stale — the world changes, the robot's belief about what is where drifts from reality. The paper measures memory coherence as the fraction of stored facts (visual features and semantic labels) that still match what the camera sees right now. A fact about a red block might be true for 2 seconds but false after the block rolls away.

HiMe estimates coherence by comparing the robot's stored memory against newly observed features. When coherence drops below a threshold, the Sentry marks entries for deletion or update. This hidden quantity is critical because a robot acting on stale memory will make mistakes — a stored fact that was true five seconds ago is useless now.

Why it works

Why it works: three brains at different tempos never jam each other

A single neural network that does perception, memory, planning, and control is like one person trying to answer the phone, check email, think about strategy, and drive a car all at once. The bottleneck is the slowest task — reasoning is slow, so the whole system slows down.

HiMe's insight is to run three independent processes. The Executor (the fast reflex layer) reads the camera and memory summary at 60 frames per second and outputs motor commands. It is small and reactive — no reasoning, just learned reactive patterns. The Sentry (the watchdog, running 10 times per second) compares what the Executor is doing against what the camera now shows and updates the shared memory: if the gripper is now holding something, record it; if an expected object is gone, delete that fact. The Planner (running once per second) reads the entire history, the current memory state, and the task description, then rewrites the long-term strategy and goals. It outputs new directives to the Executor — not motor commands, but abstract intentions like "pick up the blue block."

Most importantly, none of these wait for the others. The Executor moves on every 16-millisecond tick regardless of whether the Planner has finished its reasoning. This is why the architecture works: you gain both speed and depth by not forcing them to share a bottleneck. A reaction happens in milliseconds; a plan updates every second; memory stays coherent because the Sentry is always tidying up.

The coherence update rule

First in words:

For each stored memory entry, the coherence is the dot product (overlap) of the stored feature vector and the new camera feature, divided by the product of their lengths to get a normalized score between zero and one. If coherence drops below a threshold, delete the entry.

Then the compact form:

coherence_i = (stored_feat_i · new_feat_i) / (||stored_feat_i|| * ||new_feat_i||) ; if coherence_i < theta then delete_i

Every symbol:

stored_feat_ithe visual feature vector (numbers describing what we thought we saw) stored in memory from step i
new_feat_ithe visual feature vector extracted from the current camera frame at the same location
·dot product: multiply each pair of numbers and add them up
||...||length of the vector (think of it as total magnitude)
thetathe coherence threshold (typically 0.7 to 0.9); below this, the memory is too stale to trust
A tiny worked example
Suppose the Executor stored a red-block feature (a list of three numbers [0.9, 0.2, 0.1] describing the block: bright red, square shape, medium height).
One second later, the camera shows the block in a new position; Sentry extracts the new feature [0.85, 0.25, 0.05] — same block, slightly different angle and partly occluded.
Dot product: 0.9*0.85 + 0.2*0.25 + 0.1*0.05 = 0.765 + 0.05 + 0.005 = 0.82
Magnitude of stored: sqrt(0.81 + 0.04 + 0.01) = 0.937; magnitude of new: sqrt(0.7225 + 0.0625 + 0.0025) = 0.872
Coherence = 0.82 / (0.937 * 0.872) = 0.82 / 0.817 = 1.00 (nearly perfect match; keep the entry).
But if the new feature were [0.1, 0.1, 0.9] (the block rolled away and rotated), coherence = 0.11 / 0.862 = 0.128 (far below 0.7; delete it).

This coherence score tells the Sentry which memories are living lies and which still reflect the real world.

What can go wrong

What can go wrong

Memory becomes corrupt if Sentry update rate is too slow. If the Sentry only updates every second but the world changes every 100 milliseconds, the stored facts become contradicted by observation. The robot acts on false beliefs. Fix: tune the Sentry update frequency to match the task speed.
Coherence threshold set wrong creates thrashing. If theta is too strict (e.g., 0.95), useful facts get deleted too quickly and the robot forgets everything. If theta is too loose (e.g., 0.3), stale facts persist and mislead the Executor. Fix: use a task-specific threshold or let the Planner adjust it based on recent errors.
The Executor and Planner disagree about strategy. If the Planner revises its intention while the Executor is mid-action, the robot may commit to an old goal and fail the new one. Fix: the Planner should only update intentions when the Executor reaches a decision point (e.g., after a gripper action completes), not arbitrarily.
Done right: memory coherence is checked on every Sentry tick. A well-tuned hierarchy updates memory frequently enough that facts stay accurate, uses a coherence threshold matched to the task, and synchronizes goal updates with action boundaries, so the three layers work toward the same goal.
What a runnable demo should prove

What a runnable demo should prove

A concrete demo builds a simulation of a robot arm in a cluttered bin with 10 small objects. The task is a 15-step sequence: "Move the red block to the left, then the blue block on top of it, then rotate the entire stack 90 degrees." Run the naive flat model (a single network that reads a stacked history of the last 10 frames) and HiMe side-by-side. The flat model slows down to 2 frames per second and fails on step 8 (it re-reasons too slowly and drops the block). HiMe runs the Executor at 30 frames per second (tight closed-loop control), updates Sentry every 50 milliseconds (fast memory tracking), and Planner every 500 milliseconds (deep reasoning). Both models use the same underlying vision-language encoder; the difference is purely in the architecture.
