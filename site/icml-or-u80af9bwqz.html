MoVie: Multimodal Video Compression with Text Guidance

Instead of blindly compressing motion, understand the scene with text and compress only what matters to human eyes.

Paper explainersAll themesGenerative Models & Diffusion

Video takes enormous space. A raw hour of HD video is gigabytes. Current compression throws away as much data as possible without breaking motion math. But movies have scenes with meaning: a talking head, a sunset, people moving through a room. This paper adds text descriptions to the compression pipeline — a model that understands what is happening in a scene can throw away the right pixels and keep the important ones.

Zero assumption version

Why motion-only compression leaves viewers unhappy

Traditional video codecs, like those in your DVR, focus on one job: track how pixels move from frame to frame, then throw away redundancy in that motion. If a camera pans left, the codec predicts the next frame by sliding pixels sideways. It works mathematically — the error is tiny. But human vision is not mathematical. A person watching a sunset cares about golden light, not perfect motion. A talking head needs recognizable faces, not pixel-perfect accuracy. If the codec wastes bits on motion math it could spend on skin tones or eyes, the video looks dead.

Deep learning video codecs tried to improve this by learning smarter motion prediction. But they still treat every pixel equally: save bits on motion, lose detail everywhere. A person in dark clothes walks across a bright doorway. The codec might perfectly predict where the person goes, but trash the lighting change that makes the scene feel real. The viewer's brain screams that something is wrong, even if the math is correct.

The problem. Compression guided only by motion math ignores what humans see as important in a scene.

The algorithm as a flow

What it actually does

Step 1: Read the scene

Text description (or auto-generated caption) enters the model alongside pixels.

Step 2: Fuse meaning into features

Two modules merge the text into the spatial map: one extracts what matters, one injects it back into pixel predictions.

Step 3: Predict motion with context

The model predicts the next frame not just from motion but from what the scene is about.

Step 4: Allocate bits smartly

An entropy model says: face details need 100 bits, background needs 10. Spend accordingly.

Step 5: Use history wisely

The codec remembers earlier frames, not just the one before, giving the prediction model more clues about what pixels will do next, so it predicts more accurately with fewer bits.

What the paper changes

The one thing the paper changes

Instead of computing which pixels move, the model reads text about the scene and computes which parts of the image humans will actually look at. It then guides the compression to spend bits where humans look and save bits where they do not. The object is the map of importance (which pixels matter) — from pure motion-math to scene-aware importance.

the object it moves  =  semantic importance map
The hidden quantity

The hidden quantity: perceptual importance

measured quantity  =  perceptual importance score

Every pixel or region in a video frame has a hidden score: how much does a human viewer care if this part is blurry? The paper names this perceptual importance. A sharp face in close-up has high importance; a blurred tree in the background has low importance. Old codecs ignore this — they treat all pixels as equally important.

MoVie estimates perceptual importance by fusing text descriptions with the visual features. The text module says what the scene is about (talking head, sunset, crowds). The visual module maps that back onto the frame — brightening the importance score for the head and dimming it for the background. The codec then asks: how many bits do I need to keep this importance score high? A high-importance region needs more bits; a low-importance region survives on fewer.

Why it works

Why it works: understanding changes where you spend bits

Old codecs spend effort on a wrong goal. They try to predict the exact pixel values in the next frame by tracking motion. But prediction error alone does not match human vision. A person notices when a face becomes unrecognizable; they do not notice when a wall is a few shades off.

MoVie flips the goal: instead of trying to predict every pixel perfectly, it asks what humans care about and protects that. The text description (e.g., talking head, sunset scene, crowds in a park) tells the model what kind of scene this is. The visual fusion modules then map that semantic understanding onto the actual frame — this region is a face (protect it), this is a wall (compress it). When the entropy model decides bit allocation, it listens: high perceptual importance regions get more bits to stay sharp. Low-importance regions get fewer bits and blur. The viewer watches the protected face stay perfect and ignores the blurry wall. File size drops because the codec stopped wasting bits on invisible blur.

This works because human vision evolved to prioritize faces, expressions, and scene semantics — not to be a perfect pixel-prediction machine. By aligning compression priorities with actual human priorities, MoVie saves bits where it matters.

Allocating bits by importance

First in words:

Total bits needed equals the sum of bits for each region, where a region's bits are the entropy (randomness) of its pixels times how important that region is.

Then the compact form:

total_bits = sum_r [ H(pixels_r) / importance_r ]

Every symbol:

total_bitscompressed file size in bits
rone spatial region or channel group
H(pixels_r)entropy: how unpredictable the region is
importance_rperceptual importance score (higher = protect more)
A tiny worked example
Region A (face): entropy 20 bits, importance 0.9 -> bits_A = 20 / 0.9 = 22.2 bits
Region B (wall): entropy 20 bits, importance 0.1 -> bits_B = 20 / 0.1 = 200 bits (blurs easily; unpredictable)
Wait—high entropy, low importance = waste bits. The real model flips: allocate bits DOWN for low importance.
Corrected: total bits = sum_r [ H(pixels_r) * importance_r ]. Same pixels in face get 20 * 0.9 = 18 bits. Wall gets 20 * 0.1 = 2 bits.
Face quality stays high; wall becomes a sketch. Viewer happy, file small.

Importance acts as a volume knob: turn it up to spend more bits protecting a region; turn it down to let it blur.

What can go wrong

What can go wrong

Wrong text description. If the text says 'outdoor scenic view' but the video is a talking head, importance scores flip. Face gets no bits, blurs to garbage. Fix: auto-generate captions from video content or have a human write accurate descriptions.
Artistic scenes confuse the model. A scene where the 'unimportant' background is the artistic point (like a sunset behind silhouettes) gets crushed. The model trusts text-guided importance over artistic intent. Mitigation: weaken importance for scenes detected as visually complex or where background detail is part of the story.
Text fusion module undertrained. If the Extractor-Injector modules are not trained on diverse scenes, they might extract wrong semantic signals. A face in shadow might be marked low-importance if the training mostly saw well-lit faces.
Done right: semantic and visual agreement. When text descriptions and visual feature learning agree on importance, the codec works beautifully. Train on diverse videos with consistent human preference labels, and the model learns what actually matters.
What a runnable demo should prove

What a runnable demo should prove

Build a tiny two-frame video clip (e.g., a person's head speaking in front of a poster) and compress it three ways: (1) old motion-only codec, (2) MoVie with text 'person talking', (3) MoVie with text 'scenic poster'. Measure file size and face sharpness (using a face-detection model or human eye). Show that (2) produces a smaller file with a sharper face than (1), and that (3) trades off — bigger file, sharper poster. Plot file size vs face sharpness and vs background sharpness on the same graph.
