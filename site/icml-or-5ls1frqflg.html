MIMO-LP: Multiplexing Link Prediction

Instead of running message-passing separately for each link prediction query, MIMO-LP layers many queries into one shared computation space so they can reuse work on overlapping neighborhoods.

Paper explainersAll themesGraph & Geometric Learning

Link prediction means guessing which new edges (connections) will form in a graph. Subgraph methods do this accurately by looking at the local neighborhood around each pair of nodes you want to connect. But they are slow because each prediction forces a fresh round of message-passing (passing information around nearby nodes). MIMO-LP fixes this by running many predictions together in a single pass, letting them share the expensive computation.

Zero assumption version

Why is subgraph-based link prediction slow?

Imagine a social network. You want to predict which friendships will happen next. If you look at each node pair in isolation — checking their friends, their friends' friends, and so on — you get accurate predictions because you see the true local pattern. That is the whole appeal of subgraph-based methods.

But here is the trap: if you want to predict 1,000 friendships at once, the naive approach runs the full neighborhood lookup 1,000 times, even though many of those neighborhoods overlap. You are doing the same arithmetic many times. The computer walks through the friend-of-friend graph over and over for the same nodes. This redundancy kills speed.

The bottleneck. Each prediction query gets its own subgraph and its own message-passing loop, even when many queries overlap in the same neighborhood.

The algorithm as a flow

What it actually does

Extract subgraphs

For each query node pair, pull out its local neighborhood from the full graph.

Stack the queries

Instead of processing them one at a time, concatenate all the subgraph structures into one batch.

Run one message-passing pass

All queries run through the neural network together, nodes exchange information once.

Route to shared intermediate space

Each query's intermediate states are projected into a shared intermediate space to minimize interference.

Extract predictions

Read off the link scores for all queries in parallel from the single shared representation.

What the paper changes

What the paper changes

The paper changes how message-passing (the algorithm that exchanges information between neighboring nodes) is scheduled. Instead of doing it sequentially for each query, MIMO-LP does it once for all queries together in a shared computation.

the object it moves  =  Message-passing scheduling
The hidden quantity

Interference: how much one query scrambles another's computation

measured quantity  =  Cross-query interference

When you layer multiple queries into one computation, they share intermediate values (numbers that carry information forward from one node to the next, called embeddings: just lists of numbers that summarize what the model learned about each node). If query A's computation corrupts the shared values, it will mess up query B's answer. The paper calls this interference, and it is the main risk of multiplexing.

MIMO-LP estimates interference by measuring how much each query's gradients (the learning signals that update the model) collide and cancel each other out. High interference means the queries are fighting each other. The paper uses a gating mechanism — a learned switch that can dial down any query that is interfering badly — to keep interference small even when many queries share the space.

Why it works

Why sharing the computation works without breaking answers

Most of the neighborhood — the nodes that both queries touch — does not need separate processing. It can compute its intermediate representations once, and both queries can read from that shared result. Only the unique parts of each query's subgraph need isolation.

MIMO-LP enforces this split using learned gates (binary switches on shared intermediate values that can be turned off per query). When query A reads from the shared intermediate space, it only listens to the dimensions (the positions in the number list) that are safe for it; query B listens to a different safe subset. This way, the shared computation is fast (one big forward pass handles all queries), and interference is minimal (each query hears only the signals meant for it). The gates are learned during training, so they automatically discover which connections are safe to share and which must stay private.

Math after the picture

The scoring equation

First in words:

Each query's predicted link score is the sum of masked latent embeddings from both nodes in the pair, gated so only safe dimensions contribute.

Then the compact form:

s_q = (g_q * h_u) · (g_q * h_v)

Every symbol:

s_qPredicted link score for query q
g_qQuery-specific learned gate: which latent dimensions are safe for query q
h_uShared latent embedding for the first node in query q
h_vShared latent embedding for the second node in query q
·Dot product: multiply matching dimensions and sum
A tiny worked example
Query 1: nodes A and B. Shared embedding h_A = [1.0, 0.5, 2.0, 0.3]. Gate g_1 = [1, 1, 1, 0] (last dimension is gated off for q1). Masked h_A = [1.0, 0.5, 2.0, 0]. Similarly h_B masked = [0.8, 0.4, 1.8, 0]. Dot product: 1.0*0.8 + 0.5*0.4 + 2.0*1.8 = 4.4.
Query 2: same nodes A and B. But gate g_2 = [1, 0, 1, 1] (gates off dimension 2 instead). Masked h_A = [1.0, 0, 2.0, 0.3]. Masked h_B = [0.8, 0, 1.8, 0.25]. Dot product: 1.0*0.8 + 2.0*1.8 + 0.3*0.25 = 4.275.
Same nodes, different gates, different scores. Each query only trusts the dimensions its learned gate allows, avoiding corruption.

The gate acts like a binary selector: it allows each query to use only the dimensions that were learned to be safe for it, blocking the ones that carry other queries' interference. This works because during training, the gate learns which dimensions reliably predict links for each query type, and blocks the rest; by using only trusted dimensions, each query avoids reading corrupted signals.

What can go wrong

What can go wrong

Too much interference between queries. If the gate is not learned well, many queries can read from the same latent dimensions, making them corrupt each other. Accuracy drops below the one-at-a-time baseline.
Overfitting the gate to the training queries. If only a few query patterns appear during training, the gates learn to handle just those. On different query patterns at test time, interference spikes and accuracy falls.
Insufficient latent space size. If the shared latent embedding is too small, even with gates there is not enough room to isolate all queries' representations, forcing unwanted sharing.
Done right. Train the gate on diverse query patterns, use a latent space that is large enough to hold each query's unique signal, and measure interference on a held-out test set to confirm gates are working.
What a runnable demo should prove

What a runnable demo should prove

Build a tiny graph with 20 nodes and 50 edges. Create 10 random link prediction queries (asking does node A connect to node B). Run MIMO-LP on all 10 together in one forward pass, measuring total time. Then run the same 10 predictions one at a time using a naive baseline. Plot the time difference. Separately, compare accuracy: measure the link prediction AUC (area under the curve, a standard metric) for the batched version vs. the one-at-a-time version. Both should be similar in accuracy because the gates prevent interference, and MIMO-LP should be much faster because all queries run in a single neural network pass instead of 10 separate passes.

speedup = time_naive / time_mimo; accuracy_loss = auc_naive - auc_mimo

The demo must show that multiplexing many queries into one forward pass gives a substantial speedup (at least 5x) without sacrificing the accuracy of the link predictions.
