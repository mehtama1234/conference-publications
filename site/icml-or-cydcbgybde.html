Sparse ActionGen: Accelerating Diffusion Policy with Real-time Pruning

A robot can generate actions just as well by running only the critical computation blocks in a diffusion model and reusing cached results from nearby blocks.

Zero assumption version

Diffusion models are too slow for live robot control

A diffusion model (a type of neural network that gradually removes noise from random signals) can generate actions for a robot by running multiple denoising steps. For example, to pick up an object, the model might start with pure noise and refine it over 50 steps into a real, sensible action. The problem: each step runs through many computational blocks (attention layers, feed-forward networks) inside the model. A modern GPU can run one full step in 1 millisecond, so 50 steps takes 50 milliseconds — fast by human standards, but the robot must decide every 10 to 20 milliseconds, so this is too slow.

A naive solution is to run fewer denoising steps (say, 5 instead of 50), but that degrades the action quality because the model has less time to refine the noise into a good decision. Existing acceleration methods use fixed caching schedules that pre-compute and store results, but a robot-environment situation keeps changing, so a rigid schedule misses opportunities to skip blocks when the robot's state is different.

The problem in one sentence. Diffusion models can generate good robot actions, but their multi-step process is too slow for real-time control, and fixed acceleration schedules cannot adapt to new robot situations.

The algorithm as a flow

What it actually does

Step 1: Encode the robot's view and state

Convert the camera image and joint positions into numbers the model understands.

Step 2: Run the learned pruner once

Feed the encoded state to a small neural network that predicts which blocks to skip in which denoising steps.

Step 3: Start denoising with the pruning mask

Run the diffusion model's denoising steps, but skip any block marked as redundant by the pruner.

Step 4: Reuse saved outputs from earlier blocks

When a block is skipped, use a saved intermediate result from a nearby earlier block instead of recomputing.

Step 5: Output the final action

The refined action is ready 4 times faster than running every block, because only 25% of blocks are actually computed; cached results fill the rest.

What the paper changes

What the paper changes: the pruning mask

The paper does not change the trained diffusion model itself. Instead, it changes which computational blocks actually run during action generation. It learns a pruning mask — a binary choice (run or skip) for each block in each denoising step. This mask is adaptive: it changes based on the robot's current state, so different situations skip different blocks.

The hidden quantity

The hidden quantity: redundancy across timesteps and blocks

measured quantity  =  Redundancy

Redundancy means that the same computation (or nearly the same) happens in multiple places. In a diffusion model, redundancy occurs in two ways: across denoising timesteps (step 10 computes similar things as step 11) and across blocks within a single step (the cross-attention block in layer 3 produces a similar output to layer 4). If a computation is redundant, its output can be predicted or reused from somewhere else, so running it is wasteful.

The paper estimates redundancy by running the full model and measuring how different each block's output is from cached results at nearby locations. Blocks with tiny changes are marked as redundant and can be skipped. The pruner learns to predict this redundancy pattern from the robot's current observation, without needing to run every block to test it.

Plain reading. A computation is redundant if its output is almost identical to a cached result from a nearby step or block. If you can reuse the old result instead of recomputing, no information is lost.
Paper reading. The paper measures cross-timestep and cross-block redundancy by comparing layer outputs when the model is running (inference means when the model answers a new question, in contrast to training where it learns from data). It then trains a global sparsity loss that guides a pruner to select which computations to skip under a strict computational budget.
Why it works

Why it works: learning which computations can vanish without breaking the result

The core insight is that not every block in every denoising step carries unique information. Some blocks refine the action by 0.1%, while others refine it by 5%. If you skip a 0.1% block and reuse the saved intermediate result from the previous block (the numbers that passed through earlier computation), the final action is almost identical.

The paper builds a tiny neural network called a pruner that looks at the robot's current observation and predicts a pruning mask — which blocks to skip. The pruner only runs once per action generation, not once per step, so its overhead is minimal. It encodes the robot's state and uses positional information (which denoising step, which layer) to output a sparse pattern. During inference, the diffusion model runs the pruning mask: compute blocks marked as 'run', and for blocks marked as 'skip', fetch the cached output from the previous block. This zig-zag reuse across timesteps and blocks minimizes the total information loss because redundant blocks are skipped, but dependencies are still satisfied by nearby cached results.

Math after the picture

The global sparsity loss: balancing speed and accuracy

First in words:

Total loss = fidelity loss plus lambda times the absolute difference between actual computation count and the target budget.

Then the compact form:

L_total = L_fidelity + lambda * |actual_budget - target_budget|

Every symbol:

L_fidelityHow different the pruned policy's action is from the ground-truth action
lambdaA dial controlling how strictly the budget is enforced
actual_budgetSum of all blocks that the pruner kept (ran)
target_budgetThe speed goal (e.g. run 75% of blocks instead of 100%)
A tiny worked example
Suppose we want to run 75% of blocks (target = 0.75). The pruner predicts we can safely skip 26% (actual = 0.74).
Fidelity loss = 0.02 (the action differs slightly, but is still good).
Budget difference = |0.74 - 0.75| = 0.01.
If lambda = 10, then L_total = 0.02 + 10 * 0.01 = 0.12.
If the pruner tries to skip 40% (actual = 0.60), budget difference = 0.15, and L_total = 0.02 + 10 * 0.15 = 1.52 (much higher penalty), so training steers the pruner back toward 75%.

The loss pulls the pruner toward a target speed (actual budget) while keeping the action quality high (fidelity), so the final model runs only the blocks it must.

What can go wrong

What can go wrong

Pruner skips too much. If the target budget is set too aggressively (e.g. run only 50% of blocks), the pruner may skip blocks that carry unique information. The action quality drops, and the robot makes poor decisions.
Pruner ignores the robot state. If the pruner is not trained on diverse robot situations, it may predict the same mask for all observations. Then the mask cannot adapt to changing environments, and some new situations perform poorly.
Cached result mismatch. If the zig-zag reuse pattern is not carefully designed, a skipped block might fetch a cached result from a place with very different meaning (e.g. a different denoising step with a very different noise level), causing a mismatch in what the reused result represents.
Done right. With a reasonable budget target (e.g. 70-80% blocks), diverse training data, and careful zig-zag design, the pruner learns to skip only truly redundant blocks, and the action quality is preserved.
What a runnable demo should prove

What a runnable demo should prove

Build a simple robotic pick-and-place task (e.g. in simulation) where a robot arm must grasp an object. Load a pretrained Diffusion Policy model and a trained pruner. For a fixed robot observation (image of the scene, current arm pose), run the full diffusion (all 50 blocks in all denoising steps), record the output action and the wall-clock time. Then run Sparse ActionGen with the same observation and the same budget target (e.g. 75% of blocks), record the output action and the time. Measure the difference between the two actions (in joint space, should be < 1% different). Measure the speedup (should be 3-4 times faster) because the sparse version computes far fewer blocks, so total computation time drops proportionally.

Speedup = time_full / time_sparse; action_error = norm(action_full - action_sparse)

The demo must show that the sparse action is nearly identical to the full action, but arrives 3-4 times faster because redundant blocks are skipped and cached results substitute for them. This is what makes real-time robot control possible.
