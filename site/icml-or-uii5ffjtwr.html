DiscoverLLM: From Executing Intents to Discovering Them

Train an assistant to help a user discover what they want by rewarding progress from vague goals toward concrete choices.

Paper explainersAll themesAgents & Tool Use

Many assistants assume the user already knows the target and only needs help expressing it. That assumption fails for open-ended work such as writing, design, or planning, because the user often needs to see options before deciding. DiscoverLLM treats the conversation as intent formation, not just intent execution. It trains the assistant to widen the search when the goal is still vague and narrow the search when the user's preferences become concrete, because that behavior helps the user reach a usable decision in fewer turns.

Zero assumption version

Why direct question answering fails when the user has not decided yet

A standard assistant waits for a clear request, asks for missing details, and then executes. That works when the user already has a stable target. It breaks when the user says something broad such as "help me write this" or "help me design this" and has not yet chosen the direction, because the assistant is asking for decisions before the user has enough options to compare.

In that setting, a clarification question can still be too early. If the user does not know the tone, structure, or visual style yet, asking for a precise choice produces weak answers because the assistant is requesting a decision before enough options have been surfaced. The paper addresses that gap by training the assistant to uncover intent through interaction, because exposing useful alternatives can make the user's preferences more definite.

The central move. Reward the assistant for increasing intent concreteness, because the right next step is sometimes to open the space of options and sometimes to narrow it.

The algorithm as a flow

What it actually does

Model user intent as a hierarchy.

Represent the user's goal at several levels of detail so the system can tell whether the conversation is still broad or already specific.

Simulate user development.

Use a simulator that updates the user's state after each assistant move, because training needs examples where intent becomes clearer over time.

Score intent concreteness.

Measure how much the user's goal has sharpened so the training signal rewards moves that make the next choice easier.

Diverge when intent is unclear.

Surface relevant alternatives when the state is still broad, because more coverage helps the user discover what matters.

Converge when intent is clearer.

Refine and execute once enough structure is known, so that the conversation does not stay wide longer than needed.

The hidden quantity

The hidden quantity

measured quantity  =  degree of intent concreteness

The important hidden quantity is how concrete the user's intent currently is. Two conversations can have the same number of turns while being very different internally: in one, the user is still testing broad directions; in the other, the user is choosing among close variants.

DiscoverLLM estimates this quantity through a hierarchy of intent states. A move is useful when it increases concreteness because it either removes irrelevant directions or exposes a distinction the user can now evaluate. That makes the system care about progress in the user's decision state, not only about the surface form of the reply.

Why it works

Why divergence then convergence helps

When intent is unclear, asking for a final specification is inefficient because the user has too little structure to answer well. DiscoverLLM instead widens the conversation in a controlled way by surfacing plausible options, because user reactions to those options reveal which attributes matter.

Once the reactions start to align, the system narrows the space. That shift matters because continuing to list many alternatives after the user has already shown a preference wastes turns and slows completion. The policy learns this switch through reward on intent concreteness, so it is pushed toward whatever move best advances the user's decision state at that moment.

The user simulator is central because direct supervision for intent discovery is scarce. The simulator creates training trajectories where the assistant can observe whether a move made later choices easier. That supplies the missing signal needed to train the exploration-to-refinement transition.

Math after the picture

Reward progress toward a concrete goal

First in words:

A compact summary is to reward each assistant move for increasing intent concreteness and subtract a cost for extra turns, because a good conversation should both clarify the target and finish efficiently.

Then the compact form:

score = task_success + alpha * intent_clarity_gain - beta * turns

Every symbol:

task_successquality of the final outcome on the user's task
alphaweight on progress toward a more concrete intent state
intent_clarity_gainhow much clearer the user's goal becomes after the move
betapenalty on long conversations
turnsnumber of assistant-user exchanges used to finish
A tiny worked example
Move A gives a useful set of options, so intent_clarity_gain = 4 while adding 1 turn.
Move B asks for a final style too early, so intent_clarity_gain = 1 while adding the same 1 turn.
If alpha = 3 and beta = 1, Move A adds 12 - 1 = 11 points before final task success.
Move B adds 3 - 1 = 2 points before final task success.
The policy prefers Move A because it makes the user's next choice much easier.

The exact training setup is more detailed, but the paper's key objective is to favor moves that make the user's intent more concrete while keeping the dialogue short.

What can go wrong

What can go wrong

The simulator may misread how users decide. If the simulated user state does not match real user behavior, the policy may learn poor exploration habits because the reward signal is tied to the simulator's own progress measure.
The system can widen the space too much. If the assistant keeps adding alternatives after enough preference evidence has appeared, the user may face extra comparison work because the conversation does not converge soon enough.
Weak option design gives weak signals. If the surfaced options are too similar or not relevant, user reactions reveal little about intent because the differences do not expose clear tradeoffs.
Done right. The method works when the option set is relevant and the policy can detect when the user has become more specific, because then the system broadens only when discovery is needed and narrows once execution becomes appropriate.
What a runnable demo should prove

What a runnable demo should prove

Build a writing assistant with three modes: execute immediately, ask direct clarification questions, and DiscoverLLM-style intent discovery. Give users broad requests such as drafting a cover letter or shaping a product description. Record how many turns each mode uses, whether the user reaches a final choice, and how satisfied the user is with the final draft.

The demo should show that the discovery policy surfaces helpful alternatives early and then narrows quickly after preference signals appear, because that pattern is the paper's core claim.

intent_efficiency = final_quality * intent_clarity / turns

A convincing demo must show that helping users form intent changes outcomes, because some tasks are blocked by uncertainty in the user's goal rather than by the assistant's ability to execute instructions.
