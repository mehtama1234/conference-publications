MATHMO: Automated Mathematical Modeling Through Adaptive Search

A search method that automatically explores mathematical equations and frameworks to find models that balance speed, accuracy, and other real-world trade-offs, using an AI assistant to guide the exploration.

Paper explainersAll themesAI for Science

Writing down equations to describe a real-world system — crop growth, river flow, particle motion — takes months of trial, error, and expert intuition. This paper asks: what if an AI system could automatically explore thousands of candidate equations and hand back the best ones? MATHMO does exactly that, treating the job as a systematic search problem with multiple conflicting goals (accurate predictions, simple equations, fast computation) and even subjective preferences.

Zero assumption version

Manual modeling is a bottleneck

In fields like biology, engineering, and physics, building a mathematical model of reality means writing equations by hand. A researcher sits with data, hypothesizes a mechanism, proposes an equation, checks it against real measurements, tweaks the numbers, and repeats. This cycle takes months or years.

The core difficulty is that there are infinitely many equations you could try. Do you use a polynomial? Exponential growth? A differential equation with feedback loops? Each choice spawns sub-choices: how many terms, what order, which variables interact? A human expert navigates this space through intuition and luck.

A beginner would try all combinations exhaustively. This fails because the search space is huge, and many combinations are nonsensical or redundant.

In one sentence. MATHMO automates the model-building search by having an AI assistant repeatedly propose candidate equations, score them on multiple objectives (speed, accuracy, simplicity), and iteratively refine the best ones.

What the paper changes

The choice: equation and framework

A mathematical model is a choice of equation (or set of equations), the variables it uses, and the numbers multiplying each term (called coefficients). MATHMO's job is to explore this choice space and find models that work well. The paper does not change how you evaluate a model — you still test it against real data — but it systematically explores which models to test.

The hidden quantity

The Pareto frontier: models that balance trade-offs

measured quantity  =  Pareto-efficient model set

In the real world, you never have just one goal. You want a model that predicts accurately, runs fast, and stays simple enough to understand. These goals conflict: the most accurate model might be a huge neural network that runs slowly. The fastest model might be just a constant.

A Pareto-efficient set is the collection of models where no single model is better at every goal. If model A is faster than model B but less accurate, both are in the frontier because each excels in one dimension. MATHMO's goal is to discover this frontier — the set of models that represent genuine trade-offs, not obviously bad choices.

Plain reading. The Pareto frontier is the set of model choices where you cannot improve one objective without hurting another, because they occupy different regions of the performance space — a fast model is slow-to-build, an accurate one is compute-heavy. MATHMO finds this set automatically by testing all candidates and filtering out obvious losers.
Paper reading. The paper uses Pareto optimization to balance multiple objectives (accuracy, computational cost, model simplicity, and subjective user preferences) without picking a single winner.
Why it works

The search strategy: two levels of navigation

Trying every equation combination is hopeless. MATHMO uses a two-level strategy. At the high level, an LLM explorer suggests diverse mathematical frameworks — should we use polynomial models, exponential growth, differential equations with feedback, or something else? At the low level, within each framework, the system refines the specific coefficients and equation structure.

Here is why this works: the LLM is good at high-level reasoning and exploring diverse ideas (that is what large language models do). The scoring function is good at checking whether an equation fits the data well. Together, they exploit the structure of the search space — frameworks cluster similar equations, so you do not jump around randomly.

Balancing multiple objectives with a score function

First in words:

For each model, compute a weighted sum of scores: overall_score = w_accuracy * accuracy_score + w_speed * speed_score + w_simplicity * simplicity_score, where w_accuracy, w_speed, w_simplicity are weights chosen by the user to reflect how much each goal matters.

Then the compact form:

score_total = w_acc * (1 - error_rate) + w_speed * (1 / compute_time) + w_simple * (1 / num_terms)

Every symbol:

error_ratehow far predictions deviate from real data (0 = perfect, 1 = useless)
compute_timehow long the model takes to predict one output (in milliseconds)
num_termsthe number of terms in the equation (more terms = harder to interpret)
w_accweight for accuracy importance (user sets this)
w_speedweight for speed importance (user sets this)
w_simpleweight for simplicity importance (user sets this)
score_totalthe combined score a model gets on all three objectives
A tiny worked example
Model A: error_rate = 0.1, compute_time = 5ms, num_terms = 3 terms. Weights: w_acc = 0.5, w_speed = 0.3, w_simple = 0.2.
Accuracy component: 0.5 * (1 - 0.1) = 0.5 * 0.9 = 0.45.
Speed component: 0.3 * (1 / 5) = 0.3 * 0.2 = 0.06.
Simplicity component: 0.2 * (1 / 3) = 0.2 * 0.333 = 0.067.
Total score for Model A: 0.45 + 0.06 + 0.067 = 0.577.
Model B: error_rate = 0.05, compute_time = 20ms, num_terms = 8 terms. Accuracy: 0.5 * 0.95 = 0.475. Speed: 0.3 * 0.05 = 0.015. Simplicity: 0.2 * 0.125 = 0.025. Total: 0.515.
Model A scores higher (0.577 vs 0.515) because our weights favor accuracy and simplicity; Model B is more accurate but slower and more complex.

The equation translates user preferences into a score that ranks candidate models fairly on all dimensions, allowing the search to find trade-offs rather than false winners.

What can go wrong

What can go wrong

The LLM proposes useless frameworks. If the LLM does not understand the domain, it may suggest equations that are mathematically invalid or nonsensical for the application. Example: proposing a polynomial model for a system that is fundamentally exponential. Mitigation: seed the LLM with domain context and examples.
Scoring ignores important objectives. If you do not include an objective in the score function (e.g., numerical stability, interpretability for regulators), MATHMO will optimize for what you told it to and ignore the rest. The frontier will be misleading.
Overfitting to the training data. A complex equation might fit the historical data perfectly but fail on new data. MATHMO's score can be misled if it evaluates models only on one data snapshot. Mitigation: use cross-validation or held-out test data to score candidates.
Done right. Include domain knowledge in the LLM prompt, score on all real objectives (and separate training from test data), and iteratively refine the preference weights as you learn what trade-offs actually matter.
What a runnable demo should prove

What a runnable demo should prove

A demo should pick a real-world dataset with multiple, conflicting objectives. Example: modeling the spread of a disease in a population. You want accuracy (predictions match real case counts), but also speed (the model must run on a mobile device), and simplicity (health officials must understand the mechanism). Run MATHMO to search for models, plot the Pareto frontier, and show that each model on the frontier represents a real trade-off — improving one goal breaks another.

frontier_coverage = (number of Pareto-optimal models found) / (true size of frontier), computed by comparing MATHMO's results to models humans generated in the same time budget.

The demo must show that MATHMO discovers models a human would have taken weeks to find, and that the frontier genuinely represents trade-offs (not just a list of bad models).
