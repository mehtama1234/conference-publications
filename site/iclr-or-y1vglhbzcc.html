Instead of hand-writing planning domains, this method builds them automatically by watching one robot demo and asking an LLM to name the things the robot cares about.

The manual domain bottleneck

Long-horizon robot tasks need a planner that thinks in abstract steps: put down the bowl, pick up the spoon, stir the mixture. But planners only work if you first hand-write what matters—the predicates, like bowl_on_table or gripper_open. An engineer studies the robot and its world and writes these rules by hand, a weeks-long process.

LLMs can generate task steps from language, but they often skip physical reality and get stuck on long tasks. The real problem: neither LLMs alone nor hand-coded domains alone work well for long chains of actions.

The bottleneck. Watch one demo, have the LLM infer the predicates, then wire them up to the actual robot.

The algorithm as a flow

What it actually does

Ingest the demo

Feed one robot trajectory (all arm positions over time) and a short task description into the system.

LLM names low-level facts

The LLM reads the trajectory and generates first-order predicates: gripper_open(t), object_in_place(t), hand_above_table(t). These are facts that are true or false at each moment.

Compute physical constraints

Simulation runs the demo and measures what regions of space each predicate occupies: if gripper_open is true between time steps 5-40, those correspond to specific gripper angles in 3D space.

LLM derives higher-order actions

From the low-level predicates, the LLM infers higher-order actions: pick_object(object) requires gripper not open, then opens gripper, then object in hand. Each action lists preconditions and effects.

LoCA connects domain to motion

The Logical Constraint Adapter retrieves the physical constraint regions for each predicate and hands them to the motion planner, so abstract steps become real motion commands.

What the paper changes

What the paper changes

The paper removes the need to hand-write planning domains. Instead of an engineer writing predicates and actions, the method watches one demo and has the LLM infer them, then ties each fact to the physical robot poses and joint angles the demo showed.

The hidden quantity

The hidden quantity: predicate grounding

measured quantity  =  constraint region per predicate

A constraint region is the set of robot configurations (joint angles, hand positions, gripper openings) where one predicate is true. For example, gripper_open might be true for gripper angles > 40 degrees; that angle range is the constraint region. The demo shows exactly which configurations make each predicate true.

The paper measures constraint regions by running simulation on the demo trajectory: every time the demo changes from gripper_closed to gripper_open, the system records the exact joint angles and hand position. These snapshots define the boundary of the region. LoCA uses these regions to constrain the motion planner's search.

Why it works

Why it works: two-stage domain learning plus constraint grounding

The LLM is good at naming abstract concepts from examples, but it cannot reason about physical robot poses and joint angles alone. Simulation is good at measuring physical poses but cannot reason about task meaning. The paper pairs them: the LLM infers what matters (the predicates and actions), and simulation measures where each fact lives in the space of robot configurations.

LoCA enforces that every abstract step in a new task must obey the constraints the demo showed. If the demo never had the gripper fully open while the object was inside it, LoCA forbids that state in new tasks. This ground truth from the single demo makes new task plans much more likely to work in the real world, because they cannot venture into untested territory.

Math after the picture

Predicate grounding via constraint regions

First in words:

Each predicate defines a region in configuration space. An action is valid if its motion stays within the conjunction of regions required by its preconditions and achieves the region defined by its effect.

Then the compact form:

valid_action = motion_traj in (Ppre_regions) AND endpoint in (Peff_region)

Every symbol:

Ppre_regionsset of all configuration regions required by the action preconditions
Peff_regionconfiguration region that satisfies the action effect
motion_trajthe continuous robot motion the planner proposes
valid_actiontrue if the motion stays in precondition space and ends in effect space
A tiny worked example
Demo shows: when gripper angle is 0-20 degrees, gripper_closed is true. When angle is 40-90 degrees, gripper_open is true.
LLM infers action open_gripper: precondition is gripper_closed (angle 0-20), effect is gripper_open (angle 40-90).
Motion planner is asked to open the gripper in a new task. It must start in state where angle is 0-20 (satisfies precondition) and end in state where angle is 40-90 (satisfies effect). Planner searches only those regions, not the full 0-360 degree space.
Result: planner finds valid motion quickly (no bad states to explore) and motion matches what the demo showed.

The constraint regions come directly from the demo, so new plans cannot venture into untested configurations.

What can go wrong

What can go wrong

Single demo is not representative. If the demo was sloppy or took an odd path, the inferred regions are too narrow or misaligned. A demo where the gripper only opened slowly may not cover fast-open scenarios the new task requires.
LLM names predicates that do not matter. The LLM might infer a color predicate or a position predicate that does not actually change the task outcome. Irrelevant predicates bloat the domain and make planning slower.
Constraint regions are violated in reality. Simulation estimates geometric constraints from the demo, but real robot execution has noise and physics differences. A constraint region estimated as gripper angle 40-90 might fail at angle 38 due to calibration drift.
Done right. Collect a clean demo that exercises the full range of each predicate. Verify inferred predicates are causally relevant by ablating them. Test the domain on a few validation tasks before deployment.
