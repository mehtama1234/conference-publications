DynaSchedBench: Calibrated Dynamic Scheduling Benchmarks and Observability Paradox in LLM-based Scheduling Agents

Build dynamic scheduling tasks with controlled difficulty, then test whether extra system state really helps an agent choose the next job well.

Paper explainersAll themesAgents & Tool Use

Dynamic shop scheduling is hard because the task changes while the planner is acting. New jobs arrive, machines become busy, and one choice changes what can be done next. This paper builds a benchmark that controls task difficulty instead of sampling cases loosely, then uses that benchmark to test scheduling agents. The striking result is that giving the agent more system state can hurt, because the extra detail can distract it from the few facts that decide the next useful action.

Zero assumption version

Why dynamic scheduling is hard to measure

A dynamic flexible job shop is not a one-shot plan. Jobs arrive over time, several machines may be able to process the same step, and the best next move depends on what is waiting right now and what is likely to arrive soon.

Research progress is hard to judge when the test set is weak. Static benchmark sets reward tuning to a fixed collection of cases, while loose random generators blur real skill with noise because the generated tasks do not line up cleanly by difficulty. This paper tries to fix that measurement problem before judging the agents themselves.

The paper's move in one sentence. Create dynamic scheduling tasks whose difficulty is calibrated to a target stress level, then use them to test how agents behave under short and information-heavy views of the shop.

The algorithm as a flow

What it actually does

Step 1: Define a difficulty target

Specify the intended stress level of a dynamic scheduling instance by combining signals such as arrival pressure, machine contention, and due-time pressure.

Step 2: Calibrate an instance generator

Use the sequential calibrator to search for generated cases whose measured stress matches that target closely.

Step 3: Simulate the shop online

Expose the current shop state one decision at a time so agents and dispatch rules must react as events unfold.

Step 4: Compare information views

Run each agent with either a concise state view or a richer structural state view and measure whether that changes dispatch quality.

Step 5: Score scheduling quality

Evaluate the final production outcome using delay and completion quality so that good local choices matter only when they improve the whole run.

What the paper changes

What the paper changes

The paper changes both the test environment and the question being asked. It replaces loose dynamic scheduling tests with calibrated ones so that score differences can be tied to intended stress rather than accidental generator noise, then asks whether richer shop descriptions actually help an agent choose better actions online.

the object it moves  =  calibrated dynamic scheduling benchmark plus information-view comparison
The hidden quantity

The hidden quantity

measured quantity  =  decision-relevant state density

The important hidden quantity is how much of the visible shop state actually matters for the next dispatch choice. A larger description is only helpful when the added facts increase the share of useful signals in what the agent reads.

The paper shows an opposite pattern in some settings. Full state access can lower decision-relevant state density because the agent sees many details that do not affect the next good move, so the critical cues are harder to isolate.

Why it works

Why the benchmark and paradox matter

Calibrated generation matters because the benchmark should vary difficulty on purpose. If one test case is harder than another only by accident, then a score gap does not tell us much about what the method can truly handle. The stress index helps because it turns difficulty into a target that can be matched deliberately.

The information-view comparison matters because online scheduling is a repeated local decision problem. The next action often depends on a small set of urgent signals such as due-time pressure, queue length, and immediate machine availability. When the state view grows faster than the agent's ability to rank those signals, the policy can worsen because effort is spent on detail that does not change the right local choice.

A compact way to think about calibration

First in words:

The generator searches for an instance whose measured stress is close to the requested stress target.

Then the compact form:

calibration_error(instance) = abs(SSI(instance) - target_SSI)

Every symbol:

SSI(instance)the measured schedule stress of one generated dynamic scheduling case
target_SSIthe requested difficulty level for the benchmark case
calibration_error(instance)how far the generated case is from the desired stress level
A tiny worked example
Suppose the benchmark wants a case with target_SSI = 0.70.
Generator candidate A measures SSI(instance) = 0.66, so calibration_error = 0.04.
Generator candidate B measures SSI(instance) = 0.83, so calibration_error = 0.13.
Candidate A is the better benchmark case because its stress level is closer to the intended difficulty.
Now compare two agents on that same calibrated case.
If the short state view yields lower delay than the full state view, then the extra visible detail did not help the decision process on that case.

This equation captures the benchmark side of the paper. The agent side asks whether more visible state lowers or raises final schedule quality on those calibrated cases.

What can go wrong

What can go wrong

Calibration mismatch. A benchmark case can miss its intended difficulty if the measured stress index does not capture the type of pressure that truly drives dispatch quality.
Information overload. A richer state view can reduce action quality because the agent spends effort on secondary details instead of the next urgent conflict.
Prompted refinement stall. Extra tool calls or self-revision can add cost without helping because the main problem is not missing words but weak selection of the decisive shop facts.
Done right. A strong system should extract a compact action view from the full simulator state so that the next choice is based on bottlenecks, due-time pressure, and current availability rather than on a long undifferentiated description.
What a runnable demo should prove

What a runnable demo should prove

Build a small dynamic shop simulator with three machines, incoming jobs, due times, and multiple machine options per job step. Add a simple stress score based on queue pressure and lateness risk, then generate cases until the score lands near a chosen target.

Run the same agent with two views: a short action table and a full shop dump. The demo should prove that calibration matters because the cases can be grouped by intended stress, and that extra visible detail can hurt because the full dump may lead to worse dispatch choices even on the same case.

average_delay = total_late_time / finished_jobs ; view_gap = average_delay(full_view) - average_delay(short_view)

If view_gap stays above zero on several medium-stress cases, the demo has reproduced the paper's central paradox.
