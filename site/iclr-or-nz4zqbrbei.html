Searching for Privacy Risks in LLM Agents via Simulation

A search algorithm finds privacy attacks on LLM agents by alternating between making attacks stronger and defenses better, using the same simulator.

Paper explainersAll themesAlignment, Safety & Fairness

Imagine a chatbot that handles sensitive data (like your medical history) on your behalf. A bad actor could create another chatbot designed to trick it into leaking that data. But we do not know ahead of time what tricks will work or how to defend against them. This paper presents a method to discover both: run millions of simulated conversations where attack agents and defense agents compete, and use an LLM to analyze what worked and propose new strategies. The attacks and defenses grow more complex together until we find the truly dangerous moves and the guardrails that stop them.

Zero assumption version

Why manual security analysis fails

LLM agents now handle real tasks: booking flights, sending emails, filling tax forms — all with access to sensitive data like medical records or passwords. A malicious actor could build another LLM agent to chat with yours and trick it into revealing secrets.

The danger is invisible to humans. You cannot predict what subtle tricks will work (a fake identity? a emotional appeal? forging agreement?). You cannot list all possible attacks and manually design defenses for each. The conversations are long, multi-turn, and context-dependent — a trick that fails on day one might work on day five. This is not like traditional security, where you know the attack surface.

Existing defenses are too simple: a rule that says do not reveal names, do not share emails. But a clever attacker can work around any single rule.

The core challenge. You cannot find dangers manually, and simple rules do not hold.

The algorithm as a flow

What it actually does

Step 1: Set up a private scenario

Define a privacy norm (e.g., protect this person's health records). Create three agents: a data holder, a legitimate data user, and an attacker.

Step 2: Run a batch of simulated conversations

Each conversation is a full multi-turn dialogue. Measure how much sensitive data leaked (the leak velocity).

Step 3: Have the LLM analyze what worked

Show the LLM the conversations where the most data leaked. Ask it to spot patterns and suggest better attack instructions, because the LLM can recognize what made an attack succeed (e.g., impersonation worked better than direct requests) and combine successful tricks into a single new instruction.

Step 4: Update the attacker instructions and re-run

The new attacks are usually more effective. Keep the best instruction found so far.

Step 5: Now improve the defense the same way

Analyze which defenses failed most badly. Use the LLM to propose stronger guardrails, because the LLM can see why an attack succeeded (e.g., it forged consent) and design a guard that blocks that specific trick. Repeat attack-defense-attack until both plateau.

What the paper changes

What the paper changes

The paper changes the agent's instruction (the text prompt that tells an LLM agent what to do). For the attacker, it is the instruction that guides how to extract data. For the defender, it is the guardrail that specifies how to protect it. Instead of writing these by hand, a search algorithm proposes them and tests them millions of times in simulation.

the object it moves  =  agent instructions (attack and defense prompts)
The hidden quantity

The leak velocity: a named hidden quantity

measured quantity  =  leak velocity (bits of data per turn)

This is the amount of sensitive information that flows from the honest agent to the attacker, measured per conversation turn. It is not just whether data leaked (yes/no), but how much and how fast. A clever attack might extract ten facts in five turns; a crude one might need twenty turns to extract two.

The paper estimates leak velocity by running the full simulated conversation and scanning the attacker's output for sensitive keywords (names, numbers, email addresses, medical terms). The higher the leak velocity, the more successful the attack. The search algorithm uses leak velocity as its fitness score: it keeps trying new attack instructions until it finds one with high leak velocity, then freezes it and improves defenses by minimizing leak velocity.

Why it works

Why alternating search finds both attacks and defenses

The core insight is that an LLM can reflect on its own failures. If you tell an LLM, here are 50 attack attempts and their leak velocities, the LLM can spot patterns: oh, the ones that mentioned false credentials had higher leak velocity than direct questions. It will propose a new instruction that combines the successful tricks. This is much more efficient than random guessing or resampling, because the LLM is using semantic understanding to infer what worked (impersonation is better than confrontation) rather than blindly recombining random words.

Alternating search works because attacks and defenses are symmetric. When the attacker is frozen and the defense evolves, each new guardrail is tested against the best current attack. When roles switch, the defense freezes and the attack evolves against the best defense. The algorithm uses parallel search on multiple threads, and when one thread finds a breakthrough (a new instruction that beats the previous best), that discovery is broadcast to all other threads. This cross-thread propagation means a good idea discovered on one thread spreads to all threads instantly.

The escalation from simple to multi-layered tactics happens naturally: early attacks are blunt (just ask directly), but as defenses evolve (no, I will not tell you), the LLM optimizer sees that directness fails and proposes creativity (fake credentials, impersonation, false consent). The final attacks are multi-step and contextual because the defenses have learned to catch one-step tricks.

Math after the picture

The search loop in one formula

First in words:

At each search step, keep the instruction that maximizes leak velocity (for attack) or minimizes it (for defense). The best instruction is selected from all parallel threads (not just the current thread), ensuring discoveries propagate.

Then the compact form:

I_best <- arg_max_I [ mean_over_P_runs( leak_velocity(I, scenario, defend) ) ]

Every symbol:

Ia candidate instruction (text prompt)
leak_velocity(I, scenario, defend)the amount of sensitive data extracted when using instruction I against the current defense
Pnumber of simulation runs per instruction
mean_over_P_runs(...)average the leak velocity across multiple random runs
I_bestthe instruction with the highest score so far (keep this frozen, move to defense evolution)
arg_maxpick the I that gives the largest value
A tiny worked example
Suppose the search tries 3 attack instructions against the current defense: ask_directly, fake_credentials, and emotional_appeal.
Each is tested 20 times; the average leak velocities are: ask_directly = 8 bits, fake_credentials = 15 bits, emotional_appeal = 12 bits.
The algorithm picks fake_credentials as I_best (highest value, 15 bits) and freezes it.
Now the defense search begins: try new defense instructions against fake_credentials. Whichever defense most reduces leak velocity wins.
After 30 defense steps, suppose identity_verification (a multi-step proof) reduces leak velocity from 15 to 3 bits.
Swap back: attack search now tries to break identity_verification. The cycle repeats.

The algorithm is a simple maximize-then-minimize alternation, but it works because the LLM optimizer proposes smart new instructions based on what it learned from failures.

What can go wrong

What can go wrong

Search finds spurious attacks that do not transfer. If the search optimizes too narrowly on one scenario, the discovered attack might be a quirk of that simulation (e.g., a typo in the defense prompt that happens to confuse that LLM model). When tested on a different scenario or model, it fails. The paper validates transfer by testing attacks and defenses on out-of-distribution scenarios and different backbone models (GPT-4, Claude, etc.). Real attacks transfer; spurious ones do not.
The simulator does not capture real attack complexity. The simulated agent conversations are text-based and run in isolation. Real attacks might involve timing (waiting weeks for an agent update), side-channel data (inferring secrets from response latency), or physical interaction (social engineering). The simulation is a proxy; it is comprehensive but not perfect.
The LLM optimizer gets stuck in local maxima. If the search only tries variations on one theme (e.g., only emotional appeals), it might miss an entirely different attack vector (e.g., technical social engineering). The paper mitigates this with parallel search: many threads explore different regions of the space, and cross-thread propagation brings good ideas back into the mainstream.
Done right (if these hold). The defenses discovered are practical (implementable in real agents) and generalize to unseen scenarios. They scale to more complex agent architectures (not just ReAct agents). The attack-defense co-evolution finds the true dangerous moves, not artifacts of the search.
What a runnable demo should prove

What a runnable demo should prove

A minimal demo simulates a single privacy norm (e.g., protect a specific person's bank account number). Set up two agents: an honest one holding the account number, and an attacker agent with a basic attack instruction (just ask directly). Run 20 simulations and measure the baseline leak velocity. Then run the attack search algorithm for 5 steps: at each step, the LLM proposes a new attack instruction, test it 20 times, keep the best. Plot the leak velocity over the 5 steps. You should see it rise from 0 (direct requests fail because the defense is a simple no) to 3 or 4 (the LLM discovers impersonation or forged context). Now switch to defense evolution: freeze the best attack and run 5 defense steps. The leak velocity should drop back down as defenses evolve (identity checks, multi-turn verification). The key proof: after one cycle of attack and defense co-evolution, both have added layers of trickery and verification, and the defense blocks attacks that worked at the start.

leak_velocity = (count of sensitive entity mentions in attacker messages) / (number of turns in the conversation)

The demo must show leak velocity rising during attack search and falling during defense search, proving that the search algorithm can steer both toward sophistication and that defenses actually get harder to break.
