RoboInter: Intermediate Representations for Robot Learning

A dataset and framework that teaches robots via step-by-step plans, not just raw video-to-action, by adding intermediate goals (grasp point, hand height, object state) that break the hard problem down.

Paper explainersAll themesRobotics & Control

Robots learn tasks by watching videos and copying actions, but this is brittle: each robot body is different, and watching thousands of videos costs money. RoboInter solves this by teaching robots to think in steps — instead of jumping from camera image straight to motor commands, the robot first predicts intermediate goals (where to grasp, how high to lift), then uses those step-by-step plans to figure out what to do. A dataset of 200,000 robot videos, labeled with these intermediate milestones, lets researchers build and test this idea.

Zero assumption version

Why learning from robot videos is stuck

Today's robot learning works like this: show a robot 1,000 videos of a human (or another robot) doing a task, and the robot tries to copy by learning a rule that says 'given camera picture X, move joints Y.' This fails in three ways. First, each robot body is different — different arm length, different gripper — so a rule learned on Robot A does not work on Robot B without expensive retraining. Second, the jump from image to joint-motion is enormous: there are thousands of tiny motor choices to make at each moment, and picking them all at once from a single image is like trying to solve a 10-step puzzle by guessing the whole answer at once. Third, robots today are costly — collecting 10,000 real robot videos can take months. The result: robot systems are brittle and expensive, and they do not generalize.

A beginner's fix would be to just collect more videos, but that hits a wall: more videos cost more money, and they still do not solve the fundamental problem that 'picture to motors in one step' is just too much to learn.

In one sentence. RoboInter breaks the task into steps by labeling videos with intermediate waypoints — things the robot should achieve along the way, like 'gripper open' or 'hand at height 20cm' — so the robot learns a plan first, then executes it.

The algorithm as a flow

What it actually does

Video ingestion

Collect robot videos of manipulation tasks (grasping, moving, stacking).

Frame labeling

For each video frame, annotate where the gripper should go, how open it is, object position — dense per-frame supervision.

Plan prediction

Train a vision model to look at one frame and predict the next 9 waypoints: grasp location, hand pose, grip strength, object location, release pose, etc.

Execution binding

A separate model takes those waypoints and converts them into real motor commands for whichever robot body you have.

Test on new tasks and robots

The plan layer generalizes to unseen tasks; the execution layer adapts to new robot bodies without retraining the planner.

What the paper changes

What the paper changes

The paper adds a new layer to robot learning: intermediate representations — waypoints or subgoals that sit between raw video and final motors. Instead of the model predicting joint angles directly, it predicts waypoint sequences. This is the single structural change: insert a planning stage before execution.

the object it moves  =  intermediate waypoint representations
The hidden quantity

The hidden quantity: Task alignment

measured quantity  =  How well predicted waypoints match human intent

Every task is a sequence of sub-goals. When a human grasps an object, they intend three things to happen in sequence: gripper opens, hand moves to grasp point, gripper closes. The hidden quantity is how well a learned waypoint prediction captures these intended sub-steps — do the predicted waypoints actually look like checkpoints a human would choose, or are they random noise? This is 'task alignment.' It is not measured by final success (which depends on the executor too); instead, it is measured by comparing predicted waypoints to human labels: if the model predicts 'hand at (10, 20, 30)' and a human labeled 'hand at (9.8, 20.2, 29.9)' at that frame, they align.

RoboInter measures this by building a 200,000-video dataset where humans have labeled every frame with nine categories of waypoints (grasp pose, grip state, object pose, etc.), and then testing whether a trained vision model's predicted waypoints are close to the human labels. The paper calls this the 'embodied QA' evaluation: does the model know what a manipulation expert would say the robot should do next?

Why it works

Why breaking tasks into steps makes robots learn better

The mechanism is simple: a hard problem broken into smaller pieces is easier to solve. Learning 'image to nine waypoints' is easier than learning 'image to 15 joint angles' because each waypoint is a single, concrete thing (grasp point is x-y-z coordinates; grip state is open-or-closed). Each waypoint is also invariant to the robot body — a grasp point in world space is the same whether the robot has a 6-joint or 7-joint arm. So a model trained to predict 'hand should move to (10, 20, 30)' works on any robot, while a model trained to predict 'joint 1: 45 degrees, joint 2: -20 degrees...' only works on that exact robot. The executor (a separate model or controller) then translates 'move hand to (10, 20, 30)' into whatever joint commands that specific robot needs.

The data efficiency gain comes from the same source: humans label fewer examples if each label is simpler. Instead of annotating 1,000 full trajectories with every joint angle at every frame (expensive), you annotate 200,000 videos with just nine waypoint categories (cheaper, because waypoints are faster to label and reuse across robots). The model sees more task diversity with fewer annotations, so it generalizes better to new tasks, new objects, and new robot bodies.

The waypoint prediction equation

First in words:

predicted waypoint = function of image and task history; loss = sum of squared differences between predicted and labeled waypoints, plus a small penalty for jerky motion

Then the compact form:

L = sum_t ||W_pred(I_t) - W_label_t||^2 + lambda * sum_t ||W_t - W_t-1||^2

Every symbol:

Ltotal training loss (error to minimize)
W_pred(I_t)predicted waypoints from image I at frame t
I_tcamera image at frame t
W_label_thuman-labeled waypoints at frame t
||·||^2squared distance (sum of squared differences in x, y, z, etc.)
lambdasmoothness weight (how much to penalize jittery predictions)
W_t - W_t-1change from previous waypoint
A tiny worked example
Frame t: human labeled hand position at (10, 20, 30), grip-state open. Model predicts (10.2, 19.8, 30.1), grip open.
Prediction error: (0.2)^2 + (-0.2)^2 + (0.1)^2 + 0^2 = 0.04 + 0.04 + 0.01 + 0 = 0.09.
Frame t+1: human labeled (12, 21, 29), grip-closed. Model predicts (11.8, 21.2, 28.9), grip-closed.
Error: (0.2)^2 + (0.2)^2 + (0.1)^2 + 0^2 = 0.09.
Smoothness penalty: change from (10.2, 19.8, 30.1) to (11.8, 21.2, 28.9) = (1.6, 1.4, -1.2). Penalty = lambda * (1.6^2 + 1.4^2 + 1.2^2) = lambda * 5.32.
Total loss for these two frames: 0.09 + 0.09 + lambda * 5.32. If lambda = 0.1, loss = 0.18 + 0.532 = 0.712.

The model learns to predict waypoints that are close to human labels and smooth (not jittery), because both are penalized equally; increasing lambda makes the model prefer smooth paths over perfectly matching one frame.

What can go wrong

What can go wrong

Waypointsgrasps may not exist for all tasks. Some tasks (like pushing) do not have a clear grasp point. If you try to label a 'grasp' that does not exist, the annotation becomes arbitrary or noisy, and the model learns garbage. Failure: model predicts random grasp points for a pushing task, then the executor freezes.
Executor failure cascades. If the executor (the control policy that converts waypoints to motors) is buggy or poorly trained, the robot fails even if waypoints are perfect. The plan-then-execute split hides this: you see 'model predicts good waypoints' but the robot still does not move. Debugging is hard because you must test the executor separately.
Labeling is expensive and subjective. Humans must label 200,000 videos by hand (or semi-automatically). If one human says 'grasp at x=10' and another says 'x=11', the model gets conflicting targets. Dense per-frame annotation is slower than sparse labeling, so cost can creep up if not careful.
Done right. When waypoints are clearly defined (grasp pose, grip state), the executor is well-trained on the target robot, and annotations are consistent, the method works well across new task variants and even new robot bodies.
What a runnable demo should prove

What a runnable demo should prove

A demo should take a set of robot videos (previously unseen by the model), run the model to predict waypoints for each frame, display the predictions overlaid on the video (grasp point as a red dot, hand trajectory as a line, object position as a box), and then run the executor to generate motor commands. The demo should show two key things: (1) predicted waypoints match expert intent (they look sensible when you watch), and (2) the same waypoints generalize to a different robot body or task variant (waypoints are consistent even though joint angles change).

transfer_success_rate = (success on new robot + success on new task variant) / 2

The core proof is this: the same predicted waypoints lead to success on both the training robot and a robot with different body dimensions, showing that the waypoint layer is truly robot-invariant.
