MAS-Architect: Declarative Multi-Agent System Design via Separation of Concerns

Generate a team of specialized workers by describing roles and links separately from worker internals, so the system can search for a cheaper and stronger team layout.

Paper explainersAll themesAgents & Tool Use

Many multi-worker systems are assembled in one tangled step: choose how workers connect, decide what each worker does, and tune the whole arrangement together. That makes automatic design hard because changing the team layout also changes the meaning of each worker. MAS-Architect splits those concerns. It uses one description for the communication graph and another for worker behavior behind a shared interface. That separation lets the system search over team layouts from scratch, keep only the useful ones, and train toward layouts that solve tasks well with lower query cost.

Zero assumption version

Why automatic team design gets stuck

Suppose you want a system that solves a hard reasoning task by dividing work across several workers. One worker may gather facts, another may check them, and another may combine the results. A common approach hard-wires that structure first and then tunes the workers inside it. That limits the search because the system cannot easily ask whether a different team layout would be better.

The deeper problem is entanglement. If the worker code depends on one exact graph layout, then every structural change forces a redesign of the workers too. The search space becomes unstable because topology choices and worker implementation choices interfere with each other. MAS-Architect attacks that instability by separating team layout from worker internals.

The central move. Describe who talks to whom separately from how each worker operates, because that makes architecture search possible without rebuilding every worker each time the layout changes.

The algorithm as a flow

What it actually does

Represent the team declaratively.

Write the team structure as nodes and communication links under a shared interface so that worker internals do not depend on one fixed topology.

Generate candidate layouts.

Produce different team graphs from scratch so the search can consider chains, trees, reviewers, or wider groups depending on the task.

Run the team on benchmark tasks.

Evaluate each layout on tasks and record both task quality and query cost because good architecture should help both.

Distill strong designs.

Preserve useful layout patterns from successful candidates so the search starts from competent structures instead of random noise.

Explore nearby alternatives.

Search around the distilled designs so the system can improve them further by keeping the parts that already succeed and changing only nearby structure.

The hidden quantity

The hidden quantity

measured quantity  =  architectural fit between the task and the worker graph

The important hidden quantity is architectural fit: whether the chosen graph matches the structure of the task. A simple task may need only a short chain, while a task with many subgoals may need branching workers and a reviewer. That fit is not visible from one answer alone because two teams can both succeed once while one is much more wasteful.

MAS-Architect estimates fit by observing which layouts repeatedly solve tasks at lower query cost. A layout that routes information through the right number of workers avoids unnecessary back-and-forth, because each worker receives the amount of context it actually needs.

Why it works

Why separating layout from workers helps

When topology and worker code are fused, architecture search becomes brittle. A small graph change can invalidate the whole design because the workers were written for one exact message pattern. By enforcing one shared interface, MAS-Architect makes workers swappable across many graphs. That gives the search process a stable object to manipulate: the graph itself.

The distill-then-explore schedule matters because pure exploration wastes many trials on weak layouts, while pure reuse gets trapped in one pattern. Distillation copies the structural ideas that already work, such as when a checker improves factual tasks by catching wrong intermediate claims or when a branching plan helps decomposition by letting different subproblems be handled separately. Exploration then mutates those good seeds so the system can discover cheaper or stronger arrangements nearby by changing one part of a proven layout instead of restarting from random structure.

The result is better cost-quality balance because the framework is free to discover that some tasks need more coordination and others need less. It does not pay for a large team by default; it earns that cost only when the task structure justifies it.

Math after the picture

Score a team by quality minus communication cost

First in words:

A compact summary is to give each candidate team a score that rewards correct task solutions and subtracts the cost of the messages and worker calls needed to produce them.

Then the compact form:

score(team) = task_quality(team) - lambda * query_cost(team)

Every symbol:

teamone candidate multi-worker architecture
task_quality(team)how well that team solves the benchmark tasks
query_cost(team)the total query usage spent by the team while solving tasks
lambdahow strongly the search penalizes expensive team designs
A tiny worked example
Team A solves a task set with quality 82 and uses cost 40.
Team B solves the same task set with quality 79 and uses cost 18.
If lambda = 0.5, Team A scores 82 - 20 = 62.
Team B scores 79 - 9 = 70.
Team B wins because it gives up little quality while saving much more cost.

The real training method is richer than this one-line score, but the paper's main tradeoff is exactly this: keep quality high while reducing expensive coordination.

What can go wrong

What can go wrong

The shared interface can be too weak. If workers can only exchange shallow messages, then separating topology from implementation may remove useful specialization because the graph can no longer carry the information that some tasks need.
Search can still overfit the benchmarks. A layout may look efficient on the training tasks and then fail on a new benchmark because the search learned a narrow communication pattern rather than a generally useful one.
Distillation can preserve a local habit for too long. If the early good designs are only moderately good, heavy reuse can slow discovery of better layouts because the search keeps circling the same neighborhood.
Done right. The method works when the interface is expressive enough and the search balances reuse with fresh exploration, because then the system can discover task-matched teams without paying for unnecessary coordination.
What a runnable demo should prove

What a runnable demo should prove

Build a small architecture search loop over three or four worker roles such as planner, retriever, checker, and summarizer. Define a declarative graph format that specifies nodes and message links separately from worker internals. Evaluate candidate graphs on a few reasoning tasks with measured query cost, keep the strongest graphs, and explore nearby graph edits such as adding or removing a checker or changing a branch into a chain.

The demo should show that different tasks settle on different team layouts because task structure changes the right amount of coordination. It should also show that a searched layout can beat a hand-fixed one by achieving similar or better quality with fewer messages.

efficiency_gain = (quality_found / cost_found) - (quality_fixed / cost_fixed)

A convincing demo must show that separating topology from worker internals makes architecture search feasible, because the system can then improve cost and quality by changing the graph without rebuilding every worker.
