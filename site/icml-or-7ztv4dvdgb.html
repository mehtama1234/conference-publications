AutoRAS: Learning Robust Agentic Systems with Primitive Representations

Search over short symbolic building blocks for multi-agent system design, and score those designs using both task success and attack resistance so the final workflow keeps working when parts fail or inputs are adversarial.

Paper explainersAll themesAgents & Tool Use

Multi-agent systems are usually assembled by hand: choose a set of roles, connect them in some order, and hope the workflow still works when one agent is wrong or when an attacker perturbs the input. This paper automates that design process by representing the whole system as a sequence of symbolic primitives, then learning which primitive sequences produce strong task results and small performance drop under stress.

Zero assumption version

Why hand-built agent workflows break under stress

A multi-agent system has many design choices: how many agents to use, which role each agent plays, who sends information to whom, and what each step does. People usually choose these pieces manually. That often gives a workflow that looks good on the benchmark it was tuned for, but small disruptions can break it because the design never learned to cope with internal errors or hostile inputs.

The difficult part is that task quality and attack resistance interact. Adding more discussion can help one task because extra review can catch local mistakes, but it can also spread a wrong intermediate result more widely. Adding a checker can catch one failure but slow everything down. The paper reframes the problem as search over a compact design language, because then the system can evaluate many candidate workflows and prefer the ones whose performance degrades less when the environment turns hostile.

The move. Represent the agent system as a sequence of symbolic primitives and learn which sequences give high task quality while keeping performance drop small under attacks and internal failures.

The algorithm as a flow

What it actually does

Define a primitive set.

The system starts from a library of small structural and behavioral actions such as adding a reviewer, routing output, or revising a draft.

Encode a workflow as a primitive sequence.

Each candidate agent system is written as an ordered list from that library, so the search space becomes explicit and finite.

Run the workflow on tasks and stressed variants.

Candidates are executed on ordinary tasks and on perturbed settings that contain adversarial inputs or internal failure cases.

Compute a score from outcomes.

The objective rewards high clean-setting task quality and small degradation under stress, because a design is only useful if it keeps working when conditions worsen.

Update the design generator.

The learner shifts toward primitive sequences that repeatedly earn higher scores across task families because those sequences preserve more task quality under both clean and stressed settings.

What the paper changes

What the paper changes

The paper changes the unit of design. Instead of choosing a workflow by ad hoc prompting, it builds workflows from explicit primitives that describe both structure and behavior. Once the system design is expressed in that language, the learner can search, compare, and improve full workflows directly because each candidate is written in the same comparable form.

the object it moves  =  The system design language: explicit primitive sequences
The hidden quantity

The hidden quantity: degradation under stress

measured quantity  =  Performance degradation under stress

The central hidden quantity is not raw task score by itself. It is how much score is lost when the same workflow faces adversarial inputs or internal faults. Two designs can tie on clean tasks, yet one can collapse under small perturbations while the other loses only a little. That difference is what matters for deployment.

AutoRAS makes this quantity part of the learning signal. The learner observes both clean-setting results and stressed-setting results, then prefers designs whose gap is small. That encourages recovery structure, redundancy, and checking behavior only when those additions actually preserve performance under pressure.

Why it works

Why it works

The method works because it gives the search process a compositional language and a stress-aware score. The primitive language makes workflows comparable: one design may differ from another by only one added review step or one changed routing edge, which lets the learner discover which structural choices actually matter. The stress-aware score then keeps the search honest, because a workflow is rewarded only when it performs well and keeps that performance under attack.

This matters more than optimizing clean accuracy alone. If the score ignored stressed settings, the learner would often select brittle workflows that exploit quirks of the benchmark. By including degradation directly in the objective, the search pushes toward designs that contain repair, checking, or diversification only when those components demonstrably preserve output quality.

The objective

First in words:

Score a workflow by its clean-setting result minus a weighted penalty for how much it degrades under stress.

Then the compact form:

objective(workflow) = clean_score(workflow) - lambda * max(0, clean_score(workflow) - stressed_score(workflow))

Every symbol:

clean_score(workflow)task quality on the ordinary benchmark setting
stressed_score(workflow)task quality on attacked or failure-prone settings
lambdahow strongly the learner penalizes performance drop
max(0, ...)counts only positive degradation, not accidental improvement
A tiny worked example
Workflow A gets 90 on the clean setting and 50 under attack.
Its drop is 90 - 50 = 40.
With lambda = 0.5, objective(A) = 90 - 0.5 * 40 = 70.
Workflow B gets 86 on the clean setting and 74 under attack.
Its drop is 86 - 74 = 12.
Objective(B) = 86 - 0.5 * 12 = 80.
The learner prefers Workflow B because it keeps more of its quality when conditions worsen.

The point of the penalty is to reward designs whose quality survives, not designs that look strong only in the easiest setting.

What can go wrong

What can go wrong

Primitive library is too weak. If the primitive set cannot express useful repair or checking behavior, the search will never discover a strong workflow because the right building blocks do not exist.
Stress tests are unrealistic. If the attacked settings do not resemble real failure modes, the learner may optimize for synthetic tricks instead of genuine system reliability.
Penalty weight is mis-set. If the degradation penalty is too small, brittle high-score designs dominate. If it is too large, the learner can prefer overcautious designs that protect themselves by doing too little useful work.
Done right. Use a primitive library that can express real repair behavior, evaluate on realistic stress cases, and tune the degradation penalty so that the search values survivable quality rather than empty caution.
What a runnable demo should prove

What a runnable demo should prove

Give the search system a primitive library with roles such as propose, critique, verify, revise, and stop. Compare a hand-built baseline against searched workflows on both ordinary tasks and adversarial variants where one agent receives misleading context or a corrupted intermediate result.
