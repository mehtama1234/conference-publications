MVP-LAM: Learning Action-Centric Latent Action via Cross-Viewpoint Reconstruction

Learn action representations from videos by forcing one camera view's action code to predict what happens next in a different camera view.

Paper explainersAll themesRobotics & Control

When a robot learns to grasp from human videos, it needs to extract what the action actually is — not just memorize camera-specific details like lighting or angle. This paper shows how to train action representations that focus on the real movement and ignore viewpoint noise by asking one camera view to explain the future in a different camera view.

Zero assumption version

The viewpoint trap: actions tangled with camera angles

When robots learn to grasp from human videos, they need to compress each action into a code — a small set of numbers. A naive approach: watch the frames and guess what action happened. But this breaks because the code soaks up camera-specific junk: sunlight from the left, the angle of the table, the person's height. Two videos of the identical grasp from different camera angles produce wildly different codes.

A beginner might try: collect videos from one camera angle and hope the code stays pure. This fails because real robot deployments see new angles, new lighting, new tables. The code learned from one view does not generalize.

The core problem. Action codes end up encoding camera angles and lighting instead of the real action, making them useless when the camera moves.

The algorithm as a flow

What it actually does

Record videos

Film the same robot action or human task from two or more camera angles at once.

Compress one view

Train an encoder that reads left-camera frames and squashes them into a small action code.

Decode to other view

Build a decoder that takes that action code and reconstructs what the right-camera will see next.

Measure cross-view loss

Measure how wrong the reconstruction is; tune the encoder and decoder to minimize error.

Strip viewpoint noise

Because lighting and camera angle do not transfer between views, the code is forced to retain only real action.

What the paper changes

The one thing the paper changes

The paper changes how action codes are learned. Instead of a single-view encoder that predicts actions from one camera, it builds a cross-view encoder: given frames from camera A, produce an action code that must reconstruct the future pixels in camera B.

The hidden quantity

The hidden quantity: mutual information with ground-truth action

measured quantity  =  how much action the code retains

The paper measures a hidden quantity: does the learned action code actually contain the ground-truth action, or just camera artifacts? The paper calls this mutual information — a number (in bits) that counts how much information the code shares with the true action, measured on held-out data.

The paper estimates this by asking: given the action code, how well can a separate predictor guess the true action label (grasp, pinch, push, etc.)? A higher score means the code absorbed the action; a low score means the code is full of camera noise. MVP-LAM's key claim: cross-viewpoint reconstruction training raises this score higher than single-view training.

Why it works

Why it works: the cross-view bottleneck

The encoder reads left-camera frames and squeezes them into a tiny code. The decoder must then reconstruct what the right camera sees next, using only that code. Camera-specific junk — sunlight from the left, the table tilt in the left frame, the arm's position in the left camera's coordinates — does not transfer to the right camera, because the right camera has different lighting, a different viewing angle, and a different coordinate system. The decoder cannot use sunlight or angle to predict right-camera pixels; only the pure hand motion (gripper opening, reach direction, approach angle) appears in both views.

So the encoder is forced to discard camera junk and keep only the action. This is a bottleneck: the code is small (many details cannot fit), and the only details that pass through are the ones that appear in both views — the action itself. The decoder learns to take the action code and predict which pixels the right camera will see next, using the known camera angles and positions.

inputLeft-camera frames (pixels + lighting + table angle)
stepEncoder squashes to small action code
stepDecoder reads code, knows right-camera angle and position

The cross-viewpoint reconstruction loss

First in words:

Take the action code from camera A and try to reconstruct the pixels in camera B. The penalty is the sum of squared differences between predicted and actual pixels. Sum this over all pixel positions.

Then the compact form:

L = sum_pixels (predicted_right_pixels - actual_right_pixels)^2

Every symbol:

Lthe total error the optimizer tries to shrink
predicted_right_pixelswhat the decoder guesses the right camera will show
actual_right_pixelswhat the right camera actually showed in the video
A tiny worked example
Say the right camera has 100 pixels and the prediction is off by 0.1 per pixel on average.
Error for one pixel: (predicted - actual)^2 = (0.1)^2 = 0.01.
Total error: 100 pixels × 0.01 = 1.0.
If a pixel is off by 0.2, that single pixel contributes 0.04, making the total 1.03.
The encoder learns to keep only information that reduces this pixel error across all 100 pixels and all frames.

The magic is that pixels only match if the code captures the true action motion, not camera-specific confounds.

What can go wrong

What can go wrong

Need multi-view video. The method requires recording the same action from multiple camera angles. Single-camera datasets cannot be used; this is a hard constraint.
Occlusions break reconstruction. If one camera view shows the hand but the other view has the hand hidden behind the table, reconstruction becomes impossible and the code must memorize the occlusion, not the action.
Synchronized timing required. If the two cameras are not perfectly time-synchronized, frame A from the left camera does not match frame A from the right camera. Timestamp misalignment ruins the loss signal.
Scaling to many tasks. MVP-LAM works well when the dataset is consistent: similar lighting, similar robot or hand, similar tasks. It is less clear if one dataset of grasps and one dataset of pouring can be mixed; each may need separate training.
What a runnable demo should prove

What a runnable demo should prove

Record 10 seconds of a robot grasp from two mounted cameras. Train a simple encoder (e.g. a 3-layer convolutional neural network) using the cross-viewpoint objective: encode left-camera frames into a code of fixed size (e.g. 128 numbers), then train a decoder to reconstruct right-camera frames from that code alone. Log the reconstruction error as training progresses. Then freeze the encoder and test it on a new grasp task (a different object, a different hand position). Measure: on new data, how well does the code from camera A still reconstruct camera B? This should stay high if the code is action-centric and low if it is camera-specific.

action_generalization = (reconstruction_error_known_task - reconstruction_error_new_task) / reconstruction_error_known_task

The demo succeeds when the code trained on known grasps still reconstructs new grasps from the alternate camera, proving the code learned the action, not the camera.
