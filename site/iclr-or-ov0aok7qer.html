PPE: Positional Preservation Embedding for Token Compression

Instead of throwing away position information when squishing visual tokens, embed position data directly into each token so the model remembers where each piece came from.

Paper explainersAll themesMultimodal

Multimodal models (ones that read images and text together) compress images into lists of tokens (tiny numeric summaries of image pieces) to save memory. But when tokens get squished together, the model forgets which part of the image each token came from. PPE solves this by keeping position tags attached to each compressed token, so the model never loses track of where things are.

Zero assumption version

Why image compression breaks layout understanding

Multimodal models read images as sequences of tokens—tiny numeric summaries of patches (small rectangular pieces) of the image. A high-resolution image becomes hundreds of tokens, which is slow and memory-intensive. So researchers built token merging methods: algorithms that cluster nearby tokens together and replace a dozen tokens with one.

But merging creates a hidden cost: the merged token has no memory of where its original pieces came from. A compressed token that represents six different regions of the image gets the same generic position tag as every other merged token. When the model later asks itself 'what is in the upper-left corner?', it has forgotten which patch was upper-left because all position information was averaged away. This breaks tasks where layout matters: counting objects, reading text from images (which requires knowing character position), and understanding temporal order in video.

The problem in one sentence. Existing token merging methods forget position information, breaking any task where spatial or temporal location matters.

The algorithm as a flow

What it actually does

Assign position ID to each patch

Before merging, mark every patch with its location coordinates (row, column, frame number).

Disentangle positions for merging

When two patches merge, split their position IDs into separate encoded pieces so both can be stored in one token.

Embed positions into token dimension

Add the position codes directly into the merged token as extra features, not as separate metadata.

Apply to multiple compression rounds

PPE can be applied layer by layer in cascade, preserving fine-grained layout even with aggressive compression.

Model reads position from token

When the model attends to a merged token, it can recover position information and make layout-aware decisions.

What the paper changes

The single thing being changed

PPE changes how position information is encoded when visual tokens are merged. Instead of averaging position tags to a single value (losing all spatial context), PPE keeps encoded versions of multiple original positions packed inside each merged token.

the object it moves  =  position encoding of merged tokens
The hidden quantity

The hidden quantity: preserved positional precision

measured quantity  =  position information retention rate

When tokens merge, how much position information survives? This is a measurable quantity: the fraction of original patch locations that the compressed token can still distinguish or reconstruct. In traditional merging, when six patches become one token with one generic position tag, this retention is near zero—you have lost five sixths of the location knowledge.

PPE measures and preserves this by encoding multiple original position IDs into the token's feature space. The paper estimates this by checking whether downstream attention patterns can recover the correct spatial relationship (e.g., does the model's attention later correctly identify that part of a token comes from the upper-left?).

Why it works

Why it works: the causal chain

When you merge tokens naively, you lose position because you compute a single average. PPE sidesteps averaging by breaking position into pieces. Here is the concrete chain:

Each visual token starts with a position ID: a coordinate like (row 3, column 5, frame 2). When two tokens merge, PPE does not average their IDs; instead, it encodes both IDs in a disentangled way—meaning the encoding keeps the two positions separable in feature space. This is possible because position is just arithmetic: coordinates are numbers, and you can represent multiple numbers in a single list (called a vector, which is just an ordered collection of numbers) as long as you use different slots or features.

The merged token's feature list now contains encoded versions of both original positions. Later, when the transformer model (a type of neural network that reads sequences of tokens and finds patterns in how they relate to each other) processes the token, it has access to both position signals. The model can use self-attention (a mechanism where tokens look at each other and reweight their importance based on similarity) to recover which spatial region a feature belongs to, because the position encoding is attached to it.

This works layer by layer: PPE can be applied at multiple stages of compression (early layers merge loosely, later layers merge more aggressively), and each stage preserves position from the previous stage, so layout information never completely disappears.

The equation and worked example

First in words:

For each merged token, encode the positions of all its original patches as separate features. Position_merged = Encode(position1) + Encode(position2) + ... where Encode is a function that turns grid coordinates into vectors and keeps them separable. The token is smaller (fewer original patches squeezed into one), but its position dimension is expanded to hold multiple original coordinates.

Then the compact form:

token_merged = [features_averaged, pos_code_1, pos_code_2, pos_code_3]

Every symbol:

token_mergedthe new smaller token after merging
features_averagedthe visual content (color, texture) of all merged patches combined
pos_code_iencoded position of the i-th original patch
Encode()a function that turns (row, column) coordinates into feature vectors that don't overlap
A tiny worked example
Suppose three patches with coordinates (0,0), (0,1), (1,0) merge into one token.
Standard merging: position becomes average = (0.33, 0.33), losing detail.
PPE: position codes are Encode((0,0))=[1, 0, 0], Encode((0,1))=[0, 1, 0], Encode((1,0))=[0, 0, 1].
Merged token includes: [visual_features, 1, 0, 0, 0, 1, 0, 0, 0, 1] — three separate position slots, all preserved.
Now the model can ask: 'which parts came from the left side?' and recover positions (0,0) and (1,0) from the token.

Disentangled position codes mean each original location gets its own feature slot in the merged token. When the model later attends to this token, it can recover position because each position has its own dedicated feature channel, not averaged away—so the model never forgets how many patches are packed inside.

What can go wrong

What can go wrong

Too many original patches in one token. If merging ratio is too aggressive (hundreds of patches into one token), even disentangled position codes have limited space to represent all positions. The token becomes a lossy compression of its own locations.
Position encoding conflicts. If the Encode function is not truly disentangled (if two different positions produce overlapping feature representations), the model cannot recover which region is which. This requires careful design of the position encoding scheme.
Incompatibility with certain merging algorithms. PPE assumes that the merging algorithm preserves some structure. If merging is random or chaotic, position codes cannot guide the model reliably.
Done right. When position encoding is truly disentangled, merging ratio is reasonable (e.g., 90% compression, not 99%), and the merging algorithm respects visual structure, PPE keeps position information intact across compression and cascade stages.
What a runnable demo should prove

What a runnable demo should prove

Build a small multimodal model that reads images of grids with labeled objects. Create two versions: one that merges tokens without PPE, and one with PPE. Both compress to 50% of original token count. Then ask the model to answer layout-sensitive questions: 'Is the red square in the top half or bottom half?' and 'How many objects are in the left column?'. Measure accuracy on these questions.

layout_accuracy = (correct_positional_questions / total_positional_questions) * 100

The PPE version should correctly answer 80%+ of layout questions after compression, while the naive merging version drops to 40-50%, proving that position preservation is the actual difference.
