PPE: Positional Preservation Embedding for Token Compression

When a vision-language model compresses its visual tokens to run faster, explicitly remember where each token came from so the model still understands layout and motion.

Paper explainersAll themesMultimodal

Multimodal models read images as a list of small pieces called tokens and answer questions about them. To speed up inference (when the finished model answers a new question), engineers shrink the token list by merging similar pieces together. The problem is, existing merge methods forget spatial positions — they mix tokens from opposite corners into one blob, destroying the model's sense of layout and motion. PPE solves this by encoding position information directly into each compressed token.

Zero assumption version

Visual models run slow when they read too many tokens

A vision-language model works like this: it splits an image into hundreds of small patches, each a token (just a list of numbers). It treats the whole image as a sequence, like reading left-to-right word by word, and outputs text that describes the image or answers a question. The catch: processing hundreds of tokens is slow and expensive.

To speed up inference (when the finished model answers a new question), engineers merge similar tokens together before feeding them to the core model. This shortens the sequence, so inference runs faster because the model processes fewer items. A beginner's naive approach: just throw away the tokens that look least important, or merge the most similar-looking ones. But this breaks the model's spatial sense. When you merge a token from the top-left corner with one from the bottom-right, the resulting merged token no longer knows where it came from. The model forgets the layout of the image and struggles on tasks that need precise spatial understanding (like reading text in a photo) or temporal understanding (like spotting motion across video frames).

The core problem. Existing token compression loses spatial and temporal positional information, making the model blind to layout and motion.

What the paper changes

The one thing PPE changes

PPE modifies how tokens are merged: instead of discarding positional information during compression, PPE encodes positional data (row, column, time) directly into each compressed token. This is purely an encoding trick — no new trainable weights or changes to the model architecture.

The hidden quantity

The hidden quantity: position reconstruction error

measured quantity  =  spatial-temporal position loss

When you merge multiple tokens into one, you lose information about where each piece came from. The hidden quantity PPE tracks is how much of that positional information survives in the merged token. PPE measures this by checking whether the downstream model can still infer the original positions of the patches that were merged. Lower position loss means the model retains clearer spatial and temporal understanding.

The paper estimates this implicitly by testing the model on tasks that require position awareness (reading text layout, tracking motion) and checking whether performance holds steady. If the position information survives in the compressed token, the model can still solve these position-dependent tasks at high accuracy. Better retention on these tasks means the hidden position information is still there, because those tasks would fail if position cues were truly lost.

Why it works

Why position preservation fixes the problem

Token merging solves slowness by shortening the sequence. The cost is lost positional information. PPE recovers that cost by making position explicit. Here is the causal chain:

When you merge tokens, you are collapsing multiple visual pieces into one representation. Normally, the merged token forgets the row, column, and time-step coordinates of its sources. PPE adds those coordinates back: it encodes them as a list of numbers and embeds them alongside the visual content in the merged token. This means the compressed token is not just a blob of visual features; it is a visual blob tagged with position labels.

When the model processes this position-tagged token, it can reason about where the patch came from and infer spatial relationships (top vs. bottom, left vs. right) and temporal order (frame 1 vs. frame 2). This restores the model's ability to understand layout and motion. On tasks that depend on these cues (like reading text stamped onto an image or tracking where something moved), the model performs much better than naive merging because the position signal is still there.

PPE also works with cascade compression (merging repeatedly in rounds). In each round, the position tags carry forward, so spatial and temporal structure survives multiple collapses. This is why the method is generic: it wraps around any existing merging strategy without changing that strategy's logic.

Math after the picture

The formula behind position encoding

First in words:

For each merged token, take all the row, column, and time indices of the source tokens and convert each coordinate into a list of numbers (using learned or fixed basis functions). Concatenate these lists to the merged token representation. The downstream model sees the merged visual content plus position codes.

Then the compact form:

merged_token = [visual_features] + [pos_encode(row_1), pos_encode(col_1), pos_encode(time_1), pos_encode(row_2), pos_encode(col_2), pos_encode(time_2), ...]

Every symbol:

visual_featuresthe compressed visual content from merged source tokens
pos_encode(coordinate)a fixed or learned function that turns a coordinate into a list of numbers
row, col, timethe spatial row/column and temporal frame index of each source token
merged_tokenthe final compressed token fed to the main model
A tiny worked example
Suppose we merge tokens from positions (row=2, col=3, time=1) and (row=4, col=1, time=1).
Visual features of the merge: [0.5, -0.2, 0.7] (three numbers holding color and texture).
Position encoding for (2,3,1): [0.9, 0.1, 1.0] (using a fixed formula). Position encoding for (4,1,1): [0.3, 0.8, 1.0].
Merged token becomes: [0.5, -0.2, 0.7, 0.9, 0.1, 1.0, 0.3, 0.8, 1.0] (nine numbers total).
The downstream model now receives a token that says visual content (0.5, -0.2, 0.7) came from two places: upper-center and lower-left. It can use this to infer layout.

Position encoding turns coordinates into numbers so they can be stored alongside visual features, letting the model reason about both content and location jointly.

What can go wrong

What can go wrong

Position encoding overhead. Adding position codes to each token increases the token dimension slightly. If the dimension grows too much, compression savings shrink and inference speed gain diminishes. The paper limits this by using compact position encodings.
Cascade compression artifacts. In later merging rounds, position codes from previous rounds can accumulate or conflict. If positional noise propagates, the downstream model may struggle to extract the original coordinates. This is mitigated by disentangling coordinates (keeping row, column, time separate).
Tasks that do not need position. On coarse-grained classification tasks (e.g., does this image show a dog?), position cues may provide no benefit or even add noise. PPE still helps marginally because position is cheap, but gains are smaller.
Done right. PPE shines on fine-grained spatial tasks (text recognition, layout understanding) and temporal tasks (video understanding). It adds no trainable weights, so it can be added to any token merging method without retraining.
What a runnable demo should prove

What a runnable demo should prove

Build a small vision-language model and compress its image tokens using standard merging. Then add PPE position encoding on top. Measure performance on two tasks: (1) a layout-aware task like describing where objects are in an image, and (2) a motion-aware task like tracking an object across video frames. Compare naive merging vs. PPE merging. The demo should show that naive merging breaks spatial and temporal reasoning, but PPE preserves it.

position_preservation_gain = (ppe_layout_score - naive_layout_score) + (ppe_motion_score - naive_motion_score)

The demo must make it impossible to miss that position information is the difference between a model that understands layout and motion and one that does not.
