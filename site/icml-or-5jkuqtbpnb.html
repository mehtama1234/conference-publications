UAV² Unified Adaptive Scheduling for Drone Flight

Teach a drone's onboard computer what order to run its navigation and steering tasks by watching how well the drone flies, instead of using fixed timing rules.

Paper explainersAll themesRobotics & Control

Drones need two things happening constantly: figuring out where to go next (navigation) and actually steering the aircraft (flight control). Right now, most drones run these on separate chips, so no one piece of code can coordinate them together. This paper moves them onto one computer and uses a learning system (a program that adjusts its decisions based on feedback) that watches the drone's flight path accuracy to discover which order of tasks keeps the drone on course best.

Zero assumption version

Separate brains break coordination

Every drone has two jobs running all the time. Navigation asks: Where am I? Where do I want to go? What is the next target? Flight control asks: How do I angle the motors right now to actually get there? Most drone platforms split these between two separate computers, like having a car's GPS on one device and the steering wheel on another.

When the two are separate, nothing sees the whole picture. If the navigation gets delayed by one millisecond and the steering doesn't know, the drone wobbles. If the flight control is tuned too aggressively and navigation is too slow to keep up, they fight each other and the drone crashes or drifts. A beginner might say: just run both as fast as possible, or run them on a fixed schedule like every 10 milliseconds. But these do not work because sometimes navigation needs more time to think (the world is complex), sometimes flight control needs to run more often (turbulence is here now), and the two interact in hidden ways.

In one sentence. The paper puts navigation and flight control on one computer and learns the best switching schedule by watching how well the drone actually flies.

The algorithm as a flow

What it actually does

Merge onto one platform

Navigation and flight control run on the same onboard computer, so decisions are synchronized.

Frame scheduling as a puzzle

At each moment, pick which task runs next (navigation or flight control) to minimize how far the drone drifts from its target.

Watch the drone fly

As the drone completes each short cycle, measure how well it tracked its path.

Reward good choices

When a task order leads to lower drift, increase the weight on that choice, because lower drift means the drone is following commands more accurately.

Discover the pattern

Over many flights, which tasks to run first in different situations becomes clear because the weighting pushes toward orders that reduce drift.

What the paper changes

What the paper moves

The paper changes the scheduling decision — which task runs at which moment in the onboard computer's cycle. Instead of a fixed sequence (like navigation, then flight control, then navigation again every fixed 10 milliseconds), the scheduler learns to pick each task adaptively based on how well the drone is currently flying.

the object it moves  =  scheduling order
The hidden quantity

Flight tracking error — the signal the system learns from

measured quantity  =  tracking error per cycle

The hidden quantity is how far the drone actually strayed from its intended path in this one cycle, measured in meters or attitude angle. This is not the same as the problem statement — we are not looking at why scheduling fails in general, we are looking at the specific number the learning system uses to decide if a schedule choice was good.

The paper estimates this by running the drone in simulation (a hardware-in-the-loop test bench where the autopilot software runs on real chips but the physics is simulated) and recording position and heading after each cycle. The learning system uses this error signal to rank different scheduling choices: if task order A produces smaller tracking error than task order B, the system will gradually favor A in future flights because a smaller error means the drone is obeying commands more precisely.

Why it works

How changing the schedule fixes the problem

The core mechanism is tight feedback: each time the drone completes a cycle, the system immediately knows whether that schedule choice was good (small error) or bad (large error). Because the two tasks are now on one computer, the scheduler can react instantly if it realizes navigation is falling behind or flight control is stale. In contrast, the old separate-computer design had no way to know; each computer just did its thing on its fixed schedule.

The learning system (called reinforcement learning) works like this: try a scheduling order, watch the drone's error shrink or grow, and then nudge the system's decision weights toward choices that led to smaller errors. Over hundreds of flights in simulation, this nudging finds schedules that balance the two competing demands — sometimes navigation needs the computer first to think ahead, sometimes flight control needs it to respond to immediate wobble. A fixed schedule can never adapt to these changing demands; a learning system can.

Math after the picture

The scheduling reward formula

First in words:

Total reward equals the negative of tracking error, minus a small cost for computational work.

Then the compact form:

R_t = - error_t - alpha * work_cost_t

Every symbol:

R_treward for this cycle
error_thow far drone drifted from target
work_cost_tcomputational load of running both tasks
alphahow much to penalize high CPU usage (tuning knob)
A tiny worked example
Cycle A: navigation runs, then flight control. Drift = 2 centimeters. Work = 80% CPU. Reward = -2 - 0.1 * 80 = -10.0
Cycle B: flight control runs, then navigation. Drift = 0.5 centimeters. Work = 75% CPU. Reward = -0.5 - 0.1 * 75 = -8.0
Cycle B has higher (less negative) reward, so learning nudges the system toward that order.

The learning system collects these rewards over many cycles and adjusts its scheduling choices to maximize cumulative reward — that is, to keep drift small and CPU usage reasonable.

What can go wrong

What can go wrong

Learning only in simulation, not on a real drone. The system is trained in a simulated physics world (hardware-in-the-loop), so it may overfit to quirks of that simulation. Wind, real-world sensor noise, or motor delays might differ, causing the learned schedule to fail on actual hardware.
Hidden interdependencies between navigation and flight control. The paper treats them as two separate tasks, but in reality they might have complex feedback loops (flight wobbles affect sensor readings, which affect navigation). The learning system might not discover these interactions if they are rare or delayed.
Tuning the learning rate and reward weights is manual. The coefficients in the reward formula (how much to penalize CPU work, for example) are set by hand. A wrong setting can trap the learning system in a local optimum or cause instability.
Done right. Train on a diverse set of simulated scenarios (calm air, wind, heavy load, lightweight), test on trajectories the learning system never saw, and gradually increase the gap between simulation and reality to catch brittleness early.
What a runnable demo should prove

What a runnable demo should prove

Build a simple drone autopilot simulator (a 2D position-and-heading model that responds to navigation and flight-control inputs). Create two drones: one with a fixed schedule (navigation, then flight control, alternating every 50 milliseconds) and one with a learned schedule trained on 100 simulated flights. Fly both drones along the same path (e.g., follow a square, hover in wind, track a moving target). Measure position drift over 60 seconds for each.

The learned schedule must show smaller mean drift than the fixed schedule. Ideally, show a plot of drift over time: the fixed schedule should oscillate and grow, while the learned schedule should stay low and stable.
