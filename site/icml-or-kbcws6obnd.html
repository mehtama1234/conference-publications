TreeCUA: Efficiently Scaling GUI Automation with Tree-Structured Verifiable Evolution

Instead of collecting GUI trajectories as flat lists, organize them as trees where branches share common steps, then learn from shared structure to plan better.

Paper explainersAll themesAgents & Tool Use

Teaching a computer to use graphical interfaces (clicking buttons, filling forms) requires collecting thousands of real action sequences. Today's systems collect these as one-by-one independent recordings, wasting effort on redundant clicks. This paper observes that interface exploration naturally follows a tree structure — many attempts share early steps like opening the same app or navigating to the same page. TreeCUA organizes those recordings as a tree, reuses shared branches (meaning each click is stored only once instead of repeated), and learns from how adjacent branches differ (because when two nearly identical paths diverge, their differences stand out and teach the model what matters), making data collection far cheaper and planning far better.

Zero assumption version

The bottleneck in teaching computers to use screens

A computer that can use a website or desktop app needs to learn thousands of action sequences: click here, type that, scroll, wait. Each sequence is called a trajectory. The naive approach collects trajectories one at a time, independently. When the agent explores a website, it might click File > Open > Browse in attempt 1, then start over and click File > Open > Browse again in attempt 2. Every redundant click means wasted computation and wasted time.

Worse, the quality of learned planning depends on having many trajectories that show how to reach different goals. But most collected trajectories follow similar early steps. A system exploring a web form might visit the login page in 90% of its attempts. Collecting that login page redundantly a hundred times teaches nothing new about what comes after.

The problem in one sentence. Collecting GUI trajectories as independent recordings wastes computation on redundant early steps (because each identical click is recomputed), and fails to use the natural structure of exploration to improve learning (because when two paths diverge only at the end, seeing both teaches you nothing the first one did not already teach).

The algorithm as a flow

What it actually does

Collect trajectories with multiple agents

Different agents explore the same interface in parallel, documenting every click and outcome.

Verify each action's result

For each click, check whether the intended effect actually happened (e.g., the button opened a dialog).

Arrange into a tree

Merge trajectories that share early steps into branches, eliminating duplicate recording.

Balance exploration depth and breadth

Add new branches to explore harder tasks and diverse goals, avoiding redundant repetition.

Train on branches, not just individual paths

The learning algorithm uses differences between adjacent branches to improve planning predictions, because when two branches share most steps and diverge only at the end, the difference between them teaches which exact features matter for planning.

What the paper changes

What the paper actually changes

Instead of storing and learning from GUI trajectories as isolated sequences, TreeCUA stores them as a tree where branches share common early steps and split when actions diverge. The object is the data structure and training procedure used to represent and learn from these action sequences.

the object it moves  =  trajectory data structure: from flat list to tree
The hidden quantity

The hidden quantity: Trajectory similarity and branch relatedness

measured quantity  =  Branch relatedness score

A branch is a path in the tree from some node to a leaf. The hidden quantity the paper measures is how much learning one branch can borrow from neighboring branches — that is, how closely related two branches are. Two branches that share many common early steps and diverge only near the end are highly related; an algorithm that learns one of them has already captured most of the knowledge needed for the other.

TreeCUA estimates this relatedness by examining the tree structure itself. If two branches share a long common prefix (early steps), they are related. The paper uses this structure to determine which trajectories should influence each other during learning.

Why it works

Why organizing as a tree makes planning faster and better

The core mechanism has two parts. First, redundancy elimination: when ten different exploration attempts all click the same button first, the tree stores that click once, and every trajectory shares that single node. This reduces computation and storage. Second, shared learning: when two branches diverge for the first time at node X, the model learns that whatever comes after node X depends on which branch is taken. By comparing the trajectories of adjacent branches — which are nearly identical except for that final divergence — the model learns which exact features matter for planning. This comparison teaches the model far more than learning from one isolated trajectory, because differences stand out sharply when context is nearly the same.

Additionally, the paper uses world knowledge (e.g., "buttons are likely near the top of a dialog") to guide exploration, and global memory backtracking to avoid collecting low-quality trajectories (e.g., attempts that lead to dead ends). Together, these mechanisms mean the data collected is both smaller and more informative.

The learning equation: difference-based ranking

First in words:

For two adjacent branches B1 and B2 that diverge at a node, the penalty is: if the model scores B1 lower than B2 but B1 is actually better, incur a loss; otherwise, no loss. This trains the model to rank branches correctly even when their contexts are nearly identical.

Then the compact form:

loss = log(1 + exp(s(B2) - s(B1))) where B1 is better

Every symbol:

s(B)the model's score (confidence) for branch B
B1the ground-truth better branch
B2the comparison branch
exp(...)the exponential function
log(...)the natural logarithm
A tiny worked example
Suppose two branches diverge at the same node. Branch A (model score 2.1) is better (reaches goal). Branch B (model score 2.5) is worse (gets stuck).
Difference s(B) - s(A) = 2.5 - 2.1 = 0.4.
exp(0.4) = 1.49, so log(1 + 1.49) = log(2.49) = 0.91.
This loss (0.91) penalizes the model for ranking B higher than A, teaching it to downweight B and upweight A.
If model scores were flipped (A=2.5, B=2.1), the difference would be -0.4, exp(-0.4)=0.67, log(1.67)=0.51 — a smaller loss, meaning the ranking is closer to correct.

The equation learns branch rankings by penalizing reversed orderings, and the penalty grows sharply when the model is confident in the wrong direction — exactly when learning is most needed.

What can go wrong

What can go wrong

Poor tree construction. If the tree-building algorithm incorrectly merges two trajectories that should remain separate (because the interface state is actually different), the tree is wrong and comparisons between those branches are misleading. The paper's solution: verify each action before merging.
Imbalanced exploration. If the agent explores only one type of task (e.g., only login workflows), the tree becomes very deep but narrow, and branch comparisons do not teach diversity. The paper's solution: the adaptive algorithm explicitly balances depth (harder tasks) and breadth (different goals).
Low-quality trajectories contaminate neighbors. If one branch gets stuck (fails to reach any goal), learning from that branch teaches the model to fail. The paper's solution: memory backtracking — if exploration reaches a dead end, the system backtracks and retries from an earlier node rather than committing the failed branch.
Done right. Tree structure, verification, balancing, and backtracking together ensure that collected data is both compact and clean, and that branch comparisons are valid lessons.
What a runnable demo should prove

What a runnable demo should prove

Build a simple interface task (e.g., a series of web forms or a desktop application with buttons and text fields). Collect two datasets: one using flat independent trajectories, one using TreeCUA's tree structure. Train two separate planning models on each. Measure both the size of collected data (how much storage and computation) and the accuracy of the model at predicting the next correct action on held-out test tasks.

improvement = (accuracy_tree - accuracy_flat) / accuracy_flat × 100%; data_reduction = (size_flat - size_tree) / size_flat × 100%

The demo must show that tree-structured data is both smaller to collect and produces a model that predicts actions more accurately, especially on new interface layouts the model has never seen.
