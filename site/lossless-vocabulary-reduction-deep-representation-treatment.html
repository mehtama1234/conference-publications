Lossless Vocabulary Reduction

This page treats vocabulary reduction as a first-principles representation problem: which word pieces can be removed without removing what the model can still say, read, and recover?

Core idea

A vocabulary is the model's box of reusable pieces

A language model does not read raw text as whole thoughts. It first breaks text into tokens. Those tokens are the small pieces the model is allowed to handle.

So vocabulary reduction is not a boring cleanup step. It changes the first representation of language. It decides which strings deserve their own symbol and which strings must be rebuilt from smaller pieces.

text -> token pieces -> token embeddings -> model computation -> answer

The first-principles question is simple: if we shrink the model's piece set, can it still preserve the same usable meaning?

Tokens as chunks

The model sees chunks, not words

A person sees the word internationalization and may understand it as one word. A tokenizer may split it into several pieces. Different vocabularies split it differently.

Large vocabulary
internationalization

One large reusable piece. Short sequence, but the vocabulary must store that piece.

Smaller vocabulary
internationalization

Two smaller pieces. Slightly longer sequence, but fewer special entries in the vocabulary.

This tradeoff is everywhere. A bigger vocabulary gives more ready-made chunks. A smaller vocabulary forces the model to build meanings from parts.

What lossless means

Lossless does not mean nothing changes

After vocabulary reduction, the token list changes. The sequence may become longer. Some old tokens disappear. The model may need to read two or three pieces where it previously read one.

Lossless means the removed token was not carrying a meaning that cannot be rebuilt. The surface token is gone, but the useful content survives.

not required: same token sequence required: same text recoverable same important distinctions preserved same downstream behavior retained

That is the deeper point. We do not care whether the model uses the exact same symbol. We care whether the new set of symbols can still carry the job-relevant differences.

Cost

Every vocabulary entry has a price

Each token in the vocabulary needs an embedding row. The model has to store it, update it during training, and consider it when predicting the next token. A huge vocabulary can waste memory on rare pieces that barely matter.

But removing too much creates another cost: sequences get longer. The model spends more steps reading and producing text. So the problem is not simply smaller is better.

Large vocabulary

Shorter sequences, more stored symbols, more rare entries.

Small vocabulary

Fewer stored symbols, longer sequences, more rebuilding from parts.

Good vocabulary

Keeps pieces that save real work and removes pieces that can be rebuilt cheaply.

Safe removal

A token is removable only if its work can be done by other tokens

Suppose the vocabulary contains refund, tax, deadline, and also a rare token tax_refund_deadline. The rare combined token may look useful, but maybe it is not needed. The model can still express the idea using the smaller pieces.

tax_refund_deadline tax refund deadline

Now compare that with a chemical name, a code keyword, a person's name, or a math symbol. Splitting those badly may erase a useful identity.

NaCl def Aisha ∑

The deep question is: does this token carry a distinction the model needs to keep exact, or is it only a shortcut for pieces that already carry the same distinction?

Concrete examples

What must stay, what can be rebuilt

ordinary phrasetax refund deadline can usually be represented by three normal tokens. A single combined token is convenient but not essential.
nameMehta should not be split into pieces that make it look like unrelated common fragments if identity matters.
codeasync, await, def, return, braces, dots, and indentation-like pieces may need stable treatment because small changes alter the program.
medicineA drug name may need to stay recoverable as a clear unit because one letter can distinguish two different things.
multilingual textA token that is rare in English may be common and important in another language. Removing it based only on English frequency can damage that language.
mathSymbols like ∑, ≤, or variable patterns may carry exact structure. Bad splitting can make equations harder to copy and reason over.

So the paper's real target is not just token count. It is the difference between a removable shortcut and a necessary symbol.

How to test it

The test is whether behavior survives

You can reduce a vocabulary in a way that still reconstructs text but quietly hurts the model. The model may become worse at names, code, rare words, or non-English text. So the check has to cover the cases where tokens carry exact information.

1. Remove candidate tokensPick tokens that seem rebuildable from smaller pieces.
2. Retokenize textRewrite old sequences using the smaller vocabulary.
3. Preserve recoveryMake sure the original text can still be reconstructed exactly.
4. Run behavior testsCheck language, code, names, math, and retrieval.
5. Keep or rejectReject removals that break important distinctions.
good removal: token disappears, meaning and behavior survive bad removal: token disappears, rare or exact distinctions get damaged
Connections

This is the same representation question at the input layer

CSRv2 asked how few active embedding dimensions can carry meaning. Lossless Vocabulary Reduction asks how few token pieces can carry language. Both are about useful compression.

The discrete communication page said a representation is a message. This page says the first message starts before the model even thinks. It starts when raw text is cut into reusable pieces.

Same idea as CSRv2.

Say less, but keep the few signals that still control the task.

Same idea as self-supervision.

Learn which details must remain stable and which surface forms can change.

Same idea as hidden causes.

Keep pieces that point to real causes: identity, syntax, entity, action, relation.

Same idea as structure.

Do not break pieces that carry exact structure, such as code, math, names, or domain terms.

Failure cases

What can go wrong?

Frequency-only removal.

A rare token may still be important. Rare names, rare medical words, and rare code tokens can carry exact meaning.

Longer sequences erase the gain.

If removing tokens makes text much longer, the model may spend more compute even though the vocabulary is smaller.

English-heavy pruning.

Tokens that look useless in English may be central in another language or script.

Exact-copy damage.

The model may become worse at copying names, numbers, code, equations, or citations because those strings are now awkward to represent.

Takeaway

The first-principles line

Lossless Vocabulary Reduction asks which language pieces can disappear as separate symbols while their meaning, identity, and use can still be rebuilt from other pieces.

The deeper representation lesson is this: a smaller code is only better when it removes unused shortcuts, not when it removes distinctions the model needs to keep exact.

raw text -> choose pieces -> remove rebuildable pieces -> preserve exact distinctions -> model behavior survives
