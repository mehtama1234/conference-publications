Co-RedTeam: Orchestrated Security Discovery and Exploitation with LLM Agents

Split automated security work into coordinated discovery and exploitation stages so agents can test, validate, and reuse what earlier attempts learned.

Paper explainersAll themesAgents & Tool Use

Automated security work is difficult because the agent cannot stop at reading code and guessing what might be wrong. It must inspect the program, form a concrete attack hypothesis, run actions against a live target, read the execution result, revise the hypothesis, and then decide whether an exploit really works. Co-RedTeam is built around that workflow. It uses multiple agents, separates discovery from exploitation, grounds reasoning in execution feedback, and stores long-term experience from earlier trajectories. The point is to make the system behave as an actual red-team loop instead of a single pass over static text.

Zero assumption version

Why automatic vulnerability work is harder than code reading

A security bug is not fully understood when the agent can describe it in words. The harder part is proving whether the bug can actually be triggered, under what conditions, and whether the observed behavior supports the attack hypothesis. Static inspection alone is often too weak because many apparent issues disappear when the program is executed or when the environment is slightly different.

Single-agent approaches struggle here for three reasons. They often interact too narrowly with the target, so they do not test enough concrete attack paths. They are weakly grounded in execution, so they keep reasoning from guesses instead of live results. And they fail to reuse earlier experience, so each new attempt restarts from scratch. Co-RedTeam is designed to fix those three gaps.

The main change. Treat security work as a coordinated loop of discovery, execution, validation, refinement, and memory reuse instead of a one-shot code analysis pass.

The hidden quantity

The hidden quantity

measured quantity  =  validated attack progress

The key quantity is not how many possible bugs the system mentions. It is how far the system has progressed toward a validated exploit. Progress is high when a hypothesis has survived execution checks and low when the system only has untested suspicions.

Co-RedTeam increases validated attack progress by coupling every reasoning stage to execution feedback and by saving earlier outcomes in memory. That matters because each new attempt starts from tested evidence instead of only from fresh speculation.

Why it works

Why staged execution-grounded reasoning helps

Discovery and exploitation require different kinds of work. Discovery asks where a weakness might exist. Exploitation asks whether that weakness can actually be triggered under concrete conditions. Combining both into one undifferentiated loop often leads to shallow behavior because the agent keeps switching tasks without preserving the right intermediate state.

Co-RedTeam separates these stages and ties them together through execution results and memory. The discovery stage proposes structured hypotheses. The exploitation stage tests them. The observed outcome then feeds back into the next round, which improves the next hypothesis because failed paths are recorded and promising paths are refined. Memory is important for the same reason: a security task often needs several tries, and the later tries should inherit what earlier tries already disproved.

A simple progress update

First in words:

next attack state = old state plus validated execution feedback from the latest attempt

Then the compact form:

AttackState_(t+1) = Update(AttackState_t, ExecutionResult_t)

Every symbol:

AttackState_tthe current record of hypotheses, confirmed facts, failed paths, and next actions at attempt t
ExecutionResult_tthe live outcome of the exploitation attempt at step t
Update( , )the rule that confirms, rejects, or refines the current hypothesis using the execution result
AttackState_(t+1)the revised state used by the next discovery or exploitation step

Suppose AttackState_1 contains one hypothesis: an input field may allow command injection.
The agent sends a test payload and receives an execution result showing the payload was escaped safely.
Update records that this path failed and marks the sanitization step as confirmed.
AttackState_2 now drops that route and shifts effort toward a different path such as file upload handling.
That saves work because the next attempt starts from tested evidence instead of retrying the same failed idea.

What can go wrong

What can go wrong

Execution feedback can be noisy. A failed exploit attempt may reflect a bad environment setup rather than a wrong hypothesis, so the system can discard a valid path if it reads the feedback too confidently.
Stored memory can preserve a wrong conclusion. If an early attempt records a weak interpretation as fact, later attempts may inherit that mistake because memory is reused across trajectories.
Discovery and exploitation can drift apart. If the discovery stage proposes abstract issues without concrete execution plans, the exploitation stage may spend effort on paths that were never well grounded.
Done right. A strong system should store both positive and negative outcomes with enough context to explain why a path worked or failed, so the next attempt can refine rather than merely repeat.
What a runnable demo should prove

What a runnable demo should prove

Build a small security playground with a few intentionally vulnerable services. Run one baseline agent that inspects code and proposes issues in a mostly linear way. Run a second system that separates discovery from exploitation, executes concrete checks, and stores the outcome of each attempt for later reuse.

Measure vulnerability detection, exploit success, and repeated failed attempts. The demo should show that the staged system reaches validated exploits more often because it grounds each revision in execution results and remembers what earlier attempts already proved.

validated_progress = confirmed_exploit_steps / total_attempt_steps

If validated_progress rises while repeated failed attempts fall, the orchestration is improving the security workflow in the way the paper claims.
