Online Change Point Detection for Multivariate Poisson Processes

Detect sudden changes in earthquake or epidemic counts in real time by reading low-rank patterns in event rates.

When you count earthquakes or disease cases over time, the underlying rate sometimes jumps suddenly. You need to spot that jump the moment it happens, not after waiting for a mountain of data. This paper builds a method that watches multivariate counts (many kinds of events at once) and triggers an alert the instant the rate changes, using only constant memory and one pass through the data.

Spotting earthquakes and epidemics in the stream

Real-world event streams never stay stationary. In seismology you measure foreshocks, mainshocks, and aftershocks—each phase has a different rate of events. In epidemiology an outbreak suddenly shifts the number of new cases per day. A beginner might collect months of data then fit a model, but by then the crisis is old news.

The core difficulty is speed: the rates spike and drop at unpredictable times, so you cannot wait for a slow batch method to finish processing weeks of old data. You need a signal now, while the crisis is still unfolding. Also, you have many kinds of events happening together (earthquakes in different regions, cases of different diseases), and when you watch each type alone, random noise can mimic a real signal, making it hard to know if something truly changed.

In one sentence. Detect when event rates jump, instantly, in a stream of multivariate counts, without storing all past data.

The algorithm as a flow

What it actually does

Build a low-rank model

Assume the true rates can be written as a small weighted mix of basic patterns.

Watch one number at a time

Each new observation updates the estimate of the low-rank patterns online.

Score how much things changed

Compute how far the new observation sits from what the old model predicted.

Accumulate surprises

Add up the individual surprises until they cross a threshold.

Fire alert and reset

When threshold breaks, announce a change point and start watching for the next one.

What the paper changes

What the paper moves

The paper changes the internal representation of rate patterns from a dense full matrix (needing to store and update all entries) to a low-rank factorization (two smaller matrices whose product recovers the original). This cuts memory footprint and makes each update cheap.

the object it moves  =  Low-rank intensity representation
The hidden quantity

Temporal drift: how much the rates have moved

measured quantity  =  Temporal drift

Drift is the sum of all the small surprises between what the old model predicted and what actually arrived. If the rate stays steady, drift stays near zero. When the rate jumps, drift climbs fast.

The paper estimates drift by comparing each new observed event count against the model's prediction under the current low-rank rates, accumulating a squared-error score. When drift crosses a learned threshold, a change point is declared.

Why it works

Why low-rank tracking detects changes faster

A change in the underlying rates shows up as a consistent pattern across multiple regions: maybe three regions spike while others stay flat. A low-rank model captures this as a single vector (the shared spike pattern) plus weights (which regions respond how much). When the true rates shift, that shared vector must move.

A naive method stores a separate number for each region-time pair, so it cannot tell a real change from random noise until it has seen many observations. The low-rank model ties all regions together through a few shared patterns. When one region suddenly differs, the model sees it immediately as a misfit to the shared pattern, and the accumulation of prediction errors jumps fast.

Mathematically, the algorithm maintains a running estimate of the low-rank factors using efficient matrix updates that cost constant time per observation. It compares each new count to the predicted count under the current low-rank model, and sums these squared prediction errors. The sum is the drift signal. A threshold on drift, tuned to keep false alarms rare given realistic temporal correlation, triggers the alert.

inputNew event counts from all regions arrive
stepPredict: multiply low-rank factors to estimate expected counts
stepCompare: compute squared difference from observed to expected
stepAccumulate: add the squared differences to the drift signal
stepUpdate: revise low-rank factors by moving in the direction that shrinks error
outputAlarm if drift exceeds threshold; otherwise return to step 1
Math after the picture

The change point statistic

First in words:

The detection signal grows as the sum of squared gaps between what we observe and what the low-rank model predicts. Formally, for each time step we compute the residual (observed count minus expected count under the current low-rank rates), square it, and add it to a running total. The algorithm triggers when this sum crosses a threshold.

Then the compact form:

T_n = sum_{t=1}^{n} (y_t - lambda_t)^2 / lambda_t, where detection fires when T_n >= c_alpha

Every symbol:

T_ncumulative drift signal up to time n
y_tobserved counts at time t (vector of all regions)
lambda_tpredicted counts under current low-rank model at time t
c_alphathreshold tuned so false alarm probability equals alpha
A tiny worked example
Time 1: Observe 5 counts, predict 4.8 (based on steady rate). Residual squared: (5 - 4.8)^2 / 4.8 = 0.04 / 4.8 ≈ 0.008. Running total T_1 = 0.008.
Time 2: Observe 5 counts, predict 4.8. Residual squared: 0.008. Running total T_2 = 0.016.
Time 3: Observe 8 counts, predict 4.8 (rate has spiked). Residual squared: (8 - 4.8)^2 / 4.8 = 10.24 / 4.8 ≈ 2.13. Running total T_3 = 0.016 + 2.13 ≈ 2.15.
If threshold c_alpha = 2.0, then at time 3 the signal crosses and an alarm fires. A bigger jump produces a bigger residual, so the method detects fast changes quickly.

The denominator lambda_t normalizes by the rate itself, so a jump of 3 events in an area that normally sees 5 is a bigger signal than a jump of 3 in an area that normally sees 100.

What can go wrong

What can go wrong

Model rank mismatch If the true pattern is rank-3 but the algorithm assumes rank-1, it will miss subtle multi-way changes and false-alarm on noise trying to fit the missing structure.
Threshold too sensitive Set the alarm threshold too low and random fluctuations fire alerts every hour. Set it too high and you miss real events for hours.
Long-range dependence If events cluster in time (aftershocks follow mainshocks), the temporal correlation violates the standard independence assumption, and the false alarm rate becomes unpredictable.
Done right The paper provides a new Matrix Bernstein inequality that accounts for temporal dependence, so the threshold can be tuned honestly even when observations are not independent.

What a runnable demo should prove

Implement the low-rank algorithm with rank-1 factors and run it with no prior knowledge of when the change occurs. Measure detection delay (how many steps after time 201 does the algorithm alarm) and false alarm count (how many times does it alarm before time 200). Compare to a naive per-region method that watches each region independently.
