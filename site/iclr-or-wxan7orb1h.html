FreeKV: Boosting KV Cache Retrieval for Efficient LLM Inference

FreeKV speeds up LLM inference by pulling key-value data from memory in the background, so the GPU doesn't have to wait.

Paper explainersAll themesEfficiency & Systems

When a large language model answers a long question, it keeps a massive lookup table (the KV cache) in memory that grows with each word. Retrieving data from this table becomes a bottleneck. FreeKV solves this by fetching the needed data speculatively—before the GPU even asks—and by storing data smartly across both CPU and GPU memory.

Zero assumption version

The KV cache bottleneck

When an LLM (a neural network that generates text one word at a time) processes a long document, it maintains a lookup table called the KV cache. This table stores past context so the model can reference earlier words, because when the model generates the next word, it needs to know what all the previous words were in order to pick the most sensible continuation. The cache size grows with every new word—a 1,000-word document creates a cache 1,000 times bigger than a 1-word cache.

To find the right cached values when generating the next word, the GPU must fetch them from memory. This fetch is slow: the data lives far from where the computation happens, and memory access causes the GPU to idle waiting. With long contexts, this idle time kills performance. Naive approaches try to compress the cache by dropping tokens (cutting out words), but this breaks accuracy because the model loses information it needs.

The core problem. The GPU generates output slowly because it sits idle waiting for memory to deliver cached data, and there is no way to speed this up without breaking accuracy.

The algorithm as a flow

What it actually does

Step 1: Predict which cache entries will be needed

Before the GPU asks, guess which past words the next word will look back to.

Step 2: Fetch those entries into GPU memory in the background

Start pulling the guessed data from CPU or GPU memory while the GPU is still computing on other things.

Step 3: GPU proceeds with computation

The GPU does not wait; it works on the current step while the data arrives.

Step 4: Verify and correct

Once the prediction is done, check if the fetch was right and fix errors quickly with a small correction pass.

Step 5: Reuse the layout

Data is stored in a smart order across CPU and GPU, so future fetches are contiguous and fast, not scattered.

What the paper changes

What the paper changes

FreeKV reshapes when and how the KV cache is fetched from memory. Instead of fetching on demand (blocking computation), it fetches speculatively in advance, in the background, and from a cleverly organized memory layout.

The hidden quantity

The hidden quantity: Latency hiding ratio

measured quantity  =  How much of the memory fetch time is hidden by overlapping with GPU work

The core insight is that a memory fetch takes time (say 10 milliseconds), but the GPU is doing other work too (say 8 milliseconds). If you can overlap them, the GPU finishes its work just as the data arrives, and zero time is wasted. FreeKV measures this overlap: the fraction of fetch time that the GPU can hide by computing in parallel.

The paper achieves this by predicting which cache entries will be needed next, fetching them while the GPU computes, and storing data contiguously so the fetch is a single fast stream instead of scattered random accesses.

Why it works

Why it works: The causal chain

The KV cache fetch is slow because the GPU must wait for data to arrive from far-away memory. FreeKV breaks this chain by making the fetch happen in parallel with GPU work. Here is how: before the GPU finishes its current computation, FreeKV guesses (speculatively) which tokens the next step will need and sends a request to fetch them. This request goes to the memory system as a background task, not interrupting the GPU. While the fetch is in flight, the GPU keeps working on its current output. By the time the GPU finishes, the data has already arrived (or is just arriving), so there is no additional wait.

On the system side, FreeKV stores the cache in a hybrid layout: frequently-accessed entries stay in fast GPU memory, others live in CPU memory. But they are organized contiguously (one after another in order), not scattered. This turns a slow, random-access fetch (jumping around in memory) into a fast, sequential stream (reading data in order), which is orders of magnitude faster because modern memory systems are optimized to pull data in chunks and can deliver contiguous blocks much quicker than scattered random locations.

The fine-grained correction step is insurance: if the speculation got a token's access pattern wrong, a quick re-fetch of just that one token fixes it, with minimal overhead. The double-buffering technique means one batch of data is being fetched while another is being used, so fetches never stall computation.

The core equation

First in words:

Total time per inference step equals max(GPU compute time, memory fetch time). With overlap, fetch time does not add to total time.

Then the compact form:

step_time = max(T_compute, T_fetch_hidden) + T_correction

Every symbol:

T_computeTime for the GPU to compute the next token from the fetched data
T_fetch_hiddenMemory fetch time minus the overlap with GPU compute (the truly visible wait)
T_correctionTime to verify the speculative prediction and fix errors if needed
max(A, B)Take the larger of A or B; computation and fetch happen in parallel if possible
A tiny worked example
Suppose: GPU compute takes 10 ms, memory fetch takes 8 ms without overlap.
Without FreeKV: total time = 10 ms (compute) + 8 ms (wait for fetch) = 18 ms.
With FreeKV (full overlap): fetch starts before compute finishes; by the time GPU is done (10 ms), fetch is done (8 ms started earlier, so yes, it is ready).
New total time = max(10, 8) = 10 ms, plus small correction time (0.5 ms) = 10.5 ms.
Speedup: 18 / 10.5 ≈ 1.7×. With longer contexts and better prediction, overlap improves and speedup reaches 13×.

Memory fetch and computation can run at the same time. Scheduling the fetch early hides it from view, so only GPU compute time matters.

What can go wrong

What can go wrong

Bad speculation ruins the overlap. If the prediction about which cache entries to fetch is wrong, the fetch completes too early (wasted), or too late (GPU still waits), and latency hiding fails. Fix: use a fast, accurate prediction model trained on access patterns from the real tasks.
Correction overhead kills gains. If every misprediction requires a second fetch, the correction can be slower than the original fetch. Fix: make correction a fast, local operation (just re-fetch the wrong entries, not the whole batch).
Memory layout fragmentation returns. If data is scattered across memory, the fetch becomes random-access (slow) instead of streaming (fast), because the memory system has to hunt for pieces one at a time, making prediction useless—the overlap does not help since the fetch will still stall. Fix: keep the cache organized (entries in one order that matches access patterns), not scattered by cache eviction or compression.
Done right. Prediction is accurate, correction is cheap, and memory is organized. Latency is truly hidden, and the model's output speed is limited only by GPU compute, not memory wait.
