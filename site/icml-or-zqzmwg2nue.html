VeRO: A Harness for Agents to Optimize Agents

The paper builds an outer control system that versions, runs, and scores agent code changes so one agent can improve another agent in a controlled loop instead of editing blindly.

Paper explainersAll themesAgents & Tool Use

When a coding agent edits another coding agent, the task is not ordinary software maintenance. The target agent system mixes deterministic code with random model calls, so one small code change can alter both intermediate traces and final task outcomes in hard-to-measure ways. If you want an optimizer agent to improve that system, you need more than a unit test because one run is too noisy to prove the edit helped. You need snapshots, controlled budgets, repeatable evaluations, and structured records of what happened during each run. VeRO is that outer control system. It gives the optimizer a disciplined environment in which edits can be proposed, run, compared, and judged against real outcomes.

Zero assumption version

Improving an agent is hard when the target is noisy

A normal software benchmark can often run one program version once and compare the output to a known answer. Agent-system optimization is harder. The target agent calls a language model, chooses tools, accumulates traces, and may behave differently across runs even when the code is unchanged.

That means an optimizer agent cannot trust one lucky run. It needs a way to version the target agent system, evaluate it under a fixed budget, capture what happened inside the run, and compare candidate edits fairly. Without that scaffolding, the optimizer edits in the dark because it cannot tell whether a change helped for a real reason or only got lucky once.

The problem. An agent that edits another agent needs controlled versions, budgets, traces, and outcomes, because a single run is too noisy to prove that a code change actually helped.

What the paper changes

What the paper changes

The paper adds an outer control layer around agent optimization. Instead of letting an optimizer agent patch a target agent system and hope for the best, VeRO turns each edit into a versioned experiment with structured observations and bounded evaluation. The changed object is the optimization environment itself: it becomes inspectable and comparable across rounds.

the object it moves  =  the outer control system that versions, evaluates, and traces target-agent edits
The hidden quantity

The hidden quantity: expected improvement per evaluation budget

measured quantity  =  reward gain after accounting for run budget and variance

The real question is not whether a candidate version won one run. The real question is whether it improves expected task reward enough to justify the evaluation budget spent testing it. VeRO makes this visible by logging both downstream outcomes and the cost of getting them.

This quantity matters because agent optimization is expensive. If a candidate edit raises success by a tiny amount but doubles run cost, the edit may not be worth keeping. If another edit raises success modestly while preserving budget and producing cleaner traces, that edit is easier to trust because the gain comes with operational discipline.

Why it works

Why an outer control system improves agent optimization

An optimizer agent needs feedback that is detailed and controlled. Detailed feedback means seeing traces, errors, and final task scores. Controlled feedback means runs happen under known budgets with exact version snapshots. VeRO provides both, so edits can be compared on the same footing.

This reduces false progress. Without an outer control system, an optimizer may keep a change because one run happened to succeed. VeRO counters that by preserving the version, the evaluation procedure, and the evidence from inside the run. If the candidate only won through noise, later comparison exposes that because the gain does not repeat under the same rules.

The outer control system also makes research possible. Once versions, traces, and rewards are structured, you can ask which kinds of edits help most often, which tasks are sensitive to prompt changes versus code changes, and how much budget is needed to detect real gains. That is why the benchmark matters alongside the control system: it turns agent optimization from anecdote into a measurable capability.

Math after the picture

The edit-scoring equation

First in words:

Score a candidate version by its average task reward minus a penalty for evaluation cost. A change is useful only when it increases reward enough to cover the extra budget it consumes.

Then the compact form:

score(version) = average_task_reward(version) - lambda * evaluation_cost(version)

Every symbol:

score(version)overall value assigned to one candidate harness version
average_task_reward(version)mean downstream task performance for that version across evaluation runs
evaluation_cost(version)budget spent to run that version, such as calls, time, or money
lambdatradeoff constant that says how much cost should count against reward
versionone specific snapshot of the target harness after an edit
A tiny worked example
Baseline version: average task reward = 68, evaluation cost = 10, lambda = 1. Score = 68 - 10 = 58.
Candidate version B: average task reward = 74, evaluation cost = 13. Score = 74 - 13 = 61.
Candidate version C: average task reward = 76, evaluation cost = 21. Score = 76 - 21 = 55.
Version B is better than the baseline because its reward gain is larger than its extra cost.
Version C has the highest raw reward but the worst score because the added cost is too large.
The optimizer should keep B because it improves downstream performance by enough to justify the budget.

The exact reward and cost terms can vary across tasks, but the principle stays the same: edits should be judged by net gain under controlled evaluation.

What can go wrong

What can go wrong

Benchmark mismatch. If the benchmark tasks do not reflect real deployment goals, the optimizer can improve benchmark score while making the target agent system worse in practice because it learned to satisfy the wrong objective. The outer control system is only as useful as the tasks it uses for measurement.
Too little evaluation budget. If each candidate is tested on too few runs, noisy outcomes can look like true improvement. This hurts selection because weak edits may survive while strong edits are discarded by chance.
Trace collection misses key events. If important intermediate events are not logged, the optimizer loses the evidence needed to diagnose why a change helped or hurt. That slows future rounds because the system sees reward shifts without seeing the cause.
Done right. Use representative tasks, enough repeated evaluation to smooth noise, and traces that capture the decisions most likely to explain success or failure. Then the optimizer can keep edits because they show repeatable value rather than one-off luck.
What a runnable demo should prove

What a runnable demo should prove

Build a small target coding agent with editable prompt rules and tool policies. Wrap it in an outer control system that snapshots each version, runs a fixed task set under a strict call budget, records tool traces, and scores final task success. Then let a simple optimizer propose prompt or rule edits and compare accepted edits against a baseline.

net_improvement = average_task_reward_after_edit - average_task_reward_before_edit - lambda * (evaluation_cost_after_edit - evaluation_cost_before_edit)

The demo should show that accepted edits improve net task value because the outer control system exposes both reward and cost, so the optimizer can reject changes that win only through extra spending or noise.
