Differentiable Model Predictive Control on the GPU

Make model predictive control run on GPUs by solving its quadratic subproblems in parallel instead of one by one.

Paper explainersAll themesRobotics & Control

Model predictive control (a way to make decisions by solving an optimization problem at every step) is clean and interpretable but slow because its traditional solver runs one calculation after another, which GPUs cannot speed up. This paper rewrites the solver to exploit the problem's time structure—where each timestep only talks to the next—so all timesteps' subproblems can run in parallel on a GPU (because they can all be set up at once without waiting), and a custom preconditioned solver converges 50x faster (because it knows the chain structure), making training 10-100 times quicker.

Zero assumption version

Sequential solvers bottleneck GPU training

Model predictive control (deciding what action to take by solving an optimization problem that predicts what will happen next) is a clean, interpretable way to control robots and vehicles. The solver finds the best sequence of actions by solving one timestep at a time, in order: solve for time zero, then time one, then time two, and so on.

A naive approach would be to just call the CPU solver on a GPU machine. But the bottleneck is not arithmetic—it is the sequential dependency. Each step depends on the previous step's answer, so the GPU sits idle 99% of the time while one CPU thread drags through the calculation one timestep at a time. Even though modern GPUs have thousands of cores, this design wastes them.

In one sentence. Restructure the solver to unroll all timesteps in parallel on the GPU, using a custom preconditioned solver tailored to the problem's sparse time structure.

The algorithm as a flow

What it actually does

Forward pass: set up and solve

Evaluate cost and constraint matrices in parallel for each of 50 timesteps; reformulate as 50 coupled quadratic subproblems.

Sequential quadratic programming

Iteratively replace the original nonlinear problem with a simpler quadratic one, solving it, then updating based on how far off we are.

Custom preconditioned solver

Use conjugate gradient (a method that finds the answer by taking smarter and smarter guesses) with a preconditioner (a shortcut that tells it which guesses matter).

Exploit time structure

The preconditioner knows that timesteps form a chain; it builds a shortcut matrix (tridiagonal: only touching neighbors) so the solver converges in 10 iterations instead of 500.

Learning the control weights via implicit differentiation

Compute gradients (which way to nudge the weights to shrink the loss) by solving the same system again with a modified right-hand side, enabling the model to learn.

What the paper changes

What changes: the solver itself

The object is the optimization solver—the algorithm that finds the best actions. Instead of running one timestep sequentially, the solver now operates on all timesteps at once, in parallel.

The hidden quantity

The hidden quantity: convergence speed

measured quantity  =  How many solver iterations until convergence

The paper measures one critical hidden quantity: how many times the solver needs to run its update loop before it finds a good answer. With the standard conjugate gradient solver, you need about 500 iterations. With the custom preconditioned version, you need about 10, because the preconditioner tells the solver upfront which updates matter most (those connecting neighboring timesteps in the chain).

The paper estimates this by counting solver iterations during training on benchmark tasks, and by testing the preconditioner on synthetic quadratic problems of multiple sizes. The preconditioner works because it captures the exact time structure of the problem: in model predictive control, what happens at time t only directly affects what happens at time t+1, so a sparse shortcut matrix captures all the important dependencies.

Why it works

Why it works: parallelizing sequential structure

The core mechanism is transforming a sequential algorithm into one that exploits the inherent parallel structure. Here is how it works.

Original sequential solver: Start at time zero, solve for the action. Use that action to advance to time one, solve for the next action. Repeat for 50 timesteps. Each step waits for the previous one.

New parallel solver: Set up 50 quadratic subproblems (one for each timestep) all at once. They are coupled—the solution at time t affects the boundary conditions for time t+1. But the coupling is sparse: only neighboring timesteps touch. So you can set up all 50 subproblems on the GPU in parallel, then solve the coupled system using conjugate gradient (a method that guesses the answer by taking smarter and smarter steps) with a preconditioner that knows the sparsity pattern. The preconditioner compresses the problem: it tells the solver that the time structure is a chain, so most of the heavy lifting is in the tridiagonal part (the connections between neighbors), and far-away timesteps do not interfere.

Because the preconditioner compresses the problem, the solver converges 50x faster. And because all 50 timesteps are set up at once, the GPU's thousands of cores run in parallel instead of waiting. Together, these changes give a 10-100x end-to-end speedup.

Math after the picture

The core equation: preconditioned linear system

First in words:

At each iteration of sequential quadratic programming, solve a coupled quadratic problem by applying conjugate gradient to the KKT system (the matrix equation that encodes the optimality conditions). The preconditioner is tridiagonal, matching the time chain structure.

Then the compact form:

[G H^T] [dz] = [-dℓ/dz] [H 0 ] [dλ] [ 0 ]

Every symbol:

GHessian of the quadratic cost (how steep the penalty surface is)
HJacobian of the linear constraints (how the constraints change)
dzchange in the optimization variables (actions and states)
dλchange in the dual variables (Lagrange multipliers, how to weight the constraints)
dℓ/dzgradient of the loss with respect to the optimization variables
A tiny worked example
Suppose we have a 6-step control problem with 2 variables per step (state + action). Full system is 12×12.
Stock conjugate gradient needs ~500 iterations to converge (solution error shrinks by factor of 0.5^500 ≈ 10^-150).
Tridiagonal preconditioner exploits that steps only talk to neighbors: error shrinks by 0.5^10 ≈ 10^-3 convergence in 10 iterations.
Speedup: 500 ÷ 10 = 50x fewer iterations. On GPU, all 6 steps' subproblems run in parallel, so 50x fewer serial stages. Overall: ~100x speedup vs sequential CPU.

The matrix equation is the standard KKT optimality condition for a constrained quadratic program. The preconditioner replaces it with a tridiagonal approximation, which the solver can use to make smarter guesses.

What can go wrong

What can go wrong

Inequality constraints not directly supported. The method solves equality-constrained quadratic programs. Inequality constraints (like bounds on actions) must be enforced via penalization or external simulation, which can degrade solution quality if the penalty is loose.
Preconditioner only works for chain-structured problems. If the time coupling is not tridiagonal (e.g., in problems with longer-range memory or feedback), the preconditioner does not compress the problem, and convergence slows back down.
Convergence depends on problem conditioning. Ill-conditioned cost matrices (where small changes in the state cause huge swings in cost) can cause the solver to stall, because the preconditioner does not capture all the problem structure and the conjugate gradient method wastes iterations on poorly-scaled directions. Adding a small penalty term (a small nudge that favors staying near the original weights) improves the balance of the cost matrix so that small changes map to roughly similar-sized changes in the cost—this makes the problem well-conditioned, so the preconditioner's hint becomes more accurate and the solver converges faster.
Done right: large batches and long horizons. The method shines when solving many control problems in parallel (batch size ≥ 32) with long horizons (≥ 100 timesteps), because this is when GPU parallelism and preconditioner efficiency pay off most.
What a runnable demo should prove

What a runnable demo should prove

A good demo would take a standard reinforcement learning or imitation learning task (e.g., learning to steer a car or imitate a human trajectory), run it with three solvers: the CPU sequential solver, a naive GPU solver without preconditioning, and the GPU solver with the tridiagonal preconditioner. Measure the wall-clock training time for each and the final task performance.

speedup = time_CPU_sequential ÷ time_GPU_preconditioned

The demo must show that the GPU preconditioned solver trains at least 2x faster than the CPU solver (because all timesteps solve in parallel instead of sequentially) and 5x faster than an unpreconditioned GPU solver (because the preconditioner cuts iterations from 500 to 10), while reaching the same or better final task performance. This proves that both parallelization and preconditioning are necessary for the full speedup.
