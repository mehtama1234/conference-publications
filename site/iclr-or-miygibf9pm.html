ATLAS: Constraints-Aware Multi-Agent Collaboration for Real-World Travel Planning

Use multiple planning agents that track constraints, critique drafts, and keep searching until the trip plan satisfies the real travel rules.

Paper explainersAll themesAgents & Tool Use

Travel planning looks simple until the real constraints pile up. A user may need specific dates, prices, locations, transfer limits, and changing preferences, while the available flights and hotels can also change during the interaction. Single-agent planners often fail because they miss constraints or stop searching too early. This paper proposes ATLAS, a multi-agent framework for travel planning that separates the work into constraint management, plan critique, and adaptive search. The central claim is that travel plans improve when constraints are tracked explicitly and when several specialized agents repeatedly inspect and revise the plan, because missed constraints and weak search results are caught before the final itinerary is returned.

Zero assumption version

Why travel planning breaks under real constraints

A valid trip plan must satisfy many rules at once: budget, timing, locations, user preferences, and availability in the external world. Some rules are written directly by the user, while others are implied by the situation, such as the time needed between connections.

The planning problem is hard because these constraints interact. A hotel choice can force a different arrival airport. A cheaper flight can create an impossible transfer because its arrival time may leave too little time for the next leg. A user correction in the middle of the conversation can invalidate the whole draft. The planner therefore needs to keep a live picture of which constraints are active and whether the current itinerary still satisfies them.

The paper's move in one sentence. Assign separate agents to track constraints, critique drafts, and search for better options so that the final itinerary is revised until it satisfies the active travel rules.

The algorithm as a flow

What it actually does

Collect active constraints.

A constraint manager gathers rules from the user request, the conversation history, and the current world state.

Search for candidate options.

Planning agents query tools or sources to find flights, stays, and route choices that could satisfy those rules.

Assemble a draft itinerary.

The system combines candidate options into a complete trip proposal.

Critique the draft.

A critique agent checks for broken rules, missing information, and low-quality decisions.

Revise until constraints are met.

The search and critique loop repeats until the itinerary passes the active rule checks because unresolved violations trigger another search round.

The hidden quantity

The hidden quantity: constraint satisfaction state

measured quantity  =  which travel rules are currently satisfied, violated, or still unknown

The planner only succeeds if it knows the state of each relevant constraint. A draft itinerary can look plausible while still breaking a budget cap, missing a visa timing rule, or relying on an impossible connection.

The paper's real target is therefore a live constraint satisfaction state. That state must be updated whenever the plan changes or new world information arrives. Without it, the system cannot tell whether a revision helped or simply moved the failure from one part of the trip to another.

Why it works

Why multiple specialized agents can help

Travel planning mixes different kinds of work: remembering rules, exploring options, and checking whether the current draft is still valid. One agent can do all of that in principle, but errors accumulate because those tasks compete for limited planning focus.

A multi-agent system can help by assigning those responsibilities explicitly. Constraint tracking prevents the rules from getting lost. Critique exposes hidden failures before the trip is returned. Adaptive search reopens the world lookup when the current draft does not work. The gain comes from repeated correction, because each specialized role can catch errors the others leave behind.

Math after the picture

A compact statement of the planner target

First in words:

Prefer itineraries that satisfy more constraints and pay less travel cost, while penalizing every unresolved violation.

Then the compact form:

plan_score(itinerary) = travel_value(itinerary) - alpha * violation_count(itinerary) - beta * unknown_constraint_count(itinerary)

Every symbol:

travel_value(itinerary)the overall usefulness of the itinerary, including cost, timing, and fit to user preferences
violation_count(itinerary)how many active travel rules the itinerary currently breaks
unknown_constraint_count(itinerary)how many relevant rules still have unresolved status
alphathe penalty weight for each known rule violation
betathe penalty weight for each still-unchecked rule
plan_score(itinerary)the value used to compare candidate itineraries
A tiny worked example
Suppose itinerary A has travel_value = 80, but it breaks one timing rule and leaves one hotel rule unchecked.
Let alpha = 20 and beta = 10.
Then plan_score(A) = 80 - 20 * 1 - 10 * 1 = 50.
Itinerary B has travel_value = 74 and no known violations or unknown rules.
Then plan_score(B) = 74 - 20 * 0 - 10 * 0 = 74.
Even though A looked better at first, B wins because it satisfies the full rule set more reliably.
This is why critique and re-search matter: they expose hidden failures before the planner commits to a glossy but invalid trip.

Penalizing unresolved rules is important because a travel plan is not trustworthy when some key constraints have never been checked.

What can go wrong

What can go wrong

Constraint extraction misses a rule. If an implicit travel requirement is never recorded, the rest of the system cannot protect it, so the final itinerary may fail in practice even when internal checks look clean.
External information becomes stale. Flights and rooms change quickly, so a plan can become invalid after it was drafted unless the search stage refreshes critical facts before final return.
The critic finds problems but the planner cannot repair them. A critique-only loop is not enough. The search stage must be able to reopen the world lookup and explore better options when a violation is found, because the current candidate set may contain no valid repair.
Done right. The framework works when constraints are tracked explicitly, critique is strong enough to surface hidden failures, and the planner keeps searching until every important rule has a verified status.
