Distilling Task-Level Coordination Policies for Generalizable Multi-Agent Cooperation

Distill reasoning from expensive large language models into lightweight agent policies by having the LLM demonstrate coordination through tool calls, then train simple policies to replicate its decisions.

Paper explainersAll themesAgents & Tool Use

Multi-agent teams need someone to say what to do when. Large language models can reason about cooperation well, but running them during every decision is slow and expensive. This paper cuts out the middleman: use the LLM once to show how coordination works, then train a tiny policy that learns to make the same decisions without the LLM.

The coordinator bottleneck

When multiple agents must work together, someone needs to decide what each one should do. A natural idea: use a large language model as the coordinator. The LLM reads the state and outputs the next action for each agent.

This fails at three points. First, even when the LLM reasons correctly, the individual agents often cannot execute what it asks for—they get stuck trying to follow instructions that do not match their actual capabilities. Second, the reasoning model sees the full state but agents only see local information around them, creating a mismatch. Third, running the LLM for every single decision is prohibitively slow and expensive, especially as teams grow.

A naive solution: collect human experts annotating which action to take in each situation. This works but requires vast labeled datasets and throws away the reasoning ability already inside the LLM.

The paper's one-sentence move: Rather than run the LLM live for every decision, have it demonstrate coordination through tool calls once, then train a small policy network to replicate those decisions cheaply.

The algorithm as a flow

What it actually does

Define tool interface

Specify which coordination actions are allowed and how agents can request them (e.g., 'grab object', 'pass to neighbor').

Run LLM as coordinator

Feed the LLM the task state and have it decide which tools to invoke, building up a log of decisions.

Collect trajectories

Extract the sequence of state-action pairs where the LLM invoked tools, forming a demonstration dataset.

Train distilled policy

Train a small neural network to predict which tool to invoke given only the local state each agent sees.

Deploy policy

Replace the LLM with the trained policy at execution time, keeping coordination fast because the policy answers in milliseconds.

What the paper changes

What the paper changes

The paper moves the coordination decision-maker from an expensive large language model (run live when answering each question) to a small trained policy (run cheaply at execution time). This shifts the computation burden from live reasoning to a one-time training phase.

the object it moves  =  coordinator: LLM to small policy
The hidden quantity

Task-level action consistency

measured quantity  =  How often the policy matches the LLM's decision

The paper's core quantity is the match rate: out of all the coordination decisions the LLM makes on test tasks, how many does the trained policy replicate exactly? If the policy chooses 'grab' when the LLM chose 'pass', coordination falls apart.

The paper estimates this by running both the LLM and the trained policy on the same states and comparing their tool choices. A high match means the policy captured the LLM's reasoning; a low match means the policy learned only superficial patterns. The paper also tracks efficiency: the tiny policy runs in microseconds while the LLM takes seconds per decision.

Why it works

Why distillation captures coordination

The LLM is good at reasoning about what the whole team needs to do, but expensive. The tool interface constrains the LLM to output only valid coordination actions. When you have the LLM demonstrate coordination repeatedly on varied states, it reveals patterns: 'when agent A is far from the goal and agent B is close, agent B should grab the object.' These patterns repeat. A small policy network, trained to predict which tool the LLM would invoke given a state, learns those patterns. The policy does not need to reason like the LLM; it only needs to recognize the same situations and fire the same tools.

Generalization happens because the policy learns abstract patterns (e.g., 'closer agent acts first') rather than memorizing specific states. When the team size changes or the environment grows, if the states still follow those patterns, the policy keeps working. The LLM's reasoning got compressed into a tiny lookup table that runs without slowing the system down.

The distillation objective

First in words:

The loss penalizes the policy when it predicts a different tool than the LLM did on the same state. Minimize: mean number of wrong tool predictions across all training states.

Then the compact form:

L = mean[ I(policy_action != llm_action) ]

Every symbol:

policy_actionwhich tool the trained policy chose for this state
llm_actionwhich tool the LLM chose for this state
I(...)indicator function: 1 if true, 0 if false
mean[...]average across all training states
A tiny worked example
State 1: LLM chose 'grab', policy chose 'grab'. Indicator = 0 (match). Loss += 0.
State 2: LLM chose 'pass', policy chose 'wait'. Indicator = 1 (mismatch). Loss += 1.
State 3: LLM chose 'wait', policy chose 'wait'. Indicator = 0 (match). Loss += 0.
On 3 states: loss = (0 + 1 + 0) / 3 = 0.33 (33% of decisions are wrong). Training nudges the policy to fix state 2.

The loss is zero only when the policy mimics the LLM perfectly on all training states; in practice, a small error rate (e.g., 5%) is acceptable if the policy still generalizes to new teams and layouts.

What can go wrong

What can go wrong

Policy overfits to the LLM's specific mistakes. If the LLM occasionally makes suboptimal coordination choices during demonstration, the policy learns and repeats those mistakes. The distilled policy is a faithful copy of the teacher, flaws and all.
Generalization cliff when team composition changes. The policy trains on a fixed team structure (e.g., Agent A is a pusher, Agent B is a turner). If at test time agents swap roles, the policy may output actions incompatible with each agent's actual capabilities.
Tool interface mismatch between training and deployment. If the training trajectories use tools like 'grab-object' but at deployment the agents can only 'push-object', the policy outputs become invalid and coordination fails.
Done right. Maintain a gap between training and test conditions during evaluation: train on team size 2-3, test on unseen size 4-5. If the policy generalizes, it has learned abstract coordination patterns, not spurious state details.
What a runnable demo should prove

What a runnable demo should prove

Build a tiny cooperative task: two agents trying to move objects into a goal zone. First, prompt the LLM to name which agent should act in each state, collecting a small log of decisions. Train a small policy (a neural network with a few hundred tunable weights, one or two layers) to mimic those LLM decisions from the state alone. Run both the LLM and the policy on a new test scenario and measure: (a) how often they make the same choice, (b) how much faster the policy answers (because the policy runs one forward pass through the network in milliseconds, while the LLM outputs words one by one, each word taking time to decide), and (c) whether the team achieves the goal with the policy acting as coordinator.

match_rate = number of states where policy == LLM / total test states

The demo must show that a tiny policy trained on one task generalizes to a slightly larger task (e.g., more objects or farther goal) without retraining, proving that distillation captures reusable coordination patterns.
