$\tau^2$-Bench: Evaluating Conversational Agents in a Dual-Control Environment

A benchmark for agents that must not only use tools themselves but also tell a user which tool actions to take in the same changing system.

Paper explainersAll themesOther

Many agent benchmarks test a simpler setting than real support work. The agent can act on the system, but the user cannot. Real support sessions are different. The user and the agent both act on the same account, device, or service state, and the agent succeeds only if it gives instructions the user can actually carry out at the right time. This paper builds a benchmark around that shared-control setting, then separates failures caused by wrong task reasoning from failures caused by weak guidance and coordination.

Zero assumption version

Single-controller benchmarks miss the hardest part of support work

In technical support, the agent usually does not control the whole system. The customer may need to reboot hardware, confirm account details, move a cable, approve a setting, or read back a status code. Those user actions change the world state just as much as the agent's tool calls do.

A benchmark where only the agent can act turns this into a planning problem with one controller. That removes the coordination problem. The agent never has to decide what the user should do next, whether the user has enough information to do it, or whether a delay or misunderstanding changed the state before the next agent step. The paper argues that this missing piece changes the task itself, because many real failures come from bad guidance rather than from bad internal planning.

The core gap. A support agent must reason over a shared state that can be changed by two actors, because success depends on both correct tool use and correct user guidance.

The algorithm as a flow

What it actually does

Build a shared environment.

Create a telecom support world where both the agent and the user can inspect or change state, because dual control is the feature being tested.

Generate tasks from atomic parts.

Compose tasks from reusable pieces such as outages, account checks, device resets, and plan constraints, so the benchmark can vary difficulty while keeping success conditions verifiable.

Attach a user simulator to the same state.

Let the simulator act only through the tools and observations a user would have, because the benchmark should test whether the agent's instructions are executable from the user's side.

Run agents in the dual-control setting.

Measure whether they choose good internal actions and whether they ask the user for the right external actions at the right time.

Separate failure types.

Analyze whether a failure came from wrong world reasoning, weak communication, or poor coordination across the two actors, because those are distinct weaknesses.

The hidden quantity

The hidden quantity

measured quantity  =  coordination load across agent and user actions

The benchmark is not only measuring whether the agent knows a fix. It is measuring how much coordination work the task requires after the fix is known. Coordination load means the amount of state-dependent guidance needed to get the user and the agent to perform the right sequence of actions without contradiction or dead ends.

That quantity matters because two tasks can require the same support knowledge but differ sharply in execution difficulty. A line reset that the agent can perform alone is one problem. A line reset that also requires the user to inspect lights, reboot hardware, and confirm a configuration state is a different problem, because the agent must translate its plan into instructions the user can follow from their limited view.

Why it works

Why this benchmark reveals failures that older ones hide

Once the user can act, the agent has to solve three linked problems. It must infer the hidden service state from partial evidence, choose its own tool calls, and decide what instructions will cause the user to change the state in a useful way. Leaving out any one of those three makes the task easier in a way that removes common real failures.

The task generator matters because benchmark coverage should not depend on a small hand-written list of cases. By composing tasks from atomic support components, the benchmark can vary which actor has the next necessary action, what information each side can observe, and how many dependent steps must happen before the terminal condition is satisfied.

The user simulator matters because communication quality cannot be tested if the user is only a text source. The simulator is tied to the same state and the same limited action set a real user would have, so an agent is penalized when it gives an instruction the user cannot execute, gives it too early, or omits the state check that should come before it.

Math after the picture

The decision object

First in words:

Each step must choose an action for one actor under partial information while accounting for how that action changes the next observations and which actor can move next.

Then the compact form:

next_score = task_reward(shared_state, agent_action, user_action_history)

Every symbol:

shared_statethe underlying telecom world state that both sides affect but neither side fully sees
agent_actionthe support-tool action or message chosen by the agent at the current step
user_action_historythe sequence of user actions already taken in response to prior instructions
task_rewardthe success measure that checks whether the task is progressing toward the required terminal state
A tiny worked example
The modem is offline, but only the user can see the front-panel light.
If the agent resets the account first, the shared state changes but the root cause may remain hidden.
If the agent first asks the user to read the light status, then the next observation becomes more informative.
If the user reports a red light, the agent can choose a line test instead of a billing change.
The benchmark rewards the sequence that uses the right actor at the right time, because that sequence reaches the terminal condition with fewer wasted actions.

The benchmarked difficulty comes from action choice under split control, not only from knowledge of telecom procedures.

What can go wrong

What can go wrong

The simulator may still be easier than a real user. A simulator can constrain user behavior more tightly than real people do, because real users may misunderstand, skip steps, or report observations imprecisely.
Domain coverage can be narrow. A telecom environment may not capture every kind of shared-control work, because other domains may have longer delays, more safety rules, or harder observation gaps.
Error categories can overlap. A bad message can come from bad reasoning about the state, so separating communication and reasoning failures may still require judgment about the root cause.
Done right. The benchmark is most useful when its task generator, simulator, and scoring stay tightly tied to executable user actions, because that is what makes dual-control failure visible.
What a runnable demo should prove

What a runnable demo should prove

Build a small support world with a shared state, two action sets, and a few tasks where some required steps are agent-only and others are user-only. Include at least one task that fails if the agent knows the fix but asks the user to do steps in the wrong order.

Compare an agent evaluated in an agent-only version of the world against the same agent in the dual-control version. The demo should report task completion, wasted actions, and how often the next required state change came from the wrong actor, because those numbers expose the extra coordination load created by shared control.

coordination_error_rate = wrong_actor_or_wrong_order_steps / total_required_steps

The benchmark earns its keep if an agent that looks strong in the agent-only world breaks once user guidance becomes part of the task.
