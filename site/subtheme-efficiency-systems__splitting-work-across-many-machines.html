Splitting work across many machines

These papers tackle the challenge of training and running models on multiple computers together, deciding which machine handles which part, and keeping performance good even when machines have different capabilities.

All themesField mapMathematicsAll explainers
What this is

When a network is too big to fit on one computer, you have to split it. One machine might handle the first half of the layers, another the second half — this is called pipeline parallelism. Or each machine gets a chunk of the data and computes in parallel — data parallelism. Or for truly huge models, the weights themselves get divided: each machine holds only part of the network — model parallelism. The challenge is that these machines have to talk to each other constantly, sending the results of their computations forward and backward. That communication — moving data across the network — can be slower than the computation itself.

The hard part is load balancing. If one machine finishes its work but has to wait for another one, that is wasted time. And all the machines have to coordinate their gradients — the updates to the weights that learning requires. If the machines have different capabilities (some are GPUs, others are TPUs, some older hardware), how do you divide the work fairly? Some papers focus on scheduling — deciding which machine does what. Others work on reducing communication: maybe you can compress the data being sent, or send it less frequently, without losing the ability to learn well.

A related problem: what if machines fail or go offline? Or what if you want to add more machines mid-training without starting over? These papers tackle distributed training for real-world conditions where things are messy and unpredictable, not just clean lab setups.

How the work breaks down

Work in this subtheme splits into four directions: training on many machines when clients have different hardware and data, deciding which expert in a group should handle each input and balancing load across experts, combining models trained separately by different machines, and organizing pipeline parallelism for long sequences where machines have to coordinate their work.

Federated Learning with Heterogeneous Clients

When training happens across many machines owned by different organizations—hospitals, banks, or schools—those machines rarely have the same capabilities or the same data. One machine might be a fast GPU server with lots of memory; another might be a laptop with a slower processor and less memory. And the data on each machine might be completely different from every other machine's data: a hospital in New York has different patient patterns than a hospital in Tokyo. The challenge is training one model across all these machines without centralizing everyone's private data, while still getting accuracy that is as good as if all the data was in one place.

The Bridging Generalization Gap paper solves this by using generative models to create synthetic data locally on each client machine, which helps each client understand patterns that might be rare in its own data but common elsewhere. This narrows the gap between specialized models (each trained only on local data) and a global shared model that everyone contributes to. CLoVE takes a different approach: instead of one global model that all clients use, it clusters clients whose data patterns are similar and trains separate models for each cluster. By figuring out which clients belong together based on their loss patterns, it converges much faster because each client trains with others who have similar data—the training stays stable rather than oscillating when mixing incompatible data. Heterogeneous Federated Fine-Tuning with Parallel One-Rank Adaptation—Fed-PLoRA—handles the case where clients want to fine-tune a large language model but have vastly different hardware (some have 8GB memory, others have 80GB). By using parallel low-rank adapters—small learned adjustments that split across machines—instead of storing them all on one client, it lets weak machines participate without needing to store the full model. All three papers show that when you accommodate differences in hardware and data rather than ignoring them, federated training works better and faster in the real world because you get more reliable convergence, fuller participation from all machines, and each client learns in a way that actually fits its constraints.

Mixture of Experts: Routing Decisions and Expert Specialization

When a model is too big to fit on one machine, one solution is to split it into many smaller models called experts, where each expert is small enough to run on its own hardware. But then there is a critical decision to make: for any given input, which experts should actually run? Running all experts is wasteful because many will be irrelevant to that input. The challenge is routing tokens—deciding which expert processes which part of an input—in a way that specializes each expert to handle specific patterns, without overwhelming any one expert.

LD-MoE: Learnable Dynamic Routing learns to route tokens differently at different layers of the network, adapting which experts handle which parts of an input based on what the token actually needs. This learns patterns like 'layer 5 should send math tokens to math-expert-3' and 'layer 9 should send language tokens to language-expert-2'. By learning these routing rules end-to-end, it outperforms fixed routing strategies. LoRA-Mixer combines mixture-of-experts with low-rank adapters (small learned adjustments to the network) by learning which expert specializes in which capability—maybe expert-1 knows coding, expert-2 knows math, expert-3 knows common sense—then learning to route through serial scoring, a simpler mechanism than traditional expert routing that rates how well each expert fits each token one at a time. This specialization is so effective that it gets 3.79% improvement on math problems and 3.95% on common-sense reasoning with fewer trainable parameters than standard approaches. MoBE: Mixture-of-Basis-Experts solves a different part of the routing puzzle: when you have very large models like Qwen3-235B with many experts, you can compress them by noticing that many experts are redundant. If five experts all learn very similar patterns, why run five? MoBE replaces them with a single expert that learns a basis decomposition, like finding that twenty experts can be reconstructed from just five basis experts. This shrinks the model by 24-30% with only 1-2% accuracy loss, and it still works with the existing routing decisions. UltraMemV2: Memory Networks Scaling to 120B takes the opposite view: instead of splitting work across many experts, it uses one large model with specialized memory blocks that handle different patterns. By learning which memory blocks to activate for which inputs—a form of dynamic routing applied to memory—it achieves performance matching eight-expert mixture-of-experts models but with lower memory access costs and better long-context performance. Together, these four papers show that the key to efficient multi-machine training is routing decisions that specialize each expert rather than making experts redundant.

Combining Models Trained Separately

In distributed systems, different teams often train models independently—one team trains a model for English, another for Mandarin, another for code. Eventually you need to combine these separate models into one system. But you cannot just average their weights like you would average numbers, because the weights might represent completely different features learned in different ways. The challenge is merging independent models without losing what each one learned.

LS-Merge: Merging Language Models in Intermediate Space shows that averaging models in the space of their intermediate outputs (the hidden states—what the model 'thinks' about halfway through processing) works much better than averaging their weights (the actual numbers stored in the network). When you average weights directly, you often destroy information because small shifts in what each weight represents mean the combined result loses meaning. But if you average the intermediate representations that the model produces during computation, you preserve the key ideas. This technique even works when merging models of different sizes by learning a scaling factor in intermediate space. LEGO-FL: Learning Heterogeneous Federated Models as a LEGO Assembly takes a modular view: instead of treating each model as a solid block, it breaks them into pieces and lets different clients learn different pieces together. Like LEGO bricks, a simple foundation layer might be shared across clients and tasks, but specialized blocks—adapters for coding, blocks for biology—are learned locally and snapped together. This lets heterogeneous devices participate in one global system without retraining everything. Both papers demonstrate that combining models works when you respect the structure of what was learned rather than treating all weights the same way.

Context Parallelism and Pipeline Training at Scale

When you try to train a language model on very long sequences—documents with thousands of tokens—the memory cost explodes because computing which tokens relate to each other requires scoring every token against every other token, and storing those scores takes quadratic memory. One way to split this work is context parallelism, where different machines each process different parts of the sequence in parallel. But if machine A finishes its part of the sequence first, it has to wait for machine B before it can compute the next layer, which is inefficient. The other problem is training with reinforcement learning on multiple machines: you generate many trajectories in parallel, but machines finish at different times, and synchronizing them wastes compute.

Long-Context Attention Benchmark: From Computational Efficiency to Distributed Context Parallelism provides the first practical study of how context parallelism works across a real cluster of up to 96 GPUs. It benchmarks different methods for computing token relationships—some are fast but lose information, others are slow but keep everything—and measures the end-to-end training time across many machines. This lets researchers see that context parallelism trades off computation speed for memory savings, and now they know which trades are worth it. UNIVERSAL AND EFFICIENT LOADING BALANCING FOR RL TRAINING—FlexRL—solves the machine-synchronization problem for reinforcement learning. In RL training, you generate trajectories on many machines in parallel, then collect rewards and learn from them. The problem is machines finish at different times, creating idle periods. FlexRL schedules which machine generates which trajectory, predicting how long each will take and keeping machines busy instead of idle. It achieves 4.2x to 7.7x speedup on 128 GPUs compared to production systems, because nobody is waiting. Both papers address the core inefficiency in distributed training: machines working out of sync, waiting for each other, and that wasted time costs money.
