Multi-Armed Bandits with Minimum Revenue Constraints

When you must decide which arm to pull in each context while keeping every arm above a minimum reward, this paper trades off between chasing high rewards and obeying the fairness rule.

Paper explainersAll themesLearning Theory

Imagine a recommendation system that must show ads fairly: each advertiser needs a minimum number of views across all users. But you also want to maximize clicks. This is a bandit problem where you learn which arm is best in each context, but you cannot just greedily chase the highest reward—you must also keep each arm above its threshold. This paper designs two algorithms that sit at opposite ends of a tradeoff: one chases reward and breaks the fairness rule sometimes, the other obeys fairness strictly but leaves rewards on the table.

Zero assumption version

The fairness and performance trap

A bandit problem is a choice machine: in each round, you pick one of several options (arms) without knowing their rewards in advance, get feedback, and repeat. A multi-armed bandit learns which arm is best over time. But real systems add constraints: if you are allocating views across advertisers, each one needs a minimum. If you are routing traffic across servers, each must handle a fair load. If you are doing clinical trials, each treatment must accumulate enough data. Greedily pulling the highest-reward arm ignores these fairness rules.

A beginner might try this: play each arm just enough to hit its minimum, then chase the highest-reward arm forever. This fails because the highest-reward arm changes depending on context—who is using the system, what time it is, what their preferences are. In some contexts, a low-reward arm must be played to keep it above its minimum, eating into reward. The trade-off between reward and fairness is real and unavoidable.

In one sentence. The paper designs two algorithms that navigate a Pareto frontier: one prioritizes reward and sometimes breaks fairness, the other prioritizes fairness and sometimes sacrifices reward.

The algorithm as a flow

What it actually does

Observe the context.

Learn which user, time of day, or situation we are in this round.

Build an optimism or pessimism band.

Estimate upper or lower confidence bounds on each arm's reward in this context.

Solve a linear program.

Find the best mix of arm-plays that respects the minimum constraints while maximizing (or protecting) reward.

Sample an arm from that mix.

Draw randomly according to the allocation—arm with weight 50% gets picked 50% of the time.

Update beliefs and track violations.

Record the actual reward and constraint surplus or deficit to tighten estimates for the next round.

What the paper changes

What the paper changes

The paper changes the allocation rule—the mixture of plays across arms in each context. Instead of a fixed greedy rule or a naive uniform split, the algorithm re-solves a linear program each round to find the best allocation that respects constraints.

the object it moves  =  Arm allocation per context
The hidden quantity

The saturated constraint set

measured quantity  =  Which constraints are tight

The hidden quantity is the set of constraints that are exactly met—saturated. If arm Red needs a 40% minimum and gets exactly 40%, its constraint is saturated. If it gets 50%, it has slack. At optimality, some constraints are tight (they drive the solution) and others have room to spare. The paper estimates which constraints will be saturated in the limit.

The paper estimates this by maintaining optimistic (best-case) and pessimistic (worst-case) upper confidence bounds on each arm's reward, then solving the linear program to find which constraints must be tight to achieve the target objective. The faster this estimate converges to the true saturated set, the fewer wasted plays occur, because the algorithm stops guessing wrong about which arms need to be played to hit their minimums and can focus plays on high-reward arms instead. Each wrong guess translates to rounds spent allocating to an unnecessary arm.

Why it works

Why the tradeoff works the way it does

The mechanism hinges on two choices: optimism or pessimism. In each round, the algorithm builds confidence bounds on each arm's reward—a best-case guess (optimistic) or a worst-case guess (pessimistic). The optimistic algorithm (OLP) solves the linear program using the best-case bounds, so it assumes high rewards are achievable and allocates greedily within the constraint. This prioritizes total reward but can violate constraints because the best-case guess was too rosy. The pessimistic algorithm (OPLP) uses worst-case bounds, so it plays it safe, over-allocating to arms with risky constraints to guarantee they hit their minima. This keeps constraints satisfied but leaves high-reward arms under-played because the pessimistic guess was too cautious.

Why does the linear program work at all? Because the problem has a special structure: the constraints are linear thresholds on cumulative reward, and the objective is total reward. The optimal solution always allocates to a subset of arms such that some constraints are exactly met (saturated) and the others are not. The algorithm does not need to enumerate all possibilities—it solves a single linear program to find that optimal active set and the allocation that saturates it.

Math after the picture

The linear program at each step

First in words:

Maximize total reward w times mu, subject to: for each arm k, the cumulative reward times w k is at least lambda k (the minimum), and all w sum to 1.

Then the compact form:

max_w: sum_k w_k * mu_k, s.t. w_k * mu_k >= lambda_k for all k, sum_k w_k = 1, w_k >= 0

Every symbol:

w_kHow often to play arm k (a fraction between 0 and 1)
mu_kThe average reward of arm k in this context
lambda_kThe minimum total reward required for arm k
sum_k w_kAll arm fractions must add up to 1 (all plays accounted for)
A tiny worked example
Context: User A. Red arm has mu = 10, minimum lambda = 4. Blue arm has mu = 5, minimum lambda = 4.
Constraints: w_Red * 10 >= 4, so w_Red >= 0.4. And w_Blue * 5 >= 4, so w_Blue >= 0.8.
But w_Red + w_Blue must equal 1. Since 0.4 + 0.8 = 1.2 > 1, the constraints are infeasible in this context alone.
So the algorithm spreads plays across contexts to accumulate reward. If User B has Blue reward = 9, the algorithm can play Red in context A (even below minimum) and Blue in context B to hit both thresholds on average.
Total effect: plays in many rounds sum up; the algorithm solves the LP to find the overall mix that hits all constraints while maximizing total reward.

The linear program finds the exact mixture of arm-plays needed each round to balance reward and fairness without waste.

What can go wrong

What can go wrong

Infeasible constraints. If the sum of all arm minimums exceeds what can be satisfied (the constraints are contradictory even in hindsight), no algorithm wins. The paper handles this by showing the regret still scales well even when feasibility is barely possible.
Heavily skewed rewards. If one arm dominates in all contexts, the algorithm must still allocate to all arms to hit their minimums. This can waste a lot of plays. The paper shows this cost as part of the regret bound.
Optimism or pessimism misaligned with true rewards. If the confidence bounds are set too wide or too narrow, the algorithm wastes rounds learning the true rewards. The paper derives bounds assuming standard concentration inequalities hold.
Done right: context matters. By allowing aggregation across contexts, the paper avoids infeasibility in single contexts. If Red is bad for User A but good for User B, the algorithm can hit Red's minimum by playing it for User B and leaving it lower in context A.
What a runnable demo should prove

What a runnable demo should prove

A runnable demo simulates a recommendation system with two advertisers (arms) and two user types (contexts). Red advertiser pays 8 per show to users of type A but only 2 to users of type B. Blue advertiser pays 3 to type A but 8 to type B. Each advertiser has a minimum of 30 shows. Run the optimistic and pessimistic algorithms on 500 rounds where each round is a random user type, and plot total reward and constraint satisfaction (do both arms hit their minimums) over time.

Regret = (optimal total reward - algorithm total reward) + 100 * (number of rounds where constraint is violated)

The demo must show OLP converging to higher reward but violating constraints early, while OPLP stays feasible from the start but plateaus lower. Both converge to the true optimal allocation by the end, just by different paths.
