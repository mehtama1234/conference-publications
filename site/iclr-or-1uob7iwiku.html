Code World Models for General Game Playing

Ask an LLM to write the game in Python code, then search with a real planner instead of asking the LLM to play.

Paper explainersAll themesLLMs & Foundation Models

When you ask an LLM to play chess, it often breaks the rules or makes weak moves because it tries to pattern-match directly from text. This paper does something different: it asks the LLM to first translate the game rules into working Python code—a simulation that can enumerate legal moves, check if the game is over, and report the score. Then a classical search algorithm (Monte Carlo tree search) searches that simulation to find winning moves. This splits the job: the LLM does what it is good at (understanding natural language), and the planner does what it is good at (exploring possibilities).

Zero assumption version

LLMs play games badly when you ask directly

When a language model is prompted to play a game like chess or poker, it tries to pick the next move by matching patterns it learned during training. But games have precise rules: you cannot move a piece off the board, you cannot play a card you do not have, and some moves are only legal in specific situations. The LLM's pattern-matching is fragile—it breaks these rules often. And even when the LLM does produce a legal move, that move is shallow and weak because the model is not actually exploring future possibilities; it is just guessing based on surface similarity.

A beginner's fix would be: add a rule checker as a filter after the LLM outputs a move (check if it is legal, if not, reject it). But this is like asking someone to walk blindfolded and then correcting them after each illegal step. The LLM still has no picture of the game ahead.

The real problem. Language models are trained to guess the next token of text, but games need three things: (1) a way to check if a move is legal (because the rules are precise, not fuzzy), (2) a way to explore many possible futures (because the winning move is not always obvious from context), and (3) a way to pick the move that leads to a win (because you need to compare futures and rank them). Direct LLM prompting does not have these.

Translate to executable code

The LLM outputs Python functions: is_legal(state, move), next_state(state, move), game_over(state), evaluate_score(state).

Verify the code runs

Execute the generated code against the examples to check: does is_legal reject illegal moves? Does next_state transition correctly?

What the paper changes

The thing the paper changes

Instead of asking the LLM to generate a move directly, the paper asks it to generate the game itself: the rules as executable code (a world model in Python). This shifts what the LLM has to do—from playing the game to understanding the rules and writing a simulation.

the object it moves  =  what the LLM generates
The hidden quantity

Code correctness: Does the generated world model match the real rules?

measured quantity  =  correctness of the generated code

The hidden quantity is whether the Python code the LLM generates is faithful to the real game rules. If the code is wrong (it allows illegal moves, or it reports the score incorrectly), then MCTS will search in a broken simulation and pick moves that look smart inside the fake game but fail on the real board, because the fake game rules do not match reality.

The paper estimates this by unit testing: after generation, it runs the code on the sample game trajectories provided. If the functions return the right outputs (is_legal correctly rejects moves that should be illegal, next_state produces the right board after each move), the code passes verification and MCTS can trust it. If the code fails these tests, the system must reject it and ask the LLM to try again.

Why it works

Why this works

The core insight is a division of labor: the LLM is good at reading and writing natural language, understanding what rules mean. It is bad at combinatorial search (exploring millions of futures). The planner (MCTS) is the opposite—it is dumb about language but brilliant at exploring a space systematically.

When the LLM writes Python code, it is translating: from fuzzy prose (the rule book) to precise logic (functions that return true or false). This is a narrower task than playing the game. And once the code is written and checked, MCTS can search fearlessly—every state it visits is provably reachable within the rules.

In contrast, if you ask the LLM to play directly, it has to do both jobs at once: understand the rules and find the winning move. That is too much. It breaks rules because the rules are implicit in its training data, fragile and entangled with context. And it plays shallow moves because it is not exploring the game tree; it is just pattern-matching.

The search is strategic: MCTS can try thousands of futures and pick the move that won most often. This beats the LLM's pattern-matching on any game where the winning strategy is not obvious from surface similarity.

Counting wins in the search tree

First in words:

For each move from the current state, count how many of N simulated games win if we play that move. Pick the move with the highest win count.

Then the compact form:

best_move = argmax_m { count_wins(m, simulations=N) } where count_wins(m, N) = sum over simulations i of (1 if game_from(state, m) eventually wins else 0)

Every symbol:

ma candidate move from the current game state
best_movethe move with the highest win count after search
count_wins(m, N)number of times playing move m leads to a win in N simulated games
statethe current board position
simulationstotal number of futures to explore (e.g., 100 or 1000)
A tiny worked example in tic-tac-toe
Current board: X has three in the top row (X X X), O has two in the middle column (O . O). Only the center square is empty.
Candidate move: Play in the center square (only legal move left).
Simulate 10 games from this state, each time playing randomly for both players.
Outcome: All 10 simulations end in a win for X (X got 3 in a row on the first move or O did not block in time, though X already won).
Win count for center move: 10 out of 10.
Best move: center (no other moves available).
MCTS decision: Play center. The high win rate makes the choice clear.

What can go wrong

What can go wrong

The LLM writes code that looks right but is subtly wrong. Example: the LLM implements the rule for castling in chess but misses that the king or rook must not have moved yet. MCTS will search using the wrong rule, and the strategy it finds will fail in real play.
The generated code handles known cases but fails on edge cases. Example: the code works for the small tic-tac-toe in the examples (3 by 3), but if you run it on a larger 4 by 4 board, the win-condition check is hard-coded for 3 and misses larger boards.
The code has a performance bug and times out. Example: next_state recalculates the full board from scratch instead of incrementally updating it. For large games like Chess, this is too slow and MCTS cannot simulate enough futures before the move deadline.
Verification passes and code is correct. Done right: the unit tests on the sample games exercise the code well enough to catch most errors. MCTS searches the verified model and finds strategy.
What a runnable demo should prove

What a runnable demo should prove

Build a simple game (tic-tac-toe or Connect-Four) with three implementations: (1) the real rules as a reference, (2) an LLM-generated world model in Python, and (3) a direct LLM policy (prompt and parse the output). For 100 random positions, run the LLM policy and the MCTS policy (using the generated model). Count illegal moves, wins, and game length.

illegal_move_rate = count of illegal moves / total moves attempted; win_rate = games won / total games played; avg_game_length = total moves in all games / total games

The demo must show: the LLM policy breaks rules frequently, the MCTS policy with generated code never breaks rules (because the code is verified), and MCTS strategy depth beats the LLM's pattern-matching on unfamiliar positions.
