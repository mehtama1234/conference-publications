LiveFigure: Generating Editable Scientific Illustration with VLM Agents

Generate scientific figures as editable slide objects by planning the layout, writing drawing actions as code, and checking the rendered result before delivery.

Paper explainersAll themesOther

A scientific figure is not only an image. It is a structured document made of text boxes, arrows, shapes, spacing rules, and labels that authors often need to revise manually before submission. Most image generators produce pixels, which means a user cannot easily move one arrow, fix one label, or align one box without redrawing the whole figure. LiveFigure changes the target output: it plans a figure, writes executable drawing steps for PowerPoint, renders the figure, inspects the result, and revises the code until the output is editable and close to publication quality.

Zero assumption version

Scientific figures must stay editable after generation

Researchers use figures to show pipelines, experiment setups, model components, and result summaries. Those figures usually need late revisions: a label changes, a box needs more room, an arrow direction is wrong, or a reviewer asks for a panel to be reordered. Raster images make those changes expensive because each visual element has been flattened into pixels.

That means the actual task is not standard image generation. The system has to output a structured drawing program whose objects can still be selected and edited. Existing prompt-to-image tools miss this requirement because they optimize visual plausibility, while the paper optimizes for object-level correctness, editability, and layout repair.

The paper's move. Generate a figure through the same stages a careful author would use: plan the structure, write object-level drawing commands, render them, inspect the result, and repair the specific objects that failed.

The hidden quantity

The hidden quantity

measured quantity  =  editability at the object level

The hidden quantity is object-level editability: whether each important visual element still exists as a separate object after generation. A figure can look acceptable on first glance and still be a bad scientific artifact if its labels are baked into one bitmap, because the user then cannot correct a single term or move one panel cleanly.

LiveFigure raises this quantity by generating through PowerPoint commands. Each rectangle, text box, arrow, and grouped panel remains a separate object with coordinates and style fields. That matters because publication workflows require both visual quality and revision speed, and only object-level outputs support both.

Why it works

Why the multi-agent loop works

The key design choice is separating planning from drawing. Figure planning is about semantic structure: what panels exist, what each one says, and which arrows connect them. Drawing is about executable detail: exact positions, font sizes, object dimensions, and grouping commands. One module rarely handles both well at once, because the planning errors and drawing errors are different.

The second design choice is rendering before finalizing. A drawing script can look plausible in text while still producing overlap, clipped labels, or broken alignment. Rendering exposes those failures in the same medium that a human reviewer sees. The diagnosis agent can then point to concrete defects and request local code changes instead of regenerating the whole figure.

The final design choice is using an editable slide format as the execution environment. This matters because the system is judged not only on appearance but on whether downstream authors can correct details quickly. Code that creates native slide objects preserves that edit path by construction.

The repair objective

First in words:

The system wants a figure that matches the requested structure while requiring few manual edits after generation. A simple way to express that goal is to combine a structural error term with a manual-edit penalty.

Then the compact form:

total_figure_cost = structure_error + manual_edit_penalty

Every symbol:

total_figure_costoverall quality score that the generation and repair loop tries to reduce
structure_errorhow far the rendered figure is from the intended objects, labels, and relations
manual_edit_penaltyhow much cleanup a human still needs to do after generation
A tiny worked example
Suppose the blueprint requires 10 labeled objects and 6 connectors.
The first rendered slide misses 2 labels and misplaces 3 connectors, so the structure error is high.
It also needs 12 human edits, so the manual-edit penalty is high.
After one repair pass, all labels exist and only 1 connector is misaligned.
Manual edits drop from 12 to 4, so the total figure cost drops with them.
The method keeps repairing until most of the remaining cost comes from details a human can finish quickly.

The paper uses richer evaluation than this shorthand, but the central objective is clear: preserve structure and reduce manual cleanup at the same time.

What can go wrong

What can go wrong

The blueprint can omit essential structure. If the planning stage forgets a panel or a relation, later agents may render a clean figure that still says the wrong thing because the missing object was never requested in the first place.
Diagnosis depends on the rendered view. A visual checker can catch overlap and clipping, but it may miss a subtle scientific mistake such as a mislabeled axis or a wrong causal direction unless the plan explicitly encodes that requirement.
PowerPoint skills constrain the figure space. Some specialized scientific art, such as dense molecular drawings or custom plotting styles, may be awkward to express with standard slide objects, so the code generator may need domain-specific drawing libraries.
Done right. The method is strongest on workflow and method figures because those are built from reusable objects, explicit relations, and local layout repairs that slide-native commands can represent cleanly.
What a runnable demo should prove

What a runnable demo should prove

Build a small figure generator for method diagrams with boxes, arrows, icons, and captions. Give it a prompt such as a three-stage machine learning pipeline and require it to output native slide objects instead of a flat image.

Then force a repair loop by checking for overlap, missing text, and connector mistakes after rendering. The demo passes if a user can open the final file, move one object without breaking the rest of the figure, and finish the remaining corrections in only a few edits.

The decisive result is not only that the figure looks good, but that the final artifact remains easy to revise because the generator never collapsed the structure into pixels.
