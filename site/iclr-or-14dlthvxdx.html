Discrete Controller Modules for Symbolic Planning

A Transformer learns to solve algorithmic puzzles by inserting small program executors that handle loops, variable storage, and conditional branches.

Paper explainersAll themesAgents & Tool Use

Transformers (a type of AI model built from attention, which means examining many parts of the input at once to find the right answer) are excellent at spotting patterns in text, but they struggle when a task requires a sequence of logical steps: hold a number in memory, update it, make a decision based on it, and loop back. This paper adds small program executors to Transformer layers—think of them as tiny calculators that track variables and make choices step by step.

Zero assumption version

Transformers get lost in long procedural tasks

A Transformer reads text by sliding a technique called attention (which looks at all positions in the input at once to find connections) across all positions and combining them. This works brilliantly for spotting similar words, recognizing objects, or translating. But it breaks on tasks where you must hold a number in memory, update it step by step, and make branching choices. A Transformer has no natural way to say 'if the sum is greater than 10, jump back to line 3; otherwise add 5 to the register.'

When the task gets longer than the training examples, Transformers fail even more. They have never learned the underlying algorithm, just the shape of shorter versions. A human who has learned to sort by hand can sort lists of any length. A Transformer trained on sorting lists up to 50 items may fail on 100-item lists. It lacks the loop structure.

In one sentence. The paper inserts small discrete program executors (tiny instruction processors) into Transformer blocks so the model can execute loops, store and update variables, and branch conditionally—because giving the model explicit state (registers and flags to hold values and decisions) lets it learn a repeatable algorithm instead of memorizing attention patterns.

Five-panel picture

1. The problem

Transformer reads words, but no memory or loops. Each position treated alone.

2. The controller modules
ASSIGN | ADD | COMPARE | BRANCH (four program primitives)

Four operation types plug into each layer: assign a value, add numbers, compare them, branch based on truth.

3. Register state

The model tracks state across layers: registers hold numbers, flags hold true/false. State flows forward.

4. Selection and execution
Gumbel-Softmax picks operation at each step; registers update from chosen primitive

At each layer, a soft selector chooses which of the four operations to run. Registers update smoothly.

5. Length generalization

Model trained on 50 steps learns the loop pattern and executes it on 100- and 200-step lists.

The algorithm as a flow

What it actually does

At each layer, choose an operation

A soft selector (Gumbel-Softmax, which turns raw scores into smooth fractions that sum to 1) picks ASSIGN, ADD, COMPARE, or BRANCH with learned weights.

Execute the chosen primitive

The operation reads registers and updates them: set a register to a new value, add to it, compare two registers, or skip ahead.

Update flags and jumps

COMPARE sets a flag to true or false. BRANCH uses the flag to decide whether to jump to a different layer or continue.

Pass registers forward

Register state (the numbers and flags currently tracked) flows to the next layer so later operations can read them.

After each layer, merge back into the Transformer

The Transformer's usual attention and feedforward layers run, but now they can see the current register values as extra context.

What the paper changes

What the paper changes: layer-by-layer control flow

Rather than giving a Transformer a bag of tricks and hoping it learns loops, the paper inserts explicit, tiny program executors. Each layer can now hold a small state (a handful of registers and boolean flags), select one of four primitive operations, and execute it.

the object it moves  =  Discrete program state and operation selection
The hidden quantity

The hidden quantity: register role and operation clarity

measured quantity  =  Register alignment and operation purity

The hidden quantity is how cleanly each register's role maps to ground truth. In a sorting task, one register might naturally represent 'the smallest unsorted value,' another 'the next position to fill,' and so on. The paper measures whether the learned registers line up with these roles by training a simple linear classifier on top of the register values and checking if it predicts the ground truth role.

A second hidden signal is operation purity: the fraction of the time each primitive is used correctly. If COMPARE is called 100 times in an ideal execution trace, does the Gumbel-Softmax selector actually choose COMPARE when needed, or does it pick the wrong operation? High purity means the model has learned a clean, interpretable execution.

Why it works

Why the method works: learning becomes program synthesis

The root cause of Transformer failure on long procedural tasks is that attention and feedforward layers are stateless. Each position produces output from the current input and learned weights alone. On a sorting task, this means the model must pack the entire algorithm's state into the pattern of attention—which position attended to which, and how the weights combined them. This explodes in complexity as the task grows longer.

The paper sidesteps this by giving the model an explicit state: registers and flags. Now, when the Transformer needs to hold a value, it literally stores it in a register. When it needs to make a conditional choice, it sets a flag. The Gumbel-Softmax selector learns which primitive to call at each step, and the model can tune these choices to match the ideal algorithm.

Why does this enable length generalization? Because the learned algorithm is now modular and repeatable. If sorting loops five times in the training data, the Transformer learns the five-operation sequence. If at test time sorting requires twenty loops, the model applies the same sequence repeatedly. It has learned a loop, not just an attention pattern specific to short lists.

Math after the picture

The core equation: soft discrete selection with relaxation error bounds

First in words:

The total cost is the Transformer loss plus a penalty term that measures how far the relaxed (soft) execution deviates from the ideal discrete (hard) operation sequence. The penalty grows with selection noise and comparison sharpness defects.

Then the compact form:

loss = L_cross_entropy + beta * (tau + kappa_inv) * sum_t ||soft_op_t - discrete_op_t||

Every symbol:

L_cross_entropystandard Transformer prediction loss (negative log-likelihood)
betaweight controlling how much we penalize relaxation error
tauGumbel-Softmax temperature (higher = softer, noisier selection)
kappa_invinverse comparison sharpness (higher = fuzzier comparisons)
soft_op_tthe soft (continuous) operation probabilities at step t
discrete_op_tthe ideal hard operation (0 or 1 for each choice) at step t
A tiny worked example
Suppose tau = 0.1 (sharp selector) and kappa_inv = 0.2 (sharp comparisons). Then tau + kappa_inv = 0.3.
Transformer loss = 1.5 (not predicting perfectly). Relaxation penalty = 0.8 * 0.3 * 2 steps with deviation = 0.48.
Total loss = 1.5 + 0.48 = 1.98. If we increase temperature to tau = 0.5 (softer, noisier selection), tau + kappa_inv = 0.7.
New penalty = 0.8 * 0.7 * 2 = 1.12. Total = 1.5 + 1.12 = 2.62. The model learns to turn down temperature to stay sharp and reduce relaxation error.

The equation formalizes the tradeoff: soft selection lets the model learn (gradients flow), but the paper bounds how much error that softness introduces and trains to minimize it.

What can go wrong

What can go wrong

Registers get tangled. If two different roles (e.g., loop counter and comparison flag) try to use the same register, the model's signals interfere. The learned algorithm becomes fragile and breaks when task lengths are far from what it was trained on (longer than training examples).
The selector remains soft and noisy. If the Gumbel-Softmax temperature stays high, the model picks the wrong operation at critical steps. This adds random error that accumulates over many loop iterations. Longer tasks suffer more.
Memory (if used) overflows. If the task requires storing more values than the available memory cells, the model has nowhere to put them. This can only be solved by increasing memory size at design time.
Done right. When the controller modules are tuned, each register takes a clear role, the selector is sharp enough to pick the right operation, and memory size matches task demands. The model learns a clean, repeatable algorithm that transfers to any length.
What a runnable demo should prove

What a runnable demo should prove

A minimal demo on a sorting task: train the controller-augmented Transformer on sorting lists of length 1 to 50. Then test it on lists of length 100, 200, and 500. Plot the accuracy as a function of length. Alongside the plot, show the learned operation trace (which operation fires at which step) and visualize the register values as the algorithm runs. The reader should see three things: (1) accuracy stays high even at 500 items (the Transformer is running the learned loop, not memorizing), (2) the operation trace is clean and repeatable across different random list inputs (ASSIGN at step 1, COMPARE at step 2, BRANCH at step 3, ASSIGN again if true, loop back), and (3) the register values track the algorithm's internal state—one register holding the running minimum, another holding the insertion position.

The gap should be <10 points for the controller model (vs. >50 points for vanilla Transformer). The operation trace and register visualization should be interpretable enough that a human could re-code the learned algorithm as pseudocode.
