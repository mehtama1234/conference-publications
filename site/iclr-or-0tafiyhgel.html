Unlocking the Value of Text: Event-Driven Reasoning for Time Series

When you are trying to predict the future of a real-world process like stock prices or energy demand, treating numbers as just numbers misses what caused the numbers to change—the paper shows how to use text stories about events alongside the numbers to guess better.

Paper explainersAll themesTime Series & Sequential

Time series forecasting is guessing future values in ordered data like daily temperatures or stock prices. Today's methods look only at the historical numbers. But in the real world, events change those numbers: a news headline about a new regulation shifts energy markets, or a holiday announcement changes demand patterns. This paper asks: what if we gave the forecasting model text descriptions of the events that shaped the numbers, plus the raw numbers themselves? It proposes VoT (Value of Text), which lets an LLM reason step-by-step from both stories and numbers to make better predictions.

Zero assumption version

Why numbers alone are not enough

Time series forecasting is a tool that guesses what comes next in a stream of measurements. A power grid predicts tomorrow's electricity demand. A store predicts next week's sales. Hospitals predict patient arrivals. Today's forecasting models take in the historical numbers and detect patterns—if sales have grown every Monday for three months, they guess they will grow next Monday too. The problem is that the real world has invisible shocks. A sudden news story about a fuel shortage does not leave a trace in the previous numbers; it creates a new number today that breaks the old pattern. A holiday announcement does not show up in historical data; it warps next week's demand in a way the model has never seen. So when an event the model has not encountered before hits, the numbers jump in a direction the pattern-detector cannot foresee. This leaves forecasting models stuck: they can spot regular ups and downs in past numbers, but they cannot reason about why the numbers are changing.

A beginner might try to get around this by collecting every possible event and manually labeling what each one means for the forecast. That would work but is slow and brittle: a new kind of event requires a human to design a new label. Or the beginner might try to feed text descriptions of events directly into the model as raw text, hoping the model figures out which parts matter. But LLMs (the large language models designed to read and reason about text) are not directly designed to output number forecasts—they are built to output words—so the connection between what the text understands and what the numbers predict stays loose and hard to steer.

In one sentence. The paper builds a method that lets an LLM reason step-by-step from event text to produce a forecast, and then it blends that text-based forecast with a traditional number-based forecast, letting each one catch what the other missed.

The algorithm as a flow

What it actually does

Step 1: Describe the current moment

Convert recent numbers into a short English sentence (e.g., 'Energy demand was high yesterday, up 10%, likely due to cold weather').

Step 2: Retrieve a memory

Find the most similar example from training data where the LLM already worked through a similar situation.

Step 3: Reason from the past

Show that old example to the LLM and ask it to reason step-by-step to a forecast for the new situation.

Step 4: Also run the number forecast

In parallel, use a traditional number-based model (a Transformer that reads time series) to make its own guess.

Step 5: Blend both forecasts

Weight-combine the text forecast and the number forecast using frequency analysis to balance their strengths.

What the paper changes

The single thing the method changes

What the paper moves is the forecast itself. Normally, a forecasting model takes historical numbers and outputs numbers. VoT keeps that, but adds a second path: one that takes event text, sends it through an LLM to get a text-based forecast, and then merges it with the number-based forecast. The method does not change the numbers or the LLM itself; it changes where the final forecast comes from by building a new combination rule.

the object it moves  =  the forecast: now from text reasoning plus numbers
The hidden quantity

The hidden quantity: similarity to the past

measured quantity  =  relevance of historical examples

When the LLM sees a new event, it needs guidance on how to reason about it. The hidden quantity is: how similar is this new event to events the LLM has already reasoned through? The paper measures this by comparing the descriptions of the events—if a new event description is close in meaning to a stored description, the old example is likely to be a good template for reasoning. The method computes this similarity using embedding vectors (just a way to turn text into lists of numbers so you can measure closeness).

The paper's technique retrieves stored examples from a knowledge base: during training, it saves the LLM's reasoning steps for each event-data snapshot, because storing worked examples lets the LLM learn the reasoning patterns. During forecasting, when a new event arrives, it finds the stored example whose text description is most similar to the new event, and hands that example to the LLM as a hint: 'Here is how you reasoned about something like this before. Now reason about this new one the same way.' This similarity score is the hidden quantity—it is the glue that connects current events to learned patterns, and the paper never directly shows you this number, but it is controlling the entire reasoning pipeline.

Why it works

Why this works: the real reason

The core insight is that LLMs are designed to reason step-by-step through text, but they do not know how to apply that reasoning to time series forecasting—they have never been trained on time series data, so they lack a sense of scale, trend, or seasonality in numbers. When you show an LLM an event description alone and ask it to guess numbers, it is starting from scratch. But if you first show it a similar past example where humans have already verified the reasoning, the LLM can copy the reasoning structure and adapt it to the new numbers. This is why retrieval matters: retrieval finds the template that makes the LLM's reasoning task concrete.

Meanwhile, the traditional number-based forecasting model (a Transformer applied to time series) has the opposite strength: it sees patterns in the numerical sequences that the LLM does not—if there is a weekly cycle, or a seasonal dip every year, the Transformer catches it. But it misses events outside its training distribution. So the payoff comes from fusion: the text branch handles events the number branch has not learned, and the number branch handles regular patterns the text branch might misinterpret. The fusion step uses frequency analysis—it looks at the raw numerical forecast and the text-based forecast side by side, and where they agree on the shape of the forecast (e.g., both say 'go up'), it trusts that signal; where they differ, it checks which frequencies (fast wiggles vs. slow trends) are relevant for this particular dataset, and weights them accordingly. In datasets where events drive the market (like energy prices during policy shifts), the text branch becomes trustworthy and dominates. In datasets with strong numerical seasonality, the number branch dominates. Neither one drowns out the other—they vote, and the vote is weighted by whether each branch is currently seeing reliable patterns.

Math after the picture

The equation and worked example

First in words:

The fused forecast at the end combines weighted frequency components from the text-derived forecast (from event reasoning) and the number-derived forecast (from pattern detection). Each frequency band (low for trends, mid for medium cycles, high for wiggles) gets its own weight that the model learns during training. The final output is the inverse Fourier transform (turning frequency back into time) of this weighted combination.

Then the compact form:

Ffused = sum_b ( wb * Fb ) where b in {low, mid, high} and Fb in {event-based, number-based}; Yfinal = inverse_FFT(Ffused)

Every symbol:

Ffusedthe combined frequency spectrum after weighting each band
wbthe learned weight for frequency band b (how much to trust that band)
Fbthe frequency components from event-driven or number-driven forecasting
bone of three frequency bands: low (slow trends), mid (weekly cycles), high (daily wiggles)
inverse_FFTa mathematical operation that converts frequency-domain data back into time-domain numbers
A tiny worked example
Suppose the event-driven branch predicts: 100 units for tomorrow (low freq), 5 units wiggle (high freq).
Suppose the number-based branch predicts: 95 units for tomorrow (low freq), 8 units wiggle (high freq).
Learned weights during training: wlow = 0.4, whigh = 0.6 (meaning the number branch is better at detecting fast changes, the event branch is better at trends).
Fused low frequency: 0.4 * 100 + 0.6 * 95 = 40 + 57 = 97 units (a blend favoring the numeric trend).
Fused high frequency: 0.4 * 5 + 0.6 * 8 = 2 + 4.8 = 6.8 units (a blend favoring the numeric wobble).
Reconstruction via inverse_FFT: the final forecast is 97 units with a 6.8-unit wiggle, representing both the event-reasoning trend and the numerical seasonality.

The equation says: take each frequency band separately, weight-blend the two forecasts, then stitch them back together as a time-series number.

What can go wrong

What can go wrong

Cold-start failure: no similar past event exists. If the dataset is short or the new event type has never happened before, the retrieval step returns a poor template, and the LLM's reasoning becomes unreliable guesses. The text branch fails, and the forecast reverts to numbers-only accuracy.
Text description quality matters a lot. If the event text is vague, missing, or wrong (e.g., a typo in the news headline), the LLM cannot reason well and the retrieval cannot find the right template. The method is only as good as the input text.
Prediction cost explodes. LLMs are slow to run. The event-reasoning branch takes 5.9 seconds per step (as the paper reports), while the number branch takes 0.002 seconds. For real-time forecasting systems that need updates every minute, this is too slow for production, because the LLM must think through its reasoning step-by-step, which takes time, while the number-based branch just applies learned pattern detection instantly.
Done right: when events are common and text is detailed. The method shines on datasets like energy trading, where policy announcements and weather reports regularly shift the market. When the event text is detailed and the training dataset is long enough to have many examples of similar events, the LLM's reasoning becomes trustworthy and retrieval finds good templates, because the model has seen similar reasoning paths before and can adapt them reliably.
What a runnable demo should prove

What a runnable demo should prove

Build a toy forecasting task: three months of daily stock prices and daily news headlines for one stock. Manually create or label five major events that occurred during this period (e.g., 'Product announcement', 'Earnings beat', 'Market crash', 'Analyst downgrade', 'Competitor bankruptcy'). Split the data: first month for training, next month for retrieval memory, final month for testing. Implement the number-based branch using a simple Transformer encoder on the time series. Implement the text branch using an LLM (even a small open model) that takes the event description and a retrieved similar past event as context, then outputs a reasoning trace and a numeric forecast. Measure accuracy: compare the number-only forecast, the text-only forecast, and the fused forecast on the held-out test month. In particular, test a day with an event the model has not seen before (e.g., a completely new type of news) and observe whether text-reasoning plus retrieval gets it closer than numbers alone.
