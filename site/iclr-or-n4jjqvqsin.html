Forge: Compiling Linear Attention into Fast Kernels

Forge is a compiler that turns different linear attention designs into fast, hardware-optimized code by breaking them into three universal steps.

Paper explainersAll themesEfficiency & Systems

Softmax attention (the foundation of large language models) gets incredibly slow on long texts because it has to compare every token (word or symbol) to every other token — that is quadratic time complexity (doubling the text length makes it four times slower). Linear attention variants fix this by using simple math that runs in linear time (doubling text only doubles the work). But unlike softmax, which has decades of hand-tuned, lightning-fast code, linear attention variants are slow because nobody has written optimized code for them yet. Forge solves this: it is a compiler that takes a simple description of any linear attention idea and automatically generates the fastest possible code for modern GPUs.

Zero assumption version

Linear attention is slow because it lacks fast code

Softmax attention runs in quadratic time (each token compared to all tokens), which is too slow for long sequences. Researchers invented linear attention: a simpler math trick that runs in linear time — just one pass through the data. But there is a catch: linear attention comes in many variants (different authors invent different versions), and each variant needs hand-written code to run fast on GPUs. Writing that code is hard, repetitive, and most variants never get optimized code, so they run slow despite the better math.

A beginner would try: write the linear attention math in Python, run it, and hope it is fast enough. It is not. Python is slow, and GPUs need special low-level code written in compiled languages. Each time a researcher invents a new linear attention variant, they either hand-write the low-level code themselves (weeks of work) or live with slow Python. This is a massive bottleneck — nobody can experiment because the startup cost is too high.

The problem in one sentence. Linear attention math is fast in theory but slow in practice because it lacks automated, hardware-optimized code generation.

The algorithm as a flow

What it actually does

Decompose

Map the linear attention algorithm into three phases: within-chunk math, state propagation between chunks, output merging.

Tile

Divide the data into small tiles that fit in fast GPU cache, process each tile with fused operations (no stalls).

Fuse

Combine computation and data movement into single GPU kernels so the processor does not wait.

Distribute

Automatically partition the tiled computation across many GPUs, with minimal synchronization overhead.

Generate

Output the compiled, optimized GPU code (fast kernel) that runs the algorithm at hardware speed.

What the paper changes

What the paper changes: the code generation target

Before Forge, a researcher would write their linear attention algorithm in PyTorch (readable but slow). Forge takes that PyTorch code and automatically generates the low-level optimized GPU kernel code. The thing it changes is: the target of compilation — from slow, general-purpose code to fast, specialized code.

The hidden quantity

The hidden quantity: GPU memory bandwidth utilization

measured quantity  =  Fraction of peak data-movement bandwidth used

A GPU has two limits: raw computation speed and how fast data can move in and out of memory. Most code bottlenecks not on compute but on memory: the processor finishes a calculation and sits idle waiting for data. The hidden quantity is the fraction of the GPU's maximum memory bandwidth that the code actually uses. If this fraction is low, the GPU is starving for data and the code is slow.

Forge measures this by profiling the generated kernels and computing: actual bytes moved per second / peak bytes per second. Fused kernels move data once and reuse it within a tile; unfused kernels move the same data back and forth to main memory, wasting bandwidth. By fusing computation and communication into a single kernel, Forge drives this fraction close to the hardware limit.

Why it works

Why it works: decomposition enables automated optimization

The core insight is that all linear attention variants, despite superficial differences, share the same three-step structure: (1) compute on local chunks independently, (2) propagate state from one chunk to the next, (3) merge the results. This structure is hidden in the PyTorch code, but Forge extracts it via the three-phase abstraction. Once exposed, the compiler knows exactly where the synchronization points are and can optimize around them.

Here is why this fixes the speed problem. Hand-written code for each variant hides this structure, so each kernel is a one-off optimization. Forge infers the structure automatically, so it can apply the same set of optimizations (tiling, fusion, pipelining) to any variant without rewriting. The three phases also reveal the distributed communication pattern: chunks can be processed independently on different GPUs, and only the inter-chunk states need synchronization. Forge automatically inserts asynchronous communication to hide these stalls — the next chunk computation overlaps with the previous chunk's state transfer, so the GPU is never idle.

On a single GPU, tiling keeps data in fast cache and fusing eliminates memory round-trips, driving bandwidth usage high. On multiple GPUs, the three phases become stages in a pipeline: GPU-1 finishes intra-chunk math while GPU-2 is still propagating its inter-chunk state, so both are busy. The payoff is obvious: fast code without hand-tuning and scaling from one GPU to 128 GPUs with near-linear efficiency.

Math after the picture

The main operation: fused three-phase linear attention

First in words:

For each tile, compute local attention (chunk math), propagate the reduced state to the next tile, then mix in the propagated state to compute final outputs. All three steps are fused into one GPU kernel so memory is not written and reloaded.

Then the compact form:

O[tile] = (Q[tile] * K[tile]^T * V[tile]) + (state_in * V[tile]) * scale ; state_out = state_in + (K[tile]^T * V[tile]) * scale

Every symbol:

Q[tile]queries in the current chunk
K[tile]keys in the current chunk
V[tile]values in the current chunk
state_inreduced state carried forward from prior chunks
state_outreduced state passed to the next chunk
scalenormalization factor to keep numbers stable
Tiny worked example: attending across two chunks
Chunk 1 (tile size 4): Q=[1,2,3,4], K=[1,1,1,1], V=[10,20,30,40].
Local attention within chunk 1: K^T*V = [100] (sum of all values), output = Q*100 = [100,200,300,400].
State after chunk 1: state_out = [100] (sum to carry forward).
Chunk 2: Q=[5,6], K=[2,2], V=[50,60]. No prior state: state_in = 0.
Local attention within chunk 2: K^T*V = [220], output = Q*220 = [1100,1320].
Total output from chunk 2: [1100,1320] (unfused approach: recompute; fused approach: compute once, reuse state).
Key insight: state = [100] is reused, not recomputed. Save bandwidth and time.

Fusing keeps the reduced state in fast cache instead of writing it to main memory and reading it back, shrinking both latency and power.

What can go wrong

What can go wrong

Algorithm variants that do not fit the three-phase abstraction. Forge assumes the linear attention algorithm can be decomposed into independent intra-chunk computation, global state propagation, and output merging. Some exotic variants might not fit this pattern. In that case, Forge cannot optimize them without extension.
Incorrect state propagation on very long sequences. If the reduced state (the hidden representation passed between chunks) accumulates rounding errors over thousands of chunks, the attention approximation can drift. The paper does not deeply analyze numerical stability over extreme lengths.
Communication overhead dominates on weak GPUs or networks. The distributed version overlaps communication with computation to hide latency. On a slow network or with few GPU cores per rank, communication stalls might not be fully hidden, limiting scaling efficiency.
Done right. The three-phase abstraction is general enough to cover most practical linear attention variants (gated attention, multi-query attention, sliding window attention), and the measured results show that Forge scales to 128 GPUs with realistic speedups. The compiler automatically handles the abstraction, so users do not need to worry about these edge cases if their algorithm fits the pattern.
What a runnable demo should prove

What a runnable demo should prove

A demo should show: (1) write a linear attention algorithm in plain PyTorch (20 lines), (2) run Forge to generate the kernel, (3) run both the PyTorch and kernel versions on a single GPU and measure speedup. For the distributed version, show that the speedup scales with GPU count — e.g., on 8 GPUs, expect 6-7x speedup because communication between GPUs causes some idle time, but Forge pipelines (overlaps) computation with communication so most of that cost is hidden; on 64 GPUs, expect 40-50x speedup because the fixed communication overhead is amortized across more computation, and the pipeline hides most remaining stalls. The demo proves that the compiler output is correct (same numerical results) and fast (orders of magnitude speedup).

speedup = time(hand-written PyTorch) / time(Forge-generated kernel) ; distributed_efficiency = observed_speedup / ideal_speedup * 100%

The demo must show that Forge users write once and run fast everywhere — no hand-tuning, no per-variant optimization, no sacrifice of correctness for speed.
