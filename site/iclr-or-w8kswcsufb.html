Relational Feature Caching for Accelerating Diffusion Transformers

Speed up diffusion image generation by predicting how model internals will change, using what went in to guess what will come out.

Paper explainersAll themesEfficiency & Systems

Diffusion models (which generate images step-by-step from noise) use a transformer (a type of neural network that processes sequences) that is slow because it recomputes the same internal values over and over. Recent work tries to skip recomputation by guessing what the internals will be at future steps using only the past. This paper notices that guess is often wrong because the internal values jump around erratically. Instead, it predicts the jump size by looking at what goes into the module, because the input and output of a module are tightly linked.

Zero assumption version

Diffusion transformers recompute the same things over and over

Diffusion models work by running a transformer (a type of neural network) many times in a loop, each loop called a timestep. At each timestep, it processes the image and runs it through expensive modules like attention heads (which figure out which parts of an image matter for each region).

A naive solution is to just run all the modules every single time. But most timesteps are similar — the image noise is being gently sculpted, not flipping from cat to dog each step. So, the outputs of these expensive modules should also be similar.

When you look at cached output from an earlier timestep and use it again now, you save the expensive recomputation. The catch: if the output has changed since the cached step, using the stale output makes the image look glitchy or degraded. So the question is: how do you know when the cache is still good enough, and when do you need to recompute?

In one sentence. The paper guesses whether a cached output is still accurate by looking at the input instead of guessing from past outputs.

The algorithm as a flow

What it actually does

Look at the input

Before deciding to use the cache, examine the input features to the module.

Predict the output change

Use a learner that estimates how much the output will differ from the cached version.

Compare against a threshold

If the predicted change is small, use the cached output. If large, recompute.

Recompute only when risky

Run the full module only when the input signals a big divergence from cache.

Accumulate speedup

Over many timesteps, skipping recomputation when safe adds up to faster generation, because each skipped module run saves the time that run would have taken, and time savings multiply across all timesteps.

What the paper changes

What the paper changes

The paper changes how the cache scheduler decides whether to recompute: instead of guessing from historical trends in the outputs, it now guesses from the current input. This one shift in decision logic is what the paper changes.

The hidden quantity

The hidden quantity: prediction error

measured quantity  =  prediction error on the output

A prediction error is the gap between what you guessed the output would be and what it actually turned out to be. If you guess 50 and the true value is 47, your error is 3.

The paper estimates this error by looking at the input features. When the input looks unusual or different from when the cache was made, the method predicts the error will be large and decides to recompute. When the input looks stable, it predicts the error will be small and reuses the cache.

Why it works

Why input-output relationships are tighter than temporal trends

In a diffusion model, the transformation a module performs depends almost entirely on what is fed into it. The input and output are mechanically linked. If you know the input, you have a strong signal about what the output will be.

By contrast, naively predicting the future output from the past outputs only looks at a time series: was the output 42, then 45, then 48? Guess 51. But diffusion transformers do not follow smooth time series. The network can make sharp jumps when the denoising strategy shifts or the image regions being refined change. So temporal trend-following fails.

The paper learns a small estimator that takes the input and outputs a number: the predicted magnitude of change in the output. This estimator can be right much more often than a linear trend, because it learns the actual input-output correlation rather than assuming smooth time flow.

The decision rule

First in words:

predicted error on output equals a learned function of the input features; if that function outputs a number larger than a threshold, recompute; otherwise reuse cache

Then the compact form:

error_pred = f_theta(input_features); if error_pred > threshold then recompute else reuse_cache

Every symbol:

error_predpredicted size of the gap between cached and true output
f_thetaa small learned estimator (a little neural network) with weights theta
input_featuresthe features flowing into the module at this timestep
thresholda tunable boundary; higher means recompute more often
A tiny worked example
Timestep 5: input features are [0.2, 0.1, 0.3]. The estimator f_theta outputs 0.08 (predicted error).
Threshold is set to 0.15. Since 0.08 < 0.15, reuse the cached output.
Timestep 6: input features are [0.8, 0.9, 0.7]. The estimator outputs 0.42 (predicted error is large).
Since 0.42 > 0.15, recompute the module. The recomputation reveals the output changed a lot, vindicating the decision.

The estimator learns which input patterns signal big changes in the output; the threshold controls the trade-off between speed (cache more) and quality (recompute more).

What can go wrong

What can go wrong

The estimator is misaligned with true errors. If the learned estimator f_theta does not actually correlate with real prediction errors, it will make wrong cache decisions. The estimator must be trained on real data where the true output divergence is measured.
Threshold set too conservatively. If the threshold is set too high (always recompute), you lose all speedup. If too low (always cache), quality falls. Tuning is needed per model and task.
The input-output relationship is not learnable. In some models or at some layers, the input may not correlate with output changes well enough to be useful. The method has no built-in fallback for such cases.
Done right. Train the estimator on diverse data, set the threshold by testing on held-out examples, and verify on a validation set before deploying.
What a runnable demo should prove

What a runnable demo should prove

A demo should show that a diffusion transformer running with relational feature caching produces images with quality indistinguishable from full recomputation, but measurably faster, because the input-based error estimator correctly identifies when the cache is stale and recomputes in those cases. Start with a small DiT model (e.g., DiT-S), a standard dataset (e.g., ImageNet 256x256), and a stopping criterion (e.g., 50 timesteps). Cache some modules (e.g., attention heads). Train the relational estimator f_theta on a small validation split, then run generation on a test set.

speedup = full_time / cached_time; quality_drop = LPIPS_cached - LPIPS_full; show speedup > 1.5 and quality_drop < 0.02

The demo must show that aggressive caching (reuse often) with input-based error prediction beats aggressive temporal prediction, and that quality stays visually acceptable.
