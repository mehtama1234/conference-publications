Interactive Agents to Overcome Underspecificity in Software Engineering

Agents that ask clarifying questions when instructions are incomplete solve problems better than agents that guess.

Paper explainersAll themesAgents & Tool Use

AI agents are deployed to write code based on user instructions, but many instructions are incomplete—missing file locations, design decisions, or constraints. Today's agents either make silent guesses or fail silently. This paper evaluates whether agents can detect when information is missing and ask the user clarifying questions to fill the gaps.

Zero assumption version

Agents guess, and guessing fails

When a user tells an agent to write code, the instruction often leaves out important details. An expert human would ask: 'Which file should I modify?' or 'What should happen if the input is empty?' But the agent doesn't know to ask. Instead, it makes an assumption and plows forward, often in the wrong direction.

The real-world problem is worse: missing information doesn't arrive all at once—it accumulates. The agent might need to explore the codebase first to understand what's even possible, then realize midway through that it doesn't know what success looks like.

The failure mode. An agent that cannot ask for clarification will either guess incorrectly or waste steps trying solutions that can never work.

The algorithm as a flow

What it actually does

Step 1: Read the instruction

Agent receives an instruction that may omit key information.

Step 2: Detect if information is missing

Agent checks whether the instruction has enough detail to succeed.

Step 3: Ask targeted questions

Instead of guessing, agent asks the user for the missing details.

Step 4: Receive the answer

User provides the clarification; agent updates its understanding.

Step 5: Solve with complete information

With gaps filled, agent solves the task correctly.

What the paper changes

What changes: detection + dialogue

The paper evaluates three separate capabilities: whether the agent can detect that information is missing, whether it asks sensible clarifying questions, and whether it uses the answers to do better. This separation matters because it reveals exactly where each model fails. Some models never detect the gap at all. Others detect it but ask useless questions. Others ask good questions but then ignore the answers.

the object it moves  =  detection, questions, and interaction
The hidden quantity

The specification gap

measured quantity  =  Information completeness

The hidden quantity is how much of the specification the agent has understood. A complete specification tells an expert coder exactly what success looks like; an incomplete one leaves critical details out. The paper measures this by comparing the task description before and after interaction.

The paper estimates completeness using embeddings—think of embeddings as compressed fingerprints of text. It measures the difference between the fingerprint of the original instruction and the fingerprint of all the clarifications combined. A large difference means the agent learned something significant.

Why it works

Why asking beats guessing

An agent that guesses is working blind. It tries file A, and fails; tries B, and fails; tries C. Each failed guess teaches nothing because the agent doesn't know why it failed. It might be the wrong file, or the wrong strategy, or a missing constraint. With no signal, the agent is fumbling.

When an agent is trained or prompted to ask clarifying questions instead, it flips the burden. The user, who knows the full context, directly fills in the gap. No wasted steps. The agent learns which file to edit, what the output should look like, or what constraint it missed. Each answer is targeted, not random.

The paper shows this interaction is worth up to 74% more correct solutions. Why? Because interaction gives the agent real information rather than random exploration. A human-in-the-loop always knows more than a model guessing alone.

Math after the picture

Measuring the information gained

First in words:

distance between task embedding before and embedding of all clarifications after

Then the compact form:

info_gain = 1 - cos_similarity( embedding(instruction_before), embedding(all_questions_and_answers) )

Every symbol:

embedding(X)compressed fingerprint of text X—a list of numbers that captures its meaning
cos_similarityhow much two fingerprints overlap, a number between 0 and 1, where 1 means identical
info_gainhow much new information the agent received, measured as distance between the two fingerprints
instruction_beforethe original task description
all_questions_and_answersevery question asked and every user response, combined
A tiny worked example
Original instruction embedding: [0.1, 0.2, 0.15, 0.05, 0.3]
After questions and user answers embedding: [0.4, 0.5, 0.45, 0.6, 0.7]
Cosine similarity between them: 0.82 (fairly close but not identical)
Information gain: 1 - 0.82 = 0.18 (the agent learned 18% new information)
A larger gain (say 0.35) means the user answered very different questions than what was implied in the original instruction.

High information gain means the original instruction was vague and interaction was valuable; low gain means the instruction was already clear.

What can go wrong

What can go wrong

Agent doesn't recognize missing information. Some models (like Qwen 3 Coder in the paper) rigidly follow predetermined steps and ignore signals that information is missing. They barrel forward confidently into a wrong solution.
Agent asks useless questions. Instead of asking what it actually doesn't know, the agent might ask questions it could answer itself by exploring the codebase. This wastes the user's time and doesn't fill the real gap.
Agent doesn't integrate the answer. Sometimes the agent receives a clarification but fails to update its solution plan. It asked the question but then ignores the response—a form of mechanical compliance without understanding.
Done right. An agent trained on real examples of incomplete instructions, clarifying questions, and course corrections will learn to ask first, explore second, and only guess last.
What a runnable demo should prove

What a runnable demo should prove

A minimal demo takes a real software engineering task with deliberately hidden information (e.g., 'Add a feature to the codebase' without saying which file, what the feature does, or how to test it), runs the agent in two modes—one forbidden from asking questions, one encouraged to ask—and measures how many produce correct solutions.

interaction_benefit = (success_rate_with_interaction - success_rate_silent) / success_rate_silent

The metric proves interaction is foundational, not optional: without it, the agent fails because it is working blind; with it, the agent succeeds because it has real information.
