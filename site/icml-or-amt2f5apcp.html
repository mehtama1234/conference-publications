DocOS: Towards Proactive Document-Guided Actions in GUI Agents

This paper studies GUI agents that first search for task instructions in online documents, then turn those instructions into exact screen actions.

Paper explainersAll themesAgents & Tool Use

A GUI agent often fails on a rare task because the needed steps were never stored in its training weights. This paper studies a different loop: search for the right document, read the steps, then click and type by grounding each instruction into the current page state.

Zero assumption version

GUI agents break when the needed procedure is outside their stored knowledge

Many GUI agents are trained to map a screen and an instruction directly to the next action. That works on common tasks, but it breaks on long-tail tasks because the exact procedure lives in product documentation pages, setup guides, or API docs rather than in the model's stored knowledge.

A direct action loop also wastes steps because the agent has to explore by trial and error. The agent clicks around, opens the wrong menu, and then loses state. The main problem is not only acting. It is first finding the right external procedure, then following it exactly.

The idea in one sentence. Treat document search as part of the task, because many GUI jobs cannot be solved from stored knowledge alone.

The algorithm as a flow

What it actually does

State the task

Give the agent a goal in an interactive browser environment.

Search for a document

Let the agent open search pages or documentation centers and look for a document that describes the needed procedure, because the needed steps may be absent from the prompt and from stored knowledge.

Read the procedure

Extract the ordered steps from the retrieved page.

Ground each step

Map the written step to the current visible control, field, or menu item on the screen.

Execute and check

Carry out the step, inspect the new page state, and continue until the task is complete.

What the paper changes

What the paper changes

The paper changes the unit of competence from 'act from memory' to 'find, read, and apply a procedure'. It also adds a benchmark that separates failures in document search from failures in action grounding.

the object it moves  =  the agent's decision loop
The hidden quantity

The hidden quantity: Procedure grounding accuracy

measured quantity  =  how often the agent maps a written step to the right screen action

Procedure grounding accuracy measures whether the agent turns a retrieved instruction into the correct on-screen action. A document may be perfectly relevant, yet the agent can still fail if it clicks the wrong tab or types into the wrong field.

The paper exposes this hidden quantity by designing tasks that require both retrieval and execution. That split matters because a low final score can come from bad search, bad reading, or bad grounding, and those failures need different fixes.

Why it works

Why document-guided acting helps

The method helps on long-tail tasks because the needed procedure can live in external documentation even when it was absent from training. By letting the agent search first, the system can import the missing steps at run time.

The second half is just as important. Retrieved text only helps if the agent grounds it into exact page actions. That is why the benchmark emphasizes dual bottlenecks: weak search prevents the right procedure from entering the loop, while weak grounding turns a good procedure into wrong clicks.

Math after the picture

The core equation

First in words:

Think of total task success as depending on both retrieval success and grounding success. If either side is weak, the final completion rate stays low.

Then the compact form:

task_success = retrieval_success * grounding_success

Every symbol:

task_successhow often the full browser task is completed
retrieval_successhow often the agent finds a document with the needed procedure
grounding_successhow often the agent turns the written step into the right screen action
A tiny worked example
Suppose the agent finds the right document in 8 out of 10 tasks.
Suppose that, once it has the right document, it grounds the steps correctly in 6 out of 10 cases.
Then the rough full-task success rate is 0.8 times 0.6, which is 0.48.
That means the agent finishes about 48 out of 100 tasks.
The example shows why improving only one side is not enough, because the weak side still limits the end result.

This page uses a product form only to show the bottleneck structure. The main lesson is that both search and grounding must work together.

What can go wrong

What can go wrong

The search query is too vague. If the agent asks for a broad documentation page instead of the exact setup procedure, it retrieves a page that contains related words but not the needed steps, so the later action sequence starts from the wrong instructions.
The document is right but the grounding is wrong. A step such as 'open settings' fails if several controls have similar labels and the agent clicks the wrong one.
The page state changed after an earlier action. A later step can fail when the screen no longer matches the document because a modal, redirect, or permission page changed the layout.
Done right. The system works best when retrieval is focused, the agent checks visible state after each action, and each written step is grounded to a specific control rather than to a loose text match.
What a runnable demo should prove

What a runnable demo should prove

Build a small browser task set where each task needs an outside documentation page, such as connecting an integration, changing a billing setting, or turning on a product feature, because those tasks cannot be completed reliably from the prompt alone. Give the agent a search tool, a browser, and access to the documentation center so that it can retrieve the missing procedure before acting. Compare two versions: one that acts directly from the task prompt and one that can search for documents first. The demo should log document choice, extracted steps, chosen controls, and final task outcome so that each failure can be traced to retrieval or grounding.

The demo proves the paper's point if document-guided acting wins on tasks whose procedure is absent from the prompt, because the search step brings in the missing instructions and the grounding step turns them into concrete clicks.

completion_lift = completion_rate(document_guided) - completion_rate(direct_action)

A convincing result is not only a higher completion rate. It also shows where the gain comes from by separating document search from action grounding.
