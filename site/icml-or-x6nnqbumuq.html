Towards Professional-Grade Financial Agents: Benchmarking, Tooling, and Structured Reasoning

ProFinAgent tackles finance work with a large task benchmark, a finance-specific tool library, and a directed acyclic plan, so that tool calls can run in the right order and in parallel when possible.

Paper explainersAll themesAgents & Tool Use

Finance tasks often require several linked calculations, document lookups, and rule checks. A plain step-by-step agent can fail because it chooses tools in the wrong order, forgets past similar cases, or waits for one tool call to finish before starting independent work. ProFinR and ProFinAgent attack the problem at three levels. The benchmark defines what serious financial reasoning looks like. The Financial Tool Universe supplies domain-specific tools. The agent then plans work as a directed acyclic graph and consults a case memory of past examples. This structure improves both answer quality and speed because independent subproblems can run in parallel and past cases can guide choices early.

Why finance agents need more structure

A professional finance task is rarely one isolated question. It may involve pulling market data, computing ratios, reading policy rules, comparing scenarios, and merging several intermediate results into one decision.

A loosely organized agent can break in two ways. It may reason with the wrong tool order because one calculation depends on another. It may also waste time by handling every subtask strictly one after another even when some parts are independent. The paper asks how to benchmark this setting and how to build an agent that respects both dependency structure and past experience.

The paper's move in one sentence. Define a professional finance benchmark, supply a finance-specific tool universe, and plan tool usage as a directed acyclic graph with case memory, so that complex tasks can be solved with the right dependencies and faster execution.

The algorithm as a flow

What it actually does

Step 1: Benchmark the task space

Use ProFinR so that the system is evaluated on realistic expert-designed finance problems.

Step 2: Provide domain-specific tools

Expose the 53 tools across 13 categories because finance tasks need operations beyond generic text generation.

Step 3: Retrieve similar earlier cases

Consult case memory so that earlier successful decompositions can guide the current plan.

Step 4: Build a directed acyclic plan

Arrange subtasks by dependency so that prerequisites are respected and independent work can run together.

Step 5: Execute, merge, and answer

Run the tool graph and combine the outputs so that the final decision uses all required intermediate results.

The hidden quantity

The hidden quantity: dependency fidelity

measured quantity  =  how well the plan matches the true prerequisite structure of the financial task

The key quantity is dependency fidelity. A financial answer is often wrong because one branch used inputs that had not been established yet or because two independent branches were handled as if one depended on the other.

ProFinAgent improves dependency fidelity with the directed acyclic plan and case memory. That helps accuracy because each tool call gets the information it actually needs, and it helps speed because independent branches can run together.

Why it works

Why it works

The benchmark matters because professional finance reasoning is broader than a few isolated examples. A benchmark with many expert-designed problems forces the system to handle varied workflows rather than one narrow pattern.

The finance tool universe matters because domain tasks depend on calculations, lookups, and rules that a generic agent may not execute precisely on its own. Better tools improve the raw ingredients of the answer by producing more accurate intermediate results.

The directed acyclic plan is the central design choice because it captures both ordering and parallel opportunity. Case memory helps by supplying useful decompositions from similar tasks, so the planner starts from a stronger structure.

A compact planning objective

First in words:

Choose a dependency-respecting tool plan that maximizes answer quality while minimizing unnecessary waiting.

Then the compact form:

J = answer_quality(plan) - alpha * latency(plan) - beta * dependency_errors(plan)

Every symbol:

Jthe planning objective
answer_quality(plan)quality of the final finance answer produced by the tool plan
latency(plan)time spent executing the plan
dependency_errors(plan)mistakes where a tool call runs without the inputs it truly needs or in the wrong order
alphaweight on execution time
betaweight on dependency mistakes
A tiny worked example
A task asks for a risk assessment that depends on current prices, company filings, and a ratio calculation.
Fetching prices and filings can happen together because they are independent branches.
The ratio calculation must wait because it needs the fetched numbers first.
A sequential agent waits too long and may mix the order, while the graph planner starts both fetches early and merges them only after both finish.
That improves both answer quality and speed because the plan respects the true dependency structure.

The objective summarizes the paper's main idea: good finance reasoning needs the right tools in the right order, because order errors damage both correctness and efficiency.

What can go wrong

What can go wrong

The dependency graph may be wrong. If the planner misses a prerequisite edge, a later tool can run on incomplete data because the true task order was not captured.
Case memory may pull a misleading example. A weak earlier case can bias the plan toward the wrong decomposition because the current task only looks similar on the surface.
The tool universe may still miss key operations. A planner cannot fix a missing capability because some finance tasks need domain operations that generic tools do not provide.
Done right. The approach works when the graph matches real dependencies and the retrieved case is genuinely relevant, because then parallel branches and ordered merges both help.
