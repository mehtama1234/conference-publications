ROSETTA: Code-Based Reward from Language Preference

Turn spoken or written human preferences into executable code that scores whether a robot has done what you wanted.

Paper explainersAll themesRobotics & Control

When you tell a robot what you want it to do, the instruction is usually vague: "organize the table nicely" or "pick the red mug carefully." ROSETTA takes that plain-language instruction, uses a foundation model to figure out exactly what it means, turns that meaning into executable code, and runs that code as the robot acts — so the robot can learn from real feedback, not from a pre-built reward model trained on a thousand generic tasks.

The ambiguity problem

Most robots today learn from reward signals that a person has to design by hand: point at the goal location, set the target orientation, count penalties for bumping things. These hand-crafted rewards take weeks to tune and only work for the exact task they were built for.

A more natural way is to let people describe what they want in plain language — 'stack the blocks in height order' or 'grasp the bottle by the handle, not the label.' But human language is messy: different people phrase the same goal differently, one instruction might mean multiple things depending on context, and what counts as 'done' is ambiguous. Naive approaches either ignore the nuance or require months of offline training to build a general reward model. The paper faces this head-on: how do you turn a single, unconstrained sentence into a reward that a robot can learn from, right now, without extensive pre-training?

The move. Ground the language in real-world visuals, turn the meaning into code, and run that code live as the robot acts.

The algorithm as a flow

What it actually does

Hear the preference

Person describes a task in natural language, unrestricted and casual.

Look at the world

Foundation model (vision + language) observes the robot, the objects, and the current state.

Disambiguate the intent

Model queries itself with both the language and visual observations to extract what concretely needs to happen.

Compose executable code

Model generates Python code that, given the robot state and camera images, outputs a numeric score.

Learn from live feedback

Robot acts; code scores each attempt; reinforcement learning nudges the policy to maximize that score.

What the paper changes

What the paper changes

ROSETTA changes what provides the reward signal during learning. Instead of a static, pre-trained reward model (always the same network, trained months ago on generic data), ROSETTA generates task-specific Python code on the fly. That code directly checks properties of the world — object positions, gripper state, camera observations — against the grounded interpretation of what the human asked for.

The hidden quantity

The grounding signal

measured quantity  =  alignment between language and visual observation

The hidden quantity is the degree to which the human's language preference has been correctly mapped onto the actual visual scene. It is not a number the paper measures directly, but rather a property that emerges when the foundation model runs — its internal representations of language and vision are aligned enough to extract the right constraints.

ROSETTA uses this alignment implicitly: when the vision and language encoders of the foundation model agree on what objects exist and which relationships matter, the generated code does what it is supposed to do. If they disagree (e.g., the human said 'red block' but the camera sees a green cylinder), the code generation will either fail gracefully or produce a code snippet that checks for the wrong thing. The paper tests this by measuring how often the generated code, when run on the robot's real camera feed, actually captures the human's intent.

Why it works

Why grounding + code generation works

Grounding language to vision solves the ambiguity problem because a picture is concrete. When you say 'stack them high,' the model can look at the camera feed, see three objects, measure their positions, and infer exactly which spatial relationship you meant — taller stack, stable base, no tipples. The foundation model has already been trained on huge amounts of vision-language data, so it is good at this. Generating Python code makes that meaning executable: instead of hoping a fixed reward model will generalize, you generate fresh code that can check the exact properties that matter for this task.

Why this works better than pre-trained reward models: a generic reward model is trained once on a diverse set of tasks, so it must learn abstract features that work across all of them — but no single feature generalizes perfectly. A code-generated reward is written from scratch for this human's preference, so it can check the exact relationships that matter. You trade a little generality (the code might be brittle to minor visual changes) for a lot of specificity and adaptability (it is perfect for what the human actually asked).

The reward as executable code

Then the compact form:

R_t = CodeGen(language_pref, observations_t)

Every symbol:

A tiny worked example
Human says: 'stack blocks in height order, no wobbles.'
CodeGen produces: reward = 0; if blocks_sorted_by_height(): reward += 10; if stack_stable(): reward += 5; return reward
At t=0 (blocks scattered): observations show random positions, code returns 0.
At t=100 (blocks stacked correctly): code returns 15.
At t=50 (blocks stacked but shaky): code returns 10 (height good, stability bad).
RL agent learns to reach the 15-point state and stay there.

The reward is not a neural network, it is a fresh function with straightforward checks, so the robot learns exactly what the human asked for.

What can go wrong

What can go wrong

Misgrounding: language-vision mismatch. If the human says 'the red cup' but the camera sees a pink bowl, the foundation model might guess wrong. The generated code will check for the wrong object, and the robot will learn the wrong behavior. This is most likely when the scene is cluttered, lighting is poor, or the human uses an indirect phrase like 'grab my morning drink' when they mean the cup on the table.
Code generation bugs. The foundation model might generate code with a subtle logical error (e.g., checking for one property twice instead of two). The robot will learn to optimize for the buggy code, not the human's actual intent.
Unintended optimization. If the generated code only checks 'cup is lifted,' the robot will lift the cup but not care if it spills. The code was correct, but incomplete. ROSETTA mitigates this by including multi-stage reward composition (checking multiple constraints), but it is not foolproof.
Done right. If the human iteratively clarifies their preference ('no, I meant gently, don't shake it'), ROSETTA re-generates code. The online adaptation loop lets humans correct misunderstandings in real time.
What a runnable demo should prove

What a runnable demo should prove

A minimal working demo would show: (1) a human says a preference for a simple pick-and-place task, (2) ROSETTA grounds it and generates code, (3) code runs while the robot learns, (4) the success rate climbs, and (5) when the human changes the preference mid-learning ('now be gentle'), success dips briefly but then climbs again as the agent re-adapts. The demo should show a few constraints with visibly different scores across attempts.

success_rate = (number of episodes where final reward exceeded threshold) / (total episodes); human_satisfaction = (human approves outcome) / (total outcomes)

The non-negotiable outcome: the code-generated reward is stable enough for reinforcement learning to converge, and the robot's learned behavior matches what the human actually described, not what a pre-trained model guessed.
