Language Agents for Hypothesis-driven Clinical Decision Making

Two language agents work together to diagnose patients by testing one hypothesis at a time, learning through real-world feedback which tests matter most.

Paper explainersAll themesAI for Science

Doctors diagnose by starting with a guess, then asking for tests that narrow it down. This paper teaches language models to do the same thing: one agent proposes the likely disease and how sure it is, another agent picks the next best test to request. The system learns which tests actually help by trying many combinations and rewarding moves that reach correct diagnoses quickly.

Zero assumption version

Diagnosis needs back-and-forth, but language models do not naturally do it

A real doctor sees a patient, hears some symptoms, and thinks of several possible diseases. Then the doctor says, 'Let us do a blood test and an ultrasound.' New results come back. The doctor revises the guess and asks for more tests. This cycle repeats until the doctor is confident in a diagnosis. It is messy, interactive, and driven by which diseases are still plausible given the clues so far.

Large language models today either assume the unrealistic case where all information arrives at once (like the patient walked in with every test result already done), or they just run the model as-is without any task-specific training. Neither matches how real diagnosis works. A beginner might ask a model, 'What disease does this patient have?' and get an answer based on everything known. But the model does not know which tests to request next, how confident its guess is, or whether it should wait for more evidence before committing to a diagnosis.

The method in one sentence. Train two language agents to work as a team: one keeps a running diagnosis hypothesis and its confidence level; the other decides which test to request next, learning by trial-and-error which test sequences lead to correct, efficient diagnoses.

The algorithm as a flow

What it actually does

1. Hypothesis generation

Language model reads patient symptoms and medical history, outputs a ranked list of disease possibilities and a confidence score for the top guess, based on what it learned from many past patient cases during training.

2. Decision agent evaluates

Second language model looks at the hypothesis and the patient data so far, then decides: request another test, or commit to a diagnosis?

3. Test simulation and feedback

The chosen test result is added to the patient data. The agents run again with the new information.

4. Reinforcement learning rewards short, correct paths

The decision agent learns through trial-and-error: sequences that reach the correct diagnosis quickly get a reward; wasteful ones get a penalty.

5. Cyclic training adjusts each part

Training alternates between teaching better hypothesis guessing, better confidence estimates, and better test selection, because cycling lets each piece stabilize before the next part trains against it, avoiding moving-target problems that destabilize simultaneous training.

What the paper changes

What the paper changes

The paper trains language agents to sequentially request tests during diagnosis, rather than trying to answer in one shot. The key change is teaching the model when to ask for more information instead of guessing blindly from day one.

The hidden quantity

The hidden quantity: which tests matter most

measured quantity  =  Test informativeness

In diagnosis, some tests are worth their cost and time; others are not. A blood test might narrow down three possible diseases very clearly. A rare scan might only confirm a single disease that your hypothesis agent already ruled out. The paper does not explicitly name a 'feature importance' or 'relevance score,' but the decision agent must implicitly learn which tests matter—which ones move the hypothesis most when results come back.

The paper learns this through reinforcement learning: the decision agent tries many test sequences in simulation, and sequences that reach correct diagnoses with fewer, cheaper tests are rewarded. This works because the reward directly encourages the agent to select tests that actually separate competing disease hypotheses, not just order tests at random. Over many episodes, the agent learns which tests typically provide the most useful signal given a particular set of plausible diseases.

Why it works

Why it works: the teaching cycle

The reason this works is that the paper splits the problem into pieces, trains each piece separately, then cycles. Start by teaching the hypothesis agent to make good guesses from partial information (supervised learning on examples of correct diagnoses). That agent learns the disease patterns. Next, teach the same agent to say how confident it is in its guess (a separate supervised loss that trains confidence calibration). Then freeze that agent and teach the decision agent via trial-and-error (reinforcement learning) which tests lead to correct diagnoses most efficiently. Finally, cycle back and refine the hypothesis agent again, knowing the decision agent has learned something new about which situations it will face.

Why is cycling better than training all three things at once? Simultaneous training creates a moving target: the decision agent learns to exploit a hypothesis agent that is also changing, so it never settles on a stable strategy. Cycling lets each piece stabilize before the next piece trains against it. The hypothesis agent learns to make good guesses; the decision agent learns which tests best expose errors in those guesses; the hypothesis agent then learns from those harder cases.

Math after the picture

The training objective for efficient testing

First in words:

reward equals correctness of diagnosis minus cost of tests, so training pushes the agent to diagnose accurately while requesting as few tests as possible

Then the compact form:

reward = (1 if diagnosis_correct else 0) - lambda * number_of_tests

Every symbol:

diagnosis_correct1 if the predicted disease matches ground truth, else 0
number_of_testscount of diagnostic tests requested before committing to diagnosis
lambdathe trade-off weight; higher lambda penalizes extra tests more heavily
A tiny worked example
Scenario A: Agent orders 3 tests, reaches correct diagnosis. Reward = 1 - 2.5 * 3 = 1 - 7.5 = -6.5.
Scenario B: Agent orders 5 tests, reaches correct diagnosis. Reward = 1 - 2.5 * 5 = 1 - 12.5 = -11.5.
Scenario C: Agent orders 2 tests, reaches correct diagnosis. Reward = 1 - 2.5 * 2 = 1 - 5 = -4.
Scenario C has the highest reward, so training pushes the agent toward it. Both correctness and efficiency matter, but when both succeed, fewer tests win.

The agent learns to request tests that most sharply separate the leading disease candidates, because unnecessary tests drag the reward down without improving accuracy.

What can go wrong

What can go wrong

Overfitting to the training dataset. If the agent trains only on common abdominal diseases, it may fail on rare conditions or when disease prevalence differs from the training set. The test selections the agent learned reflect what worked in the training data and may not generalize to new populations.
Circular reasoning in hypothesis updates. If confidence calibration fails, the hypothesis agent might report 95 percent confidence in a wrong guess, and the decision agent may stop requesting tests. Cascading errors are hard to recover from once commitment is made.
Reward hacking. The decision agent might learn to exploit the reward formula itself: ordering only the cheapest tests to minimize the penalty, even if they do not genuinely help diagnosis. This happens because the agent chases the formula, not the underlying goal, so the weight parameter (lambda) must be tuned carefully to balance accuracy and cost—if the cost penalty is too high, the agent orders no tests at all and loses accuracy.
Done right. Cycling training, honest confidence calibration, and a reward that genuinely trades off accuracy and efficiency keep the agent learning a strategy that works in practice, not just on paper.
What a runnable demo should prove

What a runnable demo should prove

Build a small simulator: a set of synthetic patient cases with ground-truth diseases (e.g., 50 patients, 4 possible abdominal diseases each). Implement the two-agent system: a hypothesis agent that reads symptoms, outputs a ranked disease list and a confidence score; a decision agent that decides whether to order a test or commit. For each patient, run the agents in a loop: hypothesis agent guesses, decision agent chooses next action, test result comes back, patient data updates, then repeat until diagnosis or max tests reached. Train the decision agent via reinforcement learning on half the patients, then test on the other half.

diagnostic_accuracy = (number_of_correct_diagnoses) / (total_patients); efficiency = (average_tests_per_correct_diagnosis); confidence_calibration = average(reported_confidence_when_correct) - average(reported_confidence_when_wrong)

The demo must show that the trained agent diagnoses more accurately than a baseline, while asking roughly the same or fewer tests, and its confidence scores align with actual correctness (high confidence when right, low when wrong).
