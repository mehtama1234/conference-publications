AOEB: Benchmarking Agent-Oriented Multimodal Embeddings

Test retrieval representations for agents on the tasks agents actually face, across code, tools, reasoning, memory, text, and images, so that evaluation matches practical agent use rather than generic search alone.

Paper explainersAll themesAgents & Tool Use

Many agent systems depend on retrieval, yet the representations used for retrieval are still mostly judged on broad generic benchmarks. That creates a mismatch: a representation can look good on average search tasks and still be weak when an agent needs to recall a tool description, find a past memory, retrieve code, or connect text with an image. AOEB builds an agent-oriented benchmark to measure those practical differences directly, because agent retrieval is shaped by the tasks the agent must complete rather than by search quality in the abstract.

Why generic retrieval tests miss what agents need

An agent does not retrieve documents for their own sake. It retrieves the next piece of information needed to act. That piece may be a code fragment, a tool description, an earlier memory, a reasoning hint, or a visual item tied to the current question. Generic retrieval tests often blur those cases together.

Because of that blur, a representation can rank well overall and still fail badly on one agent-critical use case. If an agent cannot retrieve the right tool usage note or the right past state, the whole task can fail. A benchmark for agent retrieval should therefore separate those capabilities instead of hiding them inside one average score.

The paper's move in one sentence. Build a benchmark that splits agent retrieval into several practical task types and includes both text and image inputs so that retrieval representations are tested under agent-like workloads.

What it actually does

Define agent-centered retrieval capabilities

Separate the major retrieval jobs agents rely on, such as code lookup, tool lookup, memory recall, and reasoning support.

Build task sets for each capability

Create evaluation tasks that reflect those retrieval jobs instead of relying on one undifferentiated search benchmark.

Include both text and visual data

Test each capability with multiple input forms because many agents work across screenshots, diagrams, and text instructions together.

Evaluate representative retrieval models

Measure different representations on the same task families so that their strengths and weaknesses become visible.

Report a capability profile, not one score alone

Summarize how each representation behaves across tasks because the best choice depends on the agent workload.

Why it works

Why this works: evaluate retrieval the way agents use it

A representation used by an agent is only as helpful as its weakest important retrieval skill. If it cannot recover the right past memory or the right tool note, overall task performance can collapse even when its generic search score is high. Breaking evaluation into agent-relevant retrieval jobs reveals that mismatch.

The text-plus-visual design matters because many real agents work across screenshots, interfaces, diagrams, and written instructions. A text-only benchmark would miss those cases. AOEB therefore gives a more practical picture because it asks whether the retrieval representation can support the mixed workloads that modern agents actually face.

Math after the picture

Measure workload fit, not only average retrieval quality

First in words:

A compact summary is to value one retrieval representation by averaging its performance across the agent retrieval capabilities that matter for the intended workload.

Then the compact form:

agent_retrieval_score(model) = sum_i weight_i * capability_i(model)

Every symbol:

agent_retrieval_score(model)overall score of one retrieval representation for agent use
capability_i(model)performance of the representation on one retrieval capability such as code, tools, memory, reasoning, or text-image matching
weight_iimportance of that capability for the intended agent workload
sum_iadd the weighted capabilities across the benchmark categories
A tiny worked example
Model A is strong on code lookup and weak on memory recall.
Model B is the opposite: weaker on code lookup but stronger on memory recall and tool lookup.
If the target agent is a software assistant, the weights may favor code lookup.
If the target agent is a personal assistant, the weights may favor memory and tool lookup.
The benchmark is useful because it shows which model fits which workload.

The paper reports detailed benchmark results rather than one hand-designed formula, but this equation captures the central point that agent retrieval quality depends on workload composition.

What can go wrong

What can go wrong

The benchmark can still miss future agent workloads. Agent behavior changes quickly, so a task set that is practical today may become incomplete later because new tools and new interaction styles appear.
Capability boundaries can overlap. A task may need memory recall and reasoning support at once, so neat category splits can simplify reality more than developers would like.
A better benchmark does not by itself fix the model. The benchmark reveals weak spots, but a weak representation still needs new training or design work because measurement alone does not improve retrieval.
Done right. The benchmark matters because it measures retrieval in the form agents actually consume it: as task-specific support for action.
What a runnable demo should prove

What a runnable demo should prove

Build a small benchmark with four retrieval tracks: code lookup, tool documentation lookup, memory recall from past conversation state, and text-image matching from screenshots. Evaluate several retrieval models on the same tracks and report both the overall score and the per-track profile.

The demo should include at least one case where the best overall model is not the best model for a specific agent workload. That example matters because the paper's claim is that practical model choice changes when the retrieval job is broken down by agent need.

profile_gap = best_overall_score - best_task_specific_score ; workload_fit = sum_i weight_i * capability_i

A good agent retrieval benchmark should tell you not only who wins overall, but also who is the right tool for the job.
