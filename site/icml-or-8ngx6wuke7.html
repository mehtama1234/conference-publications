AOrchestra: Automating Sub-Agent Creation for Agentic Orchestration

Represent each sub-agent as a recipe of model, task, tools, and context, then let one orchestrator create the right specialist on demand instead of relying on fixed roles.

Paper explainersAll themesAgents & Tool Use

Multi-agent systems often use either generic worker threads with weak specialization or hand-built expert roles that must be designed in advance. Both choices are limiting. Generic workers lack focused capability, while fixed roles cost human setup effort and do not adapt well when the task changes. AOrchestra introduces a common recipe for describing an agent and lets a central orchestrator instantiate specialists only when they are needed. The system can therefore choose the right model, tools, and context for each subtask while keeping the overall framework flexible.

Zero assumption version

Why fixed multi-agent designs waste capability

Suppose you want an agent system to solve software tasks, web research tasks, and planning tasks. One option is to create a small set of static roles up front: a planner, a coder, a reviewer, and a researcher. That helps a little, but the roles are locked in because the system can only use the workers that were designed ahead of time. If the task needs a file-migration specialist or a browser-debugging specialist, the system cannot create that shape unless a human already designed it.

The other option is to spawn generic worker threads with the same model and the same broad instructions. That is flexible but shallow. The workers may differ only by local context, so they often lack the focused tools, filtered context, and model choice that a true specialist would need. The result is wasted cost and weak adaptability.

The paper's move. Describe any agent with one compositional recipe, then let the orchestrator assemble a task-specific specialist by choosing the right model, task, tools, and context at the moment it is needed.

The algorithm as a flow

What it actually does

Analyze the current subtask

The orchestrator determines what capability the next step really needs.

Assemble an agent recipe

Choose a model, a precise subtask description, a tool set, and the minimal supporting context.

Spawn the specialist

Instantiate a sub-agent from that recipe for the current step only.

Delegate execution

Let the specialist run its subtask with the selected tools and context.

Collect results and continue

The orchestrator absorbs the result, updates the global plan, and may create another specialist if the next step differs.

What the paper changes

What the paper changes

The paper changes what a sub-agent is. Instead of treating workers as fixed hand-crafted roles or as generic copies of the same assistant, it models each worker as a recipe that can be concretized differently for each subtask.

the object it moves  =  Sub-agent definition and creation policy
The hidden quantity

The hidden quantity: capability fit

measured quantity  =  How well one agent recipe matches one subtask

For any subtask, many possible sub-agents could be created. Some will be overpowered and expensive. Some will lack the right tools. Some will have too much context and become distracted. The hidden quantity is capability fit: how well the chosen recipe matches the actual demands of that subtask.

The orchestrator estimates capability fit by choosing the four recipe parts jointly. A strong fit means the chosen model has enough ability, the task framing is specific, the tools are relevant, and the context is trimmed to what matters. Performance improves because each worker is created with a sharper match to the subtask rather than with a one-size-fits-all design.

Why it works

Why on-demand sub-agent creation helps

Complex tasks are not uniform. A web debugging step needs browser tools and recent page state. A code patch step needs repository files and edit authority. A planning step may need almost no tools but a broader summary of earlier results. If every worker is fixed ahead of time, the system keeps carrying the wrong baggage into many subtasks.

The recipe abstraction helps because it makes specialization explicit. A sub-agent is defined by four concrete parts: which model it uses, what precise task it is told to solve, which tools it can access, and which context it receives. That means the orchestrator can build a narrow and efficient worker for each subtask. Performance improves because each worker sees less irrelevant context, uses only the needed tools, and can be matched to a cheaper or stronger model depending on task difficulty.

This also reduces human engineering effort. A developer no longer needs to pre-author every specialist role. The orchestrator can derive new specialists from the common recipe language. That matters on open-ended benchmarks because the system can adapt to new subtask shapes without redesigning the agent roster by hand.

Math after the picture

Choosing the best agent recipe

First in words:

For each subtask, score a candidate recipe by combining expected task success and expected cost. Choose the recipe with the best trade-off.

Then the compact form:

recipe_score(r, s) = success(r, s) - lambda * cost(r, s)

Every symbol:

recipe_score(r, s)quality of recipe r for subtask s
success(r, s)expected chance that recipe r completes subtask s correctly
cost(r, s)expected resource use of recipe r on subtask s
lambdaweight controlling how strongly the system penalizes cost
A tiny worked example
Subtask: patch one bug and run tests.
Recipe A uses a medium model, edit tools, test tools, and a focused code context. success=0.8, cost=0.3.
Recipe B uses a strong model with many tools and a wide context. success=0.85, cost=0.8.
With lambda = 0.5, score(A)=0.8 - 0.5*0.3 = 0.65.
score(B)=0.85 - 0.5*0.8 = 0.45, so A is chosen because the extra cost of B is not justified by its small gain.

The paper frames the trade-off more broadly, but this captures the stated goal of approaching a performance-cost frontier through dynamic recipe selection.

What can go wrong

What can go wrong

Subtask analysis is wrong. If the orchestrator misunderstands the next step, it may spawn the wrong specialist because the recipe was built on a false task description.
Context curation is too narrow. If the spawned worker receives too little history, it may miss a constraint that matters because the recipe dropped information needed for correct execution.
Too many specialists create coordination overhead. If the system spawns new workers for trivial subtasks, coordination cost can outweigh specialization gains because orchestration itself is now doing too much work.
Done right. The method works when the orchestrator creates specialists only when the subtask truly changes and when each recipe is tightly matched to the capability, tools, and context that step requires.
What a runnable demo should prove

What a runnable demo should prove

Build a benchmark with mixed subtasks such as web lookup, code editing, file inspection, and plan synthesis. Compare three systems: one fixed-role multi-agent setup, one pool of generic workers, and one dynamic recipe-based orchestrator. Track success on the benchmark, total cost, and the number of times a newly created specialist directly resolves a subtask that the fixed systems mishandle.

The demo should show that on-demand specialist creation helps because it gives each subtask a better-matched worker without requiring humans to predefine every role.
