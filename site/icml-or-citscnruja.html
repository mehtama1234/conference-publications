AutoTool: Dynamic Tool Selection and Integration for Agentic Reasoning

Train an agent to choose useful tools step by step instead of assuming one fixed tool set for every problem.

Paper explainersAll themesAgents & Tool Use

Many tool-using agents are trained under one fixed menu of tools. That works until the tool set changes, a new tool appears, or an old tool stops being useful. AutoTool treats tool choice as part of the task itself. It trains the agent to rank candidate tools at each step and to revise that ranking during a long solution because different stages of the same problem need different outside actions.

Zero assumption version

Why fixed tool menus break down

A tool-using agent usually has two jobs. It must reason about the user question, and it must decide when an outside tool would add needed information or carry out a subtask. Many current systems train only the first job well. They assume the second job is simple because the available tools are fixed during training and testing.

That assumption fails in real use because tool sets change over time. New search tools, code tools, and visual tools arrive, and older ones may disappear or perform badly on some requests. If the agent learned only one frozen mapping from problem type to tool name, it cannot adapt when the menu changes.

The paper's move in one sentence. Teach the agent to rank candidate tools during each reasoning step so that tool choice can change with the question and with the currently available tool set.

The algorithm as a flow

What it actually does

Stabilize long solution traces

First train the agent to produce coherent multi-step solutions so that tool decisions are made inside a stable reasoning process.

List candidate tools at each step

Present the currently available tools so that the agent chooses from the real menu instead of from a fixed memorized list.

Rank the candidates

Order the tools by expected usefulness for the current step because only some tools help with the next missing piece.

Call the best tool and update the trace

Read the tool result and continue reasoning so that later choices can react to the new evidence.

Train on many tasks and tool sets

Repeat across diverse problems so that the agent learns a general tool-choice habit rather than one narrow rule.

The hidden quantity

The hidden quantity

measured quantity  =  Expected value of each tool at the current step

The key hidden quantity is how useful each available tool would be for the next step of the current solution. You cannot read that value directly from the question alone because usefulness changes as the partial solution changes.

AutoTool tries to estimate that step-specific value from the current reasoning state, the task type, and the available tools. That estimate matters because the best tool early in a solution may be a poor choice later after the agent has already gathered new evidence.

Why it works

Why this works: treat tool choice as a repeated ranking problem

A fixed tool policy fails because the same question can move through several subproblems. Early on, the agent may need to search for facts. Later it may need a code runner or a calculator. A repeated ranking step works better because it lets the agent revise its outside help after each new result.

The second part of the method matters too. AutoTool does not only learn from final success. It is trained on long traces with explicit tool-choice reasoning because those traces show which tool was useful at each stage and why that tool fit the local need better than the alternatives.

Math after the picture

Score the next tool choice

First in words:

For each step, give every candidate tool a score from the current reasoning state and then prefer the tool with the largest score.

Then the compact form:

score(tool, step) = fit_to_need(tool, step) + consistency(tool, step) - waste(tool, step)

Every symbol:

score(tool, step)overall value of choosing one tool at the current step
fit_to_need(tool, step)how well that tool matches the missing information or action in the current partial solution
consistency(tool, step)how well the choice agrees with successful multi-step training traces on related situations
waste(tool, step)cost from choosing a tool that adds little value, delays progress, or sends the solution in the wrong direction
A tiny worked example
The agent must answer a science question with a missing numeric step.
Search tool: fit 4, consistency 2, waste 3, total 3.
Calculator: fit 8, consistency 3, waste 1, total 10.
Code runner: fit 5, consistency 2, waste 2, total 5.
The agent picks the calculator because the next gap is numeric and the other tools add less direct value.

The paper uses a trained ranking objective rather than this exact formula, but the formula captures the tradeoff the system is trying to learn.

What can go wrong

What can go wrong

Bad candidate sets. If the right tool is missing from the available menu, the ranking step cannot recover because it can only choose among the listed options.
Weak step descriptions. If the current reasoning state is unclear, the tool ranking can drift because the model no longer knows what local gap it is trying to fill.
Overusing outside help. A model may call tools too often if it learns that tool use is usually rewarded, so the waste term has to matter because unnecessary calls slow the solution.
Done right. The method is useful because it separates stable long-trace reasoning from dynamic tool choice, so the agent learns both coherent solutions and adaptable outside help.
What a runnable demo should prove

What a runnable demo should prove

Build a small benchmark with three tool menus that overlap but are not identical. Include math questions, search-heavy questions, and code questions. Run one agent that assumes a fixed tool mapping and one agent that ranks tools at every step. After each tool call, log the current step, the ranked list, the chosen tool, and whether the call reduced the next missing gap.

The demo should show higher end-to-end task success for the ranking system because the useful tool changes across steps and across menus. It should also show some success on unseen tools with familiar descriptions because the model is learning a choice rule, not only memorized tool names.

tool_choice_gain = success_dynamic - success_fixed

The core proof is that dynamic tool ranking keeps working when the tool set changes because the agent is learning how to choose, not only what it used before.
