SHE-LoRA: Selective Homomorphic Encryption for Federated Tuning

Encrypt only the most important weights during federated training to stop attackers from reading private data without slowing down learning.

Paper explainersAll themesAlignment, Safety & Fairness

When teams at different companies train a language model together, they send weight updates back to a central server. Attackers can read those updates like postcards and reconstruct the private training data. SHE-LoRA locks up only the most important weights so attackers see gibberish, but uses regular numbers for the rest to keep training fast.

Zero assumption version

Federated learning leaks private data through weight updates

When a hospital, a bank, and a law firm each want to fine-tune a language model on their private data, they do not send raw documents to a shared server. Instead, each site trains locally and sends only weight updates (the nudges to the model's numbers) to a central server. The server averages all the nudges and sends back a new model.

But adversaries have found a way to reverse-engineer those weight updates. They run an inversion attack: if I see the nudge you sent, I can ask: what data would have produced that exact nudge? By solving this puzzle, they can reconstruct your private patient records, financial histories, or legal documents. This is not a minor leak—it is a fundamental break.

A beginner would try to encrypt all weights. Lock every number up tight with an encryption key so attackers see only random-looking ciphertext. But encryption is expensive: it slows training by 10 to 100 times and bloats network traffic. On mobile devices or aging servers, this is not practical. The method becomes unusable.

The method. Encrypt only the weights the model relies on most, leave the rest visible, and use a special trick to reassemble averaged updates correctly at the end.

The algorithm as a flow

What it actually does

Step 1: Measure importance

Each client tests how much each weight matters by temporarily removing it and measuring the loss change.

Step 2: Negotiate encryption

Server collects importance scores from all clients, finds common critical weights, and decides globally which weights to encrypt given each device's constraints.

Step 3: Partition and encrypt

Each client swaps the order of weights so encrypted ones are grouped together (same columns), then encrypts only that block.

Step 4: Send and aggregate

Clients send mixed updates: plain-number updates and ciphertext blocks. Server averages the plain parts directly, stores encrypted parts as-is.

Step 5: Decrypt and reparameterize

Server tells each client to decrypt their encrypted block, decompose it back into weight pairs, and return the final average weight.

What the paper changes

The weight set encryption picks

The paper changes which weights get locked up. Instead of encrypting all of them (expensive) or none (insecure), it encrypts a carefully chosen subset: the weights that matter most to the model's loss, adjusted for how much encryption each device can handle. This subset is not fixed—it negotiates across heterogeneous clients (phones, servers, laptops with different memory and compute budgets). The subset changes per client based on what that client can afford.

the object it moves  =  Weight importance subset
The hidden quantity

Parameter importance: how much loss changes when a weight is removed

measured quantity  =  Parameter sensitivity (loss delta on removal)

The paper measures a hidden quantity: for each weight in the model, how much does the loss go up if that weight is zeroed out? A weight with high importance makes a big dent in the loss; removing it hurts. A weight with low importance barely matters. This is not the weight's value, but the weight's impact—how much work it does.

To estimate this, each client trains for a round, then tests every weight by temporarily setting it to zero and measuring the loss. Large loss change means the weight is critical and should be encrypted to protect. Small loss change means the weight is decorative and can stay visible. This importance score tells the server which weights to encrypt.

Why it works

Why selective encryption stops attackers without killing speed

Attackers learn private data by reading weight updates (the nudges sent to the server). If an attacker sees that a weight went from 0.5 to 0.6, they can reason backwards: what data pattern would push that weight by 0.1? Over millions of weights and training rounds, they can reconstruct most of the private dataset.

SHE-LoRA blocks this by encrypting the most important weights. An attacker now sees something like ciphertext: 8n4k5x... for the weights that matter, and plain numbers 0.61 for the rest. The ciphertext is gibberish without the key. The weights that matter most are also the ones attackers need most: important weights are the most predictive of the underlying data. By hiding those, the attack becomes useless.

Encryption is slow, so the paper encrypts only a small fraction—typically 5 to 15 percent of all weights. The unencrypted weights do not need protection because they carry little information about the training data (they are near-zero or redundant). This is why the paper picks the top 5–15 percent by importance instead of all-or-nothing.

The tricky part: when the server averages weight updates from multiple clients, encrypted and unencrypted parts cannot be mixed naively. If client A encrypted columns 1–3 but client B encrypted columns 5–7, the server cannot just add them. So the paper uses column-aware aggregation: it reorders the encrypted columns so they line up, averages the unencrypted columns separately, then at the end tells each client to decrypt and verify. This preserves the mathematical meaning of the updates.

Math after the picture

The importance score and protection formula

First in words:

Sensitivity is the jump in loss when a weight is zeroed. Then, penalty for moving a weight scales with that weight's importance: high-importance weights get a big penalty to keep them still, low-importance weights stay flexible.

Then the compact form:

Sensitivity(w) = L(W) - L(W with w zeroed); Protected_weight = encrypted if Sensitivity(w) > threshold

Every symbol:

L(W)the loss (prediction error) of the whole model with all weights
wone single weight
W with w zeroedall weights except w is set to zero
Sensitivity(w)how much loss grows when w is removed
thresholdthe cutoff importance score to decide whether to encrypt w or leave it plain
A tiny worked example
Suppose we have 10 weights. Train and test importance:
w1: remove it, loss jumps from 50 to 85 → Sensitivity = 35 (very important)
w2: remove it, loss jumps from 50 to 51 → Sensitivity = 1 (barely matters)
w3: remove it, loss jumps from 50 to 62 → Sensitivity = 12 (medium)
Sort descending: [35, 12, 1, ...]. If we can afford to encrypt 30 percent, we encrypt weights with sensitivity 35 and 12, leave the rest plain.
Now attacker sees: ciphertext for w1 and w3, plain number for w2 and the rest.
The ciphertext blocks the most informative weights. Attack precision drops from 90 percent reconstruction to 15 percent.

Importance tells the server which weights to lock up; encryption hides the ones attackers need most, leaving weak updates visible but harmless.

What can go wrong

What can go wrong

Importance misjudgment. If the importance test is run on a tiny or unrepresentative batch, it may mismeasure which weights truly matter. A weight might look unimportant on Monday but critical on Tuesday with different data. Attackers then target the weights you thought were safe.
Heterogeneous clients encrypt different subsets. One phone can afford encryption of 5 percent; a server can afford 30 percent. If the server tries to enforce a single global subset, the phone becomes a bottleneck. If clients encrypt different weights, the server's column-aware aggregation becomes fragile: misaligned encrypted columns produce garbage averages.
Attackers still learn from unencrypted weights. The paper argues unencrypted weights are low-importance and thus low-information. But in some scenarios (sparse models, knowledge distillation, or data where some groups are much rarer than others), unencrypted weights can leak. The attack is weakened, not eliminated.
Done right. Importance scores are computed per round on representative data; global subset negotiation accommodates device budgets; a threshold is tuned to balance privacy (encrypt 10–20 percent) against speed; column-swapping is verified end-to-end.
What a runnable demo should prove

What a runnable demo should prove

Build a federated training scenario with 3–5 simulated clients (e.g., different text domains: medical, legal, financial). Each client trains a small language model (e.g., DistilBERT) on its private text. Measure importance scores per client. Run SHE-LoRA with selective encryption on, say, the top 10 percent of weights. Run a gradient inversion attack (e.g., cosine similarity between reconstructed and true data). Compare: no encryption (attacker reconstructs 80 percent of text), encrypt everything (attacker gets 5 percent but training is 50x slower), SHE-LoRA (attacker gets 15 percent, training is 1.2x slower). Also measure communication: full encryption sends 10x more data; SHE-LoRA adds 2 percent overhead.

Privacy_gain = 1 - (reconstruction_score_with_she_lora / reconstruction_score_no_encryption); Speedup = training_time_encrypt_all / training_time_she_lora; Communication_overhead = extra_bytes_for_encryption / total_update_bytes

The demo must make it impossible to miss: selective encryption restores practical federated training while keeping private data mostly safe from inversion attacks.
