K²-Agent: Co-Evolving Know-What and Know-How for Hierarchical Mobile Device Control

A phone-control agent learns both what steps to take and how to execute them by splitting learning into a high-level planner that reads its own mistakes and a low-level executor trained on balanced, self-guided practice.

Paper explainersAll themesAgents & Tool Use

Imagine trying to teach someone to use a phone. You cannot just tell them the steps once and expect perfect performance. They need to practice, learn where they went wrong, and get feedback on both what went wrong (the plan) and how to actually do it (the technique). K²-Agent models this exactly: it separates planning (knowing what to do) from execution (knowing how to do it), then trains each one independently so they can improve together.

Zero assumption version

Why phone agents fail at hard tasks

A phone-control agent must solve two completely different problems at once: deciding what steps to take (clicking a button, filling a text field, swiping left) and actually doing each step correctly. When the agent fails, we do not know which problem broke. Did it choose the wrong step, or did it click in the wrong spot? When training fails, both systems break together, like teaching someone to drive by having them sit in a car once and hope they remember.

Existing agents use a single big model that tries to do both jobs. This mixes up two kinds of learning. The high-level planner needs examples of long task sequences so it learns task logic. The low-level executor needs dense feedback on every single action so it learns smooth, accurate motions. But one model cannot specialize in both at once.

The core problem. A single agent that plans and executes learns both too slowly and too clumsily, like a student trying to study history and piano at the same time.

The algorithm as a flow

What it actually does

Step 1: Planner gets one example

A human shows the agent one complete sequence for a task type (e.g., open settings, change brightness). That is all the data the planner starts with.

Step 2: Planner refines itself through self-correction

The planner executes its understanding, watches where it breaks, names why, and edits its own notes. It repeats this cycle several times to catch and fix gaps.

Step 3: Executor trains on sorted mistakes

The low-level executor collects action examples from many failed attempts. Errors are sorted: clicks-at-wrong-coordinates go separate from clicks-on-wrong-element. Each bucket is sampled fairly during training.

Step 4: Expert prefixes guide hard samples

When training on a hard example, the executor is shown some of the correct expert actions first, like an apprentice watching the journeyman before trying the move themselves.

Step 5: Both solve the task together

The tuned planner picks steps; the trained executor executes them. On unseen tasks, the planner transfers its logic and the executor uses its learned skills.

What the paper changes

The two things the paper improves

Most agents are monolithic: a single neural network handles planning and execution together. K²-Agent splits this into two specialized learners. The high-level planner is a large vision-language model that reads task context and runs a reflection loop. The low-level executor is a smaller, trainable model that learns precise action sequences.

The object being changed is the separation of planning from execution, plus the training method for the executor. The planner improves through self-critique because when it watches its own plan fail, it can identify the exact step that broke and edit only that step, rather than retraining from scratch. The executor improves through curriculum learning with error-sorted experience because mixing action-type mistakes with position mistakes confuses the learning signal, but separating them lets each problem be solved independently. Expert guidance works because showing the first few correct steps anchors the executor in the right part of action space before it attempts the harder steps.

The hidden quantity

Error-sorted experience: the hidden quantity that makes training work

measured quantity  =  Error type balance in the practice examples

When the executor fails on an action, it usually fails for one of two reasons: the action type was wrong (clicked a button that does not exist), or the coordinates were off by a few pixels (clicked the right element but in the wrong spot). These are completely different problems and need different fixes. Grouping failures by error type lets the trainer focus on one kind of mistake at a time.

K²-Agent measures error-type explicitly using a simple rule: actions are judged as correct only if both the action type (click, long-press, swipe, type) and the coordinates match the expert action within a small threshold. When training, the executor samples from a balanced pool where each error type appears proportionally, so the model does not just memorize the common mistakes and ignore the rare ones, because unbalanced data causes the model to optimize for frequency rather than accuracy. This is the hidden mechanism that makes fast learning possible.

Why it works

Why separating planning from execution unlocks faster learning

The planner and executor face opposite scaling problems. The planner needs long-horizon reasoning: given a phone screen, figure out the correct five-step sequence to complete the task. The executor needs micro-precision: click here, type this, swipe at exactly this angle. A single model cannot excel at both because their training signals conflict. A long sequence of corrections confuses the executor because each correction pulls the weights in a different direction, like being asked to learn five languages at once; micro-feedback does not help the planner see the big picture because task-level errors are too sparse and coarse to guide the fine-grained weights that control high-level reasoning.

K²-Agent solves this by training each layer separately. The planner starts from one demonstration and improves by running itself, detecting where it failed (using a Summarize-Reflect-Locate-Revise loop), and editing its own task notes. It refines its understanding of the high-level strategy without needing the executor to be perfect. Meanwhile, the executor trains on action-level data: thousands of real action samples sorted by error type. This dense, focused feedback lets the executor learn precise coordination.

The trick is that they co-evolve. After the planner stabilizes, it generates candidate trajectories the executor can practice on. After the executor trains, it makes the planner's trajectories more reliable because a well-trained executor executes the planner's steps accurately, so the planner receives honest feedback about whether its high-level plan is sound or needs revision. The separation prevents two learning tasks from fighting; the co-evolution ensures they bootstrap each other. Error-decoupled pools and expert prefixes make executor training converge faster because the model sees a realistic mix of mistakes and receives guidance proportional to difficulty.

The reward that sorts errors and guides learning

First in words:

reward equals 1 if action type matches AND position error is small, 0 otherwise

Then the compact form:

r(a, a_hat) = 1 if action_type(a) = action_type(a_hat) AND distance(coords(a), coords(a_hat)) < epsilon, else 0

Every symbol:

athe action the executor produced
a_hatthe correct expert action
action_type(a)the primitive operation (click, long-press, swipe, type)
coords(a)the x,y position on screen where the action occurs
epsilonthe tolerance threshold in pixels, about 10-20 pixels
r(a, a_hat)the reward: 1 for correct, 0 for any mistake
A tiny worked example
Expert action: click at (450, 300) [the Settings button].
Executor tries: click at (452, 301). Action type matches (click), distance = sqrt(2^2 + 1^2) ≈ 2.2 pixels, less than epsilon=20. Reward = 1.
Executor tries again: long-press at (450, 300). Action type does not match (long-press vs click). Reward = 0. This sample goes to the 'wrong-action-type' pool.
Executor tries third time: click at (380, 200). Action type matches (click), but distance = sqrt(70^2 + 100^2) ≈ 122 pixels, greater than epsilon. Reward = 0. This goes to the 'position-error' pool.
Training uses a balanced mix: 1/3 from correct, 1/3 from position-error pool, 1/3 from action-type pool, so the executor learns both skills equally fast.

This simple binary rule creates two separate feedback signals: action-type correctness and coordinate precision. Splitting them into different training pools forces the executor to learn both skills instead of collapsing into one.

What can go wrong

What can go wrong

The planner gets stuck in bad local plans. If the initial demonstration is atypical or misleading, the planner's reflection loop may convince itself that a wrong plan is right. The Locate module must correctly identify the first failure point; if it misdiagnoses the problem, edits backfire.
The executor overfits to expert prefixes. Expert demonstrations injected as context can make the executor memorize those exact sequences rather than learning general action skills. The injection must be carefully balanced: too much and the model becomes a copier; too little and it fails on hard samples.
Error-decoupled pools become unbalanced in rare tasks. On a task with few position-error failures (because the clicks are simple), the action-type-error pool may dominate. If the task is unseen at test time, the executor has not practiced position errors enough.
Done right: planner and executor are truly independent. The planner is a frozen vision-language model that reasons in natural language. The executor is a separate trainable model. If one layer is wrong, retraining only that layer does not corrupt the other, making the system modular and debuggable.
What a runnable demo should prove

What a runnable demo should prove

Build a minimal K²-Agent on a toy phone task: a simple two-screen sequence like opening an app and tapping a button. Start with one human demo. Show the planner generating a plan, running it, detecting a failure (e.g., clicked the wrong spot), and correcting its notes in a single iteration. Collect action examples from the planner's outputs where clicks miss the target. Sort them by error type: action-type errors (clicked a non-clickable region) in one bucket, position errors (right element, wrong pixel) in another. Train the executor on a balanced sample of both buckets, with expert prefixes shown only on the position-error samples. Measure final task success before and after training.

success_rate = (tasks_completed_correctly) / (total_tasks_attempted)

The demo must show that error-decoupled training converges faster (fewer steps to reach 80% accuracy) than uniform sampling because balancing error types ensures the executor practices both skills equally, preventing the common trap of memorizing the dominant mistake type. Expert prefixes accelerate learning on position-error samples without creating blind spots because the model learns to continue an expert trajectory rather than start from scratch, making each learning step more reliable and speeding convergence.
