CRAMER: Control via Request-Aware Masking for Editing Recommenders

Modify a frozen sequential recommender immediately from a user's natural-language request by masking selected model weights instead of retraining the whole system.

Paper explainersAll themesOther

A sequential recommender predicts what a user may want next from their recent interaction history. That works well when the goal is to continue existing behavior, but users often issue immediate requests such as 'show fewer expensive items' or 'surface outdoor gear for this weekend'. Standard recommenders do not react cleanly to those requests without retraining, and language-model overlays can add too much cost at serving time. CRAMER treats the request as a control signal and converts it into masks over the frozen backbone, because the mask can change how strongly certain pathways contribute without rewriting all of the stored weights.

Zero assumption version

Sequential recommenders are good at continuation but weak at immediate control

A recommender trained on click or purchase sequences learns stable patterns: users who bought one item later bought another, or users who watched one type of content later explored a related type. That training objective captures average behavior over time, not sudden one-off instructions that arrive at recommendation time.

As a result, a user request can conflict with the learned default. A user may usually buy premium electronics and still ask for budget options today. Editing the full model for every request is too expensive, and sending every recommendation through a large language model can raise serving cost and latency. The paper asks how to get direct control over a trained recommender without discarding the value already stored in its backbone.

The paper's move. Keep the recommender backbone frozen and let the user request generate masks that scale or suppress selected weight pathways, so the same backbone can express different recommendation behaviors on demand.

What the paper changes

What the paper changes

The paper changes how a recommender is controlled at serving time. Instead of updating the backbone weights directly, it inserts a lightweight masking layer that edits how the backbone is used for one request.

the object it moves  =  the serving-time control interface
The hidden quantity

The hidden quantity

measured quantity  =  controllability of the ranking function

The hidden quantity is controllability: how much the recommendation ranking can be moved in a requested direction without rebuilding the whole model. A system with low controllability either ignores the request or requires heavy retraining to obey it. A system with high controllability can redirect the ranking immediately while still using the learned structure from historical data.

CRAMER raises this quantity by masking internal pathways rather than replacing the recommender. That choice matters because a user request usually does not ask for a brand-new model. It asks for a selective edit to the current model, such as boosting one attribute, suppressing another, or reweighting recent intent against long-term history.

Why it works

Why masking can edit recommendations cheaply

A trained recommender already contains many useful pathways: some respond to recency, some to category preference, some to price range, and some to item transitions. A user request often needs only a selective change in how those pathways are weighted. Full retraining is wasteful because the request does not invalidate the entire model.

Masking works because multiplying internal weights or channels changes the effective computation while leaving the stored backbone unchanged. If the request says to emphasize affordability, the control module can damp pathways associated with premium signals and strengthen pathways associated with cheaper alternatives, because the final ranking depends on the relative strength of those pathways. The model then produces a new ranking through the same backbone, but under a different active pattern.

This is computationally attractive because the expensive part of the model stays frozen. The request only has to generate masks, which are much smaller than the backbone itself. That means the system can respond immediately to diverse requests while still preserving the historical structure that made the recommender useful.

Math after the picture

The masking equation

First in words:

The edited recommender multiplies the original backbone weights by a request-dependent mask. Values near one keep a pathway mostly unchanged, values below one suppress it, and values above one strengthen it.

Then the compact form:

effective_weight = backbone_weight * request_mask

Every symbol:

effective_weightthe weight actually used for this request
backbone_weightthe stored parameter from the frozen recommender
request_maskthe control value produced from the user's request
A tiny worked example
Suppose one pathway scores premium products strongly with backbone weight 0.9.
The user request is 'show cheaper options today'.
The control module outputs a mask of 0.3 for that pathway.
The effective weight becomes 0.9 times 0.3, which gives 0.27.
A budget-sensitive pathway with backbone weight 0.5 might receive a mask of 1.6, giving 0.8.
The edited ranking shifts because the request changed the relative influence of those pathways.

The important point is that the edit happens through the mask, not through retraining the backbone weights themselves.

What can go wrong

What can go wrong

The backbone may not expose the right internal pathways. If the frozen model never learned features related to the request, masking cannot create them from nothing because it can only reweight what already exists inside the recommender.
Aggressive masks can damage ranking quality. If the control module suppresses too many pathways or amplifies a weak one too strongly, the edited recommender may obey the request superficially while losing relevance to the user's actual intent.
Language requests can be ambiguous. A request such as 'something more suitable' may not map cleanly to one ranking change, so the control module can struggle unless the training data link text requests to clear recommendation edits.
Done right. The method works best when the backbone already contains broad item and sequence structure, because masking can then redirect that structure toward the specific request without paying the cost of retraining.
What a runnable demo should prove

What a runnable demo should prove

Build a toy recommender on shopping sessions with item attributes such as price, category, season, and brand. Train one sequential backbone on the raw sessions, then add a request module that receives instructions such as 'fewer premium items', 'more outdoor gear', or 'prefer local brands'.

The demo should compare three modes: no request editing, full fine-tuning per request, and request-aware masking. The interesting result is whether masking can shift the top-ranked items in the requested direction while preserving most of the backbone's base relevance and using far less serving-time work than full retraining.

request_alignment = fraction_of_top_ranked_items_that_match_the_current_request

The central check is whether one frozen recommender can express many on-demand behaviors because the request edits internal pathways rather than demanding a new model each time.
