Hierarchical Software Engineering Agents via Bandit Optimization

Instead of one giant model solving software engineering end-to-end, train a crew of small agents each good at one task, and use bandit search to find the best structure.

Paper explainersAll themesAgents & Tool Use

Software engineering with AI is hard because a single model must do everything at once: read the bug report, explore the code, pinpoint the fault, write the fix, test it. When a model learns to do five different tasks together, its internal representations become entangled—it has no room to specialize, so it fails when it sees a problem different from training data. This paper argues for a different approach: split the job into smaller sub-tasks, assign a specialized agent to each, and let a main orchestrator decide the flow. The trick is finding which sub-tasks matter most and in what order. The paper shows how to do this efficiently using bandit search—a method that balances trying new structures with focusing on the ones that work.

Zero assumption version

Why one agent fails at messy real problems

A typical AI software engineer is a single large model that reads an issue description and tries to solve it in one long chain of reasoning. It must simultaneously understand the problem, navigate a massive codebase it has never seen, identify where the bug is, write correct code, and validate that the fix works. This is like asking one person to be a detective, a map-reader, a code-writer, and a tester all at once.

The problem is that each of these sub-tasks requires different skills and different types of reasoning. A model trained to do them all becomes a generalist and succeeds at none. More critically, when it encounters a codebase or problem unlike anything in its training data, it has no specialized fallback—it just fails. Engineers naturally solve problems by breaking them into steps and asking specialists to handle each step.

In one sentence. The paper replaces one giant agent with a team of small specialized agents, each trained for a single sub-task, and uses bandit search to discover which team structure works best.

The algorithm as a flow

What it actually does

Start with sub-task definitions

Write a small set of potential sub-tasks (e.g., reproduce-bug, localize-fault, modify-code, test-fix).

Create agents for each

Train or prompt a small language model to handle one sub-task well.

Define possible structures

An orchestrator can run agents in different orders and with different information flows.

Run bandit search

Test many structures on a small set of training problems; track which structure solves the most bugs correctly.

Deploy the winner

Use the best structure found on new unseen bugs; it generalizes better because each agent is specialized.

What the paper changes

The one thing the paper changes

The paper changes the architecture: from a single monolithic model to a hierarchy of specialized agents orchestrated by a central coordinator. The object is the agent structure itself—which agents exist, how they connect, and the order in which they run.

The hidden quantity

The hidden quantity: how well structures work on new bugs

measured quantity  =  generalization to unseen problem types

The paper measures one key quantity that is hard to observe directly: how well does the solution method handle bugs and code structures the model has never seen during training? This is generalization—the ability to work on new problems, not just variations on training data.

The paper estimates this by testing the discovered hierarchy on SWE-bench-Live, a leaderboard with recent software engineering problems that are deliberately different from historical training sets. A high score on this test set proves the agent structure actually learned to be flexible, not merely memorized patterns.

Why it works

Why splitting into agents and searching for structure works

The core reason is specialization. A model trained to do one thing well has learned a simpler pattern than one trained to do five things. When a new problem shows up that differs from training data, the specialized model still works better because it relies on one core skill, not a fragile pipeline of five. If the bug-reading agent has seen many styles of bug reports, it will parse a new one correctly. If the fault-finding agent has internalized the patterns of a hundred code-bases, it will spot faults in new code. The single monolithic agent has no such depth—it is a generalist, only weighted averages across all tasks.

The bandit search matters because there are too many possible hierarchies to try manually. A naive search would try thousands of orderings. Bandit search—which keeps testing promising structures and discarding poor ones—lets us find a good structure on a small budget of test problems. The orchestrator learns which sub-tasks to run in which order, and this learned structure generalizes because it is built on specialized components.

Math after the picture

The bandit equation: balancing exploration and exploitation

First in words:

For each structure, the bandit tracks a score (how many recent problems it solved) and an uncertainty (how confident we are). The next test chooses the structure that maximizes the score plus a bonus for trying uncertain structures. This balance avoids getting stuck testing only obvious choices.

Then the compact form:

arm_value = win_count / total_pulls + sqrt(ln(total_tests) / total_pulls)

Every symbol:

arm_valuethe score of one structure: expected wins plus uncertainty bonus
win_counthow many of the test problems this structure solved correctly
total_pullshow many times this structure has been tested so far
total_teststhe total number of test steps across all structures
sqrt(ln(total_tests) / total_pulls)the uncertainty bonus: larger when rarely tested
A tiny worked example with two candidate structures
Structure A: tested 10 times, solved 6 correctly. Score = 6/10 + sqrt(ln(20)/10) = 0.6 + sqrt(0.299) = 0.6 + 0.546 = 1.146
Structure B: tested 10 times, solved 8 correctly. Score = 8/10 + sqrt(ln(20)/10) = 0.8 + 0.546 = 1.346
Structure C: tested 2 times, solved 1 correctly. Score = 1/2 + sqrt(ln(20)/2) = 0.5 + sqrt(1.498) = 0.5 + 1.224 = 1.724
Next test tries Structure C because the big uncertainty bonus outweighs its lower win rate. This is exploration: trying a structure we have not learned much about yet.

The bandit equation ensures that we spend more effort testing promising structures but do not ignore untested ones—exactly the right balance for finding a good hierarchy efficiently.

What can go wrong

What can go wrong

Bandits assume finite structure space. If the possible hierarchies are huge or continuous, bandit search becomes inefficient. The paper works because the sub-tasks are discrete and small.
Specialization requires good sub-task definitions. If the sub-tasks are poorly chosen (e.g., overlapping or one-sided), the agents cannot specialize. Manual decomposition matters—bad sub-tasks doom the approach.
Smaller models are sometimes harder to chain. Orchestrating multiple agents adds latency and requires agents to produce output consumable by the next agent; format mismatches cause failures.
Done right. When sub-tasks are well-defined and the bandit budget is adequate, the approach yields hierarchies that beat single-agent systems on new problems.
What a runnable demo should prove

What a runnable demo should prove

Build a simple software engineering task (e.g., find and fix off-by-one bugs in a set of toy Python functions). Create three agents: a Reader (understands the bug description), a Locator (finds the line with the bug), and a Fixer (writes the corrected line). Then write a bandit loop that tests different orderings (Reader into Locator into Fixer, Reader into Fixer with Locator skipped, etc.) on a small set of training bugs. Track which ordering solves the most bugs. Finally, test the winning ordering on a held-out set of new bugs you did not use in the bandit search. The specialized hierarchy generalizes better because each agent has internalized a single task deeply, so when a new bug arrives with unfamiliar patterns, each agent still applies its core skill correctly—whereas a monolithic model has no such specialization and fails when the problem deviates from training data.

generalization = (accuracy on held-out bugs) - (accuracy on training bugs)

The demo proves that the learned hierarchy—discovered via bandit search—handles unseen bugs better than a monolithic approach because each agent is specialized and the structure is learned, not guessed.
