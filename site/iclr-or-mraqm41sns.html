One for Two: Unified Framework for Imbalanced Graph Classification

When graphs in a dataset are unevenly distributed (some classes rare, some node patterns over-represented), this paper learns prototype examples that fairly represent each class and rebalances training so minority graphs get proper weight.

Paper explainersAll themesGraph & Geometric Learning

Graph Neural Networks are models that learn patterns from graphs (networks of connected nodes). They excel at classifying whole graphs, but struggle when some classes of graphs are much rarer than others, or when the connection patterns themselves are lopsided. This paper introduces a unified approach that tackles both kinds of imbalance by learning representative prototype graphs and adjusting how training examples influence the model.

Zero assumption version

Two flavors of imbalance break graph learning

Suppose you have a dataset of chemical molecules (each is a graph: atoms are nodes, bonds are connections). You want to train a model to classify them into categories like "toxic" or "safe". The problem: 95% of your data is safe molecules, 5% are toxic. A naive model sees so many safe examples that it learns to predict "safe" for everything, ignoring what it learned about toxic ones.

But there is a second, trickier imbalance. Some molecular structures dominate your dataset: simple chains, tight rings, star patterns. Other structures are rare: complex branching, unusual cycles. Even if the class labels (toxic/safe) are balanced, the model still over-learns the common structures and misses patterns in rare ones. A beginner might collect more data or just weight examples equally, but neither fully solves this: more data often just adds more common patterns, and equal weights ignore that rare structures genuinely teach less (because there is less of them).

The paper's move in one sentence. Learn representative example graphs (called prototypes) for each class, then reweight training so that minority graphs and rare topologies pull the model toward them just as strongly as majority graphs do.

The algorithm as a flow

What it actually does

Capture topological variety

Extract graph structure at multiple scales (neighborhoods, motifs) and add learnable perturbations to increase the diversity of examples the model sees.

Learn class prototypes

From all graphs in a class, compute a representative prototype: the typical graph that best captures that class's essence.

Measure sample influence

Compute a score for each graph: how much does this graph deviate from its class prototype? Graphs far from the prototype are rarer or noisier.

Reweight training nudges

Use that score to adjust how strongly each graph pulls the model during training: closer to prototype gets smaller weight, farther gets bigger weight.

Converge to balanced representations

With adjusted weights, the model gradually learns equally accurate boundaries for all classes and all topological patterns.

What the paper changes

The single thing the paper changes

The paper changes the training weight (how strongly each example pulls the model's learning) for individual graphs. Normally every graph counts the same. UniImb gives minority graphs and atypical graphs bigger weight during training, and common graphs smaller weight, so all contribute equally to the final model's understanding.

the object it moves  =  training weight per graph
The hidden quantity

The hidden quantity: deviation from prototype

measured quantity  =  distance from class prototype

A prototype is a representative example built from all graphs in a class: it is the central average representation that best captures what makes a graph belong to that class. The paper measures how far each individual graph is from its class's prototype. Graphs very close to the prototype are typical and common; graphs far from it are unusual or rare.

The paper uses this distance to estimate influence during training. Graphs with small distance (typical, likely abundant) get small training weights. Graphs with large distance (atypical, likely rare) get large training weights. This reversal ensures that the model learns from rare examples just as much as common ones.

Plain reading. Each graph in your dataset can be measured by how close it is to the typical example of its class. Graphs that match the typical form are common; graphs that differ a lot are unusual. UniImb measures this gap and uses it to decide how hard each graph should push the model during training.
Paper reading. The paper calls this the dynamic balanced prototype distance. It is computed for each graph as the distance (in the model's learned representation space) from that graph to the learnable prototype vector for its class. Load-balancing weighting then inverts this: graphs with large distance receive proportionally larger training nudges (adjustments to the model's weights).
Why it works

Why it works: the causal chain

Training a neural network is like steering a boat: you measure how far off-course you are (the error), then nudge the helm (update the weights) to correct it. The size of each nudge is typically the same for every example. With imbalanced data, this equal nudging fails: you steer hard based on the 95 majority-class examples and barely move based on the 5 minority ones. The boat ends up pointing at the majority perfectly, ignoring the minority entirely.

UniImb fixes this by measuring how unusual each graph is (using the prototype distance) and increasing the size of the nudge for unusual graphs. Now the 5 minority examples exert larger nudges than the 95 majority examples exert per-example, so their signal is heard. The boat's final heading balances both groups. The paper justifies this by appealing to information theory: the model should allocate learning capacity (information) equally across classes and topological patterns, not waste it all on whatever is most common.

Math after the picture

Equation: the load-balanced training loss

First in words:

Total loss equals the classification error, adjusted by a penalty term that upweights graphs far from their class prototype and downweights graphs close to it.

Then the compact form:

L = L_cls + lambda * sum_i w_i * (proto_dist_i)^2

Every symbol:

Ltotal loss (error to minimize)
L_clsclassification loss (how wrong predictions are)
lambdastrength of prototype balancing (a tuning knob)
w_itraining weight for graph i (inverse of distance from prototype)
proto_dist_idistance of graph i from its class prototype
sum_iadd up over all graphs in the batch
A tiny worked example with two graphs
Suppose graph A (common, close to prototype) has proto_dist = 0.5, so weight w_A = 1.0.
Suppose graph B (rare, far from prototype) has proto_dist = 2.0, so weight w_B = 4.0.
Both make the same classification error of 1.0.
With lambda = 1.0, graph A contributes 1.0 * 1.0 * (0.5)^2 = 0.25 to the penalty.
Graph B contributes 4.0 * 1.0 * (2.0)^2 = 16.0 to the penalty.
Same error, but rare graph B pulls training 64 times harder, ensuring its signal reaches the model.

The weight for each graph (call it w) scales how strongly that graph's error nudges the model, so rare graphs (with large distance) create larger training nudges than common graphs.

What can go wrong

What can go wrong

Prototype collapse. If the prototype for a class is computed from too few examples, it may not be representative. A single outlier can pull the prototype far from the true class center, breaking the distance metric.
Over-weighting noise. Graphs far from the prototype might be noisy mislabeled examples, not true rare members of the class. High weights amplify their error signals, corrupting the model.
Imbalance in the imbalance. If minority classes are also topologically homogeneous, the prototype still captures them well. But if a minority class has diverse topologies, some minority subgroups might remain invisible.
Done right. Regularization and careful tuning of lambda (the balancing strength) mitigate these. The paper uses learnable perturbations to increase graph diversity, reducing the chance that the prototype misses real variability.
What a runnable demo should prove

What a runnable demo should prove

Build a small dataset: 80 common graphs from one class, 20 rare graphs from another. Use a standard GNN (no UniImb) and a UniImb-equipped GNN. Measure accuracy separately for the common and rare classes. The naive GNN should get roughly 85% on common and 40% on rare. UniImb should narrow that gap, reaching roughly 75% on both. The key observation: training nudges per example for rare graphs are larger than for common graphs.

Fairness gap = accuracy_common - accuracy_rare. Naive GNN should show large gap (45+). UniImb should show small gap (below 15).

The demo makes it impossible to miss: equal training weights create unfair accuracy drops for minority data, because the model receives far more nudges from majority examples. Prototype load-balancing fixes this by giving rare examples bigger nudges, so the model receives equal total pressure from both classes.
