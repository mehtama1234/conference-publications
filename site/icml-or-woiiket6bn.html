SafeDec: Constrained Decoding for Safe Autoregressive Robot Navigation Policies

A runtime safety filter for robot policies that enforces formal behavioral guarantees without retraining the model.

Paper explainersAll themesRobotics & Control

Modern robot navigation policies are neural networks trained on lots of real and simulated robot trajectories. They work well in practice but have a fundamental gap: they have no explicit way to guarantee that the actions they choose are safe. SafeDec plugs this gap by adding a safety filter at the moment the policy decides on an action, using formal rules written in plain symbolic language to block or redirect unsafe moves—all without retraining anything.

The robot policy's safety blind spot

A modern robot navigation policy is a neural network that learns from thousands of recorded robot trajectories. It takes in camera images and sensor readings and outputs a sequence of motor commands (move forward, turn left, grasp object). In the lab and in real deployments, these policies generalize remarkably well—they can navigate new rooms and handle situations they never saw during training.

But there is a hidden cost. The policy is purely data-driven. It has no explicit internal representation of what counts as safe. It simply learns patterns from the data. If the data contained an unsafe move in some edge case (or if the new situation is different enough from training), nothing stops the policy from outputting that unsafe action. A robot might move toward a cliff because the training data never showed that specific cliff angle, or it might activate a gripper in an unsafe configuration because it learned a correlation that does not hold generally.

A beginner might try to collect more and more data, hoping to cover every edge case. This fails because the state space is infinite—you can never record every scenario. Or one might try to add safety constraints during training, but that requires retraining the entire policy every time a new safety rule is needed. This is slow and expensive.

In one sentence. SafeDec adds a runtime safety filter that accepts or rejects each action the policy proposes, using formal logical rules to guarantee correctness without any retraining.

What the paper changes

What the paper changes

SafeDec modifies the output of the policy at decoding time. Instead of letting the neural network freely choose an action from all possibilities, SafeDec inserts a filter that masks out dangerous actions and redistributes probability mass only to the safe subset. This happens once per step and requires no training.

the object it moves  =  which actions the policy is allowed to pick from
The hidden quantity

The constraint satisfaction score

measured quantity  =  whether the action keeps the system safe

SafeDec needs a way to know which actions will result in a safe state. It does this by checking each candidate action against a formal specification—a set of logical rules about what states and transitions are allowed. The specification is written in Signal Temporal Logic (STL), a formal language that uses predicates (like 'distance to obstacle < 0.5 meters') and logical operators (and, or, always, eventually) to express safety rules without any ambiguity.

At runtime, for each action the policy proposes, SafeDec evaluates: if the robot takes this action from the current state, does the resulting new state satisfy all the safety rules? If yes, the action is allowed. If no, it is filtered out. This is a boolean quantity—safe or unsafe—but the paper extends it to soft penalties that reflect how close the system is to violating a rule, allowing a numerical search to pick the best allowed action.

Why it works

Why it works: the decoding-time filter

The central idea is that safety can be checked at the moment an action is about to be executed, without waiting for the model to be retrained. Here is how it works:

First, the policy outputs a probability distribution over actions (some actions scored high, others low). Second, SafeDec maintains a formal safety specification as a set of logical constraints. Third, for each action the policy wants to consider, SafeDec simulates what the new state would be if that action runs. Fourth, SafeDec checks whether the new state violates any constraint. Fifth, any action that violates a constraint is blocked. Sixth, the remaining probability mass is redistributed among the allowed actions in a way that respects the policy's original ranking—the highest-scored allowed action becomes the new first choice. This means SafeDec is fully agnostic to the policy's internals: it does not need to know how the neural network works, only what actions it proposes.

This works because formal verification is a one-time computation per step. The specification (the safety rules) is written once by a human expert or extracted from requirements. Once written, it applies to any policy that uses the same robot and environment. A new policy can be swapped in and SafeDec still works—no retraining needed.

Math after the picture

The constraint satisfaction equation

First in words:

For each candidate action, compute the cost: how much does this action violate the safety specification? If the cost is zero or negative (safe), allow it. If positive (unsafe), penalize it.

Then the compact form:

cost(a) = max_constraint c in STL { violation_margin(c, s_next(a)) }

Every symbol:

aa candidate action the policy proposed
s_next(a)the next robot state if action a is executed
cone of the formal safety constraints
violation_margin(c, s)how far the state s is from satisfying constraint c; negative means satisfied
max_constraintthe worst-case constraint; if any constraint fails, the action fails
A tiny worked example: one action with two constraints
Constraint 1: distance_to_wall >= 0.5 meters. Current state has wall at 0.7m. If we move forward 0.3m, wall is at 0.4m (inside the safe zone).
violation_margin for Constraint 1 = 0.4 - 0.5 = -0.1 (negative = violated)
Constraint 2: gripper_force <= 10 Newtons. Current force is 8N. Action maintains it.
violation_margin for Constraint 2 = 8 - 10 = -2 (negative = satisfied)
cost(a) = max(-0.1, -2) = -0.1. Action violates the distance rule, so cost is positive-ish. This action is filtered out.

The cost rolls up all constraints into one number: zero or below means safe, above means unsafe. SafeDec uses this number to decide which actions to allow, because actions with zero or negative cost satisfy all the formal safety rules, while positive cost means at least one rule is violated.

What can go wrong

What can go wrong

The formal specification is wrong or incomplete. If the STL rules do not actually describe what is safe, then SafeDec will either filter out good actions (because it mistakenly blocks them) or allow bad ones (because it mistakenly permits them), since the decoding filter can only enforce the rules it is given. The responsibility for writing correct specifications lies with the system designer. SafeDec enforces what you ask it to enforce.
The model of robot dynamics is inaccurate. SafeDec predicts the next state by running the assumed dynamics model forward. If the real robot does not behave as the model predicts (e.g., slipping, latency, sensor noise), then the filtered action might still lead to an unsafe state. This is especially risky in high-speed or high-consequence scenarios.
Filtering too aggressively removes all allowed actions. If the constraints are too strict or the current state is already unsafe, SafeDec may have no legal actions to choose from. In that case, the system must have a fallback behavior (usually stop or go to a safe state), but the robot may fail its task.
Done right: specification + simulation + verification. When the formal rules are accurate, the dynamics model is validated, and the constraints are tuned to be strict enough for safety but loose enough to allow useful behaviors, SafeDec provably prevents the robot from entering an explicitly forbidden state, because the decoding filter systematically rejects every action that would lead to a state violating any rule.
What a runnable demo should prove

What a runnable demo should prove

A convincing demo would take a trained navigation policy, write a simple STL rule (e.g., keep distance to obstacles above 0.5 meters), run the policy on a procedurally generated test environment with and without SafeDec, and measure: (1) how many times the robot violates the distance rule with SafeDec on versus off, and (2) how much the success rate drops due to over-aggressive filtering. A good demo would show that SafeDec catches most violations with minimal performance loss.

safety_gain = (violations_without_filter - violations_with_filter) / violations_without_filter; performance_cost = (success_without_filter - success_with_filter) / success_without_filter

The demo must make it impossible to miss that SafeDec can turn an unsafe-but-successful policy into a safe-and-still-mostly-successful policy, all at runtime, without touching the model.
