Draft-and-Audit Reinforcement Learning for Optimization Modeling

A model learns to write then fix its own optimization programs by getting rewarded only when the final fixed version works correctly.

Paper explainersAll themesAgents & Tool Use

When you ask a model to turn a sentence like "maximize profit subject to inventory limits" into a working math problem, it often writes code that looks right but produces wrong answers — a silent failure. This paper teaches the model to write a first attempt, then critique and fix its own work, and rewards it only when the final result actually works.

Zero assumption version

Silent failures in language-to-math translation

A program that turns English sentences into math problems needs to get two things right: the syntax (does the code parse?) and the semantics (does it actually solve what the person asked for?). A sentence like "find the cheapest shipping route that stays under budget" could be coded badly in ways that are syntactically fine but wrong in meaning — the optimizer runs without error but gives nonsense answers.

A naive attempt: train the model to copy-paste examples, then hope it generalizes. This fails because the silent failures are invisible to a simple loss function ("does the code run?"). The model never learns that semantically wrong solutions are unacceptable.

In one sentence. The model learns to draft a solution, then audit and revise its own work, receiving a reward only when the final audited version actually solves the problem correctly.

The algorithm as a flow

What it actually does

Step 1: Draft

Given English text, the model writes an optimization program.

Step 2: Execute

The program runs and produces an answer.

Step 3: Audit

The model checks if the answer is correct by comparing to a known solution.

Step 4: Revise

If wrong, the model resets and writes a new attempt that fixes the detected error.

Step 5: Reward

Training reward is given only when the final program executes correctly.

What the paper changes

What the paper changes

The paper changes the training signal. Instead of rewarding syntax or intermediate feedback, it rewards only the final audited program — the one the model produced after seeing and fixing its own mistakes.

the object it moves  =  training reward timing
The hidden quantity

Revisability: drafts that are easy to fix

measured quantity  =  revisability score

Revisability is the hidden quantity this paper measures. It means the model learns to generate first drafts that are structurally easy to fix, not just attempts that might work. A revisable draft has clear error patterns (missing constraints, wrong objective direction) that the model can spot and correct in a second pass.

The paper finds this by looking at the model's performance over training: when the auditor catches an error, does the revision step actually fix it? Do revisions become shorter and more targeted? If yes, the model has learned to draft in a way that makes revision work well — the first turn and second turn operate together instead of independently.

Why it works

Why learning to self-correct works

The mechanism is this: when the model only gets rewarded at the end (after revisions), it learns that a good first draft is one that, when audited, yields useful error signals and changes. Bad drafts either fail in obscure ways (hard to fix) or succeed silently (audit passes but result is wrong). The pressure to maximize terminal reward pushes the model to internalize what makes a draft revisable.

During revision, the model sees its own first attempt plus the auditor's verdict. It learns: where does the code go wrong? What rubric-guided changes fix it? Over thousands of episodes, the model learns patterns: "if the objective is stated backwards, negate it; if a constraint is missing, add it as a penalty." The two turns become tightly coupled. The first turn generates a draft structured so the second turn can reliably fix it.

The learning signal

First in words:

Total reward equals one if the final audited program is correct, zero otherwise. No intermediate rewards for syntax or partial progress.

Then the compact form:

R = 1 if audit(final_program) == correct else 0

Every symbol:

Rtotal reward for this episode
final_programthe code after draft and revision
audit(program)run the program and check if the answer is right
correctthe known correct solution
A tiny worked example
Episode 1: Model drafts a program with the objective backwards. Auditor runs it, catches the error, model revises. Final version is correct. Reward = 1.
Episode 2: Model drafts a program with a missing constraint. Auditor catches it, model adds the constraint, final version is correct. Reward = 1.
Episode 3: Model drafts a program that runs but is semantically wrong. Auditor misses the error (or the rubric is incomplete). Final version is wrong. Reward = 0.
Over many episodes, the model learns which kinds of drafts lead to caught errors (and correctable revisions) versus silent failures. Drafts that are easy to audit and fix earn reward more often.

The key is that reward is only given when the full cycle (draft, audit, revise, audit again) ends with a correct solution. This forces the model to learn self-correction as a policy.

What can go wrong

What can go wrong

Incomplete or wrong audit rubric. If the auditor (the checker that runs the program and compares to expected output) is flawed or incomplete, the model learns to fool it. For instance, if the rubric only checks if the program runs but not if it optimizes the right thing, the model will learn to write plausibly correct-looking code that still solves the wrong problem.
Input shift: language or problem types change. The model is trained on specific English phrasings and problem types. If deployed on very different language (a different dialect, or highly mathematical notation) or new problem classes, the learned correction patterns may not transfer. The model has not seen those input patterns before, so it reverts to generic guesses.
Circular reasoning in revisions. If the model learns to make superficial changes in the revision step without actually understanding the error, it may cycle: draft -> audit finds an error -> model makes a cosmetic change -> audit still fails -> model gets no reward. This is rare if the audit rubric is clear, but possible if the rubric is vague.
Done right. A strong audit rubric (clear, unambiguous, covers both syntax and semantics), diverse training problems, and episodic feedback (train on complete draft-audit-revise cycles) minimize these risks. The paper shows this works in practice on NL-to-optimization benchmarks.
What a runnable demo should prove

What a runnable demo should prove

Build a small dataset of English optimization problems (5-10 problems, each with a known correct formulation and one or two intentional modeling errors). Train a small language model (or use an existing one) with Draft-and-Audit RL: on each episode, the model drafts a program, runs it, audits against the expected output, and revises if wrong. Track: (1) how many drafts are revisable (audit catches and labels the error correctly), (2) how many revisions actually fix the problem, (3) does the final audited version reach 100% correctness?

correctness_after_audit = (final_program_matches_expected_output ? 1 : 0); revisability = (audit_catches_error / attempts_with_error)

The demo must show that the model's second-turn revisions actually fix the errors the audit caught, and that over time, the model learns to generate drafts that the audit can reliably fix.
