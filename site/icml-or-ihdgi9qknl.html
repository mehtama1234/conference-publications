Implicit Intelligence - Evaluating Agents on What Users Don't Say

Test whether an agent can uncover hidden user requirements by exploring the world instead of obeying only the visible request.

Paper explainersAll themesAgents & Tool Use

Many real requests leave out facts that people expect a capable helper to infer. A user may ask for a restaurant suggestion without saying that wheelchair access matters, or ask for a meeting summary without saying that private details should stay private. An agent that follows only the literal words can still fail the real goal. Implicit Intelligence measures that gap by placing agents in small interactive worlds where the spoken request looks simple but the correct solution depends on facts the agent must discover.

Why explicit instruction tests are not enough

Most agent evaluations check whether the system obeys a clear prompt. That setup misses a large part of practical help because people often speak in shorthand. They assume shared norms about safety, privacy, accessibility, cost, and local context. If a benchmark states every requirement in advance, the agent never has to notice that something important is missing.

That missing pressure matters because a strong answer sometimes requires extra investigation before acting. An agent should inspect the environment, ask follow-up questions, or choose a cautious plan because the visible request may hide a requirement that changes what success means. The paper argues that current tests overestimate practical competence by rewarding literal completion instead of goal fulfillment under incomplete instructions.

The paper's move in one sentence. Build scenarios where the request is underspecified, hide deciding constraints in the environment, and score whether the agent discovers them before acting.

The algorithm as a flow

What it actually does

Write underspecified scenarios

Create tasks where the visible request is easy to state but the real goal depends on hidden accessibility, privacy, safety, or context constraints.

Represent each world in editable files

Describe places, objects, clues, and interaction rules in YAML so that scenarios are easy to inspect and expand.

Let the agent act inside the world

The agent can explore, inspect, and make choices so that it has a fair chance to discover what matters.

Grade against the full requirement

Check whether the final behavior satisfies the hidden constraint because goal fulfillment is stricter than literal instruction following.

Compare many agent systems

Run a shared set of scenarios so that researchers can see which systems search for context and which ones act too early.

What the paper changes

What the paper changes

The paper changes what counts as intelligence in agent evaluation. Instead of asking only whether the system obeys the sentence it was given, it asks whether the system reaches the user's real goal when part of that goal must be inferred from context.

The hidden quantity

Constraint discovery: the hidden quantity

measured quantity  =  How much of the real requirement the agent has uncovered before it acts

The central hidden quantity is not the final answer alone. It is how much of the missing requirement the agent has uncovered while exploring. A system may look fluent and efficient while still acting on the wrong objective because it never found the fact that changes the decision.

The benchmark makes this quantity visible by storing deciding constraints in the environment rather than in the prompt. That design helps because failures can be traced to a specific missed clue, weak search strategy, or premature action instead of being hidden inside one final pass-or-fail label.

Why it works

Why this works

The benchmark works by separating visible instructions from discoverable requirements. That separation matters because it forces an agent to choose between acting immediately and spending effort to inspect the world. Systems that only mimic direct prompt completion are exposed, while systems that reason about missing information have a path to succeed.

The Agent-as-a-World setup also matters because it keeps scenario design flexible. Researchers can express worlds in readable YAML and simulate interactions with language, so the benchmark can cover many hidden-constraint patterns without writing a custom software environment for each one.

A simple success score

First in words:

Score each run by whether the agent finished the visible task and whether it respected the hidden requirement, then reward exploration only when that exploration uncovers a needed constraint.

Then the compact form:

score = task_done * (alpha * hidden_ok + (1 - alpha) * visible_ok) ; hidden_ok <= discovered_constraint

Every symbol:

scoreoverall scenario score
task_done1 if the agent completed the requested task at all, else 0
visible_ok1 if the output matches the visible request
hidden_ok1 if the output also satisfies the unstated but discoverable requirement
discovered_constraint1 if the agent found the deciding clue that reveals the hidden requirement
alphaweight on satisfying the hidden requirement, chosen close to 1 because missing it should hurt strongly
A tiny worked example
A user asks for a dinner venue. The world contains a note showing that one guest uses a wheelchair.
Agent A picks a popular upstairs venue without checking access. Then task_done = 1, visible_ok = 1, discovered_constraint = 0, and hidden_ok = 0.
With alpha = 0.8, score(A) = 1 * (0.8 * 0 + 0.2 * 1) = 0.2.
Agent B inspects the venue details, finds the access note, and chooses an accessible venue.
For Agent B, task_done = 1, visible_ok = 1, discovered_constraint = 1, and hidden_ok = 1.
Score(B) = 1 * (0.8 * 1 + 0.2 * 1) = 1.0.
The benchmark favors Agent B because it fulfilled the real goal rather than only the spoken sentence.

The paper reports scenario pass rate rather than this exact formula, but the equation captures the benchmark's main idea: hidden constraints matter more than surface completion.

What can go wrong

What can go wrong

The hidden clue may be too obscure. If a scenario hides the deciding fact too deeply, poor scores may reflect benchmark design rather than weak reasoning because even a careful agent may lack a fair path to discovery.
Language world simulation can blur hard boundaries. A simulated world may not capture every real consequence, so some passes may still overstate real-world reliability because the environment is text driven.
Exploration can become aimless. An agent may search too long and never act, which hurts usefulness because good behavior requires both discovery and timely completion.
Done right. Give the agent a discoverable path to the missing fact and then grade the final choice against the full goal so that contextual reasoning, not guessing, determines success.
What a runnable demo should prove

What a runnable demo should prove

Build three small worlds: one with an accessibility requirement, one with a privacy boundary, and one with a safety concern. In each world, provide a short user request plus several discoverable clues. Let one baseline agent answer immediately and let one search-oriented agent inspect the world before acting. Record whether each system finds the deciding clue and whether the final action satisfies the full goal.

The demo should prove that contextual exploration improves real task success because the best answer often depends on a fact the user did not say directly.

context_gain = full_goal_pass_after_search - full_goal_pass_without_search

A useful agent must do more than follow instructions. It must notice when the real requirement is still missing and go find it.
