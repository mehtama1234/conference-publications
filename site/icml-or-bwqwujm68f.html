MonoScale: Scaling Multi-Agent Systems with Monotonic Improvement

When you add new agents to a multi-agent team, the router learns which agents are reliable by testing them on tailored warmup tasks, recording what it learns in natural language, and updating its decision-making memory conservatively.

Paper explainersAll themesAgents & Tool Use

A multi-agent system is a team where a coordinator (called the router) breaks a complex task into pieces, assigns each piece to a different specialist agent, then combines their answers. The problem: if you add new agents to the team without careful onboarding, the router does not know which agents work or when to use them, causing the whole system to fail. MonoScale solves this by giving the router a learning process: before the new agents handle real tasks, they take tailored test questions designed to expose their strengths and weaknesses; the router records what happened in a readable memory; and it updates its decisions using a trust-based rule that never makes things worse.

Zero assumption version

The cold-start problem when teams grow

A multi-agent system works by having a central router (a decision-maker) that reads an incoming task, breaks it into subtasks, and sends each subtask to a specialist. For example, one agent might do web search, another executes code, another plans steps. The router has learned which agent is best for which kind of task.

When you add new agents to the team, the router has never seen them before. It does not know: Does this new agent actually work? What kinds of tasks is it good at? When it fails, how badly does it fail? If the router assigns tasks to untested agents at random, it makes mistakes. Worse, when the coordinator keeps failing, it damages the whole system's performance—this is called performance collapse.

A naive first attempt is to just turn the new agents loose and let the router learn from real-world mistakes. But in a production system, every bad routing decision wastes resources and erodes trust. You need a controlled way to onboard new agents before they handle real work.

The method in one sentence: Before new agents help with real tasks, run them on tailored test questions that probe what they can do, learn which agents are trustworthy by reading their success and failure patterns, save that knowledge as natural-language memory, and update the router's decisions conservatively so performance never drops.

The algorithm as a flow

What it actually does

Generate warmup tasks

Create test questions designed to expose the new agent's strengths and edge cases.

Run the agent in parallel

Let the new agent attempt 4 different plans for each warmup task; record successes and failures.

Filter noisy samples

Drop tasks where the agent failed all 4 attempts; they teach less than balanced examples.

Distill into readable memory

Write plain-language findings: what the agent is good at, what breaks it, how often it fails.

Update router conservatively

Test both: have the router use old memory on a batch of tasks and time its success rate. Have it use new memory on the same batch. If new is equal-or-higher, adopt new memory; else keep the old one.

What the paper changes

What gets changed: the router's decision memory

The paper changes the router's internal knowledge base. Before MonoScale, the router had a fixed set of patterns about which agent to use when. Now, the router maintains an editable, readable memory—essentially a notebook that records what each agent can and cannot do, and how reliable it is. This memory is written in natural language, not as mathematical weights, so it can be inspected and even corrected by a human.

the object it moves  =  router's task-assignment memory
The hidden quantity

The hidden quantity: agent reliability under task-specific context

measured quantity  =  task-specific agent reliability profile

The paper measures something called the agent's reliability profile—not a single number, but a collection of reliability scores that depend on both the agent and the specific kind of task. For example: this agent succeeds 90% of the time on coding tasks, but only 60% of the time on web search. This is richer than just asking 'Is agent X good?' because the same agent can be very good at one thing and very fragile at another.

MonoScale estimates this by running warmup tasks and observing the success/failure pattern. The tailored test tasks are designed to hit edge cases and expose where the agent breaks. The router then uses these observations to build a readable profile—'Agent X is strong at code, fragile on retrieval, 70% reliable overall'—and stores this in memory. When deciding which agent to assign to a real task, the router consults this profile.

Why it works

Why conservative memory updates prevent collapse

When you add a new agent, the router could accidentally send it unsuitable tasks and fail. MonoScale prevents this by using three mechanisms working together.

First, the warmup tasks are not random—they are tailored to amplify contexts where the new agent will likely be used. This means the test data is not average; it is targeted. The router sees many examples of the new agent succeeding and failing in the kinds of situations it will actually face.

Second, the router learns in natural language. Instead of updating raw numerical weights (which are opaque and can have unintended side effects), MonoScale saves readable findings: 'This agent is strong at coding but fragile on retrieval.' A human can read, understand, and even correct this knowledge. It is auditable, which matters because humans can spot and fix mistakes that the algorithm might make.

Third, and most important, memory updates follow a trust-region rule. The algorithm tests whether adopting the new memory would cause a performance drop. If yes, it rejects the update and keeps the old memory. The reason this works: if you measure before accepting, and accept only when results are equal-or-better, then the sequence of accepted updates can never go downhill.

Math after the picture

The trust-region constraint: never accept a memory update that hurts

First in words:

new_memory is accepted only if: performance_with_new_memory is greater-than-or-equal-to performance_with_old_memory. Otherwise use: new_memory = old_memory (no change).

Then the compact form:

m_t+1 = m_candidate if Performance(m_candidate) >= Performance(m_t), else m_t+1 = m_t

Every symbol:

m_tthe router's memory after step t
m_candidatea proposed new memory based on warmup-task evidence
Performance(m)the system's task-completion rate using memory m
m_t+1the router's memory after step t plus 1
A tiny worked example
Old memory m_t: 'Agent A is good at coding (90% success rate), Agent B handles retrieval (75%).'
After adding Agent C, we observe: C succeeds at data validation 85% of the time, fails on coding 30% of the time.
Candidate memory m_candidate: 'Agent A: coding 90%, Agent B: retrieval 75%, Agent C: validation 85%.'
Test the candidate: when the router uses this new memory to assign tasks, does it outperform the old plan?
If yes (e.g., 82% -> 84% overall success), accept m_t+1 = m_candidate.
If no (e.g., 82% -> 81%), reject the update and m_t+1 = m_t (keep the old memory).
Result: performance is monotonically non-decreasing. It never falls.

The trust-region constraint is the key safety mechanism: by rejecting any memory update that would lower performance, the system can never get worse, even if bad updates are proposed.

What can go wrong

What can go wrong

Warmup tasks do not match real tasks. If the test questions are too easy or too specific, the router learns a misleading profile. For example, if warmup tasks only test the agent on toy problems, but real tasks are much harder, the router will over-trust the agent and assign it unsuitable work.
The agent is nondeterministic or its reliability varies over time. If the agent's success rate drifts (e.g., an external API becomes flaky), the memory based on past warmup tasks goes stale. The router will not automatically re-learn.
Too many agents in the pool exceed routing capacity. The paper focuses on small pools (up to 10 agents in main experiments). Real systems have thousands of agents. The approach assumes you can afford to run warmup tasks for each new agent; scaling to massive pools may require retrieval-driven routing (finding a small candidate set first).
Done right. Use task customization to generate warmup problems that match the kinds of tasks the router will see in real use and expose edge cases. Invest in readable memory so humans can inspect and correct the profiles. Use trust-region updates as a safety check: never accept a memory change that hurts. Periodically re-probe agents whose reliability is uncertain or has drifted.
What a runnable demo should prove

What a runnable demo should prove

Build a multi-agent system with a router and a small team (4-6 agents). Some agents are reliable; some are deliberately flaky (e.g., one fails randomly 40% of the time, another only works on specific task types). Implement the MonoScale expansion step: (1) add a new agent to the pool, (2) generate tailored warmup tasks for it, (3) run the warmup and record success/failure, (4) distill findings into a simple readable memory, (5) apply a trust-region check before updating the router, (6) measure the system's overall task-success rate before and after. Plot the performance line: it should stay flat or rise, because each new agent was tested first and memory was only updated if it improved results.

performance_improvement = (success_rate_after - success_rate_before) >= 0

Visually compare performance drop with and without MonoScale. Without: collapse after adding new agents. With: flat or rising performance because each new agent goes through warmup and is tested before integration.
