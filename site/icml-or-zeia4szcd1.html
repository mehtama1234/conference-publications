TapSampling: Inference-Time Sampling with a Task-Progress-Understanding Verifier

When a robot model picks actions, generate multiple choices and pick the one most likely to succeed, without retraining.

Paper explainersAll themesRobotics & Control

Generative models used in robotic control can produce many different actions for the same situation. Most systems pick just one at inference time (the moment the robot acts). This paper shows that by exploring multiple action options and choosing wisely, you can get better performance without ever changing the model weights.

Zero assumption version

Why picking one action at inference time is stuck

Generative models (models that produce new outputs like diffusion or models that build output one piece at a time) can naturally generate many different valid actions for the same robot state. When you ask such a model what action the robot should take next, it does not give a single answer — it gives you one sample from the full range of plausible answers.

Today's robotic systems take that one sample and use it immediately. One sample is a lottery: you might pick the right action, but you might pick a mediocre one. If the model generated five good action options and a verifier selected the highest-scoring one based on estimated task progress, you would do better, because verifier-based selection is more likely correct than random draw.

The naive approach — just run the policy multiple times and average the results — fails because averaging unaligned actions (a grasp from the left plus a grasp from the right) creates garbage; you need to pick a single winning action, not mush them together.

If you have five good action options and a system that picks the best one, you perform better than picking randomly, because selection eliminates luck: five good guesses plus a perfect picker beats one random guess every time.

The paper's move, one sentence. Generate multiple action candidates using a learned compact action space, then score each one by predicting whether it will succeed, and pick the highest-scoring action.

The algorithm as a flow

What it actually does

Compress actions into a small space

An Action-VAE (a learnable encoder-decoder) maps all raw actions down to a compact set of numbers, then back up to actions.

Sample the compact action space

Draw many samples from the learned compact representation; decode each to a full action candidate.

Score each candidate

A verifier model, trained on robot videos, predicts task progress (whether this action moves toward the goal).

Select the best

Keep only the action with the highest predicted task progress; discard the rest.

No retraining needed

The original policy, the Action-VAE, and the verifier all stay frozen; this is a pure inference-time strategy.

What the paper changes

What the paper changes

The paper changes the action selection step at inference time. Instead of accepting the first sampled action, it generates multiple candidates from the compact action space and picks the one most likely to succeed.

The hidden quantity

Task progress: the silent ingredient

measured quantity  =  Task progress (chance an action moves toward the goal)

The verifier learns a hidden quantity: for any action in a given state, what is the likelihood that taking it will move the robot closer to its goal? This is not the same as accuracy or reward; it is a forward-looking prediction of incremental progress. The paper calls this task-progress outcome prediction.

The verifier is trained directly on robotic videos using the sequential structure already present in the data: if frame A comes before frame B in a successful trajectory, the action linking them moved toward the goal. This grounds the verifier in what actually happens in the robot's world, making it interpretable (you can see which actions the verifier trusts).

Why it works

Why generating and selecting actions works

Generative models produce a distribution of actions because the world is ambiguous — many actions can work. The policy learned this distribution from training data. By sampling from it multiple times, you get different valid options, not repeats of the same choice. A single sample might be mediocre; multiple samples include at least one good candidate.

But you need a way to tell them apart. A verifier trained on trajectories (action sequences over time) learns which actions lead forward. It does not need the policy to be retrained; it just needs to score candidates. This scoring is cheap at inference time: one forward pass per candidate, then pick the max.

The compressor (Action-VAE) helps by mapping a high-dimensional raw action space into a tight distribution. Sampling from that compact space is more efficient, because you draw only from the region where the policy actually operates (not random points in the high-dimensional space), and this keeps candidates in the valid region where the policy worked well during training. Fewer bad candidates means the verifier's job is easier: it only scores plausible actions.

Math after the picture

The verifier scoring equation

First in words:

For each candidate action, the verifier predicts task progress as the dot product of the action embedding and a learned progress direction vector, then passes the result through a sigmoid to get a probability between 0 and 1.

Then the compact form:

p_i = sigmoid(w_progress * enc(a_i))

Every symbol:

p_ipredicted task progress of candidate action i (0 to 1, where 1 means moves toward goal)
a_ithe i-th candidate action
enc(a_i)learned embedding of that action (a list of numbers)
w_progresslearned vector that points in the direction of task progress
sigmoidfunction that squashes any number into the range 0 to 1
A tiny worked example
Suppose enc(action_1) = [0.5, -0.2] and w_progress = [2.0, 1.0], sigmoid acts at 0.5.
Dot product: 0.5 * 2.0 + (-0.2) * 1.0 = 1.0 - 0.2 = 0.8
Sigmoid(0.8) ≈ 0.69, so action_1 has 69% predicted task progress.
For action_2: enc(action_2) = [-0.3, 0.1], dot product = -0.3 * 2.0 + 0.1 * 1.0 = -0.6 + 0.1 = -0.5
Sigmoid(-0.5) ≈ 0.38, so action_2 has only 38% predicted task progress.
System picks action_1; the verifier learned to recognize productive actions.

The verifier ranks actions by how well they align with a learned direction of progress, and the system picks the top-scoring candidate.

What can go wrong

What can go wrong

Verifier overfits to demonstrations. If the verifier is trained only on successful trajectories and sees out-of-distribution actions at test time, it may misjudge them. The fix: train on a diverse set of trajectory outcomes (successes and near-misses), not just clean successes.
Action-VAE collapses to a point. If the encoder maps all actions to the same compact representation, sampling from that space yields near-duplicate candidates, defeating the diversity goal. The fix: use standard VAE regularization (a penalty term in the training loss) to keep the compact representation spread out across the space.
Computational cost at inference time. Generating and scoring N candidates costs N times more computation than a single-shot policy. If N is large or the verifier is slow, inference becomes impractical. The fix: balance N and verifier efficiency; the paper likely tests small N (5–10).
Done right. Train the verifier on diverse, well-labeled trajectory data; keep the Action-VAE compact representation spread out via regularization; and tune the number of samples to balance quality and speed.
What a runnable demo should prove

What a runnable demo should prove

A demo should show a robot (simulated or real) performing a manipulation task. First, run the policy alone once and record the outcome (success or failure). Then, run TapSampling with 5 candidate actions and show that the verifier's chosen action succeeds more often. The demo should include a side-by-side visualization: the baseline action, the 5 sampled candidates with their verifier scores, and the final action executed. Make clear that only the verifier scores change at inference time; no model weights are adjusted.

improvement = success_rate_with_TapSampling - success_rate_baseline

The demo must show that the same policy and verifier, applied to the same task, achieve higher success by exploring multiple actions and picking the best.
