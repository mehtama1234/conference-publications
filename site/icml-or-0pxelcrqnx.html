Cross-Domain Log Anomaly Detection via Flow Matching

A log-anomaly detector trained once on many systems uses flow matching to ask whether each log came from the normal pattern, protecting shared knowledge while respecting domain differences.

Paper explainersAll themesTime Series & Sequential

When a data center runs many different systems (database, web server, storage), their logs speak different languages but share a common idea: anomalies are rare, normal operation is repetitive. Instead of training a separate anomaly detector for each system, you want one model that works across all of them. The challenge: forcing their patterns into one mold breaks the model (a behavior normal in system A might be suspicious in system B), and just measuring distance to the normal cluster misses anomalies that hide near the edge.

Zero assumption version

Why a single cross-domain log detector is hard

A log is a sequence of events: each line records a timestamp, an action, and maybe an error code. In a working system, logs follow patterns (database checkpoints every hour, user login attempts cluster in business hours). Anomalies break these patterns: a sudden spike in errors, a forbidden access, a cascade of restarts. A security team wants to catch anomalies across all their systems at once, with one trained model, to save cost and effort.

The obvious approach: collect logs from all systems, mark what is normal, train a detector. But this fails. First, normality looks different on each system: a buffer timeout that is routine in system A is a red flag in system B. Forcing all systems into the same distance metric creates noise — normal logs from system B look like outliers. Second, the distance-to-normal-cluster approach is too simple: anomalies sometimes hide near the cluster edge (a small but wrong deviation), and the detector misses them.

The method in one sentence. MPFM trains one model on logs from many systems by learning what normal generation looks like (shared knowledge), respecting how each system differs (private knowledge), and asking whether each log could plausibly have been generated by that system's normal process.

The algorithm as a flow

What it actually does

Shared-private split

Learn what log patterns all systems have in common (shared) and what each system does uniquely (private).

Flow matching setup

For each system, build a path from random noise to real normal logs, guided by both shared and system-specific knowledge.

Generation: noise to log

To score a log, gradually transform it backward into noise; count steps needed and how much effort.

Anomaly decision

High effort (hard to generate) means anomaly; low effort (flows naturally) means normal.

Hard-example mining

Focus training on logs near the boundary so the detector catches subtle anomalies.

The hidden quantity

The named hidden quantity: plausibility

measured quantity  =  log plausibility score

Plausibility is a single number measuring how easily a log could be generated by the normal process. A log is plausible if the model, following the shared and system-specific patterns it learned, can smoothly transform it from noise in a short path and without fighting the learned dynamics. An anomaly is implausible: the model struggles to construct it, needing many steps or fighting against what it learned normality looks like.

The paper estimates plausibility by running the reverse process: starting with the real log, step-by-step corrupt it toward noise, measuring how well the learned flow predicts each corruption. High prediction accuracy (the model saw this pattern coming) means plausible; low accuracy (the model is surprised) means anomalous.

Why it works

Why flow matching catches cross-domain anomalies

Flow matching works by learning a smooth path from noise to real data. For logs, the path says: start with random noise, apply the shared log grammar (add typical event types, timing structures), then the system-specific flavor (add this system's error rates and recovery patterns), and you get a real log. Anomalies cannot follow this path smoothly because they violate either the shared or system-specific assumptions.

Flow matching is better than distance because it checks both the numbers and the structure. Distance alone treats all deviations equally; an anomaly very close to the cluster edge appears normal. Flow matching instead asks about the deep structure: can you construct this log using what the model learned about normality? If a log has an impossible event sequence (events that never co-occur) or a system-impossible error pattern, the flow gets stuck and the model struggles because it was never trained on such sequences. This struggle shows up as high prediction error, revealing the anomaly. Distance methods have no way to detect this structural impossibility; they only see the numerical distance.

Most importantly, the shared-private split prevents negative transfer. The shared part learns universal log structure (restarts, logins, errors happen). The private part learns that system A tolerates buffer timeouts but system B does not. When training on system A's data, the shared part sees normal buffers and does not penalize them; the private part learns they are system-A-normal. When testing system B, the private part knows buffer timeouts are B-anomalous even if the shared part saw them before.

The flow-matching equation

First in words:

The plausibility score sums the prediction errors across all steps of the reverse flow, weighted by how much each step changes the log. High weight on steps where the model struggles means the overall score is low (anomalous); low weight on confusing steps means anomalies near the edge still score low because those edge steps are emphasized.

Then the compact form:

plausibility = -sum_t w_t * ||z_t - z_theta(x_t, t, s)||^2 + lambda * (shared_loss + private_loss)

Every symbol:

z_tactual noise added at step t in reverse
z_thetanoise predicted by the learned model at step t
x_tthe partially-corrupted log at step t
twhich step in the reverse process (0 to T)
sthe system ID (shared A, B, or C)
w_tstep weight (emphasizes hard steps near decision boundary)
lambdabalance between flow matching and prototype learning
shared_lossloss on shared pattern reconstruction
private_lossloss on system-specific anomalies during training
A tiny worked example
Assume 3 steps in reverse (T=3) with weights w = [1.0, 2.0, 1.5].
Step 1 (t=0): model predicts noise perfectly, error = 0.0. Contribution: 1.0 * 0 = 0.0.
Step 2 (t=1): model is confused by a rare error pattern, error = 0.4. Contribution: 2.0 * 0.4^2 = 0.32.
Step 3 (t=2): model recovers, error = 0.1. Contribution: 1.5 * 0.1^2 = 0.015.
Total plausibility = -(0.0 + 0.32 + 0.015) = -0.335. A normal log might score -0.05; this log is anomalous.
High weight on step 2 ensures the model is sensitive to rare patterns, catching anomalies that hide in common backgrounds.

The sum of prediction errors measures whether the model's learned flow path fits the real log; high errors mean the log is implausible.

What can go wrong

What can go wrong

Over-generalizing shared knowledge. If the shared part tries to explain away system-specific patterns as universal, it oversmoothes the model. A timeout that is normal in system B might get absorbed into shared knowledge, making the private part ineffective. Fix: weight the shared loss moderately so system-specific signals survive.
Negative transfer when domains are very different. If one system's anomalies (e.g., high error rates) look normal in another, the shared part confuses training. The model learns that high errors are normal, ruining performance on both. Fix: ensure the private part has enough capacity to override shared knowledge for system-specific cases.
Anomalies that mimic normal variation. Some anomalies are subtle (a legitimate error that happens slightly more often than usual). Plain flow matching might score them as plausible if they stay within the learned distribution. Fix: use hard-example mining during training to emphasize boundary cases.
Done right. When the shared part learns true universals (events, timeouts, restarts) and the private part captures genuine system differences, and boundary cases are given high training weight, the model catches both obvious and subtle anomalies across all systems.
What a runnable demo should prove

What a runnable demo should prove

Build a small synthetic log dataset: three systems (A, B, C) each with 100 normal logs (typical events, rare errors). Inject 20 anomalies into each (impossible event sequences, cascading errors, timing violations). Train MPFM on a mix of logs from all three systems. Measure how many anomalies it catches in each system compared to a baseline (simple distance classifier or a single-domain detector). The demo should show that MPFM catches similar anomaly rates across all three systems despite their different patterns, and catches more edge-case anomalies than distance-based methods.

anomaly_detection_rate = (true_anomalies_caught / total_anomalies) per system; improvement = MPFM_rate - baseline_rate

The key observation: a single model catches anomalies equally well in all three systems. This works because the shared part learns universal log structure (what all systems do), while the private part learns system-specific normality (what this system tolerates). Together they know what normal looks like in each system, so they catch anomalies in any system without confusion.
