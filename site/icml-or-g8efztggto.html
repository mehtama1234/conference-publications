DREAM: A Unified Framework for Drift-Corrected Federated Multi-Objective Learning

Train several conflicting objectives across many clients by correcting local update drift and by correcting task aggregation bias in one loop.

Paper explainersAll themesOther

Federated multi-objective learning trains one shared system from data that stay on many devices or organizations while serving several goals at once. Those goals can conflict: one task may push the shared model toward one direction while another task pushes back. The setting is harder than ordinary federated learning because two errors stack on top of each other. First, each client takes several local steps before syncing, so its update drifts away from the update that full central training would have produced. Second, the server must combine several task updates, and that combination can favor some tasks too much when their update directions, meaning the directions in model-weight space, disagree. DREAM treats both errors as one coupled problem. It stabilizes local training with drift-aware control variates, meaning stored correction terms that pull each client update back toward the shared reference, and it stabilizes server aggregation with a regularized quadratic program, meaning an optimization problem over a curved score with a penalty term, that chooses a compromise direction across tasks.

Zero assumption version

Why federated multi-objective learning drifts twice

Ordinary federated learning already has a mismatch between local and global training. A client computes several steps on its own data, so the model it returns is based on stale information about the rest of the system because other clients may have changed the shared model during the same round. That mismatch grows when client data are different from one another.

Multi-objective training adds another mismatch. The server is no longer averaging updates for one goal. It must combine several task-specific updates into one shared step, and a naive average can overreact to a task with a large update norm or can cancel useful progress when tasks disagree. The result is unstable training because local drift changes the task updates, and the changed task updates then distort the server's compromise.

The paper's move in one sentence. Correct client drift before aggregation, then solve a server-side compromise problem that knows each task update has already been bias-corrected.

The algorithm as a flow

What it actually does

Keep one correction term per client and task

Maintain a control variate for each client-task pair so local training can estimate how far its update has wandered from the current shared reference.

Run momentum-smoothed local updates

Each client takes local steps with smoothing over recent steps, because abrupt swings from noisy batches make the drift estimate harder to use and make cross-task conflict noisier at the server.

Return corrected task updates

Before sending updates back, subtract the stored drift estimate so the server receives task directions that are closer to what synchronized training would have produced.

Solve a regularized multi-task aggregation problem

The server combines the corrected task updates by optimizing a quadratic objective with a task correction matrix, meaning a table of numbers that adjusts how strongly each task interacts with each other task.

Broadcast the shared step and refresh corrections

Update the global model, then refresh the control variates so the next round starts from a corrected reference instead of letting the same drift accumulate again.

What the paper changes

What the paper changes

The paper changes the unit of correction. It does not treat client drift and task conflict as separate afterthoughts. It learns and aggregates task updates under a single drift-corrected view, so the server solves the compromise problem on cleaner inputs.

the object it moves  =  drift-corrected shared update for federated multi-objective training
The hidden quantity

The hidden quantity

measured quantity  =  the corrected task compromise direction that would remain after removing local client drift

The server never directly sees the ideal joint update. It only sees client-produced approximations after several local steps. The important hidden quantity is therefore not the raw average update. It is the shared step that would have been chosen if each task update had been measured without local drift.

DREAM estimates that quantity in two stages. The client-side correction terms try to recover cleaner task directions, and the server-side quadratic program chooses a compromise among those corrected directions. This split matters because correcting only the clients still leaves unresolved task conflict, while correcting only the server still mixes in biased client updates.

Why it works

Why the two corrections belong together

Client drift and aggregation bias feed each other. If a local client overshoots, the task update that reaches the server is already distorted. When the server then tries to balance tasks, it is balancing partly wrong directions. That can assign too much weight to one task or create false conflict between tasks that would have aligned under synchronized training.

Control variates matter because they reuse information from earlier rounds to estimate repeatable local bias. That estimate does not need to be exact on every batch. It only needs to remove enough of the systematic drift that the returned task directions are closer to the shared reference.

The quadratic aggregation step matters because corrected task directions still conflict. The task correction matrix lets the server encode how strongly one task should count against another when their directions disagree. The regularization term matters because it prevents the solver from chasing one sharp task direction too aggressively, so the shared step changes more steadily from round to round.

Math after the picture

The server aggregation objective

First in words:

choose task weights that produce a low-conflict shared update while staying close to a stable reference

Then the compact form:

min_w (1/2) w^T C w - g^T w + lambda ||w||^2

Every symbol:

wthe weights assigned to the task updates at the server
Cthe task correction matrix that measures how task directions interact
gthe vector of corrected task gains from the client updates
lambdathe regularization weight that penalizes unstable or extreme task weights
A tiny worked example
Suppose task 1 and task 2 both improve the global model, but their directions partly disagree.
If raw gains are 8 and 6, a naive average may weight them equally and ignore the disagreement.
If the correction matrix says the two tasks strongly interfere, the optimizer may choose weights such as 0.6 and 0.3 instead of 0.5 and 0.5.
If the regularization weight is larger, the chosen weights move less from one round to the next.
The final shared step is smaller than a raw average, but it is less distorted by conflict and less sensitive to noisy local drift.

The exact quadratic form is a server-side way to turn corrected task directions into one stable compromise update.

What can go wrong

What can go wrong

The correction terms can go stale. If the global model changes too much between rounds, an old control variate may subtract the wrong bias. That creates a second error instead of removing the first one.
The task correction matrix can encode the wrong conflict pattern. If task interaction is estimated poorly, the quadratic program can downweight a task that is actually useful, because the server believes the task conflicts more than it really does.
Very uneven client data can dominate the round. If one group of clients has highly unusual data, their corrected updates may still point away from the rest. The framework reduces systematic drift, but it does not remove every source of population imbalance.
Done right. Refresh the control variates often enough, check whether task conflict estimates match observed training behavior, and keep local step counts moderate so the server is not trying to correct very long unsynchronized trajectories.
What a runnable demo should prove

What a runnable demo should prove

Build a toy federated system with several clients, two or three conflicting tasks, and different client data mixtures. Compare four variants: plain federated averaging, drift correction only, task aggregation correction only, and the combined DREAM pipeline.

Track local drift size, angle disagreement between task updates, and final task scores after each communication round. The demo should show that the combined method works because it removes repeated local bias before the server solves the cross-task compromise.
