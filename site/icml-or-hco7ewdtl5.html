SorryDB: Real-World Lean Theorem Proving Benchmark

SorryDB is a living, community-driven benchmark of real Lean theorems from actual projects, not competition puzzles, that catches when AI provers learn the test set instead of learning to prove.

Paper explainersAll themesDatasets & Benchmarks & Evaluation

Lean is a programming language for writing mathematical proofs where every step is checked by a machine. Teams of mathematicians use it to formalize real theorems in shared projects on GitHub. But most benchmarks that test AI provers use old puzzle-like competition problems. SorryDB is different: it is a constantly-updated collection of genuine Lean tasks pulled directly from live community projects, updated as mathematicians add new theorems. This matters because AI provers trained on static puzzles often memorize the exact set, so their scores do not mean they can help with new real theorems.

Zero assumption version

The trap of frozen test sets

When researchers build a benchmark (a test of how good your AI is), they usually fix it once and never change it again. This works fine if your metric is about accuracy on a single fixed task, like image classification. But for theorem proving, this creates a hidden trap: an AI prover team might spend months training their model to pass that exact benchmark. They will optimize every detail to score high on those 1000 specific theorems. Their score goes up. Everyone celebrates. But they have not actually learned to prove new theorems — they learned to recognize and solve the 1000 puzzles in the benchmark.

Meanwhile, mathematicians working in Lean are formalizing brand new theorems in real projects every month. These new theorems use complex dependencies on earlier proofs and handle edge cases the old benchmark never saw. When the prover team tries to help with these real theorems, their tools fail, because the model was never trained on proofs with these particular structures and dependencies. The benchmark score was meaningless.

In one sentence. SorryDB pulls real Lean tasks from live GitHub projects and updates them constantly, so AI provers cannot cheat by memorizing a frozen test set.

What the paper changes

The one thing that changed

Instead of using a fixed benchmark, SorryDB uses a living, constantly-updated collection of real Lean tasks pulled from active GitHub projects. Every month, the benchmark refreshes: old proofs that mathematicians completed are marked done, and new incomplete proofs from the projects are added.

the object it moves  =  the benchmark source: from frozen puzzles to live community projects
The hidden quantity

How much reasoning versus memorization

measured quantity  =  Memorization resistance: immunity to test-set contamination

The hidden quantity is how much an AI prover's score comes from genuine reasoning versus from having memorized the exact benchmark. In a frozen benchmark, this quantity starts high for memorization (bad) and low for reasoning (good). Over time, as teams optimize, memorization creeps up and reasoning stagnates. But in a constantly-refreshing benchmark, memorization becomes impossible. Every time a team trains their model, half the test set has changed. So a high score can only come from reasoning.

SorryDB estimates this by checking: when a prover is tested on new tasks added since the model was trained, does its accuracy drop sharply (meaning the model memorized the old set) or hold steady (meaning it genuinely reasons)? A steady score on new tasks is the paper's proof that memorization did not happen.

Why it works

Why a moving target catches cheaters

The mechanism works like this. In a frozen benchmark, a team can memorize the entire test set through brute-force optimization. They try millions of small changes to their model, measure the score on the fixed 1000 tasks, and keep changes that raise it. After months, the model is perfectly tuned to those exact tasks. Its weights contain patterns that say 'if you see a theorem with these exact symbols and this exact structure, output this exact proof.' But the model never learned how to generalize to new theorems.

SorryDB breaks this by updating the benchmark. When the team retrains and retests next month, 30% of the benchmark is new. Their memorized patterns no longer match. The only way to maintain a high score is to have learned the underlying reasoning skill: understanding what a Lean proof is, how to decompose a goal, which tactics work in which contexts, and how to search for a valid path through the proof space.

This is why SorryDB claims its scores reflect community needs and actual capability. A high score on a constantly-moving benchmark proves the model generalized, not that it memorized.

Measuring memorization resistance

First in words:

contamination_score = accuracy_on_new_tasks / accuracy_on_old_tasks

Then the compact form:

R = Acc_new / Acc_old

Every symbol:

Rmemorization resistance (1 means perfect generalization, 0 means total memorization)
Acc_newaccuracy on tasks added after the model was trained
Acc_oldaccuracy on tasks that existed when the model was trained
Acc_new ≈ Acc_oldmeans the model learned to reason, not memorize
A tiny worked example
Old benchmark (500 tasks): Model trained on these, scores 80 out of 100 correct.
Model retrained once.
New tasks (250 fresh tasks from new projects): Model scores 75 out of 100.
Resistance = 75 / 80 = 0.94. Nearly equal scores mean the model did not memorize — it reasoned.
Contrast: if model had memorized, new-task score would drop to 20, giving 20/80 = 0.25 (low resistance, high contamination).

When the ratio is high (close to 1), the model generalizes. When it drops (near 0), the model memorized the old set.

What can go wrong

What can go wrong

Dependency hell. A Lean task depends on a theorem from an earlier proof. If that earlier theorem changes or is deleted, the task breaks. SorryDB must track and update dependencies constantly.
Overfitting to the theme pattern. If mathematicians add many new tasks in one narrow area (e.g., group theory) but few in others, the benchmark skews. A prover can score high by becoming expert in the dominant theme without learning breadth.
Proof-completion lag. When a 'sorry' task is completed by a mathematician, SorryDB must detect it, verify it, and mark it resolved. Delays cause stale tasks to remain in the benchmark.
Done right. Regular automated scans of GitHub projects, versioned snapshots of the benchmark with resolved proofs clearly marked, and balanced representation across proof themes keep the benchmark clean and useful.
What a runnable demo should prove

What a runnable demo should prove

Build a simple Lean 4 theorem-proving agent (even a greedy one that picks the most common tactic at each step). Train it on a snapshot of 500 SorryDB tasks. Then test it on: (1) the same 500 old tasks, and (2) 100 new tasks added to SorryDB the next week. Measure accuracy on both.

generalization = accuracy_on_new / accuracy_on_old

If generalization is close to 1, your agent learned to prove. If it drops sharply, your agent memorized the old set. SorryDB's power is that you cannot hide this difference.
