FlyPrompt: Brain-Inspired Expert Routing for Learning Without Task Boundaries

The paper copies the fruit fly's brain architecture to route new information to the right expert module without knowing where task boundaries are.

Paper explainersAll themesRepresentation & Self-Supervised Learning

When you learn from a stream of data without knowing where one task ends and another begins, you face two problems: how to decide which adaptation expert should handle each piece of data, and how to prevent old experts from forgetting when the data shifts. FlyPrompt solves this by mimicking the fruit fly's brain — using random projections to route information forward-only to the right expert, and temporal averaging to keep the expert's decision boundaries honest as new data arrives.

Zero assumption version

Learning from an endless stream without task labels

A pretrained model (a neural network trained on massive amounts of data beforehand) has a frozen backbone — a fixed feature extractor. When new data arrives in a stream, you cannot retrain the backbone, only add lightweight adapters on top (small parameter packs like prompt prefixes). Your job: adapt these small modules to classify new data correctly.

The catch: the data stream never tells you when one task ends and another begins. Old data might be pictures of birds, then suddenly cars, then dogs again — mixed, with no announcement. Worse, one shared output head keeps adapting to all new data, slowly drifting away from the representation space that early adapters carved out.

Naive approach: use a learned router (a small network that predicts which expert to use). But learning a router requires clear task labels or many passes through the data — both unavailable in a real stream. Existing routers trained this way misroute about 20-30% of inputs, and their mistakes cause cascading forgetting in the experts they mistarget.

In one sentence. Use fixed random projections to route without learning, and average the output head over time to keep it aligned with each expert's frozen features.

The algorithm as a flow

What it actually does

Fixed random projection

Apply a predefined random matrix to the input embedding — no weights to learn.

Closed-form routing

Use simple algebra to solve which expert's stored statistics best match the projected input.

Forward pass

Send data through the chosen expert's trainable adapter and classifier head.

Blend the head

Update the classification head as a weighted average of old and new weight updates.

Repeat

New batch arrives; router assigns it again without knowing where task boundaries are.

What the paper changes

What the paper changes

FlyPrompt replaces the learned router (a trained network that takes many passes to get right) with a random projection router — fixed weights that never update. It also replaces a single shared classifier head with a time-weighted blend of per-expert heads, each one frozen after training and then warmed as new data hits the expert.

the object it moves  =  routing gate and output head
The hidden quantity

The routing confidence

measured quantity  =  routing alignment (how well a projection matches an expert's data pattern)

The routing confidence is the score that measures whether a random projection places the current input in the right expert's region. It is computed as a simple inner product: the projected input dot the expert's stored statistics (mean of all projected inputs from that expert's training). High scores mean aligned; low scores mean misaligned.

The paper estimates this on-the-fly during inference: project the input, compute its dot product with each expert's stored mean, pick the expert with the highest score. The paper proves this closed-form solution is optimal when the goal is to minimize misrouting error, and the random projection is chosen from a standard distribution (uniform random rotation).

At inference, the score for expert m on input x is the inner product of the fixed random projection of x with the stored mean of that expert's projected training data.
Why it works

Why it works: the two moves

The first move: random projections are stable and fast because they never change. Unlike a learned router that needs weight updates flowing backward through training data, a fixed random matrix can route instantly. The fruit fly's brain does this too — its sparse expansion circuit uses random synaptic weights that are genetically fixed. The projection space is high-dimensional (many random features), so different task data patterns naturally separate into different regions, and a simple dot product can find the right one. This works in closed form: just solve a linear equation once per expert per task, not iteratively.

The second move: temporal ensemble on the output head decouples the head's drift from the features. A normal approach trains one head for all experts, so as new tasks come, the head keeps shifting to match the latest data — forgetting how it should work with early adapters. FlyPrompt instead keeps each expert's output head separate and updates it as a blend: the head weights are mostly the old weights, with a tiny mix of the new weight update (exponential moving average with a blend factor staying near 1, like 95% old and 5% new). When a new batch arrives, the head shifts only a little, never abandoning the decision boundary it learned from the expert's frozen features. The fruit fly's mushroom body does this too, maintaining separate memory traces that update gradually.

Math after the picture

The routing and head-blending equations

First in words:

For each incoming batch, compute the projected features. Build a router matrix that maps each task's projected data to its expert. At inference, route an input to the expert with highest dot product between its projection and that expert's stored mean projection. Update each expert's head by blending old and new weights with an exponential moving average.

Then the compact form:

route_score_m = projected_input · mean_m ; selected_expert = argmax(route_scores) ; new_head_t = alpha_t × old_head_t + (1 - alpha_t) × head_update

Every symbol:

projected_inputthe input after fixed random matrix multiplication
mean_mthe average of all projected inputs seen by expert m
alpha_tthe blend factor for expert t (0.9 to 1.0, close to 1 = slow change)
head_updatethe gradient-based update from this batch's predictions and targets
A tiny worked example
Expert 1 saw birds; its stored mean is [0.6, 0.8]. Expert 2 saw cars; mean is [0.2, 0.1]. New input projects to [0.55, 0.75].
Route score for Expert 1: 0.55×0.6 + 0.75×0.8 = 0.33 + 0.60 = 0.93.
Route score for Expert 2: 0.55×0.2 + 0.75×0.1 = 0.11 + 0.075 = 0.185.
Expert 1 wins (0.93 > 0.185). Input goes to Expert 1, correct (input is closer to bird features).
Expert 1's head: old = [0.9, 0.2], weight update says [0.1, 0.05], alpha = 0.95.
New head = 0.95 × [0.9, 0.2] + 0.05 × [0.1, 0.05] = [0.855, 0.19] + [0.005, 0.0025] = [0.860, 0.1925]. Tiny shift, head stays aligned.

The dot product measures similarity in the random projection space. The moving average keeps the head stable as new data arrives, because alpha stays near 1.

What can go wrong

What can go wrong

Random projection dimension too small. If the random projection has too few dimensions, different task distributions may overlap, and routing becomes ambiguous. You need enough dimensions that each task's data occupies a distinct region. The paper uses projection to about 2000 dimensions for ViT embeddings.
Exponential moving average blends away real shifts. If alpha (the blend factor) is too close to 1, the head barely updates, and it can miss genuine changes in the task distribution. Too close to 0, and it forgets old tasks. The paper uses per-expert alpha values tuned on a held-out validation stream.
Experts become imbalanced. If many early tasks get routed to the same expert, that expert's head sees far more data than others. Its statistics dominate, and later tasks get misrouted. The paper handles this by re-balancing the router matrix periodically.
Done right. Use high enough random dimensions, tune alpha per expert on a small validation set from each task, and monitor routing accuracy in a sliding window. These prevent catastrophic failure.
What a runnable demo should prove

What a runnable demo should prove

Take a standard benchmark like CIFAR-100 where you can synthetically remove task labels: arrange 100 image classes into a stream (birds first, then vehicles, then animals, etc.). Split into 10 experts. Run FlyPrompt with fixed random projections and temporal ensemble heads. For comparison, run a learned router baseline. Measure: (1) routing accuracy on held-out test data (what fraction of inputs go to the right expert?), (2) old task accuracy (can early experts still classify birds correctly after cars arrived?), and (3) new task accuracy (can later experts classify new classes?). FlyPrompt should route correctly 85%+ of the time, retain 85%+ of old task accuracy, and reach 80%+ on new tasks — while the learned router drops to 70% routing and 65% old-task retention.

routing_accuracy = (inputs routed to correct expert) / (total inputs) ; old_task_retention = old_task_accuracy_after - old_task_accuracy_before ; forgetting = max(0, old_task_accuracy_before - old_task_accuracy_after)

The demo must make it impossible to ignore: no task labels were given, the router never learned anything, yet the random projection routed correctly most of the time. That is the power of using a fixed random structure that naturally separates different types of data.
