Guiding Queries to the Right Client in Federated Learning

Instead of always averaging models across hospitals, learn which hospital is best for each new patient.

Paper explainersAll themesLearning Theory

Federated learning lets hospitals train a shared model without sending patient data to a central server. But hospitals have different patient types, so averaging the models works poorly. This paper asks: what if the central server learned to do two things at once: train good local models AND figure out which hospital should handle each new patient? That is the real problem federated learning has been missing.

Zero assumption version

Hospitals have different patients, but standard methods average their models anyway

Imagine five hospitals training a shared model to diagnose diseases. Hospital A treats a lot of cancer patients. Hospital B treats a lot of heart patients. If you average their models into one, the average model is mediocre for both groups—it is trying to solve two different problems at once, so it is not expert at either.

The standard approach is to just accept this and aggregate anyway. But that is not how hospitals actually work. A new patient arrives, and a skilled triage nurse asks: which specialist is best for this patient? The same logic applies to federated learning: a new query comes in, and the central server should ask: which hospital's model will work best?

In one sentence. The server learns to route each new query to whichever client has learned the most about that type of problem.

What the paper changes

What the paper changes: routing logic at the server

Standard federated learning treats the server as a passive aggregator—it simply averages model weights from all clients. This paper changes that. The server now learns an active routing function that scores each incoming query against the patterns it sees in each client's data and picks the best match.

The hidden quantity

The hidden quantity: density ratio for each client

measured quantity  =  Density ratio: how much each client's data stands out

A density ratio is a number that tells you: is this new data point more likely to have come from Client A or Client B? It is like a fingerprint of each hospital's patient population. The paper learns one density ratio per client by measuring how each client's model fails in a particular way—the pattern of errors reveals the underlying patient population.

Concretely, the server observes: which samples does Hospital 1's model misclassify? Which does Hospital 2 misclassify? The pattern of misclassifications is a window into each hospital's actual patient mix. The density ratio model learns to predict: given a new patient's features, are they more likely from Hospital 1's patient type or Hospital 2's patient type?

Plain reading. A density ratio is how likely a new data point is to belong to one group versus another, based on a fingerprint of each group's data pattern.
Paper reading. The density ratio model is a semiparametric estimator trained by maximizing measured likelihood—a probability model that assigns weights to observed samples without assuming they fit a standard pattern.
Why it works

Why learning a density ratio solves the routing problem

Data from different clients (hospitals) has different shapes. If Hospital A treats mostly cancer and Hospital B treats mostly heart disease, their data has different fingerprints. A density ratio model is trained to recognize those fingerprints.

Here is the chain: (1) The server initializes a backbone model (a feature extractor—a neural network that turns raw data into a list of numbers) and client-specific heads (one classifier per hospital). (2) During training, each hospital computes nudge directions on its own data and sends them back, but the server does not blend them blindly. Instead, the server learns a density ratio—a function that predicts: how likely are these features to come from Hospital 1 versus Hospital 2? (3) When a new query arrives, the server runs it through the shared backbone to extract features, then passes those features through the density ratio model. The density ratio outputs: Hospital 2 is a 95 percent match. (4) The server picks Hospital 2's classifier and uses that to answer the query. (5) Why does this work? Because the density ratio learned the fingerprint of each hospital's patient type by observing which kinds of mistakes each hospital makes. A high mistake rate on certain feature types tells the server: this hospital sees different kinds of patients than the others.

Math after the picture

One equation that captures the core idea

First in words:

The method minimizes a combined loss: a prediction loss for each hospital's local model, plus a client classification loss that learns to route queries. The two components are weighted by a trade-off parameter lambda.

Then the compact form:

total_loss = (1 - lambda) * prediction_loss + lambda * routing_loss

Every symbol:

prediction_lossHow wrong each hospital's local model is on its own patients
routing_lossHow wrong the density ratio is at predicting which hospital a sample came from
lambdaA weight (between 0.5 and 1) that controls how much the server should focus on routing versus local accuracy. Higher lambda means spend more effort learning to route.
A tiny worked example with two hospitals
Hospital 1 prediction loss: 0.4 (model is somewhat wrong on local patients)
Hospital 2 prediction loss: 0.3 (model is better on its patients)
Routing loss: 0.5 (the density ratio still confuses some queries between the two)
With lambda = 0.7: total = (1 - 0.7) * ((0.4 + 0.3) / 2) + 0.7 * 0.5 = 0.3 * 0.35 + 0.7 * 0.5 = 0.105 + 0.35 = 0.455
The server back-propagates this loss: push down prediction errors (the 0.35 part) AND push down routing mistakes (the 0.5 part).
Over time, both the local models and the routing function get better.

The trade-off parameter lambda lets you choose: do you want each hospital to be a specialist (low lambda) or the server to be really good at routing (high lambda)?

What can go wrong

What can go wrong

Hospitals with very similar patients. If Hospital 1 and Hospital 2 treat the same patient type, the density ratio cannot distinguish them, so routing breaks down. The method works only when there is real heterogeneity.
A rare disease arrives. If a new query represents a patient type no hospital has seen much, the density ratio will be weak at all hospitals. Routing will still pick the best fit, but the absolute accuracy may drop.
Imbalanced client sizes. If one hospital has 1000 patients and another has 10, the density ratio learns more about the large hospital. The routing function may favor the large hospital even when the small one specializes in a different population.
Done right: heterogeneity is clear. When hospitals do treat genuinely different patient types (one oncology, one cardiology, etc.), the density ratio learns sharp fingerprints and routing becomes highly accurate.
What a runnable demo should prove

What a runnable demo should prove

A minimal demo would split a medical image dataset (e.g., retinal images for diabetic retinopathy) across three clients where each client's data has a different label distribution: Client 1 has mostly healthy patients, Client 2 has mostly diseased patients, Client 3 has a 50/50 mix. Train FedDRM and a baseline standard federated learning method for the same number of rounds. At the end, take 100 test samples and route each one using the density ratio. Measure two metrics: average accuracy (did the routed model get the answer right) and routing precision (did the density ratio pick the right client).

routing_accuracy = fraction of test samples routed to the client with the best model

The demo must show that FedDRM routes most queries to a client that specializes in that query type, while standard averaging has no way to do this—it can only use one global average.
