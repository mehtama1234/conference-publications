AutoWebWorld: Synthesizing Infinite Verifiable Web Environments via Finite State Machines

AutoWebWorld creates web training sites from explicit state graphs so every click can be checked automatically.

Paper explainersAll themesAgents & Tool Use

Web agents need large amounts of interaction data, but real websites hide their internal state. That makes step-by-step checking expensive because you usually need a person or a judge model to decide whether each action was correct. AutoWebWorld removes that ambiguity by generating web environments from explicit state graphs where the legal actions and goal states are written down ahead of time.

Why web-agent data is hard to verify

A web agent learns by trying actions on pages such as search, checkout, or account settings. On a real site, the true page state is hidden inside the site's code and backend. From the outside you only see pixels, text, and button labels.

That hidden state creates a data bottleneck. You can record trajectories, but it is hard to know whether each click was correct, whether the page changed for the right reason, and whether the task is truly complete. Verification becomes slow and expensive because each step needs an external judge.

The paper's move in one sentence. Write the site as an explicit graph of states and actions first, then generate the website from that graph so every action can be checked against the graph rules.

The algorithm as a flow

What it actually does

Write a finite state machine

Define every page state, allowed action, and resulting next state for a task family.

Generate an interactive website from the state graph

A coding agent translates those rules into a working website so a web agent can interact with it using normal browser actions.

Sample tasks and action paths

The system searches through the graph to create many goal-directed tasks with verified solution paths.

Run agents and check each step

Every click, type, or selection is checked against the graph because the current state and legal actions are explicit.

Use the verified trajectories for training

The resulting data is cheap to scale because verification is built into the environment itself.

The hidden quantity

The hidden quantity

measured quantity  =  Verifiability of each interaction step

Verifiability asks whether the system can tell, with no outside guesswork, if a step was correct. Real websites score low on this quantity because the internal state is hidden and page appearance alone may be ambiguous.

AutoWebWorld raises verifiability by construction because the site is generated from an explicit state graph. The current state and legal next states are known, so correctness becomes a direct rule check.

Why it works

Why it works

The method works because it closes the gap between environment generation and trajectory verification. If the same state graph defines both the website and the checker, then every step has a ground-truth answer built in. That removes noisy judging and lowers cost because no external verifier has to infer hidden page logic.

It also scales well because one finite state machine can generate many task paths. You can sample different start states, goal states, and action orders from the same graph, so one environment produces many verified trajectories without manual labeling.

Math after the picture

The verification rule

First in words:

A step is correct when the chosen action is legal in the current state and lands in the next state defined by the graph.

Then the compact form:

valid(step_t) = 1 if action_t in A(state_t) and next(state_t, action_t) = state_(t+1), else 0

Every symbol:

state_tthe current page state at step t
action_tthe agent action taken at step t
A(state_t)the set of legal actions in the current state
state_(t+1)the next state after the action
valid(step_t)whether the step obeys the graph rules
A tiny worked example
State A is a search page with an empty query box.
Legal actions include typing a query and pressing search.
The agent types 'laptop' and presses search.
The graph says that action leads from State A to State B, the results page.
If the next page is State B, the step is valid.
If the agent clicks checkout from State A, the step is invalid because that action is not legal there.

Task success is then checked by whether the final state is one of the goal states defined in the graph.

What can go wrong

What can go wrong

Synthetic sites may miss real-world messiness. If the generated sites are too clean, an agent trained only on them may struggle on real websites because real interfaces contain noise, layout quirks, and unexpected edge cases.
State graph too small. If the finite state machine covers only a narrow set of flows, then the resulting tasks will also be narrow because the agent can only explore what the graph permits.
Poor translation from graph to site. If the coding agent builds a site that does not faithfully implement the graph, then verification loses meaning because the visible site and the rule system no longer match.
Done right. The method is strongest when you need large amounts of checked interaction data quickly, because the environment itself supplies the answer key.
What a runnable demo should prove

What a runnable demo should prove

Build a tiny shopping site from a state graph with five states: home, search results, item page, cart, and checkout. Generate fifty tasks such as find an item, add it to the cart, and complete checkout. Compare two data pipelines: one that records real browser traces and judges them from outside, and one that uses the state graph for automatic checking. The demo should show that the graph-based pipeline scales faster because every step and final outcome can be verified directly from the rules.
