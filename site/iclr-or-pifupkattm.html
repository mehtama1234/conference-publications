station2radar: query-conditioned gaussian splatting for precipitation field

QCGS turns sparse station readings plus satellite images into radar-like rain maps by rendering only the places you ask about instead of drawing the whole map every time.

Paper explainersAll themesOther

Rainfall mapping has three awkward data sources. Weather stations are accurate but sparse. Satellite images cover large areas but do not directly give rainfall at the ground. Radar provides the best rain field, but radar coverage is expensive and incomplete. This paper builds a system that fuses station readings with satellite imagery to generate a radar-like rain field. The system renders only queried rain regions, so it preserves sharp structure while avoiding work in dry areas where nothing needs to be drawn.

Zero assumption version

Rain data is either accurate, sparse, or incomplete

A weather station gives a trustworthy rainfall reading at one point. A satellite gives dense image coverage across a huge area, but it measures cloud appearance rather than rain at the ground. Radar gives the closest thing to a full rain map, yet many places do not have dense radar coverage because installation and upkeep are costly.

A naive system would spread station readings over a grid and smooth everything together with the satellite image. That blurs storm boundaries and wastes computation across dry regions, because the method treats empty land the same way it treats an active rain cell.

The core gap. We want radar-like rain fields without radar coverage, using sparse stations plus satellite context.

The algorithm as a flow

What it actually does

Read station and satellite data

Take point rainfall measurements from automatic weather stations and a matching satellite image for the same region and time.

Propose likely rain-support locations

A proposal network marks where strong rain structure probably exists.

Predict local rendering settings

An implicit network assigns size, weight, and shape values to each proposed location using both station and satellite context.

Answer a spatial query

When the system is asked for rainfall over a region, it renders only the proposed locations that affect that query.

Assemble the rain field

The selected local contributions are summed into a radar-like rainfall map.

What the paper changes

What the paper changes

The paper changes the rendering strategy for rainfall fields. Instead of drawing the full map every time, it renders only the parts touched by the current rainfall query.

The hidden quantity

The hidden quantity: rain-support coverage

measured quantity  =  which local locations actually carry useful rainfall structure

The system depends on a hidden map of support locations: small local places where rain structure should be represented explicitly. This quantity matters because most of the scene may be dry, while a few compact regions contain almost all of the useful detail.

The proposal network estimates this hidden support by combining station evidence with patterns in the satellite image. If it marks the right support locations, the renderer can stay focused and sharp because it spends its effort on wet regions instead of washing detail across the whole map.

Why it works

Why query-conditioned rendering helps

Full-map rendering spends equal attention on wet and dry areas. That is wasteful because rainfall is usually concentrated in limited regions. By first proposing support locations, the model knows where explicit local detail matters.

The renderer then answers only the region you ask for. That reduces computation because dry locations are skipped, and it preserves sharp storm boundaries because the method sums compact local contributions instead of spreading everything through a coarse grid. Station readings anchor the field to ground truth, while the satellite image supplies the broader spatial context that stations alone cannot provide.

This combination is especially useful outside radar coverage. The station data supplies trustworthy rainfall values, the satellite image provides spatial continuity, and query-conditioned rendering turns both into a flexible rain field that can be produced at different resolutions.

Math after the picture

The field equation

First in words:

Rainfall at a queried location is the sum of local weighted contributions from the proposed support points.

Then the compact form:

R(x) = sum_i w_i(x) * a_i

Every symbol:

R(x)predicted rainfall at location x
ione proposed support point
w_i(x)how much support point i contributes at location x
a_irainfall strength assigned to support point i
A tiny worked example
Suppose a queried location sits near three proposed support points.
Their contributions are 0.6, 0.3, and 0.1, and their rainfall strengths are 12, 8, and 2 mm/hr.
Then R(x) = 0.6*12 + 0.3*8 + 0.1*2.
That gives 7.2 + 2.4 + 0.2 = 9.8 mm/hr.
If the query moves into a dry area, the nearby weights drop toward zero, so the system returns little or no rain.

The whole method depends on learning good local weights and strengths, because those terms decide where rain appears and how sharp each boundary stays.

What can go wrong

What can go wrong

Missed support locations. If the proposal network fails to mark an active rain cell, the renderer cannot recover that structure later because it never draws from that missing support.
Station coverage too sparse. When very few stations exist in a region, the model must rely heavily on satellite appearance, which can confuse thick cloud with ground rainfall.
Fast storm movement between sensors. If station and satellite observations are misaligned in time, the fused field can shift storms into the wrong place because the data no longer describes the same weather state.
Done right. With aligned station and satellite inputs plus accurate support proposals, query-conditioned rendering improves rainfall mapping because it keeps detail in wet regions and avoids wasted work in dry ones.
