SK2Decompile: Skeleton to Skin Binary Decompilation

SK2Decompile reads binary code in two stages: first recovering the program's logical structure, then filling in readable variable names.

Paper explainersAll themesInterpretability

When you have only a compiled binary (no source code), you want to read what the program does. An LLM can guess the source, but it gets two things wrong: it mangles the program's true structure (control flow, data patterns), and it invents bad variable names. SK2Decompile fixes this by doing the work in two separate passes, each guided by clear rules about what makes source code valid.

Zero assumption version

Decompilation is broken in two ways at once

When you reverse-engineer a binary, you want back the original source code. Modern LLMs are good at guessing, but they fail at two independent things: they produce code that does not match the binary's actual logic (the if-then structure, the loops, the data flow), AND they invent bad names (call something x17 when it was really user_count).

The naive fix: train one LLM on all source code, end to end, binary-to-source. But when one model tries to learn both structure and names at once, they interfere. A model that has to guess control flow AND variable names simultaneously spends its learning energy fighting itself.

The fix in one sentence. Split decompilation into two jobs: first recover the program's true structure (as safe intermediate code), then fill in readable names.

The algorithm as a flow

What it actually does

Phase 1: Extract skeleton

LLM reads binary, outputs intermediate code respecting compiler rules (RL rewards syntactic validity).

Phase 2: Recover semantics

Second LLM takes intermediate code, replaces generic placeholders with variable names that match the reference code.

RL for structure

Reinforce outputs that compile and run; penalize malformed control flow.

RL for naming

Reinforce names that match reference code meaning; penalize generic placeholders.

Combine: structure + names

Merge phases into final readable source with both correct logic and real identifiers.

What the paper changes

What the paper changes

The paper splits the decompilation target into two independent LLM tasks instead of one. The first model learns to output intermediate code (a standard compiler format that captures structure but hides names). The second model learns to fill in readable names into that scaffold.

the object it moves  =  decompilation pipeline architecture
The hidden quantity

The hidden quantity: Structural fidelity

measured quantity  =  Syntactic and semantic rule adherence

The paper measures how well the recovered intermediate code respects compiler rules: does it have valid control flow (no unreachable code)? Do variable types match? Can it compile without errors? This is not measured in the paper as a single number, but it is the core thing RL optimizes—every reward signal for Phase 1 checks whether the output is structurally valid.

Without RL, an LLM might generate code that looks readable but violates hidden rules (e.g., a loop body that refers to a variable declared inside the loop, or a function that returns two different types). RL prevents this by penalizing any output that fails a syntax check.

Why it works

Why separating structure and names works

When one LLM tries to recover both program structure and variable names at once, every learning step has to satisfy two conflicting goals: match the binary's logic AND pick good names. Both are hard, and fixing one breaks the other. The learning signal (the feedback telling the model how to improve) gets confused: which failures are due to wrong structure, and which to wrong names?

By splitting into two stages, each model has a single, clear objective. Phase 1 ignores names entirely (uses safe placeholders) and focuses purely on: does this code have the same structure (if-then, loops, memory reads) as the binary? RL provides a strong signal: try to compile or run the intermediate code, and reward it if it succeeds. This is concrete and binary (pass or fail).

Phase 2 then works on a clean scaffold. It sees code structure that is already correct (because Phase 1 was RL-trained to obey compiler rules). Now it only has to solve the naming puzzle: which variables are user IDs, which are counters? This is easier because structure is not in the way. RL for Phase 2 compares predicted names to reference code, giving another clear signal.

The decompilation objective

First in words:

total_score = (phase_1_structure_score * lambda_struct) + (phase_2_name_score * lambda_name), where structure_score is high if the intermediate code compiles, and name_score is high if predicted names are semantically similar to reference code.

Then the compact form:

L_total = lambda_1 * L_struct(IR, binary) + lambda_2 * L_name(names, reference) + R_1(RL_phase1) + R_2(RL_phase2)

Every symbol:

IRintermediate representation (code that respects compiler rules)
binarythe original compiled binary code
namesvariable names predicted by phase 2
referenceground-truth source code
L_structloss for structure recovery (how far from binary)
L_nameloss for naming (how far from reference names)
R_1, R_2RL reward signals (1=structure validity, 2=name correctness)
lambda_1, lambda_2weights balancing structure and naming
A tiny worked example
Binary encodes: if (x > 5) { y = x + 1 }, compiled to hex jumps and memory ops.
Phase 1 LLM outputs: IF (var_a > 5) THEN var_b := var_a + 1 (structure correct, names generic).
RL Phase 1 compiles it: pass (+reward). LLM learns to keep this form.
Phase 2 LLM reads structure, outputs: IF (threshold > 5) THEN result := threshold + 1 (comparing to reference where x->threshold, y->result).
RL Phase 2 scores semantic match: 0.85 similarity. LLM learns this naming is good.
Final output has both correct logic and readable names.

The key is that RL phase 1 only checks if code compiles, giving a clear binary signal; phase 2 only renames, making naming easier.

What can go wrong

What can go wrong

Obfuscated binaries confuse phase 1. If the binary has been deliberately scrambled (control flow flattened, variable names stripped), the structure LLM may output code that is syntactically valid but does not match the binary's actual behavior. RL only checks compilation; it does not verify behavioral correctness.
Phase 2 names can be wrong if training data is biased. The naming model learns by comparing to reference code. If the reference data over-represents certain variable types (e.g., many counters named i, few user names), phase 2 will mislabel rare patterns.
RL can overfit to the compiler checker. Phase 1 RL might find code that compiles but is not faithful to the binary's actual execution (e.g., unused branches that satisfy the compiler but diverge from the original logic).
Done right: intermediate representation is checked for semantic similarity to the binary. Best practice checks not only that IR compiles, but that it produces the same outputs as the binary on test inputs, catching unfaithful rewrites.
What a runnable demo should prove

What a runnable demo should prove

Build a small binary (e.g., a C function that computes factorial or reverses a string, compiled to x86). Run SK2Decompile's phase 1 on it: extract the intermediate code and verify it compiles. Then run phase 2: check that variable names are sensible (not placeholder names). Finally, run both outputs side by side and confirm the decompiled code executes the same test cases as the original binary.

decompilation_score = (1 - L_struct) * (1 - L_name), where L_struct is how far the structure is from the binary and L_name is the naming error rate.

The demo must make clear that phase 1 enforces correctness (structure matches the binary) and phase 2 enforces readability (variable names make sense), and together they produce a source file that is both executable and understandable.
