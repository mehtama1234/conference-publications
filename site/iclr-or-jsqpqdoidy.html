SK2Decompile: Two-Phase Binary Decoding

Decode compiled programs back to readable source by first recovering structure, then filling in names that match the original semantics.

Paper explainersAll themesInterpretability

When you compile a program, the binary loses all the original variable and function names—they become anonymous numbers. SK2Decompile solves this by breaking the decoding task into two independent steps: first, recover the skeleton (control flow, data structures), then add the skin (names that match the original code's intent). Each step uses a language model trained with reinforcement learning to produce code that a real compiler accepts and semantically matches the original.

Zero assumption version

Binary code loses identity information

When a program is compiled, the names of variables, functions, and types vanish—the binary only contains memory addresses and operations. A naive approach tries to decode binary directly to source code in one shot, but it fails because the model has to guess the structure and names simultaneously. It cannot tell what matters (control flow, data types) from what is noise (naming choices), so it produces code that is either syntactically broken or semantically incoherent.

The real problem: asking a model to solve two hard problems at once (restore structure; invent names) means it cannot specialize at either, and small errors in one cascade into large errors in the other.

The core idea. Split the decoding task into two phases: first recover the program structure cleanly, then name variables to match the original semantics.

The algorithm as a flow

What it actually does

Parse and obfuscate

Convert source code to an abstract syntax tree, then replace all variable/function names with generic placeholders, preserving structure.

Train Structure Recovery

Teach a language model to translate binary to this obfuscated skeleton, using reinforcement learning that rewards compilable output.

Generate clean skeleton

Feed binary to the Structure Recovery model, producing intermediate code with correct control flow but no real names.

Train Identifier Naming

Teach a second language model to replace placeholders with real names, rewarded for semantic similarity to originals.

Produce final readable code

Apply Identifier Naming to the skeleton, resulting in decoded source that runs and reads like the original.

What the paper changes

What the paper changes

Instead of asking one model to decode everything at once, SK2Decompile splits the problem into two sequential steps, each with its own model and its own reinforcement learning objective. The object being changed is the architecture of the decompilation pipeline itself—from monolithic to two-phase.

the object it moves  =  the decompilation pipeline
The hidden quantity

The hidden quantity: Structural coherence

measured quantity  =  Structural coherence (compilability + type correctness)

The paper measures a hidden quantity that traditional decoding ignores: how much the recovered code matches the original program's structure. This is not about names; it is about whether loops, branches, function calls, and data types are in the right place.

The paper estimates this by running the recovered code through a real compiler. If the compiler accepts it and type-checking passes, the structure is coherent. Reinforcement learning then rewards the model for producing output that passes these checks.

Plain reading. A program's skeleton is the control flow (which code runs when) and data structures (arrays, records, types). Two programs with the same structure but different variable names are the same program. Structural coherence means the skeleton is correct and will compile.
Paper reading. The paper uses compiler feedback as the signal for structural coherence. Specifically, the compiler can check whether the generated intermediate representation is syntactically valid and type-safe. This is what drives the reinforcement learning reward in Phase 1.
Why it works

Why separating structure from naming works

The mechanism works because structure and naming are two orthogonal problems. When a model tries to solve both at once, it spreads its learning capacity thin—every error in structure production corrupts the names, because the model cannot tell whether a poor name resulted from structural confusion or poor naming, and every naming error makes it harder to verify that the structure is correct, since a misnamed variable may hide a control-flow bug.

By decoupling them, each model can specialize. The Structure Recovery model focuses only on translating binary opcodes to high-level control flow and data types, ignoring the naming problem entirely by using placeholders. This is a simpler signal: the compiler tells you immediately if the structure is wrong. The Identifier Naming model then operates on a clean, validated skeleton, so it only has to match semantics of names to the original code, without worrying whether the underlying structure is correct.

Reinforcement learning in each phase explicitly rewards correctness of that phase's goal. In Phase 1, the reward is compilability: does the compiler accept this output without errors? In Phase 2, the reward is semantic similarity: how close are the predicted names to the original variable names? Separating these rewards means each model learns a sharper objective.

The training objective

First in words:

Total loss = cross-entropy loss (standard language modeling) + reinforcement learning reward based on compiler feedback (Phase 1) or name similarity (Phase 2)

Then the compact form:

L_total = L_CE(theta) + beta * R(output) where R(output) is either compiler_accepts(output) or semantic_similarity(predicted_names, original_names)

Every symbol:

L_CE(theta)standard cross-entropy loss, measures how often the model predicts the next token correctly
betahow much weight to give the reinforcement learning reward
R(output)reward signal: in Phase 1, a score from the compiler; in Phase 2, how similar the names are
thetathe weights of the language model
A tiny worked example (Phase 1 Structure Recovery)
Binary input: a sequence of 20 opcodes for integer addition, memory read, loop branch.
Model predicts next token (IR snippet) at each step.
Cross-entropy loss penalizes wrong predictions: model says 'int x' but should say 'int index', penalty = 0.8.
Compiler runs on full predicted skeleton: accepts it, no type errors. Reward = +1.0.
Total loss for this batch = sum of cross-entropy penalties (0.8 + 0.6 + ... ≈ 5.2) + beta * 1.0. If beta=0.5, total = 5.2 + 0.5 = 5.7.
Model learns to balance: predict tokens accurately AND produce compilable output.

Separating the two phases means each can use a specialized reward: Phase 1 measures if the structure compiles, Phase 2 measures if the names are semantically right.

What can go wrong

What can go wrong

Phase 1 produces syntactically invalid code. If the Structure Recovery model generates IR that the compiler rejects (e.g., mismatched parentheses, type errors), the reinforcement learning signal fails to guide improvement. Mitigation: use a very strict compiler reward and pre-train heavily on valid code.
Phase 2 guesses semantically nonsensical names. Even if the skeleton is structurally perfect, the Identifier Naming model may replace placeholders with names that do not match the original semantics (e.g., calling a counter variable 'output_file'). This happens if the RL reward is too weak. Mitigation: ensure the similarity check between predicted and original names (measured by comparing how close the meanings are) strongly penalizes off-target names.
Obfuscated intermediate representation loses information. The skeleton phase uses generic placeholders (func_1, var_2). If those placeholders erase all hints about what variables are used for, Phase 2 cannot learn how to name them. For example, erasing a comment or annotation that says 'accumulator' means the naming model has to guess the purpose from context alone. The trade-off is worth it (generic names force the structure to stand on its own), but it is still a limitation.
Done right. Train Phase 1 until the compiler consistently accepts the output, then train Phase 2 on that high-quality skeleton. Use separate, well-tuned RL rewards for each phase. Test both phases on a held-out set of binaries not seen during training.
What a runnable demo should prove

What a runnable demo should prove

Build a small decompiler that takes a simple C program, compiles it to binary, then runs SK2Decompile's two phases to recover source. Measure whether the recovered code compiles and whether variable names match the originals.

re-executability = (recovered_code compiles and runs correctly) / (total_test_cases); name_accuracy = (predicted_name == original_name) / (total_identifiers)

The key moment is seeing that Phase 1 produces valid but named-generically code, and Phase 2 transforms it into human-readable source with the original semantics. This proves the value of decoupling.
