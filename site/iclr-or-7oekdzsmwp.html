Multi-View Encoders for Performance Prediction in LLM-Based Agentic Workflows

Instead of testing hundreds of LLM agent setups, train a lightweight machine to predict which ones will work.

Paper explainersAll themesAgents & Tool Use

When you build an LLM agent (a tool that lets a language model pick actions, call functions, write code), there are countless ways to set it up: which model to use, what prompt to give it, which tools to connect. Testing them all is expensive. This paper trains a fast predictor that learns to guess which setup will succeed, cutting the trial-and-error cost dramatically.

Zero assumption version

Testing every agent setup is too expensive

An LLM agent is a system where a language model picks its own actions: should it write code, search the internet, use a calculator? The designer chooses dozens of details: which model, what system prompt, which tools to offer, how to format the interaction history. Without a way to predict success, you have to actually run each candidate setup end-to-end, feed it a task, and wait for the result. Across 50 candidate configurations and 100 test tasks, that is 5,000 runs.

A beginner might try a heuristic shortcut: does the prompt sound good? Is the model large (with many learned weights and values)? But these guesses are unreliable. The setup that looks best on paper often crashes in practice, because the actual performance depends on hidden interactions between the prompt wording, the tool set, and the model's decision-making.

The problem in one sentence. You need to predict which agent setup will work without running and testing every single one.

The algorithm as a flow

What it actually does

Collect agent workflows

Gather many LLM-agent setups from different tasks and domains, with no performance labels yet.

Encode all three views

Run three separate learning systems: one on the code structure, one on the system prompt, one on the tool connection graph.

Pretrain on unlabeled data

Use contrastive and reconstruction losses so the three views learn a shared representation that captures overlapping information, without seeing any labels.

Fine-tune on a small labeled set

Take a small batch of workflows where you know the performance, and adjust the learned representation to predict that performance accurately.

Predict and rank

For new candidate setups, use the learned predictor to guess which will succeed, and test only the top-ranked ones.

What the paper changes

The thing that moves: workflow encodings

Normally, you would feed raw workflows to a predictor. But raw workflows are messy and partial: some are represented as code, some as diagrams, some as prompt text. This paper turns each workflow into a rich, unified encoding (a list of numbers) by looking at it from three angles simultaneously. That unified encoding is what actually predicts performance.

the object it moves  =  workflow encodings
The hidden quantity

The hidden quantity: multi-view completeness

measured quantity  =  multi-view completeness

Multi-view completeness is the degree to which a workflow encoding captures all the information that actually matters for success: the algorithm (captured in code structure), the reasoning (captured in the prompt), and the connections (captured in the tool graph). A workflow that has detailed information visible in all three views is more predictable than one where key details are missing or scattered.

The paper measures this indirectly: by training encoders on all three views simultaneously, it builds representations where important patterns emerge across views. A workflow where the code, prompt, and graph tell a consistent story encodes more completely than one where they conflict or contradict.

Why it works

Why it works: three-view consistency teaches generalization

A workflow setup contains hidden clues about whether it will succeed: the code structure hints at careful step-by-step execution, the prompt wording hints at task understanding, the tool connections hint at capability. But these clues are scattered across three different modalities (code, text, graphs). A naive learner trained on only the prompt might miss that a broken code structure will fail anyway.

This paper solves it by training three separate encoders in parallel and combining their outputs. During pretraining on unlabeled data, the three views learn to reconstruct each other: if the code encoder sees a careful step-by-step structure, it should encourage the prompt encoder to learn prompt patterns typical of careful workflows. This cross-view consistency acts as an internal teacher. When views disagree (for instance, code says careful but prompt says rushed), the learner learns to flag this pattern as unusual; when they agree, it confirms a consistent workflow. After pretraining, the learner has built a representation space where workflows cluster by actual success patterns, not by happenstance. Then, on a small labeled set, you just learn a linear classifier on top of that learned space, which needs far fewer labels because the heavy lifting (learning what matters) was done by the unlabeled cross-domain data.

The payoff: because the representation was built on unlabeled workflows from many domains, it generalizes to new domains. It has learned abstract clues about which code, prompts, and tool patterns predict success in general, not just on the narrow domain it was fine-tuned on.

Math after the picture

The learning equations

First in words:

loss equals reconstruction term plus contrastive term, summed across all encoders and unlabeled workflows. fine-tuned loss is classification or regression of predicted performance against ground truth.

Then the compact form:

loss_pretrain = lambda_recon * loss_reconstruction + lambda_contrast * loss_contrastive; loss_finetune = cross_entropy(predicted_performance, true_performance)

Every symbol:

loss_reconstructionerror in reconstructing each view from the others; encourages views to encode shared information
loss_contrastiveerror in distinguishing similar workflows from different ones; pushes related setups closer in the learned space
lambda_reconweight controlling how much reconstruction matters during pretraining
lambda_contrastweight controlling how much contrastive learning matters during pretraining
predicted_performancethe predictor's guess for success rate or binary pass/fail
true_performancemeasured actual performance of the workflow on held-out tasks
A tiny worked example
Suppose a workflow has code coherence score 0.8, prompt clarity score 0.7, graph connectivity score 0.75. During pretraining, reconstruction loss penalizes if code encoder fails to hint at prompt clarity 0.7 (error = 0.1, squared = 0.01). Contrastive loss penalizes if this workflow is not clustered near other successful workflows (error = 0.3, squared = 0.09). Combined loss = 0.5 * 0.01 + 0.5 * 0.09 = 0.05. After 20 epochs on many unlabeled workflows, the encoder learns to emphasize the patterns that separate success from failure. Then fine-tuning on 100 labeled workflows adjusts the final prediction layer. A workflow similar to observed successful ones now scores close to 1.0 (success predicted).

The pretraining loss teaches the three views to agree; the fine-tuning loss teaches the fused representation to predict actual performance, so the predictor can make accurate guesses with far fewer labels.

What can go wrong

What can go wrong

Pretraining domain is too narrow. If the unlabeled workflows in pretraining come only from one domain (e.g., only code-search agents), the learned representation will be biased toward that domain. When you fine-tune on a different domain (e.g., reasoning chains), prediction accuracy drops.
One view is much noisier than the others. If the tool graph is incomplete or mislabeled while the prompt and code are clean, the graph encoder learns spurious patterns. The fusion layer then down-weights the graph unfairly, and you lose information.
Labeled fine-tuning data is too small. If you have fewer than 20 labeled workflows per domain, overfitting occurs and the predictor memorizes labels instead of learning generalizable patterns. Cross-domain transfer fails.
Done right. The paper uses unlabeled workflows from at least three distinct domains during pretraining, ensures all three views are well-formed and informative, and reserves at least 100 labeled examples per domain for fine-tuning. Under these conditions, the predictor generalizes to new domains and new agent frameworks unseen during training.
What a runnable demo should prove

What a runnable demo should prove

Build a small benchmark: collect 200 agent setups (code, prompt, tool list) from two domains (e.g., code search and arithmetic reasoning). Label 100 of them by actually running them and measuring success rate. Hold out 100 for testing. Pretrain the multi-view encoders on unlabeled workflows from a third domain (e.g., web navigation), then fine-tune on your 100 labeled examples. Use the predictor to rank all 200 setups, pick the top 20, and test them. Compare the average success rate of the top 20 against a random sample of 20. The demo should show that the predictor's ranked top-20 contains far more successes than random, because the predictor learned which structural patterns, prompt styles, and tool configurations correlate with success.

accuracy = number of top-20 predicted setups that actually succeed divided by 20; compare against baseline accuracy from random 20-sample

The core finding: after just 100 labeled examples, the predictor finds high-performing agent setups that random search would miss. The ranking is not perfect, but it cuts down the testing cost dramatically.
