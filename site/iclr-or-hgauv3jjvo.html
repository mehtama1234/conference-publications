Code Optimization Through Problem-Oriented Learning and Anchor Verification

Instead of teaching an LLM to tweak one person's slow code, show it dozens of solutions to the same problem and verify correctness by running the old code as a ground-truth anchor.

Paper explainersAll themesLLMs & Foundation Models

Today's large language models (LLMs) like GPT-4 can write code, but optimizing code for speed is much harder. The main challenge: when you teach an LLM to make a slow program faster, it learns only from one person's particular approach, so it stays trapped in small local tweaks and misses the big algorithmic breakthroughs other programmers discovered for the same problem. This paper shifts the lens entirely — instead of learning from one programmer's iterations, it learns from many programmers' different solutions to the same problem. It also adds a safety check: if an "optimized" code gives the wrong answer, the old slow code serves as a referee to catch the mistake before it ships.

Zero assumption version

Why LLMs get stuck at tiny optimizations

Imagine an LLM trained to optimize code. The usual approach: take a slow program from one programmer, take their fast version, and learn the pattern of change. The LLM picks up small habits — swap a list for a set, use a hash map instead of nested loops. The problem: that one programmer's method is just one solution path. They might not have seen the best algorithm for this problem at all.

Also, when an LLM tries to get clever, it often trades speed for correctness. It might return wrong answers to save 100 milliseconds, which is a disaster. The old slow code, which gets the right answer, is just discarded. So the LLM has no safety net.

The paper's move in one sentence. Pool optimization examples from many programmers solving the same problem, and let the original slow code verify that fast code produces the correct result before accepting it.

The algorithm as a flow

What it actually does

Pool solutions across programmers

For each problem, gather slow and fast code from many different people, not just one.

Embed and rank by structural difference

Convert code to numbers, pick pairs with big algorithmic shifts, not tiny tweaks.

Train the LLM

Show the model: when you see slow code with this pattern, produce fast code with that pattern.

LLM proposes optimization

Given a slow program, the model generates a candidate faster version, because it learned patterns from slow-to-fast code transformations in the training examples.

Run slow code as truth and verify

Execute the original slow code on test inputs, run the optimized code, compare outputs. Accept only if both match.

What the paper changes

What the paper changes

The single change: swap the training pairs from user-oriented to problem-oriented. Instead of pairing "Alice's slow version A -> Alice's fast version A2" (one person's local refinement), pair "many solutions to problem X" where some are slow and some are fast. This means the LLM sees the diversity of algorithmic approaches the community found for the same task.

the object it moves  =  training pairs
The hidden quantity

The hidden quantity: global algorithmic improvement fraction

measured quantity  =  fraction of pairs with major algorithmic changes

The paper measures how many of the optimization examples involve a fundamental change in algorithm (like swapping nested loops for prefix sum + hash), versus just tweaks (variable names, reordering, API swaps). Call this the global algorithmic improvement fraction.

In the old user-oriented pairs, only a small fraction involved true algorithmic breakthroughs because one person's iterations are often just incremental. In the problem-oriented pairs, this fraction rises sharply because many programmers tackled the same problem with different algorithms. The paper estimates this by embedding each program as a list of numbers, measuring the edit distance (how different the code structure is), and categorizing pairs by size of change.

Why it works

Why it works: two mechanisms

First mechanism: diversity of examples. Imagine problem "find the minimum difference between two elements." Alice solves it with a naive nested loop (checking every pair), then optimizes by sorting first. Bob, from the start, uses a hash table (fast lookup). Carol uses a two-pointer scan (one pass after sort). The LLM trained on just Alice learns only the nested-loop-to-sort pattern. Trained on Alice, Bob, and Carol together, it learns multiple breakthrough patterns and can recognize which one fits the slow code in front of it.

Second mechanism: anchor verification prevents the correctness trade-off. When the LLM proposes an optimization, there is always a temptation to shorten output early or skip an edge case to save microseconds. The anchor check runs the original slow code on the same inputs. If the new code gives a different answer, it is rejected, no matter how fast. This removes the false choice between correctness and speed.

Math after the picture

The speedup formula

First in words:

speedup equals original time divided by new time

Then the compact form:

SPEEDUP = time_slow / time_fast

Every symbol:

time_slowwall-clock seconds to run the slow code
time_fastwall-clock seconds to run the optimized code
SPEEDUPa factor > 1 means faster; 4x means four times quicker
A concrete example
Slow code runs in 8 seconds, fast code in 2 seconds: SPEEDUP = 8 / 2 = 4x
Slow code is 100 milliseconds, optimized is 50 milliseconds: SPEEDUP = 100 / 50 = 2x
The paper's results show speedups around 4.48x (best problem-oriented approach with highest structural difference), compared to 3.75x or lower in weaker variants

Higher speedup is better, but only if the answer stays correct because a fast wrong answer is useless; the anchor check ensures the denominator never buys an error by rejecting any proposal where outputs diverge from the slow code's truth.

What can go wrong

What can go wrong

Anchor code itself is slow. The verification step runs the original slow code every time. If the slow code is genuinely prohibitively slow (e.g., O(2^n) on large inputs), verification itself times out. Mitigation: apply a timeout budget; if slow code hits it, set aside that test case.
LLM proposes code that runs fast on test cases but is subtly wrong on hidden cases. Anchor verification can only check outputs on the inputs actually run. If the test set has gaps, a wrong algorithm might slip through. For example, if test cases never include negative numbers and the optimized code has a bug with negatives, verification misses it.
Global algorithms don't transfer across problems. A breakthrough algorithm for problem A (e.g. binary search) does not always work for problem B. The paper addresses this by training separately per problem, so diversity helps within the same task but does not auto-generalize.
Done right. Pool solutions from many programmers who tackled the same exact problem, use anchor verification, and set reasonable timeouts. The method shows strong results on standard coding benchmarks.
What a runnable demo should prove

What a runnable demo should prove

Build a demo on a single coding problem (e.g., 'find the longest increasing subsequence' or 'compute edit distance'). Gather 5-10 different solutions from human programmers or existing code repositories, with varying speeds. Train a small LLM (or use a pre-trained one) on problem-oriented pairs: slow-fast pairs drawn from these solutions, emphasizing pairs with large structural differences. Then give it a new slow baseline code, let it propose an optimization, and run anchor verification: execute the slow code to get true outputs, run the proposed fast code on the same inputs, and compare.

The demo makes impossible to miss: (1) the model proposes a code change, (2) you run both versions and confirm they give the same answer, (3) you measure the speedup factor, and (4) you show that the structure of the optimization (e.g., changing loop order, using a hash, swapping algorithms) appears in one of the training examples.

correct_optimization_rate = count(proposals where output matches AND speedup > 1) / count(proposals); average_speedup = geometric_mean(speedup factors for correct proposals)

The demo succeeds when the model generates an optimization that both preserves correctness (checked by running the slow code as referee) and achieves significant speedup (>1.5x or better).
