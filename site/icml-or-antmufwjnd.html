AgentWebBench: Multi-Agent Coordination in Agentic Web

When user agents must coordinate with many content-specific agents instead of accessing a central database, larger models and careful planning close the performance gap.

Paper explainersAll themesAgents & Tool Use

The internet is shifting from one big searchable database to a network of specialized agents. A user agent (the model helping you) now must ask different website agents (specialized for their own content) to fetch information. We built a benchmark to study how well this works and found that larger models do better because they can hold and synthesize information from many agents without forgetting, test-time planning helps because it avoids wasted queries to slow or unreliable agents, and the best results need smart interaction strategies that route to the most useful agent at each step.

Zero assumption version

The world before: centralized information always available

Today, when you search the web, you query a central index. The search engine cached everything and ranked it. You get answers fast because one database has the whole picture.

But now websites are deploying their own agents to serve their data. Instead of letting Google index them, a news site keeps its agent, a shop keeps its agent, a research library keeps its agent. If you want information, you ask each one separately. The user agent cannot see the corpus directly—it has to negotiate with many specialized agents.

A beginner might think: just ask all of them in parallel and combine the answers. But this breaks for several reasons. One agent might be slow or wrong. The interaction cost explodes (asking ten agents is way more expensive than one central lookup). Contradictions arise—which agent to trust? The user agent must plan carefully which questions to ask whom, in what order.

In one sentence. The paper measures how well a user agent can answer questions by coordinating with many content-specific agents instead of accessing one central database.

What the paper changes

The thing being changed: agent interaction strategy

The paper changes how a user agent decides which content agents to contact and in what order. The object is the interaction plan—the sequence and scope of agent requests.

the object it moves  =  interaction plan
The hidden quantity

The hidden quantity: coordination cost versus quality

measured quantity  =  interaction reliability and coverage trade-off

As the user agent asks more agents more questions, it gets better answers (higher coverage, fewer missed facts) because each agent holds a different piece of the knowledge—asking one agent gets a partial view, but asking five agents from different sources fills in gaps. But each interaction costs time and compute. Content agents timeout, give bad results, or contradict each other. The hidden quantity is how many interactions the user agent must make before answers converge—before asking more gets diminishing returns. Call it the interaction depth.

The paper measures this by comparing performance (accuracy, completeness) across different numbers of agent interactions. It finds that small models hit a wall early (even asking 10 agents doesn't help much) because their limited memory can't hold or synthesize all the conflicting evidence, while large models keep improving with more interactions because they can track and resolve contradictions. This gap is the hidden quantity the paper really studies.

Why it works

Why coordination with planning beats naive multi-agent

The core mechanism has two parts. First, a larger model can hold more information in its head. When asking agent A a question, then agent B a follow-up, the model must remember A's answer and use it to guide B's query. Tiny models forget or mix up the evidence. Larger models keep it all straight.

Second, planning matters because naive parallelism (ask everything at once) is wasteful. If the user agent is smart, it asks the most likely source first, and only if that agent is silent or contradicts itself does it ask a second source. This sequential planning (asking agents in order of expected usefulness) reduces timeouts and contradictions. The user agent learns which agents are fast and reliable, so it chooses them first.

Together: a large model with a planner can use many agents efficiently. Each interaction yields new signal. The planner routes to the best next agent, not randomly. So the performance gap shrinks—multi-agent coordination starts to match or beat centralized retrieval, because the planner is smarter than a static ranking.

Math after the picture

How to score multi-agent answers

First in words:

accuracy_multi_agent = base_accuracy + bonus_per_interaction × num_interactions_used - penalty_per_conflict × num_conflicts

Then the compact form:

A_multi = A_base + β · I - γ · C

Every symbol:

A_multifinal accuracy with multi-agent coordination
A_basebaseline accuracy with just one agent
βhow much each new interaction improves the answer
Inumber of useful interactions the planner made
γpenalty for each conflict between agents
Cnumber of contradictions found
A tiny worked example
Start: baseline accuracy A_base = 72 (one agent gives a decent answer).
User agent asks 4 more agents (I = 4). Each adds β = 3 points: 4 × 3 = 12.
But 2 agents contradict each other (C = 2). Each costs γ = 2 points: 2 × 2 = 4.
Final: A_multi = 72 + 12 - 4 = 80. The multi-agent coordination improved accuracy from 72 to 80.
If planning had picked bad agents (C = 5 instead), accuracy would be 72 + 12 - 10 = 74, barely better than baseline.

The planner's job is to maximize useful interactions and minimize conflicts—pick the right agents to ask, in an order that resolves uncertainty early.

What can go wrong

What can go wrong

Small models can't hold multi-agent context. A tiny language model forgets or misattributes the answer from agent A when asking agent B. It confuses which fact came from which source. The interaction depth stays low—asking more agents just adds noise.
Agents timeout or have no answer. Some content agents are slow or offline. If the planner has no good heuristic to detect this, it wastes compute waiting for dead endpoints. Random ordering amplifies timeouts; planning should choose fast, reliable agents first.
Contradictions between agents aren't resolved. Agent A says the laptop costs 999 dollars, agent B says 899. The user agent has no method to fact-check, so the final answer is ambiguous. Synthesis requires strong reasoning.
Done right: planning + large model + multi-hop reasoning. A large model with a planner learns which agents are reliable for which query types. It queries in sequence, stopping early if one agent's answer is confident and consistent. This closes the gap to centralized retrieval.
What a runnable demo should prove

What a runnable demo should prove

Build a tiny simulation of multi-agent coordination. Use three mock agents (a news agent, a shop agent, a fact-check agent). Each has a small knowledge base and sometimes returns slow or conflicting answers. Implement a planner that picks the order to query them. Run it on ten sample questions. Measure the final answer accuracy before and after planning. Measure how many interactions you needed. This proves that planning reduces wasted interactions (because the planner learns which agents are fast and skips the slow ones) and that model size enables better synthesis (because a larger model can hold and compare multiple conflicting answers from different agents).

improvement_ratio = (accuracy_planned - accuracy_naive) / accuracy_naive

The demo must show that the planner's chosen interaction order outperforms random order (because the planner avoids slow agents and focuses on reliable ones), and that a slightly-larger model with the same planner reaches the centralized baseline faster (because it synthesizes conflicting answers more accurately).
