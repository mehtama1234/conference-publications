CrossQ: Task-Aligned Cross-Token Conditional Quantization

CrossQ shrinks the massive lookup tables that search engines store by smarter compression that understands which token scores actually matter for ranking.

Paper explainersAll themesRepresentation & Self-Supervised Learning

ColBERT, a search engine that ranks answers by comparing many small number-lists (tokens) from a question against many small number-lists from each document, finds good matches. But storing all these lists for billions of documents fills entire hard drives. CrossQ cuts storage by 64 times by compressing these number-lists more intelligently: instead of squeezing numbers equally, it learns which numbers are critical for ranking and protects those.

The storage wall

A late-interaction retriever (a search engine that matches many small parts of text, not just one big meaning) stores millions of tiny number-lists — one for each word or phrase in every document. For billions of documents, this fills terabytes. The naive approach: squeeze each number-list by rounding its numbers to fewer bits, preserving average reconstruction accuracy. But search does not care about average. It cares about whether the ten highest-scoring documents remain in the top ten after compression.

When you compress by averaging, the exact winner tokens (the few numbers that decide ranking) get mangled just like the irrelevant ones, and the ranking breaks.

In one sentence. CrossQ compresses token lists by learning which tokens matter for ranking, and it protects those while squeezing the rest.

The algorithm as a flow

What it actually does

Encode at search time

Question and document words become number-lists (embeddings).

Index with context

For each document, compute lightweight summary; store conditioned token codes (compressed lists).

Match at query time

Question tokens score against document tokens using the compressed codes.

Ranking-aware training

During training, protect high-score tokens; don't care if low-score tokens get fuzzy.

Storage and speed

Each token now takes 2-8 bits instead of 32; 64x smaller index, similar ranking.

The hidden quantity

The hidden quantity: winner-token fidelity

measured quantity  =  Winner-token fidelity

Not all tokens are equal when ranking. A few high-scoring tokens ('winners') determine whether a document ranks in the top ten. Fidelity is how accurately the compressed codes preserve the original scores of these winners. Standard compression erodes fidelity of winners equally with losers, breaking ranking. CrossQ's hidden measure is how well the conditioned codes keep winner scores intact while allowing losers to degrade.

The paper estimates fidelity by running the ranking task and measuring whether top-ten documents stay top-ten after compression. It is inferred from ranking metrics (MRR@10, nDCG@10) rather than measured directly, but the mechanism ensures high-scoring tokens are protected during training.

Why it works

Why it works: conditioning + ranking-aligned training

Standard quantization (rounding numbers) treats all tokens the same: find one codebook (a set of allowed rounded values) that reconstructs all tokens with minimum error. But reconstruction error and ranking are decoupled: a document can lose ranking even if reconstructed tokens look close on average.

CrossQ uses two tricks. First, conditioning: instead of one global codebook, each token's code depends on lightweight context about its document (computed at indexing, not stored). This gives different tokens different compression budgets — tokens in high-quality documents can afford more bits, while low-importance tokens compress harder. Second, ranking-aligned objectives: during training, the system learns codes by directly protecting ranking metrics. It uses triplet losses (keeping margins between relevant and hard-negative documents intact) and score distribution matching (ensuring the distribution of match scores stays similar). This means the training process explicitly cares about preserving which documents rank where, not just reconstruction.

The mechanism: light document context lets token codes adapt to document importance; ranking-aligned training ensures the adaptation preserves ranking decisions, not average fidelity.

The compression equation

First in words:

Loss = reconstruction error of tokens + ranking loss (triplet margin + score distribution matching) + lambda times penalty for high bit budget.

Then the compact form:

L = MSE(token_original, quantize(token, context)) + margin_loss(scores_pos, scores_neg) + dist_loss(P_scores, Q_scores) + lambda * bits_used

Every symbol:

token_originalthe original floating-point number-list for one word
quantize(token, context)the rounded version, conditioned on document context
scores_posmatch scores of relevant documents (should be high)
scores_negmatch scores of hard negatives (should be low)
margin_losspenalty if the gap between relevant and negative is too small
P_scoresdistribution of scores before compression
Q_scoresdistribution of scores after compression
dist_losspenalty if the two distributions differ
lambdaweight controlling how much to trade off storage for quality
A tiny worked example
Suppose a winner token's original score is 8.0, and a loser token's score is 1.5.
Standard quantization (fixed codebook) rounds both: 8.0 -> 7.9, 1.5 -> 1.6 (small errors, but ranking intact in this case).
CrossQ with context: winner tokens get more bits, so 8.0 -> 8.01 (0.01 error); losers compress harder, 1.5 -> 1.2 (0.3 error).
Ranking-aligned loss: trains to keep the score gap (8.0 - 1.5 = 6.5) similar after compression (8.01 - 1.2 = 6.81), so ranking is preserved.
Storage: winner uses more bits, loser fewer. Average bits per token drop 64x while top-ten ranking survives.

The loss balances three things: keeping tokens close to original, preserving score gaps between relevant and hard negatives, and keeping the overall score distribution honest.

What can go wrong

What can go wrong

Hard negatives mislabeled. If the training data marks the wrong documents as 'negative', the ranking-aligned loss will protect false negatives and break ranking. The paper depends on clean training labels.
Document context bloat. If the lightweight document summary grows too large (even if not stored, it must be computed at index time), indexing becomes slow. The method works only if context stays cheap to compute.
Out-of-distribution queries. If a query at search time asks about topics far outside the training corpus (e.g., new scientific discoveries), the token codes may be misaligned. The paper trains on a specific retrieval corpus and may not generalize to very different domains.
Done right. When training data is clean, context is lightweight, and queries stay in-distribution, CrossQ delivers both small storage and intact ranking.
What a runnable demo should prove

What a runnable demo should prove

Build a tiny late-interaction search engine: store 1000 documents (news articles or Wikipedia snippets) with uncompressed and CrossQ-compressed token vectors. Compress at 4 bits per token. Run 50 test queries, and measure ranking (rank of ground-truth document in the top-100 results). Compare MRR@10 (mean rank of the first relevant result) before and after compression. Also measure storage used (bytes per token). The demo should show that MRR@10 drops by less than 2% while storage shrinks to ~1.6% of uncompressed.

MRR_retention = MRR@10_compressed / MRR@10_uncompressed; Storage_ratio = bytes_per_token_compressed / bytes_per_token_uncompressed

The winning insight: smart compression is not about preserving average reconstruction — it is about preserving ranking decisions, and that requires knowing which tokens decide rankings.
