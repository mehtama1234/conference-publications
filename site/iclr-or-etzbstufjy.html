USTBench: Spatiotemporal Reasoning in Urban LLM Agents

Instead of measuring only whether an LLM gets a city problem right, measure the steps it takes to get there, so you can see exactly where its reasoning breaks.

Paper explainersAll themesDatasets & Benchmarks & Evaluation

Large language models (AI systems trained to predict text word-by-word) can help plan cities, predict traffic, and manage urban systems, because they can understand text descriptions of cities and reason about them. But today we only check if they got the answer right or wrong. We never look at how they thought about the problem. This makes it impossible to know what is actually broken. USTBench fixes this by measuring each intermediate reasoning step, revealing that even advanced reasoning models struggle with long-term planning and learning from mistakes in city environments.

Zero assumption version

We only measure the final answer

When an LLM tries to solve a city problem, we check: did it predict the right traffic level? Did it pick the right road to build? Today, the only thing we measure is the answer at the end. If the model fails, we see failure but not why.

A naive solution is to just try harder models—throw more compute at reasoning. But that does not tell us where the real gaps are. Does the model fail because it cannot understand what the city looks like right now? Because it cannot predict what will happen next? Because it cannot plan multiple steps ahead? Because it refuses to learn from its own mistakes? Without measuring each step, we have no idea which problem to fix.

The method. Build a benchmark with specific questions that measure each reasoning step separately, so you can see exactly where a model gets stuck.

The algorithm as a flow

What it actually does

Set up the measurement frame

Define four reasoning steps: understanding the current city state; forecasting what happens next; planning which action works best; reflecting on what went wrong.

Build 62,466 process-level questions

For each task and each reasoning step, write specific questions the model must answer correctly to move forward.

Create real urban scenarios

Build an interactive city simulator that produces actual spatiotemporal data: traffic flows, power outages, movement patterns, congestion over time.

Test 14 LLMs on all steps

Run each model through every question and measure what fraction of each reasoning step it handles correctly.

Find which step breaks first

Compare models: which reasoning step is most likely to fail? Whether a model was trained on complex logic does not always help city planning because different domains require different reasoning patterns. Identify which gaps are specific to urban environments.

What the paper changes

What the paper changes

The old approach measures only the final outcome: accuracy, traffic efficiency, plan quality. USTBench changes that to measure intermediate reasoning steps. Instead of asking did the model solve the problem, it asks did the model correctly understand the situation, then forecast what comes next, then pick a good action, then recognize its mistakes and adapt.

The hidden quantity

The hidden quantity: Intermediate step quality

measured quantity  =  quality of each reasoning step

The hidden quantity is how well the model executes each intermediate step. It is not visible from the final answer alone. A model might get a prediction right by accident, or wrong despite understanding the situation perfectly. By measuring each step separately with specific questions, the benchmark reveals which steps are strong and which are weak.

USTBench estimates this by asking targeted questions for each step: Show me you understand the current traffic pattern (understanding). Given that pattern, predict the next hour (forecasting). Now pick the best action (planning). And after you act, admit what went wrong (reflection). Each answer tells you if that step works.

Why it works

Why measuring steps reveals what is broken

When you measure only the final answer, a model's weakness hides behind all the steps that worked. Imagine the model understands traffic patterns perfectly but fails at planning because it cannot think multiple moves ahead. You would never know, because you only look at the bottom-line prediction error.

By decomposing the task into four steps and measuring each separately, you expose the bottleneck. The model gets 80 out of 100 on understanding, 75 on forecasting, 40 on planning, and 20 on reflection. Now it is clear: planning and learning from mistakes are the real gaps. This allows researchers to design targeted improvements because they know which exact step to improve. For instance, the benchmark revealed that models trained on complex logic problems (like DeepSeek-R1) do not necessarily help with urban spatiotemporal tasks, and this happens because those models are trained to solve math and logic puzzles, which use different reasoning patterns than predicting traffic and planning cities. This means specialized training for city reasoning is more valuable than generic reasoning training. That insight would be invisible if you only measured the final answer.

Math after the picture

Measuring each reasoning step

First in words:

accuracy_step = (correct_answers_for_step / total_questions_for_step). Overall process_accuracy = (sum of step accuracies) / (number of steps). The gap is final_accuracy minus process_accuracy.

Then the compact form:

process_score = (score_understand + score_forecast + score_plan + score_reflect) / 4

Every symbol:

score_understandfraction of understanding questions answered correctly
score_forecastfraction of forecasting questions answered correctly
score_planfraction of planning questions answered correctly
score_reflectfraction of reflection questions answered correctly
A tiny worked example
Model A on traffic prediction: understand 80%, forecast 75%, plan 40%, reflect 20%. Process score = (80 + 75 + 40 + 20) / 4 = 53.75%.
Model B on traffic prediction: understand 85%, forecast 78%, plan 38%, reflect 18%. Process score = (85 + 78 + 38 + 18) / 4 = 54.75%.
Both might get 60% on the final answer, but process score shows Model B is slightly more balanced. Without process-level measurement, you would miss the insight that both fail at planning.

By summing step scores and dividing by four, you get a balanced view of where each model is strong and weak.

What can go wrong

What can go wrong

Question order bias. If you ask understanding questions in an easy-to-hard order, a model might answer the easy ones and then fail not because it does not understand but because it ran out of focus or space in its internal memory for more text.
Confusing the measurement with the ability. A model might fail a reflection question because the question is poorly worded or context-dependent, not because the model cannot reflect. The benchmark must design questions carefully so failure means actual weakness.
Domain-specific knowledge gap. An LLM trained mostly on internet text might not have learned typical urban patterns (traffic flow, pedestrian behavior, power grid dynamics), so it fails not because its reasoning is weak but because it lacks domain data.
Done right. Questions are designed to isolate one reasoning step at a time; all models see the same questions and evaluation order; the benchmark includes diverse urban scenarios so that results generalize across cities.
What a runnable demo should prove

What a runnable demo should prove

Build a small urban scenario (three roads, traffic from two time steps, one action choice). Write four questions: 1) Do you understand this traffic pattern now? 2) What will traffic be next hour? 3) Which road should be built? 4) What did you get wrong? Run two models (a small one and a large one) on the four questions separately and measure their per-step accuracy. The demo should make it obvious that the large model does not necessarily win at every step.

step_accuracy_per_model = (correct_answers / total_questions). Winning model per step is the one with higher accuracy on that step only.

The demo proves that measuring steps reveals different model strengths, not visible when you only check the final answer.
