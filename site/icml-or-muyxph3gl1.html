MatchFixAgent: Language-Agnostic Autonomous Repository-Level Code Translation Validation and Repair

The paper checks whether translated repositories really preserve behavior by breaking validation into explicit semantic subproblems, then using the same structure to repair translations that fail.

Paper explainersAll themesOther

Repository-level code translation is not finished when a model produces code in a new programming language. The important question comes after generation: does the translated repository behave the same way as the source repository? Standard automatic checks often rely on existing tests, build success, or language-specific analysis tools. Those signals are incomplete. A translation can compile and still implement the wrong logic, and many repositories have weak tests. MatchFixAgent treats validation as a structured semantic-analysis problem. It decomposes the translation pair into multiple checks, produces an equivalence or non-equivalence verdict for most pairs, and then uses the discovered mismatch to guide repair.

Zero assumption version

Why repository translation needs stronger validation than tests alone

Code translation across programming languages changes syntax, type systems, standard libraries, error handling, and project structure. A correct translation must preserve behavior across those changes. Existing validation methods often depend on running the target repository's tests or on language-specific static tools. That fails for two reasons. First, many repositories have incomplete tests, so passing tests does not imply semantic equivalence, meaning the programs may still differ on untested inputs. Second, language-specific tooling creates high engineering overhead, which makes broad language coverage difficult.

Repository-level translation also introduces cross-file dependencies. A bug in one translated module can silently alter behavior in another module that still compiles. So the validation problem is not merely checking individual functions. It is checking whether the source repository and target repository implement the same behavior under the same external contracts.

The central issue. A translation is only useful if it preserves behavior, but the common automatic signals for behavior are too weak or too language-specific.

The algorithm as a flow

What it actually does

Analyze source and target repositories together.

Collect repository structure, interfaces, and key code regions because behavior can depend on relationships across files rather than one file alone.

Divide validation into semantic tasks.

Assign sub-agents to inspect control logic, data handling, API correspondence, and edge cases so the verdict is built from multiple focused checks.

Synthesize an equivalence verdict.

Combine the sub-analyses into an explicit judgment with evidence, which means the system can say both whether the translation differs and where the difference appears.

Plan a repair.

Use the detected mismatch to propose edits that target the behavior gap instead of rewriting large regions blindly.

Re-validate after repair.

Run the same semantic checks again so the system can confirm whether the edit fixed the mismatch without introducing new divergence.

What the paper changes

What the paper changes

The paper changes the post-translation workflow. Instead of trusting tests or custom language-pair tooling, it builds a language-agnostic validation-and-repair loop centered on semantic analysis of repository behavior.

the object it moves  =  the procedure used to judge and repair translated repositories
The hidden quantity

The hidden quantity

measured quantity  =  semantic equivalence at repository level

The hidden quantity is not text similarity between the source and target files. It is whether both repositories implement the same observable behavior under the same inputs, state transitions, and interface contracts. That quantity is hard to observe directly because programs can differ in syntax while remaining correct, and they can look similar while failing on important cases.

MatchFixAgent estimates this quantity through decomposed evidence. Each sub-agent checks one part of the behavior story, such as how data values are transformed or how error cases are handled. The final verdict uses these pieces together because no single signal is strong enough by itself.

Why it works

Why decomposed semantic validation improves both checking and repair

The approach helps because equivalence is too broad for one undifferentiated judgment. A repository translation can fail by changing control flow, by mishandling special values, by using the wrong library call, or by breaking interactions across files. If one agent tries to reason about all of that at once, it can miss evidence or produce vague conclusions. Decomposition improves coverage because each sub-agent asks a narrower question with clearer criteria.

The same decomposition also improves repair because a repair model needs to know what kind of behavior diverged and where the divergence likely lives. An equivalence verdict without explanation does not provide that. MatchFixAgent uses the sub-analyses to point repair toward concrete semantic faults, which means the repair step can make targeted edits rather than broad rewrites. That raises repair yield because targeted edits are less likely to damage correct parts of the translation.

Math after the picture

Score equivalence as agreement across semantic checks

First in words:

Combine several semantic-check scores into one overall equivalence score, then compare that score with a threshold to decide whether the translation is acceptable.

Then the compact form:

equiv_score = sum_k alpha_k * check_k(source_repo, target_repo)

Every symbol:

check_k(·)the k-th semantic check, such as API correspondence or edge-case handling
alpha_kthe weight assigned to that check
equiv_scorethe combined evidence score for behavioral equivalence
source_repothe original repository
target_repothe translated repository
A tiny worked example
Suppose the system uses three checks: API behavior, control logic, and error handling.
API behavior agrees, so that check gets 1.
Control logic mostly agrees but one branch is wrong, so that check gets 0.4.
Error handling disagrees, so that check gets 0.
With equal weights, the combined score is 1 plus 0.4 plus 0, then divided by three, which is about 0.47.
If the acceptance threshold is 0.8, the translation is judged inequivalent and sent to repair.

The paper does not reduce everything to one literal formula in this simple way, but the operational idea is exactly this: aggregate multiple semantic signals into a verdict.

What can go wrong

What can go wrong

Repository behavior may depend on external systems not captured in code. If the real semantics depend on deployment settings, undocumented services, or runtime data outside the repository, a code-only analysis can miss the true equivalence conditions.
Sub-agent analyses can still share the same blind spot. Using multiple agents helps coverage because each one inspects a narrower semantic question, but it does not guarantee independence, so a subtle semantic bug may escape all sub-analyses if they rely on the same mistaken assumption.
Repair can introduce second-order regressions. A targeted edit may fix one mismatch while changing another module interaction, which means the re-validation loop is necessary and may still need several iterations.
Done right. The method works when the semantic decomposition covers the important repository contracts and the repair stage is guided by specific mismatch evidence, because then fixes are both more precise and easier to verify.
What a runnable demo should prove

What a runnable demo should prove

Take a small repository in one language, create both correct and intentionally flawed translations into another language, and compare three validators: test-only, build-plus-tests, and MatchFixAgent. Include flaws that weak tests often miss, such as altered edge-case handling, incorrect library substitutions, and one cross-file state bug.

Then enable the repair loop only for the flawed translations because repair quality matters only after validation has identified true semantic failures. The demo should show that the paper method is valuable twice over: it finds semantic failures that the weaker validators miss, and it gives repair enough structured evidence to correct more of them.

repair_gain = repaired_by_agent / inequivalent_translations

A strong demo shows higher detection of true inequivalence and a higher fraction of successful repairs on the same translation set.
