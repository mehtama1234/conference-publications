EvoC2F: Tool Orchestration Through Compilation and Verified Learning

Instead of agents freely writing tool calls, compile tool usage into a structured representation that can be optimized, parallelized, and verified before execution.

Paper explainersAll themesAgents & Tool Use

When a language model calls a tool (say a calculator or web search), it usually just writes out the request one at a time, hoping each call works. This is slow and fragile. EvoC2F treats tool orchestration the way a programmer writes code: it compiles tool calls into a verified intermediate representation, catching errors ahead of time and running things in parallel. It also gates new learned skills through testing so bad shortcuts never pollute the library.

Zero assumption version

Tool calls are written freestyle, slow, and error-prone

Today's language model agents write tool calls in a freeform way: the model decides which tool to use, constructs the call, and waits for the result before moving to the next step. A beginner might think this is fine: just ask the model to write the right call each time. But it fails in practice because models often write malformed calls, there is no way to spot errors before execution wastes time, multiple independent tool calls cannot run at the same time, and when agents learn new tool combinations and store them as reusable skills, those shortcuts often degrade over time because they were never properly tested.

Agents that try to patch this by learning from experience face a second problem: the library of learned skills grows with unverified snippets that seemed to work in one case but may fail elsewhere, creating a mounting liability that eventually drags performance down.

The core issue. Agents treat tool calls like prose instead of code: they lose the chance to optimize, parallelize, verify, or test new learned skills before using them.

The algorithm as a flow

What it actually does

Step 1: Capture intent

Agent expresses what tools to use in structured form (intermediate representation, not freeform text).

Step 2: Verify and annotate

The IR captures not just the call but its semantics (what inputs matter, what the output means), so the system can reason about it.

Step 3: Optimize and parallelize

Reorder tool calls so independent ones run at the same time, eliminating artificial waiting.

Step 4: Execute with fault tolerance

Run the compiled plan, catching errors because they were predictable from the IR.

Step 5: Test learned skills

When the agent discovers a new useful tool combination, run it through automated tests before adding it to the skill library.

What the paper changes

What the paper changes: representation of tool plans

The paper changes how agents represent the steps they need to take. Instead of freeform text (the agent just writes what it wants), EvoC2F constrains plans to an intermediate representation—a structured, machine-readable format like what a compiler uses for code. This representation explicitly says which tools depend on which, what each tool's inputs and outputs mean semantically, and how things can be reordered. The object is the plan representation itself.

The hidden quantity

The hidden quantity: semantic dependency graph

measured quantity  =  Semantic dependency graph

The hidden quantity is the semantic dependency graph built from the plan. This is the structure the compiler infers from the structured IR: which tool outputs feed into which tool inputs, which calls have no dependencies and can run in parallel, and which sequences are forced by the logic. The system measures this graph to detect cycles (an error—a tool waiting for its own output), find parallelizable regions, and verify that substituting a learned skill does not break downstream logic.

The paper uses this graph during compilation to optimize the plan by reordering calls so independent ones run together, which cuts wall-clock time. It uses the graph during execution to dispatch tools in parallel when no dependency blocks them, so calls that do not depend on each other start immediately instead of waiting. During learning, it uses the graph to test that a new skill does not violate the semantic contracts that downstream tools expect, ensuring substituting the skill does not break the rest of the pipeline.

Why it works

Why this works: compilation catches errors and enables optimization

The mechanism works in two parts: optimization and verification. First, by casting tool orchestration as a compilation problem, EvoC2F can use classical compiler optimizations. The structured intermediate representation makes the dependency graph explicit, so the system can spot which tool calls are independent and run them in parallel instead of sequentially. This cuts latency because independent calls run at the same time instead of one after another. Second, because the plan is structured and semantically annotated, the system can verify it before execution: check that there are no data-flow cycles, no tool receives malformed inputs, and no tool produces outputs incompatible with what downstream tasks expect. This catches whole classes of errors that a freeform text agent would write and only discover at runtime.

For learned skills, the mechanism is a gate: when the agent proposes adding a new skill (a learned shortcut), the system compiles it into the same intermediate representation, verifies it does not violate the semantic contracts of tools that use it, and runs it through a test suite. Only after passing do tests does it enter the skill library, preventing untested abstractions from polluting the library and causing cascading failures later.

Math after the picture

The verification formula

First in words:

For each learned skill S, compute the set of semantic constraints C it must satisfy, and the set of test cases T that cover those constraints. Admit S to the library if and only if S passes all tests in T and does not introduce new constraint violations in the dependency graph.

Then the compact form:

Admit(S) := ∀t ∈ T, S(t) ✓ ∧ ∀d ∈ DG, Substitute(S, d) satisfies semantics(d)

Every symbol:

Admit(S)boolean: true if skill S is added to the library
∀t ∈ Tfor every test case in the test suite
S(t) ✓skill S passes test t
∀d ∈ DGfor every dependency in the semantic graph
Substitute(S, d)replace the original implementation with skill S in dependency d
semantics(d)the semantic contract that dependency d must satisfy
A tiny worked example
Suppose the agent learns a skill: 'combined web_search + parse_json' to replace those two calls.
Test suite T has 5 cases: valid_url, invalid_url, malformed_json, empty_result, timeout.
Dependency graph has two downstream uses: d1 (expect JSON object) and d2 (expect list).
The skill passes all 5 tests: ✓✓✓✓✓
Check d1: substitute the skill, verify downstream gets an object type. ✓
Check d2: substitute the skill, verify downstream gets a list type. ✓
Conclusion: Admit(S) = true. The skill enters the library.
If the skill had failed one test or violated d1's contract, Admit(S) = false, and it stays out.

The formula says learned skills must pass tests and preserve the semantic guarantees that the rest of the agent depends on. This is what keeps the library clean over time.

What can go wrong

What can go wrong

Semantic annotation bottleneck. The intermediate representation requires humans to annotate tool semantics (what inputs/outputs mean). If annotations are incomplete or wrong, the verification is unsound. The paper must show annotations are maintainable as tools evolve.
Test suite incompleteness. A learned skill that passes a small test suite may still fail in production edge cases. The gate is only as good as the tests. If the test suite is too narrow, untested failure modes can still enter the library.
Overhead of compilation and verification. Compiling, verifying, and testing every new skill adds latency upfront. If the compilation itself is slow or the test suite is large, the gating process may become a bottleneck, making it unattractive to learn new skills.
Done right. The paper shows the system works when the intermediate representation captures the real semantics, test suites are comprehensive enough to cover realistic scenarios, and the compilation + verification cost is small relative to the savings from parallelism and error prevention.
What a runnable demo should prove

What a runnable demo should prove

Build a simple agent task that requires calling multiple tools (e.g., search for a person, fetch their email, send a message). Run it against a naive agent that chains calls sequentially, and run EvoC2F with the same tools. Measure: (1) wall-clock latency (how long before the result), (2) malformed-call rate (how many calls fail), and (3) library quality after learning (how many learned skills are later used successfully vs. reverted or removed). The demo must show that EvoC2F has lower latency, fewer errors, and a stable skill library over time.

latency_improvement = (latency_naive - latency_evoC2F) / latency_naive; malformed_call_rate = calls_that_fail / total_calls; skill_retention_rate = skills_still_in_use_after_100_calls / skills_learned

The demo is successful if EvoC2F reduces latency by at least 30% through parallelism, drops malformed-call errors to near zero through pre-flight verification, and maintains a skill library where at least 80% of learned skills are still in active use after repeated agent runs (indicating the gating process keeps only valuable skills).
