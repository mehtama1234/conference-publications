Residual-Guided Multi-Resolution Refinement of Foundation Models

A drought forecasting system wraps frozen weather models to predict step-by-step, correcting each guess based on its error.

Paper explainersAll themesTime Series & Sequential

Weather models predict rainfall weeks ahead using historical climate data. But raw predictions miss local details that climatologists catch by studying the prediction error and refining it step-by-step at different timescales. This paper shows how to attach a refinement wrapper to any frozen weather model (TimesFM, TimeGPT, TabPFN) that mimics this iterative, multi-scale fixing without retraining the model.

Zero assumption version

Single-pass predictions miss local patterns

Weather models trained on decades of climate data make one prediction for rainfall weeks ahead. This single-pass approach works for broad patterns — El Niño years, dry seasons — but misses hyperlocal drought signals. A climatologist, by contrast, makes a first guess, sees where it fails (the residual, or leftover error), then studies that error at finer timescales to refine the guess. A naive wrapper that just asks the model to predict the error directly fails: it repeats the same single-pass blind spot.

The real challenge: How do you get a frozen model (one you cannot retrain) to act like it is reasoning iteratively when it was built for one-shot prediction?

In one sentence. Wrap a frozen weather model with a refinement layer that predicts the error at multiple timescales and feeds each correction back into the guess.

The algorithm as a flow

What it actually does

Step 1: Freeze the model

Take a pre-trained weather model (never retrain it) and lock its weights so they do not change.

Step 2: Collect first-pass error

Feed historical data through the frozen model, measure how far each prediction misses the true rainfall (the residual).

Step 3: Build three correction paths

Train three separate lightweight modules: one learns slow (monthly) error patterns, one learns medium (weekly), one learns fast (daily).

Step 4: Predict error at each timescale

For a new forecast, run all three modules on recent data to estimate the residual at each timescale.

Step 5: Combine corrections

Add the three residual predictions to the frozen model's raw forecast to get the final refined rainfall number.

What the paper changes

What the paper changes

The paper introduces a multi-resolution refinement wrapper that sits outside the frozen model. Instead of retraining the model or training one global error corrector, it trains three separate modules — each learning to correct prediction error at a different timescale (slow, medium, fast). At test time, the wrapper feeds the frozen model's raw prediction and recent history through all three modules, combines their corrections, and outputs the refined forecast.

the object it moves  =  Inference-time residual adapter (prediction-time error corrector)
The hidden quantity

The hidden quantity: Multi-scale prediction error

measured quantity  =  Decomposed residual signal

The paper measures the prediction error (residual) — the gap between the model's guess and true rainfall — and discovers that this error itself has structure: some of it is slow (changes over months), some medium (changes over weeks), some fast (changes day to day). No single model sees all three timescales well because the frozen model was built for one-pass, full-spectrum prediction.

RGMR estimates each timescale's residual separately by training three lightweight modules in parallel. Each one ignores the others and focuses on its timescale. At test time, these estimates are added back to the frozen prediction, so the final output knows which errors came from which timescale and corrects them independently.

Why it works

Why multi-scale correction works

A frozen model was trained to predict rainfall using all patterns in the data at once. It found one global best guess. But climatologists know that prediction error is not random: it clusters at certain timescales. Fast error (daily noise) looks different from slow error (seasonal drift). A single global corrector, trained on mixed error, learns to average these signals and misses both.

RGMR separates the error correction task into three independent problems, one per timescale. Each lightweight module sees only the residual at its timescale, so it can learn a precise pattern without competing with others for capacity. When you add all three corrections together, you get a refined prediction that addresses slow drifts, medium cycles, and fast wobbles in parallel, instead of trying to fix them with one blunt averaging correction.

This works because the error at each timescale has its own causal source (e.g., slow error from seasonal climate shifts, fast error from weather noise) and separating them lets each module specialize.

The refinement equation

First in words:

Refined forecast equals the frozen model prediction plus corrections from three timescale-specific residual estimators.

Then the compact form:

F_refined = F_base + R_slow + R_medium + R_fast

Every symbol:

F_refinedThe final refined rainfall forecast
F_baseThe frozen model's raw single-pass prediction
R_slowCorrection for slow timescale error (trained lightweight module)
R_mediumCorrection for medium timescale error (trained lightweight module)
R_fastCorrection for fast timescale error (trained lightweight module)
A tiny worked example
Frozen model predicts: F_base = 50 mm (its single-pass guess for monthly rainfall)
Slow timescale module predicts: R_slow = +5 mm (this month is drier than the seasonal average)
Medium timescale module predicts: R_medium = -2 mm (the past few weeks were wetter than normal, damping the coming month)
Fast timescale module predicts: R_fast = +1 mm (daily weather is trending drier right now)
Refined forecast: 50 + 5 - 2 + 1 = 54 mm (closer to the true 56 mm than the raw 50 mm guess)

Each module trains on residuals at its own frequency, so they learn independent patterns and their corrections add up without interference.

What can go wrong

What can go wrong

Timescales chosen by hand. If you pick slow, medium, fast boundaries wrongly (e.g., calling 2-week patterns slow when they are medium), the modules will not specialize cleanly and corrections cancel or reinforce randomly. The paper does not say how it chose timescales — this is a hidden hyperparameter.
Overfitting the residual. The three modules see the same ground-truth error data just at different frequencies. If they memorize historical errors, they will fail on new climate regimes (e.g., a never-before-seen drought pattern).
Backbone model must be good enough. If the frozen model is already terrible on a region, refinement adds noise. The wrapper assumes the base forecast is in the right ballpark and just polishes it.
Done right. Validate timescale choices on held-out climate years. Use regularization to prevent residual overfitting. Test on multiple architectures (TimesFM, TimeGPT, TabPFN) to ensure the wrapper is genuinely architecture-agnostic.
What a runnable demo should prove

What a runnable demo should prove

Build a toy drought forecaster using synthetic rainfall data with known slow drift (yearly), medium cycle (monthly), and fast noise (daily). Train a baseline model (e.g., a simple neural network) on the first two years. Freeze it. Then train RGMR's three modules on the residuals from a validation year. Test on held-out data from year four and measure whether the multi-scale corrections reduce error compared to the frozen model's raw forecast.

Error_reduction = (MSE_frozen - MSE_refined) / MSE_frozen × 100%

The demo must make clear that RGMR does not retrain the base model (it stays frozen) and that each of the three modules learns a genuinely different error pattern (by plotting their separate predictions, you see they do not overlap).
