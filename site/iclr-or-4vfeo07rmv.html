Chain-of-Decomposition for Knowledge Base Question Answering

Break down knowledge base question answering into separate retrieval, reformulation, and verification steps so the LLM only handles the hard part.

Paper explainersAll themesGraph & Geometric Learning

Knowledge base question answering means answering questions by reasoning over structured data: a network of facts connected by relationships. Today's language models struggle because they have to do everything at once: find relevant facts, organize them, and reason through the answer. This paper breaks the task into three separate, simpler pieces: a fast tool finds the facts, a rule-based tool organizes them, and the language model only has to verify if the reasoning is sound.

Zero assumption version

The all-at-once trap

Today, when you ask a language model a question about facts in a database (like "who did Robert Pattinson marry?"), the model tries to do everything in one go: search through millions of facts, figure out which ones matter, connect them together into a chain of logic, and output the answer. This is exhausting and expensive, especially when the knowledge base is huge.

A beginner might try: prompt the model with the whole database, hope it reads through everything, and answers correctly. But this fails because the database is enormous (too big to fit), the model gets confused by irrelevant facts, and it has to invent connections that should follow from pure logic.

The paper's move in one sentence. Stop asking the language model to do retrieval and rule-following; instead, use fast tools to fetch and organize the facts, and have the model only check if the reasoning is logically valid.

The algorithm as a flow

What it actually does

Fast retrieval

A simple index-based tool finds facts related to the question without running the language model.

Rule application

A logic rule engine converts raw database facts into explicit reasoning chains, like IF X married Y THEN...

Path assembly

The reformulator creates one clean path from question to candidate answer, e.g., 'To find who Robert Pattinson married, follow the spouse link.'

Verification

The language model reads the reasoning path and outputs yes or no: does this path logically answer the question?

Train only the verifier

Fine-tuning touches only the verification model; retrieval and reformulation stay fixed, so training is fast and cheap.

What the paper changes

What the paper changes

Instead of asking the language model to find and organize facts, the paper changes what the model does to just one task: verify if a pre-made reasoning path answers the question correctly.

the object it moves  =  model's role
The hidden quantity

Logical validity

measured quantity  =  path coherence score

The paper measures whether a reasoning chain makes logical sense given the question and knowledge base. This is the score the language model learns to output: a number from 0 to 1 saying 'does this path actually answer the question?'

The model computes this by reading the original question, the facts in the path, the reasoning rules applied, and the final answer, then judging if every step follows logically. The paper trains on examples where humans labeled whether each path was sound; the model learns what valid reasoning looks like because it sees many labeled examples and adjusts its weights to match the human labels.

Why it works

Why splitting the work matters

The reason this works is that retrieval and rule-following are already solved: graph indices are fast, logical rule-following is automatic. The only hard part is judging whether a path actually answers the original question, which requires understanding both the question and subtle differences between paths. By isolating that judgment task, the model can focus fully on learning what counts as valid reasoning without wasting energy on tasks it could outsource.

A concrete example: if you ask 'who did Robert Pattinson marry?', the retriever finds a dozen paths (spouse links, character relationships, rumors in the data). The reformulator turns each into a logical chain. The model then only has to learn 'spouse link answers marriage questions, but character link does not.' This is easier than learning to search and reason at the same time, so even a small model learns it well.

The verification formula

First in words:

For each reasoning path, the model outputs a score saying how likely the path correctly answers the question. The score depends on the path's logical structure, the rules applied, and how well each step connects to the last.

Then the compact form:

validity_score = sigmoid( w_q * embed(question) + w_p * embed(path) + w_r * embed(rules) )

Every symbol:

validity_scorenumber from 0 to 1 rating whether the path answers the question
w_qlearned weight showing how much the question matters
embed(question)list of numbers representing the question's meaning
w_plearned weight for the reasoning path
embed(path)list of numbers representing the path's facts and connections
w_rlearned weight for the logic rules applied
embed(rules)list of numbers representing which rules were used
sigmoidfunction that squashes any number into the range 0 to 1
A tiny worked example
Question embedding: [0.5, -0.2, 0.8]
Path embedding (spouse link): [0.9, 0.3, -0.1]
Rules embedding (marriage rule): [0.6, 0.7, 0.2]
Learned weights: w_q=2.0, w_p=1.5, w_r=1.8
Dot product: 2.0*(0.5) + 1.5*(0.9) + 1.8*(0.6) = 1.0 + 1.35 + 1.08 = 3.43
After sigmoid: 1/(1+e^-3.43) = 0.97, meaning 97% confidence this path is valid.

The model learns weights by seeing many examples of paths that do and do not answer questions correctly.

What can go wrong

What can go wrong

Retrieval step misses the answer. If the index does not find any path that actually leads to the right answer, the model cannot verify it, because the model can only rank and judge paths it sees. This happens when the knowledge base is missing facts or when relationships are named inconsistently across the data.
Reformulation applies wrong rules. If the rule engine misidentifies which logical rules apply to the facts, it builds an invalid path. The model then learns to reject a path that happens to be right, or accept a wrong one.
Model confusion on similar paths. If two paths look very similar but only one is valid, the model might score them the same if it has not seen enough examples of the difference.
Done right. The retriever must index every relationship in the knowledge base, because missing facts mean missing paths. Reformulation rules must cover all reasoning types in the benchmark, because a rule that is not defined cannot build a path. Training examples must include tricky pairs of similar valid and invalid paths so the model learns to tell them apart, because without such examples the model will guess randomly on close calls.
What a runnable demo should prove

What a runnable demo should prove

Build a small knowledge base with 50 entities and 200 facts (relationships like spouse, parent, writes_book). Hand-write 10 reasoning rules (if X spouse Y, then married(X,Y)). Create 20 test questions and have humans label whether each of 5 candidate paths answers it. Train a small language model as the verifier on 80 labeled path-question pairs. On the 20 test questions, measure accuracy: what fraction of the time does the verifier pick the truly valid path?

accuracy = (count of questions where top-ranked path is valid) / (total test questions)

The demo must show that the verifier learns to distinguish valid from invalid reasoning paths even when they are structurally very similar.
