View Space: Learning Representation across Arbitrary Graphs

Learn a shared representation space for graph data so that a single pretrained model works on graphs with different numbers and types of features.

Paper explainersAll themesGraph & Geometric Learning

When you train a model on one graph dataset and try to use it on a different graph, it fails because the new graph has different features (different numbers of them, different meanings). This paper proposes that graphs have an additional structure beyond just their features—a view space—that lets one model work across all of them. This opens the door to foundation models for graphs, the way pretrained language models work for text.

Zero assumption version

The graph feature mismatch

A graph is a structure of nodes (points) connected by edges (links). Each node usually has features (measurements or descriptions). When you train a neural network to classify nodes on one graph, the network learns to read that specific set of features. But graphs in the wild differ wildly. One graph describing biochemistry has 600 features per node. Another graph showing citations has only 4. A naive approach would be to retrain the model on each new graph from scratch, which is slow and defeats the point of pretraining.

The core problem: the feature dimension (the number of features per node) changes from dataset to dataset. Everything inside a trained neural network is wired to expect exactly 600 inputs (or 4, or whatever). Trying to feed it a different number breaks it immediately.

The core idea in one sentence. View space is an alternative way to represent graphs that depends on graph structure instead of feature count, letting one model handle any number of features.

The algorithm as a flow

What it actually does

Observe the structure axis

Graph structure (which nodes connect to which) stays the same even if features change. Treat this separately from features.

Define view space

A representation space that depends on graph topology, not feature count. Size of this space is fixed and shared across all graphs.

Map features into view space

Learn a mapping (called Graph View Transformation) that compresses any set of features into the fixed view space. Different feature counts all become the same size.

Process in view space

Once in view space, use standard graph neural network operations (message passing between neighbors) that work the same way for all graphs.

Train once, use anywhere

Pretrain on one large graph. Apply to any other graph's features without retraining, because the view-space bottleneck standardizes the input.

What the paper changes

What the paper changes

The paper changes how information enters a graph neural network. Instead of feeding node features directly, it adds a learned layer that transforms features into a fixed-size view space first. This transformation is the only thing that must adapt to the new feature count; everything after it stays the same.

the object it moves  =  feature input pathway
The hidden quantity

Feature-to-structure alignment

measured quantity  =  alignment score

The paper implicitly measures how well features encode the graph's structure. When a node's feature vector aligns with the roles that node plays in the topology (central vs peripheral, well-connected vs isolated), the transformation to view space preserves more signal. When features are misaligned or noisy, the transformation loses information.

The paper uses recurrent message passing in the view space to iteratively refine this alignment. Each round of message passing lets nodes talk to neighbors, which re-weights how much each feature matters for predicting labels.

Why it works

Why it works: the structure-feature decoupling

Graph structure (the topology itself) contains signal independent of the features on it. A node that is central in the graph is useful to know about whether or not its features say so. By separating structure (graph topology) from its description (features), the method can learn one model that adapts the description layer while keeping the structure-reading part fixed.

Here is the causal chain: (1) Graph topology is universal—all graphs have neighbors. (2) Feature counts vary, so a fixed network layer breaks on new feature sizes. (3) Learn a mapping from any feature count into a fixed view-space size. (4) In view space, message passing works the same for all graphs because it only looks at topology. (5) Train once in view space, test anywhere because the transformation layer automatically adapts to new feature counts. The transformation acts as a universal adapter that leaves structure-processing unchanged.

Math after the picture

The view transformation equation

First in words:

Each node's features get transformed into view space by a learned matrix multiply, then message passing iteratively updates representations using neighbor information.

Then the compact form:

v_i^(t) = recurrent_cell( w( f_i ), { v_j^(t-1) for j in neighbors(i) } )

Every symbol:

v_i^(t)the view-space vector for node i after round t
f_ithe original feature vector for node i
w( f_i )the learned transformation from features f_i into view space
neighbors(i)the set of nodes connected to node i by an edge
recurrent_cella neural network cell that combines own view and neighbor views
A tiny worked example
Start with node A (biochemistry graph): 600 features.
Transform w(f_A) maps 600 numbers into view space (say, 32 dimensions).
Neighbor nodes B and C also transform their features into 32 dimensions.
Recurrent cell reads: own 32 dims + neighbor B's 32 dims + neighbor C's 32 dims = 96 inputs.
Cell outputs new 32-dim view vector for node A after round 1.
Same recurrent cell works on node X in citation graph with only 4 features.
Transform w(f_X) maps 4 numbers into same 32-dimension view space.
Neighbors transform too, cell runs same operation, same output size: 32 dims.
One model, two graphs, zero retraining.

The transformation w is learned during pretraining; at test time, it automatically adapts to new feature counts because it is applied first, before any fixed-size operations.

What can go wrong

What can go wrong

Feature-to-label disconnect. If the features on a new graph are completely unrelated to the label you want to predict, the model cannot recover. Example: predicting biochemistry function from citation counts. The transformation will map nonsense into view space, and no message passing fixes that.
Topology mismatch. If the new graph's structure (which nodes are neighbors) is fundamentally different from the pretraining graph, the learned message-passing patterns may not apply. A densely connected molecule versus a sparse social network have different neighbor statistics.
Extreme feature sparsity. If the new graph has very few features and they are highly redundant (all the same value, or highly correlated), the transformation loses information and cannot reconstruct distinguishing details that matter for labels.
Done right. Pretraining on a large, diverse graph with many useful features helps, because the transformation layer learns which patterns across feature types signal structure-relevant information; at test time, it reuses that learned extraction pattern for any new feature set.
What a runnable demo should prove

What a runnable demo should prove

Train the model on one large graph (e.g. OGBN-Arxiv: citation network with 169,000 papers and 40 feature dimensions). Freeze the model. Now run it on a different graph (e.g. a molecular property dataset with 1,000 atoms and 9 features, or a social network with 50,000 nodes and 10 features) without retraining anything. Measure how many nodes it classifies correctly on each new graph.

accuracy_unseen_graph = (nodes correctly predicted on new graph) / (total nodes on new graph)

The demo must show that a single pretrained model scores well on graphs that were never seen during training and have completely different feature counts.
