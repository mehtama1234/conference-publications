AnalogVerifier: A Neuro-Symbolic Framework for Analog Circuit Verification

AnalogVerifier turns loose circuit specifications into ordered testbench tasks, then checks numbers and repairs failures with deterministic tools.

Paper explainersAll themesAgents & Tool Use

Analog circuit verification is hard to automate because the specification is usually written in loose engineering language while the final testbench must obey exact signal dependencies and exact numeric limits. A plain language model struggles here because it can misread dependencies, mix up task order, or invent thresholds. AnalogVerifier splits the job into four smaller parts so the language model handles interpretation while symbolic tools handle ordering and exact numeric grounding.

Why analog verification resists plain language-model automation

An analog verification spec may say things such as: sweep this input range, wait for settling, measure gain at this node, and reject the design if a voltage crosses a limit. Those instructions are spread across prose, tables, and domain conventions. A testbench generator has to convert them into an ordered executable plan.

That conversion is brittle because order matters. Some checks depend on earlier setup steps, some ports must be driven before others, and numeric limits must match the spec exactly. If a generated testbench gets even one dependency or threshold wrong, the run can fail or produce a misleading pass.

The paper's move in one sentence. Let the language model break the spec into atomic tasks, then use symbolic scheduling, deterministic numeric grounding, and repair from simulation feedback so the final testbench obeys design rules.

The algorithm as a flow

What it actually does

Serialize the spec into atomic tasks

The system breaks the mixed specification into small test actions so each requirement can be handled separately.

Build a port dependency graph

Task dependencies are written as a graph so the system can determine which signals and checks must happen before others.

Ground numeric limits with a symbolic oracle

Exact thresholds are computed by deterministic rules or calculators so the final testbench uses the correct values.

Generate the testbench in the required order

The ordered tasks are converted into executable verification code.

Run simulation and repair

Simulation feedback reveals missing coverage or failing logic, and the system revises the testbench until it passes functional checks.

What the paper changes

What the paper changes

The paper changes the path from specification text to final verification code. Instead of asking one model to do interpretation, ordering, arithmetic, and repair in a single pass, it assigns those roles to separate components because each part of the job needs a different kind of reliability.

The hidden quantity

The hidden quantity

measured quantity  =  Specification faithfulness

Specification faithfulness asks whether the produced testbench still means the same thing as the original engineering spec. This quantity is hidden because a testbench may run without obvious errors while still checking the wrong order or the wrong numeric limit.

AnalogVerifier raises faithfulness by separating interpretation from enforcement. The language model proposes atomic tasks, but symbolic scheduling and deterministic threshold derivation constrain the output so the testbench stays closer to the source requirements.

Why it works

Why it works

The main gain comes from dividing the job by failure mode. Language models are useful for turning messy text into candidate tasks because they can read broad specification language. They are less trustworthy for strict ordering and exact numeric derivation. AnalogVerifier improves reliability by moving those strict parts to deterministic components.

Closed-loop repair adds a second gain because simulation gives concrete evidence about what is missing. If a testbench fails or lacks coverage, the repair step has a grounded signal to act on, so revisions are guided by execution results instead of guesswork.

The scheduling rule

First in words:

A task can run only after all tasks it depends on have already been scheduled.

Then the compact form:

sched(task_j) > sched(task_i) for every dependency task_i -> task_j

Every symbol:

task_ian earlier verification task that another task depends on
task_ja later verification task that needs task_i first
sched(task)the position of a task in the final execution order
task_i -> task_ja dependency relation from the graph
A tiny worked example
Task 1: set bias current.
Task 2: wait for the circuit to settle.
Task 3: measure output gain.
Task 4: compare gain against the allowed limit.
Task 3 depends on Task 1 and Task 2 because measuring before setup gives nonsense.
Task 4 depends on Task 3 because the comparison needs the measured value.
A valid schedule is [1, 2, 3, 4].

The paper uses a port dependency graph to encode these order rules before testbench generation.

What can go wrong

What can go wrong

Wrong task serialization. If the first step breaks the spec into the wrong atomic tasks, later symbolic checks cannot fully recover because the meaning was already distorted.
Missing dependency edges. If the dependency graph omits a real constraint, then the scheduler may produce an invalid order because it never knew that relation existed.
Weak repair signal. If simulation feedback is too coarse, the repair step may know that the testbench failed but not why, so the fix becomes harder to target.
Done right. The framework is most useful when specifications are heterogeneous and order-sensitive, because that is where symbolic enforcement and execution feedback add the most value.
What a runnable demo should prove

What a runnable demo should prove

Take a small analog component such as an amplifier with a short mixed-format spec. Build two pipelines: one plain text-to-testbench generator and one staged pipeline with task serialization, dependency scheduling, exact threshold grounding, and repair after simulation. Compare pass rate, number of manual edits, and coverage of required checks. The demo should show that the staged system produces more faithful testbenches because the strict parts of the job are enforced by deterministic tools.

pass_rate = passing_testbenches / total_testbenches ; repair_load = manual_edits / total_testbenches

The demo must show fewer manual fixes and more correct end-to-end verification runs.
