Test Cases, Not Proofs: A Smarter Way to Check LLM Specifications

To fairly measure whether LLMs can write formal specifications, test them on concrete cases instead of asking hard proofs.

Paper explainersAll themesLLMs & Foundation Models

Writing formal specifications is so tedious that most programmers skip it. LLMs have gotten good at writing verified code, but can they write the specifications themselves? Existing tests try to prove the LLM's rule is equivalent to the reference rule, which is so hard that it conflates the LLM's writing ability with the theorem prover's proving ability. This paper proposes a smarter test: check whether the LLM's specification correctly accepts or rejects concrete test cases. It is much easier to verify and isolates specification quality from proof difficulty.

Zero assumption version

The unfair test for LLM specifications

A formal specification is a set of rules that tell a computer what a program is supposed to do. For example: given a list, return a new list where every element at position 3, 6, 9 is sorted and all others stay in place. Writing these rules by hand is slow and expensive.

Programmers want LLMs to write specifications for them. But how do you know if the LLM's specification is correct? The obvious test is: can a theorem prover prove that your LLM-written rule and the reference rule are identical? The catch: that proof is extremely hard. A flawed specification and a good one might both fail to prove. The test result tells you almost nothing about the LLM, only about how hard the proof is.

The problem. You cannot tell if a specification is bad because it is wrong, or because the proof is hard.

The algorithm as a flow

What it actually does

Prepare test cases

For each HumanEval problem, create correct test cases by running the reference Python function. Create wrong test cases by mutating the function, these produce answers spec should reject.

Prompt the LLM to write Rocq

Give the LLM the problem in plain English, the reference code, ask it to write a Rocq formal specification.

Syntax check

Does the Rocq code compile without syntax errors? Only valid specifications proceed to next stage.

Run against test cases

Instantiate the LLM's specification on each test case and ask: does Rocq prover accept this case or reject it?

Score: what fraction passed

Specification quality is how many test cases it got right. High pass rate means LLM captured true rule, low rate means it wrote something vague or wrong.

What the paper changes

The one thing the paper changes

The paper replaces the evaluation method: instead of asking a theorem prover to prove logical equivalence, it feeds the LLM's specification concrete test cases and checks whether the specification correctly accepts or rejects each case. Equivalence proofs are abandoned; specification quality is now measured by test case agreement.

The hidden quantity

The hidden quantity: specification quality score

measured quantity  =  Fraction of test cases accepted correctly

The paper measures one hidden quantity: what fraction of the test cases does the LLM's specification handle correctly? For positive cases (correct outputs), the spec should accept. For negative cases (wrong outputs), the spec should reject. If a spec gets 80 out of 100 cases right, its quality score is 0.80.

The paper estimates this by instantiating the formal specification on each test case and recording whether the Rocq prover can discharge the proof obligation. This is fast because each case is concrete; no general proof required.

Why it works

Why test cases are smarter than equivalence proofs

Proving two formal rules are logically equivalent is a foundational problem in mathematics. A proof might take hours or fail to terminate, even if both rules are correct and simple. This buries the real question: did the LLM write a good rule or not?

Test cases turn this around. Each test case is a single concrete input and its expected output. When you instantiate the specification on a concrete case, the prover does not search for a general proof. It just checks: does this specific answer satisfy this specific rule? For a well-written specification, this check is fast and unambiguous. If the spec is wrong, it fails on concrete cases quickly.

Why this works: asymmetric reasoning. A successful proof that a case satisfies the specification is reliable evidence that the spec is correct on that case. A failed proof is ambiguous, maybe the spec is wrong, or maybe the proof is just hard. But on concrete cases, failures usually mean the spec is wrong, not that the proof is too hard. Test case instances separate specification quality from prover capability.

Math after the picture

The scoring equation

First in words:

specification_quality equals the number of correctly handled test cases divided by total test cases. For each test case a case is correctly handled if either the case is positive and spec accepts it or the case is negative and spec rejects it.

Then the compact form:

quality = sum(correct_judgments_i) / total_cases

Every symbol:

correct_judgments_i1 if spec handles case i right, 0 otherwise
total_casestotal number of test cases positive and negative
qualityfraction of cases handled correctly from 0 to 1
A tiny worked example
Suppose 10 test cases total: 5 positive correct outputs, 5 negative wrong outputs.
Spec correctly accepts all 5 positive cases, 5 points.
Spec incorrectly accepts 2 of 5 negative cases, correctly rejects 3, giving 3 points.
Total correct: 5 plus 3 equals 8 out of 10. Quality score equals 8 divided by 10 equals 0.80.

The score measures honest specification correctness: can the LLM's rule distinguish right answers from wrong ones on concrete examples?

What can go wrong

What can go wrong

LLM refuses to write Rocq. Some LLMs cannot generate syntactically valid Rocq code, so the spec fails syntax check and never reaches test stage. This is a capability limit of the model.
Insufficient test cases. If you only test a few cases, a spec might pass by accident even though it misses edge cases. The method requires enough positive and negative cases to cover rule boundaries.
Proof attempts time out. For complex specifications, even concrete case instantiation can take too long to prove because the Rocq prover must search through all the logical rules that could apply to the spec, and for a complicated spec this search space explodes. Paper allows LLMs three attempts with compiler feedback, but some specs remain intractable because their logical structure is inherently expensive for the prover to verify.
Done right. When test cases are representative of rule behavior, instantiation-based evaluation cleanly separates specification quality from prover capability and gives honest quality score.
What a runnable demo should prove

What a runnable demo should prove

Build a small Python script that takes one HumanEval problem and reference implementation, prompts an LLM to write Rocq specification for it, generates 5 positive test cases by running the reference function on sample inputs, generates 5 negative test cases by mutating the reference and running it to get wrong answers, instantiates the LLM's specification on each case using Rocq backend, scores how many cases the spec handled correctly.

pass_rate = correct_positive_accepts plus correct_negative_rejects divided by 10

The demo makes it obvious: good LLM spec immediately agrees with test cases because the spec correctly encodes the rule the test cases embody, and bad spec does not because it encodes a different or incomplete rule. No proof needed because you can see correctness directly from concrete answers.
