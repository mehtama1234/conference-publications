Zephyrus: an agentic framework for weather science

Pair a language model with weather-specific tools so it can reason about both language questions and high-dimensional meteorological data.

Paper explainersAll themesAgents & Tool Use

Weather forecasting models are excellent at crunching numbers but cannot answer questions posed in natural language. Language models can read and reason about text but cannot directly work with weather datasets. Zephyrus solves this by building a conversational agent that speaks in English while having direct access to weather data, forecasting tools, and geographic information. The agent breaks down a question into Python code, runs it against real weather data, and refines its answer based on what it observes.

Zero assumption version

Two separate worlds collide

Weather forecasting models like Stormer are neural networks trained to predict wind speed, temperature, and rainfall from numerical weather data. They work well when you feed them gridded numbers. But they cannot answer questions like Where will the heaviest rain fall next Tuesday in Texas? because they do not understand English.

Language models like Claude understand human questions and can reason about concepts. But they have no access to meteorological data or the tools to look up real numbers. A beginner might try to give a language model a dump of weather data and ask it to solve the problem—but the model would not know how to select the right grid points, compute regional averages, or call a forecasting tool.

The real world needs both: a system that understands a person's question, consults actual weather data, and gives an honest answer grounded in numbers.

The paper's one move. Build a Python environment that wraps weather tools and data, then pair it with a language model that can write and run Python code in a loop: read the question, write code, run it on weather data, see the result, refine the code if needed.

What it actually does

A conversation between human and agent begins; the human asks a weather question in natural language.

Generate code

Language model writes Python code to solve the problem using the ZephyrusWorld toolkit (dataset access, forecasting, geoquerying).

Execute safely

Code runs in a sandboxed server; results and any error messages are captured and returned.

Observe and decide

Agent reads the output, decides if the answer is complete, or refines the code for another iteration.

Reply to human

Agent converts the data result into a natural language response and presents it back to the user.

What the paper changes

What the paper moves: the control flow

The paper introduces ZephyrusWorld: a Python environment where tools (dataset access, forecasting, geoquerying, climatology) are exposed through clean function calls. Instead of the weather model and language model working separately, the language model now controls the flow. It reads a question, writes Python code that calls ZephyrusWorld functions, observes the result, and decides what to do next.

The hidden quantity

The hidden quantity: task resolution

measured quantity  =  Task resolution

Task resolution is the core metric: did the agent actually answer the human's question correctly? Unlike a simple classification benchmark where you just measure accuracy, here every question has multiple steps—looking up geography, fetching data, running a forecast, comparing results. Task resolution measures whether the agent completed all those steps and arrived at a correct numerical answer.

The paper measures this by generating thousands of question-answer pairs from templates, computing ground truth using human-verified Python code applied to real weather data (ERA5), and then scoring whether the agent's code produced the right number. For location-based questions, the paper matches the agent's output to a standard geographic database and computes distance; for numeric questions, it checks if the answer is within tolerance.

Why it works

Why it works: the conversion loop

A language model alone cannot write correct code because it has no way to test and debug. It produces a plausible-sounding script and sends it, hoping for the best. If the code fails (a typo, a wrong variable name, a misunderstood API), the model never knows.

Zephyrus closes that loop. The language model writes code, the execution server runs it, and the server sends back the output and any error messages. The model then sees exactly what went wrong—KeyError: region_name or RuntimeError: forecast model expects shape (8, 721, 1440)—and rewrites the code to fix it. This is the core mechanism: immediate feedback accelerates learning. The model refines the code iteratively until it succeeds. Because weather data has a single ground truth (the ERA5 reanalysis is the data), the model can verify its answer by inspection and stop when it is right.

Easy questions (find the coldest temperature on a specific date) succeed on the first try because the model generates correct code immediately. Harder questions (identify the most extreme rain event in the past decade and explain its meteorological context) require multiple refinements; the model must write code, read error messages, adjust, and iterate. This is where harder tasks fail more: the problem space is too large for the model to reliably explore in a few turns.

The scoring equation

First in words:

correctness = sum of (1 if answer matches ground truth) divided by total questions, weighted by difficulty and task type

Then the compact form:

correctness = (1 / N_total) * sum_i [ 1 if agent_answer_i matches ground_truth_i else 0 ]

Every symbol:

N_totaltotal number of benchmark questions
agent_answer_ithe answer produced by Zephyrus for question i
ground_truth_ithe correct answer computed from ERA5 data
1 if ... else 0indicator: 1 point for a correct answer, 0 for incorrect
A tiny worked example
Suppose ZephyrusBench has 100 questions (20 easy, 30 medium, 50 hard).
Easy questions: Zephyrus gets 18 right (90% accuracy). Easy contribution: 18.
Medium questions: Zephyrus gets 21 right (70% accuracy). Medium contribution: 21.
Hard questions: Zephyrus gets 15 right (30% accuracy). Hard contribution: 15.
Total correct: 18 + 21 + 15 = 54.
Overall correctness = 54 / 100 = 0.54 or 54%. On easy tasks alone, Zephyrus beats text-only baselines (which scored ~30% on easy). On hard tasks, Zephyrus and text-only both score ~30%, showing the gap closes where reasoning is deepest.

The paper does not show a closed-form formula; this equation formalizes the scoring described in Section 4.2 (measured from actual benchmark results).

What can go wrong

What can go wrong

Code generation is brittle on hard tasks. When a question requires 5 or more steps (forecast, extract a time series, find extrema, compare to climatology, explain context), the model must write code that chains these correctly. If any step is wrong, downstream steps fail. The paper shows Zephyrus plateaus at baseline performance on hard tasks, suggesting the model cannot reliably plan and execute long reasoning chains.
Geoquerying can fail silently. If a user asks about South Sudan, the geoquerier must map that name to a geographic boundary. Misspellings, ambiguous place names (London, UK vs. London, Ontario), and polygons that cross date lines can break the lookup. The agent may generate code that runs but retrieves the wrong region.
Forecast model outdates climatology. Zephyrus uses Stormer (a neural weather prediction model) and compares results to precomputed climatological means from 1979–2000. If the agent is comparing a 2025 forecast to 1979 climate statistics, the baseline changes and the comparison is invalid.
Done right: iterative code refinement works. On questions where the agent can test its code and see the result immediately (easy lookups, simple forecasts), the feedback loop catches errors and the agent converges to the right answer. This is where Zephyrus outperforms text-only baselines decisively, because the agent can verify its answer by running code against real data, whereas a text-only model must guess and cannot check whether its answer is correct.
What a runnable demo should prove

What a runnable demo should prove

A demo should show the three components working together: a natural language question, the code the agent writes, and the final answer grounded in real weather data. Specifically, build a small weather task (e.g., What was the maximum temperature in Tokyo in July 2020?) and show the agent writing Python code that calls the Stormer forecast model and the climatology tool, executing it safely, and returning the numeric answer along with a confidence interval drawn from the climatology baseline.

correctness on demo = (1 if final answer matches ground truth from ERA5 else 0) combined with iteration count (number of times the agent rewrote the code before getting it right)

The demo must make clear that the answer is not hallucinated: the agent produced code, ran it, and the number came from real meteorological data.
