SkillNet: Hierarchical Skill Modeling for Compositional Generalization

A robot learns to do new tasks by organizing its atomic behaviors in a hierarchy, then mixing and recombining them when it sees something it has never done before.

Paper explainersAll themesRobotics & Control

A robot trained on a few tasks learns a bag of repeatable atomic behaviors called skills. To generalize to new tasks it has never seen, the robot must combine these skills in new ways. This paper organizes skills into a hierarchy that captures their similarities, then uses that structure to route the right mix of skills to the right parts of new tasks, so the robot can compose learned behaviors in ways it never trained on.

Zero assumption version

The world before: skills are loose and interchangeable

When you teach a robot to pour, grasp, and place, it learns those three behaviors as separate black boxes. Each one is trained on its own task with its own rewards. But in reality, pouring and watering a plant both share something: the wrist must move a certain way. Grasping a banana and grasping a sphere both need the same finger positions.

A naive approach is to take these three skills and try to apply them one after another to a new task like filling a vase. The robot runs the pour skill, then the place skill. But the robot has no way to know which parts of pouring are relevant to filling a vase, or whether it should activate pouring experts fully or just partly. It treats every skill as an all-or-nothing switch, so it either applies the full pour or applies nothing at all.

The result: the robot fails on unseen task combinations because its skills are not connected — it cannot mix them. It cannot say 'use 70% of what you learned in pouring but only 40% of what you learned in grasping' because it has no way to measure or express what pouring and grasping share.

The fix in one sentence. Organize skills into a hierarchy that names what they share, then use that shared knowledge to decide how much of each skill to activate on new tasks.

The algorithm as a flow

What it actually does

Step 1: Name shared structure

Sort each skill by its mechanical properties (hand position, motion speed, contact force) and semantic role (pushing, rotating, inserting). Build a hierarchy of skills based on these properties.

Step 2: Train the hierarchy

Train a mixture-of-experts router that looks at the current situation and decides what fraction of each skill to activate. Use the hierarchy as a soft constraint: similar skills should activate similarly.

Step 3: Test on new tasks

On a task the robot has never seen, the hierarchy lets the router know which skills are likely to be useful based on their mechanical and semantic properties, even if that exact skill combination was never trained.

Step 4: Measure how much the hierarchy helps

Compare the robot's success on new tasks with and without the hierarchy, and compare to baselines that do not organize skills at all.

Step 5: Real-world proof

Test the hierarchical model on unseen task combinations in a real robot and in simulation. Measure improvement in success rate and generalization to zero-shot and few-shot scenarios.

What the paper changes

What the paper changes: the activation levels of expert skills

In standard mixture-of-experts, a router scores each expert as either on or off based on the immediate task. SkillNet changes this: it uses the skill hierarchy to produce soft constraints. Instead of letting each expert fire independently, it nudges similar experts to fire at similar levels, because if two skills share the same mechanical properties, they should activate together.

The actual object being changed: the routing gates (a list of numbers from 0 to 1, one per skill) are now kept close to each other if their skills are similar in the hierarchy. Pouring and watering should have close gate values because they are mechanically similar. This coupling propagates the robot's learned knowledge from one skill into neighboring skills in the hierarchy.

the object it moves  =  routing gates (expert activation levels)
The hidden quantity

The hidden quantity: skill similarity measured by the hierarchy

measured quantity  =  hierarchical skill affinity

The paper measures a quantity that does not appear in raw training data: how similar two skills are in the hierarchy. This is not just human intuition. It is built from motion codes (recorded motion patterns for each skill, like 'linear push' or 'circular rotate') and VerbNet roles (linguistic categories from a linguistic resource that sorts verbs by their arguments and actions, like 'put', 'cause to move', 'apply force'). The paper extracts these features for each skill and builds a metric: two skills are similar if they share the same motion pattern or the same semantic role.

During training, the paper estimates this affinity for each pair of skills and uses it as a soft constraint on the routing gates. The affinity matrix becomes part of the loss function: if two skills are high-affinity in the hierarchy, their gates must stay close to each other.

Why it works

Why it works: the hierarchy propagates learning across related skills

Without the hierarchy, when the robot trains on pouring, it learns expert weights for 'pour experts' and nothing else. When it sees a new task like watering a plant, it must activate from scratch, because there is no connection between pouring and watering in the model.

With the hierarchy, pouring and watering are marked as similar (same motion patterns, same semantic role). During training on pouring, the hierarchy constraint pushes the watering experts to have similar routing gates as the pouring experts. This does not require training data for watering; it happens automatically because of the constraint. When the robot later sees watering, the watering experts are already primed to similar activation levels as pouring, so the robot can do watering by mixing in the pre-learned structure. The hierarchy acts as a bridge: knowledge learned on pouring silently teaches the watering experts what to do, even without explicit watering training.

The mixture-of-experts router is key here. Instead of one 'grasp network' or one 'pour network', there are many small experts (each one learning part of a skill). The router picks which experts to activate. By constraining the routing gates of similar skills to be close, the paper makes sure that similar tasks activate overlapping sets of experts. This is why compositional generalization works: new task combinations can be solved by mixing and recombining the same experts that learned the original skills.

Math after the picture

The equation: hierarchical soft constraint on routing gates

First in words:

The loss is the standard mixture-of-experts loss plus a penalty term. The penalty term measures how different the routing gates are between similar skills, weighted by how similar they are in the hierarchy. Skill pairs that are very similar get a large penalty if their gates diverge. Skill pairs that are dissimilar get a small penalty.

Then the compact form:

loss = moe_loss + lambda * sum_ij affinity_ij * (gate_i - gate_j)^2

Every symbol:

moe_lossstandard mixture-of-experts loss (how well the selected experts solve the task)
lambdastrength of the hierarchy constraint (how much to prioritize similarity)
affinity_ijhow similar skill i and skill j are in the hierarchy (0 to 1)
gate_ithe routing gate for skill i (how much to activate it, 0 to 1)
gate_jthe routing gate for skill j (how much to activate it, 0 to 1)
A tiny worked example with two skills
Suppose pour and water have affinity 0.9 (very similar in the hierarchy).
During training on pour, the router learns gate_pour = 0.8.
Without hierarchy constraint: gate_water could be 0.2 or 0.8 or anything; no penalty.
With hierarchy constraint: if gate_water = 0.2, penalty = 0.9 * (0.8 - 0.2)^2 = 0.9 * 0.36 = 0.324.
If gate_water = 0.7, penalty = 0.9 * (0.8 - 0.7)^2 = 0.9 * 0.01 = 0.009.
The training algorithm minimizes loss, so it prefers gate_water = 0.7 over 0.2, pulling the similar skill toward the learned behavior.
Result: watering gate is primed by pouring knowledge, without any watering training data.

The affinity matrix comes from the motion codes and semantic roles; it is built once and fixed. The hierarchy constraint pulls the routing gates of similar skills together during training.

What can go wrong

What can go wrong

Hierarchy is wrong or incomplete. If the motion codes or semantic roles do not capture the real similarities between skills, the constraint does harm. Pouring and watering look similar by motion code but require different force profiles; the constraint would force watering experts to use pouring forces, breaking the new task.
Lambda is set too high. If the hierarchy constraint is too strong (lambda is large), the model is forced to make all similar skills identical, even when they need to be different. This kills specialization. On the other extreme, if lambda is too small, the hierarchy does not help at all, because the penalty term becomes negligible and the optimizer ignores the constraint, so gates diverge and skills do not transfer knowledge.
Skills are too diverse or too few. If the robot has only two skills and they are very different, the hierarchy cannot find shared structure to reuse. If skills are numerous but all highly similar, the model collapses to one expert and loses expressiveness.
Done right. The hierarchy should capture true mechanical and semantic similarities, lambda should be tuned to balance hierarchy loss and task performance, and there should be enough skills for patterns to emerge, but not so many that everything is similar.
What a runnable demo should prove

What a runnable demo should prove

Build a robot simulator with 10 base skills: pour, grasp, place, insert, rotate, flip, push, swipe, lift, lower. Train a mixture-of-experts model with the hierarchy constraint on 20 tasks that combine 2-3 skills each. Hold out 10 unseen task combinations (like 'insert while rotating' or 'grasp then lift'). Test zero-shot transfer: run the trained model on the held-out tasks without any new training data. Measure success rate on the held-out tasks.

generalization_gain = (success_rate_with_hierarchy - success_rate_without_hierarchy) / success_rate_without_hierarchy

The demo must show two things: (1) the hierarchy improves success on unseen task combinations by at least 15%, because the soft constraint couples similar skills, allowing knowledge from one skill to transfer to similar ones; (2) similar skills activate at similar gate values, proving the constraint is actually working.
