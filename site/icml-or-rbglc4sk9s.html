AutoRPA: Efficient GUI Automation through LLM-Driven Code Synthesis from Interactions

AutoRPA watches how a search-heavy GUI agent solves a task, rewrites those actions into reusable procedures, and compiles them into direct automation code so repeated jobs run cheaply.

Paper explainersAll themesAgents & Tool Use

A GUI agent that reasons from scratch at every click can solve hard tasks, but the repeated reasoning cost becomes wasteful on routine office work. Traditional Robotic Process Automation avoids that runtime cost because it executes fixed code, yet people usually have to write and maintain that code by hand. AutoRPA connects those two worlds. It first lets a strong interactive agent solve tasks. It then rewrites the observed action traces into reusable procedures and turns those procedures into automation code. The key idea is to distill expensive interactive behavior into reusable programs so the next similar task runs as direct automation instead of fresh reasoning.

Zero assumption version

Why repeated GUI reasoning is expensive

A modern GUI agent can open windows, read on-screen text, choose buttons, and recover from minor mistakes. That flexibility is useful on new tasks, but it is expensive on tasks that repeat every day. If the agent re-plans every step each time, you keep paying for full reasoning even when the answer is already known from yesterday's run.

Classic automation has the opposite tradeoff. It runs quickly because it executes fixed code, but that code is brittle and costly to write by hand. The paper asks whether an interactive agent can produce that code automatically by solving examples first and then compiling its own behavior into reusable automation procedures.

The move. Use an interactive GUI agent to generate demonstrations, translate those demonstrations into soft reusable procedures, and then build direct automation code from multiple successful runs so repeated tasks execute cheaply.

The algorithm as a flow

What it actually does

Collect successful interaction traces.

Run a strong GUI agent on example tasks and save the screen states, chosen actions, and outcomes so that later stages can learn from real task executions.

Translate literal actions into procedures.

Replace hard-coded values such as exact screen positions with screen-dependent procedures because reusable automation must adapt when similar tasks differ in details.

Build automation code from several traces.

Use retrieval over earlier successful runs to synthesize one automation function that captures shared structure across related tasks.

Execute the generated code.

Run the automation in the real GUI so that failures appear as concrete execution errors rather than hidden design mistakes.

Repair with a hybrid strategy.

Use direct automation when it works and fall back to interactive reasoning only on failing steps, because targeted repair is cheaper than re-running the entire task interactively.

What the paper changes

What the paper changes

The paper changes GUI automation from hand-written scripts or permanently interactive agents into a distillation pipeline that converts solved interaction traces into reusable automation functions.

the object it moves  =  task-solving behavior turned into reusable GUI code
The hidden quantity

The hidden quantity: procedural stability

measured quantity  =  how well a translated procedure stays correct when the same task appears with small screen-level variation

The key quantity is procedural stability. A raw trace can solve one exact instance and still fail on the next one if it depends on brittle details such as one fixed button location or one fixed row number. A useful automation procedure must keep the task logic while dropping the accidental details of the original run.

AutoRPA estimates this stability by comparing several successful traces for similar tasks. If the same high-level step appears across runs even when screen content changes, that step is a good candidate for reusable code. If a step only works in one trace, the system knows that it should not be copied blindly.

Why it works

Why it works

Interactive agents are good teachers because they can solve tasks that we do not yet know how to script. Once a task is solved a few times, those traces reveal repeated structure: find a field, extract a value, open the right page, submit the form, and verify completion. That repeated structure is exactly what an automation function needs.

The translator stage matters because raw traces are too literal. A click at coordinates alone is not reusable, but a step that says 'open the row whose label matches the request' can survive small interface changes because it refers to the task meaning instead of one screen accident.

The builder stage matters because one trace is often too noisy. Several traces expose which parts are stable and which parts are incidental. Verification then closes the loop. When execution fails, the repair stage can modify only the weak part instead of restarting from zero, so the final function becomes cheaper and more reusable over time because repeated full interactive runs are no longer needed for every similar task.

Math after the picture

The reuse objective

First in words:

Choose the automation function that solves the current batch of similar GUI tasks while minimizing repeated reasoning cost and preserving execution success.

Then the compact form:

score(function) = success_rate(function) - lambda * repeated_reasoning_cost(function)

Every symbol:

functiona candidate generated automation procedure
success_rate(function)fraction of similar GUI tasks that the generated procedure completes correctly
repeated_reasoning_cost(function)how much expensive interactive reasoning is still needed at runtime
lambdahow strongly we penalize repeated runtime reasoning
A tiny worked example
Suppose function A solves 9 of 10 invoice-entry tasks and still calls the interactive agent on 6 steps per task.
Suppose function B solves 8 of 10 tasks and calls the interactive agent on only 1 step per task.
If lambda is small, A may be preferred because success matters most.
If lambda is larger, B may win because it preserves most of the success while removing far more repeated reasoning cost.
AutoRPA aims for functions that keep success high and runtime reasoning low because that combination makes repeated GUI work practical.

The equation captures the paper's central tradeoff: preserve task success while distilling away repeated expensive reasoning.

What can go wrong

What can go wrong

The translated procedure may still be too literal. If generated code depends on one exact screen layout, it will fail on nearby tasks because the distillation step did not remove the brittle details.
Too few traces can hide the true task structure. With only one or two demonstrations, the builder may overfit accidental choices because it cannot see which steps stay stable across related tasks.
Repair may patch symptoms instead of causes. A local fix can make one failing run pass while preserving a weak procedure, so repeated failures can continue because the underlying task logic was never rewritten well.
Done right. The method works best when several successful traces are available and verification is used to refine only the unstable parts, because that produces automation code that is both cheap and reusable.
What a runnable demo should prove

What a runnable demo should prove

Build a small desktop workflow such as invoice entry, customer record updates, or repeated form submission. First solve a set of examples with an interactive GUI agent and save the traces. Then generate one reusable automation function and test it on similar tasks with changed field values and small layout differences. Measure task completion and how often the system still needs expensive interactive help. The demo should show that direct automation handles most of the repeated work because the solved traces have been distilled into reusable code.

reuse_gain = solved_tasks_without_fresh_reasoning / total_similar_tasks

A convincing demo must show that the generated automation function keeps task success high while cutting repeated reasoning cost, because that is the paper's main promise.
