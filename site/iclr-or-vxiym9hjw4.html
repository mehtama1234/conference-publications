Bridging ML and algorithms: comparison of hyperbolic embeddings

The algorithm from the computer science algorithms community is 100 times faster than machine-learning methods while producing equally good or better embeddings of hierarchical networks.

Paper explainersAll themesGraph & Geometric Learning

Hyperbolic space is a mathematical structure where distances grow exponentially as you move away from the center, fitting hierarchical structures like trees naturally. Two research communities study how to convert networks and hierarchies into embeddings (numerical vectors) in this space: computer scientists and machine learners. They developed different algorithms independently and never directly compared them. This paper compares performance and quality head-to-head, finding that an algorithm from the algorithms community vastly outperforms the popular machine-learning embeddings that were widely accepted as the best approaches because it uses direct mathematical construction instead of slow iterative optimization.

Zero assumption version

Two communities, separate algorithms, no comparison

Hyperbolic embeddings map networks and hierarchies into vectors (lists of numbers) using hyperbolic space, where the amount of room available expands exponentially as you move away from center, naturally fitting tree-like hierarchies. Computer scientists and machine learners both study this problem, but they work independently and publish in separate venues, so they never directly tested which approach is faster or produces better embeddings.

A naive approach would be to try each method and hope for the best, but practitioners did not know how much time or quality they were sacrificing. The popular machine-learning approaches (Poincaré embeddings from NIPS 2017 and Lorentz embeddings from ICML 2018) were well-cited, so most practitioners assumed they were close to optimal. Without a direct benchmark, no one knew a simpler algorithm from the algorithms community was available.

In one sentence. The paper directly measures and compares the speed and quality of hyperbolic embedding algorithms across both research communities on real networks.

What it actually does

1. Gather test networks

Collect real-world hierarchies and networks, plus simulated networks with known structure.

2. Run embedding methods

Apply Blsius (algorithms), Poincaré (ML), and Lorentz (ML) to each network and measure wall-clock time.

3. Score embedding quality

Test how well each method preserves hierarchy and proximity: do close nodes stay close in the embedding?

4. Compare on speed

Compute the speedup: wall-clock time for Blsius divided by time for each ML method.

5. Report findings

Show that Blsius is 100x faster because it avoids iterative optimization, while achieving equal or better quality.

What the paper changes

What the paper changes

This paper does not propose a new algorithm—it brings an existing algorithm from the computer science algorithms community into direct comparison with the dominant machine-learning methods. By benchmarking all three side-by-side on the same networks with the same quality metrics, it reveals that the prior belief (that ML methods were best) was based on incomplete information.

The hidden quantity

The hidden quantity: computational cost per embedding

measured quantity  =  Computation time to embed a network

Computational cost is how long the algorithm takes (in seconds or minutes) to convert a network into embeddings. Machine-learning methods like Poincaré and Lorentz use gradient descent—a slow iterative process where the algorithm starts with random guesses and gradually improves them by nudging each number in a direction that reduces error. The Blsius algorithm, by contrast, uses direct construction based on mathematical principles: it builds the embedding by solving mathematical problems directly, without iteration. This makes it much faster because each iteration of gradient descent touches every node and every edge, multiplying the cost by the number of iterations needed to converge; Blsius avoids that multiplication entirely.

The paper measures cost by running each method on the same hardware and timing wall-clock seconds. It also records memory usage. The dramatic speed difference—100x—comes from the gap between iterative refinement (slow) and direct mathematical solution (fast).

Why it works

Why Blsius is so much faster

Poincaré and Lorentz embeddings use gradient descent, an iterative optimization loop. The algorithm starts with random numbers (coordinates in hyperbolic space) and repeatedly adjusts them—compute how far off we are from the target, compute which direction to nudge each number, nudge it, repeat thousands of times until the error stops shrinking. Each iteration touches every node and every edge, so the total time grows as iterations multiplied by network size. With thousands of iterations needed to converge, this is slow.

Blsius uses a different strategy: it constructs the embedding in a single pass using mathematical rules. It starts at the center of hyperbolic space and places nodes by computing the angular distance that represents proximity in the original network, placing each node at that angle, then scaling its distance from center to match its hierarchy level. No iteration is needed; the construction is direct. This runs in linear time—proportional to the number of nodes, not quadratic or worse.

The embedding distance formula

First in words:

In hyperbolic space, the distance between two points is not Euclidean. Instead, it grows exponentially with the radius. The closer a point is to the center, the more space is packed around it. This naturally represents hierarchies because roots are central and branches spiral outward, with each level having more space.

Then the compact form:

d_hyp(u, v) = arccosh(cosh(r_u) * cosh(r_v) - sinh(r_u) * sinh(r_v) * cos(theta_diff))

Every symbol:

d_hyp(u, v)distance between points u and v in hyperbolic space
r_u, r_vdistance from center (radius) for each point
theta_diffangular separation between the points
cosh, sinh, arccoshhyperbolic trigonometric functions (describe curved distances)
A tiny worked example
Point A at radius 2.0, angle 0 degrees: r_A = 2.0, theta_A = 0
Point B at radius 3.0, angle 90 degrees: r_B = 3.0, theta_B = 90
Angle difference theta_diff = 90 degrees (convert to radians: pi/2 ≈ 1.57)
cosh(2.0) ≈ 3.76, sinh(2.0) ≈ 3.63
cosh(3.0) ≈ 10.07, sinh(3.0) ≈ 10.02
cos(1.57) ≈ 0
d_hyp(A,B) = arccosh(3.76 * 10.07 - 3.63 * 10.02 * 0) = arccosh(37.86) ≈ 4.63
Interpretation: the distance is 4.63 in hyperbolic metric—much larger than straight-line distance would predict, because hyperbolic space expands.

Blsius computes these radii and angles once per node using geometric rules; ML methods adjust them thousands of times via gradient descent.

What can go wrong

What can go wrong

Networks without clear hierarchy. If the network is a dense random graph (not tree-like), hyperbolic embeddings of any kind will be poor because hyperbolic space is built for hierarchies. The paper tests on hierarchies and tree-like networks, so this is a limitation.
Numeric precision in hyperbolic trig. The hyperbolic functions (cosh, sinh, arccosh) can overflow for large radii if computed carelessly. Blsius and the ML methods must use numeric libraries that handle large hyperbolic radii safely, or embeddings will become invalid.
Initialization sensitivity in ML methods. Poincaré and Lorentz embeddings can get stuck in local minima (suboptimal solutions) depending on random initialization. Poor initialization leads to poor embeddings. Blsius avoids this entirely by using mathematical rules, not optimization.
Done right. When benchmarking, ensure all three methods use the same network data, the same hardware, the same quality metrics, and enough iterations for ML methods to converge. The paper does this carefully.
What a runnable demo should prove

What a runnable demo should prove

A demo should take a hierarchical network (for example, a category taxonomy or a tree of topics), embed it using all three methods, and plot wall-clock time and quality scores. The key is to vary network size—small, medium, large—so the 100x speedup becomes visible as the network grows. Record memory usage too. A good demo would also visualize the resulting embeddings (plot them as a 2D projection) to show that all three methods produce similar-looking embeddings, just at different speeds.

speedup = time_poincare / time_blasius, quality_difference = quality_blasius - quality_poincare

The demo must make it impossible to miss that Blsius wins decisively on speed with no sacrifice in quality.
