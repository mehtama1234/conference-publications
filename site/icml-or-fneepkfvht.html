PaperBanana: Automating Academic Illustration

PaperBanana teaches an AI to draw research diagrams the way humans do: grab reference pictures, plan the design, render the image, then fix it when it goes wrong.

Paper explainersAll themesAgents & Tool Use

Scientists spend weeks drawing diagrams for papers—flowcharts, brain sketches, data charts. PaperBanana automates this. It works like a human illustrator: an AI retrieves pictures for reference, plans what to draw and how it should look, renders the image using a generative model, then critiques its own work and fixes problems. The result is publication-ready illustrations that match what humans would make.

Zero assumption version

Drawing research diagrams is slow

Every research paper needs diagrams: flowcharts showing how a system works, sketches of neural networks, plots of experimental results. Drawing these takes a scientist days or weeks. A naive approach—ask a generative image model to draw a diagram just from a text description—fails because the AI has no reference, no design plan, and no way to fix mistakes. It produces blurry, mislabeled, or logically broken illustrations.

The bottleneck is that diagrams must be accurate (they show methods and results), visually clear (easy to read in a paper), and styled consistently (they look like they belong together). A bare text prompt cannot capture all this.

The problem in one sentence. A generative image model without reference pictures, a design plan, or a way to self-correct produces inaccurate, ugly diagrams that scientists must redraw by hand.

The algorithm as a flow

What it actually does

Retrieval step

AI searches for example diagrams matching the research domain and finds related papers.

Vision read

Vision model reads the reference diagrams and extracts style rules, layouts, and visual patterns.

Planning step

Planner agent synthesizes a design spec: what shapes, text labels, colors, and layout the new diagram should use.

Rendering step

Image generation model renders the diagram from the design spec, producing pixel art.

Critique and fix

Vision model examines the output, finds errors (wrong labels, broken lines, unclear contrast), and the loop refines until correct.

What the paper changes

The thing that changes

PaperBanana changes the diagram-generation process from a single black-box generative call into a multi-step workflow. Each step is specialized: one agent retrieves reference images, another plans the design, a third renders, and a fourth critiques. Each agent is an AI doing one job well, and they talk to each other. The key move is making the process visible, breakable into steps, and self-correcting.

The hidden quantity

The hidden quantity: Diagram fidelity

measured quantity  =  Fidelity score (how close the generated diagram is to what a human would draw)

The paper measures something invisible: how much the AI-generated diagram matches what a human expert would create. This is not just 'does it look pretty'—it is 'does it show the method correctly, with clear labels, good spacing, and consistent style?' The hidden quantity is fidelity: a score combining accuracy (are labels right?), clarity (can you read it?), and aesthetics (does it look professional?).

PaperBanana estimates fidelity in two ways. First, the vision model's self-critique step directly estimates it—the AI examines the image and scores its own correctness. Second, the paper compares PaperBanana's output to human-drawn diagrams from NeurIPS papers using benchmark metrics like BLEU (how much text overlap with human captions) and visual alignment (do the shapes and text boxes overlap with human versions?).

Why it works

Why orchestrating steps works better than one big call

A single image-generation call fails because the model has no grounding. It has only a text description—'draw a neural network with three layers'—and must invent style, layout, and correctness from scratch. It hallucinates labels, misaligns shapes, and produces artifact.

PaperBanana breaks this into steps, and each step solves one part of the problem. First, retrieval finds real examples that show what good diagrams in this research area look like. The planner then reads those examples and learns the visual language—where labels go, what colors are used, how shapes are sized. It builds a detailed design spec, not just a text prompt. The renderer then has a much clearer target: not 'draw a flowchart' but 'draw a flowchart with boxes at these coordinates, labels in this font size, colors from this palette.' The renderer's job is easier because the spec is precise. Finally, the critique step catches errors the renderer made—wrong text, misaligned boxes, low contrast—and feeds them back. The loop refines until the diagram is correct. Because each step is narrow and has feedback, the final result is much higher fidelity.

The deeper reason: orchestrating specialized agents distributes the complexity. One agent does not have to solve 'understand the method, find references, design the layout, generate pixels, and self-correct' all at once. Each agent has a narrow job and can be tuned for that job alone.

A simple model of the refinement loop

First in words:

fidelity_iteration_t = fidelity_t_minus_1 + critique_delta * (1 - fidelity_t_minus_1), where critique_delta is the improvement found by each self-critique cycle

Then the compact form:

F_t = F_(t-1) + delta * (1 - F_(t-1))

Every symbol:

F_tfidelity score at iteration t (0 to 1, where 1 is perfect)
F_(t-1)fidelity score from the previous iteration
deltaimprovement amount found by the critique step (0 to 1, depends on how many errors are found)
1 - F_(t-1)the remaining room to improve (if fidelity is 0.6, there is 0.4 left to gain)
A tiny worked example
Iteration 0: AI first renders. Fidelity score F_0 = 0.5 (half the labels are wrong, colors are muddy). Room to improve = 1 - 0.5 = 0.5.
Critique finds errors: critique_delta = 0.3 (the errors are fixable; the method is actually coherent).
Iteration 1: F_1 = 0.5 + 0.3 * 0.5 = 0.5 + 0.15 = 0.65. After fixes, fidelity rises to 0.65. Room left = 1 - 0.65 = 0.35.
Critique round 2: subtle spacing issues remain. critique_delta = 0.2.
Iteration 2: F_2 = 0.65 + 0.2 * 0.35 = 0.65 + 0.07 = 0.72. Each loop gets harder; gains shrink as fidelity rises.

The loop converges because the term (1 - F_(t-1)) shrinks: early on, there is lots of room to improve so gains are large; as F rises toward 1, the room shrinks and each critique finds only minor issues, so delta*room gets smaller. Running more iterations costs more compute but yields fidelity closer to 1.

What can go wrong

What can go wrong

Reference mismatch. If the retrieval step finds diagrams from the wrong domain (e.g., searching for neural network layouts but getting biological cell diagrams), the planner learns the wrong visual style and the final diagram looks misplaced. Mitigation: retrieval must be precise—use domain keywords and validate retrieved papers.
Hallucinated labels. The planner may write labels or equations that do not match the paper's actual method—invented math, fake variable names. The critique step should catch this, but only if the vision model understands the domain. Mitigation: feed the paper's text directly to the critique step so it can verify correctness.
Critique loop does not converge. If critique_delta stays large (many errors persist after each refinement), the loop may run forever or settle on a low-fidelity diagram. This happens when the render model cannot fix the specific error the critic finds. Mitigation: set a maximum iteration count and also adjust the prompt to the renderer based on past critiques.
Style leakage from bad references. If one retrieved reference diagram is poorly formatted (small fonts, low contrast), and the planner copies its style, the final diagram inherits those flaws. Mitigation: quality-gate the references—filter by publication venue or visual quality score before showing them to the planner.
Done right. Validate references by domain and quality, feed the paper text to the critique step, set iteration limits, and monitor whether critique_delta shrinks over time (convergence). If these hold, the method produces high-fidelity diagrams consistently.
What a runnable demo should prove

What a runnable demo should prove

Build a tiny version of PaperBanana that generates a simple flowchart (e.g., a neural network with three layers) from a paper description. Retrieve two reference flowcharts from a small local image set. Use a lightweight vision model (e.g., CLIP or a small captioner) to extract style rules from the references (colors, font sizes, spacing). Have a text model write a design spec. Feed the spec to a simple image renderer (even a SVG-drawing script with text labels and colored boxes will work). Implement one critique round: have the vision model compare the rendered output to the reference diagrams and report errors (missing labels, wrong colors, misalignment). Fix the top error and re-render. Compare the one-shot output (no refinement) to the one-loop-refined output on fidelity metrics (e.g., how many labels match the input description, how much the layout resembles the references).

fidelity = (labels_correct / total_labels) + (alignment_overlap / reference_area) / 2, where alignment_overlap is the pixel overlap between rendered and reference boxes, and alignment_gap = initial_fidelity - refined_fidelity after one critique loop

The demo must show that a single critique loop raises fidelity on a real flowchart, because the vision model can spot label errors and misalignments that the initial render missed, and feeding those errors back to the planner and renderer produces a second pass that fixes them.
