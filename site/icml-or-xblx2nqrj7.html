FullStack-Agent: Enhancing Agentic Full-Stack Web Coding via Development-Oriented Testing and Repository Back-Translation

Build real web apps, not only polished pages, by combining planning, codebase navigation, bug finding, and tests that check the front end, server, and storage together.

Paper explainersAll themesAgents & Tool Use

This paper targets a gap in code agents for websites. Many systems can draw attractive pages, yet they fail once the task needs form handling, server logic, or saved data. FullStack-Agent treats full-stack coding as a development workflow rather than a one-shot page generation problem. It combines a multi-worker builder, a self-improvement loop built from existing repositories, and a benchmark that checks whether the produced app actually works across the full request path.

Zero assumption version

Why full-stack coding is harder than page generation

A polished page can hide the absence of real application logic. A user may see forms, tables, and buttons, yet no request reaches a server and no data is saved. That is why front-end-only success is an incomplete measure for web coding agents.

A real web app must coordinate several linked parts: page behavior, server routes, storage, package versions, and bug repair. If one part is wrong, the whole request path fails because the app depends on end-to-end agreement across files and services.

The paper's claim in one line. Treat full-stack coding as planning plus testing plus repair, because visible page quality alone does not prove that the application works.

The algorithm as a flow

What it actually does

Plan the app.

The system first decides which features, routes, and storage pieces are needed so code edits can be judged against an explicit development plan.

Navigate the repository.

Workers inspect existing files and dependencies because correct edits depend on where data already enters, moves, and is stored.

Edit and localize faults.

The builder writes code and then isolates likely fault locations, so repair work targets the files that actually break the request path.

Run full-stack tests.

The benchmark checks page behavior, server behavior, and storage behavior together because each layer can pass alone while the end-to-end flow still fails.

Learn from repositories.

Back-translation turns existing web projects into training examples because the model then sees realistic project structure and repair patterns.

The hidden quantity

The hidden quantity

measured quantity  =  end-to-end consistency of the application state path

The key hidden quantity is whether the same data idea is represented consistently across page code, server code, and storage code. A button may send one field name while the server expects another, or the server may write a shape that the page cannot later read. Those mismatches stay hidden until a real task crosses the full path.

FullStack-Agent tries to expose that hidden consistency through development-oriented tests. The tests help because they do not stop at surface rendering. They force one user action to travel through each layer, so broken links become visible.

Why it works

Why development-oriented testing helps

The main reason this helps is that full-stack errors are often relational errors, because a single file may look correct while still disagreeing with another file about names, routes, or saved fields. A development loop that only inspects local code quality misses those cross-file agreements because they appear only when the pieces interact.

The repository back-translation step helps for a second reason because real projects contain recurring structures for server handlers, saved data, and page updates. Turning repositories back into training examples gives the system many concrete traces of how working projects are organized, so later generation can reuse patterns that already preserve end-to-end agreement.

Math after the picture

Score an app by linked-layer success

First in words:

A simple summary is to reward an app when the same task works on the page, on the server, and in storage, then subtract the cost of failures that break the path between those layers.

Then the compact form:

score(app) = page_pass(app) + server_pass(app) + storage_pass(app) - break_cost(app)

Every symbol:

score(app)overall value of one generated application
page_pass(app)how well the page behavior passes the relevant tests
server_pass(app)how well server routes and handlers pass their tests
storage_pass(app)how well reads and writes pass storage tests
break_cost(app)penalty for mismatches that break the full request path
A tiny worked example
App A renders the page and accepts form input, so page pass is 8.
Its server route works, so server pass is 8, but it never saves the data, so storage pass is 1.
The missing save path adds a break cost of 5.
App B scores 7 on the page, 7 on the server, and 7 on storage, with break cost 1.
App B wins because slightly lower page polish is worth more when the full path actually works.

The real system uses richer tests and learning signals, but the paper's point is captured by this score: reward linked-layer success, not isolated page quality.

What can go wrong

What can go wrong

Tests can still miss realistic failures. A benchmark can cover many paths and still miss a deployment-only fault, so passing tests is strong evidence but not a full guarantee.
Repository back-translation may copy local habits. If the source repositories share one narrow style, the training signal may favor that style even when a new task would benefit from a different structure.
Bug localization may narrow too soon. If the system blames the wrong file early, later repair effort can be wasted because the true mismatch lives in another layer of the request path.
Done right. The method is strongest when app plans, repository evidence, and end-to-end tests point to the same target behavior, because then each repair step has clearer feedback.
What a runnable demo should prove

What a runnable demo should prove

Build a small web application task set with at least one create action, one read action, and one update action. For each task, require the app to render a page, hit a server route, and save or load data from storage. Log where failures occur: page, route, or storage. Compare a front-end-heavy agent against a development-oriented full-stack agent.

The demo should show higher end-to-end pass rates for the full-stack agent because tests expose broken links across layers and repository-based learning gives the builder better examples of working project structure. The logs should also show shorter repair cycles when bug localization points to the correct layer.

path_success = full_stack_task_passes / total_tasks

A convincing demo must prove that full-stack coding improves when the agent is trained and evaluated on full request paths, because page appearance alone does not measure application correctness.
