Tab-MIA: Membership Inference Attacks on Tabular Data in LLMs

A benchmark showing that LLMs memorize structured data and can be tricked into revealing whether a row was in their training set.

Paper explainersAll themesDatasets & Benchmarks & Evaluation

When an LLM is trained on a spreadsheet full of personal data—like medical records or financial tables—it absorbs the patterns. An attacker can ask simple questions to test whether a specific row was memorized. This paper creates the first systematic test suite to measure how well LLMs keep spreadsheet data secret.

Zero assumption version

Structured data leaks in plain sight

Text models are trained on documents, books, and web pages—content that's naturally scattered and vague. But when a company trains an LLM on a spreadsheet of customers, patients, or employees, the model absorbs exact rows: an email, a salary, a diagnosis, all laid out in columns. If the model memorizes rows, an attacker can query it to reveal which rows it learned.

A beginner might assume that because a table is just numbers and short text, it is less memorable than a story. But tables are the opposite: every column has a tight semantic meaning (date, price, customer ID), every value is exact, and rows are often unique and distinctive. This tight structure means a model can memorize rare rows as distinct patterns, and an attacker can ask the model to repeat the row by probing it with specific column values—much easier than extracting a buried phrase from a long story.

The paper's move in one sentence. Tab-MIA is a benchmark dataset with five real tables encoded six different ways, used to test whether membership inference attacks—which guess if a row was in training—actually work on LLMs trained on structured data.

What the paper changes

What the paper changes

Before Tab-MIA, membership inference attacks on LLMs were tested only on unstructured text. The paper creates the first benchmark for structured data—tables with explicit columns and uniform types. It encodes the same five tables in six different formats and measures whether membership inference succeeds on each one.

the object it moves  =  benchmark dataset + encoding variants
The hidden quantity

The hidden quantity: memorization signature

measured quantity  =  Membership inference success rate (AUROC)

AUROC (area under the receiver operating curve) is a number from 0 to 1 that measures how well an attack can distinguish a row the model saw during training from a row it never saw. At 0.5, the attack is just guessing; at 1.0, it is always right.

The paper estimates this by training LLMs on half of each table, withholding the other half as test data, then running membership attacks and scoring how often the attack correctly identifies which rows were in training. The higher the AUROC, the more the model has memorized and exposed that specific row signature.

Why it works

Why it works: memory leaves a trace

An LLM trained on tabular data learns patterns: if email always ends in @company.com and salary is always in a range, the model absorbs those regularities. Most important, it also absorbs rare, distinctive features of individual rows—a unique combination of values that appears only once.

During training, the model optimizes its weights to predict rows it has seen. After training, when an attacker feeds in a row the model has memorized, the model's loss (prediction error) is lower and its confidence is higher, because its weights are finely tuned to that exact pattern. Rows the model never saw trigger higher loss and lower confidence. An attacker exploits this gap: high confidence on a test row hints it was in training; low confidence hints it was not.

Different table encodings (CSV vs. JSON vs. SQL) change the surface form of the row but not its underlying pattern, so membership leaks across formats. Fine-tuning amplifies the signal: even three epochs of training on a table causes the model to memorize distinctive rows strongly enough that AUROC exceeds 0.9.

Math after the picture

Scoring membership via model loss

First in words:

membership_score = 1 minus normalized_loss; if loss is low, the score is high (membership likely); if loss is high, the score is low (membership unlikely).

Then the compact form:

score(row) = 1 - (loss(row) / max_loss); AUROC = integral_threshold [TP(threshold) / (TP + FN)] d(FP / (FP + TN))

Every symbol:

loss(row)average prediction error on that row
max_lossworst loss seen on any row (for normalization)
TP (true positive)attack correctly guessed row was in training
FP (false positive)attack incorrectly guessed row was in training
FN (false negative)attack missed a row that was in training
TN (true negative)attack correctly guessed row was not in training
Tiny worked example: two rows
Row A (was in training): model loss = 0.4
Row B (not in training): model loss = 2.8
max_loss = 2.8
score(A) = 1 - (0.4 / 2.8) = 1 - 0.14 = 0.86 (high, signals membership)
score(B) = 1 - (2.8 / 2.8) = 1 - 1.0 = 0.0 (low, signals non-membership)
Attacker sorts by score: rows with score > threshold are guessed to be in training.
With threshold = 0.43, both decisions are correct.

Low loss on a memorized row gives it a high membership score; an attacker uses this score difference to decide which rows to flag as trained.

What can go wrong

What can go wrong

Noise and data imbalance. Rows with many missing values or outlier patterns are harder to memorize, so attacks perform worse. A table with many missing entries is less vulnerable than a dense, clean table.
Weak fine-tuning. If a model is fine-tuned for only one epoch, it may not memorize individual rows deeply. Attack AUROC can drop to 0.6–0.7. The paper shows vulnerability grows with training epochs.
Adversarial encoding. Future defenses could encode rows with noise or anonymization before training. The paper does not test such defenses, only six standard formats.
Clean membership leaks for dense, distinctive data. When a table has many unique rows with clear semantics (like a customer database), attacks reliably achieve AUROC > 0.85, making the benchmark effective at revealing real risk.
What a runnable demo should prove

What a runnable demo should prove

Train a small LLM (e.g., a 1B-parameter model) on half of a real table (e.g., UCI Adult or a subset of WikiBio). Fine-tune for three epochs. Hold out the other half. For each held-out row, compute the model's loss. Then for a held-out row, measure its loss versus a row from the training set, sorted by loss and score via the formula above.

demo_AUROC = count(correctly_ranked_membership_pairs) / total_pairs; show that demo_AUROC > 0.75 on most tables

The demo must show that rows the model trained on produce lower loss than rows it never saw—a direct, measurable signal of memorization and membership leakage.
