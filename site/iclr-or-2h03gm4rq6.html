TRACE: Self-Evolving Agent Benchmarks

Instead of manually writing harder test questions, let agents themselves invent new variations of old tasks and record how they did it, so we can check the answers are real.

Paper explainersAll themesDatasets & Benchmarks & Evaluation

Agent benchmarks are running out of steam. When a new agent beats the current test set, we throw it away and write new tests by hand — which is slow and expensive. TRACE flips this: it has agents automatically evolve existing benchmark tasks into harder versions while recording their work step-by-step, so humans can verify the answers are genuine. This turns testing from a one-time job into a continuous, self-feeding system.

The Benchmark Collapse Problem

Evaluating intelligent agents (large language models that can use tools like web browsers, calculators, and APIs) used to be simple: give them a task, see if they solve it. But as agents got better, they started beating almost every benchmark, because each year brings new, more capable models and the old test set does not challenge them anymore. A task that was hard last year becomes routine this year.

The naive solution is to hire people to write harder tasks. But real-world agent tasks are complicated: they involve multiple steps, many tools, branching choices, and decisions that interact in unexpected ways. Writing them by hand is expensive and slow because a human must invent each one from scratch, think through whether it is solvable, test it, and document it — all labor-intensive. You cannot keep up with how fast agents improve because the rate of new models far exceeds the rate humans can author tests. You get stuck with old tests that no longer measure anything interesting.

The problem in one sentence. Benchmarks saturate because agents improve faster than humans can write new tests.

What the paper changes

What the Paper Changes

Instead of manually writing new benchmark tasks, TRACE automates task evolution by letting agents explore, propose changes, and concretize one into a harder version. The agent records its reasoning and every tool invocation as it solves the new task, creating what the paper calls an execution trajectory.

The hidden quantity

The Hidden Quantity: Validatable Task Trajectories

measured quantity  =  reproducibility through step-by-step replay

A trajectory is the full record of how an agent solved a problem: every reasoning step, every tool call (like searching the web or running code), every result it saw back. Most agent evaluations just check the final answer. TRACE insists on recording trajectories — the entire path the agent took to get there.

The paper measures whether each evolved task's trajectory is validatable: can we replay every step and get the same results? This matters because it proves the evolved task is real, not fabricated. The validator runs each tool call again, checks that the outputs match what was recorded, and confirms logical consistency across steps. A trajectory is only valid if every step reproduces.

Why it works

Why It Works: The Three-Stage Evolution Engine

TRACE separates task proposal from task verification into three stages. First, the agent explores freely without worrying about whether a task is hard or can be verified. This divergent thinking produces wild, diverse ideas. Second, the agent concretizes one idea into an actual task and solves it, creating a full trajectory (its complete work record). Third, the validator audits that trajectory by replaying every step and confirming reproducibility.

This works because it lets agents and humans do what they do well. Agents excel at exploring and inventing; humans excel at verification. The agent proposes and solves (its strength); the validator checks that every step is real and reproducible (our strength). The evolved task is harder because the agent can jump across capability areas (from retrieval to math to coding) and layer constraints in ways humans rarely think to combine. And because every step is recorded and replayed, the answer cannot be faked: the task is genuine and verifiable.

The Validation Equation

First in words:

For each step in the recorded trajectory, replay the tool call and check that the output matches. A trajectory is validatable if all steps reproduce.

Then the compact form:

valid(tau) = all_steps_reproduce(replay(S_i, a_i) == o_i for each step S_i)

Every symbol:

tauthe trajectory (sequence of steps)
S_ithe i-th step in the sequence
a_ithe action taken at step i (tool call, code, etc.)
o_ithe observed result recorded at step i
replay(S_i, a_i)running that step again and collecting the new result
valid(tau)1 if all steps reproduce, 0 otherwise
A tiny worked example
Step 1: Agent calls web search with query 'Tyler Hilton TV series'. Recorded result: One Tree Hill. Replay: web search returns One Tree Hill. Match: yes.
Step 2: Agent calls web search with query 'Tyler Hilton music career'. Recorded result: 4 albums. Replay: web search returns 4 albums. Match: yes.
Step 3: Agent outputs 'One Tree Hill + music career'. Recorded result in step 2 feeds into this step. Replay confirms the dependency. All three steps reproduce.
Conclusion: valid(tau) = 1. The evolved task and its answer are genuine and can be verified.

A trajectory is only safe to use as a benchmark task if every step reproduces when we replay it, because that proves the answer is real and not a mistake or hallucination.

What can go wrong

What can go wrong

Evolved task depends on external state. If a step uses a live API and that API changes (the website redesigns, the database updates), replay will fail. The validator will catch this, and the task will be rejected.
Agent creates a task only it can solve. If the evolved task requires a specific capability the agent has but other agents do not, it is not a fair benchmark. The paper does not fully solve this; it relies on choosing agents wisely and monitoring capability diversity.
Validation overhead grows with trajectory length. A task with 50 steps takes 50 times longer to validate than a one-step task. Long trajectories are harder to audit and more likely to have subtle non-reproducibility.
Done right: mix agents and validate hard. Use multiple agent architectures in the evolution loop, so the evolved tasks reflect a consensus about what is hard. Replay every step and require reproducibility before accepting a task into the benchmark.
What a runnable demo should prove

What a runnable demo should prove

Implement the TRACE loop on a small existing benchmark (e.g., 5 simple retrieval tasks). Run an agent through the exploration stage and let it propose 3 to 5 task variations. Pick one, have the agent solve it, and record the full trajectory (reasoning, tool calls, results). Then independently replay the trajectory and verify that every step reproduces. Show that agents score lower on the evolved tasks and that the validation catches any non-reproducible steps.

validation_pass_rate = (tasks_with_all_steps_reproducible / total_evolved_tasks) * 100; difficulty_gain = avg_accuracy_original - avg_accuracy_evolved

The demo must make clear that evolved tasks are genuinely harder and that trajectories are verifiable: humans cannot (and do not need to) write these tasks; the system creates and validates them automatically.
