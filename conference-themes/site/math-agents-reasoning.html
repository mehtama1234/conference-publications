Agents and reasoning as a controlled work loop

This page expands the agents lane at paper level. The common problem is that an agent does not only answer. It keeps a working state, chooses an action, observes what happened, checks the result, remembers useful evidence, and decides whether to continue or stop. A reasoning system works when that process keeps evidence the final answer would otherwise hide.

FIRST PRINCIPLE

The Answer Is A Compressed Report From A Process

A final answer is a compressed report. It hides the trace, tool calls, internal working state, retrieved evidence, and failed branches. That is useful for users but weak for understanding what happened. If the process is unobserved, we cannot tell whether the model reasoned, guessed, copied a template, exploited a checker, or accidentally reached the right endpoint.

Agent math is about controlling that loop. Like a technician deciding which test to run next, the system has a current belief about the task, chooses an action to reduce doubt or change the world, receives feedback, and uses that feedback to choose the next action. What must stay the same is progress toward the real task. What may change is the question asked, tool used, memory kept, or stopping point. Name used later: controlled inference for choosing actions in order to learn enough or change enough to decide.

FORMULA PASS

Paper-Specific Math Boxes

These boxes state the compact test each major agents/reasoning paper is really asking for. They are not theorem statements; they name the thing being tracked, the condition it should satisfy, and the evidence that would make the claim credible.

RAGEN-2

Object. A trace that changes when the task input changes.

Why it works. Like checking whether a student's scratch work changes when the problem numbers change, the trace must carry evidence from this input. A generic reasoning template can look fluent while carrying almost nothing about the specific problem. What must stay the same is dependence on task-specific evidence. What may change is the input perturbation. Name used later: mutual information for how much knowing the trace tells us about the input.

credible trace requires I(input; trace) high under task perturbations

Evidence check. Perturb inputs, compare trace dependence, and verify that generic templates fail on tasks where task-specific state is necessary.

The Tell-Tale Norm

Object. A cheap internal signal for deciding when extra reasoning is worth spending.

Why it works. Extra compute is useful only when it changes the answer for the better. A hidden-state norm is just a number from inside the model; it matters only if high values reliably identify cases where recursion, steering, or selection helps.

route extra compute when E[gain | norm, state] exceeds compute cost

Evidence check. Intervene on routing decisions, compare to random and length-based routing, and test whether high-norm states are the ones that benefit.

h1

Object. Training that grows the number of dependent steps only while feedback is still useful.

Why it works. Like teaching a recipe one stage at a time before asking for the whole meal, the method keeps feedback close enough to the step it should teach. If the task is too long too early, the final reward does not say which local move helped or hurt. What must stay the same is learnable credit for useful local moves. What may change is task length. Name used later: horizon for how far ahead the task depends on earlier moves.

increase horizon H only while reward signal still identifies useful local transitions

Evidence check. Sweep dependency length, measure where direct RL loses signal, and test whether short learned dependencies compose rather than memorize templates.

Verifying Chain-of-Thought

Object. A map of which intermediate claims support which later claims.

Why it works. Like checking whether every line in a proof follows from earlier lines, the trace becomes checkable only when support is explicit. What must stay the same is the support relation between steps. What may change is a premise, edge, or intermediate claim being tested. Name used later: dependency graph for this support map.

valid trace means each claim node is supported by predecessor nodes and rules

Evidence check. Corrupt one step, remove edges, or swap premises; the verifier should localize the unsupported claim, not merely judge the final answer.

ParetoPO

Object. A menu of tool-use choices where better answer quality has visible cost.

Why it works. Like deciding whether another lab test is worth its time and price, a tool call is rational only when the expected gain pays for latency, money, state risk, and checker cost. What must stay the same is honest reporting of both benefit and cost. What may change is which tool path is chosen. Name used later: Pareto frontier for non-wasteful options where improving one side would worsen another.

choose action a when Delta quality(a) is not dominated by Delta cost(a)

Evidence check. Plot quality against calls, latency, and failures; inspect where fewer calls preserve quality and extra calls produce no frontier movement.

Skill-Pro

Object. A reusable procedure with clear start conditions and stop conditions.

Why it works. A skill is like a recipe that says when it applies and when it is done. It helps only if it fires in states where the learned steps still apply and stops when the goal is reached. What must stay the same is the situation the workflow was meant for. What may change is the task instance. Names used later: precondition and termination for those start and stop tests.

skill pi_k is valid when precondition(s) and termination(s') are both reliable

Evidence check. Replay skills on perturbed tasks, measure false activation, successful termination, and reuse benefit against re-deriving the workflow.

CyberGym

Object. A runnable proof that changes program behavior before a patch and fails after the patch.

Why it works. Like testing a lock before and after a repair, a cyber claim is credible when it becomes executable behavior, not persuasive prose. What must stay the same is the attempted exploit. What may change is whether the code is vulnerable or repaired. Name used later: counterfactual certificate for checking the same exploit against those two nearby states.

certificate passes when exploit(pre_patch)=true and exploit(post_patch)=false

Evidence check. Execute the proof of concept, log side effects, vary configuration, and separate real exploit behavior from explanatory prose quality.

OMAC

Object. A team structure that says which agent has which role, what messages move, and how outputs are combined.

Why it works. Like assigning one person to inspect wiring and another to inspect plumbing, multiple agents help only if the team creates independent or specialized evidence that one call would not have produced. What must stay the same is useful independent contribution. What may change is role, message route, or voting rule. Name used later: collaboration graph for the role-and-message structure.

team value = information gained by role graph - coordination and correlation cost

Evidence check. Ablate roles and edges, measure minority-correct evidence survival, and test transfer beyond the architecture-search benchmark.

OBJECT 01

Trace Information

RAGEN-2

Problem. Agentic RL can reward generic chains that look like reasoning while barely depending on the input.

Object. A check that the reasoning trace changes with the task input.

Why it works. Like comparing scratch work after changing the problem, input dependence catches template collapse. Entropy alone is not enough: a trace can vary while still not carry task-specific evidence. What must stay the same is task dependence. What may change is the input. Name used later: mutual information for how much the trace tells us about the input.

Connection. This is the same issue as benchmark validity: the measured artifact must reduce doubt about the hidden capability, not merely look like it.

OpenThoughts

Problem. Reasoning models depend on trace data, but trace data is itself generated through sources, filters, and teacher choices.

Object. A public recipe for producing reasoning paths, not just final answer labels.

Why it works. Like publishing the lab recipe instead of only the final result, inspectable pipelines let researchers ask which domains, trace shapes, and filtering rules produce transferable intermediate computation. What must stay the same is trace usefulness for later reasoning. What may change is source, teacher, or filter. Name used later: distribution for the mix of traces the model sees.

Connection. OpenThoughts supplies the data-side counterpart to RAGEN-2's diagnostic: one builds trace data, the other checks whether learned traces still carry task information.

T3

Problem. A failed long reasoning rollout may contain locally correct moves that should not be thrown away.

Object. The value of a partial path before the final answer is known.

Why it works. Like saving the correct first steps of a solution even when the ending is wrong, credit becomes less sparse when useful partial paths are preserved. What must stay the same is whether a local move reduced doubt. What may change is the later branch. Name used later: prefix-level utility for scoring a partial trace.

Connection. This is the reasoning analog of data valuation: value is conditional and sequential, not attached to the whole example uniformly.

Verifying Chain-of-Thought

Problem. A chain can be fluent while the dependencies among steps are invalid.

Object. Like checking a proof by asking whether each line really follows from earlier lines, the object is the set of claims, operations, and support links inside the reasoning.

Why it works. What must stay the same is dependency support: later steps should be justified by earlier evidence or operations. What may change is wording or explanation style. The checker can point to the exact unsupported step instead of judging a whole paragraph by whether it sounds coherent. Name used later: computational graph.

Connection. It turns reasoning from prose into a checkable object, like code verification does for software agents.

CE-Graph And TRACE Effort

Problem. Models can pass final checks through shortcuts, low-effort traces, or reward-hacking behavior.

Object. Tests for whether effort, dependencies, counterexamples, and checker sensitivity actually matter.

Why it works. Process diagnostics compare how the system behaves when the trace is shortened, pressured by counterexamples, or checked for dependencies. If success survives after the supposed reasoning is removed, the trace was not doing the claimed work.

Connection. These diagnostics share the same logic as saliency in multimodal models: measure whether the claimed evidence actually caused the output.

OBJECT 02

Compute Allocation

The Tell-Tale Norm

Problem. A model needs a cheap signal for when extra reasoning is useful.

Object. A number from the hidden state that predicts when more computation helps.

Why it works. Like a dashboard light that is useful only if it predicts a real problem, the norm matters only after evidence ties it to cases where extra reasoning helps. What must stay the same is the link between the signal and useful extra work. What may change is whether recursion, steering, or selection is routed. Name used later: L2 norm for this internal size measurement.

Connection. This is compute allocation through an internal measurement, like EntroKV uses remaining uncertainty to allocate cache budget.

ASAG And Reasoning With Sampling

Problem. Sampling more candidates helps only when the candidates explore uncertainty that matters.

Object. Several plausible solution paths plus a rule for choosing or combining them.

Why it works. Like trying genuinely different routes through a maze, extra samples buy value when they cover distinct paths and a verifier can identify better ones. What must stay the same is coverage of meaningful alternatives. What may change is the sampled path. Name used later: distribution for the spread of sampled paths.

Connection. This is the inference-time version of coverage in generative modeling.

h1

Problem. In long tasks, the reward may arrive so late that the model cannot tell which earlier step helped.

Object. Like teaching a long song by first learning short phrases and then joining them, the object is a training ladder where dependency chains get longer over time.

Why it works. What must stay the same is the final long-task skill. What may change is how much of the dependency chain is trained at once. Short tasks give feedback close to the action that caused it; longer tasks are added after the model can already handle the smaller pieces. Name used later: curriculum over horizon length.

Connection. This mirrors midtraining bridges: timing and path matter because the same evidence helps only when the optimizer can still absorb it.

ThinkV And EntroKV

Problem. Long inference cannot keep all hidden states and cache entries at full detail.

Object. Like deciding which notes to keep before an open-book exam, the system should keep an old state only if it can still change a later answer.

Why it works. What must stay the same is the evidence needed for future tokens, tool calls, or grounding. What may change is memory size and detail. Cache entries should be preserved when they still reduce doubt about future decisions and discarded when they are only clutter. Name used later: cache value. Entropy means remaining uncertainty.

Connection. This is the systems form of reasoning control: compute is allocated where state still matters.

ParetoPO

Problem. Tool use improves accuracy but costs latency, money, and risk.

Object. A non-wasteful tradeoff menu over task success and tool-use cost.

Why it works. The method avoids hiding everything inside one score. What must stay visible is both answer gain and action cost. What may change is the tool-use policy. Name used later: Pareto frontier, meaning the menu where no option can improve one goal without worsening another.

Connection. This is the same frontier logic as safety/fidelity tradeoffs and compression/capability tradeoffs.

OBJECT 03

Tools And Environments

THOR

Problem. Pure text reasoning can hide invalid algebra, search, or computation.

Object. A tool call as a concrete action that returns a concrete result.

Why it works. A calculator, solver, browser, or code runner turns "I think this is right" into an outside observation. The important thing is not that the agent used a tool; it is that the tool gives a smaller place where failure can be seen. What must stay the same is the task claim being checked. What may change is the tool call. Name used later: structured feedback for feedback whose pieces say what failed.

Connection. THOR and RefineStat share the same principle: domain tools make generation repairable because the artifact has named failure modes.

Skill-Pro

Problem. Agents repeatedly rediscover workflows they have already executed.

Object. A saved workflow with a start test, a list of steps, and a stop test.

Why it works. A useful skill is like a recipe that says when it is safe to use and when it is finished. It helps only if the current task still matches the situation where the recipe was learned. What must stay the same is the match between workflow and task state. What may change is the instance. Names used later: activation, execution, and termination for starting, running, and stopping the workflow.

Connection. This is memory as reusable work rather than transcript storage.

MEnvAgent And TerminalTraj

Problem. Software-agent data is weak if the environment cannot be reproduced or checked.

Object. A replayable work session: starting files, command, output, changed files, and checker.

Why it works. Like a lab notebook with timestamps and results, the record shows what the agent saw, what it did, and what changed afterward. What must stay the same is replayable state change. What may change is the command or file state. Name used later: trajectory for this watched path through states and actions.

Connection. This is the agent version of scientific workflows: the benchmark is the stateful lab, not a static prompt.

ADP And AgentFlow

Problem. Agent systems use different actions, memories, tools, and modules, so two failures can look unrelated even when the same loop broke.

Object. A common log format for what was observed, what action was chosen, which module ran, what memory changed, and what outcome followed.

Why it works. Like putting every repair ticket into the same fields, shared logs make failures comparable across browser, code, tool, and research settings. What must stay the same is the work-loop meaning. What may change is environment or module. Name used later: normalized trace schema for that shared log shape.

Connection. This prepares the ground for cross-paper synthesis: different agent benchmarks can be read as different environments over the same loop.

GEPA

Problem. Prompt updates often use only the final score while ignoring where the work session failed.

Object. A search over prompt rules that keeps different useful tradeoffs alive.

Why it works. A failure trace says more than "bad answer." It can show that the tool was called too late, the checker was ignored, or the plan skipped a needed step. What must stay visible is which kind of improvement each rule buys. What may change is the prompt rule. Name used later: Genetic-Pareto search for trying rule variants and keeping ones that improve different goals.

Connection. It links agent learning to selection over attempted fixes and to multi-objective optimization.

OBJECT 04

Verification

CyberGym

Problem. Cybersecurity claims are cheap to state and hard to validate.

Object. A proof-of-concept behavior checked against code before and after a patch.

Why it works. Running the exploit separates a real vulnerability demonstration from a plausible explanation. The patch contrast asks the plain question: does the same attack work before the repair and fail after it? What must stay the same is the attack attempt. What may change is the vulnerable versus repaired code. Name used later: counterfactual for comparing those two nearby worlds.

Connection. This is outcome-level evaluation for code, like robot tasks use physical success and multimodal tasks use visual outcome checks.

VERINA And WZ-LLM

Problem. Mathematical and program claims can sound valid while breaking the rules of the proof or programming language.

Object. Like a password that either passes the lock or does not, the object is a proof or program that a strict checker accepts or rejects.

Why it works. What must stay the same is the language rule for each symbol, step, and dependency. What may change is the wording or search path used to build the artifact. The checker does not reward persuasive wording; it checks whether the artifact obeys the rules. Name used later: formal semantics.

Connection. The verifier changes the learning problem from "write convincing text" to "construct an artifact in a language of proof."

WebDevJudge And Vision2Web

Problem. Web artifacts can match text specs superficially while failing visually or interactively.

Object. The page as users experience it: layout, visible state, clicks, forms, and resulting behavior.

Why it works. A website is not only source code or a written description. The judge must inspect the artifact in the medium where success lives. What must stay the same is user-visible task behavior. What may change is source code structure or implementation route. Name used later: rendered interface for the page after the browser has built what the user sees.

Connection. This is the same evaluator design issue as multimodal grounding: the verifier must see the right world state.

AlgoVeri And Weak-Strong Verification

Problem. A checker helps only if the model can use the failure message to make a better next attempt.

Object. A repair loop: try, receive checker feedback, change the attempt, and try again.

Why it works. Like a compiler error that points to a fixable line, feedback is useful when it points to a change the model can actually make. What must stay the same is progress toward a valid artifact. What may change is the next attempted action. Name used later: policy for the rule that maps the current situation and feedback to the next action.

Connection. Verification is not just a final gate; it is a transition rule in test-time computation.

FRABench, UFEval, And OmniVerifier

Problem. Judges can miss the part of quality that actually matters.

Object. A score broken into the parts the artifact can fail on.

Why it works. Like grading a web app separately for layout, clicks, data, and errors, one number can hide a broken visual detail, failed interaction, wrong file, or task-specific miss. What must stay the same is the quality being claimed. What may change is the score component being inspected. Name used later: structured measurement instrument for a judge that records those pieces instead of only a final preference.

Connection. Agent evaluation inherits benchmark math: scores are readings from an instrument, not the ability itself.

OBJECT 05

Memory And Context

Mamba-3 And MrRoPE

Problem. Long context must preserve usable past information without making every new token compare to every old token at full cost.

Object. A compact memory plus an address system that still knows where old facts sit.

Why it works. Like keeping both notes and page numbers while reading a long book, the model needs a summary of what mattered before and a way to keep before, after, nearby, and far away meaningful. What must stay the same is recoverable past evidence. What may change is memory size or address rule. Names used later: memory state for the kept summary, and positional geometry for the address system over the sequence.

Connection. Long context is not only more tokens. It is remembered evidence plus assumptions about how far-away evidence still relates.

LLMs Get Lost And SCOPE

Problem. Relevant evidence can be present in the prompt while still not be usable by the model.

Object. The step where a needed fact must be found and used.

Why it works. Like having a note somewhere in a messy folder but failing to find it when needed, these diagnostics separate "the fact was included" from "the model recovered it at the moment it mattered." What must stay the same is use of the needed fact. What may change is its location or wrapper. Names used later: retrieval for finding old context, and attention for letting it affect the next decision.

Connection. This is missingness inside context: information that cannot be recovered behaves like information that was never provided.

tau2-bench

Problem. A conversation agent and user can both change the same account, order, ticket, or task state, so dialogue history alone is incomplete.

Object. The shared world state: user actions, agent actions, tool changes, and rules about what is allowed.

Why it works. Like two people editing the same order form, the benchmark forces the agent to track what changed across turns and actors. What must stay the same is the actual account or task state. What may change is user action, agent action, or tool result. Name used later: policy constraints for the rules that say which actions are allowed.

Connection. This is multi-agent state control in a customer-service setting.

DLMR And LatentLM

Problem. Image, video, audio, and text evidence often need to be remembered in different forms.

Object. Separate hidden notes for different evidence channels, with routing that sends each channel to the memory it needs.

Why it works. Like keeping photos, measurements, and conclusions in separate lab folders, a visual detail can be erased if it is forced into the same summary as an abstract plan. What must stay the same is evidence in the form that keeps it usable. What may change is the channel or memory route. Name used later: routed latent memory for hidden memory that keeps different evidence types in usable places.

Connection. This bridges the agents lane with multimodal credit assignment.

OBJECT 06

Multi-Agent Systems

OMAC

Problem. Multi-agent systems often add agents without knowing which division of labor helps.

Object. A team plan: who has which role, who talks to whom, who compares answers, and how the final decision is chosen.

Why it works. A team helps when its structure brings in evidence or decomposition that one call would not have produced. What must stay the same is useful evidence reaching the decision. What may change is role layout or message route. Name used later: architecture for that role-and-message design.

Connection. This is mechanism design for reasoning systems: shaping the rules of interaction so useful evidence reaches the decision.

Rational Agents

Problem. An agent needs to decide which question, search, or tool call is worth paying for.

Object. The expected drop in doubt after seeing a possible answer or observation.

Why it works. Like asking a follow-up question only if the answer could change your decision, a question is useful only if it removes enough doubt to justify the cost. What must stay the same is decision value. What may change is the observation purchased. Names used later: information gain for doubt removed, and posterior for the agent's revised belief after the observation.

Connection. This is the same principle behind adaptive benchmarks and active perception.

Value Of Variance

Problem. Disagreement among agents can be useful evidence or repeated confusion.

Object. How spread out the proposals are after accounting for the same prompt, model family, and evidence.

Why it works. Like getting second opinions from people who noticed different clues, disagreement helps when it reveals different plausible explanations. It hurts when all agents share the same blind spot or merely rephrase the same uncertainty. What must stay the same is useful alternative evidence. What may change is the proposal. Name used later: variance for the amount of spread.

Connection. This gives a first-principles test for multi-agent debate: diversity matters only when it adds information.

MASPOB And LatentMAS

Problem. Several agents often see only part of the situation and must still avoid duplicating or blocking each other's work.

Object. Each agent's local belief, hidden role, messages, and action rule.

Why it works. Like a kitchen team where one person preps and another cooks, a hidden role tells an agent what it is responsible for even when the full team state is not visible. What must stay the same is coordinated progress. What may change is local belief, message, or role. Names used later: latent role for a role inferred from behavior or context, and role-conditioned policy for an action rule that changes by role.

Connection. This links collaboration to equilibrium: a stable joint behavior where each agent's action makes sense given what the others do.

OBJECT 07

Steering And Latent Control

Steer Like The LLM

Problem. A prompt changes behavior partly by changing the model's internal working state, but the useful change may depend on the current context.

Object. An internal adjustment that changes with the current state instead of applying the same shove everywhere.

Why it works. Like adjusting a mixing board differently for each song, the method learns the internal change a prompt would have caused in this situation. What must stay the same is the intended behavior change. What may change is the current internal state. Names used later: activation space for the model's internal numbers, and state-dependent intervention for a change chosen from the current internal state.

Connection. It separates instruction from control, the same way tool agents separate user intent from executable action.

Assistant Axis

Problem. A deployed assistant can drift in persona or instruction-following mode across contexts.

Object. Like a volume slider for speaking style, the method looks for an internal setting where moving it predictably makes the model more or less assistant-like.

Why it works. What must stay the same is the task facts and useful instruction-following. What may change is the hidden setting that controls tone, caution, or assistant mode. If moving that setting changes behavior in the expected way, limiting movement along it can stabilize the interaction without retraining the whole model. Name used later: latent direction.

Connection. This is a safety boundary inside hidden state.

CRV And MINT

Problem. Faulty reasoning or hallucination may come from a specific internal part or from the place where evidence channels are combined.

Object. A targeted internal edit plus a before-and-after output check.

Why it works. Like changing one wire while leaving the machine assembled, changing an internal feature tests whether that feature actually caused the output. What must stay the same is a believable working state. What may change is the targeted internal part. Name used later: causal patch for replacing or changing internal state to test whether the answer changes for the claimed reason.

Connection. This is local cause-finding inside a model.

Learning Unmasking Policies

Problem. Diffusion language models must decide which blank positions to fill first.

Object. A rule for choosing which unknown piece to reveal next.

Why it works. Like filling the easiest crossword clues first because they unlock harder ones, filling one blank changes the clues available for filling the others. What must stay the same is progress toward a coherent sequence. What may change is which blank is revealed next. Names used later: policy for the action rule, and active inference for choosing actions that make future decisions easier.

Connection. This matches agent planning: choose the next action that makes the future decision easier.

OBJECT 08

Infrastructure Risk

SandboxEscapeBench

Problem. Tool-using agents can cross security boundaries that ordinary chat models never touch.

Object. Whether an action path can get from the sandbox to protected host state.

Why it works. Like checking whether a locked room can be entered through any allowed hallway, the benchmark makes the boundary concrete: success for the attacker means reaching evidence that should be unreachable. What must stay the same is the protected boundary. What may change is the sequence of allowed steps. Name used later: reachability for whether some sequence can arrive at a forbidden state.

Connection. Safety becomes infrastructure-state checking, not only refusal classification.

Jailbreak Foundry

Problem. Written jailbreak methods can become reusable attacks when agents operationalize them.

Object. Like turning a recipe into an actual dish others can taste, the object is an attack description converted into runnable steps.

Why it works. What must stay the same is the defense claim being tested. What may change is the implementation route from paper to code. The benchmark is stronger when threat knowledge becomes executable and inspectable, because defenses must survive attacks that run rather than attacks that merely sound plausible. Name used later: paper-to-code attack workflow.

Connection. This is scientific reproducibility applied to adversarial safety.

Trojan-Speak And Covert Channels

Problem. Agents can hide coordination or unsafe intent in channels monitors do not inspect.

Object. How much hidden intent can be carried by allowed-looking communication.

Why it works. Like passing a signal through timing or formatting instead of the words themselves, a monitor must check not only explicit content but what can be encoded and decoded through allowed outputs. What must stay the same is detection of hidden intent. What may change is timing, wording, or format. Name used later: mutual information for how much the visible message reveals about the hidden intent.

Connection. This links safety to information flow: the dangerous variable may be transmitted without appearing as direct harmful text.

MAP And Production Agent Studies

Problem. Deployed agents may be far simpler and more human-gated than benchmark stories assume.

Object. Like observing how a support team really uses an assistant, the object is the actual production record: prompts, short tasks, human checks, tool limits, and points where someone intervenes.

Why it works. What must stay the same is the real deployment setting being claimed. What may change is the benchmark story, autonomy level, or tool path. Measuring production prevents the field from optimizing for agents that are not the ones people actually run. Name used later: deployment workflow state.

Connection. Deployment evidence is a measurement instrument for the field itself.

SYNTHESIS

The Lane In One Mathematical Sentence

Agents and reasoning papers ask how to act when the system cannot see everything, each action can change the situation, and thinking time, memory, tools, checkers, collaborators, and security boundaries are all limited. The successful approaches pick one hidden part of that work loop, explain what it should preserve, and make it visible enough to control.

Trace -> Tool -> Verifier

RAGEN-2 asks whether the reasoning path actually changes with the input. THOR and Skill-Pro turn parts of that path into outside actions or reusable workflows. CyberGym, VERINA, and WebDevJudge check whether the action changed the artifact in the place where failure would show up. Together they form a chain: reasoning is useful when it becomes an action whose effect can be checked.

Compute -> Memory -> Steering

The Tell-Tale Norm asks when extra thinking is worth spending. ThinkV and EntroKV ask which old notes still matter later. Steer Like the LLM asks how to change the model's internal working state without retraining it. Together they treat inference as a budget problem over hidden state.

Agent -> Multi-Agent -> Mechanism

Rational Agents asks which question is worth its cost, OMAC asks which team structure moves useful evidence, and ParetoPO asks when tool use pays for itself. Together they show that agent capability is not "more steps"; it is useful interaction under cost, remaining doubt, and incentives.

FOCUSED CHAIN

Reasoning Collapse, Tool Cost, And Checker Gaming

A deployed agent fails when any part of the process can look successful while losing the task. This chain puts four papers into one loop: the trace must depend on the input, tool calls must be worth their cost, the verifier must observe the right artifact, and process diagnostics must catch low-effort success.

RAGEN-2: The Trace Must Carry Task Information

Plain object. Like checking whether a student's scratch work changes when the math problem changes, the test asks whether the model's middle work is tied to this exact input.

Why it matters. A trace can be long, varied, and familiar-looking while still being nearly the same for many inputs. What must stay the same is dependence on the actual task facts. What may change is wording, length, and route. Name used later: mutual dependence between input and trace.

Remaining failure. Input dependence is necessary but not sufficient. A trace can depend on shallow words or spurious cues, so later verification still has to check consequences.

ParetoPO: A Tool Call Must Buy Information

Plain object. Like choosing between answering from memory, paying for a lookup, or running a full audit, the agent needs a menu where every extra cost buys something visible.

Why it matters. Tool use is not automatically better reasoning. Each external action spends latency, money, risk, and state complexity. What must stay visible is the user-facing answer quality and the real cost paid. What may change is which tool gets called. Name used later: Pareto frontier, meaning the visible menu where no option is clearly wasteful because any improvement has a cost.

Remaining failure. The frontier is only as good as the measured costs. If the benchmark omits security risk, user interruption, hidden tool side effects, or checker cost, the agent can still overuse tools in deployment.

CyberGym: The Claim Must Become Executable

Plain object. Like proving a key works by opening the lock before the repair and failing after the repair, the security claim has to become a run with observable behavior.

Why it matters. Cybersecurity skill is not a persuasive description. What must stay the same is the before-and-after security claim. What may change is the exploit text or patch text. The generated exploit must change real program behavior in the expected direction. Name used later: behavioral certificate.

Remaining failure. Execution checks a defined environment. If the vulnerability needs a different configuration, timing condition, dependency, or deployment topology, the certificate can be too narrow even when it is real.

TRACE Effort: Passing The Verifier Is Not The Same As Doing The Work

Plain object. Like erasing a student's scratch work and seeing whether the grade changes, the test asks whether the checker actually used the process it claims to judge.

Why it matters. If a model still passes when the supposed reasoning is removed, the trace was not the source of success. What must stay the same is the link between evidence and checker decision. What may change is the trace length, detail, or quality. Name used later: verifier sensitivity.

Remaining failure. A process diagnostic can itself become a target. Once models are trained against a diagnostic, the diagnostic must be refreshed or made harder to game.

The Loop

Shared object. A work loop with input, reasoning path, action cost, outside artifact, checker output, and pressure against shortcuts.

First-principles read. The agent is reliable only when all four links hold: the trace changes with the task, tools are chosen because they pay for themselves, the checker observes the right artifact, and the process cannot pass through cheap imitation. Breaking any link creates a system that can look capable while solving a different problem.

input -> trace -> tool action -> artifact -> verifier -> diagnostic; each arrow needs its own evidence
FOCUSED CHAIN

Multi-Agent Mechanisms: Disagreement, Roles, And Incentives

Adding agents is not a mathematical improvement by itself. A group helps only when it changes the information structure of the decision: independent evidence, specialized roles, useful disagreement, or incentives that make truthful costly effort more likely than coordinated imitation.

Value Of Variance: Disagreement Must Be Information, Not Noise

Plain object. Like asking several mechanics for diagnoses after they see the same car, disagreement helps only if it reveals real remaining possibilities, not random guessing.

Why it matters. What must stay fixed is the shared evidence everyone received. What may change is each agent's route through the problem. Disagreement is valuable only when it reveals plausible alternatives the single-agent path would not explore. Name used later: conditional variance.

Remaining failure. Spread can be high because agents are confused in the same way, prompts induce style differences, or all agents share a blind spot. Then debate adds motion without adding evidence.

useful disagreement requires Var(answer | evidence) to track remaining doubt

OMAC: Search The Collaboration Graph

Plain object. Like assigning a planner, checker, researcher, and builder on a project, the useful question is who sees which clue and where their message goes next.

Why it matters. A planner, critic, retriever, executor, and judge do not form a team merely by being separate calls. What must stay intact is the evidence needed at each decision point. What may change is role assignment and message routing. Name used later: collaboration graph.

Remaining failure. The optimized architecture can overfit the benchmark task mix. A role can become ceremonial, a message can erase evidence, or aggregation can reward agreement even when the minority agent found the relevant fact.

team policy = aggregate_i role_i(observation_i, messages_i)

Rational Agents: Ask When Information Value Exceeds Cost

Plain object. Like deciding whether another medical test is worth the time and money, the agent should ask only when the answer could change the final action enough to pay for itself.

Why it matters. A good multi-agent system needs a rule for asking, stopping, and delegating. What must stay fixed is the final decision standard. What may change is which question or action is purchased. Names used later: expected value of information and posterior uncertainty.

Remaining failure. The agent can be wrong about its own uncertainty. Then it may ask low-value questions, stop too early, or pay for evidence that cannot change the final action.

act or ask by comparing E[value after observation] - current value - cost

MASPOB And LatentMAS: Roles Are Hidden State

Plain object. Like a team silently deciding who is the driver, navigator, and lookout, each agent needs a role that fits what it knows and what the group needs.

Why it matters. Coordination becomes easier when agents know what kind of work they are responsible for. What must stay the same is useful local evidence flowing into the team action. What may change is the inferred role and message pattern. Names used later: latent role and role-conditioned policy.

Remaining failure. A wrong hidden role can be worse than no role. Agents may coordinate around an incorrect division of labor, hide uncertainty from each other, or settle into a locally stable but globally bad convention.

policy_i(a_i | belief_i, role_i, messages) couples local evidence to team action

ParetoPO And Accuracy Auctions: Capability Has A Price Surface

Plain object. Like choosing between a quick answer, a paid lookup, and a careful audit, list only choices where saving cost would lose something important.

Why it matters. Multi-agent systems are expensive action rules. What must stay visible is answer quality, tool cost, user value, and risk. What may change is which tool, agent, or pricing rule is used. ParetoPO asks when a tool call is worth paying for; accuracy-auction logic asks how correctness should be weighted when different users value errors differently. Name used later: Pareto frontier, meaning the visible menu where every better capability requires paying with cost, risk, latency, or some other goal.

Remaining failure. If the cost model ignores security risk, user interruption, hidden side effects, or unequal stakes, the frontier can select rules that look efficient while being wrong for deployment.

choose policy on frontier: quality, cost, risk, user value

AdvGame And Mechanism Papers: Other Agents Respond

Plain object. Like setting rules for an online marketplace, define who can act, what each person knows, what they want, and what moves are allowed.

Why it matters. Once agents are deployed, users, attackers, sellers, evaluators, and other agents adapt to the rule. What must stay the same is the claimed outcome under those reactions. What may change is each actor's move after seeing the rules. The method works only when the rule still leads to the claimed behavior after others respond. Name used later: mechanism design.

Remaining failure. A mechanism claim fails when real actors have actions outside the model: collusion, prompt sharing, hidden channels, off-platform incentives, or attacks that change who knows what.

deployed outcome = response path under the mechanism, not isolated optimum

The Mechanism Chain

Shared object. A team decision process where agents hold partial beliefs, choose messages or actions, pay costs, observe each other, and combine into one decision.

First-principles read. Multi-agent reasoning works when the team adds usable evidence faster than it adds shared error and coordination cost. The central question is not "how many agents?" but "what new evidence enters the decision, who sees it, who can challenge it, and what incentive makes the challenge honest?"

private evidence -> role graph -> messages -> aggregation -> action; value requires new information minus coordination cost
