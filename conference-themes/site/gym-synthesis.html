FIRST PRINCIPLE

A gym is a world with a contract

A normal benchmark asks for an answer. A gym asks for behavior inside a world. The agent observes a state, chooses actions from a constrained interface, receives new observations, and eventually succeeds or fails under a verifier. That means the benchmark is not only the task prompt. It is the whole contract between world, agent, tools, trace, and scoring rule.

The conference themes make this clear from several directions. Agent papers care about tool loops and process collapse. Security papers care about executable proof and sandbox boundaries. Evaluation papers care about verifiers, environment variation, and tail failures. Robotics papers care about state, action, dynamics, and control. Causality and scientific-discovery papers care about whether the agent chooses the right intervention, not merely whether it writes a plausible explanation. A serious gym has to encode those same objects explicitly.

CONTRACT

What Every Useful Gym Must Contain

Task

The task is the goal stated in domain terms, not just a question. It should say what must be changed, found, repaired, exploited, diagnosed, planned, or proven.

Examples: fix a failing test, exploit a patched vulnerability, complete a web workflow, recover a root cause, generate a feasible robot plan.

World State

The world state is what changes as the agent acts. It can be a browser DOM, repository checkout, container filesystem, simulator state, graph, medical table, or robot scene.

Design rule: the state must be inspectable enough to debug and constrained enough that success cannot be faked by text.

Observations

Observations are the partial view given to the agent. They decide what the agent can know at each step and whether the task tests perception, memory, reasoning, or tool use.

Failure mode: if observations leak the answer, the gym becomes a reading-comprehension test.

Actions and Tools

Actions are the allowed moves. Tools are the interfaces for those moves: browser clicks, shell commands, API calls, patches, scans, probes, planners, or simulator controls.

Design rule: log every action with arguments, result, and state transition.

Verifier

The verifier is the authority that decides success. The strongest verifiers execute something: tests pass, exploit works, UI state changes, simulator reaches target, or root-cause ranking matches ground truth.

Priority: deterministic verifiers first; LLM judges only where the target is inherently semantic.

Trace

The trace is the record of what happened, not decoration. It is how we classify failure, replay behavior, compare agents, and separate lucky final answers from reliable process.

Minimum: prompt, observations, actions, tool outputs, intermediate artifacts, verifier result, timing, cost, and environment version.

Failure Taxonomy

A gym should produce categories, not just scores. Did the agent misunderstand the goal, choose the wrong tool, loop, hallucinate state, corrupt files, stop early, or fail the verifier?

Use: failure categories make benchmark results actionable for model and agent-system improvement.
NORMALIZATION

What Agent Data Protocol Is For

The reason to normalize through an agent data protocol is simple: every external gym invents its own names for the same objects. One calls it an observation, another calls it state. One logs a command, another logs an action. One has a reward, another has a verifier. One stores screenshots, another stores DOM snapshots, another stores container diffs. Without normalization, every analysis script becomes gym-specific glue.

LANES

The Four Gym Lanes We Should Build Toward

Browser and UI Gyms

The agent sees a visual/DOM state, takes UI actions, and must complete a user workflow. The verifier checks final app state, not whether the agent described the right clicks.

Conference anchors: OpenApps, MomaGraph, Camera-Aware MLLM, OmniVerifier, environment-variation evaluation.

Security Gyms

The agent works inside a sandbox, inspects code or infrastructure, and produces an executable exploit, patch, or diagnostic. The verifier runs the exploit or checks the before/after security condition.

Conference anchors: CyberGym, SandboxEscapeBench, Trojan-Speak, Invisible Safety Threat, agent infrastructure risk.

Code and Developer Gyms

The agent receives a repository state and an edit or debugging goal. It can inspect, patch, run tests, and iterate. The verifier is the test suite plus any targeted behavioral assertion.

Conference anchors: EditBench, program synthesis and verification, developer reliability, statistical code synthesis.

Robotics and Scientific Gyms

The agent acts in a simulator, graph, causal system, physical model, or scientific data workspace. It must choose interventions, plans, or computations that satisfy domain constraints.

Conference anchors: differentiable MPC, HDFlow, BRCD, MedAgentGym, scientific discovery, time-series and dynamical systems.
VERIFIERS

Verifier Hierarchy

The production-readiness question is mostly a verifier question. If success is vague, the gym becomes a prompt-evaluation dataset. If success is executable, the gym becomes a behavioral benchmark.

LevelVerifier typeUse whenRisk
1Deterministic state checkThe final condition is exact: file changed, UI flag set, simulator state reached, exploit result observed.Can be too narrow if it misses alternate valid solutions.
2Executable testThe task is code, security, data analysis, or workflow behavior that can be run.Tests may be incomplete or overfit by the agent.
3Reference-backed semantic checkThe output must match a known diagnosis, plan, or explanation with structured evidence.Needs careful rubrics and evidence fields.
4LLM judgeThe target is inherently semantic and no deterministic verifier captures it.Judge drift, prompt sensitivity, and false confidence.
FAILURES

Failure Categories the Trace Should Produce

Goal Misread

The agent optimizes the wrong target, solves a nearby task, or treats constraints as optional.

State Hallucination

The agent claims a UI element, file, vulnerability, or robot state exists when the observation does not support it.

Tool Misuse

The right tool exists, but the agent calls it with wrong arguments, wrong order, or no check of the result.

Verifier Blindness

The agent never runs the verifier, misreads the verifier, or stops after a partial signal.

Looping

The trace repeats actions or observations without new information or narrowing the search space.

Unsafe Shortcut

The agent modifies the benchmark, weakens tests, corrupts state, escapes a sandbox, or hides failure instead of solving the task.

NEXT BUILD

The Meaty End-to-End Goal

The next useful milestone is not another survey page. It is an end-to-end gym conversion lane: take one external gym family, normalize its tasks/actions/observations/verifiers/traces into our format, run a small agent suite, classify failures, and publish a benchmark report that proves the adapter is not just a schema exercise.

Pick the first lane

Browser/security/code are the strongest first candidates because they have executable verifiers and rich traces. Browser gyms test UI grounding; security gyms test sandboxed executable proof; code gyms test repository modification and tests.

Convert, do not summarize

For each task, preserve the raw environment object and produce normalized task, observation, action, verifier, trace, outcome, and failure-category records.

Run agents through it

Use the same small agent set across tasks so the report can compare behavior, not just catalog gym formats.

Publish the evidence

The output should include task cards, verifier results, trace excerpts, failure counts, and examples where the normalized schema revealed a cross-gym pattern.
